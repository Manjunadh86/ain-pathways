Capstone project

Research Agent with Your Own MCP Server

Build a research agent by hand, rebuild it in a framework, and give it tools through an MCP server you wrote.

IntermediateAbout 32 hours (estimate)

The brief

Build an agent that takes a research question (for example "compare three open-source vector databases for a small team"), plans the work, searches and reads sources, keeps notes, and writes a short report with citations that a person approves before it is saved.

You build the agent twice. First by hand, with nothing but a model API, so that you understand every step of the loop. Then in one framework of your choice, so that you can say exactly what the framework bought you and what it cost. The tools live in an MCP server that you write, so any MCP-capable client can use them.

What you build

  • A hand-written agent loop with tool calling, step limits and error recovery.
  • An MCP server exposing search, fetch and note-taking tools, tested with a second client.
  • The same agent rebuilt in one framework, with a written comparison.
  • A workflow that splits research across workers and reviews the draft before a human approves it.
  • A short design note explaining which parts are fixed workflow and which are agentic, and why.

Milestones

  1. 1

    Design note and hand-built loop

    Decide the shape of the system on paper, then implement the loop yourself with two or three plain function tools. Log every model request and tool result so you can read a full run.

    Deliverables

    • The design note separating workflow steps from agentic steps.
    • A working loop with a step limit and a readable run log.
    • Tool definitions with descriptions and error messages reviewed against a failed run.

    Covers R1, R2, R3

  2. 2

    Move the tools into an MCP server

    Turn the tools into an MCP server and make the agent an MCP client. Prove the server is reusable by connecting a second, unrelated client to it.

    Deliverables

    • An MCP server exposing the tools, passing a check in the MCP Inspector.
    • The agent calling the tools through MCP over stdio and over HTTP.
    • A note on the authorization a remote deployment would require.

    Covers R4, R5

  3. 3

    Planning, memory and collaboration

    Add the plan, external notes with compaction, the orchestrator with parallel workers and the evaluator loop. Add one piece at a time and rerun the same three research questions after each.

    Deliverables

    • Runs showing a plan, a replan after a failed step and notes that survive compaction.
    • A report produced by parallel workers and revised after evaluator feedback.

    Covers R6, R7, R8

  4. 4

    Approval, safety and the framework rebuild

    Add the approval gate and the safety checks, then rebuild in a framework and write the comparison.

    Deliverables

    • A run that pauses for approval and resumes from saved state.
    • A demonstration that a planted instruction in a fetched page is ignored.
    • The framework version and a comparison table against the hand-built version.

    Covers R9, R11, R10

Acceptance criteria

The project is done when every statement below is true.

  • The hand-built agent answers three different research questions within its step limit and cites a source for every claim in the report.
  • A tool failure produces a recovery step, not a crash or a silent wrong answer.
  • The MCP server works unchanged with two different clients.
  • The same tools work over stdio and over Streamable HTTP.
  • The agent stops for approval before saving and resumes correctly after approval and after a change request.
  • The evaluator loop ends after at most two revisions.
  • A planted instruction in a fetched page does not change the agent's behaviour in five consecutive runs.
  • The comparison names at least two things the framework made easier and two it made harder, each with evidence from your code.

Stretch goals

  • Package one capability as an Agent Skill and show it being loaded only when needed.
  • Expose the agent to another agent over A2A, or stream its progress to a small UI with AG-UI.
  • Publish your MCP server's metadata in the format the MCP Registry expects.
