Capstone project

Ship and Operate a Support Agent

Take a working support agent to a state where you would let real customers use it, and show the evidence.

AdvancedAbout 34 hours (estimate)

The brief

Start from a simple support agent: it answers questions from a small knowledge base and can look up an order and issue a refund through two mock APIs. It works on your laptop. Your job is everything that comes after that.

The scenario and the APIs are hypothetical and you can mock them. The deliverable is an operating agent plus a launch review document in which every claim (quality, safety, cost, reliability) links to a trace, an evaluation run or a test.

What you build

  • A deployed agent with session isolation, durable state and a documented architecture.
  • Tracing in one observability tool, with a second tool compared on the same traces.
  • An evaluation suite for final answers and for tool-use trajectories, running in CI.
  • Guardrails, scoped permissions and human approval for refunds, tested by a red-team exercise.
  • A launch review with cost per conversation, failure modes found and the decision you would make.

Milestones

  1. 1

    Architecture, durability and deployment

    Write the architecture down, make state durable, then deploy. Test durability by killing the process in the middle of a refund flow.

    Deliverables

    • An architecture document with a diagram of sessions, state and credentials.
    • A recorded test in which a restart in mid-flow neither loses the conversation nor repeats the refund.
    • A reachable deployment and a short decision record for the chosen target.

    Covers R1, R2, R3

  2. 2

    Observe

    Instrument the agent and read real traces before building evaluations. Find at least three failure patterns by reading traces; they become evaluation cases in the next milestone.

    Deliverables

    • Traces for at least 30 runs with cost and latency.
    • A comparison of two observability tools on the same runs.
    • Three failure patterns found by reading traces.

    Covers R4

  3. 3

    Evaluate and test

    Build the evaluation set, including the failure patterns you found, score answers and trajectories, and wire the suite into CI.

    Deliverables

    • The evaluation set stored as data, with reference trajectories for tool-using cases.
    • Final-answer and trajectory scores for the current agent.
    • A CI run that fails when a deliberately broken prompt is committed.

    Covers R5, R6, R7

  4. 4

    Harden, optimise and review

    Add guardrails and permissions, red-team the result, set the cost and reliability controls, and write the launch review.

    Deliverables

    • A red-team log with findings, severities and the regression test added for each confirmed finding.
    • Measured cost per conversation and latency before and after one optimisation.
    • A launch review in which every claim links to a trace, an evaluation run or a test.

    Covers R8, R9, R10, R11

Acceptance criteria

The project is done when every statement below is true.

  • A restart during a refund flow never produces a duplicate refund or a lost conversation.
  • Two concurrent users cannot see each other's orders or conversation state.
  • Every run is traceable from the user message to each model and tool call, with cost.
  • The trajectory evaluation fails any run that issues a refund without recorded approval.
  • The CI suite fails on a deliberately degraded prompt and passes on the current one.
  • An instruction planted in a knowledge-base article is not followed in ten consecutive runs.
  • The agent cannot read another user's order even when asked directly, and each refused attempt is in the audit log.
  • Every confirmed red-team finding has a regression test.
  • The launch review states measured cost per conversation, the known failure modes and a clear go or no-go decision.

Stretch goals

  • Deploy the same agent to a second platform and compare operating effort and cost.
  • Add online evaluation that samples production traces into a review queue.
  • Run a chaos test in which the model provider returns errors and timeouts, and show graceful degradation.
