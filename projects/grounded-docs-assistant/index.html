Capstone project

Grounded Documentation Assistant

Build a question-answering assistant over a real documentation set that cites its sources and proves its quality with evals.

IntermediateAbout 28 hours (estimate)

The brief

Pick the public documentation of an open-source project you use (any project with a few hundred pages is enough). Build an assistant that answers questions about it, quotes the passages it relied on, and says so when the documentation does not contain the answer.

The assistant itself is the smaller half of the work. The larger half is showing, with an evaluation set and traces, that it answers correctly, refuses when it should, resists injected instructions and stays inside a cost budget.

What you build

  • An ingestion pipeline that parses, chunks, embeds and indexes the documentation.
  • A retrieval-augmented answering service with citations and a streamed response.
  • An evaluation suite with deterministic checks and a calibrated LLM judge.
  • Guardrails against prompt injection carried in documents and against out-of-scope questions.
  • Tracing with cost and latency per request, and a written optimisation that you measured.

Milestones

  1. 1

    Choose models and build the index

    Decide on the models, then ingest the documentation. Inspect twenty random chunks by hand before going further; most retrieval problems are visible at this stage.

    Deliverables

    • A short model decision record.
    • An index of the documentation with metadata on every chunk.
    • Notes from the manual chunk inspection and any chunking changes it caused.

    Covers R1, R2

  2. 2

    Retrieve and answer with citations

    Get an end-to-end answer working, then add the tool. Keep the first version simple so that the evaluation in the next milestone has a baseline to beat.

    Deliverables

    • A service that returns a streamed answer with cited passages.
    • A refusal path for questions the documentation cannot answer.
    • One working tool with a trace showing its use.

    Covers R4, R7, R3

  3. 3

    Evaluate before you improve

    Build the evaluation set and judge, record the baseline, and only then improve retrieval. Report retrieval metrics and generation metrics separately so you know which half a change affected.

    Deliverables

    • The evaluation set, stored as data in the repository.
    • A judge prompt with its measured agreement against your labels.
    • A before and after table for the retrieval improvement.

    Covers R5, R6, R11

  4. 4

    Harden, trace and optimise

    Add the security checks and tracing, then make one optimisation and measure it against the evaluation set.

    Deliverables

    • A demonstration that a planted instruction in a document is not obeyed.
    • Traces showing cost and latency per request.
    • A measured optimisation with its effect on quality.

    Covers R8, R9, R10

Acceptance criteria

The project is done when every statement below is true.

  • Every answer lists the passages it used, and each cited passage really contains the supporting text.
  • At least 80 percent of the unanswerable questions in the evaluation set are declined instead of answered.
  • Retrieval and generation metrics are reported separately, before and after each change.
  • The judge's agreement with human labels is reported with the sample size.
  • The planted injection is not followed in ten consecutive runs.
  • Cost per request and latency are visible in traces for every request.
  • The optimisation's effect on cost, latency and eval scores is reported as measured numbers.
  • Rerunning the evaluation suite takes one documented command.

Stretch goals

  • Compare the hosted model with an open-weight model you run yourself on the same evaluation set.
  • Add image understanding for diagrams and screenshots in the documentation.
  • Fine-tune a small model on your evaluation failures and report whether it helped.
