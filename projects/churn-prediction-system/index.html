Capstone project

Customer Churn Prediction System

Take a tabular dataset from raw file to a monitored prediction service, and justify every decision on the way.

IntermediateAbout 30 hours (estimate)

The brief

A subscription business wants to know which customers are likely to cancel next month so that its retention team can call them first. You are given a customer table and a month of usage logs. Your job is to build the whole system a small ML team would own, and not just a model in a notebook.

Use any public churn dataset (for example a telecom churn dataset from an open data repository) or generate a synthetic one, and state which you chose. The scenario is hypothetical. The practices are the ones the lessons in this path teach.

The project is graded on reasoning as much as on the score. A reviewer should be able to read your repository and see why each cleaning step, feature, metric and threshold was chosen.

What you build

  • A data preparation pipeline that turns the raw files into a clean, documented training table.
  • At least three candidate models compared fairly with cross-validation.
  • A tuned final model with an explanation of what drives its predictions.
  • A prediction service packaged in a container, with a tracked model version behind it.
  • A monitoring report that would tell the team when the model needs retraining.

Requirements and the lessons they practise

#RequirementLessons practised
R1Load the raw data, document its quality problems (missing values, duplicates, inconsistent types, outliers) and fix each one with a stated reason.
  • Data Collection and Cleaning
  • The Python Data Stack (NumPy, pandas, scikit-learn)
R2Produce an exploratory analysis that shows the churn rate, the distributions of the main features and at least three relationships worth modelling.
  • Exploratory Data Analysis
  • Statistics for ML
R3Engineer features inside a single preprocessing pipeline (encoding, scaling, at least two derived features) so the same steps run at training and prediction time.
  • Feature Engineering and Scaling
R4Split the data so that no information from the evaluation period leaks into training, and explain why your split is leak-free.
  • Train/Test Splits and Cross-Validation
R5Train a logistic regression baseline, a random forest and a gradient boosting model, and compare them with the same cross-validation folds.
  • Logistic Regression
  • Random Forests and Bagging
  • Gradient Boosting (XGBoost, LightGBM)
  • Bias, Variance and Overfitting
R6Choose the evaluation metric and decision threshold from the cost of a missed churner versus a wasted retention call, and handle the class imbalance explicitly.
  • Classification Metrics
  • Handling Imbalanced Data
R7Tune the best model with a documented search and report the gain over its default settings on held-out data.
  • Hyperparameter Tuning and Model Selection
  • Regularization (Ridge, Lasso, Elastic Net)
R8Explain the final model globally and for three individual customers, and check its error rates across at least one customer segment.
  • Explainable AI (SHAP, LIME, Feature Importance)
  • Fairness and Bias in ML
R9Log every training run (parameters, metrics, artifacts) and register the chosen model version.
  • Experiment Tracking and Model Registries
  • ML Pipelines, Feature Stores and Continuous Training
R10Serve predictions from a containerised HTTP endpoint that accepts one customer record and returns a churn probability and the model version.
  • Model Deployment and Serving
  • Docker and Containers
  • REST APIs and System Integration
R11Simulate a later month with shifted inputs and produce a monitoring report that detects the drift and recommends an action.
  • Model Monitoring and Drift
  • A/B Testing and Online Experiments

Milestones

  1. 1

    Understand and prepare the data

    Get the data clean and understood before any modelling. Write down each data quality decision in a short data log. Finish with a reproducible script or notebook that produces the training table from the raw files.

    Deliverables

    • A data log listing every quality problem found and how it was handled.
    • An exploratory report with charts and three modelling hypotheses.
    • A preprocessing pipeline object that can be fitted on training data only.

    Covers R1, R2, R3, R4

  2. 2

    Model, evaluate and tune

    Compare the candidate models fairly, pick the metric and threshold from the business costs, then tune the winner. Keep the held-out test set untouched until the very end.

    Deliverables

    • A comparison table of the three models with cross-validated scores and their spread.
    • A one-page metric and threshold decision with the cost assumptions written out.
    • The tuned model and its final test-set results.

    Covers R5, R6, R7

  3. 3

    Explain the model and track the work

    Make the result trustworthy and repeatable. Someone else should be able to rerun any experiment and see why the model predicts what it does.

    Deliverables

    • Global feature attributions and three individual explanations written for a non-technical reader.
    • Error rates for at least two customer segments, with a comment on any gap.
    • An experiment tracking store containing every run and one registered model version.

    Covers R8, R9

  4. 4

    Serve and monitor

    Put the registered model behind an endpoint and show how the team would notice when it stops working.

    Deliverables

    • A container image that serves predictions over HTTP, with a documented request and response.
    • A drift report on simulated later data, with the retraining trigger you would use.

    Covers R10, R11

Acceptance criteria

The project is done when every statement below is true.

  • Running one documented command rebuilds the training table and the final model from the raw data.
  • The test set is used exactly once, and the write-up says where.
  • The chosen metric and threshold are derived from stated costs, not from convention.
  • All preprocessing is fitted on training data only; a reviewer cannot find a leak.
  • The comparison uses identical folds for every model and reports variation across folds.
  • The endpoint returns a probability and a model version for a valid record, and a clear error for an invalid one.
  • The monitoring report flags the simulated drift and does not flag an unshifted control sample.
  • Every decision in the data log and the metric decision has a reason a teammate could disagree with.

Stretch goals

  • Calibrate the predicted probabilities and show a reliability curve before and after.
  • Add a scheduled pipeline that retrains when the drift trigger fires.
  • Design the A/B test that would measure whether calling predicted churners reduces churn.
