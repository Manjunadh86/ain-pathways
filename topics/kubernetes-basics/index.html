Kubernetes Basics

Kubernetes is an open source system that runs containers across a group of machines. You describe what should be running in objects such as Pods, Deployments, Services, ConfigMaps and Secrets, and its controllers keep changing the cluster until what is running matches that description.

1Overview

Why it matters

One container on one machine is a single docker run command. Twenty services on thirty machines that have to survive a crashed process, a dead machine and a deploy in the middle of a busy day are a coordination problem. Kubernetes is a common answer to that problem, and you will meet it in customer environments: when a customer says "we will give you a namespace", your work has to arrive as Deployments, Services, ConfigMaps and Secrets.

Most day-to-day Kubernetes trouble comes from a handful of basics. A Pod stuck in Pending usually has a resource request that no node can fit. A container that keeps restarting with reason OOMKilled and exit code 137 has gone over its memory limit. A Service that refuses or drops connections usually selects no Pods or points at the wrong port. A password stored in a ConfigMap, or a Secret that someone assumed was encrypted, is a security finding. Knowing the model also tells you when to leave it alone: for one small application, a cluster can cost more to run than it gives back.

  • Judge when Kubernetes is unnecessary and name the simpler alternative.

Key terms

Cluster
A set of machines that one Kubernetes control plane manages together as a single place to run containers.
Control plane
The components that store and manage cluster state, namely the API server, the etcd data store, the scheduler and the controller manager. Clusters that integrate with a cloud provider add an optional cloud controller manager.
Node
A worker machine, physical or virtual, that runs Pods. An agent on it called the kubelet starts and watches the containers.
Pod
The smallest unit Kubernetes deploys. It holds one or more containers that always run on the same node and share one IP address.
Deployment
An object that says how many copies of a Pod should run and from which template, and that replaces them gradually when the template changes.
ReplicaSet
The object a Deployment creates to keep a fixed number of identical Pods running. You rarely create one yourself.
Service
A stable IP address and DNS name that forwards traffic to whichever Pods currently carry a given set of labels.
Label and selector
A label is a key-value tag on an object, such as app=web. A selector is a query for objects with certain labels, and it is how Deployments and Services find their Pods.
Controller
A loop that watches the cluster, compares what exists with what an object's spec asks for, and makes changes to bring the two together.
Request and limit
A request is the CPU or memory a container asks the scheduler to set aside. A limit is the most the kernel will let it use.

2Explanation

Introduction

In Docker and Containers you packaged an application into an image and started it with one command on one machine. That is enough until the questions change. What restarts the container when it crashes at night? What happens when the whole machine fails? How do you run five copies, send traffic to all of them and replace them with a new version without dropping requests? How does another service find them when their addresses keep changing?

You could answer each question with a script. Kubernetes answers all of them with one idea, the one a thermostat uses. You do not tell a thermostat to run the heater for ten minutes. You set a temperature, and it keeps comparing the room with the setting and switches equipment on or off. The Kubernetes documentation uses the same analogy (opens in a new tab): the setting is the desired state, the room is the current state, and the loop that closes the gap is a controller.

In Kubernetes the settings are objects that you send to the cluster's API, usually written as YAML files called manifests. This lesson covers the five you will use first:

  • Pod: one or more containers that run together on one machine and share an IP address.
  • Deployment: keep N copies of this Pod running, and roll out changes gradually.
  • Service: a stable name and address in front of a changing set of Pods.
  • ConfigMap and Secret: configuration and credentials kept outside the image.

After the objects, the lesson explains how requests and limits tell the cluster how much CPU and memory a container needs and may use, then walks through a complete example on a free local cluster. It ends with a question beginners are rarely asked: whether you need Kubernetes at all. Commands and behaviour follow the documentation for Kubernetes v1.37, the current release in October 2026. The objects covered here have been stable parts of the API for years.

How it works

A cluster is a control plane plus nodes

A cluster (opens in a new tab) has two kinds of machine. The control plane stores and manages the cluster's state:

  • kube-apiserver exposes the Kubernetes HTTP API. Every read and write goes through it, including yours, because kubectl is an API client.
  • etcd is the key-value store that holds all API data.
  • kube-scheduler finds Pods that have no node yet and assigns each one to a suitable node.
  • kube-controller-manager runs the built-in controllers.
  • cloud-controller-manager is optional. It connects the cluster to a cloud provider's API.

Each worker node runs a kubelet, the agent that makes sure the containers of the Pods assigned to that node are running. It also runs a container runtime and usually kube-proxy, which maintains the network rules behind Services. On a managed service such as GKE or EKS, the provider runs the control plane for you.

Objects and the reconciliation loop

Most objects you create carry a spec, the desired state you wrote. A controller (opens in a new tab) is a loop that never ends:

python
# pseudocode: the shape of every controller
while True:
    desired = read_spec_from_api_server()
    current = observe_cluster()
    if current != desired:
        make_a_change_toward_desired()

Three properties follow from this shape.

  • The cause of a gap does not matter. A crashed container, a failed node, a Pod you deleted by hand and a replica count you raised all look the same to the loop: current differs from desired.
  • You change things by editing desired state. Delete a Pod that a Deployment owns and a replacement appears, because the spec still says three. To stop the application, change or delete the Deployment.
  • Controllers are small and chained. A controller rarely does the final work itself. For a Deployment, the Deployment controller creates a ReplicaSet, the ReplicaSet controller creates Pods, the scheduler assigns each Pod to a node, and that node's kubelet starts the containers. Each step only reads and writes objects through the API server.

The documentation adds that a cluster may never settle into a perfectly stable state, and that this is acceptable as long as the controllers keep running and making useful changes.

Pods

A Pod (opens in a new tab) is the smallest unit you can deploy: one or more containers that are always placed on the same node and share network and storage. A Pod gets its own IP address (one per IP family), shared by all its containers, which reach each other on localhost. Most Pods hold one application container, sometimes with a helper beside it.

Pods are disposable. A Pod stays on its node until it finishes, is deleted, is evicted for lack of resources, or the node fails. Kubernetes does not move it to another node. When a controller replaces a lost Pod, the replacement is a new Pod with a new name and, in practice, a new IP address. That is why you rarely create Pods directly, and why nothing you want to keep should live only in a Pod's filesystem.

Deployments

A Deployment (opens in a new tab) holds a Pod template, a replica count and a label selector. It creates a ReplicaSet, and the ReplicaSet keeps that many Pods from the template running.

Changing the template, for example the image tag, triggers a rollout: the Deployment creates a new ReplicaSet and scales it up while scaling the old one down. Changing only the replica count does not. Two settings pace the rollout, and both default to 25%: maxSurge is how many Pods may exist above the replica count (rounded up), and maxUnavailable is how many may be missing (rounded down). With 3 replicas that gives ⌈0.75⌉=1\lceil 0.75 \rceil = 1⌈0.75⌉=1 and ⌊0.75⌋=0\lfloor 0.75 \rfloor = 0⌊0.75⌋=0, so a rollout never has fewer than 3 available Pods or more than 4 in total.

Old ReplicaSets are kept, 10 by default, which is what lets kubectl rollout undo return to the previous template. Deployments suit applications that keep no state in the Pod. Workloads that need a stable identity or their own storage use other controllers, such as StatefulSets.

Services

Because Pods come and go, their IP addresses are no use to clients. A Service (opens in a new tab) gives a set of Pods one stable virtual IP address and DNS name. The set is defined by a label selector: the Service's controller keeps scanning for Pods whose labels match and records their addresses in EndpointSlice objects. Traffic goes only to endpoints that are ready, so a Pod that is not yet ready is left out. Nothing links a Service to a Deployment except matching labels.

Inside the cluster, a Service named web in namespace shop resolves as web from the same namespace and as web.shop from other namespaces. In the manifest, port is what clients connect to and targetPort is the container port that receives the traffic. Routing HTTP host names and paths from outside is done by separate objects, Ingress or the Gateway API, that sit in front of Services. Networking Essentials covers the DNS, TLS and proxy ideas they build on.

ConfigMaps and Secrets

A ConfigMap (opens in a new tab) stores non-confidential settings as key-value pairs, up to 1 MiB. A Pod in the same namespace can receive them as environment variables, as command arguments or as files in a mounted volume. The delivery method decides what happens when the ConfigMap changes: mounted files are updated after a delay, environment variables stay as they were until the Pod is restarted, and files mounted with subPath are not updated.

A Secret (opens in a new tab) has the same shape and is meant for passwords, tokens and keys. Be precise about what it protects. Values in its data field are base64-encoded, which is an encoding and not encryption. (The stringData field used in the worked example is a convenience that accepts plain text and stores it encoded in data.) By default Secrets are stored unencrypted in etcd, and anyone allowed to create a Pod in a namespace can read every Secret in it. The documentation's remedies are encryption at rest, least-privilege access rules and, optionally, an external secret store. What you do get by default is narrower: a Secret is sent only to nodes that run a Pod using it, and when it is mounted into a Pod the kubelet keeps its copy in memory-backed storage (tmpfs) instead of writing it to durable storage.

Requests and limits

Each container can declare two numbers for each resource (opens in a new tab). CPU is measured in cores, so 250m (250 millicores) is a quarter of a core. Memory is measured in bytes with suffixes such as Mi and Gi.

  • A request is for the scheduler. A Pod is placed only on a node where the requests of the Pods already there, plus its own, fit within what the node can offer. Actual usage is ignored, so a nearly idle node can still be full.
  • A limit is enforced by the Linux kernel on the node.

The two resources fail differently. A container at its CPU limit is throttled and runs slower. A container over its memory limit can be killed by the kernel, and Kubernetes then reports OOMKilled with exit code 137 and restarts it. If you set a limit but no request, and nothing else supplies a default request, the request is set equal to the limit.

Requests and limits also decide a Pod's quality-of-service class (opens in a new tab). It is Guaranteed when every container has CPU and memory requests that equal its limits, BestEffort when no container sets any, and Burstable otherwise. When a node runs short of resources, BestEffort Pods are evicted first and Guaranteed Pods last.

What Kubernetes leaves to you

The project overview (opens in a new tab) is explicit about what Kubernetes is not. It does not build your application or deploy source code. It has no built-in database, message queue or cache. It does not choose a logging, monitoring or alerting system for you. A working platform is therefore a cluster plus everything you add and maintain around it: an image build pipeline (see CI/CD Pipelines), a way to route outside traffic in, certificate handling, metrics and logs, access rules and regular upgrades. Count that work when you decide whether a cluster is worth having.

Worked example: Three web server replicas on a local kind cluster, configured, exposed, broken and updated

This example runs on a laptop for free. You need Docker (or Podman), kubectl and kind (opens in a new tab), a tool that runs the nodes of a Kubernetes cluster as containers. Create a one-node cluster with kind create cluster, then save the following as web.yaml. It declares four objects separated by ---.

yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: web-content
data:
  index.html: |
    Hello from a ConfigMap
---
apiVersion: v1
kind: Secret
metadata:
  name: web-secret
type: Opaque
stringData:
  API_TOKEN: demo-token-123
---
apiVersion: apps/v1
kind: Deployment
metadata:
  name: web
spec:
  replicas: 3
  selector:
    matchLabels:
      app: web
  template:
    metadata:
      labels:
        app: web
    spec:
      containers:
        - name: nginx
          image: nginx:1.30
          ports:
            - containerPort: 80
          env:
            - name: API_TOKEN
              valueFrom:
                secretKeyRef:
                  name: web-secret
                  key: API_TOKEN
          resources:
            requests:
              cpu: 100m
              memory: 64Mi
            limits:
              cpu: 250m
              memory: 128Mi
          volumeMounts:
            - name: content
              mountPath: /usr/share/nginx/html
      volumes:
        - name: content
          configMap:
            name: web-content
---
apiVersion: v1
kind: Service
metadata:
  name: web
spec:
  selector:
    app: web
  ports:
    - port: 80
      targetPort: 80

kubectl apply -f web.yaml

The page came from the ConfigMap, mounted as a file. The token came from the Secret, injected as an environment variable. The third line is the Secret as the API stores it. Pipe it through base64 -d and demo-token-123 comes back, which shows that the value is encoded and not encrypted. Stop the port-forward with Ctrl+C before the next step. It is attached to one Pod and ends when that Pod goes away.

Step 3. Break it and watch the reconciliation. Delete one Pod, using a name from your own list, and list the Pods again:

bash
kubectl delete pod web-6c9f8b7d5c-4kzqp
kubectl get pods -l app=web

There are three Pods again, and one is a few seconds old. Nobody restarted anything. The ReplicaSet controller saw two Pods where the spec asks for three and created one.

Step 4. Check the resource arithmetic. Run kubectl get pod web-6c9f8b7d5c-9xw2t -o jsonpath='{.status.qosClass}' with one of your Pod names. It prints Burstable, because requests are set and are lower than the limits. Then run kubectl describe node kind-control-plane and find the table of non-terminated Pods. Each web Pod is listed with a CPU request of 100m, a CPU limit of 250m, a memory request of 64Mi and a memory limit of 128Mi.

rollout status prints progress lines while the Pods are replaced, so your output may be longer. The template changed, so the Deployment created a second ReplicaSet and moved the Pods across one at a time, never dropping below 3 available Pods or going above 4, as the rollout plot earlier shows. The old ReplicaSet stays at zero replicas so that kubectl rollout undo deployment/web can scale it back up.

Clean up with kind delete cluster. Notice what you did not do in any step: you never started or stopped a container yourself. You changed the desired state three times (apply, delete, set image) and controllers did the rest.

Edge cases and limitations

A ConfigMap change reaches some Pods and not others
How a Pod consumes a ConfigMap decides whether it sees an update. The documentation states that keys projected into a mounted volume are updated eventually, after a delay of up to the kubelet sync period plus a cache delay, that values consumed as environment variables are not updated and need a Pod restart, and that a subPath mount does not receive updates. After changing a ConfigMap that feeds environment variables, run kubectl rollout restart on the Deployment. An application that reads a mounted file only at startup needs the same restart.
A nearly idle node refuses a new Pod
The scheduler compares requests with node capacity and ignores live usage. The documentation notes that it refuses to place a Pod when the capacity check fails even if actual CPU or memory use on the node is very low, to protect against a shortage when usage rises later. The Pod stays Pending with a FailedScheduling event that names the insufficient resource. Lower inflated requests, add a node, or remove Pods that are no longer needed.
A memory limit is enforced after the fact
A CPU limit is a hard ceiling: the kernel does not give a container more CPU time than its limit. Memory limits are enforced reactively. The documentation says a container that goes over its memory limit may not be killed immediately, because the kernel acts when it detects memory pressure, but it can be killed at any later moment. A container that survives above its limit for a while is not evidence that the limit is safe. Size the limit from measured peak usage and watch the restart count.
A rollout needs room for one extra Pod
With the default settings and 3 replicas, maxUnavailable rounds down to 0, so the Deployment has to start a new Pod before it may remove an old one. If no node has room for that extra Pod's requests, it stays Pending and the rollout stops making progress. After progressDeadlineSeconds, 600 by default, the Deployment reports that it has failed to progress. Keep spare capacity for one surge Pod, or set maxUnavailable to 1 and accept one Pod fewer during updates.
Two workloads that share a label get mixed up
A Deployment and a Service find Pods only by label selector. The documentation warns against overlapping selectors between controllers: Kubernetes does not stop you, and the controllers may conflict and behave unexpectedly. Services are just as literal. A Service that selects app=web sends traffic to every Pod with that label, including Pods of a different Deployment that reuses it. Give each workload a distinct label value and check what a selector matches with kubectl get pods -l followed by the selector.
A lowercase m in a memory value means millibytes
Quantity suffixes are case-sensitive. For CPU, 400m is 0.4 of a core. For memory, the documentation points out that 400m is a request for 0.4 bytes, when the author almost certainly meant 400Mi. The object is accepted, the scheduler then treats the Pod as needing almost no memory, and nodes can end up overcommitted. Write memory with Mi or Gi and keep m for CPU.

When to use it, and when something simpler is enough

Use it when

  • You run many services on several machines and need failed containers and failed nodes handled without a person, because controllers replace and reschedule Pods.
  • Several teams deploy to shared infrastructure and should not wait for an operations ticket. GitHub adopted Kubernetes to give its engineers a self-service way to deploy and scale services.
  • You deploy into an environment that already standardises on Kubernetes, such as a customer's cluster, where manifests are the expected delivery format.
  • You need behaviour that exists as an add-on controller, such as automatic certificate renewal with cert-manager, or you need to build custom scheduling policy as OpenAI did for research jobs.
  • Load varies enough that packing workloads onto shared nodes and adding replicas on demand saves real money or effort.

Think twice when

  • You have one or a few containers on one or two hosts with steady load. 37signals found that a small Rails application needed only containers on hosts behind a load balancer.
  • Nobody on the team can own cluster upgrades, networking, access rules and monitoring, and no managed Kubernetes service is available to take part of that work.
  • The workload is a stateless, request-driven service that a managed container platform can run from an image without any cluster.
  • The main component is a database or another stateful system that a managed service already runs for you.

A simpler alternative. Start with Docker Compose on one virtual machine, with a managed container platform that runs an image for you (Google's documentation describes Cloud Run as needing no cluster to create and no infrastructure to manage), or with an imperative deploy tool such as Kamal that starts containers on hosts over SSH. These stop being enough when you need automatic rescheduling across machines, many teams sharing capacity safely, or controllers that extend the platform.

Key takeaways

  • Kubernetes works by reconciliation: you declare desired state in objects, and controllers keep comparing it with the cluster and acting on the difference, whatever caused it.
  • A Pod is a disposable group of containers with one IP address, a Deployment keeps a set number of Pods running and replaces them gradually when the template changes, and a Service gives them a stable address by label.
  • ConfigMaps hold plain settings and Secrets hold credentials, but a Secret is only base64-encoded and is stored unencrypted in etcd unless you turn on encryption at rest.
  • Requests decide where a Pod can be scheduled and limits are enforced by the kernel: going over a CPU limit throttles the container, and going over a memory limit can get it killed with reason OOMKilled.
  • To change a running system you change its desired state, because a manual fix to a managed Pod is undone by the next reconciliation.
  • Kubernetes brings its own operating cost, so for a few containers on a few hosts a simpler tool is usually the better choice.

Example 1 of 5

GitHub moving the github.com web and API tier onto Deployments and Services

GitHubDocumented in an engineering article

GitHub's engineering post Kubernetes at GitHub (August 2017) describes how the Ruby on Rails application behind github.com and api.github.com moved from Puppet-managed servers to containers in Kubernetes clusters running in GitHub's own data centres, and how a per-pull-request environment called review lab was built on the way. [14]

The problem

The main application was deployed much as it had been eight years earlier: a process manager kept Unicorn worker processes running on configured servers, and a deploy tool connected to every frontend server over SSH, updated the code in place and restarted the processes. When load exceeded capacity, site reliability engineers provisioned additional capacity and added it to the pool of frontend servers. As the number of services grew, the post says new services took days, weeks or months to deploy, depending on their complexity and the team's availability. Engineers needed a self-service platform to experiment, deploy and scale, and the main application needed extra capacity in seconds instead of hours or days.

Where this topic fits

Kubernetes replaced the pool of frontend servers. The workload is described as Kubernetes resources kept as YAML in the application's repository, and GitHub's existing deployment tool applies them to a namespace. In front of the cluster sits GitHub's own load balancer, which was extended to send traffic to NodePort Services. Behind the cluster are the data services the application already depended on. The post says the first migration was intentionally limited to stateless workloads.

How it is applied, step by step

  1. The team redesigned the frontend tier with Pods, Deployments and Services and wrote the resources as YAML files checked into the application repository.
  2. The internal deployment tool was extended to apply those resources to a Kubernetes namespace and to create Kubernetes Secrets from GitHub's internal secret store. A typical effect is that credentials do not have to appear in the YAML kept in the repository.
  3. Review lab came first as a proving ground. Each deploy of a pull request gets its own namespace holding a complete copy of the application's resources, and cleaning up is one operation, deleting the namespace.
  4. For production, clusters were built in the data centres and the load balancer learned to route to NodePort Services, which is how outside traffic reaches Pods whose addresses keep changing.
  5. A production set of resources ran in parallel with the old servers. Traffic moved in stages: staff who opted in, then 100 requests per second, then 10% of requests, then the rest as servers were converted into nodes.
  6. After a failure test showed that losing one API server node could disturb a whole cluster, the application was spread over several clusters per site so that traffic can be moved away from an unhealthy one.

Why this approach fits

The old process depended on people: someone had to provision a server, configure it and add it to the pool. With a Deployment, capacity is a number in a file, and a controller does the provisioning that used to be a ticket. Namespaces give every pull request an isolated copy of dozens of objects that can be created and removed as a unit, which is hard to do with long-lived servers. Because Pods are replaced automatically, node failures become something the platform absorbs.

Limitation or tradeoff

None of this was quick or free. The post lists nine sub-projects shipped while building review lab and six more for the on-premises clusters, from cluster provisioning and certificate tooling to a log-forwarding service and load balancer changes, over roughly a year. The team reports that under high load some nodes still crashed with kernel panics, and that a simulated failure of one API server node disrupted a whole cluster, which was one of the reasons for running several clusters per site. The first migration was limited on purpose to stateless workloads.

What the sources document

  • Before the move, the main Rails application ran as Unicorn processes managed by a process manager called God on Puppet-managed servers, and deploys used Capistrano over SSH to update code in place on each frontend server and restart the processes. [14]
  • The team designed and validated a replacement for the frontend servers using Kubernetes primitives such as Pods, Deployments and Services, and shipped YAML representations of more than 50 Kubernetes resources checked into the application's repository. [14]
  • Each review lab is created in its own Kubernetes namespace. The sample deployment message in the post lists 12 ConfigMaps, 17 Deployments, 1 Ingress, 1 Namespace, 6 Secrets and 23 Services, and labs are cleaned up by deleting the namespace one day after their last deploy. [14]
  • Production traffic was moved gradually, starting with staff who opted in, then 100 requests per second, then 10% of requests to github.com and api.github.com, and the frontend transition was completed in just over a month. [14]
  • During periods of high load or high container churn some nodes kernel-panicked and rebooted, and the post states that Kubernetes routed around these failures while traffic stayed within the team's target error bounds. [14]

The facts above come from the cited sources. The steps and analysis in this example are our explanation of how they fit together.

Example 2 of 5

OpenAI scheduling large machine learning jobs on clusters of 7,500 nodes

OpenAIDocumented in an engineering article

OpenAI's post Scaling Kubernetes to 7,500 nodes (January 2021) describes the clusters its research teams use for large training jobs and for small experiments, and the changes needed to run Kubernetes at that size for a workload very different from web services. [15]

The problem

A large training job spans many nodes and runs best when it has all the hardware on each node, so that GPUs can communicate directly. The biggest jobs use MPI, a message-passing standard for parallel programs, and if any participating Pod dies the whole job halts and restarts from its last checkpoint. Research teams each have an allocation of capacity and found it hard to get all of it as the clusters grew, and the post notes that Kubernetes lacks the fair-sharing features of traditional job schedulers.

Where this topic fits

Kubernetes is the scheduler and the API that researchers submit work to. The Pod is the unit of work, and for many workloads one Pod fills one node. Services and load balancing play almost no part. The reconciliation model appears twice: in the built-in controllers that keep jobs' Pods in existence, and in a controller OpenAI wrote itself to turn a ConfigMap of team allocations into node taints.

How it is applied, step by step

  1. Researchers submit jobs as sets of Pods. A new job can create many hundreds of Pods at once, and for many workloads each Pod occupies an entire node.
  2. Pods in a job talk to each other directly on their Pod IP addresses instead of going through Services, after a single lookup of the participants when the job starts.
  3. A service called team-resource-manager reads a ConfigMap that lists, for each team, a node selector, a team label and an allocation amount. It reconciles that list with the nodes that exist and taints the right number of nodes for each team.
  4. An admission webhook adds a matching toleration to each submitted job based on the submitter's team, so the scheduler places a team's Pods on that team's nodes. Lower-priority Pods can carry a toleration for any team and borrow idle capacity.
  5. A balloon Deployment of low-priority Pods occupies otherwise idle nodes so that the cluster autoscaler does not remove them. When real work arrives, the scheduler evicts balloon Pods to make room.
  6. New nodes join with a preflight taint. A DaemonSet runs GPU test Pods on them, and a passing test removes the taint so that normal Pods can be scheduled there.

Why this approach fits

OpenAI needed scheduling policy that Kubernetes does not ship, and the platform's design let the team add it without changing researchers' code: taints and tolerations constrain the scheduler, an admission webhook edits Pods as they are submitted, and a small custom controller follows the same compare-and-correct pattern as the built-in ones. The post describes the result as a simple infrastructure that lets research teams scale up without changing their code.

Limitation or tradeoff

The authors stress that their workload is unusual and that their solutions may not suit other setups. The assumption that Pods are disposable holds only partly here: the post calls the Pods semi-stateful, because replacing one interrupts a whole job. Default scheduling can also deadlock two experiments that each ask for the whole cluster by placing half of each, which the team addressed with a coscheduling plugin. At this size the control plane itself needs care: the post reports up to 70GB of heap per API server.

What the sources document

  • For many of OpenAI's workloads a single Pod occupies an entire node, so bin-packing and fragmentation are not common problems, while load on the scheduler is spiky because a new job may create many hundreds of Pods at once. [15]
  • The largest jobs run MPI. If any participating Pod dies the entire job halts and is restarted from its last checkpoint, and the post describes the Pods as semi-stateful for that reason. [15]
  • A service named team-resource-manager takes a ConfigMap of (node selector, team label, allocation amount) tuples, reconciles it with the current nodes by applying a team NoSchedule taint, and runs an admission webhook that adds the corresponding toleration to submitted jobs. [15]
  • A balloon Deployment of low-priority Pods occupies resources on nodes so that the cluster autoscaler does not consider them idle, and the scheduler can evict those Pods immediately to make room for actual work. [15]
  • The largest clusters run 5 API servers and 5 etcd nodes on dedicated machines, and for the cluster with 7,500 nodes the team observed up to 70GB of heap in use per API server. [15]

Example 3 of 5

GKE Autopilot sizing nodes and bills from Pod resource requests

Google CloudDocumented in official docs

Google Kubernetes Engine (GKE) Autopilot is a mode in which Google manages the nodes. The documentation page Resource requests in Autopilot and the GKE pricing page describe how the requests written in a Pod specification drive node provisioning and, for general-purpose Pods, the bill. [16][17]

The problem

When the provider owns the nodes, something has to decide how much machine capacity to provision for a workload and what to charge for it. Workloads that state no requests, or tiny ones, would also be unstable, because the scheduler would pack them onto nodes as if they needed almost nothing. The documentation says Autopilot manages request values to improve workload stability.

Where this topic fits

The resources.requests block of each container, the same field the scheduler reads in any cluster, is the input. Autopilot checks and adjusts it when the workload is submitted, provisions node capacity for the result, and for general-purpose Pods bills on the requested amounts. Everything else about the Deployment is ordinary Kubernetes.

How it is applied, step by step

  1. You submit a Deployment as usual, with CPU and memory requests in the Pod template.
  2. When the workload is deployed, GKE validates the requests against the minimum and maximum allowed for the compute class. Containers with no requests receive default values.
  3. Requests below the minimum are raised automatically. If the ratio of CPU to memory is outside the allowed range, the smaller resource is increased. Requests above the maximum are rejected with an error.
  4. Limits are reconciled with requests. A container with only limits gets requests equal to them, and in clusters that do not support bursting, limits are set equal to requests.
  5. Autopilot configures nodes to fit the resulting requests, and the scheduler places the Pods. You do not choose machine sizes for general-purpose Pods.
  6. While the Pods run, the Pod-based billing model charges for the CPU, memory and ephemeral storage they request, in one-second increments.

Why this approach fits

The request is already the number Kubernetes uses to decide placement, so using it to size nodes and to bill means one declaration drives scheduling, capacity and cost. Operators no longer pick machine types or work out how many Pods fit on a node, and a team's bill follows what its manifests declare instead of how a shared node pool happened to be sized.

Limitation or tradeoff

You pay for what you request, not for what you use, so a habit of generous requests becomes a cost problem, and so does forgetting to write them: case B above is charged for four times the memory of case A. Autopilot may also change the numbers you wrote, which surprises people who expect the manifest to be the final word. Pods that select specific hardware such as GPUs use a different, node-based billing model, and you give up most control over node configuration.

What the sources document

  • Autopilot uses the resource requests specified in the workload configuration to configure the nodes that run the workloads, and enforces minimum and maximum requests based on the compute class or hardware configuration. [16]
  • If a container specifies no requests, Autopilot applies defaults. For the general-purpose compute class the defaults are 0.5 vCPU and 2 GiB of memory, and containers outside DaemonSets also receive a default ephemeral storage request of 1 GiB. [16]
  • Requests below the minimum are modified automatically to fall within the allowed range, requests above the maximum cause the workload to be rejected with an error message, and the general-purpose class requires a CPU-to-memory ratio between 1:1 and 1:6.5 (vCPU:GiB). [16]
  • When limits are set without requests, Autopilot sets requests to the value of the limits, and in clusters that do not support bursting GKE sets limits equal to requests. [16]
  • In the Pod-based billing model, charges accrue in one-second increments for the CPU, memory and ephemeral storage that running Pods request, and Autopilot's default or increased values apply when a request is missing or below the required minimum. [17]

cert-manager keeping TLS certificates renewed inside Kubernetes Secrets

cert-managerDocumented in official docs

cert-manager is an open source add-on that issues and renews TLS certificates inside a cluster. Its documentation pages Certificate resource and Annotated Ingress resource describe how a declared certificate becomes a Kubernetes Secret that the add-on keeps current. [18][19]

The problem

TLS certificates expire. The documentation's default lifetime is 90 days, so someone or something has to request a new certificate, store the private key safely and deliver both to the servers that terminate TLS, again and again. Done by hand, a forgotten renewal means clients start rejecting the service's certificate.

Where this topic fits

cert-manager adds a new object type, Certificate, and a controller for it. The output is an ordinary Secret of type kubernetes.io/tls, the object covered in this lesson, which an Ingress or a Pod can then use. The whole mechanism is the reconciliation loop applied to a new kind of desired state: a valid certificate for these names should exist in this Secret.

How it is applied, step by step

  1. An administrator installs cert-manager and creates an Issuer or ClusterIssuer that can sign certificates.
  2. A team creates a Certificate object that names the DNS names, the issuer and the Secret to write to. Alternatively it annotates an Ingress, and a cert-manager component creates the Certificate for it.
  3. cert-manager generates a private key and a CertificateRequest and obtains a signed certificate from the issuer.
  4. It stores the certificate and key in the named Secret under the keys tls.crt and tls.key, in the same namespace as the Certificate.
  5. It calculates a renewal time, by default two thirds of the way through the certificate's lifetime, records it in the Certificate's status, and issues a replacement when that time arrives.
  6. Whatever consumes the Secret picks up the new certificate. The page notes that an application that detects changes to the mounted files can reload them, while one that loads the key and certificate only at startup needs a restart.

Why this approach fits

Renewal is a task with a deadline that people forget, which is exactly what a control loop is good at. Expiry is treated as one more difference between desired and observed state, so no calendar reminder or cron job is involved. Because the output is a plain Secret, nothing downstream needs to know that cert-manager exists: an Ingress refers to a Secret name in the usual way.

Limitation or tradeoff

The private key sits in a Secret, so every caveat about Secrets applies: it is only as protected as your access rules and encryption-at-rest settings make it. The documentation warns that a renewBefore value close to the certificate's duration can cause a renewal loop. With some issuers, such as ACME issuers, the Secret has no ca.crt entry. cert-manager is also one more controller that the cluster's owners must install, monitor and upgrade.

What the sources document

  • A Certificate resource is a human-readable definition of a certificate request. cert-manager uses it to generate a private key and a CertificateRequest in order to obtain a signed certificate from an Issuer or ClusterIssuer, and stores the signed certificate and private key in the specified Secret. [18]
  • The documentation's example Secret has type kubernetes.io/tls and contains tls.crt, tls.key and ca.crt. It notes that with the ACME issuer the CA is not known, so ca.crt does not exist in the Secret. [18]
  • The default value of spec.duration is 90 days. By default the renewal time is two thirds of the way through the issued certificate's duration unless renewBefore or renewBeforePercentage is set, and cert-manager records the renewal time in the Certificate's status. [18]
  • The documentation warns that setting renewBefore very close to duration can lead to a renewal loop in which the Certificate is always in its renewal period. [18]
  • A sub-component called ingress-shim watches Ingress resources. For an Ingress carrying a supported annotation such as cert-manager.io/cluster-issuer, it ensures that a Certificate named after the tls.secretName field exists in the Ingress's namespace. [19]

4Common mistakes

  1. Running a long-lived application as a bare Pod instead of through a Deployment.

    Why it causes problems
    Nothing owns a bare Pod. If its node fails or the Pod is evicted, no controller creates a replacement, and there is no rolling update or rollback. The application is gone until a person notices.
    How to recognise it
    The Pod's name has no ReplicaSet hash in it, kubectl get pod NAME -o yaml shows no ownerReferences entry, and kubectl get deployments does not list the application.
    How to fix it
    Put the Pod template inside a Deployment with a replica count, even when the count is 1, apply it, and delete the bare Pod.

  2. Fixing a managed workload by hand instead of changing its desired state.

    Why it causes problems
    Controllers undo manual changes. A Pod deleted to stop an application comes back, and a container patched from a shell inside it is replaced by an unpatched one at the next restart or rollout. The cluster also stops matching any file a colleague can read.
    How to recognise it
    Pods that reappear after deletion, behaviour that changes after an unrelated redeploy, and differences between the output of kubectl get -o yaml and the manifests in version control.
    How to fix it
    Edit the manifest and apply it. To stop an application, scale its Deployment to zero or delete the Deployment. Keep manifests in version control so that the desired state has one source.

  3. Writing a Service selector or targetPort that does not match the Pods.

    Why it causes problems
    A Service whose selector matches no Pods has no endpoints, so every connection fails although all Pods are healthy. A wrong targetPort produces endpoints that refuse connections.
    How to recognise it
    kubectl get endpointslices -l kubernetes.io/service-name=NAME shows no addresses, or shows addresses with a port the container does not listen on.
    How to fix it
    Copy the labels from the Deployment's Pod template into the Service selector, set targetPort to the container's port, and check the EndpointSlice again.

  4. Leaving out requests and limits, or copying numbers without measuring.

    Why it causes problems
    With nothing set, the Pod is BestEffort: the scheduler places it as if it needed nothing, and it is the first to be evicted when the node runs short. Requests far above real use strand capacity and leave other Pods Pending. A memory limit below the real peak causes repeated kills.
    How to recognise it
    The Pod's status.qosClass is BestEffort, Pods are Pending with FailedScheduling events while nodes look idle, or kubectl describe pod shows a last state of Terminated with reason OOMKilled and a growing restart count.
    How to fix it
    Measure usage under realistic load, for example with kubectl top pod where cluster metrics are available. Set requests near typical use and the memory limit above the observed peak, then review the numbers after the first weeks in production.

  5. Treating a Secret as encrypted and committing its manifest to Git.

    Why it causes problems
    The values are base64-encoded, so anyone who can read the repository or the object can decode them. Inside the cluster, Secrets are stored unencrypted in etcd by default and can be read by anyone who is allowed to create Pods in the namespace.
    How to recognise it
    Files in the repository with kind Secret and a data or stringData block, or a cluster where encryption at rest has never been configured.
    How to fix it
    Keep Secret values out of Git, enable encryption at rest, restrict access to Secrets with least-privilege rules, and consider an external secret store that supplies values at deploy time.

  6. Adopting Kubernetes for one small application because it is the default choice.

    Why it causes problems
    The team takes on a control plane, upgrades, traffic routing, certificates and monitoring in order to run a workload that a couple of hosts could serve. 37signals describes spending more than it got back, in money and in operations work.
    How to recognise it
    A cluster with more system Pods than application Pods, and a team that spends more time on the platform than on the application.
    How to fix it
    Start with the simplest setup that meets the availability target, such as containers on hosts or a managed container platform. Move to Kubernetes when rescheduling, sharing between teams or add-on controllers become real needs.

Write a reconciliation loop and a request-based scheduler in Python

CodingIntermediateAbout 50 min (estimate)Hypothetical scenario

Build a tiny model of the two control loops from this lesson, using only the Python standard library. The cluster is a dictionary. state["pods"] maps a Pod name to the node it runs on, or to None when the Pod is Pending. state["nodes"] maps a node name to what it offers. Every Pod requests the amounts in REQUEST.

Write three functions, controller, scheduler and reconcile, and add them above this starting code. Save the file as reconcile.py and run it with python3 reconcile.py.

python
REQUEST = {"cpu": 500, "memory": 1024}   # each Pod: millicores and Mi


def show(title, state, log):
    pending = sorted(n for n, node in state["pods"].items() if node is None)
    placed = {node: sorted(n for n, where in state["pods"].items() if where == node)
              for node in sorted(state["nodes"])}
    print(f"== {title}")
    print("   actions:", ", ".join(log) if log else "none")
    print("   placed: ", placed)
    print("   pending:", pending)


if __name__ == "__main__":
    size = {"cpu": 2000, "memory": 3500}
    state = {"desired": 3, "pods": {}, "next_id": 1,
             "nodes": {"node-a": size, "node-b": size}}

    state, log = reconcile(state)
    show("apply: replicas 3", state, log)

    state = {**state, "pods": {n: w for n, w in state["pods"].items() if n != "web-2"}}
    state, log = reconcile(state)
    show("someone deletes web-2", state, log)

    state, log = reconcile({**state, "desired": 5})
    show("scale to 5", state, log)

    state = {**state, "nodes": {n: s for n, s in state["nodes"].items() if n != "node-b"}}
    state, log = reconcile(state)
    show("node-b fails", state, log)

    state, log = reconcile(state)
    show("reconcile again", state, log)

    state, log = reconcile({**state, "nodes": {**state["nodes"], "node-c": size}})
    show("node-c joins", state, log)

Requirements

  • controller(state) returns a new state and a list of action strings. It drops Pods whose node no longer exists (action "lost NAME"), creates Pending Pods named web-N from the next_id counter until the count equals desired (action "create NAME"), and deletes the highest-numbered Pods when there are too many (action "delete NAME").
  • scheduler(state) takes Pending Pods in number order and binds each to the node with the most free CPU among the nodes where both the CPU and the memory request fit (action "bind NAME -> NODE"). Ties go to the node whose name sorts first. A Pod that fits nowhere stays Pending.
  • reconcile(state) runs controller and then scheduler repeatedly until neither returns an action, and returns the final state with the combined list of actions.
  • No function may modify the state it receives. Each returns new dictionaries.
  • Calling reconcile twice in a row with no change in between must produce no actions the second time.

def controller(state):
    """Compare desired replicas with the Pods that exist; create or delete Pods."""
    pods = {name: node for name, node in state["pods"].items()
            if node is None or node in state["nodes"]}      # Pods on a lost node are gone
    actions = [f"lost {name}" for name in state["pods"] if name not in pods]
    next_id = state["next_id"]
    while len(pods) < state["desired"]:
        pods = {**pods, f"web-{next_id}": None}             # None means Pending
        actions = [*actions, f"create web-{next_id}"]
        next_id += 1
    while len(pods) > state["desired"]:
        newest = max(pods, key=lambda name: int(name.split("-")[1]))
        pods = {name: node for name, node in pods.items() if name != newest}
        actions = [*actions, f"delete {newest}"]
    return {**state, "pods": pods, "next_id": next_id}, actions


def free(state, node, pods):
    used = sum(1 for assigned in pods.values() if assigned == node)
    return {key: state["nodes"][node][key] - used * REQUEST[key] for key in REQUEST}


def scheduler(state):
    """Bind each Pending Pod to the fitting node with the most free CPU."""
    pods, actions = state["pods"], []
    for name in sorted((n for n, node in pods.items() if node is None),
                       key=lambda n: int(n.split("-")[1])):
        fits = [node for node in sorted(state["nodes"])
                if all(free(state, node, pods)[key] >= REQUEST[key] for key in REQUEST)]
        if fits:
            best = max(fits, key=lambda node: free(state, node, pods)["cpu"])
            pods = {**pods, name: best}
            actions = [*actions, f"bind {name} -> {best}"]
    return {**state, "pods": pods}, actions


def reconcile(state):
    """Run controller and scheduler until neither has anything left to do."""
    log = []
    while True:
        state, changed = controller(state)
        state, bound = scheduler(state)
        if not changed and not bound:
            return state, log
        log = [*log, *changed, *bound]

How it maps to the lesson:

  • Level-triggered behaviour. controller never asks why the count is wrong. A deleted Pod, a raised replica count and a failed node all lead to the same comparison of len(pods) with desired.
  • Chained controllers. controller creates Pods with no node, exactly as a ReplicaSet controller creates Pod objects. Placement is the scheduler's job.
  • Requests, not usage. After node-b fails, node-a holds three Pods. It has 2000 - 3 x 500 = 500 millicores free, which is enough CPU for one more Pod, but only 3500 - 3 x 1024 = 428 Mi of memory, which is less than the 1024 Mi request. Both new Pods stay Pending until node-c joins. On a real cluster this is a FailedScheduling event that reports insufficient memory.
  • Idempotence. The fifth block prints actions: none. A reconciler that is run again with nothing changed must do nothing, and it also must not give up: the two Pods are still Pending, and they are bound as soon as a node with room appears.
  • A deliberate simplification. max returns the first of several equal candidates, and the node list is sorted, so ties go to the alphabetically first node. The real scheduler scores nodes with many more rules.

Check your answer

  • Does your output match the expected text line for line, including the Pod numbers?
  • After node-b fails, are web-7 and web-8 Pending because of memory although node-a still has 500 millicores of CPU free?
  • Does the fifth block print no actions while still listing two Pending Pods?
  • Is the state you pass to reconcile unchanged after the call?
