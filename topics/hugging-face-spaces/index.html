Hugging Face Spaces

Hugging Face Spaces is a hosting service on the Hugging Face Hub that runs a web app from a git repository. You choose how it runs (Gradio, Docker or static HTML) and what hardware it gets, and the Hub builds the app and serves it at its own web address.

1Overview

Why it matters

A demo, an agent or a tool that only runs in your notebook cannot be tried by a teammate, a customer or an MCP client. Spaces turns a git push into a URL, which is why it is a common home for prototypes, demo agents, annotation tools and small tool servers that live next to the models and datasets on the Hub.

The mistakes that cost people are mundane. A token committed to a public repository instead of stored as a secret. A GPU left running over a weekend. Data written to a disk that is wiped at the next restart. An MCP tool whose docstring tells the model nothing. Anyone who ships demos, whether as an AI engineer or as a forward deployed engineer showing a prototype to a customer, needs to know how a Space is built, billed, configured and secured.

Before you start

  • LLM APIs and StreamingBeginner

What you will be able to do

  • Create a Space from a git repository and explain what the README.md settings block and each push do.
  • Choose between Gradio, Docker and static Spaces, and say how a Streamlit app is hosted today.
  • Pick hardware for a workload, estimate its monthly cost, and use sleep time, pausing or ZeroGPU to avoid paying for idle GPUs.
  • Store tokens as secrets and settings as variables, and read both from Python and from a Dockerfile.
  • Share a demo or an agent with the right visibility, and publish a Gradio function as an MCP tool.
  • Say which data survives a restart and where to keep data that must.

Key terms

Space
A git repository on the Hugging Face Hub that holds an app and the settings needed to build, run and serve it.
Space SDK
The runtime a Space uses, set by the sdk key in README.md. The configuration reference lists gradio, docker and static.
Hardware flavor
A named machine type a Space can run on, such as cpu-basic, cpu-upgrade or t4-small, each with its own CPU, memory, GPU and hourly price.
Sleep time
The period of inactivity after which a Space stops itself. The next visitor starts it again. Free CPU Spaces have a fixed period, and upgraded Spaces can have a custom one.
ZeroGPU
Shared GPU capacity that a Gradio Space borrows only while a function decorated with spaces.GPU is running, paid for from a daily quota instead of an hourly rate.
Variable
A non-sensitive setting stored in the Space settings, readable by anyone and copied into duplicates of the Space.
Secret
A sensitive setting such as an API token. Its value cannot be read back from the settings page and is not copied into duplicates.
Storage Bucket
Mutable, non-versioned object storage on the Hub that can be mounted into a Space so files survive restarts.
MCP badge
A marker on a Gradio Space that exposes its functions as Model Context Protocol tools. Public Spaces with the badge can be added to an assistant's tool list in one click.

2Explanation

Introduction

In LLM APIs and Streaming you called a model from a script on your own machine. A script like that is useful to you and invisible to everyone else. For a colleague, a customer or another program to use it, the code has to run on a machine that stays on, has a public address, and knows your API keys without having them written into the source. Setting that up yourself means picking a host, writing a container, and handling certificates and secrets, which is a lot of work for a prototype.

Hugging Face Spaces is the shortcut offered by the Hugging Face Hub. A Space (opens in a new tab) is a git repository, like the model and dataset repositories beside it. The top of its README.md holds a block of settings, and the rest of the repository holds your app. Each time you push a commit, the Hub rebuilds the app, restarts it, and serves it at an address of the form https://<space-subdomain>.hf.space. You never log in to a server.

Four decisions shape every Space, and they give this lesson its structure. Which SDK runs the app: Gradio for Python demos, Docker for anything else including Streamlit, or static HTML. Which hardware: a small free CPU by default, paid CPUs and GPUs, or shared ZeroGPU. How configuration reaches the app: variables for public settings and secrets for tokens. And who can reach it: public, protected or private, plus tool access for assistants.

Two uses matter most for agent work. One is sharing an agent demo so that other people can try it, as the Hugging Face Agents Course does with its first-agent template. The other is turning a Gradio function into an MCP tool that an assistant can call, which you will meet again in Building an MCP Server. For the wider picture of getting agents to users, see Agent Deployment Architecture.

How it works

A Space is a repository plus settings

Two things define a Space: the files in its git repository, and the settings kept outside the repository (variables, secrets, hardware, visibility). The top of README.md opens a YAML block that configures the Space. The configuration reference (opens in a new tab) lists every key. These are the ones you will touch first.

KeyWhat it does
sdkgradio, docker or static
sdk_versionThe Gradio version to install. The New Space form fills it in

python_versionThe Python version; the reference gives 3.10 as the default
startup_duration_timeoutHow long the app may take to start before the Space is flagged unhealthy; 30 minutes by default
preload_from_hubModels or files to download at build time so that start-up is faster
hf_oauth, suggested_hardwareSign in with Hugging Face; a hardware hint for people who duplicate your Space

What happens after a push

The Hub builds an image, starts a container on the hardware you chose, and sends web traffic to the port your app opens. On a Gradio Space the SDK runs your app file and installs requirements.txt. On a Docker Space your Dockerfile does everything. The Hub's Streamlit template starts its server on 0.0.0.0 and on the port it declares in app_port; a server that listens elsewhere cannot be reached by the Hub. The container runs as user ID 1000, so use COPY --chown=user rather than a recursive chown, which copies every file into a new image layer.

Three limits shape what you can do inside the container. The disk is ephemeral and 50 GB by default, with more on larger GPU flavors. No GPU is visible during a Docker build, so checks such as torch.cuda.is_available() belong in the running app. Outbound network calls are limited to ports 80, 443 and 8080.

Choosing an SDK

Gradio is the shortest path for Python: an app.py and a requirements.txt, and the SDK serves the app. Streamlit needs one extra step. The Streamlit page of the docs still shows sdk: streamlit, but the configuration reference now lists only gradio, docker and static, and the Hub's own Streamlit template is a Docker Space on port 8501. Creating a Gradio or Docker Space needs a paid plan: PRO for a personal account, Team or Enterprise for an organization. Static Spaces are free, and a free personal account in good standing may host up to two Gradio Spaces on ZeroGPU.

Hardware, billing and sleep

A new Space runs on CPU Basic: 2 vCPU, 16 GB of memory, no hourly charge. Upgrades run from CPU Upgrade ($0.03 per hour) through single GPUs (T4 small $0.40, L4 $0.80, A10G large $1.50, A100 large $2.50 per hour) to multi-GPU machines. These are the prices on the docs page on the access date; the pricing page is authoritative. The billing rules matter more than the price list:

  • You are charged by the minute while the Space is Starting or Running, whether or not anyone uses it. The build is not billed.
  • On CPU Basic a Space goes to sleep after 48 hours without use, and the next visitor restarts it. An upgraded Space never sleeps unless you set a sleep time.
  • A paused Space stops completely and is not billed. Only its owner can restart it.
  • Changing a secret or the hardware restarts the app.

Cost is therefore arithmetic: hourly price times billed hours.

ZeroGPU: a GPU for the length of one function call

ZeroGPU attaches a GPU only while a decorated function runs. It works with the Gradio SDK only.

python
import spaces

@spaces.GPU(duration=120)   # at most 120 s of GPU for this call; the default is 60 s
def generate(prompt):
    return pipe(prompt).images

Put the model on cuda at module level, outside the decorated function. The docs explain that outside @spaces.GPU an emulation mode lets this succeed without a real GPU. Instead of an hourly rate, each visitor spends a daily GPU quota that depends on the account: 2 minutes unauthenticated, 5 minutes for a free account, 40 minutes for PRO or Team, 60 minutes for Enterprise. PRO, Team and Enterprise users can continue past the quota with credits at $1 per 10 minutes. The default size, large, is half of an NVIDIA RTX Pro 6000 Blackwell GPU with 48 GB of memory. Adding size="xlarge" to the decorator asks for a whole one with 96 GB, which counts double against the quota.

Variables and secrets

Never write a token into the repository. In Settings add a variable for public configuration or a secret for anything sensitive. A Gradio app reads both as environment variables:

python
import os

model_id = os.getenv("MODEL_REPO_ID", "default-model")   # a variable
token = os.environ["HF_TOKEN"]                           # a secret

A Docker Space gets variables as build arguments and as runtime environment variables. Secrets are available at runtime as environment variables, and at build time only if you mount them in the Dockerfile:

dockerfile
RUN --mount=type=secret,id=HF_TOKEN,mode=0444,required=true \
    curl -H "Authorization: Bearer $(cat /run/secrets/HF_TOKEN)" -o model.bin https://example.com/private/model.bin

The Hub scans for hard-coded secrets and warns the owner, but treat that as a safety net. The huggingface_hub guide (opens in a new tab) scripts the same settings with add_space_secret, add_space_variable and request_space_hardware; secret values are write-only, so you can list the keys but never read the values back.

Where data lives

Anything written to the container disk is lost when the Space restarts, and restarts happen on every push, every settings change and every wake-up. Data that must survive goes elsewhere: a Storage Bucket mounted into the container, a dataset repository you upload to, or an external database. A bucket is mutable and not versioned, and the Docker docs note that its mount is available at runtime but not during the build. The suggested_storage key is ignored, because the configuration reference says the older persistent storage feature is no longer available.

Sharing a demo or an agent

People can reach a Space through its page, through an embed (the <gradio-app> web component or an iframe pointing at https://<space-subdomain>.hf.space), through the API that Gradio generates for almost any app, or through Sign in with Hugging Face when hf_oauth: true is set. Visibility has three levels. A public Space shows code and app to everyone. A protected Space keeps its source private but leaves the running app open at its embed address (PRO, Team or Enterprise). A private Space is hidden from everyone but its owner and collaborators, and other people get a 404. For a quick look from a laptop, launch(share=True) creates a temporary public link that Gradio says expires after one week, and gradio deploy publishes the same app as a Space. Duplicating a Space copies its code and public variables but not its secrets. Dev Mode (PRO, Team or Enterprise) opens an SSH and VS Code session in the running container so you can iterate without rebuilding; its changes are discarded unless you commit them with git.

Spaces as MCP servers and agent tools

Install gradio[mcp] and set mcp_server=True in launch(). Gradio turns each API endpoint into a tool: the function name becomes the tool name, and the docstring and type hints become the description and the parameter schema. The server lives at /gradio_api/mcp/ on the app's host, and /gradio_api/mcp/schema lists the tools. A Gradio Space that does this gets an MCP badge, and when the Space is public anyone can add it to their Hugging Face MCP settings. Private Spaces need an Authorization: Bearer <token> header. In the other direction, agent code can call a Space as a tool, for example with smolagents' Tool.from_space.

Worked example: Publish a one-function MCP tool as a Space, then budget its hardware

This example publishes a small Python function as a Gradio Space that is also an MCP server, checks it on your machine, and then works out what different hardware would cost. The function is the letter counter from the Hub's MCP documentation (opens in a new tab) with an added guard and a longer docstring.

Step 1: write the files

Create the Space in the browser (New Space, SDK Gradio) and clone it. The form writes README.md for you, including sdk: gradio and the current sdk_version; leave that file as it is. Add two files.

app.py:

python
import gradio as gr


def letter_counter(word: str, letter: str) -> int:
    """Count how many times a letter appears in a word, ignoring case.

    Args:
        word: The word to search in, for example "strawberry".
        letter: The single letter to count, for example "r".

    Returns:
        The number of times the letter appears in the word.
    """
    if len(letter) != 1:
        raise ValueError("letter must be exactly one character")
    return word.lower().count(letter.lower())


demo = gr.Interface(fn=letter_counter, inputs=["text", "text"], outputs="number")

if __name__ == "__main__":
    demo.launch(mcp_server=True)

requirements.txt:

text
gradio[mcp]

Step 2: test the logic without Gradio

The function is plain Python, so check it before involving any web server. These results come from running the function itself:

text
>>> letter_counter("strawberry", "r")
3
>>> letter_counter("Mississippi", "s")
4
>>> letter_counter("Mississippi", "S")
4
>>> letter_counter("abc", "ab")
ValueError: letter must be exactly one character

Step 3: run it locally

Install the extra with pip install "gradio[mcp]" and run python app.py. Gradio serves the web page on port 7860 by default, so http://127.0.0.1:7860/gradio_api/mcp/schema lists the tool. You should find one tool named letter_counter with the parameters word and letter, described by the docstring. If the description is missing, the docstring is not in the Args: format.

Step 4: push it

bash
git add app.py requirements.txt
git commit -m "Add letter counter MCP tool"
git push

The Space rebuilds and starts. For a Space called letter-counter owned by your-name, the host is your-name-letter-counter.hf.space, and the MCP endpoint is that host plus /gradio_api/mcp/. A client that supports streamable HTTP takes this configuration:

json
{
  "mcpServers": {
    "letter-counter": {
      "url": "https://your-name-letter-counter.hf.space/gradio_api/mcp/"
    }
  }
}

If the Space is private, add "headers": {"Authorization": "Bearer <your-token>"} next to the URL. The Hugging Face MCP settings page, described in the Hub MCP server docs (opens in a new tab), is the alternative: add the Space there and your assistant sees it as a tool without any JSON.

Step 5: budget the hardware

This tool needs no GPU, so CPU Basic is enough. The same arithmetic matters the moment a Space grows a model. With the hourly prices from the GPU docs (opens in a new tab), the monthly cost is

cost=hourly price×billed hours\text{cost} = \text{hourly price} \times \text{billed hours}cost=hourly price×billed hours

Billed hours are the hours the Space is Starting or Running. Always on for 30 days is 24×30=72024 \times 30 = 72024×30=720 hours. Running 8 hours a day on 22 working days, and pausing it otherwise, is 8×22=1768 \times 22 = 1768×22=176 hours.

The Hub's docs say a PRO account can generate up to 600 images a day with FLUX.1-schnell on a 40-minute quota. That implies 40×60/600=440 \times 60 / 600 = 440×60/600=4 seconds of quota per image, and at 4 seconds a call the same arithmetic gives 75 calls a day for a free account (5 minutes) and 30 for an unauthenticated visitor (2 minutes). Your own model will use a different number of seconds, so measure it before you promise a daily limit to anyone.

Edge cases and limitations

Guides and tutorials disagree with each other
Hosting docs change faster than the pages that cite them. The Streamlit page still describes sdk: streamlit, while the configuration reference lists only gradio, docker and static. Argilla's quickstart still tells you to set persistent storage to SMALL, while the configuration reference says that feature is no longer available and the Spaces docs recommend Storage Buckets. The MCP Course shows an /sse endpoint, while the current Gradio guide uses /gradio_api/mcp/ and sends clients without streamable HTTP support to the mcp-remote bridge. When two pages conflict, trust the configuration reference and the page for the version you run, then test the result.
The free tier is narrower than older tutorials suggest
Static Spaces are free for everyone, but creating or duplicating a Gradio or Docker Space needs a paid plan. According to the huggingface_hub guide, doing so on cpu-basic without a subscription fails with HTTP 402. The exception is up to two ZeroGPU Gradio Spaces on a free personal account in good standing (verified email, account older than 30 days). The same guide adds that a Space created directly on paid hardware needs only a payment method and prepaid credits, which the Overview does not say, so confirm in the New Space form what your account can create. Decide which plan you have before you design the architecture, because it limits which of the four SDK and hardware combinations you can use.
ZeroGPU has its own rules
Only the Gradio SDK works. Put models on cuda at module level, not inside the decorated function. torch.compile is not supported because each GPU call runs in a freshly started process, so use ahead-of-time compilation as the Hub's blog post shows. A call that needs more than 60 seconds must declare a longer duration, which is the maximum run time of that call. On the access date the docs listed PyTorch 2.8.0 and later and two Python versions, 3.12.12 and 3.10.13, so check the list before you pin versions in requirements.txt.
A restart erases local state
A restart discards the container's disk and the app's memory. It happens on every push, on every change to a secret, variable or hardware setting, and when a sleeping Space wakes up. In-memory caches, SQLite files and uploaded files all vanish, and so do Dev Mode edits that were never committed with git. Design for a safe cold start: load models when the app starts and keep durable data in a bucket, a dataset repository or an external database.
A public MCP Space is a public tool
Anyone can add a public Space that has an MCP badge, and anyone who knows the URL can call it, so put no secrets in its code and do not assume the caller is the person you expect. Going the other way, a tool you add from someone else's Space runs on their server with whatever arguments your assistant sends, and its output goes into your model's context. Treat that output as untrusted input. Private Spaces need an Authorization bearer token from the client.

When to use it, and when something simpler is enough

Use it when

  • You need a shareable address for a Python or container-based demo, annotation tool or small API, and the models and datasets it uses already live on the Hub.
  • You want a Gradio function to become an MCP tool that assistants can add in one click, without running a server of your own.
  • A GPU demo is used in bursts, so a ZeroGPU daily quota or a pause-when-idle schedule costs less than a GPU that stays on.

Think twice when

  • You need network isolation inside a customer's cloud account, a contractual uptime commitment, or full control over where data is processed. Use a cloud platform or an on-premises deployment instead.
  • The data is confidential and the app would have to be public to work, as with a Langfuse server that must be reachable by SDKs elsewhere and receives real user traces.
  • The job is a long batch run or training with no web interface. A web app on a Space is the wrong shape for it, so run it as a batch job.

A simpler alternative. To show something to one person this week, call launch(share=True) in Gradio. It creates a temporary public link served from your own machine, which Gradio says expires after one week. Move to a Space when the demo has to stay up while your laptop is closed.

Key takeaways

  • A Space is a git repository whose README.md settings and files tell the Hub how to build, run and serve the app, and every push rebuilds and restarts it.
  • Gradio and Docker are the SDKs to choose between, Streamlit runs as a Docker Space, and creating either kind needs a paid plan apart from a small ZeroGPU allowance for free accounts.
  • Paid hardware is billed by the minute while the Space is running, whether or not anyone visits, so sleep time, pausing and ZeroGPU matter more than the hourly price.
  • Tokens belong in secrets and public settings in variables; both reach the app as environment variables, but only variables are copied into duplicates.
  • The container disk is wiped on every restart, so anything that must survive goes in a Storage Bucket, a dataset repository or an external database.
  • Setting mcp_server=True turns a Gradio function into an MCP tool whose name, description and parameters come from the function name, docstring and type hints.

Example 1 of 5

Hugging Face Agents Course, sharing a smolagents agent as a Gradio Space

Hugging FaceDocumented in official docs

Unit 1 of the Hugging Face Agents Course has learners build a first agent with smolagents and publish it as a Space. The Unit 4 final assignment starts from a template that learners duplicate and asks them to submit a link to their public Space. The two course pages describe the setup, and the Spaces overview documents duplication and secrets. [14][15][1]

The problem

Each learner needs a running copy of an agent, using their own model token, at an address they can send to a friend, without provisioning a server. The course also needs a way to collect and score submissions from those agents.

Where this topic fits

The agent is a Gradio app. The template Space is the unit that gets duplicated, the HF_TOKEN secret is the per-learner configuration, and the Space URL is what is shared. In the final assignment the learner's public Space also serves as the code link submitted to the scoring API.

How it is applied, step by step

  1. The learner duplicates the agents-course/First_agent_template Space into their own profile, so the code, requirements and Gradio entry point arrive as a working copy.
  2. They create a secret named HF_TOKEN in the duplicated Space's Settings, using a Hugging Face token with inference permission. Secrets are not copied when a Space is duplicated, so each learner supplies their own.
  3. They edit app.py, adding tools written with the tool decorator to the CodeAgent, which uses a hosted model through the serverless inference API and is limited to six steps.
  4. The Space rebuilds on each commit and serves the Gradio interface that GradioUI(agent).launch() creates. The learner shares the Space URL with friends and colleagues.
  5. In the final assignment, learners duplicate a second template Space, run their agent on the course's questions through the scoring API, and submit their username, a link to their Space code and their answers.
  6. The scoring service compares each answer with the ground truth by exact match and updates the leaderboard, and the course asks learners to keep the Space public so that the code behind a score can be checked.

Why this approach fits

Duplication turns one published Space into a template that every learner owns. Secrets are the natural boundary, because a token is personal and must not travel with the copy. A Gradio interface needs no front-end work, so the unit stays about the agent.

Limitation or tradeoff

The Space hosts the interface, while the thinking happens in a hosted model, so the learner's experience depends on that service's quotas and availability. A free-tier Space sleeps when idle, so a shared link can be slow to open. By our reading of the current Spaces overview, duplicating a Gradio Space needs a paid plan, apart from the ZeroGPU exception, so a learner on a free account may be stopped at the first step; check the course page for current guidance. The course itself says its leaderboard is for fun and that scores can be submitted without full verification.

What the sources document

  • The tutorial tells learners to duplicate the agents-course/First_agent_template Space, create a secret named HF_TOKEN under Variables and Secrets in the copy's Settings, and edit app.py, the only file they need to change. [14]
  • The template's agent is a smolagents CodeAgent that reaches Qwen/Qwen2.5-Coder-32B-Instruct through the serverless inference API, is limited to 6 steps, and is started with GradioUI(agent).launch(). The tutorial encourages learners to share the agent with friends and colleagues. [14]
  • The final assignment provides an API with the routes GET /questions, GET /random-question, GET /files/{task_id} and POST /submit. Submissions are scored by exact match against the ground truth and update a leaderboard. The evaluation set is 20 level-1 questions from the GAIA validation set. [15]
  • A submission consists of the learner's Hugging Face username, a link to their Space code and their answers. The page asks learners to keep the Space public and to start by duplicating the provided template onto their own profile. [15]
  • The Spaces overview says that when you duplicate a Space you choose the owner, name, visibility (private by default) and hardware, that public variables are carried over, and that secrets are not added to the duplicate. [1]

The facts above come from the cited sources. The steps and analysis in this example are our explanation of how they fit together.

Example 2 of 5

Langfuse on a Docker Space, a stateful observability server with sign-in control

LangfuseDocumented in official docs

The Hugging Face Hub docs include a guide, Langfuse on Spaces, for deploying the open-source Langfuse LLM-observability platform as a Docker Space from a template. Argilla's quickstart describes a similar deployment of its annotation tool. The Docker Spaces, Storage Buckets and disk-usage pages describe the mechanisms both rely on. [12][5][10][9][13]

The problem

Langfuse keeps traces, prompts and accounts, and the applications that report traces need a stable address to reach it. That is a long-lived server with state, not a one-off demo. It needs a Docker runtime, secrets for its keys, storage that survives restarts and a way to limit who can sign in.

Where this topic fits

This is a Docker Space, not a Gradio one, because Langfuse is not a Python interface. The Space template supplies the Dockerfile, a Storage Bucket supplies durable state, environment variables carry the keys, and Hugging Face OAuth is the sign-in layer in front of the app.

How it is applied, step by step

  1. Create a new Space, choose Docker as the SDK and Langfuse as the template, so the Dockerfile and README.md metadata arrive pre-written.
  2. Attach a Storage Bucket so Langfuse's data persists across restarts. Without one, the container disk is lost every time the Space restarts.
  3. Set the Space to public so that Langfuse SDKs running elsewhere can reach it, and, as the guide recommends but marks optional, replace the default NEXTAUTH_SECRET, SALT and ENCRYPTION_KEY values with random ones (the guide generates them with openssl rand -base64 32 for the first two and openssl rand -hex 32 for the key).
  4. Limit who can sign in. Either add hf_oauth_authorized_org to the Space's README.md so only members of the named organizations get in, or set AUTH_DISABLE_SIGNUP to true after signing in yourself.
  5. Point instrumented applications at the Space's address with LANGFUSE_HOST and the project's public and secret keys. The guide shows an OpenAI-compatible client and a Gradio chat template Space sending traces to it.

Why this approach fits

A Docker Space gives Langfuse the runtime it already has, instead of forcing it into a Gradio app. Hugging Face OAuth and organization restriction reuse accounts the team already holds, and a bucket gives the server a disk that outlives restarts. The result is an observability backend for agent demos that sits on the same platform as the demos.

Limitation or tradeoff

The guide needs the Space to be public so the SDKs can reach it, so sign-in is the only access control, and by default any logged-in Hugging Face user can open the app until you restrict it. Argilla's quickstart tells readers to enable persistent storage, which the configuration reference says is no longer available. The bucket mechanism that replaced it is the one the Langfuse guide uses, so read each page against the current docs. On free hardware a Space also sleeps after 48 hours idle; our inference is that a sleeping tracing server cannot accept traces until someone wakes it.

What the sources document

  • The Hub guide says to create a Space with Docker as the SDK and Langfuse as the template, attach a Storage Bucket so data persists across restarts, and set the Space to public so Langfuse API and SDK clients can reach it. [12]
  • The Langfuse Space comes pre-configured with Hugging Face OAuth. By default any logged-in Hugging Face user can access the public Space; access can be restricted with the hf_oauth_authorized_org metadata field or by setting AUTH_DISABLE_SIGNUP to true. The guide also recommends replacing the default NEXTAUTH_SECRET, SALT and ENCRYPTION_KEY values. [12]
  • Storage Buckets are mutable object storage without versioning, and the Spaces disk-usage page calls them the recommended way to persist data in a Space, mounted into the container at the path you specify. The Docker Spaces page says data written to disk is lost whenever a Docker Space restarts. [10][9][5]
  • Argilla's quickstart documents deploying Argilla to Spaces from the argilla/argilla-template-space template with OAuth sign-in, and tells readers to set persistent storage to SMALL or lose their data when the Space restarts. [13]

Example 3 of 5

ZeroGPU, serving FLUX.1-dev demos from borrowed GPUs and making them faster

Hugging FaceDocumented in an engineering article

ZeroGPU is Hugging Face's shared GPU pool for Gradio Spaces. The Hub blog post "Make your ZeroGPU Spaces go brrr with ahead-of-time compilation" (September 2025) shows how its authors speed up FLUX.1-dev and other image and video demos on it, and the ZeroGPU docs describe the allocation model and the quotas. [16][4]

The problem

An image or video demo needs a large GPU for a few seconds per request and nothing in between. Renting a GPU around the clock for that traffic wastes money, while a demo without a GPU is too slow to use. On ZeroGPU the process is also freshly started for almost every GPU call, which defeats the usual torch.compile approach to speeding up a model.

Where this topic fits

ZeroGPU is the hardware choice of a Gradio Space: the GPU exists only inside functions decorated with spaces.GPU. The compilation step sits between loading the model at start-up and serving requests. The compiled transformer is applied to the pipeline once, and every later call reuses it.

How it is applied, step by step

  1. Load the pipeline at module level and move it to cuda. The docs explain that an emulation mode makes this work before any real GPU is attached.
  2. Decorate the request function with spaces.GPU. When a visitor calls it, ZeroGPU attaches a GPU, runs the function in a forked process, and releases the GPU afterwards.
  3. At start-up, inside a spaces.GPU function with a long duration, run the pipeline once under spaces.aoti_capture to record the transformer's real inputs, export it with torch.export, and compile it with spaces.aoti_compile.
  4. Call spaces.aoti_apply to patch the pipeline so its transformer uses the compiled binary. Later requests then skip compilation.
  5. Optionally combine the compiled model with FP8 quantization and Flash-Attention 3 kernels loaded through the kernels library, which the post reports speed it up further.
  6. Each visitor's calls are charged to a daily GPU quota that depends on the account tier, and a shorter declared duration improves queue priority.

Why this approach fits

A demo with bursty traffic and heavy compute per request is where paying per GPU-second beats paying per hour. The GPU is attached for the roughly 105 seconds that a 28-step call may need in this sketch, not for the hours between visitors. Compilation targets the cost that ZeroGPU makes visible, the time inside each GPU slot, because quota and queue priority are both counted in those seconds.

Limitation or tradeoff

The pool is Gradio-only and, the docs warn, may be less compatible than ordinary GPU Spaces. The speedups are the authors' measurements on FLUX.1-dev, Wan and LTX on the hardware of September 2025, which the post describes as an H200 slice. The ZeroGPU docs now describe NVIDIA RTX Pro 6000 Blackwell GPUs, so re-measure before quoting the numbers. Quota is per visitor: a popular demo leaves anonymous visitors with 2 minutes a day and a low queue priority.

What the sources document

  • The post explains that ZeroGPU sets up the GPU just in time. It forks the process, sets it up on CUDA, runs the GPU task and kills the fork when the GPU is released, so torch.compile cannot reuse its work and falls back to a filesystem cache that takes from a few dozen seconds to a couple of minutes. [16]
  • The authors report that ahead-of-time compilation made FLUX.1-dev 1.7x faster, that FP8 quantization added another 1.2x, and that speedups across Flux, Wan and LTX ranged from 1.3x to 1.8x. [16]
  • The post's code uses spaces.aoti_capture to record example inputs, torch.export to export the transformer, spaces.aoti_compile to compile it and spaces.aoti_apply to patch the pipeline. The compilation runs inside a spaces.GPU function with duration=1500, which the post calls the maximum allowed during startup. [16]
  • The ZeroGPU docs describe dynamic GPU allocation for decorated functions with a default duration of 60 seconds, support for the Gradio SDK only, and daily quotas of 2 minutes for unauthenticated users, 5 for free accounts, 40 for PRO and Team, and 60 for Enterprise, with credits at USD 1 per 10 minutes for paid tiers. [4]
  • Free personal accounts in good standing can host up to 2 ZeroGPU Spaces, PRO accounts up to 10, and organizations on Team and Enterprise plans up to 50. [4]

Spaces as MCP tools, Gradio functions that assistants can call

Hugging FaceDocumented in official docs

The Hugging Face MCP Server docs and the Spaces as MCP servers guide describe how MCP-compatible Gradio Spaces become tools in clients such as VS Code, Cursor and Claude Code. The Gradio guide and the Hugging Face MCP Course describe building one, and the smolagents API docs describe the agent-side route of loading a Space as a tool. [17][18][19][21][22]

The problem

Assistants need tools, and many useful ones, such as image generators, transcribers and converters, already exist as Gradio demos on the Hub. Without a standard route, each would need its own wrapper server, hosting and authentication.

Where this topic fits

The Space is the MCP server. Gradio generates the protocol layer from the function signature, the Hub gives the server a hosted address and a badge, and either the Hugging Face MCP Server or a client configuration points the assistant at it.

How it is applied, step by step

  1. Write the function with type hints and a docstring in the Args format. Gradio uses its name, docstring and hints as the tool name, description and parameter schema.
  2. Launch with mcp_server=True, add gradio[mcp] to requirements.txt, and push the code to a Gradio Space.
  3. The Space gets an MCP badge. Another person opens their Hugging Face MCP settings, picks their client and adds the Space with Add to MCP tools, or points a client straight at the Space's /gradio_api/mcp/ address.
  4. When the assistant calls the tool, the arguments go to the Space and the function runs there. On a ZeroGPU Space the caller's own ZeroGPU quota is used.
  5. Agent code can use the same Space through smolagents' Tool.from_space, giving the Space's id, a name and a description.

Why this approach fits

The Gradio function is already the unit of work, so no new server code is needed. The docstring does double duty as documentation for people and as the description a model reads, and hosting on the Hub gives the tool a stable HTTPS address without extra infrastructure.

Limitation or tradeoff

A tool is only as usable as its docstring, and a vague one leaves the model unsure when to call it. The MCP Course page documents an SSE endpoint, /gradio_api/mcp/sse, while the current Gradio guide documents /gradio_api/mcp/ and notes that clients without streamable HTTP support need the mcp-remote bridge, so test your own client. Gradio's guide calls hosting on Spaces free, whereas the Hub docs now require a paid plan to create Gradio Spaces, with the ZeroGPU exception. A public MCP Space can be called by anyone.

What the sources document

  • Per the Hub docs, any public Space with a visible MCP badge can be added as a callable tool in clients such as VS Code, Cursor and Claude Code using Add to MCP tools. A Hugging Face token with READ permission is needed, and a Spaces filter, mcp-server, lists compatible Spaces. [17]
  • To build one, create a Gradio Space, install gradio[mcp], write type-hinted functions with docstrings and call launch(mcp_server=True). Pushing it to a Gradio Space gives it the MCP badge automatically. [17]
  • The Gradio guide says the MCP server is served at /gradio_api/mcp/ with its schema at /gradio_api/mcp/schema, that the docstring and type hints generate the tool description and parameters, that the function name becomes the tool name, and that private Spaces need an Authorization bearer header. [19]
  • The Hugging Face MCP Server docs list a Dynamic Spaces option that lets an assistant discover and use MCP-compatible Spaces at runtime. For ZeroGPU Spaces the caller's quota is used when the tool is called, and the Spaces guide says a PRO account can generate up to 600 images a day with FLUX.1-schnell. [18][17]
  • smolagents' Tool.from_space creates a tool from a Space given its id, a name and a description, and its documentation example wraps black-forest-labs/FLUX.1-schnell as an image generator. The MCP Course unit deploys a Gradio MCP server by pushing app.py and requirements.txt to a Space. [22][21]

Streamlit apps on Spaces, a text-completion demo and a dataset explorer

Hugging FaceDocumented in an open-source project

Hugging Face's 2021 blog post on Streamlit Spaces builds two Streamlit apps and hosts them on Spaces: a replica of Write With Transformer and a dataset explorer. Today the Hub's Streamlit template is a Docker Space, as the template's own repository and the huggingface_hub guide show. [23][7][24][2][11]

The problem

A data or ML team wants an interactive page where a reader can change parameters or explore a dataset, written in Python without front-end code and hosted next to the model and dataset it uses.

Where this topic fits

Streamlit re-runs the script from top to bottom whenever the user changes a widget, which suits explorers and parameter-driven demos. On Spaces it is served by the container's Streamlit process on port 8501, started by the Dockerfile.

How it is applied, step by step

  1. Write the app in Python with Streamlit widgets. The first demo in the post uses a text area and sidebar sliders for the generation settings, and the second uses a dataframe, a bar chart and a seaborn plot.
  2. Load models and data from the Hub inside the script. The dataset demo reads its dataset in streaming mode so it does not download everything.
  3. List extra dependencies in requirements.txt, and make the Streamlit version on your own machine the same as the one the Space runs.
  4. Create the Space from the Streamlit template, which is a Docker Space with app_port 8501 and a Dockerfile that installs the requirements and runs streamlit run on that port, bound to 0.0.0.0.
  5. Edit src/streamlit_app.py and push. The Hub rebuilds the image and serves the app at the Space's address, where it can also be embedded in an iframe with ?embed=true.

Why this approach fits

Streamlit's re-run model gives an interactive page from a single Python file. The Docker SDK also removes the version coupling of the older SDK, because the Dockerfile and requirements decide exactly what runs.

Limitation or tradeoff

Because the script re-runs on every interaction, a model loaded at the top of the file is loaded again each time unless the app caches it, which makes naive model demos slow; the Streamlit documentation covers caching. ZeroGPU supports only the Gradio SDK, so a Streamlit Space that needs a GPU needs paid GPU hardware. The 2021 post and the Hub's Streamlit page describe the older sdk: streamlit route, and the page still shows Streamlit 1.25.0 as the latest supported version, so follow the template for new work.

What the sources document

  • The 2021 post recreates Write With Transformer, a GPT-2 and XLNet text-completion app with a text area and sidebar sliders for hyperparameters, and a dataset explorer that loads merve/poetry in streaming mode and shows a dataframe, a bar chart and seaborn plots. [23]
  • The post says to drag and drop the files into a Space and to list extra dependencies in requirements.txt, and adds a terse note that your local Streamlit version is the same as the Space's. [23]
  • The Hub's Streamlit page describes Streamlit as re-running the code each time the app state changes, says only port 8501 is allowed for Streamlit Spaces, and shows iframe embedding with ?embed=true. [7]

4Common mistakes

  1. Putting an API token in app.py, in README.md or in a committed .env file

    Why it causes problems
    A public Space shows every file to everyone, and git history keeps the token after you delete the line. Whoever finds it can spend your quota or read private data until the token is revoked.
    How to recognise it
    The Hub warns the owner that its secrets scanner found a hard-coded secret, or a text search of the repository for your provider's key prefix finds a match.
    How to fix it
    Revoke the token first, because rewriting history does not make an exposed token safe. Create a new one, store it as a secret in the Space settings (or with add_space_secret), and read it with os.environ.

  2. Leaving paid hardware running when nobody is using it

    Why it causes problems
    Billing is by the minute while the Space is Starting or Running, used or not. A T4 small left on for 30 days costs USD 288 at the docs' price of USD 0.40 per hour, and an A100 large costs USD 1,800.
    How to recognise it
    The hardware badge shows a GPU, the Space has few recent visitors, and the billing page shows continuous usage for it.
    How to fix it
    Set a sleep time so the Space stops when idle, pause it when you are done, move it back to cpu-basic, or move a bursty demo to ZeroGPU. The huggingface_hub guide shows request_space_hardware, set_space_sleep_time and pause_space.

  3. Saving user data to the container disk and expecting it to be there tomorrow

    Why it causes problems
    The disk is ephemeral. Every push, every settings change and every wake-up from sleep restarts the Space and removes what you saved, without any error message.
    How to recognise it
    Files or rows written yesterday are gone after you edit a secret, or after the Space was asleep over the weekend.
    How to fix it
    Attach a Storage Bucket and write under its mount path, upload to a dataset repository, or use an external database. Test by restarting the Space on purpose before you rely on it.

  4. Running a Docker server the Hub cannot reach or that cannot write its files

    Why it causes problems
    If the server listens on 127.0.0.1 or on a port other than app_port, the Space never serves a page. The container runs as user ID 1000, so files owned by root cause permission errors as soon as the app writes a cache or downloads a model.
    How to recognise it
    The container logs show the server on a different address or port than the metadata declares, or they show a PermissionError during start-up. The Space stays in Starting until the startup timeout.
    How to fix it
    Bind to 0.0.0.0, make app_port match, create a user with ID 1000 and set its home and working directory, and use COPY --chown=user. Read the build and container logs after every change.

  5. Publishing an MCP tool without a docstring or type hints

    Why it causes problems
    Gradio builds the tool description and parameter schema from them. Without them the assistant sees a tool with a bare function name and no explanation of when to call it or what each argument means.
    How to recognise it
    The schema at /gradio_api/mcp/schema shows an empty description or parameters without descriptions, and the assistant rarely or wrongly chooses the tool.
    How to fix it
    Name the function for what it does, annotate every parameter, and add an Args block that describes each one. Read the schema again after every change before you share the Space.

Exercise 1

Build a Space-ready MCP tool that reads a variable and a secret

Hands-onBeginnerAbout 40 min (estimate)Hypothetical scenario

Create a folder text-tools/ with an app.py and a requirements.txt that you could push to a Gradio Space unchanged. The app exposes two MCP tools.

  • word_count(text, min_length) counts the whitespace-separated words that have at least min_length characters.
  • status() reports whether a service token is configured. It reads a public variable SERVICE_NAME and a secret SERVICE_TOKEN from the environment, and it must never return the token itself.

Everything up to the last requirement needs only Python 3 and the free package gradio[mcp] (pip install "gradio[mcp]"). You do not need a Hugging Face account to do it. Pushing to a Space is optional, because creating a Gradio Space needs a paid plan or a ZeroGPU allowance.

Requirements

  • word_count has type hints and a docstring with an Args block, and raises ValueError when min_length is less than 1.
  • status reads SERVICE_NAME (default "text-tools") and SERVICE_TOKEN from os.environ when it is called, not when the module is imported, so tests can set them.
  • status returns "<name>: token configured" or "<name>: token missing", and never contains the token value.
  • The two functions are served as tabs of one gr.TabbedInterface, launched with mcp_server=True.
  • A unittest file covers counting, filtering by min_length, the ValueError, a configured token, a missing token and the rule that the token is not returned.
  • After python app.py, the schema at /gradio_api/mcp/schema lists two tools with their descriptions.

Expected behaviour

word_count("the quick brown fox") returns 4, word_count("the quick brown fox", 4) returns 2, word_count("a bb ccc", 2) returns 2, word_count("", 1) returns 0, and word_count("x", 0) raises ValueError.

With SERVICE_NAME=demo and SERVICE_TOKEN=abc, status() returns demo: token configured. With neither variable set it returns text-tools: token missing. The schema URL lists exactly two tools, word_count and status, each with the description taken from its docstring.

Hint 1

str.split() with no argument splits on any run of whitespace, so you do not need a regular expression.

Hint 2

Call os.getenv inside the function. In tests, unittest.mock.patch.dict(os.environ, {...}) sets variables for one test only.

Hint 3

gr.TabbedInterface takes a list of interfaces and a list of tab names. An interface with no inputs can be created with inputs=None.

Hint 4

If a tool shows no description in the schema, check that the docstring has an Args block with indented parameter names.

Show solution

requirements.txt:

text
gradio[mcp]

app.py:

python
import os

import gradio as gr


def word_count(text: str, min_length: int = 1) -> int:
    """Count the words in a text that have at least a given length.

    Args:
        text: The text to analyse. Words are separated by whitespace.
        min_length: Only words with at least this many characters are counted. Must be 1 or more.

    Returns:
        The number of words that have at least min_length characters.
    """
    if min_length < 1:
        raise ValueError("min_length must be 1 or more")
    return sum(1 for word in text.split() if len(word) >= min_length)


def status() -> str:
    """Report whether the service token is configured, without revealing it.

    Returns:
        A short status line that starts with the service name.
    """
    name = os.getenv("SERVICE_NAME", "text-tools")
    configured = bool(os.getenv("SERVICE_TOKEN"))
    return f"{name}: token {'configured' if configured else 'missing'}"


count_tab = gr.Interface(fn=word_count, inputs=["text", gr.Number(value=1, precision=0)], outputs="number")
status_tab = gr.Interface(fn=status, inputs=None, outputs="text")
demo = gr.TabbedInterface([count_tab, status_tab], ["Word count", "Status"])

if __name__ == "__main__":
    demo.launch(mcp_server=True)

test_app.py:

python
import os
import unittest
from unittest.mock import patch

from app import status, word_count


class WordCountTests(unittest.TestCase):
    def test_counts_all_words_by_default(self):
        self.assertEqual(word_count("the quick brown fox"), 4)

    def test_filters_short_words(self):
        self.assertEqual(word_count("the quick brown fox", 4), 2)
        self.assertEqual(word_count("a bb ccc", 2), 2)

    def test_empty_text_has_no_words(self):
        self.assertEqual(word_count("", 1), 0)

    def test_rejects_zero_min_length(self):
        with self.assertRaises(ValueError):
            word_count("x", 0)


class StatusTests(unittest.TestCase):
    def test_token_configured(self):
        with patch.dict(os.environ, {"SERVICE_NAME": "demo", "SERVICE_TOKEN": "abc"}):
            self.assertEqual(status(), "demo: token configured")

    def test_token_missing_uses_default_name(self):
        env = {k: v for k, v in os.environ.items() if k not in ("SERVICE_NAME", "SERVICE_TOKEN")}
        with patch.dict(os.environ, env, clear=True):
            self.assertEqual(status(), "text-tools: token missing")

    def test_token_value_is_never_returned(self):
        with patch.dict(os.environ, {"SERVICE_TOKEN": "s3cret-value"}):
            self.assertNotIn("s3cret-value", status())


if __name__ == "__main__":
    unittest.main()

Run python -m unittest -v test_app; all seven tests should pass. Then run SERVICE_NAME=demo SERVICE_TOKEN=abc python app.py and open http://127.0.0.1:7860/gradio_api/mcp/schema. The environment variables stand in for what a Space does when you create the variable SERVICE_NAME and the secret SERVICE_TOKEN in its Settings. On a Space, read both the same way; nothing in the code changes. To publish, create a Gradio Space, clone it, copy app.py and requirements.txt in, then commit and push.

Reading the environment inside status instead of at import time is what keeps the tests simple. It also means a changed secret takes effect after the restart that Spaces performs anyway.

Exercise 2

Plan and cost a Space for a team's agent demo

AnalysisIntermediateAbout 30 min (estimate)Hypothetical scenario

A six-person team has built a Gradio chat demo of an agent. The agent calls a hosted model API with a token, and it appends a feedback rating to a small JSON Lines file after each conversation. Only members of the team's Hugging Face organization may use it. Colleagues use it on 22 working days a month, between 08:00 and 16:00. A second proposal runs a 7-billion-parameter model inside the Space on a T4 small instead of calling the hosted API.

Use these hourly prices from the Hub's GPU docs: CPU Upgrade USD 0.03 and T4 small USD 0.40. Plan the configuration of both proposals and compare their monthly cost.

Requirements

  • Choose the SDK and the hardware for each proposal and justify the choice in one or two sentences.
  • Classify MODEL_API_TOKEN, MODEL_ID and LOG_LEVEL as variables or secrets.
  • Choose the Space visibility, say how team-only access is enforced, and say where the feedback file is stored so that it survives restarts.
  • Compute the monthly cost of CPU Upgrade and of T4 small when always on (720 hours) and when billed for 176 hours, and say what you would do to achieve the lower figure.
  • Recommend one proposal and name one fact that would change your mind.

Expected behaviour

A complete answer picks the Gradio SDK, puts the token in a secret and the other two settings in variables, keeps the feedback in a mounted Storage Bucket or a dataset repository, and shows these figures: CPU Upgrade USD 21.60 always on and USD 5.28 for 176 hours; T4 small USD 288.00 always on and USD 70.40 for 176 hours.

Hint 1

Hourly price times billed hours is the whole formula. Billed hours are the hours in which the Space is Starting or Running.

Hint 2

A private Space is visible only to its owner and collaborators, and a Space can also restrict sign-in to members of named organizations.

Hint 3

Ask what is written to disk and what happens to that disk when the Space restarts.

Show solution

Configuration. Both proposals use the Gradio SDK, because the demo is a Python chat interface. Proposal A (hosted model API) needs no GPU. CPU Basic is enough to start, since it has no hourly charge (creating the Space in the organization still needs a Team or Enterprise plan), and CPU Upgrade (8 vCPU, 32 GB) is the step up if the interface is slow with six users. Proposal B needs a GPU, and a T4 small has 16 GB of GPU memory. A 7-billion-parameter model stored at 2 bytes per parameter needs about 14 GB for its weights alone, which leaves little room for anything else unless the model is quantized. That is our estimate, not a figure from the docs.

Variables and secrets. MODEL_API_TOKEN is a secret: it cannot be read back from the settings page and is not copied if someone duplicates the Space. MODEL_ID and LOG_LEVEL are variables: they are non-sensitive, visible to anyone who can open the settings, and are copied into duplicates, which is what you want for configuration. Both kinds reach the app as environment variables.

Access and storage. Make the Space private, so that the source and the running app are available only to the owner and collaborators and other people get a 404. If the team needs a reachable app with the code kept private, a protected Space (a PRO, Team or Enterprise feature) with hf_oauth: true and hf_oauth_authorized_org set to the organization is the alternative. For the feedback file, mount a read-write Storage Bucket and write the JSON Lines file under its mount path. Writing it to the container disk would lose it at every restart.

Cost. The formula is hourly price times billed hours.

HardwarePrice per hour720 hours176 hours
CPU Upgrade$0.03$21.60$5.28
T4 small$0.40$288.00$70.40

The 176 hours come from 8 hours times 22 days. To reach it, pause the Space outside working hours with pause_space and restart_space on a schedule, or set a sleep time. A sleep time of one hour stops billing once the Space has been idle that long, so each active day is billed for up to 9 hours instead of 8, which gives 9 x 22 = 198 hours: $5.94 for CPU Upgrade and $79.20 for T4 small. The first visitor after a sleep waits for the restart.

Recommendation. Choose proposal A. The 14 GB estimate leaves little headroom on the T4, and even with a sleep time the T4 costs about 13 times as much as CPU Upgrade (79.20 / 5.94 = 13.3). What would change the decision: a requirement that prompts never leave the team's own infrastructure, which the hosted API cannot satisfy, or a price for the hosted API that exceeds the difference of about USD 73 a month between the two proposals (79.20 minus 5.94).
