What Is AI Engineering?

AI engineering is the work of building software products on top of pre-trained foundation models. Instead of training a model, you take one that already exists and make it useful and dependable for a specific job through the prompt you write, the context you supply, the tools you connect and the evaluations you run.

1Overview

Why it matters

Calling a language model takes one HTTP request, so a convincing demo can be built in an afternoon. Turning that demo into a feature people can rely on is a different job, and it is the job this roadmap teaches. A LinkedIn team reported reaching about 80% of its intended experience in the first month and then spending four more months trying to get past 95%. Honeycomb's team shipped a natural-language query feature in a month and wrote that most of the effort was ordinary product work, plus a set of problems that only appear with language models: limited context, slow responses, vague inputs and prompt injection.

Knowing what AI engineering is tells you where to spend effort. Teams that mistake it for machine learning engineering start by collecting training data and fine-tuning when a better prompt or better context would have been enough. Teams that mistake it for ordinary API integration ship with no way of measuring quality and learn from their users that answers are wrong. Developers, product managers and technical leads need the same map: which parts of the system are yours to design, which part is rented, and how you will know whether the whole thing works.

Before you start

No prerequisites. You can start here.

What you will be able to do

  • Define AI engineering and explain what it means to build on a pre-trained foundation model.
  • Compare the work of an AI engineer and an ML engineer by starting point, main levers and how quality is checked.
  • Name the five layers of the application stack (model, prompt, context, tools, evaluation) and say what each one controls.
  • Run a small five-layer application, read its evaluation score and identify which layer caused each failure.
  • Calculate the cost of a model request from token counts and the success rate of a chain of model calls.
  • Describe how building on a foundation model changes the way a product is planned, tested and maintained.

Key terms

Foundation model
A large model trained once on very broad data so that it can be adapted to many tasks. The large language models behind chat assistants are the best-known kind.
Pre-trained
Already trained by someone else before you use it. You receive the finished model, usually behind an API, and you do not see or change its training.
Inference
Running a trained model to get an output. Every request your application sends to a model is an inference call, billed and timed on its own.
Token
The unit a language model reads and writes, roughly a fragment of a word. Prices, size limits and speed are all measured in tokens.
Prompt
The instructions sent to the model with a request, describing the task, the rules and the format of the answer.
Context
The information placed in a request so the model can do the task, such as retrieved documents, records about the user and earlier messages.
Tool
A function your application offers to the model. The model asks for it by name with arguments, and your code decides whether to run it.
Evaluation (eval)
A repeatable test of the application's outputs against expectations, run on a fixed set of example inputs each time something changes.
Fine-tuning
Continuing to train an existing model on your own examples, which changes its weights. It is where AI engineering borrows most directly from ML engineering.
Model adaptation
Making a general model fit your task, either without changing its weights (prompt, context, tools) or by changing them (fine-tuning).

2Explanation

Introduction

If you have ever called a web API for payments, maps or weather, you already know the first move of AI engineering: send a request, get a response, build a feature around it. The difference is what sits behind the API. A payments API follows a written contract and returns the same thing for the same input. A language model generates its reply on the spot. The reply is usually right and sometimes wrong, and nothing in it tells you which.

A useful picture is a capable contractor on their first day. They are well read and quick, but they know nothing about your company, cannot see your systems and will not remember yesterday. You would not send them back to school. You would give them a clear brief, hand them the documents they need, give them access to the right systems, and check their work until you trust it. Those four moves are the craft of AI engineering: the prompt, the context, the tools and the evaluation, arranged around a model that someone else trained.

Until recently, a product that needed to understand language had to begin with machine learning: collect labelled examples, train a model for that one task, then build the product. Foundation models, which are large models trained once on broad data and adaptable to many tasks, changed the order. Shawn Wang's 2023 essay The Rise of the AI Engineer (opens in a new tab), which argued that this work deserves its own job title, put it this way: tasks that took a research team five years in 2013 now need API documentation and a spare afternoon. Chip Huyen's book AI Engineering supplies the definition used in this lesson. You work with a model someone else has trained, so the job is less about developing models and more about adapting and evaluating them (opens in a new tab).

This lesson explains what it means to build on a pre-trained model, how an AI engineer's work differs from an ML engineer's, what each of the five layers does, and how the approach changes the way products are planned, tested and maintained. Each later lesson in this roadmap goes deeper into one of the layers.

How it works

Starting from a model someone else trained

A foundation model is produced by pre-training: a lab trains a very large model on a huge body of text, and often images and audio, using an amount of data and computing power that few organisations have. How Large Language Models Work covers that process. As an AI engineer you meet the model after all of it is finished, usually as a hosted API that charges per token and sometimes as open weights you run yourself.

You make the general model fit your task in one of two ways, which Huyen calls model adaptation:

  • Without changing the weights. You give the model instructions, information and tools at request time. This needs little data, is quick to try, and is where almost every project starts.
  • By changing the weights. Fine-tuning continues training on your own examples. It can improve quality, speed and cost, but it needs data and training runs, and the work has to be repeated when the base model changes.

The authors of What We've Learned From a Year of Building with LLMs (opens in a new tab) advise against fine-tuning until you have shown that it is necessary. Most of this roadmap is about the first route.

AI engineer versus ML engineer

The two roles share a subject and differ in where they start. An ML engineer starts from data: collect and label examples, choose an architecture, train, then deploy the model that results. The model is the thing they build. An AI engineer starts from a model that already works and a product idea, and builds everything around the model.

Three cautions about this comparison:

  • The line is crossed in both directions. Wang calls the boundary permeable: AI engineers fine-tune and host models when a product needs it, and research engineers build on APIs.
  • ML knowledge is optional at the start and valuable later. Huyen writes that it is no longer a must-have for building AI applications, and that it still widens your options and helps when a model misbehaves. Evaluation borrows most from ML practice: held-out test sets, metrics and careful experiments.
  • Titles vary. Huyen shows job adverts that put both roles under one name. Read the description: if the work is prompts, context, tools and evals around an existing model, it is AI engineering whatever the title says.

The application stack

Huyen describes three layers in any AI system: application development on top, model development (training, fine-tuning, datasets) beneath it, and infrastructure (serving, compute, monitoring) at the bottom. AI engineers start at the top and move down only when they must. Within that top layer, each request your application makes passes through five layers of its own. Four of them are visible in the request.

Here is a request body for Anthropic's Messages API, written for this lesson. The field layout follows the tool use documentation (opens in a new tab) and the Messages API guide (opens in a new tab).

json
{
  "model": "claude-sonnet-5-5",
  "max_tokens": 300,
  "system": "You answer return questions for a shop. Reply with exactly one word: yes or no.",
  "tools": [{
    "name": "lookup_order",
    "description": "Look up one order by id. Returns whether it was a clearance item.",
    "input_schema": {
      "type": "object",
      "properties": {"order_id": {"type": "string"}},
      "required": ["order_id"]
    }
  }],
  "messages": [{
    "role": "user",
    "content": "POLICY: Returns are accepted within 30 days of delivery. Clearance items are final sale.\n\nQUESTION: I received order C09 10 days ago. Can I still return it?"
  }]
}

model is the model layer, system is the prompt, the policy text inside messages is context, and tools lists what the model may ask for. If the model wants the tool, its response contains a tool_use block. Your code runs the lookup and sends the result back in a tool_result block. The model never touches your database itself.

Evaluation is the one layer with no field in the request. It lives beside the application as a set of example inputs with known good answers, rerun whenever one of the other four layers changes. Huyen's walk-through of a generative AI platform (opens in a new tab) starts from a bare model call, adds one component at a time, and makes two points worth keeping: context construction does for foundation models what feature engineering does for classical ML, and evaluation is needed at every step.

Where AI changes product development

The product comes first. In classical ML the product is built last, after data collection and training. With a working model available on day one, the usual order is to prototype the feature with a prompt, show it to users, and invest in data or tuning only if it proves useful. Wang calls this "fire, ready, aim".

Tests become evaluations. OpenAI's evaluation guide (opens in a new tab) states the problem directly: models sometimes produce different output from the same input, so traditional software testing is not enough. A unit test asserts one exact answer. An eval runs many examples and reports a rate, such as 46 of 50 correct. Anthropic's guide to defining success criteria (opens in a new tab) says to fix a specific, measurable target before you start improving prompts. Its example is an F1 score of at least 0.85 on a held-out set of 10,000 posts.

Getting to "mostly works" is quick, and the rest is slow. A demo has to work once. A product has to work nearly every time, on inputs you did not choose. In the examples below, LinkedIn's team reached 80% of its target in one month and spent four more on the rest, and Honeycomb shipped in a month with several problems still open.

Errors multiply across steps. If each of nnn model calls in a chain succeeds independently with probability ppp, the whole chain succeeds with probability

P(all n steps succeed)=pnP(\text{all } n \text{ steps succeed}) = p^nP(all n steps succeed)=pn

Honeycomb's team did this sum when it decided against chaining: five steps at 90% each give 0.95=0.590.9^5 = 0.590.95=0.59. Real steps are not fully independent, so treat the formula as a reason to measure the whole chain and not as a prediction.

Every request has a price and a wait. One sample response in Anthropic's Messages API guide, the reply to "Can you describe LLMs to me?", reports 30 input tokens and 309 output tokens. At the list price for Claude Opus 5.5 on the day this lesson was written ($4 per million input tokens and $20 per million output tokens, from the models overview (opens in a new tab)), that one reply costs

30×4+309×201,000,000=0.0063 dollars\frac{30 \times 4 + 309 \times 20}{1{,}000{,}000} = 0.0063 \text{ dollars}1,000,00030×4+309×20​=0.0063 dollars

About two thirds of a cent looks like nothing. At 100,000 requests a day it is $630 a day, and 98% of it pays for output tokens. The wait follows the same pattern, because output is generated one token at a time. Huyen's illustration is that at 10 ms per token a 100-token reply takes a second, and Honeycomb measured between 2 and more than 15 seconds per query. Token counts are a design decision in the way query counts are for a database.

The model is a rented dependency that changes. Providers retire models. Anthropic's deprecations page (opens in a new tab) says that requests to a retired model fail and that customers get at least 60 days' notice. A prompt tuned for one model may behave differently on its replacement, so the eval set doubles as the regression suite you run before every model change.

New kinds of risk appear. Text that reaches the model can try to override your instructions (prompt injection), and sending customer data to a model provider raises privacy and contract questions that an ordinary feature does not.

Worked example: A returns helper built layer by layer and scored on six test questions

A shop wants a helper that answers one kind of question: can I still return this order? The real rule is in the shop's policy (returns within 30 days of delivery, clearance items are final sale). Whether an order was a clearance item is in the order database.

The program below builds the helper three times, adding one layer each time, and scores every version on the same six test questions. So that everyone gets identical output without an API key, the model is a small deterministic stand-in. It imitates the two properties that matter here: it can use only what is in the prompt, and where the prompt is silent it falls back on a generic belief (shops allow 14 days), the way a real model falls back on what it absorbed in pre-training. It is not a language model, and the scores say nothing about real model accuracy. The structure and the workflow are the real part.

Save this as returns_helper.py and run python3 returns_helper.py. It needs only the standard library.

python
import re

POLICY = "Returns are accepted within 30 days of delivery. Clearance items are final sale."
ORDERS = {  # live records that no pre-trained model has ever seen
    "A17": False, "B42": False, "C09": True, "D55": False, "E30": False, "F77": True,
}  # order id -> is it a clearance item?
INSTRUCTIONS = "You answer return questions for a shop. Reply with exactly one word: yes or no."


def stub_model(prompt):
    """Layer 1, the model. A deterministic stand-in so that everyone gets the same output.
    Like a real model it knows only what the prompt says, plus a generic belief
    ('shops allow 14 days') that stands in for what pre-training taught it."""
    if "TOOLS: lookup_order" in prompt and "TOOL RESULT" not in prompt:
        return "CALL lookup_order " + re.search(r"order (\w+)", prompt).group(1)
    days = int(re.search(r"(\d+) days ago", prompt).group(1))
    limit = re.search(r"within (\d+) days", prompt)
    limit = int(limit.group(1)) if limit else 14
    final_sale = "final sale" in prompt and "clearance=True" in prompt
    return "yes" if days <= limit and not final_sale else "no"


def lookup_order(order_id):
    """Layer 4, a tool: ordinary code that fetches a fact the model cannot know."""
    return f"order {order_id} clearance={ORDERS[order_id]}"


def answer(question, use_context=False, use_tool=False):
    parts = [INSTRUCTIONS]                                   # layer 2: prompt
    if use_context:
        parts.append("POLICY: " + POLICY)                    # layer 3: context
    if use_tool:
        parts.append("TOOLS: lookup_order(order_id)")        # layer 4: the tool is offered
    parts.append("QUESTION: " + question)
    reply = stub_model("\n".join(parts))
    if reply.startswith("CALL lookup_order"):                # our code runs the tool
        parts.append("TOOL RESULT: " + lookup_order(reply.split()[-1]))
        reply = stub_model("\n".join(parts))
    return reply


EVAL_SET = [  # layer 5: evaluation. (order id, days since delivery, correct answer)
    ("A17", 19, "yes"), ("B42", 47, "no"), ("C09", 10, "no"),
    ("D55", 5, "yes"), ("E30", 25, "yes"), ("F77", 3, "no"),
]


def evaluate(name, **layers):
    failed = []
    for order_id, days, expected in EVAL_SET:
        question = f"I received order {order_id} {days} days ago. Can I still return it?"
        if answer(question, **layers) != expected:
            failed.append(order_id)
    passed = len(EVAL_SET) - len(failed)
    print(f"{name}: {passed}/{len(EVAL_SET)} correct, failed: {', '.join(failed) or 'none'}")
    return passed


if __name__ == "__main__":
    evaluate("v1 prompt only")
    evaluate("v2 + context", use_context=True)
    evaluate("v3 + context + tool", use_context=True, use_tool=True)

It prints:

text
v1 prompt only: 2/6 correct, failed: A17, C09, E30, F77
v2 + context: 4/6 correct, failed: C09, F77
v3 + context + tool: 6/6 correct, failed: none

Reading the three lines:

  • v1, prompt only (2/6). The instructions are clear and the replies are well formed, but four are wrong. A17 (19 days) and E30 (25 days) are refused because the model's generic 14-day belief is not this shop's policy. C09 and F77 are approved because nothing told it about clearance items. This is the usual failure of an unaided model: fluent, confident and based on general knowledge instead of your facts.
  • v2, plus context (4/6). Adding the policy text fixes A17 and E30. C09 and F77 still fail: the policy now says clearance items are final sale, but the model cannot know that these two orders were clearance items. More prompt wording cannot supply a missing fact.
  • v3, plus a tool (6/6). The model asks for lookup_order, our code runs it and returns clearance=True, and the last two cases pass.

What to take from the run:

  1. stub_model never changed. All of the improvement came from the layers around the model.
  2. The evaluation did the diagnosis. A bare score says "not good enough". The list of failing cases says which kind of fact is missing, and so which layer to change.
  3. The check is cheap to repeat. A new policy, a different model or a reworded prompt can each be judged by running the same six cases again.

To use a real model, replace stub_model with a function that sends the prompt to a model API and returns the reply text. Then expect the same input to give different outputs now and then, grow the eval set from six cases to a few hundred, and track a pass rate instead of expecting a perfect score.

Edge cases and limitations

The same request can return different answers
A language model samples its output, so two identical requests can produce different text. You cannot always switch this off. Anthropic's Messages API guide states that the temperature, top_p and top_k sampling parameters are not supported on Claude 4.7 and later models and that setting them to a non-default value returns a 400 error. Write checks that tolerate variation: test properties of the answer (valid format, contains the right fact) over many examples and watch a pass rate over time, instead of asserting one exact string.
The model you built on is retired
Hosted models have a lifecycle. Anthropic's deprecations page defines four states (active, legacy, deprecated and retired), says requests to a retired model will fail, and commits to at least 60 days of notice for publicly released models. Its models overview shows a retirement date of the form "not sooner than" beside each current model. Keep the model id in configuration, keep an eval set that can be run against the replacement, and treat migration as routine maintenance.
Prompts and context stop being enough
Some tasks stay below the quality bar however the prompt is written, typically ones that need a strict output syntax or knowledge that no public model has. The Applied LLMs authors give Honeycomb's query assistant as a case: a manual and examples in the prompt worked decently, and fine-tuning later improved output on the syntax and rules of the query language. The sign is an eval score that has stopped moving after many prompt and context changes. That is the moment to bring in fine-tuning and ML engineering skills, with the eval set as the yardstick.
The job title does not tell you the job
Huyen's chapter shows job adverts from December 2023 in which some companies list AI engineering and ML engineering as one role and others separate them. A post titled AI engineer may involve training models, and a post titled ML engineer may involve building on an API. Read for the verbs. Prompts, retrieval, tool integration and evals describe AI engineering. Datasets, training runs and model architectures describe ML engineering.
Wrong context is worse than no context
A model follows the context it is given. If retrieval returns the wrong document, the model answers confidently from it. Honeycomb reports a hit-or-miss experience when the most relevant schema fields were truncated out of the prompt, and GitHub measured each context change with A/B tests instead of assuming it helped. Evaluate after every change to the context layer, and print the assembled prompt for a failing case before blaming the model. The first exercise reproduces this failure.
A cheaper tool would do the job
A foundation model is one option among several. Discord's engineering blog says generative AI should not be applied when other tools are a better fit, and the Applied LLMs authors describe lightweight models such as DistilBERT as a surprisingly strong baseline for classification. If the task is a fixed rule, a lookup, or a narrow prediction with plenty of labelled data, try the rule, the query or the small model first.

When to use it, and when something simpler is enough

Use it when

  • The task means reading, interpreting or producing unstructured content, such as summarising documents, extracting fields from free text, drafting replies or translating a question into a query.
  • You have little or no labelled training data, but you can describe the task in words and supply the relevant facts at request time.
  • A wrong output can be caught before it does harm: code can validate it, a person reviews it, or the action is easy to undo.
  • You need to find out quickly whether a product idea is worth pursuing, before investing in data collection or model training.

Think twice when

  • A fixed rule, a database query or a lookup already gives the right answer, as with tax calculations, permission checks or order status.
  • The task is a narrow prediction on structured data with plenty of labelled history, such as fraud scoring or ranking, where a small trained model is cheaper, faster and easier to measure.
  • The response must arrive in tens of milliseconds or cost a tiny fraction of a cent, which a call to a large model cannot meet.
  • A wrong output takes effect immediately and cannot be checked or reversed, for example moving money or deleting records with no review step.

A simpler alternative. Ordinary code: a rule, a regular expression, a SQL query or keyword search, and for prediction tasks a small classical model. These stop being enough when the inputs are open-ended language that no finite set of rules covers. A sign that you have reached that point is a rule list that keeps growing while users keep finding phrasings it misses.

Key takeaways

  • AI engineering means building products on a pre-trained foundation model, so the work is adapting and evaluating a model that someone else trained.
  • An ML engineer starts from data and builds the model, while an AI engineer starts from a working model and a product idea and builds everything around it. The two roles meet at fine-tuning and evaluation.
  • The application stack has five layers: the model you choose, the prompt you write, the context you supply, the tools you connect and the evaluation that measures the result.
  • Evaluations take the place of exact-match unit tests because outputs vary, and the list of failing cases tells you which layer to change.
  • A demo shows that an idea can work once. Most of the effort goes into the remaining errors, the cost and wait of every request, and chains of calls whose errors multiply.
  • The model is a rented dependency that will be replaced, so keep it configurable and keep an eval set you can rerun against its successor.

Example 1 of 5

Honeycomb Query Assistant turning plain English into queries on a hosted model

HoneycombDocumented in an engineering article

Honeycomb is an observability product. Phillip Carter of Honeycomb describes how the team built Query Assistant, a natural-language querying feature, in the article All the Hard Stuff Nobody Talks About when Building Products with LLMs. A later practitioner essay, What We've Learned From a Year of Building with LLMs, reports what the team did next. [11][4]

The problem

Users had to learn Honeycomb's query builder before they could ask a question of their data. The team wanted a text box where someone could type a question, such as which service has the highest latency, and get back a query that runs. They had about a month. Some customers had schemas with more than 5,000 fields, the available models took seconds to respond, and users typed everything from full queries written out in English to the single word "slow".

Where this topic fits

The whole feature is AI engineering in the sense of this lesson. No model was trained for the first release. The team chose a hosted model, wrote the prompt, decided what context to put in it, validated the output in code and fitted the result into the existing product. Most of the article is about decisions in the prompt and context layers and about the product work around them.

How it is applied, step by step

  1. Choose a hosted commercial model. The article says gpt-3.5-turbo and Claude were the best options available at the time and that GPT-4 was too slow for this use.
  2. Assemble a prompt from seven ingredients: the user's text, a description of what a Honeycomb query is, domain knowledge about instrumentation data, the customer's schema, few-shot examples, the existing query if there is one, and instructions.
  3. Fit the schema into the context window by including only fields that received data in the past seven days, and cut the field list down further for the customers where that is still too large.
  4. Make one model call per request. The team rejected chains of calls because each call adds seconds of latency and because errors compound across steps.
  5. Parse the output, correct it where possible and validate it, then run it against the query engine and show the result in the normal query builder, where the user can adjust it.
  6. Limit what a manipulated prompt could do. The output is non-destructive and undoable, the model call is not connected to databases or other services, inputs and outputs are cut to a maximum length, and each user has a daily rate limit.
  7. Do the work that has nothing to do with the model: audit the model providers for security and compliance, write new terms, add a control that turns the feature off, and handle customers with special agreements case by case.

Why this approach fits

Turning a loosely worded question into a structured query is a language task that a general pre-trained model already does reasonably well. What the model lacks is specific to Honeycomb: the query format and each customer's schema. Both can be supplied as text at request time, so the prompt and context layers carry everything that makes the feature Honeycomb's, and no training data was needed to launch. The output is also easy to make safe. A query can be validated by code, shown to the user and edited, so a wrong answer costs little.

Limitation or tradeoff

The context layer had no complete solution. When a schema had to be cut short, the article calls the experience hit-or-miss, depending on whether the relevant fields survived. The team also found correctness and usefulness pulling against each other: a prompt change that improved outputs tended to narrow the range of inputs that worked. Prompt injection is described as unsolved, which is why the feature was kept away from anything destructive. Prompting was not the end state either. The Applied LLMs authors report that fine-tuning later gave better output on the syntax and rules of the query language.

What the sources document

  • The article lists what is passed to the model: the user's natural-language input, information about what constitutes a Honeycomb query, information about the domain of instrumentation data, the schema, several examples in the manner of a few-shot prompt, the existing query if it exists, and instructions. The output is parsed, corrected if correctable and executed against the query engine. [11]
  • Some customers have schemas with over 5,000 unique fields. Constraining a schema to fields that received data in the past seven days usually lets it fit in gpt-3.5-turbo's context window, but for some customers the fields are still truncated, which the author describes as a hit-or-miss experience. [11]
  • The article gives latency of two to more than 15 seconds for producing a valid query, says GPT-4 was far too slow for the use case, and illustrates compound probabilities with a 90% accurate process repeated five times giving 0.59. [11]
  • The author writes that an LLM is not a product but an engine for features, that the bulk of the work was no different from most product work and was scoped aggressively to meet a one-month deadline, and that the legal and compliance tasks were done in under a month alongside everything else. [11]
  • The Applied LLMs essay states that Honeycomb's Query Assistant initially put a programming manual in the prompt together with n-shot examples, that this worked decently, and that fine-tuning the model led to better output on the syntax and rules of the domain-specific language. [4]

The facts above come from the cited sources. The steps and analysis in this example are our explanation of how they fit together.

Example 2 of 5

GitHub Copilot improving code suggestions by changing what goes into the prompt

GitHubDocumented in an engineering article

GitHub Copilot is a code completion product built on a model from OpenAI. The GitHub Blog article How GitHub Copilot is getting better at understanding your code (May 2023, updated February 2024) describes how GitHub's researchers and engineers improved suggestions by working on the prompt and its context. [12]

The problem

The code that matters to a developer is spread over many files, but the article says that transformers fast enough to power Copilot could process about 6,000 characters at a time. The model also has to answer while the developer is typing. The question was which pieces of the developer's code to put in front of the model, and in what order, to get the most useful suggestion inside that budget and without adding delay.

Where this topic fits

The model layer came from OpenAI (Codex, a descendant of GPT-3 that GitHub gave input on). The work described in the article sits in the prompt and context layers, and the evaluation layer decided what to keep: each technique was tested with A/B experiments on whether developers accepted more suggestions.

How it is applied, step by step

  1. Treat the prompt as something code builds, not something a person types. Algorithms run in the background and can generate a prompt at any point while the developer is coding.
  2. Gather candidate context: snippets and comments from the current file and from other sources.
  3. Prioritise, filter and assemble the candidates into a final prompt that fits the model's limit. This logic lives in what GitHub calls the prompt library.
  4. Add neighbouring tabs: search the files open in the editor for code that matches the code around the cursor, and add the matches to the prompt.
  5. Add fill-in-the-middle: send the code after the cursor (the suffix) as well as the code before it (the prefix), and tell the model which part is which.
  6. Measure each change with an A/B test on suggestion acceptance, and use caching so that the extra context work does not slow suggestions down.

Why this approach fits

GitHub could not retrain the model for each developer's project, and it did not need to. What differs from one developer to the next is the surrounding code, and that can be supplied at request time. Selecting and ordering context is ordinary software (matching, ranking, trimming to a budget) that GitHub's engineers could change and test quickly, and the acceptance rate gave them a number to steer by.

Limitation or tradeoff

The size limit means that not all of a developer's code can be used, so relevant code can be left out. The article reports that a very low bar for including a match worked best, which means the prompt sometimes carries weakly related code. An acceptance rate measures whether developers kept a suggestion, not whether the code was correct. The figures date from 2023 and describe the models and limits of that time.

What the sources document

  • GitHub gave input to OpenAI as it built Codex, a descendant of GPT-3 and the model that would power GitHub Copilot. Copilot launched as a technical preview in June 2021 and became generally available in June 2022. [12]
  • The article says transformers fast enough to power GitHub Copilot can process about 6,000 characters at a time, so not all of a developer's code can be used as context. [12]
  • Prompts are generated by algorithms in the background. A series of algorithms selects relevant snippets or comments from the current file and other sources, which are then prioritised, filtered and assembled into the final prompt. Most of this work takes place in what GitHub calls a prompt library. [12]

The problem

Members wanted quick takeaways from a post, an assessment of their fit for a job, or the latest on a company. Where this topic fits

All five layers appear in the article. Models: smaller ones for routing and retrieval, bigger ones for generation. Prompts: global templates shared by every team. How it is applied, step by step

  1. Fix a three-step pipeline. Routing decides whether the query is in scope and which agent handles it, retrieval decides which services to call, and generation filters the retrieved data and writes the response.

The problem

Generative AI was new enough in practice that it was unclear how to start, how to tell whether a prompt change had helped, and when to pay for a commercial model or run one in-house. Discord wanted a repeatable way to go from an idea to a launched feature quickly, without first building machine learning infrastructure for an idea that might not work.

Where this topic fits

The post describes the working process of AI engineering, not one feature. It begins with the product question, uses an off-the-shelf model to answer it cheaply, puts evaluation between the prototype and the launch, and leaves the ML engineering decision (self-hosting or fine-tuning a model) to the end, when there is evidence that the feature is worth it.

How it is applied, step by step

  1. Look for suitable use cases: problems that involve analysing or interpreting unstructured content at scale, that need scaling which would otherwise be prohibitive, or that are hard for rules-based or traditional ML approaches.
  2. Write product requirements along seven dimensions: latency, task complexity, prompt length, quality, safety, language support and estimated queries per second.
  3. Prototype with an advanced commercial model. The post's reasoning is that if a state-of-the-art model cannot solve the problem, current technology probably cannot, and if it can, the team is free to work on the product instead of on infrastructure.
  4. Iterate on the prompt and judge each change with AI-assisted evaluation: a second, critic prompt sent to a more capable model, which rates the task output with a yes or no answer or a score.
  5. Release to a limited audience, for example as an A/B test, and watch user satisfaction, latency, throughput, error rates (including badly structured output) and cost.
  6. Project the cost of a full launch from the tokens per second used during the limited release.
  7. Decide how to run the feature at scale: stay on the commercial API, or self-host an open-source or fine-tuned model to cut cost and keep data in-house, accepting more development and maintenance work.

Why this approach fits

The order of the stages keeps the slow and expensive work (GPUs, model servers, fine-tuning) behind a cheap test of whether the feature is worth building at all. That is the reversed order of work described earlier in this lesson, written down as one company's method. Putting an evaluation step between the prototype and the launch also answers a problem the post states plainly: after many adjustments to a prompt, it is hard to tell whether the changes are improving the results.

Limitation or tradeoff

The post describes a method and names no specific feature, metric or outcome, so it shows how Discord works but not how well the method performed. AI-assisted evaluation depends on a critic model that can itself be wrong and has to be checked against human judgement. 4Common mistakes

  1. Treating a working demo as a nearly finished product and planning the launch date from it.

    Why it causes problems
    A demo shows the feature working on inputs its author chose. Real users bring inputs nobody anticipated, and the remaining errors are the expensive ones to remove. LinkedIn's team reached 80% of the intended experience in a month and needed four more months for the next stretch, so a plan based on the first month would have been wrong several times over.
    How to recognise it
    A schedule whose only evidence is a demo, no written quality bar, and no measurement on inputs supplied by someone other than the developer.
    How to fix it
    Before committing to a date, write the pass bar, collect a few dozen real or realistic inputs, and measure. Plan for the time needed to close the gap between the measured score and the bar, not the time it took to build the demo.

  2. Shipping with no evaluation set and judging changes by trying a few prompts by hand.

    Why it causes problems
    Each prompt edit fixes the example in front of you and may break others you are not looking at. Without a fixed set of cases there is no way to tell an improvement from a regression, and quality drifts with every change. OpenAI's evaluation guide lists this as an anti-pattern under the name vibe-based evals.
    How to recognise it
    Nobody can say what share of test cases passed before and after the last prompt change, and bug reports from users are the main source of information about quality.
    How to fix it
    Start with 20 to 50 cases drawn from real inputs, each with an expected answer or a property that code can check. Rerun them on every change to the model, prompt, context or tools, and add a case each time a new failure is found.

  3. Reaching for fine-tuning or a custom model before trying prompt, context and tool changes.

    Why it causes problems
    Fine-tuning needs labelled data, training runs and hosting, and the work has to be repeated when the base model is replaced. The Applied LLMs authors report that many of the teams they saw fine-tune early came to regret it. If the real problem was a missing fact, a tuned model still lacks that fact.
    How to recognise it
    A plan that begins with collecting training data while nobody has read the failing outputs to see whether the model lacked instructions, information or access to a system.
    How to fix it
    Sort the failures by cause first. An unclear task is a prompt problem, missing knowledge is a context problem, and missing live data or a missing action is a tool problem. Consider fine-tuning only when the eval score has stopped improving and the remaining failures are about style, syntax or speed.

  4. Treating the model as the product and shipping a chat box in place of a designed feature.

    Why it causes problems
    A general chat interface leaves the user to work out what to ask, widens the range of inputs you must handle, and makes prompt injection attempts easy to try. Honeycomb's write-up says that an LLM is an engine for features, and the team chose not to build a chat interface for reasons of this kind.
    How to recognise it
    The feature is described as "chat with our data", there is no defined task with a checkable output, and the model's raw text is shown to the user without validation.
    How to fix it
    Define one task with a clear input and a verifiable output, place it where the user already works, validate the output in code, and let the user edit or undo the result.

  5. Chaining several model calls without measuring how reliable the whole chain is.

    Why it causes problems
    Errors multiply. Five steps that each succeed 90% of the time succeed together only 59% of the time, and every step adds latency and cost. A design that looks reasonable step by step can be unusable end to end.
    How to recognise it
    Per-step tests pass while end-to-end results are poor, or there are no end-to-end tests at all. Response times are the sum of several multi-second calls.
    How to fix it
    Measure end to end first. Remove steps that one well-specified call can absorb, validate each remaining step's output in code before the next step runs, and improve the weakest step before adding new ones.

  6. Writing one model name into the code in many places and never retesting when the model changes.

    Why it causes problems
    Hosted models are retired on a published schedule, and requests to a retired model fail. The replacement can read the same prompt differently, so a forced migration with no testing can break the feature or quietly lower its quality.
    How to recognise it
    The model id appears as a string in many files, nobody knows the retirement date of the model in use, and there is no record of how the current prompt scores.
    How to fix it
    Put the model id in configuration, note its retirement date, and run the eval set against the replacement well before the deadline, adjusting prompts where scores fall.

import re
import sys

import returns_helper as app

DOCS = {
    "shipping": "Parcels ship within 2 days of payment.",
    "warranty": "Warranty claims are accepted within 365 days of delivery.",
    "returns": app.POLICY,
}


def naive_retrieve(question):
    """Return the first document that shares any word with the question."""
    words = set(question.lower().split())
    for text in DOCS.values():
        if words & set(text.lower().split()):
            return text
    return ""


def build_prompt(question, retrieve):
    return [app.INSTRUCTIONS, "POLICY: " + retrieve(question),
            "TOOLS: lookup_order(order_id)", "QUESTION: " + question]


def answer(question, retrieve):
    parts = build_prompt(question, retrieve)
    reply = app.stub_model("\n".join(parts))
    if reply.startswith("CALL lookup_order"):
        parts.append("TOOL RESULT: " + app.lookup_order(reply.split()[-1]))
        reply = app.stub_model("\n".join(parts))
    return reply


def evaluate(name, retrieve):
    failed = []
    for order_id, days, expected in app.EVAL_SET:
        question = f"I received order {order_id} {days} days ago. Can I still return it?"
        if answer(question, retrieve) != expected:
            failed.append(order_id)
    passed = len(app.EVAL_SET) - len(failed)
    print(f"{name}: {passed}/{len(app.EVAL_SET)} correct, failed: {', '.join(failed) or 'none'}")
    return passed

    evaluate("naive retrieval", naive_retrieve)

def stems(text):
    """Lower-case words with a trailing s removed, so 'Returns' matches 'return'."""
    return {word.rstrip("s") for word in re.findall(r"[a-z0-9]+", text.lower())}


def better_retrieve(question):
    """Return the document that shares the most word stems with the question."""
    return max(DOCS.values(), key=lambda text: len(stems(question) & stems(text)))

1. Cost. Cost per ticket = (input tokens × input price + output tokens × output price) ÷ 1,000,000. The month has 20,000 × 30 = 600,000 tickets.

DesignInput costOutput costPer ticketPer month
A3,500 × 2 ÷ 1,000,000 = $0.0070300 × 10 ÷ 1,000,000 = $0.0030$0.0100$6,000
B3,500 × 4 ÷ 1,000,000 = $0.0140300 × 20 ÷ 1,000,000 = $0.0060$0.0200$12,000
C5,100 × 2 ÷ 1,000,000 = $0.0102370 × 10 ÷ 1,000,000 = $0.0037$0.0139$8,340

In all three designs the input side costs more than the output side. That is the opposite of the single-reply example in the lesson, because each request here carries a long context and asks for a short answer.

2. Success rate. A: 176 ÷ 200 = 88.0%. B: 186 ÷ 200 = 93.0%. C: 0.98 × 0.95 × 0.97 = 0.90307, which is 90.3%. Every step of C is at or above 95%, yet the chain is barely above 90%.

3. Drafts to edit each month. A: 12.0% of 600,000 = 72,000. B: 7.0% of 600,000 = 42,000. C: 9.693% of 600,000 = 58,158.

4. Recommendation. A misses the bar. B and C meet it on paper. C is $3,660 a month cheaper than B, but three things count against taking that at face value.

  • The margin is inside the noise. On 200 cases, 90.3% is 180.6 cases against a bar of 180, and a single case is worth 0.5 points. One unlucky ticket puts C below the bar, and a real model does not return identical results on every run. B clears the bar by six cases.
  • The independence assumption is untested. The figure for C was computed from separate step rates, not measured end to end. Run the whole chain on the 200 tickets before trusting it.
  • Latency. C makes three calls in sequence, so the agent waits for three responses instead of one.

One defensible answer is B, if the budget allows $12,000 a month, because it has a real margin and the simplest design. Another is to keep C as a candidate and do more work first: measure it end to end, enlarge the eval set until a 0.3-point margin means something, and improve its weakest step. Raising the drafting step from 0.95 to 0.97 lifts the chain to 0.98 × 0.97 × 0.97 = 0.922. Choosing C only because 90.3 is greater than 90 is not defensible.

5. Improving A. Read the 24 failing drafts before changing anything, and sort them by cause. The 2,800 tokens of retrieved articles are the first suspect. If the failures cluster on tickets where the retrieved articles were wrong or missing, the fix is in the context layer (better retrieval). If the right articles were present and the draft ignored them or took the wrong tone, the fix is in the prompt layer. If the drafts were wrong about the customer's order or account, the model needs a tool. Only when the failures show no pattern that these layers can fix is the stronger model of design B the right place to spend.

Check your answer

  • Did you get 0.0100, 0.0200 and 0.0139 dollars per ticket for designs A, B and C?
  • Is your success rate for design C 90.3%, found by multiplying 0.98, 0.95 and 0.97?
  • Did you get 72,000, 42,000 and 58,158 drafts to edit per month?
  • Does your recommendation point out that design C's margin over the bar is smaller than one eval case?
  • Does your answer to question 5 begin with reading the failing drafts and name a specific layer?
