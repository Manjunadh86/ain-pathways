Chunking and Document Ingestion

Document ingestion is the offline pipeline that turns source files into searchable index entries: it parses each file into text, splits the text into chunks, attaches metadata, embeds each chunk and writes the result to an index. Chunking is the splitting step, which decides what one retrievable piece of text is.

1Overview

Why it matters

A retrieval system can only return what ingestion stored. If the parser turned a table into loose cell values, or the chunker cut a sentence so that "Card refunds take 5 to" sits in one chunk and "7 business days" in the next, no retriever, reranker or prompt will bring the right passage back. When a RAG answer is wrong, the first thing to check is whether a chunk containing the answer exists in the index at all. Often it does not, and the fault lies in a stage that ran weeks before the question was asked.

Ingestion also sets the cost and the freshness of the system. Chunk size and overlap decide how many vectors are stored and how many tokens each retrieved result adds to a prompt. The sync logic decides whether a policy edited on Monday can be answered correctly on Tuesday, and whether a document deleted last month is still being quoted. Anyone who builds, debugs or reviews a RAG system needs to be able to read a chunk, say why its boundaries are where they are, and say how it would be replaced if its source changed.

Before you start

  • Retrieval-Augmented Generation (RAG)Intermediate

What you will be able to do

  • Describe the stages of an ingestion pipeline (parse, chunk, enrich, embed, write, sync) and what each one produces.
  • Calculate how many chunks a document yields for a given chunk size and overlap, and how much overlap enlarges the index.
  • Compare fixed-size, recursive, structure-aware, semantic and hierarchical chunking and choose one for a given kind of document.
  • Decide which metadata a chunk needs for citation, context, filtering and synchronisation.
  • Implement hash-based change detection that skips unchanged chunks, embeds new ones and deletes removed ones.
  • Recognise parsing, boundary and staleness failures from their symptoms in retrieval results.

Key terms

Ingestion
The offline work of turning source documents into index entries, covering parsing, chunking, metadata, embedding, writing to the index and later re-synchronisation.
Parsing
Converting a file such as a PDF or web page into text plus structure, for example which lines are headings and where a table begins and ends.
Chunk
One piece of a document that is embedded, stored and retrieved as a unit. It is what the model is shown when a search matches.
Chunk size
The maximum length of a chunk, counted in tokens, characters or words depending on the tool.
Overlap
Text repeated from the end of one chunk at the start of the next, so that a passage no longer than the overlap always appears whole in at least one chunk.
Structure-aware chunking
Splitting at boundaries the document already has, such as headings, list items, table edges or the functions in source code.
Semantic chunking
Splitting where the meaning changes, found by embedding neighbouring sentences and cutting where their embeddings differ most.
Hierarchical chunking
Storing small child chunks for matching together with the larger parent chunks they belong to, and returning the parent to the model. Also called parent-child chunking.
Metadata
Fields stored beside a chunk's text and vector, such as its source, heading path, page number, access group and content hash.
Incremental sync
Updating an index by processing only the documents that were added, changed or deleted since the last run, in place of rebuilding everything.

2Explanation

Introduction

In Retrieval-Augmented Generation you saw the two halves of a RAG system: an offline step that builds an index, and an online step that searches it and writes an answer. That lesson treated the index as given. This one is about how it gets built, and above all about the decision that shapes everything retrieved later: what counts as one piece of text.

Think of the index at the back of a textbook. It does not send you to the whole book, and it does not send you to single words. It sends you to pages, a unit small enough to read quickly and large enough to make sense. Somebody chose that unit, and somebody updates the index for each new edition. Document ingestion is the same job done by a program, and a chunk is its version of the page.

There are two reasons to split documents at all. Embedding models accept a limited amount of text: Microsoft's chunking guide (opens in a new tab) gives 8,191 tokens for Azure OpenAI's text-embedding-3-small model. And a document that fits is still often represented poorly by a single vector. The same guide uses the example of a wiki page covering many sub-topics, which retrieves better when it is indexed at a finer grain.

An ingestion pipeline has five stages, plus a sixth that runs for as long as the system is in use:

  1. Parse each source file into text and structure.
  2. Chunk the text into retrievable units.
  3. Enrich each chunk with metadata such as its source, heading and page.
  4. Embed each chunk into a vector.
  5. Write vectors, text and metadata to the index.
  6. Sync when sources are added, edited or deleted.

Every stage can lose information that no later stage can recover. A table flattened by the parser stays flattened. A sentence cut in half by the chunker is embedded in halves. A deleted policy that is never removed from the index keeps being quoted. The sections below take the stages in order: parsing, chunk size and overlap, the main chunking strategies, metadata, and keeping the index fresh. The worked example then runs two chunkers on one small document and counts how much each must re-embed after a one-sentence edit.

How it works

Parsing comes first

A chunker can only split what the parser gives it. Parsing turns a PDF, Word file, web page or spreadsheet into text plus structure: which lines are headings, where a table starts and ends, which page a passage came from.

Plain text extraction throws that structure away. Amazon Bedrock's default parser (opens in a new tab) outputs text only, and AWS recommends one of its other parsers when documents contain figures, charts or tables. Layout-aware tools keep the structure. The open-source unstructured library partitions (opens in a new tab) a file into typed elements such as Title, NarrativeText, ListItem and Table. Azure AI Search's Document Layout skill (opens in a new tab) returns Markdown sections, each labelled with the headings above it.

Product options change. AWS now also offers Bedrock Managed Knowledge Bases (opens in a new tab), where the service runs the ingestion pipeline with a built-in parser for multimodal files, and its comparison table lists built-in or fixed-size chunking for that kind. The Bedrock parser and chunking options in this lesson come from AWS's parsing and chunking pages, so check which kind of knowledge base you are creating.

Before tuning anything else, open the parsed output of a few documents, including the messiest one. Look for tables that became loose cell values, two columns read as one line, page headers repeated inside the text, and scanned pages that produced nothing. Parsing has a cost side too. Layout models and OCR are slower than text extraction, and the unstructured documentation recommends its fast strategy for PDFs whose text can be extracted directly.

Chunk size and overlap

Chunk size is counted in tokens (see Tokens and Context Windows), characters or words. The hard ceiling is the embedding model's input limit, but useful sizes are far below it, because an embedding is a single vector for the whole chunk:

  • A small chunk holds one idea, so its vector matches a specific question closely. It may be too short to make sense alone.
  • A large chunk carries its own context, but its vector blends several topics, and every retrieved hit uses more of the prompt.

Documented starting points differ widely, which shows that there is no universal answer:

ProductDocumented default or starting point
Amazon Bedrock Knowledge Basesabout 300 tokens, keeping sentences whole
Azure AI Search guidance512 tokens with 25% overlap (128 tokens)
OpenAI vector stores800 tokens with 400 tokens of overlap
unstructuredat most 500 characters per chunk

Overlap repeats the end of one chunk at the start of the next. A passage no longer than the overlap then appears whole in at least one chunk, wherever the boundaries fall; a longer passage can still be cut in every chunk. The price is a larger index. For a document of LLL tokens that is longer than one chunk, with chunk size sss and overlap ooo, the number of chunks is

n=⌈L−os−o⌉n = \left\lceil \frac{L - o}{s - o} \right\rceiln=⌈s−oL−o​⌉

so the index grows by a factor of about s/(s−o)s / (s - o)s/(s−o): 1.33 at 25% overlap and 2.0 at 50%. Azure's guide shows the effect on a real e-book. Chunks of 1,000 characters produced 172 chunks without overlap and 216 with 200 characters of overlap, a ratio of 1.26 against a predicted 1.25.

Does the repeated text help retrieval? Chroma's chunking evaluation (opens in a new tab) measured token-level recall (the share of relevant tokens that were retrieved) and precision (the share of retrieved tokens that were relevant) over 472 questions.

Recall stayed between 85% and 90% in all four settings, while precision rose more than fourfold as chunks shrank and overlap was removed. The same report also found pressure in the other direction. With a small embedding model and 250-token chunks, removing overlap lowered one splitter's recall from 82.4% to 77.1%. A sensible start is a few hundred tokens with 0 to 25% overlap, followed by measurement on your own questions (see Evaluating RAG Systems).

Five ways to choose boundaries

  • Fixed-size chunking counts tokens and cuts. It needs no knowledge of the document.
  • Recursive splitting tries large units first. LangChain's RecursiveCharacterTextSplitter (opens in a new tab) keeps paragraphs whole, falls back to sentences when a paragraph is too long, and then to words. LangChain recommends it as the place to start.
  • Structure-aware chunking uses the document's own outline: Markdown headers, HTML tags, or the functions and classes in code. The by_title strategy in unstructured never puts text from two sections into one chunk and keeps every table separate. It depends on a parser that found the structure.
  • Semantic chunking looks for changes of topic. The text is split into sentences, each sentence is embedded together with a few neighbours, and a boundary is placed wherever the distance between consecutive embeddings passes a percentile threshold (the 95th in the LlamaIndex example (opens in a new tab)). It adds embedding work at ingestion and is not automatically better. In Chroma's main results table the semantic chunker that LangChain later adopted had the lowest recall, 83.6%, while the report's own cluster-based variant reached 91.3%.
  • Hierarchical (parent-child) chunking indexes small child chunks for precise matching and gives the model the larger parent they came from. Amazon Bedrock Knowledge Bases and LlamaIndex's HierarchicalNodeParser both offer it.

These combine. A common design splits by structure first and applies a size limit inside any section that is still too long, as the worked example does. A further option is to generate a short piece of context for every chunk and embed it together with the chunk. Anthropic's Contextual Retrieval (opens in a new tab) does this, and Advanced Retrieval covers it.

Metadata travels with the chunk

A chunk is stored as text, a vector and metadata fields. The fields do four jobs:

JobTypical fields
Cite and reassemblesource URL or id, page number, position in the document
Give contextdocument title, heading path
Filterdepartment, date, language, access group
Synchronisecontent hash, last-modified time, pipeline version

Two rules prevent most metadata mistakes. Text that should influence vector matching, such as the heading path, must be part of what is embedded, because an embedding is computed from the chunk text alone and a vector search never looks inside a stored field. (A keyword index can be built over chosen fields. Uber's Genie, described below, runs BM25 over summaries, FAQs and keywords kept as metadata.) Values used for filtering must be stored as fields, because a filter cannot read them out of prose. Access control is the filter that matters most. If one index holds documents meant for different audiences, every chunk has to carry the access group of its source, so that retrieval can exclude what the asker may not see.

Keeping the index fresh

An index is a copy of the source, and copies go stale. Each sync has to answer three questions about every document: is it new, has it changed, has it gone? Amazon Bedrock's sync documentation (opens in a new tab) gives the standard answers. An unchanged document is skipped. A changed one is parsed, chunked, embedded and indexed again. A new one is ingested, and a deleted one is removed from the vector store.

  • Detecting change. Compare a timestamp or a content hash with the value recorded at the last sync. Azure's blob indexer uses each blob's LastModified time. LangChain's index function (opens in a new tab) hashes content and metadata and keeps the result in a record manager. LlamaIndex's IngestionPipeline (opens in a new tab) stores a map from document id to document hash.
  • Replacing, not appending. When a document changes, its old chunks must be removed. Give every chunk a source id so that they can be found.
  • Deletions. A deleted file produces nothing to process, so it is the case most often missed. Azure's documentation states that its indexer does not track deletions (opens in a new tab) unless a soft-delete policy is configured. In LangChain, incremental cleanup only tidies sources seen in the current run, so removing vanished sources needs full mode and a loader that returns the whole dataset.
  • Reusing work. Cache embeddings by chunk hash, so that an edit to one section does not re-embed the rest of the file.

Changing the embedding model, the chunking settings or the parser is a different situation. Every stored chunk is affected, so build a new index beside the old one and switch over when it is complete.

Worked example: One edit, two chunkers: what has to be re-embedded?

The document is a short returns handbook in Markdown. Version 2 adds one sentence to the Refunds section. We chunk both versions in two ways, with fixed-size windows and by heading, then compare chunk hashes to see what a sync would have to do. Words stand in for tokens so that the script needs only the Python standard library (3.9 or later). Save it as chunk_sync.py.

python
import hashlib
import math
import re

DOC_V1 = """# Returns Handbook
## Eligibility
Items can be returned within 30 days of delivery. The item must be unused and in its original packaging. Sale items can be returned within 14 days only.
## Refunds
Refunds go back to the original payment method. Card refunds take 5 to 7 business days. Store credit is issued within 24 hours.
### Exceptions
Gift cards and custom orders cannot be refunded. Shipping fees are refunded only when the item arrived damaged.
## Contact
Email support@example.com with your order number. Phone support is open on weekdays from 9 to 5.
"""
DOC_V2 = DOC_V1.replace("Store credit", "PayPal refunds take 3 days. Store credit")
HEADING = re.compile(r"(#+) (.+)")
SIZE, OVERLAP = 25, 5


def fixed_chunks(text, size, overlap):
    """Windows of `size` words. Each window repeats the last `overlap` words of the one before."""
    words = text.split()
    starts = range(0, max(len(words) - overlap, 1), size - overlap) if words else []
    return [" ".join(words[i:i + size]) for i in starts]


def heading_chunks(markdown, size=40, overlap=8):
    """One chunk per section, prefixed with its heading path. Long sections fall back to windows."""
    chunks, path, body = [], (), ""
    for line in [*markdown.splitlines(), "# END"]:
        heading = HEADING.fullmatch(line)
        if not heading:
            body = f"{body} {line}"
            continue
        label = " > ".join(path)
        chunks = [*chunks, *(f"[{label}] {piece}" for piece in fixed_chunks(body, size, overlap))]
        depth = len(heading.group(1))
        path, body = (*path[:depth - 1], heading.group(2)), ""
    return chunks


def key(chunk):
    return hashlib.sha256(chunk.encode("utf-8")).hexdigest()[:8]


def sync_plan(old_chunks, new_chunks):
    old, new = {key(c) for c in old_chunks}, {key(c) for c in new_chunks}
    return {"keep": len(old & new), "embed": len(new - old), "delete": len(old - new)}


def plain(markdown):
    """Drop the # marks and keep each heading as a short sentence."""
    return HEADING.sub(r"\2.", markdown)


if __name__ == "__main__":
    words = len(plain(DOC_V1).split())
    fixed_v1 = fixed_chunks(plain(DOC_V1), SIZE, OVERLAP)
    expected = math.ceil((words - OVERLAP) / (SIZE - OVERLAP))
    print(f"{words} words -> {len(fixed_v1)} fixed chunks (formula: {expected})")
    print("stored words:", sum(len(chunk.split()) for chunk in fixed_v1))
    print("fixed chunk 2:", fixed_v1[1])
    sections_v1 = heading_chunks(DOC_V1)
    for chunk in sections_v1:
        print(key(chunk), chunk[:58])
    print("fixed sync:  ", sync_plan(fixed_v1, fixed_chunks(plain(DOC_V2), SIZE, OVERLAP)))
    print("heading sync:", sync_plan(sections_v1, heading_chunks(DOC_V2)))

What to notice:

  • Chunk count. The text has 91 words. With s=25s = 25s=25 and o=5o = 5o=5 the formula gives ⌈(91−5)/20⌉=5\lceil (91 - 5) / 20 \rceil = 5⌈(91−5)/20⌉=5 chunks. They store 111 words: the 91 originals plus four overlaps of 5.
  • A bad boundary. Fixed chunk 2 starts in the middle of Eligibility, runs into Refunds and stops at "Card refunds take 5 to". Only the 5-word overlap saves the sentence: chunk 3 starts again at "Card refunds" and holds it whole.
  • Structure-aware chunks. Splitting by heading gives four chunks, one topic each, prefixed with the heading path. The prefix is embedded with the text, so the Exceptions chunk still says that it concerns refunds.
  • The edit. One added sentence shifts every later window, so three of the five fixed chunks get new hashes although only one section changed. With heading chunks only the Refunds chunk changes: one embedding call, one deletion, three chunks skipped.

sync_plan is incremental sync in three set operations. Hashes present in both versions are kept, hashes only in the new version are embedded and inserted, and hashes only in the old version are deleted. A production pipeline stores each hash beside its chunk together with a source id. The comparison is the same.

Edge cases and limitations

A table is larger than the chunk size
The unstructured documentation states that a Table element is never combined with other elements and that an oversized table is divided into TableChunk pieces by text-splitting. Text-splitting cuts by length, so a piece from the middle of a table can arrive without the header row, and a retrieved cell value then has no column name. Raise the size limit for tables, repeat the header in each piece, or index a short summary of the table and return the whole table with it.
Overlap has documented upper limits
OpenAI's guide says the overlap should not exceed half the chunk size, and Azure's Text Split skill requires it to be less than half the page length. At half, every token is already stored about twice. The Azure guide's LangChain example also warns that setting the overlap too large can result in no overlap appearing at all. After changing the setting, read a few consecutive chunks to confirm that the repeated text is really there.
Parent-child retrieval can return fewer results than requested
With hierarchical chunking in Amazon Bedrock Knowledge Bases, matching child chunks are replaced by their parents, and the documentation notes that fewer results may be returned than were requested. Several matching children can share one parent. A request for five results may therefore deliver two long passages. Size the request and the prompt budget for parents, not for children.
One inserted sentence changes every later fixed-size chunk
Fixed windows are positioned by counting from the start of the document, so an insertion moves every boundary after it. A cache keyed on chunk content then misses for all of those chunks, and the sync re-embeds text that did not change. In the worked example three of five chunks change after a one-sentence edit. Boundaries anchored to structure, such as headings or functions, keep an edit local.
Deletion handling added after the first load
Azure's documentation says a deletion detection policy must be in place from the very first indexer run. Documents deleted before the policy existed stay in the index even if the policy is added later, and the suggested remedy is a new index. The same page notes that restoring a soft-deleted blob, or renaming a directory in Data Lake Storage, does not update timestamps, so the indexer may not pick the content up again. Design and test deletion and rename handling before the first ingestion.
The index lags behind a finished sync
A sync that reports success is not always visible to queries at once. OpenAI's Retrieval guide says that removing a file from a vector store is eventually consistent and that results may include its content for a short period. The Amazon Bedrock guide says newly synced embeddings can take a few minutes to become available with some vector stores. A test that edits a document and queries immediately can fail for this reason alone, so poll for the change before asserting on it.

When to use it, and when something simpler is enough

Use it when

  • The corpus is too large to place in a prompt, or single documents exceed the input limit of the embedding model.
  • Documents cover several topics each, so that one vector per document would match most questions only weakly.
  • Sources change while the system is in use and answers must reflect the current version, which calls for incremental sync and deletion handling.
  • Answers must cite a page or section, so each retrievable unit needs a known position in its source.

Think twice when

  • The whole knowledge base fits in the model's context. Anthropic's Contextual Retrieval article suggests including the entire knowledge base in the prompt when it is under about 200,000 tokens.
  • Each record is already a small self-contained unit, such as an FAQ entry, a support ticket or a product row. Index one record per vector and skip the chunker.
  • The content is better searched exactly or queried as data, for example identifiers and code symbols with keyword search, or tables of numbers with SQL.

A simpler alternative. Use a recursive splitter at a few hundred tokens with little or no overlap, attach the source and title as metadata, and rebuild the whole index whenever anything changes. This stops being enough when a full rebuild takes longer than the staleness you can accept or costs too much to repeat, or when evaluation shows answers lost to split tables and sections. Add incremental sync for the first problem and structure-aware parsing and chunking for the second.

Key takeaways

  • Ingestion decides what retrieval can find: content that was lost in parsing or split badly in chunking cannot be recovered by a better retriever or prompt.
  • Read the parsed output before tuning anything else, because tables, columns and headings are where parsers most often lose structure.
  • Chunk size trades precise matching against self-contained context, and overlap protects sentences at boundaries at the price of a larger index.
  • Boundaries that the document already has, such as headings, usually make better chunks than a fixed count, with a size limit applied only inside sections that are still too long.
  • Every chunk should carry metadata for citation, context, filtering and synchronisation, and anything meant to affect vector matching must be part of the embedded text.
  • An index stays fresh only if each sync skips unchanged content, replaces the chunks of changed documents and removes the chunks of deleted ones.

Example 1 of 5

OpenAI vector stores: fixed-size chunks with overlap as a hosted default

OpenAIDocumented in official docs

OpenAI's Retrieval guide documents vector stores, the containers behind its Retrieval API and its file search tool. The guide describes what happens to a file when it is added to a vector store and which chunking settings a developer can change. [11][12]

The problem

A developer wants semantic search over uploaded files without building a parsing, chunking and embedding pipeline. The service therefore has to split every supported file type automatically, with a rule that needs no knowledge of a document's structure, and it has to let the developer change that rule when the default does not suit the content. Storage is what the guide says is billed, so the rule also decides what an index costs.

Where this topic fits

Chunking happens inside the service when a file is attached to a vector store, before its chunks are embedded and indexed. The developer's controls are the chunking_strategy passed when adding the file and the attributes stored with it. At query time a search returns matching chunks with similarity scores and the file each came from.

How it is applied, step by step

  1. A developer uploads a file and attaches it to a vector store. The service chunks, embeds and indexes it without further input.
  2. With no strategy given, each file is cut into chunks of up to 800 tokens, and each chunk shares 400 tokens with the one before it.
  3. By the formula in this lesson, 50% overlap stores each token about twice, so the indexed text is roughly double the source text. This is our calculation, not a figure from the guide.
  4. A developer who wants different behaviour passes a static chunking strategy with a chunk size between 100 and 4,096 tokens and an overlap of at most half that size.
  5. Attributes attached to a file, such as a department, let a search filter by file before the semantic comparison runs.
  6. To apply a new chunk size to a file that is already indexed, a typical approach is to remove the file from the vector store and add it again, because the strategy is set when a file is added.

Why this approach fits

Fixed-size chunking needs no knowledge of structure, so one rule can be applied to every supported file type. A large overlap is a cautious default for a service that cannot see where its boundaries fall: any passage shorter than the overlap appears whole in at least one chunk. Sizes counted in tokens also make storage easy to predict from a file's token count.

Limitation or tradeoff

The default roughly doubles the stored text, and a retrieved 800-token chunk usually contains much more than the question needs. Chroma's 2024 evaluation, which assumed a token-based splitter, reported slightly below-average recall and the lowest scores on its other metrics for 800-token chunks with 400 tokens of overlap. Fixed windows also ignore headings and tables. Attributes belong to the file, not to individual chunks, so they cannot record a page or section. The guide notes that file removal is eventually consistent, so a replaced file can briefly still appear in results. A comment in the guide's Ruby batch sample says live validation of per-file batches returned default chunking despite overrides, and the sample reads the file back and raises an error if the requested strategy is missing. After any per-file override, read the stored chunking strategy back instead of assuming it was applied.

What the sources document

  • The guide states that when a file is added to a vector store it is automatically chunked, embedded and indexed, and that vector stores power semantic search for the Retrieval API and the file search tool. [11]
  • By default max_chunk_size_tokens is 800 and chunk_overlap_tokens is 400, which the guide describes as every file being split into 800-token chunks with 400-token overlap between consecutive chunks. [11]
  • A chunking_strategy can be set when adding files to a vector store. max_chunk_size_tokens must be between 100 and 4096 inclusive, and chunk_overlap_tokens must be non-negative and should not exceed half of max_chunk_size_tokens. [11]
  • Each vector store file can have attributes, a dictionary of at most 16 keys with a limit of 256 characters each, which can be used for attribute filtering in semantic search. Storage is charged according to the size of parsed chunks and their embeddings. [11]
  • Chroma's report cites OpenAI's documented default of 800-token chunks with 400 tokens of overlap and, assuming a token-based splitter, observes slightly below-average recall and the lowest scores on all its other metrics for that setting. [12]

The facts above come from the cited sources. The steps and analysis in this example are our explanation of how they fit together.

Example 2 of 5

Amazon Bedrock Knowledge Bases: a parser and a chunking strategy chosen per data source

Amazon Web ServicesDocumented in official docs

The Amazon Bedrock user guide and API reference describe how a knowledge base ingests a data source. A parsing option and a chunking strategy are configured for the data source, and an ingestion job applies them before embedding. [4][5][8][9][10]

The problem

A managed service has to ingest very different content for different customers: plain text files, PDFs full of tables and charts, and collections in which each file is already one record. One fixed rule cannot serve all of them. Small chunks match precisely but give the model little context, and large chunks do the reverse.

Where this topic fits

Parsing and chunking are settings of the data source. During ingestion the service splits each document according to the chosen strategy, embeds the chunks and writes them to a vector index while keeping a mapping to the original document. With hierarchical chunking the concept reaches into retrieval as well, where matching child chunks are swapped for their parents.

How it is applied, step by step

  1. Choose a parser for the data source. The default parser extracts text only and has no usage charge. Amazon Bedrock Data Automation or a foundation model can be chosen when documents contain figures, charts or tables.
  2. Choose a chunking strategy: fixed-size, hierarchical, semantic or none. Default chunking produces chunks of about 300 tokens that keep sentences whole.
  3. For hierarchical chunking, set a maximum token size for the parent layer and for the child layer, plus the number of tokens that adjacent chunks in the same layer share.
  4. For semantic chunking, set the maximum tokens per chunk, a buffer size (how many neighbouring sentences are embedded with each sentence) and a breakpoint percentile threshold.
  5. Run the ingestion job. The chunks are embedded and written to the vector index.
  6. At query time with hierarchical chunking, the service searches the child chunks and returns their parents, so the model receives the wider passage.

Why this approach fits

Making the strategy a setting of each data source lets one service handle unlike collections without custom code: sentence-bounded chunks for general prose, parent-child chunks where a precise match needs surrounding context, and no chunking where each file is already a unit. Hierarchical chunking answers the size tradeoff directly, because the text that is embedded is small and the text handed to the model is large.

Limitation or tradeoff

Each option has a documented cost or restriction. Semantic chunking uses a foundation model during ingestion and is charged for it. Choosing Data Automation or a foundation model as the parser applies it to every PDF in the data source, including PDFs that contain only text. Hierarchical chunking can return fewer results than requested, is not recommended with an S3 vector bucket as the vector store, and can meet metadata size limits when the layers are large. With no chunking, page numbers are not available for citations or filtering. The options also depend on the kind of knowledge base, as the note on Bedrock Managed Knowledge Bases in the parsing section explains.

What the sources document

  • The default parser only parses text in text files and incurs no usage charge. AWS recommends Amazon Bedrock Data Automation or a foundation model as the parser when documents include figures, charts, tables or images. [5]
  • If Data Automation or a foundation model is chosen as the parser, it is used for all PDF files in the data source, even those that contain only text, and the account is charged for that parsing. [5]
  • The valid chunking strategies in the API are FIXED_SIZE, NONE, HIERARCHICAL and SEMANTIC. Default chunking splits content into chunks of approximately 300 tokens while honouring sentence boundaries, and with no chunking each document is treated as a single chunk. [4][8]

  • Semantic chunking takes a maximum token count, a buffer size and a breakpoint percentile threshold. A buffer size of 1 means three sentences (previous, current and next) are embedded together, and the guide notes additional costs because the strategy uses a foundation model. [4]

unstructured: partitioning files into typed elements, then chunking by title

UnstructuredDocumented in an open-source project

unstructured is an open-source Python library for preparing documents for retrieval. Its documentation describes two separate steps: partitioning a file into typed elements, and chunking those elements. [18][17]

The problem

A text splitter sees only characters. In PDFs, Word files and HTML pages, the boundaries that matter (a section heading, a list item, the edge of a table) are not reliably marked by blank lines. Splitting on newline patterns therefore breaks tables apart and attaches headings to the wrong text.

Where this topic fits

The library covers the first two stages of the pipeline. Partitioning is the parsing stage and produces a list of elements with metadata. Chunking runs on those elements and produces chunks ready for embedding. The documentation notes that chunking is typically faster than partitioning, which is why the two can be run separately while tuning chunk settings.

How it is applied, step by step

  1. Call a partition function on the file. The generic `partition` function detects the file type and routes the file to the matching format-specific function.
  2. For PDFs, choose a strategy. `fast` extracts the embedded text, `hi_res` runs a layout detection model and is the only strategy that extracts tables, and `ocr_only` runs OCR.
  3. The result is a list of elements such as `Title`, `NarrativeText`, `ListItem` and `Table`, each with metadata such as its page number.
  4. Call `chunk_by_title` on the elements. Consecutive elements are combined until the size limit is reached.
  5. A `Title` element closes the current chunk and starts a new one, so no chunk mixes two sections. A table always forms a chunk of its own.
  6. Only an element that is larger than the limit by itself is cut by plain text-splitting.
  7. Each chunk can keep its original elements in `metadata.orig_elements`, so page numbers and coordinates can be read back for citations.

Why this approach fits

Chunk boundaries are placed where the document's author put them. Because whole elements are the building blocks, a paragraph or list item is never cut unless it is too long by itself, and a heading stays with the text that follows it. Separating the slow step (layout analysis) from the fast step (combining elements) also makes it cheap to try several chunk sizes on the same parsed output.

Limitation or tradeoff

The result is only as good as the element classification. The documentation notes that partitioning may label a list item or short paragraph as a Title, which produces chunks much smaller than intended unless small sections are combined. It also notes that hi_res has difficulty ordering elements in documents with multiple columns. Layout detection and OCR need extra dependencies and time. An oversized table is still divided by text-splitting, and a chunk built from several elements no longer has a single page number or position.

What the sources document

  • Partitioning functions break a document into elements such as Title, NarrativeText and ListItem, and the generic partition function detects the file type and invokes the appropriate partitioning function. [18]
  • For PDFs the hi_res strategy identifies the document layout with a detection model and is described as the only strategy that currently extracts tables, the fast strategy extracts text with pdfminer and is recommended for most PDFs with extractable text, and ocr_only runs the document through Tesseract. [18]
  • The chunking documentation says the library only resorts to text-splitting when a single element exceeds the maximum chunk size, and that otherwise every chunk contains one or more whole elements. max_characters defaults to 500 and overlap defaults to 0. [17]
  • With the by_title strategy a single chunk never contains text from two different sections: a Title element closes the prior chunk and starts a new one. By default a page break does not start a new chunk, and sequential small sections are combined. [17]
  • A Table element is always isolated and never combined with another element, an oversized table is divided into TableChunk elements by text-splitting, and the original elements of a chunk can be accessed through metadata.orig_elements with their page numbers and coordinates. [17]

Cursor's codebase index (January 2026): Merkle-tree sync and a chunk-level embedding cache

CursorDocumented in an engineering article

An article on Cursor's blog from January 2026 describes how the editor built and maintained a semantic index of a user's codebase. Cursor's documentation, read in October 2026, describes a different search design, so this example documents the indexing system as the article presents it. [20][21]

The problem

Code changes constantly, and a large repository can hold tens of thousands of files. The article says that indexing such a repository naively can take hours. Reading and embedding everything again after each edit is not an option, and even sending a full list of file hashes on every update means moving megabytes of data.

Where this topic fits

The concept is the sync stage, applied at two levels. A Merkle tree finds which files differ between the client's copy of the code and the server's index. Inside a changed file, chunking and a cache keyed on chunk content decide which chunks need new embeddings.

How it is applied, step by step

  1. The client hashes every file and computes a hash for each folder from the hashes of its children, up to a single root.
  2. On a sync, the client's hashes are compared with the server's to find where the two trees diverge. A typical implementation starts at the root and does not descend into a folder whose hash matches.
  3. Entries whose hashes differ are synced. Entries missing on the client are deleted from the server, and entries missing on the server are added.
  4. A changed file is split into syntactic chunks, which follow the structure of the code.
  5. Embeddings are cached by chunk content, so only chunks that are not already in the cache are embedded. That work runs in the background.
  6. For a new teammate, the server finds an existing index of a similar codebase, copies it and then syncs the differences.

Why this approach fits

The cost of a sync follows the size of the change, not the size of the repository. An edit to one file changes the hashes on a single path from that file to the root, and every other branch is skipped. Chunking along syntactic units means that an edit inside one function usually leaves the chunks of other functions byte-identical, which is what makes a cache keyed on content effective. The worked example in this lesson shows the opposite case, where fixed windows shift and such a cache would miss.

Limitation or tradeoff

A hash tree detects that content changed, not whether the change matters, so reformatting a file produces new chunks to embed. Reusing a teammate's index needed extra machinery to stop results appearing for files a user does not have. Most importantly, the Search page of Cursor's documentation in October 2026 does not describe this index. It describes Instant Grep, a search built on a local index for exact and regex matching, and states that Cursor does not store embeddings of the codebase for search. An embedding index has to be kept in sync for as long as it exists, and searching the files directly removes that work.

What the sources document

  • The article says Cursor builds its view of a codebase with a Merkle tree that has a cryptographic hash of every file and hashes of each folder based on the hashes of its children, which lets it detect which files and directories changed without reprocessing everything. [20]
  • Cursor compares the client's hashes with the server's version to see where the trees diverge. Entries whose hashes differ are synced, matching entries are skipped, entries missing on the client are deleted from the server and entries missing on the server are added. For fifty thousand files, file names and SHA-256 hashes come to roughly 3.2 MB. [20]
  • When a file changes, Cursor splits it into syntactic chunks that are converted into embeddings in the background. Embeddings are cached by chunk content, so unchanged chunks hit the cache. [20]
  • The article reports that clones of the same codebase average 92% similarity across users in an organisation, and that reusing a teammate's index cut median time-to-first-query from 7.87 seconds to 525 milliseconds and the 99th percentile from 4.03 hours to 21 seconds. [20]
  • Cursor's search documentation states that Instant Grep builds and queries its index on the user's machine, and that Cursor does not upload file paths or code to build a search index and does not store embeddings of the codebase for search. [21]

4Common mistakes

  1. Tuning chunk size and overlap before reading what the parser produced.

    Why it causes problems
    If tables arrive as loose cell values or two columns are interleaved, every chunking setting produces unusable chunks. Time goes into parameters that cannot fix the problem, and answers that depend on tables stay wrong.
    How to recognise it
    Print the parsed text of the documents behind your worst answers. Look for numbers with no labels, sentences that jump between topics in the middle of a line, and page headers or footers repeated in the body.
    How to fix it
    Change the parsing first: use a layout-aware parser for documents with tables, convert tables to Markdown or HTML, or ingest from a better source format. Choose chunk settings after that.

  2. Copying a product's default chunk size and overlap without measuring on your own questions.

    Why it causes problems
    Documented defaults range from about 300 tokens to 800 tokens with 50% overlap. A setting chosen for someone else's documents can double the index and fill each prompt with text the question did not need.
    How to recognise it
    Retrieved chunks in which the relevant sentence is a small fraction of the text, near-identical passages appearing twice among the top results, or an index several times the size of the source.
    How to fix it
    Collect a small set of real questions with known answer passages, try two or three sizes and overlaps, and compare how often the passage is retrieved and how much other text comes with it.

  3. Embedding chunks that have lost their document title and heading.

    Why it causes problems
    A chunk that says only that revenue grew by 3% does not say which company or period it concerns, so it matches the wrong questions and misleads the model when it is retrieved. Anthropic's Contextual Retrieval article uses this example.
    How to recognise it
    Read ten random chunks with no other information. If you cannot tell which document or section a chunk belongs to, the embedding cannot either.
    How to fix it
    Prefix each chunk with its title and heading path before embedding, as the worked example does, and keep the same values as metadata fields for display and filtering.

  4. Re-ingesting a changed document by adding its new chunks without removing the old ones.

    Why it causes problems
    The index now holds two versions of the same passage. Retrieval can return the outdated one, or both, and the model has no way to know which is current.
    How to recognise it
    Count the chunks per source id before and after a re-ingestion and see the count roughly double. Search results show near-duplicates with different values for the same fact.
    How to fix it
    Store a source id on every chunk and delete or overwrite by that id when the source changes. Compare the stored chunk hashes with the new ones and delete those that no longer appear.

  5. Handling new and changed documents in the sync but not deleted ones.

    Why it causes problems
    A withdrawn policy or a removed page stays searchable indefinitely. The system answers confidently from a source that no longer exists, and the citation leads nowhere.
    How to recognise it
    Delete a test document from the source, run the sync, and search for a phrase that only that document contained. If it still comes back, deletions are not handled.
    How to fix it
    On every sync, compare the full list of source ids with the ids recorded in the index and delete what is missing, or use the deletion mechanism your tool documents, such as a soft-delete policy or a full cleanup mode.

  6. Changing the embedding model or the chunking settings in place on a live index.

    Why it causes problems
    Vectors from two embedding models are not comparable, and chunks made with two settings overlap in content. Until every document has been reprocessed, search quality is unpredictable and partly stale.
    How to recognise it
    Chunks of clearly different sizes for the same source, or a pipeline version field, if you store one, with more than one value in the same index.
    How to fix it
    Record a pipeline version in chunk metadata. For a change that affects every chunk, build a new index beside the old one, check it against your test questions, and then switch the application over.

import re

TEXT = (
    "Items can be returned within 30 days of delivery. The item must be unused and in its original packaging. "
    "Sale items can be returned within 14 days only. Refunds go back to the original payment method. "
    "Card refunds take 5 to 7 business days. Store credit is issued within 24 hours. "
    "Gift cards and custom orders cannot be refunded. Shipping fees are refunded only when the item arrived damaged."
)


def fixed_chunks(text, size, overlap):
    words = text.split()
    starts = range(0, max(len(words) - overlap, 1), size - overlap) if words else []
    return [" ".join(words[i:i + size]) for i in starts]


def count_words(sentences):
    return sum(len(sentence.split()) for sentence in sentences)


def sentence_chunks(text, max_words, overlap_sentences=1):
    sentences = [s for s in re.split(r"(?<=[.!?])\s+", text.strip()) if s]
    chunks, current = [], []
    for sentence in sentences:
        if not current or count_words([*current, sentence]) <= max_words:
            current = [*current, sentence]
            continue
        chunks = [*chunks, " ".join(current)]
        carried = current[-overlap_sentences:] if overlap_sentences else []
        fits = count_words([*carried, sentence]) <= max_words
        current = [*carried, sentence] if fits else [sentence]
    return [*chunks, " ".join(current)] if current else chunks


def report(name, chunks):
    cut = sum(1 for chunk in chunks if chunk[-1] not in ".!?")
    stored = sum(len(chunk.split()) for chunk in chunks)
    print(f"{name}: {len(chunks)} chunks, {stored} stored words, {cut} end mid-sentence")


if __name__ == "__main__":
    print(len(TEXT.split()), "words in the source text")
    report("fixed 25/5   ", fixed_chunks(TEXT, 25, 5))
    report("sentences 25 ", sentence_chunks(TEXT, 25, overlap_sentences=1))
