LlamaIndex Agents and Workflows

LlamaIndex is an open-source Python framework for building LLM applications over your own data. Its agent layer provides pre-built agents (FunctionAgent and AgentWorkflow) that loop over tool calls, and both run on Workflows, an event-driven engine in which steps receive typed events and return new ones.

1Overview

Why it matters

Most business agents are only as good as their access to data. An agent that answers a refund question needs the order record and the right paragraph of the policy, and it needs them without being handed a two-hundred-page manual. LlamaIndex is built around that side of the problem: indexes, retrievers and query engines are its core, and its agents are designed to consume them as tools. If you know how a query engine becomes a tool, you can explain why an agent searched the wrong source or answered from a stale document, and you can fix it in the tool instead of in the prompt.

The library also gives you three levels of control: a single agent that decides everything, a group of agents that hand work to each other, and a workflow in which your own code decides the order of steps. Choosing the wrong level is costly in both directions. A free-running agent is hard to test when the steps are fixed, and a hand-written workflow is wasted effort when a ten-line agent would do. The agent classes were also replaced in 2025, so anyone maintaining a LlamaIndex application has to tell current code from the many older tutorials that no longer run.

Key terms

Query engine
A LlamaIndex object that takes a natural-language question, retrieves from an index or database, and returns an answer. It runs a fixed pipeline and makes no decisions about what to do next.
QueryEngineTool
A wrapper that gives a query engine a tool name, a description and an argument schema so that an agent can call it like any other tool.
FunctionAgent
The pre-built LlamaIndex agent that uses a model's native tool calling. It calls the model, runs the requested tools, feeds the results back and repeats until the model answers.
AgentWorkflow
A pre-built workflow that runs one or more named agents, keeps one of them active at a time, and lets the active agent pass control to another.
Handoff
The act of one agent passing control of the conversation to another. In AgentWorkflow it is an ordinary tool call to a tool named handoff.
Workflow
A Python class whose methods are steps. The engine runs a step whenever an event of the type that step accepts appears, until a step returns a stop event.
Step
An async function marked with the step decorator. Its parameter type says which event it handles, and its return type says which events it may emit.
Event
A small typed data object (a Pydantic model) passed between steps. StartEvent carries the run's inputs and StopEvent carries its result.
Context
The per-run object that holds shared state in a key-value store, lets steps send events and write to the output stream, and can be serialized to resume a run later.
Event stream
The sequence of events a running workflow publishes for the caller, such as model text, tool calls and tool results, read with the handler's stream_events method.

2Explanation

Introduction

In Agentic RAG you made retrieval a tool that an agent chooses to call, and in Choosing an Agent Framework you saw that frameworks differ mainly in how much of the control flow they own. LlamaIndex comes at agents from the data side. Its core package describes itself as an interface between LLMs and your data, and its agents are built to use its indexes and query engines as tools. Building with it usually starts with the question "what data does this agent need, and how will it ask for it?" and only then moves to the agent itself.

The pieces stack up as follows. A query engine answers one question over one data source. A tool gives a query engine, or any Python function, a name and a description that a model can read. A FunctionAgent runs the loop from The Agent Loop over a list of tools. An AgentWorkflow runs several such agents and lets them pass control to each other. Underneath the agents is the Workflows engine, which you can also use directly when you want your own code to decide the order of steps.

Workflows are the part that is new if you have only used agent loops. Picture a restaurant kitchen with a ticket rail. The grill station reacts only to "steak ordered" tickets and puts up a "steak ready" ticket. The pass reacts to "steak ready" and puts up "plate ready". Nobody holds a master script for the evening. The kinds of ticket, and which station accepts which kind, define everything that can happen. In a workflow the tickets are events, the stations are steps, and the engine is the rail: it delivers each event to the step that accepts that type. A loop is a station putting up a ticket that an earlier station accepts, and a branch is a station choosing between two kinds of ticket.

This lesson covers how a query engine becomes a tool, what FunctionAgent and AgentWorkflow do on each iteration, how to write a workflow yourself, and how to choose between these levels. The code targets llama-index-core 0.14 and llama-index-workflows 2.x, the versions current when the lesson was written.

How it works

Two packages, one engine

llama-index-core holds the indexes, query engines, tools and agent classes. PyPI listed 0.14.25 as its latest release when this lesson was written. The engine underneath is a separate package, llama-index-workflows (2.25.0 at the same date), which core depends on and re-exports. So from llama_index.core.workflow import Workflow and from workflows import Workflow name the same class, and you can install the engine alone when you do not need the rest. Both packages require Python 3.10 or later.

Tutorials written before mid-2025 use AgentRunner, FunctionCallingAgent or OpenAIAgent. Core 0.13.0 removed those classes in favour of the workflow-based agents described here.

Query engines become tools

The documentation defines a query engine (opens in a new tab) as a generic interface that takes a natural-language query and returns a response, usually built on an index through a retriever. An agent cannot call it until it is a tool. There are two ways to make it one:

python
from llama_index.core import SimpleDirectoryReader, VectorStoreIndex
from llama_index.core.tools import QueryEngineTool

# Uses the configured embedding model and LLM (OpenAI unless you set others).
index = VectorStoreIndex.from_documents(SimpleDirectoryReader("policies").load_data())
policy_engine = index.as_query_engine(similarity_top_k=3)

policy_tool = QueryEngineTool.from_defaults(          # way 1: the wrapper class
    policy_engine,
    name="refund_policy",
    description="Answers questions about refund, return and warranty rules. "
                "Input: one complete question in plain English.",
)

async def search_policy(query: str) -> str:           # way 2: a plain function
    """Answers questions about refund, return and warranty rules."""
    return str(await policy_engine.aquery(query))

Either way the model sees a name, a description and an argument schema, and nothing else. It never sees the index. The tools guide (opens in a new tab) notes that which tool is selected, and with what arguments, depends strongly on the name and description, and that tuning them can change behaviour a lot. A plain function becomes a tool automatically: its name is the tool name and its docstring is the description.

Retrieval, reranking and answer synthesis all happen inside the tool. The agent receives a short answer, not a pile of chunks. That keeps the agent's context small, at the price of one extra model call inside each tool call. Setting return_direct=True on a tool makes its output the final response and ends the loop.

FunctionAgent: the pre-built loop

python
from llama_index.core.agent.workflow import FunctionAgent
from llama_index.core.workflow import Context
from llama_index.llms.openai import OpenAI

agent = FunctionAgent(
    tools=[policy_tool, order_lookup],     # order_lookup is a plain Python function
    llm=OpenAI(model="gpt-4o-mini"),
    system_prompt="Answer support questions. Use the tools and do not guess.",
)
ctx = Context(agent)                       # holds chat history between runs
response = await agent.run(user_msg="Can I return order A-1042?", ctx=ctx, max_iterations=8)

The agents guide (opens in a new tab) lists what a run does: the agent takes the latest message and the chat history, sends them with the tool schemas to the model, and gets back either a direct response or a list of tool calls. Every tool call is executed, the results join the history, and the model is called again. Four details come from the source (opens in a new tab):

  • Iteration limit. Model turns are counted, and the default limit is 20. When the count reaches the limit the run raises WorkflowRuntimeError. Pass early_stopping_method="generate" to get one final model call that answers from what has been gathered instead.
  • Tool errors. An exception inside a tool is caught and becomes a tool result marked as an error, with the exception text as its content. A call to a tool name that does not exist returns a "not found" result. The model sees both and can correct itself.
  • Several calls per turn. One ToolCall event is sent per requested call, and the agent waits for all results before the next model turn.
  • Model type. FunctionAgent needs a model with native tool calling. ReActAgent prompts for text-formatted actions instead, and AgentWorkflow.from_tools_or_functions picks between them for you.

Without a Context, each run starts with empty history. By default agents keep history in a ChatMemoryBuffer.

What runs underneath

FunctionAgent is itself a workflow with six steps. Each arrow in the diagram is a typed event.

The same events are published to the caller. Keep the handler instead of awaiting it, and iterate handler.stream_events() to receive AgentStream (text deltas), ToolCall and ToolCallResult as they happen. This is how a user interface shows progress while the agent works.

AgentWorkflow: several agents and a handoff tool

python
from llama_index.core.agent.workflow import AgentWorkflow

triage = FunctionAgent(name="Triage", description="Looks up orders and routes questions.",
                       system_prompt="...", llm=llm, tools=[order_lookup], can_handoff_to=["Refunds"])
refunds = FunctionAgent(name="Refunds", description="Decides refunds from the written policy.",
                        system_prompt="...", llm=llm, tools=[policy_tool], can_handoff_to=["Triage"])
team = AgentWorkflow(agents=[triage, refunds], root_agent="Triage", initial_state={"order": None})

AgentWorkflow adds one extra tool, handoff(to_agent, reason), to each agent when there is more than one. Its description lists the agents this one may hand to, with their descriptions. Calling it records the next agent, and the following model turn goes to that agent with the same memory. Only one agent is active at a time, and the multi-agent guide (opens in a new tab) calls this the linear "swarm" pattern. Give every agent in a multi-agent setup a distinct name and a useful description, because those are what the other agents choose from.

initial_state is a dictionary stored in the Context under the key state. At the start of a run its current contents are added to the latest message, and any tool whose first parameter is ctx: Context can read and update it. State is how one agent leaves notes for the next without relying on the transcript.

The same guide describes two alternatives: an orchestrator agent that calls sub-agents as tools, and a custom planner written as a workflow.

Writing your own Workflow

A workflow needs no agent at all. The rules, from the Workflows documentation (opens in a new tab):

  • An event is a Pydantic class. StartEvent receives the keyword arguments of run(), and returning StopEvent(result=...) ends the run with that result.
  • A step is an async method with the @step decorator. Its parameter annotation names the event it accepts and its return annotation names what it may emit. You never declare edges. The engine reads the annotations and validates the graph before running: every produced event needs a consumer and a stop event must be reachable.
  • A branch is a return type of A | B. A loop is a step returning an event that an earlier step accepts.
  • Returning list[Task] fans out to one event per element, run concurrently up to the step's num_workers (4 by default). A step that accepts list[Done] fans in and fires once with the whole batch.
  • ctx.store holds shared state (await ctx.store.get(key), await ctx.store.set(key, value)). ctx.write_event_to_stream(event) publishes progress to the caller.
  • A plain Workflow times out after 45 seconds unless you pass timeout=. The agent classes pass no timeout by default.
python
# Pseudocode skeleton. Draft and Retry are Event subclasses; the worked example is the runnable version.
class ReviewLoop(Workflow):
    @step
    async def write(self, ev: StartEvent | Retry) -> Draft: ...

    @step
    async def review(self, ev: Draft) -> Retry | StopEvent: ...   # Retry loops back to write

Choosing a level

The documentation's advice is to start with AgentWorkflow when prototyping, move to an orchestrator agent when you need more control over the sequence, and write a custom planner only when neither can express the flow. A further rule of thumb, which is ours and not the documentation's: when you already know the order of steps, write it as a workflow and call a model inside the steps.

Designing from the data outward

  • One tool per source or question type. Say in the description what the data covers and what it does not, so that two tools never look interchangeable to the model.
  • Keep retrieval inside the tool. Chunk size, similarity_top_k and reranking are tool settings. Return an answer or a few passages. For APIs that return huge payloads the library offers utility tools such as LoadAndSearchToolSpec, which index the payload and expose a search tool over it.
  • Query structured data as structured data. Use a text-to-SQL query engine limited to named tables, with a read-only database role, instead of embedding rows.
  • Write findings to state. A tool that records what it found in state makes the result available to later steps and to other agents.

Worked example: A two-source refund agent written as an event-driven Workflow, with a scripted model

The task: decide whether order A-1042 can be returned and how much is refunded. There are two data sources, a structured order table and three unstructured policy passages, and each has one query function. The model is replaced by a script of three decisions so that everyone gets the same output and no API key is needed. Everything else is a real workflow: typed events, a loop, shared state, a streamed progress event and a turn limit. Its three steps mirror what FunctionAgent does internally.

Install the engine with pip install llama-index-workflows (Python 3.10 or later) and save this as refund_agent.py:

python
import asyncio
from workflows import Context, Workflow, step
from workflows.events import Event, StartEvent, StopEvent

ORDERS = {"A-1042": {"item": "headphones", "price": 80.00, "days_since_delivery": 12, "opened": True}}
POLICY = [
    "Refunds are accepted within 30 days of delivery.",
    "Opened items are refunded minus a 15 percent restocking fee.",
    "Gift cards are never refunded.",
]


def order_lookup(order_id: str) -> str:
    """Structured data: exact lookup by order id."""
    return str(ORDERS.get(order_id, f"ERROR: unknown order {order_id}"))


def policy_search(query: str, top_k: int = 2) -> str:
    """Unstructured data: the top_k passages sharing the most words with the query."""
    words = set(query.lower().split())
    ranked = sorted(POLICY, key=lambda p: -len(words & set(p.lower().rstrip(".").split())))
    return " ".join(ranked[:top_k])


TOOLS = {"order_lookup": order_lookup, "policy_search": policy_search}
SCRIPT = [  # stands in for the LLM: one decision per model turn
    {"tool": "order_lookup", "args": {"order_id": "A-1042"}},
    {"tool": "policy_search", "args": {"query": "refunds for opened items after delivery"}},
    {"answer": "Refund 68.00: 80.00 minus the 15 percent fee, inside the 30 day window."},
]


class ModelTurn(Event):
    pass


class ToolRequest(Event):
    tool: str
    args: dict


class Progress(Event):
    msg: str


class RefundAgent(Workflow):
    @step
    async def setup(self, ctx: Context, ev: StartEvent) -> ModelTurn:
        await ctx.store.set("history", [f"user: {ev.question}"])
        await ctx.store.set("turns", 0)
        await ctx.store.set("max_turns", ev.get("max_turns", default=6))
        return ModelTurn()

    @step
    async def call_model(self, ctx: Context, ev: ModelTurn) -> ToolRequest | StopEvent:
        turns = await ctx.store.get("turns")
        if turns >= await ctx.store.get("max_turns"):
            return StopEvent(result={"status": "max_turns", "answer": None, "turns": turns})
        decision = SCRIPT[turns]  # a real agent sends the history and tool schemas to an LLM here
        await ctx.store.set("turns", turns + 1)
        if "answer" in decision:
            return StopEvent(result={"status": "finished", "answer": decision["answer"], "turns": turns + 1})
        return ToolRequest(tool=decision["tool"], args=decision["args"])

    @step
    async def run_tool(self, ctx: Context, ev: ToolRequest) -> ModelTurn:
        result = TOOLS[ev.tool](**ev.args)
        history = await ctx.store.get("history")
        await ctx.store.set("history", [*history, f"{ev.tool}: {result}"])
        ctx.write_event_to_stream(Progress(msg=f"{ev.tool} -> {result}"))
        return ModelTurn()


async def run_once(max_turns: int) -> None:
    workflow = RefundAgent(timeout=30)
    handler = workflow.run(question="Can I return order A-1042? How much do I get back?", max_turns=max_turns)
    async for ev in handler.stream_events():
        if isinstance(ev, Progress):
            print(ev.msg)
    print(await handler)


async def main() -> None:
    await run_once(max_turns=6)
    await run_once(max_turns=2)


if __name__ == "__main__":
    asyncio.run(main())

Run python3 refund_agent.py. The first call, with max_turns=6, prints:

text
order_lookup -> {'item': 'headphones', 'price': 80.0, 'days_since_delivery': 12, 'opened': True}
policy_search -> Refunds are accepted within 30 days of delivery. Opened items are refunded minus a 15 percent restocking fee.
{'status': 'finished', 'answer': 'Refund 68.00: 80.00 minus the 15 percent fee, inside the 30 day window.', 'turns': 3}

What to notice:

  • Routing by type. Nothing says "after run_tool, go to call_model". run_tool returns a ModelTurn, and call_model is the step that accepts ModelTurn. That return is the loop.
  • The branch. call_model returns ToolRequest | StopEvent. Which one it returns decides whether the run continues.
  • The data. policy_search scores each passage by shared words. The first two passages share two words each with the query and the gift-card passage shares none, so the top two come back. The order was delivered 12 days ago, inside the 30-day window, and it was opened, so the refund is 80.00 × 0.85 = 68.00.
  • The limit. The second call, with max_turns=2, prints the same two tool lines and then {'status': 'max_turns', 'answer': None, 'turns': 2}. FunctionAgent raises an error at its limit; this workflow returns a status, which is a choice you get to make when you own the steps.

With a real model the three steps collapse into FunctionAgent(tools=[order_lookup, policy_search], llm=llm, system_prompt=...), and Progress is replaced by the built-in ToolCallResult event.

Edge cases and limitations

The iteration limit raises an error by default
FunctionAgent and AgentWorkflow count model turns and raise WorkflowRuntimeError when the count reaches max_iterations, which is 20 unless you pass another value to run(). In an AgentWorkflow the count covers all agents together, so a writer and a reviewer that keep handing work back and forth share one budget. Catch the error and report a stopped run, or pass early_stopping_method="generate" to get a final answer built from what has been gathered so far.
An agent forgets everything between runs unless you reuse the Context
The documentation states that AgentWorkflow is stateless between runs by default. Chat history and the state dictionary live in the Context, so create one with Context(agent) and pass ctx=ctx to every run of the same conversation. To continue later or in another process, serialize it with ctx.to_dict() and restore it with Context.from_dict(). Anything stored must be serializable, so keep clients and indexes out of the state.
A plain Workflow stops after 45 seconds
The Workflow constructor's timeout defaults to 45 seconds, and a run that exceeds it raises a timeout error. A workflow with several model calls or a wait for human input passes that easily. Set timeout to a value based on measured run times, or to None for flows that wait on people. FunctionAgent and AgentWorkflow pass no timeout unless you give one, so the two defaults differ.
Events are matched by exact type
A step annotated with a parent event class does not receive events of a subclass. The documentation says routing is exact by default, to stop a growing event model from changing the flow by accident, and that a step can opt in with accept_event_subclasses=True. If a step never fires, check that the event type returned upstream is exactly the annotated type.
Fan-in results arrive in completion order
When a step returns a list of events and a later step accepts the list of results, the results are in the order the workers finished, not the order they were sent. The documentation's example sorts the list inside the joining step. Carry an index or an id on each event whenever position matters, for example when the results are sections of one report.
Resuming a workflow can run a step twice
A run restored from a saved Context continues from its pending events, and the documentation describes resume as at-least-once: a step that was in progress when the snapshot was taken runs again from the top. The DBOS runtime has the same property because it recovers by replaying a journal. A step that sends an email or charges a card needs an idempotency key or a check in the state before it acts.

When to use it, and when something simpler is enough

Use it when

  • The agent's job is mostly answering from your own data, such as documents, SQL tables or APIs, and you want indexing, retrieval and query engines from the same library that runs the agent.
  • You need explicit control over the order of steps, with loops, branches, parallel work or a pause for a person, and prefer plain async Python with typed events to drawing a graph of nodes and edges.
  • Different stages need different levels of autonomy, for example a fixed ingestion workflow that calls a FunctionAgent for one open-ended step.
  • Callers must see progress as it happens. Every agent and workflow publishes an event stream that a user interface or a logger can consume.

Think twice when

  • One retrieval and one answer are enough. A query engine alone is cheaper and easier to evaluate than an agent that wraps it.
  • Your application is not async Python. Workflows are built on asyncio, and bridging them into a synchronous or non-Python service adds work that a provider SDK with a plain loop avoids.
  • You need durable execution across crashes and deployments and are not prepared to add checkpointing or a runtime plugin. Workflows keep state in memory by default.
  • The team already runs another orchestration framework in production. LlamaIndex query engines can be called from any framework as ordinary functions, so you can keep its retrieval without its agents.

A simpler alternative. A single query engine, or a hand-written loop over llm.chat_with_tools() as shown in the agents guide. A query engine stops being enough when a question needs more than one source or more than one retrieval. A hand-written loop stops being enough when you need streaming events, shared state, handoffs or a resumable run, which FunctionAgent and Workflows already provide.

Key takeaways

  • LlamaIndex builds agents from the data upward: an index feeds a query engine, a tool gives the query engine a name and description, and an agent chooses among tools.
  • FunctionAgent is a pre-built loop over native tool calls that turns tool errors into observations and raises an error when it reaches max_iterations, which defaults to 20.
  • AgentWorkflow keeps one agent active at a time and moves control with a handoff tool, while a shared state dictionary in the Context carries facts between agents.
  • A Workflow is a set of async steps routed by event type, so a branch is a union return type and a loop is a step returning an event that an earlier step accepts.
  • Use the lowest level of autonomy that works: a query engine for one lookup, an agent when the order of tool calls is unknown, and a custom workflow when you already know the order.
  • State, memory and progress all live in the Context and the event stream, and neither survives a restart unless you serialize the Context or use a durable runtime.

Example 1 of 5

Jeppesen's Unified Chatbot Framework, an internal agent platform built on event-driven Workflows

Jeppesen (a Boeing company)Documented in a case study

A customer case study published by LlamaIndex describes how Jeppesen's enterprise AI engineering team built the Unified Chatbot Framework (UCF), a shared internal platform for building and deploying agents, and names LlamaIndex's event-driven agent workflows as its core. [25][12][11]

The problem

Teams across the organisation were building chatbots independently. According to the case study they duplicated components, each team had to get through AI governance and IT policy approval on its own, interfaces and deployment models differed from team to team, and building a single chatbot or agent from scratch took about 512 hours.

Where this topic fits

The case study places LlamaIndex's event-driven agent workflows at the core of the platform and says the platform provides workflow templates for single-agent and multi-agent systems. Our reading is that the platform team writes those templates once and a product team supplies configuration instead of its own loop: the case study says an agent takes about 50 lines of code and a JSON config file, and it lists the model provider, tool connectors, vector database and conversation memory store as the pluggable parts. The case study does not name the LlamaIndex classes involved, so the mapping to Workflows is our explanation.

How it is applied, step by step

  1. A small frameworks team writes workflow templates for the common shapes, such as a single agent with tools or several cooperating agents. In Workflows terms such a template would typically be a class whose steps and event types are fixed.
  2. A product team imports a template and supplies a JSON configuration plus a short piece of code. The configuration selects the model provider, the tool connectors, the vector database and the conversation memory store.
  3. Tool connectors for systems such as GraphQL, SQL, REST APIs, Neo4j and Databricks are exposed to the agent as tools, so the template's tool-calling step does not change from one product to the next.
  4. Session and conversation state are kept by the framework. A typical implementation holds per-run state in the workflow Context and writes conversation memory to the configured store between runs.
  5. Security and compliance controls live in the shared layer, so every agent built from a template inherits them instead of each team seeking approval separately.
  6. The case study says the platform also supports event-triggered tasks that have no chat interface. In Workflows terms, a typical implementation would start such a run from an external event instead of a user message and reuse the same steps and tools.

Why this approach fits

A platform has to standardise the parts that must not vary (how tools are called, how state is kept, what is logged) while letting teams vary the parts that should (model, tools, data). Workflows separate the two cleanly: the steps and events are the fixed part, and the objects a step uses are injected. The team's stated reasons for choosing the library match this, namely control over agent logic, inputs and execution flow, and state management built into the engine.

Limitation or tradeoff

This is a vendor-published case study. The hour figures come from the customer's team, and the page does not say how the 512-hour baseline or the hours saved were measured. A shared template also concentrates risk: a bug or a poor default in it reaches every agent built on it, so the platform needs its own tests and versioning. Configuration-driven agents suit common shapes and resist unusual ones, and the case study does not say how answer quality is evaluated across the products.

What the sources document

  • A team of five to seven people built the Unified Chatbot Framework as a unified, secure and reusable framework for building and deploying agents, and the case study places LlamaIndex's event-driven agent workflows at the heart of it. [25]
  • The listed reasons for choosing LlamaIndex include event-driven workflows with session and state management, support for custom tool creation and template injection, and fine-grained control over agent logic, inputs and execution flow. [25]
  • The team reports that agents can be built with about 50 lines of code and a JSON config file, and that the time to develop and deploy a new agent fell from 512 hours to 64 hours. [25]
  • Platform capabilities listed include workflow templates for single and multi-agent systems, tool connectors for GraphQL, SQL, REST APIs, Neo4j and Databricks Data Mesh, bring-your-own LLM and vector database, and conversation memory stores on Azure Cosmos DB, Azure Table and Azure Cache for Redis. [25]
  • The case study states that the framework is onboarded with 10 to 11 production products used by internal teams across Boeing. [25]

Google's Gemini API guide for a three-agent research workflow with handoffs

Google (Gemini API documentation)Documented in official docs

The Gemini API documentation on Google AI for Developers includes a guide, Research agent with Gemini and LlamaIndex, that builds a multi-agent report writer with AgentWorkflow, FunctionAgent and Gemini's built-in Google Search tool. LlamaIndex's own multi-agent guide documents the same pattern. [27][6][7][8][18]

The problem

Producing a researched report involves three different jobs: finding information on the web, writing the report from notes, and reviewing it. Each job needs its own instructions and its own tools, and the notes, the draft and the review have to travel from one job to the next. A single prompt holding all the tools and all the instructions mixes the roles together.

Where this topic fits

AgentWorkflow is the coordinator. Gemini is the model behind each of the three FunctionAgents. Web search sits one level down, inside a tool that calls a second Gemini client configured with Google Search. The shared state dictionary in the Context is where notes, the report and the review are kept, and the event stream is what the guide prints to show progress.

How it is applied, step by step

  1. The tools are async Python functions whose first parameter is the Context. record_notes, write_report and review_report each read the dictionary stored under the key state, change one entry and write it back.
  2. search_web sends the query to a Gemini client that was created with the Google Search tool enabled and returns the text of its response, so grounding happens inside the tool and not in the agent.
  3. Three FunctionAgents are created. Each gets a name, a description, a system prompt, its own tool list and a can_handoff_to list naming the agents it may pass control to.
  4. An AgentWorkflow is created from the three agents with the research agent as root_agent and an initial_state holding empty notes and starter text for the report and the review.
  5. The workflow is started with run(user_msg=...). The guide keeps the handler and iterates stream_events() to print each change of agent, each tool call and each tool result.
  6. When an agent calls the handoff tool that AgentWorkflow added for it, the library records the target agent, and the next model turn is sent to that agent with the same memory.
  7. After the run, the final report and review are read from the state through the handler's Context.

Why this approach fits

The three roles need different prompts and tools but share one conversation and one set of facts. Handoff as a tool call gives exactly that: the active agent changes, while memory and state stay. The can_handoff_to lists narrow each agent's choices, which makes the route more predictable without hard-coding it. Because every tool call is an event, the guide can show progress with a single loop over the stream.

Limitation or tradeoff

The route is suggested by prompts, not enforced. A model can hand off early, skip the review, or bounce between writer and reviewer until the shared iteration limit ends the run with an error. Only one agent works at a time, so nothing runs in parallel. The guide itself lists reasons to move to a custom workflow, including control over the exact path, parallel work, planning first and self-correction. Passing whole reports through tool arguments also means the model rewrites long text on every call.

What the sources document

  • The guide builds a multi-agent system with the AgentWorkflow class from three FunctionAgents named ResearchAgent, WriteAgent and ReviewAgent, which search the web, write the report and review it. [27]
  • The tools search_web, record_notes, write_report and review_report are Python functions, and the guide states that the Context class passes the state between agents and tools and that each agent has access to the current state of the system. [27]
  • The guide says can_handoff_to optionally specifies which other agents an agent can talk to, and that without it the system will try to figure this out on its own. [27]
  • The AgentWorkflow is created with the research agent as root_agent and an initial_state containing research_notes, report_content and review entries. [27]
  • LlamaIndex's multi-agent guide describes AgentWorkflow as giving the root agent the user message, executing the tools that agent selects, allowing the agent to hand off control to another agent when it decides, and repeating until an agent returns a final answer. [6]

AWS sample research assistant that puts a knowledge base next to API tools as a query engine tool

Amazon Web ServicesDocumented in an engineering article

An AWS Machine Learning Blog post from May 2025 builds an agentic RAG research tool with LlamaIndex and the Mistral Large 2 model on Amazon Bedrock. The agent can call arXiv, GitHub, TechCrunch and DuckDuckGo and can query a knowledge base of documents through a QueryEngineTool. [28][4][3][5][22]

The problem

A research question may need internal documentation, recent papers, popular code repositories or news, and often more than one of these. A fixed RAG pipeline searches only the indexed documents. The post wants one assistant that picks the right source for each question and can combine internal knowledge with live API results.

Where this topic fits

The RAG pipeline is built first and tested on its own as a query engine. It is then wrapped as one tool and placed in the same list as the API tools. A function-calling agent reads the tool names and descriptions and decides which to call for each question. The query engine is the boundary: everything about chunking, retrieval and reranking stays behind it.

How it is applied, step by step

  1. The Bedrock model and the Titan embedding model are configured once as the LlamaIndex defaults, so the query engine and the agent use them without further wiring.
  2. API tools are written as Python functions with type hints and detailed docstrings and wrapped with FunctionTool.from_defaults. For arXiv and DuckDuckGo the post uses ready-made tool specs instead.
  3. In the first option, PDFs are loaded, split into chunks and stored in an Amazon OpenSearch Serverless vector index, and the index is turned into a query engine with a reranker as a post-processor.
  4. In the second option, an Amazon Bedrock knowledge base is reached through a retriever class and wrapped in a RetrieverQueryEngine, so the managed service does the loading and chunking.
  5. Either query engine is wrapped in a QueryEngineTool with a tool name and a description of what the documents cover, and added to the list of API tools.
  6. A function-calling agent is created from the combined list and a system prompt and asked the user's question. It chooses tools turn by turn until it can answer.

Why this approach fits

The post swaps the whole retrieval backend, from a hand-built OpenSearch index to a managed knowledge base, and the agent code stays the same apart from the tool object. That is the benefit of putting a query engine behind a tool: the agent depends on a name, a description and a string in, string out contract. Retrieval quality can be tuned and tested separately from agent behaviour.

Limitation or tradeoff

The post's agent classes were removed from llama-index-core two months after it was published, so its code needs the port shown above to run on current versions. Each call to a query engine tool includes retrieval, reranking and a synthesis call to the model, which adds latency and cost to every agent turn that uses it. The tool description is the only routing signal: the post gives both knowledge options the same description, which is harmless there because they are alternatives, but two tools with identical descriptions in one agent would be indistinguishable. No evaluation results are given.

What the sources document

  • The post describes the application as a research tool that uses Mistral Large 2 on Amazon Bedrock for the agent flow, interacts with arXiv, GitHub, TechCrunch and DuckDuckGo, and can access knowledge bases containing documentation and internal knowledge. [28]
  • Two options are presented for the RAG part: loading and chunking documents with LlamaIndex and storing them in Amazon OpenSearch Serverless, or using Amazon Bedrock Knowledge Bases through the AmazonKnowledgeBasesRetriever class. [28]
  • In the first option documents are split into chunks of 1,024 tokens with a 20-token overlap, and the query engine retrieves 10 candidates from which a Bedrock reranker keeps 3. [28]
  • The post converts the query engine into a QueryEngineTool with a tool name and a description, combines it with the API tools, and passes the list to a FunctionCallingAgentWorker that an AgentRunner executes. [28]

Example 4 of 5

DBOS as a durable runtime under LlamaIndex Workflows

DBOS and LlamaIndexDocumented in official docs

The llama-agents-dbos package plugs the DBOS durable execution engine into LlamaIndex Workflows. The integration is documented on both sides: in the LlamaIndex Workflows documentation and in the DBOS documentation. [17][29][16][15]

The problem

A workflow keeps its pending events and its state in memory. If the process dies halfway through a long run, such as a fan-out over many documents or a wait for a person's approval, everything is lost unless the developer has written a loop that snapshots the Context after each step. Waiting workflows also occupy memory for as long as they wait.

Where this topic fits

The runtime sits underneath the workflow, not inside it. Events, steps and the Context are written exactly as before. Passing a DBOSRuntime object to the workflow's constructor replaces the default in-process runtime with one that records each step transition in a database (SQLite for a single process, Postgres for several replicas).

How it is applied, step by step

  1. DBOS is configured with an application name and a database. Without further settings it uses SQLite, which needs no external service.
  2. The workflow is defined as usual. Nothing in the event classes or the step methods refers to DBOS.
  3. A DBOSRuntime is created and passed as runtime= when the workflow is instantiated, and the runtime is launched before the first run.
  4. A run is started with a run_id. As steps complete, the runtime journals the completions and the stream events to the database.
  5. After a crash, starting the run again with the same run_id replays the journal to rebuild the Context and continues from the last recorded step.
  6. When workflows are served over HTTP with WorkflowServer, an idle timeout lets the runtime release a waiting workflow from memory and restore it from the database when the awaited event arrives.

Why this approach fits

A workflow advances one event at a time, so its state is well defined at every step boundary. That makes step completion a natural place to write a journal entry, and it is why durability can be added as a runtime without changing workflow code. For runs that wait on people, moving the waiting state into a database also removes the need to keep a process alive for hours.

Limitation or tradeoff

Recovery works by replay, so a step that was interrupted before its journal entry was committed runs again. Steps with side effects must be safe to repeat. The documentation also states that a workflow and all of its steps run in one process, so a single run cannot spread its work across replicas, and that changing a workflow's code while old runs are in progress can break replay unless the new version is registered under a new name. The class name is the default durable identity, so renaming or moving a class hides its in-flight runs.

What the sources document

  • The LlamaIndex documentation says the llama-agents-dbos package plugs a DBOS-backed runtime into workflows so that every step transition is persisted automatically and a crashed workflow resumes where it left off without snapshot code. [17]
  • The DBOS documentation describes the same integration, notes that workflows must be defined before the runtime is launched, that run_id is equivalent to a DBOS workflow ID, and that its example uses SQLite while Postgres is recommended for production. [29]
  • Both pages state that if the counter example is killed mid-run, for example at tick 8, calling run again with the same run_id resumes from tick 8 instead of restarting from zero. [17][29]
  • The LlamaIndex page states that recovery is replay-based, so steps may execute more than once if they were interrupted before the journal entry was committed, and that a workflow and all of its steps run in the same process with no distribution of steps across replicas. [17]
  • Without a runtime plugin, the durable workflows page says there is no built-in checkpointer to enable: the caller snapshots the Context with to_dict() when a step finishes, and resume is at-least-once. [16]

SkySQL's SkyAI agents answering questions from operational databases

SkySQLDocumented in a case study

A customer case study published by LlamaIndex describes how SkySQL, a managed database service, uses LlamaIndex as the orchestration engine for agents that turn natural-language questions into SQL over a customer's operational data. [26][9]

The problem

Operational databases can have dozens or hundreds of tables, ambiguous column names and sparse foreign keys. The case study says this schema complexity causes errors in cross-table joins and nested queries. SkySQL also had to control which metadata and sample data reach the model, keep context current as schemas change, let developers and DBAs correct the agent's understanding, and balance accuracy against latency and token cost.

Where this topic fits

This is data-centric agent design in a narrow form. The agent's quality depends on the context attached to the data: table schemas, sample rows and instructions. LlamaIndex retrieves the relevant context and its structured query engine generates the SQL. An evaluation step after the answer decides whether to accept it, fall back or rerun.

How it is applied, step by step

  1. For each agent, a context is assembled automatically from the relevant table schemas, sample rows and prompt instructions.
  2. Developers and DBAs review that context and edit it, for example by adding a missing relationship or clarifying a column name. Their corrections are saved and reused in later sessions.
  3. When a question arrives, the context relevant to it is retrieved. In LlamaIndex terms a typical implementation indexes one schema object per table and retrieves the best matches for the question.
  4. A structured query engine combines the retrieved schema context with the question, generates a SQL query, runs it and writes an answer from the rows.
  5. A separate judging model scores the response. A low score triggers a fallback, logging or a rerun that uses known-good SQL patterns.
  6. The agents run next to the database in a sandbox, and semantic search uses the database's own vector support instead of an external vector store.

Why this approach fits

The hard part of text-to-SQL is not the loop but the grounding: the model has to know what the tables mean. Retrieving only the relevant schemas keeps the prompt small on databases with hundreds of tables, and storing expert corrections with the table definition means every later question benefits. The same design also answers the governance concern, because what reaches the model is an explicit, reviewable context and not the whole database.

Limitation or tradeoff

The case study reports significantly improved SQL accuracy but gives no figures, so the size of the gain cannot be judged from it. It also does not say whether or how the engine is exposed to the agents as a tool, so the QueryEngineTool wrapper in the sketch is our illustration of this lesson's pattern and not SkySQL's documented design. Generated SQL is executed, and the LlamaIndex guide warns that running arbitrary SQL is a security risk and recommends restricted roles, read-only databases and sandboxing. Schema context goes stale when tables change, and a judging model adds a second model call per answer and can itself be wrong.

What the sources document

  • The case study states that SkySQL uses LlamaIndex as the core orchestration engine for its SkyAI agents, with LlamaIndex orchestrating retrieval and synthesis for SQL generation. [26]
  • It lists a SQL table retriever engine among the architectural choices, described as LlamaIndex's structured query engine transforming context and prompts into executable SQL. [26]
  • Developers and DBAs can view, adjust or override the agent's context, such as adding missing relationships or refining instructions, and the corrections are persisted and reused. [26]
  • Each response is scored by an LLM-as-judge model, and low-confidence answers trigger fallbacks, logging or reruns using golden SQL patterns. [26]
  • The LlamaIndex structured data guide says SQLTableRetrieverQueryEngine retrieves the relevant table schema from an index and synthesizes a SQL query and a response, and it warns that executing arbitrary SQL can be a security risk, recommending restricted roles, read-only databases and sandboxing. [9]

4Common mistakes

  1. Giving a query engine tool a vague name and description such as "search" or "knowledge base".

    Why it causes problems
    The name and description are all the model knows about what is behind the tool. With two vaguely described tools it picks one more or less at random, or calls both on every question, which doubles cost and mixes unrelated passages into the answer.
    How to recognise it
    In the event stream, ToolCall events go to the wrong tool for a question whose source is obvious to a person, or every question triggers calls to all tools.
    How to fix it
    State what the data covers, what form the input should take and what the tool is not for. Print the schema the model receives with tool.metadata.get_parameters_dict() and read it as if you knew nothing else.

  2. Following a tutorial that uses AgentRunner, FunctionCallingAgent, OpenAIAgent or agent.chat().

    Why it causes problems
    Those classes were removed in llama-index-core 0.13.0, so the code fails at import on a current install. Pinning an old version to make it run locks you out of current integrations and fixes.
    How to recognise it
    Import errors from llama_index.core.agent, or example code that calls agent.chat() instead of awaiting agent.run().
    How to fix it
    Use FunctionAgent, ReActAgent or AgentWorkflow from llama_index.core.agent.workflow. Tools and query engines carry over unchanged; only the agent construction and the run call differ.

  3. Calling agent.run() repeatedly in a conversation without passing a Context.

    Why it causes problems
    Each run starts with empty chat history and a fresh state dictionary, so the agent cannot answer a follow-up question and tools that rely on earlier state find it missing.
    How to recognise it
    The second message in a conversation gets an answer that ignores the first, and the state read after a run shows only initial_state values.
    How to fix it
    Create ctx = Context(agent) once per conversation and pass ctx=ctx to every run. Serialize it with ctx.to_dict() when the conversation has to outlive the process.

  4. Using an AgentWorkflow with handoffs for a process whose order is fixed.

    Why it causes problems
    Handoffs are model decisions. A step can be skipped or repeated, the run is hard to test because the route changes between runs, and every handoff costs a model turn that adds no information.
    How to recognise it
    System prompts full of ordering instructions such as "always hand off to the reviewer after writing", and traces in which the order of agents varies for the same input.
    How to fix it
    Write the order as a custom Workflow with one step per stage and call a model, or a FunctionAgent, inside the steps that need judgement. Keep handoffs for cases where the next role depends on content.

  5. Storing clients, indexes or large documents in ctx.store or on events.

    Why it causes problems
    State and in-flight events are serialized when a run is snapshotted or journaled. A value the JSON serializer cannot encode makes the whole snapshot fail, and large values make every snapshot slow.
    How to recognise it
    Context.to_dict() raises a serialization error, or checkpoints grow by megabytes per step.
    How to fix it
    Keep only small, serializable data such as ids, counters and short text in state and events. Inject clients and indexes as resources or build them in the step, and pass document ids instead of documents.

  6. Returning whole documents or raw API payloads from a tool.

    Why it causes problems
    The agent appends every tool result to its history and resends it on each later turn, so one large result is paid for repeatedly and can overflow the context window before the iteration limit is near.
    How to recognise it
    Input token counts jump after one tool call and stay high, or runs fail with a context-length error after a search tool is used.
    How to fix it
    Return the query engine's synthesized answer or the top few passages. For bulky API responses, wrap the tool with LoadAndSearchToolSpec so the payload is indexed and the agent searches it instead.

Exercise 1

Add a human approval gate to the refund workflow

CodingIntermediateAbout 45 min (estimate)Hypothetical scenario

Start from refund_agent.py in the worked example. The business rule is new: any refund above 50.00 must be approved by a person before the workflow returns it.

Workflows have two built-in events for this. A step that returns InputRequiredEvent publishes it on the event stream and the run waits. The caller answers by sending a HumanResponseEvent into the same run with await handler.send_event(...), and a step that accepts HumanResponseEvent continues.

Change the script's last entry so that it carries the amount:

python
{"answer": "Refund 68.00: 80.00 minus the 15 percent fee, inside the 30 day window.", "refund": 68.00}

Then change the workflow and the caller so that the approval rule is enforced. Replace the person with a reply argument to run_once so the program runs without keyboard input, and give run_once a limit argument that is passed to run(). This needs only pip install llama-index-workflows; no model and no API key.

Requirements

  • Read the approval limit from the start event with a default of 50.00 and keep it in ctx.store.
  • When the final answer's refund is above the limit, store the pending result in ctx.store and return an InputRequiredEvent whose prefix asks for approval and shows the amount with two decimals.
  • Add a step that accepts HumanResponseEvent and returns a StopEvent with status approved when the response is yes, and status rejected with answer None otherwise.
  • When the refund is at or below the limit, finish without asking, with status finished.
  • In run_once, answer every InputRequiredEvent from the stream with a HumanResponseEvent carrying the reply argument.

Expected behaviour

Calling run_once("yes"), run_once("no") and run_once("no", limit=100.00) in turn prints:

text
Approve refund of 68.00? yes
{'status': 'approved', 'answer': 'Refund 68.00: 80.00 minus the 15 percent fee, inside the 30 day window.', 'turns': 3}
Approve refund of 68.00? no
{'status': 'rejected', 'answer': None, 'turns': 3}
{'status': 'finished', 'answer': 'Refund 68.00: 80.00 minus the 15 percent fee, inside the 30 day window.', 'turns': 3}

In the third run the limit is 100.00, so no approval is requested and the reply is never used.

Hint 1

The return annotation of call_model must list every event the step can emit, so add InputRequiredEvent to the union.

Hint 2

InputRequiredEvent and HumanResponseEvent accept extra keyword fields. InputRequiredEvent(prefix="...") and HumanResponseEvent(response="...") are enough here.

Hint 3

The step that handles the reply cannot see the model's answer unless call_model saved it first. Use ctx.store for that.

Hint 4

You do not write the pending event to the stream yourself. Returning an InputRequiredEvent from a step publishes it.

Show solution

Three things change: the imports, the call_model step and a new decide step. setup stores the limit, and run_once answers the approval request. ORDERS, POLICY, the two tool functions, TOOLS, the event classes and run_tool stay as in the worked example.

python
from workflows.events import Event, HumanResponseEvent, InputRequiredEvent, StartEvent, StopEvent

SCRIPT = [
    {"tool": "order_lookup", "args": {"order_id": "A-1042"}},
    {"tool": "policy_search", "args": {"query": "refunds for opened items after delivery"}},
    {"answer": "Refund 68.00: 80.00 minus the 15 percent fee, inside the 30 day window.", "refund": 68.00},
]


class RefundAgent(Workflow):
    @step
    async def setup(self, ctx: Context, ev: StartEvent) -> ModelTurn:
        await ctx.store.set("history", [f"user: {ev.question}"])
        await ctx.store.set("turns", 0)
        await ctx.store.set("limit", ev.get("limit", default=50.00))
        return ModelTurn()

    @step
    async def call_model(self, ctx: Context, ev: ModelTurn) -> ToolRequest | InputRequiredEvent | StopEvent:
        turns = await ctx.store.get("turns")
        decision = SCRIPT[turns]
        await ctx.store.set("turns", turns + 1)
        if "answer" not in decision:
            return ToolRequest(tool=decision["tool"], args=decision["args"])
        result = {"status": "finished", "answer": decision["answer"], "turns": turns + 1}
        if decision["refund"] <= await ctx.store.get("limit"):
            return StopEvent(result=result)
        await ctx.store.set("pending", result)          # the reply step will need it
        return InputRequiredEvent(prefix=f"Approve refund of {decision['refund']:.2f}? ")

    # run_tool is unchanged

    @step
    async def decide(self, ctx: Context, ev: HumanResponseEvent) -> StopEvent:
        pending = await ctx.store.get("pending")
        if ev.response.strip().lower() == "yes":
            return StopEvent(result={**pending, "status": "approved"})
        return StopEvent(result={**pending, "status": "rejected", "answer": None})


async def run_once(reply: str, limit: float = 50.00) -> None:
    handler = RefundAgent(timeout=30).run(question="Can I return order A-1042?", limit=limit)
    async for ev in handler.stream_events():
        if isinstance(ev, InputRequiredEvent):
            print(ev.prefix + reply)
            await handler.send_event(HumanResponseEvent(response=reply))
    print(await handler)


async def main() -> None:
    await run_once("yes")
    await run_once("no")
    await run_once("no", limit=100.00)


if __name__ == "__main__":
    asyncio.run(main())

Why it works. call_model now has three possible outputs, and its return annotation tells the engine about all of them. An InputRequiredEvent returned from a step does not need a consuming step: the engine writes it to the stream and the run stays alive with nothing in progress. The caller's send_event puts a HumanResponseEvent into the run, and decide is the only step that accepts that type, so it fires. The pending result travels through ctx.store because the two steps never call each other. The turn-limit check from the worked example is left out here to keep the listing short; keep it in real code.

Two things to carry into production. The limit check happens in code, not in a prompt, so the model cannot talk its way past it. And a real approval can take hours, so the timeout of 30 seconds would have to be removed and the Context saved while waiting, as the human-in-the-loop documentation shows.

Check your answer

  • Does the second run end with status rejected and answer None, without printing a refund?
  • Does the third run, with limit=100.00, finish with status finished and print no approval line?
  • Does call_model's return annotation include InputRequiredEvent, and is there exactly one step that accepts HumanResponseEvent?
  • Is the approval decision made by comparing numbers in code, with no reliance on the scripted model's text?

Exercise 2

Design the tools and choose the level of control for a bike shop support agent

DesignIntermediateAbout 40 min (estimate)Hypothetical scenario

A bike shop wants a support assistant. It has three data sources:

  • 40 PDF service manuals, one per bike model (about 30 pages each).
  • A Postgres database with tables orders, order_items, customers and 22 other tables used by the warehouse system.
  • A carrier REST API that returns the full tracking history of a parcel as JSON, often several hundred lines.

Typical requests:

  1. "Where is my order 5531?"
  2. "How do I adjust the rear derailleur on the Trail 3?"
  3. "My order 5531 arrived with a bent wheel. What are my options?" (needs the order, the warranty section of the manual for that model, and then either a replacement order or a refund, both of which a staff member must approve.)

Write a design, on paper or in a document, that answers these questions. For each data source: what kind of query engine or function will you build, and what are the tool's name and description? Which level will you use for requests 1 and 2, and which for request 3: a query engine alone, a FunctionAgent, an AgentWorkflow or a custom Workflow? What goes into state? What iteration limit and timeout will you set, and what happens when they are reached? Name one failure you will test for before launch. No code is required.

Requirements

  • Give each data source exactly one tool with a name and a description that says what it covers and what it is not for.
  • Say where the retrieval settings and the database permissions live, and limit the SQL tool to named tables.
  • Choose a level of control for requests 1 and 2 and a level for request 3, and justify each choice in one or two sentences.
  • Place the staff approval in code rather than in a prompt, and say which workflow events carry it.
  • State the iteration limit, the timeout, and the behaviour when each is reached.

Expected behaviour

A good design has three tools with clearly separated descriptions, keeps the carrier payload out of the agent's context, restricts SQL to the three customer-facing tables through a read-only role, uses a single FunctionAgent for the open questions, and wraps the damaged-order process in a custom Workflow whose approval step cannot be skipped by the model. It names concrete limits and a concrete test.

Hint 1

Ask which parts of request 3 are always in the same order. Those parts belong in workflow steps, not in a prompt.

Hint 2

The carrier API returns far more text than the agent needs. Decide what the tool should return instead.

Hint 3

The database has 25 tables. Consider what the SQL engine needs to see and what it must never be able to do.

Show solution

Tools, built from the data outward

SourceWhat to buildTool name and description
Service manualsA vector index over the PDFs with the bike model stored as metadata on every chunk, and a query engine with a small similarity_top_k and a rerankerservice_manual: "Answers how-to, maintenance and warranty questions from the official service manual of one bike model. Input: the model name and one question. Not for order status."

Chunking, similarity_top_k and reranking are settings of the manual query engine, so they can be tuned against test questions without touching the agent. The SQL engine sees three table schemas, not 25, which keeps its prompt small and makes the warehouse tables unreachable. The read-only role is the real guard: a description that says "read-only" is advice to the model, and the database permission is enforcement. The tracking function reduces several hundred lines of JSON to three fields before the agent sees anything.

Levels of control

  • Requests 1 and 2: one FunctionAgent with the three tools. The number and order of calls depend on the question (request 1 needs order_data and then track_parcel, request 2 needs only service_manual), and there is one role. A query engine alone cannot do request 1, because it spans two sources. An AgentWorkflow would add handoff turns without adding ability.
  • Request 3: a custom Workflow. The order is fixed: look up the order, read the warranty terms for that model, propose replacement or refund, get staff approval, then act. The proposal step can call the FunctionAgent or a single model call, because that is where judgement is needed. The approval is a step that returns InputRequiredEvent, and the action happens only in the step that receives a HumanResponseEvent with an approval. The model cannot skip a step that it does not control.
  • Routing between the two: a first workflow step classifies the message (damaged or defective item versus everything else) and returns one of two event types.

State

Keep the order id, the bike model, the tracking number, the proposed remedy and the approval result in ctx.store. These are small, serializable values. Do not keep the database connection, the index or the manual text there.

Limits

  • max_iterations=6 for the FunctionAgent. Requests 1 and 2 need at most three model turns (two tool calls and the answer), so six leaves room for one corrected call. Catch WorkflowRuntimeError and reply that the request is being passed to a person.
  • A timeout of about 60 seconds for the question-answering path. For the damaged-order workflow, no timeout while waiting for staff: save the Context after the approval request and restore it when the reply arrives, or use a durable runtime.

A failure to test

Ask about an order number that does not exist. The SQL tool should return an empty result, and the agent should say that the order was not found. A failing design invents a status or calls track_parcel with a made-up tracking number. A second test worth running: send request 3 and reject the approval, then check that no replacement order or refund was created.

Check your answer

  • Could a new colleague tell from the three tool descriptions alone which tool answers each of the three requests?
  • Is the staff approval enforced by a workflow step and a database permission, with no dependence on the model obeying an instruction?
  • Did you give a specific number for the iteration limit and say what the user sees when it is reached?
  • Does the carrier tool return a few fields instead of the full tracking history?
