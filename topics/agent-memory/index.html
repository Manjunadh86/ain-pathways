Agent Memory

Agent memory is everything an agent's program stores and later puts back into the model's context, so that the model can use information from earlier steps, earlier conversations or earlier corrections. Short-term memory is the message history of one conversation thread. Long-term memory is information saved outside the thread and reused in later ones.

1Overview

Why it matters

A language model keeps nothing between calls. Whatever an agent "remembers" is text that your code saved and chose to send again. Without that, a support agent asks for the order number it was given two messages ago, a coding agent repeats the mistake you corrected yesterday, and a long task dies when its history no longer fits the context window. Careless memory fails more quietly: a stale address is used for a delivery, one customer's details appear in another customer's chat, or an instruction planted in a web page is saved and obeyed in every later session.

Anyone who designs or reviews an agent should be able to answer four questions about it. What stays in the thread, and for how long? What is written to long-term storage, and who decides? What is read back on each call? What gets deleted, and when? The answers set cost and latency, because every remembered token is paid for again on every call. They also set how personal the agent feels and which privacy obligations you take on.

Before you start

  • The Agent Loop (ReAct)Intermediate

What you will be able to do

  • Distinguish short-term (thread) memory from long-term memory and say where each one is stored.
  • Classify a piece of information as semantic, episodic or procedural memory and pick a storage pattern for it.
  • Keep a thread inside a token budget with trimming and summarization, and state what each technique loses.
  • Design a user profile store with clear rules for updates, isolation between users and deletion.
  • Rank memories by relevance, recency and importance, and compute the half-life of a decay factor.
  • Choose between writing memories during a turn and writing them in the background.

Key terms

Thread
One conversation or task run, identified by an id, whose messages are stored and loaded together. Some frameworks call it a session.
Short-term memory
The message history and working state of the current thread. It is sent to the model on every call and ends with the thread.
Long-term memory
Information saved outside any single thread, keyed by a user or an application, and loaded into later threads.
Semantic memory
Stored facts, such as a user's preferences or the details of their account.
Episodic memory
Stored records of past events or task runs, such as what the agent tried last time and how it turned out.
Procedural memory
Stored instructions for how to do a task, such as the system prompt or a project conventions file.
Compaction
Replacing older parts of a thread with something shorter, usually a model-written summary, so that the thread fits a token budget.
Profile
A single structured record per user or entity that is updated in place when a fact changes.
Consolidation
Merging newly extracted information with stored memories by creating, updating or deleting records.
Time to live (TTL)
A lifetime attached to a stored record, after which the record is deleted automatically.

2Explanation

Introduction

In The Agent Loop the context only grew. Every reply and every tool result was appended to one list of messages, and each model call saw the whole list. That list is already a memory. This lesson is about what to do when the list gets too long, and about what should survive once the conversation is over.

Start from one fact: a language model stores nothing between calls. If a model appears to remember your name, a program saved the name somewhere and put it into the prompt again. Agent memory is therefore not a property of the model. It is two operations that your code performs around the loop: writing (deciding what to save and where) and reading (deciding what to put back into the context for this call).

Memory has two scopes:

  • Short-term memory belongs to one thread, meaning one conversation or one task run. It is the message history plus any working state. It is what lets an agent read "what about tomorrow?" as a follow-up to a question about the weather in Seattle.
  • Long-term memory lives outside any thread. It is keyed by a user, a team or the whole application, and it lets a new conversation start from what earlier conversations established.

Google's whitepaper Context Engineering: Sessions & Memory (opens in a new tab), the Day 3 reading of the Kaggle agents course (opens in a new tab), gives a picture worth keeping. A session is the workbench for one project: covered in tools and notes, all within reach, all temporary. Memory is the filing cabinet. When the project ends you do not push the whole messy desk into storage. You file the few documents worth keeping. The LangGraph documentation (opens in a new tab) draws the same line, between short-term working memory for ongoing reasoning and long-term memory across sessions.

Long-term memory is usually divided into three kinds, with names borrowed from cognitive science: semantic (facts), episodic (past experiences) and procedural (how to do things). The rest of the lesson covers how thread memory is stored and compressed, how the three long-term kinds are written and read, how a user profile is kept correct, and how memories should age and be forgotten.

How it works

Short-term memory: the thread

A thread's memory is a list of messages stored under a thread id. Before each model call the program loads the list. After the call it appends the new messages and saves. Frameworks differ only in who does the bookkeeping. In LangGraph a checkpointer saves the graph's state under a thread_id. This excerpt from the LangGraph memory guide (opens in a new tab) is the whole mechanism (builder is your graph definition):

python
from langgraph.checkpoint.memory import InMemorySaver

graph = builder.compile(checkpointer=InMemorySaver())
graph.invoke(
    {"messages": [{"role": "user", "content": "hi! i am Bob"}]},
    {"configurable": {"thread_id": "1"}},
)

A later call with the same thread_id sees the earlier messages, and a different id starts empty. InMemorySaver is for development; the same page lists database-backed savers for production. The OpenAI Agents SDK calls the same idea a session (opens in a new tab): before a run it prepends the stored items to the new input, and after the run it stores the new ones.

Keeping the thread inside a budget

Left alone, a thread grows until it no longer fits the context window. Long before that it costs more, responds more slowly and answers worse, because models attend less reliably to a long context (see Tokens and Context Windows). Three techniques shrink it:

TechniqueWhat it doesWhat it loses
TrimmingSends only the last N turns, or as many recent messages as fit a token limitEverything older, including constraints stated at the start
Clearing tool resultsReplaces old tool outputs with a short stubThe raw data, which can usually be fetched again
Summarization (compaction)Replaces older messages with a model-written summary and keeps recent ones word for wordAny detail the summarizer judged unimportant

Summaries are usually rolling: each compaction asks a model to extend the previous summary with the messages that are about to be removed. Something must trigger it. The Kaggle whitepaper names three kinds of trigger: a count (tokens or turns pass a threshold), time (the user has been idle for a while) or an event (a sub-task has finished). When you cut a thread, never separate a tool call from its result: most chat APIs expect every tool result to follow the call that produced it.

Compaction is lossy by design. Anthropic's context engineering article (opens in a new tab) describes the version in Claude Code: the summary keeps architectural decisions, unresolved bugs and implementation details, and discards redundant tool outputs. Anything that must survive every compaction, such as a hard constraint from the user, belongs somewhere compaction does not touch: the system prompt or long-term memory.

Long-term memory: three kinds

The CoALA paper (opens in a new tab) organised agent memory with terms from cognitive science, and frameworks have adopted them.

  • Semantic memory holds facts, which in most products means facts about the user. There are two storage patterns. A profile is one structured document per user, updated in place and cheap to load in full. A collection is many small records added over time and searched when needed. The LangGraph memory overview (opens in a new tab) states the tradeoff: a profile becomes error-prone to rewrite as it grows, while a collection loses less information but moves the difficulty into search and into updating or deleting old items.
  • Episodic memory holds experiences: what the agent did in an earlier run and how it ended. A common use is few-shot prompting, where a similar past case is retrieved and shown to the model.
  • Procedural memory holds instructions. CoALA counts the model's weights and the agent's code as procedural memory too. The part an agent can realistically change is its prompt, so an agent that edits a rules file after being corrected is updating procedural memory.

Long-term records are stored under a namespace that names their owner, so that a search for one user can never return another user's records. A fragment in the style of the LangGraph store API:

python
namespace = (user_id, "memories")
store.put(namespace, "diet", {"data": "User is vegetarian"})
hits = store.search(namespace, query="meal preferences", limit=3)

A user profile in practice

A profile is often the first long-term memory a product adds, and three rules keep it trustworthy. Give it named fields, so that a new value replaces the old one instead of sitting beside it. Record where each value came from and when, because a value the user typed into a form deserves more trust than one inferred from a remark. Keep it small enough to load on every call.

json
{
  "user_id": "u-4821",
  "home_airport": {"value": "BER", "source": "user_stated", "updated": "2026-09-30"},
  "seat": {"value": "aisle", "source": "user_stated", "updated": "2026-03-02"},
  "diet": {"value": "vegetarian", "source": "inferred", "updated": "2026-08-14"}
}

At the start of a thread the program reads this document by user id and writes its values into the system prompt. Nothing has to be searched.

Writing: extraction and consolidation

A stored transcript is a log, not a memory. Writing a memory has two stages:

  1. Extraction selects what is worth keeping, guided by topics you define. A support agent keeps order numbers and device models. A tutoring agent keeps goals and weak areas.
  2. Consolidation compares each extracted item with what is already stored and picks one operation: create a new record, update an existing one, or delete one that the new information contradicts. Without it the store fills with duplicates and with pairs of facts that cannot both be true, such as two home addresses.

The timing of the write is a separate choice. Writing in the hot path means the agent calls a save-memory tool during the turn. The memory is usable immediately, but the turn is slower and the model has to think about remembering while doing its real task. Writing in the background means a separate job processes the conversation after the reply has been sent. It adds no latency, but the memory does not exist until the job has run. Explicit requests ("remember that I am vegetarian") suit the hot path. Facts the user only mentions in passing are usually extracted in the background.

Reading: always loaded or searched on demand

Small, stable memories such as a profile or a rules file are loaded at the start of every thread, usually into the system prompt. Large collections are searched. Either the program runs a search before every call, or the model gets a memory-search tool and decides when to use it, as in Agentic RAG.

Searching by similarity alone is a known weakness, because it returns records that resemble the query even when they are old or trivial. The Generative Agents paper (opens in a new tab) introduced a blend that the Kaggle whitepaper also recommends. Each memory is scored on three dimensions:

score=wrel⋅relevance+wrec⋅recency+wimp⋅importance\text{score} = w_{rel}\cdot\text{relevance} + w_{rec}\cdot\text{recency} + w_{imp}\cdot\text{importance}score=wrel​⋅relevance+wrec​⋅recency+wimp​⋅importance

Relevance is the similarity between the query and the memory (see Embeddings). Importance is a rating given when the memory is written. Recency falls for as long as the memory goes unused.

Forgetting and aging

A store that only grows gets slower and less accurate, because stale facts crowd out current ones. Forgetting has a soft form and a hard form.

Aging is the soft form. The record stays, but its recency decays, so it is retrieved less and less. With a decay factor γ\gammaγ per unit of time and Δt\Delta tΔt units since the memory was last used:

recency=γΔt,half-life=ln⁡0.5ln⁡γ\text{recency} = \gamma^{\Delta t}, \qquad \text{half-life} = \frac{\ln 0.5}{\ln \gamma}recency=γΔt,half-life=lnγln0.5​

The Generative Agents paper used γ=0.995\gamma = 0.995γ=0.995 per hour, which is a half-life of about 138 hours, or 5.8 days. The clock restarts whenever a memory is retrieved, so memories that keep proving useful stay fresh.

Deletion is the hard form, and it has four sources:

  • Consolidation removes a record that newer information contradicts.
  • A TTL removes a record after a fixed lifetime. Google's Memory Bank (opens in a new tab) lists this as automatic expiration.
  • A pruning job removes records that have gone unused for a long time. The Claude memory tool documentation (opens in a new tab) recommends this for memory files.
  • The user asks for something to be forgotten.

The last source is not optional. A memory feature needs a way for a person to list, correct and delete what is stored about them (see Data Privacy and Compliance).

Worked example: Ranking six stored memories for a flight booking, then updating one and forgetting another

A travel assistant holds six long-term memories about one user. On day 400 the user writes "book me a flight to lisbon next month", and the context has room for three memories. Which three should be loaded? The script scores every memory, shows why similarity alone chooses badly, and then applies one update and one forgetting pass.

Three simplifications keep the numbers checkable by hand. Relevance is word overlap (shared words divided by all distinct words, after dropping a few filler words), where a real system would compare embeddings. Recency uses a half-life of 30 days. All three weights are 1.

Save this as memory_ranking.py. It needs only the Python standard library (3.9 or later).

python
HALF_LIFE_DAYS = 30   # recency halves after 30 days without use
TTL_DAYS = 180        # unused for longer than this: delete, unless pinned
PIN_IMPORTANCE = 8    # importance at or above this is never auto-deleted
STOPWORDS = {"a", "an", "the", "to", "on", "is", "user", "me"}

MEMORIES = [  # last_used is a day number, importance is 1 to 10
    {"id": "seat", "text": "user prefers an aisle seat on a flight", "last_used": 395, "importance": 6},
    {"id": "old-trip", "text": "user cancelled a flight to lisbon", "last_used": 40, "importance": 3},
    {"id": "diet", "text": "user is vegetarian", "last_used": 380, "importance": 7},
    {"id": "home", "text": "user home airport is berlin", "last_used": 398, "importance": 8},
    {"id": "weather", "text": "user asked about lisbon weather next spring", "last_used": 300, "importance": 2},
    {"id": "layover", "text": "user avoids an overnight layover", "last_used": 250, "importance": 5},
]


def words(text):
    return {word for word in text.lower().split() if word not in STOPWORDS}


def relevance(query, text):
    """Word overlap (Jaccard). A real system compares embeddings instead."""
    q, m = words(query), words(text)
    return len(q & m) / len(q | m)


def recency(last_used, today):
    return 0.5 ** ((today - last_used) / HALF_LIFE_DAYS)


def score(memory, query, today):
    parts = (relevance(query, memory["text"]),
             recency(memory["last_used"], today),
             memory["importance"] / 10)
    return (*parts, sum(parts))


def recall(memories, query, today, k=3):
    ranked = sorted(memories, key=lambda m: score(m, query, today)[3], reverse=True)[:k]
    used = {m["id"] for m in ranked}
    refreshed = [{**m, "last_used": today} if m["id"] in used else m for m in memories]
    return ranked, refreshed   # reading a memory resets its age


def remember(memories, new):
    """Consolidate: replace the record with the same id, or add a new one."""
    if any(m["id"] == new["id"] for m in memories):
        return [new if m["id"] == new["id"] else m for m in memories]
    return [*memories, new]


def forget(memories, today):
    return [m for m in memories
            if today - m["last_used"] <= TTL_DAYS or m["importance"] >= PIN_IMPORTANCE]


if __name__ == "__main__":
    query, today = "book me a flight to lisbon next month", 400
    print(f"{'id':<9}{'relevance':>9}{'recency':>9}{'importance':>11}{'total':>7}")
    for m in MEMORIES:
        rel, rec, imp, total = score(m, query, today)
        print(f"{m['id']:<9}{rel:>9.3f}{rec:>9.3f}{imp:>11.1f}{total:>7.3f}")
    by_relevance = sorted(MEMORIES, key=lambda m: relevance(query, m["text"]), reverse=True)
    print("relevance only:", [m["id"] for m in by_relevance[:3]])
    top, memories = recall(MEMORIES, query, today)
    print("blended score: ", [m["id"] for m in top])
    moved = {"id": "home", "text": "user home airport is munich", "last_used": today, "importance": 8}
    memories = remember(memories, moved)
    print("after remember:", len(memories), "records, home =", memories[3]["text"])
    print("after forget:  ", [m["id"] for m in forget(memories, today)])

Check one row by hand. The query's words are book, flight, lisbon, next and month. The old-trip memory's words are cancelled, flight and lisbon. Two words are shared and six are distinct, so its relevance is 2 / 6 = 0.333, the highest in the table. It was last used on day 40, which is 360 days or 12 half-lives ago, so its recency is 0.512≈0.00020.5^{12} \approx 0.00020.512≈0.0002. With importance 0.3 the total is 0.634.

What the run shows:

  • Similarity alone picks stale records. Ranked by relevance, the top three are a trip cancelled a year ago, a weather question and the seat preference. The home airport, which the booking cannot start without, scores zero because it shares no word with the query.
  • The blend picks what the task needs. home (0 + 0.955 + 0.8 = 1.755), seat (0.125 + 0.891 + 0.6 = 1.616) and diet (0 + 0.630 + 0.7 = 1.330) are loaded.
  • Reading is also a write. recall returns a new list in which the three memories it used have last_used set to 400, so their recency starts again at 1.
  • Consolidation updates in place. The user mentions a move, and remember replaces the home record. The store still has 6 records, not 7 with two different airports.
  • Forgetting removes what was never used. old-trip has gone unused for 360 days, past the 180-day TTL, and its importance of 3 is below the pin level of 8, so it is deleted. layover, unused for 150 days, survives for now.

The weights are a design decision. Equal weights let a recent, important but unrelated memory outrank a related one. That is fine for a handful of profile-like facts and wrong for a large collection of mixed topics. There, raise the relevance weight, or load stable facts from a profile and keep scoring for the collection.

Edge cases and limitations

Compaction drops an instruction that was only given in conversation
A constraint stated early in a chat, such as never booking a particular airline, can disappear when that turn is summarized. The Claude Code documentation describes this case: an instruction given only in conversation may be lost after compaction, while the project CLAUDE.md file is re-read from disk and put back. Store lasting constraints in the system prompt or in long-term memory, and tell the summarizer which kinds of statement it must keep.
A cut separates a tool call from its result
Trimming at a fixed message count can keep a tool result whose call was removed, or the reverse, and the next model call then fails or misreads the orphaned half. The trimming example in the LangGraph memory guide passes settings for the message types a trimmed history may start and end on. Cut on turn boundaries, and move the cut earlier when it would land between a call and its result.
A background write is not there yet
With background extraction, a fact from this conversation is missing from long-term memory until the job has run. The AgentCore documentation states that long-term memory generation is asynchronous and that episodic records are produced only once an episode is detected as complete. A second session opened seconds later will not see the fact. Rely on the thread for anything said in the current conversation, and write explicit remember requests in the hot path.
Two sessions update the same profile at once
If a user has two conversations open and each rewrites the whole profile, the later write silently erases the earlier one. The Kaggle whitepaper lists race conditions on the same memory as a production concern and suggests transactional operations or optimistic locking. Update single fields, not whole documents, or check a version number before writing.
A memory was true when written and is false now
A record such as the user being about to travel to Lisbon is correct for a few weeks and misleading after that. Relative dates make it worse, because next month has no meaning a year later. Store absolute dates in the text, give time-bound facts a TTL, and keep a last-modified time so that the model and a reviewer can judge how current a record is. Claude Code records such a timestamp in its memory files.
Tool output is saved as if it were a fact about the user
Prices, stock levels and search results go stale quickly. The Kaggle whitepaper discourages generating memories from tool output because such memories tend to be brittle and stale, and suggests short-term caching for that data. Tool output can also carry text written by a third party, so saving it gives an injected instruction a way to persist across sessions.

When to use it, and when something simpler is enough

Use it when

  • Conversations or tasks run longer than fits comfortably in the context window, so the thread has to be trimmed or summarized to keep working.
  • The same user returns across sessions and would otherwise repeat preferences, account details or decisions that were already made.
  • The agent keeps making a mistake that someone has already corrected, which means the correction needs to be stored as an instruction.
  • A task spans several sessions, such as multi-day coding or research, and each session must resume from recorded progress.

Think twice when

  • Each request is self-contained, such as a one-off classification or translation. Storing anything adds cost and privacy exposure and gives nothing back.
  • The information is shared reference material such as product documentation. That belongs in a retrieval index that every user reads, not in per-user memory.
  • The fact changes faster than you would refresh it, such as a price or a stock level. Fetch it with a tool each time.
  • You cannot yet show users what is stored about them or delete it on request. Build those controls before turning on automatic extraction.

A simpler alternative. Keep the full message history of the thread, a hand-written system prompt, and nothing else. For facts that must cross sessions, start with a small explicit profile that the user fills in on a settings page. This stops being enough when threads outgrow the token budget (add trimming, then summarization), or when the useful facts only come up in conversation and nobody will type them into a form (add extraction and consolidation).

Key takeaways

  • A model keeps nothing between calls, so agent memory is always text that a program saved and chose to put back into the context.
  • Short-term memory is one thread's message history. It has to be trimmed or summarized before it outgrows the token budget, and both techniques lose detail.
  • Long-term memory holds facts (semantic), past experiences (episodic) and instructions (procedural), stored outside any thread under a namespace that names the owner.
  • Writing a memory means extracting what matters and consolidating it with what is stored by creating, updating or deleting records. Appending transcripts is not memory.
  • Retrieval improves when relevance is blended with recency and importance, because similarity alone returns stale and trivial records.
  • Forgetting is part of the design. Decay, TTLs, handling of contradictions and deletion on request keep the store accurate and respectful of the people it describes.

Example 1 of 5

ChatGPT Memory: a per-user memory built from saved memories and past chats, with user controls

OpenAIDocumented in official docs

OpenAI's Help Center article Memory in ChatGPT describes how the product remembers details across conversations, which sources the remembered information comes from, and how a user reviews, corrects and deletes it. [12]

The problem

One person uses a general-purpose assistant for unrelated tasks over many months. Without memory every chat starts from nothing, and the user repeats their role, preferences and ongoing projects. With memory the product holds personal information, so the user must be able to see what is held, fix what is wrong and remove what should no longer be used. The article notes that features and controls vary by plan, region, platform and workspace settings.

Where this topic fits

This is long-term semantic memory organised around one user. It is read from several sources (saved memories, past chats, custom instructions, files and connected apps), and the product decides for each response which remembered information is relevant. The current chat is the thread, and it is separate. A temporary chat is a thread that is deliberately cut off from the write path.

How it is applied, step by step

  1. The user controls the feature under Settings, Personalization, Memory. Turning Memory off does not delete past chats, which stay in the history until the user deletes them.
  2. A saved memory is created when the user explicitly asks ChatGPT to remember something, or when ChatGPT saves a detail as useful context where that behaviour is available. It is stored separately from the chat it came from.
  3. With chat history referencing on, information derived from past conversations is also used. Unlike an explicit saved memory, this derived information changes as the system updates what is most useful to remember.
  4. In a new conversation ChatGPT looks for relevant context when it is likely to improve the response. The article says it does not search the user's history for every response.
  5. When personal context was used, Sources may appear below the response and show which past chat, saved memory, custom instruction or file contributed.
  6. The user reviews the memory summary, enters corrections, asks for something not to be mentioned again, or deletes items. To remove a fact completely, the user deletes it from every source that holds it.

Why this approach fits

An assistant used for everything gains most from memory that is about the person, not about any single task. Keeping explicit saved memories apart from memory derived from chat history gives two levels of control: individual items a user can inspect and delete one by one, and a broader summary that adapts without the user managing it. The Sources display and the correction controls address the main risk of implicit memory, which is the system keeping something the user did not mean to hand over.

Limitation or tradeoff

Forgetting is not one action. The same fact can live in a saved memory, in the chat where it was said, in a file and in a connected app, and removing one copy leaves the others. The article also says the memory summary is a high-level view that may omit details, so a user cannot inspect everything that could shape a response. Memory derived from chat history changes as the system updates it, which in our view makes the assistant's behaviour harder to predict than a fixed list would. Deletion is not instant either: the article states that logs of deleted saved memories may be kept for up to 30 days.

What the sources document

  • With Memory enabled, ChatGPT can remember relevant preferences and details from chats and other available sources, which depending on plan and region can include past chats, saved memories, custom instructions, files in Library and content from connected apps. It does not retain every detail from every conversation. [12]
  • Saved memories are details the user explicitly asks ChatGPT to remember or that ChatGPT saves as useful context. They are stored separately from chat history, and deleting the original chat does not automatically delete a saved memory created from it. [12]
  • The article distinguishes improved Memory, which continually updates a broader summary of relevant context, from legacy saved memories, which use a more explicit list of individual memory items. [12]
  • If Reference chat history is turned off, information remembered from past chats is scheduled for deletion from OpenAI systems within 30 days, and OpenAI may retain logs of deleted saved memories for up to 30 days for safety and debugging purposes. [12]
  • Temporary chats do not create or update memories, even with personalization on, and before starting one the user can choose whether it uses existing memories. [12]

The facts above come from the cited sources. The steps and analysis in this example are our explanation of how they fit together.

Example 2 of 5

Claude Code: procedural memory kept as CLAUDE.md files and notes the agent writes for itself

AnthropicDocumented in official docs

The Claude Code documentation page How Claude remembers your project describes two mechanisms that carry knowledge between coding sessions. The page Explore the context window describes what happens to them when a long session is compacted. [9][10]

The problem

Every Claude Code session starts with a fresh context window, yet a codebase has build commands, conventions and past corrections that the agent needs each time. Explaining them again in every session wastes effort, and a correction given only in chat is gone the next day. The documentation's own test for what to write down is whether you would otherwise re-explain it, for example when Claude makes the same mistake a second time.

Where this topic fits

This is mostly procedural memory, stored as plain files outside the thread. CLAUDE.md holds instructions that people write and that are loaded at the start of every session. Auto memory holds notes the agent writes during a session, with an index that is always loaded and topic files that are read on demand. Because both live on disk and not in the message history, thread compaction does not destroy them.

How it is applied, step by step

  1. A team writes a project CLAUDE.md with build and test commands, conventions and layout, and shares it through version control. Personal preferences go in a user-level file that applies to all projects.
  2. At launch Claude Code loads the CLAUDE.md files from the working directory and the directories above it and concatenates them. Files in subdirectories load later, when Claude works with files there.
  3. During work, when the user corrects Claude or asks it to remember something, Claude writes a note into the project's auto memory directory: one topic file per memory, plus one line in the MEMORY.md index.
  4. At the start of the next session the beginning of MEMORY.md is loaded. Topic files are not loaded at startup. Claude reads them with its normal file tools when it needs the detail.
  5. When a long session is compacted, the conversation is replaced by a summary, and the project-root CLAUDE.md and the auto memory are re-injected from disk.
  6. People audit the memory with the /memory command, which lists the files. The files are plain Markdown that anyone with access can edit or delete.

Why this approach fits

Instructions that change how an agent behaves for a whole team should be reviewable, and a file in version control gets code review, history and blame at no extra cost. Loading a short index every time and reading topic files only when needed keeps the fixed context cost small while still letting the memory grow. Splitting human-written rules from agent-written notes also makes it clear who is responsible for each line.

Limitation or tradeoff

The documentation is explicit that these files are context, not enforced configuration. Claude reads them and tries to follow them, with no guarantee for vague or conflicting instructions, and blocking an action reliably needs a hook instead. Longer files consume more context and reduce adherence, which is why the documentation suggests staying under 200 lines per file. Anything past the index's load limit is not loaded at session start. Auto memory is local to one machine and is not shared across machines or cloud environments.

  • Each Claude Code session begins with a fresh context window, and two mechanisms carry knowledge across sessions: CLAUDE.md files, which the user writes, and auto memory, which is notes Claude writes itself based on the user's corrections and preferences. [9]
  • The first 200 lines of MEMORY.md, or the first 25KB, whichever comes first, are loaded at the start of every conversation. Topic files are not loaded at startup and are read on demand. [9]

Generative Agents: an episodic memory stream ranked by recency, importance and relevance

Stanford University and GoogleDocumented in a paper

The paper Generative Agents: Interactive Simulacra of Human Behavior (Park and colleagues, 2023) describes 25 simulated characters in a small town called Smallville. Each is driven by a language model with a long-term memory the authors call a memory stream. Section 4 describes the design and Section 6 the evaluation. [7]

The problem

Each character perceives a continuous flow of events over simulated days, far more than a prompt can hold. To behave consistently a character has to act on the few past experiences that matter at this moment, such as yesterday's conversation with the person now standing in front of it. It also has to draw general conclusions from many small observations, which raw event records do not provide.

Where this topic fits

The memory stream is episodic long-term memory. A retrieval function selects the subset of it that goes into the prompt each time the character decides what to do. A second process, reflection, turns groups of episodes into higher-level statements and stores them back into the same stream, where they are retrieved like any other memory.

How it is applied, step by step

  1. Every observation is appended to the memory stream as a record with a natural-language description, a creation timestamp and a most-recent-access timestamp.
  2. The language model rates how important each memory is on a scale from 1 (mundane, such as brushing teeth) to 10 (highly significant, such as a break-up).
  3. When the character must act, its current situation is the query. Every memory gets a recency score from exponential decay, its importance score, and a relevance score from embedding similarity.
  4. The three scores are rescaled to the range 0 to 1 and added with equal weights. The highest-ranked memories that fit in the context window go into the prompt.
  5. Because recency is measured from the last retrieval and not from creation, a memory that keeps being retrieved stays near the top, and one that is never used sinks.
  6. When the importance of recent events adds up past a threshold, the character generates reflections, which are stored in the stream with pointers to the memories they were drawn from.

Why this approach fits

Nothing is deleted, so the whole history stays available, and ranking decides what the model sees. Recency anchors the character in the present. Importance keeps rare, significant events reachable long after they happened. Relevance ties retrieval to the situation at hand. Reflection covers what raw episodes cannot: many small observations do not add up to a conclusion unless something synthesises them.

Limitation or tradeoff

The stream only grows. Decay lowers a memory's rank but puts no bound on storage or on the cost of scoring every record. The authors report retrieval failures in their evaluation: characters sometimes failed to retrieve the right memory, and sometimes embellished what they knew. Importance is rated once, by a model, at write time, so a wrong rating is never revisited. The setting is a simulation of invented characters with no privacy obligations, and the decay factor and weights were chosen for that environment, not tuned for a product.

What the sources document

  • The memory stream is described as a database that maintains a comprehensive record of an agent's experience. Each memory object contains a natural language description, a creation timestamp and a most recent access timestamp. [7]
  • Recency is an exponential decay function over the number of sandbox game hours since the memory was last retrieved, with a decay factor of 0.995. Importance is rated by the language model on a scale of 1 to 10. Relevance is the cosine similarity between the embedding vectors of the memory and the query. [7]
  • The recency, relevance and importance scores are normalised to the range 0 to 1 with min-max scaling and combined as a weighted sum, and in the authors' implementation all the weights are set to 1. [7]
  • Reflections are generated when the sum of the importance scores of the latest perceived events exceeds 150, which in practice was roughly two or three times a day, and each reflection is stored in the memory stream with pointers to the memory objects it cites. [7]
  • In the controlled evaluation the full architecture had a TrueSkill rating of 29.89, the ablation with no memory, planning or reflection had 21.21, and the crowdworker condition had 22.95. The authors also report agents failing to retrieve the correct memories and embellishing their knowledge. [7]

Amazon Bedrock AgentCore Memory: session events turned into long-term records in the background

Amazon Web ServicesDocumented in official docs

The Amazon Bedrock AgentCore developer guide documents AgentCore Memory, a managed service that stores an agent's short-term and long-term memory. The guide's running scenario is a customer support agent for a shopping website. [14][15][16][17][18]

The problem

An agent deployed as a stateless service loses everything between requests. A team building a support agent needs the conversation to survive a restart, and needs the agent to recognise a returning customer's preferences and earlier problems. It does not want to build and operate its own event store, extraction prompts, search index and background workers to get there.

Where this topic fits

The service covers both scopes. Short-term memory is the raw events of one session. Long-term memory is records extracted from those events by strategies the developer configures. The write path to long-term memory runs entirely in the background, so the agent's hot path only appends events and reads records.

How it is applied, step by step

  1. The developer creates a memory resource and attaches strategies, which decide what kinds of information are extracted. With no strategy the resource provides short-term memory only.
  2. During a conversation the agent stores each exchange as an event with the CreateEvent operation, tagged with a session identifier.
  3. To continue a session, even after a restart or when the customer returns later, the agent lists that session's events and reloads the conversation as it happened.
  4. After events are stored, a background process extracts insights according to each strategy and consolidates them with the records that already exist.
  5. Records are kept under namespaces. Session summaries, for example, are stored at session level, and episodes can be stored per strategy, per actor or per session.
  6. In a later session the agent calls RetrieveMemoryRecords with a query, and a semantic search returns the most relevant records to add to the context.

Why this approach fits

Separating raw events from extracted records keeps the hot path cheap (append and read) while the expensive model calls for extraction run asynchronously. The strategies turn the memory kinds from this lesson into configuration: facts, preferences, per-session summaries, and episodes with reflections. Managed consolidation deals with duplicates and contradictions that a team would otherwise handle in its own code.

Limitation or tradeoff

Asynchronous extraction means a fact is not in long-term memory straight away. The guide notes that episodic records are generated only once a completed episode is detected, and take longer when the conversation might still continue. Built-in strategies offer limited customisation, and overriding the prompts or managing the pipeline yourself moves work back to the team. Reflections can span several actors, and the guide tells developers to consider the privacy implications of that cross-actor analysis. The memory is also tied to one platform's operations and data model.

What the sources document

  • Short-term memory stores raw interactions as events created with the CreateEvent operation, each associated with a session through a session identifier, so that the agent can reload the conversation as it happened even if the service restarts or the customer returns later. [14]
  • Long-term memory generation is an asynchronous process that runs in the background after raw conversation is stored in short-term memory. It performs extraction and consolidation, and the RetrieveMemoryRecords operation performs a semantic search over the resulting records. [14]
  • Memory strategies determine what types of information are extracted from raw conversations, and if no strategies are specified, long-term memory records are not extracted for that memory. [15]
  • The built-in strategies are semantic, user preference, summary and episodic. A strategy is made of steps that can include extraction, consolidation and reflection, and several strategies can be combined. [16]
  • The summary strategy generates condensed summaries of conversations within a single session. Episodic memory records are generated only once a completed episode is detected, and reflections analyse multiple episodes to extract broader insights such as successful strategies and common failure modes. [17][18]

Google ADK context compaction: summarizing older session events on a sliding window

GoogleDocumented in official docs

The Agent Development Kit (ADK) documentation page Compress agent context for performance describes a built-in compaction feature for long-running sessions. Google's whitepaper Context Engineering: Sessions & Memory, the Day 3 reading of the Kaggle agents course, explains the design choices behind it. [19][5]

The problem

As an ADK agent runs, its session collects user instructions, retrieved data, tool responses and generated content. The documentation states that processing times typically increase as this context grows. The whitepaper adds context window limits, cost per token and falling answer quality. An application needs to bound what is sent to the model without each developer writing summarization code.

Where this topic fits

This is management of short-term memory. Compaction works on the event list of one session before model calls, and nothing is written to long-term memory. The whitepaper treats session compaction as the first case of a broader idea it calls memory generation: extracting persistent knowledge from a verbose and noisy source.

How it is applied, step by step

  1. The developer adds an EventsCompactionConfig to the App, with a compaction interval and an overlap size.
  2. The agent runs as usual and appends events to the session.
  3. When the configured number of events has completed, ADK summarizes that window of events with a model.
  4. The next window includes the last events of the previous one, as many as the overlap size says, so that context carries over from one summary to the next.
  5. As an alternative, a token threshold triggers compaction when the session passes it, and a retention size sets how many recent events stay uncompacted. When both strategies are configured, the token-based one takes priority.
  6. A developer who needs different summaries supplies a summarizer object with its own model and prompt template.

Why this approach fits

A count-based trigger is predictable, and the whitepaper calls that approach often good enough for managing context length. The overlap lowers the chance that a fact sitting on a window boundary falls between two summaries. Putting compaction in configuration instead of code means every agent in the application is bounded in the same way.

Limitation or tradeoff

A fixed interval compacts whether or not the conversation is at a natural break, so a summary can cut through the middle of a task. Every summary is written by a model, loses detail and costs an extra model call, which is why the whitepaper recommends running expensive summarization in the background and persisting the result. Compaction is also not long-term memory: nothing survives beyond the session unless a memory service is used as well. The feature depends on the ADK version: the documentation's support badge names Python v1.16.0.

What the sources document

  • The ADK documentation says the context compaction feature summarizes older session history using a sliding window approach for collecting and summarizing agent workflow event data within a Session. [19]
  • With a compaction interval of 3 and an overlap size of 1, the documentation's example compresses all 3 events when event 3 completes, events 3 to 6 when event 6 completes, and events 6 to 9 when event 9 completes, each time including the overlap of 1 prior event. [19]
  • A token threshold triggers compaction once it is reached, the event retention size is the number of recent events kept in raw form, and if both strategies are configured the system prioritises token-based compaction and skips sliding-window compaction for that turn. [19]
  • The whitepaper lists keeping the last N turns, token-based truncation and recursive summarization as compaction strategies, and count-based, time-based and event-based triggers for deciding when to compact. [5]
  • The whitepaper states that expensive operations such as recursive summarization should be performed asynchronously in the background with the results persisted, and that the agent must keep a record of which events are included in the compacted summary. [5]

4Common mistakes

  1. Storing whole transcripts and calling them long-term memory.

    Why it causes problems
    Retrieval returns greetings, filler and both sides of old dialogue instead of facts. The same fact is stored many times in different words, and contradictions are never resolved, so the model receives noise and you pay for it on every call.
    How to recognise it
    Memory records that start with a greeting or contain several turns of dialogue, many near-duplicate records for one fact, and a store that grows in step with message volume.
    How to fix it
    Extract discrete facts under topics you define, then consolidate each one against what is stored by creating, updating or deleting records. Keep the transcript in the thread store, where it belongs.

  2. Retrieving memories by similarity alone.

    Why it causes problems
    Old and trivial records that happen to share words or meaning with the query outrank current, important ones. In the worked example a trip cancelled a year earlier ranked first and the home airport ranked last.
    How to recognise it
    The agent brings up cancelled plans, old addresses or finished projects. The top search results have old timestamps, and nothing in the ranking code reads a timestamp.
    How to fix it
    Store a last-used time and an importance rating with each record and blend them into the score. Load stable facts from a profile so that they do not have to win a search at all.

  3. Appending new facts without ever updating or deleting old ones.

    Why it causes problems
    The store ends up holding two values for the same attribute, such as two home cities, and the model picks one arbitrarily. Stale personal data also stays in storage long after anyone needs it.
    How to recognise it
    One attribute stored with two values, record counts that only rise, and no code path that deletes a memory.
    How to fix it
    Give each kind of fact a stable key and replace on write, delete records that newer information contradicts, set a TTL on time-bound facts, and provide a delete operation for users.

  4. Reading and writing memories without scoping them to one user.

    Why it causes problems
    A search that is not filtered by owner can return another person's records, and the agent then repeats one customer's details to a different customer. That is a data leak, not a quality problem.
    How to recognise it
    Search calls that pass a query but no user or tenant identifier, a single shared namespace, and no test in which a second user tries to see the first user's memories.
    How to fix it
    Put the owner in the namespace or key of every record, enforce it in the storage layer and not in the prompt, and add a two-user test that must return nothing across users.

  5. Saving whatever a conversation or a tool result says without checking it.

    Why it causes problems
    A false statement or an instruction hidden in a web page or document becomes a stored memory and is loaded into every later session. One poisoned write keeps steering the agent after the original conversation is gone.
    How to recognise it
    Memory records phrased as commands to the agent, records whose origin is a tool output or a fetched page, and no field that records where a memory came from.
    How to fix it
    Record the source of every memory, do not create memories from untrusted tool output, validate content before it is written, and let users review what has been stored.

def compact(messages, summarise, budget=BUDGET, keep_recent=KEEP_RECENT):
    if tokens(messages) <= budget:
        return messages
    head, body = messages[0], messages[1:]
    cut = max(len(body) - keep_recent, 0)
    while cut > 0 and body[cut]["role"] == "tool":
        cut -= 1                      # keep a tool result together with its call
    old, recent = body[:cut], body[cut:]
    previous = ""
    if old and old[0]["content"].startswith(SUMMARY_PREFIX):
        previous, old = old[0]["content"][len(SUMMARY_PREFIX):].strip(), old[1:]
    if not old:
        return messages               # nothing new to fold into the summary
    summary = {"role": "user", "content": f"{SUMMARY_PREFIX} {summarise(previous, old)}"}
    return [head, summary, *recent]

A record of last Tuesday's drill therefore fades within three weeks unless the same error comes back and the record is retrieved again, which restarts its clock. For a learner who studies twice a week that is reasonable. For one who studies monthly the decay is too fast, and a per-day factor would fit better.

Part D

  • Time. Remove the exam date from the profile the day after 14 March. Delete episodic records that have not been retrieved for 180 days.
  • Contradiction. When the learner states a new level, goal or exam date, replace the profile field instead of adding a second value. When the learner says emojis are fine again, delete instruction 6.
  • User request. "Forget that" deletes the named record at once and confirms it. A settings page lists every stored record with a delete button, and closing the account deletes everything stored under that learner's namespace.

Check your answer

  • Did you place the team's correction rule and the learner's no-emoji request in procedural memory, with different owners?
  • Did you keep the dictionary result and the hospital remark out of long-term memory, and can you say why for each?
  • Is your half-life about 138 hours, or 5.8 days?
  • Is your recency after 7 days about 0.43, and does it fall below 0.1 after about 19 days?
  • Does each forgetting rule name its trigger and the records it affects?

    ArticleIntermediateFreeAbout 2 to 3 hours (estimate)

    When to use it
    When you are about to design memory for a real product and need the production concerns that this lesson only names.

    CourseBeginnerFree

    PaperAdvancedFreeAbout 1 to 2 hours (estimate)

    When your agent runs long single tasks, such as coding or research, and thread size is the problem you are trying to solve.
