Vector Databases and Similarity Search

A vector database stores embeddings together with ids and metadata, and answers one question quickly: which stored vectors are closest to this query vector? To stay fast on millions of vectors it uses an approximate nearest neighbor index such as HNSW or IVF, which examines a small part of the data and accepts that it will sometimes miss a true nearest neighbor.

1Overview

Why it matters

Semantic search, retrieval for RAG, similar-item recommendations and duplicate detection all reduce to the same operation: find the stored vectors nearest to a query vector. The embedding model produces that query vector with one call. The search over everything you have stored decides the latency, the memory bill and whether the right passage is found at all. When a RAG system fails to use a document that exists in its corpus, the cause is often in the store: an index that skipped the correct neighbor, a filter applied after the search that left three results where ten were requested, or a distance metric that does not match the embedding model.

Engineers who build retrieval have to decide whether to add pgvector to a Postgres database they already run, operate a dedicated vector store, or embed a library in a service. They also have to set index parameters whose defaults differ from product to product. Without knowing what those parameters trade, and without a way to measure recall, a team ships the defaults and cannot tell whether a bad answer came from the model or from retrieval.

Key terms

Vector store
A system that keeps embeddings with their ids and metadata and can return the stored vectors nearest to a query vector. It may be a dedicated database, a Postgres extension or a library inside your program.
Nearest neighbor search
Finding the k stored vectors with the smallest distance (or largest similarity) to a query vector. Also written k-NN search.
Approximate nearest neighbor (ANN)
A search that inspects only part of the data and returns neighbors that are very likely, but not guaranteed, to be the true nearest ones.
Distance metric
The rule that turns two vectors into one number saying how close they are. L2 distance, inner product and cosine similarity are the usual three.
Recall@k
The fraction of the true k nearest neighbors that an approximate search returned, averaged over a set of test queries.
Flat index
No index structure at all. Every query is compared with every stored vector, which gives exact results at a cost that grows with the size of the collection.
IVF (inverted file index)
An index that groups vectors into clusters with k-means and searches only the few clusters whose centres are closest to the query.
HNSW
Hierarchical Navigable Small World, an index that links each vector to near neighbors in a layered graph and finds results by walking that graph towards the query.
Metadata filter
A condition on stored fields, such as tenant, language or availability, that results must satisfy in addition to being close to the query. Some products call the fields a payload.
Quantization
Storing vectors in a compressed form, for example fewer bits per number or a short code per vector, to save memory at some cost in accuracy.

2Explanation

Introduction

In Embeddings you turned text into vectors and saw that texts with similar meaning land close together. That lets you compare two pieces of text. An application needs more: given one query vector, find the closest few among everything stored, which may be ten thousand support articles or billions of page fragments.

The obvious method is to compute the distance from the query to every stored vector and keep the smallest. This is called exact or flat search, and it always finds the true nearest neighbors. It is the right choice more often than people expect. Its cost grows in direct proportion to the number of vectors, though, so past some size it becomes too slow or too expensive for an interactive product.

A library handles the same problem with physical books. Nobody walks past every shelf. Books are grouped by subject, you go to the two or three sections that could hold what you want, and you scan only those. You may miss a relevant book that was shelved under a neighbouring subject. A vector index makes the same trade. It organises the vectors ahead of time so that a query looks at a small fraction of them, and it accepts that the result is occasionally not the exact top ten. This is approximate nearest neighbor (ANN) search.

A vector store keeps three things per item, whether it is a Postgres table with the pgvector extension or a dedicated service:

  • an id that points back to the source record,
  • the vector, typically a few hundred to a few thousand 32-bit floats,
  • metadata such as tenant, language, date or permissions, used to filter results.

On top of those rows it maintains an index that makes the search fast.

The write path embeds each chunk and stores it. The query path embeds the question with the same model, asks the index for the nearest vectors that pass the filter, and returns ids so that the application can fetch the text.

This lesson covers how closeness is measured, how the two main index families (IVF and HNSW) work and what their parameters trade, how to measure the accuracy you gave up, why metadata filters are harder than they look, and how to choose between pgvector, a dedicated store and a library. What to do with the retrieved text is the subject of Retrieval-Augmented Generation.

How it works

Measuring closeness

Every search needs a rule for "close". Three are in common use. For vectors aaa and bbb with ddd components:

The pgvector documentation (opens in a new tab) advises inner product for best performance when vectors are normalised to length 1; it needs no square root and no division. The rule is to use the metric your embedding model was trained for and to build the index for that same metric. pgvector exposes the metrics as operators: <-> for L2, <#> for negative inner product and <=> for cosine distance, which is 1 minus cosine similarity.

Exact search and recall

Exact search does NNN distance computations per query, each over ddd numbers. Storage is N×d×4N \times d \times 4N×d×4 bytes for 32-bit floats, so one million 1,536-dimensional vectors take 6.1 GB before any index is added.

An approximate index returns a top-kkk list that may differ from the exact one. Recall measures the damage:

recall@k=∣approximate top-k∩exact top-k∣k\text{recall@}k=\frac{\lvert \text{approximate top-}k \cap \text{exact top-}k\rvert}{k}recall@k=k∣approximate top-k∩exact top-k∣​

Recall 0.95 at k=10k=10k=10 means that on average 9.5 of the true 10 nearest neighbors come back. Every ANN index trades recall, query speed, memory and build time against each other. The trade is only visible when you run exact search on a sample of queries as the reference.

IVF: search a few clusters

An inverted file (IVF) index runs k-means over the vectors to find nlist centroids, then files every vector under its nearest centroid. A query is compared with the centroids first, and only the nprobe closest lists are scanned. The work per query is roughly

nlist+nprobe×Nnlist\text{nlist} + \text{nprobe}\times\frac{N}{\text{nlist}}nlist+nprobe×nlistN​

distance computations. With one million vectors, 1,000 lists and 10 probes that is 11,000 comparisons, or 1.1% of the data. The risk is a true neighbor that sits just across a cluster boundary, in a list that was not probed. Raising nprobe recovers it at a proportional cost, and the Faiss wiki (opens in a new tab) notes that nprobe = nlist gives the brute-force result again. The worked example below measures this curve.

pgvector's IVFFlat index suggests starting with rows/1000 lists up to a million rows and rows\sqrt{\text{rows}}rows​ beyond that, with lists\sqrt{\text{lists}}lists​ probes. Its default is 1 probe. It also tells you to create the index after the table has data, because the centroids are learned from the rows present at build time.

HNSW: walk a graph

Hierarchical Navigable Small World (HNSW), from a 2016 paper by Malkov and Yashunin (opens in a new tab), builds a graph where IVF builds clusters. Each vector is a node linked to a limited number of near neighbors, set by the parameter M. A search starts at an entry node and keeps moving to whichever linked node is closer to the query, like asking for directions and being passed from person to person.

Walking a single large graph would take many hops, so HNSW stacks layers. Every node is in layer 0. Each node also draws a random top level ⌊−ln⁡(u)⋅mL⌋\lfloor -\ln(u)\cdot m_L \rfloor⌊−ln(u)⋅mL​⌋, with uuu uniform between 0 and 1 and mL=1/ln⁡Mm_L = 1/\ln MmL​=1/lnM, which places a fraction M−lM^{-l}M−l of all nodes in layer lll or higher. Upper layers are sparse, so their links cover long distances.

A query enters at the top, walks greedily to the closest node in that layer, drops down one layer and repeats. At layer 0 it keeps a list of the best ef_search candidates found so far, explores their neighbors and returns the best kkk. The paper reports logarithmic complexity scaling of the search as NNN grows.

ParameterControlsRaising it gives
Mmaximum links per node in each layerbetter recall, more memory, slower build
ef_constructioncandidates examined when inserting a nodea better graph, slower build
ef_searchcandidates kept while answering a querybetter recall, slower queries

Defaults differ by product. pgvector uses m 16, ef_construction 64 and ef_search 40. Qdrant defaults to m 16 and ef_construct 100, and Spotify's Voyager to M 12 and ef_construction 200. pgvector's summary is that HNSW has a better speed-recall trade-off than IVFFlat but builds more slowly and uses more memory. The Faiss index guidelines (opens in a new tab) give the memory as d×4+M×2×4d\times 4 + M\times 2\times 4d×4+M×2×4 bytes per vector, because the full vectors and the links are both kept. Deletes and constant updates are the weak point of graph indexes: Faiss's HNSW index cannot remove vectors, and Airbnb (opens in a new tab) reports an HNSW index whose memory footprint grew too large under frequent listing updates.

When full vectors do not fit in memory, stores compress them (quantization). pgvector's halfvec type stores half-precision numbers, and Faiss's product quantization replaces each vector with a code of a few bytes. Compression lowers recall.

Metadata filtering

Real queries carry conditions such as one tenant, one language or items in stock. A filter can be combined with an ANN index in three ways.

StrategyHow it worksWhere it fails
Post-filterANN search first, then drop rows that fail the filterReturns fewer than kkk rows when few rows match
Pre-filterFind the matching rows first, then exact search over themSlow when many rows match
Filter inside the indexSkip non-matching nodes or lists during the searchNeeds index support; a strict filter can disconnect a graph

pgvector applies the filter after the index scan and gives the arithmetic: if a condition matches 10% of rows, the default ef_search of 40 leaves about 4 rows. Since version 0.8.0 its iterative index scans keep scanning until enough rows pass or a limit is reached. For filters known in advance it offers partial indexes and partitioning. Qdrant builds the filter into the graph. Its indexing documentation (opens in a new tab) describes extra graph edges derived from indexed payload fields, and a query planner that scans the matching points directly when the filter leaves only a few. A filter that every query carries, such as a tenant id, usually works best as a partition, so that a query only ever touches one tenant's vectors.

In pgvector the whole path, from table to filtered query, is four statements. The operator in ORDER BY must belong to the operator class the index was built with (<=> with vector_cosine_ops here), or Postgres cannot use the index for that query.

sql
CREATE TABLE chunks (id bigserial PRIMARY KEY, tenant_id int, body text, embedding vector(3));
CREATE INDEX ON chunks USING hnsw (embedding vector_cosine_ops) WITH (m = 16, ef_construction = 64);
SET hnsw.ef_search = 100;
SELECT id, body FROM chunks WHERE tenant_id = 7 ORDER BY embedding <=> '[0.1, 0.9, 0.2]' LIMIT 5;

Where the index lives

The index algorithms are the same everywhere. What differs is what surrounds them. A library gives you the index and nothing else. pgvector puts the index next to your relational data, so one SQL statement can filter, join and rank. A dedicated store adds filter-aware indexes, sharding and tenancy features, at the price of a second system to keep in sync. Stack Overflow's account (opens in a new tab) of choosing Weaviate shows the kind of requirement that settles the choice in practice: it had to be open source and self-hosted on their existing Azure infrastructure, support hybrid lexical and semantic search on the same data, and connect to their Spark pipelines. None of these requirements is a benchmark result. Combining keyword and vector results is covered in Advanced Retrieval.

Worked example: Building an IVF index in plain Python and measuring its recall against exact search

The script below builds a small IVF index by hand and measures what the approximation costs. It creates 2,000 vectors of 8 dimensions scattered around 25 topic centres, as a stand-in for document embeddings, plus 100 query vectors drawn the same way. It answers every query twice: once by exact search and once through the index with different nprobe values. It needs only the Python standard library (3.9 or later) and runs in a few seconds. Save it as ivf_demo.py.

python
import random

DIM, N_VECTORS, N_QUERIES, N_TOPICS = 8, 2000, 100, 25
N_LISTS, K, KMEANS_ROUNDS = 40, 10, 8
rng = random.Random(7)


def near(center, spread=0.4):
    """A point close to a topic centre: stands in for the embedding of one document."""
    return [c + (rng.random() * 2 - 1) * spread for c in center]


def dist2(a, b):
    """Squared L2 distance. It ranks vectors in the same order as L2 distance."""
    return sum((x - y) * (x - y) for x, y in zip(a, b))


topics = [[rng.random() for _ in range(DIM)] for _ in range(N_TOPICS)]
vectors = [near(topics[i % N_TOPICS]) for i in range(N_VECTORS)]
queries = [near(topics[i % N_TOPICS]) for i in range(N_QUERIES)]


def exact_search(query, k):
    """Flat search: compare the query with every stored vector."""
    return sorted(range(N_VECTORS), key=lambda i: dist2(query, vectors[i]))[:k]


def assign(centroids):
    """Put every vector id into the list of its nearest centroid."""
    lists = [[] for _ in centroids]
    for i, vector in enumerate(vectors):
        nearest = min(range(len(centroids)), key=lambda c: dist2(vector, centroids[c]))
        lists[nearest].append(i)
    return lists


def mean(ids):
    return [sum(vectors[i][d] for i in ids) / len(ids) for d in range(DIM)]


# Build the IVF index: k-means finds N_LISTS centroids, then each vector joins one list.
centroids = vectors[:N_LISTS]
for _ in range(KMEANS_ROUNDS):
    lists = assign(centroids)
    centroids = [mean(ids) if ids else centroids[c] for c, ids in enumerate(lists)]
lists = assign(centroids)


def ivf_search(query, k, nprobe):
    """Scan only the nprobe lists whose centroids are closest to the query."""
    probed = sorted(range(N_LISTS), key=lambda c: dist2(query, centroids[c]))[:nprobe]
    candidates = [i for c in probed for i in lists[c]]
    return sorted(candidates, key=lambda i: dist2(query, vectors[i]))[:k], len(candidates)


if __name__ == "__main__":
    truth = [set(exact_search(query, K)) for query in queries]
    sizes = sorted(len(ids) for ids in lists)
    print(f"{N_LISTS} lists, smallest {sizes[0]}, largest {sizes[-1]} vectors")
    print("nprobe  compared  recall@10")
    for nprobe in (1, 2, 3, 4, 6, 8, 12, 16, 40):
        hits = compared = 0
        for query, true_ids in zip(queries, truth):
            ids, scanned = ivf_search(query, K, nprobe)
            hits += len(true_ids & set(ids))
            compared += N_LISTS + scanned          # centroids first, then list members
        share = compared / (N_QUERIES * N_VECTORS)
        print(f"{nprobe:>6}  {share:>8.1%}  {hits / (N_QUERIES * K):>9.3f}")

How to read the result:

  • The compared column is the cost. It is the share of the 2,000 vectors each query was compared with, including the 40 centroids. Check the fourth row with the formula from the IVF section: the average list holds 2,000 / 40 = 50 vectors, so 4 probes cost 40 + 4 × 50 = 240 comparisons, which is 12.0% of 2,000.
  • One probe is cheap and wrong. Scanning only the closest list touches 4.7% of the data and finds 5.58 of the true 10 neighbors on average. The others sit in adjacent lists.
  • Recall rises quickly, then flattens. Four probes reach 0.918 and eight reach 0.991. Going from 0.991 to 1.000 takes about twice the work again. This shape is typical of ANN indexes, and it is why a target such as "recall 0.95 or better" is chosen first and the cheapest setting that meets it second.
  • Probing everything is worse than no index. With nprobe = 40 the result is exact, but each query costs 102% of a flat scan because the centroids were compared too.

The same procedure tunes a production index. Take a sample of real queries, compute their exact neighbors once, then sweep the query-time parameter (ivfflat.probes or hnsw.ef_search in pgvector) and pick the smallest value that meets your recall target. The absolute numbers above belong to this toy data set, with 2,000 vectors in 8 dimensions. Real embeddings have hundreds of dimensions and a different cluster structure, so measure on your own data.

Edge cases and limitations

A filtered query returns fewer rows than LIMIT asks for
With post-filtering, the index hands back a fixed number of candidates and the filter then removes most of them. pgvector's documentation gives the case of a condition matching 10% of rows with the default hnsw.ef_search of 40, which leaves about 4 rows. Nothing errors, so the only symptom is a short result list. Options are a larger candidate list, iterative index scans (pgvector 0.8.0 and later), a partial index or partition for that filter, or exact search when the filter leaves few rows.
An IVF index built on too little or unrepresentative data
The centroids are learned from whatever rows exist when the index is built. pgvector's documentation lists creating the index after the table has data as the first key to good recall, and names too little data for the number of lists as the likely cause of missing results. If the content later shifts to topics the centroids never saw, lists become unbalanced and recall drops at the same probes setting. Rebuild the index after large loads and track recall over time.
Deletes and updates wear down a graph index
HNSW is easy to add to and awkward to remove from. The Faiss guidelines state that its HNSW index does not support removing vectors, and Airbnb reports that frequent real-time updates to listing data made its HNSW index's memory footprint grow too large. If your vectors change constantly, check how your store handles deletes, plan periodic rebuilds, or consider a cluster-based index.
Changing the embedding model invalidates the whole index
Vectors from two different models live in different spaces, so distances between them mean nothing even when the dimensions match. A model change means re-embedding every item and building a new index. Notion reports that it switched to a newer embedding model during a store migration and did a full re-index. Store the model name and version with each vector, and never mix two models in one index.
The vector is too wide for the index type
Index types have dimension limits. pgvector's documentation lists up to 2,000 dimensions for an indexed vector column and up to 4,000 for the half-precision halfvec type. A 3,072-dimensional embedding therefore cannot be indexed as a plain vector column. Check the limit before choosing a model, then use a compressed type or a shorter embedding if the model can produce one.
Results change when an index is added
pgvector's documentation warns that, unlike ordinary database indexes, an approximate index changes query results. A test that passed with exact search can fail after CREATE INDEX with no code change. Tests that check retrieval should compare against an exact baseline with a recall threshold instead of asserting one fixed result list.

When to use it, and when something simpler is enough

Use it when

  • You need to find items by meaning instead of by exact words, as in semantic search, retrieval for RAG, similar-item recommendations or near-duplicate detection.
  • You have measured exact search at your vector count and query rate and it misses your latency budget, which is the point where an ANN index earns its complexity.
  • Queries combine similarity with structured conditions such as tenant, permissions or availability, and the store can apply those conditions inside the same query.
  • Slightly imperfect results are acceptable and you can measure recall against an exact baseline whenever data or parameters change.

Think twice when

  • Users search for exact identifiers, product codes, names or error strings. Keyword or full-text search finds those reliably, and embeddings often do not.
  • The collection has a few hundred items or fits in the model's context window. A loop over an array, or no retrieval at all, is simpler.
  • Every true match must be returned, for example in a legal or compliance search. An approximate index can silently miss results, so use exact search there.

A simpler alternative. Exact search with no ANN index: a table with a vector column and an ordinary index on the filter column, or an array of vectors scanned in memory. It has perfect recall and nothing to tune. It stops being enough when a measured full scan at your collection size and query rate exceeds your latency or cost budget. Add an approximate index at that point, and measure the recall you gave up.

Key takeaways

  • A vector store keeps an id, a vector and metadata per item, and an index that finds the nearest vectors to a query without comparing against all of them.
  • Use the distance metric your embedding model was trained for and build the index for that metric; for unit-length vectors L2, cosine and inner product give the same ranking.
  • IVF searches a few k-means clusters and HNSW walks a layered graph. Each has a query-time setting (nprobe, ef_search) that buys recall with extra work.
  • Approximate indexes can miss true neighbors, so measure recall@k against exact search on real queries before trusting any default.
  • A metadata filter applied after an approximate search can return fewer than k results; use iterative scans, partitions or a filter-aware index.
  • Start with exact search where your data already lives, and move to an ANN index, pgvector or a dedicated store only when measured latency, scale or filtering needs require it.

Example 1 of 5

Spotify Voyager: an HNSW library behind similar-item recommendations

SpotifyDocumented in an engineering article

Spotify's engineering post Introducing Voyager (October 2023) describes the open-source nearest-neighbor search library that succeeded Annoy inside Spotify. Voyager's Python API reference documents the index parameters and methods. [6][7]

The problem

Spotify uses nearest-neighbor search to recommend similar items, such as tracks, artists or albums, without running slow and expensive machine learning algorithms in real time. Its own library for this, Annoy, dated from 2013. The post says that by 2023 other systems could produce results twice as accurate in the same time, or results of similar quality in a tenth of the time. Spotify teams had experimented with the HNSW library hnswlib since 2018, but running it at scale showed that they wanted changes to its on-disk format, its API and its architecture that would have broken compatibility.

Where this topic fits

Voyager is the index and nothing else. Models elsewhere produce one vector per item. A build job creates a Voyager index from those vectors and saves it. A service loads the index into memory and answers nearest-neighbor calls in-process from Python or Java. No database server sits in the path, and what comes back is a list of item ids and distances for the recommendation code to use.

How it is applied, step by step

  1. A model outside Voyager produces one vector per item, for example per track.
  2. A build job creates an index with a distance space (Euclidean, inner product or cosine), the number of dimensions, and the HNSW parameters M and ef_construction, then adds the vectors. Adding builds the graph.
  3. The job saves the index to a file or stream. The post lists stream-based I/O compatible with Google Cloud Platform and index files with corruption detection among the library's features.
  4. A serving process loads the index and calls query with a vector and k. It receives the neighbor ids and their distances.
  5. The ef value, set on the index or per query, controls how many candidates the graph search examines, which is the recall-versus-speed setting described in this lesson.
  6. Choosing the 8-bit E4M3 storage type instead of 32-bit floats reduces memory, with less numeric precision per component.

Why this approach fits

Similar-item candidates are read far more often than the vectors change, the index can be rebuilt in batch when the model is retrained, and a "tracks like this one" lookup carries no per-user filter. Under those conditions the features of a database (transactions, filtering, a network API) add latency and operations work without adding value. An in-process HNSW index gives a strong speed-recall trade for data that fits in memory.

Limitation or tradeoff

A library leaves everything around the index to the team: distributing index files to servers, rebuilding when vectors change, splitting the data when one machine's memory is exceeded, and any filtering by attributes. The speed and accuracy figures in the post are Spotify's own comparison with Annoy and are not an independent benchmark.

What the sources document

  • Annoy, Spotify's earlier nearest-neighbor library, dates from 2013 and powered features including Discover Weekly and Home. [6]
  • Voyager is based on hnswlib, an implementation of HNSW. Spotify teams had experimented with hnswlib since 2018, and Voyager has served production traffic for many teams at Spotify since 2022. [6]
  • The post states that Voyager offers more than 10 times the speed of Annoy at the same recall, or up to 50% more accuracy at the same speed, and up to 4 times less memory usage than Annoy thanks to E4M3 8-bit floating point storage. [6]
  • The post describes nearest-neighbor search as a way to recommend similar tracks, artists or albums without running slow and expensive machine learning algorithms in real time, and says many Spotify systems run it in memory, which allows stateless deployments on Kubernetes and almost entirely removes the burden of maintaining a stateful database cluster. [6]
  • Voyager's Python Index constructor takes a space (Euclidean, InnerProduct or Cosine) and a number of dimensions, with M defaulting to 12 and ef_construction to 200, and query returns neighbor ids and distances. [7]

The facts above come from the cited sources. The steps and analysis in this example are our explanation of how they fit together.

Example 2 of 5

Faiss: compressed similarity search over one billion image vectors

Meta (Facebook AI Research)Documented in an engineering article

The engineering post Faiss, A library for efficient similarity search (March 2017) by Hervé Jégou, Matthijs Douze and Jeff Johnson introduces the library and reports results on data sets of a billion vectors. The Faiss wiki's index guidelines document the index types it combines. [3][5]

The problem

The post explains that traditional databases are built around structured tables and cannot find similar high-dimensional vectors efficiently. At a billion vectors a second problem appears: the vectors themselves do not fit in memory. The authors note that even 32 bytes per vector takes up a lot of memory when a billion vectors must be indexed. The task is to answer nearest-neighbor queries in milliseconds on a billion image descriptors within a fixed memory budget.

Where this topic fits

Faiss is a library, written in C++ with Python bindings, that sits inside a larger system. Vectors come from an image model upstream. Faiss supplies the index, which here combines two ideas from this lesson: partitioning the data so that a query visits only some cells (the IVF idea), and quantization, which stores a short code in place of each full vector. Results are ids and approximate distances.

How it is applied, step by step

  1. Describe the index as three parts, written in Faiss as the factory string OPQ20_80,IMI2x14,PQ20: a pre-processing transform, a partitioning scheme and an encoding.
  2. Train the index on sample vectors so that it learns the transform, the partition centroids and the quantizer codebooks. This is the training stage that the Faiss wiki describes for IVF indexes.
  3. Add the billion vectors. Each one is assigned to a partition and stored as a 20-byte product-quantizer code in place of its original floats.
  4. At query time, find the partitions nearest to the query and compare the query with the codes stored in those partitions only. This is how a typical IVF with product quantization search proceeds.
  5. Evaluate on three axes named in the post, which are speed, memory and accuracy, with accuracy measured against brute-force results.
  6. When more throughput is needed, use the GPU implementations. The post describes them as drop-in replacements for the CPU equivalents of the main indexing methods.

Why this approach fits

At a billion vectors memory is the binding constraint. An index that keeps full vectors, as HNSW does, would need hundreds of gigabytes for vectors of around a hundred float32 dimensions, before any graph links. Product quantization cuts the footprint to a few tens of bytes per vector, and partitioning keeps each query from touching all billion codes. Being a library also suits the workload: the index is built offline and queried by systems that need raw speed.

Limitation or tradeoff

Compression costs accuracy. The operating point reported in the post returns the true nearest neighbor in first position for 40% of queries, which is useful for generating candidates that a later stage re-ranks, and too weak to serve as a final answer. A product-quantized IVF index must also be trained before use and retrained if the data distribution moves. As with any library, storage, filtering, updates and serving are left to the caller.

What the sources document

  • Faiss is presented as a library for quickly searching for multimedia documents that are similar to each other, implemented in C++ with bindings in Python. [3]
  • The post names three axes for evaluating similarity search (speed, memory usage and accuracy) and measures accuracy against brute-force results with 1-recall@1 and 10-intersection. [3]
  • The authors write that Faiss focuses on methods that compress the original vectors because they are the only ones that scale to data sets of billions of vectors. [3]
  • For the Deep1B evaluation with memory limited to 30 GB of RAM, the index OPQ20_80,IMI2x14,PQ20 combines a pre-processing step, a partitioning mechanism and a product quantizer that generates 20-byte codes. The post reports a 1-recall@1 of 40 percent at a query time under 2 ms per vector. [3]
  • The Faiss index guidelines state that only the flat indexes guarantee exact results, that HNSW needs (d x 4 + M x 2 x 4) bytes per vector, and that product quantization is the option when memory is constrained. [5]

The problem

Grocery search has to respect what a particular store can sell right now. The post says prices, availability and discounts change several times a day and that the search system must reflect those changes. Text retrieval already ran in Postgres. Where this topic fits

The vector index moved to where the filterable data already lives. Item embeddings sit in the same Postgres search clusters as the item attributes, and pgvector indexes them. A search embeds the query, then one database round trip can restrict by availability and rank by vector distance. The candidates then go on to the later ranking stages.

How it is applied, step by step

  1. A bi-encoder model produces embeddings for items and for queries. Item vectors are stored in a pgvector column next to the item's other attributes.
  2. When a search arrives, the query is embedded and sent to Postgres together with the store context.
  3. Real-time inventory availability is applied as a pre-filter, which shrinks the set of items the semantic search has to consider. A typical implementation expresses this as a WHERE clause in the same SQL statement as the vector ORDER BY.
  4. Indexes are organised by retailer characteristics. The team replaced the one-index-per-retailer layout with what the post calls hybrid indexes.
  5. Postgres is tuned for the workload. The post mentions raising the parallel worker settings to 8 to speed up scans where the planner chooses not to use a pgvector index, and keeping the embedding column inline instead of in TOAST storage.
  6. The team validated the design on a lab-scale cluster that mimicked production traffic, then ran an online A/B test.

Why this approach fits

The deciding constraint is a filter on data that changes constantly. Availability already lives in Postgres, so running the vector search there turns the filter into part of the query over fresh data. A separate index would have to be kept in sync with that data, and its results post-processed. It also removes one service and one merge step from every search.

Limitation or tradeoff

The post reports that pgvector was marginally slower than FAISS for larger retailers in offline tests. A filtered vector query in Postgres also depends on the planner, which may choose an exact scan instead of the vector index, so latency needs tuning per workload. Only availability is used as a pre-filter so far; the post lists brand and category as attributes still to be explored.

Airbnb: IVF cluster ids used as an ordinary filter in the listing search index

AirbnbDocumented in an engineering article

Airbnb's engineering post Embedding-Based Retrieval for Airbnb Search and the related arXiv paper Applying Embedding-Based Retrieval to Airbnb Search (January 2026) describe the retrieval stage that narrows all eligible homes to a smaller pool for the ranking models. [9][10]

The problem

The retrieval stage must pick candidate listings by embedding similarity, under two constraints that the sources spell out. Pricing and availability data change constantly, which produces a high volume of real-time updates per listing. Most searches also carry filters, especially geographic ones. Airbnb evaluated HNSW and IVF. HNSW scored slightly better on recall, their main evaluation metric, but its index size and memory footprint grew too large under the update load, and applying filters in parallel with HNSW retrieval gave poor latency.

Where this topic fits

The approximate index is folded into the existing search engine. A two-tower model produces listing embeddings offline each day and query embeddings at request time. An offline k-means job assigns every listing to a cluster. The cluster id is stored on the listing document, next to the fields that the existing filters use. At query time the choice of clusters becomes one more filter.

How it is applied, step by step

  1. The listing tower runs offline each day and produces one embedding per listing. The query tower runs online for each search request.
  2. After the daily embedding run, a k-means job clusters the listing embeddings. The paper's experiments use 128 clusters.
  3. Each listing's cluster id is written into the listing index. Only cluster ids and centroids are needed at runtime.
  4. For a search, the query embedding is compared with the centroids and the closest nprobes clusters are selected.
  5. The search engine retrieves listings whose cluster id is among the selected clusters and which also pass the ordinary filters. In the paper's words, the cluster ids are treated as a normal filter in Apache Lucene.
  6. The retrieved listings are scored by similarity to the query embedding and passed to the ranking models.

Why this approach fits

IVF reduces approximate search to something a filter-first search engine already does well, which is intersecting sets of document ids. A graph index would have needed its own traversal that cooperates with filters and absorbs constant updates. Because clustering happens offline and the runtime state is one small integer per listing, updates to price or availability do not disturb the index at all.

Limitation or tradeoff

IVF recall depends on balanced clusters. The paper shows that with dot product similarity one or two clusters held about 20% of the data, and recall at 4 probes was 47% against 75% with Euclidean distance, so the choice of similarity function had to change. HNSW still scored slightly better on recall in their evaluation. Cluster assignments are also only as fresh as the daily job.

What the sources document

  • HNSW performed slightly better on evaluation metrics, but IVF offered the best trade-off between speed and performance. The high volume of real-time updates to pricing and availability made the HNSW index's memory footprint grow too large, and parallel retrieval with HNSW alongside filters gave poor latency. [9]
  • With IVF, listings are clustered beforehand and only cluster centroids and cluster assignments are stored in the search index. At serving time the cluster assignments are treated as a standard search filter. [9]
  • The paper states that an offline k-means clustering stage runs daily after the listing embeddings are recomputed, and that IVF's cluster ids can be treated as a normal filter in Apache Lucene. [10]
  • Table 2 of the paper reports recall@100 against true k-NN with 128 clusters, for the V3 model on a sample of query embeddings. Euclidean distance reaches 75% at 4 probes and 98% at 16, while dot product reaches 47% and 66%, which the authors attribute to Euclidean distance producing more balanced clusters. [10]
  • The paper reports that adopting IVF in the second version of the system reduced compute resources by around 16% relative to the baseline, and that the three retrieval launches together gave a 0.31% relative increase in conversion. [10]

Notion's engineering post Two years of vector search at Notion (February 2026) recounts how the store behind Notion AI Q&A was run and re-platformed after its launch in November 2023. turbopuffer's architecture documentation describes the engine that Notion migrated to. [11][12]

The problem

The post says Notion AI answers natural-language questions by searching content across a user's workspace and connected tools such as Slack and Google Drive, so that content has to be embedded and stored. It describes a waitlist of millions of workspaces at launch and indexes that were close to capacity within a month. The first store ran on dedicated "pod" clusters that coupled storage and compute. As indexes filled up, new sets had to be provisioned and workspaces routed to them, and the later serverless design is described as charging for usage where the first charged for uptime. Every page edit also triggered re-chunking, re-embedding and re-uploading of all the spans of that page, even when one character had changed.

Where this topic fits

Pages are chunked into spans, each span is embedded, and the vector is written to the store with metadata such as authors and permissions. In the first architecture the store was sharded with the workspace id as the partitioning key. The vector store sits between an indexing pipeline (batch jobs on Spark for existing documents and Kafka consumers for live edits) and the Q&A feature that retrieves spans for the model.

How it is applied, step by step

  1. Each page is split into spans. Each span is embedded and stored with its metadata.
  2. In the first architecture the workspace id is the partitioning key, and range-based partitioning routes each workspace to the right index. When a set of indexes nears capacity a new set is provisioned with a generation id that decides where reads and writes go.
  3. In May 2024 the workload moves to a serverless architecture that decouples storage from compute and charges by usage.
  4. The workload then moves to turbopuffer, which is built on object storage and treats each namespace as an independent index, so the application no longer manages shards. The move includes a full re-index of the corpus and a switch to a newer embedding model.
  5. To stop re-embedding unchanged content, two hashes are kept per span, one of the text and one of the metadata. A changed text hash means re-embed. A changed metadata hash alone means patch the metadata and keep the vector.

Why this approach fits

The post uses the workspace id as its partitioning key, which fits a product where the tenant boundary is the strongest filter available. In a typical multi-tenant design, making that boundary a partition means a search never touches other tenants' vectors, and most partitions stay small. With millions of tenants, many of them are likely to be idle at any moment (our assumption, as the post gives no activity figures), and an engine that keeps cold data on object storage and pays for compute on use matches that workload better than clusters sized for peak. turbopuffer's documentation adds that its index is centroid-based, because such an index needs fewer round trips to storage than a graph index.

Limitation or tradeoff

An engine built on object storage is slower on data it has not cached. turbopuffer's documentation gives a p50 of 874 ms for a first query over one million documents against 14 ms once cached. Migrating stores at this size is a long project: the post dates the turbopuffer evaluation and migration from May 2024 to January 2025. Partitioning by tenant also makes any search across tenants a different and more expensive problem.

4Common mistakes

  1. Adding an approximate index before measuring whether exact search is fast enough.

    Why it causes problems
    You take on build time, extra memory, parameters to tune and results that are no longer exact, for a collection that a full scan would have served within the latency budget.
    How to recognise it
    An HNSW or IVF index on a table with a few thousand rows, or nobody on the team able to state the latency of the same query without the index.
    How to fix it
    Time exact search at your real vector count and query rate first. Add an ANN index when that measurement misses the budget, and keep the exact query available as the reference for recall checks.

  2. Shipping index defaults without ever measuring recall.

    Why it causes problems
    Defaults are starting points and differ between products. pgvector's IVFFlat default of 1 probe scans a single list. Relevant items are skipped with no error, and the system looks as if the embedding model or the LLM were at fault.
    How to recognise it
    No test compares approximate results with exact results, and answers improve noticeably when ef_search or probes is raised by hand.
    How to fix it
    Keep a sample of real queries with their exact top-k. Sweep ef_search or probes, plot recall against latency and choose the smallest value that meets a stated recall target. Repeat after large data loads.

  3. Querying with a different distance metric from the one the index was built for.

    Why it causes problems
    In pgvector the planner cannot use an index whose operator class does not match the query operator, so the query silently becomes a full scan. In other stores a mismatch between the model's intended metric and the collection's metric ranks by vector length when you meant direction.
    How to recognise it
    EXPLAIN shows a sequential scan although a vector index exists, or longer documents rank high for unrelated queries when inner product is used on vectors that were not normalised.
    How to fix it
    Read the embedding model's documentation for its intended metric, normalise vectors if required, and create the index and write the query with the matching operator.

  4. Filtering in application code after fetching the top k from the vector index.

    Why it causes problems
    If the filter removes most candidates the user gets too few results, and over-fetching to compensate costs latency and still gives no guarantee. Instacart describes exactly this over-fetching as a limitation of its earlier FAISS service.
    How to recognise it
    Result counts that vary with the filter, a fetch size many times larger than the page size, and filtered searches that return nothing although matching items exist.
    How to fix it
    Pass the filter to the store so that it is applied during the search, use iterative scans or a filter-aware index, and turn filters that every query carries into partitions or partial indexes.

  5. Running a separate vector system with no plan for keeping it in sync with the source data.

    Why it causes problems
    Deleted or changed records stay searchable, permission changes arrive late, and the two systems disagree about what exists. Re-embedding everything on every change hides the problem at high cost.
    How to recognise it
    Search results that point to records which no longer exist or that the user may not see, and an embedding bill that tracks edit volume instead of new content.
    How to fix it
    Treat the vector store as a derived index. Record what was indexed, with a content hash and the model version, propagate deletes and metadata changes explicitly, and re-embed only when the text changes.

  6. Mixing vectors from two embedding models, or two versions of one model, in the same index.

    Why it causes problems
    Distances between vectors from different models carry no meaning, so results degrade in a way that looks random and cannot be fixed by tuning the index.
    How to recognise it
    Retrieval quality drops for content indexed after a model change, while older content still retrieves well with queries embedded by the old model.
    How to fix it
    Store the model identifier with every vector, build a new index for a new model, re-embed the whole collection, and switch queries over only when the new index is complete.

python
from ivf_demo import (K, N_LISTS, N_VECTORS, centroids, dist2, ivf_search,
                      lists, queries, rng, vectors)

in_stock = [rng.random() < 0.1 for _ in range(N_VECTORS)]   # about 10% of items pass the filter


def exact_filtered(query, k):
    """Ground truth: the k nearest vectors among those that pass the filter."""
    allowed = [i for i in range(N_VECTORS) if in_stock[i]]
    return sorted(allowed, key=lambda i: dist2(query, vectors[i]))[:k]


def post_filter(query, k, nprobe, fetch):
    """Search first, filter afterwards: keep the in-stock ids among the top `fetch`."""
    ids, _ = ivf_search(query, fetch, nprobe)
    return [i for i in ids if in_stock[i]][:k]


def filter_in_index(query, k, nprobe):
    """Apply the filter to the candidates inside the probed lists, then rank."""
    probed = sorted(range(N_LISTS), key=lambda c: dist2(query, centroids[c]))[:nprobe]
    candidates = [i for c in probed for i in lists[c] if in_stock[i]]
    return sorted(candidates, key=lambda i: dist2(query, vectors[i]))[:k]


def iterative(query, k, nprobe=4):
    """Probe more lists until k filtered results are found or every list is probed."""
    while True:
        ids = filter_in_index(query, k, nprobe)
        if len(ids) >= k or nprobe >= N_LISTS:
            return ids, nprobe
        nprobe = min(nprobe * 2, N_LISTS)


def report(name, results):
    returned = sum(len(ids) for ids in results) / len(results)
    hits = sum(len(set(ids) & true_ids) for ids, true_ids in zip(results, truth))
    print(f"{name:<34} {returned:>8.2f} {hits / (len(results) * K):>7.3f}")


truth = [set(exact_filtered(query, K)) for query in queries]
print(f"{sum(in_stock)} of {N_VECTORS} vectors pass the filter")
print(f"{'strategy':<34} {'returned':>8} {'recall':>7}")
report("post-filter, fetch 10, nprobe 4", [post_filter(q, K, 4, 10) for q in queries])
report("post-filter, fetch 40, nprobe 4", [post_filter(q, K, 4, 40) for q in queries])
report("post-filter, fetch 200, nprobe 8", [post_filter(q, K, 8, 200) for q in queries])
report("filter in index, nprobe 4", [filter_in_index(q, K, 4) for q in queries])
report("filter in index, nprobe 16", [filter_in_index(q, K, 16) for q in queries])
runs = [iterative(q, K) for q in queries]
report("iterative, start at nprobe 4", [ids for ids, _ in runs])
print("average nprobe used by iterative:", sum(n for _, n in runs) / len(runs))

  • Filtering inside the index fixes the count before it fixes the quality. At nprobe 4 almost every query gets 10 results, yet recall is 0.718. Without a filter the same setting gave 0.918 in the worked example. In-stock items are ten times sparser, so the 10 nearest of them are spread over more lists. Sixteen probes bring recall to 0.981.
  • Stopping at k results is not a recall guarantee. The iterative strategy stops as soon as it has 10 results, which is nearly always after the first round (average nprobe 4.04), so its recall of 0.722 is barely above the fixed nprobe 4 run. A full result page tells you nothing about whether the best items are on it. Tune the starting nprobe against the filtered ground truth.

If the team later adds HNSW, a post-filtered query with ef_search 40 would return about 40 × 1/12 ≈ 3.3 rows where 10 were requested. The fixes are iterative index scans (pgvector 0.8.0 and later), a higher ef_search, or partitioning the table by product. Measurement: latency of the exact filtered query at 5 queries per second.

Team B. Raw vectors: 50,000,000 × 768 × 4 = 153.6 GB, more than twice the 64 GB available. HNSW with M = 32 needs 50,000,000 × (3,072 + 256) = 166.4 GB, which is worse. Product quantization with 64-byte codes needs 50,000,000 × 64 = 3.2 GB, a 48-fold reduction from 3,072 bytes per vector. Nothing here needs a server, filters or concurrent writes, so a library fits: Faiss with an IVF index and PQ codes. The Faiss guidelines suggest IVF262144_HNSW32 as the coarse structure for 10 to 100 million vectors. The first parameter to tune is nprobe. Measurement: recall@k of the compressed index against exact search on a sample of a few thousand products, because compression lowers recall. If it is too low, re-rank the top candidates with the original vectors read from disk.

Team C. Raw vectors: 2,000,000,000 × 1,024 × 4 = 8.19 TB. This cannot be held in memory as one index at any sensible cost. The average workspace has 2,000,000,000 / 100,000 = 20,000 vectors, about 82 MB raw. Because every query names one workspace, partition by workspace. A search then touches one small partition, and the tenant filter costs nothing. For an average workspace even an exact scan of 20,000 vectors is feasible, while the largest workspaces need an ANN index. With most tenants idle, an engine that keeps cold partitions on cheap storage and loads them on demand suits the workload, as in the move to turbopuffer that Notion describes. A dedicated store with namespaces or per-tenant partitions is the choice. A single Postgres table would have to hold all 8 TB behind one index, and a library would leave you to build the tenancy, storage and routing yourself. Measurement: latency of the first query against a cold workspace, and the distribution of workspace sizes, since a few very large tenants can dominate cost.

Check your answer

  • Did you get 0.49 GB, 153.6 GB and 8.19 TB for the three raw vector sizes?
  • Did you find that team A's post-filtered query returns about 3 rows where 10 were requested?
  • Did you show that 64-byte codes for team B take 3.2 GB and say that recall must then be measured?
  • Did you compute 20,000 vectors for the average workspace of team C and use it to justify partitioning?
  • Does each recommendation name a measurement that could prove it wrong?

6Curated resources

Chosen for accuracy and usefulness, not search rank. Time figures are estimates.

  • pgvector: Open-source vector similarity search for Postgres (README) (opens in a new tab)

    pgvector project on GitHub

    DocumentationIntermediateFreeAbout 45 minutes (estimate)

    What it teaches
    The complete pgvector reference in one page: vector types, the distance operators, HNSW and IVFFlat options with their defaults, filtering, iterative index scans, and how to check recall against exact search.
    When to use it
    When you are ready to store embeddings in Postgres, and again whenever a filtered query returns fewer rows than expected.

  • Hierarchical Navigable Small Worlds (HNSW) (opens in a new tab)

    Pinecone (Faiss learning series)

    ArticleIntermediateFreeAbout 30 minutes (estimate)

    What it teaches
    A slower, illustrated walk through HNSW, from skip lists and navigable small world graphs to the layered search, followed by Faiss experiments that show how M, efConstruction and efSearch change recall, search time and memory on the Sift1M data set.
    When to use it
    After this lesson, when you want to see the graph search drawn step by step or need a feel for how much memory a larger M costs.

  • Guidelines to choose an index (opens in a new tab)

    Faiss wiki (facebookresearch on GitHub)

    DocumentationAdvancedFreeAbout 20 minutes (estimate)

    What it teaches
    A decision guide from the Faiss maintainers: when a flat index is enough, when to use HNSW, how many IVF centroids to use for each data set size, and which product quantization setting matches a memory budget.
    When to use it
    When you have to choose an index type and its sizes for a specific number of vectors and a specific amount of memory.

  • Filtering in Vector Search: When to Use What (opens in a new tab)

    Qdrant

    DocumentationIntermediateFreeAbout 20 minutes (estimate)

    What it teaches
    How one dedicated store handles filters: why it filters during the graph search, why every filtered field needs a payload index, how the query planner picks a strategy, and how to lay out many tenants in one collection.
    When to use it
    When your queries always carry filters or tenant ids and you are comparing how different stores apply them.

  • ANN-Benchmarks (opens in a new tab)

    Martin Aumueller, Erik Bernhardsson and Alec Faitfull

    InteractiveIntermediateFree

    What it teaches
    Recall against queries-per-second plots for dozens of ANN implementations on standard data sets, which show the recall-speed curve of each index type and how far parameter choices move a single library along it.
    When to use it
    When you want to compare index families or libraries on neutral data before running your own measurements, which you should still do.
