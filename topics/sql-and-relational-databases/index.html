SQL and Relational Databases

A relational database stores data as tables of rows and columns, links the tables to each other through keys, and applies groups of changes completely or not at all. SQL is the language used to define those tables and to ask questions of them, and PostgreSQL is a widely used open-source relational database.

1Overview

Why it matters

Most business data you will meet on a customer project already lives in a relational database: accounts, orders, tickets, invoices, permissions. To build anything on top of it you have to pull the right rows out, and the common ways of getting that wrong are quiet ones. A join that multiplies rows doubles a revenue figure without raising an error. A filter on a column with no index works on a test table and times out on the production one. Two updates that should have been one transaction leave money debited from one account and never credited to the other.

The same skills carry into AI work. Retrieval pipelines, evaluation sets, agent memory and application state are usually tables, and a model that writes SQL for a user still needs someone who can read the query plan and say why it is slow. Knowing what a relational database is good at also tells you when to pick something else, such as a key-value store for data that is only ever looked up by one key.

Before you start

No prerequisites. You can start here.

What you will be able to do

  • Define tables with primary keys, foreign keys and check constraints, and say what each one stops from happening.
  • Write queries that join and aggregate, and predict the rows returned by INNER versus LEFT JOIN and by WHERE versus HAVING.
  • Read an EXPLAIN (ANALYZE, BUFFERS) plan, spot a sequential scan that throws most rows away, and fix it with an index.
  • Group related changes in a transaction and explain what COMMIT, ROLLBACK and the default isolation level guarantee.
  • Use everyday PostgreSQL tools such as psql meta-commands, ANALYZE, CREATE INDEX CONCURRENTLY and timeouts.
  • Decide from a workload's access patterns whether a relational database or a NoSQL store is the better fit.

Key terms

Primary key
A column, or group of columns, whose value identifies exactly one row of a table. It must be unique and can never be null.
Foreign key
A column whose values must match a key in another table, so that a row can only refer to something that exists.
Join
A query operation that pairs rows from two tables wherever a condition, usually one key equal to another, is true.
Aggregate function
A function such as count, sum or avg that computes one result from many input rows.
Index
A separate sorted structure, by default a B-tree, that lets the database find rows by a column's value without reading the whole table.
Query plan
The tree of steps the database chose in order to run a query, shown by the EXPLAIN command.
Sequential scan
Reading every row of a table in storage order and keeping the rows that pass the filter.
Transaction
A group of statements that the database applies as a single all-or-nothing unit.
Isolation level
The setting that decides how much of other transactions' unfinished or recently committed work a transaction can see.
NoSQL store
A database that does not use the relational model, such as a key-value, wide-column or document store. It usually gives up joins or multi-row transactions in exchange for easy partitioning across servers.

2Explanation

Introduction

If you have used a spreadsheet you already know the shape of relational data: a sheet has named columns, and each row describes one thing. A relational database keeps many such sheets, called tables, and adds three things a spreadsheet does not give you. It enforces rules about what a row may contain. It lets many programs read and write at the same time without corrupting each other's work. And it answers questions that span several tables in one request.

Take a shop. One table, customers, has a row per customer. Another, orders, has a row per order. An order does not copy the customer's name and city. It stores the customer's id, a small number that points at one row in customers. That pointer is a foreign key, and the column it points at is the primary key of the other table. Because each fact is stored once, changing a customer's city is a one-row update and every order sees it immediately. To read an order together with its customer you join the two tables on that key.

SQL (Structured Query Language) is how you talk to the database. It is declarative: you describe the rows you want, and a component called the planner works out how to fetch them, for example whether to read a whole table or to use an index. The lesson keeps returning to this split. You write what, EXPLAIN shows you how, and an index or a rewritten query changes the how without changing the answer.

The lesson covers, in order: tables, keys and constraints; joins; aggregation; indexes and query plans; transactions; the PostgreSQL tools you use every day; and the workloads where a non-relational (NoSQL) store is the better choice. The worked example and the exercise solutions were run on PostgreSQL 18, the current major version when this was written. You need nothing installed to follow along: the PGlite REPL (opens in a new tab) runs a real PostgreSQL build inside a browser tab, and any PostgreSQL server with psql behaves the same way.

To see where these tables sit in a larger system afterwards, read Data Pipelines and ETL and System Design Fundamentals.

How it works

Tables, keys and constraints

A table is created with a list of columns, a type for each, and constraints, which are rules the database checks on every insert and update:

sql
CREATE TABLE customers (
  id     integer PRIMARY KEY,
  name   text NOT NULL,
  credit numeric(10,2) NOT NULL DEFAULT 0 CHECK (credit >= 0)
);
CREATE TABLE orders (
  id          integer PRIMARY KEY,
  customer_id integer NOT NULL REFERENCES customers (id),
  amount      numeric(10,2) NOT NULL CHECK (amount > 0)
);
  • A primary key is unique and not null, and a table has at most one. PostgreSQL creates a unique B-tree index for it automatically.
  • A foreign key (REFERENCES) means the value must appear in some row of the other table. The constraints chapter (opens in a new tab) calls this referential integrity. ON DELETE decides what happens when the referenced row is removed: raise an error (NO ACTION, the default), CASCADE to delete the referencing rows too, or SET NULL.
  • NOT NULL and CHECK reject rows with missing or impossible values.

A violated constraint is an error, not a warning, so bad data is kept out whichever program tried to write it.

Joins

A join (opens in a new tab) pairs rows of two tables wherever the ON condition is true.

JoinRows returned
a JOIN b (inner)Only pairs that match. A customer with no orders disappears.
a LEFT JOIN bEvery row of a at least once. Where b has no match, its columns are null.
a FULL JOIN bUnmatched rows from both sides as well, padded with nulls.

Give tables short aliases and qualify every column (o.amount, not amount). The PostgreSQL tutorial recommends this so that a query does not break when a column of the same name is later added to the other table.

Aggregation and the order of clauses

An aggregate function (opens in a new tab) (count, sum, avg, min, max) turns many rows into one value, and GROUP BY produces one output row per group. The clauses of a SELECT are not processed in the order you write them. The documented order (opens in a new tab) explains most beginner errors:

WHERE runs before grouping, so it filters rows and cannot contain an aggregate. HAVING runs after grouping, so it filters groups. Without ORDER BY, rows come back in whatever order was fastest to produce, and that order can change from one day to the next.

Indexes and query plans

With no index, the only way to find the orders of customer 42 is a sequential scan: read every row and test it. An index (opens in a new tab) is a sorted copy of one or more columns with pointers back to the rows, like the index at the back of a book. The default type, B-tree, serves equality and range conditions (=, <, >, BETWEEN, IN) and can return rows already sorted.

sql
CREATE INDEX orders_customer_id_idx ON orders (customer_id);

For a table of nnn rows with rrr rows per page and fff entries per index page, a scan reads about n/rn/rn/r pages. Finding one row through a B-tree reads about ⌈log⁡fn⌉+1\lceil \log_f n \rceil + 1⌈logf​n⌉+1 pages: one per level of the tree, plus the table page that holds the row.

Indexes are not free. Every insert and update must maintain each one, and the PostgreSQL manual says indexes that are seldom used should be removed. Three rules cover most cases:

  • A foreign key does not create an index on the referencing column. Add one if you filter or join on it.
  • A multicolumn index on (a, b) is most useful when the query constrains a, its leading column.
  • When a large share of the table matches, the planner ignores the index and scans, and it is right to.

The planner estimates a cost for each candidate plan from table statistics and picks the cheapest. EXPLAIN (opens in a new tab) prints the chosen plan as a tree, with scan nodes at the bottom and join, sort and aggregate nodes above them.

text
Seq Scan on orders  (cost=0.00..1887.08 rows=100 width=5)

The four numbers are the estimated start-up cost, total cost, rows returned and row width in bytes. Cost is in arbitrary units in which reading one page sequentially costs 1.0. EXPLAIN (ANALYZE, BUFFERS) runs the query for real and adds the actual rows, the time, and the number of 8 kB pages touched. (In PostgreSQL 18, ANALYZE switches BUFFERS on by itself, so plain EXPLAIN ANALYZE prints the same counts. Older versions need it spelled out.) Read it for three things: a Seq Scan on a big table, a large Rows Removed by Filter, and estimated rows far from actual rows, which points to stale statistics that ANALYZE refreshes.

Plan nodeWhat it does
Seq ScanReads the whole table
Index ScanWalks the index and fetches each matching row
Bitmap Index Scan + Bitmap Heap ScanCollects matches from the index, then reads those pages in storage order
Nested LoopFor each row of one input, looks up its matches in the other

Merge JoinWalks two inputs that are both sorted on the join key

Transactions

A transaction (opens in a new tab) bundles several statements into one all-or-nothing operation:

sql
BEGIN;
UPDATE customers SET credit = credit - 30 WHERE id = 1;
UPDATE customers SET credit = credit + 30 WHERE id = 3;
COMMIT;   -- or ROLLBACK; to undo both

The guarantees are abbreviated ACID. A transaction is atomic (all of its steps or none), keeps the data consistent with every constraint, is isolated (other sessions never see its half-finished state) and is durable (once COMMIT returns, the change has been logged to disk). Without BEGIN, each statement is its own transaction.

Isolation comes in levels. PostgreSQL's default, Read Committed (opens in a new tab), gives each statement a snapshot of the data committed before that statement began, so two SELECTs in one transaction can see different data. An UPDATE that reaches a row another transaction is changing waits for that transaction to finish. Repeatable Read and Serializable keep one snapshot for the whole transaction, and may fail with a serialization error that the application must answer by retrying the whole transaction.

The backslash commands belong to psql (opens in a new tab), the terminal client, not to SQL. A plain CREATE INDEX lets reads continue but blocks inserts, updates and deletes until it finishes, which is why production migrations use CONCURRENTLY. EXPLAIN ANALYZE really executes the statement, so wrap a write in a transaction that you roll back. Both timeouts (opens in a new tab) are off by default.

When a NoSQL store fits better

Relational databases are built for flexible questions over related data. AWS's design guide for DynamoDB (opens in a new tab) states the trade plainly: in a relational system data can be queried flexibly but queries are relatively expensive, while a NoSQL store answers a limited number of query shapes efficiently and anything else slowly. The Dynamo paper (opens in a new tab) describes the workload these stores were built for: services such as a shopping cart that only read and write one item by its key, where the authors found a relational database inefficient and a limit on scale and availability.

StoreData modelFits when
Key-valueOne value per keySessions, carts and caches that are always fetched by one id
Wide-columnRows grouped by a partition key and sorted inside itVery large append-heavy data read by key and range, such as the messages of a channel
DocumentOne nested JSON document per keyAn object is always read and written whole

What you give up is usually joins, ad hoc queries and transactions across items, so you must know your access patterns before you design the schema. Flexible fields alone are not a reason to leave: PostgreSQL's jsonb (opens in a new tab) type stores and indexes JSON documents beside ordinary columns.

Worked example: An orders database on PostgreSQL 18: keys, a join, an index and a transaction

Everything below was run on PostgreSQL 18.3. Enter one statement at a time in psql or the PGlite REPL (line breaks inside a statement do not matter, so you may join the lines). Timings will differ on your machine, and the planner's estimated row counts can shift slightly because ANALYZE samples the table. Actual row counts and page counts should not differ.

1. Two tables linked by a key

sql
CREATE TABLE customers (
  id     integer PRIMARY KEY,
  name   text NOT NULL,
  city   text NOT NULL,
  credit numeric(10,2) NOT NULL DEFAULT 0 CHECK (credit >= 0)
);
CREATE TABLE orders (
  id          integer PRIMARY KEY,
  customer_id integer NOT NULL REFERENCES customers (id),
  placed_on   date NOT NULL,
  status      text NOT NULL CHECK (status IN ('paid', 'pending', 'refunded')),
  amount      numeric(10,2) NOT NULL CHECK (amount > 0)
);
INSERT INTO customers VALUES
  (1, 'Asha', 'Pune', 50), (2, 'Ben', 'Leeds', 20),
  (3, 'Chen', 'Pune', 0),  (4, 'Dara', 'Cork', 75);
INSERT INTO orders VALUES
  (101, 1, '2026-09-01', 'paid', 120.00), (102, 1, '2026-09-03', 'paid', 80.00),
  (103, 2, '2026-09-03', 'paid', 45.50),  (104, 2, '2026-09-04', 'refunded', 45.50),
  (105, 3, '2026-09-05', 'paid', 300.00), (106, 1, '2026-09-07', 'pending', 60.00);

The foreign key now refuses an order for a customer who does not exist. INSERT INTO orders VALUES (107, 9, '2026-09-08', 'paid', 10.00); fails with:

text
ERROR:  insert or update on table "orders" violates foreign key constraint "orders_customer_id_fkey"

2. Join and aggregate: paid revenue per customer

sql
SELECT c.name, count(o.id) AS paid_orders, coalesce(sum(o.amount), 0) AS revenue
FROM customers c
LEFT JOIN orders o ON o.customer_id = c.id AND o.status = 'paid'
GROUP BY c.id, c.name
ORDER BY revenue DESC, c.name;

Asha's 200.00 is 120.00 + 80.00. Her pending order and Ben's refund are excluded by the ON condition. Dara has no orders, and the LEFT JOIN keeps her with a count of 0. Move o.status = 'paid' into a WHERE clause and Dara's row vanishes, because her null status fails the filter. Adding HAVING sum(o.amount) >= 100 would keep only Chen and Asha.

3. Make the table big enough for the planner to care

sql
INSERT INTO customers
SELECT g, 'Customer ' || g, 'Pune', 0 FROM generate_series(5, 1000) AS g;
INSERT INTO orders
SELECT 1000 + g, 1 + g % 1000, DATE '2026-01-01' + g % 365, 'paid', 10 + g % 90
FROM generate_series(1, 100000) AS g;
ANALYZE;

orders now has 100,006 rows in 637 pages, and every customer has 100 generated orders. Ask for one customer's total and look at the plan:

sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT count(*), sum(amount) FROM orders WHERE customer_id = 42;
text
Aggregate  (cost=1887.58..1887.59 rows=1 width=40) (actual time=8.800..8.800 rows=1.00 loops=1)
  Buffers: shared hit=637
  ->  Seq Scan on orders  (cost=0.00..1887.08 rows=100 width=5) (actual time=0.000..8.700 rows=100.00 loops=1)
        Filter: (customer_id = 42)
        Rows Removed by Filter: 99906
Execution Time: 8.800 ms

The scan read all 637 pages and threw away 99,906 of 100,006 rows. You can rebuild its cost estimate by hand: 637 pages × 1.0, plus 100,006 rows × 0.01, plus 100,006 filter checks × 0.0025, is 1887.08.

4. Add the index the foreign key did not create

sql
CREATE INDEX orders_customer_id_idx ON orders (customer_id);

The same EXPLAIN now prints:

text
Aggregate  (cost=272.22..272.23 rows=1 width=40) (actual time=0.800..0.800 rows=1.00 loops=1)
  Buffers: shared hit=100 read=2
  ->  Bitmap Heap Scan on orders  (cost=5.07..271.71 rows=100 width=5) (actual time=0.100..0.600 rows=100.00 loops=1)
        Recheck Cond: (customer_id = 42)
        Heap Blocks: exact=100
        ->  Bitmap Index Scan on orders_customer_id_idx  (cost=0.00..5.04 rows=100 width=0) (actual time=0.100..0.100 rows=100.00 loops=1)
              Index Cond: (customer_id = 42)
Execution Time: 0.900 ms

Two index pages located the 100 rows, which sit on 100 different table pages: 102 pages instead of 637, and no rows discarded. The answer is unchanged, a count of 100 and a sum of 5100.00. (Planning lines and repeated buffer lines are trimmed from both plans, and the Index Searches: 1 line that PostgreSQL 18 adds is trimmed from the second.)

The index does not help every query. EXPLAIN SELECT count(*) FROM orders WHERE customer_id <= 900; still shows a Seq Scan: the planner estimates that about 90,000 rows match (90,175 on our latest run), and one pass over the table is cheaper than reaching nearly all of it through the index.

5. Move credit atomically

Try to move 30.00 of credit to Chen from Ben, who has only 20.00:

sql
BEGIN;
UPDATE customers SET credit = credit + 30 WHERE id = 3;   -- Chen: 0 -> 30
UPDATE customers SET credit = credit - 30 WHERE id = 2;   -- Ben: 20 -> -10
text
ERROR:  new row for relation "customers" violates check constraint "customers_credit_check"

The first update had succeeded: a SELECT inside the transaction showed Chen at 30.00. After the error, PostgreSQL rejects every further statement with current transaction is aborted, commands ignored until end of transaction block. ROLLBACK; ends it, and both rows are back where they started: Ben 20.00, Chen 0.00. The same transfer from Asha, who has 50.00, succeeds, and after COMMIT the balances are Asha 20.00, Ben 20.00, Chen 30.00 and Dara 75.00. The total is 145.00 before and after.

Clean up with DROP TABLE orders, customers;, or keep the tables for the second exercise.

Edge cases and limitations

NULL never equals anything, including NULL
A comparison with NULL is neither true nor false, so a filter written as agent_id = NULL returns no rows even when some values are null. Write IS NULL. In the first exercise's data the equals form counts 0 tickets and IS NULL counts 1. Aggregates skip nulls too: count(column) counts only non-null values while count(*) counts rows, and avg ignores missing values instead of treating them as zero. By default a unique constraint in PostgreSQL also accepts several rows whose value is null.
A WHERE filter on the right-hand table cancels a LEFT JOIN
A left join fills the right-hand columns with nulls where there is no match. A WHERE condition on one of those columns is false for the padded rows, so they are removed and the result is the same as an inner join. In the worked example, moving status = 'paid' from ON to WHERE drops the customer with no orders and the report has 3 rows instead of 4. Put conditions about which right-hand rows may match in ON, and conditions on the finished result in WHERE.
A join can multiply rows before an aggregate adds them up
Joining orders to a table that has several rows per order, such as order items, repeats each order once per item. A sum of the order amount taken after that join counts it once per item: order 101 is 120.00, but joined to two item rows its sum is 240.00, and no error is raised. Aggregate at the level the value belongs to. Sum order amounts before joining to items, or sum a value that is stored on the item rows.
The planner skips an index that would not help
With the index on customer_id in place, the filter customer_id <= 900 still gets a sequential scan in the worked example, because about 90% of the rows match and one pass over 637 pages is cheaper than index visits to nearly all of them. Tiny tables behave the same way: the PostgreSQL manual notes that a table occupying a single page is almost always scanned whatever indexes exist. A plan seen on a toy table therefore says little about the plan on a large one, so test with production-sized data.
One error aborts the whole transaction in PostgreSQL
After any statement fails inside BEGIN, PostgreSQL refuses further statements with the message that the current transaction is aborted, until you issue ROLLBACK. The earlier statements of that transaction are undone as well. Code that catches the error and carries on using the same transaction fails on its next query. Roll back and retry the whole unit, or set a SAVEPOINT before the risky statement and return to it with ROLLBACK TO.
Two reads in one transaction can disagree
Under the default Read Committed level each statement sees the data committed before that statement started. If another session commits between your two SELECTs, the second sees the change even though both are in one transaction, so a report that reads a total and then the detail rows may not add up. Use Repeatable Read for multi-statement reads that must agree, and be ready to retry: at that level and at Serializable, PostgreSQL can cancel a transaction with a serialization failure (SQLSTATE 40001).

When to use it, and when something simpler is enough

Use it when

  • The data has several kinds of record that refer to each other, and you need to ask questions you cannot list in advance, such as reports, filters and ad hoc analysis.
  • Several rows or tables must change together or not at all, as with money, stock levels, bookings or permissions.
  • Rules such as uniqueness, valid references and allowed value ranges should be enforced in one place, whichever program writes the data.
  • The write load fits on one primary server, with replicas added for reads. That covers most applications. OpenAI reports serving ChatGPT and its API from a single PostgreSQL primary with nearly 50 read replicas, while moving its shardable, write-heavy workloads to a sharded system.

Think twice when

  • Every request reads or writes one item by a known key, at a volume or size beyond a single server, and you can do without joins and multi-row transactions. A key-value or wide-column store partitions such data with far less effort.
  • The main workload is one a specialised engine handles better: analytical scans over billions of rows (a columnar warehouse), relevance-ranked text search (a search engine) or a cache whose contents may be lost (an in-memory store).

A simpler alternative. SQLite, a relational database kept in a single file and used through a library with no server to run, or for one-off analysis a CSV file loaded into a spreadsheet or pandas. SQLite's own guidance is that it suits data stored on the same device as the application, and it allows only one writer at a time. Move to a client/server database such as PostgreSQL when many programs must write at once, when clients reach the data over a network, or when the data must be replicated to survive the loss of a machine.

Key takeaways

  • A relational database stores each fact once in a table, connects tables through primary and foreign keys, and rejects any row that breaks a declared constraint.
  • An inner join keeps only matching pairs and a left join keeps every left-hand row, while WHERE filters rows before grouping and HAVING filters groups after it.
  • An index replaces a read of the whole table with a walk down a tree, but every index slows writes, so add them for the queries you actually run and confirm the effect with EXPLAIN (ANALYZE, BUFFERS).
  • A transaction makes several statements succeed or fail as one unit, and under PostgreSQL's default Read Committed level each statement sees only the data committed before it began.
  • On a production PostgreSQL, build indexes with CONCURRENTLY, refresh statistics with ANALYZE after bulk changes, and set timeouts so that one statement or idle session cannot hold everything up.
  • A NoSQL store fits when every request goes through one known key at a scale beyond one server and joins and multi-row transactions are not needed; otherwise start with a relational database.

Example 1 of 5

GitLab engineers reading EXPLAIN plans and adding a partial index on the users table

GitLabDocumented in official docs

GitLab publishes its internal database guidelines as part of its developer documentation. The page Understanding EXPLAIN plans walks through real plans for queries on GitLab's users and projects tables, and the page Adding database indexes sets out the rules a new index has to meet. [15][16][6][8]

The problem

A query that counts users with a non-empty Twitter handle read the whole users table. The plan in the guide shows a sequential scan that kept 51,833 rows and removed 2,487,813 with its filter, touching 202,662 buffers in about 1.27 seconds. GitLab's stated target is around 100 milliseconds of SQL time per request, and its guide gives 10 milliseconds as a general guideline for a single query, so a query that takes over a second is worth fixing.

Where this topic fits

This is the index-and-plan loop from this lesson used as a review step. A developer writes or changes a query, produces its plan on production-like data, reads the node types, the filter counts and the buffers, and only then decides whether an index is justified. The index is added in a migration and the plan is checked again afterwards.

How it is applied, step by step

  1. Run the query under EXPLAIN (ANALYZE, BUFFERS) against a database with production-like data. The guide says GitLab team members can use Database Lab Engine, which gives each developer their own clone of the production database.
  2. Read the plan from the innermost node outwards. Here the inner node is a Seq Scan on users whose filter discards about 98% of the rows it reads.
  3. Check how selective the condition is. Few rows match, so an index can help. In the guide's contrasting example on the projects table, about 98% of the table matches, so an index cannot help.
  4. Create an index that contains only the matching rows by adding a WHERE clause to CREATE INDEX (a partial index), and build it with CONCURRENTLY so that writes to the table are not blocked.
  5. Run the same EXPLAIN again. The plan is now an Index Only Scan on the new index and finishes in about 20 milliseconds.
  6. Weigh the index against its cost before keeping it. Every write to the table has to update it, and GitLab caps a table at 15 indexes.

Why this approach fits

A sequential scan is the right plan when most of a table is wanted and the wrong one when a small slice is. The plan output separates the two cases with evidence (rows removed by the filter, buffers read) instead of intuition. A partial index suits this column because most users have no Twitter handle, so an index holding only the rows the query can return stays small.

Limitation or tradeoff

The index is paid for on every write to users, and it serves only queries whose condition implies twitter != ''. The guide is explicit that some queries cannot be fixed this way: when 98% of projects matches the filter, no index beats reading the table, and the query or the feature has to change. Plans measured on a small development database also mislead, which is why the guide insists on production-like data.

What the sources document

  • The guide's example query counts rows in users where twitter is not empty. Its plan shows a Seq Scan returning 51,833 rows with Rows Removed by Filter: 2487813, 202,662 shared buffer hits and an execution time of 1271.180 ms. [15]
  • After a partial index is created with CREATE INDEX CONCURRENTLY on users (twitter) WHERE twitter != '', the plan becomes an Index Only Scan with 44,036 buffer hits and an execution time of 19.848 ms. The guide describes this as about 20 milliseconds and about 344 MB of buffers instead of 1.58 GB. [15]
  • The guide states a target of around 100 milliseconds of SQL time per request and, as a general guideline rather than a hard requirement, says a query should take no more than 10 milliseconds. It describes a projects query that retrieves about 98% of the table as one it can do little to improve other than not running it. [15]
  • GitLab's index guidelines say that all of a table's indexes are updated on every write, that a table with fewer than 1,000 records may not need an index, that GitLab enforces a limit of 15 indexes per table, and that CONCURRENTLY must be used because a normal index build holds a write lock on the table. [16]
  • The PostgreSQL manual states that a standard index build allows reads but blocks inserts, updates and deletes until it finishes, and that a multicolumn B-tree index is most efficient when the query constrains its leading columns. GitLab's guidelines repeat the leading-column rule. [6][8][16]

Example 2 of 5

Wikimedia's Wiki Replicas: public SQL over MediaWiki's page and revision tables

Wikimedia FoundationDocumented in official docs

MediaWiki, the software behind Wikipedia, keeps its data in a relational schema that is documented table by table on mediawiki.org. Wikimedia exposes sanitised copies of the production databases, called Wiki Replicas, which volunteers and researchers query with SQL through tools such as Quarry. Wikitech's help pages describe the service. [17][18][19][20][21]

The problem

Editors, researchers and tool authors want answers that the wiki's web pages do not show, such as how often an article was edited each month. The data is spread over normalised tables: page holds one row per page, revision one row per edit, and separate tables hold the editors and the edit summaries. Answering the question means joining those tables on their keys and aggregating, on tables that for a large wiki are far too big to scan.

Where this topic fits

This is tables, keys, joins and aggregation used for analysis against a live schema. The schema documentation tells the analyst which column is the key on each side of a join and which indexes exist. The replicas are separate servers, so analysis queries do not compete with the site's own traffic.

How it is applied, step by step

  1. Open a SQL session on a replica, for example through the Quarry web interface, and choose the database for the wiki (enwiki_p for English Wikipedia).
  2. Find the page by its unique key. The page table has a unique index on (page_namespace, page_title), so a lookup by namespace and title is an index search that yields the page_id.
  3. Join to revision on rev_page = page_id. The revision table has an index on (rev_page, rev_timestamp), so one page's edits can be read from the index in time order instead of scanning every edit ever made.
  4. Group the joined rows, for example by the month part of rev_timestamp, and count them.
  5. When filtering by editor, query the alternative view revision_userindex instead of revision. The help page explains that the alternative views are redacted in a different way so that the index on the editor column can be used.
  6. Download or share the result. Quarry offers CSV, TSV, JSON and wikitable formats.

Why this approach fits

The question is different every time, so the flexible side of SQL is what is needed. The same normalised tables answer edits per month, edits per editor or pages by size with no redesign. Documented keys make the joins unambiguous, and a composite index that starts with the join column keeps a single-page question cheap even when the revision table is enormous.

Limitation or tradeoff

Replicas lag behind production, and the help page explains how to check the current lag, so results are not exactly current. Queries are time-limited, sensitive data is redacted, and a plain EXPLAIN is not permitted on the replica servers, so plans have to be inspected through a workaround. The SQL dialect is MariaDB's, which differs from PostgreSQL in functions and types.

What the sources document

  • The page table has an entry for each page of the wiki. page_id is its primary key, page_latest is described as a foreign key to rev_id of the current revision, and there is a unique index on (page_namespace, page_title). [17]
  • The revision table holds metadata for every edit. rev_id is its primary key, rev_page equals the page_id of the page the revision belongs to, rev_actor is a foreign key to the actor table, and its indexes include one on (rev_page, rev_timestamp). [18]
  • Wiki Replicas are copies of Wikimedia's production databases with private data removed, reachable through Quarry and Superset on the web, Toolforge, PAWS notebooks and Cloud VPS. Database names add _p to the project name, as in enwiki_p. Quarry is described as a public querying interface for the replicas whose results can be downloaded as CSV, TSV, JSON or wikitable. [19][21]
  • The analytics service name lets queries run for longer than the web service name. When the page was read it gave 3 hours instead of 5 minutes. [19]
  • The queries help page recommends alternative views such as revision_userindex when filtering on columns such as rev_actor, because the data there is redacted in a different way so that the corresponding indexes can be used. It also notes that a simple EXPLAIN does not work on the replica servers. [20]

Example 3 of 5

Solid Queue at 37signals: a job queue built on transactions and FOR UPDATE SKIP LOCKED

37signalsDocumented in an open-source project

Solid Queue is the database-backed job queue that 37signals wrote for Ruby on Rails and runs in HEY, one of its products. Its README on GitHub and the announcement on the 37signals developer blog explain how workers take jobs from a table without blocking each other, and the PostgreSQL manual documents the locking clause it depends on. [22][23][5]

The problem

Background jobs (send this email, resize that image) are rows waiting in a table, and many worker processes poll that table at once. Each job must be run by exactly one worker. With ordinary row locks the workers would queue up behind each other on the same first rows. 37signals had been running jobs on Resque with Redis, reported challenges operating it at scale, and wanted jobs to run from a database so that a Rails app needs no separate queue system to get background processing.

Where this topic fits

This is the transactions part of the lesson applied to concurrency. Claiming a job is a small transaction: select candidate rows with a row lock, record that this worker owns them, commit. FOR UPDATE SKIP LOCKED is the piece that lets many such transactions run side by side.

How it is applied, step by step

  1. Enqueueing a job inserts rows. Jobs that are ready to run are kept in their own table, solid_queue_ready_executions, which the workers poll.
  2. A worker selects a batch of ready rows with FOR UPDATE SKIP LOCKED. The clause locks the rows it returns and passes over rows that another transaction has already locked.
  3. A second worker running the same statement at the same moment therefore receives different rows instead of waiting for the first worker's locks.
  4. In the same transaction a typical implementation records which worker claimed the jobs, removes them from the ready table and commits. If the worker dies before the commit, the transaction rolls back and the rows are available again.
  5. The worker runs the jobs. Jobs scheduled for later sit in a separate table, and a dispatcher moves them into the ready table when they fall due.
  6. Polling stays cheap because the ready table holds only runnable jobs and the polling queries are written so that an index can answer them.

Why this approach fits

The database already provides what a queue needs: durable storage, atomic changes of state and row locks. Keeping jobs beside the application's data means a job can be enqueued in the same transaction as the change that needs it, so neither exists without the other. SKIP LOCKED removes the one obstacle, workers waiting on each other's locks, without adding a separate queueing system to operate.

Limitation or tradeoff

The README warns that relying on that shared transaction is a sharp tool: move the queue to another database or another backend and the guarantee silently disappears, which is why Solid Queue is configured in a separate database by default. The PostgreSQL manual notes that SKIP LOCKED gives an inconsistent view of the data and is meant for queue-like tables, not for general queries. On databases without the clause, the README says several workers on one queue may run into lock waits. A typical implementation also spends several database writes on every job, so the queue adds load to the database it shares.

What the sources document

  • The README describes Solid Queue as a queuing backend for Active Job that keeps its jobs in a SQL database (MySQL, PostgreSQL or SQLite), and says it uses the FOR UPDATE SKIP LOCKED clause where the database has it so that workers polling for jobs do not wait on each other's locks. [22]
  • According to the README, workers pick jobs from the solid_queue_ready_executions table, dispatchers move due jobs into it from solid_queue_scheduled_executions, and the design gives the highest throughput on MySQL 8+, MariaDB 10.6+ or PostgreSQL 9.5+ because those versions support FOR UPDATE SKIP LOCKED. [22]
  • The README's section on transactional integrity says that keeping jobs in the same ACID-compliant database as application data lets an action and its job commit together, warns that this can backfire if the queue is later moved, and states that Solid Queue is therefore configured in a different database from the main app by default. [22]
  • 37signals wrote in December 2023 that it used Solid Queue in HEY to run about a third of its roughly 18 million jobs per day, with around 1,300 polling queries per second averaging 110 microseconds and examining 0.02 rows per query. The same post says the company does not use PostgreSQL and that the queue had to support MySQL, PostgreSQL and SQLite at a minimum. [23]
  • The PostgreSQL manual says SKIP LOCKED makes a query pass over rows it cannot lock at once instead of waiting for them, warns that the result is an inconsistent view of the table and so unsuitable for general queries, and names queue-like tables read by several consumers as the intended use. [5]

Example 4 of 5

OpenAI running ChatGPT on one PostgreSQL primary with nearly 50 read replicas

OpenAIDocumented in an engineering article

OpenAI's engineering article Scaling PostgreSQL to power 800 million ChatGPT users (January 2026) describes the PostgreSQL deployment behind ChatGPT and the API. A second article from September 2026, about its Habitat storage platform, explains where newer workloads went. [24][25][13]

The problem

The article reports PostgreSQL load growing more than tenfold in a year, with every write going to a single primary instance. Its incidents followed one pattern: an upstream event such as a cache failure, a burst of expensive multi-table joins or a write storm from a launch raised database load, queries slowed and timed out, and client retries amplified the load further. The team needed to keep one unsharded PostgreSQL serving millions of queries per second without those spirals.

Where this topic fits

This is the PostgreSQL in practice part of the lesson at an extreme scale. The relational model is unchanged. What the article adds is the operating discipline around it: where reads and writes go, how connections are shared, which queries and schema changes are allowed, and which workloads are moved out of PostgreSQL altogether.

How it is applied, step by step

  1. Send reads to replicas wherever possible, and keep the primary for writes and for reads that are part of a write transaction, so that the single writer has spare capacity for spikes.
  2. Find and fix expensive queries. The article's example is a query joining 12 tables whose spikes caused high-severity incidents. The team avoids complex multi-table joins and reviews the SQL its ORM generates.
  3. Put PgBouncer in front of the database in statement or transaction pooling mode, so that many clients share few server connections and stay under the 5,000-connection limit of an instance.
  4. Set timeouts such as idle_in_transaction_session_timeout so that sessions left idle inside a transaction cannot block autovacuum.
  5. Restrict schema changes to lightweight operations with a 5-second timeout, create and drop indexes concurrently, and rate-limit backfills.
  6. Isolate workloads on separate instances by priority, rate-limit at several layers and guard against cache-miss storms, so that one feature cannot starve the rest.
  7. Move write-heavy workloads that can be partitioned by key to a sharded system, Azure Cosmos DB, and stop adding new tables to this PostgreSQL deployment.

Why this approach fits

The workload is read-heavy. Reads scale out across replicas, while a single primary keeps writes simple and transactional. The article argues that sharding the existing application would mean changing hundreds of endpoints, so tuning one primary bought more than re-architecting. Most of the measures are rules from this lesson enforced at scale: check query plans, keep expensive joins off hot paths, build indexes concurrently and keep transactions short.

Limitation or tradeoff

One primary is a ceiling on writes and a single point of failure. The article says writes would fail if it went down, and that a hot standby reduces the downtime. It attributes PostgreSQL's weakness under heavy writes to its multiversion concurrency control: an update copies the whole row, and the dead versions cause bloat and need autovacuum. OpenAI's later Habitat article says a single expensive new SQL query on a hot path was a frequent cause of outages, and that its storage platform now offers a deliberately limited NoSQL interface on Azure Cosmos DB instead of arbitrary SQL.

What the sources document

  • OpenAI reports supporting ChatGPT and its API with a single primary Azure PostgreSQL flexible server instance and nearly 50 read replicas across regions, handling millions of queries per second, after its PostgreSQL load grew by more than 10x in a year. [24]
  • The article says PostgreSQL remains unsharded with one primary serving all writes, that shardable write-heavy workloads have been and are being migrated to sharded systems such as Azure Cosmos DB, and that adding new tables to the current PostgreSQL deployment is no longer allowed. [24]
  • It describes an extremely costly query that joined 12 tables and was responsible for past high-severity incidents, advises avoiding complex multi-table joins, and notes that many problematic queries are generated by ORMs. It recommends timeouts such as idle_in_transaction_session_timeout, which the PostgreSQL manual defines as terminating a session that stays idle in an open transaction for longer than the set time. [24][13]
  • It reports deploying PgBouncer in statement or transaction pooling mode against a limit of 5,000 connections per instance, with average connection time in its benchmarks falling from 50 ms to 5 ms, and permitting only lightweight schema changes under a strict 5-second timeout, with indexes created and dropped concurrently. [24]
  • OpenAI's September 2026 article on its Habitat storage platform states that most of its online data used to be stored on Postgres, that a single expensive new query on a hot path was a frequent cause of outages, and that Habitat exposes a simple NoSQL API instead of letting clients construct arbitrary SQL. [25]

Example 5 of 5

Discord storing chat messages in Cassandra and ScyllaDB, partitioned by channel

DiscordDocumented in an engineering article

Two Discord engineering articles, How Discord Stores Billions of Messages (2017) and How Discord Stores Trillions of Messages (2023), describe the store behind chat history: first MongoDB, then Cassandra, then ScyllaDB. [26][27]

The problem

Messages are written constantly and read back a channel at a time, newest first. The 2017 article says the original MongoDB replica set held up until about 100 million messages, when the data set and its index had outgrown memory and response times could no longer be predicted. Discord wanted a store that scaled by adding nodes with no manual re-sharding, failed over automatically and kept response times predictable.

Where this topic fits

This is the last section of the lesson in practice: a workload where a non-relational store fits better. The access pattern is fixed and narrow (the messages of one channel, in time order), needs no joins, and is far larger than one server. So the schema is designed around that one query, and the data is partitioned by key across many nodes.

How it is applied, step by step

  1. Write down the access pattern first: fetch a page of one channel's messages in time order, and insert new messages.
  2. Choose a partition key that puts the rows read together on the same nodes. Discord partitions by channel id, so one channel's messages are stored together.
  3. Choose a clustering key that sorts the rows inside a partition. Discord uses the message id, a Snowflake id that sorts chronologically.
  4. Bound the size of a partition. Partitions over 100 MB were found, and the 2017 article says large partitions put garbage-collection pressure on Cassandra during compaction and cluster expansion, so a time bucket of about 10 days was added to the partition key.
  5. Read by key. A query names a channel and a bucket and reads a range of message ids, and an active channel usually finds enough messages in its newest bucket.
  6. Accept what the store does not do. There are no joins and no general multi-row transactions, and writes are eventually consistent, which the application has to handle.

Why this approach fits

Every read and write carries the channel id, so the data splits cleanly by that key and each request touches one small, contiguous slice. Nothing in the workload asks a question across channels, so the joins and ad hoc queries of a relational database would go unused while its single writer would be the bottleneck. Adding nodes adds capacity without reorganising the application.

Limitation or tradeoff

The model is rigid: a question the key does not serve, such as all messages by one author, needs another table or another system. Popular channels create hot partitions, and the 2023 article describes unpredictable latency and heavy on-call work from them, from compactions and from garbage-collection pauses before the move to ScyllaDB. Eventual consistency also reached the application: an edit racing a delete left a partial row, and the markers left by deleted messages once made a nearly empty channel very slow to load.

What the sources document

  • Discord first stored messages in a single MongoDB replica set. Around November 2015, at about 100 million stored messages, the data set and its index had outgrown RAM and response times were no longer predictable. [26]
  • The 2017 article reports reads scattered randomly across the data with roughly as many reads as writes, and lists requirements for the replacement that include linear scalability with no manual re-sharding, automatic failover and predictable performance. [26]
  • The messages table uses PRIMARY KEY ((channel_id, bucket), message_id). Partitions over 100 MB were found, so a bucket of about 10 days of messages was added to the partition key, and message ids are Snowflakes, which sort chronologically. [26][27]
  • The 2017 article describes Cassandra as a database that favours availability over strong consistency, and reports that a concurrent edit and delete could leave a row holding only its key and text, and that tombstones from mass deletions caused long garbage-collection pauses when one channel was loaded. [26]
  • The 2023 article reports growth from 12 Cassandra nodes storing billions of messages in 2017 to 177 nodes with trillions in early 2022, problems with hot partitions, compaction and garbage collection, and a migration to 72 ScyllaDB nodes after which p99 latency for fetching historical messages fell from 40-125 ms to 15 ms. [27]

4Common mistakes

  1. Building a SQL statement by gluing user input into the query string.

    Why it causes problems
    Input that contains a quote changes the meaning of the statement. An attacker can read other customers' rows or remove a table, and an honest user called O'Brien simply gets an error. This is SQL injection, one of the oldest and most exploited kinds of security bug.
    How to recognise it
    String concatenation or formatting next to SELECT, INSERT, UPDATE or DELETE in application code, and failures whenever a value contains an apostrophe.
    How to fix it
    Pass values as parameters, using the placeholders your database driver provides, so that they can never be parsed as SQL. Give the application's database role only the privileges it needs.

  2. Shipping a query without ever looking at its plan on realistic data.

    Why it causes problems
    A filter or join on an unindexed column reads the whole table. On a development database with a few hundred rows it returns instantly. In production it takes seconds, holds a connection and, repeated across requests, can use up the database's CPU.
    How to recognise it
    EXPLAIN (ANALYZE, BUFFERS) shows a Seq Scan on a large table whose Rows Removed by Filter is far greater than the rows returned, as in the worked example (99,906 removed to return 100). Foreign-key columns are a common culprit because PostgreSQL does not index them automatically.
    How to fix it
    Check the plan of every new query against production-sized data, index the columns you filter and join on when the condition is selective, and run the plan again to confirm the index is used.

  3. Adding an index for every column and never removing any.

    Why it causes problems
    Each index has to be updated on every insert and on many updates, takes disk space and memory, and slows bulk loads. In the second exercise the three indexes left on the orders table occupy more pages (758) than the table itself (637).
    How to recognise it
    Tables with overlapping indexes, such as one on customer_id and another that starts with customer_id, and indexes whose idx_scan counter in pg_stat_user_indexes stays at zero.
    How to fix it
    Create indexes for specific queries, prefer one multicolumn index that serves several queries to many single-column ones, and drop indexes that are redundant or unused.

  4. Making related changes in separate statements with no transaction, or leaving a transaction open.

    Why it causes problems
    Without a transaction, a failure between two statements leaves half of the change applied, such as credit removed from one account and never added to the other. The opposite error, a transaction left open while the application waits for a user or an API call, holds locks and, as OpenAI's article notes, can block autovacuum.
    How to recognise it
    Data that breaks a rule you expected to hold (totals that do not add up, orders with no items), and sessions listed with the state idle in transaction in pg_stat_activity.
    How to fix it
    Wrap each logical change in BEGIN and COMMIT, keep transactions short with no network calls inside them, and set idle_in_transaction_session_timeout as a backstop.

  5. Running a plain CREATE INDEX or a table-rewriting ALTER TABLE on a busy production table.

    Why it causes problems
    A standard index build blocks inserts, updates and deletes on the table until it finishes, which on a large table can take minutes. Some schema changes rewrite the whole table. Requests pile up behind the lock and the application appears to be down.
    How to recognise it
    A deployment or migration that coincides with a spike of waiting queries and timeouts on one table.
    How to fix it
    Use CREATE INDEX CONCURRENTLY, keep to schema changes that do not rewrite the table, set a lock timeout so that a blocked change gives up quickly, and backfill data in small rate-limited batches.

  6. Choosing a NoSQL store for scale before the access patterns are known.

    Why it causes problems
    A key-value or wide-column schema is built around specific queries. When requirements change, a question the keys do not serve needs a new table, a data migration or a second system, and guarantees such as foreign keys and multi-row transactions have to be rebuilt in application code.
    How to recognise it
    Application code that joins data by hand across several lookups, scans whole tables to produce a report, or repairs inconsistent records in a background job.
    How to fix it
    List the queries first. If they are varied or still changing, start with a relational database, and move a workload to a NoSQL store when it has one clear key and a measured scaling problem, as OpenAI and Discord did.

Exercise 1

Report on a support desk with joins, aggregates and one transaction

CodingBeginnerAbout 40 min (estimate)Hypothetical scenario

A small support team tracks its tickets in two tables. Create them in PostgreSQL (the PGlite REPL (opens in a new tab) in a browser is enough), entering one statement at a time.

sql
CREATE TABLE agents (
  id   integer PRIMARY KEY,
  name text NOT NULL,
  team text NOT NULL
);
CREATE TABLE tickets (
  id                 integer PRIMARY KEY,
  agent_id           integer REFERENCES agents (id),   -- null = not assigned yet
  opened_on          date NOT NULL,
  priority           text NOT NULL CHECK (priority IN ('low', 'high')),
  minutes_to_resolve integer                           -- null = still open
);
INSERT INTO agents VALUES
  (1, 'Mira', 'billing'), (2, 'Omar', 'billing'),
  (3, 'Lena', 'technical'), (4, 'Raj', 'technical');
INSERT INTO tickets VALUES
  (1, 1, '2026-10-01', 'high', 30),     (2, 1, '2026-10-01', 'low', 90),
  (3, 2, '2026-10-02', 'high', NULL),   (4, 3, '2026-10-02', 'high', 45),
  (5, 3, '2026-10-03', 'low', 15),      (6, 3, '2026-10-03', 'high', 60),
  (7, NULL, '2026-10-04', 'low', NULL), (8, 1, '2026-10-04', 'high', 60);

Write SQL for each task:

  1. For every agent, including agents with no tickets, show the name, the number of tickets assigned, the number resolved, and the average minutes to resolve.
  2. Show each team whose resolved high-priority tickets took more than 50 minutes on average, with the number of such tickets and the average.
  3. Count the tickets that have no agent.
  4. Omar is leaving. Hand all of his tickets to Lena and delete his row, so that either both changes happen or neither does.

Requirements

  • Task 1 returns exactly four rows, one per agent, ordered by agent id.
  • Task 2 uses WHERE for the conditions on rows and HAVING for the condition on the average.
  • Task 3 returns 1, not 0.
  • Task 4 runs as a single transaction, and afterwards no ticket refers to an agent who does not exist.
  • No query uses SELECT *, and every column in a query that joins is qualified with its table alias.

Expected behaviour

Task 1:

nameticketsresolvedavg_minutes
Mira3360.0
Omar10null
Lena3340.0
Raj00null

A null average is shown as an empty cell in psql. Task 2 returns one row: technical, 2 tickets, average 52.5. Task 3 returns 1. After task 4 the agents are Mira, Lena and Raj, with 3, 4 and 0 tickets.

Hint 1

Start task 1 from agents and LEFT JOIN tickets, so that an agent with no tickets still produces a row.

Hint 2

count(*) counts rows, including the null-padded row that a LEFT JOIN creates. count(t.id) and count(t.minutes_to_resolve) count only values that are not null.

Hint 3

A comparison with null is never true. Use IS NULL.

Hint 4

Try deleting Omar first and read the error. It tells you which statement has to come first.

Show solution

Task 1. Start from agents so that nobody is lost, and count columns of tickets instead of rows:

sql
SELECT a.name,
       count(t.id)                         AS tickets,
       count(t.minutes_to_resolve)         AS resolved,
       round(avg(t.minutes_to_resolve), 1) AS avg_minutes
FROM agents a
LEFT JOIN tickets t ON t.agent_id = a.id
GROUP BY a.id, a.name
ORDER BY a.id;

Mira's average is (30 + 90 + 60) / 3 = 60.0 and Lena's is (45 + 15 + 60) / 3 = 40.0. Omar has one ticket, still open, so resolved is 0 and the average of no values is null. Raj's row exists only because of the LEFT JOIN, and count(*) would have reported 1 ticket for him.

Task 2. Conditions on rows go in WHERE, the condition on the aggregate in HAVING:

sql
SELECT a.team,
       count(*)                            AS resolved_high,
       round(avg(t.minutes_to_resolve), 1) AS avg_minutes
FROM tickets t
JOIN agents a ON a.id = t.agent_id
WHERE t.priority = 'high'
  AND t.minutes_to_resolve IS NOT NULL
GROUP BY a.team
HAVING avg(t.minutes_to_resolve) > 50
ORDER BY a.team;

Billing has resolved high-priority tickets of 30 and 60 minutes (average 45.0). Technical has 45 and 60 (average 52.5), so only the technical row passes. An inner join is right here, because an unassigned ticket has no team.

Task 3.

sql
SELECT count(*) FROM tickets WHERE agent_id IS NULL;

The answer is 1 (ticket 7). WHERE agent_id = NULL returns 0, because that comparison is never true.

Task 4. Deleting first fails, which is the foreign key doing its job. DELETE FROM agents WHERE id = 2; gives:

text
ERROR:  update or delete on table "agents" violates foreign key constraint "tickets_agent_id_fkey" on table "tickets"

Reassign, then delete, inside one transaction:

sql
BEGIN;
UPDATE tickets SET agent_id = 3 WHERE agent_id = 2;
DELETE FROM agents WHERE id = 2;
COMMIT;

Had the DELETE failed for any reason, you would issue ROLLBACK and the tickets would still belong to Omar. Counting tickets per agent again now gives Mira 3, Lena 4 and Raj 0.

Check your answer

  • Does your task 1 result have a row for Raj with 0 tickets, and a null average (not 0) for Omar?
  • Is your task 2 result the single row technical, 2, 52.5?
  • Does task 3 return 1, and can you explain why the version written with = NULL returns 0?
  • After task 4, does counting tickets where agent_id = 2 return 0, and does Lena have 4 tickets?

Exercise 2

Make two slow queries fast and prove it with EXPLAIN

Hands-onIntermediateAbout 45 min (estimate)Hypothetical scenario

Use the customers and orders tables from the worked example, including the bulk load in step 3 and the index orders_customer_id_idx from step 4. If you dropped them, run steps 1, 3 and 4 again.

Two queries from a customer portal need to be fast:

sql
-- Q1: the five most recent orders of one customer
SELECT id, placed_on, amount
FROM orders
WHERE customer_id = 42
ORDER BY placed_on DESC, id DESC
LIMIT 5;

-- Q2: a daily total
SELECT count(*), sum(amount)
FROM orders
WHERE placed_on = DATE '2026-03-15';
  1. Run each under EXPLAIN (ANALYZE, BUFFERS). For each one, note the scan node, whether there is a Sort node, any Rows Removed by Filter, and the top-level Buffers total.
  2. Create one index that lets PostgreSQL answer Q1 without sorting. Confirm it with EXPLAIN.
  3. Predict whether that index helps Q2, then check.
  4. Create an index for Q2 and confirm it.
  5. One index on the table is now redundant. Say which one and why, drop it, and show that the worked example's query (SELECT count(*), sum(amount) FROM orders WHERE customer_id = 42) still avoids a sequential scan.

Requirements

  • Q1's final plan has no Sort node and reads fewer than 20 buffers.
  • Q2's final plan has no Seq Scan.
  • You create exactly two new indexes and drop one existing index.
  • Both queries return the same rows before and after your changes.

Expected behaviour

Q1 returns orders 86041 and 13041 (both placed on 2026-12-28), then 63041, 40041 and 90041. Q2 returns a count of 274 and a sum of 15347.00.

On PostgreSQL 18.3 the buffer totals were 102 before and 8 after for Q1, and 637 before and 276 after for Q2. Your node types should match. Exact buffer counts and all timings may differ a little.

Hint 1

An index stores its entries sorted. If that order matches the ORDER BY for the rows that pass the WHERE clause, the rows can be read off the index already in order.

Hint 2

Put the column tested with = first in the index, then the ORDER BY columns with the same directions.

Hint 3

For step 3, ask which column leads your new index and whether Q2 puts any condition on it.

Hint 4

Two indexes overlap when the columns of one are the leading columns of the other.

Show solution

Step 1. With only the worked example's index, Q1 uses that index to find the customer's 100 rows and then sorts them to pick five (cost and timing figures trimmed):

text

  Buffers: shared hit=102
  ->  Sort  (actual rows=5.00 loops=1)
        Sort Key: placed_on DESC, id DESC
        Sort Method: top-N heapsort  Memory: 17kB
        ->  Bitmap Heap Scan on orders  (actual rows=100.00 loops=1)
              Recheck Cond: (customer_id = 42)
              ->  Bitmap Index Scan on orders_customer_id_idx  (actual rows=100.00 loops=1)
                    Index Cond: (customer_id = 42)

Q2 has no usable index: a Seq Scan on orders with Rows Removed by Filter: 99732 and Buffers: shared hit=637.

Step 2. Equality column first, then the sort columns in the query's directions:

sql
CREATE INDEX orders_customer_recent_idx
  ON orders (customer_id, placed_on DESC, id DESC);
text
Limit  (cost=0.42..19.30 rows=5 width=13) (actual time=0.100..0.100 rows=5.00 loops=1)
  Buffers: shared hit=5 read=3
  ->  Index Scan using orders_customer_recent_idx on orders  (cost=0.42..378.15 rows=100 width=13) (actual time=0.100..0.100 rows=5.00 loops=1)
        Index Cond: (customer_id = 42)

Inside the index, customer 42's entries are already in the order the query asks for, so PostgreSQL reads the first five and stops: 8 buffers instead of 102, and the Sort node is gone.

Step 3. It does not help. Q2 puts no condition on customer_id, the leading column, so the entries it needs are scattered through the whole index. The plan is still a Seq Scan that removes 99,732 rows.

Step 4.

sql
CREATE INDEX orders_placed_on_idx ON orders (placed_on);

Q2 becomes a Bitmap Index Scan on orders_placed_on_idx under a Bitmap Heap Scan, with Buffers: shared hit=274 read=2. The 274 matching orders sit on 274 different pages, so this is 276 pages instead of 637. The gain is smaller than Q1's because every matching row costs a page read.

Step 5. orders_customer_id_idx is redundant. customer_id is the leading column of orders_customer_recent_idx, which can serve every query the single-column index served.

sql
DROP INDEX orders_customer_id_idx;
EXPLAIN SELECT count(*), sum(amount) FROM orders WHERE customer_id = 42;
text
Aggregate  (cost=272.34..272.35 rows=1 width=40)
  ->  Bitmap Heap Scan on orders  (cost=5.19..271.84 rows=100 width=5)
        Recheck Cond: (customer_id = 42)
        ->  Bitmap Index Scan on orders_customer_recent_idx  (cost=0.00..5.17 rows=100 width=0)
              Index Cond: (customer_id = 42)

The estimated cost barely moved (272.34, against 272.22 with the dedicated index), and every write to orders now maintains one index fewer. List what is left with SELECT indexname, indexdef FROM pg_indexes WHERE tablename = 'orders';. You should see orders_pkey, orders_customer_recent_idx and orders_placed_on_idx. On our run they occupied 276, 388 and 94 pages, 758 in total against 637 for the table itself. That is the price of the fast reads.

Check your answer

  • Does Q1's final plan show an Index Scan on your new index directly under Limit, with no Sort node?
  • Did Q2 remain a Seq Scan after step 2, and can you name the column that made the new index useless for it?
  • Does Q2 return 274 and 15347.00 both before and after you add its index?
  • After step 5, does pg_indexes list exactly three indexes on orders, including the primary key's?

    How to read every part of a plan: the cost numbers and how they are computed, the scan and join node types, what EXPLAIN ANALYZE adds, and the caveats that make plans from small test tables misleading.

    The first time a real query is slow, and again whenever a plan contains a node you do not recognise.

    When to use it
    Before you have a PostgreSQL server to hand, or for a quick experiment. It gives you one session, so you cannot watch two transactions interleave.
