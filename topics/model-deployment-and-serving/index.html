Model Deployment and Serving

Model deployment is the work of moving a trained model out of the training environment and into a system that other software can use. Serving is the running part of that system: it loads the model, accepts inputs and returns predictions, either on a schedule (batch) or on request (online).

1Overview

Why it matters

A model that only runs in a notebook changes nothing. What makes it useful is a set of engineering decisions: whether predictions are computed overnight or at the moment a user clicks, how the model and its exact library versions get onto a server, how fast an answer must come back, and how a new version replaces the old one without hurting the people who depend on it.

Each decision has a typical failure. Precomputed scores go stale, or do not exist for a customer who signed up this morning. A service that reloads the model on every request, or that reports only its average latency, looks fine in a demo and times out under real traffic. A new model that scored better offline is switched on for everyone at once, and the first sign of a broken feature pipeline is a drop in revenue. Data scientists, ML engineers and the backend engineers who call the model need a shared vocabulary for these choices, and a few numbers they can compute before anything is built.

Key terms

Inference
Running a trained model on new input to get a prediction. Training changes the model; inference only uses it.
Batch inference
Scoring many records in a scheduled job and storing the results so that applications can read them later.
Online inference
Computing a prediction when a request arrives and returning it in the response, usually within milliseconds. Also called real-time inference.
Model artifact
The versioned file or folder that training produces. It holds the learned weights and whatever else is needed to run them.
Model server
A ready-made program that loads artifacts in a known format and exposes them over HTTP or gRPC with standard endpoints, batching and metrics.
Replica
One running copy of the serving container. A load balancer spreads requests across the replicas.
Latency percentile
The latency that a given share of requests stay under. A p95 of 80 ms means 95 percent of requests finished within 80 ms.
Throughput
The number of requests a service completes per second.
Shadow deployment
Running a new model on a copy of live requests while its outputs are logged and never returned to users.
Canary rollout
Sending a small share of real traffic to a new version and watching it for a set time before shifting the rest.

2Explanation

Introduction

You have trained a model, and in the notebook one line produces predictions: model.predict(X). Deployment starts with four questions the notebook never asked. Who calls predict? When? How quickly do they need the answer? And what happens on the day you want to replace the model with a better one?

A bakery makes the first two questions concrete. Bread is baked overnight for the shelf, because the baker knows roughly what will sell and a customer accepts a loaf that is a few hours old. A sandwich is made to order, because nobody can prepare every combination in advance. The first is batch inference: a scheduled job scores every record it knows about and writes the results to a table, and applications later read a stored score. The second is online inference: a service keeps the model loaded in memory, receives a request with the inputs, and returns the prediction in the response.

Both paths start from the same model artifact, the versioned file that training produced (see experiment tracking and model registries). They differ in when the model runs and in what can go wrong. A batch job can take an hour and nobody notices, but its scores are as old as the last run and exist only for the records the job saw. An online service answers for any input, using data that is seconds old, but it now sits in the request path: if it is slow or down, so is the product feature that calls it.

The rest of this lesson spends most of its time on the online path, because that is where most of the engineering is. It covers how to wrap a model in an HTTP API (building on REST APIs), why the service ships as a container image (building on Docker and containers), when a dedicated model server replaces hand-written API code, how to state speed requirements as latency and throughput budgets, and how shadow and canary rollouts let a new version prove itself before it serves everyone.

How it works

Batch or online: when is the prediction computed?

The first decision is timing. It follows from two facts about the use case: whether the inputs are known in advance, and how old a prediction is allowed to be.

Batch inferenceOnline inference
Model runsOn a schedule, over many recordsPer request
InputsMust exist before the job startsCan include the last few seconds
Result reaches the appRead from a table or fileReturned in the response
Speed requirementThe job meets its deadlineEach request meets a latency limit
Typical failureStale or missing scoresTimeouts in the request path

Cloud platforms offer both. In Amazon SageMaker, batch transform (opens in a new tab) gets inferences from large datasets without a persistent endpoint, while the endpoint options (opens in a new tab) include real-time inference for interactive, low-latency workloads and asynchronous inference, which queues requests with large payloads or long processing times. One model can take both paths: Uber's Michelangelo (opens in a new tab) deploys a model either to a Spark job that writes batch predictions on a schedule or to an online prediction cluster behind a load balancer.

Packaging: a model behind an API

An online model is an ordinary web service with one unusual dependency: a large file that must be in memory before the first request. The serving process has four jobs.

  1. Load the artifact once, at startup. FastAPI's documented pattern is a lifespan function (opens in a new tab). Code before yield runs once, before the application starts receiving requests. The documentation's own example is an ML model that is slow to load from disk.
  2. Validate the input. A request with a missing field or a negative age is rejected with a 4xx status, not scored.
  3. Apply the same preprocessing as training, ideally shipped inside the artifact (for example a scikit-learn Pipeline), so that the service cannot drift from the training code.
  4. Return the model version with the prediction, so that every logged prediction can be traced to the artifact that produced it.
python
from contextlib import asynccontextmanager
from fastapi import FastAPI

models = {}

@asynccontextmanager
async def lifespan(app: FastAPI):
    models["churn"] = load_artifact("model.json")  # your loader; runs once
    yield
    models.clear()

app = FastAPI(lifespan=lifespan)

The worked example has the complete file. The artifact format matters as much as the code. scikit-learn's guide to model persistence (opens in a new tab) warns that pickle-based files, including joblib files, can execute arbitrary code when loaded and must come only from a trusted source, and that loading a model with a different scikit-learn version from the one that trained it is unsupported. It lists ONNX as the option for serving without the original Python environment. In practice: pin exact library versions, record them next to the artifact, and treat a model file as code.

Containers: the environment travels with the model

Predictions depend on exact versions of numerical libraries, so "it works on my machine" is a real risk. A container image freezes the interpreter, the libraries, the serving code and often the artifact into one versioned unit. The FastAPI container guide (opens in a new tab) shows the standard shape: copy the requirements file and install dependencies first so that Docker reuses that layer on later builds, copy the code last, and run a single server process per container. You scale by running more identical containers (replicas) behind a load balancer. The guide adds that memory-heavy applications such as ML models need their memory use checked when deciding how many containers fit on a machine.

The artifact can be baked into the image (one unit to roll back) or downloaded from object storage when the container starts (smaller images, and a new model needs no rebuild). Either way, loading can take seconds to minutes, so the container must signal when it is ready. In Kubernetes, a failing readiness probe (opens in a new tab) removes the pod from its Service's endpoints so that it receives no traffic, and a startup probe gives a slow-starting container time before the other probes begin.

Model servers: when the API layer is generic

If every model gets its own hand-written service, the same code is written repeatedly: request parsing, batching, metrics, health checks, version switching. A model server is that code written once: you put an artifact in a supported format into a directory or bucket and the server exposes it. TensorFlow Serving, NVIDIA Triton Inference Server and the runtimes behind KServe work this way.

KServe documents a wire format meant to be the same across inference servers, the Open Inference Protocol (opens in a new tab) (also called the KServe V2 protocol). It defines health endpoints, model metadata and an inference call:

text
POST /v2/models/churn/infer

{"inputs": [{"name": "features", "shape": [1, 3], "datatype": "FP32", "data": [5.0, 80.0, 3.0]}]}

The response carries model_name, an optional model_version and an outputs list in the same tensor format. Hand-written API code suits a team with one or two models, or a model wrapped in business logic. A model server pays off when many models share one operational pattern or need features such as request batching on GPUs.

Latency and throughput budgets

Latency is the time one request takes. Throughput is how many requests complete per second.

Latency is stated in percentiles, not averages. Google's SRE book explains why in its chapter on service level objectives (opens in a new tab): a simple average can obscure the slow tail, and in its example a typical request takes about 50 ms while 5 percent of requests are 20 times slower. A latency budget names a percentile and a limit, such as "p95 under 150 ms", and is then divided among the stages of a request: network, feature lookup, model computation and post-processing. Measure each stage, because the model is often not the slowest one.

Throughput decides the replica count. Load-test one replica to find the request rate it sustains while still meeting its latency budget, then compute

replicas=⌈peak requests per secondcapacity per replica×target utilisation⌉\text{replicas} = \left\lceil \frac{\text{peak requests per second}}{\text{capacity per replica} \times \text{target utilisation}} \right\rceilreplicas=⌈capacity per replica×target utilisationpeak requests per second​⌉

Target utilisation is set well below 1 (this lesson uses 0.6), because queues grow sharply as a server approaches full load. In the simplest queueing model, one server with random arrivals, the mean response time is S/(1−ρ)S / (1 - \rho)S/(1−ρ) for service time SSS and utilisation ρ\rhoρ: a 20 ms model answers in 40 ms on average at 50 percent load and in 200 ms at 90 percent.

Batching trades latency for throughput. Scoring 16 inputs in one call costs far less than 16 separate calls, especially on a GPU, so model servers can hold requests briefly and group them. Triton's dynamic batcher (opens in a new tab) is switched on per model:

protobuf
dynamic_batching {
  max_queue_delay_microseconds: 5000
}

Triton's documentation recommends measuring with its Performance Analyzer and raising the batch size or the delay only while latency stays within the budget. The plot shows the trade with a simple cost model: one batch of bbb inputs takes 8+2b8 + 2b8+2b ms, so a model instance that is always busy completes 1000b/(8+2b)1000b / (8 + 2b)1000b/(8+2b) requests per second.

Rolling out a new version: shadow first, then canary

Offline metrics cannot show how a model behaves on live inputs, under production load, with the real feature pipeline. Two techniques expose a new version to production gradually.

In a shadow deployment the router sends each request to the current model as usual and a copy to the new one. Amazon SageMaker's shadow tests (opens in a new tab) work this way: only the production variant's responses are returned to the caller, and the shadow variant's responses are discarded or logged for comparison.

Shadowing shows, at no risk to users, whether the new version stays up, how fast it is and how its predictions differ. It cannot show how users react, because no user sees its output.

In a canary rollout a small share of real requests, for example 5 percent, is answered by the new version. Its error rate, latency and prediction statistics are compared with the old version during a fixed observation window, often called a baking period. The share is then raised in steps or returned to zero. The rollback condition is fixed before the rollout starts and is best enforced automatically. In KServe the mechanism is one field: setting canaryTrafficPercent: 10 (opens in a new tab) routes 10 percent of traffic to the newest revision, removing the field promotes it, and setting it to 0 rolls back.

A canary protects against operational regressions. Whether the new model improves a business metric is a separate question, answered by a controlled experiment (see A/B testing and online experiments).

Worked example: Serving a churn score: one artifact, one container, one sizing calculation

A subscription company wants a churn score on the support agent's screen while a customer's page loads. The scenario and its traffic numbers are invented for teaching; the code, commands and arithmetic are real and can be reproduced. The page allows the score 150 ms at p95, and peak load is 400 page loads per second.

2. The service

app/main.py (next to an empty app/__init__.py):

python
import json
import math
from contextlib import asynccontextmanager

from fastapi import FastAPI
from pydantic import BaseModel, Field

MODEL = {}


@asynccontextmanager
async def lifespan(app: FastAPI):
    with open("app/model.json") as f:  # runs once, before the first request
        MODEL.update(json.load(f))
    yield
    MODEL.clear()


app = FastAPI(lifespan=lifespan)


class Customer(BaseModel):
    tenure_months: float = Field(ge=0)
    monthly_charge: float = Field(ge=0)
    support_tickets: int = Field(ge=0)


@app.get("/healthz")
def healthz():
    return {"status": "ok", "model_version": MODEL["version"]}


@app.post("/predict")
def predict(customer: Customer):
    weights = MODEL["weights"]
    z = MODEL["intercept"] + sum(weights[name] * value for name, value in customer.model_dump().items())
    return {"churn_probability": round(1 / (1 + math.exp(-z)), 4), "model_version": MODEL["version"]}

Edge cases and limitations

A batch table has no row for a key that appeared after the job ran
A customer who signed up this morning, or a search query nobody typed before, is missing from last night's predictions. The application must decide in advance what to do on a lookup miss: fall back to a default score, a simpler rule, or an online call. Measure the miss rate, because a rising miss rate is the usual signal that the use case has outgrown batch inference.
Cold starts break latency budgets that were measured on a warm service
A new replica is useless until its model is loaded, and a platform that scales to zero pays that load time on the first request after an idle period. The SageMaker documentation describes serverless inference as suited to workloads that can tolerate cold starts. For a strict budget, keep a minimum number of warm replicas, and add capacity before the peak instead of during it.
Dynamic batching adds delay without benefit at low traffic
A queue delay only forms larger batches when several requests arrive within it. At two requests per second, a 5 ms delay almost never groups anything and every request simply waits 5 ms longer. Triton also states that the dynamic batcher is for stateless models; models that keep state across a sequence of requests need its sequence batcher so that related requests reach the same instance.
A shadow model can cause real side effects and real load
Shadow responses are discarded, but anything the shadow service does on the way is not. If scoring writes to a database, calls a paid API or sends a notification, the shadow copy does it a second time. Shadow traffic also doubles the read load on shared dependencies such as a feature store. Disable side effects in shadow mode and size the dependencies for the copied traffic, or mirror only a sample.
A canary on a low-traffic service cannot detect much
A 5 percent canary on a service with 2 requests per second sees 180 requests in 30 minutes. If the normal error rate is 0.2 percent, the expected number of errors is below one, so one unlucky request looks like a regression and a real one can pass unnoticed. Raise the canary share, lengthen the window, or rely more on shadow results and offline replay for services with little traffic.
Percentiles do not add up across stages or fan-out
The p95 of a request is not the sum of the p95 values of its stages, and a request that calls five models in parallel is slow whenever any one of them is slow. With independent calls, the chance that all five finish within their own p95 is 0.95 to the fifth power, about 77 percent. Measure the end-to-end percentile directly and budget the per-call percentile more tightly when there is fan-out.

When to use it, and when something simpler is enough

Use it when

  • Use batch inference when every input is known before the job runs and a prediction that is hours old is acceptable, as with a nightly churn list or a weekly demand forecast.
  • Use online inference when the input only exists at request time (a new search query, the current session, a payment being made) or when acting on stale data costs money.
  • Use a dedicated model server when many models share one operational pattern, or when you need its batching, multi-framework support or GPU scheduling.
  • Use shadow and canary stages whenever a wrong or slow prediction reaches a user or a business decision directly.

Think twice when

  • Avoid an always-on online endpoint for a job that scores a known list once a day; a scheduled batch job is cheaper and has no latency requirement or outage risk in the request path.
  • Avoid a model server for a single small model wrapped in business rules; a plain API service is easier to test, debug and hand over.
  • Avoid long shadow and canary stages for an internal report or a prototype with a handful of users, where a failed deployment costs minutes and a rollback is one command.

A simpler alternative. Score everything in a scheduled job and write the results to a table that the application reads. This needs no serving infrastructure and no latency budget. It stops being enough when lookups start to miss (new users, long-tail inputs), when the features that matter are minutes old, or when most precomputed scores are never read.

Key takeaways

  • Batch inference computes predictions ahead of time for known inputs, while online inference computes them per request, and the choice depends on whether inputs exist in advance and how stale a prediction may be.
  • An online model is a web service that loads its artifact once at startup, validates inputs, reuses the training preprocessing and returns the model version with every prediction.
  • A container image fixes the library versions the model depends on, and replicas of that image behind a load balancer provide capacity.
  • Latency requirements are stated as percentiles and split into a budget per stage, and the replica count follows from peak traffic, measured capacity per replica and a target utilisation well below one.
  • A shadow deployment tests a new version on copied traffic without returning its answers, and a canary then gives it a small share of real traffic with a rollback rule fixed in advance.
  • A dedicated model server replaces hand-written serving code when many models share the same operational needs, and its batching trades extra latency for throughput.

Example 1 of 5

Instacart: from precomputed lookup tables to online model endpoints

InstacartDocumented in an engineering article

Instacart's engineering post "Lessons Learned: The Journey to Real-Time Machine Learning at Instacart" (September 2022) describes how the grocery delivery company moved most of its ML systems from batch-generated predictions to real-time serving, and what that change cost. [15]

The problem

Most of Instacart's ML systems began as batch systems. Models generated predictions offline and wrote them to database tables that production applications read. The post lists what went wrong with that design as the product grew: precomputed predictions were stale and handled new search queries poorly, daily scoring of all customers wasted compute on people who were not active that day, and predictions could not be cached for every user-item pair, so the long tail was cut off.

Where this topic fits

This is the batch-versus-online decision, made twice. The original design sits on the batch path: a job writes scores and the application performs a lookup. The new design sits on the online path: the application calls a model endpoint at request time, and that endpoint reads features from a store. Rollout safety and a latency budget only became requirements after the move.

How it is applied, step by step

  1. Start on the batch path. A scheduled job scores the customers, queries and user-item pairs it knows about and writes the model outputs to database tables; production services read a score by key.
  2. Trace each complaint to a property of batch inference. Stale answers come from the schedule, missing answers from inputs that did not exist when the job ran, and wasted compute from scoring records nobody asks about.
  3. Add two platform pieces for the online path: a Feature Store, which is a key-value store for fast feature retrieval, and an Online Inference Platform that hosts each model as an RPC endpoint.
  4. Put one interface (Griffin) in front of the platform so that unit tests, integration tests, canary deployments and monitoring are standard for every model instead of rebuilt by each team.
  5. Treat latency and availability as new requirements. Feature retrieval, feature engineering and prediction now all happen inside a user request and must fit one latency budget.
  6. Only then move the inputs to real time as well: events flow through Kafka and Flink into the Feature Store, so that online models see signals that are seconds old.

Why this approach fits

The three batch problems are structural, so tuning the batch job could not remove them. A lookup table can only contain keys that existed when the job ran, and a schedule fixes how old a score is. Computing on request removes both limits at once and spends compute only on predictions that are used. Moving serving first and features second also kept each step measurable: the first change fixed coverage and waste while still using batch features, and the second fixed freshness.

Limitation or tradeoff

The post is explicit about the price. The model endpoint became a dependency in the request path, so a slow feature read or prediction is now a slow page, and an endpoint failure is a product failure. That required monitoring, error handling and deployment practices that a nightly job never needed, plus new tools for the ML engineers to learn. Online serving also does nothing for stale inputs by itself; the first phase still predicted from batch features.

What the sources document

  • Most ML systems at Instacart started as batch-oriented systems in which models only had access to batch features and generated predictions offline in batches, consumed offline for analytics or online through a lookup table; engineers wrote model outputs to database tables that applications read in production. [15]
  • The post lists limitations of the batch systems, including stale predictions that performed poorly on new queries, wasted resources from generating daily predictions for customers who are not active every day, and limited coverage because predictions cannot be cached for all user-item pairs, so pairs in the long tail are truncated. [15]
  • Real-time serving was made possible by a Feature Store, described as a key-value store for fast feature retrieval, and an Online Inference Platform that hosts each model as an RPC endpoint. [15]
  • The post names latency and availability as challenges of real-time serving: feature retrieval, feature engineering and model prediction must fit a tight latency budget, and the inference system is a new failure point that can cause downtime in the backend service. [15]
  • The authors report that the real-time platform serves hundreds of models in real time and generates features with latency in the order of seconds, compared with hours before. [15]

The facts above come from the cited sources. The steps and analysis in this example are our explanation of how they fit together.

Example 2 of 5

Grab Catwalk: TensorFlow Serving containers on Kubernetes as a shared model server

GrabDocumented in an engineering article

Grab's engineering post "Catwalk: Serving Machine Learning Models at Scale" (July 2019) describes the ride-hailing company's self-service serving platform. The TensorFlow Serving Docker guide documents the container interface that the platform runs. [16][14]

The problem

As more teams at Grab adopted ML, each built its own model serving solution. The post reports two costs: data scientists had to understand the serving infrastructure underneath their models, and much of the effort was duplicated across teams. Deploying or updating a model took attention away from the modelling work.

Where this topic fits

Catwalk is the model-server and container layers of this lesson, offered as a platform. It sits between an exported model in object storage and an HTTP endpoint that other services call. The data scientist never writes API code; a standard server image is configured with the location of the model.

How it is applied, step by step

  1. A data scientist exports the trained model in TensorFlow's SavedModel format and uploads the folder to a models bucket in S3. That path is the whole interface between the data scientist and the platform.
  2. The platform runs the TensorFlow Serving container image, pointed at that path. The server loads the model files and exposes a prediction endpoint, so no per-model serving code exists.
  3. Each model gets its own set of Kubernetes resources: a deployment of two or more TensorFlow Serving pods with CPU and memory limits, an autoscaler, and a load balancer with an HTTP endpoint.
  4. Kubernetes places the pods on nodes that have room for them, which keeps one model from starving another of CPU and removes the manual work of deciding which cluster serves which model.
  5. To update a model, the data scientist uploads a new export to the same folder. TensorFlow Serving watches the path and loads the new version, replacing the old one or serving both, depending on configuration.
  6. Every pod reports request statistics and logs through agents that run on each node, so monitoring comes with the platform.

Why this approach fits

When most models share one framework and one request pattern, the serving code is the same for all of them, and a generic server removes it from every team's backlog. Containers make that server a fixed, tested unit, and Kubernetes supplies the parts that are also the same for every model: replicas, load balancing, scaling and isolation between workloads. The team's interface shrinks to an exported folder and a traffic estimate.

Limitation or tradeoff

The design assumes the model fits the server. The post notes that TensorFlow Serving supports only TensorFlow models by default, which was acceptable because Grab was standardising on TensorFlow; a team with another framework or with custom logic around the model needs a different server or its own service. Automatic loading of whatever is uploaded is also a rollout with no shadow or canary stage unless the platform adds one, so a bad export can go straight to production traffic.

Cloudflare bot detection: a latency budget measured in microseconds

CloudflareDocumented in an engineering article

Cloudflare's post "Every request, every microsecond: scalable machine learning at Cloudflare" (June 2023) describes how bot-detection models are evaluated inside the path of HTTP requests on its network, and how the team measured and cut the latency of that step. [17]

The problem

Cloudflare's ML detection runs on live HTTP traffic, at an average of more than 46 million requests per second, and produces the final bot score for most of them. The models need features that aggregate behaviour across many requests. Those features were fetched from a separate feature service over a Unix socket, and as features and traffic grew the median fetch time rose from about 200 to about 500 microseconds, with a p99 near 10 milliseconds at peak. Fetch timeouts also reduced feature availability, which the post says raised the likelihood of false positives and false negatives for a subset of requests.

Where this topic fits

This is a latency budget applied stage by stage. The request path is: extract keys from the request, look up features, run the CatBoost model, expose the score to the firewall. The post states that model inference is only one component of latency and that feature extraction and preparation are the others. The work described is finding the stage that consumed the budget and redesigning it.

How it is applied, step by step

  1. Score in the request path. Every HTTP request waits for the bot score, so the budget for the whole ML step is far below a millisecond and the tail matters as much as the median.
  2. Measure each stage with percentiles. The feature fetch had a p50 of 532 microseconds and a p99 of 9,510 microseconds, a tail almost 18 times the median.
  3. Locate the cost. It was not the model. It was moving feature data between two processes: socket contention, serialisation, copying and garbage-collection pauses.
  4. Remove the hop. Features are written by a sidecar service into memory-mapped files and read directly by a library loaded into each worker, with wait-free synchronisation and zero-copy deserialisation, so a lookup no longer crosses a socket.
  5. Re-measure the same percentiles after rollout and report them next to the old ones, together with the effect on the whole bot management module.

Why this approach fits

When a prediction gates every request, the model cannot sit behind a network call with its own queue and tail; the budget is too small. Running inference inside the request-handling process, with features already in local memory, removes the hop entirely. The case also shows the general method behind any latency budget: split the request into stages, measure each one at p50 and p99, and spend effort on the stage that dominates, which here was data access and not model computation.

Limitation or tradeoff

This design is expensive to build and narrow in use. It needed a custom Rust library, careful concurrency work and tight coupling between ML code and the proxy that handles traffic, so a bug in the scoring library runs inside the request path. It suits small tree models on CPU and would not suit a large neural network that needs a GPU. Most teams should exhaust the ordinary options first: caching features, co-locating the service and trimming the model.

What the sources document

  • Cloudflare states that it serves on average over 46 million HTTP requests per second and that machine learning detection provides the final Bot Score decision for over 72% of all HTTP requests; it also runs several machine learning models in shadow mode for every HTTP request. [17]
  • The models are CatBoost models, and the article says model inference is just one component of the overall latency, alongside machine learning feature extraction and preparation. [17]
  • In the previous design, features were fetched with memcached requests over a Unix socket from Gagarin, a Go-based feature serving platform; its median latency grew from around 200 to 500 microseconds and its p99 reached roughly 10 milliseconds at peak times. [17]
  • After the redesign around memory-mapped files, wait-free synchronisation and zero-copy deserialisation, the reported feature fetch latency fell from 532 to 9 microseconds at p50, from 9,510 to 18 at p99 and from 16,000 to 29 at p999, and Bot Management module latency improved by an average of 55.93%. [17]

Amazon SageMaker deployment guardrails: canary traffic shifting with automatic rollback

Amazon Web ServicesDocumented in official docs

The Amazon SageMaker AI developer guide documents deployment guardrails, a managed feature for updating the model behind an existing inference endpoint. Its overview page and its page on canary traffic shifting describe the behaviour used here. [7][8]

The problem

Replacing the model behind a live endpoint can go wrong in ways offline tests do not catch. The guide names increased model latency and high error rates as the result of a regressive update, leading to unplanned downtime and business impact. Without a managed feature, each team has to build its own orchestration, monitoring and rollback for every update.

Where this topic fits

This is the canary stage of a rollout, implemented by the platform. It starts when a new endpoint configuration (new model, container or instance type) is ready and ends when either all traffic is on the new fleet or all of it is back on the old one. In the guide's terms the old fleet is blue and the new fleet is green.

How it is applied, step by step

  1. Before the update, create CloudWatch alarms on the endpoint's metrics. These alarms are the rollback criteria, and the guide lists them as a prerequisite.
  2. Call UpdateEndpoint with a blue/green update policy of type CANARY, a canary size and a wait interval, and name the alarms in the auto-rollback configuration.
  3. SageMaker provisions the green fleet next to the blue fleet and routes the canary's share of traffic to it. Both fleets now answer real requests.
  4. During the baking period the alarms watch the green fleet. If any alarm trips, SageMaker rolls back and all traffic returns to the blue fleet.
  5. If no alarm trips, the rest of the traffic shifts to the green fleet and a final baking period begins.
  6. When the final baking period ends without an alarm, the green fleet serves all traffic and the blue fleet is terminated.

Why this approach fits

The two things that make a canary trustworthy are both enforced by the platform here. The rollback rule exists before the rollout begins, because the update cannot be configured without alarms, and the rollback itself needs no person to be awake, because a tripped alarm returns traffic to the old fleet. Keeping the blue fleet running until the end makes that rollback a routing change instead of a redeployment.

Limitation or tradeoff

Alarms only see what they measure. Error counts and latency catch a crashing container or a slow model, but a model that returns fast, well-formed and wrong predictions trips nothing unless you publish and alarm on prediction statistics yourself. Running two fleets costs extra during the update, a short baking period can miss time-of-day effects, and the guide notes that deployment guardrails apply only to real-time and asynchronous endpoints.

What the sources document

  • Deployment guardrails are described as a set of model deployment options for updating models in production; blue/green deployments shift traffic from an old (blue) fleet to a new (green) fleet using all-at-once, canary or linear traffic shifting, where canary shifts traffic in two steps and linear in n linearly spaced steps. [8]
  • With canary traffic shifting, a portion of the green fleet called the canary receives traffic first, and the canary size should be less than or equal to 50% of the new fleet's capacity. [7]
  • During the baking period CloudWatch alarms monitor the green fleet; if any alarm trips, SageMaker initiates a rollback and all traffic returns to the blue fleet, and otherwise the remaining traffic shifts to the green fleet, followed by a final baking period after which the blue fleet is terminated. [7]
  • Creating CloudWatch alarms is a stated prerequisite for canary traffic shifting, and the example UpdateEndpoint call sets CanarySize, WaitIntervalInSeconds, TerminationWaitInSeconds and an AutoRollbackConfiguration that lists alarms by name. [7]
  • The overview states that a regressive update can cause unplanned downtime and business impact such as increased model latency and high error rates, and that deployment guardrails only apply to asynchronous and real-time inference endpoint types. [8]

Uber Michelangelo: shadow deployments as a standard gate before rollout

UberDocumented in an engineering article

Three Uber Engineering posts describe model serving on its Michelangelo platform: the 2017 platform overview, a 2021 post on continuous deployment for online serving, and a 2025 post on model deployment safety. Together they document how shadowing became a built-in platform feature. [18][19][20]

The problem

The 2025 post states the difficulty directly: models are probabilistic and tightly coupled to data, so static tests validate them poorly, and a model can perform well offline and still fail in production because of data drift or integration edge cases. The platform runs hundreds of use cases, and the 2021 post notes that different teams had different strategies for shadowing, so the mechanism was built into the prediction service to spare teams from implementing it repeatedly.

Where this topic fits

Shadowing sits between offline validation and the controlled rollout. A candidate that passed offline evaluation and backtesting is exercised with live inputs while the production model keeps answering. Only after that does it receive a small slice of real traffic, with automatic rollback behind it.

How it is applied, step by step

  1. The candidate model is loaded into the prediction service next to the production model. The 2017 post already notes that more than one model can be deployed to the same serving container.
  2. The model owner declares a shadow relation and shadow criteria through an API: which production (primary) model the candidate shadows, what to shadow and for how long.
  3. For each selected request, the service returns the primary model's prediction and also runs the shadow model on the same input. Features already fetched for the primary are reused, and only the additional ones are read from the online feature store.
  4. Predictions from both models are collected for the same requests and compared over a window of days or weeks.
  5. Shadow work has lower priority than production work: under load, shadow models can be paused and later resumed.
  6. A candidate that passes enters a controlled rollout that starts with a small traffic slice. If error rates, latency or CPU and GPU utilisation cross thresholds, the platform reverts to the last known good version.

Why this approach fits

A shadow run is the closest thing to production that carries no user risk: the same inputs, the same feature pipeline, the same load. Building it into the serving platform changes it from a project each team must fund into a setting each team switches on, which is how it can become a default step in retraining pipelines. Reusing the primary model's features keeps the extra cost close to the cost of one more model evaluation.

Limitation or tradeoff

Shadowing measures agreement and operational health, not benefit. If the model's output changes what a user sees or does, the logged outcomes were produced by the primary model's decisions, so the shadow model's effect on those outcomes stays unknown until it serves real traffic. Shadowing also consumes compute and feature-store capacity, which is why it is paused under load, and the 2025 post reports coverage of over 75 percent of critical online use cases, not all of them.

What the sources document

  • The 2025 post describes shadow testing as running the candidate model in parallel with production on identical live inputs and logging its outputs for comparison without affecting user-facing predictions, and says it is part of over 75% of critical online use cases at Uber. [18]
  • The same post says deployments start with a small traffic slice while system health and prediction quality are monitored, and that auto-rollback reverts to the last known good version if error rates, latency or CPU/GPU utilisation breach thresholds. [18]
  • The 2021 post lists common characteristics of model shadowing at Uber: shadow results are not used in production but collected for analysis, shadowing usually runs for days or weeks, and shadow traffic can be 100% or picked by criteria of the primary model's traffic. [19]
  • The 2021 post says users configure shadow relations and shadow criteria through API endpoints, that the prediction service fetches only the features not already used by the primary model for shadow models, and that shadow models can be treated as second class and paused or resumed when the service is under pressure. [19]
  • The 2017 post states that more than one model can be deployed at the same time to a given serving container, which allows safe transitions from old models to new models and side-by-side A/B testing. [20]

4Common mistakes

  1. Loading the model inside the request handler instead of once when the process starts.

    Why it causes problems
    Every request pays for reading and deserialising the artifact, which can take far longer than the prediction itself. Latency rises by the load time, memory use spikes under concurrent requests, and throughput collapses long before the CPU is busy.
    How to recognise it
    Latency is large and almost identical for every request, whatever the input. A profile shows most of the time in file reads or deserialisation, and the first and the thousandth request are equally slow.
    How to fix it
    Load the artifact in a startup hook such as a FastAPI lifespan function, keep it in memory, and let the health endpoint report ready only after loading has finished.

  2. Rewriting the training preprocessing by hand in the serving code.

    Why it causes problems
    A different scaling constant, category order or default for a missing value produces predictions that look plausible and are wrong. Nothing crashes and no alarm fires; the model simply performs worse in production than it did offline. This is known as training-serving skew.
    How to recognise it
    Score the same rows in the training environment and through the deployed API. Any difference beyond rounding is skew. A shadow run that disagrees with offline scores for identical inputs is another sign.
    How to fix it
    Ship preprocessing inside the artifact (for example a single pipeline object) or import one shared function in both places. Keep a parity test in the build and a hand-computed smoke-test request for every deployment.

  3. Judging speed by average latency and planning replicas for 100 percent utilisation.

    Why it causes problems
    The average hides the slow tail, so one request in twenty can time out while the dashboard looks healthy. A fleet sized to run full has no room for queues, and its latency climbs steeply at exactly the moment traffic peaks.
    How to recognise it
    Clients report timeouts while mean latency is well inside the limit, the p99 is many times the p50, or latency rises sharply during the daily peak although the request mix has not changed.
    How to fix it
    Record p50, p95 and p99. State the budget as a percentile, measure the request rate one replica sustains within it, and size the fleet with a target utilisation well below one, then load-test the result.

  4. Building the image from unpinned dependencies or loading a pickled model with other library versions.

    Why it causes problems
    The scikit-learn documentation states that loading a model with a different version from the one that trained it is unsupported and can give unexpected results or crash. Two builds of the same code made weeks apart can therefore serve different predictions. Pickle-based files also execute code when loaded.
    How to recognise it
    Version warnings such as InconsistentVersionWarning appear in the service logs at startup, or the smoke-test request returns a slightly different number after a rebuild that changed no code.
    How to fix it
    Pin exact versions in a lock file, build the image only from it, and store the library versions next to the artifact. Load artifacts only from your own registry, and consider a format such as ONNX when the serving environment cannot match the training one.

  5. Starting a canary without numeric rollback criteria or without enough traffic to judge it.

    Why it causes problems
    The decision to continue becomes "it looked fine". With few requests in the window, a real regression passes unnoticed and a single unlucky error can trigger a needless rollback.
    How to recognise it
    Nobody can state the error rate or latency that would have stopped the rollout, or the expected number of errors in the observation window at the normal error rate is in single digits.
    How to fix it
    Before the rollout, write down the thresholds, multiply request rate by window length to get the expected event counts, and attach the thresholds to alarms that return traffic to the old version automatically.

  6. Sending traffic to a new replica before its model has finished loading.

    Why it causes problems
    Every deployment and every scale-up produces a burst of errors or very slow first requests. During a canary those errors are blamed on the new model and can trigger a rollback of a healthy version.
    How to recognise it
    Errors and latency spikes line up with the start times of new containers, and disappear a short and regular time after each start.
    How to fix it
    Expose a health endpoint that succeeds only once the model is in memory and use it as the readiness check, with a startup probe when loading takes longer than the normal probe timeout allows.

Show solution

scoring.py holds the only copy of the formula:

python
import json
import math

FIELDS = ("distance_km", "items", "rush_hour")


def load_model(path="model.json"):
    with open(path) as f:
        return json.load(f)


def score(model, row):
    values = {}
    for name in FIELDS:
        if name not in row:
            raise ValueError(f"missing field: {name}")
        values[name] = float(row[name])
        if values[name] < 0:
            raise ValueError(f"{name} must not be negative")
    z = model["intercept"] + sum(model["weights"][n] * values[n] for n in FIELDS)
    return round(1 / (1 + math.exp(-z)), 4)

import json
from http.server import BaseHTTPRequestHandler, ThreadingHTTPServer

from scoring import load_model, score

MODEL = load_model()  # loaded once, when the process starts


class Handler(BaseHTTPRequestHandler):
    def _send(self, status, body):
        data = json.dumps(body).encode()
        self.send_response(status)
        self.send_header("Content-Type", "application/json")
        self.send_header("Content-Length", str(len(data)))
        self.end_headers()
        self.wfile.write(data)

    def do_GET(self):
        if self.path == "/healthz":
            self._send(200, {"status": "ok", "model_version": MODEL["version"]})
        else:
            self._send(404, {"error": "not found"})

    def do_POST(self):
        if self.path != "/predict":
            return self._send(404, {"error": "not found"})
        try:
            length = int(self.headers.get("Content-Length", 0))
            result = score(MODEL, json.loads(self.rfile.read(length)))
        except (ValueError, TypeError) as err:
            return self._send(400, {"error": str(err)})
        self._send(200, {"late_probability": result, "model_version": MODEL["version"]})

    def log_message(self, *args):  # keep the console quiet during the latency test
        pass


if __name__ == "__main__":
    ThreadingHTTPServer(("127.0.0.1", 8000), Handler).serve_forever()

2. Prediction differences. Only request 3 changes its flag (0.48 to 0.53), so the flip rate is 1 / 20 = 5 percent. The absolute differences sum to 0.69, so the mean is 0.69 / 20 = 0.0345.

3. Decision. p95 of 58 ms is within 60 ms, 5 percent is within 10 percent, and 0.0345 is within 0.05. v2 may start its canary. The criteria miss the tail: request 19 took 140 ms in v2, three times its v1 time and more than twice the p95 limit. Twenty samples cannot estimate a p99, so the canary should run with a p99 alarm and the shadow report should be repeated on a much larger sample. Request 12 is also worth a look: its probability moved by 0.09, the largest shift, without changing the flag.

4. Replicas.

v1: ⌈30060×0.6⌉=⌈8.33⌉=9v2: ⌈30040×0.6⌉=⌈12.5⌉=13canary: ⌈3040×0.6⌉=⌈1.25⌉=2\text{v1: } \left\lceil \frac{300}{60 \times 0.6} \right\rceil = \lceil 8.33 \rceil = 9 \qquad \text{v2: } \left\lceil \frac{300}{40 \times 0.6} \right\rceil = \lceil 12.5 \rceil = 13 \qquad \text{canary: } \left\lceil \frac{30}{40 \times 0.6} \right\rceil = \lceil 1.25 \rceil = 2v1: ⌈60×0.6300​⌉=⌈8.33⌉=9v2: ⌈40×0.6300​⌉=⌈12.5⌉=13canary: ⌈40×0.630​⌉=⌈1.25⌉=2

v2 needs 13 replicas where v1 needs 9, about 44 percent more. That cost belongs in the promotion decision next to the accuracy gain.

5. Canary. Ten percent of 300 is 30 requests per second, and 20 minutes is 1,200 seconds, so the canary answers 36,000 requests. At 0.2 percent that is 72 errors; at 1 percent it is 360. A rule that fits these numbers: return all traffic to v1 if, over any 5-minute window (9,000 canary requests, about 18 errors at the normal rate), the canary's error rate exceeds 1 percent (90 errors), its p95 exceeds 60 ms, or its p99 exceeds 150 ms. Also compare the share of orders flagged by v2 with the share flagged by v1; a sudden gap points to a broken feature, not to a better model.

import math

LOG = [  # (v1_prob, v2_prob, v1_ms, v2_ms)
    (0.12, 0.10, 14, 22), (0.81, 0.84, 15, 25), (0.48, 0.53, 13, 21), (0.05, 0.04, 16, 27),
    (0.66, 0.70, 14, 24), (0.33, 0.29, 18, 31), (0.92, 0.95, 15, 23), (0.57, 0.61, 21, 36),
    (0.22, 0.18, 14, 22), (0.74, 0.79, 17, 29), (0.09, 0.07, 13, 20), (0.61, 0.52, 24, 41),
    (0.38, 0.35, 15, 26), (0.88, 0.90, 16, 28), (0.45, 0.41, 19, 33), (0.70, 0.73, 31, 58),
    (0.16, 0.13, 14, 24), (0.53, 0.56, 15, 25), (0.97, 0.98, 46, 140), (0.29, 0.25, 17, 30),
]


def nearest_rank(values, q):
    ordered = sorted(values)
    return ordered[math.ceil(q * len(ordered)) - 1]


for name, column in (("v1", 2), ("v2", 3)):
    times = [row[column] for row in LOG]
    print(name, nearest_rank(times, 0.50), nearest_rank(times, 0.95), max(times))

flips = sum((a >= 0.5) != (b >= 0.5) for a, b, _, _ in LOG)
print("flip rate", flips / len(LOG))
print("mean abs diff", round(sum(abs(a - b) for a, b, _, _ in LOG) / len(LOG), 4))
for name, rate, capacity in (("v1", 300, 60), ("v2", 300, 40), ("canary", 30, 40)):
    print(name, "replicas", math.ceil(rate / (capacity * 0.6)))
