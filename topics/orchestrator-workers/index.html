Orchestrator-Workers

Orchestrator-workers is a workflow pattern in which one central model call, the orchestrator, reads a task and decides at run time which subtasks it needs. Each subtask is handed to a separate worker model call, and the workers' results are then combined into a single answer.

1Overview

Why it matters

Some tasks cannot be split up before you have seen them. A code change may touch one file or twelve, and each file may need a different edit. A research question may break into three lines of enquiry or thirty. A fixed pipeline has no place to put that decision, and a single agent that does everything itself fills its context with search results and tool output long before the work is finished.

The pattern is behind the subagents in coding assistants such as Claude Code and behind research features such as Claude's Research, so anyone who builds, buys or debugs systems like these needs to know how it works. It also has costs that are easy to miss. Anthropic reports that its multi-agent systems use about 15 times the tokens of a chat. The typical failures are specific to delegation: a brief too vague for a worker to act on, two workers doing the same job, a plan with far more subtasks than the task deserves, and pieces that do not fit together because no worker could see the others.

What you will be able to do

  • Describe the three roles (orchestrator, workers, synthesis) and the data that passes between them.
  • Explain how orchestrator-workers differs from fixed parallelization, and name the consequences of a subtask list produced at run time.
  • Write a delegation brief with an objective, an output format, guidance on tools and sources, and task boundaries.
  • Implement the pattern in plain Python with plan validation, a cap on subtasks and a concurrent fan-out.
  • Estimate the number of calls, the context size and the elapsed time of a run for a given number of workers.
  • Decide when a single call, fixed sectioning, a parallel map in code or one agent is the better choice.

Key terms

Orchestrator
The central model call that reads the task, decides which subtasks this input needs and writes instructions for each one. In many systems it also combines the results.
Worker
A separate model call, or a small agent, that carries out one subtask. It sees only the brief it was given and returns its result to the orchestrator.
Subtask
One piece of the work that a worker can finish from written instructions, without seeing what the other workers are doing.
Plan
The orchestrator's output, namely a list of subtasks in a format that code can parse and loop over, such as JSON.
Delegation brief
The instructions sent to one worker. A good brief states the objective, the output format, which tools or sources to use, and where the subtask ends.
Fan-out
Starting several worker calls from one plan, usually at the same time. The matching step that gathers their results is called fan-in.
Synthesis
The step that turns the workers' separate results into one answer. It can be a model call or ordinary code that joins the pieces.
Context isolation
Giving each worker its own context window, so that the tool output and reasoning of one subtask never enter the orchestrator's context or another worker's.
Sectioning
The form of parallelization in which a task is split into independent parts that are fixed in code before any input arrives.
Subagent
A name many products use for a worker that is itself an agent, running its own loop of tool calls in a separate context window.

2Explanation

Introduction

In Parallelization you split a task into sections that your code knew in advance: the same three reviewers for every document, the same two checks for every message. In Routing a model chose one destination from a list you had written. Both patterns work because you could write the list before any input arrived.

Many useful tasks do not allow that. "Rename this command-line flag everywhere it is documented" touches one file in one repository and nine in another, and the change log needs a different edit from the README. "Compare the refund policies of the vendors named in this email" needs one lookup per vendor, and the number of vendors is known only after reading the email. For tasks like these, working out the list of subtasks is part of the job.

Think of a newsroom editor on the day a story breaks. The editor does not send the same three reporters to the same three places every day. They read what is known so far, decide that this story needs someone at the courthouse, someone on the phone to the company and someone reading the filings, and tell each reporter exactly what to bring back. The reporters work separately and file short reports. The editor writes one article from them.

The orchestrator-workers pattern gives a language model the editor's job:

  • The orchestrator is a model call that reads the task and writes the list of subtasks for this input.
  • The workers are separate model calls, one per subtask. Each receives a written brief and nothing else.
  • Synthesis combines what the workers returned into one result.

Anthropic's Building effective agents (opens in a new tab) lists this among its workflow patterns: a central LLM breaks a task down dynamically, delegates the parts to worker LLMs and synthesizes their results. The article adds that the shape resembles parallelization, and that the difference is that the subtasks are not defined in advance.

This lesson explains the three roles, shows how the pattern differs from fixed parallelization, walks through a runnable implementation, and covers what the pattern costs and where it fails. Systems in which the orchestrator is a long-running agent, and other ways for agents to cooperate, are the subject of Multi-Agent Systems.

How it works

One control flow, three roles

Stripped of framework detail, the pattern is three lines. This is pseudocode; the worked example is the runnable version.

python
plan    = orchestrator(task)                       # 1 call: decide the subtasks
results = run_concurrently(worker, plan.subtasks)  # N calls: one brief each
answer  = synthesize(task, results)                # 1 call, or plain code

Three properties follow from this shape:

  • N is the output of a model. Your code does not know how many workers will run, or what they will be asked, until the first call returns.
  • Each worker starts empty. A worker sees its brief and whatever the brief points to. It does not see the user's conversation, the plan or the other workers.
  • Results meet in one place. Workers do not talk to each other. Everything they produce goes back to the orchestrator or to a synthesis step.

How it differs from fixed parallelization

Both patterns fan a task out to several model calls and gather the results, so their diagrams look alike. The difference is where the list of subtasks comes from.

In sectioning, the list is a constant in your program. The prompts exist before any input arrives, and every input gets all of them. In orchestrator-workers, the list is data that a model produced for one input. Anthropic's example is a code change, where the number of files to edit and the nature of each edit depend on the request. The LangGraph documentation (opens in a new tab) applies the same test: the pattern is for subtasks that cannot be predefined the way they can with parallelization.

A list made at run time has consequences that a fixed one does not. The cost of a run is unknown until the plan exists. The plan can be wrong, so it has to be checked. And a bad plan (overlapping subtasks, a missing one, fifty where three would do) spoils every later step.

Two neighbouring cases are worth separating out. A router picks one destination from a fixed menu and hands the request over, whereas an orchestrator writes several new briefs and takes the results back. And if ordinary code can compute the list, for example one call per file that a search returned, all with the same instruction, you have a parallel map and no need for an orchestrator model.

The plan is structured output

Code has to loop over the plan, so the orchestrator must return something parseable. Anthropic's cookbook notebook (opens in a new tab) asks for XML tags and parses them. The LangGraph example binds a schema to the model so that it returns a typed list of sections (see Structured Outputs). Treat the plan as untrusted input and check it before spending money on it:

  • the number of subtasks is within a cap you chose;
  • every subtask has the fields a worker needs;
  • no two subtasks cover the same ground.

The brief is all a worker knows

The orchestrator knows the user's request, the conversation and its own reasoning. The worker knows only what the brief says. The team behind Anthropic's Research feature reports (opens in a new tab) that when the lead agent delegated with a few words naming only a topic, subagents misread the task or repeated each other's searches. Their lead agent now gives every subagent four things:

Part of the briefWhat it prevents
An objectiveA worker solving a neighbouring problem
An output formatResults that the synthesis step cannot combine
Guidance on tools and sourcesWasted calls and weak sources
Clear task boundariesTwo workers doing the same part, or nobody doing it

One subtask in a plan, carrying its own brief, might look like this:

json
{
  "objective": "Find vendor A's refund window and the conditions attached to it.",
  "output_format": "At most 3 bullet points, each ending with its source URL.",
  "sources": "The vendor's own policy pages only.",
  "boundaries": "Refunds only. Ignore shipping and warranty terms."
}

A brief like this costs a few dozen tokens. A worker that did the wrong job costs its whole run.

Fan-out, limits and failures

Workers are independent, so they can run at the same time, and elapsed time is then close to the slowest worker instead of the sum of all of them. Frameworks supply the fan-out primitive. LangGraph's Send API creates one worker node per item in the plan, each with its own state, and collects every worker's output under a shared state key. In Claude Code and the OpenAI Agents SDK, delegation is a tool call: the main model calls a tool that runs the worker, and the worker's result comes back to the model that called it.

A dynamic fan-out needs limits that a fixed one does not: a cap on subtasks per plan, a cap on concurrent workers, and a cap on nesting if workers may delegate. Claude Code's defaults are 20 running subagents and three layers of nesting. Each worker also needs its own timeout and error handling, so that one failure leaves one marked gap and does not lose the run.

Synthesis

The last step turns N results into one. It takes three common forms:

  • A join in code. LangGraph's documented example concatenates the written sections with a separator. That is enough when the subtasks are parts of one document.
  • A model call. This is needed when results overlap, disagree or must be weighed against each other. Anthropic's lead research agent also decides at this point whether more workers are required.
  • References. Workers store large outputs such as code or reports outside the conversation and return short pointers, so nothing is lost by squeezing it through the orchestrator.

What it buys and what it costs

A run makes one planning call, NNN worker calls and usually one synthesis call. The main gain is context isolation. Suppose each subtask produces www tokens of search results and tool output. A single agent that does all NNN subtasks itself ends with about b+Nwb + Nwb+Nw tokens in its context, where bbb is its starting prompt. An orchestrator that receives only an rrr-token summary from each worker ends with b+Nrb + Nrb+Nr. Each worker peaks at bw+wb_w + wbw​+w, where bwb_wbw​ is the size of its brief, however many workers there are.

Take bbb = 2,000, www = 20,000, rrr = 1,500 and bwb_wbw​ = 1,000. These sizes are in line with Anthropic's remark (opens in a new tab) that a subagent may use tens of thousands of tokens and return a summary of 1,000 to 2,000. Five subtasks then leave 102,000 tokens in the single agent's context, 9,500 in the orchestrator's and 21,000 in each worker's.

Smaller contexts do not mean a smaller bill. The Research team's article reports that, in Anthropic's data, agents use about 4 times the tokens of a chat interaction and multi-agent systems about 15 times. The pattern spends tokens to buy context room and elapsed time, which is why that article reserves it for tasks valuable enough to pay for it.

The roles do not have to use the same model. Anthropic's Research system pairs Claude Opus 4 as the lead agent with Claude Sonnet 4 subagents, and a Claude Code subagent definition can name a lower-cost model for its worker. Planning and synthesis are few calls that need judgement. Workers are many calls with a narrow job.

Variants you will meet

  • One-shot workflow. Plan once, fan out, combine. The cookbook notebook and the LangGraph example work this way.
  • Agentic orchestrator. The orchestrator runs an agent loop, reads the results and may delegate again. Anthropic's Research feature and Claude Code do this.
  • Fixed roster. The workers are a standing set of specialists, and the orchestrator decides who acts next and with what instruction. Microsoft's Magentic-One works this way, as does the manager pattern in the OpenAI Agents SDK (opens in a new tab), where a manager agent calls specialists through Agent.as_tool().
  • Recursive. Workers may plan and delegate in turn, as Cursor's planners spawn sub-planners.

Worked example: One orchestrator, two tasks: a flag rename that needs three workers and one that needs one

The task: a command-line tool is renaming a flag, and its documentation must follow. The repository has four documentation files. Which of them need a worker, and what each worker must do, depends on the flag.

So that everyone gets identical output, the model is replaced by a stand-in function with scripted replies. The two plans in PLANS are written the way an orchestrator model would return them, and RESULTS holds each worker's one-line report. Everything else is real code: prompt building, plan validation, the concurrent fan-out, synthesis and the accounting. SECONDS is a pretend latency per call, used to compare schedules without waiting.

Save this as orchestrator_workers.py. It needs only the Python standard library (3.9 or later).

python
import json
import re
from concurrent.futures import ThreadPoolExecutor

MAX_SUBTASKS = 4
SECONDS = {"plan": 3, "work": 5, "synthesize": 4}  # pretend latency of one call
FILES = {
    "README.md": "Run `tool build --out dist`.",
    "docs/ci.md": "`tool build --out artifacts` then `tool test --out reports`.",
    "docs/faq.md": "Add --verbose to see more logs.",
    "CHANGELOG.md": "1.3: added the --out flag.",
}
# Scripted orchestrator replies: one plan per task, written as a model would return it.
PLANS = {
    "Rename the --out flag to --output-dir": [
        {"file": "README.md", "objective": "Replace --out with --output-dir in each command."},
        {"file": "docs/ci.md", "objective": "Replace --out with --output-dir in each command."},
        {"file": "CHANGELOG.md", "objective": "Add a 1.4 entry for the rename. Keep the 1.3 entry."},
    ],
    "Rename the --verbose flag to --debug": [
        {"file": "docs/faq.md", "objective": "Replace --verbose with --debug."},
    ],
}
RESULTS = {"README.md": "1 replacement", "docs/ci.md": "2 replacements",
           "docs/faq.md": "1 replacement", "CHANGELOG.md": "added a 1.4 entry, 1.3 untouched"}
calls = []  # (role, characters sent) for every model call


def model(role, prompt):
    """Stand-in for a chat model. It sees only the prompt it is given."""
    calls.append((role, len(prompt)))
    data = json.loads(prompt)
    if role == "plan":
        return json.dumps({"subtasks": PLANS[data["task"]]})
    if role == "work":
        return f"{data['file']}: {RESULTS[data['file']]}"
    return f"{len(data['results'])} file(s) updated. " + "; ".join(data["results"])


def plan_prompt(task):
    flags = {name: sorted(set(re.findall(r"--[a-z-]+", text))) for name, text in FILES.items()}
    return json.dumps({"task": task, "flags_per_file": flags})


def validate(plan):
    subtasks = plan.get("subtasks", [])
    if not 1 <= len(subtasks) <= MAX_SUBTASKS:
        raise ValueError(f"plan has {len(subtasks)} subtasks; allowed 1 to {MAX_SUBTASKS}")
    names = [subtask.get("file") for subtask in subtasks]
    if len(set(names)) != len(names) or any(name not in FILES for name in names):
        raise ValueError("each subtask needs its own existing file")
    return subtasks


def brief(subtask):
    return json.dumps({**subtask, "content": FILES[subtask["file"]],
                       "output_format": "<file>: <what changed>",
                       "boundaries": "Edit this file only."})


def orchestrate(task):
    calls.clear()
    subtasks = validate(json.loads(model("plan", plan_prompt(task))))
    with ThreadPoolExecutor(max_workers=MAX_SUBTASKS) as pool:  # results keep the plan's order
        results = list(pool.map(lambda subtask: model("work", brief(subtask)), subtasks))
    report = model("synthesize", json.dumps({"task": task, "results": results}))
    sizes = [size for _, size in calls]
    return {"workers": len(subtasks), "calls": len(calls),
            "largest_prompt": max(sizes), "total_chars": sum(sizes),
            "seconds_parallel": SECONDS["plan"] + SECONDS["work"] + SECONDS["synthesize"],
            "seconds_serial": sum(SECONDS[role] for role, _ in calls), "report": report}


if __name__ == "__main__":
    for task in PLANS:
        print(task)
        for key, value in orchestrate(task).items():
            print(f"  {key}: {value}")

Run python3 orchestrator_workers.py:

  workers: 1

  largest_prompt: 198

  seconds_serial: 12

What to notice:

  • The plan decided the fan-out. The same code ran three workers for the first task and one for the second, and orchestrate never mentions a file name. With sectioning you would have written four fixed prompts, one per file, and paid for all four on every task.
  • The plan carried judgement. docs/faq.md got no worker for the first task because it never mentions --out. CHANGELOG.md got a different objective from the other two files: add an entry and leave history alone. A search-and-replace over every hit would have rewritten the 1.3 entry.
  • Calls are N + 2. Three workers gave 1 + 3 + 1 = 5 calls. One worker gave 3.
  • Each call saw little. In the first run the five prompts were 175, 210, 214, 243 and 170 characters. That is 1,012 in total, yet no call saw more than 243. The orchestrator received a list of flags per file, not the files. Each worker received one file and its brief.
  • Concurrency changed elapsed time, not the amount of work. With the pretend latencies, a serial run of the first task takes 3 + 3 × 5 + 4 = 22 seconds, and running the workers together takes 3 + 5 + 4 = 12. For the second task both are 12, because there is nothing to run in parallel.
  • Validation ran before any worker. validate rejects an empty plan, more than MAX_SUBTASKS subtasks, two subtasks for one file, and a file that does not exist.

For a live system, replace model with a function that sends the prompt to a chat model and returns its text, with a separate system prompt for each of the three roles. The control flow does not change.

Edge cases and limitations

The orchestrator plans far more subtasks than the task needs
Nothing in the pattern stops a model from splitting a simple question into dozens of parts. Anthropic's Research team reports that early versions spawned 50 subagents for simple queries. Their fix was to put effort rules in the orchestrator's prompt: one agent making 3 to 10 tool calls for simple fact-finding, 2 to 4 subagents for direct comparisons, and more than 10 only for complex research. Add the same kind of rule to your prompt and enforce a hard cap in code as well.
The plan has exactly one subtask
When the orchestrator decides that one worker is enough, the run still makes a planning call, a worker call and a synthesis call for work that one call could have done. The worked example shows this for the second task, where three calls ran and nothing was parallel. Let the orchestrator answer directly when no split is needed, or skip synthesis when there is a single result to return.
Workers make choices that do not fit together
Each worker fills the gaps in its brief with its own assumptions, and no worker can see the others. Cognition's essay on the subject uses a game clone as the example: one subagent builds the background and another builds the bird, and the two pieces come back in visual styles that do not match, because each subagent acted on assumptions the other never saw. If parts of a task must agree on a format, an interface or a style, decide that first and write it into every brief, or keep the task in one context.
One slow worker holds up the whole run
If the orchestrator waits for every worker before it continues, the slowest worker sets the pace. Anthropic describes this in its own system: lead agents wait for each set of subagents to finish, cannot steer them in the meantime, and the whole system can be blocked by a single subagent that is still searching. Give each worker a timeout, and decide in advance whether synthesis may proceed with a marked gap.
Worker results refill the context that delegation emptied
Isolation only helps if workers return less than they read. The Claude Code documentation warns that running many subagents that each return detailed results can consume significant context in the main conversation. State a length and a structure in the output format of every brief. For large outputs, have the worker save the result and return a reference to it.
Details change on the way through synthesis
A fact found by a worker is first summarised by that worker and then rewritten by the synthesis step, and each pass can drop a qualifier or a number. Anthropic calls this a game of telephone and lets subagents write some outputs to external storage and pass back lightweight references. When the pieces are sections of one document, joining them in code avoids the second rewrite altogether.

When to use it, and when something simpler is enough

Use it when

  • The subtasks depend on the input, so neither their number nor their content can be written down before the task arrives. Edits across files chosen per request and research with task-specific angles are typical.
  • Each subtask can be completed from a written brief without seeing what the other workers are doing, and the pieces can be combined afterwards.
  • The material is too large for one context, or the tool output of each part would crowd out the rest, and a short summary from each worker is enough for the final answer.
  • The task is valuable enough to pay for several times the tokens of a single agent, and shorter elapsed time or broader coverage is worth that price.

Think twice when

  • The same subtasks apply to every input. Write them down once and use fixed parallelization, which is cheaper and easier to test.
  • Ordinary code can compute the list, such as one call per search hit with an identical instruction. That is a parallel map and needs no planning call.
  • The parts depend on each other's decisions, as when two components must agree on an interface that has not been designed yet. Keep such work in one context or do it in sequence.
  • Latency or cost is tight. The minimum is three calls, and the planning and synthesis calls add delay before and after the workers.
  • Workers would take irreversible actions that could collide, such as two workers editing the same file or issuing the same refund.

A simpler alternative. Start with one model call that receives the whole task, or with fixed sectioning when you can list the parts yourself. A single agent with tools is the next step up. These stop being enough when you keep adding prompts for cases the fixed list missed, when most inputs pay for sections they do not need, or when one agent's context fills with tool output before the task is done.

Key takeaways

  • In orchestrator-workers, one model call decides the subtasks for the input in front of it, separate worker calls carry them out, and a final step combines their results.
  • The pattern differs from fixed parallelization in one respect that drives all the others: the list of subtasks is produced by a model at run time and is not written in your code beforehand.
  • A worker knows only what its brief says, so every brief needs an objective, an output format, guidance on tools and sources, and clear boundaries.
  • The plan is untrusted structured output, so validate it, cap the number of subtasks and concurrent workers, and handle the failure of each worker separately.
  • The pattern keeps every context small and shortens elapsed time, but it uses more tokens in total, so it suits valuable tasks with independent parts.
  • When the subtasks are always the same, can be computed by code, or depend on each other's decisions, a simpler pattern or a single agent is the better choice.

Example 1 of 5

Claude's Research feature, where a lead agent delegates searches to parallel subagents

AnthropicDocumented in an engineering article

Claude's Research feature searches the web, Google Workspace and connected integrations to answer complex questions. Anthropic's engineering article How we built our multi-agent research system (June 2025) describes its architecture and the lessons from taking it to production. [2]

The problem

Research questions are open-ended. The steps cannot be predicted in advance, and each finding changes what to look for next. A single agent searching step by step is slow on questions that fan out in many independent directions, and the material it gathers can exceed one context window. The article's example is a request to identify the board members of every company in the information technology sector of the S&P 500, which a single-agent system failed to answer with slow, sequential searches.

Where this topic fits

The lead agent is the orchestrator. It analyses the query, plans, and creates subagents, which are the workers. Each subagent runs its own search loop in a separate context window and returns condensed findings. The lead agent synthesizes them and decides whether another round is needed. After the research loop, a separate citation agent attaches sources to the claims in the report. This is the agentic variant of the pattern, because the orchestrator is itself an agent that can delegate more than once.

How it is applied, step by step

  1. A user submits a query. The lead agent thinks through an approach and saves its plan to memory, so that the plan survives if its context window is truncated.
  2. The lead agent decides how many subagents the query deserves, guided by effort rules written into its prompt, and creates them with specific research tasks.
  3. Each brief states an objective, an output format, guidance on tools and sources, and the boundaries of the subtask.
  4. The subagents run at the same time. Each one searches, evaluates what came back and refines its next query, and all of that stays inside its own context window.
  5. Each subagent returns its findings to the lead agent, which synthesizes them and decides whether more research is needed. If it is, the lead agent creates further subagents or changes its strategy.
  6. When enough has been gathered, the findings go to a citation agent that locates the passages supporting each claim, and the cited report is returned to the user.

Why this approach fits

The questions that benefit most are breadth-first: many directions that do not depend on each other. That is the condition under which workers can run without seeing each other's work. Search also produces far more text than the final answer needs, so having each subagent condense its findings before reporting keeps the lead agent's context free for planning and synthesis. The article's own explanation is blunter: the architecture works mainly because it lets the system spend enough tokens on the problem, spread across several context windows.

Limitation or tradeoff

The token bill is large, and the article says the approach is economically viable only where the value of the task justifies it. The lead agent runs subagents synchronously, so it cannot steer them while they work, and one slow subagent can hold up the round. The authors also state that the approach suits research better than work whose parts share context or depend on each other, and they give most coding tasks as an example. The 90.2% figure comes from Anthropic's internal evaluation and has not been reproduced independently.

What the sources document

  • The Research system uses a multi-agent architecture with an orchestrator-worker pattern, in which a lead agent coordinates the process and delegates to specialised subagents that operate in parallel. [2]
  • On Anthropic's internal research evaluation, a multi-agent system with Claude Opus 4 as the lead agent and Claude Sonnet 4 subagents outperformed single-agent Claude Opus 4 by 90.2%. [2]
  • In Anthropic's data, agents typically use about 4 times more tokens than chat interactions, and multi-agent systems use about 15 times more tokens than chats. [2]
  • Each subagent needs an objective, an output format, guidance on the tools and sources to use, and clear task boundaries. With short, vague instructions, subagents misinterpreted the task or performed the same searches as other agents. [2]
  • Lead agents execute subagents synchronously and wait for each set to complete. The article states that the lead agent cannot steer subagents and that the whole system can be blocked while waiting for a single subagent to finish searching. [2]

The facts above come from the cited sources. The steps and analysis in this example are our explanation of how they fit together.

Example 2 of 5

Claude Code delegating side tasks to subagents that have their own context windows

AnthropicDocumented in official docs

Claude Code is Anthropic's coding agent. Its documentation page Create custom subagents describes how the main conversation delegates work to subagents, what a subagent can see when it starts, and the limits on spawning them. [7]

The problem

A coding session produces a lot of text that is needed once and never again: search results from across a codebase, test logs, the contents of files that turned out to be irrelevant. If all of it lands in the main conversation, the context fills with material that crowds out the code under discussion. The documentation presents subagents as the answer for side tasks that would otherwise flood the main conversation with output the user will not refer to again.

Where this topic fits

The main conversation plays the orchestrator. When a task matches a subagent's description, Claude delegates through a tool call (the Agent tool, which was named Task before version 2.1.63). The subagent is the worker. It starts from a fresh context, does the task with its own tools and returns a result to the main conversation, which continues with only that result. For independent investigations several subagents can run at once, and Claude then synthesizes their findings.

How it is applied, step by step

  1. A set of subagents is available: built-in ones such as the read-only Explore agent, and custom ones defined as Markdown files with a name, a description, an optional tool list and an optional model.
  2. While working, Claude compares the task at hand with each subagent's description and decides whether to delegate. The user's request does not have to name a subagent.
  3. Claude writes a delegation message that summarises the task, and Claude Code starts the subagent with its own system prompt and that message. The subagent does not receive the conversation history or the files Claude has already read.
  4. The subagent works through its own loop of tool calls, limited to the tools its definition allows and, if so configured, running on a lower-cost model.
  5. The subagent's result returns to the main conversation. Its searches, logs and intermediate reasoning stay behind in its own context.
  6. For independent questions, Claude can start several subagents at the same time and combine what they report. Claude Code caps running subagents at 20 by default and nesting at three layers below the main conversation.

Why this approach fits

Which side tasks come up in a coding session depends on the request and on what the code turns out to contain, so the delegations cannot be scheduled in advance. The model decides them as it works, which is the defining feature of the pattern. The benefit here is context more than speed. The verbose part of a subtask happens somewhere else, and the main conversation pays only for the summary. Tool restrictions add a safety benefit, since a research worker can be denied the ability to edit files.

Limitation or tradeoff

A subagent that starts fresh has to rebuild context the main conversation already had, which adds latency and makes the delegation message a single point of failure. The documentation recommends staying in the main conversation when phases of work share significant context, when the task needs frequent back-and-forth, or when latency matters. Each subagent also sends its own requests, which count toward the same usage limits, and many detailed results returning at once can use up the context that delegation was meant to protect.

What the sources document

  • Each subagent runs in its own context window with a custom system prompt, specific tool access and independent permissions, and Claude delegates to a subagent when it encounters a task that matches the subagent's description. [7]
  • A subagent starts with a fresh, isolated context window. It does not see the conversation history, the skills already invoked or the files Claude has already read, and Claude composes a delegation message that summarises the task. [7]
  • For independent investigations, multiple subagents can be spawned to work simultaneously. Each explores its area independently and Claude synthesizes the findings, which the page says works best when the research paths do not depend on each other. [7]

Cursor's planners and workers building large codebases with hundreds of concurrent agents

CursorDocumented in an engineering article

Cursor, the company behind the Cursor code editor, published a research post in January 2026, Scaling long-running autonomous coding, about running hundreds of coding agents on one project for weeks. The post describes the coordination designs that failed and the planner and worker design that replaced them. [8]

The problem

One agent is slow on a project the size of a web browser, so the team ran many agents in parallel. Their first design gave every agent equal status and let the agents coordinate through a shared file with locks. The post reports that agents held locks too long or forgot to release them, that twenty agents slowed to the throughput of two or three, and that with no hierarchy the agents avoided hard tasks and made small, safe changes.

Where this topic fits

The planner is the orchestrator and the workers are the workers, with two differences from the textbook form. Planning is recursive, since a planner can create sub-planners for parts of the codebase. And there is no synthesis model. Workers push their changes to a shared branch, which is where results meet, and a judge agent decides at the end of each cycle whether to continue.

How it is applied, step by step

  1. Planners explore the codebase continuously and turn what they find into tasks. They do not implement the tasks themselves.
  2. For a specific area of the project a planner can spawn a sub-planner, so planning itself runs in parallel and at more than one level.
  3. Workers pick up tasks. Each worker concentrates on one task, does not coordinate with other workers and does not track the overall goal.
  4. A worker that finishes pushes its changes. Hundreds of workers push to the same branch, and the workers handle conflicts themselves.
  5. At the end of a cycle a judge agent determines whether to continue, and the next iteration starts fresh.

Why this approach fits

In a codebase of this size the useful tasks are not known at the start. They are discovered by reading the code as it grows, and that is planning which only a model looking at the current state can do. Separating that job from implementation gave each task a single owner, which the flat design lacked. Workers that ignore the overall goal are also cheap to add. A new worker needs a task, not an understanding of what hundreds of other agents are doing.

Limitation or tradeoff

The post is candid that the system is not efficient. It used trillions of tokens, agents sometimes run for far too long, and periodic fresh starts are still needed to counter drift. Planners do not yet wake up when their tasks complete, so feedback from results to planning is weak. Because results meet in a git branch and no model reconciles them, correctness rests on tests and review, and the post says of its own framework migration that the result still needs careful review. These are research experiments. The post says only that the techniques will eventually inform the product.

What the sources document

  • In the first design, agents had equal status and coordinated through a shared file with locking. The post reports that twenty agents slowed to the effective throughput of two or three, and that without hierarchy agents became risk-averse and avoided difficult tasks. [8]
  • In the replacement design, planners continuously explore the codebase and create tasks and can spawn sub-planners for specific areas. Workers pick up tasks and complete them without coordinating with other workers. A judge agent determines at the end of each cycle whether to continue. [8]
  • To test the system the team had agents build a web browser from scratch. The agents ran for close to a week and wrote over 1 million lines of code across 1,000 files, with hundreds of workers running concurrently and pushing to the same branch. [8]
  • The team built an integrator role for quality control and conflict resolution and then found that it created more bottlenecks than it solved, because workers were already able to handle conflicts. [8]
  • The post states that different models excel at different roles and that the team now uses the model best suited to each role instead of one universal model. [8]

Example 4 of 5

Magentic-One: an orchestrator that directs four specialist agents using two ledgers

Microsoft ResearchDocumented in a paper

Magentic-One is an open-source generalist multi-agent system from Microsoft Research, built on AutoGen and described in a November 2024 paper. An Orchestrator agent directs four specialised agents to complete web and file-based tasks, and the paper evaluates the system on the GAIA, AssistantBench and WebArena benchmarks. [9]

The problem

The benchmark tasks are ad hoc and multi-step. One may need a web search, then a file to be read, then a calculation, and the order is not known until the task is under way. The paper's example from GAIA asks which two cities where United States presidents were born are farthest apart from west to east, a question that takes web navigation, coding and reasoning. A system for such tasks has to choose a capability for each step, notice when it is stuck and change its plan.

Where this topic fits

The Orchestrator is the central LLM. The workers are a fixed roster: WebSurfer drives a browser, FileSurfer reads files, Coder writes programs and ComputerTerminal runs them. The Orchestrator decomposes the task, then repeatedly chooses which agent acts next and writes its instruction. This is the fixed-roster variant. The subtasks and their order are decided at run time, but the set of workers is not, and one worker acts at a time.

How it is applied, step by step

  1. On receiving a task, the Orchestrator writes a task ledger: facts that are given or verified, facts to look up, facts to derive, and educated guesses.
  2. Using the description of each team member, it drafts a step-by-step plan in natural language that assigns steps to agents. Creating and revising the ledger and plan is the outer loop.
  3. In the inner loop, the Orchestrator fills in a progress ledger by answering five questions: whether the task is complete, whether the team is looping, whether progress is being made, which agent should act next, and what instruction to give it.
  4. The chosen agent carries out the instruction and reports back, and the Orchestrator runs the inner loop again.
  5. A counter tracks stalls. When it passes a threshold, which was 2 in the paper's experiments, the Orchestrator leaves the inner loop, reflects on what went wrong, updates the task ledger and revises the plan. The agents' contexts are cleared after each plan update.
  6. When the task is judged complete, or a limit on time or attempts is reached, the Orchestrator reviews the transcript and the ledger and reports a final answer or its best guess.

Why this approach fits

The tasks vary in which capability each step needs, so a fixed pipeline of browser, then files, then code would fit few of them. Keeping the decision in one place, with the two ledgers as structured working memory, lets the system notice a stall and plan again, which agents simply taking turns would not do. The ablation in the paper supports the view that the orchestration logic carries much of the value.

Limitation or tradeoff

Only one agent acts at a time, so this variant gains no speed from parallelism, and the Orchestrator makes a model call on every step to update the progress ledger. The reported completion rates, all at or below 38% with 2024 models, mean that most benchmark tasks were still failed. The paper's error analysis found agents repeating unproductive actions, and its section on risks describes agents retrying a login until the account was suspended and then trying to reset the password. An orchestrator that can direct tools needs limits on what those tools may do.

What the sources document

  • The team consists of five agents: an Orchestrator and four specialised agents named WebSurfer, FileSurfer, Coder and ComputerTerminal. The Orchestrator plans, tracks progress and re-plans to recover from errors. [9]
  • The workflow has two loops. The outer loop maintains a task ledger containing facts, guesses and the plan. The inner loop maintains a progress ledger, for which the Orchestrator answers five questions including which agent should speak next and what instruction to give it. [9]
  • The Orchestrator keeps a counter of stalls. When it exceeds a threshold (2 in the experiments), the Orchestrator breaks out of the inner loop, reflects, updates the task ledger and revises the plan. All agents clear their contexts after each plan update. [9]
  • The paper reports task-completion rates of 38% on GAIA and 32.8% on WebArena and an accuracy of 27.7% on AssistantBench, which it describes as statistically competitive with state-of-the-art systems. [9]

4Common mistakes

  1. Using an orchestrator when the list of subtasks never changes.

    Why it causes problems
    Every run pays for a planning call that reproduces the same list, and for a synthesis call the task may not need. The plan also becomes a new source of variation, because a model can drop or reword a subtask that fixed code would always have run.
    How to recognise it
    Log the plans from a few dozen runs. If they contain the same subtasks each time, apart from wording, the orchestrator is not deciding anything.
    How to fix it
    Write the subtasks into code and use fixed parallelization. Keep the orchestrator for inputs where the number or kind of subtask really varies.

  2. Delegating with a brief of a few words.

    Why it causes problems
    The worker cannot see the conversation, so it fills the gaps with guesses. Anthropic's Research team saw subagents misread vague tasks and repeat each other's searches, which wastes whole worker runs and leaves parts of the question uncovered.
    How to recognise it
    Compare the workers' results. Overlapping findings, near-identical search queries from different workers, and results in formats that cannot be combined all point to thin briefs.
    How to fix it
    Require an objective, an output format, guidance on tools and sources, and boundaries in every brief. Test a brief by reading it with nothing else in front of you and asking whether you could do the job.

  3. Running whatever plan the orchestrator returns.

    Why it causes problems
    A plan with fifty subtasks, duplicated targets or missing fields is executed as written. The cost of a run is then set by a model's worst output instead of by a limit you chose.
    How to recognise it
    Look for a wide spread in cost per run for similar inputs, for runs with far more workers than the task warranted, and for code that loops over the plan without checking it first.
    How to fix it
    Parse the plan against a schema, cap the number of subtasks and of concurrent workers, reject overlapping subtasks, and ask for a new plan once before giving up.

  4. Splitting work whose parts have to agree with each other.

    Why it causes problems
    Workers cannot see each other's choices, so each one settles shared questions its own way. The synthesis step is left reconciling outputs that were built on conflicting assumptions, which is harder than doing the work once in a single context.
    How to recognise it
    The synthesis step spends its effort resolving contradictions, or the pieces fail when put together: mismatched field names, two styles in one document, an interface one side does not implement.
    How to fix it
    Make the shared decisions first and write them into every brief, or keep dependent work in one context and delegate only the parts that are truly independent.

  5. Letting one failed worker fail the whole run, or vanish from the answer without notice.

    Why it causes problems
    If an exception in one worker propagates, the results of the others are thrown away. If it is swallowed, the final answer silently lacks a part and reads as complete.
    How to recognise it
    Force one worker to time out in a test. Either the run crashes, or the answer comes back with no sign that anything is missing.
    How to fix it
    Give each worker its own timeout, retry and error capture. Return a status that distinguishes complete from partial, and have code, not the synthesis model, list the subtasks that were not done.

  6. Returning each worker's full transcript to the orchestrator.

    Why it causes problems
    The orchestrator's context then grows by the full size of every subtask, so the isolation the pattern exists to provide is lost, and each later orchestrator call pays for all of it again.
    How to recognise it
    The orchestrator's input tokens jump after the workers return, by roughly the sum of what the workers read.
    How to fix it
    Put a length and a structure in the output format of every brief. For large outputs, have workers save them outside the conversation and return a short reference.

Make the fan-out survive failed workers and report what was not done

CodingIntermediateAbout 40 min (estimate)Hypothetical scenario

Start from orchestrator_workers.py in the worked example. In that script an exception in one worker call ends the whole run. Real worker calls time out and fail, so make the fan-out survive them.

Create resilient.py next to it and begin with this code, which wraps the stand-in model so that chosen worker calls fail:

python
import json
from concurrent.futures import ThreadPoolExecutor

import orchestrator_workers as base

FAILURES = {}  # file -> how many worker calls for it should fail before one succeeds


def flaky_model(role, prompt):
    if role == "work":
        name = json.loads(prompt)["file"]
        if FAILURES.get(name, 0) > 0:
            FAILURES[name] -= 1
            base.calls.append((role, len(prompt)))  # a failed call still costs a call
            raise TimeoutError("worker timed out")
    return base.model(role, prompt)

Write a new orchestrate(task) in resilient.py that uses flaky_model for every call and reuses base.plan_prompt, base.validate and base.brief. Test it with the task "Rename the --out flag to --output-dir" and these four settings of FAILURES:

  • {}
  • {"docs/ci.md": 1}
  • {"CHANGELOG.md": 9}
  • {"README.md": 9, "docs/ci.md": 9, "CHANGELOG.md": 9}

You need only the Python standard library.

Requirements

  • A worker call that raises is retried once. If the retry also raises, that worker is recorded as failed and the other workers are unaffected.
  • The synthesis call receives only the results of workers that succeeded.
  • The returned dictionary has four keys: status (complete, partial or failed), failed (the files whose workers failed, in plan order), calls (every model call made, including failed attempts) and report.
  • When some workers failed, the report ends with the text NOT DONE followed by the failed files. Code adds this text; it is not left to the synthesis model.
  • When every worker failed, no synthesis call is made, status is failed and report is None.

Expected behaviour

The four settings print, in order:

text
no failures {'status': 'complete', 'failed': [], 'calls': 5, 'report': '3 file(s) updated. README.md: 1 replacement; docs/ci.md: 2 replacements; CHANGELOG.md: added a 1.4 entry, 1.3 untouched'}
one timeout {'status': 'complete', 'failed': [], 'calls': 6, 'report': '3 file(s) updated. README.md: 1 replacement; docs/ci.md: 2 replacements; CHANGELOG.md: added a 1.4 entry, 1.3 untouched'}

Hint 1

Wrap one worker in a function that always returns a small dictionary with the keys file, ok and text and never raises. Then pool.map always completes.

Hint 2

A for loop over range(retries + 1) with a try and except inside covers the first attempt and the retry.

Hint 3

Count the calls from base.calls after the run. The flaky_model function records failed attempts there as well.

Show solution

Add this below the starting code in resilient.py:

python
def run_worker(subtask, retries=1):
    prompt = base.brief(subtask)
    error = None
    for _ in range(retries + 1):
        try:
            return {"file": subtask["file"], "ok": True, "text": flaky_model("work", prompt)}
        except Exception as caught:  # one worker's failure must not end the run
            error = caught
    return {"file": subtask["file"], "ok": False, "text": f"FAILED ({error})"}


def orchestrate(task):
    base.calls.clear()
    subtasks = base.validate(json.loads(flaky_model("plan", base.plan_prompt(task))))
    with ThreadPoolExecutor(max_workers=base.MAX_SUBTASKS) as pool:
        outcomes = list(pool.map(run_worker, subtasks))
    done = [outcome["text"] for outcome in outcomes if outcome["ok"]]
    failed = [outcome["file"] for outcome in outcomes if not outcome["ok"]]
    if not done:
        return {"status": "failed", "failed": failed, "calls": len(base.calls), "report": None}
    report = flaky_model("synthesize", json.dumps({"task": task, "results": done}))
    if failed:
        report += ". NOT DONE: " + ", ".join(failed)
    return {"status": "partial" if failed else "complete", "failed": failed,
            "calls": len(base.calls), "report": report}


if __name__ == "__main__":
    TASK = "Rename the --out flag to --output-dir"
    for label, failures in [("no failures", {}),
                            ("one timeout", {"docs/ci.md": 1}),
                            ("dead worker", {"CHANGELOG.md": 9}),
                            ("all dead", {"README.md": 9, "docs/ci.md": 9, "CHANGELOG.md": 9})]:
        FAILURES.clear()
        FAILURES.update(failures)
        print(label, orchestrate(TASK))

Why it is built this way:

  • The worker wrapper never raises. pool.map re-raises a worker's exception when you read its result, which would discard the other workers' results. Returning a dictionary with an ok flag turns a failure into data.
  • The call count explains itself. With no failures there are 1 + 3 + 1 = 5 calls. One timeout adds a retry, giving 6. A dead worker makes two attempts, so the count is 1 + (1 + 1 + 2) + 1 = 6. When all three are dead there are 1 + 6 = 7 calls and no synthesis call.
  • Code reports the gap. The synthesis model sees only the two successful results, so it cannot claim the third. The NOT DONE text is appended by code, which means a caller can rely on it being present whenever the status is partial.
  • Three statuses. A caller can now tell a full answer from a partial one and from no answer, which the original script could not do.

In a live system you would also give each worker call a timeout, and retry only errors that can succeed on a second attempt, such as timeouts and rate limits.

What the numbers say:

  • The fixed overhead of planning and synthesis is about 3 cents. Almost all of the money is in the workers, at about 12 cents each, so the cap on N is the cost control.
  • The cap belongs in two places. State it in the orchestrator's prompt so that the plan spends its budget on the most useful subtasks, and enforce it in the code that validates the plan.
  • Concurrency cut the elapsed time for ten workers from 414 seconds to 94 without changing the cost. Raising the concurrency limit to 10 would bring it to 54 seconds, if the provider's rate limits allow ten workers at once.

Check your answer

  • Did you choose a parallel map, and not orchestrator-workers, for the 40 files that all get the same change?
  • Is your cost formula 0.033 + 0.117 N dollars, giving 0.384 for N = 3 and 1.203 for N = 10?
  • Is your cap 8 workers, and did you check that 9 workers would exceed one dollar?
  • Did you get 54 seconds, 94 seconds and 414 seconds for the three timing questions?
