System Design Fundamentals

System design is the practice of choosing and sizing the building blocks around an application (load balancers, caches, queues, database replicas and partitions) so that it handles a stated workload, keeps working when a machine fails, and gives each reader data that is fresh enough for its purpose.

1Overview

Why it matters

A prototype that runs on one server and one database meets its first real test when a customer describes the production workload: a million parcels a day, a morning peak, a notification that must go out within five minutes. Whether the system survives that depends on a small number of decisions. Can more servers be added behind one address? Which reads may be answered from memory, and how old may that answer be? What happens to slow work when it arrives faster than it can be done? How many copies of the data exist, and what does a reader see while they disagree?

Getting these wrong produces the outages that engineering teams write about afterwards: a queue that fills memory and locks up, a cache restart that sends every read to the database at once, a table that grows until routine maintenance stops working. A forward deployed engineer also has to answer the plainer question a customer asks in the first design review, which is how many machines this needs and why. This lesson gives you the vocabulary for the five standard building blocks and the arithmetic to size them.

Key terms

Load balancer
A component that receives every incoming request and forwards each one to one of several identical servers, skipping servers that fail its health checks.
Stateless server
A server that keeps nothing between requests that another server would need, so any server can handle any request. Sessions and files live in a database, cache or object store instead.
Cache hit ratio
The fraction of reads answered from the cache. With a hit ratio of 0.9, only one read in ten reaches the database.
Time to live (TTL)
The number of seconds a cached entry is kept before it expires and must be fetched again. It is an upper bound on how stale that entry can become.
Message queue
A store that holds units of work, called messages or jobs, until a worker process takes them. It lets the part that creates work and the part that does it run at different speeds.
Idempotent
Describes an operation that gives the same result whether it runs once or several times, such as setting a status to delivered. Queue consumers need this because a job can be delivered twice.
Replication
Keeping copies of the same data on more than one machine, so that one machine can fail without losing data and reads can be spread across the copies.
Partitioning (sharding)
Splitting a dataset so that each row lives in exactly one partition, chosen by a partition key. It is usually called sharding when the partitions sit on different database servers.
Eventual consistency
A guarantee that all copies of a piece of data will agree once updates stop arriving, with no promise about what a read returns in the meantime.
Peak factor
The busiest period's request rate divided by the daily average rate. Capacity is sized for the peak, so this single number can multiply the hardware a design needs.

2Explanation

Introduction

In REST APIs and System Integration you built a service that answers HTTP requests, and in SQL and Relational Databases you stored its data in one database. One application server talking to one database is where almost every system starts, and it is a good place to start. System design is what you do when a number says it is no longer enough.

Think of a small post office with one clerk and one ledger. When the line gets long you open more counters and put someone at the door to send each customer to a free one (a load balancer). The clerks keep answering the same questions, so you pin the answers on a board (a cache). Parcels that take ten minutes to wrap go into a tray for the back room (a queue). A second clerk keeps an identical copy of the ledger in case the first is lost (replication), and when the ledger gets too thick to handle it is split into volumes A to M and N to Z (partitioning).

Each building block relieves one specific pressure:

The same data is read again and againCacheAnswers from memory instead of the database

The database machine can fail, or reads overload itReplicationSeveral copies of the same data
Data or writes outgrow one machinePartitioningEach machine holds one slice of the data

None of these is free. Each adds a component that can fail, and three of them (caches, replicas and partitions) put the same fact in more than one place, so two readers can briefly get different answers. That is the consistency tradeoff, and deciding where it is acceptable is a large part of the design work.

The way to decide is arithmetic. Before drawing boxes, turn the customer's description of the workload into requests per second, gigabytes and jobs per second. The sections below explain how each block works and what it costs, then show how to do the estimate, with a complete one for a parcel-tracking service.

How it works

Load balancing: many servers behind one address

A load balancer forwards each request to one of several identical servers. This only works when the servers are stateless, so that it does not matter which one answers. Two settings define its behaviour.

  • How it picks a server. NGINX documents three methods (opens in a new tab): round-robin (the default, each server in turn), least-connected (the server with the fewest active connections) and ip-hash (a hash of the client address, so one client keeps reaching the same server).
  • How it notices a dead server. NGINX counts failed attempts. After max_fails of them (1 by default) it stops sending traffic to that server for fail_timeout, then probes it again with live requests.
nginx
# inside the http block of nginx.conf
upstream api {
    least_conn;
    server app1.internal:8000 max_fails=2 fail_timeout=10s;
    server app2.internal:8000 max_fails=2 fail_timeout=10s;
    server app3.internal:8000 backup;   # used only when the others are down
}

A layer 4 load balancer forwards TCP connections without reading them. A layer 7 one, like the NGINX example, reads the HTTP request, so it can route by host or path. An even spread is not guaranteed: Google's SRE book reports that simple round robin left up to a 2x spread in CPU use (opens in a new tab) between the least and most loaded tasks, because requests differ in cost and machines differ in speed.

Caching: answer repeated reads from memory

A cache keeps copies of results in memory under a key such as parcel:8841. The standard pattern, which AWS calls lazy loading (opens in a new tab), is:

  1. Ask the cache. On a hit, return the value.
  2. On a miss, query the database.
  3. Write the result to the cache, then return it.

With hit ratio hhh, the database receives only the fraction 1−h1 - h1−h of reads. The price is stale data, because nothing updates the cached copy when the database changes. There are three controls. A TTL expires each entry after a fixed number of seconds, which bounds staleness. Invalidation deletes the key when the row is written. Write-through updates the cache on every write, which keeps it fresh but fills it with data nobody may read. The same AWS page suggests adding a TTL to either strategy.

A cache has a memory limit, and when it is full it must evict entries. Redis recommends the allkeys-lru policy (opens in a new tab), which evicts the least recently used keys, as a good default. Plan for the empty cache too: after a restart the hit ratio is zero and every read reaches the database.

Queues: store slow work and do it later

A queue holds jobs until a worker takes them. The API can answer as soon as the job is stored, and workers process at their own steady rate while arrivals come in bursts.

Delivery is normally at least once. In Amazon SQS (opens in a new tab) a received message stays in the queue but is hidden for a visibility timeout (30 seconds by default). The worker deletes it after finishing. If the worker crashes first, the message reappears and another worker gets it. The same job can therefore run twice, so handlers must be idempotent. Route a message that keeps failing to a dead-letter queue, where it can be inspected without blocking the rest.

A queue adds time, not capacity. If jobs arrive at λ\lambdaλ per second and workers finish ccc per second, the backlog grows by λ−c\lambda - cλ−c every second while λ>c\lambda > cλ>c, and afterwards it drains only at the spare rate. Amazon engineers call this bimodal behaviour (opens in a new tab): fast with no backlog, and slower and slower once one forms. Monitor the age of the oldest message.

Replication: more than one copy

PostgreSQL uses leader-based replication: one primary accepts writes and streams them to standbys. The documentation (opens in a new tab) describes two modes.

  • Asynchronous (the default). The primary confirms a commit before the standbys have it. Commits are fast, but a read from a standby can miss recent changes, and if the primary crashes, the commits that had not yet been shipped are lost.
  • Synchronous. A commit waits until a standby has written it to disk. Nothing confirmed is lost, but every commit costs at least a network round trip, and commits wait if no synchronous standby answers. synchronous_standby_names = 'ANY 1 (s1, s2)' waits for either of two standbys.

Partitioning: split what outgrows one machine

Replication copies all the data to every machine. Partitioning splits it, and a partition key decides where each row goes. PostgreSQL offers (opens in a new tab) range, list and hash partitioning inside one server.

MethodRows are placed byGood forWatch for
RangeKey ranges, such as one monthTime-ordered data; old data is removed by dropping a partitionAll new writes land in the newest partition
HashA hash of the key, such as a customer IDAn even spread of rows and loadA scan across many keys touches every partition

The PostgreSQL advice is to partition by the column that appears most often in WHERE clauses, because the planner can then skip (prune) partitions that cannot match. A query without the key must visit them all. When partitions sit on different servers, joins and transactions across them become slow or impossible, so pick a key, such as a tenant ID, that keeps one request inside one partition.

How keys map to servers matters when servers are added. With hash(key) mod n, changing nnn moves most keys. Consistent hashing, described in Amazon's Dynamo paper (opens in a new tab), places servers and keys on a ring so that a new server takes over only its neighbours' share. Exercise 2 measures the difference.

Consistency tradeoffs

As soon as data lives in two places, the copies can disagree for a while. Strong consistency means every read returns the latest confirmed write, as if there were one copy. Eventual consistency means the copies converge, and a read in between may return older data.

The CAP theorem states the limit. When a network fault separates the copies, a system must either refuse some requests to stay consistent, or answer from a copy that may be out of date to stay available. Eric Brewer (opens in a new tab), who proposed it, stresses that the decision is made at a timeout and can differ per operation. In one system, a payment can refuse to proceed while a like counter accepts a slightly old value.

Leaderless stores expose the choice as three numbers. Each key has NNN copies, a write waits for WWW acknowledgements, and a read asks RRR copies. When R+W>NR + W > NR+W>N, the copies a read asks always include at least one that took the latest write.

Between the two extremes sit weaker guarantees, which Jepsen's map of consistency models (opens in a new tab) orders by strength. Often it is enough that a user sees their own change (read your writes), which you can get by reading from the primary for a few seconds after that user writes. DynamoDB (opens in a new tab) makes the choice per request: reads are eventually consistent by default and cost half as much as a strongly consistent read requested with ConsistentRead.

Estimating capacity

Google's SRE workbook calls this non-abstract design (opens in a new tab): turning a whiteboard sketch into concrete resource estimates at each step. Five calculations cover most customer workloads.

  1. Average rate = events per day ÷ 86,400 seconds.
  2. Peak rate = average rate × peak factor. Ask the customer for an hourly traffic histogram.
  3. Servers = peak rate ÷ (load-tested limit per server × target utilisation), rounded up, plus spares. The SRE book's example is N+2 (opens in a new tab): a peak of 19,000 queries per second on clusters that break at 5,000 needs about six clusters.
  4. Work in flight = rate × duration. AWS Lambda documents the same formula as concurrency (opens in a new tab): 100 requests per second that each take 0.5 seconds mean 50 in flight at once. Use it for worker and connection pools.
  5. Storage = writes per day × bytes per row × days kept × number of copies.

Worked example: Sizing a parcel-tracking service from five facts about the workload

A parcel carrier asks you to size a tracking service for peak season. Discovery gives you these facts:

  • 1,080,000 parcels a day. Each is scanned 6 times (a write) and looked up 20 times (a read).
  • The busiest hour carries 4 times the daily average.
  • A load test shows one app server stays inside the latency target up to 200 requests per second.
  • Every scan triggers one notification job that takes 0.2 seconds of worker time. Notifications should go out within 5 minutes.
  • A scan event row is about 500 bytes and is kept for 13 months (395 days).

Save this as capacity.py and run python3 capacity.py. It uses only the standard library.

python
import math

SECONDS_PER_DAY = 86_400
parcels_per_day = 1_080_000
scans_per_parcel, lookups_per_parcel = 6, 20   # writes and reads per parcel
peak_factor = 4                                 # busiest hour compared with the daily average

avg_writes = parcels_per_day * scans_per_parcel / SECONDS_PER_DAY
avg_reads = parcels_per_day * lookups_per_parcel / SECONDS_PER_DAY
peak_writes, peak_reads = avg_writes * peak_factor, avg_reads * peak_factor
peak_total = peak_writes + peak_reads
print(f"average: {avg_reads:.0f} reads/s, {avg_writes:.0f} writes/s")
print(f"peak:    {peak_reads:.0f} reads/s, {peak_writes:.0f} writes/s, {peak_total:.0f} in total")

# App servers: load-tested limit of 200 requests/s each, run at 60%, plus 2 spares
server_limit, target_utilisation, spares = 200, 0.60, 2
needed = math.ceil(peak_total / (server_limit * target_utilisation))
servers = needed + spares
print(f"app servers: {needed} needed + {spares} spare = {servers}")
print(f"peak utilisation: {peak_total / servers / server_limit:.0%} with all {servers}, "
      f"{peak_total / needed / server_limit:.0%} with {spares} down")

# Cache and database
hit_ratio = 0.90
db_peak = peak_reads * (1 - hit_ratio) + peak_writes
print(f"database at peak: {db_peak:.0f} queries/s with the cache, {peak_total:.0f} with an empty cache")

# Storage
event_bytes, retention_days = 500, 395
gb_per_day = parcels_per_day * scans_per_parcel * event_bytes / 1e9
print(f"storage: {gb_per_day:.2f} GB/day, {gb_per_day * 30:.1f} GB/month, "
      f"{gb_per_day * retention_days:,.0f} GB retained")

# Notification queue: one job per scan, 0.2 s per job, a one-hour peak, a 300 s target
job_seconds, spike_seconds, max_wait = 0.2, 3600, 300
print(f"busy workers: {avg_writes * job_seconds:.0f} on average, {peak_writes * job_seconds:.0f} at peak")
for workers in (30, 45, 56):
    capacity = workers / job_seconds
    backlog = max(0.0, (peak_writes - capacity) * spike_seconds)
    wait = backlog / capacity
    drain = backlog / (capacity - avg_writes)
    print(f"{workers} workers: {capacity:.0f} jobs/s, backlog {backlog:,.0f}, "
          f"longest wait {wait:,.0f} s, drained {drain / 60:.0f} min after the peak")
required = peak_writes * spike_seconds / (spike_seconds + max_wait)
print(f"rate needed for a {max_wait} s wait: {required:.1f} jobs/s = "
      f"{math.ceil(required * job_seconds)} workers")

What the numbers decide:

  • Servers. 1,300 requests per second at 120 usable per server needs 11. Two spares make 13, so the service runs at 59% with one server out for a deploy and another failed.
  • Cache. A 90% hit ratio cuts the database's peak from 1,300 to 400 queries per second. After a cache restart it must still survive 1,300, so load-test the database at that rate.
  • Replication, not sharding. 300 writes per second fits one primary. Two standbys with 'ANY 1 (s1, s2)' keep every confirmed scan through the loss of one machine.
  • Partitioning inside one database. Range-partition the 1,280 GB events table by month (about 97 GB each) and drop the oldest partition monthly.
  • Workers. The average needs 15 and the peak 60. With 30, the peak hour leaves 540,000 jobs waiting and the last is an hour late. The 5-minute target needs 56, close to full peak capacity.

Edge cases and limitations

Least-connections routing can favour a broken server
A server that fails every request immediately always has few open connections, so a policy that picks the least busy server sends it more traffic. Google's SRE book describes this with least-loaded balancing, where an unhealthy task that returns errors quickly attracts requests. Count error responses as failures in the load balancer's health checks, and alert on the error rate of each server, because a fleet-wide average hides one bad machine.
An empty cache moves the whole read load onto the database
A cache with a 90% hit ratio hides nine tenths of the reads from the database. After a restart, a failover to an empty node or a mass expiry, the database receives all of them at once. Facebook's memcache paper describes this risk and keeps a small spare pool, named Gutter, that takes over from failed cache servers. Load-test the database at the no-cache rate, or limit how quickly requests may fall through to it while the cache refills.
A popular key expires and many requests rebuild it at once
When a hot entry is missing, every concurrent request misses and runs the same expensive query. Facebook measured a set of such keys: the peak database query rate was 17K per second without protection, and 1.3K per second once the cache gave out one permission to refill a key every 10 seconds and told other readers to wait and retry. A simple version is a per-key lock around the refill. Adding random jitter to TTLs also stops many entries from expiring in the same second.
A job runs twice because delivery is at least once
The SQS documentation states that, because of at-least-once delivery, a message can be delivered more than once. A message also becomes visible again when the visibility timeout ends before the worker has deleted it, even if that worker is still running. A handler that sends an SMS or charges a card would then do it twice. Record each job ID with its result and skip IDs already recorded, and set the visibility timeout above the longest processing time or extend it with a heartbeat.
One synchronous standby turns its own failure into a write outage
The PostgreSQL documentation warns that a commit waiting for a synchronous standby may never complete if that standby crashes. With a single synchronous standby, the loss of the less important machine blocks every write on the healthy primary. Name at least two candidates, for example ANY 1 (s1, s2), so that either one can acknowledge a commit.
Retries multiply load when the system is already slow
The SRE book gives the arithmetic. If a database is overloaded and the backend, the frontend and the browser code each make 3 retries (4 attempts), one user action can become 4 x 4 x 4 = 64 attempts on the database. Retry at one layer only, use randomised exponential backoff, cap the retries per request, and return an error quickly once the cap is reached.

When to use it, and when something simpler is enough

Use it when

  • Add a load balancer and more servers when the estimated peak rate exceeds what one load-tested server handles at your target utilisation, or when one server failing must not take the service down.
  • Add a cache when the same data is read far more often than it changes and readers can accept an answer that is up to one TTL old.
  • Add a queue when a piece of work takes longer than the request can wait and its result is not needed in the response, such as sending notifications or processing an upload.
  • Add replicas when losing the database machine would breach the availability the customer needs, or when reads that tolerate lag are overloading the primary.
  • Partition when the data volume or write rate exceeds what the largest practical database server handles, and most queries include a key that keeps them inside one partition.

Think twice when

  • The estimate shows one server and one database handle the peak with headroom. Each block adds a component to deploy, monitor and recover.
  • The value must be correct at the moment it is read, such as a balance or remaining stock. Read those from the primary and do not cache them.
  • The caller needs the result in the same response. A queue only moves the wait somewhere less visible.
  • No single key appears in most queries. Sharding such data turns ordinary queries into requests to every shard.

A simpler alternative. One larger database server with good indexes, a standby for failover, and two or three app servers behind a managed load balancer. This goes further than most people expect. Stack Overflow's 2016 architecture post reports 209 million HTTP requests in a day served by 9 primary web servers, 4 SQL Servers and 2 Redis servers. It stops being enough when the capacity estimate exceeds the load-tested limit of the largest machine you can run, or when maintenance on one very large table stops being safe.

Key takeaways

  • Each building block relieves one pressure: load balancers add servers, caches remove repeated reads, queues defer slow work, replicas survive failures and spread reads, and partitions split data that has outgrown one machine.
  • Caches, replicas and partitions put the same fact in more than one place, so decide for each kind of data how stale a read may be and whether a user must see their own writes.
  • A queue buys time and not capacity: a backlog grows at the arrival rate minus the processing rate and drains only at the spare rate afterwards.
  • Queue delivery is at least once, so every consumer must give the same result when the same job runs twice.
  • Size for the peak and not the average, using the load-tested limit per server, a target utilisation and spare servers, and check what the database receives when the cache is empty.
  • Do the capacity arithmetic before choosing blocks, because it often shows that one database with a standby is enough and sharding is not needed.

Example 1 of 5

GLB Director spreading GitHub's edge traffic across proxy servers

GitHubDocumented in an engineering article

GitHub's engineering post GLB: GitHub's open source load balancer (August 2018) describes the layer 4 load balancer that sits at GitHub's network edge in front of its proxy servers. GitHub runs it on its own hardware and released it as open source. [16]

The problem

One public IP address has to be served by many machines, and connections must survive when a load balancer or proxy server is added, removed or fails. The post explains why the two usual approaches fall short. Router-level ECMP alone spreads packets across servers, but when the set of servers changes, connections are rebalanced and some of them break. Adding a tier of LVS directors avoids that at the price of duplicate state: every director has to store a mapping from connection to proxy server, and that state has to be propagated between directors.

Where this topic fits

Load balancing happens in two tiers before any application code runs. Routers spread packets for one IP address across a group of director servers. The directors work at layer 4: they choose a proxy server for each flow and forward the packet without terminating the connection. The proxy tier, which runs software such as HAProxy, terminates TCP and handles HTTP. Replies travel from the proxy straight back to the client.

How it is applied, step by step

  1. Routers spread incoming packets across the directors. A director hashes fields of the packet to pick one row of a forwarding table. Each row names a primary and a secondary proxy server, and every director holds the same table.
  2. The table is built in advance with rendezvous hashing. For each row, every proxy server is hashed together with the row number, the servers are sorted by that hash, and the first two become primary and secondary.
  3. The director wraps the packet in an encapsulation header that also carries the secondary's address and sends it to the primary. It keeps no record of the connection.
  4. On the proxy, a kernel module checks whether the packet belongs to a connection that the local TCP stack knows. If not, it forwards the packet to the secondary. This second chance lets existing connections finish after the table has changed.
  5. A health checker watches every proxy. When one fails, the rows where it is primary have their primary and secondary swapped, so new connections go to the healthy server.
  6. The proxy sends its reply directly to the client, without passing back through the director tier.

Why this approach fits

The design keeps connection state in exactly one place, the proxy that owns the TCP connection, and makes everything in front of it a pure function of the packet and a static table. Any director can therefore handle any packet, and a reshuffle by the routers does not break flows. Rendezvous hashing limits the damage of a change: when a proxy joins, it becomes primary for about one row in N and the previous primary becomes the secondary, which is exactly where second-chance forwarding will look for the old connections.

Limitation or tradeoff

The post states that the design requires no more than one proxy server at a time to be in any state other than active, because each row has only one fallback. A layer 4 balancer also cannot route on anything inside the HTTP request, so a layer 7 proxy tier is still needed behind it. Running this yourself means operating BGP, ECMP and kernel modules. Most customer deployments are better served by a managed cloud load balancer, and the transferable idea is to keep the balancer stateless.

What the sources document

  • GitHub states that it serves tens of thousands of requests every second out of its network edge, operating on its own metal cloud. [16]
  • GLB Director is described as a Layer 4 load balancer that scales a single IP address across a large number of physical machines while attempting to minimise connection disruption during any change in servers. [16]
  • The director tier is completely stateless in terms of TCP flows. It uses a table of 65k rows, each containing a primary and a secondary server, and the order of servers for a row comes from hashing each server together with the row number and sorting by that hash. [16]
  • When a server fails, the primary and secondary entries are swapped wherever that server is primary. The implementation requires that no more than one proxy server at a time is in a state other than active. [16]
  • Packets from the proxy server back to the client do not travel through the director tier, an arrangement the post calls Direct Server Return. [16]

The facts above come from the cited sources. The steps and analysis in this example are our explanation of how they fit together.

Example 2 of 5

Memcache as a look-aside cache in front of Facebook's databases

FacebookDocumented in a paper

The NSDI 2013 paper Scaling Memcache at Facebook, written by Facebook engineers, describes how the company runs memcached servers as a distributed cache between its web servers and its MySQL databases and other backend services. [17]

The problem

The paper starts from a property of the workload: users consume an order of magnitude more content than they create, so the load is dominated by fetching data, and loading one popular page fetches an average of 521 distinct items. Introducing a cache to absorb those reads creates its own problems, which most of the paper is about: values that go stale, bursts of identical database queries when a popular entry is missing, and the load that falls back on the databases when cache servers fail.

Where this topic fits

The cache sits beside the database, not in front of it. A web server asks memcache first and only queries the database on a miss, then fills the cache itself. On a write, the web server updates the database and then deletes the cached key. The database stays the source of truth, and the cache is allowed to drop any entry at any time.

How it is applied, step by step

  1. On a read, the web server requests the key from memcache. On a miss it runs the database query and sets the key to the result, so the cache is filled only with data that was actually requested.
  2. On a write, the web server sends the SQL statement to the database and then sends a delete for the key to memcache. The next reader repopulates it.
  3. Keys are spread across the hundreds of memcached servers in a cluster by consistent hashing in the client library, so a web server knows which cache server to ask.
  4. To stop stale values, a miss returns a lease token to the client. The later set is accepted only if the token is still valid, and a delete that arrives in between invalidates it.
  5. To stop bursts on a hot key, a server issues a token for a given key only once every 10 seconds by default. Other clients are told to wait briefly and retry, by which time the value is usually back.
  6. When a memcached server does not respond, clients retry against a small spare pool called Gutter instead of rehashing its keys onto the remaining servers, which could overload them.

Why this approach fits

A look-aside cache asks nothing of the database except ordinary queries, so it can be scaled separately from storage, which the paper lists as its first lesson. Deleting on write is the safer of the two possible choices. A delete can be repeated or arrive late without storing a wrong value, while two concurrent sets can arrive in the wrong order and leave the older value in place.

Limitation or tradeoff

The cache is never guaranteed to be current. Between the database write and the delete, and for longer across regions, readers can get the old value, and the paper describes extra mechanisms that only reduce the probability of that. Gutter protects the databases at the cost of slightly stale data. Every protection added (leases, spare pools) is another system to operate. Small systems should start with a TTL and delete-on-write before adding any of this.

What the sources document

  • The paper states that users consume an order of magnitude more content than they create, which results in a workload dominated by fetching data and suggests that caching can have significant advantages. [17]
  • Memcache is used as a demand-filled look-aside cache. On a miss the web server retrieves the data from the database and populates the cache. On a write it issues SQL statements to the database and then sends a delete request to memcache, and deletes are chosen over updates because they are idempotent. [17]
  • A lease is a 64-bit token bound to the key a client missed on. By default servers return a token only once every 10 seconds per key. For a set of keys susceptible to thundering herds, the peak database query rate was 17K/s without leases and 1.3K/s with leases. [17]
  • Gutter accounts for approximately 1% of the memcached servers in a cluster. The paper reports that it reduces the rate of client-visible failures by 99% and converts 10% to 25% of failures into hits each day. [17]
  • Loading one of Facebook's popular pages results in an average of 521 distinct items fetched from memcache. [17]

Slack's job queue: a durable Kafka buffer in front of Redis workers

SlackDocumented in an engineering article

The Slack Engineering post Scaling Slack's Job Queue describes the asynchronous job system used for every message post, push notification, URL unfurl, calendar reminder and billing calculation, and how it was redesigned after a production outage. [18][4]

The problem

Web requests hand slow work to a job queue that was originally held in Redis, an in-memory store. The post describes an outage in which contention in the database layer slowed job execution. Redis then reached its configured memory limit and no new jobs could be enqueued. Because dequeuing also needed free memory, the queue stayed locked up after the database recovered and needed extensive manual work to restore. The team also lists structural problems, among them that Redis had little memory headroom and that dequeuing cost more as a queue grew longer.

Where this topic fits

The queue sits between the web application, which produces jobs, and pools of workers that run them. The redesign adds a durable buffer at the front of that path: the web app posts each job to a small service that writes it to Kafka, a relay service moves jobs from Kafka into Redis at a controlled rate, and the existing workers keep taking jobs from Redis as before.

How it is applied, step by step

  1. The web app sends each job over HTTP to Kafkagate, a stateless service whose task is to write the job to a Kafka topic.
  2. Kafka stores jobs on disk and replicates them across brokers, so a backlog consumes disk space instead of the memory of the store the workers depend on.
  3. JQRelay, another stateless service, reads each topic and writes the jobs into Redis, respecting a rate limit that operators can change while it runs.
  4. If Redis is unavailable, the relay retries until it returns. When workers fall behind, operators lower the relay's rate limit or pause it. In both cases the web app keeps enqueuing at full speed and the backlog waits in Kafka.
  5. The rollout wrote jobs to both systems at first, ran the relay in a mode that discarded what it read, compared job counts at each stage, and then moved one job type at a time.

Why this approach fits

The failure was a queue that could not absorb a period in which arrivals exceeded processing, which is the one thing a queue exists to do. A disk-backed log in front fixes that with a small change: producers get a buffer far larger than any memory limit, and the relay's rate limit gives operators a valve between the buffer and the fragile part.

The memory limit deserves a closer look. Redis can evict keys when memory runs out, which suits a cache, but a queue cannot use that because an evicted job is a lost job. Without eviction, Redis documents that commands which add data fail at the limit. That matches the lock-up in the post, although the post does not say how Slack's Redis was configured.

Limitation or tradeoff

The post is open about the tradeoffs. Kafkagate waits only for the lead broker to acknowledge a job and not for the copies, which gives the lowest latency and a small risk of losing jobs if a broker dies before replicating. The design adds a Kafka cluster and two services to operate. It also does not add processing capacity. A sustained shortfall of workers still produces a growing backlog, now on disk, and jobs that wait there for long may no longer be worth running, such as a push notification for a message the user has already read.

What the sources document

  • On its busiest days the system processes over 1.4 billion jobs at a peak rate of 33,000 per second. [18]
  • In the outage described, resource contention in the database layer slowed job execution, Redis reached its maximum configured memory limit and new jobs could not be enqueued. The queue remained locked up after the database contention was resolved and required extensive manual intervention. [18]
  • The team decided to add Kafka in front of Redis rather than replace Redis outright. Kafkagate waits only for the leader to acknowledge a write, which the post says gives the lowest latency but creates a small risk of lost jobs if a broker dies before replicating. [18]
  • Every Kafka topic has 32 partitions, a replication factor of 3 and a retention period of 2 days. In the new system the web app can sustain a high enqueue rate because jobs are written to durable storage, and the rate limits in JQRelay are adjusted to match the dequeue rate or enqueues to Redis are paused. Dynamo: tunable replication for Amazon's always-writable shopping cart

AmazonDocumented in a paper

The SOSP 2007 paper Dynamo: Amazon's Highly Available Key-value Store, published on Werner Vogels' site All Things Distributed, describes the storage system Amazon built for services such as the shopping cart on its e-commerce platform. [19]

The problem

The paper's requirement is that customers can add and remove cart items even amid network and server failures, so the store must always accept writes. Its services are also held to response-time targets measured at the 99.9th percentile, and the paper's example is a response within 300 ms for 99.9% of requests at a peak of 500 requests per second. A replicated store that refuses writes whenever it cannot reach every copy cannot meet either requirement.

Where this topic fits

Three of this lesson's ideas are combined. Partitioning decides which nodes own a key, using consistent hashing. Replication places each key on N nodes. The consistency tradeoff is exposed as two numbers, R and W, that each service sets for itself, and the cost of choosing availability is paid later, when an application has to merge versions that diverged.

How it is applied, step by step

  1. A key is hashed to a position on a ring. Walking clockwise from that position, the first node found owns the key and coordinates requests for it.
  2. Each physical machine is given many positions on the ring, called virtual nodes, so that when a machine leaves or joins, the load is spread across many others.
  3. The coordinator stores the item and replicates it to the next N-1 nodes clockwise, so every key has N copies.
  4. A write returns to the caller once W copies have acknowledged it, and a read returns once R copies have answered. With R + W greater than N the two sets overlap.
  5. If one of the usual N nodes is unreachable, the write goes to the next healthy node with a hint naming the intended owner, and is handed back when that node returns. Writes therefore keep succeeding during failures.
  6. Because writes are accepted on whichever nodes are reachable, two versions of the same cart can exist. The cart service merges the versions it reads and writes the merged cart back.

Why this approach fits

For a shopping cart, the two kinds of error have very different costs. Refusing an add-to-cart loses revenue immediately. Showing a cart that is briefly out of date, or one that has to be merged, is usually invisible. Dynamo lets each service choose its own point between the two, and consistent hashing lets the cluster grow one machine at a time without moving most of the data.

Limitation or tradeoff

The merge is the application's job, and it is not always clean. The paper notes that with its cart merge an added item is never lost but deleted items can resurface. The R + W > N overlap holds only for a strict quorum, and Dynamo's willingness to write to substitute nodes during failures means a read can still miss a recent write. Low values of W also put durability at risk, since a write is reported as successful while it exists on a single node. Data that must never diverge, such as payments or stock counts, needs a store that refuses writes it cannot replicate.

What the sources document

  • The paper says that to achieve its level of availability Dynamo sacrifices consistency under certain failure scenarios, and that a put() call may return to its caller before the update has been applied at all the replicas. [19]
  • Each data item is assigned to a node by hashing its key to a position on the ring and walking clockwise to the first node with a larger position. The coordinator also replicates the keys at the N-1 clockwise successor nodes. [19]
  • Setting R and W such that R + W > N yields a quorum-like system, and the common (N,R,W) configuration used by several instances of Dynamo is (3,2,2). The latency of a get or put is dictated by the slowest of the R or W replicas. [19]
  • With the cart's reconciliation mechanism an add to cart operation is never lost, but deleted items can resurface. [19]
  • In a 24-hour profile of the shopping cart service, 99.94% of requests saw exactly one version, 0.00057% saw 2 versions, 0.00047% saw 3 versions and 0.00009% saw 4 versions. [19]

Notion partitioning its Postgres monolith by workspace ID

NotionDocumented in an engineering article

Notion's engineering post Herding elephants: Lessons learned from sharding Postgres at Notion (October 2021) describes splitting one PostgreSQL database into 480 logical shards on 32 physical databases. A July 2023 follow-up, The Great Re-shard, describes tripling the number of databases. [20][21]

The problem

Notion's data lived in a single Postgres database that the post says had served through five years and four orders of magnitude of growth. The warning signs were operational: the Postgres VACUUM process began to stall consistently, which stopped the database reclaiming disk space, and the team faced the risk of transaction ID wraparound, a safety mechanism in which Postgres stops processing all writes. Engineers were also dealing with frequent database CPU spikes.

Where this topic fits

This is partitioning across servers, done in the application. Every row in the sharded tables carries a workspace ID, the application works out which logical shard that workspace belongs to, and connects to the physical database that holds it. Capacity estimation comes first: stated limits per table and per database determined how many shards and databases were needed.

How it is applied, step by step

  1. Decide what moves together. Notion sharded every table reachable from its block table through foreign keys, so related rows stay in the same shard.
  2. Choose the partition key. Each block belongs to one workspace and users usually query one workspace at a time, so the workspace ID keeps most queries inside one shard.
  3. Set capacity limits and work backwards. With an upper bound of 500 GB per table and 10 TB per physical database, the team chose 480 logical shards spread evenly over 32 databases.
  4. Pick a shard count that divides many ways. 480 allows a move from 32 to 40 to 48 hosts by relocating whole logical shards, without splitting any of them.
  5. Create each logical shard as a separate Postgres schema with its own tables, and do all routing in the application so there is one source of truth for where a workspace lives.
  6. Migrate without losing writes: record every write in an audit log and replay it on the new databases, backfill old data, verify by comparing records and by reading from both systems, then switch over.

Why this approach fits

The partition key matches how the product is used. Almost every request is about one workspace, so almost every query can be answered by one shard and the joins the application relies on keep working. Separating logical shards from physical databases is what makes later growth cheap: the mapping from workspace to logical shard never changes, and adding hosts only changes which host holds which shard.

Limitation or tradeoff

The team lists what it would do differently. It wishes it had sharded earlier, because the strained database ruled out gentler migration methods, and the switch-over took Notion down for five minutes of scheduled maintenance. The estimate also had a shelf life. The follow-up post reports that by 2023 some shards exceeded 90% CPU at peak traffic and the fleet was expanded from 32 to 96 databases. Beyond what the posts say, a workspace key cannot split one very large workspace, and any question that spans workspaces has to ask every shard.

What the sources document

  • The post reports that the Postgres VACUUM process began to stall consistently and that the team faced transaction ID wraparound, described as a safety mechanism in which Postgres would stop processing all writes. [20]
  • Notion decided to shard all tables reachable from the block table via foreign key relationships and used the workspace ID as the partition key, noting that users typically query data within a single workspace at a time, which avoids most cross-shard joins. [20]
  • The team set an upper bound of 500 GB per table and 10 TB per physical database, and chose 480 logical shards evenly distributed across 32 physical databases. [20]
  • The post explains that 480 is divisible by a lot of numbers, which gives flexibility to scale from 32 to 40 to 48 hosts. Its stated lessons include sharding earlier and aiming for a zero-downtime migration; the switch-over took Notion down for five minutes of scheduled maintenance. [20]
  • The 2023 follow-up reports that some shards were exceeding 90% CPU utilisation at peak traffic, and that Notion expanded from 32 to 96 databases, leaving each with 5 logical schemas instead of 15. [21]

4Common mistakes

  1. Sizing servers and workers for the daily average request rate.

    Why it causes problems
    Traffic is never flat. In the worked example the busiest hour is four times the average, so a system sized for 325 requests per second meets 1,300. Servers saturate, response times climb, clients retry, and the retries add to the load that caused the problem.
    How to recognise it
    A design document that states requests per day and never states requests per second at peak, or utilisation graphs that touch 100% at the same hour every day.
    How to fix it
    Ask the customer for an hourly traffic histogram of their busiest day, derive the peak factor, and size against a load-tested limit per server with a target utilisation and spare servers.

  2. Adding a cache without deciding how its entries become fresh again.

    Why it causes problems
    Lazy loading alone never updates an entry after the database changes, so users see old data until something evicts it. Teams then add manual cache flushes, which empty the cache and send the full read load to the database at the worst moment.
    How to recognise it
    Cache writes with no TTL argument, write paths that never touch the matching cache key, and support tickets that say a refresh or a wait fixed the problem.
    How to fix it
    Set a TTL on every entry, delete the key after each database write, and write down the maximum acceptable staleness for each kind of data so that the TTL has a reason.

  3. Treating a queue as extra capacity and leaving it unbounded and unmonitored.

    Why it causes problems
    When arrivals exceed processing for long enough, the backlog consumes the store's memory or disk and the delay grows without limit. Slack's Redis-backed queue reached its memory limit this way and could neither accept nor release jobs.
    How to recognise it
    A queue-depth graph that climbs through every busy period, no alert on the age of the oldest message, and no dead-letter queue.
    How to fix it
    Compute the worker count from the peak rate and the delay you can accept, alert on the age of the oldest message, and decide in advance what happens at a size limit: slow the producers, or drop work that is too old to matter.

  4. Sending a user's next read to a replica immediately after their write.

    Why it causes problems
    With asynchronous replication the replica may not have the change yet, so the user saves a form and sees the old value. They save again, or report data loss, although nothing was lost.
    How to recognise it
    Bug reports that cannot be reproduced on a quiet system, and pages that are correct after a reload a second later.
    How to fix it
    Route a user's reads to the primary for a short window after that user writes, or serve the value just written from the response instead of reading it back. Keep replica reads for data where lag is acceptable.

  5. Sharding before measuring, or on a key that most queries do not carry.

    Why it causes problems
    Every query without the partition key has to ask every shard, joins across shards stop working, and the team now operates many databases. If the estimate was never done, all of that cost may have bought nothing.
    How to recognise it
    Queries with no partition key in the WHERE clause, application code that loops over shards and merges results, and a write rate that one server would have handled.
    How to fix it
    Do the capacity estimate first. Use a larger server, replicas for reads and partitioning inside one database before sharding, and when sharding is needed choose a key, such as a tenant ID, that almost every request already carries.

Show solution
python
import bisect
import hashlib
from collections import Counter


def position(text):
    """Map any string to a stable 64-bit position on the ring."""
    return int.from_bytes(hashlib.md5(text.encode()).digest()[:8], "big")


def modulo_owner(key, nodes):
    return nodes[position(key) % len(nodes)]


def build_ring(nodes, vnodes):
    """Return sorted (position, node) pairs: each node appears vnodes times."""
    return sorted((position(f"{node}#{i}"), node) for node in nodes for i in range(vnodes))


def ring_owner(key, ring):
    """Walk clockwise to the first ring position after the key's position."""
    index = bisect.bisect_right(ring, (position(key), ""))
    return ring[index % len(ring)][1]


def moved(before, after):
    return sum(1 for key in before if before[key] != after[key]) / len(before)


KEYS = [f"parcel:{n}" for n in range(10_000)]
OLD = ["db1", "db2", "db3", "db4"]
NEW = [*OLD, "db5"]

before = {key: modulo_owner(key, OLD) for key in KEYS}
after = {key: modulo_owner(key, NEW) for key in KEYS}
print(f"modulo:        {moved(before, after):.1%} of keys moved")

for vnodes in (1, 100):
    old_ring, new_ring = build_ring(OLD, vnodes), build_ring(NEW, vnodes)
    before = {key: ring_owner(key, old_ring) for key in KEYS}
    after = {key: ring_owner(key, new_ring) for key in KEYS}
    to_new = all(after[key] == "db5" for key in KEYS if before[key] != after[key])
    load = sorted(Counter(after.values()).items())
    print(f"ring, {vnodes:>3} vnodes: {moved(before, after):.1%} moved, all to db5: {to_new}, load {load}")

Why modulo moves 80%. A key stays only if its position gives the same remainder for 4 and for 5. For a random number that happens for 4 residues out of every 20, so about one key in five stays and four in five move. Most of those moves are between old servers and achieve nothing.

Why the ring moves less. Adding db5 inserts new positions on the ring. A key changes owner only if one of those new positions now sits between the key and its old owner, so every move is to db5 and no data shuffles between the old servers.

Why virtual nodes matter. With one position per server the arcs between positions have random lengths, so db5 happened to take 38% of the keys and db4 was left with 253. With 100 positions per server the arcs average out, the new server takes 20.2%, close to the ideal 1/5, and every server holds about 2,000 keys. This is the reason the Dynamo paper assigns each node many points on the ring.

  • Does your program confirm that every key that moved on the ring moved to db5?
  • Can you explain why the ring with a single position per server gave such uneven key counts?
  • If you changed the number of keys to 100,000, would you expect the percentages to change much, and why not?

Chosen for accuracy and usefulness, not search rank. Time figures are estimates.

  • Introducing Non-Abstract Large System Design (opens in a new tab)

    Google (The Site Reliability Workbook, Chapter 12)

    BookIntermediateFreeAbout 1 to 2 hours (estimate)

    What it teaches
    A full capacity-driven design walk-through from Google: requirements, a first design for one machine, then disks, memory and machine counts for a distributed version, with every calculation shown.
    When to use it
    After the worked example here, when you want to practise turning a design sketch into resource numbers on a larger problem.

  • Avoiding insurmountable queue backlogs (opens in a new tab)

    Amazon Web Services (Amazon Builders' Library)

    ArticleIntermediateFreeAbout 30 minutes (estimate)

    What it teaches
    How queue-based systems behave once a backlog forms, how to measure them (the age of each message when it is dequeued, dead-letter rates) and techniques Amazon uses to recover, such as moving old messages to a separate backlog queue.
    When to use it
    Before you put a queue into a customer design, and again when a queue you operate starts to fall behind.

  • Caching strategies for Memcached (opens in a new tab)

    Amazon Web Services (Amazon ElastiCache User Guide)

    DocumentationBeginnerFreeAbout 15 minutes (estimate)

    What it teaches
    Lazy loading, write-through and TTL, each with short pseudocode and a plain list of advantages and disadvantages. The patterns apply to any cache, not only to the AWS service.
    When to use it
    When you are about to write your first cache wrapper and need to choose how entries are filled and refreshed.

  • Addressing Cascading Failures (opens in a new tab)

    Google (Site Reliability Engineering book, Chapter 22)

    BookIntermediateFreeAbout 1 hour (estimate)

    What it teaches
    How overload spreads from one server to a whole service, and the defences: load testing to the breaking point, spare capacity, short queues, load shedding, retry limits and deadlines.
    When to use it
    Once you can size a system for normal operation and want to know how it behaves when demand exceeds that size.

  • Consistency Models (opens in a new tab)

    Jepsen

    DocumentationAdvancedFree

    What it teaches
    A clickable map of consistency models from read uncommitted to strict serializable, showing which model implies which and which models cannot be totally available on an asynchronous network.
    When to use it
    When a database's documentation uses a term such as snapshot isolation or read your writes and you need its exact meaning.

  • Stack Overflow: The Architecture - 2016 Edition (opens in a new tab)

    Nick Craver (Stack Overflow engineer, personal blog)

    ArticleBeginnerFreeAbout 20 minutes (estimate)

    What it teaches
    Real traffic figures next to the real hardware list of a large site: load balancers, web servers, a two-level cache and replicated SQL Servers, with notes on headroom and redundancy.
    When to use it
    When you are tempted to propose a distributed design and want a reference point for how far a small number of well-sized machines can go.
