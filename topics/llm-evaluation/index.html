Evaluating LLM Applications

Evaluating an LLM application means running it on a fixed set of realistic test inputs, scoring every output with code checks, a grading model or human reviewers, and comparing those scores across prompt or model changes and against what happens in production.

1Overview

Why it matters

An LLM application can look fine on the three inputs you tried by hand and still fail on a meaningful share of real requests. The same input can produce different outputs, and a prompt edit that fixes one case can quietly break another, so reading a few answers cannot tell you whether a change helped. Anthropic's engineers describe where teams end up without evals: they wait for complaints, reproduce the problem by hand, fix it and hope nothing else regressed.

An eval turns "it feels worse" into a number you can track and a list of cases you can read. It decides whether a prompt edit is safe to merge, whether you can move to a new model in days instead of weeks of manual testing, and whether quality in production is drifting. Anyone who writes prompts, ships an LLM feature or reviews a change to one needs to know how to build and read an eval.

Before you start

  • Prompt EngineeringBeginner

What you will be able to do

  • Build a small eval dataset from real failures and manual checks, with an expected answer or criteria for each case.
  • Write deterministic checks (match, pattern, schema, outcome) and explain where they are too brittle.
  • Design a model-graded check with a rubric, and describe how to calibrate it against human labels.
  • Say when human evaluation is needed and how to keep reviewers consistent.
  • Distinguish offline from online evaluation and turn production failures into new offline cases.
  • Regression-test a prompt change and judge with a paired comparison and an interval whether a difference is real.

Key terms

Eval
A repeatable test of an AI system. You give the system an input, apply grading logic to its output and record a score.
Eval dataset
The fixed collection of test cases an eval runs on. Each case has an input and either an expected answer or notes on what a good answer must contain. Also called a test set.
Grader
Logic that scores one output. It can be code, a second model guided by a rubric, or a human reviewer.
Deterministic check
A grader written as ordinary code, such as an exact match, a regular expression, a schema validation or a unit test. It returns the same verdict every time for the same output.
Model-graded evaluation
Using a second LLM call, guided by a written rubric, to score an output. It is also called LLM-as-a-judge.
Rubric
Written criteria that say what a good output must contain, specific enough that two graders reach the same verdict.
Trial
One attempt at a test case. Because outputs vary between runs, a case may be run several times.
Offline evaluation
Running the application on a fixed dataset before release, where the expected answers are known.
Online evaluation
Scoring real production requests as they happen, usually without a known expected answer.
Regression test
A rerun of cases that used to pass, after a change, to confirm that nothing that worked has stopped working.

2Explanation

Introduction

In Prompt Engineering you improved a prompt by trying it on a few inputs and reading the answers. That works for a first draft. It stops working when the prompt must handle hundreds of different requests, when you edit it every week, or when the model underneath it is replaced. A tweak that fixes the answer you were looking at can break three you were not looking at, and nothing tells you.

Software engineers solved this for ordinary code with automated tests. An eval is the same idea adapted to a system whose output is free text and changes from run to run. You collect a fixed set of realistic inputs (the eval dataset), run your application on all of them, score every output with a grader, and add the scores up. Change the prompt, run again, and compare. The score is rarely a hard gate in the way a unit test is. It is a measurement that says whether a change helped, and the list of failing cases says what to fix next.

Three kinds of grader exist, and good evals combine them:

  • Deterministic checks are ordinary code: an exact match, a regular expression, a JSON schema, a unit test. They are fast, cheap and repeatable, but they can only check what you can write down as a rule.
  • Model-graded checks ask another LLM to score an output against a written rubric. They cope with open-ended text, but they cost money, vary from run to run and must be checked against people.
  • Human review is the reference the other two are calibrated against. It is slow and expensive, so it is used on samples.

The second split is about when you evaluate. Offline evaluation runs on a dataset before you ship, where you know the right answers. Online evaluation scores live traffic after you ship, where usually you do not. They feed each other: production failures become new test cases, and the test cases protect you when you fix them.

This lesson shows how to build the dataset, how to choose graders, how to tell a real improvement from noise, and how to rerun everything each time a prompt changes. The examples later on come from teams and tools that document how they do it, including Rechat, Anthropic, LinkedIn, Honeycomb and Promptfoo.

How it works

What one eval run consists of

Every eval, from a ten-line script to a hosted platform, has the same five parts:

  1. A dataset of test cases, each with an input and an expected answer or notes on what a good answer needs.
  2. The system under test: the prompt, the model and its settings, and any tools or retrieval around it.
  3. One or more trials per case, since outputs vary.
  4. Graders that turn each output into a score, usually pass or fail.
  5. An aggregate (pass rate per check, per category, overall) to compare with the previous version.

Keep the dataset as one JSON object per line in a file in your repository, next to the prompt:

json
{"id": "t05", "input": "Please send me last year's invoices", "expected": {"category": "billing", "urgent": false}, "tags": ["billing", "routine"]}

Building the dataset

Teams delay evals because they think they need hundreds of cases. Anthropic's guide to evals (opens in a new tab) argues that 20 to 50 simple tasks drawn from real failures is a good start, because early changes tend to have large effects that small samples can show. Anthropic's research team began with about 20 queries (opens in a new tab) that represented real usage. Useful sources, roughly in order of value: the manual checks you already run before a release, your bug tracker and support queue, failed or thumbs-down requests from production, and last, synthetic cases an LLM generates from hand-written seeds, which LangSmith's documentation says work best when they start from several high-quality, hand-crafted examples.

Four rules keep a dataset useful:

  • Write unambiguous cases. A good case is one where two domain experts would independently reach the same verdict. An ambiguous case turns into noise in the score. With a capable model, a case that never passes across many trials usually points at a broken case or grader.
  • Balance the set. Include cases where a behaviour should happen and cases where it should not. Anthropic describes web-search evals that needed queries where the model should search and queries where it should answer from memory, because testing one side pushes the system to over-trigger.
  • Include the awkward inputs. Claude's documentation lists irrelevant or nonexistent input, very long input, poor or harmful user input and cases even humans find hard to judge. OpenAI's guide adds adversarial cases.
  • Keep some cases aside. If you tune the prompt against every case, the score measures how well the prompt fits that list. Hold back a slice for a check before release.

Deterministic checks first

Use code wherever a rule can decide:

Anthropic recommends deterministic graders where possible because they are fast, cheap and reproducible. Their weakness is brittleness: a grader that expects 96.124991 marks 96.12 wrong. Anthropic reports that one model's CORE-Bench score rose from 42% to 95% after a researcher fixed grading bugs and used a less constrained scaffold, so read failing cases before trusting a low score. Grade what the system produced rather than the exact steps it took, since valid approaches vary, and split a case into several named checks so the report shows which one failed. The worked example does this.

Model-graded checks for what rules cannot decide

Tone, completeness, whether an answer is supported by its sources and whether a summary is faithful cannot be written as a regular expression. For these, a second model call grades the output against a written rubric. The grader prompt contains the rubric, the output and, when you have one, a reference answer, and it returns a verdict plus a short reason. LLM-as-a-Judge covers this in depth. Three points matter here:

  • Prefer simple verdicts. OpenAI's evaluation best practices (opens in a new tab) recommend pairwise comparison or pass/fail for reliability, and warn about position bias (the order of two answers sways the verdict) and verbosity bias (longer answers score higher).
  • Give the judge a way out. Anthropic suggests an instruction to return "Unknown" when the information is insufficient, so the judge does not invent a verdict.
  • Test the judge like any other component. The authors of the MT-Bench paper (opens in a new tab) report that a strong judge (GPT-4) agreed with human preferences more than 80% of the time, the same level as agreement between humans: 85% against 81% when tie votes are excluded. That was one study's setting, so label 25 to 50 of your own outputs, compare them with the judge, and repeat now and then. When most outputs pass, raw agreement flatters the judge, so report the precision and recall of its fail verdict instead.

Human evaluation

People remain the reference. Use them to label the sample that calibrates a model judge, to grade subjective qualities, and to find failures nobody wrote a check for. In Anthropic's research system, human testers noticed that early agents chose SEO-optimised content farms over academic PDFs, a bias no rubric had covered. Humans help only if they apply one standard, so write guidelines with examples first, use a small consistent group of reviewers, and start with a binary good/bad label, which Hamel Husain (opens in a new tab) finds easier to manage than detailed scores. Plan for the delay too: LinkedIn reports roughly a day of turnaround from its annotators.

One run is one sample

Because outputs vary, a case that passes once may fail on the next run. When the variation matters, run each case several times and decide which question you are asking. With a per-trial success probability ppp (assuming trials are independent):

LangSmith's documentation (opens in a new tab) describes how the two fit together: online evaluations surface issues that become offline test cases, offline evaluations validate the fixes, and online evaluations confirm that production improved. Without a reference answer, online checks look for properties that can be verified alone: the output parses, the generated query runs, no personal data appears, a rubric score, a thumbs-down. Microsoft Foundry (opens in a new tab) documents the same split: datasets before deployment, then continuous evaluation of sampled production traffic and scheduled runs on test datasets to detect drift.

Regression testing prompts

A prompt is code that changes behaviour, so it gets a test suite and a rule for when the suite runs:

  1. Keep the prompt, model identifier, parameters and eval dataset in version control.
  2. Run the suite in CI on every change to any of them, and again whenever you change models.
  3. Compare with the last accepted version on the same cases. Read the cases that flipped from pass to fail before you look at the average.
  4. Decide the gate in advance. Anthropic separates capability evals, which start at a low pass rate and measure progress, from regression evals, which should stay near 100% and protect what works. A capability eval with a high pass rate can graduate into a regression suite. Hamel Husain notes that, unlike with unit tests, the required pass rate is a product decision.
  5. Save results with the prompt version so you can chart quality over time.

An eval at 100% still tracks regressions but shows no improvement, so keep adding hard cases from production failures. Prompt Management and Versioning covers storing and releasing prompts.

Worked example: Regression-testing a ticket-triage prompt on 12 saved cases

A support tool sends each ticket to an LLM with a triage prompt. The reply must be a JSON object with a category (one of billing, bug, account, other) and an urgent flag (a JSON boolean). The application calls json.loads on the reply and routes the ticket, so a reply that is not exactly a JSON object breaks it. A teammate has rewritten the prompt (v2) and asks whether it is safe to merge.

To make the numbers reproducible without an API key, the replies of both prompt versions were saved in advance. We wrote them by hand to resemble typical failures; they are not recordings of a real model. Everything else is a real eval: a dataset with expected answers, deterministic graders and a comparison of two versions on the same cases. With a live model you would call it inside run, and run each case more than once. Save this as triage_eval.py; it needs only the Python standard library.

python
import json
import math

ALLOWED = {"billing", "bug", "account", "other"}

# id: (ticket text, expected category, expected urgent)
DATASET = {
    "t01": ("I was charged twice for May", "billing", True),
    "t02": ("The export button does nothing", "bug", False),
    "t03": ("How do I change my email address?", "account", False),
    "t04": ("App crashes on launch, I cannot work", "bug", True),
    "t05": ("Please send me last year's invoices", "billing", False),
    "t06": ("Password reset email never arrives and I am locked out", "account", True),
    "t07": ("Great product, keep it up", "other", False),
    "t08": ("Refund me now or I cancel today", "billing", True),
    "t09": ("Dark mode flickers on the settings page", "bug", False),
    "t10": ("Please delete my account and data", "account", False),
    "t11": ("Do you have an office in Berlin?", "other", False),
    "t12": ("My invoice shows the wrong VAT number", "billing", False),
}

FENCE = "`" * 3  # three backticks: models often wrap JSON in a code fence
V1 = {  # saved replies from prompt v1 (hand-written for this lesson)
    "t01": '{"category": "billing", "urgent": true}',
    "t02": FENCE + 'json\n{"category": "bug", "urgent": false}\n' + FENCE,
    "t03": '{"category": "Account", "urgent": false}',
    "t04": '{"category": "bug", "urgent": true}',
    "t05": '{"category": "billing", "urgent": false}',
    "t06": FENCE + 'json\n{"category": "account", "urgent": true}\n' + FENCE,
    "t07": '{"category": "other", "urgent": false}',
    "t08": '{"category": "billing", "urgent": "yes"}',
    "t09": '{"category": "bug", "urgent": false}',
    "t10": '{"category": "account", "urgent": false}',
    "t11": '{"category": "other", "urgent": false}',
    "t12": '{"category": "billing", "urgent": true}',
}
V2 = {  # saved replies from prompt v2
    "t01": '{"category": "billing", "urgent": true}',
    "t02": '{"category": "bug", "urgent": false}',
    "t03": '{"category": "account", "urgent": false}',
    "t04": '{"category": "bug", "urgent": true}',
    "t05": '{"category": "billing", "urgent": true}',
    "t06": '{"category": "account", "urgent": true}',
    "t07": '{"category": "other", "urgent": false}',
    "t08": '{"category": "billing", "urgent": true}',
    "t09": '{"category": "bug", "urgent": false}',
    "t10": '{"category": "account", "urgent": false}',
    "t11": '{"category": "other", "urgent": false}',
    "t12": '{"category": "billing", "urgent": true}',
}


def grade(reply, expected_category, expected_urgent):
    """Return the first failed check for one reply, or None if every check passes."""
    try:
        data = json.loads(reply)  # the app calls json.loads, so a fenced reply is a real failure
    except json.JSONDecodeError:
        return "not valid JSON"
    if not isinstance(data, dict) or data.get("category") not in ALLOWED:
        return "category not in allowed set"
    if not isinstance(data.get("urgent"), bool):
        return "urgent is not a boolean"
    if data["category"] != expected_category:
        return "wrong category"
    if data["urgent"] != expected_urgent:
        return "wrong urgent flag"
    return None


def run(replies):
    return {tid: grade(replies[tid], cat, urg) for tid, (_, cat, urg) in DATASET.items()}


v1, v2 = run(V1), run(V2)
n = len(DATASET)
print(f"v1 pass rate: {sum(r is None for r in v1.values())}/{n}")
print(f"v2 pass rate: {sum(r is None for r in v2.values())}/{n}")
for tid in DATASET:
    if (v1[tid] is None) != (v2[tid] is None):
        kind = "FIXED    " if v2[tid] is None else "REGRESSED"
        print(f"{kind} {tid}: v1={v1[tid] or 'pass'} | v2={v2[tid] or 'pass'}")

# Paired difference: both versions ran on the same 12 tickets.
d = [(v2[t] is None) - (v1[t] is None) for t in DATASET]
mean = sum(d) / n
se = math.sqrt(sum((x - mean) ** 2 for x in d) / (n - 1) / n)
print(f"mean difference {mean:+.3f}, standard error {se:.3f}, "
      f"95% CI [{mean - 1.96 * se:+.3f}, {mean + 1.96 * se:+.3f}]")

FIXED     t06: v1=not valid JSON | v2=pass

Reading the result

  1. v1 passes 7 of 12. Four of its five failures are format problems: two replies wrapped in a code fence (t02, t06), a capitalised Account (t03) and the string "yes" for the urgent flag (t08). Code finds these in milliseconds, and v2 was written to remove them.
  2. v2 fixes all four and rises to 10 of 12, but the average hides t05. v2 now flags a routine request for old invoices as urgent, which v1 handled correctly. This is the regression to fix before merging, and only the case-by-case comparison shows it.
  3. t12 fails in both versions with the same wrong urgent flag. Before changing the prompt, check the case itself: is a wrong VAT number really not urgent? A failing case sometimes means a wrong expected label.
  4. The paired differences are +1 for four cases, -1 for one and 0 for seven, so the mean difference is +0.25 with a standard error of 0.179. The 95% interval, -0.10 to +0.60, includes zero: twelve cases cannot show that v2 is better on average. If the same pattern held on 48 cases (16 fixed, 4 regressed, 24 passing in both, 4 failing in both), the interval would be +0.08 to +0.42. With only 12 cases the multiplier 1.96 is slightly optimistic; a t-based interval would be wider (about -0.14 to +0.64), so the conclusion stands.

The next step is to add several routine billing and account requests that must not be flagged urgent, fix the over-flagging, and rerun. Twelve cases were enough to surface a regression and a doubtful label, and not enough to certify the prompt.

Edge cases and limitations

A wrong grader looks exactly like a wrong model
A rigid or buggy grader lowers the score of correct answers. Anthropic reports that one model's CORE-Bench score rose from 42% to 95% after a researcher fixed grading bugs, including a grader that rejected 96.12 because it expected 96.124991, and used a less constrained scaffold. Ambiguous task specifications were also among the problems found. The sign is failures that look unfair when you read them, or many failures with one shared cause. Read a sample of failing outputs and fix the grader or the case before you touch the prompt.
A small dataset can only reveal large changes
At an 80% pass rate on 50 cases the 95% interval is about plus or minus 11 points, and the worked example's 12 cases could not separate a 25-point gain from zero. Small sets are still worth having, because early changes are often large and the failing cases are informative, but a 3-point gain on 40 cases is not evidence of improvement. Add cases, run several trials per case and compare paired. For tiny sets or rates near 0% or 100% the normal approximation is crude, so treat the interval as a rough guide.
The dataset stops resembling real traffic
Scores can stay high while users complain, because the dataset was written once and real inputs moved on. OpenAI's guide lists datasets that do not reproduce production traffic as an anti-pattern, and Anthropic warns that automated evals can create false confidence when they do not match real usage. The sign is production failures or thumbs-down cases that nothing in the suite resembles. Sample production inputs regularly and add each new kind of failure as a case.
Hosted evaluation platforms can be retired
As of October 2026, [OpenAI's documentation](https://developers.openai.com/api/docs/guides/evals) says its Evals platform becomes read-only for existing users on October 31, 2026 and is scheduled to shut down on November 30, 2026. If your only copy of the dataset and graders lives in a vendor dashboard, a retirement forces a rebuild. Keep the dataset as JSONL, the graders as code and the rubric prompts as text files in your own repository, and treat any platform as a runner you could replace.
Eval cases leak into the prompt
If cases from the eval set are pasted into the prompt as few-shot examples, or you reword the prompt until every case passes, the score measures memorisation of the list rather than behaviour on new inputs. The sign is a large gain on the dataset that never shows up in production feedback. Keep a held-out slice, check that no eval input appears in the prompt, and refresh the held-out slice with new production cases.

When to use it, and when something simpler is enough

Use it when

  • You change a prompt, model, retrieval setting or tool more than once, and need to know whether each change helped without rereading outputs by hand.
  • The feature has rules you can state, such as valid JSON, allowed labels or no leaked identifiers. Start there with deterministic checks that run on every commit.
  • You are about to switch models or providers. A fixed suite lets you compare the candidates on your own inputs in days instead of weeks of manual testing.
  • The feature is live and quality is hard to see. Online checks on sampled traffic, plus user feedback, show drift and give you failing cases to add to the dataset.

Think twice when

  • You are tempted to use a public benchmark score as your evaluation. Benchmarks compare models in isolation, so use them only to shortlist models, then test on your own task distribution.
  • You would make a model-graded score a release gate before comparing its verdicts with human labels on your own outputs.
  • The correct answer can be worded many ways and you only have an exact-match check. Use a rubric, key-fact checks or human review instead, or the score will punish valid answers.

A simpler alternative. A JSONL file of 20 real cases, a Python script with three assertions and a quick read of every failing output. That already beats judging by feel, and it is often enough until the prompt changes weekly or several people edit it. At that point move the suite into CI, add a rubric for the qualities rules cannot check, and start sampling production.

Key takeaways

  • An eval is a fixed set of realistic cases, a grader for each output and a comparison with the previous version, and it replaces judging a change from a few hand-picked answers.
  • Start with 20 to 50 cases taken from real failures, use code checks wherever a rule can decide, add rubric-graded checks for open-ended qualities, and keep humans for calibration and for failures nobody anticipated.
  • A score from a small dataset or a single run is a noisy estimate, so compare versions on the same cases, report an interval and read the cases that flipped from pass to fail.
  • Offline evals protect a release and online checks find what the dataset missed, so every production failure should come back as a new offline case.
  • Regression-testing a prompt means keeping the prompt, model and dataset in version control and running the suite on every change against a gate you decided in advance.

Example 1 of 5

Rechat's Lucy assistant, scoped assertions and synthetic inputs run in CI

Rechat, described by Hamel HusainDocumented in a case study

Rechat is a SaaS application for real estate professionals, and Lucy is its conversational AI assistant. Hamel Husain's March 2024 post "Your AI Product Needs Evals" describes the evaluation system built to improve Lucy, and that post is the cited document. [6]

The problem

After quick early progress from prompt engineering, Lucy's quality plateaued as its surface area grew. Fixing one failure mode made others appear, there was little visibility into how well the assistant did across tasks beyond informal checks, and the prompts grew long as they tried to cover more edge cases.

Where this topic fits

This is the first and cheapest level of evaluation in the post: assertions that run quickly on every change. They sit before the slower human and model-based review of logged conversations, and before A/B tests on real users.

How it is applied, step by step

  1. Split the assistant into features, such as finding real estate listings, and split each feature into scenarios, such as one listing matches, several match, or none match.
  2. Write an assertion for each scenario that checks observable behaviour, for example the number of listings the CRM query returns.
  3. Add generic assertions that apply to every reply, such as a regular expression that fails when an internal UUID appears in the text shown to the user.
  4. Generate test inputs with an LLM from a prompt, run them against the real tools, and apply the assertions to what happens.
  5. Run the suite in CI and track the results over time in an analytics tool (the post names Metabase for Rechat), keeping them with the versions of the tests and prompts so error rates can be charted.
  6. Add new assertions whenever human review or real users reveal a new failure, and accept a pass rate below 100% if that is the failure rate the product can tolerate.

Why this approach fits

Features such as listing search have a verifiable ground truth: the CRM either returns the expected rows or it does not. Code can check that in milliseconds on every commit, points at one feature and scenario, and does not depend on a second model's opinion. Synthetic inputs let the team start before enough real traffic exists to build a dataset from.

Limitation or tradeoff

Assertions only catch failures that someone thought to write down, and they say nothing about tone, helpfulness or whether the user got what they wanted. Synthetic inputs are guesses about users until real usage refines them. The post itself says that many teams outgrow unit tests as a product matures, which is why it adds model-based and human evaluation and A/B tests on top.

What the sources document

  • The post describes Lucy as the AI assistant in Rechat's real estate software. It says progress from prompt engineering plateaued as Lucy's scope grew: fixing one failure produced others, visibility beyond informal checks was limited, and prompts became long and unwieldy. [6]

Anthropic's engineering post "How we built our multi-agent research system" (June 2025) describes how the team evaluated its Research feature, in which several Claude agents explore complex topics. [2]

Where this topic fits

A small offline dataset of real-usage queries is run through the system after each change. An LLM judge scores every output against a rubric, and people test the system separately to catch what the rubric misses. What they find goes back into the prompts.

How it is applied, step by step

  1. Collect about 20 queries that represent real usage, instead of waiting until a large test set exists.
  2. Run the research system on each query after a prompt or design change and keep the outputs for grading.
  3. Grade every output with an LLM judge that applies a written rubric covering factual accuracy, citation accuracy, completeness, source quality and tool efficiency.
  4. Have the judge return a 0.0 to 1.0 score and a pass or fail grade in a single call, and compare with the earlier version.
  5. Let people test the system by hand in parallel, because they find failures that the rubric did not list.

Why this approach fits

About 20 queries can reveal only large effects; as the system improves, smaller differences need more cases. The post reports no agreement figures for the judge beyond saying the single-call design was the most consistent and aligned with human judgements.

Example 4 of 5

Honeycomb's Query Assistant, scoring every production request with a pass or fail check and an SLO

HoneycombDocumented in an engineering article

Honeycomb's post "Improving LLMs in Production With Observability" (updated September 2023, by Phillip Carter) explains how the team monitors Query Assistant, a feature that turns a natural-language question into a Honeycomb query. [8]

The problem

Once Query Assistant was live, the team asked how likely users were to get a relevant, useful query, how to fix their errors, and how to know whether prompt changes brought tangible benefits across all users. User inputs are unpredictable and small prompt changes can alter behaviour a lot, so guessing was not an option.

Where this topic fits

This is online evaluation. A pass or fail check that needs no reference answer scores every real request, failing requests guide the next round of prompt work, and user feedback adds a second signal.

How it is applied, step by step

  1. Log, for every request, the user input, the model's response and any error.
  2. Define a per-request success check that fails when calling the model, parsing its output or running the resulting query raises an error.
  3. Set a service level objective on that check, here 75% successful requests over seven days, with an alert before the error budget runs out.
  4. Use the objective's view of failing requests to see which field values, such as the error message, are most common, then open a query on one error and add the user input and model output so all three can be read together.
  5. Correct predictable model mistakes in code, and watch the success rate over the following weeks to see whether the fixes worked.
  6. Read the "no" answers from the feedback box for patterns the success check cannot see.

Why this approach fits

There is no reference answer for a user's novel question, but there is a cheap, objective check: does the generated query parse and run? Applying it to every request gives a continuous measure that exposes regressions after a prompt change and ranks failure types by how often they occur.

Limitation or tradeoff

The check measures validity, not relevance: a query can run and still be the wrong query. The team also reads user feedback, but the post notes that users tend to give feedback when things are not great, so it cannot show how the feature does overall.

What the sources document

  • Query Assistant works by gathering context with the user's input and having the LLM produce a JSON Honeycomb query specification. The team reviews triplets of user input, LLM response and error to find fixable problems. [8]
  • The objective counts a request as failed if calling OpenAI, parsing its output or running the query returns an error. The initial target was 75% successful requests over seven days, with a Slack notification four hours before the budget would be exhausted, chosen because the feature is not mission-critical. [8]
  • After a few weeks of correcting fixable model outputs, for example removing a column from a COUNT operation, the team raised the target to 80% and says the success rate was up nearly 15% compared with launch. [8]
  • A feedback box asks users whether the query was what they wanted, with yes, no and not sure buttons. The post says users tend to give feedback when things are not great, so it cannot show overall performance, but even a "no" helps identify patterns. [8]

Promptfoo's GitHub Action, a before-and-after prompt evaluation on every pull request

PromptfooDocumented in official docs

Promptfoo is a command-line tool for evaluating prompts and models. Its GitHub Actions guide documents a workflow that runs an evaluation whenever a pull request changes prompt files, and its getting-started and CI/CD guides document the test format and quality gates. [9][10][11]

The problem

Prompts live in files that people edit in pull requests, and a small wording change can alter behaviour on many inputs. Reviewers need to see the effect of the edit on a fixed set of test cases before the merge, not after users hit the regression.

Where this topic fits

The evaluation runs in CI, between a prompt edit and its merge. The test cases and their assertions form the regression suite, the action compares the edited prompt with the previous version, and the result appears on the pull request.

How it is applied, step by step

  1. Keep prompts in files, and define test cases with variables and assertions in a promptfooconfig.yaml file.
  2. Add a workflow that triggers on pull requests that touch the prompt files or the config.
  3. Let the action run the suite on the edited prompts, compare before with after, and post a link to the results on the pull request.
  4. Have the reviewer open the web viewer to see outputs side by side and which assertions changed.
  5. Cache model requests and outputs so unchanged inputs are not paid for again.
  6. Add a quality gate that fails the build on any failure or below a chosen pass rate, then merge when it passes.

Why this approach fits

A prompt edit is a small diff with potentially large effects, so running a fixed suite on every pull request puts the evidence in the place where the change is reviewed, using the same trigger that already runs other tests. Mixing string and code assertions with rubric assertions in one config keeps the cheap checks first.

Limitation or tradeoff

Every run calls the model and costs money, assertions catch only what the config checks, and outputs vary, so a borderline case can flip between runs. Because the documented workflow caches requests and outputs to save cost, a scheduled check for model drift would need caching turned off, or it would replay stored outputs. A single pass-rate threshold also hides which case failed unless someone reads the report.

What the sources document

  • The GitHub Actions guide describes an automatic before-versus-after evaluation of edited prompts. On every pull request that modifies a prompt, the action runs a full comparison and provides a link to a web viewer for exploring the before and after. [9]
  • The example workflow triggers on pull requests that change files under prompts/ and runs the promptfoo/promptfoo-action with inputs for the prompt file patterns and the config file path. A cache of LLM requests and outputs is kept to speed up runs and save cost. [9]
  • Test cases in the configuration pair variables with assertions. The getting-started guide shows contains and icontains string checks, a javascript check and model-graded llm-rubric assertions, and says assertions are optional. [10]
  • The CI/CD guide describes quality gates: the eval command with the fail-on-error option fails the build on any test failure, and a script can compute the pass rate from the JSON output and fail below a threshold, shown with 95% as the example. [11]

4Common mistakes

  1. Judging a prompt change by a few hand-picked outputs

    Why it causes problems
    A fix for the case you were reading can break cases you were not reading, and run-to-run variation makes one lucky or unlucky output look like a trend. With no baseline you cannot tell whether the change helped, so the team drifts into fixing complaints one at a time.
    How to recognise it
    Quality discussions rest on phrases like "it seems better" and on screenshots of single outputs. Regressions are reported by users after a merge, and nobody can say what the pass rate was last week.
    How to fix it
    Build a dataset of 20 to 50 cases from real failures and manual checks, run the old and new prompt on all of them, and compare per-case results before merging. Read the cases that flipped from pass to fail first.

  2. Trusting a score without reading the failing outputs

    Why it causes problems
    Graders have bugs and cases have wrong labels. A rigid grader can reject correct answers, as in the CORE-Bench example where fixing grading and task problems moved one model's score from 42% to 95%, so you may end up tuning the prompt against a measurement error.
    How to recognise it
    Failures look fair to the grader but not to you, many failures share one cause such as a formatting quirk, or a case never passes across many trials.
    How to fix it
    Read a sample of failing outputs with the grader's reason beside each one. Fix the grader or the expected label where it is wrong, and keep a reference answer for each case that proves the case can pass.

  3. Using a model judge that was never compared with human labels

    Why it causes problems
    Judges have documented biases, including favouring longer answers and the answer shown first, so a score can reward style over quality. When most outputs are good, a judge that approves everything still looks fine on raw agreement while missing every real failure.
    How to recognise it
    Your own reading of a sample disagrees with the judge, the score rises when you merely make answers longer, or swapping the order of two answers in a pairwise comparison changes the winner.
    How to fix it
    Label 25 to 50 outputs yourself before looking at the judge. Compute the precision and recall of its fail verdict, prefer pass/fail or pairwise verdicts to fine scales, randomise answer order, and repeat the check whenever you change the judge prompt or model.

  4. Reading only the average pass rate

    Why it causes problems
    An average hides a regression on an important case when other cases improve, and it hides noise. In the worked example a rise from 7 of 12 to 10 of 12 concealed a newly broken case, and the interval around the gain included zero.
    How to recognise it
    The release note says "pass rate up 5 points" but nobody has listed which cases changed, and rerunning the same version gives a different number.
    How to fix it
    List the cases that flipped in each direction, mark must-pass cases that block a merge, run several trials where the output varies, and report the paired difference with its interval.

  5. Filling the dataset with easy or one-sided cases

    Why it causes problems
    A suite of typical inputs scores high on every version and cannot detect brittleness. A one-sided suite pushes the system to over-trigger: if every case expects a search, an assistant that always searches scores perfectly.
    How to recognise it
    Every change scores 95% or more, production failures are not represented in the suite, or all cases expect the same action.
    How to fix it
    Add edge cases, adversarial inputs and cases where the right behaviour is to do nothing. Turn each production failure into a case, prioritising by user impact.

  6. Keeping the only copy of the dataset and graders inside a vendor platform

    Why it causes problems
    Platforms change. As of October 2026, OpenAI's documentation says its Evals platform becomes read-only for existing users on October 31, 2026 and is scheduled to shut down on November 30, 2026. If the dataset exists only in a dashboard, a shutdown forces you to rebuild the suite while you are still shipping.
    How to recognise it
    You cannot export the cases and grader logic to files, and a new teammate cannot run the eval from a clean checkout of the repository.
    How to fix it
    Store the dataset as JSONL, and graders and rubric prompts as files, in the repository next to the prompt. Use a platform as a runner and dashboard on top of them.

Compare pass rate, any-success and all-success on repeated trials

TRIALS = {
    "refund-simple": [1, 1, 1, 1, 1],
    "refund-angry": [1, 1, 0, 1, 1],
    "address-change": [1, 0, 1, 0, 1],

    "out-of-scope-question": [1, 1, 1, 1, 0],

}

Then answer in two sentences: which metric should gate a release of a customer-facing assistant, and which case would you read first?

Requirements

  • Print the pass rate of each case across its five trials.
  • Print the suite pass rate per trial, the number of cases with at least one pass in five trials, and the number of cases that pass all five.
  • Print the names of the unstable cases, meaning those that neither always pass nor always fail.
  • Write the two-sentence answer as comments at the end of the script.

Hint 1

`any(trials)` is true when at least one trial passed, and `all(trials)` is true when every trial passed.

Hint 2

A case is unstable when its pass rate is strictly between 0 and 1.

Hint 3

Anthropic's guide notes that a case that never passes across many trials most often signals a broken task or grader rather than an incapable model, so treat a case that passes only once in five with the same suspicion.

Show solution
python
TRIALS = {
    "refund-simple": [1, 1, 1, 1, 1],
    "refund-angry": [1, 1, 0, 1, 1],
    "address-change": [1, 0, 1, 0, 1],
    "cancel-subscription": [0, 0, 1, 0, 0],
    "out-of-scope-question": [1, 1, 1, 1, 0],
    "greeting": [1, 1, 1, 1, 1],
}

rates = {case: sum(trials) / len(trials) for case, trials in TRIALS.items()}
for case, rate in rates.items():
    print(f"{case:24s} pass rate {rate:.2f}")

n = len(TRIALS)
print(f"suite pass rate per trial: {sum(rates.values()) / n:.3f}")
print(f"cases with at least one pass in 5 trials: {sum(any(t) for t in TRIALS.values())}/{n}")
print(f"cases that pass all 5 trials: {sum(all(t) for t in TRIALS.values())}/{n}")
unstable = [case for case, rate in rates.items() if 0 < rate < 1]
print("unstable cases:", ", ".join(unstable))

# A customer-facing assistant should be gated on the all-success count (2 of 6 here), because users expect
# it to work every time. The at-least-one count (6 of 6) only shows that each case is possible.
# Read cancel-subscription first: it passed once in five trials, which suggests a broken case or grader.

Exercise 2

Build a 20-case eval for your own prompt and calibrate a judge against your labels

Hands-onIntermediateAbout 1 h 30 min (estimate)Hypothetical scenario

Pick one small LLM task you can run for free, for example "turn a customer email into a one-sentence summary and a JSON list of action items". Use a local model (for instance through Ollama), a free tier of any provider, or, if you have no model access, replies that you write by hand to resemble model output; the grading practice is identical. Build the eval in plain Python:

  1. Write 20 test inputs in a JSONL file, at least 5 of them hard (an empty email, a very long one, one in another language, one with no action items, one that tries to give the model instructions).
  2. Write at least three deterministic checks and report each by name for every case.
  3. Write a short rubric for one quality that code cannot check, such as "the summary states nothing the email does not say", and have a model (or a friend) apply it as pass, fail or unknown to every output.
  4. Label 15 of the outputs pass or fail yourself for that quality, before you read the judge's verdicts.
  5. Compute raw agreement, precision and recall of the judge's fail verdict against your labels.
  6. Change the prompt, rerun everything, and list the cases that went from pass to fail and from fail to pass.

Requirements

  • The dataset has 20 cases in JSONL, at least 5 of them edge cases and at least 3 where the right behaviour is to do nothing or decline.
  • There are at least three deterministic checks, and the report names the failing check for each failing case.
  • The rubric allows an "unknown" verdict, and you record verdicts for at least 15 outputs.
  • Agreement, precision and recall are computed from your own labels.
  • A second run with a changed prompt prints the cases that flipped in each direction.

Expected behaviour

Your results will differ from the sample below, but the report should show per-check pass rates, the judge's precision and recall on your labels, and a short flip list for the prompt change. With 15 labelled outputs, expect the judge to miss at least one real failure; if it misses none, add a few outputs that you know contain an invented fact and see whether it catches them.

Hint 1

Decide the expected behaviour for every case before you run the model, so you cannot rationalise the output afterwards.

Hint 2

Label before you look at the judge; otherwise your labels will drift towards its verdicts.

Hint 3

If the judge passes nearly everything, add outputs you know are bad, because with mostly good outputs raw agreement hides misses.

Hint 4

Count a judge "unknown" separately instead of treating it as pass or fail.

Show solution

A possible set of deterministic checks for the email task, each returning a named result:

python
import json
import re

EMAIL = re.compile(r"[\w.+-]+@[\w-]+\.[\w.]+")

def checks(reply):
    """Named deterministic checks for one reply, as {name: passed}."""
    try:
        data = json.loads(reply)
    except json.JSONDecodeError:
        return {"valid_json": False, "summary_short": False,
                "actions_are_strings": False, "no_email_address": False}
    if not isinstance(data, dict):
        return {"valid_json": False, "summary_short": False,
                "actions_are_strings": False, "no_email_address": False}
    summary, actions = data.get("summary", ""), data.get("actions")
    return {
        "valid_json": True,
        "summary_short": isinstance(summary, str) and 0 < len(summary.split()) <= 40,
        "actions_are_strings": isinstance(actions, list) and all(isinstance(a, str) for a in actions),
        "no_email_address": isinstance(summary, str) and not EMAIL.search(summary),
    }

A rubric with a way out:

text
You compare an email with a one-sentence summary of it.
Answer "fail" if the summary states anything the email does not say.
Answer "pass" if every statement in the summary is supported by the email.
Answer "unknown" if the email is empty or unreadable.
Reply with one word: pass, fail or unknown.

Metrics against your own labels, treating "fail" as the positive class (this snippet uses sample data for 15 outputs; replace it with yours):

python
human = ["pass", "fail", "pass", "pass", "fail", "pass", "fail", "pass", "pass", "fail", "pass", "fail", "pass", "pass", "fail"]
judge = ["pass", "fail", "pass", "pass", "pass", "pass", "fail", "pass", "fail", "fail", "pass", "pass", "pass", "pass", "fail"]

pairs = list(zip(human, judge))
tp = sum(h == "fail" and j == "fail" for h, j in pairs)   # judge caught a real failure
fp = sum(h == "pass" and j == "fail" for h, j in pairs)   # judge flagged a good output
fn = sum(h == "fail" and j == "pass" for h, j in pairs)   # judge missed a real failure
tn = sum(h == "pass" and j == "pass" for h, j in pairs)

print(f"tp={tp} fp={fp} fn={fn} tn={tn}")
print(f"agreement={(tp + tn) / len(pairs):.2f} precision={tp / (tp + fp):.2f} recall={tp / (tp + fn):.2f}")

Interpretation: the judge agrees with you on 80% of outputs, but it misses two of the six real failures (recall 0.67), so it should not be a release gate yet. To compare prompts, store each run's per-case results in a dict keyed by case id and print the ids whose pass status differs between the two runs.     Before you claim that one prompt or model beat another on a test set.
