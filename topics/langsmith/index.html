LangSmith

LangSmith is LangChain's platform for observing and evaluating LLM applications. It records each request as a trace of nested runs, scores those runs with datasets, experiments, automatic evaluators and human review queues, and stores versioned prompts. It receives data through SDKs and OpenTelemetry, so the application does not have to be built with LangChain.

1Overview

Why it matters

An LLM application fails in ways that ordinary logs do not show. The request returns HTTP 200, but the answer cites the wrong document, the agent passed a bad argument to a tool four steps earlier, or yesterday's prompt edit broke a case that used to work. Finding these needs four things: the full record of each request, a fixed set of test cases to rerun after every change, a way to score live traffic that has no known right answer, and a place where a domain expert can say that an output is wrong and supply the correct one. LangSmith puts all four on one data model, which is why a production trace can become a test case without anyone copying data by hand.

You will meet LangSmith on teams that use LangChain or LangGraph, because tracing turns on there with two environment variables, and on teams that use neither. Engineers need to know how to instrument code and read a trace. Whoever owns quality needs to know the difference between an offline experiment and an online evaluator, because the two answer different questions and cost different amounts. Anyone responsible for customer data needs to know what a trace contains and how long it is kept.

Key terms

Run
One unit of work inside a request, such as a model call, a tool call or a traced function. It is LangSmith's name for what OpenTelemetry calls a span.
Trace
All the runs produced by one request, linked by a shared trace id and arranged as a tree.
Thread
The traces of one multi-turn conversation, grouped because their runs carry the same thread_id value in metadata.
Tracing project
A named container for the traces of one application or service.
Feedback
A score attached to a run. It has a key, such as correctness, and a numeric or categorical value, and it can come from a user, an evaluator or a human reviewer.
Dataset and example
A dataset is a list of test cases called examples. Each example has inputs, optional reference outputs and optional metadata.
Experiment
The stored result of running one version of an application over a dataset, with the output, trace and evaluator scores for every example.
Evaluator
A function, an LLM prompt or a person that scores a run. Offline evaluators run on dataset examples and online evaluators run on production traffic.
Annotation queue
A work list of runs or threads that human reviewers score against a rubric, with progress tracking and an option to save reviewed items to a dataset.
Prompt commit and tag
A commit is one saved version of a prompt, identified by a hash. A tag is a movable label, such as production, that points at one commit.

2Explanation

Introduction

In LLM and Agent Observability you saw that one request to an LLM application is recorded as a trace: a tree of spans for the model calls, retrieval steps and tool calls that happened along the way. That lesson was about the idea. This one is about a product that stores those trees and builds a quality workflow on top of them.

Think of what a racing team keeps in its garage. A data logger records every lap in detail. A test bench reruns the same fixed programme after each engine change, so results can be compared. A mechanic inspects the cases the instruments cannot judge. LangSmith has the same three parts for an LLM application:

  • Tracing is the data logger. Every request is stored as a trace made of runs, which is LangSmith's word for spans.
  • Datasets and experiments are the test bench. A dataset is a fixed list of inputs with expected outputs. An experiment is one version of your application run over that list and scored by evaluators.
  • Online evaluators and annotation queues deal with live traffic. Evaluators score a sample of production runs automatically, and queues hand selected runs to human reviewers.

A fourth part, prompt management, stores prompts as versioned objects, so the text your application sends to a model can change without a code deployment.

The parts share one data model, and that is the main reason to use one tool for all of them. A production run that a user marked as wrong can go to a review queue, be corrected by a reviewer, be saved as a dataset example and then appear in the next experiment.

Two notes on names. LangSmith is made by LangChain, the company, but it is a separate product from LangChain, the open-source framework. It accepts traces from plain Python, from other agent frameworks and from OpenTelemetry exporters. The brand has also grown: the LangSmith product page (opens in a new tab) now lists deployment, sandboxes, a model gateway and a no-code agent product next to observability and evaluation. This lesson covers tracing, evaluation, human review and prompts, because the other products build on them.

How it works

The data model

LangSmith stores a small number of record types. Every screen in the product is a view over them.

RecordWhat it isWorth knowing
RunOne unit of work: a model call, a tool call, a retrieval step or any function you traceHas a run_type such as llm, tool, retriever or chain. Equivalent to an OpenTelemetry span.
TraceAll the runs of one requestThe root run's id is the trace id. A trace holds at most 25,000 runs.
ThreadThe traces of one conversationGrouped by a thread_id key in run metadata. Each turn is its own trace.
Tracing projectThe traces of one application or serviceSet with LANGSMITH_PROJECT. The fallback project is named default.
FeedbackA key and a score attached to a runUsers, evaluators and reviewers all write the same record.
Dataset, exampleA list of test cases; each has inputs, optional reference outputs, optional metadataReference outputs are read by evaluators only. Your application never sees them.
ExperimentOne application version run over one datasetKeeps the output, the trace and the scores for every example.

A run stores more than inputs and outputs. The run data format (opens in a new tab) lists its name, start and end time, error message, tags, the id of its parent run and, for model calls, prompt, completion and total token counts with their cost. Tags are plain strings and metadata is key-value pairs. Both exist so that you can filter and group runs later, for example by application version or customer plan.

Sending traces, with or without LangChain

The SDK is configured through environment variables: an API key, an on switch and, optionally, a project name.

bash
export LANGSMITH_TRACING=true
export LANGSMITH_API_KEY="<your-api-key>"
export LANGSMITH_PROJECT="support-bot"   # optional

A workspace in the EU region also needs LANGSMITH_ENDPOINT=https://eu.api.smith.langchain.com.

With LangChain or LangGraph that is all. The framework's components report themselves, and the LangChain tracing guide (opens in a new tab) states that no extra code is needed.

Without LangChain you mark the functions you care about with the SDK's @traceable decorator and, optionally, wrap the model client:

python
from langsmith import traceable
from langsmith.wrappers import wrap_openai
from openai import OpenAI

client = wrap_openai(OpenAI())                  # each chat completion becomes an llm run


@traceable(run_type="retriever")
def search_docs(question: str) -> list[str]:
    return ["Refunds are issued within 14 days."]


@traceable(name="answer_question", tags=["prompt-v3"])
def answer_question(question: str) -> str:
    context = search_docs(question)             # child run
    reply = client.chat.completions.create(     # child run
        model="gpt-5-mini",
        messages=[
            {"role": "system", "content": f"Answer using only this context: {context}"},
            {"role": "user", "content": question},
        ],
    )
    return reply.choices[0].message.content


answer_question(
    "How long do refunds take?",
    langsmith_extra={"metadata": {"thread_id": "conv-812", "plan": "pro"}},
)

The decorator records the function's arguments as inputs and its return value as outputs. When one traced function calls another, the SDK nests the second run under the first, and that nesting is the tree you see in the UI. Runs are posted in the background so that tracing does not delay the request. The price is that a short script can exit before its last runs are sent unless it flushes the client first.

From another framework or language there are three options: a ready-made integration (the first real-world example below uses the one for the OpenAI Agents SDK), the SDKs for TypeScript, Go and Java, or OpenTelemetry (opens in a new tab). For the last one, point an OTLP exporter at https://api.smith.langchain.com/otel with an x-api-key header, and spans that follow the GenAI, OpenInference or OpenLLMetry conventions are mapped to runs.

Feedback: one record for every kind of score

Whoever does the judging, the result has the same shape: a key, a score or category, an optional comment, attached to a run. A thumbs-down from your own UI is written with client.create_feedback; the documentation's sample passes key="user_feedback", a score, the trace_id and the id of the tracing project as session_id. An evaluator returns the same fields, and so does a reviewer filling in a rubric. Because the shape is shared, one filter can combine them, such as "runs where user_feedback is 0 and groundedness is below 0.5".

Offline evaluation: datasets, experiments and evaluators

Offline evaluation is testing before release. It has three ingredients.

  1. A dataset. The evaluation concepts (opens in a new tab) page suggests starting with 10 to 20 hand-written examples that cover common cases and edge cases, then adding real traces. LangSmith creates a new dataset version whenever examples change, and examples can belong to named splits.
  2. A target function that takes one example's inputs and returns your application's outputs.
  3. Evaluators. In the SDK an evaluator is a function that accepts any of inputs, outputs and reference_outputs and returns a score.
python
from langsmith import Client


def correct(outputs: dict, reference_outputs: dict) -> bool:
    return outputs["answer"] == reference_outputs["answer"]


Client().evaluate(
    target,                       # def target(inputs: dict) -> dict
    data="refund-questions",      # dataset name
    evaluators=[correct],
    experiment_prefix="prompt-v3",
    max_concurrency=4,
)

Each call creates one experiment. A bare boolean or number takes the function's name as its feedback key. Returning a dictionary with key, score and comment lets you name the metric and explain a failure. Evaluators come in four families: code (deterministic checks), LLM-as-judge (see LLM-as-a-Judge), pairwise (which of two versions answered better) and human. Teams that already use a test runner can keep it: the pytest and Vitest/Jest integrations log every test run as an experiment, which is the usual way to put evaluations into CI.

Online evaluation: scoring live traffic

A production run has no reference output, so an online evaluator cannot compare against an answer key. It looks for problems visible in the run itself: an answer not supported by the retrieved text, a refusal, a malformed output, a policy violation. An online evaluator (opens in a new tab) is attached to a tracing project and has three settings: a filter (which runs), a sampling rate (what fraction of them) and the evaluator itself, either an LLM-as-judge prompt or a code function. Its result is written as feedback on the run. Multi-turn evaluators do the same for whole threads. They wait until a thread has been idle, ten minutes by default, and then judge the conversation.

Online evaluators are one action of a broader mechanism called automation rules. A rule is a filter, a sampling rate and an action. The other actions add matching runs to a dataset, add them to an annotation queue, call a webhook or extend their retention.

Annotation queues: structured human review

An annotation queue is a work list for human reviewers. You write a rubric (instructions plus the feedback keys to fill in), choose how many reviewers must complete each item, and can turn on reservations so that two people do not open the same item at once. Runs arrive from the trace view, from a bulk selection, from an automation rule or from an experiment. A reviewer reads the inputs and outputs, scores the rubric, adds notes and can save the item to a dataset. A second queue type shows two runs side by side for a pairwise judgement.

Prompts: commits, tags and the hub

LangSmith versions prompts the way git versions files. Saving a prompt creates a commit with a unique hash. A tag is a readable label, such as production, that points at one commit and can be moved. Code asks for a version by name:

python
from langsmith import Client

prompt = Client().pull_prompt("refund-answer:production")   # or "refund-answer:12344e88"

Pointing production at a newer commit changes what this line returns with no deployment, and pointing it back is the rollback. LangSmith reserves the names staging and production for this deployment use; other tags, such as v2, are free-form. Public prompts in the LangChain Hub are pulled by their author's handle, in the form owner/prompt-name. Two details matter in practice. First, pull_prompt returns a LangChain prompt template object, so this feature uses LangChain's types even when the rest of your code does not; helper functions such as convert_prompt_to_openai_format turn the filled-in prompt into a provider request. Second, the SDK caches pulled prompts in memory, for five minutes by default, so running processes do not see a moved tag at once. The Playground is the UI for editing a prompt, changing the model and running it over a dataset before you commit. Prompt Management and Versioning covers the general practice.

Worked example: Trace, test and compare two versions of a ticket router, with no model key needed

The application is a support-ticket router that puts each ticket in one of four categories. So that everyone gets identical numbers it uses keyword rules, not a model. Everything specific to LangSmith is the same as it would be for an LLM: the functions are traced with @traceable, the test cases go in a dataset, and each version is scored in an experiment.

Save this as ticket_router.py. It needs Python 3.9 or later and pip install -U langsmith.

python
import re
import sys

from langsmith import Client, traceable

DATASET = "ticket-router-golden"
ALLOWED = {"billing", "access", "bug", "other"}
RULES_V1 = {
    "billing": ["invoice", "refund", "charge"],
    "access": ["password", "login", "locked"],
    "bug": ["error", "crash"],
}
RULES_V2 = {**RULES_V1, "bug": ["error", "crash", "crashes"]}
TICKETS = [
    ("I was charged twice, please refund the second invoice.", "billing"),
    ("I can't login, my account is locked.", "access"),
    ("The app crashes when I export a report.", "bug"),
    ("Login page shows an error after the update.", "bug"),
    ("How do I change my invoice address?", "billing"),
    ("Do you offer a student discount?", "other"),
    ("It says error: wrong password, but I just reset it.", "access"),
]
EXAMPLES = [{"inputs": {"ticket": text}, "outputs": {"category": label}} for text, label in TICKETS]


@traceable(run_type="chain", name="normalize")
def normalize(text: str) -> str:
    return re.sub(r"[^a-z0-9 ]", " ", text.lower())


@traceable(run_type="tool", name="match_keywords")
def match_keywords(text: str, rules: dict) -> dict:
    words = text.split()
    hits = {label: [word for word in keywords if word in words] for label, keywords in rules.items()}
    return {label: found for label, found in hits.items() if found}


def make_router(rules: dict, tie_break: list):
    """One version of the application. tie_break lists labels from most to least preferred."""

    @traceable(run_type="chain", name="route_ticket")
    def route_ticket(inputs: dict) -> dict:
        hits = match_keywords(normalize(inputs["ticket"]), rules)
        if not hits:
            return {"category": "other", "matched": []}
        best = max(hits, key=lambda label: (len(hits[label]), -tie_break.index(label)))
        return {"category": best, "matched": hits[best]}

    return route_ticket


ROUTERS = {
    "v1": make_router(RULES_V1, tie_break=["billing", "access", "bug"]),
    "v2": make_router(RULES_V2, tie_break=["bug", "billing", "access"]),
}


def category_match(outputs: dict, reference_outputs: dict) -> bool:
    return outputs["category"] == reference_outputs["category"]  # needs the reference: offline only


def valid_category(outputs: dict) -> bool:
    return outputs["category"] in ALLOWED  # needs no reference: could also run online


def run_locally() -> None:
    for version, router in ROUTERS.items():
        outputs = [router(example["inputs"]) for example in EXAMPLES]
        passed = [category_match(out, example["outputs"]) for out, example in zip(outputs, EXAMPLES)]
        valid = [valid_category(out) for out in outputs]
        marks = "".join("P" if ok else "F" for ok in passed)
        print(f"{version} category_match={sum(passed)}/{len(passed)}={sum(passed) / len(passed):.3f} "
              f"valid_category={sum(valid) / len(valid):.3f} per-example={marks}")


def create_dataset() -> None:
    client = Client()
    dataset = client.create_dataset(dataset_name=DATASET, description="Seven labelled support tickets.")
    client.create_examples(dataset_id=dataset.id, examples=EXAMPLES)


def run_experiments() -> None:
    client = Client()
    for version, router in ROUTERS.items():
        client.evaluate(router, data=DATASET, evaluators=[category_match, valid_category],
                        experiment_prefix=f"router-{version}", max_concurrency=2)


if __name__ == "__main__":
    command = sys.argv[1] if len(sys.argv) > 1 else "local"
    {"local": run_locally, "create": create_dataset, "evaluate": run_experiments}[command]()

Step 1: check the numbers locally. python3 ticket_router.py needs no account. With LANGSMITH_TRACING unset, the traced functions run as ordinary functions and nothing is sent:

text
v1 category_match=5/7=0.714 valid_category=1.000 per-example=PPFFPPP
v2 category_match=6/7=0.857 valid_category=1.000 per-example=PPPPPPF

Step 2: send it to LangSmith. Set LANGSMITH_TRACING=true and LANGSMITH_API_KEY, run python3 ticket_router.py create once, then python3 ticket_router.py evaluate. The first command stores the seven examples in a dataset. The second creates two experiments whose names start with router-v1 and router-v2. Each holds seven traces of this shape, and each root run carries two feedback records named after the evaluator functions:

text
route_ticket         chain   inputs: one ticket   outputs: category, matched keywords
├── normalize        chain
└── match_keywords   tool

Step 3: compare. On the dataset's Experiments tab, select both experiments and click Compare. With v1 as the source experiment, the view marks rows that regressed in red and rows that improved in green. The same result as a table:

#Ticket (shortened)Referencev1v2
1charged twice, refund the invoicebillingbillingbilling
2can't login, account is lockedaccessaccessaccess
3app crashes on exportbugother (fail)bug
4login page shows an errorbugaccess (fail)bug
5change my invoice addressbillingbillingbilling
6student discountotherotherother

What to notice:

  • The arithmetic. v1 passes 5 of 7, so its mean category_match is 5 / 7 = 0.714. v2 passes 6 of 7, which is 0.857.
  • The mean hides a regression. v2 fixed examples 3 and 4: it knows the word crashes, and it prefers bug when two categories tie. The same tie-break broke example 7, where error and password tie. The average rose by 0.143 while one case that used to pass now fails.
  • Two kinds of evaluator. valid_category is 1.000 for both versions. It needs no reference output, so the same rule could run as an online evaluator on production traffic, but it says nothing about correctness. category_match needs the reference label and exists only offline.
  • The child run locates the fault. In v1's trace for example 3, the match_keywords run has an empty output, because crashes is not the keyword crash. The root run only shows the wrong category.

Exercise 1 removes the regression with a third version.

Edge cases and limitations

Traces expire, and scoring them can change which ones are kept longer
The usage and billing documentation describes two retention tiers: base traces are kept for 14 days and extended traces for 180 days. After that a trace is no longer available in the UI or the API. A trace moves to the extended tier when an online evaluator with its retention setting enabled scores it, or when an automation rule with retention extension matches one of its runs, and upgrades are billed as a separate line. Anything you need permanently, such as a failure you want as a regression test, should be added to a dataset.
A very long agent run can reach the 25,000-run limit
The concepts documentation limits one trace to 25,000 runs. A batch job or a long-running agent that traces every inner step under a single root can reach that. Start a new trace for each unit of work, such as each document or each agent task, and tie them together with a shared metadata value or a thread_id so they can still be viewed as one sequence.
Short scripts and serverless functions can lose their last runs
Runs are posted in the background, and the instrumentation guide warns that a process may end before all traces are posted. The symptom is a trace that is missing or stuck without outputs for the final steps, seen only in batch scripts, tests or function-as-a-service handlers. Flush the client before the process exits.
Turning tracing off does not silence RunTree objects
LANGSMITH_TRACING controls the traceable decorator and the trace context manager. The instrumentation guide states that RunTree objects, the low-level API for building runs by hand, are not affected by that switch and always send data when posted. If a test environment must send nothing, check for manual RunTree code as well as the environment variable.
Thread-level evaluators judge late, not live
A multi-turn online evaluator waits until a thread has been idle before it scores the conversation. The documentation gives a default idle time of 10 minutes and a minimum of 2, and says runs must be less than one week old. The score therefore arrives after the user has left. Use these evaluators to monitor and to pick conversations for review, and use a guardrail in the request path when a response must be blocked before the user sees it.
A moved prompt tag does not reach running processes at once
The SDK caches pulled prompts in memory by default (up to 100 prompts, a 300 second time to live and a background refresh every 60 seconds, per the prompt management guide). After you move a tag, some processes keep serving the older commit for a short time. If a rollback has to be immediate, pull with skip_cache=True on the critical path or restart the workers, and record the commit hash in run metadata so you can tell which version produced a given trace.

When to use it, and when something simpler is enough

Use it when

  • You build with LangChain or LangGraph and want traces immediately, because two environment variables turn tracing on with no code change.
  • You want tracing, regression datasets, online scoring and human review on one data model, so that a production run can become a test case without an export step.
  • Domain experts or support staff need to review outputs or try prompt changes through a UI, without access to the code.
  • You already run pytest or Vitest in CI and want each run stored as an experiment that can be compared with the previous one.

Think twice when

  • Traces must stay inside your own infrastructure and you are not buying the Enterprise plan. The pricing page lists self-hosted and hybrid deployment under Enterprise, so an open-source tool that you host yourself, such as Langfuse or Arize Phoenix, is the better fit.
  • The application is one prompt with a handful of test cases and no production traffic yet. A test file and printed outputs are enough at that stage.
  • Your organisation has standardised on an OpenTelemetry backend and needs only spans and dashboards, not datasets, evaluators or review queues.
  • You need every raw trace kept for years. Retention is 14 or 180 days by tier, so long-term records have to be exported or stored as dataset examples.

A simpler alternative. Structured JSON logs of every model call plus a pytest file of fixed cases. This costs nothing and is easy to reason about. It stops being enough when a request has several nested steps that must be read together, when more than one person has to look at failures, or when you need scores on production traffic and not only on test cases.

Key takeaways

  • LangSmith stores each request as a trace of nested runs, and every score, whether it comes from a user, an evaluator or a reviewer, is feedback attached to a run.
  • With LangChain or LangGraph, tracing needs only environment variables. Without them you use the traceable decorator, client wrappers, a framework integration or OpenTelemetry.
  • An offline experiment runs one version of the application over a dataset that has reference outputs, and you compare it with the previous experiment example by example, not only by the mean.
  • An online evaluator scores a filtered sample of production runs with no reference output, so it detects problems but cannot prove that an answer is correct.
  • Annotation queues give human reviewers a rubric and a work list, and the runs they correct are the best source of new dataset examples.
  • Pin prompts in code by commit hash or tag, and treat what a trace contains, how long it is kept and how much traffic evaluators sample as privacy and cost decisions.

Example 1 of 5

Sending OpenAI Agents SDK traces to LangSmith through a trace processor

OpenAI and LangChainDocumented in official docs

The OpenAI Agents SDK is OpenAI's Python framework for building agents and contains no LangChain code. Its tracing guide lists LangSmith among the external tracing processors, and LangSmith's documentation describes the matching processor class, so the integration is documented by both vendors. [19][18][1][17][15]

The problem

An Agents SDK application is traced by default, but the traces go to OpenAI's own backend. A team that keeps its datasets, evaluators and review queues in LangSmith wants these agents' runs in the same place as its other applications. It does not want to rewrite the agents in another framework or add a decorator to every function.

Where this topic fits

Only the tracing layer changes. The Agents SDK already produces a trace for each agent run, with spans for agent steps, model generations, tool calls, guardrails and handoffs. A trace processor is the SDK's hook for delivering those spans somewhere. LangSmith's processor receives them and writes them as runs in a tracing project. From there, feedback, automation rules, annotation queues and datasets work on those runs exactly as they do for any other trace.

How it is applied, step by step

  1. Install the langsmith package with its openai-agents extra, and set LANGSMITH_API_KEY and, optionally, LANGSMITH_PROJECT.
  2. Create an OpenAIAgentsTracingProcessor and register it with the Agents SDK before the first agent run.
  3. Choose how to register it. set_trace_processors replaces the default processors, so traces stop going to OpenAI's backend. add_trace_processor keeps the default exporter and adds a second destination.
  4. Run the agent as usual. The SDK emits its spans and the processor forwards them to LangSmith.
  5. Open the tracing project. Each agent run is one trace whose child runs are the agent steps, model calls, tool calls and handoffs.
  6. Before production traffic flows, decide what the spans may contain, because generation and tool spans carry prompts, outputs and tool arguments by default.

Why this approach fits

A trace processor is an extension point that the framework provides for exactly this purpose, so the agent code stays untouched. The example also shows the general rule for using LangSmith without LangChain: anything that already describes the steps of your application, whether a framework's own spans, OpenTelemetry spans or functions you decorate, can be mapped to runs.

Limitation or tradeoff

The trace is only as detailed as the spans the Agents SDK emits. Work inside a tool function, such as separate retrieval and reranking steps, is not broken out unless you instrument it yourself. Replacing the default processors means OpenAI's own trace viewer no longer receives these runs, which matters if another team relies on it. The integration couples two release cycles: LangSmith's page requires langsmith>=0.3.15, and the processor has to follow changes in the SDK's span types. Sending full prompts and tool outputs to a second vendor also doubles the number of places where sensitive data is stored.

What the sources document

  • OpenAI's tracing guide says tracing is enabled by default in the Agents SDK and that the default processor exports traces and spans in batches to the OpenAI backend. [19]
  • The same guide says add_trace_processor adds an additional processor that receives traces and spans, while set_trace_processors replaces the default processors, so traces are not sent to the OpenAI backend unless a processor that does so is included. LangSmith appears in its list of external tracing processors. [19]
  • LangSmith's documentation gives the install command for the openai-agents extra, requires version 0.3.15 or later of the Python SDK, and shows an OpenAIAgentsTracingProcessor passed to set_trace_processors, after which the agent's execution flow, including its spans, is logged to LangSmith. [18]
  • The LangSmith product page describes LangSmith Observability as framework agnostic and names Python, TypeScript, Go and Java SDKs. The OpenTelemetry guide gives the OTLP endpoint https://api.smith.langchain.com/otel, authenticated with an x-api-key header. [1][17]
  • OpenAI's guide notes that generation and function spans may contain sensitive data and that trace_include_sensitive_data is True by default. The problem

Every organisation has its own labels and its own habits for applying them, and tuning a prompt for each organisation does not scale. The article calls prompts finicky and model-dependent, and fine-tuned models complex to manage. Dosu already had a natural signal: when it labels an issue wrongly, a user fixes the labels. The problem was getting that signal back into the product automatically.

Where this topic fits

Here LangSmith is part of the production data path, not only a debugging tool. Labelling requests are traced as runs. A user's correction is saved on the run that produced the labels. A rule turns corrected runs into dataset examples. At inference time Dosu looks up similar recent examples for the same organisation and puts them in the prompt as few-shot examples (see Few-Shot Prompting and Chain of Thought).

How it is applied, step by step

  1. Each auto-labelling request is traced, so there is a run with the issue as input and the chosen labels as output.
  2. When a user adds a label Dosu missed or removes one it added, a webhook saves that change as a correction on the LangSmith run.
  3. A rule picks up the corrected run and inserts it into a dataset as an example, with metadata such as the organisation id.
  4. When a new issue arrives, Dosu runs a similarity search over recent examples for that input and that organisation.
  5. The top examples are injected into the labelling prompt as few-shot examples, and the model call is traced as a new run.
  6. The cycle repeats, so each organisation's examples keep following its own labelling habits.

Why this approach fits

The correction already exists as a user action, so capturing it as feedback costs the user nothing. Feedback is attached to a specific run, which means the corrected output arrives together with the exact input that produced the wrong one, and that pair is a dataset example. A rule removes the manual step between the two. Few-shot examples then change behaviour without anyone editing the prompt text or training a model.

Limitation or tradeoff

The reported improvement of over 30% comes with no baseline, sample size or measurement method, so treat it as the team's own summary. Corrections are noisy labels: a user may change a label because the issue changed, not because the model was wrong, and a rule that adds every corrected run stores those too. Examples must be filtered by organisation at retrieval time, or one customer's issues leak into another's prompt. The similarity search runs in Dosu's pipeline; LangSmith only stores the examples. A correction can also only be attached while the run still exists, so retention has to outlast the time users take to fix labels.

4Common mistakes

  1. Comparing two experiments by their average score and nothing else.

    Why it causes problems
    A mean can rise while a case that used to pass starts failing. In the worked example the average went from 0.714 to 0.857 and ticket 7 broke. In a real product that one case may be the refund path or a safety refusal, and shipping on the average alone ships the regression.
    How to recognise it
    The comparison view shows a non-zero regression count for a feedback key even though the experiment's average improved, or a user reports a failure on an input that is already in your dataset.
    How to fix it
    Open the comparison with the current production version as the source experiment and read every regressed row before release. Keep must-pass cases in their own split and require all of them to pass, whatever the overall mean is.

  2. Sending production inputs and outputs to LangSmith without masking sensitive fields.

    Why it causes problems
    A run stores the full inputs and outputs of each step. Without masking, customer names, emails, documents and tool results are copied to another system, kept for the retention period and shown to everyone who can open the project, including reviewers in annotation queues.
    How to recognise it
    Open a recent production trace and search its inputs and outputs for an email address or account number. Check whether the client is created with an anonymizer or hide functions, or whether the hide environment variables are set.
    How to fix it
    Mask before data leaves the process. Set LANGSMITH_HIDE_INPUTS and LANGSMITH_HIDE_OUTPUTS for a blanket rule, pass an anonymizer with regex rules to the client for pattern-based redaction, or give a traced function process_inputs and process_outputs functions for field-level control.

  3. Running an LLM-as-judge online evaluator on every production run.

    Why it causes problems
    Every evaluated run costs a judge model call, so judging everything can cost as much as serving the traffic. A trace scored by an online evaluator whose retention setting is enabled is also upgraded to extended retention, which is billed separately.
    How to recognise it
    The evaluator has no filter and a sampling rate of 100%, judge spend is close to application model spend, or the invoice line for extended retention upgrades is close to the total trace count.
    How to fix it
    Filter to the runs the judge is meant for, set a sampling rate that fits the budget (exercise 2 works one out), and switch off retention extension for evaluators whose scored traces you do not need beyond the base period.

  4. Pulling a prompt by name alone in production code.

    Why it causes problems
    An identifier with no tag and no commit hash pins nothing. Whoever next saves an edit to that prompt in the UI changes what production sends to the model, with no experiment, no review and no deployment record.
    How to recognise it
    Search the code for pull_prompt calls whose identifier has no colon. Another sign is a behaviour change in production on a day when nothing was deployed.
    How to fix it
    Pull a tag such as name:production and move the tag only after the new commit has passed its experiment, or pull a commit hash when you need strict reproducibility. Write the commit hash into run metadata so every trace says which prompt version produced it.

  5. Tracing only the model call and not the request around it.

    Why it causes problems
    If only the model client is wrapped, each model call arrives as its own single-run trace. Retrieval, tool calls and post-processing are invisible, the calls of one request are not linked, and feedback or a thread_id has no root run to attach to.
    How to recognise it
    Traces in the project contain exactly one run of type llm, and one user request shows up as several unrelated traces.
    How to fix it
    Decorate the entry-point function of the request with traceable so that everything it calls nests under one root run, trace the retrieval and tool functions as well, and pass thread_id in the metadata of the root run for conversations.

Exercise 1

Add a third router version and a regression check to the worked example

CodingIntermediateAbout 40 min (estimate)Hypothetical scenario

The worked example ends with router v2 scoring higher than v1 on average while failing a ticket that v1 handled. Extend the code so that this cannot be missed.

Start from ticket_router.py exactly as it appears in the worked example. In a new file exercise1.py next to it:

  1. Add a third router version, v3, that scores 7/7 on category_match. You may change keyword lists and the tie-break order. You may not change the seven tickets or their labels.
  2. Write a new category_match that returns the dictionary form of an evaluator result, with key, score and comment. When the score is false, the comment must say which category was expected and which was produced.
  3. Write regressions(before, after). It takes two lists of results for the same examples and returns the 1-based positions of the examples that passed before and fail after.
  4. Print each version's score, the comment of every failing example, and the regressions and fixes for v1 to v2, v2 to v3 and v1 to v3.

Everything runs locally with python3 exercise1.py once the langsmith package is installed. No account or API key is needed, because the traced functions run as ordinary functions when LANGSMITH_TRACING is unset. If you have a LangSmith account, also run v3 as a third experiment and open the comparison view with the v2 experiment as the source.

Requirements

  • Router v3 passes all seven examples, with the tickets and labels unchanged.
  • The new category_match returns a dictionary with the keys key, score and comment.
  • regressions returns [7] for v1 to v2 and an empty list for v2 to v3.
  • The script runs with LANGSMITH_TRACING unset and sends nothing to LangSmith.

Expected behaviour

Running python3 exercise1.py prints:

text

   example 3: expected bug, got other
   example 4: expected bug, got access
v2: 6/7 = 0.857
   example 7: expected access, got bug

Hint 1

Read ticket 7 word by word and look for a word that is in no keyword list. One of them is strong evidence for the access category.

Hint 2

The router prefers the category with more matched keywords and uses the tie-break only when the counts are equal, so one extra keyword can decide ticket 7 without touching the tie-break order.

Hint 3

A fix from version A to version B is a regression from B to A, so one function can report both.

Show solution

Ticket 7 is "It says error: wrong password, but I just reset it." In v2 it matches one bug keyword (error) and one access keyword (password), and the tie-break prefers bug. Adding reset to the access keywords gives access two matches against one, so the tie-break is never consulted. Ticket 4, "Login page shows an error after the update.", still ties one to one and still goes to bug.

python
from ticket_router import EXAMPLES, ROUTERS, RULES_V2, make_router

RULES_V3 = {**RULES_V2, "access": ["password", "login", "locked", "reset"]}
ALL_ROUTERS = {**ROUTERS, "v3": make_router(RULES_V3, tie_break=["bug", "billing", "access"])}


def category_match(outputs: dict, reference_outputs: dict) -> dict:
    expected, actual = reference_outputs["category"], outputs["category"]
    return {
        "key": "category_match",
        "score": actual == expected,
        "comment": "ok" if actual == expected else f"expected {expected}, got {actual}",
    }


def results(router) -> list:
    return [category_match(router(example["inputs"]), example["outputs"]) for example in EXAMPLES]


def regressions(before: list, after: list) -> list:
    """1-based positions of examples that passed before and fail after."""
    pairs = zip(before, after)
    return [index for index, (old, new) in enumerate(pairs, start=1) if old["score"] and not new["score"]]


def fixes(before: list, after: list) -> list:
    return regressions(after, before)


if __name__ == "__main__":
    scored = {version: results(router) for version, router in ALL_ROUTERS.items()}
    for version, rows in scored.items():
        passed = sum(row["score"] for row in rows)
        print(f"{version}: {passed}/{len(rows)} = {passed / len(rows):.3f}")
        for index, row in enumerate(rows, start=1):
            if not row["score"]:
                print(f"   example {index}: {row['comment']}")
    for old, new in [("v1", "v2"), ("v2", "v3"), ("v1", "v3")]:
        print(f"{old} -> {new}: regressions {regressions(scored[old], scored[new])}, "
              f"fixes {fixes(scored[old], scored[new])}")

The output is the block shown under expected behaviour. Three points to take from it:

  • The dictionary form of the evaluator does in code what the comparison view does in the UI. In LangSmith the comment is stored with the feedback, so a failed row explains itself without anyone opening the trace.
  • regressions is the release gate that the mean cannot be. v2 would have failed a rule of "no regressions against the previous version" even though its average was higher.
  • v3 reaches 7/7 on seven examples, which proves little. The keyword reset will also match "reset my invoice settings". The honest next step is to add tickets like that to the dataset, which is how real datasets grow: every surprising failure becomes an example.

To run it in LangSmith, pass ALL_ROUTERS["v3"] and the new category_match to client.evaluate with experiment_prefix="router-v3", then compare the v2 and v3 experiments with v2 as the source.

1. Judge sampling rate. $30 / $0.004 = 7,500 runs a day. 7,500 / 30,000 = 0.25, so the evaluator samples 25% of matching runs.
