Planning and Task Decomposition

Planning is the step in which an agent writes out the subtasks a goal requires, and their order, before or while it acts. Task decomposition is the splitting itself: turning one large request into smaller tasks, each of which can be run, checked and retried separately.

1Overview

Why it matters

An agent that decides one step at a time works well on short tasks and badly on long ones. It pays for a model call before every tool call. It cannot run independent steps side by side, because it never sees them together. After thirty steps it can lose track of what the user asked for. A plan addresses all three by making the structure of the task explicit: what has to be done, what depends on what, and what is already finished.

Plans bring their own failure. A plan is a prediction, and tools time out, searches come back empty and assumptions turn out to be wrong. An agent that follows a stale plan to the end produces a confident answer built on a step that never worked. Anyone who builds agents for research, coding or work across several systems has to decide how far to plan ahead, who carries the plan out, what form the plan takes and when to discard it. Those four decisions set the cost, the latency and the reliability of the system.

Key terms

Plan
An explicit list of the steps an agent intends to take, written down before those steps are carried out.
Task decomposition
Breaking one goal into smaller subtasks that can each be executed and checked separately.
Interleaved reasoning
Deciding one step at a time, with each decision made after reading the result of the previous step. ReAct is the standard example.
Plan-and-execute
A design in which one model call writes a multi-step plan first, and the steps are then carried out without asking that model what to do after each one.
Planner
The model call or agent that turns the goal into a plan.
Executor
The function, tool, smaller model or sub-agent that carries out one planned step. Also called a worker.
Solver
The final model call that reads the plan and the collected results and writes the answer. Some systems call it a joiner, and let it ask for more work instead of answering.
Task list
A plan stored as ordered items, each with a status such as pending, in progress or completed.
DAG plan
A plan stored as a directed acyclic graph, in which each task lists the tasks it depends on, so tasks that do not depend on each other can run at the same time.
Replanning
Revising the remaining part of a plan after a step fails, progress stalls or new information arrives.

2Explanation

Introduction

In The Agent Loop the model chose one action, read the result and chose again. In Few-Shot Prompting and Chain of Thought you saw that asking a model to reason step by step before it answers improves multi-step answers. Planning joins the two ideas. The model reasons about the whole task first and writes the steps down, and the steps are then carried out with tools.

You already plan this way. To cook a dinner with three dishes, you do not decide your next movement from scratch every thirty seconds. You list the dishes, notice that the rice can boil while you chop vegetables, and see that the sauce cannot start until the stock is ready. If the oven turns out to be broken, you do not cancel dinner, and you do not carry on as if it worked. You keep what is already cooked and change the rest of the list.

That paragraph contains every idea in this lesson:

  • Decomposition. The goal becomes small tasks that can each be done and checked.
  • Dependencies. Some tasks must wait for others, and the rest can overlap.
  • A split of roles. Whoever wrote the list does not have to be the one stirring the pot.
  • Replanning. When a step fails, finished work is kept and the remaining plan is revised.

Agent builders have names for these choices. Interleaved reasoning means deciding step by step, as ReAct does. Plan-and-execute means writing the plan first. A planner-executor split gives the two jobs to different model calls or different agents. The plan itself is stored as a task list or as a DAG (a directed acyclic graph, which records what depends on what). The DeepLearning.AI course Agentic AI (opens in a new tab) lists planning as one of four agentic design patterns, next to reflection, tool use and multi-agent collaboration.

The lesson explains each choice and what it costs, builds a small plan executor in plain Python, and then looks at five research and production systems that made these choices in different ways.

How it works

Deciding as you go, or deciding first

An interleaved loop makes one model call per action. A task with nnn tool calls takes n+1n + 1n+1 model calls, and each call re-reads everything so far. The LangChain team's write-up on planning agents (opens in a new tab) names two costs of this design: it needs a model call for every tool invocation, and the model plans for only one sub-problem at a time, so it is never forced to reason about the whole task.

Plan-and-execute moves the reasoning to the front. In pseudocode:

text
plan    = planner(task)                      # one model call: all the steps
results = [execute(step) for step in plan]   # tools, code or smaller models
answer  = solver(task, plan, results)        # one model call: write the answer

The smallest version needs no tools. Plan-and-Solve prompting (opens in a new tab) (Wang and colleagues, 2023) replaces the zero-shot chain-of-thought trigger with an instruction to first understand the problem and devise a plan, and then carry the plan out step by step. The authors designed it to reduce missing-step errors, in which step-by-step reasoning skips a step the problem needs.

The planner-executor split

A plan-first system has three roles, which may be three prompts for one model or three different models:

  • The planner sees the goal and the tool descriptions and writes the plan. It is usually the strongest model in the system.
  • An executor carries out one step. It can be a plain function call, a smaller model or a sub-agent with its own loop.
  • The solver reads the plan and the results and writes the answer, or reports that more work is needed.

The split pays in three ways. Cost: the LangChain write-up notes that sub-tasks can go to smaller, domain-specific models while the larger model is called only for planning, replanning and the final response. Context: each executor reads its own step, not the whole transcript. Inspection: a plan is an artefact that a program can validate and a person can read before anything runs. Anthropic's guide to building agents (opens in a new tab) counts explicitly showing an agent's planning steps as part of keeping a system transparent.

What crosses the boundary matters most. Anthropic's account of its multi-agent research system (opens in a new tab) reports that vague subtask descriptions led subagents to duplicate each other's work, and that each subtask needs an objective, an output format, guidance on tools and sources, and clear task boundaries. Write every plan step as a brief for someone who has not seen the rest of the conversation. Orchestrator-Workers covers delegation in depth.

Two shapes of plan: the task list and the DAG

A task list is a sequence of items with a status:

text
[x] 1. Read the failing test
[>] 2. Find where the date string is parsed
[ ] 3. Fix the parser
[ ] 4. Run the test suite

A task list is often used inside an interleaved loop. The agent still decides step by step, but it keeps the list through a tool and updates it as it works. That shows progress to the user and keeps the goal in view. The team behind the Manus agent describes this effect (opens in a new tab): their agent rewrites a to-do file as it goes, which recites the objectives into the end of the context. A typical Manus task takes about 50 tool calls, the article says, which is long enough for an agent to drift from its goal.

A DAG plan adds dependencies. Each task names the tasks whose results it needs:

json
[
  {"id": "t1", "tool": "search", "args": {"query": "Microsoft market cap"}, "deps": []},
  {"id": "t2", "tool": "search", "args": {"query": "Apple market cap"}, "deps": []},
  {"id": "t3", "tool": "compare", "args": {"a": "$t1", "b": "$t2"}, "deps": ["t1", "t2"]}
]

Results travel by placeholder. ReWOO (opens in a new tab) writes #E1 for the evidence from step 1, and LLMCompiler (opens in a new tab) writes $1. Here t1 and t2 can run together and t3 must wait. The executor needs no model call to work that out. It repeatedly takes every task whose dependencies are finished, which gives a sequence of waves. The same procedure catches an impossible plan: if tasks remain and none is ready, the dependencies form a cycle.

What planning saves

Use the cost model from The Agent Loop: the first call sends bbb tokens and each completed step adds ddd tokens of history. An interleaved loop with nnn tool calls makes n+1n + 1n+1 model calls, each longer than the last:

Tinterleaved(n)=(n+1) b+d n(n+1)2T_{\text{interleaved}}(n) = (n+1)\,b + d\,\frac{n(n+1)}{2}Tinterleaved​(n)=(n+1)b+d2n(n+1)​

A plan-first run makes one planner call of bbb tokens and one solver call that reads all nnn results. A replan made after mim_imi​ completed steps reads those mim_imi​ results:

Tplan(n)=2b+n d+∑i(b+mi d)T_{\text{plan}}(n) = 2b + n\,d + \sum_{i} \left(b + m_i\,d\right)Tplan​(n)=2b+nd+i∑​(b+mi​d)

With b=1000b = 1000b=1000, d=500d = 500d=500 and 10 tool calls, the interleaved loop sends 38,500 input tokens. The plan-first run sends 7,000, or 10,500 with one replan after step 5.

Measured results point the same way. The ReWOO authors report about 9,795 tokens per HotpotQA question for their ReAct baseline against about 1,986 for ReWOO, with accuracy of 40.8 and 42.4. The LLMCompiler authors report latency speedups of up to 3.7 times and cost savings of up to 6.7 times against ReAct. Both used 2023 models, so treat the direction as the lesson, not the exact ratios.

The formula also carries a warning. Replan after each of the first n−1n - 1n−1 steps and the sum works out to exactly Tinterleaved(n)T_{\text{interleaved}}(n)Tinterleaved​(n). A plan saves only as much as you are willing not to look.

Replanning

A plan is a guess made before the evidence arrived. Four signals should trigger a new one:

  1. A step fails. A tool raises an error or returns nothing usable.
  2. Progress stalls. Nothing raises an error, but nothing advances. Magentic-One checks after every step whether the team is looping or making progress, and rewrites its plan when a stall counter passes a threshold.
  3. A checkpoint arrives. The smolagents library has a planning_interval setting (opens in a new tab): every few steps the agent takes a step with no tool call, in which the model updates the facts it knows and what to do next.
  4. A person edits the plan. In Claude Code's plan mode (opens in a new tab) the agent researches and writes a plan without editing source files, and the user approves it, edits it or asks for changes.

A replanner needs the goal, the current plan, the results of the completed steps and the exact error. It should return only the work that remains. Three rules keep replanning safe:

  • Keep finished work. Anthropic's research-system article notes that restarting from the beginning after an error is expensive and frustrating, so its system resumes from where the error occurred.
  • Retry before you replan. A timeout may need the same step again. A missing capability needs a different plan.
  • Cap the replans and return a distinct status when the cap is reached, exactly as a step limit does for a loop.

Worked example: A DAG plan for a two-supplier price comparison, run in waves, with one failed step and one replan

The task: which supplier is cheaper for 40 units of part P-7, and by how much in USD? Northwind quotes in EUR and charges 35 USD shipping. Tokai quotes in JPY and charges 60 USD shipping.

The planner's answer is written into the script as PLAN: two price lookups, two exchange rates, two cost calculations and one subtraction. The planner and the replanner are scripted so that everyone gets identical output. The validation, scheduling, execution and replanning are real. One tool is broken on purpose: the Tokai quote API times out.

Save this as plan_executor.py. It needs only the Python standard library (3.9 or later).

python
MAX_REPLANS = 2
SECONDS = {"get_quote": 2.0, "get_catalog_price": 1.0, "get_fx_rate": 0.5, "landed_cost": 0.1, "subtract": 0.1}
QUOTES = {("northwind", "P-7"): 12.50}  # the Tokai quote API is down today
CATALOG = {("tokai", "P-7"): 1950.0}
USD_PER = {"EUR": 1.10, "JPY": 0.0065}


def get_quote(supplier, sku):
    if (supplier, sku) not in QUOTES:
        raise RuntimeError(f"{supplier} quote API timed out; try get_catalog_price")
    return QUOTES[(supplier, sku)]


TOOLS = {
    "get_quote": get_quote,
    "get_catalog_price": lambda supplier, sku: CATALOG[(supplier, sku)],
    "get_fx_rate": lambda currency: USD_PER[currency],
    "landed_cost": lambda units, price, rate, shipping: round(units * price * rate + shipping, 2),
    "subtract": lambda a, b: round(a - b, 2),
}

PLAN = [  # the planner's output: "deps" are the edges of the DAG, "$t1" means the result of t1
    {"id": "t1", "tool": "get_quote", "args": {"supplier": "northwind", "sku": "P-7"}, "deps": []},
    {"id": "t2", "tool": "get_quote", "args": {"supplier": "tokai", "sku": "P-7"}, "deps": []},
    {"id": "t3", "tool": "get_fx_rate", "args": {"currency": "EUR"}, "deps": []},
    {"id": "t4", "tool": "get_fx_rate", "args": {"currency": "JPY"}, "deps": []},
    {"id": "t5", "tool": "landed_cost", "args": {"units": 40, "price": "$t1", "rate": "$t3", "shipping": 35}, "deps": ["t1", "t3"]},
    {"id": "t6", "tool": "landed_cost", "args": {"units": 40, "price": "$t2", "rate": "$t4", "shipping": 60}, "deps": ["t2", "t4"]},
    {"id": "t7", "tool": "subtract", "args": {"a": "$t5", "b": "$t6"}, "deps": ["t5", "t6"]},
]


def waves(plan, done):
    """Group unfinished tasks into waves. A task is ready when its deps are finished."""
    known = {task["id"] for task in plan} | set(done)
    for task in plan:
        if task["tool"] not in TOOLS or not set(task["deps"]) <= known:
            raise ValueError(f"invalid task {task['id']}")
    finished, remaining, result = set(done), [t for t in plan if t["id"] not in done], []
    while remaining:
        ready = [t for t in remaining if set(t["deps"]) <= finished]
        if not ready:
            raise ValueError("plan has a dependency cycle")
        result = [*result, ready]
        finished = finished | {t["id"] for t in ready}
        remaining = [t for t in remaining if t["id"] not in finished]
    return result


def run_task(task, results):
    args = {name: results[value[1:]] if str(value).startswith("$") else value
            for name, value in task["args"].items()}
    return TOOLS[task["tool"]](**args)


def execute(plan, results):
    """Run the plan wave by wave. Stop after the first wave in which a task fails."""
    clock = 0.0
    for wave in waves(plan, results):
        failures = {}
        for task in wave:  # independent, so a real executor runs them concurrently
            try:
                results = {**results, task["id"]: run_task(task, results)}
            except Exception as error:
                failures = {**failures, task["id"]: str(error)}
        clock += max(SECONDS[task["tool"]] for task in wave)
        print("wave", [f"{t['id']}={results.get(t['id'], 'FAILED')}" for t in wave])
        if failures:
            return results, failures, clock
    return results, {}, clock


def scripted_replanner(plan, results, failures):
    """Stands in for a model call that sees the plan, the results so far and the errors."""
    return [{**task, "tool": "get_catalog_price"} if task["id"] in failures else task for task in plan]


def plan_and_execute(plan, replanner):
    results, model_calls, seconds = {}, 1, 0.0  # 1 = the planner call
    for attempt in range(MAX_REPLANS + 1):
        results, failures, clock = execute(plan, results)
        seconds += clock
        if not failures:  # +1: the solver call that writes the answer
            return {"status": "finished", "results": results,
                    "model_calls": model_calls + 1, "tool_seconds": round(seconds, 1)}
        if attempt < MAX_REPLANS:
            print("replan after", failures)
            plan, model_calls = replanner(plan, results, failures), model_calls + 1
    return {"status": "replan_limit", "results": results,
            "model_calls": model_calls, "tool_seconds": round(seconds, 1)}


if __name__ == "__main__":
    print(plan_and_execute(PLAN, scripted_replanner))
    print(plan_and_execute(PLAN, lambda plan, results, failures: plan)["status"])

What to notice:

  • Waves. waves found four tasks with no dependencies and released them together. A wave takes as long as its slowest task, so the tools took 2.0 + 1.0 + 0.1 + 0.1 = 3.2 simulated seconds. One at a time, the same eight calls take 2 + 2 + 0.5 + 0.5 + 1 + 0.1 + 0.1 + 0.1 = 6.3 seconds.
  • Replanning kept finished work. t2 failed and the replanner swapped its tool. t1, t3 and t4 did not run again, and t5 no longer waited for t2.
  • The arithmetic. Northwind: 40 × 12.50 × 1.10 + 35 = 585.00. Tokai: 40 × 1950 × 0.0065 + 60 = 567.00. Tokai is cheaper by 18.00 USD. That rests on a list price, which the solver should say.
  • Model calls. Planner, replanner and solver make 3. An interleaved loop needs 9: one before each of the eight tool calls and one to answer.
  • The cap. The last line passes a replanner that returns the plan unchanged. t2 fails three times and the run ends as replan_limit without guessing an answer.

With a real model, the planner returns the PLAN list as JSON (see Structured Outputs) and the replanner receives the plan, results and failures.

Edge cases and limitations

The plan needs facts that only execution can reveal
When later steps depend on what earlier steps find, such as which file holds the bug or what a page links to, a planner that writes every step up front has to guess. The ReWOO authors note that relying fully on reasoning in advance becomes impractical when little is known about the environment. The sign is a plan with vague steps ("fix the problem found") or with invented file names and ids. Plan only as far as you can see: list the discovery steps, run them, then replan with the results. LLMCompiler does this in its Game of 24 experiment, where the planner plans one iteration at a time.
A placeholder carries more, or less, than the next step expects
DAG plans pass results by reference. If a search returns three paragraphs and the next task expects one number, the executor delivers three paragraphs into a numeric argument. Nothing in the plan format prevents this. Give tools typed, structured outputs, insert an extraction step between a search and a calculation, and pass whole values as the worked example does instead of splicing text into a string. Check the type before the dependent task runs and treat a mismatch as a failed step.
A failure in a parallel wave leaves its siblings finished
When one task in a wave fails, the others have already run and may have changed something: a row written, a message sent. Tasks are released together because their inputs are independent, which says nothing about their side effects. Tell the replanner exactly which tasks succeeded, keep tools with side effects idempotent (safe to repeat) or out of parallel waves, and never rerun a completed task just because the plan was revised.
Nothing fails, yet nothing progresses
A search that returns irrelevant pages is a successful tool call. A plan executor that only reacts to exceptions will finish every step and hand the solver useless evidence. Magentic-One handles this with a progress check after every step that asks whether the request is satisfied, whether the team is looping and whether progress is being made, and it replans when a stall counter passes a threshold. If you cannot afford a model call per step, check cheap signals in code: empty results, repeated arguments, or outputs that fail a schema.
The checklist can cost more than it gives
A task list is not free. Its tool definitions and reminders occupy context on every call. The Claude Code tools reference says that on newer models Claude keeps track of multi-step work without a written checklist, and it provides the task tools by default only on older model families. Test your own agent with and without the list on your own tasks before assuming it helps, and keep the list when people or other agents need to read the progress.

When to use it, and when something simpler is enough

Use it when

  • The task takes many tool calls and most of them can be predicted from the request alone, for example collecting the same five facts about each of eight companies.
  • Several steps do not depend on each other, so a dependency graph lets them run in parallel and shortens the wait.
  • A person or a policy check must approve the approach before anything slow, expensive or irreversible happens. A plan is something they can read in a minute.
  • The work will outlast one context window or involve several agents, so the record of what is done and what remains has to live outside any one conversation.
  • Steps can go to cheap executors such as plain functions or smaller models, with a stronger model kept for planning and the final answer.

Think twice when

  • The task needs one or two tool calls. A planner call and a solver call would double the cost and add nothing.
  • Each step depends on what the previous step discovered, as in debugging or exploring an unfamiliar website. The plan would be rewritten after every step, which is an interleaved loop with extra overhead.
  • The steps are the same every time. Hard-code them as a prompt chain; no model needs to plan them.
  • You have no way to detect a failed or useless step. Without that signal a plan only delivers the wrong answer faster.

A simpler alternative. A plain interleaved loop with a step limit, or a fixed prompt chain when the steps never vary. The loop stops being enough when traces show the agent repeating searches, answering before every part of the request is done, or waiting on calls that could have run together. The first fix to try is the cheapest one: ask for a short plan at the start of the same prompt before adding a separate planner.

Key takeaways

  • An interleaved loop decides after every observation, while plan-and-execute decides once up front, which cuts model calls from one per tool call to about two plus one per replan.
  • A planner-executor split works only when each plan step is a complete brief with an objective, an expected output, the tools to use and a clear boundary.
  • A task list tracks status in order; a DAG plan also records dependencies, so an executor can run independent tasks in parallel and reject an impossible plan without a model call.
  • Every plan is a guess, so an executor needs replanning triggers (a failed step, stalled progress, a checkpoint or a human edit), must keep finished work, and must cap the number of replans.
  • Replanning after every step costs as much as the interleaved loop, so planning pays only on tasks whose structure can be predicted before acting.

Example 1 of 5

LLMCompiler planning a dependency graph of function calls and running them in parallel

UC Berkeley, ICSI and LBNLDocumented in a paper

An LLM Compiler for Parallel Function Calling (Kim and colleagues, first posted in December 2023) presents a research system for function calling. Section 3 of the paper describes its planner, and the LangChain team's article on planning agents describes an implementation of the design in LangGraph. [4][5]

The problem

ReAct-style function calling runs one call at a time, with a model call before each. For a question that compares two companies or checks eight films, the calls do not depend on each other, so the waiting is unnecessary. The authors also report accuracy problems that come from deciding step by step. On HotpotQA, ReAct repeated the same call when a Wikipedia search returned too little. On the Movie Recommendation benchmark it often gave its answer before searching for all eight films.

Where this topic fits

Planning is the first of three components. The Function Calling Planner turns the question into tasks with dependencies. The Task Fetching Unit, which is ordinary code, releases each task once its inputs exist and fills in the placeholders. The Executor runs the released tasks concurrently. If the results are not enough to answer, they go back to the planner for a new set of tasks.

How it is applied, step by step

  1. The planner model receives the question, the tool definitions and optional examples, and writes the tasks to run with their arguments. A task that needs an earlier result refers to it with a placeholder such as $1.
  2. Together the tasks and their placeholders form a directed acyclic graph of dependencies.
  3. The Task Fetching Unit sends every task whose dependencies are resolved to the executor and replaces each placeholder with the real output of the earlier task. This step needs no model call.
  4. The executor runs the dispatched tasks concurrently using the tools the developer supplied, which can be simple functions or other agents.
  5. When the right next step depends on intermediate results, those results are sent back to the planner, which produces a new set of tasks. The cycle repeats until the final result is ready.
  6. In the LangGraph implementation described by the LangChain team, a model step called the joiner makes that choice: answer now, or pass the progress back for replanning.

Why this approach fits

The structure of these questions can be read from the question itself: two searches and a calculation, or eight searches and a choice. When the structure is visible in advance, deciding it once is cheaper than rediscovering it one call at a time, and a dependency graph is the smallest representation that tells an executor which calls may run together. Listing all the calls up front also removes the temptation to stop early, because the plan names all eight searches before any result arrives.

Limitation or tradeoff

The planner is overhead on every query. The paper notes that it blocks the other components until its output is ready, and reports that LLMCompiler ran slightly slower than ReAct on the WebShop benchmark for that reason. A plan fixed up front suits questions whose calls are predictable. When the path depends on results, the system falls back to replanning, which adds planner calls. In the authors' own failure analysis, 8% of LLMCompiler's failures were attributed to the planner, 64% to the executor and 28% to the final output step, so a good plan does not fix weak tools. The reported gains are against ReAct baselines built on 2023 models.

  • The planner identifies the necessary tasks, their input arguments and their inter-dependencies, forming a directed acyclic graph. A task that depends on an earlier task carries a placeholder variable such as $1, which is later substituted with the actual output of that task. [4]
  • The Task Fetching Unit fetches tasks to the Executor as soon as they are ready using a greedy policy, and the paper states that it can be implemented with a simple fetching and queuing mechanism without a dedicated LLM. [4]
  • When replanning, intermediate results are sent back from the Executor to the Function Calling Planner, which generates a new set of tasks with their dependencies, and the cycle continues until the desired final result is achieved. [4]
  • The abstract reports latency speedup of up to 3.7 times, cost savings of up to 6.7 times and accuracy improvement of up to about 9% compared with ReAct. On the Movie Recommendation benchmark the authors observed that around 85% of ReAct examples stopped before completing all 8 movie searches. [4]

Example 2 of 5

Magentic-One: an orchestrator that keeps two ledgers and replans when progress stalls

Microsoft ResearchDocumented in a paper

Magentic-One is a multi-agent system from Microsoft Research for open-ended web and file tasks, described in a Microsoft Research article and a technical report from November 2024. Its design is now offered as the Magentic orchestration in Microsoft Agent Framework, whose documentation is dated September 2026. [11][12][13]

The problem

Open-ended tasks, such as finding a figure on the web, downloading a file and analysing it, take many steps across different tools. A first plan is often wrong: a page will not load, a login fails, a search finds nothing useful. The system needs a plan that several specialised agents can follow, and a way to notice that the plan has stopped working even when no single step raises an error.

Where this topic fits

Planning belongs to one agent, the Orchestrator. It writes the plan, hands each step to a specialist (WebSurfer, FileSurfer, Coder or ComputerTerminal) and checks progress after every step. The specialists are the executors and do not plan the overall task. Replanning happens in the Orchestrator's outer loop, which runs again whenever its inner loop stalls.

How it is applied, step by step

  1. The Orchestrator begins its outer loop by filling a task ledger with given or verified facts, facts to look up, facts to derive and educated guesses. It then writes a plan in natural language that assigns steps to agents.
  2. In the inner loop it fills a progress ledger each round by answering five questions: is the request satisfied, is the team looping, is forward progress being made, which agent should speak next, and what instruction should that agent receive.
  3. The chosen agent carries out the instruction, for example browsing a page, reading a file or running code, and reports back.
  4. If the progress ledger shows a loop or a lack of progress, a stall counter goes up. While the counter stays within its threshold, the inner loop continues with the next team action.
  5. When the counter passes the threshold, the Orchestrator leaves the inner loop, reflects on what went wrong, updates the task ledger with what it has learned and revises the plan.
  6. When the progress ledger says the request is satisfied, the Orchestrator produces the final answer from the team's work.

Why this approach fits

The two ledgers separate two questions that a single transcript blurs: what do we know and intend (the task ledger), and is the current step working (the progress ledger). Asking the progress questions every round gives the system a failure signal that does not depend on an exception. Open-ended web tasks need that, because a page full of irrelevant text is still a successful tool call. Keeping all planning in one agent also lets the specialists stay simple.

Limitation or tradeoff

Every round costs an extra orchestrator model call for the progress ledger, on top of the specialist's own work. The technical report describes the plan as a hint that agents are not required to follow exactly, so it cannot be validated or run in parallel the way a DAG can. The Agent Framework documentation says it is untested how well the pattern performs outside the original Magentic-One design. The Microsoft Research article also reports that during development a misconfiguration led agents to repeat failed logins until a test site suspended the account, which shows why a system that replans on its own still needs limits and human oversight.

What the sources document

  • The Microsoft Research article describes the Orchestrator as the lead agent responsible for task decomposition and planning, directing other agents in executing subtasks, tracking overall progress and taking corrective actions as needed. [11]
  • The technical report states that the task ledger is pre-populated with given or verified facts, facts to look up, facts to derive and educated guesses, and that the plan is expressed in natural language as a sequence of steps assigned to individual agents. [12]
  • The progress ledger answers five questions: whether the request is fully satisfied, whether the team is looping or repeating itself, whether forward progress is being made, which agent should speak next, and what instruction or question to give that agent. [12]
  • When the stall counter exceeds its threshold, which the report gives as at most 2 in the authors' experiments, the Orchestrator breaks from the inner loop, reflects on what may have gone wrong, updates the task ledger and revises the original plan. [12]
  • The Agent Framework documentation states that consecutive non-progressing rounds increment a stall counter, that exceeding the configured maximum triggers an automatic reset and replan, and that optional plan review lets a person approve or revise the plan. Plan review is off by default in Python and on by default in .NET. [13]

Example 5 of 5

Cursor running hundreds of coding agents with planners, workers and a judge

CursorDocumented in an engineering article

Scaling long-running autonomous coding, published on Cursor's blog in January 2026, describes experiments in which many coding agents worked on a single project for weeks, including building a web browser from scratch. [18]

The problem

One agent is slow on a very large project, so the team wanted many agents working on the same codebase at once. Their first designs gave every agent the same role and let the agents coordinate among themselves, first through a shared file with locks and then with optimistic concurrency control. The post reports that locking cut twenty agents to the throughput of two or three, and that without a hierarchy the agents avoided hard tasks and made small, safe changes.

Where this topic fits

Decomposition became a dedicated role. Planner agents own the question of what should be done next and turn it into tasks. Worker agents each own one task. A judge decides at the end of each cycle whether to continue. This is the planner-executor split applied to a whole team instead of a single request, with the set of open tasks acting as the plan.

How it is applied, step by step

  1. Planner agents continuously explore the codebase and create tasks.
  2. A planner can spawn sub-planners for specific areas, which makes planning itself parallel and recursive.
  3. Worker agents pick up a task and focus entirely on finishing it. They do not coordinate with other workers or consider the wider project, and they push their changes when done.
  4. At the end of each cycle, a judge agent determines whether to continue.
  5. The next iteration then starts fresh, and the cycle repeats.

Why this approach fits

Separating the roles removes both problems of the flat design. Workers no longer negotiate over shared state, so adding workers adds throughput. And one role is explicitly responsible for the hard question of what to do next, so that question is no longer avoided. The single-request case in this lesson has the same structure: a plan gives each executor a bounded job and keeps the overall goal in one place.

Limitation or tradeoff

The post says the problem is not solved. Planners should wake up when their tasks complete to plan the next step, agents occasionally run for far too long, and periodic fresh starts are still needed to combat drift and tunnel vision. The team removed an integrator role built for quality control and conflict resolution because it created more bottlenecks than it solved, and notes that too much structure makes a system fragile. The scale is also unusual: the post describes hundreds of agents running concurrently and trillions of tokens spent on a single goal, which few projects can afford.

  • After the team moved to optimistic concurrency control, it found that with no hierarchy the agents became risk-averse, avoided difficult tasks and made small, safe changes, and that no agent took responsibility for hard problems. [18]
  • In the revised design, planners continuously explore the codebase and create tasks and can spawn sub-planners. A judge agent determines at the end of each cycle whether to continue, and the next iteration starts fresh. [18]
  • The post reports that the agents building a web browser ran for close to a week and wrote over 1 million lines of code across 1,000 files. [18]
  • The open problems the post lists are that planners should wake up when their tasks complete, that agents occasionally run for far too long, and that periodic fresh starts are still needed to combat drift and tunnel vision. [18]

4Common mistakes

  1. Running the rest of the plan after one of its steps has failed.

    Why it causes problems
    Tasks that depended on the failed step receive an error message or nothing at all as their input. The solver then writes a confident answer from evidence that was never collected.
    How to recognise it
    A final answer that cites a figure no tool returned, or a trace in which a failed task is followed by its dependents running anyway.
    How to fix it
    Stop at the end of the wave in which the failure happened, mark the dependent tasks as blocked, and call the replanner with the exact error. Return a distinct status if no replan succeeds.

  2. Writing plan steps as titles instead of briefs.

    Why it causes problems
    An executor that has not seen the conversation must guess the scope of a step such as "research competitors". Two executors cover the same ground, a third returns a different format, and the solver cannot combine the results. Anthropic reports exactly this duplication with vague subtask descriptions.
    How to recognise it
    Overlapping results from different steps, outputs in inconsistent formats, or executors that ask what the step means.
    How to fix it
    Give every step an objective, the expected output format, the tools it may use and a boundary that says what belongs to other steps.

  3. Planning every step of a task whose later steps depend on what the early steps find.

    Why it causes problems
    The planner has to invent details it cannot know yet, such as file names, record ids or URLs. Steps built on invented arguments fail, or succeed on the wrong object.
    How to recognise it
    Plan arguments that the planner had no way of knowing, and runs in which almost every step is followed by a replan.
    How to fix it
    Plan the discovery steps only, run them, and replan with the results. If every step is a discovery step, use an interleaved loop for that part of the task.

  4. Replanning from scratch and running completed steps again.

    Why it causes problems
    The run pays twice for work it already has, and any tool with a side effect acts twice: two emails, two orders, two database rows.
    How to recognise it
    The same tool call with the same arguments appears in the trace both before and after a replan.
    How to fix it
    Pass the completed results to the replanner, execute only tasks that have no result yet, and make tools with side effects safe to repeat.

  5. Letting the replanner run without a limit.

    Why it causes problems
    A replanner that returns the same failing plan costs a planner call per attempt and never finishes. Unlike a loop with a step limit, nothing stops it.
    How to recognise it
    Consecutive plans in the trace that are identical or that alternate between two versions, and runs that end only on a timeout.
    How to fix it
    Cap the number of replans, as the worked example does and as Microsoft Agent Framework's Magentic builder does with its maximum number of plan resets. Compare each new plan with the previous one, and return a status such as replan_limit so the caller can tell an abandoned run from a finished one.

  6. Executing a DAG plan without validating it first.

    Why it causes problems
    A task that uses another task's result but does not list it as a dependency is scheduled too early and fails on a missing value. A cycle leaves tasks that can never start, and a naive executor waits forever.
    How to recognise it
    Lookup errors in the first wave, or an executor that stops making progress with tasks still pending.
    How to fix it
    Before running anything, check that every tool exists, every dependency id exists, every placeholder id is listed in the task's dependencies and the graph has no cycle. Send validation errors back to the planner.

SECONDS = {"search_flights": 3.0, "get_weather": 0.5, "pick_area": 1.0, "search_hotels": 2.0, "summarize": 0.5}

TRIP_PLAN = [
    {"id": "a", "tool": "search_flights", "args": {"to": "Lisbon"}, "deps": []},
    {"id": "b", "tool": "get_weather", "args": {"city": "Lisbon"}, "deps": []},
    {"id": "c", "tool": "pick_area", "args": {"weather": "$b"}, "deps": ["b"]},
    {"id": "d", "tool": "search_hotels", "args": {"area": "$c"}, "deps": ["c"]},
    {"id": "e", "tool": "summarize", "args": {"flights": "$a", "hotels": "$d"}, "deps": ["a", "d"]},
]


def placeholders(task):
    """Ids that the task's arguments refer to with a leading dollar sign."""
    return {value[1:] for value in task["args"].values() if isinstance(value, str) and value.startswith("$")}


def validate_plan(plan, tools):
    ids = [task["id"] for task in plan]
    if len(ids) != len(set(ids)):
        raise ValueError("duplicate task id")
    for task in plan:
        if task["tool"] not in tools:
            raise ValueError(f"{task['id']}: unknown tool {task['tool']}")
        missing = set(task["deps"]) - set(ids)
        if missing:
            raise ValueError(f"{task['id']}: unknown dependency {sorted(missing)}")
        hidden = placeholders(task) - set(task["deps"])
        if hidden:
            raise ValueError(f"{task['id']}: placeholder {sorted(hidden)} is not listed in deps")
    waves(plan)  # raises on a cycle


def waves(plan):
    finished, remaining, result = set(), list(plan), []
    while remaining:
        ready = [task for task in remaining if set(task["deps"]) <= finished]
        if not ready:
            raise ValueError("plan has a dependency cycle")
        result = [*result, ready]
        finished = finished | {task["id"] for task in ready}
        remaining = [task for task in remaining if task["id"] not in finished]
    return result


def sequential_time(plan, seconds):
    return sum(seconds[task["tool"]] for task in plan)


def wave_time(plan, seconds):
    return sum(max(seconds[task["tool"]] for task in wave) for wave in waves(plan))


def greedy_time(plan, seconds):
    """Every task starts the moment its last dependency finishes."""
    finish = {}
    for wave in waves(plan):  # waves are in dependency order, so deps are already in finish
        for task in wave:
            start = max((finish[dep] for dep in task["deps"]), default=0.0)
            finish = {**finish, task["id"]: start + seconds[task["tool"]]}
    return max(finish.values())


def check(name, plan):
    try:
        validate_plan(plan, SECONDS)
        print(name, "ok")
    except ValueError as error:
        print(name, "rejected:", error)


if __name__ == "__main__":
    check("trip", TRIP_PLAN)
    cyclic = [{**task, "deps": ["e"]} if task["id"] == "a" else task for task in TRIP_PLAN]
    check("cyclic", cyclic)
    hidden = [{**task, "deps": []} if task["id"] == "d" else task for task in TRIP_PLAN]
    check("hidden", hidden)
    unknown = [{**task, "tool": "book_hotel"} if task["id"] == "d" else task for task in TRIP_PLAN]
    check("unknown", unknown)
    print([[task["id"] for task in wave] for wave in waves(TRIP_PLAN)])
    print(sequential_time(TRIP_PLAN, SECONDS), wave_time(TRIP_PLAN, SECONDS), greedy_time(TRIP_PLAN, SECONDS))

Why the three times differ. One after another, the five calls take 3.0 + 0.5 + 1.0 + 2.0 + 0.5 = 7.0 seconds. In waves, wave 1 lasts 3.0 seconds, because the short weather call has to wait for the flight search before wave 2 may start, which gives 3.0 + 1.0 + 2.0 + 0.5 = 6.5. Released greedily, the chain b, c, d finishes at 0.5 + 1.0 + 2.0 = 3.5 seconds while the flight search finishes at 3.0, so the summary starts at 3.5 and ends at 4.0. The greedy time equals the longest chain of dependent tasks, which project planners call the critical path. No schedule can beat it, however many tasks run at once.

Why the placeholder check matters. In the copy with the empty deps list, task d would be placed in the first wave and would look up a result that does not exist yet. Catching this before execution takes a few lines. Catching it afterwards costs a failed run and a replan.

Part 1. The interleaved loop makes 13 model calls.

Tinterleaved(12)=13×1200+600×12×132=15,600+46,800=62,400T_{\text{interleaved}}(12) = 13 \times 1200 + 600 \times \frac{12 \times 13}{2} = 15{,}600 + 46{,}800 = 62{,}400Tinterleaved​(12)=13×1200+600×212×13​=15,600+46,800=62,400

Part 2. One planner call and one solver call that reads all 12 results.

Tplan(12)=2×1200+12×600=2,400+7,200=9,600T_{\text{plan}}(12) = 2 \times 1200 + 12 \times 600 = 2{,}400 + 7{,}200 = 9{,}600Tplan​(12)=2×1200+12×600=2,400+7,200=9,600

62,400 / 9,600 = 6.5, so the plan-first run sends 6.5 times fewer input tokens.

Part 3. Each replan sends the first-call tokens plus the history so far.

  • After step 4: 1,200 + 4 × 600 = 3,600
  • After step 8: 1,200 + 8 × 600 = 6,000

Total: 9,600 + 3,600 + 6,000 = 19,200 tokens, still 3.25 times fewer than the interleaved loop.

Part 4. Eleven replans, after steps 1 to 11:

  • Fixed part: 11 × 1,200 = 13,200
  • History part: 600 × (1 + 2 + ... + 11) = 600 × 66 = 39,600

Total: 9,600 + 13,200 + 39,600 = 62,400 tokens. That is exactly the interleaved total. A system that replans after every step is an interleaved loop under another name, and it has given up everything the plan was meant to save. Replan on a signal (a failure, a stall, a checkpoint), not on every step.

Part 5.

  • (a) Plan-first DAG. Every call can be listed from the request: the same lookups for six suppliers, none depending on another. They form one wave, followed by one task that builds the table.
  • (b) Interleaved loop. "Find out why" means each finding decides what to inspect next: the invoice lines, then perhaps the order history, then perhaps a currency or tax field. A plan written up front would be replaced after almost every step. Use a step limit, and consider a short task list so the user can see progress.
  • (c) Neither. One tool call answers it. A planner call and a solver call would roughly double the cost of a single round trip.

Check your answer

  • Did you get 62,400 tokens for the interleaved loop and 9,600 for the plan-first run?
  • Is your total with two replans 19,200 tokens?
  • Does replanning after each of steps 1 to 11 bring the plan-first total back to exactly 62,400?
  • Can you point to the words in request (b) that tell you the steps cannot be listed in advance?
