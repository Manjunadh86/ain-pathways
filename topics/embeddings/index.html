Embeddings

An embedding is a fixed-length list of numbers (a vector) that stands for a word, sentence, image, product or other item. A trained model places items so that those with similar meaning or behaviour get nearby vectors, which lets a program measure similarity with simple arithmetic such as cosine similarity.

1Overview

Why it matters

Search by meaning, retrieval for RAG, "similar items" shelves, duplicate detection, clustering and classification with few labels all rest on one move: convert each item to a vector, then compare vectors. The embedding layer sits between raw content and everything built on it, so its choices (which model, how many dimensions, which similarity measure) set a ceiling on the quality of the whole system.

Most failures are not in the arithmetic, which is a dot product, but in the plumbing around it. Queries are embedded with a different model from the documents. A dot product is taken on vectors whose lengths vary. A shortened vector is never re-normalised. A model is picked from a leaderboard and never tested on the team's own queries. A search for an exact error code returns pages about error codes in general. Changing the model later means re-embedding the whole corpus: Pinterest's engineers wrote that each improvement to an embedding required a full back-fill that could be prohibitively expensive. Engineers who add search or retrieval to a product need these details before they choose an API.

Before you start

No prerequisites. You can start here.

What you will be able to do

  • Explain what an embedding is and how a dense vector differs from a one-hot vector.
  • Compute the dot product, cosine similarity and Euclidean distance for small vectors, and say when the three give the same ranking.
  • Describe three ways embeddings are learned (predicting neighbours, contrastive pairs, user behaviour) and why vectors from different models cannot be compared.
  • Request embeddings from an API or an open-source library while handling query versus document inputs, output dimensions and normalisation.
  • Build and test a small semantic search, and recognise where it fails (short queries, exact identifiers).
  • Estimate the storage an embedding index needs for a chosen number of dimensions and numeric precision.

Key terms

Embedding
A list of numbers (a vector) that represents an item such as a word, sentence, image or product, learned so that similar items get nearby vectors.
Dimension
One position in the vector. A 768-dimensional embedding has 768 numbers. Individual dimensions are rarely interpretable on their own.
One-hot vector
A vector as long as the vocabulary with a single 1 marking the item and 0 everywhere else. It is sparse and treats every pair of items as equally different.
Embedding space
The set of all vectors a model can produce. Distances and angles inside it are what carry similarity.
Cosine similarity
The cosine of the angle between two vectors, from -1 to 1. It ignores how long the vectors are and compares only their direction.
Dot product
Multiply two vectors position by position and add the results. It equals the two lengths times the cosine of the angle between them.
Normalisation
Dividing a vector by its length so that its length becomes 1. For unit-length vectors the dot product and cosine similarity are the same number.
Contrastive learning
Training that pulls the vectors of matching pairs (a question and its answer, an image and its caption) together and pushes the vectors of non-matching items apart.
Static embedding
An embedding table with one fixed vector per word, whatever sentence the word appears in. word2vec produces these.
Semantic search
Search that ranks documents by closeness of meaning, measured between embeddings, instead of by shared keywords.

2Explanation

Introduction

You already know that a keyword search for "cheap flights" will not find a page titled "budget airfare": the words differ, so the pages look unrelated. People handle meaning easily; a program that compares strings does not. An embedding is the standard fix. It turns an item (a word, a sentence, an image, a product) into a vector, a list of real numbers such as [0.12, -0.40, 0.05, ...], in such a way that items with similar meaning end up with similar numbers.

Think of a map. Every town has two coordinates, and towns with close coordinates are close on the ground, so "which town is nearest?" becomes a subtraction. An embedding is a map of meaning. A real map has two dimensions (coordinates). An embedding has hundreds or thousands, for example 768 in the model that Stack Overflow's search prototype uses, described later in this lesson. You cannot point at dimension 417 and say what it stands for. Only the distances and directions between whole vectors carry meaning. The set of all vectors a model can produce is its embedding space.

Two parts make this usable. An embedding model is a trained neural network that maps an item to its vector. A similarity measure (cosine similarity, dot product or Euclidean distance) turns two vectors into one number saying how close they are. Together they give semantic search: embed every document once and store the vectors, embed the query with the same model at search time, and return the documents whose vectors are nearest.

The rest of the lesson covers where the vectors come from, how the three similarity measures differ and when they agree, how to call embedding APIs and libraries correctly, and where semantic search breaks. A small example with real arithmetic follows the explanation. Storing and searching millions of vectors quickly is the subject of vector databases, and using the retrieved text to answer questions is retrieval-augmented generation. The arithmetic is the dot product from linear algebra for ML.

How it works

Why dense vectors

The simplest way to give a word to a model is a one-hot vector: one position per vocabulary word, a 1 at the word's position and 0 everywhere else. With 5,000 words every vector has 5,000 entries and any two different words are equally far apart, so "hot dog" is no closer to "shawarma" than to "salad". Google's Machine Learning Crash Course (opens in a new tab) opens its embeddings module with this problem and presents embeddings as lower-dimensional (dense) representations that capture semantic relationships. A dense vector has hundreds or thousands of entries, almost all non-zero, arranged so that related items sit near each other. Real sizes: Stack Overflow's search prototype uses a model that produces 768 dimensions, OpenAI's text-embedding-3-small returns 1,536 numbers by default and text-embedding-3-large 3,072, and Gemini's default is 3,072.

The numbers themselves are not readable. The Crash Course notes (opens in a new tab) that individual dimensions are rarely as understandable as "dessertness", so you judge an embedding by how its nearest neighbours behave, not by inspecting coordinates.

Where embeddings come from

An embedding is a by-product of training a network on a task that forces similar items to have similar vectors. Three recipes cover most systems.

Predict the neighbours. word2vec's skip-gram model learns one vector per word by predicting the words around it in a large text, which pulls words with similar contexts together. The word2vec phrases paper (opens in a new tab) reports that vec("Madrid") - vec("Spain") + vec("France") is closer to vec("Paris") than to any other word vector. These are static embeddings: the Crash Course describes word2vec as learning a single global embedding per word, so (our example) "bank" has the same vector in "river bank" and "bank account".

Pull matching pairs together. Modern text, image and code models are trained on pairs that belong together. In a batch of NNN pairs, each item's partner is the right answer and the other N−1N-1N−1 partners are negatives. With cosine similarity sijs_{ij}sij​ between item iii and partner jjj, and a temperature τ\tauτ that controls how sharp the contrast is, the contrastive (InfoNCE) loss is

It is small when every item is closer to its own partner than to any other partner in the batch. CLIP (opens in a new tab) trains an image encoder and a text encoder jointly this way (with a symmetric version of the loss) on 400 million image-text pairs, so that a photo and its caption share one space. GitHub reports (opens in a new tab) contrastive learning with InfoNCE loss and "hard negatives" (code that looks correct but is not) for its Copilot embedding model. Sentence-BERT (opens in a new tab) is an earlier sentence-level relative: it modifies a pre-trained BERT network with siamese and triplet network structures so that sentences can be compared with cosine similarity. Its abstract gives the payoff: finding the most similar pair among 10,000 sentences takes about 65 hours when BERT must read every pair, and about 5 seconds when each sentence is embedded once.

Learn from behaviour. Etsy's retrieval model is trained on cart-adds and purchases from search logs, so that the vector for a query and user lands near the vectors of products people bought. Nothing in it is "meaning" in a dictionary sense. The geometry records what behaviour says belongs together.

For text, a typical encoder splits the input into tokens, computes a vector for each token in context, pools them into one vector (averaging is common) and often scales it to length 1. A static embedding skips the encoder and looks the word up in a table.

Three measures are in common use. For vectors aaa and bbb:

Google's recommendation course (opens in a new tab) notes that the dot product grows with the norm of an embedding and that items frequent in training tend to have large norms, so popular items can dominate. Cosine uses direction only. Euclidean distance reacts to both. When every vector has length 1 the three agree: a⋅b=cos⁡(a,b)a\cdot b=\cos(a,b)a⋅b=cos(a,b) and ∥a−b∥2=2−2cos⁡(a,b)\lVert a-b\rVert^2 = 2-2\cos(a,b)∥a−b∥2=2−2cos(a,b), so ranking by dot product, cosine or distance gives one order. OpenAI (opens in a new tab) and Voyage (opens in a new tab) both document that their embeddings are normalised to length 1, so cosine similarity can be computed as a plain dot product. Read the documentation of the model you use; vectors that are not unit length need cosine or an explicit normalisation step.

Calling an embedding model

A hosted API takes text and returns vectors. A minimal call with the OpenAI Python SDK (our code; it needs an API key and was not executed for this lesson):

python
from openai import OpenAI

client = OpenAI()  # reads OPENAI_API_KEY from the environment
response = client.embeddings.create(
    model="text-embedding-3-small",
    input=["Reset a forgotten password", "Track your parcel"],
    dimensions=512,  # optional: ask for a shorter vector
)
vectors = [item.embedding for item in response.data]
print(len(vectors), len(vectors[0]))  # expected: 2 512

Four details cause most real bugs:

  • One model on both sides. Embed documents and queries with the same model and version, and store the model name beside every vector.
  • Say whether the text is a query or a document. Voyage's input_type parameter prepends a retrieval prompt, and its documentation says not to omit it for retrieval. Gemini's gemini-embedding-001 (opens in a new tab) takes a task_type such as RETRIEVAL_QUERY or RETRIEVAL_DOCUMENT, and gemini-embedding-2 expects the task written into the prompt. Sentence Transformers offers encode_query and encode_document (opens in a new tab) for asymmetric search, where short questions are matched against long passages.
  • Choose the size. OpenAI's dimensions, Gemini's output_dimensionality (128 to 3,072) and Voyage's output_dimension return shorter vectors from models trained with Matryoshka Representation Learning, where the leading numbers already form a usable smaller embedding. If you cut a stored vector yourself, divide it by its new length afterwards. Gemini says gemini-embedding-2 normalises truncated outputs automatically and that gemini-embedding-001 needs manual normalisation for any size other than 3,072.
  • Respect input limits. OpenAI documents 8,192 tokens per input for its embedding models, Gemini 8,192 for gemini-embedding-2 but only 2,048 for gemini-embedding-001, and most Voyage text models 32,000, while the open all-MiniLM-L6-v2 (opens in a new tab) model (384 dimensions) truncates input beyond 256 word pieces. Long documents are split into chunks first; see chunking and document ingestion.

Hosted APIs need no hardware but send your text to a provider and bill per token. Open models run on your own machine through Sentence Transformers. Anthropic states that it does not offer its own embedding model and points to Voyage AI.

Semantic search end to end

Offline, split documents into chunks, embed each one and store the vectors with ids and metadata. At query time, embed the query, compare it with the stored vectors and return the top kkk. A plain loop over a few thousand vectors is fine; millions need an approximate index (vector databases). Stack Overflow warns that semantic search does worse with two- or three-word queries and with specific error codes, and Anthropic pairs embeddings with BM25 keyword matching for the same reason (advanced retrieval covers hybrid search).

To choose a model, test it on your own data. The MTEB (opens in a new tab) benchmark spans 8 embedding tasks and 58 datasets and found that no single method dominates every task, so a leaderboard position is only a starting point. Label 50 real queries with their correct documents and measure how often the correct one appears in the top kkk (recall@kkk).

Step 4: check it in code

This script uses only the Python standard library:

python
import math

def dot(a, b):
    return sum(x * y for x, y in zip(a, b))

def norm(a):
    return math.sqrt(dot(a, a))

def normalize(a):
    n = norm(a)
    return [x / n for x in a]

def cosine(a, b):
    return dot(a, b) / (norm(a) * norm(b))

def distance(a, b):
    return math.sqrt(sum((x - y) ** 2 for x, y in zip(a, b)))

query = [0.8, 0.2]
articles = {
    "A": [0.6, 0.1],  # Reset a forgotten password
    "B": [0.1, 0.9],  # Track your parcel
    "C": [0.3, 2.0],  # Orders, delivery and returns: the full guide
    "D": [0.5, 0.4],  # Change the email on your account
}

def show(title, q, vectors):
    print(title)
    for name, v in vectors.items():
        print(f"  {name}  dot={dot(q, v):.4f}  cosine={cosine(q, v):.4f}  distance={distance(q, v):.4f}")
    print("  by dot     :", sorted(vectors, key=lambda n: -dot(q, vectors[n])))
    print("  by cosine  :", sorted(vectors, key=lambda n: -cosine(q, vectors[n])))
    print("  by distance:", sorted(vectors, key=lambda n: distance(q, vectors[n])))

show("raw vectors", query, articles)
show("unit-length vectors", normalize(query), {n: normalize(v) for n, v in articles.items()})

What it means. Which measure you use only matters when vector lengths differ. The OpenAI and Voyage documentation say their embeddings already have length 1, which is Step 3 done for you. The raw case still happens with models that are not normalised, such as a recommender trained for dot-product scoring, and then the choice of measure changes which item wins.

Edge cases and limitations

Vectors from different models cannot be compared
Two models can both return 1,536 numbers and still use unrelated coordinate systems, so a score between a vector from one and a vector from the other is meaningless. A new model version, a different dimension setting or a different query prefix also changes the space. Changing any of them means re-embedding the whole corpus. Pinterest's paper describes a full back-fill for each embedding improvement as potentially prohibitively expensive. Store the model name, version and dimension with every vector.
Short queries and exact identifiers
Stack Overflow's engineers note that semantic search does worse with two- or three-word queries and with specific error codes or unique keywords. Anthropic's example is the query "Error code TS-999", where an embedding model may return pages about error codes in general and miss the exact match. The sign is a near-miss at rank 1 (TS-404 above TS-999). Add keyword matching such as BM25 and merge the two rankings, or rewrite short queries into fuller questions.
Shortened vectors that were not re-normalised
Cutting a unit-length vector down to its first 256 numbers leaves a vector shorter than 1, with a length that differs from item to item. A dot product on such vectors then favours items whose weight sits in the kept positions, and scores stop being cosine similarities. Divide the shortened vector by its length, or request the smaller size from the API. Truncation also only works for models trained for it (Matryoshka training); cutting an ordinary model's vector at random positions throws information away.
Text longer than the model's input limit
Every embedding model has a maximum input length. all-MiniLM-L6-v2 truncates beyond 256 word pieces, so the end of a long page is never represented. Stack Overflow's engineers also stress that the text embedded should be neither too little nor too much; a likely reason is that a long passage blends several topics into one vector. Split documents into focused chunks and pick the chunk size by testing retrieval on your own queries.
Static embeddings give each word one vector
A word2vec table holds a single vector per word, so "bank" in "river bank" and "bank account" gets the same numbers, and a rare or misspelled word may be missing altogether. Embedding models used for search encode the whole passage in context, so the same word can contribute differently in different sentences. Use a sentence-level model for search, and treat word vectors as a teaching tool or a cheap feature for small projects.
Nearest does not mean relevant or true
Embeddings capture topical closeness. A sentence and its negation, or two policies that differ by one number, can sit close together because they talk about the same thing. The top result may therefore be on topic yet wrong. Rerank the top candidates with a stronger model, or have the answering step check the retrieved text, and keep a labelled query set so you can measure how often the top result is right.

When to use it, and when something simpler is enough

Use it when

  • Users phrase the same need in different words, as in support search, FAQs, product search and duplicate-question detection, so keyword overlap misses relevant items.
  • A language model needs relevant passages from a large collection, which is retrieval for RAG, and the passages are too many to put in the prompt.
  • You want "more like this" for items that have text, images or interaction history, and you can compute a vector for each item once and reuse it.
  • You have little labelled data and want a ready-made feature set for clustering or a simple classifier.

Think twice when

  • Users look up exact strings such as order numbers, error codes, SKUs or function names. A keyword or database index returns the exact match and an embedding may not.
  • The collection is small and the queries share vocabulary with the documents, so BM25 or a SQL filter already finds the right item and avoids a model, a store and re-indexing.
  • You must explain to a user or an auditor why an item matched. A similarity score between vectors has no readable reason behind it.

A simpler alternative. Start with keyword search (BM25 or your database's full-text search) plus filters, and log the queries that return nothing useful. Add embeddings when those failures are mostly paraphrases and synonyms. Keep the keyword search alongside the embeddings (hybrid search) when exact identifiers also matter.

Key takeaways

  • An embedding is a dense vector produced by a trained model so that similar items get nearby vectors, and only the distances and directions between whole vectors carry meaning, not individual dimensions.
  • Embeddings are learned by predicting neighbours, by pulling matching pairs together against in-batch negatives, or from user behaviour, which is why vectors from different models or versions can never be compared.
  • Dot product, cosine similarity and Euclidean distance give the same ranking on unit-length vectors, so check whether your model returns them, normalise when it does not, and re-normalise after you shorten a vector.
  • Embed documents and queries with the same model, use the model's query and document settings for retrieval, and keep chunks within its input limit.
  • Semantic search is weakest on short queries and exact identifiers, so pair it with keyword matching and judge any model on your own labelled queries rather than on a leaderboard.

Example 1 of 5

Stack Overflow: natural-language search over questions and answers

Stack OverflowDocumented in an engineering article

Stack Overflow's engineering post "Ask like a human" (July 2023) describes a semantic search prototype built on embeddings from a pre-trained BERT model in the open-source SentenceTransformers library, stored in the Weaviate vector database. The post presents the feature as forthcoming. [13]

The problem

Keyword (lexical) search was, in the post's words, rigid: it expected users to know specialised punctuation and boolean operators. Stack Overflow wanted people to search in natural language and still find the right posts when their wording differed from the post's.

Where this topic fits

Embeddings sit between the data platform and the search service. A batch pipeline turns post text into vectors that are stored in the vector database. At query time the user's text goes through the same model and the nearest stored vectors come back as results.

How it is applied, step by step

  1. Decide what text each embedding represents. Embedding models have a fixed context length, so the team had to include enough text to carry the meaning but not too much, and built the pipeline so a post can have more than one embedding.
  2. Run the chosen text through a pre-trained BERT model from the SentenceTransformers library in the existing Azure Databricks pipeline. The post says the open-source model the team is using for the time being produces 768 dimensions.
  3. Store the vectors in Weaviate, selected because it is open source, supports hybrid search (lexical and semantic on the same data) and connects natively to Spark.
  4. At search time, transform the query into a vector in the same way the documents were indexed.
  5. Find the nearest stored vectors by cosine distance and return the matching posts.
  6. Because the store can run lexical and semantic search over the same data, the two can be combined for the cases the post lists as weak spots for semantic search: very short queries and exact error codes.

Why this approach fits

A question title and the best answer's wording often differ, which is the kind of gap a sentence-embedding model is built to close by placing paraphrases near each other. A compact open-source model (the post notes that closed-source models can produce double or triple its 768 dimensions) keeps storage and cost modest, and a self-run model and database keep the data on infrastructure the company already runs.

Limitation or tradeoff

The post itself says semantic search does worse with two- or three-word queries and with specific error codes or unique keywords. It describes a prototype and calls the feature forthcoming. It reports no precision, recall, latency or engagement numbers, only one illustrative query, so how much better the results are is not established by this source.

What the sources document

  • Stack Overflow moved beyond lexical search because it demanded rigid syntax such as specialised punctuation and boolean operators, and the company wanted users to search in natural language. [13]
  • The pipeline from the company's existing Azure Databricks data platform feeds a pre-trained BERT model from the SentenceTransformers library to generate the embeddings. Separately, the post says the pre-tuned open-source model the team is using for the time being produces 768 dimensions. [13]
  • Weaviate was chosen as the vector database because it is open source, supports hybrid search (lexical and semantic on the same data) and has a native Spark connection. [13]
  • A query is transformed into a vector in the same way the documents were indexed, and the search finds nearby vectors using cosine distance. [13]
  • The post says semantic search does worse with short queries of two or three words, and with a specific error code or unique keyword. [13]

The facts above come from the cited sources. The steps and analysis in this example are our explanation of how they fit together.

Example 2 of 5

Pinterest: one image embedding shared by three visual search products

PinterestDocumented in a paper

The paper "Learning a Unified Embedding for Visual Search at Pinterest" (Zhai et al., 2019) describes replacing separate image embeddings with a single unified embedding that serves Flashlight, Lens and Shop-The-Look. [14]

The problem

Each visual search product needs a different notion of "similar image": related Pins from a starting image, Pins matching a camera photo, and products matching an object in a home scene. Pinterest had built three specialised embeddings, and every improvement to an embedding needed a full back-fill of the stored vectors before it could be deployed, which the authors call prohibitively expensive.

Where this topic fits

The embedding is a feature computed for each image by a deep network. The paper represents the relevance of an image pair as the distance between their embeddings, so each product reduces to a nearest-neighbour lookup. The training objective decides what "near" means for each product.

How it is applied, step by step

  1. Treat similarity as distance: two images are relevant to each other when their embeddings are close.
  2. Train one network with multi-task metric learning that jointly optimises relevance for browsing and for searching, using classification-based metric learning over three datasets: engagement feedback for Flashlight, human-labelled cross-domain data for Lens and human-labelled product matches for Shop-The-Look.
  3. Serve the one resulting embedding to all three products in place of the three specialised ones, so a future model improvement needs one back-fill rather than three.
  4. Binarise the embedding by thresholding at zero for cheaper storage and retrieval. Earlier work had found little loss from this, but the paper reports a significant drop for a binarised version of its baseline, so it changes the network (among other things, GroupNorm in place of LayerNorm) to make the binary embedding hold up.
  5. Compare against the specialised embeddings already deployed, using offline precision metrics, human judgments and online experiments. The authors report that the unified embedding outperformed them.

Why this approach fits

Embeddings let several products share one expensive artefact. Training, storing and back-filling one vector per image costs far less than maintaining three, and a distance-based objective optimises the quantity the products actually use. Binary vectors shrink the index again.

Limitation or tradeoff

One embedding has to serve three goals, so the training mixes three datasets and the authors had to balance them. Binarising was not free: the paper reports a significant drop for a binarised version of its baseline and needed network changes to recover it, and its final binary model is slightly below the earlier float baseline on Lens (18.4 against 18.6 average precision@20) while above it on Shop-The-Look and level on Flashlight. Shop-The-Look had not launched to users, so it was judged by human ratings rather than an A/B test. Replacing the model still means re-embedding every image once, and what counts as similar is whatever the engagement and human-labelled training data encode.

Etsy: query, user and product vectors for personalised search retrieval

EtsyDocumented in a paper

The paper "Unified Embedding Based Personalized Retrieval in Etsy Search" (Jha et al.) describes a two-tower model that puts products and (query, user) pairs in one embedding space and is used to retrieve candidate listings in Etsy search. [16]

The problem

Search must retrieve relevant listings even when the query's wording differs from the listing's text, which the paper calls the semantic gap, and the right results also depend on who is searching. The retrieval step has to be fast enough for production, with the authors reporting under 20 ms at the 99th percentile.

Where this topic fits

This is first-stage retrieval. Product vectors are stored in an approximate nearest-neighbour index. At search time the query-and-user tower produces one vector and the nearest products become the candidates for later ranking stages.

How it is applied, step by step

  1. Build a product encoder from transformer-based text representations, a bipartite graph encoder and token and ID embeddings, concatenated and passed through feed-forward layers into one product vector.
  2. Build a query-user encoder that takes the search query, recent search queries, recently clicked shops, the user's location and tags of items the user has purchased, and produces one vector for the pair.
  3. Train both encoders on search-log cart-adds and purchases from about one month of data, so that a purchased product's vector is close to the matching query-user vector.
  4. Score a (query, user, product) triple as the cosine between the product vector and the query-user vector.
  5. Serve the product vectors from a 4-bit product-quantised fast-scan index in Faiss, trading a small loss of recall for latency.
  6. Test online in A/B experiments and report the effect on purchase and conversion rates.

Why this approach fits

A shared space lets one nearest-neighbour search handle both text matching and personalisation, because user context is just more input to the query-side tower. Product vectors can be computed ahead of time and indexed, and a cosine over precomputed vectors is cheap enough to retrieve from a large catalogue.

Limitation or tradeoff

Quantising the index costs recall: the authors report a loss below 4% in production. The lift figures are aggregated over Etsy's own A/B tests and need not transfer to another marketplace. A model trained on one month of purchases learns from behaviour, so listings and shops with more past interactions give it more signal than new ones, which is our reading of the training set-up rather than a claim in the paper.

Anthropic: chunk embeddings combined with BM25 for retrieval-augmented generation

AnthropicDocumented in an engineering article

Anthropic's engineering post "Introducing Contextual Retrieval" describes how chunks of a knowledge base are embedded for RAG, where embedding search falls short, and how much a change to the embedded text reduces retrieval failures. [17]

The problem

A RAG system retrieves chunks and gives them to a language model. Chunks often lose the context that identifies them: the post's example is "The company's revenue grew by 3% over the previous quarter", which names neither the company nor the period. Embeddings can also miss exact strings, such as a query for "Error code TS-999".

Where this topic fits

The embedding model is the semantic retrieval stage. Chunking comes before it, a keyword (BM25) search runs beside it, and rank fusion, optional reranking and the language model come after it.

How it is applied, step by step

  1. Break the knowledge base into chunks of usually no more than a few hundred tokens.
  2. Prepend a short, chunk-specific explanation of where the chunk comes from to each chunk, then embed the result with an embedding model and store the vectors in a vector database.
  3. At query time, embed the query and find the chunks whose vectors are nearest, so paraphrases and related wording match.
  4. In parallel, run BM25 over the (contextualised) chunks to catch exact strings such as an error code.
  5. Combine and deduplicate the two result lists with rank fusion, optionally rerank, and pass the top chunks to the language model.

Why this approach fits

Embedding search handles paraphrase and topic, and adding context repairs chunks that are ambiguous on their own. BM25 handles exact strings. The two retrievers fail on different queries, so combining them covers more than either alone.

Limitation or tradeoff

Adding context means generating a note for every chunk with a language model before indexing, which adds cost and a step to keep up to date; that is our reading of the method. The percentages come from Anthropic's own evaluation sets and a top-20-chunk metric, so they show the direction of the effect and not what your corpus will gain.

4Common mistakes

  1. Embedding queries and documents with different models, or with different versions of the same model

    Why it causes problems
    The two sets of vectors live in unrelated spaces, so similarity scores are close to random. Nothing fails loudly, because the dimensions may even match, and the search keeps returning plausible-looking but wrong results.
    How to recognise it
    A query copied from a document's own title does not bring that document to the top. Scores between a query and its source document are no higher than between random pairs.
    How to fix it
    Store the model name, version, dimension and any query or document setting beside every vector. Build a new index for a new model, re-embed everything, and switch over only after a fixed set of test queries passes on the new index.

  2. Ranking with a dot product on vectors that are not unit length

    Why it causes problems
    A longer vector scores higher at the same angle, so a few long vectors, often from popular or long items, crowd into the top results for many unrelated queries. Google's recommendation course notes that items frequent in training tend to have large norms.
    How to recognise it
    The same handful of items appears in the results for different queries, and ranking the same candidates by cosine similarity gives a visibly different order.
    How to fix it
    Read the model's documentation. If vectors are not normalised, divide each by its length when indexing and querying, or use cosine similarity. After you shorten a vector, normalise it again.

  3. Leaving out the query-versus-document setting of a retrieval embedding model

    Why it causes problems
    Several models embed a short query and a long passage differently on purpose. Voyage's documentation says to specify the input type for retrieval and not to omit it, and Gemini and Sentence Transformers offer task types and separate query and document methods. Skipping them lowers retrieval quality without any error.
    How to recognise it
    The model's documentation lists a task type, input type or query/document method that your code never sets. On a small labelled test set, recall improves when you add it.
    How to fix it
    Use the documented setting on both sides: `input_type` for Voyage, `task_type` or the task instruction for Gemini, `encode_query` and `encode_document` in Sentence Transformers.

  4. Choosing an embedding model from a leaderboard rank without testing it on your own queries

    Why it causes problems
    The MTEB authors found that no single embedding method dominates every task. A model that leads on average can be weaker on your language, your domain or your text length, and a larger model costs more storage and latency for every vector.
    How to recognise it
    Nobody on the team can state recall@k for the current model on real queries, and quality complaints arrive only after launch.
    How to fix it
    Collect 50 to 100 real queries with their correct documents. Compare two or three candidate models, including a smaller output size, on recall@k, latency and storage, and pick the cheapest that meets the target.

  5. Treating a similarity score as a probability or copying a score cut-off from a tutorial

    Why it causes problems
    Score ranges differ between models and between query types, so a cut-off of 0.8 can mean a strong match in one model and a weak one in another. A copied threshold either lets irrelevant results through or hides relevant ones.
    How to recognise it
    Relevant results fall just below the cut-off, or irrelevant ones sit just above it, when you list the scores of labelled good and bad pairs.
    How to fix it
    Choose the threshold per model from labelled pairs, or return a fixed top $k$ and let a later step filter. Compare ranks, not raw scores, when you compare models.

import math

def dot(a, b):
    return sum(x * y for x, y in zip(a, b))

def norm(a):
    return math.sqrt(dot(a, a))

def normalize(a):
    n = norm(a)
    return [x / n for x in a]

def cosine(a, b):
    return dot(a, b) / (norm(a) * norm(b))

def euclidean(a, b):
    return math.sqrt(sum((x - y) ** 2 for x, y in zip(a, b)))

query = [0.8, 0.2, 0.1, 0.5]
docs = {
    "d1 Reset your password": [0.7, 0.3, 0.1, 0.6],
    "d2 Track my parcel": [0.1, 0.9, 0.2, 0.2],
    "d3 Update your billing card": [0.5, 0.2, 0.8, 0.1],
    "d4 Change delivery address": [0.2, 0.8, 0.1, 0.5],
    "d5 Close my account": [0.6, 0.1, 0.3, 0.7],
}

def ranking(score, data, reverse=True):
    items = sorted(data.items(), key=lambda item: score(query, item[1]), reverse=reverse)
    return [name.split()[0] for name, _ in items]

print("raw dot     :", ranking(dot, docs))
print("cosine      :", ranking(cosine, docs))

import re
from sentence_transformers import SentenceTransformer, util

corpus = [
    "To reset your password, choose Forgot password on the sign-in page.",
    "Parcels usually arrive within three to five working days.",
    "You can change the card used for billing in account settings.",
    "Refunds are issued to the original payment method within ten days.",
    "Error TS-999 means the export job timed out.",
    "Error TS-404 means the report template was not found.",
    "Two-factor codes are sent by text message or an authenticator app.",
    "To close your account, contact support from the help page.",
    "Delivery addresses can be edited until the order has shipped.",
    "Invoices are emailed on the first day of each month.",
]
queries = {"I can't get into my account": 0, "money back": 3, "TS-999": 4, "refund": 3}

STOP = {"i", "t", "can", "my", "to", "the", "a", "of", "in", "by", "or", "you", "your", "are", "be", "from", "on", "is", "for"}

def tokens(text):
    return set(re.findall(r"[a-z0-9]+", text.lower())) - STOP

def keyword_top(query):
    overlaps = [len(tokens(query) & tokens(doc)) for doc in corpus]
    best = max(range(len(corpus)), key=lambda i: (overlaps[i], -i))
    return None if overlaps[best] == 0 else best

model = SentenceTransformer("sentence-transformers/all-MiniLM-L6-v2")
doc_vectors = model.encode(corpus, normalize_embeddings=True)

def cosine_scores(query):
    query_vector = model.encode(query, normalize_embeddings=True)
    return util.cos_sim(query_vector, doc_vectors)[0]

def hybrid_top(query, weight=0.5):
    words = tokens(query)
    overlap = [len(words & tokens(doc)) / max(len(words), 1) for doc in corpus]
    combined = [c + weight * o for c, o in zip(cosine_scores(query).tolist(), overlap)]
    return max(range(len(corpus)), key=lambda i: combined[i])

for query, correct in queries.items():
    values, indices = cosine_scores(query).topk(2)
    best = indices[0].item()
    margin = values[0].item() - values[1].item()
    print(f"{query!r}: keyword={keyword_top(query)} semantic={best} (margin {margin:.3f}) "
          f"hybrid={hybrid_top(query)} correct={correct}")

The sizes are 24.576 GB (3,072 dims), 12.288 GB (1,536), 6.144 GB (768) and 2.048 GB (256) as float32, and 6.144 GB (int8) and 0.768 GB (1 bit) at 3,072 dimensions. Four options fit: 768 and 256 as float32, and 3,072 as int8 or binary. The cut vector is (0.5, 0.5) with length 0.7071, and after division it is (0.7071, 0.7071). The team must measure recall@k on real queries.

Hint 1

Memory in bytes is the number of vectors times the dimensions times the bytes per number; 1 bit is one eighth of a byte.

Hint 2

The length of (0.5, 0.5) is the square root of 0.25 + 0.25.

Hint 3

Index structures and metadata add memory on top of the raw vectors, so leave some headroom.

The int8 and 1-bit rows are one quarter and one thirty-second of the float32 row for the same number of dimensions, which matches the 4x and 32x savings Voyage's documentation states for these data types.

For the cut vector, (0.5, 0.5, 0.5, 0.5) has length 1. Its first two numbers give (0.5, 0.5) with length 0.25+0.25=0.7071\sqrt{0.25 + 0.25} = 0.70710.25+0.25​=0.7071, so it is no longer a unit vector. Dividing by 0.7071 gives (0.7071, 0.7071), which has length 1 again. Skipping the division would leave dot products too small and dependent on how much of each vector sat in the kept positions.

Fitting in memory is necessary, not sufficient. Shorter or quantised vectors lose some information, and only a labelled query set shows how much. The team should compute recall@k (how often the correct chunk is in the top k) for each fitting option on real queries, then pick the cheapest option that meets the recall target. They should also leave headroom for the index structure and metadata.

Check your answer

  • Do you get 24.576 GB for the 3,072-dimension float32 option?
  • Is your list of fitting options exactly four?
  • Is the re-normalised cut vector (0.7071, 0.7071) with length 1?
  • Did you name recall@k on real queries as the thing to measure before choosing?
