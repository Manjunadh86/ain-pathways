Authentication and Authorization (OAuth, SSO, RBAC)

Authentication is how a system checks who or what is making a request. Authorization is how it decides what that caller may do. API keys, OpenID Connect and SAML are common ways to establish identity, OAuth 2.0 is the standard way to grant an application limited access to an API, and role-based access control (RBAC) is a common way to organise permissions.

1Overview

Why it matters

Enterprise deployments often meet these questions early. The customer's staff usually will not create separate passwords for your tool, so it has to sign users in through their identity provider. Their APIs often will not accept a shared username and password, so your integration has to obtain OAuth tokens. Their security review will ask which roles can see which records and how access is removed when someone leaves. If you cannot answer in their vocabulary (SSO, SAML, OIDC, scopes, RBAC), the project waits.

Getting it wrong is also a leading way for APIs to leak data. The OWASP API Security Top 10 ranks a missing per-record authorization check first and broken authentication second. The failures are usually small: a token whose signature is checked but whose audience is not, an endpoint that trusts the ID in the URL, a secret key committed to a repository. Anyone who builds, integrates or reviews an API needs to be able to spot them.

Before you start

  • REST APIs and System IntegrationBeginner

What you will be able to do

  • Distinguish authentication from authorization and map each failure to the 401 or 403 status code.
  • Choose between an API key, an OAuth 2.0 access token, an OpenID Connect ID token and a SAML assertion for a given integration.
  • Trace the OAuth 2.0 authorization code flow with PKCE and compute an S256 code challenge.
  • List the checks a service must make on a signed token before it trusts any claim inside it.
  • Describe SAML single sign-on and say what the identity provider and the service provider each do.
  • Design a small role-to-permission table and add the per-record check that roles alone do not provide.

Key terms

Authentication (AuthN)
Checking that a caller is who or what it claims to be, by verifying a credential such as a password, an API key or a signed token.
Authorization (AuthZ)
Deciding whether an already identified caller is allowed to perform a specific action on a specific piece of data.
API key
A long random secret issued to one client application, sent with every request so the API knows which program is calling.
Bearer token
A credential that works for whoever holds it, with no further proof of identity. API keys and most OAuth access tokens are bearer credentials.
Access token
The credential an OAuth 2.0 authorization server issues to a client. It represents a limited scope of access for a limited time and is presented to the API.
Scope
A named slice of access, such as read:user, that a client requests and a token carries. The API refuses calls that need a scope the token lacks.
ID token
A signed JSON Web Token defined by OpenID Connect that tells a client which user signed in, who vouches for it and when the statement expires.
Identity provider (IdP)
The system that holds user accounts, signs users in and issues signed statements about them to other applications. Microsoft Entra ID, Okta and Google are common examples.
Single sign-on (SSO)
An arrangement in which a user signs in once at an identity provider and is then accepted by many separate applications without signing in to each.
Role-based access control (RBAC)
An authorization model in which permissions are attached to roles and users are assigned roles, so that access follows job function.

2Explanation

Introduction

In REST APIs and System Integration you sent requests with headers and read status codes. Two of those codes, 401 and 403, exist because every protected API asks two separate questions before it does any work:

  1. Authentication (AuthN): who is calling? The caller presents a credential, such as a password, an API key or a signed token, and the server checks that it is genuine.
  2. Authorization (AuthZ): is this caller allowed to do this? Knowing who the caller is, the server decides whether the requested action on the requested data is permitted.

A hotel works the same way. The front desk checks your passport once and hands you a key card. That is authentication. The card then opens your room and the gym, but not the room next door or the staff office. That is authorization, and it happens at every door, not once at the desk.

The two fail differently. The HTTP specification (opens in a new tab) defines 401 Unauthorized for a request that lacks valid authentication credentials, and 403 Forbidden for a request the server understood but refuses to fulfil. In the first case the server does not know who you are. In the second it knows, and the answer is no.

Most of the vocabulary in this area names a way of answering one of the two questions:

  • API keys identify a calling program.
  • OAuth 2.0 lets a user or an organisation grant an application limited access to an API without handing over a password.
  • OpenID Connect (OIDC) and SAML let an application rely on a separate identity provider to sign users in. This is what enterprise single sign-on (SSO) is built on.
  • Role-based access control (RBAC) organises the authorization decision around job roles.

This lesson explains each mechanism, shows the messages it exchanges, and ends with the short list of checks that prevent the most common API security failures. A forward deployed engineer meets all of them early in most enterprise projects: the customer wants sign-in through their identity provider, their APIs require OAuth tokens, and their security team asks who can see what.

How it works

API keys: a password for a program

An API key is a long random string that a service issues to one client application. The client sends it with every request, usually in the Authorization header:

http
GET /v1/invoices HTTP/1.1
Host: api.example.com
Authorization: Bearer rk_live_EXAMPLE

The server looks the key up, learns which account or integration it belongs to, and applies the permissions attached to that key. A key is a bearer credential: RFC 6750 (opens in a new tab) describes a bearer token as one that any party in possession of it can use. So a key must travel only over TLS, live in a secrets manager and never in source code or a browser, carry only the permissions the integration needs, and be rotated when someone who knew it leaves.

Keys identify programs, not people. OWASP's page on broken authentication (opens in a new tab) says API keys should be used only to authenticate API clients, never users.

OAuth 2.0: delegated access without sharing a password

OAuth 2.0 (opens in a new tab) is an authorization framework. It lets an application obtain limited access to an HTTP service, on behalf of a user or on its own behalf, without ever seeing the user's password. It defines four roles:

RoleWhat it isExample
Resource ownerThe user or organisation that owns the dataYou
ClientThe application that wants accessA CI tool
Authorization serverAuthenticates the owner, asks for consent, issues tokensgithub.com/login/oauth
Resource serverThe API that holds the data and accepts tokensapi.github.com

The client ends up with an access token, a string that represents a specific scope (a named slice of access such as read:user) for a limited time. It goes in the Authorization: Bearer header. A refresh token, sent only to the authorization server, obtains a new access token when the old one expires.

The way a client obtains a token is called a grant or flow. Choose it by who is present:

SituationFlowNotes
A user is at a browser or phoneAuthorization code with PKCEThe default for web, single-page and mobile apps
No user: one service calls anotherClient credentialsThe client authenticates as itself
A user, but the device has no browser or keyboardDevice authorizationCLI tools and TVs, RFC 8628 (opens in a new tab)
Legacy codeImplicit, passwordRFC 9700 (opens in a new tab) says clients should not use implicit and must not use the password grant

Three details of the authorization code flow carry its security:

  • The code is useless on its own. With PKCE (RFC 7636 (opens in a new tab)) the client invents a random code_verifier, sends only its hash in step 2 (code_challenge = BASE64URL(SHA256(code_verifier))) and reveals the verifier in step 8. Someone who intercepts the code cannot redeem it. RFC 9700 requires PKCE for public clients, meaning apps that cannot keep a secret, and recommends it for the rest.
  • state ties the response to the request. The client sends an unguessable value and rejects any callback that does not return it, which blocks cross-site request forgery.
  • Redirect URIs are matched exactly. The authorization server sends codes only to addresses registered in advance.

For back-end integrations you will most often write the client credentials flow. It is one request, shown here as it appears in RFC 6749. The Authorization header is the client ID and secret, s6BhdRkqt3:gX1fBat3bV, encoded in base64:

http
POST /token HTTP/1.1
Host: server.example.com
Authorization: Basic czZCaGRSa3F0MzpnWDFmQmF0M2JW
Content-Type: application/x-www-form-urlencoded

grant_type=client_credentials

The response is a JSON object with an access_token and an expires_in value in seconds. It normally has no refresh token: when the token expires, the service asks again. An API that receives a token without the scope a call needs answers 403 with the error insufficient_scope.

OpenID Connect: OAuth plus proof of who signed in

An access token says what the client may do. It is meant for the API, and it does not tell the client who the user is. OpenID Connect (opens in a new tab) adds that piece as an identity layer on top of OAuth 2.0. When the client includes openid in the scope, the token response also contains an ID token: a JSON Web Token (JWT (opens in a new tab)) signed by the identity provider, with these required claims:

ClaimMeaningCheck the client makes
issWho issued the tokenExactly equals the provider's issuer URL
subStable identifier of the user at that issuerUse it as the user's key
audWho the token is forContains this client's client_id
exp, iatExpiry time and issue timeThe current time is before exp

A JWT is three base64url parts separated by dots: a header, the claims and a signature. Before trusting any claim, verify the signature with the provider's published key, using an algorithm you chose in advance. Then make the checks in the table, plus nonce if you sent one.

OpenID Connect Core defines three flows. The code flow returns every token from the token endpoint, the implicit flow from the authorization endpoint, and the hybrid flow from both. This lesson follows the code flow, which keeps tokens out of the browser redirect and is the one PKCE protects.

Providers publish their endpoints and keys in a discovery document. This one is real and needs no account:

bash
curl https://accounts.google.com/.well-known/openid-configuration
json
{
  "issuer": "https://accounts.google.com",
  "authorization_endpoint": "https://accounts.google.com/o/oauth2/v2/auth",
  "token_endpoint": "https://oauth2.googleapis.com/token",
  "jwks_uri": "https://www.googleapis.com/oauth2/v3/certs",
  "id_token_signing_alg_values_supported": ["RS256"],
  "code_challenge_methods_supported": ["plain", "S256"]
}

SAML: single sign-on in the enterprise

SAML 2.0 solves the same sign-in problem as OIDC with older technology: XML documents carried through the browser. Many enterprise identity providers and business applications still speak it. The OASIS technical overview (opens in a new tab) defines two roles. The identity provider (IdP) authenticates the user and issues a signed assertion stating who the user is, how and when they authenticated, and attributes such as department or group. The service provider (SP) is the application that consumes the assertion and creates its own session.

Trust is set up once, in advance: the two sides typically exchange metadata that contains their endpoints and signing keys. From then on the SP accepts only assertions signed by that IdP. Because every application redirects to the same IdP, a user signs in once and reaches all of them, and disabling one directory account blocks new sign-ins everywhere.

RBAC: turning identity into permissions

Authentication yields an identity. Role-based access control turns it into a decision with two lookups. In NIST's description (opens in a new tab), each user is assigned one or more roles and each role is assigned one or more privileges, so administrators assign people to roles in place of specifying access for each user individually.

Roleinvoice:readinvoice:writeinvoice:delete
vieweryesnono
accountantyesyesno
adminyesyesyes

A request is allowed when at least one of the caller's roles includes the permission the endpoint needs. Roles usually arrive from the identity provider, as a group attribute in a SAML assertion or a claim in a token, and the application maps them to its own permissions.

Roles answer "may this kind of user perform this kind of action?". They do not answer "may this user touch this record?". That second, object-level check (same tenant, owner of the record) is separate code that the endpoint must contain.

API security basics

The OWASP API Security Top 10 (opens in a new tab) puts broken object level authorization first, broken authentication second and broken function level authorization fifth. A short checklist addresses all three:

  1. Use TLS for every request (see Networking Essentials), and send credentials in the Authorization header, never in a URL, where they end up in logs and browser history.
  2. Authenticate every request. Validate each token's signature, issuer, audience and expiry on every call.
  3. Authorize on the server for every request, at two levels: the function (does a role allow this action?) and the object (does this caller have a right to this record?).
  4. Deny by default, and issue credentials with the narrowest scope and the shortest lifetime that work. RFC 6750 notes that tokens living an hour or less limit the damage of a leak.
  5. Keep secrets in a secrets manager, rotate them, and rate-limit sign-in and token endpoints.

The same two questions apply when the caller is an AI agent or a tool server. Agent Identity, Permissions and Least Privilege and MCP Transports and Authorization continue from here.

Worked example: One API, eight requests: verify a signed token, then check the role and the record

An invoices API receives a bearer token with each request. It must authenticate the caller and then authorize the action. The script below is the whole decision in standard-library Python (3.9 or later). mint stands in for the identity provider. Tokens are JWTs signed with HS256, an HMAC over the header and claims using a secret that the issuer and the API share. The clock is fixed at NOW = 1800000000 (15 January 2027, 08:00 UTC) so that everyone gets the same output. Save it as check_request.py.

python
import base64, hashlib, hmac, json

KEY = b"demo-secret-shared-with-the-issuer"  # HS256: issuer and API hold the same key
ISSUER, AUDIENCE, NOW = "https://login.example.com", "invoices-api", 1_800_000_000
ROLE_PERMISSIONS = {"viewer": {"invoice:read"},
                    "admin": {"invoice:read", "invoice:delete"}}
INVOICE_TENANT = {"inv-1": "acme", "inv-2": "globex"}
NEEDS = {"GET": "invoice:read", "DELETE": "invoice:delete"}


def b64url(raw):
    return base64.urlsafe_b64encode(raw).rstrip(b"=").decode()


def unb64url(text):
    return base64.urlsafe_b64decode(text + "=" * (-len(text) % 4))


def encode(obj):
    return b64url(json.dumps(obj, separators=(",", ":")).encode())


def mint(claims, key=KEY):
    """Stand-in for the identity provider: sign the claims as an HS256 JWT."""
    signed_part = encode({"alg": "HS256", "typ": "JWT"}) + "." + encode(claims)
    mac = hmac.new(key, signed_part.encode(), hashlib.sha256).digest()
    return signed_part + "." + b64url(mac)


def authenticate(token, now):
    """Who is calling? Return verified claims, or raise ValueError."""
    try:
        head, body, signature = token.split(".")
        algorithm = json.loads(unb64url(head)).get("alg")
        given = unb64url(signature)
    except Exception:
        raise ValueError("malformed token") from None
    if algorithm != "HS256":                      # never let the token choose the check
        raise ValueError("unexpected algorithm")
    expected = hmac.new(KEY, f"{head}.{body}".encode(), hashlib.sha256).digest()
    if not hmac.compare_digest(expected, given):
        raise ValueError("bad signature")
    claims = json.loads(unb64url(body))           # trusted only after the signature check
    if claims.get("iss") != ISSUER:
        raise ValueError("wrong issuer")
    if claims.get("aud") != AUDIENCE:
        raise ValueError("wrong audience")
    if now >= claims.get("exp", 0):
        raise ValueError("token expired")
    return claims


def authorize(claims, permission, invoice_id):
    """May this caller do this to this object? Return a refusal reason, or None."""
    granted = set()
    for role in claims.get("roles", []):
        granted |= ROLE_PERMISSIONS.get(role, set())
    if permission not in granted:                 # function level: role check
        return f"no role grants {permission}"
    if INVOICE_TENANT[invoice_id] != claims.get("tenant"):   # object level
        return "invoice belongs to another tenant"
    return None


def handle(method, invoice_id, token, now=NOW):
    try:
        claims = authenticate(token, now)
    except ValueError as problem:
        return 401, str(problem)
    refusal = authorize(claims, NEEDS[method], invoice_id)
    if refusal:
        return 403, refusal
    return 200, f"{claims['sub']} did {NEEDS[method]} on {invoice_id}"


def claims_for(sub, roles, aud=AUDIENCE):
    return {"iss": ISSUER, "aud": aud, "sub": sub, "tenant": "acme",
            "roles": roles, "exp": NOW + 900}


ana = mint(claims_for("ana", ["viewer"]))
raj = mint(claims_for("raj", ["admin"]))
head, body, signature = ana.split(".")
forged_body = encode(claims_for("ana", ["admin"]))
unsigned = encode({"alg": "none"}) + "." + forged_body + "."
tampered = f"{head}.{forged_body}.{signature}"
other_api = mint(claims_for("ana", ["admin"], aud="payroll-api"))

if __name__ == "__main__":
    requests = [("GET", "inv-1", unsigned, NOW), ("GET", "inv-1", tampered, NOW),
                ("GET", "inv-1", ana, NOW + 900), ("GET", "inv-1", other_api, NOW),
                ("GET", "inv-1", ana, NOW), ("DELETE", "inv-1", ana, NOW),
                ("DELETE", "inv-2", raj, NOW), ("DELETE", "inv-1", raj, NOW)]
    for number, (method, invoice_id, token, now) in enumerate(requests, 1):
        status, detail = handle(method, invoice_id, token, now)
        print(f"{number}. {method:6} {invoice_id} -> {status} {detail}")

Running python3 check_request.py prints:

text
1. GET    inv-1 -> 401 unexpected algorithm
2. GET    inv-1 -> 401 bad signature
3. GET    inv-1 -> 401 token expired
4. GET    inv-1 -> 401 wrong audience
5. GET    inv-1 -> 200 ana did invoice:read on inv-1
6. DELETE inv-1 -> 403 no role grants invoice:delete
7. DELETE inv-2 -> 403 invoice belongs to another tenant
8. DELETE inv-1 -> 200 raj did invoice:delete on inv-1

What each line shows:

  • 1 and 2 are forgeries. Both carry claims that say Ana is an admin. The first sets alg to none and has no signature. The second reuses the signature from Ana's real viewer token, which no longer matches the altered claims.
  • 3 and 4 have valid signatures and are still rejected. Ana's token expires at NOW + 900, so a request at exactly that second is too late. Request 4 uses a token the same issuer minted for payroll-api. Without the audience check, a token issued for any other API would work here.
  • 5 to 8 are authenticated, so every refusal is a 403. Ana's viewer role does not include invoice:delete. Raj is an admin, but inv-2 belongs to Globex and his token says Acme. Deleting his own tenant's invoice succeeds.

Delete the tenant comparison in authorize and request 7 returns 200: an admin of one customer deletes another customer's invoice. That one missing line is broken object level authorization.

A production API would use an asymmetric algorithm such as RS256, so that it holds only a public key and cannot mint tokens itself, and it would use a maintained JWT library. The checks and their order stay the same. A maintained library also handles aud arriving as a list of strings, which RFC 7519 allows; this script compares a single string to stay short.

Edge cases and limitations

A valid signature is not a validated token
Signature verification proves who signed a token, not that the token was meant for your service. Microsoft's investigation of the 2023 Storm-0558 intrusion reports that its mail system accepted a request for enterprise email with a token signed by a consumer signing key, because developers assumed the validation libraries performed complete validation and did not add the required issuer and scope validation. After the signature check, compare the issuer, audience and expiry yourself, and keep a test that sends a correctly signed token from the wrong issuer.
An access token is not proof of login
An OAuth access token shows that some client was granted some scope. It is addressed to the API, and a client that receives one cannot safely conclude who the user is. OWASP's API security guidance says plainly that OAuth is not authentication. To sign a user in, request the openid scope and validate the ID token, whose aud claim must contain your own client ID. To call an API, send the access token. Do not use one in place of the other.
Email addresses change, subject identifiers do not
It is tempting to key user records on the email claim. Google's OpenID Connect documentation warns against it and says to use the sub claim, which stays the same when a user changes their email address. OpenID Connect defines sub as locally unique and never reassigned within the issuer, so store the issuer and sub together as the user's key. Keying on email can hand an old user's data to whoever holds that address later.
A signed token stays valid after the permission is removed
A resource server that validates JWTs locally does not ask the issuer on each request. If an administrator removes Ana's role at 09:00 and her token expires at 09:15, she keeps the old permissions for fifteen minutes. Shorter lifetimes shrink the window, and RFC 6750 suggests bearer tokens that live an hour or less. For actions that cannot wait, read the user's current roles on the server or call the issuer's revocation or introspection endpoint, and accept the extra request.
A 403 confirms that the record exists
Answering 403 for another tenant's invoice tells the caller that the invoice exists. RFC 9110 allows a server that wants to hide a forbidden resource to answer 404 Not Found. A common design for object-level refusals is to put the tenant into the database query, so a record outside the caller's tenant is simply not found. Keep 403 for function-level refusals, and always send a WWW-Authenticate header with a 401, which the same RFC requires.
With HS256, every verifier can also issue tokens
The worked example signs with a shared secret, so the API that checks tokens holds the same key that mints them. Any service given that key can forge a token for any user. This is acceptable when one system both issues and checks. Across services, use an asymmetric algorithm such as RS256: the issuer keeps the private key and publishes public keys at its jwks_uri, as Google's discovery document shows, so verifiers can check signatures without being able to create them.

When to use it, and when something simpler is enough

Use it when

  • Use an API key when the caller is a server-side program you can name, one key per integration, and no end user's consent or identity is involved.
  • Use the OAuth 2.0 authorization code flow with PKCE when an application must act on a user's data in another system without ever handling that user's password.
  • Use the OAuth 2.0 client credentials flow when one service calls another and no user is present, and you want short-lived scoped tokens in place of a permanent key.
  • Use OpenID Connect or SAML single sign-on when the customer's staff must sign in with their corporate accounts. Pick whichever protocol both their identity provider and your application support.
  • Use RBAC when permissions follow job function and a handful of roles covers almost everyone.

Think twice when

  • Do not use an API key to identify end users, and do not put a secret key in browser or mobile code, where anyone can read it.
  • Do not build your own password store, login page or token format when the customer already has an identity provider that speaks OpenID Connect or SAML.
  • Do not rely on roles alone when access depends on the specific record, such as its owner or tenant. Add an object-level check or an attribute-based rule.
  • Do not start new work on the OAuth implicit grant or the password grant. Current OAuth security guidance advises against the first and prohibits the second.

A simpler alternative. One API key per integration, sent over TLS and stored in a secrets manager, is enough for an internal prototype with a single trusted caller and no per-user data. It stops being enough when a second kind of user needs different access, when the customer requires sign-in through their identity provider, or when a third party needs access on behalf of individual users. At that point move to OpenID Connect or SAML for sign-in, OAuth 2.0 for API access, and roles for permissions.

Key takeaways

  • Authentication establishes who or what is calling and fails with 401, while authorization decides what that caller may do and fails with 403.
  • An API key identifies a program, an OAuth 2.0 access token carries scoped and delegated access to an API, and an OpenID Connect ID token or SAML assertion is an identity provider's signed statement about who signed in.
  • The authorization code flow with PKCE is the default OAuth flow when a user is present, client credentials is the flow when no user is involved, and the implicit and password grants do not belong in new work.
  • A signature check alone does not validate a token, because the issuer, audience and expiry must also match what your service expects on every request.
  • RBAC maps users to roles and roles to permissions, which decides whether a kind of user may perform a kind of action but not whether this user may touch this record.
  • Every endpoint that accepts a record ID needs a server-side object-level check, because leaving it out is the highest-ranked risk in the OWASP API Security Top 10.

Example 1 of 5

Stripe API keys: publishable, secret and restricted keys for program-to-program calls

StripeDocumented in official docs

Stripe's payments API authenticates every request with an API key. The Stripe documentation pages on API keys and restricted API keys, and the authentication section of the API reference, describe the key types, how a key is sent and how it is rotated. [22][23][24][13]

The problem

A merchant's systems call the Stripe API from places with very different levels of trust: checkout code running in a customer's browser, a back-end billing service, a reporting job and third-party tools. Most of these calls have no person signing in, so the credential has to identify the merchant's account by itself. It also has to limit the damage when a copy leaks, because a key that can move money is a target.

Where this topic fits

The API key is the authentication step. It tells Stripe which account and which integration is calling. Stripe then attaches authorization to the key itself, through the key type and, for restricted keys, a permission level per resource. The merchant creates keys in the Dashboard beforehand. On each request Stripe authenticates the key and then checks whether that key may make the call.

How it is applied, step by step

  1. Stripe issues several key types per account. The prefix shows the type and the mode: pk_ for publishable, sk_ for secret and rk_ for restricted, followed by test_ or live_.
  2. Browser and mobile code uses the publishable key, which can identify the account and create tokens from payment details but cannot perform sensitive operations.
  3. Server code sends a secret or restricted key over HTTPS as the HTTP Basic auth username with an empty password, or as a bearer token.
  4. For each back-end service the merchant creates a restricted key and sets None, Read or Write for each resource. A call outside those permissions is refused with an error.
  5. Keys are supplied from a secrets vault or an environment variable, never from source code, and an access policy can limit a key to known server addresses.
  6. When a key may have leaked, or a team member with access leaves, the merchant rotates it. The old and new keys overlap for a grace period so services can switch without downtime.

Why this approach fits

There is nobody to send to a sign-in page when a billing service calls an API at night, so an interactive protocol does not fit. A key is one header and works from any language. Stripe's design adds the two things a bare key lacks. Distinct key types separate code that runs in public from code that runs on a server, and restricted keys apply least privilege per service, so a leaked reporting key cannot create charges.

Limitation or tradeoff

A key is a long-lived bearer secret. Whoever copies it can use it until someone rotates it, and the request does not show which person or process sent it. Stripe's documentation is direct about this: an unrestricted secret key can do anything in the account, which is why Stripe recommends restricted keys and does not recommend secret keys for new use cases. A key also carries no user identity and no user consent, so it cannot stand in for signing a person in. Rotation needs planning, because every service that holds the old key must be updated before the grace period ends.

What the sources document

  • Stripe uses API keys to authenticate requests from an integration and to determine which Stripe resources it can access. The key types table describes the publishable key as safe to expose and unable to perform sensitive operations, and the secret key as having unrestricted permissions. [22]
  • A restricted key has a permission of Read, Write or None for each resource. If it lacks the permission for a request Stripe returns an invalid request error, and Stripe advises a separate restricted key for each service that uses its APIs. [23]
  • The API authenticates requests with HTTP Basic Auth, using the API key as the username and no password. Bearer auth can be used instead, and calls made over plain HTTP fail. [24]

  • The OWASP API Security Top 10 page on broken authentication says API keys should not be used for user authentication and should only be used to authenticate API clients. [13]

Example 2 of 5

GitHub OAuth apps: delegated API access for web apps and command-line tools

GitHubDocumented in official docs

GitHub lets third-party applications call its API on a user's behalf through OAuth apps. The GitHub Docs pages "Authorizing OAuth apps" and "Scopes for OAuth apps" describe the two supported flows and how scopes limit a token. [15][16][7][2]

The problem

Continuous integration services, editors and command-line tools need to read or change a user's repositories. Asking for the user's GitHub password would give the tool everything the user can do, and the user could not withdraw access from one tool without changing the password for all of them. Command-line tools add a second problem: they often run where there is no browser to redirect and no web address to receive a callback.

Where this topic fits

This is OAuth 2.0 used for authorization, with GitHub in two roles. github.com is the authorization server that signs the user in, shows the consent screen and issues tokens. api.github.com is the resource server that accepts them. The third-party tool is the client and the user is the resource owner. Before the flow, the developer registers the app to get a client ID and secret. After it, every API call carries the access token.

How it is applied, step by step

  1. A web app redirects the user to GitHub's authorize endpoint with its client ID, the scopes it wants, a random state value and, as GitHub strongly recommends, a PKCE code challenge.
  2. GitHub signs the user in if needed and shows the requested scopes. The user approves, and may grant fewer scopes than the app asked for.
  3. GitHub redirects back to the app with a temporary code and the state. The app aborts if the state does not match the value it sent.
  4. The app's server exchanges the code, its client secret and the PKCE code verifier at the token endpoint for an access token.
  5. A tool without a browser uses the device flow. It requests a device code and a short user code, shows the user code, and polls the token endpoint while the user enters the code at github.com/login/device on any device.
  6. The app calls the API with the token in the Authorization header. A call succeeds only if the token's scopes cover it and the user has that permission in the first place.

Why this approach fits

The password is typed only on github.com, so the tool never holds it. The token is limited to the scopes on the consent screen, and the user can withdraw one tool's access without affecting the others. The device flow keeps the same properties where a redirect is impossible: it moves the approval step to a browser on another device and lets the tool wait.

Limitation or tradeoff

OAuth app scopes are coarse. The documentation describes repo as full access to public and private repositories, so a tool that needs one repository receives all of them. The same page suggests considering a GitHub App instead, which uses fine-grained permissions in place of scopes. OAuth app tokens are bearer tokens, and GitHub describes expiring tokens as something an app opts in to, so a copied token may keep working until it is revoked. The device flow can also be abused for phishing: RFC 8628 notes that an attacker can start the flow on a device of their own and persuade a user to enter the code, so users should enter a code only for a device in front of them.

What the sources document

  • GitHub's OAuth implementation supports the standard authorization code grant and the OAuth 2.0 Device Authorization Grant, and does not support the implicit grant. The state parameter is described as an unguessable random string that protects against cross-site request forgery, the code challenge method must be S256, and the temporary code expires after 10 minutes. [15]
  • The device flow must be enabled in the app's settings. Its first response contains a device code, a user code, a verification URI, an expiry that defaults to 900 seconds and a minimum polling interval, and the app then polls the token endpoint with the device_code grant type. [15]
  • The scopes page states that scopes only limit what an OAuth token can do and never give it more permission than the user already has, and it describes the repo scope as full access to public and private repositories. [16]
  • RFC 8628 defines the authorization_pending and slow_down polling errors, and its security considerations describe remote phishing, in which the flow is started on a device in an attacker's possession. [7]
  • RFC 7636 defines the S256 code challenge as the base64url encoding of the SHA-256 hash of the code verifier, and says a client that is capable of using S256 must use it. [2]

Sign in with Google: OpenID Connect login that ends in a validated ID token

GoogleDocumented in official docs

Google's identity platform lets any application sign users in with their Google accounts. The Google for Developers page "OpenID Connect" documents the flow, and Google publishes a live discovery document listing its current endpoints and capabilities. [17][18][8]

The problem

An application wants users to sign in without creating another password, and wants to stay out of the business of storing passwords, resetting them and running multi-factor prompts. It needs a trustworthy answer to one question, which user is this, from a party it has reason to believe. A business application often needs a second answer: does this account belong to our company's Google Workspace domain?

Where this topic fits

This is authentication delegated to an identity provider. Google is the OpenID provider and the application is the relying party. The flow is the OAuth 2.0 authorization code flow with the openid scope, and its product is an ID token. Everything after that belongs to the application: it creates its own session and applies its own roles. Google's token says who the user is. It does not say what the user may do in your product.

How it is applied, step by step

  1. The application reads Google's endpoints from the discovery document at a well-known URL, so that it does not hard-code them.
  2. It creates an anti-forgery state token and redirects the user to Google's authorization endpoint with response_type=code, a scope that includes openid, its redirect URI, the state and a nonce.
  3. After the user signs in to Google, the application confirms the returned state and exchanges the code, together with its client secret, at the token endpoint.
  4. The response contains an access token and an ID token, which is a signed JWT.
  5. The application validates the ID token: the signature against Google's published keys, the iss value, the aud value against its own client ID, the expiry, and the hd claim when sign-in is restricted to one Workspace domain.
  6. It looks the user up by the sub claim, creates its own session and applies its own authorization rules.

Why this approach fits

The application never sees or stores a password, and Google's sign-in protections apply without extra work. Because the flow is standard OpenID Connect, the same relying-party code can work with any provider that publishes a discovery document, which is how one sign-in implementation can serve different customers' identity providers. The ID token is addressed to the application through aud, and that is what makes it usable as proof of sign-in.

Limitation or tradeoff

An ID token authenticates. It carries no permissions for your product, so authorization is still yours to build. The hd request parameter is only a hint to Google's sign-in screen, and the documentation warns that the application must check the hd claim in the token to restrict access to a domain. Emails can change, which is why sub is the key. Sign-in also now depends on a third party: people without a Google account cannot use it, and a suspended account locks the user out of your application too. The documentation allows skipping validation only when the token arrives directly from Google over HTTPS, and says any other component that receives the token must validate it.

What the sources document

  • Google states that its OAuth 2.0 APIs can be used for both authentication and authorization, and that its implementation for authentication conforms to the OpenID Connect specification and is OpenID Certified. [17]
  • The documented server flow has six steps: create an anti-forgery state token, send an authentication request to Google, confirm the state token, exchange the code for an access token and ID token, obtain user information from the ID token, and authenticate the user. [17]
  • Validation of an ID token is listed as verifying the issuer's signature with keys from the jwks_uri in the discovery document, checking that iss is https://accounts.google.com or accounts.google.com, that aud equals the app's client ID, that exp has not passed, and that hd matches when an hd parameter was used. [17]
  • The page warns against using the email field as a unique identifier and says to always use sub. It also says the hd request parameter must not be relied on to control access, because client-side requests can be modified. [17]
  • On 11 October 2026 Google's discovery document listed the issuer https://accounts.google.com, RS256 as the only ID token signing algorithm, and plain and S256 as supported PKCE code challenge methods. [18]

AWS Management Console sign-in through a corporate SAML identity provider

Amazon Web ServicesDocumented in official docs

AWS lets an organisation's employees reach the AWS Management Console by signing in at the organisation's own SAML 2.0 identity provider. The IAM User Guide pages on enabling SAML federated principals to access the console and on configuring SAML assertions describe the flow and the required attributes. [20][21][9]

The problem

A company with hundreds of engineers needs to give them console access to its AWS accounts. Creating a separate AWS user and password for each person duplicates the corporate directory, and accounts tend to stay behind when someone changes team or leaves. The company wants the directory to remain the single place where people are added, grouped and removed, and wants each group to receive only the AWS permissions its job needs.

Where this topic fits

SAML handles authentication: the company's identity provider signs the user in and vouches for them, and AWS acts as the service provider. Authorization travels in the same message. The assertion names one or more IAM roles, and each role's policies decide what a session may do. An administrator establishes trust in both directions beforehand. At sign-in, AWS exchanges the assertion for temporary credentials. In SAML's terms the documented flow is IdP-initiated, because the user starts at the organisation's own portal rather than at AWS. The sequence diagram earlier in this lesson shows the service-provider-initiated variant.

How it is applied, step by step

  1. An administrator exchanges metadata. The identity provider's metadata document is uploaded to IAM to create a SAML provider, and AWS's SAML metadata file is installed at the identity provider so that it knows AWS as a service provider.
  2. The administrator creates an IAM role. Its trust policy names the SAML provider as the trusted principal and allows the AssumeRoleWithSAML action under stated conditions. Its permission policy lists what the role may do.
  3. The identity provider is configured to place a Role attribute in each assertion, pairing a role with the provider. A typical setup derives it from the user's directory groups.
  4. At sign-in the user opens the organisation's portal and chooses AWS. The portal verifies the user's identity and generates a SAML authentication response.
  5. The browser posts the assertion to the AWS sign-in endpoint, which requests temporary security credentials for the user and builds a console sign-in URL.
  6. The browser is redirected to the console. If the assertion maps to more than one role, the user first chooses which role to use.

Why this approach fits

The directory stays the only source of truth. Removing someone from a directory group removes the role from their next assertion, and nobody has a long-lived AWS password to forget about. The role mapping is RBAC expressed across two systems: the identity provider decides who holds which role, and AWS decides what each role can do. Sessions run on temporary credentials that expire without anyone having to clean up.

Limitation or tradeoff

The identity provider becomes the most sensitive system in the chain. Anyone who can change its group memberships or attribute rules, or who obtains its signing key, can obtain AWS roles. A session that has already started keeps working until its credentials expire, which can be up to 12 hours for a console session, even if the directory account is disabled in the meantime. The documentation points to revoking a role's active sessions for that case. The setup is also unforgiving: attribute names are case-sensitive, and a mistake in the trust policy conditions either blocks everyone or admits more people than intended.

What the sources document

  • In the documented flow the user starts at the organisation's portal, the portal verifies the user's identity and generates a SAML authentication response, the browser posts the assertion to the AWS sign-in endpoint, and the endpoint requests temporary security credentials and creates a console sign-in URL. The guide says the user never has to supply any AWS credentials. [20]
  • The IAM role must identify the organisation's identity provider as a trusted principal, and the role also defines what users authenticated by that provider are allowed to do in AWS. The example trust policy allows the sts:AssumeRoleWithSAML action with a condition on saml:aud. [20]
  • The Role attribute holds one or more values, each a comma-delimited pair of a role ARN and a SAML provider ARN. With several pairs the user is asked which role to assume, and the attribute's Name is case-sensitive. [21]
  • The optional SessionDuration attribute accepts 900 to 43200 seconds, and without it the credentials last one hour. The same page says active console sessions for a role can be disabled with Revoke Sessions. [21]
  • The SAML technical overview uses the term IdP-initiated web SSO for a flow in which the user has first authenticated at the identity provider and then goes to a protected resource at a service provider. [9]

Kubernetes RBAC: roles and bindings that authorize every request to the cluster API

KubernetesDocumented in official docs

Kubernetes decides whether each request to its API server is allowed by evaluating RBAC objects stored in the cluster. The Kubernetes reference page "Using RBAC Authorization" defines these objects and the rules that govern them. [19]

The problem

A cluster's API is shared by people and by programs. Developers from several teams, CI pipelines and the workloads themselves all send requests to the same API server, which can read secrets and delete running services. Each caller must be limited to what its job needs, for example a developer who may list pods in one team's namespace but may not read secrets or touch other namespaces.

Where this topic fits

RBAC is the authorization step. The API server first authenticates the caller as a user, a group member or a service account. The RBAC authorizer then answers one question: may this subject perform this verb on this resource in this namespace? Roles hold the permissions, bindings attach roles to subjects, and administrators manage both as ordinary API objects.

How it is applied, step by step

  1. The cluster administrator starts the API server with the RBAC authorizer enabled.
  2. A Role (inside one namespace) or a ClusterRole (cluster-wide) lists rules. Each rule names API groups, resources and the verbs allowed on them, such as get, list and watch on pods.
  3. A RoleBinding grants a role to subjects within one namespace, and a ClusterRoleBinding grants it across the cluster. Subjects are users, groups or service accounts.
  4. For each request the permissions from all of the caller's bindings are added together. There are no deny rules, so a request that no rule allows is refused.
  5. Teams reuse the built-in ClusterRoles view, edit and admin by binding them inside their own namespaces, which avoids writing rules from scratch.
  6. The API refuses to let a user create or change a role or binding that grants permissions the user does not already hold, unless that user has been given the escalate or bind verb.

Why this approach fits

The number of people and programs grows much faster than the number of distinct jobs, so attaching permissions to a few roles and binding subjects to them keeps the rules reviewable. Because roles and bindings are API objects, they can be kept in version control and audited like any other configuration (see Kubernetes Basics). Additive rules with no deny make the outcome easy to reason about: a subject can do the union of what its bindings grant and nothing else.

Limitation or tradeoff

Additive-only rules cannot express an exception such as "everything except secrets". You have to list what is allowed. Rules work on resource types and names, so they cannot say "only the pods this user created". Broad roles also hide surprises: the documentation notes that the edit role allows reading Secrets and running pods as any service account in the namespace, which is a route to that account's API access, and it strongly discourages granting cluster-admin to all service accounts. RBAC only authorizes. It depends entirely on the API server's authentication to say who the caller is.

What the sources document

  • The page defines RBAC as a method of regulating access to computer or network resources based on the roles of individual users within an organisation, and says RBAC authorization uses the rbac.authorization.k8s.io API group. [19]
  • The RBAC API declares four kinds of object: Role, ClusterRole, RoleBinding and ClusterRoleBinding. A Role always sets permissions within one namespace, a ClusterRole is not namespaced, and permissions are purely additive with no deny rules. [19]
  • A role binding holds a list of subjects (users, groups or service accounts) and a reference to the role being granted. After a binding is created, the role it refers to cannot be changed. [19]
  • The default view role does not allow viewing Secrets, because reading them would give access to service account credentials in the namespace, which the page calls a form of privilege escalation. [19]
  • A user can create or update a role only if they already hold all the permissions it contains at the same scope, or have been granted the escalate verb on roles or clusterroles. [19]

4Common mistakes

  1. Verifying a token's signature and then trusting every claim inside it.

    Why it causes problems
    A correctly signed token from a different issuer, for a different API or past its expiry is accepted. Microsoft's Storm-0558 investigation describes this gap in its mail system: the signature was checked, and the issuer and scope were not.
    How to recognise it
    Find the token validation call and read the options it sets. A decode call with no expected issuer or audience, or a test suite with no wrong-audience case, is the sign.
    How to fix it
    Pin the algorithm, issuer and audience in configuration and reject tokens that fail any of them. Add tests that send an expired token, a token for another audience and an unsigned token.

  2. Loading a record by the ID in the request without checking that the caller may access that record.

    Why it causes problems
    Any authenticated user can read or change other users' data by changing an ID in the URL. OWASP ranks this flaw, broken object level authorization, first among API security risks.
    How to recognise it
    Sign in as user A and copy the ID of one of A's records. Then request it as user B from a different tenant. A 200 response is the bug.
    How to fix it
    Put the caller's tenant or user ID from the verified token into every data query, answer 404 or 403 when nothing matches, and add an automated two-user test for each endpoint that takes an ID.

  3. Putting a secret key or client secret in a mobile app, a single-page app or a Git repository.

    Why it causes problems
    Anything shipped to a device or pushed to a repository can be extracted. The secret then works for whoever found it, with all of its permissions, until it is rotated.
    How to recognise it
    Search the repository history and the built front-end bundle for key prefixes such as sk_live_ and for the words secret and token. A secret scanner in CI automates the search.
    How to fix it
    Keep secrets on the server in a secrets manager. Give public clients only publishable identifiers, use the authorization code flow with PKCE for them, and rotate any secret that has ever been committed.

  4. Treating an OAuth access token or an API key as proof of which user is signed in.

    Why it causes problems
    An access token issued to a different application for the same user is accepted as a login. A shared API key makes every request look like the same caller, so actions cannot be attributed to a person.
    How to recognise it
    The login code calls a profile endpoint with an access token and never checks an ID token's audience, or the audit log shows one identity for every user of an integration.
    How to fix it
    Sign users in with OpenID Connect or SAML and validate the ID token or assertion. Use access tokens only to call APIs, and API keys only to identify client programs.

  5. Enforcing permissions only in the user interface by hiding buttons and menu items.

    Why it causes problems
    The API still performs the action for anyone who sends the request directly. The OWASP Authorization Cheat Sheet says developers must never rely on client-side access control checks.
    How to recognise it
    Sign in as a low-privilege user and replay an administrator's request with curl. If it succeeds, the server is not checking.
    How to fix it
    Check the permission on the server for every request, in shared middleware instead of handler by handler, deny by default, and treat hidden interface elements as a convenience only.

  6. Giving every integration one all-powerful key, or assigning most users an admin role.

    Why it causes problems
    A single leak or a single mistaken click has the largest possible effect, and an access review cannot tell who needs what.
    How to recognise it
    Count the credentials and roles in use. One key shared by several services, or more administrators than ordinary users, shows that least privilege was skipped.
    How to fix it
    Create one credential per integration with only the scopes it uses, define roles from job functions, and review role assignments on a schedule.

Exercise 1

Compute a PKCE challenge and enforce it on a toy authorization server

CodingIntermediateAbout 35 min (estimate)Hypothetical scenario

OAuth clients protect the authorization code with PKCE. RFC 7636 gives a test vector in its Appendix B:

  • code_verifier: dBjftJeZ4CVP-mB92K27uhbUJU1p1r_wW1gFWFOEjXk
  • expected code_challenge for the S256 method: E9Melhoa2OwvFrEMTJguCHaoeK1t8URWbuGJSstw-cM

Write pkce.py using only the Python standard library. It must contain:

  1. make_verifier(), which returns a new random code verifier.
  2. challenge(verifier), which returns the S256 code challenge.
  3. A small AuthorizationServer class with authorize(code_challenge, method), which returns a one-time authorization code, and token(code, code_verifier), which returns a token response or an error.

Then show three things: your challenge reproduces the RFC value, a client that holds the verifier can redeem its code, and an attacker who stole a code but not the verifier cannot.

Requirements

  • The S256 transformation is BASE64URL(SHA256(ASCII(code_verifier))) with the trailing = padding removed.
  • make_verifier builds the verifier from 32 random bytes taken from the secrets module, which gives 43 characters from the URL-safe alphabet.
  • The authorize method refuses any challenge method other than S256.
  • The token method returns an invalid_grant error for an unknown code, a reused code or a verifier whose challenge does not match, and it compares the values with hmac.compare_digest.
  • A code can be redeemed at most once, even when the first attempt failed.

Expected behaviour

Running the script prints the following. Token values are random, so the script prints only the field names of a successful response.

text
RFC 7636 vector matches: True
verifier length: 43
attacker with stolen code: {'error': 'invalid_grant'}
client with verifier: ['access_token', 'expires_in', 'token_type']
replayed code: {'error': 'invalid_grant'}

Hint 1

base64.urlsafe_b64encode adds = padding. Remove it with rstrip(b"=") before decoding to text.

Hint 2

Hash the ASCII bytes of the verifier string, not the 32 random bytes the verifier was made from.

Hint 3

Remove the code from the server's store before you compare challenges, so that a failed attempt also uses the code up.

Show solution
python
import base64
import hashlib
import hmac
import secrets

RFC_VERIFIER = "dBjftJeZ4CVP-mB92K27uhbUJU1p1r_wW1gFWFOEjXk"
RFC_CHALLENGE = "E9Melhoa2OwvFrEMTJguCHaoeK1t8URWbuGJSstw-cM"


def b64url(raw):
    return base64.urlsafe_b64encode(raw).rstrip(b"=").decode()


def make_verifier():
    return b64url(secrets.token_bytes(32))  # 32 random bytes become 43 characters


def challenge(verifier):
    return b64url(hashlib.sha256(verifier.encode("ascii")).digest())


class AuthorizationServer:
    """Only the parts of an authorization server that PKCE touches."""

    def __init__(self):
        self.challenges = {}  # authorization code -> code_challenge

    def authorize(self, code_challenge, method):
        if method != "S256":
            raise ValueError("only S256 is accepted")
        code = secrets.token_urlsafe(16)
        self.challenges = {**self.challenges, code: code_challenge}
        return code

    def token(self, code, code_verifier):
        stored = self.challenges.get(code)
        self.challenges = {k: v for k, v in self.challenges.items() if k != code}  # one use
        if stored is None or not hmac.compare_digest(challenge(code_verifier), stored):
            return {"error": "invalid_grant"}
        return {"access_token": secrets.token_urlsafe(24), "token_type": "Bearer", "expires_in": 3600}


if __name__ == "__main__":
    print("RFC 7636 vector matches:", challenge(RFC_VERIFIER) == RFC_CHALLENGE)

    verifier = make_verifier()
    print("verifier length:", len(verifier))

    server = AuthorizationServer()
    stolen_code = server.authorize(challenge(verifier), "S256")
    print("attacker with stolen code:", server.token(stolen_code, make_verifier()))

    code = server.authorize(challenge(verifier), "S256")
    print("client with verifier:", sorted(server.token(code, verifier)))
    print("replayed code:", server.token(code, verifier))

    try:
        server.authorize(verifier, "plain")
    except ValueError as problem:
        print("plain method:", problem)

Why it works. The authorization request carries only the hash of the verifier. SHA-256 cannot be run backwards, so someone who sees the request and later intercepts the code still does not know the verifier. The server stores the challenge next to the code and recomputes it from whatever verifier arrives at the token endpoint. A guessed verifier produces a different hash, so the attacker receives invalid_grant.

The first print is the important test: it shows that the encoding details (ASCII input, URL-safe alphabet, no padding) match the specification. A challenge that is off by one padding character fails against every real authorization server.

The server removes the code before it compares, so each code gets exactly one attempt. An attacker who redeems a stolen code first with a wrong verifier therefore also blocks the real client, who has to start the flow again. That is the safe outcome. The plain method is refused because it sends the verifier itself as the challenge, which protects nothing when the first request can be observed.

7AuthorizationThe role is read from a header the client controlsAdd X-Role: admin to any request and the check passes
9AuthorizationThe status code is wrong: 401 for a known caller who lacks permissionClients treat it as a sign-in problem and retry, and monitoring cannot tell failed logins from denied actions
10AuthorizationNo object-level check: the report is fetched by ID aloneAn analyst at customer A requests a report ID belonging to customer B and receives it
11Authorizationreport may be NoneAn unknown ID raises an error and returns 500, so the difference between 500 and 200 reveals which IDs exist

Lines 6 and 7 together mean that the endpoint has no working authentication and no working role check. Line 10 would remain a serious flaw even if they were fixed, because every correctly signed-in analyst could still read every tenant's reports. That is broken object level authorization, the first item in the OWASP API Security Top 10.

Part 2. The corrected order of checks

  1. Read the token from the Authorization: Bearer header. If it is missing, return 401 with a WWW-Authenticate: Bearer header.
  2. Verify the signature with the identity provider's public key and an algorithm fixed in configuration. Check iss, aud and exp. On any failure, return 401.
  3. Take the roles and the tenant from the verified claims only. Ignore X-Role.
  4. If no role grants report:read, return 403.
  5. Fetch the report by ID and tenant. If nothing matches, return 404.
  6. Return the report with 200.
python
@app.get("/api/reports/<report_id>")
def get_report(report_id):
    claims = authenticate(request.headers.get("Authorization"))  # raises -> 401
    if "report:read" not in permissions_of(claims["roles"]):
        return {"error": "forbidden"}, 403
    report = db.reports.find_one(id=report_id, tenant=claims["tenant"])
    if report is None:
        return {"error": "not found"}, 404
    return report.to_json(), 200

This is an outline: authenticate and permissions_of are the two functions from the worked example, adapted to your framework. Separately, remove the key on line 1 from the code and from the mobile app, rotate it, and load its replacement from a secrets manager on the server only.

Part 3. Roles

Rolereport:readreport:createreport:deleteuser:manage
support_agentyesnonono
analystyesyesnono
tenant_adminyesyesyesyes

Two rules do not fit in the table:

  • "In their own tenant" applies to all three roles. It depends on which record is requested, so it is an object-level check: compare the tenant in the verified token with the tenant of the record, as step 5 does.
  • "Only for customers assigned to them" depends on a relationship between the support agent and a customer. It needs a lookup in an assignment table at request time.

A role answers what kind of action a kind of user may take. Both of these rules ask about a particular record, which is where attribute-based or relationship-based rules are added on top of RBAC.

Check your answer

  • Did you find the unverified signature, the X-Role header and the missing tenant filter?
  • Does your corrected handler return 401, 403 and 404 for three different failures?
  • Does your table give support agents only report:read and tenant admins all four permissions?
  • Did you name both the tenant boundary and the customer assignment as rules outside the role table?
