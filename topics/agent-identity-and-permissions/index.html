Agent Identity, Permissions and Least Privilege

Agent identity is the answer to who an AI agent is acting as when it calls a tool: an identity of its own, a user it represents, or both. Permissions and least privilege limit what that identity can reach, so a mistaken or manipulated agent can do only bounded damage, and an audit trail records what it did and under whose authority.

1Overview

Why it matters

A language model chooses its next action from text, and some of that text is written by strangers: web pages, emails, issue comments, tool results. Whatever credentials the agent holds are what an attacker gets when that text steers it. In May 2025 Invariant Labs showed an agent with a user's GitHub account connected that read a malicious issue in a public repository and then copied details of the user's private repositories into a public pull request. Their write-up calls this an architectural problem at the agent-system level, not a bug in the GitHub server code, and says a well-aligned model did not prevent it.

Identity and permission decisions are therefore security decisions made before any prompt is written. They also decide practical questions: whether a security team can say which actions an agent took and for whom, whether one misbehaving agent can be switched off without touching a person's account, and whether a customer will let an agent near their systems at all. Engineers who connect agents to real APIs, and the reviewers and forward deployed engineers who sign those connections off, need this vocabulary.

  • Write allow, ask and deny rules for an agent's tools and say which layer enforces each one.

  • Name the three root causes of excessive agency and one control for each.
  • Specify the fields of an audit record that lets you reconstruct who did what through which agent.

Key terms

Agent identity
A distinct, registered identity for an agent, separate from the person who runs it and from the application that hosts it, so its actions can be told apart, limited and revoked on their own.
Delegation
The agent acts for a user using rights the user chose to pass on, while keeping its own identity, so a service can see both parties. RFC 8693 contrasts this with impersonation.
Impersonation
The agent is given all of a user's rights and cannot be told apart from that user, for example because it holds the user's own password or long-lived token.
Scope
A named permission carried by a token, such as mail.read, that a service checks before it acts.
Audience
The service a token is addressed to. A service must reject tokens whose audience is some other service.
Token exchange
A request to a token service to swap one token for another that is narrower, shorter-lived or addressed to a different service (OAuth 2.0 Token Exchange, RFC 8693).
Least privilege
Giving an identity only the permissions the task needs, for only as long as it needs them.
Confused deputy
A program that holds authority and is tricked by a party without that authority into using it on that party's behalf.
Excessive agency
OWASP's name for an LLM system that can take damaging actions because it has too many functions, too many permissions or too much autonomy.
Complete mediation
Authorising every request in the downstream system itself, instead of trusting the model or the calling agent to have done so.

2Explanation

Introduction

In Authentication and Authorization you met the basic split: authentication proves who you are, and authorization decides what you may do. An ordinary web app can answer both from a login session. Agents break that assumption in two ways. The party deciding what happens next is a language model reading text, and Prompt Injection and LLM Security showed that anyone who can put text in front of the model can try to steer it. And the agent calls tools (see Designing Tools for Agents) that reach real systems with real credentials.

A hotel shows how this is normally handled. A guest gets a keycard for one room and the gym until checkout. A housekeeper gets a card for one floor, issued to that person by name. A delivery driver is escorted. Nobody is handed the master key and trusted to behave. Each card says who holds it, opens only certain doors, expires, and leaves a record in the lock. Agent security applies the same ideas to software and adds a question hotels rarely face: whose authority is the card carrying at this moment, the agent's or the guest's?

Five questions organise this lesson, and each one is a layer of control that sits on top of the one before it. If one layer fails, the layers below it still limit the damage.

We take the layers in order. First, who the agent acts as and how it gets a narrow credential. Then which tools it may call, how the confused deputy problem turns an obedient agent into a risk, and what an audit trail must record. A runnable example of about ninety lines shows a token exchange, a per-tool policy and an audit log working together, and five documented products show how real teams answer the same questions.

How it works

Who is the agent acting as?

Every tool call is made by some principal, meaning an identity that can be authenticated and given permissions. There are three ways to choose it, and RFC 8693 (opens in a new tab) supplies the vocabulary. With impersonation, A is given all of B's rights and cannot be told apart from B. With delegation, A keeps its own identity and it is understood that A acts representing B.

Vendors describe the same split in their own words. Microsoft's Entra Agent ID documentation separates autonomous access (rights given directly to the agent identity) from delegated access (rights belonging to a user, who controls which ones are passed on). Amazon's AgentCore Identity calls the first the client credentials grant (2LO), where the agent authenticates as itself, and the second the authorization code grant (3LO), where a user consents. AgentCore also defines an agent access token that carries both a workload identity and a user identity, so a downstream service can decide using both.

A rule of thumb: if the data or authority belongs to one person, delegate. If it belongs to the organisation, such as a nightly report or a shared queue, give the agent its own identity with a narrow role. If the action is hard to undo, put a person's approval in front of it whichever identity is used.

Scoped credentials and token exchange

An agent should not hold the user's own token. That token is often broad, long-lived and addressed to a different service, so whatever steals it from the agent gets everything the user has. Instead the agent asks a token service for a new token for one job. Token Exchange defines the request: the subject token says whose authority is being used, the optional actor token says who is acting, and the audience and scope narrow the result.

text
POST /token
grant_type=urn:ietf:params:oauth:grant-type:token-exchange
subject_token=USER_TOKEN          (whose authority is used)
subject_token_type=urn:ietf:params:oauth:token-type:access_token
actor_token=AGENT_TOKEN           (who is acting)
actor_token_type=urn:ietf:params:oauth:token-type:access_token
audience=https://mail.example     (the one service this token is for)
scope=mail.read                   (the narrowest permission that does the job)

The issued token records both parties. In RFC 8693 the sub claim is the subject, the act claim identifies the actor, and a chain of delegation is expressed by nesting one act inside another.

json
{
  "sub": "priya",
  "act": { "sub": "assistant-7" },
  "aud": "https://mail.example",
  "scope": "mail.read",
  "exp": 130
}

Demand four properties of any credential an agent receives: a narrow scope, a single audience, a short lifetime, and a record of both the user and the agent. The audience rule matters as much as the scope. The MCP authorization specification requires a server to validate that a token was issued specifically for it and to refuse any other token, and its security guidance calls the opposite habit, passing a client's token on to a downstream API ("token passthrough"), an anti-pattern: it lets a token be replayed elsewhere, bypasses the server's own controls and blurs the logs.

Keep the agent's own long-term secrets out of its code. Entra's documentation prefers managed identities over client secrets for production agents, and AgentCore stores OAuth tokens and keys in a vault that releases them only to the agent and user combination that obtained them.

Per-tool permissions

A tool call can be stopped in three places: the model's instructions, the harness that runs the tool, and the service the tool calls. Only the last two are controls. An instruction such as "never email outside the company" shapes what the model tries, and text from a stranger can override it. Claude Code's documentation states the right design plainly: permission rules are enforced by the program, not by the model.

A workable policy gives each tool one of three outcomes. Deny blocks the call. Ask pauses for a person. Allow runs it. Claude Code evaluates deny first, then ask, then allow, and the first match wins, so a convenience rule added later cannot undo a safety rule. Rules can apply to a whole tool or to its arguments, but argument patterns on shell commands are fragile: the same documentation shows that a rule against curl does not catch /usr/bin/curl, and recommends an operating-system sandbox as a second layer.

OWASP's entry on excessive agency names three root causes, and each has its own control:

Root causeWhat it looks likeControl
Excessive functionalityThe tool list has a shell, open-ended URL fetching, or write tools the task never usesRemove the tool, split reading from writing, prefer narrow tools to open-ended ones
Excessive permissionsThe tool's credential can do more than the tool is meant toScoped credentials in the user's own context, and authorisation in the downstream service
Excessive autonomyHigh-impact actions run with no checkAsk rules, human approval, rate limits

Meta's Agents Rule of Two turns this into a design check, and Meta frames it as holding until research can reliably detect and refuse prompt injection. Within one session an agent should have no more than two of these properties: (A) it processes untrustworthy inputs, (B) it accesses sensitive systems or private data, (C) it can change state or communicate externally. An agent that needs all three should not run autonomously and needs supervision, such as human-in-the-loop approval of its actions.

The confused deputy and excessive agency

The original example comes from Norm Hardy's essay (opens in a new tab) about a compiler on a commercial timesharing system. The compiler was licensed to write files in its home directory, where it kept a statistics file. A user could tell the compiler where to put its optional debugging output, named the system's billing file in that directory, and the compiler, using its own authority, overwrote it. The user had no right to that file. The compiler did, and could not tell whose authority it was exercising.

An agent is a deputy in exactly this sense. It holds authority, such as a token or an open connection, and it takes instructions from text it did not write. In the Invariant Labs case the agent had GitHub connected to the user's account. An issue in a public repository told it what to do, and it used the user's access to read private repositories and publish what it found in a public pull request. The model was not the missing control.

Three defences work together:

  1. Authorise downstream, on the user's rights. OWASP calls this complete mediation: the service decides for each request, instead of trusting that the model or the agent already did.
  2. Bind authority to the request. AWS documents the same bug in cross-account and cross-service access and prevents it with values the attacker cannot choose: an external ID that a vendor generates per customer, and condition keys such as aws:SourceArn that say on whose behalf a service is acting. The agent equivalents are audience binding, the act claim and per-client consent in MCP proxy servers.
  3. Shrink the deputy. Fewer functions, narrower permissions and the Rule of Two leave less for an injected instruction to use.

Audit trails

An audit trail answers who did what, through which agent, under whose authority, and who allowed it. Record at least these fields:

FieldWhy you need it
User and agent identityWhose authority was used and which agent used it
Tool and targetWhat was attempted, and on which resource
Argument summaryThe detail needed to understand the action, without secrets
Decision and deciding ruleAllowed, asked or denied, and by config, hook or person
ResultSuccess or the error type
Time and correlation idTies the call back to the prompt or run that caused it

Write records in the harness and in the downstream service. The MCP security guidance warns that when tokens are passed through, the downstream service's logs may show a different identity than the one that acted. Log denials as well as successes, because a burst of refused calls can be an early sign of an injection attempt. Treat the log as sensitive: Claude Code's telemetry keeps prompt text redacted unless you switch it on, and gates tool arguments behind a second setting.

Worked example: A calendar assistant with token exchange, per-tool policy and an audit log in 91 lines of Python

The scenario: a calendar and mail assistant, assistant-7, works for a user named priya. A script of six tool calls replaces the model so the output is identical on every run, and the first send_email call stands in for an injected instruction that tries to make the agent send mail. The token service, the services behind the tools and the clock are simulated in one file. This is a teaching model of an RFC 8693-style exchange, not production code: a shared HMAC key stands in for a token service's signing keys, and real systems should use an identity provider.

Save this as agent_auth.py. It needs Python 3.9 or later and nothing else.

python
import base64
import hashlib
import hmac
import json

SIGNING_KEY = b"demo-key-for-teaching-only"
AGENT_API = "https://agent.example"
MAIL, CALENDAR = "https://mail.example", "https://calendar.example"
EXCHANGE_TTL = 120  # seconds an exchanged token stays valid
AGENT_GRANTS = {"assistant-7": {"calendar.read", "mail.read"}}  # all the agent may ever ask for
TOOLS = {  # tool name -> (audience, scope, policy)
    "read_calendar": (CALENDAR, "calendar.read", "allow"),
    "read_inbox": (MAIL, "mail.read", "allow"),
    "send_email": (MAIL, "mail.send", "ask"),
}


class Denied(Exception):
    """A check refused the request; the message says which one."""


def b64(raw):
    return base64.urlsafe_b64encode(raw).rstrip(b"=").decode()


def sign(body):
    return b64(hmac.new(SIGNING_KEY, body.encode(), hashlib.sha256).digest())


def mint(claims):
    body = b64(json.dumps(claims, sort_keys=True).encode())
    return f"{body}.{sign(body)}"


def check(token, audience, scope, now):
    """What every service does with a bearer token: signature, expiry, audience, scope."""
    body, signature = token.split(".")
    if not hmac.compare_digest(signature, sign(body)):
        raise Denied("bad signature")
    claims = json.loads(base64.urlsafe_b64decode(body + "=" * (-len(body) % 4)))
    if claims["exp"] <= now:
        raise Denied("token expired")
    if claims["aud"] != audience:
        raise Denied(f"audience is {claims['aud']}, not {audience}")
    if scope not in claims["scope"].split():
        raise Denied(f"scope {scope} not granted")
    return claims


def exchange(user_token, agent, audience, scope, now):
    """Token service: swap the user's token for a narrow one that also names the agent."""
    user = check(user_token, AGENT_API, "agent.act", now)
    if scope not in user["scope"].split():
        raise Denied(f"user {user['sub']} does not hold {scope}")
    if scope not in AGENT_GRANTS.get(agent, set()):
        raise Denied(f"{agent} is not granted {scope}")
    return mint({"sub": user["sub"], "act": {"sub": agent}, "aud": audience,
                 "scope": scope, "iat": now, "exp": now + EXCHANGE_TTL})


def run_tool(name, user_token, agent, now, log, approved=False, token=None):
    """Harness: tool policy, then token exchange, then the service's own check, then the log."""
    audience, scope, policy = TOOLS[name]
    user = check(user_token, AGENT_API, "agent.act", now)["sub"]
    record = {"seq": len(log) + 1, "t": now, "user": user, "agent": agent, "tool": name, "scope": scope}
    try:
        if policy == "ask" and not approved:
            raise Denied("approval required")
        presented = token or exchange(user_token, agent, audience, scope, now)
        check(presented, audience, scope, now)  # stands in for the downstream service
        outcome = {"decision": "allow"}
    except Denied as reason:
        outcome = {"decision": "deny", "reason": str(reason)}
    return [*log, {**record, **outcome}]


if __name__ == "__main__":
    user_token = mint({"sub": "priya", "aud": AGENT_API, "iat": 0, "exp": 3600,
                       "scope": "agent.act calendar.read mail.read mail.send"})
    calendar_token = exchange(user_token, "assistant-7", CALENDAR, "calendar.read", 10)
    log = []
    log = run_tool("read_calendar", user_token, "assistant-7", 10, log)
    log = run_tool("read_inbox", user_token, "assistant-7", 20, log)
    log = run_tool("send_email", user_token, "assistant-7", 30, log)
    log = run_tool("send_email", user_token, "assistant-7", 40, log, approved=True)
    log = run_tool("read_inbox", user_token, "assistant-7", 50, log, token=calendar_token)
    log = run_tool("read_calendar", user_token, "assistant-7", 131, log, token=calendar_token)
    for r in log:
        print(f"{r['seq']} t={r['t']:<3} {r['tool']:<13} {r['decision']:<5} {r.get('reason', '')}".rstrip())
    print(json.dumps(log[0]))
    print(json.dumps(check(calendar_token, CALENDAR, "calendar.read", 10), sort_keys=True))

Run python3 agent_auth.py. The output is:

text
1 t=10  read_calendar allow
2 t=20  read_inbox    allow
3 t=30  send_email    deny  approval required
4 t=40  send_email    deny  assistant-7 is not granted mail.send
5 t=50  read_inbox    deny  audience is https://calendar.example, not https://mail.example
6 t=131 read_calendar deny  token expired
{"seq": 1, "t": 10, "user": "priya", "agent": "assistant-7", "tool": "read_calendar", "scope": "calendar.read", "decision": "allow"}
{"act": {"sub": "assistant-7"}, "aud": "https://calendar.example", "exp": 130, "iat": 10, "scope": "calendar.read", "sub": "priya"}

What to notice:

  • The effective permission is an overlap. priya holds mail.send, but AGENT_GRANTS for assistant-7 does not, so no exchange can produce a token with that scope. An action can use only rights that the user holds, the agent may request and the tool needs, all at once.
  • Calls 1 and 2 succeed. The exchanged token for call 1 is the last output line: sub is priya, act is assistant-7, the audience is the calendar service, the only scope is calendar.read, and exp is 130 because it was issued at t = 10 with a 120-second lifetime.
  • Call 3 shows the ask policy. send_email is marked ask, so without approval the harness denies it before any token is requested. An injected instruction to send mail stops here first.
  • Call 4 is approved and still denied. Approval is not authority: the token service refuses because the agent was never granted mail.send. Allowing it would take a deliberate, reviewable edit to AGENT_GRANTS.
  • Call 5 replays the calendar token at the mail service, which refuses it because the audience is the calendar service. This is the token passthrough case from the MCP guidance; every service checks the audience itself.
  • Call 6 replays that token at t = 131. A token is rejected when exp <= now, so it is refused from t = 130 onward (10 + 120 = 130). priya's own token (exp 3600) is still valid, so only the exchanged token failed.
  • The audit trail is the log list. Every call, allowed or denied, leaves a record with user, agent, tool, scope, decision and reason. The first record is printed as JSON. A real downstream service would also keep its own record.

Edge cases and limitations

Approval does not create authority
A person clicking Approve confirms that an action should happen. It does not give the agent rights its identity lacks. In the worked example the approved send_email call is still refused because the agent was never granted mail.send. In Stripe's flow an approval gives the agent an approval token and the agent then retries the operation. Design approval as an extra condition on top of authorisation, never as a replacement for it.
Argument patterns on shell commands are not a boundary
Claude Code's documentation shows that a deny rule for Bash(curl *) stops curl https://example.com but not /usr/bin/curl or sh -c 'curl ...', and says such rules are not a security boundary around the program. If a shell tool must exist, add an operating-system sandbox and keep secrets out of its environment so a missed pattern cannot reach anything valuable.
Background agents outlive the user's attention
Entra documents refresh tokens for asynchronous scenarios and background processes. An agent that holds one keeps working after the user has closed the laptop. Give such agents their own identity for unattended work where you can, cap token lifetimes, and make sure the user or an administrator can list and revoke grants, as Stripe's OAuth sessions page allows.
A client may ask for every scope by default
The MCP specification tells a client to fall back to all scopes in scopes_supported when the server gives no scope hint, and the security guidance lists publishing every scope as a common mistake. A server that advertises broad scopes therefore invites broad tokens. Publish a minimal basic scope and challenge for more when a privileged tool is first used.
Chains of agents can lose track of the user
When an orchestrator hands work to a sub-agent, each hop adds an actor, and RFC 8693 expresses this by nesting act claims. Without a rule such as "a sub-agent may not hold more than its parent" and a limit on chain depth, authority can widen with every hop, and the audit record can no longer say who started the chain. The RFC treats prior actors in nested act claims as informational only for access control decisions, so the limits must travel in the scope, audience and expiry of each token. The first exercise builds both rules.
Logs can leak what they are meant to protect
Prompts, tool arguments and tool output can contain personal data and secrets. Claude Code's telemetry keeps prompt text redacted unless OTEL_LOG_USER_PROMPTS is set and gates tool details behind another variable. Decide per field what to record, store logs with the same care as the data they describe, and keep secrets out of arguments in the first place.

When to use it, and when something simpler is enough

Use it when

  • The agent can reach systems that hold data or actions you would not give an anonymous caller: email, repositories, payments, customer records, production infrastructure.
  • One agent serves many users, or many agents share a service, so the rights that apply differ from request to request and one agent must be revocable without affecting the rest.
  • A security, audit or customer reviewer must be able to say which agent did something and for whom, even months later.
  • The agent runs unattended, reads untrusted content, or can take actions that are expensive or impossible to undo.

Think twice when

  • A throwaway prototype that reads only public data, has no write tools and holds no credential worth stealing. One read-only key and a short allow list are enough there.
  • You are tempted to enforce policy by instructing the model ("never send mail outside the company"). That is a hint to the model, not a control.
  • You are about to write your own token service for production. Use your identity provider's token exchange and agent identity features; the worked example is a teaching model.

A simpler alternative. For one agent used by one person on their own machine, a single-purpose read-only credential plus the harness's allow, ask and deny rules is often enough. Move to per-agent identities and token exchange once the agent is shared, runs unattended, or acts on the data of people other than the one who started it.

Key takeaways

  • An agent should act as a named identity that is separate from any person's login, and every action should be traceable to that agent and, when there is one, to the user it represents.
  • Delegation lets a service see both the user and the agent, and the rights in play are the overlap of what the user holds, what the agent may request and what the tool needs.
  • Credentials given to an agent should be narrow in scope, addressed to one service and short-lived, and a token issued for one service must never be forwarded to another.
  • Allow, ask and deny rules must be enforced by code outside the model, with deny winning over ask and ask over allow, and each downstream service must still authorise every request itself.
  • An agent that holds authority and reads untrusted text is a confused deputy waiting to happen, so remove excessive functionality, excessive permissions and excessive autonomy before relying on the model's judgement.
  • An audit record names the user, the agent, the tool, the decision and the rule that made it, and it is written for denied calls as well as allowed ones.

Example 1 of 5

Microsoft Entra Agent ID gives agents their own directory identity, with autonomous and on-behalf-of access

MicrosoftDocumented in official docs

Microsoft Entra Agent ID is the part of Microsoft Entra that creates and manages identities for AI agents. Two Microsoft Learn pages describe it: "What are agent identities?" and the agent OAuth on-behalf-of flow. [12][13]

The problem

Directory identity systems were built for people and for long-lived applications (service principals). The documentation says agents are often created dynamically, may exist for minutes, and may be created and destroyed thousands of times a day. An organisation still has to tell agent operations apart from human and application ones, give agents right-sized access, keep them away from its most critical roles, and manage them at scale.

Where this topic fits

Agent identity sits in the identity provider, before any tool call. The agent identity is the principal that requests tokens. From there it works in one of two ways the pages describe: autonomously, with rights assigned to it directly, or on behalf of a signed-in user, using an on-behalf-of exchange.

How it is applied, step by step

  1. An agent is created, for example by a user building one in Copilot Studio or by automation, and receives an agent identity in the tenant. For Copilot Studio agents the creating user is recorded as the sponsor.
  2. For autonomous work an administrator assigns access rights directly to the agent identity, such as Microsoft Graph permissions or Azure RBAC roles. What the agent does with them is attributed to the agent.
  3. For delegated work a user signs in to a client application and obtains a token whose audience is the agent identity blueprint, the parent from which agent identities are created.
  4. The blueprint first presents its own credential, preferably a managed identity token, and receives an exchange token (T1) tied to the child agent identity. The agent identity then sends T1 together with the user's token in an on-behalf-of request and receives a token for the target API. Entra rejects a user token whose audience is not the blueprint.
  5. Agent identities cannot start interactive sign-in, so an administrator pre-authorises delegated permissions on the blueprint and child agent identities inherit them without a consent prompt.
  6. Sign-ins by agents are logged in Entra ID as AI agent activity and can be viewed in the Entra admin center.

Why this approach fits

A directory identity lets the controls an organisation already runs for people and applications, such as role assignments, policies, lifecycle and sign-in logs, apply to agents too, and it keeps a misbehaving agent revocable without touching anyone's personal account. Because delegated rights come from the user, the model the pages describe bounds an agent acting for a user by the rights that user holds and chooses to delegate.

Limitation or tradeoff

The overview page says Agent ID is available to all Entra customers but that extending Entra security features to agents requires Microsoft Agent 365, so the governance benefits depend on licence and tenant configuration. Agent ID issues Entra tokens, so it helps most for resources that accept them; an API with its own authentication still needs its own credential. Inheritance is applied per blueprint, so a generous pre-authorised grant on a blueprint reaches every child agent identity under it, and grants deserve review at the blueprint level.

What the sources document

  • Agent identities are accounts in Microsoft Entra ID for AI agents, intended to distinguish agent operations from those of workforce, customer or workload identities. They differ from service principals, which assume long-term stability, because agents can exist for minutes and be created and destroyed thousands of times a day. [12]
  • An agent can act autonomously with access rights given directly to its agent identity, or act on behalf of a human user with rights given to the user, who controls which rights are delegated. An agent identity can be paired one-to-one with a special agent user account where a system needs the agent to appear as a user. [12]
  • A Copilot Studio agent gets an agent identity when it is created, its creator is recorded as sponsor, and its authentications are logged in Entra ID as AI agents. Queries by the Conditional Access optimization agent are likewise recorded as performed by an AI agent. [12]
  • In the on-behalf-of flow an agent identity blueprint cannot start an interactive authorize flow and must receive a user token from a client application whose audience is the blueprint. Child agent identities cannot be consented interactively; delegated permissions are pre-authorised through inheritable permissions on the blueprint. [13]
  • The overview page says extending Entra security features to agents requires Microsoft Agent 365, and the flow page says client secrets should not be used as credentials for agent identity blueprints in production, recommending federated credentials with managed identities or certificates. [12][13]

MCP authorization binds tokens to one server and closes a confused deputy path in proxy servers

Model Context Protocol projectDocumented in a specification

The Model Context Protocol authorization specification defines how a client obtains and uses an OAuth token for a protected MCP server. The project's security best-practices page describes attacks and mitigations, including a confused deputy attack on MCP proxy servers. [8][9]

The problem

An MCP server is the gateway between an agent and real APIs. If it accepts any token it is handed, or forwards a client's token to a downstream API, a token issued for one purpose can be replayed for another and the server stops being a checkpoint. A second problem hits proxy servers that front a third-party API: with one static OAuth client ID, dynamic client registration and a consent cookie, an attacker's client can obtain an authorization code without the user's consent.

Where this topic fits

The control sits between the agent's client and the MCP server (an OAuth resource server) and again between that server and any third-party API. It applies to every request: the token's audience and scope are checked before a tool runs.

How it is applied, step by step

  1. The client discovers the server's authorization server and requests a token with the OAuth resource parameter naming the MCP server's canonical URI, in both the authorization request and the token request.
  2. The authorization server issues a token whose audience is that MCP server, carrying the scopes the user approved.
  3. On every request the client sends the token in the Authorization header. The MCP server validates that the token was issued for it and rejects tokens issued for any other resource.
  4. If a tool needs a permission the token lacks, the server answers 403 with error insufficient_scope and the scope required. The client may run a step-up authorization and retry a limited number of times.
  5. When the server must call a third-party API it uses a token issued for that API. It does not forward the client's token, because token passthrough is forbidden.
  6. A proxy server in front of a third-party authorization server keeps a per-user registry of approved client IDs and shows its own consent page before forwarding the user, which closes the confused deputy path.

Why this approach fits

Binding a token to one audience means a stolen or replayed token is useful at one service only, and the server remains the single place where rate limits, validation and logging apply. Challenging for a scope at the moment a tool needs it lets the first token be small, which limits what an injected instruction can do with it.

Limitation or tradeoff

Authorization is optional in MCP, and a server using the STDIO transport is told to take credentials from its environment instead. When a server gives no scope hint the specification tells clients to request every scope in scopes_supported, so broad servers invite broad tokens. Audience checks stop token reuse but not an agent misusing permissions it legitimately holds, which is why tool-level permissions are still needed.

What the sources document

  • MCP clients must send the OAuth resource parameter naming the MCP server's canonical URI in both authorization and token requests. MCP servers must validate that access tokens were issued specifically for them as the audience, and must not accept or transit any other tokens. [8]
  • The best-practices page calls token passthrough an anti-pattern that the authorization specification explicitly forbids. Its listed risks include circumventing controls such as rate limiting and harming accountability, because downstream logs may show requests as coming from a different source or identity. [9]
  • It describes a confused deputy attack on MCP proxy servers that use a static client ID with a third-party authorization server, allow dynamic client registration and rely on a consent cookie. The required mitigation is per-client consent, with a registry of approved client IDs checked before the third-party flow. [9]
  • The guidance recommends a minimal initial scope set with step-up challenges when privileged operations are first attempted, and lists wildcard or omnibus scopes such as * or all among common mistakes. The specification shows a 403 response with error insufficient_scope and the scope required. [8][9]
  • Authorization is optional for MCP implementations. Implementations using an HTTP-based transport should follow the specification, and those using STDIO should instead retrieve credentials from the environment. [8]

Example 3 of 5

Stripe separates user-delegated OAuth from agent API keys and adds approval rules to money-moving actions

StripeDocumented in official docs

Stripe's MCP server documentation and its API keys page describe two ways an AI agent can authenticate to a payments account, and how Stripe keeps a person in the loop for high-impact actions. [14][15]

The problem

A payments API can refund customers, pay out funds and change account settings. An agent connected to it can make mistakes, invent an action or be steered by injected text, and some of its actions cannot be undone. Stripe has to support interactive agents that act for a signed-in user and unattended agents that need their own persistent access, without handing either one unlimited power.

Where this topic fits

The credential type chooses the principal: the signed-in user through OAuth, or the agent itself through a tagged restricted key. The key's permissions bound which API calls the agent can make, and approval rules or confirmation links put a person in front of the highest-impact writes.

How it is applied, step by step

  1. For an interactive client the user connects through OAuth, sees Stripe's consent page and chooses which live-mode accounts or sandboxes the client may use, with different permissions for each.
  2. For an unattended agent someone with Dashboard access creates a restricted API key with only the permissions the agent needs and tags it as an agent key. The Dashboard marks such keys with an Agent badge.
  3. Agent-tagged keys are automatically subject to approval rules. Stripe provides default rules for high-risk actions such as payouts, refunds and account configuration changes, and a designated reviewer must approve a sensitive action before it takes effect.
  4. When an agent is connected with a user's credentials, certain write calls such as refunds and outbound payments need human confirmation through a link the agent passes to the person. The person opens it, reviews the request and approves, Stripe gives the agent an approval token, and the person must tell the agent to retry. An unapproved request expires after 24 hours.
  5. Users and administrators can list OAuth sessions and revoke a client, and request logs show what a key did.

Why this approach fits

Two credential types make the question of who is acting explicit. OAuth ties actions to a person who can see and revoke the grant. An agent key gives the agent a separate, labelled identity with its own permission set, which suits work no user is present for. Approval rules then add per-action control where an error costs the most, and Stripe applies them on its side rather than relying on the agent.

Limitation or tradeoff

The confirmation applies to certain stripe_api_write actions, such as refunds and outbound payments, and the page does not list them all. Other writes rely on the permissions granted and on the client's own tool approval, which Stripe's page tells users to turn on. An agent key is still a long-lived secret that must live in a vault or environment variable. Stripe also announces that from 31 October 2026 its MCP server stops accepting full-access secret keys and restricted keys without the Agent tag, so these rules are changing quickly and the current page should be checked.

What the sources document

  • Stripe's MCP server supports OAuth, for a client acting on behalf of a Stripe user account, and agent API keys, for an AI application that needs independent, persistent access. For autonomous clients that cannot use OAuth the page says to create an agent API key with only the permissions the client needs. [14]
  • A restricted API key can be tagged as belonging to an autonomous agent. Agent-tagged keys authenticate and carry permissions like other restricted keys but are automatically subject to approval rules, with default rules for high-risk actions such as payouts, refunds and account configuration changes. [15]
  • Stripe requires human confirmation before certain stripe_api_write actions such as refunds and outbound payments. The person approves through a link, Stripe gives the agent an approval token, the agent must retry the operation, and an unapproved request expires after 24 hours. [14]
  • Users can revoke authorised MCP clients under OAuth sessions, and administrators with the right permissions can view or revoke other users' sessions and enable or disable MCP access for the team. The page advises turning on the client's tool-approval setting and warns about prompt injection when Stripe MCP is combined with other servers. [14]
  • Beginning 31 October 2026 Stripe MCP no longer accepts full-access secret keys or restricted API keys without the Agent tag. The keys page says secret keys have unrestricted permissions and recommends restricted keys instead for new use cases. [14][15]

Example 4 of 5

Claude Code enforces deny, ask and allow rules per tool and records each decision as a telemetry event

AnthropicDocumented in official docs

Claude Code is Anthropic's coding agent. Its permissions page documents per-tool rules, settings precedence and managed settings, and its monitoring page documents the OpenTelemetry events it can emit for tool decisions and results. [10][11]

The problem

A coding agent reads files, edits code, runs shell commands and fetches web pages with a developer's file access and network. Each tool carries different risk. The developer, a team and a security group all need to set rules at their own level, and afterwards need to find out what was allowed and who or what allowed it.

Where this topic fits

The rules are checked by the harness immediately before each tool runs, outside the model. The telemetry then records the decision and, if the tool ran, the result.

How it is applied, step by step

  1. A rule has the form Tool or Tool(specifier), for example Read(./.env), Edit(/docs/**) or Bash(git push *), and an MCP server can be named with a rule such as mcp__puppeteer.
  2. Rules sit in three lists, deny, ask and allow. For each tool call the harness checks deny first, then ask, then allow. The first match decides, and a narrower allow cannot override a broader deny.
  3. Settings are layered, and managed settings set by an administrator take precedence over all other levels, including command-line arguments. A deny at any level cannot be undone by an allow at another.
  4. Because the harness enforces the rules, wording in a prompt or in a project instruction file cannot loosen them. For shell commands the documentation advises an operating-system sandbox as a second layer, since a rule matches command text.
  5. With telemetry switched on, each decision becomes an event with accept or reject and a source such as config, hook or a user choice, followed by a result event, all linked by a prompt id.

Why this approach fits

Deny-first evaluation means a broad safety rule, such as never reading the .env file, cannot be undone by a convenience rule added later, and managed settings let an organisation fix the rules that matter without trusting every developer's local file. Putting the check in the harness means an injected instruction can change what the model asks for but not what the harness permits. The decision events give reviewers the record that the rules alone do not.

Limitation or tradeoff

Rules that constrain command arguments are fragile: the documentation shows that Bash(curl *) does not stop /usr/bin/curl or sh -c 'curl ...' and says such rules are not a security boundary around the program. Tool rules also say nothing about what credentials sit in the environment, so they complement least-privilege credentials rather than replace them. Telemetry is opt-in and prompt text is redacted by default, so the audit trail has to be switched on before the incident, not after it.

What the sources document

  • Rules are evaluated deny first, then ask, then allow, and the first match decides. Specificity does not change the order, so an allow rule cannot carve an exception out of a deny rule. [10]
  • The page states that permission rules are enforced by Claude Code, not by the model: instructions in a prompt or CLAUDE.md shape what Claude tries to do but do not change what Claude Code allows. A bare tool-name deny rule removes the tool from Claude's context entirely. [10]
  • Managed settings have the highest precedence, no other level including command-line arguments can override a managed permission rule, and a tool denied at any level cannot be allowed by another level. [10]
  • Bash deny and ask rules match command text and are not a security boundary: Bash(curl *) stops curl https://example.com but not /usr/bin/curl or sh -c invocations. The page recommends sandboxing for filesystem and network enforcement that does not depend on command text. [10]
  • Telemetry is opt-in through CLAUDE_CODE_ENABLE_TELEMETRY. The claude_code.tool_decision event records accept or reject with a source such as config, hook or a user choice, and claude_code.tool_result records success and duration. Events share a prompt.id, prompt text is redacted unless OTEL_LOG_USER_PROMPTS=1, and tool details need OTEL_LOG_TOOL_DETAILS=1. [11]

GitHub Copilot cloud agent works under separation of duties with attributed commits and session logs

GitHubDocumented in official docs

GitHub's page "Risks and mitigations for GitHub Copilot cloud agent" lists the risks of an agent that can change a repository and the controls GitHub applies around it: who may trigger it, where it can write, who can approve its work and what administrators can see afterwards. [16]

The problem

A coding agent that pushes to a shared repository could write to important branches, approve or merge its own work, trigger workflows that run with repository access, or leave changes nobody can attribute. The owners need it to be useful while a human stays accountable for whatever is merged.

Where this topic fits

The constraints are applied by the platform around the agent, not inside its prompt. They act at trigger time (who can start it), write time (which branch), review time (who can approve), CI time (workflow approval) and afterwards (attribution and logs).

How it is applied, step by step

  1. Only a user with write access to the repository can trigger the agent, so someone without write access cannot start it.
  2. The agent can push to a single branch: the pull request's own branch when triggered on an existing pull request, otherwise a new copilot/ branch. It performs only simple push operations and cannot run git commands itself.
  3. It cannot mark its pull requests ready for review, approve or merge. The person who asked for the pull request cannot approve it either, so a second person must review.
  4. By default, workflows do not run on the agent's code until a user with write access reviews it and selects Approve and run workflows.
  5. Commits are authored by Copilot with the requesting developer as co-author and are signed so they show Verified. Session logs and audit log events are available to administrators.
  6. The agent's internet access is restricted, and hidden characters are filtered out of user input before it reaches the agent.

Why this approach fits

Separation of duties makes the agent a contributor rather than an owner. Whatever it writes passes through the same review as a human's change, so a mistaken or manipulated agent cannot ship code on its own authority. Attribution and logs let an administrator answer who asked, which agent wrote the change and what it did.

Limitation or tradeoff

The controls limit what the agent may do, not how good its code is: the page itself lists unvalidated code introducing vulnerabilities, and the agent having access to sensitive information, among its risks. The review step is only as strong as the reviewer's attention, and controls the page describes as defaults, such as workflow approval, weaken if a repository relaxes them.

What the sources document

  • Only users with write access to the repository can trigger the agent. It can push to a single branch, the pull request's own branch or a new copilot/ branch, and can only perform simple push operations: it cannot directly run git push or other Git commands. [16]
  • The agent cannot mark its pull requests Ready for review and cannot approve or merge a pull request. The user who asked it to create a pull request is prevented from approving it. [16]
  • By default, workflows are not triggered until the agent's code has been reviewed and a user with write access clicks Approve and run workflows. [16]
  • Commits are authored by Copilot with the developer who assigned the issue or requested the change marked as co-author, and they are signed so they appear as Verified. Session logs and audit log events are available to administrators. [16]
  • GitHub restricts the agent's access to the internet and filters hidden characters from user input before passing it to the agent. [16]

4Common mistakes

  1. Giving the agent the user's own long-lived credential, or one shared service account for every agent.

    Why it causes problems
    Every action looks like the user's or like the shared account's, so nobody can tell human from agent or one agent from another. Stealing the credential from the agent yields everything the user or account can do, and switching off one agent means rotating a credential that others depend on.
    How to recognise it
    The same account name appears in the logs for people and for several agents, one key is copied into many configuration files, or revoking a single agent would break unrelated systems.
    How to fix it
    Register each agent as its own identity with a named owner. For work on a user's behalf, exchange the user's token for a narrow, short-lived one that names both parties, and keep long-term secrets in a vault or managed identity instead of agent code.

  2. Putting the policy in the system prompt instead of in the harness and the downstream service.

    Why it causes problems
    Instructions are inputs to the model, and so is everything else it reads. Injected text can contradict them, and nothing stops the call when it does. The Invariant Labs write-up tested Claude 4 Opus, a state-of-the-art aligned model, and still saw private data leak.
    How to recognise it
    Rules that exist only as sentences such as "never send mail outside the company", and no deny, ask or allow list that the program checks before a tool runs.
    How to fix it
    Enforce rules in code with deny winning over ask and ask over allow, and let each downstream service decide again from the requesting user's rights. Keep the prompt for guidance, not control.

  3. Forwarding a token to another service, or accepting tokens that were not issued for your service.

    Why it causes problems
    A token meant for one service becomes usable at others, the receiving service's own limits and checks can be skipped, and logs may show an identity other than the one that acted. The MCP guidance forbids this explicitly.
    How to recognise it
    The same token string appears in requests to more than one service, a service never reads the audience claim, or a stolen token from one product works at another.
    How to fix it
    Validate the audience and scope of every token at the receiving service. When a service must call another, have it obtain a token issued for that second service through a token exchange.

  4. Requesting every scope up front to avoid consent prompts later.

    Why it causes problems
    A stolen or misused token reaches everything the broad grant covers, revoking it disrupts every workflow that shares it, and users learn to click through long consent screens.
    How to recognise it
    Tokens carrying wildcard or omnibus scopes such as all or full access, a server that advertises its whole scope list, or consent screens that list far more than the task needs.
    How to fix it
    Start with a minimal scope set and step up when a privileged tool is first used, as the MCP guidance recommends. Review the scopes in tokens against the tools actually called.

  5. Auditing only successful calls, or logging raw prompts and secrets in full.

    Why it causes problems
    Without denials you miss the first sign of an injection attempt, and without the deciding rule you cannot say why a call ran. Full prompts and tool output turn the log into a second copy of the sensitive data.
    How to recognise it
    Logs with no record of refused calls, no field naming the rule or person that approved a call, or customer data and keys visible in log search.
    How to fix it
    Record the user, agent, tool, argument summary, decision, deciding rule, result and a correlation id for every call, allowed or denied. Redact prompts and tool output by default and switch on detail only where you need it.

Exercise 1

Let a sub-agent act under a parent agent without widening anyone's rights

CodingIntermediateAbout 45 min (estimate)Hypothetical scenario

A multi-agent assistant lets assistant-7 hand mail-reading work to a sub-agent, summarizer-2. Extend agent_auth.py from the worked example (Python 3.9 or later, standard library only) so that the sub-agent receives its own token while the audit trail still names the whole chain.

Add a function delegate(parent_token, sub_agent, audience, scope, now) that returns a new token. Use these tables, which are part of the exercise:

python
SUB_GRANTS = {"summarizer-2": {"mail.read"}, "ocr-1": {"mail.read"}}
MAX_CHAIN = 2  # most actors a token may name, counting the first agent

Test it with priya's user token from the worked example. Mint the parent token with exchange(user_token, "assistant-7", MAIL, "mail.read", 20), which expires at t = 140.

Requirements

  • The new token keeps the same `sub`, `aud` and `scope` as the parent token and adds the sub-agent as the outermost `act`, with the parent's `act` nested inside it, as RFC 8693 describes.
  • The sub-agent must appear in `SUB_GRANTS` for the requested scope, otherwise raise `Denied`.
  • A token may name at most `MAX_CHAIN` actors. A request that would make the chain longer must raise `Denied`.
  • The new token must never expire later than its parent, and its own lifetime is at most `EXCHANGE_TTL` seconds.
  • A parent token that is expired, has a different audience or lacks the scope must be refused before any grant is consulted.
  • Print the chain as `priya -> assistant-7 -> summarizer-2` using a helper that follows the nested claims.

Expected behaviour

Delegating mail.read to summarizer-2 at t = 60 succeeds and the chain prints as priya -> assistant-7 -> summarizer-2 | exp 140. Four attempts are refused with these reasons: asking for mail.send (the parent lacks it), a third hop to ocr-1 (chain deeper than 2), delegating at t = 141 (token expired), and delegating to an agent that is not in SUB_GRANTS.

Hint 1

Call the existing `check(parent_token, audience, scope, now)` first. It already refuses expired tokens, wrong audiences and missing scopes.

Hint 2

Write a small function that follows `act`, then `act["act"]`, and so on, and returns the names. Its length is the number of actors.

Hint 3

Build the new claims with `{**parent, ...}` so you do not modify the parent's dictionary, and use `min` for the expiry.

Show solution

Save this as delegation.py next to agent_auth.py. It imports the token functions from the worked example and adds the sub-agent hop.

python
from agent_auth import AGENT_API, EXCHANGE_TTL, MAIL, Denied, check, exchange, mint

SUB_GRANTS = {"summarizer-2": {"mail.read"}, "ocr-1": {"mail.read"}}
MAX_CHAIN = 2  # most actors a token may name, counting the first agent


def actors(claims):
    """Actor names from the outermost (current) to the innermost (first) act claim."""
    names, node = [], claims.get("act")
    while node:
        names = [*names, node["sub"]]
        node = node.get("act")
    return names


def chain_text(claims):
    return " -> ".join([claims["sub"], *reversed(actors(claims))])


def delegate(parent_token, sub_agent, audience, scope, now):
    """Exchange a parent agent's token for a narrower one held by a sub-agent."""
    parent = check(parent_token, audience, scope, now)  # same audience, scope not widened
    if scope not in SUB_GRANTS.get(sub_agent, set()):
        raise Denied(f"{sub_agent} is not granted {scope}")
    if len(actors(parent)) + 1 > MAX_CHAIN:
        raise Denied(f"delegation chain deeper than {MAX_CHAIN}")
    return mint({**parent, "act": {"sub": sub_agent, "act": parent["act"]},
                 "iat": now, "exp": min(parent["exp"], now + EXCHANGE_TTL)})


if __name__ == "__main__":
    user_token = mint({"sub": "priya", "aud": AGENT_API, "iat": 0, "exp": 3600,
                       "scope": "agent.act calendar.read mail.read mail.send"})
    parent = exchange(user_token, "assistant-7", MAIL, "mail.read", 20)
    child = delegate(parent, "summarizer-2", MAIL, "mail.read", 60)
    claims = check(child, MAIL, "mail.read", 60)
    print(chain_text(claims), "| exp", claims["exp"])
    attempts = [
        ("widen scope", (parent, "summarizer-2", MAIL, "mail.send", 60)),
        ("third hop", (child, "ocr-1", MAIL, "mail.read", 70)),
        ("expired parent", (parent, "summarizer-2", MAIL, "mail.read", 141)),
        ("unknown agent", (parent, "unknown-9", MAIL, "mail.read", 60)),
    ]
    for label, args in attempts:
        try:
            delegate(*args)
        except Denied as reason:
            print(f"{label}: {reason}")

Run python3 delegation.py. The output is:

text
priya -> assistant-7 -> summarizer-2 | exp 140
widen scope: scope mail.send not granted
third hop: delegation chain deeper than 2
expired parent: token expired
unknown agent: unknown-9 is not granted mail.read

How it works:

  • actors walks the nested act claims, so chain_text can print the whole chain from the user to the current actor: priya, then assistant-7, then summarizer-2.
  • check(parent_token, audience, scope, now) is called first, so a delegated token can never widen the scope, change the audience or outlive its parent's validity. The mail.send attempt fails there because the parent token only carries mail.read.
  • The grant table and the depth limit are separate rules. ocr-1 is allowed the scope, but a third actor would make the chain longer than MAX_CHAIN.
  • min(parent["exp"], now + EXCHANGE_TTL) makes the child expire at t = 140, the parent's expiry, instead of t = 180. Delegation can only shorten authority.
  • The parent token expires at t = 140, so the expired-parent attempt at t = 141 fails in check before any grant is consulted.

  • Does the delegated token keep priya as `sub` and name both agents in nested `act` claims?
  • Is the delegated token's expiry never later than its parent's, even when the current time plus 120 is later?
  • Does the third hop fail because of the chain limit even though the sub-agent holds the scope?
  • Did you check the parent token with `check` before looking at `SUB_GRANTS`, so an expired parent is reported as expired?

Review an over-privileged support agent and redesign its access

AnalysisIntermediateAbout 35 min (estimate)Hypothetical scenario

A company has deployed a customer support agent. Here is its current specification:

text

Reads:      customer emails and chat messages
Tools:      stripe_api_write (any endpoint), run_shell, fetch_url (any URL), read_file (any path)

Review this design as a security reviewer would and write a short redesign.

Requirements

  • For each line of the specification, name the problem and match it to excessive functionality, excessive permissions, excessive autonomy or an audit gap.

Rule of Two. Customer emails are untrusted input (A). The agent reads customer and payment data (B). It can change state through refunds and communicate externally through fetch_url and the shell (C). It has all three, so it should not run autonomously. The redesign below removes the open-ended channels but still has all three properties, so its automatic tier is a deliberate, bounded risk that the agent's owner has to accept. A stricter option is to remove property C by letting the agent only propose refunds for a person to execute.

Redesign (the numbers are assumptions for this exercise)

  • Identity: register refund-helper as its own agent identity with a named human owner, separate from the billing service and from the other 13 agents.
  • Credential: a restricted key issued to this agent alone, able to read customers and charges and to create refunds, nothing else, kept in a secrets vault and never readable by a tool.
  • Tools: get_customer, get_charge, search_help_articles (read only) and create_refund(charge_id, amount), which rejects an amount above the charge. Remove run_shell, fetch_url and read_file.
  • Approval: refunds of 50 USD or less on charges under 30 days old run automatically, with a limit of 20 per hour. Anything larger or older needs a person's approval. This leaves the agent with a bounded external action instead of an open one.
  • Audit record: time, ticket id, run id, agent id, tool, charge id, amount, decision (auto, approved by whom, or denied), the rule that decided, and the result. Redact customer text and card details, and log prompts only when debugging is switched on.
