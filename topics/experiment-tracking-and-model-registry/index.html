Experiment Tracking and Model Registries

Experiment tracking records the parameters, metrics, code version, data version and output files of every training run, so that runs can be compared and reproduced. A model registry stores the chosen models as numbered versions, with labels that say which version is in use and a link back to the run that produced it.

1Overview

Why it matters

Training a model is cheap to repeat and easy to lose track of. After a week of tuning you have forty result files and a notebook cell that once printed 0.91. Without a record you cannot say which settings produced the model that is in production, whether last month's score was measured on the same data, or how to rebuild the model when a bug report arrives.

The gap shows up at specific moments. A customer or auditor asks what data a model was trained on. A new model behaves worse in production and the previous one has to be back within minutes. Two teammates report different numbers for the same experiment. A file called model_final_v3.pkl is deployed and nobody knows which run wrote it. Data scientists and ML engineers need these records to choose a model on evidence, release managers need them to approve and roll back, and platform teams treat them as the precondition for automated retraining.

Before you start

  • Hyperparameter Tuning and Model SelectionIntermediate

What you will be able to do

  • Log parameters, metrics, tags and artifacts for every training run with MLflow, and say which store each one lands in.
  • Compare runs with a search query and choose a model on a validation metric instead of on memory.
  • Explain how DVC versions a large data or model file with a content hash kept in Git, and restore an earlier version.
  • Register a model, read its version history, and promote or roll back by moving an alias.
  • Trace a deployed model back to its run, parameters, code commit and data hash.

Key terms

Run
One execution of training code, recorded with its parameters, metrics, tags, start and end time and output files.
Experiment
A named group of runs that attack the same problem, so that their parameters and metrics can be laid side by side.
Parameter
An input chosen before training, such as a learning rate or a number of neighbours. MLflow stores parameter values as strings.
Metric
A number measured during or after training, such as validation error. It can be logged once, or at every step to form a curve.
Artifact
A file that a run produces, such as the trained model, a plot or a predictions file. Artifacts are stored apart from the metadata because they can be large.
Content hash
A fingerprint computed from a file's bytes (DVC uses MD5). Any change to the file changes the hash, so one hash names one exact version.
Model version
One numbered entry under a registered model name, whose model files do not change afterwards. The first registration is version 1 and each later one adds one.
Alias
A movable name such as champion that points at one model version, so that serving code can ask for the alias and never mention a version number.
Stage
A fixed lifecycle label for a model version, such as Staging or Production. MLflow deprecated stages in version 2.9.0 in favour of aliases and tags.
Lineage
The recorded chain from a deployed model back to its run, its parameters, the code version and the data version.

2Explanation

Introduction

In the hyperparameter tuning lesson you trained one model many times with different settings and kept the one with the best validation score. A grid search does that inside a single function call and hands back the winner. Real projects are messier. The runs are spread over weeks, several people and several versions of the data, and the question is no longer "which setting won?" but "which setting, on which data, with which code, produced the file that is serving customers right now?"

A chemist answers that kind of question with a lab notebook: what went into the flask is written down before the result is known, every time, including the attempts that failed. Experiment tracking is a lab notebook that the training script fills in by itself. Each execution of the script is a run. For every run the tracker stores the parameters (the settings you chose), the metrics (the numbers that came out), free-form tags, and the artifacts (files such as the trained model). Runs that attack the same problem are grouped into an experiment, so that they can be laid side by side:

Runk (neighbours)Training errorValidation error
knn-k110.0001.657
knn-k220.8460.206
knn-k884.0263.815

These three rows come from the worked example below, and nobody had to remember them.

Two more kinds of record complete the picture. Training data and model files are often too large for Git, so a data versioning tool such as DVC keeps a short fingerprint of each file in Git and stores the bytes elsewhere. And once a model has been chosen, a model registry gives it a name and a version number, and holds a movable label, such as champion, that tells the serving system which version to load.

This lesson uses MLflow for tracking and for the registry, and DVC for data versioning, because both are open source and run on a laptop. It covers what a run records and where the records are stored, how to compare runs, how a content hash versions a file, and how versions, stages and aliases work in a registry. The chain that links a deployed model back to its run, code and data is called lineage. It is what ML pipelines and model deployment build on.

How it works

A run is the unit of record

MLflow Tracking (opens in a new tab) is organised around runs. Its documentation describes a run as one execution of a piece of data science code, for example a single python train.py, and an experiment as a group of runs for one task. Inside a run you log four kinds of record:

RecordExampleWhat to know
Parameterlearning_rate = 0.01An input you chose. The value is stored as a string (opens in a new tab).
Metricval_loss = 0.42 at step 2A number. Log it once, or once per step to get a curve.
Tagdata_md5 = 25654e92…A label for filtering: data version, owner, ticket number.
Artifactmodel/, notes.txtA file or folder, often large.
python
from pathlib import Path

import mlflow

mlflow.set_experiment("churn-model")
with mlflow.start_run(run_name="lr-0.01"):
    mlflow.log_params({"learning_rate": 0.01, "epochs": 3})
    for epoch, loss in enumerate([0.61, 0.48, 0.42]):
        mlflow.log_metric("val_loss", loss, step=epoch)
    mlflow.set_tag("data_md5", "25654e92dfec5244cad1402aacfc3e5d")
    Path("notes.txt").write_text("baseline features only")
    mlflow.log_artifact("notes.txt")

MLflow adds what you would forget: the start and end time, the source file and, when the script runs inside a Git repository, the commit hash as the tag mlflow.source.git.commit (see the tracking API guide (opens in a new tab)). Calling mlflow.autolog() before training goes further: for supported libraries such as scikit-learn, XGBoost and PyTorch it logs parameters, metrics and the model with no explicit statements. Autologging cannot know your data version or your business metric, so log those yourself.

Where the records go

A tracking setup has two stores. The backend store holds the small structured records: run IDs, times, parameters, metrics and tags. The artifact store holds the files, on local disk or in object storage such as Amazon S3.

Where they live by default depends on the MLflow version. The backend store page (opens in a new tab) of the MLflow 3.17 documentation says the default is a SQLite database, sqlite:///mlflow.db, in the current directory. It also says that the file-based store in ./mlruns was the default in earlier versions and is now in maintenance mode. Do not rely on the default. Call mlflow.set_tracking_uri("sqlite:///mlflow.db") when you work alone, or pass the URL of a shared tracking server when you work in a team. The model registry requires a database-backed store. To browse the runs, start the web UI with mlflow server --backend-store-uri sqlite:///mlflow.db --port 5000 and open port 5000 on your machine.

Comparing runs

The UI lists the runs of an experiment in a table, lets you search them by parameter or metric value, and charts the metrics of the runs you select. The same comparison is available in code. mlflow.search_runs returns a pandas DataFrame with one row per run and columns named params.*, metrics.* and tags.*:

python
top = mlflow.search_runs(
    experiment_names=["churn-model"],
    filter_string='metrics.val_loss < 0.5 AND params.epochs = "3"',
    order_by=["metrics.val_loss ASC"],
    max_results=5,
)

The search syntax (opens in a new tab) has three rules worth memorising. Metrics are compared as numbers. Parameters and tags are strings, so their values need quotes even when they look numeric. Conditions are joined with AND, and OR is not supported.

A comparison is fair only when the runs were scored on the same validation data. That is why the data version belongs in every run, and why the next tool exists.

Versioning data and models with DVC

Git works well for code and badly for a 2 GB table. DVC (Data Version Control) keeps Git as the history and stores the bytes elsewhere. According to its get started guide (opens in a new tab), dvc add data/data.xml does three things:

  1. It hashes the file's content with MD5 and moves the file into a cache, at a path built from the hash (.dvc/cache/files/md5/22/a1a2931c…), then links it back into your working folder.
  2. It writes a small pointer file, data/data.xml.dvc.
  3. It adds the data file itself to .gitignore.
yaml
outs:
  - md5: 22a1a2931c8370d3aeedd7183606fd7f
    path: data.xml

You commit the pointer file to Git. dvc push copies the cached content to remote storage such as an S3 bucket, and dvc pull brings it back on another machine. To return to an old version, check out the old pointer file with Git and run dvc checkout, which puts the bytes with that hash back in place. The guide is candid that DVC is technically not a version control system by itself: it manipulates pointer files, and Git versions them. Because the hash is computed from the content, an unchanged file is stored once however many commits refer to it.

The same mechanism versions a model file. For multi-step work, a dvc.yaml (opens in a new tab) file declares stages, each with a command, its dependencies and its outputs, and DVC records the hash of every dependency and output, together with the parameter values, in dvc.lock. That file is lineage for files: it states which data and which parameter values produced which model file. DVC also has its own experiment table (opens in a new tab), dvc exp show, fed by a logger called DVCLive.

The tools are complementary. Put the DVC hash into the run as a tag, or let mlflow.log_input (opens in a new tab) record a dataset's name, digest and source, and the tracker and the data store refer to the same bytes.

The model registry: versions, aliases and stages

Most runs are discarded. The few that matter are registered:

python
version = mlflow.register_model("runs:/<run_id>/model", "churn")

The registry (opens in a new tab) creates version 1 the first time a name is used and increments the number on every later registration. A version's number and model files stay fixed, and the version keeps a link to the run that produced it. What changes over time is which version counts as current, and registries have used two designs for that.

  • Stages. Each version sits in one of four fixed stages: None, Staging, Production or Archived. Serving code loads models:/churn/Production. MLflow deprecated stages in version 2.9.0 (opens in a new tab). The reasons it gives: the fixed stages were inflexible, they doubled as a marker for the environment a model runs in, and access controls could not be attached to them.
  • Aliases and tags. An alias is a mutable named reference to one version. client.set_registered_model_alias("churn", "champion", 3) points champion at version 3, and serving code loads models:/churn@champion. Promotion moves the alias forward and rollback moves it back; no file is copied. A version can carry several aliases, for example champion and challenger during an A/B test. Status goes into a version tag, such as validation_status changing from pending to passed. Environments become separate registered models, such as dev.churn and prod.churn, with copy_model_version to promote from one to the other.

Other registries use different words for the same pattern. Amazon SageMaker attaches an approval status to each version, and Uber's platform deploys a model to a tag. In every case the versions stay fixed and a label moves.

Read downward, the chain answers an auditor: this alias, this version, this run, these parameters, this code commit, this data hash. Read upward, it answers an incident: which registered models were trained on the file that turned out to be corrupt? Either direction works only if every link was written down at training time.

Worked example: Track five kNN runs on solar data, register the best one and trace it back

Twelve days of readings from a rooftop solar panel: hours of sunshine and the energy generated in kWh. The numbers are invented so that every result can be checked by hand. Eight days are for training and four for validation. The model is a k-nearest-neighbours regressor, which predicts the average output of the k training days with the most similar sunshine, and k is the hyperparameter to choose.

You need Python with MLflow (pip install mlflow, which also installs scikit-learn). The code targets MLflow 3, version 3.17 at the time of writing, where log_model takes a name argument; examples written for MLflow 2 pass artifact_path instead. Work in an empty folder and save the Python blocks below, in order, as one script.

Step 1: log one run per setting

python
import hashlib
import math
from pathlib import Path

import mlflow
from mlflow import MlflowClient
from sklearn.neighbors import KNeighborsRegressor

CSV = """split,sun_hours,kwh
train,0.9,1.4
train,2.2,4.5
train,3.3,4.4
train,4.5,8.1
train,5.2,7.4
train,6.5,11.1
train,7.5,11.0
train,9.0,14.5
val,1.6,2.8
val,3.8,6.2
val,6.1,9.4
val,8.4,13.1
"""
Path("solar.csv").write_bytes(CSV.encode())
data_md5 = hashlib.md5(Path("solar.csv").read_bytes()).hexdigest()

rows = [line.split(",") for line in CSV.splitlines()[1:]]
X_train = [[float(h)] for s, h, _ in rows if s == "train"]
y_train = [float(k) for s, _, k in rows if s == "train"]
X_val = [[float(h)] for s, h, _ in rows if s == "val"]
y_val = [float(k) for s, _, k in rows if s == "val"]


def rmse(model, X, y):
    errors = [target - guess for target, guess in zip(y, model.predict(X))]
    return math.sqrt(sum(e * e for e in errors) / len(errors))


mlflow.set_tracking_uri("sqlite:///mlflow.db")
mlflow.set_experiment("solar-knn")

for k in [1, 2, 3, 5, 8]:
    with mlflow.start_run(run_name=f"knn-k{k}"):
        model = KNeighborsRegressor(n_neighbors=k).fit(X_train, y_train)
        mlflow.log_params({"model": "knn", "n_neighbors": k})
        mlflow.set_tag("data_md5", data_md5)
        mlflow.log_metric("train_rmse", rmse(model, X_train, y_train))
        mlflow.log_metric("val_rmse", rmse(model, X_val, y_val))
        mlflow.sklearn.log_model(sk_model=model, name="model")

Each pass through the loop is one run. When the loop ends, the experiment solar-knn holds five runs, each with two parameters, two metrics, one tag and a model folder. The parameters and metrics are rows in mlflow.db, and the model files are in a local artifact folder, mlruns by default.

Step 2: compare the runs

python
runs = mlflow.search_runs(experiment_names=["solar-knn"], order_by=["metrics.val_rmse ASC"])
for _, run in runs.iterrows():
    print(
        f"k={run['params.n_neighbors']}  train_rmse={run['metrics.train_rmse']:.3f}  "
        f"val_rmse={run['metrics.val_rmse']:.3f}  data={run['tags.data_md5'][:8]}"
    )
text
k=2  train_rmse=0.846  val_rmse=0.206  data=25654e92
k=3  train_rmse=1.562  val_rmse=0.630  data=25654e92
k=1  train_rmse=0.000  val_rmse=1.657  data=25654e92
k=5  train_rmse=2.080  val_rmse=1.908  data=25654e92
k=8  train_rmse=4.026  val_rmse=3.815  data=25654e92

The output shows three things that memory would have lost.

  • The training metric alone would have picked the wrong model. With k = 1 every training day is its own nearest neighbour, so the training error is exactly 0, yet its validation error is eight times that of k = 2.
  • The winner can be checked by hand. For the validation day with 3.8 hours of sun, the two nearest training days have 3.3 hours (4.4 kWh) and 4.5 hours (8.1 kWh). Their average is 6.25 kWh, and the meter read 6.2.
  • All five runs carry the same data hash, so the comparison is between settings and nothing else. Note also that params.n_neighbors came back as the string "2", not the integer 2.

Step 3: register the winner and point an alias at it

python
best = runs.iloc[0]
version = mlflow.register_model(f"runs:/{best['run_id']}/model", "solar-forecast")
client = MlflowClient()
client.set_registered_model_alias("solar-forecast", "champion", version.version)

champion = mlflow.pyfunc.load_model("models:/solar-forecast@champion")
print(f"version {version.version} predicts {float(champion.predict([[5.0]])[0]):.2f} kWh")
text
version 1 predicts 7.75 kWh

register_model created the registered model solar-forecast with version 1, linked to the k = 2 run. The alias champion points at that version, and the last two lines load the model through the alias, the way a serving process would. The prediction for 5.0 hours of sun is the average of the training days at 5.2 hours (7.4 kWh) and 4.5 hours (8.1 kWh), which is 7.75.

Step 4: walk the lineage back

python
current = client.get_model_version_by_alias("solar-forecast", "champion")
source = client.get_run(current.run_id)
print(
    f"champion -> version {current.version}, k={source.data.params['n_neighbors']}, "
    f"data={source.data.tags['data_md5'][:8]}"
)
text
champion -> version 1, k=2, data=25654e92

Starting from nothing but the alias, the registry returned the version, the version returned its run, and the run returned the hyperparameter and the fingerprint of the training file. If solar.csv were tracked with dvc add, its pointer file in Git would carry an MD5 of the same file, and dvc checkout could restore those exact bytes.

MLflow prints its own log lines between the ones shown here, for example when the model is registered. Run IDs are random, which is why the script never prints one. If you run the script a second time, the experiment holds ten runs and the registry gains version 2, because a tracker appends and never overwrites.

Edge cases and limitations

Running the script again adds runs; it does not replace them
A tracker appends. Execute the worked example twice and the experiment holds ten runs, a search returns all ten, and the registry gains a second version of the same model. That is the intended behaviour, but it surprises people who expect a rerun to overwrite a result. Give related runs a shared tag, such as a sweep name or the Git commit, and filter on it when you compare.
Metrics from different validation data are not comparable
Two runs with identical parameters can differ by several points only because one was scored after the validation file was refreshed. The tracker will rank them without complaint. Log a hash of the training and validation data in every run, and treat a difference in that hash as a different experiment, not as an improvement.
Moving an alias changes the model for every caller at once
MLflow's documentation notes that when an alias is reassigned, the next load through that alias picks up the new version. There is no gradual rollout in that mechanism, and a version that expects different input columns will break callers the moment the alias moves. Test a new version under a second alias first. Remember too that a service which loaded the model at start-up keeps the old one in memory until it reloads.
Parameters are strings, with a length limit
MLflow string-ifies parameter values, and its built-in backend stores accept values up to 6,000 characters. A search filter must therefore quote the value, as in params.epochs = "3", and a long feature list or a whole configuration file does not belong in a parameter. Log large structures as an artifact file and keep parameters to the handful of settings you sweep.
A committed pointer file without pushed data is a dead link
DVC puts only a hash in Git. If the pointer file is committed but dvc push never ran, a colleague or a CI job that clones the repository has the hash and no way to get the bytes, and if the local cache is later cleared that version is gone for everyone. Push data before pushing the Git commit, and have CI run dvc pull on a clean checkout so that a missing object fails fast.
Recorded inputs do not guarantee identical outputs
The same code, data and parameters can still give a slightly different model when the random seed is not fixed, when a library version changed or when a GPU operation is non-deterministic. Tracking tells you what happened; it does not replay it. Log the seed and the package versions, and expect to reproduce a metric to within a tolerance, not to the last digit.

When to use it, and when something simpler is enough

Use it when

  • You train more than a handful of model variants and must choose one on evidence, as in any hyperparameter search, feature experiment or architecture comparison.
  • More than one person, or a scheduled job, trains or deploys the model, so the record cannot live in one person's notebook.
  • The model's predictions affect customers, money or compliance, and you may be asked which data and code produced it.
  • The training data changes over time through new exports or relabelling, and you need to rerun or compare against an earlier snapshot.
  • Deployment is separate from training and needs a stable name to load, plus a fast way back to the previous model.

Think twice when

  • The work is a one-off analysis or a teaching notebook in which one model is fitted once and never deployed. The notebook is the record.
  • The data already lives in a store that versions it, such as a table format with snapshots. Log the snapshot identifier in the run and skip a second file-versioning layer.
  • There is one model, one environment and one person deploying it. A registry is another service to run, and a tagged container image or Git tag can carry the same pointer.

A simpler alternative. Have the training script append one row per run to a CSV file: timestamp, Git commit, parameters and metrics, with the model saved under a file name that contains the same timestamp. This costs ten lines and already beats memory. It stops being enough when two people write to the file, when you want metric curves or artifacts next to the numbers, when the files outgrow Git, or when a deployment needs to ask which model is current.

Key takeaways

  • A run is one execution of training code, and a tracker records its parameters, metrics, tags and artifacts so that nothing depends on memory.
  • Runs are comparable only when they were scored on the same data, so the data version belongs in every run next to the hyperparameters.
  • DVC versions a large file by keeping its content hash in a small pointer file that Git tracks, while the bytes live in a cache and in remote storage.
  • A model registry holds numbered versions whose files never change, and aliases, stages or approval statuses are movable labels that say which version is current.
  • Promotion and rollback are pointer moves, not file copies, and they take effect for every caller that loads the model through that label.
  • Lineage is the chain from alias to version to run to code commit and data hash, and it exists only if each link was recorded at training time.

Example 1 of 5

Uber Michelangelo: a versioned record for every trained model

UberDocumented in an engineering article

Michelangelo is Uber's internal machine learning platform. The engineering post "Meet Michelangelo: Uber's Machine Learning Platform", published in 2017 by members of the platform team, describes what the platform stores for each trained model and how deployed models are referenced at serving time. [12]

The problem

The post explains that models are trained as part of a methodical exploration of features, algorithms and hyper-parameters, and that it is not uncommon to train hundreds of models that do not make the cut before the one that goes to production. Keeping track of them (who trained each one and when, on what data set, with which hyper-parameters), evaluating them and comparing them with each other is described as a big challenge at that volume.

Where this topic fits

The record is written by the platform when a training job finishes, and it is what the "evaluate models" step of the platform's workflow works from: the web UI and the API read it to show one model or to compare several. The model it describes is what the "deploy models" step later refers to by identifier.

How it is applied, step by step

  1. A training job finishes, and the platform, not the engineer, writes a versioned object for the model into a model repository held in Cassandra.
  2. The object records who trained the model, when the job started and ended, the full configuration including the features used and the hyper-parameter values, and references to the training and test data sets.
  3. It also stores the evaluation results, including accuracy metrics, standard charts for the model type, the distribution and relative importance of each feature, and the learned parameters.
  4. Engineers open these records in a web UI or query them through an API, either to inspect one model in detail or to compare several.
  5. A chosen model is deployed and is identified at serving time by its UUID and, optionally, by a tag that was given at deployment.
  6. A client that asks for a tag gets the model most recently deployed to that tag, so a replacement with the same input signature can take over without a change to the caller.

Why this approach fits

The decisive design choice is that the platform writes the record. An engineer cannot forget to log a run or log only the good ones, so the hundreds of discarded models stay available as evidence for why the chosen one was chosen.

The tag plays the role this lesson calls an alias. Callers name a stable label, and the mapping from label to model is changed at deployment time, which separates releasing a model from releasing the service that calls it.

Limitation or tradeoff

The post describes the system as it stood in 2017, and it is an in-house platform, not a product you can install. Redeploying to a tag switches every caller of that tag at once, and the post makes the replacement conditional on both models expecting the same set of features. A gradual switch is done differently, by deploying under a UUID and changing configuration in the client, and comparing two models on live traffic relies on a separate experimentation framework. A reference to a data set is also only as good as the guarantee that the data set behind it has not changed.

What the sources document

  • The post says it is not uncommon to train hundreds of models that do not make the cut before arriving at the ideal model, and that keeping track of these models (who trained them and when, on what data set, with which hyper-parameters), evaluating them and comparing them are typically big challenges. [12]
  • For every model trained in Michelangelo, a versioned object is stored in a model repository in Cassandra. It records who trained the model, the start and end time of the training job, the full model configuration (features used, hyper-parameter values), a reference to the training and test data sets, the distribution and relative importance of each feature, accuracy metrics, standard charts, the full learned parameters and summary statistics. [12]
  • The information is available through a web UI and programmatically through an API, both for inspecting an individual model and for comparing one or more models with each other. [12]
  • At serving time a model is identified by its UUID and an optional tag (or alias) specified during deployment. For an online model the client sends the feature vector with the UUID or tag, and for a tag the container uses the model most recently deployed to that tag. [12]
  • If a new model has the same signature as the old one, users can deploy it to the same tag and the container starts using it immediately. Competing models can be deployed under UUIDs or tags and traffic split between them with Uber's experimentation framework. [12]

The facts above come from the cited sources. The steps and analysis in this example are our explanation of how they fit together.

Example 2 of 5

GitLab: MLflow-compatible experiment tracking inside the code host

GitLabDocumented in official docs

GitLab's documentation pages "MLflow client compatibility" and "Model registry" describe how GitLab projects accept logging calls from the open-source MLflow client, so that runs, models and model versions are stored in the same project as the code and its CI/CD pipelines. [13][14]

The problem

Training code that already logs with MLflow needs a tracking server to send its records to. Running a separate server means one more service to host and secure, and the runs end up apart from the repository, merge requests and pipeline jobs that produced them. GitLab's pages address this by letting the existing client talk to a GitLab project, with what the documentation calls minimal changes to existing code.

Where this topic fits

Nothing changes inside the training loop: the script still calls start_run, log_param and log_metric. The integration sits at the destination of those calls. An environment variable points the client at a project's MLflow-compatible endpoint, and GitLab stores what arrives as model experiments, runs and registry entries that are browsable in the project.

How it is applied, step by step

  1. Create an access token with the api scope and find the numeric ID of the GitLab project.
  2. Set MLFLOW_TRACKING_URI to the project's endpoint, which ends in /api/v4/projects/ followed by the project ID and /ml/mlflow, and set MLFLOW_TRACKING_TOKEN to the token.
  3. Remove any call to mlflow.set_tracking_uri from the training code, so that the environment variables decide where records go.
  4. Run the script. Experiments and runs appear in the project, with the logged parameters, metrics and artifacts.
  5. When the script runs in a CI/CD job, set the tag gitlab.CI_JOB_ID to the job's ID inside the run, and GitLab associates the run with that job.
  6. Register models through the same client. GitLab keeps each model version's files as a package, and a version created in a CI/CD job can be linked to the job, its logs, its merge request and its pipeline.

Why this approach fits

The MLflow client has become a common interface, so a platform that accepts its calls can replace the server without anyone rewriting training code. Storing the run beside the job that executed it closes a lineage link that is otherwise recorded by hand: from a metric you can reach the job log, the commit and the merge request in one system with one set of permissions.

Limitation or tradeoff

Compatibility is partial. The page lists the supported client methods and their caveats: log_model saves the artifacts but not the model data, artifact paths must be empty, directories are not supported, search_runs accepts a single experiment when ordering, and methods outside the list "might still work but have not been tested". In the registry, version names must follow semantic versioning, the stages argument is ignored, and creating a model version from a run is not yet supported. Each file is limited to 5 GB. A team that depends on the full MLflow feature set still needs an MLflow server.

Thoughtworks CD4ML: DVC ties a deployed model to its data and code

ThoughtworksDocumented in an engineering article

"Continuous Delivery for Machine Learning", published on martinfowler.com in September 2019 by three Thoughtworks consultants, walks through a sales-forecasting application built to demonstrate the approach. The Thoughtworks Technology Radar entry for DVC, moved to Adopt in April 2023, reports that the firm's teams use the tool in production. [15][16][10]

The problem

The article starts from the observation that a machine learning application changes along three axes: code, model and data. Training data and model files are too large for the source repository, the trained model has to reach a separate application build as a versioned artifact, and a change in the data does not trigger a delivery pipeline because no code has changed.

Where this topic fits

DVC is the layer between Git and bulk storage. Upstream it tracks the raw data file and the stages that turn it into a model. Downstream it is the hand-off: the training pipeline publishes the model file to storage, and the application pipeline fetches that file by the hash recorded in Git.

How it is applied, step by step

  1. Each step of training (fetch the data, split it, train the model) is declared to DVC with its dependencies, its outputs and a metrics file, and DVC writes a small file per step that is committed to Git.
  2. Anyone with the repository can re-execute the whole pipeline with one command, because DVC keeps the dependency graph and the commands.
  3. In the delivery tool, a machine learning pipeline trains and evaluates the model and runs a threshold test. If the model passes, the pipeline runs dvc push to publish the model file to external storage.
  4. A second pipeline builds the application, runs dvc pull to fetch the promoted model, and packages both into one Docker image that is deployed to production.
  5. To react to new data, the raw file is put under dvc add. Its checksum lives in a metadata file in Git, so a change in the data becomes a commit, and the commit triggers the pipeline.
  6. Experiments are kept on Git branches, with DVC showing metrics across branches, and an MLflow Tracking server provides a web view of runs with their parameters and metrics.

Why this approach fits

Continuous delivery tools react to commits. By turning a data version and a model version into small files inside a commit, DVC lets one Git hash name the code, the data and the model together, and lets the existing pipeline machinery do the rest. The authors say they chose it because it is a simple command-line tool that solves this part of the problem well; no additional server has to be run.

Limitation or tradeoff

The authors name two gaps themselves: keeping the full history of data that changes frequently is not always feasible, and a checksum does not record which processing step changed the data. Tracking experiments on Git branches also runs against their own preference for integrating on a single trunk. The Radar entry adds that file-system snapshots become expensive as data sets grow. The commands shown date from 2019; current DVC documentation declares the same stages in a dvc.yaml file and records their hashes in dvc.lock.

What the sources document

  • The authors used DVC to formalise model training in code, listing that it stores large files on external storage outside the source repository, keeps track of those files' versions, keeps the dependency graph and commands of the pipeline so it can be reproduced elsewhere, and integrates with Git branches. [15]
  • Each dvc run creates a file that can be committed to version control and lets other people reproduce the whole pipeline with dvc repro. In the GoCD setup the machine learning pipeline trains and evaluates the model, runs a threshold test and, if the model is good, performs dvc push; the application deployment pipeline fetches the promoted model with dvc pull, packages it with the application as a Docker image and deploys it to a Kubernetes production cluster. [15]
  • Running dvc add on the raw data file creates a metadata file that tracks a checksum of the file's content and can be committed to Git. When the content changes, the checksum changes, and that commit triggers a pipeline execution. [15]
  • The April 2023 Radar entry places DVC in Adopt, says Thoughtworks teams have used it in production to enable continuous delivery for ML with storage such as AWS S3, Google Cloud Storage, MinIO and Google Drive, and warns that file system based snapshotting can become expensive as data sets grow. Amazon SageMaker Model Registry: an approval status that gates deployment

Amazon Web ServicesDocumented in official docs

Amazon SageMaker AI is a managed machine learning service. Three pages of its Developer Guide describe the Model Registry: what it catalogues, how a model version is registered into a Model Group, and how a version's approval status is updated and what that update sets in motion. [17][18][19]

The problem

The guide states the situation plainly: after a model version is created, you typically want to evaluate its performance before it is deployed to a production endpoint. Something has to hold a newly trained model back until that evaluation has happened, record the decision, and start deployment only for versions that passed.

Where this topic fits

The registry stands between the training pipeline and the deployment automation. A version arrives from training with a pending status. The status field is the gate: changing it is the event that deployment reacts to, and changing it back is the rollback path.

How it is applied, step by step

  1. Create a Model Group for the problem. It will hold every version of the model trained for that problem.
  2. Each run of the training pipeline registers its model as a new version in the group, giving the location of the model artifacts and the inference image, with the approval status set to PendingManualApproval.
  3. A reviewer, or a condition step in the pipeline, evaluates the pending version against the team's requirements.
  4. If it passes, the status is updated to Approved through the API or the Studio console. With the project templates that SageMaker provides, that change initiates CI/CD deployment of the approved version.
  5. If it fails, the status is set to Rejected, and no action follows.
  6. If an approved version later has to be withdrawn, changing it from Approved to Rejected starts CI/CD to deploy the latest version that still has an Approved status.

Why this approach fits

An approval status separates two duties that should not sit with the same script: producing a model and deciding that it may serve traffic. Because the decision is a field on the version, it is recorded where the version's metrics and lineage already are, and because a change to the field is an event, deployment can be automated without giving the training job any permission to deploy.

Limitation or tradeoff

The status has three values and belongs to one version, so it expresses "may be deployed" but not "is the one deployed": the documented rollback rule simply picks the latest approved version. The automatic deployment described on the page is the behaviour of the project templates SageMaker provides; outside them you must build the reaction to a status change yourself. And an approval is only as good as the evaluation behind it. The field records that someone approved, not what they checked.

What the sources document

  • The Model Registry page lists what the registry is for, including cataloguing models for production, managing model versions, associating metadata such as training metrics with a model, viewing model lineage for traceability and reproducibility, managing the approval status of a model and automating model deployment with CI/CD. [17]
  • Models are catalogued in Model (Package) Groups that contain different versions of a model. In the typical workflow each run of an ML pipeline creates a model version that is registered in the Model Group. [17]
  • A model version is registered with the create_model_package operation, naming the Model Group and the inference specification. The example sets ModelApprovalStatus to PendingManualApproval. [18]
  • With a SageMaker-provided project template, a change from PendingManualApproval to Approved initiates CI/CD deployment of the approved version, a change to Rejected causes no action, and a change from Approved to Rejected initiates CI/CD to deploy the latest version with an Approved status. [19]
  • The status can be updated with update_model_package in Boto3, in the Studio console, or as part of a condition step in a SageMaker pipeline, and the page notes that the update can be automated from the result of an evaluation of the model's performance. [19]

Hugging Face Hub: pinning a model download to a Git revision

Hugging FaceDocumented in official docs

The Hugging Face Hub hosts models in Git-based repositories that are downloaded by name. The Hub guide "Getting Started with Repositories" and the huggingface_hub library guide "Download files from the Hub" document how files are versioned by commit and how a client selects a specific revision. [20][21]

The problem

A model on the Hub is addressed by a repository name, and its owner can push new weights or a new configuration at any time. A program that downloads the model by name alone gets whatever is newest, so the same code can load different weights next month, and a result built on a public base model cannot be reproduced unless the exact files are identified.

Where this topic fits

This is model versioning from the consumer's side. The repository is the registry entry, each commit is a version, and the main branch is a moving pointer like an alias. The revision argument at download time is where a consumer chooses between following the pointer and fixing a version.

How it is applied, step by step

  1. A publisher adds or changes files and pushes a commit. The Hub keeps the history, and every commit can be inspected with its diff. Large files such as weights are handled by the Xet extension.
  2. A consumer who calls the download function with only a repository name and a file name receives the latest version on the main branch.
  3. To fix the version, the consumer passes a revision, which can be a branch name, a tag, a pull request reference or a commit hash. A commit hash must be given in full.
  4. The library stores the file in a version-aware local cache, in a snapshots folder named after the commit, so several revisions of one model can coexist on disk.
  5. A careful consumer then logs the hash as a parameter or tag of the training or evaluation run, which extends that run's lineage to the upstream model.

Why this approach fits

Git already provides an identifier that cannot be reassigned, the commit hash, so the Hub gets immutable versions without inventing a numbering scheme, and pinning costs the consumer one argument. Keeping the default on main suits exploration, where the newest files are usually wanted, while the pin suits anything that has to give the same answer twice.

Limitation or tradeoff

A repository's history versions files, not the process that made them. Nothing in a commit links the weights to a training run, its parameters or its data, so that part of the lineage depends on what the publisher chose to write down. Branch names and tags are also movable, so only a full commit hash is a real pin. A pin does not protect against a repository being deleted or made private; keep a copy of any external model that a production system depends on.

What the sources document

  • hf_hub_download downloads the remote file, caches it on disk in a version-aware way and returns the local path. The example path printed in the guide contains a snapshots folder followed by a folder with a 40-character hexadecimal name. [20]
  • By default the latest version from the main branch is downloaded. The revision parameter selects a particular version, such as a branch, a pull request, a tag or a commit hash. [20]
  • When a commit hash is used as the revision it must be the full-length hash, not a 7-character one. [20]
  • snapshot_download downloads an entire repository at a given revision and takes the latest revision by default. [20]
  • The repositories guide describes a commit as something that can be thought of as a revision of the project, says the repository keeps track of every change made through the add, commit and push cycle, and that the web interface shows the history and the diff introduced by each commit. [21]

4Common mistakes

  1. Logging only the runs that turned out well, or writing the numbers down after choosing the winner.

    Why it causes problems
    The discarded runs are the evidence for the choice. Without them nobody can see what was already tried, work gets repeated, and a score that was the best of fifty attempts looks like the result of one.
    How to recognise it
    The experiment holds one run per week, every run has a good metric, or the run start times are all minutes before a report was due.
    How to fix it
    Put the logging inside the training function so that every execution creates a run, or call mlflow.autolog() once at the top of the script. Decide after the runs exist, by querying them.

  2. Comparing runs that were trained or validated on different versions of the data.

    Why it causes problems
    A gain that came from a refreshed validation file is reported as a modelling improvement, and a model is promoted for a reason that does not exist. The ranking in the tracking UI looks equally confident either way.
    How to recognise it
    Two runs with identical parameters and the same code commit have clearly different metrics, or the runs carry no tag or logged input that identifies the data.
    How to fix it
    Log a content hash of the training and validation data in every run, by hand as a tag, from the DVC pointer file, or with mlflow.log_input. Filter on that value before you rank runs.

  3. Committing datasets and model files to Git, or versioning them through file names such as model_final_v2.pkl.

    Why it causes problems
    The repository grows with every retrain and every clone downloads all of it, while a file name says nothing about which run, code or data produced the file. Two people will eventually overwrite each other's final version.
    How to recognise it
    The repository is hundreds of megabytes, clones are slow, or a models folder contains several files whose names differ only by a suffix such as v2, new or final.
    How to fix it
    Track large files with DVC, or log them as run artifacts, and commit only the pointer file. Refer to a model by its registry version or run ID, never by a file name.

  4. Hard-coding a version number or a storage path for the model in the serving code.

    Why it causes problems
    Every promotion becomes a code change and a redeploy of the service, and a rollback takes as long as a release. The registry no longer shows which model is live, because the truth is in a source file.
    How to recognise it
    Searching the serving repository finds a URI that ends in a version number, or a bucket path with a model file name in it.
    How to fix it
    Load the model through an alias, such as models:/churn@champion, and change the alias in the registry to promote or roll back. Keep one registered model per environment if dev and prod must differ.

  5. Treating the move of an alias or the approval of a version as if it were the test.

    Why it causes problems
    A label only records a decision. If the decision was made on the training metric, or without checking the model's input columns against the callers, the new version fails in production for every caller at the same moment.
    How to recognise it
    The registry shows versions promoted minutes after registration, with no validation tag, no evaluation run attached and no period under a second alias.
    How to fix it
    Require a recorded check before promotion: an evaluation run on held-out data, a comparison with the current champion, and a status tag such as validation_status set to passed. Give the candidate its own alias and send it a share of traffic first.

Exercise 1

Build a small data versioner to see what DVC stores

CodingIntermediateAbout 40 min (estimate)Hypothetical scenario

The core idea of DVC is small enough to build yourself. Using only the Python standard library, write a script that versions a file the way dvc add and dvc checkout do.

Implement two functions:

  • add(path) reads the file's bytes, computes their MD5 hash, and copies the bytes into a store at .store/files/md5/ followed by a folder named after the first two hex characters of the hash and a file named after the remaining thirty. If that object already exists it is not written again. The function returns a pointer: a dictionary with the keys md5, size and path.
  • checkout(pointer) reads the object the pointer names, checks that its hash still matches, and writes it back to pointer["path"].

A Python list called history plays the part of Git. It holds one pointer per commit.

The first version of prices.csv is these three lines, each ending with a single newline character:

text
item,price
tea,3.50
coffee,4.20

Run this scenario:

  1. Write prices.csv with exactly those bytes, add it and append the pointer to history.
  2. Append the line cocoa,4.80 to the file, add it again and append the second pointer.
  3. Print both pointers as JSON and print the number of objects in the store.
  4. Check out the first pointer and print the restored bytes. Add the file once more, print whether the returned pointer equals the first one, and print the number of objects again.

Requirements

  • Use only the standard library (hashlib, json, pathlib, shutil). Do not install DVC for this exercise.
  • Write and read the file in binary mode, so that the bytes and therefore the hashes are the same on every operating system.
  • The store path must be derived from the hash alone, never from the file name or the time.
  • Adding content that is already in the store must not create a second object.
  • checkout must raise an error if the stored object no longer matches its hash.

Expected behaviour

The script prints exactly this (the hashes depend only on the bytes, so yours must match):

text
commit 1: {"md5": "d5008e649c3c978802d30adbdb8ce353", "size": 32, "path": "prices.csv"}
commit 2: {"md5": "17f729000bc2b96c7f4c78228594a517", "size": 43, "path": "prices.csv"}
objects in store: 2
restored: b'item,price\ntea,3.50\ncoffee,4.20\n'
same pointer after re-adding: True
objects in store: 2

The store holds two objects after two versions, and still two after the first version is added a third time.

Hint 1

hashlib.md5(data).hexdigest() returns 32 hex characters. Slice it into the first two and the remaining thirty to build the folder and file name.

Hint 2

Open the file with mode ab to append bytes. Text mode may translate the newline on Windows and change the hash.

Hint 3

If your first hash differs from the expected one, print the bytes of the file. A missing final newline or a stray space is the usual cause.

Show solution
python
import hashlib
import json
import shutil
from pathlib import Path

STORE = Path(".store/files/md5")


def add(path):
    """Copy the file into the store under its hash and return a pointer."""
    data = Path(path).read_bytes()
    digest = hashlib.md5(data).hexdigest()
    target = STORE / digest[:2] / digest[2:]
    if not target.exists():
        target.parent.mkdir(parents=True, exist_ok=True)
        target.write_bytes(data)
    return {"md5": digest, "size": len(data), "path": str(path)}


def checkout(pointer):
    """Rewrite the working file from the stored content the pointer names."""
    digest = pointer["md5"]
    data = (STORE / digest[:2] / digest[2:]).read_bytes()
    if hashlib.md5(data).hexdigest() != digest:
        raise ValueError(f"stored object {digest} is corrupted")
    Path(pointer["path"]).write_bytes(data)


def stored_objects():
    return sorted(p.parent.name + p.name for p in STORE.glob("*/*"))


shutil.rmtree(".store", ignore_errors=True)  # start from an empty store
history = []  # stands in for Git: one pointer per "commit"

Path("prices.csv").write_bytes(b"item,price\ntea,3.50\ncoffee,4.20\n")
history.append(add("prices.csv"))

with open("prices.csv", "ab") as handle:
    handle.write(b"cocoa,4.80\n")
history.append(add("prices.csv"))

for number, pointer in enumerate(history, start=1):
    print(f"commit {number}: {json.dumps(pointer)}")
print("objects in store:", len(stored_objects()))

checkout(history[0])
print("restored:", Path("prices.csv").read_bytes())
print("same pointer after re-adding:", add("prices.csv") == history[0])
print("objects in store:", len(stored_objects()))

Running it prints the six lines given under expected behaviour.

What each part corresponds to in DVC:

In the scriptIn DVC
add() hashing and copying into .store/files/md5/d5/008e…dvc add moving the file into .dvc/cache/files/md5/
The returned dictionaryThe .dvc pointer file, with its md5 and path fields
The history listGit commits of the pointer file
checkout(history[0])git checkout of the old pointer, then dvc checkout
Copying .store to another diskdvc push to a remote

Two properties fall out of naming objects by their hash. The same content is stored once, however many times it is added, which is why the count stays at 2. And corruption is detectable, because an object whose bytes no longer hash to its own name is wrong by definition. What the script leaves out is what makes DVC practical: links instead of copies for large files, directories, remote storage and the .gitignore entry that keeps the data out of Git.
