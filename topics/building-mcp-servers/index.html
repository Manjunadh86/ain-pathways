Building an MCP Server

Building an MCP server means writing a program, usually with an official SDK, that publishes tools (each with a name, a description and an input schema) so that any MCP client can list and call them. You test it with the MCP Inspector and connect it to a host by launching it over stdio or serving it over HTTP.

1Overview

Why it matters

A model can only act on the systems it has tools for, and an MCP server is how you give it those tools once, for every client that speaks the protocol. The server author decides what the model can see and do: which operations exist, how they are named and described, which arguments are accepted, and what comes back when something fails. Those choices decide whether an agent picks the right tool, recovers from a bad argument, or does damage quietly.

The mistakes are ordinary and expensive. One print() in a stdio server corrupts the protocol stream. A vague error leaves the model guessing. Mirroring a whole REST API as hundreds of tools crowds the model's context. A config entry with a relative path makes the server disappear from the host with no obvious error. Anyone who connects an agent to internal data, a SaaS product or a company API will build a server or review one, and needs to know how to test it before a model ever calls it.

  • Decide how many tools to expose, and which to hide or gate, using the practice of real servers.

Key terms

MCP server
A program that answers MCP requests by publishing capabilities, most commonly tools, to a client that launches it or connects to it.
SDK
An official library (for example the Python package `mcp` or the TypeScript package `@modelcontextprotocol/server`) that handles the protocol so you write only tool logic.
Tool
A named operation with a description and an input schema that a model can ask the client to call.
Input schema
A JSON Schema object that states which arguments a tool accepts. The SDK checks every call against it.
Tool execution error
A failure reported inside an ordinary result with `isError: true`, so the model can read the message and retry.
Protocol error
A JSON-RPC error response used when the request itself is wrong, such as an unknown tool. The host sees it; the model usually does not.
stdio transport
The local transport in which the client starts your server as a subprocess and exchanges one JSON message per line over its standard input and output.
Streamable HTTP
The remote transport in which every message is an HTTP POST to a single endpoint such as `/mcp`.
MCP Inspector
The reference developer tool that connects to a server as a stand-in client, in a browser, a terminal or a script, to list tools, call them and show the raw messages.

2Explanation

Introduction

In MCP Primitives you met the three things a server can offer: tools the model calls, resources the application reads and prompts the user picks. This lesson is about the other side of the wire: writing the server. We concentrate on tools, because almost every server ships them first and most mistakes happen there.

A useful picture is a function library with a strict front desk. Your tool is an ordinary function. The SDK is the front desk: it publishes a catalogue of functions with their argument rules, checks each incoming call against those rules, runs the function, and wraps the result (or the failure) in the message format the protocol requires. You write the function, the rules and the error messages; the SDK writes the protocol.

The diagram also shows the tool that makes development comfortable. The MCP Inspector is a stand-in client. You point it at your server, it lists the tools, lets you call them and shows the raw messages, and no model or chat application is involved until you choose to add one.

A version note matters here. This lesson follows the documentation current on 2026-10-11: protocol revision 2026-07-28, the Python SDK 2.x (mcp 2.3.0 on PyPI that day) and the TypeScript SDK v2 packages (2.3.1 on npm). Many tutorials still show the Python class FastMCP from SDK v1, which v2 renamed to MCPServer. The ideas carry over, but import lines and some error behaviour differ, so check which SDK version a tutorial uses before copying from it.

The lesson covers declaring tools and their schemas, reporting errors, running a server over stdio or HTTP, testing in layers and connecting a client. A worked example builds a small loan-calculator server in Python and checks every number.

How it works

The jobs of a server author

Whatever the language, a server comes down to six jobs: declare tools, write handlers, report failures on the right channel, choose a transport, test in layers, and connect a client. The official quickstart has tabs for Python, TypeScript, Java, Kotlin, C#, Ruby, Rust and Go, and each SDK offers the same features in its own idiom.

Declare a tool

A tool has a name, an optional title, a description and an inputSchema, which is a JSON Schema object. The description is prompt text: the model reads it when it chooses a tool, so write it for the model. The specification suggests names of 1 to 128 characters (letters, digits, underscore, hyphen, dot) that are unique within the server. Schemas default to JSON Schema 2020-12, and a tool without parameters should use { "type": "object", "additionalProperties": false }.

In Python you do not write the schema. The @mcp.tool() decorator reads the function name, the docstring and the type hints and generates it. Annotated[int, Field(ge=1, le=50, description="...")] adds bounds and per-argument descriptions, and the SDK validates arguments against them before your function runs, returning a validation error to the model. In TypeScript you pass a schema object to registerTool; the SDK quickstart uses Zod.

python
from mcp.server import MCPServer

mcp = MCPServer("Bookshop")

@mcp.tool()
def search_books(query: str, limit: int = 10) -> str:
    """Search the catalog by title or author."""
    return f"Found 3 books matching {query!r} (showing up to {limit})."
typescript
import { McpServer } from "@modelcontextprotocol/server";
import * as z from "zod/v4";

const server = new McpServer({ name: "bookshop", version: "1.0.0" });

server.registerTool(
  "search_books",
  {
    description: "Search the catalog by title or author",
    inputSchema: z.object({ query: z.string(), limit: z.number().int().min(1).max(50) }),
  },
  async ({ query, limit }) => ({
    content: [{ type: "text", text: `Found 3 books matching "${query}" (showing up to ${limit}).` }],
  }),
);

The Python snippet follows the SDK documentation; the TypeScript one is our adaptation of the SDK quickstart. Both produce a tools/list entry with a name, a description and an inputSchema. A handler returns content blocks (text, image, audio, resource links or embedded resources). A tool may also declare an outputSchema and return structuredContent that matches it, in which case the specification recommends including the same JSON as text too. ToolAnnotations such as read_only_hint describe behaviour to clients, but clients must treat annotations as untrusted unless the server is trusted.

How many tools to publish is a design decision of its own. The examples below show real servers that group tools into toolsets, offer a few generic tools over a very large API, or switch writes off.

What the SDK does on each call

Revision 2026-07-28 is stateless. There is no initialize handshake and no protocol-level session: every request carries the protocol version and the client's capabilities in _meta, and a server must not rely on earlier requests on the same connection. The SDK handles this. Clients and servers on the earlier revision still use the handshake, so SDKs and the Inspector keep a legacy mode beside the modern one. Your part is to keep hidden per-connection state out of tool code. If calls must share state, return an explicit handle from a creation tool, accept it as an argument, bind it to the authenticated user, and state its lifetime in the description.

Two ways to fail

A protocol error is a JSON-RPC error response for problems with the request: an unknown tool, a malformed request, a server fault. A tool execution error is an ordinary result with isError: true, used for API failures, input validation problems and business-rule violations. The specification says clients should pass tool execution errors to the model so it can correct itself, and may pass protocol errors on, though they rarely lead to recovery.

The SDKs differ in detail. In Python, raise ToolError(message) shows the message to the model (prefixed with Error executing tool <name>:), raise MCPError(code, message) produces a JSON-RPC error that only the host sees, and any other exception is treated as a crash: the model gets only generic text ("Error executing tool" plus the tool's name) and the traceback is logged. The TypeScript SDK turns anything a tool handler throws into an isError result carrying the exception's message. Write that message for the model: say what went wrong and what to do next. Keep secrets, stack traces and internal hostnames out of it.

The SDKs also disagree about an unknown tool name. The specification's example is a JSON-RPC -32602 error, and the TypeScript SDK's v2 upgrade guide says unknown tool calls now reject with that error. The Python SDK's troubleshooting page describes the other shape: Unknown tool: <name> comes back as an isError result. Test what your SDK version does instead of assuming.

The specification also lists duties no SDK can perform for you. Servers must validate all tool inputs, enforce access controls, rate limit tool calls and sanitize outputs.

The stdout rule

A stdio server writes JSON-RPC to stdout, one message per line, and the specification forbids writing anything else there. A stray print() in Python or console.log() in Node corrupts the stream and the host reports a broken connection. Log to stderr instead (the Python logging module and console.error both do) and the host captures it. Over HTTP, stdout is free. Protocol-level log notifications are deprecated as of 2026-07-28 in favour of stderr and OpenTelemetry.

Run it over a transport

With stdio, the host starts your server as a subprocess, writes requests to its stdin and reads responses from its stdout, and shuts it down by closing stdin. Credentials come from the environment, for example the env key of the host's config entry. In Python, mcp.run(transport="stdio") does this. With Streamable HTTP, the server exposes one endpoint path such as /mcp; each client message is its own POST, and the reply is a JSON object or an event stream. A server must validate the Origin header to prevent DNS rebinding, should bind to 127.0.0.1 when run locally, and should authenticate connections. In Python, mcp.run(transport="streamable-http", host=..., port=...) serves it.

Test in layers, then connect

Test the plain logic first, then the protocol behaviour, then a real host. Python's Client(mcp) calls the server object in memory, and the Inspector shows the exact messages. Connecting a stdio server means adding an entry with a command and args to the host's config using absolute paths; a remote server needs only a URL. The worked example below does each step with real commands.

Worked example: A loan-calculator server: build it, break it, inspect it, connect it

We build a server with two tools for a fixed-rate loan, test it layer by layer and connect it to a host. It needs no network or API key. You need Python 3.10 or newer, uv, and Node.js 22.19 or newer for the Inspector. Create a project with uv init loan-server, cd loan-server and uv add "mcp[cli]".

At r=0r = 0r=0 the first formula divides by zero, so the code handles that case separately. Save this as loan_math.py; it has no MCP code, so it can be tested alone.

python
def payment_for(principal: float, annual_rate_percent: float, years: int) -> float:
    n = years * 12
    r = annual_rate_percent / 100 / 12
    if r == 0:
        return principal / n
    return principal * r / (1 - (1 + r) ** -n)


def balance_after(principal: float, annual_rate_percent: float, years: int, payments_made: int) -> float:
    n = years * 12
    r = annual_rate_percent / 100 / 12
    if r == 0:
        return principal * (1 - payments_made / n)
    growth = (1 + r) ** payments_made
    payment = payment_for(principal, annual_rate_percent, years)
    return max(0.0, principal * growth - payment * (growth - 1) / r)

Over 360 payments the borrower repays 431,676.38, of which 231,676.38 is interest. After 120 payments the balance B120B_{120}B120​ is 167,371.45, and a month-by-month loop (balance = balance * (1 + r) - P) gives the same figure. Check them in a unittest file with assertAlmostEqual(..., places=2), plus a zero-rate case such as payment_for(12000, 0, 1) equal to 1000.

2. The server

Save this as loan_server.py.

python
import logging
from typing import Annotated

from mcp.server import MCPServer
from mcp.server.mcpserver.exceptions import ToolError
from mcp.types import ToolAnnotations
from pydantic import Field

from loan_math import balance_after, payment_for

logging.basicConfig(level=logging.INFO)  # stderr by default: safe for stdio
logger = logging.getLogger(__name__)

mcp = MCPServer("loan-calculator")
READ_ONLY = ToolAnnotations(read_only_hint=True, open_world_hint=False)

Principal = Annotated[float, Field(gt=0, description="Amount borrowed, in any currency.")]
Rate = Annotated[float, Field(ge=0, le=100, description="Yearly interest rate in percent, e.g. 6 for 6%.")]
Years = Annotated[int, Field(ge=1, le=50, description="Loan term in whole years.")]


@mcp.tool(annotations=READ_ONLY)
def loan_payment(principal: Principal, annual_rate_percent: Rate, years: Years) -> str:
    """Monthly payment for a fixed-rate loan repaid in equal monthly payments."""
    n = years * 12
    pay = payment_for(principal, annual_rate_percent, years)
    logger.info("loan_payment principal=%s rate=%s years=%s", principal, annual_rate_percent, years)
    return (f"Monthly payment: {pay:,.2f} over {n} payments. "
            f"Total repaid: {pay * n:,.2f}; total interest: {pay * n - principal:,.2f}.")


@mcp.tool(annotations=READ_ONLY)
def remaining_balance(principal: Principal, annual_rate_percent: Rate, years: Years,
                      payments_made: Annotated[int, Field(ge=0, description="Monthly payments already made.")]) -> str:
    """Amount still owed after a number of monthly payments."""
    n = years * 12
    if payments_made > n:
        raise ToolError(f"payments_made is {payments_made}, but a {years}-year loan has only {n} payments. "
                        f"Use a value from 0 to {n}.")
    owed = balance_after(principal, annual_rate_percent, years, payments_made)
    return f"Balance after {payments_made} of {n} payments: {owed:,.2f}."


if __name__ == "__main__":
    mcp.run(transport="stdio")

The type hints and Field bounds become the input schema. The rule "payments cannot exceed the term" involves two arguments, so a per-argument schema cannot state it; it is raised as a ToolError that tells the model the valid range. Logging goes to stderr and nothing prints to stdout.

Add the server to the host's config using absolute paths. For Claude Desktop on macOS the file is ~/Library/Application Support/Claude/claude_desktop_config.json:

json

  "mcpServers": {

Quit and reopen the app completely. Ask the host for a 30-year, 200000 loan at 6 percent and the answer should quote 1,199.10.

Edge cases and limitations

A zero interest rate breaks the textbook payment formula
With a rate of 0 the payment formula divides by zero, because 1 - (1 + r)^-n is 0. The schema allows 0 (it is a valid rate), so the failure would surface as an unexpected exception. Handle the case in the pure function (principal divided by n) and add a unit test for it. Any tool whose maths has a singular input needs the same treatment, since a model will eventually send it.
The two SDKs differ on unexpected exceptions and unknown tools
In the Python SDK an exception other than ToolError or MCPError reaches the model only as the generic text "Error executing tool", with the traceback logged on the server. In the TypeScript SDK, anything a tool handler throws becomes an isError result whose text is the exception message. An unknown tool name differs as well: TypeScript sends a JSON-RPC error, while Python 2.3 returns an isError result. Test what the model actually sees for a forced failure, and never rely on exception text as a safe channel for internal details.
Per-argument schemas cannot express rules across arguments
"payments_made must not exceed years times 12" involves two arguments, and a JSON Schema on each property cannot state it. Check such rules in the handler and report them as a tool error that names the valid range, as the worked example does. A message that only says "invalid input" leaves the model to guess.
A host launches stdio servers with a different working directory and environment
A client may start your server from an undefined working directory (such as / on macOS) and passes it only a limited set of environment variables. Relative paths and variables set in your shell then fail only inside the host. Use absolute paths in the config, put needed variables under the entry's env key, and reproduce the failure by running the exact command from another directory.
Annotations and approval prompts are hints, not a security boundary
Tool annotations such as read_only_hint help clients decide when to ask the user, but the specification tells clients to treat them as untrusted unless the server is trusted, and the Python SDK docs say they are not security mechanisms. A server that must stay safe has to enforce limits itself: validate inputs, scope credentials, and expose only the tools the job needs.

When to use it, and when something simpler is enough

Use it when

  • You want one integration to work across several hosts, such as desktop chat apps, IDEs and coding agents, instead of writing a separate plugin for each.
  • The capability is a set of discrete operations a model can choose between, such as search, read and create, each with clear arguments and a result small enough to read.
  • You need the same tools locally for one user over stdio and as a hosted service for many users over Streamable HTTP with OAuth, from one codebase.

Think twice when

  • Only your own application calls the function, from code you control. Defining the function for your model provider's tool calling directly is simpler and has no extra process.
  • You would expose an unrestricted escape hatch, such as a tool that runs any SQL or shell command. Every prompt injection then becomes a tool call, and annotations will not stop it.
  • The tool itself must be the security boundary. Hosts and annotations help, but the server must enforce limits.

A simpler alternative. If a single application talks to a single model provider, plain tool calling with the same name, description and JSON Schema is simpler: you run the function inside your own agent loop. An MCP server pays off when a second client, a second team or a remote deployment appears.

Key takeaways

  • An MCP server is ordinary code behind an SDK: you declare tools with names, descriptions and input schemas, and the SDK publishes them, validates calls and speaks the protocol.
  • Failures travel on two channels: tool execution errors with isError true reach the model and should say how to fix the call, while protocol errors reach only the host.
  • A stdio server must never write to stdout, because that stream carries the protocol; log to stderr and keep secrets and stack traces out of error messages.
  • Test in layers: plain functions first, then an in-process SDK client, then the Inspector, then a real host, and use absolute paths in host config.
  • The tool list is a design decision, not a mirror of an API: real servers narrow it with toolsets, a few generic tools or read-only modes, and enforce safety on the server rather than trusting hints.

Example 1 of 5

GitHub MCP Server: one large API, narrowed by toolsets and a read-only switch

GitHubDocumented in an open-source project

The GitHub MCP Server is GitHub's own server for connecting AI tools to GitHub. Its repository README and contributing guide describe how it is run locally (a Docker image or a binary) or used as a server GitHub hosts, and how its tool list is configured. [17][18]

The problem

GitHub's API spans repositories, issues, pull requests, Actions, security findings, discussions, gists and more. Publishing every operation as a tool in every deployment would give the model a long list to choose from and would offer write operations where an operator only wants read access. The README gives the motivation itself: enabling only the toolsets you need can help the model with tool choice and reduce context size.

Where this topic fits

Tool selection happens at server startup, before any model call. The operator picks toolsets and optionally read-only mode, the server registers only the matching tools, and clients later see exactly that list through tools/list. It is the "declare tools" job of this lesson, made a deployment setting instead of a code change.

How it is applied, step by step

  1. The maintainers group related tools into named toolsets such as repos, issues, pull_requests and actions, instead of publishing one flat list.
  2. At launch the operator passes an allow-list through the `--toolsets` flag or the `GITHUB_TOOLSETS` environment variable. If nothing is given, a documented default set (context, repos, issues, pull_requests, users) applies.
  3. The server registers only the tools in the chosen toolsets, so the list the model reads is limited to what the job needs. A separate `--tools` flag can add individual tools to that set.
  4. Read-only mode removes every write tool and wins over any explicit request, so a tool named in `--tools` is still skipped if it writes.
  5. On the maintainer side, contributors regenerate the repository's tool snapshots with a documented command when a change affects them, and a renamed tool must keep its old name as an alias so existing configurations still work.

Why this approach fits

A server for a platform this size cannot be right for every user at once. Treating the tool list as configuration lets one codebase serve a reviewer who needs read access to issues and an automation that also opens pull requests, without maintaining two servers. A read-only switch is a cheap default for exploration, and tool-name aliases let the maintainers improve names without breaking existing setups.

Limitation or tradeoff

The selection is made when the server starts, so a task that needs a tool outside the chosen toolsets cannot be done until the operator reconfigures it. The README notes that an invalid tool name makes the server fail at startup, so a typo is caught early but also stops the server. Read-only mode limits what the tools can change; it does not stop the model from reading private data the token can reach.

What the sources document

  • The README describes the server as connecting AI tools to GitHub so agents can read repositories and code files, manage issues and pull requests, analyze code and automate workflows. [17]
  • Groups of functionality are enabled or disabled with the `--toolsets` flag or the `GITHUB_TOOLSETS` environment variable, and the README says enabling only the toolsets you need can help the LLM with tool choice and reduce context size. [17]
  • With no toolsets specified, the default set is context, repos, issues, pull_requests and users. [17]
  • Read-only mode (`--read-only`, or `GITHUB_READ_ONLY` under Docker) offers only read-only tools and takes priority: write tools are skipped even if explicitly requested through `--tools`. [17]
  • Contributors update snapshots with `UPDATE_TOOLSNAPS=true go test ./...`, a renamed tool needs a deprecation alias, and the README adds that tool names must match exactly and an invalid name makes the server fail at startup. [18][17]

The facts above come from the cited sources. The steps and analysis in this example are our explanation of how they fit together.

Example 2 of 5

Playwright MCP: returning a web page as an accessibility snapshot instead of pixels

Microsoft PlaywrightDocumented in an open-source project

Playwright MCP is a server from the Playwright project (the microsoft/playwright-mcp repository) that lets a model drive a real browser. Its README documents the design choice, the tool list and the options. [19]

The problem

A model that must operate a web page needs to know what is on it. Screenshot-based approaches need a vision-capable model and leave ambiguity about what to click, which the README names as the problem to avoid. The server has to decide what each tool returns, because the tool output is everything the model will know about the page.

Where this topic fits

This example is about the result side of a tool: what content the handler returns. The author chose a compact, structured text representation, then designed the action tools (click, type, navigate) to accept references taken from that representation.

How it is applied, step by step

  1. The server launches and controls a real browser through Playwright, with options for a persistent profile on disk or an isolated in-memory one.
  2. A snapshot tool returns the page's accessibility tree as text. According to the README this is better than a screenshot, and screenshots are offered but cannot be used to perform actions.
  3. Action tools such as click take a `target`, an exact element reference from the snapshot, plus an optional human-readable `element` description that the README says is used to obtain permission to interact with it.
  4. Each tool is flagged read-only or not in the README's tool reference, so a client can treat a snapshot differently from a click when it decides when to ask the user.
  5. The model reads the new snapshot after each action and decides the next step, which is the agent loop running through the server.

Why this approach fits

The tool result is the model's only view of the page, so its format decides how reliably the model can act. A structured tree gives names and roles the model can refer to exactly, needs no vision model, and keeps the link between "what I saw" and "what I clicked" explicit through references. The same principle applies to any server: design results for a reader that has nothing else to go on.

Limitation or tradeoff

The README itself weighs the cost: it says command-line workflows can be more token-efficient for coding agents because they avoid loading large tool schemas and verbose accessibility trees, and it keeps the MCP form for loops that benefit from persistent state. Stripe MCP: a hosted server with a few generic tools and human confirmation for risky writes

The problem

Stripe's API has a very large number of methods for payments, billing, invoices, tax, payouts and more. One tool per method would flood the model's context. Some of those methods move money, so the server also needs identity, scoped credentials and a way for a person to approve actions that an agent proposes.

Where this topic fits

This is a remote server, reached by URL over HTTP, whose author made two design choices described in this lesson: keep the tool list short with generic tools, and put the dangerous operations behind a confirmation step that the server itself enforces rather than relying on the client.

How it is applied, step by step

  1. Stripe hosts the server and publishes one URL, so users register a URL in their client instead of installing a package. Clients authenticate with OAuth, or with an agent API key as a bearer token for autonomous use.
  2. In a typical flow the model first uses a search tool to find an API method by keyword and a details tool to read its parameters.
  3. It then calls a generic read tool (for GET methods) or a generic write tool (for POST, PATCH, PUT and DELETE methods) with that method and its parameters.
  4. For certain writes, such as refunds and outbound payments, the server asks for human confirmation: the person opens a URL from the agent, approves, and Stripe returns an approval token.
  5. The person must then tell the agent to retry; the retried call needs no further confirmation, and an unapproved request expires after 24 hours.
  6. Administrators control access in the Dashboard: they can enable or disable MCP access for the team and review or revoke OAuth sessions.

Why this approach fits

Four generic API tools keep that part of the tool list small and stable while the API grows, because the search and details tools supply the detail on demand. Enforcing approval on the server means every client gets the same protection, including clients with weak approval prompts. Separate OAuth and agent-key paths match the two real situations: a person at a keyboard, and an unattended agent.

Limitation or tradeoff

Generic tools move work onto the model: it must find the right method, read the parameters and compose a valid call, which takes several round trips and puts more weight on the API's own validation than on a per-tool schema. 4Common mistakes

  1. Printing to stdout from a stdio server

    Why it causes problems
    On the stdio transport, stdout carries the protocol and the specification forbids anything but valid MCP messages there. A stray print() or console.log() breaks the parsing of the message stream, so the host drops the connection or shows the server as failed, often seconds after startup.
    How to recognise it
    The same code works when you start it by hand but the host or the Inspector reports a connection or parse error. Search the code for print( and console.log( and read the host's log file for the server.
    How to fix it
    Send all logging to stderr with the logging module in Python or console.error in Node, and keep stdout for the SDK. Check the connection with the Inspector before trying a host.

  2. Reporting failures as ordinary text, or letting raw exceptions through

    Why it causes problems
    A failure returned with isError false looks like a success, so the model carries on with wrong data. A bare exception gives the model either a generic message or, in some SDKs, internal details, and neither helps it correct the call.
    How to recognise it
    In the Inspector a failed call shows isError false, or the text says only "Error executing tool". Force a failure for each tool and read exactly what comes back, including the CLI exit code (5 means isError).
    How to fix it
    Raise ToolError in Python or return isError true in TypeScript, with a message that says what was wrong and what to try next, such as the valid range. Log the details to stderr and keep secrets out of the message.

  3. Mirroring a whole REST API as one tool per endpoint

    Why it causes problems
    A long list of near-duplicate tools costs context on every request and makes the model more likely to pick the wrong one. GitHub's README says enabling only the needed toolsets helps tool choice and reduces context size.
    How to recognise it
    The tool list has dozens of entries with overlapping descriptions, and traces show the model calling a neighbouring tool or asking for a tool that exists under another name.
    How to fix it
    Design around tasks. Group tools into toolsets or skills that operators can enable, publish a few generic tools with a search step for very large APIs as Stripe does, and offer a read-only mode so write tools are opt-in.

  4. Using relative paths or shell habits in the host config

    Why it causes problems
    A host may start a stdio server from an undefined working directory and with only a limited set of environment variables, so a relative script path, a bare command or a variable set in your shell fails only inside the host and the server never appears.
    How to recognise it
    The server works from your terminal but is missing in the host. The host's MCP log files (for Claude Desktop, mcp*.log under ~/Library/Logs/Claude) show a file-not-found or import error, and the config contains paths that start with ./ or a bare command.
    How to fix it
    Use absolute paths, give the full path of the launcher (the output of which uv or which node), set needed variables under the entry's env key, and fully quit and reopen the host after every config or code change.

  5. Copying SDK code from an older tutorial

    Why it causes problems
    The Python SDK renamed FastMCP to MCPServer in v2 and moved imports, so old code fails at import. Behaviour such as how exceptions become results also differs between versions, so code that appears to run can still behave differently.
    How to recognise it
    You see ModuleNotFoundError for mcp.server.fastmcp, or the tutorial's imports and class names do not match the current quickstart. Check the SDK version your lockfile resolved.
    How to fix it
    Start from the current official quickstart for your language, pin the SDK version, and use the SDK's migration guide to translate any older example line by line.

  6. Relying on annotations or the client's approval prompt to keep a tool safe

    Why it causes problems
    The specification tells clients to treat tool annotations as untrusted unless the server is trusted, and Playwright's README says it is not a security boundary. A powerful tool protected only by a hint or a prompt can be called with harmful arguments, for example after a prompt injection.
    How to recognise it
    A tool can delete, send or spend, and the only protection is its description or a readOnlyHint, with no scoped credential, input validation or server-side confirmation.
    How to fix it
    Enforce limits on the server: validate inputs, use the least-privileged credential, offer read-only modes, and require confirmation for dangerous actions on the server side, as Stripe does for refunds.

Build, test and inspect a unit-converter server

CodingIntermediateAbout 50 min (estimate)Hypothetical scenario

Build an MCP server named unit-converter with one tool, convert, using the Python SDK. It needs no network and no API key. You need Python 3.10 or newer, uv and Node.js 22.19 or newer (for the Inspector). Use these exact sizes:

UnitKindSize
mlength1 metre
kmlength1000 metres
milength1609.344 metres
ftlength0.3048 metres
kgmass1 kilogram
lbmass0.45359237 kilograms

The tool takes value (a number), from_unit and to_unit, and returns one line such as 10 km = 6.21371 mi, formatted as f"{value:g} {from_unit} = {result:.6g} {to_unit}". Converting between kinds, for example km to kg, is a rule that a per-argument schema cannot express.

Requirements

  • Put the arithmetic in a module with no MCP imports and cover it with unittest tests.
  • Type from_unit and to_unit as a Literal of the six units so the published schema contains an enum.
  • Raise ToolError for a cross-kind conversion, with a message that names both kinds and lists the valid units.
  • Send all logging to stderr and print nothing to stdout.
  • Add an in-process test with the SDK's Client that asserts is_error for km to kg.
  • Check one good call and one cross-kind call with the Inspector CLI and note the exit codes.

Expected behaviour

convert(10, "km", "mi") returns 10 km = 6.21371 mi, convert(5, "lb", "kg") returns 5 lb = 2.26796 kg and convert(100, "ft", "m") returns 100 ft = 30.48 m. convert(1, "km", "kg") returns a result with isError true and the text Error executing tool convert: Cannot convert km (length) to kg (mass). Choose a length unit instead: m, km, mi, ft. (the Python SDK adds the tool-name prefix). Listing the tools shows from_unit and to_unit as enums of six values. The Inspector CLI exits 0 for the good call and 5 for the cross-kind call.

Hint 1

Keep one dictionary per kind that maps each unit to its size in the base unit, and convert through the base unit with value * table[from_unit] / table[to_unit].

Hint 2

Raise ValueError in the pure function and translate it into ToolError inside the tool, so the logic stays free of MCP imports and easy to unit test.

Hint 3

For the in-process test, follow the SDK testing page: open `async with Client(mcp, raise_exceptions=True) as client` and call `await client.call_tool("convert", {...})`. Install pytest with `uv add --dev pytest`.

Hint 4

Run the Inspector CLI from the project folder, for example `npx @modelcontextprotocol/inspector --cli uv run converter_server.py --method tools/call --tool-name convert --tool-arg value=1 --tool-arg from_unit=km --tool-arg to_unit=kg`, and read the exit code with `echo $?`.

Show solution

Pure logic in converter.py:

python
LENGTH_IN_METRES = {"m": 1.0, "km": 1000.0, "mi": 1609.344, "ft": 0.3048}
MASS_IN_KILOGRAMS = {"kg": 1.0, "lb": 0.45359237}
KINDS = {"length": LENGTH_IN_METRES, "mass": MASS_IN_KILOGRAMS}


def kind_of(unit: str) -> str:
    for kind, table in KINDS.items():
        if unit in table:
            return kind
    raise ValueError(f"Unknown unit {unit!r}.")


def convert_value(value: float, from_unit: str, to_unit: str) -> float:
    from_kind, to_kind = kind_of(from_unit), kind_of(to_unit)
    if from_kind != to_kind:
        options = ", ".join(KINDS[from_kind])
        raise ValueError(
            f"Cannot convert {from_unit} ({from_kind}) to {to_unit} ({to_kind}). "
            f"Choose a {from_kind} unit instead: {options}."
        )
    table = KINDS[from_kind]
    return value * table[from_unit] / table[to_unit]


def describe(value: float, from_unit: str, to_unit: str) -> str:
    result = convert_value(value, from_unit, to_unit)
    return f"{value:g} {from_unit} = {result:.6g} {to_unit}"

The server in converter_server.py:

python
import logging
from typing import Literal

from mcp.server import MCPServer
from mcp.server.mcpserver.exceptions import ToolError
from mcp.types import ToolAnnotations

from converter import describe

logging.basicConfig(level=logging.INFO)  # stderr, never stdout
logger = logging.getLogger(__name__)

mcp = MCPServer("unit-converter")
Unit = Literal["m", "km", "mi", "ft", "kg", "lb"]


@mcp.tool(annotations=ToolAnnotations(read_only_hint=True, open_world_hint=False))
def convert(value: float, from_unit: Unit, to_unit: Unit) -> str:
    """Convert a length (m, km, mi, ft) or a mass (kg, lb) from one unit to another."""
    try:
        return describe(value, from_unit, to_unit)
    except ValueError as error:
        logger.info("rejected conversion: %s", error)
        raise ToolError(str(error)) from error


if __name__ == "__main__":
    mcp.run(transport="stdio")

A safer tool surface:

python
from typing import Annotated, Literal

from mcp.server import MCPServer
from mcp.server.mcpserver.exceptions import ToolError
from mcp.types import ToolAnnotations
from pydantic import Field

mcp = MCPServer("orders")
READ_ONLY = ToolAnnotations(read_only_hint=True, open_world_hint=False)


@mcp.tool(annotations=READ_ONLY)
def get_order(order_id: Annotated[int, Field(ge=1)]) -> str:
    """Fetch one order by id."""
    row = find_order(order_id)  # parameterised query on a read-only connection
    if row is None:
        raise ToolError(f"No order with id {order_id}. Use list_orders to find valid ids.")
    return row


@mcp.tool(annotations=READ_ONLY)
def list_orders(status: Literal["open", "shipped", "cancelled"],
                limit: Annotated[int, Field(ge=1, le=50)] = 20) -> str:
    """List recent orders with a given status."""
    return format_orders(query_orders(status, limit))

find_order, query_orders and format_orders stand for your own data-access code, which must use parameterised queries. Cancelling or deleting orders, if needed at all, should be a separate tool that takes one order_id, checks the caller's permissions on the server, and asks for confirmation on the server side, the way Stripe's hosted server does for refunds.
