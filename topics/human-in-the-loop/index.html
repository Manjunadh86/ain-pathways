Human-in-the-Loop

Human-in-the-loop is a design in which an AI agent pauses at defined points so that a person can approve, edit, reject or take over what it is about to do. The run then continues from saved state with that decision recorded.

1Overview

Why it matters

An agent loop will execute whatever tool call the model produces. That is acceptable for a search and unacceptable for a refund, an email to a customer, a production deploy or a recursive delete. Models make mistakes, and tool results can carry instructions planted by someone else (see Prompt Injection and LLM Security). A human checkpoint at the right step is often the only control that knows enough about the business to say no. The Model Context Protocol specification (opens in a new tab) says there should always be a human in the loop with the ability to deny tool invocations.

The hard part is engineering, not principle. A reviewer may answer in two seconds or two days, so the run has to stop without losing its work and restart without repeating it. A gate that fires on every action trains people to click yes without reading. A reviewer who sees a summary instead of the real arguments approves something other than what runs. Anyone who gives an agent a tool that writes, sends, pays or deletes needs to design these parts deliberately, and so does anyone who staffs the queue where the requests land.

Key terms

Human-in-the-loop (HITL)
A system design in which a person must make or confirm certain decisions before an automated process continues.
Approval gate
A check in the agent's code that stops a proposed action until a person, or a rule acting for one, allows it.
Policy
The rules that sort each proposed tool call into allow, ask or deny, usually by tool name and arguments.
Interrupt
A deliberate pause in a run that hands a question or a pending action to someone outside the agent and waits for the answer.
Checkpoint
A saved copy of a run's state from which the run can continue later, possibly in a different process.
Decision
The reviewer's answer to a pending action, commonly approve, edit or reject, with a reason attached to a rejection.
Escalation
Handing a task or conversation from the agent to a person because the agent cannot or should not continue alone.
Review queue
The place where pending approvals and escalations wait for people, such as an inbox, a ticket list or a set of open pull requests.
Approval fatigue
The loss of attention caused by too many approval prompts, which leads people to approve without reading.
Idempotent
An operation that has the same effect whether it runs once or several times.

2Explanation

Introduction

In The Agent Loop you saw that the model never executes anything. It emits a request, and your program decides whether and how to run it. Human-in-the-loop (HITL) uses that gap: before certain requests run, the program stops and asks a person.

Offices already work this way. A junior accountant can prepare any payment, but a payment above a set amount needs a manager's signature. A developer can write any change, but it reaches the main branch only after a colleague approves the pull request. In both cases most work flows without interruption, a small class of consequential actions waits for a second person, and that person can sign, send it back with corrections, or refuse.

An agent needs the same arrangement, built from five parts:

  • A gate. A rule in code, called a policy, sorts every proposed tool call into allow, ask or deny.
  • An interrupt with resumable state. When the answer is ask, the run pauses. Its state is saved so that it can continue minutes or days later, even in another process.
  • A decision. The reviewer approves the action, edits its arguments, or rejects it with a reason the model can read.
  • Escalation. When the agent is stuck, unsure or out of its depth, it hands the whole task to a person together with what it has learned.
  • A review queue. Requests that nobody is waiting for in a chat window sit in an inbox, a ticket list or a list of pull requests, and somebody needs the time to clear it.

The person does not always stand in the same place. They can approve an action before it runs, review the result afterwards while it is still reversible, or only watch and step in when something looks wrong. This lesson covers how to choose between those positions, how pausing and resuming work in current frameworks, how to let reviewers edit proposals safely, when to escalate, and how to keep a review queue from turning into a rubber stamp.

How it works

Where the gate sits

The gate is one branch added between the reason and act stages of the loop. The block below is pseudocode; the worked example is runnable.

python
call = model(context)                      # the model proposes a tool call
verdict = policy(call.name, call.args)     # allow, ask or deny
if verdict == "deny":
    result = "Blocked by policy"           # goes back to the model as an observation
elif verdict == "ask":
    save(run_id, context, pending=call)    # checkpoint, then stop
    return Paused(run_id, call)
else:
    result = run_tool(call)

Two rules make the gate trustworthy. First, it lives in code. A system prompt that says "ask before deleting" is a request to the model, and a confused or manipulated model will not honour it. The Claude Agent SDK's documentation shows the pattern: when Claude requests a tool, the SDK checks permissions in a fixed order (opens in a new tab) (hooks, deny rules, ask rules, the permission mode, allow rules, then your approval callback) before anything runs. Second, the restrictive answer wins. Deny rules are checked before ask rules and allow rules, and a matching deny rule blocks the call in every mode, so a narrow allow rule cannot carve an exception out of a broad deny rule (see Claude Code permissions (opens in a new tab)).

Frameworks expose the same branch under different names: needs_approval on a tool in the OpenAI Agents SDK (opens in a new tab), interrupt_on in LangChain's human-in-the-loop middleware (opens in a new tab), and a canUseTool callback in the Claude Agent SDK (opens in a new tab).

Products also let the person choose where the gate sits. In Claude Code's Manual mode, edits and shell commands outside a small read-only set ask first; in its auto mode a classifier model reviews actions in place of the person (permission modes (opens in a new tab)).

Deciding what to gate

Gate by consequence. Three questions sort most actions: can it be undone, does its effect leave your system, and how much could it cost?

The verdict often depends on the arguments, because refunding 20 USD and refunding 2,000 USD are the same tool. The OpenAI Agents SDK therefore accepts a function for needs_approval that receives the parsed arguments. Its documentation adds that the rule fails closed: when the arguments cannot be parsed safely, the call requires manual approval. LangChain's middleware offers the same with a when predicate on a tool's interrupt_on entry (langchain 1.3.3 or later).

Interrupts and resumable state

A reviewer may take days, and no server process should be kept waiting that long. A pause is therefore save and stop, and a resume is load and continue:

  1. Save everything the run needs: the message history, the pending call (tool name, arguments, call ID) and the decisions already made.
  2. Return the pending request to the caller with an identifier for the saved state.
  3. When a decision arrives with that identifier, load the state, apply the decision and re-enter the loop.

In LangGraph (opens in a new tab), calling interrupt(payload) inside a node saves the graph state through a checkpointer under a thread_id and surfaces the payload to the caller. Invoking the graph again with Command(resume=value) and the same thread_id continues the run, and value becomes the return value of interrupt(). The OpenAI Agents SDK returns a result whose interruptions list holds the pending approvals. result.to_state() gives a RunState that can be stored with to_string(), restored with RunState.from_string(), marked with state.approve(...) or state.reject(...) and passed back to Runner.run. Amazon Bedrock Agents (opens in a new tab) return an invocationId with the action awaiting confirmation, and the application sends the user's CONFIRM or DENY back as the confirmationState of the result, in the session state of its next request. The Claude Agent SDK's approval callback (opens in a new tab) can stay pending indefinitely, so for slow reviewers its documentation points to a PreToolUse hook that returns a defer decision, which lets the process exit and resume later from the persisted session.

Resuming has a trap. LangGraph restarts the interrupted node from its first line; it does not continue from the line where interrupt() was called. Code before the interrupt runs again, so a record created there is created twice. Put side effects after the interrupt, or make them idempotent. Durable Execution and Long-Running Agents covers the persistence layer in depth.

What the reviewer can decide

DecisionEffect on the pending callWhat the model sees next
ApproveRuns with the proposed argumentsThe real tool result
EditRuns with arguments the reviewer changedThe result of the edited call
RejectDoes not runThe reviewer's reason, as the observation
RespondDoes not runThe reviewer's answer, when the "tool" was really a question

These are the four decision types of LangChain's middleware. The Claude Agent SDK expresses the first three as allow, optionally with an updated input, and deny with a message.

Editing is the most useful decision and the most delicate. The reviewer fixes a recipient or lowers an amount without sending the agent back to redo its work. But the model proposed one thing and something else happened. LangChain's documentation warns that significant edits may cause the model to re-evaluate its approach and call the tool again, and the Claude Agent SDK notes that Claude sees the result but is not told that the input was changed. So keep edits small, check the edited arguments with the same policy as the original, and say in the tool result that a reviewer changed them.

A rejection needs a reason. "Rejected" alone invites the model to try the same call again. "Rejected: the order is outside the 30-day window, offer store credit" gives it somewhere to go.

Escalation

Approval answers a yes-or-no question about one action. Escalation hands over the problem. Good triggers are specific, and checked in code where possible:

  • The model asks. Give the agent a tool for questions. In the Claude Agent SDK, AskUserQuestion arrives at the same callback as approval requests.
  • The user asks for a person.
  • The agent is stuck. The same failure repeats, or an automated reviewer keeps blocking it. In Claude Code's auto mode, where a classifier model reviews actions in place of the user, Anthropic describes stopping the model and escalating to the human (opens in a new tab) after 3 consecutive denials or 20 in total in a session. A headless run has nobody to ask. The March 2026 post says it is terminated, but the permission modes documentation (opens in a new tab) now says the blocked action does not run and Claude keeps working, so decide that case yourself.
  • The topic is reserved for people, such as a legal threat or a safety issue.

An escalation is only as good as its handoff. The person needs the conversation so far, what the agent tried, the data it gathered and why it stopped. Otherwise the user has to repeat everything.

Review queues

When the reviewer is not the person talking to the agent, pending items wait in a queue. Each item should stand alone: the exact tool and arguments, why the agent proposed it, the evidence, the allowed decisions and a deadline.

A queue has a capacity. If the agent proposes NNN actions an hour, the policy sends a share ppp of them to review, and ccc reviewers each decide μ\muμ items an hour, the backlog after ttt hours is

B(t)=max⁡(0,  (pN−cμ) t)B(t) = \max\bigl(0,\; (pN - c\mu)\,t\bigr)B(t)=max(0,(pN−cμ)t)

With N=40N = 40N=40, one reviewer and μ=12\mu = 12μ=12 (five minutes per item), a 20% share keeps up, a 40% share leaves 32 items waiting after eight hours, and a 60% share leaves 96. Real arrivals come in bursts, so real waits are longer than this steady-rate estimate.

Overload has a second cost. Anthropic's engineers describe approval fatigue (opens in a new tab): people who are asked constantly may stop paying close attention to what they approve, and they report that sandboxing cut permission prompts by 84% in their internal use. Their post on Claude Code's auto mode (opens in a new tab) reports that users approve 93% of permission prompts, and it says the classifier that replaces some of them is not a drop-in replacement for careful human review on high-stakes infrastructure. Spend human attention where it changes outcomes: keep the ask tier narrow, pre-approve safe patterns, contain what you can in a sandbox (see Code Execution and Sandboxing), and audit a random sample of what ran without review.

Securing the approval path

The approval channel is an attack surface. The OpenAI Agents SDK documentation gives the rules for a web or mobile approval screen: keep the saved run on the server, send the reviewer only the details they may see plus an opaque identifier, take the reviewer's identity from the authenticated session and never from the request body, apply the decision to the server's copy of the pending call, and make sure one saved run cannot be resumed twice.

Worked example: A refund approval gate that pauses, survives a restart and resumes with an edited amount

The task: a support agent must refund a damaged item in order A-1001, which cost 120.00. Refunds above 50.00 need a person, and a refund larger than the order total is never allowed. As in The Agent Loop, a scripted function stands in for the model so that everyone gets the same output. Everything else is real: the policy, the pause, the serialised state and the resume.

Save this as approval_gate.py. It needs only the Python standard library (3.9 or later).

python
import json

ORDERS = {"A-1001": {"total": 120.00, "status": "delivered"}}
APPROVAL_LIMIT = 50.00
LEDGER = []  # stands in for the payment system: the only side effect in this file


def lookup_order(order_id):
    return json.dumps(ORDERS[order_id])


def issue_refund(order_id, amount):
    LEDGER.append((order_id, amount))
    return f"refunded {amount:.2f} on {order_id}"


TOOLS = {"lookup_order": lookup_order, "issue_refund": issue_refund}


def policy(name, args):
    """Classify one proposed tool call as allow, ask or deny."""
    if name == "lookup_order":
        return "allow"                                   # read-only
    if name == "issue_refund":
        if args["amount"] > ORDERS[args["order_id"]]["total"]:
            return "deny"                                # never valid
        return "ask" if args["amount"] > APPROVAL_LIMIT else "allow"
    return "deny"                                        # unknown tools are blocked


def run(state, model):
    """Advance the loop until it finishes or needs a person. state is JSON-serialisable."""
    while True:
        reply = model(state["messages"])
        if "final" in reply:
            return {**state, "status": "finished", "answer": reply["final"]}
        call = reply["call"]
        verdict = policy(call["name"], call["args"])
        if verdict == "ask":                             # interrupt: nothing has run yet
            return {**state, "status": "paused", "pending": call}
        result = TOOLS[call["name"]](**call["args"]) if verdict == "allow" else "DENIED by policy"
        state = {**state, "messages": [*state["messages"], {"call": call}, {"result": result}]}


def resume(state, decision, model):
    """Apply a reviewer's decision to the pending call, then continue the loop."""
    call = state["pending"]
    if decision["type"] == "reject":
        result = f"REJECTED by reviewer: {decision['reason']}"
    elif decision["type"] == "edit":
        call = {**call, "args": {**call["args"], **decision["args"]}}
        result = TOOLS[call["name"]](**call["args"]) + " (arguments edited by reviewer)"
    else:                                                # approve
        result = TOOLS[call["name"]](**call["args"])
    messages = [*state["messages"], {"call": call}, {"result": result}]
    return run({"messages": messages, "status": "running"}, model)


def scripted_model(messages):
    """Stands in for an LLM: decides from the tool results seen so far."""
    results = [m["result"] for m in messages if "result" in m]
    if len(results) == 0:
        return {"call": {"name": "lookup_order", "args": {"order_id": "A-1001"}}}
    if len(results) == 1:
        return {"call": {"name": "issue_refund", "args": {"order_id": "A-1001", "amount": 120.00}}}
    return {"final": f"Outcome: {results[-1]}"}


if __name__ == "__main__":
    print([policy("issue_refund", {"order_id": "A-1001", "amount": a}) for a in (30, 120, 500)])

    task = {"messages": [{"user": "Refund the damaged item in order A-1001."}], "status": "running"}
    paused = run(task, scripted_model)
    saved = json.dumps(paused)        # this string can sit in a database for days
    print(paused["status"], paused["pending"], "| refunds so far:", len(LEDGER))

    restored = json.loads(saved)      # later, possibly in a different process
    done = resume(restored, {"type": "edit", "args": {"amount": 80.00}}, scripted_model)
    print(done["status"], "|", done["answer"], "|", LEDGER)

    again = resume(json.loads(saved), {"type": "reject", "reason": "photo shows no damage"}, scripted_model)
    print(again["status"], "|", again["answer"], "|", LEDGER)

Run python3 approval_gate.py. It prints:

text
['allow', 'ask', 'deny']
paused {'name': 'issue_refund', 'args': {'order_id': 'A-1001', 'amount': 120.0}} | refunds so far: 0
finished | Outcome: refunded 80.00 on A-1001 (arguments edited by reviewer) | [('A-1001', 80.0)]
finished | Outcome: REJECTED by reviewer: photo shows no damage | [('A-1001', 80.0)]

What to notice:

  • Line 1, the policy. One tool gets three verdicts depending on its arguments: 30.00 is under the limit, 120.00 needs a person, and 500.00 exceeds the order total.
  • Line 2, the pause. lookup_order ran without asking. issue_refund did not run, so the ledger is empty. run returned plain data and json.dumps turned it into a string. Nothing about the paused run lives in process memory, which is what lets the reviewer answer after a deploy or a crash.
  • Line 3, resume with an edit. The reviewer lowered the amount to 80.00. The tool ran once with the edited argument, the observation says that a reviewer changed it, and the final answer reports 80.00, not the 120.00 the model proposed.
  • Line 4, a rejection and a warning. The reason became the observation, and the ledger still holds one refund. But this line resumed the same saved state a second time, and the code allowed it. Had the second decision been an approval, the customer would have been refunded twice. A real system must consume each pending request exactly once.

The edit path has a second gap: nothing stops a reviewer from typing 500.00, because edited arguments skip the policy. The first exercise closes both gaps.

Edge cases and limitations

Code before the pause runs again on resume
LangGraph's documentation states that a resumed node restarts from its beginning, not from the line where interrupt was called, and that a parent node and a subgraph node both restart when the interrupt is inside a subgraph. Anything before the interrupt therefore executes at least twice. A notification sent or a row inserted there is duplicated on every resume. Move side effects after the interrupt, put them in a separate node, or use operations that are safe to repeat, such as an upsert in place of an insert.
The world changed while the request was waiting
An approval given on Thursday applies to a proposal made on Monday. The order may have been cancelled, the price may have moved, or the agent's tools may have been redeployed. Re-run the policy and any cheap validation at resume time, give each pending request an expiry after which it must be proposed again, and store a version marker with the saved state. The OpenAI Agents SDK documentation recommends such a marker so that old state is deserialised by matching code when models, prompts or tool definitions change.
One saved state is resumed twice
Two reviewers click approve at the same moment, or a client retries a request that timed out. If both resumes load the same snapshot, the pending action can run twice; the last line of the worked example shows one snapshot being resumed a second time. Mark the pending request as consumed in the same atomic operation that starts the resume, and reject any later decision for it. The OpenAI Agents SDK documentation asks for exactly this so that concurrent or replayed submissions cannot resume the same snapshot twice.
An auto-approval rule silently bypasses the gate
In the Claude Agent SDK the approval callback is the last step of permission evaluation. The documentation warns that the callback never fires for a tool that an allow rule or a permissive mode has already approved, so checks written there are skipped for that tool. The same shape exists in any layered system. Put a check that must see every call in the earliest layer (a pre-tool hook in that SDK), and test the gate with the production configuration, not a default one.
Several calls are pending at once
A model can propose more than one gated call in a turn. LangChain's middleware requires one decision per pending action, supplied in the same order as the actions appear in the interrupt. The OpenAI Agents SDK lets a reviewer resolve some interruptions and rerun; the unresolved ones pause the run again. Show the calls together, because approving a transfer makes little sense without seeing the email that announces it. Where decisions are matched by position, build the decision list in code from the pending list so that the order cannot drift.
Nobody answers
Frameworks wait as long as you let them: LangGraph's documentation says a graph waits indefinitely after an interrupt, and the Claude Agent SDK's approval callback can stay pending indefinitely. A queue item with no owner blocks its task for ever. Decide in advance what a timeout means for each kind of action. For irreversible actions the safe default is to treat silence as a rejection and tell the requester; for time-critical ones, route the item to a second reviewer before the deadline.

When to use it, and when something simpler is enough

Use it when

  • The action has an effect outside your system that cannot be undone, such as moving money, sending a message to a customer, deleting data or deploying to production.
  • The agent reads content you do not control (web pages, emails, tickets, tool results) and also has tools that could leak data or cause damage if that content redirected it.
  • The agent is new and you have no evidence yet of how often it is wrong; approvals lower the stakes while you collect that evidence, and can be relaxed for the patterns that prove safe.
  • A person with the authority and the information to judge the action can respond within the time the task can wait.
  • Policy, contract or regulation requires that a named person authorises this class of decision.

Think twice when

  • The action is read-only or easily reversed inside a sandbox. Prompts here cost attention and teach reviewers to approve without reading.
  • Volume exceeds what reviewers can decide. A gate that sends more items than the queue can clear produces either a growing backlog or rubber-stamping; narrow the gate or sample instead.
  • The reviewer cannot evaluate what they are shown, for example a 4,000-line generated diff or a query in a language they do not read. That is the appearance of oversight, not the substance.
  • The task needs a response in seconds and no person is on hand. Use hard limits in the tool instead.

A simpler alternative. Remove the risk instead of supervising it. Give the agent read-only tools, enforce limits inside the tool (a refund tool that cannot exceed the order total), run it in a sandbox with no network access, or deny the dangerous pattern outright. These controls need no reviewer and never tire. They stop being enough when the task itself requires an irreversible action whose correctness depends on judgement, such as deciding whether this customer should get this refund.

Key takeaways

  • A human-in-the-loop gate is a branch in your code that sorts each proposed tool call into allow, ask or deny; it must be enforced by the program, because a prompt instruction can be ignored.
  • Gate by consequence: let read-only and reversible actions run, ask before irreversible or external ones, and deny what should never happen.
  • A pause is save-and-stop and a resume is load-and-continue, so the saved state must be serialisable, each pending request must be consumed once, and code that runs before the pause must be safe to repeat.
  • Reviewers need more than yes and no: an edit fixes a proposal without redoing the work, and a rejection must carry a reason that goes back to the model as an observation.
  • Escalation hands over the whole task with its context, and it should be triggered by specific signals such as a user request, repeated failure or a reserved topic.
  • Human attention is the scarce resource: size the review queue against reviewer capacity, keep the ask tier narrow, and audit samples of what ran without review.

Example 1 of 5

Claude Code asking before shell commands and file edits on a developer's machine

AnthropicDocumented in official docs

Claude Code is Anthropic's coding agent. It runs in a developer's terminal, editor or desktop app with access to the developer's files and shell. Its security and permissions documentation describe Manual mode, where it asks before acting. From Claude Code v2.1.283, interactive terminal and VS Code sessions start in auto mode instead, where a classifier model reviews actions in place of the developer. Anthropic's engineering posts report how people respond to approval prompts and when the classifier hands back to a person. [7][9][8][10][11]

The problem

A coding agent proposes shell commands and file edits on a machine that holds the developer's source code, credentials and git remotes. One wrong or manipulated command can destroy uncommitted work or push code where it should not go. Asking about every action is not a solution either: Anthropic's engineering post on sandboxing says that constantly clicking approve slows down development cycles and can lead to approval fatigue, where users might not pay close attention to what they approve. The auto mode post puts a number on it: users approve 93% of permission prompts.

Where this topic fits

The gate sits between the model's tool call and its execution, and the reviewer is the developer in the session. The permissions documentation says rules are evaluated in the order deny, ask, allow and the first match decides, while the permission mode sets the baseline for calls no rule settles. In Manual mode the prompt shows what Claude is about to do and lets the developer approve once, approve and stop being asked about that kind of call, or decline. In auto mode a classifier model makes those calls instead, explicit ask and deny rules still apply, and repeated blocks send the decision back to the person.

How it is applied, step by step

  1. File reads and searches inside the working directory run without a prompt, because the documentation classes read-only tools as needing no approval there. A built-in set of read-only shell commands such as ls, cat and git status also runs without asking.
  2. In Manual mode (config value default), other shell commands and file edits stop at a permission prompt that shows what Claude is about to do. Commands that match no rule require approval by default.
  3. The developer approves once, approves and chooses not to be asked again for that kind of call, or declines.
  4. Choosing not to be asked again for a shell command saves a permission for that repository and command, so later matching commands skip the prompt. An approval for file edits lasts only until the session ends.
  5. A declined call does not run. On a No answer the developer can attach a comment, and the documentation says Claude Code sends it to Claude as the reason for the denial, so the model has something to adjust to instead of repeating the call.
  6. Teams move routine commands out of the ask tier by allowlisting them per user, codebase or organisation, and block dangerous patterns with deny rules, which are checked first and block in every permission mode.
  7. In auto mode a classifier model reviews actions in place of the developer, and explicit ask and deny rules still apply. After 3 consecutive denials or 20 in total in a session, Anthropic's post says it stops the model and escalates to the person; the current documentation words this as auto mode pausing and Claude Code resuming prompts.

Why this approach fits

The developer is present, knows the repository and can judge a command in seconds, so asking at the moment of action is cheap and well informed. The tiers follow risk: reading is free, edits are approved per session, and shell commands are approved per pattern. Saved rules mean each kind of safe command is judged once instead of every time, which keeps attention for the unusual ones. Because the program enforces the rules, an instruction injected through a file or a web page cannot talk its way past a deny rule.

Limitation or tradeoff

Prompts wear people down: Anthropic reports that users approve 93% of them and says this leads to approval fatigue. Auto mode answers that by letting a classifier decide, but the same post reports a 17% false-negative rate for the full classifier pipeline on 52 real overeager actions, a small set, and says auto mode is not a drop-in replacement for careful human review on high-stakes infrastructure. Rules are patterns over command text, and a deny rule matches the command as written, so a command phrased another way can slip past it; the security page points to sandbox network isolation for enforcement that does not depend on the command text. Each rule needs testing against the commands the agent really produces.

What the sources document

  • The permissions page tabulates approval by tool type in Manual mode. Read-only tools need no approval inside the working directories, Bash commands and file modifications do, and a don't-ask-again answer is kept permanently per repository and command for Bash but only until session end for file modification. Rules are evaluated deny, then ask, then allow, the first match decides, and the rules are enforced by Claude Code, not by the model. [7]
  • The security page describes Manual mode as starting with read-only permissions and asking before Claude Code edits files, runs tests or executes commands, with the user choosing to approve once or allow it from then on. It lists allowlisting frequently used safe commands per user, per codebase or per organisation, and says a deny rule matches the command as written. [9]

The problem

The agent works in the background with nobody watching each step, and it has access to the code and the ability to push. GitHub's risk page names what can go wrong: unvalidated code can introduce vulnerabilities, the agent can push changes to the repository, it can see sensitive information, and prompts can be injected through issues and comments. Where this topic fits

The human checkpoint comes after the work and before it reaches anything shared. The agent is free inside an isolated environment and a single branch. Its output is a draft pull request, and ordinary pull request review is the gate. A second gate covers continuous integration: by default, workflows do not run on the agent's code until a person approves, so generated code does not trigger repository automation unreviewed.

How it is applied, step by step

  1. A user with write access to the repository starts the task. The documentation says only such users can trigger the agent.
  2. The agent edits files and runs tests and linters in an ephemeral cloud environment with restricted internet access, and it can push to a single branch only.
  3. Its work arrives as a draft pull request. The agent cannot mark the pull request ready for review, approve it or merge it.
  4. GitHub Actions workflows do not run on the agent's code until a user with write access has reviewed it and clicked the Approve and run workflows button.
  5. A person reviews the diff. The user who asked the agent for the pull request cannot be the one who approves it, so a second person is involved wherever approvals are required.
  6. The reviewer asks for changes or merges. Each commit is authored by Copilot with the requesting developer as co-author and links to the session log, so a reviewer or auditor can see how the change was produced.

Why this approach fits

Code on a branch is reversible until it is merged, so the agent can work without interruption and the person can judge a finished, testable result instead of dozens of intermediate steps. Pull requests are already a review queue with diffs, required reviewers, checks and history, so no new approval tool has to be built or learned. Barring the requester from approving applies the separation of duties that teams already use for human authors.

Limitation or tradeoff

Review at the end sees the outcome, not the path. A reviewer facing a large generated diff is tempted to skim, and GitHub's own page tells users to review and test the output before using it in production. Reviewer time becomes the bottleneck when many sessions open pull requests at once. Some protections depend on settings: the workflow gate is a default that can be configured away, and the block on the requester approving the pull request exists to maintain a required-approvals rule, so it adds nothing where the repository requires no approval.

Amazon Augmented AI sending low-confidence document extractions to human reviewers

Amazon Augmented AI (A2I) is an AWS service that adds human review to machine learning predictions. The SageMaker AI developer guide describes its built-in integration with Amazon Textract, which extracts key-value pairs from scanned forms. AWS notes that A2I is no longer open to new customers; existing customers can keep using it. [16][17][18][19]

The problem

A model that reads scanned forms is right most of the time and wrong in ways that matter: the guide's own example is mortgage application forms with low-quality scans or poor handwriting. Reviewing every document by hand throws away the benefit of automation, and reviewing none lets errors through. The guide adds that building a review system yourself means workflow logic, custom software for tasks and results, and managing a large group of reviewers.

Where this topic fits

Here the reviewed object is a prediction, not a tool call. The gate sits after the model's output and before the application uses it. Activation conditions, written as JSON, decide which outputs need a person. Matching items become tasks for a work team, and the reviewed result is stored for the application. This is the review-queue pattern in its plainest form: route by confidence, and sample the rest.

How it is applied, step by step

  1. The developer creates a human review workflow (a flow definition) that names a work team, a worker task template for the review screen, and the activation conditions.
  2. The application calls Textract's AnalyzeDocument with that workflow. Textract returns key-value pairs with confidence scores.
  3. A2I evaluates the conditions against the result, for example a named form key whose confidence is below a threshold, an important key that is missing, or a random percentage of all documents.
  4. If any condition is true, a human loop is created and the task appears in the reviewers' interface with the document and the extracted values.
  5. Reviewers confirm or correct the values, and the results are saved to Amazon S3 where the application reads them.
  6. Documents that match no condition pass straight through, and the random sample gives an ongoing measure of how often the unreviewed output is wrong.

Why this approach fits

Reviewer time goes to the items where the model is least sure, which is where a person adds the most. The threshold is a dial: lowering it shrinks the queue and lets more errors through unreviewed, and the team can measure both. Random sampling covers the weakness of confidence routing, because it is the only way to find errors the model was confident about. A managed queue with a work team and a task screen replaces software the team would otherwise write.

Limitation or tradeoff

Confidence is not correctness. A model can be confidently wrong, and a threshold chosen without measurement is a guess; the sample is what tells you whether it is set well. The result is not final until a person finishes, so latency depends on staffing. The documentation states that activation conditions are not available for custom task types, where the application must do its own filtering before starting a human loop. The service is also closed to new customers, so treat it as a documented design to learn from, not a recommendation for a new build.

The post describes ambient agents as agents that listen to an event stream and may act on several events at once, so nobody is sitting in a chat window when they act. For an email assistant the events are incoming mail. An email sent in the user's name is hard to take back, so the agent cannot simply send. A chat-style approval prompt does not fit either, because many threads can be waiting at the same time and the user looks at them when it suits them.

Where this topic fits

The checkpoint sits at the point where the agent wants to act for the user, for example to send a drafted reply. The graph node calls LangGraph's interrupt with the proposed action and the list of responses the user may give. The run's state is saved by the persistence layer and the request shows up in the inbox. The user's response becomes the return value of the interrupt call, and the run continues from there.

How it is applied, step by step

  1. An incoming event starts a run, and the agent works until it has an action to propose, such as a drafted email.
  2. The node builds a request that holds the action name and arguments, a config saying which responses are allowed (accept, edit, respond, ignore), and a description for the reader.
  3. The node calls interrupt with that request. LangGraph saves the graph state through the checkpointer and the run waits.
  4. Agent Inbox lists the pending request alongside every other open thread, so the user can see all outstanding actions in one place.
  5. The user accepts the action, edits its arguments, responds with text, or ignores it.
  6. The response returns to the node as the result of the interrupt call. A typical node sends the accepted or edited email, or passes a text response back to the model to revise the draft.

Why this approach fits

A draft is the natural unit of review for writing: most of the value is in the draft, and the person fixes the last details in seconds with an edit instead of sending the agent round again. An inbox separates the agent's timing from the person's, which a background agent needs. Offering a text response as well as accept and edit turns the checkpoint into a channel for feedback. The post argues that agents which communicate in familiar human patterns build user trust, and that this human feedback is what lets an agent learn over time and align with its user.

An inbox is a queue, and an ignored queue is a pile of paused runs that wait indefinitely. The node restarts from its first line on resume, so anything placed before the interrupt call runs twice. The tooling has also moved: GitHub marks both the agent-inbox repository and the executive-ai-assistant repository as archived and read-only, so the schema shown here is evidence of the pattern, and new work should start from the current LangGraph and LangChain human-in-the-loop documentation.

4Common mistakes

  1. Asking for approval on every tool call.

    Why it causes problems
    Reviewers see dozens of harmless prompts for each one that matters and learn to approve without reading. The gate is still there on paper, but the dangerous call gets the same reflex yes as the directory listing before it.
    How to recognise it
    Approval rates close to 100%, median decision times of a second or two, and users who switch to an approve-everything mode as soon as they find it.
    How to fix it
    Sort tools into tiers. Let read-only and reversible actions run, pre-approve safe patterns, contain what you can in a sandbox, and keep prompts for irreversible or external effects.

  2. Putting the gate in the prompt instead of the code.

    Why it causes problems
    An instruction such as "always ask the user before deleting" depends on the model obeying it. A model that misreads the situation, or that has read injected text telling it the user already agreed, will call the tool directly and nothing will stop it.
    How to recognise it
    Search the codebase for the place where a risky tool is blocked. If the only match is a sentence in the system prompt, there is no gate.
    How to fix it
    Enforce the policy in the code path that executes tools, so that a call the policy marks ask cannot run without a recorded decision. Keep the prompt instruction as a courtesy to the model, not as the control.

  3. Holding a paused run in process memory.

    Why it causes problems
    A pause implemented as a blocking wait for input lives only as long as the process. A deploy, a crash or a scale-down discards every pending approval, and the reviewer's answer arrives for a run that no longer exists.
    How to recognise it
    Pending approvals vanish after a restart, or the approval code path contains a blocking call and no write to a database.
    How to fix it
    Serialise the run state when it pauses, store it under an identifier, and return. Resume in a new invocation that loads the state. Test it by restarting the service between the pause and the decision.

  4. Showing the reviewer a summary instead of the real call.

    Why it causes problems
    A model-written description such as "send a follow-up to the customer" can hide the wrong recipient or an attachment. The reviewer approves the description, and the arguments are what run.
    How to recognise it
    The approval screen has prose but no tool name or argument values, or reviewers cannot tell two different requests apart.
    How to fix it
    Display the exact tool name and arguments that will be executed, rendered by your code from the pending call and escaped as untrusted content. Add the model's rationale as a separate, clearly labelled field.

  5. Rejecting without telling the model why.

    Why it causes problems
    The model receives an error or a bare "rejected" and has nothing to adjust, so it proposes the same call again or abandons a task it could have completed another way. Reviewers then reject the same request repeatedly.
    How to recognise it
    Traces in which the same tool call reappears straight after a rejection, and review queues with near-duplicate items from one run.
    How to fix it
    Require a reason with every rejection and return it as the tool's observation. Where there is an acceptable alternative, say so in the reason.

  6. Trusting whatever the approval request contains.

    Why it causes problems
    If the client sends back the saved state, the tool arguments or the reviewer's name, anyone who can reach the endpoint can approve their own request, swap the arguments, or replay an old approval.
    How to recognise it
    The approval endpoint accepts a full state blob or an arguments field, takes the reviewer identity from the request body, or accepts the same decision twice.
    How to fix it
    Keep the state on the server. Accept only an opaque request ID and a decision, authenticate and authorise the reviewer from the session, apply the decision to the server's copy, and consume each request once.

Exercise 1

Harden the approval gate with single-use requests, re-checked edits and an audit log

CodingIntermediateAbout 45 min (estimate)Hypothetical scenario

Start from approval_gate.py in the worked example. It has three weaknesses: one saved state can be resumed twice, anyone can submit a decision, and an edited amount is never checked against the policy.

Write guarded_gate.py. It should import LEDGER, TOOLS, policy, run and scripted_model from approval_gate and add two functions:

  • submit(store, pending_id, paused) files a paused run in a review store (a dictionary from id to serialised state) and returns the new store.
  • decide(store, audit, pending_id, reviewer, decision, model) applies one decision and returns (outcome, new_store, new_audit).

Then run this scenario and print the result of each step:

  1. Pause the refund run from the worked example and submit it as p-1.
  2. mallory tries to approve p-1.
  3. dana edits the amount of p-1 to 80.0.
  4. dana approves p-1 again.
  5. Pause a second run, submit it as p-2, and have lee edit the amount to 500.0.

You need only the Python standard library.

Requirements

  • Only reviewers named in a REVIEWERS set (use dana and lee) may decide; anyone else gets an error and nothing changes.
  • A pending id can be decided once. A second decision for the same id returns an error and runs no tool.
  • Before executing an approved or edited call, run the policy on the arguments that will really be used. If the verdict is deny, do not execute; return the denial to the model as the observation.
  • Append an audit entry for every applied decision with the id, the reviewer, the decision type, the proposed arguments, the final arguments and the result.
  • Do not mutate the store or the audit list that were passed in; return new ones.

Expected behaviour

The five steps produce four decisions. Step 2 returns an error because mallory is not a reviewer, and the ledger is still empty. Step 3 issues one refund of 80.00. Step 4 returns an error because p-1 has already been decided, and the ledger still holds exactly one refund. Step 5 is refused by the policy because 500.00 exceeds the order total, the model is told so, and the ledger is unchanged. The audit log has two entries: p-1 dana edit 120.0 -> 80.0 and p-2 lee edit 120.0 -> 500.0.

Hint 1

Build the new store with a dictionary comprehension that leaves out the consumed id, before you execute anything.

Hint 2

Compute the final call first (the proposed call, or the proposed call with the edited arguments merged in), then ask the policy about the final call.

Hint 3

An unauthorised or repeated decision should return the original store and audit list unchanged.

Show solution

Save this next to approval_gate.py as guarded_gate.py.

python
import json

from approval_gate import LEDGER, TOOLS, policy, run, scripted_model

REVIEWERS = {"dana", "lee"}


def submit(store, pending_id, paused):
    """File a paused run in the review store under a one-time id."""
    return {**store, pending_id: json.dumps(paused)}


def decide(store, audit, pending_id, reviewer, decision, model):
    """Apply one decision. Returns (outcome, new_store, new_audit)."""
    if reviewer not in REVIEWERS:
        return {"status": "error", "reason": "reviewer not authorised"}, store, audit
    if pending_id not in store:
        return {"status": "error", "reason": "unknown or already decided"}, store, audit

    state = json.loads(store[pending_id])
    remaining = {key: value for key, value in store.items() if key != pending_id}  # consume first
    proposed = state["pending"]
    final = proposed
    if decision["type"] == "edit":
        final = {**proposed, "args": {**proposed["args"], **decision["args"]}}

    if decision["type"] == "reject":
        result = f"REJECTED by reviewer: {decision['reason']}"
    elif policy(final["name"], final["args"]) == "deny":   # re-check what will really run
        result = "DENIED by policy: edited arguments are not allowed"
    else:
        result = TOOLS[final["name"]](**final["args"])
        if final != proposed:
            result += " (arguments edited by reviewer)"

    entry = {"id": pending_id, "reviewer": reviewer, "decision": decision["type"],
             "proposed": proposed["args"], "final": final["args"], "result": result}
    messages = [*state["messages"], {"call": final}, {"result": result}]
    outcome = run({"messages": messages, "status": "running"}, model)
    return outcome, remaining, [*audit, entry]


if __name__ == "__main__":
    task = {"messages": [{"user": "Refund the damaged item in order A-1001."}], "status": "running"}
    store = submit({}, "p-1", run(task, scripted_model))
    audit = []

    outcome, store, audit = decide(store, audit, "p-1", "mallory", {"type": "approve"}, scripted_model)
    print(1, outcome, len(LEDGER))
    outcome, store, audit = decide(store, audit, "p-1", "dana", {"type": "edit", "args": {"amount": 80.0}}, scripted_model)
    print(2, outcome["answer"], LEDGER)
    outcome, store, audit = decide(store, audit, "p-1", "dana", {"type": "approve"}, scripted_model)
    print(3, outcome, LEDGER)

    store = submit(store, "p-2", run(task, scripted_model))
    outcome, store, audit = decide(store, audit, "p-2", "lee", {"type": "edit", "args": {"amount": 500.0}}, scripted_model)
    print(4, outcome["answer"], LEDGER)
    for entry in audit:
        print(entry["id"], entry["reviewer"], entry["decision"], entry["proposed"]["amount"], "->", entry["final"]["amount"])

Why it is built this way:

  • Identity first. The reviewer check runs before anything is loaded, so an unauthorised caller learns nothing about what is pending. In a real service the name would come from the authenticated session, never from the request.
  • Consume, then act. remaining is built without the id before the tool runs. In a database this is one atomic update (for example, delete the row where the id matches and continue only if a row was deleted), so two simultaneous approvals cannot both proceed.
  • Policy on the final arguments. The reviewer is trusted to judge, not to bypass limits. Line 4 shows an edit to 500.00 being refused by the same rule that binds the model, and the model is told why so it can respond to the customer.
  • The audit entry records both versions. Proposed 120.0 and final 80.0 side by side is what lets you measure how often reviewers change the agent's proposals, which is the best evidence for tightening or relaxing the policy.

One weakness remains on purpose: there is no expiry. Adding a creation time to each stored item and refusing decisions after a deadline is a good next step.

For part 3, the audit sample is taken from the refunds that were not gated, not from all refunds.

Show solution

Part 1. The agent proposes N=320/8=40N = 320 / 8 = 40N=320/8=40 refunds an hour, and a reviewer decides μ=12\mu = 12μ=12.

PolicyShare reviewedReviews per hourReviewers needed
Everything100%4040 / 12 = 3.33, so 4
Above 25 USD30 + 16 + 4 = 50%2020 / 12 = 1.67, so 2
Above 100 USD16 + 4 = 20%88 / 12 = 0.67, so 1
Above 500 USD4%1.61.6 / 12 = 0.13, so 1

Part 2. Arrivals are 20 an hour and capacity is 12, so the backlog grows by 8 an hour:

B(8)=(0.5×40−1×12)×8=64B(8) = (0.5 \times 40 - 1 \times 12) \times 8 = 64B(8)=(0.5×40−1×12)×8=64

Clearing 64 requests at 12 an hour takes 64/12=5.3364 / 12 = 5.3364/12=5.33 hours, which is 5 hours 20 minutes. A customer whose refund was proposed at the end of the shift waits that long, and the next shift starts behind.

Part 3. Gated refunds: 20% of 40 = 8 an hour. Refunds that run without review: 40 - 8 = 32 an hour. A 5% audit of those is 1.6 an hour. Total load is 8 + 1.6 = 9.6 reviews an hour, and 9.6 / 12 = 80% of one reviewer's capacity. That leaves a fifth of the reviewer's time for bursts, which a steady-rate calculation does not show. The audit reviews happen after the refund has run, so they do not delay customers; their job is to measure how often the ungated refunds were wrong.

Part 4. A review item should contain at least:

  • the exact tool name and arguments (order ID, amount, refund method),
  • the order facts the decision depends on (total, delivery date, previous refunds),
  • the customer's request and any evidence, such as a photo,
  • the agent's stated reason for proposing this amount,
  • the decisions allowed (approve, edit amount, reject with reason) and a deadline,
  • a link to the full conversation trace.

Triggers that should reach a person whatever the amount, with the reason an amount cannot capture them:

  • The customer has already been refunded for this order. The risk is repetition, and each refund on its own looks small.
  • The conversation contains a signal reserved for people, such as a legal threat, a safety complaint or a request to speak to a person. These are about the situation, not the money.
  • The refund destination differs from the original payment method. This is a fraud signal that is independent of size.

Check your answer

  • Did you get 4, 2, 1 and 1 reviewers for the four policies?
  • Is your end-of-shift backlog 64 requests, taking 5 hours 20 minutes to clear?
  • Did you take the 5% audit sample from the 32 ungated refunds an hour, giving 1.6 and a total of 9.6?
  • Does each review item field help the reviewer decide without opening another system?
  • Do your two triggers depend on something other than the refund amount?
