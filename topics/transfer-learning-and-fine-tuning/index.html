Transfer Learning and Pre-Trained Models

Transfer learning reuses a model that was already trained on one large task as the starting point for a different, usually smaller task. You keep the pre-trained layers, replace the output layer, and then either train only the new layer (feature extraction) or continue training the whole network gently (fine-tuning).

1Overview

Why it matters

Many projects that need an image classifier, a text classifier or a speech recogniser have hundreds or a few thousand labelled examples, not millions. A network with tens of millions of weights trained from random values on that little data memorises it. Starting from a model that has already learned general features from a much larger dataset is what makes these projects feasible, and it cuts the cost sharply: the BERT paper (opens in a new tab) reports four days to pre-train each model but at most an hour to fine-tune it on a single Cloud TPU.

The price is a new set of ways to go wrong. A checkpoint expects its inputs to be prepared exactly as they were during pre-training. Unfreezing a large network at a high learning rate can wipe out what made it useful. A pre-trained model can be worse than training from scratch when the new task needs information the old task ignored, and the only way to know is to run the baseline. Anyone who ships a model built from a public checkpoint also inherits its licence terms and its blind spots. Engineers, data scientists and technical product owners need this vocabulary because most modern vision, speech and language systems are built this way.

Key terms

Pre-trained model (checkpoint)
A network whose weights were already learned on a large dataset and saved so that others can load them. The saved file is called a checkpoint.
Backbone (body)
The layers of a pre-trained network that turn raw input into a feature vector, which is everything except the final output layer.
Head
The last layer or layers, which turn features into the task's outputs such as class scores. It is replaced when the task changes.
Freezing
Excluding a layer's weights from updates during training so that they keep their pre-trained values.
Feature extraction
Using a frozen pre-trained backbone to compute features and training only a new head on them.
Fine-tuning
Continuing to train some or all of the pre-trained layers on the new task, usually with a small learning rate.
Self-supervised pre-training
Pre-training on a task whose labels are made from the data itself, such as predicting a hidden word, so no human annotation is needed.
Model hub
A website or library that hosts pre-trained checkpoints together with documentation and versions, such as the Hugging Face Hub.
Catastrophic forgetting
The loss of earlier knowledge when a network is trained on new data, so that it no longer handles what it used to.
Domain shift
A difference between the data a model was pre-trained on and the data it must now handle, such as everyday photographs versus medical images.

2Explanation

Introduction

Think about learning a second language that shares an alphabet with your first. You do not relearn how letters work, how sentences are built or what a verb is. You reuse all of that and spend your effort on the new vocabulary. Neural networks behave in a similar way. A convolutional network trained to recognise 1,000 kinds of object in photographs ends up with early layers that respond to edges and colour contrasts and later layers that respond to more specific patterns. Yosinski et al. (opens in a new tab) describe the first-layer features of such networks as resembling Gabor filters and colour blobs, which suit many datasets and tasks, not only the 1,000 objects the network was trained on.

Transfer learning exploits this. You take a pre-trained model, a network whose weights were already learned on a large dataset, and use it as the starting point for your own task instead of random weights. The Keras guide (opens in a new tab) gives the usual motive: the new dataset is too small to train a large network from scratch. There are then two main ways to adapt the model. In feature extraction you freeze the pre-trained layers and train only a new output layer on top. In fine-tuning you also let the pre-trained layers move, with a small learning rate so that they adapt instead of being overwritten.

Pre-training does not always need labels. Self-supervised methods create their own training signal from raw data, for example by hiding a word in a sentence and asking the model to predict it. That lets a lab pre-train on billions of unlabelled words or thousands of hours of audio and publish the result, usually through a model hub, so that everyone else can adapt it with a few hundred labelled examples.

This lesson explains why features transfer and which layers carry them, how to choose between extraction and fine-tuning, and where self-supervised pre-training and model hubs fit. You then run a small experiment in plain Python that measures when pre-training helps, when it does not and what fine-tuning repairs. It builds on convolutional neural networks; the text-focused continuation is fine-tuning LLMs.

How it works

Why features transfer

A deep network is a stack of layers, and each layer builds on the one below it. Yosinski et al. (opens in a new tab) measured how general each layer is. They report that first-layer features appear whatever the task, that higher layers become specific to the original task, and that transferring features even from a fairly distant task can beat random features. The CS231n notes (opens in a new tab) state the practical consequence: generic features sit in the earlier layers, and specificity to the original classes grows with depth.

Yosinski et al. also give two reasons transfer can disappoint: top-layer neurons are specialised to the original task, and cutting a network between layers that co-adapted during training makes optimisation harder.

Backbone and head

Split any pre-trained classifier into a backbone, which turns the input into a feature vector, and a head, which turns features into class scores. The old head predicts the old classes, so you discard it and attach a new, randomly initialised head with one output per class you care about. In Keras you load a backbone without its classifier with include_top=False; in PyTorch you replace the final fc layer.

The proportions explain why this works with little data. In the Keras guide a frozen Xception backbone has 20,861,480 non-trainable parameters, and the entire trainable part is the new Dense(1) layer with 2,049 parameters, which fits one output unit on 2,048 pooled features (2,048 weights plus a bias). Fitting 2,049 numbers to a few thousand labelled images is a very different statistical problem from fitting 20 million.

Strategy 1: feature extraction

Freeze the backbone and train only the head. The calls below follow the official PyTorch tutorial (opens in a new tab) with torchvision's ResNet-18, plus the preprocessing that the torchvision documentation (opens in a new tab) bundles with the weights:

python
import torch
from torch import nn
from torchvision import models

weights = models.ResNet18_Weights.IMAGENET1K_V1
model = models.resnet18(weights=weights)
for param in model.parameters():
    param.requires_grad = False                  # freeze the whole backbone
model.fc = nn.Linear(model.fc.in_features, 5)    # new head, trainable by default
optimizer = torch.optim.SGD(model.fc.parameters(), lr=0.001, momentum=0.9)
preprocess = weights.transforms()                # resize, crop and normalise as in pre-training

Because the backbone never changes, you can compute its features once and train the head, or even a logistic regression, on the stored vectors. This is cheap and makes a strong baseline. In the BERT paper (opens in a new tab)'s named-entity-recognition comparison with BERT-BASE, the best frozen-feature setup (the top four hidden layers concatenated, feeding a small trainable BiLSTM) reached 96.1 development F1, against 96.4 for fine-tuning the whole model, a gap of 0.3 F1.

One trap: requires_grad = False stops weight updates, but batch-normalisation layers still update their running mean and variance whenever the model is in training mode. The Keras guide says that when you unfreeze a model that contains batch-normalisation layers you should keep those layers in inference mode, because otherwise the updates to their non-trainable statistics can destroy what the model has learned. In PyTorch, put the backbone's batch-norm layers in eval() mode, and do it again after every call to model.train(), which switches them back.

Strategy 2: fine-tuning

Fine-tuning unfreezes some or all backbone layers and keeps training. Three habits recur in the sources.

  1. Train the head first. The Keras guide says to unfreeze only after the frozen model has trained to convergence, because a randomly initialised head produces large gradient updates that would destroy the pre-trained features.
  2. Give pre-trained weights a smaller learning rate than the new head. CS231n recommends this. There is no universal value: the Keras guide fine-tunes with Adam at 1e-5, and Esteva et al. (first example below) fine-tuned every layer at 0.001 with decay. The right rate depends on the optimiser, the model and how far the target is from the source.
  3. Move the layers gradually. ULMFiT (opens in a new tab) uses discriminative fine-tuning, a separate rate per layer, with each lower layer's rate set to the one above divided by 2.6, and gradual unfreezing: unfreeze the last layer, train one epoch, unfreeze the next lower layer, and repeat.

With a top-layer rate of 0.01, the rule ηl−1=ηl/2.6\eta_{l-1} = \eta_l / 2.6ηl−1​=ηl​/2.6 gives these rates from the top group down:

Choosing a strategy

CS231n sorts the choice by two questions: how much data you have, and how similar it is to the original data.

Treat the grid as a starting hypothesis. Pre-training does not always win. He et al. (opens in a new tab) trained object detectors from random weights on COCO and matched their ImageNet-pre-trained counterparts, given more training iterations; they conclude that pre-training speeds up early convergence but does not necessarily improve final accuracy. Raghu et al. (opens in a new tab) report that on two large medical-imaging tasks, transfer from ImageNet offered little benefit. When you have enough data to try, train a from-scratch baseline too.

Self-supervised pre-training

Supervised pre-training such as ImageNet needs a human label for every image. Self-supervised pre-training makes the labels from the data. BERT hides 15 percent of the tokens in each sequence and learns to predict them, and it learned from BooksCorpus (800 million words) and English Wikipedia (2,500 million words). wav2vec 2.0 masks spans of latent speech representations and solves a contrastive task. Neither needs a transcript or a class label for pre-training; labels enter only at the fine-tuning stage.

Adapting such a model can be very light. For classification, BERT adds only a weight matrix of size K×HK \times HK×H on the final hidden vector of the first token, where KKK is the number of labels and H=768H = 768H=768 for BERT-BASE. With two labels that is 2×768=1,5362 \times 768 = 1{,}5362×768=1,536 new parameters on top of about 110 million. The paper reports that its fine-tuning results can be replicated in at most one hour on a single Cloud TPU, while each pre-training run took four days.

Model hubs

A model hub is where checkpoints are stored, documented and loaded by name. The Hugging Face Hub (opens in a new tab) hosts community checkpoints; torch.hub (opens in a new tab) loads models that a GitHub repository publishes through a hubconf.py file; and Keras Applications (opens in a new tab) ships architectures with ImageNet weights. Worked example: Scratch, feature extraction and fine-tuning as labels grow

This experiment needs only Python 3 and runs in about a minute. It is a toy, so we control what the pre-trained layers learn.

The data. Each input has 10 numbers, x0x_0x0​ to x9x_9x9​, and only two directions matter: z1z_1z1​ is the sum of x0x_0x0​ to x4x_4x4​ divided by 5\sqrt{5}5​, and z2z_2z2​ is half of x5+x6−x7−x8x_5 + x_6 - x_7 - x_8x5​+x6​−x7​−x8​. Both are standard normal; the rest is noise.

TaskExamplesLabel
Source1,200Six classes: the 60-degree sector of the (z1,z2)(z_1, z_2)(z1​,z2​) plane
Similar target6 to 96Two classes: the side of a 30-degree line through the origin, same plane
Shifted target6 to 96The same rule in the plane of z1z_1z1​ and x9x_9x9​, which was pure noise in the source task

The model. One hidden layer of 12 tanh units (the body, 132 parameters) and a softmax output layer (the head). For each target we train three models on the same n examples: scratch (random start, all weights trained), extract (pre-trained body copied and frozen, new head) and tune (extract, then everything unfrozen at a learning rate five times smaller). Freezing is the skipped update in the freeze_body branch of train.

python
import math
import random
import statistics

D, H = 10, 12                                  # input features, hidden units
A = [1 / math.sqrt(5)] * 5 + [0.0] * 5         # direction a (unit length)
B = [0.0] * 5 + [0.5, 0.5, -0.5, -0.5, 0.0]    # direction b (unit length)


def make_data(n, seed, task):
    rng = random.Random(seed)
    xs, ys = [], []
    for _ in range(n):
        x = [rng.gauss(0, 1) for _ in range(D)]
        z1 = sum(a * v for a, v in zip(A, x))
        z2 = x[9] if task == "shifted" else sum(b * v for b, v in zip(B, x))
        angle = math.degrees(math.atan2(z2, z1)) % 360
        y = int(angle // 60) if task == "source" else int(((angle - 30) % 360) // 180)
        xs.append(x)
        ys.append(y)
    return xs, ys


def init(seed, classes):
    rng = random.Random(seed)
    return {"W1": [[rng.gauss(0, 0.3) for _ in range(D)] for _ in range(H)], "b1": [0.0] * H,
            "W2": [[rng.gauss(0, 0.3) for _ in range(H)] for _ in range(classes)], "b2": [0.0] * classes}


def forward(p, x):
    h = [math.tanh(sum(w * v for w, v in zip(row, x)) + b) for row, b in zip(p["W1"], p["b1"])]
    z = [sum(w * v for w, v in zip(row, h)) + b for row, b in zip(p["W2"], p["b2"])]
    e = [math.exp(v - max(z)) for v in z]
    return h, [v / sum(e) for v in e]


def accuracy(p, xs, ys):
    hits = 0
    for x, y in zip(xs, ys):
        probs = forward(p, x)[1]
        hits += probs.index(max(probs)) == y
    return hits / len(ys)


def train(p, xs, ys, epochs, lr, seed, freeze_body=False):
    rng = random.Random(seed)
    W1, b1 = [r[:] for r in p["W1"]], p["b1"][:]      # work on copies; p is not changed
    W2, b2 = [r[:] for r in p["W2"]], p["b2"][:]
    for _ in range(epochs):
        for i in sorted(range(len(xs)), key=lambda _: rng.random()):
            h, probs = forward({"W1": W1, "b1": b1, "W2": W2, "b2": b2}, xs[i])
            dz = [q - float(k == ys[i]) for k, q in enumerate(probs)]
            dh = [(1 - h[j] ** 2) * sum(W2[k][j] * dz[k] for k in range(len(dz))) for j in range(H)]
            for k in range(len(dz)):
                b2[k] -= lr * dz[k]
                for j in range(H):
                    W2[k][j] -= lr * dz[k] * h[j]
            if not freeze_body:                        # freezing = skip the update of the body
                for j in range(H):
                    b1[j] -= lr * dh[j]
                    for d in range(D):
                        W1[j][d] -= lr * dh[j] * xs[i][d]
    return {"W1": W1, "b1": b1, "W2": W2, "b2": b2}


def pretrain():
    xs, ys = make_data(1200, 0, "source")
    return train(init(1, 6), xs, ys, epochs=20, lr=0.05, seed=2)


def compare(pretrained, task, n, s, test):
    xs, ys = make_data(n, 100 + s, task)
    fresh = init(200 + s, 2)
    scratch = train(fresh, xs, ys, 200, 0.05, 300 + s)
    start = {**pretrained, "W2": fresh["W2"], "b2": fresh["b2"]}   # pretrained body, new head
    extract = train(start, xs, ys, 200, 0.05, 400 + s, freeze_body=True)
    tune = train(extract, xs, ys, 100, 0.01, 500 + s)
    return {name: accuracy(m, *test) for name, m in (("scratch", scratch), ("extract", extract), ("tune", tune))}


def main():
    pretrained = pretrain()
    print("source task, held-out accuracy:", accuracy(pretrained, *make_data(1000, 1, "source")))
    body, head = H * D + H, 2 * H + 2
    print("trainable parameters: scratch", body + head, "| extract", head, "| tune", body + head)
    for task in ("similar", "shifted"):
        test = make_data(2000, 999, task)
        for n in (6, 12, 24, 48, 96):
            runs = [compare(pretrained, task, n, s, test) for s in range(10)]
            cells = [f"{k} {statistics.mean(r[k] for r in runs):.3f}±{statistics.pstdev(r[k] for r in runs):.3f}" for k in runs[0]]
            print(task.ljust(8), str(n).rjust(3), *cells)


if __name__ == "__main__":
    main()

Reading the result.

  1. The body works: 96% held-out accuracy on six classes (chance is 16.7%). Head-only models train 26 parameters, not 158.
  2. Similar target: with 12 labels scratch reaches 0.748 and extract 0.866. The advantage is 18.3 points at 6 labels, 0.1 at 48, and gone at 96 (0.939 against 0.937). Tuning adds almost nothing: the head already fits the training set (accuracy 1.0 at 6 and 12 labels).
  3. Shifted target: extract is worse than scratch at every size (0.560 against 0.752 at 12 labels). The body's weights on x9x_9x9​ are small (root-mean-square about 0.18, against about 1.8 on the informative inputs), so frozen features barely see it. Fine-tuning recovers much of the loss (0.879 at 96 labels) but never catches scratch.

Pre-training paid when labels were scarce and the target resembled the source, the benefit faded as labels accumulated, and a frozen body could not supply what it never learned. Standard deviations reach 0.086, so small gaps at small n are unreliable.

Edge cases and limitations

Preprocessing must match pre-training
A checkpoint learned from inputs prepared one specific way: image size and crop, pixel scaling, per-channel mean and standard deviation, or for text the same tokenizer and vocabulary. The torchvision documentation warns that preprocessing must match the weights, since a mismatch can reduce accuracy or produce wrong outputs, and it bundles the transforms with the weights (`weights.transforms()`). A mismatch rarely raises an error; the model just performs worse than it should. Load the preprocessing from the same place as the weights.
Frozen layers can still change when they contain batch normalisation
Batch-normalisation layers carry running statistics that are updated in training mode even when their weights are frozen. The Keras guide notes that setting a batch-norm layer to non-trainable makes it run in inference mode, and that when you unfreeze a model for fine-tuning you should keep those layers in inference mode, because otherwise the updates to the non-trainable statistics can destroy what the model has learned. In PyTorch, call `eval()` on the batch-norm modules yourself, and again after every `model.train()` call.
Pre-training is not always better than training from scratch
He et al. matched ImageNet-pre-trained object detectors on COCO by training from random weights for longer, and Raghu et al. found little benefit from ImageNet transfer on two large medical-imaging tasks. The worked example shows a case by construction: when the target needs an input the source never used, frozen features lose to scratch at every size tried. Pre-training often buys faster convergence and good results from few labels, so test a scratch baseline whenever you have enough data to train one.
Retraining the head replaces the old label set
MediaPipe Model Maker warns that retraining makes the model forget classes it recognised before, so the new model recognises only the classes in the new dataset. A related but distinct risk is losing the useful pre-trained knowledge itself: the ULMFiT authors report that language models overfit small datasets and suffered catastrophic forgetting when fine-tuned with a classifier. If you need the old classes as well as the new ones, include examples of both in training, or keep the original model alongside the new one.
There is no universal fine-tuning learning rate
The Keras guide fine-tunes with Adam at 1e-5, the PyTorch tutorial uses SGD at 0.001 for its new layer, ULMFiT uses a maximum rate of 0.01 with a different rate per layer, and Esteva et al. used 0.001 for every layer. In the worked example's toy network the best fine-tuning rate for the shifted target was the largest one tried, 0.5 (Exercise 1). Optimiser, model size and the distance between source and target all move the right value, so search over rates on a validation set.

When to use it, and when something simpler is enough

Use it when

  • Your labelled set is small (hundreds to a few thousand examples) and a public checkpoint exists for the same kind of input, such as photographs, English text or speech audio.
  • You need a working baseline quickly. Head-only training on frozen features takes seconds to minutes and shows how much the pre-trained features already know about your task.
  • The target data resembles the pre-training data closely enough that early-layer features still describe it, as with clinical photographs and everyday photographs.
  • You have plenty of unlabelled text or audio in your own domain but few labels. Continue the self-supervised pre-training on that data first, as ULMFiT does with its target-task language-model stage, then fine-tune.

Think twice when

  • Your inputs differ fundamentally from anything the available checkpoints saw, and you have enough labelled data to train a smaller model from scratch. Run both and compare.
  • The licence, size or latency of the checkpoint does not fit the product, or the model card lists limitations that cover your use.
  • The model must keep recognising its original classes after adaptation, because plain retraining of the head replaces the label set.

A simpler alternative. If you only need to compare or retrieve items, use the pre-trained network as a fixed encoder and put a nearest-neighbour or logistic-regression model on its embeddings, with no network training at all. Move to fine-tuning only when that setup plateaus below your requirement and you have enough labelled data to adapt the pre-trained layers without overfitting.

Key takeaways

  • Transfer learning starts from a network pre-trained on a large dataset instead of random weights, which lets a small labelled dataset train a large model without simply memorising it.
  • Early layers learn generic features and later layers learn task-specific ones, so the head is always replaced, early layers are frozen most often, and late layers are the first to be unfrozen.
  • Feature extraction trains only a new head on frozen features and is the cheap baseline; fine-tuning also updates the pre-trained layers, with a small learning rate and after the new head has been trained.
  • Self-supervised pre-training builds its labels from raw data, such as masked words or masked audio, which is how models like BERT and wav2vec 2.0 can be adapted with very little labelled data.
  • Pre-training helps most when labels are scarce and the target resembles the source; in the toy experiment it was worth about 12 to 18 accuracy points with 6 to 12 labels, nothing at 48, and negative when the task needed an input the source never used.
  • Before reusing a hub checkpoint, match its preprocessing, read its model card and licence, and compare against a from-scratch baseline.

Example 1 of 5

Skin-lesion classification: ImageNet Inception v3 fine-tuned on clinical photographs

Documented in a paper

Esteva and colleagues' Nature paper on classifying skin lesions from photographs (the author manuscript on PubMed Central) describes starting from an ImageNet-pre-trained Inception v3, fine-tuning it on a large clinical image dataset and testing it against board-certified dermatologists. [8][18]

The problem

Deciding from a photograph whether a skin lesion is, for example, a malignant melanoma is a fine-grained visual task, and labelled clinical images are slow and costly to collect. The authors assembled 129,450 images covering 2,032 diseases, which they describe as two orders of magnitude larger than earlier datasets, yet still about a tenth of the 1.28 million images used for ImageNet pre-training. That makes reusing ImageNet's general visual features attractive.

Where this topic fits

Transfer learning supplies the starting weights and the training strategy. The ImageNet network is the checkpoint, a new output layer is sized for the skin-disease classes, and all layers are then fine-tuned on the dermatology images. In the strategy grid this is the large-data case, where updating every layer is affordable, even though ImageNet's categories are generic objects, not skin diseases.

How it is applied, step by step

  1. Start from Inception v3 with weights pre-trained on about 1.28 million ImageNet images in 1,000 object categories, so the early layers already detect general visual structure.
  2. Group the 2,032 diseases into 757 training classes with the authors' skin-disease taxonomy and a partitioning algorithm, so that the classes are suitable for training.
  3. Replace the 1,000-way ImageNet output with an output layer for the 757 training classes (our inference: a 1,000-way ImageNet output cannot predict skin-disease classes).
  4. Augment each image with a random rotation, a crop of the largest upright inscribed rectangle and a vertical flip with probability 0.5, so that the large network sees varied views of the clinical data.
  5. Fine-tune all layers, not only the new output, with one global learning rate of 0.001 and a decay factor of 16 every 30 epochs.
  6. Keep 1,942 biopsy-labelled images for testing and compare the network with at least 21 board-certified dermatologists on biopsy-proven images.

Why this approach fits

A skin-lesion photograph is still a natural image, so the edge, colour and texture detectors learned on ImageNet remain useful, and starting from them means the 129,450 clinical images are spent on learning what separates lesions, not on learning to see. With this much target data, updating every layer is affordable, which lets the upper layers specialise on lesion patterns that no ImageNet class contains.

Limitation or tradeoff

The authors state that further research is needed to evaluate the technique in a real-world clinical setting across the full range of lesions seen in practice. How much the ImageNet start contributed is a separate question that only a from-scratch comparison answers, and Raghu et al. (opens in a new tab) found little benefit from ImageNet transfer on two large medical-imaging tasks (not skin lesions), so the benefit should be measured rather than assumed.

What the sources document

  • The authors used a Google Inception v3 network pre-trained on about 1.28 million images in 1,000 object categories from the 2014 ImageNet challenge and trained it on their dataset using transfer learning. [8]
  • The dataset has 129,450 clinical images of 2,032 different diseases; a taxonomy and a partitioning algorithm map the diseases into 757 training classes. [8]
  • Every layer of the network was fine-tuned with RMSProp, using one global learning rate of 0.001 and a decay factor of 16 applied every 30 epochs. [8]

MediaPipe Model Maker: customising an image classifier with a frozen backbone

Google (MediaPipe)Documented in official docs

Google's "Image classification model customization guide" for MediaPipe Model Maker explains how to retrain an existing image classifier on your own labelled folders and export a TensorFlow Lite model. The guide itself names this transfer learning. The page now carries a notice that Model Maker is still available but no longer actively maintained (read on 2026-10-11), so treat it as a documented example of the pattern, not as a tool to start a new project with. [9]

The problem

A developer wants an app to recognise their own categories (the guide's example is five types of flowers) but has only a modest folder of photographs per class (the guide's example has 600 to 800), not a large-scale vision dataset. The result also has to come out as a TensorFlow Lite model file.

Where this topic fits

Model Maker implements feature extraction as the default and fine-tuning as an option. It loads a pre-trained backbone, trains a new classification layer on the developer's data, and leaves the backbone frozen unless do_fine_tuning is switched on. Transfer learning is packaged as one setting.

How it is applied, step by step

  1. Arrange the labelled images in one folder per class (`<image_path>/<label_name>/<image_names>.*`) and load them with `Dataset.from_folder`.
  2. Split the data into training, validation and test sets; the guide uses 80 percent for training and splits the remainder in half.
  3. Choose a pre-trained base model from the supported list (MobileNet-V2 or an EfficientNet-Lite variant) and set the hyperparameters, where `do_fine_tuning` is False by default.
  4. Call `ImageClassifier.create`, which trains the new classification layer on the training data while the base module's pre-trained weights stay frozen.
  5. Evaluate with `model.evaluate(test_data)` on images the model never trained on.
  6. Export with `export_model()` to produce the TensorFlow Lite file and a label file. Turn on `do_fine_tuning` only if the frozen-backbone result is not good enough and there is enough data (our advice, following the strategy grid).

Why this approach fits

The target is a small set of custom classes with a modest folder of photographs, which is the small-data, similar-domain case where training only a head is the right first move. Training touches just the classification layer, so it is fast and cannot overfit the backbone, and a developer without deep-learning expertise gets a usable model from one folder of images.

Limitation or tradeoff

Frozen features can express only what the backbone already encodes, so classes that differ in ways the pre-training task ignored can plateau, as the shifted target does in the worked example. The guide also warns that retraining makes the model forget the classes it knew: the new model recognises only the classes of the new dataset. Model Maker itself is marked deprecated, so check the current Google AI Edge documentation before building on it.

What the sources document

BERT: self-supervised pre-training, one-layer fine-tuning and use in Google Search

GoogleDocumented in an engineering article

The BERT paper by Devlin and colleagues describes pre-training a Transformer on unlabelled text and fine-tuning it per task. A Google blog post from October 2019 describes applying BERT models to ranking and featured snippets in Google Search. [5][10]

The problem

Search must understand what a query means, not only which words it contains. The Google post gives the case of a query from a Brazilian traveller to the USA asking about a visa: earlier systems missed that the word "to" signals direction and returned results for Americans travelling to Brazil. Pre-training on plentiful unlabelled text is one way to give a model such language knowledge before any task-specific training (our framing; the post does not discuss label counts).

Where this topic fits

BERT is the pre-training stage for language. It learns from unlabelled text once; each downstream task then adds a small output layer and fine-tunes the whole model on labelled data. Google reports using BERT models in two Search components, ranking and featured snippets, which is the deployed end of that pipeline.

How it is applied, step by step

  1. Pre-train on unlabelled text. BERT masks 15 percent of the tokens in each sequence and learns to predict them, and also learns to tell whether one sentence follows another, using BooksCorpus (800 million words) and English Wikipedia (2,500 million words).
  2. Save the result as a checkpoint. Each pre-training run took four days on Cloud TPUs, and Google open-sourced BERT so that others can build on it.
  3. For a new task, add a small output layer: for classification, a weight matrix applied to the final hidden vector of the first token; for question answering, a start vector and an end vector.
  4. Fine-tune all parameters on the labelled task data for a few epochs at a small learning rate. The paper reports that learning rates of 5e-5, 3e-5 and 2e-5, batch sizes of 16 and 32, and 2 to 4 epochs worked well across tasks, and suggests an exhaustive search over them.
  5. In Search, Google reports using BERT models for ranking and for featured snippets. The post does not describe how the models are fine-tuned or served, so a typical deployment (one fine-tuned model per component) is our assumption.

Why this approach fits

Language offers a huge supply of unlabelled text and a small supply of task labels, which is where pre-training on the abundant data and fine-tuning on the scarce data pays off. Because only a tiny head is added, one expensive pre-training run can serve many tasks, and predicting masked words forces the model to use context on both sides of each word.

Limitation or tradeoff

Fine-tuning produces a separate full copy of the model for each task (our analysis), 110 million parameters each for BERT-BASE. Pre-training is expensive: four days on 16 to 64 TPU chips per model, so most teams reuse a released checkpoint. The Google post reports the effect on searches in general terms and does not give the fine-tuning or serving details.

What the sources document

  • BERT is pre-trained on unlabelled text with a masked language model task (15 percent of WordPiece tokens masked) and a next-sentence prediction task, using BooksCorpus (800 million words) and English Wikipedia (2,500 million words); each pre-training run took 4 days on Cloud TPUs. [5]
  • Adapting the pre-trained BERT model to a task needs only one extra output layer; for classification the new parameters are a K by H weight matrix, and the paper says its fine-tuning results can be replicated in at most 1 hour on a single Cloud TPU or a few hours on a GPU. [5]
  • The fine-tuning hyperparameter ranges the paper found to work well across tasks were batch sizes of 16 and 32, Adam learning rates of 5e-5, 3e-5 and 2e-5, and 2, 3 or 4 epochs. [5]
  • Google introduced and open-sourced BERT as a technique for natural language processing pre-training, and reports applying BERT models to both ranking and featured snippets in Search; at launch it said BERT would help Search better understand one in 10 searches in the U.S. in English. [10]
  • For featured snippets Google reported using a BERT model in the two dozen countries where the feature is available, with significant improvements in languages such as Korean, Hindi and Portuguese. [10]

wav2vec 2.0: self-supervised speech pre-training, then recognition from ten minutes of labels

Documented in a paper

The wav2vec 2.0 paper by Baevski, Zhou, Mohamed and Auli describes pre-training a speech model on unlabelled audio and then fine-tuning it for speech recognition on labelled subsets as small as ten minutes. [7]

The problem

Transcribed speech is costly to produce, while unlabelled audio is plentiful. The paper asks how well a recogniser can do when only minutes to a few hours of transcribed audio exist, and evaluates labelled subsets of 10 minutes, 1 hour, 10 hours, 100 hours and 960 hours.

Where this topic fits

Both halves of the lesson appear: self-supervised pre-training on unlabelled speech, then fine-tuning with a new, randomly initialised output layer. Freezing is used inside fine-tuning too. The convolutional feature encoder is not trained during fine-tuning, and for the first 10,000 updates only the new output layer trains before the Transformer is updated as well.

How it is applied, step by step

  1. Encode raw audio with a convolutional feature encoder into latent speech representations.
  2. Pre-train without any transcripts. Mask spans of the latent representations and train the Transformer on a contrastive task that must identify the true latent for each masked position among distractors, using up to 53.2 thousand hours of unlabelled audio.
  3. Add a randomly initialised linear layer from the Transformer output to the vocabulary and train it with a CTC loss on the small labelled subset.
  4. Keep the feature encoder frozen for the whole of fine-tuning.
  5. For the first 10,000 updates train only the new output layer, then update the Transformer as well.
  6. Measure word error rate on held-out recordings, with or without decoding by a language model; the paper's headline numbers use one.

Why this approach fits

Speech has abundant audio and scarce transcripts, the same asymmetry as text. A model that has already learned the structure of speech needs labels only to map its representations onto characters, so a small new layer and a staged unfreezing are enough to reach a low error rate from minutes of labelled data, when decoding uses a language model. The staged schedule mirrors the lesson's advice: change little until the new head is sensible.

Limitation or tradeoff

Pre-training used tens of thousands of hours of audio, which is realistic for a lab or vendor but not for most product teams, who would reuse a released checkpoint. The reported error rates are measured on LibriSpeech test sets, so they do not by themselves show accuracy on noisy, accented or domain-specific speech where the target differs from the pre-training audio. The ten-minute headline also depends on language-model decoding; the paper's appendix reports error rates near 40 percent without one.

What the sources document

  • Pre-training masks spans of latent speech representations and solves a contrastive task over quantised latents, using unlabelled speech from Librispeech (960 hours) or LibriVox (53.2 thousand hours). [7]
  • Fine-tuning adds a randomly initialised linear projection on top of the context network into the vocabulary and minimises a CTC loss; the feature encoder is not trained during fine-tuning, and for the first 10 thousand updates only the output classifier is trained before the Transformer is updated. [7]
  • Ten minutes of labelled data corresponds to 48 recordings with an average length of 12.5 seconds. [7]
  • With ten minutes of labelled data and 53 thousand hours of unlabelled pre-training data, the paper reports 4.8 and 8.2 word error rate on the Librispeech test-clean and test-other sets. Its appendix shows that this is with Transformer language-model decoding: the same Large model scores 6.6 and 10.3 with a 4-gram language model and 40.2 and 38.7 with no language model. [7]
  • With one hour of labelled data the model outperforms the previous best result on the 100-hour labelled subset, while using 100 times less labelled data. [7]

Hugging Face Hub: finding, fine-tuning and republishing a pre-trained checkpoint

Hugging FaceDocumented in official docs

Hugging Face's Hub documentation (the Model Hub and Model Cards pages) and the Transformers guides for fine-tuning describe how pre-trained checkpoints are hosted, documented and reused: download a checkpoint, fine-tune it, and publish the result with a model card that names its base model. [11][12][13][14]

The problem

Reusing someone else's pre-trained model is practical only if you can find a suitable checkpoint, learn what it was trained on and under which licence, and load it with one call. After fine-tuning, the result has to be shared so that others can see where it came from.

Where this topic fits

The hub is the distribution layer between pre-training and fine-tuning. It stores the checkpoints that labs produce at great cost, and the fine-tuned model is published back into the same hub, where the model card metadata records that it derives from its base model.

How it is applied, step by step

  1. Filter models by task, library, licence or dataset, using the metadata in each model card.
  2. Read the model card: intended uses and limitations, training parameters, the datasets used and the evaluation results.
  3. Load the checkpoint and its tokenizer by name. For classification, load with `AutoModelForSequenceClassification` and the number of labels, so that a head with that many outputs sits on top of the pre-trained model.
  4. Fine-tune with the Trainer; the guide uses a learning rate of 2e-5, a batch size of 16 and 2 epochs on the IMDb movie reviews.
  5. Publish with `push_to_hub`, and name the starting checkpoint in the `base_model` field of the new model card so that the Hub records the lineage.

Why this approach fits

A hub turns pre-training from a private, expensive step into a shared one: reuse becomes a download, and the team spends its effort on its own data. Metadata such as task, library, licence and dataset makes checkpoints discoverable, and base_model makes lineage searchable.

Limitation or tradeoff

A hub hosts models uploaded by many parties. The documentation says what a model card should contain, not that every card is complete or accurate, so quality, licence terms and biases still have to be checked by the user. A fine-tuned derivative also inherits whatever constraints its base model carries.

What the sources document

  • The Model Hub hosts checkpoints that community members upload, so that models can be stored, found and shared; pre-trained models can be downloaded with the huggingface_hub library, with Transformers for fine-tuning, or with any of over 15 integrated libraries. [11]
  • A model card is the README.md of a model repository. It should describe the model, its intended uses and limitations, training parameters, datasets and evaluation results, and its YAML metadata supports filtering by task, licence and dataset. [12]
  • The `base_model` metadata field names the model that a fine-tune, adapter, quantised version or merge derives from; the Hub shows it on the model page and lets users filter for models derived from a given base model. [12]
  • The Transformers text-classification guide fine-tunes DistilBERT on the IMDb dataset to classify movie reviews as positive or negative, loading the checkpoint with `num_labels=2`, training with Trainer and sharing the result with `push_to_hub`. [13]
  • The Transformers fine-tuning guide describes fine-tuning as ordinary training that begins from pre-trained weights instead of random ones, and says it needs much less compute, data and time. [14]

4Common mistakes

  1. Unfreezing the whole network at once while the new head is still random

    Why it causes problems
    A random head makes large errors, and their gradients flow back into every unfrozen pre-trained layer. The Keras guide warns that the resulting very large updates wreck the pre-trained features, which leaves you with an expensive model that is worse than the frozen one.
    How to recognise it
    Validation accuracy or loss is worse in the first epochs after unfreezing than it was with the frozen backbone, or the training loss spikes at the start of fine-tuning.
    How to fix it
    Train the head with the backbone frozen until it converges, then unfreeze and rebuild the optimiser with a much smaller learning rate for the pre-trained layers (in Keras, call compile() again after changing trainable flags). For a large model, unfreeze gradually from the top.

  2. Fine-tuning every layer of a large network on a tiny dataset

    Why it causes problems
    A large pre-trained network has millions of parameters, and a few hundred examples let it memorise them quickly. The Keras guide says large weight updates risk overfitting very quickly for this reason, and the ULMFiT authors report that language models overfit small datasets.
    How to recognise it
    Training accuracy approaches 100 percent while validation accuracy stalls or falls, especially after several epochs of fine-tuning.
    How to fix it
    Keep most layers frozen and unfreeze from the top, use a low learning rate, add data augmentation or weight decay, and stop early on validation loss.

  3. Skipping the baselines

    Why it causes problems
    Without a head-only model and a from-scratch model you cannot tell whether the pre-trained start helped, did nothing or hurt. The worked example's shifted target and the results of He et al. show that pre-training can lose to training from scratch.
    How to recognise it
    You can quote one accuracy figure but no comparison, or the fine-tuned model has only been compared with a weaker, untuned alternative.
    How to fix it
    Train the head-only model, the fine-tuned model and, when the data allows, a from-scratch model on the same split with the same seeds. Report all three with the spread across several seeds.

  4. Choosing the strategy, learning rate or unfreeze depth by looking at test accuracy

    Why it causes problems
    With a few dozen labels the differences between strategies are within noise (in the worked example the standard deviation reaches 0.086 at 6 labels), so reporting the best of many variants on the test set gives an optimistic score that will not hold on new data.
    How to recognise it
    You tried many settings and report the highest test number, or you cannot say which data the settings were chosen on.
    How to fix it
    Choose settings on a validation split or by cross-validation (see [train/test splits and cross-validation](/topics/train-test-split-and-cross-validation/)), evaluate once on the untouched test set, and repeat over several seeds.

  5. Reusing a hub checkpoint without reading its model card, licence or loading code

    Why it causes problems
    The licence may not allow your use, the model card may list limitations that cover your case, and torch.hub-style loading runs code from a repository. PyTorch added its trust_repo parameter in version 1.12 so that users only run code from repositories they trust.
    How to recognise it
    You cannot say what data the checkpoint was trained on or under which licence it is published, or the loading call fetched code you have not read.
    How to fix it
    Read the model card and the licence metadata before choosing a checkpoint, pin the exact version, load code only from repositories you trust, and record the checkpoint id and licence next to your own model's documentation.

import statistics
from transfer_demo import accuracy, init, make_data, pretrain, train

RATES = (0.001, 0.01, 0.05, 0.2, 0.5)
pretrained = pretrain()
for task, n in (("similar", 12), ("shifted", 48)):
    valid, test = make_data(2000, 998, task), make_data(2000, 999, task)
    rows = {"head only": [], **{f"tune lr {r}": [] for r in RATES}, "no warm-up": []}
    for s in range(10):
        xs, ys = make_data(n, 100 + s, task)
        fresh = init(200 + s, 2)
        start = {**pretrained, "W2": fresh["W2"], "b2": fresh["b2"]}
        head_only = train(start, xs, ys, 200, 0.05, 400 + s, freeze_body=True)
        models = {"head only": head_only, "no warm-up": train(start, xs, ys, 200, 0.05, 600 + s)}
        for r in RATES:
            models[f"tune lr {r}"] = train(head_only, xs, ys, 100, r, 500 + s)
        for name, model in models.items():
            rows[name].append((accuracy(model, *valid), accuracy(model, *test)))
    print(task, n, "validation accuracy")
    for name, values in rows.items():
        print("  ", name.ljust(14), f"{statistics.mean(v[0] for v in values):.3f}")
    best = max(rows, key=lambda k: statistics.mean(v[0] for v in rows[k]))
    print("   chosen:", best, "-> test accuracy", f"{statistics.mean(v[1] for v in rows[best]):.3f}")

Small labelled data, abundant unlabelled in-domain text: first continue the self-supervised language-modelling objective on the 200,000 unlabelled emails, as ULMFiT's target-task stage does, then fine-tune a classifier on the 800 labelled emails, unfreezing gradually from the top with a small learning rate for the body. Baselines: frozen embeddings with logistic regression, and the checkpoint without the extra pre-training stage, which shows what the unlabelled emails bought. Risk: check the model card for Spanish coverage and the licence for your use, and check that the unlabelled emails may be used this way under your privacy rules.

Check your answer

  • Does each plan name what is frozen and describe a learning-rate approach, not a single number copied from a tutorial?
  • Does each plan include a baseline that could show the pre-trained start did not help?
  • Is each risk specific to its project, such as leakage by plant, scratch matching pre-training, or licence and privacy for the emails?

    The Keras workflow end to end with runnable code: loading a backbone without its head, freezing, how `trainable` behaves, the batch-normalisation caveat, and a low-learning-rate fine-tuning stage on a cats-versus-dogs dataset.

  • Transfer Learning for Computer Vision Tutorial (opens in a new tab)

    DocumentationBeginnerFreeAbout 30 minutes (estimate)

    What it teaches
    A small PyTorch project that runs both strategies on an ants-versus-bees dataset with a ResNet-18: fine-tuning the whole network and using it as a fixed feature extractor.
    When to use it
    When you want a hands-on PyTorch run, which the page lets you open in Google Colab, to compare the two strategies yourself.

  • BERT: Pre-training of Deep Bidirectional Transformers for Language Understanding (opens in a new tab)

    arXiv (Devlin, Chang, Lee, Toutanova)

    PaperIntermediateFreeAbout 60 minutes (estimate)

    What it teaches
    How self-supervised pre-training and fine-tuning are specified in practice: the pre-training tasks, the one-layer heads, the fine-tuning hyperparameter ranges and a comparison of frozen features with fine-tuning.
    When to use it
    After the lesson, to see how a landmark pre-train-then-fine-tune recipe is written down, or before reading about fine-tuning large language models.

  • Model Cards (opens in a new tab)

    DocumentationBeginnerFreeAbout 15 minutes (estimate)

    What a model card should contain and how its metadata (licence, datasets, task, base model) drives search and lineage on the Hugging Face Hub.

    Before you download or publish a checkpoint, as a checklist for what to read and what to document.
