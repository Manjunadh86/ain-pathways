Reasoning Models and Thinking Budgets

A reasoning model is a language model that writes a stretch of working-out text, called reasoning or thinking tokens, before it writes its visible answer. A thinking budget or effort level is the request setting that controls how much of that working-out the model may do.

1Overview

Why it matters

Reasoning tokens are billed as output tokens and count against the output limit, yet most APIs never show them to you in full. A request whose visible answer is 160 tokens can be billed for 1,200. A request whose limit was sized for the answer alone can spend the whole limit on reasoning and return nothing. Teams that switch to a reasoning model without reading the usage data see their bill and their response times multiply and cannot say why.

The settings also change what good engineering looks like. Prompts written for earlier models, with instructions to think step by step, can waste tokens or make results worse. A tool-calling loop has to hand the model's reasoning back unchanged, or the request fails or the model starts its reasoning again. Anyone who chooses models, writes prompts, builds agents or owns an LLM budget needs to know where reasoning tokens come from, which control limits them, and which tasks repay the cost.

What you will be able to do

  • Explain what reasoning tokens are, where a response reports them, and why they are billed although you cannot read them.
  • Choose between an effort level, a token budget and an output cap, and say which of them is guidance and which is a hard limit.
  • Calculate the cost and the waiting time that reasoning adds to a request from its usage data.
  • Judge from the shape of a task whether more reasoning is likely to improve the result.
  • Rewrite a chain-of-thought prompt so that it suits a reasoning model.
  • Keep reasoning items intact through a tool-calling loop and explain what breaks when they are dropped.

Key terms

Reasoning model
A model trained and served so that it generates internal reasoning before its answer, without being asked to in the prompt.
Reasoning tokens (thinking tokens)
The tokens a model generates while working a problem out. They are billed as output and use context window space, but are hidden or returned only as a summary.
Reasoning effort
A named level such as low, medium or high that tells the model how much reasoning to spend. It guides behaviour and does not guarantee a token count.
Thinking budget
A target number of reasoning tokens for one request, used by Claude 4.5 and earlier models (deprecated on Claude 4.6) and by Gemini 2.5. Newer models replace it with effort levels.
Adaptive thinking
A mode in which the model decides on each request whether to reason and for how long, guided by the effort level. Google calls the same idea dynamic thinking.
Output cap
The request parameter, max_tokens or max_output_tokens, that sets a hard limit on reasoning and visible output added together.
Reasoning summary
A short readable account of the model's reasoning that an API returns in place of the raw reasoning text.
Interleaved thinking
Reasoning that happens between tool calls, after each tool result, as well as before the first action.
Signature (encrypted reasoning)
An opaque, encrypted copy of the reasoning that the API returns so you can send it back on a later call without being able to read it.

2Explanation

Introduction

In Few-Shot Prompting and Chain of Thought you asked a model to reason step by step before answering, and its answers to multi-step problems improved. The reasoning arrived inside the reply, so you paid for it as output and had to pick the final answer out of it. A reasoning model does the same thing without being asked. It is trained to work the problem out first, and the API keeps that working-out apart from the answer.

Think of a written exam. You are given scratch paper, and you hand in only the answer sheet. Hard questions use more scratch paper and take longer, and easy ones need almost none. A reasoning model's scratch paper is a run of reasoning tokens (OpenAI's term) or thinking tokens (the term Anthropic and Google use). They are ordinary generated tokens, produced one after another by the same model that then writes the answer.

Three properties of those tokens drive everything else in this lesson:

  • You pay for them. They are billed at the output-token price.
  • You wait for them. The answer cannot start until the reasoning in front of it has been generated.
  • You mostly cannot read them. The OpenAI, Claude and Gemini APIs return a summary, or nothing, in place of the raw text.

The chart shows the usage figures that OpenAI's reasoning guide (opens in a new tab) gives as its example of one response.

Of the 1,186 output tokens billed, 1,024 were reasoning and 162 were the answer a user would read.

The rest of the lesson covers how to read those numbers in a response, the controls that limit them (effort levels, token budgets and output caps), what they cost in money and waiting time, which tasks repay that cost, how prompts should change for these models, and what a tool-calling loop must do with the reasoning it receives. The examples use the OpenAI, Claude and Gemini APIs and local models served by Ollama, as documented in October 2026. Model names, levels and defaults change often, so treat the specific values as examples and check the current pages before you rely on them.

How it works

One request, two phases

In the simplest case a reasoning model answers in two phases inside one generation. First it writes reasoning: it restates the task, tries an approach, checks an intermediate result and drops a path that fails. Then it writes the answer. Every generated token becomes context for the tokens after it, so the answer is conditioned on the finished working-out and a wrong start can be corrected before anything is shown to the user. Anthropic's thinking documentation (opens in a new tab) describes this as working through the problem before answering, and OpenAI's guide says a model may generate anywhere from a few hundred to tens of thousands of reasoning tokens depending on the problem.

The usage data of the response is the reliable place to see how much reasoning happened:

APIField that counts reasoningHow it relates to output
OpenAI Responsesusage.output_tokens_details.reasoning_tokensPart of output_tokens
Claude Messagesusage.output_tokens_details.thinking_tokensPart of output_tokens
Gemini Interactionsusage.total_thought_tokensReported beside total_output_tokens and billed with it

Two rules hold on all three platforms. Reasoning is billed at the output price, and the billed count is the full reasoning even when the API returns a summary or an empty block. OpenAI and Anthropic also state that reasoning generated in the current turn takes up space in the context window (see Tokens and Context Windows).

None of these three hosted APIs returns the raw reasoning. OpenAI returns a summary only if you set reasoning.summary. Claude returns thinking blocks whose text is a summary, or empty when display is "omitted", the default on its newest models. Gemini returns thought summaries when thinking_summaries is "auto". Each can also return an opaque encrypted copy (a signature on Claude and Gemini, encrypted_content on OpenAI) so that the reasoning can be sent back later. Local open-weight models are the exception: Ollama returns the full trace in a separate thinking field.

Three kinds of control

  • An effort level is a named setting. It is guidance: the model still spends less on easy inputs and more on hard ones. Claude's documentation describes effort as a behavioural signal and not a strict token budget.
  • A thinking budget is a target number of reasoning tokens. It is also soft. Anthropic's extended thinking page (opens in a new tab) calls the budget a target and not a strict cap, and Google's generateContent guide (opens in a new tab) says the model may overflow or underflow it. Budgets are the older design. Claude 4.7 and later reject budget_tokens with a 400 error, and Google recommends levels from Gemini 3 onwards.
  • An output cap is the only hard limit, and it covers reasoning and answer together. It applies to one request. On Claude, each request in a tool loop has its own cap, so a cap does not bound the spend of the whole turn.

Most current models decide for themselves how much to reason within the level you set. A model can skip reasoning entirely on an easy request, so code must not assume every response contains a reasoning item.

What reasoning costs

Because reasoning is output, the cost of one request is

cost=Tin pin+(Treason+Tanswer) pout1,000,000\text{cost} = \frac{T_{in}\,p_{in} + (T_{reason} + T_{answer})\,p_{out}}{1{,}000{,}000}cost=1,000,000Tin​pin​+(Treason​+Tanswer​)pout​​

where each TTT is a token count and each ppp is a price in dollars per million tokens. The wait before the first visible word is about Treason/sT_{reason} / sTreason​/s (plus the time to process the input), and the whole response takes about (Treason+Tanswer)/s(T_{reason} + T_{answer}) / s(Treason​+Tanswer​)/s, where sss is the generation speed in tokens per second. Two consequences follow.

Latency grows with reasoning. The Ollama post (opens in a new tab) that introduced its thinking option shows a local model generating 2,514 tokens, with an evaluation time of about 47.8 seconds, to count the letter r in one word. Hosted models can reason for minutes on hard problems. That is why OpenAI offers a background mode (opens in a new tab) that you poll, and why Anthropic advises batch processing when thinking passes roughly 32,000 tokens per request.

A small cap fails silently. If the cap is reached during reasoning, the response ends with no answer and you are still billed. OpenAI reports this as status: "incomplete", and Claude as stop_reason: "max_tokens". OpenAI suggests reserving at least 25,000 tokens for reasoning and output while you learn what your prompts need. To spend less, lower the effort level and leave the cap generous. Google's thinking guide (opens in a new tab) gives the same advice for Gemini.

Which tasks benefit

More reasoning helps when the answer depends on intermediate work that a single pass would skip. The vendors' own guidance agrees closely:

Task shapeExamplesReasoning setting to try first
Lookup, classification, extraction, reformattingNaming a capital city, routing an emailOff, minimal or low
Comparison, drafting, routine tool useComparing two products, a support chatLow or the default
Multi-step maths, debugging, planning, rules with many conditions, dense documentsOptimising an algorithm, contract review, agent planningThe default, then one level higher

GitHub's account of testing o1-preview in Copilot (opens in a new tab) is a concrete case. The model produced a more efficient optimisation of a tokenizer's byte pair encoder because it handled the code's constraints and edge cases, where GPT-4o stayed with the obvious changes.

More is not always better. Anthropic's post on extended thinking (opens in a new tab) reports that, for Claude 3.7 Sonnet, accuracy on maths questions improved logarithmically with the thinking tokens allowed. Each doubling of the allowance then adds about the same gain, so each extra token buys less than the one before. Run your own evaluation at two or three levels before choosing (see Evaluating LLM Applications).

How prompting changes

Habit from earlier modelsWith a reasoning model
"Think step by step", "explain your reasoning"Remove it. OpenAI's best practices (opens in a new tab) say it is unnecessary and can sometimes hinder.
A hand-written step-by-step planState the goal, the constraints and the output format. Anthropic's prompting guide (opens in a new tab) finds that a general instruction to think thoroughly often beats a prescribed plan.
Few-shot examples by defaultTry zero-shot first. Add examples when the output needs them, and keep them consistent with the instructions.
Asking for the reasoning inside the answerRequest the API's reasoning summary. Some Claude models may refuse a prompt that tries to extract reasoning into the reply.
No definition of doneSay what counts as finished and how the model should check its work.

Wording can still nudge how often an adaptive model thinks. Anthropic's steering guide (opens in a new tab) says to set the effort level first and add prompt guidance only if the behaviour is still off. OpenAI adds a caution from the other side: treat effort as a tuning knob, not as the main way to recover quality.

Reasoning with tool calls

In an agent loop the model reasons, requests a tool, receives the result and continues. From the model's side that whole sequence is one turn, so its earlier reasoning must still be present when the tool result arrives.

  • Return reasoning items unchanged. On Claude, thinking and redacted_thinking blocks must go back complete and unmodified with the tool result, and a modified block is rejected with a 400 error. OpenAI strongly recommends passing back every reasoning item since the last user message so that the model does not restart its reasoning. In Gemini's stateless mode all thought blocks must be resent as received.
  • Or let the server keep state. previous_response_id on OpenAI and previous_interaction_id on Gemini carry the reasoning forward for you.
  • Reasoning can happen between calls. With interleaved thinking the model reflects on each tool result before its next action. It is automatic with Claude's adaptive thinking.
  • Keep settings stable within a turn. On Claude, changing the thinking configuration or the top-level effort starts the prompt cache over. A per-message effort change on Claude (in beta) or a configuration_update item on OpenAI changes effort without breaking the cached prefix, on the models that support them.
  • Old reasoning becomes input. On Claude models that keep earlier thinking in context, it is billed as input on later requests, so long sessions accumulate it.

Worked example: Measuring what thinking adds on a local model, then pricing a documented response

Part 1: measure it. Ollama runs open-weight models on your own machine at no charge. Its chat endpoint takes a think option and reports how many tokens were generated and how long generation took. The script below asks two questions twice each, with thinking off and then on. The first question is a lookup. The second needs three steps: find a duration, convert it to minutes, subtract the stop.

Save this as think_meter.py. It needs Python 3.9 or later, a running Ollama server and one thinking-capable model. Ollama's thinking guide (opens in a new tab) links to the list of them.

python
import json
import sys
import urllib.request

URL = "http://localhost:11434/api/chat"
NANOSECONDS = 1_000_000_000
PROMPTS = [
    "What is the capital of Australia? Answer with the city name only.",
    "A train leaves at 09:40 and arrives at 13:05. It stops for 12 minutes on the way. "
    "How many minutes was it moving? Answer with the number only.",
]


def ask(model, prompt, think):
    body = {"model": model, "think": think, "stream": False,
            "options": {"seed": 7, "temperature": 0},
            "messages": [{"role": "user", "content": prompt}]}
    request = urllib.request.Request(URL, data=json.dumps(body).encode("utf-8"),
                                     headers={"Content-Type": "application/json"})
    with urllib.request.urlopen(request, timeout=600) as response:
        return json.load(response)


def summarise(reply):
    message = reply["message"]
    return {"tokens": reply["eval_count"],
            "seconds": round(reply["eval_duration"] / NANOSECONDS, 1),
            "thinking_chars": len(message.get("thinking") or ""),
            "answer": message["content"].strip()}


if __name__ == "__main__":
    model = sys.argv[1] if len(sys.argv) > 1 else "qwen3"
    for prompt in PROMPTS:
        print(prompt[:33])
        for think in (False, True):
            print(f"  think={think}: {summarise(ask(model, prompt, think))}")

Run python3 think_meter.py <model>. The output below is from one run with the model qwen3.5:4b on Ollama 0.34.2 on a Mac. Your token counts and times will differ with the model and the hardware.

  think=False: {'tokens': 3, 'seconds': 0.1, 'thinking_chars': 0, 'answer': 'Canberra'}
  think=True: {'tokens': 175, 'seconds': 6.5, 'thinking_chars': 605, 'answer': 'Canberra'}
A train leaves at 09:40 and arriv
  think=False: {'tokens': 4, 'seconds': 0.1, 'thinking_chars': 0, 'answer': '425'}
  think=True: {'tokens': 948, 'seconds': 30.9, 'thinking_chars': 2263, 'answer': '193'}

Check the second question by hand: 09:40 to 13:05 is 3 hours 25 minutes, which is 205 minutes, and 205 − 12 = 193.

  • Lookup. Thinking did not change the answer. It multiplied the generated tokens by 58 (175 / 3) and turned a tenth of a second into about six seconds.
  • Multi-step question. The direct answer was wrong and the reasoned answer was right. It took 948 tokens and about half a minute.
  • Separate fields. The thinking text came back in message.thinking, apart from the short answer in message.content.

One run of one small model shows the pattern and proves nothing general. To choose a setting for real work, run a set of test cases at each level.

The output cap needs the same arithmetic. This response used 1,186 output tokens. A cap of 300 would fit the 162-token answer comfortably, yet generation would stop during reasoning and return no answer at all. What the numbers mean: reasoning was 86% of the output bill, the response cost nearly seven times what the same answer would cost without reasoning, and the cap has to be sized for reasoning plus answer. None of this is visible unless you read the usage data.

Edge cases and limitations

The cap is reached while the model is still reasoning
The response ends with no visible answer, and the reasoning tokens are still billed. OpenAI returns status incomplete with the reason max_output_tokens, Gemini returns status incomplete with truncated or empty output, and Claude stops with the stop reason max_tokens. Check the status before you read the text. Then raise the cap or lower the effort level. Retrying with the same settings usually fails the same way.
The reasoning you can read is not the reasoning you paid for
Claude and Gemini return a summary of the full reasoning, and OpenAI returns a summary only on request. All three bill the full reasoning, so the token count of the text you see will not match the billed count. Use the usage fields for accounting. Anthropic also cautions that a model's visible thought process may not faithfully represent what drove its answer, so treat summaries as a debugging aid and not as an audit record.
A model may not reason at all on an easy request
With adaptive or dynamic thinking the model decides on every request. Anthropic's documentation says a turn in which Claude chose not to think contains no thinking block, and that follow-up requests in a tool loop can skip thinking even at the highest effort levels. Select response content by its type and never by its position, and do not assume the first item is reasoning.
The same setting behaves differently on another model
Supported levels and defaults vary by model. In the documentation read for this lesson, Claude Opus 5.5 defaults to medium while most Claude models default to high, GPT-6 Astra rejects the none level, several Claude models cannot have thinking turned off, and Claude 4.7 and later reject a token budget with a 400 error. Anthropic notes that the effort scale is calibrated per model. Read the model's page and rerun your evaluation whenever you switch.
More reasoning can score lower
In Anthropic's tau-bench experiments with Claude 3.7 Sonnet, extended thinking scored 0.770 on the retail domain against 0.783 for the baseline with no reasoning aid. Anthropic's effort documentation also warns that the highest level can lead to overthinking on some structured-output tasks. A higher setting is a hypothesis to test against your own cases, not a guaranteed improvement.
Earlier reasoning may or may not stay in context
Platforms differ on whether reasoning from previous turns is shown to the model again. Recent Claude models keep prior thinking blocks in context and bill them as input, while older ones strip them after the turn. OpenAI exposes the choice as a reasoning context setting, and persisted reasoning can be reused only within one model family. Long sessions therefore grow faster on some models, and switching model in the middle of a conversation can drop the earlier reasoning.

When to use it, and when something simpler is enough

Use it when

  • The task needs several dependent steps that a single pass tends to skip, such as a multi-step calculation, debugging across files or applying a policy with many conditions.
  • The input is long and dense and the answer depends on relating separate parts of it, as in contract review or reconciling several documents.
  • A wrong answer costs much more than a slow one, and the response is allowed to take seconds to minutes or to run in the background.
  • An agent has to plan a multi-step task or decide what to do after each tool result, and your loop keeps its reasoning items intact.
  • You have an evaluation set and can show that a higher level improves results by enough to justify its measured cost and latency.

Think twice when

  • The task is a lookup, classification, extraction or reformatting that a direct answer already gets right. Reasoning then adds cost and delay and changes nothing.
  • The user is waiting for the first word within about a second, as in voice, autocomplete or live chat suggestions.
  • The volume is high and each request is worth little, so multiplying output tokens several times over breaks the budget.
  • You need a guaranteed ceiling on reasoning spend per request and plan to rely on an effort level for it. Effort is guidance. Only the output cap is a guarantee.

A simpler alternative. A standard model call at the lowest reasoning setting with a clear prompt, plus a chain-of-thought instruction or a fixed prompt chain for the few multi-step cases. This stops being enough when your evaluation shows wrong answers on multi-step or ambiguous inputs that better prompts do not fix. A middle path is routing: send only the hard requests to a higher effort level and keep everything else low.

Key takeaways

  • A reasoning model generates reasoning tokens before its answer. They are billed as output, count against the output cap and use context, although you see at most a summary of them.
  • Effort levels and thinking budgets are guidance on how much to reason. The output cap is the only hard limit, and it must leave room for the reasoning and the answer together.
  • Reasoning adds cost and waiting time in proportion to the tokens generated, so read the reasoning count in the usage data before you estimate either.
  • Extra reasoning pays off on multi-step, ambiguous or dense-document tasks and is wasted on lookups, classification and formatting. Test levels against your own evaluation set.
  • A prompt for a reasoning model states the goal, the constraints, the output format and what counts as done, and leaves out instructions to think step by step.
  • In a tool-calling loop, return the model's reasoning items unchanged with each tool result and keep the reasoning settings the same for the whole turn.

Example 1 of 5

Claude Code exposing effort levels to control reasoning in a coding agent

AnthropicDocumented in official docs

Claude Code is Anthropic's coding agent for the terminal and editor. Its model configuration documentation describes how a session's effort level is chosen, what each level is for and how an organisation can cap it. The Claude API's effort page documents the parameter underneath. [12][9]

The problem

A coding session mixes trivial steps, such as renaming a variable or reading a file, with hard ones, such as finding the cause of a bug that spans several modules. One fixed amount of reasoning would either slow down and overprice the easy steps or shortchange the hard ones. The user is charged for every thinking token, including thinking that the interface collapses or redacts, so someone has to decide how much reasoning a session may use, and an organisation may want to limit that decision.

Where this topic fits

The effort level is resolved before requests are sent. Claude Code takes the first source that applies (an explicit choice, then saved settings, then the model's default) and passes the level to the API. Inside each step the model then uses adaptive reasoning to decide whether to think and how deeply. The level therefore sits between the developer's intent for the session and the model's own judgement on each step.

How it is applied, step by step

  1. Claude Code picks the session's level from the first source that applies: an explicit choice (the CLAUDE_CODE_EFFORT_LEVEL variable, the --effort flag or the /effort command), then saved settings, then the model's default.
  2. The level accompanies the session's requests, and the model uses adaptive reasoning to decide at every step whether to think and for how long.
  3. A developer lowers the level for quick exchanges they will review themselves, such as a rename, and raises it for work where verification and edge cases matter, such as fixing a bug in an existing codebase.
  4. For a single hard prompt the developer can include the keyword ultrathink. Claude Code adds an instruction to the context asking for deeper reasoning on that turn and leaves the effort level sent to the API as it was.
  5. A skill or subagent file can set its own effort in its frontmatter, so a cheap helper task can run at a lower level than the main session.
  6. An administrator can cap the level with the maxEffortLevel managed setting or, on Enterprise plans, with per-role limits. A request for a higher level then runs at the cap.

Why this approach fits

A coding agent makes many model calls of very uneven difficulty. A named level that the model interprets step by step suits that better than a fixed token budget, because easy steps can skip thinking and hard steps can take more. Offering the control in several places matches who owns each decision: the developer for the task in front of them, the team for defaults and helper tasks, and the organisation for the ceiling on spend.

Limitation or tradeoff

The levels are calibrated per model, so the same name does not buy the same amount of reasoning on two models, and defaults differ between models. The documentation warns that max may show diminishing returns and is prone to overthinking. Effort is guidance, so a cap on the level is not a cap on tokens. On several current models thinking cannot be switched off at all. Changing the level in the middle of a session can also invalidate the prompt cache, which the /effort command warns about.

What the sources document

  • Effort levels control adaptive reasoning, in which the model decides whether and how much to think on each step; lower effort is faster and cheaper and higher effort reasons more deeply. Users are charged for all thinking tokens generated, even when the thinking is collapsed or redacted in the interface. [12]
  • The guidance table suggests low for quick exchanges such as a rename, high for work where verification matters such as fixing a bug in an existing codebase, and max for hard problems such as finding security vulnerabilities, adding that max may show diminishing returns and is prone to overthinking. [12]
  • Including the keyword ultrathink in a prompt makes Claude Code add an in-context instruction asking for deeper reasoning on that turn, while the effort level sent to the API is unchanged. [12]
  • Enterprise administrators can set a maximum effort level per model for each custom role, and the maxEffortLevel managed setting caps effort on the client on any plan and provider. [12]
  • The API's effort page describes effort as a behavioural signal and not a strict token budget, says it affects all tokens in a response including tool calls, and says lower levels tend to make fewer tool calls. [9]

The facts above come from the cited sources. The steps and analysis in this example are our explanation of how they fit together.

Example 2 of 5

Hebbia and Endex using o1 to find decisive terms in dense financial documents

Documented in official docs

OpenAI's reasoning best practices guide lists patterns of successful use that it has observed from customers and quotes the companies involved. Two of them, Hebbia (an AI knowledge platform for legal and finance) and Endex (an AI financial intelligence platform), describe using the o1 reasoning model on credit agreements and acquisition documents. [2]

The problem

Deal documents are long, and the term that matters may be a capacity defined across several clauses or a provision in a footnote. Answering a question such as which baskets are available under the restricted payments capacity means finding the relevant definitions, combining them and ignoring everything else. A model that answers in one pass tends to return the most obvious passage. The guide files these cases under navigating ambiguous tasks and finding a needle in a haystack.

Where this topic fits

The reasoning model is the analysis step. In a typical implementation, the application gathers the documents into the prompt with a short instruction before it, and the answer goes after it to a finance professional or to the next stage of a larger system (Hebbia describes its platform, Matrix, as multi-agent). The reasoning spend sits in the one call that receives a long input and a simple question.

How it is applied, step by step

  1. In a typical implementation, the application places the documents, or the relevant sections of them, in the prompt, with clear delimiters so the model can tell one document from another.
  2. It adds a short, direct instruction that names the question and the form of the answer. Hebbia describes using a basic prompt.
  3. The model spends reasoning tokens working through the material: finding the relevant definitions and provisions, relating them to one another and discarding what does not bear on the question.
  4. It returns the answer, for example the baskets available under a capacity, or a flagged provision together with its consequence.
  5. A typical workflow then has a person review what was flagged. In the Endex account the output supports finance professionals by pointing them to the critical information.

Why this approach fits

This is work that a single pass skips. Several definitions have to be found, held together and reconciled before an answer exists, and that intermediate work is what reasoning tokens pay for. The instruction can stay short because the difficulty lies in the documents and not in the wording of the task, which matches the guide's advice to keep prompts simple and direct. The cost is acceptable because a missed provision in a deal is expensive and nobody needs the answer within a second.

Limitation or tradeoff

The evidence is a set of customer statements published by the model's vendor. The figures are reported by the companies without a description of the test set or the method, and they compare o1 with the models available at the time. The statements say nothing about cost or response time. A long input combined with high effort is the most expensive way to call a model, and a reasoning model can still miss or misread a clause, so someone who can check the cited sections has to review the output.

What the sources document

  • The guide describes its reasoning models as trained to think longer and harder about complex tasks and to make decisions based on large volumes of ambiguous information, and its GPT models as lower-latency, more cost-efficient models for straightforward execution. [2]
  • Hebbia reports that o1 let its Matrix platform identify the baskets available under the restricted payments capacity in a credit agreement with a basic prompt, and that o1 gave stronger results on 52% of complex prompts on dense credit agreements compared to other models. [2]

Example 3 of 5

Anthropic testing where a customer-service agent should reason between tool calls

AnthropicDocumented in an engineering article

Anthropic's engineering article on the think tool (March 2025, updated December 2025) reports experiments with Claude 3.7 Sonnet on tau-bench, a benchmark of customer-service agents that must follow airline and retail policies while calling tools. It compares a baseline, extended thinking before the response, and a tool that gives the model a place to reason in the middle of a task. [17][6][10]

The problem

A customer-service agent has to apply a long policy (cancellation rules, baggage allowances, payment limits) to facts it only learns from tool results partway through the conversation. Reasoning done before the first action cannot take account of facts that arrive later. The benchmark's metric, pass^k, asks whether the agent succeeds on all of k independent trials of a task, so an occasional policy slip counts heavily.

Where this topic fits

The reasoning is placed inside the tool-calling loop, after a tool result and before the next action or reply. In the experiments this was a think tool whose only effect is to record a thought. On current Claude models the same position is filled by interleaved thinking, which Anthropic's documentation says is automatic with adaptive thinking.

How it is applied, step by step

  1. In the benchmark setup the agent receives the customer's request, works under a written policy and calls tools to fetch the reservation or the customer's profile.
  2. When a tool result arrives, the agent stops to reason about which rules apply, whether every required detail has been collected and whether the planned action complies with the policy.
  3. In the experiments this pause was a call to a think tool that changes nothing in the database and only logs the thought. A typical current implementation gets the same pause from thinking blocks between tool calls.
  4. For the harder airline policy, the system prompt also contained worked examples of what to reason about, such as the checks to run before cancelling a flight.
  5. The agent then takes the next action or answers the customer, and the cycle repeats with the next tool result.
  6. The team ran each configuration over repeated trials and compared pass^k for k from 1 to 5.

Why this approach fits

Following a policy across a multi-step conversation is a case where the facts needed for the decision arrive from tools after the task has started. Reasoning placed at that point can check the new facts against the rules. The results also show that the prompt matters on a hard domain: the same mechanism did much better when the prompt showed what to reason about, which is a different lesson from the advice to delete step-by-step instructions.

Limitation or tradeoff

Reasoning was not a uniform win. In the retail domain, extended thinking scored slightly below the baseline at k=1, and in the airline domain the unprompted think tool and extended thinking were close to each other and well below the prompted version. The article says the technique increases prompt length and output tokens and gives no benefit for single or parallel tool calls or for simple instruction following. The numbers come from Claude 3.7 Sonnet on a benchmark with simulated users, so the ordering of the configurations may not hold on current models.

What the sources document

  • tau-bench tests a model's use of tools in realistic customer service scenarios with policy guidelines, and its pass^k metric measures the probability that all k independent trials of a task succeed, averaged across tasks. [17]
  • For the airline domain with Claude 3.7 Sonnet, the results table lists pass^1 of 0.584 for the think tool with an optimised prompt, 0.404 for the think tool alone, 0.412 for extended thinking and 0.332 for the baseline. The article's summary sentence gives 0.570 and 0.370 for the first and last of these. [17]
  • For the retail domain, the table lists pass^1 of 0.812 for the think tool without extra prompting, 0.770 for extended thinking and 0.783 for the baseline. [17]
  • The article says the think tool brings no improvement for non-sequential tool calls or simple instruction following, and that it comes at the cost of increased prompt length and output tokens. [17]
  • An update dated 15 December 2025 recommends extended thinking over a dedicated think tool in most cases. Anthropic's documentation states that interleaved thinking is automatic with adaptive thinking and shows a two-tool comparison in which the model thinks after each tool result. [17][6][10]

OpenAI background mode for reasoning requests that run for minutes

OpenAIDocumented in official docs

OpenAI's Responses API has a background mode, described in its background mode guide and recommended in its deep research guide. The guide introduces the feature by pointing to Codex and Deep Research as evidence that reasoning models can take several minutes on complex problems. [4][5]

The problem

A request that reasons for minutes does not fit an ordinary HTTP request and response. Connections time out or drop, and a client that loses its connection has no result to show. The deep research guide says its models can take tens of minutes on a task, and it advises raising client timeouts for anyone who does not use background mode.

Where this topic fits

Background mode changes how the response is delivered and leaves the reasoning itself alone. The request starts the work on the server and returns straight away with an id and a status. The application later polls for the result, or is told by webhook that it is ready, and reads the same response object it would have received from a synchronous call.

How it is applied, step by step

  1. The application sends a normal Responses API request with the background flag set to true.
  2. The API returns immediately with a response object whose status shows that the work is queued or in progress.
  3. The model reasons and calls its tools on the server for as long as the task needs.
  4. The application polls the response by its id while the status is queued or in progress, or registers a webhook that is notified when the response is ready.
  5. When the status reaches a final state, the application reads the output. It can also cancel a response that is no longer needed.
  6. Where a person is watching, the application can stream a background response and keep a cursor so that a dropped connection can be resumed.

Why this approach fits

When reasoning time is long and hard to predict, the dependable design is to separate starting the work from collecting it. Polling or a webhook survives client restarts and network drops, which a single long-lived connection does not. A deadline with cancellation gives the application a way to give up on a run that nobody is waiting for any more.

Limitation or tradeoff

Background mode keeps response data for roughly ten minutes so that polling works. The deep research guide describes this as incompatible with zero data retention requirements, so check your retention terms before using it for sensitive prompts. The background mode guide also notes that the time to first token of a streamed background response is currently higher than for a synchronous one. It does nothing to shorten the reasoning: the user waits just as long and the same tokens are billed, so the product still needs a design that tolerates the delay, such as a job status page or a notification.

What the sources document

  • The background mode guide states that agents like Codex and Deep Research show that reasoning models can take several minutes to solve complex problems, and that background mode lets developers run long tasks without worrying about timeouts or other connectivity issues. [4]
  • A background response is started by setting background to true, its status is checked by polling while it is queued or in progress, and an in-flight response can be cancelled. [4]
  • The deep research guide says its models can take tens of minutes to complete tasks and recommends background mode, optionally with webhooks, or higher client timeouts when background mode is not used. [5]
  • Background mode retains response data for roughly ten minutes so that polling works reliably, which the deep research guide says makes it incompatible with zero data retention requirements.   • The background mode guide notes that the time to first token from a background response is currently higher than from a synchronous one. [4]

Example 5 of 5

Ollama separating the reasoning trace of open-weight models from their answers

OllamaDocumented in official docs

Ollama is a runtime for open-weight models on your own hardware. Its thinking documentation, and the blog post that introduced the feature in May 2025, describe a think option for reasoning models such as DeepSeek R1 and Qwen 3 and a reply format that keeps the reasoning trace apart from the answer. [15][16]

The problem

An application that runs a local reasoning model has two needs that pull in different directions. Sometimes it wants only the answer and wants it quickly. Sometimes it wants the model to reason and wants to show or log that reasoning without mixing it into the answer. Model families also differ in what they offer: some can only be switched on or off, and others have named levels.

Where this topic fits

The control sits in the request to the local server and in the shape of its reply. Before generation, the think field says whether, or how hard, the model should reason. After generation, the server returns the trace and the answer in separate fields, and the application decides what to do with each.

How it is applied, step by step

  1. The application asks the show endpoint which thinking values the model supports and which one is the default. A model may offer true and false, or named levels such as low, medium and high.
  2. It sends a chat or generate request with think set to true, false or a supported level name, or leaves it unset to get the model's default.
  3. The model generates. With thinking on, the reasoning tokens come first and the answer tokens follow.
  4. The server returns the reasoning in message.thinking and the answer in message.content, or in thinking and response for the generate endpoint.
  5. The application shows the answer and hides the trace, logs it for debugging or displays it as a progress indicator. When streaming, the first thinking chunk marks the start of the reasoning section.
  6. For questions that need no reasoning, the application sets think to false so that the model answers directly.

Why this approach fits

Splitting the trace from the answer on the server gives every client the same clean result, with no model-specific parsing. A switch on each request lets one local model serve quick lookups and harder questions alike. That matters most on local hardware, where generation is slow and every reasoning token is felt as waiting time. Because the trace is returned in full, it is also the cheapest way to study what a reasoning model does with its tokens.

Limitation or tradeoff

The controls depend on the model. The documentation says numbers are not supported for think, so there is no token budget, and an unsupported level name falls back to the model's default. A model with no thinking metadata might reason anyway. The trace is raw model output that can be wrong or confused, so it is not an explanation to show end users. Speed is limited by local hardware: the blog's sample reply reports 2,514 generated tokens for a one-line question, with an evaluation duration of about 47.8 seconds if the value is read as nanoseconds.

What the sources document

  • Thinking-capable models emit a thinking field that separates the reasoning trace from the final answer. The chat endpoint returns message.thinking and message.content, and the generate endpoint returns thinking and response. [15]
  • The think field accepts true, false, null for the model default, or a string naming a supported level. Numbers are not supported, and unsupported names use the model default. [15]
  • The show endpoint returns a thinking object listing the values a model supports and its default; the documentation's example lists low, medium and high with a default of medium. [15]
  • The blog post announcing the feature names DeepSeek R1 and Qwen 3 as the supported models at launch and says that with thinking disabled the model does not think and outputs the content directly. [16]
  • The blog's sample chat reply to a letter-counting question on deepseek-r1 shows a prompt_eval_count of 10, an eval_count of 2514 and an eval_duration of 47770692833. [16]

4Common mistakes

  1. Setting the output cap to fit the visible answer and forgetting that reasoning counts against it.

    Why it causes problems
    The model can spend the whole cap on reasoning and return an empty or cut-off answer. You are billed for the reasoning tokens, the user gets nothing, and a retry with the same cap fails in the same way.
    How to recognise it
    Responses with status incomplete or a stop reason of max_tokens, empty output text, and a reasoning token count close to the cap.
    How to fix it
    Measure reasoning tokens on real traffic, set the cap to cover the largest reasoning you see plus the answer with a margin, and handle the incomplete status in code. When you want to spend less, lower the effort level and leave the cap alone.

  2. Keeping chain-of-thought instructions and demands to show all reasoning in a prompt moved to a reasoning model.

    Why it causes problems
    The instruction duplicates what the model already does and lengthens the visible answer, and OpenAI's guidance says it can sometimes hinder performance. On some Claude models a request to write internal reasoning into the reply may be refused.
    How to recognise it
    Search your prompts for phrases such as step by step and explain your reasoning, and for reasoning tags. Look for answers that restate their working at length, or refusals with a reasoning extraction category.
    How to fix it
    Take the instruction out. State the goal, the constraints and the output format, and use the API's reasoning summary when you need to inspect the reasoning. If the reasoning is too shallow, raise the effort level.

  3. Filtering, rebuilding or summarising the assistant message before sending tool results back.

    Why it causes problems
    The model loses the reasoning that led to the tool call. Claude rejects a modified thinking block with a 400 error. On OpenAI the model may have to restart its reasoning, which OpenAI says lowers function-calling performance and raises reasoning-token use in complex agentic cases with many function calls.
    How to recognise it
    Code that keeps only text and tool-call items, or that filters on one block type and so loses redacted thinking blocks. Also 400 errors that mention thinking blocks, and reasoning counts that stay high on every step of a loop.
    How to fix it
    Append the model's output items to the history exactly as received and then add the tool result, or let the server hold the state with a previous response or previous interaction id.

  4. Choosing the highest effort level for everything, or carrying a level over from a different model.

    Why it causes problems
    Cost and latency multiply on requests that did not need the reasoning, and the highest level can overthink simple or structured tasks. Level names are calibrated per model and defaults differ, so the same word buys a different amount of reasoning after a model change.
    How to recognise it
    A high reasoning share of output tokens on easy request types, long waits on simple questions, and an effort setting that nobody has tested since the last model upgrade.
    How to fix it
    Start from the model's default, run your evaluation set at two or three levels and pick the lowest level whose quality you accept. Repeat the sweep whenever you change model.

  5. Changing the effort level or thinking settings between requests of a cached conversation.

    Why it causes problems
    On Claude the thinking configuration and the effort level are rendered into the prompt, so a change starts the prompt cache over and the history is written to the cache again instead of being read from it. Toggling thinking in the middle of a tool loop silently disables it for that request.
    How to recognise it
    Cache read tokens fall to zero straight after a settings change, or thinking blocks disappear from responses partway through a tool loop.
    How to fix it
    Pick one configuration per conversation. Where the platform supports it, change effort with a per-message setting (beta on Claude) or a configuration update item, which keeps the cached prefix.

INPUT_PRICE = 2.00    # USD per million input tokens
OUTPUT_PRICE = 10.00  # USD per million output tokens; reasoning is billed here
MARGIN = 1.25
ROUND_TO = 1_000
REQUESTS_PER_DAY = 5_000

LOG = [...]  # the twelve records from the prompt


def cost(record):
    return (record["input"] * INPUT_PRICE + record["output"] * OUTPUT_PRICE) / MILLION


def visible(record):
    return record["output"] - record["reasoning"]


completed = [r for r in LOG if r["status"] == "completed"]
incomplete = [r for r in LOG if r["status"] == "incomplete"]

total_output = sum(r["output"] for r in LOG)
total_reasoning = sum(r["reasoning"] for r in LOG)
print(f"reasoning share of output: {total_reasoning / total_output:.1%}")

total_cost = sum(cost(r) for r in LOG)
wasted = sum(cost(r) for r in incomplete)
print(f"total cost: ${total_cost:.4f}, spent on incomplete responses: "
      f"${wasted:.4f} ({wasted / total_cost:.1%})")

max_reasoning = max(r["reasoning"] for r in completed)
max_visible = max(visible(r) for r in completed)
new_cap = math.ceil((max_reasoning + max_visible) * MARGIN / ROUND_TO) * ROUND_TO
print(f"largest completed reasoning: {max_reasoning}, "
      f"largest visible answer: {max_visible}, new cap: {new_cap}")

      f"of which reasoning: ${average_reasoning_cost:.5f}")

      f"of which reasoning: ${average_reasoning_cost * REQUESTS_PER_DAY:.2f} "
