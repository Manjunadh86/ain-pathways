Choosing an Agent Framework

An agent framework is a library that supplies the agent loop together with the parts that grow around it: state, orchestration, tracing and integrations with model providers and tools. Choosing one means deciding which of those parts a task needs, which programming style fits it, and how much of your code you are willing to tie to one project's design.

1Overview

Why it matters

A hand-written loop is a few dozen lines, but production requirements add work around it: pausing for an approval, surviving a restart, recording every model and tool call, switching model provider. A framework hands you those pieces in exchange for a dependency whose design decisions you inherit. Adopt one too early and you debug someone else's abstraction without understanding your own loop. Avoid one for too long and you maintain a home-made framework that has no tests and no documentation.

The choice is also hard to reverse. Tools and prompts usually move between frameworks with little work. State schemas, saved checkpoints and orchestration code do not. Vendors replace their own products too: LangChain moved its prebuilt agent to a new package and interface in version 1, and Microsoft publishes a guide for moving from AutoGen to its successor. Engineers who build agents, tech leads who approve the dependency and reviewers of an architecture proposal all need a repeatable way to make this decision and to explain it afterwards.

Key terms

Agent framework
A library that runs the agent loop for you and adds supporting parts such as state storage, orchestration, tracing and adapters for model providers and tools.
Orchestration
The rules that decide what runs next and when a run stops, including loop limits, routing, hand-offs between agents and approval gates.
State
What an agent keeps between steps and between runs, such as message history, intermediate results and session data.
Checkpoint
A saved copy of an agent's state at one point in a run, used to resume after a pause, a crash or a restart.
Tracing
Recording each model call and tool call of a run as timed spans with inputs, outputs and token counts, so that the run can be inspected later.
Graph style
A way of building agents in which you declare the steps as nodes and the allowed transitions as edges over a shared state.
Role-based style
A way of building agents in which you describe several agents by role, goal and background and give them tasks, and the framework coordinates who works on what.
Code-first style
A way of building agents in which you create an agent object, pass plain functions as tools and let the model plan the steps inside a loop the framework runs.
Hard filter
A requirement that a candidate either meets or fails, such as the programming language, so that failing it removes the candidate whatever its other strengths.
Lock-in
The cost of leaving a framework, made up of the code, saved data and operating habits that only work with that framework.

2Explanation

Introduction

In The Agent Loop you wrote the loop yourself: call the model, run the tool it asks for, append the result, and repeat until it answers or a limit fires. That version needed nothing but a model provider's SDK. An agent framework is a library that gives you that loop ready-made, together with the parts that tend to grow around it.

If you have built a web application you have met this choice before. You can answer HTTP requests with a bare handler function, or you can adopt a web framework that brings routing, sessions and logging and expects you to follow its conventions. Nobody asks whether web frameworks are good or bad. They ask whether this project needs what the framework brings and whether its conventions suit the team. The same two questions apply to agents.

What an agent framework brings falls into four groups:

  • State. Message history, sessions that survive a restart, checkpoints, and the ability to pause a run and resume it later.
  • Orchestration. The rules for what happens next: loop limits, routing, hand-offs between agents and approval gates.
  • Tracing. A record of every model call and tool call that you can inspect and export.
  • Integrations. Adapters for model providers, tool definitions, MCP servers and data stores.

The price is a dependency that sits between your code and the model. Anthropic's guide Building effective agents (opens in a new tab) grants that frameworks make the low-level work easier, and warns that their extra layers can hide the prompts and responses you need to see when debugging. Its advice is to start with the model API directly and, if you do adopt a framework, to understand the code underneath it. The guide dates from December 2024, and its page now carries a note that much of the tooling it describes has changed, so take its principle and not its list of tools.

This lesson gives you a method for the decision. You will see what the four groups look like in real products, learn the three orchestration styles (graph, role-based and code-first), place LangChain's prebuilt agents, LangGraph, CrewAI, Agno, Haystack, Strands Agents and the TypeScript framework Mastra in one comparison, score a shortlist, and find out where lock-in comes from. Product details were checked against each project's documentation on 11 October 2026. These libraries change quickly, so re-check the details and keep the method.

How it works

What a framework adds to the loop

The loop itself is small. The work around it is what grows. Two sources list that work from different angles. The Hugging Face Agents Course (opens in a new tab) identifies six features an agent needs from its library: a model engine, a list of tools, a parser that extracts tool calls, a system prompt that matches the parser, a memory system, and error logging with retries. The Strands Agents documentation, on a page called Choosing an Agent Foundation (opens in a new tab), lists ten jobs that a production agent tends to accumulate and marks nine of them as do-it-yourself for a hand-written loop (the tenth, model providers, is marked "per provider"). Sorted under this lesson's four headings, the ten jobs are:

GroupJobs on the Strands checklistWhat you write if you do it yourself
StateMemory and sessionsStorage for history, a checkpoint after each step, code to resume
OrchestrationLoop controls, multi-agent, streaming, guardrails and interventionsTurn and token limits, cancellation, routing, approval gates
TracingTracing, evaluationSpans around each model and tool call, an exporter, a test harness
IntegrationsTools and structured output, MCP, model providersSchemas from function signatures, an MCP client, one adapter per provider

That page is written by a framework vendor, so read it as an argument. Its test is still a fair one: count how many of these jobs your agent needs now and how many it will need soon. The page also says to keep your own loop when most of the following hold: one model from one provider, a handful of tools and a single agent, short or tightly scoped runs, minimal dependencies that matter more than features, and a wish for full control of the loop's shape.

Three styles of orchestration

Frameworks differ most in how they answer one question: who decides what happens next?

StyleYou writeWho picks the next step
GraphNodes (functions), edges between them and a shared stateYour edges. A node may ask a model to choose a branch
Role-basedAgents described by role, goal and backstory, plus the tasks they ownThe framework's process, which hands tasks to agents
Code-firstOne agent object, tools as plain functions, ordinary control flowThe model, inside a loop the framework runs

The fragments below follow each project's documentation and show how the styles look on the page. They were not executed for this lesson.

python
# Graph (LangGraph): every step and every edge is declared.
from langgraph.graph import StateGraph, MessagesState, START, END

def draft_reply(state: MessagesState):
    return {"messages": [{"role": "assistant", "content": "draft"}]}

graph = StateGraph(MessagesState)
graph.add_node(draft_reply)
graph.add_edge(START, "draft_reply")
graph.add_edge("draft_reply", END)
app = graph.compile()
python
# Role-based (CrewAI): an agent is described the way you would brief a colleague.
from crewai import Agent

analyst = Agent(
    role="Research Analyst",
    goal="Find and summarize information about specific topics",
    backstory="You are an experienced researcher with attention to detail",
)
python
# Code-first (Strands Agents): tools are functions and the model plans the steps.
from strands import Agent, tool

@tool
def letter_counter(word: str, letter: str) -> int:
    """Count occurrences of a letter in a word."""
    return word.lower().count(letter.lower())

agent = Agent(tools=[letter_counter])
agent("How many times does r appear in strawberry?")

A style is a default, not a fence. CrewAI's documentation tells you to start a production application with a Flow, an event-driven workflow that holds state and control logic, and to call a crew of role-playing agents from inside one of its steps. LangChain's create_agent is a code-first function whose agents run on LangGraph (opens in a new tab). Haystack lets an agent be one component of a fixed pipeline, or a pipeline be one tool of an agent. Choose the style that matches most of your task, then check that the framework lets you step outside it for the rest.

Where the named frameworks fit

Three things in the grid deserve a second look:

  • A prebuilt agent is still a framework choice. LangChain documents three levels: Deep Agents as a batteries-included harness, create_agent as a configurable tool loop, and LangGraph (opens in a new tab) for mixing fixed steps with agentic ones. Starting at the top still commits you to the runtime underneath.
  • Some frameworks are also platforms. Agno pairs its Python SDK with AgentOS, a runtime that serves your agents behind a FastAPI application. Strands states the opposite position: it runs as a library in your own process with no hosted control plane.
  • Language is a hard constraint. Mastra is a TypeScript framework. Strands ships Python and TypeScript SDKs, and LangChain documents a JavaScript createAgent. A TypeScript team therefore has several candidates, and a Python team has more.

A naming note on Strands: its Python quickstart now calls the SDK the Strands Harness SDK, while Anthropic's guide and the AWS announcement cited here use the name Strands Agents. The Python package is still strands-agents and the import is still strands. This lesson says Strands Agents for the project and its SDK.

Selection criteria, in order

Work through these in order. Each one can end the search early.

  1. Need. Count the jobs from the first table that the task needs now or within a few months. Few or none means the hand-written loop is still the right tool.
  2. Control. If the order of steps must be fixed in code, for audit or approval reasons, look at graph frameworks. If the work divides among specialists, look at role-based ones. Otherwise start code-first.
  3. Hard filters. Programming language, model providers, where the agent must run, licence, and the tracing backend you already operate. A candidate that fails one is out, and no score buys it back.
  4. Team fit. Can you print the exact prompt sent to the model? How many new concepts does a minimal agent need? How do you debug a step that went wrong?
  5. Stability. Release pace, how breaking changes are announced, whether migration guides exist, and whether the features you need are in the open-source library or only in the vendor's paid platform.

Then build the same thin slice in the top two candidates: one tool, one forced tool error and one pause. Two days of that tells you more than a comparison table.

Lock-in: what moves and what does not

Lock-in is the cost of leaving. It is not spread evenly across your code.

Usually portableUsually tied to the framework
Tools written as plain functionsState schemas and saved checkpoints
Prompts kept in your own repositoryGraph, flow or crew definitions
MCP serversHooks, middleware and callbacks
Traces emitted as OpenTelemetry spansTrace history and dashboards in a vendor console
Evaluation datasetsDeployment to the vendor's runtime

Two published migration guides show the right-hand column at work. In version 1, LangChain moved its prebuilt agent from langgraph.prebuilt.create_react_agent to langchain.agents.create_agent. The migration guide (opens in a new tab) lists a renamed prompt parameter, model hooks replaced by middleware, custom state restricted to TypedDict, and a streaming node renamed from agent to model. Microsoft's AutoGen migration guide (opens in a new tab) shows a subtler risk: agent code that looks almost identical in both frameworks while the defaults underneath differ.

Three habits keep the exit affordable:

  • Keep business rules and tools in plain functions, and wrap them for the framework in one thin module.
  • Emit traces in an open format. Strands and Haystack can send OpenTelemetry spans to a backend you choose, and LangSmith documents an OpenTelemetry mode for LangChain and LangGraph applications.
  • Pin versions, read the migration guide before every major upgrade, and write down what leaving would cost at the moment you make the decision.

Worked example: Scoring a shortlist for a refund-approval agent, then changing the task

A four-person Python team at an online retailer is building an agent that reads a refund request, looks up the order, checks the refund policy and proposes a refund. The scenario is invented. The framework facts come from the documentation cited in this lesson. The requirements are:

  • Refunds above a limit need a person's approval, which may arrive the next day, so a run must pause and survive a restart.
  • The policy check must always happen before a refund, and that order must be enforced in code.
  • Traces must reach the company's existing OpenTelemetry collector.
  • Models come from Amazon Bedrock today, and management wants the freedom to switch.

Step 1: is a framework needed at all? Of the ten jobs on the Strands checklist, the task needs five now (loop controls, tools, sessions with pause and resume, an approval gate, tracing) and one soon (a second provider). A hand-written loop would mean building all six, so frameworks go on the shortlist and the loop stays as the baseline.

Step 2: hard filters and style. Mastra is a TypeScript framework, so it fails the language filter. The task has one agent and nothing to divide among roles, so the role-based style has nothing to organise and CrewAI is set aside. That leaves the hand-written loop, LangGraph (graph) and Strands Agents (code-first). A real evaluation would also score create_agent, Agno and Haystack. They are left out here only to keep the table readable.

Step 3: score each requirement against the documentation. The rubric is 2 for documented and built in, 1 for documented but reached through a companion package or extra code, and 0 for something you write yourself.

CriterionHand-written loopLangGraphStrands Agents
Pause for approval, resume after a restart02: an interrupt saves state through a checkpointer and waits2: interrupts, persisted by a session manager
Step order enforced in code2: it is your code2: edges fix the order1: a hook can block a tool call, the model orders the rest
Traces to an OpenTelemetry collector01: through the LangSmith SDK's OpenTelemetry mode2: traces are built on OpenTelemetry
Switch model provider01: through LangChain's model interface2: the same agent code runs on any supported provider
Small framework surface in our code20: state, nodes and edges are all framework-shaped1: an agent object and a tool decorator, plus a hook

The evidence for the framework cells is in the LangGraph interrupts (opens in a new tab) page, the LangSmith OpenTelemetry (opens in a new tab) page, the LangChain overview (opens in a new tab) for the model interface, and the Strands pages on interrupts (opens in a new tab), traces (opens in a new tab) and model providers (opens in a new tab).

The first four rows rest on those pages. The last row is a judgement about how much framework-shaped code you would write and not a documented capability, so it is the least certain score in the table.

Step 4: weight the criteria and add up. Save this as score_frameworks.py. It needs only the Python standard library.

python
CRITERIA = ["pause_resume", "step_order", "otel_traces", "provider_switch", "small_surface"]

# Rubric: 2 = documented and built in, 1 = documented but needs a companion
# package or extra code, 0 = you write it yourself.
SCORES = {
    "Hand-written loop": [0, 2, 0, 0, 2],
    "LangGraph":         [2, 2, 1, 1, 0],
    "Strands Agents":    [2, 1, 2, 2, 1],
}

# One weight per criterion, in the same order as CRITERIA.
SCENARIOS = {
    "A  refund approval":           [4, 2, 2, 1, 1],
    "A2 same, step order weighs 5": [4, 5, 2, 1, 1],
    "B  FAQ answerer":              [0, 1, 2, 0, 7],
}


def total(scores, weights):
    return sum(score * weight for score, weight in zip(scores, weights))


for scenario, weights in SCENARIOS.items():
    best_possible = 2 * sum(weights)
    print(scenario)
    ranked = sorted(SCORES, key=lambda option: total(SCORES[option], weights), reverse=True)
    for option in ranked:
        points = total(SCORES[option], weights)
        print(f"  {option:<18}{points:>3} / {best_possible}  {points / best_possible:.0%}")

Edge cases and limitations

Code that looks the same can behave differently
Microsoft's migration guide shows an AutoGen agent and an Agent Framework agent created with nearly identical lines. The first stops after one tool iteration unless a setting is raised and keeps its own conversation history. The second keeps calling tools until it can answer and holds no history unless you pass a session. When you port or compare frameworks, test behaviour over two turns with a tool call, and do not rely on the code reading the same.
Default step limits differ by a factor of five
CrewAI documents a default of 20 iterations per agent before it must give its best answer. Haystack's Agent component documents a default of 100 steps. Neither number was chosen for your task, and the two count slightly different things. Set the limit explicitly from the number of steps successful runs take, and treat an inherited default as a missing configuration.
A resumed run repeats code that ran before the pause
LangGraph's interrupts page states that on resume a node restarts from its beginning, so any code before the interrupt call runs again. The Strands interrupts page warns that an `AfterToolsEvent` hook with side effects can run more than once for one assistant message, and says a `BeforeToolsEvent` hook runs again on resume. Sending an email or charging a card before the pause point would happen twice. Put side effects after the approval, or make them safe to repeat.
Tracing can be off, or empty of content, until you configure it
Haystack states that it never enables tracing automatically and that recording component inputs and outputs is disabled by default to protect sensitive data. CrewAI uploads a trace only after an authenticated export or explicit consent. A demo that shows rich traces does not mean your production configuration records them. Verify by forcing a failure and looking for the failing call in your own backend.
A prebuilt agent is a graph underneath
LangChain's create_agent runs on LangGraph, so graph details reach your code even if you never draw a graph. The version 1 migration guide lists a streaming node renamed from agent to model. Code that filters streamed events by the old node name would keep running and match nothing. When you use a prebuilt layer, learn enough of the layer below to read its node names, state keys and checkpoints.
A migration guide's compatibility table can date
The model client table in Microsoft's AutoGen guide, last updated in August 2026, lists Anthropic and Ollama clients as available in AutoGen and as planned in Agent Framework. Microsoft's own Anthropic provider page for Agent Framework, updated in October 2026, now documents a Python client, installed as a pre-release package. A team that trusted the table alone could rule out a framework that already supports its provider. A team that never checked could begin a migration that one missing integration then blocks. Check provider, tool and storage support for your exact setup on the target framework's current pages, and note each package's release status, before you estimate the move.

When to use it, and when something simpler is enough

Use it when

  • The agent must pause for a person and resume after a restart, and you would otherwise write and test checkpointing yourself.
  • The same agent has to run on more than one model provider, or you expect to switch provider within the life of the project.
  • Several agents or a fixed multi-step flow must be coordinated, and you need one trace that covers all of them.
  • Several people build agents in the same organisation and need shared conventions for tools, state and tracing so that the agents can be maintained by anyone on the team.

Think twice when

  • One model from one provider, a handful of tools, a single agent and short runs. The loop from the previous lesson is enough and has no dependency to maintain.
  • You cannot yet say what your own loop sends to the model at each step. Learn that first, then adopt a framework.
  • The runtime is constrained, such as an edge function or a library you ship to others, and every added dependency is a real cost.
  • The control flow is unusual enough that you would spend your time working around the framework's abstractions.

A simpler alternative. The hand-written loop against the provider's SDK, as built in The Agent Loop. Anthropic recommends starting there because many patterns take only a few lines of code. It stops being enough when you catch yourself writing the same support code a second time, such as a second token counter or a second provider adapter. The Strands documentation names that moment as the signal to reconsider.

Key takeaways

  • A framework adds four things to the agent loop: state, orchestration, tracing and integrations. Count how many of them your task needs before you compare products.
  • Graph frameworks fix the order of steps in code, role-based frameworks divide work among described agents, and code-first frameworks let the model plan inside a loop that the framework runs.
  • Apply hard filters such as language and model provider first, then score the survivors against weighted requirements and check how easily the ranking flips.
  • The same score table gives different winners for different tasks, so your requirements and their weights matter more than any general ranking of frameworks.
  • Tools, prompts and OpenTelemetry traces usually move between frameworks, while state schemas, checkpoints and orchestration code do not.
  • Start with a hand-written loop, adopt a framework when you catch yourself rebuilding one, and record an exit plan and a review date with the decision.

Example 1 of 5

Elastic Security building three AI features on LangChain, LangGraph and LangSmith

ElasticDocumented in an engineering article

Elastic's engineering post How we built Automatic Import, Attack Discovery, and Elastic AI Assistant using LangChain (August 2024), written by three authors, one of them from LangChain, describes the framework stack behind three generative AI features of the Elastic Security product. [25][11][14]

The problem

Security analysts spend time on tasks that the three features are meant to shorten: writing queries in Elastic's ES|QL language, identifying and describing attacks, and building a data integration from sample data. Each feature needs reasoning over the customer's own security data. The product also lets customers connect the model of their choice, and the Elastic team needs to debug individual model requests, track performance and estimate cost.

Where this topic fits

The framework choice appears as a mapping from requirement to component. Open-source LangChain and LangGraph carry the reasoning workflows, with LangGraph graphs for the generation workflows. LangChain's model interfaces supply provider choice. LangSmith supplies tracing. Elasticsearch sits upstream as the retrieval store, and the finished workflows sit inside the Elastic Security product.

How it is applied, step by step

  1. The team states what each feature must do: generate ES|QL queries from natural-language questions, identify and describe attacks, and craft a data integration from sample data.
  2. For query generation it uses retrieval-augmented generation. A retrieval step, built on a modified Elasticsearch vector store component for LangChain, fetches the reference content the model needs.
  3. A LangGraph graph runs the generation workflow from end to end, so the order of retrieval and generation is declared in code and is not left to the model.
  4. Automatic Import uses a second graph that turns sample data into an integration package. The post describes this as building a stateful workflow.
  5. LangChain's chat model interfaces, together with Elastic's inference API, let customers connect the model of their choice.
  6. LangSmith records every request to a model, which gives the team the detail it needs to debug failures, follow performance and estimate cost.

Why this approach fits

Three of this lesson's criteria are visible in the post. Control: query generation for a security product should follow the same steps every time, and a graph makes that order explicit. Provider portability is close to a hard filter here, because customers decide which model they connect. Tracing is treated as a requirement from the start. A purely model-driven loop would have left the step order to the model, which is a poor fit when the output is a query an analyst will run against production data.

Limitation or tradeoff

The post is from 2024, was co-written with the framework vendor and compares no alternatives, so it shows a fit and not a contest. The user figure it gives comes from a LangChain engineer's quotation. All three layers come from one vendor, which concentrates exit cost: orchestration, model interfaces and trace history would all have to move together. Any team on this stack also inherits its release cycle. The LangChain version 1 migration guide lists moved imports and renamed parameters that agent code written against the earlier prebuilt interface has to absorb. LangSmith does document an OpenTelemetry mode, which is the route to keeping traces in a backend you control.

What the sources document

  • The post says Elastic Security's integration uses open-source LangChain and LangGraph for context-aware reasoning in Elastic AI Assistant, Attack Discovery and Automatic Import, and LangSmith for detailed tracing of requests to LLMs so that the team can debug issues, track performance and estimate costs. [25]
  • For ES|QL generation the post states that Elastic AI Assistant uses retrieval augmented generation to give context to the chosen LLM, that LangGraph powers the end-to-end generation workflow, and that a modified Elasticsearch LangChain vector store component is part of the graph. It also states that Automatic Import uses LangGraph to generate the integration package. [25]
  • The post says Elastic Security users are free to integrate the generative AI features with their LLM of choice, citing Elastic's inference API and LangChain's chat model ecosystem, and it quotes a LangChain engineer saying the assistant had reached over 350 users in production. [25]
  • LangChain's version 1 migration guide states that the prebuilt agent moved from langgraph.prebuilt.create_react_agent to langchain.agents.create_agent, that the prompt parameter was renamed to system_prompt, and that pre-model and post-model hooks were replaced by middleware. [11]
  • LangSmith's documentation describes an OpenTelemetry integration for LangChain and LangGraph applications that is enabled with the LANGSMITH_OTEL_ENABLED environment variable, and a setting that sends traces only to another OpenTelemetry endpoint. [14]

Example 2 of 5

AWS's Amazon Q Developer teams building Strands Agents after complex frameworks got in the way

Amazon Web ServicesDocumented in an engineering article

The AWS Open Source Blog post Introducing Strands Agents, an Open Source AI Agents SDK (May 2025) is written by an AWS senior principal engineer. It explains why the author's team and the Amazon Q Developer teams built a model-driven SDK and names AWS teams that run it in production. [4][5][6][7][8]

The problem

The author's team began building agents in early 2023, when models needed elaborate prompt instructions, response parsers and orchestration logic to use tools reliably. They relied on complex agent framework libraries for that scaffolding, and it still took months of tuning to make an agent ready for production. As models gained native tool use and reasoning, the post says, the team realised it no longer needed such complex orchestration, and some of those libraries started to get in the way of using what newer models can do.

Where this topic fits

This is a decision about orchestration style. The post contrasts frameworks that require developers to define complex workflows with a model-driven approach in which the model directs its own steps. In the Strands design an agent is a model, a list of tools and a prompt, the SDK runs the loop, and the same agent can be deployed behind an API or run locally.

How it is applied, step by step

  1. The team observes that scaffolding built for earlier models, such as prompt instructions for tool use and response parsers, no longer pays for itself once models call tools natively.
  2. It reduces the definition of an agent to three things written in code, namely a model, tools and a prompt.
  3. The SDK runs the loop: it calls the model with the context and the tool descriptions, executes the tool the model selects, returns the result and repeats until the task is complete.
  4. Behaviour is customised through tools, not workflow definitions. Even multi-agent patterns such as workflow, graph and swarm are offered as tools that the model may decide to use.
  5. Model access goes through a provider interface, so the same agent code can run on Amazon Bedrock, the Anthropic API, a local Ollama model and others.
  6. Telemetry is emitted with OpenTelemetry, so traces can go to any compatible backend the team already operates.

Why this approach fits

When a model reliably plans and calls tools, workflow code repeats work the model already does, and it has to be revisited every time a stronger model arrives. A thin loop improves as models improve. A developer assistant also receives open-ended requests, so the number and order of steps cannot be drawn as a fixed graph in advance. Both points favour the code-first, model-driven style.

Limitation or tradeoff

The change from months to days and weeks is the team's own description. It is not a measured comparison, and the post does not name the frameworks the team moved away from or say that every team replaced an earlier framework. The source is also the framework's own announcement. Model-driven control gives up explicit step order: where a step must be gated, you add it back with hooks and interrupts, which the Strands documentation covers. The approach depends on the quality of the model, so a weaker or local model may need more structure than this style provides.

4Common mistakes

  1. Choosing the framework with the most stars or tutorials before writing down what the task requires.

    Why it causes problems
    Popularity says nothing about whether you need durable pauses, a fixed step order or a particular language. Teams end up with a graph runtime around a three-tool question answerer, or with a model-driven loop where an auditor needs a fixed sequence.
    How to recognise it
    The decision document has no list of required jobs and no rejected candidates, or its reasons would apply equally well to any other project.
    How to fix it
    List the jobs needed now and soon, apply the hard filters, score at least two candidates plus the hand-written loop, and keep the table with the decision.

  2. Adopting a framework before you have written and traced a loop yourself.

    Why it causes problems
    When a run misbehaves you cannot tell whether the cause is your prompt, your tool, or a prompt and a default that the framework added. Anthropic's guide names incorrect assumptions about what is under the hood as a common source of error.
    How to recognise it
    Nobody on the team can show the exact request that the framework sent to the model for a given step.
    How to fix it
    Build the hand-written loop once for the same task. Then turn on the framework's debug output or tracing and compare the two requests line by line.

  3. Writing business rules inside framework constructs such as node functions, hooks or decorated tools.

    Why it causes problems
    Every rule becomes part of a future migration. The LangChain version 1 guide shows hooks replaced by middleware and state types narrowed, and a change of that kind touches every place that used them.
    How to recognise it
    Framework imports appear in most files, and a unit test cannot call a business rule without first constructing an agent or a graph.
    How to fix it
    Keep rules and tools as plain functions in their own module and wrap them in one adapter file, as in the second exercise.

  4. Defaulting to a multi-agent or role-based design for a job that one agent can do.

    Why it causes problems
    Each extra agent adds model calls, hand-off messages and places where context can be lost, and the roles have to be maintained as prose. The Marsh case study records that even with specialist agents the team anticipates the same routing problem if specialist agents ever number a hundred.
    How to recognise it
    Agents whose only action is to pass the previous agent's output along, or traces in which most tokens are spent on coordination.
    How to fix it
    Start with one agent and its tools. Split into roles only when one agent's tool list or instructions have grown too large for it to choose from reliably.

  5. Leaving step limits, tracing and content logging at the framework's defaults.

    Why it causes problems
    Defaults differ widely. CrewAI documents 20 iterations per agent and Haystack documents 100 steps, and Haystack leaves tracing off until you enable it. A default you never read becomes an unplanned cost or a blind spot in production.
    How to recognise it
    The code contains no explicit limit and no tracing configuration, and nobody can state the values currently in effect.
    How to fix it
    Set limits and tracing explicitly in code, with values taken from measured runs, and add a test that forces the limit to fire.

  6. Upgrading across a major version without reading the migration guide, or leaving versions unpinned.

    Why it causes problems
    Renamed parameters and changed defaults can alter behaviour without raising an error. A streaming node renamed from agent to model, for example, leaves a filter on the old name matching nothing.
    How to recognise it
    A dependency file with open version ranges, and behaviour that changes after a fresh install with no change to your own code.
    How to fix it
    Pin exact versions, upgrade on a branch, read the guide for renamed and removed items, and compare traces from before and after the upgrade.

Exercise 2

Write a tool once and adapt it to two framework shapes

CodingIntermediateAbout 45 min (estimate)Hypothetical scenario

Frameworks ask for tools in different shapes. To keep a business rule portable, write it once as a plain function and add one thin adapter per shape. Use only the Python standard library.

Start from this rule. It must not import or mention any framework:

python
def refund_decision(order_total: float, days_since_delivery: int) -> str:
    """Decide how a refund request is handled."""
    if days_since_delivery > 30:
        return "reject"
    if order_total > 100:
        return "needs_approval"
    return "auto_refund"

Write two adapters:

  • as_tool_spec(function) for a code-first framework. It returns a dictionary with the keys name, description, parameters (a dictionary from parameter name to type name, such as "float") and handler (the function itself). Build it from the function's signature and docstring so that nothing is typed twice.
  • as_graph_node(function, output_key) for a graph framework. It returns a function node(state) that reads the function's arguments from the state dictionary by parameter name and returns a partial update {output_key: result}. If a needed key is missing it raises KeyError and names the missing keys.

Then show that both adapters give the same decision for three cases, written as (order total, days since delivery): (249.0, 12), (249.0, 40) and (20.0, 3).

Requirements

  • The refund_decision function stays free of framework code and is not edited.
  • The as_tool_spec adapter derives the name, the description and the parameter types with the inspect module and does not repeat them by hand.
  • The as_graph_node adapter returns only the new key and leaves the caller to merge it into the state.
  • A missing state key raises KeyError with the missing names in the message.
  • The script prints the result of both adapters for all three cases and shows that they agree.

Expected behaviour

The tool spec prints as a dictionary whose parameters are order_total: float and days_since_delivery: int. Both adapters return needs_approval for (249.0, 12), reject for (249.0, 40) and auto_refund for (20.0, 3). Calling the node with a state that lacks days_since_delivery raises a KeyError that names it. Moving to another framework would mean writing one new adapter of about ten lines. The rule and its tests would stay as they are.

Hint 1

inspect.signature(function).parameters is an ordered mapping from each parameter name to a Parameter object, and its annotation attribute holds the type.

Hint 2

inspect.getdoc(function) returns the docstring with its indentation cleaned up.

Hint 3

Inside the node, build the keyword arguments with a dictionary comprehension over the parameter names.

Show solution

Save this as portable_tool.py and run python3 portable_tool.py.

python
import inspect


def refund_decision(order_total: float, days_since_delivery: int) -> str:
    """Decide how a refund request is handled."""
    if days_since_delivery > 30:
        return "reject"
    if order_total > 100:
        return "needs_approval"
    return "auto_refund"


def as_tool_spec(function):
    """Adapter for the code-first shape: describe the function as a tool."""
    signature = inspect.signature(function)
    parameters = {name: parameter.annotation.__name__
                  for name, parameter in signature.parameters.items()}
    return {"name": function.__name__,
            "description": inspect.getdoc(function),
            "parameters": parameters,
            "handler": function}


def as_graph_node(function, output_key):
    """Adapter for the graph shape: read inputs from state, return an update."""
    names = list(inspect.signature(function).parameters)

    def node(state):
        missing = [name for name in names if name not in state]
        if missing:
            raise KeyError(f"state is missing {missing}")
        return {output_key: function(**{name: state[name] for name in names})}

    return node


if __name__ == "__main__":
    spec = as_tool_spec(refund_decision)
    print({key: value for key, value in spec.items() if key != "handler"})
    print(spec["handler"](order_total=249.0, days_since_delivery=12))

    node = as_graph_node(refund_decision, output_key="decision")
    state = {"order_total": 249.0, "days_since_delivery": 12, "customer": "C-17"}
    update = node(state)
    print(update)
    print({**state, **update})

    for order_total, days in [(249.0, 40), (20.0, 3)]:
        via_tool = spec["handler"](order_total=order_total, days_since_delivery=days)
        via_node = node({"order_total": order_total, "days_since_delivery": days})["decision"]
        print(order_total, days, via_tool, via_node, via_tool == via_node)

    try:
        node({"order_total": 20.0})
    except KeyError as error:
        print("KeyError:", error)

What to notice:

  • The rule has no framework in it. refund_decision can be unit-tested with three plain calls, and it would survive any migration untouched.
  • Each adapter is short and knows one shape. as_tool_spec builds the description a code-first framework wants from the signature, in the way real frameworks derive tool schemas from type hints and docstrings. as_graph_node maps state keys to arguments and returns a partial update, which is the contract a graph node follows.
  • The node returns only its own key. The caller merges the update into a new state with {**state, **update}, so the original state is not modified.
  • Switching framework means writing one more adapter. That adapter is the whole exit cost for this tool. The same cannot be said for orchestration and state, which is why those two deserve the most attention when you choose.

With a real framework the adapter becomes a line or two, such as applying the framework's tool decorator to refund_decision in the adapter module and leaving the definition alone.
