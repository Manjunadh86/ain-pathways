Agent Deployment Architecture

Agent deployment architecture is the set of runtime services around an agent loop that let it serve many users in production: isolated sessions, durable state, long-running execution, identity and secrets, a governed path to tools, and a way to scale. You either assemble these on infrastructure you operate or rent them from a managed runtime.

1Overview

Why it matters

An agent that works in a notebook has one user, one working directory and your own credentials. In production the same loop becomes a long-lived process that runs actions chosen by a model, keeps state between turns, and holds access to other systems. Runs can last minutes or hours, which is longer than a typical web request. When the surrounding architecture is missing, the failures are concrete: a deploy or scale-down kills sessions that were half finished, one customer's files or settings turn up in another customer's session, a prompt-injected agent reads an API key out of its own environment, and a standalone agent server that scales to zero may lose tasks.

Anyone who ships an agent beyond a demo makes these decisions, either deliberately or by default: engineers choosing between their framework's hosting and a cloud runtime, forward deployed engineers placing an agent inside a customer's network, and reviewers asking where state and secrets live. The choice between running the runtime yourself and renting it decides who patches it, where the data sits, and which failures you inherit.

Key terms

Session
One conversation or task together with its event history, working files and the compute that runs it. Platforms key it differently (a session ID, a LangSmith thread ID, a Cloudflare agent name), and state and routing attach to that key.
Harness
The program that runs the agent loop: it calls the model, routes tool calls to the right place and feeds the results back. The Agent Loop lesson builds one.
Sandbox
An isolated execution environment, such as a container or microVM, where model-chosen commands and code run with limited files, network access and privileges.
microVM
A small virtual machine with its own kernel, far lighter than a traditional VM. AgentCore Runtime gives each session one, and Firecracker is an example of the technology.
Session store
Durable storage outside the harness and the sandbox that records what happened in a session, so a replacement harness can pick up where a failed one stopped.
Checkpoint
A saved snapshot of an agent run's state, written as the run progresses so that an interrupted run can resume from the last snapshot instead of from the beginning.
Credential proxy
A service outside the agent's boundary that adds API keys or tokens to outgoing requests, so the agent can make a call without ever holding the secret.
Tool gateway
One governed endpoint through which agents reach tools. It authenticates callers, translates protocols such as MCP, injects credentials and can enforce policy.
Workload identity
An identity issued to a program, here an agent, rather than to a person. Other services can verify it and grant it specific permissions.
Session affinity
Routing every request of a session to the same worker so that in-memory state stays valid. Also called sticky routing.

2Explanation

Introduction

In The Agent Loop you wrote a loop that calls a model, runs the tool it asks for and repeats. On your laptop that loop has one user, one working directory and your own credentials. Putting it in front of many users changes the problem, because the loop stops being the hard part. The hard part is everything around it.

Think of the web services you already know. A stateless HTTP handler can run on any server, finishes in milliseconds and loses nothing when a server restarts, so a load balancer can send any request anywhere. An agent session breaks each of those assumptions. It lasts a long time, it accumulates state, it executes actions chosen by a model that has read untrusted text, and it usually holds credentials for other systems.

A stateless handler is like a vending machine: any machine can serve any customer, and nothing is remembered between purchases. A hotel is a better picture of an agent session. Each guest (a session) gets a room of their own (a sandbox) and a key card that opens only that room (scoped credentials). The front desk (a tool gateway) makes calls to the outside world on the guest's behalf. A folio kept at the front desk (the session log) records what happened, so a new night manager can carry on where the last one stopped. Platforms build these parts differently, but nearly all of them provide them.

An agent runtime is the set of services that provides those parts. This lesson names six jobs it has to do: isolate sessions, keep state and memory, run for a long time, manage identity and secrets, give access to tools through a gateway, and scale. It then compares running these yourself (self-hosted) with renting them (managed), using the public documentation of AWS, LangChain, Anthropic, Cloudflare, Microsoft, Google and OpenAI. The vendors describe their own products, so treat the pages as accurate descriptions of design, not as independent comparisons.

Follow one request through the diagram now and come back to it at the end. Each box on the path is a place where one of the six jobs is done.

How it works

What changes when the loop becomes a service

Four properties of an agent session shape every design in this lesson:

  • Long-lived. A session spans many turns, and one run can take minutes or hours.
  • Stateful. It accumulates conversation history, files and in-process variables that the next turn needs.
  • Acting on model output. It runs shell commands, code and tool calls whose content was chosen by a model reading text that may be hostile (see Prompt Injection and LLM Security).
  • Credentialed. To be useful it holds access to databases, repositories and SaaS APIs.

The Claude Agent SDK hosting guide (opens in a new tab) makes the first two concrete. The SDK starts a claude subprocess for each session, and that subprocess owns a shell, a working directory and session files on disk. Each running agent is a long-lived process tied to local state, not a function call.

1. Session isolation

The unit of isolation is the session. In AgentCore Runtime (opens in a new tab) each session gets a dedicated microVM with its own compute, memory and filesystem; when the session ends, the microVM is terminated and its memory sanitized. In the Agent SDK each session is a subprocess, and sessions that need separate filesystems get a distinct working directory. LangSmith organises by thread instead: a worker executes up to 10 runs at once, so separation between threads is logical, not a per-session sandbox.

How strong the wall is depends on the technology. The Anthropic secure deployment guide (opens in a new tab) compares them: an OS-level sandbox runtime and plain containers share the host kernel; gVisor intercepts system calls in user space; a VM such as Firecracker runs its own kernel. Its table rates overhead from very low (sandbox runtime) to high (VMs).

Isolation does not decide who owns a session. AgentCore states that it does not enforce a mapping from users to session IDs, so your backend must keep that mapping and check it on every call. A session ID sent by a client is a handle, not proof of ownership.

2. State and memory

Three kinds of state have different lifetimes, and mixing them up is a common way to lose data:

KindExamplesLives as long as
Working stateProcess variables, files in the sandboxThe compute, by default
Session recordOrdered events, transcript, checkpointsUntil you delete it, if stored outside the harness
Long-term memoryPreferences and facts extracted across sessionsAcross sessions

By default the first kind is ephemeral. AgentCore's microVM is ephemeral unless you configure session storage, and the Agent SDK keeps transcripts and CLAUDE.md files on the container's disk, where they do not survive a restart, scale-down or move to another node. The second kind must live outside the harness: LangSmith's Agent Server writes checkpoints to PostgreSQL, the SDK offers a SessionStore adapter, and Anthropic's Managed Agents keeps an append-only session log outside the harness. The third kind has its own service, such as AgentCore Memory or the LangSmith store. Agent Memory covers how to design it.

The design rule that follows: keep the record outside the harness, so any harness can be replaced. Cloudflare takes the opposite route and puts state next to the compute, in a per-agent object with its own SQL storage.

3. Long-running execution

A request that stays open for an hour is fragile. Runtimes therefore accept work and let it continue in the background while clients stream or poll. Two documented shapes:

  • Session kept alive by health status. AgentCore Runtime stops a session after 15 idle minutes by default, unless the agent's /ping endpoint reports HealthyBusy. A microVM lives at most 8 hours (the default); Instances, a separate compute type, allow up to 14 days.
  • Durable queue and workers. In LangSmith's Agent Server an API server enqueues a run, a queue worker leases it, executes it and writes checkpoints, and at most one run executes per thread at a time.

Retries, idempotent tools and resuming after a crash get their own lesson: Durable Execution and Long-Running Agents. Even without them, put a bound on every run. The Agent SDK has no top-level session timeout, so its guide tells you to set a maximum turn count.

4. Identity and secrets

Identity points in two directions. Inbound is who may call the agent: the SDK guide says to authenticate at a gateway in front of the container so that the agent receives requests already authenticated. Outbound is what the agent may touch. Platforms give each agent its own workload identity (AgentCore Identity, a dedicated Microsoft Entra identity per Foundry hosted agent) and support OAuth flows for acting on a user's behalf. See Agent Identity, Permissions and Least Privilege.

Secrets deserve a firmer rule: keep them out of the place where model-chosen code runs. If an injected prompt persuades the agent to read its own environment, a key stored there is gone. Anthropic describes two patterns. In its secure deployment guide, a credential proxy outside the agent's boundary adds the key to outgoing requests, so the agent makes the call without seeing the key. In its Managed Agents engineering post, a vault holds OAuth tokens and a proxy fetches them for each tool call. One limit from the guide applies: a proxy that only forwards an encrypted HTTPS tunnel cannot add headers to it. Either route the call through a custom tool or MCP server, or use a TLS-terminating proxy.

5. Tool gateway

Letting every agent hold its own integration code and secrets for every API does not scale. A gateway gives agents one governed endpoint. AgentCore Gateway turns APIs and Lambda functions into MCP tools, authenticates callers, injects credentials per tool and offers semantic search over large tool sets. Foundry toolboxes expose a curated tool set behind one managed MCP endpoint with central authentication, governance and versioning. The price is one more hop and one more component to operate. MCP explains the protocol.

6. Scaling

The unit of scale is the session, not the request. For self-hosted agents the limit is usually memory, because every concurrent session is a process. The hosting guide gives the sizing formula:

agents per host=⌊Rhost−RoverheadRsession⌋\text{agents per host} = \left\lfloor \frac{R_{\text{host}} - R_{\text{overhead}}}{R_{\text{session}}} \right\rflooragents per host=⌊Rsession​Rhost​−Roverhead​​⌋

Measure RsessionR_{\text{session}}Rsession​ as peak memory of a representative session run to your target length. The guide's 1 GiB per agent is a starting floor, not a ceiling, so measured peaks can be much higher.

Route a session's requests to the same container, for example by consistent hashing on the session ID, as the guide suggests for long-running sessions; AgentCore does it with a session header. Scale the tiers separately when you can: LangSmith scales API servers on request volume and queue workers on pending runs, and each worker runs up to 10 runs at once by default. Do not run a standalone Agent Server in a serverless environment: its docs warn that scale-to-zero may cause task loss.

Self-hosted, managed or split

Three placement decisions are independent: where the loop (harness) runs, where the sandbox runs, and where the session state lives. Each can be yours or the provider's. Managed Agents, for example, hosts the loop but lets you run the sandbox yourself, and LangSmith's bring-your-own-cloud option puts the data plane in your virtual private cloud (VPC) while LangChain operates the control plane.

Vendors present the same spectrum. OpenAI's agents guide (opens in a new tab) compares an Agents API where OpenAI runs the harness and saves progress (low integration effort), an Agents SDK that runs inside your application (medium), and the Responses API where your application runs the harness (high). Microsoft's Foundry Agent Service (opens in a new tab) offers prompt agents, hosted agents (your code in a container) and a Responses API route for agents you already run. Google's Agent Runtime (opens in a new tab) deploys any containerized agent that meets its runtime contract. The pattern is consistent: the less you run, the less you control.

Choose by asking what you cannot compromise on. If data location or retention rules are fixed, you may need to run state or the sandbox yourself. If time to production matters more and a prebuilt loop is enough, a managed harness removes most of the work. If you need custom orchestration, a managed container runtime that accepts your code sits in between.

Worked example: A mini agent runtime that survives a crash and keeps tenants apart

This example is the smallest runtime that shows four of the six jobs: durable state outside the harness, resumption after a crash, session ownership, and a credential that never enters the agent's context. The model is a scripted stand-in so the output is deterministic; the store, proxy and harness are real. It needs only Python 3.9 or newer.

The scenario: tenant A asks about order 1001. Harness 1 calls a tool through the proxy and crashes after the result is logged. Harness 2 wakes from the log and finishes without repeating the call.

Save it as mini_runtime.py and run it with python3.

python
import json, re, sqlite3, tempfile, uuid
from pathlib import Path

SESSION_ID = re.compile(r"[A-Za-z0-9-]{8,64}")  # reject "../" and similar at the boundary


class SessionStore:  # durable, append-only event log shared by every harness
    def __init__(self, path):
        self.db = sqlite3.connect(path)
        self.db.execute("CREATE TABLE IF NOT EXISTS sessions (id TEXT PRIMARY KEY, tenant TEXT)")
        self.db.execute("CREATE TABLE IF NOT EXISTS events (sid TEXT, seq INT, kind TEXT, body TEXT,"
                        " PRIMARY KEY (sid, seq))")

    def create_session(self, tenant):
        sid = str(uuid.uuid4())
        self.db.execute("INSERT INTO sessions VALUES (?, ?)", (sid, tenant))
        return sid

    def check_owner(self, tenant, sid):
        row = self.db.execute("SELECT tenant FROM sessions WHERE id = ?", (sid,)).fetchone()
        if row is None or row[0] != tenant:
            raise PermissionError("unknown session or wrong tenant")

    def emit(self, sid, kind, body):
        (seq,) = self.db.execute("SELECT COUNT(*) FROM events WHERE sid = ?", (sid,)).fetchone()
        self.db.execute("INSERT INTO events VALUES (?, ?, ?, ?)", (sid, seq, kind, json.dumps(body)))
        self.db.commit()

    def events(self, sid):
        rows = self.db.execute("SELECT kind, body FROM events WHERE sid = ? ORDER BY seq", (sid,))
        return [(kind, json.loads(body)) for kind, body in rows]


class ToolProxy:
    """Outside the agent boundary: holds the credential and adds it to the real request."""

    def __init__(self, api_key):
        self._api_key, self.calls = api_key, 0

    def call(self, name, args):
        self.calls += 1  # a real proxy would send HTTPS here, with a header built from self._api_key
        status = {"1001": "delivered", "1002": "in transit"}.get(args["order_id"], "not found")
        return {"order": args["order_id"], "status": status}


def fake_model(events):
    """Scripted stand-in for an LLM: the next step depends on the event history alone."""
    done = [body for kind, body in events if kind == "tool_result"]
    if not done:
        return {"type": "tool_call", "name": "get_order_status", "args": {"order_id": "1001"}}
    return {"type": "final", "text": f"Order {done[0]['order']} is {done[0]['status']}."}


class Harness:  # holds no state between calls: everything is rebuilt from the session log
    def __init__(self, store, proxy, workspaces, crash_after=None):
        self.store, self.proxy, self.workspaces, self.crash_after = store, proxy, workspaces, crash_after

    def run(self, tenant, sid, user_text=None, max_steps=5):
        if not SESSION_ID.fullmatch(sid):
            raise ValueError("bad session id")
        self.store.check_owner(tenant, sid)
        workspace = self.workspaces / sid  # one working directory per session
        workspace.mkdir(parents=True, exist_ok=True)
        if user_text:
            self.store.emit(sid, "user_message", {"text": user_text})
        for _ in range(max_steps):
            events = self.store.events(sid)  # "wake": rebuild state from the log
            if events and events[-1][0] == "final":
                return events[-1][1]["text"]
            action = fake_model(events)
            if action["type"] == "final":
                self.store.emit(sid, "final", action)
                return action["text"]
            self.store.emit(sid, "tool_call", action)
            result = self.proxy.call(action["name"], action["args"])
            self.store.emit(sid, "tool_result", result)
            (workspace / "last_status.txt").write_text(result["status"])
            if self.crash_after == "tool_result":
                raise RuntimeError("simulated crash after tool_result")
        return "stopped: step limit"


root = Path(tempfile.mkdtemp())
store, proxy, work = SessionStore(root / "s.db"), ToolProxy("sk-demo-not-real"), root / "work"
a, b = store.create_session("tenant-a"), store.create_session("tenant-b")

try:
    Harness(store, proxy, work, crash_after="tool_result").run("tenant-a", a, "Where is order 1001?")
except RuntimeError as err:
    print("harness 1:", err)
print("log after crash:", [kind for kind, _ in store.events(a)])
print("harness 2 answer:", Harness(store, proxy, work).run("tenant-a", a))
print("tool calls made:", proxy.calls)
for tenant, sid in [("tenant-b", a), ("tenant-a", "../etc/passwd")]:
    try:
        Harness(store, proxy, work).run(tenant, sid)
    except (PermissionError, ValueError) as err:
        print(f"{type(err).__name__}:", err)
print("session B has no events:", store.events(b) == [])
print("session B has a workspace:", (work / b).exists())
print("secret in any log:", any("sk-demo" in json.dumps(store.events(s)) for s in (a, b)))

What this does not do. A directory is not a sandbox: real isolation needs a container, gVisor or a microVM. A crash between writing tool_call and tool_result would leave a call with no recorded outcome, and this harness would run the tool again, so tools must be safe to repeat. Durable Execution and Long-Running Agents covers that gap.

Edge cases and limitations

A stopped session keeps its ID but loses its memory
In AgentCore Runtime the compute stops after the idle timeout (15 minutes by default), the maximum lifetime or an explicit stop. The session ID stays valid, and the next call with it starts a new microVM with empty memory. The symptom is an agent that forgets everything after a quiet lunch hour. Anything that must survive belongs in AgentCore Memory or configured session storage, not in process variables or temporary files.
Two messages arrive for one session at once
A user who sends a second message while the first run is still working creates a race on the same history. LangSmith's queue allows at most one run per thread at a time, so something has to decide what happens to the new message: wait, interrupt the active run or be rejected. Decide that policy on purpose and test it, because a runtime that lets both run can interleave tool calls and corrupt the session record.
Managed does not automatically mean allowed
Managed services store session data on the provider's side. Anthropic's documentation says Managed Agents keeps conversation history, sandbox state and outputs server-side, and that it is not currently eligible for zero data retention (ZDR) or HIPAA business associate agreement (BAA) coverage. Check retention, residency and certification terms for the exact product before choosing it, and recheck when the product leaves beta, because such terms change.
Tokens usually cost more than containers
The Agent SDK hosting guide estimates that a minimally provisioned container costs roughly 0.05 US dollars per hour, while one long agent session can spend whole dollars in tokens. Tuning container packing before you have a turn limit and a per-session budget optimises the small number. Bound the loop first, as the Agent Loop lesson describes, then tune hosts.
Provisioning the sandbox first delays the first answer
If the harness waits for a container before it can call the model, every session pays the setup cost, even sessions that never need a shell. Anthropic reports that starting the model call first and provisioning a sandbox only when a tool needs one cut median time to first token by roughly 60 percent and the 95th percentile by over 90 percent. The same idea applies to your own design: lazy sandboxes, warm pools or both.

When to use it, and when something simpler is enough

Use it when

  • Several users or tasks run at the same time and the agent can read files, run code or call tools for them, so one session must not see another's data.
  • A run can outlast a normal HTTP timeout, or a deploy during a run must not lose the work.
  • The agent holds credentials for third-party systems, and those credentials must stay out of the environment where model-chosen code runs.
  • A customer, regulator or contract fixes where data may live, which forces a decision about running the state store or the sandbox yourself.

Think twice when

  • The agent makes a few tool calls inside a single request, uses no files and executes no code. A plain stateless endpoint is enough, and a runtime adds cost for nothing.
  • You are prototyping alone on a laptop, where isolation, queues and gateways add work without protecting anything yet.
  • A managed prompt-agent or workflow product already meets the requirement, so building and operating your own runtime would only add on-call burden.

A simpler alternative. One stateless HTTP service that runs a bounded agent loop (say, a maximum of 10 turns) inside the request timeout, with conversation history in the database you already run, keyed by conversation ID. Move to a real runtime when runs outlast the timeout, when the agent needs its own filesystem or shell, or when it holds credentials that a user could talk it into misusing.

Key takeaways

  • An agent session is long-lived, stateful, runs model-chosen actions and holds credentials, so it cannot be hosted like a stateless request handler.
  • A runtime has six jobs. It isolates sessions, keeps state outside the harness, runs work beyond one request, separates identity and secrets from model-run code, routes tools through a gateway, and scales per session.
  • Keep the session record outside both the harness and the sandbox, so either one can fail and be replaced without losing the session.
  • Keep secrets in a vault or credential proxy outside the sandbox, and let your backend rather than the client decide which user owns which session.
  • Self-hosted, managed and split deployments differ in who runs the loop, the sandbox and the state. Choose by data-location rules, the control you need over the loop, and the operating capacity you have.
  • Size self-hosted fleets from measured peak memory per session and bound every run with a turn limit, because tokens usually cost more than containers.

Example 1 of 5

Amazon Bedrock AgentCore Runtime: one microVM per session

Amazon Web ServicesDocumented in official docs

AWS documents AgentCore Runtime as a serverless host for agents and tools. The pages on isolated sessions, long-running agents and AgentCore Identity and Gateway describe how a session maps to a microVM, how it is kept alive or stopped, and where credentials and tools sit beside it. [1][2][3][4]

The problem

An agent session keeps state beyond the message history and performs privileged operations on a user's behalf through tools. If sessions share a process, one user's context or credentials can leak into another's, and because model behaviour is not deterministic, the boundary has to hold whatever the agent decides to do. Some work also continues for minutes or hours after the client has its first answer.

Where this topic fits

Runtime is the compute layer under the harness. The application's backend chooses a runtimeSessionId for each conversation and sends it with every call, and Runtime routes calls with that ID to the same microVM. Memory, Identity and Gateway are separate services that sit beside it.

How it is applied, step by step

  1. The application backend authenticates the user, chooses a session ID of at least 33 characters for each conversation, and records which user owns it.
  2. The first call with a new ID makes Runtime start a dedicated microVM with its own compute, memory and filesystem, and the agent code runs inside it.
  3. Later calls carry the same ID in the session header, so they reach the same microVM and still see the earlier in-memory context.
  4. Agent code that starts background work reports HealthyBusy from its ping endpoint, which keeps the session alive past the idle timeout.
  5. When the session stops (idle timeout, maximum lifetime, explicit stop or failed health check) the microVM is terminated and its memory sanitized. Anything durable must already be in AgentCore Memory or session storage.
  6. The next call with the same ID starts a fresh microVM with empty memory.

Why this approach fits

A separate microVM per session gives each user their own compute, memory and filesystem regardless of what the model chooses to run, so the isolation guarantee does not depend on prompt quality. A managed service saves you from building and patching a fleet of sandboxes, and the ping contract lets long jobs continue without holding a client connection open.

Limitation or tradeoff

AgentCore does not map users to sessions, so the application must, or one user could call another's session ID. State is ephemeral by default, so durable facts need Memory or session storage. The ping contract has a trap: the documentation warns that a time_of_last_update that changes on every ping prevents the idle timeout from ever firing, so sessions linger until the maximum lifetime and can exhaust the session quota.

What the sources document

  • Each session gets a dedicated microVM with isolated compute, memory and filesystem; after the session the microVM is terminated and its memory is sanitized. [1]
  • AgentCore does not enforce session-to-user mappings. The client backend is expected to maintain them and to manage limits such as the number of sessions per user. [1]
  • Session compute is ephemeral by default. Session storage can persist filesystem data across stop and resume, and AgentCore Memory holds conversation history and learned preferences beyond the session. [1]
  • Sessions stop after 15 minutes of inactivity and 8 hours of lifetime by default, and an agent that answers its ping with HealthyBusy stays alive beyond the idle timeout. [1][2]
  • AgentCore Identity keeps OAuth tokens and API keys in an encrypted token vault, and Gateway converts APIs and Lambda functions into MCP-compatible tools while handling inbound and outbound authentication. [3][4]

The facts above come from the cited sources. The steps and analysis in this example are our explanation of how they fit together.

Example 2 of 5

LangSmith Agent Server: API servers, queue workers, Postgres and Redis

LangChainDocumented in official docs

LangChain documents the Agent Server that LangSmith Deployment runs for LangGraph agents, and a separate guide for deploying it standalone on your own infrastructure. The architecture page names the containers, the stores and the run lifecycle, and the hosting page lists who operates what in each mode. [6][7][8]

The problem

Agent runs take long enough that holding an HTTP request open is fragile. A worker may be restarted in the middle of a run, clients still want streamed output, and the same agent code must be deployable either in the vendor's cloud or inside a customer's own cluster.

Where this topic fits

The Agent Server is the self-hostable runtime around a compiled graph. API servers accept requests, a durable queue holds runs, workers execute the graph and write checkpoints, PostgreSQL stores threads, runs and checkpoints, and Redis carries streaming signals. The harness code is the graph you supply.

How it is applied, step by step

  1. A client asks an API server to create a run on a thread. The API server writes a pending run to the durable task queue and does not execute agent code itself.
  2. A queue worker picks the run up and acquires a lease on it. The queue lets at most one run execute for a given thread at a time.
  3. The worker loads the graph and executes it, writing checkpoints to PostgreSQL as it goes. The durability mode sets how often.
  4. Streaming events pass through Redis publish and subscribe to the API server, which forwards them to the client as server-sent events.
  5. If a worker is interrupted, the run can resume from the last checkpoint instead of starting again from the beginning.
  6. Operators scale API servers on request volume and queue workers on the number of pending runs. A worker runs up to 10 runs at once by default.

Why this approach fits

Separating the API tier from execution lets long runs continue without a held connection and lets each tier scale on the signal that matters to it. Because the record lives in PostgreSQL, the containers are interchangeable, which is what makes restarts and rolling deploys survivable. The same graph code can be deployed in LangChain's cloud, in your VPC or fully on your own infrastructure.

Limitation or tradeoff

When you self-host you operate PostgreSQL, Redis, upgrades and scaling yourself. LangChain says Kubernetes with its Helm chart is the tested production path and that other orchestrators leave gaps you must fill, such as queue autoscaling and graceful draining of in-flight runs. Standalone servers must not run in serverless environments. And with one run per thread, a second message for a busy thread cannot run in parallel with the first.

What the sources document

  • API servers handle requests but do not execute agent code. Queue workers listen to the durable task queue, execute the graph and write checkpoints, and the two pools scale independently. [6]
  • PostgreSQL stores assistants, threads, runs and, by default, checkpoints and the long-term store. Redis handles signalling, cancellation and streaming between API servers and workers and keeps only ephemeral data. [6]
  • The queue enforces at most one run per thread at a time, and each worker executes up to 10 runs concurrently by default. [6]
  • Standalone Agent Servers should not run in serverless environments because scale-to-zero may cause task loss. Kubernetes with the LangSmith Helm chart is the production path LangChain tests. [7]
  • LangSmith offers Cloud, bring-your-own-cloud (LangChain runs the control plane and you run the data plane in your VPC) and self-hosted modes. It also lists a common setup that pairs LangSmith Cloud with a Hybrid deployment, keeping agent workloads in your own infrastructure while traces and evaluations stay on LangSmith Cloud. [8]

Self-hosting the Claude Agent SDK: four session patterns and a credential proxy

AnthropicDocumented in official docs

Anthropic's hosting and secure-deployment guides for the Claude Agent SDK explain how to run the SDK's per-session subprocess in containers you operate, how to persist sessions across hosts, and how to keep credentials outside the agent's boundary. [9][10]

The problem

Each agent session is a subprocess that owns a shell, a working directory and transcripts on local disk. Different workloads need different container lifetimes: a one-off bug fix, an email agent that runs all day, a research session that sits idle for hours. Local state disappears with the container, and an agent that runs model-chosen commands should not be holding the keys to other systems.

Where this topic fits

The guides sit at the self-hosted end of the spectrum. You provide the container, routing, session storage and gateway, and the SDK supplies the loop. The session pattern you pick sets how long a container lives relative to the sessions it serves.

How it is applied, step by step

  1. Choose a session pattern: ephemeral (a container per task, destroyed afterwards), long-running (persistent containers that host many sessions), hybrid (short-lived containers that load history from a SessionStore) or multi-agent (several subprocesses in one container).
  2. Run the SDK in a sandboxed container whose outbound traffic goes through an egress proxy that allows listed domains, injects credentials and logs requests.
  3. Authenticate callers at a gateway in front of the container, so the agent only receives requests that are already authenticated.
  4. For sessions users will resume, mirror transcripts to durable storage with a SessionStore adapter, and resume by session ID on whichever container starts next. Memory files and working-directory artifacts need a volume or a separate sync.
  5. In a shared container, give each tenant its own working directory and config directory and skip filesystem-loaded settings and auto memory, so one tenant's context cannot leak into another's.
  6. Size hosts with the formula and pin each session to one container in long-running pools. Bound each run with a maximum turn count, because there is no session timeout.

Why this approach fits

A subprocess-per-session loop maps naturally onto a container per task or a pool of containers per user group, and the four patterns let you match container lifetime to the workload instead of paying for idle compute. Running it yourself keeps data, network paths and secrets under your control, which some customers require.

Limitation or tradeoff

All six runtime jobs are yours to build: routing, session storage, secrets, isolation hardening and scaling. The defaults are unsafe for multi-tenant use, and the guide lists known limitations: no top-level session timeout, memory growth in long sessions and no per-subagent wall-clock deadline. The SessionStore mirrors transcripts only, and mirror writes are best effort, so you have to alert on the mirror_error messages the SDK emits when a batch cannot be delivered.

What the sources document

  • The SDK spawns a claude command-line subprocess per session that owns the shell, the working directory and the transcripts on local disk. Transcripts, CLAUDE.md files and working-directory artifacts do not survive a container restart, scale-down or move to another node. [9]
  • The guide describes four session patterns: ephemeral, long-running, hybrid and multi-agent container. The hybrid pattern requires a SessionStore, because shutting down without one loses the transcript. [9]
  • The guide says to authenticate at a gateway in front of the agent container and to keep tool credentials out of the agent environment by routing outbound calls through a proxy that adds the credential. [9][10]
  • It suggests 1 GiB of RAM, 5 GiB of disk and 1 CPU per agent as a starting point and says Anthropic token cost typically exceeds container infrastructure cost by an order of magnitude or more. [9]
  • For multi-tenant containers it advises per-tenant working and config directories, skipping settings sources, and disabling auto memory so tenants do not share context. [9]

Example 4 of 5

Claude Managed Agents: a durable session log, a stateless harness and a replaceable sandbox

AnthropicDocumented in an engineering article

Anthropic's April 2026 engineering post explains why its hosted agent service splits an agent into a session, a harness and a sandbox. The Managed Agents documentation describes the resulting service: agents, environments that run in a managed cloud sandbox or a self-hosted one, sessions and events. [11][12]

The problem

The first design put the session, the harness and the sandbox in one container. A failed container lost the session, a stuck session could only be debugged from a shell inside a container that also held user data, untrusted generated code ran next to credentials, and customers who wanted Claude to reach resources in their own VPC had to peer networks or run the harness themselves.

Where this topic fits

This is a managed runtime in which the provider runs the loop, with two of its three parts replaceable. The sandbox can be an Anthropic cloud sandbox or one you host, and the session log is the durable record that lets any harness instance resume.

How it is applied, step by step

  1. The harness writes each event to the session log as it runs the loop, so the record lives outside the harness.
  2. The harness calls the sandbox like any other tool, with a name and an input that return a string. If the container dies, the harness sees a tool-call error and Claude can retry, which provisions a fresh container.
  3. If the harness crashes, a new one is started, reads the event log and continues from the last event.
  4. Credentials stay out of the sandbox. A repository token is used while the sandbox is set up, and OAuth tokens for MCP tools sit in a vault behind a proxy that attaches them to the call.
  5. Because the harness is stateless and not inside the container, many harnesses can start cheaply, and a sandbox is provisioned only when a tool call needs one.

Why this approach fits

Making each part replaceable turns failures into routine events: a lost container is a tool error and a lost harness is a restart. Keeping tokens unreachable from the sandbox is a structural fix, instead of relying on a model never choosing to read its own environment. Letting the sandbox live in the customer's network removes the need to peer networks with the provider.

Limitation or tradeoff

The design is specific to this provider, and the service is in beta behind a beta header. Managed Agents stores conversation history, sandbox state and outputs server-side, and its documentation says it is not currently eligible for zero data retention or HIPAA BAA coverage. The split also adds a service boundary between harness and sandbox to design and debug, and the time-to-first-token figures are Anthropic's own measurements of its own system.

What the sources document

  • Anthropic splits the service into a session (an append-only log of everything that happened), a harness (the loop that calls Claude and routes tool calls) and a sandbox (where Claude runs code and edits files), each replaceable without disturbing the others. [11]
  • In the first design all three shared one container, so a failed container lost the session. After the split, a failed container reaches the harness as a tool-call error, and a crashed harness is replaced and resumes from the session log. [11]
  • Tokens are kept unreachable from the sandbox: repository tokens are used when the sandbox is set up, and OAuth tokens for MCP tools are held in a vault behind a proxy that attaches them to the call. [11]
  • Anthropic reports that provisioning containers only when needed cut median time to first token by about 60 percent and the 95th percentile by more than 90 percent. [11]
  • An environment is either an Anthropic-managed cloud sandbox or a self-hosted sandbox. Event history is persisted server-side, and the service is in beta and not currently eligible for zero data retention or HIPAA BAA coverage. [12]

Cloudflare Agents: one Durable Object per agent identity

CloudflareDocumented in official docs

Cloudflare's Agents documentation describes hosting each agent as a Durable Object, a globally addressable, single-threaded object with its own storage. The agent class internals page and the Durable Objects overview explain addressing, state, hibernation and scheduling. [13][14][15]

The problem

Some products give every user, chat room or document its own agent, which means very many agents, each with its own state, live connections and scheduled work. A warm container for each of them is wasteful, and an external database plus a layer that rebuilds the session on every request is extra code to write and run.

Where this topic fits

Here the runtime merges the compute and state layers. The unit of isolation and of scale is the agent instance, addressed by name. The harness, tools and channels (chat, voice, email, Slack, webhooks) sit on top of this runtime layer.

How it is applied, step by step

  1. Each agent is addressed by a name. Requests for that name are routed to the same Durable Object instance, which is created implicitly on first access.
  2. The agent keeps state with setState, persisted in the instance's own SQL storage, and can query that storage directly. The object is single-threaded, which simplifies reasoning about concurrent requests to the same agent.
  3. WebSocket clients stay connected while the object hibernates when idle. Only state written with setState or SQL is documented to survive eviction, so a typical implementation treats in-memory variables as a cache.
  4. Scheduled tasks wake the agent later, with the schedules kept in SQL and driven by a single alarm.
  5. Scaling means addressing more names. Cloudflare says you can have millions of Durable Objects around the world, and its Agents overview claims scaling to tens of millions of instances.

Why this approach fits

When the natural unit is one stateful agent per identity, keeping state next to the compute removes the need to rebuild a session on every request, and an idle agent can hibernate instead of holding a process. Routing by name gives the session affinity that other designs have to build separately.

Limitation or tradeoff

State lives with the object, so work that spans many agents needs extra design. The programming model is specific to Cloudflare's runtime and its Workers environment, which is a different trust and tooling model from running arbitrary containers. The overview lists sandboxed code execution as one of the agent's tools, a capability separate from the object's state and scheduling. The figure of tens of millions of instances is Cloudflare's own claim.

What the sources document

  • Cloudflare says each hosted agent session has a durable identity, local SQL storage, real-time connections, scheduled work and recoverable execution, and that agents scale to tens of millions of instances. [13]
  • The Agent class is built on Durable Objects (through a Server base class). Durable Objects are globally addressable, single-threaded compute instances with key-value and SQLite storage. [14]
  • Agents are addressed by name through a URL scheme and a routing helper, and requests for a given name reach the same instance. [14]
  • A Durable Object stays alive while it handles requests and for several seconds after going idle before it hibernates. Objects are created implicitly on first access. [15]
  • Agent state is persisted in the instance's SQL table and survives Durable Object evictions when it is updated with setState. With hibernation on, which is the default, WebSocket connections stay open while the object sleeps. [14]

4Common mistakes

  1. Keeping the only copy of session state in the container's memory or disk

    Why it causes problems
    A restart, a scale-down, an idle stop or a move to another node erases the history. On AgentCore a stopped session keeps its ID but gets a fresh microVM, and on the Agent SDK the transcripts sit on the container's local disk. Users see an agent that forgets mid-task, and half-finished work is lost.
    How to recognise it
    Kill the container in the middle of a session, or wait out the idle timeout, then send the next message. If the agent has lost its history or its files, the state was local.
    How to fix it
    Write events to a session store outside the harness and the sandbox (a database, an object store or a SessionStore adapter), keep long-lived facts in a memory service, and make resuming from the store part of your test suite.

  2. Putting API keys in the agent's environment variables or mounted files

    Why it causes problems
    The agent can run commands, so anything in its environment is one successful prompt injection away from being read and sent elsewhere. Read-only mounts of a code directory can also expose files such as .env, ~/.aws/credentials or private keys.
    How to recognise it
    Run the commands env and ls -a ~ inside the sandbox, and list every mounted path. Any token, key file or credentials directory you find is reachable by model-chosen code.
    How to fix it
    Route outbound calls through a credential proxy or tool gateway outside the sandbox that adds the secret, keep OAuth tokens in a vault, and mount only the files the task needs.

  3. Treating a client-supplied session ID as proof that the caller owns the session

    Why it causes problems
    A user who learns or guesses another user's session ID can read their history or act with their permissions. AgentCore states that it does not enforce user-to-session mappings, so the check is yours.
    How to recognise it
    Authenticate as user B and send a request carrying one of user A's session IDs. If it works, ownership is not being checked. Short or predictable IDs make this easier to exploit.
    How to fix it
    Keep a table in your backend that maps authenticated users to session IDs, check it on every request, use long random IDs, and cap the number of sessions per user.

  4. Sharing a working directory, config directory or settings between tenants in one container

    Why it causes problems
    The Agent SDK reads settings and memory files from the filesystem by default, so in a shared container one tenant's instructions or remembered facts can end up in another tenant's prompt. This is a data leak without any attack.
    How to recognise it
    Run two tenants through the same container and look for files, memory entries or settings from the first in the second's context. Identical working directories in your logs are a warning sign.
    How to fix it
    Give each tenant its own working directory and config directory, skip filesystem-loaded settings, disable auto memory, apply per-tenant egress rules, or use a separate container per tenant when the data is sensitive enough.

  5. Leaving runs unbounded, or letting health reporting keep idle sessions alive

    Why it causes problems
    The Agent SDK has no top-level session timeout, so a looping agent keeps spending tokens. On AgentCore, a ping that always looks fresh prevents the idle timeout from firing, so sessions linger until the maximum lifetime and can exhaust the session quota.
    How to recognise it
    Chart session duration and tokens per session. Sessions that all end at the maximum lifetime, or a long tail of runs with hundreds of turns, point to missing bounds.
    How to fix it
    Set a maximum turn count and a token or cost budget per run, report busy only while work is really running and change the status timestamp only when the status changes, and stop sessions explicitly when a task completes.

  6. Sizing hosts from the idle baseline or from the 1 GiB starting figure

    Why it causes problems
    Memory grows with session length and tool activity. Hosts packed to the idle footprint run out of memory mid-session, the kernel kills agent processes, and users lose runs, as the plot of agents per host shows for larger per-session ceilings.
    How to recognise it
    Run a representative session to your target length under realistic tool load and record peak memory. Compare it with the figure you assumed, and look for out-of-memory kills in container metrics.
    How to fix it
    Take the measured peak as the per-session ceiling in the sizing formula, leave headroom for host overhead, cap session length or recycle long-lived processes, and re-measure when you change tools or models.

Exercise 1

Add a session lease and a recorded step limit to the mini runtime

CodingIntermediateAbout 40 min (estimate)Hypothetical scenario

Copy the mini_runtime.py code from the worked example. Keep the classes, replace the demo code at the bottom with your own checks, and make three changes.

  1. One run per session. Add a leases table keyed by session ID. Harness.run must take the lease before it writes anything and release it afterwards, even when the run crashes. If the session already holds a lease, raise RuntimeError("session busy"). LangSmith's queue enforces the same rule with at most one run per thread.
  2. A recorded step limit. When max_steps is used up, append a stopped event with the reason step_limit and return "stopped: step_limit". Calling run again on a stopped session must return the same text without calling the model or the tool.
  3. Checks. Write plain assert statements that prove both rules and that a crashed run releases its lease.

You need Python 3.9 or newer and nothing else.

Requirements

  • A second run on a session that already holds a lease raises a RuntimeError with the message "session busy" and writes no events.
  • The lease is released in a finally block, so a run that raises an exception does not lock the session.
  • With max_steps=1 a fresh session ends with a stopped event as its last event and the tool is not called again by later calls.
  • The checks print "check 1 ok", "check 2 ok" and "check 3 ok" and use no library beyond the standard library.

Expected behaviour

Running your file prints the three ok lines and exits without an assertion error. In check 1 the event list stays empty while the lease is held. After the lease is released, the run answers Order 1001 is delivered. and the proxy has been called once. In check 2 a second call to the stopped session leaves proxy.calls unchanged. In check 3 a run that crashed with the simulated error can be resumed afterwards.

Hint 1

A primary-key INSERT is an atomic test-and-set. Catch sqlite3.IntegrityError and turn it into the busy error.

Hint 2

Split run into a short outer method that validates, takes the lease and releases it in finally, and an inner method that holds the loop you already have.

Hint 3

Check for a stopped last event at the top of each loop iteration, next to the check for final.

Hint 4

To simulate another worker holding the lease in your test, call store.acquire(session_id) yourself before calling run.

Show solution

Add the table and two methods to SessionStore:

python
# in SessionStore.__init__
self.db.execute("CREATE TABLE IF NOT EXISTS leases (sid TEXT PRIMARY KEY)")

def acquire(self, sid):
    try:
        self.db.execute("INSERT INTO leases VALUES (?)", (sid,))
        self.db.commit()
    except sqlite3.IntegrityError:
        raise RuntimeError("session busy") from None

def release(self, sid):
    self.db.execute("DELETE FROM leases WHERE sid = ?", (sid,))
    self.db.commit()
