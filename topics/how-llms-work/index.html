How Large Language Models Work

A large language model (LLM) is a neural network trained on a very large amount of text to predict the next token, a word or piece of a word, given all the text so far. It writes a reply by predicting one token, adding it to the text and repeating.

1Overview

Why it matters

Most of the behaviour that surprises people in LLM products follows directly from the mechanism. The same prompt gives two different answers because the next token is drawn from a probability distribution. A reply cites a paper that does not exist because the model always produces a likely-looking continuation, whether or not it has anything to base it on. An assistant describes last year's software version as the latest because its training text ends at a fixed date. A chatbot repeats a mistake you corrected yesterday because nothing you type changes its weights.

If you build on these models, the mechanism tells you which problems a better prompt can fix, which need information supplied at request time, which need a check in code, and which no prompt will fix. People who skip it tend to treat the model as a database or a search engine, and then ship features that work in the demo and fail on the first question about something recent, rare or private.

Before you start

No prerequisites. You can start here.

What you will be able to do

  • Distinguish training from inference and say which of the two changes the model's weights.
  • Explain what pre-training and instruction tuning each contribute to a chat model.
  • Reproduce the next-token probabilities, sampled outputs and loss values of a tiny language model in Python.
  • Explain why identical prompts can give different outputs, why models hallucinate and what a knowledge cutoff implies.
  • Choose a fitting response to a hallucination or stale-knowledge risk, such as supplied context, retrieval, permission to abstain or verification.

Key terms

Token
A unit of text the model reads and writes. A token is often a word, part of a word or a punctuation mark.
Next-token prediction
The single task an LLM performs. Given a sequence of tokens, it outputs a probability for every token that could come next.
Parameters (weights)
The adjustable numbers inside the neural network. Training sets them, and together they determine every prediction the model makes.
Autoregressive generation
Producing text one token at a time, where each generated token is appended to the input before the next one is predicted.
Training
The process of adjusting the weights so that the model gives higher probability to the tokens that really come next in example text.
Inference
Using a trained model to produce output. The weights stay fixed, so nothing is learned.
Pre-training
The first and largest training stage, in which the model learns next-token prediction from a huge general collection of text.
Instruction tuning
Further training of a pre-trained model on examples of instructions and good responses, so that it answers requests instead of merely continuing text.
Hallucination
Output that reads as fluent and plausible but is false, or is not supported by the material the model was given.
Knowledge cutoff
The date at which a model's training data ends. The model has no information about anything after it unless that information is placed in the prompt.

2Explanation

Introduction

Your phone keyboard suggests the next word as you type. It looks at the last word or two and offers the words that most often followed them in text it has seen. A large language model (LLM) does the same job with far more to go on. It reads everything in the prompt, thousands of words if necessary, and it has been fitted to an enormous amount of text. GitHub's guide to prompt engineering, written from the experience of building Copilot, describes the model in exactly these terms (opens in a new tab): it is the suggested-next-word button above a phone keypad, at scale.

Two details turn that idea into the chat assistants you have used. First, the model does not predict whole words. It works in tokens, pieces of text that are often a word, part of a word or a punctuation mark (Tokens and Context Windows covers them). Second, the model predicts only one token at a time. To write a paragraph it predicts a token, adds that token to the end of the text and predicts again. Text produced this way is called autoregressive: each output becomes part of the next input.

Take the prompt The capital of France is. The model does not look the answer up. It produces a score for every token it knows, and the scores become probabilities: Paris very likely, a and the possible, banana close to impossible. A program outside the model then picks one token from that list. The good and the bad sides of LLMs both follow from this design:

  • The pick usually involves chance, so the same prompt can produce different answers.
  • The model always produces some likely-looking continuation, even when it has no basis for one. A fluent but false answer is called a hallucination.
  • The probabilities come from training text that ends on a certain date, the knowledge cutoff. The model knows nothing later than that unless you put it in the prompt.

This lesson explains where the probabilities come from (training), how they are used (inference), how a text predictor becomes an assistant that follows instructions (pre-training and instruction tuning), and what the three consequences above mean when you build on these models.

How it works

From text to a probability for every token

An LLM is a neural network: a very large formula with billions of adjustable numbers called parameters or weights. Its input is a sequence of tokens. Its output is one score, called a logit, for every token in its vocabulary (Llama 3, for example, has a vocabulary of 128K tokens). A function called softmax turns the scores into probabilities that are positive and add up to 1:

This matches the general definition in Google's introduction to the subject: a language model estimates the probability of a token or sequence of tokens (opens in a new tab) occurring within a longer sequence.

The scores come from a transformer, a network design in which every token of the prompt can influence the prediction (see Attention and Transformers). You do not need those internals here. Treat the model as a function: tokens in, one probability per possible next token out.

Inference: the generation loop

Inference means using a trained model. The weights are fixed and the network is run forward to get a prediction. Writing a reply repeats four steps:

  1. Run the model on all tokens so far to get the next-token probabilities.
  2. Pick one token.
  3. Append it to the sequence.
  4. Stop if the token is the special end-of-sequence token or a length limit is reached. Otherwise return to step 1.

The Hugging Face LLM Course calls this the decode phase, in which the model generates one token at a time (opens in a new tab). It is why replies stream out piece by piece, and why long outputs are slow: every output token is one more pass through the network.

Nothing is learned inside this loop. A model ID names a fixed set of weights. Anthropic, for instance, states that it does not update the weights of an existing model ID (opens in a new tab). A chat appears to remember earlier turns only because the application sends the whole conversation again with every request.

Why outputs are probabilistic

Step 2 is where chance enters. Always taking the top token (greedy decoding) is one option. Chat systems usually sample instead: they draw a token at random in proportion to the probabilities, so Paris is picked about 83 times in 100 and the about 11. A different pick early on changes the input to every later step, so two runs can drift far apart. Settings such as temperature reshape the distribution before the draw; Sampling Parameters covers them.

Do not expect exact repeatability even at the most conservative settings. Anthropic's glossary notes that even with temperature set to 0, results will not be fully deterministic (opens in a new tab). Write tests and downstream code that tolerate variation in wording.

Training: where the probabilities come from

Training is the process that sets the weights. For a language model it needs no human labels, because, as the Hugging Face guide to causal language modeling puts it, the next word is the label (opens in a new tab):

  1. Take a piece of real text and hide everything after some position.
  2. Ask the model for its next-token probabilities.
  3. Read off the probability ppp it gave to the token that really came next, and compute the loss L=−ln⁡pL = -\ln pL=−lnp.
  4. Nudge every weight slightly in the direction that lowers the loss (see Loss Functions and Gradient Descent).
  5. Repeat over an enormous amount of text.

With the table above, if the real next token is Paris, the loss is −ln⁡0.831=0.185-\ln 0.831 = 0.185−ln0.831=0.185 and the weights barely move. If the real text had continued with Lyon, the loss would be −ln⁡0.01522=4.185-\ln 0.01522 = 4.185−ln0.01522=4.185 and the correction would be much larger. Nobody writes grammar or facts into the model. Spelling, syntax, common knowledge and patterns of argument end up in the weights because each of them helps predict the next token.

Pre-training and instruction tuning

Chat models are trained in at least two stages.

Pre-training runs the recipe above on a huge general corpus. The Llama 3 model card reports over 15 trillion tokens (opens in a new tab) of publicly available data. The result is a base model, which continues documents. Give a base model a question and it may answer, or it may write three more questions, because both are plausible continuations. In the words of Anthropic's glossary, pre-trained models are not inherently good at answering questions or following instructions.

Instruction tuning is further training (fine-tuning) of the base model on examples of the wanted behaviour: prompts paired with good responses. Many labs add reinforcement learning from human feedback (RLHF), in which people rank alternative outputs and the model is pushed towards the preferred ones. The data is tiny next to pre-training. The same model card mentions public instruction datasets plus over 10 million human-annotated examples.

The task itself does not change. A conversation is flattened into one token sequence, with control tokens marking who is speaking, and the model continues it. The Hugging Face documentation shows such a template and stresses that chat models are still language models that continue a sequence of tokens (opens in a new tab):

text
<|im_start|>user
Can I ask a question?<|im_end|>
<|im_start|>assistant

The sequence ends where the assistant's turn begins, so the most probable continuation is an assistant-style reply. When the model emits the end-of-turn token, the loop stops.

Hallucination

A hallucination is output that is fluent and plausible but false, or that contradicts the material the model was given. It follows from the mechanism in three ways:

  • The model must always continue. Every step produces a distribution and something is picked. The words "I don't know" appear only when those tokens are likely enough to be picked.
  • Training rewards guessing. Kalai and colleagues argue that training and evaluation procedures reward guessing over acknowledging uncertainty (opens in a new tab), in the way an exam with no penalty for wrong answers rewards a student for never leaving a blank.
  • Arbitrary facts leave weak traces. A birthday follows no pattern the model can learn, so the model can only recall it if it was seen. The same paper argues that the share of such facts that appear exactly once in the pretraining data puts a floor under how often a base model gets them wrong. It also reports asking a state-of-the-art open-source model for one author's birthday on three separate attempts and getting three different wrong dates.

Anthropic's interpretability researchers examined Claude 3.5 Haiku and found a circuit that is on by default and makes the model say it cannot answer (opens in a new tab). A "known entity" feature switches that circuit off for familiar names. The researchers trace some hallucinations to this feature firing for a name the model recognises but knows nothing more about. That matches everyday experience: models invent most readily about things that are half-familiar.

You reduce hallucination by changing which continuation is most likely. Put the source material in the prompt, say explicitly that "I don't know" is an acceptable answer, ask for supporting quotes, and verify the claims that matter. Retrieval-Augmented Generation builds on the first of these.

Knowledge cutoffs

Training stops on some date and the weights are frozen, so everything later is absent. The Llama 3 model card lists March 2023 for the 8B model and December 2023 for the 70B model. Anthropic's model table gives two dates per model, a training data cutoff and a reliable knowledge cutoff (opens in a new tab), defined as the date through which the model's knowledge is most extensive and reliable. Three consequences matter in practice:

  • A model has no clock. It cannot know today's date unless the prompt states it.
  • It will describe the latest version of a library, a law or a product as of its cutoff, with no sign that the information is stale.
  • The gap is larger than it feels. Llama 3 8B was released in April 2024 with a cutoff of March 2023, so it was thirteen months behind on its first day.

The remedy is the same as for hallucination: supply current information at inference time through the prompt, retrieval or a search tool.

Worked example: A six-sentence language model you can train, sample from and catch hallucinating

A real LLM has billions of weights, so you cannot watch it learn. This example shrinks everything until you can. The training text is six sentences, the model is a table of counts, and the context is at most three tokens. The two stages are the real ones: train on text, then run inference one token at a time. Save the code as tiny_lm.py. It needs only the Python standard library (3.8 or later).

python
import math
import random
from collections import Counter, defaultdict

CORPUS = [
    "the capital of france is paris .",
    "the capital of italy is rome .",
    "the capital of spain is madrid .",
    "paris is a city in france .",
    "rome is a city in italy .",
    "the capital of france is paris .",
]
MAX_CONTEXT = 3   # the model sees at most the 3 previous tokens
UNSEEN = 1e-9     # probability given to a token never seen after a context


def tokenize(text):
    return ["<s>"] + text.split()


def train(sentences):
    """Training: count which token follows each context of 0 to 3 tokens."""
    counts = defaultdict(Counter)
    for sentence in sentences:
        tokens = tokenize(sentence)
        for i in range(1, len(tokens)):
            for n in range(min(MAX_CONTEXT, i) + 1):
                counts[tuple(tokens[i - n:i])][tokens[i]] += 1
    return counts


def next_token_probs(counts, tokens):
    """One inference step: a probability for each candidate next token."""
    for n in range(min(MAX_CONTEXT, len(tokens)), -1, -1):  # longest context first
        context = tuple(tokens[len(tokens) - n:])
        if context in counts:
            total = sum(counts[context].values())
            return {t: c / total for t, c in counts[context].most_common()}, n


def generate(counts, prompt, rng=None, max_tokens=8):
    """The inference loop: predict, pick, append, repeat."""
    tokens = tokenize(prompt)
    for _ in range(max_tokens):
        probs, _ = next_token_probs(counts, tokens)
        if rng is None:
            token = max(probs, key=probs.get)                                  # greedy
        else:
            token = rng.choices(list(probs), weights=list(probs.values()))[0]  # sample
        tokens = [*tokens, token]
        if token == ".":                                                       # stop token
            break
    return " ".join(tokens[1:])


def loss(counts, sentence):
    """Average of -ln p(correct next token) over one sentence."""
    tokens = tokenize(sentence)
    terms = [-math.log(next_token_probs(counts, tokens[:i])[0].get(tokens[i], UNSEEN))
             for i in range(1, len(tokens))]
    return sum(terms) / len(terms)


def show(counts, prompt):
    probs, n = next_token_probs(counts, tokenize(prompt))
    listed = ", ".join(f"{t} {p:.3f}" for t, p in probs.items())
    print(f"{prompt!r} -> matched {n} tokens: {listed}")


if __name__ == "__main__":
    model = train(CORPUS)
    show(model, "the capital of")
    show(model, "the capital of italy is")
    show(model, "the capital of germany is")

    for prompt in ("the capital of", "the capital of germany is"):
        print("greedy:", generate(model, prompt))
        for seed in (1, 2, 5):
            print(f"seed {seed}:", generate(model, prompt, random.Random(seed)))

    new_fact = "the capital of germany is berlin ."
    print(f"loss before: {loss(model, new_fact):.3f}")
    retrained = train([*CORPUS, new_fact])
    print(f"loss after:  {loss(retrained, new_fact):.3f}")
    print("greedy:", generate(retrained, "the capital of germany is"))

Read the output in four parts.

  • Training built a probability table. Four training sentences contain the capital of, and france follows in two of them, so p=2/4=0.5p = 2/4 = 0.5p=2/4=0.5. italy and spain get 1/41/41/4 each.
  • Sampling makes outputs differ. Greedy decoding always completes the capital of with France. Seeds 1, 2 and 5 give France, Spain and Italy. All three sentences are true. They are draws from one distribution, and none of them is "the" answer.
  • An unknown fact still gets a fluent answer. Germany never appears in the training text. No context of three or two tokens matches of germany is, so the model falls back to what usually follows is: paris and a (2 of 6 each), rome and madrid (1 of 6 each). It writes the capital of germany is paris . as smoothly as a true sentence. This is a hallucination in miniature. The model cannot output "unknown", because every step must pick some token and no training sentence ever admitted ignorance.
  • Only training changes what the model knows. Before the Berlin sentence is in the training data its loss is 6.535. Two of its seven tokens, germany and berlin, get the floor probability 10−910^{-9}10−9 and cost −ln⁡10−9=20.723-\ln 10^{-9} = 20.723−ln10−9=20.723 each: (0.405+0+0+20.723+1.946+20.723+1.946)/7=6.535(0.405 + 0 + 0 + 20.723 + 1.946 + 20.723 + 1.946) / 7 = 6.535(0.405+0+0+20.723+1.946+20.723+1.946)/7=6.535. After retraining with one extra sentence the loss is 0.278 and the greedy answer is berlin. No number of inference runs would have produced that change. The six original sentences are this model's knowledge cutoff.

A real LLM differs in two ways that matter. It stores weights, not counts, adjusted by gradient descent to lower the same loss, which lets it give sensible probabilities to contexts it never saw word for word. It also reads its whole prompt. Paste "Berlin is the capital of Germany" into a real model's prompt and it can use that sentence. The toy cannot, because it only looks up its last three tokens.

Edge cases and limitations

Identical requests give different answers even at temperature 0
Lowering the temperature makes the pick less random, but it does not make a hosted model a pure function. Anthropic's glossary states that even with temperature set to 0 the results are not fully deterministic and identical inputs may produce different outputs across API calls. Do not write tests that compare a reply to an exact string. Check properties instead, such as whether the output parses, contains the required fields or passes a rubric.
The model does not know today's date or how stale it is
A model's sense of the present is its training data. Asked for the current year or the newest version of a tool, it answers from that data unless the prompt says otherwise. Anthropic's published system prompt for the Claude apps handles this by inserting the current date and stating the model's cutoff in the prompt itself. If you call a model through an API, nothing does this for you, so add the date to your own system prompt whenever time matters.
Models from one family can have different cutoffs
A cutoff belongs to a specific set of weights. The Llama 3 model card lists March 2023 for the 8B model and December 2023 for the 70B model, although both were released together. Swapping a large model for a small one to save money can silently remove nine months of knowledge. Read the cutoff for the exact model ID you deploy, and re-check it when you change models.
A base model continues your question; it does not answer it
Open-weight models are often published in a base and an instruction-tuned variant, and an instruction-tuned model expects its own chat format. The Hugging Face documentation warns that without the tokens that open the assistant's turn a model may continue the user's message, and that the wrong control tokens make performance drastically worse. If replies ramble or the model writes the user's next line, check the variant and the chat template before you touch the prompt.
Supplying documents reduces hallucination but does not end it
Hallucination includes statements that contradict the context you supplied, and is not limited to invented facts from memory. A model can misquote a retrieved document or merge two sources. Anthropic's guidance on reducing hallucinations lists grounding in quotes and citations, then adds that these techniques do not eliminate hallucinations entirely and that critical information should always be validated. Treat grounding as a way to make errors rarer and checkable.
One wrong token can commit the rest of the reply
Generation only moves forward. A sampled token is appended and becomes part of the input, so the model continues in a way that is consistent with it. If an early token starts a wrong name or number, the following tokens tend to elaborate on it, because a coherent continuation is more probable than a reversal. This is why one reply can be wrong from start to finish while a second attempt at the same prompt is right, and why comparing several samples can expose shaky answers.

When to use it, and when something simpler is enough

Use it when

  • The task is to produce or transform language and many different outputs would be acceptable, such as drafting, summarising supplied text, rewriting, classifying or extracting fields.
  • Everything the answer depends on can be placed in the prompt, so the model works from supplied text and not from recall.
  • The knowledge needed is general, stable and widely written about before the model's cutoff, such as explaining a common concept or the syntax of an established programming language.
  • You can check the output cheaply, with tests for code, a schema for structured data or a reviewer for prose, so that an occasional wrong answer is caught.

Think twice when

  • You need an exact, repeatable result, such as arithmetic on long numbers, a count, a sort or a lookup by key. Run code or a query, and let the model call it as a tool if needed.
  • The answer depends on events after the knowledge cutoff or on private data, and you have no way to put that information into the prompt.
  • You want specific citations, quotations, figures, URLs or identifiers from the model's memory with no source to check them against.
  • A confident wrong answer would be costly and nobody will review the output before it is acted on.

A simpler alternative. A deterministic program, such as a database query, a search index, a rules table or a regular expression. If the right output can be written as a rule or looked up, do that; it is exact, repeatable and cheap. Rules stop being enough when the input is open-ended language that nobody can enumerate in advance. At that point use an LLM for the language, and keep the deterministic tools for the facts and the arithmetic.

Key takeaways

  • An LLM does one thing: given the tokens so far, it outputs a probability for every possible next token. A reply is built by picking a token, appending it and repeating until a stop token or a length limit.
  • Training changes the weights and inference does not, so a deployed model learns nothing from your conversations and only seems to remember because the application resends the history.
  • Pre-training on raw text produces a model that continues documents, and instruction tuning on prompt-response examples and human feedback turns it into an assistant, but the task is next-token prediction throughout.
  • The next token is normally sampled from the distribution, so identical prompts can give different outputs and your code and tests must tolerate that.
  • A model always produces a plausible continuation, which makes confident false statements a normal failure that you reduce with supplied sources, permission to abstain and verification, not one you can remove.
  • Knowledge stops at the training cutoff and the model has no clock, so current dates, recent events and private facts must be supplied in the prompt or fetched by a tool.

Example 1 of 5

GitHub Copilot turning an editor into a document for a next-token predictor

GitHubDocumented in an engineering article

GitHub's engineering article A developer's guide to prompt engineering and LLMs (July 2023, updated May 2024) explains, from the experience of building GitHub Copilot, how Copilot's code completion builds a prompt from the developer's editor and lets the model continue it. [1]

The problem

A developer pauses in the middle of a function and wants a useful suggestion before they start typing again. The model behind the feature can only continue a document. It has a limited context window, and it knows nothing about this project beyond what is in the prompt. Time is short as well: the authors' rough heuristic is that every additional 10 milliseconds lowers the chance that a suggestion arrives in time by one percent. The product therefore has to choose, quickly, which text to show the model.

Where this topic fits

Next-token prediction is the engine in the middle. Before it, the editor extension gathers context, ranks it and assembles one document. After it, a stop rule decides where the suggestion ends, and the result is shown as a suggestion the developer can accept or ignore.

How it is applied, step by step

  1. The extension collects candidate context: the code above and below the cursor, the file's path and language, and code from other files open in the editor.
  2. It cuts those other files into overlapping snippets of at most 60 lines and gives each snippet a relevance score based on Jaccard similarity, keeping only the best-scoring ones. The article does not say what each snippet is compared with.
  3. Every item gets a priority. The lowest-priority items are dropped until the rest fits the context window, and the lines directly above the cursor rank highest.
  4. The surviving items are arranged as one source file: a path line at the top, snippets from other files written as comments, then the developer's own code directly above the cursor, which comes last so that it immediately precedes the completion. The article lists the text below the cursor as another candidate but does not say where it is placed.
  5. The model predicts the next token of that file again and again. Because the document is code that stops in the middle of a function, the likely continuation is the rest of the function.
  6. A stop rule ends the suggestion. The article names the first line break as the most common rule, with multi-line suggestions ending when a block of code looks complete.

Why this approach fits

A source file is a document with very regular structure, and "what comes next in this file" is the task the model was trained on. No instruction following is needed. The engineering effort goes into choosing the text before the cursor, because that text is the only thing that moves the probabilities.

Limitation or tradeoff

The suggestion is the likely continuation, which is not always the correct one. The model can call a helper function that does not exist in the project if such a call looks plausible, which is a hallucination in code. It also sees only what fits in the prompt: a relevant file that was not open, or that ranked too low, has no influence at all. The article describes the pipeline as it was in 2023 and 2024, and the product has changed since.

What the sources document

  • The authors compare an LLM to the suggested-next-word button on a phone keypad, and say the model keeps predicting tokens until it reaches a maximum number of tokens or produces a special token that marks the end of the document. [1]
  • For code completions, Copilot does not consider more than the 20 most recent tabs, cuts files into overlapping snippets no longer than 60 lines and uses Jaccard similarity as the score that reflects a snippet's relevance. [1]
  • Snippets from other files are placed in the prompt as comments introduced by a line such as "compare this snippet from utils/concatenate.py", and a file path line can be added at the very top of the prompt. [1]
  • The authors say their rough heuristics are that for every additional 10 milliseconds taken to produce a suggestion, the chance that it arrives in time decreases by one percent. [1]
  • The article says LLMs sometimes confidently produce information that is not real or true, which is usually called hallucination or fabulation. [1]

The facts above come from the cited sources. The steps and analysis in this example are our explanation of how they fit together.

Example 2 of 5

InstructGPT turning pre-trained GPT-3 into a model that follows instructions

OpenAIDocumented in a paper

The 2022 paper Training language models to follow instructions with human feedback, from OpenAI, describes how pre-trained GPT-3 models were fine-tuned into the InstructGPT models and how people rated the results against the original GPT-3. [2][3]

The problem

A pre-trained model is optimised to predict the next token of internet text. The paper points out that this objective is different from following a user's instructions helpfully and safely. The authors note that large language models can generate output that is untruthful, toxic or simply not helpful to the user, and that making a model bigger does not by itself make it better at following what a user intends.

Where this topic fits

Instruction tuning sits between pre-training and deployment. Pre-training has already produced weights that model language. The steps below adjust those weights. Inference happens afterwards, on the adjusted weights, and changes nothing further.

How it is applied, step by step

  1. Start from the pre-trained GPT-3 weights. The authors did this for three sizes: 1.3 billion, 6 billion and 175 billion parameters.
  2. Have human labelers write demonstrations, meaning the response a good assistant would give to a prompt, and fine-tune the model on them with supervised learning. This step is still next-token prediction, now on text shaped as a prompt followed by a good answer.
  3. Sample several model outputs for each prompt and have labelers rank them. Train a separate reward model to predict which output people prefer.
  4. Fine-tune the supervised model with reinforcement learning (the PPO algorithm), using the reward model's score as the reward.
  5. Ask labelers to compare the outputs of the tuned models with those of the original GPT-3 to measure whether the tuning helped.

Why this approach fits

Pre-training is where almost all the compute goes and where the model's command of language comes from, so reusing it is the efficient choice. The missing behaviour, treating a prompt as a request to fulfil, is a narrow thing to teach, and the three stages used only 13k, 33k and 31k prompts. The comparison across sizes shows why this matters more than scale: a tuned model with one hundredth of the parameters was preferred to the untuned large one.

Limitation or tradeoff

Instruction tuning changes how the model behaves. It does not give the model new facts or move its knowledge cutoff. The paper is clear that the tuned models still make simple mistakes, including making up facts. The behaviour is also shaped by whoever supplied the feedback: here a team of about 40 contractors, working on a dataset that the authors describe as over 96% English.

What the sources document

  • The abstract says the authors collected labeler demonstrations of the desired behaviour and used them to fine-tune GPT-3 with supervised learning, then collected rankings of model outputs and fine-tuned further with reinforcement learning from human feedback, calling the resulting models InstructGPT. [2]
  • In human evaluations, outputs from the 1.3B-parameter InstructGPT model were preferred to outputs from the 175B GPT-3, despite the smaller model having 100 times fewer parameters. [2][3]
  • The supervised fine-tuning dataset contains about 13k training prompts, the reward model dataset 33k and the PPO dataset 31k. The authors hired a team of about 40 contractors to produce demonstrations and rankings. [3]
  • Outputs of the 175B InstructGPT model were preferred to GPT-3 outputs 85 ± 3% of the time and to few-shot GPT-3 71 ± 4% of the time. On closed-domain tasks InstructGPT made up information about half as often as GPT-3 (a 21% versus 41% hallucination rate). [3]
  • Training the 175B SFT model required 4.9 petaflops/s-days and the 175B PPO-ptx model 60, compared with 3,640 for GPT-3. The paper also notes that InstructGPT can still fail to follow instructions, make up facts, give long hedging answers to simple questions or miss false premises. [3]

Example 3 of 5

Reading token probabilities to decide when a classification needs a human

OpenAIDocumented in official docs

The OpenAI Cookbook recipe on using logprobs shows how the Chat Completions API can return the log probability of each output token, and applies this to classifying news headlines and to a retrieval question-answering check. The page is marked as archived. [5]

The problem

A model that sorts news headlines into four categories returns a single word. That word hides how close the decision was: the model may have been nearly certain, or nearly split between two labels. In a question-answering system the hidden question is whether the retrieved article really contains the answer, or whether the model is about to fill a gap from memory.

Where this topic fits

The technique reads the probability distribution at the "pick one token" step of the generation loop, before the alternatives are thrown away. Nothing about training changes. The application asks for the probabilities, converts them and applies its own rule.

How it is applied, step by step

  1. Write the prompt so that the answer is a single token from a fixed set, such as one of four category names or the words True and False.
  2. Call the API with log probabilities switched on, and ask for the top alternatives at each output position as well as the chosen token.
  3. Convert each log probability to a probability with p = e raised to the logprob. A logprob of 0 means 100% and more negative values mean less likely.
  4. Compare the top probability with a threshold chosen from your own evaluation data. Accept the label above the threshold and send the item to manual review below it.
  5. For retrieval question answering, first ask the model whether the retrieved article contains enough information, as a True or False answer, and treat the probability of True as a confidence score before answering.

Why this approach fits

The model computes the full distribution on every step whether or not anyone looks at it, so reading it adds no extra model work. It turns a yes-or-no output into a graded one. The approach works best when the answer is one token from a small set, because then a single probability summarises the whole decision.

Limitation or tradeoff

A token probability measures how sure the model is. It does not measure whether the model is right, and a model can be confidently wrong for the same reasons it hallucinates. The recipe itself says to validate the classifications and thresholds with task-specific evaluations before relying on them. For long free-text answers no single token carries the decision. The recipe is archived and uses older models, so check the current API reference for parameter limits and for whether your model returns logprobs at all.

What the sources document

  • The recipe defines a logprob as log(p), where p is the probability of a token occurring at a specific position given the previous tokens. Higher values mean a more likely token, and 0.0 corresponds to 100% probability. [5]
  • It describes two request parameters: logprobs, which returns the log probability of each output token, and top_logprobs, which returns the most likely tokens at each position with their log probabilities. [5]
  • For the example headline about a tennis champion's symphony orchestra debut, the printed output shows Art with logprob -0.028133942 (97.23%) and Sports with logprob -4.278134 (1.39%). [5]
  • The recipe suggests automatically classifying headlines whose confidence exceeds a certain threshold and sending less certain ones for manual review. [5]
  • For retrieval question answering, the recipe has the model output whether the article contains sufficient context and uses that token's probability as a confidence score. It says this self-evaluation can serve as a guardrail to reduce retrieval-based hallucinations but should be validated with task-specific evals first. [5]

Example 4 of 5

The Claude apps telling a frozen model the date and where its knowledge ends

AnthropicDocumented in official docs

Anthropic publishes the system prompts used by claude.ai and the Claude mobile apps in its release notes. The entry for Claude Opus 5.5 dated 22 September 2026 contains a section on the knowledge cutoff, and the models overview page documents the cutoff dates of the current models. [6][7][8]

The problem

The model's weights were fixed months before any given conversation. Left alone, it has no way to know the current date. Asked about recent events, it would either present its training-time picture of the world as current or guess. People using a chat app ask about office holders, new releases and news all the time.

Where this topic fits

This is a fix applied at inference. Nothing is retrained. The application adds text to the prompt before the user's first message, and that text changes which continuations are likely: an answer that mentions its own age becomes more probable than a confident stale one.

How it is applied, step by step

  1. At the start of each conversation, the app fills a placeholder in the system prompt with the current date and time.
  2. The prompt states the model's reliable knowledge cutoff, which for Claude Opus 5.5 is the end of June 2026.
  3. It tells the model to answer as a well-informed person from that month would when talking to someone in the present, so that the model takes the time gap into account.
  4. For news and current facts, it tells the model to give its latest information from before the cutoff, to say that this may be outdated, and to point to web search.
  5. For claims about later events that it cannot check, the model is told neither to confirm nor to deny them.

Why this approach fits

The model cannot know the date, but it can condition on a date it is given. A line with today's date and a short paragraph cost a few dozen tokens per conversation. Retraining a model so that its knowledge is current every day is not an available option.

Limitation or tradeoff

The prompt tells the model that time has passed. It does not tell the model what happened in that time, so facts still have to come from search or retrieval. The published prompts cover Anthropic's own apps: the documentation says they do not apply to the Claude API, so an application built on the API starts with no date at all. An instruction also only shifts probabilities, and a model can still state stale information without the caveat.

What the sources document

  • The system prompts page says that claude.ai and the mobile apps use a system prompt to provide up-to-date information, such as the current date, at the start of every conversation, and that these system prompt updates do not apply to the Claude API. [6]
  • The Claude Opus 5.5 prompt dated September 22, 2026 states that Claude's reliable knowledge cutoff is the end of June 2026 and that Claude answers the way a highly informed individual in June 2026 would if talking to someone from the current date, which is inserted through a placeholder. [7]
  • The same section says that for current news or events Claude gives its most recent pre-cutoff information, notes that it may be outdated and points to web search, and that it neither confirms nor denies claims about later events that it cannot verify without search. [7]
  • The models overview lists a reliable knowledge cutoff and a training data cutoff for each current model, and describes the reliable knowledge cutoff as the date through which the model's knowledge is most extensive and reliable. [8]

Example 5 of 5

Gemini answering from live search results and citing its sources

GoogleDocumented in official docs

The Gemini API documentation describes Grounding with Google Search, a built-in tool that connects a Gemini model to current web content and returns the answer together with the sources it used. [14]

The problem

A developer wants answers about recent events, and wants users to be able to check those answers. The model alone can do neither. Its knowledge ends at the cutoff, and when it lacks a fact it may produce a plausible invention. The documentation names the aims directly: reduce hallucinations, answer questions about recent events, and show the sources for the model's claims.

Where this topic fits

Everything happens at inference. Between receiving the prompt and writing the answer, the model issues search queries and the results are added to what it reads. The generation loop is unchanged. It now runs over a prompt that contains the facts, so the likely continuation is one that repeats them.

How it is applied, step by step

  1. The application sends the user's prompt with the google_search tool enabled.
  2. The model analyses the prompt and decides whether a search would improve the answer.
  3. If so, the model writes one or more search queries, and they are executed automatically.
  4. The model reads the search results and writes an answer based on them.
  5. The API returns the answer together with the queries that were run and annotations that tie spans of the text to their sources.
  6. The application displays the citations so that a reader can check each claim against its source.

Why this approach fits

Stale knowledge and invented facts both come from the model answering out of its weights alone. Search moves the facts from the weights, which are fixed, lossy and undated, into the prompt, where they are current and can be quoted. The citations make whatever errors remain easy to find.

Limitation or tradeoff

The model can still misread or over-compress a source, and a citation shows where a claim came from, not that the source is correct. The decision to search belongs to the model, so some answers may still come from memory. Searches cost money and time: the documentation gives a free monthly allowance and then a price per 1,000 search queries.

What the sources document

  • The documentation says Grounding with Google Search connects the Gemini model to real-time web content, and lists three benefits: increasing factual accuracy by reducing hallucinations, access to real-time information about recent events, and citations that show the sources for the model's claims. [14]
  • It describes five stages: the application sends a prompt with the google_search tool enabled, the model analyses the prompt and determines whether a search can improve the answer, the model generates and executes search queries, it processes the results, and the API returns a grounded response. [14]
  • The response contains the search queries the model executed and text annotations of type url_citation that link segments of the answer, by start and end index, to their sources. [14]
  • For Gemini 3 and newer models, billing is per search query executed by the model, with 5,000 free search requests per month and then 14 US dollars per 1,000 search requests. The page's Python example uses the model gemini-3.8-flash. [14]

4Common mistakes

  1. Asking the model for exact figures, quotations, citations or URLs from memory and using them unchecked.

    Why it causes problems
    These are the details a next-token predictor is worst at. A specific number or reference that appeared rarely in training has no pattern behind it, so the model produces something of the right shape. The result looks authoritative, which is why invented references reach reports and customer emails.
    How to recognise it
    References that cannot be found when searched for, numbers that change when you ask again, and links that return a not-found page.
    How to fix it
    Supply the source text in the prompt and ask for answers with supporting quotes, or fetch the facts with a search or database tool. Tell the model it may answer that it does not know, and check anything that will be acted on.

  2. Assuming the model learns from conversations and corrections.

    Why it causes problems
    A correction typed into one chat changes nothing in the weights. The next conversation starts from the same frozen model and repeats the error, and a team that believes the model was taught stops looking for the real fix.
    How to recognise it
    The same wrong answer returns in a new session after someone reported fixing it by telling the model.
    How to fix it
    Put durable corrections where inference can see them every time: the system prompt, a retrieved document or the application's stored memory. Change the weights only through deliberate fine-tuning.

  3. Expecting the same prompt to return the same text every time.

    Why it causes problems
    Tests that compare replies with an exact string fail at random, and downstream code that depends on one particular phrasing breaks when the wording shifts. Lowering the temperature reduces the variation but does not remove it.
    How to recognise it
    Flaky tests on unchanged code, and parsing errors that appear in a small share of otherwise identical requests.
    How to fix it
    Ask for structured output and validate it, assert on properties instead of exact text, and run important evaluations several times so that you measure a rate and not a single sample.

  4. Trusting the model's idea of today's date, the latest version or current events.

    Why it causes problems
    The model answers from training data that ended at its cutoff, and it gives no sign that the answer is stale. Users get a superseded software version, an old price or a former office holder, stated in the present tense.
    How to recognise it
    Answers that are correct as of a past date, date arithmetic that is off by about a year, and the word latest attached to something that has been replaced.
    How to fix it
    Add the current date to the system prompt, look up the documented cutoff of the exact model you deploy, and supply anything newer than that through retrieval or a search tool.

  5. Reading fluent, confident prose as a sign that the content is correct.

    Why it causes problems
    Fluency is what the model is trained for, and it is the same whether the content is true or invented. The worked example writes a false capital city with exactly the same ease as a true one. Reviewers who skim for tone approve errors.
    How to recognise it
    Reviews that comment on style but never open a source, and incidents in which a wrong answer was well written.
    How to fix it
    Judge claims against evidence. Require citations for factual statements, compare several samples of the same prompt when an answer matters, and have a person or a test verify high-stakes output.

  6. Sending chat-style prompts to a base model, or using the wrong chat template with an open-weight model.

    Why it causes problems
    A base model continues the document, so it may extend the user's question or write both sides of a dialogue. An instruction-tuned model given the wrong control tokens sees text unlike its training data and performs far worse.
    How to recognise it
    Replies that ramble, repeat the question, or carry on with invented user turns after the answer.
    How to fix it
    Use the instruction-tuned variant for assistant tasks, and build prompts with the model's own chat template, for example through the tokenizer's apply_chat_template method, without writing control tokens by hand.

python
import random
from collections import Counter

from tiny_lm import CORPUS, generate, next_token_probs, tokenize, train

REFUSAL = "i do not know"
PROMPTS = ("the capital of germany is", "the capital of italy is")


def answer(counts, prompt, min_context=2, rng=None):
    """Generate only when the first prediction rests on enough matched context."""
    _, matched = next_token_probs(counts, tokenize(prompt))
    if matched < min_context:
        return REFUSAL
    return generate(counts, prompt, rng)


def survey(counts, prompt, writer, seeds=range(200)):
    return Counter(writer(counts, prompt, rng=random.Random(seed)) for seed in seeds)


if __name__ == "__main__":
    model = train(CORPUS)
    for prompt in PROMPTS:
        for writer in (generate, answer):
            print(f"{writer.__name__:8} {prompt!r}")
            for text, n in survey(model, prompt, writer).most_common():
                print(f"    {n:3}  {text}")

    retrained = train([*CORPUS, "the capital of germany is berlin ."])
    print(answer(retrained, "the capital of germany is"))

Each of these is evidence, and none is a guarantee.
