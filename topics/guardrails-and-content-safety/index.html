Guardrails and Content Safety

A guardrail is a check, written in code outside the model, that inspects what goes into or comes out of a language model and then allows it, blocks it, rewrites it or flags it. Content safety is the part of that policy that covers harmful text, personal data and subjects the application should not discuss.

1Overview

Why it matters

A language model's behaviour is not guaranteed: it can be talked into answering outside its remit, and it sometimes produces text nobody asked for. A support assistant can repeat a customer's card number into a log, a banking assistant can be talked into giving investment advice, and a public chatbot can be pushed into abusive language. A system prompt that tells the model to behave is a request, not an enforcement mechanism. Guardrails are the enforcement: ordinary code and small classifiers that sit around the model call and decide what is allowed through.

Anyone who ships an LLM feature to real users meets this problem. That includes engineers adding a moderation call, platform teams choosing between a managed service and an open-source framework, and the people who must answer for what the application said. The design questions are concrete. Which checks run before the model and which after? What happens to a message that is blocked? How do you know a threshold is right for your traffic, and for all of your users rather than only the average one? Wrong answers show up either as harm that slips through or as a product that refuses reasonable requests.

Before you start

  • Prompt Injection and LLM SecurityIntermediate

What you will be able to do

  • Place input, retrieval, tool-call and output checks on a request path and say what each one can catch.
  • Compare a moderation score, a severity level and a safeguard-model verdict, and set a threshold from labelled examples.
  • Mask personal data with a checksum-aware detector and decide between blocking and masking.
  • Write a topic restriction as a precise scope definition instead of a list of banned words.
  • Audit a moderation or toxicity check for higher false-positive rates on particular groups, dialects or languages.
  • Decide whether a check runs before, beside or after a model call, including when the reply is streamed.

Key terms

Guardrail
A check in your own code or service that inspects model input or output and decides to allow, block, rewrite or flag it according to a policy.
Input guardrail
A check on the user's message, and increasingly on retrieved documents and tool results, before the model reads it.
Output guardrail
A check on the model's reply before it is shown to a user or passed to another system.
Moderation API
A hosted classifier that scores text or images against harm categories such as hate, violence or self-harm and returns the result for your code to act on.
Safeguard model
A language model fine-tuned to judge conversations against a written safety policy and answer whether a prompt or a response is safe.
PII
Personally identifiable information, meaning data that identifies a person, such as a name, email address, phone number, card number or government identifier.
Redaction
Replacing detected sensitive spans with a label or a mask, or removing them, so the rest of the text can be used safely.
Threshold
The score at or above which a classifier's output is treated as a violation. It is a policy choice, not a property of the classifier.
False positive and false negative
A false positive is a harmless message that gets blocked; a false negative is a harmful message that gets through.
Fail closed
Blocking the request when a guardrail errors or times out, as opposed to failing open, which lets the request through.

2Explanation

Introduction

In Prompt Injection and LLM Security you saw how attackers get a model to follow instructions it should not follow. This lesson covers the other half of the defence: the checks you place around a model call so that bad input is stopped before it matters and bad output is stopped before anyone sees it or acts on it. Some of those checks defend against attackers. Many exist for ordinary reasons: a customer pastes a card number, a user asks a bank's assistant for stock tips, a reply contains an insult.

You already use the idea. A web form checks that an email field looks like an email before it saves anything. A mail provider scans attachments on the way in and filters spam on the way out. Neither check depends on the sender behaving well. A guardrail applies the same pattern to a language model. The model is a component whose inputs and outputs you do not fully control, so you inspect both.

Three terms recur throughout. An input guardrail examines the user's message before the model sees it. An output guardrail examines the model's reply before it reaches the user or a downstream system. Every check ends in a decision: allow, block with a fixed reply, rewrite (for example mask a phone number), or allow and log for later review.

The checks themselves come in a few kinds, and most real systems mix them. Rules and regular expressions catch fixed formats such as a card number. Classifiers, offered as moderation APIs or as models you run yourself, score text against categories such as hate or self-harm. A second language model can act as a judge for a policy that belongs to your product alone. People handle the cases that automated checks cannot settle. The rest of the lesson covers where each check runs, how to configure it, how to choose a threshold from data, and how to find out whether a check is unfair to some of your users.

How it works

Guardrails enforce; prompts only ask

A system prompt that says "never give investment advice" changes the odds but enforces nothing: the model can be argued out of it. Anthropic's guidance on jailbreaks treats the prompt as one layer beside input screening, limits on what the model can reach, screening of tool output and monitoring (mitigate jailbreaks and prompt injections (opens in a new tab)). A guardrail is enforcement in code you own: it can reject a message without asking the model, and every decision can be logged and tested.

Where the checks run

NVIDIA's NeMo Guardrails (opens in a new tab) documents this staging as five kinds of rail: input, retrieval, dialog, execution and output. Amazon Bedrock Guardrails (opens in a new tab) documents the two-sided version: input is evaluated first, a failing input discards the model call, and only a passing input is followed by evaluation of the response. OWASP lists Improper Output Handling (opens in a new tab) as a risk of its own: model text that reaches a shell, SQL query, web page or file path unvalidated causes injection and path traversal, so treat the model like any other user.

Sequential, parallel and streaming

Every check adds latency and cost, so order matters.

  • Sequential. Check the input, call the model, check the output. A blocked input never reaches the model, and Bedrock bills the evaluation but not model inference.
  • Parallel. Start the guardrail and the model call together and cancel the model call if the guardrail trips. The OpenAI guardrails cookbook (opens in a new tab) shows this with asyncio and frames it as a trade-off between accuracy, latency and cost. Latency is the slower of the two calls, but discarded model calls are still paid for.
  • Streaming. Tokens reach the user as they are produced, so a check on the complete reply comes too late to stop them. OpenAI's moderation guide says scores for a streamed generation arrive after the full output is available. Bedrock's synchronous mode buffers and scans chunks first; its asynchronous mode sends chunks at once and blocks only later ones.

Deterministic validation comes first

Rules are cheap and predictable, so run them before anything model-based. On input: length limits, allowed formats, rate limits and filters for known injection phrases. On output: parse structured replies against a schema, escape text for where it will be shown, and use parameterised queries instead of building SQL from model text. Guardrails AI (opens in a new tab) packages this as validators combined into guards. On failure you can reject, retry with the error message, or fall back to a fixed reply. A retry suits a format error; for a safety violation a fixed reply is better, since a retry only gives the model another chance to say the same thing.

Moderation APIs, severity levels and safeguard models

A moderation API sends text, and sometimes images, to a classifier that someone else runs. Results come in three styles:

  • Scores. OpenAI's moderation endpoint (opens in a new tab) returns flagged for the whole input, true or false values in categories and 0 to 1 scores in category_scores for categories such as hate, self-harm and violence.
  • Severity levels. Azure AI Content Safety (opens in a new tab) rates hate and fairness, sexual, violence and self-harm. Its text model returns severity on a 0 to 7 scale, or a trimmed 0, 2, 4, 6 scale. Azure's guardrail settings use Safe, Low, Medium and High, and your setting is the threshold: Low flags low severity and above.
  • Safeguard-model verdicts. Llama Guard (opens in a new tab) is a language model fine-tuned to read a conversation and policy categories and answer "safe" or "unsafe", plus the violated categories.

A score is the classifier's own output. OpenAI describes its scores as confidence values between 0 and 1 and says to treat them as signals for your own policy, so do not read 0.70 as a measured 70% chance of harm without checking it against labelled examples. Where you cut is a product decision. For a threshold ttt, a message is flagged when its score is at least ttt. Judge the result on labelled examples with three quantities:

recall=TPTP+FN,precision=TPTP+FP,FPR=FPFP+TN\text{recall} = \frac{TP}{TP + FN}, \qquad \text{precision} = \frac{TP}{TP + FP}, \qquad \text{FPR} = \frac{FP}{FP + TN}recall=TP+FNTP​,precision=TP+FPTP​,FPR=FP+TNFP​

Here TPTPTP counts harmful messages flagged, FPFPFP benign messages flagged, FNFNFN harmful messages missed and TNTNTN benign messages that passed. Raising ttt can only lower or leave unchanged both the false positive rate (FPR) and recall, as the worked example shows. The cookbook states the stakes: too many false positives fracture the user experience, and too many false negatives can cause lasting harm. A common compromise is two thresholds, with the band between them sent to a person or a safer fallback. A general-purpose model can also classify against your own policy, as in Anthropic's input pre-screen that replies with a JSON boolean.

PII detection and redaction

PII covers names, contact details, card and government identifiers and addresses. Detectors combine three techniques. Patterns with checksums suit structured identifiers: Presidio's supported entities (opens in a new tab) page lists its credit card detector as pattern match plus checksum (for cards, the Luhn algorithm of the worked example). Named entity recognition models find names and places, which have no fixed format. Context words near a candidate can raise its confidence, as in the Presidio Analyzer (opens in a new tab).

After detection you either block or mask. Block rejects the whole message and fits an application that never needs the data. Mask replaces each span with a label such as <PHONE_NUMBER> (Presidio's default) or {NAME} (Bedrock), so the rest of the message can continue. A typical implementation keeps a table from placeholder to original value and restores the values in the reply when the user may see them; exercise 1 builds this. Redaction has to cover the prompt, the reply and your logs. No detector finds everything, and Presidio's documentation says so directly.

Topic restrictions

A deny list names what to refuse, such as investment advice in a bank's assistant. An allow list names the only subjects to answer: the cookbook's example prompt lists cats and dogs and returns allowed or not_allowed. NeMo's Topic Control NIM labels each user message on-topic or off-topic against a prompt that sets out what to answer and what to refuse. Bedrock's guidance on denied topics is a useful template: a noun or phrase as the name, a definition of up to 200 characters that describes the subject, and no examples, instructions, exceptions or individual names in it. Test each topic with messages that are clearly in scope and clearly out of scope.

Toxicity and bias checks

Two questions share this heading: is the text toxic (the hate, harassment and insult categories above), and does the checker treat people evenly? Toxicity classifiers learn from labelled data that can carry spurious correlations. Borkan et al. describe toxicity models that mis-associate identity terms such as "gay" with toxicity, and publish bias metrics and a labelled comment dataset (paper (opens in a new tab)). Xu et al. report that detoxification methods exploit spurious correlations in toxicity datasets and so reduce a language model's usefulness on African-American English and minority identity mentions (paper (opens in a new tab)). Welbl et al. report that toxicity reduction cost coverage of texts about, and dialects of, marginalised groups (paper (opens in a new tab)).

A simple audit of your own: collect benign messages that mention each group, dialect or language you serve, run the checker at your threshold, and compute the false positive rate per group. A gap means some users are blocked for ordinary speech. Exercise 2 practises this; Fairness and Bias in ML covers the wider topic.

Failing safely

Decide in advance what happens when a guardrail times out. Failing closed (block) suits checks against serious harm; failing open (allow, and log) suits low-stakes checks where an outage should not stop the product. Tell users something useful when you block, and log the check, score and action of every decision to support tuning and spot repeat offenders. Guardrails can be attacked too, so layer deterministic checks, least-privilege limits and red-teaming (see Red Teaming LLM Apps and Agents) rather than trusting one filter.

Worked example: Masking a card number, then choosing a moderation threshold

Two small programs, runnable with the Python standard library. Part A is an input guardrail that masks personal data. Part B shows how a threshold on a moderation score turns into decisions. Both use data we wrote for the example, so nothing here is a measurement of a real service.

Part A: mask a card number and an email address

The detector finds candidate card numbers with a regular expression and keeps only those that pass the Luhn checksum. Starting from the right, it doubles every second digit, subtracts 9 from any doubled digit above 9, and adds everything up; a valid number's total is divisible by 10.

python
import re

CARD = re.compile(r"\b\d(?:[ -]?\d){12,15}\b")
EMAIL = re.compile(r"\b[\w.+-]+@[\w-]+\.[\w.-]+\b")


def luhn_ok(digits: str) -> bool:
    total = 0
    for i, ch in enumerate(reversed(digits)):
        d = int(ch)
        if i % 2 == 1:
            d *= 2
            if d > 9:
                d -= 9
        total += d
    return total % 10 == 0


def redact(text: str):
    found = []

    def card_sub(m):
        digits = re.sub(r"\D", "", m.group())
        if luhn_ok(digits):
            found.append("CARD_NUMBER")
            return "<CARD_NUMBER>"
        return m.group()          # fails the checksum: leave it alone

    def email_sub(m):
        found.append("EMAIL_ADDRESS")
        return "<EMAIL_ADDRESS>"

    out = CARD.sub(card_sub, text)
    return EMAIL.sub(email_sub, out), found


msg = ("Card 4111 1111 1111 1111, email dana@example.com. "
       "Order 4111 1111 1111 1112 ships Friday.")
clean, found = redact(msg)
print(clean)
print(found)

Output:

text
Card <CARD_NUMBER>, email <EMAIL_ADDRESS>. Order 4111 1111 1111 1112 ships Friday.
['CARD_NUMBER', 'EMAIL_ADDRESS']

The first number, 4111 1111 1111 1111, is a widely used test card number and passes the checksum, so it is masked. The second differs only in its last digit, fails the checksum and is left alone, so a 16-digit order reference is not erased by mistake. The regular expression alone would have masked both.

Part B: from a score to a decision

A moderation call returns a score between 0 and 1, and a message is flagged when its score is at least a threshold ttt. Take ten messages, label each by hand as harmful or benign, and record the score the classifier gave. The scores are invented for this example.

python
DATA = [  # (message id, moderation score, truly harmful?)
    (1, 0.96, True), (2, 0.91, True), (3, 0.74, True), (4, 0.62, True), (5, 0.41, True),
    (6, 0.83, False), (7, 0.55, False), (8, 0.33, False), (9, 0.12, False), (10, 0.05, False),
]


def metrics(threshold):
    tp = sum(1 for _, s, y in DATA if s >= threshold and y)
    fp = sum(1 for _, s, y in DATA if s >= threshold and not y)
    fn = sum(1 for _, s, y in DATA if s < threshold and y)
    tn = sum(1 for _, s, y in DATA if s < threshold and not y)
    return tp, fp, fn, tn, tp / (tp + fp), tp / (tp + fn), fp / (fp + tn)


print("threshold  TP FP FN TN  precision recall  FPR")
for t in (0.30, 0.50, 0.80):
    tp, fp, fn, tn, p, r, f = metrics(t)
    print(f"{t:>9.2f} {tp:>3}{fp:>3}{fn:>3}{tn:>3}  {p:>9.3f} {r:>6.2f} {f:>5.2f}")

At t=0.50t = 0.50t=0.50 four of the five harmful messages are caught (recall 0.80), but two of the five benign ones are blocked as well (FPR 0.40). Moving to t=0.80t = 0.80t=0.80 halves the false positives to 0.20 and cuts recall to 0.40, so three harmful messages pass. At t=0.30t = 0.30t=0.30 nothing harmful is missed and three of the five benign messages are blocked. No single threshold reaches recall 1.0 with FPR 0, because benign message 6 (0.83) scores higher than harmful message 5 (0.41).

That overlap is why teams add a review band. With block at 0.80 and above, review from 0.50 to just under 0.80, and allow below 0.50, the ten messages split into three blocked (two harmful, one benign), three reviewed (two harmful, one benign) and four allowed (one harmful, three benign). A person reads three messages instead of all ten, and one harmful message still gets through. The numbers come from ten invented messages, so do not carry 0.50 or 0.80 into a real system. What carries over is the procedure: label a sample of your own traffic, compute the three quantities across thresholds, and choose by the cost of each kind of error.

Edge cases and limitations

The reply is on screen before the check finishes
With streaming, a check on the complete reply runs after the user has already seen the text. OpenAI documents that moderation scores for a streamed response arrive only after the full output exists. Bedrock's synchronous mode buffers chunks and delays them; its asynchronous mode streams at once, blocks only later chunks, and cannot mask sensitive information. If a reply must never show prohibited content, buffer it. If latency matters more, accept that early chunks are unchecked and plan how to retract them.
The guardrail can be attacked too
The Llama Guard authors state that it may be susceptible to prompt injection that alters or bypasses its intended use, and any model-based screen reads text that an attacker controls. Keep cheap deterministic checks beside model-based ones, limit what a bypass can reach through least-privilege permissions, and include the guardrail itself in your red-team tests.
Masking protects the model call, not necessarily your logs
Bedrock documents that PII masking applies to content sent to and returned from the model but not to model invocation logs, which keep the original request, nor to the match field of the guardrail trace, which holds the original value by design. Its PII filter also does not evaluate tool-call arguments or tool results. Redact before logging, protect log storage separately, and test the tool path as its own route for personal data.
Scores drift when the provider updates the model
OpenAI says it plans to keep upgrading the model behind the moderation endpoint, so thresholds on category_scores may need recalibration. AWS says it periodically updates the models behind Bedrock policies and recommends continuing to test. Keep a labelled regression set from your own traffic, rerun it on a schedule and whenever a provider announces a change, and watch for a rising block rate.
Short text and other languages score worse
Bedrock notes that its PII model performs better with more context and advises against sending single words or short phrases. Microsoft states that its text harm models are trained and tested on eight languages and that accuracy and false positive rates may vary in others. The Llama Guard authors say most of its data is English and they do not guarantee adequate performance in other languages. Test with the message lengths and languages your users actually send, and treat untested languages as higher risk.
Topic checks depend on configuration details
Bedrock's documentation says the order in which denied topics are configured can change results, so the same prompt may be blocked under one ordering and allowed under another. Definitions that contain instructions, negations or names work poorly. After every change, rerun a fixed set of in-scope and out-of-scope messages for each topic.

When to use it, and when something simpler is enough

Use it when

  • The application accepts free text from people you do not control, such as a public chatbot, a support assistant or a form that feeds an LLM.
  • Personal, payment or health data could reach a third-party model or your logs, so detection and masking must happen before it leaves your boundary.
  • The product has a defined scope, such as a bank, a clinic or a children's service, and off-scope replies would create legal or reputational risk.
  • Model output is rendered as HTML, executed, used in a query or passed to a tool, so it must be validated like any other untrusted input.

Think twice when

  • Do not treat a guardrail as the only defence against prompt injection or data theft; restrict what the model can read and do, and keep guardrails as one layer.
  • Do not add an LLM judge for a rule that a regular expression, a checksum or a schema check can enforce exactly, because it adds a model call and is less predictable.
  • Do not switch every category to its strictest setting before measuring, since blocking a nurse's dosage question or a moderator quoting abuse is a product failure too.

A simpler alternative. For a narrow prototype, start with a length limit, a schema check on the output and one hosted moderation call on the input and on the reply, logging every result. That covers many early risks with little code. Move to a policy layer or a framework when you need several policies, topic control, PII masking or the same rules across several models and teams.

Key takeaways

  • A guardrail is code that enforces a policy on model input and output, whereas a system prompt only asks the model to follow it.
  • Put checks where they can act, which means on the user message, on retrieved text and tool arguments, and on the reply, because each sees different risks.
  • Moderation scores, severity levels and safeguard-model verdicts are signals, and the threshold is your decision, best set from labelled examples of your own traffic.
  • PII handling means detect, then block or mask, across prompts, replies and logs, and no detector is guaranteed to find everything.
  • Topic restrictions work best as precise scope definitions, and toxicity checks must be audited for higher false-positive rates on particular groups, dialects and languages.
  • Streaming, provider updates and attacks on the guardrail itself are the usual ways a working setup fails, so test, monitor and layer defences.

Example 1 of 5

OpenAI Moderation endpoint scoring text and images against harm categories

OpenAIDocumented in official docs

OpenAI's Moderation guide documents a free endpoint, served by the omni-moderation-latest model, that classifies text and images and returns per-category flags and scores. The guide is the source for everything described here. [1]

The problem

An application that accepts free text needs a quick way to decide whether a message, or a generated reply, contains hateful, violent, sexual or self-harm content, without collecting data and training a classifier of its own. It also needs the answer in a form its code can turn into a policy: block, review or allow.

Where this topic fits

The guide describes two ways to use the endpoint: classify a standalone input, or request moderation scores alongside a generated response. A typical implementation calls it on the user's message before the main model call and again on the reply, and compares each category score with thresholds the team chose for its own product.

How it is applied, step by step

  1. Send the text, and optionally an image, to the moderation endpoint with the model omni-moderation-latest.
  2. Read the response. `flagged` says whether the content is potentially harmful, `categories` holds a true or false value per category, `category_scores` holds a 0 to 1 score per category, and `category_applied_input_types` records which input types each category was applied to.
  3. Apply your own policy. A typical implementation starts from the provider's `flagged` value and adds stricter cut-offs for the categories that matter most to the product, such as self-harm for a service used by teenagers.
  4. Moderate the model's reply too, either with a second call to the endpoint or by requesting moderation alongside the generation. The guide says that for a streamed generation the scores arrive only after the full output exists, so they cannot hold back text that was already displayed.
  5. Store the category scores next to the decision, so that thresholds can be revisited when the provider upgrades the underlying model.

Why this approach fits

Harm classification is a task that many applications share, so a hosted classifier saves the cost of labelled data and training. Returning a score per category, and not only a yes or no, lets each team put its own line where its audience and risk require.

Limitation or tradeoff

The categories are OpenAI's, so rules that belong to your product, such as a competitor's name or a regulated advice topic, need another mechanism. The guide says the underlying model will keep being upgraded, so thresholds on category_scores may need recalibration, and that the endpoint is not designed to detect child sexual abuse material, which must not be sent to it.

What the sources document

  • The moderation endpoint detects harmful content in text and images. The guide describes omni-moderation-latest as accepting text and image inputs, and states that the endpoint is free to use. [1]
  • The response contains `flagged`, a `categories` map of true or false values, `category_scores` with values between 0 and 1, and `category_applied_input_types` showing which input types each category applied to. [1]
  • The categories include harassment, harassment/threatening, hate, hate/threatening, illicit, illicit/violent, self-harm (with intent and instructions variants), sexual, sexual/minors, violence and violence/graphic. Some apply to text only and others to text and images. [1]
  • If a response is streamed, moderation scores arrive after the full generated output is available. [1]
  • OpenAI plans to keep upgrading the underlying model, so custom policies that rely on `category_scores` may need recalibration over time. [1]

The facts above come from the cited sources. The steps and analysis in this example are our explanation of how they fit together.

Example 2 of 5

Amazon Bedrock Guardrails as one policy layer for denied topics and PII masking

Amazon Web ServicesDocumented in official docs

The Amazon Bedrock User Guide documents Guardrails as configurable safeguards that evaluate prompts and model responses. Its overview, how-it-works, denied-topics, sensitive-information and streaming pages are the sources for this example. [3][4][5][6][7]

The problem

An organisation with several generative AI applications wants one safety policy applied the same way everywhere: no investment advice from a banking assistant, no names or card numbers in conversation summaries, and no harmful content in chat. Rebuilding those checks inside every application is slow, and the copies drift apart.

Where this topic fits

The guardrail wraps the model call. The documentation says a guardrail is referenced by ID and version during model inference, or called on its own through the ApplyGuardrail API without invoking a model. The input is evaluated first and the response second.

How it is applied, step by step

  1. Create a guardrail from the policies you need: content filters, denied topics, word filters, sensitive information filters, contextual grounding checks or automated reasoning checks.
  2. For a denied topic, write a name and a definition of up to 200 characters, optionally add up to five sample phrases, and choose for the input and the output separately whether to block or only detect.
  3. For PII, choose entity types such as name, email or card number, and an action per direction: block the content, or mask it with a label such as {NAME}.
  4. Reference the guardrail in the Converse or InvokeModel call. The input is checked with the policies evaluated in parallel for latency, and a failing input returns the configured blocked message and discards model inference.
  5. If the input passes, the model answers and the response is checked. A violation is replaced by the blocked message, or the sensitive span is masked.
  6. For streamed replies, pick synchronous mode, which buffers and scans chunks before sending them, or asynchronous mode, which sends chunks at once and blocks later ones; asynchronous mode cannot mask sensitive information.

Why this approach fits

Because the guardrail is a separate resource referenced by ID and version, a security or compliance team can own and version the policy while application teams only reference it. Evaluating the policies in parallel, which the documentation says is done to improve latency, keeps the added delay from growing with every policy you switch on.

Limitation or tradeoff

The filters are model-based and probabilistic, and the documentation says AWS updates them periodically, so the policy needs continuing tests. PII masking does not reach model invocation logs or the trace output, the PII filter does not evaluate tool-call arguments or results, asynchronous streaming cannot mask, and denied-topic results can depend on the order of the topics. Evaluation is billed even when the guardrail blocks the request.

What the sources document

  • Bedrock Guardrails offers content filters (Hate, Insults, Sexual, Violence, Misconduct, Prompt Attack), denied topics, word filters, sensitive information filters, contextual grounding checks and Automated Reasoning checks. The page's example uses include blocking illegal investment advice in a banking application and redacting PII in call-center summaries. [3]
  • A guardrail can be applied during inference by specifying its ID and version, or through the ApplyGuardrail API without invoking a model. The input is evaluated first, with the policies evaluated in parallel for latency. An intervention returns the blocked message and discards model inference; otherwise the response is evaluated and may be overridden or masked. [3][4]
  • A denied topic has a name, a definition of up to 200 characters and up to five sample phrases. The page advises against instructions, negations and entity names in definitions, says up to 30 topics can be added, and notes that the order of topics can change evaluation results. [5]
  • The sensitive information filter can block or mask PII in prompts and responses, replacing a masked value with its type such as {NAME} or {EMAIL}. Masking does not apply to model invocation logs, the trace match field holds the original value, and tool-call arguments and results are not evaluated. [6]
  • For streaming, synchronous mode buffers and scans chunks before they reach the user, which adds latency but gives better accuracy. Asynchronous mode sends chunks immediately and may let inappropriate content through until the scan completes, and it does not support masking of sensitive information. [7]

Example 3 of 5

NVIDIA NeMo Guardrails placing programmable rails at five points in an LLM application

NVIDIADocumented in an open-source project

NeMo Guardrails is an Apache-2.0 open-source toolkit from NVIDIA. Its repository README and documentation describe five kinds of rail, a YAML configuration, and built-in or integrated checkers for content safety, topic control and PII. [8][9][11][13][12]

The problem

A team wants the same safety behaviour whichever model an application calls, and wants it to cover more than the user's message: retrieved document chunks, tool calls and the reply as well. Writing these checks by hand in every code path leaves gaps, and swapping one checker for another means editing application code.

Where this topic fits

The library sits between the application and the model. The application calls it with chat messages, and the runtime applies input rails, retrieval rails when a knowledge base is configured, dialog rails, execution rails and output rails. The architecture page states that applications do not need to implement this orchestration themselves.

How it is applied, step by step

  1. Write a configuration folder whose config.yml names the main model and lists rails as flows, for example an input flow that checks topic and one that masks sensitive data.
  2. Choose a checker for each concern. The documentation lists LLM self-checking, NVIDIA safety models and community models such as Llama Guard for content safety, a topic control model, and Presidio, GLiNER or third-party services for PII.
  3. For topic control, list allowed and prohibited topics in a system prompt in prompts.yml and enable the topic safety check flow as an input rail.
  4. For PII, enable the mask flows on input and output and list the entities, such as PERSON and EMAIL_ADDRESS. The documentation separates detection flows, which stop content that contains PII, from masking flows, which rewrite it and let it continue.
  5. Load the configuration with RailsConfig.from_path and call generate with OpenAI-style messages, or run the guardrails server, which exposes a chat completions endpoint.
  6. When the topic rail judges a message off-topic, the tutorial shows the reply "I'm sorry, I can't respond to that." and the request is blocked before the main model answers.

Why this approach fits

Rails are configuration around the model, so the same checks keep working if the main model changes, and a checker can be swapped as needs grow: a self-check prompt while prototyping, a dedicated safety model later. Covering retrieval and execution as well as input and output matters for RAG systems and agents, where untrusted text and tool arguments never pass through the user's message.

Limitation or tradeoff

Each rail is another model call or service on the request path, which adds latency and cost. What you must run depends on the checker: the documented GLiNER PII flows call a NIM, either NVIDIA-hosted with an API key or a local container, the Private AI flows call that service's API, and the topic control model is a NIM too. The retrieval flows run on LLMRails only, not IORails. The toolkit does not make a weak checker strong: a rail is only as good as the model or rule behind it.

What the sources document

  • NeMo Guardrails is an open-source toolkit for adding programmable guardrails to LLM-based conversational systems, and is released under the Apache License 2.0. [8]
  • The documentation defines input, retrieval, dialog, execution and output rails. Input rails can allow, alter or reject a message, and output rails can allow, edit or block a response. The library orchestrates them, so applications do not have to. [11]
  • For content safety the documentation lists LLM self-checking, NVIDIA safety models and community models such as Llama Guard. For PII it lists Presidio, GLiNER and third-party services, and says PII detection can either block content or mask the entities before processing. [9]
  • A Llama 3.1 NemoGuard 8B topic control model is configured as a model of type topic_control and enabled as an input flow. Allowed and prohibited topics are listed in a system prompt in prompts.yml, and an off-topic message gets the reply "I'm sorry, I can't respond to that." [13]
  • Presidio-based flows named mask sensitive data on input, output and retrieval take entity lists such as PERSON and EMAIL_ADDRESS. Detection blocks content that contains PII, masking rewrites it with placeholders, and retrieval flows work only with LLMRails. [12]

Example 4 of 5

Llama Guard classifying prompts and responses against an editable safety policy

MetaDocumented in a paper

The Llama Guard paper (arXiv, December 2023) describes an instruction-tuned model built on Llama2-7b that judges the safety of user prompts and of model responses against a taxonomy supplied in its prompt. The paper is the source for everything described here, except the note on newer versions, which comes from Meta's Llama Guard 4 model card. [14][15]

The problem

A hosted moderation API ships with a fixed policy, so a team whose rules differ cannot change them. Judging a model's reply is also a different task from judging a user's prompt, because the reply must be read in the context of the request. The team wants a classifier whose policy it can edit and which handles both sides of the conversation.

Where this topic fits

It acts as an input-output safeguard. The same model is called on the user's prompt before the main model and on the response afterwards, with a different instruction each time, and its verdict decides whether the text goes through.

How it is applied, step by step

  1. Build a prompt with four parts: a task that says whether the prompt or the response is being classified, the policy as numbered categories with plain-text descriptions of what is safe and unsafe, the conversation, and the required output format.
  2. Run the model. It generates "safe" or "unsafe" and, when unsafe, the codes of the violated categories.
  3. Read the probability of the first generated token as a score and threshold it like any classifier, trading missed harm against false alarms.
  4. To change the policy, edit the category list or add examples to the prompt (zero-shot or few-shot) instead of retraining. The paper reports that adapting to OpenAI's categories this way scored higher than no adaptation on the OpenAI Moderation dataset, and few-shot scored higher still.
  5. Allow, block or replace the text according to the verdict, and log the verdict and categories.

Why this approach fits

A model that reads its policy as text can follow a changed policy without retraining, and judging a reply together with the request catches replies that are only harmful in context. It is also a model you can evaluate and tune on your own labelled data like any other classifier.

Limitation or tradeoff

The authors list limits: the model's knowledge is limited by its training data, most of that data is English so they do not guarantee adequate performance in other languages, their policy coverage is not perfect, and the model may be susceptible to prompt injection. The largest margins in the paper come from the authors' own test set. On the external OpenAI Moderation dataset the OpenAI API baseline scored slightly higher (0.856 against 0.847), so measure on your own traffic before switching. The paper describes the original Llama2-7b model, and Meta's model card now calls Llama Guard 4 its latest safeguard model, so these figures do not describe the current release.

What the sources document

  • Llama Guard is an instruction-tuned Llama2-7b model that classifies user prompts and model responses against a safety risk taxonomy, and the authors release its weights. Meta's model card now calls Llama Guard 4 its latest safeguard model and a drop-in replacement for Llama Guard 3 8B and 11B. [14][15]
  • The taxonomy has six categories: Violence and Hate, Sexual Content, Guns and Illegal Weapons, Regulated or Controlled Substances, Suicide and Self-Harm, and Criminal Planning. The training set has 13,997 annotated prompts and responses. [14]
  • The prompt holds the guidelines, the classification type, the conversation and the output format. The model outputs safe or unsafe and then the violated categories, a score comes from the probability of the first token, and prompt and response classification differ only in the wording of the instruction. [14]
  • In Table 2 the AUPRC on the authors' own prompt test set is 0.945 for Llama Guard and 0.764 for the OpenAI API baseline. On the OpenAI Moderation dataset it is 0.847 against 0.856, and on ToxicChat 0.626 against 0.588. [14]
  • The authors state that Llama Guard may be susceptible to prompt injection attacks that could alter or bypass its intended use. They also say its knowledge is limited by its training data, that most of its data is English so adequate performance in other languages is not guaranteed, and that they do not claim perfect coverage of their policy. [14]

Example 5 of 5

Presidio detecting and anonymising personal data before text reaches a model

Presidio open-source projectDocumented in an open-source project

Presidio's documentation describes an open-source framework that identifies and anonymises PII in text and images. NVIDIA's NeMo Guardrails documentation lists it, under the name Microsoft Presidio, as a built-in PII option. [16][17][18][19][12]

The problem

Chat messages, support transcripts and documents contain names, phone numbers, email addresses and card numbers. Sending them to a hosted model, indexing them in a vector store or writing them to logs spreads personal data into places that are hard to audit. The text is free-form, so a list of known form fields cannot find it.

Where this topic fits

On the input side, Presidio runs before the prompt is built or stored. On the output side it runs before a reply is displayed or logged, and it can run in ingestion pipelines for documents. The Analyzer produces the locations of sensitive spans and the Anonymizer rewrites them.

How it is applied, step by step

  1. The Analyzer runs a set of recognizers, each responsible for one or more entity types and built from regular expressions, named entity recognition models or custom logic, with an NLP engine supplying tokens and entities.
  2. Checksums validate identifiers such as credit card numbers, and context awareness raises confidence when nearby words support the entity.
  3. Each finding comes back with entity_type, start, end and a confidence score. The application can discard findings under a cut-off it chooses.
  4. The Anonymizer takes the original text and those findings and applies an operator per entity type: replace (the default, which writes the type such as PHONE_NUMBER in angle brackets), redact, mask, hash, encrypt, custom or keep.
  5. The masked text goes to the model. If the application needs the originals back, an encrypt operator with a key can be reversed with the decrypt operator.
  6. NeMo Guardrails uses Presidio for its mask sensitive data flows on input, output and retrieval.

Why this approach fits

Free-form text rules out fixed field lists. Combining patterns, checksums, entity recognition and context handles both formatted identifiers and names, and the operator set lets one detection step feed different policies: irreversible redaction for logs, reversible encryption for a round trip through a model.

Limitation or tradeoff

The documentation states that there is no guarantee Presidio will find all sensitive information and says to use it alongside other protections. Entity recognition models typically make mistakes on unusual names and on languages they were not built for, and the score cut-off trades missed PII against over-masking. Presidio finds and rewrites text; it does not decide who is allowed to see the original.

What the sources document

  • Presidio is an open-source framework for identifying and anonymising PII in text and images, with four modules: Analyzer, Anonymizer, Image Redactor and Structured. The documentation states that there is no guarantee that Presidio will find all sensitive information. [16]
  • The Analyzer combines recognizers built from regular expressions, named entity recognition and custom logic, with an NLP engine and a context-aware enhancer. A result carries entity_type, score, start and end. [17]
  • The supported-entities page lists CREDIT_CARD as a number of 12 to 19 digits, detected by pattern matching plus a checksum. [19]
  • The Anonymizer provides replace, redact, mask, hash, encrypt, custom, keep and decrypt operators. The default operator is replace, which substitutes the entity type, for example PHONE_NUMBER in angle brackets. [18]
  • NeMo Guardrails documents Presidio-based flows named mask sensitive data on input, output and retrieval, configured with entity lists such as PERSON and EMAIL_ADDRESS. [12]

4Common mistakes

  1. Treating the system prompt as the only guardrail

    Why it causes problems
    A prompt is a request the model can be talked out of, and nothing in it is logged, tested or enforced. One successful jailbreak removes the only protection, and you have no record that a rule was ever applied.
    How to recognise it
    Your safety policy exists only as prose in a prompt, no code path can reject a request, and red-team messages that ask for forbidden content get answers.
    How to fix it
    Move enforceable rules into code: input and output checks that return a decision and log it, plus least-privilege limits on tools. Keep the prompt as one layer among several.

  2. Checking only the user's message and never the reply or the retrieved text

    Why it causes problems
    A harmless question can produce a harmful or leaking answer, and harmful text can arrive through a retrieved document or a tool result. If the reply is rendered as HTML or run as a query, unchecked model output also becomes an injection path, as OWASP's Improper Output Handling entry describes.
    How to recognise it
    A trace shows no check between retrieval or tool output and the model, or between the model and the code that displays or executes its output.
    How to fix it
    Add an output check and apply the same screening to retrieved chunks and tool results. Validate or encode output for the place it is used, such as a schema, an HTML escape or a parameterised query.

  3. Copying a default threshold without measuring it on your own traffic

    Why it causes problems
    A cut-off that suits a provider's benchmark can block many legitimate messages in your domain or miss the harm that matters to you. Provider updates can then shift the scores and move the balance without any change on your side.
    How to recognise it
    There is no labelled sample of your traffic, support tickets complain about refusals, or the block rate changes after a provider announcement.
    How to fix it
    Label a few hundred real or realistic messages, compute precision, recall and false positive rate at several thresholds, and keep the set as a regression test to rerun on a schedule and after provider changes.

  4. Masking personal data in the prompt but writing the raw text to logs

    Why it causes problems
    The sensitive values survive in logs, traces and analytics tables, where access controls are usually looser than on the production database. Bedrock's documentation shows that invocation logs and the guardrail trace can keep the original values even when the model call was masked.
    How to recognise it
    Search stored logs for email addresses or card-like numbers, and compare a logged prompt with the prompt that was actually sent.
    How to fix it
    Redact before anything is logged, or apply log-level data protection. Apply the same rule to tool-call arguments and tool results, which some PII filters do not inspect.

  5. Never auditing the checker for uneven false positives

    Why it causes problems
    A toxicity or moderation filter that over-flags identity terms, dialects or other languages silently blocks those users from the product. Aggregate accuracy hides the gap, and no error is ever raised.
    How to recognise it
    On a benign test set split by group, dialect or language, the false positive rate differs between groups at your threshold, or block rates differ by language in production.
    How to fix it
    Build a benign test set for each group you serve, report the false positive rate per group next to the overall figure, and respond with a review band, a different classifier or added human review until the gap is acceptable.

Exercise 1

Build a reversible PII redactor with a Luhn check

CodingIntermediateAbout 40 min (estimate)Hypothetical scenario

A support assistant sends customer messages to a hosted model, and the privacy team wants personal data replaced before the text leaves your system. Write two Python functions using only the standard library:

  • redact(text) returns the redacted text and a dictionary that maps each placeholder to the original value it replaced.
  • restore(text, mapping) puts the original values back into a model reply that contains placeholders.

Use this test message, in which every value is made up:

text
Email me at a@b.com or call 212-555-0100. SSN 123-45-6789. Order 4111 1111 1111 1112 is late; write a@b.com again.

Detect email addresses, phone numbers written like 212-555-0100, social security numbers written like 123-45-6789, and card numbers of 13 to 16 digits that pass the Luhn checksum.

Requirements

  • Placeholders look like `<EMAIL_1>`, `<PHONE_1>`, `<SSN_1>` and `<CARD_1>`, numbered separately for each type.
  • The same original value always receives the same placeholder, so a repeated email address reuses `<EMAIL_1>`.
  • A digit string that matches the card pattern but fails the Luhn check is left unchanged.
  • After redaction, none of the made-up email, phone or SSN values may appear in the text.
  • restore replaces every placeholder in a reply with its original value.

Expected behaviour

For the test message, the redacted text is Email me at <EMAIL_1> or call <PHONE_1>. SSN <SSN_1>. Order 4111 1111 1111 1112 is late; write <EMAIL_1> again. and the mapping has three entries. Restoring the reply Sure, I will write to <EMAIL_1> and call <PHONE_1> about the order. gives back the original email address and phone number.

Hint 1

Pass a function to `re.sub` so that each match can be inspected before it is replaced.

Hint 2

Keep two dictionaries, one from placeholder to original and one from original to placeholder, so that repeated values reuse their token.

Hint 3

Strip spaces and dashes from a card candidate before running the Luhn check, and apply the check to the card pattern only.

Hint 4

A pattern for 13 to 16 digits with optional single spaces or dashes between them is `\b\d(?:[ -]?\d){12,15}\b`.

Show solution

One way to do it:

python
import re

PATTERNS = [
    ("EMAIL", re.compile(r"\b[\w.+-]+@[\w-]+\.[\w.-]+\b")),
    ("SSN", re.compile(r"\b\d{3}-\d{2}-\d{4}\b")),
    ("PHONE", re.compile(r"\b\d{3}[-.]\d{3}[-.]\d{4}\b")),
    ("CARD", re.compile(r"\b\d(?:[ -]?\d){12,15}\b")),
]


def luhn_ok(digits):
    total = 0
    for i, ch in enumerate(reversed(digits)):
        d = int(ch)
        if i % 2 == 1:
            d = d * 2 - 9 if d * 2 > 9 else d * 2
        total += d
    return total % 10 == 0


def redact(text):
    mapping, reverse, counts = {}, {}, {}

    def make_sub(label):
        def sub(m):
            original = m.group()
            if label == "CARD" and not luhn_ok(re.sub(r"\D", "", original)):
                return original
            if original in reverse:
                return reverse[original]
            counts[label] = counts.get(label, 0) + 1
            token = f"<{label}_{counts[label]}>"
            mapping[token] = original
            reverse[original] = token
            return token
        return sub

    for label, pattern in PATTERNS:
        text = pattern.sub(make_sub(label), text)
    return text, mapping


def restore(text, mapping):
    for token, original in mapping.items():
        text = text.replace(token, original)
    return text


user = ("Email me at a@b.com or call 212-555-0100. SSN 123-45-6789. "
        "Order 4111 1111 1111 1112 is late; write a@b.com again.")
safe, mapping = redact(user)
print(safe)
print(mapping)
reply = "Sure, I will write to <EMAIL_1> and call <PHONE_1> about the order."
print(restore(reply, mapping))

Output:

text
Email me at <EMAIL_1> or call <PHONE_1>. SSN <SSN_1>. Order 4111 1111 1111 1112 is late; write <EMAIL_1> again.
{'<EMAIL_1>': 'a@b.com', '<SSN_1>': '123-45-6789', '<PHONE_1>': '212-555-0100'}
Sure, I will write to a@b.com and call 212-555-0100 about the order.

The order reference 4111 1111 1111 1112 fails the checksum and stays in the text, while the repeated email address reuses one placeholder. Three limits are worth stating in your own notes. Regular expressions find formatted identifiers but not names or street addresses, which need a recognition model such as the one in Presidio. The mapping is itself sensitive and should live only for the request, outside your logs. And the model may reorder or reword a placeholder, so restoring should be tested against real replies.

Check your answer

  • Does the redacted test message contain no copy of the email address, phone number or SSN?
  • Does 4111 1111 1111 1112 remain unchanged because it fails the Luhn check?
  • Does the second mention of a@b.com reuse `<EMAIL_1>` instead of creating `<EMAIL_2>`?
  • Does restore return the original email address and phone number for the sample reply?

Exercise 2

Audit a moderation threshold for uneven false positives

AnalysisIntermediateAbout 35 min (estimate)Hypothetical scenario

Your team uses a moderation score to block messages when the score is at least a threshold. Before launch you test it on benign messages from two groups of users, and on harmful messages. All scores below are invented for this exercise.

SetScores
Benign, group A0.05, 0.12, 0.20, 0.31, 0.44, 0.58, 0.09, 0.27
Benign, group B0.18, 0.36, 0.52, 0.61, 0.67, 0.29, 0.73, 0.47
Harmful0.97, 0.88, 0.76, 0.69, 0.58, 0.45, 0.93, 0.81, 0.64, 0.39

For thresholds of 0.50, 0.60 and 0.70, compute the false positive rate for each group and the recall on the harmful messages. Then design a three-way policy (block, review, allow) and count how many messages of each set land in each outcome. Finally, say what you would do before launch.

Requirements

  • Report FPR for group A, FPR for group B and recall at each of the three thresholds.
  • State the ratio between the two groups' FPR at 0.50 and what it implies about the filter.
  • Define a three-way policy with two thresholds and report the counts per outcome for group A, group B and the harmful set.
  • Name at least two actions you would take, and one reason why this sample is not enough to decide.

Expected behaviour

At 0.50 the FPR is 0.125 for group A and 0.500 for group B, with recall 0.80. At 0.70 the FPR is 0.000 and 0.125, with recall 0.50. The answer explains that raising the threshold narrows the gap but costs recall for everyone, and proposes a review band plus further investigation.

Hint 1

FPR for a group is the number of its benign messages with a score at or above the threshold, divided by the number of its benign messages.

Hint 2

Recall uses only the harmful set, with the same threshold.

Hint 3

For the three-way policy try block at 0.70 and above, review from 0.50 up to 0.70, and allow below 0.50.

Show solution

A short script gives the numbers:

python
benign = {
    "A": [0.05, 0.12, 0.20, 0.31, 0.44, 0.58, 0.09, 0.27],
    "B": [0.18, 0.36, 0.52, 0.61, 0.67, 0.29, 0.73, 0.47],
}
harmful = [0.97, 0.88, 0.76, 0.69, 0.58, 0.45, 0.93, 0.81, 0.64, 0.39]


def share_at_or_above(scores, t):
    return sum(s >= t for s in scores) / len(scores)


print("threshold  FPR_A  FPR_B  recall")
for t in (0.50, 0.60, 0.70):
    print(f"{t:>9.2f} {share_at_or_above(benign['A'], t):>6.3f} "
          f"{share_at_or_above(benign['B'], t):>6.3f} {share_at_or_above(harmful, t):>7.2f}")


def route(s):
    return "block" if s >= 0.70 else "review" if s >= 0.50 else "allow"


for name, scores in {**benign, "harmful": harmful}.items():
    routed = [route(s) for s in scores]
    print(name, {k: routed.count(k) for k in ("allow", "review", "block")})

Output:

text
threshold  FPR_A  FPR_B  recall
     0.50  0.125  0.500    0.80
     0.60  0.000  0.375    0.70
     0.70  0.000  0.125    0.50
A {'allow': 7, 'review': 1, 'block': 0}
B {'allow': 4, 'review': 3, 'block': 1}
harmful {'allow': 2, 'review': 3, 'block': 5}

At 0.50 group B's benign messages are blocked four times as often as group A's (0.500 against 0.125). The filter is treating group B's ordinary wording as more toxic-looking, and the cause could be identity terms, dialect or topic. Raising the threshold to 0.70 almost closes the gap but cuts recall from 0.80 to 0.50, so the harm is paid by everyone. The review band keeps recall useful while sending three of group B's eight benign messages and one of group A's to a person instead of blocking them; one benign group B message is still blocked, and two harmful messages still pass.

Before launch: read the group B messages that scored above 0.50 to find what drives the score; try another classifier or add context to the input; and set the review capacity from the counts. Eight messages per group cannot support a decision, since one message moves a rate by 0.125. You would need hundreds per group and a confidence interval on each rate.

Check your answer

  • Do you get FPR 0.125 for group A and 0.500 for group B at a threshold of 0.50?
  • Is recall 0.80, 0.70 and 0.50 at the three thresholds?
  • Under the three-way policy, do three of group B's benign messages go to review and one is blocked?
  • Did you point out that the sample is too small to set a production threshold?
