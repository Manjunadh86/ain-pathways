The Agent Loop (ReAct)

The agent loop is the control code that runs an AI agent. It repeatedly shows a language model the task and everything observed so far, carries out the action the model chooses, feeds the result back, and stops when the model gives a final answer or a limit is reached. ReAct is the pattern in which the model interleaves written reasoning with those actions.

1Overview

Why it matters

A single model call cannot query a database, see what came back and then decide what to do about it. The loop is what lets a tool-calling model work through a task step by step, and it is the part of an agent that you own. When an agent repeats the same search twelve times, runs up a large bill overnight, or reports success after a tool call failed, the cause is usually in the loop: a missing stopping rule, no step limit, or an error that was dropped instead of shown to the model.

Anyone who builds, debugs or reviews agents needs to read a trace as a sequence of loop iterations. Framework settings such as max_turns, max_steps and recursion_limit only make sense once you know what one iteration is and what each setting counts. The same knowledge explains why a long-running agent gets slower and more expensive with every step, and where to intervene.

Key terms

Agent loop
The repeating cycle in which a program calls a model, runs the tool the model asks for, returns the result to the model, and continues until a stopping rule fires.
Iteration
One pass through the loop, usually one model call plus the tool calls it requested. Frameworks also call it a step or a turn, and they do not all count it the same way.
ReAct
Short for Reason and Act. A pattern from a 2022 research paper in which the model alternates written reasoning with tool actions and reads the result of each action before continuing.
Thought
Free-text reasoning the model writes before acting. It changes what is in the context but has no effect on the outside world.
Action
A request from the model to run one named tool with specific arguments.
Observation
The result of an action as it is reported back to the model, including error messages when the action failed.
Context
Everything sent to the model on a call, namely instructions, tool definitions, the task and the history of earlier replies and observations.
Stopping criterion
A rule that ends the loop, such as a final answer from the model, a step limit or a spend limit.
Step limit
A hard cap on the number of iterations, enforced by the program whatever the model wants to do next.
Harness
The program around the model that builds prompts, runs tools and executes the loop. Some teams use the word for the whole agent runtime.

2Explanation

Introduction

In Tool Calling you saw one round trip: the model asks for a function, your code runs it, and the model uses the result. In What Are AI Agents? you saw that an agent, unlike a fixed workflow, chooses its own next step. The agent loop is the short piece of code that joins the two ideas. It repeats the tool-calling round trip until the task is finished.

You already work this way. When a test fails, you read the error message, form a guess about the cause, change a line and run the test again, then read the new output. You keep going until the test passes or you decide to ask a colleague. Nobody plans all of those steps in advance, because each result decides what to try next.

An agent loop gives a language model the same cycle. Each pass has four stages:

  • Perceive. The program assembles what the model will see: instructions, the task, the list of tools, and everything that has happened so far.
  • Reason. The model reads that context and decides what to do: call a tool, or give the final answer.
  • Act. The program, not the model, runs the requested tool.
  • Observe. The tool's result, or its error, is added to the history. It becomes part of what the model perceives on the next pass.

Sources name the stages differently. The Hugging Face Agents Course calls it the Thought-Action-Observation cycle (opens in a new tab) and compares it to a while loop that runs until the agent's objective is met. Google's Introduction to Agents (opens in a new tab) whitepaper, the Day 1 reading of the Kaggle agents course, lists five steps: get the mission, scan the scene, think it through, take action, observe and iterate. Both describe the same loop.

This lesson covers the ReAct pattern that made the loop standard, how to write the loop yourself in plain Python, how to decide when it should stop, and how to keep one failed step from ruining the whole run.

How it works

One iteration, four stages

Stripped of framework detail, every agent loop has the same skeleton. The block below is pseudocode; the worked example is the runnable version.

python
context = [instructions, task]            # perceive: everything the model will see
for step in range(max_steps):
    reply = model(context)                # reason: next action, or a final answer
    if reply.is_final:
        return reply.answer               # stop: the model says the task is done
    result = run_tool(reply.action)       # act: your code executes the tool
    context = context + [reply, result]   # observe: the result joins the context
return "stopped: step limit reached"      # stop: the program says enough

Three properties follow from this shape:

  • The model never executes anything. It emits a request, and your program decides whether and how to run it. That is where permissions, sandboxing and logging live.
  • The context only grows. Each iteration appends the model's reply and the observation, and the next call sees all of it. This transcript is the agent's working memory, and each observation is the model's only evidence of what really happened.
  • Two parties can end the run. The model ends it by answering. The program ends it by enforcing a limit. A loop that has only the first exit will eventually run until someone notices the bill.

The ReAct pattern

ReAct (Reason + Act) comes from a 2022 paper by Yao and colleagues (opens in a new tab). Earlier prompting styles did one half each: chain-of-thought prompts reasoned but could not look anything up, and act-only prompts issued actions without saying why. ReAct interleaves three kinds of entry in a single transcript:

EntryWritten byEffect
Thoughtthe modelNone outside the transcript. It records a plan, a fact taken from the last result, or a change of approach.
Actionthe modelAsks the program to run a tool, for example search[entity].
Observationthe programReports what the tool returned.

The paper is precise about thoughts: a thought does not affect the external environment and produces no observation. Its job is to add useful information to the context so that later steps go better.

In a text implementation the model writes Thought: and Action: lines, and the program parses the action, runs it and appends an Observation: line. One detail decides whether this works: generation must stop after the action. If it does not, the model continues and writes an Observation: line itself, which is an invented tool result. The Hugging Face Agents Course (opens in a new tab) reproduces this failure and fixes it by passing Observation: as a stop sequence.

The same pattern with native tool calling

Current chat APIs have the action format built in (see Tool Calling), so most loops no longer parse free text. The roles are unchanged:

Thoughttext or thinking blockreasoning item
Actiontool_use block, with stop reason tool_usefunction_call item
Observationtool_result block in the next user messagefunction_call_output item
Finisha response whose stop reason is end_turnan assistant message with no tool call

Anthropic's documentation describes the client loop as a while loop keyed on stop_reason (opens in a new tab): while it is tool_use, run the tools and send the results back. Any other value ends the loop, either because the model has finished (end_turn) or for a reason your code must handle, such as max_tokens. The OpenAI Agents SDK states the same rule from the other side: output is final when it is text of the expected type and contains no tool calls.

Stopping criteria

Anthropic's guide to building agents notes that a task usually ends when it is complete, but that it is common to add stopping conditions such as a maximum number of iterations to keep control. A production loop has several exits, and each one should produce a different, named outcome.

The step limit deserves the most care, because defaults differ widely and count different things:

  • The ReAct authors gave a run 7 steps on HotpotQA and 5 on FEVER before backing off to another prompting method, noting that more steps did not improve results.
  • The sample loop in Anthropic's computer use documentation defaults to 10 iterations.
  • smolagents defaults to 20 steps.
  • The Claude Agent SDK applies no turn limit and no spend limit unless you set max_turns or max_budget_usd.
  • LangGraph's recursion_limit counts graph super-steps and has defaulted to 1000 since version 1.0.6.

Do not inherit a default. Measure how many steps successful runs of your task take, set the limit a little above that, and add a spend limit as a second guard.

When a limit ends the run, say so. The Claude Agent SDK returns a result whose subtype is error_max_turns and which carries no answer text. The OpenAI Agents SDK raises MaxTurnsExceeded unless you register a handler that supplies a fallback output. In both designs the caller can tell a finished task from an abandoned one.

Why each step costs more than the last

The loop resends the whole context on every call. If the first call sends bbb tokens and each iteration adds ddd tokens (the reply plus the observation), call number kkk sends b+(k−1)db + (k-1)db+(k−1)d tokens, and nnn calls send in total:

T(n)=nb+d n(n−1)2T(n) = nb + d\,\frac{n(n-1)}{2}T(n)=nb+d2n(n−1)​

With b=1000b = 1000b=1000 and d=500d = 500d=500, ten calls send 32,500 input tokens and twenty calls send 115,000. Doubling the number of steps multiplied the input by about 3.5.

OpenAI's Codex team makes the same observation about its own loop and describes two mitigations: keep each new prompt an exact extension of the previous one so that prompt caching can reuse earlier work, and compact the conversation once it passes a token threshold. A step limit is therefore a cost control as much as a safety control. Context Engineering covers what to do about the growth itself.

Error recovery

Errors arrive at three levels, and each needs a different response.

  1. A tool fails (bad argument, timeout, service down). Catch the exception and return it as the observation. In the Claude API this is a tool_result with is_error set to true. Anthropic's guidance is to write instructive messages that say what went wrong and what to try next, because the model can only recover from what it can read.
  2. The model's output is malformed (unknown tool name, invalid JSON, missing argument). Treat it the same way, with an observation that names the problem. Frameworks differ here. The OpenAI Agents SDK raises ModelBehaviorError by default when the model names a tool that does not exist, and lets you opt in to returning a model-visible error instead.
  3. The loop itself is in trouble (provider API errors, a spent budget, the same failing action again and again). The model cannot fix these. Retry transient API failures in code, detect repeated actions, and stop with a clear status. The ReAct paper lists repetition of earlier thoughts and actions as a recurring failure.

Feeding an error back is only useful when a different action could succeed. A missing credential or a revoked permission fails identically on every retry, so stop and hand the problem to a person (see Human-in-the-Loop).

Worked example: A hand-written ReAct loop that prices an order, recovers from a bad argument and respects a step limit

The task: an order has 3 units of product A-100 and 2 units of B-200, and we want the total with 8% tax. The agent has two tools, a price lookup and a calculator. So that everyone gets identical output, the model is replaced by a script of five pre-written replies. Everything else is a real loop. The first scripted reply contains a deliberate mistake (a SKU without its hyphen) so that you can watch the loop recover.

Save this as react_loop.py. It needs only the Python standard library (3.9 or later).

python
import ast
import json
import operator
import re

PRICES = {"A-100": 19.99, "B-200": 5.50, "C-300": 42.00}
MAX_STEPS = 8
OPERATORS = {ast.Add: operator.add, ast.Sub: operator.sub,
             ast.Mult: operator.mul, ast.Div: operator.truediv}
SYSTEM_PROMPT = """Solve the task step by step. Tools:
- lookup_price(sku): unit price of a product
- calculate(expression): evaluate arithmetic
Reply with a Thought line, then either
Action: {"tool": "<name>", "args": {...}}
or
Final Answer: <answer>"""


def lookup_price(sku):
    if sku not in PRICES:
        raise ValueError(f"unknown SKU {sku!r}. Valid SKUs: {', '.join(PRICES)}")
    return f"{PRICES[sku]:.2f}"


def evaluate(node):
    if isinstance(node, ast.Constant) and isinstance(node.value, (int, float)):
        return node.value
    if isinstance(node, ast.BinOp) and type(node.op) in OPERATORS:
        return OPERATORS[type(node.op)](evaluate(node.left), evaluate(node.right))
    raise ValueError("only numbers and + - * / ( ) are allowed")


def calculate(expression):
    return f"{evaluate(ast.parse(expression, mode='eval').body):.4f}"


TOOLS = {"lookup_price": lookup_price, "calculate": calculate}


def act(reply, tools):
    """Run the action named in a model reply and return the observation text."""
    match = re.search(r"Action:\s*(\{.*\})", reply, re.S)
    if not match:
        return "ERROR: no Action found. Reply with an Action line or a Final Answer line."
    try:
        call = json.loads(match.group(1))
    except json.JSONDecodeError as error:
        return f"ERROR: Action is not valid JSON ({error.msg})."
    name, args = call.get("tool"), call.get("args", {})
    if name not in tools:
        return f"ERROR: unknown tool {name!r}. Available tools: {', '.join(tools)}."
    try:
        return tools[name](**args)
    except Exception as error:  # a failed tool call becomes an observation, not a crash
        return f"ERROR: {type(error).__name__}: {error}"


def run_agent(task, model, tools, max_steps=MAX_STEPS):
    messages = [{"role": "system", "content": SYSTEM_PROMPT},
                {"role": "user", "content": task}]
    for step in range(1, max_steps + 1):
        size = sum(len(message["content"]) for message in messages)
        print(f"--- step {step}: sending {len(messages)} messages, {size} characters")

        reply = model(messages)                           # reason
        reply = reply.split("\nObservation:")[0].strip()  # drop any observation the model wrote
        print(reply)
        messages = [*messages, {"role": "assistant", "content": reply}]

        final = re.search(r"Final Answer:\s*(.+)", reply, re.S)
        if final:                                         # stop: the model says it is done
            return {"status": "finished", "answer": final.group(1).strip(), "steps": step}

        observation = act(reply, tools)                   # act
        print(f"Observation: {observation}")
        messages = [*messages, {"role": "user", "content": f"Observation: {observation}"}]  # observe
    return {"status": "step_limit", "answer": None, "steps": max_steps}


def scripted_model(replies):
    remaining = iter(replies)  # stands in for an LLM: one scripted reply per call
    return lambda messages: next(remaining)


SCRIPT = [
    'Thought: I need the unit price of the first product.\n'
    'Action: {"tool": "lookup_price", "args": {"sku": "A100"}}',
    'Thought: The SKU format was wrong. The valid form has a hyphen.\n'
    'Action: {"tool": "lookup_price", "args": {"sku": "A-100"}}',
    'Thought: Now the second product.\n'
    'Action: {"tool": "lookup_price", "args": {"sku": "B-200"}}',
    'Thought: I have both prices. Total = (3 * 19.99 + 2 * 5.50) * 1.08.\n'
    'Action: {"tool": "calculate", "args": {"expression": "(3 * 19.99 + 2 * 5.50) * 1.08"}}',
    'Thought: 76.6476 rounds to 76.65.\n'
    'Final Answer: The order total is 76.65 USD including 8% tax.',
]
TASK = "An order has 3 units of A-100 and 2 units of B-200. What is the total with 8% tax?"

if __name__ == "__main__":
    print(run_agent(TASK, scripted_model(SCRIPT), TOOLS))
    print(run_agent(TASK, scripted_model(SCRIPT), TOOLS, max_steps=3))

Run python3 react_loop.py. The first call to run_agent prints:

text

What to notice:

  • Error recovery (steps 1 and 2). lookup_price raised a ValueError. act caught it and returned the message as the observation, so the next call could see the valid SKUs and try A-100.
  • Stopping (step 5). The reply contained Final Answer:, so the loop returned without calling a tool. Check the arithmetic: 3 × 19.99 = 59.97, 2 × 5.50 = 11.00, their sum is 70.97, and 70.97 × 1.08 = 76.6476.
  • Context growth. The prompt grew from 314 to 929 characters. Because each call resends everything, the five calls sent 314 + 507 + 647 + 755 + 929 = 3,152 characters, about 3.4 times the final prompt.
  • Step limit. The second call sets max_steps=3. It prints the same first three steps and then {'status': 'step_limit', 'answer': None, 'steps': 3}. The loop reports that it ran out of steps. It does not guess a total from the prices it has.

For a live agent, replace scripted_model(SCRIPT) with a function that sends messages to a chat model and returns its reply text, with Observation: as a stop sequence. The loop does not change.

Edge cases and limitations

The model writes its own observation
In a text-protocol loop the model may keep generating past its action and produce a plausible Observation line, which is a tool result that never happened. The Hugging Face course shows this with a weather agent. Pass the observation marker as a stop sequence, and also discard anything after the action in code, as the worked example does. Native tool calling avoids the problem because tool results can only come from your application.
Several tool calls arrive in one reply
A model can request more than one tool in a single response. Every call needs its own result before the next model call. Anthropic's computer use documentation states that a request that leaves any tool_use block unanswered is rejected, and that after a failed action the remaining actions in the batch must be answered as not executed. A hand-written loop should iterate over all calls and never assume there is exactly one.
A step is not the same unit in every framework
The OpenAI Agents SDK counts agent-loop turns, which its documentation equates with LLM calls. The Claude Agent SDK documents max_turns as counting tool-use turns only. LangGraph counts graph super-steps, and its documentation gives a default limit of 1000 from version 1.0.6. Copying a limit of 10 from one framework to another can give a very different budget. Read the definition before you set the number.
The limit arrives halfway through a change
A step limit can fire after the agent has edited a file but before it has rerun the tests, or after it created a record but before it confirmed it. The Claude Agent SDK documentation gives exactly this example, a turn cap that stops a session before the edit step, and its result still carries a session id so the run can be resumed with a higher limit. Return the trace with the limit status, design tools so that repeating them is safe, and prefer resuming over restarting.
The reply was cut off, not finished
A response that ends because the output token limit was reached is not a final answer, and it may contain half of a tool call. Anthropic's stop reason documentation says to retry such a request with a higher max_tokens value. Check the stop reason before parsing. The same page describes pause_turn, returned when a server-run tool loop reaches its own iteration limit (10 per request by default); the fix is to send the response back so the model can continue.
A spend cap can be overshot
A budget is checked after a response arrives, because the cost of a call is only known from its reported usage. The Claude Agent SDK documentation states that the response that reaches the cap still completes and is counted, so spending can pass the cap by up to one response. Set the cap below the amount you can really afford.

When to use it, and when something simpler is enough

Use it when

  • The number and order of tool calls cannot be known before the task starts, because each result changes what should happen next. Debugging, multi-hop research and navigating an unfamiliar interface are typical.
  • The environment returns feedback the model can check its progress against, such as test output, API responses or search results.
  • You can bound the run with a step limit and a spend limit, and the user can accept a response time that varies from run to run.
  • Tool actions are reversible, sandboxed or gated by approval, so a wrong step can be caught before it does lasting damage.

Think twice when

  • The steps are fixed and known in advance. A hard-coded sequence of calls is cheaper, faster and easier to test.
  • One tool call always answers the request. A single tool-calling round trip needs no loop.
  • There is a strict latency budget. Every iteration adds a full model round trip plus a tool execution.
  • Actions are irreversible and cannot be verified or approved first, for example sending money or deleting records.

A simpler alternative. A single tool-calling round trip (call the model, run the one tool it asks for, call the model again for the answer) or a fixed prompt chain where your code decides the order of steps. These stop being enough when the model must react to results in ways you cannot list in advance. A sign that you have reached that point is code that keeps gaining branches such as retrying with a different query when a search returns nothing.

Key takeaways

  • An agent loop repeats four stages (perceive, reason, act, observe) until the model gives a final answer or the program enforces a limit.
  • ReAct interleaves thoughts, actions and observations in one transcript. Native tool calling keeps the same roles, with structured tool calls and tool results in place of parsed text.
  • The model only requests actions. Your program executes them, which is why permissions, limits and logging belong in the loop.
  • Every loop needs an explicit step limit and a spend limit, and it must return a distinct status when a limit ends the run so that callers never mistake a stopped run for a finished one.
  • Return tool failures and malformed output to the model as informative observations, and stop in code when the same action repeats or when no retry could succeed.
  • Each call resends the whole context, so the total input sent grows roughly with the square of the number of steps.

Example 1 of 5

ReAct answering multi-hop questions through a Wikipedia API

Princeton University and Google ResearchDocumented in a paper

The original ReAct paper (Yao et al., first posted in 2022) evaluates the pattern on HotpotQA, a multi-hop question answering benchmark, and FEVER, a fact verification benchmark. A frozen language model has to find the facts it needs by interacting with a simple Wikipedia API. Section 3 of the paper describes the setup and results. [1]

The problem

A multi-hop question needs facts from two or more Wikipedia passages, and the model is given only the question. Reasoning-only prompting can lay out the steps but must rely on what the model remembers, which the authors found led to hallucinated facts. Acting-only prompting can retrieve passages but, in the authors' comparison, did worse at combining them into a final answer.

Where this topic fits

The loop is the whole method. The prompt holds a few solved examples and the new question. From there the model alternates thought, action and observation, with the Wikipedia API as the environment. The run ends when the model issues the finish action. In the paper's combined ReAct and CoT-SC method, a run that reaches the step cap without an answer falls back to a different prompting method.

How it is applied, step by step

  1. The prompt contains a handful of solved examples written as thought, action and observation sequences, followed by the new question.
  2. The model writes a thought, for example which entity to look up first, and then a search action naming that entity.
  3. The harness calls the API and appends the returned sentences as the observation. A typical implementation parses the bracketed action text to find the action name and its argument.
  4. The model reads the observation and writes the next thought, such as extracting a fact or deciding to reformulate the search, followed by the next action.
  5. When the model has what it needs, it issues the finish action with the answer, which ends the run.
  6. In the paper's combined method, a run that has produced no answer within the step cap falls back to the answer from self-consistent chain-of-thought prompting (CoT-SC).

Why this approach fits

What to look up second depends on what the first lookup returned, so the sequence of calls cannot be written down in advance. That is the situation where a loop beats a fixed pipeline. The written thoughts make each retrieval targeted, and they leave a transcript that a person can inspect to see where the reasoning went wrong.

Limitation or tradeoff

The loop did not win everywhere. The paper reports that ReAct alone scored slightly below chain-of-thought on HotpotQA, and its error analysis names two loop-specific failures: the model repeating earlier thoughts and actions, and uninformative search results derailing the reasoning. The best results came from combining ReAct with another method. The numbers are for 2022 models prompted with a few examples, so the absolute scores do not transfer to current models.

What the sources document

  • The paper defines three actions for the Wikipedia API. Search returns the first five sentences of an entity's page or suggests similar entities, lookup returns the next sentence on the page containing a given string, and finish ends the task with an answer. [1]
  • A thought is described as an action in the language space that does not affect the external environment and therefore yields no observation feedback; it updates the context to support future reasoning or acting. [1]
  • In the combined ReAct to CoT-SC method, when ReAct did not return an answer within 7 steps on HotpotQA or 5 steps on FEVER, the system backed off to CoT-SC. The authors state that they chose these caps because more steps did not improve ReAct performance. [1]
  • With PaLM-540B, ReAct scored 27.4 exact match on HotpotQA and 60.9 accuracy on FEVER, against 25.7 and 58.9 for the act-only baseline and 29.4 and 56.3 for chain-of-thought. The best prompting results combined ReAct with CoT-SC: 35.1 on HotpotQA and 64.6 on FEVER. [1]
  • In a manual study of HotpotQA trajectories the authors describe a frequent error pattern specific to ReAct in which the model repeatedly generates previous thoughts and actions, and report that non-informative search accounted for 23% of the error cases. [1]

The facts above come from the cited sources. The steps and analysis in this example are our explanation of how they fit together.

Example 2 of 5

Codex CLI running a local coding agent through the Responses API

OpenAIDocumented in an engineering article

OpenAI's engineering article Unrolling the Codex agent loop (January 2026) describes the harness inside Codex CLI, a software agent that runs on the developer's machine. The article explains how the harness coordinates the user, the model and the tools the model invokes. [13]

The problem

A request such as adding an architecture diagram to a README takes an unknown number of steps: reading files, running shell commands, editing and checking. The harness has to keep the model supplied with the results of each step while the prompt keeps growing. The article points out that an agent may make hundreds of tool calls in a single turn and could exhaust the model's context window.

Where this topic fits

The loop is the core logic of the harness. Before it comes prompt assembly: instructions, tool definitions, messages describing the sandbox and working directory, and the user's message. Inside it, each model response is either a tool call to execute or a message for the user. After it, control returns to the user, who may start another turn on the same history.

How it is applied, step by step

  1. Codex builds the first request from its instructions, the tool definitions (a shell tool, a plan tool, a web search tool provided by the Responses API and any tools from configured MCP servers), environment messages and the user's message.
  2. It sends the request to the Responses API and reads the stream of events that comes back.
  3. When the output contains a function call, such as a shell command, Codex runs it locally and appends the model's reasoning item, the function call and the call's output to the input list.
  4. It queries the model again with the longer input. The previous prompt is an exact prefix of the new one, which lets prompt caching reuse earlier computation.
  5. The cycle repeats until the model produces an assistant message instead of a tool call. That message ends the turn.
  6. When the conversation passes a token threshold, Codex compacts it by replacing the input with a smaller list of items that represents the conversation so far.

Why this approach fits

A code change can be checked against the environment: file contents and command output tell the model whether its last step worked. Each iteration therefore brings real evidence, which is what a loop needs. Appending to the input rather than rewriting it keeps every request self-contained and keeps earlier content stable for caching.

Limitation or tradeoff

The article confirms that the amount of data sent grows quadratically over a conversation, and that caching only helps when the start of the prompt is unchanged. It lists changes that cause a cache miss, including changing the available tools or the model in the middle of a conversation. Compaction frees context by replacing history with a shorter representation, so detail from early steps may no longer be available to the model. The article describes context management rather than a fixed step cap as the control on long turns.

What the sources document

  • The article states that each inference step ends in one of two ways: the model produces a final response, or it requests a tool call, in which case the agent executes the call, appends the output to the prompt and queries the model again. [13]
  • The process repeats until the model stops emitting tool calls and produces an assistant message. Every turn ends with an assistant message, which the article describes as a termination state of the agent loop. [13]
  • Codex CLI runs inference by sending HTTP requests to the Responses API, and the old prompt is deliberately an exact prefix of the new prompt so that later requests can benefit from prompt caching. [13]
  • The author agrees that the loop is quadratic in the amount of JSON sent over a conversation, says Codex does not use previous_response_id so that requests stay stateless and Zero Data Retention configurations are supported, and notes that with cache hits sampling is linear instead of quadratic. [13]
  • Codex compacts the conversation automatically when the auto_compact_limit is exceeded, using a dedicated compact endpoint of the Responses API that returns a shorter list of items to continue from. [13]

Example 3 of 5

Claude computer use, a loop whose observations are screenshots

AnthropicDocumented in official docs

Anthropic's computer use documentation describes how an application lets Claude operate a desktop with mouse, keyboard and screenshot actions. The application runs an agent loop between the Claude API and a container or virtual machine that the developer controls. [10][8]

The problem

A graphical interface cannot be operated in one shot. The model does not know where a button is until it sees the screen, and it does not know whether a click worked until it sees the screen again. The application has to carry each requested action to the machine and bring back what the screen now shows, many times, with no person in between.

Where this topic fits

The documentation names the concept directly: the agent loop is the repeated exchange in which Claude responds with tool requests and the application responds with their results, without user input. The application's half of the loop is code the developer writes. Perception arrives as a screenshot image inside a tool result.

How it is applied, step by step

  1. The application sends the task with the computer use toolset declared in the request.
  2. Claude replies with one or more actions, such as taking a screenshot, clicking or typing, and a stop reason that signals tool use.
  3. The application performs each action in order on its own machine and returns one result per action: an image for a screenshot or a zoom, a short text for the others.
  4. If an action fails, the application marks that result as an error and answers the remaining actions in the batch as not executed. Claude sees which actions succeeded and plans again.
  5. Claude reads the results and either requests more actions or replies with text, which ends the loop.
  6. The sample loop in the documentation also stops after a fixed number of iterations.

Why this approach fits

The state of a screen can only be learned by looking, and every action changes it. Perceive, act and observe is therefore the only workable structure. Keeping the loop in the developer's application also puts the developer in charge of the environment, of any confirmation step before a consequential action, and of the iteration cap.

Limitation or tradeoff

Each iteration costs a model call and usually an image, so desktop tasks take many more round trips than the same task done through an API. In the shape shown above, reaching the cap and finishing normally both return the message list, so the caller must inspect the last message to tell them apart. Screens can also show content from outside sources. Anthropic's tool documentation warns that tool results may carry injected instructions and should be treated as untrusted.

What the sources document

  • The documentation defines the agent loop as the repetition, without user input, of the application returning tool results and Claude responding with further tool use requests. [10]
  • If Claude determines that more actions are needed it responds again with a tool_use stop reason; otherwise it returns a text response to the user. [10]
  • The simplified example loop on the page takes a max_iterations parameter with a default of 10 and runs until Claude stops requesting tools or the iteration limit is reached. [10]
  • When an action fails the application returns an error result for that block, later actions in the same batch are answered as not executed, and Claude replans on its next turn. A request that leaves any tool_use block unanswered is rejected. [10]
  • The tool-call documentation says tool results often carry content from sources outside the developer's control and should be treated as untrusted, because such content may embed instructions that try to redirect the model. [8]

Amazon Bedrock Agents, a managed orchestration loop with an inspectable trace

Amazon Web ServicesDocumented in official docs

The Amazon Bedrock user guide describes how a Bedrock agent processes an InvokeAgent request and how its trace exposes each orchestration step. AWS now calls the service Amazon Bedrock Agents Classic and has closed it to new customers, while existing customers can continue to use it. [14][15]

The problem

A company wants an assistant that completes user requests by calling its internal APIs, defined as action groups, and by querying its knowledge bases. It does not want to write and operate the loop itself, and it needs to be able to see why the agent took each step when something goes wrong.

Where this topic fits

The loop is the orchestration stage of the documented runtime sequence. It sits between an optional pre-processing step that validates and categorises the input and an optional post-processing step that formats the final response. AWS runs the loop. The developer supplies instructions, action groups backed by Lambda functions, knowledge bases and, if needed, edited prompt templates.

How it is applied, step by step

  1. The InvokeAgent call starts the sequence, and pre-processing can validate the user's input.
  2. In orchestration, the foundation model interprets the input and produces a rationale for the next step.
  3. The agent predicts which action to invoke or which knowledge base to query. It either calls the Lambda function for the action group or returns control to the calling application with the parameters.
  4. The output of the action or query becomes an observation, which is added to the prompt for the next model call.
  5. The loop continues until the agent returns a response to the user or needs to ask the user for more information.
  6. With tracing turned on, the rationale, invocation input and observation of every step can be inspected afterwards.

Why this approach fits

The trace has the same three parts as a ReAct transcript, namely a rationale, an action and an observation, so an operator can audit a run step by step without access to the loop's code. A managed loop also gives every agent in an organisation the same structure, which makes traces comparable.

Limitation or tradeoff

The service runs the loop, so its stopping behaviour is not the developer's code. The two pages cited here describe how to customise prompts and parsers for each step but do not describe a step limit that the developer sets. The product is also in maintenance mode: the user guide says it is no longer open to new customers and points to Amazon Bedrock AgentCore. Read this example as evidence of the pattern in a managed service, not as a recommendation for a new build.

What the sources document

  • The runtime sequence started by InvokeAgent has three main steps, pre-processing, orchestration and post-processing, and post-processing is turned off by default. [14]
  • During orchestration the agent generates a rationale, predicts an action to invoke or a knowledge base to query, and produces an observation that augments the base prompt. The guide states that this loop continues until the agent returns a response to the user or needs to prompt the user for extra information. [14]

  • The Observation object in the trace has a type field with values that include ACTION_GROUP, KNOWLEDGE_BASE, REPROMPT, ASK_USER and FINISH, and its finalResponse field appears when the type is ASK_USER or FINISH. [15]

Example 5 of 5

smolagents, an open-source ReAct loop with a step cap and final-answer checks

Hugging FaceDocumented in an open-source project

smolagents is Hugging Face's open-source agent library. Its documentation states that every agent in the library is built on one class, MultiStepAgent, which it describes as an abstraction of the ReAct framework. The conceptual guide, guided tour and API reference describe the loop and its settings. [16][17][18][19][20]

The problem

A general-purpose library cannot know the task in advance. Its users need one reusable loop that works with many models and tools, records each step so that runs can be inspected, cannot run forever, and can refuse a final answer that fails the application's own checks, such as an answer that must be an integer.

Where this topic fits

The loop is the core of the library and is what runs when a user calls the agent's run method. The system prompt and task are stored first. Then each iteration turns memory into messages, calls the model, parses an action, executes it and logs the result. The run ends on a call to the final answer tool or at the step cap.

How it is applied, step by step

  1. When a run starts, the system prompt and the task are stored as the first entries in the agent's memory.
  2. Each iteration converts the memory into chat messages and sends them to the model.
  3. The completion is parsed into an action: a JSON tool call for a ToolCallingAgent, or a Python snippet for a CodeAgent.
  4. The action is executed and its result is logged in memory as an action step, so the next model call sees it. Errors are logged the same way.
  5. The run ends when the agent calls the final answer tool or reaches the maximum number of steps.
  6. Optional final-answer checks validate the proposed answer. If a check fails, the failure is logged and the loop continues.

Why this approach fits

An explicit final answer tool gives the loop an unambiguous stop signal that does not depend on a particular provider's response format. The step cap bounds the run whatever the model does. The checks let the application, not only the model, decide whether the task is done, which closes the gap between the model saying it has finished and the answer being usable.

Limitation or tradeoff

A default of 20 steps is a ceiling, not a budget: each step still resends the whole memory. Agents that write code as their action need an isolated place to run it, and the guided tour notes that local execution is potentially unsecure (see Code Execution and Sandboxing). The library's own guidance is that giving a model agency adds error risk and that the simplest workflow with the fewest model calls is usually best.

Reaching the cap also does not return an empty result. In the library source for version 1.26.0, a run that uses up its steps makes one more model call that writes a final answer from the agent's memory. Only the full result object, requested with return_full_result=True, records the state max_steps_error. A caller that reads just the returned answer cannot tell a capped run from a finished one.

What the sources document

  • The documentation states that all agents in smolagents are based on the MultiStepAgent class, which it calls an abstraction of the ReAct framework. [16]
  • The documented loop writes the agent's memory to chat messages, sends them to the model, parses the completion into an action (a JSON blob for ToolCallingAgent, a code snippet for CodeAgent), then executes the action and logs the result into memory. [16]
  • The API reference lists max_steps as the maximum number of steps the agent can take to solve the task, with a default of 20. [18]
  • By default an agent runs until it calls the final_answer function or reaches the maximum number of steps. If any function passed as final_answer_checks returns False, the agent logs the error and continues the run. [17]
  • The guide on building good agents says well-programmed agentic systems have error logging and retry mechanisms so that the model has a chance to correct its mistake, and that an error trace logged in memory can help the model fix a failed tool call. [19]

4Common mistakes

  1. Relying on the model to stop and setting no step or spend limit.

    Why it causes problems
    A model that keeps calling tools will keep being called. Because each call resends a longer context, the cost of a runaway run grows faster than its length, and nothing ends it except a provider error or a person noticing.
    How to recognise it
    Traces with dozens of near-identical calls, runs that end in a context-length error, or a framework setting left at a default you have never looked up.
    How to fix it
    Set an explicit step limit based on how many steps successful runs take, add a token or cost limit, and test both by forcing a run to hit them.

  2. Letting a tool exception propagate out of the loop.

    Why it causes problems
    A mistyped argument or a brief network failure ends the whole run, although the model could have corrected the call on the next iteration if it had seen the message.
    How to recognise it
    Runs that fail on the first bad argument, and stack traces in your logs where an observation should be.
    How to fix it
    Catch exceptions around tool execution and return them as the observation, with a message that names what was wrong and what a valid call looks like. Reserve hard stops for failures the model cannot fix.

  3. Returning the model's last text as the answer when the step limit fires.

    Why it causes problems
    The caller receives a partial thought or a guess that looks like a result. Downstream code, or a user, acts on an answer that no observation supports.
    How to recognise it
    Answers that cannot be traced to any tool result, and return types with no field that distinguishes a finished run from a stopped one.
    How to fix it
    Return a status alongside the answer, with distinct values for finished, step limit, budget and stuck, and make callers handle each one.

  4. Parsing a text-protocol reply without a stop sequence.

    Why it causes problems
    The model writes the observation itself, then reasons from the invented result. The tool never ran, but the transcript reads as if it did.
    How to recognise it
    Observation text in the transcript with no matching entry in the tool execution log, or a tool result that arrives faster than the tool could have run.
    How to fix it
    Pass the observation marker as a stop sequence, discard any text after the action before parsing, or move to native tool calling where the API ends the response at the tool call.

  5. Appending every tool result to the context in full.

    Why it causes problems
    One large file or verbose command output is paid for again on every later call, and it pushes the run towards the context window limit long before the step limit.
    How to recognise it
    A sudden jump in input tokens after one step that never comes back down, and long runs that slow with each iteration.
    How to fix it
    Cap the size of each observation, return summaries or the relevant slice with a way to fetch more, and compact old history in long sessions.

  6. Returning error observations that say only that something failed.

    Why it causes problems
    The model has nothing to correct, so it repeats the same call or abandons a task it could have completed. Steps are spent without progress.
    How to recognise it
    The same action appearing twice or more in a row after an error whose text gives no detail.
    How to fix it
    Include the cause and the valid alternatives in the message, as the worked example does by listing the valid SKUs, and add a guard that detects repeated actions.

Exercise 1

Add a repeated-action guard to the hand-written loop

CodingIntermediateAbout 40 min (estimate)Hypothetical scenario

Start from react_loop.py in the worked example. The scripted model below is stuck: it sends the same invalid action on every call.

python
STUCK_SCRIPT = [
    'Thought: I need the price.\nAction: {"tool": "lookup_price", "args": {"sku": "A100"}}'
] * 8

With the original loop, run_agent(TASK, scripted_model(STUCK_SCRIPT), TOOLS) runs the failing tool eight times and ends with status step_limit. Write a new version of run_agent that notices the repetition and stops early. You need only the Python standard library.

Requirements

  • Two actions count as the same when they name the same tool with the same arguments, whatever the spacing or key order of the JSON.
  • When an action is identical to the one in the previous step, do not run the tool again. Return an observation that tells the model the action was repeated and that it must try something else.
  • When the same action arrives three times in a row, stop and return a result with status stuck.
  • Add a tool_calls field to every returned result, counting how many times the loop tried to execute an action.
  • The original SCRIPT from the worked example must still finish in 5 steps with the same answer.

Expected behaviour

With STUCK_SCRIPT the result is {'status': 'stuck', 'answer': None, 'steps': 3, 'tool_calls': 1}: the tool runs once, the second attempt gets a warning instead of a tool run, and the third ends the run.

With the original SCRIPT the result is {'status': 'finished', 'answer': 'The order total is 76.65 USD including 8% tax.', 'steps': 5, 'tool_calls': 4}.

Hint 1

Parse the action JSON and re-serialise it with json.dumps and sort_keys=True. Comparing those strings ignores spacing and key order.

Hint 2

Keep two extra variables between iterations: the previous action's canonical string and a count of how many times in a row it has appeared.

Hint 3

A reply with no valid action should never count as a repeat, so reset the counter when parsing fails.

Show solution

Save this next to react_loop.py as guarded_loop.py. It reuses the tools, prompt and act function and replaces only the loop.

python
import json
import re

from react_loop import MAX_STEPS, SCRIPT, SYSTEM_PROMPT, TASK, TOOLS, act, scripted_model

MAX_REPEATS = 3
REPEAT_WARNING = (
    "WARNING: this is the same action as the previous step, so it was not run again. "
    "Read the previous observation and choose a different action."
)


def action_key(reply):
    """Canonical text of the action in a reply, or None when there is no valid action."""
    match = re.search(r"Action:\s*(\{.*\})", reply, re.S)
    if not match:
        return None
    try:
        return json.dumps(json.loads(match.group(1)), sort_keys=True)
    except json.JSONDecodeError:
        return None


def run_agent(task, model, tools, max_steps=MAX_STEPS):
    messages = [
        {"role": "system", "content": SYSTEM_PROMPT},
        {"role": "user", "content": task},
    ]
    previous_key, repeats, tool_calls = None, 0, 0
    for step in range(1, max_steps + 1):
        reply = model(messages).split("\nObservation:")[0].strip()
        messages = [*messages, {"role": "assistant", "content": reply}]

        final = re.search(r"Final Answer:\s*(.+)", reply, re.S)
        if final:
            return {"status": "finished", "answer": final.group(1).strip(),
                    "steps": step, "tool_calls": tool_calls}

        key = action_key(reply)
        repeats = repeats + 1 if key is not None and key == previous_key else 1
        previous_key = key
        if repeats >= MAX_REPEATS:  # third identical action in a row: give up
            return {"status": "stuck", "answer": None, "steps": step, "tool_calls": tool_calls}

        if repeats == 2:            # second identical action: warn instead of re-running
            observation = REPEAT_WARNING
        else:
            observation = act(reply, tools)
            tool_calls += 1
        messages = [*messages, {"role": "user", "content": f"Observation: {observation}"}]
    return {"status": "step_limit", "answer": None, "steps": max_steps, "tool_calls": tool_calls}


STUCK_SCRIPT = [
    'Thought: I need the price.\nAction: {"tool": "lookup_price", "args": {"sku": "A100"}}'
] * 8

if __name__ == "__main__":
    print(run_agent(TASK, scripted_model(STUCK_SCRIPT), TOOLS))
    print(run_agent(TASK, scripted_model(SCRIPT), TOOLS))

Running python3 guarded_loop.py prints:

text
{'status': 'stuck', 'answer': None, 'steps': 3, 'tool_calls': 1}
{'status': 'finished', 'answer': 'The order total is 76.65 USD including 8% tax.', 'steps': 5, 'tool_calls': 4}

Why it is built this way. The guard compares parsed JSON, not raw text, so a model that changes only its wording or spacing is still caught. The first repeat produces a warning observation, which gives the model one chance to change course at the cost of a model call but no tool call. The second repeat ends the run with its own status, so the caller can tell a stuck agent from one that hit the step limit. In the original script no two consecutive actions are identical (the SKU changes from A100 to A-100), so the guard never fires and the result matches the worked example.

  • Does the stuck script end after 3 steps with status stuck and exactly 1 tool call?
  • Does the original script still return 76.65 USD after 5 steps and 4 tool calls?
  • If you add spaces inside the JSON of the second stuck reply, is it still detected as a repeat?
  • Does a reply with no Action line reset the repeat counter instead of counting as a repeat?

Exercise 2

Size a step limit from a token budget

AnalysisBeginnerAbout 20 min (estimate)Hypothetical scenario

A support agent's first model call sends 1,500 input tokens: the system prompt, the tool definitions and the customer's message. Logs show that each loop iteration adds about 700 tokens to the context (the model's reply plus the tool result). The team wants no single run to send more than 100,000 input tokens in total. Ignore output tokens and caching.

  1. Write the formula for the total input tokens after nnn model calls, and compute it for n=15n = 15n=15 and n=16n = 16n=16.
  2. What is the largest step limit that keeps a run within the budget? How many tokens does the last call send at that limit?
  3. A colleague truncates tool results so that each iteration adds only 300 tokens. What is the largest step limit now?
  4. Name two stopping conditions, other than a step limit, that this agent should have. Say what each one returns to the caller.

Requirements

  • Use the formula from this lesson and show the arithmetic for each value you report.
  • Give whole-number step limits and check both the limit and the next value above it.
  • For part 4, name the signal the loop checks and the status or value it returns.

Expected behaviour

Part 1 gives 96,000 tokens for 15 calls and 108,000 for 16. Part 2 gives a step limit of 15, with a last call of 11,300 tokens. Part 3 gives a step limit of 21. Part 4 names two conditions from the stopping table in this lesson, each with a distinct return value.

Hint 1

The first call sends 1,500 tokens and every later call sends 700 more than the one before it.

Hint 2

The sum 0 + 1 + 2 + ... + (n - 1) equals n(n - 1) / 2. Multiply it by the tokens added per iteration.

Hint 3

For parts 2 and 3 you can test values of n one at a time; there is no need to solve a quadratic.

Show solution

  • T(15) = 22,500 + 350 × 210 = 22,500 + 73,500 = 96,000
  • T(16) = 24,000 + 350 × 240 = 24,000 + 84,000 = 108,000

Part 2. 96,000 is within the budget and 108,000 is not, so the largest step limit is 15. The last call at that limit sends 1,500 + 700 × 14 = 11,300 tokens, more than seven times the first call.

Part 3. With 300 tokens per iteration the total is 1500n+150 n(n−1)1500n + 150\,n(n-1)1500n+150n(n−1).

  • T(21) = 31,500 + 150 × 420 = 31,500 + 63,000 = 94,500
  • T(22) = 33,000 + 150 × 462 = 33,000 + 69,300 = 102,300

The largest step limit is 21. Cutting the growth per step by 57% bought 6 more steps, a 40% increase, because the fixed 1,500 tokens are still resent on every call.

Part 4. Any two of these, with the signal and the return value:

  • Spend limit. Signal: the running total of tokens or cost passes the cap. Return: a budget status with the usage so far and the trace.
  • Needs a person. Signal: the model asks the customer a question, or it requests an action that policy says needs approval, such as a refund above a threshold. Return: the question or the pending action, with enough state to resume.
  • No progress. Signal: the same action or the same error twice in a row. Return: status stuck with the trace.
  • Output cut off. Signal: the stop reason reports that the output token limit was reached. Return: nothing to the caller yet; retry the call with a higher limit.

The normal exit, a final answer with no tool call, is assumed and does not count as one of the two.
