Git and GitHub Workflows

Git is a version control system that records a project as a chain of commits, each one a snapshot of every tracked file. A GitHub workflow is the routine a team agrees on (branch, commit, push, pull request, review, merge) for moving those commits into a shared repository.

1Overview

Why it matters

Almost every piece of software you touch on an engagement lives in a Git repository, and most of those are hosted on GitHub or on a service that works the same way. Git decides whether your change can be reviewed, tested, shipped and, when necessary, undone. When two people edit the same file, Git is what notices. When a release breaks, the commit history is how the team finds the change that broke it.

A forward deployed engineer usually works in a repository that someone else owns. The customer's team has already decided how branches are named, what a commit message looks like, who must approve a change and which merge button is allowed. A pull request that ignores those rules is blocked by automation or by a reviewer, and a careless force push can erase a colleague's work. If you understand the mechanics (what a commit, a branch, a merge and a rebase really are), you can follow any team's conventions without having to memorise one team's commands.

Before you start

No prerequisites. You can start here.

What you will be able to do

  • Describe a commit, a branch and HEAD in terms of snapshots and pointers.
  • Predict whether a merge will fast-forward, create a merge commit or stop with a conflict.
  • Explain what a rebase does to commit hashes and state when rebasing is unsafe.
  • Resolve a conflict by reading the markers, then finish or abort the merge or rebase.
  • Take a change through a pull request and choose between merge commit, squash and rebase merging.
  • Find and follow a repository's conventions before making the first commit in it.

Key terms

Repository
The project folder plus Git's hidden .git directory, which holds every commit ever recorded for the project.
Commit
A saved snapshot of all tracked files, stored with an author, a message and a link to the commit or commits that came before it.
Hash (SHA)
The identifier Git computes from an object's content: 40 hexadecimal characters in a standard SHA-1 repository. Change anything in a commit and its hash changes.
Staging area
The list of changes that will go into your next commit. Git also calls it the index.
Branch
A named pointer to one commit. It moves forward each time you commit while on that branch.
HEAD
Git's pointer to where you are now: normally the branch you have checked out, or a specific commit when HEAD is detached, as it is in the middle of a rebase.
Remote
A copy of the repository hosted somewhere else, such as on GitHub. The one you cloned from is usually named origin.
Merge commit
A commit with two or more parents, recorded when Git combines branches that each have commits the other lacks.
Rebase
Replaying your commits one at a time on top of a different commit, which creates new commits with new hashes.
Pull request
A proposal on GitHub to merge one branch into another, where the change is discussed, checked automatically and approved.

2Explanation

Introduction

You have probably saved a file as report_final.docx, then report_final_v2.docx, then report_final_v2_REAL.docx. That is version control done by hand. Each copy is a save point you can return to. The method stops working when there are two hundred files, or when two people edit their own copies and someone has to combine them.

Git automates the save points. A commit is a snapshot of the whole project at one moment, with a message that says why it was made. Each commit links back to the one before it, so the project carries its full history. A branch is a separate line of commits where you can work without disturbing anyone else. All of this is stored on your own machine, in a hidden .git folder inside the project, so committing, branching and reading history are fast and work offline.

GitHub adds the shared part. It hosts a copy of the repository that the whole team can reach, and it adds the pull request: a page where you propose merging your branch, automated checks run, teammates review the change and the merge is recorded. A typical change travels like this:

GitHub's documentation calls the shortest version of this routine GitHub flow (opens in a new tab): create a branch, make changes, create a pull request, address review comments, merge, delete the branch. Teams add their own rules on top, and those rules differ from one repository to the next.

This lesson explains the mechanics first (commits, branches, merges and rebases), then the collaboration layer (pull requests, code review and conflicts), and finally how to read the rules of a repository you did not set up, such as a customer's. Command behaviour was checked against the Git reference pages for versions 2.54 to 2.56 (2.56 is the newest release in October 2026), and the worked example and the first exercise were run with Git 2.55.0. If the terminal is new to you, start with Linux and the Shell.

How it works

Commits are snapshots with an address

Many older tools store a list of changes per file. Git stores snapshots (opens in a new tab). Each commit records what every tracked file looked like, and a file that did not change is stored as a link to the copy Git already has. A commit object holds a pointer to that snapshot, the author's name and email, the message, and a pointer to its parent commit. The first commit has no parent, an ordinary commit has one, and a merge commit has two or more.

Git names every object by a checksum of its content, a 40-character SHA-1 hash such as 24b9da6552252987aa493b52f8696cd6d3b00373. Two consequences matter every day. A commit cannot be edited in place, because any change gives a different hash and therefore a different commit. And because a commit records its parent's hash, a single hash pins down the whole history behind it.

Git can also create repositories that use SHA-256, whose hashes are 64 characters long. SHA-1 is still the default for new repositories, so every hash in this lesson is SHA-1.

Three places a change can be

PlaceWhat it holdsCommand that moves a change onward
Working treeThe files you editgit add <file>
Staging area (index)What will go into the next commitgit commit -m "message"
Repository (.git)Commits, stored permanentlygit push copies them to a remote

The staging area lets a commit contain exactly one logical change even when your working tree holds several. git status shows what is in each place, and git diff --staged shows what the next commit will contain.

A commit message is read far more often than it is written. The Git documentation (opens in a new tab) suggests a summary line of no more than 50 characters, a blank line, then a fuller description. Git treats the text before the first blank line as the commit's title and shows it throughout its tools.

Branches are pointers

A branch (opens in a new tab) is a small file that holds the hash of one commit. Creating a branch writes 41 bytes and copies nothing. When you commit, the branch you are on moves forward to the new commit, and HEAD records which branch that is.

bash
git switch -c fix-login     # create a branch at the current commit and switch to it
git switch main             # go back (Git 2.23 or later; older guides use git checkout)
git push -u origin fix-login   # upload the branch and link it to its copy on the remote

Your clone also keeps remote-tracking branches such as origin/main. They record where the remote's branches were the last time you fetched from or pushed to it, which matters later for safe force pushes.

Merging has three outcomes

git merge other brings the work on other into the branch you are on. The result (opens in a new tab) depends on the shape of the history.

  1. Fast-forward. Your branch has no commits that other lacks. Git moves your branch pointer forward and creates no new commit.
  2. Three-way merge. Both branches have new commits. Git compares each tip with their common ancestor, called the merge base, combines the two sets of changes and records a merge commit whose parents are the two tips.
  3. Conflict. A three-way merge in which both sides changed the same lines, or one side edited a file that the other deleted. Git stops and asks you to decide.

For each region of a file the rule is mechanical. If only one side changed it since the merge base, Git takes that side. If both made the identical change, Git takes it once. If they changed it differently, that is a conflict.

Rebasing gives the same files and new commits

Run on your branch, git rebase main replays (opens in a new tab) your commits one at a time on top of main. The final files are the same as a merge would produce, but the history is a straight line with no merge commit.

The replayed commits are new commits. They have new parents, so they have new hashes, and the originals are abandoned. That is harmless for commits only you have. For commits that other people have built on, it forces everyone to repair their own history, which is why Pro Git (opens in a new tab) states the rule this way: do not rebase commits that exist outside your repository and that people may have based work on.

After you rebase a branch you had already pushed, a plain git push is refused, because the remote branch is no longer an ancestor of yours. Use git push --force-with-lease (opens in a new tab). It overwrites the remote branch only if that branch still points where your remote-tracking branch says it does, so a teammate's newer push is not silently destroyed. Plain --force skips that check.

Conflicts

When a merge or rebase stops, Git writes both versions into the file between markers (opens in a new tab):

text
<<<<<<< HEAD
timeout_seconds: 20
=======
timeout_seconds: 60
>>>>>>> raise-timeout

The block above ======= is the version on HEAD, the branch you were on. The block below it comes from the branch being merged in. Resolving means editing the file until it is correct and the three marker lines are gone. You may keep either side, combine them or write something new.

StepDuring a mergeDuring a rebase
Mark the file resolvedgit add <file>git add <file>
Finishgit commitgit rebase --continue
Give up and restore the earlier stategit merge --abortgit rebase --abort

During a rebase the two sides are swapped. Git is replaying your commits onto the other branch, so the top block (HEAD) is the branch you are rebasing onto and the bottom block is your own commit. Setting git config merge.conflictStyle zdiff3 adds a middle block that shows the merge base, which often makes the right answer obvious.

Pull requests and code review

A pull request (opens in a new tab) proposes merging your branch (the head) into another branch (the base). With push access you push your branch to the shared repository. Without it you fork the repository, push to your fork and open the pull request from there. A draft pull request shares unfinished work: it cannot be merged, and code owners are not asked to review it yet.

A review (opens in a new tab) is submitted as a comment, an approval or a request for changes. You respond by pushing more commits to the same branch, and the pull request updates itself. Small pull requests get better reviews. Google's engineering guide (opens in a new tab) says that 100 lines is usually a reasonable size for a change and 1,000 lines is usually too large, though it leaves the final call to your reviewer.

Once the pull request is approved, GitHub offers up to three merge methods (opens in a new tab). The repository's settings decide which of them are available.

The repository's rules

Every team layers conventions on top of these mechanics. Most are written down inside the repository or enforced by its settings.

Where to lookWhat it tells you
CONTRIBUTING.md (opens in a new tab) in the root, docs/ or .github/Branch names, commit message format, how to run tests, whether to rebase or merge
Pull request template (opens in a new tab)The sections every pull request description must fill in
CODEOWNERS (opens in a new tab)Who is asked to review each path. The last matching pattern wins
Branch protection rulesRequired approvals and status checks, signed commits, linear history
git log --oneline -20 on the default branchWhat merged commits really look like, whatever the documents say

Branch protection (opens in a new tab) is the part that says no. A protected branch refuses force pushes and deletion by default. It can also require pull request reviews, passing status checks (see CI/CD Pipelines), a branch that is up to date with its base, signed commits, or a linear history, which allows only squash and rebase merges.

In a customer's repository, read before you write. Clone it, read the files above, open three recently merged pull requests and copy their shape: branch name, commit style, description and size. Ask which merge method the team uses and whether they update branches by rebasing or by merging. Do not push to the default branch directly, and do not rewrite a branch that someone else has pushed to.

Worked example: One line changed on two branches: merge it, then rebase it, and compare the results

Two people changed the same setting. On main a teammate lowered a timeout to 20 seconds. On your branch you raised it to 60 and switched logging to debug. You will combine the work twice, once with a merge and once with a rebase, and confirm that both roads end at the same files. You need Git 2.28 or later and a terminal (Git Bash on Windows).

1. Build the history.

bash
mkdir timeout-demo && cd timeout-demo
git init -b main
git config user.name "Demo User"
git config user.email "demo@example.com"

printf 'service: billing-api\ntimeout_seconds: 30\nretries: 3\nregion: eu-west-1\nlog_level: info\n' > config.yaml
git hash-object config.yaml
git add config.yaml
git commit -m "Add service config"

git switch -c raise-timeout
printf 'service: billing-api\ntimeout_seconds: 60\nretries: 3\nregion: eu-west-1\nlog_level: debug\n' > config.yaml
git commit -am "Raise timeout to 60 seconds for slow exports"

git switch main
printf 'service: billing-api\ntimeout_seconds: 20\nretries: 3\nregion: eu-west-1\nlog_level: info\n' > config.yaml
git commit -am "Lower timeout to 20 seconds to fail fast"

git log --oneline --graph --all

git init -b main names the first branch; without -b the name comes from your Git configuration and may be master. git hash-object prints 8d4aebb1c64416587aa2457e8936896b4f3d23c4 on any machine, because a file's hash depends only on its bytes. A commit's hash also covers the author, the time and the parent, so your commit hashes will differ from the placeholders used below:

text
* 7c1d2e4 (HEAD -> main) Lower timeout to 20 seconds to fail fast
| * 4b8e9a1 (raise-timeout) Raise timeout to 60 seconds for slow exports
|/
* 1f3a9c2 Add service config

The history has forked. Each branch has one commit the other lacks, and the merge base is 1f3a9c2.

2. Road A: merge. Use a scratch branch so that main stays untouched.

bash
git switch -c try-merge
git merge raise-timeout
cat config.yaml

The merge stops, and cat shows what Git left in the file:

text
Auto-merging config.yaml
CONFLICT (content): Merge conflict in config.yaml
Automatic merge failed; fix conflicts and then commit the result.
service: billing-api
<<<<<<< HEAD
timeout_seconds: 20
=======
timeout_seconds: 60
>>>>>>> raise-timeout
retries: 3
region: eu-west-1
log_level: debug

Apply the three-way rule to the two lines that changed:

LineMerge baseHEAD (try-merge)raise-timeoutResult
timeout_seconds302060Both sides changed it differently, so Git reports a conflict
log_levelinfoinfodebugOnly one side changed it, so Git takes debug without asking

Git cannot know which timeout is right. Suppose you ask your teammate and agree on 45. Write the resolved file, mark it resolved and finish the merge:

bash
printf 'service: billing-api\ntimeout_seconds: 45\nretries: 3\nregion: eu-west-1\nlog_level: debug\n' > config.yaml
git add config.yaml
git commit -m "Merge branch 'raise-timeout' into try-merge"
git log --oneline --graph
text
*   9d0e1f2 (HEAD -> try-merge) Merge branch 'raise-timeout' into try-merge
|\
| * 4b8e9a1 (raise-timeout) Raise timeout to 60 seconds for slow exports
* | 7c1d2e4 (main) Lower timeout to 20 seconds to fail fast
|/
* 1f3a9c2 Add service config

The merge commit 9d0e1f2 has two parents, 7c1d2e4 and 4b8e9a1.

3. Road B: rebase. Go back to your branch and replay it onto main.

bash
git switch raise-timeout
git rebase main
cat config.yaml

Git reports the same CONFLICT (content) line, then error: could not apply 4b8e9a1... and hints naming the three ways out: --continue, --skip and --abort. The file has the same two blocks, but read the labels:

text
<<<<<<< HEAD
timeout_seconds: 20
=======
timeout_seconds: 60
>>>>>>> 4b8e9a1 (Raise timeout to 60 seconds for slow exports)

HEAD is now main's commit, because Git moved to the tip of main and is replaying your commit onto it. Your own change is the bottom block. Resolve to 45 again and continue. GIT_EDITOR=true accepts the existing commit message without opening an editor.

bash
printf 'service: billing-api\ntimeout_seconds: 45\nretries: 3\nregion: eu-west-1\nlog_level: debug\n' > config.yaml
git add config.yaml
GIT_EDITOR=true git rebase --continue
git log --oneline --graph
text
* 5e6f7a8 (HEAD -> raise-timeout) Raise timeout to 60 seconds for slow exports
* 7c1d2e4 (main) Lower timeout to 20 seconds to fail fast
* 1f3a9c2 Add service config

The history is a straight line and your commit has a new hash: 5e6f7a8 has replaced 4b8e9a1. Its message still says 60 although the file says 45, so in real work you would run git commit --amend to correct the message before pushing.

4. Fast-forward and compare.

bash
git switch main
git merge raise-timeout
git rev-parse 'main^{tree}' 'try-merge^{tree}'

After the Switched to branch 'main' line, the output is:

text
Updating 7c1d2e4..5e6f7a8
Fast-forward

 1 file changed, 2 insertions(+), 2 deletions(-)
ddd58e1b8d4b4bd33a5a7a4fd23bb6edd494eb39
ddd58e1b8d4b4bd33a5a7a4fd23bb6edd494eb39

main had no commits of its own to combine, so the merge was a fast-forward: the pointer moved and no commit was created. The last two lines are the hashes of the two final snapshots. They are identical, and you will get the same value, because both roads ended with the same file contents. Merge and rebase produced the same project with different histories. One history has a merge commit and the original 4b8e9a1. The other is linear and contains a rewritten commit.

Edge cases and limitations

A merge with no conflicts can still break the build
Git merges text, not meaning. If one branch renames a function and another adds a call to the old name, the two changes touch different lines, merge cleanly and fail at run time. This is why GitHub offers the strict setting Require branches to be up to date before merging, and a merge queue that reruns checks on the combined result so the branch is never broken by incompatible changes. Run the tests after every merge or rebase, even a clean one.
One side edited a file that the other side deleted
There are no markers to edit in this kind of conflict. GitHub's guide shows git status listing the file as deleted by us; when the other branch removed it, Git says deleted by them. You decide the file's fate as a whole: git add the file to keep it, or git rm the file to accept the deletion, then commit as usual.
A rebase of several commits can stop several times
A merge resolves all conflicts once, in the merge commit. A rebase replays commits one at a time and stops at the first commit that does not apply, so a branch of five commits that each touch the conflicting lines can stop five times. If that happens, git rebase --abort, squash the branch into fewer commits and try again, or use a merge if the team allows merge commits on feature branches.
Reusing a branch after a squash merge
After Squash and merge, the base branch holds one new commit and none of your branch's commits. GitHub's documentation warns that if you keep working on the same head branch, later pull requests can include commits that were already squashed, which makes conflicts more likely. Delete the branch after the merge and start the next piece of work on a new branch cut from the updated base.
A background fetch weakens --force-with-lease
The lease compares the remote branch with your remote-tracking branch. The Git documentation warns that this interacts very badly with anything that runs git fetch in the background, such as a scheduled job or an editor integration, because the fetch updates the remote-tracking branch to include a teammate's commits that you have never looked at, and the check then passes. Adding --force-if-includes makes Git also verify that the remote tip was integrated into your local branch.
GitHub's Rebase and merge is not the same as git rebase
GitHub's documentation states that its rebase and merge always updates the committer information and creates new commit SHAs, whereas git rebase leaves the committer information alone when the rebase happens on top of an ancestor commit. The commits on the base branch are therefore different objects from the ones on your local branch, even when your branch was already up to date. Compare by content or pull request number, not by hash.

When to use it, and when something simpler is enough

Use it when

  • More than one person changes the same codebase, or one person needs to return to earlier states of their own work and see why each change was made.
  • Use a merge commit to combine branches whose commits have already been shared, or when the team wants to see in the history where a branch joined.
  • Use rebase to bring a branch that only you work on up to date with its base, or to tidy its commits before review.
  • Use squash merging when a pull request is one logical change and its intermediate commits (typo fixes, review feedback) would only add noise to the base branch.
  • Use a pull request with required checks and review whenever a broken default branch would block other people or reach production.

Think twice when

  • Do not rebase, amend or force push commits that teammates have already pulled or built on. Merge instead, or add a new commit.
  • Do not commit secrets such as API keys. A later commit that removes the file does not remove it from the history that every clone carries, so the key must be rotated.
  • Do not use plain Git as storage for large binary files that change often, such as datasets or model weights. Every version stays in the history that each clone carries, so the repository grows with each change and stays large unless the history is rewritten.

A simpler alternative. For a solo project, committing straight to main and pushing is enough, with no branches and no pull requests. Add a branch per change as soon as a second person contributes or you want a change reviewed before it lands. Add branch protection once a broken main would stop other people from working.

Key takeaways

  • A commit is an immutable snapshot named by a hash of its content, and a branch is only a movable pointer to one commit.
  • Merging two diverged branches compares both tips with their common ancestor and records a merge commit. When only one side has new commits, Git fast-forwards the pointer and creates nothing.
  • Rebasing replays your commits onto a new base and gives them new hashes, so it is safe for commits only you have and harmful for commits that others have built on.
  • A conflict means both sides changed the same lines. You resolve it by editing the file, staging it and then committing or continuing the rebase, and you can always abort.
  • A pull request is where checks and reviewers approve a change, and the repository's settings decide whether it lands as a merge commit, one squashed commit or rebased commits.
  • In someone else's repository, read the contributing guide, the CODEOWNERS file and the branch rules, and copy the shape of recently merged pull requests before you write code.

5 documented uses of Git and GitHub Workflows. Each one names the real system, the problem it solves and its tradeoff, with links to the sources.

  1. Linux kernel: written rules for when a maintainer may rebase and when to merge
  2. Kubernetes: OWNERS files and comment commands route each pull request through two approvals

Example 1 of 5

Linux kernel: written rules for when a maintainer may rebase and when to merge

Linux kernelDocumented in official docs

The Linux kernel's maintainer documentation includes a page called Rebasing and merging, written for the subsystem maintainers who collect patches in their own Git trees and send them upstream as pull requests. A companion page, Submitting patches, sets the rules for each individual commit. [21][22][8]

The problem

Kernel development happens in many Git trees at once, and people routinely pull from each other's trees. The documentation opens by saying that maintainers often get in trouble when they use rebase and merge incorrectly. Rewriting history that someone else has already pulled creates work for everyone downstream, and merging the upstream tree back into a subsystem tree for no reason (a back merge) muddies the history of that tree.

Where this topic fits

The rules apply between a contributor's patch and the mainline tree. A maintainer applies patches to a branch, may reorganise that branch while it is private, then publishes it and asks for it to be pulled. From the moment of publication the history is normally left unchanged, and merging is the tool for combining it with other work.

How it is applied, step by step

  1. A contributor splits the work into patches that each contain one logical change, so that the kernel builds and runs properly after every patch and git bisect can stop at any point in the series.
  2. Each commit message describes the change in imperative mood and ends with a Signed-off-by line, which git commit -s adds automatically.
  3. A maintainer applies the patches to a branch. While that branch exists only on the maintainer's own system, rebasing it to fix a broken commit or reorder patches is acceptable.
  4. Once the branch has been exposed to others, the maintainer stops rewriting it. If its starting point really must change, the documentation says to choose a stable point such as an -rc release, not a random commit, and to treat the series as needing fresh testing.
  5. The maintainer does not merge mainline back into the subsystem tree just to stay current. If a conflict with mainline is expected, the maintainer warns about it in the pull request and leaves the conflict visible.
  6. The upstream maintainer pulls the branch, which normally records a merge commit showing where the subsystem's work joined mainline.

Why this approach fits

The line the kernel draws is publication, which is exactly where rebasing changes from harmless to harmful. A rebase creates new commits, so rewriting a published branch leaves every downstream copy holding commits that no longer exist upstream. A merge keeps the published commits exactly as they were tested and adds one commit that records the join. Rebase stays available where it is safe, for cleaning up private work before anyone else sees it.

Limitation or tradeoff

The rules are stated as rules of thumb ("should usually not be changed"), so they depend on a maintainer's judgement. The kernel exchanges patches by email and pull requests between trees, not through GitHub pull requests, so its review tags do not map onto an Approve button. Requiring every commit in a series to build and run is also more work per commit than teams that squash on merge ask for.

What the sources document

  • The page states that history which has been exposed to the world beyond a maintainer's private system should usually not be changed, because others may have pulled a copy of the tree and built on it. [21]
  • It tells maintainers not to rebase a branch that contains history created by others, and warns that reparenting a patch series changes the environment in which it was developed and likely invalidates much of the testing that was done. [21]
  • It reports that the 5.1 development cycle included 1,126 merge commits, nearly 9% of the total, and says that Linus is adamant he would much rather see merge conflicts than unnecessary back merges. [21]
  • The patch submission guide requires each patch to contain one logical change and the kernel to build and work after each patch in a series, because developers using git bisect may split the series at any point. [22]
  • A Signed-off-by line certifies that the contributor wrote the patch or has the right to submit it, and git commit -s adds it. Git's own documentation names the Developer Certificate of Origin as the sign-off used by the Linux kernel and Git projects. [22][8]

The facts above come from the cited sources. The steps and analysis in this example are our explanation of how they fit together.

Example 2 of 5

Kubernetes: OWNERS files and comment commands route each pull request through two approvals

KubernetesDocumented in official docs

The Kubernetes contributor guide documents how pull requests to the project's repositories are reviewed and merged. OWNERS files inside the repository name the reviewers and approvers for each directory, and an automation system called Prow reads commands typed in pull request comments and merges approved changes. [23][24][25][16]

The problem

A project of this size receives pull requests that touch many directories, each looked after by a different group. One maintainer cannot review everything, and handing the merge button to a large number of people would make it unclear who had checked what. The OWNERS guide's overview says that the quality of a person's code review is limited by their familiarity with the code under review. It also refers to the idea of having at least two sets of eyes on a pull request: reviewers check code quality, correctness and style, and approvers check wider concerns such as compatibility and API definitions.

Where this topic fits

The process sits between opening a pull request from a fork and the merge. Contributors do not press a merge button at all. Review, approval and merging are driven by labels that the automation applies in response to comment commands.

How it is applied, step by step

  1. The contributor forks the repository, creates a branch and keeps it current with git fetch upstream followed by git rebase upstream/master, as the workflow guide instructs.
  2. After the push and the pull request, automation finds the OWNERS files nearest to the changed code, requests at least two reviewers and lists suggested approvers in a comment.
  3. A reviewer checks code quality, correctness and style. If the change looks good, the reviewer comments /lgtm and Prow adds the lgtm label.
  4. The author assigns the suggested approvers. An approver, who must be listed in the relevant OWNERS file, checks wider concerns such as compatibility and API definitions, then comments /approve.
  5. When one approver from each identified OWNERS file has approved, Prow adds the approved label. With both labels present, no blocking label such as do-not-merge/hold, and the presubmit jobs passing, the pull request is merged automatically.
  6. If review feedback left fixup commits behind, the author squashes them with an interactive rebase and pushes with --force-with-lease, or asks the bot to squash by adding a label.

Why this approach fits

Ownership is stored in files that live next to the code they govern, so it is visible to every contributor and versioned like everything else in the repository. Splitting review (/lgtm, open to organisation members) from approval (/approve, restricted to OWNERS) spreads the reading work across many people while keeping a named owner accountable for each directory. GitHub's built-in CODEOWNERS file solves a similar routing problem, but there an approval from any one owner of a path satisfies the requirement, and it does not separate the two roles.

Limitation or tradeoff

The process depends on Prow, custom automation that most teams do not run. The OWNERS guide lists its own quirks: an approver's /lgtm can also act as an /approve, which works against having two sets of eyes (the pull request guide says Prow's behaviour is configurable per project), and unresponsive reviewers or approvers can stall a pull request. Because the workflow guide asks contributors to update a branch by rebasing and not by merging, they must force push after each update, and a force push can make it harder for a reviewer to see what changed since the last look. The pull request guide softens this by asking authors not to squash until review is nearly finished.

What the sources document

  • An OWNERS file lists approvers, the GitHub usernames or aliases that can /approve a pull request, and reviewers, who are good candidates to /lgtm it. [23]
  • In the documented review process, automation chooses at least two suggested reviewers and one suggested approver from each relevant OWNERS file, a reviewer's /lgtm makes Prow apply the lgtm label, and only people listed in the relevant OWNERS files can act as approvers. [23]
  • A pull request is merged automatically when required labels such as lgtm and approved are present, blocking labels such as do-not-merge/hold are absent, and any configured presubmit jobs pass after being re-run one last time. [23]
  • The workflow guide tells contributors to update a branch with git fetch upstream and git rebase upstream/master, and asks them not to use git pull because it performs a merge and creates merge commits. [24]
  • The pull request guide asks for commit subject lines of 50 characters or less and never more than 72, a body wrapped at 72 characters, imperative mood, and no GitHub keywords or @mentions in commit messages. [25]

GitHub: a merge queue that tests pull requests together before they reach main

GitHubDocumented in an engineering article

A March 2024 post on GitHub's engineering blog describes how the company replaced a manual process called trains in its own large monorepo with merge queue, and says that by 2023 all of its repositories responsible for production services were on the queue. GitHub Docs describes how the feature works for any repository. [20][19][15]

The problem

The post says that by 2016 nearly 1,000 pull requests a month were merging into GitHub's large monorepo. To test and deploy changes together, the team grouped pull requests into a train, a special pull request managed by a person called the conductor. Trains could hold the changes of 15 pull requests, and a conflict between two of them could remove a developer's change after a wait of more than eight hours. Underneath is a general problem: a pull request tested against yesterday's main says little about whether it works on top of the changes that merged since.

Where this topic fits

The queue is the last gate before the default branch. A pull request first passes its own checks and review as usual. The developer then adds it to the queue in place of pressing merge, and the queue decides the order, reruns the checks on the combined code and performs the merge.

How it is applied, step by step

  1. An administrator enables Require merge queue in the branch protection for main, and the CI workflows are set to run on the merge_group event as well as on pull requests.
  2. When a pull request has passed its required checks and reviews, a user with write access adds it to the queue.
  3. The queue creates a temporary branch that contains the latest target branch, the changes from the pull requests ahead in the queue, and this pull request.
  4. CI runs the required checks on that temporary branch, so the code being tested is the code that main would contain after the merge.
  5. If the checks pass, the changes are merged into the target branch. If they fail, or the pull request conflicts with the base, it is removed from the queue and the entries behind it are regrouped.

Why this approach fits

Git can tell you that two changes do not overlap as text. It cannot tell you that they work together. Testing each pull request on top of everything queued ahead of it catches that class of failure before it lands. GitHub Docs describes the queue as giving the benefit of requiring branches to be up to date without making each author update the branch and wait for checks again, which matters when main moves many times an hour. The queue also automates work that the post says a human conductor used to handle, and GitHub Docs says it merges pull requests in first-in-first-out order.

Limitation or tradeoff

Every merge now waits for a second run of the checks, including one-line changes, and a failing pull request ahead of yours forces a rebuild of the entries behind it. The queue only protects against failures that the required checks can detect. It needs CI that responds to the merge_group event, and GitHub Docs presents it as useful for busy branches with many merges a day, so a small repository gains little. The numbers are GitHub's own report about its own product.

What the sources document

  • The post states that by 2016 nearly 1,000 pull requests were merging into GitHub's large monorepo every month, and that a train was a special pull request grouping several pull requests to be tested, deployed and merged together, handled by a user called a conductor. [20]
  • It says developers could wait more than eight hours after joining a train, only to be removed because of a conflict between two pull requests in the train. [20]
  • GitHub reports that every month over 500 engineers merge 2,500 pull requests into its large monorepo with merge queue, and that the average wait time to ship a change fell by 33%. [20]
  • GitHub Docs states that a pull request is removed from the queue if, after being grouped with the latest target branch and the changes ahead of it, required status checks fail or it conflicts with the base branch. [19]
  • Repositories that run required checks with GitHub Actions must add the merge_group event to their workflows, and third-party CI must run on branches that begin with the prefix gh-readonly-queue/{base_branch}. Require merge queue is a branch protection setting. [19][15]

Example 4 of 5

Microsoft release flow: short-lived topic branches, sprint release branches and cherry-picked hotfixes

MicrosoftDocumented in a case study

The Microsoft Learn article How Microsoft develops with DevOps describes the branching and release flow that Microsoft says it uses across its teams, which the article calls the Microsoft release flow. The article sits in the Azure DevOps documentation, so its pull request pages and branch policies are Azure DevOps features, and the underlying Git mechanics are the same as on GitHub. [26][9]

The problem

The article describes teams of several hundred developers in a single repository who can complete over 200 pull requests into main per day. It argues that deploying every pull request to production before merging would leave developers waiting in a deployment queue. The teams release on a three-week sprint cadence instead, which raises a second problem: an urgent fix has to reach production between releases without ever being lost from main.

Where this topic fits

This is a branching strategy, the answer to where commits live between a laptop and production. Normal work flows from a topic branch through a pull request into main and later into a release branch. A hotfix follows the same path into main and then takes one extra step, a cherry-pick into the release branch that is currently deployed.

How it is applied, step by step

  1. A developer syncs to the latest main and creates a short-lived topic branch, usually named users/<username>/feature. Unfinished features are hidden behind feature flags, not kept on long-lived branches.
  2. The developer pushes the branch and opens a pull request. Branch policies build the change and run a fast test pass, and the owners of the touched code are added as reviewers automatically.
  3. When the policies pass and reviewers sign off, the topic branch merges into main. Slower acceptance tests run after the merge.
  4. At the end of a sprint the team creates a release branch from main, for example releases/M129, and deploys that branch. Main stays open for the next sprint's work.
  5. For a hotfix, the developer makes the fix on a topic branch from main and merges it into main through the normal pull request first.
  6. The merged change is then cherry-picked into the release branch through a new pull request that targets the release branch, where it is reviewed, tested and deployed.
  7. The next release branch, releases/M130, is cut from main and so already contains the fix. The old release branch is abandoned and is never merged back.

Why this approach fits

Fixing main first makes the dangerous mistake impossible. If the fix existed only on the release branch, production would look healthy until the next release branch was cut from main and the bug came back. In the main-first order the only thing that can be forgotten is the cherry-pick, and that omission is visible immediately because production is still broken. A cherry-pick suits the job because it copies one commit's change without bringing along everything else that has landed in main since the release branch was created.

Limitation or tradeoff

A cherry-pick creates a new commit with a different hash, and Git keeps no link between the two unless you record one with -x (which Git adds only to cherry-picks without conflicts), so knowing which fixes are in which release takes discipline. The release branch may have drifted from main, so the cherry-pick can conflict or need small adjustments. While two release branches are live during a rollout the fix must be ported to both. The model also depends on feature flags, which carry their own cost, and the article notes that requirements differ between Microsoft teams.

What the sources document

  • Developers create short-lived topic branches off the main branch for every contribution, usually named users/<username>/feature, and avoid long-running feature branches by using feature flags. [26]
  • The pull request process builds the proposed change and runs a quick test pass; the article says the first- and second-level test suites run around 60,000 tests in less than five minutes. [26]
  • Some teams have several hundred developers working in a single repository who can complete over 200 pull requests into the main branch per day, and deployments are batched into timed releases that usually follow a three-week sprint cadence. [26]
  • At the end of each sprint the team creates a release branch from main, such as releases/M129, and release branches never merge back to the main branch. [26]
  • A hotfix always starts with the change in main and is then cherry-picked into the release branch through a new pull request targeting that branch. The article explains that fixing only the release branch would let the bug recur at the next deployment. [26]

Where this topic fits

The convention applies at the earliest step of the workflow, git commit, and it is the kind of rule a newcomer finds in a repository's contributing guide. GitHub links to that guide when someone opens a pull request. The message has to be right by the time the commit lands on the main branch, because that is the history release tooling reads.

How it is applied, step by step

  1. The contributor reads the commit guideline in the repository's contributing docs before making the first commit.
  2. Each commit gets a header of the form type(scope): short summary. The type comes from a fixed list and the scope is the name of the npm package the change affects.
  3. The summary is written in the imperative present tense, with no capital first letter and no final period.
  4. The body explains why the change is being made. It is mandatory for every type except docs and must be at least 20 characters long.
  5. The footer carries structured notes, a BREAKING CHANGE or DEPRECATED block and references to the issues or pull requests the commit closes.
  6. A release tool can then group commits by scope and type. A typical implementation parses the header with a pattern like the one below, and the releases page shows the outcome as per-package tables.

Why this approach fits

The person who knows whether a change is a fix, a feature or a breaking change is its author, at the moment of writing the commit. Capturing that as a small fixed vocabulary in the header turns the Git history itself into the data source for release notes. Nobody has to maintain a separate changelog file by hand, a file that every pull request would otherwise edit and conflict on.

A format check verifies syntax, not truth, so a breaking change labelled fix passes. 4Common mistakes

  1. Staging everything with git add . and committing without reading what was staged.

    Why it causes problems
    Unrelated edits, debug output, generated files or a credentials file end up in the commit. Reviewers have to wade through noise, and a secret that reaches a pushed commit stays in the history of every clone even after a later commit deletes the file.
    How to recognise it
    The Files changed tab of your pull request lists files you do not remember editing, or the diff contains changes that the description does not mention.
    How to fix it
    Run git status and git diff --staged before every commit and stage paths deliberately. Keep generated files out with a .gitignore entry. If a secret was pushed, rotate it first and clean up second.

  2. Rebasing or amending a branch that a teammate has already pulled, then force pushing it.

    Why it causes problems
    The rewritten commits have new hashes, so the teammate's clone now holds commits that no longer exist on the remote. Their next pull produces duplicates or conflicts, and a plain --force can delete commits they pushed in the meantime.
    How to recognise it
    git push is rejected as non-fast-forward right after you rebased, on a branch other people also push to. Teammates report that the branch has diverged or that commits appear twice.
    How to fix it
    On a shared branch, add new commits or merge. Rewrite only branches that you alone work on. When a rewrite of a pushed branch is necessary, tell the people involved and use --force-with-lease, never plain --force.

  3. Resolving every conflict by keeping your own block and deleting the other one.

    Why it causes problems
    The other author's change disappears without any error, because Git accepts whatever you stage as the resolution. During a rebase it is worse, since the sides are swapped and the block labelled HEAD is the other branch, so people who think they are keeping their own change discard it.
    How to recognise it
    After the merge, a fix that a teammate landed last week is gone, or tests that passed on both branches now fail. Searching the project for <<<<<<< also finds markers that were committed by accident.
    How to fix it
    Read both blocks and, with merge.conflictStyle set to zdiff3, the base version too. Decide what the code should do, ask the other author when unsure, run the tests, and only then git add. If the resolution is going badly, git merge --abort or git rebase --abort and start again.

  4. Opening one large pull request that mixes a feature, a refactor and formatting changes.

    Why it causes problems
    Reviewers skim large diffs, so real problems are missed. The branch lives longer, which means more conflicts with main, and when something breaks the whole change has to be reverted together.
    How to recognise it
    The diff runs to a thousand lines or more, the description needs the word also, or a reviewer asks which part of the diff is the behaviour change.
    How to fix it
    Split the work into pull requests that each make one self-contained change, keeping tests with the code they test. Put refactoring and reformatting in their own pull requests, merged first.

  5. Carrying a previous team's habits into a new repository without checking its rules.

    Why it causes problems
    A merge commit pushed where linear history is required, a commit message in the wrong format or a missing sign-off gets the pull request blocked by automation. On a customer engagement it also costs the reviewers' time and some of their trust.
    How to recognise it
    Required checks fail on things that are not code, such as a commit message lint, or review comments are about process and not about your change.
    How to fix it
    Before the first commit, read CONTRIBUTING.md, the pull request template and CODEOWNERS, look at how recently merged pull requests were written, and ask a maintainer how branches are updated and merged.

  6. Letting a feature branch live for weeks without taking in changes from the default branch.

    Why it causes problems
    The longer two lines of history stay apart, the more of the same files both will have changed. The eventual merge has many conflicts at once, each needing knowledge of work done weeks ago by someone else.
    How to recognise it
    GitHub reports that the pull request has conflicts that must be resolved, or the branch is hundreds of commits behind its base.
    How to fix it
    Keep branches short-lived and merge small pieces often, hiding unfinished features behind a flag if necessary. Update a longer-running branch from its base every day or two, by rebase or merge according to the team's rule.

Exercise 1

Squash a pushed branch and update it without destroying a teammate's commit

Hands-onIntermediateAbout 45 min (estimate)Hypothetical scenario

A bare repository on your own disk can stand in for GitHub, so this exercise needs only Git 2.28 or later. The setup creates a "remote" and your clone, and leaves a pushed branch with three untidy commits.

bash
mkdir lease-lab && cd lease-lab
git init --bare -b main remote.git

git init -b main you && cd you
git config user.name "You" && git config user.email "you@example.com"
printf 'def greet(name):\n    return "Hello " + name\n' > greet.py
git add greet.py && git commit -m "Add greet function"
git remote add origin ../remote.git
git push -u origin main

git switch -c add-farewell
printf '\ndef farewell(name):\n    return "Bye " + name\n' >> greet.py
git commit -am "Add farewell function"
printf 'print(farewell("debug"))\n' >> greet.py
git commit -am "wip debug print"
printf 'def greet(name):\n    return "Hello " + name\n\ndef farewell(name):\n    return "Goodbye " + name\n' > greet.py
git commit -am "Remove debug print, say Goodbye"
git push -u origin add-farewell

Part A. Reduce the three commits on add-farewell to one commit with the message Add farewell function, without changing the content of greet.py. Print git rev-parse 'HEAD^{tree}' before and after. Then update the remote branch: try a plain git push first, read the rejection, and then push in the safest way that works.

Part B. A teammate clones the repository and adds a commit to your branch:

bash
cd .. && git clone remote.git teammate && cd teammate
git config user.name "Teammate" && git config user.email "mate@example.com"
git switch add-farewell
printf 'def greet(name):\n    return "Hello " + name\n\ndef farewell(name):\n    """Return a goodbye message."""\n    return "Goodbye " + name\n' > greet.py
git commit -am "Document farewell" && git push
cd ../you

Without fetching, you decide to reword your commit and push it:

bash
git commit --amend -m "Add farewell helper"
git push --force-with-lease

Explain what happens and why. Say what plain --force would have done. Then bring your clone to a state that contains the teammate's commit.

Requirements

  • After part A, git log --oneline main..HEAD shows exactly one commit, with the message Add farewell function.
  • The tree hash printed before the squash equals the tree hash printed after it.
  • The remote branch is updated in part A with --force-with-lease, not with --force.
  • In part B the teammate's commit Document farewell is still on the remote branch at the end.
  • Your final local branch contains the teammate's commit and git status reports a clean working tree.

Expected behaviour

Part A: both tree hashes are 06a2315f83dc7540ef4cbf5e857c80f1d7aa3d37. The plain push is rejected with the reason (non-fast-forward). git push --force-with-lease succeeds and its summary line ends with (forced update).

Part B: git push --force-with-lease is rejected with the reason (stale info) and the remote branch is unchanged. After you fetch and adopt the remote branch, git log --oneline -3 lists Document farewell, Add farewell function and Add greet function, and git rev-parse 'HEAD^{tree}' prints a369c88ec390cdbae04f801b2c46590464fb5690.

Hint 1

git reset --soft main moves the branch pointer back to main but leaves your files and the staging area exactly as they are, ready for one new commit. An interactive rebase (git rebase -i main) is the other route.

Hint 2

After the squash your branch and the remote branch have diverged, because your new commit is not a descendant of the three commits you pushed earlier.

Hint 3

The lease compares the remote branch with origin/add-farewell, your record of where the remote branch was at your last fetch or push. Ask what that record says in part B and what the remote really holds.

Hint 4

A reworded commit message is rarely worth rewriting a branch that now holds someone else's work. Consider giving up the reword.

Show solution

Part A. Squash with a soft reset, then push.

bash
git rev-parse 'HEAD^{tree}'        # 06a2315f83dc7540ef4cbf5e857c80f1d7aa3d37
git reset --soft main              # branch pointer goes back to main; files and index stay
git commit -m "Add farewell function"
git rev-parse 'HEAD^{tree}'        # the same hash: the snapshot did not change
git log --oneline main..HEAD       # one commit
git push

The push fails:

text
 ! [rejected]        add-farewell -> add-farewell (non-fast-forward)
error: failed to push some refs to '../remote.git'

The remote branch still points at the third of your old commits. Your new commit is not a descendant of it, so accepting the push would throw those commits away, and Git refuses by default. Here that is what you want, and nobody else has touched the branch, so overwrite it with a lease:

bash
git push --force-with-lease

The summary line reads + <old>...<new> add-farewell -> add-farewell (forced update). The lease held because the remote branch was exactly where origin/add-farewell said it was.

Part B. The amended commit is another rewrite, so it also needs a forced push, but this time the output is:

text
 ! [rejected]        add-farewell -> add-farewell (stale info)
error: failed to push some refs to '../remote.git'

Your origin/add-farewell still points at your squashed commit. The remote branch has moved on to the teammate's commit. The two differ, so the lease is broken and Git leaves the remote alone. Plain --force performs no such comparison. It would have replaced the remote branch with your reworded commit, and Document farewell would have vanished from the remote without any message.

Look at what you nearly destroyed, then adopt the shared history and drop the reword:

bash
git fetch origin
git log --oneline HEAD..origin/add-farewell   # Document farewell, and the commit your amend replaced
git reset --hard origin/add-farewell
git log --oneline -3
git rev-parse 'HEAD^{tree}'        # a369c88ec390cdbae04f801b2c46590464fb5690

git reset --hard discards the amended commit, which is acceptable because it only changed a message. If the rewrite had mattered, the right move would be to talk to the teammate first, because any further rewrite forces them to reset their clone as well. The rule from the lesson applies as soon as a second person pushes to a branch: stop rewriting it.

An interactive rebase also solves part A. Run git rebase -i main, keep pick on the first line and change the other two to fixup. The resulting tree hash is the same.

  • Do both tree hashes in part A equal 06a2315f83dc7540ef4cbf5e857c80f1d7aa3d37?
  • Did the plain git push fail with non-fast-forward, and did --force-with-lease report a forced update?
  • Did the second --force-with-lease fail with stale info while the remote kept the commit Document farewell?
  • After the recovery, does git rev-parse 'HEAD^{tree}' print a369c88ec390cdbae04f801b2c46590464fb5690?
  • Can you explain in one sentence what the lease compares and why a background fetch would defeat it?

  • Did you assign the Terraform file to @acme/sre-leads and not to @acme/infra?

  • Do your commands for question 5 use git rebase origin/main and git push --force-with-lease?
  • Did you mention that the approval may be dismissed when the pushed commits change the diff?
