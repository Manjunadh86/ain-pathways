k-Nearest Neighbors

k-nearest neighbors (k-NN) predicts the label or value of a new example by finding the k most similar examples in the stored training data and letting them vote (classification) or averaging their values (regression). Similarity is measured as a distance between feature vectors.

1Overview

Why it matters

k-NN is the simplest model that makes useful predictions. There is no training step and only one idea: similar inputs have similar outputs. That makes it a baseline you can stand up in minutes, a model that absorbs new labelled examples the moment they arrive, and a prediction you can explain by showing the actual neighbours behind it. The lookup at its core, finding the stored vectors closest to a query vector, is also the operation inside recommendation systems, semantic search and vector databases. Understanding where it works and where it breaks pays off twice: once as a classifier and again when you build retrieval over embeddings.

Almost everything that goes wrong is in the distance, not in the vote. A feature measured in thousands silently outvotes one measured in fractions. Irrelevant columns scramble the neighbours. With many features every point is far from every other, so the "nearest" neighbours are not similar at all. And because the model is the stored data, memory and prediction time grow with every row, which is what pushes large systems from exact search to approximate search. Anyone who builds a classifier on tabular data, or a search or recommendation feature on embeddings, needs to recognise these failures.

Key terms

Feature vector
The list of numbers that describes one example, such as a song's tempo and energy. k-NN treats it as a point in space.
Distance metric
A rule that turns two feature vectors into one number saying how far apart they are. A smaller distance means the examples are more similar.
Euclidean distance
Straight-line distance. Square the difference in each feature, add the squares and take the square root.
k (number of neighbours)
The number of stored neighbours consulted for each prediction. It is a hyperparameter that you choose; nothing in the data sets it.
Majority vote
The classification rule of k-NN. The predicted class is the one that appears most often among the k nearest neighbours.
Lazy learner
A model that only stores the training data when it is fitted and does all of its computation when a prediction is requested.
Standardisation
Rescaling a feature by subtracting its mean and dividing by its standard deviation, so that every feature has a comparable spread.
Curse of dimensionality
The effect that, as features are added, data become sparse and the distances between points become nearly equal, so the nearest neighbours are no longer similar.
Approximate nearest neighbour (ANN) search
Search that examines only part of the stored data and returns most, but not necessarily all, of the true nearest neighbours in far less time.
Recall (of a search)
The fraction of the true k nearest neighbours that an approximate search actually returned. Exact search has a recall of 1.

2Explanation

Introduction

You already predict this way. To guess what a flat should rent for, you look at a few similar flats and take roughly their average. To guess whether a friend will like a film, you think of people with similar taste and ask what they thought. k-nearest neighbors (k-NN) turns that habit into an algorithm: to predict something about a new example, find the kkk most similar examples you have already seen and let them decide.

Here is a concrete case. Fourteen songs have been sorted by hand into two playlists, "calm" and "workout". Each song is described by two features (measured inputs): its tempo in beats per minute and an energy score between 0 and 1. A new song arrives with a tempo of 119 BPM and an energy of 0.86. Which playlist should it join?

On the chart the answer looks easy. The three dots closest to the new song are one calm song and two workout songs, so a vote among k=3k = 3k=3 neighbours says "workout". That is the whole method: store the labelled examples, measure the distance from the new point to each of them, keep the kkk nearest and take a majority vote. For a numeric target such as a rent, average the neighbours' values instead of voting. Nothing is fitted in advance, which is why k-NN is called a lazy learner: all the work happens when a prediction is requested.

Three decisions are hidden inside the word "closest", and they are the subject of this lesson.

  • What distance means. The chart quietly stretched both axes to the same width. The raw numbers are not so polite: tempo differences are in the tens and energy differences are fractions. The worked example shows the prediction flipping to "calm" when that is ignored. Choosing a distance metric and scaling the features is most of the craft.
  • How many neighbours to ask. One neighbour copies whatever the nearest example says, mistakes included. Too many, and the vote is dominated by songs that are not similar at all. The value of kkk is chosen with cross-validation.
  • How to find the neighbours quickly. Comparing against fourteen songs is instant. Comparing against a hundred million is not, which leads to exact search structures and then to approximate search, the engine inside vector databases.

A fourth issue cuts across all three. As the number of features grows, every point drifts far from every other point and "nearest" stops meaning "similar". This is the curse of dimensionality, and it decides when k-NN is the wrong tool.

How it works

Prediction is a lookup

Fitting a k-NN model stores the training rows, possibly inside an index that speeds up search. scikit-learn's user guide (opens in a new tab) calls neighbour methods non-generalizing, because they remember the training data instead of building a compact model. A prediction for a query point xxx takes three steps:

  1. Compute the distance from xxx to every stored point.
  2. Keep the kkk points with the smallest distances. Call this set Nk(x)N_k(x)Nk​(x).
  3. For classification, return the label with the most votes in Nk(x)N_k(x)Nk​(x). For regression, return the mean of the neighbours' target values.

The distance does the modelling

The usual family of metrics is the Minkowski distance between points xxx and zzz with DDD features:

d(x,z)=(∑j=1D∣xj−zj∣p)1/pd(x, z) = \Big( \sum_{j=1}^{D} \lvert x_j - z_j \rvert^{p} \Big)^{1/p}d(x,z)=(j=1∑D​∣xj​−zj​∣p)1/p

With p=2p = 2p=2 this is Euclidean distance, the straight-line distance and scikit-learn's default. With p=1p = 1p=1 it is Manhattan distance, the sum of absolute differences, which is less dominated by one large gap in a single feature. For text and embedding vectors the common choice is cosine distance, one minus the cosine of the angle between two vectors, which compares direction and ignores length. On vectors scaled to length 1 it ranks neighbours exactly as Euclidean distance does, because ∥a−b∥2=2−2cos⁡(a,b)\lVert a - b \rVert^2 = 2 - 2\cos(a, b)∥a−b∥2=2−2cos(a,b). For yes/no features, Hamming distance counts the positions that differ.

Whatever the metric, two consequences follow from adding up differences across features.

  • Features must be on comparable scales. A feature measured in large numbers swamps the rest. In scikit-learn's feature-scaling example (opens in a new tab) one wine feature ranges up to about 1,000 and another only up to about 10, so without scaling the neighbours are chosen almost entirely by the first. Standardise each feature (subtract its mean, divide by its standard deviation) and fit the scaler on training data only.
  • Every feature gets a say, including useless ones. k-NN cannot learn that a column is irrelevant. A noise feature adds a random amount to every distance and reshuffles the neighbours. Dropping weak features helps k-NN more than it helps most models.

Choosing k

  • k=1k = 1k=1 copies the single nearest example. Training accuracy is 100 %, because each training point is its own nearest neighbour, and one mislabelled example creates a pocket of wrong predictions around it. This is the high-variance end.
  • Larger kkk averages over more examples. The scikit-learn guide summarises the trade: a larger kkk suppresses the effects of noise but makes the classification boundaries less distinct.
  • k=nk = nk=n asks every stored point, so every query gets the majority class. This is the high-bias end.

The best value depends on the data, so treat kkk as a hyperparameter: try a range with cross-validation and keep the test set out of the search, a rule the CS231n notes (opens in a new tab) state flatly. With two classes, odd values avoid tied votes. The same search can cover the weighting and the metric:

python
from sklearn.model_selection import GridSearchCV

from sklearn.pipeline import make_pipeline
from sklearn.preprocessing import StandardScaler

# X_train and y_train are your own training features and labels
pipe = make_pipeline(StandardScaler(), KNeighborsClassifier())
search = GridSearchCV(
    pipe,
    {
        "kneighborsclassifier__n_neighbors": [1, 3, 5, 7, 9, 15, 21],

    },
    cv=5,
)
search.fit(X_train, y_train)  # the scaler is refitted inside every fold
print(search.best_params_, round(search.best_score_, 3))

The curse of dimensionality

k-NN assumes that nearby points have similar labels, which only helps if the neighbours really are nearby. The Cornell CS4780 notes (opens in a new tab) make the problem concrete. Scatter nnn points uniformly in a unit cube with DDD dimensions. The smallest cube that contains the kkk nearest neighbours of a point has edge length

ℓ≈(kn)1/D\ell \approx \left( \frac{k}{n} \right)^{1/D}ℓ≈(nk​)1/D

With n=1000n = 1000n=1000 and k=10k = 10k=10, ℓ\ellℓ is 0.1 in two dimensions, 0.63 in ten and 0.955 in a hundred. In a hundred dimensions the "neighbourhood" spans almost the full range of every feature. Keeping ℓ=0.1\ell = 0.1ℓ=0.1 would take n=k⋅10Dn = k \cdot 10^{D}n=k⋅10D points.

A second symptom is that distances bunch together. Beyer and colleagues (opens in a new tab) showed that, under broad conditions, the distance to the nearest point approaches the distance to the farthest as dimensionality grows. Their experiments on synthetic data suggest that the effect can appear with as few as 10 to 20 dimensions.

This is the behaviour of data with no structure. Real data often lie close to a surface with far fewer dimensions than the raw feature count, and the same paper names two workloads where high-dimensional neighbour queries stay meaningful: data whose underlying dimension is much lower than its raw feature count, and clustered data when the query falls inside one cluster (there the sensible answer is the nearby cluster as a whole, not one single nearest point). The remedies all reduce the effective dimension: remove irrelevant features, project with PCA, or measure distance between learned embeddings, in which similar items have been trained to sit close together.

Exact and approximate neighbour search

Brute force compares the query with all NNN stored points, so one query costs on the order of N×DN \times DN×D operations. It is exact and, as the scikit-learn guide notes, competitive on small datasets.

Tree indexes (KD trees and ball trees) are also exact. They split the data into nested regions and skip regions that cannot contain a closer point, which brings a query down to roughly Dlog⁡ND \log NDlogN operations in low dimensions. The guide warns that a KD tree is very fast below about 20 dimensions and degrades toward brute force above that. With algorithm="auto", scikit-learn 1.9 picks brute force when there are more than 15 features.

Approximate nearest neighbour (ANN) indexes give up the guarantee of returning the true neighbours and in return examine only a small part of the data. An inverted-file (IVF) index clusters the vectors into lists and searches only the lists closest to the query. An HNSW (opens in a new tab) index links each vector to nearby vectors in a layered graph and walks the graph toward the query. Quality is measured as recall, the share of the true kkk nearest neighbours that the index returned; the Faiss announcement (opens in a new tab) weighs it against speed and memory. The pgvector documentation (opens in a new tab) states the trade plainly: a query without an index is an exact search with perfect recall, and adding an index trades some recall for speed. Faiss's index guidelines (opens in a new tab) say that only its flat, brute-force index guarantees exact results and that it is the baseline for the others.

Start with exact search. Move to an approximate index when latency or memory forces the change, and measure its recall against brute force on a sample of real queries before trusting it.

Step 4: choose k with leave-one-out cross-validation

Hold out each song in turn, refit the scaler on the other 13, predict the held-out song and count the hits. This script uses only the Python standard library and reproduces steps 1 to 4.

python
from collections import Counter
from math import dist, sqrt

songs = [  # (tempo in BPM, energy from 0 to 1, playlist)
    (72, 0.30, "calm"), (84, 0.22, "calm"), (95, 0.41, "calm"), (107, 0.33, "calm"),
    (115, 0.46, "calm"), (120, 0.28, "calm"), (124, 0.82, "calm"),
    (90, 0.36, "workout"), (101, 0.78, "workout"), (110, 0.74, "workout"), (128, 0.92, "workout"),
    (134, 0.74, "workout"), (142, 0.86, "workout"), (150, 0.95, "workout"),
]
query = (119, 0.86)
points = [(tempo, energy) for tempo, energy, _ in songs]
labels = [label for _, _, label in songs]

def fit_scaler(rows):
    """Mean and population standard deviation of each feature."""
    stats = []
    for column in zip(*rows):
        mean = sum(column) / len(column)
        stats.append((mean, sqrt(sum((v - mean) ** 2 for v in column) / len(column))))
    return stats

def scale(row, stats):
    return [(v - mean) / std for v, (mean, std) in zip(row, stats)]

def predict(train_x, train_y, q, k):
    """Majority label among the k stored points nearest to q."""
    nearest = sorted((dist(x, q), y) for x, y in zip(train_x, train_y))[:k]
    return Counter(y for _, y in nearest).most_common(1)[0][0]

print("raw units, k=3:", predict(points, labels, query, 3))
stats = fit_scaler(points)
scaled = [scale(p, stats) for p in points]
for k in (1, 3, 5):
    print(f"scaled, k={k}:", predict(scaled, labels, scale(query, stats), k))

for k in (1, 3, 5, 7, 9, 13):                      # leave-one-out
    correct = 0
    for i in range(len(points)):
        rest_x, rest_y = points[:i] + points[i + 1:], labels[:i] + labels[i + 1:]
        s = fit_scaler(rest_x)                     # the held-out song takes no part in scaling
        fold = [scale(p, s) for p in rest_x]
        correct += predict(fold, rest_y, scale(points[i], s), k) == labels[i]
    print(f"leave-one-out, k={k}: {correct} of 14 correct")

Edge cases and limitations

Tied votes and tied distances
With an even k and two classes the vote can split evenly, and two candidates for the last neighbour slot can sit at exactly the same distance. Libraries break both ties by an arbitrary rule. scikit-learn's documentation warns that when neighbours k and k+1 have identical distances but different labels, the result depends on the ordering of the training data. Use an odd k for two classes, and expect tied distances whenever features are integers or categories. Distance weighting makes exact vote ties rare.
A rare class cannot win a large vote
In a two-class problem, a class with only 4 training examples can never win an unweighted vote among k = 9 neighbours, because it needs 5 votes, wherever the query lies. Overall accuracy still looks healthy because the common class dominates the test set as well. Check recall for each class, keep k below twice the size of the smallest class, and consider distance weighting so that a few very close rare examples can outweigh many distant common ones.
k-NN regression cannot extrapolate
A regression prediction is an average of stored targets, so it can never exceed the largest target in the training set or fall below the smallest. Beyond the edge of the data every query gets the same outermost neighbours and the prediction goes flat. If rents rise with floor area, a flat larger than any in the training data is given roughly the rent of the largest flats seen. Flag queries whose nearest-neighbour distance is unusually large, and use a model with a trend, such as linear regression, when you must predict outside the observed range.
Categorical and mixed features have no natural distance
Euclidean distance on a category coded 1, 2, 3 pretends that category 3 is twice as far from 1 as category 2 is. One-hot encoding removes the false ordering but adds a dimension per category, and every mismatch then contributes a fixed amount that may dwarf, or be dwarfed by, the scaled numeric features. Decide deliberately how much a category mismatch should count against one standard deviation of a numeric feature, or use a model that handles categories natively, such as a tree ensemble.
The model file contains the training data
A fitted k-NN model is the stored rows plus an index. Its size and its prediction time grow with every example, and anyone who receives the model receives the data, which matters for personal or licensed records. The same property is useful in the other direction: adding or deleting one example changes predictions immediately with no retraining, although an approximate index may have to be rebuilt before the change is visible.
Cosine and Euclidean neighbours differ on unnormalised vectors
On vectors of length 1, cosine distance and Euclidean distance return the same neighbours in the same order. On raw vectors they do not: a long vector that points the same way as the query is close by cosine distance and far by Euclidean distance. Use the metric the embedding model was trained with, and make sure the index was built for the same metric that the queries use.

When to use it, and when something simpler is enough

Use it when

  • You have a small or medium dataset with a handful of meaningful numeric features, and you want a working baseline within minutes.
  • The pattern is local and irregular, so that similar cases behave alike but no simple formula describes the boundary, and every region of the feature space has enough examples.
  • New labelled examples or whole new classes arrive continuously and must take effect immediately, without a retraining job.
  • You need case-based explanations, where each prediction can be justified by showing the stored examples it came from.
  • You are searching embeddings for similar items, where the nearest-neighbour lookup is the product feature and the embedding model has already made distance meaningful.

Think twice when

  • There are many features and most are irrelevant, or the inputs are raw high-dimensional data such as pixels with no good embedding to measure distance in.
  • Prediction latency or memory is tight, the training set is large, and neither sampling nor approximate search is acceptable.
  • You must predict beyond the range of the training data, or you need a compact model whose behaviour can be summarised in a few coefficients or rules.
  • The features are mostly categorical, or mixed in a way that gives no defensible definition of distance.

A simpler alternative. A nearest-centroid classifier: represent each class by the mean of its training points and assign a query to the class with the closest mean. It has nothing to tune, stores one vector per class and predicts instantly, and scikit-learn's guide recommends it as a baseline. It stops being enough when a class is not one compact blob, for example when it forms several separate groups or wraps around another class, because a single mean cannot describe that shape.

Key takeaways

  • k-NN predicts by finding the k stored examples closest to the query and taking a majority vote for a class or the mean for a number, and fitting the model only stores the data.
  • The distance is the model, so scale the features, drop irrelevant ones and choose a metric that suits the data, such as cosine distance for embeddings.
  • A small k follows noise and a large k drifts toward the majority class, so choose k by cross-validation and never by the test score.
  • With many unstructured dimensions all points become almost equally far apart, and k-NN works again only after the effective dimension is reduced by feature selection, PCA or learned embeddings.
  • Brute force and tree indexes return the true neighbours, while approximate indexes such as IVF and HNSW trade a measurable loss of recall for far less work per query.
  • Because the model is the data, memory and prediction time grow with every stored row, and that cost is often what rules k-NN out before accuracy does.

The problem

An app wants to recognise quick sketches that each user invents, for example a doodle that stands for a particular emoji sticker, and turn each one into its label. The classes do not exist when the app ships. Every user supplies only a handful of examples (Apple's sample asks for three drawings per new sticker), the update has to finish on a phone or tablet while the user waits, and the drawings should stay on the device.

Where this topic fits

The model is a two-stage pipeline. A pretrained neural network converts a 28 × 28 grayscale sketch into a vector of 128 numbers, an embedding. A k-NN classifier then stores embeddings with their labels and classifies a new sketch from its nearest stored embeddings. Personalisation touches only the second stage: an update adds labelled vectors to the k-NN classifier, and the network stays as shipped.

How it is applied, step by step

  1. The app ships with the embedding network and an empty k-NN classifier. With nothing stored, the pipeline returns its default label for every input, which is "unknown" in the Core ML Tools guide.
  2. When the user creates a new sticker, the app collects a few drawings of it (three in Apple's sample) and pairs each drawing with the sticker's label.
  3. The app starts an update task on the device with those labelled drawings. Each drawing passes through the embedding network, and the resulting vector is stored in the k-NN classifier together with its label.
  4. To recognise a later sketch, the pipeline embeds it, finds the nearest stored vectors (three neighbours in the guide's configuration) and combines their labels using inverse-distance weights.
  5. The app writes the updated model to disk and loads it for later predictions. Adding another sticker repeats the same steps, with no retraining of the network.

Why this approach fits

Fitting k-NN means storing examples, so a new class exists as soon as its first examples are saved. There are no gradients to compute on a battery-powered device, and adding one sticker cannot disturb the classes already stored. Three examples per class would be hopeless on raw pixels. They are enough here because distance is measured between embeddings from a pretrained network, in which drawings of the same thing already sit close together. With 128 dimensions and a few dozen stored vectors an exact linear scan is fast, so no approximate index is needed.

Limitation or tradeoff

Accuracy is capped by the fixed embedding. If the pretrained network maps two different symbols to nearby vectors, more examples will not separate them, because an update changes nothing in the network. With three examples per class and k=3k = 3k=3, one careless drawing is a third of that class's evidence. Storage and the linear scan both grow with every stored example, which is fine for a personal sticker set and would not be for millions of vectors.

KNNimpute and scikit-learn's KNNImputer: filling missing values from the most similar rows

scikit-learnDocumented in a paper

Troyanskaya and colleagues (Bioinformatics, 2001) compared ways of estimating missing values in gene-expression microarray data, including a weighted k-nearest-neighbour method they call KNNimpute. scikit-learn's KNNImputer cites that paper, and its user guide and API reference document how the library applies the idea to any table. [18][4][5][6]

The problem

Microarray experiments produce data matrices with missing entries. The paper's abstract points out that many analysis methods, hierarchical clustering and K-means among them, need a complete matrix and can lose effectiveness with even a few gaps. Discarding incomplete rows throws data away, and filling a gap with a row average or a zero ignores everything else that is known about the row.

Where this topic fits

Imputation is a preprocessing step that runs before clustering or a predictive model. It is k-NN regression turned inwards: for each missing cell, the column with the gap is the target, the other columns are the features and the neighbours are other rows of the same table. Because the rows being compared have gaps of their own, the distance has to cope with missing coordinates.

How it is applied, step by step

  1. For a row with a missing value in one column, compute its distance to every other row using only the coordinates present in both rows, then scale the result up to compensate for the coordinates that were skipped. scikit-learn calls this the nan_euclidean distance.
  2. Among the rows that have a value in the missing column, keep the n_neighbors nearest (five by default in scikit-learn).
  3. Replace the missing entry with the mean of those neighbours' values, either unweighted or weighted by the inverse of each neighbour's distance.
  4. If a row has gaps in several columns, repeat the search for each column, because the rows that can serve as neighbours may differ from one column to the next.
  5. Fit the imputer on the training rows and apply it unchanged to validation and test rows, so that held-out rows are filled in from training neighbours only.

Why this approach fits

A row that resembles another on the features both have observed is a good guess for the feature one of them lacks, and that holds without assuming any formula that relates the columns. One imputer handles every column, and each filled-in value can be traced to the specific rows it came from. In the paper's comparison the k-NN method was more robust than the SVD-based method, and both beat the row average.

Limitation or tradeoff

Every weakness of k-NN carries over. Features on different scales distort the distances, so scale them first. When rows share few observed columns, or the table has many columns, the distances become unreliable. Searching all training rows for every incomplete row is slow on large tables. An imputed value is an average, so the filled column has less spread than the truth and a downstream model sees more certainty than exists. Nearest rows are also a poor guide when a value is missing for a reason related to the value itself.

  • The authors implemented and evaluated an SVD-based method (SVDimpute), weighted K-nearest neighbors (KNNimpute) and row average over the range of 1 to 20 % missing values. LEMMA Gradient Nearest Neighbor maps: assigning forest inventory plots to 30-metre pixels

LEMMA research groupDocumented in a case study

LEMMA is a forest-mapping research group whose site is hosted at Oregon State University. Its methods page describes the Gradient Nearest Neighbor (GNN) technique, its data page describes the published regional maps, and the technique was introduced by Ohmann and Gregory in the Canadian Journal of Forest Research in 2002. [19][20][21]

The problem

Forest policy analysis and ecological research need detailed vegetation information, such as which species are present and how large the trees are, for every location across whole regions. Field crews measure those attributes on inventory plots, but plots sample only a tiny share of the land. Satellite imagery and mapped environmental data cover everything and record none of those attributes directly. The task is to carry the detail of the plots across to every map pixel.

Where this topic fits

This is nearest-neighbour prediction with k=1k = 1k=1 and a distance that was fitted to the data. Each map pixel is a query. Its features are spectral and environmental variables, and the stored examples are inventory plots described by the same variables. A statistical ordination step, run beforehand, decides which combinations of variables matter for vegetation, and distance is measured in that reduced space. The prediction for a pixel is the full set of ground measurements from its single nearest plot.

How it is applied, step by step

  1. Assemble a regional database of inventory plots and a set of mapped explanatory variables, spectral and environmental, that are available for every pixel and for every plot location.
  2. Run a stepwise canonical correspondence analysis that relates the plots' ground measurements to the explanatory variables. It produces axes, each a weighted combination of the variables, ordered by how much of the variation in vegetation they account for.
  3. For every pixel, compute its scores on the first eight axes from its explanatory variables. The pixel is now a point in an eight-dimensional gradient space, and so is every plot.
  4. Find the single plot nearest to the pixel, using Euclidean distance with the axis scores weighted by their eigenvalues, so that axes that explain more count for more.
  5. Copy that plot's ground attributes to the pixel. The published grids store the plot's number in each pixel, which links to the plot database.
  6. Mask out non-forest areas using separate land-cover data, because the plot sample covers forest land only.

Why this approach fits

With k=1k = 1k=1 a pixel receives one real plot's complete record, so the species mix and stand structure assigned to a pixel form a combination that was observed together in the field. Averaging several plots, or fitting a separate regression for each attribute, could produce mixtures that exist nowhere; the paper reports that mapped predictions maintained the covariance structure among the response variables. The ordination step deals with k-NN's blindness to feature relevance: instead of treating many raw variables equally, distance is measured along eight derived axes, weighted by how much each one explains.

Limitation or tradeoff

A single neighbour is the high-variance end of k-NN, and the authors are direct about the consequence: the maps suit regional planning, policy analysis and research, and are not meant to guide local management decisions. A pixel can only receive a plot that exists, so conditions absent from the plot sample cannot be predicted and nothing is interpolated between plots. The published models apply to forest land only, because no consistent regional plot sample of non-forest areas is available.

Spotify: approximate nearest-neighbour search over track vectors, from Annoy to Voyager

SpotifyDocumented in an engineering article

Spotify's engineering blog post introducing its Voyager library (October 2023) describes a decade of using nearest-neighbour search for recommendations. The README of Annoy, the library Spotify open-sourced earlier, explains how that search was built and tuned. [22][23]

The problem

Spotify wants to recommend similar tracks, artists or albums without running slow and expensive machine-learning models at request time. Its models represent every user and item as a vector, and the Annoy README describes many millions of tracks in a high-dimensional space, with memory usage a prime concern. Comparing a query vector with every track on every request is too slow at that size, and an index copied into each serving process would multiply the memory bill.

Where this topic fits

Neighbour search is the retrieval step between model training and the product. Offline, models produce the vectors and an index is built over them. Online, a feature takes a query vector, asks the index for its nearest neighbours and passes those candidates on. The search is deliberately approximate: the index examines a fraction of the vectors and is tuned to the recall the product needs.

How it is applied, step by step

  1. Models such as matrix factorisation run offline and produce a vector for every user and item, so that similar items end up close together.
  2. An index is built over the item vectors. Annoy builds a forest of trees, each made by repeatedly splitting the space with a random hyperplane. Voyager builds an HNSW graph instead.
  3. The Annoy index is written to a file and memory-mapped, so many serving processes share one copy of the data instead of each loading its own.
  4. At request time a service passes a query vector to the index, which returns approximate nearest items by descending the trees (Annoy) or walking the graph (Voyager) and ranking only the candidates it reaches.
  5. Accuracy is tuned against cost. In Annoy, more trees at build time and more nodes inspected at query time both give more accurate results, at the price of a larger index or a slower query.
  6. Spotify later built Voyager, an HNSW-based library that its engineering post says is intended to succeed Annoy for production use, and reports more speed at the same recall and lower memory use.

Why this approach fits

A recommendation does not need the mathematically nearest thousand tracks. It needs a good set of similar ones, quickly, and that tolerance is what approximate search exploits. The vectors come from models trained so that distance reflects similarity in listening behaviour, which eases the curse-of-dimensionality trouble that raw features would bring, although the README still advises keeping dimensions moderate. Separating the offline build from the online lookup lets an expensive index be built once and then served cheaply by many processes.

Limitation or tradeoff

The search can miss true neighbours and nothing in the result says so, so recall has to be measured against exact search on sample queries. An Annoy index is static: no items can be added after it is built, so new tracks appear only after a rebuild. The README says Annoy works better with fewer than about 100 dimensions, although it also reports good results up to 1,000. By Spotify's own account the field has moved on: Annoy now ranks only mid-field, and the company built the HNSW-based Voyager to succeed it. Above all, neighbours are only as meaningful as the vectors: a weak embedding produces fast, confident and wrong recommendations.

Amazon SageMaker k-NN: sampling, dimension reduction and a Faiss index for large training sets

Amazon SageMaker AI includes a built-in k-NN algorithm for classification and regression. The AWS developer guide documents how it trains (sampling, optional dimension reduction and index building), its hyperparameters and its inference formats. [24][25][26]

The problem

A plain k-NN model keeps every training row in memory and compares each query with all of them. On a large, high-dimensional training set that means a model too big for the serving instance, slow predictions and the sparsity problems of the curse of dimensionality. A managed service has to bound memory and latency while still returning a k-NN prediction.

Where this topic fits

Everything the algorithm calls training is preparation for neighbour search. Three stages shrink and organise the data: sample the rows, optionally project them to fewer dimensions, and build an index. At inference the endpoint queries the index for the kkk nearest sampled points and applies the usual rule, the most frequent label for a classifier or the average for a regressor.

How it is applied, step by step

  1. Choose predictor_type (classifier or regressor), k, and sample_size, the number of training points to keep. Sampling exists so that the retained data fits in memory.
  2. Optionally set dimension_reduction_type to sign (a projection with a matrix of random signs) or fjlt (a fast Johnson-Lindenstrauss transform), with a target dimension smaller than the number of features.
  3. Choose index_type. In Faiss a flat index is an exhaustive, exact search, and faiss.Flat is the default here. faiss.IVFFlat and faiss.IVFPQ are inverted-file indexes, and the second adds product quantization, which stores a compressed form of each vector.
  4. Training writes three files: the serialized index, the labels, and a JSON metadata file that records k, the predictor type and the dimension-reduction settings.
  5. At inference the endpoint looks up the k nearest indexed points for each request and returns the most frequent label or the mean of the neighbours' labels. The recorded reduction settings allow a query to be projected in the same way as the training data.
  6. In verbose output mode the response also carries the neighbours' distances and labels, which makes an individual prediction inspectable.

Why this approach fits

Each stage answers one cost of k-NN. Sampling caps the number of stored rows, and therefore memory, at a figure chosen in advance. Random projection shrinks every stored vector and every distance computation while roughly preserving distances, and AWS presents it as a way to avoid the curse of dimensionality on data with more than a thousand features. The index type lets a team start with exact search and switch to an approximate index only if latency demands it. Because prediction is still "look up neighbours and vote", kkk and even the predictor type can be changed in the metadata file without retraining.

Limitation or tradeoff

Every shortcut costs accuracy. Rows that were not sampled cannot be neighbours, which hurts rare classes most. The AWS documentation says that dimension reduction introduces noise that can reduce prediction accuracy. The inverted-file indexes are approximate, and the IVFPQ index does not support the inner-product or cosine metrics. Feature scaling and the choice of kkk still have to be handled and validated by the user.

4Common mistakes

  1. Feeding unscaled features to k-NN, or fitting the scaler on all the data before splitting.

    Why it causes problems
    Without scaling, the feature with the largest numbers picks the neighbours and the others are ignored, as when tempo in BPM drowned out energy in the worked example. Scaling before the split is a quieter error: the held-out rows influenced the mean and standard deviation, so the validation score is slightly optimistic.
    How to recognise it
    Multiply one feature by 1,000 and run again. If the predictions change, the model depends on units. In code, look for a scaler's fit or fit_transform called on the full dataset above the train/test split.
    How to fix it
    Put the scaler and the k-NN model in one pipeline and pass the pipeline to cross-validation, so that the scaler is refitted on each training fold. Then compare the cross-validated score with and without each feature to see which ones help.

  2. Choosing k, the weighting or the metric by the score on the test set.

    Why it causes problems
    With several candidates, the best test score is partly luck, and reporting it overstates how the model will do on new data. k-NN makes this tempting because trying another k costs nothing.
    How to recognise it
    The reported test accuracy is the maximum over a list of k values, or the test set appears inside the tuning loop. A clear drop on fresh data is the late symptom.
    How to fix it
    Tune with cross-validation on the training data only, fix k, the weights and the metric, and score the test set once at the end.

  3. Judging the model by its training accuracy, especially at k = 1.

    Why it causes problems
    Each training point is its own nearest neighbour, so 1-NN scores 100 % on the data it stored whatever the labels are, unless two identical rows carry different labels. That number says nothing about new data. In the simulated example in this lesson the same model scored 73.7 % under cross-validation.
    How to recognise it
    Training accuracy is at or near 100 % while the cross-validated score is clearly lower, and the gap narrows as k increases.
    How to fix it
    Report cross-validated or held-out scores only. For a quick check on the stored data, use leave-one-out, so that a point never votes for itself.

  4. Adding every available column, including identifiers, one-hot categories with many levels and near-constant features.

    Why it causes problems
    Each extra dimension adds noise to every distance and pushes the data toward the regime in which all points are almost equally far apart. Accuracy degrades gradually and no error is raised.
    How to recognise it
    Cross-validated accuracy falls when columns are added. For a sample of queries, the distance to the nearest neighbour is close to the distance to a randomly chosen point.
    How to fix it
    Select features by cross-validated score, merge or drop sparse one-hot columns, or reduce the dimension with PCA or a learned embedding before measuring distance.

  5. Switching to an approximate index without measuring its recall.

    Why it causes problems
    An approximate search returns plausible-looking neighbours even when it misses the true ones, so a badly tuned index lowers quality without failing. pgvector's documentation notes that queries return different results after an approximate index is added.
    How to recognise it
    No recall figure exists anywhere in the project, or predictions changed after an index was added or re-tuned and nobody can say by how much.
    How to fix it
    Keep a brute-force search as the reference. On a sample of real queries, compute the fraction of true top-k neighbours the index returns, then raise the search effort (lists probed, search width, trees) until recall meets the target at an acceptable latency.

# name: (area in square metres, distance to the centre in km, monthly rent in euros)
flats = {
    "A": (35, 1.0, 900), "B": (42, 6.5, 540), "C": (48, 3.0, 1020), "D": (50, 2.0, 980),
    "E": (58, 8.0, 770), "F": (64, 3.5, 1070), "G": (70, 0.8, 1180), "H": (72, 6.0, 920),
    "I": (78, 5.0, 1140), "J": (90, 7.5, 1060),
}
query = (60, 2.5)

def fit_scaler(points):
    """Mean and population standard deviation of each of the two features."""
    stats = []
    for j in range(2):
        column = [p[j] for p in points]
        mean = sum(column) / len(column)
        std = sqrt(sum((v - mean) ** 2 for v in column) / len(column))
        stats.append((mean, std))
    return stats

def scale(point, stats):
    return tuple((point[j] - stats[j][0]) / stats[j][1] for j in range(2))

def distance(a, b):
    return sqrt(sum((x - y) ** 2 for x, y in zip(a, b)))

def neighbours(train, q, k):
    """train holds (name, point, rent); returns the k nearest as (distance, name, rent)."""
    return sorted((distance(p, q), name, rent) for name, p, rent in train)[:k]

def predict(train, q, k, weighted=False):
    near = neighbours(train, q, k)
    if not weighted:
        return sum(rent for _, _, rent in near) / k
    weights = [1 / d for d, _, _ in near]
    return sum(w * rent for w, (_, _, rent) in zip(weights, near)) / sum(weights)

raw = [(name, (area, km), rent) for name, (area, km, rent) in flats.items()]
print("raw, k=3:", [(n, round(d, 2)) for d, n, _ in neighbours(raw, query, 3)],

python
import random
from math import dist          # Euclidean distance, Python 3.8+

DIM, N, N_QUERIES, CELLS, K = 16, 2000, 100, 20, 10

def make_points(rng, n, clustered):
    if not clustered:
        return [[rng.random() for _ in range(DIM)] for _ in range(n)]
    centres = [[rng.random() for _ in range(DIM)] for _ in range(CELLS)]
    points = []
    for _ in range(n):
        centre = centres[rng.randrange(CELLS)]
        points.append([c + rng.gauss(0, 0.12) for c in centre])
    return points

def exact_search(data, q, k):
    """Brute force: one distance per stored point, then keep the k smallest."""
    return sorted(range(len(data)), key=lambda i: dist(data[i], q))[:k]

def build_ivf(data, cells, rounds=5):
    """A tiny inverted-file index: k-means centroids plus the list of points owned by each one."""
    centroids = [data[i] for i in range(0, len(data), len(data) // cells)][:cells]
    for _ in range(rounds):
        lists = [[] for _ in range(cells)]
        for i, p in enumerate(data):
            lists[min(range(cells), key=lambda c: dist(centroids[c], p))].append(i)
        centroids = [
            [sum(data[i][j] for i in members) / len(members) for j in range(DIM)] if members else centroids[c]
            for c, members in enumerate(lists)
        ]
    return centroids, lists

def ivf_search(data, index, q, k, nprobe):
    centroids, lists = index
    probe = sorted(range(len(centroids)), key=lambda c: dist(centroids[c], q))[:nprobe]
    candidates = [i for c in probe for i in lists[c]]
    found = sorted(candidates, key=lambda i: dist(data[i], q))[:k]
    return found, len(centroids) + len(candidates)      # distances computed for this query

def experiment(clustered):
    rng = random.Random(42)
    points = make_points(rng, N + N_QUERIES, clustered)
    data, queries = points[:N], points[N:]
    index = build_ivf(data, CELLS)
    truth = [set(exact_search(data, q, K)) for q in queries]
    print("clustered data" if clustered else "uniform data")
    print(f"  exact scan: recall 1.000, {N} distances per query")
    for nprobe in (1, 2, 3, 5, 10, 20):
        hits = work = 0
        for q, true_ids in zip(queries, truth):
            found, computed = ivf_search(data, index, q, K, nprobe)
            hits += len(true_ids & set(found))
            work += computed
        print(f"  nprobe={nprobe:2d}: recall@10 {hits / (K * N_QUERIES):.3f}, "
              f"{work / N_QUERIES:6.0f} distances per query")

experiment(clustered=True)

Clustered data. Probing a single list returns 94 % of the true neighbours for about 7 % of the work, because a query's neighbours nearly always live in the query's own cluster. Two lists reach a recall of 0.985 with 250 distances, an eighth of a brute-force scan, so nprobe = 2 is the smallest setting that meets a 0.98 target.

Uniform data. With no cluster structure, the cells are arbitrary slices of a featureless cloud, and a query's true neighbours are spread over many of them. One list finds a third of the neighbours, and it takes ten lists, half the data, to reach 0.95. An index can only exploit structure that exists. Unstructured high-dimensional data, the setting of the curse of dimensionality, push approximate search back toward a full scan.

At nprobe = 20 every list is searched, so recall is exactly 1 and the work is 2,020 distances, slightly more than brute force, because the 20 centroid comparisons are pure overhead. An approximate index run at full effort is an exact search that costs extra, which is why you tune the effort to a recall target instead of turning it all the way up.
