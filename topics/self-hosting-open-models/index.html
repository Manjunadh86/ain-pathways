Running Open-Weight Models (Ollama, vLLM, Hugging Face)

Self-hosting an open-weight model means downloading its trained weights from a model hub and running them on hardware you control, with a local runtime such as Ollama or LM Studio or a server such as vLLM, usually behind an OpenAI-compatible HTTP endpoint that existing client code can call.

1Overview

Why it matters

A hosted API charges per token, runs on the provider's hardware and changes on the provider's schedule. Running an open-weight model yourself changes all three. Teams do it when prompts and documents must stay inside their own network, when they need a model version that never changes underneath them, when they want to work offline, or when their volume is high enough that owned GPUs might undercut per-token pricing. The last reason has to be measured rather than assumed, because a GPU server also costs engineering and operations time.

The decision is mostly arithmetic. A model whose weights do not fit in GPU memory will not start. One that fits but leaves no room for its attention cache can serve only a short conversation at a time. A tool built for a laptop handles one request per model at a time by default, so fifty users queue behind one another, and a data-centre inference server is wasted on one developer. Anyone who picks a model for a product, sizes a deployment for a customer or reviews an infrastructure bill needs to estimate memory, understand quantization and know which kind of tool fits the workload.

Key terms

Open-weight model
A model whose trained weights can be downloaded and run by anyone who accepts its licence. The training data and code may or may not be published, and the licence may restrict use.
Model hub
A website that hosts model files as versioned repositories with licences and download tools. The Hugging Face Hub is the most widely used one.
Local runtime
A program such as Ollama or LM Studio that downloads a model and runs it on one machine with little setup, aimed at one user or a small team.
Inference server
A program such as vLLM that serves a model over HTTP to many users at once, using GPU memory and request scheduling techniques designed for throughput.
Quantization
Storing a model's weights with fewer bits each, together with a scale that maps the small integers back to real values, so that the model needs less memory at some cost in accuracy.
GGUF
A single-file model format used by llama.cpp, Ollama and LM Studio that stores the weights together with standardised metadata such as the tokenizer and chat template.
KV cache
The keys and values the model has already computed for every earlier token in a conversation, kept in GPU memory so that each new token does not recompute them. It grows with context length and with the number of concurrent conversations.
Continuous batching
Letting new requests join the batch the GPU is already processing at every generation step, instead of waiting for the whole batch to finish.
OpenAI-compatible endpoint
An HTTP API that accepts the same paths and JSON as the OpenAI API, such as /v1/chat/completions, so that OpenAI client libraries work against it after a change of base URL.
Tensor parallelism
Splitting each layer's weights across several GPUs so that a model too big for one GPU can be served, at the price of communication between the GPUs.

2Explanation

Introduction

In Choosing a Model and Provider you compared hosted models by quality, price and limits, and in LLM APIs and Streaming you called one over HTTP. In both cases the model ran on someone else's machines. This lesson covers the alternative: taking the weights, the learned numbers that define a model, and running them yourself.

The difference is like taking a taxi versus owning a car. The taxi (a hosted API) needs no garage, no fuel and no servicing, and you pay for every ride. The car (a self-hosted model) is yours to drive at any hour, and it also needs a garage big enough to hold it, regular maintenance and someone who understands the warning lights. In this lesson the garage is GPU memory, and the first skill is checking that the car fits in it.

A self-hosted setup has four moving parts, and the diagram stacks them with your application on top and the hardware at the bottom:

  • A model hub such as the Hugging Face Hub stores the weights as versioned files.
  • A runtime or inference server loads those files into memory and generates tokens. Local runtimes (Ollama, LM Studio) suit one person on one machine. Inference servers (vLLM, Text Generation Inference) suit many simultaneous users on GPUs.
  • Quantization stores the weights with fewer bits so that they take less memory.
  • An OpenAI-compatible endpoint exposes the model over HTTP with the same paths and JSON as the hosted API, so existing code and tools work after a change of URL.

The lesson follows that order and then works one sizing example in full, with a real model configuration and a 24 GiB GPU, because memory arithmetic is where self-hosting plans most often go wrong. It builds on Tokens and Context Windows and on How Large Language Models Work.

How it works

What you download

An open-weight model is a folder of files: the weights, a configuration file describing the architecture, and tokenizer files. Open-weight means the weights can be downloaded; the licence still decides how you may use them. Some repositories are gated: you agree to share your username and email with the authors, who can approve requests automatically or by hand and can withdraw access at any time (Hub documentation on gated models (opens in a new tab)). Qwen3-8B, the model used in this lesson's worked example, lists the apache-2.0 licence on its model card (opens in a new tab).

Pin the version you download, because the default is whatever is on the main branch today:

python
from huggingface_hub import snapshot_download

snapshot_download(
    repo_id="Qwen/Qwen3-8B",
    revision="<full 40-character commit hash>",   # a branch, tag or pull request also works
    allow_patterns=["*.json", "*.txt", "*.safetensors"],   # skip file formats you will not use
)

The revision parameter takes a branch, tag, pull request or commit hash, and a hash must be the full-length one (download guide (opens in a new tab)). Prefer safetensors files. Pickle-based weights, the default PyTorch format, can run arbitrary code when loaded, which is why the Hub's pickle documentation (opens in a new tab) advises loading them only from publishers you trust.

Local runtimes and inference servers

Both kinds of tool load weights and generate tokens. They differ in who they are built for.

  • Local runtimes put one model on one machine with little setup. Ollama starts a model with ollama run, and the Hub documentation describes it as an application based on llama.cpp. LM Studio is a desktop application with a local server, a command-line tool called lms and a headless daemon called llmster for servers and CI (LM Studio developer docs (opens in a new tab)). Its compatibility page (opens in a new tab) lists /v1/models, /v1/chat/completions, /v1/completions, /v1/embeddings and /v1/responses. The Hub lists both as tools for GGUF files (GGUF documentation (opens in a new tab)).
  • Inference servers serve many users at once on GPUs. vLLM combines continuous batching with a paged KV cache. Its quickstart lists Linux as the operating system and mentions macOS only through a separate vLLM-Metal backend. Text Generation Inference (TGI) shares those ideas, but its documentation (opens in a new tab) now states that it is in maintenance mode and recommends vLLM and SGLang, plus llama.cpp or MLX for local use.

Memory budget, part one: the weights

The weights are the largest fixed cost: bytes = parameters × bits per weight ÷ 8. At 16 bits (BF16 or FP16) each parameter takes two bytes, so a model with PPP billion parameters needs about 2P2P2P GB. Hugging Face's Inference Endpoints vLLM page (opens in a new tab) uses this for Llama 3 8B (about 16 GB) and Llama 3 70B (about 140 GB). The Accelerate memory estimator (opens in a new tab) warns that its figures cover loading the model, not running it, and suggests adding up to 20% for inference, following EleutherAI. That rule does not include the cache described next, which grows with context length.

Memory budget, part two: the KV cache

While generating, the model attends to every earlier token in every layer. It stores each token's keys and values instead of recomputing them. That store is the KV cache, and its size per token is:

bytes per token=2×nlayers×nkv heads×dhead×b\text{bytes per token} = 2 \times n_{\text{layers}} \times n_{\text{kv heads}} \times d_{\text{head}} \times bbytes per token=2×nlayers​×nkv heads​×dhead​×b

The 2 counts keys and values, dheadd_{\text{head}}dhead​ is the size of one attention head and bbb is the bytes per stored number (2 for 16-bit). The Transformer Inference Arithmetic (opens in a new tab) article gives the same expression for models without grouped-query attention. Most recent models use grouped-query attention, where several query heads share fewer key and value heads (see the GQA paper (opens in a new tab)), so nkv headsn_{\text{kv heads}}nkv heads​ is smaller than the head count. Qwen3-8B has 32 query heads and 8 KV heads. The cache is per conversation: ten concurrent users need ten caches.

Servers plan around this. vLLM claims a fraction of GPU memory up front (--gpu-memory-utilization, 0.92 by default in the engine-arguments reference (opens in a new tab)), and whatever the weights leave over becomes KV cache. If the cache fills, vLLM preempts some requests and recomputes them later, which raises latency (tuning guide (opens in a new tab)). The levers are --max-model-len, --max-num-seqs, an 8-bit KV cache (--kv-cache-dtype fp8) and more GPUs through tensor parallelism.

Quantization

Quantization stores each weight in fewer bits plus a scale that maps the integers back to real values. This sketch quantizes eight weights to 4-bit integers with one scale. It is a teaching illustration, not the algorithm of any one library:

python
weights = [0.12, -0.50, 0.33, 0.91, -0.07, 0.25, -0.88, 0.04]
scale = max(abs(w) for w in weights) / 7          # signed 4-bit integers -7..7
q = [round(w / scale) for w in weights]           # what is stored
restored = [round(v * scale, 3) for v in q]
print(q)         # [1, -4, 3, 7, -1, 2, -7, 0]
print(restored)  # [0.13, -0.52, 0.39, 0.91, -0.13, 0.26, -0.91, 0.0]

The largest error is 0.06. One outlier damages its whole block: replace 0.04 with 4.0 and the scale grows from 0.13 to about 0.57, which raises the average error from 0.029 to 0.156. Real formats therefore quantize small blocks and store a scale per block. In GGUF's Q4_K, 4-bit values come with a 6-bit scale and 6-bit minimum for each 32-weight block, which the Hub documentation says averages 4.5 bits per weight. That is why a "4-bit" model costs about 4.5 to 4.9 bits per weight: the llama.cpp README lists 4.8944 for Q4_K_M and 8.5008 for Q8_0, against 16.0005 for F16. On GPUs the formats are AWQ, GPTQ, FP8 and others, and support depends on the GPU generation: vLLM's table shows FP8 W8A8 on Ada and Hopper GPUs but not on Ampere.

Smaller weights also generate faster. Producing one token reads every weight from memory once, so at small batch sizes speed is bounded by memory bandwidth rather than arithmetic, as the inference-arithmetic article (opens in a new tab) derives. The llama.cpp table shows the effect: 29.17 tokens per second for F16 and 71.93 for Q4_K_M on its unstated hardware, while prompt processing does not speed up (923 against 822 tokens per second). The cost is accuracy. The README names perplexity and KL divergence as the measures but its table reports neither, so test on your own task with the methods in Evaluating LLM Applications. The KV cache can be quantized separately: Ollama's FAQ describes q8_0 as using about half the memory of f16 with a very small loss in precision, and says the cache can be quantized when Flash Attention is enabled.

OpenAI-compatible endpoints

A server that implements the OpenAI API's HTTP paths lets you reuse existing client libraries. Three values change: the base URL, the key and the model name.

ServerBase URL in its documentationAPI key
Ollamahttp://localhost:11434/v1/Required by the client, ignored by Ollama
vLLMhttp://localhost:8000/v1Optional: --api-key or VLLM_API_KEY
LM Studiohttp://localhost:1234/v1Not covered on the page read
TGIhttp://localhost:3000/v1 in its examplesAny placeholder; the example uses -
python
from openai import OpenAI   # pip install openai

client = OpenAI(base_url="http://localhost:11434/v1", api_key="ollama")
reply = client.chat.completions.create(
    model="llama3.2",       # a model you have already pulled
    messages=[{"role": "user", "content": "Say hello in five words."}],
)
print(reply.choices[0].message.content)

Compatibility is partial. Ollama's compatibility page marks the chat-completion fields tool_choice, logit_bias, user and n as unsupported, and log probabilities as an unsupported feature. The page can lag the software: when this lesson was reviewed, an Ollama 0.34.2 server ignored n in a test request but did return log probabilities. vLLM ignores user, does not support suffix, and needs a chat template for the chat endpoint, which --chat-template can supply for a model that lacks one. Test the features you depend on, such as streaming, tool calls and JSON output, against the server you will actually run.

Running it safely

Ollama listens on 127.0.0.1 port 11434 by default, and its FAQ shows OLLAMA_HOST for exposing it to other machines. Because it ignores API keys, put anything reachable from a network behind an authenticated proxy (see Networking Essentials). The FAQ also gives a default of one parallel request per model (OLLAMA_NUM_PARALLEL), a five-minute keep-alive for loaded models and a queue of 512 requests. A runtime that serves one person well can be the wrong tool for a team, so measure concurrency before you choose.

Worked example: Fitting Qwen3-8B on a 24 GiB GPU

Question. You have one GPU with 24 GiB of memory. Can you serve Qwen3-8B on it, how much conversation can it hold at once, and what changes if you quantize?

Inputs. The model card (opens in a new tab) gives 8.2 billion parameters, 36 layers and 32 query heads with 8 KV heads. The config.json (opens in a new tab) gives a head dimension of 128. vLLM's --gpu-memory-utilization defaults to 0.92. One input is our own assumption: 1.5 GiB for the CUDA context, activations and graph capture. Real overhead varies, so treat the server's startup log as the final check.

StepCalculationResult
Usable memory24 × 0.9222.08 GiB
BF16 weights8.2e9 × 16 ÷ 8 ÷ 2^3015.27 GiB
KV budget22.08 − 15.27 − 1.55.31 GiB
KV bytes per token2 × 36 × 8 × 128 × 2147,456 bytes = 144 KiB
Tokens that fit5.31 GiB ÷ 144 KiB38,639 tokens

The BF16 model fits, but the whole GPU can hold only about 38,600 tokens of conversation: one 32,768-token conversation, or four of 8,192 tokens with a little to spare. The script below repeats the arithmetic for three weight precisions plus an 8-bit cache. It uses only the standard library, so you can run it as it stands:

python
GIB = 2**30
PARAMS, LAYERS, KV_HEADS, HEAD_DIM = 8.2e9, 36, 8, 128   # Qwen3-8B: model card and config.json
GPU_GIB, UTILIZATION, OVERHEAD_GIB = 24, 0.92, 1.5        # OVERHEAD_GIB is our assumption


def plan(label, bits_per_weight, kv_bytes=2):
    weights = PARAMS * bits_per_weight / 8 / GIB
    kv_budget = GPU_GIB * UTILIZATION - weights - OVERHEAD_GIB
    per_token = 2 * LAYERS * KV_HEADS * HEAD_DIM * kv_bytes
    tokens = int(kv_budget * GIB // per_token)
    print(f"{label:<24}{weights:6.2f} GiB{kv_budget:8.2f} GiB{per_token // 1024:5d} KiB{tokens:9,d}{tokens / 32768:6.1f}")


print(f"{'':<24}{'weights':>10}{'KV budget':>12}{'per tok':>9}{'tokens':>9}{'x 32k':>6}")
plan("BF16", 16)
plan("Q8_0", 8.5008)
plan("Q4_K_M", 4.8944)
plan("Q4_K_M + 8-bit KV cache", 4.8944, kv_bytes=1)
text

BF16                     15.27 GiB    5.31 GiB  144 KiB   38,639   1.2
Q8_0                      8.11 GiB   12.47 GiB  144 KiB   90,768   2.8
Q4_K_M                    4.67 GiB   15.91 GiB  144 KiB  115,836   3.5
Q4_K_M + 8-bit KV cache   4.67 GiB   15.91 GiB   72 KiB  231,673   7.1

Reading the result. Quantizing the weights to Q4_K_M frees more than ten GiB, which becomes KV cache: capacity triples, from 38,639 to 115,836 tokens. Storing the cache itself in 8 bits halves the bytes per token and doubles capacity again. Q4_K_M is a GGUF type used by llama.cpp, Ollama and LM Studio. A 4-bit AWQ or GPTQ checkpoint for vLLM has its own bits per weight, so substitute the real figure when you size one.

Serving it. With vLLM the matching commands are below. They show the flags discussed above; the script was run for this lesson, the server commands were not. Qwen3-8B reasons before it answers by default, and its model card describes /no_think in a prompt as a soft switch that turns that off, so the request below adds it. Without it, a short max_tokens can end inside the reasoning text and leave no visible answer.

bash
VLLM_API_KEY=change-me vllm serve Qwen/Qwen3-8B --max-model-len 32768 --gpu-memory-utilization 0.92

curl http://localhost:8000/v1/chat/completions \
  -H "Authorization: Bearer change-me" -H "Content-Type: application/json" \
  -d '{"model": "Qwen/Qwen3-8B", "messages": [{"role": "user", "content": "Say hello in five words. /no_think"}], "max_tokens": 64}'

Compare the cache size vLLM reports at startup with the 38,639 tokens estimated here. If the two differ by more than a few percent, your overhead assumption was off, and the server's number is the one to trust.

Edge cases and limitations

The default context window may be smaller than the model's limit
Ollama's context-length page says its default depends on VRAM: 4k tokens under 24 GiB, 32k from 24 to 48 GiB and 256k from 48 GiB, and that agents and coding tools should be given at least 64000. Its FAQ still describes a 4096-token default, so check the version you run. A model that advertises 128k tokens can run with a 4k window until you raise it, and raising it costs memory. Read the CONTEXT column of `ollama ps` before blaming the model for forgetting things.
The weights fit but the cache has no room
A model can load and still serve badly. In the worked example Qwen3-8B in BF16 leaves about 5 GiB of a 24 GiB card for the KV cache, enough for a single 32k-token conversation. With more users, vLLM preempts requests and recomputes them, and its tuning guide says the resulting warning suggests raising gpu_memory_utilization or tensor_parallel_size. Quantize the weights or the cache, lower max-model-len, or add GPUs.
Spilling to CPU memory is a performance cliff
Ollama uses a single GPU when the whole model fits on it and otherwise spreads the model across the available GPUs. The PROCESSOR column of `ollama ps` shows where the model ended up, including splits such as 48%/52% CPU/GPU, and the context page advises avoiding CPU offload for best performance. A larger context can push a model that fit at 4k over the edge, so recheck the column after you change the context length.
A model without a chat template cannot serve chat requests well
vLLM's chat endpoint requires a chat template, and its docs say chat requests error without one; `--chat-template` supplies one for a model that lacks it. Ollama reads the template from the GGUF file's tokenizer.chat_template metadata, and the Hub documentation says a repository that lacks one needs a `template` file written in Go template syntax, not Jinja. A base model with no template may answer chat requests badly. Choose instruction-tuned checkpoints for chat endpoints.
A quantization format your GPU does not support
vLLM's hardware table shows FP8 W8A8 for Ada, Hopper and AMD GPUs but not Ampere (a separate Marlin row lists GPTQ, AWQ, FP8 and FP4 for Ampere), and marks AWQ unsupported on Volta. Downloading a checkpoint in a format your GPU generation cannot run wastes a multi-gigabyte transfer. Check the table for your GPU first, and pick a format it lists.
The engine you chose may be in maintenance mode
TGI's documentation states that the project is in maintenance mode and recommends vLLM, SGLang, llama.cpp or MLX instead. Check a project's status before you standardise on it, and keep application code on the OpenAI-compatible API so that changing engines means changing a URL and a launch command, not your app.

When to use it, and when something simpler is enough

Use it when

  • Prompts or documents must stay inside your own network, and policy requires a private or air-gapped deployment. See [Data Privacy and Compliance](/topics/data-privacy-and-compliance/).
  • You need one model version to behave identically for months, or the system must work without an internet connection.
  • Request volume is steady enough to keep GPUs busy, and you have measured that owned or rented GPU hours cost less than per-token pricing for the same quality.
  • You want to build and test against an OpenAI-compatible API on a developer machine without spending tokens.

Think twice when

  • Traffic is small, bursty or unpredictable. A GPU costs money while idle, and a hosted API charges only for use.
  • The task needs the quality of the strongest hosted models and you have not shown, on your own evaluation set, that an open-weight model reaches it.
  • Nobody can patch, monitor and secure the server, or be on call when it fails.
  • The model you want needs more GPU memory than you can budget, as a 70-billion-parameter model does at 16 bits (about 140 GB for weights alone).

A simpler alternative. Try the same open-weight model on a managed endpoint first, such as Hugging Face Inference Endpoints (the second example), where a TGI-based endpoint can be called with OpenAI client libraries. You can then compare quality and price before buying hardware. Move to your own machines when data rules or a measured cost comparison require it. See [LLM Cost and Latency Optimization](/topics/llm-cost-and-latency-optimization/) for how to run that comparison.

Key takeaways

  • Self-hosting is a stack of weights from a hub, a runtime or inference server, optional quantization and an OpenAI-compatible endpoint, with Ollama and LM Studio built for one machine and vLLM for many users on GPUs.
  • GPU memory must hold the weights (parameters times bits per weight, divided by eight) and a KV cache that grows with context length and with the number of concurrent conversations.
  • The KV cache costs 2 times layers times KV heads times head dimension times bytes per number for every token, which is 144 KiB per token for Qwen3-8B with a 16-bit cache.
  • Quantization trades accuracy for memory and generation speed. A "4-bit" format costs about 4.5 to 4.9 bits per weight, and its quality loss has to be measured on your own task.
  • OpenAI-compatible endpoints let existing clients work after you change the base URL, key and model name, but each server supports only part of the API, so test the features you use.
  • A local runtime is built for one user: Ollama serves one request per model at a time by default and ignores API keys, so expose it only behind authentication and move to an inference server when concurrency matters.

Example 1 of 5

LMSYS moves Vicuna and Chatbot Arena from a Transformers backend to vLLM

LMSYS and UC BerkeleyDocumented in an engineering article

The vLLM launch post of 20 June 2023 says vLLM was developed at UC Berkeley and had been deployed at Chatbot Arena and the Vicuna demo for the previous two months. The PagedAttention paper, which describes vLLM's design, supplies the memory analysis behind it. [10][12]

The problem

LMSYS released the Vicuna chat models in April 2023 and served them to millions of users in Chatbot Arena. The first serving backend was based on Hugging Face Transformers, and the post describes the hardware only as a limited number of university-sponsored GPUs. The paper explains where GPU memory went: each request's KV cache is large and its final size is unknown in advance, and systems that reserve space for the longest possible output waste most of it, which caps the number of requests in a batch.

Where this topic fits

vLLM is the inference-server layer. The post describes a FastChat-vLLM integration in which vLLM replaced the Hugging Face Transformers serving backend inside FastChat, the software LMSYS used to serve the demo. That is a backend swap, so the chat interface and the models sat above the change. What changed was how the KV cache is stored and how requests are batched.

How it is applied, step by step

  1. LMSYS released Vicuna in April 2023 and served it through FastChat, first with a Hugging Face Transformers backend.
  2. As the demo became more popular, peak traffic rose several times and the Hugging Face backend became a significant bottleneck, according to the post. LMSYS and the vLLM team then built the FastChat-vLLM integration.
  3. vLLM stores each sequence's KV cache in fixed-size blocks that a block table maps to physical memory. Blocks are allocated as tokens are generated instead of reserving the maximum length up front.
  4. With far less reserved-but-unused memory, more requests fit in each batch on the same GPU, which is where the extra throughput comes from.
  5. The post reports that LMSYS could cut the number of GPUs serving this traffic by 50%, with vLLM handling an average of 30K requests a day and a peak of 60K.

Why this approach fits

Chat output lengths are unpredictable, so each request's cache grows by an unknown amount. An allocator that reserves the maximum for every request wastes memory on short replies, and memory is what limits the batch size on a GPU. Paging the cache removes that waste at its source without touching the model, and it lives entirely in the server, which is why a chat service could adopt it by swapping the backend.

Limitation or tradeoff

The numbers come from the vLLM team and LMSYS themselves, from 2023, on LLaMA-class models and A10G or A100 GPUs, with request lengths sampled from ShareGPT conversations. The post gives no GPU count for LMSYS. Its throughput gains depend on the workload: it reports up to 24x over Hugging Face Transformers but up to 3.5x over TGI, so a comparison with a better-tuned baseline on your own traffic may look very different.

What the sources document

  • The post, dated 20 June 2023, says vLLM was developed at UC Berkeley and had been deployed at Chatbot Arena and the Vicuna demo for the previous two months, and that LMSYS FastChat initially used a Hugging Face Transformers based serving backend for the chat demo. [10]
  • It states that, in an early internal micro-benchmark by LMSYS, the vLLM serving backend can achieve up to 30x higher throughput than an initial Hugging Face backend, and that with vLLM LMSYS was able to cut the number of GPUs used for serving the above traffic by 50%. [10]
  • It reports that vLLM handled an average of 30K requests a day in Chatbot Arena and a peak of 60K. [10]
  • The post says that, in its discussion of the KV cache, existing systems waste 60% to 80% of memory through fragmentation and over-reservation, and that PagedAttention confines waste to the last block of each sequence, under 4%. [10]
  • For OPT-13B the paper gives 800 KB of KV cache per token, up to 1.6 GB for one request, about 65% of an A100 40 GB for weights and close to 30% for dynamic request state, and says existing systems use only 20.4% to 38.2% of KV cache memory for actual token states. [12]

The facts above come from the cited sources. The steps and analysis in this example are our explanation of how they fit together.

Example 2 of 5

Hugging Face Inference Endpoints, choosing GPUs and parallelism for a vLLM endpoint

Hugging FaceDocumented in official docs

Hugging Face Inference Endpoints runs open models on GPU instances that you choose when you create an endpoint. Its vLLM engine page, which says TGI, vLLM and SGLang are equivalently good options for most use cases, documents how an instance's GPUs are divided between tensor and data parallelism. A separate TGI Messages API page documents calling TGI-based endpoints with OpenAI client libraries. [22][9][7][21]

The problem

A team has chosen an open-weight model and must choose an instance type and how to use its GPUs. Too few GPUs and the weights do not fit. Too many for a small model and some GPUs sit idle. The wrong split leaves too little memory for the KV cache, or too little throughput for the traffic.

Where this topic fits

This is the sizing step between choosing a model and launching a server. The inputs are the model's weight size and the instance's GPU count and memory. The outputs are two vLLM settings, tensor_parallel_size and data_parallel_size, whose product must equal the number of GPUs. After launch the endpoint is a URL you call over HTTP.

How it is applied, step by step

  1. Estimate the weight size from the parameter count and precision. The page uses about 16 GB for Llama 3 8B, about 140 GB for Llama 3 70B and about 810 GB for Llama 3.1 405B, all at FP16.
  2. Choose the smallest tensor_parallel_size whose combined GPU memory holds the weights. The page's example needs at least two 80 GB GPUs for the 70B model.
  3. Divide the instance's GPU count by that number to get data_parallel_size, the number of independent copies. For 70B on 8 x H100 the page arrives at tensor parallelism 2 and data parallelism 4.
  4. Weigh the tradeoff the page describes. More copies raise throughput. Fewer, wider copies leave more memory for the KV cache and so allow longer contexts.
  5. Optionally lower the KV cache precision, which the page lists as a configuration option with fp8 choices, to stretch the memory that remains.
  6. Call the endpoint. For TGI-based endpoints the Messages API page shows an OpenAI client pointed at the endpoint URL, ending in /v1/, with a Hugging Face API key. The vLLM page shows no client call, so check how your own endpoint is called.

Why this approach fits

The weights are a fixed cost that must fit before anything else works, so computing the minimum tensor-parallel size is a safe first step. Turning the leftover GPUs into independent copies converts spare hardware into throughput. Exposing both numbers as engine arguments lets the same container run on different instance types.

Limitation or tradeoff

The minimum is a floor, not a recommendation. In our arithmetic the two-GPU copy of the 70B model leaves only about 7 GB for the KV cache and everything else, so long contexts or many users would be starved. The page itself notes that fewer, wider copies allow longer contexts, and vLLM's tuning guide notes that tensor parallelism adds synchronisation overhead. The page's sizes are approximate and the example is a worked illustration, not a benchmark.

What the sources document

  • By default an endpoint sets tensor_parallel_size to the number of GPUs on the chosen instance and data_parallel_size to 1, which the page says prioritises fitting larger models. [22]
  • The page's sizing examples are Llama 3 8B in FP16 at about 16 GB on one GPU, Llama 3 70B at about 140 GB on two 80 GB GPUs and Llama 3.1 405B at about 810 GB on eight 80 GB GPUs. [22]
  • The page gives tensor_parallel_size times data_parallel_size equals the total GPUs, and says higher data parallelism gives more throughput with less KV cache memory per copy, while higher tensor parallelism allows longer contexts at lower throughput. [22]
  • vLLM's engine-arguments reference lists --gpu-memory-utilization with a default of 0.92 and --tensor-parallel-size with a default of 1, and its tuning guide says tensor parallelism shards the weights to free memory for the KV cache but can add synchronisation overhead. [9][7]
  • The TGI Messages API page shows an OpenAI client with base_url set to an Inference Endpoints URL ending in /v1/ and a Hugging Face API key, and says this works for any endpoint running TGI with an LLM that has a chat template. [21]

4Common mistakes

  1. Sizing a GPU from the weights alone.

    Why it causes problems
    The model loads, then the server runs out of memory, preempts requests or caps concurrency at one or two conversations, because the KV cache needs memory too and grows with context length and with the number of users.
    How to recognise it
    Startup succeeds but long prompts fail or slow down, vLLM logs preemption warnings, or `ollama ps` shows a CPU/GPU split after you raise the context length.
    How to fix it
    Compute KV bytes per token from layers, KV heads and head dimension, multiply by the tokens you must hold at once, and add that to the weights plus overhead. If the total is over budget, quantize the weights or the cache, lower max-model-len, or add GPUs.

  2. Choosing a quantization level by file size alone.

    Why it causes problems
    A smaller file always looks like a win, but quantization costs accuracy, and the published size and speed tables do not show that cost. The loss on your task may be larger than on the benchmark a repository advertises.
    How to recognise it
    The model feels fine in a few casual chats but scores lower on your own evaluation set than the higher-precision version of the same model.
    How to fix it
    Run the same evaluation set at two or three quantization levels and pick the smallest one that meets your quality threshold. See [Evaluating LLM Applications](/topics/llm-evaluation/).

  3. Leaving a local runtime reachable from the network without authentication.

    Why it causes problems
    Ollama ignores API keys and listens on localhost by default. Binding it to 0.0.0.0 lets anyone who can reach the port use your GPU and your models, and nothing in the request identifies them.
    How to recognise it
    The port answers from another machine, `OLLAMA_HOST` is set to 0.0.0.0, and no proxy or gateway log shows authenticated callers.
    How to fix it
    Keep the default localhost binding. To share a model, put an authenticating reverse proxy or gateway in front, use a server that supports keys such as vLLM's --api-key, and restrict the port with a firewall.

  4. Downloading the main branch, or pickle-based weights from an unknown publisher.

    Why it causes problems
    An unpinned download can change under you, so results cannot be reproduced. Pickle files can run code when they are loaded, so a malicious weight file can compromise the machine that loads it.
    How to recognise it
    No `revision` in your download code, weights shipped as `.bin` or `.pt` files, and publishers you cannot identify.
    How to fix it
    Pin the revision to a full commit hash, prefer safetensors files, load models only from publishers you trust, and read the licence and any gating terms before building on a model.

  5. Using a laptop runtime as the production server.

    Why it causes problems
    Ollama defaults to one parallel request per model, so simultaneous users wait in a queue, and requests beyond the queue limit of 512 are rejected. Latency grows with every added user.
    How to recognise it
    Response time climbs in step with the number of simultaneous users, and a load test at expected concurrency shows requests waiting rather than running together.
    How to fix it
    Load-test at the concurrency you expect. If it matters, move to an inference server with continuous batching, such as vLLM, and size the KV cache for that many conversations.

  6. Assuming an OpenAI-compatible endpoint supports everything the hosted API does.

    Why it causes problems
    Unsupported parameters are ignored or rejected, so tool choice, log probabilities, multiple choices or stateful Responses features behave differently or fail, often only in a code path a quick test misses.
    How to recognise it
    A feature works against the hosted API and fails or changes behaviour after you change the base URL.
    How to fix it
    Write a small contract test that exercises the features you use, namely streaming, tool calls and structured output, against each server, and rerun it whenever you upgrade the server or the model.

Show solution

The function is a direct translation of the formulas. The sign check matters: without it, the one-GPU 70B case would print a negative number of tokens.

python
GIB = 2**30


def plan(*, params, layers, kv_heads, head_dim, bits_per_weight, kv_bytes=2,
         gpus=1, gpu_gib=24, utilization=0.92, overhead_gib_per_gpu=1.5):
    weights_gib = params * bits_per_weight / 8 / GIB
    usable_gib = gpus * gpu_gib * utilization
    kv_budget_gib = usable_gib - weights_gib - gpus * overhead_gib_per_gpu
    bytes_per_token = 2 * layers * kv_heads * head_dim * kv_bytes
    fits = kv_budget_gib > 0
    cached_tokens = int(kv_budget_gib * GIB // bytes_per_token) if fits else 0
    return {
        "weights_gib": round(weights_gib, 2),
        "kv_budget_gib": round(kv_budget_gib, 2),
        "kv_kib_per_token": bytes_per_token // 1024,
        "cached_tokens": cached_tokens,
        "fits": fits,
    }

import json
import os
import sys
import time
import urllib.request

BASE_URL = os.environ.get("BASE_URL", "http://localhost:11434/v1")
PROMPT = "Explain in three sentences why the KV cache grows with context length."


def chat(model, max_tokens=200):
    body = json.dumps({
        "model": model,
        "messages": [{"role": "user", "content": PROMPT}],
        "temperature": 0,
        "max_tokens": max_tokens,
    }).encode()
    request = urllib.request.Request(
        f"{BASE_URL}/chat/completions",
        data=body,
        headers={"Content-Type": "application/json", "Authorization": "Bearer ollama"},
    )
    start = time.perf_counter()
    with urllib.request.urlopen(request, timeout=300) as response:
        payload = json.load(response)
    return payload, time.perf_counter() - start


for model in sys.argv[1:]:
    payload, seconds = chat(model)
    tokens = payload.get("usage", {}).get("completion_tokens")
    rate = f"{tokens / seconds:.1f} tok/s" if tokens else "usage not reported"
    print(f"{model}: {seconds:.1f} s, {tokens} tokens, {rate}")
    print("   ", payload["choices"][0]["message"]["content"][:80].replace("\n", " "))

Hint 1

Use the model name from the NAME column of `ollama list` in the API call, including its tag.

Hint 2

Compare ratios instead of absolute sizes, because tools report decimal GB or binary GiB differently.

Hint 3

If the response has no `usage` field, compare wall-clock time for the same `max_tokens` instead of tokens per second.

Hint 4

If the printed reply is empty, the model may have spent its token budget on reasoning before answering, as some newer models do. Raise `max_tokens` or choose a model that does not reason first.

Show solution

Run the commands in this order, replacing the model names with the ones ollama list prints:

bash
ollama run hf.co/bartowski/Llama-3.2-3B-Instruct-GGUF "Say hi"
ollama run hf.co/bartowski/Llama-3.2-3B-Instruct-GGUF:Q8_0 "Say hi"
ollama list
ollama ps
python3 client.py "<name of the first model>" "<name of the Q8_0 model>"
python3 client.py "<name of the first model>" "<name of the Q8_0 model>"

Keep the output of the second client.py run. To predict sizes, take the parameter count from the model card (about 3.2 billion for a Llama 3.2 3B model; confirm it there) and apply the formula from the lesson:

python
params = 3.2e9
for name, bits in [("Q8_0", 8.5008), ("Q4_K_M", 4.8944)]:
    print(name, round(params * bits / 8 / 2**30, 2), "GiB")
print("ratio", round(8.5008 / 4.8944, 3))   # 1.737

With 3.2 billion parameters that prints roughly 3.17 GiB for Q8_0 and 1.82 GiB for Q4_K_M. Your ollama list sizes should follow the same pattern, so compare the ratio rather than the absolute numbers.

A reasonable conclusion has this shape. The Q4_K_M file is about 1.7 times smaller and generates tokens faster, so it is the sensible default for chat on a laptop. Before relying on it, run the same set of questions that matter to you, ideally with known answers, through both models and compare the results. That is the same method as in Evaluating LLM Applications, and the README does not provide quality numbers for you. The client script was checked against a local stub server and, during review, against a real local Ollama 0.34.2 server with a different, reasoning model, where it printed the token count and rate. It was not run with the Llama 3.2 3B files named here.

Check your answer

  • Did both calls succeed with the exact model names from `ollama list`, and did you discard each first call?
  • Is your measured size ratio close to 1.74, and if not, did you verify which quantization the default tag pulled?
  • Do your two sentences include a specific extra test, rather than only a preference?
