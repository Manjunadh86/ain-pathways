Pydantic AI

Pydantic AI is an open-source Python framework for building LLM agents, made by the team behind the Pydantic validation library. You declare an agent's dependencies, tools and output as Python types. The framework turns those types into schemas for the model, validates everything the model sends back, and asks the model to try again when validation fails.

1Overview

Why it matters

Many agent failures in production are ordinary software bugs at the boundary between code and model. The model returns JSON with a missing field. It calls a tool with a string where the function needs a date. A database handle reaches a tool through a global variable, so the tests cannot run without a real database. A provider change turns into a rewrite. Pydantic AI treats each of these as a typing problem: the types you already write describe what may cross the boundary, and the framework enforces them on every run.

It suits Python teams that want agent code to be read, reviewed and tested like the rest of their backend. Knowing how it works also tells you what it does not do. A validated output has the right shape, but it can still be the wrong answer, which is why the framework ships hooks for tracing and evaluation next to the type system. Anyone comparing agent frameworks, or debugging a run that keeps retrying, needs to know where validation happens and what each retry costs.

What you will be able to do

  • Pass per-run data and services to instructions, tools and output validators through deps and RunContext.
  • Register function tools and choose between ModelRetry, ToolFailed and an ordinary exception when a tool cannot succeed.
  • Define a validated structured output and trace what happens when the model's output fails validation.
  • Switch model providers with a provider-prefixed model string and run an agent offline with TestModel or FunctionModel.
  • Add OpenTelemetry tracing to an agent and write a small Pydantic Evals dataset that scores its behaviour.

Key terms

Agent
The main Pydantic AI object. It bundles instructions, tools, a dependency type, an output type and an optional default model, and it runs the agent loop for you.
Dependencies (deps)
The data and services one run needs, such as a customer id or a database client. You declare their type once and pass an instance each time you run the agent.
RunContext
The object Pydantic AI passes as the first argument to tools, dynamic instructions and output validators. Its deps attribute holds the dependencies of the current run.
Output type
The Python type a run must return, for example a Pydantic model. The framework builds a JSON schema from it and validates the model's final answer against it.
Function tool
A Python function the model may call during a run. Its signature and docstring become the tool schema, and its arguments are validated before the function executes.
ModelRetry
An exception you raise from a tool or output validator to send a message back to the model and ask it to try again. Each one uses part of a retry budget.
Model string
A name of the form provider:model, such as anthropic:claude-sonnet-4-6, that selects the model class, the provider connection and the model profile in one step.
Capability
The V2 unit of reuse. It packages tools, hooks, instructions and model settings so that the same behaviour can be attached to several agents.
Test model
A stand-in for a real LLM. TestModel generates schema-valid data with plain code, and FunctionModel lets a function you write play the model, so tests need no API key.
Instrumentation
The built-in OpenTelemetry tracing that records each agent run, model request and tool call as spans you can send to an observability backend.

2Explanation

Introduction

You have met the pieces already. Tool Calling and Structured Outputs showed that a model can be handed a JSON schema and asked to fill it in. The Agent Loop showed the while loop that runs tools until the model gives a final answer. Choosing an Agent Framework explained that frameworks differ mainly in how much of that they write for you. Pydantic AI's answer is specific: it writes the loop, the schemas and the validation, and it derives all three from Python type hints.

If you have used FastAPI, the idea is familiar. There you write a function with typed parameters, and the framework validates each HTTP request before your code runs and rejects bad input with a precise error. Pydantic AI comes from the team that maintains Pydantic, the validation library FastAPI is built on, and it applies the same design to the model side. The "client" sending data is now an LLM. When its tool arguments or its final answer do not match your types, the framework sends the validation error back to the model and lets it correct itself.

Here is the smallest useful case, a support message classified into a typed object:

python
from typing import Literal

from pydantic import BaseModel
from pydantic_ai import Agent


class Ticket(BaseModel):
    category: Literal['billing', 'bug', 'other']
    urgent: bool


agent = Agent('openai:gpt-5.2', output_type=Ticket, instructions='Classify the support message.')
result = agent.run_sync('I was charged twice this month and need it fixed today.')
print(result.output)  # one possible result: category='billing' urgent=True

result.output is a Ticket instance. There is no string to parse, your editor knows that result.output.urgent is a bool, and a reply with "category": "refunds" never reaches your code, because it fails validation and the model is asked again.

The rest of the lesson follows the diagram: the typed agent, dependency injection, tools, validated output, model providers, limits, and the hooks for testing, tracing and evaluation. It uses the V2 API. Pydantic AI reached V1 in September 2025 and V2.0 on 23 June 2026, and the Upgrade Guide (opens in a new tab) lists what changed, so check which version a tutorial was written for. The documentation moved from ai.pydantic.dev, which now redirects, to pydantic.dev/docs/ai (opens in a new tab).

How it works

An agent is a typed container

The Agents documentation (opens in a new tab) describes an Agent as a container for instructions, function tools, a structured output type, a dependency type, an optional default model, model settings and capabilities. A capability is the V2 unit of reuse: it packages tools, hooks, instructions and model settings so that several agents can share them. This snippet uses the first five components:

python
from dataclasses import dataclass

from pydantic import BaseModel, Field
from pydantic_ai import Agent, ModelRetry, RunContext


@dataclass
class Deps:
    customer_id: int
    orders: dict[str, float]  # order id -> total paid; stands in for a database client


class RefundDecision(BaseModel):
    order_id: str
    approve: bool
    refund_amount: float = Field(ge=0)


agent = Agent(
    'anthropic:claude-sonnet-4-6',
    deps_type=Deps,
    output_type=RefundDecision,
    instructions='Decide refunds. Look the order up first.',
)


@agent.tool
def get_order_total(ctx: RunContext[Deps], order_id: str) -> float:
    """Return the total paid for one order of the current customer."""
    if order_id not in ctx.deps.orders:
        raise ModelRetry(f'No order {order_id!r}. Known ids: {list(ctx.deps.orders)}')
    return ctx.deps.orders[order_id]


result = agent.run_sync('Refund order A-100, it never arrived.', deps=Deps(42, {'A-100': 59.97}))
print(result.output.refund_amount)  # a float that has already been validated

The agent's type is Agent[Deps, RefundDecision]. Because it is generic in both types, mypy or pyright flags a tool that declares RunContext[str], or code that treats result.output as a string. Type checking is optional. The hints on tool parameters and output_type are not, because they are used at run time to build schemas and validate data.

run_sync is one of five ways to run an agent. run is the async version, run_stream and run_stream_events stream output or events, and iter steps through the loop node by node. A run ends when the model produces an output that validates.

Dependency injection

deps_type takes the type, not an instance, and exists for type checking. Each run receives its own instance through deps=. Any function whose first parameter is RunContext[Deps] reads it from ctx.deps: tools (opens in a new tab), dynamic instructions (@agent.instructions) and output validators. A customer id, a database session or an HTTP client therefore reaches a tool as an argument and never through a global, and a test can swap in a fake with agent.override(deps=...). The Dependencies page (opens in a new tab) adds that plain def functions run in a thread pool, so prefer async def when a dependency does I/O.

Function tools

Register a tool with @agent.tool (it receives the context), @agent.tool_plain (it does not) or Agent(tools=[...]). Every parameter except the context goes into the tool's JSON schema. The docstring supplies the description, including per-parameter descriptions written in Google, NumPy or Sphinx style. Before your function runs, Pydantic validates the arguments the model sent. From there the documented outcomes (opens in a new tab) are:

In the toolWhat the model receivesRetry budget
Arguments fail validationA retry prompt listing the validation errorsOne tool retry used
raise ModelRetry('...')A retry prompt with your messageOne tool retry used
raise ToolFailed('...')A failed tool result it can reason aboutNone used
Any other exceptionNothing. The run stops and your code gets the exceptionNot applicable

Retries are counted per tool and default to 1. Change the budget with Agent(retries=...) or @agent.tool(retries=...). A tool that uses up its budget ends the run with UnexpectedModelBehavior.

Validated structured output

output_type accepts scalars, lists, dataclasses, Pydantic models and unions. In the default mode the output schema is registered as a special output tool, and the run ends when the model calls it with arguments that validate. If str is not among the output types, a plain-text reply does not count as a final answer. The Output page (opens in a new tab) documents three modes:

Rules that need I/O or run data belong in an @agent.output_validator function. It receives the context and the parsed output, and it raises ModelRetry to reject an answer. Output failures have their own budget, which also defaults to 1.

Model-agnostic providers

A model is chosen with a string of the form provider:model, such as openai:gpt-5.2, anthropic:claude-sonnet-4-6 or google:gemini-3-flash-preview, given to the Agent or to a single run with model=. Behind it are three parts, described in Models and Providers (opens in a new tab): a model class that speaks one vendor API, a provider that handles authentication and the endpoint, and a profile that records model quirks such as limits on tool schemas. A FallbackModel tries several models in order when one raises an API error.

Three details matter in V2. The bare openai: prefix uses the Responses API (openai-chat: selects Chat Completions). A name without a provider prefix raises an error. A plain pip install pydantic-ai, which needs Python 3.11 or later (opens in a new tab), brings the OpenAI, Anthropic and Google integrations, and other providers are extras such as pydantic-ai[bedrock,groq]. Portable code is not identical behaviour: models differ in output-mode support and quality, so rerun your evals after a switch.

Limits, and how retries multiply

UsageLimits caps a run. request_limit bounds the model responses the agent acts on and defaults to 50, and there are limits for tool calls, tokens and cost. Crossing one raises UsageLimitExceeded.

The Retries page (opens in a new tab) warns that retry layers stack. If one logical call can issue NNN model requests, across FFF fallback models, each sent by an SDK client allowed MMM attempts over a transport allowed KKK attempts, the worst case on the wire is

N×F×M×KN \times F \times M \times KN×F×M×K

Its example: an output budget of 2 gives N=3N = 3N=3, the OpenAI SDK default gives M=3M = 3M=3, and a transport stopped after two attempts gives K=2K = 2K=2, so 3×1×3×2=183 \times 1 \times 3 \times 2 = 183×1×3×2=18 requests, or 36 with a two-model fallback. request_limit bounds only NNN.

Testing, tracing and evals

Three hooks cover what types cannot.

  • Tests. TestModel (opens in a new tab) calls every tool with generated arguments and then returns generated output, using plain code and no LLM. FunctionModel lets your own function play the model. agent.override(model=..., deps=...) swaps either in around application code, and models.ALLOW_MODEL_REQUESTS = False blocks accidental real calls. See Testing Agents.
  • Tracing. Instrumentation is built on OpenTelemetry. logfire.configure() followed by logfire.instrument_pydantic_ai() sends a trace per run, with a span for each model request and tool call, to Pydantic Logfire. Agent.instrument_all() does the same with an OpenTelemetry SDK you configured, for any backend that understands the GenAI semantic conventions. See LLM and Agent Observability.
  • Evals. Pydantic Evals is a separate package, pydantic_evals. A Dataset holds Case objects and evaluators such as EqualsExpected, LLMJudge and HasMatchingSpan. dataset.evaluate_sync(task) runs every case and returns a report you can print or gate a release on. See Evaluating Agents.

Worked example: A refund agent run offline, with three kinds of failure corrected in five model requests

The task: a customer says one of three mugs in order A-100 arrived broken, and the agent must return a validated RefundDecision. So that everyone gets the same output without an API key, the LLM is replaced by a FunctionModel that replays five pre-written tool calls. Three of them are deliberately wrong. The agent, the tool, the validator and the loop are the real framework.

Install with pip install pydantic-ai (Python 3.11 or later) and save this as refund_agent.py:

python
from dataclasses import dataclass

from pydantic import BaseModel, Field
from pydantic_ai import Agent, ModelMessage, ModelResponse, ModelRetry, RunContext, ToolCallPart
from pydantic_ai.models.function import AgentInfo, FunctionModel


@dataclass
class Order:
    units: int
    unit_price: float

    @property
    def total(self) -> float:
        return round(self.units * self.unit_price, 2)


@dataclass
class Deps:  # per-run data and services; a real app would hold a database client here
    customer_id: int
    orders: dict[str, Order]


class RefundDecision(BaseModel):  # the only shape a run may return
    order_id: str
    approve: bool
    refund_amount: float = Field(ge=0)
    reason: str


agent = Agent(deps_type=Deps, output_type=RefundDecision, retries=2,
              instructions='Decide refunds. Look the order up before you decide.')


@agent.tool
def get_order(ctx: RunContext[Deps], order_id: str) -> str:
    """Look up one order of the current customer.

    Args:
        order_id: The id printed on the receipt, for example A-100.
    """
    order = ctx.deps.orders.get(order_id)
    if order is None:
        raise ModelRetry(f'No order {order_id!r}. Known ids: {", ".join(ctx.deps.orders)}')
    return f'{order_id}: {order.units} x {order.unit_price:.2f} = {order.total:.2f} USD'


@agent.output_validator
def refund_within_total(ctx: RunContext[Deps], output: RefundDecision) -> RefundDecision:
    order = ctx.deps.orders.get(output.order_id)
    if order is None:
        raise ModelRetry(f'No order {output.order_id!r}.')
    if output.refund_amount > order.total:
        raise ModelRetry(f'Refund {output.refund_amount:.2f} exceeds the order total {order.total:.2f}.')
    return output


def describe(part) -> str:
    if part.part_kind == 'retry-prompt':
        detail = part.content
        if not isinstance(detail, str):  # a list of Pydantic error details
            detail = '; '.join(f"{'.'.join(map(str, e['loc']))}: {e['msg']}" for e in detail)
        return f'retry-prompt for {part.tool_name}: {detail}'
    return f'{part.part_kind}: {part.content}'


class ScriptedModel:
    """Stands in for an LLM: answers each request with the next pre-written tool call."""

    def __init__(self, calls):
        self.calls = list(calls)
        self.step = 0

    async def __call__(self, messages: list[ModelMessage], info: AgentInfo) -> ModelResponse:
        self.step += 1
        tool, args = self.calls.pop(0)
        if tool == 'OUTPUT':  # the output tool generated from RefundDecision
            tool = info.output_tools[0].name
        print(f'[{self.step}] model sees:  {describe(messages[-1].parts[-1])}')
        print(f'    model calls: {tool}({args})')
        return ModelResponse(parts=[ToolCallPart(tool, args)])


good = {'order_id': 'A-100', 'approve': True, 'refund_amount': 19.99, 'reason': 'One mug arrived broken.'}
script = [
    ('get_order', {'order_id': 'A100'}),                           # wrong id
    ('get_order', {'order_id': 'A-100'}),
    ('OUTPUT', {k: v for k, v in good.items() if k != 'reason'}),  # a required field is missing
    ('OUTPUT', {**good, 'refund_amount': 199.9}),                  # more than the order total
    ('OUTPUT', good),
]
deps = Deps(customer_id=42, orders={'A-100': Order(3, 19.99), 'B-200': Order(2, 5.50)})

result = agent.run_sync(
    'Order A-100: one of the three mugs arrived broken. Refund that mug.',
    model=FunctionModel(ScriptedModel(script)),
    deps=deps,
)
print(result.output)
print('model requests:', result.usage.requests)

Run PYDANTIC_AI_NO_BANNER=1 python refund_agent.py. The variable hides a short notice that an uninstrumented process otherwise prints to stderr on its first run. Expected output:

text
[1] model sees:  user-prompt: Order A-100: one of the three mugs arrived broken. Refund that mug.
    model calls: get_order({'order_id': 'A100'})
[2] model sees:  retry-prompt for get_order: No order 'A100'. Known ids: A-100, B-200
    model calls: get_order({'order_id': 'A-100'})
[3] model sees:  tool-return: A-100: 3 x 19.99 = 59.97 USD
    model calls: final_result({'order_id': 'A-100', 'approve': True, 'refund_amount': 19.99})
[4] model sees:  retry-prompt for final_result: reason: Field required
    model calls: final_result({'order_id': 'A-100', 'approve': True, 'refund_amount': 199.9, 'reason': 'One mug arrived broken.'})
[5] model sees:  retry-prompt for final_result: Refund 199.90 exceeds the order total 59.97.
    model calls: final_result({'order_id': 'A-100', 'approve': True, 'refund_amount': 19.99, 'reason': 'One mug arrived broken.'})
order_id='A-100' approve=True refund_amount=19.99 reason='One mug arrived broken.'
model requests: 5

What to notice:

  • Request 2, a tool asks for a correction. get_order raised ModelRetry. The framework turned the message into a retry prompt, and the scripted model's next call used the right id.
  • Request 4, the schema rejects an output. final_result is the output tool generated from RefundDecision. Pydantic found reason missing, so the validator function never ran and no incomplete object reached your code.
  • Request 5, a business rule rejects an output. 199.9 is a valid non-negative float, so the schema passed. The output validator compared it with the order total from ctx.deps (3 × 19.99 = 59.97) and rejected it.
  • The retry budget. The output tool failed twice in a row. With the default budget of 1 the run would have ended at the second failure with UnexpectedModelBehavior, which is why the agent sets retries=2.
  • Dependencies. Neither the tool nor the validator touches a global. Give agent.run_sync a different Deps and the same agent serves another customer or a test.

To use a real model, delete the model= argument and construct the agent with a model string such as 'anthropic:claude-sonnet-4-6'. Nothing else changes.

Edge cases and limitations

A validated output is not a correct output
Validation checks shape and the rules you wrote, nothing more. A RefundDecision that approves the wrong order with a plausible amount passes every check in the worked example. Put rules you can compute into an output validator, keep free-text fields to a minimum, and measure everything else with evals on real cases. Treat a passing type check as the start of quality work.
The default retry budget allows one correction
Tool retries and output retries both default to 1, and tool retries are counted per tool. A tool that fails twice in a row, or an output that is rejected twice, ends the run with UnexpectedModelBehavior. Raise the budget where corrections are normal, with the retries argument on the agent or on one tool. When a call has finished and simply failed, raise ToolFailed instead of ModelRetry. The documentation states that ToolFailed shows the model a failed result without using the retry budget.
A run-level request limit does not bound network requests
The request limit counts the model responses the agent acts on, 50 by default. It does not see provider SDK retries, transport retries or the attempts a fallback model moved past, and those layers multiply. The documentation's example reaches 18 wire requests from an output budget of 2, and 36 with a two-model fallback. Set SDK retries to zero when you use a FallbackModel, as the documentation recommends, and budget for the worst case.
Output modes are not supported equally by every model
Native Output depends on the provider's structured output feature, which not all models have, and the documentation notes that Gemini models before Gemini 3 cannot combine it with function tools. Prompted Output works everywhere but is described as often the least reliable mode, because nothing forces the model to follow the schema. An agent that works with one model string can fail with another, so test each model you intend to use.
Tutorials written for V1 break in small ways on V2
The Upgrade Guide lists the changes. Among them: result.usage and result.timestamp became properties, so calling them as methods fails. The bare openai prefix now selects the Responses API. Model names without a provider prefix raise an error. Agent arguments such as instrument and mcp_servers moved to capabilities and toolsets. The default end strategy changed, so function tools requested in the same response as a successful output now run. Check the version before copying code.
Type checkers cannot always infer a union output type
Pydantic AI accepts a union such as Success or InvalidRequest as the output type at run time, but the documentation explains that mypy and Pyright before 1.1.412 do not accept such an expression as a value. You then write the generic parameters on the Agent yourself and add a type-ignore comment, or pass the types as a list. The agent behaves correctly either way; only the static check needs help.

When to use it, and when something simpler is enough

Use it when

  • The application is written in Python with type hints, and you want agent code that backend engineers can review and unit-test like any other module.
  • The agent's result feeds code, such as a database write, an API call or a branch, so it must arrive as validated structured data and never as free text to parse.
  • Tools need per-request resources such as a tenant id, a database session or an HTTP client, and tests must be able to replace them with fakes.
  • You expect to change or mix model providers, or need a fallback model, and do not want provider SDK types spread through your code.
  • You already run an OpenTelemetry backend and want agent runs to appear there as traces.

Think twice when

  • The application is not in Python, or is pinned to a Python version older than 3.11, which the current release does not support.
  • One model call with a JSON schema does the whole job. The provider SDK's structured output feature is less to learn and one less dependency.
  • The people building the agent do not write code. A visual builder such as Flowise, Langflow or n8n fits them better.
  • The design centres on an explicit graph with checkpoints and human review at fixed nodes. A graph-first framework such as LangGraph makes that structure the main abstraction.

A simpler alternative. A provider SDK's structured output feature, a Pydantic model for validation and the hand-written loop from the agent loop lesson. That is enough for one model, a few tools and no retries. It stops being enough when you find yourself writing schema generation for tools, a retry-on-validation-error path, a second provider adapter and fake models for tests, which is the code Pydantic AI already contains.

Key takeaways

  • A Pydantic AI agent bundles instructions, tools, a dependency type and an output type, and it is generic in the last two so that a type checker can catch misuse before the code runs.
  • Dependencies are passed to each run with deps and reach tools, dynamic instructions and output validators through RunContext, which removes globals and lets tests substitute fakes.
  • Pydantic validates every tool argument and every final output, and a failure goes back to the model as a retry prompt within a budget that defaults to one retry per tool and one for the output.
  • The model is selected by a provider-prefixed string, so switching providers is a one-line change, but models differ in capability and you should rerun your evals afterwards.
  • Validation guarantees shape and not correctness, so usage limits, OpenTelemetry tracing and Pydantic Evals are part of a production setup and not optional extras.
  • TestModel and FunctionModel replace the LLM with plain code, which makes it possible to test an agent's tools, validators and retry paths offline and for free.

Example 1 of 5

Qualio gates every AI release on a Pydantic Evals pass rate

QualioDocumented in a case study

Qualio sells a compliance and quality management platform to medical device makers, pharma companies and biotechs. A case study published by Pydantic in July 2026 describes how its engineering team builds a chat assistant on Pydantic AI and tests its AI features with Pydantic Evals. [22][12][13][14]

The problem

Qualio's customers are audited, so every release has to ship with evidence that the software behaves as described. For years that evidence came from browser-automation tests with yes-or-no answers. The case study explains why this stopped working for AI features: a browser test can confirm that an assistant rendered, but not that it found the right policy document, cited it accurately or declined to invent a regulation. Without a regression suite for that behaviour, a prompt change or a model upgrade could degrade the product without anyone noticing.

Where this topic fits

Pydantic AI is the agent framework for the assistant: one agent whose tools are plain Python functions. Pydantic Evals sits in the deploy pipeline. The dataset runs against every prompt, orchestration or model change, and a pass rate under the team's threshold blocks the release. The same eval results serve as the evidence that customers' compliance teams review.

How it is applied, step by step

  1. The team compared Bedrock Agents, AG2, Strands Agents, LangGraph and Pydantic AI head to head and chose Pydantic AI for iteration speed, because an agent could be defined simply and tied to tools that are ordinary Python methods.
  2. For actions that need a person, the relevant tool sends a prompt to the user over the websocket connection and waits for a confirmation or rejection before the agent proceeds.
  3. The assistant started as one agent per domain behind a delegating main agent. Coordinating message histories added latency and crowded out business logic, so the team consolidated to a single agent with two high-level tools, running old and new versions side by side behind a feature flag.
  4. The team maintains roughly 160 test cases and 300 evaluations across its AI features and runs them on every prompt, orchestration or model change.
  5. Most evaluators use a cheaper LLM as a judge against criteria written in plain language. One evaluator inspects spans to confirm that the agent called the tools it was supposed to call.
  6. A pass rate below the threshold blocks the deploy. Because non-engineers can read the criteria, the same results are shown to customers during due-diligence reviews.

Why this approach fits

An eval only changes behaviour when it is attached to a decision, and here the decision is the deploy. Plain-language rubrics do double duty as test definitions and as audit evidence a compliance reviewer can read. The framework choice supports the same loop: with tools as ordinary functions, changing a tool is a code change that the eval suite can check within minutes, where the case study says the Bedrock alternative needed an infrastructure deployment for every tool change. A light framework also let the team replace a multi-agent design with a single agent while the evals confirmed nothing regressed.

Limitation or tradeoff

An LLM judge is itself a model. It can be wrong, it can share blind spots with the model it grades, and its verdicts can shift when the judge model is upgraded, so the gate needs its own spot checks. A threshold below 100% means some failing cases ship by design. Several hundred judged evaluations on every change cost time and tokens. A span-based check depends on span names and attributes that can change between instrumentation versions. The account is published by the framework's vendor and does not give the threshold value or examples of regressions the gate caught.

4Common mistakes

  1. Reading a module-level database client or API key inside a tool instead of taking it from ctx.deps.

    Why it causes problems
    The tool is now tied to one global resource. Tests need monkeypatching or a live service, and in a server that handles several users at once a shared global can leak one tenant's connection or identity into another tenant's run.
    How to recognise it
    Tools registered with tool_plain that import clients from other modules, tests that patch module attributes before calling the agent, and an agent created without deps_type even though its tools perform I/O.
    How to fix it
    Put the client, the user or tenant id and any keys into a dependencies dataclass, declare it with deps_type, read it from ctx.deps in tools, instructions and validators, and pass a fake instance in tests with deps or agent.override.

  2. Catching every exception in a tool and returning the error text as if it were a normal result.

    Why it causes problems
    The model receives the error string as data. It may quote it to the user as an answer or continue as if the call succeeded, and the retry budget and the trace both record a success. The opposite error, letting a fixable problem such as a mistyped id raise an ordinary exception, ends the whole run.
    How to recognise it
    Tool functions with a broad try and except that returns a string starting with words like Error. Traces where a tool span is marked successful but its return value is an error message.
    How to fix it
    Choose the signal on purpose. Raise ModelRetry when different arguments could succeed, raise ToolFailed when the call is finished and failed so the model can see that and decide, and let real programming errors propagate so they fail loudly.

  3. Treating an output that passed validation as an answer that is correct.

    Why it causes problems
    A wrong decision with the right fields flows straight into the database or the next API call. Because nothing raised, there is no error to alert on, and the problem appears later as bad data.
    How to recognise it
    No output validators on agents whose outputs trigger actions, no eval dataset in the repository, and incident reviews in which the model's output was well formed but wrong.
    How to fix it
    Encode every rule you can compute in the type or in an output validator that uses ctx.deps, and cover the rest with an eval dataset built from real cases that runs before each release.

  4. Raising the retry budget to make validation errors go away.

    Why it causes problems
    Every retry is another model request, so latency and cost rise, and the retry layers multiply with SDK and transport retries. The underlying cause, usually an unclear field or tool description or a schema that is too complicated, stays in place.
    How to recognise it
    Traces in which the same field fails validation again and again, a retries value that keeps growing in code review, and a rising number of model requests per run.
    How to fix it
    Read the retry prompts in a trace to see what the model gets wrong. Then add field descriptions, simplify or split the output type, improve the tool docstring, and keep the budget small with a request limit as a backstop.

  5. Turning on tracing without deciding whether prompts and tool arguments may leave your systems.

    Why it causes problems
    Instrumentation records message content and tool call arguments by default. Customer messages, document text and any identifiers a tool receives are then stored in the observability backend, which may breach a data-handling agreement.
    How to recognise it
    Open one trace and look for user text and tool arguments in the span attributes. Check whether the backend's region, retention and access rules match the rules for that data.
    How to fix it
    Decide per environment. Where content must not be exported, pass InstrumentationSettings with include_content set to False, which keeps the structure and timings of the run, and redact or avoid sensitive values in tool arguments.

Build a typed triage agent and test its retry paths without an API key

A support team wants an agent that triages incoming messages. Build it with Pydantic AI and prove with three offline tests that its validation and retry paths work. You need only pip install pydantic-ai (Python 3.11 or later). No API key and no network access are required.

Data for the tests:

Use this helper so that a scripted function plays the model. Each tuple is one model reply: a tool name and its arguments, or 'OUTPUT' for the agent's output tool.

python
from pydantic_ai import ModelMessage, ModelResponse, ToolCallPart
from pydantic_ai.models.function import AgentInfo, FunctionModel


def scripted(*calls):
    """Build a FunctionModel that replays the given tool calls, one per model request."""
    remaining = list(calls)

    def model(messages: list[ModelMessage], info: AgentInfo) -> ModelResponse:
        tool, args = remaining.pop(0)
        name = info.output_tools[0].name if tool == 'OUTPUT' else tool
        return ModelResponse(parts=[ToolCallPart(name, args)])

    return FunctionModel(model)

Write triage_test.py containing the agent and three tests:

  1. A free customer (c-9): the model calls get_plan, then returns priority 2. The output is accepted.
  2. An enterprise customer (c-7): the model calls get_plan, returns priority 2, is sent back, and returns priority 4.
  3. A free customer: the model skips the tool and returns priority 9, is sent back, and returns priority 3.

Requirements

  • The dependencies are a dataclass with a customer_id string and a plans dictionary, declared on the agent with deps_type. The agent has no default model, and every run passes model explicitly.
  • The output type is a Pydantic model named Triage with category limited to billing, bug or how-to, priority limited to the integers 1 to 5, and a reply string.
  • A tool named get_plan takes only the run context and returns the customer's plan from ctx.deps, with free as the default. It must not read any module-level variable.
  • An output validator raises ModelRetry when the customer's plan is enterprise and the priority is below 4.
  • models.ALLOW_MODEL_REQUESTS is set to False so that an accidental call to a real provider raises.

Expected behaviour

Hint 1

A tool with no parameters besides the context is called with an empty argument dictionary, so the script entry is the tuple of the name get_plan and an empty dict.

Hint 2

Hint 3

Show solution
python
from dataclasses import dataclass
from typing import Literal

from pydantic import BaseModel, Field
from pydantic_ai import Agent, ModelMessage, ModelResponse, ModelRetry, RunContext, ToolCallPart, models
from pydantic_ai.models.function import AgentInfo, FunctionModel

models.ALLOW_MODEL_REQUESTS = False  # a call to a real provider would now raise


@dataclass
class Deps:
    customer_id: str
    plans: dict[str, str]  # customer id -> plan name


class Triage(BaseModel):
    category: Literal['billing', 'bug', 'how-to']
    priority: int = Field(ge=1, le=5)
    reply: str


triage_agent = Agent(
    deps_type=Deps,
    output_type=Triage,
    instructions='Triage the support message. Check the customer plan before you set a priority.',
)


@triage_agent.tool
def get_plan(ctx: RunContext[Deps]) -> str:
    """Return the plan of the customer who sent the message."""
    return ctx.deps.plans.get(ctx.deps.customer_id, 'free')


@triage_agent.output_validator
def enterprise_is_urgent(ctx: RunContext[Deps], output: Triage) -> Triage:
    if ctx.deps.plans.get(ctx.deps.customer_id) == 'enterprise' and output.priority < 4:
        raise ModelRetry('Enterprise customers need priority 4 or 5.')
    return output


def scripted(*calls):
    """Build a FunctionModel that replays the given tool calls, one per model request."""
    remaining = list(calls)

    def model(messages: list[ModelMessage], info: AgentInfo) -> ModelResponse:
        tool, args = remaining.pop(0)
        name = info.output_tools[0].name if tool == 'OUTPUT' else tool
        return ModelResponse(parts=[ToolCallPart(name, args)])

    return FunctionModel(model)


def answer(priority: int) -> dict:
    return {'category': 'billing', 'priority': priority, 'reply': 'We are checking the duplicate charge.'}


MESSAGE = 'I was charged twice this month.'
PLANS = {'c-7': 'enterprise', 'c-9': 'free'}


def test_free_customer_keeps_low_priority():
    model = scripted(('get_plan', {}), ('OUTPUT', answer(2)))
    result = triage_agent.run_sync(MESSAGE, model=model, deps=Deps('c-9', PLANS))
    assert result.output == Triage(**answer(2))
    assert result.usage.requests == 2


def test_enterprise_customer_is_escalated():
    model = scripted(('get_plan', {}), ('OUTPUT', answer(2)), ('OUTPUT', answer(4)))
    result = triage_agent.run_sync(MESSAGE, model=model, deps=Deps('c-7', PLANS))
    assert result.output.priority == 4
    assert result.usage.requests == 3


def test_out_of_range_priority_is_sent_back():
    model = scripted(('OUTPUT', answer(9)), ('OUTPUT', answer(3)))
    result = triage_agent.run_sync(MESSAGE, model=model, deps=Deps('c-9', PLANS))
    assert result.output.priority == 3
    assert result.usage.requests == 2


if __name__ == '__main__':
    test_free_customer_keeps_low_priority()
    test_enterprise_customer_is_escalated()
    test_out_of_range_priority_is_sent_back()
    print('3 tests passed')

Why it works:

  • No globals. get_plan and the validator read everything from ctx.deps, so each test chooses the customer by constructing a different Deps. PLANS is test data, and the agent never refers to it.
  • Two different rejections. In the enterprise test the output is well formed, so Pydantic accepts it and your validator rejects it with ModelRetry. In the out-of-range test Pydantic rejects it first, and the retry prompt the model receives is built from the validation error.
  • Request counts. Every tool call and every rejected output costs one more model request, which is what the assertions on result.usage.requests pin down.
  • Budget. Each script fails the output once, inside the default budget of 1. Script two bad outputs in a row and the run raises UnexpectedModelBehavior until you raise the budget, for example with Agent(..., retries={'output': 2}).

In application code you would give the agent a default model string and tests would swap it with triage_agent.override(model=scripted(...)). As an optional check, change RunContext[Deps] to RunContext[str] on get_plan and run pyright or mypy. The type checker reports the mismatch with the agent's dependency type without running anything.

  • It prints the pass rate as passed over total and exits with status 1 when the rate is below 0.9 and with status 0 otherwise.
  • After your fix to the router, the same script passes without any change to the cases or the threshold.

Expected behaviour

The first run prints a report table in which the invoice case is the only failure, then pass rate: 4/5 = 0.80 and GATE FAILED, and exits with status 1. The router has no rule for the word invoice, so that message falls through to how-to. After you add a rule for it, the script prints pass rate: 5/5 = 1.00 and GATE PASSED and exits with status 0.

Hint 1

Each entry of report.cases has an assertions dictionary. Its values are results with a value attribute that is True or False.

Hint 2

In bash or zsh, the command echo followed by a dollar sign and a question mark prints the exit status of the previous command.

Hint 3

Do not change an expected output to make the gate pass. The label is the specification, and the function is what is wrong.

Show solution
python
import sys

from pydantic_evals import Case, Dataset
from pydantic_evals.evaluators import EqualsExpected

THRESHOLD = 0.9


def route(message: str) -> str:
    text = message.lower()
    if 'refund' in text or 'charged' in text:
        return 'billing'
    if 'error' in text or 'crash' in text:
        return 'bug'
    return 'how-to'


dataset = Dataset(
    name='ticket_routing',
    cases=[
        Case(name='double_charge', inputs='I was charged twice this month', expected_output='billing'),
        Case(name='refund_request', inputs='Please refund my last order', expected_output='billing'),
        Case(name='crash', inputs='The app crashes when I open settings', expected_output='bug'),
        Case(name='export', inputs='How do I export my data?', expected_output='how-to'),
        Case(name='invoice', inputs='My invoice shows the wrong amount', expected_output='billing'),
    ],
    evaluators=[EqualsExpected()],
)

report = dataset.evaluate_sync(route)
report.print(include_input=True, include_output=True, include_durations=False)

results = [r.value for case in report.cases for r in case.assertions.values()]
pass_rate = sum(results) / len(results)
print(f'pass rate: {sum(results)}/{len(results)} = {pass_rate:.2f}')
if pass_rate < THRESHOLD:
    print('GATE FAILED')
    sys.exit(1)
print('GATE PASSED')

The first run ends with:

text
pass rate: 4/5 = 0.80
GATE FAILED

Four of the five cases match, and 4 / 5 = 0.80 is below the 0.9 threshold. The failing case is invoice: the message contains none of the billing keywords, so route returns how-to. Fix the function, not the label:

python
def route(message: str) -> str:
    text = message.lower()
    if any(word in text for word in ('refund', 'charged', 'invoice')):
        return 'billing'
    if 'error' in text or 'crash' in text:
        return 'bug'
    return 'how-to'

The second run ends with:

text
pass rate: 5/5 = 1.00
GATE PASSED

Answer to the question: an agent's free-text reply has no single correct string, so exact equality can no longer check whether the reply is accurate and appropriate in tone. You would keep EqualsExpected for the category, add an LLMJudge with a specific rubric for the reply, and accept that the judge is itself a model whose verdicts need occasional review.

The gate has the same structure as the one in the Qualio example: a dataset, evaluators, a pass rate and an exit code that a CI system can act on. Only the task and the evaluators change when the function under test becomes an agent.
