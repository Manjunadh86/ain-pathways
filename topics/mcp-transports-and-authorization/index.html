MCP Transports and Authorization

MCP defines two standard transports for carrying its JSON-RPC messages. With stdio the client launches the server as a local subprocess; with Streamable HTTP each message is an HTTP POST to the server's URL. Remote servers usually protect access with OAuth-based authorization, which the specification makes optional, while stdio servers take credentials from their environment.

1Overview

Why it matters

The transport decides who can reach a server, whose machine runs its code, and where its credentials live. A stdio server is a program that runs with your own user's permissions, so installing one is closer to installing software than to adding a web service. A remote server runs on someone else's infrastructure and holds a token for your account, so the questions become who may call it, what that token allows, and what data you send it. Teams get these choices wrong in predictable ways: a local server that only one developer can use, an HTTP server on a laptop port that any web page can reach, or an npm package given the keys to an email account.

Anyone who connects an agent to a hosted service, publishes a server for other people, or approves servers for a company needs this. The details also moved recently. Revision 2026-07-28 of the specification removed protocol-level sessions and the initialize handshake, so tutorials that mention Mcp-Session-Id describe an earlier protocol. Documented incidents, such as a malicious email-sending package and a code-execution bug in a OAuth proxy for MCP clients, show what the risks look like in practice.

Key terms

Transport
The binding that frames and delivers MCP's JSON-RPC messages between a client and a server. It does not change what the messages mean.
stdio
The transport in which the client launches the server as a subprocess and exchanges one JSON-RPC message per line over the process's standard input and output.
Streamable HTTP
The transport in which each client message is an HTTP POST to a single MCP endpoint, and the server replies with one JSON object or with a stream of events.
Server-Sent Events (SSE)
A web standard in which one HTTP response stays open and delivers a series of events. In Streamable HTTP the stream belongs to a single request.
Resource server
In OAuth, the API that accepts access tokens. A protected MCP server plays this role.
Protected Resource Metadata
A JSON document, defined by RFC 9728, in which an MCP server names itself and the authorization servers whose tokens it accepts.
PKCE
Proof Key for Code Exchange. The client invents a secret, sends only its hash when asking for an authorization code, and reveals the secret when redeeming it, so a stolen code is useless to anyone else.
Resource indicator
The `resource` parameter of RFC 8707. The client states which server a token is for, so the token can be bound to that server as its audience.
Token passthrough
The forbidden pattern in which an MCP server accepts a token that was not issued to it, or forwards the client's token to another API.
Client ID Metadata Document
A JSON document hosted at an HTTPS URL that doubles as the client's `client_id`, so a client can introduce itself to an authorization server it has never met.

2Explanation

Introduction

In Model Context Protocol (MCP) you met the host, the client and the server, and saw that they exchange JSON-RPC messages. This lesson is about what sits underneath: how those messages physically travel, who is allowed to send them, and how far you should trust the program at the other end.

Think of two ways to use a power tool. You can take one from your own toolbox: you run it, only you hold it, and it can do anything you can do in your workshop. Or you can use one at a hire shop: the shop runs it, many customers share it, and you show identification to get a pass that covers specific tools for a limited time. MCP has both arrangements. A local server is started by your host as a subprocess and talks over the stdio transport. A remote server is operated by someone else, reached by URL over the Streamable HTTP transport, and usually protected by OAuth, the standard that lets an application obtain a limited access token on your behalf without ever seeing your password.

Four decisions follow from that picture. Which transport carries the messages? Does the server run on your machine or on someone else's? How does a remote server decide who is calling and what they may do? And how much do you trust a server you did not write? The first half of the lesson covers the transports and the OAuth flow as the specification defines them. The second half covers the risks of third-party servers, using documented cases: GitHub's local and hosted servers, Cloudflare's tooling for remote servers, Claude Code's client behaviour, a code-execution flaw in an OAuth proxy, and a malicious npm package.

How it works

One message format, two transports

The specification treats a transport as a binding: it defines how messages are framed and delivered, how request metadata travels, and how cancellation and shutdown are signalled. What a message means does not change with the transport. This lesson follows revision 2026-07-28, in which every request carries its own protocol version and capabilities in _meta (see MCP).

stdio. The client launches the server as a subprocess and talks over its standard streams.

  • The server reads JSON-RPC messages from stdin and writes them to stdout, one message per line. A message must not contain embedded newlines.
  • The server may write UTF-8 log text to stderr. It must not write anything to stdout that is not a valid MCP message, so a stray print("debug") corrupts the channel.
  • There is no authorization step: the process belongs to the user who started it.
  • To shut down, the client closes the server's input, waits, and forcibly terminates the process if it does not exit. If the process dies unexpectedly, the client should restart it and retry what was in flight.

Streamable HTTP. The server is an independent process with a single HTTP endpoint, such as https://example.com/mcp.

  • Every client message is its own POST, with an Accept header that lists both application/json and text/event-stream.
  • For a request, the server replies with one JSON object, or with a Server-Sent Events (SSE) stream scoped to that request that may carry progress notifications before the final response. A POSTed notification gets 202 Accepted (this revision defines no core client notifications on HTTP, so you will rarely see one). Closing the stream cancels the request.
  • Each POST carries MCP-Protocol-Version and Mcp-Method, plus Mcp-Name for tools/call, resources/read and prompts/get. They mirror fields of the body so that load balancers and gateways can route without parsing it. A mismatch must be rejected with 400 Bad Request and error code -32020.
  • Servers must validate the Origin header (an invalid one gets 403 Forbidden), should bind to 127.0.0.1 when they run locally, and should authenticate connections. Without these, a web page can use DNS rebinding to reach a server on your machine.

The same tools/call on both transports (JSON abbreviated: the optional clientInfo is left out):

text
stdio: one line written to the server's stdin (wrapped here for reading only)
{"jsonrpc":"2.0","id":1,"method":"tools/call","params":{"name":"get_weather",
 "arguments":{"location":"Seattle, WA"},"_meta":{"io.modelcontextprotocol/protocolVersion":"2026-07-28",
 "io.modelcontextprotocol/clientCapabilities":{}}}}

Streamable HTTP: one POST (same JSON as the body)
POST /mcp HTTP/1.1
Accept: application/json, text/event-stream
Content-Type: application/json
MCP-Protocol-Version: 2026-07-28
Mcp-Method: tools/call
Mcp-Name: get_weather

Earlier revisions (2025-03-26 to 2025-11-25) let a server assign an Mcp-Session-Id, open a standalone GET stream for server-initiated messages and resume streams with Last-Event-ID. Revision 2026-07-28 removed all three, so a server that supports only the new revision should answer GET with 405 and ignore a session header. The older HTTP+SSE transport is deprecated.

Local or remote

The architecture overview calls a server that runs on your machine over stdio a local server, and one that runs on a platform over Streamable HTTP a remote server. Local servers typically serve one client; remote servers typically serve many. Neither is safer by default. They move trust to different places: with stdio you trust the code you run, with a remote server you trust the operator with the data you send and the token you grant.

Authorization for remote servers

Authorization is optional in MCP. An HTTP-based server that uses it should follow the authorization specification, a selected subset of OAuth 2.1 and related standards. A stdio server should not; it reads credentials from its environment. The protected MCP server is an OAuth resource server, the client is an OAuth client acting for a user, and an authorization server (hosted with the MCP server or separately) signs the user in and issues tokens.

  1. Challenge. A request without a valid token gets 401 Unauthorized. The WWW-Authenticate: Bearer header can carry resource_metadata, the URL of the server's metadata, and scope, the permissions the operation needs.
  2. Protected Resource Metadata. The client fetches that URL or, without one, probes /.well-known/oauth-protected-resource/<path> and then /.well-known/oauth-protected-resource. The document (RFC 9728 (opens in a new tab)) names the server's resource and its authorization_servers. RFC 9728 makes the second optional; MCP requires at least one.
  3. Authorization server metadata. The client tries RFC 8414 and OpenID Connect discovery URLs in a fixed order and discards a document whose issuer differs from the one used to build the URL.
  4. Client registration. In priority order: pre-registered client details; a Client ID Metadata Document, if the server advertises client_id_metadata_document_supported; Dynamic Client Registration, which is now deprecated; otherwise ask the user.
  5. Authorization request. The client uses PKCE with S256 (RFC 7636 (opens in a new tab)) and refuses to continue if the metadata lacks code_challenge_methods_supported. It sends resource= with the MCP server's canonical URI and asks for the challenged scopes. It records the expected issuer and checks the iss value in the redirect before redeeming the code.
  6. Token request. It repeats resource and sends the code_verifier.
  7. Use. Every HTTP request carries Authorization: Bearer <token>. Tokens never go in the query string.
  8. Validation and step-up. The server must check that the token was issued for it. An invalid token gets 401. A valid token with too few permissions gets 403 with error="insufficient_scope" and the scopes needed. The client unions them with its earlier scopes, re-authorizes and retries a limited number of times.

A server that calls an upstream API is a separate OAuth client there and uses a separate token. It must not pass the client's token through.

Risks of third-party servers

  • Local code execution. A stdio server runs with the host's privileges, so a malicious start command or package acts as you. Hosts with one-click setup must show the exact command and ask for approval, and should sandbox servers.
  • Data and instructions. A remote server receives what the model sends it, and what it returns enters the model's context. Tool descriptions are untrusted unless the server is, and fetched content can carry prompt injection.
  • Hostile metadata. Clients follow URLs the server supplies: the metadata URL, the authorization server list and its endpoints. These can point at internal addresses (SSRF) or use schemes such as javascript:.
  • Confused proxies. A proxy that fronts a third-party API with one static client ID and allows dynamic registration must get per-client consent. Accepting tokens issued for other services breaks audience separation.

Worked example: Connecting to a protected remote server, from the first 401 to a step-up

Everything below uses invented hosts under example.com, a name reserved for documentation, so you can run the code without contacting anyone. The scenario: a client whose client ID is https://app.example.com/client.json wants to call tools on https://mcp.example.com/mcp. The server's authorization server is https://auth.example.com/tenant1.

The challenge. The client posts a tool call with no token. The server answers (the shape follows the specification's examples):

http
HTTP/1.1 401 Unauthorized
WWW-Authenticate: Bearer resource_metadata="https://mcp.example.com/.well-known/oauth-protected-resource/mcp",
                         scope="files:read"

The server's metadata. A GET on that URL returns a document like this. Section 3.3 of RFC 9728 requires the client to discard it if resource is not identical to the URL it used to call the server, here https://mcp.example.com/mcp.

json
{"resource": "https://mcp.example.com/mcp",
 "authorization_servers": ["https://auth.example.com/tenant1"],
 "scopes_supported": ["files:read", "files:write"]}

Discovery URLs, PKCE and the authorization URL. Save the script as mcp_auth_trace.py and run python3 mcp_auth_trace.py; it needs only the standard library. The verifier is the test vector from RFC 7636, appendix B, so you can compare the challenge with the RFC. A real client generates a fresh random verifier of 43 to 128 characters for every authorization request, for example with secrets.token_urlsafe(48).

python
import base64, hashlib, re
from urllib.parse import quote, urlencode, urlsplit

def prm_urls(mcp_url):
    p = urlsplit(mcp_url)
    base = f"{p.scheme}://{p.netloc}/.well-known/oauth-protected-resource"
    return ([base + p.path.rstrip("/")] if p.path.strip("/") else []) + [base]

def as_urls(issuer):
    p = urlsplit(issuer)
    origin, path = f"{p.scheme}://{p.netloc}", p.path.rstrip("/")
    if path:
        return [f"{origin}/.well-known/oauth-authorization-server{path}",
                f"{origin}/.well-known/openid-configuration{path}",
                f"{origin}{path}/.well-known/openid-configuration"]
    return [f"{origin}/.well-known/oauth-authorization-server",
            f"{origin}/.well-known/openid-configuration"]

def s256(verifier):
    digest = hashlib.sha256(verifier.encode("ascii")).digest()
    return base64.urlsafe_b64encode(digest).rstrip(b"=").decode()

def challenge_params(header):
    return dict(re.findall(r'(\w+)="([^"]*)"', header))

def scope_union(old, new):
    return " ".join(dict.fromkeys(old.split() + new.split()))

header = ('Bearer resource_metadata="https://mcp.example.com/.well-known/oauth-protected-resource/mcp", '
          'scope="files:read"')
verifier = "dBjftJeZ4CVP-mB92K27uhbUJU1p1r_wW1gFWFOEjXk"   # RFC 7636, appendix B
challenge = s256(verifier)
query = urlencode({"response_type": "code", "client_id": "https://app.example.com/client.json",
                   "redirect_uri": "http://127.0.0.1:3000/callback", "code_challenge": challenge,
                   "code_challenge_method": "S256", "resource": "https://mcp.example.com/mcp",
                   "scope": challenge_params(header)["scope"], "state": "xyz123"}, quote_via=quote)

print(challenge_params(header))
print(prm_urls("https://mcp.example.com/mcp"))
print(*as_urls("https://auth.example.com/tenant1"), sep="\n")
print(challenge, challenge == "E9Melhoa2OwvFrEMTJguCHaoeK1t8URWbuGJSstw-cM")
print("https://auth.example.com/tenant1/authorize?" + query)
print(scope_union("files:read", "files:write"))

files:read files:write

Read the output line by line. Line 1 is what the client extracts from the 401. Line 2 lists where it would look for the server's metadata if the header had no resource_metadata, most specific first. Lines 3 to 5 are the places to look for the metadata of an issuer that has a path. Line 6 is the S256 challenge, and True confirms it matches the RFC. Line 7 is the URL the client opens in the user's browser: it contains the challenge but not the verifier, and resource names the MCP server. Line 8 is the scope set after a step-up, explained below.

Token request and use. After the user approves, the browser is redirected to http://127.0.0.1:3000/callback with a code and, because this authorization server supports RFC 9207, an iss parameter, which the client compares with the issuer it recorded. The client then posts a form to the token endpoint with grant_type=authorization_code, the code, redirect_uri, client_id, code_verifier and resource=https%3A%2F%2Fmcp.example.com%2Fmcp. The response contains an access token issued for the MCP server. From then on, every POST to /mcp carries Authorization: Bearer <token> together with the transport headers from the previous section.

Step-up. Calling a write tool with the files:read token fails:

http
HTTP/1.1 403 Forbidden
WWW-Authenticate: Bearer error="insufficient_scope", scope="files:write",
                         resource_metadata="https://mcp.example.com/.well-known/oauth-protected-resource/mcp"

The client takes the union of what it already had and what the challenge names (files:read files:write, the last output line), repeats the authorization and token requests with that scope set, and retries the call. It gives up after a few attempts instead of looping.

Edge cases and limitations

Older servers and tutorials still use sessions and initialize
Servers written for revisions up to 2025-11-25 expect an `initialize` handshake and may issue an `Mcp-Session-Id`. A client that supports both eras sends a modern request first and reads the body of any `400` before falling back. A recognised modern error, such as an unsupported-version error, means the server is modern, so falling back would be wrong. On stdio the equivalent probe is `server/discover`. A client that speaks only the modern protocol cannot talk to a legacy server.
A local HTTP server is reachable from web pages
A server bound to `0.0.0.0`, or to localhost without an Origin check, can be reached by JavaScript on any page you visit, and DNS rebinding makes the browser treat the attacker's domain as your own machine. The specification's countermeasures are to validate `Origin` (answering `403` for a bad one), to bind to `127.0.0.1`, and to require authentication. If the server does not need to be shared, stdio avoids the problem because no network port exists.
A 401 and a 403 call for different client behaviour
A `401` means there is no valid token, so the client discovers the server's metadata and authorizes. A `403` with `insufficient_scope` means the token is fine but too narrow, so the client re-authorizes with the union of its old scopes and the scopes in the challenge. The specification asks clients to cap these attempts, because a server that keeps challenging would otherwise trap the client in a loop. Servers should list every scope an operation needs in one challenge to avoid repeated round trips.
A stdio-only host reaching a remote server needs a bridge
Some hosts can only start local commands. A proxy such as mcp-remote runs as a local stdio server, acts as the OAuth client on the host's behalf, and forwards messages over HTTP. It stores the tokens it obtains (its README names `~/.mcp-auth`) and processes metadata from whatever server it is pointed at, so it is one more program you must trust and keep updated. The CVE example below is a bug in exactly that role.
A client metadata document cannot prove which local program is listening
With Client ID Metadata Documents the `client_id` is a URL that proves control of a domain. It cannot prove which process listens on a `localhost` redirect URI, so an attacker can reuse a real client's URL and catch the authorization code on a local port. The authorization server must show the redirect hostname and should warn on localhost-only redirects, and users should read the consent screen instead of clicking through it.

When to use it, and when something simpler is enough

Use it when

  • Use stdio when the server needs the user's local files, shell or database, one host uses it, and you trust and can pin the code that runs.
  • Use Streamable HTTP when many users or hosts share one server, when the data lives in a hosted service, or when fixes should reach everyone without each person updating a package.
  • Use the OAuth flow when a remote server acts for a person inside a service that has its own accounts, and consent, revocation and an audit trail per user matter.

Think twice when

  • Avoid running an unreviewed, unpinned third-party stdio package with real credentials, because every update runs with your permissions.
  • Avoid putting access tokens in URLs, or API keys in configuration files that are committed to a repository.
  • Avoid exposing a local HTTP server on all network interfaces without authentication and Origin validation.

A simpler alternative. For a personal tool used by one host on one machine, a stdio server that reads one narrowly scoped credential from an environment variable is enough. Move to Streamable HTTP with OAuth when a second person or machine needs the same server, or when the credential should not live on user machines.

Key takeaways

  • A transport only decides how MCP's JSON-RPC messages travel. stdio runs the server as a subprocess of the client, and Streamable HTTP puts it behind a URL with one POST per message.
  • In revision 2026-07-28 each HTTP request is self-contained. There are no sessions or handshake, and the mirrored headers MCP-Protocol-Version, Mcp-Method and Mcp-Name must match the body.
  • For remote servers the client reads the 401 challenge, finds the authorization server through Protected Resource Metadata, runs PKCE with the resource parameter, and sends a bearer token on every request.
  • A server must accept only tokens issued for itself and must never forward a client's token upstream. Calls to other APIs use their own tokens.
  • Third-party servers are risky in different ways. A local one runs code with your permissions, and a remote one receives your data, so consent prompts, sandboxing, pinned versions and least-privilege scopes matter more than the transport.
  • Clients should treat everything a server supplies as untrusted input, including OAuth metadata URLs and tool descriptions.

Example 1 of 5

GitHub MCP Server: one integration offered over HTTP and over stdio

GitHubDocumented in an open-source project

The github/github-mcp-server repository documents the same GitHub integration in two deployment modes: a server hosted by GitHub that a host reaches by URL, and a Docker image that the host starts on the user's machine. The repository README is the cited document. [16][11][1]

The problem

People want an agent to work with repositories, issues and pull requests. The integration has to work in hosts that can open a remote connection, and also for users who prefer to run the server themselves with a credential they control. Each way of running it implies a different transport and a different way of proving who the user is.

Where this topic fits

This is the deployment choice described in this lesson. The remote mode is an http server entry, which is the Streamable HTTP transport of this lesson, authenticated with an OAuth sign-in or with a personal access token (PAT) sent in an Authorization header. The local mode uses stdio: the host launches a container, and the credential arrives through the environment or through a browser login that the server performs itself.

How it is applied, step by step

  1. In remote mode the host configuration holds only a server type of `http` and the URL, and the host's MCP client sends its POST requests to that endpoint.
  2. In a host that supports the OAuth option, the user signs in through the browser. Alternatively the configuration adds an `Authorization: Bearer` header whose value comes from a prompted input variable, so the token is not typed into the file.
  3. In local mode the host configuration holds a command, `docker run -i --rm` plus the image name. The `-i` flag keeps standard input open so the client can write messages to the container.
  4. The container receives its credential through an environment variable, or runs a browser login of its own the first time it starts.
  5. In both modes the tools act with the permissions of the signed-in user or of the PAT's scopes, so the credential decides how much harm a mistaken or manipulated tool call can do.

Why this approach fits

The same GitHub tools are available behind two bindings, so users can choose on constraints instead of features. The hosted server needs no local install and is updated by its operator, and an OAuth sign-in avoids creating and storing a long-lived token. The container keeps the process on the user's machine and under their control, which suits people who want to pin the image or cannot use a remote connection.

Limitation or tradeoff

Each mode moves risk rather than removing it. The remote mode needs a host with remote-server support, trusts the operator with whatever the model sends, and offers OAuth only where the host application has set up its own GitHub App or OAuth App; otherwise a PAT is the route. The local mode needs Docker, and a PAT in an environment variable is a long-lived credential on the user's machine. In both modes the token's permissions bound what a prompt-injected agent could do, so a token broader than the task needs is a larger danger than the choice of transport.

What the sources document

  • The README presents a remote GitHub MCP Server that GitHub hosts and a local server distributed as the Docker image ghcr.io/github/github-mcp-server. [16]
  • For the remote server the README lists a host with remote-server support, such as VS Code 1.101 or later, Claude Desktop, Cursor or Windsurf, as a prerequisite. Its configuration uses type http and the URL https://api.githubcopilot.com/mcp/, with a variant that sends a GitHub PAT as a Bearer value in an Authorization header. It adds that each host application must configure its own GitHub App or OAuth App for the OAuth option, and that any host with remote-server support should work with a PAT. [16]
  • For the local server the README says a PAT can be supplied through the GITHUB_PERSONAL_ACCESS_TOKEN environment variable, which takes precedence over OAuth, and that otherwise the official image runs a browser-based login on first use and keeps the resulting token in memory only. [16]
  • The MCP architecture overview describes a local server launched over stdio as typically serving a single client, and a remote server on Streamable HTTP as typically serving many clients. [11]
  • The specification's transports overview names stdio and Streamable HTTP as the two standard bindings and states that protocol semantics are identical on every transport. [1]

The facts above come from the cited sources. The steps and analysis in this example are our explanation of how they fit together.

Example 2 of 5

Cloudflare Workers: hosting a remote MCP server with Streamable HTTP and an OAuth provider

CloudflareDocumented in official docs

Cloudflare's Agents documentation describes how to build a remote MCP server on Workers. Its transport page covers Streamable HTTP and the handler to use, and its authorization page covers the OAuth options for signing users in. [17][18][8]

The problem

A developer who wants many people to share one MCP server has to serve a Streamable HTTP endpoint and sign users in, usually through an identity provider they already use such as GitHub or Google. The provider's own token has to stay away from MCP clients, and clients that can only start local commands still need a way to connect.

Where this topic fits

This is the server side of the OAuth flow. In the third-party case the Worker is the resource server and the authorization server as seen by MCP clients, and an OAuth client as seen by GitHub or Google. It sits between the client's 401-driven discovery and the tool handlers that act for the signed-in user.

How it is applied, step by step

  1. The Worker exports an OAuth provider whose API route is `/mcp` and whose API handler is the Streamable HTTP handler. In a typical setup, requests to `/mcp` reach the MCP handler only after the provider has checked their access token.
  2. The provider exposes `/authorize`, `/token` and `/register`, which an MCP client uses to register, send the user to sign in, and exchange the code for a token.
  3. For a third-party identity provider, the default handler you write sends the user to GitHub or Google and completes the grant when they return.
  4. The Worker then issues its own token to the MCP client instead of passing along the identity provider's token.
  5. Tool handlers read the signed-in user's identity from the authentication context and can refuse or hide tools that the user may not use.
  6. A client that supports only local servers can connect through the mcp-remote adapter, which the transport page describes as bridging local-only clients to remote servers.

Why this approach fits

Issuing its own token lets the Worker apply the rule that a server accepts only tokens issued for it. The token an MCP client holds is meaningful at this server, while the GitHub or Google token need not leave the Worker. Putting identity in a provider also lets tool handlers make per-user decisions, and Streamable HTTP lets one deployed endpoint serve many clients.

Limitation or tradeoff

The structure is the proxy pattern that the MCP security guidance warns about. When a server fronts a third-party authorization server with one static client ID and also accepts dynamic client registration, it must obtain consent for each client itself, match redirect URIs exactly and handle the state parameter correctly, or an attacker can exploit a consent cookie. A library can implement much of this, but the authorize handler you write still has to present a real consent step.

CVE-2025-6514: a hostile remote server turns OAuth metadata into code execution in mcp-remote

JFrogDocumented in an engineering article

JFrog's security research team published a write-up of CVE-2025-6514, a critical flaw in mcp-remote, the local proxy that lets stdio-only hosts reach remote MCP servers. The mcp-remote README and the MCP security guidance supply the surrounding context. [20][21][8]

The problem

mcp-remote does the OAuth client's work for a host that cannot, so it reads OAuth metadata from whatever remote server it is configured with. If that server is hostile, or the connection can be altered on the network, the metadata is attacker-controlled input to a program running on the user's machine.

Where this topic fits

This is the discovery step of the authorization flow. The client takes the authorization_endpoint from server-supplied metadata and opens it in a browser, and that step turns untrusted data from the network into an action on the local machine.

How it is applied, step by step

  1. A stdio-only host is configured to start mcp-remote with the URL of a remote MCP server, as the README shows.
  2. When the server requires sign-in, mcp-remote begins the OAuth flow and reads the server's OAuth metadata.
  3. A hostile server puts a crafted string in the `authorization_endpoint` field instead of a web address.
  4. mcp-remote passes the string to the function that opens URLs through the operating system. JFrog reports that on Windows this ran arbitrary commands, and on macOS and Linux it ran arbitrary executables with limited control over their arguments.
  5. JFrog describes two ways to reach the bug: connecting to an untrusted server, or connecting over plain HTTP, where an attacker on the same network can substitute the response.
  6. The fix shipped in version 0.1.16, and JFrog advises connecting only to trusted servers over HTTPS.

Why this approach fits

The example shows that authorization is not only a server concern. The client consumes URLs and fields chosen by the server, so each one must be validated before it triggers a request or starts a program. The guidance addresses this class of bug directly: allow only http and https, accept http only for loopback, reject schemes such as javascript:, data: and file:, and never open URLs through a shell.

Limitation or tradeoff

A scheme check is necessary but not sufficient. A well-formed https URL can still point at an internal address, which is the SSRF risk the guidance describes, and DNS can change between the check and the request. A proxy also adds a second place where tokens are stored and where metadata is parsed, so using one widens the set of programs you must keep patched.

What the sources document

  1. A publisher uploads a package named after the legitimate email service's MCP server, with code copied from the real one, as reported.
  2. Users add it to their host as a command to run and give it their email API credential, which is the usual setup for a local server.

4Common mistakes

  1. Printing debug output to standard output in a stdio server.

    Why it causes problems
    On stdio the server's standard output carries the protocol, and the specification forbids writing anything to it that is not a valid MCP message. A stray print statement corrupts the stream, so the client sees a parse error or a hung connection, often with no helpful message.
    How to recognise it
    The server works when you run it by hand, but the host reports a malformed message, disconnects at once or shows no tools. Run it in a terminal and look for text on stdout that is not a JSON object.
    How to fix it
    Send every log line to standard error, which the client may capture, forward or ignore. Configure the logging library with a stderr handler instead of using print, and flush after each protocol message.

  2. Accepting any valid-looking token, or forwarding the client's token to an upstream API.

    Why it causes problems
    A token issued for another service gets accepted, which breaks the audience boundary. Forwarding it lets the downstream API trust a credential it did not issue to the MCP server, bypasses controls such as rate limits, muddles audit logs, and turns the server into a proxy for stolen tokens.
    How to recognise it
    Tokens validate even though their audience names another service, or the upstream API's logs show requests under the user's identity with no trace of the MCP server that actually made them.
    How to fix it
    Compare the audience or resource of every token with the server's own canonical URI and answer anything else with 401. For upstream calls, act as an OAuth client of that API and use a separate token issued to the MCP server.

  3. Putting tokens in URLs or in configuration files that are committed to a repository.

    Why it causes problems
    The specification forbids access tokens in the URI query string because URLs are logged by proxies, browsers and servers. A key committed to a shared file reaches everyone with repository access and stays in the history after you delete it.
    How to recognise it
    Search configuration files and logs for `access_token=`, `key=` and long literal strings, and search the repository history as well as the working tree.
    How to fix it
    Send tokens in the Authorization header. Reference secrets through environment variables or the host's input prompts, prefer OAuth when the server offers it, and rotate any credential that has been committed.

  4. Requesting every scope up front or publishing a catch-all scope.

    Why it causes problems
    A stolen broad token exposes the whole surface, revoking it breaks every workflow, and users who see a long list of permissions decline. The MCP security guidance lists wildcard and omnibus scopes among the common mistakes.
    How to recognise it
    Tokens carry scopes such as `*`, `all` or `admin:*`, every challenge returns the full scope catalogue, or consent screens list permissions that no tool uses.
    How to fix it
    Publish a small `scopes_supported` covering basic functionality, challenge for the scopes each operation needs through `WWW-Authenticate`, and let clients add scopes through step-up with a cap on retries.

  5. Treating possession of a handle, or an open connection, as proof of identity.

    Why it causes problems
    Revision 2026-07-28 has no protocol sessions, so servers that keep state mint handles, such as a cart ID, that come back as tool arguments. If the server trusts whoever presents a handle, anyone who guesses or obtains one can read or change another user's state.
    How to recognise it
    A tool call with another user's handle succeeds, handles are short or sequential, or stored state is keyed by the handle alone.
    How to fix it
    Authorize every request, key stored state by the authenticated user together with the handle (taking the user ID from the verified token), use unguessable random handles, and let them expire.

  6. Installing a third-party stdio server with real credentials and no review.

    Why it causes problems
    The package runs with your permissions and receives the credential you give it, and every later version runs the same way. The postmark-mcp incident shows a later release quietly copying mail to its publisher.
    How to recognise it
    A configuration that runs `npx -y package@latest`, a publisher you cannot match to the vendor's own documentation, or a credential that allows far more than the server's tools need.
    How to fix it
    Confirm the publisher in the vendor's documentation, pin a version you have reviewed, give the server a narrow and rotatable credential, run it in a sandbox where the host supports one, and prefer an official remote server with OAuth.

Exercise 1

Write and test a Streamable HTTP request validator

CodingIntermediateAbout 45 min (estimate)

Streamable HTTP in revision 2026-07-28 mirrors a few body fields into headers, and the server must reject a request when they disagree. Write validator.py with a function check_request(headers, body, allowed_origins) that returns (http_status, jsonrpc_error_code_or_None) for one POST to the MCP endpoint. Use only the Python standard library.

Rules to implement (from the Streamable HTTP page): an Origin header that is present but not allowed gives 403. The MCP-Protocol-Version header must exist and equal _meta["io.modelcontextprotocol/protocolVersion"] in the body, otherwise 400 with error -32020 (HeaderMismatch). If the version is not supported (only 2026-07-28 is) the answer is 400 with -32022. Mcp-Method must equal the body's method. For tools/call, prompts/get and resources/read, Mcp-Name must equal params.name (or params.uri for resources/read); a value of the form =?base64?...?= is Base64 of the UTF-8 text and must be decoded before comparing. Header names are case-insensitive.

Save this as tests_ex1.py next to your file and run python3 tests_ex1.py. Every line should print PASS.

python
VERSION_KEY = "io.modelcontextprotocol/protocolVersion"
ORIGINS = {"http://localhost:3000"}


def body(method="tools/call", name="get_weather", version="2026-07-28"):
    params = {"name": name, "arguments": {}, "_meta": {VERSION_KEY: version}}
    return {"jsonrpc": "2.0", "id": 1, "method": method, "params": params}


def headers(name="get_weather", version="2026-07-28", **extra):
    base = {"MCP-Protocol-Version": version, "Mcp-Method": "tools/call", "Mcp-Name": name}
    return {**base, **extra}


CASES = [
    ("valid call", headers(), body(), (200, None)),
    ("header names ignore case", {k.lower(): v for k, v in headers().items()}, body(), (200, None)),
    ("tool name differs", headers("other_tool"), body(), (400, -32020)),
    ("Mcp-Method missing", {k: v for k, v in headers().items() if k != "Mcp-Method"}, body(), (400, -32020)),
    ("origin not allowed", headers(Origin="https://evil.example"), body(), (403, None)),
    ("origin allowed", headers(Origin="http://localhost:3000"), body(), (200, None)),
    ("base64 name", headers("=?base64?SGVsbG8sIOS4lueVjA==?="), body(name="Hello, 世界"), (200, None)),
    ("unsupported version", headers(version="1900-01-01"), body(version="1900-01-01"), (400, -32022)),
    ("version header differs from body", headers(version="2025-11-25"), body(), (400, -32020)),
]

if __name__ == "__main__":
    from validator import check_request
    failed = 0
    for label, hdrs, msg, expected in CASES:
        got = check_request(hdrs, msg, ORIGINS)
        failed += got != expected
        print("PASS" if got == expected else "FAIL", label, got)
    raise SystemExit(failed)

Requirements

  • Return 403 for a present but disallowed Origin header, before any other check.
  • Return 400 with -32020 when MCP-Protocol-Version is missing or differs from the version in the body, and 400 with -32022 when the matching version is unsupported.
  • Compare Mcp-Method with the body's method, and Mcp-Name with params.name or params.uri, decoding the Base64 sentinel form first.
  • Treat header names as case-insensitive and header values as case-sensitive, and use only the standard library.

Expected behaviour

All nine cases in the test file print PASS and the script exits with status 0. Changing any single header in a valid request to a different value produces a 400 with -32020, except an Origin outside the allowed set, which produces 403.

Hint 1

Lower-case the header names once at the start, into a new dictionary, so every later lookup is case-insensitive.

Hint 2

The Base64 sentinel is the literal prefix `=?base64?` and suffix `?=`. Strip both, decode the middle with `base64.b64decode`, then decode the bytes as UTF-8.

Hint 3

Decide the order of checks first. The Origin check comes first because it does not depend on the body at all.

Show solution

One possible validator.py. The order of checks matters: origin first, then the version header against the body, then support for that version, then the method, then the name.

python
import base64

VERSION_KEY = "io.modelcontextprotocol/protocolVersion"
SUPPORTED_VERSIONS = {"2026-07-28"}
HEADER_MISMATCH = -32020
UNSUPPORTED_VERSION = -32022
NAMED_METHODS = {"tools/call", "prompts/get", "resources/read"}


def decode_header_value(value: str) -> str:
    """Undo the =?base64?...?= sentinel encoding used for non-ASCII header values."""
    if value.startswith("=?base64?") and value.endswith("?="):
        return base64.b64decode(value[len("=?base64?"):-len("?=")]).decode("utf-8")
    return value


def check_request(headers: dict, body: dict, allowed_origins: set) -> tuple:
    """Return (HTTP status, JSON-RPC error code or None) for one POST to the MCP endpoint."""
    h = {name.lower(): value for name, value in headers.items()}
    if "origin" in h and h["origin"] not in allowed_origins:
        return 403, None
    params = body.get("params", {})
    version = h.get("mcp-protocol-version")
    if version is None or version != params.get("_meta", {}).get(VERSION_KEY):
        return 400, HEADER_MISMATCH
    if version not in SUPPORTED_VERSIONS:
        return 400, UNSUPPORTED_VERSION
    if h.get("mcp-method") != body.get("method"):
        return 400, HEADER_MISMATCH
    if body["method"] in NAMED_METHODS:
        expected = params.get("uri") if body["method"] == "resources/read" else params.get("name")
        try:
            actual = decode_header_value(h.get("mcp-name", ""))
        except ValueError:                      # bad base64 or bad UTF-8
            return 400, HEADER_MISMATCH
        if "mcp-name" not in h or actual != expected:
            return 400, HEADER_MISMATCH
    return 200, None

Reviewing again at each version bump and rotating credentials are part of the answer.

Check your answer

  • Did you find all seven findings in the table, including the three separate problems with the notes server?
  • Does your rewritten file contain any literal key, token or query-string credential?
  • Did you say what would still be risky after your fixes instead of declaring the file safe?
