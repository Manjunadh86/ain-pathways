Data Collection and Cleaning

Data collection is gathering the raw records a model will learn from, out of files, databases and web APIs. Data cleaning is finding what is wrong with those records (missing values, duplicates, wrong types, suspicious extremes), fixing or flagging each problem, and writing down every decision.

1Overview

Why it matters

A model treats every cell it is given as a fact. An identifier read as a number loses its leading zeros. A blank and a -1 both mean "not recorded", but only the blank is counted as missing. A customer who appears twice counts double. One mistyped measurement drags an average far from the typical row. None of these raises an error: the code runs, the chart is drawn, the model trains, and the result is wrong in a way nobody sees until a prediction is checked against reality.

The step also decides what a result can claim. Dropping every incomplete row, filling gaps with a median and keeping or removing an extreme value are choices, and different choices produce different models from the same raw file. Anyone who trains, evaluates or signs off a model needs to be able to say where the data came from, what was changed and why. That is only possible when collection and cleaning are done by a script with a written record, not by hand in a spreadsheet.

Key terms

Schema
The list of a table's columns together with the data type each column holds, such as text, whole number or date.
Type inference
A loader guessing each column's type from the text it reads. It is convenient and sometimes wrong, for example when an identifier looks like a number.
Missing value
A cell with no recorded value. pandas shows it as NaN, NaT or <NA> depending on the column's type.
Sentinel value
An ordinary-looking value such as -1, 9999 or "unknown" that a system uses as a code for "not recorded". Software does not treat it as missing until you tell it to.
Imputation
Filling a missing cell with an estimate, such as the median of the column, so that the rest of the row can still be used.
Key
The column, or combination of columns, whose value should identify one row and appear only once, such as an order number.
Duplicate
A row that repeats another. An exact duplicate matches in every column; a key duplicate shares the key but differs elsewhere.
Outlier
A value that lies far from the other values in its column. It can be a recording error, a rare real case or a sign that two different kinds of thing were mixed.
Interquartile range (IQR)
The distance between the first quartile (25 % of values lie below it) and the third quartile (75 % lie below it). It measures spread without being moved by extremes.
Cleaning log
A record with one line per cleaning rule that states what the rule did, how many rows or cells it affected and why it was applied.

2Explanation

Introduction

You have probably inherited a spreadsheet from someone else: a column where most cells hold numbers and a few say "n/a", dates typed three different ways, the same customer entered twice. Before you could add anything up you had to tidy it. Data collection and cleaning is that job done deliberately: get the records out of wherever they live, find what is wrong with them, fix or mark each problem, and keep a note of what you did.

A model cannot do this for itself. Take a file of twelve rental listings, used in the worked example below. Loaded with pandas' default settings it reports 2 missing cells. There are really 4, because one rent says unknown and one floor area is -1, the export's code for "not recorded". Two listings appear twice. Two cities are spelled four ways. One flat claims 640 m². Nothing raises an error. The average floor area simply comes out at 117 m², when the typical flat in the file is about 60 m².

The work has two halves. Collection is getting the data out of its source: a CSV or JSON file, a Parquet file, a SQL or document database, or a web API. Each source keeps a different amount of information about what its columns mean, and that decides how much your loader has to guess. Cleaning deals with four problems that turn up in almost every table: missing values, duplicates, inconsistent types (numbers stored as text, dates in several formats, one category spelled several ways) and outliers, values far from the rest that may be errors or may be the most interesting rows you have.

A fifth part is easy to skip: writing the decisions down. Dropping a row and filling a gap are choices, and someone, often you three months later, will need to know which were made. This lesson uses pandas from the Python data stack. Its output feeds exploratory data analysis and feature engineering. Moving data between systems on a schedule is the subject of data pipelines and ETL.

How it works

What each source remembers

A table has a schema: its column names and the type of each column. Sources differ in how much of the schema they carry, and whatever is not carried has to be guessed by the loader.

CSV carries the least. RFC 4180 (opens in a new tab), an informational memo and not a standard, describes records, commas, double quotes and an optional header line. It defines no data types and no way to say "missing". Parquet sits at the other end. Its file layout (opens in a new tab) keeps each column's values together and ends with metadata that a reader consults first, so a reader can fetch only the columns it needs, and the column types travel with the file. A SQL table declares its types up front. A document database such as MongoDB does not have to: its manual (opens in a new tab) says documents in one collection need not share the same fields, and one field may hold different types in different documents. Web APIs return JSON a page at a time. GitHub's REST API, for example, returns 30 items per page by default (opens in a new tab) and puts the address of the next page in a link header.

Missing values

pandas marks a missing cell as NaN, as NaT in date columns or as <NA> in nullable types such as Int64. Its missing data guide (opens in a new tab) gives three rules worth memorising. NaN is not equal to itself, so test with isna(), never with ==. Sums and means skip missing cells without saying so. An integer column with a gap silently becomes float64 unless you ask for Int64.

pandas only recognises the markers it knows. A sentinel value such as -1 or 9999 stays an ordinary number until you convert it, for example with df["area_sqm"].mask(df["area_sqm"] < 0). Then choose a remedy by asking why the value is missing:

A feature is missing in a few rows, with no patternImpute the median (numbers) or most frequent value (categories)Keeps the rest of the row

A column is mostly emptyDrop the columnThe filled values would be mostly invention
Short gaps in time-ordered readingsForward-fill or interpolate, with a limitNeighbouring readings are informative

scikit-learn's imputation guide (opens in a new tab) covers SimpleImputer and its add_indicator option. Whatever you fill with must be learned from training rows only, a point developed in train/test splits and cross-validation.

Duplicates

An exact duplicate matches another row in every column; df.drop_duplicates() removes it. A key duplicate shares an identifier but differs elsewhere, like a listing scraped again a week later at a new price. Sort so that the row you want comes last, then call drop_duplicates(subset="listing_id", keep="last") (opens in a new tab). Normalise text first, because "lisbon " and "Lisbon" are different strings. If a table has no key, two identical rows may be two real events, and removing one destroys data.

Inconsistent types

  • Numbers stored as text. pd.to_numeric(col, errors="coerce") turns anything unreadable into NaN. Compare isna().sum() before and after to see what the conversion cost. Keep the default errors="raise" when no failure is acceptable.
  • Dates. Pass an explicit format. The to_datetime reference (opens in a new tab) calls format="mixed" risky, and the worked example shows why.
  • Categories. Strip spaces, fix the case, map synonyms to one spelling, then recheck value_counts().
  • Identifiers. A postcode, account number or product code is text. Read as a number, 02134 becomes 2134.
  • Units. One column, one unit. Convert grams to kilograms or Fahrenheit to Celsius before combining sources.

Outliers

The NIST handbook defines (opens in a new tab) an outlier as an observation that appears to deviate markedly from the others, and notes that it may be bad data, random variation or something scientifically interesting. So the work has two steps: a rule nominates values, then a person judges them. The box-plot rule (opens in a new tab) uses the quartiles:

IQR=Q3−Q1,lower fence=Q1−1.5 IQR,upper fence=Q3+1.5 IQR\text{IQR} = Q_3 - Q_1, \qquad \text{lower fence} = Q_1 - 1.5\,\text{IQR}, \qquad \text{upper fence} = Q_3 + 1.5\,\text{IQR}IQR=Q3​−Q1​,lower fence=Q1​−1.5IQR,upper fence=Q3​+1.5IQR

Tools compute quartiles in slightly different ways. This lesson uses the pandas default, which interpolates linearly between the ordered values; NIST's worked example instead takes the 0.25(N+1)th and 0.75(N+1)th ordered points, so fences can differ a little from tool to tool.

Quartiles ignore how far away the extremes are, so making a wild value wilder does not move the fences. The z-score, z=(x−xˉ)/sz = (x - \bar{x})/sz=(x−xˉ)/s, lacks that protection, because the outlier inflates the standard deviation sss it is measured with. NIST gives the consequence: in a sample of nnn values no z-score can exceed (n−1)/n(n-1)/\sqrt{n}(n−1)/n​. That bound is below 3 for every nnn up to 10.

A robust alternative from the same page is the modified z-score, M=0.6745 (x−x~)/MADM = 0.6745\,(x - \tilde{x})/\text{MAD}M=0.6745(x−x~)/MAD, where x~\tilde{x}x~ is the median and MAD is the median of the absolute deviations from it. Values with ∣M∣>3.5|M| > 3.5∣M∣>3.5 are potential outliers. Then judge each flagged value:

  • An error (impossible, or contradicted by other columns): correct it from the source if you can, otherwise set it to missing.
  • Real but extreme: keep it. Rare real cases are often what the model most needs to see.
  • A different population (a warehouse in a table of flats): filter it out and say so.

Write down every decision

Keep the raw file untouched and put every change in a script. Have the script build a cleaning log with one line per rule: what it did, how many rows or cells it affected, and why. Datasheets for Datasets (opens in a new tab) proposes that every dataset ship with answers to a fixed list of questions. Three of them make a good minimum for your own table: was any cleaning done (the paper names removal of instances and processing of missing values), was the raw data saved, and is the software that did the cleaning available?

Step 2: clean with a script that keeps a log

python
import pandas as pd

raw = pd.read_csv("rentals.csv", dtype=str, keep_default_na=False)   # every cell stays text
log = [("load as text", len(raw), "nothing interpreted yet")]

# Types: known missing-value codes first, then explicit conversions
text = raw.replace(["", "N/A", "unknown"], pd.NA)
iso = pd.to_datetime(text["listed_on"], format="%Y-%m-%d", errors="coerce")
day_first = pd.to_datetime(text["listed_on"], format="%d/%m/%Y", errors="coerce")
df = text.assign(
    city=text["city"].str.strip().str.title(),
    area_sqm=pd.to_numeric(text["area_sqm"], errors="coerce"),
    bedrooms=pd.to_numeric(text["bedrooms"], errors="coerce").astype("Int64"),
    rent_eur=pd.to_numeric(text["rent_eur"].str.replace(",", ""), errors="coerce"),
    listed_on=iso.fillna(day_first),
)
lost = int((df.isna().sum() - text.isna().sum()).sum())
log.append(("convert types", len(df), f"{lost} cells failed to convert"))

# Sentinel: -1 is this export's code for "area not recorded"
df = df.assign(area_sqm=df["area_sqm"].mask(df["area_sqm"] < 0))

# Duplicates: identical rows, then one row per listing (the most recent)
df = df.drop_duplicates()
log.append(("drop identical rows", len(df), "L003 was exported twice"))
df = df.sort_values("listed_on").drop_duplicates(subset="listing_id", keep="last")
log.append(("keep latest row per listing_id", len(df), "L002 was re-listed on 9 March"))

# Outliers: nominate with the 1.5 x IQR rule, then judge with a second column
q1, q3 = df["area_sqm"].quantile([0.25, 0.75])
upper = q3 + 1.5 * (q3 - q1)
flagged = df.loc[df["area_sqm"] > upper, ["listing_id", "area_sqm", "rent_eur"]]
print(f"Q1 = {q1}, Q3 = {q3}, upper fence = {upper}")
print(flagged.assign(eur_per_sqm=(flagged["rent_eur"] / flagged["area_sqm"]).round(1)).to_string(index=False))
df = df.assign(area_sqm=df["area_sqm"].mask(df["listing_id"] == "L007"))
log.append(("set L007 area to missing", len(df), "2.6 EUR per m2 is not credible; L008 kept"))

# Missing values: a row without the target is dropped; features are imputed and marked
df = df.dropna(subset=["rent_eur"])
log.append(("drop rows without rent", len(df), "rent is the target"))
area_median, bedrooms_median = df["area_sqm"].median(), int(df["bedrooms"].median())
df = df.assign(
    area_was_missing=df["area_sqm"].isna(),
    area_sqm=df["area_sqm"].fillna(area_median),
    bedrooms=df["bedrooms"].fillna(bedrooms_median),
)
log.append(("impute area and bedrooms", len(df), f"medians {area_median} and {bedrooms_median}"))

print(df.sort_values("listing_id").to_string(index=False))
print(pd.DataFrame(log, columns=["step", "rows", "note"]).to_string(index=False))

Edge cases and limitations

A missing-value marker that is real data
By default read_csv treats strings such as NA, N/A, NULL, None and the empty string as missing. That is wrong when the text is a real value: NA is the country code for Namibia, and None can be a genuine answer in a column such as heating type. Reading a two-row file with the codes NA and NO gives one missing country. Pass keep_default_na=False together with an explicit na_values list for columns where these strings can be real, and check isna().sum() against what you expect.
Dates that parse without error and are wrong
03/04/2026 is 4 March in the United States and 3 April in most of Europe. pandas reads it as 4 March unless told otherwise, and nothing can detect the mistake when the day is 12 or lower. A column that mixes sources may mix both conventions. Parse each source with its own explicit format, and afterwards check that the earliest and latest dates fall inside the period the data is supposed to cover.
Whole numbers that turn into decimals
NumPy integers cannot hold a missing value, so an integer column with one gap is read as float64 and order number 1001 becomes 1001.0. Written back to a file or joined to another table, it no longer matches the original 1001. Read identifiers as text, and use the nullable Int64 type for real integer quantities that have gaps.
Containers with a fixed capacity
Some tools between the source and your table hold a fixed number of rows. Microsoft documents a worksheet limit of 1,048,576 rows by 16,384 columns for current Excel versions, and a file with more rows than that cannot be held in one sheet. Rows lost this way look like nothing at all, because every row that did arrive is valid. Only comparing the record count at the source with the count after loading reveals the loss.
The 1.5 × IQR rule on skewed data
Incomes, prices, durations and counts have long right tails. On such columns the upper fence flags a steady share of perfectly real rows, and the lower fence can fall below zero and flag nothing. Apply the rule to the logarithm of the values, or replace it with limits from the domain (a trip cannot last minus five minutes or thirty days), and always look at what was flagged before acting.
Identical rows that are separate events
Two rows showing the same customer, product, amount and minute may be a double export or two real purchases. Without a key such as a transaction number the data cannot tell you, and drop_duplicates will silently delete real sales. Ask the source for a key. If none exists, keep the rows and record the uncertainty in the log.

When to use it, and when something simpler is enough

Use it when

  • Data arrives from outside your own code, such as an export, a vendor file, a scrape or an API response, and you are about to compute a statistic or train a model on it.
  • You are combining sources that name, type or code the same things differently, such as two systems with different date formats or units.
  • The table will be rebuilt later, for retraining or a monthly report, so the cleaning has to be a script that gives the same result each time.
  • A metric looks too good, a chart has an odd spike or a model behaves strangely, and you need to rule out the data before blaming the model.

Think twice when

  • Do not remove rows because they are inconvenient for the model. In fraud, fault and safety data the rare extreme rows are the signal, and finding them is the subject of anomaly detection.
  • Do not compute fill values or outlier limits on the full dataset before splitting it. Statistics that include test rows make the test score optimistic.
  • Do not edit cells by hand in a spreadsheet when the data will be loaded again. The edits cannot be repeated or reviewed, and the spreadsheet may change types as it saves.

A simpler alternative. For a one-off table of a few hundred rows, read it as text, convert the columns you need, remove exact duplicates, drop the rows that have a gap in a column you use, and note the row count before and after. That stops being enough when the dropped rows exceed a few percent of the table, when the gaps are concentrated in one group of rows, when more than one source is involved, or when the data will be refreshed.

Key takeaways

  • Sources differ in how much they remember. CSV carries no types and no marker for missing, so every type is the loader's guess, while Parquet files and SQL tables carry their types with them.
  • Read doubtful data as text, profile it (rows, types, missing cells, duplicate keys, ranges), then convert explicitly and count every value that fails to convert.
  • A missing value needs a reason before a remedy. Drop rows that lack the target, impute features with a value learned from training rows, and add an indicator when being missing may be informative.
  • Deduplicate on a key you can defend, after normalising text, and choose on purpose which copy survives.
  • A rule such as 1.5 × IQR only nominates values for review. Whether a flagged value is an error or a real extreme is decided with other columns and knowledge of the subject.
  • Keep the raw data untouched and do all cleaning in a script that writes a log, so every removed row and changed cell has a recorded rule and reason.

Example 1 of 5

NOAA GHCN-Daily: weather observations flagged by quality checks, not deleted

NOAA National Centers for Environmental InformationDocumented in official docs

The Global Historical Climatology Network daily (GHCNd) is NOAA's integrated database of daily weather observations from land stations. Its product page describes how sources are merged and checked, and its readme (version 3.35) documents the file layout, the missing-value code and the quality flags. [17][18]

The problem

Daily observations reach NOAA from many separate source datasets, and the same station can appear in more than one of them. Individual values can be duplicated, internally inconsistent, out of line with neighbouring stations or physically impossible. Users need one record per station and day, and they need to know which values failed a check, without the archive discarding anything that might later turn out to be right.

Where this topic fits

Every part of this lesson appears in one production system. Collection is the merge of many sources with a rule for which source wins. Missing values have one documented code. Duplicates and outliers are found by automated checks. The decisions are documented twice: per value, in a quality flag stored beside it, and for the whole dataset, in the readme.

How it is applied, step by step

  1. Merge the sources. When one station and day is available from more than one source, keep the observation from the most preferred source. This is a key-based duplicate rule with a published priority order.
  2. Store each station, month and element (such as TMAX or PRCP) as one fixed-width record with 31 daily slots. A day that was not observed, or that does not exist in a short month, holds -9999.
  3. Run the automated quality checks. A value that fails one keeps its place in the file and receives a one-letter code in its quality flag, for example D for the duplicate check or O for the climatological outlier check.
  4. Rebuild the whole dataset on a schedule, so that corrections in a source and improvements to the checks reach every record and not only new ones.
  5. Leave the decision to the user. An analyst reading the files converts -9999 to missing, applies the documented units (temperatures are stored in tenths of a degree Celsius) and usually keeps only values whose quality flag is blank.

Why this approach fits

A flag keeps the cleaning decision reversible. The archive records that a value failed a named check and leaves the value in place, so a user studying heat records can inspect the flagged extremes while a user computing monthly means can exclude them. With values numbering in the billions, checks have to be automatic, and publishing how often they are wrong lets each user judge whether a blank flag is good enough for their purpose.

Limitation or tradeoff

4Common mistakes

  1. Letting the loader guess every column's type and never looking at the result.

    Why it causes problems
    Identifiers lose their leading zeros or become floats, and a numeric column containing one stray word is loaded as text. Joins on the damaged identifier then match nothing, and arithmetic on the text column either fails or is skipped.
    How to recognise it
    Print df.dtypes straight after loading. An identifier shown as int64 or float64, or a quantity shown as str or object, means the guess was wrong.
    How to fix it
    Pass dtype for the identifier columns when loading. Convert the other columns with to_numeric and to_datetime, and compare the missing-cell counts before and after each conversion.

  2. Leaving sentinel codes such as -1, 0, 999 or 9999 in a numeric column.

    Why it causes problems
    The code is averaged in with real measurements. A single -9999 in thirty temperature readings near 15 degrees pulls their mean down to about -319, and a model will treat the code as a real, very extreme value.
    How to recognise it
    describe() shows a minimum or maximum that is impossible for the quantity, and value_counts() shows a spike at one suspiciously round number.
    How to fix it
    Read the source's documentation for its missing-value codes and convert them to missing with mask or replace before computing any statistic. Record each code in the cleaning log.

  3. Calling dropna() on the whole table to get rid of missing values.

    Why it causes problems
    A row is removed if any column has a gap, including columns the analysis never uses. The rows that survive can be a biased subset, for example only the customers who filled in every optional field.
    How to recognise it
    Compare len(df) before and after. A loss of more than a few percent, or one concentrated in a single group of rows, needs an explanation.
    How to fix it
    Use dropna(subset=[...]) with only the columns that must be present, such as the target. Impute or flag the remaining gaps and log how many rows each rule removed.

  4. Computing fill values or outlier limits on all rows before the train/test split.

    Why it causes problems
    The median or the fences then contain information from the test rows, so the test score overstates how well the model will do on data it has never seen.
    How to recognise it
    In the notebook the fillna or imputer call appears above the split, or an imputer is fitted on the full feature table.
    How to fix it
    Split first. Learn the fill values from the training rows only, most easily by placing a SimpleImputer inside a scikit-learn Pipeline, and apply the fitted values to the test rows.

  5. Deleting every value a z-score or IQR rule flags without looking at it.

    Why it causes problems
    Rare real cases are removed along with the errors: the large flat, the fraud case, the equipment fault. The model then never sees the rows it most needs, and summary statistics look calmer than the world is.
    How to recognise it
    The cleaning script filters on an outlier rule and never prints or counts what it removed, and nobody can say how many rows the rule dropped or what they were.
    How to fix it
    Add a true/false flag column, print the flagged rows, and check them against other columns. Set confirmed errors to missing, keep real extremes, and summarise the flagged rows by group and date.

  6. Fixing values by hand in a spreadsheet and saving over the raw file.

    Why it causes problems
    The edits cannot be repeated when next month's file arrives or reviewed by anyone else, and the spreadsheet may convert identifiers and dates as it saves. The original evidence of what the source sent is gone.
    How to recognise it
    There is no script that turns the raw file into the cleaned one, or the raw file's modification date is later than the date it was received.
    How to fix it
    Store raw files read-only. Make every change in a script that is kept under version control and writes a cleaning log, so the cleaned table can be rebuilt from the raw data at any time.

import io
import pandas as pd

raw = pd.read_csv(io.StringIO(CSV_TEXT), dtype=str, keep_default_na=False)

# 1. Types and missing-value codes. to_numeric raises if an unexpected token appears.
temp = pd.to_numeric(raw["temp"].replace(["ERR", "-9999"], pd.NA))
df = raw.assign(
    timestamp=pd.to_datetime(raw["timestamp"], format="%Y-%m-%d %H:%M"),
    unit=raw["unit"].str.upper(),
    temp=temp,
)
log.append(("ERR and -9999 to missing", len(df), int(df["temp"].isna().sum())))

# 2. One unit per column
is_f = df["unit"] == "F"
celsius = df["temp"].where(~is_f, (df["temp"] - 32) * 5 / 9).round(2)
df = df.assign(temp_c=celsius).drop(columns=["temp", "unit"])
log.append(("Fahrenheit to Celsius", len(df), int(is_f.sum())))

# 3. Duplicates on the key
before = len(df)
df = df.drop_duplicates(subset=["sensor_id", "timestamp"], keep="first")
log.append(("one row per sensor and hour", len(df), before - len(df)))

# 4. Outliers: flag, look, then set to missing
q1, q3 = df["temp_c"].quantile([0.25, 0.75])
low, high = q1 - 1.5 * (q3 - q1), q3 + 1.5 * (q3 - q1)
suspect = (df["temp_c"] < low) | (df["temp_c"] > high)
print(f"Q1 = {q1:.2f}, Q3 = {q3:.2f}, fences = ({low:.2f}, {high:.2f})")
print(df.loc[suspect, ["timestamp", "temp_c"]].to_string(index=False))
df = df.assign(temp_c=df["temp_c"].mask(suspect))
log.append(("outliers to missing", len(df), int(suspect.sum())))

# 5. Fill one-hour gaps from the neighbouring readings and mark them
df = df.sort_values("timestamp")
df = df.assign(
    was_imputed=df["temp_c"].isna(),
    temp_c=df["temp_c"].interpolate(limit=1, limit_area="inside").round(2),
)
log.append(("interpolate one-hour gaps", len(df), int(df["was_imputed"].sum())))

print(df.to_string(index=False))

  2. Make total a float, email trimmed and lower-case, and created_at a UTC datetime.
  3. Remove the order that the export repeated.
  4. Load the customers with pd.read_sql_query and attach country to each order without losing any order.
  5. Print revenue per country and a quality report with the number of rows loaded, duplicates removed, missing totals, missing emails and the orders whose customer is not in the database.

Requirements

  • Flatten the nested customer object with pd.json_normalize, not by hand-written loops over the keys.
  • Convert total without errors="coerce", so that an unreadable amount stops the script.
  • Deduplicate on order_id.
  • Use a left join with validate="many_to_one" and indicator=True, so that a duplicated customer id raises an error and unmatched orders can be listed.
  • Keep orders with a missing total or an unknown customer in the table and count them in the report.

Expected behaviour

The flattened table has the columns order_id, total, created_at, customer.id and customer.email, and total holds five strings, one integer and one None. After cleaning there are six orders. Revenue is 1370.0 for ES from two orders and 64.9 for PT from two orders with a known total, and one order of 60.5 has no country. The report shows 7 rows loaded, 1 duplicate removed, 1 missing total (A-1004), 1 missing email (A-1003) and one order without a customer record (A-1006).

Hint 1

json.loads on each line gives a list of dictionaries, which is the input json_normalize expects.

Hint 2

The total column mixes strings, an integer and None. Converting it to the pandas string type with astype first gives every value the same type, after which str.replace can remove the thousands separator.

Hint 3

After a merge with indicator=True, the _merge column says left_only for rows that found no partner.

Hint 4

groupby drops missing keys unless you pass dropna=False.

Show solution

Continuing from the starter code in the prompt:

python
# 1. Collect: one JSON object per line; nested keys become dotted column names
records = [json.loads(line) for line in ORDERS_JSONL.splitlines()]
orders = pd.json_normalize(records)
print(list(orders.columns))
print(orders["total"].map(lambda value: type(value).__name__).value_counts().to_dict())

# 2. Types
total_text = orders["total"].astype("string").str.replace(",", "")
clean = (
    orders.assign(
        total=pd.to_numeric(total_text).astype("float64"),
        email=orders["customer.email"].str.strip().str.lower(),
        created_at=pd.to_datetime(orders["created_at"], utc=True),
    )
    .drop(columns=["customer.email"])
    .rename(columns={"customer.id": "customer_id"})
)

# 3. Duplicates
rows_loaded = len(clean)
clean = clean.drop_duplicates(subset="order_id", keep="first")

# 4. Second source: SQL, joined with checks on the key
customers = pd.read_sql_query("SELECT id AS customer_id, country FROM customers", con)
joined = clean.merge(customers, on="customer_id", how="left",
                     validate="many_to_one", indicator=True)
unmatched = joined.loc[joined["_merge"] == "left_only", "order_id"].tolist()
joined = joined.drop(columns="_merge")

# 5. Result and quality report
print(joined.to_string(index=False))
print(joined.groupby("country", dropna=False)["total"].agg(["count", "sum"]))
print({
    "rows_loaded": rows_loaded,
    "duplicates_removed": rows_loaded - len(clean),
    "missing_total": int(joined["total"].isna().sum()),
    "missing_email": int(joined["email"].isna().sum()),
    "orders_without_customer_record": unmatched,
})

Each source brought its own problem. The JSON kept the nesting but not the types: total arrived as text, as a number and as null, and one customer object had no email key at all, which json_normalize turned into a missing cell. The SQL table had clean types but did not contain customer 31. A left join keeps that order, and the _merge column makes the gap visible. An inner join would have dropped A-1006 and its 60.5 of revenue without a trace. validate="many_to_one" guards the other direction: if the customers table ever held an id twice, the join would duplicate orders, and this argument raises an error instead.

Nothing was imputed. A missing total is not filled, because any estimate would be reported as revenue; it is counted, and count in the summary shows that PT's figure rests on two of its three orders.
