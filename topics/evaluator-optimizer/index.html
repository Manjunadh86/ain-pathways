Evaluator-Optimizer (Reflection)

The evaluator-optimizer pattern is a loop in which one language-model call writes a draft, a second step judges the draft against stated criteria and writes feedback, and the first call revises it, repeating until the draft is accepted or a stopping rule ends the loop. Reflection is the same loop when a model critiques its own output.

1Overview

Why it matters

A model's first draft is often close but not right: a translation that misses the register, a SQL query that names a column that does not exist, code that passes its tests and still mishandles an edge case. Calling the model again does not help unless something tells it what was wrong. This pattern supplies that signal automatically, the way a reviewer does for a human author. It needs no new model and no training, only extra calls and a clear idea of what good output looks like.

It also fails in specific, recognisable ways. A critic that always finds one more thing to improve keeps the loop running until the budget is gone. A critic that approves everything adds cost and no quality. A loop with no stopping rule turns one request into dozens of model calls. Anyone who builds or reviews a design with a "critic", "reviewer" or "QA" step needs to be able to answer three questions: what are the criteria, who checks them and with what evidence, and what makes the loop stop.

  • Prompt ChainingBeginner

What you will be able to do

  • Trace one round of the loop and name what the generator, the evaluator and the controlling code each do.
  • Compare self-critique, a separate LLM evaluator, an evaluator with tools and plain code checks, and say when each is enough.
  • Write criteria and an evaluator output format that produce specific, actionable feedback.
  • Choose stopping rules (acceptance, round cap, no progress) and return a distinct status and the best draft for each.
  • Implement the loop in plain Python with scripted model replies and reproduce the lesson's trace.
  • Decide from pass rates and call costs whether the loop is worth adding, and when to remove it.

Key terms

Generator (optimizer)
The model call that writes the first draft and then revises it using feedback. The optimizer in the pattern's name refers to this role, because it improves the draft each round.
Evaluator (critic)
The step that judges a draft against the criteria and writes feedback. It can be a model, ordinary code, a test run, or a combination.
Criteria
The explicit list of things a draft must satisfy, written precisely enough that two reviewers would reach the same verdict.
Rubric
Criteria together with a scoring scale and a pass threshold for each criterion.
Feedback
The evaluator's account of what is wrong with a draft and what to change, which is passed to the generator for the next round.
Reflection
Prompting a model to review an output, usually its own, and then to improve the output using that review.
Self-critique
Reflection in which the same model plays both roles, with one prompt for generating and another for criticising.
External feedback
Evidence from outside the model, such as a test result, a database error or a rendered page, that the evaluator uses to judge a draft.
Round
One generate-or-revise step followed by one evaluation of the resulting draft.
Stopping rule
A condition checked by code that ends the loop, such as acceptance, a maximum number of rounds, a budget or a lack of progress.

2Explanation

Introduction

In Prompt Chaining you saw a fixed sequence of model calls with checks, or gates, between the steps. When a gate fails, the chain stops or tries again. The evaluator-optimizer pattern turns one of those gates into a loop: when the check fails, the draft goes back to the step that produced it, together with a written explanation of what is wrong.

You know this loop from ordinary work. A writer hands a draft to an editor. The editor does not rewrite it. They mark what is unclear or missing, and the writer revises. A developer opens a pull request, a reviewer comments, and the developer pushes a fix. Two things make the cycle productive: the reviewer judges against something definite (a style guide, the requirements, the tests), and at some point someone decides the work is good enough to ship.

Anthropic's Building effective agents (opens in a new tab) describes the pattern in one sentence: one model call produces a response, a second call evaluates it and returns feedback, and the two repeat. Three roles are involved:

  • The generator (the optimizer in Anthropic's name) writes a draft and later revises it.
  • The evaluator, also called the critic, judges the draft against explicit criteria and writes feedback.
  • The controller is ordinary code. It carries drafts and feedback between the two and decides when to stop.

The same idea is taught under the name reflection. In Andrew Ng's letter on the reflection pattern (opens in a new tab), a model is asked to criticise its own output and then to rewrite the output using that criticism. When one model plays both roles with two different prompts, people say self-critique or self-refinement. When the roles are separate, they say evaluator-optimizer or generator-critic. The mechanics are identical.

This lesson covers how one round works, who can play the evaluator and why that choice matters most, how to write criteria that produce useful feedback, the stopping rules every loop needs, and how to tell whether the loop is earning its cost.

How it works

One round, three roles

Stripped of framework detail, the loop looks like this. The block is pseudocode; the worked example is the runnable version.

python
draft = generate(task, criteria)                         # first draft
for round_number in range(1, max_rounds + 1):
    verdict = evaluate(task, criteria, draft)            # scores plus written feedback
    if verdict.passed:
        return draft, "accepted"                         # stop: the criteria are met
    draft = generate(task, criteria, draft, verdict.feedback)   # revise
return best_draft_so_far, "max_rounds"                   # stop: the program says enough

Three properties follow from this shape:

  • The evaluator judges and does not rewrite. Google's description of the critic inside its Jules coding agent is that the critic flags a problem and hands the patch back to be improved. Each prompt then has one job, and the evaluator has no stake in the draft.
  • Feedback is what makes round two different from round one. Without it, a retry is just another sample. The generator needs the previous draft and the feedback. Self-Refine also appends every earlier draft and its feedback so that old mistakes do not return, at the price of a prompt that grows each round.
  • Code owns the loop. In The Agent Loop the model chooses each next action. Here the path is fixed (generate, evaluate, revise) and only the number of rounds varies, which is why Anthropic lists this pattern among workflows and not agents.

Who plays the evaluator

This choice sets the ceiling for the whole loop, because the generator can only fix what the evaluator can see.

The same model with a critic prompt. This is self-critique, and it is the quickest version to build. The Self-Refine paper (opens in a new tab) used one model to generate, give feedback and refine, and reported clear gains on six of its seven tasks. The seventh shows the weakness. On math reasoning the scores barely moved, and the authors found that ChatGPT's feedback said everything looked good for 94% of instances. A model that could not see the error while writing often cannot see it while reviewing. Anthropic's harness design article (opens in a new tab) reports the same tendency in agents: asked to grade their own work, they praise it confidently.

A separate LLM evaluator. A second call with its own prompt and rubric, and possibly a different model. The same Anthropic article says separation alone does not remove leniency, but that it is much easier to tune a separate evaluator towards scepticism than to make a generator critical of its own output. The author calibrated the evaluator with a few graded examples.

An evaluator with outside evidence. Tests, a compiler, a database or a rendered page tell the evaluator things the generator did not know. LinkedIn's SQL Bot team states the principle directly: a validator is most useful when it draws on information the query writer did not have. The Reflexion paper (opens in a new tab) measured it. On 50 hard Rust problems, reflection without running tests scored 52%, below the 60% of the base model, and reflection with tests scored 68%. Andrew Ng's reflection letter makes the same point, and the reflection module of DeepLearning.AI's Agentic AI course (opens in a new tab) has a lesson on using external feedback.

Plain code. Anything exact, such as a length limit, a required field, valid JSON or a table that must exist, should be checked by code. Code is cheaper than a model call and is never lenient. Run code checks first and spend the LLM evaluator only on what code cannot judge, such as meaning, tone and completeness.

Criteria and feedback

Anthropic's test for whether the pattern fits has two parts: the output improves when a person spells out feedback, and a model can produce that kind of feedback. Both depend on criteria.

  • Name each criterion and define a pass. "Is this design good?" cannot be graded consistently. The Anthropic harness replaced it with four named criteria (design quality, originality, craft and functionality), and its full-stack version gave each criterion a hard threshold.
  • Ask for a structured verdict. Have the evaluator return a score per criterion and a feedback field (see Structured Outputs), and let code compare the scores with the thresholds. The evaluator-optimizer example in the LangGraph documentation (opens in a new tab) does this with a schema that has a grade and a feedback field, and a conditional edge that either ends the graph or routes back to the generator.
  • Require feedback that is specific and actionable. In Self-Refine's terms, feedback is actionable when it names something concrete to do, and specific when it points at the exact part of the output to change.

The paper's ablation shows how much this matters (scores on each task's own metric, from its Table 2):

Feedback passed to the refine stepCode optimizationSentiment reversalAcronym generation
Specific and actionable27.543.256.4
Generic, such as "improve the efficiency"26.031.254.0
None, only repeated refinement24.8048.0

In the same paper's analysis of failed refinements, 33% traced to feedback that misplaced the error and 61% to feedback that proposed the wrong fix. Only 6% were the refiner failing to apply good feedback. When a loop underperforms, read the feedback before you touch the generator prompt.

Reflection across attempts

The draft does not have to be a document. In an agent it can be a whole attempt at a task. Reflexion runs three models: an actor makes the attempt, an evaluator scores it, and a self-reflection model turns the score and the transcript into a short written lesson. The lesson is stored in memory, limited to the most recent one to three, and given to the actor on its next attempt. It is the same loop, with feedback that persists between rounds (see Agent Memory).

Stopping rules

The evaluator's pass is one exit. A loop needs others, and code must enforce them.

RuleSignal the code checksWhat the loop returns
AcceptedEvery criterion meets its thresholdThe draft, status accepted
Round capThe round counter reaches the maximumThe best draft so far, status max_rounds
No progressThe best score has not improved for k rounds, or a draft repeatsThe best draft, status no_progress
BudgetTokens, cost or elapsed time pass a limitThe best draft, status budget
Fixed roundsA set number of rounds, often one, with no verdictThe last draft

Published systems use the first two rules and the last. The no-progress and budget rules are cheap additions for production use.

  • Google's Agent Development Kit states that its LoopAgent (opens in a new tab) does not decide for itself when to stop. You must add a termination mechanism: a maximum number of iterations, an escalation signal from a sub-agent, or both. Its sample caps the loop at 5 iterations and gives the refiner an exit_loop tool.
  • Self-Refine stops at a fixed iteration or on a stop indicator in the feedback, and ran at most 4 iterations. Reflexion loops until its evaluator passes the attempt or a trial limit is reached.
  • Andrew Ng's translation-agent uses fixed rounds: exactly one reflection and one improvement.
  • The sample loop in Anthropic's cookbook notebook (opens in a new tab) is while True and exits only on PASS, and its evaluator prompt allows a pass only when there are no further suggestions. That is fine for a demonstration. A critic asked for suggestions can always find one, so add a cap before you reuse it.

A small cap usually loses little, because in the published measurements most of the gain arrives early. In Self-Refine's iteration analysis, code optimization improved by 5.0 points in the first round and by 0.9 in each of the next two.

Keep the best draft, not the last. Quality does not rise every round. Self-Refine shows an acronym whose total score went 11, 17, 12, 17 over four iterations, and the method selects the highest-scoring output. The Anthropic author regularly preferred a middle iteration to the final one. Store each draft with its score.

Report how the loop ended. A caller must be able to tell an accepted draft from one that ran out of rounds, so return a status with the draft.

What the loop costs

Every round adds a generator call and an evaluator call, one after the other, so cost and latency grow with the number of rounds. In Anthropic's experiment a single agent built a game maker in 20 minutes for $9, and the planner, generator and evaluator harness took 6 hours and $200. The author's conclusion is that an evaluator pays for itself only on tasks the current model cannot yet do reliably alone, and that after a model upgrade some of those checks became overhead.

So measure before you commit. Record the first-round pass rate and the pass rate of each later round, and compare outputs with and without the loop on a test set (see Evaluating LLM Applications). If nearly every first draft passes, the evaluator is adding cost and nothing else.

Worked example: A release-note loop with a code check, a scored review and a round cap

The task is a customer-facing release note for a bug fix. A draft is accepted when it has at most 45 words, which code checks, and when an evaluator scores it at least 4 out of 5 on accuracy, clarity and actionability. So that everyone gets identical output, both models are replaced by scripts: three pre-written drafts and two pre-written reviews. Everything else is a real loop.

Save this as refine_loop.py. It needs only the Python standard library (3.9 or later).

python
import json

FACTS = ("CSV exports with more than 10,000 rows were cut off at row 10,000. "
         "Fixed in version 2.4.1. Customers should update and re-run affected exports.")
CRITERIA = {
    "accuracy": "matches the facts exactly, including the row limit and the version",
    "clarity": "a customer can tell whether they were affected",
    "actionability": "says what the customer should do next",
}
PASS_SCORE = 4   # every criterion must score at least this, on a 1 to 5 scale
MAX_WORDS = 45
GENERATOR_PROMPT = """Write a release note for customers. Reply with the note only.
Facts: {facts}
Limit: {limit} words. It will be reviewed for: {criteria}
{revision}"""
EVALUATOR_PROMPT = """Review this release note. Do not rewrite it.
Facts: {facts}
Draft: {draft}
Score each criterion from 1 to 5: {criteria}
In the feedback, quote the phrase to change and say what to change it to.
Reply with JSON only: {{"scores": {{"<criterion>": <1-5>}}, "feedback": "<text>"}}"""


def evaluate(draft, evaluator):
    words = len(draft.split())
    if words > MAX_WORDS:  # an exact rule is checked in code first and costs no model call
        return {"by": "code", "passed": False, "total": 0,
                "feedback": f"The draft has {words} words; the limit is {MAX_WORDS}."}
    prompt = EVALUATOR_PROMPT.format(facts=FACTS, draft=draft, criteria=json.dumps(CRITERIA))
    verdict = json.loads(evaluator(prompt))
    scores = {name: int(verdict["scores"][name]) for name in CRITERIA}
    passed = all(score >= PASS_SCORE for score in scores.values())  # code applies the threshold
    return {"by": "model", "passed": passed, "total": sum(scores.values()),
            "scores": scores, "feedback": verdict["feedback"]}


def refine(generator, evaluator, max_rounds=4):
    revision, history = "", []
    for round_number in range(1, max_rounds + 1):
        prompt = GENERATOR_PROMPT.format(facts=FACTS, limit=MAX_WORDS,
                                         criteria=", ".join(CRITERIA), revision=revision)
        draft = generator(prompt).strip()             # generate, or revise using the feedback
        verdict = evaluate(draft, evaluator)          # judge the draft against the criteria
        history = [*history, {"draft": draft, **verdict}]
        print(f"round {round_number}: {len(draft.split())} words, judged by {verdict['by']}, "
              f"scores {verdict.get('scores', '-')}, {'ACCEPT' if verdict['passed'] else 'REVISE'}")
        if verdict["passed"]:                         # stop rule 1: every criterion is met
            break
        print(f"  feedback: {verdict['feedback']}")
        revision = (f"Your previous draft: {draft}\nReviewer feedback: {verdict['feedback']}\n"
                    "Revise the draft so that every point of the feedback is addressed.")
    last = history[-1]                                # stop rule 2: the round cap ended the loop
    best = last if last["passed"] else max(history, key=lambda entry: entry["total"])
    return {"status": "accepted" if last["passed"] else "max_rounds", "rounds": len(history),
            "model_calls": len(history) + sum(entry["by"] == "model" for entry in history),
            "draft": best["draft"]}                   # the best draft, which may not be the last


def scripted(replies):
    remaining = iter(replies)  # stands in for an LLM: one scripted reply per call
    return lambda prompt: next(remaining)


DRAFTS = [
    "We are pleased to announce that in this release we have resolved an issue that some of our "
    "customers may have noticed when using the CSV export feature, where large exports were sometimes "
    "not complete. This has been fixed in version 2.4.1 and everything should now work as expected.",
    "Version 2.4.1 fixes a bug in CSV export. Large exports were sometimes incomplete.",
    "Version 2.4.1 fixes a bug in CSV export: exports with more than 10,000 rows stopped at row "
    "10,000. If you exported a larger file, update to 2.4.1 and run the export again.",
]
REVIEWS = [
    '{"scores": {"accuracy": 4, "clarity": 2, "actionability": 1}, "feedback": "Replace \'Large '
    'exports were sometimes incomplete\' with the row limit, and add what the customer should do."}',
    '{"scores": {"accuracy": 5, "clarity": 5, "actionability": 4}, "feedback": "Meets all criteria."}',
]

if __name__ == "__main__":
    print(refine(scripted(DRAFTS), scripted(REVIEWS)))
    print(refine(scripted(DRAFTS), scripted(REVIEWS), max_rounds=2))

Run python3 refine_loop.py. The first call to refine prints:

text
round 1: 49 words, judged by code, scores -, REVISE
  feedback: The draft has 49 words; the limit is 45.
round 2: 13 words, judged by model, scores {'accuracy': 4, 'clarity': 2, 'actionability': 1}, REVISE
  feedback: Replace 'Large exports were sometimes incomplete' with the row limit, and add what the customer should do.
round 3: 32 words, judged by model, scores {'accuracy': 5, 'clarity': 5, 'actionability': 4}, ACCEPT
{'status': 'accepted', 'rounds': 3, 'model_calls': 5, 'draft': 'Version 2.4.1 fixes a bug in CSV export: exports with more than 10,000 rows stopped at row 10,000. If you exported a larger file, update to 2.4.1 and run the export again.'}

What to notice:

  • Round 1 never reached the evaluator model. Code counted 49 words and wrote the feedback itself.
  • Round 2 failed on two of three criteria. Accuracy scored 4, which meets the threshold. Clarity (2) and actionability (1) did not. The feedback quotes the weak phrase and names both changes, and draft 3 makes both.
  • Code made the decision. The evaluator returned scores. The line with PASS_SCORE decided that 5, 5 and 4 is a pass.
  • Cost. Three generator calls plus two evaluator calls is 5 model calls, against 1 for a single pass.
  • Round cap. The second call sets max_rounds=2. It prints the same first two rounds and returns status max_rounds after 3 model calls, with draft 2 as the best draft it has. The caller can see that this draft was not accepted.

To go live, replace the two scripted(...) arguments with functions that send the prompt to a chat model and return its reply text. The loop does not change.

Edge cases and limitations

The evaluator never says pass
A critic that is asked for improvements can always find one more. The sample loop in Anthropic's cookbook notebook exits only on PASS and tells the evaluator to pass only when it has no further suggestions, and Google's ADK documentation warns that its LoopAgent does not decide on its own when to stop. Apply the thresholds in code, cap the rounds, and ask the evaluator to separate blocking problems from optional polish so that only blocking problems send a draft back.
The evaluator approves everything
An evaluator can be lenient as well as blind. Anthropic's author watched an early QA agent find real issues and then talk itself into approving the work, and found that it tested superficially instead of probing edge cases. The sign is a first-round pass rate near 100% while people still find faults. Give the evaluator outside evidence, calibrate it with graded examples, read its logs for verdicts you disagree with, and audit a sample of accepted drafts by hand.
A later draft is worse than an earlier one
Fixing one criterion can break another. In Self-Refine's acronym example a revision raised the pronunciation and spelling scores in one round and lost them again in the next, so the total fell from 17 to 12 before it recovered. Keep every draft with its per-criterion scores and return the highest-scoring one. When the generator revises, send it the full list of criteria again and not only the latest complaint.
Generated tests are themselves wrong
When the evaluator is a set of tests the model wrote, a bad test misleads the loop. Reflexion reports that on MBPP 16.3% of solutions that passed its self-written tests were actually wrong, against 1.4% on HumanEval, and on MBPP it scored 77.1, below plain GPT-4 at 80.1. A false pass ends the loop on broken code. A false failure sends the generator after a bug that does not exist. Prefer tests that people wrote, where they exist.
The evaluator's reply cannot be parsed
A reply with extra prose or a missing field crashes a naive loop (the worked example's json.loads call would raise), and a score outside the scale can slip past the threshold unnoticed. Self-Refine found that a weaker model, Vicuna-13B, could not consistently produce feedback in the required format. Treat an unreadable or out-of-range verdict as a failed round, never as a pass, count it against the round cap, and use structured outputs where the API offers them. Exercise 1 adds the first guard.
A better model makes the evaluator redundant
Anthropic's harness author found that after a model upgrade the evaluator became unnecessary overhead for work the new model handled well alone, while it still helped on the hardest parts of a build. The evaluator's value depends on where the task sits relative to what the generator can do unaided. Re-measure the first-round pass rate after every model change and remove the loop where it no longer pays.

When to use it, and when something simpler is enough

Use it when

  • You can write the acceptance criteria down, and drafts that fail them get better when someone points out what is wrong. These are the two signs of fit that Anthropic gives for the pattern.
  • The evaluator can see something the generator could not, such as test results, a database error, a rendered page or a rubric with graded examples.
  • Quality matters more than response time, as in background jobs, documents, translations and code changes that are reviewed before a person sees them.
  • A comparison on your own test set shows that the loop's outputs beat single-pass outputs by enough to pay for the extra calls.

Think twice when

  • Nearly every first draft already passes. The evaluator then adds a model call to each request and changes nothing.
  • Nobody can state what good means, or the evaluator has no more information than the generator. The loop then polishes wording while the real error stays.
  • A user is waiting on a strict latency budget. Each extra round adds two model calls that run one after the other.
  • The failure cannot be fixed by rewriting, for example missing source data or a missing permission. Revision only produces a different wrong answer.

A simpler alternative. One well-prompted call with the criteria written into the prompt, followed by a deterministic check and a single retry that passes the error message back, for example validating the JSON, running the query through EXPLAIN or running the tests. This stops being enough when the remaining failures are ones that code cannot detect, such as tone, completeness or a subtle logic error, and written feedback from a reviewer demonstrably fixes them.

Key takeaways

  • The evaluator-optimizer pattern is a loop: generate a draft, evaluate it against explicit criteria, revise it with the feedback, and let ordinary code decide when to stop.
  • Reflection and self-critique are the same loop with one model in both roles, and a separate or tool-equipped evaluator catches more because it does not share the generator's blind spots.
  • The evaluator sets the ceiling, so give it named criteria, evidence the generator did not have, and a required format for specific, actionable feedback.
  • Every loop needs stopping rules enforced in code (acceptance by threshold, a round cap and a no-progress check), each returning its own status.
  • Most of the improvement arrives in the first one or two rounds and later drafts can be worse, so keep the cap small and return the best-scoring draft.
  • The loop multiplies cost and latency, so measure it against a single-pass baseline and remove it when the model passes reliably without it.

Example 1 of 5

Anthropic's generator and evaluator harness for frontend design and long app builds

AnthropicDocumented in an engineering article

Anthropic's engineering article Harness design for long-running application development (March 2026), written by a member of its Labs team, describes a generator agent and a separate evaluator agent built on the Claude Agent SDK. The loop was first used for frontend design and then extended to multi-hour builds of full-stack applications. [4]

The problem

Left alone, the model produced layouts that worked but looked generic, and applications that looked impressive but had real bugs when someone used them. Asking the same agent to check its work did not help: the article reports that agents asked to evaluate what they have produced tend to praise it confidently, even when a human observer finds the quality mediocre. Design made this worse because it has no pass-or-fail check comparable to a software test.

Where this topic fits

The loop is the centre of the harness. A generator creates an HTML, CSS and JavaScript frontend from the user's prompt. A separate evaluator opens the live page, scores it against four written criteria and writes a critique. The critique is the input to the generator's next iteration. In the full-stack version a planner runs first to expand a short prompt into a product spec, and the evaluator grades each chunk of work against criteria with hard thresholds.

How it is applied, step by step

  1. The author wrote four grading criteria (design quality, originality, craft and functionality) and put them in the prompts of both the generator and the evaluator, weighting the first two more heavily.
  2. The generator builds a frontend from the user's prompt.
  3. The evaluator, a separate agent, uses the Playwright MCP to navigate the live page and take screenshots, then scores each criterion and writes a detailed critique.
  4. The critique goes back to the generator, which was told to make a strategic choice after each evaluation: refine the current direction if scores are improving, or switch to a different aesthetic if they are not.
  5. The cycle repeats. The author ran 5 to 15 iterations for each generation.
  6. The evaluator itself was tuned: calibrated with few-shot examples that had detailed score breakdowns, and, for the full-stack version, adjusted by reading its logs and editing its prompt wherever its judgement differed from the author's.
  7. In full-stack builds each criterion had a hard threshold. If any score fell below it, the sprint failed and the generator received detailed feedback on what went wrong.

Why this approach fits

"Is this design good?" cannot be answered the same way twice, but a written rubric can be scored consistently enough to iterate against. Putting the judge in a separate agent means scepticism is tuned in one prompt without weakening the generator. The evaluator also brings evidence the generator did not have, because it looks at the rendered, running page instead of the source code.

Limitation or tradeoff

The loop is slow and expensive. Design runs lasted up to four hours, and for one game-maker prompt the article gives 20 minutes and $9 for a single agent against 6 hours and $200 for the full harness. Quality did not rise every round: the author regularly preferred a middle iteration to the last one, and the wording of the criteria pulled designs towards a particular look. The evaluator needed several rounds of prompt tuning and still missed bugs in features it had not exercised. After a model upgrade the author found the evaluator was unnecessary overhead for tasks the new model could do alone.

What the sources document

  • The article states that agents asked to evaluate their own work tend to praise it confidently even when the quality is mediocre, and that it proved much easier to tune a separate evaluator towards scepticism than to make a generator critical of its own work. [4]
  • Four grading criteria (design quality, originality, craft and functionality) were given to both the generator and the evaluator, and the evaluator was calibrated with few-shot examples that had detailed score breakdowns. [4]
  • The evaluator was given the Playwright MCP so that it could interact with the live page before scoring. The author ran 5 to 15 iterations per generation, and full runs stretched up to four hours. [4]
  • Scores generally improved over iterations but not always in a clean line, and the author regularly saw cases where a middle iteration was preferable to the last one. [4]
  • For a retro game maker prompt the article lists a solo run of 20 minutes costing 9 US dollars and a full harness run of 6 hours costing 200 US dollars, and concludes that the evaluator earns its cost on tasks that lie beyond what the current model can do reliably by itself. [4]

Example 2 of 5

Jules: a critic that reviews every patch before the developer sees it

Google LabsDocumented in an engineering article

Jules is Google's AI coding agent. A Google Developers Blog post from August 2025, written by its product director and two research engineers, announces a critic built into Jules and names the approach critic-augmented generation. [7]

The problem

The post says the convenience of a coding agent can come with subtle bugs, missed edge cases and untested assumptions. Its examples are failures that tests and linters let through: a patch that passes every test but is wrong on inputs the tests do not cover, a change that compiles but silently drops a required field, and code that is correct but needlessly quadratic. The stated goal is fewer low-quality pull requests, better test coverage and stronger security.

Where this topic fits

The critic runs after a patch is generated and before it is submitted to the developer. It reviews the candidate patch and its description, flags problems and hands the patch back to Jules, which replans and updates it. The review can repeat on the updated patch. What the developer finally receives has already been through this internal review.

How it is applied, step by step

  1. The developer gives Jules a task, and Jules produces a candidate patch with a description.
  2. The critic reviews the complete patch and its description in a single pass and forms an overall judgement.
  3. The critic does not edit the code. It flags each problem with a short reason and returns the patch to Jules.
  4. Jules replans and produces an updated patch that responds to the flags.
  5. The critic can review the updated patch again, and it continues to flag problems until none remain.
  6. The developer receives the patch and is still expected to review it carefully before using it.

Why this approach fits

Code review is an established evaluator-optimizer loop between people, and the post moves it earlier, into generation itself, so that flagged problems are fixed before they cost a developer's attention. The critic judges intent and robustness without a reference solution, which is what a linter's fixed rules and a test's specific assertions cannot do. Keeping the critic from fixing code keeps the two roles separate. The post compares the design to actor-critic reinforcement learning, with the difference that feedback changes the current task state and not the model's parameters.

Limitation or tradeoff

By the post's own description this first version is a one-shot critic: it evaluates the finished output in a single pass and does not call tools, so it cannot run code to confirm a suspicion. The post presents tool use and review at earlier stages as future work. It gives no figures for how many defects the critic catches or how often it flags correct code, and it does not state a cap on review rounds. The developer's own review is still required, and every round adds time before the patch arrives.

The problem

A direct LLM translation can be accurate and still miss what a careful translator would catch: the regional variety of the target language, idioms, and consistent handling of names and technical terms. The README's aim is a translation workflow that can be steered through prompts, for example towards a formal or informal style, a glossary, or Spanish as spoken in Latin America and not in Spain.

Where this topic fits

Reflection is the whole workflow. For a text that fits in one chunk the code makes exactly three model calls: translate, reflect on the translation, and improve it using the reflection. Longer texts are split into chunks and each chunk goes through the same three steps. There is no evaluator verdict and no loop back.

How it is applied, step by step

  1. The translate function counts the tokens in the source text and chooses the single-chunk or the multi-chunk path.
  2. The first call asks the model for an initial translation of the source text.
  3. The second call, prompted as an expert linguist, receives the source text and the translation and writes a list of specific suggestions on accuracy, fluency, style and terminology. When a country is given, the prompt asks for the target language as colloquially spoken there.
  4. The third call receives the source text, the first translation and the suggestions, and returns an edited translation.
  5. The edited translation is returned. The stopping rule is a fixed count of one round, and nothing scores the result.

Why this approach fits

Translation is the first example Anthropic gives for this pattern: a translator model misses nuances that an evaluator model can point out. The four named aspects give the reflection step something definite to look for. Limitation or tradeoff

The README is frank about the results. Measured with BLEU on traditional translation datasets, the workflow is sometimes competitive with leading commercial systems and sometimes worse, and the authors say the project is not mature software. It is also slower and more expensive than a conventional translation model, which the README notes are often faster and cheaper to run. Because no step issues a verdict, the caller never learns whether the final translation is acceptable, and the README reports no measurement of what the reflection step adds over a single call.

Self-Refine: one model generating, critiquing and refining across seven tasks

Carnegie Mellon University and collaboratorsDocumented in a paper

The Self-Refine paper (Madaan and colleagues, 2023) defines an iterative feedback and refinement method and evaluates it on seven generation tasks, from dialogue responses to code optimization and math reasoning, using GPT-3.5, ChatGPT and GPT-4 as base models. [5]

The problem

A language model does not always produce its best output on the first attempt. Earlier refinement methods needed supervised training data or a separately trained refiner. The paper asks whether a single model, with no extra training, can improve its own output at test time by giving itself feedback.

Where this topic fits

Self-Refine is the loop itself, with one model in all three roles. A generation prompt produces the initial output, a feedback prompt produces the critique, and a refine prompt produces the next output. The feedback and refine steps alternate until a stopping condition is met.

How it is applied, step by step

  1. The model produces an initial output from a few-shot generation prompt.
  2. The same model, with a feedback prompt, writes feedback on that output. The prompt's examples steer it towards feedback that is actionable and specific.
  3. The same model, with a refine prompt, receives the input together with all earlier outputs and their feedback, and writes an improved output.
  4. The loop stops at a fixed number of iterations or when a stop indicator extracted from the feedback says so. The experiments ran at most 4 iterations.
  5. For tasks judged on several aspects, the feedback includes a numeric score per aspect, and the output with the highest score across iterations is selected.

Why this approach fits

Many generation tasks have qualities that a model can describe even when it did not achieve them on the first attempt, such as readability, strength of sentiment or coverage of required words. For those tasks the model's own critique contains real information, and one model with three prompts needs no training and no second model. The paper's largest gains are on tasks of this kind, such as dialogue response and sentiment reversal.

Limitation or tradeoff

Self-critique fails where the model cannot see its own errors. On math reasoning the gain was between 0 and 0.2 points, and ChatGPT's feedback said everything looked good for 94% of instances. When an external signal told the model that an answer was wrong, the gain for GPT-3.5 rose to 4.8 points. Returns diminish after the first round, quality can fall between rounds on multi-aspect tasks, and a weaker model (Vicuna-13B) could not reliably produce feedback in the required format. The figures are for 2023 models with few-shot prompts and do not transfer directly to current models.

What the sources document

  • The paper states that Self-Refine uses a single LLM as the generator, refiner and feedback provider and requires no supervised training data, additional training or reinforcement learning. [5]
  • The stopping condition either stops at a specified timestep or extracts a stop indicator from the feedback. In the experiments the feedback and refine iterations continued up to a maximum of 4, and the history of previous feedback and outputs is appended to the refine prompt. [5]
  • Across seven tasks the abstract reports an average improvement of about 20% absolute over one-step generation. In Table 1, GPT-4 on code optimization rises from 27.3 to 36.0, while GPT-4 on math reasoning moves only from 92.9 to 93.1. [5]
  • With generic instead of specific feedback, the sentiment reversal score fell from 43.2 to 31.2 and the code optimization score from 27.5 to 26.0. With no feedback they were 0 and 24.8. [5]
  • In a manual analysis of cases where refinement failed, 33% were due to feedback that inaccurately located the error, 61% to feedback that suggested an inappropriate fix, and 6% to the refiner incorrectly implementing good feedback. [5]

4Common mistakes

  1. Making the evaluator's pass the only way out of the loop.

    Why it causes problems
    A critic that is asked for improvements keeps finding them, so the loop runs until a provider error or a person stops it. Each extra round costs two more model calls, and late rounds mostly trade one style preference for another.
    How to recognise it
    Loop code written as while True with a single break, runs with many rounds whose late feedback is cosmetic, and no status field that could say the loop gave up.
    How to fix it
    Add a round cap and a no-progress check in code, apply pass thresholds to scores in code, and have the evaluator label each point as blocking or optional so that only blocking points trigger a revision.

  2. Trusting approval from an evaluator that knows nothing the generator did not know.

    Why it causes problems
    The same model with the same information tends to approve its own blind spots. The loop then adds cost and a false sense of review, and wrong drafts are shipped with an accepted status.
    How to recognise it
    A first-round pass rate close to 100%, feedback that mostly says the draft looks good, and a manual audit of accepted drafts that still finds faults.
    How to fix it
    Use a separate evaluator prompt with graded examples, give the evaluator outside evidence such as test results or a database check, and audit a sample of accepted drafts by hand on a schedule.

  3. Writing vague criteria and accepting free-form feedback such as make it better.

    Why it causes problems
    Generic feedback gives the generator nothing to act on, so it rewrites at random. Self-Refine measured a drop from 43.2 to 31.2 on one task when specific feedback was replaced with generic feedback.
    How to recognise it
    Feedback that never quotes the draft, scores that swing from round to round on similar drafts, and revisions that change parts nobody complained about.
    How to fix it
    Name each criterion and define its pass level, require the feedback to quote the phrase to change and state the change, and return the verdict as structured output with one score per criterion.

  4. Returning the last draft with no status when the round cap fires.

    Why it causes problems
    The last draft can be worse than an earlier one, and the caller cannot tell an accepted draft from one the loop abandoned. Unreviewed text reaches users looking exactly like reviewed text.
    How to recognise it
    A return value that is a bare string, no stored scores per round, and downstream code with no branch for a draft that was not accepted.
    How to fix it
    Store every draft with its scores, return the highest-scoring draft together with a status such as accepted, max_rounds or no_progress, and make callers handle each status.

  5. Asking the LLM evaluator to check rules that code can check exactly.

    Why it causes problems
    A model call is spent on a word count, a JSON check or a required field, and the answer is less reliable than code because the evaluator can miscount or wave a violation through.
    How to recognise it
    Evaluator prompts that contain rules such as under 45 words or must be valid JSON, and accepted drafts that break those rules.
    How to fix it
    Run deterministic checks first and let them write the feedback themselves. Send a draft to the LLM evaluator only after it passes them, as the worked example does.

  6. Adding the loop without measuring it against a single-pass baseline.

    Why it causes problems
    The loop at least doubles the number of model calls per request. On some tasks it adds nothing, as Self-Refine found for math reasoning, and a model upgrade can make an evaluator that once helped redundant.
    How to recognise it
    No test set, no record of the first-round pass rate or of pass rates per round, and a loop that has not been re-examined since the model was last changed.
    How to fix it
    Compare loop and single-pass outputs on a fixed test set, log the pass rate of every round, and repeat the comparison whenever the generator model changes.

python
import json

from refine_loop import (CRITERIA, DRAFTS, FACTS, GENERATOR_PROMPT, MAX_WORDS, REVIEWS,
                         evaluate, scripted)

UNREADABLE = "The review could not be read. Check the draft against every criterion again."


def safe_evaluate(draft, evaluator):
    """Like evaluate, but an unreadable review is a failed round instead of a crash."""
    try:
        return evaluate(draft, evaluator)
    except (ValueError, KeyError, TypeError):
        return {"by": "unreadable", "passed": False, "total": 0, "feedback": UNREADABLE}


def refine(generator, evaluator, max_rounds=4, patience=2):
    revision, history, best, stale = "", [], None, 0
    status = "max_rounds"
    for round_number in range(1, max_rounds + 1):
        prompt = GENERATOR_PROMPT.format(facts=FACTS, limit=MAX_WORDS,
                                         criteria=", ".join(CRITERIA), revision=revision)
        draft = generator(prompt).strip()
        verdict = safe_evaluate(draft, evaluator)
        entry = {"round": round_number, "draft": draft, **verdict}
        history = [*history, entry]
        if verdict["passed"]:
            best, status = entry, "accepted"
            break
        if best is None or verdict["total"] > best["total"]:
            best, stale = entry, 0          # a new best draft resets the counter
        else:
            stale = stale + 1               # no improvement on the best draft so far
        if stale >= patience:
            status = "no_progress"
            break
        revision = (f"Your previous draft: {draft}\nReviewer feedback: {verdict['feedback']}\n"
                    "Revise the draft so that every point of the feedback is addressed.")
    return {"status": status, "rounds": len(history), "best_round": best["round"],
            "model_calls": len(history) + sum(entry["by"] != "code" for entry in history),
            "draft": best["draft"]}


def review(accuracy, clarity, actionability):
    scores = {"accuracy": accuracy, "clarity": clarity, "actionability": actionability}
    return json.dumps({"scores": scores, "feedback": "Name the row limit and say what to do next."})

STALL_REVIEWS = [review(4, 3, 2), review(5, 4, 3), review(5, 3, 3), review(4, 4, 3),

if __name__ == "__main__":

  • Cap of 4: 0.9712 × 0.08 = 0.0777, about 7.8%

A higher cap does not reduce this number. If the evaluator's error rate stays at 8%, more rounds mean more accepted drafts and therefore slightly more wrongly accepted ones. Notice the sizes: 7.2% of tickets visibly fail at the cap, and a slightly larger share fails invisibly with an accepted status. The round cap controls the first number only. The second is fixed by improving the evaluator: calibrate it with graded examples from the audit, give it evidence such as the order record the reply refers to, and keep auditing.

Part 5. One reasonable set of rules:

RuleSignalNext step
AcceptedEvery rubric score meets its thresholdSend the draft to the agent's queue with status accepted
Round capRound 3 ends without a passRoute the best-scoring draft and the last feedback to a human agent, status max_rounds
No progressThe best total has not improved for 2 rounds, or a draft repeatsSame route as the cap, earlier, status no_progress
Unreadable reviewThe evaluator's reply cannot be parsedCount a failed round and continue; never treat it as a pass
Policy checkA code check finds a forbidden promise, such as a refund above the limitFail the round with feedback written by code, without calling the evaluator

Every path ends either in the queue with an accepted draft or with a person, so no ticket is dropped. See Human-in-the-Loop for designing that handoff.

Check your answer

  • Did you get 82% accepted within two rounds and 92.8% within three?
  • Is your expected number of rounds 1.63 and your expected cost about 0.0261 dollars per ticket?
  • Did you find that a cap of 4 raises the share of wrongly accepted tickets from about 7.4% to about 7.8%?
  • Does every stopping rule in part 5 say what happens to the ticket next?
