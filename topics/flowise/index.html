Flowise

Flowise is an open-source visual builder for LLM applications and agents. You connect nodes on a canvas into a chatflow or an agentflow, then call the saved flow through a REST endpoint, embed it as a chat widget, or self-host the whole server. Its maintainers froze feature development in July 2026 and archived the repository in August 2026.

1Overview

Why it matters

A visual builder lets a team assemble a retrieval chatbot or a multi-step agent in an afternoon and show the whole flow on one screen to someone who does not read code. Flowise was a popular open-source example (its GitHub repository showed about 55,000 stars when checked in October 2026), so you will still meet its flows in existing projects, tutorials and client environments.

Learning it teaches skills that transfer to any visual builder: how boxes on a canvas map to inputs, state and an API call; where credentials live; what happens when an endpoint is public by default; and how to scale a single Node.js server. It also teaches a hard lesson about dependence. The maintainers ended the project in 2026, so anyone running Flowise now owns patching, forking or migration, and the reason they gave is a direct statement about the limits of visual builders.

What you will be able to do

  • Call a saved flow through the Prediction API with an API key, a session and a human-approval resume, and read the response fields.
  • Explain where credentials, variables and API keys are stored and which of them can be exposed by a mistake.
  • Describe how to self-host Flowise, what must be persisted, and when queue mode is needed.
  • Assess the project's archived status and decide whether to fork, keep or migrate an existing flow.

Key terms

Node
One box on the canvas that does a single job, such as calling a chat model, loading a document or running a tool, and that has inputs and outputs you connect to other nodes.
Chatflow
A flow built for single-agent systems, chatbots and simple LLM pipelines, made of LangChain-style component nodes.
Agentflow
The most general flow type. It adds branching, loops, shared state, multiple agents and pauses for human approval, and it covers what a chatflow and an assistant can do.
Assistant
The beginner builder: a chat assistant defined by instructions, a few tools and uploaded files it can answer from.
Flow state
A key-value store shared by the nodes of one Agentflow V2 run. Keys are declared in the Start node and the store is discarded when the run ends.
Credential
A third-party key, such as a model provider's API key, that Flowise stores encrypted and attaches to nodes at run time.
Prediction API
The HTTP endpoint that sends a message to a saved flow and returns its answer. It is the main way other programs use a flow.
Document Store
A Flowise area where documents are loaded, split into chunks, embedded and upserted into a vector store, before any flow queries them.
Queue mode
A deployment mode in which the web server puts prediction jobs on a Redis queue and separate worker processes run the flows.
Archived repository
A GitHub repository its owner has made read-only: the code stays visible and can be forked, but there are no new commits, issues or pull requests.

2Explanation

Introduction

In What Are AI Agents? an agent was a model that chooses its own next step, and a workflow was a fixed path that your code decides. Either is normally written as code: a loop, some tool functions, a prompt. Flowise lets you draw the same structure instead. You drag boxes called nodes onto a canvas (a chat model, a document loader, a vector store, a tool), join them with lines and save. The saved diagram is a program that the Flowise server runs each time someone sends the flow a message.

A spreadsheet is a fair comparison. A chain of cell formulas is a program, but you can see every intermediate value and a colleague can follow it without reading code. A Flowise canvas gives the same visibility and has the same weakness: once the sheet grows, it is hard to review, test and change safely.

Flowise has three builders. An Assistant is the beginner option, defined by instructions, tools and uploaded files. A Chatflow is for single-agent systems and simple chains. An Agentflow is the most general, with branching, loops, shared state, several agents and pauses for human approval. Whichever you use, the saved flow gets an ID and is served by the same HTTP endpoint, and Flowise can also render it as an embeddable chat widget.

One fact shapes how to read this lesson. The Flowise team has ended the project. Its published timeline dates the announcement and code freeze to 29 July 2026 (the GitHub post that carries it is dated 13 August): feature development stopped, the GitHub repository was archived in August 2026, and the core team's presence on Discord and GitHub was due to end on 31 August 2026. The Apache-2.0 code remains public and can be forked. So this lesson teaches the concepts Flowise made visible, which carry over to Langflow and n8n, and the practical skills for running or retiring an existing deployment. It does not recommend starting a new production system on it.

The sections below cover how builders and nodes work, how a flow is called and embedded, how secrets are kept, how to self-host and scale, and where visual builders run out of road.

How it works

Where the project stands

The sunset page (opens in a new tab) lists three dates. From 29 July 2026, it says, active feature development ceases and new pull requests are no longer reviewed or accepted. The GitHub repository was to move to public archive status in August: the sunset page says 10 August, the maintainers' announcement (opens in a new tab) (a discussion post dated 13 August 2026) says 13 August, and the repository (opens in a new tab) is now archived and read-only, with its last commit on 13 August 2026. The freeze was not absolute: GitHub's commit list shows ten more commits to the main branch after the 3.1.4 release of 29 July, mostly bug fixes plus the sunset notice, and no release followed. On 31 August 2026 the core team's presence on Discord and GitHub was due to end. The reason given is that as models reason better, rigid low-code workflows hit their limit on complex work and developers turn to coding agents instead.

The code stays public. LICENSE.md (opens in a new tab) grants Apache 2.0 for most of it, but files under packages/server/src/enterprise and files with an explicit notice carry a separate commercial licence, so read it before you fork. The newest npm release is 3.1.4, published on 29 July 2026 according to the npm registry (opens in a new tab).

Three builders, one endpoint

BuilderWhat the introduction (opens in a new tab) says it is for
AssistantThe most beginner-friendly option: a chat assistant that follows instructions, uses tools and answers from uploaded files.
ChatflowSingle-agent systems, chatbots and simple LLM flows, with more flexibility than an Assistant (retrievers, rerankers, Graph RAG).
AgentflowA superset of both: chat assistants, single- and multi-agent systems and workflow orchestration.

Nodes, references and flow state

The docs present Chatflow nodes as a visual front end to LangChain (opens in a new tab) components, organised into sections such as Chat Models, Document Loaders, Embeddings, Text Splitters, Tools and Vector Stores. Agentflow V2 (opens in a new tab) uses native nodes instead: Start, LLM, Agent, Tool, Retriever, HTTP, Condition, Condition Agent, Iteration, Loop, Human Input, Direct Reply, Custom Function and Execute Flow. Three distinctions help when you read one:

  • Agent versus Tool. An Agent node lets the model pick among its tools and knowledge sources. A Tool node runs exactly the tool the designer chose, with no model reasoning.
  • Condition versus Condition Agent. A Condition node branches on rules such as equals, contains or is empty. A Condition Agent asks a model to classify the input into scenarios you describe in words.
  • Loop versus Iteration. A Loop node jumps back to an earlier node, at most Max Loop Count times (default 5). An Iteration node runs a nested sub-flow once for each item in an array.

Data moves between nodes in two ways. A node can reference an earlier node's output with double braces, for example {{ llmAgentflow_0.output.subject }}. Or nodes can share flow state: you declare every key with a default in the Start node, nodes with an Update Flow State setting may then change those keys, and any field can read one as {{ $flow.state.next }}. Flow state is created when a run starts and destroyed when it ends, and concurrent runs each have their own.

Preparing knowledge: Document Stores

A Document Store (opens in a new tab) separates preparing documents from answering questions. You pick a loader and a text splitter with a chunk size and overlap, preview the chunks and process them. A second step embeds the chunks and upserts them into a vector store, with an optional record manager that stops a re-upsert from creating duplicate vectors. The embedding model and the vector index must have the same number of dimensions or the upsert fails. A flow then queries the store when a question arrives. See Retrieval-Augmented Generation and Chunking and Document Ingestion for the theory.

Overlap trades accuracy for storage and cost. For a fixed-window splitter with chunk size sss and an overlap o<so < so<s, a document of N>sN > sN>s characters becomes

chunks=1+⌈N−ss−o⌉\text{chunks} = 1 + \left\lceil \frac{N - s}{s - o} \right\rceilchunks=1+⌈s−oN−s​⌉

chunks. The recursive splitter used in the docs breaks at sentence and section boundaries, so real counts differ a little from this formula.

Credentials, variables and API keys

Flowise keeps three kinds of secret in different places.

  • Credentials are third-party keys such as an OpenAI or Pinecone key. They are stored encrypted with an encryption key that is generated when the app starts and saved to a file path. If that key or its path changes, flows fail with "Credentials could not be decrypted", so set your own key with FLOWISE_SECRETKEY_OVERWRITE or keep it in AWS Secrets Manager.
  • Variables are named values you create in Flowise. The Variables page (opens in a new tab) says a variable is either static, saved with the value you type, or runtime, with its value read from the server's .env file. They are referenced as $vars.name in code and {{$vars.name}} in text fields, and the docs' custom MCP example puts Bearer {{$vars.githubPAT}} in a header instead of pasting the token. The docs describe encryption only for credentials and say nothing about static variables, so keep real secrets in a credential where the node accepts one, and otherwise in a runtime variable.
  • Flow API keys protect the prediction endpoint, described next. The Render guide lists APIKEY_PATH beside the database and encryption-key paths, so the key store is also something a redeploy can lose.

Calling a flow: the Prediction API

POST /api/v1/prediction/:id is the main endpoint. The body needs question (or form, when the Start node takes form input) and may carry streaming, overrideConfig, history, uploads and, to resume a paused run, humanInput. The reply includes text, chatId and chatMessageId, plus sourceDocuments, usedTools or an action object when they apply.

bash
curl -X POST "http://localhost:3000/api/v1/prediction/<flow-id>" \
  -H "Content-Type: application/json" \
  -H "Authorization: Bearer <your-api-key>" \
  -d '{"question": "What is AI?", "streaming": false}'
  • Authentication. A new flow is public: anyone who knows its ID can run it. Assigning an API key to the flow makes every call need Authorization: Bearer <key>.
  • Sessions and overrides. The docs pass a session through overrideConfig.sessionId. Since v2.1.4 override is disabled by default, and an administrator must enable it and choose which keys callers may change.
  • Streaming. With "streaming": true tokens arrive as server-sent events of type start, token, metadata, sourceDocuments, usedTools, error and end.

The Embed page (opens in a new tab) adds the browser side: a script tag loads the flowise-embed widget from a CDN and calls Chatbot.init with chatflowid and apiHost. The widget calls the same endpoint from the visitor's browser, so a page on another origin needs the server's CORS_ORIGINS (and IFRAME_ORIGINS for iframes) to allow it. The docs' example sets both to *, which allows every origin; in production, list only the sites that embed the widget (our judgment, since the docs show only the wildcard).

Self-hosting and scaling

Per the quickstart (opens in a new tab), run npm install -g flowise then npx flowise start and open http://localhost:3000, or, in a clone of the repository, copy docker/.env.example to docker/.env and run docker compose up -d. The default database is SQLite, and DATABASE_TYPE can be mysql or postgres. On a host with an ephemeral filesystem, mount a persistent disk and point DATABASE_PATH, APIKEY_PATH, SECRETKEY_PATH, LOG_PATH and BLOB_STORAGE_PATH at it, as the docs' Render guide does.

By default one Node.js process runs every flow. For heavy traffic, queue mode (MODE=queue) puts a Redis queue between the web server and separate worker processes, so you can add workers without touching the web tier.

Where a visual builder runs out of road

  • Complexity. A canvas with many branches, loops and state keys stops being easier to read than code. That is our judgment, and the maintainers' reason for ending Flowise, given above, points the same way.
  • Start small. Flowise's customer-support tutorial advises starting with one agent, evaluating it, and considering several only when the work spans a wide range of support areas or passes roughly 15 to 20 tools and knowledge sources.
  • Escape hatches are code. Custom Tool and Custom Function nodes run JavaScript typed into a text box on the server. Logic that lives there is harder to review, test and version than a file in a repository.

Worked example: Calling a protected agentflow, pausing for approval and resuming it by API

The email-reply agentflow from the Human In The Loop tutorial (opens in a new tab) drafts a reply, pauses at a Human Input node and waits for a person to proceed or reject. The task here is to drive that loop from a client program and see every request and response field that matters. No Flowise install or model key is needed: the script starts a small stub server that copies the documented fields (the path, the Bearer check, chatId, text, action and humanInput). Its action object is a trimmed copy of the documented one, which also carries an id, a mapping and the message history. The stub is our teaching code. It is not Flowise, and its text is canned. To use the same client against a real instance, change base_url, FLOW_ID and API_KEY to your server's values and ask a flow that has a Human Input node.

Save this as flowise_api_demo.py. It uses only the Python standard library (3.9 or later).

python
import json
import threading
import urllib.error
import urllib.request
from http.server import BaseHTTPRequestHandler, HTTPServer

FLOW_ID = "demo-email-flow"
API_KEY = "demo-key-123"
NODE_ID = "humanInputAgentflow_0"
WAITING = {}  # chatId -> id of the Human Input node the stub has paused at
CHATS = {"count": 0}


class StubFlowise(BaseHTTPRequestHandler):
    """Stand-in for a Flowise server. It copies the documented fields; it is not Flowise."""

    def log_message(self, *args):
        pass  # keep the demo output clean

    def reply(self, status, body):
        data = json.dumps(body).encode()
        self.send_response(status)
        self.send_header("Content-Type", "application/json")
        self.send_header("Content-Length", str(len(data)))
        self.end_headers()
        self.wfile.write(data)

    def pause_for_approval(self, chat_id, draft):
        WAITING[chat_id] = NODE_ID
        action = {"elements": [{"type": "agentflowv2-approve-button", "label": "Proceed"},
                               {"type": "agentflowv2-reject-button", "label": "Reject"}],
                  "data": {"nodeId": NODE_ID, "input": {"humanInputEnableFeedback": True}}}
        return {"text": draft, "chatId": chat_id, "action": action}

    def do_POST(self):
        if self.path != f"/api/v1/prediction/{FLOW_ID}":
            return self.reply(404, {"error": "flow not found"})
        if self.headers.get("Authorization") != f"Bearer {API_KEY}":
            return self.reply(401, {"error": "unauthorized"})
        body = json.loads(self.rfile.read(int(self.headers["Content-Length"])))
        human = body.get("humanInput")
        if human is None:  # a new question starts a new chat
            CHATS["count"] += 1
            chat_id = f"chat-{CHATS['count']}"
            return self.reply(200, self.pause_for_approval(chat_id, f"Draft reply to: {body['question']}"))
        chat_id = body.get("chatId")
        if WAITING.pop(chat_id, None) != human.get("startNodeId"):
            return self.reply(400, {"error": "nothing is waiting for approval in this chat"})
        if human["type"] == "reject":  # the Loop node sends the flow back to the agent
            draft = f"Revised draft using feedback: {human.get('feedback', '')}"
            return self.reply(200, self.pause_for_approval(chat_id, draft))
        return self.reply(200, {"text": "Email sent.", "chatId": chat_id})


def call(base_url, payload, api_key=None):
    headers = {"Content-Type": "application/json"}
    if api_key:
        headers["Authorization"] = f"Bearer {api_key}"
    request = urllib.request.Request(f"{base_url}/api/v1/prediction/{FLOW_ID}",
                                     data=json.dumps(payload).encode(), headers=headers, method="POST")
    try:
        with urllib.request.urlopen(request, timeout=10) as response:
            return response.status, json.load(response)
    except urllib.error.HTTPError as error:  # 401, 404 and 400 carry a JSON body with an "error" field
        return error.code, json.load(error)


def decide(base_url, previous, kind, feedback=""):
    human = {"type": kind, "startNodeId": previous["action"]["data"]["nodeId"], "feedback": feedback}
    return call(base_url, {"chatId": previous["chatId"], "humanInput": human}, API_KEY)


if __name__ == "__main__":
    server = HTTPServer(("127.0.0.1", 0), StubFlowise)
    threading.Thread(target=server.serve_forever, daemon=True).start()
    base_url = f"http://127.0.0.1:{server.server_port}"  # for a real instance use http://localhost:3000

    print("1.", call(base_url, {"question": "Where is my order?"}))
    status, first = call(base_url, {"question": "Where is my order?",
                                    "overrideConfig": {"sessionId": "user-123"}}, API_KEY)
    print("2.", status, first["text"], "| chatId =", first["chatId"], "| paused =", "action" in first)
    status, second = decide(base_url, first, "reject", "Mention the tracking number.")
    print("3.", status, second["text"], "| paused =", "action" in second)
    print("4.", *decide(base_url, second, "proceed"))
    print("5.", *decide(base_url, second, "proceed"))
    server.shutdown()

Run python3 flowise_api_demo.py. It prints:

text
1. (401, {'error': 'unauthorized'})
2. 200 Draft reply to: Where is my order? | chatId = chat-1 | paused = True
3. 200 Revised draft using feedback: Mention the tracking number. | paused = True
4. 200 {'text': 'Email sent.', 'chatId': 'chat-1'}
5. 400 {'error': 'nothing is waiting for approval in this chat'}

What to notice:

  • Step 1, no key. The flow is protected, so the call is refused. The docs' troubleshooting list gives 401 for an API-key-protected flow, and the API reference shows an error field in the body of its 400, 401 and 404 responses. The exact wording of the stub's messages is ours.
  • Step 2, the pause. The response carries chatId and an action object, and no final answer. The client must keep chatId; the docs warn that it is needed to resume. The sessionId in overrideConfig is ignored by the stub. A real server uses it to key conversation memory once an administrator has enabled the override.
  • Step 3, reject with feedback. The resume request contains only chatId and humanInput (type, startNodeId copied from action.data.nodeId, feedback). The loop sends the agent back for a new draft and the flow pauses again with a fresh action.
  • Step 4, proceed. The reply has no action, so the run is finished.
  • Step 5, a repeat. Approving twice fails with 400 because nothing is waiting any more. Your client should treat a resume as one-shot and not retry it blindly. The error wording belongs to the stub; a real server's message will differ.

Edge cases and limitations

A new flow is public until you give it an API key
By default anyone who knows a chatflow ID can run it through the API or the embed. Assigning a key in the dashboard makes calls need a Bearer header. A key pasted into browser JavaScript is visible to every visitor, so a public widget should talk to a flow whose tools can do little harm, and anything powerful should sit behind your own server, which holds the key.
Override config is off by default, and turning it on widens what callers control
Since v2.1.4 a caller can only override settings (a system message, variables, a session ID) that an administrator has enabled under Configuration. If a session or variable you send seems to be ignored, check that setting first. Enable the fewest keys you need, because each enabled key is something any caller with access to the endpoint can change.
Credentials stop decrypting after a redeploy
Stored credentials are encrypted with a key saved to a file path. If the container is rebuilt without that path on a persistent disk, a new random key is generated and every flow fails with "Credentials could not be decrypted". Set FLOWISE_SECRETKEY_OVERWRITE, or use AWS Secrets Manager, and use the same key on the main server and every worker in queue mode.
The docs and the package disagree about versions
The quickstart says Node v18.15.0 or v20 and above, the repository README says 20 or later, and the npm metadata for 3.1.4 declares Node ^24. The streaming page's curl example uses /api/v1/predictions/ while every other page uses /api/v1/prediction/. Pin the Flowise version you test, read its engines field, and treat a single docs page as a hint to verify rather than a contract.
Ephemeral hosts lose everything that is not on a disk
The Render guide states that a service's default filesystem is ephemeral. The SQLite database, API keys, encryption key, uploads and logs all default to paths on that filesystem, so a redeploy can erase flows and keys together. Mount a disk and set the path variables, or move to PostgreSQL and S3.
Archived does not yet mean gone, and the pages leave gaps
When checked on 11 October 2026 none of the 104 versions in the npm registry's metadata carried a deprecation message, although the sunset page and the announcement said packages would be marked deprecated, and the documentation site was still online. The sunset pages do not say what happens to Flowise Cloud or to the docs. If you depend on either, plan as if it could disappear, and keep your own copy of the flows and the version you run. Also note that GitHub's commit list shows ten commits to the main branch after the 3.1.4 release, mostly fixes, and no later release, so the npm package does not contain them. If you fork, choose your starting point on purpose.

When to use it, and when something simpler is enough

Use it when

  • You inherit an existing Flowise deployment and need to read, run, back up or migrate its flows, which requires knowing how nodes, credentials and the prediction endpoint fit together.
  • You are learning visual orchestration (nodes, shared state, loops, human approval, document ingestion) and want a free, self-hostable tool to see those ideas drawn out, knowing the concepts transfer to other builders.
  • The job is a fixed pipeline such as retrieve, answer and reply with a few branches, and the real need is an HTTP endpoint or chat widget that non-developers can inspect, and your team accepts maintaining its own fork.

Think twice when

  • You are starting a new production system that needs upstream security patches and bug fixes. The repository is archived, the last npm release is 3.1.4, and any vulnerability becomes your own fork's problem.
  • The logic is complex enough to need code review, automated tests and version history on every change. A flow edited on a canvas, with JavaScript in text boxes, is harder to test than ordinary code.
  • Approvals must come from a named, authorised person. The documented resume request for a Human Input node carries only a chat ID and a decision, so that check would have to live in your own layer in front of Flowise.

A simpler alternative. Write the flow as code: one model call with a tool or two, using a provider SDK (see [Tool Calling](/topics/tool-calling/)), or a small framework as in [Choosing an Agent Framework](/topics/choosing-an-agent-framework/). Flowise's own customer-support tutorial recommends starting with a single agent. Move to a visual builder when non-developers must see or edit the flow, and prefer a maintained one such as [Langflow](/topics/langflow/) or [n8n](/topics/n8n-ai-agents/).

Key takeaways

  • Flowise lets you build chatflows and agentflows by wiring nodes on a canvas, and every saved flow is served by the same prediction endpoint and can be embedded as a chat widget.
  • In Agentflow V2, data moves by referencing earlier node outputs or through flow state that is declared in the Start node and lives for one run, and a Human Input node pauses the run until a person proceeds or rejects.
  • A new flow is public to anyone who has its ID, API keys and the override-config setting decide what callers can do, and stored credentials stop working if the encryption key or its file path changes.
  • Self-hosting means persisting the database, keys and uploads, using PostgreSQL and S3 at scale, and switching to queue mode with Redis and workers when one Node.js process is not enough.
  • The maintainers froze feature development from 29 July 2026 and archived the repository in August 2026, so Flowise is a tool to understand, fork or migrate away from, not one to start a new production system on.
  • Visual builders pay off for fixed pipelines that non-developers need to see, and they strain as logic grows, which is the reason the Flowise team gave for ending the project.

Example 1 of 5

Document Stores preparing a homeowners insurance policy for question answering

Documented in official docs

The Document Stores guide in the Flowise documentation builds a retrieval system over a PDF of an insurance policy, the "LibertyGuard Deluxe Homeowners Policy", from upload to a tested retrieval query. The Flowise LangChain page describes the loaders, splitters, embeddings and vector stores that the guide draws on. [15][16]

The problem

A model cannot answer questions about a specific policy it was not trained on, and sending the whole PDF with every question is slow and expensive. The guide describes this policy as a topic that language models are not extensively trained on. The document has to be split into chunks, turned into vectors and stored where a flow can search it, and someone has to be able to check what was stored.

Where this topic fits

The Document Store is the ingestion stage. It runs once per document set, after the documents are chosen and before any flow retrieves from them. At question time a chatflow uses the configured vector store (or the Document Store (Vector) node) as its retriever, and an agentflow adds the store to an Agent node.

How it is applied, step by step

  1. Create a Document Store named for the policy, choose the PDF loader and upload the file. The guide adds a custom metadata key so the dataset can be filtered later.
  2. Choose the Recursive Character Text Splitter and set chunk size and overlap. The guide previews its result with a chunk size of 1500 and an overlap of 750 and notes that the best overlap depends on the data.
  3. Process the chunks. Afterwards individual chunks can be edited, deleted or added, which is how wrong or irrelevant text is cleaned up.
  4. Configure the upsert: an embedding model, a vector store and, optionally, a record manager. The embedding dimensions and the vector index dimensions must match.
  5. Upsert, then use the Retrieval Query button to test which chunks come back for a sample question before attaching the store to a flow.
  6. At question time the flow runs a similarity search and passes the top K chunks (4 by default) to the model, which composes the answer from them.

Why this approach fits

Searching only the top few chunks means each question sends a few thousand characters instead of the whole policy. Preparing the data in its own stage lets a non-programmer preview the chunks and fix a bad one before any user sees an answer built on it. The metadata key lets several datasets share one vector index, and a record manager means a revised policy can be upserted again without duplicate vectors.

Limitation or tradeoff

Chunk size and overlap are chosen by trial. The guide says the best overlap depends on the data, and the plot above shows what overlap costs in storage and embedding work. Switching to a different embedding model means re-embedding every chunk into an index with matching dimensions. The guide demonstrates that a test query returns relevant chunks. It does not measure answer quality, which needs its own evaluation (see Evaluating RAG Systems).

What the sources document

  • The guide builds a retrieval-augmented generation system over the LibertyGuard Deluxe Homeowners Policy, a topic it says language models are not extensively trained on, using a PDF Loader on the policy PDF. [15]
  • It splits the text with a Recursive Character Text Splitter, previews chunks at chunk_size 1500 and chunk_overlap 750, and shows a custom metadata field (company set to liberty) inserted into each chunk so the dataset can be filtered later. [15]
  • Upserting has three parts: an embedding model (the guide uses OpenAI text-embedding-ada-002 with 1536 dimensions), a vector store (its example retrieval comes from Upstash) and an optional record manager. The guide states that the embedding model and the vector store index must have the same number of dimensions or the upsert errors. [15]
  • The guide explains top K, whose default is 4, as the number of most similar chunks retrieved, and says raising the overlap or top K can improve accuracy while increasing cost. Example 2 of 5

An email-reply agentflow that waits for a person's approval before it sends

Documented in official docs

The Human In The Loop tutorial in the Flowise docs builds an email-reply agent in Agentflow V2 and then shows a simpler variant. The Prediction page documents how an API client resumes the paused run, and the Agentflow V2 page describes the Human Input node and its checkpoints. [17][9][10][8]

The problem

Sending an email to a customer cannot be undone, and a model-written reply may be wrong, off-tone or based on a poor web search. The flow must let a person read the draft, ask for changes and approve it, and only then send, without keeping a server thread blocked while the person decides.

Where this topic fits

The Human Input node sits between the Agent that drafts and the LLM and Tool nodes that format and send. A reject output leads to a Loop node that returns to the agent, and a proceed output continues. For an API client the pause appears as a response containing an action object, and the resume is a second POST to the same endpoint.

How it is applied, step by step

  1. A Start node with Form Input captures the incoming email's subject, body and sender address.
  2. An Agent node with Google Custom Search and Current DateTime tools writes the reply, following a system message that names the support persona and forbids placeholders.
  3. A Human Input node (fixed description "Are you sure you want to proceed?", feedback enabled) pauses the run and shows the draft to a reviewer.
  4. A reject sends the run through a Loop node back to the agent with the reviewer's feedback, at most five times (Max Loop Count 5). A proceed continues.
  5. An LLM node with JSON structured output (subject and body) formats the approved text, and a Tool node using Gmail sendMessage sends it to the original sender.
  6. The simpler variant drops the Human Input node. One Agent has the Gmail createDraft tool with Require Human Input switched on, so the run pauses after the agent decides to call the tool and before the tool runs.

Why this approach fits

The irreversible step is isolated behind a node that cannot be skipped, and rejection feeds the reviewer's words back to the agent instead of starting over. Because the pause is a saved checkpoint, the reviewer can take minutes or hours without a request being held open. Any client that can render two buttons and make a POST can host the approval.

Limitation or tradeoff

The documented resume request carries a chat ID and a decision. It does not identify who is approving, so if approvals must come from named, authorised people you have to enforce that in your own layer in front of Flowise. The Loop node caps rework at five rounds, and the tutorial does not show what the reviewer sees after the fifth rejection, so test that path. The email is only as good as the single search tool behind the draft.

What the sources document

  • The tutorial builds an automated email reply system that generates a draft response, asks a human for approval, allows revisions and then sends the approved email. [17]
  • Its nodes are a Start node with Form Input (subject, body, from), an Agent with Google Custom Search and Current DateTime, a Human Input node with a fixed description and feedback enabled, a Loop node with Max Loop Count 5, an LLM node producing subject and body as JSON, and a Tool node using Gmail sendMessage. [17]
  • The tutorial also shows switching on Require Human Input for an agent's Gmail createDraft tool, so the agent asks for approval before the draft is created. [17]
  • When a run halts for human input the prediction response contains an action object and the chatId must be saved. The client resumes by sending the same endpoint a humanInput with type proceed or reject, the startNodeId taken from the action, and optional feedback. The API reference lists humanInput as the way to resume execution from a stopped checkpoint. [9][10]
  • The Agentflow V2 page says execution pauses without blocking the running thread and that each checkpoint is saved, so the workflow can resume even after an application restart. [8]

The problem

A help desk gets inquiries about unrelated areas: HR policy, event bookings and everything else. One agent given every document and every tool becomes unfocused. The tutorial says that once a system has more than 15 or 20 tools and knowledge sources, dedicated agents tend to perform better.

Where this topic fits

Routing is the first step after the Start form. A Condition Agent classifies the inquiry into one of three scenarios, and each scenario output feeds one specialist agent: one answers from a document store, one calls an API through an OpenAPI toolkit, and one is the fallback.

How it is applied, step by step

  1. A Start node with Form Input collects a subject and a body for each inquiry.
  2. A Condition Agent node receives the subject as input and has three scenarios written in words: related to HR, related to events, and a general query. Each scenario is its own output.
  3. The HR Agent has a system message about applying internal knowledge and a document store called "Human Resources Law", with return of source documents enabled.
  4. The Event Manager agent has a system message about creating, updating, getting, listing and deleting events, and an OpenAPI toolkit configured for an event-management API.
  5. The General Agent is the fallback route and needs no tools. The tutorial says a Direct Reply node could replace it.
  6. The routing instructions tell the model not to mention the transfers, so the user sees one conversation.

Why this approach fits

Each specialist gets a short prompt, a small tool list and only the knowledge it needs, which keeps tool selection manageable as the desk grows. The model only has to choose a route, a much easier task than doing every job. The three branches are visible on the canvas, so a reviewer can see what happens to each kind of inquiry.

Limitation or tradeoff

The tutorial itself says this example could realistically be handled by one agent, and it advises starting with a single agent, measuring, and splitting only when the evidence calls for it. Misroutes only show up if you test with real inquiries (see Routing).

Example 5 of 5

Scaling Flowise past one process with queue mode and a production layout

Documented in official docs

The Flowise docs describe queue mode in "Running Flowise using Queue", give a recommended production layout in "Running in Production", list the environment variables, and show a hosted example in the Render guide. The quickstart gives the single-process starting point. [7][24][25][14][26]

The problem

By default Flowise runs every flow in one Node.js main thread, which the docs say does not scale well for large numbers of predictions. A hosted deployment can also lose its database and keys, because some platforms give a service an ephemeral filesystem.

Where this topic fits

This is the deployment layer under the flows. The flows and the Prediction API in front of them do not change. What changes is where the work runs, where state is stored, and where the encryption key lives.

How it is applied, step by step

  1. Start with the quickstart: install with npm or run Docker, and use the default port and SQLite database.
  2. Move state off the local disk: PostgreSQL through the database variables, S3 for files and logs, and on a host with an ephemeral filesystem a mounted disk with the path variables pointed at it.
  3. Switch to queue mode with the MODE variable, point every process at the same Redis, use the same encryption key on the main server and each worker, and start the worker processes.
  4. Put load-balanced main servers in front and run several workers. The docs' starting recommendation is 2 main servers and 4 workers, each from 4 vCPU and 8 GB of memory, with autoscaling on traffic.
  5. Set the proxy count so the rate limiter sees real client addresses behind the balancer, keep the encryption key in AWS Secrets Manager, and load test with Artillery.

Why this approach fits

Model calls are slow and many users wait at once. Moving execution to workers lets you add capacity without changing the web tier, and Redis publish-subscribe carries streamed tokens back, so streaming still works. The production layout puts every piece of state, including the encryption key, somewhere that survives a server being replaced.

Limitation or tradeoff

Queue mode adds Redis, a database server, object storage, a secrets service and a load balancer, each of which you must run and patch. The sizing figures are the docs' starting recommendation, not a result we measured, and the default worker concurrency of 10000 is a ceiling, not a capacity claim. The docs also disagree in places: the production page says S3 is the only supported blob store while the environment variables page also lists Google Cloud Storage, and a Docker example on that page writes the database type as postgresdb while its table lists postgres. With the project archived, you carry all of this yourself.

What the sources document

  • By default Flowise runs in a Node.js main thread, which the docs say does not scale well with large numbers of predictions, so there are two modes: main (default) and queue. In queue mode the main server sends jobs to a message queue and does not execute them, and one or more workers execute them and send results back. [24]
  • Queue mode is configured with MODE set to queue and a Redis connection. The queue name defaults to flowise-queue and worker concurrency to 10000. Workers start with pnpm run start-worker, the main server and workers must share the same secret key, Postgres is recommended for production, and Redis publish-subscribe streams data back to the UI. [24]
  • The Running in Production page recommends queue mode with 2 load-balanced main servers and 4 workers, each starting from 4 vCPU and 8 GB, PostgreSQL instead of SQLite at scale, S3 for files and logs, AWS Secrets Manager for the encryption key, a correct proxy count for rate limiting, and Artillery for load tests. [25]
  • The Render guide states that the default filesystem on Render is ephemeral and has you mount a disk at /opt/render/.flowise and set DATABASE_PATH, APIKEY_PATH, SECRETKEY_PATH, LOG_PATH and BLOB_STORAGE_PATH to locations on it. The environment variables page lists DATABASE_TYPE as sqlite, mysql or postgres. [26][14]

4Common mistakes

  1. Treating a flow's ID as a secret and leaving the flow without an API key.

    Why it causes problems
    By default anyone who knows a chatflow ID can run it through the API or the embed. Strangers can then spend your model credits and trigger every tool the flow holds, such as sending email or calling an internal API.
    How to recognise it
    Call the prediction URL with curl and no Authorization header. A normal answer instead of a 401 means the flow is public.
    How to fix it
    Assign an API key to the flow and call it from your own server. Do not paste the key into page JavaScript, and give a flow that backs a public widget only low-risk tools.

  2. Letting the encryption key live only on the container's own disk.

    Why it causes problems
    A rebuilt container generates a new random key, and every stored credential becomes unreadable. Flows that need a model, vector store or tool key fail until someone re-enters each credential.
    How to recognise it
    After a redeploy, flows fail on model calls and the logs or UI show "Credentials could not be decrypted".
    How to fix it
    Set FLOWISE_SECRETKEY_OVERWRITE or keep the key in AWS Secrets Manager, back it up together with the database, and use the same key on the main server and every queue-mode worker.

  3. Enabling override config for every setting to make testing easy.

    Why it causes problems
    Any caller who can reach the endpoint can then change the system message or variables, which removes the guardrails written into the flow's prompt.
    How to recognise it
    Open Settings, Configuration, Security and look for toggles that are on. Send a request that overrides the system message and see whether the flow obeys it.
    How to fix it
    Enable only the keys your client needs, for example the session ID, keep the system message locked, and re-check the list after every upgrade.

  4. Hosting on an ephemeral filesystem without mounting a disk or an external database.

    Why it causes problems
    The SQLite database, API keys, encryption key and uploads all default to local paths. A routine redeploy then erases the flows and the keys together.
    How to recognise it
    Flows, API keys or uploaded files vanish after a restart or redeploy, and the host's documentation says its default filesystem is ephemeral.
    How to fix it
    Mount a persistent disk and point DATABASE_PATH, APIKEY_PATH, SECRETKEY_PATH, LOG_PATH and BLOB_STORAGE_PATH at it, or use PostgreSQL and S3.

  5. Changing the embedding model without rebuilding the index it feeds.

    Why it causes problems
    The embedding model and the vector index must have the same number of dimensions, so a mismatch makes the upsert fail. A model with the same dimensions but different vectors fails silently, because queries are compared against vectors made by a different model and retrieval quality drops.
    How to recognise it
    An upsert error mentioning dimensions, or answers that suddenly cite irrelevant chunks after a model change.
    How to fix it
    Record which embedding model built each index, use the same model for ingestion and for query, and re-embed every chunk into a fresh index when you change it.

  6. Building a multi-agent flow before one agent has been shown to fail.

    Why it causes problems
    Every extra agent adds a prompt to tune and a routing decision that can be wrong. The Flowise customer-support tutorial itself says its example could be handled by a single agent.
    How to recognise it
    A flow where each agent has two or three tools, or where the routing node's scenarios overlap and test inquiries land in different branches on different runs.
    How to fix it
    Start with one agent, measure where it fails, and split only when the tool and knowledge count, or measured errors, justify it. The tutorial's rough threshold is more than 15 to 20 tools and knowledge sources.

Exercise 1

Write an approval-loop client with a retry cap

CodingIntermediateAbout 40 min (estimate)Hypothetical scenario

Start from flowise_api_demo.py in the worked example. It provides StubFlowise, call, decide and API_KEY. Write a new file, approval_loop.py, that imports them and defines review_until_approved(base_url, question, reviewer, max_rounds=3).

reviewer(draft_text, round_number) is a function that returns a pair (kind, feedback), where kind is "proceed" or "reject". Your function sends the question with the API key, shows each draft to the reviewer, resumes the flow with the reviewer's decision, and stops when the flow finishes. It copies the idea of the Loop node's Max Loop Count: if no draft is approved within max_rounds, it gives up.

Test it with two scripted reviewers. The first rejects drafts 1 and 2 and proceeds on draft 3. The second rejects every draft. You need only the Python standard library.

Requirements

  • Send the question with the Bearer key. If the first response has no action object, return its text with zero rounds and do not call the reviewer.
  • Treat any non-200 status as an error and raise RuntimeError with the status and the error text from the response body.
  • Pass the reviewer's feedback to the flow in the humanInput of a reject.
  • Return a dict with the final text and the number of rounds used. When max_rounds drafts are rejected, raise RuntimeError saying the draft was not approved after that many rounds.

Expected behaviour

With the first reviewer the function returns {'text': 'Email sent.', 'rounds': 3}. With the second reviewer and max_rounds=3 it raises RuntimeError: not approved after 3 rounds.

Hint 1

The response to a reject is a normal 200 with a new action object, so the loop continues by reading `"action" in reply` again. A proceed response has no action.

Hint 2

Keep `status` and `reply` from the latest call in variables that the loop reads at the top of each round, and check the status there.

Hint 3

After the last allowed reject the loop ends without a return. Decide what a non-200 status at that point means before you raise the "not approved" error.

Show solution

Save this as approval_loop.py next to flowise_api_demo.py.

python
import threading
from http.server import HTTPServer

from flowise_api_demo import API_KEY, StubFlowise, call, decide


def review_until_approved(base_url, question, reviewer, max_rounds=3):
    """Send a question, then ask `reviewer` about each draft until it proceeds or the rounds run out."""
    status, reply = call(base_url, {"question": question}, API_KEY)
    for round_number in range(1, max_rounds + 1):
        if status != 200:
            raise RuntimeError(f"HTTP {status}: {reply.get('error')}")
        if "action" not in reply:  # the flow finished without asking for approval
            return {"text": reply["text"], "rounds": round_number - 1}
        kind, feedback = reviewer(reply["text"], round_number)
        status, reply = decide(base_url, reply, kind, feedback)
        if status == 200 and kind == "proceed":
            return {"text": reply["text"], "rounds": round_number}
    if status != 200:
        raise RuntimeError(f"HTTP {status}: {reply.get('error')}")
    raise RuntimeError(f"not approved after {max_rounds} rounds")


def reject_twice_then_proceed(draft, round_number):
    return ("proceed", "") if round_number == 3 else ("reject", f"change {round_number}")


def always_reject(draft, round_number):
    return "reject", "try again"


if __name__ == "__main__":
    server = HTTPServer(("127.0.0.1", 0), StubFlowise)
    threading.Thread(target=server.serve_forever, daemon=True).start()
    url = f"http://127.0.0.1:{server.server_port}"
    print(review_until_approved(url, "Where is my order?", reject_twice_then_proceed))
    try:
        review_until_approved(url, "Where is my order?", always_reject)
    except RuntimeError as error:
        print("RuntimeError:", error)
    server.shutdown()

Running python3 approval_loop.py prints:

text
{'text': 'Email sent.', 'rounds': 3}
RuntimeError: not approved after 3 rounds

Each pass of the loop reads the latest response. A 200 with an action means the flow is waiting, so the reviewer is asked and the decision is sent back. A reject returns a new draft and a new action, which starts the next round. A proceed returns the final text. If the last allowed reject is answered with a fresh draft, the loop falls out of the for statement and raises the "not approved" error. Against a real Flowise server you would also keep chatId, which decide already reads from the previous reply.

Check your answer

  • Does the first scripted reviewer produce exactly three rounds and the text "Email sent."?
  • Does a response with no action return immediately, without calling the reviewer?
  • If you change the API key to a wrong value, does your function raise an error that includes the 401 status?
  • Does the second reviewer end with an exception after exactly three rejected drafts, rather than looping forever?

Most of the code is Apache 2.0, but files under the server's enterprise directory carry a commercial licence, which matters for any fork.

Risks (judgment unless marked).

  1. The public website flow has no stated protection. Documented: a flow without an API key can be run by anyone with its ID. Judgment: with no upstream fixes, abuse protection is now your job alone.
  2. The CRM token sits in Custom Tool JavaScript that runs on the server. If a public flow can reach that tool, a visitor can cause CRM calls. Judgment: move the token out of the code into a runtime variable and limit the tool.
  3. One VM with SQLite and a locally stored encryption key is a single point of loss. Documented: a changed key makes stored credentials undecryptable.
  4. No security patches will arrive from upstream, so any vulnerability found later in Flowise or its dependencies is for the consultancy or the client to fix in a fork.

Options.

OptionEffortMain drawback
Pin and hardenLowRisks 1, 2 and 4 are reduced, not removed.
Fork and maintainMedium to highYou now own a large Node.js codebase.
Migrate to a maintained tool or to codeMedium, per flowEach flow must be rebuilt and retested.

Recommendation. Pin and harden now, and migrate over a planned period, starting with the simplest flows. This week: back up the database and the encryption key together, assign an API key to every flow that does not need to be public and call it from the client's server, move the CRM token out of the Custom Tool code into a runtime variable ($vars, which the Variables page documents for Custom Tool functions) and cut the tool down to the calls it needs, and put the instance behind a reverse-proxy rule that exposes only the prediction route. Before any change, export each flow and record the Flowise and Node versions. Then rebuild the simplest flow in the replacement tool and compare answers on saved test questions before moving the rest.

Check your answer

  • Did you separate documented facts from your own judgment?
  • Did you name the public embedded flow and the CRM Custom Tool as specific risks?
  • Is there a first action that can be done this week without a migration decision?
  • Did you include a backup of the encryption key as well as the database?
