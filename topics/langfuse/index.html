Langfuse

Langfuse is an open-source platform for observing and evaluating applications built on language models. It records each request as a trace of nested steps, stores versioned prompts, attaches quality scores to what it recorded and runs experiments against datasets, either as a hosted service or on your own servers.

1Overview

Why it matters

An LLM application fails in ways that ordinary logs do not show. The answer was wrong because the retrieval step returned the wrong document, or because someone edited a prompt last Tuesday, or because one tool call in forty timed out. To find the cause you need the full sequence of steps for a single request, the exact prompt version that was used, and a way to tell whether quality went up or down after a change. Langfuse keeps those three things in one place and links them to each other.

It is also a tool you can run yourself with the same core features as the hosted service, which settles the question for teams whose data may not leave their own infrastructure. Engineers who build agents, the people who review their output, and platform teams who offer tracing to many projects all work with the same seven objects: traces, observations, sessions, prompts, scores, datasets and experiments. This lesson explains what each one is and how they connect.

Key terms

Observation
One recorded step of an application, such as a model call, a tool call or a retrieval. Langfuse uses this word for what OpenTelemetry calls a span.
Trace
One request or operation from start to finish. In Langfuse it is the group of all observations that share the same trace id.
Generation
The observation type for a call to a generative model. It carries the model name, the token usage and the cost in addition to input and output.
Session
An optional group of traces that belong to one interaction, usually the turns of a chat thread, identified by a session id that you choose.
Score
A stored quality judgment with a name, a value and a data type, attached to a trace, an observation, a session or a dataset run.
Prompt label
A named pointer to one version of a prompt, such as production or staging. Code fetches a prompt by label, so moving the label changes what the code receives.
Dataset
A named collection of test cases. Each item has an input and, optionally, an expected output or a description of what a good output must contain.
Experiment
One execution of your task on every item of a dataset, with evaluators scoring each output so that different versions can be compared.
LLM-as-a-judge evaluator
An evaluator that asks a language model to score an output against a rubric you wrote and stores the result as a score with the model's reasoning.
OTLP
The OpenTelemetry Protocol, the standard wire format for sending traces. Langfuse accepts it over HTTP as JSON or protobuf.

2Explanation

Introduction

LLM and Agent Observability explained why you record each model call, tool call and retrieval step as a span inside a trace. Langfuse is one concrete system for doing that. It adds three things on top of tracing: a store for versioned prompts, a store for quality scores, and a way to rerun your application against a fixed set of test cases.

Picture a team that runs a support chatbot. A customer complains that the bot quoted the wrong refund period. With plain logs, someone searches for the customer's message and finds one line. With Langfuse, they open the conversation as a session, pick the turn that went wrong (a trace) and read its steps (observations): the search query, the documents that came back, the prompt sent to the model, the tokens used and the answer. They see that the prompt was a version published two days earlier. They add the customer's question to a dataset, fix the prompt, run an experiment that replays the dataset against both versions, compare the scores, and move the production label to the version that won.

Three facts about the product, as of October 2026, help you read its documentation and older tutorials:

  • It is open source and can be self-hosted. All core features are MIT licensed. You can use Langfuse Cloud, which has EU, US, Japan and HIPAA regions, or run the same containers yourself. The instrumentation code is the same for both (opens in a new tab).
  • It is built on OpenTelemetry. The Python and JS/TS SDKs are thin layers over OpenTelemetry, and any program that can send OTLP over HTTP can send traces, whatever language it is written in.
  • Version 4 changed the data model. Since August 2026 Langfuse stores one wide table of observations (opens in a new tab) instead of separate trace and observation tables. Tutorials that update traces after the fact or run evaluators on whole traces describe the earlier model. ClickHouse, the company behind the database Langfuse stores its data in, acquired Langfuse in January 2026 (opens in a new tab) and stated that it stays open source and self-hostable.

The rest of the lesson covers the data model, how data gets in, prompt management, scores and LLM-as-a-judge evaluators, datasets and experiments, and what you run when you host it yourself.

How it works

Observations, traces and sessions

An observation is one step of your application: a model call, a tool call, a retrieval. Observations nest, so a step can contain sub-steps. A trace is one request from start to finish, defined as all observations that share a trace_id. A session is an optional group of traces that belong together, typically the turns of one chat thread. You create a session by putting the same session_id on its observations. There is nothing to register first.

Every observation has a type. span is the generic one. generation is a model call and carries the model name, token usage and cost. The other types (agent, tool, chain, retriever, evaluator, embedding, guardrail, event) say what a step does so that you can filter on it. Framework integrations set types for you, and in your own code you pass as_type.

Trace-level attributes such as user_id, session_id, tags and metadata describe the whole trace, but Langfuse stores a copy on every observation (opens in a new tab). That is why a question such as "what did this user's model calls cost last week" needs no join. The SDKs copy the attributes for you. If you send raw OpenTelemetry spans, you must set them on every span yourself.

Getting data in

There are three routes, and all of them deliver observations to the same backend.

  1. An integration. from langfuse.openai import openai is a drop-in replacement for the OpenAI client that records every call, and a callback handler does the same for LangChain.
  2. The SDK. Decorate functions, or open context managers, as below.
  3. Plain OpenTelemetry. Any language can POST spans to /api/public/otel/v1/traces with Basic Auth: the public key is the user name and the secret key is the password. Attributes in the langfuse.* namespace, such as langfuse.observation.type and langfuse.session.id, map spans onto the data model (opens in a new tab). Langfuse accepts OTLP over HTTP, as JSON or protobuf, and not over gRPC. The worked example uses this route.
python
from langfuse import get_client, observe, propagate_attributes

langfuse = get_client()   # reads LANGFUSE_PUBLIC_KEY, LANGFUSE_SECRET_KEY, LANGFUSE_BASE_URL


@observe(as_type="retriever")
def search_kb(query):
    return ["refund-policy.md: annual plans are refundable for 30 days"]


@observe(as_type="agent")
def support_turn(question, ticket_id):
    with propagate_attributes(session_id=ticket_id, user_id="user-82"):
        documents = search_kb(question)   # recorded as a child observation
        return f"Based on {len(documents)} document(s): yes, within 30 days."


support_turn("Can I get a refund on an annual plan after 20 days?", "ticket-4711")
langfuse.flush()   # a short-lived script must flush before it exits

The SDK does not send each observation as it is created. It queues finished observations, and a background exporter sends them in batches, so your request does not wait on the network. The price of that design is that a script or a serverless function can exit with observations still in the queue. flush() sends them now.

Usage and cost

For generation and embedding observations Langfuse records usage (units per type, such as input and output tokens) and cost in USD. Each can be ingested, which means you or an integration send the numbers from the provider's response, or inferred from the model name through a model definition that holds a price per usage type. Ingested values take priority. Langfuse ships definitions for popular OpenAI, Anthropic and Google models. For any other model, add a definition or send cost_details yourself.

Prompt management

A prompt has a name, a type (text or chat, fixed at creation) and a list of versions numbered 1, 2, 3. Saving a change adds a new version. Labels are pointers to versions. latest always moves to the newest version. production is what the SDK fetches when you ask for a prompt without saying which one.

python
prompt = langfuse.get_prompt("support-answer")                    # the version labelled production
staging = langfuse.get_prompt("support-answer", label="staging")  # another label
text = prompt.compile(question="Can I get a refund?")             # fills {{question}}

Deploying means moving the production label to a new version. Rolling back means moving it back. Neither needs a code change. Two details matter in practice. First, the SDK caches prompts in the client (opens in a new tab) for 60 seconds by default and refreshes them in the background. A fetch therefore costs no latency after the first one, but a label change reaches a running process only after its cached copy is older than that and a later call has triggered the refresh. Second, when you pass the prompt object to the generation that uses it, Langfuse links the two (opens in a new tab), and you can compare metrics and scores per prompt version. Prompt Management and Versioning covers the practice in general.

Scores and evaluators

A score is the one object in which every quality judgment is stored. It has a name, a value, a data type (NUMERIC, CATEGORICAL, BOOLEAN or TEXT) and an optional comment, and it attaches to a trace, an observation, a session or a dataset run. What differs is who produces it:

MethodWho or what produces the scoreTypical use
API or SDKYour own codeUser thumbs up or down, guardrail results, checks in a pipeline
Code evaluatorPython or TypeScript that Langfuse runsDeterministic checks such as valid JSON
LLM-as-a-judgeA model that Langfuse calls with your rubricTone, relevance or groundedness at volume
UI and annotation queuesPeopleSpot checks and building ground truth

An LLM-as-a-judge evaluator (opens in a new tab) is a prompt with {{variables}}, a model and a score definition. A rule decides where it runs: a filter over incoming observations plus a sampling rate. When an observation matches, the Langfuse worker fills the variables from that observation's input, output, metadata or tool calls, calls the judge model through an LLM connection you configured, and writes back the score with the judge's reasoning. The judge sees only the matched observation. To judge a whole request, target the root observation and make sure your code records the overall input and output there. LLM-as-a-Judge explains how to write and calibrate the rubric.

Datasets and experiments

A dataset is a named list of items, each with an input and optionally an expected output. An experiment runs a task, which is your application code, on every item and scores the outputs:

python
from langfuse import Evaluation


def task(*, item, **kwargs):
    return support_turn(item["input"], "experiment")


def correct_period(*, output, expected_output, **kwargs):
    return Evaluation(name="correct_period", value=float(expected_output in output))


result = langfuse.run_experiment(
    name="support-prompt-v8",
    data=[{"input": "Refund on an annual plan after 20 days?", "expected_output": "30 days"}],
    task=task,
    evaluators=[correct_period],
)
print(result.format())

Each execution is traced like production traffic, so you can open a bad result and inspect its steps. Run-level evaluators compute aggregates such as an average. In CI, the script raises RegressionError when a score breaks your threshold and the langfuse/experiment-action GitHub Action fails the job. This is offline evaluation. Rules on live traffic are online evaluation. The two connect when a failure found in production is added to the dataset.

Self-hosting

A self-hosted deployment runs the same software as Langfuse Cloud: two application containers and four storage services.

The web container serves the UI and the APIs. It writes each incoming batch to blob storage and puts a reference on a Redis queue. The worker picks the batch up and writes it to ClickHouse, which holds traces, observations and scores. Postgres holds transactional data, including prompts. The worker also runs evaluators, so it is the worker that needs network access to your LLM provider.

Docker Compose starts all of this on one machine with docker compose up. It is meant for local use and testing, because it has no high availability, scaling or backups. For production the documentation points to Kubernetes with Helm or to Terraform modules for AWS, Azure and GCP. A license key adds enterprise features such as project-level roles, audit logs, data retention policies and SCIM.

Worked example: One support-chat turn as a trace: build it, cost it, send it and score it

To see exactly what Langfuse receives, this example builds one trace by hand and sends it with curl, with no SDK. The trace is one turn of a support chat with four observations: the turn itself, a knowledge-base search, a model call and a policy check. Save the script as build_trace.py. It needs only the Python standard library (3.9 or later).

python
import hashlib
import json
import sys
import time

PRICE_PER_MILLION = {"input": 0.50, "output": 2.00}   # USD, example prices for a model you host
SHARED = {   # trace-level attributes, copied onto every observation
    "langfuse.trace.name": "support-turn",
    "langfuse.session.id": "ticket-4711",
    "langfuse.user.id": "user-82",
    "langfuse.environment": "development",
}
STEPS = [   # name, observation type, parent, start ms, end ms, extra attributes
    ("support-turn", "agent", None, 0, 1840, {
        "langfuse.observation.input": "Can I get a refund on an annual plan after 20 days?",
        "langfuse.observation.output": "Yes. Annual plans can be refunded within 30 days."}),
    ("search-kb", "retriever", "support-turn", 20, 210, {
        "langfuse.observation.input": "refund annual plan",
        "langfuse.observation.output": "refund-policy.md: annual plans are refundable for 30 days"}),
    ("draft-answer", "generation", "support-turn", 230, 1500, {
        "langfuse.observation.model.name": "example-chat-small"}),
    ("check-policy", "guardrail", "support-turn", 1510, 1560, {
        "langfuse.observation.output": "pass"}),
]
USAGE = {"input": 1850, "output": 240}   # tokens reported for draft-answer
COST = {kind: round(tokens * PRICE_PER_MILLION[kind] / 1_000_000, 6) for kind, tokens in USAGE.items()}


def hex_id(text, length):
    return hashlib.sha256(text.encode()).hexdigest()[:length]


def to_span(label, start_ns, name, kind, parent, start_ms, end_ms, extra):
    attributes = {**SHARED, "langfuse.observation.type": kind, **extra}
    if kind == "generation":
        attributes = {**attributes,
                      "langfuse.observation.usage_details": json.dumps(USAGE),
                      "langfuse.observation.cost_details": json.dumps(COST)}
    span = {
        "traceId": hex_id(label, 32),
        "spanId": hex_id(f"{label}/{name}", 16),
        "name": name,
        "startTimeUnixNano": str(start_ns + start_ms * 1_000_000),
        "endTimeUnixNano": str(start_ns + end_ms * 1_000_000),
        "attributes": [{"key": key, "value": {"stringValue": value}} for key, value in attributes.items()],
    }
    return {**span, "parentSpanId": hex_id(f"{label}/{parent}", 16)} if parent else span


if __name__ == "__main__":
    label = sys.argv[1] if len(sys.argv) > 1 else "ticket-4711/turn-1"
    start_ns = time.time_ns() - 2_000_000_000   # pretend the turn started two seconds ago
    spans = [to_span(label, start_ns, *step) for step in STEPS]
    with open("trace.json", "w") as file:
        json.dump({"resourceSpans": [{"scopeSpans": [{"spans": spans}]}]}, file)

    total_ms = STEPS[0][4] - STEPS[0][3]
    print(f"trace {hex_id(label, 32)}")
    for name, kind, parent, start_ms, end_ms, _ in STEPS:
        duration = end_ms - start_ms
        print(f"{'  ' if parent else ''}{name:<13} {kind:<10} {duration:>5} ms {duration / total_ms:>6.1%}"
              f"  {hex_id(f'{label}/{name}', 16)}")
    child_ms = sum(end - start for _, _, parent, start, end, _ in STEPS if parent)
    print(f"outside child observations: {total_ms - child_ms} ms")
    print(f"draft-answer cost: {COST} total {sum(COST.values()):.6f} USD")
    print(f"10,000 turns a day: {sum(COST.values()) * 10_000:.2f} USD")

Running python3 build_trace.py writes trace.json and prints:

Check the numbers. The three child durations are 210 − 20 = 190, 1500 − 230 = 1270 and 1560 − 1510 = 50 ms. Together that is 1510 ms of the 1840 ms turn, which leaves 330 ms in the turn's own code. The cost is 1850 × 0.50 / 1,000,000 = 0.000925 USD for input plus 240 × 2.00 / 1,000,000 = 0.00048 USD for output.

Now send the file to a Langfuse project, on Langfuse Cloud or on a local instance:

bash
export LANGFUSE_PUBLIC_KEY="pk-lf-..."
export LANGFUSE_SECRET_KEY="sk-lf-..."
export LANGFUSE_HOST="https://cloud.langfuse.com"   # or http://localhost:3000

curl -s -o /dev/null -w "%{http_code}\n" -X POST "$LANGFUSE_HOST/api/public/otel/v1/traces" \
  -u "$LANGFUSE_PUBLIC_KEY:$LANGFUSE_SECRET_KEY" \
  -H "Content-Type: application/json" \
  -H "x-langfuse-ingestion-version: 4" \
  --data-binary @trace.json

curl -X POST "$LANGFUSE_HOST/api/public/scores" \
  -u "$LANGFUSE_PUBLIC_KEY:$LANGFUSE_SECRET_KEY" \
  -H "Content-Type: application/json" \
  -d '{"traceId": "71cab3273b8b8d267cb7586d7f46f37a", "observationId": "02dbeafb98c21abc",
       "name": "answer_grounded", "value": 1, "dataType": "BOOLEAN",
       "comment": "Matches refund-policy.md"}'

The first command prints the HTTP status of the ingestion request, and a status in the 200 range means the batch was accepted. Processing continues after the request returns, so the trace can take a moment to appear. The second attaches a boolean score to the model call. In the UI the trace appears as support-turn with three nested observations, session ticket-4711 lists it, and draft-answer carries its usage (1,850 input and 240 output tokens), a cost of 0.001405 USD and the score.

What this shows:

  • A trace is only a set of spans that share an id. Nesting comes from parentSpanId.
  • The session and user attributes are on all four spans, which is what the v4 data model expects.
  • Cost was ingested. Langfuse has no price for example-chat-small, so the script sent cost_details.
  • Timing points at the model call. It takes 69% of the turn, so a faster search would change little.

Edge cases and limitations

A prompt change does not reach running processes at once
The SDKs cache prompts in the client with a default time to live of 60 seconds. When the entry is stale the SDK still returns it immediately and refreshes it in the background, so the first calls after you move a label can use the old version. In development, pass a cache time of 0 seconds to fetch on every call. In production, wait a minute before you judge a rollout by its traces, and consider a fallback prompt for the case where the cache is empty and the API cannot be reached.
A label that no version carries is an error, not a fallback
Fetching a prompt by a label that is not assigned to any version returns 404 Not Found. Langfuse does not fall back to production or latest. Fetching without a label asks for production and fails the same way when nothing has been promoted yet, and passing both a label and a version returns 400. A typo in a label name therefore shows up as a failed fetch on the first call and not as the wrong prompt.
A session id that is too long is dropped
A session id must be a US-ASCII string shorter than 200 characters, and the documentation states that an id longer than 200 is dropped. It does not say what happens at exactly 200, so stay well below it. A dropped id leaves the trace without a session, so expect it to be missing from the session view. If you build session ids from user input or long composite keys, hash them to a fixed length first.
Text scores and boolean scores behave differently from numeric ones
A TEXT score holds 1 to 500 characters of free text and is not supported in experiments, in LLM-as-a-judge evaluators or in score analytics, because free text cannot be aggregated. A boolean score is sent as 0 or 1 and must declare the BOOLEAN data type, otherwise the value is stored as numeric. Use a score comment for the reasoning behind a number, and TEXT only for standalone reviewer notes.
Raw OTLP ingestion needs the version header and HTTP
When you send spans straight to the OTLP endpoint without the header x-langfuse-ingestion-version set to 4, the documentation says the data can take up to 10 minutes to appear. The endpoint accepts HTTP with JSON or protobuf bodies and does not accept gRPC, so a collector that exports over gRPC by default has to be switched to its HTTP exporter.
Older setups stop working on Langfuse Cloud on 16 November 2026
Langfuse Cloud becomes v4-only on that date. Evaluators that run on whole traces are deprecated and stop producing results there, and the documentation describes OTLP as the replacement for the legacy ingestion endpoint. Self-hosted deployments have no forced date, and the changelog states that version 3 receives security patches through January 2027. Check the SDK version of an old project before you copy its code: the changelog names Python SDK 4.7.0 and JS/TS SDK 5.4.0 as the versions from which the SDKs put trace-level attributes on every observation.

When to use it, and when something simpler is enough

Use it when

  • You need traces, prompt versions, scores and experiment results in one tool, linked to each other, so that a bad answer can be traced to a prompt version and turned into a test case.
  • Your data may not leave your own infrastructure, or you want that option later. The same software runs self-hosted, with core features under the MIT license.
  • Your stack mixes languages or uses no agent framework. Anything that can send OTLP over HTTP can report to Langfuse, and Python and JS/TS have SDKs.
  • People who do not deploy code, such as product managers, support leads or domain experts, need to edit prompts, review outputs or set up evaluators.
  • You want prompt and agent changes checked against a dataset in CI before they are merged.

Think twice when

  • You have a prototype or a script with a handful of model calls and one developer. Printing the prompt, the response and the token counts is quicker than setting up a project.
  • You need general infrastructure monitoring such as CPU, HTTP error rates or database latency. Langfuse is built for LLM steps, and its documentation describes sending the same traces to Langfuse and to an infrastructure tool such as Datadog at the same time.
  • You must self-host but cannot operate ClickHouse, Postgres, Redis and blob storage with backups and upgrades. The Docker Compose setup is not meant for production.
  • You need project-level roles, audit logs or SCIM in a self-hosted deployment and cannot buy a license. Those features are not part of the open-source edition.

A simpler alternative. Write one JSON line per model call to your normal log, with a request id, the prompt, the response, the token counts and the latency, and keep prompts in version control next to the code. That is enough while one person owns one prompt and each request makes one or two calls. It stops being enough when requests fan out into many steps, when several people need to read the same run, or when you want to compare quality before and after a change with numbers.

Key takeaways

  • Langfuse stores an application run as observations grouped into a trace by a shared trace id, with optional sessions that group traces by a session id you choose.
  • The SDKs are built on OpenTelemetry and send data in the background, so any OTLP-over-HTTP sender can report to Langfuse and short-lived programs must flush before they exit.
  • Prompts have numbered versions and movable labels. Code fetches by label, so deploying or rolling back a prompt is a label move that reaches clients after the cache refreshes.
  • Every quality judgment is a score, whether it comes from your code, a person or an LLM-as-a-judge evaluator, and a judge evaluator sees only the single observation its rule matched.
  • An experiment runs your task on every dataset item and scores the outputs, which turns failures found in production into regression tests you can run in CI.
  • Self-hosting gives you the same software as the cloud service, at the cost of operating two containers plus Postgres, ClickHouse, Redis and blob storage yourself.

Example 1 of 5

Hugging Face tracing an overnight model-discovery agent with one session per paper

Hugging FaceDocumented in a case study

A Langfuse customer story published in August 2026 describes an agent built by Niels Rogge, a machine learning engineer at Hugging Face. It runs overnight, goes through new arXiv papers, looks for models and datasets that were released with them, and contacts the authors through GitHub issues and pull requests. [25][4][3]

The problem

The agent works unattended, and its messages are written as if the engineer himself were reaching out, so he has to trust each decision. Before tracing he could see only the final actions. The prompts are assembled dynamically, and there was no way to see what had been filled into a template or how one step fed the next. The usual idea of a session as the turns of a chat did not apply either, because the agent has no conversations. It processes one paper at a time.

Where this topic fits

Tracing sits inside the agent's existing Python code. The grouping follows the work: one paper is one session, each run of the agent on that paper is one trace, and the LLM-call steps inside a run are observations. Reading those traces is the step between running the agent and deciding what to change in it.

How it is applied, step by step

  1. The Langfuse Python SDK is added to the agent's existing code in a few lines. No separate service is set up.
  2. The arXiv id of the paper is used as the session id, so everything that happens for one paper is grouped together even though no chat exists.
  3. Each run on a paper becomes a trace. Its LLM steps (finding a GitHub URL, checking a project page as a fallback, classifying the paper and taking a majority vote) appear as observations under it.
  4. The engineer reads the rendered prompts in the traces to check what the model really saw, for example whether the GitHub link was present in the input of the extraction step.
  5. The traces show that a single classification call often gets a paper wrong. He changes the step to run five times in parallel and adds a majority vote.
  6. He then reviews 50 recent pull requests by hand in a spreadsheet, uses the traces to find the cause of the hallucinations he sees there, and adds the missing README text to the system prompt.

Why this approach fits

A session id is only a string that you choose, so it can stand for any unit of work that produces more than one trace. A batch agent has an obvious unit, the paper, and using it means a question about one paper leads to every run and every model call for it. Nested observations then show each of the four steps with its own input and output, which is how the unreliable classification step was found.

Limitation or tradeoff

Tracing showed where the problems were but did not measure quality. 4Common mistakes

  1. Ending a script, job or serverless function without flushing the SDK.

    Why it causes problems
    Observations are queued in memory and exported in the background. A process that exits first takes the queue with it, so the run leaves no trace or only part of one. The gap tends to appear in batch jobs and evaluation scripts, which are the runs you most want to inspect.
    How to recognise it
    Traces from the web service arrive but traces from cron jobs, notebooks or functions are missing or stop before the last step. Adding a pause at the end of the script makes them appear.
    How to fix it
    Call flush on the client before the process exits. In JS/TS, shut down the OpenTelemetry SDK at the end of the run, which delivers the spans that are still buffered.

  2. Setting the user id and session id only on the root span when sending plain OpenTelemetry.

    Why it causes problems
    Filters and aggregations in Langfuse now work on individual observations. A model call that lacks the user id is left out of that user's cost and of any evaluator rule that filters on the attribute, even though the trace as a whole looks complete.
    How to recognise it
    Filtering observations by user or session returns the root observation only. Cost per user is lower than the cost shown on the same user's traces.
    How to fix it
    With a Langfuse SDK, wrap the work in propagate_attributes. With plain OpenTelemetry, set the attributes as baggage and add a baggage span processor so that every span receives them, and keep sensitive values out of baggage because it travels to downstream services.

  3. Fetching the latest label in production, or hard-coding a version number in the code.

    Why it causes problems
    The latest label moves to every newly saved version, so a draft that somebody saved for testing reaches users as soon as the client caches refresh. A hard-coded version number has the opposite problem: every prompt change needs a code deployment, and the label workflow is bypassed.
    How to recognise it
    Production generations are linked to a prompt version that nobody promoted, or a prompt edit is followed by a pull request that only changes a number.
    How to fix it
    Fetch without a label in production, which resolves to the production label, and use latest or a staging label only in development and test builds. Promote and roll back by moving the production label.

  4. Treating an LLM judge as if it saw the whole trace and as if its scores were ground truth.

    Why it causes problems
    An observation-level evaluator receives one observation. If the retrieved documents are on a sibling observation, a groundedness judge is rating the answer against nothing and still returns a confident score. A judge that was never compared with human labels can also drift from what reviewers think.
    How to recognise it
    Judge reasoning that mentions missing context, scores that barely vary, or a dashboard that looks healthy while reviewers in the annotation queue keep rejecting answers.
    How to fix it
    Map every variable to data that exists on the matched observation, or record a summary of the context on the root observation and target that. Score a sample by hand and compare it with the judge before you rely on the trend, and repeat the comparison when the judge prompt or model changes.

  5. Putting the Docker Compose deployment into production unchanged.

    Why it causes problems
    The Compose file runs every component on one machine with no high availability, scaling or backups, and it ships with secrets that are marked to be changed. A full disk or a lost VM takes all traces, prompts and datasets with it, and prompts fetched at runtime are then served only from client caches and fallbacks.
    How to recognise it
    One VM hosts the web, worker, database and storage containers, the secrets still have their default values, and nobody can say when the last backup of Postgres and ClickHouse was taken.
    How to fix it
    Use Compose for local work and evaluation only. For production, deploy with the Helm chart or the Terraform modules, change every secret, use managed or replicated storage services, and test a restore.

python
from dataclasses import dataclass


@dataclass(frozen=True)
class Evaluation:
    name: str
    value: float
    comment: str = ""


@dataclass(frozen=True)
class ItemResult:
    item: dict
    output: str
    evaluations: tuple


class RegressionError(Exception):
    pass


def make_task(version):
    def task(*, item, **kwargs):
        return ANSWERS[version][item["id"]]
    return task


def contains_all(*, input, output, expected_output, **kwargs):
    missing = [phrase for phrase in expected_output if phrase.lower() not in output.lower()]
    comment = "missing: " + ", ".join(missing) if missing else "all required phrases present"
    return Evaluation(name="contains_all", value=0.0 if missing else 1.0, comment=comment)


def word_count(*, output, **kwargs):
    return Evaluation(name="word_count", value=float(len(output.split())))


def average(name):
    def run_evaluator(*, item_results, **kwargs):
        values = [e.value for result in item_results for e in result.evaluations if e.name == name]
        return Evaluation(name=f"avg_{name}", value=sum(values) / len(values))
    return run_evaluator


def run_item(item, task, evaluators):
    output = task(item=item)
    evaluations = tuple(
        evaluator(input=item["input"], output=output,
                  expected_output=item["expected_output"], metadata=item["metadata"])
        for evaluator in evaluators)
    return ItemResult(item, output, evaluations)


def run_experiment(*, name, data, task, evaluators, run_evaluators):
    item_results = [run_item(item, task, evaluators) for item in data]
    run_evaluations = tuple(evaluate(item_results=item_results) for evaluate in run_evaluators)
    return {"name": name, "item_results": item_results, "run_evaluations": run_evaluations}


def passed(result):
    return {r.item["id"] for r in result["item_results"]
            if any(e.name == "contains_all" and e.value == 1.0 for e in r.evaluations)}


def gate(baseline, candidate):
    required = {item["id"] for item in DATASET if item["metadata"]["required"]}
    failed_required = sorted(required - passed(candidate))
    regressed = sorted(passed(baseline) - passed(candidate))
    if failed_required or regressed:
        raise RegressionError(f"required cases failing: {failed_required}; regressed cases: {regressed}")


def report(result):
    print(f"== {result['name']}")
    for r in result["item_results"]:
        scores = {e.name: e for e in r.evaluations}
        print(f"{r.item['id']:<15} contains_all={scores['contains_all'].value:.0f} "
              f"words={scores['word_count'].value:>2.0f}  {scores['contains_all'].comment}")
    for e in result["run_evaluations"]:
        print(f"{e.name} = {e.value:.3f}")


if __name__ == "__main__":
    results = {
        version: run_experiment(
            name=f"support-prompt-{version}", data=DATASET, task=make_task(version),
            evaluators=[contains_all, word_count],
            run_evaluators=[average("contains_all"), average("word_count")])
        for version in ("v1", "v2")
    }
    for result in results.values():
        report(result)
    try:
        gate(results["v1"], results["v2"])
        print("GATE: pass")
    except RegressionError as error:
        print(f"GATE: fail ({error})")

Two things differ from the local version: the result is an object with item_results and run_evaluations attributes, not a dictionary, and the SDK's own RegressionError takes the result, the metric, its value and the threshold as keyword arguments.

Exercise 2

Run Langfuse locally, send a trace, score it and test prompt label resolution

Hands-onIntermediateAbout 1 h (estimate)

Run Langfuse on your own machine with Docker Compose and repeat the worked example against it, then explore how prompt labels resolve. You need git, Docker with Docker Compose (Docker Desktop on macOS or Windows), curl and Python 3.9 or later. Everything runs locally and nothing has to be paid for.

Use build_trace.py from the worked example. Work through these tasks in order and note what you observe at each step:

  1. Start Langfuse locally, create a user, an organisation, a project and a pair of API keys.
  2. Send the trace for ticket-4711/turn-1, then a second trace for ticket-4711/turn-2.
  3. Attach the boolean score answer_grounded to the draft-answer observation of the first trace.
  4. Create a text prompt named support-answer through the API without assigning any label, and find out which status code you get when you fetch it by the labels production and latest.
  5. Assign the production label to version 1 in the UI and fetch it again.

Requirements

  • Langfuse runs from the repository's docker-compose.yml file and the UI opens at http://localhost:3000.
  • Both traces are sent to the local OTLP endpoint with Basic Auth and the header x-langfuse-ingestion-version set to 4, and both belong to the session ticket-4711.
  • The score is created through the scores endpoint with the trace id and observation id that the script printed.
  • The prompt is created with a POST to /api/public/v2/prompts whose body contains only type, name and prompt, and it is fetched with GET /api/public/v2/prompts/support-answer and a label query parameter.
  • You record the HTTP status code of each prompt fetch before and after assigning the production label.

Expected behaviour

After two to three minutes the langfuse-web-1 container logs "Ready" and the UI is reachable. There is no default login, so the first step in the browser is Sign up.

Each ingestion request returns a status in the 200 range. The project then shows two traces named support-turn, each with a root observation and three children, and the session ticket-4711 contains both. The first trace's draft-answer generation shows the token usage, the cost of 0.001405 USD and the score answer_grounded.

According to the label-resolution rules in the documentation, the fetch with label=production returns 404 while no version carries that label, the fetch with label=latest returns 200, and after you assign production to version 1 the first fetch returns 200 with the prompt text and version 1.

Hint 1

The local OTLP endpoint is http://localhost:3000/api/public/otel/v1/traces. Set LANGFUSE_HOST to http://localhost:3000 and reuse the curl commands from the worked example unchanged.

Hint 2

API keys belong to a project. Create them in the project settings after you have created the organisation and the project.

Hint 3

Add -s -o /dev/null -w "%{http_code}\n" to a curl command to print only the status code.

Show solution

1. Start Langfuse. The documentation asks you to update the secrets in docker-compose.yml before the first start. Change every line marked # CHANGEME to a long random value.

bash
git clone https://github.com/langfuse/langfuse.git
cd langfuse
docker compose up

Wait until langfuse-web-1 logs "Ready". Open http://localhost:3000, choose Sign up, create an organisation and a project, and create API keys in the project settings.

2. Send two traces. In a second terminal, in the folder that holds build_trace.py:

bash
export LANGFUSE_PUBLIC_KEY="pk-lf-..."     # the keys of your local project
export LANGFUSE_SECRET_KEY="sk-lf-..."
export LANGFUSE_HOST="http://localhost:3000"

for turn in ticket-4711/turn-1 ticket-4711/turn-2; do
  python3 build_trace.py "$turn"
  curl -s -o /dev/null -w "%{http_code}\n" -X POST "$LANGFUSE_HOST/api/public/otel/v1/traces" \
    -u "$LANGFUSE_PUBLIC_KEY:$LANGFUSE_SECRET_KEY" \
    -H "Content-Type: application/json" \
    -H "x-langfuse-ingestion-version: 4" \
    --data-binary @trace.json
done

The script prints the trace id and the observation ids for each turn. For turn 1 they are 71cab3273b8b8d267cb7586d7f46f37a and, for draft-answer, 02dbeafb98c21abc.

3. Score the model call.

bash
curl -X POST "$LANGFUSE_HOST/api/public/scores" \
  -u "$LANGFUSE_PUBLIC_KEY:$LANGFUSE_SECRET_KEY" \
  -H "Content-Type: application/json" \
  -d '{"traceId": "71cab3273b8b8d267cb7586d7f46f37a", "observationId": "02dbeafb98c21abc",
       "name": "answer_grounded", "value": 1, "dataType": "BOOLEAN"}'

4. Create a prompt and fetch it by label.

bash
curl -X POST "$LANGFUSE_HOST/api/public/v2/prompts" \
  -u "$LANGFUSE_PUBLIC_KEY:$LANGFUSE_SECRET_KEY" \
  -H "Content-Type: application/json" \
  -d '{"type": "text", "name": "support-answer",
       "prompt": "Answer using only the policy text. Question: {{question}}"}'

for label in production latest; do
  curl -s -o /dev/null -w "$label %{http_code}\n" \
    "$LANGFUSE_HOST/api/public/v2/prompts/support-answer?label=$label" \
    -u "$LANGFUSE_PUBLIC_KEY:$LANGFUSE_SECRET_KEY"
done

A new version receives the latest label automatically, and nothing was promoted, so the expected output is production 404 and latest 200. This is the behaviour that makes a typo in a label fail loudly.

5. Promote and fetch again. Open the prompt in the UI, assign the production label to version 1 and rerun the loop. Both lines now end in 200. Fetch once without -o /dev/null to see the JSON, which contains the prompt text, "version": 1 and the labels.

Clean up. Stop the containers with Ctrl+C and docker compose down. Your local data stays in the Docker volumes until you remove them.

What you ran is the same architecture as a production deployment, squeezed onto one machine: the web and worker containers, Postgres, ClickHouse, Redis and an S3-compatible store. That is also why it is not a production setup: one disk and one machine hold everything.

  • Did the fetch by the production label return 404 before you assigned the label and 200 afterwards?
