MCP Primitives (Tools, Resources, Prompts)

MCP primitives are the fixed kinds of thing that a Model Context Protocol server and client can offer each other. A server offers tools (functions the model calls), resources (data the application reads) and prompts (templates the user picks). A client can offer elicitation, sampling and roots. Each kind is found through a listing or discovery request.

1Overview

Why it matters

The primitive you choose decides who is in charge. The model can call a tool on its own initiative. A resource normally enters the conversation because the host application or the user attaches it. A prompt normally runs because the user picks it. Put a destructive action behind the wrong one and it can fire when nobody asked. Put a reference document behind a tool the model never thinks to call and the data never shows up.

Support also differs from client to client. Anthropic's hosted MCP connector imports tools and nothing else, IDEs turn prompts into slash commands, and the July 2026 revision of the specification deprecated sampling and roots and changed how a server asks the client for input. Anyone who builds a server, picks servers for an agent or reviews what an agent is allowed to do needs to know which primitive is which, what a listing returns, and what each listed tool costs in context.

Key terms

Primitive
One of the fixed kinds of capability defined by MCP. Servers offer tools, resources and prompts, and clients offer elicitation, sampling and roots.
Tool
A named function with a JSON Schema for its arguments that a server exposes and a model can ask to have called.
Resource
A piece of data on a server that is identified by a URI, such as a file or a database schema, and that the host application can read and add to the model's context.
Resource template
A URI pattern with parameters, such as weather://forecast/{city}/{date}, that stands for a whole family of resources.
Prompt
A reusable template on a server that returns ready-made conversation messages when the user selects it and fills in its arguments.
Capability
A declaration by a server or client of which primitives and optional features it supports, so that the other side never calls something that is not there.
Elicitation
A client primitive that lets a server ask the user for input, either through a form or by sending the user to a web page.
Sampling
A client primitive that lets a server ask the client's language model for a completion. It is deprecated in specification revision 2026-07-28.
Roots
A client primitive that tells a server which folders the user is working in, as a list of file:// URIs. It is deprecated in specification revision 2026-07-28.
Cursor
An opaque string a server returns with one page of a list so that the client can ask for the next page.

2Explanation

Introduction

In Model Context Protocol (MCP) you met the three roles: a host application such as an IDE or a chat app, the client inside it, and a server that connects it to some outside system. This lesson is about what travels over that connection. A server cannot offer just anything. MCP defines a small, fixed set of kinds of thing, called primitives, and each kind has its own rule about who may use it.

Picture a workshop that you share with an assistant. Tools hang on the wall, and the assistant may pick one up whenever the job calls for it. Reference binders sit on a shelf, and somebody has to take one down and open it on the bench before it is any use. A drawer holds laminated job cards such as "weekly stock check", and you choose one and hand it over to start that job. What separates the three is who reaches for each.

An MCP server offers the same three things:

  • Tools are functions the model can call, such as create_issue. The model decides when.
  • Resources are pieces of data with an address, such as a file or a database schema. The host application decides when to read one, often because the user attached it.
  • Prompts are ready-made message templates, such as "review this pull request". The user decides when.

Traffic also runs the other way. A client can offer three primitives of its own, which a server may use while it is working on a request: elicitation (ask the user a question), sampling (ask the client's model for a completion) and roots (ask which folders are in scope).

None of this is hard-coded into the host. A client finds out what a server offers by asking, with listing requests such as tools/list. The rest of the lesson covers each primitive and its messages, how discovery and listing work, and how a server reaches the client primitives.

One note on versions before you start. The current specification revision is 2026-07-28, according to the MCP versioning page (opens in a new tab). It changed how discovery and the client primitives work, and it deprecated sampling and roots. A lot of deployed software still speaks 2025-11-25 or earlier, so where the two differ this lesson shows both.

How it works

Three server primitives and who controls each

The specification gives each server primitive a controller. Tools are model-controlled, resources are application-driven and prompts are user-controlled. The grid below adds the three client primitives, which are covered later in this section.

The label says who decides when a primitive is used. It does not say who wrote it, and the protocol does not enforce it: for every primitive the specification says hosts are free to expose it through any interface. Claude Code (opens in a new tab), for example, lets users reference resources by hand and also gives its model tools for listing and reading them.

Tools

A tool definition is what the model reads when it chooses, so it has the same parts as a function in Tool Calling: a name, a description and an inputSchema written in JSON Schema. Optional parts are a display title, an outputSchema, and annotations such as readOnlyHint that describe behaviour. Clients are told to treat annotations as untrusted unless they trust the server.

A call names the tool and passes arguments:

json
{"jsonrpc": "2.0", "id": 2, "method": "tools/call",
 "params": {"name": "get_weather", "arguments": {"location": "New York"}}}

The result holds a content array whose items are text, images, audio, links to resources or embedded resources. A tool that declares an outputSchema also returns matching JSON in structuredContent.

Failures travel on two channels, and picking the right one matters:

  • A protocol error is a JSON-RPC error object. Use it for an unknown tool or a malformed request.
  • A tool execution error is an ordinary result with isError: true and a message. Use it for a failed API call or an invalid value. Clients should pass these to the model so that it can correct itself, which is the recovery path described in The Agent Loop.

Resources

A resource is data with a URI, such as file:///project/README.md or a custom scheme like note://standup. resources/list returns descriptors: uri and name, plus optional title, description, mimeType and size. resources/read takes a URI and returns contents, each holding either text or a base64 blob.

When a whole family of resources differs only by a parameter, such as a city and a date, a server publishes a resource template instead of listing every member. A template is a URI pattern such as weather://forecast/{city}/{date}, found with resources/templates/list. The host fills in the parameters and reads the resulting URI. Resources can carry annotations (audience, priority, lastModified) that help a host decide what to include, and a client can subscribe to be told when one particular resource changes.

The official overview describes resources as passive, read-only data sources. That is why a host can let users attach them freely while it puts a confirmation step in front of tool calls.

Prompts

prompts/list returns each prompt's name, description and arguments. prompts/get takes a name and argument values and returns messages. Each message has a role (user or assistant) and content that can be text, an image, audio or an embedded resource. The host places those messages in the conversation.

"User-controlled" means the user chooses when a prompt runs. The text still comes from the server, so a prompt from a server you do not trust deserves the same caution as any other third-party text (see Prompt Injection and LLM Security).

Discovery and listing

A client learns what a server offers in four steps.

  1. Capabilities. The server declares which primitives it supports, for example {"tools": {"listChanged": true}, "resources": {}}. In revision 2026-07-28 the client reads this from server/discover, a request that every server must implement and that a client may skip. In 2025-11-25 and earlier, both sides exchanged capabilities once, in the initialize handshake of the earlier lifecycle (opens in a new tab) that opened every connection.
  2. Lists. For each supported primitive the client sends the list request. Results can be paginated: a response may include nextCursor, and the client sends that value back as cursor to get the next page. The server picks the page size, cursors are opaque, and a missing nextCursor marks the end.
  3. Freshness. In 2026-07-28 every list result carries ttlMs (how long the client may treat it as fresh) and cacheScope (public or private). A list must not differ from one connection to another, though it may depend on the credentials sent with the request. Tools should come back in a stable order so that clients and prompt caches can reuse them.
  4. Changes. A server that declared listChanged sends notifications/tools/list_changed (or the prompts or resources equivalent) when a list changes, and the client lists again. In 2026-07-28 the client opts in to these notifications by opening a subscriptions/listen stream.

Listing is not the same as loading. tools/list tells the host what exists. The host then decides which definitions go into the model's context, and every definition it loads is paid for in tokens on every model call (see Tokens and Context Windows). MCP's client guidance (opens in a new tab) describes the alternative, progressive discovery: keep the definitions on the host side, give the model a search tool, and load a definition only when it is needed. The guidance suggests switching once definitions pass a threshold, for example 1% to 5% of the context window.

Client primitives

PrimitiveWhat the server asks the client to doRequestStatus in 2026-07-28

RootsReport which file:// folders are in scoperoots/listDeprecated

A client declares which of these it supports, and a server must not use one that was not declared.

Elicitation has two modes. In form mode the server sends a message and a flat JSON Schema (strings, numbers, booleans and enum choices only), and the host renders a form. In URL mode, added in 2025-11-25, the server sends a link for the user to open, and what happens on that page never passes through the client. Every answer has an action: accept, decline or cancel. Secrets such as passwords and API keys must not be requested in form mode.

Sampling lets a server borrow the host's model. The server sends messages and optional model preferences. The client chooses the model, can show the request to the user, and returns the completion, so the server needs no API key of its own. The recommended replacement is to call a model provider's API directly.

Roots are a list of file:// URIs with optional names that tell a server which folders the user is working in. The specification calls them informational guidance and not an access-control mechanism. The recommended replacement is to pass paths as tool parameters, resource URIs or server configuration.

Both deprecated features still work. The deprecation registry (opens in a new tab) says neither can be removed before the first revision released on or after 28 July 2027. The same revision also deprecated the logging utility, which is outside the scope of this lesson.

How a server reaches the client

In 2025-11-25 and earlier the connection was a session. A server could send its own JSON-RPC request, such as elicitation/create, to the client in the middle of a tool call and wait for the reply.

Revision 2026-07-28 made the protocol stateless. Every request carries the protocol version and the client's capabilities in a _meta field (opens in a new tab), and servers no longer send requests. A server that needs something answers the client's own call with a result whose resultType is input_required:

json
{"resultType": "input_required",
 "inputRequests": {"confirm_delete": {"method": "elicitation/create", "params": {
   "mode": "form", "message": "Delete note 'standup'?",
   "requestedSchema": {"type": "object", "properties": {"confirm": {"type": "boolean"}}}}}},
 "requestState": "opaque-string-chosen-by-the-server"}

The client gathers the answers and sends the original call again with a new id. It adds inputResponses, keyed like inputRequests, and echoes requestState unchanged. The specification names this pattern multi round-trip requests (MRTR) and allows it on tools/call, resources/read and prompts/get only. Because the state passes through the client, a server must treat requestState as attacker-controlled input and protect it, for example with a signature, whenever it affects what the server does.

SDKs hide most of this, and a client or server can support both eras at once. What you need to keep in mind is which side asks, which side decides, and that a server must cope when the client declines the request or does not support the primitive at all.

Worked example: A notes server in plain Python that lists and uses all three server primitives

The server below keeps team notes. It offers one tool (add_note), one prompt (summarize_note) and every note as a resource (note://<title>). It follows revision 2026-07-28 and needs only the Python standard library (3.9 or later). A real server would use an SDK (see Building an MCP Server). Save it as notes_mcp.py.

python
import json

VERSION = "2026-07-28"
V_KEY = "io.modelcontextprotocol/protocolVersion"
C_KEY = "io.modelcontextprotocol/clientCapabilities"
NOTES = {"standup": "Ship the search fix by Friday."}
TOOL = {"name": "add_note", "description": "Create or replace a note.",
        "inputSchema": {"type": "object", "required": ["title", "text"],
                        "properties": {"title": {"type": "string"}, "text": {"type": "string"}}}}
PROMPT = {"name": "summarize_note", "description": "Summarize one note.",
          "arguments": [{"name": "title", "required": True}]}
FRESH = {"ttlMs": 60000, "cacheScope": "public"}  # caching hints, required on list results


class RpcError(Exception):
    def __init__(self, code, message, **data):
        self.error = {"code": code, "message": message, **({"data": data} if data else {})}


def note(title):
    if title not in NOTES:
        raise RpcError(-32602, f"Unknown note: {title}")
    return NOTES[title]


def call_tool(p):
    if p.get("name") != "add_note":
        raise RpcError(-32602, f"Unknown tool: {p.get('name')}")  # protocol error
    args = p.get("arguments", {})
    if not args.get("title") or not args.get("text"):  # execution error: the model can fix it
        return {"content": [{"type": "text", "text": "title and text are required."}],
                "isError": True}
    NOTES[args["title"]] = args["text"]
    return {"content": [{"type": "text", "text": f"Saved note://{args['title']}"}]}


def read_resource(p):
    text = note(p.get("uri", "").removeprefix("note://"))
    return {"contents": [{"uri": p["uri"], "text": text}], "ttlMs": 0, "cacheScope": "private"}


def get_prompt(p):
    text = "Summarize in two bullets: " + note(p.get("arguments", {}).get("title"))
    return {"messages": [{"role": "user", "content": {"type": "text", "text": text}}]}


METHODS = {
    "server/discover": lambda p: {"supportedVersions": [VERSION], **FRESH,
                                  "capabilities": {"tools": {}, "resources": {}, "prompts": {}}},
    "tools/list": lambda p: {"tools": [TOOL], **FRESH},
    "resources/list": lambda p: {"resources": [{"uri": f"note://{t}", "name": t} for t in NOTES],
                                 **FRESH},
    "prompts/list": lambda p: {"prompts": [PROMPT], **FRESH},
    "tools/call": call_tool, "resources/read": read_resource, "prompts/get": get_prompt,
}


def handle(request):
    try:
        params = request.get("params", {})
        meta = params.get("_meta", {})
        if V_KEY not in meta or C_KEY not in meta:
            raise RpcError(-32602, "Missing required _meta fields")
        if meta[V_KEY] != VERSION:
            raise RpcError(-32022, "Unsupported protocol version",
                           supported=[VERSION], requested=meta[V_KEY])
        if request["method"] not in METHODS:
            raise RpcError(-32601, f"Method not found: {request['method']}")
        result = {"resultType": "complete", **METHODS[request["method"]](params)}
        return {"jsonrpc": "2.0", "id": request["id"], "result": result}
    except RpcError as failure:
        return {"jsonrpc": "2.0", "id": request.get("id"), "error": failure.error}


LAUNCH = {"title": "launch", "text": "Go live 3 March."}
DEMO = [("server/discover", {}), ("tools/list", {}), ("resources/list", {}), ("prompts/list", {}),
        ("prompts/get", {"name": "summarize_note", "arguments": {"title": "standup"}}),
        ("tools/call", {"name": "add_note", "arguments": LAUNCH}),
        ("resources/read", {"uri": "note://launch"}),
        ("tools/call", {"name": "add_note", "arguments": {"title": "empty"}}),
        ("tools/call", {"name": "delete_note", "arguments": {"title": "launch"}})]

if __name__ == "__main__":
    meta = {V_KEY: VERSION, C_KEY: {}}
    for number, (method, params) in enumerate(DEMO, start=1):
        reply = handle({"jsonrpc": "2.0", "id": number, "method": method,
                        "params": {**params, "_meta": meta}})
        print(f"{number} -> {method} {json.dumps(params)}")
        print(f"   <- {json.dumps(reply.get('result') or reply['error'])}")

handle is the whole server: one request in, one response out. Running python3 notes_mcp.py plays the client. It sends nine requests and prints each result or error:

text
1 -> server/discover {}
   <- {"resultType": "complete", "supportedVersions": ["2026-07-28"], "ttlMs": 60000, "cacheScope": "public", "capabilities": {"tools": {}, "resources": {}, "prompts": {}}}
2 -> tools/list {}
   <- {"resultType": "complete", "tools": [{"name": "add_note", "description": "Create or replace a note.", "inputSchema": {"type": "object", "required": ["title", "text"], "properties": {"title": {"type": "string"}, "text": {"type": "string"}}}}], "ttlMs": 60000, "cacheScope": "public"}
3 -> resources/list {}
   <- {"resultType": "complete", "resources": [{"uri": "note://standup", "name": "standup"}], "ttlMs": 60000, "cacheScope": "public"}
4 -> prompts/list {}
   <- {"resultType": "complete", "prompts": [{"name": "summarize_note", "description": "Summarize one note.", "arguments": [{"name": "title", "required": true}]}], "ttlMs": 60000, "cacheScope": "public"}
5 -> prompts/get {"name": "summarize_note", "arguments": {"title": "standup"}}
   <- {"resultType": "complete", "messages": [{"role": "user", "content": {"type": "text", "text": "Summarize in two bullets: Ship the search fix by Friday."}}]}
6 -> tools/call {"name": "add_note", "arguments": {"title": "launch", "text": "Go live 3 March."}}
   <- {"resultType": "complete", "content": [{"type": "text", "text": "Saved note://launch"}]}
7 -> resources/read {"uri": "note://launch"}
   <- {"resultType": "complete", "contents": [{"uri": "note://launch", "text": "Go live 3 March."}], "ttlMs": 0, "cacheScope": "private"}
8 -> tools/call {"name": "add_note", "arguments": {"title": "empty"}}
   <- {"resultType": "complete", "content": [{"type": "text", "text": "title and text are required."}], "isError": true}
9 -> tools/call {"name": "delete_note", "arguments": {"title": "launch"}}
   <- {"code": -32602, "message": "Unknown tool: delete_note"}
  • Steps 1 to 4 are discovery. The client learns the capabilities, then lists each primitive.
  • Steps 5 to 7 are use. The user's choice triggers prompts/get, the model's choice triggers tools/call, and the host reads note://launch, which exists only because of step 6.
  • Steps 8 and 9 fail differently. A missing argument returns a result with isError: true that the model can read and fix. An unknown tool returns a JSON-RPC error.

Edge cases and limitations

A client that imports only tools never sees your resources or prompts
Anthropic's MCP connector documentation states that, of the MCP feature set, only tool calls are supported. OpenAI's guide to remote MCP servers in the Responses API covers importing and calling tools and does not describe resources or prompts. A server whose essential data is reachable only as a resource or a prompt can be half invisible to such clients. If you need to reach them, give the same data a tool-based route as well, for example a read tool next to the resource.
Two servers expose a tool with the same name
The specification scopes tool-name uniqueness to a single server, so two servers can both expose a tool called search. A host that connects to both and passes the two definitions to the model unchanged cannot tell which server a call is meant for. The specification tells clients and proxies to disambiguate, for example by prefixing the tool name with a server identifier, and warns that the server's self-reported name is not guaranteed to be unique.
An empty cursor is still a cursor
Pagination ends when nextCursor is missing from the response. The specification states that an empty string is a valid cursor and must not be treated as the end, that the server chooses the page size, and that clients must not parse or modify cursors. A client that stops at the first page, or that tests the cursor for truthiness, silently loses part of the list.
The tool list changes in the middle of a conversation
A server can add or remove tools at any time. Claude Code documents that it fetches the updated list when a list_changed notification arrives, and Anthropic's MCP connector offers a beta option to pin the recorded list so that the model sees the same tools for the whole conversation. MCP's client guidance adds that changing the tool definitions mid-conversation invalidates provider prompt caches. Decide per application whether fresh tools or a stable list matters more.
Accepting a URL-mode elicitation does not mean it finished
In URL mode an accept action only says the user agreed to open the link. The sign-in or payment happens outside the client, which is not told the outcome. In revision 2026-07-28 the client finds out by retrying the original call, and the server may answer with another input_required result if the user has not finished. Hosts should give the user a way to retry or cancel.
Annotations and roots are statements, not guarantees
A readOnlyHint annotation is the server describing itself, and the specification tells clients to treat annotations as untrusted unless the server is trusted. Roots work the same way in the other direction: the client states which folders are in scope, and the specification says the protocol does not enforce that a server stays inside them. Enforce limits where the code runs, with path checks, file permissions or a sandbox.

When to use it, and when something simpler is enough

Use it when

  • Use a tool when the model should decide, in the middle of a task, to run an action or a lookup whose arguments it has to fill in, such as searching issues or creating a record.
  • Use a resource when the data has a stable address, such as a file, a schema or a record, and the user or the host should choose whether it enters the context.
  • Use a prompt when a person starts a repeatable workflow by name and you want its wording, arguments and attached context to be the same every time.
  • Use elicitation when a call cannot finish without a value or a decision that only the user has, such as confirming a deletion or choosing between two matches.

Think twice when

  • Avoid making a resource or a prompt the only route to something essential when your users' clients import tools only, as Anthropic's MCP connector does.
  • Avoid building new servers on sampling or roots. Both are deprecated in revision 2026-07-28, so call a model API directly and take paths as tool parameters or configuration.
  • Avoid form-mode elicitation for passwords, API keys or payment details. The specification requires URL mode for those.
  • Avoid one tool per API endpoint when the model needs only a few of them. Every tool a host loads costs context on every model call.

A simpler alternative. Expose a small set of well-described tools and nothing else. Every client described in this lesson supports tools, and they are the only primitive that Anthropic's hosted MCP connector imports. This stops being enough when users need to choose context themselves (resources), start standard workflows by name (prompts), or answer a question in the middle of a call (elicitation). If one application owns both the model call and the functions, plain tool calling without MCP is simpler still.

Key takeaways

  • A server offers tools, resources and prompts, and what separates them is who decides to use each one: the model, the host application and the user.
  • Clients find everything by asking, through capabilities and the list requests tools/list, resources/list and prompts/list, whose results can be paginated, cached and refreshed after a list-changed notification.
  • A listed tool is not automatically in the model's context. The host chooses what to load, and every loaded definition costs tokens on every model call.
  • Elicitation, sampling and roots are things a server asks of the client. In revision 2026-07-28 sampling and roots are deprecated, and requests arrive as input_required results that the client answers by sending the call again.
  • A failure the model can fix belongs in a tool result with isError set to true, and JSON-RPC errors are for unknown tools and malformed requests.
  • Clients differ in which primitives they implement, so check your target hosts and give essential data a tool-based route.

Example 1 of 5

GitHub MCP Server deciding what its lists contain with toolsets, read-only mode and scope filtering

GitHubDocumented in an open-source project

GitHub's official MCP server connects AI tools to repositories, issues, pull requests, Actions and other parts of the platform. It runs as a remote server hosted by GitHub and as a local binary. The repository README and its Server Configuration Guide document how operators control which primitives the server registers. [21][22][1][19]

The problem

The server covers a large part of the GitHub API. Its README lists more than twenty toolsets, each grouping related tools. If all of them were listed to every client, the model would choose from a long menu and the definitions would fill context before any work started. The README says that enabling only the toolsets you need can help the LLM with tool choice and reduce the context size. Some operators also want a server that cannot change anything.

Where this topic fits

The control sits at discovery. Configuration given at start-up (local server) or with each connection (remote server) decides which tools, resources and prompts the server registers, and so what tools/list and the other list requests return. Everything after that, including which tools the host loads and which the model calls, works from the filtered list.

How it is applied, step by step

  1. The operator names the toolsets to enable, with the --toolsets flag or the GITHUB_TOOLSETS variable on the local server, or the X-MCP-Toolsets header or a URL path on the remote server.
  2. With no configuration the server registers its default toolsets: context, repos, issues, pull_requests and users.
  3. Each toolset brings in a group of related tools, and according to the README the relevant resources and prompts as well, so one switch covers all three server primitives.
  4. Individual tools can be added or excluded by name. Read-only mode then removes every write tool, even one that was requested explicitly.
  5. When the server is started with a classic personal access token, it checks the token's scopes and hides the tools that need a scope the token lacks.
  6. A client that sends tools/list receives only what survived these filters. A tool that is not listed cannot be loaded into the model's context or called by mistake.

Why this approach fits

Filtering at the listing stage deals with cost and safety in one move. A tool that is never listed costs no context and cannot be chosen, which is a stronger guarantee than asking the model not to use it. Grouping by product area lets an operator think in features such as "issues" instead of dozens of tool names. Filtering by token scope matches the specification's rule that a list may depend on the authorization presented with a request.

Limitation or tradeoff

The choice is made before the conversation starts, so the operator has to predict what a session will need. Too narrow a set leaves the model without a tool, and it may report that the task is impossible. Hiding a tool is also not the same as removing a permission. The configuration guide says that for token types other than classic personal access tokens and OAuth no filtering happens, all tools are shown and the GitHub API enforces permissions. What the credential may do is decided by GitHub's authorization, not by the tool list.

What the sources document

  • The README says the server supports enabling or disabling groups of functionality with the --toolsets flag, that enabling only the toolsets you need can help the LLM with tool choice and reduce the context size, and that toolsets are not limited to tools: relevant MCP resources and prompts are also included where applicable. [21]
  • MCP's client best-practices guidance says that when a host passes the tool definitions of every connected server to the model at the start of a conversation, hundreds of tools can use up the majority of the context window before the model has read the user's message, and it describes progressive discovery as the alternative. Visual Studio Code giving each MCP primitive its own control surface

MicrosoftDocumented in official docs

Visual Studio Code acts as an MCP host for its chat and agent features. Its user documentation for adding MCP servers and its MCP developer guide describe how the editor surfaces tools, resources, prompts, elicitation, sampling and roots. [24][25][6][14]

The problem

A developer installs servers from many publishers into one editor. The editor has to let its agent use server tools without surprising the user, let the user pull server data into a chat on purpose, make server-defined workflows easy to find, and stop a server from spending the user's model subscription unnoticed.

Where this topic fits

The mapping happens after discovery. Once VS Code has listed a server's tools, resources and prompts, it routes each primitive to the part of the interface that belongs to its controller: the agent for tools, the context picker for resources and the chat input for prompts. Requests that a server makes of the client (sampling, elicitation, roots) get their own permission and information paths.

How it is applied, step by step

  1. After the user trusts and starts a server, VS Code discovers the server's tools and makes them available in chat.
  2. Tools are used in agent mode, where they are invoked as the task needs them. The user can switch individual tools on or off in the tools picker.
  3. Before a tool runs, VS Code shows a confirmation dialog in which the user can edit the arguments the model generated. Tools marked with the readOnlyHint annotation skip the dialog.
  4. Resources are attached by the user through Add Context and then MCP Resources, or opened with the MCP Browse Resources command. For a resource template, VS Code asks for the parameters in a Quick Pick.
  5. Prompts appear as slash commands. The user types a slash, the server name, a dot and the prompt name in the chat input. The user documentation writes the command as /<MCP server>.<prompt> and the developer guide as mcp.servername.promptname.
  6. The first time a server makes a sampling request, the user is asked to authorize that server to use their models, and can later restrict which models it may use.
  7. VS Code also tells the server which workspace root folders are open, which is the roots primitive.

Why this approach fits

The three surfaces line up with the specification's control labels. A slash command cannot fire by itself, and attaching a resource is something the user visibly does, so neither needs a gate. Tool calls are the one thing the model starts on its own, and that is where VS Code puts the confirmation dialog. Asking for permission per server before sampling is the client keeping control of model access, which is the design reason the specification gives for routing completions through the client.

Limitation or tradeoff

The readOnlyHint that skips the confirmation dialog is supplied by the server, and the specification tells clients to treat annotations as untrusted unless the server is trusted. The protection is only as good as the decision to trust the server. Sampling and roots are deprecated in revision 2026-07-28. The developer guide links to the 2025-06-18 specification and does not mention 2026-07-28, so a server that depends on VS Code providing them should plan to call a model API itself and take paths as parameters. A server also cannot assume other hosts offer the same surfaces.

  • The user documentation says resources are attached to a chat request by selecting Add Context and then MCP Resources, or with the MCP: Browse Resources command, and that prompts are used by typing /<MCP server>.<prompt> in the chat input. The developer guide adds that for a resource template the user is prompted for the required parameters in a Quick Pick, and writes the prompt command as mcp.servername.promptname. [24][25]
  • The developer guide says users can edit model-generated input parameters in the tool confirmation dialog and that the dialog is shown for all tools that are not marked with the readOnlyHint annotation. [25]

The Filesystem reference server taking its allowed directories from the client's roots

Model Context Protocol projectDocumented in an open-source project

The Filesystem server in the official modelcontextprotocol/servers repository gives a model tools for reading, writing and searching files. Its README documents how it decides which directories it may touch, and the Claude Code documentation describes the client side of the same exchange. [23][26][7][14][13]

The problem

A file server must not read or write outside the folders the user intends, but the right folders differ from project to project. If they are fixed as command-line arguments, the user has to edit the server configuration and restart the server every time the working folder changes.

Where this topic fits

This is a client primitive at work. In a handshake-era session the server uses roots straight after initialization, before it serves any file tool, and again whenever the client reports a change. The information flows from client to server, the opposite direction from tools, resources and prompts.

How it is applied, step by step

  1. The server starts with the directories given as command-line arguments, or with an empty list of allowed directories when none are given.
  2. During initialization the server checks whether the client declared the roots capability.
  3. If it did, the server sends a roots/list request and the client answers with its configured roots as file URIs.
  4. The server replaces all of its allowed directories with the roots the client reported.
  5. When the client sends a roots list_changed notification, the server asks for the roots again and replaces its allowed directories once more, with no restart.
  6. Every file operation is checked against the allowed directories, so the enforcement happens in the server's own code.
  7. On the client side, Claude Code answers roots/list with the directory the session was launched in plus any additional working directories the user has granted.

Why this approach fits

The client knows which project the user has open, and the server does not. Letting the client state the scope keeps that knowledge in one place and lets it change without a restart. The division of labour is also sound: the client says where to work, and the server's own path checks do the enforcing.

Limitation or tradeoff

Nothing in the protocol forces a server to respect roots. The specification describes them as informational guidance and not as an access-control mechanism, so they prevent accidents by well-behaved servers and do nothing against a malicious one. The feature is also deprecated as of revision 2026-07-28, which removed the roots list_changed notification. The recommended migration is to pass directories through tool parameters, resource URIs or server configuration, which the server's command-line arguments already allow.

What the sources document

  • The README says directories can be specified through command-line arguments or dynamically through roots, and that roots notified by the client completely replace any server-side allowed directories when provided. [23]
  • The README describes the flow: during initialization the server checks whether the client supports the roots protocol, requests roots with roots/list, and requests them again when the client sends notifications/roots/list_changed. [23]
  • The Claude Code documentation says it answers roots/list with the session's launch directory plus every additional working directory the user has granted, and sends notifications/roots/list_changed when that set changes. [26]
  • The specification says roots are informational guidance rather than an access-control mechanism and that the protocol does not enforce that servers stay within roots. [7]
  • The deprecation registry lists Roots as deprecated in 2026-07-28, with the migration path of passing directories or files via tool parameters, resource URIs or server configuration, and earliest removal in the first revision released on or after 2027-07-28. The revision's changelog also lists the removal of the notifications/roots/list_changed notification. [14][13]

Example 4 of 5

Claude Code answering server elicitation requests with dialogs and hooks

AnthropicDocumented in official docs

Claude Code is Anthropic's coding agent for the terminal. Its MCP guide and its hooks reference document what happens when a connected MCP server asks for user input in the middle of a task. [26][27][5][12]

The problem

A server sometimes cannot finish a tool call with the arguments the model supplied. It may need a value that only the person has, or a sign-in that has to happen in a browser. The model should not invent the value, and a session that runs unattended needs a way to answer without a person at the keyboard.

Where this topic fits

Elicitation sits inside a tool call, between the request and its final result. Claude Code is the client, so it receives the server's request, collects the answer and passes it back. The tool call is only the carrier: the primitive in use is elicitation, which the client offers to the server.

How it is applied, step by step

  1. While handling a call, the server sends an elicitation request that carries a message and either a form schema or a URL.
  2. For form mode, Claude Code shows a dialog with the fields the server defined. For URL mode, it asks whether to open the link in the browser.
  3. The user's choice goes back to the server as one of three actions. Submitting sends accept with the field values, choosing Decline sends decline, and pressing Esc sends cancel.
  4. A team can register an Elicitation hook, matched on the server's name, that answers a known question from a script so that no dialog appears.
  5. On connections that use revision 2026-07-28, Claude Code declares that it supports both form and URL elicitation in the capabilities it sends, so the server knows it may ask.
  6. Under that revision the question arrives in an input_required result and the answer returns on the retried call, as the specification describes. The server then completes the tool call.

Why this approach fits

The server asks at the moment it knows exactly what is missing, which keeps the model from guessing and keeps the tool's input schema small. The three-way answer lets a server tell a refusal from a dismissed dialog and react differently. Hooks keep the same server usable in scripted runs, where a dialog would block for ever.

Limitation or tradeoff

The client can only show what the server asks. The specification forbids servers from requesting passwords, API keys or payment details in form mode, but it is the user who has to refuse a form that asks for one. The hooks reference notes that a hook which returns accept for a URL-mode request skips the dialog, so the URL never opens. A server also cannot count on elicitation being available: other clients may not declare it, and then the server needs another way to finish or a clear error.

What the sources document

  • The Claude Code MCP guide says that when a server requests structured input mid-task, Claude Code displays an interactive dialog and passes the response back to the server, in form mode with fields defined by the server or in URL mode by asking whether to open a link in the browser. [26]
  • The hooks reference says an Elicitation hook, matched against the MCP server name, can answer the request for the user, decline or cancel it, and that for a URL-mode request a hook that returns accept skips the dialog so the URL never opens. [27]
  • The guide says that on connections using protocol revision 2026-07-28 Claude Code declares elicitation with both form and url in its client capabilities, and that its v2 runtime asks servers whether they support the newer revision and uses it with those that do. [26]
  • The specification says a client that supports both eras should detect a server's era, on stdio by probing with server/discover and falling back to the initialize handshake for a legacy server. [12]
  • The specification says servers must not use form mode elicitation to request sensitive information such as passwords, API keys, access tokens or payment credentials, and must use URL mode for those interactions. [5]

Example 5 of 5

Anthropic's MCP connector and OpenAI's Responses API importing tool lists from remote servers

Anthropic and OpenAIDocumented in official docs

Both model APIs can connect to a remote MCP server on the developer's behalf: the MCP connector (beta) in Anthropic's Messages API and the MCP tool in OpenAI's Responses API. Each vendor's documentation describes how a server's tool list is fetched, filtered and kept across turns. [28][29]

The problem

A backend developer wants a model to use the tools of a remote MCP server without writing and running an MCP client. An API request has no user interface, so there is nowhere to show a resource picker or a slash command. Requests are also separate from one another, so the platform has to decide when to list the tools again and what happens if the server's list changes between turns.

Where this topic fits

The API platform takes the client role. It lists the remote server's tools, places the definitions in the model's context, and makes the tool call when the model selects one. Discovery and listing happen on the vendor's servers, and the result of the listing is returned to the developer as part of the response.

How it is applied, step by step

  1. The developer names the remote server in the request: an entry in mcp_servers plus an mcp_toolset for Anthropic, or an MCP tool with the server's URL for OpenAI.
  2. The platform asks the server for its tools. OpenAI returns the result as an mcp_list_tools item, and Anthropic, with its newer beta header, returns an mcp_tool_listing block.
  3. The developer narrows what the model sees, with allowed_tools on OpenAI or with enabled flags in the toolset's default_config and configs on Anthropic.
  4. The listing stays in the conversation. While the mcp_list_tools item remains in context, OpenAI does not fetch the list again, and Anthropic reuses a recorded listing that is sent back unchanged.
  5. When the model picks a tool, the platform calls the server and reports the call and its result in the response, as an mcp_call item or as mcp_tool_use and mcp_tool_result blocks.
  6. OpenAI asks for the developer's approval before data is shared with the remote server unless the developer changes the require_approval setting.

Why this approach fits

Tools are the model-controlled primitive, so they work with no interface at all, which is the situation of an API call. Returning the listing in the response turns discovery into data that the developer can inspect, store and pin. An allowlist applies least privilege at the listing stage, before a tool definition reaches the model.

Limitation or tradeoff

Only tools cross this bridge. Anthropic's documentation states that tool calls are the only part of the MCP specification the connector supports and that the server must be reachable over public HTTP, and it points developers who need prompts or resources to client-side helpers. A recorded or pinned list can also go stale: if the server removes or changes a tool, the model keeps seeing the old definition until the developer refreshes it. OpenAI's guide warns that remote servers are third parties that can change how their tools behave.

What the sources document

  • Anthropic's documentation states that, of the feature set of the MCP specification, only tool calls are currently supported, and that the server must be publicly exposed through HTTP, so local STDIO servers cannot be connected directly. [28]
  • The same page shows an allowlist made by setting enabled to false in default_config and enabling named tools in configs, and recommends denylisting write or destructive tools when building read-only assistants. [28]
  • With the mcp-client-2026-09-15 beta header, a response starts with an mcp_tool_listing block for each server the API asked, and copying a block's tools into the toolset's tools field pins the list so that the API does not ask the server for its tools. [28]
  • OpenAI's guide says that as long as the mcp_list_tools item is present in the context of a request, the API will not fetch the list of tools from the MCP server again at each turn, and that allowed_tools imports only a subset of a server's tools. [29]
  • OpenAI's guide says that by default it will request approval before any data is shared with a remote MCP server, and that the Responses API works with remote MCP servers that support the Streamable HTTP or HTTP/SSE transports. [29]

4Common mistakes

  1. Exposing everything as a tool, including reference documents and workflows that a person starts.

    Why it causes problems
    The model has to guess that a tool such as get_style_guide exists and is worth calling, so reference data often never reaches the conversation. A workflow wrapped in a tool runs when the model decides, not when the user asks. Every extra definition also takes context on every model call.
    How to recognise it
    Tools that take no arguments and return the same text every time, tool names that end in docs or guide, and users pasting long instructions into chat to trigger a routine that never varies.
    How to fix it
    Publish addressable data as resources and user-started routines as prompts. Keep a matching read tool only if you must serve clients that import tools alone.

  2. Assuming every client implements every primitive.

    Why it causes problems
    A server that needs elicitation, resources or prompts works in one host and fails or goes unused in another. Anthropic's hosted MCP connector imports only tools, and a client that never declared elicitation cannot be asked a question.
    How to recognise it
    A feature that works in an IDE but not through an API integration, capability errors such as code -32021 in server logs, or prompts and resources that usage logs show nobody has ever requested.
    How to fix it
    Read the capabilities the client declared before using a client primitive, and give each essential function a route that needs only tools, such as a required argument in place of a form.

  3. Reporting a failed tool run as a JSON-RPC error, or letting an exception escape the handler.

    Why it causes problems
    The specification says clients should pass tool execution errors to the model but only may pass protocol errors. A bad argument that comes back as a protocol error can end the run, although the model could have fixed the call if it had seen the message.
    How to recognise it
    An agent that stops at the first invalid argument instead of retrying, and error objects in your traces where a tool result with a readable message should be.
    How to fix it
    Return a normal result with isError set to true and a message that says what was wrong and what a valid call looks like. Keep JSON-RPC errors for unknown tools and malformed requests.

  4. Treating roots, tool annotations or a filtered tool list as a security boundary.

    Why it causes problems
    All three are statements by one side that the other side cannot verify. Roots do not stop a server from opening other paths, a readOnlyHint does not stop a tool from writing, and a hidden tool does not remove what the underlying credential is allowed to do.
    How to recognise it
    A file server with no path validation of its own, approval rules that depend only on annotations from servers nobody reviewed, or a broad API token behind a server that lists three tools.
    How to fix it
    Enforce limits where the code runs: validate paths in the server, run local servers in a sandbox, and issue credentials with the narrowest scopes the tools need.

  5. Reading only the first page of a list, or deciding the end of the list from the cursor's value.

    Why it causes problems
    A server chooses its own page size, so a client that ignores nextCursor silently drops tools, resources or prompts. A client that treats an empty-string cursor as the end does the same on servers that use one.
    How to recognise it
    A client shows a round number of tools for a server that has more, or the tools missing from the model's view are always the ones at the end of the server's list.
    How to fix it
    Loop until the response has no nextCursor field, pass each cursor back unchanged, and test the loop against a server that pages after one or two items.

  6. Loading every listed tool definition into the model's context.

    Why it causes problems
    Definitions are sent on every model call. With several servers connected they can take a large share of the context window before the user has typed anything, which raises cost and makes tool choice worse.
    How to recognise it
    A high input-token count on the first request of a session, a long tools array in the request log, and the model picking a similar tool from the wrong server.
    How to fix it
    Allowlist the tools a task needs, or defer definitions behind a search step and load them on demand. Enable only the server toolsets you use.

Exercise 1

Add a delete tool that asks the user to confirm through an input_required round trip

CodingIntermediateAbout 50 min (estimate)Hypothetical scenario

Start from notes_mcp.py in the worked example. In a new file, notes_confirm.py, import it and add a second tool, delete_note. Deleting cannot be undone, so the server must get the user's confirmation through elicitation, using the input_required round trip of revision 2026-07-28. The server must remember nothing between the first call and the retry.

A client that supports form elicitation declares it in the _meta of every request:

json
{"io.modelcontextprotocol/clientCapabilities": {"elicitation": {"form": {}}}}

A retry is the first call again, with a new id and two more fields in params:

json
{"inputResponses": {"confirm_delete": {"action": "accept", "content": {"confirm": true}}},
 "requestState": "<the string the server returned>"}

Write a small driver at the bottom of the file that adds a second note, launch, and then makes six tools/call requests for delete_note: one for standup without the elicitation capability, one with it, a retry that declines, a retry for launch that reuses the state issued for standup, a retry for standup that accepts, and a last plain call for standup. You need only the Python standard library.

Requirements

  • tools/list returns both add_note and delete_note, each with an input schema.
  • Calling delete_note for a title that does not exist returns a tool execution error (a result with isError true) that names the notes that do exist.
  • If the request did not declare the elicitation capability, the server returns JSON-RPC error -32021 whose data.requiredCapabilities is an object with an elicitation key.
  • A first call from a capable client returns resultType input_required with one form-mode elicitation/create request under the key confirm_delete and a requestState, and the note is still there.
  • The requestState is bound to the note title with an HMAC, and a retry whose state does not match its title is rejected with JSON-RPC error -32602.
  • A retry deletes the note only when the action is accept and confirm is true. A decline, a cancel or a false value returns a normal result that says the note was kept.
  • Running the file with the argument serve reads one JSON-RPC request per line from standard input and prints one response per line.

Expected behaviour

The six calls print, in order: an error with code -32021; an input_required result containing the question and a requestState that starts with standup.; a complete result saying the note was kept; an error with code -32602; a complete result Deleted note://standup; and a result with isError: true saying there is no note titled standup and listing launch.

Hint 1

handle builds its result as a dictionary that starts with resultType complete and then merges in what your function returns, so returning your own resultType key replaces the default.

Hint 2

Sign the title with hmac.new(secret, title.encode(), hashlib.sha256).hexdigest() and compare with hmac.compare_digest. The state can simply be the title, a dot and the digest.

Hint 3

Order the checks: does the note exist, did the client declare elicitation, is this a first call or a retry, is the state valid, and only then what the user answered.

Hint 4

Replace entries in the METHODS dictionary of the imported module instead of editing notes_mcp.py.

Show solution

Save this next to notes_mcp.py as notes_confirm.py.

python
import hashlib
import hmac
import json
import sys

import notes_mcp as base

SECRET = b"demo-secret"  # a real server loads a random key from its configuration
DELETE = {"name": "delete_note", "description": "Delete a note after the user confirms.",
          "inputSchema": {"type": "object", "required": ["title"],
                          "properties": {"title": {"type": "string"}}}}


def sign(title):
    digest = hmac.new(SECRET, title.encode(), hashlib.sha256).hexdigest()
    return f"{title}.{digest}"


def text_result(text, is_error=False):
    return {"content": [{"type": "text", "text": text}], "isError": is_error}


def delete_note(p):
    title = p.get("arguments", {}).get("title", "")
    if title not in base.NOTES:
        return text_result(f"No note titled {title!r}. Existing: {', '.join(base.NOTES)}", True)
    if "elicitation" not in p["_meta"][base.C_KEY]:
        raise base.RpcError(-32021, "Server requires the elicitation capability for this request",
                            requiredCapabilities={"elicitation": {}})
    if "inputResponses" not in p:  # first attempt: ask, and keep nothing on the server
        question = {"method": "elicitation/create", "params": {
            "mode": "form", "message": f"Delete note '{title}'? This cannot be undone.",
            "requestedSchema": {"type": "object", "required": ["confirm"],
                                "properties": {"confirm": {"type": "boolean"}}}}}
        return {"resultType": "input_required", "inputRequests": {"confirm_delete": question},
                "requestState": sign(title)}
    if not hmac.compare_digest(p.get("requestState", ""), sign(title)):
        raise base.RpcError(-32602, "requestState does not match this request")
    answer = p["inputResponses"].get("confirm_delete", {})
    if answer.get("action") == "accept" and answer.get("content", {}).get("confirm") is True:
        del base.NOTES[title]
        return text_result(f"Deleted note://{title}")
    return text_result(f"Kept note://{title}: the user did not confirm.")


def call_tool(p):
    return delete_note(p) if p.get("name") == "delete_note" else base.call_tool(p)


base.METHODS["tools/list"] = lambda p: {"tools": [base.TOOL, DELETE], **base.FRESH}
base.METHODS["tools/call"] = call_tool


def send(number, title, capabilities, **extra):
    params = {"name": "delete_note", "arguments": {"title": title}, **extra,
              "_meta": {base.V_KEY: base.VERSION, base.C_KEY: capabilities}}
    reply = base.handle({"jsonrpc": "2.0", "id": number, "method": "tools/call", "params": params})
    body = reply.get("result") or reply["error"]
    print(f"{number} <- {json.dumps(body)}")
    return body


if __name__ == "__main__":
    if sys.argv[1:] == ["serve"]:
        for line in sys.stdin:  # stdio transport: one JSON-RPC message per line
            print(json.dumps(base.handle(json.loads(line))), flush=True)
        sys.exit()
    base.NOTES["launch"] = "Go live 3 March."
    can_ask = {"elicitation": {"form": {}}}
    send(1, "standup", {})
    state = send(2, "standup", can_ask)["requestState"]
    yes = {"confirm_delete": {"action": "accept", "content": {"confirm": True}}}
    send(3, "standup", can_ask, inputResponses={"confirm_delete": {"action": "decline"}},
         requestState=state)
    send(4, "launch", can_ask, inputResponses=yes, requestState=state)
    send(5, "standup", can_ask, inputResponses=yes, requestState=state)
    send(6, "standup", can_ask)

Why it is built this way:

  • Call 1 fails before any question is sent. A server must not use a client primitive that the request did not declare, and -32021 tells the client exactly which capability is missing.
  • Call 2 deletes nothing and stores nothing. Everything the server needs to continue is in requestState, which the client must echo back unchanged.
  • Call 4 shows why the state is signed. Without the HMAC check, a client could collect a "yes" for one note and replay it against another. The specification tells servers to treat requestState as attacker-controlled input.
  • Calls 3 and 6 are ordinary results. A user saying no is not an error, and a missing note is a tool execution error that the model can read and act on.

A production server would add an expiry time and the user's identity to the signed state, as the specification recommends, and would load the key from configuration.

Exercise 2

Choose a primitive for each capability of a release-desk server

DesignBeginnerAbout 30 min (estimate)Hypothetical scenario

A platform team is designing an MCP server for its internal release desk. It will be used from an IDE that supports every primitive and from a backend service that connects through a hosted API connector, which imports tools only. The server is new, so it targets revision 2026-07-28.

The team lists eight things the server should do:

  1. Provide the deployment runbook, a Markdown document that changes about once a month.
  2. Report the current status of a named service.
  3. Roll a service back to its previous version.
  4. Offer a "prepare release notes" routine that the release manager starts by hand with a version number.
  5. Provide the configuration file for a named environment, such as staging or production.
  6. Record a reason before any rollback. The model often does not know the reason.
  7. Shorten 500 lines of deployment log before they are returned.
  8. Know which repository checkout the user is working in.

For each item, choose a primitive (or decide that none fits), say who decides when it is used, name the MCP messages involved, and say what the backend service that imports only tools will get.

Requirements

  • Every item names one primitive or states clearly why no primitive should be used.
  • Every item says who decides when the capability is used.
  • Every item names the list or use request involved, such as resources/read or tools/call.
  • Items that rely on resources, prompts or elicitation include a fallback for the tools-only client.
  • No item introduces a new dependency on a deprecated primitive.

Expected behaviour

A table with eight rows. A sound answer uses two tools, one resource, one resource template, one prompt and one elicitation, and it handles items 7 and 8 without sampling or roots. Each row that is not a tool has a tool-based fallback or an explicit statement that the tools-only client goes without.

Hint 1

Ask of each item who should decide that it happens now, the model, the user or the application.

Hint 2

A family of similar documents that differ by one name is a candidate for a resource template.

Hint 3

For items 7 and 8, look up the migration path the specification gives for the deprecated primitive.

Reasoning:

  • Items 1 and 5 are data with an address, so they are resources. Item 5 is a family that differs by one name, which is what a resource template is for. Both get a read tool because one of the two clients cannot read resources.
  • Items 2 and 3 are actions the model should pick while working, so they are tools. A rollback changes production, so the host must keep a person able to deny it.
  • Item 4 is started by a person, by name, with one argument. That is a prompt.
  • Item 6 is a value only the user has, needed in the middle of a call. Elicitation fits, but only when the client declared it. For the backend, the server returns a tool execution error that asks for the reason argument.
  • Item 7 looks like sampling, which is deprecated. Filter in code (errors only, last lines) and let the host's model summarise the smaller result, or call a model API from the server.
  • Item 8 looks like roots, which is deprecated. The specification's migration path is a tool parameter, a resource URI or server configuration.

Check your answer

  • Did you use a tool only where the model, not the user, should decide that the action happens?
  • Does every resource, prompt and elicitation in your answer say what the tools-only backend gets?
  • Did you avoid sampling and roots for items 7 and 8 and name the replacement?
  • Is the rollback protected by a person who can deny it, and not only by the tool description?
