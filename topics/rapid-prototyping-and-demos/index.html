Rapid Prototyping and Demos

Rapid prototyping is building a small, working, deliberately incomplete version of a solution, quickly, to answer one specific question. A demo is the session in which that prototype is put in front of the people who will use or approve it, so that what they do and say can support or reject the hypothesis it was built to test.

1Overview

Why it matters

A forward deployed engineer usually has days, not months, to show a customer that something can work. A sponsor cannot judge a design document, and an AI feature cannot be judged without running it on the customer's own records, because the risk sits in their data: missing keys, messy text, rules nobody wrote down. A prototype on real data is the cheapest way to find that out, and a well-run demo is how the customer's reaction becomes evidence instead of politeness.

Two things go wrong without the discipline. A team builds a polished demo on clean sample data, the customer is impressed, and the first real run in week three exposes problems that were knowable on day two. Or the prototype works, nobody wrote down what was faked, and the sponsor reads a hand-fed answer as a measured capability and asks for a go-live date. AI coding tools make it cheap to build something that looks finished, which makes both mistakes easier to commit. The lesson is for forward deployed engineers, solutions engineers and product engineers who build for another team's workflow.

What you will be able to do

  • Write a prototype hypothesis with a success threshold and a decision for each outcome before building anything.
  • Cut a thin slice that runs end to end through every layer on a sample of the customer's real data.
  • Decide component by component what is real, stubbed, hard-coded or done by a person, and write the choices down.
  • Run a demo as a test, with the user driving, the faked parts disclosed and observations logged.
  • Judge what a small replay sample can and cannot show by computing a confidence interval for its pass rate.
  • Turn observations into a proceed, change or stop decision and aim the next iteration at the riskiest remaining assumption.

Key terms

Prototype
A working but deliberately incomplete version of a solution, built to answer a question rather than to be shipped.
Hypothesis
A specific, testable belief about the customer, the data or the workflow, written together with the result that would support it and the result that would count against it.
Thin slice
One narrow path through every layer of a system, from a real input to something the user can see, built before any layer is finished.
Stub
A stand-in for a component that returns fixed or hand-prepared answers so that the rest of the slice can run.
Wizard of Oz
A prototyping method in which a person mimics the operations of a system that has not been built, so that users can experience its intended behaviour.
Fake-door test
A page, button or offer for something that does not exist yet, used to count how many people choose it.
Facade
A prototype that looks and behaves like the finished product from the customer's side while little or nothing works behind the surface.
Replay test
Running the prototype over a fixed set of past real cases and scoring each result against the answer it should have produced.
Demo test
A demo run as an experiment, in which the user performs a task, the team observes, and the result is judged against thresholds fixed beforehand.
Reality ledger
This lesson's name for a short written list stating, for each component of a prototype, whether it is real, stubbed, hard-coded or done by a person.

2Explanation

Introduction

A chef who wants to add a dish to the menu does not redesign the kitchen first. She cooks one plate, serves it to a table of regulars, watches what comes back uneaten, and decides whether the dish earns a place. The plate is not the dish at scale: the sauce was made by hand and the garnish was fixed at the pass. It does not need to be. It exists to answer one question.

A prototype works the same way. It is a working but deliberately incomplete version of a solution, built to answer a question rather than to be shipped. The question is written down first as a hypothesis: a specific belief, such as "a support agent can see the right order for an order-status email without searching", together with the result that would support it and the result that would count against it. A demo is the session in which the prototype is put in front of the people who will use it or approve it. Run well, a demo is an experiment. Run badly, it is a presentation in which everyone is pleasant and nothing is learned.

In a forward deployed engagement this skill sits between discovery and delivery. Discovery leaves you with a problem statement, a map of data and systems, and requirements. Technical scoping decides what to build first. Rapid prototyping is how you test that choice cheaply, on the customer's own data, before the build is committed. The lesson covers five moves, in order:

  1. Write the hypothesis, the threshold and the decision each outcome would trigger.
  2. Cut a thin slice: one narrow path through every layer, running on a sample of real data.
  3. Decide what is real and what is faked, write it down, and tell the audience.
  4. Run the demo as a test: the user drives, you observe, and the result is judged against thresholds fixed in advance.
  5. Turn what you saw into a decision and a smaller, better-aimed second iteration.

The loop is the point. A prototype is rarely right the first time, and its value lies in how quickly the second version can be aimed at what the first one taught.

How it works

1. Start with a hypothesis, a threshold and a decision

Eric Ries defines a minimum viable product as the version of a new product that lets a team collect the maximum amount of validated learning about customers with the least effort (Ries, Minimum Viable Product: a guide (opens in a new tab)). The word to hold on to is learning: a prototype is judged by what it teaches, not by how much exists. Before building, write three things on one page.

  • Hypothesis. One belief that would change what you build if it turned out false. Take it from discovery. GOV.UK's guidance for the alpha phase, in which government teams build prototypes, says to identify the riskiest assumptions and test those, instead of prototyping a whole journey (GOV.UK, How the alpha phase works (opens in a new tab)).
  • Threshold. The observation that counts as support, fixed before you look: "for at least 9 of 10 real order-status tickets, the panel shows the right result".
  • Decision. What you will do in each outcome: run a larger test, change the design, or stop.

The risky assumption is not always the interface, and different questions need different prototypes:

Do they want it?The offer, the price, the call to actionThe product behind itClicks, sign-ups, commitments

2. Cut a thin slice

A thin slice runs from a real input to something a user can see and react to, through every layer, for one narrow case. It is the opposite of finishing layers one at a time. Shape Up, the book in which Basecamp's team describes how it works, says why: screens with no back end, or back-end tasks with no interface, leave the work hypothetical, because nothing real can be clicked through. Its remedy is to integrate one small piece first, chosen by three criteria (Shape Up, chapter 11 (opens in a new tab)):

  • Core: without it the other parts mean nothing.
  • Small: it can be finished in days.
  • Novel: the team has not done it before, so building it removes uncertainty.

Apply the same test to a customer prototype. A login screen is neither core nor novel. Reading a real record, applying the rule or model you are unsure about, and showing the result next to data the user trusts is usually all three. Time-box the work: the cases in this lesson range from a first demoable piece in about three days (Shape Up) and a customer-tested prototype in five (GV's design sprint) to government alphas of 6 to 8 weeks.

3. Decide what is real, and write it down

The rule is to make real whatever the hypothesis is about, fake everything else, and never fake the thing under test. If the hypothesis is "a model can extract the purchase-order number from their invoice emails", a hand-picked set of easy emails, or a person typing the answers, produces a pleasant demo and a meaningless result.

The grid lists the usual substitutes. Wizard of Oz matters most for AI work. A survey paper describes it as a way to simulate the functionality and user experience of future systems, with a person mimicking operations of a system that does not exist yet. The same paper notes that acceptable performance often depends on resource-intensive tuning that is better done once the design is stable (Schlögl, Doherty and Luz (opens in a new tab)). A human wizard therefore tells you about the interaction, not about how well your model will perform.

Two habits keep faking honest. First, say what is faked in one sentence at the start of the demo. Second, keep a reality ledger: a short table in the prototype's README listing each component as real, stubbed, hard-coded or done by a person, with what would replace it in production. It stops a sponsor reading a hand-fed answer as a measured capability.

Use the customer's real data for the part under test, in the smallest amount that answers the question. Sample data hides what breaks: missing keys, typos, duplicates. Real data needs care: the ISE feasibility checklist asks teams to confirm access, set up a dedicated or restricted environment if required, and de-identify or redact sensitive information (Microsoft ISE, Feasibility Studies (opens in a new tab)). Read Data Privacy and Compliance before any customer record goes into a prototype or a hosted AI tool.

4. Build fast and keep it disposable

Stub the edges. In the interview-capture app that Shape Up describes, the team knew real interview data would go into the first piece, and protected it with plain HTTP authentication and a hard-coded password instead of building log-in. In the same spirit, use a spreadsheet export instead of an integration and a Streamlit or Gradio page instead of a React app (see Front Ends for AI Prototypes). A coding agent can produce a slice quickly (AI-Assisted Development), but you must still be able to explain any part that touches data or rules.

Three habits make a prototype reliable enough to learn from:

  • Pin the environment. Record the data snapshot date, model name and version, prompt and settings. A language-model step can answer differently on the same input, so demo cases you have already run.
  • Build a replay harness. A script that runs the slice over a fixed set of past real cases and scores each against the expected answer turns "it seems to work" into a count. The same cases later become the first test set for evaluating the LLM application.
  • Fence it off. The GOV.UK Prototype Kit guidance says teams must not use prototype code for production, because production code has to be secure and perform under load (GOV.UK Prototype Kit, Prototyping (opens in a new tab)).

5. Run the demo as a test

In a presentation the presenter drives. In a test the user drives. GV's Friday test brings in five customers, one at a time, for one-on-one interviews while the rest of the team watches by video and takes notes (Knowledge at Wharton, interview with Jake Knapp and John Zeratsky (opens in a new tab)). A customer-engagement version has five steps:

  1. Open with the hypothesis, what the prototype does, and what is faked.
  2. Hand over a task using the user's own real case, not yours, and say nothing about how to do it.
  3. Watch. Note where they hesitate, what they ask and what they ignore. Ask them to think aloud and do not rescue them.
  4. Show a failure on purpose. Run a case the slice gets wrong, so the audience learns the limits from you.
  5. Close on behaviour. "Would you use this?" invites politeness. Ask for something that costs them: next week's real cases, access to a second data source, thirty minutes with the process owner.

A small replay set finds failures well and measures rates poorly. For k correct results in n cases, the Wilson score interval gives a 95% range for the true pass rate:

With no failures at all, 12 cases support only a true rate of at least 75.7%, and about 35 clean cases are needed before the lower bound reaches 90%. If you observe 90% passing, you need about 70 cases before the lower bound passes 80%.

So use a handful of cases to find failure types, and a larger fresh set before you quote a rate.

6. Turn feedback into the next iteration

  • Log observations, not conclusions. Record who did what, what they said and which hypothesis it bears on, with your interpretation in a separate column.
  • Decide against the threshold you set. GV's John Zeratsky calls a failed Friday test an "efficient failure": usually some details fail in front of customers, and the team learns it in days instead of at the end of a long project. ISE's feasibility study ends in a report that either recommends moving towards production or details the gaps and may scope down, re-scope or look for more data.
  • Put feedback in the backlog. The ISE playbook suggests capturing each review as its own backlog user story and planning one review story per epic or feature (Microsoft ISE, External Feedback (opens in a new tab)).
  • Aim the next iteration at the riskiest remaining assumption, not the loudest comment.
  • Test fixes on new cases. A fix derived from the failed cases will pass those cases, which proves nothing. The worked example shows this.
  • Rewrite for production. Palantir's Foundry guidance illustrates the boundary: prototype metrics in a point-and-click analysis tool, put them on a quick dashboard for the sales team's feedback, and, for production use, convert the logic into a pipeline in a code repository (Palantir, Delivering a use case (opens in a new tab)). The handoff itself is covered in Production Handoff and Support.

Worked example: Replaying a lookup-panel slice on twelve tickets, and what the result can and cannot show

This is a teaching scenario with invented data. It continues the order-status problem from Customer Discovery and Requirements: support agents at a tool-hire company spend most of the handling time on order-status tickets finding the order in the ERP and its tracking in carrier portals, and the requirements named a read-only lookup panel. Before building it properly, test one hypothesis.

Hypothesis H1. For an order-status email, the panel shows the right result without the agent searching. Threshold: at least 9 of 10 tickets. Decision, fixed in advance: 90% or more on the first replay means run a fresh sample of 35 or more tickets before quoting a rate; less than 90% means study each failure, fix it, and re-run on tickets not used for the fix; a failure caused by missing data goes to the ERP owner and is not coded around.

The slice reads a real ERP export, finds the order named in a ticket, and prints it with the latest carrier event. The reality ledger shows what is real and what is not.

The script below is the replay harness. It holds twelve tickets, each with the result the panel should show: one order, a list of candidate orders when the choice is ambiguous (the rule from the discovery lesson), or none. Iteration 1 trusts the first order number in the email.

python
import math
import re

# REAL: an ERP export the customer sent (invented here): order number, customer email
ORDERS = [
    ("ORD-1001", "dana@example.com"), ("ORD-1002", "priya@example.com"),
    ("ORD-1003", "lee@example.org"), ("ORD-1004", "omar@example.net"),
    ("ORD-1005", "priya@example.com"), ("ORD-1006", "sam@example.org"),
    ("ORD-1007", "tina@example.net"), ("ORD-1008", "lee@example.org"),
    ("ORD-1009", "dana@example.com"),
]
# FAKED: latest carrier events, copied by hand from the carrier portals
CARRIER = {"ORD-1001": "out for delivery", "ORD-1003": "at depot", "ORD-1004": "delivered"}

# (ticket id, sender, body, result the panel should show)
TICKETS = [
    ("T01", "dana@example.com", "Where is ORD-1001?", "ORD-1001"),
    ("T02", "lee@example.org", "Status of ORD-1003 please", "ORD-1003"),
    ("T03", "omar@example.net", "my order ord-1004 has not arrived", "ORD-1004"),
    ("T04", "priya@example.com", "Chasing order 1005", "ORD-1005"),
    ("T05", "sam@example.org", "Where is my drill? No order number to hand.", "ORD-1006"),
    ("T06", "tina@example.net", "Has my order shipped?", "ORD-1007"),
    ("T07", "lee@example.org", "Any update on my hire? No number handy.", "LIST ORD-1003 ORD-1008"),
    ("T08", "priya@example.com", "ORD-1002 last month was fine, but is ORD-1005 late?", "LIST ORD-1002 ORD-1005"),
    ("T09", "dana@example.com", "Chasing ORD-1OO1 (typed from the paper slip)", "ORD-1001"),
    ("T10", "kim@example.com", "Where is my order? No number.", "NONE"),
    ("T11", "omar@example.net", "Where is ORD-1004? It says delivered.", "ORD-1004"),
    ("T12", "sam@example.org", "order #1006 status?", "ORD-1006"),
]
KNOWN = {order for order, _ in ORDERS}


def lookup(sender, body, v2):
    if v2:  # iteration 2: read the letter O inside an order number as a zero
        body = re.sub(r"(?i)(?<=ord-)[0-9o]{4}", lambda m: m.group().upper().replace("O", "0"), body)
    found = ["ORD-" + n for n in re.findall(r"(?i)(?:ord-?|order\s*#?\s*)(\d{4})", body)]
    found = [n for n in dict.fromkeys(found) if n in KNOWN]
    if found and not v2:
        return found[0]  # iteration 1: trust the first number mentioned
    if len(found) == 1:
        return found[0]
    if found:
        return "LIST " + " ".join(found)  # iteration 2: show every number mentioned
    mine = [order for order, email in ORDERS if email == sender]
    if len(mine) == 1:
        return mine[0]
    return "LIST " + " ".join(mine) if mine else "NONE"


def wilson(k, n, z=1.96):
    p = k / n
    centre = p + z * z / (2 * n)
    spread = z * math.sqrt(p * (1 - p) / n + z * z / (4 * n * n))
    return (centre - spread) / (1 + z * z / n), (centre + spread) / (1 + z * z / n)


for version in (1, 2):
    results = [(t, lookup(s, b, version == 2), want) for t, s, b, want in TICKETS]
    print(f"iteration {version}")
    for ticket, got, want in results:
        if got != want:
            print(f"  {ticket} FAIL  got {got!r}  expected {want!r}")
    passed = sum(got == want for _, got, want in results)
    low, high = wilson(passed, len(results))
    print(f"  {passed}/{len(results)} = {passed / len(results):.1%}, 95% interval {low:.1%} to {high:.1%}")

print("panel for T01:", lookup("dana@example.com", "Where is ORD-1001?", True), "-", CARRIER["ORD-1001"])

Running it (standard library only; tested on Python 3.13) prints:

text
iteration 1
  T08 FAIL  got 'ORD-1002'  expected 'LIST ORD-1002 ORD-1005'
  T09 FAIL  got 'LIST ORD-1001 ORD-1009'  expected 'ORD-1001'
  10/12 = 83.3%, 95% interval 55.2% to 95.3%
iteration 2
  12/12 = 100.0%, 95% interval 75.7% to 100.0%
panel for T01: ORD-1001 - out for delivery

Reading the result

  • H1 is not met. 10 of 12 is 83.3%, below 90%. The interval, 55.2% to 95.3%, is too wide to say more than that the true rate could be anywhere from poor to just above the threshold.
  • The failures are the finding. T08 mentions two orders, and iteration 1 confidently showed the first. That is the worst kind of failure, because it is wrong and looks right. In T09 a letter O was typed for a zero, so the number was ignored and the fallback by sender listed two orders without selecting the right one.
  • Iteration 2 fixes both, by reading O as 0 inside an order number and by listing every number mentioned. It scores 12/12, but both fixes were written from these twelve tickets, so the score is not evidence. Even a true 12/12 on fresh tickets supports only a pass rate of at least 75.7%.
  • The next test. About 35 fresh tickets with no failure would lift the lower bound to 90%. Ask for a month of the helpdesk export instead of working with the twelve tickets you happen to have.

What to do in the demo

  1. Open with H1 and the reality ledger: the ERP export is from a stated date, carrier events were typed by hand, and there is no login.
  2. Let an agent open their next three real tickets themselves.
  3. Run T08 on iteration 1 on purpose, so the customer sees the failure and the fix.
  4. Close on behaviour: ask for last month's ticket export and thirty minutes with the ERP owner.

Edge cases and limitations

The faked part hides the risk you meant to test
If a person types the answers, or the cases were hand-picked, a good reaction measures the interface and nothing else. A Wizard of Oz session can show whether users understand an interaction, but the accuracy they see is the wizard's, not your model's. Before each demo, name the number you will quote and check that nothing faked sits underneath it. If something does, say so aloud or drop the claim.
The demo turns into a delivery date
A working screen on real data makes sponsors ask when it goes live. The prototype has no tests, no access control and hard-coded parts, and GOV.UK's prototyping guidance says plainly that prototype code must not be used for production. State what the prototype is not at the start, show the reality ledger, and agree the next step as a larger test or a scoped build, not a launch.
Real customer data brings real exposure
Real records make the result credible and also put personal data on a laptop, in a hosted model or in a shared repository. Use the smallest sample that answers the question, de-identify where you can, keep it inside an environment the customer's security team has approved, and delete it when the prototype ends. A hard-coded HTTP password was a reasonable shortcut for one team's own early test; whether it is acceptable for a customer's records is the customer's security team's decision.
The audience is polite, or is not the user
Sponsors in a meeting room often praise what is on screen, and the people who do the work may not be there. Praise is weak evidence. Prefer a user working through their own case, and treat a request for the next step, such as more data access, another session or a month of tickets, as stronger evidence than compliments.
Model output varies between runs
A language-model step can answer differently on the same input, so a demo that depends on one lucky run misleads you and embarrasses you when it fails. Pin the model version, run every demo case beforehand, keep the outputs, and report how often the result held when you repeated it. Lowering randomness settings reduces variation but does not guarantee identical output.
Generated code you cannot explain
Coding agents make a thin slice cheap. Anthropic's July 2025 account of how its own teams use Claude Code says data scientists use it to build React applications for visualising reinforcement-learning model performance without being fluent in TypeScript, and that a weak first prompt is handled by a small tweak and another try. That is reasonable for a throwaway chart you can check by eye. In a customer demo you have to explain why the slice behaved as it did, so read the code that touches data, rules and money.

When to use it, and when something simpler is enough

Use it when

  • The open question is whether something will work on this customer's data or in their workflow, and a few days of work on a sample can answer it.
  • Stakeholders cannot judge a document or a diagram, but can react to a working screen using a case they recognise.
  • You can name a decision that depends on the result, such as scope the build, change the approach or stop.
  • The riskiest assumption is cheap to test with a stub, a facade or a hand-run version, while building the real thing would take weeks.

Think twice when

  • The problem is not yet understood. Do discovery first, because a prototype built on a guess answers the wrong question quickly.
  • The result would be read as a safety, legal or accuracy claim that a faked or small-sample prototype cannot support.
  • The customer will treat the demo as the delivery, and cannot be told otherwise.
  • The answer is already evidenced, for example by a reproducible defect with a known fix. Fix it and measure.

A simpler alternative. Do the task by hand for five or ten of the customer's real cases and show them the results next to what the customer's staff produced. It needs no software, exposes data problems at once, and often settles whether the idea is worth coding. It stops being enough when the question is about how a user interacts with the tool, or when the volume makes hand-run cases unrepresentative.

Key takeaways

  • A prototype is an experiment, so write the hypothesis, the threshold and the decision for each outcome before building anything.
  • Build one thin slice through every layer on the customer's real data, starting with the part that is core, small and novel.
  • Make real whatever the hypothesis is about, fake the rest, record the choices in a reality ledger and tell the audience what is faked.
  • Run the demo as a test in which the user works through their own case, and judge the result against the threshold you fixed beforehand.
  • A small replay set is good at finding failures and poor at measuring rates, since twelve clean results support only a pass rate of at least 75.7%.
  • Log feedback against hypotheses, aim the next iteration at the riskiest remaining assumption, test fixes on new cases, and rewrite instead of shipping the prototype.

Example 1 of 5

Basecamp builds one demoable toggle first, using stubs and real interview data

37signals (Basecamp)Documented in a case study

Shape Up, the book in which Basecamp's team describes how it builds products, devotes chapter 11, Get One Piece Done, to getting something real working in the first week or so. The chapter works through two cases: the Clients in Projects feature in Basecamp 3 and an app for capturing data from customer interviews. [5]

The problem

A project has front-end and back-end work that all seems necessary. The chapter says that when a team finishes many tasks but has no one thing to click on, it is hard to feel progress, and nobody can judge whether the work is right. Clients in Projects had three moving parts: client access, which had major back-end and caching implications, client management, and a visibility toggle on each piece of content.

Where this topic fits

This is the thin-slice step. After the project is shaped and before detailed building, the designer and programmer integrate one small piece end to end, demo it, and let what they see decide what comes next. The stubbed parts (hard-coded names, a fixed password, a toggle that does not yet change visibility) show what "fake everything else" looks like inside a real product team.

How it is applied, step by step

  1. List the moving parts from the pitch, here client access, client management and the visibility toggle, and choose one piece to integrate first.
  2. Choose the piece that is core, small and novel. The designer picked the visibility toggle because it was the most central piece of UI and the interaction customers would use most.
  3. Let design and code move in parallel. The designer tried controls and placements in the app's HTML templates while the programmer spiked the access model.
  4. Wire the front end just enough. The toggle appeared on every supported content type, changed state when clicked and saved to the database, without yet changing what clients could see.
  5. Try it on live data on a staging server instead of in a mock-up, then demo it to a manager about three days into the project and make a few tweaks before calling it done.
  6. In the interview app, hard-code the project name and subject, leave most links dead, and protect real interview data with a hard-coded HTTP password, so that real data can go in early.

Why this approach fits

The slice answers the question the team was unsure about, whether the core interaction makes sense in practice, using the real application and live data, while the expensive and well-understood parts wait. A static mock-up could not show how the toggle feels across content types. Stubbing names and authentication costs minutes and removes nothing the question depends on.

Limitation or tradeoff

The method assumes a shaped pitch that already defines the moving parts, and a small team in which one designer and one programmer can trade work within days. A stub that hides a hard problem only postpones it, which is why the programmer spiked the access model in parallel. The early back end is patchy by design, so it cannot be shown to customers as finished. The chapter reports the team's own judgement and gives no measurements of time saved.

What the sources document

  • The chapter advises aiming for something tangible and demoable in the first week or so by integrating vertically on one small piece, instead of chipping away at horizontal layers, because a team with many finished tasks but nothing to click on has little real to show. [5]
  • In Clients in Projects the designer chose the visibility toggle as the first piece, and the programmer wired it to appear on all supported content types, change state and save to the database, though it did not yet change what content was visible. This is a prototype whose only real parts are the offer, the price and the sign-up. It tests desirability and willingness to pay, the first question in this lesson's table, and its result decided whether to spend seven weeks building.

  1. Reduce the idea to one feature, a way to queue up tweets without scheduling each one individually.

Example 4 of 5

GOV.UK alpha phases prototype the riskiest assumption first, as the Register to vote team did

GOV.UK Service ManualDocumented in official docs

The GOV.UK Service Manual's page on the alpha phase, and the GOV.UK Prototype Kit's guidance on prototyping, describe how UK government service teams build and test prototypes before building a live service. [7][8]

The problem

A team coming out of discovery has several possible solutions and little evidence about which can work. Prototyping a whole journey in full would be slow and would still not answer the questions that could sink the service, such as whether the intended users go online at all, or whether a needed integration with other systems is possible.

Where this topic fits

Alpha follows discovery and comes before beta. Prototypes are built to test the riskiest assumptions, they may be sketches, click-throughs or code, and the phase ends with a decision about which tested ideas are worth taking forward.

How it is applied, step by step

  1. Take the problems learned in discovery and list the assumptions the service depends on.
  2. Rank the assumptions by risk and choose those that could make the service fail. For Register to vote, one was whether an API could integrate with the registration systems of over 400 local councils.
  3. Choose the cheapest prototype type that tests each assumption, a sketch, a click-through, or a code prototype that looks and behaves like GOV.UK.
  4. Prototype only the parts that test the assumption, not the whole journey, with code that is just complex enough for the test and not meant to be kept.
  5. Test with real users, including disabled people, and include offline elements such as letters where they bear on a risky assumption.
  6. Decide at the end which ideas to take to beta, and expect to throw away the code and many of the ideas.

Why this approach fits

Spending prototype effort where failure would be fatal gives the most learning per week. The Register to vote case shows that the riskiest assumption can be a feasibility question about an integration instead of a design question about a screen, which is where the team chose to put its alpha effort. Code prototypes exist so that research can use something that behaves like the real service.

Limitation or tradeoff

The manual says alphas tend to last between 6 and 8 weeks with a multidisciplinary team, which is far heavier than a five-day customer prototype. Alpha services should not be public and prototype code must not be reused for production, so everything proven in alpha is rebuilt, and that has a real cost. The pages do not report how many ideas are discarded or how reliable teams' risk rankings turn out to be.

What the sources document

  • The manual says alpha is where teams try out different solutions to the problems learned in discovery, by building prototypes and testing ideas, and that alpha services should not be available for the public to use. [7]
  • It tells teams to build things that are just complex enough to test different ideas, not production-quality code, and to expect to throw away any code and many of the ideas at the end of alpha. [7]
  • It says teams need not prototype the user's whole journey and may focus on the areas they think will be most challenging, in order to test their riskiest assumptions. [7]
  • The Register to vote team realised they would need an API that integrated with the registration systems of over 400 local councils. The service would not have worked without it, so that is what they focused on in alpha. [7]
  • The Prototype Kit guidance lists sketches, click-through prototypes and code prototypes, recommends code prototypes for user research because they look and behave like GOV.UK, and says prototype code must not be used for production. [8]

Example 5 of 5

Microsoft ISE tests ML feasibility on the customer's own data before committing to a build

Microsoft Industry Solutions Engineering (ISE)Documented in official docs

The ISE Engineering Fundamentals Playbook, published openly by Microsoft's Industry Solutions Engineering team, documents how its engineers assess whether a machine-learning solution is feasible on a customer's data before building it. [9]

The problem

Whether an ML idea works depends on whether the customer's data holds enough signal, in enough volume, with usable labels and joins, and none of that is known at the start. Committing to a full build first risks wasted investment. The playbook wants sufficient evidence that a solution is possible and compatible with the problem context before the team invests heavily.

Where this topic fits

The feasibility study comes early in an engagement, building on what discovery learned, and ends with a recommendation on whether to move to operationalisation. It is the playbook's thin-slice test for ML: start from the simplest reasonable baseline on the customer's real data, document each result, and report what the evidence supports.

How it is applied, step by step

  1. Define the problem and desired outcome from business and technical views, and check that the problem is complex enough that coding rules or manual scaling is unrealistic.
  2. Confirm that the whole team can access the data, set up a dedicated or restricted environment if needed, and de-identify or redact sensitive information.
  3. Hold a data exploration workshop with domain experts and check availability, quality, volume, labels and whether sources can be joined.
  4. Analyse the data, including distributions, correlations, missing values and leakage risk, and agree which data is in scope for the study.
  5. Design several candidate solutions starting from the simplest reasonable baseline, then train, evaluate, tweak and iterate, documenting each step and outcome.
  6. Test the concept with users and stakeholders where relevant, and write a feasibility report recommending whether to move towards operationalisation, scope down, re-scope or collect more data.

Why this approach fits

The cheapest moment to learn that labels are missing, or that two systems cannot be joined, is before the build. The playbook lets experiments sit outside the normal test and CI/CD rules, which keeps the study fast, and it makes the output a recommendation instead of a demo.

Limitation or tradeoff

A study of 4 to 16 weeks is far longer than a five-day customer prototype, and the playbook suggests starting with a 4-week milestone and deciding then how much more time is needed. Experiment code that skips tests and sits outside CI/CD is not production code, so assets handed forward need rework. The page says what to do and reports no statistics on how often studies change the decision.

What the sources document

4Common mistakes

  1. Demoing on clean sample data instead of the customer's real records.

    Why it causes problems
    The demo passes because the data was tidy. The missing keys, typos and duplicates in the real export appear in the first week of the build, when changing course is expensive, and the customer's confidence falls with them.
    How to recognise it
    Every case in the demo was written or chosen by the team, and nobody has measured how many real records lack the key the slice depends on.
    How to fix it
    Get an export of real records on day one, even a few dozen rows, and run the slice on a random sample before choosing demo cases. Include the ugly ones and say how many there were.

  2. Faking the part the hypothesis depends on.

    Why it causes problems
    A hand-fed answer, hand-picked examples or a person standing in for the model produces a result that says nothing about the model but looks as if it does. The sponsor then plans around a capability that was never measured.
    How to recognise it
    For each component ask whether the demo would still work if it were switched off. If the component you are about to claim for is faked, the ledger shows it as stubbed or done by a person.
    How to fix it
    Move the faking to neighbouring components. If the model cannot run yet, test only the interaction and do not quote accuracy.

  3. Presenting the prototype instead of testing it, so you drive and the audience nods.

    Why it causes problems
    Compliments feel like validation, but no hypothesis was exposed to risk. You leave without knowing whether a user can do the task or whether they would bring a second case.
    How to recognise it
    The user never touched the keyboard, no task was set, and the notes contain adjectives such as great and interesting but no observed behaviour.
    How to fix it
    Hand over a real case and stay quiet. Record hesitations, questions and workarounds, and end with a request that costs the customer something, such as more data or another session.

  4. Tuning on the demo cases and reporting the improved score.

    Why it causes problems
    Fixes written from the failing cases pass those cases by construction. The sponsor hears 12 of 12 and expects the same in production, where the rate is lower.
    How to recognise it
    The set used to find a bug and the set used to claim success are the same file, and the report gives a percentage with no sample size or interval.
    How to fix it
    Split the cases before you start: development cases for fixing, held-out cases for claiming, run once. Report the count, the interval and the failure types.

  5. Letting the prototype become the product by default.

    Why it causes problems
    Hard-coded passwords, stubs and unreviewed generated code reach production, and the team later pays for an incident or for months of untangling.
    How to recognise it
    The prototype repository has no tests, secrets in configuration, and a plan with a go-live date earlier than any rewrite.
    How to fix it
    Write a not-for-production list into the README and the demo opening, keep production code in a separate repository, and plan the rewrite explicitly, carrying over what you learned instead of the code.

  6. Building layers one at a time and polishing before anything runs end to end.

    Why it causes problems
    Weeks pass with several components almost done and nothing to click, so there is no feedback and the riskiest assumption is still untested when the deadline arrives.
    How to recognise it
    No input has travelled from start to finish, and the demo would need slides to explain what is not yet connected.
    How to fix it
    Build the narrowest end-to-end path first, with stubs on everything else, and add depth behind it only after someone has used it.

Write a Python script, using only the standard library, that reads the table above and applies the rule.

  • Compute the 95% Wilson score interval for the pass rate with z = 1.96 and print it as percentages.
  • Count failures by type and print them from most to least common.
  • Apply the three-way decision rule and print which branch it takes.
  • Compute how many further emails with no failure would lift the lower bound of the interval to 80%.

Hint 1

The interval formula is in the lesson. Compute the centre and the spread as two variables and divide both by 1 + z^2/n.

Hint 2

For the last part, increase a counter of extra passes in a while loop and recompute the interval each time, adding the counter to both k and n.

Hint 3

Put the decision rule in a function that takes k and n, so you can call it with other values when you check your work.

import csv
import io
import math

RESULTS = """case,result,failure_type
1,pass,
2,pass,
3,pass,
4,fail,two_numbers
5,pass,
6,pass,
7,pass,
8,pass,
9,fail,typo
10,pass,
11,pass,
12,pass,
13,pass,
14,pass,
15,pass,
16,pass,
17,fail,typo
18,pass,
19,pass,
20,pass,
21,pass,
22,pass,
23,fail,scanned_pdf
24,pass,
25,pass,
26,pass,
27,pass,
28,pass,
29,pass,
30,pass
"""
TARGET = 0.80


def wilson(k, n, z=1.96):
    p = k / n
    centre = p + z * z / (2 * n)
    spread = z * math.sqrt(p * (1 - p) / n + z * z / (4 * n * n))
    return (centre - spread) / (1 + z * z / n), (centre + spread) / (1 + z * z / n)


def decide(k, n):
    low, _ = wilson(k, n)
    if low >= TARGET:
        return "proceed: scope the build"
    if k / n >= TARGET:
        return "run a larger fresh sample"
    return "fix the failures first"


rows = list(csv.DictReader(io.StringIO(RESULTS)))
n = len(rows)
k = sum(row["result"] == "pass" for row in rows)
low, high = wilson(k, n)
print(f"{k}/{n} = {k / n:.1%}, 95% interval {low:.1%} to {high:.1%}")
print("decision:", decide(k, n))

failures = {}
for row in rows:
    if row["result"] == "fail":
        failures[row["failure_type"]] = failures.get(row["failure_type"], 0) + 1
print("failures by type:", dict(sorted(failures.items(), key=lambda item: -item[1])))

extra = 0
while wilson(k + extra, n + extra)[0] < TARGET:
    extra += 1
print(f"extra clean cases needed: {extra} (n = {n + extra}, lower bound {wilson(k + extra, n + extra)[0]:.1%})")
