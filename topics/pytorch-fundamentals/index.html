PyTorch Fundamentals (Tensors, Autograd, Training Loop)

PyTorch is a Python library for computing with tensors, which are n-dimensional arrays that can run on a GPU or another accelerator, and for differentiating that computation automatically. A model is trained by repeating four steps: a forward pass, a loss, a backward pass and a parameter update.

1Overview

Why it matters

A great deal of deep learning code is built from the same few PyTorch objects: a tensor holding the data, a module holding the parameters, an optimizer, and a loop that connects them. The Hugging Face fine-tuning guide, the PyTorch3D tutorial and the case studies cited in this lesson all draw on these pieces. Once you can read a training loop line by line, a new model or paper stops being a black box, because you can see what is differentiated, what is updated and when.

The mistakes are rarely in the model and almost always in the plumbing. Gradients pile up because nobody reset them. An evaluation run still has dropout switched on. A batch on the CPU meets a model on the GPU. A loss is computed between tensors of different shapes and broadcasts without complaint. A checkpoint is loaded in an unsafe way. Machine learning engineers, researchers and anyone who fine-tunes a pretrained model need to recognise these, because the first symptom is often a loss curve that merely looks plausible.

Key terms

Tensor
An n-dimensional array with a shape, a data type and a device. It is PyTorch's counterpart of a NumPy array, and it can also take part in gradient tracking.
Device
Where a tensor's memory lives and where operations on it run, such as the CPU, a CUDA GPU or another accelerator.
Autograd
PyTorch's automatic differentiation engine. It records the operations applied to tensors that require gradients and replays them backwards to compute derivatives.
requires_grad
A flag on a tensor that tells autograd to record operations involving it. Model parameters have it switched on; ordinary input data does not.
Leaf tensor
A tensor you created directly rather than obtained from a recorded operation, such as a parameter. After backward its .grad attribute holds the gradient.
nn.Module
The base class for models and layers. It keeps track of parameters and sub-modules, and calling the module runs its forward method.
Parameter
A tensor registered on a module as learnable. model.parameters() yields them, and the optimizer updates them.
Dataset and DataLoader
A Dataset returns one sample for an index. A DataLoader groups samples into batches, can reshuffle them every epoch and can load them in worker processes.
Epoch and batch
A batch is the group of samples used for one gradient step. An epoch is one full pass over the training set.
state_dict
A dictionary that maps parameter and buffer names to tensors. It is what you save to preserve a trained model's weights.

2Explanation

Introduction

You have already trained a model by hand. In gradient descent you wrote the update w←w−η ∂L/∂ww \leftarrow w - \eta \, \partial L / \partial ww←w−η∂L/∂w for a straight line, and in backpropagation you saw how the chain rule produces those partial derivatives for a network. Past a few layers, deriving every gradient yourself stops being practical. PyTorch takes over that bookkeeping and leaves the loop itself visible and editable.

It gives you four tools, and each maps onto something you already know. A tensor is a NumPy-style array from the Python data stack that can also live on a GPU. Autograd is a recorder: when a tensor is marked as needing gradients, every operation on it is remembered, and one call to backward() replays that record in reverse to deliver all the partial derivatives at once. An nn.Module is a container that owns a model's parameters and defines how they are applied to an input. A DataLoader feeds the model batches, and an optimizer from torch.optim uses the gradients to update the parameters.

Picture a spreadsheet in which every formula remembers which cells it read. Look at the error in the final cell and the sheet can walk back through the formulas, telling each input cell how much it contributed. Autograd does that for your tensor operations, and the optimizer is the person who then edits the input cells. Those pieces combine into the same loop in almost every project, from a four-point line fit to the recipes in the Hugging Face fine-tuning guide (opens in a new tab).

The diagram shows one pass. The rest of this lesson explains each box in turn, runs the loop on numbers you can check by hand, and shows how TensorFlow/Keras and JAX express the same ideas. Later lessons such as training deep networks assume this loop and change what happens inside it.

How it works

Tensors and devices

A tensor has three attributes you will check constantly: shape, dtype and device. You build one from Python data and operate on it much as you would a NumPy array, as the tensor tutorial (opens in a new tab) shows.

python
import torch

a = torch.tensor([[1.0, 2.0], [3.0, 4.0]])
print(a.shape, a.dtype, a.device)           # torch.Size([2, 2]) torch.float32 cpu
print((a @ torch.ones_like(a)).tolist())    # [[3.0, 3.0], [7.0, 7.0]]

if torch.accelerator.is_available():        # a GPU or another accelerator
    a = a.to(torch.accelerator.current_accelerator())

Three rules prevent most early errors. First, operands of one operation must share a device. The CUDA notes (opens in a new tab) say cross-GPU operations are not allowed by default, apart from copying calls such as to(), and that launching an operation on tensors spread across different devices raises an error unless peer-to-peer access is enabled. In practice a CPU tensor that meets a GPU tensor fails in the same way. Second, in-place operations, whose names end in an underscore, overwrite memory instead of creating a new tensor. The tutorial discourages them when you need derivatives, because the overwritten values are history autograd may need. Third, a CPU tensor and the NumPy array it was converted from can share memory, so changing one changes the other.

Autograd: recording and replaying

A tensor created with requires_grad=True tells autograd to record every operation that involves it. Each result keeps a reference, grad_fn, to the function that computes its local derivative. Together they form a directed acyclic graph whose leaves are the inputs and whose root is the output, as the autograd tutorial (opens in a new tab) describes. Calling backward() on the root walks that graph from root to leaves, multiplying local derivatives exactly as the chain rule in backpropagation does, and stores each leaf's gradient in its .grad.

python
x = torch.tensor(3.0, requires_grad=True)
y = x ** 2 + 2 * x
y.backward()
print(x.grad)        # tensor(8.), because dy/dx = 2x + 2 = 8 at x = 3

The rules worth memorising:

  • Only leaves keep gradients. Parameters are leaves, so .grad is filled on them and not on intermediate results.
  • Gradients accumulate. Each backward() adds into .grad instead of replacing it, so a training loop has to clear them.
  • A graph is used once. Backward frees it unless you pass retain_graph=True. The next forward pass records a new one, so ordinary Python loops and if statements work inside a model.
  • Tracking can be switched off. Inside torch.no_grad(), or on a detach()ed tensor, operations are not recorded. Use this for evaluation and for frozen parts of a model.
  • eval() is not no_grad(). The autograd notes (opens in a new tab) call evaluation mode orthogonal to no-grad mode: it changes layers such as dropout and batch normalization and does not stop recording.
  • In-place edits can break backward. Every tensor has a version counter. If a value saved for the backward pass was modified, backward raises an error instead of returning a wrong gradient.

Modules, losses and optimizers

A model subclasses nn.Module. Layers assigned as attributes in __init__ are registered, so model.parameters() can hand every learnable tensor to an optimizer and model.to(device) can move them together. forward describes the computation, and you run it by calling the module, model(x), not model.forward(x), because the call adds machinery around forward (build-model tutorial (opens in a new tab)).

python
from torch import nn

class Regressor(nn.Module):
    def __init__(self, n_features):
        super().__init__()
        self.net = nn.Sequential(nn.Linear(n_features, 16), nn.ReLU(), nn.Linear(16, 1))

    def forward(self, x):
        return self.net(x)

for name, p in Regressor(3).named_parameters():
    print(name, tuple(p.shape))

A loss function reduces predictions and targets to one number: nn.MSELoss() for regression, and nn.CrossEntropyLoss() for classification, which combines nn.LogSoftmax and nn.NLLLoss. For classification the model returns raw scores called logits and the loss applies the softmax itself, so do not add a softmax layer before it. An optimizer keeps references to the parameters and, when you call step(), changes each by a rule applied to its .grad. Plain SGD is θ←θ−ηg\theta \leftarrow \theta - \eta gθ←θ−ηg, the update from the gradient descent lesson. Adam and other optimizers are the subject of training deep networks.

Datasets and DataLoaders

A map-style Dataset implements __len__ and __getitem__, and item iii is one sample, usually a (features, label) pair. A DataLoader wraps it and handles batching and shuffling (torch.utils.data docs (opens in a new tab)). batch_size sets the group size, shuffle=True reorders the data every epoch, and num_workers sets how many processes load data; the default of 0 loads in the main process and blocks computation while it does. pin_memory=True speeds copies to a GPU. The default collate function adds a new first dimension as the batch dimension, so samples of shape (1,) become a batch of shape (B, 1).

The training loop and the evaluation loop

One pass over the data trains the model: for each batch compute the prediction and the loss, call loss.backward(), optimizer.step(), and then optimizer.zero_grad(). The optimization tutorial (opens in a new tab) explains the reset: gradients add up by default, so without it every step would use the sum of all earlier gradients.

python
def train_epoch(loader, model, loss_fn, optimizer, device):
    model.train()
    for X, y in loader:
        X, y = X.to(device), y.to(device)
        loss = loss_fn(model(X), y)
        loss.backward()
        optimizer.step()
        optimizer.zero_grad()

def evaluate(loader, model, loss_fn, device):
    model.eval()
    total, count = 0.0, 0
    with torch.no_grad():
        for X, y in loader:
            X, y = X.to(device), y.to(device)
            total += loss_fn(model(X), y).item() * len(X)
            count += len(X)
    return total / count

model.train() and model.eval() switch layers such as dropout and batch normalization between training and inference behaviour. The evaluation loop adds torch.no_grad() so no graph is built, which saves memory and time, and weights each batch loss by its size because the last batch is often smaller.

Saving and loading

A model's learned parameters live in model.state_dict(). The usual pattern saves that dictionary, then rebuilds the model and loads it back:

python
torch.save(model.state_dict(), "model.pt")

restored = Regressor(3)
restored.load_state_dict(torch.load("model.pt", weights_only=True))
restored.eval()

The save-and-load tutorial (opens in a new tab) recommends weights_only=True, which limits what unpickling may execute, because the default format is built on Python's pickle. Saving the whole model object also uses pickle and needs the class definition at load time. Call eval() before inference.

The default has changed over time. The torch.load documentation (opens in a new tab) for 2.14 lists weights_only=True as the default, and the announcement of the change (opens in a new tab) says it applies from version 2.6 and that loading a whole pickled module then fails unless you pass weights_only=False. Before 2.6 the full unpickler ran by default, so passing the argument explicitly keeps the intent clear on every version. A checkpoint for resuming training also needs the optimizer's own state_dict(), which the saving-and-loading-models tutorial (opens in a new tab) says holds buffers and parameters that are updated as the model trains.

The same ideas in TensorFlow/Keras and JAX

All three frameworks run the same cycle of forward pass, loss, gradients and update. They differ in where each piece lives.

The difference that matters most is state. PyTorch keeps the gradient on the tensor and the parameters on a module, so the loop mutates objects. TensorFlow's tape and JAX's grad hand the gradients back as values (TensorFlow guide (opens in a new tab), JAX transformations (opens in a new tab)), so there is no .grad field to clear. JAX goes further: its transformations need pure functions, so parameters and optimizer state go in as arguments and come back as results, as in the update(params, opt_state, batch) function of the JAX state page (opens in a new tab), and its arrays (opens in a new tab) are immutable. Keras follows the PyTorch shape more closely: a loop over batches, a forward pass, a gradient request and an optimizer call, as in its custom training loop guide (opens in a new tab).

Edge cases and limitations

Gradients accumulate until you clear them
Every backward() call adds to .grad. Calling it twice in the worked example turns -17.0 and -8.0 into -34.0 and -16.0, so the optimizer would take a step twice as large as intended. The same property is useful on purpose: summing the gradients of several small batches before one optimizer step simulates a larger batch, which is what the gradient_accumulation_steps option in the Hugging Face example does. Otherwise reset the gradients once per step.
A (4, 1) prediction and a (4,) target broadcast to (4, 4)
Subtracting a row from a column does not fail. PyTorch broadcasts both to a 4 by 4 grid and the mean runs over 16 differences. With the worked example's parameters after one update the correct loss is 0.535 and the broadcast loss is 9.035. Training still runs and the loss still falls, but toward the wrong objective: the minimiser is w = 0 and b = 4, the mean of y, which is a flat line. Check .shape before the loss and keep predictions and targets the same shape.
eval() and no_grad() are separate switches
model.eval() changes how dropout and batch normalization layers behave and leaves gradient recording on. torch.no_grad() stops recording and leaves dropout active. Evaluation needs both. With only eval() a graph is still recorded for every batch, which costs memory and time and piles up if you keep the loss tensors; with only no_grad() the predictions are still randomly thinned by dropout. Call model.train() again before the next training epoch.
In-place changes can invalidate what backward needs
Operations whose names end in an underscore, such as add_, overwrite memory. Every tensor carries a version counter, and if a value saved for the backward pass was modified, backward raises an error instead of silently using the new value. Replace the in-place operation with an out-of-place one and the error disappears. The optimizer's own parameter update is the legitimate in-place change, and it runs without being recorded.
A learning rate above 2 over the largest curvature diverges
In the worked example the largest eigenvalue of the loss's second-derivative matrix is 8.405, so full-batch SGD is stable only below a learning rate of about 0.238. At 0.2 the loss falls from 21 to 9.74, 4.518, 2.095 and 0.972. At 0.25 it climbs through 25.469, 30.889, 37.462 and 45.435. Real networks have no such closed form, so the practical sign is a loss that grows within the first few steps; cut the learning rate by a factor of 3 to 10 and run again.
Tensors and NumPy arrays can share memory
On the CPU, torch.from_numpy and tensor.numpy() give objects that share memory with their source, so changing the array changes the tensor and the other way round. That avoids a copy but can silently alter a dataset you thought was untouched. If you need independent data, copy it with clone() on the tensor or copy() on the array.

When to use it, and when something simpler is enough

Use it when

  • You are training or fine-tuning a neural network, or any model whose parameters are found by gradient descent on a loss you can write as tensor operations.
  • You need to read, modify or reproduce research code, or run pretrained models from libraries such as Hugging Face Transformers that are built on PyTorch.
  • You want gradients of a custom objective with respect to something other than network weights, such as the mesh vertices and colours in the PyTorch3D example.
  • You need GPU-accelerated array computation for a problem that is not a neural network, as in the LinkedIn solver example, and want one code path for one or several devices.

Think twice when

  • The data is a small table and the model is linear, a tree ensemble or a nearest-neighbour search; scikit-learn or a boosting library fits these in a few lines and needs no training loop.
  • You only call a hosted model through an API; you then need prompts and tool calls rather than tensors.
  • A standard fine-tuning run is all you need; a higher-level trainer already provides the loop, checkpoints and logging, and your own loop adds bugs without adding value.

A simpler alternative. For tabular data and classical models use scikit-learn estimators, which hide the loop entirely. Move to PyTorch when the model is a neural network, the loss is custom, or the data is images, text or audio. When the training procedure is standard, a library trainer such as Hugging Face's Trainer or Keras's fit wraps the loop, and you write your own only when you need to change what happens inside a step.

Key takeaways

  • A tensor is an array with a shape, a dtype and a device, and the operands of one operation must be on the same device.
  • Autograd records the operations applied to tensors that require gradients, and backward() replays that record in reverse to fill each leaf's .grad.
  • Gradients accumulate across backward calls, so every training step is forward pass, loss, backward, optimizer step, then clearing the gradients.
  • A model is an nn.Module whose parameters go to an optimizer, a DataLoader supplies batches, and train and eval mode are separate from gradient tracking.
  • Save the state_dict rather than the whole model object, and load it with weights_only=True into a freshly built model before calling eval().
  • TensorFlow/Keras and JAX make the same four moves; the main difference is that JAX passes state explicitly through pure functions, while PyTorch and Keras keep it in objects.

LinkedIn DuaLip: tensors and GPUs for a web-scale linear-programming solver

LinkedInDocumented in a case study

A PyTorch Foundation case study from June 2026 describes how LinkedIn rebuilt DuaLip, its distributed solver for very large linear programs, as a PyTorch system that runs on GPUs (DuaLip-GPU). [21]

The problem

LinkedIn expresses decisions such as matching jobs to job seekers, balancing business metrics in ranking, and setting email volume as linear programs: maximise value subject to limits such as budget, fairness and frequency. The article says these can involve hundreds of millions of users and trillions of decision variables with sparse, structured constraints. The earlier DuaLip ran on a Scala and Spark stack that was bound to CPUs, and its template-driven interface made new problem formulations slow to add.

Where this topic fits

This example uses the first layer of the lesson, tensors and devices, and no neural network. The solver's hot loop is repeated sparse matrix-vector products and blockwise projections, which PyTorch executes as tensor operations on a GPU. The article describes gradients computed through matrix-vector operations and notes that this makes the solver look structurally similar to neural network training; it does not say whether autograd is used.

How it is applied, step by step

  1. Express each solver iteration as tensor operations, namely sparse matrix-vector products and blockwise projections, orchestrated by a lightweight maximiser.
  2. Hold the sparse constraint data in sparse tensors on GPU memory so the dominant products run as batched GPU kernels.
  3. Partition the decision variables across several GPUs, so each device handles only its share of the products.
  4. Replicate the dual variables on every GPU and synchronise them each iteration with collective communication such as all-reduce and broadcast.
  5. Speed convergence with row normalisation and scaling, regularisation continuation, and accelerated first-order methods.
  6. Compare per-iteration wall-clock time with the original CPU implementation.

Why this approach fits

The work per iteration is regular array arithmetic over very large, mostly empty matrices, which is what a tensor library with sparse support and GPU kernels does best. The problem

Given images of an object from several camera positions, recover a 3D mesh and its surface colours. The tutorial does this without any knowledge of the ground-truth mesh, so there is no list of correct vertex coordinates to compare against, only the images. The loss therefore has to be computed between a rendered image and a target image, and the error has to be traced back to the 3D vertices and colours that produced the pixels. In the tutorial the targets are synthetic: a textured cow mesh rendered from 20 viewpoints.

Where this topic fits

This is autograd used on tensors that are not network weights. The parameters are two plain tensors, vertex offsets and per-vertex colours, created with requires_grad=True. The loop around them is the one in this lesson: clear gradients, run the forward pass (move the vertices, render, compare), call backward() and call step().

How it is applied, step by step

  1. Render a textured cow mesh from 20 camera positions to make the target images, which are the only supervision.
  2. Start from a sphere of radius 1 and create two tensors on the device, vertex offsets filled with 0.0 and vertex colours filled with 0.5, both with requires_grad=True.
  3. Give both tensors to torch.optim.SGD with learning rate 1.0 and momentum 0.9.
  4. In each of 2000 iterations, clear the gradients, offset the sphere's vertices by the current offsets and attach the current colours as its texture.
  5. Render the deformed sphere with a differentiable soft renderer from two views chosen at random out of the 20, and compare with the targets using RGB and silhouette losses plus edge-length, normal-consistency and Laplacian-smoothing regularisers, combined as a weighted sum.
  6. Call backward on the summed loss so gradients flow through the renderer to the two tensors, then step the optimizer.

Why this approach fits

Autograd differentiates any chain of tensor operations, so once the renderer is built from differentiable operations, the distance between rendered and target images can be reduced by gradient descent on shape and colour parameters. Nobody has to derive by hand how a vertex moving by a small amount changes a pixel, which would be the hard part.

The targets are rendered from a known mesh, so the tutorial shows that the optimisation works, not that real photographs behave as cleanly. Hugging Face safetensors: sharing model weights without running pickled code

Hugging FaceDocumented in official docs

The safetensors documentation describes a file format for storing tensors that is used by libraries such as Transformers and Diffusers. It addresses the same job as PyTorch's torch.save, whose tutorial recommends loading with weights_only=True. [18][19][7][9][10]

The problem

Trained weights are shared as files that other people download and load. PyTorch's standard serialization is built on pickle, and its tutorial advises restricting what unpickling may execute. A format that holds only tensors removes that risk at the source, and it must still load quickly for very large models and let a process read just the part of a file it needs.

Where this topic fits

This sits at the end of the training loop. A model's state_dict() is a dictionary of named tensors, so saving trained weights means writing that dictionary to disk, and using them means building the model class again, loading the tensors into it and calling eval(). Safetensors replaces the pickle-based file in the middle of that sequence.

How it is applied, step by step

  1. After training, call model.state_dict() to get an ordered mapping from parameter names to tensors.
  2. Write it to disk, either with torch.save (a pickle-based file) or with safetensors save_file (a tensor-only file).
  3. A consumer builds the model class from code, so the architecture comes from the library and the numbers come from the file.
  4. The consumer loads the saved tensors into that model with load_state_dict, using weights_only=True for the pickle route.
  5. With safetensors the file can also be opened lazily, so a process on one GPU of several reads only the slice of a tensor it needs.
  6. Call model.eval() before inference so dropout and batch normalization layers are in evaluation mode.

Why this approach fits

A state_dict holds names and numbers and nothing else, so a format that stores only named arrays covers everything needed to restore weights and nothing that could carry code. Zero-copy reading keeps loading fast, and lazy access to slices suits models split across devices.

Limitation or tradeoff

Weights alone do not restore the architecture or the optimizer's state, so the model code and its configuration must come from somewhere else. A safe file format means loading it does not execute code, not that the weights are good or untampered. The tensor-only format cannot hold arbitrary Python objects, so anything beyond tensors, such as a whole pickled model, needs another route, and the PyTorch tutorial notes that saving a whole model needs its class definition at load time. Tensors passed to save_file must be contiguous and dense, and the Torch API page points to save_model and load_model for models whose tensors share storage, such as tied weights.

4Common mistakes

  1. Not clearing gradients between training steps.

    Why it causes problems
    Every backward() call adds into .grad, so gradients that are never reset sum across batches. The effective step grows with each iteration and mixes old batches into the update, and the loss wanders or blows up even though the model and the data are fine.
    How to recognise it
    Print a parameter's .grad.abs().max() at the start of consecutive steps. If it keeps growing instead of staying the same size, nothing is clearing it. A loss curve much worse than a reference run with the same settings is another sign.
    How to fix it
    Call optimizer.zero_grad() once per step, after optimizer.step() as the PyTorch tutorial does, or before backward(). Accumulate on purpose only to simulate a larger batch, and then step and clear every N batches.

  2. Evaluating without model.eval() and torch.no_grad().

    Why it causes problems
    Dropout stays active and batch normalization keeps using batch statistics, so the metric is noisy and usually worse than the model deserves, and it can differ between runs on identical weights. Without no_grad a graph is built for every evaluation batch, which wastes memory.
    How to recognise it
    Run the evaluation twice on the same data and weights. If the numbers differ, a stochastic layer is still active. Memory use above what the forward pass alone needs, or memory that climbs when you also store the loss tensors, points to a missing no_grad.
    How to fix it
    Wrap evaluation in model.eval() and a with torch.no_grad() block, and call model.train() again before the next training epoch.

  3. Leaving the model and the batch on different devices.

    Why it causes problems
    The operation fails with a device-mismatch error. On a machine without an accelerator the bug never shows, so it appears only when the code first runs on a GPU. Moving data back and forth by accident also slows training.
    How to recognise it
    Print next(model.parameters()).device and X.device at the top of the loop. A RuntimeError that names two different devices means one of the tensors was not moved.
    How to fix it
    Choose one device at the start, call model.to(device) once, call .to(device) on every input and target batch inside the loop, and create new tensors with device=device.

  4. Passing a prediction and a target of different shapes to the loss.

    Why it causes problems
    A (B, 1) prediction against a (B,) target broadcasts to (B, B), so the loss measures something else. In the worked example it reports 9.035 instead of 0.535 and training heads for the mean of y.
    How to recognise it
    Print pred.shape and target.shape just before the loss, and compare the loss on a handful of samples with a value computed by hand or with NumPy.
    How to fix it
    Make both tensors the same shape, for example target.unsqueeze(1) to get (B, 1) or pred.squeeze(1) to get (B,), and assert the shapes in the training script.

  5. Storing the loss tensor instead of its value.

    Why it causes problems
    A line such as total_loss += loss keeps every iteration's graph alive, because the running sum refers back to each loss and its history. Memory then grows steadily through the epoch until the process fails.
    How to recognise it
    Memory climbs during an epoch although the batch size is fixed, and printing the running total shows tensor(..., grad_fn=<AddBackward0>) instead of a plain number.
    How to fix it
    Use loss.item() for a Python number, or loss.detach() for a tensor without history, whenever you log or accumulate a loss.

  6. Loading checkpoints with default pickle behaviour or saving whole model objects.

    Why it causes problems
    A pickle file can run code when it is loaded, so opening a downloaded checkpoint is a security risk. A pickled whole model also breaks when its class definition is renamed or moved.
    How to recognise it
    Look for torch.load calls with weights_only=False, or with no argument in code that may run on a PyTorch older than 2.6, on files you did not create, and for torch.save(model, path) in a training script.
    How to fix it
    Save model.state_dict(), rebuild the model from code, load with torch.load(path, weights_only=True), or use a tensor-only format such as safetensors for shared files. Call eval() before inference.

import torch
from torch import nn
from torch.utils.data import DataLoader, Dataset


class LineData(Dataset):
    def __init__(self):
        self.x = torch.tensor([0.0, 1.0, 2.0, 3.0])
        self.y = torch.tensor([1.0, 3.0, 5.0, 7.0])

    def __len__(self):
        return len(self.x)

    def __getitem__(self, i):
        return self.x[i : i + 1], self.y[i : i + 1]      # shapes (1,) and (1,)


def train(lr, batch_size, epochs, shuffle):
    model = nn.Linear(1, 1)
    nn.init.zeros_(model.weight)
    nn.init.zeros_(model.bias)
    loss_fn = nn.MSELoss()
    optimizer = torch.optim.SGD(model.parameters(), lr=lr)
    loader = DataLoader(LineData(), batch_size=batch_size, shuffle=shuffle)
    losses = []
    for _ in range(epochs):
        for X, y in loader:                               # X and y have shape (B, 1)
            loss = loss_fn(model(X), y)
            loss.backward()
            optimizer.step()
            optimizer.zero_grad()
            losses.append(loss.item())
    return model, losses


model, _ = train(lr=0.05, batch_size=2, epochs=300, shuffle=True)
print(f"mini-batch: w={model.weight.item():.3f} b={model.bias.item():.3f}")

for lr in (0.2, 0.25):
    _, losses = train(lr=lr, batch_size=4, epochs=5, shuffle=False)

A complete review lists these six bugs. The target y has shape (40,) while predictions have shape (B, 1), so the loss broadcasts. The loop never calls optimizer.zero_grad(), so gradients accumulate. The batches are never moved to the device, which crashes on a GPU machine. total and val_total accumulate loss tensors and keep graphs alive. The validation loop runs in training mode, so dropout is active, and with gradient tracking on; once it gains eval() and no_grad(), train() must be called again at the start of every epoch. The whole model is saved and loaded with pickle, with no weights_only and no eval(). The corrected script keeps predictions and targets in the same shape, moves each batch to the device, clears gradients, uses .item(), wraps validation in eval() and no_grad(), and saves a state_dict.

Corrected script:

python
import torch
from torch import nn
from torch.utils.data import DataLoader, TensorDataset

device = torch.accelerator.current_accelerator().type if torch.accelerator.is_available() else "cpu"

x = torch.linspace(0, 3, 40).unsqueeze(1)             # (40, 1)
y = 2 * x + 1                                          # (40, 1), same shape as the predictions
train_loader = DataLoader(TensorDataset(x[:30], y[:30]), batch_size=10, shuffle=True)
val_loader = DataLoader(TensorDataset(x[30:], y[30:]), batch_size=10)


def make_model():
    return nn.Sequential(nn.Linear(1, 8), nn.ReLU(), nn.Dropout(0.2), nn.Linear(8, 1))


model = make_model().to(device)
loss_fn = nn.MSELoss()
optimizer = torch.optim.SGD(model.parameters(), lr=0.01)

for epoch in range(50):
    model.train()                                      # restore training mode every epoch
    train_total = 0.0
    for X, target in train_loader:
        X, target = X.to(device), target.to(device)
        loss = loss_fn(model(X), target)
        loss.backward()
        optimizer.step()
        optimizer.zero_grad()
        train_total += loss.item() * len(X)

    model.eval()                                       # dropout off
    val_total = 0.0
    with torch.no_grad():                              # no graph
        for X, target in val_loader:
            X, target = X.to(device), target.to(device)
            val_total += loss_fn(model(X), target).item() * len(X)
    print(epoch, train_total / 30, val_total / 10)

torch.save(model.state_dict(), "model.pt")
restored = make_model()
restored.load_state_dict(torch.load("model.pt", weights_only=True))
restored.eval()
with torch.no_grad():
    print(restored(torch.tensor([[1.5]])))

With the fixes the training loss should fall steeply over the first few epochs and then fluctuate, because dropout is active during training and each epoch sees the batches in a new order. The final prediction should land in the region of 3, the value of 2 x 1.5 + 1, but not exactly on it; how close it gets depends on the random initialisation and the 50 epochs, so no exact value is claimed. The validation points are the last 10 of a sorted range, so they lie beyond the training range (x above about 2.23) and the validation loss measures extrapolation here; on real data you would shuffle before splitting. Bug 4 is the one that looks harmless in a short run, since it only shows up as memory growth in long ones. Bug 2 does not crash either: without a reset the summed gradients act like momentum that never decays, and the loss keeps oscillating instead of settling.
