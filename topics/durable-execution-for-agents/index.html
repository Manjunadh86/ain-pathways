Durable Execution and Long-Running Agents

Durable execution means running an agent so that its progress is saved after every finished step. When the process crashes, is redeployed, or has to wait days for a person, a new process loads that record and continues from the last completed step instead of starting over.

1Overview

Why it matters

A demo agent runs for a few seconds inside one process. A production agent may run for tens of minutes, call dozens of tools, and sometimes stop to wait for a person. In that time the host can be redeployed, a provider can time out, and the user can close the tab. If the only record of progress is a list in memory, each of these events either loses the work or repeats it. Repeating is the worse outcome, because some steps change the outside world: a second attempt can send a second email or issue a second refund.

Anthropic's engineers describe this pressure in their multi-agent research system: agents keep state across many tool calls, minor failures can derail a run, and restarting from the beginning is expensive. Anyone who ships agents that outlast a request timeout, call tools with side effects, or ask a human to approve something needs to know what to save, how to make retries safe, and when a framework feature is enough versus when to use a workflow engine.

Key terms

Durable execution
A way of running code so that finished steps are recorded and a crashed or paused run can continue from the last recorded step in a new process.
Checkpoint
A saved snapshot of a run's state at a step boundary. Loading it lets a run continue without redoing the steps before it.
Journal
An append-only record of the results of finished steps. Temporal calls its journal the Event History.
Replay
Re-running the orchestration code after a restart while answering every already-finished step from the journal instead of executing it again.
Idempotent operation
An operation whose effect is the same whether it runs once or many times, such as setting a value or reading a record.
Idempotency key
A unique value sent with a request so that the receiving service can recognise a repeat and return the first result instead of acting twice.
At-least-once execution
A guarantee that a step will be attempted until it succeeds, which means it may run more than once if the result of an earlier attempt was lost.
Exponential backoff
A retry schedule in which the wait between attempts grows by a fixed factor, usually up to a cap, so that a struggling service gets time to recover.
Heartbeat
A periodic signal from a long-running step to the runtime that says it is still alive. It can also carry progress and deliver a cancellation request.
Interrupt
A deliberate pause inside a run that saves state and waits for outside input, such as a human decision.

2Explanation

Introduction

In The Agent Loop the whole run lives in one process. A list of messages grows, the loop calls the model and the tools, and the list is the agent's memory of what it has done. That works until the process stops. Agent Deployment Architecture names long-running execution and state stores as things an agent runtime must provide. This lesson explains how the two fit together.

Think of a long file download. A good download manager does not return to byte zero when your Wi-Fi drops. It keeps a record of what it has already written to disk and asks the server for the rest. Durable execution gives an agent the same property. After every step that finishes, the run writes down what happened. When a new process takes over, it reads that record, skips what is already done, and carries on from the first unfinished step.

Two things make agents harder than downloads. First, a step can have effects outside your program. If the process dies after a refund was issued but before it wrote "refund issued" in its record, the new process cannot tell, and it will try again. Second, a model call cannot be repeated faithfully. Ask the same question twice and the answers can differ, so recovery has to reuse the first answer instead of generating a new one.

The rest of the lesson covers what to save and how often, how to make repeated attempts harmless, how to set retries, timeouts and cancellation, how to wait for a person without holding a process open, how deploys interact with runs that are still going, and how to choose between three kinds of tooling: a framework checkpointer, a workflow engine, and a managed long-running runtime.

How it works

What goes wrong in a long run

A run that lasts minutes or hours meets events that a single request never sees: the process is killed or restarted by a deploy, a model or tool call times out or returns a temporary error, a tool call takes effect but its reply never arrives, the run must wait for a person, someone asks to stop it, or the code changes while the run is still going. Durable execution makes each of these survivable. Everything else builds on one idea.

Save the result of every finished step

Two designs are common. A checkpointer saves a snapshot of the agent's state at step boundaries. LangGraph saves one at each super-step (one tick in which the scheduled nodes run) and also saves each node's writes as the node finishes, so if one node fails, the nodes that succeeded in that super-step are not re-run on resume. A workflow engine such as Temporal keeps an append-only Event History of every Activity result and incoming message. After a crash a new Worker replays the Workflow code against that history to rebuild its state and carry on. AWS Lambda durable functions work in a similar way: the handler runs again from the top, and each step that already finished returns its saved result instead of running.

The storage differs but the rule is the same: a finished step is answered from the record and never executed again. The worked example implements the rule in a dozen lines (durable_step).

Record model calls, do not regenerate them

Replay re-runs your orchestration code, so the code outside recorded steps has to behave the same way each time. AWS's guide lists time, random numbers, generated UUIDs and any external I/O as non-deterministic, and says to wrap them in steps so the first result is reused. A model call is the clearest case, because asked twice it may pick a different tool or different arguments. So the reply is stored as a step result. In Temporal's integration with the OpenAI Agents SDK, the model invocation runs as an Activity that the integration supplies. Reusing the stored reply also keeps the arguments of a retried tool call identical, which matters for idempotency keys below.

How often to save

Saving after every step costs a write per step. Saving rarely costs more repeated work after a crash. Take a run of NNN steps in which a crash is equally likely to hit any step, and write a checkpoint every kkk steps, where kkk divides NNN. A crash in the middle of an interval means the finished steps since the last checkpoint are done again. The step that was running when the crash hit runs again whatever kkk is, so it is not counted:

redone(k)=k−12,writes(k)=Nk\text{redone}(k) = \frac{k-1}{2}, \qquad \text{writes}(k) = \frac{N}{k}redone(k)=2k−1​,writes(k)=kN​

With N=24N = 24N=24, saving after every step redoes nothing and costs 24 writes, while saving only at the end redoes 11.5 steps on average. In an agent a redone step is a model call plus tool calls, so the price is money and waiting time. LangGraph exposes this choice as durability modes: exit saves only when the run exits and cannot recover from a crash in the middle, async saves while the next step runs with a small risk of losing the latest checkpoint, and sync saves before the next step starts at some cost in speed.

The gap between doing and recording

No design removes this gap: a step can finish its side effect and the process can die before the result is saved. The record says "not done", so recovery runs the step again. Temporal describes exactly this case, a Worker crashing after an Activity succeeds but before it reports, and asks for Activities to be idempotent. AWS makes the choice explicit: a step is at-least-once by default and runs again after an interruption, while an at-most-once option raises an error on replay instead of repeating. The guide pairs at-most-once with a no-retry strategy for things like charging a card.

An operation is idempotent if doing it several times has the effect of doing it once. Reads are. A write becomes idempotent with an idempotency key: a unique value that lets the service recognise a repeat and return the first result. The key must be identical on every attempt of one step and different for every other step. Temporal suggests the Workflow Run ID plus the Activity ID. AWS says to generate the key inside a step, because a key generated outside one changes on replay. Do not ask the model for the key. The harness derives it from the run and step identifiers.

Retries and timeouts

Retry only errors that another attempt could fix, such as timeouts, HTTP 429 and 5xx. A bad argument or a missing permission fails the same way every time, and Temporal's documentation says permanent failures are better surfaced than retried. Wait longer between attempts so a struggling service can recover. Temporal's default Activity policy starts at 1 second, multiplies by 2.0 each time, caps the wait at 100 seconds and puts no limit on attempts. The wait before retry nnn is min⁡(1⋅2n−1, 100)\min(1 \cdot 2^{n-1},\ 100)min(1⋅2n−1, 100) seconds:

With unlimited attempts, a timeout is what bounds the work, so give every call one. Temporal documents that its server cannot detect a Worker that crashes or loses contact, and relies on the Start-To-Close Timeout to force a retry, which is why it strongly recommends always setting it. For long calls add a heartbeat: it can carry progress that the next attempt reads to continue where the last one stopped. Retry in one layer only, because an SDK that retries three times inside an engine that retries without limit multiplies attempts. For provider-level retries and fallbacks see LLM Gateways and Reliability.

Cancellation

Cancellation is a request, not a kill switch. In Temporal an Activity must heartbeat to receive a cancellation, and a cancellation can be requested only once. OpenAI's background mode has a cancel endpoint for an in-flight response. Step Functions notes that cancelling a task started with its run-a-job pattern is best effort, and a failure can incur charges from the integrated service. Write long steps to check for cancellation between units of work, and plan for effects that already happened: a cancelled run may need a compensating action such as reversing a refund.

Waiting for a person

Do not hold a process while a person thinks. Save the state, release the process and resume when the answer arrives. LangGraph's interrupt() saves state and waits indefinitely until Command(resume=...) arrives with the same thread_id. Temporal's human-in-the-loop recipe waits for a Signal for hours, days or indefinitely using no compute, with a durable timer for the deadline. Step Functions can pause on a task token until its one-year execution limit, and lets you set a heartbeat timeout so a lost callback does not hang forever. Always give the wait a deadline and a defined outcome for silence, and give each request an id so a late or duplicate answer is matched correctly. Human-in-the-Loop covers designing the approval itself.

Deploys: runs outlive code versions

Replay-based systems run your code against old records, so changing code under a running execution can break it. AWS warns that renaming a step or changing its behaviour can leave executions unable to resume, and advises pinning executions to function versions or aliases. Temporal raises a nondeterminism error when code no longer matches the history and recommends Worker Versioning. Anthropic describes rainbow deployments that run old and new versions side by side. A checkpointer avoids replay, but a new version must still be able to load the state an old one saved.

Choosing a layer

A framework checkpointer is the least machinery when you already use that framework and need pauses and crash recovery. A workflow engine fits when runs last days, need timers and signals, or must be inspected and cancelled by operators, and it asks that orchestration code be deterministic. A managed long-running runtime keeps a session alive, but the AgentCore pages read for this lesson describe session lifetimes rather than a record of finished steps, so it does not replace the layers above.

Worked example: A refund agent that dies right after the refund, replayed under three recovery designs

The task is "Refund order 1001 in full." A script stands in for the model, so every run prints the same text. The agent makes three model calls: look up the order, issue the refund, write the answer. The first lookup fails once with a simulated HTTP 503, to show a retry. Then the process is killed right after the payment API accepted the refund and before the journal was written, which is the worst moment. The program replays this under three designs: A restarts from scratch, B keeps a journal, C keeps a journal and sends an idempotency key.

Save this as durable_agent.py. It needs only the standard library (Python 3.9 or later).

python
import json
import os
import tempfile

MAX_ATTEMPTS, FIRST_DELAY, FACTOR, CAP = 4, 1.0, 2.0, 100.0


class SimulatedCrash(Exception):
    """A killed process: out-of-memory kill, lost node, deploy."""


class TransientError(Exception):
    """A timeout or an HTTP 503."""


def load(path, default):
    if path is None or not os.path.exists(path):
        return default
    with open(path) as handle:
        return json.load(handle)


def save(path, data):  # write a temp file, then rename: never a half-written file
    fd, tmp = tempfile.mkstemp(dir=os.path.dirname(path))
    with os.fdopen(fd, "w") as handle:
        json.dump(data, handle)
    os.replace(tmp, path)


def refund(ledger, order, amount, key=None):
    """Simulated payment API: a repeated key returns the saved reply."""
    data = load(ledger, {"refunds": [], "by_key": {}})
    if key in data["by_key"]:
        return data["by_key"][key]
    reply = {"refund_id": f"re_{len(data['refunds']) + 1}", "order": order, "amount": amount}
    saved = {key: reply} if key else {}
    save(ledger, {"refunds": [*data["refunds"], reply], "by_key": {**data["by_key"], **saved}})
    return reply


def make_tools(ledger, faults):
    def lookup_order(order):
        if faults["503s"] > 0:  # inject one failure
            faults["503s"] -= 1
            raise TransientError("HTTP 503")
        return {"amount": 42.5}

    return {"lookup_order": lookup_order,
            "refund": lambda order, amount, key=None: refund(ledger, order, amount, key)}


def scripted_model(seen):  # stands in for an LLM
    if not seen:
        return {"tool": "lookup_order", "args": {"order": "1001"}}
    if len(seen) == 1:
        return {"tool": "refund", "args": {"order": "1001", "amount": seen[0]["amount"]}}
    return {"final": f"Refunded {seen[1]['amount']:.2f} ({seen[1]['refund_id']})."}


def with_retries(work):
    for attempt in range(1, MAX_ATTEMPTS + 1):
        try:
            return work()
        except TransientError as error:
            if attempt == MAX_ATTEMPTS:
                raise
            delay = min(FIRST_DELAY * FACTOR ** (attempt - 1), CAP)
            print(f"    attempt {attempt} failed ({error}); retry in {delay:.1f}s")  # then sleep(delay)


def durable_step(journal, key, work, crash_after):
    """Run work() once per key; a finished key is answered from the journal."""
    done = load(journal, {})
    if key in done:
        print(f"  replay    {key}")
        return done[key]
    result = with_retries(work)
    if key == crash_after:
        raise SimulatedCrash(f"{key} ran, but the process died before journaling it")
    if journal:
        save(journal, {**done, key: result})
    print(f"  executed  {key}")
    return result


def run_agent(run_id, journal, tools, stats, use_key, crash_after=None):
    seen = []
    for index in range(6):
        def ask():
            stats["model"] += 1
            return scripted_model(seen)

        reply = durable_step(journal, f"{run_id}/{index}/model", ask, crash_after)
        if "final" in reply:
            return reply["final"]
        args = {**reply["args"], **({"key": f"{run_id}/{index}/refund"} if use_key and reply["tool"] == "refund" else {})}

        def act():
            stats["tool"] += 1
            return tools[reply["tool"]](**args)

        seen = [*seen, durable_step(journal, f"{run_id}/{index}/tool", act, crash_after)]


def scenario(title, keep_journal, use_key):
    print(f"=== {title}")
    with tempfile.TemporaryDirectory() as folder:
        ledger = os.path.join(folder, "ledger.json")
        journal = os.path.join(folder, "journal.json") if keep_journal else None
        stats, tools = {"model": 0, "tool": 0}, make_tools(ledger, {"503s": 1})
        print("process 1:")
        try:
            run_agent("r1", journal, tools, stats, use_key, crash_after="r1/1/tool")
        except SimulatedCrash as crash:
            print(f"  CRASH: {crash}")
        print("process 2 (restarted):")
        answer = run_agent("r1", journal, tools, stats, use_key)
        refunds = load(ledger, {"refunds": []})["refunds"]
        print(f"answer: {answer}\nmodel calls {stats['model']}, tool calls {stats['tool']}, "
              f"refunds {len(refunds)} totalling {sum(r['amount'] for r in refunds):.2f}\n")


if __name__ == "__main__":
    scenario("A. Restart from scratch, no key", keep_journal=False, use_key=False)
    scenario("B. Journal only", keep_journal=True, use_key=False)
    scenario("C. Journal and idempotency key", keep_journal=True, use_key=True)

Run python3 durable_agent.py. Scenario C prints the text below, and A and B print the same process 1.

What to notice:

  • Restarting repeats work and the effect (A). Process 2 pays for every model call again, 5 instead of 3, and issues a second refund.
  • A journal removes the repeated calls (B). Three finished steps are replayed without calling anything. The refund step was never recorded, so it ran again and created a second refund.
  • A key closes the gap (C). Process 2 sends the same key, r1/1/refund, and the service returns the saved response re_1 instead of acting. The key repeats because the run id and step index repeat, and the arguments repeat because the model reply came from the journal.
  • The retry costs one tool call. The 4 tool calls in B and C are the failed lookup attempt, the lookup that worked, and two refund calls. The 1.0 second backoff was printed, not slept.

Edge cases and limitations

Long-running is not the same as durable
A managed runtime that keeps a session alive for hours protects slow work, not lost work. AgentCore Runtime terminates a session's microVM after 15 idle minutes by default and limits a microVM to at most 8 hours (14 days on a capacity provider). A blocking handler that stops the health check from answering can get a busy agent terminated at the idle limit. A session can outlive its microVM because a new one is provisioned, but the AWS pages read describe lifetimes, not step-level recovery. Temporal's page on running Workers in AgentCore says a session is the compute that runs a Worker, not a durable place to store Workflow state (a pre-release integration). Put a checkpointer or an engine inside the runtime if you need recovery.
A replay must walk the same path as the record
Replay re-executes your code and expects the same sequence of steps as the record. Renaming or reordering steps, or branching on a clock, a random value or I/O outside a recorded step, can leave a run unable to resume. AWS warns that renaming a step can make in-flight executions fail to resume, and Temporal returns a nondeterminism error when Workflow code no longer matches history. Keep such decisions inside recorded steps and pin or version running executions.
The newest checkpoint may be missing
LangGraph's exit durability mode saves nothing mid-run, so a crash loses the intermediate state. Its async mode writes while the next step runs, so a crash can lose the last checkpoint. Use sync when redoing a step is costly or unsafe and accept the write cost. The in-memory saver loses every checkpoint when the process restarts, so it is for experiments only; use Postgres or another persistent saver in production.
State written outside a step disappears on replay
AWS notes that if a step body writes to a variable outside itself, replay returns the cached result and skips the body, so the variable keeps its initial value. The first run looks right and the resumed run is wrong. Return the value from the step and update shared state in the handler. The same trap exists in any design that returns saved results instead of re-running code.
Durable runs do not give a new session its memory
Durable execution keeps one run alive through process failures. It does not carry knowledge from one context window to the next. Anthropic describes agents working in discrete sessions where each new session starts with no memory, bridged by a progress file, git history and a structured feature list. Plan for both a durable run and a hand-off record; the Agent Memory and Context Engineering lessons cover the second part.
Cancellation only reaches code that is listening
Temporal delivers a cancellation to an Activity when it heartbeats, so an Activity that never heartbeats cannot receive one, and a cancellation can be requested only once. A call that never checks keeps running until it ends or times out, and in plain Python a timed-out thread keeps running too (Exercise 1 shows this). Cancelled work may already have changed the outside world, so decide in advance what compensates for it.

When to use it, and when something simpler is enough

Use it when

  • A run lasts longer than a request timeout or the gap between deploys, so a process restart during a run is expected rather than rare.
  • Steps have effects you cannot afford to lose or repeat, such as payments, tickets, emails or writes to a customer system.
  • The run must wait for a person or an external event for hours or days, and holding a process open for the whole wait would be wasteful or impossible.
  • Redoing finished work is expensive, as with long research runs where every restart repeats many model calls and the user is waiting.

Think twice when

  • The whole run is one model call or a few seconds of reads. The client can simply retry the request, and a journal would add machinery with nothing to protect.
  • Every step is a cheap read and can be repeated freely. A plain retry around the whole run is enough.
  • Nobody can operate an engine or a database for run state. Start with a managed checkpointer or a job queue rather than a system the team cannot keep healthy.

A simpler alternative. A job queue with a retry limit, plus idempotency keys on every side-effecting call, covers many agents whose runs finish in a few minutes. It stops being enough when runs wait for days, need timers and cancellation, fan out and join, or must be inspected by operators, which is when a checkpointer or a workflow engine pays for itself.

Key takeaways

  • Durable execution saves the result of each finished step, so a new process can skip completed work after a crash, a deploy or a long wait instead of starting over.
  • A checkpointer snapshots state at step boundaries, while a workflow engine records results and replays deterministic code against them. Both answer a finished step from the record.
  • Recovery is at-least-once, because a step can finish and the process die before the result is saved, so every side-effecting tool call needs an idempotency key that stays the same across retries and resumes.
  • Give every call a timeout, retry only temporary errors with capped exponential backoff, and treat cancellation as a request that reaches only code that is listening.
  • A wait for a person should save state and release the process, with a deadline and a defined outcome for silence.
  • A long-lived session is not a durable run, and runs outlive code versions, so check what your runtime really saves and plan how in-flight runs meet a deploy.

Example 1 of 5

LangGraph checkpointers and interrupt(): resuming after a failure or a human reply

LangChainDocumented in official docs

LangGraph is LangChain's library for stateful agent graphs. Its Checkpointers, Interrupts and Persistence documentation pages describe how a compiled graph saves its state and how a run is paused and resumed later. [1][2][3]

The problem

An agent graph can fail partway through, because a node raises or the process is killed, or it can need an answer from a person before it continues. Without saved state the run would restart from its first node, and a pause would mean keeping a process alive for as long as the person takes to reply.

Where this topic fits

The checkpointer sits underneath the graph. The graph is compiled with it, every invocation carries a thread_id, and the checkpointer saves state at super-step boundaries. interrupt() is a pause point inside a node that uses the same saved state, so crash recovery and human pauses share one mechanism.

How it is applied, step by step

  1. Compile the graph with a checkpointer, backed by a database such as Postgres in production, and invoke it with a thread_id in the config.
  2. After each super-step, one tick in which the scheduled nodes run, the checkpointer saves a snapshot of the state. It also stores each node's writes as that node finishes.
  3. If one node of a super-step fails, the writes of the nodes that succeeded are kept. Resuming the thread from that super-step continues without re-running those nodes.
  4. For an approval, a node calls interrupt(payload). LangGraph saves the state, returns the payload to the caller, and waits with no time limit.
  5. Later, possibly in another process, the caller invokes the graph with Command(resume=value) and the same thread_id. The node runs again from its first line, and interrupt() now returns the value.
  6. The durability setting decides when snapshots are written: when the run exits, asynchronously while the next step runs, or synchronously before the next step starts.

Why this approach fits

A graph's state is already an explicit object, so saving it at step boundaries is natural. One mechanism then gives crash recovery, human pauses and replay for debugging. The pause costs a row in a database rather than a running process, which is what makes a three-day wait practical.

Limitation or tradeoff

Recovery is at the grain of a super-step or a node. A node that dies halfway is re-run from its first line, so a side effect inside it can happen twice, and the interrupt documentation asks for idempotent operations before interrupt(). In exit mode a crash mid-run loses intermediate state, and the in-memory saver loses everything when the process restarts.

What the sources document

  • A checkpoint is a snapshot of graph state saved at each super-step. A thread_id is required, and without it the checkpointer cannot save state or resume after an interrupt. [1]
  • When a node fails in the middle of a super-step, LangGraph stores the pending writes of the nodes that succeeded, so resuming from that super-step does not re-run them. [1]
  • There are three durability modes. exit saves only when the run exits and cannot recover from a crash mid-run, async saves while the next step runs with a small risk of a missing checkpoint after a crash, and sync saves before the next step starts, giving high durability at some cost in speed. [1]
  • interrupt() saves the state and waits indefinitely. Execution resumes with Command(resume=...) and the same thread ID, and the node restarts from its beginning, so code before the interrupt runs again. [2]
  • The in-memory checkpointer keeps checkpoints in RAM and loses them when the process restarts. The page lists PostgresSaver for production and SqliteSaver for local development as persistent alternatives. [3]

The facts above come from the cited sources. The steps and analysis in this example are our explanation of how they fit together.

Example 2 of 5

Temporal running an OpenAI Agents SDK agent as a durable workflow with human approval

Temporal TechnologiesDocumented in official docs

Temporal's documentation on Workflows, Activities and retry policies, together with two AI Cookbook recipes, one for the OpenAI Agents SDK integration and one for a human-in-the-loop agent, describes an agent loop that runs as a Temporal Workflow with model and tool calls as Activities. [4][6][5][7][11]

The problem

An agent loop calls models and tools over the network, any of which can fail or hang, and some actions need a person to approve them after an unknown delay. The process hosting the loop can crash or be redeployed while all of this is going on.

Where this topic fits

Temporal wraps the loop. The agent code runs inside a Workflow, each call that touches the outside world runs as an Activity with its own timeout and retry policy, and a Signal carries the human decision back in.

How it is applied, step by step

  1. The agent runs inside a Workflow. The OpenAI Agents SDK plugin runs the model invocation as an Activity, and tools are exposed to the agent with activity_as_tool, each with a start_to_close_timeout.
  2. Each Activity result is appended to the Event History, the durable record of the Workflow Execution.
  3. A failed Activity is retried by the Temporal service under its Retry Policy. The default starts at 1 second, multiplies by 2.0, caps at 100 seconds and has no attempt limit, so timeouts are what bound the work.
  4. If the Worker process dies, another Worker fetches the Event History, replays the Workflow code against it to rebuild local state, and continues from the point of failure.
  5. For a risky action the Workflow waits for a Signal with workflow.wait_condition and a timeout. The decision may arrive hours or days later, and while it waits the agent uses no compute.
  6. On approval the Workflow runs the action. On rejection or timeout it cancels it.

Why this approach fits

The loop is mostly waiting on external services, which is what Activities with timeouts and retries are built for. Because Temporal replays the Workflow code, the orchestration can be ordinary control flow and still survive crashes, and a long human wait becomes a record in the service rather than a held connection.

Limitation or tradeoff

Workflow code must be deterministic, so anything non-deterministic belongs in an Activity. Activities run at least once: Temporal documents that a Worker can crash after an Activity succeeds but before it reports, so the call is retried and needs an idempotency key. Changing Workflow code under running executions can produce a nondeterminism error, which is why Temporal recommends Worker Versioning.

What the sources document

  • A started Workflow runs to completion, whether that takes a second or a year. If its process crashes, a new Worker fetches the Event History, replays the Workflow code against it to rebuild state, and continues from the point of failure. [4]
  • The recipe says LLM invocation is an external call that would normally run in a Temporal Activity, and the OpenAI Agents SDK integration handles it so the developer writes no such Activity. Activities become agent tools with activity_as_tool and a per-tool start_to_close_timeout, and the plugin takes a start_to_close_timeout for model calls. [6]
  • In the human-in-the-loop recipe the agent can wait for approval for hours, days or indefinitely while consuming no compute, approvals arrive as Signals, and time limits on the wait are durable timers that survive execution disruptions. [5]
  • The default Activity Retry Policy uses exponential backoff with a 1-second initial interval, a 2.0 coefficient, a 100-second maximum interval and unlimited attempts. Workflow Executions do not retry by default. [7]
  • Workflow code must make the same Workflow API calls in the same order given the same input. After a code change a mismatch with the history produces a nondeterminism error, and Worker Versioning is the recommended way to handle versioning. [11]

Example 3 of 5

Anthropic's Research feature resuming agents after errors and deploying around running agents

AnthropicDocumented in an engineering article

Anthropic's June 2025 engineering article "How we built our multi-agent research system" describes the Research feature, in which a lead agent plans a research process and creates parallel agents that search. Its section on production reliability covers state, errors and deployments. [12]

The problem

Research agents run for long periods and keep state across many tool calls, so a minor failure can derail a whole run, and a restart from the beginning is expensive and frustrating for the user. Deploying new code while agents are mid-run adds a second risk, because an agent can be at any point in its process when the update lands.

Where this topic fits

Durability sits around the agent loop as deterministic safeguards. The model supplies adaptive behaviour. The surrounding system supplies retries, checkpoints, resumption from the point of error, and a deployment method that does not move every running agent to new code at once.

How it is applied, step by step

  1. A user query starts a run. A lead agent plans the research and creates parallel agents that call tools over many steps, so a single run holds a lot of state.
  2. When an error occurs the system does not restart the run. It resumes from where the agent was when the error occurred.
  3. When a tool is failing, the agent is told so and adapts, for example by trying a different approach. The authors say this works surprisingly well.
  4. Retry logic and regular checkpoints wrap the model's behaviour as deterministic safeguards.
  5. For a release, traffic shifts gradually from the old version to the new one with both running at the same time. In a typical implementation this lets runs that are already in progress finish on the version they started with.

Why this approach fits

Research runs vary a lot in length and cost, so redoing finished work wastes money and keeps a user waiting. Resuming and gradual rollout protect the same asset, which is the progress a run has already made.

Limitation or tradeoff

The article describes the approach at a high level. It does not say how checkpoints are stored or how a resumed agent rebuilds its context, so it is a design signal and not a recipe. Running two versions at once also costs capacity and attention. The authors add that lead agents currently run subagents synchronously, so the whole system can be blocked while waiting for one slow subagent.

What the sources document

  • The authors say agents can run for long periods and maintain state across many tool calls, so code must be executed durably and errors handled along the way, and that without mitigations minor system failures can be catastrophic for agents. [12]
  • They state that on errors they cannot simply restart from the beginning because restarts are expensive and frustrating for users, so they built systems that can resume from where the agent was when the errors occurred. [12]
  • They combine the adaptability of Claude-based agents with deterministic safeguards such as retry logic and regular checkpoints, and they let the agent know when a tool is failing so it can adapt. [12]
  • Because agents might be anywhere in their process when updates deploy, they use rainbow deployments that gradually shift traffic from old to new versions while keeping both running simultaneously. [12]

Example 4 of 5

OpenAI Responses API background mode for polling, cancelling and resuming a long model call

OpenAIDocumented in official docs

OpenAI's Background mode guide describes running long Responses API requests asynchronously, so that a client polls for the result instead of holding a connection open for the whole call. [14]

The problem

Reasoning models and agentic tasks can take several minutes to answer. One long HTTP request is exposed to timeouts and dropped connections, and a client that crashes while waiting loses track of the work it started.

Where this topic fits

Background mode makes a single model call durable on the provider's side. Your application keeps only the response id, and any later process can look the call up, cancel it, or, if the request also set stream, reattach to its event stream.

How it is applied, step by step

  1. The client sends the request with background set to true. The call runs asynchronously and returns a response object with an id and a status.
  2. The application saves the response id, for example in the run's journal, before it does anything else.
  3. A worker, possibly a different process after a restart, polls the GET endpoint for that id while the status is queued or in_progress. Any other status is terminal.
  4. To stop the work, a client posts to the cancel endpoint for the same id.
  5. For streaming, the client sets both background and stream, remembers the sequence_number of the last event it processed, and after a dropped connection reconnects with starting_after to continue.

Why this approach fits

The slow part of a reasoning step is waiting on the provider. Moving that wait to the provider means a lost connection or a restarted worker costs a poll instead of a re-run, and the response id is a small piece of state that fits naturally in a journal.

Limitation or tradeoff

It protects one model call, not your multi-step agent. The loop, the tool calls and the choice of what to do next still need their own durability. A late poller can also find nothing: for projects using Modified Abuse Monitoring the page says a background response is deleted after roughly 10 minutes unless store=true is set, and Zero Data Retention projects run background requests with store=false and keep the data only about 10 minutes. Cancelling stops the model call but cannot undo effects that your own tools already had.

What the sources document

  • Background mode lets developers run long-running tasks asynchronously and poll response objects to check status over time, without worrying about timeouts or other connectivity issues. [14]
  • Clients keep polling while a response is queued or in_progress. When it leaves those states it has reached a final, terminal state. [14]
  • An in-flight response can be cancelled with a POST request to that response's cancel endpoint. [14]
  • A background response can also be streamed. The client tracks a cursor taken from the sequence_number of each event and can resume with starting_after if the connection drops. [14]
  • For projects with Modified Abuse Monitoring, background responses are retained after the polling period only when store=true is provided explicitly. Otherwise the response is deleted after roughly 10 minutes. [14]

Example 5 of 5

Stripe idempotency keys that make a payment tool safe to retry

StripeDocumented in official docs

Stripe's API reference page "Idempotent requests" documents the Idempotency-Key mechanism for retrying requests safely. Temporal's Activity Definition page and the AWS Durable Execution SDK guide say a retried step should pass such a key, which is the situation of an agent's payment or record-creating tool. [23][9][17]

The problem

A tool call that creates or changes something in an outside system can time out or lose its connection after the server has already acted. The caller cannot tell whether the charge happened, and a durable runtime will retry the step because it never saw a result. Without protection the retry can do the work twice.

Where this topic fits

Idempotency sits on the boundary between the durable runtime and the outside service. The runtime promises that a step is attempted at least once. The service's key check makes repeated attempts have the effect of one.

How it is applied, step by step

  1. Before the first attempt, the harness builds a key from values that do not change between attempts of the same step, such as the run id and the step id.
  2. The tool sends the request with the Idempotency-Key header. For API v1, Stripe saves the status code and body of the first request made with that key, once the endpoint has started executing.
  3. If the connection fails or the worker dies, the runtime retries the step and sends the same key.
  4. Stripe returns the saved response instead of acting again. If the retry's parameters differ from the original request, it returns an error.
  5. The harness records the returned response as the step's result, so a later replay reuses it.

Why this approach fits

A durable runtime trades exactly-once for at-least-once. A key moves deduplication to the service that owns the side effect, where it can be enforced reliably, and deriving the key from run and step ids ties it to the unit that the journal tracks.

Limitation or tradeoff

Keys protect only services that honour them. In the API v1 behaviour on Stripe's page, keys may be pruned after 24 hours, they matter only for POST requests, and a retry with different parameters is rejected. If the model were asked again after a crash and chose different arguments, the retry would fail instead of deduplicating, which is one more reason to replay the recorded model reply.

What the sources document

  • Stripe's API supports idempotency so that requests can be retried safely without performing the same operation twice. The client supplies a unique idempotency key. [23]
  • For API v1, Stripe saves the status code and body of the first request made with a key after endpoint execution begins, and retries with the same key return the saved response, including 500 errors. [23]
  • Keys can be up to 255 characters. Stripe suggests V4 UUIDs or another random string with enough entropy and advises against sensitive data in keys. For API v1, keys can be removed after at least 24 hours, and a request whose parameters differ from the original returns an error. [23]
  • Temporal's documentation says Activities may execute more than once, including when a Worker crashes just after an Activity succeeds, and suggests the Workflow Run ID plus the Activity ID as an idempotency key. [9]
  • The AWS Durable Execution SDK guide says to generate an idempotency key inside a step because a key generated outside a step changes on replay, and to treat a duplicate-request error from an idempotent API as success. [17]

4Common mistakes

  1. Creating a new idempotency key for every attempt of a tool call

    Why it causes problems
    The service treats each retry as a new request, so a retry after a lost reply does the work a second time. That is the exact failure the key exists to prevent, and it only shows up when something goes wrong.
    How to recognise it
    Two refunds, emails or records for one logical step, with different key values in the logs. The key changes between attempts or after a restart.
    How to fix it
    Derive the key from stable identifiers such as the run id plus the step id, or create it once inside a recorded step and pass the same value to every attempt. Treat a duplicate-request error as success.

  2. Placing a side effect above interrupt() in a node that restarts from its first line

    Why it causes problems
    LangGraph runs the node again from its beginning when the run resumes, so anything above interrupt() repeats on every resume. An email or a charge placed there is sent again after each approval.
    How to recognise it
    A customer receives a duplicate message right after a reviewer approves, or a counter in the node increments once per resume.
    How to fix it
    Move the side effect below the interrupt() call or into a separate node, or make it idempotent with a key or an upsert.

  3. Using an in-memory or local-file checkpointer in production

    Why it causes problems
    The in-memory saver loses every checkpoint when the process restarts, and a local file is invisible to another replica. A run that was paused for a human is lost, or restarts from nothing, after the first deploy.
    How to recognise it
    Resuming a known thread_id after a restart finds an empty state, or a run only resumes on the machine that started it.
    How to fix it
    Use a shared persistent store such as Postgres for checkpoints, and test recovery by killing the process in the middle of a run in a staging environment.

  4. Retrying every error forever with no timeout on the call

    Why it causes problems
    A permanent error such as a bad argument or a missing permission fails identically on each attempt. With unlimited attempts and no timeout, a hung call or a hopeless one occupies the run indefinitely and burns money.
    How to recognise it
    Attempt counts in the dozens with the same error text, or runs that stay in the running state for hours without progress.
    How to fix it
    Classify errors and fail fast on non-retryable ones. Set a timeout on every call, cap the backoff, and bound the total retry time or attempts.

  5. Calling the model, the clock or a random generator directly in replayed orchestration code

    Why it causes problems
    On replay the code can take a different path from the record, because the model answers differently and the clock has moved on. The engine then raises a nondeterminism error, or worse, continues with wrong values.
    How to recognise it
    Errors about mismatched commands or steps right after a restart, or a branch that depends on a timestamp or on a fresh model reply outside any recorded step.
    How to fix it
    Move the call into an Activity or step so its first result is recorded, and branch on the recorded value rather than on a fresh call.

  6. Renaming or reordering steps while runs from the old version are still in flight

    Why it causes problems
    A replay compares the code with the stored record. If step names or order no longer match, old runs cannot resume or produce wrong results, and the people who were waiting on them lose their work.
    How to recognise it
    Runs that started before a deploy fail or stall right after it, while newly started runs are fine.
    How to fix it
    Pin each run to the code version it started with, use the engine's versioning feature, add new steps instead of renaming existing ones, and let old runs drain or migrate them deliberately.

Exercise 1

Add timeouts, retries and cooperative cancellation to a step runner

CodingIntermediateAbout 40 min (estimate)Hypothetical scenario

This runner executes tool calls one after another with no protection. Extend it so that a call cannot hang the run, a slow call is retried, and the run can be stopped. Use only the Python standard library.

python
import time

def slow_tool(seconds):
    time.sleep(seconds)
    return f"slept {seconds}s"

def run(steps):
    return [slow_tool(seconds) for seconds in steps]

print(run([0.1, 0.1, 0.1]))

Test it with three inputs: [0.1, 0.1, 0.1], [0.1, 0.8, 0.1], and [0.2, 0.2, 0.2, 0.2] with a cancel request raised 0.35 seconds after the run starts.

Requirements

  • Each call has a timeout of 0.5 seconds. A call that times out is retried up to 2 more times, 3 attempts in all, with a 0.05 second pause between attempts.
  • A step that fails all its attempts ends the run with status failed and the index of the failed step. Steps already completed stay in the results.
  • A threading.Event named cancelled is checked before every attempt. When it is set, the run returns status cancelled with the results so far.
  • slow_tool appends to a module-level list each time a call really finishes, and the demo prints that list sorted at the end, after a one second pause.

Expected behaviour

The first input finishes with three results. The second input prints three timeout lines for step 1 and returns status failed with failed_step 1 and one result. The third input returns status cancelled with two results. The final list shows 0.8 three times, which proves that the timed-out calls kept running after the runner gave up on them.

Hint 1

concurrent.futures.ThreadPoolExecutor can run the call in a worker thread, and future.result(timeout=...) raises concurrent.futures.TimeoutError when the time is up.

Hint 2

Do not use the pool in a with block. Leaving the block waits for the thread, which defeats the timeout. Call pool.shutdown(wait=False) instead.

Hint 3

Python cannot kill a running thread, so a timed-out call carries on in the background. Think about what that means for a tool that charges a card.

Hint 4

A for loop over attempts can use its else clause to detect that every attempt failed.

Show solution

One solution, with the output it prints:

python
import threading
import time
from concurrent.futures import ThreadPoolExecutor, TimeoutError as StepTimeout

STEP_TIMEOUT_S = 0.5
MAX_ATTEMPTS = 3
RETRY_PAUSE_S = 0.05
COMPLETED = []  # every call that really finished, even after the caller gave up on it


def slow_tool(seconds):
    time.sleep(seconds)
    COMPLETED.append(seconds)
    return f"slept {seconds}s"


def call_with_timeout(work, seconds):
    pool = ThreadPoolExecutor(max_workers=1)
    try:
        return pool.submit(work).result(timeout=seconds)
    finally:
        pool.shutdown(wait=False)  # do not wait for a call we have given up on


def run(steps, cancelled):
    results = []
    for index, seconds in enumerate(steps):
        for attempt in range(1, MAX_ATTEMPTS + 1):
            if cancelled.is_set():
                return {"status": "cancelled", "results": results}
            try:
                results = [*results, call_with_timeout(lambda: slow_tool(seconds), STEP_TIMEOUT_S)]
                break
            except StepTimeout:
                print(f"  step {index} attempt {attempt}: timed out after {STEP_TIMEOUT_S}s")
                time.sleep(RETRY_PAUSE_S)
        else:
            return {"status": "failed", "failed_step": index, "results": results}
    return {"status": "finished", "results": results}


if __name__ == "__main__":
    print(run([0.1, 0.1, 0.1], threading.Event()))

    print("-- a step that always exceeds its timeout")
    print(run([0.1, 0.8, 0.1], threading.Event()))

    print("-- cancel requested 0.35s into the run")
    stop = threading.Event()
    threading.Timer(0.35, stop.set).start()
    print(run([0.2, 0.2, 0.2, 0.2], stop))

    time.sleep(1.0)  # let abandoned calls finish before reading the record
    print("calls that really completed:", sorted(COMPLETED))
text
{'status': 'finished', 'results': ['slept 0.1s', 'slept 0.1s', 'slept 0.1s']}
-- a step that always exceeds its timeout
  step 1 attempt 1: timed out after 0.5s
  step 1 attempt 2: timed out after 0.5s
  step 1 attempt 3: timed out after 0.5s
{'status': 'failed', 'failed_step': 1, 'results': ['slept 0.1s']}
-- cancel requested 0.35s into the run
{'status': 'cancelled', 'results': ['slept 0.2s', 'slept 0.2s']}
calls that really completed: [0.1, 0.1, 0.1, 0.1, 0.2, 0.2, 0.8, 0.8, 0.8]

How it works. call_with_timeout submits the call to a one-thread pool and waits at most 0.5 seconds. The for ... else in run reaches else only when no attempt ended in break, so the step has failed all three attempts. The cancel flag is checked at the top of each attempt, so cancellation takes effect between calls, never in the middle of one. In the cancel demo, step 1 finishes at about 0.4 seconds, after the request at 0.35, and the check before step 2 then ends the run.

The last line is the point of the exercise. The step that timed out three times still completed three times in the background. If slow_tool had charged a card, you would have charged it three times. A timeout stops your waiting, not the work, so a retried side-effecting call needs an idempotency key, and a cancellation needs a plan for work that already happened. Timings are approximate, so on a very slow machine the cancel demo may show a different number of results.

Check your answer

  • Does the second demo give up on step 1 after three attempts of at most 0.5 seconds each, instead of waiting for the slow calls to finish?
  • Can you explain why the final list contains 0.8 three times, and what you would add to make a retried charge safe?
  • Does the cancelled run return the results of the steps that finished before the cancel request?
  • Is the pool shut down without waiting, and why does a with block break the timeout?

Exercise 2

Find the crash windows in an invoice-payment agent

DesignAdvancedAbout 30 min (estimate)Hypothetical scenario

An agent processes supplier invoices on a durable runtime that retries a step at least once if its result was lost, on workers that can be killed at any moment. After the model has extracted the invoice data, the loop makes these four tool calls in this order:

  1. save_invoice_record: an SQL INSERT into a table that has a unique constraint on invoice_number.
  2. create_payment: a call to a payment API that accepts an Idempotency-Key header.
  3. send_supplier_email: sends "payment scheduled" through an SMTP relay that cannot deduplicate.
  4. post_ledger_entry: an SQL INSERT into the accounting ledger.

Invoices over 10,000 need approval from a finance manager, who may take up to 3 days to answer. Decide how each call survives a crash and where the approval wait belongs.

Requirements

  • For each of the four calls, state what a retry does if the worker died after the call took effect but before its result was saved.
  • Name a protection for each call (idempotency key, unique constraint, upsert, at-most-once with no retry, or a reconciliation check) and give the key value where one is used.
  • Say where the approval wait goes in the sequence, what is saved while waiting, and what the worker does during the wait.
  • Define the outcome and the notification when 3 days pass without an answer.

Expected behaviour

A table or list that covers all four calls with a retry outcome and a protection, an approval step placed before the payment is created, a description of the saved request, and an explicit expiry outcome.

Hint 1

Ask of each call what the world looks like after a second run. Is anything created twice?

Hint 2

The unique constraint on invoice_number turns a duplicate INSERT into an error. Decide whether that error means failure or success, and what else you must store to tell a retry from a genuinely duplicate invoice.

Hint 3

Compare the cost of a duplicate email with the cost of a missing one before choosing between at-least-once and at-most-once.

Hint 4

The approval request needs an id, so that a late or repeated answer can be matched to the right invoice.

Show solution
CallWhat a retry doesProtection
save_invoice_recordThe second INSERT hits the unique constraint on invoice_number and raises an errorStore the run id in the row. On that specific error, read the existing row: if it carries this run's id the retry already succeeded, so treat the error as success; if it carries another run's id, report a duplicate invoice. The record is then safe to repeat
create_paymentWithout protection, a second paymentSend Idempotency-Key built from run id and step id, for example run-7f3a/step-3-create_payment. The key is identical on every retry and replay, so the API returns the first response
send_supplier_emailA second email, because the relay cannot deduplicateChoose by consequence. A duplicate "payment scheduled" email is a nuisance, so at-least-once is defensible. If duplicates matter, run the step at-most-once with no retry and add a check against a sent-mail table, accepting that a rare email may be missing
post_ledger_entryA second ledger lineAdd a unique key such as (invoice_number, entry_type) and treat the duplicate error as success

Approval wait. Put it after save_invoice_record and before create_payment, because paying is the only step that cannot be undone cheaply. For invoices over 10,000 the run saves an approval request with its own request id, the invoice number, the amount and the deadline (now plus 3 days), then pauses. Use whatever your runtime offers for this: a LangGraph interrupt, a Temporal Signal with a timer, or a Step Functions task token with a heartbeat. While it waits, no worker holds the run, so a deploy or crash during those 3 days costs nothing. The answer must carry the request id so that a late or duplicate answer is matched to the right invoice and ignored if the request has already closed.

Expiry. When 3 days pass with no answer, do not pay and do not leave the run hanging. Mark the invoice "approval expired", notify the finance manager and the requester, and optionally escalate a day earlier. Record the outcome in the journal so the run ends in a visible final state.

Common wrong answers: generating a fresh random key inside each attempt (the retry then pays twice), putting the payment before the approval, and holding a worker thread open for 3 days.

  • Is the approval wait placed before the payment, with a request id and a deadline saved?
