Infrastructure as Code (Terraform)

Infrastructure as code (IaC) means describing servers, networks, permissions and other cloud resources in text files kept in version control, and letting a tool create and change the real resources to match. Terraform is a widely used tool of this kind: you declare the end state you want, and it works out and applies only the difference.

1Overview

Why it matters

A pilot that works in your own cloud account has to be rebuilt in someone else's. The customer has a different network range, a different identity setup, different quotas, and a security team that wants to know what will be created before anything is. Rebuilt by hand from memory and screenshots, the copy differs from the original in ways nobody wrote down, and the difference shows up as an outage during the demo.

Infrastructure as code turns the environment into files that can be reviewed, repeated and deleted. It decides the outcome whenever the same environment must exist twice, whenever a change needs a second pair of eyes, and whenever leftovers cost money, such as GPU nodes or managed databases still running after a pilot ends. Anyone who deploys AI services into environments they do not own, from forward deployed engineers to platform teams, needs to read a plan, understand what the state file is, and know why a one-line edit can rebuild half of an environment.

What you will be able to do

  • Explain what declarative means for infrastructure and why a declaration can be applied twice safely.
  • Read a Terraform configuration and name its providers, resources, variables, outputs and the dependencies between resources.
  • Read the symbols in a plan (+, ~, - and -/+) and say what each one does to real resources.
  • Explain what the state file records, why it needs locking and a remote home, and what drift is.
  • Trace a plan by hand for a four-resource environment, including the order in which resources are built and removed.
  • Design how to reproduce an environment in a customer's cloud account, covering inputs, credentials, state, review and teardown.

Key terms

Infrastructure as code (IaC)
Managing infrastructure through files that can be versioned, reviewed and rerun, instead of through manual clicks or one-off commands.
Declarative configuration
A description of the end state you want. The tool decides which actions are needed to reach it from the current situation.
Provider
A plugin that teaches Terraform about one platform, such as AWS or Cloudflare, by adding resource types that it creates, reads, updates and deletes through that platform's API.
Resource
One infrastructure object declared in a configuration, for example a network or a server. Its address is the resource type plus a local name, such as aws_vpc.main.
State
Terraform's record of which real objects it created for which resource addresses, together with their attributes. It is stored in a file, usually in a remote backend.
Plan
The list of actions Terraform proposes after comparing the configuration with the state and the real objects. Reading it before applying is the main safety step.
Apply
The step that carries out a plan by calling the provider APIs in dependency order and then records the results in the state.
Module
A directory of Terraform files that is reused as a unit. Every configuration is a root module and can call child modules with inputs and outputs.
Backend
The place where state is stored and, if the backend supports it, locked while an operation runs, for example an S3 bucket.
Drift
A difference between the real infrastructure and what Terraform's state records, usually caused by someone changing a resource outside Terraform.

2Explanation

Introduction

In Cloud Platform Fundamentals you created resources by clicking through a console: a network, a subnet, a server, a role. That works once. The second time you have to remember every click, and by the tenth time a colleague asks what exactly is running in production and why. The honest answer is often "whatever someone set up last spring".

Infrastructure as code (IaC) replaces the clicks with files. You write down what should exist, keep the files in Git like any other code, and let a tool talk to the cloud's APIs for you. Terraform is a widely used tool of this kind and the subject of this lesson. Its files are declarative: they describe the end state (one network, one subnet, one server of this size) rather than the commands that produce it. A script that says "create a network" creates a second network when you run it twice. A declaration that says "there is one network" is already satisfied the second time, so nothing happens.

For that to work, Terraform has to know what it has already built. It keeps a record called the state, compares your files with the state and with the real resources, and prints a plan: the exact list of things it would create, change or delete. You read the plan, and only then apply it. Think of it as git diff for infrastructure, with the difference that the diff can be carried out.

The lesson covers each step of that loop, then providers (the part that talks to the cloud), the dependency graph that orders the work, state and drift, and modules for reuse. A worked example traces a plan by hand in runnable Python. The last section is about the situation forward deployed engineers meet most often: reproducing an environment inside a customer's cloud account, where the account, the credentials and the reviewers are not yours. Five documented systems show how real teams apply these ideas.

How it works

This lesson uses Terraform 1.16, the release line shown in HashiCorp's Terraform introduction (opens in a new tab) when the page was read. Other tools use the same ideas with different syntax, and one of them appears in the examples.

Declarative configuration

Terraform reads files ending in .tf, written in HashiCorp Configuration Language (HCL). The introduction calls them declarative, meaning that they describe the end state of your infrastructure: Terraform works out the dependencies itself and creates or modifies non-dependent resources in parallel. This small configuration shows the main blocks. It is a teaching example and has not been run against a real account:

hcl
terraform {
  required_version = ">= 1.11"
  required_providers {
    aws = {
      source  = "hashicorp/aws"
      version = "~> 6.0"
    }
  }
}

variable "region" {
  type    = string
  default = "eu-west-1"
}

provider "aws" {
  region = var.region
}

resource "aws_vpc" "main" {
  cidr_block = "10.0.0.0/16"
}

resource "aws_subnet" "app" {
  vpc_id     = aws_vpc.main.id   # a reference: Terraform must build the VPC first
  cidr_block = "10.0.1.0/24"
}

output "subnet_id" {
  value = aws_subnet.app.id
}
  • The terraform block pins the Terraform version and names the providers the configuration needs.
  • A variable is an input and an output publishes a value. A provider block configures the plugin, here with a region.
  • A resource block declares one object. aws_vpc.main is its address: the resource type, a dot and a local name. The address is also the key under which the state remembers the real object.
  • An expression such as aws_vpc.main.id reads an attribute of another resource.

Providers turn declarations into API calls

Terraform core knows nothing about AWS or Cloudflare. Each platform is covered by a plugin called a provider (opens in a new tab), which adds resource types and data sources. Providers ship separately from Terraform and have their own release cadence and version numbers. terraform init downloads the providers a configuration declares, and Terraform records the exact versions it chose in .terraform.lock.hcl. HashiCorp says to commit that file so that every machine installs the same versions.

Cloudflare's engineers describe Terraform, as an API vendor sees it, as essentially an HTTP client with lifecycle management built in (Cloudflare's post on its generated provider (opens in a new tab)): it uses the platform's public API to create, read, update and delete each object over its life, and the provider is the plugin that holds that knowledge for one platform. That is why one tool can manage a VPC, a DNS record and a SaaS workspace in the same plan.

References build a dependency graph

When one resource refers to another with <TYPE>.<LABEL> syntax, such as aws_vpc.main, Terraform records a dependency, as the resource documentation (opens in a new tab) explains. depends_on adds a dependency that no reference reveals, for example an IAM policy that must exist before a server can use it. The meta-arguments count and for_each create several instances from one block, and lifecycle settings such as prevent_destroy and create_before_destroy change how replacement behaves. prevent_destroy makes Terraform reject a plan that would destroy the resource, but, as the resource documentation notes, it does not protect a resource whose block you delete.

From these edges Terraform builds a graph and walks it. In the graph internals (opens in a new tab) a node is walked as soon as all of its dependencies have been walked, with up to ten nodes in flight by default (the -parallelism flag). The page also notes that the destroy order is often different from the create order, which is why a replacement is split into a destroy step and a create step. In practice a network can only be deleted after the subnets inside it.

State maps addresses to real objects

The state (opens in a new tab) is a JSON file, terraform.tfstate by default, that binds each address in your configuration to a remote object and stores its attributes. HashiCorp gives three reasons for it: mapping configuration to real resources, keeping metadata, and performance on large infrastructures. Because the state can hold secrets, the documentation advises against keeping it in version control or in any storage that lacks locking and secure access control, which risks data loss or exposed secrets.

Teams therefore keep state in a backend. The S3 backend (opens in a new tab) needs a bucket, a key and a region; HashiCorp strongly recommends enabling bucket versioning, supports server-side encryption, and offers lock files in the bucket through use_lockfile (the older DynamoDB locking is deprecated):

hcl
terraform {
  backend "s3" {
    bucket       = "example-terraform-state"
    key          = "customer-a/prod/terraform.tfstate"
    region       = "eu-west-1"
    encrypt      = true
    use_lockfile = true
  }
}

Plan: a three-way comparison

terraform plan (opens in a new tab) reads the current state of the remote objects that already exist, compares the configuration with the prior state, and proposes the actions that would make the real objects match. Its symbols are + create, - destroy, ~ update in place and -/+ replace (destroy and create). Whether an edit can be applied in place or forces a replacement is decided by the provider's schema for each argument.

-out=FILE saves the plan so that automation can apply exactly that plan later. The file holds your full configuration, the planned values and the input variables, and any sensitive data in it is saved in cleartext, so treat it as sensitive. -detailed-exitcode makes the command return 0 for no changes, 1 for an error and 2 when changes are proposed, which lets a CI job notice a difference.

Apply and what happens when it fails

terraform apply (opens in a new tab) either makes a fresh plan and asks for approval, or applies a saved plan file without prompting. If an operation fails, Terraform reports the error, records in the state what did succeed, and stops. It does not roll back a partly finished apply. You fix the cause and run again; the next plan shows only what is still missing.

Drift

Changing a managed resource in the console puts the real object out of step with the state. HashiCorp's drift tutorial (opens in a new tab) explains the two responses: a normal terraform plan or apply tries to revert the manual change to what the configuration says, while terraform apply -refresh-only accepts it by updating the state without touching the resource. The tutorial then edits the configuration to match the change and imports the object that was created by hand, so that code, state and reality agree again.

Modules and inputs

A module (opens in a new tab) is a collection of resources managed together. Every configuration is a root module; a module block calls a child module, with a source and, for registry modules, a version. Inputs are the child's variables and outputs are its results:

hcl
module "network" {
  source     = "./modules/network"
  cidr_block = var.cidr_block
  name       = "customer-${var.customer}"
}

Values for variables come from -var and -var-file options, *.tfvars files, TF_VAR_ environment variables or defaults, and the variables page (opens in a new tab) lists the precedence order, with command-line options winning. One .tfvars file per environment is the usual way to run the same code with different inputs.

Reproducing an environment in a customer's account

The pieces above combine into a repeatable procedure. Each point answers a question the customer's security team will ask.

QuestionPractice
What differs between customers?Put it in variables: account or project id, region, address ranges, names, tags. Keep modules and provider versions identical.
What already exists in the account?Pass the ids of existing networks and roles in as inputs instead of creating copies, and let the configuration own only what it created.
Whose identity runs this?A role in the customer's account that your credentials assume. The AWS provider's assume_role block (opens in a new tab) takes a role_arn and an optional external_id.
Where does state live?One state per customer and environment, in a backend the customer accepts. CLI workspaces (opens in a new tab) share one backend and its credentials, so they are not suited to separate credentials and access controls. The S3 backend (opens in a new tab) authenticates on its own, with its own assume_role setting, separately from the provider block.
What will change?Run plan -out, show the reviewers the plan (terraform show renders a saved plan file), and apply that same plan file.
Will we get the same versions?Commit .terraform.lock.hcl, pin required_version, and pin module versions.
How does it end?Plan the teardown first: deletion protection, dependent data, and the order in which things must go.

Worked example: Tracing a plan by hand for a four-resource environment

Terraform's plan runs inside a compiled program against real APIs, which hides the logic. This example is a short Python model of that logic that runs with nothing installed. It is a teaching model, not Terraform: the resource types are invented (toy_network and so on) and the "state" is a dictionary. What it reproduces is the comparison of configuration, state and provider schema, and the way references form dependencies.

The environment has four resources. The subnet and the firewall rule belong to the network. The server sits in the subnet and also waits for the rule.

A string such as "@toy_network.main" is a reference, like aws_vpc.main.id in HCL. References and depends_on together are the dependencies. FORCE_NEW plays the part of a provider schema: it lists the arguments that cannot be changed in place.

python
from graphlib import TopologicalSorter

# A provider schema in miniature: arguments that cannot change in place.
FORCE_NEW = {"toy_network": {"cidr"}, "toy_subnet": {"network_id"},
             "toy_rule": {"network_id"}, "toy_server": {"subnet_id"}}
SYMBOL = {"create": "+", "update": "~", "replace": "-/+", "destroy": "-"}


def deps_of(resource):  # references and depends_on are dependencies
    refs = {v[1:] for v in resource["attrs"].values() if str(v).startswith("@")}
    return refs | set(resource.get("depends_on", []))


def plan(desired, state):
    actions = {}
    for addr in TopologicalSorter({a: deps_of(r) for a, r in desired.items()}).static_order():
        res = desired[addr]
        if addr not in state:
            actions[addr] = "create"
            continue
        changed = {k for k, v in res["attrs"].items()
                   if (actions[v[1:]] in ("create", "replace") if str(v).startswith("@")
                       else state[addr].get(k) != v)}  # a rebuilt target has a new id
        actions[addr] = ("no-op" if not changed
                         else "replace" if changed & FORCE_NEW[res["type"]] else "update")
    actions.update({a: "destroy" for a in state if a not in desired})
    return actions


def config(cidr, size, server=True):
    res = {"toy_network.main": {"type": "toy_network", "attrs": {"cidr": cidr}},
           "toy_subnet.app": {"type": "toy_subnet", "attrs": {"network_id": "@toy_network.main", "zone": "a"}},
           "toy_rule.https": {"type": "toy_rule", "attrs": {"network_id": "@toy_network.main", "port": 443}}}
    if server:
        res["toy_server.api"] = {"type": "toy_server", "depends_on": ["toy_rule.https"],
                                 "attrs": {"subnet_id": "@toy_subnet.app", "size": size}}
    return res


STATE = {"toy_network.main": {"id": "net-1", "cidr": "10.0.0.0/16"},  # the state after the first apply
         "toy_subnet.app": {"id": "sub-1", "zone": "a"},
         "toy_rule.https": {"id": "rule-1", "port": 443},
         "toy_server.api": {"id": "srv-1", "size": "small"}}


def show(title, desired, state):
    actions = plan(desired, state)
    print(title)
    for addr, act in sorted(actions.items()):
        if act != "no-op":
            print(f"  {SYMBOL[act]:>3} {addr}")
    n = lambda *kinds: sum(a in kinds for a in actions.values())
    print(f"  Plan: {n('create', 'replace')} to add, {n('update')} to change, {n('destroy', 'replace')} to destroy.")


if __name__ == "__main__":
    show("A. first apply (empty state)", config("10.0.0.0/16", "small"), {})
    show("B. server size small -> large", config("10.0.0.0/16", "large"), STATE)
    show("C. network CIDR 10.0.0.0/16 -> 10.1.0.0/16", config("10.1.0.0/16", "small"), STATE)
    show("D. server removed from the configuration", config("10.0.0.0/16", "small", server=False), STATE)
    show("E. configuration unchanged", config("10.0.0.0/16", "small"), STATE)

Save it as mini_plan.py and run python3 mini_plan.py (Python 3.9 or later, for graphlib). The __main__ guard keeps the five scenarios from printing when Exercise 1 imports this file. Output from Python 3.13:

text

  Plan: 4 to add, 0 to change, 0 to destroy.

    ~ toy_server.api
  Plan: 0 to add, 1 to change, 0 to destroy.

ScenarioWhy the plan looks like this
ANothing is in the state, so every resource is created.
Bsize is not in the server's FORCE_NEW set, so the change is an update in place.
Ccidr forces the network to be replaced. The new network has a new id, so the subnet and rule, whose network_id is a reference, see a changed value, and network_id forces replacement. The server's subnet_id then changes in the same way. One edited line rebuilds the environment.
DThe server is in the state but no longer in the configuration, so it is destroyed.
EState and configuration agree, so there is nothing to do.

The order of the work follows the graph. In scenario A the network goes first, the subnet and the rule can then be built at the same time, and the server comes last. In scenario C the destroys run in reverse: server, then subnet and rule together, then network; the creates then run forward again. Exercise 1 asks you to compute these waves in code.

The model leaves out what makes the real thing harder: values only known after apply, a refresh against the live API before comparing, create_before_destroy, nested modules and the provider calls themselves. The comparison it shows is the one you read in every real plan.

Edge cases and limitations

A one-line edit can rebuild a chain of resources
Scenario C in the worked example is realistic. Changing the address range of a network, or any argument the provider marks as forcing replacement, destroys the resource and creates a new one, and everything that references the new id follows. Look for -/+ lines and the "forces replacement" note beside the changed argument before you approve. For resources that must not be lost, set lifecycle prevent_destroy so that Terraform rejects a plan that would destroy them, or create_before_destroy to build the replacement first. The resource documentation notes that prevent_destroy does not stop Terraform destroying a resource whose configuration you remove.
State files and saved plans contain secrets
The state can hold sensitive values, and the plan documentation says a saved plan file contains the full configuration, the planned values and the input variables, with any sensitive data saved in cleartext. Keep both out of Git and out of chat threads. Store state in an encrypted, versioned backend with narrow access, as the S3 backend documentation describes, and check plan output before pasting it into a ticket for the customer.
A failed apply is not rolled back
If the fourth of ten operations fails, the first three stay in place and the state records them, because Terraform does not roll back a partly finished apply. One possible cause is timing. The Databricks AWS guide documents one case, which it blames on a bug in an old AWS provider release (v3.28): a new IAM policy was not yet effective when the workspace was registered, and the guide works around it with a ten-second delay. Fix the cause and run again; the next plan shows only the remaining work.
A plan is a prediction, not a promise
The plan documentation warns that other changes made to the target system in the meantime can change the final effect of a configuration change, so you should re-check the final plan before applying. A saved plan applied by automation skips the prompt, so keep the gap between plan and apply short, and make sure the person who approved reviewed the same file that gets applied.
Workspaces are not a boundary between customers
CLI workspaces give one configuration several states, but they share one backend and one set of credentials, and the documentation says they are not appropriate for deployments that need separate credentials and access controls. For two customers, use two root configurations or backend settings, each with its own role and state location, so that nothing run for one customer can read the other's state.
Manual edits and autoscalers fight the configuration
If someone resizes a managed resource in the console, the next plan proposes to put it back, or you accept the change with refresh-only mode. The same tug of war happens with values that a service changes by itself, such as an autoscaler's desired count. Either let Terraform own the value and forbid manual edits, or tell it to ignore that argument with lifecycle ignore_changes, and write down which parts of the environment are managed elsewhere.

When to use it, and when something simpler is enough

Use it when

  • The same environment must exist more than once, for development, staging and production or for one customer after another, and the copies must stay alike.
  • A change needs review by someone other than its author, such as a customer's security team, and a plan gives them the exact list of changes to approve.
  • The environment has ordering constraints, such as network before subnet before server, that are easy to get wrong by hand and tedious to repeat.
  • The environment must be removed completely at the end, for example when a pilot finishes, so that no forgotten resource keeps billing.

Think twice when

  • The resource is a one-off experiment you will delete within the hour. A console click or one CLI command costs less than writing and reviewing a configuration.
  • The thing is changed constantly at runtime by another system, such as an autoscaler or an application writing its own files. Letting Terraform own it creates a fight over the value.
  • Nobody can protect the state: with no shared backend, no locking and no access control, a second person's apply can corrupt or lose the record of what exists.

A simpler alternative. A short shell script that calls the cloud provider's CLI and checks before it creates is enough for one or two resources made once. It stops being enough when you need to run it a second time, hand it to a colleague, preview what it will change, or tear everything down cleanly, and that is the point to move to a declarative tool.

Key takeaways

  • Terraform configuration is declarative: you describe the end state, and Terraform compares it with its state and the real resources to work out only the changes needed.
  • The plan is the reviewable artefact. It lists creates (+), in-place updates (~), destroys (-) and replacements (-/+), and a one-line edit can replace a whole chain of dependent resources.
  • References between resources form a dependency graph that orders the work: dependencies are built first and removed last, and independent resources are handled in parallel.
  • The state maps configuration to real objects, can hold secrets, and belongs in a locked, access-controlled remote backend rather than in Git or on one laptop.
  • Providers turn resource blocks into API calls and modules package repeated patterns. Pin provider versions with the lock file and module versions with version constraints.
  • To reproduce an environment in a customer's account, parameterise what differs, run under a role in their account, keep one state per customer, show them the plan before applying, and plan the teardown.

Example 1 of 5

AWS Control Tower Account Factory for Terraform creating accounts from a git push

Amazon Web ServicesDocumented in official docs

The AWS Control Tower user guide describes Account Factory for Terraform (AFT), a pipeline that provisions and customises AWS accounts from Terraform input files kept in Git. Its overview page and its provisioning-pipeline page are the sources here. [15][16]

The problem

An organisation with many AWS accounts needs every new account to start with the same governance, baseline resources and tags, and needs a record of how each account came to exist. Creating accounts by hand in a console typically produces accounts that differ in small ways and leaves no reviewable request behind.

Where this topic fits

Terraform plays two roles. The account request is itself a Terraform file, so the request is versioned and reviewed like code, and the pipeline that AFT builds uses Terraform to deploy customisations. AWS Control Tower still governs the accounts; AFT adds a Terraform-based way to provision and customise them.

How it is applied, step by step

  1. A platform engineer writes an account request as a Terraform file and pushes it to the repository AFT watches. The documentation describes this as an input file and a simple git push.
  2. AFT provisions the account through AWS Control Tower, so the new account is covered by the landing zone's governance.
  3. When that stage completes, a fixed series of steps runs. The pipeline validates the request input, retrieves details such as the account ID, stores the metadata in a DynamoDB table in the AFT management account, creates the AWSAFTExecution role in the new account, and applies the tags and the feature options chosen at deployment.
  4. Provisioning customisations come next. A Step Functions state machine that you define can call Lambda functions, container tasks and other integrations. If you define none, this stage does nothing.
  5. For each account, AFT creates a CodePipeline in the AFT management account that runs the account customisations, which can target all accounts, a set of accounts or a single account.
  6. A success or failure message goes to an SNS topic. Changing the request of an existing account, or provisioning a new account, runs the customisation steps again.

Why this approach fits

Creating an account is a repeated operation with high privileges. Putting the request in Git gives it history and review, and running it through a pipeline means that, typically, no individual has to create accounts by hand. The format that describes ordinary infrastructure now also describes the places that infrastructure will live.

Limitation or tradeoff

AFT is narrow on purpose. The AWS page says the pipeline is not meant for deploying application resources such as EC2 instances and is solely for provisioning and customising Control Tower accounts. It also needs an existing Control Tower landing zone and a separate AFT management account, so adopting it adds infrastructure of its own to operate.

What the sources document

  • AFT sets up a Terraform pipeline to provision and customise accounts in AWS Control Tower. An account request Terraform file is the input that triggers the workflow, and account creation can be started with an input file and a git push. [15]
  • AFT works with HCP Terraform, Terraform Enterprise and Terraform Community Edition. It creates a separate AFT management account for its own components and requires an existing Control Tower landing zone. [15]
  • After provisioning, the pipeline validates the request input, stores account metadata in DynamoDB, creates the AWSAFTExecution IAM role in the new account, applies tags and feature options, runs provisioning customisations, creates a CodePipeline per account and sends a notification to an SNS topic. [16]
  • Customisations can be added to all accounts, to a set of accounts or to individual accounts, and the customisation steps are restarted by changing an existing account request or provisioning a new account. [15][16]
  • The AFT pipeline is not intended for deploying resources such as EC2 instances that accounts need to run applications. It is solely for automated provisioning and customisation of Control Tower accounts. [15]

The facts above come from the cited sources. The steps and analysis in this example are our explanation of how they fit together.

Example 2 of 5

Hootsuite reviewing and applying Terraform from pull requests with Atlantis

HootsuiteDocumented in an engineering article

The Atlantis project's launch post, dated September 2017, describes in the first person how Hootsuite had used Atlantis for over a year, and what problems with its Terraform workflow led to it. [17]

The problem

As Hootsuite adopted Terraform, two problems appeared. Reviewing a pull request that shows only the configuration diff is hard, because a small-looking change can produce a large plan, and the main branch can drift away from what was actually applied. And developers who could write Terraform had no credentials to run it, while handing them credentials made it hard to see what was being applied.

Where this topic fits

Atlantis sits between version control and the cloud account. It runs plan and apply on behalf of a pull request, so the plan becomes a review artefact attached to the change, and the credentials needed to apply do not have to sit on each developer's laptop.

How it is applied, step by step

  1. A developer changes Terraform files on a branch and opens a pull request.
  2. A comment on the pull request asks Atlantis to plan. Atlantis runs the Terraform plan and posts the output as a comment, and the developer can repeat this until the change looks right.
  3. An operations engineer reviews the plan output on the pull request, not only the file diff. In the require-approval mode, apply is refused until the pull request has an approval.
  4. After approval, apply runs from the pull request and its output appears there, so the change is applied before the merge and the main branch matches what is running.
  5. Developers write and apply Terraform without holding credentials locally. The post names code review and approvals as the safeguard against applying something they should not.

Why this approach fits

A plan is exactly what a reviewer needs and a diff lacks. Moving plan and apply onto the pull request puts the evidence next to the discussion and ties "merged" to "applied". It also let an operations team widen who could change infrastructure without widening who held cloud credentials.

Limitation or tradeoff

The control moves into review discipline. The post itself calls letting developers apply a risk and answers it with code review and approvals, so a rubber-stamp approval defeats it. A typical Atlantis server must be able to apply changes to the account, which makes it a powerful component to secure. Hootsuite also split its Terraform into many states, each with a repository, so a change that spans states needs coordination. The numbers are Hootsuite's own from 2017.

The problem

Customers manage Cloudflare settings such as DNS records with Terraform, so the provider has to expose every API attribute. Cloudflare reports that the hand-written provider was hard to keep current: a change needed at least three pull requests, and small yet important attributes could be forgotten and never exposed to customers.

Where this topic fits

This is the provider layer, the plugin between Terraform core and an HTTP API. A provider must do more than an SDK: it manages the lifecycle of each resource, so every attribute needs a known value after apply to be stored in state. That requirement is what drove the changes to the schemas and the provider framework.

How it is applied, step by step

  1. A service team documents a new product feature in the OpenAPI schema, which Cloudflare treats as the source of truth for its SDKs, API reference and now the Terraform provider.
  2. The generation pipeline produces the provider's resources from the schema, so a new attribute reaches Terraform users together with the SDKs and the documentation.
  3. The generated resources use the terraform-plugin-framework rather than the older SDKv2, because SDKv2 could not reliably represent a boolean that is unset, true or false.
  4. The schemas now state default values, response properties that vary with the request, and attributes the server computes, so that Terraform knows every value after apply and avoids the "inconsistent result after apply" error.
  5. The existing acceptance tests, which create real resources, check the generated provider, and lint rules on the schemas stop recurring classes of bug before they reach code generation.
  6. A customer declares a cloudflare_dns_record block and gets the same plan-and-apply workflow as for any other resource.

Why this approach fits

A SaaS configuration is infrastructure too: a DNS record or a rule set is something a team wants reviewed, versioned and repeatable. Generating the provider from the API's own schema keeps the Terraform surface from falling behind the API, which is the failure customers noticed.

Limitation or tradeoff

Generation moves the difficulty into schema quality. The post describes the work of making schemas explicit about defaults and computed values, and notes that bugs hide behind other bugs because an error can occur at schema validation, in the API call or in the check after apply. The post announces a 5.0.0-alpha1 preview, so it describes the approach before the provider was generally available.

What the sources document

  • Cloudflare made its OpenAPI schemas the source of truth for its SDKs and API reference, and the post announces that the Terraform provider and the API reference documentation are now generated from them. [19]
  • Under the previous approach a change to the provider took a minimum of three pull requests, or four when cf-terraforming support was added, and even then coverage of all available attributes was not guaranteed. [19]
  • The post describes Terraform as essentially an HTTP client with lifecycle management built in that uses the public APIs to create, read, update and delete resources over their life. [19]
  • For Terraform all values must be known at apply time so they can be saved in state. The schemas now explicitly call out default values, response properties that vary with the request payload and server-side computed attributes. [19]
  • Cloudflare moved the provider from terraform-plugin-sdk (SDKv2) to terraform-plugin-framework because SDKv2 could not reliably write back unset values, which broke booleans that can be unset, true or false. At the time of the post, the platform had 1,330 API endpoints. [19]

4Common mistakes

  1. Committing the state file or a saved plan to Git.

    Why it causes problems
    State can contain sensitive values, and a saved plan holds the full configuration and input variables and stores any sensitive data in cleartext. Anyone who can read the repository can read them, and Git history keeps them after the file is deleted.
    How to recognise it
    terraform.tfstate, terraform.tfstate.backup or a plan file shows up in git status, or a secret scanner flags the repository.
    How to fix it
    Add them to .gitignore, store state in a remote backend with encryption and versioning, keep plan files in a short-lived artefact store, and rotate any secret that has already been committed.

  2. Editing Terraform-managed resources in the console.

    Why it causes problems
    The real object drifts away from the state. The next apply either quietly undoes the fix somebody made during an incident, or fails in a way that nobody connects to the manual edit.
    How to recognise it
    A plan that proposes changes although no code changed, or a plan that reports objects changed outside of Terraform.
    How to fix it
    Make changes in the configuration. If an emergency edit was unavoidable, copy it into the code, then bring state and code together with apply or refresh-only mode. Run plan with -detailed-exitcode on a schedule and alert on exit code 2.

  3. Using -auto-approve without anyone having read the plan.

    Why it causes problems
    The apply documentation recommends running and reviewing a plan first when you use this option in automation. Without that, a replacement of a network or a database is carried out with no human having seen it.
    How to recognise it
    A pipeline that runs apply with -auto-approve on every merge and stores no plan, or approvals that are granted within seconds of a plan being posted.
    How to fix it
    Save the plan with -out, publish it for review, and apply that exact file after approval. Mark resources that must survive with prevent_destroy (deleting the block removes that protection), and read every destroy and replace line, not only the summary count.

  4. Putting every customer or environment into one state.

    Why it causes problems
    One state means one blast radius and one set of credentials. A mistake made for one customer can plan changes for another, a lock held by one team blocks unrelated work, and no customer can keep their own state in their own account.
    How to recognise it
    Workspaces named after customers that share one backend and one role, or a single root module with a block per customer.
    How to fix it
    Use one root configuration and one state per customer and environment, share logic through versioned modules, and give each its own role. Hootsuite reports splitting its Terraform into multiple states, each in its own repository, and had 144 such repositories by the time of its 2017 post.

  5. Leaving provider and module versions unpinned.

    Why it causes problems
    A new provider release can change what a plan proposes. A plan that was clean last week shows new changes, or an environment built for a customer cannot be rebuilt the same way.
    How to recognise it
    No .terraform.lock.hcl in the repository, no version in required_providers, or module blocks that point at a registry module with no version.
    How to fix it
    Commit the lock file, set required_version and version constraints, and upgrade deliberately in a pull request whose plan you read.

Exercise 1

Compute the order of operations for a plan

CodingIntermediateAbout 40 min (estimate)Hypothetical scenario

Start from mini_plan.py in the worked example. It says what will happen to each resource but not in what order. Write waves.py with a function waves(desired, actions) that groups the operations into waves. Every operation in a wave could run in parallel, and a wave starts only when the previous one has finished.

Operations are ("apply", address) for a create, an update or the create half of a replacement, and ("destroy", address) for a destroy or the destroy half of a replacement. Use graphlib.TopologicalSorter with prepare(), get_ready() and done(). You can import STATE, config, deps_of and plan from mini_plan. You need only the Python standard library.

Requirements

  • An apply operation waits for the apply operations of its dependencies, but only for those that are also being changed in this plan.
  • A replaced resource is destroyed before it is created again.
  • A destroy operation waits for the destroy operations of everything that depends on it, so dependents go first.
  • A resource whose action is no-op produces no operation.
  • Return a list of waves, each a sorted list of strings such as `apply toy_network.main`.

Expected behaviour

For the first apply (empty state) there are three waves: the network, then the rule and the subnet, then the server. For the CIDR change there are six: destroy the server, destroy the rule and the subnet, destroy the network, then apply the network, apply the rule and the subnet, apply the server. Removing the server gives a single wave that destroys it.

Hint 1

Create one graph node per operation, keyed by a tuple such as ("destroy", address), and map each node to the set of nodes that must finish before it.

Hint 2

For a resource and each dependency from deps_of, add an apply edge when both are applied, and the reverse destroy edge when both are destroyed.

Hint 3

A resource deleted from the configuration is not in desired, so you cannot look up its dependencies there. Skip them for this exercise; real Terraform keeps that information in its state.

Show solution

Save this as waves.py next to mini_plan.py.

python
from graphlib import TopologicalSorter

from mini_plan import STATE, config, deps_of, plan


def waves(desired, actions):
    """Group operations into waves; every operation in a wave could run in parallel."""
    graph = {}  # node -> set of nodes that must finish first
    for addr, act in actions.items():
        if act in ("destroy", "replace"):
            graph[("destroy", addr)] = set()
        if act in ("create", "update", "replace"):
            graph[("apply", addr)] = set()
    for addr, act in actions.items():
        if act == "replace":
            graph[("apply", addr)].add(("destroy", addr))  # destroy, then create
        for dep in deps_of(desired[addr]) if addr in desired else ():
            if ("apply", addr) in graph and ("apply", dep) in graph:
                graph[("apply", addr)].add(("apply", dep))  # build dependencies first
            if ("destroy", addr) in graph and ("destroy", dep) in graph:
                graph[("destroy", dep)].add(("destroy", addr))  # remove dependents first
    sorter, result = TopologicalSorter(graph), []
    sorter.prepare()
    while sorter.is_active():
        ready = sorted(sorter.get_ready())
        result.append([f"{kind} {addr}" for kind, addr in ready])
        sorter.done(*ready)
    return result


if __name__ == "__main__":
    for title, desired, state in [
        ("A. first apply", config("10.0.0.0/16", "small"), {}),
        ("C. CIDR change", config("10.1.0.0/16", "small"), STATE),
        ("D. server removed", config("10.0.0.0/16", "small", server=False), STATE),
    ]:
        print(title)
        for number, wave in enumerate(waves(desired, plan(desired, state)), start=1):
            print(f"  wave {number}: {', '.join(wave)}")

Replacement is modelled as two nodes, a destroy and an apply, which is why a single -/+ line takes two steps of the walk. The destroy edges run opposite to the apply edges, so dependents are removed first. Scenario C needs six waves because nothing can be built until everything that depends on the old network is gone. Real Terraform's -parallelism setting limits how many operations of one wave run at once, and the optional create_before_destroy setting changes this ordering for resources that must never be missing.

  backend.tf           # S3 backend in the customer's state bucket
  main.tf              # calls the modules
  variables.tf
  customer.tfvars      # the only file that differs between customers
  .terraform.lock.hcl  # committed
  modules/network  modules/app  modules/storage  modules/vector-store

Inputs. Per customer: region, address range, availability zones, the deploy role ARN, the external id, the pilot name and the tag values. Identical for every customer: the modules, the provider versions and the resource naming scheme.

Identity. The customer's cloud team creates the deploy role and the state bucket by hand or with their own tooling before day one, scoped to the pilot's resources. The configuration assumes that role, using short-lived credentials from the customer's single sign-on or CI identity (the AWS provider also offers an assume_role_with_web_identity block), so no long-lived access keys exist:

hcl
provider "aws" {
  region = var.region
  assume_role {
    role_arn    = var.deploy_role_arn
    external_id = var.external_id
  }
  default_tags {
    tags = { pilot = var.pilot_name }
  }
}

State. The backend block holds literal values, because backend blocks cannot read variables. The backend authenticates separately from the provider block, so it carries its own assume_role setting for the same deploy role (the account id below is a documentation placeholder). The bucket has versioning on, and the deploy role may list the bucket, read and write the state object, and read, write and delete the lock file:

hcl
terraform {
  backend "s3" {
    bucket       = "example-logistics-pilot-tfstate"
    key          = "pilot/prod/terraform.tfstate"
    region       = "eu-west-1"
    encrypt      = true
    use_lockfile = true
    assume_role = {
      role_arn = "arn:aws:iam::111122223333:role/pilot-deploy"
    }
  }
}

Review flow. A pull request triggers terraform plan -var-file=customer.tfvars -out=pilot.plan in the customer's CI, under the assumed role. The rendered plan is posted on the pull request. The customer's cloud team approves that plan, and the pipeline applies the same pilot.plan file. The plan file is kept as a short-lived artefact in the customer's account because sensitive values in it are stored in cleartext.

Versions. required_version set to a range, ~> 6.0 for the AWS provider, module versions pinned, the lock file committed. Upgrades go in their own pull request with their own plan.

Teardown. Review terraform plan -destroy, switch off deletion protection and remove any prevent_destroy rule (it makes Terraform reject destroy operations) in a separate reviewed change, run terraform destroy, and then query by the pilot tag to confirm that nothing remains. The state bucket is the customer's to delete.

Risks. (1) The deploy role is over-broad: scope it to tagged resources and a time window, and have the customer remove it at the end. (2) Someone edits resources in the console and the code drifts: run a scheduled plan with -detailed-exitcode and alert on exit code 2. (3) State is lost or corrupted: keep bucket versioning on, restrict write access to the deploy role, and rely on locking so two applies cannot run together.

Check your answer

  • Does every one of the customer's four rules map to a named mechanism in your plan?
  • Have you said what exists before the first apply and who creates it?
  • Is there a file, not a verbal agreement, that the customer's cloud team approves before apply?
  • Could someone who was not on the project verify the teardown with one query?
