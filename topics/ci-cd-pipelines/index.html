CI/CD Pipelines

A CI/CD pipeline is an automated sequence of stages that takes every code change from a commit to a running release. It builds and tests the change (continuous integration), packages it once, and moves that package through environments to production behind checks, approvals and a controlled rollout (continuous delivery).

1Overview

Why it matters

Many production incidents begin with a change. A pipeline decides how large that change is, how much evidence exists that it works before users see it, how many users see it first, and how quickly it can be undone. Without one, a release depends on a person remembering a checklist on their own laptop. Tests get skipped under deadline pressure, the build running in production is not the one that was tested, and a bad release reaches every user at the same moment.

On a customer engagement the pipeline is also how trust is earned. A customer's security team will ask who can deploy to production, what must pass first, where the credentials live and how a release is rolled back. A workflow file in the repository, an environment with named approvers and a staged rollout answer those questions with something the customer can inspect. Anyone who ships software, reviews a deployment plan or is on call for a service needs to be able to read a pipeline and say what each stage proves.

Key terms

Continuous integration (CI)
The practice of merging every developer's work into the shared main branch at least daily, with each merge verified by an automated build and test run.
Continuous delivery (CD)
Keeping the software in a state where any version that passed the pipeline can be released to production on demand, usually by pressing one button.
Continuous deployment
Continuous delivery with the button removed. Every change that passes every stage is released to production automatically.
Stage
A group of checks or actions in a pipeline that answers one question, such as whether the unit tests pass, and blocks everything after it when the answer is no.
Artifact
The file a build produces and later stages deploy, for example a container image, a wheel or an archive. It is identified by a version and a checksum.
Workflow
A GitHub Actions pipeline definition. It is a YAML file in the .github/workflows directory that names the events that start it and the jobs it runs.
Runner
The machine that executes one job of a workflow. GitHub-hosted runners are freshly provisioned virtual machines.
Environment
A named deployment target in GitHub, such as staging or production, that carries protection rules and its own secrets.
Canary
A small share of production traffic or servers that receives a new version first, so that problems show up while most users are still on the old version.
Bake time
A deliberate wait after a rollout step during which metrics are watched before the next, larger step begins.

2Explanation

Introduction

In Git and GitHub Workflows a pull request could be merged only after its status checks passed. In Docker and Containers you built an image that runs the same way on every machine. This lesson covers the machinery around those two things: what produces the checks, what builds the image, and how the result reaches production without anyone copying files by hand.

Picture shipping a one-line fix manually. You pull the latest main, run the tests, build the image, push it to a registry, log in to the server, start the new version and watch the logs for a while. That is seven steps. Each one is easy, and each one is easy to skip at six in the evening. A pipeline is that checklist written as code and run by a machine for every change, in the same order every time, with one firm rule: when a step fails, nothing after it runs.

Three terms describe how far the automation reaches:

  • Continuous integration (CI). Everyone merges small changes into the main branch often, and every merge is built and tested automatically.
  • Continuous delivery (CD). Every change that passes is packaged and proven deployable, so releasing it is a decision and not a project.
  • Continuous deployment. The decision is automated as well. Every change that passes every stage goes to production.

Notice two things in the diagram. The artifact is built once, and that same file moves through every later stage. And every stage has a way to say no: a failed test stops the build, a failed smoke test or a rejected approval stops the release, and unhealthy metrics during the rollout send production back to the previous version.

The rest of the lesson explains what CI and CD ask of a team, what each stage proves, how GitHub Actions expresses stages as a workflow file, how environments and approvals gate a deployment, and how rolling, blue-green and canary rollouts limit the damage a bad release can do. The worked example is a complete pipeline that you can run in a free public repository.

How it works

Continuous integration: small merges, verified every time

Martin Fowler's definition of continuous integration (opens in a new tab) has two halves. Every developer merges into the shared mainline at least daily, and every merge is verified by an automated build that includes tests. The practices behind it are concrete:

  • Everything needed to build is in version control, and one command builds and tests it.
  • Every push triggers that build on a machine other than the author's.
  • A broken mainline is fixed or reverted before any other work continues.
  • The first build stays fast. Fowler cites the Extreme Programming guideline of ten minutes. Slower suites move to a later stage.

Frequent merging keeps each change small, and size matters more than it seems. Suppose each change has an independent probability ppp of breaking something. A batch of nnn changes then contains at least one bad change with probability

P(at least one bad change)=1−(1−p)nP(\text{at least one bad change}) = 1 - (1 - p)^nP(at least one bad change)=1−(1−p)n

With p=0.05p = 0.05p=0.05, a single change fails 5% of the time, a batch of 10 fails 40% of the time and a batch of 20 fails 64% of the time. When a batch does fail, someone still has to find which of the nnn changes caused it.

From integration to delivery and deployment

CI ends with a verified mainline. Continuous delivery (opens in a new tab) extends the automation so that any version that passed can be deployed to any environment on demand. Continuous deployment removes the last manual trigger. Among the examples below, Amazon's service pipelines come closest to continuous deployment, because code review is the last manual approval a change receives. At Slack a person, the deploy commander, decides each step of every rollout, which is closer to continuous delivery.

To judge whether a pipeline is helping, use DORA's software delivery metrics (opens in a new tab). Three measure throughput (change lead time, deployment frequency, failed deployment recovery time) and two measure instability (change fail rate, deployment rework rate). DORA's research finds that speed and stability are not trade-offs: teams that do well tend to do well on all five.

Pipeline stages

A stage is a group of checks that answers one question. Cheap, fast stages run first, and a failure stops everything after it.

StageQuestion it answersTypical contents
CommitIs this change correct on its own?Lint, type checks, unit tests with mocked dependencies
BuildCan we produce the release artifact?Build the image or package once, record version and checksum
AcceptanceDoes the artifact work with real dependencies?Deploy to staging, run integration and smoke tests
Release gateIs someone accountable for this release?Approval, deployment window, wait timer
Production rolloutDoes it behave under real traffic?Staged rollout, monitoring, rollback

Three rules hold whatever tool runs the pipeline:

  • Build once and promote the same artifact. The image that passed staging is the image that reaches production. Rebuilding for each environment means production runs something that was never tested. Differences between environments belong in configuration.
  • The pipeline is code. Its definition is reviewed and versioned next to the application.
  • A red stage is a stop sign. The fix is a new commit that goes through the same pipeline.

GitHub Actions: a pipeline as a workflow file

In GitHub Actions (opens in a new tab) a pipeline is a workflow, a YAML file in .github/workflows/.

TermMeaning
Event (on)What starts a run: pull_request, push, a schedule, or a manual workflow_dispatch
JobA set of steps that run in order on one runner
StepA shell command (run) or a reusable action (uses)
RunnerThe machine that executes a job; GitHub-hosted runners are fresh virtual machines

Six facts shape every workflow:

  • Jobs run in parallel unless needs says otherwise. needs is what turns jobs into stages. When a needed job fails or is skipped, the jobs that need it are skipped too.
  • Jobs share no files. Each job gets its own runner, so files move between jobs as artifacts (opens in a new tab). One job uploads with actions/upload-artifact and a later job downloads with actions/download-artifact.
  • A matrix multiplies a job across language versions or operating systems.
  • permissions narrows the job's token. Once you set any permission, every unlisted one becomes none, so contents: read at the top of the file is a sound default.
  • concurrency serialises runs. Only one job in a concurrency group (opens in a new tab) runs at a time. By default a newer pending run replaces an older pending one. Adding cancel-in-progress: true also cancels the run that is executing, which suits pull requests and is dangerous for a deployment.
  • Third-party actions are code that runs with your token. GitHub's security reference (opens in a new tab) recommends pinning them to a full commit SHA, because a tag can be moved.

Environments and approvals

An environment (opens in a new tab) is a named deployment target such as staging or production. A job opts in with environment: production. It does not start (opens in a new tab), and cannot read the environment's secrets, until every protection rule passes:

  • Required reviewers. Up to six people or teams can be listed, and one approval releases the job. An option prevents people from approving their own deployment.
  • Wait timer. A delay of 1 to 43,200 minutes (30 days).
  • Deployment branches and tags. For example, only main may deploy to production.

A job that nobody approves within 30 days fails. On the Free, Pro and Team plans, required reviewers and wait timers are available only in public repositories.

Credentials need the same care. With OpenID Connect (opens in a new tab) (OIDC) the job presents a token signed by GitHub that names the repository, the Git ref (branch or tag) and the environment. The cloud provider checks it against a trust rule and returns a credential that lasts only for the job, so no long-lived cloud secret is stored in GitHub.

Safe rollout strategies

Passing the earlier stages shows that a change worked under test conditions. The rollout limits the damage when production disagrees.

Recreate. Stop every old instance, then start the new ones. In a Kubernetes Deployment this is strategy.type: Recreate, which terminates all old pods before any new pod is created. It needs no extra capacity and never runs two versions together, but the service is down in between.

Rolling update. A Kubernetes Deployment (opens in a new tab) replaces pods gradually within two bounds: maxSurge (extra pods allowed, default 25%, rounded up) and maxUnavailable (pods that may be missing, default 25%, rounded down). With 10 replicas there are at most 10+⌈2.5⌉=1310 + \lceil 2.5 \rceil = 1310+⌈2.5⌉=13 pods and at least 10−⌊2.5⌋=810 - \lfloor 2.5 \rfloor = 810−⌊2.5⌋=8 available. kubectl rollout undo returns to the previous revision. A rollout that stalls is only reported, after 600 seconds by default. Kubernetes does not roll it back for you.

Blue-green. Two complete environments exist, one live and one idle. The new version is tested in the idle one, then a router moves all traffic across and can move it back (Fowler's description (opens in a new tab)). The database is the awkward part. Fowler advises deploying a schema change that works for both versions first and the new application afterwards.

Canary. A small share of traffic goes to the new version while the rest acts as the control group. Google's SRE workbook (opens in a new tab) gives the arithmetic: a 5% canary that fails 20% of its requests produces a 1% error rate overall. Compare the canary with the control over the same minutes, not with last week's numbers, because traffic changes over time. Then widen the share in steps. Slack, for example, goes from about 2% to 10, 25, 50, 75 and 100 percent.

Two additions make any strategy safer. Bake time is a wait after each step, so that slow problems appear before the next step starts. Automatic rollback connects the rollout to alarms. Both rely on the old and the new version running side by side, so database and API changes must be backward compatible: add the new column in one release and remove the old one in a later release. Feature flags go one step further and separate deploying code from switching it on.

Worked example: A four-job GitHub Actions pipeline that tests pull requests, deploys main to staging and gates production

The repository holds one function, its tests and one workflow. The deploy jobs unpack the artifact and run a smoke test on the runner as a stand-in for a real deployment, so the example costs nothing. Use a public repository, because required reviewers need one on a free plan.

shipping.py:

python
import math

BASE_FEE = 4.00           # flat fee, covers the first kilogram
PER_EXTRA_KG = 1.25       # for each started kilogram after the first
FREE_FROM = 50            # order value at which shipping is free


def shipping_cost(weight_kg, order_value):
    if weight_kg <= 0:
        raise ValueError("weight_kg must be positive")
    if order_value >= FREE_FROM:
        return 0.0
    extra_kg = math.ceil(weight_kg) - 1
    return round(BASE_FEE + PER_EXTRA_KG * extra_kg, 2)

test_shipping.py:

python
import unittest

from shipping import shipping_cost


class ShippingCostTest(unittest.TestCase):
    def test_first_kilogram_costs_the_base_fee(self):
        self.assertEqual(shipping_cost(0.4, 20), 4.00)

    def test_each_started_extra_kilogram_adds_a_fee(self):
        self.assertEqual(shipping_cost(2.3, 20), 6.50)

    def test_orders_from_50_ship_free(self):
        self.assertEqual(shipping_cost(2.3, 50), 0.0)

    def test_weight_must_be_positive(self):
        with self.assertRaises(ValueError):
            shipping_cost(0, 20)

Locally, python3 -m unittest ends with Ran 4 tests and OK. The pipeline is .github/workflows/pipeline.yml:

yaml
name: pipeline

on:
  pull_request:
  push:
    branches: [main]

permissions:
  contents: read

concurrency:
  group: ${{ github.workflow }}-${{ github.event.pull_request.number || github.sha }}
  cancel-in-progress: true

jobs:
  test:
    runs-on: ubuntu-latest
    timeout-minutes: 10
    strategy:
      fail-fast: false
      matrix:
        python-version: ["3.13", "3.14"]
    steps:
      - uses: actions/checkout@v7
      - uses: actions/setup-python@v7
        with:
          python-version: ${{ matrix.python-version }}
      - run: python -m unittest -v

  build:
    needs: test
    if: github.event_name == 'push'
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v7
      - name: Package once
        run: |
          mkdir dist
          tar -czf dist/app.tar.gz shipping.py
          echo "$GITHUB_SHA" > dist/VERSION
          cd dist && sha256sum app.tar.gz VERSION > SHA256SUMS
      - uses: actions/upload-artifact@v7
        with:
          name: app
          path: dist/
          if-no-files-found: error

  deploy-staging:
    needs: build
    runs-on: ubuntu-latest
    environment: staging
    concurrency: deploy-staging
    steps:
      - uses: actions/download-artifact@v8
        with:
          name: app
          path: dist/
      - name: Verify, unpack, smoke test
        run: |
          (cd dist && sha256sum -c SHA256SUMS)
          mkdir release && tar -xzf dist/app.tar.gz -C release
          cd release
          python3 -c "from shipping import shipping_cost as c; assert c(2.3, 20) == 6.5"
          echo "Deployed $(cat ../dist/VERSION) to staging"

  deploy-production:
    needs: deploy-staging
    runs-on: ubuntu-latest
    environment: production
    concurrency: deploy-production
    steps:
      - uses: actions/download-artifact@v8
        with:
          name: app
          path: dist/
      - name: Verify, unpack, smoke test
        run: |
          (cd dist && sha256sum -c SHA256SUMS)
          mkdir release && tar -xzf dist/app.tar.gz -C release
          cd release
          python3 -c "from shipping import shipping_cost as c; assert c(2.3, 20) == 6.5"
          echo "Deployed $(cat ../dist/VERSION) to production"

In the repository settings create two environments: staging with no rules, and production with yourself as a required reviewer and deployments limited to main.

Run 1: a pull request with a bug

A branch changes >= to > in the free-shipping rule. Both test jobs fail (fail-fast: false lets each matrix job finish instead of being cancelled when the other fails), and each log contains:

text
FAIL: test_orders_from_50_ship_free (test_shipping.ShippingCostTest.test_orders_from_50_ship_free)
AssertionError: 6.5 != 0.0
FAILED (failures=1)

An order worth exactly 50 was charged 6.50. unittest exits with status 1, the step fails, and the pull request shows two red checks. With both test checks required by branch protection, the bug cannot be merged.

Run 2: the fix is merged
JobOn a pull requestOn a push to main
test (2 matrix jobs)RunsRuns
buildSkipped by its ifRuns after both tests pass
deploy-stagingSkipped, because it needs a skipped jobRuns with no approval
deploy-productionSkippedWaits for a reviewer, then runs

What to notice:

  • One artifact. build runs once. Both deploy jobs download app and check SHA256SUMS, so production receives the bytes that staging tested, and VERSION records the commit.
  • The gate is not in the file. environment: production is one line. Who may approve is a repository setting that a pull request cannot edit.
  • Concurrency. A new push to a pull request cancels that pull request's older run. On main the group is the commit SHA, so runs never cancel each other, and concurrency: deploy-production lets only one production job run at a time.
  • Least privilege. The workflow token can read the repository and do nothing else.
  • Pinned versions. The actions/* steps use version tags to keep the file short. For a third-party action, GitHub's security reference recommends a full commit SHA, because a tag can be moved.

To make the pipeline real, replace each echo with your deploy command and keep its credentials in the environment.

Edge cases and limitations

Quick merges can drop a pending deployment
GitHub's concurrency documentation states that by default a newly queued job cancels any job already pending in the same group and takes its place. If three commits reach main while a production job is running, the middle commit's production job is cancelled and only the newest one waits. That is fine when every deployment contains all earlier commits and harmful when each run must happen, for example a migration per commit. The queue option set to max keeps up to 100 pending runs, but the same page says ordering is not guaranteed.
An approval can expire, and an administrator can skip it
A job that waits for required reviewers fails if nobody approves it within 30 days, so an old run cannot be approved months later. The environments reference also says administrators can bypass protection rules by default and that this can be switched off for each environment. If the approval is a control your customer relies on, switch the bypass off and say so in the handover notes.
A stalled Kubernetes rollout is reported, not undone
When new pods never become ready, a Deployment stops making progress. After progressDeadlineSeconds, 600 by default, Kubernetes sets a Progressing condition with the reason ProgressDeadlineExceeded and does nothing else. The old pods that are still running keep serving, but half-rolled-out state stays until the pipeline or a person runs kubectl rollout undo. Make the deploy step wait for the rollout status and roll back when it fails.
A canary on a quiet service proves very little
A 2% canary on a service that receives one request per second sees about 12 requests in ten minutes, too few to separate a regression from noise. Spinnaker's canary guidance asks for at least 50 time series data points per metric before its statistical test is reliable. For low-traffic services use a larger share, a longer bake time or synthetic requests, and accept that a fast rollback matters more than the canary.
Two versions run at once during every gradual rollout
Rolling and canary rollouts serve old and new code side by side, and a rollback puts old code in front of data the new code has written. A release that renames a database column or changes a message format in one step breaks one of the two versions. Amazon's pipelines keep a one-box stage in which a single unit runs the new code beside the old fleet, partly to catch this. Split such changes into a backward-compatible addition, a code change and a later removal.
A pull request workflow must not hold deployment secrets
A pull request runs code that nobody has reviewed yet, and in a public repository any user can open one. GitHub's security reference warns that workflows started by the pull_request_target trigger are privileged: they may have write access to the repository and access to referenced secrets, so checking out the pull request's code inside one hands those to its author. Run tests on the plain pull_request trigger with a read-only token and no secrets, and deploy only from pushes to protected branches, as the worked example does.

When to use it, and when something simpler is enough

Use it when

  • More than one person commits to the repository, or one person commits more often than they would run every check by hand.
  • Other people depend on the deployed software, so a release needs evidence that it works, a record of who released it and a tested way back.
  • A customer or auditor asks what was tested and who approved a release. Run history and environment approvals answer that without extra paperwork.
  • You release weekly or more often, so that the manual steps of a release cost more over a few months than automating them once.

Think twice when

  • The code is a throwaway prototype or a one-off analysis that will be shown once and deleted. Keep the tests and skip the deployment stages.
  • You are considering canary analysis or multi-wave rollouts for a service with one instance and a handful of users. There is not enough traffic for a canary to mean anything, and a quick rollback is enough.
  • You are adding a manual approval that the approver has no way to evaluate. A gate nobody can judge slows delivery without adding safety, and an automated check is the better control.

A simpler alternative. One workflow that runs the tests on every pull request, plus a short documented deploy script or the hosting platform's built-in deploy on push. That stops being enough when a second person needs to deploy, when a failed release has cost a customer something, or when nobody can say which commit is running in production.

Key takeaways

  • Continuous integration means merging small changes into the main branch at least daily and verifying every merge with a fast automated build and test run.
  • Continuous delivery keeps every passing version ready to release on demand, and continuous deployment releases it automatically.
  • A pipeline is an ordered set of stages in which cheap checks run first, a failed stage stops everything after it, and the artifact is built once and promoted unchanged.
  • In GitHub Actions, needs orders jobs into stages, artifacts carry files between jobs, and an environment with required reviewers holds a deployment job and its secrets until someone approves.
  • Rolling, blue-green and canary rollouts all limit how many users meet a bad release, and each one needs health metrics, a rollback path and changes that tolerate old and new versions running together.
  • The larger a batch of changes, the more likely it contains a failure and the harder that failure is to find, so small and frequent releases are the safer ones.

Example 1 of 5

Flask: a test matrix on every pull request and a tag-triggered, gated release to PyPI

Pallets (Flask)Documented in an open-source project

Flask is the Python web framework maintained by the Pallets organisation. Two of the GitHub Actions workflow files in its public repository, tests.yaml and publish.yaml, are read here as they stood on the main branch at commit d086db8 (7 October 2026) and, for publish.yaml, also at the 3.0.3 release tag. PyPI's documentation describes the trusted publishing mechanism that the release job uses. [25][23][24][26][27]

The problem

A library has to work on every Python version and operating system its users run, and volunteer maintainers cannot check each combination by hand for each pull request. Releasing carries a different risk. An upload credential stored in CI is a long-lived secret, and PyPI's documentation points out that such a token gives prolonged access to whoever obtains it. A release of a widely installed package should also not go out just because someone pushed a tag by mistake.

Where this topic fits

Both halves of the pipeline are plain workflow files. The Tests workflow is the commit stage and runs on pull requests and on pushes to the main and stable branches. The Publish workflow is the delivery half. It starts when a tag is pushed, builds the distribution files once, and then feeds two jobs from that one artifact: a draft GitHub release, and the upload to PyPI behind a GitHub environment.

How it is applied, step by step

  1. A pull request or a push to main or stable starts the Tests workflow. Path filters skip it when only the documentation or the README changed.
  2. A matrix of eleven named configurations runs the test suite through tox: CPython 3.11 to 3.15, a 3.14t build, PyPy 3.11, Windows and macOS on 3.14, and two runs called Minimum Versions and Development Versions. With fail-fast set to false, a failure in one configuration does not cancel the others.
  3. A separate typing job runs the type checker, and a concurrency group cancels a run when a newer commit arrives for the same pull request or branch.
  4. To release, a maintainer pushes a tag. The build job of the Publish workflow builds the distribution files and uploads them as an artifact named dist.
  5. The create-release job downloads that artifact and creates a draft GitHub release that contains the files, so they can be inspected before anything is published.
  6. The publish-pypi job names the environment publish, so GitHub holds it until that environment's protection rules pass. The 3.0.3 version of the file says the job waits for approval for this reason.
  7. Once released, the job downloads the same artifact and runs the PyPA publish action. It is the only job with the id-token write permission, which lets it trade a GitHub OIDC token for a short-lived PyPI token. The workflow references no stored PyPI password or API token.

Why this approach fits

The matrix turns "works on my machine" into eleven recorded results per change at no cost to the contributor. The release side follows the build-once rule: the files a maintainer inspects in the draft release are the files that reach PyPI, because both jobs download one artifact. By the maintainers' comment in the 3.0.3 file, the environment puts a person between the tag and a step that is hard to take back, since other people may install a new release within minutes. OIDC removes the one secret whose theft would let an attacker publish as Flask.

Limitation or tradeoff

The workflow file shows that the job is tied to an environment, but not what the environment requires. Reviewers are a repository setting, so the file on main cannot prove that an approval happens; only the comment in the 3.0.3 version says so. Trusted publishing also binds PyPI to this repository and workflow, and PyPI issues a token only when the incoming OIDC token matches a configured publisher, so a change on the GitHub side has to be mirrored in the PyPI configuration. Finally, an eleven-way matrix multiplies runner time for every push.

What the sources document

  • At that commit Flask's tests.yaml runs on pull requests and on pushes to main and stable, ignores changes under docs and to README.md, and defines a matrix of eleven named configurations with fail-fast set to false. Each one runs tox through uv. [25]
  • publish.yaml at that commit is triggered by a push of any tag and has three jobs: build, which runs uv build and uploads an artifact named dist; create-release, which needs build and creates a draft release; and publish-pypi, which needs build, uses the environment named publish and has the id-token write permission. Every action is pinned to a commit SHA. [23]
  • In the 3.0.3 version of publish.yaml a comment on the publish-pypi job says it waits for approval before attempting to upload to PyPI, which allows reviewing the files in the draft release. That version contains no reference to a stored secret. [24]
  • PyPI describes trusted publishing as using OpenID Connect to exchange a short-lived identity token from a trusted third-party service for a PyPI API token, and says that token is valid for only 15 minutes from its creation. [26]
  • PyPI's instructions for GitHub Actions say the id-token write permission is mandatory for trusted publishing and is best set at the job level, and that specifying a GitHub environment is optional but strongly encouraged. [27]

The facts above come from the cited sources. The steps and analysis in this example are our explanation of how they fit together.

Example 2 of 5

The Rust compiler: quick checks on each pull request, the full suite before every merge

Rust projectDocumented in official docs

The Rust Compiler Development Guide is the Rust project's own documentation for contributors. Its chapter Testing with CI describes how the rust-lang/rust repository is tested on GitHub Actions and how a bot named bors merges pull requests. [22]

The problem

The compiler must build and pass its tests on many operating systems and targets, and the guide says the full suite can take several hours. Running it for every push to every pull request would be far too slow and wasteful. The project still wants a hard guarantee that its main branch always passes the test suite.

Where this topic fits

Continuous integration is split into two tiers, which is the staged build that the explanation describes. The first tier is a short check on each pull request. The second tier is the full run, and it is placed at the moment of merging: the candidate merge commit is tested before main moves. A third, on-demand tier called a try build lets a contributor run selected jobs without merging.

How it is applied, step by step

  1. A contributor pushes to a pull request. The pull request workflow runs a short suite of about 40 minutes made of a few Linux jobs, which is meant to catch common problems early.
  2. A reviewer approves the pull request through bors. People cannot merge by hand, so every change takes the same route.
  3. Bors takes the next approved pull request from its queue, creates a merge commit on top of the latest main and pushes it to a dedicated branch. That push starts the full auto workflow, which has tens of jobs across operating systems and targets.
  4. When every job is green, bors fast-forwards main to the merge commit that was tested. If an auto job fails, the workflow ends and main does not move.
  5. Because one merge is tested at a time and a full run takes hours, about ten merges fit in a day. Team members therefore combine several trivial pull requests into one rollup that is tested as a unit.
  6. Linux jobs run inside Docker images whose layers are cached in a registry, and compiled LLVM artifacts are cached with sccache, so a run does not rebuild everything from nothing.

Why this approach fits

The fast tier gives a contributor feedback on the commonest mistakes without spending hours of machine time. The slow tier is spent once per merge, at the only point where it can give a guarantee: the exact commit that becomes main has passed everything. Testing the merge commit and not the pull request branch also catches two changes that each pass alone and break when combined.

Limitation or tradeoff

Throughput is capped. The guide says plainly that testing one pull request at a time with a long CI run limits the project to roughly ten merges a day. A pull request can pass the quick tier and still fail a platform-specific job hours after it was approved. Rollups recover throughput by making batches larger, which is the opposite of what the batch-size formula in this lesson recommends, so they are reserved for changes that are very unlikely to fail.

  • Pull request jobs run a relatively short test suite of about 40 minutes on Linux, while the full suite is described as slow: it can take several hours until all auto jobs finish. [22]
  • Manual merges are forbidden. All pull requests are approved through the bors bot, which pushes the merge commit it wants to test to dedicated branches and fast-forwards main to that commit when the results are green. [22]

Amazon: a pipeline that carries a change to every Region with no human after code review

Amazon Web ServicesDocumented in an engineering article

Automating safe, hands-off deployments is an article by Clare Liguori from the Amazon Builders' Library, now served from builder.aws.com. It describes the continuous deployment pipelines that AWS service teams use for their microservices. [15]

The problem

A service runs in many Regions and Availability Zones. A change that looks correct in testing can still fail under production traffic, and if it is deployed everywhere at once the failure is everywhere at once. Having engineers watch every deployment does not scale, and the article's aim is a pipeline that a developer can trust enough to forget about after merging.

Where this topic fits

The pipeline is the whole path from merge to production, in four phases: source, build, test and production. The article puts the only human judgement at the start, in code review, and replaces every later decision with an automated check: tests in pre-production environments, alarms during deployment, and waiting periods between steps.

How it is applied, step by step

  1. A team member reviews and approves the change before it merges to the mainline branch. The article calls this the last manual review and approval the change receives.
  2. The build phase compiles the code, runs unit tests against mocked dependencies, runs static analysis and packages the result.
  3. Pre-production starts with alpha and beta, where functional API tests and end-to-end integration tests run. Gamma follows. It is as production-like as possible, with the same deployment configuration, monitoring and alarms.
  4. A one-box stage deploys the new code to the smallest unit while the rest of the fleet keeps the current code. Its metrics show whether the new code is healthy and whether a mixed fleet works.
  5. Production is deployed in waves. The first wave is a Region with few requests, the second a Region with many, and later waves cover several Regions in parallel. Each step touches one Availability Zone or cell per Region.
  6. Inside a Region the deployment is rolling: at most a third of the boxes are replaced at a time, so about two thirds of capacity keeps serving.
  7. After each step the pipeline bakes. It waits a fixed time and for a minimum number of data points, such as 100 requests to one API, so that a quiet period cannot pass for a healthy one.
  8. If a high-severity alarm fires during a deployment or a bake, the deployment rolls back automatically to the previously deployed image or package. New deployments are also blocked outside time windows.

Why this approach fits

Every safeguard is a rule the pipeline applies the same way every time, so safety does not depend on who is deploying or how tired they are. Exposure grows in an order chosen to limit harm: one box, one Availability Zone, a quiet Region, a busy Region, then many Regions. Long bake times add a second dimension, because some faults such as slow leaks only appear after hours.

Limitation or tradeoff

The default bake times make a change take about four or five business days to reach every Region, which is slow for an urgent fix. The article notes that developers can override the blockers for high-severity issues, and such an override is exactly the kind of manual path that needs its own care. Automatic rollback is only as good as the alarms behind it, since a regression that no metric measures passes every gate. Every change must also tolerate old and new code running together, which constrains how schema and API changes are made. A team with one Region and a few servers needs far less than this.

What the sources document

  • The article describes four pipeline phases (source, build, test and production) and says that code review is the last manual review and approval a change receives from an engineer before it is deployed to production. [15]
  • In a production one-box stage the one box typically serves at most ten percent of the requests for its Region or Availability Zone. During a rolling deployment at most 33 percent of a service's boxes in a Region are replaced at a time, leaving at least 66 percent of capacity healthy. [15]
  • A typical pipeline waits at least one hour after each one-box stage, at least 12 hours after the first regional wave and at least two to four hours after each later wave. With these default bake times a change reaches all Regions in about four or five business days. [15]
  • If a high-severity alarm for the team's microservices goes into the alarm state, the team's ongoing deployments in that Region roll back automatically, and a rollback switches the environment back to the container image or deployment package that was previously deployed. [15]
  • Deployment time windows exclude nights, office holidays and weekends, because on-call engineers typically take longer to engage at those times. [15]

The problem

Each deploy carries the merged work of many engineers, and Slack ships about twelve of them every working day. A fault has to be noticed while it affects as few customers as possible, somebody has to own the decision to continue or stop, and the people who can fix a problem have to be at work when it appears.

Where this topic fits

Continuous integration ends when a pull request has been reviewed, has passed all tests and is merged. The article is about what follows: the release gate and the production rollout. A person, the deploy commander, runs each rollout through staging, an internal tier, a canary and five percentage steps, using Slack's deploy tooling to move from one step to the next.

How it is applied, step by step

  1. A pull request needs a code review and passing tests before it can merge. Merged code is deployed only during North American business hours, when the team is fully staffed.
  2. For each deploy a release branch is created. It tags the release and gives engineers a place to cherry-pick hotfixes for problems found during the rollout.
  3. The build goes to staging, a production environment that receives no public traffic, where automated smoke tests and manual checks run.
  4. Next comes dogfood, a set of hosts that serves Slack's own internal workspaces, so employees meet a problem before customers do. Then comes canary, which receives about 2% of production traffic.
  5. The deploy commander watches the charts at each step and widens the rollout in increments of 10, 25, 50, 75 and 100 percent.
  6. A problem found before production is handled by reverting the offending pull request and making a new build. A problem in production is handled by rolling back to the previous working build first and investigating afterwards.
  7. On each server the switch is atomic. New code is copied into an unused cold directory while the hot directory keeps serving, and the two are swapped once the server has drained its active processes.

Why this approach fits

Each step raises exposure only after the step before it stayed quiet, so most faults are met by employees or by 2% of traffic. A named commander means the decision to stop never waits for a meeting. Limitation or tradeoff

The process needs a trained person for every deploy, twelve times a day, and it is confined to business hours, so a change merged late waits until the next day. Deciding by watching charts is a judgement call, and two commanders may read the same spike differently. That gap is what automated canary analysis fills. A deploy also bundles many pull requests, so when something breaks the first job is to find which one caused it.

Kayenta in Spinnaker: a pipeline stage that scores a canary statistically

Google and NetflixDocumented in an engineering article

Kayenta is the open-source automated canary analysis service that Google and Netflix announced in April 2018 and integrated into the Spinnaker continuous delivery platform. The Google Cloud announcement and Spinnaker's canary documentation describe how it works. Its standalone repository has since been archived and the code lives in the Spinnaker monorepo. Netflix's own article on the subject could not be fetched for this lesson. [17][19][20][21][18]

The problem

Deciding whether a canary is healthy by having a person look at dashboards does not keep up with frequent releases. The announcement names the weaknesses of manual or ad hoc canary analysis: it is a speed and scale bottleneck, people misread or selectively read metrics, and it is hard to tell a real deviation from random noise.

Where this topic fits

Kayenta sits inside the production rollout, between deploying the canary and widening it. In Spinnaker it appears as a canary stage in the pipeline. Its output is a score, and the pipeline uses the score to promote the release, stop and roll back, or hand the decision to a person.

How it is applied, step by step

  1. The pipeline deploys the new version as a canary and, following Spinnaker's guidance, an equivalent baseline at the same time. The baseline runs the current version with the same size and configuration, so the version is the only difference between the two groups.
  2. A small share of production traffic is routed to the canary and to the baseline at the same time. The announcement uses 1% as its example.
  3. For each analysis interval Kayenta fetches the configured metrics for both groups from the metric store, for example Prometheus, Datadog or Stackdriver.
  4. The judge validates the data, can remove outliers, and compares the canary's values with the baseline's using a Mann-Whitney U test. Each metric is labelled Pass, High or Low.
  5. Metrics are organised in weighted groups. A group's score is the percentage of its metrics that passed, and the weighted group scores give a summary score from 0 to 100.
  6. The summary score is compared with two thresholds. At or above the pass threshold the release continues, between the thresholds the result is marginal, and below the marginal threshold the canary fails.

Why this approach fits

The same rule judges every release, so the outcome does not depend on who is on shift or how closely they looked. A statistical test deals with the noise that makes two healthy groups differ slightly. Using a baseline created at the same moment as the canary removes differences such as cache warm-up and heap size that would otherwise look like regressions.

Limitation or tradeoff

The analysis needs data. Spinnaker's guidance asks for at least 50 time series data points per metric and suggests starting with a three-hour canary analysed in one-hour intervals, which adds hours to a release and is out of reach for a low-traffic service. The score only covers the metrics you configure, so a regression in something unmeasured passes. The guidance also warns that one failing metric in a large group is diluted by the passing ones, so the most important metrics need to be marked critical or put in their own group.

What the sources document

  • The announcement describes Kayenta as an open-source canary analysis service developed jointly by Google and Netflix and integrated with Spinnaker as a canary stage.   • Spinnaker's documentation says the judge compares canary and baseline with the Mann-Whitney U test at 98% confidence, labels each metric (Pass, High, Low or a no-data label), scores a group as the passing count divided by the counted metrics times 100 (metrics with no data are left out of the count), and combines group scores using the configured weights. [19]

4Common mistakes

  1. Rebuilding the application separately for staging and for production.

    Why it causes problems
    Two builds of the same commit can differ, because a dependency released in between or a different base image changes the result. Production then runs an artifact that no test has ever touched, and a failure there cannot be reproduced in staging.
    How to recognise it
    The deploy job for each environment contains a build or docker build step, and the image digests or checksums recorded for staging and production differ for the same commit.
    How to fix it
    Build once in a job that only pushes to main can reach, publish the artifact with a version and a checksum, and have every deploy job download and verify that artifact. Pass environment differences as configuration.

  2. Putting cancel-in-progress on a concurrency group that contains a deployment job.

    Why it causes problems
    A new push cancels a deployment that is halfway through. Some servers run the new version and some the old, a database migration may have been applied without the code that needs it, and nothing records the state that was reached.
    How to recognise it
    Deploy jobs in the run history show the status cancelled, and they share a workflow-level concurrency block with pull request jobs.
    How to fix it
    Give deployments their own job-level concurrency group without cancel-in-progress, so a new deployment waits for the running one. Keep cancellation for pull request runs, where the only loss is a test result nobody needs.

  3. Storing a long-lived production credential as a repository secret that every job can read.

    Why it causes problems
    Any workflow in the repository, including one added on a feature branch, can read the secret and use it. Anyone with write access can therefore deploy to production or copy the key, whatever the approval rules say.
    How to recognise it
    The production key appears under repository secrets and not under an environment, jobs that only run tests can reference it, and the workflow has no permissions block.
    How to fix it
    Move the credential into the production environment so that it is released only after the protection rules pass, or replace it with an OIDC trust rule limited to that repository and environment. Set permissions to contents read at the top of the workflow and widen it per job.

  4. Rerunning a failed job until it turns green and merging while the main branch is red.

    Why it causes problems
    A flaky test teaches the team to ignore failures, so a real failure is rerun as well. Once the main branch is red, every later change is tested on a broken base and new breakages hide behind the old one.
    How to recognise it
    Runs commonly succeed on a second or third attempt, the main branch has stayed red for more than a few hours, and people ask in chat whether a failure is the known one.
    How to fix it
    Treat a red main branch as the top priority and fix it or revert the change that broke it. Quarantine or repair flaky tests instead of rerunning them, and keep the first stage fast enough that people wait for it.

  5. Using a manual approval as the test.

    Why it causes problems
    An approver who sees only a button cannot tell a good release from a bad one. The gate adds delay and a sense of safety but catches nothing, and it encourages larger and rarer releases, which fail more often.
    How to recognise it
    Approvals are given within seconds, the approver cannot say what changed or what was tested, and nobody remembers a deployment being rejected.
    How to fix it
    Put the evidence in front of the approver: the commit range, test results and the staging deployment. Move every check a machine can do into an automated stage, and keep a human gate only where a person really decides, such as timing or customer communication.

  6. Shipping a rollout with no tested way back.

    Why it causes problems
    When the new version misbehaves, the team finds out that the previous artifact was deleted, or that a schema change makes the old code crash. Recovery then means writing a fix under pressure while users are affected.
    How to recognise it
    Nobody has run the rollback command for this service, old artifacts are pruned as soon as a deploy finishes, and migrations rename or drop columns in the release that changes the code.
    How to fix it
    Keep the previous artifacts, make every schema change backward compatible for one release, and rehearse the rollback in staging. Decide the rollback trigger, for example an error rate, before the rollout begins.

Exercise 2

Calculate rolling-update bounds and how many requests a staged rollout puts at risk

CodingIntermediateAbout 40 min (estimate)Hypothetical scenario

A service receives a steady 300 requests per second. Its next release contains a fault that makes the new version fail 20% of the requests it handles, while the old version fails none. Write a Python script, using only the standard library, that answers three questions.

Part A: rolling update. Kubernetes rounds maxSurge up and maxUnavailable down when they are percentages. With the defaults of 25% each, how many pods may exist at most, and how many stay available at least, during a rolling update of 1, 3 and 10 replicas?

Part B: staged rollout. The rollout plan sends 2%, 10%, 25%, 50% and then 100% of traffic to the new version, and each stage lasts 10 minutes. For each stage compute the overall error rate seen by users and the number of failed requests if the fault lasts for the whole stage.

Part C: detection. Compare three outcomes, assuming the fault is caught at the end of the stage in which it becomes visible and the rollout is then rolled back:

  1. The release goes to 100% at once and is caught after 10 minutes.
  2. The staged plan is used and the only alarm is an overall error rate of 1% or more.
  3. The staged plan is used and the canary is compared with the rest of the fleet, which shows the 20% failure rate in the first stage.

Requirements

  • Use integer arithmetic for the rounding so that 25% of 10 gives a surge of 3 and an unavailable count of 2.
  • Print one line per replica count for part A and one table row per stage for part B.
  • Compute the failed requests of a stage as traffic share times requests per second times seconds times failure rate.
  • For part C print the total failed requests in each of the three outcomes and how many times smaller outcomes 2 and 3 are than outcome 1.

Expected behaviour

Part A prints at most 2 pods and at least 1 available for 1 replica, 4 and 3 for 3 replicas, and 13 and 8 for 10 replicas.

Part B gives overall error rates of 0.4%, 2%, 5%, 10% and 20%, and 720, 3,600, 9,000, 18,000 and 36,000 failed requests per stage.

Part C gives 36,000 failed requests for the all-at-once release, 4,320 when the overall alarm fires in the 10% stage (720 + 3,600), and 720 when the canary comparison catches the fault in the first stage. Those are 8.3 times and 50 times fewer failures.

Hint 1

Rounding a positive fraction a/b up with integers is -(-a // b), and rounding it down is a // b.

Hint 2

The overall error rate at a stage is the traffic share times the new version's failure rate, because the old version fails nothing.

Hint 3

Ten minutes at 300 requests per second is 180,000 requests in total across both versions.

Show solution
python
def rolling_bounds(replicas, max_surge_pct=25, max_unavailable_pct=25):
    """Return (most pods that may exist, fewest pods that stay available)."""
    surge = -(-replicas * max_surge_pct // 100)            # percentage rounds up
    unavailable = replicas * max_unavailable_pct // 100    # percentage rounds down
    return replicas + surge, replicas - unavailable


def failed_requests(share_pct, rps, minutes, failure_rate_pct):
    """Requests that fail while share_pct of traffic is on the bad build."""
    return share_pct * rps * minutes * 60 * failure_rate_pct // 10_000


RPS, STAGE_MINUTES, FAILURE_PCT = 300, 10, 20
LADDER = [2, 10, 25, 50, 100]
ALARM_OVERALL_PCT = 1.0

for replicas in (1, 3, 10):
    most, fewest = rolling_bounds(replicas)
    print(f"{replicas:>2} replicas: at most {most} pods, at least {fewest} available")

print("share  overall error  failed in stage  cumulative")
cumulative, caught_at = 0, None
for share in LADDER:
    overall = share * FAILURE_PCT / 100
    failed = failed_requests(share, RPS, STAGE_MINUTES, FAILURE_PCT)
    cumulative += failed
    print(f"{share:>4}%  {overall:>12.1f}%  {failed:>15,}  {cumulative:>10,}")
    if caught_at is None and overall >= ALARM_OVERALL_PCT:
        caught_at = (share, cumulative)

all_at_once = failed_requests(100, RPS, STAGE_MINUTES, FAILURE_PCT)
canary_only = failed_requests(LADDER[0], RPS, STAGE_MINUTES, FAILURE_PCT)
print(f"all at once, caught after {STAGE_MINUTES} min: {all_at_once:,} failed")
print(f"overall alarm fires at the {caught_at[0]}% stage: {caught_at[1]:,} failed")
print(f"canary compared with baseline, caught at {LADDER[0]}%: {canary_only:,} failed")
print(f"reduction: {all_at_once / caught_at[1]:.1f}x and {all_at_once / canary_only:.0f}x")

  • Part A. With one replica the surge rounds up to 1 and the unavailable count rounds down to 0, so the new pod starts before the old one stops. With three replicas the service never drops below three available pods. Only at ten replicas may capacity fall, to eight.
  • Part B. In the 2% stage users see an overall error rate of 0.4%, because 0.02×0.20=0.0040.02 \times 0.20 = 0.0040.02×0.20=0.004. An alarm on the overall rate with a 1% threshold stays silent, although one request in five on the canary is failing.
  • Part C. The overall alarm first fires in the 10% stage, after 720 + 3,600 = 4,320 failures. Comparing the canary with the rest of the fleet catches the same fault in the first stage, after 720. A staged rollout limits exposure, and it limits it far more when the canary is measured on its own and not through a fleet-wide average.

Check your answer

  • Does your script print at most 13 pods and at least 8 available for 10 replicas?
  • Is the overall error rate in the 2% stage 0.4%, which is below the 1% alarm?
  • Do the failed requests of the five stages add up to 67,320?
  • Can you explain why the canary comparison catches the fault one stage earlier than the overall alarm?
