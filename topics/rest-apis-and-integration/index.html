REST APIs and System Integration

A REST API exposes a system's data as resources, each with its own URL, that programs read and change with the standard HTTP methods and whose outcomes are reported with HTTP status codes. System integration is the work of making two systems cooperate reliably through such interfaces.

1Overview

Why it matters

Almost every integration job comes down to calling someone else's API or receiving calls from it: pulling customer records out of a CRM, creating invoices in a billing system, reacting when a payment clears. The happy path takes an afternoon. What decides whether the integration survives production is the unhappy path: a timeout after the server already created the record, a list endpoint that quietly returns only the first 30 items, a webhook delivered twice, a field that disappears when the provider ships a new version.

Each of these has a known answer in the conventions of HTTP APIs. Method semantics say what is safe to repeat, status codes say whether repeating can help, pagination and idempotency keys make long reads and risky writes repeatable, webhooks replace polling, and versioning keeps old clients working. A forward deployed engineer reads these conventions off a customer's API documentation in the first hour of a project, and applies the same ones when building the API that the customer's systems will call.

Before you start

No prerequisites. You can start here.

What you will be able to do

  • Read an HTTP request and response and name the method, resource, headers, status code and body.
  • Choose the method and status code for an operation, and say which methods are safe and which are idempotent.
  • Design resource URLs for a small domain using nouns, plural collections and shallow nesting.
  • Page through a collection with a cursor and explain why offset pagination degrades on large or changing data.
  • Make a write safe to retry with an idempotency key, and decide from the status code whether to retry, wait or stop.
  • Receive a webhook correctly, pin an API version, and judge when GraphQL fits better than REST.

Key terms

Resource
Anything an API gives a name and a URL to, such as one order, the collection of all orders, or a customer's invoices.
Representation
The data that travels in a request or response to describe a resource's state, usually a JSON document. It is a copy for transfer, not the stored record itself.
Endpoint
One combination of HTTP method and URL pattern that an API accepts, for example GET /orders/{id}.
HTTP method
The word at the start of a request (GET, POST, PUT, PATCH, DELETE) that says what kind of operation the client wants on the resource.
Status code
The three-digit number at the start of a response that says how the request went. Its first digit gives the class, such as 2 for success or 4 for a client error.
Safe method
A method that only reads. The client is not asking for any change on the server, so repeating the request does no harm.
Idempotent
Having the same intended effect on the server whether a request is sent once or many times. PUT and DELETE are idempotent, POST is not.
Idempotency key
A unique value the client attaches to a write so that the server can recognise a retry of the same operation and return the first result without doing the work again.
Cursor
An opaque token returned with one page of results that tells the server where the next page starts.
Webhook
An HTTP request that a provider sends to a URL you registered when an event happens, so that you do not have to keep asking.

2Explanation

Introduction

You already use an API every time you open a web page. The browser sends an HTTP request that names a URL, and a server answers with a status and some content. A web API is the same exchange with a program on the client side instead of a person, and structured data (almost always JSON) in place of a page.

REST, short for Representational State Transfer, is the style that most public web APIs follow, at least loosely. The name comes from Roy Fielding's doctoral dissertation (opens in a new tab) of 2000, which describes the architecture of the web itself. Its central idea is the resource: any information that can be named, such as one order, the collection of all orders, or today's weather in a city. Each resource has a URL. Clients never reach into the server's database. They exchange representations of a resource, typically JSON documents, through a small uniform set of operations, the HTTP methods. Every request carries all the information the server needs to handle it, so no conversation state has to be kept between requests.

A library is a fair picture. The catalogue number identifies a book (the URL). You can ask to see the book, add a new one, replace it or remove it (the methods). The librarian's first words are a short standard answer: here it is, no such book, you are not a member (the status code). You never need to know how the shelves are arranged.

Every exchange has the same parts. The arrows are annotations, not part of the messages.

text
POST /orders HTTP/1.1               <- method and resource
Host: api.example.com
Content-Type: application/json      <- headers: facts about the request
Idempotency-Key: k-001

{"sku": "A-100", "qty": 3}          <- body: a representation

HTTP/1.1 201 Created                <- status code
Location: /orders/1                 <- headers: facts about the response
Content-Type: application/json

{"id": 1, "sku": "A-100", "qty": 3}

Integration means joining two systems through these exchanges, and it runs in both directions. Sometimes your code asks, by sending a request to their API. Sometimes their system tells you, by sending a webhook: an HTTP request to a URL you own, triggered by an event on their side.

The lesson takes the pieces in the order you meet them on a real project: how resources are named, what each method promises, how to read status codes, how to page through long lists, how to retry without doing something twice, how to receive webhooks, how APIs change without breaking their clients, and where GraphQL offers a different trade. Proving who the caller is comes next, in Authentication and Authorization.

How it works

Resources and URLs

A URL names a thing, not an action. Microsoft's API design guide (opens in a new tab) sets out the conventions most public APIs follow:

  • Use nouns. POST /orders creates an order; /create-order is the pattern to avoid, because the method already supplies the verb.
  • Name collections in the plural and put items beneath them: /orders is the collection, /orders/1 is one order.
  • Show ownership with one level of nesting, such as /customers/5/orders, and stop there. The guide advises against URLs more complex than collection/item/collection.
  • Model business entities, not database tables, so that the API survives a schema change.

Filtering, sorting and paging go in the query string (/orders?status=shipped&limit=25), because they select a view of the same collection.

What each method promises

RFC 9110 (opens in a new tab), the HTTP standard, defines two properties that decide how a client may behave when something goes wrong:

  • A safe method is essentially read-only. The client is not asking for any state change, so caches, crawlers and retry logic may repeat it freely. GET is safe.
  • An idempotent method has the same intended effect on the server whether it arrives once or several times. PUT, DELETE and the safe methods are idempotent. The RFC gives the reason this matters: such a request can be repeated automatically when the connection fails before the client reads the response.

POST is neither. Sending POST /orders twice creates two orders. PATCH, which applies a partial change, is not guaranteed to be idempotent either. Note that idempotence describes the server's state, not the reply: a second DELETE /orders/3 may answer 404, and the order is gone either way.

Pagination

A collection endpoint does not return everything. In GitHub's documentation, a request for a repository's issues returns only 30 of more than 1,600 open issues (opens in a new tab). Raising per_page helps only up to a cap (100 for most endpoints), so a client that reads just the first response loses the rest without any error. Three designs are common:

  • Offset: ?limit=25&offset=50. It is simple and lets you jump to any page. The costs are that the database must read and throw away every skipped row, and that rows inserted while you page shift the window, which produces duplicates or gaps.
  • Page links: the server sends the URL of the next page. GitHub puts it in a Link header marked rel="next".
  • Cursor: the response includes an opaque token marking where you stopped. You send it back, and the server seeks straight to that position.

A simple cost model shows the difference. Serving page kkk of size LLL by offset reads kLkLkL rows, so walking nnn pages reads L n(n+1)/2L\,n(n+1)/2Ln(n+1)/2 rows. With a cursor each page reads about LLL rows, nLnLnL in total.

Whatever the design, loop until the server says there is no more, and use the link or cursor it hands you instead of constructing page URLs yourself.

Retries and idempotency keys

Stripe's engineering blog (opens in a new tab) names the three places a call can fail: before the request arrives, while the server is working on it, or after the work is done but before the response gets back. The client sees the same timeout in all three. For GET, PUT and DELETE the answer is to send the request again. For POST, a blind retry may charge a card twice.

An idempotency key closes the gap. The client generates a unique value, usually a UUID, for each logical operation and sends it in a header, by convention Idempotency-Key. The server stores the key with the result of the first request. A retry carrying the same key receives the stored result, and nothing runs a second time.

An IETF Internet-Draft (opens in a new tab) describes the header (it has not become a standard) and recommends the error cases: 400 when a required key is missing, 422 when a key is reused with a different payload, and 409 when the first request is still being processed.

Retry only what can succeed later: network errors, 5xx responses and 429, with a capped number of attempts (a 501 will not improve by waiting). Wait between attempts, doubling the delay each time and adding a random amount (jitter) so that many clients do not retry in step. When the server sends Retry-After, obey it.

Webhooks

Polling, such as asking GET /orders?since=... every minute, spends requests on mostly empty answers and is always a little late. With a webhook you register a URL once and the provider sends an HTTP POST to it when an event occurs. GitHub's documentation (opens in a new tab) describes webhooks as needing less effort and fewer resources than polling, and as delivering near real-time updates.

Your endpoint is now a public URL that anyone can call, so a correct receiver does four things:

  1. Verifies the sender. The provider signs the raw request body with a shared secret (an HMAC) and puts the signature in a header. Recompute it and compare before trusting anything in the payload.
  2. Answers fast. Store the event, return a 2xx, and do the real work from a queue. GitHub records a delivery as failed when the answer takes longer than 10 seconds.
  3. Tolerates duplicates and disorder. Providers retry, so the same event can arrive twice, and Stripe states (opens in a new tab) that it does not guarantee delivery in order. Keep the IDs of deliveries you have handled.
  4. Recovers what it missed. No provider retries forever. Reconcile periodically through the ordinary API.

Versioning

Adding an optional field or a new endpoint does not break existing clients. Removing or renaming a field, changing a type or adding a required parameter does. Providers ship such changes under a new version and keep the old one working for a published period. The version travels in one of a few places:

Where the version livesDocumented example
URL pathShopify (opens in a new tab): /admin/api/2026-10/..., a new version every three months, each supported for at least 12 months
Request headerGitHub (opens in a new tab): X-GitHub-Api-Version: 2026-03-10 (a request without the header gets 2022-11-28), each version supported for 24 months after a newer one is released, retired versions answer 410 Gone
Account setting with a header overrideStripe (opens in a new tab): each account has a default API version, and a Stripe-Version header overrides it for one request

As a client, state the version explicitly, ignore response fields you do not recognise instead of failing on them, and track the provider's retirement dates.

GraphQL as an alternative

REST returns fixed representations: GET /orders/1 gives whatever the server decided an order contains. A screen that needs an order, its customer and that customer's last three tickets makes several requests and discards most of each response. GitHub's documentation gives a concrete case (opens in a new tab): the logins of ten of your followers, and of ten followers of each of them, take 11 REST requests (one for your followers, then one per follower) or one GraphQL request.

GraphQL is a query language served from a single endpoint. The client sends a query that names exactly the fields it wants, normally as a POST with a JSON body, and the server validates it against a typed schema and answers with JSON of the same shape.

graphql
query {
  order(id: 1) {
    sku
    customer { name tickets(first: 3) { subject } }
  }
}

The trade is real. Calls are normally POSTs to one URL, so method semantics and URL-based caching tell a proxy little about the request, and status codes say less about the outcome. A response can be 200 OK and still contain an errors list (opens in a new tab), because HTTP has no code for partial success. The server has to defend itself against expensive queries, so limits are often counted by query cost instead of by request. GraphQL services usually avoid versions (opens in a new tab): because clients receive only the fields they ask for, new fields can be added without breaking anyone.

Worked example: A small orders API on your own machine, exercised with curl

You will run a tiny orders API locally and talk to it with curl, so that every status code in this lesson appears on your own screen. It needs only Python 3.9 or later. Save this as orders_api.py.

python
import base64
import json
from http.server import BaseHTTPRequestHandler, HTTPServer
from urllib.parse import parse_qs, urlparse

PORT = 8765
MAX_LIMIT = 50


def encode_cursor(last_id):
    return base64.b64encode(f"order:{last_id}".encode()).decode()


def decode_cursor(cursor):
    return int(base64.b64decode(cursor).decode().split(":")[1])


def item_id(path):
    tail = path.removeprefix("/orders/")
    return int(tail) if tail.isdigit() else None


class Api(BaseHTTPRequestHandler):
    def send(self, status, body=None, **headers):
        data = b"" if body is None else json.dumps(body).encode()
        self.send_response(status)
        for name, value in headers.items():
            self.send_header(name.replace("_", "-"), value)
        if body is not None:
            self.send_header("Content-Type", "application/json")
            self.send_header("Content-Length", str(len(data)))
        self.end_headers()
        self.wfile.write(data)

    def do_POST(self):
        db = self.server
        if self.path != "/orders":
            return self.send(405, {"error": "POST is only allowed on /orders"}, Allow="GET, DELETE")
        raw = self.rfile.read(int(self.headers.get("Content-Length", 0)))
        key = self.headers.get("Idempotency-Key")
        if key in db.replays:  # a retry: answer from the record, create nothing
            first_raw, order = db.replays[key]
            if first_raw != raw:
                return self.send(422, {"error": "Idempotency-Key was used with a different body"})
            return self.send(201, order, Location=f"/orders/{order['id']}", Idempotent_Replayed="true")
        try:
            item = json.loads(raw)
            order = {"id": db.next_id, "sku": str(item["sku"]), "qty": int(item["qty"])}
        except (ValueError, KeyError, TypeError):
            return self.send(400, {"error": "body must be JSON with sku and qty"})
        if order["qty"] < 1:
            return self.send(422, {"error": "qty must be at least 1"})
        db.orders = {**db.orders, order["id"]: order}
        db.next_id = db.next_id + 1
        if key:
            db.replays = {**db.replays, key: (raw, order)}
        self.send(201, order, Location=f"/orders/{order['id']}")

    def do_GET(self):
        db, url = self.server, urlparse(self.path)
        if url.path != "/orders":
            order = db.orders.get(item_id(url.path))
            return self.send(200, order) if order else self.send(404, {"error": "no such order"})
        query = parse_qs(url.query)
        try:
            limit = max(1, min(int(query.get("limit", ["2"])[0]), MAX_LIMIT))
            after = decode_cursor(query["cursor"][0]) if "cursor" in query else 0
        except (ValueError, IndexError):
            return self.send(400, {"error": "invalid limit or cursor"})
        ids = sorted(i for i in db.orders if i > after)
        page = [db.orders[i] for i in ids[:limit]]
        next_cursor = encode_cursor(page[-1]["id"]) if len(ids) > limit else ""
        self.send(200, {"data": page, "next_cursor": next_cursor})

    def do_DELETE(self):
        db, order_id = self.server, item_id(self.path)
        if order_id not in db.orders:
            return self.send(404, {"error": "no such order"})
        db.orders = {i: order for i, order in db.orders.items() if i != order_id}
        self.send(204)


if __name__ == "__main__":
    server = HTTPServer(("127.0.0.1", PORT), Api)
    server.orders, server.replays, server.next_id = {}, {}, 1
    print(f"Orders API listening on http://127.0.0.1:{PORT}")
    server.serve_forever()

Start it with python3 orders_api.py and leave it running. In a second terminal, create an order. (In Windows cmd, use Git Bash or WSL so that the quoting works as written.)

Now pretend that response never arrived, and run the identical command again, as a client would after a timeout. The reply is the same 201 with the same Location: /orders/1, plus the line Idempotent-Replayed: true, a header this demo adds so that you can see the replay. No second order exists. Continue with these requests:

#RequestResponseWhat it shows
3Same POST and key, body changed to "qty": 9422, Idempotency-Key was used with a different bodyOne key means one operation
4POST {"sku": "B-200", "qty": 0}, no key422, qty must be at least 1Valid JSON, unacceptable content
5POST B-200, C-300, D-400 with "qty": 1201 three times, ids 2, 3 and 4The server assigns the URLs
6GET /orders?limit=2200, orders 1 and 2, "next_cursor": "b3JkZXI6Mg=="A full page and a pointer onward
7GET /orders?limit=2&cursor=b3JkZXI6Mg==200, orders 3 and 4, "next_cursor": ""An empty cursor ends the loop
8curl -i -X DELETE .../orders/3204 No Content, no bodySuccess with nothing to say
9The same DELETE again404, no such orderSame state, different reply
10POST /orders/1405 with Allow: GET, DELETERight resource, wrong method

What to notice:

  • One order from two POSTs. GET /orders?limit=50 now lists ids 1, 2 and 4. The retry in step 2 created nothing, because the server answered from replays before reaching the code that creates.
  • The cursor is opaque to the client. b3JkZXI6Mg== is Base64 for order:2, the last id on the page. The server may change that encoding at any time, so a client only stores it and sends it back.
  • Idempotent does not mean identical replies. After step 8 the order is gone. Step 9 leaves the server in the same state, which is what makes DELETE safe to retry, although the status differs.
  • Each failure has its own code. Malformed JSON (try -d 'oops') gets 400, a rule violation 422, an unknown id 404 and a wrong method 405. A client can branch on the number without parsing the message.

A production server would keep the keys in a database, make the key check and the insert a single atomic step, and expire keys after a documented period.

Edge cases and limitations

A timeout does not tell you whether the write happened
When a POST times out, the server may never have seen it, may be halfway through, or may have finished and lost the reply. Treating the timeout as a failure and telling the user to try again is how duplicate orders are made. Retry with the same idempotency key, or, where the API offers no key, look the record up by a unique business reference before creating it again.
Idempotency keys expire
A key protects a retry only while the server still remembers it. Stripe's API reference says that for its v1 API keys can be removed once they are at least 24 hours old, and that a key reused after pruning produces a new request. A job that resumes yesterday's failed batch with yesterday's keys can therefore create duplicates. Find out the retention period and reconcile anything older by reading first.
PUT replaces, PATCH merges
PUT carries a complete representation, so a field you leave out is removed or reset, depending on the API. PATCH carries only the changes. Reading a record, changing one field and sending the whole thing back with PUT also overwrites edits that someone else made in between. Microsoft's guidance suggests 409 Conflict for a change that cannot be applied to the current state; many APIs pair this with a version number or ETag that the client must echo.
A cursor is not a bookmark
Cursors describe a position for the short term. Slack's documentation says its cursors expire, warns against keeping them for hours or days, and returns an invalid_cursor error for a stale one. Cursor pagination also gives no total count and no way to jump to page 40. For a resumable export, store the last item's own id or timestamp and restart with a filter, not with a saved cursor.
The same webhook arrives twice, or a redelivery looks like a duplicate
Providers retry deliveries they believe failed, including ones your server processed but answered too slowly. GitHub notes that a requested redelivery carries the same X-GitHub-Delivery value as the original. Record a delivery id only after its work has succeeded. Then a true duplicate is skipped, while a redelivery of an event you failed to process is still handled.

When to use it, and when something simpler is enough

Use it when

  • The data is naturally a set of entities with create, read, update and delete operations, and many different clients need a stable, documented way to reach it.
  • You are integrating with a third-party product. Its REST API and webhooks are usually the supported way in, and reading its database directly is not an option.
  • Changes must be validated one record at a time and the caller needs an immediate, specific answer such as 201, 409 or 422.
  • Responses can be cached or served through proxies and gateways, which understand HTTP methods and status codes without knowing your application.

Think twice when

  • Clients need many differently shaped views across connected objects and are making several calls per screen. A GraphQL API, if the provider offers one, fits that access pattern better.
  • You are moving millions of rows on a schedule. Paging through a REST API for a nightly bulk copy is slow and collides with rate limits; a bulk export or a pipeline is the better tool.
  • You need to know about changes within seconds and the provider offers webhooks. Polling a list endpoint in a tight loop spends your rate limit on empty answers.

A simpler alternative. For a one-off or occasional transfer, a file export from one system and an import into the other needs no client code, retries or pagination at all. It stops being enough when the data must stay current during the day, when each record needs its own validation and error handling, or when the other side must be able to trigger the exchange itself.

Key takeaways

  • A REST API names things with URLs and acts on them with HTTP methods, and the status code is the first thing a client should read in every response.
  • GET, PUT and DELETE can be repeated after a failure because they are idempotent, while POST needs an idempotency key before it is safe to retry.
  • Retry network errors, 5xx responses and 429 with growing delays, and treat any other 4xx as a request that must be corrected, not resent.
  • List endpoints return pages, so a client must loop until the server signals the end, and cursors hold up better than offsets when the data is large or changing.
  • A webhook receiver verifies the signature, answers quickly, queues the work and expects duplicates and missed deliveries.
  • Pin the API version you built against, and consider GraphQL when clients keep stitching many REST calls together to build one view.

Example 1 of 5

Stripe idempotency keys for retrying payment requests safely

StripeDocumented in an engineering article

Stripe's payment API accepts an Idempotency-Key header on POST requests. The engineering article Designing robust and predictable APIs with idempotency (2017) explains the reasoning, and the current API reference page Idempotent requests documents the behaviour. [13][14][15]

The problem

A merchant's server asks Stripe to create a charge and the connection breaks. The article lists three possibilities that the client cannot tell apart: the connection failed before the request reached Stripe, the call failed partway through the operation, or the charge succeeded and only the response was lost. Retrying a plain POST risks charging the customer twice. Not retrying risks shipping goods that were never paid for.

Where this topic fits

The key travels with every state-changing POST between the merchant's server and the Stripe API. Before the call, the client generates the key and keeps it with the pending operation. After a failure, the retry policy (exponential backoff with jitter) decides when to send the same request again. On Stripe's side an idempotency layer in front of the endpoint logic decides whether to execute or to replay.

How it is applied, step by step

  1. The client creates a unique key for one logical operation, such as one attempt to charge one order. Stripe's reference suggests a V4 UUID or another random string with enough entropy.
  2. It sends the POST with the key in the Idempotency-Key header.
  3. On the first request Stripe executes the endpoint and, for API v1, saves the status code and body of the result against the key once execution has begun.
  4. If the client gets no response, it waits and sends the identical request with the same key. The article recommends waits that grow exponentially, with random jitter added.
  5. Stripe recognises the key. If the first attempt never arrived, this one is processed normally. If it completed, the saved response is returned and no second charge is made.
  6. If the retry's parameters differ from the original, the idempotency layer returns an error instead of guessing which request the client meant.

Why this approach fits

The client is the only party that knows two requests are the same attempt, and the server is the only party that knows whether the first one took effect. The key carries the client's knowledge to the server in one header. It needs no new protocol and no distributed transaction, and it turns the retries a client must make anyway into a single effect. Payments are the natural home for the pattern because a duplicate charge and a missed charge are both expensive.

Limitation or tradeoff

The guarantee lasts only as long as the stored key. Stripe's reference says v1 keys can be removed once they are at least 24 hours old, after which the same key starts a fresh request. Results are saved only after endpoint execution begins, so a request rejected by validation, or one that collided with a concurrent request using the same key, is not recorded and has to be sent again. A saved 500 is replayed as a 500 in API v1, so recovering from some failures takes a new key and a reconciliation step first. On the server side the layer costs storage, and the key check and the operation must be atomic.

What the sources document

  • The article identifies three failure points for a call: the initial connection can fail, the call can fail midway while the server is fulfilling the operation, or the call can succeed and the connection break before the server can tell the client. It says a retry after a connection failure reaches a server that sees the key for the first time and processes it normally, while a retry after a lost response gets a cached result. [13]
  • The API reference states that for API v1 Stripe saves the status code and body of the first request made with a given idempotency key after endpoint execution begins, and that retries with the same key return the saved response, including 500 errors. [14]
  • The API reference says keys can be up to 255 characters long, suggests V4 UUIDs, says v1 keys can be removed once they are at least 24 hours old, and says the idempotency layer compares incoming parameters with those of the original request and errors if they are not the same. [14]

Slack replacing offset pages with cursors in its Web API

SlackDocumented in an engineering article

Slack's Web API returns collections such as the members of a workspace through list methods. The engineering article Evolving API Pagination at Slack (2017) describes the move from offset pages to cursors, and Slack's developer documentation describes the scheme as it works today. [16][17]

The problem

The article explains that endpoints designed on the expectation of returning several hundred records at most were by then returning hundreds of thousands. Offset pagination with page and count had two faults at that size. A query with LIMIT and OFFSET still makes the database read offset + count rows before discarding the offset. And when items are written frequently the page window becomes unreliable, so a client can receive the same results twice or skip some.

Where this topic fits

Pagination sits between a list method such as users.list and the query that feeds it. The client supplies limit and, after the first call, cursor. The server returns the items plus response_metadata.next_cursor. The rest of the method, including its other parameters and the shape of each item, is unchanged.

How it is applied, step by step

  1. The client calls a paginated method with a limit and no cursor to get the first page.
  2. The server orders the rows by a unique, sequential column and fetches one row more than the limit asks for.
  3. It returns the first limit rows. The extra row is not returned, but its id, encoded as an opaque Base64 string, becomes next_cursor inside response_metadata.
  4. The client passes that string back as the cursor argument. The server decodes it and starts the next query at that row, so the cost of a page no longer depends on how deep it is.
  5. The client repeats until next_cursor comes back empty, which is the signal that the collection is exhausted.
  6. Because the cursor is opaque, each method can encode whatever its own data source needs, and the encoding can change without changing the interface.

Why this approach fits

A workspace directory or a channel history is large, grows constantly and is usually read from start to end by a sync job, not browsed by page number. A cursor matches that access pattern: each page costs about the same, and rows arriving during the walk do not shift what the next page contains.

Limitation or tradeoff

Slack's article lists what is given up: the cursor must rest on a unique, sequential column, there is no total count, and the client cannot jump to an arbitrary page. A screen that shows page 7 of 31 cannot be built on it. Cursors are also short-lived. Slack's documentation says they expire and should not be kept for hours or days, so a sync that pauses overnight has to restart from a known item, not from a saved cursor. The documentation also warns that a page may hold fewer items than the limit while more remain, so only an empty cursor means the end.

What the sources document

  • The article says Slack's endpoints were designed around returning several hundred records in the most extreme cases and were by then returning hundreds of thousands, and that pagination went from none, to offset pagination, to a cursor-based scheme. [16]
  • It states that LIMIT with OFFSET does not scale well for large datasets because the database still has to read up to offset plus count rows before discarding the offset, and that with frequent writes the page window becomes unreliable, potentially skipping or returning duplicate results. [16]
  • In the new scheme the client sends a cursor and receives next_cursor in a response_metadata object. The article's example cursor dXNlcjpXMDdRQ1JQQTQ= is decoded on the server to user:W07QCRPA4, the user id to start from. [16]
  • The article lists three trade-offs of cursor pagination: the cursor must be based on a unique, sequential column, there is no concept of the total number of pages or results, and the client cannot jump to a specific page. [16]
  • Slack's documentation recommends 100 to 200 results per call, gives a maximum limit of 1000 that may vary by method, says an empty, null or missing next_cursor indicates no further results, and defines an invalid_cursor error for cursors that are malformed or too old. [17]

GitHub webhooks as signed deliveries with a response deadline

GitHubDocumented in official docs

GitHub delivers repository, organisation and app events to external systems through webhooks. Five pages of GitHub's documentation describe the contract: About webhooks, Webhook events and payloads, Validating webhook deliveries, Best practices for using webhooks and Handling failed webhook deliveries. [18][19][20][21][22]

The problem

A CI system, a deployment tool or a chat notifier needs to know when something happens in a repository. Polling the REST API for changes costs requests and reacts late, and GitHub's documentation says webhooks scale better when many resources are watched. But a webhook URL is reachable by anyone on the internet. The receiver has to tell a real delivery from a forged one, and GitHub has to be able to tell whether the receiver got it.

Where this topic fits

Here the roles are reversed: GitHub is the HTTP client and your server is the API. The concept covers the whole delivery contract, from the POST request and its headers, through signature validation and the response deadline, to what happens after a failure.

How it is applied, step by step

  1. You create a webhook with a payload URL and a secret, and subscribe only to the event types you need.
  2. When a subscribed event occurs, GitHub sends an HTTP POST with data about the event to the URL. The X-GitHub-Event header names the event type and X-GitHub-Delivery identifies the delivery.
  3. GitHub computes an HMAC-SHA256 of the payload with your secret and sends it in the X-Hub-Signature-256 header, prefixed with sha256=.
  4. Your server computes the same HMAC over the raw body, compares the two values with a constant-time function, and rejects the request if they differ.
  5. Your server stores or queues the payload and answers with a 2XX status inside the 10-second limit. A worker then checks the event type and the action field and does the work.
  6. If the server was down or too slow, GitHub records the delivery as failed and does not retry by itself. A scheduled script can find failed deliveries through the REST API and ask for redelivery.

Why this approach fits

Push fits events that are rare for any one repository but numerous across many, where polling would be mostly wasted requests. An HMAC over the body with a shared secret authenticates the sender and detects tampering in one check, using nothing beyond a hash function and a header. Because the receiver acknowledges before it processes, a slow downstream job cannot turn into a failed delivery.

Limitation or tradeoff

Delivery is not guaranteed. GitHub does not automatically redeliver a failed delivery, so an outage on your side loses events unless you build the redelivery script or reconcile through the REST API. The 10-second deadline forces asynchronous processing even for simple handlers. A redelivery carries the same X-GitHub-Delivery value as the original, so deduplicating on that header alone can discard a redelivery you asked for. The signature proves origin and integrity but not freshness, which is why the delivery id is also needed against replays.

What the sources document

  • GitHub's documentation says that when a subscribed event occurs GitHub sends an HTTP request with data about the event to the URL you specified, and that compared with polling an API, webhooks require less effort and fewer resources and scale better. [18]
  • GitHub uses the webhook secret to create an HMAC hex digest of the payload and sends it in the X-Hub-Signature-256 header, whose value always starts with sha256=. The documentation says never to use a plain == comparison, and publishes test values: the secret "It's a Secret to Everybody" with the payload "Hello, World!" gives 757107ea0eb2509fc211221cce984b8a37570b6d7586c22c46f4379c8b043e17. [20]
  • The payloads page says deliveries are HTTP POST requests to the configured URL that carry special headers, including X-GitHub-Event (the name of the event that triggered the delivery), X-GitHub-Delivery (a GUID identifying the event) and X-Hub-Signature-256 (sent when a secret is configured). [19]
  • A server should respond with a 2XX response within 10 seconds of receiving a delivery. Otherwise GitHub terminates the connection and considers the delivery a failure. The page suggests a queue to process payloads asynchronously. [21]
  • GitHub does not automatically redeliver failed deliveries; they can be redelivered manually or by a script that uses the REST API. A requested redelivery has the same X-GitHub-Delivery header value as the original delivery. [22][21]

Stripe's dated API versions and version change modules

StripeDocumented in an engineering article

Stripe's engineering article APIs as infrastructure: future-proofing Stripe with versioning (2017) describes how the API keeps old integrations working while it changes. The current Versioning page of the API reference and the webhooks documentation describe how versions are selected today. [23][24][25]

The problem

A payments integration is written once and then expected to keep working for years. The article compares the API to infrastructure: a power company should not change its voltage every two years. Yet the API itself has to change, and by the time of the article Stripe had made almost a hundred backwards-incompatible upgrades. Forcing every user to migrate with each one was not acceptable, and neither was freezing the API.

Where this topic fits

Versioning sits between the API's current internal behaviour and each response. A request is tied to a version through the account or through a header. The core code produces the newest shape, and a compatibility layer rewrites it into the shape that version promised. Webhook payloads follow the same rule.

How it is applied, step by step

  1. Versions are named by date. According to the 2017 article, the first time a user makes an API request the account is pinned to the most recent version available. The current reference calls this the account's default API version and says it is controlled in Workbench.
  2. Later requests from that account get that version's behaviour. A client can override the version for a single request with the Stripe-Version header, and the account's version can be upgraded from the dashboard.
  3. Client libraries add a second pin. From stripe-python v6, for example, requests carry the API version that was current when that library release was made, so the version follows the library you install.
  4. Each backwards-incompatible change is written as a version change module: a self-contained unit that documents the change and knows how to turn a response back into the older shape.
  5. To answer a request, the API first builds the response in the current format, then walks back through time applying each version change module it passes until it reaches the request's target version.
  6. Compatible additions, such as a new field, need no module, because older clients are expected to ignore what they do not recognise.
  7. Since the 2024-09-30.acacia release, according to the current reference, Stripe publishes a new version each month with no breaking changes and reserves breaking changes for two major releases a year. The reference currently lists 2026-09-30.endive as the current version.

Why this approach fits

Pinning by account means an integration that nobody is maintaining never sees a breaking change, while a team that wants a new feature can test one request at a time with the header before moving the whole account. Expressing each breaking change as a transformation keeps the main code on the newest model only. The price of an old version is one small module per change, not a parallel copy of the API.

Limitation or tradeoff

The article is frank about the limits. Some changes cannot be expressed as a transformation of the response. Such modules are marked as having side effects, and their logic has to live in the core code, which weakens the encapsulation. Every retained version is a maintenance cost that grows with time. Pinning also lets users stay on very old behaviour indefinitely, so they miss improvements unless they choose to upgrade. And an event's structure is fixed by the version in force when it was created, so upgrading an account does not rewrite events that already exist.

What the sources document

  • The article states that the first time a user makes an API request their account is automatically pinned to the most recent version available, and that users can override the version of a single request with the Stripe-Version header or upgrade the pinned version from the dashboard. [23]
  • It describes version change modules that encapsulate backwards-incompatible changes, and says the API formats a response at the current version and then walks back through time, applying each version change module along the way until the target version is reached. [23]
  • The article says Stripe has maintained compatibility with every version of its API since the company's inception in 2011, through almost a hundred backwards-incompatible upgrades over the six years before it was written. [23]
  • The API reference states that starting with the 2024-09-30.acacia release Stripe releases new API versions monthly with no breaking changes and issues a major release with breaking changes twice a year, lists 2026-09-30.endive as the current version, and says client libraries such as stripe-python v6 and later send the API version that was current at the library's release. [24]
  • The webhooks documentation says the API version in the account settings when an event occurs dictates the structure of the Event sent to a destination, unless a version was set when the endpoint was created, and that Event objects cannot be changed after creation. [25][24]

Shopify making GraphQL the primary Admin API for apps

Shopify's Admin API lets apps read and change a merchant's products, orders and customers. Shopify's developer documentation marks the REST Admin API as legacy and documents the GraphQL Admin API that replaces it, and the announcement All-in on GraphQL (October 2024) gives the reasons. [26][27][28]

The problem

An app that manages a store works across many connected objects: products, their variants, inventory, orders, customers. The announcement describes the Admin API as extensive and says GraphQL lets an app select and traverse a tree of data in a single request and avoid over-fetching. Some capabilities, such as support for 2,000 product variants, were offered only through GraphQL, so an app could not stay on REST and use everything the platform had.

Where this topic fits

GraphQL replaces the many REST resource URLs with one versioned endpoint. The app still authenticates with a token in a header and still pins an API version in the URL. What changes is that resource selection moves out of the URL and into the query, and rate limiting moves from counting requests to counting the cost of each query.

How it is applied, step by step

  1. The app sends an HTTP POST to the store's single GraphQL endpoint, whose URL contains the API version, with its access token in the X-Shopify-Access-Token header.
  2. The JSON body carries a query that names the objects and fields wanted, for example the title of the first product.
  3. Shopify checks the query against the schema and assigns it a cost in points, based on the fields it could return.
  4. The response contains a data object shaped like the query, plus an extensions.cost object reporting the requested cost, the actual cost and the current throttle status.
  5. The app reads the throttle status, meaning how many points remain and how fast they are restored, to pace its next queries instead of counting requests.

Why this approach fits

A commerce back office has a wide, heavily connected data model and a large population of apps that each want a different slice of it. Fixed REST representations make each app fetch whole objects and stitch them together. Letting the client name its fields puts the shaping work into one query, and charging by query cost ties the rate limit to the work the server really does, which a per-request limit cannot. A typed schema that can be queried for its own structure also gives tooling a single source of truth.

Limitation or tradeoff

The move is costly for integrators: an app built on REST resources has to be rewritten around queries and mutations. Shopify's announcement leaves existing apps unaffected and applies the requirement to new public apps. In operation, a 200 OK that carries errors defeats monitoring and retry logic that look only at status codes. Cost-based limits are harder to reason about than a request count, and a carelessly broad query can spend much of an app's budget in one call. Responses to POST queries are also not reused by ordinary HTTP caches the way GET responses are.

What the sources document

  • Shopify's REST Admin API reference states that the REST Admin API is a legacy API as of October 1, 2024, and that starting April 1, 2025 all new public apps must be built exclusively with the GraphQL Admin API. [27]
  • The announcement says there are no changes for existing apps, which can continue to use the REST Admin API, and that GraphQL had become a true superset of the REST API with exclusive features such as support for 2,000 product variants. [26]
  • Among its reasons the announcement lists efficient data access across the platform in a single request, minimising over-fetching by specifying exactly the data needed, and a strongly typed schema.   • The GraphQL Admin API reference says the API is rate-limited using calculated query costs measured in cost points, and its example response reports requestedQueryCost, actualQueryCost and a throttleStatus with maximumAvailable, currentlyAvailable and restoreRate. [28]
  • The same reference states that the GraphQL API can return a 200 OK response code in cases that would typically produce 4xx or 5xx errors in REST. [28]

4Common mistakes

  1. Reading the first page of a list endpoint and treating it as the whole collection.

    Why it causes problems
    The sync looks complete in testing, where there are few records, and silently drops everything past the default page size in production. GitHub's documentation, for example, shows a repository's issues request returning 30 issues out of more than 1,600.
    How to recognise it
    Record counts that stop at a round number such as 30, 50 or 100, or totals that differ from what the provider's own interface shows.
    How to fix it
    Loop until the response signals the end, such as an empty cursor or no next link, and test against a collection that is larger than one page.

  2. Retrying a POST with no idempotency key, or generating a fresh key for each attempt.

    Why it causes problems
    If the first attempt succeeded and only the response was lost, the retry creates a second order, charge or ticket. A new key per attempt gives the server no way to connect the two requests.
    How to recognise it
    Duplicate records created seconds apart, clustered around timeouts or deployments, and key generation code that sits inside the retry loop.
    How to fix it
    Generate the key once per logical operation, outside the loop, store it with the pending operation and reuse it for every attempt. Where the API has no key support, look the record up by a unique business reference before sending again.

  3. Handling every response that is not 2xx in the same way.

    Why it causes problems
    Retrying a 400 or 422 repeats a request that can never succeed and can get an integration rate limited or suspended. Giving up on a 503 or 429 turns a brief outage into lost data.
    How to recognise it
    Logs that show the same 4xx repeated many times, or jobs that fail permanently during a provider incident and need manual reruns.
    How to fix it
    Branch on the class. Correct the request and stop on 4xx. Wait and retry on 429 and 5xx with growing delays, and honour Retry-After when it is present.

  4. Doing the real work inside the webhook request handler.

    Why it causes problems
    A slow database write or downstream call pushes the response past the provider's deadline. The delivery is marked failed although your system processed it, and a retry or redelivery then runs the same work a second time.
    How to recognise it
    Timeouts in the provider's delivery log for events that your system did handle, and side effects that happen twice.
    How to fix it
    Verify the signature, store the raw event, return a 2xx, and process from a queue with deduplication by delivery id.

  5. Parsing and re-serialising a webhook body before checking its signature.

    Why it causes problems
    The signature covers the exact bytes that were sent. A framework that parses the JSON and writes it out again changes spacing or key order, so genuine deliveries fail the check, and teams respond by turning verification off.
    How to recognise it
    Signature checks that fail for every delivery although the secret is correct, and handlers that read a parsed object where they should read raw bytes.
    How to fix it
    Capture the raw request body, verify the signature over those bytes with a constant-time comparison, and only then parse the JSON.

  6. Relying on the provider's default API version.

    Why it causes problems
    A default can move when an old version is retired. Fields then change shape under a running integration, with no deployment on your side to explain the breakage.
    How to recognise it
    Requests that carry no version header or version path segment, and failures that begin on a date listed in the provider's changelog.
    How to fix it
    Send the version explicitly on every request, keep it in configuration, and plan upgrades against the provider's published retirement dates.

Exercise 1

Fetch every page of a flaky list endpoint

CodingIntermediateAbout 40 min (estimate)Hypothetical scenario

The fake API below behaves like a real list endpoint. It returns pages with a next_cursor, and it can be told to fail on chosen calls. Save it as fake_api.py. It needs only the Python standard library.

python
PAGES = {
    "": (["ord_1", "ord_2"], "c2"),
    "c2": (["ord_3", "ord_4"], "c4"),
    "c4": (["ord_5"], ""),
}


def make_api(failures):
    """Return (get, calls). `failures` maps a call number to (status, headers)."""
    calls = []

    def get(cursor):
        calls.append(cursor)
        if len(calls) in failures:
            status, headers = failures[len(calls)]
            return status, headers, {}
        items, next_cursor = PAGES[cursor]
        return 200, {}, {"data": items, "next_cursor": next_cursor}

    return get, calls

get(cursor) returns a tuple (status, headers, body), and calls records every cursor requested. In a new file fetch_all.py, write fetch_all(get, sleep). It must return every item in order, survive temporary failures and stop on permanent ones. sleep is a function that takes a number of seconds. Pass time.sleep in real use and a recording function in tests, so that the tests run instantly.

Test it with these three failure maps:

python
FLAKY = {2: (503, {"Retry-After": "2"}), 3: (429, {"Retry-After": "1"}), 5: (500, {})}
BAD_REQUEST = {2: (404, {})}
DOWN = {n: (503, {}) for n in range(2, 20)}

Requirements

  • Start with an empty cursor and keep requesting pages until next_cursor is empty. Never decide that the list has ended from the number of items on a page.
  • Treat 429 and every 5xx status as temporary: wait, then request the same cursor again.
  • Wait the number of seconds given in the Retry-After header when it is present. Otherwise wait 0.5 times 2 to the power r seconds, capped at 8, where r is 0 for the first retry of a page.
  • Give up on a page after 4 retries, which is 5 attempts, by raising an ApiError that carries the status and the number of attempts.
  • Treat every other 4xx status as permanent and raise ApiError immediately, without waiting.

Expected behaviour

With a recording function in place of sleep, the three scenarios produce:

text
flaky: ['ord_1', 'ord_2', 'ord_3', 'ord_4', 'ord_5']
  calls=['', 'c2', 'c2', 'c2', 'c4', 'c4'] waits=[2.0, 1.0, 0.5]
bad request: ApiError: HTTP 404 after 1 attempt(s)
  calls=['', 'c2'] waits=[]
down: ApiError: HTTP 503 after 5 attempt(s)
  calls=['', 'c2', 'c2', 'c2', 'c2', 'c2'] waits=[0.5, 1.0, 2.0, 4.0]
Hint 1

Split the problem in two. One function gets a single page and owns the retry loop. The other follows cursors and knows nothing about failures.

Hint 2

Count retries per page, not per run. The backoff starts again at 0.5 seconds for each new cursor.

Hint 3

Header values arrive as strings. Convert Retry-After with float before passing it to sleep.

Show solution
python
from fake_api import make_api

MAX_RETRIES = 4
BASE_DELAY = 0.5
MAX_DELAY = 8.0


class ApiError(Exception):
    def __init__(self, status, attempts):
        super().__init__(f"HTTP {status} after {attempts} attempt(s)")
        self.status, self.attempts = status, attempts


def is_retryable(status):
    return status == 429 or 500 <= status <= 599


def wait_time(headers, retry_number):
    if "Retry-After" in headers:                      # the server knows best
        return float(headers["Retry-After"])
    return min(MAX_DELAY, BASE_DELAY * 2 ** retry_number)


def get_page(get, cursor, sleep):
    for retry_number in range(MAX_RETRIES + 1):
        status, headers, body = get(cursor)
        if status == 200:
            return body
        if not is_retryable(status) or retry_number == MAX_RETRIES:
            raise ApiError(status, retry_number + 1)
        sleep(wait_time(headers, retry_number))


def fetch_all(get, sleep):
    items, cursor = [], ""
    while True:
        body = get_page(get, cursor, sleep)
        items = [*items, *body["data"]]
        cursor = body["next_cursor"]
        if not cursor:                                # empty cursor: that was the last page
            return items


def run(label, failures):
    get, calls = make_api(failures)
    waits = []
    try:
        result = fetch_all(get, waits.append)
    except ApiError as error:
        result = f"ApiError: {error}"
    print(f"{label}: {result}\n  calls={calls} waits={waits}")


if __name__ == "__main__":
    run("flaky", {2: (503, {"Retry-After": "2"}), 3: (429, {"Retry-After": "1"}), 5: (500, {})})
    run("bad request", {2: (404, {})})
    run("down", {n: (503, {}) for n in range(2, 20)})

Running python3 fetch_all.py prints the output shown under expected behaviour.

Why it is built this way:

  • Retrying is safe here because the request is a GET. Fetching the same cursor twice changes nothing on the server. The same loop around a POST would need an idempotency key.
  • The status decides the branch. In the flaky run, calls 2 and 3 fail with 503 and 429, both temporary, and the server's Retry-After values (2 and 1 seconds) are used as given. Call 5 fails with a 500 that carries no header, so the wait is the first backoff step, 0.5 seconds.
  • A 404 stops at once. No amount of waiting makes a missing resource appear, so the bad-request run makes two calls and never sleeps.
  • The retry budget is bounded. In the down run the page is tried five times with waits of 0.5, 1, 2 and 4 seconds, and then the error is raised with the status, so the caller can report or reschedule instead of hanging.
  • The end is the empty cursor. The last page holds one item, fewer than the others, but the loop never looks at page sizes.

For real traffic, multiply each computed wait by a random factor (jitter), so that many clients that failed together do not all retry at the same instant.

Check your answer

  • Does the flaky scenario return all five ids in order, with waits of exactly 2.0, 1.0 and 0.5 seconds?
  • Does the 404 scenario raise after one attempt on that page and record no waits?
  • Does the down scenario stop after five attempts on the same cursor, with waits of 0.5, 1.0, 2.0 and 4.0?
  • If you add a fourth page with a single item, does your loop still stop only when next_cursor is empty?
  • Is the retry counter reset for each new cursor?

6PATCH /tickets/7 with {"status": "closed"}200409, the ticket cannot be closed in its current stateYes for this body
7POST /tickets/7/comments201 with Location: /comments/4404, no ticket 7No
8DELETE /comments/3204404, no such commentYes, DELETE is idempotent
9POST /exports with {"resource": "tickets"}202 with Location: /exports/12429, too many exports requestedNo

Reasoning:

  • Nesting stops at collection, item, collection. Creating a comment needs its ticket, so that URL is /tickets/7/comments. Once it exists, comment 3 is addressed on its own as /comments/3, which keeps every URL within the depth that Microsoft's guidance recommends.
  • Filters are query parameters. Open tickets are a view of the /tickets collection, so there is no /open-tickets resource. Because the list is paged, the response carries a cursor for the next request.
  • Closing is a state change. The ticket already exists and one of its fields changes, so the operation is a PATCH on the ticket, not a /closeTicket URL.
  • PATCH needs care. The method carries no general idempotency guarantee, because a patch can mean "add 1" as easily as "set to 5". These two patches set a field to a fixed value, so repeating them leaves the same state. A client library that retries automatically should still treat PATCH as unsafe unless it knows the body.
  • PUT replaces everything. A field left out of the body is lost, which is why operation 4 uses PATCH. The 409 protects against overwriting someone else's edit.
  • The export is its own resource. The client creates an export job and gets 202 Accepted, which means queued and not finished. It then polls GET /exports/12 until the job reports that it is done and gives the file's URL.
  • The three POSTs need keys. Each one creates something new on every call, so after a timeout the client must retry with the same Idempotency-Key or risk two tickets, two comments or two exports.

Other answers can be right. Some APIs return 200 when asked to close a ticket that is already closed, which makes the operation idempotent in its reply as well as its effect. What matters is that the choice is deliberate and documented.

Check your answer

  • Do all nine URLs consist only of nouns, ids and query parameters?
  • Did you use 201 for the two creations, 202 for the export and 204 for the deletion?
  • Did you mark exactly the three POST operations as unsafe to retry without a key?
  • Can you say why operation 4 is a PATCH and operation 5 is a PUT?
  • Does your export design give the client a URL to check the job's progress?

    DocumentationBeginnerFreeAbout 45 minutes (estimate)

    What it teaches
    Resource naming, the status codes to return for each method, PATCH formats, asynchronous operations with 202, filtering and paging, and four ways to version an API, each with its trade-offs.
    When to use it
    When you are about to design an API of your own, or want a checklist against which to review someone else's design.

  • Designing robust and predictable APIs with idempotency (opens in a new tab)

    Stripe

    ArticleIntermediateFreeAbout 20 minutes (estimate)

    What it teaches
    Why network failures make retries unavoidable, how an idempotency key makes a retried POST safe, and how exponential backoff with jitter keeps retrying clients from overwhelming a recovering server.
    When to use it
    Before you write client code that creates or changes anything important, such as payments, orders or messages.

  • Best practices for using the REST API (opens in a new tab)

    GitHub Docs

    DocumentationBeginnerFreeAbout 15 minutes (estimate)

    What it teaches
    Practical client rules from a large public API: prefer webhooks to polling, handle rate-limit responses with the retry-after and x-ratelimit headers, follow redirects, use conditional requests, and do not ignore repeated errors.
    When to use it
    When your integration starts running on a schedule or at volume, and before you ask a provider for a higher rate limit.

  • RFC 9110: HTTP Semantics (opens in a new tab)

    IETF (RFC Editor)

    SpecificationAdvancedFreeAbout 1 hour for sections 9 and 15 (estimate)

    What it teaches
    The authoritative definitions of every method and status code, including the exact meaning of safe and idempotent and the rules for when a client may retry automatically.
    When to use it
    When a design discussion turns on what a method or status code really means, or when two sources disagree and you need the standard's wording.
