CrewAI

CrewAI is an open-source Python framework for multi-agent applications. You describe agents by role, goal and backstory, give them tasks, group them into a crew that runs the tasks in order or under a manager, and use Flows to decide in ordinary event-driven code when each crew, model call or function runs.

1Overview

Why it matters

Some jobs split naturally into stages that different specialists would do: gather the facts, check them against a policy, write the answer. CrewAI gives that split a vocabulary and a runtime. It decides which model call sees which instructions, in what order, and with whose output attached. If you do not know those rules you cannot explain why the writer agent ignored the research, why a four-task crew costs far more than you expected, or why a run took a different path the second time.

The framework has two layers that solve different problems. Crews give agents room to work out how to do a task. Flows give you control over what happens when. Teams that use only crews tend to push branching and business rules into prompts, where they are followed most of the time. Teams that know both layers put each decision where it belongs. That choice is what an engineer makes when evaluating CrewAI, reviewing its cost, or debugging a production run.

Key terms

Agent
A configured worker made of a role, a goal, a backstory, a language model and optional tools. It runs a tool-calling loop until it has an answer for the task it was given.
Role, goal and backstory
The three required strings of an agent. CrewAI inserts them into the prompt, so together they act as the agent's system prompt.
Task
One assignment for an agent, written as a description of the work plus an expected output that says what a finished answer looks like.
Expected output
The part of a task that states the criteria for the final answer, for example a format, a length or the fields that must be present.
Crew
A group of agents and an ordered list of tasks, plus a process that says how the tasks are executed.
Process
The execution strategy of a crew. CrewAI has two, sequential and hierarchical, and sequential is the default.
Manager agent
The extra agent used by the hierarchical process. It receives each task, delegates the work to a crew member and reviews what comes back.
Flow
A Python class whose methods are workflow steps. Decorators connect the steps by events, and a shared state object carries data between them.
Router
A Flow method whose returned string is treated as an event name, so that different listeners run depending on the value it returns.
Kickoff
The call that starts a run. Both crews and Flows have a kickoff method that accepts an inputs dictionary and returns the result.

2Explanation

Introduction

In Multi-Agent Systems you saw why a job is sometimes divided between several agents, and in Choosing an Agent Framework you compared how frameworks express that division. CrewAI models the work the way a small team is staffed.

Think of how an agency produces a client report. There are job descriptions (a researcher, an analyst, a writer). There are work orders that say what must be delivered. There is a rule for how work moves through the team: one person after another, or handed out by a manager. And there is an office procedure that decides whether the team is needed at all, because a simple request is answered by a clerk with a form. CrewAI has one building block for each of these:

  • An agent is the job description: a role, a goal and a backstory, plus a model and tools.
  • A task is the work order: a description and an expected output, usually assigned to one agent.
  • A crew is the team: a list of agents, an ordered list of tasks and a process.
  • The process is the rule for moving work: sequential (in list order) or hierarchical (through a manager).
  • A Flow is the office procedure: plain Python methods connected by events, with shared state, that decide when a crew, a single model call or ordinary code runs.

The official documentation (opens in a new tab) covers each block, and its introduction (opens in a new tab) calls Flows the backbone of an application and crews the units of work inside it. This lesson teaches the pieces from the bottom up: agents, tasks, crews and their two processes, then Flows. It uses CrewAI 1.15, the release line current in October 2026. One change matters if you learned from older tutorials: new crew projects are now scaffolded as JSON configuration files, while the YAML and decorator layout that most tutorials show is the "classic" option. The concepts are identical in both, and everything can also be written in plain Python, which is what this lesson does.

How it works

Agents: a role, a goal and a backstory

An Agent needs three strings. The Agents reference (opens in a new tab) defines role as the agent's function and expertise, goal as the objective that guides its decisions, and backstory as context and personality. They are not metadata. CrewAI's default prompt templates (opens in a new tab) turn them into the opening of the prompt:

text
You are {role}. {backstory}
Your personal goal is: {goal}

Writing an agent is therefore writing a system prompt in three parts. The remaining settings configure the agent loop that each agent runs:

SettingDefaultWhat it controls

allow_delegationFalseWhether it may hand work to, or question, other agents in the crew

respect_context_windowTrueSummarise the history when it outgrows the model's window instead of failing

Tasks: a description and an expected output

A Task needs a description and an expected_output, and usually an agent. Both strings go into the prompt. The expected output is introduced with the words "This is the expected criteria for your final answer", so a concrete format there is worth more than an adjective. Names in braces such as {topic} inside agent or task text are filled from the inputs dictionary at kickoff.

The Tasks reference (opens in a new tab) lists the optional controls. The ones you will use most:

  • context: a list of other tasks whose outputs this task should receive.
  • tools: limits the agent to these tools for this task.
  • output_pydantic or output_json: a Pydantic model the answer must fit. Only one output type may be set.
  • guardrail: a function that returns (True, result) or (False, "reason"). A failure is fed back to the agent, up to guardrail_max_retries times (3 by default).
  • human_input, async_execution and output_file: a human review of the answer, running without blocking the next task, and saving the result.

Crews and the two processes

A crew (opens in a new tab) combines agents, tasks and a process. crew.kickoff(inputs={...}) runs it and returns a CrewOutput with raw text, optional pydantic or json_dict, the list tasks_output and token_usage. The output of the final task is the output of the crew.

python
from crewai import Agent, Crew, Process, Task

researcher = Agent(role="Market Researcher", goal="Find facts about {topic}",
                   backstory="You name a source for every claim.")
writer = Agent(role="Briefing Writer", goal="Turn research into a one-page brief",
               backstory="You write for busy executives.")
research = Task(description="Research {topic}.", agent=researcher,
                expected_output="Ten bullet points, each with a source.")
brief = Task(description="Write the brief on {topic}.", agent=writer,
             expected_output="Under 300 words with three headings.")

crew = Crew(agents=[researcher, writer], tasks=[research, brief], process=Process.sequential)
print(crew.kickoff(inputs={"topic": "heat pumps"}).raw)

Sequential is the default. Tasks run in list order, each by its own agent. The Processes page (opens in a new tab) says the output of one task serves as context for the next. The source (opens in a new tab) is more specific: a task with no context setting receives the raw outputs of all tasks completed before it, joined by a divider line. With context=[...] it receives only the listed tasks' outputs. Either way the text is appended under the line "This is the context you're working with:".

The default matters for cost. If task iii produces oio_ioi​ tokens, the context added to task kkk is:

ck=∑i<koic_k = \sum_{i<k} o_ick​=i<k∑​oi​

Hierarchical needs process=Process.hierarchical plus either manager_llm or manager_agent; without one, the crew fails validation. Given only a model, CrewAI builds a manager with the role "Crew Manager" and gives it two tools: one to delegate work to a coworker and one to ask a coworker a question. Coworkers are listed in those tools by role, which is one more reason to give agents distinct roles. The crew still walks the task list in order, but every task goes to the manager, who chooses which agent does the work and reviews the result. The hierarchical guide (opens in a new tab) describes this as task delegation plus result validation. A custom manager must not have tools of its own, and when a task names an agent, the manager may delegate that task only to that agent. The price is extra model calls for the manager's reasoning on every task, and an assignment that is now a model decision.

The same two coworker tools appear in a sequential crew for any agent with allow_delegation=True.

Flows: event-driven control

A Flow (opens in a new tab) is a Python class. Its methods are steps, and decorators say which event runs each step:

python
from crewai.flow.flow import Flow, listen, router, start
from pydantic import BaseModel

class TicketState(BaseModel):
    text: str = ""
    urgent: bool = False

class TicketFlow(Flow[TicketState]):
    @start()
    def classify(self):
        self.state.urgent = "outage" in self.state.text.lower()

    @router(classify)
    def pick_path(self):
        return "urgent" if self.state.urgent else "routine"

    @listen("urgent")
    def page_on_call(self):
        return "paged the on-call engineer"

    @listen("routine")
    def queue_for_crew(self):
        return "queued for the support crew"

print(TicketFlow().kickoff(inputs={"text": "Checkout outage since 09:00"}))

The text contains "outage", so the router returns urgent, only page_on_call runs, and the script prints paged the on-call engineer.

  • @start() marks an entry point. @listen(x) runs a method when method x finishes or when a router emits the label x. @router(x) runs after x, and the string it returns becomes the next event. or_(a, b) fires on either event and and_(a, b) waits for both.
  • self.state is a dictionary or, with Flow[Model], a Pydantic model. Every state gets an id. kickoff(inputs=...) merges the inputs into the state and returns the output of the last method to finish.
  • @persist saves state (SQLite by default) so that a run can be reloaded. @human_feedback pauses for a person and needs version 1.8.0 or later. flow.plot() writes an HTML diagram of the Flow.
  • Any step can call a crew: result = crew.kickoff(inputs=...), then store result.raw or result.pydantic in the state.

"Event-driven" means you never write the call order. Each method declares what it reacts to and the runtime fires it. A loop is a router that returns a label an earlier step listens for. As a safety net the runtime (opens in a new tab) stops a run with a RecursionError once one method has been called more than 100 times.

CrewAI's production guidance (opens in a new tab) is to start with a Flow. The Flow holds the state and the control logic, and each crew is a focused unit of work called from one of its steps.

Project layout and versions

PyPI (opens in a new tab) listed crewai 1.15.27, for Python 3.10 to 3.13, on 9 October 2026. crewai create crew <name> now generates JSON-first projects: one agents/<name>.jsonc file per agent and a crew.jsonc with the tasks and the process, started with crewai run. Adding --classic generates the older layout of config/agents.yaml, config/tasks.yaml and a crew.py that uses the @CrewBase, @agent, @task and @crew decorators. crewai create flow <name> scaffolds a Flow project with one embedded crew.

Worked example: A refund-request Flow that calls a two-agent crew only for the hard cases

An online shop receives refund requests. Small refunds are paid automatically. Damaged-item claims above the limit need a policy check and a written reply. Everything else goes to a person. The routing is a business rule, so it belongs in Flow code. Reading the policy and writing the email is language work, so it belongs in a crew.

Step 1: the Flow, with the crew stubbed out

Install CrewAI with pip install crewai in a Python 3.10 to 3.13 environment and save this as refund_flow.py. This step makes no model calls and needs no API key.

python
from crewai.flow.flow import Flow, listen, router, start
from pydantic import BaseModel

AUTO_REFUND_LIMIT = 50.00


class RefundState(BaseModel):
    order_id: str = ""
    amount: float = 0.0
    reason: str = ""
    route: str = ""
    reply: str = ""


def draft_reply(state: RefundState) -> str:
    """Stand-in for the crew. Step 2 replaces this function."""
    return f"[crew drafts a reply about {state.order_id}]"


class RefundFlow(Flow[RefundState]):
    @start()
    def receive_request(self):
        return self.state.order_id

    @router(receive_request)
    def choose_route(self):
        if self.state.amount <= AUTO_REFUND_LIMIT:
            self.state.route = "auto_refund"
        elif "damaged" in self.state.reason.lower():
            self.state.route = "crew_review"
        else:
            self.state.route = "human_review"
        return self.state.route

    @listen("auto_refund")
    def refund_now(self):
        self.state.reply = f"Refund of {self.state.amount:.2f} USD issued for {self.state.order_id}."
        return self.state.reply

    @listen("crew_review")
    def ask_crew(self):
        self.state.reply = draft_reply(self.state)
        return self.state.reply

    @listen("human_review")
    def queue_for_human(self):
        self.state.reply = f"{self.state.order_id} queued for a human agent."
        return self.state.reply


REQUESTS = [
    {"order_id": "A-1001", "amount": 19.99, "reason": "Changed my mind"},
    {"order_id": "A-1002", "amount": 240.00, "reason": "Arrived damaged, box crushed"},
    {"order_id": "A-1003", "amount": 310.50, "reason": "Late delivery"},
]

if __name__ == "__main__":
    for request in REQUESTS:
        flow = RefundFlow()
        result = flow.kickoff(inputs=request)
        print(f"{request['order_id']}: {flow.state.route} -> {result}")

A-1002: crew_review -> [crew drafts a reply about A-1002]
A-1003: human_review -> A-1003 queued for a human agent.
RequestAmount at or under 50?"damaged" in reason?Label from the routerMethod that runs

For each request, kickoff(inputs=request) copies the three values into the state. The @start method runs, the router runs after it, and the label it returns is the event that exactly one listener is waiting for. kickoff returns that listener's return value because it is the last method to finish.

Step 2: replace the stub with a crew

Replace draft_reply with the version below and add the import at the top of the file. This step calls a model, so set MODEL to a provider/model-id your account can use and provide that provider's API key. If the provider's SDK is missing, install the extra that the LLMs page (opens in a new tab) names for it, such as crewai[openai].

python
from crewai import Agent, Crew, Process, Task

MODEL = "openai/gpt-4o"


def draft_reply(state: RefundState) -> str:
    analyst = Agent(
        role="Refund Policy Analyst",
        goal="Decide whether a refund request meets the written policy",
        backstory="You have handled returns for an online homeware shop for years "
                  "and you always name the policy clause you rely on.",
        llm=MODEL,
    )
    writer = Agent(
        role="Customer Support Writer",
        goal="Write a short, polite reply that states the decision and the next step",
        backstory="You write plain-language emails and never promise anything "
                  "the analyst did not approve.",
        llm=MODEL,
    )
    assess = Task(
        description="Order {order_id}: the customer asks for a refund of {amount} USD. "
                    "Reason given: {reason}\n"
                    "Policy: damaged items are refunded in full when reported within 30 days. "
                    "Above 200 USD a photo of the damage is required first.",
        expected_output="One line that starts with APPROVE, REJECT or NEED_PHOTO, "
                        "then one sentence naming the policy clause.",
        agent=analyst,
    )
    reply = Task(
        description="Write the email reply to the customer for order {order_id}.",
        expected_output="An email body under 80 words.",
        agent=writer,
    )
    crew = Crew(agents=[analyst, writer], tasks=[assess, reply], process=Process.sequential)
    result = crew.kickoff(
        inputs={"order_id": state.order_id, "amount": state.amount, "reason": state.reason}
    )
    return result.raw

Run the file again. A-1001 and A-1003 behave exactly as before and still make no model calls. Only A-1002 reaches the crew, which runs assess and then reply. The writer never sees the policy text directly. It sees the analyst's answer as context. Assembled from the default templates in the repository, the writer's call has this shape:

text

you MUST return the actual complete content as the final answer, not a summary.

(the analyst's full answer, for example a line starting NEED_PHOTO)

The exact wording differs between versions, and tools, memory or structured output add more instructions. The Customizing Prompts guide (opens in a new tab) shows how to print the real prompt for your own agent.

The result to notice is the division of labour. Three requests produced one crew run. The rule that decides who gets an automatic refund is two lines of Python that behave the same way every time, and the model is used only where judgement and wording are needed.

Edge cases and limitations

By default every task receives every earlier output
A task with no context setting gets the raw outputs of all tasks completed before it, not only the one directly before it. In a long crew the last task carries the whole history, which raises cost and can bury the one result it needs. Set context to the specific tasks a step depends on, and ask upstream tasks for compact structured output.
An agent that reaches max_iter returns its best attempt, not an error
The documented behaviour of max_iter (20 by default) is that the agent must then provide its best answer. A task that ran out of iterations therefore looks like a normal completion. Add a guardrail or a structured output model that would reject a half-finished answer, and watch iteration counts in a trace.
A hierarchical crew can fail before it starts, or cost more than it saves
Without manager_llm or manager_agent the crew does not validate, and a custom manager that has tools raises an exception. When it does run, the manager adds model calls to every task and may delegate to a different agent than you expected. If you can write down who does what, use the sequential process.
Labels and method names share one event namespace in a Flow
A listener on "review" fires when a method called review finishes and also when a router returns "review". A label that matches the name of the method listening for it creates a loop. The runtime raises RecursionError after a method has been called more than 100 times, so name router labels after outcomes and methods after actions.
Automatic summarisation can drop the detail a later step needs
With respect_context_window left at True, CrewAI summarises an agent's conversation when it no longer fits the model's window and carries on. That keeps long runs alive but can lose exact figures or clauses. For work where missing detail is worse than a failure, the documentation suggests setting it to False so the run stops, and moving large inputs into retrieval tools.
Only the last result is returned
crew.kickoff returns the final task's output, and flow.kickoff returns the output of the last method to finish. In a Flow with parallel branches that may not be the method you think of as the end. Write every result you need into the Flow state, or read tasks_output on the crew result, instead of relying on the return value.

When to use it, and when something simpler is enough

Use it when

  • The work divides into stages that read like job roles, and each stage hands a text or structured result to the next, such as research, analysis and writing.
  • You need deterministic steps and agent steps in one application: a Flow holds the rules, state and branching, and calls a crew only where judgement is needed.
  • People who are not framework experts must read or edit the agent and task definitions, which CrewAI keeps in JSON or YAML configuration files separate from code.
  • You want a human approval point, persistence of state between steps, or a visual plot of the workflow without building those parts yourself.

Think twice when

  • One model call or one agent with a few tools already does the job. Each extra agent and task adds model calls, latency and another prompt to maintain.
  • The order of work is known in advance and you are considering the hierarchical process. A manager model then re-decides on every run something you could have written down once.
  • Your stack is not Python, or you need to control every transition of a graph yourself. A lower-level graph framework such as LangGraph fits that better.
  • Latency per request is tightly bounded. A two-task crew needs at least two model calls in series before anything is returned.

A simpler alternative. A prompt chain, meaning two or three model calls in plain Python where each call receives the previous output, covers most fixed pipelines without a framework. It stops being enough when steps need their own tools and loops, when you want typed state with persistence and human review, or when several people must maintain the agent definitions as configuration.

Key takeaways

  • An agent's role, goal and backstory are prompt text, and a task's description and expected output are the rest of that prompt, so writing them precisely is the main way to control a crew.
  • The sequential process runs tasks in list order and, unless you set context yourself, gives each task the raw outputs of all the tasks before it.
  • The hierarchical process puts a manager model between the task list and the agents, which costs extra model calls and makes the assignment of work a model decision.
  • A Flow is ordinary Python connected by start, listen and router events with shared state, and it is the right place for rules, branching, loops and human approval.
  • The pattern the documentation recommends for production is a Flow as the backbone with small, focused crews called from its steps.
  • Before adding an agent, check whether a single model call or a line of code in the Flow would do the same job more cheaply and more predictably.

Example 1 of 5

IBM Consulting combining Flows and crews for federal eligibility decisions

IBM ConsultingDocumented in a case study

CrewAI's published case study "IBM automates federal eligibility with Agents" is based on an interview with Narayanan Alavandar of IBM Consulting (Federal). It describes two pilots inside United States federal agencies that determine whether an applicant is eligible for a programme. [21][2][11][9]

The problem

The case study describes agencies with an ageing workforce and decades-old legacy systems that struggle to process critical applications quickly and cost-effectively. Coordinating several synchronous and asynchronous systems with traditional robotic process automation (RPA) tools had left gaps in speed, scalability and control over business rules.

Where this topic fits

Both CrewAI layers are used, each for a different kind of step. The case study calls the design a hybrid of "AI Flows + Crew Agents" whose purpose is to control when a rules-based decision runs and when autonomous agents run. The agents extract applicant data from documents, summarise findings and calculate programme eligibility. Models are served by IBM's watsonx.ai runtime. Around the Flow sit the legacy and modern agency systems that it coordinates.

How it is applied, step by step

  1. The case study does not publish the pilots' code, so the steps below describe how a Flow of this kind is typically built from the pieces it names.
  2. A Flow run is started for each application. Its typed state holds the application identifier, the fields extracted so far and the current decision.
  3. An early step calls a crew whose agents read the submitted documents, extract the applicant's data and summarise what they found. The result is written into the state as structured fields.
  4. A router inspects the state and returns a label. Cases that fixed business rules can settle go to a plain-code step. Cases that need interpretation go to a step that uses agents.
  5. The rules step computes the outcome with ordinary code, so the same inputs always give the same decision and the rule can be unit-tested.
  6. Each agent's llm setting points at a model served through watsonx.ai, and the final step passes the determination back to the surrounding agency systems.

Why this approach fits

An eligibility decision mixes two kinds of work. Thresholds and programme rules must be applied the same way to every applicant and must be explainable afterwards, which is what code is good at. Reading scanned or free-text documents is what language models are good at. A Flow lets each part be built the right way and makes the boundary between them an explicit, testable router instead of a sentence in a prompt. It also replaces the coordination role that RPA scripts played, because a Flow step is ordinary Python that can call any system.

Limitation or tradeoff

This is a vendor-published case study about pilots, and it gives no measurements: "faster, more efficient" is not quantified. It also does not show the architecture in detail, so the steps above are a reconstruction. In this setting an extraction error flows straight into the rule step and produces a confident wrong decision, so a real deployment needs validation of extracted fields, human review of uncertain cases and an audit record. Flow state persistence helps with the last point but is not an audit system by itself.

What the sources document

  • The case study states that by 2025 the team had two CrewAI pilots running inside federal agencies, integrated with IBM's watsonx foundation-model runtime. [21]
  • It says the team built a hybrid "AI Flows + Crew Agents" architecture to control when rules-based decisions versus autonomous agents run. [21]
  • It says multiple agents were deployed to extract applicant data from documents, summarize findings and calculate program eligibility. [21]
  • It reports that early pilots show faster, more efficient eligibility determinations than legacy RPA, without giving figures, and that IBM Consulting was finalizing enterprise-license deals with federal agencies with the aim of moving the pilots into production. [21]
  • CrewAI's documentation recommends this structure in general. Its introduction and production guidance say to start with a Flow that manages state and control and to delegate complex work to crews, and its state guide shows a router that chooses a label from values held in the Flow state. [2][11][9]

The facts above come from the cited sources. The steps and analysis in this example are our explanation of how they fit together.

Example 2 of 5

Gelato running agents behind its platform for catalogue mapping and carrier onboarding

GelatoDocumented in a case study

CrewAI's published case study "Gelato accelerates fulfillment via agentic integration" is based on an interview with Styrbjörn Holmberg of Gelato, a print-on-demand platform that sends orders to local printers. It describes agents working behind the Gelato Connect product and inside the company. [22][5]

The problem

According to the case study, a printer joining Gelato's network had to map as many as 200,000 product codes (SKUs) by hand. That task previously took 9 to 24 months and often stalled, which cost both sides revenue. Inside the company, adding a new logistics carrier took days of engineering effort and slowed expansion into new regions.

Where this topic fits

The agents sit behind an existing product, out of sight of its users. The case study names three uses: agents behind Gelato Connect that map bulk product catalogues automatically and validate file uploads, logistics agents that generate, test and deploy carrier-integration code, and internal crews for routine operations work. In each one a crew stands between an incoming document (a catalogue file or a carrier's API description) and a system of record that needs clean, structured data or working code.

How it is applied, step by step

  1. The case study does not publish Gelato's crew definitions, so these steps describe how a generate, test and deploy crew is typically assembled in CrewAI.
  2. An integration agent receives the carrier's API description as task input. The task's expected output names the exact functions the platform's carrier adapter must provide.
  3. A second task, owned by a testing agent with a tool that runs code against sandbox shipments, has an expected output of one pass or fail line per test. Its context is limited to the code task.
  4. A guardrail on the testing task rejects any answer that reports a failure, which sends the failure text back to the agent for another attempt, up to the retry limit.
  5. Deployment is a plain-code step that runs only after the tests pass, for example a Flow step behind a router, so that shipping code is never left to an agent's judgement.
  6. For catalogue mapping, one crew definition is started once per batch of products with kickoff_for_each or its async variants, which is how a single definition becomes thousands of runs.

Why this approach fits

Both jobs are repetitive transformations from messy text into something a machine can check. A mapped product either matches a catalogue entry or does not, and generated adapter code either passes its tests or does not. That makes them a good match for tasks with a precise expected output followed by a verification stage. Running the agents behind an existing product also means customers experience a faster onboarding step and never have to learn that agents are involved.

Limitation or tradeoff

The figures are the company's own, reported in a vendor case study without a method or a baseline period, so treat them as claims. Deploying generated integration code is only as safe as the tests in front of it, and carrier APIs have edge cases that a sandbox does not show. Thousands of agent runs also mean real model cost and rate limits, and a wrong catalogue mapping turns into a wrongly printed order, so sampling and review of the output still matter.

Tracing a crew's agent and model calls in Langfuse through OpenTelemetry

LangfuseDocumented in official docs

Both projects document this integration. CrewAI's observability pages include a Langfuse guide, and Langfuse's integration catalogue includes a CrewAI page. Each one shows a small crew whose execution appears as a trace in Langfuse. [15][16]

The problem

One kickoff call hides many model calls made by different agents. When the final answer is wrong you need to see which task and which agent produced what, with which inputs, and how long each step took. Both guides present the integration as the way to get that: observability and debugging for a CrewAI application, with traces a team can inspect after the run.

Where this topic fits

Tracing is set up once, before any crew is created, and it is not part of the crew definition. An instrumentation library hooks into CrewAI, and each run then emits OpenTelemetry spans that are exported to Langfuse. The agents, tasks and kickoff call stay exactly as they were. Afterwards the run is opened in the Langfuse trace view. See Langfuse for the platform itself.

How it is applied, step by step

  1. Install the Langfuse SDK and one instrumentation package. The Langfuse page uses openinference-instrumentation-crewai, and the CrewAI page uses openlit.
  2. Set the Langfuse public key, secret key and host as environment variables, create the client with get_client() and confirm the credentials with auth_check().
  3. Initialise the instrumentation once at start-up: CrewAIInstrumentor().instrument(skip_dep_check=True) on the Langfuse route, or openlit.init() on the CrewAI route.
  4. Define agents, tasks and the crew as usual. Nothing in them refers to tracing.
  5. Call kickoff. On the Langfuse route the call can be wrapped in start_as_current_observation with a span name, which groups the whole run under one named parent.
  6. Call langfuse.flush() before a short-lived script exits so that the spans are exported, then open the trace.

Why this approach fits

A crew is hard to debug from its final output because the mistake usually happened two tasks earlier. A trace turns the run into a tree of spans that can be read task by task. Instrumenting the framework, instead of adding logging to every agent, means new agents and tasks are traced without extra work. The data travels as OpenTelemetry spans, so the same instrumentation can feed a different backend later.

Limitation or tradeoff

The two official guides use different instrumentation libraries, so span names and attributes differ between them. Choose one route and do not enable both. The Langfuse page warns that other libraries in the application may emit OpenTelemetry spans that still count toward billable units, and that some attributes may land in the metadata object instead of mapped fields. Traces contain prompts and outputs, so customer data in a task leaves your system unless you self-host or mask it.

The official Lead Score Flow sample with a human review loop

CrewAIDocumented in an open-source project

The crewAI-examples repository, maintained by CrewAI, contains a Lead Score Flow project. Its README and main.py show a complete Flow that scores records with a crew, pauses for a person, and then writes emails. It is a maintained reference sample, not a customer deployment. [24][8][19]

The problem

Many records have to be scored by a language model, a person has to look at the top results before any email is written, and that person may want the scoring repeated with extra guidance. This needs parallel work, a human decision and a loop of unknown length, none of which a single sequential crew can express. Although the project is named for leads, the sample's data are job candidates scored against a job description.

Where this topic fits

The Flow is the application and owns the state: the loaded records, their scores and the reviewer's feedback. Crews appear inside two of its steps, once per record for scoring and once per record for writing an email. Between those steps sits a router whose return value is the reviewer's decision.

How it is applied, step by step

  1. load_leads is the @start method. It reads leads.csv and stores one Candidate object per row in the Flow state.
  2. score_leads listens for either the end of load_leads or the label scored_leads_feedback. It starts one LeadScoreCrew run per candidate with kickoff_async and waits for all of them with asyncio.gather.
  3. LeadScoreCrew is one agent and one task with output_pydantic set to a CandidateScore model, so every run returns a typed score and reason that the Flow appends to its state.
  4. human_in_the_loop is a @router on score_leads. It sorts the scored candidates, prints the top three and asks the reviewer to quit, rescore with feedback, or proceed.
  5. On a rescore it saves the feedback in the state and returns scored_leads_feedback, the label that score_leads listens for. That closes the loop, and the feedback reaches the task through an additional_instructions input.
  6. On proceed it returns generate_emails. write_and_save_emails listens for that label, runs a LeadResponseCrew per candidate concurrently and writes one text file for each.

Why this approach fits

Whether to continue, repeat or stop is a person's decision, and how many rescoring rounds happen is not known in advance. A router that returns a label is a direct way to write that. The crews stay small, one agent and one task each, and are reused for every record. Structured output is what makes the arrangement work: because each crew run returns a typed score, the Flow can sort and select in plain Python instead of parsing prose.

Limitation or tradeoff

The sample reads the reviewer's choice with input(), so it only works at a terminal. A deployed application would use the @human_feedback decorator or another asynchronous mechanism, as covered in Human-in-the-Loop. All records are scored at once, which can hit provider rate limits on a large file. The loop has no cap of its own beyond the reviewer's patience and the runtime's limit of 100 calls per method. The README pins an older CrewAI release (0.130.0), so expect to adjust it for the 1.x line.

4Common mistakes

  1. Writing an expected_output such as "a good summary" and then parsing the answer with string matching.

    Why it causes problems
    The expected output is the acceptance criterion the model reads. When it is vague, the shape of the answer changes from run to run, and the code that picks values out of result.raw breaks without warning.
    How to recognise it
    Regular expressions or split calls applied to result.raw, and bug reports that trace back to a heading or bullet style the model changed.
    How to fix it
    State the format, length and required fields in expected_output, set output_pydantic to a model and read result.pydantic, and add a guardrail for rules the model cannot be trusted to keep.

  2. Choosing the hierarchical process for a pipeline whose order and owners are already known.

    Why it causes problems
    A manager model is called on every task to decide something you could have written down, which adds cost and latency and lets the assignment vary between runs.
    How to recognise it
    Traces in which a manager step restates each task before delegating it, and a hierarchical run that costs clearly more than the same tasks run sequentially.
    How to fix it
    Use the sequential process with an agent named on every task. If the path really varies, put the decision in a Flow router and keep each crew sequential.

  3. Putting business rules and branching into task descriptions or backstories instead of Flow code.

    Why it causes problems
    A sentence such as "if the amount is over 50, escalate" is followed most of the time, not every time, and it cannot be unit-tested or audited.
    How to recognise it
    If-then sentences inside prompts, and occasional runs that take the wrong branch on inputs that should be clear-cut.
    How to fix it
    Move the condition into a @router method that reads typed Flow state, and let the crew handle only the branch that needs judgement.

  4. Leaving context unset in a crew with many tasks.

    Why it causes problems
    Each task then receives the raw output of every earlier task, so prompt size grows with position in the list and later agents are distracted by material they do not need.
    How to recognise it
    Prompt token counts that rise task by task in a trace, and late tasks that quote text from steps they had no reason to see.
    How to fix it
    Set context on each task to the tasks it depends on, and ask upstream tasks for short structured results instead of long prose.

  5. Setting allow_delegation=True on every agent.

    Why it causes problems
    Every agent gains the coworker tools, so agents can hand work back and forth. Each handover means more model calls, and nothing but the iteration limit stops two agents from repeatedly consulting each other.
    How to recognise it
    Traces with repeated delegate or ask-question tool calls between the same two agents and tasks that end at the iteration limit.
    How to fix it
    Leave delegation off, which is the default, and turn it on for a single coordinating agent only when you can name the situation in which it should delegate.

Show solution

The loop is made of three pieces: a listener that reacts to two labels, a router attached to that listener, and a counter in the state that the router uses to stop.

python
from crewai.flow.flow import Flow, listen, or_, router, start
from pydantic import BaseModel

AUTO_REFUND_LIMIT = 50.00
MAX_ATTEMPTS = 2
MAX_WORDS = 40

TOO_LONG = ("We are sorry to hear that. " * 12).strip()   # 72 words, no order number
GOOD = "Order A-1002: your refund of 240.00 USD is approved. Please reply with a photo of the damage."


class RefundState(BaseModel):
    order_id: str = ""
    amount: float = 0.0
    reason: str = ""
    drafts: list[str] = []      # scripted stand-in for the crew's answers
    attempts: int = 0
    path: list[str] = []
    reply: str = ""


class RefundFlow(Flow[RefundState]):
    @start()
    def receive_request(self):
        return self.state.order_id

    @router(receive_request)
    def choose_route(self):
        if self.state.amount <= AUTO_REFUND_LIMIT:
            label = "auto_refund"
        elif "damaged" in self.state.reason.lower():
            label = "crew_review"
        else:
            label = "human_review"
        self.state.path = [*self.state.path, label]
        return label

    @listen("auto_refund")
    def refund_now(self):
        self.state.reply = f"Refund of {self.state.amount:.2f} USD issued for {self.state.order_id}."
        return self.state.reply

    @listen(or_("crew_review", "revise"))
    def ask_crew(self):
        self.state.attempts += 1
        self.state.reply = self.state.drafts[self.state.attempts - 1]
        return self.state.reply

    @router(ask_crew)
    def check_reply(self):
        reply = self.state.reply
        acceptable = self.state.order_id in reply and len(reply.split()) <= MAX_WORDS
        if acceptable:
            label = "send"
        elif self.state.attempts < MAX_ATTEMPTS:
            label = "revise"
        else:
            label = "human_review"
        self.state.path = [*self.state.path, label]
        return label

    @listen("send")
    def send_reply(self):
        return self.state.reply

    @listen("human_review")
    def queue_for_human(self):
        self.state.reply = f"{self.state.order_id} queued for a human agent."
        return self.state.reply


REQUEST = {"order_id": "A-1002", "amount": 240.00, "reason": "Arrived damaged, box crushed"}

if __name__ == "__main__":
    for name, drafts in [("flaky", [TOO_LONG, GOOD]), ("hopeless", [TOO_LONG, TOO_LONG])]:
        flow = RefundFlow()
        result = flow.kickoff(inputs={**REQUEST, "drafts": drafts})
        print(f"{name}: path={flow.state.path} attempts={flow.state.attempts} -> {result}")

Trace of the flaky run: choose_route returns crew_review, so ask_crew runs (attempts becomes 1) and takes the 72-word draft. check_reply finds no order id and more than 40 words, and because 1 is below MAX_ATTEMPTS it returns revise. ask_crew listens for that label too, so it runs again (attempts becomes 2) and takes the 17-word draft that contains A-1002. check_reply returns send, and send_reply is the last method to finish, so its return value is what kickoff returns.

In the hopeless run the second draft is also rejected. Now attempts is 2, which is not below MAX_ATTEMPTS, so the router returns human_review and the existing queue_for_human method ends the run. The label human_review is emitted by two different routers and handled by one listener, which is a normal and useful arrangement.

This is the same shape as the official Lead Score Flow sample: a listener on or_(..., "label"), a router after it, and a label that points back. To use a real crew, replace the line that reads from drafts with a call to the Step 2 draft_reply function and pass the previous reply and the reason it was rejected as extra inputs, so that the second attempt is a revision and not a blind retry.

class WeeklyState(BaseModel):
    summary: Summary = Summary()
    policy_notes: str = ""
    plan: str = ""


class WeeklyFlow(Flow[WeeklyState]):
    @start()
    def summarise(self):
        # Tasks 1 and 2. Task 2 sets output_pydantic=Summary.
        self.state.summary = summary_crew.kickoff().pydantic

    @router(summarise)
    def need_policy(self):
        return "policy_needed" if self.state.summary.policy_questions else "policy_skipped"

    @listen("policy_needed")
    def run_policy_check(self):
        questions = "\n".join(self.state.summary.policy_questions)
        self.state.policy_notes = policy_crew.kickoff(inputs={"questions": questions}).raw

    @listen(or_("policy_skipped", run_policy_check))
    def draft_plan(self):
        inputs = {
            "complaints": "\n".join(self.state.summary.complaints),
            "policy_notes": self.state.policy_notes,
        }
        self.state.plan = plan_crew.kickoff(inputs=inputs).raw
        return self.state.plan

The router tests policy_questions, a typed list produced by the summary task. When it is empty the policy crew is never started, so the skip costs nothing and happens every time the condition holds. The plan step listens for either the skip label or the end of the policy check, so both paths meet again.

  • Do your default contexts read 0, 2,400, 3,000 and 3,300, with a total of 8,700 tokens?
  • Do your explicit contexts read 0, 2,400, 600 and 900, with a total of 3,900 tokens and a saving of 55.2%?
  • Did you name manager_llm or manager_agent as the requirement of the hierarchical process?
  • Does your alternative decide the skip in a router that reads a structured field, not in a prompt?
