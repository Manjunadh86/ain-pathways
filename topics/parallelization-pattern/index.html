Parallelization (Sectioning and Voting)

Parallelization is a workflow pattern in which your code sends several LLM calls at the same time and combines their outputs with a fixed rule. In sectioning, each call handles a different, independent part of the task. In voting, the same task is run several times and the answers are counted or compared.

1Overview

Why it matters

A prompt chain runs one call after another, so its latency is the sum of its steps. When the steps do not depend on each other, that waiting is wasted: four one-second calls can return in about one second instead of four. Parallelization is also a quality tool. A single prompt that has to answer a customer, screen the request for abuse and extract three fields must split its attention, and Anthropic's guidance is that models generally do better when each consideration gets its own call. Running the same check several times and requiring agreement is how some production systems cut false alarms and how evaluation setups avoid trusting a single judge.

The pattern is easy to draw and easy to get wrong. Every extra branch is billed, a burst of simultaneous requests can trip a rate limit, one slow or failed branch can hang the whole request, and votes from near-identical calls agree with each other without being right. Anyone who designs, reviews or debugs LLM workflows needs to be able to say which branches are truly independent, how their outputs are aggregated, and what happens when one of them fails.

Key terms

Parallelization
A workflow in which code starts several LLM calls at once and combines their outputs with a rule fixed in advance.
Sectioning
The variant in which each parallel call does a different, independent part of the task, such as one call per concern or per document section.
Voting
The variant in which the same task is attempted several times and the answers are counted, averaged or compared.
Fan-out and fan-in
Fan-out is the point where one input becomes several concurrent calls. Fan-in is the point where their outputs are collected into one result.
Aggregator
The code, or sometimes a further LLM call, that turns the branch outputs into a single result by merging, counting or synthesising.
Independent subtasks
Subtasks where none needs the output of another, so each could be completed even if the others never ran.
Vote threshold
The number of votes, k out of n, that must agree before the aggregator takes an action such as flagging content.
Quorum
The minimum number of valid votes that must come back before the aggregator is allowed to decide at all.
Concurrency limit
A cap on how many calls may be in flight at once, used to stay inside provider rate limits.
Self-consistency
A voting method from a 2022 paper that samples several reasoning paths from one model and returns the most frequent final answer.

2Explanation

Introduction

In Prompt Chaining each LLM call waits for the one before it, because step two needs the output of step one. Many tasks contain steps with no such dependency. Extracting the order number from a support ticket does not require the summary of that ticket, and checking a message for abuse does not require the answer to it. When nothing flows between two steps, there is no reason to run them one after the other.

You already organise work this way. A news editor with a deadline hands the sports, weather and business pages to three reporters at once and assembles the paper when all three have filed. Nobody waits for the weather page before starting on sport. That is sectioning: split a job into independent parts, run them at the same time and combine the results.

A different habit has the same shape. Before surgery, a patient may ask three doctors to read the same scan and act on what most of them say. No doctor does a different job. The point is that three separate readings are less likely to share one mistake. That is voting: run the same task several times and aggregate the answers.

Anthropic's guide Building effective agents (opens in a new tab) puts both under one workflow, parallelization, which it describes as LLMs working simultaneously on a task and having their outputs aggregated programmatically. Both variants are workflows in that guide's sense: your code, not the model, decides how many calls are made and what each one is asked.

The diagram has three parts, and each is a design decision. The fan-out decides what the branches are. The branches are ordinary LLM calls that know nothing about each other. The aggregator, also called the fan-in, turns several outputs into one result. Most of the engineering goes there: a merge for sectioning, a count against a threshold for voting.

This lesson covers how to tell whether branches are independent, how to aggregate sections and votes, what the pattern does to latency, cost and rate limits, how to keep one failed branch from ruining a request, and how the pattern differs from Orchestrator-Workers, which looks the same on a whiteboard.

How it works

Fan out, wait, fan in

Stripped of framework detail, the pattern is three lines. This block is pseudocode; the worked example is the runnable version.

python
prompts = build_branch_prompts(task)                  # fan out: decided by your code
outputs = await gather(*(llm(p) for p in prompts))    # branches run concurrently
result = aggregate(outputs)                           # fan in: merge or count

LLM calls are I/O-bound. Your program spends the time waiting for network responses, so a single Python process can hold many calls open at once with asyncio, or with a thread pool as Anthropic's cookbook (opens in a new tab) does. Two properties follow from the shape. No branch can see another branch's output, because every prompt is built before any reply arrives. And the set of branches is fixed by code before the model has said anything.

Sectioning: different jobs at the same moment

In sectioning each branch gets a different instruction, a different slice of the input, or both. Three documented uses show the range:

  • A guardrail beside the main call. One call answers the user while another screens the request. Anthropic notes that this tends to perform better than one call handling both jobs.
  • One specialist per concern. Claude Code's Code Review sends several agents over the same diff, each looking for a different class of issue.
  • One criterion per evaluator. An automated evaluation scores the same output on different aspects in separate calls.

The test for a safe split is one question: could each branch do its job if the others never ran? If a branch needs a fact that another branch produces, the two belong in a chain. The aggregator for sections is usually plain code that assembles a record. It can be a further LLM call when the parts must be woven into prose, in which case the fan-out is followed by one chain step.

Voting: one job, several attempts

In voting every branch attempts the same task and the aggregator counts. Votes only add information when the attempts can disagree, so something must differ between them:

Source of diversityDocumented in
Sampling with a temperature above zeroSelf-consistency (opens in a new tab): many sampled reasoning paths, majority vote on the final answer
Reordering the inputCursor's Bugbot at launch: eight passes over a shuffled diff
Different prompts for one questionAnthropic's guide: several prompts review code and flag problems
Different modelsPoLL (opens in a new tab): three judges from three model families

The aggregation rule is a policy choice. With nnn votes on a yes-or-no question, act when at least kkk say yes:

  • k=1k = 1k=1 (any vote) catches the most real problems and raises the most false alarms.
  • k=(n+1)/2k = (n+1)/2k=(n+1)/2 (majority, for odd nnn) balances the two.
  • k=nk = nk=n (unanimous) raises almost no false alarms and misses the most.

Anthropic's guide names this lever: different vote thresholds balance false positives against false negatives. Scores on a scale are averaged instead of counted.

How much does a majority help? If each vote is correct with probability ppp, independently of the others, the majority of nnn votes (odd nnn) is correct with probability

Pmajority(n,p)=∑j=(n+1)/2n(nj) pj(1−p)n−jP_{\text{majority}}(n, p) = \sum_{j=(n+1)/2}^{n} \binom{n}{j}\, p^{j} (1-p)^{n-j}Pmajority​(n,p)=j=(n+1)/2∑n​(jn​)pj(1−p)n−j

For p=0.8p = 0.8p=0.8 and n=5n = 5n=5 the three terms are 0.2048+0.4096+0.3277=0.9420.2048 + 0.4096 + 0.3277 = 0.9420.2048+0.4096+0.3277=0.942.

The formula restates the Condorcet jury theorem (opens in a new tab), and its two assumptions are the two ways voting disappoints. Each voter must be right more often than wrong: below p=0.5p = 0.5p=0.5 the majority is worse than a single call. And errors must be independent. Five samples from one model with one prompt share training data, instructions and blind spots, so real gains are smaller than the curve. Measure on labelled examples before relying on the formula.

What you gain and what you pay

Latency. With branch latencies t1,…,tnt_1, \dots, t_nt1​,…,tn​ and aggregation time tat_ata​:

Tsequential=∑iti+taTparallel=max⁡iti+taT_{\text{sequential}} = \sum_{i} t_i + t_a \qquad T_{\text{parallel}} = \max_{i} t_i + t_aTsequential​=i∑​ti​+ta​Tparallel​=imax​ti​+ta​

The slowest branch sets the pace, so one slow branch erases most of the gain.

Cost. Parallel calls are not cheaper. They finish sooner. Every branch is billed, and context shared by the branches is sent once per branch. A 3,000-token document with four 100-token instructions costs 4×3,100=12,4004 \times 3{,}100 = 12{,}4004×3,100=12,400 input tokens as four calls, against 3,400 as one combined call. Prompt caching can discount the repeated part, but Anthropic's prompt caching documentation (opens in a new tab) notes that a cache entry only becomes available after the first response begins, so branches sent in the same instant all miss it.

Rate limits. A fan-out is a burst. Anthropic's rate limit documentation (opens in a new tab) says a per-minute limit may be enforced over shorter intervals, so short bursts can trigger HTTP 429 errors, which carry a retry-after header. Cap the number of calls in flight with an asyncio.Semaphore (opens in a new tab):

python
gate = asyncio.Semaphore(4)              # at most four calls in flight

async def limited(prompt):
    async with gate:
        return await llm(prompt)

When a branch fails

If one call in a hundred fails, a ten-branch fan-out meets a failure in about one request in ten (1−0.9910=0.0961 - 0.99^{10} = 0.0961−0.9910=0.096). Decide the policy before that happens:

  • Wait for everything and keep failures as values. asyncio.gather (opens in a new tab) with return_exceptions=True returns results in the order the calls were passed, with the exception object in place of each failed one. Use it when partial results are useful.
  • Fail the whole group. asyncio.TaskGroup (Python 3.11 and later) cancels the remaining tasks when one fails. Use it when an incomplete result is worthless.
  • Bound the wait. Wrap each branch in asyncio.wait_for so that a stalled call becomes a TimeoutError and not a hung request.

Then tell the aggregator what a missing branch means. A missing optional section can be left empty. A missing vote shrinks the electorate, so require a quorum. A missing guardrail verdict must count as a block, because a safety check that passes when it fails to run is not a check.

Anthropic's guide calls Orchestrator-Workers topographically similar to parallelization and names the difference: its subtasks are not pre-defined but determined by the orchestrator from the specific input. If you can write the list of branches before seeing any input, you want parallelization.

Frameworks ship the pattern as a primitive. In LangGraph, nodes that fan out from the same node run concurrently in one super-step (opens in a new tab). A state key that several of them update is given a reducer, which combines the updates and does not let the last writer overwrite the rest (the documentation's example uses operator.add), and the super-step is transactional: if one branch raises, none of the updates are applied. Google's ADK has a ParallelAgent (opens in a new tab) whose sub-agents run in separate branches with no automatic sharing of history or state; its documentation notes that from ADK 2.0 for Python and Go, graph-based workflows supersede this template. The OpenAI Agents SDK ships a parallelization example (opens in a new tab) that is plain asyncio.gather followed by an agent that picks the best of three outputs.

Worked example: Triage one support ticket with four parallel sections and a five-vote escalation check

The task: a support ticket arrives, and before any reply is drafted the system needs four independent facts about it (a one-line summary, a category, the order number and the language) and one judgement (should a person review this before the bot replies?). The four facts are sectioning. The judgement is put to five votes.

So that everyone gets the same output, the model is replaced by fake_llm, which waits for a scripted time and returns a scripted reply. Everything else, including the concurrency, is real. Save this as triage_parallel.py. It needs only the Python standard library (3.9 or later).

python
import asyncio
import time
from collections import Counter

TICKET = ("Order 48213 arrived with a cracked screen. This is the second time. "
          "I want a refund today or I will dispute the charge with my bank.")

# name: (instruction, scripted latency in seconds, scripted reply)
SECTIONS = {
    "summary": ("Summarise the ticket in one sentence.", 0.30,
                "Second cracked screen on order 48213; customer wants a refund today."),
    "category": ("Classify as damaged_item, late_delivery, billing or other.", 0.20, "damaged_item"),
    "order_id": ("Return the order number, digits only.", 0.10, "48213"),
    "language": ("Return the ISO 639-1 code of the ticket's language.", 0.40, "en"),
}
VOTE_INSTRUCTION = "Should a person review this ticket before any reply is sent? Answer yes or no."
VOTE_SCRIPT = [(0.25, "yes"), (0.15, "no"), (0.30, "yes"), (0.20, "yes"), (0.10, "no")]


async def fake_llm(prompt, latency, reply):
    """Stands in for one API call. A real client would send `prompt` and return the model's text."""
    await asyncio.sleep(latency)              # the network round trip
    if reply is None:
        raise RuntimeError("529 overloaded")  # a scripted provider failure
    return reply


def section_call(sections, name):
    instruction, latency, reply = sections[name]
    return fake_llm(f"{instruction}\n\nTicket: {TICKET}", latency, reply)


async def one_after_another(sections):
    return {name: await section_call(sections, name) for name in sections}


async def run_sections(sections):
    names = list(sections)
    results = await asyncio.gather(                 # fan out, then wait for every branch
        *(section_call(sections, name) for name in names),
        return_exceptions=True,                     # a failed branch becomes a value
    )
    return {name: None if isinstance(result, Exception) else result   # fan in, fixed order
            for name, result in zip(names, results)}


async def run_votes(script, threshold):
    prompt = f"{VOTE_INSTRUCTION}\n\nTicket: {TICKET}"
    answers = await asyncio.gather(*(fake_llm(prompt, latency, reply) for latency, reply in script))
    counts = Counter(answers)
    return {"votes": dict(counts),
            "agreement": max(counts.values()) / len(answers),
            "escalate": counts["yes"] >= threshold}


async def timed(awaitable):
    start = time.perf_counter()
    result = await awaitable
    return result, time.perf_counter() - start


async def main():
    _, slow = await timed(one_after_another(SECTIONS))
    record, fast = await timed(run_sections(SECTIONS))
    print(f"sections one after another: {slow:.1f} s")
    print(f"sections in parallel:       {fast:.1f} s")
    print(record)

    decision, vote_time = await timed(run_votes(VOTE_SCRIPT, threshold=3))
    print(f"five votes in parallel:     {vote_time:.1f} s")
    print(decision)

    broken = {**SECTIONS, "language": ("Return the language code.", 0.05, None)}  # this branch fails
    print(await run_sections(broken))


if __name__ == "__main__":
    asyncio.run(main())

What to notice:

  • Latency is the slowest branch, not the sum. The four sections take 0.30 + 0.20 + 0.10 + 0.40 = 1.00 s one after another and 0.40 s together, the latency of the language call. The five votes add up to 1.00 s and finish in 0.30 s.
  • The cost did not change. Four section calls and five vote calls were made either way, and every prompt contains the full ticket, so the ticket was sent nine times.
  • The order is fixed by the code. order_id finished first, yet the record lists summary first, because gather returns results in the order the calls were passed. The aggregator never has to work out which reply belongs to which section.
  • The vote was 3 to 2. With threshold=3 the ticket is escalated. With threshold=4 the same votes would not escalate it. Log the agreement of 0.6: a 3-2 split is a weak signal and a 5-0 split a strong one. The self-consistency authors report that the share of samples agreeing with the winning answer is highly correlated with accuracy.
  • One failure did not sink the request. In the last line the language call raised an error. Because of return_exceptions=True the other three sections survive and the record holds None for the missing one. What to do with that None is the aggregator's decision. A missing language code can default to English; a missing guardrail verdict could not default to safe.

If each vote were right 80% of the time and the errors were independent, a majority of five would be right 94.2% of the time by the formula above. Votes from one model on one prompt are not independent, so read that figure as an upper bound.

For a live system, replace fake_llm with a function that sends prompt to a chat model through an async client and returns the reply text. Ask for constrained outputs (a fixed label set, digits only) so that sections can be validated and votes can be counted (see Structured Outputs). The rest of the code stays as it is.

Edge cases and limitations

Branches that look independent but are not
A summary branch and an order-number branch can each be reasonable alone and still contradict each other, for example when a ticket mentions two orders and each branch picks a different one. Parallel branches cannot coordinate, because no branch sees another's output. The sign is an assembled result whose parts disagree on a shared fact. Extract shared facts in one step that runs first and pass them into every branch, or move the dependent steps into a chain.
Free-text votes never match exactly
Counting works for labels and numbers. Two bug reports or two summaries that mean the same thing will almost never be the same string, so a naive count finds no majority. The self-consistency paper says the method applies only when answers come from a fixed answer set, unless a measure of consistency between generations is defined. Cursor's Bugbot added a step that combined similar bugs into buckets before voting. Constrain votes to a fixed label set where you can. Otherwise add an explicit grouping step and test it separately, because the grouping is itself a fallible judgement.
Voters that share a blind spot
Identical calls at temperature zero return near-identical answers, so five votes carry about as much information as one. Even with sampling, one model with one prompt tends to make the same mistake on the same inputs, and a unanimous vote can be confidently wrong. The PoLL paper observed a GPT-4 judge ranking another GPT-4 variant above its true position, a bias that a panel drawn from three model families reduced. Vary something that changes the errors, such as the input order, the prompt wording or the model, and check the vote against labelled examples.
A parallel guardrail that fires too late
When a screening call runs beside the main call, the main call may already have done work by the time the screen says stop. The OpenAI Agents SDK documentation states this for its default parallel mode: if the tripwire triggers, the agent may already have consumed tokens and executed tools before being cancelled. Wasted tokens are an acceptable loss. A tool call that sent an email or issued a refund is not. Run the guardrail in blocking mode whenever the guarded step can act on the outside world.
The burst trips a rate limit and misses the cache
Twenty requests sent in the same instant can be rejected with HTTP 429 even when the per-minute total is inside your limit, because Anthropic documents that a per-minute rate may be enforced over shorter intervals. The same burst gets no prompt-cache discount on the shared prefix, since a cache entry only becomes available after the first response begins. Limit the calls in flight with a semaphore, retry 429 responses after the retry-after interval, and for a large shared prefix send one call first and fan out the rest once it has started responding.
Ties and missing votes
An even number of voters can split evenly, and a failed or timed-out call turns five votes into four. Decide both cases before they happen. Use an odd number of votes, state which side a tie falls on (the cautious side for a safety decision), and set a quorum below which the aggregator returns an explicit undecided status. Never divide by the planned number of votes when fewer arrived: three yes votes out of three is not the same evidence as three out of five.

When to use it, and when something simpler is enough

Use it when

  • The task splits into subtasks that need nothing from each other, and a user is waiting, so cutting latency from the sum of the calls to the slowest call matters.
  • One prompt is being asked to handle several distinct concerns, such as answering and screening, or checking five review criteria, and quality on each improves when it gets its own focused call.
  • A wrong single answer is expensive, answers can be compared mechanically (labels, numbers, pass or fail), and you can afford several attempts to get a vote.
  • You need a confidence signal. The share of votes that agree tells you which cases to send to a person.

Think twice when

  • A step needs another step's output. That is a dependency, and it belongs in a prompt chain.
  • You cannot list the subtasks until you have seen the input, for example which files a code change touches. An orchestrator that plans for each input fits better.
  • A single call is already accurate and fast enough. Every added branch multiplies token cost for a gain you have not measured.
  • Branches take actions with side effects such as sending, writing or paying. Concurrent or cancelled branches can leave the outside world half-changed.
  • You are close to your provider rate limit or on a tight budget, and the fan-out would turn one request into many.

A simpler alternative. One call that returns all the sections in a single structured output, or one low-temperature call followed by a deterministic validator. This stops being enough when the combined prompt is long enough that quality on individual sections drops, when the output takes too long to generate in one piece, or when the measured error rate on a high-stakes decision is still too high after prompt work.

Key takeaways

  • Parallelization sends several LLM calls at once and combines them with a rule your code fixes in advance. Sectioning gives each call a different job, and voting gives every call the same job.
  • Branches must be independent. If one needs another's output, chain them instead.
  • Parallel calls cut latency from the sum of the calls to the slowest call, but every call is still billed, so cost grows with the number of branches.
  • A vote only adds information when the attempts can disagree and do not share their errors, which is why systems vary the sampling, the input order, the prompt or the model.
  • The vote threshold is a policy lever. A low threshold catches more real problems and raises more false alarms, and a high threshold does the reverse.
  • Give every branch a timeout, cap the calls in flight, and decide in advance what the aggregator does when a section or a vote is missing.

Example 1 of 5

Claude Code Review splitting a pull request review across specialised agents

AnthropicDocumented in official docs

Code Review is Anthropic's managed pull request reviewer for GitHub, in research preview for Team and Enterprise plans. The Code Review page of the Claude Code documentation describes how a review runs, and Anthropic's launch article of March 2026 reports how the system performs on Anthropic's own pull requests. [3][4][1]

The problem

A reviewer has to look for several unrelated kinds of defect in one diff: logic errors, security vulnerabilities, broken edge cases and subtle regressions. The launch article says many pull requests were getting skims instead of deep reads, and that before Code Review only 16% of Anthropic's pull requests received substantive review comments. A single automated pass faces two risks, and each maps to a design choice in the documentation. Asked to hunt for everything at once, a model gives each concern less attention, which is the argument in Anthropic's guide for one call per consideration. Allowed to report everything it suspects, it posts false alarms, which is what the documented verification step exists to filter out.

Where this topic fits

The fan-out is the middle of the pipeline. A pull request event triggers the review. Several agents then analyse the diff and the surrounding code in parallel, each responsible for a different class of issue, which is sectioning by concern. Their candidate findings pass to the aggregation stages: a verification step, deduplication, ranking by severity and posting as inline comments.

How it is applied, step by step

  1. A pull request is opened, pushed to, or mentioned with a review command, depending on the trigger configured for the repository.
  2. Several agents start together on Anthropic's infrastructure. Each one analyses the diff and the surrounding code, and each looks for one class of issue.
  3. Each agent produces candidate findings. In a fan-out of this shape, no agent depends on what another agent found.
  4. A verification step checks the candidates against how the code actually behaves and drops the ones it cannot confirm.
  5. The surviving findings are deduplicated, since two agents with different briefs can arrive at the same line, and are ranked by severity.
  6. The result is posted as inline comments on the relevant lines with a summary in the review body, each finding tagged Important, Nit or Pre-existing.

Why this approach fits

The concerns are separable. Whether a change opens a security hole and whether it breaks an edge case are different questions about the same diff, so each agent can do its job without the others' output. Giving each agent one class of issue is the focused-attention argument for sectioning, and starting them together keeps the wall-clock time near that of the slowest agent. The aggregator is where precision is won. Parallel specialists over-report by design, and verification, deduplication and ranking turn many candidates into a short list worth a developer's time.

Limitation or tradeoff

The cost is the sum of every agent's tokens. The documentation gives averages of 15 to 25 US dollars and 20 minutes per review, and the launch article describes the product as more expensive than lighter-weight options. It is also not a purely fixed fan-out: the launch article says large or complex changes get more agents and trivial ones get a lightweight pass, which moves the design towards Orchestrator-Workers. Findings never block a merge, so the pattern supports a human reviewer and does not replace one.

What the sources document

  • When a review runs, multiple agents analyze the diff and surrounding code in parallel on Anthropic infrastructure, and each agent looks for a different class of issue. [3]
  • A verification step checks candidates against actual code behavior to filter out false positives. The results are then deduplicated, ranked by severity and posted as inline comments on the specific lines, with a summary in the review body. [3]
  • The documentation states that reviews complete in 20 minutes on average and that each review averages 15 to 25 US dollars, billed on token usage and scaling with pull request size, codebase complexity and how many issues require verification. [3]
  • Anthropic reports running Code Review on nearly every pull request internally, that the share of pull requests receiving substantive review comments rose from 16% to 54%, and that less than 1% of findings are marked incorrect. [4]
  • The launch article says reviews scale with the pull request: large or complex changes get more agents and a deeper read, and trivial ones get a lightweight pass. [4]

The facts above come from the cited sources. The steps and analysis in this example are our explanation of how they fit together.

Example 2 of 5

OpenAI Agents SDK running an input guardrail concurrently with the main agent

OpenAIDocumented in official docs

The OpenAI Agents SDK for Python lets a developer attach input guardrails to an agent. Its Guardrails documentation describes two execution modes for them, and the API reference documents the run_in_parallel flag that selects the mode. [5][6][1]

The problem

The documentation's scenario is a customer-support agent built on a very capable model that is slow and expensive. Some users will send requests the agent should refuse; the page's example is someone asking it to do their math homework. Screening with the big model wastes its time on requests it should never have seen, and running a separate check before the agent adds the check's latency to every legitimate request.

Where this topic fits

The guardrail is a second, independent branch over the same user input. A fast, cheap model classifies the request while the main agent starts work on it. This is the first sectioning example in Anthropic's guide: one model instance processes the query while another screens it. The aggregation rule is a tripwire. If the guardrail trips, its verdict overrides the main branch and the run ends with an exception. Otherwise the main branch's output is used unchanged.

How it is applied, step by step

  1. The developer writes a guardrail function that runs a small classifier agent on the user's input and returns whether the tripwire was triggered.
  2. The guardrail is attached to the first agent in the chain, because input guardrails run only for that agent.
  3. On each run in the default parallel mode, the runner starts the guardrail and the main agent at the same time on the same input.
  4. If the guardrail finishes without tripping, the main agent's result is returned as usual, and the user did not wait separately for the check.
  5. If the tripwire triggers, the runner raises InputGuardrailTripwireTriggered and halts the agent. The application catches the exception and replies with a refusal.
  6. For an agent whose tools have side effects, the developer sets run_in_parallel to False, so that the guardrail completes before the agent starts.

Why this approach fits

The two branches are independent: the screen does not need the answer, and the answer does not need the screen. Most requests are legitimate, and for those the check's latency disappears, because the answer takes longer than the check. A separate small model also keeps the screening instructions out of the main prompt. Anthropic's guide gives that as the reason this split tends to perform better than one call that handles both the guardrail and the core response.

Limitation or tradeoff

The speed comes from speculative execution: the main agent starts before anyone knows whether it should have. The documentation is explicit that when the tripwire triggers in parallel mode, the agent may already have consumed tokens and executed tools before being cancelled. Tokens are a small loss. A tool call with a side effect cannot be taken back, which is why the blocking mode exists. Output guardrails cannot be run this way at all, because they need the finished output.

What the sources document

  • Input guardrails support two execution modes. In parallel execution, the default (run_in_parallel=True), the guardrail runs concurrently with the agent's execution, which the page says provides the best latency since both start at the same time. [5]
  • The documentation warns that in parallel mode, if the guardrail's tripwire is triggered, the agent may have already consumed tokens and executed tools before being cancelled. [5]
  • In blocking execution (run_in_parallel=False) the guardrail runs and completes before the agent starts, and if the tripwire triggers the agent never executes. The page calls this ideal for cost optimization and for avoiding potential side effects from tool calls. [5]
  • Input guardrails run only for the first agent in the chain. Output guardrails always run after the agent completes, so they do not support the run_in_parallel parameter. [5]
  • The API reference documents the run_in_parallel argument of the input_guardrail decorator as whether to run the guardrail concurrently with the agent, with True as the default. [6]

Self-consistency: a majority vote over sampled reasoning paths

Google ResearchDocumented in a paper

The paper Self-Consistency Improves Chain of Thought Reasoning in Language Models, by Wang and colleagues at Google Research (ICLR 2023), evaluates voting as a decoding strategy on arithmetic and commonsense reasoning benchmarks with four language models. [8]

The problem

Chain-of-thought prompting with greedy decoding produces one reasoning path per question, and a single slip in that path gives a wrong final answer. The authors start from the intuition that a complex reasoning problem typically admits several different ways of thinking that lead to its one correct answer. A single path cannot exploit that.

Where this topic fits

Voting replaces the single call. The same few-shot chain-of-thought prompt is sampled many times, each sample is a separate attempt at the same question, and the aggregator takes the final answer from each sample and returns the most frequent one. The rest of the pipeline is unchanged: there is no extra training, no second model and no verifier.

How it is applied, step by step

  1. Write a few-shot chain-of-thought prompt for the task, exactly as for a single call.
  2. Sample the model's output many times with a non-zero temperature so that the reasoning paths differ. The paper samples 40 outputs per question.
  3. Parse the final answer out of each sampled output. The reasoning text is not compared, only the answers.
  4. Take a majority vote over the parsed answers and return the most frequent one.
  5. Optionally record the share of samples that agree with the winner and treat a low share as a sign that the model is unsure.

Why this approach fits

The answers are short and exact (a number or a choice), so they can be counted without judgement. The attempts differ because sampling takes different reasoning paths, and the paper's comparison with beam search shows why that matters: beam search gave less diverse outputs and smaller gains. The method needs no labelled data, no extra training and no auxiliary model, so it is an inexpensive kind of voting to try.

Limitation or tradeoff

The authors name the cost themselves: more samples mean more computation. They suggest starting with 5 or 10 paths because performance saturates quickly. The method applies only where the final answer comes from a fixed answer set, unless a measure of consistency between free-text outputs is defined. The reported gains are for 2022 models on benchmark questions and should not be assumed for a current model on a different task.

What the sources document

  • The method samples a diverse set of reasoning paths from the model's decoder instead of taking only the greedy one, then takes a majority vote over the final answers; the paper calls the winner the most consistent answer. [8]
  • Results are averaged over 10 runs with 40 outputs sampled independently in each run. Sampling used temperature 0.5 with top-k 40 for UL2-20B and LaMDA-137B, temperature 0.7 with top-k 40 for PaLM-540B, and temperature 0.7 without top-k truncation for GPT-3. [8]
  • On GSM8K, accuracy rose from 60.1 with greedy chain-of-thought to 78.0 with self-consistency on code-davinci-002, and from 56.5 to 74.4 on PaLM-540B, a gain of 17.9 points in both cases. [8]
  • A plain majority vote scored 74.4 on GSM8K with PaLM-540B, very close to the 74.1 obtained by weighting each answer by its normalised probability. [8]
  • The paper states that self-consistency incurs more computation cost, that a small number of paths such as 5 or 10 realises most of the gains, and that it can be applied only to problems where the final answer is from a fixed answer set. [8]

Example 4 of 5

Cursor Bugbot's launch pipeline: eight shuffled passes and a vote filter

CursorDocumented in an engineering article

Bugbot is Cursor's code review agent for pull requests. The article Building a better Bugbot, published on Cursor's blog in January 2026, describes the pipeline the product launched with and how the team later replaced it. [9]

The problem

A model asked to find bugs in a diff reports some that are not real. The article says that with earlier versions of Bugbot the team needed to restrain the models to minimise false positives. The team needed a way to separate likely-real findings from one-off guesses automatically, on every pull request.

Where this topic fits

Voting is the first three steps of the seven-step launch pipeline. Eight bug-finding passes run in parallel over the same diff, their findings are grouped into buckets, and a vote filter decides which buckets survive. The remaining steps are sequential clean-up: merging each bucket into one description, filtering unwanted categories, a validator model and deduplication against earlier runs.

How it is applied, step by step

  1. Run eight bug-finding passes in parallel on the same pull request, giving each pass the diff in a different random order.
  2. Combine similar bugs from the eight outputs into buckets, since two passes rarely describe one bug in the same words.
  3. Apply the vote: filter out every bug that was found during only one pass, and treat agreement between passes as evidence that a bug is real.
  4. Merge each surviving bucket into a single clear description.
  5. Filter out unwanted categories such as compiler warnings and documentation errors, then run the results through a validator model to catch remaining false positives.
  6. Remove bugs already posted by previous runs, and post the rest on the pull request.

Why this approach fits

In code review a wrong comment costs the author time and trust, while a missed bug leaves things no worse than before the tool existed, so a filter that demands agreement suits the economics. Shuffling the diff is a cheap source of diversity. The model and the prompt stay the same, but each pass reads the change in a different order and reasons along a different route. The bet behind the vote is that an invented bug is unlikely to be invented twice, while a real one tends to be found again; the article reports the team treating agreement between passes as a stronger signal, not a measured error rate.

Limitation or tradeoff

Eight passes cost roughly eight times one pass, before the grouping and validation calls. A real but subtle bug that only one pass notices is discarded by design. Grouping free-text reports is itself a judgement that can merge two different bugs or split one. The design also did not last: the article says the largest gains came when Bugbot switched to a fully agentic design that decides where to dig deeper instead of following a fixed sequence of passes. The reported rise in resolution rate from 52% to over 70% spans 40 experiments, including that switch, and cannot be credited to voting.

What the sources document

  • The article says one of the most effective early quality improvements was running multiple bug-finding passes in parallel and combining their results with majority voting. [9]
  • Each pass received a different ordering of the diff, which the author says nudged the model toward different lines of reasoning. When several passes independently flagged the same issue, the team treated it as a stronger signal that the bug was real. [9]
  • The launch flow is listed as seven steps: eight parallel passes with randomized diff order, combine similar bugs into one bucket, majority voting to filter out bugs found during only one pass, merge each bucket into a single description, filter unwanted categories, a validator model, and dedupe against bugs posted from previous runs. [9]
  • The team later switched Bugbot to a fully agentic design, in which the agent reasons over the diff, calls tools and decides where to dig deeper instead of following a fixed sequence of passes, and the article says this produced the largest gains. [9]
  • The article reports that 40 major experiments since launch raised the resolution rate from 52% to over 70%, and that Bugbot reviews more than two million pull requests per month. [9]

Example 5 of 5

PoLL: three different models voting on whether an answer is correct

CohereDocumented in a paper

The paper Replacing Judges with Juries, by Verga and colleagues at Cohere (2024), evaluates a Panel of LLM evaluators, PoLL, as a replacement for a single large judge model when scoring other models' answers on question answering datasets and on Chatbot Arena. [10]

The problem

Automated evaluation often uses one large model to judge whether another model's answer is correct. The authors name three problems with that practice: it is costly, a single judge introduces intra-model bias, and the ranking of the models being evaluated changes drastically depending on which model is chosen as the judge.

Where this topic fits

Voting sits at the scoring step of an evaluation pipeline. For each question and candidate answer, three judge models from different families score the answer independently, and a voting function pools the three scores into the one that is recorded. The diversity comes from using different models, not from sampling one model several times.

How it is applied, step by step

  1. Choose a panel of judges from different model families. The paper uses Command R, Haiku and GPT-3.5.
  2. Give every judge the same question, reference answer and candidate answer, and collect each verdict independently. Nothing prevents the three calls from running at the same time.
  3. Pool the verdicts with a voting function that matches the score type: a max vote for binary correct or incorrect judgements, an average for ratings from 1 to 5.
  4. Record the pooled score as the evaluation result. Keeping the individual verdicts as well makes disagreements between judges easy to inspect.
  5. Validate the panel against human judgements before trusting it. The paper measures agreement with human annotators using Cohen's kappa.

Why this approach fits

A verdict on short-answer correctness is a label, so pooling is mechanical. The errors the authors want to remove are specific to each model family, and that is the situation in which adding voters of different origin does more than adding samples from one model. Because the panel members are small models, three calls cost less than one call to the large judge, an unusual case in which voting lowers the bill.

Limitation or tradeoff

A three-member panel often fails to produce a clear majority on a 1 to 5 scale, which is why the authors switch to averaging there. They state that they investigated only three evaluator settings and a limited number of judges and panel compositions, that further work is needed to see how the method applies to mathematical or reasoning evaluations, and that panel selection is left to future work. The cost advantage rests on 2024 prices and on small models being adequate judges for the task.

What the sources document

  • The panel is built from three models drawn from three different model families: Command R, Haiku and GPT-3.5. Each evaluator scores a model output independently, and the individual scores are pooled through a voting function. [10]
  • For the question answering datasets the authors use max voting because all judgements are binary. For Chatbot Arena they use average pooling, because scores range from 1 to 5 and a three-judge panel often does not produce a clear majority decision. [10]
  • On the KILT Natural Questions set, agreement with human judgements measured by Cohen's kappa was 0.763 for PoLL and 0.627 for GPT-4 as a single judge. [10]
  • On Chatbot Arena Hard the GPT-4 judge ranked another GPT-4 variant in position 2 when its actual position was 4, which the authors present as intra-model bias. They report that pooling judgements across a panel of heterogeneous models reduces this bias. [10]
  • At the prices quoted in the paper, running the entire three-model panel was seven to eight times less expensive than running a single GPT-4 Turbo judge. The authors did not run explicit latency evaluations. [10]

4Common mistakes

  1. Running steps in parallel when one of them needs another's output.

    Why it causes problems
    The dependent branch has to guess what the other branch will say, so the assembled result contains parts that contradict each other, such as a reply drafted for the wrong order number. No aggregator can repair a fact that was never shared.
    How to recognise it
    Sections of one result that disagree on a name, a number or a decision, and branch prompts containing phrases such as "based on the classification" when no classification was passed in.
    How to fix it
    Apply the independence test to every pair of branches. Move shared facts into one extraction step that runs first and feed its output to all branches, or turn the dependent steps into a chain.

  2. Launching every branch at once with no concurrency cap and no per-call timeout.

    Why it causes problems
    The burst is rejected with rate-limit errors, or one stalled call holds the whole request open. The pattern that was added for speed then makes the slowest requests slower than a chain would.
    How to recognise it
    HTTP 429 responses clustered at the start of each request, and a latency distribution whose median improved while its worst cases got worse.
    How to fix it
    Put a semaphore around the calls, wrap each call in a timeout, retry rate-limit responses after the interval the provider states, and size the fan-out from your limits, not from the number of subtasks.

  3. Treating a failed branch as if it had nothing to report.

    Why it causes problems
    A guardrail that timed out is read as no objection and unsafe input goes through, or a missing vote is silently counted as a no. The system fails open exactly when the provider is under stress.
    How to recognise it
    Aggregation code that filters out errors before counting, and decision records that never say how many branches actually answered.
    How to fix it
    Represent a failed branch as an explicit value, require a quorum of valid votes, make safety checks fail closed, and return an undecided status when too little came back.

  4. Sending the same prompt several times at temperature zero and calling the agreement a vote.

    Why it causes problems
    Near-identical calls return near-identical answers, so the system pays several times for one opinion and reports unanimous confidence on answers that are wrong.
    How to recognise it
    Votes that are unanimous on almost every input, including inputs that your labelled test set says were answered wrongly.
    How to fix it
    Change something that changes the errors: sample with a non-zero temperature, reorder the input, reword the prompt or use different models. Then measure on labelled data whether the vote beats a single call.

  5. Counting free-text answers by exact string match.

    Why it causes problems
    Two answers that mean the same thing are counted as different votes, so real agreement is missed and the result is a spurious tie or an arbitrary winner.
    How to recognise it
    Vote tallies in which nearly every answer has a count of one, even though the answers read alike.
    How to fix it
    Constrain each vote to a fixed label set or a normalised value with structured output, or add an explicit grouping step before counting, as Bugbot's launch pipeline did, and test that step on its own.

  6. Judging the design by latency alone and ignoring the token bill.

    Why it causes problems
    Every branch resends the shared context, so a four-branch fan-out over a long document costs close to four times one call, and a simultaneous burst gets no cache discount. The feature ships and the bill arrives later.
    How to recognise it
    Input tokens per request that are a multiple of the document size, and cache-read counts near zero on the fan-out calls.
    How to fix it
    Estimate tokens per request before building, send each branch only the slice of context it needs, and for a large shared prefix warm the cache with one call before fanning out the rest.

Exercise 1

Build a bounded fan-out with timeouts and a quorum vote

CodingIntermediateAbout 45 min (estimate)Hypothetical scenario

A moderation service asks seven differently worded prompts whether a product review breaks the site's policy. Each prompt answers flag or allow. The provider is having a bad minute: one call hangs and one fails. Start from this file, which scripts the seven calls so that your output is reproducible:

python
import asyncio

# (latency in seconds, reply). A reply of None means the provider returns an error.
SCRIPT = [(0.10, "flag"), (0.20, "allow"), (2.00, "flag"), (0.10, "flag"),
          (0.15, None), (0.10, "allow"), (0.20, "flag")]

Write async def moderate(script, max_concurrent=3, timeout=0.5, threshold=3, quorum=5) that runs all the calls and returns a decision. You need only the Python standard library (3.11 or later, because the solution catches the built-in TimeoutError).

Requirements

  • Never have more than max_concurrent calls in flight at the same time.
  • Give each call its own timeout, measured from the moment the call starts and not from the moment it began waiting for a free slot.
  • A call that times out or raises must not stop the other calls. Record it as a failed vote.
  • If fewer than quorum valid votes came back, return the decision needs_review. Otherwise return flag when at least threshold valid votes say flag, and allow when they do not.
  • Return a dictionary with the decision, the number of flag votes, the number of allow votes, the number of failed calls, and the largest number of calls that were in flight together.

Expected behaviour

moderate(SCRIPT) returns {'decision': 'flag', 'flag': 3, 'allow': 2, 'failed': 2, 'peak_in_flight': 3}. Five valid votes meet the quorum of 5, and three flags meet the threshold of 3.

moderate(SCRIPT, quorum=6) returns the same counts with the decision needs_review.

moderate(SCRIPT, max_concurrent=7, threshold=4) returns the decision allow with peak_in_flight equal to 7.

Hint 1

An asyncio.Semaphore used with async with lets a fixed number of coroutines into a block at once. Put the timeout inside that block.

Hint 2

asyncio.wait_for raises TimeoutError when the time is up. Catch it, together with the provider's RuntimeError, inside the function that makes one call.

Hint 3

To measure the peak, have each call return its start and end times, then count how many of those intervals overlap.

Show solution

Save this as moderate.py.

python
import asyncio
import time
from collections import Counter
from itertools import accumulate

# Seven differently worded prompts ask the same question. Scripted (latency, reply) per call.
SCRIPT = [(0.10, "flag"), (0.20, "allow"), (2.00, "flag"), (0.10, "flag"),
          (0.15, None), (0.10, "allow"), (0.20, "flag")]


async def fake_llm(latency, reply):
    await asyncio.sleep(latency)
    if reply is None:
        raise RuntimeError("529 overloaded")
    return reply


def peak_in_flight(spans):
    """Largest number of (start, end) spans that overlap at any moment."""
    changes = sorted([(start, 1) for start, _ in spans] + [(end, -1) for _, end in spans])
    return max(accumulate(change for _, change in changes))


async def moderate(script, max_concurrent=3, timeout=0.5, threshold=3, quorum=5):
    gate = asyncio.Semaphore(max_concurrent)

    async def guarded(latency, reply):
        async with gate:                               # wait here for a free slot
            started = time.perf_counter()              # the timeout clock starts after the wait
            try:
                answer = await asyncio.wait_for(fake_llm(latency, reply), timeout)
            except (TimeoutError, RuntimeError):       # one bad branch must not sink the rest
                answer = None
            return answer, started, time.perf_counter()

    outcomes = await asyncio.gather(*(guarded(latency, reply) for latency, reply in script))
    valid = [answer for answer, _, _ in outcomes if answer is not None]
    counts = Counter(valid)
    if len(valid) < quorum:
        decision = "needs_review"
    elif counts["flag"] >= threshold:
        decision = "flag"
    else:
        decision = "allow"
    return {"decision": decision, "flag": counts["flag"], "allow": counts["allow"],
            "failed": len(outcomes) - len(valid),
            "peak_in_flight": peak_in_flight([(start, end) for _, start, end in outcomes])}


if __name__ == "__main__":
    print(asyncio.run(moderate(SCRIPT)))
    print(asyncio.run(moderate(SCRIPT, quorum=6)))
    print(asyncio.run(moderate(SCRIPT, max_concurrent=7, threshold=4)))

Running python3 moderate.py prints:

text
{'decision': 'flag', 'flag': 3, 'allow': 2, 'failed': 2, 'peak_in_flight': 3}
{'decision': 'needs_review', 'flag': 3, 'allow': 2, 'failed': 2, 'peak_in_flight': 3}
{'decision': 'allow', 'flag': 3, 'allow': 2, 'failed': 2, 'peak_in_flight': 7}

Why it is built this way:

  • The semaphore is the concurrency cap. gather starts all seven coroutines at once, but only three can be inside the async with gate block. The others wait at its entrance, which is why the measured peak is 3.
  • The timeout sits inside the gate. A call that waited 0.3 s for a slot still gets its full 0.5 s. With the timeout outside, queueing time would be charged to the call, and a healthy call late in the queue could be cancelled before it had run for long.
  • Failures become values. The third call (2.0 s) hits the timeout and the fifth raises. Both are recorded as None inside guarded, so gather never sees an exception and the other five votes are kept.
  • The quorum is checked before the threshold. With five valid votes, three flags are a majority. With quorum=6 the same five votes are not enough evidence to decide, so the function says so and does not guess.
  • The threshold is policy. The third run changes only threshold (and lifts the cap), and the same votes produce allow. Sort order makes peak_in_flight safe at instants where one call ends and another starts: the tuple (t, -1) sorts before (t, 1).

A much larger share than that in the tallies, with few reviews in the middle at three or four flags, is the sign of correlated errors.

Two changes that address it:

  • Make the votes differ. Use prompts that each look for a different kind of violation, reorder or rephrase the input, or use models from different families, so that the reviews one voter misses are not the ones every voter misses.
  • Improve the single call and route by agreement. Voting amplifies base accuracy and cannot create it, so add examples of the missed kinds to the prompt. Send split votes, such as three or four flags out of seven, to a human reviewer and do not force a decision.

Then measure again on the labelled set. The binomial figures are a best case and the test set is the evidence.

Check your answer

  • Did you get 0.86% and 5.79% for five votes with a threshold of three?
  • Did you get 0.27% and 3.33% for seven votes with a threshold of four?
  • Is your daily cost for seven calls 1,400 US dollars, seven times the single-call cost?
  • Does your answer to part 4 name correlated errors and describe what the vote tallies would look like?
