LangGraph

LangGraph is an open-source library for building agents and workflows as a graph. Functions called nodes read and update one shared state, edges decide which node runs next, and the runtime can save the state after every step so that a run can pause, resume, recover from a crash and stream its progress.

1Overview

Why it matters

A hand-written agent loop works until the process dies halfway through a twenty-minute task, a manager has to approve a refund tomorrow, or a user wants to watch progress instead of a spinner. Each of those needs the same thing: the program's state saved at known points, outside the process, in a form that can be reloaded. LangGraph is a runtime built around that idea. You describe the control flow as a graph, and it gives you checkpoints, pause-and-resume, streaming and a record of every step.

It is also a library you will meet whether or not you choose it. LangChain's create_agent, the Deep Agents SDK and Google Cloud's LanggraphAgent template all run on it, and engineering teams at Uber and GitLab have published designs that depend on its routing and its checkpoints. To debug those systems you need to know what a super-step is, what a thread is, and which code runs again after a pause. Without that, the usual failures look mysterious: a payment made twice after an approval, a list that lost its history, a conversation that forgot everything after a restart.

What you will be able to do

  • Add a checkpointer and a thread id, then inspect a thread with get_state and get_state_history.
  • Pause a run with interrupt, resume it with Command(resume=...), and explain which code runs twice.
  • Choose a stream mode that fits what a user interface needs to show.
  • Decide when the prebuilt create_agent is enough and when to write the graph yourself.

Key terms

State
The single shared data structure of a graph run, usually a typed dictionary. Every node reads it, and every node's output is merged into it.
Node
A function that receives the current state and returns a partial update, meaning only the keys it wants to change.
Edge
A rule that says which node runs after another. A normal edge is fixed and a conditional edge is chosen at run time.
Reducer
A function attached to one state key that combines the stored value with a node's update. Without one, the update replaces the stored value.
Conditional edge
An edge whose target is picked by a routing function that reads the state after a node has run.
Super-step
One tick of graph execution. All nodes scheduled for that tick run, possibly in parallel, and their updates are applied together.
Checkpointer
A storage component that saves a snapshot of the state at every super-step, in memory or in a database such as SQLite or PostgreSQL.
Thread
The saved history of one conversation or job, identified by a thread id that you pass on every call.
Interrupt
A pause requested from inside a node. The state is saved and the run continues only when the caller sends a resume value.
Stream mode
The kind of event a graph emits while it runs, such as full state, per-node updates, model tokens or custom data.

2Explanation

Introduction

In The Agent Loop you wrote an agent as a while loop: call the model, run the tool it asks for, append the result, repeat. In Choosing an Agent Framework you saw that frameworks differ mainly in how much of that loop they hide. LangGraph hides very little. Its documentation (opens in a new tab) calls it a low-level orchestration framework and runtime for long-running, stateful agents, and says that it does not abstract prompts or architecture.

What changes is the shape of the program. In place of one loop with if statements inside it, you write small functions and connect them:

  • State is one shared data structure, usually a typed dictionary, that holds everything the run knows.
  • Nodes are ordinary Python functions. Each receives the current state and returns only the keys it wants to change.
  • Edges say which node runs next. A normal edge always leads to the same node. A conditional edge calls a function that reads the state and picks.

The documentation's own summary is that nodes do the work and edges tell what to do next. Here is the agent loop from the earlier lesson, redrawn that way:

Think of a paper form moving through an office. The form is the state. Each desk (a node) reads it, fills in one box and passes it on. A routing slip (an edge) names the next desk, and sometimes the next desk depends on what was just written. Now add one rule: every time the form leaves a desk, the office photocopies it and files the copy under the case number. With that filing cabinet you can stop for the night, hand the case to a colleague, look up what the form said three desks ago, or wait a week for a signature. In LangGraph the cabinet is a checkpointer and the case number is a thread id.

This lesson uses LangGraph 1.2 for Python (pip install -U langgraph, Python 3.10 or later). The library is MIT-licensed, is built by LangChain Inc, and can be used without LangChain. The lesson covers state graphs, conditional routing, checkpointers and persistence, interrupts for human approval, streaming, and the prebuilt agent that most people start with.

How it works

State and reducers

The state schema is usually a TypedDict. A node does not return the whole state. It returns a partial update, and LangGraph merges that update key by key with a reducer: a function that takes the stored value and the new value and returns what to store.

python
import operator
from typing import Annotated
from typing_extensions import TypedDict

class State(TypedDict):
    total: float                              # no reducer: an update replaces the value
    log: Annotated[list[str], operator.add]   # reducer: an update is added to the list

If the state is {"total": 1.0, "log": ["a"]} and a node returns {"log": ["b"]}, the new state is {"total": 1.0, "log": ["a", "b"]}. Without the annotation, log would become ["b"]. For chat history use the built-in add_messages reducer or the ready-made MessagesState. It appends new messages and replaces a message whose id already exists.

Nodes, edges and compiling

python
from langgraph.graph import END, START, StateGraph

def add_fee(state: State):                # a node: state in, partial update out
    return {"total": state["total"] + 2.5, "log": ["fee added"]}

builder = StateGraph(State)
builder.add_node("add_fee", add_fee)
builder.add_edge(START, "add_fee")        # START marks where the input enters
builder.add_edge("add_fee", END)          # END marks that nothing follows
graph = builder.compile()                 # checks the structure; required before use
print(graph.invoke({"total": 10.0, "log": ["start"]}))
# {'total': 12.5, 'log': ['start', 'fee added']}

START and END are virtual nodes. compile() is also where you attach a checkpointer.

Super-steps: how a run executes

The execution model (opens in a new tab) is borrowed from Google's Pregel system. A run proceeds in discrete super-steps. In each one, every node that received new state runs, and their updates are applied together. Nodes in a sequence are in separate super-steps. Nodes that fan out from the same node share a super-step and run in parallel. Three consequences:

  • Two parallel nodes that write the same key need a reducer on that key. Without one LangGraph raises an error (INVALID_CONCURRENT_GRAPH_UPDATE), because it cannot tell which value should win.
  • A super-step is transactional. If one parallel branch raises, none of that step's updates are applied.
  • The recursion_limit config key caps the super-steps in one run, and GraphRecursionError is raised when it is exceeded. The default has been 1000 since version 1.0.6, so set your own: graph.invoke(inputs, {"recursion_limit": 25}).

Conditional routing

A conditional edge runs a routing function after a node and uses the return value as the name of the next node, or a list of names. This one is from the worked example below:

python
from typing import Literal

def route(state: State) -> Literal["auto_approve", "ask_manager"]:
    return "auto_approve" if state["total"] <= 100 else "ask_manager"

builder.add_conditional_edges("add_up", route)

A loop is a conditional edge that points back to an earlier node and returns END when a stopping condition holds. Two related tools:

  • Command(update={...}, goto="node"), returned from a node, updates state and routes in one place. Annotate the return type, for example Command[Literal["node"]], so the graph knows the possible targets.
  • Send("node", {...}), returned in a list from a routing function, starts one copy of a node per item, each with its own input. This is how map-reduce is built when the number of branches is known only at run time.

Give each node one routing mechanism. If a node has both a normal edge and a Command(goto=...), both targets run.

Checkpointers and persistence

Compile with a checkpointer and pass a thread id on every call:

python
from langgraph.checkpoint.memory import InMemorySaver

graph = builder.compile(checkpointer=InMemorySaver())
config = {"configurable": {"thread_id": "claim-1"}}
graph.invoke({"total": 10.0, "log": []}, config)

The checkpointer (opens in a new tab) saves a snapshot of the state at every super-step boundary, filed under the thread id. That one mechanism provides four things:

  • Memory. A second invoke with the same thread id continues from the saved state. A new id starts empty.
  • Fault tolerance. After a failure you can restart the run from the last completed super-step. Nodes that finished inside the failed step are not run again, because their writes were stored as they completed.
  • Inspection and time travel. graph.get_state(config) returns the latest StateSnapshot (values, next, metadata and more) and graph.get_state_history(config) returns all of them, newest first. Invoking with an older checkpoint_id replays from that point, and update_state forks it with edited values.
  • Human-in-the-loop, covered in the next section.

InMemorySaver loses everything when the process exits. SqliteSaver (package langgraph-checkpoint-sqlite) suits local work, and PostgresSaver (langgraph-checkpoint-postgres) is what the documentation suggests for production. A checkpointer is scoped to one thread. Facts that must outlive a thread, such as user preferences, belong in a separate store (see Agent Memory).

Checkpoints are not free. By default each one writes the full value of every state channel, so a thread whose message list grows by one message per step has stored 1+2+⋯+n=n(n+1)/21 + 2 + \dots + n = n(n+1)/21+2+⋯+n=n(n+1)/2 message copies after nnn steps if every checkpoint is kept.

Plan a retention policy, keep large objects out of the state, and look at DeltaChannel (beta, version 1.2 or later), which stores only what each step added.

Interrupts

Calling interrupt(payload) (opens in a new tab) inside a node pauses the run. The state is saved and the caller receives the payload under the __interrupt__ key of the result. With a database checkpointer the process does not have to stay alive while it waits. To continue, invoke the graph again on the same thread with Command(resume=value). The value becomes the return value of the interrupt() call. Again from the worked example:

python
from langgraph.types import Command, interrupt

def ask_manager(state: State):
    approved = interrupt({"question": "Approve?", "total": state["total"]})
    return {"status": "approved" if approved else "rejected"}

graph.invoke(Command(resume=True), config)   # later, with the same thread id

The mechanism explains the rules. interrupt pauses by raising a special exception that the runtime catches, and on resume the node starts again from its first line:

  • Code before the interrupt call runs twice, so it must be idempotent (safe to repeat). Put side effects after the call or in a later node.
  • A bare try/except Exception around the call swallows the pause.
  • With several interrupts in one node, resume values are matched by position, so the order of the calls must not change between runs.
  • Payloads should be JSON-serialisable.

Interrupts need a checkpointer and a thread id. The interrupt_before and interrupt_after arguments of compile() are static breakpoints meant for debugging, not for approvals. Human-in-the-Loop covers the design side.

Streaming

graph.stream() yields events while the run is in progress. The stream_mode argument chooses what you receive, and you can pass several modes in a list.

With version="v2" (LangGraph 1.1 or later) every item is a dict with type, ns and data, whatever the mode. Version 1.2 added event streaming, which the streaming guide (opens in a new tab) recommends for new applications: graph.stream_events(inputs, version="v3") returns one object with separate projections such as stream.messages and stream.values, plus stream.interrupts for a pending pause.

Prebuilt agents

Most agents are the same small graph: a model node, a tool node and a conditional edge that loops until the model stops asking for tools. LangGraph's quickstart builds it by hand with two nodes and one conditional edge. The prebuilt version is create_agent (opens in a new tab) in the langchain package, which runs on LangGraph:

python
from langchain.agents import create_agent
from langchain.tools import tool
from langgraph.checkpoint.memory import InMemorySaver

@tool
def get_order_status(order_id: str) -> str:
    """Look up the shipping status of an order."""
    return f"Order {order_id} shipped yesterday."

agent = create_agent(
    model="anthropic:claude-sonnet-5",     # any provider:model string you have access to
    tools=[get_order_status],
    system_prompt="Answer order questions briefly.",
    checkpointer=InMemorySaver(),
)
config = {"configurable": {"thread_id": "customer-42"}}
agent.invoke({"messages": [{"role": "user", "content": "Where is order A-17?"}]}, config)

Thread ids, checkpointers and streaming work on it as described above. You customise it with middleware, for example HumanInTheLoopMiddleware to require approval before named tools run.

A version note: tutorials written before LangGraph 1.0 import create_react_agent from langgraph.prebuilt. Version 1 deprecated it in favour of create_agent. ToolNode and tools_condition are still in langgraph.prebuilt for hand-built graphs. Start with the prebuilt agent, and write your own graph when you need fixed steps before or after the loop, parallel branches, or routing that the model should not control.

Worked example: An expense-claim graph that approves small claims by itself and pauses large ones for a manager

The rule: add up the items on a claim. A total of 100 or less is approved automatically. Anything larger waits for a manager. Either way a notification step runs last. No model is involved, so everyone gets the same output. Install with pip install -U langgraph (this was written against version 1.2) and save the code as claims.py.

python
import operator
from typing import Annotated, Literal

from typing_extensions import TypedDict
from langgraph.checkpoint.memory import InMemorySaver
from langgraph.graph import END, START, StateGraph
from langgraph.types import Command, interrupt

AUTO_APPROVE_LIMIT = 100.0


class State(TypedDict):
    items: list[float]
    total: float
    status: str
    log: Annotated[list[str], operator.add]   # reducer: append


def add_up(state: State):
    total = round(sum(state["items"]), 2)
    return {"total": total, "log": [f"add_up: total={total}"]}


def route(state: State) -> Literal["auto_approve", "ask_manager"]:
    return "auto_approve" if state["total"] <= AUTO_APPROVE_LIMIT else "ask_manager"


def auto_approve(state: State):
    return {"status": "approved", "log": ["auto_approve: under the limit"]}


def ask_manager(state: State):
    print(f"ask_manager: asking about {state['total']}")
    approved = interrupt({"question": "Approve this claim?", "total": state["total"]})
    status = "approved" if approved else "rejected"
    return {"status": status, "log": [f"ask_manager: manager said {approved}"]}


def notify(state: State):
    return {"log": [f"notify: claim {state['status']}"]}


builder = StateGraph(State)
builder.add_node("add_up", add_up)
builder.add_node("auto_approve", auto_approve)
builder.add_node("ask_manager", ask_manager)
builder.add_node("notify", notify)
builder.add_edge(START, "add_up")
builder.add_conditional_edges("add_up", route)
builder.add_edge("auto_approve", "notify")
builder.add_edge("ask_manager", "notify")
builder.add_edge("notify", END)
graph = builder.compile(checkpointer=InMemorySaver())

# Run 1: a small claim, streamed, then its checkpoints oldest first
small = {"configurable": {"thread_id": "claim-1"}}
for part in graph.stream({"items": [12.5, 30.0, 41.25]}, small, stream_mode="updates", version="v2"):
    print(part["data"])
for snapshot in reversed(list(graph.get_state_history(small))):
    print(snapshot.metadata["step"], snapshot.next)

# Run 2: a large claim pauses for a person
large = {"configurable": {"thread_id": "claim-2"}}
paused = graph.invoke({"items": [80.0, 45.5, 19.99]}, large)
print(paused["__interrupt__"][0].value)
print(graph.get_state(large).next)

final = graph.invoke(Command(resume=True), large)
print(final["status"], final["log"])

Run 1. 12.5 + 30.0 + 41.25 = 83.75, which is under 100, so route returns "auto_approve". The updates stream shows one item per node, containing only the keys that node returned. The history shows five checkpoints: an empty one before the input (step -1), the input (step 0), and one after each of the three nodes. next is the node about to run, and the empty tuple on the last line means the run is complete.

Run 2. 80.0 + 45.5 + 19.99 = 145.49, so route returns "ask_manager". That node calls interrupt, and invoke returns early with the payload under __interrupt__. get_state(...).next confirms the thread is parked in front of ask_manager.

Three things to take from the second run:

  • The node ran twice. ask_manager: asking about 145.49 is printed once before the pause and once after the resume, because a resumed node restarts from its first line. If that line had sent an email, the manager would have received two.
  • The reducer kept the history. Three nodes each returned a one-item log, and the final log has all three entries in order. Remove the Annotated[..., operator.add] and it would hold only 'notify: claim approved'.
  • Threads are separate. claim-1 and claim-2 never see each other's state. Swap InMemorySaver for a database checkpointer and the resume call could come days later from a different process, as long as it uses the thread id claim-2.

Edge cases and limitations

A subgraph's interrupt restarts the parent node as well
When a node calls another graph as a function and that subgraph calls interrupt, resuming runs the parent node again from its first line and also restarts the subgraph node that paused. Code placed before the subgraph call therefore runs twice, exactly like code before a direct interrupt. Keep such nodes free of side effects before the call, or move the side effects into a later node.
An empty update does not clear a key that has a reducer
With an appending reducer, returning an empty list merges nothing in and the old values stay. The documentation uses an errors list as its example: one node returns an error, the next returns an empty list, and the error is still in the state. To reset the key, return the new value wrapped in Overwrite from langgraph.types, which bypasses the reducer for that one update.
Branches of different lengths can run the join node more than once
If two branches lead to the same node through separate edges and one branch has an extra step, the join node runs once in every super-step in which a branch finishes. Use a list-form edge, for example add_edge(["b_2", "c"], "d"), which runs d once after all listed nodes complete, or add the node with defer=True. With the list form, if one listed branch never runs, d never runs and no error is raised.
Private state keys are visible in a stream
Input, output and private schemas limit what a node reads and what invoke returns. They do not hide anything from a stream. In values mode the graph emits all state channels, including private ones. If a stream reaches end users, pass output_keys to restrict it to the keys you intend to show, or use updates mode and filter the items yourself.
A paused thread limits how you can change the graph
The documentation states that for threads that have finished you may change the whole topology, but for threads that are currently interrupted every change is supported except renaming or removing nodes, because the thread may be about to enter one of them. State keys that are renamed lose their saved values in existing threads. Before deploying a change, check whether paused threads exist.
Passing Command(update=...) as input makes a finished thread look stuck
Any Command given to invoke resumes from the latest checkpoint. It does not start from the beginning. On a thread that has already finished, nothing runs, so the graph appears stuck. Command(resume=...) is the only form intended as input. To continue a conversation, pass a plain input dictionary with the same thread id.

When to use it, and when something simpler is enough

Use it when

  • The control flow mixes fixed, hand-coded steps with model-driven steps, and you need to state exactly which decisions the model is allowed to make.
  • A run has to survive a restart or wait for a person, as in long tasks, approvals and conversations that continue over days.
  • You need to inspect, replay or edit intermediate state to debug a run or to audit what an agent did.
  • Independent pieces of work should run in parallel and be merged, including a number of branches that is known only at run time.

Think twice when

  • One model call or a fixed two-step chain does the job. A graph adds a state schema, a compile step and new failure modes for no benefit.
  • You need a standard tool-calling agent with no custom control flow. Use the prebuilt create_agent, which still runs on LangGraph, and do not write a graph.
  • Nobody will operate a checkpoint database. Without a durable checkpointer you lose memory across restarts, interrupts and crash recovery, which are the main reasons to choose the library.
  • Your organisation already runs a durable workflow engine and wants agents inside it. LangChain's own comparison page lists Temporal and Inngest as other runtimes in the same category.

A simpler alternative. A plain Python loop over a list of messages, as in The Agent Loop lesson, or the prebuilt create_agent when you want that loop without writing it. These stop being enough when the run must outlive the process, pause for a person at a specific step, or guarantee that certain steps always happen in a fixed order around the model. At that point you are rebuilding checkpoints and routing by hand, and LangGraph is less code.

Key takeaways

  • A LangGraph program is one shared state, node functions that return partial updates, and edges that choose the next node, with a reducer on each key deciding how an update is merged.
  • A run advances in super-steps, parallel nodes share one, and any key written by two nodes in the same super-step needs a reducer.
  • A checkpointer saves the state at every super-step under a thread id, and that single mechanism provides memory, crash recovery, state history and pause-and-resume.
  • An interrupt pauses by raising inside a node, and the node restarts from its first line on resume, so everything before the call must be safe to run twice.
  • Stream modes choose what you see while a run is in progress: the full state, per-node updates, model tokens or custom data.
  • Start with the prebuilt create_agent, and write your own graph when you need fixed steps, parallel branches or routing that the model should not control.

Example 1 of 5

Uber Finch: a supervisor that routes finance questions and reports progress in Slack

UberDocumented in an engineering article

Uber's engineering blog post Unlocking Financial Insights with Finch (July 2025) describes Finch, an AI agent inside Slack that lets Uber's finance teams ask for financial data in plain language. The post names LangGraph as the tool used to construct and orchestrate its agents. [16][7]

The problem

Before Finch, the post says, an analyst who needed a number had to log into several platforms and either write the SQL personally or send a request to the data science team and wait hours or days. A chat agent that answers such questions has to do different jobs for different questions: some need a query written against the right table, others need a document read. The work also takes long enough that a silent wait in Slack would look like a failure.

Where this topic fits

LangGraph is the orchestration layer between Slack and the specialised agents. A Supervisor Agent receives each question and passes it to a sub-agent chosen by the nature of the question, such as the SQL Writer Agent. In LangGraph terms that is conditional routing. While the graph runs, a callback handler in the LangGraph application updates a Slack status message, which is the streaming side of the design. Model access and metadata search sit behind the nodes.

How it is applied, step by step

  1. A finance user asks a question in Slack, and the application starts a graph run with the question as input.
  2. The supervisor node reads the question and decides which sub-agent should handle it. A typical LangGraph implementation writes that choice into the state and lets a conditional edge select the next node, or returns a Command from the supervisor node.
  3. For a data question the SQL Writer Agent looks up table and column metadata, which the post says is held in an OpenSearch index together with natural-language aliases, and writes a query.
  4. If the query fails, the agent rewrites it using the error message. In a graph this is a loop: a conditional edge that returns to the writing step until the query runs or a limit is reached.
  5. As each stage starts, a callback handler pushes a short status to Slack so the user can see what the agent is doing. The built-in equivalent in current LangGraph is the custom stream mode shown below.
  6. The final step posts a structured answer in Slack. Offline, the team evaluates each sub-agent and the supervisor's routing separately.

Why this approach fits

Routing and progress reporting are properties of the control flow, not of any one prompt. Putting the supervisor's decision on an explicit edge means each sub-agent can be developed and evaluated alone, which matches how Uber says it tests Finch: every sub-agent against expected responses, and the supervisor's routing accuracy as its own measurement. Because the runtime knows which node is running, status updates come from one place and are not scattered through the business logic.

Limitation or tradeoff

A supervisor is a single point of misrouting. The post names intent collisions, where the supervisor makes the wrong choice on an ambiguous question, as the problem its routing evaluation is designed to find. The authors also state that Finch is not 100% reliable and is prone to hallucination, and they plan a Request validation button that sends an answer to a subject matter expert. The graph structures the work but does not make the generated SQL correct. The post gives no latency or accuracy figures, so the benefit cannot be quantified from it.

What the sources document

  • The post states that the team uses LangChain's LangGraph to construct and orchestrate Finch's agents. [16]
  • A Supervisor Agent receives the query and sends it to an appropriate sub-agent, such as the SQL Writer Agent, and the agents are selected based on the nature of the query. [16]
  • A dedicated callback handler in the LangGraph application updates Slack status messages in real time so that users can track what the agent is doing at every stage of the query process. [16]
  • Evaluation is described at several levels: each sub-agent is evaluated independently against expected responses, supervisor routing accuracy is measured to find intent collisions, and historical queries are re-run as regression tests before updates are deployed. [16]
  • LangGraph's streaming guide says the custom stream mode delivers data that a node or tool emits with get_stream_writer to the caller of stream. [7]

The facts above come from the cited sources. The steps and analysis in this example are our explanation of how they fit together.

Example 2 of 5

GitLab Duo Workflow: LangGraph checkpoints stored in GitLab, with a pause for tool approval

GitLabDocumented in official docs

GitLab's public handbook contains the architecture design document for GitLab Duo Workflow (created in May 2024, status ongoing), the service behind GitLab's agentic coding workflows in the editor and in CI. The document states that the Workflow service is built on top of LangGraph and describes how its state is checkpointed. [17][4][5]

The problem

The agent executes commands and edits files, so that part runs in a separate executor, in the user's editor or in a CI pipeline, while a Python service plans the work. The design document sets hard constraints on that service: it has no storage of its own, its in-memory state can be lost at any time, and two instances must never run the same workflow. On top of that, some tool calls have to wait for the user to approve, deny or correct them, and the user may take a long time.

Where this topic fits

LangGraph runs the workflow graph inside the Workflow service. Its state object, which includes the prompt history between user and agents, is persisted through GitLab's own APIs into PostgreSQL as checkpoints, so GitLab itself is the checkpoint store. A tool approval subgraph sits between the agent node, which produces the model's function calls, and the ToolExecutor node, which runs them. When approval is needed the workflow is saved and hibernated, the same pause-and-resume pattern that interrupt provides.

How it is applied, step by step

  1. Before running, the service acquires a lock for the workflow from GitLab, so that only one instance drives a given workflow.
  2. The LangGraph graph runs. An agent node asks the model for the next function calls, and a ToolExecutor node carries them out through the executor.
  3. While the graph runs, the service saves LangGraph checkpoints through GitLab's API into PostgreSQL, and the executor pushes a hidden Git ref with the code written so far, so state and files can be restored together.
  4. Before the ToolExecutor node runs, the pending function calls are compared with an allow list of pre-approved privileges. If any call is not on the list, the tool approval subgraph is entered.
  5. At the approval verification node the workflow is hibernated. The state is checkpointed and the workflow waits in a status that signals that input is required.
  6. When the user approves, the executor is restarted and the workflow resumes from the checkpoint. A denial or written feedback routes back to the agent node so that it can change course.
  7. Clients do not read raw checkpoints. A separate API field exposes only the messages the interface needs.

Why this approach fits

The service was designed to be disposable, and a checkpoint per step is what makes a disposable process safe: any instance can load the last checkpoint and continue. Because a checkpointer is an interface, GitLab could put the storage where its permissions, tenant isolation and backups already are, in its own database, and avoid operating a new one. Approval then needs no special machinery. A pause is a saved checkpoint and a resume is a load.

Limitation or tradeoff

Checkpoints are an internal format. The design document says they were exposed directly to clients early on to allow quicker iteration, and that a dedicated duo_messages field later replaced the deprecated checkpoint field to give clients a proper contract and smaller payloads. Storage also grows: the document plans retention limits, using PostgreSQL partitioning to drop old workflow data. And a checkpoint is only the last guaranteed point. Work done after it is lost if the service dies, and the node that was running is executed again on resume.

What the sources document

  • The Duo Workflow Service is described as a Python service built on top of LangGraph, and the Workflow service uses LangGraph internally to execute workflows. [17]
  • The service has no persisted state of its own. The state of running workflows is kept in memory and periodically checkpointed in GitLab, and because the in-memory state can be lost at any time, a checkpoint is the only guaranteed point that can be returned to. [17]
  • The LangGraph state object is persisted to PostgreSQL through GitLab APIs, and the code the agent has written is checkpointed by pushing hidden Git refs to the GitLab instance. [17]

The problem

A managed runtime has to receive an agent as a package, start it on machines the developer does not control, and expose it through a fixed set of remote operations. Three things make that awkward for an agent. Model and database clients cannot be serialised and shipped, so they must be created after deployment. Conversation state cannot live in the process, because instances come and go. And callers need standard query and streaming methods whatever the agent does inside.

Where this topic fits

LangGraph supplies the agent itself and the state model. With default settings the template builds its runnable by calling LangGraph's prebuilt create_react_agent with the model bound to the tools you pass. Persistence is opt-in through a checkpointer_builder function that returns a LangGraph checkpointer, and the class offers LangGraph's thread operations (get_state, get_state_history, update_state) next to query and stream_query.

How it is applied, step by step

  1. The developer constructs LanggraphAgent with a model name and a list of tools. Nothing is connected yet, which keeps the object serialisable for deployment.
  2. At set-up time, on the runtime, the template creates the model client and builds the runnable. By default that is the prebuilt ReAct agent: a model node, a tool node and the loop between them.
  3. If a checkpointer_builder was supplied, the template calls it to create the checkpointer, for example one backed by a Spanner database, and the agent uses it to save state.
  4. A caller sends query or stream_query with a config that carries a thread id. A typical run loads that thread's latest checkpoint, executes the graph and saves new checkpoints.
  5. Later calls with the same thread id continue the conversation, and get_state or get_state_history read back what was saved.
  6. To run a custom graph in place of the prebuilt agent, the developer passes a runnable_builder function that returns it.

Why this approach fits

The prebuilt agent gives the template a sensible default that needs only a model and tools, which is what most first deployments are. The builder functions solve the serialisation problem by postponing every connection until the code is running where it will stay. And because LangGraph separates the graph from its checkpointer, the same agent can use an in-memory saver in a notebook and a database-backed one in production by changing one function.

Limitation or tradeoff

The default is easy to outgrow, and it lags behind LangGraph itself. The reference shows the template importing create_react_agent from langgraph.prebuilt, which LangGraph's version 1 migration guide lists as deprecated in favour of create_agent. Without a checkpointer_builder there is no state history, so every query starts from nothing. The Spanner example in the reference also drops the checkpoint tables before calling setup(). That is convenient in a demo and would erase every saved thread if it were copied into a service that restarts.

The problem

One user request triggers several independent pieces of work: deciding which actions are relevant, calculating fallbacks, and searching the help pages for an answer. Run one after another, each adds its full latency to the reply. The team also had to combine the results of those pieces into a single response, and the case study describes the text-to-data logic as intricate if-statement code.

Where this topic fits

LangGraph sits at the centre of the assistant's execution flow. The independent pieces of work are separate nodes that run in the same super-step, and their outputs are merged in the shared state before a reply is built. The case study credits LangGraph with two things here: running independent code branches in parallel, and making it simpler to aggregate responses from different nodes.

How it is applied, step by step

  1. A property manager's request enters the graph as the initial state.
  2. The graph fans out. According to the case study, while the assistant determines relevant actions it simultaneously calculates fallbacks and runs a question-answering bot over help pages.
  3. In LangGraph, nodes that start from the same point run in one super-step. Each returns a partial update, and a reducer on the shared key merges the updates so that none overwrites another.
  4. A later node waits for the branches and composes one reply from the merged state, including related suggestions.
  5. For the text-to-data flow, named routes in the graph take the place of nested if-statements, so each case is a visible path.
  6. The team tests individual steps and whole executions, with evaluations run in continuous integration.

Why this approach fits

The three jobs do not depend on each other's output, so nothing is gained by running them in order. Putting them in one super-step means the wait is roughly that of the slowest branch, not the sum of all three. The shared state gives the composing step one place to read every result from, which is the aggregation benefit the case study names. A hand-written version would need threads or async tasks plus its own merging code.

Limitation or tradeoff

Every branch runs on every request, so the help-page search and the fallback calculation are paid for even when the main branch succeeds. Parallel writes need a reducer, and LangGraph's guide warns that updates from a parallel super-step may not arrive in a consistent order, so the composing step must not rely on list position. A super-step is also transactional: if one branch raises, none of that step's updates are applied unless the error is caught or a retry policy is set. The case study is published by the framework's vendor and gives no latency measurements.

Exa's deep research agent: a planner that fans out a variable number of tasks

ExaDocumented in a case study

A LangChain case study from June 2025 describes the deep research agent built by Exa, a company known for its search API. The agent explores the web for a research query and returns structured results through an API. The case study says the multi-agent system is built entirely on LangGraph. [20][2]

The problem

A research query can need one lookup or many separate investigations, and that number is not known until the query has been read. Each investigation uses tools and produces intermediate reasoning that is useless, and expensive, to show to the others. The product is an API, so the final result must be reliable structured data. According to the case study, Exa's earlier answers endpoint used no framework, and the team re-evaluated its options when the architecture became this complex.

Where this topic fits

LangGraph coordinates three roles. A planner analyses the query and generates parallel tasks. The tasks are independent research units with their own tools. An observer keeps the full context across planning, reasoning, outputs and citations. The number of task runs is decided at run time, which in LangGraph is the job of the Send primitive: one Send per task, each with its own input.

How it is applied, step by step

  1. The planner node reads the research query and produces a list of tasks. Its length depends on how complex the query is.
  2. A routing function turns the list into one unit of work per task. The case study does not name the API. In LangGraph the standard way is to return a list of Send objects, one per task.
  3. Each task run receives only what it needs: its instructions, a required output format given as a JSON schema, and access to Exa's API tools.
  4. In a typical implementation the task runs execute in parallel in one super-step and write their cleaned results to a shared key that has a reducer.
  5. Tasks do not see each other's intermediate reasoning. They receive only final cleaned outputs, while the observer has visibility of everything.
  6. The observer assembles the structured result that the API returns.

Why this approach fits

A fixed graph cannot express work whose width is unknown in advance, and a single agent loop would do the investigations one at a time in one ever-growing context. Send gives each task a private input, which is the context isolation the case study describes, and the reducer collects results without the tasks knowing about each other. Keeping the fan-out in the graph also makes the number of tasks visible in traces, which matters for a product whose cost depends on token usage.

Limitation or tradeoff

Fan-out multiplies cost. Every extra task is at least one more model call plus its tool calls, and nothing in the pattern limits how many tasks a planner may request, so a cap must be coded into the planner or the routing function. Isolation cuts both ways, because a task cannot benefit from something another task discovered midway. The response time the case study reports ranges from seconds to minutes, which rules the pattern out for interactive use without streaming. The case study is published by LangChain, and its figures are not independently verified.

4Common mistakes

  1. Declaring a list key without a reducer and returning a new list from each node.

    Why it causes problems
    Every update replaces the stored list. A conversation keeps only the most recent message, or a log keeps only its last line, and no error is raised to tell you.
    How to recognise it
    The final state holds one item where you expected many, or an agent answers as if it had never seen the earlier turns. If two parallel nodes write the key, you get the concurrent-update error instead.
    How to fix it
    Annotate the key with a reducer, such as Annotated[list[str], operator.add], or use add_messages or MessagesState for chat history.

  2. Putting a side effect before interrupt() in the same node.

    Why it causes problems
    The node restarts from its first line on resume, so the charge, email or database insert happens once before the pause and again after it. If the person rejects, the first one has already happened.
    How to recognise it
    Duplicate records or messages that appear only on runs that were paused, and an effect that happens before anyone has approved.
    How to fix it
    Keep the approval node free of side effects. Put the action after the interrupt call or in a separate later node, and make it idempotent with a key or an upsert.

  3. Using InMemorySaver, or no checkpointer at all, in a deployed service.

    Why it causes problems
    Memory, interrupts and crash recovery all depend on stored checkpoints. An in-memory saver loses every thread when the process restarts, and a second server instance cannot see threads held by the first.
    How to recognise it
    Conversations that forget everything after a deploy, and resume calls that fail or start from empty state when a different instance handles them.
    How to fix it
    Use a database checkpointer such as PostgresSaver in production, run its setup step once, and plan how old checkpoints are pruned.

  4. Treating the thread id as a per-request value, or sharing one id between users.

    Why it causes problems
    A new id on every request means every call starts from empty state, so nothing is remembered and nothing can be resumed. One shared id mixes different users' messages into a single state.
    How to recognise it
    A resume that does nothing, a follow-up question answered without context, or one user seeing content from another user's conversation.
    How to fix it
    Create the thread id once per conversation or job, store it with that record, and send the same id on every later call, including the resume.

  5. Leaving the recursion limit at its default, or setting it inside configurable.

    Why it causes problems
    The default allows 1000 super-steps since version 1.0.6, which is a very long and expensive loop for an agent. A recursion_limit placed inside the configurable dictionary is not the standalone config key the documentation requires, so the limit you intended is not the one applied.
    How to recognise it
    A looping run that goes on far longer than you intended, or a limit you believed you set that never triggers GraphRecursionError.
    How to fix it
    Pass it at the top level of the config, for example {"recursion_limit": 25, "configurable": {...}}, choose the number from how many steps good runs take, and use RemainingSteps in state to finish gracefully.

  6. Giving one node both a normal edge and dynamic routing.

    Why it causes problems
    A Command with goto, or a conditional edge, only adds a target. The normal edge still fires, so both next nodes run in the same super-step and the graph does work you did not ask for.
    How to recognise it
    A node that should have been skipped appears in the updates stream or the trace next to the node you routed to.
    How to fix it
    Use one mechanism per node. Remove the normal edge when a node routes with Command or with a conditional edge.

Run two order checks in parallel and route on the merged result

python
import operator
from typing import Annotated, Literal

from typing_extensions import TypedDict
from langgraph.graph import END, START, StateGraph

STOCK = {"A-100": 12, "B-200": 0, "C-300": 3}
REVIEW_ABOVE = 500.0
ORDERS = [
    {"sku": "A-100", "quantity": 2, "amount": 59.97},
    {"sku": "C-300", "quantity": 5, "amount": 1250.0},
]


class Order(TypedDict):
    sku: str
    quantity: int
    amount: float
    flags: Annotated[list[str], operator.add]
    decision: str
    message: str


def check_stock(order: Order):
    available = STOCK.get(order["sku"], 0)
    if available >= order["quantity"]:
        return {"flags": []}
    return {"flags": [f"stock: only {available} of {order['sku']} left"]}


def check_fraud(order: Order):
    if order["amount"] <= REVIEW_ABOVE:
        return {"flags": []}
    return {"flags": [f"fraud: amount {order['amount']:.2f} needs review"]}


def decide(order: Order):
    return {"decision": "hold" if order["flags"] else "ship"}


def route(order: Order) -> Literal["ship", "hold"]:
    return order["decision"]


def ship(order: Order):
    return {"message": f"shipping {order['quantity']} x {order['sku']}"}


def hold(order: Order):
    return {"message": f"held with {len(order['flags'])} flag(s)"}


builder = StateGraph(Order)
for node in (check_stock, check_fraud, decide, ship, hold):
    builder.add_node(node)
builder.add_edge(START, "check_stock")
builder.add_edge(START, "check_fraud")
builder.add_edge(["check_stock", "check_fraud"], "decide")
builder.add_conditional_edges("decide", route)
builder.add_edge("ship", END)
builder.add_edge("hold", END)
graph = builder.compile()

for order in ORDERS:
    result = graph.invoke(order)
    print(result["decision"], "|", result["message"], "|", sorted(result["flags"]))

for part in graph.stream(ORDERS[1], stream_mode="updates", version="v2"):
    print(list(part["data"]))

Why it works:

  • Both checks have an edge from START, so they are scheduled in the first super-step and run in parallel. Each returns a partial update for flags, and operator.add joins the two lists.
  • The list-form edge makes decide wait for both checks and run once. Here the two branches have the same length, so two separate edges would also run it once. The list form states the intent and stays correct if a branch gains a step.
  • decide only writes the decision. The conditional edge reads it and picks the node. Keeping the choice on an edge is what lets a trace, a stream or a diagram show which way each order went.
  • The flags are sorted when printed because the documentation warns that updates from a parallel super-step may not be ordered consistently.

For the second order: 3 units of C-300 are in stock and 5 were ordered, so check_stock flags it. 1250.0 is above 500.0, so check_fraud flags it too. Two flags means hold, and the message counts them.

Without the reducer, flags is a plain replace-on-write key. It receives two writes in one super-step, which LangGraph refuses, and since the super-step is transactional nothing from that step is applied.

  • Does the first order print ship with an empty flag list, and the second print hold with exactly two flags?
  • Does the updates stream for the second order contain exactly one item for decide?
  • After removing the reducer, does the error appear on the first order too, although that order has no flags?
  • Can you explain why the flags are sorted before printing and never compared by position?

Find the defects in a refund approval graph

AnalysisIntermediateAbout 25 min (estimate)Hypothetical scenario

A colleague asks you to review this graph before it goes live. payments.create_refund sends real money and is not idempotent. Managers often approve the next day. You do not need to run anything.

python
from uuid import uuid4

from typing_extensions import TypedDict
from langgraph.graph import END, START, StateGraph
from langgraph.types import Command, interrupt

import payments   # the company's payment client


class State(TypedDict):
    order_id: str
    amount: float
    approved: bool
    receipt_id: str


def refund(state: State):
    try:
        receipt_id = payments.create_refund(state["order_id"], state["amount"])
        approved = interrupt(f"Refund {state['amount']} for {state['order_id']}?")
    except Exception:
        approved = False
        receipt_id = ""
    return {"approved": approved, "receipt_id": receipt_id}


builder = StateGraph(State)
builder.add_node("refund", refund)
builder.add_edge(START, "refund")
builder.add_edge("refund", END)
graph = builder.compile()

graph.invoke({"order_id": "A-17", "amount": 120.0}, {"configurable": {"thread_id": str(uuid4())}})
# ... the next day, in the web handler for the manager's click:
graph.invoke(Command(resume=True), {"configurable": {"thread_id": str(uuid4())}})

List every defect that would cause wrong behaviour, say what the business would observe, and rewrite the graph.

Requirements

  • Identify at least four distinct defects and tie each one to a rule from this lesson.
  • For each defect, state the observable consequence and not only the rule that is broken.
  • The rewritten graph must make the refund at most once per approved request and never for a rejected one.
  • The rewrite must still work when the approval arrives a day later in a different process.

A correct review finds at least these four defects: the refund call sits before the interrupt, the bare except Exception wraps the interrupt, the graph is compiled without a checkpointer, and the resume uses a new thread id. The rewrite separates approval and payment into two nodes joined by a conditional edge, compiles with a durable checkpointer, stores one thread id with the refund request and resumes on that same id.

With only the ordering defect left, create_refund runs twice for an approved request: once before the pause and once when the node restarts on resume.

Read the node top to bottom twice, once for the first call and once for the resume, and note which lines execute each time.

Hint 2

Ask where the state lives between the two invoke calls, and how the second call finds it.

Show solution

Defects

  1. Side effect before the interrupt. create_refund runs before anyone is asked, so the money leaves whatever the manager decides. On resume the node restarts from its first line and would pay again.
  2. Bare except Exception around interrupt. The pause is implemented by raising an exception. This clause catches it, so the graph never pauses: it records approved = False with an empty receipt and finishes, after the refund has already been paid. The books show a rejected refund that was in fact sent.
  3. No checkpointer. interrupt needs saved state to resume from. Without a checkpointer nothing is stored between the two calls.
  4. A new thread id on resume. A thread id is the pointer to the saved state. A fresh uuid4() names an empty thread, so there is nothing to resume.
  5. A day-long wait needs a durable checkpointer. InMemorySaver would fix defect 3 on a laptop but not in a service, because the handler runs in another process and possibly after a restart.

Rewrite

python
from typing import Literal

from typing_extensions import TypedDict
from langgraph.graph import END, START, StateGraph
from langgraph.types import Command, interrupt

import payments


class State(TypedDict):
    order_id: str
    amount: float
    approved: bool
    receipt_id: str


def ask_approval(state: State):      # no side effects: safe to run twice
    approved = interrupt(
        {"question": "Approve this refund?", "order_id": state["order_id"], "amount": state["amount"]}
    )
    return {"approved": bool(approved)}


def route(state: State) -> Literal["pay_refund", END]:
    return "pay_refund" if state["approved"] else END


def pay_refund(state: State):        # runs only after an approval was recorded
    return {"receipt_id": payments.create_refund(state["order_id"], state["amount"])}


builder = StateGraph(State)
builder.add_node("ask_approval", ask_approval)
builder.add_node("pay_refund", pay_refund)
builder.add_edge(START, "ask_approval")
builder.add_conditional_edges("ask_approval", route)
builder.add_edge("pay_refund", END)
graph = builder.compile(checkpointer=checkpointer)   # a database checkpointer created at start-up

config = {"configurable": {"thread_id": "refund-A-17"}}   # saved with the refund request
result = graph.invoke({"order_id": "A-17", "amount": 120.0}, config)
# result["__interrupt__"][0].value is what the approval screen shows

# the next day, in the handler for the manager's click:
graph.invoke(Command(resume=True), config)   # resume=False rejects and ends without paying

The approval node now contains nothing that is harmful to repeat, the payment is in a node that is reached only through the approved branch, and both calls use the same thread id against a checkpointer that outlives the process.

One hardening step remains. A node can also run again if the process dies after create_refund returns but before the super-step's checkpoint is written. If the payment API accepts an idempotency key, pass one derived from the order id so that a repeated call cannot pay twice.

The count. With only the ordering defect left, create_refund runs twice: once on the first invoke before interrupt pauses the node, and once on resume when the node starts again from its first line.

Check your answer

  • Did you find that the except clause prevents the pause entirely, and not only that it hides errors?
  • Does your rewrite contain no side effects before the interrupt call in the same node?
  • Is the thread id in your rewrite created once and reused for the resume?
  • Did you answer two for the number of create_refund calls, and can you say which two moments they are?
