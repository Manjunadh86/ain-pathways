Structured Outputs

A structured output is a model reply that follows a schema you supply, most often a JSON Schema, so that a program can parse it and use it without guessing. Providers enforce the schema while the reply is being generated, a technique called constrained decoding, and your code still validates the result.

1Overview

Why it matters

Most model calls in a real application are read by code. A router picks a branch from a label, an extraction step writes rows into a database, and an agent hands a plan to the next step. Each of those consumers needs exact keys, types and allowed values. A reply that begins with "Sure, here is the JSON", drops a required field or invents a category makes the parser throw, and a failure rate that looks small on one call becomes a daily incident at volume.

Structured outputs turn the format from a request in the prompt into a rule enforced by the decoder. That removes one class of failure completely and leaves others untouched: a refusal, a reply cut off by the token limit, and a value that fits the schema but is wrong. Anyone who builds extraction pipelines, tool-calling agents or evaluation harnesses needs to know which guarantees come from the provider, which checks remain their own job, and how schema limits differ between OpenAI, Anthropic, Gemini and open-weight model servers.

  • Check a reply in the right order (stop reason, parsing, schema validation, semantic rules).
  • Implement a bounded validate-and-retry loop that feeds errors back and returns a distinct failure status.
  • Design a schema that fits strict-mode limits and move unsupported constraints into code.

Key terms

JSON Schema
A declarative format, itself written in JSON, that describes which keys, types and values a JSON document may contain.
Structured output
A model reply that is required to match a schema supplied with the request, so that a program can parse it directly.
JSON mode
An API setting that makes the reply parse as JSON but does not check it against any schema.
Constrained decoding
Generation in which, before each token is chosen, every token that would break a grammar is removed from the choices. Also called constrained sampling or guided generation.
Grammar
A set of rules that defines exactly which strings are valid. Providers compile a JSON Schema into a grammar before generation starts.
Token mask
The set of tokens allowed at one step of generation. Tokens outside the mask are given probability zero.
Strict mode
The strict flag on an OpenAI schema, or on an OpenAI or Anthropic tool definition, that turns schema adherence from best effort into an enforced constraint.
Schema validation
Checking parsed data against the schema in your own code, usually with a library such as Pydantic or Zod.
Semantic validation
Checks on meaning that a schema cannot express, such as a total that must equal the sum of its line items or an ID that must appear in the source text.
Refusal
A reply in which the model declines the request for safety reasons. It is reported through a separate field or stop reason and does not follow your schema.

2Explanation

Introduction

In Prompt Engineering you asked a model for JSON by describing the format and showing an example. That works most of the time. This lesson is about the rest of the time, and about the tools that turn the format from a request into a guarantee.

Think about the difference between a letter and a web form. If you ask customers to write a letter giving their order number, the date and the reason for a return, most will include all three, some will forget one, and a few will write the date in a way you cannot read. A web form with a required order-number box, a date picker and a drop-down list of reasons cannot be submitted in the wrong shape. The form does not make the customer careful, though. Someone can still pick the wrong reason from the list.

A model reply has the same three levels:

  • Prompt only. You describe the JSON you want. The model usually complies, and sometimes adds a greeting, wraps the object in a Markdown code fence, leaves a field out or invents a value.
  • JSON mode. The API promises that the reply parses as JSON. It does not promise your keys, your types or your allowed values.
  • Schema-constrained output. You send a JSON Schema (opens in a new tab), a small JSON document that lists the allowed keys, types and values, and the provider restricts generation so that the reply matches it. OpenAI, Anthropic and Google all call this feature structured outputs. This is the web form.

Even the third level is a guarantee about shape only. The code around the call still has work to do, as the diagram shows.

The rest of the lesson follows that pipeline. You will see how a decoder enforces a schema token by token, what the request looks like on the main APIs, which failures survive enforcement, how to validate and retry without looping forever, and where schema design runs into provider limits. The same mechanism makes tool arguments reliable, which is the subject of Tool Calling.

How it works

Three levels of guarantee

With a prompt alone, the format is an instruction the model may or may not follow. LinkedIn's engineers reported (opens in a new tab) that about 10% of the replies that were supposed to carry structured parameters contained mistakes, and some could not be parsed at all.

JSON mode closes the syntax gap and nothing else. In the OpenAI API you turn it on with text: {"format": {"type": "json_object"}}, and the guide (opens in a new tab) states that it will not make the output match any specific schema. It also has a trap: without an instruction to produce JSON the model may emit whitespace until the token limit, so the API rejects a request whose context never mentions JSON.

Schema-constrained output closes the structure gap. You pass the schema itself, and required keys, types and enum values are enforced while the reply is generated.

How constrained decoding works

A model writes one token at a time. At each step it scores every token in its vocabulary and one of them is chosen (see How Large Language Models Work). Nothing in that process knows about JSON, which is why an unconstrained model is free to emit a brace, a greeting or a made-up key at any point.

Constrained decoding adds one step between scoring and choosing. OpenAI's engineering write-up (opens in a new tab) describes it: the schema is converted into a context-free grammar, a formal set of rules for which strings are valid. After every token, the inference engine works out which tokens the grammar allows next and masks all the others, which sets their probability to zero. The model chooses among the survivors.

The grammar is a real artefact that you can read. llama.cpp documents the converter it uses (opens in a new tab), and shows a property declared as "age": {"type": "integer", "minimum": 0, "maximum": 150} turning into a rule that spells out which digit sequences are allowed:

text
item-age ::= ([0-9] | ([1-8] [0-9] | [9] [0-9]) | "1" ([0-4] [0-9] | [5] "0")) space

Compiling a schema into a grammar takes time, so providers do it on the first request and cache the result. The edge cases below give the numbers.

Asking for it

Each API has its own parameter, and the names have changed over time (Anthropic, for example, moved output_format to output_config.format), so check the current reference before copying an old tutorial.

A minimal request body for the Anthropic Messages API looks like this:

json
{
  "model": "claude-opus-5-5",
  "max_tokens": 1024,
  "messages": [{"role": "user", "content": "Extract the contact: John Smith, john@example.com"}],
  "output_config": {
    "format": {
      "type": "json_schema",
      "schema": {
        "type": "object",
        "properties": {"name": {"type": "string"}, "email": {"type": "string"}},
        "required": ["name", "email"],
        "additionalProperties": false
      }
    }
  }
}

The reply's text block is a JSON object with exactly those two keys. In practice you rarely write the schema by hand. You define a Pydantic model or a Zod schema, the SDK generates the JSON Schema from it, and the same definition validates the reply, so the two cannot drift apart.

What enforcement does not cover

A schema-constrained reply can still be unusable in four documented ways:

  1. Refusal. The model may decline for safety reasons. OpenAI returns a content item of type refusal in place of the JSON. Anthropic (opens in a new tab) returns stop_reason: "refusal" and says the output may not match the schema.
  2. Truncation. If generation hits the output token limit, the JSON stops in the middle of the object. OpenAI reports status: "incomplete" and Anthropic reports stop_reason: "max_tokens".
  3. Wrong values. The decoder guarantees that total is a number. It cannot make it the right number. Google's guidance (opens in a new tab) is to always validate values in your application.
  4. Forced answers. The model has to fill every required field even when the input has nothing to do with the schema, and OpenAI warns that this can produce hallucinated values. Give the model a legal way out, such as a nullable field or an unknown enum value.

So check in this order: refusal or stop reason, then parsing, then the schema, then your own rules.

Validate, then retry or repair

Validation has two layers. The JSON Schema guide itself says that a schema describes surface structure, and that relationships between values need a second, semantic check written in ordinary code.

When a check fails you have three options:

  • Retry with feedback. Send the invalid reply back with the exact error messages and ask for a corrected object. Put a bound on it. The Instructor library's retry guide (opens in a new tab) suggests two or three attempts for validation errors and offers a token budget for the retries.
  • Repair in code. Strip a code fence, fix a known quoting mistake, turn "3" into 3. LinkedIn chose this route because a second model call added latency and used GPU capacity.
  • Fail with a status. When attempts run out, return a distinct failure and never a half-valid object.

The arithmetic is worth doing. If each call is valid with probability qqq, a job of nnn independent calls has no invalid reply with probability qnq^nqn. If a call is invalid with probability ppp and attempts were independent, kkk attempts would all fail with probability pkp^kpk. At p=0.1p = 0.1p=0.1, one retry gives q=0.99q = 0.99q=0.99 and two retries give q=0.999q = 0.999q=0.999.

Real attempts are not independent, because the same prompt on the same input tends to fail in the same way. That is why the error message goes back with the retry.

Schema design limits

Standard JSON Schema is permissive: unless a schema says otherwise, an object may omit any property and may carry extra ones (opens in a new tab). A grammar cannot be that loose, so strict modes make you close the object, and each platform supports its own subset of the language.

RuleOpenAI (strict)Anthropic
Optional fieldsNone. Every key goes in required; use a type such as ["string", "null"] for a value that may be absentAllowed, at most 24 across a request
additionalPropertiesMust be falseMust be false
minimum, maximumSupported, except on fine-tuned modelsNot supported
Recursive schemasSupportedNot supported
Size limits5,000 properties, 10 nesting levels, 1,000 enum values16 union-typed parameters, 20 strict tools, 180-second compile timeout

OpenAI also requires the root to be an object. Gemini's page lists its supported types and keywords (including minimum and maximum) and warns that very large or deeply nested schemas may be rejected.

Depending on the platform, an unsupported keyword is rejected, moved into a description by an SDK helper, or silently skipped (see the edge cases). A benchmark paper (opens in a new tab) tested six constrained decoding engines on 10,000 real-world schemas and the JSON Schema Test Suite. The best engine supported twice as many of the real-world schemas as the worst, and some engines accept a schema and then allow output that violates it. Validate in your own code anyway.

Three rules of thumb follow from the mechanism:

  • Order fields the way they should be written. OpenAI emits keys in schema order. Anthropic emits required keys first, then optional ones. Put a short reason field before the verdict it supports, so the verdict is generated after the evidence. Keep it short: Anthropic warns that a property asking for step-by-step thinking can trigger a refusal.
  • Use enum for every closed set and description for meaning. On hosted APIs the descriptions guide the model. llama.cpp uses the schema only to build the grammar and does not show it to the model, so repeat the field meanings in the prompt there.
  • Keep schemas flat and small. Anthropic notes that each optional parameter roughly doubles part of the grammar's state space.

Worked example: Extracting a support ticket with a schema check, a semantic check and bounded retries

A support tool has to turn a customer message into four fields: a category from a fixed list, a priority from 1 to 3, the order ID if one is mentioned, and a short summary. So that everyone gets identical output, the model is replaced by four scripted replies, each wrong in a different way until the last. Everything else is real: the schema, both validators and the retry loop.

Save this as validate_retry.py. It needs only the Python standard library (3.9 or later).

python
import json

SCHEMA = {
    "type": "object",
    "properties": {
        "category": {"type": "string", "enum": ["billing", "bug", "how_to"]},
        "priority": {"type": "integer", "enum": [1, 2, 3]},
        "order_id": {"type": ["string", "null"]},
        "summary": {"type": "string"},
    },
    "required": ["category", "priority", "order_id", "summary"],
    "additionalProperties": False,
}
TICKET = "I was charged twice for order A-1024. Please refund one payment today."
TYPES = {"object": dict, "string": str, "integer": int, "null": type(None)}


def has_type(value, name):
    return isinstance(value, TYPES[name]) and not (name == "integer" and isinstance(value, bool))


def schema_errors(value, schema, path="$"):
    """Check the small JSON Schema subset used here and return a list of messages."""
    names = schema["type"] if isinstance(schema["type"], list) else [schema["type"]]
    if not any(has_type(value, name) for name in names):
        return [f"{path}: expected {' or '.join(names)}, got {json.dumps(value)}"]
    if "enum" in schema and value not in schema["enum"]:
        return [f"{path}: {json.dumps(value)} is not one of {json.dumps(schema['enum'])}"]
    if not isinstance(value, dict):
        return []
    props = schema.get("properties", {})
    missing = [f"{path}: missing required key '{key}'"
               for key in schema.get("required", []) if key not in value]
    extra = [f"{path}: unexpected key '{key}'" for key in value
             if key not in props and schema.get("additionalProperties") is False]
    nested = [error for key in props if key in value
              for error in schema_errors(value[key], props[key], f"{path}.{key}")]
    return [*missing, *extra, *nested]


def semantic_errors(data, source):
    """A rule no schema can express: the order id must be copied from the ticket."""
    if data["order_id"] is not None and data["order_id"] not in source:
        return [f"$.order_id: '{data['order_id']}' does not appear in the ticket text"]
    return []


def check(reply, source):
    try:
        data = json.loads(reply)
    except json.JSONDecodeError as error:
        return None, [f"not valid JSON: {error.msg} at line {error.lineno} column {error.colno}"]
    errors = schema_errors(data, SCHEMA)
    return data, errors or semantic_errors(data, source)


def extract(source, model, max_attempts=4):
    task = f"Return one JSON object for this ticket.\nSchema: {json.dumps(SCHEMA)}\nTicket: {source}"
    messages = [{"role": "user", "content": task}]
    errors = []
    for attempt in range(1, max_attempts + 1):
        reply = model(messages)
        data, errors = check(reply, source)
        print(f"attempt {attempt}:", "ok" if not errors else "rejected")
        if not errors:
            return {"status": "ok", "attempts": attempt, "data": data}
        print("".join(f"  - {error}\n" for error in errors), end="")
        feedback = "Rejected:\n- " + "\n- ".join(errors) + "\nReturn only the corrected JSON object."
        messages = [*messages, {"role": "assistant", "content": reply},
                    {"role": "user", "content": feedback}]
    return {"status": "invalid", "attempts": max_attempts, "errors": errors}


def scripted_model(replies):
    remaining = iter(replies)  # stands in for an LLM: one scripted reply per call
    return lambda messages: next(remaining)


REPLIES = [
    'Sure! Here is the ticket:\n```json\n{"category": "billing", "priority": 1}\n```',
    '{"category": "Billing issue", "priority": "high", "order_id": "A-1024",'
    ' "summary": "Charged twice", "confidence": 0.9}',
    '{"category": "billing", "priority": 1, "order_id": "A-1042", "summary": "Charged twice"}',
    '{"category": "billing", "priority": 1, "order_id": "A-1024", "summary": "Charged twice"}',
]

if __name__ == "__main__":
    print(extract(TICKET, scripted_model(REPLIES)))
    print(extract(TICKET, scripted_model(REPLIES), max_attempts=2))

Run python3 validate_retry.py. The first call to extract prints:

text
attempt 1: rejected
  - not valid JSON: Expecting value at line 1 column 1
attempt 2: rejected
  - $: unexpected key 'confidence'
  - $.category: "Billing issue" is not one of ["billing", "bug", "how_to"]
  - $.priority: expected integer, got "high"
attempt 3: rejected
  - $.order_id: 'A-1042' does not appear in the ticket text
attempt 4: ok
{'status': 'ok', 'attempts': 4, 'data': {'category': 'billing', 'priority': 1, 'order_id': 'A-1024', 'summary': 'Charged twice'}}

Each rejected attempt fails at a different level, and a different tool would have prevented it:

AttemptWhat went wrongWhat prevents it
1A greeting and a code fence around the JSONJSON mode or a schema constraint
2An extra key, a category outside the enum, text where an integer belongsA schema constraint (strict mode)
3Order ID A-1042, but the ticket says A-1024Only the semantic check in your code

Attempt 1 was also missing two required keys, and nobody found out, because parsing failed first. Attempt 3 is the one to remember. It satisfies the schema completely and it is wrong.

The second call sets max_attempts=2. It prints the same first two attempts and returns a dictionary with 'status': 'invalid', 'attempts': 2 and the three schema errors. It does not return the half-valid object from attempt 2.

For a live system, replace scripted_model(REPLIES) with a function that sends messages to a model. If you also turn on the provider's structured output feature, attempts 1 and 2 cannot occur. The loop then exists for refusals, truncated replies and failures like attempt 3.

Edge cases and limitations

A reply cut off by the token limit is not valid JSON
If generation stops at the output token limit, the object ends in the middle of a string or an array and the schema guarantee no longer holds. OpenAI reports status incomplete with the reason max_output_tokens. Anthropic reports the stop reason max_tokens and advises retrying with a higher limit. Check for this before you parse, and size the limit for the largest object the schema allows, long arrays included.
A refusal replaces the schema
The model can decline for safety reasons even under a strict schema. OpenAI returns a refusal content item in place of the JSON. Anthropic returns the stop reason refusal with an HTTP 200 status, bills the generated tokens and warns that the output may not match the schema. Code that goes straight to parsing will throw, or read a partial object as if it were data. Branch on the refusal signal first and log or show the refusal text.
The first request with a new schema is slow
The provider has to compile the schema into a grammar before it can generate. OpenAI's announcement gives under 10 seconds for typical schemas and up to a minute for complex ones on the first request, with no penalty afterwards. Anthropic caches a compiled grammar for 24 hours from its last use and stops compilation after 180 seconds. A schema built per request, for example with a different enum for every user, pays the cost every time. Keep schemas stable and send one warm-up request at deploy time.
The model must answer even when the input does not fit
Under a strict schema every required field receives a value. OpenAI's guide notes that the model will always try to adhere to the schema, which can produce hallucinated values when the input is unrelated to it. An invoice extractor that is handed a restaurant menu still returns an invoice number. Add an explicit way out, such as nullable fields or a status field with a not_applicable value, and state in the prompt when to use it.
One unsupported keyword, three different behaviours
OpenAI's strict mode and the Anthropic API reject a schema that uses an unsupported feature. Anthropic's SDK helpers instead strip constraints such as minimum and maxLength, append them to the field description and re-check them after the reply arrives. llama.cpp's converter skips unsupported features silently, so the grammar is looser than the schema you wrote. The same schema therefore behaves in three ways across platforms. Run your own validator on every reply so that the rule holds everywhere.
Enum values can come back with different capitalisation
Anthropic documents that structured outputs do not guarantee the capitalisation of enum and const strings. A schema value written as Conversation topic 3 may come back as Conversation Topic 3, with no error and a normal stop reason, so an exact string comparison fails on a reply the API treats as valid. Choose enum values that differ by more than letter case, prefer lower-case identifiers such as billing_issue, and compare case-insensitively.

When to use it, and when something simpler is enough

Use it when

  • The reply is consumed by code: written to a database, sent to another API, used to choose a branch, or passed to the next step of a chain or an agent.
  • The answer comes from a closed set, such as a category, a routing decision or a yes or no. An enum or boolean schema removes every other possible reply.
  • You extract fields from documents at volume, where even a one percent rate of format failures means failures every day.
  • You render a user interface from the reply, and each part of the answer has to land in a known place on the screen.

Think twice when

  • A person reads the answer directly and no code needs its parts. A schema then adds a compile step and design limits and gives the reader nothing.
  • The schema would be generated fresh for each request. Every new schema pays the grammar compilation delay, and the provider's cache never helps.
  • You need a feature the provider documents as incompatible. On the Claude API, citations and message prefilling cannot be combined with JSON outputs.
  • The structure exceeds the platform's limits on nesting, optional fields or union types. Split the task into several smaller calls instead of forcing one large schema through.

A simpler alternative. Ask for JSON in the prompt with one example, parse the reply, validate it, and retry once with the error message. That is enough for a prototype, a low-volume internal tool or a model with no schema support. It stops being enough when format failures become a regular event at your volume, when you find yourself writing repair code for specific mistakes, or when a wrong key could trigger an action. For a single label, an enum-only schema or a server-side choice constraint is simpler than a full object.

Key takeaways

  • JSON mode guarantees only that a reply parses as JSON, while schema-constrained output also guarantees your keys, types and enum values.
  • Constrained decoding compiles the schema into a grammar and, before each token is chosen, masks every token that the grammar does not allow.
  • The guarantee covers shape only, so a reply can still be a refusal, be cut off at the token limit, or hold values that fit the schema and are wrong.
  • Check every reply in a fixed order (stop reason, parsing, schema, semantic rules), retry a bounded number of times with the error messages, and return a distinct failure status when attempts run out.
  • Each platform supports a different subset of JSON Schema, so design small, flat schemas with enums and nullable fields, and keep unsupported constraints as checks in your own code.

Example 1 of 5

OpenAI API: constrained decoding behind Structured Outputs

OpenAIDocumented in an engineering article

OpenAI's announcement of Structured Outputs in August 2024 explains how the API enforces a developer's JSON Schema during generation, and the current Structured Outputs guide documents how the feature behaves today. [2][1]

The problem

JSON mode, introduced the year before, made replies parse as JSON but did not make them conform to a particular schema. The announcement says developers had been working around this with open-source tooling, prompting and repeated retries so that outputs matched the formats their systems needed. Training alone did not close the gap. The model that OpenAI trained to follow complicated schemas reached 93% on the company's benchmark, which the team considered short of what robust applications need.

Where this topic fits

Enforcement sits inside the provider's inference engine, between the model's scores for the next token and the sampling step. Before it, the developer sends a schema with strict: true. After it, the application receives JSON that matches the schema, a refusal, or an incomplete response, and has to tell the three apart.

How it is applied, step by step

  1. The developer sends a request in which the text format, or a function definition, carries a JSON Schema with strict set to true.
  2. On the first request with that schema, the API converts it into a context-free grammar and preprocesses it into a cached structure. Later requests with the same schema reuse the cache.
  3. During generation, after every token, the engine determines which tokens the grammar allows next, given the text produced so far.
  4. Tokens outside that set are masked, which lowers their probability to zero, and the model samples from the remaining ones.
  5. The response carries the JSON text, or a refusal item if the model declined, or an incomplete status if a token limit stopped it early.
  6. The application checks for a refusal and for an incomplete status, and only then parses the text into its own type.

Why this approach fits

Prompting and training make a format likely. Masking makes every other format impossible, which is the step OpenAI added to take its own evaluation from 93% to 100%. Doing it inside the inference engine also means the developer writes no parsing tricks and no retry loop for format errors. Choosing a grammar over a regular expression lets the feature cover nested and recursive structures, which the announcement gives as the reason for that design.

Limitation or tradeoff

The guarantee has documented gaps. A refusal or a response cut short by a token limit does not match the schema, and the values inside a matching object can still be wrong. Only a subset of JSON Schema is accepted, every field must be required, and the first request with a new schema is slow. The 100% figure comes from OpenAI's own evaluation in 2024 and measures adherence to the schema, not the correctness of what was extracted.

What the sources document

  • The announcement states that JSON mode improves reliability for generating valid JSON but does not guarantee that the model's response will conform to a particular schema. [2]
  • On OpenAI's evals of complex JSON schema following, gpt-4o-2024-08-06 with Structured Outputs scored 100%, compared with less than 40% for gpt-4-0613. Training alone took the new model to 93% on the benchmark before the constraint was added. [2]
  • The API converts each supplied JSON Schema into a context-free grammar and, after every token, determines which tokens are valid next and masks the sampling step, which lowers the probability of invalid tokens to zero. [2]
  • The first response with a new schema incurs additional latency while the schema is processed and cached. The announcement says typical schemas take under 10 seconds and more complex ones may take up to a minute. [2]
  • The guide states that the model might not produce a response matching the schema when it refuses for safety reasons or when a max tokens limit leaves the response incomplete, and that Structured Outputs can still contain mistakes. [1]

The facts above come from the cited sources. The steps and analysis in this example are our explanation of how they fit together.

Example 2 of 5

vLLM: choice, regex, JSON and grammar constraints for self-hosted models

vLLMDocumented in official docs

vLLM is an open-source inference server for open-weight models. Its Structured Outputs documentation describes how the OpenAI-compatible server constrains generation with a list of choices, a regular expression, a JSON Schema or a context-free grammar. [9][12]

The problem

A team that serves an open-weight model itself has no provider feature to switch on, and the model was not necessarily trained to follow schemas. Many of its tasks also do not need a JSON object. A classifier needs exactly one label from a list, an ID generator needs a string in a fixed pattern, and a query builder needs output in a small SQL-like language.

Where this topic fits

The constraint is applied by a decoding backend inside the server (the documentation names xgrammar and guidance) on every request that carries a structured_outputs field or an OpenAI-style response_format. The client is an ordinary OpenAI SDK call pointed at the local server, and the application parses and validates the reply afterwards as it would with a hosted API.

How it is applied, step by step

  1. The operator starts the server with a model. Structured outputs are on by default in the OpenAI-compatible server, and the backend setting defaults to auto, which picks a backend for each request.
  2. For a single label, the client passes a list of choices in the request's extra body, and the reply is exactly one of the listed strings.
  3. For a patterned string the client passes a regular expression, and for a custom language it passes a context-free grammar written in EBNF.
  4. For an object, the client passes a JSON Schema as a response format of type json_schema, usually generated from a Pydantic model.
  5. The prompt still describes the wanted fields, because the documentation notes that stating the schema in the prompt usually improves the results.

Why this approach fits

Because the constraint is applied by the server while it decodes, it works with any model the server can load, including models that were never trained for function calling or schemas. Offering choices and regular expressions next to JSON Schema matters as well. A one-word label is simpler as a choice constraint than as a JSON object with a single enum field, and a grammar can describe formats that JSON Schema cannot.

Limitation or tradeoff

Behaviour depends on the backend. The documentation notes that regular expression syntax differs between backends, and the JSONSchemaBench study, published in early 2025, found that engines differ widely in which JSON Schema features they enforce. In that study XGrammar, one of the backends vLLM names, had the most cases in which output that violated the schema was allowed. The request fields have also been renamed, so client code has to track the server version. Validation in the application is still needed.

What the sources document

  • Structured outputs are supported by default in the OpenAI-compatible server, and the backend option defaults to auto, which tries to choose an appropriate backend based on the details of the request. [9]
  • The fields guided_json, guided_regex, guided_choice and guided_grammar were removed in v0.12.0, and requests now use the structured_outputs field. [9]

  • In the JSONSchemaBench analysis of the JSON Schema Test Suite, XGrammar minimised compilation errors but showed the highest number of under-constrained failures, which the paper defines as allowing JSON instances that are invalid under the schema. [12]

Where this topic fits

4Common mistakes

  1. Treating JSON mode as if it enforced your schema.

    Why it causes problems
    JSON mode only makes the reply parse. Keys can be missing, renamed or extra, and values can have any type, so downstream code fails with key errors or quietly stores nulls.
    How to recognise it
    The request sets a json_object format, or format json on a local server, and no schema appears anywhere in the call. Failures show up as missing keys and wrong types, not as parse errors.
    How to fix it
    Pass the schema itself through the platform's structured output parameter. Where a model does not support that, keep JSON mode and add schema validation with a bounded retry.

  2. Parsing the reply without first checking for a refusal or a truncated response.

    Why it causes problems
    A refusal and a reply cut off by the token limit are the two documented cases in which the text does not match the schema. The parser throws on them, or reads a partial object, and the real cause is hidden behind a generic JSON error.
    How to recognise it
    Intermittent JSON errors on long outputs or sensitive inputs, and code that reads the output text without looking at the stop reason, the status or the content type.
    How to fix it
    Check the stop reason or status and the refusal signal before parsing. Raise the token limit and retry a truncated reply. Route a refusal to its own handling path.

  3. Skipping your own validation because the platform guarantees the schema.

    Why it causes problems
    The guarantee covers structure. An amount with two digits swapped, a date in the wrong month and an ID that is not in the source all pass. So does output from an engine that silently ignored a constraint it does not support.
    How to recognise it
    No validation runs after parsing, bad records are found later by users or reconciliation jobs, and a minimum or pattern in the schema turns out to have no effect on one of your platforms.
    How to fix it
    Validate every reply against the original schema in code, and add semantic checks for the rules that matter, such as totals, date ranges and IDs that must appear in the input.

  4. Retrying a failed reply with the same prompt and no limit.

    Why it causes problems
    The same input tends to fail in the same way, so a blind retry repeats the failure while each attempt adds latency and cost. With no cap, one difficult document can loop until somebody notices.
    How to recognise it
    Logs show identical invalid replies one after another, retry counts have no upper bound, and failures surface to users as timeouts.
    How to fix it
    Send the validation errors back with the retry, cap attempts at two or three, add a token budget where the library offers one, and return a named failure status when the cap is reached.

  5. Making every field required with no way to say that a value is absent.

    Why it causes problems
    Under a strict schema the model has to produce a value for each required key. When the document holds no such value, the model writes a plausible one, and it arrives looking exactly like real data.
    How to recognise it
    Extracted fields are never empty, even for inputs where a person would leave them blank, and spot checks find values that do not occur anywhere in the source.
    How to fix it
    Keep the key required and allow null, or add an enum value such as unknown, and state in the prompt that null is the correct answer when the information is missing.

  6. Maintaining the JSON Schema by hand next to separate type definitions.

    Why it causes problems
    The schema and the types in the code drift apart. The model then returns objects that match the schema and break the code, or the code expects fields that the schema never asked for.
    How to recognise it
    A field is renamed in one place and not the other, validation is written against a different shape from the one sent to the API, and bugs appear straight after a schema edit.
    How to fix it
    Define the shape once as a Pydantic model or a Zod schema, generate the JSON Schema from it and validate replies with the same definition. OpenAI's guide also suggests a CI rule that flags when the two diverge.

Build a token mask and watch it override the model

CodingIntermediateAbout 40 min (estimate)Hypothetical scenario

A decoder that enforces a constraint needs two things: a way to score tokens and a way to tell which tokens are legal next. Build one for the smallest useful case, a reply that must be one of three exact JSON strings.

Save the starter code as mask_decode.py. The scores function stands in for a model. Given the text so far, it returns a score for a few tokens, and every token it does not mention scores 0.0. You need only the Python standard library.

python
VOCAB = ["Sure", "!", "{", '{"', '"', "label", '":"', "great", "pos", "neg",
         "itive", "ative", "neutral", '"}', "}", "<eos>"]
VALID = ['{"label":"positive"}', '{"label":"negative"}', '{"label":"neutral"}']
MAX_TOKENS = 12


def scores(prefix):
    """Stand-in for a model: fixed preferences that depend on how the text ends."""
    if prefix == "":
        return {"Sure": 3.0, '{"': 2.0, "{": 1.0}
    if prefix.endswith("Sure"):
        return {"!": 3.0}
    if prefix.endswith(("!", "{")):
        return {'{"': 3.0, '"': 2.0}
    if prefix.endswith('{"'):
        return {"label": 3.0}
    if prefix.endswith("label"):

    if prefix.endswith(("great", "itive", "ative", "neutral")):

    return {"<eos>": 3.0}

Add allowed_tokens(prefix), best(candidates, table) and decode(constrained), then run the decoder twice, once without the constraint and once with it.

Requirements

  • allowed_tokens(prefix) returns, in VOCAB order, every token other than <eos> for which the prefix plus the token is the beginning of at least one string in VALID. When the prefix is itself in VALID it returns only <eos>.
  • best(candidates, table) returns the candidate with the highest score, treats a token missing from the table as 0.0, and on a tie returns the candidate that comes first.
  • decode(constrained) builds the text greedily for at most MAX_TOKENS steps and stops when <eos> is chosen. When constrained is true it chooses only among the allowed tokens.
  • In constrained mode, print one line per step showing the token the model wanted, how many tokens were allowed and the token emitted, and count the steps in which exactly one token was allowed.
  • Print both final texts and whether each one is in VALID.

Show solution

The complete file is below. Only allowed_tokens, best, decode and the main block are new.

python
VOCAB = ["Sure", "!", "{", '{"', '"', "label", '":"', "great", "pos", "neg",
         "itive", "ative", "neutral", '"}', "}", "<eos>"]
VALID = ['{"label":"positive"}', '{"label":"negative"}', '{"label":"neutral"}']
MAX_TOKENS = 12


def scores(prefix):
    """Stand-in for a model: fixed preferences that depend on how the text ends."""
    if prefix == "":
        return {"Sure": 3.0, '{"': 2.0, "{": 1.0}
    if prefix.endswith("Sure"):
        return {"!": 3.0}
    if prefix.endswith(("!", "{")):
        return {'{"': 3.0, '"': 2.0}
    if prefix.endswith('{"'):
        return {"label": 3.0}
    if prefix.endswith("label"):
        return {'":"': 3.0}
    if prefix.endswith('":"'):
        return {"great": 3.0, "pos": 2.0, "neutral": 1.0, "neg": 0.5}
    if prefix.endswith("pos"):
        return {'"}': 2.0, "itive": 1.0}
    if prefix.endswith(("great", "itive", "ative", "neutral")):
        return {'"}': 3.0}
    return {"<eos>": 3.0}


def allowed_tokens(prefix):
    """Tokens that keep the text a prefix of at least one valid string."""
    if prefix in VALID:
        return ["<eos>"]
    return [token for token in VOCAB
            if token != "<eos>" and any(text.startswith(prefix + token) for text in VALID)]


def best(candidates, table):
    return max(candidates, key=lambda token: table.get(token, 0.0))  # ties: first in VOCAB order


def decode(constrained):
    prefix, forced = "", 0
    for step in range(1, MAX_TOKENS + 1):
        table = scores(prefix)
        wanted = best(VOCAB, table)
        options = allowed_tokens(prefix) if constrained else VOCAB
        token = best(options, table)
        if constrained:
            forced = forced + (len(options) == 1)
            print(f"{step}: wanted {wanted!r:9} allowed {len(options)}  emitted {token!r}")
        if token == "<eos>":
            break
        prefix = prefix + token
    return prefix, forced


if __name__ == "__main__":
    text, _ = decode(constrained=False)
    print("unconstrained:", text, "| valid:", text in VALID)
    text, forced = decode(constrained=True)
    print("constrained:  ", text, "| valid:", text in VALID, "| forced steps:", forced)

How it works:

  • The mask is a prefix test. A token is legal when the text so far plus that token is still the beginning of some valid string. A production engine asks the same question of a grammar instead of a list, and precomputes the answer for every grammar state so that it does not scan the vocabulary at each step.
  • Token boundaries do not line up with the grammar. At step 1 both { and {" are legal, because the same text can be reached through different tokens. The mask has to test each token's characters, and the one with the higher score wins.
  • Forced steps carry no information. At steps 2, 5 and 7 one token is legal, so the model's scores cannot change the outcome. An engine can emit such tokens without calling the model. The JSONSchemaBench paper reports that one framework, Guidance, generates faster than the unconstrained model by fast-forwarding certain generation steps.
  • Valid is not the same as right. At step 4 the model wanted great, and the mask turned that into pos. At step 5 it wanted to close the string after pos, and the mask forced itive. The result is a legal label. Nothing here checks that it is the correct label for the input, which is why the lesson's pipeline keeps a validation stage after decoding.

  • At step 1, are exactly two tokens allowed, the brace on its own and the brace followed by a quote?
  • Can you explain why the constrained output being valid tells you nothing about whether positive is the right label?

Lint a schema against strict-mode rules and repair it

    "type": "array",

        "type": "object",

Hint 1

Write one generator that yields every subschema with its path and depth. Each rule then becomes a short loop over that list.

Hint 2

Show solution

Save as strict_lint.py and run python3 strict_lint.py.

python
import json

MAX_DEPTH = 10          # OpenAI guide: up to 10 levels of nesting
MAX_PROPERTIES = 5000   # OpenAI guide: up to 5000 object properties in total

DRAFT = {
    "type": "array",
    "items": {
        "type": "object",
        "properties": {
            "verdict": {"type": "string", "enum": ["approve", "reject", "escalate"]},
            "reason": {"type": "string"},
            "amount": {"type": "number", "minimum": 0},
            "currency": {"type": "string"},
            "notes": {"type": "string"},
        },
        "required": ["verdict"],
    },
}


def walk(schema, path="$", depth=1):
    """Yield (path, depth, schema) for the schema and every nested subschema."""
    yield path, depth, schema
    for key, sub in schema.get("properties", {}).items():
        yield from walk(sub, f"{path}.{key}", depth + 1)
    if isinstance(schema.get("items"), dict):
        yield from walk(schema["items"], f"{path}[]", depth + 1)
    for index, sub in enumerate(schema.get("anyOf", [])):
        yield from walk(sub, f"{path}<{index}>", depth)


def strict_problems(schema):
    problems = []
    if schema.get("type") != "object" or "anyOf" in schema:
        problems = [*problems, "$: the root must be an object and must not use anyOf"]
    nodes = list(walk(schema))
    for path, depth, node in nodes:
        if depth > MAX_DEPTH:
            problems = [*problems, f"{path}: nested deeper than {MAX_DEPTH} levels"]
        if node.get("type") != "object":
            continue
        if node.get("additionalProperties") is not False:
            problems = [*problems, f"{path}: additionalProperties must be false"]
        optional = [key for key in node.get("properties", {}) if key not in node.get("required", [])]
        if optional:
            problems = [*problems, f"{path}: not in required: {', '.join(optional)}"]
    total = sum(len(node.get("properties", {})) for _, _, node in nodes)
    if total > MAX_PROPERTIES:
        problems = [*problems, f"$: {total} properties, more than {MAX_PROPERTIES}"]
    return problems


FIXED = {
    "type": "object",
    "properties": {
        "decisions": {
            "type": "array",
            "items": {
                "type": "object",
                "properties": {
                    "reason": {"type": "string", "description": "One or two sentences of evidence."},
                    "verdict": {"type": "string", "enum": ["approve", "reject", "escalate"]},
                    "amount": {"type": ["number", "null"], "description": "Refund amount, or null."},
                    "currency": {"type": ["string", "null"], "description": "ISO 4217 code, or null."},
                    "notes": {"type": ["string", "null"]},
                },
                "required": ["reason", "verdict", "amount", "currency", "notes"],
                "additionalProperties": False,
            },
        },
    },
    "required": ["decisions"],
    "additionalProperties": False,
}


def business_errors(data):
    """Rules kept in code so they hold on every provider."""
    errors = []
    for index, item in enumerate(data["decisions"]):
        if item["amount"] is not None and item["amount"] < 0:
            errors = [*errors, f"decisions[{index}].amount must not be negative"]
        if (item["amount"] is None) != (item["currency"] is None):
            errors = [*errors, f"decisions[{index}]: amount and currency must be set together"]
    return errors


if __name__ == "__main__":
    for problem in strict_problems(DRAFT):
        print("DRAFT", problem)
    print("FIXED problems:", strict_problems(FIXED))
    reply = '{"decisions": [{"reason": "Duplicate charge on the statement.", "verdict": "approve", "amount": -20, "currency": null, "notes": null}]}'
    print(business_errors(json.loads(reply)))

Design decisions in FIXED:

  • Root. The array is wrapped in an object with one key, decisions, because the root has to be an object.
  • Optional values. amount, currency and notes stay in required and accept null. The model can now say that no amount applies without inventing one.
  • Field order. reason comes before verdict, so the evidence is written before the decision it supports. The description asks for one or two sentences, not for step-by-step reasoning.
  • Portability. minimum is removed and the rule moves to business_errors. A constraint enforced in code holds on every platform, including engines that skip unsupported keywords without telling you.
  • A rule the strict subset cannot state. "Amount and currency are set together" relates two fields. Full JSON Schema has conditional keywords for this, such as dependentRequired and if with then, but OpenAI's guide lists them as unsupported in strict mode, so the rule lives in code.

The last line of output shows why the second layer matters: the reply matches FIXED exactly and still breaks two business rules.

Check your answer

  • Does your linter report exactly three problems for DRAFT and an empty list for your rewritten schema?
  • Is every property of every object in your rewritten schema listed in required, including the ones that may be null?
  • Does business_errors return two messages for a reply with an amount of -20 and a null currency?
  • Can you name the rule in your solution that relates two fields, and say why it is enforced in code and not in the strict schema?
