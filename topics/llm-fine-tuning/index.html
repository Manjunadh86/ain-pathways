Fine-Tuning LLMs

Fine-tuning continues the training of a pretrained language model on a curated set of example inputs and desired outputs, so that the new behaviour lives in the model's weights instead of being repeated in every prompt. Parameter-efficient methods such as LoRA train a small set of added weights and leave the original model frozen.

1Overview

Why it matters

Fine-tuning usually takes the most effort of the three ways to change what a model does, so choosing it for the wrong problem wastes weeks. Teams reach for it to teach a model new facts and find the answers are still out of date, or they tune on a few hundred noisy examples and ship a model that is worse than the prompt it replaced. Knowing which failures training can fix, and which belong to the prompt or to retrieval, decides whether the project works at all.

Anyone who owns an LLM feature meets this decision: a prompt has grown to dozens of examples, an output format breaks on some calls, a small model has to match a large one on a narrow task, or prompt tokens have become the biggest line on the bill. A tuned model also brings obligations that a prompt does not: a dataset to curate, an evaluation to rerun, and a model or adapter to retrain whenever the base model changes.

  • Turn raw examples into a clean chat-format JSONL training set with separate training, validation and test splits.
  • Explain how LoRA adds trainable low-rank matrices to frozen weights, and compute the trainable parameters for a given rank.
  • Estimate GPU memory for full fine-tuning, LoRA and QLoRA from a model's parameter count.
  • Evaluate a tuned model against a prompted baseline on held-out data and read training and validation loss curves.
  • List the recurring costs of a tuned model and the events that force retraining.

Key terms

Supervised fine-tuning (SFT)
Further training on pairs of a prompt and the reply you want, so the model learns to produce that kind of reply. It is the method this lesson covers.
Base model
The pretrained model you start from. A fine-tuned model or an adapter is tied to one specific version of it.
Epoch
One complete pass of the training process over every example in the training set.
Held-out set
Examples kept out of training. A validation set guides choices such as the stopping point; a test set is used once at the end to report the result.
Overfitting
Fitting the training examples so closely that performance on new inputs gets worse. Training loss keeps falling while validation loss rises.
LoRA (low-rank adaptation)
A parameter-efficient method that freezes the original weights and trains two small matrices whose product is added to a layer's output.
Rank (r)
The inner size of the two LoRA matrices. A higher rank means more trainable parameters and more capacity to change the model.
Adapter
The small set of trained weights that LoRA produces. It can be stored on its own, swapped at run time or merged into the base weights.
QLoRA
LoRA training on top of a base model stored in 4-bit precision, which cuts the memory needed to hold the frozen weights.
Catastrophic forgetting
Loss of abilities the base model had before training, because the new data pushed the weights away from what supported them.

2Explanation

Introduction

You have already met two ways to change how a model behaves. In Prompt Engineering you changed the instructions and examples inside the request. In Retrieval-Augmented Generation you changed the facts placed inside the request. In both cases the model itself stayed the same, so everything it needed had to travel with every call.

Fine-tuning is the third option, and it changes the model. You collect examples of the inputs real users send and the outputs you would want back, then continue training a pretrained model on them. Afterwards, behaviour that used to need a long prompt, such as a house style, a strict output schema or a classification rule, comes from the model's weights.

An analogy: a new employee can be handed a binder of reference material to look things up (retrieval), a page of instructions and sample answers for each task (prompting), or months of practice until the work becomes habit (fine-tuning). Practice does not help when the answer depends on today's price list, because the price list changes after the practice ends. It helps a great deal when the problem is doing the same kind of task the same way every time. OpenAI's guide to optimizing LLM accuracy (opens in a new tab) separates the two kinds of failure in the same way: a model that lacks or has out-of-date knowledge needs better context, and a model that behaves inconsistently needs to be optimised itself.

Updating every weight of a modern model needs a lot of GPU memory, so parameter-efficient fine-tuning (PEFT), and LoRA in particular, is a common choice. This lesson covers when to fine-tune at all, how to prepare training examples, how LoRA and QLoRA work and what they save, how to evaluate a tuned model, and what it costs to keep one running.

How it works

What training changes

Supervised fine-tuning (SFT) keeps the pretraining objective, predicting the next token, but narrows the data. Each example is a prompt plus the reply you want. The loss is the average negative log-probability of the reply's tokens given everything before them, which the TRL documentation (opens in a new tab) writes as a token-level cross-entropy. Libraries can mask the prompt so that only the reply is scored: TRL does this by default for prompt-completion data and with assistant_only_loss=True for chat data.

Hosted services wrap the same idea: you upload a training file and a validation file, pick a base model and get back a model identifier. Microsoft Foundry's overview (opens in a new tab) also lists other training signals: preference tuning (DPO), which learns from preferred and rejected replies, and reinforcement fine-tuning, which learns from a grader's scores. SFT is the place to start because it only needs examples of good output. Check that a provider still accepts new jobs before you plan around it: OpenAI's guide (opens in a new tab) says it is winding down its fine-tuning platform, which is closed to new users.

Fine-tune, prompt or retrieve?

Start from the kind of failure your evals show.

Failure in the evalsLikely causeFirst thing to try
Wrong, outdated or unknown facts, or private data the model never sawMissing contextRetrieval
Facts are right but tone, format or reasoning varies from call to callBehaviour the model has not learnedA stronger prompt, then fine-tuning
Quality is fine but the prompt is long, slow and costlyBehaviour carried in the prompt instead of the modelFine-tune, possibly a smaller model

The evidence behind this split is consistent. OpenAI's guide (opens in a new tab) separates context problems (missing or out-of-date knowledge) from behaviour problems (inconsistent format, wrong tone, reasoning not followed), names prompt engineering as the usual place to start, and says the two methods are additive rather than exclusive, so evals that show both kinds of problem can call for fine-tuning plus RAG. Ovadia and colleagues compared unsupervised fine-tuning with RAG (opens in a new tab) on knowledge-intensive tasks and found RAG consistently better, with models struggling to learn new facts from fine-tuning alone. In an agriculture study the gains from fine-tuning and from RAG added up (see the examples below). The usual answer is retrieval for the facts and fine-tuning for the habits.

Preparing training examples

Data quality usually matters more than any training setting.

  • Format. Chat services expect JSONL: one JSON object per line, each with a messages list of system, user and assistant turns. TRL also accepts prompt-completion pairs.
  • Realism. OpenAI asks for prompts and outputs that are as realistic as possible for what the application will see. A practice we recommend (it is not from OpenAI's guide) is to put the production system prompt in every example, so the model trains under the conditions it will run in.
  • Quality over quantity. OpenAI's guide (opens in a new tab) sets a minimum of 10 examples, recommends starting with 50 well-crafted ones, and says to rethink the task or prompt if 50 have no effect. The LIMA (opens in a new tab) paper fine-tuned a 65B model on 1,000 curated examples, and the QLoRA (opens in a new tab) paper reports a 9k-example set beating a 450k-example one on chatbot quality.
  • Consistency. The model copies what the data does, including contradictory labels and sloppy replies. Read a sample, remove duplicates and fix labels.
  • Splits. Keep validation and final test examples out of training. Split before you paraphrase or augment, and keep related examples (same document, same customer, near-duplicates) in one split, otherwise leakage inflates the test score.
  • Sensitive data. Training data is copied into a training pipeline, so remove or mask personal information first.

LoRA: train a small correction

Full fine-tuning updates every weight. LoRA freezes each adapted weight matrix W0W_0W0​ (shape d×kd \times kd×k) and learns a correction as the product of two thin matrices, BBB (d×rd \times rd×r) and AAA (r×kr \times kr×k), where the rank rrr is far smaller than ddd and kkk:

h=W0x+αrBAxh = W_0 x + \frac{\alpha}{r} B A xh=W0​x+rα​BAx

The constant α\alphaα scales the correction (PEFT also offers a rank-stabilised variant, use_rslora=True, that divides by r\sqrt{r}r​ instead of rrr). In the original paper (opens in a new tab) AAA starts with random Gaussian values and BBB starts at zero, so training begins exactly at the base model's behaviour; PEFT's default draws AAA from a Kaiming-uniform distribution instead and also keeps BBB at zero. One pair has r(d+k)r(d+k)r(d+k) trainable parameters instead of dkdkdk: for d=k=4096d = k = 4096d=k=4096 and r=8r = 8r=8 that is 65,536 instead of 16,777,216, or 0.39%.

For GPT-3 175B the paper reports 10,000 times fewer trainable parameters and 3 times less GPU memory than full fine-tuning, with quality on par or better on the models it tested. It adds no inference latency, because αrBA\frac{\alpha}{r}BArα​BA can be merged into W0W_0W0​ after training (PEFT calls this merge_and_unload() (opens in a new tab)), or the adapter can stay separate so it can be swapped.

You choose which layers to adapt (target_modules in PEFT; attention blocks are typical, and Apple's adapters also cover feed-forward layers), the rank and α\alphaα. Because only new parameters are learned, TRL notes that adapters usually take a higher learning rate, around 1e-4.

Two trade-offs matter. First, LoRA is not free quality: for programming and mathematics, Biderman and colleagues (opens in a new tab) found that LoRA substantially underperformed full fine-tuning under standard low-rank settings, while forgetting less of what the base model knew. Second, an adapter belongs to one base model. PEFT saves only the adapter, which for a model with roughly 700MB of weights was about 6.3MB, and Foundry warns that an adapter is not interchangeable across similarly named base models.

QLoRA keeps the frozen base model in 4-bit NormalFloat precision and trains LoRA adapters on top, with double quantization and paged optimizers to absorb memory spikes. Its authors fine-tuned a 65B model on one 48GB GPU, where regular 16-bit fine-tuning of that model needs more than 780GB.

Evaluating a tuned model

A falling training loss only shows that the model fits your data. To decide whether the product got better:

  1. Fix the test set before training and never tune on it. Score it with checks that fit the task: exact match or schema validation for classification and extraction, a rubric or model grader for free text (see Evaluating LLM Applications and LLM-as-a-Judge).
  2. Compare with the strongest prompted baseline: base model, best prompt, few-shot examples included. Compare cost and latency as well, because a smaller tuned model that matches a larger prompted one is a win at equal accuracy.
  3. Read the curves. Platforms report training and validation loss and token accuracy per epoch or checkpoint. When training loss keeps falling while validation loss rises, the model is memorising, so choose the checkpoint from before the turn.
  1. Check what training may have broken. Qi and colleagues (opens in a new tab) fine-tuned GPT-3.5 Turbo on 10 adversarial examples for under 20 US cents and the model then complied with harmful requests; they also found that benign datasets erode alignment to a lesser degree. Rerun your safety and regression sets on the tuned model.
  2. Read failures. Sample wrong outputs from the test set by hand; they usually point to a labelling or coverage problem in the data.

Cost and maintenance

  • Data. Collecting, reviewing and relabelling examples is usually the largest human cost, and it repeats when the task changes.
  • Training runs. Compute grows with tokens in the dataset times epochs, and you will run several experiments. Microsoft advises budgeting for repeated runs, evaluation, hosting and inference.
  • Serving. Hosted fine-tuned models can carry hosting charges, and cancelling a training job does not stop deployment charges. Self-hosted adapters let one base model serve many tasks.
  • Maintenance. A tuned model is tied to a base-model snapshot. Apple says adapters must be retrained with each new base model version, and OpenAI's deprecation page (opens in a new tab) says fine-tuned models stay available for inference only until their base model is deprecated. The provider's offer can change too: the same page records OpenAI closing self-serve fine-tuning in stages, to new organisations first and, from 6 January 2027, to existing customers, and AWS's Claude 3 Haiku fine-tuning walkthrough now carries a banner saying that model reached end of life on 10 September 2026 (see the first example). Keep the dataset, the training configuration and the eval set under version control so that a retrain is a rerun and not a project.

A rough break-even rule: fine-tuning pays off when (cost saved per request times requests over the model's lifetime) exceeds (data plus training plus evaluation plus hosting plus retraining). Savings normally come from shorter prompts or a cheaper model, and the size of the saving is yours to measure.

Worked example: Clean a ticket dataset, then size a LoRA run for a 7B model

A support team wants a small model that labels tickets as billing, bug or how_to. The tickets are invented for this lesson, but every number below is printed by the code, which needs only the Python standard library.

Step 1: clean, deduplicate and split

python
import hashlib, json

SYSTEM = "Classify the support ticket as billing, bug, or how_to. Reply with the label only."
LABELS = {"billing", "bug", "how_to"}
RAW = [
    ("I was charged twice for my March invoice.", "billing"),
    ("The export button does nothing when I click it.", "bug"),
    ("How do I add a teammate to my workspace?", "how_to"),
    ("Please refund the duplicate payment on my card.", "billing"),
    ("The app crashes when I upload a PDF.", "bug"),
    ("Where can I change the notification schedule?", "how_to"),
    ("i was charged twice for my march invoice.  ", "billing"),
    ("Why is my plan price higher this month?", "billing"),
    ("Search returns an error 500 for any query.", "bug"),
    ("Can I rename a project after creating it?", "how_to"),
    ("Dark mode resets every time I log in.", "Bug "),
    ("What does the Reports tab show?", ""),
    ("Invoice PDF shows the wrong company name.", "billing"),
    ("The mobile app freezes on the login screen.", "bug"),
    ("How do I export my data to CSV?", "how_to"),
]

def normalise(text):
    return " ".join(text.lower().split())

seen, rows, dropped = set(), [], []
for text, label in RAW:
    label = label.strip().lower()
    if label not in LABELS:
        dropped.append((text, "bad label"))
    elif normalise(text) in seen:
        dropped.append((text, "duplicate"))
    else:
        seen.add(normalise(text))
        rows.append({"messages": [
            {"role": "system", "content": SYSTEM},
            {"role": "user", "content": text.strip()},
            {"role": "assistant", "content": label},
        ]})

# Order by a hash of the ticket text: stable, and independent of file order.
rows.sort(key=lambda r: hashlib.sha256(r["messages"][1]["content"].encode()).hexdigest())
n_eval = max(1, round(0.15 * len(rows)))
split = {"train": rows[:-2 * n_eval], "validation": rows[-2 * n_eval:-n_eval], "test": rows[-n_eval:]}

print("kept", len(rows), "of", len(RAW), "dropped:", [reason for _, reason in dropped])
print({name: len(items) for name, items in split.items()})
print(json.dumps(split["train"][0]))

Output:

text

{'train': 9, 'validation': 2, 'test': 2}
{"messages": [{"role": "system", "content": "Classify the support ticket as billing, bug, or how_to. Reply with the label only."}, {"role": "user", "content": "Invoice PDF shows the wrong company name."}, {"role": "assistant", "content": "billing"}]}

The lower-case ticket about being charged twice repeats the first row once case and spacing are normalised, so it is dropped. If both stayed, a random split could put one copy in training and the other in the test set, and the test score would reward memorising. The Reports-tab ticket has no label and is dropped, while the dark-mode ticket has the label Bug and is cleaned to bug. Sorting on a hash of the ticket text keeps the split stable when someone reorders the file. Thirteen examples only demonstrate the mechanism: OpenAI suggests starting with 50 well-crafted examples, and a two-example validation set is too small to trust.

Step 2: size the adapter and estimate memory

python
def lora_params(d_out, d_in, r):
    return r * (d_out + d_in)              # B is d_out x r, A is r x d_in

layers, hidden, r = 32, 4096, 8            # assumed 7B-class shape; LoRA on q_proj and v_proj
base = 6_738_415_616                       # parameters of the frozen model (the size of Llama 2 7B)
adapter = layers * 2 * lora_params(hidden, hidden, r)
print(adapter, f"{adapter / base:.4%}", adapter * 2, "bytes at 16-bit")

# Bytes per parameter: weights 2, gradients 2, two fp32 Adam moments 8 (activations ignored)
GB = 1e9
full = base * (2 + 2 + 8) / GB
lora = (base * 2 + adapter * (2 + 2 + 8)) / GB
qlora = (base * 0.5 + adapter * (2 + 2 + 8)) / GB
print(f"{full:.1f} {lora:.2f} {qlora:.2f}")

# Cross-check with the PEFT quicktour: Llama-3.2-1B, default LoRA (r=8) on q_proj and v_proj.
# Hidden size 2048, 16 layers, v_proj maps 2048 -> 512 (8 key/value heads of size 64).
print(16 * (lora_params(2048, 2048, 8) + lora_params(512, 2048, 8)))

Output:

text

851968
  • Each adapted 4096 by 4096 matrix gets 8 x (4096 + 4096) = 65,536 trainable parameters. Two matrices per layer across 32 layers give 4,194,304, which is 0.0622% of the base model and 8.4 MB at 16 bits per value.
  • The third line is a cross-check. The PEFT quicktour prints 851,968 trainable parameters for Llama-3.2-1B with the default LoRA configuration, and the formula r(d+k)r(d+k)r(d+k) reproduces it exactly.
  • The memory model charges 12 bytes per fully trained parameter: 2 for the 16-bit weight, 2 for its gradient and 8 for two 32-bit Adam moments. For a 65B model that gives 780 GB, consistent with the QLoRA paper's statement that 16-bit fine-tuning of a 65B model needs more than 780 GB. With LoRA only the adapter needs gradients and optimizer state, so the 13.53 GB is almost all frozen weights. With QLoRA the frozen weights shrink to about half a byte each, giving 3.42 GB.

These are lower bounds: activations, quantization constants and framework overhead come on top and grow with batch size and sequence length. The result is still the practical point of LoRA: model state that needs about 81 GB under full fine-tuning fits in about 14 GB with LoRA or 3.4 GB with QLoRA, at the price of the quality trade-offs described above.

Edge cases and limitations

Fine-tuned facts go stale and are hard to correct
A model trained on a product catalogue knows the catalogue as it was on the training date. When a price or policy changes you must retrain, while a retrieval index changes by editing a document. Ovadia and colleagues found that models learn new facts poorly from fine-tuning alone. The sign is a tuned model that answers confidently with last quarter's values; move the facts to retrieval and keep tuning for format and tone.
Leakage makes the validation score useless
Templated tickets, paraphrases of one document or one customer's messages spread across splits let the model memorise test items. The sign is a validation or test score near perfect on a model that performs poorly on fresh production inputs. Split by source (document, customer, template) before augmenting, and keep one final test set that nobody looks at while tuning.
General ability and safety can regress
Training pulls the weights toward your data. Qi and colleagues showed that a few adversarial examples, and to a lesser degree ordinary datasets, weaken safety behaviour. Biderman and colleagues found LoRA forgets less than full fine-tuning, which still means it forgets some. Run a fixed regression set of general tasks and safety prompts on every candidate, not only the task you tuned for.
Low rank can be too little capacity
On programming and mathematics, Biderman and colleagues found that LoRA underperformed full fine-tuning in standard low-rank settings, and that full fine-tuning learned weight changes of much higher rank. When a rank-8 adapter plateaus below your target, try a higher rank, more layers in target_modules or better data before you conclude that the approach has failed.
The tuned model dies with its base model
A tuned model is bound to one base version. Apple states that adapters must be retrained with each new base model version, and OpenAI says fine-tuned models remain available for inference only until their base model is deprecated. One of the examples on this page shows the pattern: Claude 3 Haiku could be fine-tuned in Amazon Bedrock from 2024, and AWS now lists it as end of life on 10 September 2026. Treat the dataset, configuration and eval set as the durable asset, and track the provider's deprecation notices.
A format problem may not need training
If the only failure is that output sometimes breaks a JSON schema, try structured outputs or constrained decoding first (see [Structured Outputs](/topics/structured-outputs/)). They enforce the shape without training data, and fine-tuning can then concentrate on the quality of the content.

When to use it, and when something simpler is enough

Use it when

  • Evals show inconsistent format, tone or task behaviour that a well-written prompt with examples has not fixed.
  • The prompt carries many examples or long instructions, and moving that behaviour into the model would cut tokens per request enough to repay training at your traffic.
  • A smaller, cheaper model must match a larger one on a narrow, stable task, and you can produce hundreds of verified examples, for instance by having a larger model draft replies that people check.
  • You can state a held-out test set and a baseline score before training starts.

Think twice when

  • The failure is missing, private or fast-changing knowledge; use retrieval, so that an update is an index change rather than a training run.
  • You have no eval set, or too few trustworthy examples; OpenAI suggests starting at about 50, so build the evals and the prompt first.
  • The task definition still changes every week, because each change invalidates the dataset.
  • Policy forbids sending the data to a training service and you cannot run the training yourself.

A simpler alternative. A better prompt with a few well-chosen examples and structured outputs, optionally with retrieval for facts. Move to fine-tuning only when evals show the failure is behavioural and a strong prompted baseline has plateaued or costs too much per request.

Key takeaways

  • Fine-tuning changes how a model behaves, not what it can look up, so use retrieval for missing or changing facts and fine-tuning for consistent style, format and task skill.
  • Dataset quality and a held-out test set decide the outcome; start with about 50 carefully checked examples, evaluate, and add data only if the evals call for it.
  • LoRA freezes the base weights and trains two small matrices per adapted layer, which cut trainable parameters to 0.06% in the 7B example here, and QLoRA also stores the frozen model in 4-bit form.
  • Judge a tuned model against the best prompted baseline on unseen data, keep the checkpoint with the best validation result, and test for regressions in general ability and safety.
  • A tuned model has recurring costs in data upkeep, training reruns, serving and evaluation, and it must be retrained when its base model version changes.

Example 1 of 5

Fine-tuning Claude 3 Haiku in Amazon Bedrock, with a telecom support case

Anthropic and Amazon Web Services (Claude 3 Haiku on Amazon Bedrock)Documented in a case study

Anthropic's announcement of fine-tuning for Claude 3 Haiku in Amazon Bedrock (10 July 2024) and the AWS Machine Learning Blog walkthrough published the same day describe how customers train the model on their own prompt-completion pairs. Anthropic quotes SK Telecom, a South Korean telecommunications operator, on a custom Claude model for support workflows; the page does not say which Claude model it was. The AWS page now carries a banner saying Claude 3 Haiku reached end of life on 10 September 2026. [15][16][17]

The problem

A general-purpose model answers in a general voice, and a team that wants its own formats, vocabulary and standards has to repeat long instructions in every prompt. The announcement presents fine-tuning as the way to get better results on specialised tasks, naming classification, custom API interactions and industry-specific data interpretation, and says it can also produce consistently structured outputs.

Where this topic fits

Fine-tuning comes after the team has gathered high-quality prompt-completion pairs, the replies it wants the model to give for each kind of request, and before the customised model is deployed. In Anthropic's announcement the training data stays in the customer's AWS environment, and AWS's walkthrough serves the result through Provisioned Throughput.

How it is applied, step by step

  1. Collect prompt-completion pairs: for each kind of support request, the reply an expert would want sent. AWS suggests starting with 50 to 100 high-quality rows and iterating on evaluation.
  2. Write them as JSON Lines in the Messages API layout the AWS walkthrough describes, with optional system text and alternating user and assistant messages. AWS caps training data at 10,000 records and validation data at 1,000.
  3. A typical team then reviews the pairs by hand for accuracy and consistent tone, and holds a test set back from both files.
  4. Create the customisation job in Amazon Bedrock. AWS says validation loss is computed at the end of each epoch and training stops early when it stops improving.
  5. A typical team compares the customised model with the base model on the held-out requests, using its own metrics and feedback from agents.
  6. To serve the model, buy Provisioned Throughput, which AWS says is billed hourly, so the support traffic has to justify a standing charge.
  7. A typical team plans for the base model's end of life: AWS now shows Claude 3 Haiku as end of life, so the same dataset has to be rerun on a newer base model and the comparison repeated.

Why this approach fits

Support replies need a consistent voice and vocabulary, which are easier to show with examples than to describe in a prompt. Training moves that behaviour into the model, so each request needs less prompt text; the announcement's comment-moderation example, with 85% fewer tokens per query, follows the same pattern on a classification task. Because the training data stays in the customer's cloud account, the approach also suits teams with data-handling rules.

Limitation or tradeoff

This is a vendor announcement and a vendor how-to, not an evaluation. SK Telecom's two percentages are a quoted statement with no stated test set, baseline prompt or definition of the feedback and KPIs, and the page does not name the Claude model it used, so they show direction but cannot be reproduced. The 81.5% to 99.6% figures come from an example Anthropic ran itself. The model has also aged out: Anthropic retired Claude Haiku 3 on its own platforms on 20 April 2026 (partner platforms set their own schedules) and AWS shows end of life on 10 September 2026. A customised model is tied to its base, and Provisioned Throughput is billed hourly, so the tuned model carries a standing serving cost.

Example 2 of 5

Apple's on-device model specialised with swappable LoRA adapters

AppleDocumented in an engineering article

Apple Machine Learning Research posts from June 2024 and June 2025 describe a language model of about three billion parameters that runs on the device and is specialised for individual features with small LoRA adapters, and explain how developers can train their own adapters. [18][19][6]

The problem

One small model on a phone has to serve many different features, such as summarisation, and memory and storage are limited. Keeping a separate fully tuned copy of the model for every feature would multiply storage and memory use, so the specialisation has to be small and loadable on demand.

Where this topic fits

LoRA adapters sit on top of the pretrained base model after its training and before release. At run time the system selects the adapter for the task at hand, so the large base weights stay resident and only small task weights change.

How it is applied, step by step

  1. Start from the on-device language model of about three billion parameters, whose weights stay fixed while an adapter is trained for one feature.
  2. Train a small adapter per feature on feature-specific data. It modifies the attention matrices, the attention projection matrix and the feed-forward layers of a chosen set of decoder layers.
  3. Keep the adapter separate from the base weights. For a rank-16 adapter on the three-billion-parameter model this is tens of megabytes.
  4. At run time load the adapter for the task at hand, cache it temporarily and swap it when the task changes, so a single base model serves many features.
  5. Evaluate each adapter on samples drawn for its use case before release. For summarisation Apple used 750 responses sampled for each use case.
  6. Retrain the adapter whenever the base model version changes. Apple's 2025 update states that adapters must be retrained with each new version of the base model.

Why this approach fits

With LoRA the expensive part of the model is shared and each feature adds only an adapter, so adding a feature costs megabytes of storage and a load, not another copy of the model. Because training touches only the adapter, each feature can be retrained and evaluated on its own data without disturbing the others.

Limitation or tradeoff

The adapters are bound to one base model version, and Apple advises exploring what the base model can already do before building an adapter, because every base update means retraining each adapter and re-running its evaluation. The quality figures in the 2024 post are Apple's own and use Apple's evaluation sets, so they are not a benchmark you can reproduce.

What the sources document

The problem

A team wants a model to answer location-specific farming questions from a body of PDF documents. The knowledge can be put in the prompt through retrieval, put in the weights through fine-tuning, or both, and the team needs measurements to choose between them rather than an opinion.

Where this topic fits

This is the decision step that opens the lesson. The same question set is scored with and without retrieval for both the base and the fine-tuned model, and the fine-tuning data is generated from the same kind of documents that retrieval searches, so the comparison separates what each technique adds.

How it is applied, step by step

  1. Extract text and information from the agricultural PDFs.
  2. Generate question-answer pairs from the documents with LLMs, both as fine-tuning data and as ground-truth questions for evaluation; the paper describes about 270 GPT-4-generated ground-truth pairs in its evaluation section.
  3. Fine-tune models on question-answer data derived from the documents (the paper tunes Llama2 models and GPT-4 among others), and separately give models retrieved passages at question time.
  4. Score answers with a GPT-4 grader under four conditions: base model, retrieval only, fine-tuning only and both.
  5. Read the effects as differences between conditions. For GPT-4 the paper's results table lists accuracy of 75% for the base model, 80% with RAG, 81% fine-tuned and 86% fine-tuned with RAG, and the abstract summarises the gains as over 6 percentage points from fine-tuning, cumulative with 5 more from RAG.

Whether knowledge belongs in the prompt or in the weights is an empirical question that depends on the data and the model, and a four-condition comparison shows each contribution and whether they add up. Limitation or tradeoff

The authors name the high initial cost of fine-tuning on new data as a significant consideration, note that the correctness of technical answers is hard for non-experts to judge, and describe their work as a baseline. Ground truth and grading both rely on GPT-4, so its errors and style can leak into the scores, and the gains are percentage points on one agricultural question set. Ovadia and colleagues tested unsupervised fine-tuning on text, a different setup from question-answer fine-tuning, so the two results are not directly comparable.

4Common mistakes

  1. Fine-tuning a model to teach it facts that change

    Why it causes problems
    The model keeps answering with the values it saw in training. Every update means a new training run and evaluation, and the model can still blend old and new facts.
    How to recognise it
    A tuned model quotes last quarter's price or policy with confidence, or retrieval of the same document gives a different answer to the tuned model's.
    How to fix it
    Put changing facts behind retrieval and tune only the behaviour, such as answering in the house format from the retrieved text. Use the failure table in this lesson to classify the problem before collecting data.

  2. Evaluating on data that overlaps with the training set

    Why it causes problems
    The score measures memory, not skill. A model can look nearly perfect on validation and still fail on new production inputs, and the team ships on false confidence.
    How to recognise it
    Validation or test accuracy is far higher than the live acceptance rate, or the same message appears in two splits with only case or punctuation changed.
    How to fix it
    Normalise and deduplicate before splitting, group near-duplicates and related items (same document, customer or template) into one split, and keep a final test set that is only scored once.

  3. Comparing the tuned model with a weak prompt instead of the best prompt

    Why it causes problems
    The project pays for data, training and hosting to win a gain that a stronger prompt, a few examples or structured outputs would have delivered for free.
    How to recognise it
    The baseline prompt is one line, has no examples, and was never iterated on, or no one has measured the base model with its best prompt.
    How to fix it
    Spend a day on the baseline first. Score the best prompt on the same held-out set, then require the tuned model to beat it by a margin that repays the full cost of the project.

  4. Training for many epochs and shipping the final checkpoint

    Why it causes problems
    Later epochs fit the quirks of the training set. Validation quality falls while training loss keeps improving, so the shipped model is worse than an earlier checkpoint.
    How to recognise it
    Training loss falls every epoch while validation loss or validation token accuracy turns the wrong way, or the model repeats training phrasing in unrelated answers.
    How to fix it
    Hold out a validation file, compare checkpoints on validation metrics and on the task test set, and keep the best one. Start with the platform's default epochs and learning rate.

  5. Letting the training data disagree with itself and with production

    Why it causes problems
    The model learns every contradiction. Mixed label spellings, different system prompts and sloppy replies produce an inconsistent model that no hyperparameter will repair.
    How to recognise it
    Outputs vary across runs on near-identical inputs, or a hand review of 30 random training rows finds more than a few wrong labels or mismatched formats.
    How to fix it
    Review a random sample of the dataset by hand before every run, fix labels at the source, and use the production system prompt and message format in every training example.

  6. Having no plan for the base model's retirement

    Why it causes problems
    Fine-tuned models and adapters depend on one base version. When it is deprecated, inference stops or quality drifts, and a team with no saved dataset or configuration must rebuild from scratch.
    How to recognise it
    The training data lives only in a vendor console, no one owns the eval set, and the provider's deprecation notices are not tracked.
    How to fix it
    Keep the dataset, the training configuration and the eval set in version control, record the base model version with every tuned model, and schedule a retrain-and-compare step when the provider announces a deprecation.

python
import hashlib
import json
import re

SIZES = {"small", "medium", "large"}
RAW = [
    ("two large oat lattes please", '{"item": "oat latte", "qty": 2, "size": "large"}'),
    ("One small espresso", '{"item": "espresso", "qty": 1, "size": "small"}'),
    ("3 medium chai lattes", '{"item": "chai latte", "qty": 3, "size": "medium"}'),
    ("Two large oat lattes, please!", '{"item": "oat latte", "qty": 2, "size": "large"}'),
    ("A medium americano for me", '{"item": "americano", "qty": 1, "size": "medium"}'),
    ("One small espresso please", '{"item": "espresso", "qty": 1, "size": "small"}'),
    ("4 large flat whites", '{"item": "flat white", "qty": 4, "size": "large"}'),
    ("I'd like a large mocha", '{"item": "mocha", "qty": 1, "size": "large"}'),
    ("two medium teas", 'Sure! {"item": "tea", "qty": 2, "size": "medium"}'),
    ("a small hot chocolate", '{"item": "hot chocolate", "qty": "one", "size": "small"}'),
    ("5 small cortados", '{"item": "cortado", "qty": 5, "size": "small"}'),
    ("one extra-large latte", '{"item": "latte", "qty": 1, "size": "xl"}'),
    ("Two medium oat lattes", '{"item": "oat latte", "qty": 2, "size": "medium"}'),
    ("3 large chai lattes", '{"item": "chai latte", "qty": 3, "size": "large"}'),
]

def words(text):
    return re.findall(r"[a-z0-9']+", text.lower())

def valid(reply):
    try:
        obj = json.loads(reply)
    except json.JSONDecodeError:
        return False
    return (isinstance(obj, dict) and set(obj) == {"item", "qty", "size"}
            and isinstance(obj["item"], str) and type(obj["qty"]) is int and obj["size"] in SIZES)

def jaccard(a, b):
    return len(set(a) & set(b)) / len(set(a) | set(b))

rows, dropped, seen = [], [], set()
for text, reply in sorted(RAW, key=lambda pair: (" ".join(words(pair[0])), pair[0])):
    key = " ".join(words(text))
    if not valid(reply):
        dropped.append((text, "invalid reply"))
    elif key in seen:
        dropped.append((text, "duplicate"))
    else:
        seen.add(key)
        rows.append({"text": text, "reply": reply, "words": words(text)})

# Group near-duplicates (Jaccard >= 0.7) so a group never straddles two splits.
group = list(range(len(rows)))
def find(i):
    while group[i] != i:
        i = group[i]
    return i
for i in range(len(rows)):
    for j in range(i + 1, len(rows)):
        if jaccard(rows[i]["words"], rows[j]["words"]) >= 0.7:
            group[find(j)] = find(i)
clusters = {}
for i, row in enumerate(rows):
    clusters.setdefault(find(i), []).append(row)

def order(cluster):
    key = min(" ".join(row["words"]) for row in cluster)
    return hashlib.sha256(key.encode()).hexdigest()

n_eval = max(1, round(0.15 * len(rows)))
split = {"test": [], "validation": [], "train": []}
for cluster in sorted(clusters.values(), key=order):
    name = "test" if len(split["test"]) < n_eval else "validation" if len(split["validation"]) < n_eval else "train"
    split[name].extend(cluster)

print("kept", len(rows), "of", len(RAW), "dropped:", [reason for _, reason in dropped])
print("clusters:", len(clusters), {name: len(items) for name, items in split.items()})
for name, items in split.items():
    print(name, [r["text"] for r in items])

Choices.

  • A: retrieval. The fee table changes monthly, so the facts must live in an index. The eval that would change this is a failure that persists with the correct table in the prompt, for example wrong rounding or format, which would then be a behaviour problem.
  • B: fine-tuning, after a baseline with schema-constrained output. Invalid JSON is a format failure, and 800 reviewed examples are enough to test a tuned model. If constrained output removes the failures, keep it and tune only if content quality still lags.
  • C: retrieval for the weekly documents plus a prompt with a few style examples. Tune for style only if evals show the prompt cannot hold the voice, and only on style data that does not contain document facts.

Sizing for B.

python
layers, hidden, r = 24, 2048, 16
base = 1_000_000_000
per_matrix = r * (hidden + hidden)          # B is 2048 x 16, A is 16 x 2048
adapter = layers * 4 * per_matrix           # q, k, v, o in every layer
print("per matrix", per_matrix, "adapter", adapter, f"share {adapter / base:.3%}")
GB = 1e9
full = base * 12 / GB
lora = (base * 2 + adapter * 12) / GB
qlora = (base * 0.5 + adapter * 12) / GB
print(f"full {full:.2f} GB, lora {lora:.2f} GB, qlora {qlora:.2f} GB")
print("adapter file at 16-bit:", adapter * 2 / 1e6, "MB")

The estimate counts weights, gradients and optimizer state only. Activations, quantization constants, the framework and the batch all add memory on top.

Evaluation plan for B.

  • Split the 800 examples as 600 train, 100 validation and 100 test, grouping near-duplicates and examples from the same customer into one split.
  • Baseline: the base model with the best prompt and with schema-constrained output, scored on the 100 test examples before any training.
  • Metrics: the share of replies that validate against the schema, and field-level exact match against the reviewed answer.
  • Pass criterion, set before training: at least 99% schema validity and field-level exact match at least 3 points above the baseline on the test set, with no drop on a fixed set of 50 unrelated general prompts.
  • Choose the checkpoint with the best validation score, then score the test set once.
  • Regression check: rerun the safety prompts the product already uses and compare refusals with the base model.

Check your answer

  • Did you classify A, B and C by the kind of failure, not by which technique sounds most advanced?
  • Do you get 65,536 trainable parameters for one 2048 by 2048 matrix at rank 16, and 6,291,456 in total?
  • Is your pass criterion a number fixed before training, measured on data the model never trained on?
  • Does your plan include a baseline, a held-out test set and a regression check?
