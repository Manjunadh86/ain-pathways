Handling Imbalanced Data

A dataset is imbalanced when one class is far rarer than the other, such as 2 fraudulent payments in every 100. Handling it means measuring the model with metrics that reflect the rare class and, where needed, changing the training data, the loss or the decision threshold so that rare cases are not ignored.

1Overview

Why it matters

The cases worth predicting are usually the rare ones: a fraudulent payment, a failing part, a patient with a disease, a customer about to leave. On such data a model can score 98% or 99% accuracy while catching few of the cases it exists to find, and a team that watches only accuracy will ship it. The first job is therefore measurement: knowing which numbers stay honest when one class dominates.

The second job is choosing a remedy without making things worse. Resampling done before the train/test split leaks information and produces scores that collapse in production. Class weights and resampling raise recall but also inflate every predicted probability, which breaks anything downstream that treats the output as a real risk, such as an expected-loss calculation or an ad-ranking system. Often the cheapest fix is to leave training alone and move the decision threshold. Anyone who builds, reviews or signs off a classifier for rare events needs to know which lever does what and what each one costs.

Key terms

Class imbalance
A dataset in which one label is much more common than the other. The common label is the majority class and the rare one is the minority class.
Prevalence (base rate)
The fraction of all cases that are positive. With 200 frauds among 10,000 payments the prevalence is 2%.
Decision threshold
The cut-off applied to a predicted probability or score to turn it into a yes or no prediction. Most libraries default to 0.5.
Class weight
A multiplier on the loss of every training row of one class, so that an error on a rare-class row costs more than an error on a common-class row.
Under-sampling
Removing rows of the majority class from the training set, usually at random, to make the classes less unequal.
Over-sampling
Adding rows of the minority class to the training set, either by duplicating existing rows or by creating synthetic ones.
SMOTE
Synthetic Minority Over-sampling Technique. It creates new minority rows at random points on the line between a real minority row and one of its nearest minority neighbours.
Calibration
The property that predicted probabilities match observed frequencies. Among cases scored 10%, about 10% turn out positive.
Balanced accuracy
The average of recall on the positive class and recall on the negative class. A model that always predicts one class scores 0.5.
Average precision
A one-number summary of the precision-recall curve. A model with no skill scores about the prevalence, not 0.5.

2Explanation

Introduction

In classification metrics you met the confusion matrix and the numbers computed from it. This lesson is about what happens to those numbers, and to the model itself, when one class is rare.

Picture a payment processor checking 10,000 payments, of which 200 are fraudulent. That is a prevalence of 2%: the fraction of cases that are positive. Fraud, the rare class, is the minority class and legitimate payments are the majority class. A dataset like this is class-imbalanced. Now take a "model" that contains no machine learning at all and calls every payment legitimate. It is right 9,800 times out of 10,000, so its accuracy is 98%. It also catches no fraud whatsoever.

A real model looks barely better by the same yardstick. The logistic regression fitted in the worked example reaches 98.4% accuracy on 10,000 held-out payments, yet it finds only 58 of the 200 frauds.

Accuracy hides the problem because 98% of the cases are negatives, so 98% of the score comes from them. Two separate things are going on, and they need separate fixes:

  • The measurement is wrong. Accuracy rewards agreeing with the majority. Metrics built around the rare class, such as recall, precision and the precision-recall curve, do not.
  • The decision is wrong. A classifier predicts "positive" only when its estimated probability passes a decision threshold, 0.5 by default. When positives are rare, few cases ever receive a probability that high, even from a good model.

There are three levers for the second problem. You can change the data the model trains on (resampling: under-sampling, over-sampling and SMOTE), change the loss it minimises (class weights), or change the decision made from its output (threshold moving). The lesson explains each lever, shows on one dataset that they often land in nearly the same place, and explains why that makes the simplest lever the one to try first.

How it works

Why accuracy misleads

Accuracy is an average of how well the model does on each class, weighted by class size. With prevalence π\piπ, recall (the share of positives caught) and specificity (the share of negatives left alone):

accuracy=π⋅recall+(1−π)⋅specificity\text{accuracy} = \pi \cdot \text{recall} + (1 - \pi) \cdot \text{specificity}accuracy=π⋅recall+(1−π)⋅specificity

At π=0.02\pi = 0.02π=0.02, zero recall with perfect specificity scores 0.98. The SMOTE paper (opens in a new tab) makes the point with mammography data: 260 of 11,183 samples are calcifications, so labelling every sample as not a calcification is 97.68% accurate.

Metrics that stay informative:

  • Recall TP/(TP+FN)TP / (TP + FN)TP/(TP+FN) and precision TP/(TP+FP)TP / (TP + FP)TP/(TP+FP), reported together.
  • Balanced accuracy, the mean of recall and specificity. scikit-learn's metrics guide (opens in a new tab) notes that it drops to chance level when a classifier merely exploits an imbalanced test set.
  • The precision-recall curve and its summary, average precision. A model with no skill scores about π\piπ, so 0.30 is strong at 2% prevalence and useless at 50%.

ROC AUC needs care. It is built from recall and the false positive rate, and neither depends on prevalence, so it can look excellent while precision is poor. Saito and Rehmsmeier (opens in a new tab) show a ROC curve that is unchanged between a balanced test set and a 1:10 one while the precision-recall curve changes. Precision does depend on prevalence:

precision=π⋅TPRπ⋅TPR+(1−π)⋅FPR\text{precision} = \frac{\pi \cdot TPR}{\pi \cdot TPR + (1 - \pi) \cdot FPR}precision=π⋅TPR+(1−π)⋅FPRπ⋅TPR​

A detector with 90% recall and a 5% false positive rate has precision 0.95 at π=0.5\pi = 0.5π=0.5, 0.27 at π=0.02\pi = 0.02π=0.02 and 0.018 at π=0.001\pi = 0.001π=0.001.

Estimating and deciding are separate

scikit-learn's threshold guide (opens in a new tab) splits classification into a statistical problem, learning to predict class probabilities, and a decision problem, acting on them. predict hard-codes the decision: positive when the probability exceeds 0.5. Imbalance mostly hurts the decision. A model trained with log loss on 2% positives is doing its job when most of its probabilities sit far below 0.5.

Lever 1: move the threshold

Suppose a false alarm costs CFPC_{FP}CFP​ and a miss costs CFNC_{FN}CFN​. For a case with probability ppp of being positive, flagging it costs (1−p) CFP(1 - p)\,C_{FP}(1−p)CFP​ on average and letting it through costs p CFNp\,C_{FN}pCFN​. Flagging is cheaper when

p>CFPCFP+CFNp > \frac{C_{FP}}{C_{FP} + C_{FN}}p>CFP​+CFN​CFP​​

With a $4 false alarm and a $100 miss the threshold is 4/104≈0.03854 / 104 \approx 0.03854/104≈0.0385, not 0.5. This is the two-class rule in Elkan's paper on cost-sensitive learning (opens in a new tab) when correct decisions cost nothing, and it assumes calibrated probabilities. When costs are unknown, tune the threshold for a chosen metric on data the model was not fitted on. TunedThresholdClassifierCV (opens in a new tab) does this (it has existed since scikit-learn 1.5) with internal cross-validation, by default five stratified folds, then refits the model:

python
from sklearn.linear_model import LogisticRegression
from sklearn.model_selection import TunedThresholdClassifierCV

model = TunedThresholdClassifierCV(LogisticRegression(), scoring="balanced_accuracy")
model.fit(X_train, y_train)    # cross-validates the threshold, then refits on all of X_train
print(model.best_threshold_)   # the chosen cut-off, usually far below 0.5 on rare-class data

The default scoring is balanced accuracy. That is the same as charging each error in inverse proportion to its class size, which for calibrated probabilities puts the best threshold near the prevalence π\piπ. It is a reasonable default, but it is not your real cost ratio, so pass a scorer that encodes your costs when you know them.

Lever 2: class weights

Weights change the loss. For logistic regression the weighted log loss is

L=−∑iwyi [ yiln⁡pi+(1−yi)ln⁡(1−pi) ]L = -\sum_{i} w_{y_i}\,\bigl[\,y_i \ln p_i + (1 - y_i)\ln(1 - p_i)\,\bigr]L=−i∑​wyi​​[yi​lnpi​+(1−yi​)ln(1−pi​)]

so an error on a positive row counts w1w_1w1​ times. In scikit-learn, class_weight="balanced" sets (opens in a new tab) wc=n/(k⋅nc)w_c = n / (k \cdot n_c)wc​=n/(k⋅nc​) for nnn rows, kkk classes and ncn_cnc​ rows of class ccc. With 300 positives in 15,000 rows, w1=25w_1 = 25w1​=25 and w0≈0.51w_0 \approx 0.51w0​≈0.51, a ratio of 49. XGBoost exposes the same idea as scale_pos_weight, and its tuning notes (opens in a new tab) draw the line this lesson draws: use it when only the ranking matters (AUC), and do not re-balance when you need the right probability.

Weighting positives by a factor rrr makes the model behave as if positives were rrr times more common, which multiplies the odds it predicts by about rrr. Predicting positive at 0.5 on the weighted model is then the same as predicting positive at 1/(1+r)1 / (1 + r)1/(1+r) on the unweighted one: with r=49r = 49r=49, a threshold of 0.02. So weights and threshold moving are close substitutes, and a weighted model's outputs are no longer probabilities of anything real.

Lever 3: resample the training data

  • Random under-sampling deletes majority rows. It is fast and cuts training cost, but discards information. imbalanced-learn's under-sampling guide (opens in a new tab) also covers methods that choose which majority rows to drop.
  • Random over-sampling duplicates minority rows, which amounts to giving them integer weights. The SMOTE paper argues that replication makes a decision tree carve out very specific regions around the copies, which is a form of overfitting.
  • SMOTE creates synthetic minority rows. For a minority row xix_ixi​, pick one of its kkk nearest minority neighbours xzix_{zi}xzi​ (the paper uses five) and a random λ\lambdaλ between 0 and 1:
xnew=xi+λ (xzi−xi)x_{new} = x_i + \lambda\,(x_{zi} - x_i)xnew​=xi​+λ(xzi​−xi​)

With xi=(6,4)x_i = (6, 4)xi​=(6,4), neighbour (4,3)(4, 3)(4,3) and λ=0.5\lambda = 0.5λ=0.5, the new row is (5,3.5)(5, 3.5)(5,3.5). Interpolation assumes numeric features for which "halfway between" means something. imbalanced-learn (opens in a new tab) offers SMOTENC for mixed data and notes that SMOTE can connect inliers and outliers.

Two rules apply to every resampler. First, resample only the training data, after the split and inside each cross-validation fold. imbalanced-learn's pitfalls page (opens in a new tab) explains that resampling the whole dataset leaks information and tests the model on a balanced set it will never meet. Its pipeline (opens in a new tab) applies samplers during fit only:

python
from imblearn.over_sampling import SMOTE
from imblearn.pipeline import make_pipeline
from sklearn.linear_model import LogisticRegression
from sklearn.model_selection import cross_validate

model = make_pipeline(SMOTE(k_neighbors=5, random_state=0), LogisticRegression())
scores = cross_validate(model, X_train, y_train, scoring="average_precision", cv=5)

Second, a model trained on resampled data predicts in the resampled world. If a fraction www of the negatives was kept, its output ppp maps back to the real base rate as

q=pp+(1−p)/wq = \frac{p}{p + (1 - p) / w}q=p+(1−p)/wp​

This is the correction Facebook's ads team published (opens in a new tab). Google's crash course (opens in a new tab) describes an alternative: down-sample the majority class, then up-weight the kept majority rows by the same factor, so that the loss still reflects the true class ratio.

Which lever first

For simple models such as logistic regression, all three levers trade precision for recall along roughly the same curve, and none adds information about the rare class. A simulation study of logistic regression (opens in a new tab) found that under-sampling, over-sampling and SMOTE all gave strongly overestimated probabilities without better discrimination, and that shifting the threshold gave similar sensitivity and specificity. Elkan's paper gives the same practical advice for standard Bayesian and decision-tree learners: learn a classifier from the training set as given, then compute the decisions from its probability estimates. So fit on the data as it is, check average precision, then set the threshold. Reach for weights or resampling when training itself struggles: mini-batches with no positives, a learner that ignores the rare class, or more data than you can afford to train on. Compare by average precision on untouched validation data.

Worked example: Fraud scoring on 10,000 payments with all three levers

The data are simulated so that you can reproduce every number. Each payment has one risk score: legitimate payments centre on 0 and frauds on 2.5, both with standard deviation 1, so the classes overlap. The training set and the test set each hold 10,000 payments, 200 of them fraudulent (2%). A missed fraud costs $100 and a false alarm $4, so the cost threshold from Lever 1 is 4 / 104 = 0.0385. The script needs only Python 3.

python
import math
import random
from statistics import mean

COST_FP, COST_FN = 4, 100              # dollars per false alarm and per missed fraud


def normal(rng, centre):                 # Box-Muller
    u1, u2 = rng.random(), rng.random()
    return centre + math.sqrt(-2 * math.log(1 - u1)) * math.cos(2 * math.pi * u2)


def make_data(seed, n_neg=9800, n_pos=200, gap=2.5):
    rng = random.Random(seed)
    return [(normal(rng, 0), 0) for _ in range(n_neg)] + [(normal(rng, gap), 1) for _ in range(n_pos)]


def sigmoid(z):
    return 1 / (1 + math.exp(-z))


def fit(rows, w_pos=1.0):              # logistic regression by Newton's method, one feature
    b0 = b1 = 0.0
    for _ in range(25):
        g0 = g1 = h00 = h01 = h11 = 0.0
        for x, y in rows:
            w = w_pos if y else 1.0    # class weight multiplies the positive rows
            p = sigmoid(b0 + b1 * x)
            g0, g1 = g0 + w * (y - p), g1 + w * (y - p) * x
            s = w * p * (1 - p)
            h00, h01, h11 = h00 + s, h01 + s * x, h11 + s * x * x
        det = h00 * h11 - h01 * h01
        b0, b1 = b0 + (h11 * g0 - h01 * g1) / det, b1 + (h00 * g1 - h01 * g0) / det
    return lambda x: sigmoid(b0 + b1 * x)


def show(name, rows, probs, threshold):
    flag = [p >= threshold for p in probs]
    tp = sum(f and y for f, (_, y) in zip(flag, rows))
    fp = sum(f and not y for f, (_, y) in zip(flag, rows))
    fn = sum(y for _, y in rows) - tp
    tn = len(rows) - tp - fp - fn
    recall, spec = tp / (tp + fn), tn / (tn + fp)
    prec = f"{tp / (tp + fp):.3f}" if tp + fp else "  -  "
    print(f"{name:<31}{(tp + tn) / len(rows):>7.3f}{recall:>8.3f}{prec:>10}{(recall + spec) / 2:>9.3f}"
          f"{fp:>6}{fn:>5}{COST_FP * fp + COST_FN * fn:>9,}")


def average_precision(rows, probs):    # mean of the precision at each true positive's rank
    ranked = sorted(zip(probs, (y for _, y in rows)), reverse=True)
    hits, total = 0, 0.0
    for rank, (_, y) in enumerate(ranked, start=1):
        hits, total = hits + y, total + y * (hits + y) / rank
    return total / hits


def roc_auc(rows, probs):              # rank-sum form of the ROC area
    ranked = sorted(zip(probs, (y for _, y in rows)))
    n_pos = sum(y for _, y in ranked)
    rank_sum = sum(rank for rank, (_, y) in enumerate(ranked, start=1) if y)
    return (rank_sum - n_pos * (n_pos + 1) / 2) / (n_pos * (len(ranked) - n_pos))


train, test = make_data(seed=1), make_data(seed=2)
cost_threshold = COST_FP / (COST_FP + COST_FN)               # 4 / 104 = 0.0385

print("rule                            accuracy  recall precision  bal.acc    FP   FN     cost")
plain = fit(train)
p = [plain(x) for x, _ in test]
show("always legitimate", test, [0.0] * len(test), 0.5)
show("plain model, threshold 0.5", test, p, 0.5)
show("plain model, threshold 0.0385", test, p, cost_threshold)
print(f"ROC AUC {roc_auc(test, p):.3f}   average precision {average_precision(test, p):.3f}   (no skill: 0.020)")

weighted = fit(train, w_pos=COST_FN / COST_FP)               # a missed fraud counts 25 times
pw = [weighted(x) for x, _ in test]
show("class weight 25, threshold 0.5", test, pw, 0.5)
same = mean([(a >= 0.5) == (b >= cost_threshold) for a, b in zip(pw, p)])
print(f"same decisions as plain at 0.0385: {same:.4f}   mean probability: plain {mean(p):.4f}, weighted {mean(pw):.4f}")

keep = 0.1                                                   # keep about 10% of the legitimate rows
rng = random.Random(0)
small = [row for row in train if row[1] or rng.random() < keep]
under = fit(small)
pu = [under(x) for x, _ in test]
corrected = [v / (v + (1 - v) / keep) for v in pu]           # q = p / (p + (1 - p) / w)
show("under-sampled, threshold 0.5", test, pu, 0.5)
show("under-sampled, corrected", test, corrected, cost_threshold)
print(f"training rows {len(small)}   mean probability: raw {mean(pu):.4f}, corrected {mean(corrected):.4f}")

It prints:

text
rule                            accuracy  recall precision  bal.acc    FP   FN     cost
always legitimate                0.980   0.000       -      0.500     0  200   20,000
plain model, threshold 0.5       0.984   0.290     0.763    0.644    18  142   14,272
plain model, threshold 0.0385    0.935   0.865     0.218    0.901   622   27    5,188

same decisions as plain at 0.0385: 0.9996   mean probability: plain 0.0188, weighted 0.1209
under-sampled, threshold 0.5     0.964   0.740     0.327    0.854   304   52    6,416

Read the output from top to bottom.

The accuracy trap. "Always legitimate" scores 0.980 and catches nothing. The fitted model at the default 0.5 scores 0.984, with recall 0.290: 58 frauds found, 142 missed. Its balanced accuracy of 0.644 and its cost of $14,272 ($20,000 for doing nothing) tell the real story.

Ranking versus deciding. ROC AUC is 0.968, which sounds excellent, yet average precision is 0.565 against a no-skill 0.020. The scores rank payments well; the 0.5 cut-off is what wastes them. With one feature every variant below ranks payments identically, so AUC and AP stay the same; with many features they can shift.

Lever 1: threshold. The same model at 0.0385 finds 173 of 200 frauds (recall 0.865) at precision 0.218, and the cost drops to $5,188. Accuracy falls from 0.984 to 0.935, so a team that watched accuracy would reject the better decision.

Lever 2: class weight. Counting each fraud 25 times (the cost ratio) and cutting at 0.5 gives the same decision as Lever 1 for 99.96% of test payments, at $5,204. The price is honesty: the mean predicted probability is 0.1209, six times the true 0.02, while the plain model's 0.0188 is close.

Lever 3: under-sampling. Keeping about 10% of legitimate rows leaves 1,199 training rows. The model's raw mean probability is 0.0737, 3.7 times too high. Applying q=p/(p+(1−p)/w)q = p / (p + (1 - p) / w)q=p/(p+(1−p)/w) with w=0.1w = 0.1w=0.1 brings it to 0.0198, and cutting the corrected value at 0.0385 costs $5,156. Cutting the raw value at 0.5 is just another threshold, here equal to a true probability of 0.091.

All three levers end near $5,200; differences of a few dozen dollars are noise with only 200 frauds. The cheapest lever was moving the threshold of a model fitted to the data as it is.

Edge cases and limitations

With few positives, tuning on a validation set is noisy
The first exercise sweeps thresholds on a 10,000-payment validation set that holds 200 frauds. The sweep picks 0.035 and then costs 5,352 dollars on the test set, while the formula value 0.0385 costs 5,188 dollars. With so few positives, the sweep partly fits noise. Prefer a threshold derived from costs, or tune with repeated stratified cross-validation, and report how much the chosen value moves between folds.
Prevalence in production differs from prevalence in training
Precision depends on prevalence, and a cost threshold assumes probabilities that match the live base rate. The same detector with 90% recall and a 5% false positive rate has precision 0.27 at 2% fraud and 0.43 at 4%. A model trained on re-sampled data also carries its training base rate inside its output. Monitor the positive rate, re-derive the threshold when it moves, and keep the sampling fraction so you can correct probabilities.
One metric can improve while another gets worse
With flexible models such as decision trees, resampling changes how the model ranks cases, not just where it cuts. The Fraud Detection Handbook reports experiments with decision trees on a simulated card-transaction dataset in which resampling improved ROC AUC but in almost every case lowered average precision. Choose the metric that matches how alerts are used before comparing levers: average precision for ranking quality, precision at a fixed alert budget for a review queue.
SMOTE needs distances that mean something
SMOTE picks neighbours by distance, so a feature measured in dollars swamps one coded 0 or 1, and integer codes for categories are not points on a line. Scale numeric features first, use SMOTENC or another mixed-data method when categories are present, and be wary in very high dimensions, where nearest neighbours are barely nearer than anything else.
Many labels per example, or more than two classes
With several rare labels per example, as in chest X-ray tagging, resampling rows is awkward because one image is rare for one disease and common for another. Weights per label entry fit better, and each label then needs its own threshold. For more than two classes, report per-class recall and macro-averaged metrics, because a micro-average hides the rare class again.

When to use it, and when something simpler is enough

Use it when

  • The cases you care about are a small share of the data, roughly under 10%, and a miss costs far more than a false alarm, as in fraud, safety faults, disease screening or churn.
  • A plain model reaches high accuracy but poor recall or precision on the rare class, and you need to know whether the cause is the metric, the 0.5 threshold or the training signal.
  • Predicted probabilities feed a calculation such as an expected loss or an ad ranking, so you must keep or restore calibration while raising recall.
  • The training set is too large to use whole and is mostly negatives, so down-sampling negatives, with a probability correction, cuts training cost.

Think twice when

  • The classes are roughly balanced and the costs of the two errors are similar. The default threshold and plain accuracy are fine, and rebalancing only adds distortion.
  • You have only a few dozen positives. Resampling cannot create information that is not there, so collect more labelled cases or treat the problem as anomaly detection.
  • You are about to resample before splitting the data, or to run SMOTE on categorical codes. Fix the pipeline first, because the scores it gives will not hold up in production.

A simpler alternative. Fit the model on the data as it is, judge it with precision, recall and average precision on untouched validation data, and move the decision threshold to match your costs. Reach for class weights or resampling only when training itself fails, for example when the learner ignores the rare class or mini-batches contain no positives.

Key takeaways

  • Accuracy is dominated by the majority class, so a model can score 98% while catching almost none of the rare cases; report recall, precision and average precision instead.
  • A threshold of 0.5 is a default, not a law; for calibrated probabilities the cost-minimising cut-off is the false alarm cost divided by the sum of both error costs, and moving it is often the cheapest fix.
  • Class weights, under-sampling, over-sampling and SMOTE mostly shift the same precision-recall trade-off as the threshold does, and they inflate the model's predicted probabilities.
  • Resample only the training data, after the split and inside each cross-validation fold, and evaluate on data that keeps the natural class mix.
  • If you resample or reweight and still need real probabilities, correct them, for example with q = p / (p + (1 - p) / w) after down-sampling negatives.

Example 1 of 5

Facebook ads: down-sampling negatives, then recalibrating click predictions

FacebookDocumented in a paper

The click-prediction system for Facebook ads, described in the ADKDD 2014 paper "Practical Lessons from Predicting Clicks on Ads at Facebook" by He and colleagues. Section 6 of the paper tests ways to cope with massive training data. XGBoost's parameter-tuning notes document the same trade-off between ranking and probabilities for ads click logs. [15][13]

The problem

A small fraction of one day of Facebook ad impressions already holds many hundreds of millions of rows, the paper says, and clicks are rare among impressions: its own illustration assumes an average click-through rate of 0.1%. Cutting the training data lowers cost, but the predicted click probability is used directly, because the paper says the expected value of an ad depends on it. The cut must therefore leave the model's output matching the real click rate.

Where this topic fits

Between the impression and click logs and the boosted-tree model. Rows without a click are down-sampled before training, and after training each prediction is mapped back to the real click rate before it is used in live traffic.

How it is applied, step by step

  1. Build labelled rows by joining impressions with clicks. The large majority of rows are impressions without a click.
  2. Pick a negative down-sampling rate w. Keep every row that has a click and keep a fraction w of the rows that do not.
  3. Train the boosted-tree model on the sampled rows and evaluate it with normalized entropy and calibration.
  4. Repeat for several rates and keep the best. The paper reports the best result at a rate of 0.025.
  5. Because clicks are over-represented in the sampled data, the model predicts in the down-sampled space. Map each prediction p back with q = p / (p + (1 - p) / w).
  6. Use the corrected q wherever the system needs a click probability, such as in live traffic experiments.

Why this approach fits

Ad data is both huge and extremely imbalanced. Each no-click row carries little information on its own, while every click is scarce, so keeping all the clicks and a fraction of the rest cuts cost at a small price. The closed-form correction lets the system keep treating the output as a probability, which the ad-ranking side needs and which a plain weight or resampling step would otherwise distort.

Limitation or tradeoff

The correction is exact only when negatives were sampled uniformly at a known rate, and it restores the average level rather than repairing other distortions. The best rate was found by experiment on Facebook's data and need not transfer. The paper also finds that sampling choices matter much less than having the right features and the right model.

What the sources document

  • The paper compares uniform subsampling with negative down sampling, which it investigates as a way to address class imbalance, as ways to reduce the cost of training on very large impression logs, and evaluates both with calibration and normalized entropy. [15]
  • It states that the best performance was achieved with a negative down-sampling rate of 0.025, while listing the rates it varied as 0.1, 0.01, 0.001 and 0.0001. [15]
  • A model trained on down-sampled negatives is calibrated in the down-sampled space: with a 0.1% average click rate and 0.01 negative down-sampling the empirical rate becomes roughly 10%, so predictions are re-calibrated with q = p / (p + (1 - p) / w), where w is the negative down-sampling rate. [15]
  • The paper says that handling of data freshness, learning rate schema and data sampling improves the model only slightly, much less than adding a high-value feature or picking the right model. [15]
  • XGBoost's parameter-tuning notes use an ads click-through log as their example of an extremely imbalanced dataset. They advise balancing weights with scale_pos_weight if only the ranking order (AUC) matters, and say you cannot re-balance the dataset if you need the right probability. [13]

ChestX-ray8: balancing factors in the loss for rare disease labels

Documented in a paper

The ChestX-ray8 paper (Wang and colleagues, CVPR 2017) releases a database of chest X-ray images with text-mined disease labels and trains a multi-label deep network on it. The paragraph on its multi-label classification loss layer describes how the authors handled the scarcity of positive labels. [16]

The problem

Each image carries a label vector with one entry per disease, and the vectors are sparse, with far more 0s than 1s. The authors report that with standard losses the network had difficulty learning the positive instances. They attribute the sparse labels to their one-hot-like labelling and to the unbalanced numbers of pathology and Normal images.

Where this topic fits

Inside the training loss of the convolutional network, before any decision about which diseases to report. The balancing factors are computed from the labels in each training batch and multiply the positive and negative terms of the cross-entropy, so the rare 1s have more influence on the gradient than the many 0s.

How it is applied, step by step

  1. Store each image's findings as a label vector with a 0 or 1 for every disease. Most entries are 0.
  2. Train first with standard losses (hinge, Euclidean and cross-entropy) and observe that positive instances are learned poorly because 0s far outnumber 1s.
  3. In every batch, count |P|, the number of 1s, and |N|, the number of 0s, in the batch's label vectors.
  4. Set the factors β_P = (|P| + |N|) / |P| and β_N = (|P| + |N|) / |N|. The rarer label gets the larger factor.
  5. Minimise the weighted cross-entropy: the −ln f(x) terms of positive entries are multiplied by β_P and the −ln(1 − f(x)) terms of negative entries by β_N.
  6. Read each disease output of the trained network as a score. Turning scores into yes or no calls remains a separate threshold decision.

Why this approach fits

When every image has several labels, resampling images is awkward, because one image can be a rare positive for one disease and a common negative for the others. A weight on each entry of the label vector treats every disease separately, and it needs no change to the images or to the batch sampler.

Limitation or tradeoff

A batch with no positive entry makes β_P undefined, so an implementation must guard against division by zero. The weights change what the outputs mean, so they are no longer calibrated probabilities and each disease still needs an operating threshold chosen on validation data. The labels were mined from radiology reports by language processing, so label noise limits what any loss can recover.

What the sources document

  • ChestX-ray8 contains 108,948 frontal-view chest X-ray images from 32,717 unique patients, with eight common disease labels mined from radiological reports using natural language processing. [16]
  • The authors found that with hinge, Euclidean and cross-entropy losses the model had difficulty learning positive instances, and that the image labels were sparse with far more 0s than 1s, which they attribute to their one-hot-like labelling and the unbalanced numbers of pathology and Normal classes. [16]
  • To enforce the learning of positive examples they introduce positive and negative balancing factors β_P and β_N into a weighted cross-entropy loss, setting β_P to (|P| + |N|) / |P| and β_N to (|P| + |N|) / |N|, where |P| and |N| are the numbers of 1s and 0s in a batch of image labels. [16]

Stripe Radar: a risk score with block and review thresholds, tested before use

StripeDocumented in official docs

Stripe Radar, the fraud screening that is built into Stripe payments, as described on Stripe's documentation pages for transaction risk prevention, for fraud prevention rules and for risk settings. [17][18][19]

The problem

Every card payment must be allowed, reviewed or blocked in real time, and fraud is a minority of payments (the pages give no rate). The pages treat the two errors as a balance the merchant manages: rules can block a large number of legitimate payments or let many risky ones through if they are set up badly, and a review queue that grows too large burdens the team that works it.

Where this topic fits

After the model. Radar's models produce a risk score and a risk level for each payment, and a separate rule layer maps those to actions. The decision threshold is therefore a setting that can be moved without retraining the model.

How it is applied, step by step

  1. The model scores each payment in real time using many risk factors and reports a risk level, and on some plans a risk score from 0 to 99.
  2. By default the highest risk level is blocked and the elevated level is allowed, with a review queue for it if the plan supports one.
  3. A merchant who wants a different balance writes a rule of the form action if attribute operator value, for example one that combines the risk level with the payment amount.
  4. Alternatively, a merchant on a plan that supports it picks a risk setting (maximise protection, balance risk and revenue, or maximise revenue). Radar then adjusts the blocking thresholds of its risk controls, and the dashboard shows projected effects based on the last four months of payments.
  5. Before enabling a rule, the merchant runs Test rule, which replays the last six months of charges and shows how many legitimate, fraudulent and blocked payments the rule would have touched.
  6. If unsure, the merchant starts with a review rule rather than a block rule, and rolls the rule out on a small share of matching payments before widening it.
  7. After launch, rule metrics such as the estimated false positive rate and the estimated fraudulent payments prevented show whether the cut-off still suits the business.

Why this approach fits

Fraud is rare, the two errors cost different amounts, and the balance differs between merchants because their margins, review staff and tolerance for lost sales differ. Keeping the decision in a rule layer lets each merchant move the cut-off, or add a review band between allow and block, without retraining the model, and lets the change be checked against past payments first. This is Lever 1 offered as a product feature.

Limitation or tradeoff

A threshold on a fixed score only trades fraud caught against customers blocked along the ranking the model already produces. It cannot improve the ranking. A replay of the last six months assumes the next months look similar, and blocked payments never reveal whether they would have been fraud, so the false positive figures rest on Stripe's estimates. The score is also shown only on some plans. Stripe's risk-settings page says the block rule that uses the classic risk score is being deprecated in favour of risk settings, so the 65 and 75 defaults describe that classic score, and a newer account may manage its thresholds through risk settings instead.

What the sources document

  • Where available, each payment has a risk score from 0 to 99, provided only with certain Radar plans. By default a score of 65 or above indicates elevated risk and 75 or above indicates high risk. High-risk payments are blocked by default. Elevated-risk payments are allowed by default and, if the plan supports it, can be evaluated in a manual review queue. [17]
  • Custom rules are written as an action, an attribute, an operator and a value. The Test rule step simulates a rule on the last six months of charges to show how many legitimate, fraudulent and blocked payments it would have affected. [18]
  • The rules page says a good block rule blocks significantly more fraudulent than legitimate payments, suggests a review rule first when unsure, and offers traffic allocation so a rule can start on a small percentage of matching payments or run at 0% without applying its action. [18]
  • For a small subset of payments Stripe modifies the reported risk score so that it can measure its models, and it says this keeps key metrics such as false positive rate and recall within desirable ranges. [17]
  • Risk settings (maximise protection, balance risk and revenue, maximise revenue) set different blocking thresholds on Radar's risk controls to balance authorisation against fraud, and show estimated projections from the last four months of payments when changed. For the fraudulent dispute control a custom threshold can be set and backtested before it is applied. The page says Radar is deprecating the block rule that uses the classic risk score in favour of risk settings, which use separate models. [19]

Azure Machine Learning automated ML: detecting imbalance and trying class weights

Microsoft Azure Machine LearningDocumented in official docs

The automated ML feature of Azure Machine Learning, as described on the Microsoft Learn page "Prevent overfitting and imbalanced data with Automated ML". The page metadata dates this version to November 2025. [20]

The problem

An automated service trains and compares many models without anyone inspecting each one. The page warns that imbalanced data can give a falsely good impression of accuracy, because the input is biased toward one class and the trained model mimics that bias. The service therefore has to notice imbalance by itself and offer a treatment and a metric that do not reward the majority class.

Where this topic fits

Inside the managed training job and its reporting. The service checks class counts when it prepares the run, tests whether weights help, generates charts that expose minority-class behaviour, and lets the user pick an imbalance-robust primary metric for choosing among the models it trains.

How it is applied, step by step

  1. The job counts the samples in each class of a classification task.
  2. It flags imbalance when the minority class has no more than 20% as many samples as the majority class. This is a ratio of counts, not a share of the whole dataset.
  3. It runs an experiment on subsampled data to check whether class weights improve performance, and applies the weights only if they do.
  4. The job produces a confusion matrix, a precision-recall chart and a ROC curve, so the user can see how the rare class is treated.
  5. The user can choose a primary metric such as AUC_weighted, which counts each class by its relative number of samples, when comparing models.
  6. Automated ML builds a column of weights as input, which can be used to make a class more or less important.

Why this approach fits

A managed service has to be safe by default for users who will not read their confusion matrix. Testing for a count ratio is cheap, and checking on a subsample that weights help avoids applying them where they would hurt. Offering a metric that weights classes by their size guards the choice among many candidate models against the accuracy trap.

Limitation or tradeoff

The detection rule looks only at the class ratio. It ignores the absolute number of positives and the cost of each error, so the user still has to choose a metric and a threshold that reflect the business. The page also lists resampling only as something to do outside automated ML, and notes that it takes expertise.

What the sources document

  • Automated ML jobs automatically generate a confusion matrix, a precision-recall chart and ROC curves, which help identify models potentially affected by imbalanced data. [20]
  • The service detects imbalance when the number of samples in the minority class is equal to or fewer than 20% of the number in the majority class. It then runs an experiment with subsampled data to check whether class weights improve performance and applies the remedy if they do. [20]
  • Automated ML creates a column of weights as input, which can make a class more or less important, and the page suggests an imbalance-robust metric such as AUC_weighted, which calculates each class's contribution from its relative number of samples. [20]
  • The page lists up-sampling small classes or down-sampling large ones as options outside automated ML that require expertise, and points to F1, precision and recall as metrics to review. [20]

Amazon SageMaker Data Wrangler: a Balance data step with random sampling and SMOTE

Amazon SageMaker Data WranglerDocumented in official docs

The Balance data transform of Amazon SageMaker Data Wrangler, documented on the AWS page "Transform Data". It lets a user rebalance a dataset for binary classification as one step in a visual data flow. [21]

The problem

A data scientist preparing tabular data for a binary classifier often has a small positive class. The page's own example is fraud in only 10% of the rows. They need a step in the data-preparation flow that evens out the class proportions without writing sampling code, and a choice between duplicating, deleting and synthesising rows.

Where this topic fits

A transform step in a Data Wrangler data flow, after loading and cleaning and before the data is exported for training. Each transform produces a new dataframe that later steps use. The page does not discuss train and test splits, so a careful user applies the step to the training portion only, after the split, to avoid the leak described earlier in this lesson.

How it is applied, step by step

  1. Open the data flow, add a transform and choose Balance data for a dataset that has an under-represented category.
  2. Pick an operator: random oversampling duplicates minority rows, random undersampling removes rows of the over-represented class, and SMOTE creates synthetic minority rows.
  3. For SMOTE, find neighbouring minority rows using only the numeric features to measure distance.
  4. For two real minority rows, build a new row whose numeric values are a random weighted average of the two.
  5. Copy each non-numeric value from one of the two real rows, chosen with random probabilities.
  6. Add the step. Every later step in the flow then works on the balanced dataframe.

Why this approach fits

Tabular fraud-style data with mostly numeric features suits interpolation, and offering oversampling, undersampling and SMOTE side by side lets a user try all three on their own data. A visual step also makes the rebalancing explicit and repeatable instead of leaving it buried in a notebook.

Limitation or tradeoff

The step balances whatever it is given. Applied before the train and test split, it puts duplicated or interpolated rows on both sides and inflates scores. Applied to training data, it shifts predicted probabilities, which then need correcting. Only numeric features define who counts as a neighbour, so categorical columns do not influence the interpolation, and the page notes that datasets containing column vectors cannot be balanced.

What the sources document

  • Balance data is offered for datasets with an under-represented category to help create better binary classification models. The page notes that datasets containing column vectors cannot be balanced. [21]
  • The three operators are random oversampling, which duplicates minority samples (the page's example is fraud in 10% of the data, duplicated 8 times to reach equal proportions), random undersampling, which removes samples from the over-represented category, and SMOTE. [21]
  • SMOTE interpolates new minority samples from neighbouring real ones using only numeric features to measure distance. Numeric values are a randomly weighted average of two real samples, for example 0.7A plus 0.3B, and non-numeric values are copied from one of the two real samples with randomly assigned probabilities. [21]

4Common mistakes

  1. Resampling the whole dataset first and splitting it into train and test sets afterwards

    Why it causes problems
    Copies of, or interpolations between, the same positive rows end up on both sides of the split, and the test set no longer has the class mix the model will meet. Scores look far better than production will deliver.
    How to recognise it
    Cross-validation or test scores clearly higher than the score on a fresh time period or a separate untouched holdout, or a test set that is 50% positive.
    How to fix it
    Split first with stratification, resample inside each training fold using an imbalanced-learn pipeline, and keep the validation and test sets at their natural class mix.

  2. Reporting accuracy or ROC AUC alone for a rare-event model

    Why it causes problems
    Both can look excellent while the model finds little of the rare class or raises a flood of false alarms, so a reader approves a model that fails in use.
    How to recognise it
    Accuracy close to one minus the prevalence, or a high ROC AUC next to a low average precision or a small precision at the chosen threshold.
    How to fix it
    Report the prevalence, the confusion matrix at the operating threshold, recall and precision, and average precision compared with its no-skill value, which equals the prevalence.

  3. Using the probabilities of a weighted or resampled model as if they were real risks

    Why it causes problems
    The outputs are inflated. In the worked example the weighted model averaged 0.12 against a true rate of 0.02, so any expected-loss or ranking-by-value calculation is wrong by a large factor.
    How to recognise it
    The mean predicted probability on held-out data sits far above the base rate, or a calibration curve lies far above the diagonal.
    How to fix it
    Correct for the weights or sampling fraction, for example q = p / (p + (1 - p) / w), or recalibrate on held-out data with the natural class mix, or skip resampling and move the threshold instead.

  4. Choosing the threshold on the training rows or on the test set

    Why it causes problems
    A threshold fitted to a few positives captures noise, and a test set that helped choose the cut-off no longer gives an honest estimate. scikit-learn warns against tuning on the data used to fit the model.
    How to recognise it
    A large gap between the cost or F-score at the chosen threshold on the tuning data and on fresh data.
    How to fix it
    Choose the threshold on validation data or inside cross-validation, keep the test set untouched, and prefer the cost-derived threshold when positives are few.

  5. Running SMOTE on categorical codes or unscaled features

    Why it causes problems
    Interpolating between integer category codes produces values that mean nothing, and a feature with a large scale decides who counts as a neighbour. The synthetic rows then lie where real data never does.
    How to recognise it
    Synthetic rows with fractional category codes, or synthetic minority rows that sit inside regions full of majority rows.
    How to fix it
    Scale the numeric features first, use SMOTENC or another mixed-data method when categories are present, or fall back to class weights or threshold moving.

def smote_1d(rows, k=5, seed=0):
    """Add synthetic positives until both classes have the same number of rows."""
    rng = random.Random(seed)
    minority = sorted(x for x, y in rows if y)
    near = {x: sorted(minority, key=lambda v: abs(v - x))[1:k + 1] for x in minority}   # [0] is x itself
    made = []
    for i in range(sum(1 for _, y in rows if not y) - len(minority)):
        x = minority[i % len(minority)]            # cycle through the real positives
        z = rng.choice(near[x])                    # one of its k nearest positive neighbours
        made.append((x + rng.random() * (z - x), 1))   # x + lambda * (z - x)
    return rows + made
