AI-Assisted Development (Coding Agents)

AI-assisted development means building software with a coding agent: a language model wrapped in a program that can read your repository, edit files, run commands and tests, and report what it did. The developer supplies the context and the instructions, and stays responsible for checking and reviewing every change before it ships.

1Overview

Why it matters

A coding agent can read an unfamiliar repository, change several files and run the tests in minutes. That is why many engineers now use one, including those who work in other people's codebases. The speed cuts both ways. In the 2025 Stack Overflow developer survey, 84% of respondents were using or planning to use AI tools, yet more developers distrusted the accuracy of the output (46%) than trusted it (33%). In a METR trial with experienced open-source developers, those who were allowed to use AI tools took 19% longer per issue, and still believed afterwards that the tools had made them faster.

What goes wrong is rarely dramatic code. It is a plausible change that skips an edge case, a test written to match the bug, a command run against the wrong environment, or a file the agent should never have been able to read. The skills in this lesson prevent those failures: giving the agent the right context, giving it a way to check its own work, reviewing what comes back, and limiting what it can touch. Anyone who ships code into a customer's systems needs them, because the customer, not the tool, owns the consequences.

Key terms

Coding agent
A program that pairs a language model with tools for reading files, editing code and running commands, and keeps working until the task is done or it needs you. Claude Code, Codex, Cursor's Agent and GitHub Copilot's cloud agent are examples.
Harness
The software around the model that supplies the tools, assembles the context and enforces permissions. Anthropic's documentation describes Claude Code as this layer.
Instruction file
A Markdown file in the repository that the agent loads at the start of every session, such as CLAUDE.md, AGENTS.md or a Cursor rule file. It holds the commands and conventions you would otherwise repeat.
Context window
Everything the model can see on one call: the conversation, the files it has read, command output and the instruction files. It fills up during a long session, and quality can drop as it does.
Permission mode
The setting that decides which actions the agent may take without asking you, such as editing files, running shell commands or reaching the network. Codex calls the matching setting an approval policy.
Sandbox
Operating-system isolation that limits which files and network destinations a command can reach, whatever the agent decides to run.
Plan mode
A mode in which the agent reads the code and proposes a plan but does not edit files, so you can agree on the approach before any change is made.
Verification
A check that returns a pass or fail the agent can read, such as a test suite, a build, a linter or a screenshot compared with a design.
Diff
The line-by-line difference between the code before and after a change. It is what a reviewer reads when deciding whether to approve a change.
Vibe coding
Simon Willison's definition of Andrej Karpathy's term: building software with an LLM without reviewing the code it writes.

2Explanation

Introduction

In Git and GitHub Workflows you learned the loop that teams use to change code safely: branch, commit, open a pull request, have someone review it, merge. AI-assisted development keeps that loop and changes who writes the first draft. A coding agent reads the repository, edits files, runs commands and tests, and hands you a diff. You still decide what is built, how it is checked and whether the change is good enough to merge.

There are three levels of tool, and this lesson is about the third. Autocomplete suggests the next few lines while you type. A chat assistant answers questions about code you paste in. A coding agent works inside your project: it searches files, makes coordinated edits across several of them, runs your test suite, reads the failures and tries again. The Agent Loop explains that cycle in general terms. Anthropic's documentation for Claude Code describes it as gathering context, taking action and verifying results.

A useful picture is a capable contractor who starts every morning with no memory of yesterday. They can do real work in your repository, but they know only what you tell them, what the code shows and what you wrote in the README for contractors, which for an agent is an instruction file. They stop when the work looks finished, so you must give them a way to prove that it is. And you review their pull request as you would anyone's, because they can be confidently wrong.

The products differ in detail, and this lesson compares four of them: Claude Code, OpenAI's Codex, Cursor's Agent and GitHub's Copilot cloud agent. The workflow is the same in all four. The lesson covers how agents get context, how to write instructions and task prompts, how to verify and review what they produce, how permissions and sandboxes limit the damage a mistake can do, and where vibe coding stops being acceptable, which matters most when the system belongs to a customer.

How it works

What happens inside one session

A session is the tool-calling loop from The Agent Loop pointed at a repository. Claude Code's documentation groups its built-in tools into file operations, search, execution (shell commands, tests, git), web access and code intelligence. Asked to "fix the failing tests", it might run the suite, read the errors, search for the source files, edit them and run the suite again. Each result decides the next step.

Where the agent runs changes the risk. Claude Code (opens in a new tab) runs on your machine, on cloud virtual machines, or on your machine while you drive it from a browser. Codex is offered as a CLI, an IDE extension, ChatGPT apps and Codex Cloud. GitHub's Copilot cloud agent works in an ephemeral cloud environment instead of your editor. A local agent shares your files, credentials and network; a cloud agent has only the access its provider and your settings give it.

Giving the agent context

Three kinds of context reach the model: what you type, including files you point to with an @ mention; what the agent finds by searching and reading; and what is loaded automatically at the start of every session, the instruction files. A new Claude Code session starts with a fresh context window, so anything you do not want to re-explain belongs in one. The files differ in name (the comparison grid further down lists them) but behave alike:

  • They are advice, not enforcement. Anthropic's documentation says Claude treats CLAUDE.md as context, not enforced configuration, and recommends a hook when an action must be blocked whatever the model decides.
  • They are layered. Claude Code loads CLAUDE.md from the working directory and every directory above it, joined from the root down, so the instructions nearest to you are read last. Codex builds the same kind of chain from the repository root to the current directory. The AGENTS.md (opens in a new tab) site says the closest file to the code being edited wins and an explicit user prompt overrides everything.
  • They must stay short. Anthropic suggests under 200 lines for a CLAUDE.md, Cursor suggests under 500 lines per rule, Codex stops adding files once the combined text reaches 32 KiB by default, and GitHub's example prompt for generating a Copilot instruction file limits the result to two pages. Anthropic warns that a bloated file gets its rules ignored.
  • They hold what the agent cannot guess: build and test commands, conventions that differ from the defaults, environment quirks and gotchas. Leave out what the code already shows. Anthropic's test for each line is whether removing it would cause mistakes.
  • They grow from mistakes. Add a line when the agent makes the same mistake twice or a code review catches something it should have known. Codex's guide says the same: add rules after repeated mistakes.

Writing the task prompt

Codex's best-practices page lists four parts of a strong prompt: the goal, the context (files, folders, documents, examples, errors), the constraints, and what "done" means. Anthropic adds practical habits: name the files, point to an existing pattern to copy, and describe a bug as a symptom, a likely location and what "fixed" looks like.

For a change that spans several files, or when you are unsure of the approach, ask for a plan first (plan mode in Claude Code and Codex, Plan in Cursor) and read it before any edit. Anthropic's rule of thumb: if you could describe the diff in one sentence, skip the plan. For a larger feature, ask the agent to interview you and write a spec file, then start a fresh session to implement it.

Verification: close the loop

Anthropic's best-practices page makes this its first recommendation. The agent stops when the work looks done, and without a check it can run, "looks done" is the only signal it has. Give it something that returns pass or fail: tests, a build, a linter, a script that compares output with a fixture, a screenshot compared with a design. Ask it to show evidence, such as the test output, instead of asserting success.

There is a trap. If the agent writes both the code and the tests, the tests can encode the same misunderstanding as the code, and everything passes. The worked example below shows it happening. Derive some of the test cases from the requirement itself, before the agent starts if you can. Anthropic calls the hazard the trust-then-verify gap and gives the rule: if you cannot verify it, do not ship it.

Checks can be made harder to skip. A Stop hook in Claude Code blocks the turn from ending until your script passes, and CI gives the same guarantee for every change whoever wrote it. A second session with a fresh context reviews better because it is not biased toward code it just wrote. A reviewer asked to find gaps will usually report some, so tell it to flag only gaps that affect correctness or the stated requirements.

Reviewing what comes back

Read the diff as you would a colleague's pull request. This checklist is our advice, not a vendor's:

  1. Requirement coverage. Each rule in the ticket maps to a test that would fail without the change.
  2. Scope. Open every changed file. Unexpected edits to configuration, lockfiles, CI workflows or existing tests are where surprises hide.
  3. Dependencies. A new package is a decision: does it exist, is it needed, is the licence acceptable?
  4. Security. Check input validation, queries built from strings, secrets and error messages. Veracode's 2025 study tested code from over 100 models in four languages and reports that 45% of the code samples failed its security tests, a vendor's own figure, so run static analysis on agent code like any other.
  5. Explainability. Simon Willison's rule is not to commit code you could not explain to somebody else.

Organisations build the same review into their process. Google's migration team reports that people review LLM-generated code like any other code. GitHub's Copilot cloud agent cannot mark its pull requests ready, approve them or merge them, and the person who asked for the pull request cannot approve it.

Permissions, sandboxes and customer systems

Every tool offers two controls. An approval policy decides when the agent must stop and ask. A sandbox decides what a command can physically touch.

  • Claude Code's Manual mode asks before file edits and shell commands, Accept edits mode approves edits for you, Plan mode blocks edits, and Auto mode lets a classifier review actions. Since version 2.1.283 interactive sessions start in Auto mode, so check the mode on a customer's repository. Permission rules are checked in the order deny, ask, allow, and the first match wins, so a deny rule beats an allow rule in any settings scope.
  • Codex has the sandbox modes read-only, workspace-write and danger-full-access, plus approval policies such as on-request. It recommends workspace-write with on-request for version-controlled folders, keeps network access off by default there, and marks danger-full-access as not recommended.
  • Cursor has three run modes: Auto-review (the recommended default since version 3.6), Allowlist and Run Everything. Auto-review sandboxes shell commands where it can and sends the rest to a classifier, and Cursor says it is not a security boundary.

Rules are not walls. Claude Code's Read and Edit deny rules cover its file tools and the file commands it recognises in Bash, but not a Python script that opens files itself, so protecting a secret needs the OS-level sandbox as well. Its checkpoints undo file edits, but not changes to databases, APIs or deployments.

In a customer's environment, add these habits:

  • Work on a branch of a copy, never on the customer's main branch. Git history is your undo.
  • Give the agent development credentials only. After the reported deletion of a user's production database, Replit's CEO announced automatic separation of development and production databases.
  • Treat what the agent reads as untrusted. A README, an issue or a web page can carry instructions aimed at the agent (Prompt Injection and LLM Security). Anthropic advises reviewing suggested commands, not piping untrusted content into the agent, and using virtual machines when it works with external services.
  • Know where the code goes. Everything the agent reads enters the context window, so unless the model runs inside the customer's boundary, assume file contents leave it. Check the contract first (Data Privacy and Compliance, Deploying in Customer Environments).
  • Use organisation controls where they exist, such as Claude Code's managed settings, which user and project settings generally cannot override.

Vibe coding and where it stops

Andrej Karpathy coined the phrase for fully giving in to the vibes and forgetting that the code exists. Simon Willison's sharper definition is building software with an LLM without reviewing the code it writes. He is happy with it for low-stakes projects and prototypes, and says code you reviewed, tested and can explain is software development, not vibe coding.

SituationVibe coding acceptable?Reason (our judgment)
Throwaway script, your machine, fake dataYesNothing is lost if it is wrong.
Demo shown to a customerOnly if labelled, with no real dataSee Rapid Prototyping and Demos.
Code the customer will run or maintainNoThey inherit code nobody reviewed.
Credentials, personal data, payments, production writesNoThe Replit incident below, and the 45% figure above.

Worked example: Reviewing an agent's shipping-cost function with tests derived from the requirement

You can reproduce every step with Python 3 and its standard library. The code below is a teaching example in the style of a first draft from a coding agent. No named tool produced it.

The requirement is copied from the ticket and is the source of truth:

RuleValue
Standard price$4.00 covers the first kilogram or part of a kilogram
Each further kilogram or part of a kilogram$1.50
Expressthe standard price multiplied by 1.35, rounded half up to the cent
Valid weightsabove 0 and at most 30 kg, otherwise raise ValueError

The instruction file the team already has, AGENTS.md:

markdown
# Shipping service
- Run the tests with `python3 -m unittest`.
- Money is `Decimal`, never `float`. Round to cents with `ROUND_HALF_UP`.
- Pricing rules are in docs/pricing.md. Read them before changing prices.

The prompt gives a goal, context, constraints and a done criterion:

text
Goal: add shipping_cost(weight_kg, express) to shipping.py.
Context: the rules are in docs/pricing.md. Follow the style of billing.py.
Constraints: Decimal only, no new dependencies, do not edit billing.py.
Done when: test_shipping.py covers the rules and python3 -m unittest passes.

The agent's draft, saved as shipping.py:

python
from decimal import Decimal

FIRST_KG = Decimal("4.00")
EXTRA_KG = Decimal("1.50")
EXPRESS_FACTOR = Decimal("1.35")
MAX_KG = Decimal("30")


def shipping_cost(weight_kg: Decimal, express: bool = False) -> Decimal:
    if weight_kg <= 0 or weight_kg > MAX_KG:
        raise ValueError("weight_kg must be above 0 and at most 30")
    extra_kg = max(int(weight_kg) - 1, 0)
    price = FIRST_KG + extra_kg * EXTRA_KG
    if express:
        price = price * EXPRESS_FACTOR
    return price.quantize(Decimal("0.01"))

The tests. The class AgentTests is what the agent wrote with the draft. SpecTests is what you add as reviewer, with every expected price worked out by hand from the requirement table. Save both as test_shipping.py:

python
import unittest
from decimal import Decimal

from shipping import shipping_cost


class AgentTests(unittest.TestCase):  # written by the agent
    def test_one_kg(self):
        self.assertEqual(shipping_cost(Decimal("1")), Decimal("4.00"))

    def test_three_kg(self):
        self.assertEqual(shipping_cost(Decimal("3")), Decimal("7.00"))

    def test_three_kg_express(self):
        self.assertEqual(shipping_cost(Decimal("3"), True), Decimal("9.45"))

    def test_zero_rejected(self):
        with self.assertRaises(ValueError):
            shipping_cost(Decimal("0"))


SPEC_CASES = [  # (weight_kg, express, price worked out from the rules)
    ("0.5", False, "4.00"),
    ("1", False, "4.00"),
    ("1.01", False, "5.50"),
    ("2.2", False, "7.00"),
    ("2", True, "7.43"),
    ("30", False, "47.50"),
]


class SpecTests(unittest.TestCase):  # written by the reviewer
    def test_prices(self):
        for weight, express, expected in SPEC_CASES:
            with self.subTest(weight=weight, express=express):
                self.assertEqual(shipping_cost(Decimal(weight), express), Decimal(expected))

    def test_out_of_range(self):
        for weight in ("0", "-1", "30.01"):
            with self.subTest(weight=weight):
                with self.assertRaises(ValueError):
                    shipping_cost(Decimal(weight))

Run 1: the agent's tests only. python3 -m unittest test_shipping.AgentTests prints Ran 4 tests and OK. By the agent's own measure the task is done.

Run 2: all tests. python3 -m unittest test_shipping prints Ran 6 tests and FAILED (failures=3). The failing lines, trimmed:

FAIL: test_prices (test_shipping.SpecTests.test_prices) (weight='2', express=True)

The fix changes three places in shipping.py: the import, the weight calculation and the final rounding.

python
from decimal import ROUND_CEILING, ROUND_HALF_UP, Decimal
...
    chargeable_kg = int(weight_kg.to_integral_value(rounding=ROUND_CEILING))
    price = FIRST_KG + (chargeable_kg - 1) * EXTRA_KG
...
    return price.quantize(Decimal("0.01"), rounding=ROUND_HALF_UP)

Run 3, python3 -m unittest test_shipping, prints Ran 6 tests and OK.

What the result means. The agent's four tests passed because they used whole kilograms and one express price, 7.00 × 1.35 = 9.45, that has no rounding tie. The tests came from what the code handled, not from what the rules demand. Six hand-worked cases from the requirement exposed two defects. Finally, feed the lesson back into the instruction file, using the habit of adding a line whenever a review catches something:

markdown
- Chargeable weight rounds UP to whole kg (`ROUND_CEILING`). `int()` truncates.
- Expected values in pricing tests come from docs/pricing.md, never from the code under test.

Edge cases and limitations

Tests written by the agent can copy its mistakes
When an agent writes the code and the tests together, the expected values can come from what the code returns instead of what the requirement says. The sign is a first run in which every new test passes and no test covers a boundary such as a part kilogram or a rounding tie. Write the failing tests from the requirement first, as Anthropic's guide suggests for bugs, and tell the agent not to edit them.
Instruction files are advice, not guarantees
Anthropic's documentation says Claude treats CLAUDE.md as context, not enforced configuration. In the Replit incident, the user says he told the agent not to change code without permission and reports that it deleted his production database anyway (The Register, Fortune). A rule that must hold, such as never touching migrations or never pushing, belongs in a deny rule, a hook, a sandbox or branch protection, with the instruction file as backup.
Long sessions forget and drift
Anthropic's best-practices page says the context window fills quickly and performance degrades as it does. Compaction keeps requests and key code but can lose detailed instructions given early. Put lasting rules in the instruction file, clear the context between unrelated tasks, and after two failed corrections start again with a better prompt instead of correcting a third time.
Permission rules do not match every way of doing the same thing
Claude Code's documentation gives a concrete case. With a deny rule for git push, a push written as git -C . push is not matched. Its Read deny rules also do not cover a Python script that opens a file itself. Treat rules as a first layer, add the OS-level sandbox, and rely on server-side branch protection for what must never happen.
Your own sense of the speed-up is unreliable
METR's 2025 trial found developers forecasting a 24% speed-up and afterwards believing in 20%, while the measured result was 19% longer per issue. In February 2026 METR called its follow-up data an unreliable signal, mainly because many developers now decline to work without AI or skip tasks they would not want to do without it. Neither number is a law. Track time to merge, review effort and post-merge defects on your own work.
The agent only knows what the repository shows
Business rules in someone's head, a customer's unusual environment or a script that must run first are invisible to the agent, and it fills such gaps with plausible guesses. Codex's guide notes that many quality problems are really setup problems, such as a wrong working directory or missing tool access. Write these facts into the instruction file the first time they cause a mistake.

When to use it, and when something simpler is enough

Use it when

  • You can state the task and a check the agent can run, such as a failing test, a build or a linter.
  • The change is mechanical and repeated across many files, such as a library or API migration, and a test suite can validate each file.
  • You are learning an unfamiliar codebase and want answers to questions like how logging works or where an endpoint is defined.
  • You are building a throwaway prototype or internal script that holds no real customer data.

Think twice when

  • You can neither verify the result nor explain it, because there are no tests and no reviewer with time to read the diff.
  • The agent would hold credentials for, or write access to, a production system or customer data that may not be sent to the model provider.
  • The change touches authentication, payments or other security-critical paths and nobody with the expertise will review it line by line.

A simpler alternative. For a one-line fix, a rename or an edit your editor can refactor, do it by hand: Anthropic's own guide says to skip planning when you could describe the diff in one sentence. For questions about code, ask in a chat or in a read-only or plan mode first. Reach for an agent when the task spans several files and you have a check it can run.

Key takeaways

  • A coding agent edits files and runs commands in your repository in a loop, so the useful skills are giving it context, giving it a check it can run, and reviewing the result.
  • Instruction files such as CLAUDE.md and AGENTS.md carry what the agent cannot infer, but they are advice and must stay short, while only permissions, hooks, sandboxes and CI enforce anything.
  • Tests the agent wrote itself can share its misunderstanding, so derive some cases from the requirement and review the diff as you would a colleague's pull request.
  • Limit what the agent can touch by using a branch, development credentials only, a sandbox and approval settings that match the customer's risk.
  • Vibe coding means not reviewing the code; it is acceptable for throwaway work and not for code that handles customer data, credentials, payments or production systems.
  • Evidence on speed is mixed and people misjudge their own speed-up, so measure results on your own tasks instead of trusting a single number.

Example 1 of 5

Claude Code: a project CLAUDE.md, a check to run and permission rules

AnthropicDocumented in official docs

Anthropic's Claude Code documentation describes how the terminal agent remembers a project (the memory page), how to work with it (the best-practices page) and how its actions are permissioned (the permissions page). [2][1][5]

The problem

A developer wants an agent to make multi-file changes in an existing repository without re-explaining the build command, the test runner and the team's conventions in every session, without approving every step, and without letting the agent run arbitrary commands. Each Claude Code session begins with a fresh context window, and the agent stops when the work looks done, so by default it knows neither the conventions nor how to prove its change works.

Where this topic fits

The instruction file is loaded before the first prompt. The check closes each pass of the agent loop, and the permission rules gate the actions between passes. The developer's review of the diff is the last step before a commit.

How it is applied, step by step

  1. Run `/init` to generate a starter CLAUDE.md from the project structure, then cut it down to the commands and conventions the agent cannot guess from the code.
  2. Check the file into git so the team shares it, and run `/context` in a session to confirm that it loaded.
  3. Prompt with scope, a pattern to copy and a verification step, for example "write a failing test that reproduces the issue, then fix it".
  4. Let the agent read, edit and run the check in a loop. Pre-approve the safe commands (running the tests) and deny the dangerous ones (pushing, reading secret files) through permission rules.
  5. Review the diff and the evidence the agent shows, then commit. When a review catches something the agent should have known, add a line to CLAUDE.md.

Why this approach fits

A multi-file change in a repository with its own build and test commands is where the agent's missing knowledge (the commands and conventions) and missing feedback (does it pass?) cost the most. Both are cheap to supply once and reuse in every session. Pre-approved rules let the developer decide in advance what is safe instead of clicking through prompts until approval becomes a habit.

Limitation or tradeoff

The instruction file is context, not enforced configuration, so the agent can still ignore a line, especially in a long file. Anthropic lists the over-specified CLAUDE.md among common failure patterns. The deny rules cover the agent's file tools and the file commands it recognises, but not a script that reads files indirectly, so strong guarantees need the sandbox as well.

What the sources document

  • The memory page says each Claude Code session begins with a fresh context window, that CLAUDE.md files are loaded at the start of every session, and that Claude treats them as context, not enforced configuration. It recommends targeting under 200 lines per file. [2]
  • The best-practices page says to include Bash commands Claude cannot guess, code style rules that differ from defaults and testing instructions in CLAUDE.md, and to leave out anything Claude can work out by reading the code. [1]
  • The best-practices page says Claude stops when the work looks done, recommends giving it a check it can run such as tests, a build, a linter or a screenshot comparison, and lists the trust-then-verify gap as a failure pattern, with the advice that code you cannot verify should not ship. [1]
  • The permissions page says rules are evaluated in the order deny, ask, allow with the first match deciding, so an allow rule cannot make an exception to a deny rule. It also says Read and Edit deny rules do not cover subprocesses that read files indirectly and points to the sandbox for OS-level enforcement. [5]

The facts above come from the cited sources. The steps and analysis in this example are our explanation of how they fit together.

Example 2 of 5

AGENTS.md in a monorepo, read by Codex and several other coding agents

OpenAIDocumented in official docs

OpenAI's Codex documentation page on custom instructions with AGENTS.md explains how Codex builds its instructions from AGENTS.md files. The AGENTS.md site lists other agents that read the same format, and the Cursor and GitHub documentation confirm that they read nested files too. [7][6][11][18]

The problem

A monorepo holds several services with different commands and rules, for example a payments service with stricter conventions than a search service, and developers use different coding agents. One instruction file per tool per folder would drift apart. One giant root file would spend context on rules that matter in a single folder.

Where this topic fits

The files are read before the agent does any work and sit between the user's prompt and the code. The agent assembles a chain from the repository root down to the folder it works in, and closer files refine or override the ones above them.

How it is applied, step by step

  1. Put repository-wide expectations, such as the test command and pull request conventions, in AGENTS.md at the repository root.
  2. Add an AGENTS.md inside each service folder with only that service's commands and rules, such as how to run its tests.
  3. Where a folder needs a stricter or temporary rule set, add an AGENTS.override.md there. Codex checks the override file first in each folder and includes at most one file per folder.
  4. At startup Codex reads the global file in ~/.codex, then each folder from the Git root down to the working directory, and joins the files in that order so the closest text comes last.
  5. Codex stops adding files once the combined text reaches 32 KiB by default, so each file has to stay short.
  6. Cursor combines nested AGENTS.md files with those in parent directories, and GitHub's Copilot agents give precedence to the nearest one, so one set of files can serve a team that mixes tools.

Why this approach fits

Per-folder files keep each rule next to the code it governs, and because the nearest file wins, a service can tighten the repository-wide rules without editing them. A plain Markdown format with no required fields lets one file serve several tools, so the team does not maintain parallel copies of the same guidance for each product.

Limitation or tradeoff

Conflicts are settled by position in the combined text, not by a rule engine, so contradictory lines at different levels can still confuse a model. Files are added from the root down and Codex stops at its size limit, so in our reading of those two rules a large root file can crowd out the more specific file nearest the code.

What the sources document

  • The Codex page says Codex reads the global file in ~/.codex first, then walks from the Git root to the current directory checking AGENTS.override.md, AGENTS.md and any configured fallback names in each folder, with at most one file per folder. Files are joined from the root down, so closer files appear later and override earlier guidance. [7]
  • The Codex page says Codex skips empty files and stops adding files once the combined size reaches project_doc_max_bytes, which is 32 KiB by default. [7]
  • The AGENTS.md site describes the format as a README for agents with no required fields, now stewarded by the Agentic AI Foundation under the Linux Foundation. It lists Codex, Cursor, GitHub Copilot's coding agent, Gemini CLI, Jules, Devin and Aider among the tools that support it, and says that in a monorepo the closest file in the directory tree takes precedence. [6]
  • Cursor's rules page says nested AGENTS.md files are combined with those in parent directories, with more specific instructions taking precedence. [11]
  • GitHub's page on repository custom instructions says AGENTS.md files can be placed anywhere in a repository and that the nearest file in the directory tree takes precedence when Copilot is working. [18]

GitHub Copilot cloud agent: background tasks behind a human-approved pull request

GitHubDocumented in official docs

GitHub's documentation for the Copilot cloud agent consists of an overview page, a Risks and mitigations page that lists the controls GitHub built in, and a page on reviewing the pull requests Copilot opens. [15][16][17]

The problem

A team wants to hand well-defined issues to an agent that works in the background, without letting it merge its own work, write to other branches or reach secrets through CI. The result arrives as a pull request that another person must be able to inspect and trust enough to merge.

Where this topic fits

Between the issue and the merge. The agent runs its edit-and-test loop in an ephemeral environment, and platform rules about branches, approvals and workflow runs guard the boundary. The human review step is enforced by GitHub, not left to convention.

How it is applied, step by step

  1. A user with write access starts a task from the agents panel, a conversation, or an issue or pull request.
  2. The agent researches the repository, plans, edits files and runs tests and linters in an ephemeral cloud development environment instead of the developer's editor.
  3. It can push to only one branch: a new branch with a copilot/ prefix, or the branch of the pull request it was asked to change.
  4. Copilot opens a draft pull request. It cannot mark the pull request ready for review, approve it or merge it.
  5. GitHub Actions workflows do not run on Copilot's pushes until a reviewer clicks Approve and run workflows, so the reviewer reads the diff first, with extra care for changes under .github/workflows/.
  6. Someone other than the requester approves, because the requester's approval does not count toward required approvals. Changes are requested by mentioning @copilot in a comment.

Why this approach fits

Asynchronous delegation only works if the reviewer can rely on the boundaries without re-checking them each time. Enforcing who may approve, which branch the agent may write to and when CI may run turns the advice to always review agent code into something a hurried team cannot skip by accident.

Limitation or tradeoff

The controls limit where the agent writes and who can merge. They do not make the code correct. GitHub's own page warns that agent output can be incorrect or insecure, and a reviewer who skims a large diff gives a weaker guarantee than the rule suggests.

What the sources document

  • The overview says the cloud agent can research a repository, plan changes and implement them in the background, editing files and running tests and linters in an ephemeral cloud development environment, and that work can start from the agents panel, a conversation, or an issue or pull request. [15]
  • The overview warns that chat and agentic experiences can produce incorrect or suboptimal code, including code with security vulnerabilities, and says to review and test the output before using it in production. [15]

[16]

  • The review page says that if a repository requires approvals, the requester's approval of a Copilot pull request does not count, and that Actions workflows do not run automatically on Copilot's pushes until a reviewer clicks Approve and run workflows. [17]

Google's LLM-assisted code migrations, validated by builds, tests and human review

GoogleDocumented in a paper

An experience report by Google engineers, posted on arXiv in January 2025, on using LLMs to migrate code in Google's monorepo: widening ID types from 32 to 64 bits, moving tests from JUnit3 to JUnit4 and other migrations. The authors state that it is an experience report and not a research study. [19]

The problem

Google Ads has dozens of ID types that were defined as 32-bit integers and were expected to overflow as the business grew, in a code base of more than 500 million lines. Changing them touches very many files and needs edits that depend on the surrounding code, so a find-and-replace is not enough. Having people make every edit would be slow.

Where this topic fits

The model drafts each edit, but inside a pipeline. Tools decide which files to change, automated validation builds and tests each result, and engineers review the change before it lands. The model is one stage among several.

How it is applied, step by step

  1. Engineers identify where to change code using tools such as Kythe cross-references and Code Search, plus custom scripts.
  2. For each location the model, a Gemini model fine-tuned on Google's code, receives the file with natural-language instructions and proposes edits.
  3. Automated validation builds the changed files and runs their unit tests. A failed validation can trigger an ML-powered repair that sees the error.
  4. Engineers review the change as they would any other, adding tests for lines that are not covered.
  5. The change lands once it passes. In the JUnit migration the authors report that the speed of review was the bottleneck.

Why this approach fits

The work is repetitive, each edit can be checked by compiling and running existing tests, and the volume is far beyond manual effort. Those are the conditions in which a verification step can close the loop automatically, leaving humans to review finished, passing changes with their normal tools.

Limitation or tradeoff

This is a bespoke pipeline built by a company with large tooling investment, not a prompt typed into an agent. The authors write that simple prompting alone is not enough for anything but the simplest migrations and that a combination of AST-based techniques, heuristics and LLMs was needed, and that any long-term effect on quality remains to be seen. Their figures are estimates from an experience report, not a controlled comparison.

What the sources document

  • For the ID migration, the paper reports that 80% of the code modifications in the landed changes were fully AI-authored, measured against the model's first snapshot of each change, and says the engineers doing the migration estimated that total time was reduced by 50%. [19]
  • For JUnit3 to JUnit4, the authors report migrating 5,359 files and changing more than 149,000 lines of code in three months, with about 87% of the AI-generated code committed without any change. [19]
  • The paper says edits come from a version of Gemini fine-tuned on internal Google code and data, that the two most common validations are building the changed files and running their unit tests, and that a failed validation step can run an ML-powered repair. [19]
  • The paper says humans review the LLM-generated code the same way as any other code and add tests for changed lines, and that in the JUnit migration the bottleneck was the speed at which engineers could review the changes. [19]
  • The authors write that using LLMs alone through simple prompting is not sufficient for anything but the simplest migrations, and describe the article as an experience report, not a research study. [19]

4Common mistakes

  1. Approving a change because the agent's own tests pass

    Why it causes problems
    Tests written alongside the code share its assumptions, so a green run shows only that the code agrees with itself. In the worked example the agent's four tests passed while the function undercharged for part kilograms and rounded ties the wrong way.
    How to recognise it
    The new tests use only inputs the code handles well, their expected values look like the function's own output, and no test covers a boundary from the requirement.
    How to fix it
    Write cases from the requirement first, run them against the draft and confirm they fail for the right reason, and review test changes separately from code changes.

  2. Writing a very long instruction file

    Why it causes problems
    Anthropic warns that a bloated CLAUDE.md makes the agent ignore your real instructions because important rules get lost, and every line costs context in every session. Codex stops adding files at 32 KiB.
    How to recognise it
    The agent breaks a rule that is written down. The file holds file-by-file descriptions, generic advice such as "write clean code", or text copied from other documentation.
    How to fix it
    For each line ask whether removing it would cause mistakes, and delete it if not. Link to documentation instead of copying it, and move rules that matter in one folder into a nested file or a scoped rule.

  3. Giving the agent more access than the task needs

    Why it causes problems
    A broad rule such as Bash(git *) also allows git push, an approval prompt clicked without reading is no control, and modes such as danger-full-access or Run Everything remove the sandbox. Remote systems are beyond undo, since checkpoints cover only file edits.
    How to recognise it
    The agent's shell can see production credentials, the allow list contains broad wildcards, or you approve prompts without reading them.
    How to fix it
    Use development credentials, allow specific commands, deny destructive ones, run inside a sandbox or dev container, and keep branch protection and required reviews on the server where the agent cannot change them.

  4. Running one long session for everything

    Why it causes problems
    The context fills with unrelated files and failed attempts, quality drops, and compaction can lose detailed early instructions. Correcting the same error again and again leaves the failed approaches in context.
    How to recognise it
    The agent repeats a mistake you already corrected, asks about something you told it earlier, or gets slower and vaguer as the session grows.
    How to fix it
    Clear the context between unrelated tasks. After two failed corrections, restart with a better prompt that includes what you learned. Keep lasting rules in the instruction file and use a fresh session for research or review.

  5. Handing vibe-coded output to a customer as finished work

    Why it causes problems
    The customer inherits code nobody reviewed. Veracode reports that 45% of the AI-generated code samples it tested failed its security tests, and a module nobody can explain cannot be maintained or defended in an incident.
    How to recognise it
    No one on the team can explain a module, there are no tests that come from the requirements, and the dependency list includes packages nobody chose.
    How to fix it
    Apply the rule of not committing code you could not explain to somebody else. Review, test, run static analysis and dependency checks, and hand over tests and notes. Label demos as demos.

  6. Prompting vaguely and accepting a large diff

    Why it causes problems
    With a vague goal the agent guesses the scope, touches files it should not and over-builds. A large diff is hard to review well, so defects slip through.
    How to recognise it
    The diff spans many unrelated files, the agent stated no assumptions, and you cannot describe the change in a couple of sentences.
    How to fix it
    State the goal, context, constraints and done criteria. Name the files. Ask for a plan when several files are involved, and split the work until each change is small enough to review properly.

Exercise 1

Review an agent's pagination helpers with tests from the requirement

CodingBeginnerAbout 40 min (estimate)Hypothetical scenario

An agent was asked to add pagination helpers for the requirement below. It wrote the code and three tests, and reported that the tests pass. Review it the way this lesson describes. You need Python 3 and its standard library only.

Requirement

  • page_count(total_items, page_size) returns how many pages are needed. Zero items need zero pages. A page_size below 1 raises ValueError.
  • page_slice(items, page, page_size) returns the items on one page. Pages are numbered from 1. A page past the last page returns an empty list. A page or page_size below 1 raises ValueError.

The agent's pagination.py

python
def page_count(total_items, page_size):
    return total_items // page_size + 1


def page_slice(items, page, page_size):
    start = page * page_size
    return items[start:start + page_size]

The agent's test_pagination.py

python
import unittest

from pagination import page_count, page_slice

ITEMS = list(range(10))


class AgentTests(unittest.TestCase):
    def test_count(self):
        self.assertEqual(page_count(10, 3), 4)

    def test_first_page(self):
        self.assertEqual(page_slice(ITEMS, 0, 3), [0, 1, 2])

    def test_second_page(self):
        self.assertEqual(page_slice(ITEMS, 1, 3), [3, 4, 5])

Requirements

  • Write at least five test cases from the requirement alone, with expected values worked out by hand, in a class named `SpecTests` in the same file.
  • Run the file against the agent's code and record which tests fail and the message of each failure.
  • Fix `pagination.py` so that every `SpecTests` test passes.
  • Identify any of the agent's tests that contradict the requirement, and delete or correct them.
  • Write a two-line addition to an AGENTS.md file that would have helped the agent get the page numbering right.

Expected behaviour

Against the agent's code its three tests pass, so by its own measure the work is done. With the six example SpecTests from the solution, python3 -m unittest test_pagination reports Ran 9 tests and FAILED (failures=4): an exact multiple of the page size gets one page too many, zero items give 1 page instead of 0, page 1 returns the second page, and invalid arguments are accepted. After your fix and after removing the two agent tests that assume 0-based pages, the run ends with OK.

Hint 1

Work out each expected value by hand from the requirement. Do not run the draft to find out what it returns.

Hint 2

Test the edges - zero items, an exact multiple of the page size, one item over a multiple, the first page, the last page, a page past the end and invalid inputs.

Hint 3

A test can pass by luck. Check by hand whether `page_count(10, 3)` is right for the reason the draft implies.

Hint 4

Ceiling division without importing anything is `-(-a // b)`.

Show solution

Spec tests. These six cases come from the requirement and cover the edges listed in the hints:

python
class SpecTests(unittest.TestCase):
    def test_count_exact_multiple(self):
        self.assertEqual(page_count(9, 3), 3)

    def test_count_empty(self):
        self.assertEqual(page_count(0, 5), 0)

    def test_count_partial_last_page(self):
        self.assertEqual(page_count(10, 3), 4)

    def test_pages_are_one_based(self):
        self.assertEqual(page_slice(ITEMS, 1, 3), [0, 1, 2])
        self.assertEqual(page_slice(ITEMS, 4, 3), [9])

    def test_page_past_the_end_is_empty(self):
        self.assertEqual(page_slice(ITEMS, 5, 3), [])

    def test_invalid_arguments(self):
        with self.assertRaises(ValueError):
            page_slice(ITEMS, 0, 3)
        with self.assertRaises(ValueError):
            page_slice(ITEMS, 1, 0)
        with self.assertRaises(ValueError):
            page_count(10, 0)

Failures against the draft. With the agent's three tests kept alongside, the run prints Ran 9 tests and FAILED (failures=4):

Failing testDraft returnsRequirementCause
test_count_exact_multiple43// + 1 adds a page when the items divide evenly
test_count_empty10the same formula
test_pages_are_one_based[3, 4, 5][0, 1, 2]page * page_size treats pages as 0-based
test_invalid_argumentsno ValueErrorValueErrorthe draft has no validation

The agent's tests. test_first_page passes page 0 and test_second_page expects [3, 4, 5] for page 1, so both encode the 0-based convention and contradict the requirement. Delete them. test_count agrees with the requirement, but only by luck: 10 // 3 + 1 happens to equal the ceiling of 10/3.

The fix:

python
def page_count(total_items, page_size):
    if page_size < 1:
        raise ValueError("page_size must be at least 1")
    return -(-total_items // page_size)


def page_slice(items, page, page_size):
    if page < 1 or page_size < 1:
        raise ValueError("page and page_size must be at least 1")
    start = (page - 1) * page_size
    return items[start:start + page_size]

With only SpecTests left in the file, python3 -m unittest test_pagination prints Ran 6 tests and OK.

The instruction file lines:

markdown
- Page numbers are 1-based everywhere in this codebase. Page 0 is invalid and raises ValueError.
- Expected values in tests come from the written requirement, never from running the code under test.

  • Do your spec tests fail against the draft for the reasons in the table, and not for a mistake in the tests?
  • Did you remove or correct the two agent tests that assume 0-based pages, and can you say why?

Exercise 2

Set up permissions, instructions and review for a customer repository

DesignIntermediateAbout 35 min (estimate)Hypothetical scenario

A customer lets you use a coding agent on their Python repository invoice-portal. You know these facts:

  • .env holds the database URL and credentials, and the test suite loads .env through a library.
  • deploy.sh deploys to production. The customer's release engineer runs it by hand.
  • data/samples/ holds real invoices with customer names and addresses.
  • migrations/ is reviewed by the customer's database administrators, and nobody else edits it.
  • CI deploys to production when a pull request is merged to main. Branch protection requires one approval from a customer engineer.
  • The contract allows sending source code to the model provider but not personal data.

Produce a written answer. You can do it with a text editor and Python 3 to check the JSON.

Requirements

  • A `settings.json` in the Claude Code permission syntax that allows only the commands the agent's inner loop needs (run tests, show a diff, commit locally).
  • Deny rules for reading secrets and sample data, editing migrations, running the deploy script and pushing.
  • Name one way these rules alone would still fail to protect `.env`, and add a second control that closes the gap.
  • A review policy of at most six bullets, with each bullet marked as advisory or enforced and what enforces it.
  • A decision, with a reason, on whether vibe coding is acceptable for (a) a script that reformats a CSV export of fake data for a demo and (b) a new endpoint that reads invoices.

Expected behaviour

The JSON parses with python3 -m json.tool settings.json. The deny list covers .env, the sample data, migrations, the deploy script and git push. The answer notices that the test suite reads .env itself, which a Read deny rule does not cover. Review bullets distinguish enforced controls (branch protection on the server, the sandbox, credentials the agent never holds) from advisory ones (the instruction file, and permission rules, which match only the usual spelling of a command). Task (a) is acceptable and (b) is not.

Hint 1

Rules are evaluated deny first, so you can allow a broad command family and still deny one member of it, but a broad allow like `Bash(git *)` would also permit pushes unless you deny them.

Hint 2

Ask what a Python process started by the test command can read, and whether the Read deny rules apply to it.

Hint 3

Decide for each control whether the agent could ignore it. If it can, the control is advisory.

Hint 4

Think about who inherits the code and what data the endpoint touches when you answer (a) and (b).

Show solution

A permissions file (.claude/settings.json):

json
{
  "permissions": {
    "allow": [
      "Bash(python3 -m pytest *)",
      "Bash(git diff *)",
      "Bash(git commit *)"
    ],
    "deny": [
      "Read(./.env)",
      "Read(./data/samples/**)",
      "Edit(./migrations/**)",
      "Bash(./deploy.sh *)",
      "Bash(git push *)"
    ]
  }
}

Deny rules are checked before allow rules, so these denials hold even if a broader allow rule is added later. They match the command as written, though: git -C . push or bash deploy.sh is not matched, which is why the review table below calls them only part of the control.

The gap. Claude Code's Read deny rules cover its file tools and the file commands it recognises in Bash, but not a subprocess that opens files itself. The test command starts Python, and the library loads .env, so the agent can run code that uses the credentials even though it cannot read the file. Close the gap with a second control: make .env hold development credentials only, never production ones, and run the agent inside a sandbox or dev container that does not contain the production values.

A short instruction file (advisory):

markdown
# invoice-portal
- Run tests with `python3 -m pytest`. Never run deploy.sh or git push.
- Do not read .env or data/samples/. Use the fake fixtures in tests/fixtures/.
- migrations/ belongs to the DBAs. Propose a migration in the pull request text instead.
- Money is Decimal. Every new rule needs a test whose expected values come from the ticket.
