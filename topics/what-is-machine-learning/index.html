What Is Machine Learning?

Machine learning (ML) is a way of building software in which the rule that turns inputs into outputs is worked out from example data by an algorithm instead of being written by a programmer. The learned rule, called a model, is then used to make predictions on data it has not seen before.

1Overview

Why it matters

Some software cannot be written as a list of rules. Nobody can type out the conditions that separate spam from real email, turn a restaurant order into an accurate delivery time, or tell which word in a search query changes its meaning. Examples of the right answer, however, are plentiful. Machine learning is the method for turning those examples into working software, and it decides whether products like these can exist at all.

The common failures come from misjudging what ML is. Teams train a model where a ten-line rule would have done the job, choose a kind of learning that their data cannot support (a supervised model with no labels), or stop at a model that scores well in a notebook and never check it again after launch, while the world it was trained on drifts away. Anyone who builds, buys or manages a data-driven feature needs the vocabulary in this lesson to avoid those mistakes, and anyone choosing between an ML engineer path and an AI engineer path needs to know how the two jobs differ.

Before you start

No prerequisites. You can start here.

What you will be able to do

  • Explain how a learned model differs from a hand-written rule, and name what a person still decides in both cases.
  • Tell supervised, unsupervised, semi-supervised, self-supervised and reinforcement learning apart by the feedback each one learns from.
  • Train a one-threshold classifier by hand on a small table and reproduce the lesson's rule and accuracies.
  • Describe the five stages of the ML workflow (data, train, evaluate, deploy, monitor) and what goes wrong at each.
  • Decide whether a problem calls for a rule, a trained model or a pre-trained model behind an API.
  • Describe how the work of an ML engineer differs from the work of an AI engineer.

Key terms

Model
What training produces. A rule with numbers in it (parameters) that turns an input into a prediction.
Feature
One input value the model is allowed to look at, such as the number of links in an email.
Label
The known right answer attached to a training example, such as "spam" or "not spam".
Training
The search for parameter values that make the model's predictions match the training data as closely as possible.
Inference
Using a trained model to make a prediction for a new input. No learning happens at this point.
Generalisation
How well a model predicts on data it was not trained on. It is the thing evaluation tries to measure.
Supervised learning
Learning from examples that each come with a label, in order to predict the label for new inputs.
Unsupervised learning
Learning from inputs that have no labels, by finding structure such as groups of similar rows or rows unlike the rest.
Reinforcement learning
Learning by acting. An agent tries actions in an environment and adjusts its behaviour to collect more reward.
Concept drift
A change over time in how the features relate to the label, which makes a model less accurate although nothing in its code changed.

2Explanation

Introduction

You already know how ordinary software gets its behaviour: a person thinks of a rule and types it in. To keep junk out of an inbox you might write if links >= 3: spam. The computer follows that rule exactly. When the rule turns out to be wrong, a person has to notice and rewrite it.

Machine learning changes who writes the rule. You collect inputs together with the answer you wanted, for example emails that people have marked as spam or not spam, and hand them to a learning algorithm. The algorithm searches for a rule that reproduces those answers and returns it. The returned rule is called a model. Google's introductory course describes ML (opens in a new tab) in the same terms: software, the model, is trained on data until it can make useful predictions or generate content.

Three things stay the same. A person still decides what to predict, which features (input values, such as the number of links) the model may look at, and how a good answer is measured. The model is still an ordinary function: input in, prediction out. What changes is that the numbers inside the function come from data, so they can be recomputed when the data changes.

Tom Mitchell's definition turns "learning" into something you can check. A machine learns a task T if its performance at T, measured by some score P, reliably gets better as it gains experience E (The Discipline of Machine Learning (opens in a new tab)). For a spam filter, T is labelling an email, P is the share of emails labelled correctly and E is a set of emails with known labels. If more experience does not improve P, nothing is being learned.

The same paper names two situations in which ML beats hand-written code. In the first, the task is too complex for anyone to write down the algorithm although labelled examples are easy to collect: everyone can say which photos show their mother, and nobody can write the rule. In the second, the software has to adapt after it ships, like an email reader that learns one user's idea of spam.

This lesson covers how a model is learned, the kinds of learning (supervised, unsupervised, semi-supervised, self-supervised and reinforcement), the workflow that takes a model from data to monitored production use, and how an ML engineer's job differs from an AI engineer's.

How it works

Learning is a search for parameters

A model starts as a template with blanks in it. For the spam example the template is "spam if feature ≥ threshold", and the blanks are which feature and which number. The blanks are the model's parameters. Training fills them in:

  1. Take a candidate set of parameter values.
  2. Run the model on the training examples and measure how wrong it is. That measure is the loss. Here it is the number of emails labelled wrongly.
  3. Keep the candidate with the lowest loss.
python
def train(examples, candidates, loss):
    """Return the candidate parameters with the lowest loss on the examples."""
    return min(candidates, key=lambda params: loss(params, examples))

Learning algorithms differ mainly in how they search. With twelve candidates you can try them all, as the worked example does. Linear regression solves for the best parameters directly. A neural network has millions of parameters, so it starts from random values and repeatedly nudges them in the direction that lowers the loss, which is gradient descent.

A low loss on the training examples is not the goal. The goal is good predictions on inputs the model has never seen, called generalisation. That is why some labelled examples are held back from training and used only for scoring (see train/test splits). Using the trained model on a new input is inference. Google's course walks through the same train, evaluate, infer sequence (opens in a new tab).

Five kinds of learning, told apart by the feedback

The kinds of ML differ in where the "right answer" comes from during training.

  • Supervised learning. Every training example has a label. Predicting a number, such as a delivery time, is regression. Predicting a category, such as spam or not spam, is classification.
  • Unsupervised learning. There are no labels. The algorithm looks for structure: groups of similar rows (clustering) or rows unlike the rest (anomaly detection). Given a pile of emails with no labels, it can sort them into groups of similar messages, but it cannot say which group is spam. A person has to interpret what it finds.
  • Semi-supervised learning. A few examples are labelled and many are not. One technique, self-training, fits a model on the labelled rows, predicts labels for the unlabelled rows, adds the confident predictions as if they were labels and repeats. scikit-learn's semi-supervised module (opens in a new tab) marks unlabelled rows with the label -1.
  • Self-supervised learning. There are no human labels, but labels are manufactured from the data. Hide one word of "the parcel arrived late" and ask the model to predict it: the [MASK] arrived late has the answer parcel. Google's ML glossary (opens in a new tab) defines this as creating surrogate labels from unlabelled examples. It is how large language models are pre-trained.
  • Reinforcement learning (RL). Nobody supplies right answers. An agent takes actions in an environment, receives a reward, and learns a policy, a mapping from situations to actions, that collects the most reward over time. See reinforcement learning basics.

These categories describe the training signal, not the kind of model. The same network design can often be trained in more than one of these ways, and real systems combine them: pre-train with self-supervision on plain text, then fine-tune with supervision on a small labelled set (transfer learning). Generative AI is not a sixth kind of feedback. Google's course lists it as a category of ML system but defines it by what the model does, creating content from user input, and the large language models behind much of it are pre-trained with self-supervision.

The workflow: data, train, evaluate, deploy, monitor

Training is one step of five. Google Cloud's MLOps guide (opens in a new tab) lists eight finer steps, from data extraction to model monitoring. They group as follows.

  1. Data. Decide what to predict and how success is measured. Collect examples, clean them, and split them into training and test sets. This is often the costliest stage: the engineers behind Uber's Michelangelo platform (opens in a new tab) write that building and managing data pipelines is typically one of the most costly pieces of a complete ML solution. What goes wrong here is quiet: labels that do not measure what the product needs, or a dataset that is large but misses cases the model will meet (see the edge cases below).
  2. Train. Fit one or more kinds of model and tune their settings. The risk is a model that fits the training rows too closely, even by memorising them, which a training score alone cannot reveal. The first exercise below shows a lookup table doing exactly that.
  3. Evaluate. Score each model on held-out data and compare it with a baseline: a simple rule, or the system in use today. A model that does not beat the baseline is not deployed.
  4. Deploy. Put the model where predictions are needed: a service behind an API, a nightly batch job or a phone. Features must be computed in production exactly as they were in training. A difference between the two is training-serving skew.
  5. Monitor. The world keeps changing after launch. Spammers adapt, prices move, habits shift. When the relation between features and label changes (concept drift), the model gets worse although nobody touched it. The MLOps guide says models can decay in more ways than conventional software, so you track statistics of the incoming data and the model's live accuracy, and retrain when they move.

The loop closes because the outcomes logged during monitoring become labelled data for the next training run. Failures here are quiet. Google's Rules of ML (opens in a new tab) describes a data table that sat stale for six months while the product kept working, only worse. The MLOps guide also notes that only a small fraction of a real ML system is ML code. The rest is data collection, verification, serving and monitoring.

ML engineer and AI engineer

Both roles build products on models. They differ in whether the model is something you produce or something you start from.

The table is our summary of two sources. Google Cloud's Professional ML Engineer (opens in a new tab) description says the role builds, evaluates, productionizes and optimizes AI solutions, with proficiency in model architecture, data and ML pipeline creation, MLOps and metrics interpretation. The 2023 essay that popularised the newer title, The Rise of the AI Engineer (opens in a new tab), describes software engineers who build on foundation models through APIs, and cites Andrej Karpathy's view that a person can do well in the role without training any model.

The border is open in both directions. The essay notes that AI engineers also fine-tune and host models, and Google's certification description now expects familiarity with prompt and context engineering and has the ML engineer designing and operationalising solutions based on foundation models. The ideas in this lesson, a held-out test set, a baseline and monitoring for drift, apply on both sides. The other path starts at What is AI engineering?.

Step 1: the hand-written rule

A programmer guesses: spam if links >= 3. On the 12 emails this flags email 6 by mistake (a newsletter with three links) and misses emails 7 and 12, which have few links. That is 3 mistakes, or 9 of 12 correct.

Step 2: train

Keep the template "spam if feature ≥ t" and let the data fill the blanks. A one-threshold model of this kind is called a decision stump, the smallest possible decision tree. Count the training mistakes for every feature and every threshold from 1 to 6:

Threshold t123456
Mistakes of links >= t433345
Mistakes of caps >= t321356

Check one cell by hand. caps >= 3 flags emails 7, 9, 10, 11 and 12, all spam, and no others. It misses only email 8, which has one word in capitals. One mistake is the lowest count in the table, so the learned model is spam if caps >= 3, with 11 of 12 correct. Nobody told the algorithm to prefer caps. The count did.

Step 3: evaluate on emails the model has not seen

Six more labelled emails were set aside before training. The script below scores both rules on them.

python
# Each email: (links, caps, label). label 1 = spam, 0 = not spam.
train = [(0, 0, 0), (1, 0, 0), (0, 1, 0), (2, 0, 0), (1, 2, 0), (3, 1, 0),
         (2, 3, 1), (4, 1, 1), (5, 4, 1), (3, 5, 1), (6, 3, 1), (1, 4, 1)]
test = [(0, 0, 0), (4, 0, 0), (1, 1, 0), (2, 4, 1), (5, 3, 1), (3, 2, 1)]
later = [(3, 0, 0), (0, 1, 0), (2, 3, 0), (5, 0, 1), (6, 1, 1), (4, 0, 1)]
FEATURES = ["links", "caps"]

def hand_rule(email):
    return 1 if email[0] >= 3 else 0          # the programmer picked "links" and "3"

def make_model(feature, threshold):
    return lambda email: 1 if email[feature] >= threshold else 0

def mistakes(predict, emails):
    return sum(predict(e) != e[2] for e in emails)

def train_stump(emails):
    """Try every feature and every threshold; keep the pair with the fewest mistakes."""
    best = None
    for feature in (0, 1):
        for threshold in range(1, 7):
            m = mistakes(make_model(feature, threshold), emails)
            if best is None or m < best[0]:
                best = (m, feature, threshold)
    return best

m, feature, threshold = train_stump(train)
model = make_model(feature, threshold)
print(f"learned rule: spam if {FEATURES[feature]} >= {threshold} ({m} training mistake)")
for name, emails in [("train", train), ("test", test), ("later", later)]:
    n = len(emails)
    print(f"{name:5}  hand rule {n - mistakes(hand_rule, emails)}/{n}   learned rule {n - mistakes(model, emails)}/{n}")

m2, f2, t2 = train_stump(train + later)
print(f"retrained: spam if {FEATURES[f2]} >= {t2} ({m2} mistakes on {len(train + later)} emails)")
text
learned rule: spam if caps >= 3 (1 training mistake)
train  hand rule 9/12   learned rule 11/12
test   hand rule 4/6   learned rule 5/6
later  hand rule 5/6   learned rule 2/6
retrained: spam if links >= 4 (3 mistakes on 18 emails)

On the test set the learned rule gets 5 of 6 (83 %), a little below its 92 % on the training set, which is normal. The test score is the honest estimate of how the model will do in use. The hand rule gets 4 of 6.

Step 4: deploy and monitor

Deploying this model means shipping the function caps >= 3. Some weeks later six new emails arrive, and users label them (later in the script). Spammers have stopped writing in capitals and now send plain text with many links. The deployed model scores 2 of 6. It still runs without errors, and only a comparison of its predictions with fresh labels shows the drop. This is concept drift.

The hand rule scores 5 of 6 on that batch, because it happens to use the feature the spammers moved to. Neither rule noticed that the world had changed.

Step 5: retrain

Run the same search on the 18 labelled emails now available. The result changes to spam if links >= 4, with 15 of 18 correct. Nobody edited the rule. The data changed and the rule followed. One threshold cannot describe both the old and the new spam, though. A model that may use both features, spam if links >= 4 or caps >= 3, gets 17 of 18 on the same emails. More capable models are, at bottom, templates with more blanks.

The same model from a library

Libraries package the search. Appended to the script above, this fits the same stump with scikit-learn (documentation version 1.9.1), using the fit method shown in its getting started guide (opens in a new tab) and the score method, which returns the share of correct predictions for a classifier:

python
from sklearn.tree import DecisionTreeClassifier

X_train = [[links, caps] for links, caps, _ in train]
y_train = [label for *_, label in train]
X_test = [[links, caps] for links, caps, _ in test]
y_test = [label for *_, label in test]

stump = DecisionTreeClassifier(max_depth=1, random_state=0).fit(X_train, y_train)
print("feature:", stump.tree_.feature[0], " threshold:", stump.tree_.threshold[0])
print("test accuracy:", round(stump.score(X_test, y_test), 3))
text
feature: 1  threshold: 2.5
test accuracy: 0.833

Feature 1 is caps, and for whole numbers a split at 2.5 is the rule caps >= 3. A decision tree classifier scores each candidate split by Gini impurity, its default criterion. Computed by hand over every split of these 12 rows, the caps split at 2.5 has an impurity of about 0.14 and the next best candidate about 0.28, so the library and the hand search agree.

Eighteen emails prove nothing about real spam. The procedure is what carries over to real projects: choose a template, search for the parameters with the lowest loss, score on held-out data, watch the live score and retrain when it falls.

Edge cases and limitations

Rules and models usually run side by side
The choice is rarely rules or ML. Gmail's spam filtering combines rules-based protections with ML models, and Google's Rules of ML advises turning an existing heuristic into a feature of the model or applying it as a separate step instead of throwing it away. Keep hard requirements, such as a legal block list, as rules that cannot be outvoted, and let the model handle the cases in which evidence has to be weighed.
Labels that arrive late, or never
Monitoring accuracy needs the true outcome. A delivery-time model learns the real duration as soon as the order is delivered, but a loan-default model waits months and a spam filter only hears about the mistakes users bother to report. Until labels arrive you can only watch the inputs and the mix of predictions. Decide before launch where the labels will come from and how long they take, because that sets how quickly you can detect decay.
A large dataset that covers the wrong cases
A model learns the examples it is given, not the world. Google's course gives the case of a dataset holding 100 years of weather for the month of July only, which predicts January badly however many rows it has. Size and coverage are separate properties. Before training, list the situations the model will meet in use and check that each one appears in the data.
The same method under two names
Category names have shifted. Google's 2018 announcement of BERT calls its pre-training unsupervised, because no human labelled the text. Google's ML glossary names BERT as a model that uses self-supervised learning, because the training labels are made from the text itself, although its own BERT entry still mentions unsupervised training. Both describe the same procedure. The glossary also nests the terms: it calls self-supervised training a semi-supervised approach and self-training a variant of self-supervised learning. When you read a paper or a job description, look for where the training signal comes from and do not rely on the label alone.
Reinforcement learning needs somewhere safe to fail
An RL agent learns from the outcomes of its own actions, including a great many bad ones. That is acceptable inside a game, a simulator or a video encoder that can be run again, and unacceptable on patients or live payments. Without a cheap, faithful environment to practise in, a supervised model trained on logged decisions, or a hand-written policy, is usually the practical choice.
A pre-trained model moves the workflow but does not remove it
Calling a foundation model through an API skips data collection and training, which is why AI engineering can begin with a prompt. Somebody still trained that model, with self-supervision, on data you did not choose. You still have to evaluate it on your own held-out cases, compare it with a baseline and monitor it, because the provider can change the model and your users can change their questions.

When to use it, and when something simpler is enough

Use it when

  • Nobody can write the rule down, yet people can recognise the right answer, so labelled examples are cheap to collect (photos, speech, spam).
  • The behaviour has to adapt to each user or to conditions that keep changing, faster than a person could rewrite rules.
  • The decision weighs many weak signals together, and the hand-written rules have grown into a pile of special cases that nobody can maintain.
  • You have, or can start logging, enough examples that cover the situations the system will face, and a number that measures success.
  • Occasional wrong predictions are acceptable, and there is a way to observe them and correct course.

Think twice when

  • The logic is known and exact, such as a tax calculation, a sort or a unit conversion. Write the code, because a model can only approximate it.
  • There is no data yet. Launch with a simple heuristic, log what happens, and come back to ML when the examples exist.
  • A single wrong answer is unacceptable and cannot be caught by a rule, a check or a person.
  • Nobody will own monitoring and retraining after launch, so the model would decay unnoticed.
  • A pre-trained model behind an API already does the task well enough, which makes this an AI engineering problem and not a training problem.

A simpler alternative. Start with a heuristic: a rule of thumb such as "block senders who have sent spam before" or "rank the most recently used item first", plus the metric you would use to judge a model. Google's Rules of ML recommends exactly this order, a product that launches without ML and an ML model once data exists. The heuristic stops being enough when it has grown so many special cases that changing it is risky, or when its accuracy stalls while labelled data keeps accumulating.

Key takeaways

  • In machine learning a person chooses the task, the features and the measure of success, and an algorithm chooses the numbers inside the rule by searching for the lowest error on example data.
  • A model is judged on data it was not trained on, because the goal is correct predictions on new inputs and not a perfect score on old ones.
  • The kinds of learning differ in their feedback. Supervised uses labels, unsupervised has none, semi-supervised has a few, self-supervised makes labels from the data, and reinforcement learning uses rewards for actions.
  • Training is one of five stages. Data, training, evaluation, deployment and monitoring form a loop, and a deployed model decays when the world drifts away from its training data.
  • A simple rule is the right first version when there is no data yet or the logic is exact, and ML earns its place when the rules become too complex to maintain.
  • An ML engineer produces and operates models from data, while an AI engineer builds applications on pre-trained models, and both depend on held-out evaluation and monitoring.

Gmail spam filtering: learned models working beside hand-written rules

Google (Gmail)Documented in an engineering article

Gmail's spam protection, as described in a February 2019 Google Workspace blog post by the product manager for Gmail Security & Trust, and in the Gmail Help page on reporting spam. [11][12]

The problem

Spam is produced by people who change tactics as soon as a filter catches them, and every message carries a very large number of signals. Rules written by engineers catch the patterns somebody has already noticed. The post describes categories that were hard to detect: messages that are only an image, emails with hidden embedded content, and newly created domains that hide a small volume of spam inside legitimate traffic. What counts as spam also differs from one user to the next.

Where this topic fits

ML models sit in the filtering path next to the rules-based protections. Each incoming message is scored on many signals at once before it reaches the inbox or the Spam folder. User reports flow back from the mailbox to Google, which is where a supervised system gets its labels.

How it is applied, step by step

  1. An incoming message is turned into signals. The post says every email has thousands of potential signals; which ones Gmail uses is not published.
  2. Rules-based protections handle patterns that people have identified and written down. The sources do not list them; a typical example would be a block list of known bad senders.
  3. ML models look at the signals together and score the message, which lets them catch combinations that no rule author anticipated.
  4. Users click "Report spam" or "Not spam". The help page says Google receives a copy of a reported email and may analyse it. In supervised-learning terms each report is a label for that message. The sources do not describe the training pipeline, so treat this as the standard design and not as a documented detail.
  5. New models are trained and compared with the existing ones before they are added. The post mentions using TensorBoard to monitor training pipelines and to evaluate new models.
  6. The new models are added on top of the existing protections, not in place of them, and the cycle repeats as spam changes.

Why this approach fits

Spam filtering meets both of Mitchell's conditions from the introduction. The rule is too complex to write by hand, because it depends on thousands of weak signals in combination, and the software must keep adapting, both to each user and to senders who actively try to evade it. Retraining on fresh reports updates the filter without anyone rewriting conditions.

The rules still earn their place. A rule is the fastest fix for a pattern that is already understood, and it can be read and audited. What the post describes, models added alongside the rules and not in place of them, is the normal arrangement in production systems.

Limitation or tradeoff

A model learns from past reports, so a new kind of campaign gets through until enough labels have accumulated. The labels are noisy: one user's unwanted newsletter is another user's subscription, and most mistakes are never reported. Errors in the other direction are costly, because a real message in the Spam folder may never be read. The figure reported in the 2019 post is above 99.9 percent, not 100, and at Gmail's volume the remainder is still a large number of messages.

What the sources document

  • The post states that Gmail's existing ML models, in conjunction with its other protections, help block more than 99.9 percent of spam, phishing and malware from reaching Gmail inboxes. [11]
  • New protections built with TensorFlow complement the existing ML and rules-based protections, and the post reports that with them Gmail blocks around 100 million additional spam messages every day. [11]
  • The newly blocked categories named in the post are image-based messages, emails with hidden embedded content, and messages from newly created domains that try to hide a low volume of spam within legitimate traffic. [11]
  • The post says ML helps identify patterns in large data sets that the humans who create the rules might not catch, that every email has thousands of potential signals, and that ML-based protections help personalise spam protection for each user. [11]
  • The help page says that when you report spam or move an email into Spam, Google receives a copy of the email and may analyse it, and that as you report more spam Gmail identifies similar emails as spam more efficiently. [12]

The facts above come from the cited sources. The steps and analysis in this example are our explanation of how they fit together.

Example 2 of 5

Elastic anomaly detection: learning what normal looks like without labels

ElasticDocumented in official docs

The machine learning features of the Elastic Stack (Elasticsearch and Kibana), as described in Elastic's documentation: the overview of its ML features, the page on anomaly detection algorithms, the "Run a job" page and the API reference for creating an anomaly detection job. [13][14][15][16]

The problem

Operations and security teams store time series such as request counts, response times and bytes transferred for thousands of hosts and users. Nobody has gone through the history marking each reading as normal or abnormal, so there are no labels to train a classifier on. A fixed threshold does not help much either, because normal traffic at noon would be an incident at night.

Where this topic fits

An anomaly detection job reads a time series from Elasticsearch through a datafeed, builds a model of the usual behaviour of that series and keeps updating it as data arrives. For each time bucket it writes a result that says how unusual the new values are. Kibana displays the results and can alert on them. This is the unsupervised branch of the lesson: the only input is the data itself.

How it is applied, step by step

  1. Choose the question. A detector applies an analytical function, such as a sum or a mean, to a field, and can split the analysis so that each host or user is compared with its own past.
  2. Set the bucket span, the interval over which the data is summarised and modelled.
  3. Start the job on historical data. It builds a probability model of each series, which serves as the baseline of normal behaviour. No reading is ever marked as an anomaly by a person.
  4. For each new bucket, the job compares the observed value with what the model expects and writes a score. The scores are normalised so that the most significant anomalies rank highest.
  5. The model keeps evolving as new data arrives, so a lasting change, such as steady growth in traffic, gradually becomes part of the baseline.
  6. A person reviews the top results. The job can say that a value is unusual. Whether it is a fault, an attack or a marketing campaign is a judgement for the team.

Why this approach fits

Supervised learning is ruled out because labelled incidents are rare, expensive to collect and different every time. Hand-written thresholds are ruled out because the right threshold differs for every series and every hour of the day. An unsupervised model learns each series' own pattern from the data that is already being collected and needs nobody to say in advance what a problem looks like.

Limitation or tradeoff

Unusual is not the same as bad. The job flags a successful product launch as readily as an outage, and it cannot flag a problem that looks like normal behaviour. The baseline is learned from whatever the job sees, so an incident that lasts long enough is absorbed into "normal". Like any statistical model, a job needs some history before its scores mean much (the pages cited here give no figure). Memory use grows with the number of entities modelled: the documentation gives a default model memory limit of 1 GB, beyond which new entities are not modelled.

What the sources document

BERT in Google Search: pre-training on unlabelled text, then understanding queries

GoogleDocumented in an engineering article

BERT is a language model that Google researchers published and open-sourced in 2018 and that Google applied to Search in 2019. The sources are the Google Research blog post announcing the release, the arXiv abstract of the paper and the Search blog post by Google's vice president of Search. [17][18][19][3]

The problem

Answering a query well requires understanding its language, including small words. One of the post's examples is a query from a Brazilian traveller asking about a visa for the USA, in which the word "to" decides who is travelling where. The labelled datasets for any one language task are small, a few thousand to a few hundred thousand examples according to the research post, while deep models keep improving with far more data than that.

Where this topic fits

Self-supervised learning is the first of two training stages. In pre-training the model learns from plain text alone, with no human annotation. The pre-trained model is then adapted to specific tasks, and Google applied BERT models to ranking results and to featured snippets.

How it is applied, step by step

  1. Collect a large body of plain text. The research post names Wikipedia. No person labels anything.
  2. Make a prediction task out of the text itself: mask out some of the words in each input and train the network to predict them from the words on both sides. The hidden word is the label.
  3. Add a second task built the same way: given two sentences, predict whether the second one really follows the first in the corpus or is a random sentence.
  4. After pre-training, add one output layer and fine-tune on the small labelled dataset of a specific task. This second stage is ordinary supervised learning.
  5. Apply the resulting models in the product. Google used BERT models for ranking and for featured snippets, and served them on Cloud TPUs.
  6. Check the change before launch. The Search post says the team did a lot of testing to make sure the changes were actually more helpful.

Why this approach fits

Unlabelled text is close to unlimited and labelled text is scarce, so a method that makes its own labels can use vastly more data than a supervised one. Predicting a hidden word from both sides forces the model to use context, which is the skill a search engine needs when one small word changes what a query means. One pre-trained model can then be fine-tuned for many tasks, which spreads the cost of pre-training.

Limitation or tradeoff

Pre-training is expensive, and the Search post says serving these models required new hardware. The pretext task is not the product task: doing well at filling in hidden words does not show that search results improved, so labelled evaluation data and testing are still needed. The model also absorbs whatever regularities its text contains, including errors. The post gives a failure of its own: asked which state lies south of Nebraska, BERT's best guess was a community named South Nebraska.

What the sources document

  • The research post says most task-specific NLP datasets contain only a few thousand or a few hundred thousand human-labelled training examples, and that pre-training uses the enormous amount of unannotated text on the web, after which the model can be fine-tuned on small-data tasks. [17]
  • The research post describes BERT as an unsupervised language representation pre-trained using only a plain text corpus, Wikipedia, and trained by masking out some of the words in the input and predicting the masked words. Google's ML glossary names BERT as a model that uses self-supervised learning. [17][3]
  • The paper's abstract says BERT is designed to pre-train deep bidirectional representations from unlabeled text, and that the pre-trained model can be fine-tuned with just one additional output layer for tasks such as question answering and language inference. [18]

MuZero at YouTube: reinforcement learning for video compression decisions

Google DeepMind and YouTubeDocumented in an engineering article

A DeepMind blog post of 11 February 2022 and the abstract of the accompanying arXiv preprint describe MuZero, a reinforcement learning agent first built for board and video games, used as the rate controller of libvpx, the open-source VP9 video codec that YouTube uses. [20][21]

The problem

While encoding a video, the codec must choose a quantisation parameter (QP) for each frame, which sets how strongly that frame is compressed. The choices interact. Bits spent on one frame are not available for later ones, and the target bitrate has to be met over the whole video. Nobody can label the correct QP for a frame, because whether a choice was good only shows in the quality and size of the finished video.

Where this topic fits

The learned policy replaces the hand-engineered rate control inside the encoder. There is no dataset of right answers, so this is neither supervised nor unsupervised learning. The agent learns from the result of its own sequences of decisions, which is the definition of reinforcement learning.

How it is applied, step by step

  1. Frame the problem as sequential decision-making: one decision per frame, and one episode per video.
  2. For each frame, the agent observes the state of the encode and chooses a QP. That choice is the action.
  3. When the video is finished, measure the quality reached and whether the bitrate target was met.
  4. Turn that result into a reward. The team's self-competition mechanism compares the agent's result with its own past performance and reduces it to a win or a loss.
  5. Repeat over a large and varied set of videos, so that the learned policy also works on videos it has never seen.
  6. Deploy the learned rate controller, MuZero-RC, in place of the default one. The post reports a launch on a portion of YouTube's live traffic.

Why this approach fits

The three conditions for reinforcement learning hold. The task is a chain of decisions whose effects are delayed and coupled. No labelled right answers exist. And the environment, an encoder running on stored videos, can be run again and again at low cost and with no harm from bad attempts, so the agent can practise before any viewer is affected. The objective is also measurable, which RL requires.

Limitation or tradeoff

Designing the reward was a research problem in its own right: the team had to invent a mechanism to turn several competing requirements into one signal. The learned policy must generalise to videos unlike those it trained on, which the post names as a challenge, and QP selection is only one of many encoding decisions. The reported gain is a few percent. That is valuable at YouTube's scale and would rarely repay the engineering effort for a small service.

What the sources document

  • The post says that in VP9 bitrate is optimised most directly through the Quantisation Parameter in the rate control module, that for each frame this parameter determines the level of compression, and that QPs are decided sequentially to maximise overall quality for a target bitrate. [20]
  • The post says RL is particularly well suited to sequential decision-making problems like those in codecs, and that MuZero-RC replaces VP9's default rate control mechanism and decides the level of compression for each frame. [20]
  • The post describes a mechanism called self-competition, which converts the objective of video compression into a WIN/LOSS signal by comparing the agent's current performance against its historical performance. [20]
  • The post reports an average 4% bitrate reduction across a large, diverse set of videos since launching to production on a portion of YouTube's live traffic. [20]
  • The preprint's abstract says the work treats rate control as a sequential decision-making problem with an episodic constraint imposed by the target bitrate, and reports an average 6.28% reduction in the size of compressed videos at the same quality (PSNR BD-rate) compared with libvpx's two-pass VBR rate control policy. [21]

Uber Michelangelo: one platform for the workflow from data to monitored predictions

UberDocumented in an engineering article

Uber Engineering's article of 5 September 2017 introducing Michelangelo, the company's internal machine learning platform. It uses the UberEATS estimated time of delivery model as its running case. [22]

The problem

The article says that before the platform existed, data scientists built models with a variety of tools while separate engineering teams built one-off systems to use those models in production, and there was no established path for deploying a model. For UberEATS the prediction itself is hard: delivery time depends on the restaurant preparing the meal, a courier being dispatched, the pickup, the drive, parking and the walk to the door.

Where this topic fits

The workflow of this lesson is the product. Michelangelo is organised around six steps: manage data, train models, evaluate models, deploy models, make predictions and monitor predictions. The delivery time model is supervised regression, and it passes through every one of those steps.

How it is applied, step by step

  1. Manage data. Pipelines produce datasets of features and labels for training, and features alone for predicting. Shared features live in a feature store, with batch pipelines for historical values and streaming pipelines for recent ones.
  2. Train. UberEATS data scientists train gradient boosted decision tree regression models to predict the end-to-end delivery time.
  3. Evaluate. Each trained model is stored with its configuration, references to its training and test data and its accuracy metrics, so that candidates can be compared. The article notes that it is not uncommon to train hundreds of models that do not make the cut.
  4. Deploy. A model is released either as a batch job or to an online prediction service. The UberEATS models are deployed to serving containers and called over the network by the UberEATS services.
  5. Predict. At request time the features are assembled by the same feature expressions used in training, the model returns a delivery time, and the app shows it to the customer.
  6. Monitor. A share of predictions is logged and later joined to the delivery time that was actually observed. Accuracy metrics computed from the pairs are charted, with alerts on thresholds.

Why this approach fits

Delivery time is a number that depends on many interacting factors, which makes it a regression problem, and labels arrive at no extra cost because every completed order records how long it took. Standardising the whole workflow pays off when dozens of teams build models. Without a shared platform each team has to find its own way to production, and the article says that is how it was: separate engineering teams built bespoke one-off systems to use the models, and there was no established path to deploying one.

Limitation or tradeoff

A platform of this size is justified by scale. For a single model, a scheduled training script and a dashboard do the same job. Monitoring by joining predictions to outcomes works here because the label arrives as soon as the order is delivered; a model whose outcome takes months gets that signal too late. Detecting decay is also not the same as repairing it. At the time of the article, retraining and deployment of the UberEATS delivery models were still started by hand.

4Common mistakes

  1. Training a model for a problem that a short rule or a lookup table would solve, or before any data exists.

    Why it causes problems
    A model brings data pipelines, evaluation, deployment and monitoring with it. If the logic is already known, all of that buys nothing. If there is no data, the model will be worse than a sensible guess. The first of Google's Rules of ML is that a product can launch without machine learning.
    How to recognise it
    A domain expert can state the decision in a few sentences and colleagues agree with it. Or nobody has measured how well a simple rule performs, so there is no number the model is supposed to beat.
    How to fix it
    Ship the rule together with logging and the metric you care about. Record the rule's score as the baseline. Start on a model when the logged data has piled up and the rule has become hard to extend, and require the model to beat the baseline on held-out data.

  2. Reporting accuracy measured on the same examples the model was trained on.

    Why it causes problems
    Training accuracy rewards memorising. In the first exercise a lookup table scores 12 of 12 on its training rows and 4 of 8 on new members, which is no better than always predicting "stays". A team that looks only at the first number ships a model that is useless on real inputs.
    How to recognise it
    Only one accuracy figure is quoted and it is close to perfect. The evaluation code reads the same file as the training code, or the test rows were used again and again to choose settings.
    How to fix it
    Split the data before any training. Fit on the training set, choose between candidates on a validation set, and touch the test set once at the end. Report the test score next to the baseline's score.

  3. Treating deployment as the end of the project and never checking the model again.

    Why it causes problems
    A model keeps answering after it has stopped being right. In the worked example the deployed rule fell from 5 of 6 to 2 of 6 with no error and no change to its code. Google's Rules of ML calls these silent failures and notes that they are more common in ML systems than in other kinds of system.
    How to recognise it
    Nobody can say when the model was last retrained or what its accuracy was last week. There is a dashboard for the service's latency and errors and none for the quality of its predictions.
    How to fix it
    Log predictions, join them to the real outcomes when those arrive, and chart accuracy against the baseline with an alert. While labels are slow to arrive, track the statistics of the inputs. Name an owner and decide how often the model will be retrained.

  4. Choosing supervised learning without checking where the labels will come from.

    Why it causes problems
    The project stalls at labelling, or it trains on a stand-in such as clicks or user reports that does not measure what the product needs. A model reproduces its labels faithfully, including their gaps and their bias.
    How to recognise it
    Nobody on the team can say who or what produces the label for a row, what a label costs, or how long after the event it becomes known.
    How to fix it
    Write down the source, cost and delay of labels before choosing a method. If labels are scarce, consider semi-supervised learning, a model pre-trained with self-supervision, or a pre-trained model behind an API. If the real question is "what is unusual here", an unsupervised method may fit better.

  5. Computing a feature one way in the training code and another way in production.

    Why it causes problems
    The model receives inputs unlike those it learned from. This is training-serving skew. Predictions get worse from the first day and nothing crashes, so the cause is hard to trace.
    How to recognise it
    Live accuracy is clearly below test accuracy immediately after launch, not gradually. Feeding one training example through the production code gives different feature values or a different score, which Google's Rules of ML treats as an engineering error.
    How to fix it
    Use a single implementation of each feature for both paths, or log the features computed at serving time and train from those logs, as the Rules of ML recommends. Add a test that pushes known examples through both paths and compares the results.

Exercise 1

Compare a baseline, a hand-written rule, a learned rule and a memoriser, then monitor them

CodingBeginnerAbout 45 min (estimate)Hypothetical scenario

A gym wants to predict which members will cancel next month so that staff can call them first. The data is invented for practice. Each row is one member: visits last month, months as a member, and whether the member cancelled the following month (1 = cancelled, 0 = stayed).

train = [(0, 2, 1), (1, 14, 1), (2, 5, 1), (1, 3, 1), (3, 1, 1), (6, 8, 0),

  2. Hand-written rule. A manager proposes: a member will cancel if months <= 3. Score it on train and test.
  3. Learned rule. Use the templates "cancel if feature <= t" and "cancel if feature >= t". Try both features, both directions and every value of t that occurs for that feature in the training data.   5. Monitor. Score all four models on later. Which comparison tells you that the deployed learned rule has to be replaced?

Requirements

  • Score every model with one shared function that counts correct predictions, so the numbers are comparable.
  • Search both features, both directions (<= and >=) and only threshold values that occur in the data being trained on.
  • Never use test or later rows when choosing the rule in part 3.
  • Report each result as a count out of the number of rows, for example 6/8.
  • Answer parts 4, 5 and 6 in words as well as numbers.

Hint 2

python
# Each member: (visits_last_month, months_as_member, cancelled). cancelled 1 = yes, 0 = no.
train = [(0, 2, 1), (1, 14, 1), (2, 5, 1), (1, 3, 1), (3, 1, 1), (6, 8, 0),
         (4, 20, 0), (9, 3, 0), (12, 15, 0), (5, 2, 0), (2, 30, 0), (8, 11, 0)]
test = [(1, 6, 1), (0, 1, 1), (3, 12, 1), (5, 4, 1), (7, 9, 0), (10, 2, 0), (3, 24, 0), (6, 1, 0)]
later = [(1, 10, 0), (2, 18, 0), (0, 26, 0), (3, 7, 0), (6, 13, 0), (0, 2, 1), (1, 4, 1), (4, 3, 1)]
NAMES = ["visits", "months"]

def correct(predict, rows):
    return sum(predict(r) == r[2] for r in rows)

def majority_model(rows):
    ones = sum(r[2] for r in rows)
    answer = 1 if ones > len(rows) - ones else 0
    return lambda r: answer

def hand_rule(r):
    return 1 if r[1] <= 3 else 0

def make_stump(feature, direction, threshold):
    if direction == "<=":
        return lambda r: 1 if r[feature] <= threshold else 0
    return lambda r: 1 if r[feature] >= threshold else 0

def train_stump(rows):
    best = None
    for feature in (0, 1):
        for direction in ("<=", ">="):
            for threshold in sorted({r[feature] for r in rows}):
                score = correct(make_stump(feature, direction, threshold), rows)
                if best is None or score > best[0]:
                    best = (score, feature, direction, threshold)
    return best

def memoriser(rows):
    table = {(r[0], r[1]): r[2] for r in rows}
    fallback = majority_model(rows)
    return lambda r: table.get((r[0], r[1]), fallback(r))

score, feature, direction, threshold = train_stump(train)
models = {
    "majority": majority_model(train),
    "hand rule": hand_rule,
    "stump": make_stump(feature, direction, threshold),
    "memoriser": memoriser(train),
}
print(f"learned rule: cancel if {NAMES[feature]} {direction} {threshold}")
for name, model in models.items():
    print(f"{name:10} train {correct(model, train)}/12  test {correct(model, test)}/8  later {correct(model, later)}/8")

score2, f2, d2, t2 = train_stump(train + later)
print(f"retrained rule: cancel if {NAMES[f2]} {d2} {t2} ({score2}/20 on train + later)")

stump      train 11/12  test 6/8  later 3/8
memoriser  train 12/12  test 4/8  later 6/8

Parts 1 to 3. Seven of the twelve training members stayed, so the baseline always predicts "stays": 7/12 on train and 4/8 on test. The manager's rule gets 8/12 and 3/8, worse than the baseline on the test set. The search returns "cancel if visits <= 3", with one training mistake (the member with 2 visits and 30 months, who stayed) and 6/8 on the test set. It is the only model here that beats the baseline on unseen spring data.

Part 4. The memoriser is perfect on train because it has stored every answer. None of the eight test pairs is in its table, so it falls back to the majority class and scores exactly what the baseline scores, 4/8. It learned the rows, not a pattern. A training score alone cannot tell the memoriser from a good model. The test score can.

Part 5. On later the learned rule gets 3/8, below the 5/8 of the baseline. A model that loses to "always predict stays" is doing harm, and that comparison is the signal to replace it. Nothing in the code failed. The meaning of a feature changed: with online classes, loyal members now show few visits, so "few visits" stopped predicting cancellation.

Part 6. Retraining on the 20 rows gives "cancel if months <= 5", 17 of 20 correct. The search dropped visits and moved to membership length, because in the autumn data it is the newer members who cancel. The manager's rule, months <= 3, scores 7/8 on later: the hunch pointed at the right feature, and the data supplied a better threshold once that pattern showed up in it. A domain expert's rule is a strong baseline and a good candidate feature.

With 8 to 20 rows these scores are far too noisy to act on. The exercise is about the comparisons you should always make: model against baseline, training score against test score, and live score against the score at launch.

Before spending on pre-training, the team should check whether an existing pre-trained language model already does the job.

F has no dataset of correct movements, but it has an environment to try actions in and a clear outcome, which is the setting for reinforcement learning. The simulator is what makes the many failed attempts affordable. G has no data and no time to train, and the task is language understanding that general models already do well. The work is prompts, retrieval of the right manual passage and evaluation.

Roles. G belongs to an AI engineer: nothing is trained, and the skill is in building and testing an application around an existing model. B, C, D, E and F involve producing a model from data, which is ML engineering. In D and E a pre-trained model may be the starting point, which is where the two roles overlap. A and H are ordinary software work and need neither role.

Check your answer

  • Did you resist using ML for A and H, and can you say what a model would add there (nothing)?
  • For B, did you name the label and notice that it arrives late?
  • For C, did you say that a person, not the algorithm, gives the clusters their meaning?
  • Can you explain why F is not supervised learning even though each attempt has a clear outcome?
  • Did you assign G to an AI engineer because no model is trained?
