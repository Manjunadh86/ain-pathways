Deploying in Customer Environments

Deploying in a customer environment means running your software inside infrastructure that the customer owns or controls, such as their cloud account, their data centre or a network with no internet access, and following their rules for networking, identity and change instead of your own.

1Overview

Why it matters

A prototype that works on your laptop or in your own cloud account has not yet met the constraints that decide whether a customer can use it. In a bank, hospital or government agency the software often has to run inside the customer's network because the data may not leave it, and the customer's security team, not the vendor, decides which connections are allowed, which images may run and when anything may change. Software that quietly needs a call to a licence server, a model download at start-up or an update pushed on the vendor's schedule fails on the first day, or months later when nobody is watching.

The deployment model also decides the architecture, the support load and the speed of fixes. In your own cloud you can ship a fix in minutes. In a customer's isolated network the same fix may need a change request, a security scan, a physical transfer and a maintenance window. Forward deployed engineers, solutions engineers and platform engineers who install products at customers need to know the models, the network questions to ask in the first week, and how to change software that the customer controls without breaking it.

What you will be able to do

  • Work out the network path, DNS names and egress rules a deployment needs, including private endpoints, proxies and custom certificate authorities.
  • Package a release so that it installs with no internet access, and verify a transferred bundle with checksums.
  • Plan a change-controlled rollout with rings, bake time, rollback and a version-support policy.
  • Choose diagnostics, such as support bundles, that let you operate software you cannot log in to.

Key terms

Deployment model
The combination of where a product's code and data run and who operates it, for example vendor-run SaaS, a customer's cloud account or an isolated data centre.
Control plane and compute plane
The control plane is the management layer (web application, orchestration, metadata); the compute plane is where the customer's data is processed. A product can run them in different accounts.
VPC
A virtual private cloud, a logically isolated virtual network inside a cloud account, which the account owner configures with subnets, routes and firewall rules.
Private endpoint
An address inside the customer's network that reaches a provider's service without crossing the public internet, such as an AWS PrivateLink interface endpoint.
Egress allowlist
The list of destinations (host name or address and port) that a workload may connect out to; every other outbound connection is denied.
Air gap
A boundary between two systems with no physical connection and no automated logical connection, so data crosses only by manual, human-controlled steps.
Change control
The customer's process for requesting, approving, scheduling and recording any change to a system they operate.
Ring
A group of hosts that receive an update before the next, larger group does; staged rollout moves an update through rings only while health stays good.
Bake time
The waiting period after an update reaches a ring, during which health data is collected before the update is promoted to the next ring.
Support bundle
A package of logs, configuration and diagnostic results that the customer collects in their own environment, with sensitive fields redacted, and sends to the vendor.

2Explanation

Introduction

You have probably deployed an application to a cloud account you own. You chose the region, the network rules and the release day, and when something broke you could log in and look. A customer environment is the opposite: the servers, the network, the identity system and the change process belong to someone else, and your software is a guest.

Think of installing a machine in a client's factory. In your own workshop you decide when it is switched on and who may touch it. At the factory the gate has a visitor list, the power and network are theirs, and nobody rewires anything without an approved work order. Your engineers can only do what the site's rules allow, and the machine must be built so that it works inside those rules.

The same product can reach customers through several deployment models, which differ in where the code runs and who operates it. GitLab's documentation lists three offerings of one product: GitLab.com, the vendor-run software-as-a-service (SaaS) version; GitLab Dedicated, a single-tenant SaaS service; and GitLab Self-Managed, where the customer installs, administers and maintains their own instance (GitLab plans (opens in a new tab)). Databricks documents a middle path in which its management layer runs in its own account while compute and storage run in the customer's AWS account (Databricks architecture (opens in a new tab)). At the far end is the air gap: the NIST glossary, quoting CNSSI 4009, defines it as an interface where two systems are not physically connected and any logical connection is not automated, so data crosses only manually, under human control (NIST glossary (opens in a new tab)).

Moving down the table, the customer gains control over their data and timing, and you lose visibility, speed and the ability to fix things yourself. Everything else in this lesson follows from that trade. Private networking decides how traffic reaches software that cannot be exposed to the internet. Packaging decides how bits arrive when nothing can be downloaded. Change control decides who says when an update lands. Operating software you cannot see decides how you find out that something is wrong.

This lesson builds on cloud platform fundamentals, containers and authentication and authorization. It does not repeat DNS, TLS and firewall basics, which are in networking essentials, or the legal side of data location, which is in data privacy and compliance.

How it works

A deployment into a customer environment is a design problem before it is an installation task. The sections below take the decisions in order: the model, the split between vendor and customer, the network, the packaging and the change process, then how you operate the result.

1. Choose the model by what the customer must control

Five models cover most cases. Multi-tenant SaaS is one shared copy that the vendor operates for all customers. Dedicated (single-tenant) SaaS gives each customer its own copy, still in the vendor's cloud. Customer VPC puts compute and storage in a virtual network inside the customer's own cloud account, usually with a vendor-run management layer elsewhere. On-premises (also called self-managed) means the customer installs and runs the software in their own data centre or cloud account. Air-gapped is on-premises with no connection to the internet at all.

Customers pick a model because of a constraint: a regulator, a contract that keeps data in a region or a building, an existing cloud commitment, or a security team that will not admit a third party into the network. Three questions separate the models. Where do the data and compute run? Who operates the software day to day? Who decides when it changes? A vendor often offers several models at once, as GitLab does, and the customer's answers pick one. Discovery is where you collect those answers, before design starts.

2. Split the product into a control side and a data side

When data and compute must stay with the customer but you still want to run the product, split it. Databricks' documentation is a concrete case. Its web application and backend services form a control plane in the Databricks account, while classic compute runs in a compute plane inside the customer's own AWS account, with a customer-supplied storage bucket (Databricks architecture (opens in a new tab)). Two design rules come out of it.

  • Decide which side holds each piece of data. Query results, logs, prompts, embeddings and model outputs are easy to forget. Write the answer down, because the customer's security review will ask.
  • The customer's side dials out. Customer firewalls rarely admit inbound connections from a vendor. Databricks describes secure cluster connectivity: customer VPCs have no open ports, and clusters connect to the control plane over HTTPS on port 443 through a relay (Databricks networking (opens in a new tab)). A typical implementation is an agent in the customer network that opens the outbound connection and then receives work over it.

3. Ask four questions about every network connection

  1. Who starts it? A connection that starts inside the customer's network is the easiest for them to approve.
  2. What path does it take? The public internet, a VPN or direct link, or a private endpoint. With AWS PrivateLink a provider publishes an endpoint service behind a load balancer, a consumer creates an interface VPC endpoint in their own VPC, and traffic stays on the AWS network instead of the public internet. The provider must add permissions for the consumer's AWS principals, and the consumer starts the connection (AWS PrivateLink (opens in a new tab)).
  3. What name does it use, and who answers DNS? Private endpoints are reached by name, so the customer usually adds DNS records. Snowflake's setup, for example, requires CNAME records in the customer's DNS (Snowflake (opens in a new tab)).
  4. Does the customer's egress policy allow it? Many customers deny all outbound traffic except an approved list. Kubernetes documents the pattern: a NetworkPolicy that selects every pod and allows no egress, with a caution that it also blocks DNS (Kubernetes (opens in a new tab)). Publish exactly which hosts and ports your product calls and why. Claude Code's documentation does this with a table of hostnames to allowlist, and it explains the proxy variable HTTPS_PROXY, the custom certificate authority variable NODE_EXTRA_CA_CERTS and mutual TLS client certificates, because many enterprise networks route traffic through TLS-inspecting proxies (Claude Code (opens in a new tab)).

Put the answers in a network requirements page: host, port, direction, purpose, required or optional, and how to turn it off.

4. Package for places you cannot reach

Three habits make an install repeatable. Pin versions and digests, so the customer gets exactly what you tested. Install from a registry the customer controls, which means every image reference must be rewritable. Ship a bundle the customer can verify: a manifest of digests, signatures and a software bill of materials (SBOM), which lists the components inside.

For air-gapped sites, Zarf's documentation uses the phrase "develop connected, deploy disconnected": build a package on a connected machine, carry it across, deploy it (Zarf (opens in a new tab)). A cluster with no registry has a bootstrap problem, because it needs a registry to pull images and needs an image to start one. Zarf solves it by splitting a registry image into ConfigMap-sized chunks and reassembling it inside the cluster (Zarf init package (opens in a new tab)). K3s documents three ways to load images offline: a private registry, a tarball placed in the agent's images directory, or an embedded registry mirror (K3s (opens in a new tab)).

5. Treat change as the customer's decision

Change control is the customer's process for requesting, approving, scheduling and recording a change. Bring what the reviewer will ask for: release notes with the impact, a tested upgrade path, a rollback plan, the expected downtime and your support policy for old versions. GitLab's maintenance policy shows the last item: bug fixes are backported only to the current stable release, and security fixes also reach the previous two monthly releases (GitLab policy (opens in a new tab)). A customer who upgrades slowly falls out of the fix window through their own schedule.

When you, not the customer, push updates to many hosts, limit the damage with rings. If a defect is caught in ring kkk, and rings are cumulative shares fkf_kfk​ of a fleet of NNN hosts, the hosts exposed are

exposedk=fk×N\text{exposed}_k = f_k \times Nexposedk​=fk​×N

The Google SRE Workbook gives the same logic for canaries: a defect that fails 20% of requests, deployed to 5% of traffic, produces a 1% overall error rate, and the impact on the error budget is proportional to the traffic exposed (SRE Workbook (opens in a new tab)). Rings only help with bake time, a wait with real health signals after each promotion, and with a ring that resembles the rest of the fleet. Palantir's Apollo documentation describes a pull model: environment operators subscribe to release channels such as RELEASE, CANARY and STABLE, environment editors set constraints such as when changes are acceptable, and approval processes can use groups from the organisation's SAML identity provider (Apollo (opens in a new tab)).

6. Operate what you cannot see

Expect to have no login. Expose health and version information, make logs and configuration collectable, and give the customer's operators one command that gathers diagnostics. Troubleshoot's support bundle is a documented form of this: the customer runs it in their own cluster, and it collects data, redacts sensitive fields and analyses the result (Troubleshoot (opens in a new tab)). Agree in advance what telemetry may leave the environment, and write runbooks that the customer's staff can follow without you.

7. Use the customer's identity system

Single sign-on through the customer's identity provider, and narrowly scoped roles instead of broad administrator access, keep your product inside their access reviews. Authentication and authorization covers the protocols. The rule here is to ask for the customer's identity provider and the smallest role that works, early in the engagement.

Worked example: Pre-flight check for a release going into a locked-down customer VPC

This is a teaching scenario with invented data, built so that you can reproduce every line of output with python3 and no packages. A vendor is about to deliver release 2.4.1 of "DocTriage", a document-classification service, into a customer's AWS VPC. The customer's security team has answered a network questionnaire with two rules: containers may only be pulled from registry.customer.internal, and the only outbound destination allowed from the namespace is the customer's own identity provider on port 443. Before anyone books a change window, the vendor engineer checks the release against those rules.

Step 1: describe the release and the rules, then check them

The script covers three things the customer will ask about: where each image must be copied, which outbound calls the network would refuse, and whether a transferred bundle arrived intact.

python
import hashlib

RELEASE = {
    "version": "2.4.1",
    "images": [
        ("registry.vendor.example/doctriage/api:2.4.1", 182_000_000),
        ("registry.vendor.example/doctriage/worker:2.4.1", 940_000_000),
        ("docker.io/library/postgres:16.4", 430_000_000),
    ],
    "outbound": [  # host, port, purpose, required
        ("idp.customer.example", 443, "OIDC discovery and signing keys", True),
        ("license.vendor.example", 443, "licence check at start-up", True),
        ("huggingface.co", 443, "download model weights on first start", True),
        ("telemetry.vendor.example", 443, "usage metrics", False),
    ],
}
CUSTOMER = {"registry": "registry.customer.internal", "egress_allow": {("idp.customer.example", 443)}}

# 1. Where must each image be copied to?
total = sum(size for _, size in RELEASE["images"])
print(f"Mirror plan: {len(RELEASE['images'])} images, {total / 1e9:.2f} GB")
for ref, size in RELEASE["images"]:
    path = ref.split("/", 1)[1]
    print(f"  {ref} -> {CUSTOMER['registry']}/{path}")

# 2. Which outbound calls would the customer's network refuse?
print("Egress check:")
blocked_required = 0
for host, port, purpose, required in RELEASE["outbound"]:
    if (host, port) in CUSTOMER["egress_allow"]:
        status = "allowed"
    elif required:
        status, blocked_required = "BLOCKED (required)", blocked_required + 1
    else:
        status = "blocked (optional)"
    print(f"  {host + ':' + str(port):<30}{status:<20}{purpose}")
print(f"Blocked and required: {blocked_required} -> release cannot start as shipped")

# 3. Bundle for the transfer: a manifest of SHA-256 digests (stand-in file contents).
files = {name: (name.encode() * 400)[:size] for name, size in
         [("doctriage-api-2.4.1.tar", 1820), ("doctriage-worker-2.4.1.tar", 9400), ("postgres-16.4.tar", 4300)]}
manifest = {name: hashlib.sha256(data).hexdigest() for name, data in files.items()}
print("Manifest:")
for name, digest in manifest.items():
    print(f"  {digest[:12]}  {name}")

def verify(received, manifest):
    bad = [n for n, d in manifest.items() if n not in received or hashlib.sha256(received[n]).hexdigest() != d]
    return bad or "OK"

print("After transfer:", verify(files, manifest))
damaged = dict(files)
damaged["doctriage-worker-2.4.1.tar"] = b"X" + files["doctriage-worker-2.4.1.tar"][1:]
print("After one changed byte:", verify(damaged, manifest))

Step 2: read the result

  • Images. The three images total 1.55 GB (182 + 940 + 430 million bytes), and each must be copied into the customer's registry before install. The rewrite keeps only the repository path, so library/postgres:16.4 from Docker Hub and a same-named path from another registry would collide. Zarf's agent adds a CRC32 hash of the original image name to the tag of images that are not pinned by digest for this reason (Zarf init package (opens in a new tab)). Here the safer plan is to reference every image by digest.
  • Egress. One of four destinations is allowed. Two blocked destinations are required, so the release as shipped cannot start: it would sit waiting on a licence server and a model download that the network refuses. The engineer finds this in a script, not on install day.
  • Bundle. The manifest lists a SHA-256 digest per file. After the files are carried across, the customer recomputes the digests, and one changed byte in the worker image is reported by name. A digest proves the file arrived unchanged; a signature, as in Zarf's cosign support, would also prove who produced it.

Step 3: change the release, not the customer's rules

Blocked callChange to the releaseHow to prove it
Licence check at start-upValidate a signed licence file on the nodeStart the release with all egress denied except the identity provider and cluster DNS
Model weights downloadPut the weights in the bundle and mount them as a volumeSame test, from an empty volume to first successful request
Usage metricsOff by default; a command exports a usage report the customer can review and sendConfirm that no connection to the metrics host is attempted

What the result means. The customer's rules were reasonable and the release was the problem. Fixing the release before the change request means the request can state that the software makes exactly one outbound connection, to the customer's own identity provider. That is a sentence a security reviewer can approve. The same check belongs in your CI pipeline, run against every release, so a new dependency cannot sneak in between versions.

Edge cases and limitations

A default-deny egress policy also blocks DNS
Kubernetes documents that a policy selecting every pod with no egress rules blocks DNS traffic as well. The symptom is that every outbound call fails with a name-resolution error, including calls to destinations the customer meant to allow, so the allowlist looks broken. Ask for the cluster DNS exception explicitly, and test with the customer's real policy in a staging namespace instead of an open network.
TLS-inspecting proxies change who signs the certificate
Many enterprise networks send outbound HTTPS through a proxy that re-signs certificates with the company's own certificate authority. A client that trusts only a bundled list of public authorities fails with a certificate error even though the destination is allowed. Claude Code's documentation, for example, trusts both its bundled Mozilla set and the operating system's store by default and offers NODE_EXTRA_CA_CERTS for a custom authority. Ask early whether TLS inspection is in use, obtain the CA certificate and test with it installed.
Private connectivity usually runs in one direction
Snowflake's documentation says AWS PrivateLink controls inbound connectivity from the customer's network to Snowflake. Reaching private data sources from Snowflake, the outbound direction, uses a separate feature, the Data Connectivity Proxy. A design that needs calls in both directions needs two network paths, two approvals and two sets of DNS records. Draw each direction on the network diagram before the security review.
Customers fall behind, and fixes are not retroactive
A self-managed customer upgrades when their change process allows. GitLab's policy backports security fixes to the current release and the previous two monthly releases (with rare, process-gated exceptions), and its upgrade path requires stops at named versions with background migrations finished in between. A customer far behind needs several sequential change windows before a fix reaches them. Publish a support policy and a tested upgrade path, and track which version each customer runs.
The customer's administrators can change what your product depends on
Databricks warns customers not to delete or modify the workspace storage bucket in their own account, because the workspace depends on it and cannot be recovered if it is deleted. In any customer-VPC design, resources in the customer's account can be altered by people who have never read your documentation. Name the resources the product depends on, ask for guardrails on them and add a pre-flight check that detects drift.
A canary ring can pass while a defect is waiting
CrowdStrike's report says its parameter-count mismatch was missed by testing and by the first several successful field deployments of earlier content, partly because that content used a wildcard for the field in question. A small ring only tests what its hosts happen to exercise. Choose ring members that differ in operating system version, configuration and workload, and keep health signals broad enough to notice a failure you did not predict.

When to use it, and when something simpler is enough

Use it when

  • Data cannot leave the customer's network or country for legal, contractual or security reasons, and a hosted service would fail their security review.
  • The customer already operates their own cloud account or cluster and wants storage, logs and keys under their own controls, which points to a customer-VPC deployment.
  • The system must keep working without the internet, for example in a plant, on a ship or on a classified network, which points to on-premises or air-gapped delivery.
  • A regulated customer requires approval and a record for every change, which a continuously released SaaS cannot provide.

Think twice when

  • The customer would accept a hosted service and has no rule against it, because running software in their environment multiplies your support and release effort.
  • You cannot yet list the product's outbound dependencies or ship it without runtime downloads; fix that before offering any isolated deployment.
  • The customer has nobody who can run the platform, apply updates and respond to alerts, because self-managed software then falls behind and decays.

A simpler alternative. Start with a hosted single-tenant or SaaS deployment plus a private network link such as a private endpoint, which many security teams accept. Move to customer VPC, on-premises or air-gapped only when a written requirement rules the hosted option out, because each step removes your ability to see and fix things quickly.

Key takeaways

  • A deployment model is a decision about where data and compute run, who operates the software and who decides when it changes, and each step from SaaS to air-gapped moves control to the customer and removes your visibility.
  • Splitting a product into a vendor control side and a customer data side works best when the customer's side dials out, so the customer opens no inbound ports.
  • For every connection, settle who starts it, what path it takes, what name it uses and whether the customer's egress policy allows it, then publish the complete list of destinations.
  • Air-gapped delivery means building and verifying a bundle on a connected machine, carrying it across, and installing without any runtime download.
  • Change control belongs to the customer, so ship release notes, an upgrade path, a rollback plan and a support policy, and use rings with bake time for any update you push yourself.
  • Plan to operate without a login by building diagnostics that the customer can run, review and send, such as a redacted support bundle.

3Real-world applications

5 documented uses of Deploying in Customer Environments. Each one names the real system, the problem it solves and its tradeoff, with links to the sources.

  1. Databricks runs its control plane in its own account and compute in the customer's AWS account
  2. Snowflake gives customers a private network path to a multi-tenant service through AWS PrivateLink
  3. GitLab publishes required upgrade stops and a support window for instances its customers run themselves
  4. Zarf and K3s deliver Kubernetes applications into clusters that have no internet access

Example 1 of 5

Databricks runs its control plane in its own account and compute in the customer's AWS account

DatabricksDocumented in official docs

Databricks' AWS documentation describes a control plane that Databricks operates in its own account and a classic compute plane that runs in the customer's AWS account, and a second page describes how the two are connected (the high-level architecture page and the classic compute plane networking page). [1][2]

The problem

Customers want to process data next to their own storage, inside their own cloud account and under their own network and permission controls. They still want a managed web application and managed backend services. If the vendor had to reach into every customer network to manage clusters, each customer's security team would have to open inbound ports to a third party.

Where this topic fits

This is the customer-VPC model from the lesson, built on the control side and data side split. The vendor keeps the management layer. Compute and storage stay in the customer's account, and the compute side starts the connection.

How it is applied, step by step

  1. The vendor runs the web application and backend services in the Databricks account rather than in the customer's cloud account. Identity settings such as users, groups and single sign-on are managed at the Databricks account level.
  2. For classic compute, cluster nodes are created inside a virtual network in the customer's own AWS account, and the customer provides an S3 bucket that holds the workspace's storage.
  3. By default the customer VPC has no open ports and the nodes have no public IP addresses. The nodes open an HTTPS connection on port 443 to a relay in the control plane, and cluster management travels over that tunnel.
  4. A customer that wants tighter control supplies its own VPC when it creates the workspace, which lets it limit outgoing connections, and can enable AWS PrivateLink so that traffic between the two planes stays off the public internet.
  5. The customer's administrators now own the resources the product depends on, and the documentation tells them not to delete or modify the workspace storage bucket.
  6. A customer that prefers not to run compute in its own account can use serverless compute, which runs in a plane in the vendor's account, so one product offers two models side by side.

Why this approach fits

The customer keeps data, compute and the network boundary inside an account it already governs with its own logging, permissions and cost controls, while the vendor keeps one place to update the web application and backend services. Because the customer's nodes start the connection, the firewall review is about outbound rules rather than inbound exceptions for a third party.

Limitation or tradeoff

The vendor can no longer see or repair everything. Customer-side changes, such as a deleted bucket or an egress rule that blocks the relay, break the product in ways the vendor cannot reproduce in its own account. The control plane still sits in the vendor's account, so a rule that nothing may leave the customer's network cannot be met by this model alone. That requires an on-premises or air-gapped deployment.

What the sources document

  • The control plane, which includes the web application and the backend services Databricks manages, is in the Databricks account, not the customer's cloud account. For classic compute, the compute resources are in the customer's AWS account, in what Databricks calls the classic compute plane. [1]
  • Classic workspaces require the customer to provide an S3 bucket as workspace storage. The page warns not to delete or modify that storage because the workspace depends on it, and says a workspace cannot be recovered if its storage is deleted. [1]
  • Serverless compute runs in a serverless compute plane in the Databricks account, in the same AWS region as the workspace's classic compute plane, which the customer selects when creating the workspace. [1]
  • All new workspaces use secure cluster connectivity by default, which means customer VPCs have no open ports and classic compute resources have no public IP addresses. Clusters connect to the control plane through a secure tunnel over HTTPS on port 443, using a relay. [2]
  • Customers can provide their own VPC to keep more control of their AWS account and limit outgoing connections, and can enable AWS PrivateLink for private connectivity between the control plane and the classic compute plane. [2]

The facts above come from the cited sources. The steps and analysis in this example are our explanation of how they fit together.

Example 2 of 5

Snowflake gives customers a private network path to a multi-tenant service through AWS PrivateLink

SnowflakeDocumented in official docs

Snowflake's documentation explains how a customer connects its AWS VPCs to its Snowflake account through AWS PrivateLink. AWS's documentation describes the provider and consumer roles that this setup relies on. [4][3]

The problem

A customer's workloads inside a VPC need to reach a multi-tenant SaaS data platform without sending queries and results over the public internet. The vendor must still ensure that only authorised customer accounts can connect, and the customer must keep control of its own network configuration.

Where this topic fits

This is private networking for the SaaS model. The product stays in the vendor's cloud and stays shared, but the network path changes: a private endpoint inside the customer's VPC replaces the public route, and the customer's DNS has to point at it.

How it is applied, step by step

  1. The customer's Snowflake administrator, using the ACCOUNTADMIN role, authorises the customer's AWS account by calling a system function with the AWS account id and a federated token created with the AWS CLI. In PrivateLink terms this is the provider side permitting a consumer to connect.
  2. The administrator calls a second system function that returns the values needed for setup, including the privatelink-vpce-id and the private URLs for the account.
  3. In AWS the customer creates a VPC endpoint from that id and authorises a security group to reach ports 443 and 80 of the endpoint's address range.
  4. The customer creates CNAME records in its own DNS so that the private URLs resolve to the endpoint's DNS name, and therefore to private IP addresses inside the VPC. A record that resolves to public addresses is wrong.
  5. Clients inside the VPC use the private URLs, and traffic between the endpoint and the service stays on the AWS network.
  6. Snowflake clients also need Amazon S3 access for runtime operations such as internal stages, so the customer adds an S3 interface or gateway endpoint for that traffic. The page also describes an optional connectivity diagnostic tool, SnowCD, to run before relying on the setup.

Why this approach fits

The path leaves the public internet without the vendor moving the product into each customer's account. The provider approves which accounts connect, and the customer keeps control of its own endpoints, security groups and DNS. Security teams that accept a vendor-hosted service but not a public route often accept this.

Limitation or tradeoff

PrivateLink alone does not make everything private. Snowflake's page says its clients also need Amazon S3 access for runtime operations, and without an S3 interface or gateway endpoint that traffic uses the public internet. It also covers only the inbound direction. Snowflake states that it is not responsible for the customer's VPC endpoints, security groups or DNS records, and the feature requires the Business Critical edition or higher, so the customer's contract and plan matter as much as the network design.

What the sources document

  • Snowflake documents AWS PrivateLink as private VPC endpoints that connect a customer's AWS VPCs to the Snowflake VPC without traversing the public internet. The feature requires Business Critical edition or higher. [4]
  • Setup uses functions run by an ACCOUNTADMIN. SYSTEM$AUTHORIZE_PRIVATELINK takes the AWS account id and a federated token, and SYSTEM$GET_PRIVATELINK_CONFIG returns the privatelink-vpce-id used to create the VPC endpoint. A security group must allow ports 443 and 80 of the endpoint's CIDR. [4]

The records must resolve to private IP addresses inside the VPC, and Snowflake says it is not responsible for the customer's endpoint, security group and DNS configuration. [4]
  • PrivateLink controls inbound connectivity from the customer's network to Snowflake, while outbound access from Snowflake to private data sources uses a separate feature. Snowflake clients also need Amazon S3 access for runtime operations, and unless an S3 interface or gateway endpoint is configured that traffic uses the public internet. The optional SnowCD tool can evaluate the network connection. [4]
  • In AWS's model, a provider creates an endpoint service behind a load balancer and grants permission to specific principals, a consumer creates a VPC endpoint, the consumer starts the connection and the provider accepts or rejects it, and traffic stays on the AWS network without crossing the public internet. [3]

GitLab publishes required upgrade stops and a support window for instances its customers run themselves

GitLabDocumented in official docs

GitLab offers the same product as GitLab.com, a single-tenant Dedicated service and a Self-Managed install. Its upgrade-path page and release and maintenance policy show how a vendor handles change when the customer controls the environment. [5][6][7]

The problem

Customers who run the software themselves upgrade on their own schedules, and some skip many releases. Database migrations and other upgrade steps assume an order, so an arbitrary jump can fail. The vendor has to let customers choose timing, keep the number of supported versions affordable, and say exactly which intermediate versions cannot be skipped.

Where this topic fits

This is change control for the self-managed model. The vendor publishes constraints (required stops and a support window), and the customer's own change process turns them into scheduled, approved changes.

How it is applied, step by step

  1. In Self-Managed the customer installs, administers and maintains the instance, while the vendor runs GitLab.com and Dedicated itself, so only the self-managed customer has to plan upgrades.
  2. The vendor names some versions as required upgrade stops that cannot be skipped. Since 17.5 they fall at the x.2, x.5, x.8 and x.11 releases, which makes the schedule predictable for administrators.
  3. An administrator finds the path in the documentation or with the Upgrade Path tool kept by the vendor's support team, and upgrades to the latest patch release of each stop rather than the first patch.
  4. At each stop the administrator waits for the background migrations to finish before moving to the next stop.
  5. A customer with a strict change process would turn each stop into its own change request with a backup and a rollback point. This mapping is our suggestion, not the vendor's instruction.
  6. The maintenance policy decides how long a version keeps getting fixes, so the customer's upgrade pace decides whether it is still inside the window that receives security fixes.

Why this approach fits

Required stops turn an unbounded set of customer-chosen jumps into a short list of paths the vendor can test, and customers can plan windows and testing around them. Limiting backports to a few releases keeps the vendor's cost bounded, which is the reason the policy itself gives, and it nudges customers towards small, frequent upgrades.

Limitation or tradeoff

Control costs the customer time. In the calculation above a customer six stops behind needs six sequential upgrades, each with its own wait for migrations and, in a strict change process, its own approval, while security fixes are backported only to the most recent releases. The vendor may also not know which version each self-managed instance runs unless the customer reports it.

What the sources document

  • GitLab lists GitLab.com (the SaaS offering, with nothing to install), GitLab Dedicated (a single-tenant SaaS service for highly regulated and large enterprises) and GitLab Self-Managed, where the customer installs, administers and maintains its own instance. [5]
  • Required upgrade stops are versions that must be installed before later versions. The process is to upgrade to the next stop, allow background migrations to finish, then continue. In GitLab 17.5 and later the stops fall at x.2.z, x.5.z, x.8.z and x.11.z. [6]
  • The page advises upgrading to the latest patch release of a minor version, for example 16.8.7 instead of 16.8.0, and points to an Upgrade Path tool maintained by the GitLab Support team for working out the required stops. [6]
  • The policy backports bug fixes only to the current stable release and security fixes to the previous two monthly releases as well. Minor releases are monthly, patch releases twice monthly and major releases yearly. [7]
  • The policy gives its reasons for limiting backports. Backporting to older releases creates a high development, quality assurance and support cost, and supporting parallel versions discourages incremental upgrades. [7]

Zarf and K3s deliver Kubernetes applications into clusters that have no internet access

Zarf projectDocumented in official docs

The Zarf documentation describes packaging software on a connected machine and deploying it into a disconnected cluster, including how the cluster gets its first registry. The K3s documentation describes a three-step air-gap install of the cluster itself. [8][9][10][11]

The problem

A Kubernetes cluster in an air-gapped network cannot pull images from public registries, yet the manifests it runs reference those registries. A registry inside the cluster can serve the images, but starting a registry needs an image to be pulled from somewhere first.

Where this topic fits

This is packaging and delivery for the air-gapped model. It sits between "the bundle was verified" and "install in the approved window" in the delivery sequence diagram.

How it is applied, step by step

  1. On a connected machine the team declares what the application needs, including container images, Helm charts and manifests, and runs the package create command to build one compressed package.
  2. Because the package is a single file, the customer's reviewers can scan it and check its software bill of materials and signatures before approving the move across the boundary.
  3. In the disconnected cluster the init package solves the bootstrap problem. Zarf splits a registry image into chunks stored as ConfigMaps, and a small statically compiled injector reassembles the image and hosts it temporarily so that a long-lived registry can be deployed.
  4. The package's images are then pushed into the cluster's registry and the application is installed from the package.
  5. The Zarf agent, a mutating admission webhook, rewrites the image fields of pods to point at the in-cluster registry, so the application's own manifests need no edits. For images not pinned by digest it appends a CRC32 hash of the original name to the tag.
  6. Where the cluster itself must be built offline, K3s documents loading images from a private registry, from a tarball copied into the agent's images directory, or through an embedded registry mirror, and then installing from a locally saved script.

Why this approach fits

The cluster never needs the internet, and a single verifiable file crosses the boundary. Rewriting image references when pods are created means the vendor keeps ordinary manifests. A software bill of materials and signatures give the customer's reviewers something concrete to check before they approve the transfer.

Limitation or tradeoff

Anything not in the package fails at run time, because there is no fallback to the internet: a plugin downloaded on first use, a model pulled from a hub or a licence check will all break. Every update needs a new package and another trip across the boundary. The documentation also lists environment conditions. Zarf's default NodePort registry mode needs the kubelet to reach a cluster NodePort service, which can require firewall changes, and K3s needs a default route on every node, even a dummy one.

What the sources document

  • Zarf is a free, open source tool for declarative creation and distribution of software into air-gapped, constrained or standalone environments. Its model is to build while connected and deploy while disconnected, packaging what the application needs into a single compressed file. [8]
  • Zarf's listed features include SBOM generation, creating and verifying package signatures with cosign, and a mutating webhook that updates pod image paths and pull secrets. The create command takes an optional path argument, can sign the package, and can split a package into parts with a maximum size so that it fits smaller media such as DVDs. [8][10]
  • The init package solves the registry bootstrap problem by splitting a registry image into chunks small enough for ConfigMaps. A statically compiled injector binary reassembles the image and hosts a temporary registry, so the real registry can be deployed from it. [9]
  • The zarf-agent is a Kubernetes mutating webhook that rewrites pod image fields to point at the Zarf registry without changing the original references. For images not pinned to a digest it appends a CRC32 hash of the original name to the tag, so images from different registries with the same path do not overwrite each other. [9]
  • K3s documents three ways to load images in an air gap (a private registry, a tarball in the agent's images directory, or an embedded registry mirror). Installation uses a locally saved script with INSTALL_K3S_SKIP_DOWNLOAD=true, and nodes without a default route need one configured, even a dummy. [11]

CrowdStrike adds staged rings and customer control after a content update crashed Windows hosts

CrowdStrikeDocumented in a case study

CrowdStrike's external technical root cause analysis of Channel File 291 describes how a content update delivered to its Windows sensors on 19 July 2024 caused system crashes, and lists the changes it made to testing and to how content is deployed to customers. [12]

The problem

A vendor's agent runs inside every customer's Windows fleet, and content updates reach all of those hosts from the vendor's cloud. A defect that gets through the vendor's testing is exposed to every host at once unless the delivery path itself limits exposure and gives customers a say over when content arrives.

Where this topic fits

This is change control and operating software you do not fully control. The vendor pushes into customer environments, so the safeguards are the vendor's staged rollout and the customer's ability to choose where and when updates land.

How it is applied, step by step

  1. The sensor receives two kinds of update. Sensor Content ships with the sensor, and Rapid Response Content is delivered from the cloud in channel files so that detections can change without new sensor code.
  2. A sensor release in February 2024 added a template type whose definition expected 21 input fields while the sensor code supplied 20. Earlier content used a wildcard for the 21st field, so testing and the first field deployments never exercised the mismatch.
  3. On 19 July 2024 two more template instances were deployed, one with a non-wildcard criterion for the 21st input. Sensors that received that channel file read past the end of the input array and crashed.
  4. Among its mitigations the report lists more validation and testing, bounds checks in the sensor, and independent reviews, plus two changes to the delivery path itself, staged deployment and customer control.
  5. In the staged design a new template instance passes canary testing and is promoted through successively wider rings. After each promotion the vendor waits while it gathers telemetry on the effect, and the content can be rolled back if problems are detected.
  6. Customer control lets an organisation choose where and when content is deployed, which fits its own change process, and the report describes release notes that customers can subscribe to as part of continuing work.

Why this approach fits

An agent on every customer host makes the vendor's pipeline the only safeguard unless the delivery path itself limits exposure. Rings turn a defect that testing missed from a fleet-wide event into a small, observable one, as the exposure chart in the lesson shows, and customer-controlled groups let organisations with their own change control apply content on a schedule they have approved.

Limitation or tradeoff

Rings and customer delay are trade-offs. Security content exists to respond quickly to threats, so a customer who holds updates for days accepts exposure to whatever that content addresses. Detection depends on the signal a failed host can still send, and a machine that crashes during boot says little, so ring health must include other signals. And as the report itself shows, a latent defect can pass several clean deployments before something triggers it.

What the sources document

  • The report describes two ways of delivering content to the sensor. Sensor Content ships with the sensor, and Rapid Response Content is delivered by channel files. It states that Rapid Response Content is configuration data, not code or a kernel driver. [12]
  • The new template type defined 21 input fields but the sensor code supplied 20. The mismatch evaded build validation and testing, in part because earlier content used a wildcard for the 21st input. Content deployed on 19 July 2024 that used a non-wildcard criterion for that input caused an out-of-bounds read and a system crash. [12]
  • As a mitigation, each template instance is to be deployed in stages. Instances that pass canary testing are promoted to successively wider rings or rolled back if problems are detected, with bake-in time and telemetry gathered after each promotion. [12]
  • As a second mitigation the Falcon platform was updated so that customers can choose where and when Rapid Response Content updates are deployed, with more granular control and subscribable release notes described as continuing work. [12]

4Common mistakes

  1. Discovering the customer's network and security rules on install day.

    Why it causes problems
    The release needs a licence check, a model download or a package install that the customer's egress policy blocks, so the install fails or hangs in front of the customer. The fix needs a new release and a new change request, which can take weeks in a strict environment.
    How to recognise it
    Start the release in a namespace with default-deny egress, or run the egress audit from the exercises. Any connection attempt that is not on the approved list is a hidden dependency.
    How to fix it
    Collect the customer's network, registry and identity rules during discovery, publish a table of every destination your product calls, and run the deny-by-default test in CI for each release.

  2. Shipping images by mutable tag or pulling them at install time.

    Why it causes problems
    A tag such as latest can point at different content tomorrow, and an air-gapped cluster cannot pull anything at all. The customer then installs something you never tested, or the install stops at the first pull.
    How to recognise it
    Manifests reference tags without digests, or the install script contains curl, pip install or docker pull.
    How to fix it
    Pin every image and package by version and digest, mirror them into a registry the customer controls, and make every image reference rewritable.

  3. Pushing the same update to every customer host at once.

    Why it causes problems
    The blast radius is the whole fleet, and customers with their own change control get no chance to hold the update back. A defect that testing missed becomes an incident everywhere at the same moment.
    How to recognise it
    There is a single deployment stage, no bake time between stages, and no customer-side way to delay or group hosts.
    How to fix it
    Add rings with bake time and health gates, let customers choose where and when updates land, and publish release notes that customers can subscribe to.

  4. Assuming you will be able to log in to debug.

    Why it causes problems
    Customers often forbid remote access, so each incident turns into screenshots and long email threads, and the same questions are asked again for every customer.
    How to recognise it
    Your runbook starts with "SSH to the node" or "tail the logs", and nothing in the product collects its own diagnostics.
    How to fix it
    Provide one diagnostics command that collects logs, configuration and checks, redacts secrets and produces a single file that the customer can review and send.

  5. Treating the customer environment as a copy of your staging environment.

    Why it causes problems
    Customer environments differ in proxies, custom certificate authorities, DNS, identity providers, storage classes, operating system versions and admission policies, so the first install exposes differences you never tested.
    How to recognise it
    The first install fails in ways staging never showed, such as certificate errors, volumes stuck in pending or an admission webhook denying your pods.
    How to fix it
    Write a pre-flight check that probes DNS, TLS trust, registry access, storage and permissions inside the customer's environment before installing, and attach its results to the change request.

  6. Asking for broad administrator rights instead of a scoped role.

    Why it causes problems
    Security reviewers delay or reject broad access, and a stolen installer credential then reaches far more than the product needs.
    How to recognise it
    The install guide says "run as cluster admin" or lists wildcard permissions.
    How to fix it
    List the exact permissions the installer and the running product need, request a scoped role, and use the customer's identity provider and access review process.

Exercise 1

Plan a staged rollout and measure what a ring can miss

CodingIntermediateAbout 30 min (estimate)Hypothetical scenario

A vendor pushes a content update to 2,400 customer-managed hosts through four rings. The rings are cumulative: canary has 24 hosts, early has 240, broad has 1,200 and the last ring has all 2,400. The bake times before promotion to the next ring are 4, 24 and 24 hours, and the last ring has none. A defect crashes only hosts with one particular configuration, and 48 of the 2,400 hosts (2%) have it. Assume hosts are placed in rings uniformly at random.

Write Python that prints one row per ring with the hour at which the ring starts, the expected number of affected hosts among all hosts up to and including that ring, and the probability that those hosts include at least one affected host. Use math.comb for an exact probability. Then compare with an all-at-once release and say in one sentence what the table tells you about a 1% canary ring for a defect that affects 2% of hosts.

Requirements

  • Compute each ring's start hour as the sum of the bake times of the rings before it.
  • Compute the expected number of affected hosts among the first n hosts as n * 48 / 2400.
  • Compute the probability of at least one affected host as 1 - comb(2400 - 48, n) / comb(2400, n).
  • Print the all-at-once case, where all 2,400 hosts are exposed and all 48 affected hosts receive the update immediately.

Expected behaviour

The program prints a table with four rows. The canary row shows a probability of 0.3857, the early row 0.9940, and the broad and all rows 1.0000. The start hours are 0, 4, 28 and 52, and the expected affected hosts are 0.48, 4.80, 24.00 and 48.00.

Hint 1

The probability of seeing no affected host when drawing n hosts without replacement is comb(2400 - 48, n) divided by comb(2400, n).

Hint 2

A ring starts when the previous ring finishes baking, so keep a running total of bake hours.

Show solution
python
from math import comb

FLEET = 2400
AFFECTED = 48                      # hosts with the configuration that triggers the crash (2 percent)
RINGS = [("canary", 24, 4), ("early", 240, 24), ("broad", 1200, 24), ("all", 2400, 0)]  # name, cumulative hosts, bake hours

def p_at_least_one(n, fleet=FLEET, affected=AFFECTED):
    """Probability that n randomly chosen hosts include at least one affected host."""
    return 1 - comb(fleet - affected, n) / comb(fleet, n)

start_hour = 0
print("ring    cumulative  starts_at_h  expected_affected  P(at least one affected)")
for name, n, bake in RINGS:
    print(f"{name:<7} {n:>10}  {start_hour:>11}  {n * AFFECTED / FLEET:>17.2f}  {p_at_least_one(n):>24.4f}")
    start_hour += bake
print("all at once: hosts exposed =", FLEET, "expected affected =", AFFECTED)
text

canary          24            0               0.48                    0.3857
early          240            4               4.80                    0.9940
broad         1200           28              24.00                    1.0000
all           2400           52              48.00                    1.0000

Reading the table: the canary ring has a 0.3857 chance of containing at least one affected host, so a defect that affects 2% of hosts passes the canary about 61% of the time (1 - 0.3857 = 0.6143) without anyone seeing a crash. That is the representativeness problem. The early ring contains an affected host with probability 0.9940, so the defect is almost certain to show up there, after an expected 4.8 affected hosts have received it. A release to everyone at once exposes all 48 affected hosts immediately. The price of the staged plan is time: the last ring starts at hour 52.

The expected values are averages over many random assignments, not guarantees for one rollout. Two refinements are worth discussing. A canary chosen to differ in configuration, rather than at random, raises the chance that it contains the unusual hosts. And the 24-hour bake times only help if the health signal can actually reveal the crash within them.

  • Does the early row show 4.80 expected affected hosts and a start hour of 4?
  • Can you explain why a 1% canary can miss a defect that affects 2% of hosts, and what you would change about the canary?

Find the hidden internet dependencies of a service

Hands-onIntermediateAbout 25 min (estimate)Hypothetical scenario

A customer allows no outbound connections from the namespace where your service will run. Below is the start-up code of a small service. It works on your laptop, where nothing is blocked. Without editing these functions, write a harness that discovers every destination the start-up code tries to reach, then write the network requirements table you would send to the customer. You need only python3 and no packages, and the harness must not make real network connections.

python
import urllib.request

def check_licence():
    urllib.request.urlopen("https://license.vendor.example/v1/check", timeout=3)

def load_model():
    urllib.request.urlopen("https://huggingface.co/api/models/bert-base-uncased", timeout=3)

def send_usage():
    urllib.request.urlopen("https://telemetry.vendor.example/ingest", timeout=3)

def start():
    for step in (check_licence, load_model, send_usage):
        step()

Requirements

  • Replace `socket.getaddrinfo` before running the start-up steps so that every name lookup is recorded and then refused.
  • Run each start-up step separately and keep going after a failure, so that all destinations are found and not just the first.
  • Print the unique destinations as host and port, sorted.
  • Write a table with one row per destination giving its purpose, whether it is required, and how you would remove or replace it for an isolated customer.

Expected behaviour

Each of the three steps fails with a URLError, and the harness prints three destinations: huggingface.co:443, license.vendor.example:443 and telemetry.vendor.example:443. Nothing leaves your machine.

Hint 1

urllib resolves host names through `socket.getaddrinfo`, so replacing that one function in the socket module catches every lookup the code makes.

Hint 2

A real service often stops at its first failure, which hides the dependencies behind it. Wrap each step in its own try block.

Show solution
python
# --- the audit harness: append below the starter code ---
import socket
attempts = []

def refuse_lookup(host, port, *args, **kwargs):
    attempts.append((host, port))
    raise socket.gaierror(f"egress audit: lookup of {host} refused")

socket.getaddrinfo = refuse_lookup

for step in (check_licence, load_model, send_usage):
    try:
        step()
    except Exception as error:      # keep going so every dependency is found, not just the first
        print(f"{step.__name__:<14} failed: {type(error).__name__}")

print("Destinations attempted:")
for host, port in sorted(set(attempts)):
    print(f"  {host}:{port}")

Exercise 3

Write the delivery plan for an air-gapped hospital cluster

DesignAdvancedAbout 45 min (estimate)Hypothetical scenario

A hospital group wants your document-classification service on a Kubernetes cluster in a network with no internet access. Patient data cannot leave. Their security team scans anything that crosses the boundary and permits transfers on approved media once a month. Today you ship a Helm chart whose images come from public registries, the service downloads model weights on first start, and it reports usage to your cloud.

Write a delivery plan of no more than two pages with five parts: the contents of the bundle, the verification steps on both sides, the install and rollback plan for one maintenance window, how you will diagnose problems without access, and your support policy for old versions.

Requirements

  • Name every artefact in the bundle, including images by digest, the chart, model weights, a software bill of materials, an offline licence file and release notes.
  • State what the customer verifies after the transfer and with which mechanism, such as digests or signatures.
  • Give a rollback that works without the internet and fits inside one maintenance window.
  • Explain how a security fix reaches the customer between monthly transfers, including an emergency path.
  • State which versions you support and how a customer that falls behind catches up.

Expected behaviour

A plan that a customer's security team and your own engineers could both follow. Every runtime dependency is either inside the bundle or removed, nothing requires you to log in, and the plan says who does what in each step.

Hint 1

List everything the cluster pulls or calls at start-up, including images, charts, model weights and licence validation, then decide where each one comes from.

Hint 2

The Zarf create-then-deploy flow and the K3s air-gap guide show how others handle the registry bootstrap and the image rewrite.

Hint 3

A rollback needs the previous version's images to still be in the customer's registry.

Show solution

Product changes first. Remove the runtime downloads and the usage reporting. Ship weights in the bundle and read them from a volume. Replace the licence check with a signed licence file validated locally. Make usage reporting an exported file that the customer reviews and sends, or omits. Make every image reference rewritable.

1. Bundle contents.

  • A manifest listing the SHA-256 digest of every file, and a signature over the manifest.
  • The api, worker and database images, referenced by digest, and the Helm chart.
  • Model weights as a separate, versioned file with its own digest.
  • A software bill of materials, release notes stating the impact, and the offline licence file.
  • The previous release's images, kept for rollback, and a diagnostics collector that produces a redacted support bundle.
  • An install runbook with a pre-flight check script and the tested upgrade path from each supported version.

2. Verification. On the vendor side: scan the images, build the bundle on a connected machine, sign it and publish the manifest digest through a second channel, such as the change request. On the customer side: the security team rescans, verifies the signature and the digests against the manifest, and loads the images into the internal registry. The result is attached to the change request.

3. Install and rollback in one window. Run the pre-flight check first (DNS, registry access, storage classes, identity provider reachability, permissions). Install the new release next to the old one, switch traffic after the health checks pass, and keep the previous release running until the check period ends. Roll back by switching traffic and chart revision back; both sets of images are already in the registry, so no transfer is needed. Define in advance what failed health checks mean and who decides.

4. Diagnosing without access. The customer runs the diagnostics collector, which gathers logs, configuration and check results and redacts secrets. They review the file and send it by the route their rules allow, which may be the next transfer cycle. Document a short list of questions that a local administrator can answer by running commands, so common problems do not wait a month.

5. Support policy. Ship monthly bundles. Support the current and previous version, with security fixes for both. Publish the required upgrade stops, as GitLab does, so a customer that is several versions behind knows which bundles it needs. For a critical security fix, agree an out-of-cycle transfer procedure in advance, with named contacts on both sides, and a compensating control (such as disabling the affected feature by configuration) that the customer can apply the same day.

A weak plan hides the monthly transfer constraint, assumes a log-in is possible, or leaves one download in the install script. Check yours for those three.

  • Could the customer verify the bundle without contacting you?
