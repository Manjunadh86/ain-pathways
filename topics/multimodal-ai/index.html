Multimodal AI (Vision and Image Generation)

Multimodal AI is the use of models that take in or produce more than one kind of data, such as text together with images, documents or video. In practice it means sending pictures, PDF pages or video to a language model as extra input tokens, and asking image models to create or edit pictures from a text prompt.

1Overview

Why it matters

Most business information is not plain text. It arrives as photographed receipts, scanned forms, screenshots, product photos, slide decks and recordings. A multimodal model can read those directly, which removes a fragile chain of OCR and layout rules, but only if you know what the model is actually given. Providers resize large images before the model sees them (some let you opt out at a higher token cost), count them in tokens by their own rules, and count them again on each turn of a conversation. A team that skips this arithmetic finds out from the invoice, or from a model that cannot read a serial number that was shrunk to 13 pixels.

The accuracy limits are just as concrete. Provider documentation says outright that models miscount objects, misread small or rotated text, return only approximate positions, and can miss fast action between sampled video frames. Image generators still struggle at times with precise text placement and layout. Anyone who builds document extraction, visual question answering, screenshot-driven agents or image generation features needs to know which errors to expect and how to catch them before a user does.

Key terms

Modality
A kind of data a model can take in or produce, such as text, image, audio or video.
Multimodal model
A model that accepts more than one modality in a single request, for example an image and a question about it, or that produces a modality other than text.
Patch
A small square of an image, such as 28 by 28 pixels, that the model treats as one unit in the same way it treats a word piece in text.
Visual token
The token that represents one image patch. Visual tokens are counted and billed as input tokens alongside the text tokens of the prompt.
Image encoder
The part of a vision-capable model that converts image patches into numerical vectors before the language model reads them.
Downscaling
Shrinking an image to fit a model's size limits before processing. It caps the token cost and removes fine detail.
Frame sampling
Taking still frames from a video at a fixed rate, such as one per second, so that the video can be processed as a sequence of images.
Bounding box
Four numbers that mark a rectangle around something in an image, for example the left, top, right and bottom edges in pixels.
Mask
An image file that marks which region of a picture an editing model should change. OpenAI's image editing endpoint, for example, requires the mask to carry an alpha channel.
OCR
Optical character recognition. Software that converts pictures of text into machine-readable text without interpreting what the text means.

2Explanation

Introduction

In LLM APIs and Streaming every request was a list of messages made of text, and usage was counted in text tokens. A multimodal request has the same shape. The only change is that a message's content can hold other kinds of blocks next to the text: an image, a PDF or a video.

A modality is a kind of data, such as text, image, audio or video. A multimodal model accepts more than one. Think of how a mosaic is made. The picture is not treated as one object. It is laid out as a grid of small tiles, and each tile is one unit of the finished work. A vision model does the same to your image. It cuts the image into small squares called patches, turns each patch into a vector, and hands those vectors to the language model in the same sequence as the word tokens. To the language model, a photo is a few hundred to a few thousand extra tokens that happen to describe pixels.

Three consequences follow, and they organise this lesson:

  • Images cost tokens. The count depends on pixel dimensions, not on file size, and each provider has its own rule. A PDF page and a video frame are counted as images.
  • The model sees a resized copy. Large images are shrunk to fit a budget, so detail that you can see in the original may not exist in what the model receives.
  • Seeing is approximate. Models describe scenes well and read clear text well, but they are unreliable at counting, at exact positions and at fine detail.

Going the other way, image generation models produce a picture from a text prompt, and image editing changes an existing picture by following an instruction. These are usually separate models or separate endpoints from the ones that read images. Anthropic's vision guide (opens in a new tab), for example, states that Claude interprets images but cannot generate or edit them.

The lesson covers image, document and video input in that order, then generation and editing, and ends with the accuracy limits of each. Speech is covered separately in Voice and Speech AI.

How it works

From pixels to tokens

A typical vision-capable language model has three parts. Grab's engineers describe them in the write-up of their document model (opens in a new tab): an image encoder turns the image into numerical vectors, a projector translates those vectors into the representation the language model works with, and the language model reads the combined image and text input and writes text. The providers' documentation describes their token rules, not their encoder designs, so treat this as the common architecture, not as any one vendor's design.

Before the encoder runs, the provider resizes the image to fit its limits and divides it into patches. Each patch becomes a visual token, and visual tokens are billed as input tokens. Anthropic's guide says Claude views an image as 28×28-pixel patches and counts one token per patch. OpenAI's newer models use 32×32-pixel patches and multiply the patch count by a per-model factor, while its older models, such as gpt-4o, count 512-pixel tiles instead. The count is fixed by the pixel dimensions after resizing, so a 200 KB JPEG and a 5 MB PNG with the same dimensions cost the same.

Sending an image

An image travels inside the message content. This is the Claude Messages API shape for an image URL plus a question about it:

json
{
  "model": "claude-opus-5-5",
  "max_tokens": 1024,
  "messages": [{
    "role": "user",
    "content": [
      {"type": "image", "source": {"type": "url", "url": "https://example.com/meter.jpg"}},
      {"type": "text", "text": "Read the meter. Reply with the number only."}
    ]
  }]
}

The source can also be base64 data with a media_type, or a file_id from the Files API (on Amazon Bedrock and Google Cloud only base64 is currently available). Other providers differ mainly in field names. OpenAI's Responses API uses an input_image item with an image_url or a file_id, and Gemini's Interactions API takes input items whose type is image or video. Prompt order differs too: Anthropic advises images before text, Google's image guide puts the prompt before a single image, and its document and video guides put it after. In a multi-turn conversation the whole history is resent, so an image's tokens are input again on every later turn, and a base64 image is uploaded again each time. A file reference keeps the payload small.

How images are counted and priced

Each provider publishes its counting rule. For Claude:

visual tokens=⌈w/28⌉×⌈h/28⌉\text{visual tokens} = \lceil w / 28 \rceil \times \lceil h / 28 \rceilvisual tokens=⌈w/28⌉×⌈h/28⌉

Here www and hhh are the width and height in pixels after resizing. A 1000×1000 image is 36×36=129636 \times 36 = 129636×36=1296 tokens. Each model also has a cap. Standard-tier models allow a long edge of 1568 px and 1568 visual tokens. Claude 4.7 and later models allow 2576 px and 4784 tokens. An image over either limit is scaled down, keeping its aspect ratio, to the largest size that fits. The cap is the reason cost stops growing with resolution. Detail stops growing at the same point.

Image tokens are billed at the model's normal input rate. Anthropic's guide works an example: at $1 per million input tokens the 1000×1000 image costs about $1.30 per thousand images, and at $5 per million about $6.48. The settings that trade accuracy for cost are detail on OpenAI, media_resolution on Gemini, and on Claude the size of the image you send. Confirm any estimate against the usage block of a real response or the provider's token-counting endpoint.

Documents

A PDF is handled as a stack of page images with a text layer. Anthropic's PDF guide (opens in a new tab) gives the steps: each page is converted to an image, the page's text is extracted, and the model receives both. That is why a model can answer a question about a chart in a report, and why a PDF costs more than its text. Anthropic estimates 1,500 to 3,000 text tokens per page, plus the image tokens for the page. A request may hold up to 32 MB and 600 pages (100 when the request's context window is under 1M tokens).

Google's document guide allows up to 1,000 pages (or 50 MB) and counts 258 tokens per page. Its media-resolution page lists about 560 per page as the default on Gemini 3 models, and the document guide adds that on those models text extracted from the PDF itself is not billed. TXT, Markdown and HTML files are read as plain text, so the model does not see how they render.

Video

A video is sampled into frames, and each frame is an image. In the Gemini API's default static mode the model receives one frame per second plus the audio track, with a timestamp every second. Google's video guide (opens in a new tab) gives the arithmetic: 66 tokens per frame at low media resolution and 258 otherwise, plus 32 tokens per second of audio.

video tokens≈seconds×(fps×tokens per frame+32)\text{video tokens} \approx \text{seconds} \times (\text{fps} \times \text{tokens per frame} + 32)video tokens≈seconds×(fps×tokens per frame+32)

A 10-minute clip is 600×(66+32)=58,800600 \times (66 + 32) = 58{,}800600×(66+32)=58,800 tokens at low resolution and 600×(258+32)=174,000600 \times (258 + 32) = 174{,}000600×(258+32)=174,000 at the higher setting. Google's Gemini 3 page gives slightly different figures (see the edge cases), so measure on your own files. In static mode you can clip the video with start and end offsets and change the frame rate: lower for a lecture with slides, higher for fast action. Google also documents an agentic mode in which the model loads only the parts of the video the prompt needs. It reports up to 88% fewer tokens on long videos, with a slightly slower first token on clips under five minutes. Only some models support it (Gemini 3.8 Flash, 3.6 Flash and 3.5 Flash Lite in October 2026), and the clipping and frame-rate settings apply to static mode only.

Generating and editing images

Generation is a call to an image model. You send a prompt and options such as size, quality and output_format, and receive image bytes. This fragment follows the example in OpenAI's image generation guide (opens in a new tab); the model name is the one documented in October 2026.

python
import base64
from openai import OpenAI

client = OpenAI()
result = client.images.generate(
    model="gpt-image-2.5-sunburst",
    prompt="A flat-lay photo of sliced sourdough on a wooden board, soft daylight",
)
with open("bread.png", "wb") as f:
    f.write(base64.b64decode(result.data[0].b64_json))

Editing sends one or more existing images with an instruction. client.images.edit takes an image, a prompt and optionally a mask, which must be the same format and size as the image and carry an alpha channel, to identify the areas to replace. OpenAI states that masking is prompt-based: the model uses the mask as guidance and may not follow its exact shape. For step-by-step refinement, OpenAI's Responses API offers an image_generation tool that can generate or edit across turns, and Google recommends multi-turn conversation for iterating on an image with its Gemini image models, which accept up to 14 reference images depending on the model.

Output is priced in image tokens. Google's price list shows that one 1K image from Gemini Nano Banana 2.1 is 1,120 output tokens, about $0.034 at $30 per million, and a 4K image is 3,780 tokens. OpenAI's guide lists both GPT Image 2.5 models at $30 per million image output tokens and $8 per million image input tokens, with the tokens per image depending on quality and size. Images you send in for editing are counted as input. Google also states that every generated image carries a SynthID watermark. Many open-weight image generators are diffusion models, which start from noise and remove it step by step under the guidance of the prompt (see Diffusion Models).

Accuracy limits by modality

Anthropic lists mistakes on low-quality, rotated or very small images (under 200 pixels), approximate coordinates, and approximate counts when there are many small objects. It says Claude will not name people in images and cannot tell whether an image is AI-generated. OpenAI adds text in non-Latin alphabets, graphs whose meaning depends on line style or colour, panoramic and fisheye images, and precise spatial tasks such as reading a chess position. For video, Google warns that fast action can lose detail at one frame per second. For generation, OpenAI lists up to two minutes of latency for complex prompts, imperfect text placement, drifting characters or brand elements, and imprecise layout.

Research agrees. The Vision language models are blind (opens in a new tab) study tested four state-of-the-art models of 2024 on seven tasks that are trivial for people, such as counting line intersections, and reports 58.07% average accuracy. Treat a model's reading of an image as a draft. Ask for structured output (see Structured Outputs), check it against rules you can compute, and send what fails to a person.

Worked example: What a model sees in a 12-megapixel photo, what it costs, and where the serial number is

A field technician photographs an appliance's rating plate with a phone. The photo is 4032×3024 pixels and the characters of the serial number are 40 pixels tall. You want a Claude model to read the serial number and return its bounding box. Three questions decide whether this works: what size does the model see, what does it cost, and how do the returned coordinates map onto the original photo?

Save this as image_budget.py. It needs only the Python standard library. resized_size follows the reference algorithm Anthropic publishes in its coordinates guide (opens in a new tab). The prices are the two that the vision guide uses in its own example: $1 per million input tokens for Claude Haiku 4.5 on the standard tier, and $5 for Claude Opus 5 on the high-resolution tier.

python
import math

PATCH = 28                                   # Claude: one visual token per 28x28-pixel patch
TIERS = {"standard": (1568, 1568),           # (max long edge in px, max visual tokens)
         "high-res": (2576, 4784)}


def image_tokens(width, height):
    return math.ceil(width / PATCH) * math.ceil(height / PATCH)


def resized_size(width, height, max_edge, max_tokens):
    """Largest aspect-preserving size within both limits (Anthropic's reference algorithm)."""
    def fits(w, h):
        return (math.ceil(w / PATCH) * PATCH <= max_edge
                and math.ceil(h / PATCH) * PATCH <= max_edge
                and image_tokens(w, h) <= max_tokens)

    if fits(width, height):
        return width, height
    if height > width:
        tall, wide = resized_size(height, width, max_edge, max_tokens)
        return wide, tall
    aspect = width / height
    lo, hi = 1, width                        # lo always fits, hi never fits
    while lo + 1 < hi:
        mid = (lo + hi) // 2
        if fits(mid, max(round(mid / aspect), 1)):
            lo = mid
        else:
            hi = mid
    return lo, max(round(lo / aspect), 1)


def report(label, size, tier, usd_per_million, text_px):
    seen = resized_size(*size, *TIERS[tier])
    tokens = image_tokens(*seen)
    scale = seen[0] / size[0]
    cost = f"${tokens * usd_per_million / 1000:.2f}"
    print(f"{label:<11}{tier:<9} sees {seen[0]}x{seen[1]:<5}{tokens:>5} tokens  "
          f"text {text_px * scale:4.1f} px  {cost:>6} per 1,000 images")


def to_original(box, seen, original, offset=(0, 0)):
    """Map [x1, y1, x2, y2] from the image the model saw back onto the original photo."""
    sx, sy = original[0] / seen[0], original[1] / seen[1]
    x1, y1, x2, y2 = box
    return [round(x1 * sx) + offset[0], round(y1 * sy) + offset[1],
            round(x2 * sx) + offset[0], round(y2 * sy) + offset[1]]


PHOTO = (4032, 3024)                         # a 12-megapixel phone photo
CROP_ORIGIN, CROP = (1300, 900), (1200, 800) # the region that contains the rating plate
TEXT_PX = 40                                 # height of the serial-number characters

if __name__ == "__main__":
    report("full photo", PHOTO, "standard", 1.00, TEXT_PX)
    report("full photo", PHOTO, "high-res", 5.00, TEXT_PX)
    report("plate crop", CROP, "standard", 1.00, TEXT_PX)

    seen = resized_size(*PHOTO, *TIERS["standard"])
    print("box from full photo:", to_original([413, 302, 522, 317], seen, PHOTO))
    print("box from plate crop:", to_original([12, 59, 358, 107], CROP, CROP, offset=CROP_ORIGIN))

Running python3 image_budget.py prints:

full photo high-res  sees 2212x1659  4740 tokens  text 21.9 px  $23.70 per 1,000 images

Reading the result:

  • The model never sees 12 megapixels. On a standard-tier model the photo becomes 1270×952, a scale factor of 1270 / 4032 = 0.315. The 40-pixel characters shrink to 12.6 pixels. The token count, 46 × 34 = 1564, sits just under the 1568 cap.
  • A higher tier sees more and costs more. The high-resolution tier keeps 2212×1659, which is 4740 tokens, three times as many. At that model's higher token price a thousand photos cost $23.70 instead of $1.56.
  • Cropping beats both. A 1200×800 crop around the plate is under every limit, so it is not resized. The text stays 40 pixels tall, 3.2 times larger than in the downsized photo, and the image costs 1247 tokens, fewer than the full photo. A first, cheap call on the downsized photo can decide where to crop.
  • Coordinates belong to the image the model saw. Suppose the model returns the box [413, 302, 522, 317] for the serial number on the full photo. Multiplying x by 4032 / 1270 and y by 3024 / 952 gives [1311, 959, 1657, 1007] on the original, a box 48 pixels tall around 40-pixel characters. From the crop, the box [12, 59, 358, 107] only needs the crop's origin added, giving [1312, 959, 1658, 1007]. The two results agree to within one pixel. Used without rescaling, the first box would point at a different part of the photo.

The same arithmetic covers other media. A 90-second video in Gemini's static mode costs 90 × (66 + 32) = 8,820 tokens at low resolution and 90 × (258 + 32) = 26,100 at the higher setting. A 3-page PDF costs three page images plus the extracted text of each page.

Edge cases and limitations

The token cap can resize an image that is under the edge limit
Anthropic's example is an A4 page scanned at 130 DPI, 1075×1520 pixels. Both sides are under 1568 px, but 39 × 55 = 2145 visual tokens is over the standard tier's 1568, so the page is resized to 924×1307. Anthropic calls overlooking this the most common cause of misaligned coordinates. Compute the size with the reference algorithm instead of comparing edges by hand. A high-resolution-tier model would not resize the same scan.
More than 20 images in one request tightens the size limit
On the Claude API, once a request holds more than 20 images a stricter per-image dimension limit applies to all of them, and an image over it is rejected with an invalid_request_error. Images resent from earlier turns and screenshots inside tool results count. Long agent sessions hit this without warning. Keep every image within 2000 px on each side, or keep the request to 20 or fewer image and document blocks.
PDF pages are rendered at a size you do not control
Anthropic states that PDF pages are rasterised on the server at dimensions you cannot set, so coordinates returned for a PDF cannot be mapped reliably back onto the page. When you need positions, render the pages to images yourself and send those. Dense PDFs can also fill the context window before the page limit is reached, so split long files.
An animated GIF is read as one frame
Claude accepts JPEG, PNG, GIF and WebP, but its vision guide says animations are unsupported and only the first frame is used. A model that receives a GIF of a screen recording will describe the first frame as if it were the whole clip. Extract the frames you need and send them as separate labelled images, or use a model with video input.
Published per-frame token figures disagree and change
Google's video guide gives 66 or 258 tokens per frame and 32 per second of audio. Its media-resolution page gives about 70 or 280 per frame and 25 per second of audio for Gemini 3 models and calls the counts approximate. In agentic mode usage varies with the content. Budget with the published figures, then read the token usage reported for real requests before you commit to a price.
Some questions about an image are refused or cannot be answered
Anthropic states that Claude will not name people in images and cannot determine whether an image is AI-generated, and that it is not designed to interpret diagnostic scans such as CTs or MRIs. OpenAI states that its system blocks CAPTCHA submissions. Do not design identity checks, synthetic-image detection or clinical reading around a general vision model.

When to use it, and when something simpler is enough

Use it when

  • The information exists only as pixels, as in photographs, screenshots, scanned forms, charts or whiteboards, with no text layer to extract.
  • Layout carries meaning, as in tables, forms and diagrams, and plain text extraction would lose which value belongs to which label.
  • The questions are open-ended, so you cannot list in advance which fields or objects will matter.
  • A wrong answer can be caught by a computed check, a second source or a human reviewer before it has consequences.
  • You need many acceptable variations of non-critical imagery, such as backgrounds or illustrative photos, and can review them before they are published.

Think twice when

  • The document already has a reliable text layer and its layout does not matter. Extracted text is cheaper and avoids visual misreads.
  • The task needs exact measurements, exact counts of many small objects or pixel-precise positions, and there is no verification step.
  • The outcome is high-stakes and unreviewed, such as diagnosis from medical scans, identity decisions or safe navigation.
  • The picture must contain exact wording, a real logo or a regulated layout. Build those from templates or design tools and generate only the background.

A simpler alternative. For documents, run OCR or a PDF text extractor and send the text to an ordinary text model. For a fixed, narrow visual question, a barcode reader or a small classical vision model is cheaper and more predictable. These stop being enough when layout or visual content carries the answer, when document templates vary too much for extraction rules, or when the questions cannot be fixed in advance. Grab's team moved from traditional OCR to a vision model because of template variety.

Key takeaways

  • A model reads an image as a grid of patches, and each patch becomes a visual token that is counted with the text tokens of the request.
  • Token cost depends on pixel dimensions after the provider's resize step, so the provider's published rule, not the file size, tells you what an image costs.
  • Large images are downscaled before the model sees them, which caps the cost and removes small detail, so crop or pre-resize when the detail matters.
  • A PDF is processed as page images plus extracted text and a video as sampled frames plus audio, so both inherit every limit of image input.
  • Image generation and editing are separate calls billed in output image tokens, and they remain weak at exact text, precise layout and consistency.
  • Vision output is approximate for counts, positions and small text, so validate it with computed checks and send what fails to a person.

Example 1 of 5

Be My Eyes: describing a blind user's photo with GPT-4 and answering follow-up questions

Be My EyesDocumented in a case study

Be My Eyes is an app that connects blind and low-vision people with sighted volunteers. Its announcement of September 2023 describes Be My AI, an assistant inside the app that is powered by OpenAI's GPT-4 and describes pictures the user takes. [13]

The problem

A blind or low-vision person often needs visual information immediately: the cooking directions on a box, the buttons on an appliance with a flat control panel, a restaurant menu, a screen at a station. The app's original answer is a call with a volunteer, which means reaching and talking to another person every time. The announcement presents Be My AI as a way to get a description from a photo alone, and it warns in the same text that users may still get hallucinations and wrong answers.

Where this topic fits

This is image understanding used as open-ended visual question answering. The input is one phone photo and the output is a text description that the user can question further. Before it comes the camera and the app. After it comes whatever reads the text to the user, and a route to a human volunteer when the description is not enough.

How it is applied, step by step

  1. The user opens the Be My AI tab in the Be My Eyes app and takes a picture.
  2. The app sends the picture to the GPT-4 model. A typical implementation sends it as an image block with an instruction to describe the scene for someone who cannot see it.
  3. The model returns a detailed description of the picture as text.
  4. The user asks follow-up questions in a chat. Because the picture stays in the conversation history, each answer can draw on the same image without a new photo.
  5. When the user wants to check a result or needs more than the description offers, they contact a human volunteer from the same app.

Why this approach fits

The questions cannot be listed in advance, so a fixed pipeline such as OCR plus rules would cover only a fraction of them. A general vision model accepts any photo and any question, answers quickly at any hour (the announcement stresses 24/7 availability), and lets the user steer with follow-ups. Keeping the image in the conversation turns one photo into several answers.

Limitation or tradeoff

The user is the person least able to notice a wrong description. The announcement itself says to expect hallucinations and occasional wrong answers, and states that the feature does not and should not replace a white cane, a guide dog or another mobility aid. The documented weak spots of vision models, such as small print and counting, are common in exactly these photos. That is why the human volunteer remains available in the same app.

What the sources document

  • The announcement says Be My Eyes' AI assistant, Be My AI, is powered by GPT-4 and was rolling out to hundreds of thousands of iOS and Android users. [13]
  • To use it, a user opens the Be My Eyes app, selects the Be My AI tab and takes a picture. Be My AI gives a detailed description, and the user can chat and ask further questions to get more information. [13]
  • The announcement states that over 19,000 blind and low-vision beta testers contributed to the design and function of the feature. [13]
  • It warns that users may still get hallucinations and occasional wrong answers, and states that Be My AI does not and should not replace a white cane, guide dog or other mobility aid. [13]
  • Users who want to check its results or need more description can still reach the app's volunteers, who are described as available in 150 languages. [13]

The facts above come from the cited sources. The steps and analysis in this example are our explanation of how they fit together.

Example 2 of 5

Shopify: classifying products and extracting attributes with vision language models

ShopifyDocumented in an engineering article

Shopify Engineering's article of May 2025, Evolution of Product Classification at Shopify, describes the system that assigns a category and attributes to merchants' products using open-weight vision language models. [14]

The problem

Merchants describe products in their own words and photos. To power search, discovery and recommendations, Shopify needs each product placed in a standard taxonomy and given standard attributes. The article traces earlier attempts: a text classifier in 2018 and, in 2020, a model that combined image and text data for classification. By early 2023 the team wanted more granular product understanding than a category alone, and vision language models offered a way to get it.

Where this topic fits

This is image and text understanding with structured output, run as a high-volume service. The model reads a product's visual and textual information together. 4Common mistakes

  1. Sending the full-resolution photo and assuming the model sees every pixel.

    Why it causes problems
    The provider shrinks the image to its own limit before the model reads it. Small print, serial numbers and thin lines can fall below a readable size, and the model then guesses. You also pay for the upload time of pixels that are thrown away.
    How to recognise it
    Misread digits or invented text on images whose detail is clear to you at full size. Run the image's dimensions through the provider's resize rule and compare the result with the original.
    How to fix it
    Crop to the region that matters and send the crop at a size under the limit, or pre-resize yourself so you know what the model receives. Where fine detail is essential, use a higher-resolution model tier or a higher detail setting and accept the token cost.

  2. Using returned coordinates directly on the original image.

    Why it causes problems
    Coordinates refer to the image the model saw or to a normalised scale, and conventions differ. Claude returns pixels on the resized image, and Gemini returns values from 0 to 1000 with y first. An agent that clicks on unconverted coordinates clicks the wrong element.
    How to recognise it
    Boxes drawn on the original image are shifted or shrunk towards the top-left corner, or have width and height swapped. Errors grow with image size and vanish on small images.
    How to fix it
    Pre-resize images so that no conversion is needed, or convert with the exact resize rule for the model tier in use. Draw a sample of returned boxes on the originals before trusting them at scale.

  3. Estimating image cost from file size, or once per image instead of once per turn.

    Why it causes problems
    Tokens follow pixel dimensions and model rules, not megabytes, so a small file can be expensive and a large one cheap. In a conversation or agent loop the history is resent, so each image's tokens are input again on every later request.
    How to recognise it
    Input token counts in the usage data that climb with every turn of a session that contains screenshots, and bills that do not track the number of images uploaded.
    How to fix it
    Compute tokens from dimensions with the provider's formula, multiply by the number of requests that will carry the image, and drop or summarise old images from the history. Use prompt caching where the provider supports it.

  4. Treating extracted document values as correct because the output is well-formed JSON.

    Why it causes problems
    A model that cannot read a digit still returns a digit. Structured output guarantees the shape of the answer and says nothing about whether a total, a date or an identifier matches the page.
    How to recognise it
    Totals that do not equal the sum of their line items, identifiers that fail their known format, and spot checks against the source documents that find errors nobody reported.
    How to fix it
    Measure accuracy per field on a hand-labelled sample, add computed checks such as arithmetic and format rules, and send every document that fails a check to a person. Track the errors the checks miss.

  5. Analysing fast or text-heavy video with default sampling.

    Why it causes problems
    At one frame per second an event that lasts a fraction of a second may never be sampled, and at low media resolution small on-screen text is not legible. The model then describes the video confidently from what it did receive.
    How to recognise it
    Answers that miss brief events you can see in the footage, wrong readings of captions or scoreboards, and timestamps that are plausible but slightly off.
    How to fix it
    Raise the frame rate for the segment that matters and clip the video to that segment so the cost stays bounded. Use the high media resolution only when text must be read, and supply a transcript for speech.

  6. Asking an image generator for exact text, logos or layout and publishing the result unreviewed.

    Why it causes problems
    Providers document that text placement, recurring brand elements and precise composition are weak points. A misspelt label or a distorted logo on a published image is a visible, attributable error.
    How to recognise it
    Garbled or misspelt lettering, logos that differ slightly between images, and elements that sit in roughly but not exactly the requested position.
    How to fix it
    Generate the background or scene only, and add wording, logos and precise layout in code or a design tool. Review generated images with a checklist, automatically where possible and by a person before publication.

Map two models' bounding boxes back onto the original screenshot

A QA agent taps buttons in a mobile app by looking at screenshots. The screenshot is 1179×2556 pixels. Two models were asked for the bounding box of the Pay button on the same screenshot.

  • A Claude model on the standard resolution tier answered in pixels of the image it saw: [250, 1210, 470, 1262], in the order [x1, y1, x2, y2].
  • A Gemini model answered with box_2d equal to [772, 345, 805, 650]. Google documents this format as [ymin, xmin, ymax, xmax], with each value scaled to the range 0 to 1000.

Requirements

  • A function claude_box_to_original(box, original, tier) rescales a box by the size Claude saw for that tier and returns integers in the order x1, y1, x2, y2.
  • A function gemini_box_to_original(box_2d, original) reorders the values, because y comes first, and converts them from the 0 to 1000 scale to pixels.
  • Both functions clamp their results to the image, from 0 to the width and from 0 to the height.
  • Both functions raise ValueError for a box with no area, where x2 is not greater than x1 or y2 is not greater than y1.
  • The script prints both boxes, both tap points, how many pixels the tap would be off if the Claude box were used without rescaling, and what the Claude function returns when given the wrong tier.

Expected behaviour

The centre of the unconverted Claude box is (360.0, 1236.0), which is 811 pixels from the correct tap point. With tier="high-res" the function returns [250, 1210, 470, 1262] unchanged, because that tier does not resize a 1179×2556 image. Choosing the wrong tier therefore gives the same wrong tap as doing no conversion.

Hint 1

Find the size the model saw first, with resized_size(1179, 2556, *TIERS["standard"]). The scale factor for each axis is the original size divided by the size the model saw.

Hint 2

For the Gemini box, unpack the four numbers into named variables before any arithmetic. The first number is a y value.

Hint 3

Clamp after rounding, with max(0, min(value, upper)).

Show solution

Save this next to image_budget.py as map_boxes.py.

python
from image_budget import TIERS, resized_size


def check(box):
    x1, y1, x2, y2 = box
    if x2 <= x1 or y2 <= y1:
        raise ValueError(f"box {box} has no area")


def clamp(value, upper):
    return max(0, min(round(value), upper))


def claude_box_to_original(box, original, tier="standard"):
    """box is [x1, y1, x2, y2] in pixels of the image Claude saw after resizing."""
    check(box)
    seen_w, seen_h = resized_size(*original, *TIERS[tier])
    sx, sy = original[0] / seen_w, original[1] / seen_h
    x1, y1, x2, y2 = box
    return [clamp(x1 * sx, original[0]), clamp(y1 * sy, original[1]),
            clamp(x2 * sx, original[0]), clamp(y2 * sy, original[1])]


def gemini_box_to_original(box_2d, original):
    """box_2d is [ymin, xmin, ymax, xmax], each scaled to 0-1000."""
    ymin, xmin, ymax, xmax = box_2d
    check([xmin, ymin, xmax, ymax])
    width, height = original
    return [clamp(xmin / 1000 * width, width), clamp(ymin / 1000 * height, height),
            clamp(xmax / 1000 * width, width), clamp(ymax / 1000 * height, height)]


def centre(box):
    return ((box[0] + box[2]) / 2, (box[1] + box[3]) / 2)


SCREEN = (1179, 2556)
CLAUDE_BOX = [250, 1210, 470, 1262]
GEMINI_BOX = [772, 345, 805, 650]

if __name__ == "__main__":
    print("Claude saw:", resized_size(*SCREEN, *TIERS["standard"]))
    a = claude_box_to_original(CLAUDE_BOX, SCREEN)
    b = gemini_box_to_original(GEMINI_BOX, SCREEN)
    print("Claude box:", a, "tap", centre(a))
    print("Gemini box:", b, "tap", centre(b))
    raw = centre(CLAUDE_BOX)
    dx, dy = centre(a)[0] - raw[0], centre(a)[1] - raw[1]
    print("unscaled tap", raw, "is off by", round((dx * dx + dy * dy) ** 0.5), "px")
    print("wrong tier:", claude_box_to_original(CLAUDE_BOX, SCREEN, tier="high-res"))
    print("clamped:", claude_box_to_original([700, 1500, 730, 1580], SCREEN))
    try:
        gemini_box_to_original([805, 345, 772, 650], SCREEN)
    except ValueError as error:
        print("rejected:", error)

Use re.fullmatch for the invoice number so that extra characters at either end also fail.

Show solution
python
import re

from invoices import FIELDS, PREDICTED, TRUTH


def wrong_fields(truth, predicted):
    return [field for field in FIELDS if truth[field] != predicted[field]]


def failed_checks(doc):
    failures = []
    if abs(sum(doc["lines"]) - doc["total"]) > 0.01:
        failures.append("lines do not sum to total")
    if not re.fullmatch(r"INV-\d{4}", doc["number"]):
        failures.append("invoice number has the wrong format")
    return failures


errors = {key: wrong_fields(TRUTH[key], PREDICTED[key]) for key in TRUTH}
flags = {key: failed_checks(PREDICTED[key]) for key in PREDICTED}

for field in FIELDS:
    correct = sum(field not in wrong for wrong in errors.values())
    print(f"{field:<7} {correct}/{len(TRUTH)} correct")
total_fields = len(FIELDS) * len(TRUTH)
total_wrong = sum(len(wrong) for wrong in errors.values())
print(f"field accuracy    {(total_fields - total_wrong) / total_fields:.1%}")
print(f"documents correct {sum(not wrong for wrong in errors.values())}/{len(TRUTH)}")

for key in TRUTH:
    if errors[key] and flags[key]:
        outcome = "caught"
    elif errors[key]:
        outcome = "MISSED"
    elif flags[key]:
        outcome = "false alarm"
    else:
        outcome = "auto-accepted, correct"
    print(key, outcome, errors[key], flags[key])

What the numbers mean:

  • Field accuracy flatters the system. 87.5% of fields are right, yet half of the invoices contain an error. A document is usable only when every field is right. If each field were wrong independently one time in eight, you would expect 0.8754≈0.590.875^4 \approx 0.590.8754≈0.59 of documents to be fully correct. Report both numbers, and make decisions with the document-level one.
  • Computed checks catch inconsistency. The arithmetic check finds b and e because a wrong total or a missing line breaks a relationship between fields. The format check finds d because the correct value has a known shape.
  • They cannot catch a wrong value that is consistent. In g the model returned 2026-03-07 for 2026-07-03. Both are valid dates and nothing else on the invoice contradicts either. Catching it needs outside information: the date on the matching purchase order, a second read of a tight crop of the date field, or a human review of a random sample of auto-accepted invoices.
  • Checks have a cost. h was extracted correctly and still went to review, because the rule assumed that lines always sum to the total. That is acceptable. A false alarm costs a minute of a reviewer's time, and a missed error becomes a wrong payment. If false alarms grow, refine the rule, for example by extracting tax as its own field.
