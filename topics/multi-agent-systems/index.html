Multi-Agent Systems

A multi-agent system is an application in which two or more LLM agents, each with its own instructions, tools and context window, work on the same task and pass work or control between them. Its topology is the rule for who decides which agent acts next and what that agent is allowed to see.

1Overview

Why it matters

Splitting one agent into several changes three things at once: how many model calls a request takes, what each call can see, and who is responsible for the final answer. Done for a good reason, it keeps a specialist's context free of another domain's tool output and lets independent work run in parallel. Done by default, it multiplies cost and adds failures that a single agent cannot have, such as a handoff that drops the one fact the next agent needed, or two agents transferring a customer back and forth.

The cost is not small. Anthropic reports that multi-agent implementations typically use 3 to 10 times more tokens than single-agent approaches for equivalent tasks, and that it has seen teams spend months on elaborate multi-agent architectures before finding that better prompting of one agent gave equivalent results. Anyone who designs an agent architecture, evaluates a framework built around crews or teams, or debugs a trace that crosses agent boundaries needs to know what each topology costs and when one agent is enough.

Key terms

Agent
In this lesson, one model loop with its own instructions, its own tools and its own context window.
Multi-agent system
An application in which a task passes through more than one agent, with some rule for how the agents hand work or messages to each other.
Topology
The pattern of connections between agents. It fixes who chooses the next agent and which agents can exchange information directly.
Supervisor
An agent that keeps control of the task, calls other agents as if they were tools and writes the final answer. Also called an orchestrator, a manager or a lead agent.
Handoff
A transfer of control in which the receiving agent becomes the active agent and replies to the user directly.
Group chat
A topology in which agents take turns posting to one shared conversation thread that all of them read.
Chat manager
The code or model that picks the next speaker in a group chat and decides when the conversation is finished.
Context isolation
Giving each agent its own context window, so that tool output and reasoning from one agent enter another agent's context only when they are passed on deliberately.
Brief
The task description that a delegating agent writes for another agent. It is everything the receiving agent knows about the wider task.
Coordination cost
The extra model calls, tokens, latency and failure points that exist only because agents have to route work and exchange information.

2Explanation

Introduction

The Agent Loop described one agent: one model, one set of instructions and tools, and one context that grows with every step. Orchestrator-Workers added a lead model that splits a task and gives the pieces to workers. This lesson asks the wider question. When a system contains several agents, how should they be connected, what should each one see, and is the second agent worth having at all?

Organisations answer the same question for people. A small shop has one person who takes the order, checks the stock and handles the refund. As it grows it can organise in three familiar ways. A manager can take every request, assign pieces to staff and assemble the reply. A reception desk can work out who you need and transfer you, and from then on you talk to that person. Or everyone can sit in one meeting and hear everything that is said. Each arrangement fixes something and costs something: the manager becomes a bottleneck, a transfer can lose what you have already explained, and a meeting uses everyone's time.

Agent systems use the same three arrangements, and the names are now fairly standard across frameworks:

  • Supervisor. One agent keeps control, calls specialists as if they were tools and writes the final answer.
  • Handoff. The active agent transfers the conversation to another agent, which then answers the user itself.
  • Group chat. Agents take turns on one shared thread, and a chat manager chooses who speaks next.

Microsoft's AI Agents for Beginners (opens in a new tab) course lists group chat and hand-off among its multi-agent patterns, and Microsoft's architecture guide to orchestration patterns (opens in a new tab) describes both in detail. That guide opens with advice that matters more than any single pattern: use the lowest level of complexity that reliably meets your requirements, because each level adds coordination overhead, latency and cost.

The rest of the lesson covers how each topology routes work, what context isolation buys and what it hides, how to count coordination cost before you build, and the checks that tell you one agent is enough.

How it works

Three decisions define a topology

An agent in this lesson is one model loop with its own instructions, tools and context window. A system is multi-agent when a task passes through more than one such loop. Every design, whatever a framework calls it, answers three questions:

  1. Who picks the next agent? A supervisor, the agent that is currently active, a chat manager, or plain code.
  2. What does the next agent see? A short brief, a filtered history, or the whole conversation.
  3. Who answers the user? The coordinator, or whichever specialist is active at the end.

Supervisor: one agent delegates and merges

The supervisor receives the request, decides which specialists to call and writes the final answer. Specialists are exposed to it as tools. The OpenAI Agents SDK calls this agents as tools (opens in a new tab): a manager agent keeps control of the conversation and invokes specialists through Agent.as_tool(). LangChain calls the same shape subagents (opens in a new tab). Orchestrator-Workers is this topology with the subtasks decided per request.

Two properties follow. Each specialist starts from a fresh context holding only its own instructions and the brief, so specialists can run in parallel and cannot see each other's work. And every result passes back through the supervisor, which costs at least one extra model call and turns the supervisor into a translator. LangChain's benchmark of three architectures (opens in a new tab) found that its first supervisor lost accuracy by re-interpreting specialist replies, which the authors compare to a game of telephone. A set of changes that included letting the supervisor forward a specialist's message unchanged and keeping handoff messages out of the specialists' context raised its score by nearly 50%.

Handoff: control moves to the specialist

In a handoff the active agent stops and another agent takes over the conversation. Frameworks implement the transfer as a tool call. In the OpenAI Agents SDK, a handoff to an agent named Refund Agent appears to the model as a tool named transfer_to_refund_agent. This excerpt from the SDK's handoffs documentation (opens in a new tab) declares a triage agent that can transfer to two specialists:

python
from agents import Agent, handoff

billing_agent = Agent(name="Billing agent")
refund_agent = Agent(name="Refund agent")

triage_agent = Agent(name="Triage agent", handoffs=[billing_agent, handoff(refund_agent)])

Only one agent is active at a time, so nothing runs in parallel, and the specialist replies to the user in its own words with no supervisor in between. By default the new agent sees the entire previous conversation. An input_filter can trim it, and the built-in remove_all_tools filter removes tool items from the history.

Handoffs save calls when a conversation stays with one specialist. LangChain's documentation counts three model calls for a one-shot request with handoffs against four with subagents, and two against four on a repeat request, because the specialist is still active. The risks are routing risks. Microsoft's guide lists infinite handoff loops and unpredictable paths, and recommends a plain router when the right agent can be identified from the first message.

Group chat: everyone reads one thread

In a group chat all agents post to a single accumulating thread and a chat manager chooses the next speaker. The manager can be code, such as round-robin, or a model that reads the thread. Microsoft Agent Framework's group chat orchestration (opens in a new tab) builds a star with the orchestrator in the middle. Before each turn it synchronises the chosen agent with the conversation history, and after the turn it broadcasts the reply to the others.

Shared context is the point. Agents can review and build on each other's replies, which suits debate, brainstorming and maker-checker loops, where one agent drafts and another approves the draft or sends it back. Shared context is also the cost. Each turn re-reads a thread that every earlier turn made longer, the same growth that The Agent Loop derived for one agent, now paid by every participant. Microsoft's guide suggests limiting a group chat to three or fewer agents, and notes that agents in this pattern typically discuss in a read-only mode instead of changing running systems.

Context isolation: what crosses the boundary

Isolation means an agent's tool output and reasoning stay in its own context unless something passes them on. Anthropic's guide to multi-agent systems (opens in a new tab) gives the motivating case: a support agent whose order lookups each add thousands of tokens then has to diagnose a technical fault with that history in the way. A separate agent can read the orders and return only the 50 to 100 tokens that matter.

What crosses the boundary is a design choice with three settings:

  • Brief only. The receiver knows nothing except what the sender wrote. Anthropic's research team found that a brief needs an objective, an output format, guidance on tools and sources, and clear task boundaries. Without them, subagents duplicated work or left gaps.
  • Filtered history. The receiver gets the conversation without tool traffic or older turns.
  • Full history. Nothing is lost, and nothing is isolated.

Isolation hides decisions as well as noise. Cognition's Don't Build Multi-Agents (opens in a new tab) argues that actions carry implicit decisions, so agents that cannot see each other's work make choices that conflict. Its example is two subagents building parts of one game that do not match. The practical rule from Anthropic's guide is to split along context boundaries and not along job titles. Work that needs the same information belongs in one agent. Planner, implementer, tester and reviewer agents break that rule, because each role needs what the previous one learned.

Coordination cost

Coordination cost is everything the system spends on routing and exchanging information, on top of the task itself. It appears in four places.

  • Model calls. Every routing decision and every merge is a call that does no task work.
  • Tokens. Instructions are duplicated across agents, and every brief and summary is written by one model and read by another.
  • Links. A supervisor with nnn specialists has nnn links. If every agent may message every other, nnn agents have n(n−1)/2n(n-1)/2n(n−1)/2 links: 6 for 4 agents and 28 for 8. Each link is a place where context can be dropped or misread.
  • Errors. A wrong result that nobody checks is passed on as fact.

A study by researchers at Google Research, Google DeepMind and MIT (opens in a new tab) measured these effects across 260 configurations on six benchmarks, keeping task prompts, tools and computational budgets identical.

Independent agents, whose outputs were merged without any communication, added the fewest turns but amplified errors most, by a factor of 17.2. A central orchestrator held that factor to 4.4, which the authors attribute to validation bottlenecks that intercept errors. It did so at the price of 285% more turns than one agent.

When one agent is enough

Start from one agent and look for evidence against it. The sources agree on what counts as evidence.

  • Context pollution. Output from one subtask sits in the way of the next, and quality drops as the context fills.
  • Independent, parallel work. The subtasks do not need each other's results.
  • Tool overload. Anthropic's signals are a tool count that is often 20 or more, tools from unrelated domains, and new tools degrading existing tasks. In LangChain's benchmark a single agent's score fell sharply once two or more unrelated domains were added to its prompt.
  • Hard boundaries. Agents need different permissions, owners or models. Microsoft's guide names security boundaries as a reason a single agent can be infeasible.

Without one of these, more agents can make results worse as well as more expensive. In the Google and MIT study every multi-agent variant scored between 39% and 70% below one agent on a sequential planning benchmark, and tasks that one agent already solved more than about 45% of the time saw negative returns from extra agents. On a finance benchmark whose questions split into independent analyses, a centralised team scored 80.8% above the single agent. The shape of the task decided the outcome, not the number of agents.

Worked example: One support request sized under five designs, with every model call's context listed

A customer writes: I was charged twice for order A-17 and my Wi-Fi keeps dropping. Answering takes two lookups, a billing ledger and a router log. Before building anything you can size each design by listing its model calls and what each call would have in its context.

The script below does that. It is an accounting model, not a live agent. Each tuple is one model call, and the token sizes in SIZE are assumptions to replace with your own measurements. Save it as topology_cost.py. It needs only the Python standard library.

python
# Assumed size, in tokens, of each kind of item that can sit in a model's context.
SIZE = {"sys": 300, "user": 40, "call": 30, "ledger": 2000, "log": 3000,
        "brief": 60, "summary": 80}

ONE = ["sys", "user"]          # a specialist, supervisor, triage agent or chat manager
BOTH = ["sys", "sys", "user"]  # one generalist carrying both domains' instructions and tools

# Each tuple is one model call: (agent, the items in its context on that call).
TWO_PROBLEMS = {
    "single agent": [
        ("generalist", BOTH),
        ("generalist", BOTH + ["call", "ledger"]),
        ("generalist", BOTH + ["call", "ledger", "call", "log"]),
    ],
    "supervisor": [
        ("supervisor", ONE),                                  # writes two briefs
        ("billing", ["sys", "brief"]),
        ("billing", ["sys", "brief", "call", "ledger"]),      # returns a summary
        ("network", ["sys", "brief"]),
        ("network", ["sys", "brief", "call", "log"]),         # returns a summary
        ("supervisor", ONE + ["brief", "brief", "summary", "summary"]),
    ],
    "handoff, full history": [
        ("triage", ONE),                                      # emits a transfer call
        ("billing", ONE + ["call"]),
        ("billing", ONE + ["call", "call", "ledger"]),        # replies, then transfers
        ("network", ONE + ["call", "call", "ledger", "summary", "call"]),
        ("network", ONE + ["call", "call", "ledger", "summary", "call", "call", "log"]),
    ],
    "handoff, tools filtered": [
        ("triage", ONE),
        ("billing", ONE),
        ("billing", ONE + ["call", "ledger"]),
        ("network", ONE + ["summary"]),                       # tool items were removed
        ("network", ONE + ["summary", "call", "log"]),
    ],
    "group chat": [
        ("manager", ONE),                                     # picks the first speaker
        ("billing", ONE),
        ("billing", ONE + ["call", "ledger"]),                # posts a summary to the thread
        ("manager", ONE + ["summary"]),
        ("network", ONE + ["summary"]),
        ("network", ONE + ["summary", "call", "log"]),
        ("manager", ONE + ["summary", "summary"]),            # closes with the answer
    ],
}
ONE_PROBLEM = {
    "single agent": [("generalist", BOTH), ("generalist", BOTH + ["call", "ledger"])],
    "supervisor": [("supervisor", ONE), ("billing", ["sys", "brief"]),
                   ("billing", ["sys", "brief", "call", "ledger"]),
                   ("supervisor", ONE + ["brief", "summary"])],
    "handoff, full history": [("triage", ONE), ("billing", ONE + ["call"]),
                              ("billing", ONE + ["call", "call", "ledger"])],
}
COORDINATORS = {"supervisor", "triage", "manager"}


def report(title, runs):
    print(title)
    print(f"{'design':<25}{'calls':>6}{'coordinator':>12}{'input':>8}{'largest':>9}{'saw ledger':>12}")
    for design, calls in runs.items():
        sizes = [sum(SIZE[item] for item in context) for _, context in calls]
        coordinator = sum(agent in COORDINATORS for agent, _ in calls)
        saw_ledger = sorted({agent for agent, context in calls if "ledger" in context})
        print(f"{design:<25}{len(calls):>6}{coordinator:>12}{sum(sizes):>8}{max(sizes):>9}"
              f"  {', '.join(saw_ledger)}")


report("Request A: double charge and Wi-Fi drops", TWO_PROBLEMS)
report("Request B: double charge only", ONE_PROBLEM)

supervisor                    6           2    7460     3390  billing
handoff, full history         5           1   11160     5540  billing, network
handoff, tools filtered       5           1    6920     3450  billing
group chat                    7           3    7840     3450  billing

What the numbers show:

  • Coordination is paid in calls. The supervisor needs 6 calls where one agent needs 3, and 2 of the 6 only route and merge. The group chat spends 3 of its 7 calls on the manager.
  • Isolation shrinks the largest context. The single agent's last call carries 5,700 tokens because the ledger is still there while it reads the router log. Under the supervisor the largest call is 3,390, and only the billing agent ever sees the ledger. Total input falls from 9,010 to 7,460 because the ledger is read once, not twice.
  • A handoff carries history with it. With full history the network agent receives a ledger it does not need, and the run costs 11,160 tokens. Removing tool items at each transfer brings that to 6,920, and the network agent then depends on billing's 80-token reply for all it knows about the charge.
  • One domain, one agent. For request B the supervisor doubles the calls, 4 against 2, and trims the largest context by only 280 tokens. Nothing was polluting the context, so there was nothing to isolate.

The model flatters the multi-agent designs. It assumes a perfect split and one tool call per specialist, and it ignores the output tokens spent writing briefs and summaries. Real specialists explore and repeat work, which is how real systems reach the 3 to 10 times reported by Anthropic. Treat it as a lower bound.

Edge cases and limitations

A handoff changes which guardrails run
In the OpenAI Agents SDK, input guardrails apply only to the first agent in a handoff chain and output guardrails only to the agent that produces the final output. A specialist reached by transfer is therefore not protected by an input guardrail declared on it, and the triage agent's output guardrail never sees the specialist's reply. Put checks that must always run on the entry agent and on every agent that can end the run, or use tool-level guardrails.
A group chat may not share tool output
Shared thread does not always mean shared everything. In Microsoft Agent Framework's Python implementation, function calls, function results and other tool-control content are filtered before a reply is broadcast, and non-user messages keep their text only. An agent that looked something up must state the finding in its reply, or the other participants will never see it.
A spawned agent starts without the conversation
Isolation applies from the first token. A Claude Code teammate loads project context and the spawn prompt, and the lead's conversation history does not carry over. Anything the user said ten turns ago, such as a constraint or a rejected approach, reaches the new agent only if the brief repeats it. Review briefs as carefully as prompts, because for the receiving agent the brief is the prompt.
The supervisor can be the least accurate agent in the system
Every answer passes through the supervisor twice, once to route and once to merge. Uber evaluates supervisor routing accuracy separately for its Finch agent to catch intent collisions, where the supervisor picks the wrong sub-agent because a question is ambiguous or tools look alike. LangChain's benchmark found a supervisor losing accuracy by re-wording replies. Test routing and merging as components in their own right, and let the supervisor forward a specialist's reply unchanged when no merging is needed.
Parallel writers conflict even when each brief is correct
Two agents can each follow their brief and still produce work that does not fit together, because each made choices the other could not see. The Claude Code documentation warns that two teammates editing the same file overwrite each other, and Microsoft's guide lists sharing mutable state between concurrent agents as an antipattern. Parallel agents are safest when they only read, or when each one owns files or records that no other agent touches.

When to use it, and when something simpler is enough

Use it when

  • One agent's context fills with tool output from one subtask that the next subtask does not need, and you can see quality drop in traces as it fills.
  • The task splits into pieces that do not need each other's results, so specialists can work in parallel and return condensed findings.
  • A single agent has roughly 20 or more tools across unrelated domains and picks the wrong one, or needs conflicting behaviours such as empathetic support and critical review.
  • Agents have to stay separate for reasons outside the prompt: different permissions or security boundaries, different owning teams, or a third-party agent you cannot merge into your own.
  • The task is valuable enough to justify several times the token cost of a single agent.

Think twice when

  • The steps are sequential and each depends on details of the one before, as in multi-step planning or changes to a single codebase.
  • One agent already succeeds most of the time. Fix its remaining failures with prompt, tool and evaluation work first.
  • Several agents would write to the same files, records or other shared state at the same time.
  • The right specialist is known from the first message. A router or a fixed workflow gives the same specialisation with no conversation between agents.
  • Latency or cost budgets are tight, because every routing step and every merge is another model call.

A simpler alternative. One agent with a tighter prompt, fewer and better-described tools, and active context management: compaction on long runs, tools or skills loaded only when needed, and a deterministic router in front when requests fall into known categories. This stops being enough when traces show that unrelated tool output is degrading later steps, that independent subtasks are queuing behind each other, or that a security boundary cannot be enforced inside one agent.

Key takeaways

  • A multi-agent topology is defined by three choices: who picks the next agent, what that agent sees, and who answers the user.
  • A supervisor delegates through briefs and merges the results, a handoff transfers the conversation to a specialist who answers directly, and a group chat puts every agent on one shared thread run by a chat manager.
  • Context isolation keeps one agent's tool output out of another agent's context, but it also hides decisions, so split work only where the context really separates.
  • Coordination is paid for in extra model calls, duplicated tokens, more links between agents and errors that pass unchecked from one agent to the next.
  • Start with one agent and add another only when traces show context pollution, independent parallel work, tool overload or a boundary that one agent cannot respect.
  • Sequential, tightly dependent tasks get worse with more agents, while tasks that split into independent parts can improve substantially.

Example 1 of 5

Uber Finch: a supervisor agent routing finance questions to specialist sub-agents in Slack

UberDocumented in an engineering article

Finch is Uber's conversational data agent for its finance teams, used from Slack. Uber's engineering blog post Unlocking Financial Insights with Finch (July 2025) describes its architecture, in which a supervisor agent sends each question to a specialised sub-agent. [12]

The problem

Finance staff need figures that live in financial data systems, and getting them has meant writing SQL or asking someone who can. The post presents Finch as a way to ask in plain language from Slack and get the data back. The questions are not all of one kind. Some need a SQL query built from the right tables, and the post also names a sub-agent for reading documents. Each kind needs different tools and instructions.

Where this topic fits

The supervisor sits between the Slack message and the sub-agents. It receives every query, decides which sub-agent should handle it and passes the query on. The chosen sub-agent then does the domain work. For a data question, the SQL Writer Agent looks up table metadata, builds a query and runs it. Uber builds and orchestrates the agents with LangGraph.

How it is applied, step by step

  1. A user asks a question in Slack in plain language.
  2. The supervisor agent receives the query and sends it to a suitable sub-agent, such as the SQL Writer Agent. A Document Reader Agent is the other sub-agent the post names.
  3. The SQL Writer Agent retrieves metadata for the relevant tables from an OpenSearch index that stores SQL table columns, values and natural-language aliases.
  4. It builds the SQL query from that metadata and runs it against the appropriate data source.
  5. The result goes back to the user in Slack. In a typical supervisor implementation, the sub-agent's working context, such as the metadata it retrieved, stays with the sub-agent and only the result returns.
  6. Uber evaluates the layers separately: each sub-agent against expected responses, the supervisor's routing accuracy, end-to-end runs, and regression tests on earlier queries.

Why this approach fits

The two kinds of question need different tools and context. A SQL-writing agent needs table metadata and query rules, and a document agent needs neither. A supervisor gives users one entry point in Slack while keeping each sub-agent's prompt and tools narrow. It also makes the system testable in pieces: a wrong answer can be traced to routing, to metadata retrieval or to query writing, and the post describes a separate evaluation for each layer.

Limitation or tradeoff

The supervisor adds a routing decision to every question, and that decision can be wrong. Uber names the failure: intent collisions, where the supervisor makes the wrong choice because a question is ambiguous or tools have similar capabilities. In a finance tool a wrong route produces a confident answer from the wrong source, so routing accuracy has to be tested and monitored as its own metric. The post publishes no accuracy or cost figures, so it does not show what the multi-agent design costs compared with one agent.

What the sources document

  • The post states that the Supervisor Agent receives the query and sends it to an appropriate sub-agent, such as the SQL Writer Agent. [12]
  • Uber states that it uses LangGraph to construct and orchestrate its agents, and that Finch reaches self-hosted and third-party large language models through Uber's Generative AI Gateway. [12]
  • Finch uses an OpenSearch index to store dataset metadata, including SQL table columns, values and natural-language aliases. [12]
  • Supervisor routing accuracy is evaluated to identify intent collisions, where the supervisor makes the wrong choice when a question is ambiguous or tools have similar capabilities. [12]
  • For data retrieval agents such as the SQL Writer Agent, the results of the generated query are compared with those of a golden query. [12]

The facts above come from the cited sources. The steps and analysis in this example are our explanation of how they fit together.

Example 2 of 5

OpenAI's airline customer service demo: a triage agent handing the conversation to specialists

OpenAIDocumented in official docs

The OpenAI Agents SDK documents handoffs as its mechanism for one agent to delegate to another. OpenAI's openai-cs-agents-demo repository is a customer service interface built on the SDK, with a triage agent and five specialist agents for an airline. [5][6]

The problem

An airline customer conversation moves between topics. The README's demo flows include a seat change followed by a flight status question and then a policy question, and a disrupted trip that needs rebooking, a new seat and a compensation case. Each topic needs different tools and instructions. The customer should not have to start again when the topic changes, and the agent that owns the topic should be the one that replies.

Where this topic fits

The handoff is the step that changes which agent is active. The triage agent is the entry point and routes to a specialist. Specialists hand off onward when the topic changes: in the README's third flow the Flight Information Agent hands off to the Booking & Cancellation Agent. A relevance guardrail and a jailbreak guardrail check the conversation.

How it is applied, step by step

  1. Each specialist is its own agent with its own instructions and tools: flight information, booking and cancellation, seats and special services, FAQ, and refunds and compensation.
  2. An agent lists the agents it may transfer to in its handoffs parameter. The SDK presents each handoff to the model as a tool, named transfer_to_ followed by the target agent's name.
  3. When the model calls a transfer tool, the target agent takes over the conversation. By default it sees the entire previous conversation history.
  4. An input filter on the handoff can change what the new agent receives. The built-in remove_all_tools filter removes structured tool items from the history.
  5. The new agent replies to the customer itself and can hand off again. In the first demo flow the Seat & Special Services Agent routes a flight status question to the Flight Information Agent, which then routes a policy question to the FAQ Agent.
  6. The guardrails answer off-topic requests and attempts to extract system instructions with a fixed refusal that the assistant can only answer questions related to airline travel.

Why this approach fits

A customer conversation has one participant, who should always be talking to the agent that owns the current topic. Handoffs give that. The specialist answers in its own words with its own tools and stays active for follow-up questions on the same topic, so no supervisor has to re-word each reply. The route also cannot be fixed in advance, because the next topic is only known when the customer raises it.

Limitation or tradeoff

By default the whole conversation travels with every transfer, so after a few topics a specialist starts with other agents' tool output in its context. Filters fix that at the risk of removing something the next agent needed. Guardrails need care: input guardrails apply only to the first agent in the chain and output guardrails only to the agent that produces the final output. The mechanism does not stop two agents transferring to each other repeatedly, so a limit has to come from the run's turn limit or from the application. The repository is a demo, not a production deployment.

What the sources document

  • Handoffs are represented as tools to the LLM. A handoff to an agent named Refund Agent becomes a tool named transfer_to_refund_agent. [5]
  • When a handoff occurs the new agent takes over the conversation and sees the entire previous conversation history. An input filter can change this, and remove_all_tools removes structured tool items from the history. [5]

Example 3 of 5

Microsoft Agent Framework group chat: an orchestrator choosing speakers on a shared thread

MicrosoftDocumented in official docs

Microsoft Research's AutoGen paper (2023) introduced a group chat manager for multi-agent conversations. Microsoft Agent Framework's documentation, updated in October 2026, describes the current form of the pattern as its group chat orchestration, and Microsoft's architecture guide says when to use it. [7][8][2]

The problem

Some tasks improve when agents respond to each other, for example a writer revising after a reviewer's comments, or specialists challenging one another's recommendations. A fixed pipeline cannot decide who should speak next from what was just said, and pairwise delegation hides each exchange from the other agents. The AutoGen paper presents dynamic group chat as collaboration with no predetermined order of communication.

Where this topic fits

The orchestrator sits at the centre of a star. Participants never call each other. On every round the orchestrator chooses a speaker, brings that agent up to date with the conversation, collects its reply and shares the reply with everyone else. Ending the conversation is also the orchestrator's job, through a termination condition or a decision by an orchestrator agent.

How it is applied, step by step

  1. Participants are defined as agents with a name, a description and instructions, for example a researcher and a writer.
  2. A speaker-selection strategy is chosen: a selection function such as round-robin, an orchestrator agent that reads the conversation and picks, or a custom orchestrator.
  3. Before a participant's turn, the orchestrator synchronises that agent's session with the conversation history. The agents do not share one session object.
  4. The selected participant replies and the orchestrator broadcasts the reply to all other participants. In the Python implementation, function calls and function results are filtered out before broadcast.
  5. The orchestrator chooses the next speaker and the cycle repeats. The AutoGen paper describes the same loop as dynamically selecting a speaker, collecting its response and broadcasting the message.
  6. The conversation ends when a termination condition holds, such as a message count, or when the orchestrator agent decides the task is done.

Why this approach fits

The shared thread removes the hidden-decision problem that isolated agents have. Every participant sees what the others said and can correct it or build on it. Microsoft's guide adds that a single accumulating thread gives transparency and auditability and lets a person take part in the conversation. Keeping speaker selection in one place means the turn order can start as simple code and become a model decision only if the task needs it.

Limitation or tradeoff

Every participant reads the whole thread on every turn, so cost grows with each round and material that matters to one agent sits in everyone's context. Microsoft's guide warns about conversation loops, says control gets harder as agents are added, suggests three or fewer agents, and advises against the pattern when the chat manager has no objective way to tell that the task is complete. The evidence for model-chosen speakers is thin: the AutoGen paper's pilot study used 12 hand-written tasks.

What the sources document

  • The Agent Framework documentation says group chat orchestration assembles agents in a star topology with an orchestrator in the middle, and that the orchestrator can select speakers by round-robin, prompt-based selection or custom logic. [7]
  • Agents in a group chat do not share the same session instance. The orchestrator synchronises each agent's session with the conversation history before each turn and broadcasts each response to all other agents after the turn. [7]
  • In the Python implementation, function calls, function results, approval payloads and other tool-control content are filtered before broadcast, and non-user messages retain text only. [7]
  • The AutoGen paper describes its GroupChatManager as repeating three steps: dynamically selecting a speaker, collecting the response from that speaker, and broadcasting the message. Its pilot study of speaker selection used 12 manually crafted complex tasks. [8]
  • Microsoft's architecture guide suggests limiting group chat orchestration to three or fewer agents in order to keep control of the conversation. [2]

Claude Code agent teams: independent sessions coordinating through a task list and mailboxes

AnthropicDocumented in official docs

Claude Code's documentation describes agent teams, an experimental feature in which several Claude Code sessions work together: a lead session and teammates that each run in their own context window, with a shared task list and direct messaging between agents. [9][10]

The problem

Claude Code's subagents return a result to the agent that called them and suit focused tasks where only the result matters. Some coding work needs the workers to talk to each other: reviewers comparing findings, investigators trying to disprove each other's theories about a bug, or a change that spans frontend, backend and tests with a different owner for each. The documentation presents agent teams for that kind of work.

Where this topic fits

This is a hybrid topology. The lead acts as a supervisor: it spawns teammates, creates tasks and synthesises results. Teammates are also peers: any teammate can message any other by name, and they can claim work from a shared task list without waiting for the lead to assign it. Context isolation is complete, because each teammate is a separate session.

How it is applied, step by step

  1. The user enables the feature and describes the team in natural language. The lead session spawns the teammates and gives each one a spawn prompt.
  2. Each teammate starts with its own context window. It loads the project context a normal session would (CLAUDE.md, MCP servers and skills) plus the spawn prompt. The lead's conversation history is not included.
  3. The lead puts tasks on a shared list. A task is pending, in progress or completed, and a task with unresolved dependencies cannot be claimed.
  4. A teammate claims a task, or the lead assigns one. Claiming uses file locking so that two teammates cannot take the same task.
  5. Teammates send messages to each other by name through per-agent mailboxes, and the messages are delivered automatically.
  6. When a teammate finishes and goes idle, it notifies the lead and includes its final answer. The lead combines the findings.

Why this approach fits

The documented use cases are ones where independence is the point. Investigators with separate contexts do not anchor on the first plausible theory, and the documentation's debugging example asks teammates to try to disprove each other. Direct messages let that argument happen without routing every exchange through the lead. A locked task list coordinates who does what through a mechanism that does not depend on any model remembering it.

Limitation or tradeoff

Cost and coordination grow with the team. The documentation says agent teams use significantly more tokens than a single session and that token use scales with the number of active teammates, and the costs page gives roughly 7 times a standard session when teammates run in plan mode. It recommends starting with 3 to 5 teammates and warns that two teammates editing the same file overwrite each other. The feature is experimental, with listed limits that include no resumption of in-process teammates, task status that can lag, and no nested teams. For sequential tasks, same-file edits or work with many dependencies, the documentation says a single session or subagents are more effective.

What the sources document

  • Each teammate has its own context window. When spawned it loads the same project context as a regular session (CLAUDE.md, MCP servers and skills) and receives the spawn prompt from the lead. The lead's conversation history does not carry over. [9]
  • Tasks have three states (pending, in progress and completed) and can depend on other tasks. Task claiming uses file locking to prevent race conditions when several teammates try to claim the same task. [9]
  • The comparison table says subagents return a result to the caller and are best for focused tasks where only the result matters, while teammates message each other directly and are best for complex work requiring discussion and collaboration. [9]
  • The documentation recommends starting with 3 to 5 teammates for most workflows and says token costs scale linearly because each teammate has its own context window. [9]
  • The costs page states that agent teams use approximately 7 times more tokens than standard sessions when teammates run in plan mode. [10]

A controlled study of five agent architectures across six benchmarks

Google ResearchDocumented in a paper

Towards a Science of Scaling Agent Systems, a paper by authors from Google Research, Google DeepMind and MIT (first posted in December 2025, version 3 in April 2026), compares one single-agent architecture and four multi-agent architectures across 260 configurations. [11]

The problem

Advice on when to add agents has mostly been rules of thumb. The authors set out to measure when coordination helps, holding everything except the architecture as equal as they could, so that a difference in results can be attributed to the topology and not to different prompts or tools.

Where this topic fits

The topology is the variable under test. The paper defines a single-agent system, independent agents whose outputs go only to an aggregator, a centralised design in which an orchestrator is connected to every sub-agent, a decentralised design in which every agent is connected to every other, and a hybrid that adds peer links to an orchestrator. In this lesson's terms those are one agent, parallel workers that never communicate, a supervisor, a discussion among peers with no manager, and a supervisor whose specialists can also talk to each other.

How it is applied, step by step

  1. The authors keep the task prompts, tools and computational budgets identical, and vary the architecture, the model and the benchmark.
  2. They run 260 configurations across six benchmarks: BrowseComp-Plus, Finance-Agent, PlanCraft, Workbench, SWE-bench Verified and Terminal-Bench.
  3. For each architecture they report coordination metrics alongside task success, including average turns, overhead relative to the single agent and an error amplification factor.
  4. They compare each multi-agent architecture with the single-agent result on the same benchmark.
  5. They fit a model that predicts performance from measurable properties of the task and the system, and check whether it selects the best architecture on configurations it has not seen.

Why this approach fits

It tests this lesson's central claim directly: whether adding agents helps depends on the structure of the task. A finance question that divides into separate analyses matches a design in which an orchestrator gives independent pieces to sub-agents, and the paper reports its largest gain there. A planning task in which each step constrains the next has nothing to give out in parallel, so coordination messages use budget that reasoning needed. Because prompts, tools and budgets are held equal, the result is about topology and not about one side having better prompts.

Limitation or tradeoff

These are benchmark results with 2025 models, not production measurements. The reported changes range from +80.8% to -70.0% depending on the task, so no average claim about multi-agent systems follows from the study. Its predictive model explains a minority of the variance, with a cross-validated R squared of 0.373. The architectures are generic: a production supervisor with carefully written briefs and verification steps could do better or worse than the paper's centralised design. Use the study for its direction and its mechanisms, and measure your own single-agent baseline.

What the sources document

  • The study covers 260 configurations spanning six agentic benchmarks and five architectures, and states that it maintains identical task prompts, tools and computational budgets across configurations. [11]
  • On Finance-Agent, centralised coordination reached +80.8% relative to the single agent (mean 0.631 against 0.349). On PlanCraft every multi-agent architecture was worse: -39.1% hybrid, -41.5% decentralised, -50.3% centralised and -70.0% independent. [11]
  • Table 5 reports average turns of 7.2 for the single agent, 11.4 independent, 26.1 decentralised, 27.7 centralised and 44.3 hybrid, with overheads of 58%, 263%, 285% and 515%. [11]
  • The abstract reports that independent systems amplify trace-level errors 17.2 times, that centralised coordination contains this to 4.4 times through validation bottlenecks, and that tasks where single-agent performance already exceeds 45% accuracy see negative returns from additional agents. [11]
  • The fitted model has a cross-validated R squared of 0.373, and the paper reports 87% correct architecture selection on held-out configurations. [11]

4Common mistakes

  1. Splitting one task into planner, implementer, tester and reviewer agents because a human team has those job titles.

    Why it causes problems
    Each role needs what the previous one learned, so every boundary becomes a place where context is lost and has to be re-explained. Anthropic describes teams whose role-based agents spent more tokens coordinating than executing.
    How to recognise it
    Briefs between the agents keep growing, or the receiving agent repeats work the previous one already did. Compare what each agent needs to read: if the lists overlap heavily, the split is in the wrong place.
    How to fix it
    Group work by the context it needs. Keep phases of the same work in one agent, and separate only pieces whose inputs really differ, such as a verifier that tests the finished output without the build history.

  2. Passing the whole conversation on every handoff, or passing nothing but a one-line brief.

    Why it causes problems
    Full history carries one domain's tool output into the next agent's context and is paid for again on every later call. A one-line brief leaves the receiver to guess, and Anthropic's research team saw subagents duplicate work, leave gaps or miss information when delegation was vague.
    How to recognise it
    In traces, a specialist's first call already holds thousands of tokens of another agent's tool results, or a sub-agent repeats searches that were already done and returns something the supervisor did not ask for.
    How to fix it
    Decide per boundary. On a handoff, filter tool traffic and make the sender state its findings in text. For delegation, write a brief with the objective, the output format, guidance on tools and sources, and clear task boundaries.

  3. Letting agents transfer or discuss with no limit on handoffs, rounds or spend.

    Why it causes problems
    Two agents can pass a request back and forth, and a group chat can restate the same points, until a budget runs out. The MAST failure taxonomy, built from more than 1,600 annotated traces, includes step repetition and agents being unaware of termination conditions among its failure modes.
    How to recognise it
    The same pair of agents alternates in a trace, or the last turns of a chat thread restate earlier ones. Runs end on a token or turn limit and not on an answer.
    How to fix it
    Cap handoffs per run and rounds per chat in code, give the chat manager an objective completion test, and return a distinct status when a cap ends the run. Define what happens next, such as escalation to a person.

  4. Passing a specialist's result onward without checking it.

    Why it causes problems
    The next agent treats the result as fact and builds on it. In the Google and MIT study, independent agents with no checking step amplified errors 17.2 times, against 4.4 times with an orchestrator. Task verification is one of MAST's three failure categories.
    How to recognise it
    Final answers contain claims that no agent tested, or a verifier reports success after running only part of the checks. Anthropic's guide describes verifiers marking output as passing without thorough testing.
    How to fix it
    Validate each agent's output before it is passed on: required fields, a test run, or a comparison with the request. Give a verifier explicit instructions, for example that the complete test suite must run before anything is marked as passed.

  5. Adding agents to raise quality without first measuring one agent on the same tasks.

    Why it causes problems
    Without a baseline there is no way to tell whether the extra agents help. They may add several times the cost for the same result, or make results worse on tasks one agent already handles well.
    How to recognise it
    Nobody can state the success rate and cost per task of a single agent with the same model and tools.
    How to fix it
    Build and evaluate the single agent first. Add an agent only to fix a failure you can point to in traces, then compare success rate and cost per solved task before and after.

Stop a handoff ping-pong and trim what the next agent sees

HEALTHY = {

    "network": ["TRANSFER billing", "TRANSFER billing", "TRANSFER billing"],
}


def scripted(scripts):
    replies = {name: iter(lines) for name, lines in scripts.items()}
    return lambda agent, history: next(replies[agent])   # stands in for an LLM call


def run(request, model, start="triage"):
    history, active, path = [("user", request)], start, [start]
    while True:
        reply = model(active, history)
        kind, _, rest = reply.partition(" ")
        if kind == "ANSWER":
            return {"status": "finished", "answer": rest, "path": path}
        if kind == "TOOL":
            history = history + [("tool_call", reply), ("tool_result", LEDGER)]
            continue
        history = history + [("assistant", f"{active} transfers the conversation to {rest}")]
        active, path = rest, path + [rest]

def words(history):
    return sum(len(text.split()) for _, text in history)


def drop_tool_items(history):
    return [(role, text) for role, text in history if role not in ("tool_call", "tool_result")]


def run(request, model, start="triage", max_handoffs=3, history_filter=None):
    history, active, path, sent = [("user", request)], start, [start], 0
    while True:
        sent += words(history)                    # every call re-reads the whole history
        reply = model(active, history)
        kind, _, rest = reply.partition(" ")
        if kind == "ANSWER":
            return {"status": "finished", "answer": rest, "path": path, "words_sent": sent}
        if kind == "TOOL":
            history = history + [("tool_call", reply), ("tool_result", LEDGER)]
            continue
        if len(path) - 1 >= max_handoffs:         # a transfer was requested and the budget is spent
            return {"status": "handoff_limit", "answer": None, "path": path, "words_sent": sent}
        history = history + [("assistant", f"{active} transfers the conversation to {rest}")]
        if history_filter:
            history = history_filter(history)
        active, path = rest, path + [rest]


for label, scripts in (("healthy", HEALTHY), ("ping-pong", PING_PONG)):
    for name, history_filter in (("full history", None), ("tools dropped", drop_tool_items)):

        print(f"{label:<10}{name:<14}{result['status']:<14}{' > '.join(result['path']):<38}{result['words_sent']:>5}")

    What it teaches
    The three situations in which Anthropic sees multiple agents outperform one (context protection, parallelisation and specialisation), why to split by context and not by role, and how to set up a verification subagent.
    When to use it
    Read it before proposing a multi-agent architecture, to test whether your reason for splitting is one of the three that hold up.

    When to use it
    Use it when a multi-agent system is already running and failing, as a checklist for reading traces and naming what went wrong.
