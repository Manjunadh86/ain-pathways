Amazon Bedrock AgentCore

Amazon Bedrock AgentCore is a set of AWS managed services for running AI agents in production. You bring an agent built with any framework and any model, and AgentCore supplies what surrounds it: a hosting runtime, memory, a tool gateway, identity, observability, and sandboxed browser and code-execution tools.

1Overview

Why it matters

An agent that works on a laptop is one Python process. Its conversation history is a list in memory, its API keys sit in environment variables, and its only user is you. Put the same code in front of a thousand customers and new questions appear. Which process serves which user? What happens to a half-finished task when the server restarts? Whose Google Drive token does the agent hold? How do you find out why it called the refund tool twice? None of these are answered by the agent framework.

Teams answer them either by assembling general-purpose compute, databases, secret stores and tracing themselves, or by adopting a managed platform. AgentCore is the AWS platform for this job. Engineers who deploy LangGraph, Strands, CrewAI or ADK agents on AWS need to know which service covers which concern, what the runtime expects from their code, and what still remains their responsibility. Misreading the model has concrete costs: conversations that forget everything after fifteen idle minutes, sessions that never shut down and exhaust a quota, or a container that is rejected because it was built for the wrong CPU.

Key terms

AgentCore Runtime
The serverless hosting service that runs your agent code, packaged as a zip of code or an ARM64 container, and gives every session its own isolated compute.
Session
One conversation or task, identified by a runtimeSessionId that your application chooses and sends again with every related request.
microVM
A lightweight virtual machine with its own CPU, memory and filesystem. Runtime starts one per session and destroys it when that session's compute stops.
Service contract
The interface Runtime expects your code to expose. For the HTTP protocol it is POST /invocations and GET /ping on port 8080.
Entrypoint
The function you mark with the SDK's entrypoint decorator. It receives the payload of each invocation and returns the agent's reply.
Runtime endpoint
A named, stable address that points at one version of an agent runtime. The endpoint called DEFAULT always points at the newest version.
Short-term memory
Raw conversation events stored per actor and session in AgentCore Memory, so a conversation can be reloaded exactly as it happened.
Long-term memory
Facts, preferences or summaries that AgentCore Memory extracts from events in the background and returns by semantic search in later sessions.
Gateway target
A backend attached to an AgentCore Gateway, such as a Lambda function, an OpenAPI specification or an existing MCP server.
Workload identity
The identity AgentCore Identity assigns to an agent. The agent presents it to prove which workload is asking when it fetches credentials from the token vault.

2Explanation

Introduction

Agent Deployment Architecture listed what a production agent needs around its loop: compute to run on, a place to keep state, a way to reach tools, credentials, and traces. On your laptop all of these are invisible. The compute is your terminal, the state is a Python list, the credentials are environment variables, and the trace is whatever you printed.

Amazon Bedrock AgentCore is AWS's packaged answer to those needs. It is a group of separate services, and the AgentCore overview (opens in a new tab) says they can be used together or independently, with open-source frameworks such as CrewAI, LangGraph, LlamaIndex and Strands Agents and with any foundation model. AgentCore is therefore not an agent framework. The framework still decides what the agent does next. AgentCore decides where that code runs, who may call it and what it can reach.

A useful picture is a food stall moving into a rented commercial kitchen. The cooks and the recipes stay the same. The kitchen supplies the stoves, the cold storage, the keys to the storeroom and the inspection log. Each core service answers one question:

ServiceQuestion it answers
RuntimeWhere does the agent run, and how are users kept apart?
MemoryWhat does the agent still know after its process is gone?
GatewayHow does the agent reach many APIs and tools through one endpoint?
IdentityWho is calling the agent, and whose credentials does it act with?
ObservabilityWhat did the agent do, step by step?
Browser and Code InterpreterWhere can the agent browse the web and run code safely?

The overview page also lists newer members of the family: a managed agent loop called Harness, Policy, Evaluations, Optimization, a Registry and Payments. This lesson concentrates on the six rows above and on the path a framework-built agent takes to get onto them. It treats Gateway in its MCP tool role, although the current Gateway documentation also describes HTTP targets that proxy traffic to other agents and inference targets that route model requests. The service names, limits and prices quoted here were read from the AWS pages in October 2026. The platform changes often, so confirm the numbers before you rely on them.

How it works

Runtime: one microVM per session

Runtime hosts your agent code. Its defining property is isolation by session. Your application invents a runtimeSessionId of at least 33 characters for each conversation and sends it with every related request. (Without an ID, Runtime generates one and the client must reuse it.) The first request with a new ID makes Runtime start a dedicated microVM with its own CPU, memory and filesystem. Later requests with the same ID are routed to that same microVM, so Python variables and files from the previous turn are still there. A different ID gets a different microVM, which is how one user's half-finished reasoning and credentials stay out of another user's session.

The session documentation (opens in a new tab) lists four things that stop a session's compute: inactivity (15 minutes by default), the maximum lifetime (8 hours by default on microVMs), an explicit StopRuntimeSession call, and failed health checks. When that happens the microVM is terminated and its memory is sanitized. The session ID stays valid, but the next request starts a fresh microVM that remembers nothing. Both timers are settings, idleRuntimeSessionTimeout and maxLifetime, each between 60 and 28,800 seconds on microVMs, and the idle timeout may not exceed the lifetime. The idle timer restarts on every invocation. The lifetime timer starts when the microVM is created and cannot be reset.

Two more objects matter for releases. Every configuration change creates an immutable version, and an endpoint is an address that points at one version. The endpoint named DEFAULT follows the newest version automatically, and you can create others (for example prod) and repoint them to roll forward or back.

The contract your code must meet

Runtime treats your code as a web server that speaks one of four protocols.

ProtocolPortPathTypical use
HTTP8080/invocations, optional /wsDirect calls and streaming
MCP8000/mcpHosting a tool server (see MCP)
A2A9000/Agent-to-agent calls (see A2A)
AG-UI8080/invocations, /wsInteractive front ends (see AG-UI)

Most agents use HTTP. The HTTP contract (opens in a new tab) asks for a server on host 0.0.0.0, port 8080, built for ARM64, with two routes:

  • POST /invocations takes a JSON body such as {"prompt": "..."} and returns JSON, or a server-sent event stream for incremental output.
  • GET /ping returns {"status": "Healthy"}. Returning {"status": "HealthyBusy"} tells Runtime that background work is still running, which keeps the session alive past the idle timeout.

Putting a framework-built agent on Runtime

  1. Keep the agent as it is. A compiled LangGraph graph, a Strands Agent, an ADK runner or an OpenAI Agents SDK runner needs no rewrite. The framework examples (opens in a new tab) show all four.
  2. Add the contract adapter. The bedrock-agentcore Python SDK serves both routes for you. You mark one function as the entrypoint. The fragment below adapts the documentation's LangGraph example, with the prompt check taken from its Strands example, and was not executed for this lesson. my_agent.graph stands for your own module.
python
from bedrock_agentcore.runtime import BedrockAgentCoreApp
from my_agent.graph import graph  # your compiled graph

app = BedrockAgentCoreApp()

@app.entrypoint
def invoke(payload, context):
    prompt = payload.get("prompt", "")
    if not isinstance(prompt, str) or not prompt.strip():
        return {"error": "'prompt' must be a non-empty string"}
    state = graph.invoke({"messages": [{"role": "user", "content": prompt}]})
    return {"result": state["messages"][-1].content}

if __name__ == "__main__":
    app.run()
  1. Package it. The AgentCore CLI (npm install -g @aws/agentcore, Node.js 20 or later) scaffolds a project with agentcore create. Its default build type, CodeZip, uploads a zip of your code to Amazon S3 and needs no Docker. The Container build type produces an image instead.
  2. Deploy it. agentcore deploy uses the AWS CDK to create the agent runtime, its endpoint and CloudWatch logging. Without the CLI you push an ARM64 image to Amazon ECR and call create_agent_runtime with the image URI, an IAM role and a network mode, as the custom agent tutorial (opens in a new tab) does.
  3. Invoke it. agentcore invoke --prompt "..." from the CLI, or the InvokeAgentRuntime API with the runtime ARN, a session ID, the payload and the endpoint name as qualifier.

Your graph, prompts and tool functions survive the move. What changes is where state lives, how tools are reached and how credentials arrive.

Memory: state that outlives the microVM

AgentCore Memory (opens in a new tab) has two layers. Short-term memory stores raw events, usually conversation turns, under an actor ID and a session ID. An agent that wakes up in a new microVM can list those events and continue the conversation. Long-term memory exists only if you attach a strategy, such as semantic facts or summaries, to the memory resource. Extraction and consolidation then run asynchronously in the background, and the agent later fetches the resulting records by semantic search. Agent Memory covers the concepts; here the point is that Memory is a network service your code calls, and it is not the microVM's RAM.

Gateway: one MCP endpoint for many tools

Gateway (opens in a new tab) turns existing backends into MCP tools. You attach targets (Lambda functions, OpenAPI or Smithy definitions, existing MCP servers) and the gateway presents them as one virtual MCP server at a URL ending in /mcp. The agent connects with any MCP client and sees a single tools/list. Tool names carry the target as a prefix, as in the documentation's LambdaTarget___get_order_tool. Two details make this more than a proxy. The gateway injects the outbound credentials for each target, so API keys need not appear in the agent's code or prompt. With semantic search enabled it also exposes a tool named x_amz_bedrock_agentcore_search, which lets the agent find a few relevant tools by description instead of loading hundreds of definitions into every prompt.

Identity: two directions of trust

Inbound auth decides who may invoke the agent. A runtime accepts either AWS IAM signatures (the default) or JWT bearer tokens from an OpenID Connect provider such as Amazon Cognito, Okta or Microsoft Entra ID. It cannot accept both. Outbound auth decides what the agent can use. Each runtime receives a workload identity. A token vault stores OAuth tokens and API keys encrypted with AWS KMS keys, and agent code asks for them with decorators such as @requires_access_token, naming a credential provider, scopes and a flow. The flow is either the user's own consent (authorization code grant) or the agent's own credentials (client credentials grant). See Agent Identity, Permissions and Least Privilege for why the two must be kept apart.

Observability: OpenTelemetry into CloudWatch

AgentCore emits built-in metrics for runtime, memory, gateway, tool and identity resources into Amazon CloudWatch. Step-by-step traces need three things, described in the setup guide (opens in a new tab): CloudWatch Transaction Search enabled once per account, the aws-opentelemetry-distro package (0.18.0 or later) in your dependencies, and the opentelemetry-instrument command starting your agent. Because the format is OpenTelemetry, the spans can go to another backend instead. Setting DISABLE_ADOT_OBSERVABILITY=true removes the default exporter configuration so that you can supply your own. The concepts are in LLM and Agent Observability.

Built-in tools: a browser and a code sandbox

Code Interpreter (opens in a new tab) runs Python, JavaScript or TypeScript in an isolated sandbox with sessions of its own. Browser (opens in a new tab) provides managed Chrome sessions that an automation library drives over a WebSocket, with a live view for a human observer. Both default to 15-minute sessions and allow up to 8 hours. Code Execution and Sandboxing explains why model-written code must not run inside the agent's own process.

What you pay for

Runtime bills per second for the CPU and memory your session actually consumes. According to the pricing page (opens in a new tab), CPU scales to zero while the agent waits on I/O, and V2 also reclaims released memory. Rates depend on the platform version: V1 is the default, and V2 starts each microVM from a snapshot of your initialised agent. On 11 October 2026 the page listed $0.0895 per vCPU-hour and $0.00945 per GB-hour for V1, and $0.1276 and $0.0169 for V2 consumption pricing. Gateway cost $0.005 per 1,000 API invocations (ListTools, InvokeTool and Ping count) and $0.025 per 1,000 search calls, and Identity had no extra charge when used through Runtime or Gateway. Model usage is billed separately.

Worked example: Serving the Runtime HTTP contract locally, following one session and pricing it

You do not need an AWS account to understand what Runtime asks of your code. This example builds the HTTP contract with the Python standard library, calls it the way Runtime would, and then prices the session with published rates.

Step 1: a contract-compliant agent

Save this as contract_agent.py (Python 3.9 or later, no packages). run_agent stands in for your framework call so that everyone gets the same output.

python
import json
from http.server import BaseHTTPRequestHandler, ThreadingHTTPServer

SESSION_HEADER = "X-Amzn-Bedrock-AgentCore-Runtime-Session-Id"
ORDERS = {"A-1001": "shipped", "A-1002": "processing"}
HISTORY = {}  # session id -> earlier prompts; lives only as long as this process


def run_agent(prompt, history):
    """Stand-in for graph.invoke(...) or agent(prompt) from your framework."""
    words = [word.strip("?.,!") for word in prompt.split()]
    order_id = next((word for word in words if word in ORDERS), None)
    if order_id:
        return f"Order {order_id} is {ORDERS[order_id]}."
    if "previous" in prompt.lower() and history:
        return f"Your previous question was: {history[-1]}"
    return "I can look up orders A-1001 and A-1002."


class ContractHandler(BaseHTTPRequestHandler):
    def reply(self, status, body):
        data = json.dumps(body).encode()
        self.send_response(status)
        self.send_header("Content-Type", "application/json")
        self.send_header("Content-Length", str(len(data)))
        self.end_headers()
        self.wfile.write(data)

    def do_GET(self):  # health check
        if self.path == "/ping":
            return self.reply(200, {"status": "Healthy"})
        return self.reply(404, {"error": "not found"})

    def do_POST(self):  # agent invocation
        if self.path != "/invocations":
            return self.reply(404, {"error": "not found"})
        try:
            length = int(self.headers.get("Content-Length", 0))
            payload = json.loads(self.rfile.read(length))
        except ValueError:
            return self.reply(400, {"error": "body must be JSON"})
        prompt = payload.get("prompt") if isinstance(payload, dict) else None
        if not isinstance(prompt, str) or not prompt.strip():
            return self.reply(400, {"error": "'prompt' must be a non-empty string"})
        session_id = self.headers.get(SESSION_HEADER, "local-session")
        history = HISTORY.get(session_id, [])
        answer = run_agent(prompt, history)
        HISTORY[session_id] = [*history, prompt]
        return self.reply(200, {"result": answer, "turn": len(history) + 1})

    def log_message(self, *args):  # keep the terminal quiet
        pass


if __name__ == "__main__":
    ThreadingHTTPServer(("0.0.0.0", 8080), ContractHandler).serve_forever()
Step 2: call it as Runtime would

Start it with python3 contract_agent.py and run these in a second terminal. The session ID is the 33-character example from the AWS documentation.

bash
S1='X-Amzn-Bedrock-AgentCore-Runtime-Session-Id: user-123456-conversation-12345678'
S2='X-Amzn-Bedrock-AgentCore-Runtime-Session-Id: user-999999-conversation-00000001'
J='Content-Type: application/json'
curl -s localhost:8080/ping; echo
curl -s -X POST localhost:8080/invocations -H "$J" -H "$S1" -d '{"prompt": "Where is order A-1001?"}'; echo
curl -s -X POST localhost:8080/invocations -H "$J" -H "$S1" -d '{"prompt": "What was my previous question?"}'; echo
curl -s -X POST localhost:8080/invocations -H "$J" -H "$S2" -d '{"prompt": "What was my previous question?"}'; echo
text
{"status": "Healthy"}
{"result": "Order A-1001 is shipped.", "turn": 1}
{"result": "Your previous question was: Where is order A-1001?", "turn": 2}
{"result": "I can look up orders A-1001 and A-1002.", "turn": 1}

Now stop the server with Ctrl+C, start it again and repeat the third command with $S1. It prints {"result": "I can look up orders A-1001 and A-1002.", "turn": 1}. The history is gone.

Step 3: what this shows about Runtime
  • Session S1 kept its history between calls and session S2 could not see it. Locally one process serves everyone, so the code keys its state by session ID. On Runtime each session ID gets its own microVM, which makes the separation a property of the platform.
  • The restart is what the end of a session's compute looks like to your code. After 15 idle minutes the microVM is destroyed, and the next request with the same ID lands in a new one with empty variables. Anything that must survive belongs in AgentCore Memory or your own database.
Step 4: price the session

The pricing page gives an example session for a support agent on V2 consumption rates: 10 minutes long, 1 vCPU, CPU active for 60 seconds (the rest is waiting), and memory of 1 GB for 300 s, 2 GB for 150 s and 2.5 GB for 150 s.

One million such sessions cost about $6,703. If CPU were billed for all 600 seconds, the CPU line alone would be 600 × $0.1276 / 3600 = $0.021267 and the session would cost about $0.0258, roughly 3.9 times as much. Agents spend most of their time waiting for models and tools, so billing only active CPU matters.

Edge cases and limitations

The same session ID can meet a different microVM
A session ID stays valid after its compute stops, but the next request provisions a new microVM with empty memory and, unless session storage is configured, an empty disk. Code that assumes a session ID implies warm state fails silently after a long pause. Treat in-process state as a cache and reload what you need from AgentCore Memory or your own store at the start of each invocation.
A blocked entrypoint looks like a dead session
Runtime reads the /ping route to learn whether a session is idle, busy or unhealthy. The documentation for long-running agents warns that a single-threaded server whose entrypoint blocks also blocks /ping, and lists agents terminated after 15 minutes as the symptom. Run long work in a separate thread or as async code and report HealthyBusy while it runs.
A ping timestamp that always moves keeps sessions alive
The optional time_of_last_update field must change only when the status really changes. The HTTP contract page warns that setting it to the current time on every ping prevents the idle timeout from ever firing, so sessions last until the maximum lifetime and can exhaust the session quota. Omit the field, or let the SDK answer /ping for you.
Session operations can collide for a moment
While Runtime is provisioning or tearing down a session, a second operation on that session returns HTTP 409 with RetryableConflictException. The AWS SDKs retry it automatically when default retries are on. A client that calls the HTTPS API directly, which JWT-protected agents require, must retry with a short exponential backoff itself.
Long-term memories arrive late, or not at all
Long-term memory generation runs asynchronously after events are stored, so a fact the user stated a moment ago may not be retrievable yet by semantic search. A memory resource created without any strategy never produces long-term records. Read the recent turns from short-term memory for the current conversation and use long-term records only for knowledge from earlier sessions.
A running session keeps the code it started with
Each microVM uses the artifact that was deployed when it was created. After you update the runtime, existing sessions continue on the previous version until they end, which can take up to the maximum lifetime. Expect two versions to answer requests during a rollout, and stop sessions explicitly when a fix must take effect at once.

When to use it, and when something simpler is enough

Use it when

  • Each user or task needs its own isolated execution environment, for example because the agent writes files, holds per-user credentials or runs model-generated commands during a session.
  • Sessions are long or bursty: minutes of waiting on models and tools, background tasks of up to 8 hours, or traffic that drops to zero overnight, where paying only for active CPU matters.
  • The agent must act for individual users in third-party systems, so you need token exchange, consent flows and a credential vault and would otherwise have to build and audit them yourself.
  • Your organisation already runs on AWS, and IAM, VPC networking and CloudWatch are the controls your security and operations teams expect to use.
  • You want to keep an existing LangGraph, Strands, CrewAI or ADK code base and change only how it is hosted.

Think twice when

  • The work is a short, stateless request with no tools that need isolation. A plain function or container service is simpler, and per-session microVMs add nothing.
  • You must run outside AWS or need a deployment that is portable across clouds. The services, identity model and command-line tooling are specific to AWS.
  • One session must run for longer than 8 hours without interruption on serverless compute. That needs the Instances compute type (up to 14 days), which runs your agent on AWS-managed Amazon EC2 infrastructure in your own account, or a durable workflow engine.
  • The team cannot yet say what state must survive a restart. Moving to any session-based platform before answering that question produces agents that forget mid-task.

A simpler alternative. Run the same contract server (your framework behind one HTTP route) in a single container on a service you already operate, keep conversation state in a database you already have, and read secrets from a secret manager. This is enough for an internal tool with a handful of trusted users. It stops being enough when different users must not share a process, when the agent needs per-user OAuth tokens for outside systems, or when sessions must stay warm for hours without you paying for idle servers.

Key takeaways

  • AgentCore is a set of separate managed services (Runtime, Memory, Gateway, Identity, Observability, Browser and Code Interpreter) that surround an agent you build with any framework and any model.
  • Runtime gives every session ID its own microVM and destroys it after the idle timeout or the maximum lifetime, so anything that must survive has to live in Memory or another store.
  • A framework-built agent is deployed by adding a thin adapter that serves POST /invocations and GET /ping on port 8080, packaging it as a code zip or an ARM64 container, and creating a runtime with an endpoint.
  • Gateway presents many backends as one MCP server and Identity separates who may call the agent from whose credentials the agent uses, which keeps secrets out of prompts and agent code.
  • Telemetry is emitted in OpenTelemetry format, so traces can stay in CloudWatch or be exported to another backend, and Runtime cost follows the CPU and memory a session actually consumes, not wall-clock time alone.

Example 1 of 5

Iberdrola hosting LangGraph agents for ServiceNow change and incident work

IberdrolaDocumented in an engineering article

Iberdrola, a large utility company, and AWS describe agents that work on ServiceNow change requests and incident tickets. The account is an AWS Machine Learning Blog post from February 2026 with three Iberdrola authors. AWS's Gateway, container deployment and Runtime authentication pages document the mechanisms it names. [25][8][15][16][12]

The problem

Iberdrola's IT operations run through ServiceNow, where the post says thousands of change requests and incident tickets are managed. It names three jobs for agents: validating change requests while they are still drafts, enriching incident tickets with context such as tags, similar incidents and related changes, and helping staff choose the right change model through a conversation. The agents were written with LangGraph. The post presents AgentCore as the way to run them as production-ready services: it says Runtime scales with request volume while providing session isolation, and it describes the platform as combining serverless compute, security and integrated observability. It also stresses consistent interfaces through which every agent reaches tools such as the ServiceNow endpoints, instead of custom integration code for each data source.

Where this topic fits

The LangGraph agents are packaged as containers, pushed to Amazon ECR and hosted on AgentCore Runtime, which the post says runs inside a VPC. In front of them sits Iberdrola's own MicroGateway, which receives REST calls from ServiceNow and routes each one to the right agent. The post says AgentCore Gateway acts as an MCP server that turns external tools and services into MCP tools, and calls this particularly valuable for Iberdrola's ServiceNow endpoint connections. Identity manages inbound and outbound authentication and integrates with Entra ID through OAuth 2.0, Memory keeps state per agent session, and Observability sends OpenTelemetry data to CloudWatch, with a self-hosted Langfuse alongside. The post does not say where in the request path the Identity check happens.

How it is applied, step by step

  1. A user action in ServiceNow triggers a REST call to Iberdrola's MicroGateway, which routes the request to the agent that owns that use case.
  2. AgentCore Identity validates bearer tokens on inbound requests and authorises access to underlying resources. The post says it integrates with Entra ID through OAuth 2.0 but does not give the order of the MicroGateway and Identity hops, so our data flow below draws the check at the Runtime's inbound edge, where the AWS documentation places Runtime inbound auth.
  3. Runtime starts the LangGraph agent from its container image in an isolated session. For change validation, the post says four agents run in sequence inside one Runtime instance and pass context from one to the next.
  4. When an agent needs ServiceNow data, a typical implementation has it call AgentCore Gateway as an MCP server, so no agent carries its own hand-written ServiceNow client. The post names Gateway as particularly valuable for these connections but does not show the calls.
  5. Session state, conversation history and intermediate results are kept in AgentCore Memory as memory objects per agent session during multi-step workflows.
  6. Model calls go through a LiteLLM proxy to Amazon Nova and Anthropic Claude models on Amazon Bedrock. This part is Iberdrola's design choice and is not an AgentCore service.
  7. Telemetry is captured in OpenTelemetry format and inspected in CloudWatch and in Langfuse.

Why this approach fits

The team already had agents written as LangGraph graphs. Runtime accepts a container whatever framework is inside, so the graphs could move to managed hosting as images and not as a rewrite. Three use cases share one backend system, which is the situation Gateway is built for: the ServiceNow integration can be defined once as MCP tools and every agent can consume it the same way. Change and incident records are sensitive operational data, so identity checks and private networking belong in the hosting layer and not in each agent.

Limitation or tradeoff

The post reports no measured results: no resolution times, accuracy figures or cost numbers, only qualitative claims such as productivity gains and better data quality. It is evidence of an architecture, not of a benefit. Iberdrola also still operates several components of its own, including the MicroGateway, the LiteLLM proxy, a Langfuse deployment and the data pipeline that feeds a vector-enabled PostgreSQL database. The roadmap in the post lists an agent catalog, newer protocols such as A2A, and managed orchestration with real-time flow monitoring as future work, which suggests these were gaps when it was written.

What the sources document

  • The post says AgentCore Runtime accepts containerised agents built with any framework, in Iberdrola's case LangGraph, deployed through Amazon ECR repositories. AWS's tutorial for deploying without the CLI likewise requires a linux/arm64 image pushed to Amazon ECR. [25][8]
  • Users start requests in ServiceNow, which communicates through a REST API with a MicroGateway that routes requests to the appropriate use case agents. The change validation workflow runs four agents in sequence within a single AgentCore Runtime instance. [25]
  • The post describes AgentCore Gateway as acting as an MCP server that "MCPifies" external tools and services through standardised interfaces, which it calls particularly valuable for Iberdrola's ServiceNow endpoint connections. AWS documents that a gateway converts APIs, Lambda functions and existing services into MCP-compatible tools and, for MCP targets, combines all of its targets into one unified virtual MCP server. [25][15][16]
  • AgentCore Identity manages both inbound and outbound authentication flows, integrates with Entra ID through OAuth 2.0 protocols, and for inbound requests validates bearer tokens and authorises access. AWS documents that a runtime can be configured to validate JWT bearer tokens against an OpenID Connect discovery URL, using AgentCore Identity. [25][12]
  • AgentCore Memory keeps memory objects per agent session, holding session state, conversation history and intermediate results. AgentCore Observability captures OpenTelemetry data and surfaces it through Amazon CloudWatch, and Iberdrola additionally runs a self-hosted Langfuse on Amazon EKS. [25]

Where this topic fits

Observability on AgentCore is OpenTelemetry-shaped, so the integration happens at the exporter. The agent and its framework stay as they are. Three environment variables on the runtime change where the spans go: one switches off the default ADOT configuration, and two point the OTLP exporter at Langfuse with credentials.

  1. Build the Basic-auth value by base64-encoding the Langfuse public key and secret key joined by a colon.

Limitation or tradeoff

With ADOT disabled, the runtime's default export to CloudWatch is switched off. The two guides read for this lesson do not show how to send the same spans to both places, so plan for one primary destination or configure a second exporter yourself. The Langfuse keys travel as an environment variable, and base64 is an encoding and not encryption, so treat that header as a secret. The AWS post says the traces include request and response payloads, so with Langfuse Cloud prompts and model outputs leave your AWS account. Teams with strict data rules can self-host Langfuse inside their own network, as Iberdrola does in the first example.

4Common mistakes

  1. Keeping conversation history only in module-level variables of the deployed agent.

    Why it causes problems
    A session's microVM is destroyed after the idle timeout, 15 minutes by default, or at the maximum lifetime, and its memory is sanitized. The next request with the same session ID starts with empty variables, so the agent forgets a task halfway through and raises no error.
    How to recognise it
    Users say the agent started over after a break. A turn counter or cached plan resets to its initial value. The problem never shows up in quick local tests, because your local process stays alive.
    How to fix it
    Treat in-process state as a cache. Write each turn to AgentCore Memory or your own store, and reload what the agent needs at the start of every invocation.

  2. Sending one fixed session ID for every user, or a new random ID on every request.

    Why it causes problems
    A shared ID routes different users to the same microVM, where they share process state, files and any cached credentials. AgentCore does not enforce a mapping between users and sessions. A new ID on every request throws away warm state and may pay a cold start each time.
    How to recognise it
    One user's context appears in another user's answer, or the number of sessions in your metrics equals the number of requests and every reply is slow.
    How to fix it
    Have your backend create one ID of at least 33 characters per user conversation, store the mapping, reuse the ID for follow-up requests and cap the number of open sessions per user.

  3. Building the container for x86-64, or binding the server to localhost or another port.

    Why it causes problems
    Runtime requires an ARM64 image whose server listens on host 0.0.0.0 and port 8080 with both contract routes. An image that breaks any of these cannot be started or reached, even though it runs perfectly on the laptop that built it.
    How to recognise it
    The container answers curl locally, but the deployed runtime never becomes healthy or invocations fail. Inspecting the image shows the amd64 architecture, or the server log shows it bound to 127.0.0.1.
    How to fix it
    Build with docker buildx and the linux/arm64 platform, bind to 0.0.0.0:8080, and test /ping and /invocations with curl before pushing. The CodeZip build type avoids the image step entirely.

  4. Expecting step-by-step traces without enabling Transaction Search or instrumenting the agent.

    Why it causes problems
    Only the built-in service metrics appear. When a run goes wrong you can see that latency or errors rose, but not which model call or tool call caused it, so debugging falls back to reading raw logs.
    How to recognise it
    The CloudWatch dashboard shows invocation counts for the agent while the trace view is empty, or spans stop at the invocation and contain no model or tool steps.
    How to fix it
    Enable CloudWatch Transaction Search once per account, add aws-opentelemetry-distro to the dependencies, start the agent with opentelemetry-instrument, and make sure the framework emits OpenTelemetry spans.

  5. Putting third-party API keys or user tokens in environment variables or in the prompt.

    Why it causes problems
    Every session of the runtime then shares one secret, the agent acts with a single identity for all users, and the secret can leak through logs, traces or model output. Downstream systems cannot apply per-user permissions.
    How to recognise it
    Audit logs in the downstream system show one service user for every action. Searching the deployment configuration or the traces finds key material.
    How to fix it
    Register a credential provider in AgentCore Identity and fetch tokens at tool-call time, or put the tool behind a Gateway target so that the gateway injects the credential and the agent never holds it.

  6. Listing every Gateway tool in every prompt as the tool catalogue grows.

    Why it causes problems
    Tool definitions consume context on each model call, which raises cost and latency, and a long list of similar tools makes the model more likely to choose the wrong one.
    How to recognise it
    Input token counts per call grow whenever a new target is attached to the gateway, even for requests that use a single tool.
    How to fix it
    Enable semantic search when the gateway is created and let the agent call the built-in search tool to fetch the few relevant tools for the task, then call only those.

Simulate when a Runtime session gets a new microVM

CodingIntermediateAbout 40 min (estimate)Hypothetical scenario

You are reviewing an agent before it moves to AgentCore Runtime and want to know which requests will find warm state and which will land in a fresh microVM. Write a small simulator in plain Python. No AWS account is needed.

Model these documented rules:

  • The first invocation of a session provisions microVM number 1.
  • The idle timer restarts on every invocation. If the gap since the previous invocation is greater than or equal to idle_timeout, the old microVM is gone and a new one is provisioned.
  • The lifetime timer starts when a microVM is created and is never reset. If the time since creation is greater than or equal to max_lifetime, a new microVM is provisioned.
  • A new microVM has empty in-process state.

Simplifications: treat every invocation as instantaneous and ignore background tasks.

Write simulate(invocation_times, idle_timeout=900, max_lifetime=28800). It takes invocation times in seconds for one session ID and returns one tuple per invocation: (time, microvm_number, cold). Run it on three traces:

  • It must apply both the idle rule and the lifetime rule, and mark an invocation cold when either fires.

def simulate(invocation_times, idle_timeout=900, max_lifetime=28800):
    """Return one row per invocation: (time, microvm_number, cold)."""
    rows = []
    vm_number = 0
    vm_created = None
    last_activity = None
    for now in invocation_times:
        idle_expired = last_activity is not None and now - last_activity >= idle_timeout
        life_expired = vm_created is not None and now - vm_created >= max_lifetime
        cold = vm_created is None or idle_expired or life_expired
        if cold:
            vm_number += 1
            vm_created = now
        last_activity = now
        rows.append((now, vm_number, cold))
    return rows


def report(title, rows):
    print(title)
    for now, vm_number, cold in rows:
        state = "COLD: in-process state is empty" if cold else "warm"
        print(f"  t={now:>5}s  microVM #{vm_number}  {state}")
    print(f"  microVMs provisioned: {rows[-1][1]}")


if __name__ == "__main__":
    report("A. chat with a long pause (idle 900s, max 28800s)",
           simulate([0, 300, 1100, 2100, 2500]))
    report("B. steady polling, short max lifetime (idle 900s, max 1800s)",
           simulate([0, 600, 1200, 1800, 2400], max_lifetime=1800))
    report("C. development settings (idle 300s, max 1800s)",
           simulate([0, 200, 600, 700], idle_timeout=300, max_lifetime=1800))

The estimate leaves out model tokens, which can be a large item, as well as Gateway ListTools and Ping calls (billed like other API invocations), Code Interpreter sessions, Memory storage and retrieval, and CloudWatch or Langfuse costs. Notice that memory is 61% of the Runtime cost here ($0.00169 of $0.00275). When the CPU is idle most of the time, reducing the memory footprint saves more than speeding up the code.

  • Does your plan say what happens to in-process state when an adjuster returns after lunch?
  • Is your Runtime figure within a few cents of 137.67 US dollars per month?
  • Did you list at least one cost that the estimate does not include?
