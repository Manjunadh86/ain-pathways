A2UI (Agent-to-User Interface)

A2UI (Agent to UI) is an open protocol for agent-driven interfaces. An agent streams JSON that describes a screen as a flat list of components from a catalog the client already trusts, plus a separate data model, and the client draws it with its own native widgets without running any code from the agent.

1Overview

Why it matters

An agent that can only answer in text turns every form into an interview. Booking, approvals, comparisons and settings are things people want to see and click, and one form replaces several rounds of questions. The harder problem is trust. Agents often run on a server owned by another team or vendor, and letting such an agent send HTML and JavaScript into your page lets that party run code inside your app. A2UI settles this by sending data that your app interprets with components you chose.

Three groups need the details. Front-end engineers write the catalog and the renderer, which is where the security boundary sits. Agent engineers must get valid output from a model that the schema does not constrain, and decide what happens when it fails. Teams that plug agents into a platform such as Gemini Enterprise need to know what the host will and will not render. The protocol is still moving: as of October 2026 the A2UI project lists v0.9.1 as the current release and v1.0 as a candidate, so the concepts here matter more than any single field name.

Key terms

Surface
A region of UI that the agent creates and later updates or deletes, identified by a surfaceId. One conversation can hold several surfaces.
Component
One element of a surface, written as an object with a unique id, a type name such as Text or Button taken from the catalog, and properties for that type.
Adjacency list
A flat list of components in which containers refer to their children by id instead of nesting them, so any component can be sent or replaced on its own.
Catalog
A JSON Schema file naming the components, functions and theme properties an agent may use. It is the contract between the agent and the client.
catalogId
An opaque string, usually shaped like a URL, that names a catalog. Both sides must already know the catalog, because the identifier is not downloaded at runtime.
Data model
The JSON state of one surface, kept separate from the component list. Components read it through paths and the agent changes it with updateDataModel.
Data binding
Pointing a component property at a path such as /order/note instead of a literal value, so that changing the data changes the screen without resending the components.
Action
What happens when the user triggers a component such as a button. It is either an event sent to the agent or a function the client runs locally.
Renderer
The client library that turns A2UI messages into real widgets of one framework, for example Lit, Angular, React or Flutter.
Prompt-first
The approach introduced in v0.9 in which the schema and examples go into the model's prompt and the output is validated afterwards, instead of relying on a provider's structured-output feature.

2Explanation

Introduction

In AG-UI you saw how an agent backend and a user-facing app exchange a stream of events: text, tool calls and shared state. That protocol carries things between the two. It does not say what a rich answer should look like on screen. Until now the usual answer has been plain text, or a hand-built screen that a developer wrote for each tool.

Take an agent that books tables. In text it asks "for what day?", then "what time?", then "for how many?". A date picker and a time selector would settle all three in one step, and the A2UI project (opens in a new tab) uses exactly this booking scenario to explain why it exists. But a form raises two questions: who draws it, and what if the agent runs on a server you do not control? Sending HTML and JavaScript to run in your page hands that server control of your page. The A2UI documentation lists heavy, visually disjointed output and security complexity as the costs of the iframe approach.

A2UI makes a different bargain: the agent sends data, never code. Think of an instruction sheet that may only mention building bricks you already own. The agent says "a column holding a heading, a list of rows and a button", using names from a catalog your app agreed to, and your app builds the screen from its own widgets, in its own theme, on whatever platform it runs. The pieces are a surface (the region being drawn), a flat list of components, and a separate data model holding the values they show.

The diagram shows the whole life of a surface: three messages build it, the user fills it in locally, one button click sends an action back, and the agent patches or removes the surface. This lesson explains each message, the catalog that makes the approach safe, how the output is generated and validated, how it travels over A2A, AG-UI and MCP, and where it sits next to MCP Apps. You will also run a small client yourself.

How it works

Six messages

Server-to-client messages are JSON objects with a version field and exactly one envelope key, delivered as a stream (commonly JSON Lines, one object per line). The v0.9.1 specification (opens in a new tab) defines these:

MessageDirectionWhat it does
createSurfaceagent to clientStarts a surface with a surfaceId and a catalogId; optional theme and sendDataModel.
updateComponentsagent to clientAdds or replaces components. One component must have the id root.
updateDataModelagent to clientSets the value at a JSON Pointer path; leaving out value removes that key.
deleteSurfaceagent to clientRemoves the surface and its content.
actionclient to agentSent when the user triggers an event action; carries name, surfaceId, sourceComponentId, timestamp, context.
errorclient to agentReports a client-side problem, for example VALIDATION_FAILED.

Components are a flat list

Each component has a unique id, a component type from the catalog, and type-specific properties. Containers list child ids; they never nest them:

json
{"id": "root", "component": "Column", "children": ["title", "lines"]},
{"id": "title", "component": "Text", "text": "Review your order"}

The A2UI documentation gives three reasons for the flat shape: it is easy for a model to generate, components can be streamed one at a time, and any component can be updated by id without rebuilding its parent.

Data model and binding

State lives apart from structure, per surface. A property can hold a literal ("text": "Welcome"), a path ("text": {"path": "/user/name"}) or a function call. Paths are JSON Pointers (RFC 6901). A List or Column can take a template, {"componentId": "line", "path": "/order/lines"}: the client makes one copy of the template per array item, and inside each copy a path without a leading slash is relative to that item, so name means /order/lines/0/name for the first row. Absolute paths still reach the root.

Input components such as TextField are bound two ways. Typing updates the local data model at once and sends nothing. State goes to the agent only when an action fires, and it is the values listed in the action's context, unless the surface was created with sendDataModel, which also attaches the whole model. Before a value arrives, its path resolves to undefined and the renderer should show it empty.

The catalog is the contract

A catalog names every component, function and theme property an agent may use. createSurface refers to it by catalogId, an opaque string that need not resolve to anything; both sides must already have the catalog. The basic catalog (Text, Image, Row, Column, List, Card, Button, TextField, ChoicePicker and others) suits prototypes, while production apps usually write a custom catalog that mirrors their design system. The catalog documentation (opens in a new tab) describes the handshake: the client sends its supportedCatalogIds, ordered by preference, in message metadata; the agent picks the best match when it creates a surface; that choice is fixed for the surface's lifetime, and if nothing matches the agent sends no UI. Behaviour is data too: validation and formatting are functions referenced by name (required, regex, formatString, openUrl) that the client implements, so no code travels.

What the data-only design secures

Because the payload is data, an agent cannot make the client run code. It can only ask for components the client already ships, with properties the schema allows. Validation can run at two points: in the agent before sending, as the AG2 and CrewAI examples below do, and in the client against its own copy of the catalog, as Gemini Enterprise does. Doing both is a defence-in-depth practice we recommend; the specification itself says only that the generated JSON is validated and that an error goes back to the model. The guarantee is as strong as the catalog, though. The guide to custom catalogs (opens in a new tab) says to register only components you trust and not to render unsanitised agent content, because the text and URLs an agent supplies to a component are still untrusted input. The spec adds one multi-agent rule: the theme fields iconUrl and agentDisplayName identify who made a surface, so the orchestrator is responsible for setting or validating them.

Generating and validating A2UI

Since v0.9 the protocol is prompt-first. You place the schema, the catalog and example messages in the prompt and ask for matching JSON. The specification names the cost: the model is not constrained by the schema, so you validate afterwards and, on failure, return an error message the model can act on (code VALIDATION_FAILED, the surfaceId, a JSON Pointer path and a one-sentence message). Contrast this with Structured Outputs, where the provider enforces the schema while decoding.

Transports

A2UI does not mandate a transport, but the transport must deliver messages in order (a surface must exist before it is updated), frame them, carry metadata, and ideally offer a return path for actions. Over A2A, the extension specification (opens in a new tab) puts a list of A2UI messages in the data array of one data Part and marks it with the MIME type application/a2ui+json. The agent card can declare the catalogs the agent supports, the client's a2uiClientCapabilities rides in message metadata, and a receiver keeps processing the rest of a list when one message fails, because the list is not a transaction. The project describes AG-UI as the pipe and A2UI as the content, and the AG-UI documentation (opens in a new tab) says AG-UI is not itself a generative UI specification but a user-interaction protocol that natively supports specifications including A2UI. MCP, server-sent events, WebSockets and REST (which the spec says lacks streaming) are also listed.

Next to MCP Apps

MCP Apps takes the other route. The server provides pre-built HTML at a ui:// resource that a tool points to, and the host shows it in a sandboxed iframe. The A2UI project's comparison page (opens in a new tab) says to choose MCP Apps when the server should own the whole experience and A2UI when the UI should fit naturally into your app. Google's June 2026 post describes combining them: A2UI payloads returned from an MCP server, an MCP App embedded inside an A2UI component, and an A2UI renderer bundled inside an MCP App.

Worked example: Rendering, patching and answering a surface by hand

The script below is a miniature client written for this lesson. It is not the official renderer. It keeps only the ideas above: an allowlist, flat components, JSON Pointer paths, a list template and an action. Save it as mini_a2ui.py and run python3 mini_a2ui.py. COMPONENTS is the payload of an updateComponents message and DATA is the value of an updateDataModel message.

python
import copy, json

CATALOG = {"Text", "Column", "Row", "List", "Button", "TextField"}  # the client's allowlist
COMPONENTS = [
    {"id": "root", "component": "Column", "children": ["title", "lines", "note", "ok"]},
    {"id": "title", "component": "Text", "text": "Review your order"},
    {"id": "lines", "component": "List", "children": {"componentId": "line", "path": "/order/lines"}},
    {"id": "line", "component": "Row", "children": ["name", "qty"]},
    {"id": "name", "component": "Text", "text": {"path": "name"}},        # relative path
    {"id": "qty", "component": "Text", "text": {"path": "qty"}},
    {"id": "note", "component": "TextField", "label": "Delivery note", "value": {"path": "/order/note"}},
    {"id": "ok", "component": "Button", "child": "ok_label", "action": {"event": {
        "name": "confirm_order", "context": {"orderId": "A-1042", "note": {"path": "/order/note"}}}}},
    {"id": "ok_label", "component": "Text", "text": "Confirm"},
]
DATA = {"order": {"note": "", "lines": [
    {"name": "Apple", "qty": 10}, {"name": "Banana", "qty": 5}, {"name": "Cherry", "qty": 20}]}}

def msg(kind, **body): return {"version": "v0.9.1", kind: body}

def get_at(data, path):
    for part in [p for p in path.split("/") if p]:
        try: data = data[int(part)] if isinstance(data, list) else data[part]
        except (KeyError, IndexError, ValueError): return None   # not arrived yet
    return data

def set_at(data, path, value):            # returns a new model; never edits the old one
    if path in ("", "/"): return copy.deepcopy(value)
    new = node = copy.deepcopy(data); parts = [p for p in path.split("/") if p]
    for p in parts[:-1]: node = node[int(p)] if isinstance(node, list) else node.setdefault(p, {})
    node[int(parts[-1]) if isinstance(node, list) else parts[-1]] = value
    return new

def val(v, data, scope=""):               # literal, or {"path": ...}
    if isinstance(v, dict) and "path" in v:
        full = v["path"] if v["path"].startswith("/") else f"{scope}/{v['path']}"
        return "" if get_at(data, full) is None else get_at(data, full)
    return v

def draw(comps, data, cid="root", scope="", d=0):
    c, pad = comps[cid], "  " * d
    if c["component"] == "Text": return [f"{pad}Text: {val(c['text'], data, scope)}"]
    if c["component"] == "TextField": return [f"{pad}TextField {c['label']}: '{val(c['value'], data)}'"]
    if c["component"] == "Button": return [f"{pad}Button: " + draw(comps, data, c["child"])[0].strip()]
    out, kids = [pad + c["component"]], c["children"]
    if isinstance(kids, dict):            # template: one copy per item in the list at `path`
        for i in range(len(get_at(data, kids["path"]) or [])):
            out += draw(comps, data, kids["componentId"], f"{kids['path']}/{i}", d + 1)
    else:
        for kid in kids: out += draw(comps, data, kid, scope, d + 1)
    return out

def check(components):                    # the catalog is enforced, not advisory
    for i, c in enumerate(components):
        if c["component"] not in CATALOG:
            return msg("error", code="VALIDATION_FAILED", surfaceId="order",
                       path=f"/components/{i}/component",
                       message=f"'{c['component']}' is not in the catalog")

comps = {c["id"]: c for c in COMPONENTS}
print("\n".join(draw(comps, {})))                       # components arrived, data has not
data = set_at(DATA, "/order/lines/1/qty", 3)            # a one-value updateDataModel patch
data = set_at(data, "/order/note", "Leave at the door") # the user types: a local write
print("\n".join(draw(comps, data)))
ev = comps["ok"]["action"]["event"]                     # the user clicks Confirm
print(json.dumps(msg("action", name=ev["name"], surfaceId="order", sourceComponentId="ok",
                     timestamp="2026-10-10T09:30:00Z",
                     context={k: val(v, data) for k, v in ev["context"].items()})))
print(json.dumps(check([{"id": "root", "component": "ScriptRunner"}])))
size = lambda m: len(json.dumps(m, separators=(",", ":")).encode())
print(size(msg("updateComponents", surfaceId="order", components=COMPONENTS)),
      size(msg("updateDataModel", surfaceId="order", path="/order/lines/1/qty", value=3)))

Edge cases and limitations

The data arrives after the layout, or not at all
The spec says a data path resolves to undefined until the updateDataModel message that fills it has arrived, and renderers should show an empty value or a loading state. The worked example draws an empty List for exactly this reason. If the data never arrives, nothing reports an error: the user just sees an empty region. Send the first updateDataModel in the same turn as the components, and treat a surface that stays empty as a bug to log.
Documents, SDKs and hosts do not all speak the same version
Version 0.8 used beginRendering, surfaceUpdate and dataModelUpdate, wrapped each component as {"Text": {...}} and wrote literals as literalString. Version 0.9 renamed the messages and uses a "component" field instead. Gemini Enterprise accepts v0.9 and v0.8, Flutter's GenUI components page lists the v0.8 names surfaceUpdate and dataModelUpdate next to createSurface, and the Google Cloud blog and AG2's March 2026 post write the A2A MIME type as application/json+a2ui, while the v0.9.1 extension specification says application/a2ui+json. Copy shapes and strings only from the spec version your renderer targets.
The protocol is not at 1.0 yet
The A2UI roadmap lists v0.9.1 as current and v1.0 as a candidate, and schedules the v1.0 release for the fourth quarter of 2026 with stability guarantees and a migration path from v0.9. The candidate, described in its [evolution guide](https://a2ui.org/specification/v1.0-evolution-guide/), already changes things: it adds calls from agent to renderer and renderer to agent, lets a surface mix catalogs, and renames client and server to renderer and agent. Flutter's genui package is labelled alpha. Pin the version field and the catalogId you build against, and plan for a migration.
The catalog can reopen the hole it closes
Each component you register is trusted code, and the text and URLs an agent passes to it are still input from an untrusted party. The A2UI guide to custom catalogs says to register only components you trust, to avoid exposing dangerous capabilities, and not to render unsanitised agent content. Components that embed an iframe or open links widen what an agent can cause. The Gemini Enterprise reference agent has a GoogleMap component built on Maps Embed iframes, with the API key added on the server so the model never sees it.
A surface can claim to be a different agent
The basic catalog's theme has iconUrl and agentDisplayName so users can see which agent produced a surface. A malicious sub-agent could set these to impersonate a trusted service. The spec makes the orchestrator responsible for setting or validating them, for example by overwriting them with the verified identity of the sub-agent before forwarding createSurface. A renderer should display attribution only from a source it trusts.
No matching catalog means no UI
The client lists the catalogs it can render and the agent picks one when it creates a surface. If none matches, the agent does not send UI, so the conversation needs a text path. The client needs its own fallback too: the catalog guide advises skipping or substituting a safe placeholder for a component the renderer has not implemented, and showing a generic message if a whole surface cannot be drawn.

When to use it, and when something simpler is enough

Use it when

  • The agent runs on a server you do not control, or was built by another team or vendor, and its UI must appear inside your app without you running its code.
  • Your app has its own design system or runs on several platforms, such as web, Flutter mobile and desktop, and one agent response should render natively on each.
  • The interaction is form-like or choice-like, such as dates, selections or approvals, and text would need several turns to collect the same values.
  • The parts the agent may draw can be listed and reviewed in advance as a catalog, even though the layout built from them is chosen at runtime.

Think twice when

  • The agent needs a fully bespoke interactive module, such as a game or an editor, that no practical component catalog covers. An MCP App in an iframe, or a hybrid, fits better.
  • You own both ends and the screen never changes shape, so there is nothing for the agent to decide about layout.
  • You need a frozen, ratified standard today. A2UI is at v0.9.1 with v1.0 still a candidate, and renderers differ in maturity.

A simpler alternative. If the layout is fixed and only the values come from the agent, return typed data through tool calling or structured outputs and bind it to a component you wrote yourself, such as a flight card fed by a tool result. That is enough until the agent has to choose among many layouts or serve several client platforms. At that point a catalog plus A2UI replaces per-tool glue code.

Key takeaways

  • A2UI sends a screen as data, namely a flat list of catalog components, a separate data model and a few message types, so the agent never ships code to the client.
  • The client-side catalog is the security boundary, because the agent can only request components the client already implements and both sides validate against it.
  • Structure and state are separate, so after the first paint an agent usually sends small updateDataModel patches, and the user's typing stays local until an action sends its context.
  • Since v0.9 the model is prompted with the schema rather than constrained by it, so you validate, return VALIDATION_FAILED errors for correction, and fall back to text when retries run out.
  • A2UI is the format and not the pipe, since A2A, AG-UI, MCP and others can carry it, and MCP Apps is the alternative that ships server-owned HTML in a sandboxed iframe.
  • The protocol is still before 1.0, so pin the version and the catalogId you target and expect differences between renderers and hosts.

Example 1 of 5

Gemini Enterprise renders registered agents' A2UI in its own chat

Google Cloud (Gemini Enterprise)Documented in official docs

Gemini Enterprise's administrator guide describes registering an agent that uses A2UI for its interface and A2A for communication. A Google Cloud developer blog post of May 2026 walks through a restaurant-finder reference agent built with ADK. [17][18][11][15]

The problem

A company wants agents from different teams to show forms, pick-lists and maps inside one enterprise chat product. The product cannot run each team's front-end code, must keep one look, and wants structured input back instead of free text. The Google Cloud post names the alternative it is replacing: HTML or JavaScript fragments from a remote agent risk cross-site scripting, UI injection and visual drift from the host's design system.

Where this topic fits

A2UI is the payload between the agent's A2A endpoint and Gemini Enterprise, which owns the chat shell, the renderer and the transport client. The catalog is the host's: on each call the host tells the agent which components it can draw, and the agent builds only from those.

How it is applied, step by step

  1. A developer builds an A2A agent that carries an A2UI catalog and example payloads alongside its usual tool definitions, and hosts it on Cloud Run or Agent Runtime.
  2. A Gemini Enterprise administrator registers the agent as an A2A agent and manages it on the Agents page.
  3. When a user sends a request, Gemini Enterprise calls the agent's A2A endpoint and includes its own catalog, the list of components it can render.
  4. The agent decides whether UI helps. If so it emits A2UI JSON, for example a ChoicePicker of restaurants; if not it answers in text.
  5. Gemini Enterprise validates the JSON against its catalog and draws it in its own design language.
  6. The user's selections return to the agent as structured input on the next turn.

Why this approach fits

The host is the trust boundary, so the host's catalog is the right contract. Any agent can contribute UI without the product running that agent's code, and every agent's UI looks like the product. Because the host states its catalog on every call, the agent adapts to what this host supports instead of assuming a component set.

Limitation or tradeoff

The agent can only draw what the host's catalog offers, and the host limits versions: Gemini Enterprise supports A2UI v0.9 and v0.8. The A2UI project adds that rendering needs agents registered through the A2A path and that managed agents registered through the ADK path did not support it when the page was read. The administrator must also host and maintain every agent.

What the sources document

  • A Gemini Enterprise administrator can register an agent that uses A2UI for custom interfaces and A2A for communication; the standard A2UI components render with Gemini Enterprise's built-in styling, and versions v0.9 and v0.8 are supported. [17]
  • The agent must be hosted at an endpoint that Gemini Enterprise can reach, for example on Cloud Run or Agent Runtime, and an administrator then registers it as an A2A agent and manages it on the Agents page. [17]
  • At runtime Gemini Enterprise calls the agent's A2A endpoint with its own A2UI catalog, the agent emits A2UI JSON or falls back to text, Gemini Enterprise validates the JSON against its catalog and renders it natively, and the user's interaction goes back as structured input. [18]
  • The reference agent has a custom GoogleMap component rendered through Google Maps Embed iframes, with the API key injected server-side so the model never sees it. [18]
  • The A2UI project's ecosystem page states that A2UI rendering in Gemini Enterprise requires self-serve agents registered through the A2A path, and that managed agents registered through the ADK path do not currently support it. The December 2025 launch post said A2UI was being integrated so that enterprise agents can render rich, interactive UIs inside their host applications. [11][15]

The facts above come from the cited sources. The steps and analysis in this example are our explanation of how they fit together.

Example 2 of 5

Flutter's GenUI SDK builds agent UI from an app's own widgets

Flutter (Google)Documented in official docs

Flutter's documentation describes the GenUI SDK as an orchestration layer between the user, the app's widgets and an AI agent, and the A2UI project states that GenUI uses A2UI as its underlying protocol. [19][20][11][15]

The problem

A native app has brand-specific widgets and wants an agent to compose screens from them, such as a clickable product carousel instead of a text list, or a trip-planning form with sliders and date pickers, on mobile, desktop and web. The layout should be decided by the agent at runtime, using only widgets the app already contains.

Where this topic fits

GenUI runs inside the Flutter app and plays the renderer role. The app registers its widgets as the catalog, an adapter turns the model's text stream into A2UI messages, a controller applies them, and a bound data model rebuilds only the widgets whose data changed.

How it is applied, step by step

  1. The developer registers widgets as catalog items, each with a name the model will use, a data schema for its properties and a builder function that creates the Flutter widget.
  2. The app sends the user's message to the LLM, with the widget schemas in the system prompt so the model knows what it may use.
  3. A transport adapter parses the model's text stream into A2UI messages.
  4. A surface controller applies the messages, updates the data model, and the surface widgets listening for that id rebuild.
  5. When the user types, the data model updates directly. When the user triggers an action such as a button click, the controller sends a new user message containing the current data-model state, and the cycle starts again.

Why this approach fits

Flutter apps already own their widgets and theme, so mapping the catalog onto them means the model composes in the app's own design language, with native performance. The same agent response can serve every platform Flutter targets, and the app never executes anything the model wrote.

Limitation or tradeoff

The pages mark the package as experimental: alpha and likely to change. The components page lists the message names createSurface, surfaceUpdate, dataModelUpdate and deleteSurface, which mixes the v0.9 name createSurface with the v0.8 names surfaceUpdate and dataModelUpdate and states no protocol version, so check which version an SDK release speaks before mixing it with a v0.9.1 agent. A small widget catalog also limits what the model can compose, so the quality of widget names and schemas decides how well it chooses.

What the sources document

  • GenUI is an orchestration layer that coordinates information between the user, Flutter widgets and an AI agent. It uses a JSON-based format to compose UI from the app's existing widget catalog and feeds state changes back to the agent. [19]
  • The catalog is a set of CatalogItem objects that define the widgets the AI may use. Each item gives a name for the AI to reference, a data schema for its properties and a builder function. [20]
  • The DataModel is an observable store that widgets are bound to, and only widgets that depend on changed data are rebuilt. [20]
  • The LLM is guided by widget schemas in its system prompt, the transport adapter parses its text stream into A2UI messages, and a button click makes the controller create a new user message with the current data-model state. [20]
  • The genui package is described as alpha and likely to change. The A2UI project and its launch post say GenUI uses A2UI as the declaration format between server-side agents and Flutter applications. [19][11][15]

Example 3 of 5

CopilotKit renders A2UI from a React catalog, fixed or generated

CopilotKit (with CrewAI's guide to the same integration)Documented in official docs

CopilotKit's documentation describes an A2UI middleware for its runtime with a fixed-schema mode and a dynamic-schema mode. CrewAI's guide shows its agents using the same integration over AG-UI. [21][22][23][24]

The problem

A web app with a chat panel wants agent answers drawn as cards and panels from its own React components. Sometimes the layout is known in advance, as with a flight card. Sometimes it is not, because any question might need a different panel. Letting a model design every layout costs an extra model call and allows drift, while hand-authoring every layout cannot adapt.

Where this topic fits

A2UI is the content and AG-UI carries it. The runtime middleware intercepts tool results that contain A2UI operations, and the React front end registers a catalog of components for them. Fixed schema moves the layout into code you control, and dynamic schema lets a second model design it.

How it is applied, step by step

  1. The team writes a catalog: a schema for each component's props, a React renderer for each, and a catalog id. The basic catalog can be merged in.
  2. Fixed schema: the component tree is authored once as JSON on the agent side. A tool such as the docs' display_flight only supplies data, returned as an operations container holding createSurface, updateComponents and updateDataModel.
  3. The middleware intercepts that tool result and the front end renders the surface as soon as the tool returns.
  4. Dynamic schema: the runtime serialises the client catalog, meaning component names, prop schemas and descriptions, into a second model's context. That model designs both layout and data, and the middleware renders them progressively.
  5. Bindable props must accept either a literal or a path object, otherwise the raw binding object reaches React and rendering fails.

Why this approach fits

Fixed schema suits surfaces you know in advance: the layout is deterministic and designer-controlled, and nothing has to generate a layout. Dynamic schema suits open-ended requests, because the model can combine components you own into any panel yet can never render something you did not ship. Both use the same catalog, so a team can start dynamic and move frequent surfaces to fixed.

Limitation or tradeoff

The flight card is a documentation demo and the docs call the domain illustrative. A code comment in the demo says its button click is inert until the Python SDK exposes action handlers on its render helper, so clicks needed front-end handling when the page was read. Dynamic mode adds a model call and depends on the quality of the component descriptions, which is why the same docs recommend fixed schemas for well-known surfaces.

What the sources document

  • In fixed-schema mode the component tree lives on the agent side and the tool only supplies data. The tool returns an operations container with createSurface, updateComponents and updateDataModel, the middleware intercepts it, and the front end renders it. [21]
  • A prop that can be bound needs a literal-or-binding union such as DynString, because a plain string type makes the raw path object reach React and rendering fails. [21]
  • In dynamic-schema mode a secondary LLM generates both structure and data, and the runtime converts the client catalog's component names and Zod prop schemas into the model's context. The docs recommend dynamic when the UI shape is unknown ahead of time and fixed for well-known surfaces, which are faster, cheaper and deterministic. [22]
  • CrewAI's guide says that with A2UI enabled a generate_a2ui tool is injected, a sub-agent designs the surface against the catalog, streams it and repairs invalid output with a validate-then-retry pass, and the agent can only use components in the catalog. [23]
  • The AG-UI documentation says AG-UI is not itself a generative UI specification but a user-interaction protocol that natively supports specifications including A2UI. [24]

Example 4 of 5

AG2 validates A2UI output, retries, and falls back to prose

AG2Documented in official docs

AG2's A2UI documentation and its March 2026 announcement post describe wrapping an agent so that it produces A2UI, with schema validation, retries and server-side button handlers. [25][26]

The problem

Prompt-first generation means a model's JSON can be wrong. A framework that serves many UIs needs invalid output to stay away from the renderer, needs button clicks that run business logic without another model call, and needs one agent to be reachable both by A2A clients and by plain web clients.

Where this topic fits

This is the agent-side half of the loop, between the model and the transport. A wrapper adds the A2UI instructions and catalog to the prompt, validates every message, retries with the error on failure, and turns client actions into either a server handler call or the next turn.

How it is applied, step by step

  1. The agent is wrapped in an A2UI transport, either a REST and server-sent events server or an A2A executor, which adds the A2UI instructions and the chosen catalog to the prompt each turn.
  2. The model replies with prose and an A2UI JSON block.
  3. Each message is validated against the catalog schema. On failure the error is returned to the model, up to a retry limit.
  4. If the retries run out, the turn degrades to prose and a validation-failed event is emitted so operators can see it.
  5. A function declared as an action becomes a button. Clicking it runs the handler on the server without invoking the model, and other client actions are rewritten into the next turn.

Why this approach fits

Validation belongs where output is produced. Failing fast with an error the model can read is cheaper than a broken screen, and degrading to prose keeps the conversation useful when UI cannot be produced. Server-side handlers keep deterministic business logic, such as approving a request, out of the model.

Limitation or tradeoff

A degraded turn gives the user text where a UI was intended, so you must watch the validation-failed events to learn how often it happens. AG2's interface also moved fast: the March 2026 post configures an A2UIAgent class from an experimental module with validation and retry options, while the current overview describes a transport around a plain agent with no special subclass. Read the documentation for the version you install.

What the sources document

  • A2UI in AG2 is a transport over a plain agent, either a REST and server-sent events server or an A2A executor, with no special agent subclass, and a wrapped agent still answers in prose when a UI would not help. [25]
  • The transport applies prompt and validation middleware each turn, validates every A2UI message against the chosen catalog schema with retry on error, and on repeated failure degrades gracefully to prose. [25]
  • A validation-failed event signals that retries were exhausted and the turn degraded, and the a2ui_action decorator turns a function into a button whose click runs on the server without invoking the agent. [25]
  • The protocol versions accepted are v0.9 (the default), v0.9.1 and v1.0, the last adding function-call round trips. [25]
  • The March 2026 announcement describes a generate-validate-retry loop in which errors return to the model and, once retries are exhausted, output degrades to text. [26]

Example 5 of 5

A2UI over MCP and MCP Apps in Google's reference demos

Google (A2UI project) and the MCP communityDocumented in an engineering article

Google's Developers Blog post of 17 June 2026 and the A2UI project's A2UI over MCP guide describe three ways to combine A2UI with MCP, each with a demo. The MCP side is documented in the MCP Apps overview. [16][12][27][13]

The problem

MCP servers already provide tools and resources, and some of them need a UI. Standard forms and cards should match the host's design. Some modules, such as a game or a concert seat-selection workflow with bespoke validation, need arbitrary logic that a component catalog cannot express. Some hosts support only one approach. The post states the dilemma: MCP Apps give freedom but fragmented visuals, while A2UI gives consistency and security but only a fixed component library.

Where this topic fits

A2UI travels inside MCP primitives (resources and tool results), or wraps around an MCP App, or runs inside one. MCP is then both the transport and, for MCP Apps, the iframe runtime.

How it is applied, step by step

  1. Pattern 1, A2UI over MCP: the server serves a presentation template (createSurface and updateComponents with bindings) as an MCP resource under an a2ui:// URI, and a tool returns only an updateDataModel message as an embedded resource. The tool's metadata points to the template, which the client fetches once and caches.
  2. The post says an A2UI-capable host directs a payload with the MIME type application/a2ui+json to its native rendering engine, and the guide says clients use this identification to route payloads to A2UI processors, so this path needs no iframe.
  3. Pattern 2, MCP Apps inside A2UI: a custom component wraps an MCP App in a sandboxed iframe. The host intercepts events from the app and delegates them to the agent as A2UI actions, the agent tracks the key state, and updates flow back through the host to the native components and the embedded app.
  4. Pattern 3, A2UI inside MCP Apps: the app bundle includes an A2UI renderer, calls a server tool, and draws the returned A2UI inside its own iframe, so a host with no A2UI support can still show generative UI.
  5. Catalog compatibility is settled during MCP initialisation, or in per-message metadata for stateless servers.

Why this approach fits

For standard UI the native route removes the iframe and inherits the host's design system, so it suits most forms and cards. Resources suit prescriptive UI that can be cached, tools suit UI that depends on parameters, and an iframe is kept for the few modules that need real logic.

Limitation or tradeoff

Google's post says that dynamic control in A2UI over MCP tools is limited to the tool's input parameters, unless an agent sits behind the tool to generate more. The demos (a recipe studio, a Pong game, a document editor) are reference samples, not named production deployments. Embedding an MCP App needs a double-iframe sandbox with no allow-same-origin on the inner frame, and the guide mentions a development flag that skips the security self-test, which must not reach production.

What the sources document

  • Google's post describes three patterns: A2UI payloads (MIME type application/a2ui+json) returned from MCP servers and rendered natively, MCP Apps embedded in A2UI components through secure iframes, and an A2UI renderer bundled inside an MCP App. [16]
  • The post states the trade-off: MCP Apps give creative freedom but a fragmented experience and clashing design systems, while A2UI gives consistency and security but restricts developers to a specific component library. [16]
  • The A2UI over MCP guide serves static templates as MCP resources under a2ui:// URIs, returns dynamic values from tools as an updateDataModel in an embedded resource, and links the two with the tool's _meta.ui metadata, with client-side caching of the template. [12]
  • MCP Apps declare UI templates as ui:// resources linked from tool metadata, run views in sandboxed iframes with no access to the host's DOM, cookies or storage, and communicate with the host through postMessage using JSON-RPC. [27]
  • The A2UI guide for embedding MCP Apps uses a double-iframe pattern and requires that the inner iframe does not have the allow-same-origin permission. [13]

4Common mistakes

  1. Treating the catalog as documentation instead of an enforced allowlist

    Why it causes problems
    A renderer that draws unknown component types, or passes agent text straight into HTML or a link target, gives back the injection risk that the data-only design was meant to remove. The agent then controls more than the catalog says it can.
    How to recognise it
    Send the renderer a component name that is not in the catalog, a property with the wrong type, and a text value that looks like markup. If any of them is drawn, executed or crashes the page instead of being rejected or shown as plain text, the allowlist is not enforced.
    How to fix it
    Validate every message against the catalog schema on the client, skip or replace unknown components with a safe placeholder, escape text, and register only components you would be willing to run with attacker-chosen properties.

  2. Resending the whole component list for every change

    Why it causes problems
    It spends tokens and latency on structure that did not change, and it can make the screen flicker. In the worked example the full component message is 775 bytes while a patch to one value is 98.
    How to recognise it
    The agent's logs show an updateComponents message on every turn even though only numbers, names or statuses changed, or a long list is rebuilt for a single edited row.
    How to fix it
    Bind properties to data paths and send updateDataModel patches at the narrowest path that changed. Send updateComponents again only when the structure itself changes.

  3. Assuming that valid JSON means a valid UI

    Why it causes problems
    Since v0.9 the model is prompted with the schema, not constrained by it. It can return a child id that does not exist, an unknown property or no root, and the user sees a blank or broken surface with no explanation.
    How to recognise it
    Count messages that fail schema validation or tree checks per hundred turns. Blank surfaces with a successful model call, or errors mentioning a missing root or child, point to this.
    How to fix it
    Validate before sending, return a VALIDATION_FAILED error with the failing JSON Pointer path so the model can correct itself, cap the number of retries, fall back to text, and log every degraded turn.

  4. Mixing protocol versions in one pipeline

    Why it causes problems
    Version 0.8 messages (beginRendering, surfaceUpdate, literalString, components wrapped as {"Text": {...}}) do not validate as v0.9.1, and the reverse is also true. The symptom is often silence, because a renderer may skip a message it cannot place.
    How to recognise it
    A message is ignored or fails validation although it looks right, its envelope key is not one of the four in the spec you target, or the host's documentation lists a different version than your agent emits.
    How to fix it
    Put the version field on every message, read the evolution guide for the version you use, advertise the catalogs your client supports, and have the agent pick the catalog and shape that the client lists.

  5. Keeping secrets in the data model of a surface that sends it back

    Why it causes problems
    When createSurface sets sendDataModel to true, the client attaches the surface's entire data model to the metadata of the messages it sends to the agent that created it, such as actions. A field bound to a path, such as an obscured password input, then travels to the agent even if the action's context never named it.
    How to recognise it
    Look at createSurface for sendDataModel set to true on surfaces that contain sensitive inputs, and compare what an action message carries with what the agent actually needs.
    How to fix it
    Leave sendDataModel off unless the agent needs the whole state, put only the required values in the action's context, and keep credentials out of agent-visible data models.

Exercise 1

Extend the mini client with a shared path, a cycle check and a root guard

CodingIntermediateAbout 40 min (estimate)Hypothetical scenario

Start from the mini_a2ui.py script in the worked example. It needs only Python 3.8 or later and no packages. Make three changes and prove each one with assert statements.

  1. Absolute path in a template. Add "currency": "EUR" to the order in DATA, and add a third Text component to each row that shows it. The path must start with a slash, because the currency belongs to the order and not to one row.
  2. Tree integrity. Extend check() so that it also rejects a component list in which a component is its own descendant, for example a Column whose children contain its own id. Return the same VALIDATION_FAILED shape and say "cycle" in the message.
  3. Root guard. Make draw() return a one-item list ["(waiting for root)"] when the root component has not arrived yet, instead of raising KeyError.

Keep set_at() non-mutating: after your changes, patching /order/lines/1/qty must not alter the original DATA.

Requirements

  • Every row prints three Text lines, and the third shows EUR, read through an absolute path that starts with a slash.
  • check() returns a VALIDATION_FAILED error for a Column whose children include its own id, and returns nothing for the original COMPONENTS.
  • draw({}, {}) returns a list with one item and does not raise.
  • An assert proves that DATA is unchanged after set_at() is used to patch a quantity.

Expected behaviour

The first row prints as Row, Text: Apple, Text: 10, Text: EUR. The cycle test prints a JSON error whose message contains the word cycle. draw({}, {}) prints ['(waiting for root)']. All asserts pass silently.

Hint 1

Only `name` and `qty` need relative paths. A path with a leading slash ignores the template scope, so `/order/currency` works inside the row.

Hint 2

A depth-first walk that carries the set of ids on the current branch finds a cycle when it meets an id that is already in that set.

Hint 3

Guard `draw()` at the top with a membership test on the components dictionary before you read from it.

Show solution

Three small edits. First, the data and the row (the rest of COMPONENTS is unchanged):

DATA = {"order": {"note": "", "currency": "EUR", "lines": [
    {"name": "Apple", "qty": 10}, {"name": "Banana", "qty": 5}, {"name": "Cherry", "qty": 20}]}}
# in COMPONENTS: the row lists three children, and a new component reads the shared value
{"id": "line", "component": "Row", "children": ["name", "qty", "cur"]},
{"id": "cur", "component": "Text", "text": {"path": "/order/currency"}},

Second, replace check() with a version that also walks the tree:

python
def error(i, path, message):
    return msg("error", code="VALIDATION_FAILED", surfaceId="order",
               path=f"/components/{i}{path}", message=message)

def kids_of(c):
    kids = c.get("children", [])
    return [c["child"]] if "child" in c else kids if isinstance(kids, list) else [kids["componentId"]]

def check(components):
    by_id = {c["id"]: c for c in components}
    for i, c in enumerate(components):
        if c["component"] not in CATALOG:
            return error(i, "/component", f"'{c['component']}' is not in the catalog")
    def walk(cid, path):              # `path` holds the ids above this one
        if cid in path: return cid
        for kid in kids_of(by_id[cid]):
            if kid in by_id and (found := walk(kid, path | {cid})): return found
    for i, c in enumerate(components):
        if (found := walk(c["id"], frozenset())):
            return error(i, "", f"cycle: '{found}' is its own descendant")

Third, the first line of draw() becomes a guard:

python
def draw(comps, data, cid="root", scope="", d=0):
    if cid not in comps: return ["(waiting for root)"]
    c, pad = comps[cid], "  " * d

Replace the demo lines at the bottom with tests:

python
comps = {c["id"]: c for c in COMPONENTS}
data = set_at(DATA, "/order/lines/1/qty", 3)
assert DATA["order"]["lines"][1]["qty"] == 5          # the old model is unchanged
print("\n".join(draw(comps, data)[:7]))
assert check(COMPONENTS) is None
print(json.dumps(check([{"id": "a", "component": "Column", "children": ["a"]}])))
print(draw({}, {}))

The currency is read through an absolute path, so every copy of the row template shows the same value. The spec asks validators to check the integrity of the UI tree, for example that parents reference existing children. The cycle check extends that idea: a flat list can refer to itself in ways a nested tree cannot, so a renderer should check before it recurses, or a hostile or buggy agent could make it loop forever. set_at() copies the model before changing it, which is why the assertion about DATA holds.

Exercise 2

Audit four A2UI messages before they reach the renderer

AnalysisIntermediateAbout 25 min (estimate)Hypothetical scenario

Your client targets A2UI v0.9.1 with the basic catalog. A surface with id s1 has already been created with createSurface, and no surface s2 exists. For each message below, decide whether the client should accept it, and name the specific rule it breaks if not. No tools are needed.

json
{"version": "v0.9.1", "updateComponents": {"surfaceId": "s1", "components": [
  {"id": "root", "component": "Column", "children": ["t1", "b1"]},
  {"id": "t1", "component": "Text", "text": "Pick a time"},
  {"id": "b1", "component": "Button", "child": "b1_label", "action": {"event": {"name": "pick"}}}]}}
json
{"surfaceUpdate": {"surfaceId": "s1", "components": [
  {"id": "t1", "component": {"Text": {"text": {"literalString": "Hi"}}}}]}}
json
{"version": "v0.9.1", "updateComponents": {"surfaceId": "s1", "components": [
  {"id": "root", "component": "WebView", "url": "https://example.com/offer"}]}}
json
{"version": "v0.9.1", "updateDataModel": {"surfaceId": "s2", "path": "/user/name", "value": "Alice"}}

Requirements

  • For each of the four messages, state accept or reject and name the rule or schema constraint that decides it.
  • Write the VALIDATION_FAILED error message for the first message, with a JSON Pointer path to the failing item.
  • Say which message cannot be fixed by the agent alone if the product really needs that behaviour, and who would have to change.

Expected behaviour

Messages 1 to 4 are all rejected, each for a different reason: a dangling child reference, a v0.8 shape, a component outside the catalog, and an update for a surface that was never created. A complete answer also writes a well-formed error object for message 1 and identifies the WebView case as a client decision.

Hint 1

In the first message, compare every id in a `children` or `child` property with the ids defined in the same list.

Hint 2

The v0.9.1 server-to-client envelope has exactly four possible keys and a version field. Check the second message against both.

Hint 3

The basic catalog lists eighteen components. Look for the word in the third message.

Show solution

  1. Reject: dangling child. Button b1 points at b1_label, which is not defined in the list. The spec says validators check that parents reference existing children. The action is present, which the catalog requires, so that part is fine. Error:

    json
    {"version": "v0.9.1", "error": {"code": "VALIDATION_FAILED", "surfaceId": "s1",
           "path": "/components/2/child", "message": "child 'b1_label' does not exist"}}

  2. Reject: v0.8 message. surfaceUpdate is not one of the four v0.9.1 envelope keys, there is no version field, and the component is wrapped as {"Text": {...}} with a literalString instead of using the component field. The agent is speaking v0.8 to a v0.9.1 client. The fix is for the agent to emit v0.9.1, or for the client to negotiate a version it supports.

  3. Reject: not in the catalog. WebView is not one of the basic catalog's components, and the client validates against its local catalog definition. Whether WebView should ever exist is a decision for the client team: they would have to add a vetted component to a custom catalog and advertise its catalogId. The agent cannot fix this by itself, and loading arbitrary web content is exactly the capability the data-only design avoids, so the safer option is for the agent to use catalog components or open a link through the catalog's openUrl function.

  4. Reject: no such surface. The spec says a surface must be created before any updateComponents or updateDataModel is sent to it. Surface s2 was never created. The agent should create it first, or send the update to s1.

The pattern across the four answers is that each rule comes from either the envelope, the tree, the catalog, or the order of messages. A renderer that checks all four can reject bad output in one place and report it with the standard error shape.

  • Does your error object use the code VALIDATION_FAILED, the surfaceId s1 and a path that begins with /components/?
  • Could you explain why the WebView case needs a decision from the client team and not a fix in the agent?
