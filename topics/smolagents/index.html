smolagents (Code Agents)

smolagents is Hugging Face's open-source Python library for building agents. Its main class, CodeAgent, acts by writing a short Python snippet at each step and running it, instead of emitting a JSON tool call. ToolCallingAgent is the JSON-based alternative.

1Overview

Why it matters

Most agent frameworks ask the model to fill in a form: a tool name and its arguments, which the framework then executes. smolagents bets that a programming language is a better action format, because one snippet can loop over inputs, keep intermediate results in variables and combine several tools. When the bet pays off, a task takes fewer model calls and fewer chances to lose a value on the way. Hugging Face's own reproduction of Deep Research (opens in a new tab) scored 55.15% on the GAIA validation set with code actions and 33% with JSON actions in the same setup.

The price is that someone must run the model's code. Every decision about where that code executes is a security decision, and the library's default local interpreter is documented as not being a security boundary. Anyone who picks a framework, deploys a code agent or reviews one needs both halves: when code actions help, and what has to be isolated when you use them. The agent classes and their loop live in one source file, which makes the library a good place to see how an agent framework works inside.

  • Define a tool with the tool decorator or a Tool subclass so that its name, description, inputs and output type reach the model correctly.
  • Trace one CodeAgent run step by step, including the code action, the execution logs, an error that becomes feedback, persistent variables and final_answer.
  • Choose an executor (local, Docker, E2B, Modal or Blaxel) and state what the default local executor does not guarantee.
  • Bound a run with max_steps, authorised imports, final_answer_checks, planning and structured outputs.
  • Decide, using measured evidence, when code actions are likely to beat JSON actions and when a ToolCallingAgent or a plain workflow is the better choice.

Key terms

CodeAgent
The smolagents agent class whose action at each step is a Python snippet. The framework extracts the snippet from the model's reply and runs it in an executor.
ToolCallingAgent
The smolagents agent class whose action is a JSON tool call, the format that hosted model APIs support natively. By default it runs only the tools you registered, not model-written code.
MultiStepAgent
The base class of both agents. It implements the loop of memory, model call, action and observation, and it is the library's version of the ReAct pattern.
Code action
The Python snippet a CodeAgent writes as its action in one step. Tools appear in it as ordinary function calls, and the snippet can also use loops, conditions and variables.
Tool
A function wrapped with a name, a description, typed inputs and an output type. The framework writes these into the prompt so the model knows how to call it.
Executor
The component that runs the model's snippet. LocalPythonExecutor interprets it inside your process; Docker, E2B, Modal and Blaxel executors send it to a container or a hosted sandbox.
Authorised imports
The modules a snippet may import. The default list is short, and additional_authorized_imports extends it.
final_answer
A built-in tool that the code calls to end the run with a result. Calling it raises an exception inside the executor that carries the value out.
Managed agent
An agent given a name and a description so that another agent can call it like a tool. It is how smolagents builds hierarchies of agents.
Step callback
A function the agent calls after each step with the step record. It is used for screenshots, logging or trimming memory.

2Explanation

Introduction

In Tool Calling the model answers with a small JSON object: a tool name and its arguments. In The Agent Loop your program repeats that exchange until the task is done. smolagents, Hugging Face's open-source agent library, keeps that loop and changes one thing: the action the model writes at each step is a short piece of Python.

Picture asking a colleague for the warmest of four cities. If you can only pass notes that fit a form, you send "look up Oslo", wait, send "look up Lagos", and so on, and your colleague has no notepad between notes. If you can pass a script, you send one: loop over the four cities, keep the readings in a variable, take the maximum. The colleague runs it and reports. That is the difference between a ToolCallingAgent, whose actions are JSON, and a CodeAgent, whose actions are Python.

The change has two consequences, and the rest of the lesson is about both. First, the model gains the full expressiveness of a programming language: it can compose tools, store objects and fix its own mistakes from error messages. Second, your system now executes text that a model wrote, so the choice of executor, import list and sandbox matters as much as the prompt. The table below sets the two action formats side by side.

This lesson uses smolagents 1.26.0, the version whose documentation and tagged source were read for it. The project's API reference (opens in a new tab) calls the API experimental and subject to change, so check names against the version you install. It builds on Choosing an Agent Framework and Code Execution and Sandboxing. You will see how one CodeAgent step works, how tools are described to the model, where the code runs, how to bound a run, what measured evidence says about code against JSON, and five documented uses.

How it works

Two agent classes on one loop

Both classes inherit from MultiStepAgent, which the documentation (opens in a new tab) calls an abstraction of the ReAct framework. At the start of a run it stores the system prompt in a SystemPromptStep and the task in a TaskStep. Each iteration then writes memory into chat messages, sends them to the model, parses the reply into an action, executes it and records the result in an ActionStep. With planning switched on, a PlanningStep is added at intervals. After every step the agent calls its step callbacks. The two classes differ mainly in the action. A ToolCallingAgent receives a JSON tool call and runs the named tool. A CodeAgent receives text that contains Python and runs it.

One CodeAgent step

In version 1.26.0, read from the tagged source (opens in a new tab), a step goes like this.

  1. The model replies with a Thought and a code block. By default the block sits between <code> and </code> tags; code_block_tags="markdown" switches to fenced blocks. The call passes stop sequences such as Observation:, which cut the reply off before the model can write an observation of its own.
  2. The snippet is extracted. If no code block is found, the parsing error becomes the step's feedback.
  3. The executor runs it. Tools are plain Python functions inside the snippet. Whatever the code prints, plus the value of its last expression, comes back as the observation (Execution logs: and Last output from code snippet:), so the model must print what it wants to see next.
  4. Variables persist. The system prompt tells the model that state persists between executions. The executor keeps one namespace for the agent object, so a dict built in step 1 is still there in step 3. In the v1.26.0 source nothing clears that namespace between runs.
  5. Mistakes become feedback. A syntax error, an exception or a disallowed import is stored on the step and shown to the model on the next call with a request to retry. A failure of the model call itself, such as a rejected API request, is not retried by the loop and ends the run.
  6. The run ends when the code calls final_answer(...). Inside the executor that raises an exception which carries the value out, so code after the call never runs. Functions in final_answer_checks run first; a failed check is logged and the loop continues. If max_steps (default 20) is used up, the agent makes one more model call that writes an answer from memory, as The Agent Loop describes.

How tools reach the model

A tool is a function plus metadata: a name, a description, typed inputs and an output_type. A CodeAgent prompt shows each tool as a Python signature with its description as the docstring, so the text you write is prompt text. There are two ways to define one.

python
from smolagents import Tool, tool


@tool
def get_temperature_c(city: str) -> float:
    """Returns the temperature in degrees Celsius for a city.

    Args:
        city: Name of the city, for example Oslo.
    """
    return {"Oslo": 4.0, "Lagos": 31.0}[city]


class TemperatureTool(Tool):
    name = "get_temperature_c"
    description = "Returns the temperature in degrees Celsius for a city."
    inputs = {"city": {"type": "string", "description": "Name of the city, for example Oslo."}}
    output_type = "number"

    def forward(self, city: str) -> float:
        return {"Oslo": 4.0, "Lagos": 31.0}[city]

The decorator needs a type hint for every input and for the return value, plus an Args: section. Subclass Tool when a tool needs setup or state. Allowed types are string, boolean, integer, number, image, audio, array, object, any and null. The building good agents guide (opens in a new tab) advises that tools print useful detail, raise errors that say what was wrong, and that you merge tools to reduce model calls. Tools can also come from MCP servers, Hub Spaces and LangChain; the tools tutorial (opens in a new tab) warns that stdio MCP servers always run code on your machine and that tools loaded from the Hub need trust_remote_code=True. With the default executor, tool bodies run as ordinary Python with your privileges. Only the model's own snippet is restricted.

Where the code runs

The default LocalPythonExecutor does not hand the snippet to Python's own exec. It parses the code into a syntax tree and evaluates it node by node, which lets it enforce rules. Imports must be on an allowlist: by default collections, datetime, itertools, math, queue, random, re, stat, statistics, time and unicodedata, extended through additional_authorized_imports. Submodules need their own entry, and numpy.* allows a package and everything below it. Operations are counted; in the v1.26.0 executor source (opens in a new tab) a while loop stops at 1,000,000 iterations, a run at 10,000,000 operations, and execution at 30 seconds by default. These checks catch mistakes and obvious misuse. They are not isolation. The security policy (opens in a new tab) states that the local executor is not a security boundary and that escaping it is out of scope, and releases before 1.17.0 were affected by a sandbox escape (CVE-2025-5120 (opens in a new tab)).

For isolation, set executor_type to "docker", "e2b", "modal" or "blaxel". The snippet then runs in a container or a hosted sandbox while the model is still called from your process. The secure execution tutorial (opens in a new tab) describes the other option, running the whole agent system inside a sandbox: it supports managed agents but may require API keys inside it. Use the agent as a context manager, with CodeAgent(...) as agent:, so the sandbox is cleaned up. Code Execution and Sandboxing covers the isolation technologies themselves.

Limits and controls

  • max_steps caps the loop (default 20) and can be overridden in agent.run(task, max_steps=...).
  • final_answer_checks takes functions called as check(final_answer, memory, agent=agent); return False to reject an answer and keep the loop going.
  • instructions is a string appended to the system prompt, which is simpler than rewriting the template.
  • planning_interval=N adds a planning step every N steps in which the model updates its facts and plan.
  • step_callbacks run after each step, and additional_args passes objects into the run as variables.
  • run(..., reset=False) continues an earlier conversation, and return_full_result=True returns a result object whose state tells a finished run from one stopped by the step cap.
  • use_structured_outputs_internally=True makes the model return JSON with a thought and a code field.
  • managed_agents=[...] lets one agent call another like a tool. The called agent needs a name and a description, which the manager's prompt shows.

What the evidence says about code versus JSON

The secure execution tutorial (opens in a new tab) names four advantages of code actions. They compose (nested calls, reusable functions), they manage objects (an image can be assigned to a variable), they are general, and code is well represented in training data. Measured evidence is mixed in size. The CodeAct paper tested 17 models and reports up to a 20% higher success rate, and up to 30% fewer actions, on its multi-tool benchmark. In its results table code was the best or tied-best format on success rate for 12 of the 17 models (two of them scored the same with every format) and the best on fewer turns for 12 of 17, so the gain is not universal. On single, atomic API calls the same paper finds code best for 8 of the 17 models, JSON for 5 (all closed-source) and text for 4. Hugging Face's Deep Research reproduction measured the effect inside one system.

Code adds its own failure mode: the reply must contain a parseable block. In the structured CodeAgent post (opens in a new tab), Hugging Face analysed 15,724 traces, found that 2.4% had a parsing error on the first call, and reported success rates of 42.3% with such an error against 51.3% without. Having the model return JSON that wraps the code avoids that parsing step. The post reports scores 2 to 7 percentage points higher on average for most capable models, and a cost for small ones that it calls the structure tax.

Worked example: A three-step CodeAgent run you can reproduce without an API key

This run replaces the language model with a scripted stand-in that replays three fixed replies, so you can reproduce it exactly, offline and for free. Three replies are enough to show a code action, a mistake that becomes feedback, and variables that persist. Install the library with pip install smolagents, then save this as warmest_city.py.

python
from smolagents import CodeAgent, ChatMessage, MessageRole, Model, tool
from smolagents.memory import ActionStep

TEMPERATURES_C = {"Oslo": 4.0, "Lagos": 31.0, "Lima": 19.5, "Pune": 28.5}


@tool
def get_temperature_c(city: str) -> float:
    """Returns the current temperature in degrees Celsius for one city.

    Args:
        city: Name of the city. Known cities are Oslo, Lagos, Lima and Pune.
    """
    if city not in TEMPERATURES_C:
        raise ValueError(f"Unknown city {city!r}. Known cities: {sorted(TEMPERATURES_C)}")
    return TEMPERATURES_C[city]


REPLIES = [
    """Thought: I need four readings. A loop and a dict will do.
<code>
cities = ["Oslo", "Lagos", "Lima", "Pune"]
temps = {city: get_temperature_c(city=city) for city in cities}
print(temps)
</code>""",
    """Thought: I will average the readings with numpy.
<code>
import numpy as np
average_c = float(np.mean(list(temps.values())))
</code>""",
    """Thought: numpy is not authorised, but statistics is. The dict temps is still in memory.
<code>
import statistics
warmest = max(temps, key=temps.get)
average_c = statistics.mean(temps.values())
average_f = average_c * 9 / 5 + 32
final_answer(f"{warmest} is warmest ({temps[warmest]} C). Average {average_c:.2f} C = {average_f:.2f} F.")
</code>""",
]


class ScriptedModel(Model):
    """Replays fixed replies instead of calling an LLM, so the run is repeatable offline."""

    def __init__(self, replies):
        super().__init__(model_id="scripted")
        self._replies = iter(replies)

    def generate(self, messages, stop_sequences=None, **kwargs):
        return ChatMessage(role=MessageRole.ASSISTANT, content=next(self._replies))


agent = CodeAgent(tools=[get_temperature_c], model=ScriptedModel(REPLIES), max_steps=5)
answer = agent.run(
    "Which of Oslo, Lagos, Lima and Pune is warmest, and what is the average of the four "
    "temperatures in Fahrenheit?"
)
print(answer)
print([type(step).__name__ for step in agent.memory.steps])
print([s.step_number for s in agent.memory.steps if isinstance(s, ActionStep) and s.error is not None])

Run python warmest_city.py. The library also prints every step to the console as it goes. Following the v1.26.0 source, the last three lines printed by the script should be:

text
Lagos is warmest (31.0 C). Average 20.75 C = 69.35 F.
['TaskStep', 'ActionStep', 'ActionStep', 'ActionStep']
[2]

Here is what happened, step by step.

StepCode the model wroteWhat the executor didWhat the model saw next
1A loop over four cities that collects readings in temps and prints itRan it: four tool calls, one dictThe printed dict {'Oslo': 4.0, 'Lagos': 31.0, 'Lima': 19.5, 'Pune': 28.5} and a last output of None
2import numpy as np, then np.meanRefused the import before running anythingAn error that says the import of numpy is not allowed and lists the authorised modules, plus a request to retry
3statistics, max, the conversion and final_answer(...)Ran it; final_answer raised and ended the runNothing, the run was over

The numbers check by hand. The readings sum to 4.0 + 31.0 + 19.5 + 28.5 = 83.0, so the mean is 83.0 / 4 = 20.75 degrees Celsius. In Fahrenheit that is 20.75 × 9 / 5 + 32 = 37.35 + 32 = 69.35. The warmest city is Lagos at 31.0.

Three things to notice. Step 3 used temps from step 1 without calling the tool again, because variables persist; a JSON agent can only imitate that by copying values through the prompt. The failed import cost one model call and no human effort, because the error told the model which modules it may use. And the maximum, the mean and the unit conversion were computed by Python, not estimated by the model.

A ToolCallingAgent handles the same task differently. It asks for four get_temperature_c calls, possibly in one reply because it can run several tool calls per step, and then does the maximum and the conversion in prose or needs extra tools for them. A capable code-writing model could even merge steps 1 and 3, since it needs to see no intermediate value, and finish in one step.

Verification: we ran the three snippets in plain Python with a stub final_answer and got the values above. The smolagents wiring (the ScriptedModel, the CodeAgent arguments, the default code tags and the console output) was checked against the v1.26.0 source and was not executed here, because the library was not installed.

Edge cases and limitations

Local execution restricts the code but does not isolate it
The allowlist stops obvious misuse such as importing os, yet the documentation says no local sandbox can ever be completely secure and gives the example of an authorised imaging library being used to fill a disk. The security policy treats escaping the local executor as out of scope, and CVE-2025-5120 was a sandbox escape in the local executor, with every release before 1.17.0 listed as affected. If the agent reads web pages or public input, use a remote executor and keep credentials out of its reach.
A remote executor changes what a tool can be
In the v1.26.0 source, a non-local executor receives each tool as generated source code and defines it inside the sandbox, so the tool body runs there. Tools must therefore be self-contained, with imports inside the function and no module-level globals or local files. The same source raises an exception when managed agents are combined with a remote executor, which matches the tutorial's note that snippet-only sandboxing does not support multi-agent systems.
A final-answer check with the wrong signature rejects every answer
In the v1.26.0 source each check is called as check(final_answer, memory, agent=agent) inside a try block, and any exception counts as a failed check. A function that does not accept the agent keyword, such as the two-parameter example in the guided tour, raises a TypeError, so every proposed answer is rejected and the agent spends its steps until max_steps. Define checks as (final_answer, memory, agent=None).
The 30 percent figure is a ceiling, not a forecast
The CodeAct paper reports up to 30% fewer actions on its multi-tool benchmark, and fewer turns for 12 of 17 models. The Open-source DeepResearch post restates the figure as an average. A strong model on a task with loops and joins can gain a lot, while a task that needs one tool call gains nothing. Measure steps and success on your own tasks before promising savings.
A capped run still returns text
When max_steps is used up, the v1.26.0 agent makes one more model call that writes an answer from memory. Unless return_full_result=True is set, the caller receives that text and cannot tell it from a finished answer. Request the full result, check its state for max_steps_error, and treat that state as a failure or a partial result.
Small models and the code format
Code actions need a model that follows the reply format and writes correct Python. The structured CodeAgent post advises models of roughly 32B parameters or more for its JSON-wrapped code and shows a 7B model producing broken syntax. The guided tour warns that a local Ollama model with the default context of 2048 tokens fails badly and suggests 8192. Start with a capable model, then try smaller ones.

When to use it, and when something simpler is enough

Use it when

  • The task needs logic over several tool results, such as loops, filters, joins or arithmetic, and you cannot list the combinations as separate tools in advance. Data analysis and multi-page research are typical.
  • Intermediate objects such as data frames, images or long lists must be kept and reused across steps without being copied through the prompt.
  • You can run the model's code in an isolated executor, and the content the agent reads, such as web pages or user messages, is handled as untrusted input that cannot reach your credentials.
  • You want a compact framework whose agent loop is in one readable source file, and you accept that the project calls its API experimental and subject to change.

Think twice when

  • Each action has side effects that must be validated field by field before it runs, such as payments or deletions. Schema-checked JSON tool calls with an approval step are easier to audit than arbitrary code.
  • You cannot provide an isolated executor and the agent will read untrusted content. The default local executor is documented as not a security boundary.
  • The workflow is already known. The library's own guide on building good agents says the best agentic systems are the simplest and advises reducing the number of model calls wherever you can.
  • You are limited to a small model that cannot hold the code format. Expect parse errors and wasted steps.

A simpler alternative. A fixed workflow in ordinary code with one or two model calls, such as a prompt chain or a router, or a single tool-calling round trip. Step up to a ToolCallingAgent when you need loop-until-done behaviour with schema-checked actions. Step up to a CodeAgent when tasks need loops, filters or arithmetic across tool results that you cannot enumerate as tools, and you can isolate the execution.

Key takeaways

  • A CodeAgent acts by writing a Python snippet that the framework extracts and runs, while a ToolCallingAgent writes a JSON tool call; both share the MultiStepAgent loop of memory, model call, action and observation.
  • Code can loop, keep variables across steps and combine tool results, so some tasks that need many JSON steps fit in one, but the measured gain varies by task and model.
  • Tools reach a CodeAgent as Python signatures built from the name, description, type hints and Args text, so those strings are prompt text and deserve the same care as the prompt.
  • The default local executor restricts imports and counts operations but is documented as not a security boundary; run untrusted work in a Docker, E2B, Modal or Blaxel executor, which receives tool code too.
  • Bound every run with max_steps and final_answer_checks that accept (final_answer, memory, agent), and check the run state, because a capped run still returns text.
  • Choose a CodeAgent when results must be combined with logic and execution can be isolated; choose a ToolCallingAgent or a fixed workflow when actions must be schema-checked or the flow is already known.

Example 1 of 5

Open-source DeepResearch, where code actions scored 55.15% on GAIA and JSON actions 33%

Hugging FaceDocumented in an engineering article

Hugging Face's post Open-source DeepResearch, published in February 2025, describes an open reproduction of OpenAI's Deep Research built on smolagents, with a live demo. The post explains why the team had the agent write its actions in code and reports the effect of switching to JSON. [14][13]

The problem

OpenAI had just released Deep Research, a system that browses the web, summarises content and answers questions. Hugging Face wanted an open version quickly and measured progress on GAIA, a benchmark whose questions need several dependent look-ups, multimodal reading and an answer in a fixed format. Such a question has no fixed number of steps: what to read next depends on what the last page said.

Where this topic fits

The core of the system is a CodeAgent. At each step the model writes Python that calls two tools taken from Microsoft Research's Magentic-One agent, a simple text-based web browser and a text inspector for reading file formats. The agent, not a fixed pipeline, decides which pages to open and how to combine what it reads before the next step.

How it is applied, step by step

  1. The agent receives a GAIA-style question that needs chained look-ups and an answer in a constrained format.
  2. At each step the model reasons briefly and writes a Python snippet that calls the browser or inspector tool.
  3. Because the action is code, one snippet can loop over several pages or files, keep results in variables and combine them, where a JSON agent would need one tool call per step.
  4. The printed output goes back into memory as the observation, and the loop repeats until the agent calls final_answer.
  5. The team ran the same setup with an agent that writes JSON actions and compared both on the GAIA validation set.

Why this approach fits

A research question is a branching search, and code gives the search its natural parts: a loop over candidates, a condition to filter them and a variable to hold what was found. The two tools came from an existing agent and changed little, so the comparison in the post varies the action format while the tools and tasks stay the same.

Limitation or tradeoff

The post calls itself a first step. Its browser reads text only, and the authors say full parity with OpenAI's system needs better browser interaction. The scores are on the validation set, one benchmark, reported by the system's authors, and the 33% figure is one JSON configuration, so it does not show how a tuned JSON agent would do.

What the sources document

  • The post reports 55.15% on the GAIA validation set, up from around 46% for Magentic-One, the previous best open framework, and attributes the improvement mostly to letting the agents write their actions in code. [14]
  • When the same setup was switched to a standard agent that writes actions in JSON instead of code, its performance dropped to 33% average on the validation set. [14]
  • The post quotes 67.36% on the GAIA validation set for OpenAI's Deep Research and says full parity would need better browser interaction than the current text-only web access. [14]
  • The agent's two tools, a simple text-based browser and a text inspector, were taken from Microsoft Research's Magentic-One agent and not changed much. [14]
  • Citing the CodeAct paper, the post says code actions need 30% fewer steps than JSON on average. The paper itself reports up to 30% fewer actions on its multi-tool benchmark. [14][13]

The facts above come from the cited sources. The steps and analysis in this example are our explanation of how they fit together.

Example 2 of 5

DABstep, the Adyen and Hugging Face data-analysis benchmark, ships a smolagents CodeAgent baseline

Adyen and Hugging FaceDocumented in an open-source project

DABstep (Data Agent Benchmark for Multi-step Reasoning) was released in February 2025 by Adyen and Hugging Face. The launch post points to Hugging Face's Inference API and smolagents as a low-cost way to run it, and the baseline code in the benchmark's Hugging Face Space builds a smolagents CodeAgent. [18][16][17]

The problem

Analysts at Adyen answer questions about payments data that mix large tables with long documentation. The benchmark turns more than 450 such tasks into questions with checkable answers. An agent must read files, filter and aggregate data and cross-check written rules over several steps. The benchmark also has to be cheap and safe for outsiders to run on their own machines.

Where this topic fits

The baseline agent is a CodeAgent with an empty tool list apart from the built-in final_answer. Its only capability is the Python it writes, limited to an allowlist of imports plus a wrapper that makes the built-in open function read-only. The model loads the data with the allowed libraries and prints only the intermediate results it needs.

How it is applied, step by step

  1. The harness downloads the context files (payments data, fee rules, merchant data and a manual) and reads each task.
  2. For each task it builds a CodeAgent (a thin subclass for the reasoning models) with an empty tool list, a LiteLLM-backed model, a step limit of 10 and the list of authorised imports.
  3. The model reasons step by step and writes Python that loads and aggregates the data and prints what it finds.
  4. The executor allows only the authorised imports, and open is replaced by a function that rejects any mode except read.
  5. The final answer is saved to a file; on the developer split the harness scores it locally, and answers for the full split are saved for submission to the leaderboard.
  6. Traces are collected through the OpenInference smolagents instrumentor and a local Phoenix server.

Why this approach fits

The payments file holds about 138 thousand transactions according to the launch post, far more than fits in a prompt. Code lets the model filter and aggregate with pandas and read back only the result, and a checkable factoid answer makes scoring automatic. An allowlist and a read-only open suit a benchmark that contributors run on their own machines, where accidents matter more than determined attackers.

Limitation or tradeoff

The baseline pins smolagents 1.3.0 and edits the executor's static tools after construction. In version 1.26.0 that attribute is unset until a run starts, so the code needs the adaptation shown above. The read-only wrapper guards one route to the file system; the authorised glob, pandas and os modules offer others, so it prevents accidents and is not isolation. The paper treats its results as a lower bound from standardised prompts, and its best agent reached only 14.55% on hard tasks. See Evaluating Agents for how such benchmarks are used.

What the sources document

Example 3 of 5

Hugging Face's Computer Agent Space, a smolagents CodeAgent that drives a Linux desktop with click(x, y) calls

Hugging FaceDocumented in an open-source project

The Hugging Face Space smolagents/computer-agent is a demo in which an agent operates a remote Linux desktop from a text task. Its source files define the agent, its tools and the screenshot loop. When we accessed the Space it was paused, so we read the source rather than running it. [19][20][6]

The problem

A graphical desktop has no API: the agent can only look at screenshots and send mouse and keyboard events. The demo must turn a vision-language model's view of the screen into precise actions, keep old screenshots from filling the context, and give each user a disposable desktop so that a wrong click or a hostile web page cannot touch a real machine.

Where this topic fits

A subclass of CodeAgent, E2BVisionAgent, registers desktop actions as tools. Each step's code action is then a short call such as click(254, 308). A step callback captures a screenshot after every step and stores it as the next observation, and the desktop itself runs in a remote E2B sandbox.

How it is applied, step by step

  1. The app creates an E2B desktop sandbox for the user's session, with a 300-second timeout in the app code, and builds a fresh agent for each task, passing max_steps=20 although the class default is 200.
  2. The system prompt asks the model to write short sections (goal, what it sees, reflection) and then its action as a Python code block.
  3. The model's code calls a desktop tool, which moves the mouse, clicks or types inside the sandbox and returns a short text confirmation.
  4. The step callback waits briefly, takes a screenshot, draws a marker where the last click landed, and attaches the image to the step.
  5. The callback clears images from earlier steps so that only the latest screenshot stays in memory.
  6. If the same code ran twice in a row, the callback adds a warning to the observation, and the app's cleanup code kills sandboxes that have been idle past the timeout.

Why this approach fits

A GUI offers no structured interface, so the useful vocabulary is a handful of low-level actions. Code actions let the model call them as ordinary functions with computed arguments, while the framework's step callback supplies what code cannot, a fresh view of the screen after every step. Running the desktop in a disposable sandbox bounds the damage from a mistake or a malicious page.

Limitation or tradeoff

The Space pins smolagents 1.15.0 and calls step_callbacks.append, which the callback registry in version 1.26.0 does not have; the supported call is register. The app's own notes say that virtual machines can be blocked by a captcha and that a stuck agent needs a page refresh, and a code comment says the agent is rebuilt for every task because the vision model gets confused by old history. The agent is built without an executor setting, so its snippets run under the default local executor in the Space's own process; the E2B sandbox holds the desktop, not the interpreter. The sources we read give no accuracy figures for the demo.

What the sources document

  • The Space's source defines E2BVisionAgent as a subclass of CodeAgent with max_steps defaulting to 200, and registers desktop tools including click, right_click, double_click, move_mouse, type_text, press_key, scroll, wait, open_url, go_back, drag_and_drop and find_on_page_ctrl_f. [19]
  • A callback after each step saves a screenshot, draws a marker at the last click, removes screenshots of earlier steps from memory and adds a warning to the observation when the same action is repeated. [19]
  • The app's welcome text says the agent is powered by smolagents and Qwen-VL, linked to Qwen2.5-VL-72B-Instruct, and the code creates an E2B desktop sandbox per session with a timeout of 300 seconds. [20]
  • The system prompt in the source tells the model to give its action as a Python code block such as click(254, 308). [19]
  • The smolagents API reference lists step_callbacks as callbacks that are called at each step. [6]

Langfuse tracing for smolagents, inspecting a manager CodeAgent and its managed search agent

LangfuseDocumented in official docs

Langfuse's integration page and the smolagents tutorial Inspecting runs with OpenTelemetry document the same setup: switch on the OpenInference SmolagentsInstrumentor and send the spans to Langfuse over OpenTelemetry. [23][7]

The problem

The smolagents tutorial says agent runs are hard to debug. They are unpredictable by design, multi-step agents fill a console with logs, and most errors are mistakes the model corrects on its own at the next step. It concludes that recording runs with instrumentation is necessary in production, so teams can inspect and monitor them later.

Where this topic fits

Observability wraps the agent rather than living in it. One instrumentation call runs before the application code, the agents are built and run as usual, and each run appears in Langfuse as a trace. See LLM and Agent Observability and the Langfuse topic for the wider picture.

How it is applied, step by step

  1. Install langfuse, smolagents with the telemetry extra and the OpenInference smolagents instrumentor.
  2. Set the Langfuse public and secret keys and the host as environment variables, then create the client and check that authentication works.
  3. Call SmolagentsInstrumentor().instrument() before any agent is created or run.
  4. Build the agents as usual; the documented example has a manager CodeAgent that calls a managed ToolCallingAgent named search_agent with web search and page-visiting tools.
  5. Run the manager. Each run is sent to Langfuse as a trace.
  6. Open the trace to see where the manager delegated, what the steps did and where they failed or looped.

Why this approach fits

A code agent's most useful debugging artefact is the code it wrote at each step, and a trace keeps that next to the observation it produced and the model call that wrote it. Because smolagents adopted OpenTelemetry instead of a private log format, any compatible backend can read a run, and a hierarchy of managed agents can be followed in the trace, as the tutorial shows for Phoenix.

Limitation or tradeoff

Traces contain prompts, tool arguments and generated code, which can include sensitive data, so check what the backend stores and who can read it. The two official pages differ in small ways at the time of access: the smolagents tutorial sets LANGFUSE_HOST while Langfuse's page sets LANGFUSE_BASE_URL, and the install lines list different packages. Pin versions and test the setup rather than copying either page.

What the sources document

  • The tutorial gives Phoenix, MLflow and Langfuse as example backends and says other OpenTelemetry-compatible platforms could be used. [7]

4Common mistakes

  1. Running a CodeAgent that reads untrusted content with the default local executor.

    Why it causes problems
    The local interpreter restricts imports and counts operations, but the project's documentation and security policy say it is not a security boundary, and releases before 1.17.0 had a sandbox escape. A web page or user message that steers the model can lead to code running with your process's privileges and credentials.
    How to recognise it
    The agent browses the web or accepts public input, executor_type is left at its default of local, and the process has cloud credentials or file access in its environment.
    How to fix it
    Set executor_type to docker, e2b, modal or blaxel, run with least privilege and no secrets in reach of the code, restrict network access, and keep smolagents up to date.

  2. Authorising broad imports to silence an import error.

    Why it causes problems
    Each authorised module is a capability the generated code can use, such as file access, process control or network access. The documentation warns that even an imaging library can be used to fill a disk, and a wildcard authorises every installed package.
    How to recognise it
    additional_authorized_imports contains a star, os or a whole package where one function would do, or the log prints the caution about authorising all imports.
    How to fix it
    Authorise the smallest set of modules, name submodules explicitly (for example numpy.random), and wrap risky capabilities in a tool that validates its inputs instead of authorising the module itself.

  3. Writing tools with vague descriptions, missing argument docs or silent failures.

    Why it causes problems
    The description, argument docs and types are copied into the system prompt, so the model calls the tool only as well as the text allows. A tool that fails with a bare exception or returns an unclear string leaves the model guessing, and it spends steps on retries.
    How to recognise it
    Runs repeat the same failing call with slightly different arguments, the tool receives dates or places in formats you did not expect, or the decorator raises a type-hint error because the return type is missing.
    How to fix it
    Add type hints for every input and the return value, an Args section that states formats and allowed values, errors that say what was wrong and what is valid, and print statements with useful detail.

  4. Treating whatever agent.run returns as a finished, validated answer.

    Why it causes problems
    A run that reaches max_steps still returns text from one more model call, and a final answer can have the wrong type or format. Downstream code then consumes a guess as if it were a result.
    How to recognise it
    Prose where a number was expected, runs that always use exactly max_steps steps, or a full result whose state is max_steps_error.
    How to fix it
    Use return_full_result=True and check the state, add final_answer_checks with the signature (final_answer, memory, agent=None) that validate type and range, and handle the failure state explicitly.

  5. Reusing one agent object for unrelated tasks or for different users.

    Why it causes problems
    With reset=False the memory carries over, so earlier steps, variables and images stay in the context and cost grows. Even with the default reset=True, the v1.26.0 source clears only the memory: the executor's variables and the agent's state dictionary are not cleared, so one task's data can still be visible to the next task's code. The Computer Agent Space rebuilds its agent for every task.
    How to recognise it
    Input token counts that climb from task to task, answers that mention earlier tasks, variables from a previous run appearing in new code, or a service in which different users share one agent object.
    How to fix it
    Create a new agent, and so a new executor, for each independent task or user. Keep reset=False for genuine multi-turn conversations only, and clean up remote sandboxes with the context manager.

Exercise 1

Reject an incomplete final answer with a final_answer check

CodingIntermediateAbout 30 min (estimate)Hypothetical scenario

Start from the worked example's warmest_city.py. Its scripted model needs no API key, so the whole exercise runs offline. You will add a final-answer check, watch it reject a first attempt, and then see what a wrong check signature does.

Starter for the check:

python
def mentions_fahrenheit(final_answer, memory, agent=None) -> bool:
    ...  # accept only answers that state a Fahrenheit value
  1. Pass the check to the agent with final_answer_checks=[mentions_fahrenheit].
  2. Replace REPLIES with two replies. The first calls final_answer("Lagos is warmest") straight away. The second recomputes everything and ends with the full answer string from the worked example.
  3. Change ScriptedModel to use next(self._replies, "No scripted reply left."), so that it never runs dry.
  4. Run it, then run it again with a check that takes one parameter, def check(final_answer):, with max_steps=2 and return_full_result=True.

Requirements

  • The check accepts an answer only if its text contains " F", and has the signature (final_answer, memory, agent=None).
  • The first scripted reply is rejected by the check and the second is accepted.
  • The script prints the answer, the list of step type names and the step numbers whose error is not None.
  • For the one-parameter run the script prints the result state and output, and you explain in one sentence why no answer was ever accepted.

Expected behaviour

With the three-parameter check the script prints Lagos is warmest (31.0 C). Average 20.75 C = 69.35 F., then ['TaskStep', 'ActionStep', 'ActionStep'], then [1]. Step 1 ran final_answer, the check rejected the text, and the loop went on. With the one-parameter check every answer is rejected, because the framework passes the agent as a keyword. Both steps fail, the cap is reached, and the script prints max_steps_error | No scripted reply left. followed by [1, 2, 3], where step 3 is the record added when the cap is hit.

Hint 1

The check is called as check(final_answer, memory, agent=agent). Any exception inside it, including a TypeError from an unexpected keyword, counts as a failed check.

Hint 2

A rejected check is stored as an error on that ActionStep, which is why step.error is not None for step 1.

Hint 3

In the second run, create a fresh ScriptedModel, because the first one has used up its replies.

Show solution

Only the parts that change from the worked example are shown. TEMPERATURES_C, the tool and the imports stay as they were.

python
REPLIES = [
    """Thought: I already know the answer.
<code>
final_answer("Lagos is warmest")
</code>""",
    """Thought: The check wants a Fahrenheit value, so I compute the average.
<code>
import statistics
temps = {city: get_temperature_c(city=city) for city in ["Oslo", "Lagos", "Lima", "Pune"]}
warmest = max(temps, key=temps.get)
average_c = statistics.mean(temps.values())
average_f = average_c * 9 / 5 + 32
final_answer(f"{warmest} is warmest ({temps[warmest]} C). Average {average_c:.2f} C = {average_f:.2f} F.")
</code>""",
]


# In ScriptedModel.generate, change the content argument to:
#     content=next(self._replies, "No scripted reply left.")


def mentions_fahrenheit(final_answer, memory, agent=None) -> bool:
    return " F" in str(final_answer)


def one_parameter_check(final_answer) -> bool:
    return " F" in str(final_answer)


TASK = "Which of Oslo, Lagos, Lima and Pune is warmest, and what is the average of the four temperatures in Fahrenheit?"


def failing_steps(agent):
    return [s.step_number for s in agent.memory.steps if isinstance(s, ActionStep) and s.error is not None]


agent = CodeAgent(tools=[get_temperature_c], model=ScriptedModel(REPLIES), max_steps=5,
                  final_answer_checks=[mentions_fahrenheit])
print(agent.run(TASK))
print([type(step).__name__ for step in agent.memory.steps])
print(failing_steps(agent))

agent = CodeAgent(tools=[get_temperature_c], model=ScriptedModel(REPLIES), max_steps=2,
                  final_answer_checks=[one_parameter_check])
result = agent.run(TASK, return_full_result=True)
print(result.state, "|", result.output)
print(failing_steps(agent))

Why it behaves this way. The framework calls each check as check(final_answer, memory, agent=agent) and turns any exception into a failed check. The first reply is rejected by the three-parameter check, so step 1 carries an error and the model gets another try; the second reply passes. The one-parameter function raises a TypeError on the first call, so it rejects every answer, including the correct one. After two steps the cap is reached, the agent makes one more model call (which the scripted model answers with its spare text), and the state is max_steps_error. We checked this behaviour against the v1.26.0 source and did not execute the script, because the library was not installed in our environment.

Check your answer

  • Does step 1 of your first run show an error even though final_answer was called?
  • Does your first run print the full answer with 69.35 F, and exactly two ActionStep entries?
  • Can you explain why a check defined with one parameter rejects a correct answer?
  • Does the second run report max_steps_error rather than a normal success state?
