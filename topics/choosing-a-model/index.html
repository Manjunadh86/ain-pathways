Choosing a Model and Provider

Choosing a model and provider means deciding which language model will handle a task and which company or server will run it for you. The decision is made by testing a short list of candidates on your own examples and keeping the cheapest one that meets your quality, speed and data requirements.

1Overview

Why it matters

The same request can cost a hundred times more on one model than on another. On 10 October 2026 the list prices of current text models from three large vendors ranged from $0.10 to $10 per million input tokens. The expensive model may also take several seconds longer to answer, and it is not guaranteed to be better at your particular task. Teams that pick by reputation or from a public leaderboard can find out in production: the bill is ten times the estimate, the feature feels slow, or users report mistakes that a short test would have shown.

The choice also fixes things that are hard to change later: where your users' data is processed, which licence governs what you build, how much notice you get before a version is retired, and how much work it is to move elsewhere. New models arrive every few months, so this is a decision you will repeat. Engineers, product managers and forward deployed engineers all need a method they can run again and defend to a customer or a finance team.

Key terms

Closed model
A model whose weights are not released. You can use it only through the maker's API and products or through a cloud platform that resells it.
Open-weight model
A model whose trained weights can be downloaded and run on hardware you choose, under a licence that states what you may do with them.
Provider
The company or system that runs the model and bills you for it. It can be the model's maker, a cloud platform, an inference service or your own servers.
Reasoning model
A model that generates reasoning tokens to work through a problem before it writes the visible answer. Providers usually hide the reasoning text or return only a summary, but the tokens are still billed.
Reasoning effort
A request setting that tells a reasoning model how much to think. Lower effort is faster and cheaper, and higher effort is more thorough.
Time to first token (TTFT)
The time between sending a request and receiving the first token of the response.
Output speed
The average number of tokens received per second once the first token has arrived.
Eval set
A collection of example inputs from your own task, each with a correct answer or a rule for deciding whether a response is good enough.
Margin of error
The range around a measured score within which the true score plausibly lies, given how few examples were tested.
Quantization
Storing a model's weights with fewer bits each to save memory and cost, sometimes with a small loss of quality.

2Explanation

Introduction

In Tokens and Context Windows you saw that a model reads and writes tokens, that its context window limits how much it can read at once, and that APIs charge for every token. Those three facts turn model choice into something you can work out with a small test and some arithmetic.

Think about choosing a vehicle for a delivery business. Nobody asks which vehicle is best. They ask what has to be carried, how far, how quickly and at what cost per trip. A bicycle courier beats a truck for an envelope across town and loses badly for a piano. Language models are the same. A small model that answers in half a second for a hundredth of the price is the right tool for sorting support tickets and the wrong one for planning a database migration.

There are two choices to make, and they are separate:

  • The model is a particular set of trained weights with particular abilities, such as Claude Sonnet 5.5, GPT-6 Luna, Gemini 3.8 Flash or Llama 3.3.
  • The provider is whoever runs those weights for you, in a given place, at a given price and under given data terms. Claude models, for example, are sold by Anthropic directly and also through Amazon Bedrock, Google Cloud and Microsoft Foundry, as Anthropic's models overview (opens in a new tab) shows. An open-weight model can be rented from many companies or run on your own hardware.

A sound selection follows the same four steps every time:

  1. Write the requirements as numbers: the quality you need, the response time you can accept and the amount you can spend.
  2. Remove every candidate that breaks a hard constraint, such as a rule that data must stay in one region.
  3. Test the few that remain on examples from your own task.
  4. Keep the cheapest candidate that passes, and repeat the test when a model, a price or a requirement changes.

The rest of this lesson supplies what each step needs: the difference between closed and open-weight models, what reasoning models change, the arithmetic of capability, latency and price, the provider features that can tip a decision, and a fair way to compare candidates. Model names and prices are quoted as listed on 10 October 2026. They will change. The method will not.

How it works

Closed and open-weight models

A closed model's weights never leave its maker. You reach it through an API or through a cloud platform that resells it. The Claude, GPT and Gemini families work this way. An open-weight model's trained weights are published for download, so anyone with suitable hardware can run it. OpenAI's gpt-oss-120b (opens in a new tab) is one example. Its model card says it is released under the Apache 2.0 licence and runs on a single 80 GB GPU, and that the smaller gpt-oss-20b runs within 16 GB of memory.

Two cautions apply to the word "open":

  • Open-weight is not open source. The Open Source Initiative (opens in a new tab) describes open weights as the final weights and biases of a trained network, released without the training code or full information about the training data. You can run and fine-tune such a model, but you cannot fully study or rebuild it.
  • The licence decides what you may do. Apache 2.0 permits commercial use. The Llama 3.3 Community License (opens in a new tab) also grants broad rights but adds conditions: products must display "Built with Llama", a distributed model derived from it must have a name that begins with "Llama", and a company with more than 700 million monthly active users must request a separate licence from Meta.

Open weights add ways to run a model. The four common arrangements differ mainly in who operates the hardware and where your prompts travel.

Running Open-Weight Models covers the last two rows in practice.

Reasoning and standard models

A reasoning model writes reasoning tokens before its visible answer, working through the problem step by step. OpenAI's reasoning guide (opens in a new tab) states three facts that matter for selection: reasoning tokens are not returned by the API, they occupy space in the context window, and they are billed as output tokens. Its example response reports 1,186 output tokens, of which 1,024 were reasoning. You would pay for 1,186 tokens and read 162. Anthropic's thinking guide (opens in a new tab) says the same of Claude: the tokens spent thinking are billed as output tokens even when the text is not returned, and they count toward max_tokens. On current Claude models the thinking text is omitted unless you ask for a summary.

OpenAI's best-practices guide (opens in a new tab) calls its o-series reasoning models "the planners", suited to complex problems with ambiguous information where accuracy and reliability matter most, and its lower-latency GPT models "the workhorses", suited to well-defined tasks where speed and cost matter more than perfect accuracy. Its examples use earlier model names, but the trade-off still applies.

In current lineups this is mostly a dial on one model. OpenAI's reasoning.effort runs from none to max depending on the model, and Anthropic's effort parameter (opens in a new tab) takes low, medium, high, xhigh or max (not every model offers xhigh). Not every setting exists everywhere: GPT-6 Astra and GPT-6.1 Sol do not accept none, and thinking cannot be turned off in Claude Opus 5.5. Anthropic's model selection guide (opens in a new tab) says that tuning effort is often a better lever than switching models.

A workable rule: use low effort for extraction, classification, routing and formatting, and raise it for ambiguous instructions, multistep planning and debugging. Then confirm on your own examples, because each model calibrates its levels differently. Reasoning Models and Thinking Budgets goes deeper.

Capability, latency and price

More capable models are usually slower and cost more. The spread is wide: on these published price lists the top tier costs 100 times as much per token as the smallest.

With prices in dollars per million tokens, one request costs:

cost=Tin Pin+(Treason+Tanswer) Pout1,000,000\text{cost} = \frac{T_{\text{in}} \, P_{\text{in}} + (T_{\text{reason}} + T_{\text{answer}}) \, P_{\text{out}}}{1{,}000{,}000}cost=1,000,000Tin​Pin​+(Treason​+Tanswer​)Pout​​

Every model in the chart charges five times as much for an output token as for an input token, so reasoning tokens and long answers dominate the bill sooner than you might expect.

Response time has two parts. Artificial Analysis (opens in a new tab) defines time to first token (TTFT) as the time from sending a request to receiving the first token, and output speed as the average number of tokens per second after that. For reasoning models it also reports the time to the first answer token, because the user sees nothing while the model thinks. A useful estimate is:

response time≈TTFT+Treason+Tansweroutput speed\text{response time} \approx \text{TTFT} + \frac{T_{\text{reason}} + T_{\text{answer}}}{\text{output speed}}response time≈TTFT+output speedTreason​+Tanswer​​

The estimate assumes reasoning and answer tokens arrive at the same speed. If a provider hides its reasoning, the wait before the first visible token already contains the thinking time, so do not count those tokens twice. When in doubt, time whole requests on your own inputs.

Two things make a price list misleading on its own:

  • A token is not the same unit in every model. Anthropic's pricing page (opens in a new tab) notes that the tokenizer used by Claude 4.7 and later models produces roughly 30% more tokens for the same text than the earlier one.
  • Price per token is not cost per task. In an Anthropic benchmark (opens in a new tab) that searched a 21.6-million-token code corpus for defects, Claude Fable 5.1 cost between $468 and $552 per episode across three effort settings. Lower effort did not cut the bill, because reading the corpus was the expense and only the accuracy moved.

So measure tokens and dollars per completed task on your own inputs. LLM Cost and Latency Optimization covers how to reduce them afterwards.

Evaluating candidates on your own task

Public benchmarks help you build a shortlist. They cannot tell you which model is best at your task, with your prompts and your data. Anthropic's selection guide calls a good evaluation set the most important step in the process, and its evaluation guide (opens in a new tab) gives three design rules: mirror your real task distribution including edge cases, grade automatically wherever you can, and prefer many automatically graded cases to a few hand-graded ones.

  1. Collect at least a hundred real inputs, including awkward ones, and record the correct output or a pass rule for each.
  2. Run every candidate on the same inputs with the same prompt. Record the score, the token counts including reasoning tokens, and the response time.
  3. Check that the gap between two candidates is larger than the margin of error.
  4. Apply the requirements and keep the cheapest candidate that passes all of them.

For a pass rate ppp measured on nnn cases, the 95% margin of error is approximately:

margin≈1.96p(1−p)n\text{margin} \approx 1.96 \sqrt{\frac{p(1-p)}{n}}margin≈1.96np(1−p)​​

With p=0.9p = 0.9p=0.9 and n=100n = 100n=100 the margin is 5.9 percentage points, so scores of 90% and 93% on a hundred cases do not separate two models. A gap smaller than one margin is never enough to prefer a candidate. A larger gap is a first sign, and the firmer check is to read the cases on which the two disagree. The formula is only a rough guide when passes or failures number fewer than about ten, such as a 98% pass rate on a hundred cases.

Anthropic describes two starting points. Start efficiency-first, with the smallest model, when volume is high or latency is tight, and move up only where it fails. Start capability-first, with a strong model, when the task is hard, and move down once it works. Both paths end at the same test. Evaluating LLM Applications covers how to build the eval set itself.

Worked example: Choosing a model for a ticket-triage service that handles 40,000 tickets a day

A help desk wants every incoming ticket assigned to one of eight queues. The model reads the ticket and returns a short JSON object with the queue name. The team writes three requirements before looking at any model:

  • Quality: at least 90% of queue labels correct on an eval set of 400 past tickets that staff have already labelled.
  • Response time: no more than 3.0 seconds for a typical ticket, because the label is shown while the customer is still on the form.
  • Cost: no more than $150 a day at 40,000 tickets.

They shortlist three price tiers and try two effort settings on the cheaper ones. The prices are real list prices on 10 October 2026: $0.10 and $0.50 per million input and output tokens (Claude Haiku 5.5 and GPT-6 Luna), $2 and $10 (Claude Sonnet 5.5 and GPT-6.1 Sol), and $10 and $50 (Claude Fable 5.1 and GPT-6 Astra). The eval results, token counts and speeds below are invented for this example. A real run on your own tickets would produce your own.

Save this as pick_model.py. It needs only the Python standard library.

python
import math

REQUESTS_PER_DAY = 40_000
INPUT_TOKENS = 1_200            # instructions + one ticket
ANSWER_TOKENS = 60              # the JSON reply
EVAL_SIZE = 400                 # labelled tickets in the eval set
MIN_ACCURACY = 0.90
MAX_LATENCY_S = 3.0
MAX_COST_PER_DAY = 150.0
Z_95 = 1.96                     # 95% interval, normal approximation

# name, $ per million input tokens, $ per million output tokens,
# reasoning tokens per request, correct answers out of 400,
# seconds to first token, output tokens per second
CANDIDATES = [
    ("small, low effort",   0.10,  0.50,   0, 348, 0.35, 180),
    ("small, high effort",  0.10,  0.50, 360, 366, 0.35, 180),
    ("mid, low effort",     2.00, 10.00,   0, 362, 0.60, 110),
    ("mid, high effort",    2.00, 10.00, 150, 372, 0.60, 110),
    ("top, default effort", 10.00, 50.00, 300, 378, 1.20,  60),
]


def evaluate(candidate):
    name, in_price, out_price, reasoning, correct, ttft, speed = candidate
    billed_output = reasoning + ANSWER_TOKENS          # reasoning is billed as output
    cost = (INPUT_TOKENS * in_price + billed_output * out_price) / 1_000_000
    accuracy = correct / EVAL_SIZE
    margin = Z_95 * math.sqrt(accuracy * (1 - accuracy) / EVAL_SIZE)
    latency = ttft + billed_output / speed
    failures = []
    if accuracy < MIN_ACCURACY:
        failures.append("accuracy")
    if latency > MAX_LATENCY_S:
        failures.append("latency")
    if cost * REQUESTS_PER_DAY > MAX_COST_PER_DAY:
        failures.append("cost")
    return {"name": name, "accuracy": accuracy, "margin": margin, "latency": latency,
            "cost": cost, "per_day": cost * REQUESTS_PER_DAY, "failures": failures}


results = [evaluate(candidate) for candidate in CANDIDATES]
print(f"{'candidate':<21}{'accuracy':>9}{'+/-':>6}{'latency':>9}{'$/request':>11}{'$/day':>10}  verdict")
for r in results:
    verdict = "pass" if not r["failures"] else "fail: " + ", ".join(r["failures"])
    print(f"{r['name']:<21}{r['accuracy']:>9.1%}{r['margin']:>6.1%}{r['latency']:>8.2f}s"
          f"{r['cost']:>11.5f}{r['per_day']:>10.2f}  {verdict}")

passing = [r for r in results if not r["failures"]]
best = min(passing, key=lambda r: r["per_day"])
print(f"\nCheapest candidate that passes every requirement: {best['name']}")

needed = math.ceil(Z_95 ** 2 * best["accuracy"] * (1 - best["accuracy"]) / 0.015 ** 2)
print(f"Eval cases needed for a +/-1.5 point margin at {best['accuracy']:.1%}: {needed}")

Check the winning row by hand. Billed output is 360 reasoning tokens plus 60 answer tokens, which is 420. The cost is (1,200 × 0.10 + 420 × 0.50) / 1,000,000 = (120 + 210) / 1,000,000 = $0.00033 per ticket, and 40,000 tickets cost $13.20. The response time is 0.35 + 420 / 180 = 2.68 seconds. Accuracy is 366 / 400 = 91.5%, and the margin is 1.96 × √(0.915 × 0.085 / 400) = 0.027, or 2.7 points.

What the table shows:

  • The cheapest setting fails on quality. Raising effort on the same small model gains 4.5 points for $7.20 more per day. It also adds two seconds, because 360 reasoning tokens have to be generated before the answer appears.
  • Two candidates pass, so price decides. The mid tier at low effort is faster but costs nine times as much. Nothing in the requirements pays for that speed.
  • The most capable model is the worst choice here. It scores three points higher than the winner for 91 times the cost, and it is too slow for the form.
  • The result is not yet certain. 91.5% with a margin of 2.7 points means the true accuracy could lie anywhere from 88.8% to 94.2%, which includes values below the 90% bar. The same margin means the winner cannot be told apart from the mid tier's 93.0%.

The honest conclusion is to choose the small model at high effort, keep the mid tier at low effort as the fallback, and grow the eval set towards the 1,328 cases the script reports before treating the 90% bar as met.

Edge cases and limitations

A token is a different size in different models
Anthropic's pricing page says the tokenizer in Claude 4.7 and later models produces about 30% more tokens for the same text than the tokenizer in earlier models. Two models with the same price per million tokens can therefore charge different amounts for the same document. Compare candidates by sending the same inputs to each and reading the token counts from the usage field of the responses.
The headline price can have conditions attached
Some models are priced by prompt length. On the access date Claude Haiku 5.5 charged 0.10 USD per million input tokens for prompts up to 100,000 tokens and 0.50 USD above that, and Gemini 3.1 Pro Preview charged 2 USD up to 200,000 tokens and 4 USD above. A price can also be time-limited: Gemini 3.8 Flash was listed at 0.75 USD per million input tokens through 31 December 2026 and 1.50 USD afterwards. Price each request at the rate for its own length, and note the date of any scheduled change in your cost estimate.
Reasoning can use up the output limit before any answer appears
Reasoning tokens count against the output limit. OpenAI's reasoning guide says a response that reaches max_output_tokens comes back with status incomplete, and suggests reserving at least 25,000 tokens for reasoning and output while experimenting. Anthropic's effort page says max_tokens is a hard limit on thinking plus response text. Because reasoning comes first, a limit reached during reasoning can leave no visible answer at all. Raise the limit when you raise effort, and check the status or stop reason before parsing.
An alias can change the model underneath you
Google's models page says a latest alias is hot-swapped with every new release, with two weeks' notice by email for breaking changes, and that preview models are deprecated with at least two weeks' notice. A feature that passed your eval last month may be running on a different model today. Use a specific stable version in production and re-run the eval set before moving to a new one.
The same open-weight model is not identical on every host
Hosts may serve an open-weight model at different quantization levels. OpenRouter's routing documentation lists levels from int4 to fp32 and warns that quantized models may exhibit degraded performance for certain prompts. Supported parameters and context length can differ too. Evaluate on the provider and configuration you will actually use, and filter out quantization levels you have not tested.
An effort setting does not transfer from one model to the next
Anthropic's effort page says the levels on Claude Sonnet 5.5 were recalibrated, so a level does not produce the same amount of thinking as on Claude Sonnet 5. It also notes that Claude Opus 5.5 defaults to medium where Claude Opus 5 defaulted to high, so a request that omits effort runs one level lower after an upgrade. Set effort explicitly and repeat the effort sweep on your eval set for every new model.

When to use it, and when something simpler is enough

Use it when

  • You are starting a feature that will call a model thousands of times a day or more, so that small differences in price and response time add up.
  • A new model, a price change or a retirement notice arrives for a model you already run in production.
  • A requirement changes, for example a tighter response-time target, a data-residency rule, much longer inputs or a new language.
  • The bill or the response time has grown, and you suspect that a smaller model or a lower effort setting would still pass.

Think twice when

  • You are still finding out whether the idea works at all. Use a strong model, get one good result, and leave optimisation until there is something to optimise.
  • Usage is tiny, such as a script you run a few times a week. The time spent evaluating would cost more than any saving.
  • The task does not need a language model. A rule, a regular expression or a small trained classifier is cheaper, faster and easier to test when it does the job.

A simpler alternative. Take the default model the provider recommends for your kind of workload, write ten test inputs and read the answers yourself. This stops being enough when a wrong answer has a real cost, when the volume makes the bill noticeable, or when you can no longer tell by eye whether a cheaper model is doing as well.

Key takeaways

  • Start from written requirements for quality, response time, cost and data handling, then choose the cheapest model that passes all of them on your own examples.
  • The model and the provider are separate choices: the same weights can come with different prices, speeds, data terms and lifecycles depending on who runs them.
  • Open-weight models can be downloaded and run anywhere their licence allows, which buys control and privacy at the cost of running the hardware yourself or checking how a host serves them.
  • Reasoning tokens are hidden by default, billed as output and generated before the answer, so more reasoning effort usually means better results on hard tasks, a higher bill and a slower response.
  • Cost per request is input tokens times the input price plus all output tokens times the output price, and it should be compared per completed task because tokens differ between models.
  • A score from a small eval set has a margin of error of several points, so check that the gap between two candidates is larger than that margin before choosing between them.

Example 1 of 5

GitHub Copilot's model picker, grouped by coding task and billed by token price

GitHubDocumented in official docs

GitHub Copilot lets a developer choose among models from several AI companies for chat and agent work. Three GitHub Docs reference pages describe the choice: AI model comparison, Supported AI models in GitHub Copilot, and Models and pricing for GitHub Copilot. [17][18][19]

The problem

GitHub's supported-models page lists more than two dozen generally available models from six companies, and which of them a user sees depends on the Copilot plan and where Copilot is used. GitHub states that the model chosen affects the quality and relevance of Copilot's responses, and that models consume credits at different rates. Without guidance, a user could pick the largest model for everything, which spends credits and time on one-line questions, or stay on the smallest and get weak answers to hard problems.

Where this topic fits

The choice is made in the model picker before a chat or agent session. GitHub's guidance sits one step earlier: decide what kind of task this is, then choose from the group of models suited to it, or hand the decision to the Auto option.

How it is applied, step by step

  1. GitHub's comparison page assigns each model a task area, such as general-purpose coding and writing, fast help with simple or repetitive tasks, deep reasoning and debugging, or agentic software development.
  2. For a quick edit, a syntax question or a small utility function, the page points to the fast group, which includes GPT-5.6 Luna and Claude Haiku 4.5.
  3. For a bug that spans several files, a large refactor or an architecture decision, it points to the deep reasoning group, which includes GPT-5.5, GPT-5.6 Sol and Claude Sonnet 4.6.
  4. Each group's section says when to move to the other one: up for complex refactoring and multi-step logic, down for fast iteration and lightweight tasks.
  5. Cost follows the same ladder. Tokens are priced per model and converted into AI credits, so the same conversation uses more credits on a model with a higher token price.
  6. A user who does not want to decide can select Auto, which picks a model from availability and task complexity.

Why this approach fits

Coding help ranges from a one-line syntax question to a bug that crosses ten files, and no single point on the capability, speed and price scale suits both. Grouping models by task instead of by vendor is the "start from the requirement" rule built into a product: the user classifies the work first and only then looks at model names. Billing by token price keeps the cost of choosing a larger model visible.

Limitation or tradeoff

The groups are GitHub's editorial guidance, not measurements on your repository. The boundaries are soft: GPT-5 mini appears under both general-purpose work and deep reasoning. The lineup moves: GitHub notes that model availability is subject to change, and the comparison table links no model card yet for GPT-6.1 Sol and Claude Sonnet 5.5 although the pricing page already lists both. Auto removes the decision and with it your control over which model answered. A team with a fixed budget still has to watch its own credit usage.

  • The page describes the models for fast help with simple or repetitive tasks as optimised for speed and responsiveness and lists GPT-5.6 Luna and Claude Haiku 4.5 among them. It describes the deep reasoning and debugging models as designed for tasks that require step-by-step reasoning, complex decision-making or high-context awareness, and lists GPT-5 mini, GPT-5.5, GPT-5.6 Sol and Claude Sonnet 4.6.   • The same page says that different models consume AI credits at different rates based on their token pricing, and that the Auto option automatically selects a model based on model availability and task complexity. [17]
  • The pricing page states that each token is priced based on the model used and converted into AI credits at 1 credit to 0.01 USD, and that code completions and next edit suggestions are not billed in AI credits. On 10 October 2026 it listed, per million tokens, GPT-6 Luna at 0.10 USD input and 0.50 USD output, GPT-5.6 Sol at 4 USD and 20 USD, and GPT-6 Astra at 10 USD and 50 USD. [18]

GitLab Duo baselining candidate models on a prompt library built from its own use cases

GitLabDocumented in an engineering article

GitLab Duo is the set of AI features in GitLab. In the May 2024 engineering post Developing GitLab Duo: How we validate and test AI models at scale, GitLab describes the Centralized Evaluation Framework it uses to test foundation models against its own use cases. [20]

The problem

GitLab needs to know which foundation model serves each GitLab Duo use case well, and to notice when a change makes a feature worse. The post names two obstacles. Generic benchmark datasets may not reflect the use cases GitLab sees for its features. And GitLab does not use customer data to train its AI features, so it cannot build its tests from customer prompts.

Where this topic fits

Evaluation comes before feature work, where it produces a baseline for the candidate models. It then runs daily while a feature is being developed. Each proposed change is tried on a focused subset and then on a broader subset before it is pushed to production.

How it is applied, step by step

  1. GitLab builds a prompt library of questions and ground-truth answers. The questions stand in for the inputs it expects in production, and the answers describe the ideal response.
  2. It feeds the questions to several models and compares each model's responses with the ground truth, which gives a baseline for how well each model serves the use case.
  3. Responses are scored with more than one method: similarity scores against the reference answer and judgements from an LLM judge.
  4. With a baseline for the selected model, the team develops the feature and re-validates its performance daily during active development.
  5. Each cycle, the team looks for patterns in the scores, tries a change on a smaller focused subset of the library, and only then pushes it to production.
  6. Because the library belongs to GitLab and not to any model vendor, the same test can be run on a newly released model. This last step is our reading of why the design supports provider independence.

Why this approach fits

A model that tops a public benchmark may still be poor at explaining a merge request or suggesting code in GitLab's context. A library written for GitLab's own use cases measures the thing GitLab ships. Running it at scale turns "this model feels better" into a number that can be compared across models and tracked from day to day, and a daily run catches a regression while the change that caused it is still fresh.

Limitation or tradeoff

Scores based on similarity to a reference answer reward responses that resemble the reference, so a correct answer phrased differently can score low. An LLM judge has its own errors (see LLM-as-a-Judge). The post itself says that evaluating these systems is not a solved problem. A hand-built library can also drift away from what users really ask, and the post dates from 2024, so it describes the process as it was then and names no model versions.

What the sources document

  • GitLab states that GitLab Duo features are powered by a diverse set of models, that GitLab is not tied to a single model provider by design, and that at the time of writing it used foundation models from Google and Anthropic. [20]
  • The post says the Centralized Evaluation Framework uses thousands of prompts tied to dozens of use cases, and that GitLab built its own prompt library because generic benchmark datasets may not reflect the use cases it sees for its features. [20]
  • The prompt library consists of questions and answers: the questions represent the queries or inputs expected in production, and the answers represent a ground truth of the ideal answer. [20]
  • GitLab feeds the questions into various models to test how well they serve its customers' needs, and lists its scoring methods as Cosine Similarity Score, Cross Similarity Score, LLM Judge, and Consensus Filtering with an LLM Judge. [20]
  • The post says GitLab re-validates the performance of its features on a daily basis during active development and uses a smaller-scale dataset as a mini-proxy when testing a change. [20]

OpenRouter routing one model across many providers by price, speed, quantization and data policy

OpenRouterDocumented in official docs

OpenRouter is a service that offers many models behind one API and forwards each request to one of the providers serving that model. Its Provider Routing documentation describes how the provider is chosen and which request fields control the choice. The Llama 3.3 licence explains why many providers can serve that model. [22][15][25]

The problem

An open-weight model such as Llama 3.3 70B can be served by many companies, because its licence allows the weights to be distributed and used. Those providers differ. On 10 October 2026 OpenRouter's endpoint listing for Llama 3.3 70B Instruct showed 11 endpoints, with input prices from $0.10 to $1.04 per million tokens and quantization listed as fp8, bf16, fp16 or unknown. An application that names only the model has left the provider decision to chance.

Where this topic fits

Provider choice happens on every request, after the model has been chosen. OpenRouter applies a default rule, and the caller can override it with a provider object in the request body. The same fields can express hard constraints, such as a data policy, and preferences, such as lowest price.

How it is applied, step by step

  1. By default OpenRouter first sets aside providers that have had significant outages in the last 30 seconds.
  2. Among the stable providers it picks one at random, weighted by the inverse square of the price, so cheaper providers receive most of the traffic. The rest become fallbacks.
  3. A caller who cares more about speed can set the sort field to throughput or latency, or append the nitro shortcut to the model name. Sorting turns load balancing off and tries providers in order.
  4. A caller with a data rule can set data_collection to deny, or zdr to true, so that only providers with an acceptable data policy are considered.
  5. A caller who has evaluated the model at one precision can list the allowed quantization levels, so the request never reaches a provider serving a more heavily quantized copy.
  6. A price ceiling and a flag requiring support for every parameter in the request remove providers that are too expensive or that would silently ignore a setting.

Why this approach fits

Separating the model from the provider lets each requirement be stated once, in the request, in place of a hand-maintained list of vendors. Hard constraints (data policy, precision, maximum price) become filters, and the remaining preference (price, throughput or latency) becomes a sort order. It is the selection process from this lesson applied to providers, automatically, on every call.

Limitation or tradeoff

The default favours price, which is not always what an application needs. Two providers of the "same" model can still behave differently, so an eval run through one provider does not certify another. A router is one more service between you and the model, with its own data handling and its own failures. Strict filters can also leave few or no eligible providers. The page says a request that exceeds max_price will not run, and that a request for which no provider satisfies the account and request allow-lists fails with a 404, so handle that failure in your code and test it.

What the sources document

  • OpenRouter's default strategy sets aside providers with significant outages in the last 30 seconds, then picks among the stable candidates weighted by the inverse square of the price, and keeps the rest as fallbacks. In its example, providers cost 1, 2 and 3 USD per million tokens, the 2 USD provider is unstable, and the 1 USD provider is 9 times more likely than the 3 USD one to be tried first. [22]
  • The sort field accepts price, throughput or latency. The nitro model suffix sorts by throughput and the floor suffix sorts by price. [22]
  • The quantizations field filters providers by quantization level (int4, int8, fp4, mxfp4, nvfp4, fp6, fp8, mxfp8, fp16, bf16, fp32 and unknown), and the page warns that quantized models may exhibit degraded performance for certain prompts, depending on the method used. [22]
  • On 10 October 2026 OpenRouter's endpoint listing for meta-llama/llama-3.3-70b-instruct showed 11 endpoints, with input prices from 0.10 to 1.04 USD per million tokens and quantization values of fp8, bf16, fp16 and unknown. [25]

4Common mistakes

  1. Choosing from a public leaderboard or a launch announcement without testing on your own inputs.

    Why it causes problems
    General benchmarks measure general tasks. A model that leads them can still be mediocre at your task, with your prompt and your data, and you pay its price and wait for its answers either way. The problem usually surfaces after launch, when users report errors.
    How to recognise it
    Ask what evidence supports the current choice. If the answer is a ranking, a blog post or a colleague's impression, and nobody can produce scores on the team's own examples, the model was never tested.
    How to fix it
    Use benchmarks only to build a shortlist of two to four candidates. Then run each one on at least a hundred real inputs with known good answers and choose from those results.

  2. Comparing models by price per million tokens instead of by cost per completed task.

    Why it causes problems
    Reasoning tokens are billed as output but do not appear in the answer, tokenizers split the same text into different numbers of tokens, and a weaker model may need retries or a longer prompt. A model with a lower list price can produce a higher bill.
    How to recognise it
    The cost estimate was made from the pricing page and a guessed token count. Nobody has read the usage field of real responses, and the estimate has no line for reasoning tokens or retries.
    How to fix it
    Send the same sample of real requests to each candidate, add up the billed input and output tokens from the responses, and divide the total cost by the number of tasks completed correctly.

  3. Declaring a winner from a difference smaller than the margin of error.

    Why it causes problems
    On 50 examples a pass rate near 90% has a margin of about eight points. A team that switches models because one scored 92% and the other 88% is acting on noise, and may pay more or lose quality for nothing.
    How to recognise it
    The eval set has a few dozen cases, results change noticeably when the run is repeated, and the report gives scores without the number of cases or a margin.
    How to fix it
    Report every score with its number of cases and margin of error. If the candidates overlap, add cases until they separate, or treat them as equal on quality and decide on cost and response time.

  4. Treating the provider as an afterthought and skipping its data terms and the model's licence.

    Why it causes problems
    A prototype built on a free tier may be sending customer text that the vendor uses to improve its products. An open-weight model may carry naming, attribution or usage conditions. Discovering either after launch can force a rebuild or a difficult conversation with a customer.
    How to recognise it
    Nobody on the team can say in which region requests are processed, whether prompts are retained or used for training, or which licence the chosen open-weight model is released under.
    How to fix it
    Put data residency, retention, training use and licence terms on the requirements sheet as hard constraints, and check each candidate provider against them before any quality testing.

  5. Using the most capable model at the highest effort for every call, to be safe.

    Why it causes problems
    On current price lists the top tier costs up to 100 times more per token than the smallest, and extra reasoning adds seconds to every response. For classification, extraction and routing the extra capability usually buys nothing measurable.
    How to recognise it
    Every call in the codebase names the same top-tier model, effort is left at its default or raised everywhere, and simple high-volume steps make up most of the bill.
    How to fix it
    List the distinct tasks the application performs and run the selection separately for each. Start the simple, high-volume ones on the smallest model at low effort and move up only where the eval set fails.

  6. Pointing production at a moving alias and never re-running the evaluation.

    Why it causes problems
    An alias that tracks the latest release can switch to a model with different behaviour, token counts and effort calibration. Quality or cost then changes with no deployment on your side, and the cause is hard to trace.
    How to recognise it
    The model name in configuration contains a word such as latest, the eval set has not been run since launch, and nobody is subscribed to the provider's deprecation notices.
    How to fix it
    Call a specific version, record the eval results it was approved with, and re-run the same eval set before adopting a new version, after a price change, and when a retirement date is announced.

Choose a model for an overnight summarisation job

A call centre wants a written summary of every call transcript. The job runs once a night over 120,000 transcripts, and the summaries are only needed the next morning. Each request sends 3,000 input tokens and receives a 250-token summary. The team tested four candidates on 250 transcripts and checked each summary against a rubric (pass or fail). Hint 1

Billed output for a request is the reasoning tokens plus the 250 summary tokens.

Hint 2

The batch option is acceptable only because nobody is waiting for an individual answer.

Hint 3

For part 4, rearrange the margin formula to n = 1.96 squared times p times (1 - p), divided by the margin squared, with the margin written as 0.02.

Show solution

Cost per request is (3,000 × input price + (reasoning + 250) × output price) / 1,000,000. Multiply by 120,000 for a night and halve it for the batch price. This script does the whole exercise:

python
import math

REQUESTS = 120_000
INPUT_TOKENS = 3_000
ANSWER_TOKENS = 250
EVAL_SIZE = 250
MIN_PASS_RATE = 0.90
MAX_COST_PER_NIGHT = 700.0
BATCH_DISCOUNT = 0.50

# name, input price, output price (USD per million tokens), reasoning tokens, passed of 250
CANDIDATES = [
    ("S, low effort",      0.10,  0.50,   0, 205),
    ("S, high effort",     0.10,  0.50, 600, 216),
    ("M, default effort",  2.00, 10.00, 200, 228),
    ("T, default effort", 10.00, 50.00, 400, 233),
]

print(f"{'candidate':<19}{'pass rate':>10}{'+/-':>6}{'standard':>11}{'batch':>10}  verdict (batch price)")
for name, in_price, out_price, reasoning, passed in CANDIDATES:
    per_request = (INPUT_TOKENS * in_price + (reasoning + ANSWER_TOKENS) * out_price) / 1_000_000
    standard = per_request * REQUESTS
    batch = standard * (1 - BATCH_DISCOUNT)
    rate = passed / EVAL_SIZE
    margin = 1.96 * math.sqrt(rate * (1 - rate) / EVAL_SIZE)
    failures = [label for label, bad in (("quality", rate < MIN_PASS_RATE),
                                         ("cost", batch > MAX_COST_PER_NIGHT)) if bad]
    verdict = "pass" if not failures else "fail: " + ", ".join(failures)
    print(f"{name:<19}{rate:>10.1%}{margin:>6.1%}{standard:>11.2f}{batch:>10.2f}  {verdict}")

rate = 228 / 250
print("Cases for +/-2 points:", math.ceil(1.96 ** 2 * rate * (1 - rate) / 0.02 ** 2))

Exercise 2

Hosted API or your own GPU server? Find the break-even volume

AnalysisIntermediateAbout 25 min (estimate)Hypothetical scenario

Your team has chosen an open-weight model and must decide how to run it. All numbers are invented for practice.

  • Each request has 1,500 input tokens and 300 output tokens.
  • A hosted inference provider charges $0.20 per million input tokens and $0.60 per million output tokens for this model.
  • A rented GPU server costs $2.00 per hour and must run 24 hours a day. Fully loaded, it generates 2,000 output tokens per second in total across all concurrent requests. Because traffic is uneven, plan for 50% average utilisation.
  1. What does one request cost through the hosted provider?
  2. At how many requests per day does one always-on server cost the same as the hosted provider?
  3. How many requests per day can one server handle at 50% utilisation?
  4. Compare the daily cost of both options at 20,000 and at 400,000 requests per day.
  5. Name at least three costs or risks that this arithmetic leaves out.

Requirements

  • Show the formula and the result for the hosted cost per request.
  • Give the break-even volume as a number of requests per day.
  • For 400,000 requests per day, work out how many servers are needed before you price the self-hosted option.
  • State a recommendation for each of the two volumes, with one sentence of reasoning.

Expected behaviour

A hosted request costs $0.00048. One server costs $48 a day, so the break-even is 100,000 requests a day. One server handles 288,000 requests a day at 50% utilisation. At 20,000 requests a day the hosted provider is cheaper ($9.60 against $48). At 400,000 a day two servers are needed and self-hosting is cheaper on paper ($96 against $192), before the unpriced costs are considered.

Hint 1

There are 86,400 seconds in a day.

Hint 2

Capacity is limited by output tokens here, so divide the usable output tokens per day by 300.

Hint 3

A server is paid for whether or not it is busy, so its daily cost does not depend on volume.

Show solution

1. Hosted cost per request. (1,500 × 0.20 + 300 × 0.60) / 1,000,000 = (300 + 180) / 1,000,000 = $0.00048.

2. Break-even. One server costs 24 × $2.00 = $48 per day. $48 / $0.00048 = 100,000 requests per day. Below that volume the hosted provider is cheaper, and above it one server is cheaper, as long as one server can carry the load.

3. Capacity. 2,000 tokens per second × 86,400 seconds × 0.50 = 86,400,000 usable output tokens per day. Divided by 300 tokens per request, that is 288,000 requests per day.

4. Comparison.

python
import math

INPUT_TOKENS, OUTPUT_TOKENS = 1_500, 300
API_IN, API_OUT = 0.20, 0.60            # USD per million tokens
SERVER_PER_HOUR = 2.00
SERVER_TOKENS_PER_SECOND = 2_000         # output tokens, fully loaded
UTILISATION = 0.50

api_per_request = (INPUT_TOKENS * API_IN + OUTPUT_TOKENS * API_OUT) / 1_000_000
server_per_day = SERVER_PER_HOUR * 24
break_even = server_per_day / api_per_request
capacity = SERVER_TOKENS_PER_SECOND * 86_400 * UTILISATION / OUTPUT_TOKENS

print(f"API cost per request: {api_per_request:.5f}")
print(f"One server per day:   {server_per_day:.2f}")
print(f"Break-even volume:    {break_even:,.0f} requests per day")
print(f"Server capacity:      {capacity:,.0f} requests per day at 50% utilisation")
for volume in (20_000, 400_000):
    servers = math.ceil(volume / capacity)
    print(f"{volume:>7,} requests/day: API {volume * api_per_request:>7.2f}"
          f" | self-hosted {servers} server(s) {servers * server_per_day:>6.2f}")

5. What the arithmetic leaves out.

  • Engineering time to deploy, monitor, patch and upgrade the serving stack. The saving at 400,000 requests a day is $96 × 365 = $35,040 a year, and a modest share of one engineer's time can cost more than that.
  • Redundancy. One server is a single point of failure, so a real deployment needs a spare or a hosted fallback, which raises the fixed cost.
  • Peaks. Average utilisation of 50% still leaves moments when requests queue, and response time suffers unless you add capacity.
  • Quality differences. The provider and your server may run the model at different quantization levels, so the eval set has to be run on both.
  • Change. Hosted prices tend to move, and a better model may appear. A hosted provider lets you switch in a day, while a tuned self-hosted stack takes longer to move.
  • Data handling, which can outweigh all of the above: if prompts must not leave your infrastructure, self-hosting wins at any volume.

Check your answer

  • Did you get 0.00048 USD per hosted request and a break-even of 100,000 requests per day?
  • Did you find that one server handles 288,000 requests per day at 50% utilisation?
  • Did you price two servers, not one, for 400,000 requests per day?
  • Does your answer name at least one cost that is not a GPU or a token, such as engineering time?
