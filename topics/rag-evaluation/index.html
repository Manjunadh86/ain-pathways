Evaluating RAG Systems

Evaluating a RAG system means scoring its two stages separately on a fixed set of questions with known answers. Retrieval metrics (context precision and context recall) check whether the right passages were found and ranked well. Generation metrics (faithfulness and answer relevance) check whether the model answered the question that was asked, using those passages.

1Overview

Why it matters

A RAG answer can be wrong for reasons that need opposite fixes. The retriever may never have found the passage that holds the answer, or found it and buried it under irrelevant ones, or the model may have had the right passage and ignored it. One accuracy number cannot tell these apart, so teams change chunk sizes, prompts and models at random and cannot say what helped. Anthropic's Claude Cookbook shows the effect: after a change to indexing and re-ranking, average precision moved from 0.43 to 0.44, while mean reciprocal rank moved from 0.74 to 0.87 and end-to-end accuracy from 71% to 81%. Only the per-stage numbers show where a gain came from.

Evaluation also decides whether a vendor's claim can be believed. A 2024 preregistered study of commercial legal research tools built on RAG reports hallucination rates of 17% to 33%, and concludes that the providers' claims about eliminating hallucinations are overstated. Anyone who ships a RAG feature over private documents needs the same habit on a smaller scale: a labelled question set, metrics that name the failing stage, and a check that the automatic scores agree with a person.

Key terms

Golden set
A curated list of test questions, each with a reference answer and, where possible, the ids of the passages that contain the evidence. Every score in this lesson is computed on it.
Reference answer
The answer a trusted person says is correct for a golden-set question. Metrics that need a reference compare the system's output against it.
Retrieved contexts
The passages the retriever returned for a question, in rank order, exactly as the generator received them.
Claim
One checkable statement taken from an answer or a reference. Faithfulness and context recall split text into claims and verify each one.
Context precision
A rank-aware score for how well the retriever puts relevant passages above irrelevant ones in the list it returns. Higher is better.
Context recall
The share of the reference answer's claims that the retrieved passages support. A low value means evidence was missed.
Faithfulness
The share of an answer's claims that the retrieved passages support. Some tools call it groundedness. It does not check whether the passages themselves are right.
Answer relevance
How well an answer addresses the question that was asked, without judging whether it is factually correct.
Recall at k and MRR
Label-based retrieval scores. Recall at k is the share of relevant passages found in the top k, and mean reciprocal rank averages one divided by the rank of the first relevant passage.
Reference-free metric
A metric that needs no reference answer, so it can also run on live traffic. Faithfulness and answer relevance are reference-free.

2Explanation

Introduction

In Retrieval-Augmented Generation (RAG) you saw that a RAG system answers in two stages: a retriever picks passages from your documents, and a language model writes an answer from them. In Evaluating LLM Applications you saw how to score outputs against a fixed set of test cases, and in LLM-as-a-Judge how to use a model as the grader once you have checked it against human labels. This lesson applies those tools to the two-stage case.

Think of an open-book exam. A student can fail because the wrong chapter was put on the desk, because the right chapter was there but buried in a pile of other pages, or because the right page was open and the student wrote something else. A marker who sees only the final answer cannot tell which. A RAG evaluation gives the marker the desk as well: the retrieved passages are scored in their own right, and then the answer is scored against them.

That gives four questions to ask about every test question:

  • Did the retriever find the evidence the answer needs? This is context recall.
  • Did it rank that evidence above the noise? This is context precision.
  • Did the answer stay inside the retrieved passages? This is faithfulness.
  • Did the answer address what was asked? This is answer relevance.

Ragas (a Python library for evaluating RAG and LLM applications), TruLens, Amazon Bedrock, Microsoft Foundry and Databricks all offer some version of these checks, under slightly different names. The rest of the lesson defines each metric precisely, scores two runs by hand, shows how to build the golden set the metrics run on, and explains how to read the scores to decide which stage to fix.

How it works

Why one number is not enough

Anthropic's Claude Cookbook guide to RAG (opens in a new tab) states the rule directly: evaluate the retrieval system and the end-to-end system separately. Its own results show why. After adding summary indexing and re-ranking, precision hardly changed, yet mean reciprocal rank and end-to-end accuracy rose clearly. That pattern suggests the gain came from ranking the right chunk higher, not from retrieving fewer wrong ones.

TruLens builds the same split into its RAG triad (opens in a new tab): context relevance is checked after retrieval, groundedness after generation, and answer relevance on the final response.

What an evaluation sample contains

Ragas scores samples with four fields: user_input (the question), retrieved_contexts (what the retriever returned, in rank order), response (the system's answer) and reference (the expected answer from your golden set). Some metrics also accept reference passages or context ids. The fields a metric needs decide whether it can run without labels.

MetricNeedsStage
Faithfulnessquestion, response, retrieved contextsGeneration
Response relevancyquestion, response, plus an embedding modelGeneration
Context precisionquestion, retrieved contexts, and a reference or the responseRetrieval
Context recallquestion, retrieved contexts, referenceRetrieval

Metrics without a reference can also score live traffic. Metrics with one run only on the golden set.

For graded relevance labels, normalized discounted cumulative gain (NDCG) discounts gain by rank and scales to the range 0 to 1, and Microsoft Foundry (opens in a new tab) reports it from human-labelled relevance scores.

Without chunk labels, Ragas asks a grader model to judge relevance, chunk by chunk for context precision and claim by claim for context recall. Context recall (opens in a new tab) counts how much of the reference answer the retrieved passages support:

Its shape matches average precision. The denominator counts only the relevant chunks that were retrieved, so a missed chunk costs nothing here; recall is the metric that charges for it.

Generation metrics

Faithfulness (opens in a new tab) splits the response into claims and checks each against the retrieved contexts:

faithfulness=response claims supported by the retrieved contextsclaims in the response\text{faithfulness} = \frac{\text{response claims supported by the retrieved contexts}}{\text{claims in the response}}faithfulness=claims in the responseresponse claims supported by the retrieved contexts​

The Ragas documentation's example answers "Where and when was Einstein born?" with a context that gives 14 March 1879. The answer that he was born in Germany on 20th March 1879 scores 0.5: two claims, one unsupported. Faithfulness is not correctness. A claim counts as supported when the context says it, whether or not the context is right, and a true claim that the context does not mention counts against the answer.

Response relevancy (opens in a new tab) asks a model to write several questions (three by default) that the answer would respond to, embeds them, and averages their cosine similarity with the embedding of the real question. The documentation says it measures how well the answer matches the intent of the question, not its factual accuracy, and that incomplete or padded answers score lower.

Correctness against the reference is the check that catches an answer built faithfully on a wrong passage. Ragas has a factual-correctness metric, Amazon Bedrock (opens in a new tab) lists a correctness metric, and the LangSmith tutorial (opens in a new tab) has a correctness evaluator that compares the answer with a reference answer.

Building the golden set

Every reference-based metric is only as good as the golden set. An entry needs a question, a reference answer made of checkable claims and, for rank metrics, the ids of the chunks that hold the evidence. The Amazon Bedrock dataset format (opens in a new tab) keeps the two apart: referenceResponses is the expected end-to-end answer, not the expected passages, and the optional referenceContexts field is ignored by the built-in metrics.

Databricks lists several ways to fill an evaluation dataset (opens in a new tab), among them traces captured from your application, feedback from domain experts and synthetic data generated from your documents. The Ragas test set generator (opens in a new tab) builds a knowledge graph from your documents and produces single-hop and multi-hop questions, specific and abstract, with a chosen query length and style (the page lists personas as not yet available). Review generated questions before you trust them.

Coverage beats count. Include questions that need several passages, questions with a false premise, and questions the corpus cannot answer, where the right behaviour is to say so. Add every production failure you fix as a new entry.

Same checks, different names

The names come from the documentation of Ragas (opens in a new tab), Amazon Bedrock (opens in a new tab), Microsoft Foundry (opens in a new tab), Databricks (opens in a new tab) and the LangSmith tutorial (opens in a new tab). Record the tool, its version, the judge model and the prompt with every score, because a number from one setup does not compare with a number from another.

Trusting the scores

Faithfulness, context recall and relevance come from a grader model, so they carry the problems covered in LLM-as-a-Judge. Check them against human labels before they gate a release. The Ragas paper did this on WikiEval, and ARES (opens in a new tab) uses a small set of human-annotated points with prediction-powered inference to reduce judge error.

Running Ragas

The shape below follows the Ragas quickstart (opens in a new tab). Class names and imports have changed between Ragas releases. The metric pages now present the ragas.metrics.collections classes as the recommended API and mark the older classes as legacy, with removal planned for version 1.0, while the quickstart still uses the older style shown here. Follow the documentation for the version you install.

python
from ragas import EvaluationDataset, evaluate
from ragas.llms import LangchainLLMWrapper
from ragas.metrics import FactualCorrectness, Faithfulness, LLMContextRecall

rows = [{
    "user_input": "How long do I have to return an item?",
    "retrieved_contexts": ["Items can be returned within 30 days of delivery with the original receipt."],
    "response": "You have 30 days from delivery, and you need the receipt.",
    "reference": "Items can be returned within 30 days of delivery with the original receipt.",
}]
result = evaluate(
    dataset=EvaluationDataset.from_list(rows),
    metrics=[LLMContextRecall(), Faithfulness(), FactualCorrectness()],
    llm=LangchainLLMWrapper(judge_llm),  # judge_llm: a LangChain chat model you configure
)
print(result)

Worked example: Scoring two runs of a refund-policy assistant, by hand and in Python

A small shop answers questions from five policy chunks. The shop, the chunks and both runs are invented for teaching. One golden-set entry is scored. The chunks:

IdText
c1Items can be returned within 30 days of delivery with the original receipt.
c2Refunds go to the original payment method within 5 business days after the returned item arrives.
c3Gift items are eligible for store credit only.
c4Standard shipping takes 3 to 5 business days.
c5Opened software and digital downloads cannot be returned.

The golden-set entry names the evidence chunks and gives a reference answer:

json
{
  "id": "refund-01",
  "question": "How long do I have to return an item, and how do I get my money back?",
  "reference": "Return it within 30 days of delivery with the original receipt; the refund goes to the original payment method.",
  "relevant_chunk_ids": ["c1", "c2"]
}

The reference holds three claims: R1 returns are accepted within 30 days of delivery, R2 the original receipt is required, R3 the refund goes to the original payment method.

Run A (vector search only, k = 4) retrieved c4, c1, c3, c5 and answered: "You can return an item within 30 days of delivery if you have the original receipt. The refund goes back to your original payment method, and return shipping is free."

Run B (after a retrieval change, k = 3) retrieved c1, c2, c4 and answered: "You have 30 days from delivery to return an item, and you need the original receipt. The refund goes to your original payment method within 5 business days after the item arrives."

Step 1: judge each claim against the retrieved text

A grader (a person here, a judge model in production) splits each answer into claims and marks each claim as supported or not by the retrieved chunks.

RunAnswer claimSupported by the retrieved chunks?
AA1: returns within 30 days of deliveryYes, c1
AA2: the original receipt is neededYes, c1
AA3: the refund goes to the original payment methodNo: c2 was not retrieved
AA4: return shipping is freeNo: no chunk says so
BB1 to B4: 30 days, receipt, original payment method, within 5 business daysYes: c1, c1, c2, c2

The same check on the reference claims gives context recall. In run A, R1 and R2 are supported by c1 but R3 needs c2, so 2 of 3 are supported. In run B all three are.

Step 2: compute the scores

python
RELEVANT = {"c1", "c2"}                      # chunks a person marked as holding the evidence

def recall_at_k(retrieved):
    return len(RELEVANT & set(retrieved)) / len(RELEVANT)

def precision_at_k(retrieved):
    return len(RELEVANT & set(retrieved)) / len(retrieved)

def reciprocal_rank(retrieved):
    for rank, chunk_id in enumerate(retrieved, start=1):
        if chunk_id in RELEVANT:
            return 1 / rank
    return 0.0

def context_precision(retrieved):
    hits, total = 0, 0.0
    for k, chunk_id in enumerate(retrieved, start=1):
        if chunk_id in RELEVANT:
            hits += 1
            total += hits / k                # precision@k, added only at relevant ranks
    return total / hits if hits else 0.0

def share(verdicts):
    return sum(verdicts) / len(verdicts)

runs = {
    "A": {"retrieved": ["c4", "c1", "c3", "c5"],
          "reference_claims_supported": [True, True, False],
          "answer_claims_supported": [True, True, False, False]},
    "B": {"retrieved": ["c1", "c2", "c4"],
          "reference_claims_supported": [True, True, True],
          "answer_claims_supported": [True, True, True, True]},
}

for name, run in runs.items():
    r = run["retrieved"]
    print(f"Run {name}: recall@k={recall_at_k(r):.2f}  precision@k={precision_at_k(r):.2f}  "
          f"RR={reciprocal_rank(r):.2f}  context_precision={context_precision(r):.2f}  "
          f"context_recall={share(run['reference_claims_supported']):.2f}  "
          f"faithfulness={share(run['answer_claims_supported']):.2f}")

Output:

text
Run A: recall@k=0.50  precision@k=0.25  RR=0.50  context_precision=0.50  context_recall=0.67  faithfulness=0.50
Run B: recall@k=1.00  precision@k=0.67  RR=1.00  context_precision=1.00  context_recall=1.00  faithfulness=1.00

By hand, run A's context precision is: rank 2 is the only relevant chunk, precision@2 is 1/2, and one relevant chunk was retrieved, so the score is 0.5 / 1 = 0.5.

Step 3: read the pattern

  • Recall@k and context recall differ. Run A finds 1 of 2 evidence chunks (0.50), but the missing chunk carries only one of three reference claims (0.67). One counts chunks, the other counts facts.
  • Precision@k and context precision differ. Run A's precision@4 is 1/4. Context precision (0.50) also depends on where the relevant chunk sits and ignores the relevant chunk that was never retrieved.
  • Run A's answer looks right and is not trustworthy. It states all three reference claims, so a recall-style check against the reference alone would pass it. Faithfulness 0.50 shows that half of its claims have no support in the retrieved text: A3 happens to be true but came from somewhere other than the evidence, and A4 is invented.
  • Run B is clean. Precision@k is 0.67 only because c4, an irrelevant chunk, sits in last place. That is harmless noise, not a failure.
  • Answer relevance is not computed here because it needs an embedding model. Both answers address the question, so a high score would be expected for each.

This is one question. A real evaluation averages over the whole golden set and also lists the questions that got worse, because an average can hide a regression.

Edge cases and limitations

Faithful does not mean correct
Faithfulness only checks the answer against what was retrieved. If the corpus holds a stale or wrong passage, a perfectly faithful answer is wrong. TruLens states the limit itself: an app that passes its three checks is verified hallucination free up to the limit of its knowledge base. Pair faithfulness with a reference-based correctness check and keep the corpus current.
The right answer from the wrong source
Run A in the worked example restated a true fact that the retrieved text did not contain. A check against the reference passes it, yet the answer cannot be cited and will go stale when the fact changes. If your golden set asks about facts a model already knows, retrieval can fail without any visible effect. Prefer private or recent documents, and watch faithfulness next to correctness.
Questions the corpus cannot answer
With no relevant chunk, recall is a division by zero and precision has nothing to rank, so retrieval metrics skip the entry. The correct behaviour is to say the answer is not in the documents, which only an answer-level check can score. Keep these entries in the golden set and report them separately, or they quietly drop out of every average.
Names and definitions drift
The Ragas paper defines context relevance as the share of context sentences that are needed. The current Ragas metric pages describe context precision and context recall instead, built on rank order and claim support, and mark older classes as legacy API. Bedrock calls the recall-like check context coverage. Pin the tool version, judge model and prompts, and never compare scores across setups.
Synthetic questions flatter the retriever
A question a model writes while reading one chunk tends to reuse that chunk's words, so keyword and embedding search find it easily, while real users phrase things differently and ask about several documents at once. Use generated questions for breadth and keep a core of real or expert-written ones; Databricks lists captured traces and expert feedback beside synthetic data as sources.
Small sets make small differences noise
With 20 questions, one question flips the score by 5 points. A difference between two retrievers may rest on a single entry. Compare per question, read the entries that changed, and treat gaps of a few points as unproven until the set is larger or the same gap repeats across runs.

When to use it, and when something simpler is enough

Use it when

  • You answer from private or fast-changing documents and need to know, after each change, whether retrieval or generation got better or worse.
  • You are about to change a retrieval setting such as chunk size, k, the embedding model, hybrid search or a reranker, and need a before-and-after number on the same questions.
  • You are choosing between a managed knowledge base and your own pipeline, or between generator models, and need scores that compare.
  • Users report wrong answers and you must say which stage failed so that the fix goes to the right place.

Think twice when

  • The application has no retrieval step, so there are no passages to score; general LLM evaluation is the right tool.
  • You cannot yet label even a few dozen questions. Collect real questions and read failures by hand first, because automatic metrics on a poor golden set give confident but meaningless numbers.
  • A high-stakes decision would rest on model-graded scores alone. The legal-tool audit relied on expert labels, and judge scores need human spot-checks before they gate anything.

A simpler alternative. Label the relevant chunk ids for a few dozen real questions, track recall@k and MRR with plain code, and read the failing answers by hand. Add model-graded faithfulness and relevance once reading every answer becomes the bottleneck.

Key takeaways

  • A RAG answer can fail in the retriever or in the generator, so score the two stages separately, using context recall and context precision for retrieval and faithfulness and answer relevance for generation.
  • Context recall asks whether the evidence was found, context precision asks whether it ranked above the noise, and faithfulness asks whether the answer stayed inside the retrieved text; none of them alone says the answer is correct.
  • Faithfulness and correctness are different, because an answer can be right but unsupported by the retrieved text, or fully supported by a wrong document, so reference-based checks are still needed.
  • A golden set holds questions, reference answers and, where possible, the ids of the evidence, and it should mix real and expert-written questions, include multi-passage, false-premise and unanswerable cases, and grow with every production failure.
  • Tools name and define the same checks differently, so record the tool, version, judge model and prompt next to every score and compare only like with like.
  • Model-graded metrics must be checked against human labels before they gate a release, because a confident number from an unvalidated judge can be wrong.

Example 1 of 5

Amazon Bedrock evaluation jobs that score a knowledge base's retrieval and its answers

Amazon Web ServicesDocumented in official docs

The Amazon Bedrock user guide documents RAG evaluation jobs for Bedrock Knowledge Bases and for RAG systems hosted elsewhere. The pages on the two job types, the built-in metrics, the prompt dataset format and the job-creation steps describe what a job measures and what the golden dataset must contain. [9][10][11][12]

The problem

A team building on a managed knowledge base has to choose between knowledge bases, chunking and retrieval settings and generator models. Reading answers by hand does not scale, and a single end-to-end score hides whether retrieval or generation is the weak part.

Where this topic fits

Bedrock splits the evaluation in two. A retrieve-only job scores the passages returned for each prompt. A retrieve-and-generate job also scores the generated response. Both read a prompt dataset (the golden set) from Amazon S3, and an evaluator model that you choose acts as the grader.

How it is applied, step by step

  1. Write the golden set as JSON lines, one prompt per line, adding a reference response wherever a metric needs one.
  2. Choose the job type. Retrieve-only suits tuning retrieval settings on their own; retrieve-and-generate suits judging the final answers once the passages are good.
  3. Select built-in metrics, such as context relevance and context coverage for retrieval, and correctness, completeness and faithfulness for answers.
  4. Select an evaluator model, which grades every prompt against each metric, and run the job against a Bedrock knowledge base or against inference results exported from your own RAG system.
  5. Compare the reports for two configurations and use the retrieval scores to decide whether a weak answer score starts in retrieval.

Why this approach fits

The two job types mirror the retrieval and generation split, so a team can settle retrieval first and judge generation second. Accepting inference results from an external system lets the same golden set and metrics compare a managed knowledge base with a home-built pipeline.

Limitation or tradeoff

Scores come from an LLM grader, so they carry the usual judge caveats and need spot checks against human review. A retrieve-only dataset holds at most 1000 prompts, and context coverage needs reference responses that someone must write. The reference field holds the expected answer, not expected passages, and the built-in metrics ignore the optional referenceContexts field, so recall against labelled passages would need a custom metric or your own code.

What the sources document

  • Bedrock offers two RAG evaluation job types, retrieve-only and retrieve-and-generate, and each can evaluate a Bedrock knowledge base or response data that you bring from an external RAG source. [9]
  • The built-in retrieve-only metrics are context relevance and context coverage, and context coverage requires a ground truth in the prompt dataset. [10]
  • The built-in retrieve-and-generate metrics include correctness, completeness, helpfulness, logical coherence, faithfulness, citation precision and citation coverage, together with harmfulness, stereotyping and refusal. [10]
  • A retrieve-only prompt dataset is a JSON Lines file with up to 1000 prompts. The referenceResponses key holds the ground truth for an end-to-end answer and does not represent the expected passages. The optional referenceContexts key is not used by the built-in metrics. [11]
  • Creating a retrieve-only job in the console asks for an evaluator model, an inference source (a Bedrock knowledge base or your own inference responses), at least one built-in metric, the Amazon S3 location of the prompt dataset and an S3 location for the results. [12]

The facts above come from the cited sources. The steps and analysis in this example are our explanation of how they fit together.

Example 2 of 5

Microsoft Foundry's process and system evaluators for tuning a search-backed assistant

MicrosoftDocumented in official docs

Microsoft Learn documents a family of RAG evaluators in Microsoft Foundry. The page groups them into process evaluation of the retrieval step and system evaluation of the final response, and it describes a parameter sweep for tuning search settings. [13]

The problem

A team with a search index behind a chat assistant wants to tune the search algorithm, top_k and chunk size without judging every change by reading answers. Retrieval sits upstream of everything else, so a weak retriever caps what the model can do.

Where this topic fits

Process evaluators (Retrieval and Document Retrieval) run on the retrieval step. System evaluators (Groundedness, Relevance and Response Completeness) run on the final response. Document Retrieval is the one that needs a labelled set of relevance judgments; the others take some mix of a query, a context and a response, plus a ground truth for completeness.

How it is applied, step by step

  1. Label a set of queries by giving each important document a human relevance score. The page calls this set the retrieval ground truth.
  2. Generate retrieval results for every combination of settings to compare, such as vector or semantic search, top_k and chunk size.
  3. Score each combination with the Document Retrieval evaluator, which returns NDCG, XDCG, fidelity, max relevance and a count of unlabelled documents.
  4. Choose the settings with the best retrieval scores, then generate answers with them.
  5. Score those answers with Groundedness, Relevance and Response Completeness, reading groundedness as the precision side of the answer and completeness as the recall side.

Why this approach fits

Labelled relevance lets you tune search without a model call per answer, so a sweep over many settings is cheap and repeatable. The model-graded system evaluators are then reserved for the final answer. Splitting the answer checks into a precision-like one (groundedness) and a recall-like one (completeness) gives two separate levers.

Limitation or tradeoff

Someone has to produce graded relevance labels, and the holes count shows how fast a changed index returns unlabelled documents. The model-graded evaluators return scores from 1 to 5 with a default pass mark of 3, which is an arbitrary cut-off until you calibrate it on your own data. The page marks Groundedness Pro and Response Completeness as preview features.

What the sources document

  • The page groups Retrieval and Document Retrieval as process evaluation of the retrieval step, and Groundedness, Groundedness Pro, Relevance and Response Completeness as system evaluation of the final response. [13]
  • It describes groundedness as the precision aspect of a response, meaning nothing outside the grounding context, and response completeness as the recall aspect, meaning nothing critical missing compared with the ground truth. [13]
  • The Document Retrieval evaluator compares retrieved documents with human-labelled relevance and reports fidelity, NDCG, XDCG, max relevance and holes, where holes counts documents that lack relevance judgments. [13]
  • For a parameter sweep it suggests generating retrieval results for different search algorithms (vector, semantic), top_k values and chunk sizes, then using the Document Retrieval evaluator to find the best settings. [13]
  • The model-graded evaluators return scores from 1 to 5, and the default pass threshold is 3. [13]

Example 3 of 5

The Ragas paper checking reference-free RAG metrics against human annotators on WikiEval

Documented in a paper

The Ragas paper (Es, James, Espinosa-Anke and Schockaert, 2023) proposes three reference-free metrics for RAG and tests them on WikiEval, a dataset the authors built for that purpose. [7]

The problem

Evaluating RAG normally needs human-written answers and passage labels. The authors wanted metrics that run without ground-truth annotations, and they had to show that those metrics rank answers the way people do before anyone could rely on them.

Where this topic fits

Each metric targets one place a RAG answer can fail: context relevance for retrieval, faithfulness for use of the context, and answer relevance for the response. The WikiEval experiment is the step this lesson calls validating the judge: compare automatic scores with human choices before using the scores to gate changes.

How it is applied, step by step

  1. Choose 50 recent Wikipedia pages, have a model write questions from their introductions and answer them, then add worse alternatives: an answer written without the context, an answer with lower relevance, or a context with extra sentences added.
  2. Have two human annotators pick the better item in each pair, and settle their disagreements by discussion.
  3. Score the same pairs with each automatic metric and count how often the metric prefers the item the humans chose.
  4. Compare against two plain prompting baselines, GPT Score and GPT Ranking, to see whether claim-level scoring beats asking a model for a rating.
  5. Read the per-aspect results to learn which metric to trust most.

Why this approach fits

Each metric is decomposed into inspectable steps, so a low score can be traced to the statements or sentences that caused it. The pairwise-agreement test turns "does this metric work?" into a number per metric, which is what you need before using a score as a regression gate.

Limitation or tradeoff

Agreement differs by metric: the paper reports 0.95 for faithfulness but 0.78 for answer relevance and 0.70 for context relevance, so the retrieval-side score was the weakest. WikiEval questions and answers were written by a model over Wikipedia, so agreement may not carry over to a domain-specific corpus. The paper's context relevance is also not the context precision and context recall of current Ragas, so scores do not transfer between versions.

What the sources document

  • The paper presents a reference-free evaluation framework for RAG that measures retrieval effectiveness, the model's faithful use of retrieved passages and generation quality, without ground-truth annotations. [7]
  • Faithfulness is the share of statements extracted from the answer that can be inferred from the context. Answer relevance is the mean cosine similarity between the question and several questions generated from the answer. Context relevance is the share of context sentences that an LLM extracts as crucial. [7]
  • WikiEval consists of 50 Wikipedia pages about events since 2022. ChatGPT generated the questions and answers, and two human annotators evaluated every instance, with reported inter-annotator agreement of about 95% for faithfulness, 90% for answer relevance and 95% for context relevance. [7]
  • In agreement with human annotators, Ragas scored 0.95 on faithfulness, 0.78 on answer relevance and 0.70 on context relevance, against 0.72, 0.52 and 0.63 for GPT Score and 0.54, 0.40 and 0.52 for GPT Ranking. [7]

Example 4 of 5

An academic audit of three commercial RAG legal research tools

Documented in a paper

Magesh and colleagues report a preregistered empirical evaluation of Lexis+ AI, Westlaw AI-Assisted Research and Ask Practical Law AI, three commercial tools that retrieve legal sources and generate answers from them, with GPT-4 as a general-purpose comparison. The arXiv paper describes the query set, the labelling scheme and the results. [17]

The problem

Providers presented RAG-based legal research as reducing or removing hallucinations, and a buyer cannot test that with generic benchmarks. Legal questions are ambiguous, the relevant authority depends on jurisdiction and date, and a citation can look right while not supporting the claim it is attached to.

Where this topic fits

The audit evaluates each product from outside, because the systems are closed, with mostly hand-built queries and expert labels. Its labels check both whether the answer is correct and whether the cited sources support it, which is the same distinction as correctness versus faithfulness. Its error analysis lists causes such as naive retrieval and reasoning errors, but the authors say a closed system does not let them pin a failure on a single step.

How it is applied, step by step

  1. Fix the evaluation plan in advance, including query types and labelling rules, so that results cannot steer the design (preregistration).
  2. Assemble 202 queries across four types: general legal research, jurisdiction or time-specific questions, questions with a false premise, and factual recall. Most were hand-written or adapted.
  3. Run every query on every tool and label each response as correct, incorrect or a refusal.
  4. For correct responses, label groundedness as grounded, ungrounded or misgrounded, where misgrounded means the citations do not support the claims.
  5. Count a response as hallucinated when it is incorrect or misgrounded, report rates per tool, and analyse the failures by cause.

Why this approach fits

A black-box audit sidesteps vendor-supplied metrics. Separating correctness from groundedness catches the case that matters most in law: a confident answer with a citation that does not support it, which a correctness-only check would miss.

Limitation or tradeoff

Expert labelling is slow, so the set holds hundreds of queries, not thousands. The results describe specific products at the time they were tested, and the hallucination definition is tuned to legal citations, so it does not transfer unchanged to other domains. Because the products are closed, the audit cannot say whether a failure began in retrieval or in generation, which is the question stage-wise metrics answer when you own the pipeline.

What the sources document

  • The authors describe their work as the first preregistered empirical evaluation of AI legal research tools and conclude that provider claims about eliminating hallucinations are overstated. [17]
  • They evaluate Lexis+ AI, Westlaw AI-Assisted Research and Ask Practical Law AI, and report that each hallucinates between 17% and 33% of the time, which they describe as lower than for general-purpose chatbots such as GPT-4. [17]
  • The query set has 202 queries in four categories: general legal research, jurisdiction or time-specific questions, false-premise questions and factual recall. [17]
  • Responses are labelled correct, incorrect or refusal. Correct responses are further labelled grounded, ungrounded or misgrounded, and a response counts as hallucinated if it is incorrect or misgrounded. [17]
  • The error analysis names causes of hallucinated responses, including naive retrieval, inapplicable authority, reasoning errors and sycophancy, and says that because these are closed systems the authors cannot clearly identify a single point of failure. [17]

Example 5 of 5

Anthropic comparing retrieval pipelines on their failure rate at 20 chunks

AnthropicDocumented in an engineering article

Anthropic's engineering post introducing Contextual Retrieval (September 2024) measures every retrieval technique with a retrieval-only metric across several knowledge domains, before any generation step is considered. [18]

The problem

Chunks lose the context of the document they came from, so some relevant chunks are never retrieved. To decide whether a more complex retrieval pipeline is worth its cost, the team needed one number that isolates the retriever from the generator and compares several techniques on the same questions.

Where this topic fits

The metric sits entirely in the retrieval stage. It takes questions with known relevant chunks, runs the retriever and counts the relevant chunks that fail to appear in the top 20. Generation is a separate stage, and the post's closing advice is to always run evals, noting that responses may improve when the model is given the contextualized chunk.

How it is applied, step by step

  1. Assemble question sets for several knowledge domains, with the relevant chunks identified for each question.
  2. Run each retrieval variant on the same questions and with several embedding models: embeddings alone, contextual embeddings, contextual embeddings with BM25 (keyword search), and a reranked version.
  3. For each variant compute the share of relevant chunks missing from the top 20, written as 1 minus recall@20.
  4. Compare variants on that number and also try other cut-offs. The post reports trying 5, 10 and 20 chunks and finding 20 the most performant.
  5. A typical next step is to pass the retrieved chunks to the generator and judge answer quality with separate evals.

Why this approach fits

Recall at a fixed k answers the question the generator depends on: was the evidence in the context it was given? A retrieval-only metric is cheap, free of generator variance and repeatable given labels, so many variants can be compared quickly before any answer is generated.

Limitation or tradeoff

Recall@20 says nothing about ranking inside the 20, about noise from irrelevant chunks, or about whether the model used the evidence. A top-20 cut-off also costs context tokens. The figures are the post's own averages on its own datasets, so they will not carry over to your corpus.

What the sources document

  • The post measures retrieval with 1 minus recall@20, the percentage of relevant documents that fail to be retrieved within the top 20 chunks. [18]
  • It evaluates across several knowledge domains (codebases, fiction, ArXiv papers and science papers) and across multiple embedding models. [18]
  • The reported top-20 failure rates are 5.7% for the embedding baseline, 3.7% with contextual embeddings, 2.9% with contextual embeddings plus BM25 and 1.9% when reranking is added, which the post presents as reductions of 35%, 49% and 67%. [18]
  • The post says it tried delivering 5, 10 and 20 chunks and found 20 the most performant of those options. Its closing advice is to always run evals, since response generation may improve when the model is given the contextualized chunk and told which part is context and which is the chunk. [18]

4Common mistakes

  1. Reporting one end-to-end accuracy number for the whole RAG system

    Why it causes problems
    A gain or a drop cannot be traced to a stage, so effort goes to the wrong place: prompts get rewritten when the retriever misses evidence, or chunking gets retuned when the model ignores good passages. In the Claude Cookbook run, precision stayed near 0.43 while end-to-end accuracy rose ten points, which a single number would not explain.
    How to recognise it
    The dashboard shows one accuracy line and no retrieval number, and after a change nobody can say whether the retrieved passages or the answers moved.
    How to fix it
    Log the retrieved chunk ids and the answer for every golden-set run, and report at least one retrieval metric (recall@k or context recall) and one generation metric (faithfulness) beside the end-to-end score.

  2. Reading faithfulness as a correctness score

    Why it causes problems
    An answer built faithfully on a stale or wrong passage scores 1.0, and a correct answer that came from the model's memory scores low. The first ships wrong answers under a green dashboard; the second hides a retrieval gap behind a passing accuracy check.
    How to recognise it
    Faithfulness is high while reviewers report wrong answers, or answers match the reference while faithfulness is low, as in run A of the worked example.
    How to fix it
    Track a reference-based correctness check next to faithfulness, review the corpus for stale documents, and treat a correct but unfaithful answer as a retrieval problem to fix, not a pass.

  3. Building the golden set only from model-written questions about your own chunks

    Why it causes problems
    A question written while reading one chunk reuses that chunk's wording, so retrieval looks better than it is, and such sets rarely hold multi-document, ambiguous or unanswerable questions. Scores rise on the set while real users still fail.
    How to recognise it
    Recall is near 1.0 on the golden set but production traces show missed evidence, and almost every entry has exactly one relevant chunk.
    How to fix it
    Seed the set with real questions from traces or tickets and with expert-written ones, use generation for breadth, review every generated entry, and tag entries by type: single-passage, multi-passage, false premise, unanswerable.

  4. Putting the expected answer where the expected passages belong

    Why it causes problems
    Rank metrics need the ids of the evidence passages, while answer metrics need the reference answer. Amazon Bedrock states that its reference response is not the expected passages. Mixing the two produces metrics that run without error and measure something else.
    How to recognise it
    Context coverage or recall looks high although the chunks you would cite are not in the retrieved list, or the evidence field holds answer text.
    How to fix it
    Keep separate, clearly named fields for the reference answer and for the evidence ids, and spot-check ten entries by hand against the inputs each metric receives.

  5. Scoring retrieval at a larger k than the generator receives

    Why it causes problems
    Recall@50 can look excellent while the prompt holds five chunks, so the number describes a list the model never saw. Tuning against it hides the real bottleneck.
    How to recognise it
    Retrieval scores are strong while context recall or faithfulness computed on the prompt's contexts is weak, or the k in the evaluation script differs from the k in production.
    How to fix it
    Score the exact list placed in the prompt, in order, after reranking and filtering. Add a second cut at the retriever's own k only when you are tuning the retriever.

  6. Comparing scores from different judge models, prompts or tool versions

    Why it causes problems
    Model-graded metrics shift when the judge model, its prompt or the library changes, so an apparent improvement can be a different grader. Decisions then rest on noise.
    How to recognise it
    Scores jump after an upgrade with no change to the pipeline, or re-scoring an old output gives a different number.
    How to fix it
    Pin the judge model, prompts and library version. When you must change them, re-score the previous outputs with the new setup and compare only within one setup, and recheck the judge against human labels.

def recall_at_k(retrieved, relevant):
    return len(relevant & set(retrieved)) / len(relevant)

def reciprocal_rank(retrieved, relevant):
    for rank, doc_id in enumerate(retrieved, start=1):
        if doc_id in relevant:
            return 1 / rank
    return 0.0

def context_precision(retrieved, relevant):
    hits, total = 0, 0.0
    for k, doc_id in enumerate(retrieved, start=1):
        if doc_id in relevant:
            hits += 1
            total += hits / k
    return total / hits if hits else 0.0

def mean(values):
    return sum(values) / len(values)

def evaluate(retriever):
    answerable = [row for row in GOLDEN if row["relevant"]]      # skip q5: nothing to find
    return {
        "recall@3": mean([recall_at_k(r[retriever], r["relevant"]) for r in answerable]),
        "MRR": mean([reciprocal_rank(r[retriever], r["relevant"]) for r in answerable]),
        "context_precision": mean([context_precision(r[retriever], r["relevant"]) for r in answerable]),
        "questions_scored": len(answerable),
    }

for retriever in ("X", "Y"):
    print(retriever, {key: round(value, 3) for key, value in evaluate(retriever).items()})

print("per question (recall@3, RR):")
for row in GOLDEN:
    if row["relevant"]:
        cells = [f"{name}: {recall_at_k(row[name], row['relevant']):.2f}, {reciprocal_rank(row[name], row['relevant']):.2f}" for name in ("X", "Y")]
        print(" ", row["id"], " | ".join(cells))
