Linux and the Shell

Linux is an operating system widely used on servers, cloud instances and containers, and the shell is a text program in which you type commands to work with its files, processes and services. A small set of ideas covers most daily work on a server: one directory tree, permissions, processes, text streams, environment variables, SSH, logs and scripts.

1Overview

Why it matters

Many systems you will deploy to are Linux machines without a screen: a cloud instance, a container, a GPU server in a customer's data centre. The way in is a terminal over SSH, and the evidence of what went wrong is in log files and the process table. An engineer who cannot read Permission denied, find the service that keeps restarting, or cut ten thousand log lines down to the three that matter has to wait for someone who can.

The same skills decide whether work is repeatable. A fix typed by hand on one server is gone when the session closes. The same commands in a short script can be reviewed, rerun and handed to the customer's team. Most damage done from a shell comes from a few misunderstandings: a pipeline that hides a failed step, a key or secrets file that everyone can read, a service that never received the variable you set, or kill -9 used on a process that needed to clean up. This lesson is aimed at those.

Before you start

No prerequisites. You can start here.

What you will be able to do

  • Find your way around the Linux directory tree and translate a permission string such as rw-r----- to and from its octal mode.
  • Inspect processes, stop them with the right signal, and control a systemd service with systemctl.
  • Combine commands with pipes and redirection, and predict the exit status of a pipeline.
  • Set, export and scope environment variables, and explain why a running service does not see a later change.
  • Log in to a server with an SSH key pair and explain what the private key, authorized_keys and known_hosts each do.
  • Filter logs with grep, tail and journalctl, and write a short script with strict mode, arguments and meaningful exit codes.

Key terms

Shell
A program that reads the commands you type, starts other programs and connects their inputs and outputs. Bash is the shell found on most Linux servers.
Path
The location of a file in the directory tree. An absolute path starts at the root, written as a single slash, and a relative path starts at the current directory.
Permission mode
Nine bits on every file that say whether the owner, the group and everyone else may read, write or execute it, usually written as three octal digits such as 640.
Process
A running program. Each process has a numeric ID (PID), a parent process, an owner and its own copy of the environment.
Signal
A short notification sent to a process, for example to ask it to stop (SIGTERM) or to stop it immediately (SIGKILL).
Exit status
A number from 0 to 255 that a process leaves behind when it ends. Zero means success and any other value means failure.
Standard streams
The three channels every process starts with, namely standard input (0), standard output (1) and standard error (2).
Pipe
A connection, written as a vertical bar, that feeds the standard output of one command into the standard input of the next.
Environment variable
A named text value handed to a program when it starts, used for settings such as the search path for commands or an application's port.
Service
A long-running background process such as a web server or model server. On most current distributions systemd starts, stops and restarts services from unit files.

2Explanation

Introduction

You already use an operating system through windows and icons: a file manager to browse folders, a task manager to see what is running, a settings panel to change how programs behave. A Linux server offers the same things with no windows at all. You type a line of text, a program runs, and text comes back. The program that reads your line is the shell. On most servers it is Bash.

A command line has a simple grammar: the name of a program, then options and arguments.

bash
ls -l /var/log

Here ls is the program (list files), -l is an option (long format) and /var/log is the argument (which directory). The shell finds the program, starts it, waits for it to finish and shows a new prompt. Nearly everything in this lesson is a variation on that one exchange.

The shell is not the operating system. It is an ordinary program that asks the kernel, the core of Linux, to do the real work: open files, start processes, check permissions, send data over the network. That is why the same commands work on a laptop, on a cloud server and inside a container.

Think of the shell as a workbench of small single-purpose tools. grep only finds lines, sort only sorts, wc only counts. The power comes from joining them, so that the output of one becomes the input of the next, and from saving a sequence that worked as a script you can run again.

The lesson follows the order in which you meet these things on a real server: where files live and who may touch them, what is running and how to stop it, how to connect programs with pipes and redirection, how environment variables configure programs, how SSH gets you onto a remote machine, how to read logs, and how to write a small script. Commands are shown for Bash on a distribution that uses systemd, such as Ubuntu, Debian or Fedora. Version control, containers and networks have their own lessons: Git and GitHub Workflows, Docker and Containers and Networking Essentials.

How it works

The file system: one tree, with an owner and a mode on every file

Linux has no drive letters. Every file sits in one tree that starts at /, the root. A path that begins with / is absolute. Any other path is relative to your current directory, which pwd prints and cd changes. ~ is your home directory, . is the current directory and .. is its parent.

Where things go is a convention written down in the Filesystem Hierarchy Standard (opens in a new tab):

DirectoryWhat the standard puts there
/etcHost-specific system configuration
/homeUser home directories
/usr/binMost user commands
/var/logLog files
/var/libState that programs keep between runs
/tmpTemporary files, which programs must not expect to survive
/optAdd-on application software packages

Every file has an owner, a group and nine permission bits: read, write and execute for the owner, for the group, and for everyone else. ls -l shows them:

text
-rw-r----- 1 deploy app 2048 Mar  2 09:00 settings.env

The first character is the type (- for a file, d for a directory). Then come three triples: rw- for the owner deploy, r-- for the group app and --- for others. Each triple is also one octal digit, with read worth 4, write 2 and execute 1, so this numeric mode (opens in a new tab) is 640.

On a directory the bits mean something else: read lists the names, write creates and removes files inside it, and execute lets you reach the files in it. chmod 640 file sets a mode, chown user:group file changes ownership, and sudo command runs one command as root, the administrator account that these bits do not restrain.

Processes, signals and services

A process is a running program. It has a numeric ID (PID), a parent that started it, an owner and a set of environment variables. ps aux lists every process, top shows the busiest ones live, and pgrep -a name finds one by name.

You control a process by sending it a signal. The signal(7) manual page (opens in a new tab) lists them all. Four matter daily:

SignalNumberUsually sent byEffect
SIGINT2Ctrl+CInterrupt from the keyboard; ends the process by default
SIGTERM15kill PIDA request to stop that the program can catch, so it may clean up first
SIGKILL9kill -9 PIDEnds the process at once; cannot be caught, blocked or ignored
SIGHUP1a terminal closingHangup; ends the process by default

When a process ends it leaves an exit status from 0 to 255. Zero means success and anything else means failure. The shell keeps the last one in $?. Bash reports 127 when a command was not found, 126 when a file was found but is not executable, and 128 + N when signal N ended the process.

bash
sleep 300 &             # & starts the command in the background
kill "$!"               # $! is the PID of that job; kill sends SIGTERM
wait "$!"; echo "$?"    # prints 143, which is 128 + 15

A service is a process meant to run for a long time with no terminal attached, such as a web server or a model server. On distributions that use systemd, each service is described by a unit file and controlled with systemctl:

bash
systemctl status nginx          # current state plus the most recent log lines
sudo systemctl restart nginx    # stop, then start
sudo systemctl enable nginx     # start it at every boot (add --now to start it immediately too)

Streams, redirection and pipes

Every process starts with three open streams, each with a file descriptor number: standard input (0), standard output (1) and standard error (2). All three are attached to your terminal unless the shell re-attaches them before the program starts:

SyntaxMeaning
cmd > out.txtWrite standard output to a file, replacing its contents
cmd >> out.txtAppend standard output to a file
cmd 2> err.txtWrite standard error to a file
cmd > all.txt 2>&1Send both streams to the same file
cmd < in.txtRead standard input from a file

A pipe, written |, connects the standard output of one command to the standard input of the next. The Bash manual (opens in a new tab) specifies that each command in a pipeline runs in its own process. The stages run at the same time, so a stage can start on the first lines while the stage before it is still producing the rest. Only a stage that needs all of its input before it can answer, such as sort, holds the data back until the input ends.

Two rules prevent most surprises. Redirections are processed left to right, so > all.txt 2>&1 captures both streams while 2>&1 > all.txt leaves errors on the terminal. And the exit status of a pipeline is the status of its last command, so a pipeline whose first stage fails still reports success unless you turn on set -o pipefail.

Environment variables

When a program starts it receives a list of NAME=value strings called its environment. Programs read it for settings: PATH lists the directories searched for commands, HOME is your home directory, and applications define their own. Keeping per-deployment settings there, not in code, is the Twelve-Factor (opens in a new tab) convention.

bash
SLOW_MS=250                # a shell variable: only this shell sees it
export SLOW_MS             # now every child process receives it
SLOW_MS=400 ./report.sh    # set for this one command only
printenv SLOW_MS           # print one variable; env prints all of them

A child gets a copy of its parent's environment. A script run as a program cannot change the variables of the shell that launched it (source script.sh is the exception, because it runs the commands inside your current shell), and a running service does not notice a variable you export later. Lines in ~/.bashrc apply only to shells you start. A systemd service gets its variables from Environment= or EnvironmentFile= lines in its unit and must be restarted to see a change.

SSH: a shell on another machine

ssh user@host opens an encrypted connection and starts a shell on the remote machine. Servers usually accept a key pair in place of a password. You create one with ssh-keygen -t ed25519. The private key stays on your computer, and the public key is added as one line to ~/.ssh/authorized_keys on the server.

Two files protect you. ~/.ssh/known_hosts remembers each server's host key. The first time you connect, ssh shows the key's fingerprint and asks you to confirm it, and it warns you if the key later changes. Your private key must be readable only by you: the OpenSSH manual (opens in a new tab) states that ssh ignores a private key file that others can access. ssh -i key.pem user@host selects a specific key, and scp file user@host:/path copies a file over SSH.

Reading logs

Programs report what they are doing in logs, and Linux keeps them in two places. Plain text files live under /var/log and are read with ordinary text tools:

bash
tail -n 50 /var/log/nginx/error.log      # the last 50 lines
tail -f /var/log/nginx/error.log         # follow new lines as they arrive
grep -i "timeout" /var/log/nginx/error.log | tail -n 5

Services run by systemd write to the journal, which you query with journalctl:

bash
journalctl -u nginx --since today    # one unit, since midnight
journalctl -u nginx -f               # follow
journalctl -u nginx -p err -b        # errors or worse, since the last boot
journalctl -k                        # kernel messages

Look for the first error after the last normal line, because later errors are often consequences of it. Reading the whole system journal needs sudo or membership of a group such as systemd-journal or adm.

Shell scripts

A script is a text file of commands that the shell runs from top to bottom. A few lines make one dependable:

bash
#!/usr/bin/env bash
set -euo pipefail

input="$1"
grep "ERROR" "$input" | sort | uniq -c

The first line, the shebang, names the interpreter. set -e stops the script when a command fails, -u treats an unset variable as an error, and -o pipefail makes a pipeline fail when any stage fails. $1 is the first argument, $# is the number of arguments and "$@" is all of them. Quote every expansion ("$input", not a bare variable) so that a value containing spaces stays one word. Make the file executable with chmod +x, write error messages to standard error with >&2, and exit with a non-zero status on failure so that callers, including CI systems, can react.

Worked example: Triage an API log in a sandbox directory, then freeze the commands into a script

The scenario: a model-serving API writes one line per request, and users report failures. You will build a sandbox directory, question the log with pipelines, and turn the answer into a script. Everything runs in Bash on Linux, in WSL or in the macOS terminal, with nothing to install.

Step 1. Create the log and set its mode. The columns are timestamp, level, method, path, status code and duration in milliseconds.

bash
mkdir -p ~/shell-lab/logs && cd ~/shell-lab
cat > logs/api.log <<'EOF'
2026-03-02T09:00:01Z INFO POST /v1/chat 200 412
2026-03-02T09:00:02Z INFO GET /health 200 3
2026-03-02T09:00:04Z INFO POST /v1/chat 200 388
2026-03-02T09:00:07Z ERROR POST /v1/embed 500 30001
2026-03-02T09:00:09Z INFO GET /health 200 2
2026-03-02T09:00:12Z INFO POST /v1/chat 200 1240
2026-03-02T09:00:15Z WARN POST /v1/chat 429 5
2026-03-02T09:00:18Z ERROR POST /v1/embed 500 30002
2026-03-02T09:00:21Z INFO POST /v1/chat 200 455
2026-03-02T09:00:25Z INFO GET /health 200 3
2026-03-02T09:00:30Z ERROR POST /v1/embed 500 30000
2026-03-02T09:00:33Z INFO POST /v1/chat 200 2210
EOF
chmod 640 logs/api.log
ls -l logs/api.log | cut -c1-10
text
-rw-r-----

cat > file <<'EOF' is a here-document: the shell feeds the lines up to EOF to cat as standard input, and > sends its output into the file. Mode 640 reads as rw- (4 + 2) for you, r-- (4) for the group and --- (0) for everyone else.

Step 2. Ask questions with pipelines.

bash
grep -c ' ERROR ' logs/api.log
awk '{print $5}' logs/api.log | sort | uniq -c | sort -rn
grep ' ERROR ' logs/api.log | awk '{print $4}' | sort | uniq -c

Output, with the leading spaces that uniq -c adds trimmed:

text
3
8 200
3 500
1 429
3 /v1/embed

The second command is the pattern to memorise. awk '{print $5}' keeps the fifth column, sort puts equal values next to each other, uniq -c collapses each run into one line with a count, and sort -rn orders the counts from largest to smallest. Check it by hand: 8 + 3 + 1 = 12, the number of lines. The third command shows that all three errors come from one path, /v1/embed.

Step 3. Keep results and error messages apart. Ask grep to count in two files, one of which does not exist:

bash
grep -c ' 500 ' logs/api.log logs/missing.log > counts.txt 2> problems.txt
echo "exit status: $?"
cat counts.txt problems.txt
text
exit status: 2
logs/api.log:3
grep: logs/missing.log: No such file or directory

The count travelled on standard output into counts.txt. The complaint travelled on standard error into problems.txt. Exit status 2 tells any caller that something went wrong even though a result was produced.

Step 4. Freeze the triage as a script. Save this as log-report.sh:

bash
#!/usr/bin/env bash
# Summarise an API log: requests, server errors and slow requests.
set -euo pipefail

if [ "$#" -ne 1 ]; then
  echo "usage: $0 LOG_FILE" >&2
  exit 2
fi

log_file="$1"
slow_ms="${SLOW_MS:-1000}"   # environment variable, 1000 when unset

if [ ! -r "$log_file" ]; then
  echo "error: cannot read $log_file" >&2
  exit 2
fi

total=$(awk 'END { print NR }' "$log_file")
errors=$(awk '$5 >= 500 { n++ } END { print n + 0 }' "$log_file")
slow=$(awk -v limit="$slow_ms" '$6 > limit { n++ } END { print n + 0 }' "$log_file")

echo "requests: $total"
echo "server errors: $errors"
echo "slower than $slow_ms ms: $slow"

if [ "$errors" -gt 0 ]; then
  exit 1   # non-zero tells the caller something needs attention
fi

Run it three ways:

bash
chmod +x log-report.sh
./log-report.sh logs/api.log; echo "exit status: $?"
SLOW_MS=400 ./log-report.sh logs/api.log; echo "exit status: $?"
./log-report.sh; echo "exit status: $?"
text
requests: 12
server errors: 3
slower than 1000 ms: 5
exit status: 1
requests: 12
server errors: 3
slower than 400 ms: 7
exit status: 1
usage: ./log-report.sh LOG_FILE
exit status: 2

What to notice:

  • Permissions. If you skip chmod +x, the shell answers Permission denied with exit status 126. The execute bit is what makes a file runnable.
  • Environment. SLOW_MS=400 in front of the command placed the variable in that one process's environment. Without it the default applies. Five requests took more than 1000 ms (1240, 2210 and the three near 30000), and seven took more than 400 ms once 412 and 455 are included.
  • Exit status. 1 means the script ran and found server errors. 2 means it was used wrongly, and the usage message went to standard error, so it would not pollute a file that captures the report.

The reading: twelve requests, three server errors, all on /v1/embed, each lasting almost exactly 30 seconds. That pattern points at a timeout while waiting for something behind the embedding endpoint, not at a slow model. On a real server the next step is that service's log around 09:00:07, for example with journalctl -u, and the script is now something a teammate or a CI job can rerun.

Edge cases and limitations

set -e does not see a failure inside a pipeline
Bash's errexit option ignores the status of every pipeline stage except the last unless pipefail is also set. It also ignores a failing command that is the test of an if or while, or any part of an && or || list other than its final command. A script with only set -e can print success after its first stage failed. GitHub Actions shows how easy this is to hit: its documentation says a run step with no shell setting runs bash -e, while a step that sets shell to bash runs bash with -eo pipefail. Put set -euo pipefail at the top of your own scripts so their behaviour does not depend on who calls them.
The order of redirections changes the result
Redirections are applied from left to right. The Bash manual gives the example itself: ls > dirlist 2>&1 sends both streams to the file, but ls 2>&1 > dirlist sends only standard output there, because standard error was made a copy of standard output while that still pointed at the terminal. If an error message still appears on screen after you thought you redirected everything, check the order.
sudo does not apply to a redirection
In the command sudo echo x=1 > /etc/app.conf, your own shell opens /etc/app.conf before sudo starts, so the command fails with Permission denied although it begins with sudo. Redirection is done by the shell, not by the program being run. Pipe into a program that runs as root instead, for example echo x=1 | sudo tee /etc/app.conf.
Write permission on a directory lets you delete files you cannot edit
Removing a file changes the directory, not the file. The coreutils manual defines write permission on a directory as permission to create and remove files in it, so a user who has that permission, together with execute permission to reach the files, can delete or replace a read-only file inside it. This is why world-writable directories such as /tmp carry the sticky bit, which stops unprivileged users removing files they do not own. When you protect a file, check the mode of its directory as well.
A wrapper script can swallow the stop signal
When a shell script starts the real program as a child process, a stop signal such as SIGTERM is delivered to the script. Bash does not pass it on to the child, so the program may never get the chance to shut down cleanly. Docker's build guide shows the fix used by the Postgres official image: its entrypoint script ends with exec, so the application replaces the shell, becomes PID 1 of the container and receives the signals itself. End any launcher script with exec in front of its last command.
A running service does not see variables you set afterwards
The environment is copied when a process starts. Exporting a variable in your SSH session changes nothing for a service that systemd started, and editing the unit changes nothing until the service is restarted. The systemctl manual separates three commands that are easy to confuse: daemon-reload re-reads unit files, reload asks the service to re-read its own configuration, and restart stops and starts the process. After changing an Environment line in a unit file by hand, run daemon-reload, then restart, then check the service's log. systemctl edit performs the reload for you when the editor closes.

When to use it, and when something simpler is enough

Use it when

  • You are on a server, container or CI runner with no graphical tools and need to inspect files, processes, services or logs through a terminal.
  • The job is mostly calling existing programs in sequence and passing text between them, such as filtering a log, counting lines or restarting a service.
  • A task will be repeated by you, a colleague or a CI system (installing dependencies, running tests, collecting diagnostics) and fits in a script short enough to read in one sitting.
  • You need a single pass over text files that fit on one machine, where a streaming pipeline avoids loading the data into memory.

Think twice when

  • The script is passing about 100 lines or needs non-trivial control flow or data structures. Google's shell style guide says to rewrite in a more structured language at that point.
  • The data is structured, such as JSON, CSV with quoted fields or binary files. Line-oriented tools misread it, so use a parser such as jq, Python or a database.
  • The same change must be made on many servers and kept consistent. Use infrastructure as code or configuration management, not a loop of SSH commands.
  • The action is destructive and cannot be tested first, such as a recursive delete built from variables. Print the exact paths first, or use a tool with a dry-run mode.

A simpler alternative. For a one-off task, type the commands by hand and paste them with their output into the ticket or runbook. That is already a record someone else can follow. For a handful of project commands, a Makefile or the task runner your language already has may be enough. Move to a script when you are typing the same sequence for the third time, or when a machine such as a CI server has to run it.

Key takeaways

  • Linux keeps everything in one directory tree, and every file has an owner, a group and nine permission bits that read as three octal digits, such as 640 for rw-r-----.
  • A process is a running program with a PID, an environment and an exit status. Stop one with SIGTERM first, because SIGKILL cannot be caught and skips cleanup.
  • A pipe connects the standard output of one program to the standard input of the next, and a pipeline's exit status is that of its last command unless pipefail is set.
  • Environment variables are copied from parent to child when a process starts, so a change reaches a service only after the service is restarted with the new setting.
  • SSH logs you in with a key pair. The server holds the public key, and your private key must be readable only by you or the client will refuse to use it.
  • Find problems by filtering logs with grep, tail and journalctl, and keep any sequence you will need again in a short script that starts with set -euo pipefail and returns a meaningful exit status.

Example 1 of 5

GitHub's Scripts to Rule Them All: the same script names in every project

GitHubDocumented in an engineering article

GitHub's engineering blog post Scripts to Rule Them All (June 2015) and the README of the github/scripts-to-rule-them-all repository describe a convention that GitHub says it uses for all of its own projects: the same set of script names, kept in a script directory. [17][18]

The problem

The post describes a company with a lot of software and a lot of potential contributors. It says that getting from git clone to a running project in a development environment is imperative for fast, reliable contributions, and that contributors should not need an extensive knowledge of how each project works. Without agreed names, a newcomer would have to learn each project's own commands for installing dependencies, starting the application and running the tests (our reading of the problem). GitHub states the goal as a consistent bootstrapping experience across all projects, which reduces friction and encourages contribution.

Where this topic fits

This is the last topic of the lesson, small scripts for repeatable tasks, used as a team convention. The scripts are the entry points between a person or a CI server and the project's real tooling. A contributor runs script/setup once after cloning and script/test before pushing, and the CI server runs script/cibuild. Inside, each script calls whatever the project needs, such as a package manager or a test runner.

How it is applied, step by step

  1. Each repository gets a script directory with executable files under fixed names: bootstrap, setup, update, server, test, cibuild and console.
  2. script/bootstrap only installs or updates dependencies. Depending on the project it might call bundle install, npm install, carthage bootstrap or git submodule update.
  3. script/setup calls script/bootstrap and then puts the project into its initial state, so a new contributor runs one command after cloning.
  4. script/test runs the test suite. The README recommends accepting an optional file path so that one test can be run alone, and running linters near the start so the script fails sooner.
  5. script/cibuild is what the CI server calls. It prepares the CI environment and then calls script/test, so developers and CI run the tests the same way.
  6. Because only the names are standard, each script can be written in whatever language suits the project. The repository's example bootstrap, setup, test and cibuild scripts are short `sh` scripts for a Rails application, and each one runs `set -e` and changes to the repository root before doing anything else.

Why this approach fits

The hard part of joining a project is knowing which commands to run, in which order, for this repository. A script with a predictable name records that knowledge next to the code, is versioned with it, and is run the same way by people and by CI, so it cannot quietly go stale the way a README section does. Shell suits the job because each script mostly calls other tools and passes their exit status along.

Limitation or tradeoff

The convention standardises names, not behaviour. Nothing checks that script/setup in one repository does what it does in another, and a script that works on its author's laptop can still fail on a different operating system. The scripts need maintenance like any other code. GitHub archived the example repository in March 2024, so treat it as a description of a pattern, not as a maintained template. A build with a real dependency graph needs a build tool, not a folder of scripts.

What the sources document

  • GitHub says it has normalised on a set of script names for all of its projects and lists seven: script/bootstrap (installs or updates all dependencies), script/setup (sets up a project for first use), script/update, script/server (starts the app), script/test (runs tests), script/cibuild (invoked by continuous integration servers) and script/console. [17]
  • The post says script/setup initially calls script/bootstrap, and that script/test can be run on its own in a development environment but is also called by script/cibuild on the CI server. [17]
  • The post says the scripts can be written in whichever language is appropriate, and that script/bootstrap might call bundle install, npm install, carthage bootstrap or git submodule update. [17]
  • The repository README says a good pattern for script/test is an optional file path argument for running single tests, and suggests putting linting towards the beginning of the script so that it fails faster. [18]
  • The repository page states that the repository was archived by its owner on 8 March 2024 and is now read-only. [18]

The facts above come from the cited sources. The steps and analysis in this example are our explanation of how they fit together.

Example 2 of 5

Ollama on Linux: a model server run as a systemd service under its own user

OllamaDocumented in official docs

Ollama is a tool for running open-weight language models on your own machine. Its Linux guide, FAQ and troubleshooting page describe how the server is installed as a systemd service, configured through environment variables and inspected through the journal. [19][20][21][8]

The problem

A model server has to keep running after the person who installed it logs out, come back after a reboot or a crash, and be reachable by other programs. It should not run as root, and its settings, such as the address it listens on and the directory that holds the model files, differ from one machine to the next. The documentation handles each of these with standard Linux mechanisms, not with an Ollama-specific tool.

Where this topic fits

Four ideas from this lesson appear together. A dedicated user and group own the service's files (permissions). A unit file tells systemd how to run ollama serve (services). Environment= lines carry the configuration (environment variables). journalctl -u ollama shows what the server printed (logs).

How it is applied, step by step

  1. Create a system user and group named ollama with no login shell and a home directory at /usr/share/ollama, so the server runs under its own identity.
  2. Write a unit file at /etc/systemd/system/ollama.service whose ExecStart line runs ollama serve, with User and Group set to ollama and Restart=always so that systemd starts the process again if it exits.
  3. Run systemctl daemon-reload so systemd reads the new file, systemctl enable ollama so the service starts at boot, and systemctl start ollama to start it now.
  4. To change a setting, run systemctl edit ollama and add an Environment line under the Service section, for example OLLAMA_HOST to change the listening address. Then reload and restart, so that a new process starts with the variable in its environment.
  5. If the models are moved to another directory with OLLAMA_MODELS, give the ollama user ownership of that directory with chown, because the service reads and writes it as that user.
  6. When something goes wrong, read the server's output with journalctl -u ollama. The -e option jumps to the most recent entries.

Why this approach fits

systemd already solves supervision: start at boot, restart on failure, a dedicated user and captured output. By shipping a unit file, Ollama gets all of that without writing its own supervisor, and administrators manage it with the same systemctl and journalctl commands they use for every other service on the machine. Environment variables suit the configuration because the values are few and differ per machine.

Limitation or tradeoff

Configuration ends up split between the unit file, its drop-in override and the program's defaults, and a change does nothing until the service is restarted. Exporting OLLAMA_HOST in your own shell has no effect on the service. Binding to 0.0.0.0 makes the server listen on every network interface, so access then has to be restricted some other way, such as a firewall. The systemd manual also warns that environment variables set for a unit are not a safe place for secrets. None of this applies inside a container, where the troubleshooting page says the logs go to the container's standard output and standard error.

What the sources document

  • The Linux guide creates the account with useradd -r -s /bin/false -U -m -d /usr/share/ollama ollama and gives a unit file with ExecStart=/usr/bin/ollama serve, User=ollama, Group=ollama, Restart=always and RestartSec=3. [19]
  • The guide starts the service with systemctl daemon-reload and systemctl enable ollama, says to customise it with systemctl edit ollama or an override file at /etc/systemd/system/ollama.service.d/override.conf, and gives journalctl -e -u ollama for viewing the logs of Ollama running as a startup service. Amazon EC2: SSH login to a cloud server with a key file only you can read

Amazon Web ServicesDocumented in official docs

The Amazon EC2 User Guide documents how to connect to a Linux instance with an SSH client using the private key file of the key pair chosen when the instance was launched. Its prerequisites and troubleshooting pages cover the file permissions the key needs and the host fingerprint check. [22][23][24][9][3]

The problem

The owner of a new cloud instance has to reach it across the internet without anyone else being able to do the same, and should be sure that the machine answering is really that instance. The guide's troubleshooting page documents a failure nearly every newcomer meets: the private key file can be read by other users of the local computer, so the SSH client ignores it and the login ends in Permission denied (publickey).

Where this topic fits

Two sections of this lesson meet here: SSH and file permissions. Before the SSH step, the instance was launched with a key pair and its security group was set to allow inbound SSH from your address. After it, you have a shell on the instance as the image's default user and everything else in this lesson applies.

How it is applied, step by step

  1. Look up the instance's public DNS name and the default user name of its image. The guide lists ec2-user for Amazon Linux, ubuntu for Ubuntu and admin for Debian.
  2. Restrict the private key file with chmod 400. Octal 400 is read permission for the owner and nothing for the group or for others.
  3. Optionally fetch the instance's host key fingerprints from its console output, where they appear between BEGIN and END SSH HOST KEY FINGERPRINTS lines, using the web console or the aws ec2 get-console-output command.
  4. Run ssh with the -i option pointing at the key file and with the user name and host name as the destination.
  5. On the first connection ssh prints the host key fingerprint and asks whether to continue. Compare it with the fingerprint from the console output, then answer yes. The client records the host in its known hosts list.
  6. The server checks that the public half of the offered key is authorised for that account, the client proves it holds the private half, and a shell starts.

Why this approach fits

With key-based login no shared secret is sent to the server, which only ever holds the public half of the pair. The permission rule moves part of the security onto your own machine: a private key that other accounts can read is no longer private, so the client refuses to use it. Checking the fingerprint closes the remaining gap, which is talking to the wrong machine.

Limitation or tradeoff

The scheme is only as good as the handling of the .pem file. Anyone who copies it can log in, and the troubleshooting page has a separate section for people who have lost theirs. One key shared by a team leaves no record of who logged in. The guide marks the fingerprint check as optional, and it is easy to type yes without comparing anything. The instance must also accept SSH traffic from your address, so a blocked port looks like a timeout, not a permission error.

What the sources document

  • The prerequisites page says that for SSH connections you must set file permissions so that only you can read the private key, gives the command chmod 400 key-pair-name.pem, and says that without these permissions you cannot connect to the instance using this key pair. [23]
  • The troubleshooting page says that if the private key can be read or written by anyone but you, SSH ignores the key. It reproduces the warning UNPROTECTED PRIVATE KEY FILE, in which permissions 0777 on the key file are called too open and the login ends in Permission denied (publickey), and it gives chmod 0400 as the fix. [24]
  • The guide gives the connection command as ssh -i followed by the path of the .pem file and instance-user-name@instance-public-dns-name, and its list of default user names includes ec2-user for Amazon Linux, ubuntu for Ubuntu and admin for Debian. [22][23]
  • The guide says verifying the fingerprint protects against man-in-the-middle attacks, that the fingerprint is found in the instance's console output under BEGIN SSH HOST KEY FINGERPRINTS, and that if the fingerprints do not match someone might be attempting such an attack. [23][22]
  • The OpenSSH manual says private key files should be readable by the user but not accessible by others, and that ssh will simply ignore a private key file if it is accessible by others. [9]

Netflix: the first 60 seconds of a performance investigation on a Linux server

The Netflix page still blocked automated fetching on review (HTTP 403), so this example was checked against the PDF copy of the post that its author hosts on his own site. [25][26]

The problem

The post describes a very large fleet of Linux instances on EC2 that is watched by Netflix's own monitoring tools, Atlas and Vector, which solve most issues. Sometimes an engineer still has to log in to one instance. The question the post answers is what to check in the first minute, so that the engineer gets a high-level picture of resource usage and running processes, and knows which resources can be ruled out, before reaching for deeper tools.

Where this topic fits

This is the process and log reading part of the lesson used as a fixed checklist over SSH. Each command prints a text snapshot of one resource: the kernel's message log, the run queue, CPU use per process, disks, memory, the network. Nothing on the server is changed. The outcome is a direction for the rest of the investigation.

How it is applied, step by step

  1. Log in to the instance and run uptime to read the three load averages, which show whether demand has been rising or falling over the last 1, 5 and 15 minutes.
  2. Run dmesg piped into tail to read the last ten kernel messages. The post's sample output shows the out-of-memory killer ending a process and TCP dropping a request, either of which would explain a performance problem.
  3. Run vmstat 1 and read the r column (processes running or waiting for a CPU), free memory, the swap columns si and so, and the breakdown of CPU time.
  4. Run mpstat -P ALL 1 and pidstat 1 to see whether one CPU is much busier than the rest and which processes are using CPU. In the post's sample, pidstat points at two java processes.
  5. Run iostat -xz 1, free -m and the two sar commands to check disks, memory and the network in turn.
  6. Finish with top as a cross-check, and note which resources looked healthy so that they can be left out of the follow-up work.

Why this approach fits

A fixed, ordered list beats improvisation while a system is failing. It takes about a minute, touches every major resource once, and produces plain text that can be pasted into an incident record. Each command is a small tool with one job, and the one pipe in the list, dmesg | tail, is this lesson's pattern in its smallest form: take a long output and keep only the end.

Limitation or tradeoff

The checklist shows one machine at one moment. The post itself says that load averages cannot be properly understood without other tools, and that top makes patterns over time hard to see and can lose evidence of intermittent problems when the screen clears. Several of the commands need the sysstat package, which is not installed everywhere, and output on a current distribution may be laid out differently from the 2015 samples. For a whole fleet, the post says monitoring tools solve most issues and logging in is the exception.

What the sources document

A shell pipeline that summarised 3.46 GB of chess games faster than a Hadoop cluster

Documented in an engineering article

In the 2014 article Command-line Tools can be 235x Faster than your Hadoop Cluster, engineer Adam Drake reworks a published Hadoop job that counted wins, losses and draws in a collection of chess game files, using only standard shell tools on his laptop. The article gives every pipeline and its timing. [27]

The problem

The original analysis, by another author, used Amazon Elastic MapReduce with 7 c1.medium machines and took about 26 minutes to process about 1.75 GB of game records. That author had also run short of memory when loading games locally. The task itself is small: read every file, keep the lines that hold a game's result, and count the three outcomes. Drake's question was whether a cluster was needed at all.

Where this topic fits

This is the pipes section of the lesson applied to data processing. A directory of text files is the input, each stage is one standard tool, and the stages are joined by pipes so that data streams through without being loaded into memory. The output is four numbers: games, white wins, black wins and draws.

How it is applied, step by step

  1. Measure an upper bound first. cat *.pgn > /dev/null reads all 3.46 GB and throws it away, which took about 13 seconds on his machine.
  2. Build the simplest pipeline. cat streams the files, grep keeps the Result lines, sort groups equal lines and uniq -c counts them. This took about 70 seconds.
  3. Replace sort and uniq with one awk program that increments three counters, so nothing has to be sorted or stored. This took about 65 seconds.
  4. Notice in htop that grep is using one full CPU core, then use find and xargs with -P4 to run four grep processes in parallel over the files. This took about 38 seconds.
  5. Drop grep by letting awk do the filtering, hand each parallel awk several files, and add a final awk that sums the totals from the parallel processes. This took about 18 seconds.
  6. Swap gawk for mawk, a faster awk implementation, which brought the run to about 12 seconds.

Why this approach fits

The job is a single pass over text with a tiny amount of state, three counters, which is what stream tools are built for. Pipes give concurrency for free because every stage is its own process, and xargs -P spreads independent files over CPU cores. There is no cluster to start, no data to upload and no framework to learn. The whole program fits on one line and can be built one stage at a time, checking the output after each.

Limitation or tradeoff

This is one person's benchmark on one laptop against another person's small cluster, on data that fits on a single disk, and the speed-up figure allows for his dataset being about twice the size of the original. It does not show that pipelines beat distributed systems in general: the article says tools like Hadoop may be required when the data is huge or distributed processing is really needed. The parallel version does not preserve input order, and line-oriented tools break down when a record spans several lines or contains quoted delimiters.

What the sources document

  • Drake reports that the original Hadoop job processed about 1.75 GB containing around 2 million chess games in about 26 minutes on 7 c1.medium machines, and that he compiled a 3.46 GB dataset, about twice that size, for his own test. [27]
  • The first pipeline, cat *.pgn | grep "Result" | sort | uniq -c, gave the results in about 70 seconds. Replacing sort and uniq with awk gave about 65 seconds, with memory usage he describes as effectively zero because only the counts are stored. [27]
  • Parallelising with find and xargs -P4 brought the time to about 38 seconds and then about 18 seconds, and switching to mawk brought it to about 12 seconds, which he puts at about 270 MB per second and around 235 times faster than the Hadoop implementation. [27]
  • He notes that such a parallel pipeline does not guarantee delivery order, and demonstrates that pipeline stages run at the same time with the command sleep 3 | echo "Hello world.". [27]
  • His conclusion says that tools like Hadoop may be required for a huge amount of data or a real need for distributed processing, but that more often than not he sees Hadoop used where a traditional relational database or other solutions would be far better in performance, cost of implementation and ongoing maintenance. [27]

4Common mistakes

  1. Running chmod 777, or chmod -R 777, to make a Permission denied error go away.

    Why it causes problems
    Mode 777 lets every account on the machine read, change and replace the file. On a config or secrets file that is a leak. On a script that root or a service later runs, it lets any user run code with those privileges. Some programs then refuse to work at all: ssh ignores a private key that others can access.
    How to recognise it
    ls -l shows rwxrwxrwx, or find . -type f -perm -o+w lists files that others can write. In code review, any 777 in a script or Dockerfile deserves a question.
    How to fix it
    Work out who needs access: which user the failing process runs as (the User line of its unit, or the USER column of ps aux) and which bit is missing. Then change the owner or group with chown, or grant the narrowest mode that works, typically 640 for files and 750 for directories.

  2. Reaching for kill -9 as the first way to stop a process.

    Why it causes problems
    SIGKILL cannot be handled, so the program cannot finish requests in flight, flush buffers or remove lock files. A database or model server may need recovery on its next start, and a supervised service may simply be started again by systemd while the cause stays unknown.
    How to recognise it
    Shell history or runbooks that contain kill -9 or pkill -9 with no earlier plain kill. Stale lock files or a recovery message in the log after a restart.
    How to fix it
    Send SIGTERM with a plain kill and the PID, or use systemctl stop for a service, and wait. Check with ps or systemctl is-active that it stopped. Use kill -9 only when the process has ignored SIGTERM, and read its log first to learn why.

  3. Leaving variable expansions unquoted in scripts, for example rm -rf $dir/cache.

    Why it causes problems
    An unquoted value that contains a space becomes two arguments, so the command acts on the wrong paths. If the variable is empty or misspelled, the path collapses to /cache, and the script deletes something it was never meant to touch.
    How to recognise it
    Run ShellCheck on the script, which flags unquoted expansions. Test with a file name that contains a space. A script that works on your data and fails on a customer's is a typical sign.
    How to fix it
    Put double quotes around every expansion, start scripts with set -euo pipefail so that an unset variable stops the run, and print a destructive command with echo before running it for real.

  4. Putting passwords and API keys in a unit's Environment lines, in shell profiles or in command-line arguments.

    Why it causes problems
    The systemd manual warns that environment variables set for a unit are exposed to unprivileged clients and are passed down the process tree, so they are not suitable for secrets. Command-line arguments are visible to other users in the process list, and shell profiles end up in backups and screen shares.
    How to recognise it
    systemctl cat on the service shows a secret in plain text, ps aux shows a token inside a command line, or grep finds a key in a shell profile or in the repository history.
    How to fix it
    Keep secrets in a file that only the service user can read (mode 600), pass them with the credential settings the systemd manual recommends, such as LoadCredential, or use the platform's secret manager. Rotate any secret that has already been exposed this way.

  5. Answering yes to the SSH host key question without checking, or switching host key checking off.

    Why it causes problems
    The fingerprint check is the only proof that the machine answering is the one you meant to reach. If you skip it, a mistyped address or an intercepted connection goes unnoticed, and you may type sudo passwords or paste credentials into the wrong machine.
    How to recognise it
    StrictHostKeyChecking set to no in an SSH config file or script, or a habit of deleting lines from known_hosts whenever the warning about a changed host key appears.
    How to fix it
    Get the fingerprint through a trusted channel, such as the cloud console output or the person who administers the server, and compare it before typing yes. When a host key changes, find out why (a rebuilt server, a reused address) before removing the old entry.

  6. Starting a long job directly in an SSH session and then closing the laptop.

    Why it causes problems
    When the connection drops, the terminal goes away and the session's processes are sent SIGHUP, whose default action is to terminate them. A migration or model download that needed three hours dies partway through, sometimes leaving partial state behind.
    How to recognise it
    A job that is missing from ps when you reconnect, with no error in its own output, or work that fails only on unstable connections.
    How to fix it
    Run long work under something that outlives your session: a systemd service for real workloads, or tmux, screen or nohup for ad-hoc jobs. Redirect the output to a log file so that you can follow progress with tail -f after reconnecting.

Exercise 1

Write a script that counts server errors per endpoint and fails above a limit

CodingIntermediateAbout 45 min (estimate)Hypothetical scenario

A gateway in front of a model API writes one line per request with the same six columns as the worked example: timestamp, level, method, path, status code and duration in milliseconds. Create the sample log, then write endpoint-gate.sh, a check that an on-call engineer or a CI job can run. You need only Bash and the standard text tools (awk, sort, uniq), on Linux, WSL or macOS.

bash
mkdir -p ~/shell-lab && cd ~/shell-lab
cat > gateway.log <<'EOF'
2026-04-14T02:10:01Z INFO GET /v1/models 200 12
2026-04-14T02:10:03Z INFO POST /v1/chat 200 640
2026-04-14T02:10:04Z ERROR POST /v1/embed 503 15
2026-04-14T02:10:06Z INFO POST /v1/chat 200 702
2026-04-14T02:10:09Z ERROR POST /v1/embed 503 14
2026-04-14T02:10:11Z ERROR POST /v1/chat 500 9120
2026-04-14T02:10:12Z INFO GET /v1/models 200 11
2026-04-14T02:10:15Z ERROR POST /v1/embed 503 16
2026-04-14T02:10:18Z INFO POST /v1/chat 200 598
2026-04-14T02:10:21Z WARN POST /v1/chat 429 4
2026-04-14T02:10:22Z ERROR POST /v1/embed 502 31
2026-04-14T02:10:26Z INFO POST /v1/embed 200 88
2026-04-14T02:10:29Z INFO GET /health 200 2
2026-04-14T02:10:31Z ERROR POST /v1/chat 500 8870
2026-04-14T02:10:35Z INFO POST /v1/chat 200 611
2026-04-14T02:10:38Z INFO GET /health 200 3
EOF

The script takes the log file as its only argument and reads a limit from the environment variable MAX_5XX, which defaults to 3.

Requirements

  • Print one line per path that has at least one response with a status of 500 or above, in the form COUNT PATH, sorted with the largest count first. Print these lines on standard output.
  • For every path whose count is greater than MAX_5XX, print a line beginning with FAIL: on standard error, and make the script exit with status 1. Exit with status 0 when no path is over the limit.
  • If the log contains no server errors at all, print the single line no server errors and exit with status 0.
  • With no argument, or with a file that cannot be read, print a message on standard error and exit with status 2.
  • Start the script with a shebang line and set -euo pipefail, and quote every variable expansion.

Expected behaviour

With the sample log and the default limit:

text
$ ./endpoint-gate.sh gateway.log; echo "exit status: $?"
4 /v1/embed
2 /v1/chat
FAIL: /v1/embed has 4 server errors (limit 3)
exit status: 1

MAX_5XX=5 ./endpoint-gate.sh gateway.log prints the same two count lines, no FAIL line, and exits with status 0. ./endpoint-gate.sh gateway.log 2>/dev/null prints only the two count lines, which shows that the FAIL line is on standard error. ./endpoint-gate.sh with no argument prints a usage line and exits with status 2.

Hint 1

Build the pipeline at the prompt before you write any script. Start with an awk command that prints the path of every line whose fifth column is 500 or more, then add sort, uniq -c and a numeric sort.

Hint 2

uniq -c pads its counts with spaces. Passing the result through awk with print $1, $2 leaves exactly one space, which makes the lines easy to read back in.

Hint 3

Store the pipeline's output in a variable with command substitution, then loop over it with while read -r count path and a here-string. A loop fed by a pipe runs in a separate process, so a status variable set inside it would be lost.

Hint 4

grep -c exits with status 1 when it counts zero matches, which stops a script under set -e. Counting with awk avoids that.

Show solution

Save this as endpoint-gate.sh and run chmod +x endpoint-gate.sh.

bash
#!/usr/bin/env bash
# Print 5xx counts per path and fail when any path exceeds MAX_5XX.
set -euo pipefail

if [ "$#" -ne 1 ]; then
  echo "usage: $0 LOG_FILE" >&2
  exit 2
fi

log_file="$1"
max_5xx="${MAX_5XX:-3}"

if [ ! -r "$log_file" ]; then
  echo "error: cannot read $log_file" >&2
  exit 2
fi

counts=$(awk '$5 >= 500 { print $4 }' "$log_file" \
  | sort | uniq -c \
  | awk '{ print $1, $2 }' \
  | sort -k1,1nr -k2,2)

if [ -z "$counts" ]; then
  echo "no server errors"
  exit 0
fi

echo "$counts"

status=0
while read -r count path; do
  if [ "$count" -gt "$max_5xx" ]; then
    echo "FAIL: $path has $count server errors (limit $max_5xx)" >&2
    status=1
  fi
done <<< "$counts"

exit "$status"

Runs against the sample log:

text
$ ./endpoint-gate.sh gateway.log; echo "exit status: $?"
4 /v1/embed
2 /v1/chat
FAIL: /v1/embed has 4 server errors (limit 3)
exit status: 1
$ MAX_5XX=5 ./endpoint-gate.sh gateway.log; echo "exit status: $?"
4 /v1/embed
2 /v1/chat
exit status: 0
$ MAX_5XX=1 ./endpoint-gate.sh gateway.log >/dev/null; echo "exit status: $?"
FAIL: /v1/embed has 4 server errors (limit 1)
FAIL: /v1/chat has 2 server errors (limit 1)
exit status: 1
$ ./endpoint-gate.sh; echo "exit status: $?"
usage: ./endpoint-gate.sh LOG_FILE
exit status: 2

How it works, stage by stage. The first awk prints the path of each line whose status is 500 or more, which gives four lines of /v1/embed (three 503s and one 502) and two of /v1/chat. sort puts equal paths together and uniq -c turns each run into a count. The second awk reduces the padding to one space. The last sort orders by the first column as a number, largest first (-k1,1nr), and breaks ties by path (-k2,2).

Three details matter. The pipeline's output is captured with $( ... ) and then read by a while loop through a here-string (<<<), so the loop runs in the script's own shell and the assignment status=1 survives. The FAIL lines go to standard error with >&2, so ./endpoint-gate.sh gateway.log > report.txt stores a clean table while the warning still reaches the terminal or the CI log. And the three exit statuses mean different things to a caller: 0 is healthy, 1 is over the limit, 2 is a misuse of the script.

Check your answer

  • Does the default run print 4 /v1/embed, then 2 /v1/chat, then one FAIL line, and exit with status 1?
  • Does setting MAX_5XX to 5 for one run make the same script exit with status 0?
  • Does adding 2>/dev/null remove only the FAIL line from what you see?
  • Does running the script with no argument exit with status 2 and print nothing on standard output?

Case 4. Works in my terminal, fails at night

text
$ /opt/reports/nightly.sh && echo ok
ok
$ journalctl -u nightly-report -n 2 --no-pager
Mar 03 02:00:01 app-01 nightly.sh[4410]: /opt/reports/nightly.sh: line 6: aws: command not found
Mar 03 02:00:01 app-01 systemd[1]: nightly-report.service: Main process exited, code=exited, status=127/n/a
$ command -v aws
/home/dana/.local/bin/aws

Requirements

  • For each case, state which permission bit, exit status, stream or environment rule explains the output.
  • For each case, give one fix as a concrete command or a concrete change to a line, not a general direction.
  • For each case, name one tempting fix that would hide the problem or make the system less safe.
  • For cases 2 and 4, say which user or environment the failing process runs with and how the transcript shows it.

Expected behaviour

A good answer is four short diagnoses. Each one names a single root cause (a file mode, a directory owner, a pipeline's exit status, a search path), ties it to a specific line of the transcript, and proposes a fix that changes as little as possible. No answer should involve chmod 777, running the client or the service as root, or switching a check off.

Hint 1

In case 1, translate 0644 into three triples and ask which users other than the owner can read the file.

Hint 2

In case 2, the variable did arrive: the process tried to open the new directory. Compare the owner, group and mode of that directory with the user the service runs as.

Hint 3

In case 3, ask which command's exit status the pipeline reports, and what gzip does when its input is empty.

Hint 4

In case 4, exit status 127 has a fixed meaning in the shell. Then ask where the PATH of your terminal comes from.

Show solution

Case 1. Mode 0644 is rw-r--r--: the group and everyone else can read the private key. The OpenSSH client refuses to use a private key that others can access, so this key was never offered and the server answered Permission denied (publickey). Nothing is wrong on the server. Fix: chmod 400 ~/Downloads/customer-prod.pem (600 also works), and preferably move the file into ~/.ssh. Tempting but wrong: running ssh with sudo, or asking the customer to enable password login.

Case 2. The environment variable was applied, because the new process tried to open /data/models. The unit runs as svc-inference, shown by systemctl show -p User. The directory is owned by root, group root, with mode drwxr-x--- (750). svc-inference is neither the owner nor, as far as the transcript shows, in group root, so the --- triple for others applies and the open fails with errno 13. Fix: sudo chown -R svc-inference:svc-inference /data/models, then sudo systemctl restart inference-api and read the journal again. Tempting but wrong: chmod -R 777 /data/models, or changing the unit to User=root.

Case 3. pg_dump failed, but a pipeline reports the exit status of its last command, and gzip succeeded: it compressed an empty input into a valid 20-byte file. set -e therefore saw success, the script printed backup complete, and the exit status was 0. Fix: change the second line to set -euo pipefail, so that the failed first stage fails the pipeline and stops the script before the message. Writing to a temporary file and renaming it only after success would also stop an empty file from replacing a good backup. Tempting but wrong: checking only that backup.sql.gz exists.

Case 4. Exit status 127 means the shell could not find the command. In Dana's terminal, aws is found in /home/dana/.local/bin, a directory her shell's start-up files add to PATH. A systemd service does not read those files and starts with its own environment, so the same script cannot find aws when the unit runs it. Fix: call the program by its absolute path in the script, or install it in a directory on the system path such as /usr/local/bin, or add an Environment=PATH=... line to the unit and restart it. Tempting but wrong: wrapping line 6 in || true so that the unit reports success.

The four cases share one habit: read the exact message, turn the number in it (a mode, an errno, an exit status) back into its meaning, and find which user and which environment the failing process had.

Check your answer

  • Did you identify case 1 as a problem on the client, fixed by a mode of 400 or 600 on the key file?
  • Did you fix case 2 by changing ownership of the directory, without widening its mode to others?
  • Did you explain case 3 through the pipeline's exit status and fix it with pipefail?
  • Did you connect status 127 in case 4 to the PATH of the service, not to a missing installation?

    When to use it
    Every time you write or change a script. Paste the worked example's script into it, then remove a pair of quotes and see what it reports.
