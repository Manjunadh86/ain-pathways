Prompt Management and Versioning

Prompt management is the practice of keeping prompts as named, versioned artifacts instead of loose strings in code. Every change creates a new immutable version, environments reach a version through a movable label, and each response can be traced to the version that produced it. Versioning is what makes testing, gradual rollout and rollback of a prompt possible.

1Overview

Why it matters

A prompt change alters what a product does as much as a code change does, yet no compiler, type checker or unit test sees it. Research on few-shot prompts found that subtle formatting changes moved accuracy by up to 76 points on one open model (Sclar and colleagues (opens in a new tab)), so a harmless-looking rewording can break behaviour you were not looking at. Without versions you cannot say which wording was live when a user complained, you cannot reproduce an old answer, and you cannot undo a bad edit without another deployment.

Anyone who ships an LLM feature meets this problem: the engineers who edit prompts, the product and domain experts who want to fix one sentence without waiting for a release, and the people on call who must undo a bad change quickly. The practice also explains the tools you will meet in real projects (Langfuse, MLflow, LangSmith, Amazon Bedrock Prompt management, LaunchDarkly). Their names for things differ, but they share the same few ideas.

Key terms

Prompt version
An immutable snapshot of a prompt template together with the settings that shape its output, such as the model and its parameters. Changing anything creates a new version.
Prompt registry
A store, usually with a user interface and an SDK, that holds named prompts with their versions and labels so that applications and people can fetch and edit them.
Label (alias, tag)
A human-readable name such as production that points to one version and can be moved to another. Langfuse calls it a label, MLflow an alias and LangSmith a tag.
Environment
A deployment target such as staging or production. Registries usually model it as a label that each environment resolves at runtime.
Promotion
Moving a label to a newer version, normally after that version has passed evaluation, so that an environment starts serving it.
Rollback
Moving a label back to an earlier version. Because versions never change, the older prompt behaves as it did before.
Canary (guarded rollout)
Serving a new version to a small share of traffic while comparing its metrics with the current version, and widening the share only if they hold.
Stale-while-revalidate
A caching rule: when a cached entry has expired, serve it immediately while refreshing it in the background, so that callers never wait for the network.
Protected case
An eval case that must keep passing. A candidate that fails one is blocked even if its average score improves. The term is used in this lesson and is not a product feature. It is unrelated to Langfuse's protected prompt labels, which control who may move a label.
Trace
The recorded path of one request through an application, including which prompt version each model call used.

2Explanation

Introduction

In your first LLM feature the prompt is a string in a Python file. Editing it feels as light as editing a message: change the words, run the app, ship. That stops working the first time someone asks which wording was live on Tuesday when the refund answers went wrong, or when a domain expert wants to fix one sentence without waiting for a release, or when a small rewording quietly breaks a behaviour nobody was testing.

The underlying problem is that a prompt is configuration that executes. It changes what the product does as much as code does, yet it is edited like prose and reviewed by eye. If a prompt is an unversioned string, every edit is an untracked experiment on your users, and nobody can later say exactly which experiment a given answer belonged to.

Software teams solved the same problem for code long ago, and prompt management borrows the answer. Think of a printed book. You never rewrite a printed edition. You print a new edition, give it a number, and tell the bookshop which edition to stock. Prompt management rests on four ideas:

  • Version. An immutable snapshot of the prompt, numbered or hashed. An edit creates a new version and never changes an old one.
  • Label. A movable name such as production that points at one version. Applications ask for the label, so changing what runs means moving the label.
  • Evidence. Eval results and traces that name the version they came from, so a version is judged on data and not on impressions.
  • Rollout and rollback. A version is promoted through staging to production, in steps when the risk calls for it, and the label is moved back if it misbehaves.

A registry is the store that holds all of this: named prompts, their versions and labels, usually with a user interface for people and an SDK for applications. Some teams use a hosted registry, some keep prompts in git, and some do both.

This lesson builds on Evaluating LLM Applications, which supplies the evidence, and on Prompt Engineering, which covers writing the prompt itself. It explains what a version should contain, how labels work, where prompts should live, how to link versions to evals and traces, and how to roll out and roll back safely. A runnable registry in the worked example and five documented systems make each idea concrete.

How it works

What goes into a version

A version should hold everything that changes the output, not only the template text. If the model or the temperature can change while the version number stays the same, you cannot reproduce an old answer.

The documented systems agree that these settings belong with the prompt. The MLflow registry keeps, for each prompt, templates with version numbers, commit messages, tags, aliases, the model configuration (such as temperature and max_tokens) and response format specifications. A Bedrock prompt variant bundles the message, the model and the inference configuration. A LaunchDarkly variation holds messages or instructions, a model and its parameters. Variables such as {{genre}} are placeholders that the application fills in at call time. Their names are part of the prompt's interface, because renaming one breaks every caller.

Versions are immutable, within limits. MLflow states that once a version exists its template and initial metadata cannot change. To edit, you register a new version under the same name and the number goes up. Immutability is what makes a rollback trustworthy: version 3 is the same text today as it was last month. Read each tool's promise closely, though. MLflow also documents that a version's model configuration can be updated after the version is created, without a new version, so in MLflow a score can stop describing the setup it was earned under unless your team treats a change to the model or its parameters as a new version.

Identity comes in two styles. Langfuse, MLflow and Bedrock identify versions by number: MLflow documents sequential version numbers, Bedrock counts from 1, and Langfuse assigns a version ID automatically. LangSmith identifies each saved update by a commit hash. Numbers are easy to say aloud and hashes identify content. A number is not a promise about content, though: LaunchDarkly increments a variation's version when it is archived or restored even though nothing in it changed, so compare content and not counters. Record a short reason with each version (MLflow calls it the commit message), because a diff shows what changed and never why.

Labels, aliases and tags: the movable pointer

Versions never move and pointers do. Application code asks for "the production version of refund-answer", and the registry resolves that to a concrete version. Langfuse calls the pointer a label, MLflow an alias and LangSmith a tag. Moving it is a promotion or a rollback, and no application code changes. Environments are built from these pointers: Langfuse says labels can assign prompts to environments such as staging and production, and LangSmith reserves the staging and production tags for its Environments feature.

Langfuse documents its resolution rules precisely, and they make a good model:

RequestResult
no label, no versionthe version labelled production; a 404 error if no version has that label
label="staging"the version with that label; there is no fallback to another label
version=3exactly version 3, whatever labels it carries
a label and a version togetheran error, because they are mutually exclusive

A useful rule: applications fetch by label, so a rollback needs no redeploy, and evals and bug reproductions fetch by exact version, so a result means the same thing tomorrow. Treat the automatic latest label in Langfuse and the reserved @latest alias in MLflow with care. They follow the newest version, so an application that fetches latest serves every new edit as soon as its cache refreshes, reviewed or not. Use them in development and keep production for a label that a person or a gate moves.

Moving production changes live behaviour, so decide who may do it. Langfuse documents protected prompt labels: once a label such as production is protected, the viewer and member roles cannot modify or delete it, while admins and owners still can. The page ties the feature to the plan, so check that yours includes it.

Where the prompt lives

There are two homes, and many teams use both.

Langfuse frames the registry case as separating two jobs: prompt iteration and code deployment are done by different people, so a prompt edit should not wait for a release. The repository case keeps prompts in files that change in pull requests, and a CI job can run evals when those files change: Promptfoo's CI guide shows a workflow that triggers only when prompts/** or the config file changes. Hosted features also come and go. OpenAI's documentation now says it is deprecating reusable prompt objects, with v1/prompts scheduled to shut down on November 30, 2026, and recommends keeping prompt builders in a small module in the code. If you depend on a hosted registry, keep an export of your prompts.

Fetching at runtime needs a cache and a fallback. Langfuse's SDKs cache prompts client-side with a default lifetime of 60 seconds. When the entry expires the SDK returns the stale prompt immediately and refreshes it in the background, so callers never wait. If the server is unreachable and nothing is cached, a fallback prompt that you supply is used. Make the fallback a known-good older prompt kept in code, not a placeholder, so that an outage degrades gracefully and does not silently change behaviour. MLflow caches as well: loads by alias are cached for 60 seconds by default and loads by exact version indefinitely, because an exact version cannot change.

Tying versions to evidence

Before promotion, run the same fixed set of eval cases on the candidate and on the current production version and compare case by case, as in Evaluating LLM Applications. An average can improve while a case that matters breaks, so mark some cases as protected and block a candidate that fails any of them. In MLflow the prediction function loads a registered prompt and mlflow.genai.evaluate scores it. Load an exact version such as prompts:/name/2, so that the score belongs to one version; the guide's own example loads @latest, which is whatever is newest at that moment. The results are kept in an MLflow experiment, which retains the history of prompt performance.

After promotion, stamp every request with the version. In Langfuse you pass the fetched prompt object to the generation, and the interface then aggregates median latency, token counts, cost, generation count and median score per version. In MLflow, loading a prompt inside a traced function links the trace to that version automatically. Without this stamp, "which prompt produced this answer?" can only be guessed from deploy times.

Rollout and rollback

A typical path is development, then staging, then production, with one label per environment. For prompts that reach many users, add a canary step: serve the candidate to a small share of traffic and compare its metrics with the version it replaces. LaunchDarkly's guarded rollouts do this for AgentControl configs. Traffic to the new variation increases while chosen metrics are compared with the original, and with automatic rollback enabled LaunchDarkly rolls the release back when it detects a regression. It counts a regression when sequential testing finds a statistically significant negative impact on a monitored metric, so a bad version that moves none of the monitored metrics is not caught. A simple home-made version hashes the user id into a bucket, so each user stays on one version.

Rollback is a pointer move, but it is not instant. If the application caches prompts for a time-to-live ttt (60 seconds by default in Langfuse), each instance may keep serving the old version until its entry expires, and the first request after expiry still receives the stale copy because of stale-while-revalidate. A rough upper bound on the requests that reach a bad version is

exposed≈r⋅s⋅(d+t)\text{exposed} \approx r \cdot s \cdot (d + t)exposed≈r⋅s⋅(d+t)

where rrr is the request rate, sss the share of traffic on the new version, ddd the time taken to notice the problem and ttt the cache lifetime. The second exercise applies this formula.

Two things can make a rollback fail. The old version may call a model that has since been retired, because each Claude model ID has its own deprecation and retirement schedule. Or the old template's variables may no longer match what the callers pass. Keep variable names stable, and test the rollback target in staging before you need it.

Pin the model with the prompt

A prompt is tuned to a model. OpenAI's guide recommends pinning production applications to specific model snapshots and notes that even snapshots within one model family can give different results. Anthropic's documentation says that from the Claude 4.6 generation each model ID is a single fixed snapshot, whereas earlier dateless aliases such as claude-sonnet-4-5 point to the most recent dated snapshot and so can move. Store the exact model ID in the version, and treat a model upgrade as a new prompt version that goes through the same eval gate.

Worked example: A tiny prompt registry with an eval gate, a promotion and a rollback

The scenario: a support assistant answers refund questions. You maintain a prompt called refund-answer and you have a fixed eval set of 10 cases, c01 to c10. Two of them are protected: c04 checks that the assistant never promises a refund outside the 30-day window, and c09 checks that it refuses to reveal internal notes. Three versions exist. Their results come from a recorded eval run, which in a real project your eval harness produces (see Evaluating LLM Applications).

VersionWhat changedFailing casesPassing
v1baseline promptc08, c108 of 10
v2adds the 30-day rulec099 of 10
v3adds the 30-day rule and a "never promise" sentencec109 of 10

v2 and v3 have the same pass count, so a score-only check cannot tell them apart. v2 fixes c08 and c10 but breaks c09, which passed in v1.

The script uses only the Python standard library (3.9 or later). It never changes an object in place: each function returns a new registry. Save it as registry_demo.py.

python
import hashlib
import json

PROTECTED = {"c04", "c09"}  # cases that must never regress
# Recorded eval run: the ids of the FAILING cases per version (10 cases, c01 to c10).
FAILS = {1: {"c08", "c10"}, 2: {"c09"}, 3: {"c10"}}
N_CASES = 10


def new_registry():
    return {"versions": {}, "labels": {}, "log": []}


def register(reg, template, model, temperature):
    """Append a version. Identical content returns the existing version."""
    content = {"template": template, "model": model, "temperature": temperature}
    digest = hashlib.sha256(json.dumps(content, sort_keys=True).encode()).hexdigest()[:8]
    for number, saved in reg["versions"].items():
        if saved["hash"] == digest:
            return reg, number
    number = len(reg["versions"]) + 1
    versions = {**reg["versions"], number: {**content, "hash": digest}}
    return {**reg, "versions": versions}, number


def set_label(reg, label, number):
    previous = reg["labels"].get(label)
    entry = f"{label}: {'unset' if previous is None else f'v{previous}'} -> v{number}"
    return {**reg, "labels": {**reg["labels"], label: number}, "log": [*reg["log"], entry]}


def gate(candidate, production):
    """Return the reasons a candidate must not replace production (empty means pass)."""
    problems = [f"protected case {c} regressed"
                for c in sorted((FAILS[candidate] - FAILS[production]) & PROTECTED)]
    if len(FAILS[candidate]) > len(FAILS[production]):
        problems.append("pass count dropped")
    return problems


def promote(reg, label, number):
    current = reg["labels"].get(label)
    problems = gate(number, current) if current else []
    if problems:
        return reg, problems
    return set_label(reg, label, number), []


reg = new_registry()
for text in ("Answer refund questions.",
             "Answer refund questions. Refunds are allowed within 30 days.",
             "Answer refund questions. Refunds are allowed within 30 days. Never promise one outside it."):
    reg, number = register(reg, text, "example-model-2026-01", 0.2)
    print(f"registered v{number} ({reg['versions'][number]['hash']}), {N_CASES - len(FAILS[number])}/{N_CASES} cases pass")

reg, again = register(reg, "Answer refund questions.", "example-model-2026-01", 0.2)
print(f"same content again -> v{again}, total versions {len(reg['versions'])}")

reg = set_label(reg, "production", 1)
for candidate in (2, 3):
    reg, problems = promote(reg, "production", candidate)
    print(f"promote v{candidate}:", "blocked, " + "; ".join(problems) if problems else "ok")

reg = set_label(reg, "production", 1)  # rollback: move the pointer, no gate
number = reg["labels"]["production"]
print(f"resolve production -> v{number} ({reg['versions'][number]['hash']})")
print("\n".join(reg["log"]))

Running python3 registry_demo.py prints:

text
registered v1 (b4114c70), 8/10 cases pass
registered v2 (030b1597), 9/10 cases pass
registered v3 (99a518d5), 9/10 cases pass
same content again -> v1, total versions 3
promote v2: blocked, protected case c09 regressed
promote v3: ok
resolve production -> v1 (b4114c70)
production: unset -> v1
production: v1 -> v3
production: v3 -> v1

Reading the result

  1. Registering the same content twice returns v1 and does not create a fourth version. The short hash (b4114c70 for v1) is computed from the template, the model and the temperature, so a change to any of the three makes a new version.
  2. promote v2 is blocked. Its pass count rose from 8 to 9, but c09 is protected, passes in production and fails in v2.
  3. promote v3 succeeds. Its only failure, c10, also fails in v1, so nothing that worked has regressed. The log records v1 -> v3.
  4. The rollback is set_label without the gate. It moves production back to v1, and resolve then returns v1's text and hash. Version 3 is untouched and can be promoted again after a fix.

What an application would see. Suppose the application caches the label for 60 seconds and handles 10 requests per second. After the rollback, every instance can keep serving v3 until its cache entry expires, so at most about 60 s x 10 requests per second = 600 requests still use v3, plus one extra stale response per instance, as described in the stale-while-revalidate rule above.

The gate is only as good as the eval set. Ten cases are enough to show a regression on a protected case and not enough to prove that v3 is better on average. For the paired comparison with an interval, see Evaluating LLM Applications.

Edge cases and limitations

A version number is not a guarantee about content
LaunchDarkly raises a variation's version number when it is archived or restored, although only its publication state changes, and its page says that creating a new variation increments the numbers of the existing ones. MLflow guarantees a version's template and initial metadata, but its model configuration can be updated in place and aliases are mutable by design. Do not read a changed counter as a changed prompt, or an unchanged counter as an unchanged system. Compare the saved content or its hash, and log both the number and the hash.
Rollback lags behind the label move
With a client-side cache the old version keeps being served until each instance's entry expires, and the first request after expiry still receives the stale copy. A short lifetime shortens the lag but sends more fetches to the registry. Choose the lifetime from how long a bad prompt may run, and use a fallback that is a known-good prompt kept in code.
A new model snapshot changes a prompt that did not change
Prompts are tuned against one model. OpenAI notes that different snapshots in one family can give different results, and Anthropic notes that serving infrastructure can change behaviour slightly even when a model ID and its weights are fixed. Pin the model ID in the version, re-run the eval set when you change it, and run the set on the production version periodically to catch drift.
A new prompt version restarts provider prompt caching
Anthropic's prompt caching needs 100 percent identical prompt segments for a hit, and the default cache lifetime is 5 minutes. Promoting a new version of a long system prompt therefore starts with cache misses and a temporary rise in latency and input cost. Do not mistake that for a regression in the new wording, and compare metrics only after the cache has warmed.
Variable names and output format are an interface
Renaming a placeholder, dropping one, or changing the reply format in a new version breaks callers that still pass the old variables or parse the old format. If the callers were changed in the same release, a label rollback restores the old prompt but not the old callers. Add new variables first, change the callers, then remove the old ones, and put a contract check in the eval gate.

When to use it, and when something simpler is enough

Use it when

  • More than one person edits prompts, or the people who edit them are not the people who deploy the application.
  • You must be able to say which prompt produced a given answer, for support, audit or debugging.
  • A prompt change can reach many users or a regulated outcome, so you want evals before release and a staged rollout after it.
  • The same prompt is used by several services or environments, such as staging, production or per-tenant variants.

Think twice when

  • It is a single-developer prototype whose prompt changes together with the code, where git history is enough and a registry would add a runtime dependency.
  • You cannot accept a runtime dependency on a registry service and changes can wait for a normal deploy, so the prompt should stay in the repository.
  • You have no eval cases and no traces, so versioning would record changes but give no evidence about which one is better.

A simpler alternative. Keep the prompt in a file in the repository, change it through pull requests, log the git commit hash with every model call, and run a small eval set in CI. Move to a registry when non-engineers must edit prompts without a release, or when you need to roll back by moving a label without redeploying.

Key takeaways

  • A prompt version is an immutable snapshot of the template plus the model, parameters and output format that shape the result, and every edit creates a new one.
  • Labels, aliases and tags are movable pointers to versions, so applications fetch by label, evals and reproductions fetch by exact version, and promotion and rollback are label moves.
  • Prompts can live in the repository or in a registry fetched at runtime, and the registry gives faster changes and label rollback at the cost of a runtime dependency that needs a cache and a fallback.
  • A version earns promotion with evidence. The same fixed eval cases run on the candidate and on production, with protected cases that must not regress, and every later request is traced to its version.
  • Rollback is a pointer move but not an instant one, and the requests a bad version reaches grow with its traffic share, the time to notice and the cache lifetime, so stage the rollout when the impact is wide.
  • Pin the model ID together with the prompt, and treat a model change as a new prompt version that passes the same gate.

Example 1 of 5

Langfuse: labelled prompt versions fetched at runtime with a cache, a fallback and trace linking

LangfuseDocumented in official docs

Langfuse offers open-source prompt management. Its documentation (the overview, the versions and labels page, the caching page and the page on linking prompts to traces) describes how applications fetch labelled prompt versions at runtime. [2][3][4][5][6]

The problem

In many teams prompt iteration and code deployment are handled by different people, so a one-sentence fix to a prompt waits for an engineering release. The Langfuse overview describes this as turning a two-minute update into hours or days of waiting. The product has to let a prompt change without a deploy, while the application stays fast and available and each answer can still be traced to the wording that produced it.

Where this topic fits

Langfuse sits between the people who edit prompts and the application that calls the model. The prompt is created in the interface or through the SDK, a label marks the version that serves each environment, the application fetches by label through the SDK, and the resulting generation is linked back to the version that was used.

How it is applied, step by step

  1. A prompt is created under a name. Every save becomes a new version with an automatic version ID, so the person who owns the wording can edit it without touching application code.
  2. The version that should serve live traffic gets the `production` label. Other labels, such as `staging`, serve other environments, and the automatic `latest` label always points at the newest version.
  3. The application calls `get_prompt` with the prompt name. With no label or version the SDK returns the `production` version, and asking for a label or an exact version returns that one.
  4. The SDK answers from an in-process cache and refreshes it in the background once the time-to-live has passed. If the server cannot be reached and the cache is empty, the fallback prompt supplied in the code is used instead.
  5. The application compiles the template with its variables and calls the model, passing the prompt object into the generation so that Langfuse records which version produced the response.
  6. In the metrics view the team compares latency, tokens, cost and scores per version. If a version misbehaves, they reassign the `production` label to an earlier version in the interface.

Why this approach fits

Moving a pointer and not the code is what lets a fix reach production without a release, and the client-side cache keeps the registry off the critical path of each request. Passing the prompt into the generation gives the per-version view that is needed to judge an edit after it ships.

Limitation or tradeoff

The registry becomes part of the runtime path. The cache and the fallback protect availability, but a rollback still takes up to the cache lifetime to reach every instance, and the first request after expiry still receives the stale prompt. Anyone who can move the production label can change production behaviour, so a label move deserves the same care as a deploy. Langfuse documents protected prompt labels, which stop the viewer and member roles from changing a protected label such as production, but the page ties the feature to the plan, so check that yours includes it.

What the sources document

  • The overview says that prompt iteration and code deployment are usually done by different people, and presents prompt management as a way to update prompts without involving engineering or a deployment. [2]
  • Each prompt version gets an automatic version ID. Langfuse keeps two special labels: latest, the newest version, and production, the version served when no label is given. Fetching by label never falls back to another label, fetching by version returns exactly that version, and giving both is an error. [3]
  • To roll back, you reassign the production label to a previous version in the interface, after which that version is the default. Project admins and owners can protect a label such as production so that the viewer and member roles cannot modify or delete it. [3]
  • The SDK caches prompts client-side with a default lifetime of 60 seconds, returns the stale prompt while it refreshes in the background after expiry, and uses a supplied fallback only when the cache is empty and the API request fails. [4]
  • When a fetched prompt is linked to a generation, Langfuse aggregates per prompt version the median latency, input and output tokens and cost, the generation count and the median score. [5]

The facts above come from the cited sources. The steps and analysis in this example are our explanation of how they fit together.

Example 2 of 5

MLflow Prompt Registry: immutable versions, aliases and evaluation runs tied to a prompt version

MLflowDocumented in official docs

The MLflow documentation for generative AI describes a Prompt Registry. Its pages on registering and editing prompts, managing lifecycles with aliases, evaluating prompts and using prompts in applications describe a path from a first draft to a production alias. [7][8][9][10][11]

The problem

A team iterating on a prompt needs a history of what changed and why, a way to test a candidate against the current version, and a way to point an application at a stage without changing application code. Results must stay reproducible, which means a version cannot change after it has been evaluated.

Where this topic fits

The registry sits on the path from experiment to production in MLflow. Versions are registered during development, evaluated with mlflow.genai.evaluate with results kept in an experiment, and loaded by applications through an alias. When the application loads a prompt inside a traced function, the trace is linked to the version in use.

How it is applied, step by step

  1. Register the prompt template with a commit message. This creates version 1 and stores the template with its metadata.
  2. To change the prompt, register again under the same name. The version number increases and version 1 stays exactly as it was, so the earlier evaluation results still describe it.
  3. Write a prediction function that loads an exact version (`prompts:/name/2`) and calls the model, then run `mlflow.genai.evaluate` with a dataset and scorers. The results are stored in an MLflow experiment.
  4. Compare the results of the versions in the interface. If the candidate holds up, set the `production` alias to its version number.
  5. The application loads `prompts:/name@production`. Because the load happens inside a traced function, the trace records which prompt version was used.
  6. To roll back, point the alias at the earlier version. The application code and the versions are untouched.

Why this approach fits

Immutability and aliases split the two jobs of a version. The version is a fixed, reproducible thing to evaluate, and the alias is a movable name to deploy. Because an evaluation loads an exact version, its score belongs to that version permanently, and a rollback is an alias change.

Limitation or tradeoff

The documentation describes aliases as mutable references, and the pages read here show no approval step before an alias moves, so a gate has to come from your own process, for example a CI job that calls set_prompt_alias only after a passing evaluation. The evaluation guide connects results to a prompt through the load inside the prediction function, so a function that loads @latest, as the guide's own example does, evaluates whatever @latest is at that moment. Model configuration can be edited in place, so a score earned under one temperature can later describe another unless your process forbids that edit. Alias loads are cached for 60 seconds by default, so a separate running application would typically see an alias move only after its cache entry expires.

What the sources document

  • Prompt versions in MLflow are immutable. Once a version exists its template and initial metadata cannot change, and a change means registering the prompt again under the same name, which increments the version number. [8]
  • The registry stores prompt templates (text or chat) with version numbers, commit messages, tags, aliases, model configuration such as temperature and maximum tokens, and response format specifications. Model configuration is mutable: unlike the template, it can be updated after a version is created. [7]
  • Aliases are mutable references to versions. The documentation shows set_prompt_alias for production, loading with the prompts:/name@production form, recommends stage names such as beta, staging and production, and says that switching an alias supports roll-backs and A/B testing. Loads by alias are cached for 60 seconds by default, loads by exact version indefinitely. [9][7]
  • In the evaluation guide a prediction function loads a registered prompt and mlflow.genai.evaluate scores it, and evaluation results are tracked in an MLflow experiment to keep the history of prompt performance. [10]
  • When prompts are loaded from the registry inside traced functions, MLflow tracks which prompts are used and links them to the active trace. [11]

Amazon Bedrock Prompt management: an editable draft, numbered version snapshots and a version ARN in the call

Amazon BedrockDocumented in official docs

The AWS documentation for Prompt management in Amazon Bedrock describes creating, testing and versioning prompts, and then calling a chosen version from the Converse API or from a prompt node in a Bedrock Flow. [12][13][14][15][16]

The problem

Teams running several workflows on Bedrock want to define a prompt once, with its model, inference settings and variables, test variants of it, and give applications a fixed thing to call. They also need to keep iterating on the wording without disturbing what is already deployed.

Where this topic fits

Prompt management sits between the prompt builder in the console, where prompts are written and tested, and the application or flow that runs inference. The draft is the editable working copy. A version is the snapshot that an application calls by its ARN.

How it is applied, step by step

  1. Create a prompt with variables and at least one variant, which sets a message, a model and inference settings. Saving it creates the draft.
  2. Test the draft with values for the variables and compare variants until the output suits the use case. The test values are temporary and are not saved with the prompt.
  3. When satisfied, create a version, in the console or with the CreatePromptVersion operation. This takes a snapshot of the draft. Versions are numbered from 1 and the response returns the version's ID and ARN.
  4. Point the application at that version. Call Converse with the prompt version ARN as the model ID and the variable values in `promptVariables`, or put the ARN in a prompt node of a flow.
  5. To promote or roll back, change which version ARN the application or flow uses. Edits to the draft in the meantime do not affect the deployed version.

Why this approach fits

The draft and version split lets people keep experimenting without touching what applications call. A version ARN is an exact reference, so an application changes behaviour only when someone changes the ARN it uses. Because the model and inference settings are saved with the prompt, a version pins more than the wording.

Limitation or tradeoff

The pages read here show an exact version ARN per call and do not describe environment names, so the mapping from staging or production to a version lives in your own configuration, as in the sketch. When a managed prompt is used with Converse, fields such as inferenceConfig, system and toolConfig cannot be passed, so per-request tuning means creating another variant or version.

What the sources document

  • Saving a prompt creates a draft that you can keep modifying. A version is a snapshot of the prompt taken at a point in time, and versions let you switch between configurations and update the application with the most suitable one. [13]
  • Through the API, CreatePromptVersion takes the prompt's ARN or ID as promptIdentifier and returns an ID and ARN for the version. Versions are created incrementally, starting from 1. [14]
  • A prompt variant is an alternative configuration of a prompt, covering its message, model or inference configuration, and Prompt management lets you compare the outputs of variants and save the one to keep. [12]
  • To invoke a managed prompt with Converse you give the prompt ARN with its version as modelId and pass variable values in promptVariables. Messages and system content come from the prompt template. [15]
  • With a managed prompt, Converse and ConverseStream do not accept the additionalModelRequestFields, inferenceConfig, system or toolConfig fields, and any messages you add are appended after the messages defined in the prompt. [16]

Example 4 of 5

LaunchDarkly AgentControl: versioned prompt variations served by targeting rules and released with guarded rollouts

LaunchDarklyDocumented in official docs

LaunchDarkly's documentation for AgentControl describes configs that hold variations of messages or instructions, a model and its parameters. The application evaluates a config at runtime, targeting rules choose the variation, and a guarded rollout can release a change gradually while watching metrics. [17][18][19][20][21]

The problem

Teams that run LLM features want to change prompts and model settings without redeploying, show different variations to different audiences, and release a new variation gradually while checking that it does not make things worse. These are the needs that feature flags answer for code, and here the thing being flagged is a prompt and its model settings.

Where this topic fits

LaunchDarkly sits at delivery time. The application refers to a config by its key and passes a context (a user, an organisation or another entity). Targeting rules decide which variation that context receives, and a guarded rollout governs how quickly a new variation reaches contexts and compares its metrics with the original.

How it is applied, step by step

  1. Create a config in completion mode (messages and roles) or agent mode (instructions). Its key is what the code refers to and cannot be changed after creation.
  2. Create variations. Each holds messages or instructions, a model and model parameters, and each save gives the variation a new version number.
  3. Use the version history to compare two versions, with the model configuration shown as JSON and the messages as text, and promote an earlier version to current if a change needs undoing. Saving the promotion creates a new version that carries the older content.
  4. Set targeting rules, which decide which variation each context, such as a user or an organisation, receives, so that different audiences can be served different variations.
  5. When a rule starts serving a new variation, add a guarded rollout. Traffic to the new variation increases step by step while the metrics attached to the config are compared with the original.
  6. If a regression is detected, LaunchDarkly notifies the maintainer, and with automatic rollback enabled it rolls the release back. Changes to prompts and settings take effect without redeploying the application.

Why this approach fits

Prompts are changed by many people and need staged exposure and a quick reversal. Feature-flag machinery already provides targeting, gradual release, metric comparison and a way back, so the same system can serve prompt variations. Version numbers per variation give an audit trail and a restore path.

Limitation or tradeoff

Version numbers count saves and not content, because archiving or restoring a variation also raises its number, and so does adding another variation, so identify real changes by comparing content. A guarded rollout detects only statistically significant regressions in the metrics attached to it, so with little traffic, or with no metric that captures answer quality, a quality regression can pass. The pages read here do not describe what happens when LaunchDarkly cannot be reached, so keep a default configuration in code.

What the sources document

  • When you update prompts, instructions or model configuration in LaunchDarkly, the changes take effect immediately and the application does not need to be redeployed. [17]
  • A config is created in completion mode (messages and roles) or agent mode (instructions). Its key is what you use to reference the config in code. A suggested key is filled in from the name you enter and can be edited, but after the config is created the key cannot be modified. [18]
  • A variation holds messages (completion mode) or instructions with optional tools (agent mode), a selected model, and model parameters such as temperature and maximum tokens. Each updated variation receives a new version number. Archiving or restoring a variation also increments it, and a newly created variation increments the version numbers of existing ones. [19]
  • The version history lets you compare a version with the current one, with the model configuration shown as JSON and messages as text, and restore an earlier version with the Promote to current action, after which Review and save creates a new version with those updates. [20]
  • A guarded rollout progressively increases traffic to a new variation while monitoring selected metrics for regressions until it reaches 100 percent. A regression is a statistically significant negative impact found by sequential testing. LaunchDarkly can then pause the rollout and notify you and the maintainer, and with automatic rollback enabled it also rolls the release back. The page covers AgentControl configs as well as flags. [21]

4Common mistakes

  1. Pointing production code at the latest version instead of at a controlled label.

    Why it causes problems
    The Langfuse latest label and the MLflow @latest alias follow the newest version, so every save, reviewed or not, goes live as soon as caches refresh. An experiment in the editor becomes a production change without anyone deciding so.
    How to recognise it
    Production behaviour changes right after someone saves a draft, and the version recorded in traces changes with no promotion entry in the log.
    How to fix it
    Have production fetch a label such as production, moved only by a promotion step that follows the eval gate. Keep latest for development and playground use.

  2. Versioning the template text but not the model, the parameters or the output format.

    Why it causes problems
    The same version number then produces different answers after someone changes the model or the temperature, so an old result cannot be reproduced and an eval score cannot be trusted as describing the version.
    How to recognise it
    Outputs or eval scores shift while the prompt version is unchanged, or two services using the same version behave differently because they call different models.
    How to fix it
    Store the exact model ID, the sampling parameters and the response format in the version, as MLflow, Bedrock and LaunchDarkly do, and treat a change to any of them as a new version that passes the same gate. MLflow lets you edit a version's model configuration in place, so there you enforce this by team rule.

  3. Not recording which prompt version produced each response.

    Why it causes problems
    When a user reports a bad answer you can only guess the wording from deploy times and label history, and metrics cannot be compared per version.
    How to recognise it
    A trace or log line for a model call has no prompt name and version, and the question "which prompt was live for this request?" takes a manual search.
    How to fix it
    Link the fetched prompt to the call (pass the prompt into the Langfuse generation, or load it inside an MLflow traced function), or at least log the prompt name, version number and hash with every call.

  4. Promoting a version because its average score went up.

    Why it causes problems
    A version can fix several cases and break one that matters, such as a safety refusal or a legal statement. The average hides it, and the break reaches users.
    How to recognise it
    A case-by-case comparison with production shows a case that passed before and fails now, while the total pass count is higher.
    How to fix it
    Compare candidate and production on the same cases, mark the cases that must never regress as protected, and block promotion when any of them fails. Add a canary step for changes with wide impact.

  5. Fetching the prompt from the registry on every request with no cache and no fallback.

    Why it causes problems
    A slow or unavailable registry then slows or stops every request that needs a prompt, so a service meant to make changes safer becomes a new outage risk.
    How to recognise it
    Latency rises whenever the registry is slow, and the application cannot start or answer when it is unreachable.
    How to fix it
    Use an SDK cache with a lifetime you chose, serve stale entries while refreshing, and supply a known-good fallback prompt in code. Alert when the fallback is used so that an outage is noticed.

  6. Renaming template variables or changing the reply format inside a new prompt version.

    Why it causes problems
    Callers still pass the old variables or parse the old format, so requests fail or return unusable output, and a label rollback cannot repair callers that were changed in the same release.
    How to recognise it
    Unfilled placeholders appear in the prompt text, or JSON parsing errors begin right after a promotion.
    How to fix it
    Treat variable names and the output schema as an interface. Add the new variable first, change the callers, then remove the old one, and include a contract check in the eval gate.

Route a fixed share of users to a candidate prompt version and log the version

CodingIntermediateAbout 30 min (estimate)Hypothetical scenario

Your team wants to try version 4 of the refund-answer prompt on 5 percent of users while everyone else stays on version 3. Write the routing in plain Python 3 with no third-party packages.

Implement these three functions:

    """Return an integer from 0 to 99 that depends only on the two arguments."""

def choose_version(prompt_name, user_id, stable, candidate, percent):
    """Return candidate when the user's bucket is below percent, otherwise stable."""

    """Return a dict that a trace or log line would hold for this model call."""

Then check your work with these ten thousand users:

python
users = [f"user-{i}" for i in range(10_000)]

Report the share of users on the candidate at 5 percent, whether repeated calls give the same answer for every user, what happens at 0 and at 100 percent, and whether users who were on the candidate at 5 percent are still on it when you widen the rollout to 20 percent.

Requirements

  • `bucket` uses `hashlib` and the prompt name together with the user id, and never Python's built-in `hash`.
  • `choose_version` returns the candidate for a user exactly when `bucket(...) < percent`.
  • With 10,000 users and 5 percent, the candidate share is close to 0.05 (within about 0.01).
  • The same user always gets the same version, and 0 percent sends everyone to the stable version while 100 percent sends everyone to the candidate.
  • Every user on the candidate at 5 percent is still on the candidate at 20 percent.
  • `trace_record` includes the user, the prompt name and the prompt version actually used.

Expected behaviour

With the hashing scheme in the solution, the script prints a candidate share of 0.0527 (a little above 0.05, which is ordinary sampling variation for 10,000 users), sticky: True, a set containing only 3 at 0 percent, a set containing only 4 at 100 percent, and True for the widening check. Your exact share depends on your hashing scheme but should be near 0.05.

Hint 1

Python's built-in `hash` of a string changes from one process to the next, so the same user would move between versions after a restart. A cryptographic digest does not.

Hint 2

Hash a string such as the prompt name, a colon and the user id. Including the prompt name means two different prompts do not always pick the same users.

Hint 3

Turn the first four bytes of the digest into an integer with `int.from_bytes(..., "big")` and take it modulo 100.

Hint 4

Widening works because the bucket of a user never changes. Only the threshold moves.

Show solution

A bucket is a stable function of the prompt name and the user id, so the same user always lands in the same bucket. The threshold percent is the only thing that changes between rollout stages, which is why the users selected at 5 percent are a subset of those selected at 20 percent.

python
import hashlib


def bucket(prompt_name, user_id):
    """Map a user to a stable number 0-99 for one prompt."""
    digest = hashlib.sha256(f"{prompt_name}:{user_id}".encode()).digest()
    return int.from_bytes(digest[:4], "big") % 100


def choose_version(prompt_name, user_id, stable, candidate, percent):
    return candidate if bucket(prompt_name, user_id) < percent else stable


def trace_record(prompt_name, user_id, version):
    return {"user": user_id, "prompt": prompt_name, "prompt_version": version}


users = [f"user-{i}" for i in range(10_000)]
picks = [choose_version("refund-answer", u, stable=3, candidate=4, percent=5) for u in users]
print("candidate share:", picks.count(4) / len(users))
again = [choose_version("refund-answer", u, stable=3, candidate=4, percent=5) for u in users]
print("sticky:", picks == again)
print("0%:", {choose_version("refund-answer", u, 3, 4, 0) for u in users})
print("100%:", {choose_version("refund-answer", u, 3, 4, 100) for u in users})
widened = [choose_version("refund-answer", u, 3, 4, 20) for u in users]
stayed = all(w == 4 for p, w in zip(picks, widened) if p == 4)
print("users on v4 at 5% still on v4 at 20%:", stayed)
print(trace_record("refund-answer", "user-7", choose_version("refund-answer", "user-7", 3, 4, 5)))

Running it prints:

text
candidate share: 0.0527
sticky: True
0%: {3}
100%: {4}
users on v4 at 5% still on v4 at 20%: True
{'user': 'user-7', 'prompt': 'refund-answer', 'prompt_version': 3}

Why this works: SHA-256 output is spread evenly over its range, so bucket is close to uniform over 0 to 99 and about 5 percent of users fall below 5. The observed 0.0527 is within what chance allows for 10,000 users (the standard deviation of a 5 percent share over 10,000 users is about 0.002, so 0.0527 is roughly 1.2 standard deviations away). Logging prompt_version in each record is what lets you compare error rates and scores between the two versions afterwards.

Check your answer

  • Does `bucket` give the same value for the same user in two separate runs of the program?
  • Is every user in the 5 percent group also in the 20 percent group?
  • Does the trace record show the version the user actually received, not the version you intended to roll out?

Estimate how many requests a bad prompt version reaches under two rollout plans
