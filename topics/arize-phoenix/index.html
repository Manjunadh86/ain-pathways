Arize Phoenix

Arize Phoenix is a tool for tracing and evaluating LLM applications and agents. It receives OpenTelemetry traces that follow the OpenInference conventions, stores them, and adds evaluations, datasets, experiments and a prompt playground in one server that you run on a laptop or host yourself. Arize calls it open source; its Elastic License 2.0 bars offering it to others as a managed service.

1Overview

Why it matters

An LLM application fails quietly. The request returns HTTP 200, the answer reads well, and it is wrong because a retriever returned the wrong document or an agent called the wrong tool three steps earlier. Logs of the final answer do not show that. You need the whole run recorded step by step, and then you need a way to check that a fix really fixed it without breaking the cases that already worked.

Phoenix covers both halves with one install, and it keeps the data on infrastructure you control, which is often the deciding factor for teams that cannot send prompts and customer data to a vendor. Engineers who build agents use it to debug runs, people who own quality use it to score outputs and compare versions, and whoever deploys it has to make real decisions about storage, authentication and licence terms. Because it is built on OpenTelemetry, what you learn here about spans, attributes and exporters transfers to other observability tools.

Key terms

Trace
The record of one run of your application, made of spans that share a trace id and are linked into a tree by parent ids.
Span
One timed step inside a trace, such as a model call, a retrieval or a tool call, with a start time, an end time, a status and a set of attributes.
OTLP
The OpenTelemetry Protocol, the wire format that carries spans from an application to a collector over HTTP or gRPC.
OpenInference
A specification and set of instrumentation libraries, maintained by Arize, that defines AI-specific span kinds and attribute names on top of OpenTelemetry.
Span kind
The required OpenInference attribute that says what a span represents, for example LLM, TOOL, RETRIEVER, AGENT or CHAIN.
Instrumentor
A library that wraps a framework or SDK so that its calls produce spans automatically, without changes to your own functions.
Project
A named group of traces in Phoenix, usually one per application or environment.
Annotation
A score, label or explanation attached to a span or trace, written by an evaluator or by a person in the UI.
Dataset
A stored collection of examples, each with an input and optionally a reference output and metadata, used as a fixed test set.
Experiment
One run of a task over every example in a dataset, with evaluator scores recorded so that runs can be compared.

2Explanation

Introduction

In LLM and Agent Observability you learned what a trace is: one record per request, split into spans for each model call, retrieval and tool call. That lesson covered the idea. This one covers a specific tool that receives those traces, stores them and helps you act on them.

A useful comparison is a flight recorder plus a test bench. The flight recorder is tracing. It captures every step of every run, so when an answer is wrong you can open that run and see which step failed. The test bench is evaluation. You keep the runs that failed as test cases, change something, and run the same cases again to see whether the change helped. Many teams have the first half and do the second half in a spreadsheet. Phoenix puts both halves in one place.

Phoenix is a server with a web UI, and you run it yourself: on a laptop with one command, in a container, or on your own infrastructure. Your application sends it traces over OpenTelemetry, the standard telemetry protocol, using attribute names defined by a companion project called OpenInference. The Phoenix documentation (opens in a new tab) groups what you can do with those traces into four areas:

  • Tracing shows each run step by step, with inputs, outputs, timing and token counts.
  • Evaluation attaches scores and labels to spans. They come from code checks, from a judge model or from people.
  • Datasets and experiments rerun a fixed set of inputs through different versions of your application and compare the scores.
  • Prompt engineering gives you a playground for editing prompts against real examples, replaying a traced model call and saving prompt versions.

The four areas form the loop in the diagram. Traces show what happened, evaluations mark which runs were bad, the bad runs become a dataset, and experiments tell you whether a change is an improvement before you ship it.

The rest of this lesson explains the tracing stack underneath, the evals library, datasets and experiments, the playground, and the ways to run Phoenix from a notebook up to a PostgreSQL-backed deployment. The worked example runs the whole loop on your own machine without a model API key.

How it works

Three layers that each do one job

Phoenix tracing is built from three parts, and it helps to keep them apart.

  • OpenTelemetry (OTel) is the vendor-neutral standard for telemetry. It defines what a span is and how spans travel, using a wire protocol called OTLP. It is not a backend: it stores nothing and displays nothing.
  • OpenInference is a specification plus instrumentation libraries, maintained by Arize, layered on OTel. It fixes the attribute names an AI span carries, such as llm.input_messages and llm.token_count.total, and defines span kinds such as LLM, TOOL, RETRIEVER and AGENT.
  • Phoenix is the backend: an OTLP collector, a database and a web UI in one process.

The Phoenix docs say OTel defines how telemetry is shaped, transported and exported (opens in a new tab), while OpenInference adds the AI-specific conventions and instrumentors on top of it.

Because the wire format is plain OTLP, the instrumentation is not tied to Phoenix. The smolagents documentation (opens in a new tab) uses the same OpenInference instrumentor to feed Phoenix and Langfuse.

Sending traces

Start the server, then point your code at it.

bash
pip install arize-phoenix arize-phoenix-otel openinference-instrumentation-openai
phoenix serve    # UI and OTLP over HTTP on port 6006, OTLP over gRPC on port 4317
python
from phoenix.otel import register

tracer_provider = register(
    project_name="support-bot",  # traces are grouped into projects
    auto_instrument=True,        # switch on every installed OpenInference instrumentor
)

register is a thin wrapper around the OTel SDK. It builds a tracer provider and an OTLP exporter, reads PHOENIX_COLLECTOR_ENDPOINT (a local server at http://localhost:6006 needs no setting) and PHOENIX_API_KEY, and assigns spans to the project. With auto_instrument=True it activates every openinference-instrumentation-* package installed in the environment, so calls made through OpenAI, LangChain, CrewAI and other supported libraries produce spans with no further code. For your own functions the tracer offers decorators: @tracer.chain, @tracer.tool, @tracer.agent and @tracer.llm.

What Phoenix stores for each span

A span is an ordinary OTel span whose attributes follow the OpenInference semantic conventions (opens in a new tab). One attribute is required on every span, and the rest are reserved names used when they apply.

AttributeExample valueWhat it holds
openinference.span.kindLLMRequired. One of 11 kinds, including CHAIN, RETRIEVER, TOOL, AGENT, EMBEDDING, RERANKER, GUARDRAIL and EVALUATOR
input.value, output.value"Hello, World!"What went into the step and what came out
llm.model_name"gpt-3.5-turbo"The model that was called
llm.token_count.prompt, llm.token_count.completion10, 15Token usage of one model call
retrieval.documentsa list with document.content and document.scoreWhat a retriever returned, in order
session.id, user.idan identifier stringGroup traces into conversations and users

Spans that share a trace id form a tree through their parent ids. The UI draws the tree with latency, token counts and status per span, which is how you find the slow step or the step that returned the wrong thing.

Prompts and responses are stored in full unless you say otherwise. OpenInference defines environment variables such as OPENINFERENCE_HIDE_INPUTS and OPENINFERENCE_HIDE_OUTPUTS, which every auto-instrumentor respects. The prerequisite lesson covers what to redact.

Evals: turning traces into scores

A trace says what happened, not whether it was good. The arize-phoenix-evals package produces a score or a label for each row of data, using two kinds of evaluator:

  • Code evaluators are plain functions: an exact match, a regular expression, a JSON schema check.
  • LLM evaluators ask a judge model to classify an output against a rubric you write (see LLM-as-a-Judge).
python
from phoenix.evals import LLM, ClassificationEvaluator

TEMPLATE = """Rate how helpful the response is to the question.
Question: {{input}}
Response: {{output}}
"helpful" means the response directly addresses the question."""

helpfulness = ClassificationEvaluator(
    name="helpfulness",
    prompt_template=TEMPLATE,
    llm=LLM(provider="openai", model="gpt-4o-mini"),
    choices={"not_helpful": 0, "helpful": 1},
)

Phoenix does not parse free text from the judge. It makes the judge answer through a tool call whose schema allows only the listed labels plus an explanation, then maps the label to its score. The library also ships pre-built metrics for RAG and tool-calling agents, such as FaithfulnessEvaluator. The evaluators guide (opens in a new tab) is blunt about them: pre-built evaluators rarely fit a specific task unchanged and should be treated as starting points.

To score traces you already have, the Running Evals on Traces (opens in a new tab) guide chains four calls. Client().spans.get_spans_dataframe(project_name=...) pulls spans into a dataframe, async_evaluate_dataframe runs the evaluators over its rows, to_annotation_dataframe reshapes the results, and Client().spans.log_span_annotations_dataframe(...) writes them back. They are stored as annotations on the spans, beside any labels people add by hand in the UI, and the failing spans can then be collected into a dataset. Evaluators can also run on the server: the Evaluation page (opens in a new tab) describes evaluators configured in the Phoenix UI and attached to datasets, so that experiment results are scored without code.

Datasets and experiments

Four terms carry this part of the product:

  • A dataset is a stored collection of examples, and the datasets concepts page (opens in a new tab) says every insert, update and delete is versioned. Each example has an input, an optional reference output and optional metadata. Examples can be hand-curated, taken from production traces or generated synthetically, and the worked example below creates them in code.
  • A task is a function that takes an example and returns an output, usually by calling your application.
  • An evaluator scores that output. Phoenix binds arguments by parameter name: output is the task result, expected is the reference output, and input and metadata come from the example.
  • An experiment is one run of a task over every example, with the evaluator scores recorded.
python
experiment = client.experiments.run_experiment(
    dataset=dataset, task=task, evaluators=[exact_match], experiment_name="prompt-v2"
)

Two experiments on the same dataset can be compared side by side, and one can be marked as the baseline. Passing dry_run=3 runs three examples without sending anything to the server, which is the quick way to debug a task function. Evaluating LLM Applications explains how to choose the examples and the metrics. Phoenix supplies the bookkeeping.

Prompt playground and span replay

The playground (opens in a new tab) is a prompt editor inside the Phoenix UI. You pick a provider and model (OpenAI, Anthropic, Gemini, Azure or a custom endpoint), write a template with variables, and run it. Three features connect it to the rest of the loop:

  • Span replay (opens in a new tab). Load an LLM span from a trace and rerun that single step with a different prompt, model or parameters, instead of rerunning the whole agent.
  • Dataset runs. Run a prompt over every example of a dataset. Phoenix records the run as an experiment, and evaluators attached to the dataset score it automatically.
  • Prompt management. Save prompt versions and load them from the playground or from code (see Prompt Management and Versioning).

Every playground run is itself recorded as a trace.

Where it runs

Every option below runs the same server. What changes is where the data lives and who can reach it.

The settings that matter most when you move past a laptop:

  • Storage. SQLite is the default. Set PHOENIX_SQL_DATABASE_URL to use PostgreSQL (version 14 or later), which the docs recommend for production.
  • Authentication. It is off by default. PHOENIX_ENABLE_AUTH=true plus a PHOENIX_SECRET turns on logins and API keys, and clients then send PHOENIX_API_KEY.
  • Retention. Traces are kept forever unless you set PHOENIX_DEFAULT_RETENTION_POLICY_DAYS.
  • Tenancy. One instance is one tenant. Separate teams or environments get separate instances.
  • Licence. The Elastic License 2.0 (opens in a new tab) lets you use, modify and self-host Phoenix free of charge with every feature, but you may not provide it to third parties as a hosted or managed service that gives them access to a substantial set of its features.

Arize also sells a managed platform, Arize AX, built on the same two standards, so an application instrumented for Phoenix can send its traces there without being re-instrumented. Hosted Phoenix endpoints exist as well: two of the real-world examples below send their traces to one.

Worked example: Trace a ticket router, save six test cases and prove a fix with two experiments

This example runs the whole loop on one machine with no model and no API key, so everyone gets the same numbers. The application is a support-ticket router that picks a queue by counting keywords. Version 1 has a bug. A trace will show where it is, and an experiment will confirm the fix.

Setup. The server needs Python 3.11 or later. That is the requirement published for arize-phoenix 20.20.0, the current release when this lesson was written.

bash
pip install arize-phoenix arize-phoenix-otel arize-phoenix-client
phoenix serve

Leave the server running and open http://localhost:6006. In a second terminal, save the following as ticket_router.py and run python ticket_router.py.

python
from phoenix.client import Client
from phoenix.otel import register

# 1. Send spans to the local Phoenix server over OTLP/HTTP (port 6006).
tracer_provider = register(project_name="ticket-router", protocol="http/protobuf")
tracer = tracer_provider.get_tracer(__name__)

QUEUES = {
    "billing": ["invoice", "refund", "charge"],
    "technical": ["error", "crash", "bug"],
    "account": ["password", "email", "login"],
}
EXAMPLES = [
    ("I was charged twice for my invoice.", "billing"),
    ("The app crashes with an error when I upload a file.", "technical"),
    ("How do I change my email address?", "account"),
    ("I get an error and the app crashes when I try to pay an invoice.", "technical"),
    ("I forgot my password, the reset email never arrives and login shows an error.", "account"),
    ("What are your opening hours?", "general"),
]


@tracer.tool
def count_hits(ticket: str) -> dict:
    """Count how many keywords of each queue appear in the ticket."""
    text = ticket.lower()
    return {queue: sum(word in text for word in words) for queue, words in QUEUES.items()}


@tracer.chain
def route_v1(ticket: str) -> str:
    """Version 1: the first queue with any keyword wins."""
    for queue, hits in count_hits(ticket).items():
        if hits > 0:
            return queue
    return "general"


@tracer.chain
def route_v2(ticket: str) -> str:
    """Version 2: the queue with the most keyword hits wins."""
    hits = count_hits(ticket)
    best = max(hits, key=hits.get)
    return best if hits[best] > 0 else "general"


# 2. Produce six traces with version 1.
for ticket, _ in EXAMPLES:
    print(f"{route_v1(ticket):<10} <- {ticket}")

# 3. Store the six tickets and their correct queues as a dataset.
client = Client()
try:
    dataset = client.datasets.get_dataset(dataset="ticket-router-golden")
except ValueError:  # raised when no dataset has this name yet
    dataset = client.datasets.create_dataset(
        name="ticket-router-golden",
        inputs=[{"ticket": ticket} for ticket, _ in EXAMPLES],
        outputs=[{"queue": queue} for _, queue in EXAMPLES],
    )


# 4. A task maps one example's input to an output. An evaluator scores that output.
def task_v1(input):
    return route_v1(input["ticket"])


def task_v2(input):
    return route_v2(input["ticket"])


def exact_match(output, expected) -> bool:
    return output == expected["queue"]


# 5. Run both versions over the same examples with the same evaluator.
for name, task in (("router-v1", task_v1), ("router-v2", task_v2)):
    client.experiments.run_experiment(
        dataset=dataset, task=task, evaluators=[exact_match], experiment_name=name
    )

What the script prints. register first prints a short banner with the project name and the collector endpoint. Step 2 then prints one line per ticket. The fourth and fifth are wrong:

text
billing    <- I was charged twice for my invoice.
technical  <- The app crashes with an error when I upload a file.
account    <- How do I change my email address?
billing    <- I get an error and the app crashes when I try to pay an invoice.
technical  <- I forgot my password, the reset email never arrives and login shows an error.
general    <- What are your opening hours?

After that, run_experiment prints its own progress and summary for each experiment.

What to look at in Phoenix.

  1. Open the project ticket-router and find the trace for the fourth ticket (the fourth oldest; the experiments in step 5 call the same functions and may add later traces). It has a root span route_v1 of kind CHAIN and a child span count_hits of kind TOOL. The tool span's output is {"billing": 1, "technical": 2, "account": 0}, while the chain span's output is billing. The counting was right and the decision was wrong, so the bug is in the rule that picks a queue. You found that without adding a print statement.
  2. Open the dataset ticket-router-golden and its Experiments tab. Both experiments ran the same six examples, and each run carries an exact_match annotation of 1 or 0.
ExperimentCorrectMean exact_matchMisses
router-v14 of 60.67ticket 4 routed to billing, ticket 5 routed to technical
router-v26 of 61.00none

Check it by hand. Ticket 4 contains one billing keyword (invoice) and two technical keywords (error, crash). Version 1 walks the queues in order and stops at the first one with a hit, which is billing. Version 2 takes the queue with the most hits, which is technical. Ticket 5 contains one technical keyword (error) and three account keywords (password, email, login), so the same rule sends it to account. Four correct out of six is 4/6≈0.674/6 \approx 0.674/6≈0.67, and six out of six is 1.001.001.00.

What the result means. The dataset and the evaluator stayed fixed and only the task changed, so the two scores are comparable. That is the whole value of an experiment. To use the same script on a real LLM application, replace the router with your model call, install the matching instrumentor (for example openinference-instrumentation-openai) and pass auto_instrument=True to register. The traces then contain LLM spans with token counts. When the right answer is not a single string, replace exact_match with a ClassificationEvaluator.

Edge cases and limitations

Turning on authentication stops ingestion until API keys exist
The authentication page warns that enabling it stops trace collection and blocks all API access until API keys are created, and recommends scheduling downtime for an instance that is already in use. After setting PHOENIX_ENABLE_AUTH and PHOENIX_SECRET you must log in as the default admin, change the password, create a system API key and give it to every client as PHOENIX_API_KEY. Plan that sequence before you flip the switch on a shared instance.
A suffixed endpoint variable can send Python spans to the wrong port
PHOENIX_COLLECTOR_ENDPOINT may be a base URL or a full OTLP URL ending in /v1/traces, depending on what reads it. The Python register() function infers the transport, and the documentation states that when the variable holds a URL with the /v1/traces suffix and register() is left to infer, it rewrites the port to the gRPC port 4317 and keeps the path, so no spans arrive. Set the variable to a base URL, or pass protocol="http/protobuf" together with a suffixed one. The same page adds that Python trace export does not yet read PHOENIX_ENDPOINT, the variable the Python client reads for its REST calls, so set the collector variable when traces are what you are redirecting.
One instance is one tenant
Every user of a Phoenix instance can reach its projects, traces, datasets and experiments, subject only to instance-wide roles. The architecture page says permissions scoped to individual projects or datasets are planned and not yet available. If two teams or two customers must not see each other's prompts, run separate instances, optionally on separate PostgreSQL schemas of one database.
The licence allows self-hosting but not reselling it as a service
Phoenix is free to self-host with no feature limits, but the Elastic License 2.0 forbids providing it to third parties as a hosted or managed service that gives them access to a substantial set of its features. Read the licence text before you bundle Phoenix into a product that customers log into, and take legal advice if the case is not clear-cut.
Older tutorials use an evals API that current docs no longer show
An AWS article from June 2025 scores spans with llm_classify, a prompt template constant and px.Client().log_evaluations. The current documentation builds a ClassificationEvaluator, runs it over a dataframe and logs results through phoenix.client. The Phoenix server and its SDK packages are versioned independently, so check which package versions a tutorial assumes before copying its imports.
Alerting and production monitors are outside Phoenix
Phoenix records and scores what you send it and compares experiments. Its own comparison page lists production monitoring, alerting and custom dashboards as features of the commercial Arize AX platform, and the evaluation page points to AX for evals on production traffic with threshold-based triggers. If you need to be paged when quality drops, plan for another component.

When to use it, and when something simpler is enough

Use it when

  • You want tracing, evaluation and experiments in one tool that runs on a laptop or inside your own network, so prompts and customer data never leave infrastructure you control.
  • Your framework has an OpenInference instrumentor or already emits OpenTelemetry, and you want instrumentation that can be pointed at a different OTLP backend later.
  • You need a regression loop for prompts and agents: datasets built from real traces, experiments that compare versions on the same inputs, and a pytest suite that gates pull requests.
  • You work in a regulated or air-gapped environment where a hosted observability service is not allowed.

Think twice when

  • Nobody on the team can operate a server and a database, and you need a managed service with support, service-level agreements, alerting and vendor compliance certifications.
  • You need strict isolation between many teams or customers inside one instance, or you want to offer the tool itself to third parties as a hosted service, which the licence forbids.
  • You expect ingestion and analytical queries at a volume beyond what SQLite or PostgreSQL are designed for. The architecture page itself points such workloads to a different product.
  • The application is a single prompt with no tools or retrieval, where reading the request and response already tells you everything.

A simpler alternative. Log each prompt and response as a JSON line with a request id, and keep test cases in a file that a script replays after every change. That is enough while each request is one model call and one person is doing the testing. It stops being enough when a request has several steps whose order you cannot predict, or when two people need to compare versions on the same inputs and see why a score moved.

Key takeaways

  • Phoenix is a self-hosted server that receives OpenTelemetry traces written with OpenInference attribute names and gives you tracing, evaluations, datasets and experiments, and a prompt playground in one UI.
  • OpenTelemetry carries the spans, OpenInference defines the AI-specific span kinds and attributes, and Phoenix stores and displays them, so the same instrumentation can feed another OTLP backend.
  • Evaluators are code functions or judge-model classifiers whose results are stored as annotations on spans, and pre-built evaluators are only a starting point for your own task.
  • An experiment is trustworthy only when the dataset and the evaluators stay fixed and one thing in the task changes between runs.
  • A local or notebook instance is fine for debugging, but a shared instance needs persistent storage, authentication with API keys, a pinned image version and a retention policy.
  • The Elastic License 2.0 makes Phoenix free to self-host with all features and forbids offering it to third parties as a managed service.

Example 1 of 5

Hugging Face smolagents inspecting multi-agent runs in a local Phoenix

Hugging FaceDocumented in official docs

smolagents is Hugging Face's agent library. Its documentation page Inspecting runs with OpenTelemetry explains how to record agent runs and uses Phoenix as the first backend for collecting and viewing them. [26][4][24]

The problem

The page states the problem directly: agent runs are complicated to debug. Agent workflows are unpredictable by design, multi-step agents quickly fill a console with logs, and many errors are small model mistakes that the agent corrects on the next step. A typical consequence is that console logs make it hard to see which agent called which tool with what result, especially when a manager agent delegates to another agent.

Where this topic fits

Phoenix sits beside the agent as a local collector and viewer. Before it comes two lines of setup in the agent script. After it comes a person reading the trace tree in a browser. The agent code itself is not changed, because the OpenInference instrumentor for smolagents wraps the library's calls.

How it is applied, step by step

  1. The developer installs smolagents with the telemetry and toolkit extras, as the page instructs. The telemetry extra is what pulls in Phoenix and the OpenInference instrumentor for smolagents.
  2. The Phoenix server is started in the background as the collector, listening on port 6006.
  3. At the top of the script, register() creates the tracer provider that exports to the default local endpoint, and SmolagentsInstrumentor().instrument() switches on span creation for agent steps.
  4. The developer runs the agents normally. In the documented example a manager CodeAgent delegates a web search to a managed ToolCallingAgent.
  5. The run appears as a trace under the projects page of the local Phoenix UI, where the nesting shows the manager's steps, the delegated agent's steps and each tool call inside them.

Why this approach fits

A multi-agent run is a tree: a manager step contains a delegated agent, which contains model calls and tool calls. A trace is also a tree, so the structure of the run maps directly onto what the UI draws. Because smolagents adopted OpenTelemetry instead of a private logging format, the same OpenInference instrumentor can feed more than one backend: the page's Langfuse section calls the same SmolagentsInstrumentor, while its MLflow section uses MLflow's own autologging call instead.

Limitation or tradeoff

The setup on that page is a single-developer one: a local server with no authentication, and data that stays on that machine. It records what the agents did, including generated code and tool outputs, which may contain sensitive content unless you set the OpenInference masking variables. It does not judge whether the final answer was right. With default settings each span is exported as it ends, which suits a script; a long-running service would normally switch to batching and flush on shutdown. The page also shows MLflow and Langfuse as alternatives, so Phoenix is one option there and not a requirement.

What the sources document

  • The smolagents documentation says the library adopted the OpenTelemetry standard for instrumenting agent runs, so that after running some instrumentation code the agents run normally and everything is logged to the chosen platform. [26]
  • The page installs Phoenix by Arize AI because it is a good solution to collect and inspect the logs, and notes that other OpenTelemetry-compatible platforms could be used for collection and inspection. [26]
  • The documented steps are to install smolagents with the telemetry and toolkit extras, run the Phoenix server in the background, and call register() and SmolagentsInstrumentor().instrument(). The example run, a manager CodeAgent with a managed ToolCallingAgent that has web search and page-visit tools, is then inspected at port 6006 under the projects path. [26]
  • Phoenix's OTEL setup page lists batch processing of spans as off by default for the Python register() function, and warns that spans still queued in a processor when the process exits may not be exported. [4]
  • Phoenix's span masking page lists OpenInference environment variables, including OPENINFERENCE_HIDE_INPUTS and OPENINFERENCE_HIDE_OUTPUTS, and says the configuration is respected by all of the auto-instrumentors. [24]

The facts above come from the cited sources. The steps and analysis in this example are our explanation of how they fit together.

Example 2 of 5

Amazon Bedrock Agents traced into Phoenix and graded on tool calling

Amazon Web ServicesDocumented in an engineering article

An AWS Machine Learning Blog post dated 24 June 2025, co-written with Arize AI, announces an integration between Arize and Amazon Bedrock Agents and walks through tracing and evaluating a Bedrock agent with Arize Phoenix. [27][9]

The problem

Amazon Bedrock Agents is a managed service: Bedrock runs the orchestration, prompt handling and tool invocation for you. The post describes the resulting difficulty as a black box, where teams moving from proof of concept to production need to see response latency, token usage, runtime exceptions and function calling. Beyond seeing the steps, they need to know whether the agent chose the right tool, which the post calls a common evaluation metric for agents.

Where this topic fits

Phoenix is used twice. First as the trace backend: the application's call to the Bedrock agent runtime is instrumented and the agent's orchestration steps arrive as spans. Then as the evaluation layer: the LLM spans are queried back out, a judge model labels each tool call, and the labels are logged onto the same spans.

How it is applied, step by step

  1. The application calls register() with auto_instrument=True. With the OpenInference Bedrock instrumentation installed, calls to Bedrock and Bedrock Agents are instrumented without further code.
  2. The agent is invoked through the Bedrock agent runtime client with trace output enabled, and the instrumentation turns the agent's knowledge base lookups, orchestration steps and tool calls into spans in a Phoenix project.
  3. To evaluate, a span query selects the LLM spans, skipping any whose input mentions "evaluation", and keeps each span's input as the question and its output as the model's response.
  4. A helper extracts the tool names from each output with a regular expression, and a column of tool definitions is added so the judge can see what was available.
  5. A judge model on Bedrock classifies each row as correct or incorrect using Phoenix's tool calling template, with an explanation, and the label is converted to a score of 1 or 0.
  6. The results are logged back to Phoenix under the name Tool Calling Eval, so each span shows its label next to the trace.

Why this approach fits

With a managed agent you do not own the loop, so you cannot add logging inside it. Instrumenting the client call and letting the service's own trace events become spans gives visibility without changing the agent. Grading tool choice per LLM span, and not only the final answer, locates the failure: an agent can reach an acceptable answer through a wrong or wasteful tool call, and a per-span label exposes that.

Limitation or tradeoff

The evaluation depends on a judge model, so its labels can be wrong and should be checked against a sample of human labels. Tool names are pulled from output text with a regular expression, which breaks if the output format changes. The post's code uses llm_classify and log_evaluations, while current Phoenix docs show ClassificationEvaluator and the phoenix.client package, so the imports need checking against installed versions. The tool-definition text in the post's code names three Phoenix tools (phoenix-traces, phoenix-experiments and phoenix-datasets) and not the tools of the employee-leave agent being traced, so a real run needs the agent's own tool list. The walkthrough also sent traces to a hosted Phoenix endpoint, which moves prompts outside the AWS account unless Phoenix is self-hosted, an option the post mentions.

Phoenix pytest plugin turning an eval suite into a pull-request gate with history

The problem

A team that already has evaluation cases wants them to run on every pull request, so that a prompt or model change that breaks a known case fails the build. A plain pytest run gives pass or fail for today's commit but keeps no record. Nobody can see which cases started failing two weeks ago or how scores moved between commits, and LLM outputs vary from run to run, which makes a single pass or fail noisy.

Where this topic fits

The plugin sits inside the test run. Before it come ordinary pytest tests that call the application. During the run it creates or updates a Phoenix dataset from the test cases and records each test as an experiment run. After it, the pytest exit code decides the CI job, and Phoenix holds the history.

How it is applied, step by step

  1. Tests that should be recorded are marked with the phoenix marker and parametrised, so that each set of parameters becomes one dataset example with a stable identity taken from the parametrize ids.
  2. Inside the test, the application output is passed to log_output, and scores are attached with log_evaluation or by running an evaluator.
  3. The plugin maps the suite to a dataset and each case to an example, and records the outcome of the test's assertion as a reserved pass annotation on the run.
  4. In CI, a workflow installs the client with its pytest extra, sets the Phoenix endpoint and API key from secrets and runs pytest. A failed assertion fails the job.
  5. Each run is stored as an experiment tagged with the Git commit, so the same dataset accumulates a series of experiments that can be compared in the Phoenix UI.

Why this approach fits

Developers already know pytest and CI systems already understand its exit code, so nothing new has to be wired into the pipeline to block a merge. Recording the same cases as experiments on a fixed dataset adds the part that pytest lacks: a history of scores per commit. The repetitions option addresses run-to-run variation by running each case several times as separate recorded runs.

Limitation or tradeoff

Uploads to Phoenix are best-effort. The page says a network problem is reported as a warning and does not fail the build, so a green job does not prove the run was recorded. Parallel CI jobs that write to the same dataset name can prune each other's examples; the page advises giving each concurrent run its own dataset name. The CI runner also needs network access to the Phoenix instance and an API key, which is extra work when Phoenix lives inside a private network.

4Common mistakes

  1. Treating a notebook session or a container without a volume as durable storage.

    Why it causes problems
    Phoenix started inside a notebook does not persist data by default, and a container keeps its SQLite file inside the container filesystem. A kernel restart, a redeploy or a platform restart then erases every trace, dataset and experiment, usually just after the team has started to rely on them.
    How to recognise it
    The UI is empty after a restart, or the list of projects resets. In the deployment there is no volume mounted at the working directory and no PHOENIX_SQL_DATABASE_URL in the environment.
    How to fix it
    For one machine, mount a volume and set PHOENIX_WORKING_DIR to it. For a shared instance, set PHOENIX_SQL_DATABASE_URL to a PostgreSQL database that is backed up. Restart once on purpose and confirm the data is still there before anyone depends on it.

  2. Letting a short-lived process exit while spans are still waiting in a batch processor.

    Why it causes problems
    A batch span processor exports on a timer. A command-line script, a serverless function or a test run can finish before the timer fires, so the last spans, often the ones that contain the error, never reach Phoenix and the trace looks cut off or is missing.
    How to recognise it
    Traces from long-running services are complete, while traces from scripts and jobs end early or do not appear. The problem disappears when you add a sleep at the end of the script.
    How to fix it
    In short-lived processes keep the non-batched default of the Python register() call, or shut the tracer provider down explicitly before exit so that it flushes. Use batching in long-running servers, where its lower overhead matters. The TypeScript register() batches by default, so scripts in that language need the explicit shutdown.

  3. Running judge-model evaluations with auto-instrumentation still tracing into the application project.

    Why it causes problems
    Every judge call becomes a trace that looks like application traffic. Token and cost totals for the project are inflated, and the next evaluation pass can pick up the judge's own spans and grade them. The AWS walkthrough has to filter such spans out of its query by their input text.
    How to recognise it
    The project contains spans whose input begins with your evaluation rubric, and the number of LLM spans roughly doubles after each evaluation run.
    How to fix it
    Wrap the evaluation run in the suppress_tracing() helper described on the Phoenix tracing-helpers page, or send evaluator traces to a separate project so that they stay inspectable without polluting application data.

  4. Changing the dataset, the evaluator and the prompt between two experiments and then comparing scores.

    Why it causes problems
    A score difference then has three possible causes and you cannot tell which one produced it. Teams ship a prompt that looks better only because the new evaluator is more lenient or because hard examples were removed from the dataset.
    How to recognise it
    The two experiments have different example counts, sit on different dataset versions or list different evaluator names, or the baseline was never rerun after the evaluator was edited.
    How to fix it
    Change one thing per experiment. When the dataset or an evaluator has to change, rerun the baseline on the new dataset with the new evaluator first, mark that run as the baseline, and compare candidates only against it.

  5. Adopting a pre-built LLM evaluator as the quality metric without checking it against human labels.

    Why it causes problems
    A judge prompt written for a generic task can disagree with what your users consider correct. The dashboard then shows a steady, confident score that tracks the judge's habits and not real quality, and experiments optimise toward the judge.
    How to recognise it
    Label 30 to 50 outputs by hand and compare them with the evaluator's labels. Frequent disagreement, or explanations that cite criteria you do not care about, means the evaluator does not measure your task.
    How to fix it
    Treat pre-built evaluators as templates. Rewrite the rubric in terms of your task, read the explanations the judge returns, and keep a small human-labelled set that you rerun whenever the judge prompt or judge model changes.

  6. Exposing a shared instance with authentication off, or on with the default admin password.

    Why it causes problems
    Traces contain full prompts, retrieved documents and tool outputs. With authentication disabled, anyone who can reach port 6006 can read all of it and can also write traces. With it enabled, the default admin account starts with a published password until someone changes it.
    How to recognise it
    Opening the URL from another machine shows the UI without a login screen, or the admin account still accepts the documented default password.
    How to fix it
    Set PHOENIX_ENABLE_AUTH and a strong PHOENIX_SECRET kept in a secret store, set the initial admin password through PHOENIX_DEFAULT_ADMIN_INITIAL_PASSWORD or change it at first login, issue API keys to clients, and keep the instance behind TLS and your network controls.

cost = (prompt * PRICE_PER_MILLION["prompt"] + completion * PRICE_PER_MILLION["completion"]) / 1_000_000
print(f"tokens: prompt {prompt}, completion {completion}, total {prompt + completion}")
print(f"cost: {cost:.5f} USD")

errors = [span["name"] for span in SPANS if span["status"] == "ERROR"]
print(f"error spans: {errors}")


def window_matches(output, expected) -> bool:
    """Code evaluator: does the answer state the expected refund window?"""
    return f"{expected['window_days']} days" in output


answer = SPANS[-1]["attributes"]["output.value"]
print("window_matches:", window_matches(answer, {"window_days": 30}))

Output:

text
trace latency: 4200 ms
  search_docs    RETRIEVER   600 ms   14.3%  OK
  draft_answer   LLM        2300 ms   54.8%  OK
  policy_lookup  TOOL        200 ms    4.8%  ERROR
  final_answer   LLM        1000 ms   23.8%  OK
  time outside child spans: 100 ms
tokens: prompt 4150, completion 330, total 4480
cost: 0.01740 USD
error spans: ['policy_lookup']
window_matches: False

1. Latency. The root span runs from 0 to 4,200 ms. The four children sum to 4,100 ms, so 100 ms is glue code between steps. More than half the time is the first model call.

2. Tokens and cost. Prompt tokens are 1,850 + 2,300 = 4,150 and completion tokens are 210 + 120 = 330. Cost is 4,150 × 3 / 1,000,000 + 330 × 15 / 1,000,000 = 0.01245 + 0.00495 = 0.0174 USD. The second prompt is larger than the first because it carries the first draft forward.

3. The failure. policy_lookup ended with status ERROR after 200 ms. The application then ran final_answer anyway, and the root span reports OK. The run failed silently: nothing in the response or the top-level status says the policy tool never returned.

4. Two hypotheses.

  • Retrieval. The best document score is 0.41 and the third is 0.12. Open the search_docs span and read the retrieved documents. If none of them states the 30-day window, the model had no grounding and the fix is in indexing or the query.
  • Tool failure handled badly. Open the final_answer span and read its input messages. If the tool error is missing from the prompt, or present but ignored, the model fell back to a guess. The fix is to pass the error to the model with an instruction to say it could not verify, and to revisit the 200 ms timeout.

5. The evaluator. window_matches returns False here because the output says 14 days. Added to an experiment over a dataset of policy questions, it turns this one observed failure into a check that runs on every future version.

What the trace cannot tell you. It shows that the answer was produced and how, but not that 30 days is correct. That knowledge comes from the reference output in a dataset or from a person.

Check your answer

  • Do your four child durations add up to 4,100 ms and leave 100 ms unaccounted for?
  • Did you get 4,480 total tokens and a cost of 0.0174 USD?
  • Did you notice that the root span's status is OK although a child span has status ERROR?
  • Does each of your hypotheses name the span you would open and the attribute you would read?
  • Does your evaluator return False for the 14-day answer and True for an answer that says 30 days?
