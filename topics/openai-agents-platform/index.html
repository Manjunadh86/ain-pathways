OpenAI Agents Platform (Responses API, AgentKit)

The OpenAI agents platform is the set of hosted services for building agents on OpenAI models. Its core is the Responses API, one endpoint that runs a model together with built-in and custom tools. Around it sit MCP connections, the ChatKit chat interface, the Agents SDK and Agents API runtimes, and the AgentKit tools (Agent Builder, evals and trace grading).

1Overview

Why it matters

If you build an agent on OpenAI models, most design choices reduce to one question: which parts of the agent do you run, and which parts does OpenAI run for you? The platform will take over tool execution (web search, file search, code execution), conversation state, the agent loop, the chat interface and the evaluation dashboard. Each handover removes code you would have written and adds a dependency on pricing, on data retention rules and on the product continuing to exist.

That last dependency is real. In June 2026 OpenAI announced that Agent Builder and the Evals platform will shut down on 30 November 2026, and the Assistants API was removed in August 2026. The Responses API, MCP support, ChatKit and the Agents SDK continue. Anyone choosing this platform, or maintaining something built on it, needs to know which layer each feature belongs to, how to read what the API returns, and how to move a piece back into their own code when a hosted product is withdrawn.

Key terms

Responses API
OpenAI's main endpoint for generating model output (POST /v1/responses). It accepts and returns typed items and can run tools inside a single request.
Item
One typed entry in a request's input or a response's output, such as a message, a reasoning record, a function call or a web search call.
Hosted tool
A tool that OpenAI executes on its own servers during a request, such as web search, file search or the code interpreter. Also called a built-in tool.
Function tool
A tool you describe with a JSON schema. The model returns a function_call item, and your own code runs the function and sends back the result.
Remote MCP server
A service that exposes tools over the Model Context Protocol at a URL. The Responses API can list and call its tools on your behalf.
Connector
An OpenAI-maintained integration with a third-party service such as Gmail or Dropbox, selected with connector_id in the MCP tool. It is now a legacy option.
AgentKit
The name OpenAI gave in October 2025 to a group of agent tools, namely Agent Builder, Connector Registry, ChatKit and expanded evaluation features.
ChatKit
An embeddable chat interface with client and server SDKs for agent conversations, including streaming, threads, widgets and file attachments.
Trace
The end-to-end record of one agent run, covering its model calls, tool calls, guardrails and handoffs.
Grader
An automated check that scores an output or a trace, ranging from an exact string comparison to a second model acting as a judge.

2Explanation

Introduction

In The Agent Loop you wrote the loop yourself: call the model, run the tool it asks for, append the result, repeat. Every part of that loop ran in your process. The OpenAI agents platform is what you get when the model provider offers to run some of those parts for you.

A useful way to hold it in your head is as five layers. For each one you decide whether to own it or hand it over:

  • Tools. OpenAI can execute web search, file search and code for the model, and can call remote MCP servers on your behalf. Tools that touch your own systems stay in your code as function tools.
  • The model call. The Responses API is the endpoint underneath everything else. It returns a list of typed items (messages, reasoning, tool calls) and can keep conversation state on OpenAI's side.
  • The agent loop. You can write it yourself against the Responses API, let the open-source Agents SDK run it inside your application, or let the Agents API run it on OpenAI's servers.
  • The chat interface. ChatKit is an embeddable chat widget with a server SDK.
  • Measurement. Traces record each run, and graders and evals score them.

AgentKit is the name OpenAI gave in October 2025 to the upper part of this stack. Its year-end developer roundup (opens in a new tab) lists the pieces: Agent Builder (a visual canvas for workflows), ChatKit, a Connector Registry for administrators, and evaluation loops. The name matters less than the status of each piece. On the day this lesson was written, 9 October 2026, the Responses API, hosted tools, MCP support, ChatKit and the Agents SDK are current. Agent Builder and the Evals platform are deprecated and are scheduled to shut down on 30 November 2026.

The lesson works from the bottom of the stack upwards: how the Responses API and its tools behave, how MCP servers and connectors plug in, what Agent Builder and ChatKit add, where evals and trace grading fit, and how to choose between the hosted platform and the Agents SDK. The worked example then traces one support question through the item protocol offline, so you can see exactly which steps are yours.

How it works

The Responses API returns items, not one message

A request to POST /v1/responses carries instructions (system-level guidance), input (a string or a list of items) and tools. The reply has an output list, and every entry is a typed item. The type tells you who acted and whether anything is waiting for you:

Item typeProduced byWhat your code does
messagethe modelShow the text. Web citations arrive as annotations on it.
reasoningthe modelNothing, except pass it back if you replay history yourself.
web_search_call, file_search_call, mcp_callOpenAI, which already ran the toolNothing. Log it.
function_callthe model, asking youRun the function, then send a function_call_output item with the same call_id.
mcp_approval_requestthe platform, asking youSend an mcp_approval_response that approves or refuses.

OpenAI's migration guide (opens in a new tab) calls this an agentic loop by default: within one request the model can use several hosted tools and remote MCP servers, and can ask for your functions. Chat Completions remains supported, but Responses is recommended for new projects, and the same guide states that GPT-6 Astra and GPT-6.1 Sol require it for tool calling.

python
from openai import OpenAI

client = OpenAI()
response = client.responses.create(
    model="gpt-6-astra",  # the model name in OpenAI's docs on the day of writing
    instructions="You are a support agent for Acme.",
    tools=[
        {"type": "web_search", "filters": {"allowed_domains": ["help.acme.example"]}},
        {"type": "function", "name": "get_order", "description": "Look up an order by id.",
         "parameters": {"type": "object", "properties": {"order_id": {"type": "string"}},
                        "required": ["order_id"], "additionalProperties": False}},
    ],
    input="Where is order 1042, and can I still return it?",
)
for item in response.output:
    print(item.type)

This call needs an API key and was not run for this lesson. The worked example runs the same protocol offline.

Three kinds of tool, three owners

KindExamplesWho executes itWhat to watch
Hosted (built-in)web search, file search, code interpreter, image generationOpenAI, inside the requestYou see the call only after it ran. Search actions carry a per-call charge.
Remote MCP serverStripe's server at mcp.stripe.com, or a private server behind a tunnelOpenAI calls the server for youAnything in the model's context can be sent to that server.
Functionyour order lookup or refund APIYour codeEach round trip costs one more request.

Some tools are split between the two sides. For shell, apply-patch and computer-use tools, the tools guide (opens in a new tab) tells Agents SDK users to keep the harness in their own runtime: the model decides the action and your environment carries it out. To bound a hosted loop, the max_tool_calls request parameter caps the total number of built-in tool calls in one response.

Conversation state: three options

Responses are stored by default (store: true), which makes the second and third options possible.

OptionWhat you send next turnWhere history livesNotes
Manual replayThe whole item list, including every reasoning and tool itemYour storageWorks with store: false, so it is the option under zero data retention. Reasoning items come back encrypted and are replayed unchanged.
previous_response_idOnly the new itemsOpenAI, 30 days by defaultEarlier tokens are still billed as input. instructions are not carried over, so resend them.
Conversations APIThe new items and a conversation idOpenAI, with no 30-day limitA durable object reused across sessions, devices and jobs.

For work that runs for minutes, such as long web research, background: true lets the request continue asynchronously while you retrieve the result later.

MCP servers and connectors

The mcp tool type connects a model to a server that speaks the Model Context Protocol. You give it a server_label and one address: server_url for a public server, or tunnel_id for a private server reached through Secure MCP Tunnel, an outbound-only client that runs inside your network. The MCP guide (opens in a new tab) describes the flow:

  1. The API fetches the server's tool list and records it as an mcp_list_tools item. Keeping that item in context avoids a second fetch on later turns. allowed_tools imports only the tools you name.
  2. When the model calls a tool, the API makes the request and records an mcp_call item with the arguments and the output.
  3. By default the API asks first. It returns an mcp_approval_request, and you answer with an mcp_approval_response in the next request. require_approval can be never for a whole server or for named tools.

An OAuth token goes in the authorization field. The API does not store it, so you send it on every request. The guide is blunt about trust: a malicious server can exfiltrate anything that enters the model's context, so prefer servers hosted by the service provider itself and keep approvals on for sensitive actions.

Connectors are OpenAI-maintained integrations for eight services (Dropbox, Gmail, Google Calendar, Google Drive, Microsoft Teams, Outlook Calendar, Outlook Email and SharePoint). They use the same tool with connector_id in place of server_url. The guide now lists them as legacy connectors: connector_id is deprecated for models released after 1 September 2026, and existing models keep support. AgentKit also introduced a Connector Registry, an admin panel for managing connectors and third-party MCP servers across ChatGPT and the API.

Agent Builder and ChatKit

Agent Builder is a visual canvas. You connect nodes into a workflow: agent nodes, tool nodes (file search, guardrails, MCP), logic nodes (if/else, while, human approval) and data nodes. Publishing creates a versioned workflow with an id, which you pass to ChatKit or export as Agents SDK code. OpenAI announced the deprecation on 3 June 2026 and scheduled the shutdown for 30 November 2026. The documented way out is to export the code and continue in the Agents SDK, or to rebuild the workflow as a ChatGPT workspace agent.

ChatKit is the chat interface layer: a web component that handles streaming, threads, tool activity, attachments and interactive widgets. The ChatKit guide (opens in a new tab) gives two paths. In the hosted path your server creates a ChatKit session for a workflow id and hands a client secret to the browser. That path now serves only existing Agent Builder workflows. In the custom path you implement a ChatKitServer whose respond method streams events from your own agent backend and keeps threads in your database. New projects use the custom path.

Evals and trace grading

A trace is the record of one run. A grader returns a score from 0 to 1: a string_check, a text_similarity measure, a score_model grader that asks a second model to judge, or Python code. Trace grading runs graders over traces to find where a workflow went wrong, such as a wrong tool or a missed handoff. An eval runs graders over a dataset so that you can compare two versions of a prompt or an agent.

Graders, datasets and eval runs belong to the Evals platform, and trace grading was launched as one of its capabilities. The deprecations page (opens in a new tab) schedules the platform to become read-only on 31 October 2026 and to shut down on 30 November 2026, and says graders are part of that transition. The trace grading guide carries no notice of its own, but it depends on graders and on the evaluation dashboard, so plan as if it ends too. OpenAI's migration recipe points to Promptfoo, an open-source tool whose evals live in a configuration file next to your code. The method outlives the product, and Evaluating Agents teaches it without a vendor.

Where the Agents SDK and the Agents API fit

OpenAI's agents overview (opens in a new tab) compares three runtimes:

Responses APIAgents SDKAgents API
Who runs the loopYour codeThe SDK's runner, inside your applicationOpenAI, in a managed Codex harness
State between turnsManual history, response chaining or ConversationsYour storage and SDK sessions, or Responses stateSaved sessions
Integration effort, as the docs rate itHighMediumLow

The Agents SDK is an open-source library, and the platform is the service it talks to. Its documentation recommends the model class that calls the Responses API, an agent can carry hosted tools and hosted MCP tools, and a run can keep its state in SDK sessions or in Responses conversation state. Agent Builder exports SDK code, and ChatKit's server library has a helper that streams an SDK run. The Agents API moves the loop itself to OpenAI, which manages sessions, context compaction and recovery and can attach a sandbox. Its overview states that it does not support zero data retention.

Worked example: Tracing one support question through the Responses item protocol, offline

A customer asks a support agent: Where is order 1042, and can I still return it? The agent has two tools. Web search limited to the help centre is a hosted tool, so OpenAI runs it. get_order is a function tool, so your code runs it. Two follow-up questions continue the conversation with previous_response_id.

So that everyone gets the same output without an API key, a class named FakeResponses stands in for client.responses. It returns scripted output lists with the item shapes the real API uses, remembers each response by id, rejects a function_call_output whose call_id was never issued, and reports usage.input_tokens for the whole chain. Token counts are a rough estimate of four characters per token. Save this as responses_trace.py. It needs only the Python standard library.

python
import json

INSTRUCTIONS = "You are a support agent for Acme. Quote the returns policy when asked."
TOOLS = [
    {"type": "web_search", "filters": {"allowed_domains": ["help.acme.example"]}},
    {"type": "function", "name": "get_order", "description": "Look up an order by id.",
     "parameters": {"type": "object", "properties": {"order_id": {"type": "string"}},
                    "required": ["order_id"], "additionalProperties": False}},
]
ORDERS = {"1042": {"status": "shipped", "shipped_on": "2026-10-06"}}
FUNCTIONS = {"get_order": lambda order_id: json.dumps(ORDERS[order_id])}
RUN_BY = {"reasoning": "the model", "message": "the model",
          "web_search_call": "OpenAI, inside the request", "function_call": "YOUR CODE"}


def message(item_id, text):
    return {"type": "message", "id": item_id, "role": "assistant", "status": "completed",
            "content": [{"type": "output_text", "text": text, "annotations": []}]}


SCRIPT = [  # the output list the stand-in model returns for each request
    [{"type": "reasoning", "id": "rs_1", "summary": []},
     {"type": "web_search_call", "id": "ws_1", "status": "completed",
      "action": {"type": "search", "query": "Acme returns policy"}},
     {"type": "function_call", "id": "fc_1", "call_id": "call_1", "status": "completed",
      "name": "get_order", "arguments": "{\"order_id\": \"1042\"}"}],
    [message("msg_1", "Order 1042 shipped on 6 October. Returns are accepted for 30 days.")],
    [message("msg_2", "Yes. 30 days after 6 October is 5 November.")],
    [message("msg_3", "Yes. The policy allows returns by post or in any Acme store.")],
]


def tokens(value):  # rough estimate: about 4 characters per token
    return len(json.dumps(value)) // 4


class FakeResponses:
    """Offline stand-in for client.responses with the same item protocol."""

    def __init__(self, script):
        self.script, self.stored = iter(script), {}

    def create(self, input, previous_response_id=None):
        chain = self.stored[previous_response_id] if previous_response_id else []
        asked = {i["call_id"] for i in chain if i.get("type") == "function_call"}
        for item in input:
            if item.get("type") == "function_call_output" and item["call_id"] not in asked:
                raise ValueError(f"no function_call with call_id {item['call_id']}")
        output = next(self.script)
        response_id = f"resp_{len(self.stored) + 1}"
        self.stored = {**self.stored, response_id: [*chain, *input, *output]}
        billed = tokens(INSTRUCTIONS) + tokens(TOOLS) + tokens([*chain, *input])
        return {"id": response_id, "output": output, "usage": {"input_tokens": billed}}


def run_turn(client, new_items, previous_id=None, max_requests=4):
    for _ in range(max_requests):
        response = client.create(input=new_items, previous_response_id=previous_id)
        uploaded = tokens(INSTRUCTIONS) + tokens(TOOLS) + tokens(new_items)
        print(f"{response['id']}: uploaded ~{uploaded} tokens, "
              f"billed input ~{response['usage']['input_tokens']}")
        for item in response["output"]:
            print(f"    {item['type']:<17} run by {RUN_BY[item['type']]}")
        calls = [item for item in response["output"] if item["type"] == "function_call"]
        if not calls:
            return response
        new_items = [{"type": "function_call_output", "call_id": call["call_id"],
                      "output": FUNCTIONS[call["name"]](**json.loads(call["arguments"]))}
                     for call in calls]
        previous_id = response["id"]
    raise RuntimeError("request limit reached before a final message")


def ask(client, text, previous_id=None):
    response = run_turn(client, [{"role": "user", "content": text}], previous_id)
    print("    ->", response["output"][-1]["content"][0]["text"])
    return response["id"]


if __name__ == "__main__":
    api = FakeResponses(SCRIPT)
    turn_1 = ask(api, "Where is order 1042, and can I still return it?")
    turn_2 = ask(api, "So is 5 November the last day?", turn_1)
    ask(api, "Can I return it in a store?", turn_2)

Running python3 responses_trace.py prints:

text
resp_1: uploaded ~113 tokens, billed input ~113
    reasoning         run by the model
    web_search_call   run by OpenAI, inside the request
    function_call     run by YOUR CODE
resp_2: uploaded ~124 tokens, billed input ~226
    message           run by the model
    -> Order 1042 shipped on 6 October. Returns are accepted for 30 days.
resp_3: uploaded ~108 tokens, billed input ~295
    message           run by the model
    -> Yes. 30 days after 6 October is 5 November.
resp_4: uploaded ~108 tokens, billed input ~358
    message           run by the model
    -> Yes. The policy allows returns by post or in any Acme store.

What to notice:

  • One response, two owners. In resp_1 the web search had already run when the response arrived. The function_call was a request to your code, so run_turn ran get_order and sent a function_call_output carrying call_1. The answer needed a second request.
  • A turn is not a request. The first question took two requests and each follow-up took one. max_requests bounds the loop, like the step limit in the previous lesson.
  • Stored state shrinks the upload, not the bill. The script uploaded about 113 + 124 + 108 + 108 = 453 tokens, but billed input was about 113 + 226 + 295 + 358 = 992, because every request reads the whole chain. OpenAI documents this for previous_response_id. With manual replay the upload would also be 992: the same bill, larger requests, nothing stored at OpenAI.
  • What the stand-in omits. Real usage.input_tokens also counts what a hosted tool feeds to the model inside the request, and input_tokens_details.cached_tokens shows how much came from the prompt cache. Read usage instead of estimating.

To use the real API, replace FakeResponses(SCRIPT) with OpenAI().responses, pass model, instructions and tools to create, and read attributes (item.type, item.call_id) instead of keys.

Edge cases and limitations

previous_response_id does not make a long conversation cheaper
Chaining responses means you upload only the new items, but OpenAI's guides state that all previous input tokens in the chain are billed as input on every request. Watch usage.input_tokens per request. If it climbs steadily, trim or summarise history yourself, or use the platform's compaction features. A chain also does not carry the previous instructions forward, so a request that omits them runs without your system guidance.
Zero data retention removes the stateful options
For organisations with zero data retention, OpenAI enforces store false, so previous_response_id chains and stored responses are not available. The documented pattern is manual replay: keep every output item, including the encrypted reasoning items the API returns, and send them back on the next request. The Agents API is not an alternative here, because its overview says it does not support zero data retention and offers data residency only in the United States.
A hosted tool call cannot be vetted before it runs
A function_call waits for your code, so you can validate its arguments or ask a person. A web search or file search has already happened when you see its item. The controls are different: restrict web search with allowed domains, cap built-in calls with max_tool_calls, and for MCP servers keep approvals on so that the request pauses with an mcp_approval_request. When you show web search results to users, the web search guide requires the inline citations to be visible and clickable.
Stored responses expire but conversations do not
Response objects are kept for 30 days by default, while the conversation state guide says Conversation objects and their items are not subject to that limit. A support thread that a customer reopens after six weeks therefore needs either the Conversations API or your own copy of the items. Decide this before launch, because the choice also decides how long customer text stays on OpenAI's servers.
A connector that works today can fail after a model upgrade
connector_id is deprecated for models released after 1 September 2026, and the guide's own connector examples use an older model for that reason. A team that keeps a Gmail or SharePoint connector and then changes the model name to a newer release should expect the tool configuration to need replacing. Switch to a remote MCP server with server_url, or to a tunnel, before the model upgrade and test both changes separately.
An exported Agent Builder workflow is not the same program
The migration guide says the export does not convert the workflow graph and does not guarantee that every behaviour transfers unchanged. Control flow, triggers, tools, authentication and permissions all need review. Treat the exported Agents SDK code as a first draft, replay representative inputs from the original workflow against it, and compare the results before the canvas disappears on 30 November 2026.

When to use it, and when something simpler is enough

Use it when

  • You are building on OpenAI models and need a capability the platform already hosts, such as web search with citations, file search or code execution. One tool entry replaces a retrieval service or a sandbox you would otherwise operate.
  • The agent needs a few of your own functions next to hosted tools and a short loop is enough. Call the Responses API directly and handle function_call items yourself.
  • You want handoffs, guardrails, sessions and tracing without writing them, but the loop must run in your own process with your own storage. Use the Agents SDK on top of the Responses API.
  • Tasks run for a long time, need a sandbox for files and commands, and you accept that OpenAI stores the session. That is the case the Agents API is designed for.
  • You need a production chat interface with streaming, threads and widgets and can run a small server for it. Use ChatKit's custom server integration.

Think twice when

  • You must be able to change model provider without rewriting tool and state handling. Hosted tools, stored responses and connectors exist only on OpenAI's platform.
  • Your organisation requires zero data retention and the design depends on stored conversation state or on the Agents API.
  • You are about to start new work in Agent Builder or the Evals dashboard. Both shut down on 30 November 2026, so build the workflow in code and keep evals in your repository.
  • The agent would send sensitive data to an MCP server whose operator you cannot vet, or would let it write to a system of record without an approval step.

A simpler alternative. One Responses API call with a function tool and manual replay of the item list, which is the loop from the previous lesson with a different response format. It stores nothing at OpenAI, uses no hosted tools and leaves nothing to migrate. It stops being enough when you find yourself rebuilding what the platform already has, such as a web retrieval pipeline, a code sandbox, durable sessions or a chat interface with streaming and threads.

Key takeaways

  • The Responses API returns a list of typed items, and the type tells you who acted: hosted tool calls have already run, while a function_call or an approval request is waiting for your code.
  • Hosted tools and remote MCP servers execute inside one request, which saves round trips but removes your chance to inspect a call beforehand unless you require approval.
  • Conversation state can live in your own item list, in a previous_response_id chain or in a Conversations object, and server-side state reduces what you upload without reducing what you are billed.
  • Agent Builder and the Evals platform shut down on 30 November 2026, while the Responses API, MCP support, ChatKit and the Agents SDK continue, so check the deprecations page before depending on a hosted component.
  • The Agents SDK runs the agent loop in your process on top of the Responses API, and the Agents API runs it on OpenAI's servers, so choose by who should own the loop, the state and the execution environment.

Example 1 of 5

Collxn's record-collection chat on the Responses API with web search and 16 function tools

CollxnDocumented in a case study

Collxn is a small service for vinyl collectors that connects to a user's Discogs collection and sends a daily email about one record. Its developer describes the build in the OpenAI developer blog post From prompts to products: One year of Responses, a set of first-person stories from developers using the API. [20][5][6][7]

The problem

Collectors want to ask questions about the record in their daily email: its current market price, the artist's other albums, how rare the pressing is. Answering needs live data from the Discogs API, facts from the user's own Collxn account and, for artist news, the open web. The developer wanted this without building and operating a full retrieval-augmented generation system.

Where this topic fits

The Responses API is the backend of the chat feature, which is called Ask This Drop. The application defines its Discogs and account lookups as function tools and adds the built-in web search tool. Follow-up questions rely on the API's stateful conversations. A separate, non-interactive job, the news section of the daily email, uses the Agents SDK with a web-search agent, so the product runs on both the hosted API and the SDK.

How it is applied, step by step

  1. The application registers its own tools with the request: lookups against the Discogs API and queries on the user's Collxn account. The post counts 16 custom tools.
  2. It adds the built-in web search tool to the same request so that artist news can be looked up inside the chat.
  3. When a user asks about a record, the model decides which tools the question needs. A typical implementation receives function_call items for the Discogs lookups, runs them and returns function_call_output items.
  4. A question about recent artist news is served by hosted web search, which runs inside the request and needs no code from the application.
  5. Follow-up questions use the API's stored conversation state, so the application does not rebuild the transcript on every turn.
  6. For the daily email, a separate Agents SDK agent with web search gathers recent news about the featured artist.

Why this approach fits

The questions mix three kinds of data with three owners: Discogs (an external API the application already integrates), the user's account (private to the application) and the open web. Function tools keep the first two inside the application's own code and permissions, and the hosted search tool covers the third without a crawler or an index. Because one request can combine them, the application code stays a short loop.

Limitation or tradeoff

Sixteen function tools is close to the size at which OpenAI's function calling guide advises care: it suggests fewer than 20 functions at the start of a turn and deferring the rest with tool search. Web search actions are billed per call, and their citations must be displayed. A request-level cap such as max_tool_calls is the available guard on built-in tool use. Stored conversation state keeps users' questions on OpenAI's servers for the retention period, and every later turn is billed for the earlier tokens.

What the sources document

  • Collxn's chat interface, Ask This Drop, uses the Responses API, and the model is configured with Discogs API tools so that it can retrieve information directly from Discogs when answering. [20]

Example 2 of 5

Calling Stripe's hosted MCP server from the Responses API with OAuth and approvals

Stripe and OpenAIDocumented in official docs

OpenAI's MCP guide uses Stripe's remote MCP server as its example of an authenticated server and recommends it by name as the official one. Stripe's own documentation describes the same server at mcp.stripe.com, its authentication methods and its tools. [8][9][10][11]

The problem

An agent has to act in a payments account, for example to create a payment link or look up an invoice. Writing and maintaining a function tool for every endpoint of a large payments API is expensive, and a wrong write in a payments system costs real money. The integration also has to carry a credential for one specific Stripe account without that credential ending up in stored responses.

Where this topic fits

The MCP tool is one entry in the tools list of a Responses API request, next to any hosted or function tools. Before it comes the application's OAuth flow with Stripe, which produces the access token. During the request, OpenAI's servers talk to Stripe's server. Afterwards the application reads mcp_call items, or answers mcp_approval_request items when approval is required. A private MCP server would use a tunnel in place of a public URL.

How it is applied, step by step

  1. The application completes Stripe's OAuth flow and holds the resulting access token. Stripe also documents agent API keys for clients that cannot use OAuth.
  2. Each request adds a tool of type mcp with a server_label, the server_url https://mcp.stripe.com and the token in the authorization field.
  3. The API lists the server's tools and records them in an mcp_list_tools item. Passing allowed_tools limits the import to the tools the task needs.
  4. When the model wants a tool, the default behaviour is to pause and return an mcp_approval_request that shows the tool name and its arguments.
  5. The application, or a person using it, approves or refuses by sending an mcp_approval_response in the next request, chained with previous_response_id.
  6. After approval the API calls Stripe and records an mcp_call item with the arguments and the server's output, and the model writes its answer from that output.

Why this approach fits

Stripe maintains the server, its tool list and its permission model, so the agent gains a large API without the application defining a function per endpoint. Stripe's generic read and write tools keep the tool list short. The approval mechanism matches the risk: reads can flow, while a write pauses with its exact arguments visible, which is the point where a person or a policy check belongs.

Limitation or tradeoff

Anything in the model's context can end up in a tool argument, so the trust decision covers the whole conversation and not only the Stripe call. OpenAI's guidance also differs by document: the MCP guide allows skipping approvals for a server you have come to trust, while its agent safety guide says to keep approvals on for every operation, reads included. Auto-approving reads, as the sketch does, is a risk decision to make deliberately. The token must be resent on every request, and Stripe states that from 31 October 2026 its MCP server no longer accepts full-access secret keys or restricted keys without the Agent tag. The MCP guide adds that servers may change tool behaviour unexpectedly.

What the sources document

  • OpenAI's MCP guide shows a Responses API request whose mcp tool has the server_url https://mcp.stripe.com and an OAuth access token in the authorization field, and states that the API does not store that value, so it must be sent in every request. [8]
  • The same guide recommends connecting to official servers hosted by the service providers themselves and gives the Stripe server at mcp.stripe.com as its example. [8]
  • By default the API requests approval before data is shared with a connector or remote MCP server, which creates an mcp_approval_request item, and require_approval can skip approvals for all tools or for listed tools. OpenAI's agent safety guide separately advises keeping tool approvals on for MCP tools, including reads and writes. [8][11]
  • Stripe documents its MCP server at https://mcp.stripe.com with two authentication methods, OAuth and agent API keys, lists tools that include stripe_api_read, stripe_api_write and search_stripe_documentation, and advises turning on the client's tool-approval setting. [9]
  • OpenAI's engineering post on Secure MCP Tunnel describes the alternative for private servers: a customer-run client opens an outbound HTTPS connection to OpenAI and forwards MCP requests to an approved local server. [10]

4Common mistakes

  1. Reading only output_text and ignoring the other items in a response.

    Why it causes problems
    A response that ends in a function_call has no final text. The application shows an empty answer or stops, and the tool the model asked for never runs. Approval requests are missed the same way, so an MCP workflow stalls without an error.
    How to recognise it
    Responses whose output_text is empty while the output list is not, and conversations that end right after the model decided to use a tool.
    How to fix it
    Iterate over response.output and branch on item.type. Handle function_call and mcp_approval_request explicitly, and log any type you do not recognise instead of dropping it.

  2. Dropping reasoning or tool items when replaying history by hand.

    Why it causes problems
    OpenAI's migration guide lists this among the common errors. The model loses the reasoning attached to its tool calls, and a function result that no longer has its matching call cannot be linked by call_id. The symptoms look like an inconsistent model, so the cause is hard to find.
    How to recognise it
    Code that rebuilds the input from role and content pairs only, or that filters a response's output down to messages before storing it.
    How to fix it
    Append every item of response.output to your history unchanged, add your function_call_output items with the same call_id, and send that whole list.

  3. Setting require_approval to never for a whole MCP server that has write tools.

    Why it causes problems
    Any text the model reads, including a web page or a tool result, can steer it into calling a write tool with data from the conversation. With approvals off, the call has already happened when your code first sees it.
    How to recognise it
    An mcp tool entry with no allowed_tools and require_approval set to never, on a server whose tool list includes create, update, send or delete operations.
    How to fix it
    Import only the tools the task needs with allowed_tools, skip approval only for named read tools, and route every other mcp_approval_request to a policy check or a person.

  4. Assuming a previous_response_id chain keeps cost flat as a conversation grows.

    Why it causes problems
    Every request is billed for all earlier input tokens in the chain. A long support thread costs several times what the size of your requests suggests, and it eventually reaches the context window.
    How to recognise it
    usage.input_tokens rising on every turn while your request bodies stay small, as in the worked example.
    How to fix it
    Record usage per conversation, and compact or summarise the history once it passes a threshold you choose. Then continue from the shortened history.

  5. Starting new work on a component that already has a shutdown date.

    Why it causes problems
    A workflow drawn in Agent Builder or an eval suite created in the Evals dashboard this month has to be rebuilt before 30 November 2026. A connector_id integration has to be replaced at the next model upgrade.
    How to recognise it
    A deprecation notice at the top of the product's documentation page, or an entry under upcoming deprecations on the deprecations page.
    How to fix it
    Check the deprecations page before adopting a hosted component, prefer artefacts that live in your repository such as SDK code and eval configuration files, and write down an exit path for each hosted piece in the design document.

  6. Creating ChatKit sessions with a shared or unauthenticated user value.

    Why it causes problems
    The session's user identifier is what ties a chat session to one end user, and the ChatKit guide marks it as a security requirement. A constant value, or one accepted from the browser without checking it, removes that separation between your users.
    How to recognise it
    Session creation code that hard-codes the user field, or an endpoint that returns a client secret without first checking who is asking.
    How to fix it
    Authenticate the request on your server first, then pass a stable identifier that is unique for each end user, as the ChatKit guide requires.

Exercise 1

Write an approval loop for MCP tool calls

CodingIntermediateAbout 40 min (estimate)Hypothetical scenario

An agent talks to a remote MCP server labelled billing that has two tools, search_invoices and create_refund. Approvals are on, so each tool call first arrives as an mcp_approval_request item, and nothing runs until your code answers with an item of this shape in the next request:

python
{"type": "mcp_approval_response", "approval_request_id": "mcpr_1", "approve": True}

Save the stand-in below as mcp_fake.py. It imitates client.responses.create for this scenario and records in executed which tools the server really ran. Then write approvals.py with a function run_with_approvals(client, user_text, auto_approve, max_requests) that drives the conversation and applies an approval policy. You need only the Python standard library.

python
import json

REQUESTS = {
    "mcpr_1": ("search_invoices", {"customer": "cus_7"}),
    "mcpr_2": ("create_refund", {"invoice": "in_33", "amount": 4000}),
}


def approval_request(request_id):
    name, arguments = REQUESTS[request_id]
    return {"type": "mcp_approval_request", "id": request_id, "server_label": "billing",
            "name": name, "arguments": json.dumps(arguments)}


def say(text):
    return {"type": "message", "role": "assistant",
            "content": [{"type": "output_text", "text": text}]}


class FakeBilling:
    """Scripted stand-in for client.responses with one MCP server labelled billing."""

    def __init__(self):
        self.pending, self.count, self.executed = set(), 0, []

    def create(self, input, previous_response_id=None):
        self.count = self.count + 1
        answers = [item for item in input if item.get("type") == "mcp_approval_response"]
        if not answers:
            output = [{"type": "mcp_list_tools", "server_label": "billing",
                       "tools": [{"name": "search_invoices"}, {"name": "create_refund"}]},
                      approval_request("mcpr_1")]
        else:
            request_id, approved = answers[0]["approval_request_id"], answers[0]["approve"]
            if request_id not in self.pending:
                raise ValueError(f"no pending approval request {request_id}")
            name = REQUESTS[request_id][0]
            if approved:
                self.executed = [*self.executed, name]
            if name == "search_invoices" and approved:
                output = [{"type": "mcp_call", "server_label": "billing", "name": name,
                           "output": "{\"invoice\": \"in_33\", \"amount\": 4000}"},
                          approval_request("mcpr_2")]
            elif name == "search_invoices":
                output = [say("I cannot look up invoices without approval.")]
            elif approved:
                output = [say("Refund of 40.00 USD issued for invoice in_33.")]
            else:
                output = [say("Invoice in_33 is 40.00 USD. I did not refund it: not approved.")]
        self.pending = {i["id"] for i in output if i["type"] == "mcp_approval_request"}
        return {"id": f"resp_{self.count}", "output": output}

Requirements

  • Approve a request only when its tool name is in the auto_approve set, whose default contains only search_invoices. Refuse every other request by sending approve False. Do not leave it unanswered.
  • Answer each approval request in the next call to create, chained with previous_response_id, and never send a response for an id that was not requested.
  • Treat mcp_list_tools and mcp_call items as information. They need no reply.
  • Stop after max_requests calls, with a default of 5, and return status request_limit with text None.
  • Return a dictionary with status, text and decisions, where decisions is a list of (tool name, approved) pairs in the order the requests arrived.

Expected behaviour

With the default policy and the question Refund customer cus_7 for their last invoice., the function returns status finished, the text Invoice in_33 is 40.00 USD. I did not refund it: not approved. and the decisions [('search_invoices', True), ('create_refund', False)]. The fake reports 3 requests and executed equal to ['search_invoices'].

With auto_approve={"search_invoices", "create_refund"} the text is Refund of 40.00 USD issued for invoice in_33. and executed lists both tools. With max_requests=1 the result has status request_limit, text None and one decision.

Hint 1

Filter response["output"] for items whose type is mcp_approval_request. If there are none, the last item is the final message.

Hint 2

Build the next input as a list with one mcp_approval_response per request, each carrying that request's id and your verdict.

Hint 3

Add each decision to the log before you send the answer, so the log is complete even when the request limit ends the run.

Show solution

Save this as approvals.py next to mcp_fake.py.

python
from mcp_fake import FakeBilling

READ_ONLY = frozenset({"search_invoices"})
MAX_REQUESTS = 5
QUESTION = "Refund customer cus_7 for their last invoice."


def run_with_approvals(client, user_text, auto_approve=READ_ONLY, max_requests=MAX_REQUESTS):
    new_items = [{"role": "user", "content": user_text}]
    previous_id, decisions = None, []
    for _ in range(max_requests):
        response = client.create(input=new_items, previous_response_id=previous_id)
        requests = [item for item in response["output"] if item["type"] == "mcp_approval_request"]
        if not requests:  # mcp_list_tools and mcp_call items need no reply
            text = response["output"][-1]["content"][0]["text"]
            return {"status": "finished", "text": text, "decisions": decisions}
        verdicts = [(request, request["name"] in auto_approve) for request in requests]
        decisions = [*decisions, *[(request["name"], approved) for request, approved in verdicts]]
        new_items = [{"type": "mcp_approval_response", "approval_request_id": request["id"],
                      "approve": approved} for request, approved in verdicts]
        previous_id = response["id"]
    return {"status": "request_limit", "text": None, "decisions": decisions}


if __name__ == "__main__":
    careful = FakeBilling()
    print(run_with_approvals(careful, QUESTION))
    print("requests:", careful.count, "| tools the server ran:", careful.executed)

    careless = FakeBilling()
    print(run_with_approvals(careless, QUESTION, auto_approve={"search_invoices", "create_refund"}))
    print("requests:", careless.count, "| tools the server ran:", careless.executed)

    print(run_with_approvals(FakeBilling(), QUESTION, max_requests=1))

Running python3 approvals.py prints:

text
{'status': 'finished', 'text': 'Invoice in_33 is 40.00 USD. I did not refund it: not approved.', 'decisions': [('search_invoices', True), ('create_refund', False)]}
requests: 3 | tools the server ran: ['search_invoices']
{'status': 'finished', 'text': 'Refund of 40.00 USD issued for invoice in_33.', 'decisions': [('search_invoices', True), ('create_refund', True)]}
requests: 3 | tools the server ran: ['search_invoices', 'create_refund']
{'status': 'request_limit', 'text': None, 'decisions': [('search_invoices', True)]}

Why it is built this way. The loop has the same shape as the function-call loop in the worked example: look for items that are waiting for you, answer each one by id, chain the next request, and stop on a message or on a limit. The policy is a single set lookup, which keeps the decision in one auditable place. A refusal is still an answer. Sending approve: False lets the model tell the user what it could not do, whereas an unanswered request would leave the conversation stuck. The second run shows what the policy protects against: with both tools auto-approved, the refund is issued and no person saw its arguments. In a real application the refused branch would hand the request, with its tool name and arguments, to a person (see Human-in-the-Loop) and send the approval only after they agree.

  • With max_requests=1, is the status request_limit and is text None instead of a guessed answer?
  • Does your loop send approve False for the refund request instead of leaving it unanswered?

Order of work: the evals first, because after 31 October they can no longer be changed, and their current results are the baseline that the recreated graders must reproduce. Then the workflow and ChatKit together, before 30 November. The connector must be replaced before the model upgrade, whenever that is scheduled. The state change waits for legal's decision.

Part c.

  • Evals move to a Promptfoo configuration file in the repository that holds the prompts, provider, test cases and assertions. Verify that each recreated grader, especially the model-scored ones, gives the same pass or fail as the old one on the same cases.
  • The Agent Builder workflow becomes the exported Agents SDK code, running in the team's own service. Verify by replaying representative triage inputs and comparing the routing decisions with the original workflow.
  • ChatKit moves to the custom server integration: a ChatKitServer whose respond method streams the SDK run, with the team's own thread store. Verify that sessions are tied to an authenticated, per-user identifier and that threads survive a server restart.
  • The connector becomes an mcp tool with server_url (a remote MCP server for the calendar, run by the provider or by the team) or with tunnel_id for a private server, and the OAuth token in authorization. Verify on the current model first that allowed_tools exposes only the booking tools and that a booking pauses for approval. Change the model afterwards.
  • State moves to manual replay with store: false: keep every output item, including the encrypted reasoning items, and send the full list on each turn. Verify that a multi-turn conversation still resolves references to earlier turns and that usage.input_tokens is what you expect.

Part d. The Agents SDK. The export from Agent Builder is already SDK code, ChatKit's server library has a helper that streams an SDK run, and the SDK keeps the loop and the state in the team's own process and storage, which leaves zero data retention possible. Calling the Responses API directly would work, but the team would rewrite by hand the routing and approval logic that the export already expresses. The Agents API fits least: its overview says it does not support zero data retention, and it is aimed at long-running tasks that need a sandbox, which a triage step is not.
