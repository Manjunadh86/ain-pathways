Agent Skills

An agent skill is a folder with a SKILL.md file that gives an AI agent the instructions for one kind of task, plus optional scripts, reference files and templates. The agent reads only each skill's name and description at startup and loads the rest when a task calls for it.

1Overview

Why it matters

A capable agent still does not know how your team ships a release, which of your tables use soft deletes, or the exact steps for producing a valid spreadsheet. You can put that knowledge in the system prompt, but then every request pays for it, and a prompt that covers fifty procedures is mostly noise on any one task. You can retype it in each conversation, or build a separate custom agent for each job. Skills are the third path: package the procedure as a folder, advertise it in a sentence or two, and load the details only when the task needs them.

The result is an agent that carries many specialisms at a small standing cost, with the knowledge kept in files that can be reviewed, versioned and shared like code. Anyone who configures coding agents, builds internal developer tooling, or ships a framework with guidance for AI assistants will meet skills. Mistakes are quiet: a skill with a weak description never loads, a bloated one crowds out the user's task, and one installed from an unknown source can steer the agent into harmful actions.

Key terms

Agent skill
A folder containing a SKILL.md file and, optionally, scripts, reference documents and templates that teach an agent how to perform one kind of task.
SKILL.md
The one required file in a skill. It holds YAML frontmatter with a name and a description, followed by Markdown instructions.
Frontmatter
The block of YAML between two lines of three hyphens at the top of SKILL.md. It carries the metadata that the agent reads before it decides to open the rest of the file.
Progressive disclosure
Loading a skill in stages so that context is spent only on what the current task needs: metadata first, then the instructions, then any bundled files.
Catalog
The list of every available skill's name and description that the harness shows the model at the start of a session. It is the first tier of progressive disclosure.
Activation
The moment a skill's full instructions are loaded into the context, either because the model asked for them or because the user invoked the skill directly.
Bundled resources
Files that travel with a skill: scripts in scripts/, documents in references/ and templates or data in assets/. They are read or run only when the instructions call for them.
Trigger rate
The fraction of repeated runs of a test prompt in which the agent loads a given skill. It is how you measure whether a description works.
Harness
The program around the model that builds prompts, runs tools and manages the context. In the skills setting it is the code that scans for skills, builds the catalog and handles activation.

2Explanation

Introduction

In Model Context Protocol (MCP) you gave an agent a way to reach outside systems: a database, a ticketing tool, a file store. That answers what the agent can touch. It does not answer how your team wants the work done. A new colleague with database access still needs the onboarding guide: which tables use soft deletes, what the release checklist says, how the quarterly report is laid out. Anthropic's engineering team uses that same onboarding-guide comparison to introduce agent skills.

An agent skill is that guide, written as a folder. The only required file is SKILL.md, which opens with a short block of metadata (a name and a description) and continues with Markdown instructions. Anything else the procedure needs, such as a script, a reference document or a template, sits in the same folder. This is the smallest valid header, taken from the Agent Skills specification (opens in a new tab):

markdown
---
name: skill-name
description: A description of what this skill does and when to use it.
---

Everything below the second --- line is the instructions. The clever part is how a skill is loaded. Putting fifty procedures in the prompt would swamp every request, so agents load skills in stages, which the format calls progressive disclosure. At startup the agent sees only the name and description of each skill. When a task matches a description, the agent reads that skill's full instructions. If the instructions mention a script or a reference file, the agent opens it only when it needs it.

Anthropic developed the format and released it as an open standard. The agentskills.io (opens in a new tab) site lists dozens of supporting products, among them Claude Code, OpenAI Codex, GitHub Copilot, Gemini CLI, Cursor and Databricks Genie Code. A folder written once can therefore travel between agents, with caveats that this lesson covers. The rest of the lesson explains how a harness implements the three stages, how skills differ from tools, MCP servers and always-loaded instruction files, how to write a description that triggers, and what to check before you run someone else's skill.

How it works

What is inside a skill

A skill is a directory. The only required file is SKILL.md; the rest is optional and follows conventions rather than rules:

text
pdf-processing/
├── SKILL.md          # required: metadata + instructions
├── scripts/          # optional: executable code
├── references/       # optional: documentation loaded on demand
└── assets/           # optional: templates, schemas, data files

The specification (opens in a new tab) defines six frontmatter fields:

FieldRequiredRule
nameyes1 to 64 characters: lowercase letters, digits and single hyphens, no leading or trailing hyphen, equal to the folder name
descriptionyes1 to 1,024 characters saying what the skill does and when to use it
licensenoA license name or the name of a bundled license file
compatibilitynoUp to 500 characters on environment needs such as packages or network access
metadatanoA map of string keys to string values for client-specific extras
allowed-toolsnoSpace-separated pre-approved tools; marked experimental, so support varies

The body has no format rules. The specification recommends step-by-step instructions, input and output examples and edge cases, kept under 500 lines. Products add extensions of their own. Claude Code (opens in a new tab) accepts fields such as disable-model-invocation and context: fork, and Codex (opens in a new tab) keeps its invocation policy in an optional agents/openai.yaml. These are product features, so a skill that depends on them is less portable.

Progressive disclosure: three tiers

TierWhat loadsWhenCost
1. Catalogname and description of every skillSession startAbout 50 to 100 tokens per skill
2. InstructionsThe SKILL.md bodyThe skill is activatedUnder 5,000 tokens recommended
3. ResourcesFiles in scripts/, references/, assets/The instructions point to themNothing until used; a script's code never enters the context, only its output

Anthropic's platform documentation (opens in a new tab) gives the same three levels. Products also cap the catalog: Claude Code truncates the combined description and when_to_use text of each skill at 1,536 characters in its listing, and Codex limits its initial skill list to 2% of the model's context window (8,000 characters when the window size is unknown). With the specification's figures, 20 installed skills cost about 2,000 tokens in the catalog, against 100,000 if every body at the recommended maximum were loaded up front.

The model chooses from the description alone, so the description is the trigger. The agentskills.io guide adds a nuance: agents typically consult a skill only for tasks beyond what they can do with their basic tools, so a trivial request may not load even a perfectly matched skill.

How a harness runs skills

The format does not say who loads what. That is the harness's job, and the client implementation guide (opens in a new tab) describes it in four steps.

  1. Discover. At startup, scan the skill directories. Most local agents scan a project scope and a user scope, often both a client-specific folder and the shared .agents/skills/ convention. A skill is any subdirectory holding a file named exactly SKILL.md; skip .git and node_modules and bound the scan depth.

  2. Parse. Read the frontmatter and keep the name, description and file location. The guide recommends lenient validation: a name that does not match its folder is a warning, but a missing description skips the skill, because there would be nothing to match a task against.

  3. Disclose. Put the catalog where the model sees it, either in the system prompt or in the description of a dedicated activation tool:

    xml
    <available_skills>
  <skill>
    <name>pdf-processing</name>
    <description>Extract PDF text, fill forms, merge files. Use when handling PDFs.</description>
  </skill>
</available_skills>

  4. Activate. Most harnesses let the model decide. It either reads SKILL.md with its ordinary file tool or calls a dedicated tool, which can strip the frontmatter, wrap the text in tags, list the bundled files and restrict the skill name to the valid set so the model cannot invent one. Users can also activate directly, for example with /skill-name in Claude Code or $ in Codex.

After activation the instructions are durable guidance. The guide says to exempt them from pruning when the context is compacted, since losing them degrades behaviour without any visible error, and to skip re-injecting a skill that is already in context.

Where skills live is outside the specification, so products differ:

ProductProject scopeUser or admin scope
Claude Code.claude/skills/~/.claude/skills/, plus managed enterprise skills
OpenAI Codex.agents/skills in the working directory and repository root$HOME/.agents/skills, /etc/codex/skills
Databricks Genie CodeWorkspace/.assistant/skills//Users/{username}/.assistant/skills/

Skills, tools, MCP servers and instruction files

All four put something in front of the model, which is why they get confused. A tool is a callable function: you define a name, a description and an input schema, the model returns a structured call, and your application (or the provider, for server tools) runs it, as the Claude tool use overview (opens in a new tab) explains. An MCP server exposes data sources, tools and workflows to an AI application through the Model Context Protocol, the open standard that the MCP introduction (opens in a new tab) describes for connecting AI applications to external systems. A skill supplies know-how: instructions, templates and scripts for a kind of task. By itself it connects to nothing and calls nothing. Anthropic says it will explore how skills can complement MCP servers by teaching agents more complex workflows that involve external tools. An instruction file such as CLAUDE.md or AGENTS.md holds facts needed on every task and is always in context. Claude Code's documentation draws the dividing line: when a section has grown into a procedure rather than a fact, move it to a skill.

They are partners more than rivals. In many harnesses the activation channel for a skill is itself a tool, and bundled scripts run through a shell tool. A skill that needs live data tells the agent which tool to call.

Writing a skill that works

  • Write the description for the trigger. It is all the model reads before deciding. Say what the skill does, then when to use it, and name contexts where the user will not use the domain word. Anthropic asks for third person ("Processes Excel files"), because the description is injected into the system prompt.
  • Add what the agent lacks. Skip explanations of what a PDF is. Spend tokens on project conventions, non-obvious edge cases and a short gotchas list, which the agentskills.io guide calls among the highest-value content.
  • Match strictness to fragility. Leave judgement calls to the model; give fragile sequences as exact commands. Offer a default, not a menu.
  • Bundle scripts for deterministic steps and design them for an agent: no interactive prompts, a useful --help, errors that say what to try next, structured output and bounded output size.
  • Keep references one level deep and say when to read each: "Read references/api-errors.md if the API returns a non-200 status code."
  • Test it. Compare runs with and without the skill, and test triggering with about twenty realistic queries, half that should trigger and half near-misses that should not.

Security

A skill is instructions plus code that the agent follows with your permissions. Anthropic's guidance is to install skills only from trusted sources, audit every bundled file, watch for unexpected network calls and for instructions that send the agent to external content, and treat a skill like installed software. Harnesses add controls. The client guide suggests gating project-level skills on a trust check, because a freshly cloned repository may be untrusted. Anthropic's API runs skills in a sandbox with no network access, while Spring AI's shell tool runs scripts on the local machine without one. See Prompt Injection and LLM Security and Code Execution and Sandboxing for the wider picture.

Worked example: Build a small skills harness and measure what progressive disclosure saves

This example builds a small skills harness in plain Python and measures what progressive disclosure saves. Save the script as skills_demo.py and run python3 skills_demo.py (Python 3.9 or later, no packages). It writes five sample skill folders into demo-skills/, so you can reproduce every number below. Each sample body ends with 60 numbered filler steps so that the bodies have a realistic length; the filler is the only reason they are long.

python
"""skills_demo.py - a minimal skills harness. Python 3.9+, standard library only."""
import re
import shutil
from pathlib import Path

ROOT = Path("demo-skills")
NAME_OK = re.compile(r"^[a-z0-9]+(-[a-z0-9]+)*$")  # no leading, trailing or doubled hyphens

SPECS = {  # folder -> (name, description)
    "pdf-processing": ("pdf-processing", "Extract text and tables from PDF files, fill forms, merge documents. Use when working with PDF files or when the user mentions PDFs, forms, or document extraction."),
    "release-notes": ("release-notes", "Draft customer-facing release notes from merged pull requests. Use when the user asks for release notes or a changelog entry."),
    "sql-style": ("sql-style", "Apply the team's SQL conventions when writing or reviewing queries. Use when the user writes, edits or reviews SQL."),
    "csv-cleaner": ("CSV_Cleaner", "Clean messy CSV files. Use when the user mentions CSV cleanup."),
    "no-description": ("no-description", ""),
}


def make_samples():
    shutil.rmtree(ROOT, ignore_errors=True)
    for folder, (name, desc) in SPECS.items():
        skill_dir = ROOT / folder
        (skill_dir / "scripts").mkdir(parents=True)
        (skill_dir / "scripts" / "run.py").write_text("print('ok')\n")
        head = f"---\nname: {name}\n" + (f"description: {desc}\n" if desc else "") + "---\n\n"
        steps = "".join(f"{i}. Step {i} (filler so the body has a realistic length).\n" for i in range(1, 61))
        (skill_dir / "SKILL.md").write_text(head + f"# {folder}\n\n" + steps)


def load(path):
    """Return (skill or None, warnings). Lenient: cosmetic problems warn, no description skips."""
    head, _, body = path.read_text()[4:].partition("\n---\n")
    fields = dict(line.split(": ", 1) for line in head.splitlines() if ": " in line)
    name, desc = fields.get("name", ""), fields.get("description", "")
    if not desc:
        return None, [f"{path.parent.name}: no description, skipped"]
    warnings = []
    if not NAME_OK.match(name) or len(name) > 64:
        warnings.append(f"{path.parent.name}: name {name!r} breaks the naming rules")
    if name != path.parent.name:
        warnings.append(f"{path.parent.name}: name {name!r} does not match the folder")
    return {"name": name, "description": desc, "body": body.strip(), "dir": path.parent}, warnings


def discover():
    skills, warnings = [], []
    for path in sorted(ROOT.glob("*/SKILL.md")):  # one level down, exact file name
        skill, found = load(path)
        warnings += found
        if skill:
            skills.append(skill)
    return skills, warnings


def catalog(skills):
    rows = "".join(
        f"<skill><name>{s['name']}</name><description>{s['description']}</description></skill>\n" for s in skills
    )
    return "<available_skills>\n" + rows + "</available_skills>"


def activate(skills, name):
    skill = next((s for s in skills if s["name"] == name), None)
    if skill is None:
        return f"ERROR: unknown skill {name!r}. Valid: " + ", ".join(s["name"] for s in skills)
    files = sorted(str(p.relative_to(skill["dir"])) for p in skill["dir"].rglob("*") if p.is_file() and p.name != "SKILL.md")
    listing = "".join(f"  <file>{f}</file>\n" for f in files)
    return (f'<skill_content name="{name}">\n{skill["body"]}\n\nSkill directory: {skill["dir"]}\n'
            f"<skill_resources>\n{listing}</skill_resources>\n</skill_content>")


if __name__ == "__main__":
    make_samples()
    skills, warnings = discover()
    print("\n".join(warnings))
    print("loaded:", ", ".join(s["name"] for s in skills))
    print("tier 1, catalog at startup :", len(catalog(skills)), "characters")
    print("tier 2, all bodies         :", sum(len(s["body"]) for s in skills), "characters")
    print("tier 2, one body activated :", len(activate(skills, "pdf-processing")), "characters")
    print(activate(skills, "pdf-processing-2"))

The expected output is:

text
csv-cleaner: name 'CSV_Cleaner' breaks the naming rules
csv-cleaner: name 'CSV_Cleaner' does not match the folder
no-description: no description, skipped
loaded: CSV_Cleaner, pdf-processing, release-notes, sql-style
tier 1, catalog at startup : 774 characters
tier 2, all bodies         : 13667 characters
tier 2, one body activated : 3586 characters
ERROR: unknown skill 'pdf-processing-2'. Valid: CSV_Cleaner, pdf-processing, release-notes, sql-style
OutputWhat it shows
Two csv-cleaner linesThe name breaks two rules (uppercase and underscore, and a mismatch with the folder). A lenient harness warns and still loads the skill, as the client guide recommends.
no-description lineWith no description there is nothing to match a task against, so the skill is skipped.
loaded lineFour of the five folders became skills.
tier 1 lineThe catalog the model sees at startup: one name and description per skill.
all bodies lineWhat loading every SKILL.md body at startup would put in the context.
one body activated lineThe message returned when the model activates pdf-processing: its body, the skill directory and a list of bundled files (here only scripts/run.py).
Last lineThe model asked for a skill that does not exist, so the harness returns an error that lists the valid names and the model can correct itself.

The arithmetic: at startup the model carries 774 characters, which is 774 / 13,667 = 5.7% of the 13,667 characters that eager loading would put in front of it. After one activation the total is 774 + 3,586 = 4,360 characters, or 31.9%. Dividing by roughly four characters per token (a rule of thumb; real tokenizers differ) gives about 190 tokens at startup and about 1,090 after the activation, against about 3,400 for eager loading. Real bodies run up to the 5,000 tokens that the specification recommends as a maximum, so the saving grows with the number and the size of the skills, as the plot above shows.

What the sketch leaves out: a real YAML parser (this one reads only single-line key: value pairs), a trust check for project skills, an allowlist so that reading the skill folder does not prompt the user, protection of the activated text from context compaction, de-duplication of repeated activations and the model call itself. The shape matches the client implementation guide: scan, parse, show the catalog, return the body on request. Wire catalog() into a system prompt and activate() into a tool whose name is limited to the loaded names.

Edge cases and limitations

The skill never loads because the description is vague or the task looks easy
The description is the only thing the model sees before it decides, and "Helps with PDFs" gives it nothing to match. The agentskills.io guide adds that agents typically consult a skill only for tasks beyond what they can do with basic tools, so a one-step request such as reading a PDF may not trigger even a well-matched skill. Measure the trigger rate on realistic prompts, including near-misses, and write the specialised cases the skill exists for into the description.
An unquoted colon in the description breaks strict YAML
A line such as `description: Use this skill when: the user asks about PDFs` is invalid YAML because of the second colon, and a strict parser rejects it. The client guide notes that skills written for other clients often contain such values and suggests a fallback that quotes them or converts them to block scalars before retrying. When you write a skill, avoid the colon-and-space sequence in the description, or quote the whole value.
Instructions can be dropped or cut after the context is compacted
Once a skill is active its text sits in the conversation like any other message, so a harness that summarises old messages can lose it. Claude Code re-attaches the most recent activation of each skill after a summary, but keeps only the first 5,000 tokens of each and shares a 25,000-token budget, so older skills can be dropped entirely. Put the rules that matter most near the top of the body, and re-invoke the skill if the agent seems to have forgotten it.
The same name in two places is resolved differently by each product
The client guide says existing implementations let project skills override user skills. Claude Code ranks enterprise above personal above project, and Codex lists both skills instead of merging them. A skill you believe is active may therefore be shadowed by another with the same name. Give skills distinctive names, and when behaviour looks wrong, check the product's documented precedence before you rewrite the instructions.
A skill that works in one product may fail or change in another
Only the name and description are guaranteed. The allowed-tools field is marked experimental and fields such as context fork belong to Claude Code. Environments differ as well: Anthropic's documentation says API skills run without network access or runtime package installation, while Claude Code skills have the user's own network access, and custom skills uploaded to claude.ai, the API and Claude Code do not sync. Record requirements in the compatibility field and test in every place you ship.
Descriptions are budgeted, so a large library dilutes the catalog
Each skill adds roughly 50 to 100 tokens to the catalog, which is small until there are hundreds. Claude Code truncates a skill's listing text at 1,536 characters. Codex caps its initial list at 2% of the model's context window (8,000 characters when the window size is unknown) and shortens descriptions first when the list is too long. Put the trigger conditions first, avoid near-duplicate skills with overlapping descriptions, and remove skills you no longer use.

When to use it, and when something simpler is enough

Use it when

  • A procedure or reference is needed for some tasks but not all, such as a release process, a house SQL style or a document-format recipe, and keeping it in the context all the time would waste tokens.
  • Several agent products should share the same know-how, or a framework or library wants to ship guidance that users' coding agents can load on demand.
  • A step is fragile and deterministic, so you want a tested script bundled with the instructions, run without its code entering the context.
  • Team knowledge lives in runbooks and people's heads and should become a reviewed, versioned folder that new agents and new colleagues both use.

Think twice when

  • The information is needed on every task, such as the project layout or the build command. Put it in an always-loaded instruction file.
  • The agent must reach a system or take an action it cannot take now. That needs a tool or an MCP server; a skill alone connects to nothing.
  • You cannot vet the skill's source or its scripts, or the agent runs with broad permissions and secrets. An untrusted skill is a route for harmful instructions and code.
  • The instruction is for a single conversation. Put it in the prompt instead of building and maintaining a folder.

A simpler alternative. Begin with a few lines in the project's instruction file (CLAUDE.md or AGENTS.md). Once a section turns into a procedure, grows long, or needs a script, move it into a skill. Claude Code's documentation gives the same rule: a section that has become a procedure rather than a fact belongs in a skill.

Key takeaways

  • A skill is a folder with a SKILL.md whose frontmatter needs only a name and a description; instructions, scripts, reference files and templates are optional additions.
  • Progressive disclosure keeps the context small, because only each skill's name and description load at startup, the body loads on activation, and bundled files load only when the instructions call for them.
  • The description is all the model sees before deciding, so it must say what the skill does and when to use it, and it should be tested with queries that should and should not trigger it.
  • Skills carry know-how, tools carry actions, MCP servers carry connections and instruction files carry facts needed on every task, and a skill often tells the agent which tools to use.
  • A skill is instructions plus code that the agent will follow, so install only trusted skills, read the bundled scripts, and check that your harness gates project skills and sandboxes execution.

Example 1 of 5

Claude API document skills that generate Excel, Word, PowerPoint and PDF files

AnthropicDocumented in official docs

Anthropic's platform documentation describes pre-built Agent Skills for PowerPoint, Excel, Word and PDF that a developer enables on a Messages API request together with the code execution tool. The Skills overview and the guide to using Skills with the API describe the setup, and Anthropic's public skills repository publishes the document skills as reference implementations. [9][11][13][19]

The problem

Producing a valid .xlsx, .docx, .pptx or PDF file takes detailed knowledge of each format and code that behaves the same way every time. A developer does not want to paste that knowledge into every request or maintain it, and the model has to hand back the finished file, not only text that describes one.

Where this topic fits

The skill is chosen by id in the request. Inside the code execution container, Claude reads the skill's instructions from the filesystem when a request matches its description, runs the bundled code through bash, and writes the result file, which the API reports back by file id.

How it is applied, step by step

  1. The developer sends a Messages API request that includes the code execution tool and lists a skill in the container parameter, for example type anthropic, skill id xlsx and version latest.
  2. At the start of the run only the skill's name and description occupy the context; the documentation puts this at about 100 tokens per skill.
  3. The user asks for an Excel budget spreadsheet. The request matches the skill's description, so Claude reads the skill's SKILL.md from the container with bash and the instructions enter the context.
  4. Following those instructions, Claude runs code in the container. The documentation says a bundled script's code is not loaded into the context and only its output is.
  5. The created file appears as a file id in the code execution result. The application fetches the file's metadata and content from the Files API and saves it.

Why this approach fits

Correct output depends on precise, rarely used format knowledge and on code that must run identically each time. A skill keeps both in one versioned unit that costs about 100 tokens until a request needs it. Anthropic's documentation also points out that running a prepared script is more efficient than having the model generate equivalent code on the fly, which is the case for file formats.

Limitation or tradeoff

The API container has no network access and no runtime package installation, so a skill cannot fetch what it needs. Custom skills do not sync between claude.ai, the API and Claude Code, the pre-built document skills are not available in Claude Code, and the documentation says Agent Skills are not covered by zero data retention arrangements.

What the sources document

  • The pre-built skills are referenced by the ids pptx, xlsx, docx and pdf in the container parameter, together with the code execution tool. A request may list up to 20 skills, and Anthropic's skills are versioned by date or latest. [9][11]
  • Files created by skills come back as file id values in the code execution result and are retrieved with the Files API metadata and content endpoints. [11]
  • Skills on the API run in a sandboxed container with no network access and no runtime package installation. [9]
  • The code execution tool is a server tool, meaning it runs on Anthropic's infrastructure rather than in the developer's application. [13]
  • Anthropic's skills repository includes the docx, pdf, pptx and xlsx skills as source-available (not open source) reference implementations used in a production application, while many other skills in the repository are open source under Apache 2.0. [19]

The facts above come from the cited sources. The steps and analysis in this example are our explanation of how they fit together.

Example 2 of 5

Claude Code skills that turn repeated repository procedures into on-demand commands

AnthropicDocumented in official docs

The Claude Code documentation on skills describes folders under .claude/skills/ for a project and ~/.claude/skills/ for a user, each with a SKILL.md that Claude uses automatically or that a developer invokes by name. The page includes a worked summarize-changes skill, saved there as a personal skill, that injects the output of git diff HEAD. [12]

The problem

Developers using a coding agent keep pasting the same checklists into chat ("summarize my uncommitted changes and flag risks"), while a project instruction file that carries them all is always in the context. Some procedures also need fresh data, such as the current diff, that the model should not have to fetch for itself.

Where this topic fits

The skill sits between the always-loaded project file and the tools. Its description is in the catalog from the start. Its body enters the conversation when Claude judges it relevant or the developer types the command. A shell command embedded in the body supplies fresh data before the model reads the text.

How it is applied, step by step

  1. A developer creates .claude/skills/summarize-changes/SKILL.md with a description saying what the skill does and when to use it.
  2. At the start of a session Claude Code loads each skill's description, not its body.
  3. The developer asks what changed, or types /summarize-changes. The description matches, or the command names the skill, so the body is loaded.
  4. Before the text reaches the model, Claude Code runs the embedded command git diff HEAD and replaces the placeholder with its output. The substitution happens once, and the output is not scanned again for placeholders.
  5. The rendered text enters the conversation as one message and stays there on later turns. The model follows the standing instructions: summarize in a few bullets and list the risks.
  6. If the context is later compacted, the most recent invocation of the skill is re-attached within the documented token budget.

Why this approach fits

The procedure is the same every time but the data changes, so injecting the diff gives the model exactly the current changes without a separate tool call, and its only job is judgement. Because the body loads only when used, a long checklist costs nothing until a developer needs it, which is the reason the documentation gives for moving procedural sections out of the always-loaded CLAUDE.md. Project skills live in the repository, so a team can review and version them like code.

Limitation or tradeoff

Once loaded, the rendered text stays in the context for the rest of the session and is re-attached after compaction only within the documented budget, so a long skill is a standing cost. The embedded command runs shell code: it is subject to permission checks, it can be switched off with the disableSkillShellExecution setting, and a command that fails (any non-zero exit code, with a narrow carve-out for exit code 1 from search and comparison commands) aborts the whole invocation, so Claude never sees the skill. By our test, git diff HEAD exits with code 129 outside a git repository, so the example skill would abort in such a folder.

What the sources document

  • Project skills live at .claude/skills/NAME/SKILL.md and personal skills at ~/.claude/skills/NAME/SKILL.md. At startup Claude Code loads skill descriptions, and the full content loads only when the skill is invoked. [12]
  • A placeholder written as an exclamation mark followed by a command in backticks is replaced by the command's output before the skill content reaches Claude. Substitution runs once over the original file, and the inserted output is not scanned again for placeholders. [12]
  • The rendered SKILL.md enters the conversation as one message and stays in context on later turns. After automatic compaction the most recent invocation of each skill is re-attached, keeping the first 5,000 tokens of each within a combined 25,000-token budget. [12]
  • Setting disable-model-invocation to true stops Claude from invoking a skill automatically while leaving the slash command available, and allowed-tools pre-approves listed tools for the turn the skill runs in. [12]
  • The page advises that when a section of CLAUDE.md has grown into a procedure rather than a fact, it should move to a skill, because a skill body loads only when used. [12]

4Common mistakes

  1. Writing a vague or first-person description such as "Helps with documents"

    Why it causes problems
    The description is the only text the model sees before it decides to load a skill. A line with no scope gives it nothing to match, so the skill never loads, or it loads on unrelated requests and crowds the context. Anthropic also notes that the description is injected into the system prompt, so phrasing such as "I can help you" can cause discovery problems.
    How to recognise it
    Run about twenty realistic prompts several times each and compute the trigger rate. Should-trigger prompts that fall below 0.5, or should-not-trigger prompts that rise above it, point at the description.
    How to fix it
    State what the skill does and when to use it, in third person, with the contexts and keywords a user would really mention, including cases where they do not name the domain. Keep it under 1,024 characters and re-run the trigger tests after every change.

  2. Putting everything in one long SKILL.md, or chaining references several levels deep

    Why it causes problems
    Every token of an activated body competes with the conversation and with other skills for attention. Anthropic also reports that when a referenced file points to further files, Claude may preview them with commands such as head, so it reads only part of what it needed.
    How to recognise it
    SKILL.md runs past 500 lines or 5,000 tokens, or the trace shows partial reads of nested reference files or the same file being read again and again.
    How to fix it
    Keep SKILL.md to the core procedure and move detail into files one level deep, such as references/. Tell the agent when to read each one, for example "Read references/api-errors.md if the API returns a non-200 status code". Give any file longer than 100 lines a table of contents.

  3. Filling a skill with general advice the model already knows

    Why it causes problems
    Generic lines such as "handle errors appropriately" cost tokens on every activation and add little. The agentskills.io guide warns that overly comprehensive skills can hurt more than they help, because the agent struggles to pick out what is relevant and may follow instructions that do not apply to the task.
    How to recognise it
    For each paragraph ask whether the agent would get this wrong without it. Run the same tasks without the skill; if the results are as good, the skill is adding cost and no value.
    How to fix it
    Write from real tasks. Capture the corrections you made, the project conventions and the non-obvious edge cases, and put the sharpest ones in a gotchas section. Cut explanations of well-known concepts and name one default approach instead of a menu of options.

  4. Installing a third-party skill without reading its scripts and instructions

    Why it causes problems
    A skill is instructions plus code that the agent runs with your permissions. Anthropic warns that a malicious skill can direct the agent to use tools or run code in ways that do not match its stated purpose, which could lead to data exfiltration or unauthorised access, and that skills which fetch external content are a particular risk.
    How to recognise it
    Scripts that make unexpected network calls or touch files unrelated to the task, instructions that send the agent to fetch URLs, or a skill whose behaviour does not match its description.
    How to fix it
    Install only from sources you trust, read every bundled file before use, copy or pin a version instead of following remote updates, and run the agent in a sandbox. In a harness you build, gate project-level skills on a trust check.

  5. Bundling scripts that prompt for input or print unbounded output

    Why it causes problems
    Agents run in non-interactive shells, so a script that waits at a prompt hangs. Many harnesses also truncate tool output beyond a threshold, which the agentskills.io guide puts at around 10 to 30 thousand characters, and the truncated part may be the one the agent needed.
    How to recognise it
    The agent stalls on a script, retries it, or acts on an error message that only says "invalid input". Truncation markers appear in the trace.
    How to fix it
    Accept all input through flags, environment variables or standard input. Document usage in --help, make errors say what to try next, send structured data to stdout and diagnostics to stderr, and default to a summary with an option to page through the rest.

Requirements

  • Report ERROR when the name breaks the naming rules: 1 to 64 characters, only lowercase letters, digits and single hyphens, and no leading or trailing hyphen.
  • Report ERROR when the name differs from the name of the skill's folder.
  • Report ERROR when the description has fewer than 1 or more than 1,024 characters.
  • Report WARN, not ERROR, when SKILL.md has more than 500 lines, because the limit is a recommendation.
  • Report ERROR for every path in the body that starts with references/, scripts/ or assets/ and does not exist inside the skill folder. A trailing full stop is not part of the path.
  • Print findings as LEVEL folder: message, sorted by folder name, then one summary line. Exit with status 1 if there is at least one ERROR.

A reference solution follows. The name rule and the folder-match rule are separate checks, so Bad_Name in the folder bad-name earns two errors. A set comprehension removes duplicate paths, and sorting keeps the output stable.

python
"""skill_lint.py - check skill folders against the Agent Skills rules. Standard library only."""
import re
import sys
from pathlib import Path

NAME_OK = re.compile(r"^[a-z0-9]+(-[a-z0-9]+)*$")
REFERENCE = re.compile(r"\b((?:references|scripts|assets)/[\w./-]+)")
MAX_NAME, MAX_DESCRIPTION, MAX_LINES = 64, 1024, 500


def split_frontmatter(text):
    if not text.startswith("---\n"):
        return None, text
    head, _, body = text[4:].partition("\n---\n")
    fields = dict(line.split(": ", 1) for line in head.splitlines() if ": " in line)
    return fields, body


def lint_skill(folder):
    """Return a list of (level, message) findings for one skill folder."""
    text = (folder / "SKILL.md").read_text()
    fields, body = split_frontmatter(text)
    if fields is None:
        return [("ERROR", "no frontmatter")]
    name, description = fields.get("name", ""), fields.get("description", "")
    findings = []
    if not NAME_OK.match(name) or len(name) > MAX_NAME:
        findings.append(("ERROR", f"name {name!r} breaks the naming rules"))
    if name != folder.name:
        findings.append(("ERROR", f"name {name!r} does not match folder"))
    if not 1 <= len(description) <= MAX_DESCRIPTION:
        findings.append(("ERROR", f"description has {len(description)} characters (allowed 1 to {MAX_DESCRIPTION})"))
    line_count = len(text.splitlines())
    if line_count > MAX_LINES:
        findings.append(("WARN", f"SKILL.md has {line_count} lines (recommended maximum {MAX_LINES})"))
    for reference in sorted({r.rstrip(".") for r in REFERENCE.findall(body)}):
        if not (folder / reference).exists():
            findings.append(("ERROR", f"{reference} is referenced but does not exist"))
    return findings


def main(root):
    folders = sorted(p.parent for p in Path(root).glob("*/SKILL.md"))
    errors = warnings = 0
    for folder in folders:
        for level, message in lint_skill(folder):
            print(f"{level} {folder.name}: {message}")
            errors += level == "ERROR"
            warnings += level == "WARN"
    print(f"{len(folders)} skills checked, errors={errors}, warnings={warnings}")
    return 1 if errors else 0


if __name__ == "__main__":
    sys.exit(main(sys.argv[1]))

Running python3 skill_lint.py lint-fixtures prints the six lines shown under the expected behaviour. The 605 in the warning is the 5 header lines plus the 600 body lines that the fixture writes.

This linter checks only what a script can check. It cannot tell whether a description will make the model load the skill, which is why the second exercise adds trigger tests. The name pattern here is ASCII-only for simplicity, while the specification also allows other lowercase Unicode letters.

Turn a release runbook into a skill and write its trigger tests

DesignIntermediateAbout 45 min (estimate)Hypothetical scenario

The release runbook below is invented for this exercise. It lives on a wiki page that the team's coding agent never sees.

  1. Freeze main: post in #eng-release. No merges after 14:00.
  2. Run make verify. It must exit with code 0.
  3. Tag with git tag vX.Y.Z. The tag must match the top heading of CHANGELOG.md.
  4. Deploy to staging and wait for the smoke test (about 6 minutes).
  5. Promote to production. Allowed Tuesday to Thursday, 10:00 to 16:00 UTC only.
  6. If the error rate stays above 2% for 10 minutes after promotion, roll back. The rollback has 12 steps of its own.

Package the runbook as a skill folder named release-checklist, then write trigger tests for its description. A text editor is enough. If you have an agent that supports skills you may also run the tests, but that is optional.

Requirements

  • SKILL.md has valid frontmatter: the name equals the folder name, and the description is under 1,024 characters, says what the skill does and when to use it, and contains no colon followed by a space.
  • The main steps stay in SKILL.md, which is shorter than 60 lines. The rollback moves to references/ROLLBACK.md, and SKILL.md says exactly when to read it.
  • A Gotchas section holds the two traps from the runbook.
  • eval_queries.json holds 20 realistic queries, each with a should_trigger field: 10 that should trigger and 10 near-misses that should not.
  • Split the queries into a training file of 12 and a validation file of 8, with the same balance of positives and negatives in each.

A folder release-checklist/ with SKILL.md and references/ROLLBACK.md that passes the linter from the first exercise with no findings, and two query files whose labels are balanced: 6 positives and 6 negatives in training, 4 and 4 in validation. If you run the queries through an agent three times each, a query passes when its trigger rate is above 0.5 for a positive and below 0.5 for a negative. Use the training failures to improve the description and the validation result to check that the improvement generalises.

Hint 1

Describe what the user is trying to do, not what the folder contains, and say when to use it with a phrase like "Use when the user wants to...".

Hint 2

Near-misses share words with the skill but need something different: a changelog entry, a local git rollback, a chat message in the release channel.

Put the rule that is easiest to forget, the weekday window, in Gotchas, where the agent reads it before the promotion step.

Show solution

One possible SKILL.md. It passes the linter from the first exercise and parses as strict YAML, because the description avoids a colon followed by a space.

markdown
---
name: release-checklist
description: Walk through the team's production release procedure (freeze, verify, tag, stage, promote) and its rollback. Use when the user wants to cut, tag, deploy, ship or roll back a release, even if they do not say "release checklist".
---

# Release checklist

Work through the steps in order. Report each step as done before starting the next.

1. Freeze main: post in #eng-release. No merges after 14:00.
2. Run `make verify`. Continue only if it exits with code 0.
3. Tag the release with `git tag vX.Y.Z`. The tag must match the top heading of CHANGELOG.md.
4. Deploy to staging and wait for the smoke test, which takes about 6 minutes.
5. Promote to production.

## Gotchas

- Production promotions are allowed Tuesday to Thursday, 10:00 to 16:00 UTC only. If the request falls outside that window, stop and say so instead of continuing.
- `make verify` can pass while CHANGELOG.md is stale. Check the heading yourself in step 3.

## If something goes wrong

If the error rate stays above 2% for 10 minutes after promotion, read references/ROLLBACK.md and follow it. Do not read that file otherwise.

references/ROLLBACK.md holds the twelve rollback steps and loads only when the error rate threshold is crossed.

One possible set of queries, with T for should-trigger and N for should-not-trigger. Training: T "ok we're good to cut v3.4.0, can you walk me through shipping it to prod?"; T "tag the release and push it to staging"; T "ship the hotfix branch"; T "can you tag v2.9.0 off main and kick off the staging deploy?"; T "do the release thing for the mobile backend"; T "error rate is 4% since I promoted ten minutes ago, what now?"; N "write a changelog entry for the dark mode feature"; N "git tag --list shows 200 tags, how do I delete the old ones locally?"; N "explain what a smoke test is"; N "draft a slack message announcing new office hours in #eng-release"; N "set up a staging environment for the data team in terraform"; N "review this pull request for security issues".

The query about the 4% error rate is the likeliest early failure. A description that only mentions shipping gives the model no reason to connect an error rate with the skill. The fix is to name the general category, rolling a release back, as the description above does, and not to copy words from that one query. The local-branch rollback query in the validation set checks that the fix did not make the description too broad. The Friday query should still trigger the skill: the gotcha then tells the agent to stop, which is the correct behaviour.

  • Is the rollback in a separate file, with a sentence in SKILL.md that says when to read it?
