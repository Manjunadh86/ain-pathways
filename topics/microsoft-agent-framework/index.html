Microsoft Agent Framework

Microsoft Agent Framework is Microsoft's open-source SDK for building AI agents and multi-agent workflows in Python and .NET. It is the successor to Semantic Kernel and AutoGen, and it pairs a single agent abstraction (a model connection, instructions, tools and a session) with graph-based workflows that route typed messages between steps.

1Overview

Why it matters

If you build agents in a .NET or Python codebase that already lives on Azure, this is the framework Microsoft now points new agent projects to, and its hosting options (Foundry hosted agents, the Durable Task extension) have first-party integrations for it. It also settles the future of two older projects. AutoGen's repository says it is in maintenance mode and sends new users here, and Semantic Kernel's agent features have a published migration path to it. Anyone maintaining code written with either one will meet Agent Framework at the next upgrade.

The concepts in this lesson are the ones behind real defects. An agent called twice without a session answers the second question as if the first was never asked. A workflow object reused across web requests carries one customer's conversation into the next. A fan-out that looks parallel waits on its slowest branch because of how the workflow engine schedules steps. Telemetry with one extra flag set starts writing prompts and tool results into your trace store. Knowing how runs, sessions, supersteps, middleware and spans fit together lets you read a trace and tell which of these happened.

What you will be able to do

  • Create an agent in Python or .NET and describe what happens between calling run and getting a response.
  • Use an AgentSession to carry a conversation across runs, and choose between local and service-managed history.
  • Build a graph workflow from executors and edges, and trace a run round by round using the superstep rule.
  • Place agent, function and chat middleware at the right layer and predict the order in which they run.
  • Turn on OpenTelemetry output and name the spans and metrics that an agent run produces.
  • Map AutoGen and Semantic Kernel concepts to their Agent Framework replacements.

Key terms

Agent
An object that puts a model connection, instructions and tools behind a single run method. The type is Agent in Python and AIAgent in .NET.
Chat client
The component that talks to one model provider. An agent is built around a chat client, so switching provider means switching the client and leaving the agent code alone.
Session (AgentSession)
The conversation state container that you pass to each run of the same conversation. Older material and some current pages call it a thread.
Context provider
A component that runs around the model call. Before it, it loads chat history or adds extra context such as memories or retrieved documents. After the run, it stores the new messages.
Middleware
Code that wraps an agent run, a tool call or a model call so that it can inspect, change or block what passes through.
Workflow
A directed graph of executors connected by edges, run by an engine that delivers messages from one executor to the next.
Executor
One node of a workflow. It receives a typed message, does some work, and either sends messages onward or yields output to the caller.
Edge
A connection that carries messages from one executor to another, optionally only when a condition on the message is true.
Superstep
One round of workflow execution. Every executor with a pending message runs, and the engine waits for all of them to finish before it starts the next round.
Checkpoint
A saved snapshot of a workflow (executor state, pending messages, pending requests and shared state) taken at the end of a superstep so that the run can be resumed later.

2Explanation

Introduction

In Choosing an Agent Framework you saw that a framework packages the parts you would otherwise write by hand: the agent loop, tool schemas, conversation history and hooks for logging. Microsoft Agent Framework is Microsoft's package of those parts. It is open source, has consistent APIs for Python and .NET, reached version 1.0 (opens in a new tab) on 3 April 2026, and has a Go SDK in public preview.

It offers two ways to get work done, and much of the skill is in choosing between them. Picture a parcel depot. You could hire one experienced courier, hand over a parcel and say "get this to the right place". The courier decides every step. That is an agent: a model that reads the request, picks tools and keeps going until it has an answer. Or you could build a sorting floor with stations that each do one job, conveyor belts between them, and gates on the belts that read the label and send each parcel left or right. That is a workflow: you fix the route in code, and an engine moves typed messages from station to station. The framework lets you put a courier at any station, so one step of a fixed process can still be an agent.

The overview (opens in a new tab) gives a short rule for choosing. Use an agent when the task is open-ended or conversational. Use a workflow when the process has well-defined steps or when several agents and functions must coordinate. And if you can write a plain function to handle the task, do that instead of using an agent. The overview also lists a Harness Agent, an opinionated agent for long, multi-step tasks with planning, todo tracking, context compaction, file access and tool approval built in, and functional workflows next to the graph workflows. This lesson stays with the core agent and graph workflows.

Where it came from

Agent Framework is the direct successor to two Microsoft projects and is built by the same teams. From AutoGen it takes simple abstractions for single agents and for multi-agent patterns. From Semantic Kernel it takes the enterprise features: session-based state, type safety, filters (hooks for intercepting calls, a role that middleware plays in Agent Framework), telemetry and broad model support. Graph-based workflows with checkpoints are the main addition. AutoGen's repository (opens in a new tab) now says the project is in maintenance mode and points new users here; Microsoft AutoGen covers that side of the story.

Names have moved since the 2025 preview, so treat older tutorials with care. The conversation object is now AgentSession, although several documentation pages still say "thread". The launch post (opens in a new tab) mentions an @ai_function decorator and a ChatMessage type, where current Python documentation uses @tool and Message. This lesson follows the documentation as it stood in October 2026 and the Python package agent-framework 1.21.0 (opens in a new tab). It covers agents, sessions, workflows, middleware and telemetry, in that order.

How it works

An agent is a pipeline around a chat client

An agent puts a model connection, instructions and tools behind one run method. In Python:

python
from agent_framework import Agent, tool
from agent_framework.openai import OpenAIChatClient

@tool
def get_weather(location: str) -> str:
    """Get the weather for a location."""
    return f"The weather in {location} is sunny."

agent = Agent(
    client=OpenAIChatClient(model="gpt-5"),   # the API key comes from the environment
    name="WeatherAgent",
    instructions="You are a weather assistant.",
    tools=[get_weather],
)
result = await agent.run("What is the weather in Amsterdam?")
print(result.text)

The .NET version has the same parts under different names. Any IChatClient from Microsoft.Extensions.AI can back an agent:

csharp
AIAgent agent = new ChatClientAgent(
    chatClient,
    name: "WeatherAgent",
    instructions: "You are a weather assistant.",
    tools: [AIFunctionFactory.Create(GetWeather)]);

Console.WriteLine(await agent.RunAsync("What is the weather in Amsterdam?"));

Between your call and the model, the request passes through layers. The two languages organise them differently, but the order of events is the same.

Two defaults matter. First, the tool loop is on: Agent keeps calling tools and asking the model again until it can return a final answer, whereas AutoGen's AssistantAgent stopped after one round unless you raised max_tool_iterations. Second, the agent is stateless: two calls to run share nothing unless you pass a session.

Sessions carry the conversation

AgentSession is the state container for one conversation. The agent creates it, and you pass it to every run that belongs to that conversation:

python
session = agent.create_session()
await agent.run("My name is Alice.", session=session)
reply = await agent.run("What is my name?", session=session)   # the model now sees both turns

saved = session.to_dict()                 # store this yourself
session = AgentSession.from_dict(saved)   # later, possibly in another process

In .NET the same steps are CreateSessionAsync(), RunAsync(text, session), SerializeSession(session) and DeserializeSessionAsync(...). A Python session has a session_id, a state dictionary shared with providers, and a service_session_id that is set when the model service keeps the history. That last field reflects two storage modes:

ModeWhere the history livesWhat the session holds
Local session stateIn the session, managed by a history provider such as InMemoryHistoryProviderThe messages themselves
Service-managedIn the provider's service, for example an OpenAI Responses conversationAn ID that points to it

Persist the whole session object, not only the message text, and restore it with the same agent and provider configuration. When one API key serves many end users, a service-side ID is not an access check: keep it on the server and verify that the caller owns the conversation before you resume it. Memory that outlives one conversation is the job of context providers; see Agent Memory.

Workflows: executors, edges and supersteps

A workflow is a directed graph. Its nodes are executors and its connections are edges.

  • An executor receives a typed message and either forwards a message with ctx.send_message(...) or returns a result to the caller with ctx.yield_output(...). In Python it is a function decorated with @executor or a class with @handler methods. In .NET it is a partial class that derives from Executor and marks its methods with [MessageHandler], or a subclass of Executor<TInput> that overrides HandleAsync. An agent can be used wherever an executor is expected.
  • An edge routes messages. The kinds are direct (always), conditional (a predicate on the message), switch-case (the first matching case, with a default), fan-out (one source, several targets) and fan-in (several sources, one target).
python
workflow = (
    WorkflowBuilder(start_executor=classify)
    .add_edge(classify, refund_desk, condition=lambda t: t.category == "refund")
    .add_edge(classify, general_desk, condition=lambda t: t.category != "refund")
    .build()
)

The .NET builder reads the same way, and AddEdge also accepts a condition: argument:

csharp
WorkflowBuilder builder = new(processor);   // the start executor
builder.AddEdge(processor, validator);
builder.AddEdge(validator, formatter);
var workflow = builder.Build();

Run result = await InProcessExecution.RunAsync(workflow, inputMessage);

Building validates the graph. Message types must be compatible across each edge, every executor must be reachable from the start, and duplicate edges are rejected.

Execution follows a Pregel-style model made of supersteps. Each superstep (1) collects the messages produced by the previous one, (2) routes them along edges, (3) runs every target executor concurrently, (4) waits for all of them to finish, and (5) queues the messages they emitted for the next superstep. The run ends when nothing is pending. Step 4 is a synchronization barrier, and it has a visible cost. Suppose a start node fans out to a slow executor B (1.0 s) and to a fast chain, A1 then A2 (0.2 s each), and a join waits for both branches. A2 cannot start until B finishes, because B shares a superstep with A1:

The documented remedy is to merge the sequential steps of a branch into one executor. In return for the barrier you get a deterministic order and clean places to save state. A checkpoint is created at the end of each superstep and captures executor state, pending messages, pending requests and shared state. Python provides InMemoryCheckpointStorage, FileCheckpointStorage and CosmosCheckpointStorage (Cosmos DB in the optional agent-framework-azure-cosmos package). You pass one to WorkflowBuilder(checkpoint_storage=...) and resume with workflow.run(checkpoint_id=...). In .NET you pass a CheckpointManager when you start the run.

Executors share data by sending messages or through workflow state (ctx.set_state and ctx.get_state in Python, QueueStateUpdateAsync and ReadStateAsync with a scope name in .NET). A workflow can also pause for outside input. A Python executor calls ctx.request_info(...), the caller sees a request_info event, and the run continues when the response is sent back; in .NET the same mechanism is a RequestPort. That is how human-in-the-loop approval is built. The multi-agent patterns that came from AutoGen (sequential, concurrent, handoff, group chat and Magentic) are prebuilt workflows produced by builders such as SequentialBuilder.

Middleware: three places to intercept

Middleware wraps an operation with your code. There are three kinds, and they differ in how often they run:

Kind (Python name / .NET name)WrapsRunsTypical use
Agent middleware / agent run middlewareThe whole runOnce per runInput checks, blocking, rewriting the result
Function middleware / function calling middlewareOne tool callOnce per tool callArgument validation, timing, audit
Chat middleware / IChatClient middlewareOne request to the modelOnce per model call, so several times in a tool loopLogging raw messages, redaction
python
from collections.abc import Awaitable, Callable
from agent_framework import FunctionInvocationContext

async def block_secrets(
    context: FunctionInvocationContext,
    call_next: Callable[[], Awaitable[None]],
) -> None:
    if "password" in str(context.arguments):
        context.result = "Blocked by policy."   # the model receives this instead
        return                      # skip the tool: call_next is never awaited
    await call_next()

agent = Agent(client=client, tools=[get_weather], middleware=[block_secrets])

Each middleware awaits call_next() to continue the chain. Middleware given to the agent wraps middleware given to one run(..., middleware=[...]) call. With agent-level [A1, A2] and run-level [R1, R2] the order is A1, A2, R1, R2, the agent, then back out through R2, R1, A2, A1. To stop early in Python and return your own answer, set context.result and raise MiddlewareTermination. In .NET you attach middleware with a builder: agent.AsBuilder().Use(...).Build().

Telemetry: OpenTelemetry-native

Agents emit traces, logs and metrics that follow the OpenTelemetry GenAI semantic conventions, so any OpenTelemetry backend can receive them. Python installs no exporters, so add the package for your backend, for example opentelemetry-exporter-otlp-proto-grpc. One call then sets up the providers:

python
from agent_framework.observability import configure_otel_providers

configure_otel_providers()   # reads the standard OTEL_EXPORTER_OTLP_* variables

A run then produces a tree of spans:

  • invoke_agent <agent_name> covers the whole run and is the parent of the others.
  • chat <model_name> appears once per model call.
  • execute_tool <function_name> appears once per tool call.

The metrics are gen_ai.client.operation.duration and gen_ai.client.token.usage for model calls, and agent_framework.function.invocation.duration for tools. Prompts, responses, tool arguments and tool results are left out unless you opt in (ENABLE_SENSITIVE_DATA=true in Python, EnableSensitiveData in .NET), and the documentation says to do that only in development or test. In .NET you add .UseOpenTelemetry(sourceName: ...) to the chat client or agent builder and register the same source name with your tracer provider. For a local viewer the documentation suggests the Aspire Dashboard in Docker. LLM and Agent Observability explains how to read traces like these.

Worked example: A ticket-triage workflow you can run without a model

This example builds the smallest useful graph: classify a support ticket, then route it to one of two desks. The classifier is a keyword rule, so nothing calls a model and the output is the same on every run. The code follows the pattern of the repository's first workflow sample, step1_executors_and_edges.py (opens in a new tab), which also needs no external services.

Setup. Use Python 3.10 or later and run pip install agent-framework. Save the following as triage.py.

python
import asyncio
from dataclasses import dataclass

from agent_framework import Workflow, WorkflowBuilder, WorkflowContext, executor
from typing_extensions import Never


@dataclass
class Ticket:
    text: str
    category: str   # "refund" or "general"
    priority: str   # "high" or "normal"


@executor(id="classify")
async def classify(text: str, ctx: WorkflowContext[Ticket]) -> None:
    lowered = text.lower()
    is_refund = "refund" in lowered or "charged twice" in lowered
    await ctx.send_message(
        Ticket(
            text=text,
            category="refund" if is_refund else "general",
            priority="high" if "urgent" in lowered else "normal",
        )
    )


@executor(id="refund_desk")
async def refund_desk(ticket: Ticket, ctx: WorkflowContext[Never, str]) -> None:
    await ctx.yield_output(f"REFUND DESK ({ticket.priority}): {ticket.text}")


@executor(id="general_desk")
async def general_desk(ticket: Ticket, ctx: WorkflowContext[Never, str]) -> None:
    await ctx.yield_output(f"GENERAL DESK ({ticket.priority}): {ticket.text}")


def create_workflow() -> Workflow:
    return (
        WorkflowBuilder(start_executor=classify)
        .add_edge(classify, refund_desk, condition=lambda t: t.category == "refund")
        .add_edge(classify, general_desk, condition=lambda t: t.category != "refund")
        .build()
    )


async def main() -> None:
    tickets = [
        "URGENT: I was charged twice for order 1182",
        "How do I export my invoices?",
    ]
    for text in tickets:
        result = await create_workflow().run(text)
        print(result.get_outputs())


if __name__ == "__main__":
    asyncio.run(main())

Reading the types. The second parameter of each executor declares what it may emit. WorkflowContext[Ticket] says that classify sends Ticket messages to the next executors. WorkflowContext[Never, str] says that a desk sends nothing onward and yields a str to the caller. The builder uses these declarations when it validates the graph.

Expected output.

text
['REFUND DESK (high): URGENT: I was charged twice for order 1182']
['GENERAL DESK (normal): How do I export my invoices?']

Trace of the first ticket. Applying the superstep rule by hand gives two rounds of work. The run then finds no pending messages and ends:

RoundMessages deliveredExecutors that runWhat they emit
1The input string, to classifyclassifyOne Ticket with category refund and priority high
2The Ticket. The refund edge's condition is true and the general edge's is falserefund_deskOne workflow output, a string

After round 2 nothing is pending, so the workflow goes idle and run returns. The text is lowercased first, so "URGENT" sets the priority to high, and "charged twice" selects the refund category. In the second ticket neither phrase appears, so round 2 runs general_desk with priority normal. The engine's own superstep counter may number the rounds differently from this table: the checkpoint documentation notes that Python 1.13.0 changed iteration counts when it added an entry checkpoint. Do not write code that depends on a particular iteration number.

What to notice.

  • create_workflow() builds a new workflow for each ticket. The documentation recommends a factory like this because executor instances, and the conversations of any agents in the graph, otherwise persist across runs of the same workflow object. The three executors here are stateless functions, so sharing them is safe. Anything that holds state should be created inside the factory.
  • Routing is ordinary code. Replacing classify with an agent that returns the category as structured output changes one node and leaves the rest of the graph in place. The documentation's conditional-edge tutorial does this with a spam-detection agent.
  • To make the run resumable, pass checkpoint_storage=InMemoryCheckpointStorage() to WorkflowBuilder. With file or Cosmos DB storage, an application type such as Ticket must be listed in allowed_checkpoint_types, because non-JSON values are restored through a restricted unpickler.

Edge cases and limitations

An agent without a session has no memory
Agent is stateless between runs. If you call run twice and pass no session, the second call sends only the new message, so a follow-up such as "and in Paris?" has nothing to refer to. Create one session per conversation with create_session and pass it to every run. To continue after a restart, serialize the session or keep the service-side conversation ID in your own storage.
A fan-out moves at the pace of its slowest executor in each superstep
All executors triggered in a superstep run concurrently, but the next superstep starts only when every one of them has finished. A branch made of several quick executors therefore waits for a slow sibling branch at each hop. If branches must progress independently, the documentation says to combine the sequential steps of a branch into a single executor so that both branches fit in one superstep.
State survives across runs of the same workflow object
A built workflow is immutable, but its executor instances keep their attributes, and agents inside it keep their conversation across runs. Reusing one workflow object for unrelated tasks can carry content from one task into the next. Build executors, agents and the workflow inside a helper function and call it once per task or request. In .NET, a stateful executor that is shared on purpose must implement IResettableExecutor.
Checkpoints are pickled, and restoring them is restricted
The file, Cosmos DB and Foundry checkpoint stores in Python use pickle for values that are not plain JSON, behind a restricted unpickler that accepts only a built-in set of safe types plus the ones you list in allowed_checkpoint_types. An unlisted application type fails with WorkflowCheckpointException. The documentation calls checkpoint storage a trust boundary: never load checkpoints from a source that someone else could have written to.
A resumed workflow must have the same shape as the one that was saved
When you rehydrate a checkpoint into a new workflow instance, the topology and the executor identities have to match the workflow that created it. In .NET an agent's executor identity is derived from its Id and, when set, its Name, so agents rebuilt with different or randomly generated IDs cannot resume. Give every agent a stable ID named after its role, and never use request, user or conversation IDs for this.
Chat middleware runs once per model call, not once per request
Chat middleware sits inside the function invocation loop. A run in which the model asks for tools twice before answering makes three model calls, so chat middleware fires three times, including for the calls that carry tool results back to the model. Put once-per-request logic in agent middleware and per-tool logic in function middleware.

When to use it, and when something simpler is enough

Use it when

  • Your application is written in .NET or Python and you want agents that follow Microsoft's supported path, including hosting on Microsoft Foundry or Azure Functions.
  • You maintain AutoGen or Semantic Kernel agent code and need a successor that has published migration guides for both.
  • The process has fixed steps, branches or approvals that must be explicit, checkpointed and resumable, and some of those steps are agents.
  • You need telemetry in OpenTelemetry format so that the same traces can go to Azure Monitor, a local Aspire Dashboard or a third-party backend.

Think twice when

  • A plain function or a single model call does the job. The documentation itself says to write the function instead of using an agent.
  • Your team works in a language other than Python or .NET. The Go SDK is in public preview and lacks several features, including declarative agents and functional workflows.
  • Parallel branches must make progress completely independently of each other. Supersteps make every active executor wait at each barrier unless you merge a branch into one executor.

A simpler alternative. For one conversational assistant with a few tools, a hand-written loop around your provider's chat API is a few dozen lines and leaves no framework to upgrade. It stops being enough when you need the same agent to run against several providers, conversation state that survives restarts, interception points for policy, standard telemetry, or a multi-step process with checkpoints. Inside the framework, the simpler choice is a single agent with tools; add a workflow only when the steps must be fixed in code.

Key takeaways

  • Microsoft Agent Framework succeeds AutoGen and Semantic Kernel for Python and .NET: it keeps AutoGen's simple agent and multi-agent abstractions and Semantic Kernel's sessions, middleware and telemetry, and it adds graph workflows.
  • An agent wraps a chat client with instructions and tools, runs the tool loop by default, and remembers nothing between runs unless you pass the same AgentSession.
  • A workflow is a graph of executors joined by edges that carry typed messages, and it runs in supersteps in which every active executor must finish before the next round begins.
  • Checkpoints are taken at superstep boundaries, which makes workflows resumable and lets them pause for human input, but a resumed workflow must have the same structure and executor identities.
  • Middleware exists at three layers (agent run, tool call and model call), and telemetry follows OpenTelemetry conventions with prompts and tool data left out unless you opt in.
  • Prefer a plain function, then a single agent, and use a workflow only when the steps must be explicit; build a fresh workflow for each request so that state does not leak.

Example 1 of 5

KPMG Clara AI: an audit platform built on Semantic Kernel and aligned with Agent Framework

KPMGDocumented in a case study

Microsoft's customer story "KPMG is redefining the audit with agentic AI using Azure" (1 October 2025) describes KPMG Clara AI, the agentic AI part of the Clara audit platform that KPMG member firms use. Microsoft's launch post for Agent Framework, published the same day, lists KPMG among its early customers. [25][24][14]

The problem

The story describes audits that relied on sampling small portions of data and on manual documentation, methods that it says cannot keep pace with today's financial complexity. KPMG wanted agents to automate audit procedures for auditors in many jurisdictions, in an industry where governance and observability are conditions of use. The agent layer had been built on Semantic Kernel, which now has a successor.

Where this topic fits

Agent Framework sits where Semantic Kernel sits today: the orchestration layer between the application (a .NET 8 service on Azure App Service) and the model, search and data services beneath it. The story presents it as the runtime the platform is aligned with, and Foundry Agent Service as planned for the next version. This is the inheritance path from the introduction of this lesson, seen in one production system.

How it is applied, step by step

  1. The platform runs as .NET applications on Azure App Service, and Azure Cosmos DB holds chat history, session data and agent memory. Conversation state is therefore already kept outside the agent process.
  2. Agents are grounded in enterprise data through retrieval with Azure AI Search and use models from Azure OpenAI and Cohere, so the agent layer works against more than one model provider.
  3. The agentic capabilities are built on Semantic Kernel, which the story calls the predecessor of Microsoft Agent Framework. The story says the platform is tightly aligned with the new framework.
  4. As an illustration of the inheritance path, the migration guide's mapping for a .NET codebase of this kind is as follows. A Kernel-bound ChatCompletionAgent becomes an AIAgent created from a chat client, plugin classes become ordinary functions, and threads the caller constructed become sessions that the agent creates. The sources do not say that KPMG has made this change.
  5. Session data that lives in a database maps onto the session model in a typical migration: either the serialized AgentSession is stored per conversation, or a custom chat history provider reads and writes the messages. The story does not say which approach KPMG uses.
  6. Multi-step audit procedures that several agents share are the kind of work the workflow engine targets, with checkpoints for long runs and OpenTelemetry traces for review.

Why this approach fits

A team with a production Semantic Kernel system does not want to rewrite its agents for an unrelated framework. Agent Framework comes from the same teams and keeps the ideas such a system already depends on (agents, tools, conversation state, interception and telemetry) under new names, with the Kernel removed. For a regulated audit product the telemetry and middleware layers matter as much as the agent itself, because they are where review and policy controls attach.

Limitation or tradeoff

Apart from one executive quote, the sources describe alignment and plans, not a finished migration, and they give no result that can be attributed to Agent Framework itself. The customer story and the launch post are both Microsoft publications written to promote the platform. A migration is also real work: namespaces, agent construction, tool registration and thread handling all change, and the invocation API returns a single response object where Semantic Kernel returned a stream of items.

What the sources document

  • The customer story states that, for its agentic capabilities, KPMG Clara AI is built on Semantic Kernel, which it describes as the predecessor of the Microsoft Agent Framework. [25]
  • The story says KPMG Clara AI is tightly aligned with Microsoft Agent Framework, which it describes as built on the convergence of Semantic Kernel and AutoGen, and that Azure AI Foundry Agent Service is planned for adoption in the next version. [25]
  • According to the story, KPMG Clara AI runs on .NET 8 and Azure App Service, and Azure Cosmos DB manages chat history, session data and agent memory. [25]
  • Microsoft's launch post lists KPMG under customer momentum, says KPMG is building Clara AI, a multi-agent system that automates audit testing and documentation, and quotes KPMG's Sebastian Stöckle saying that Foundry Agent Service and Microsoft Agent Framework connect KPMG's agents to data and to each other. [24]
  • The migration guide states that every Semantic Kernel agent depends on a Kernel instance and that the caller has to know the thread type and create it manually, whereas in Agent Framework agents are created from provider clients and the agent is responsible for creating the session. [14]

The facts above come from the cited sources. The steps and analysis in this example are our explanation of how they fit together.

Example 2 of 5

BMW: a multi-agent assistant for test-fleet telemetry

BMWDocumented in a case study

Microsoft's customer story "BMW accelerates test-fleet data analysis twelvefold with multi-agentic AI in Azure" (18 November 2025) describes BMW's MDR Copilot, a multi-agent system that runs on Foundry Agent Service and works through Microsoft Agent Framework. Two other Microsoft posts mention the same system: the Agent Framework launch post (1 October 2025) and "Foundry Agent Service at Ignite 2025" (18 November 2025). [26][24][27]

The problem

AG-UI and CopilotKit: streaming an Agent Framework agent into a web front end

CopilotKitDocumented in official docs

Microsoft Learn documents an AG-UI integration for Agent Framework in Python, .NET and Go, and CopilotKit's own documentation has a Microsoft Agent Framework section that describes the same connection from the front-end side. AG-UI is an open protocol for agent user interfaces. [17][18][23]

The problem

agent.run is an in-process call. A browser or mobile app needs the agent as a remote service that streams text as it is produced, shows tool calls in progress, asks the user to approve an action and keeps a conversation going across requests. Without a shared protocol, every team invents its own event format and its own client.

Where this topic fits

The integration is a hosting adapter placed in front of an ordinary agent. It turns an incoming AG-UI request into Agent Framework messages and run options, runs the agent, and converts the agent's streaming updates into AG-UI events. Tools, middleware and sessions stay where they were. See AG-UI for the protocol itself.

How it is applied, step by step

  1. Build the agent exactly as you would for in-process use, with its tools and middleware.
  2. Add the hosting package. In Python that is agent-framework-ag-ui, which wraps the agent in an AgentFrameworkAgent and exposes it through a FastAPI endpoint. In .NET it is Microsoft.Agents.AI.Hosting.AGUI.AspNetCore, which maps an endpoint with MapAGUIServer.
  3. The AG-UI client sends an HTTP POST. In the CopilotKit setup that client is the HttpAgent inside the CopilotKit runtime. The server answers with Server-Sent Events, so text and tool-call events reach the front end while the agent is still working.
  4. The protocol's threadId keeps the conversation together across requests, which is the role a session plays when you call the agent directly.
  5. A tool marked as needing approval becomes an AG-UI human-in-the-loop exchange: the request goes to the client, the user decides, and the decision returns to the agent.
  6. On the front end, CopilotKit registers the endpoint as an HttpAgent in its runtime, and its React components render the stream.

Why this approach fits

The agent does not change. What a web client needs (transport, event format, conversation identifiers and approval prompts) is supplied by an adapter and a published protocol, so any AG-UI client can connect and the same agent can still be called in-process by tests or by a workflow.

Limitation or tradeoff

The 1.0 announcement lists the AG-UI and CopilotKit adapters as preview features whose APIs may change, and the packages are installed as pre-releases. Microsoft's page says support for AG-UI's seven scenarios varies by SDK, so check the page for your language. Putting an agent behind HTTP also makes you responsible for authenticating callers and for checking that a threadId belongs to the user who sent it.

What the sources document

  • The same page maps agent.run to an HTTP POST request, streaming runs to Server-Sent Events, function tools to backend tools, tool approval mode to human-in-the-loop, and conversation history to a threadId that maintains context across requests. [17]
  • For .NET the page says MapAGUIServer adapts the AG-UI request to Agent Framework messages and run options and converts the agent's streaming response to AG-UI events, while tool execution and approval remain part of Agent Framework. [17]

Durable Task extension: agents and workflows that survive restarts on Azure Functions

Microsoft Azure Durable TaskDocumented in official docs

The Durable Extension is documented from both sides: in the Agent Framework documentation as a hosting option, and in the Azure Durable Task documentation as an extension of that service. It runs Agent Framework agents and workflows on Durable Task infrastructure, on Azure Functions or on your own compute. [15][16][11]

The problem

An in-process session is lost when the process crashes or when the next request lands on another instance. A workflow that waits a day for an approval would hold a worker for a day. Teams need conversations and multi-step runs that persist, recover and scale out without rewriting the agent. This is the subject of Durable Execution and Long-Running Agents.

Where this topic fits

The extension is a hosting layer under an unchanged agent or workflow. You register the agent with it, and each agent session becomes a durable entity whose conversation state is stored and checkpointed by the Durable Task backend. The documentation recommends the Durable Task Scheduler as that backend.

How it is applied, step by step

  1. Write the agent or the WorkflowBuilder graph in the usual way, with no durable-specific code.
  2. Register it with the host. In Python that is AgentFunctionApp(agents=[agent]) or AgentFunctionApp(workflow=workflow). In .NET it is ConfigureDurableAgents or ConfigureDurableWorkflows on the Functions application builder.
  3. The extension generates HTTP endpoints. A POST to the agent's run endpoint returns the reply with a thread ID in a response header, and sending that ID back continues the same conversation.
  4. Conversation history is kept in durable storage, so any instance can pick up the session after a crash, a restart or a scale-out event.
  5. To coordinate several agents, an orchestration function fetches registered agents and calls them in sequence or in parallel. Each agent call is checkpointed, and completed calls are not run again on recovery.
  6. A step that needs a person waits durably. Graph workflows use ctx.request_info in Python or a RequestPort in .NET, and orchestrations wait for an external event. No compute is consumed while waiting.
  7. The Durable Task Scheduler dashboard shows each session's conversation history, tool calls and the execution flow of orchestrations and workflows.

Why this approach fits

Durability is a property of where the agent runs, not of what it does, so it belongs in the host. Keeping it there means the same agent can run in a unit test, in a plain web service or on Azure Functions. Waiting is also where long-running agent work spends most of its time, and a serverless host that charges nothing while a run is paused matches that pattern.

Limitation or tradeoff

The Azure documentation lists limits. With the Durable Task Scheduler the state of one agent session, including its whole conversation history, cannot exceed 1 MB, and compaction is manual. Every interaction is routed through the scheduler, which adds latency compared with in-memory execution. Responses are request and response underneath, so streaming needs a separate channel such as Redis Streams. Session time-to-live configuration is available in .NET only. The packages are pre-releases, and the 1.0 announcement lists hosting on Foundry or Durable Functions as a preview feature.

What the sources document

  • The Agent Framework documentation says the Durable Extension lets you persist agent sessions, checkpoint orchestration and workflow progress, recover from failures and scale across distributed hosts without changing core agent logic, with Azure Functions and bring-your-own-compute hosting in C# and Python. [15]
  • The Azure Durable Task documentation says the extension internally implements entity-based agent loops, where each agent session is a durable entity that automatically manages conversation state and checkpointing. [16]
  • For a human-in-the-loop workflow that waits 24 hours for approval on the Azure Functions Flex Consumption plan, the Agent Framework page says you pay only for a few seconds of execution time and that no compute resources are consumed during the wait. [15]
  • The Azure page's known limitations say that the maximum entity state size with the Durable Task Scheduler is 1 MB and that all agent interactions are routed through the scheduler, which adds latency compared with in-memory execution. [16]
  • The workflow human-in-the-loop page says a Python executor sends a request with ctx.request_info and receives the answer in a method marked with the response_handler decorator, and that pending requests are saved in checkpoints and emitted again when a checkpoint is restored. [11]

The problem

One agent run can contain several model calls and tool calls. To debug it or to track cost, a team needs each of those as a separate, timed record with token counts, in the observability tool it already uses, which may not be an Azure service.

Where this topic fits

This is the telemetry layer of the agent pipeline. The agent, chat and function layers emit spans, the Langfuse client supplies the OpenTelemetry exporter, and one call activates the framework's instrumentation. Langfuse covers what you can do with the traces once they arrive.

How it is applied, step by step

  1. Install agent-framework and langfuse, and set the Langfuse public key, secret key and base URL as environment variables.
  2. Create the Langfuse client with get_client() and call auth_check() to confirm that the credentials work.
  3. Activate the framework's telemetry. Microsoft's page calls enable_instrumentation() after the third party's own setup, and Langfuse's guide calls configure_otel_providers().
  4. Run the agent. Each run emits an invoke_agent span that contains a chat span per model call and an execute_tool span per tool call. All of them carry one trace ID, so a back end such as Langfuse can show a run as a single trace.
  5. Decide what content to capture. With sensitive data off, spans carry names, timings and token counts. With it on, they also carry prompts, responses, tool arguments and tool results.
  6. Optionally wrap your code with the Langfuse SDK to add a user ID, a session ID and tags to every span in the trace.

Why this approach fits

Because the framework emits standard OpenTelemetry signals that follow the GenAI semantic conventions, the backend is a deployment choice. The agent code is identical whether traces go to Langfuse, to Azure Monitor or to a local dashboard, and a team can change backend without touching agents or workflows.

Limitation or tradeoff

The two pages do not match exactly, which is common for third-party guides. Langfuse's guide installs with the pre-release flag, although PyPI now lists the main package as Production/Stable. It also uses class and method names that Microsoft's current pages no longer show, such as AzureOpenAIChatClient().create_agent(...), and it turns sensitive data on, while Microsoft's snippet turns it off. Expect to adapt the sample to the current API. A trace also shows what happened, not whether the answer was right.

4Common mistakes

  1. Calling run twice without passing a session and expecting the agent to remember the first message.

    Why it causes problems
    The agent is stateless, so each run starts from the new message alone. Follow-up questions are answered without context, and users see an assistant that forgets what they said a moment ago.
    How to recognise it
    With sensitive-data capture on in a development environment, the chat span of the second request shows only the latest user message. A quicker test is to tell the agent your name and then ask for it in a second run.
    How to fix it
    Create one session per conversation with create_session (CreateSessionAsync in .NET), pass it to every run, and serialize it or keep the service-side conversation ID on your server between requests.

  2. Building one workflow object at start-up and reusing it for every request.

    Why it causes problems
    Executor instances keep their attributes and agents inside the workflow keep their conversation across runs. One user's data or dialogue can appear in the handling of another user's request.
    How to recognise it
    An agent step refers to content from an earlier, unrelated request, or a counter held by an executor keeps growing across requests instead of starting at zero.
    How to fix it
    Put the creation of executors, agents and the workflow inside a factory function and call it once per request or task, as the workflow state documentation recommends.

  3. Turning on sensitive-data capture in production telemetry.

    Why it causes problems
    Prompts, responses, tool arguments and tool results are written into traces and logs. Personal or confidential data then sits in an observability store that usually has wider access and different retention rules than the application database.
    How to recognise it
    Chat spans carry message content, and the configuration contains ENABLE_SENSITIVE_DATA=true or EnableSensitiveData = true outside a development environment.
    How to fix it
    Leave it off outside development and test. When you need content to debug an incident, enable it in a controlled environment for a short time and restrict who can read that trace store.

  4. Putting a once-per-request check, such as a rate limit or an audit record, in chat middleware.

    Why it causes problems
    Chat middleware runs for every model call, including the calls that send tool results back to the model. A request that uses tools twice is counted three times, so limits trip early and audit logs overcount.
    How to recognise it
    Count the log lines per user request. One request that triggers two rounds of tool calls produces three entries from the same middleware.
    How to fix it
    Move per-request logic to agent middleware and per-tool logic to function middleware. Keep chat middleware for work that must see every request to the model, such as redaction.

  5. Changing the graph or letting agent IDs be regenerated, then resuming from an old checkpoint.

    Why it causes problems
    A resumed workflow must have the same topology and executor identities as the one that wrote the checkpoint. When they differ, the resume fails and the progress of a long-running process is lost.
    How to recognise it
    Resume errors appear straight after a deployment that renamed or removed an executor, or in a .NET service that constructs its agents per request without setting stable IDs.
    How to fix it
    Give executors and agents fixed IDs named after their role. Treat a change to the graph as a new workflow version and let runs that started on the old version finish or restart.

  6. Copying code from tutorials written during the 2025 preview without checking the names.

    Why it causes problems
    Names changed on the way to 1.x. The launch post refers to an @ai_function decorator and a ChatMessage type, and some third-party guides still call create_agent, while current documentation uses @tool, Message and as_agent. Old code fails at import or attribute lookup.
    How to recognise it
    An ImportError or AttributeError on the first run, a tutorial dated before April 2026, or install instructions that add the pre-release flag to the main package.
    How to fix it
    Check the installed version with pip show agent-framework, read the current Microsoft Learn page for the feature, and use the migration and upgrade guides when moving older code forward.

Add a human approval step to the refund path

CodingIntermediateAbout 45 min (estimate)Hypothetical scenario

Start from triage.py in the worked example (its __main__ guard lets you import from it without running it). The support team has decided that a person must approve every refund before anything is sent to the customer. Replace refund_desk with an executor that pauses the workflow, asks for a decision and finishes when the decision arrives.

You need only pip install agent-framework; no model or API key is involved. Use these three calls:

python
print(await handle("URGENT: I was charged twice for order 1182", decision=True))
print(await handle("URGENT: I was charged twice for order 1182", decision=False))
print(await handle("How do I export my invoices?", decision=True))

handle(text, decision) is a function you write. It runs one ticket through a new workflow, answers any approval request with decision, and returns the list of workflow outputs.

Requirements

  • Define a dataclass ApprovalRequest with the fields ticket_text and priority, and an Executor subclass with the id refund_approval whose handler receives a Ticket and calls ctx.request_info with an ApprovalRequest and response_type=bool.
  • Add a method marked with response_handler that yields "REFUND APPROVED: <ticket text>" when the response is True and "REFUND DECLINED: <ticket text>" when it is False.
  • Route refund tickets to the new executor and leave the general path unchanged.
  • In handle, run the workflow with stream=True, collect request_info events by request_id and collect output events, then call run again on the same workflow object with responses set to a dictionary of request_id to decision.
  • Create the stateful executor inside create_workflow so that each ticket gets its own instance.

Expected behaviour

The program prints five lines:

text
approval needed: ApprovalRequest(ticket_text='URGENT: I was charged twice for order 1182', priority='high')
['REFUND APPROVED: URGENT: I was charged twice for order 1182']
approval needed: ApprovalRequest(ticket_text='URGENT: I was charged twice for order 1182', priority='high')
['REFUND DECLINED: URGENT: I was charged twice for order 1182']

For a refund ticket the first run ends with one pending request and no output. The output appears only after the second call to run. The general ticket produces its output in the first run and never asks for approval.

Hint 1

The documentation's guessing-game example is the same pattern: a handler calls ctx.request_info, and a method decorated with response_handler receives the original request and the response.

Hint 2

A request_info event has a request_id and a data attribute. The data is the object you passed as request_data.

Hint 3

The second call takes no new input message: workflow.run(stream=True, responses={request_id: True}). It must be made on the same workflow object, because that object holds the paused state.

Hint 4

Use WorkflowContext[Never, str] for both methods. They send nothing onward and yield a string.

Show solution

Save this as approval.py next to triage.py. It imports Ticket, classify and general_desk from the worked example and adds the approval executor and the driver. The pattern is the request and response mechanism from the workflow human-in-the-loop documentation.

python
import asyncio
from dataclasses import dataclass

from agent_framework import (
    Executor,
    Workflow,
    WorkflowBuilder,
    WorkflowContext,
    handler,
    response_handler,
)
from typing_extensions import Never

from triage import Ticket, classify, general_desk


@dataclass
class ApprovalRequest:
    ticket_text: str
    priority: str


class RefundApproval(Executor):
    def __init__(self) -> None:
        super().__init__(id="refund_approval")

    @handler
    async def ask(self, ticket: Ticket, ctx: WorkflowContext[Never, str]) -> None:
        await ctx.request_info(
            request_data=ApprovalRequest(ticket_text=ticket.text, priority=ticket.priority),
            response_type=bool,
        )

    @response_handler
    async def decide(
        self,
        original_request: ApprovalRequest,
        approved: bool,
        ctx: WorkflowContext[Never, str],
    ) -> None:
        verdict = "REFUND APPROVED" if approved else "REFUND DECLINED"
        await ctx.yield_output(f"{verdict}: {original_request.ticket_text}")


def create_workflow() -> Workflow:
    refund_approval = RefundApproval()   # stateful class: build it per workflow
    return (
        WorkflowBuilder(start_executor=classify)
        .add_edge(classify, refund_approval, condition=lambda t: t.category == "refund")
        .add_edge(classify, general_desk, condition=lambda t: t.category != "refund")
        .build()
    )


async def collect(stream):
    """Read one run's events into pending requests and outputs."""
    requests, outputs = {}, []
    async for event in stream:
        if event.type == "request_info":
            requests[event.request_id] = event.data
        elif event.type == "output":
            outputs.append(event.data)
    return requests, outputs


async def handle(text: str, decision: bool) -> list[str]:
    workflow = create_workflow()
    requests, outputs = await collect(workflow.run(text, stream=True))
    while requests:
        for request in requests.values():
            print("approval needed:", request)
        responses = {request_id: decision for request_id in requests}
        requests, more = await collect(workflow.run(stream=True, responses=responses))
        outputs.extend(more)
    return outputs


async def main() -> None:
    refund = "URGENT: I was charged twice for order 1182"
    print(await handle(refund, decision=True))
    print(await handle(refund, decision=False))
    print(await handle("How do I export my invoices?", decision=True))


if __name__ == "__main__":
    asyncio.run(main())

Why it works: ctx.request_info does not block. The handler returns, the workflow has nothing left to do and becomes idle, and the stream ends with a request_info event in it. The pending request is part of the workflow's state, which is why the second run must use the same object. That call delivers the response, the framework matches it to decide by the types of original_request and the response, and the output is yielded. In a real service the two calls happen in different HTTP requests, possibly days apart. You would give the builder a checkpoint storage, save the checkpoint ID with the ticket and resume with both checkpoint_id and responses; pending requests are saved in checkpoints and emitted again on restore.

  • Does the general ticket print its GENERAL DESK output without any "approval needed" line?

"""A paper model of superstep (BSP) scheduling. Standard library only."""


def simulate(durations, edges, fan_in, start):
    """Return {executor: (superstep, start_time, end_time)} under the barrier rule."""
    clock = 0.0
    step = 0
    running = [start]
    arrived = set()          # fan-in sources that have already delivered a message
    timeline = {}
    while running:
        step += 1
        step_start = clock
        for name in running:
            timeline[name] = (step, step_start, round(step_start + durations[name], 2))
        # Barrier: the superstep ends when its slowest executor ends.
        clock = max(end for _, _, end in (timeline[name] for name in running))
        queued = []
        for name in running:
            queued.extend(edges.get(name, []))        # direct and fan-out edges
            if name in fan_in["sources"]:
                arrived.add(name)
        if arrived == set(fan_in["sources"]) and fan_in["target"] not in timeline:
            queued.append(fan_in["target"])           # fan-in fires once every source delivered
        running = queued
    return timeline


def report(title, durations, edges, fan_in):
    print(title)
    timeline = simulate(durations, edges, fan_in, "start")
    for name, (step, begin, end) in timeline.items():
        print(f"  superstep {step}: {name:<5} {begin:.1f}s -> {end:.1f}s")
    print(f"  total: {max(end for _, _, end in timeline.values()):.1f}s")


chained = {"start": 0.0, "a1": 0.2, "a2": 0.2, "b": 1.0, "join": 0.1}
report(
    "Chained fast branch (a1 -> a2)",
    chained,
    {"start": ["a1", "b"], "a1": ["a2"]},
    {"sources": ["a2", "b"], "target": "join"},
)

merged = {"start": 0.0, "a": 0.4, "b": 1.0, "join": 0.1}
report(
    "Merged fast branch (a)",
    merged,
    {"start": ["a", "b"]},
    {"sources": ["a", "b"], "target": "join"},
)
