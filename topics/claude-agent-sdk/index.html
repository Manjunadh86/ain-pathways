Claude Agent SDK

The Claude Agent SDK is a Python and TypeScript library that runs Claude Code's agent harness inside your own program. The harness supplies the agent loop, ready-made file, shell and web tools, permission checks, hooks, subagents, MCP connections, skills, saved sessions and automatic context compaction. Your code supplies a prompt and options, and reads a stream of messages.

1Overview

Why it matters

Most agent frameworks give you a loop and a tool interface and leave the tools to you. For an agent that works on a computer (reading a repository, editing files, running tests, searching the web), those tools are most of the engineering and most of the risk. The Agent SDK ships them already built, because it is the harness behind Claude Code. The work you still own changes shape. You no longer write the loop. You decide which tools exist, which calls run without asking, which are blocked, and when the run must stop.

Getting that configuration wrong has concrete costs. A CI job that sets allowed_tools=["Read"] together with bypassPermissions has an open shell, because the allow list never restricted anything. A long session forgets an instruction from its first prompt after compaction. A shared service leaks one customer's project instructions into another customer's run because settings were loaded from the host. Engineers who embed coding or operations agents in products, pipelines and internal tools need this lesson, and so do the people who review those deployments.

Key terms

Agent harness
The program around a model that runs the agent loop, executes tools, enforces permissions and manages the context window. In this SDK the harness is Claude Code, running as a subprocess.
Built-in tool
A tool the harness already implements and executes itself, such as Read, Edit, Bash or WebSearch. You do not write a handler for it.
Permission mode
A session-wide setting that decides what happens to tool calls that no rule has settled, for example acceptEdits, dontAsk or bypassPermissions.
Allow and deny rules
Entries such as Read or Bash(npm test *) that approve or block matching tool calls. A bare tool name covers every call to that tool, and a pattern in brackets covers only matching calls.
Hook
A callback in your application that the harness calls at a fixed point, such as just before a tool runs. Its return value can block the action, change its input or add context.
Subagent
A separate agent instance that the main agent starts through the Agent tool. It works in its own context window and sends back only its final message.
MCP server
A program that offers tools over the Model Context Protocol. The SDK can connect to external servers or host one inside your own process for custom tools.
Skill
A folder containing a SKILL.md file of instructions. Claude sees a short description at startup and loads the full text only when a task calls for it.
Session
The saved transcript of one conversation, holding the prompt, every tool call and result, and every reply. It can be continued, resumed by ID or forked.
Compaction
Replacing older conversation history with a summary when the context window is nearly full, so that a long run can keep going.

2Explanation

Introduction

In Choosing an Agent Framework you saw that a framework gives you the loop ready-made, along with state, orchestration, tracing and integrations. Notice what that list leaves out: the tools. The loop itself is small (the working one in The Agent Loop fits on a page). What takes months is the equipment around it: a file-editing tool that does not corrupt files, a shell tool that cannot hang forever, a search tool that does not flood the context, a rule for when to ask a person, and a plan for the moment the context window fills up.

Think of hiring a contractor. One arrives empty-handed, so you buy every tool and write the site safety rules yourself. Another arrives with a van: the tools, a safety routine and a logbook are already there. With the second contractor your job is different. You decide which rooms they may enter, which jobs need your signature, and at what cost you call a halt.

The Claude Agent SDK is the second contractor. Anthropic built a harness for Claude Code, its coding agent, and then published that harness as a library. The SDK overview (opens in a new tab) describes it as the same tools, agent loop and context management that power Claude Code, programmable in Python and TypeScript. This is a complete agent:

python
import asyncio
from claude_agent_sdk import query


async def main():
    async for message in query(prompt="What files are in this directory?"):
        print(message)


asyncio.run(main())

No tool is defined in those lines, yet Claude can list the directory, because file search is built in and the harness executes it. That is the difference from the frameworks where you register every function yourself.

The rest of this lesson follows the diagram downwards. It covers how the library drives the harness, which tools are built in and how permissions and hooks control them, how subagents, MCP servers and skills extend an agent, and how sessions and automatic compaction keep a long run alive.

How it works

A library that drives a subprocess

The SDK itself is thin. When your code calls query(), the library starts a separate claude process (the bundled Claude Code binary) and talks to it over standard input and output. That subprocess is the harness. It calls the Claude API, executes tools, checks permissions and writes the session transcript to local disk. As the hosting guide (opens in a new tab) puts it, every running agent is a long-lived process tied to local state, unlike a stateless API wrapper.

Install it with pip install claude-agent-sdk (Python 3.10+) or npm install @anthropic-ai/claude-agent-sdk (Node.js 18+) and put an API key in ANTHROPIC_API_KEY. Python offers query() for one task and ClaudeSDKClient for several exchanges in one session. The packages were named the Claude Code SDK until September 2025, so older tutorials import claude_code_sdk. Option names below are the Python ones; TypeScript uses camelCase (allowedTools).

The message stream

query() returns an asynchronous iterator. Each message tells you which stage of the agent loop (opens in a new tab) produced it.

MessageWhen it arrivesWhat you read from it
SystemMessage, subtype initOnce, at the startSession metadata: tools, MCP server status, skills
AssistantMessageFor each block Claude producesText, or a tool call (ToolUseBlock)
UserMessageAfter each tool executionThe tool result sent back to Claude
ResultMessageOnce, at the endsubtype, result, num_turns, total_cost_usd, session_id

A turn is one round trip: Claude asks for tools, and the harness runs them and feeds the results back. The loop ends when Claude replies with no tool call. There is no turn or spend limit unless you set max_turns (it counts tool-use turns) or max_budget_usd. When a limit ends the run, subtype is error_max_turns or error_max_budget_usd and there is no result text, so check subtype first.

Built-in tools: availability and permission

CategoryTools
Files and searchRead, Edit, Write, Glob, Grep
ShellBash
WebWebSearch, WebFetch
Orchestration and discoveryAgent, Skill, AskUserQuestion, TaskCreate, TaskUpdate, ToolSearch

The harness runs these itself, read-only tools concurrently and state-changing ones such as Edit and Bash in sequence. Reads in the working directory need no approval; edits, most shell commands and web tools do. Every tool raises two questions: does Claude see it, and may a particular call run?

OptionAnswersEffect
tools=["Read", "Grep"]AvailabilityOnly these built-ins are in Claude's context
disallowed_tools=["Bash"]AvailabilityThe tool is removed, so Claude cannot attempt it
disallowed_tools=["Bash(rm *)"]PermissionMatching calls are denied in every mode
allowed_tools=["Read", "Bash(npm test *)"]PermissionMatching calls run without asking. Nothing else is hidden or blocked

Permissions: six checks in a fixed order

When Claude requests a tool, the harness evaluates the call in the order given by the permissions guide (opens in a new tab):

  1. Hooks. A PreToolUse hook can deny the call. A hook that allows it still passes through steps 2 and 3.
  2. Deny rules. A match blocks the call, even in bypassPermissions mode.
  3. Ask rules (from settings files). A match sends the call to your approval callback.
  4. Permission mode. bypassPermissions approves what reaches this step, acceptEdits approves file edits, and the other modes pass the call on.
  5. Allow rules. A match approves the call. Calls that never need approval, such as file reads in the working directory, are also settled here.
  6. The can_use_tool callback. Your code decides. With no callback, or in dontAsk mode, the call is denied.
ModeCalls that no rule has settled
defaultSends them to can_use_tool
acceptEditsApproves file edits and common filesystem commands in the working directory
planClaude explores and plans; file edits always go to the callback
dontAskDenies anything that would prompt, without calling the callback
autoA model classifier allows or blocks each action it reviews
bypassPermissionsApproves them all. For isolated environments only

Three consequences follow. allowed_tools=["Read"] with bypassPermissions still approves Bash, because unlisted tools fall through to the mode. A call approved at an earlier step never reaches can_use_tool, so a check that must see every call belongs in a hook. And an omitted permission_mode comes from settings files or a built-in default that can be auto, so set it explicitly. Bash rules match the command text as written (Bash(rm *) does not stop /bin/rm), so real isolation needs a container or sandbox (see Code Execution and Sandboxing).

Hooks

A hook (opens in a new tab) is a callback in your application that the harness calls at a fixed event, such as PreToolUse, PostToolUse, UserPromptSubmit, Stop or PreCompact. It receives the event's input (for tool events, tool_name and tool_input) and returns a dictionary; an empty one means no opinion. A PreToolUse hook can return a permissionDecision (allow, deny, ask or defer), a reason that Claude reads, and updatedInput to rewrite the arguments. When hooks and rules disagree, deny beats defer, which beats ask, which beats allow.

Hooks run in your process, so they use no context. Each is registered with a matcher on the tool name, such as "Write|Edit". A matcher cannot see arguments, so inspect tool_input in the callback.

MCP servers and custom tools

External capabilities arrive through the Model Context Protocol. Pass servers in mcp_servers: a command for a local stdio server, or a URL for an HTTP server. Their tools are named mcp__<server>__<tool> and need permission like any other tool, for example allowed_tools=["mcp__github__*"].

Your own functions take the same route:

python
from claude_agent_sdk import create_sdk_mcp_server, tool


@tool("order_status", "Look up the status of an order", {"order_id": str})
async def order_status(args):
    return {"content": [{"type": "text", "text": f"Order {args['order_id']}: shipped"}]}


orders = create_sdk_mcp_server(name="orders", tools=[order_status])  # runs inside your process
# options: mcp_servers={"orders": orders}, allowed_tools=["mcp__orders__order_status"]

Tool search is on by default: MCP tool schemas load only when Claude needs them, so many servers do not fill the context. An MCP result over 25,000 tokens is saved to a file, and Claude is told where to read it.

Skills and project settings

Unless you pass setting_sources, the harness loads the same filesystem configuration as the Claude Code command line: user, project and local settings, CLAUDE.md instructions, and the skills, subagents and commands under .claude/. A skill is a folder such as .claude/skills/security-check/ holding a SKILL.md file. Only its description is loaded at startup; the full text enters the context when Claude invokes it through the Skill tool. The skills option narrows the set to "all", a list of names or []. Skills cannot be registered in code. For a service, pass setting_sources=[] so nothing on the host leaks in.

Subagents

A subagent is a second agent instance that the main agent starts through the Agent tool. You define one in the agents option as an AgentDefinition with a description, a prompt and optionally a tools list. Claude picks a subagent by its description.

The subagent starts with a fresh context: its own prompt, the task text Claude wrote, project instructions and its tools, but none of the parent's history. Only its final message returns. This is the orchestrator-workers pattern with two payoffs: work runs in parallel, and the main context grows by a summary, not by every file the worker read. Recent releases cap nesting at 3 levels and 20 concurrent subagents by default, and max_budget_usd counts subagent spend.

Sessions

A session is the transcript that the harness writes to disk as it works, a JSONL file under ~/.claude/projects/. Every ResultMessage carries its session_id.

OptionsFinds the session byUse it to
continue_conversation=TrueMost recent in the working directoryCarry on after a restart
resume=session_idThe ID you savedReturn to a chosen session, or recover after a limit
resume=session_id, fork_session=TrueThe ID, copied under a new oneTry another approach, keep the original

A session stores the conversation, not the files: a fork that edits files changes them for every session in that directory. Transcripts are local to one machine, so a service on several hosts needs a session_store adapter, or should carry results forward as its own state.

Automatic context compaction

The context window holds the system prompt, tool definitions and the whole history, and it only grows during a session. Near the limit, the harness summarises older history, keeps recent exchanges, and emits a system message with subtype compact_boundary.

The summary can drop a detail given early in the conversation. Rules that must survive belong in CLAUDE.md, which is sent with every request. A PreCompact hook can archive the full transcript first, and sending /compact as a prompt compacts by hand.

Worked example: A bug-fixing agent with a locked-down shell, traced through the six permission steps

The task: a small module has a failing unit test. An agent should fix it without changing the tests, deleting anything or installing packages. You need Python 3.10 or later, pip install claude-agent-sdk in a virtual environment, and an API key in ANTHROPIC_API_KEY. The run makes paid API calls. The budget option stops it near $0.50 (the response that crosses the cap still completes).

In an empty folder, create stats.py:

python
def mean(values):
    return sum(values) / len(values)

and test_stats.py:

python
import unittest

from stats import mean


class MeanTest(unittest.TestCase):
    def test_typical_list(self):
        self.assertEqual(mean([2, 4, 9]), 5)

    def test_empty_list_is_zero(self):
        self.assertEqual(mean([]), 0)

Run python3 -m unittest yourself first. It needs no API key, and its output ends like this:

text
ZeroDivisionError: division by zero

----------------------------------------------------------------------
Ran 2 tests in 0.002s

FAILED (errors=1)

Now the agent. Save this as agent.py in the same folder:

python
import asyncio

from claude_agent_sdk import (
    AssistantMessage,
    ClaudeAgentOptions,
    ClaudeSDKClient,
    HookMatcher,
    ResultMessage,
    ToolUseBlock,
)


async def protect_tests(input_data, tool_use_id, context):
    """PreToolUse hook: the agent may read test files but never change them."""
    file_name = input_data["tool_input"].get("file_path", "").split("/")[-1]
    if not file_name.startswith("test_"):
        return {}  # no opinion: the remaining permission steps decide
    return {
        "hookSpecificOutput": {
            "hookEventName": input_data["hook_event_name"],
            "permissionDecision": "deny",
            "permissionDecisionReason": "Tests are the specification. Change stats.py instead.",
        }
    }


OPTIONS = ClaudeAgentOptions(
    setting_sources=[],                              # ignore ~/.claude and ./.claude settings
    tools=["Read", "Edit", "Glob", "Grep", "Bash"],  # availability: the only built-ins Claude sees
    allowed_tools=["Read", "Glob", "Grep", "Edit", "Bash(python3 -m unittest *)"],
    disallowed_tools=["Bash(rm *)"],                 # denied in every permission mode
    permission_mode="dontAsk",                       # anything that would prompt is denied
    hooks={"PreToolUse": [HookMatcher(matcher="Edit|Write", hooks=[protect_tests])]},
    max_turns=12,
    max_budget_usd=0.50,
)


async def main():
    async with ClaudeSDKClient(options=OPTIONS) as client:
        await client.query("Run the unit tests, fix the bug that makes one fail, and run them again.")
        async for message in client.receive_response():
            if isinstance(message, AssistantMessage):
                for block in message.content:
                    if isinstance(block, ToolUseBlock):
                        print(f"tool: {block.name} {block.input}")
            elif isinstance(message, ResultMessage):
                print(f"result: {message.subtype}, turns: {message.num_turns}, "
                      f"cost: {message.total_cost_usd}, session: {message.session_id}")
                if message.subtype == "success":
                    print(message.result)


if __name__ == "__main__":
    asyncio.run(main())

Run python3 agent.py. The script prints one tool: line per tool call and ends with a result: line. The order of the calls differs from run to run, because the model chooses each step. A run that works ends with result: success, and python3 -m unittest then reports Ran 2 tests and OK. (The script was written against the documented API, and its hook was tested on sample inputs. It was not run against the live API for this lesson.)

What does not vary is how each kind of call is decided. Here are the six steps, traced by hand for this configuration:

Tool call Claude might makeDecided atOutcome
Read on stats.pyStep 5, allow rule ReadRuns
Bash: python3 -m unittestStep 5, allow rule Bash(python3 -m unittest *). A trailing * also matches the bare commandRuns
Edit on test_stats.pyStep 1, the hook returns denyBlocked. Claude reads the reason
Edit on stats.pyHook has no opinion, steps 2 to 4 pass, step 5 allow rule EditRuns
Bash: rm -rf __pycache__Step 2, deny rule Bash(rm *)Blocked in every mode
Bash: pip install pytestNo rule matches, so step 6, in dontAsk modeDenied. No callback is called
Bash: lsStep 5. Read-only commands need no approval in any modeRuns, although no rule lists it
WebFetch on any URLNot in toolsCannot be attempted. Claude never sees the tool

What to notice:

  • Three layers, three jobs. tools removed the web tools entirely. The deny rule and the hook block specific calls. dontAsk turns every call that would have prompted into a refusal, instead of a question that nobody is there to answer.
  • A denial is an observation. A blocked call returns to Claude as a tool result that carries the reason, and the loop continues. The hook's reason tells Claude what to do instead.
  • Check the subtype. With max_turns=12, a struggling run ends with result: error_max_turns and no answer text. The session ID on that line lets you resume with a higher limit by passing resume="<that id>" and a larger max_turns.
  • This is not a sandbox. Bash(rm *) matches the command text only (the rule syntax is in the permissions reference (opens in a new tab)), and Python code run by the allowed unittest command could still delete files. Run unattended agents in a container or a throwaway checkout.

Edge cases and limitations

allowed_tools does not limit what the agent can use
Listing a tool in allowed_tools only pre-approves it. Unlisted tools stay in Claude's context and fall through to the permission mode, and the permissions guide states that allowed_tools=["Read"] together with bypassPermissions still approves Bash, Write and Edit. To remove tools, name the ones you want in the tools option or put bare names in disallowed_tools. To refuse every call that would otherwise prompt, use dontAsk mode.
A limit ends the run with an error result, and a one-shot query() then raises
When max_turns or max_budget_usd is reached, the final ResultMessage has subtype error_max_turns or error_max_budget_usd and no result text. In a single-shot query() call the SDK yields that message and then raises an exception on purpose, so code after the loop does not run unless the loop is wrapped in try and except. The result still carries the session ID, so the run can be resumed with a higher limit. A budget can also be overshot by the cost of the response that crosses it.
Compaction can drop an instruction from the first prompt
Compaction replaces older messages with a summary, and the documentation warns that specific instructions from early in the conversation may not be preserved. An agent told in its first prompt never to touch a directory can lose that rule hours later. Put persistent rules in CLAUDE.md, which is re-sent on every request, add a section there that tells the summariser what to preserve, or enforce the rule in a hook, which does not depend on the context at all.
Defaults come from the machine the agent runs on
With setting_sources omitted, query() loads user, project and local settings, CLAUDE.md files and skills, the same as the command line. The migration guide notes that version 0.1.0 briefly loaded none and that this was reverted, so older tutorials describe the opposite default. Some inputs load whatever you pass, including managed policy settings and auto memory. For a multi-tenant service the hosting guide recommends setting_sources=[], CLAUDE_CODE_DISABLE_AUTO_MEMORY=1, and a separate working directory and config directory per tenant. The system prompt has a default too: since version 0.1.0 the SDK uses a minimal prompt unless you request the claude_code preset.
Resuming or forking a session does not restore files
A session stores the conversation only. If a forked session edits files, those edits are real and visible to every session working in the same directory, and resuming an old session does not put the files back as they were. File checkpointing is a separate feature. Transcripts are also local, so a session created in one container cannot be resumed in another unless you configure a session store or move the transcript file.
The Python and TypeScript SDKs differ in small ways
The hooks guide lists many events that only TypeScript supports as callbacks, such as SessionStart, SessionEnd and PostCompact. The env option is merged into the inherited environment in Python but replaces it in TypeScript, where you must spread process.env to keep PATH. Python has a ClaudeSDKClient class for multi-turn sessions, while TypeScript passes the continue option to query(). Check the reference for your language before porting an example.

When to use it, and when something simpler is enough

Use it when

  • The agent's work happens on a filesystem or in a shell, such as changing code, processing documents or data files, or operating a repository in CI, so the built-in tools do most of the job.
  • You already use Claude Code and want the same behaviour, project instructions, skills and MCP configuration inside your own application or pipeline.
  • Tasks run long enough that context management matters, and you want compaction, subagents and resumable sessions without building them yourself.
  • You can give each session its own process and working directory, preferably inside a container, and you are content to run Claude models.

Think twice when

  • You need models from several providers, or must be able to switch provider. The harness is built around Claude models, reached through Anthropic or one of the cloud platforms the quickstart lists.
  • The job is a short request and response with a few function tools and no file or shell access. A subprocess that owns a shell adds weight and attack surface for no benefit.
  • You cannot give each session an isolated process and local disk, for example in a function runtime with no writable filesystem.
  • You do not want to operate the harness at all. A hosted service such as Managed Agents runs the loop for you.
  • Every step must follow an explicit graph that you define and audit. That is the job of a workflow or graph framework, not of a model-directed loop.

A simpler alternative. Call the Messages API with tool use and write the loop yourself, or let the client SDK's tool runner drive it. That is enough for a handful of your own function tools and a short conversation. It stops being enough when you find yourself rebuilding file editing, shell execution, permission prompts or context compaction, because the harness already contains all four.

Key takeaways

  • The Agent SDK is Claude Code's harness used as a library: your code sends a prompt and options, a Claude Code subprocess runs the loop and executes built-in file, shell and web tools, and you read a stream of messages.
  • Availability and permission are separate: the tools option and bare disallowed_tools names decide which tools exist, while allowed_tools, scoped deny rules and the permission mode decide which calls run.
  • Permission checks run in a fixed order (hooks, deny rules, ask rules, mode, allow rules, callback), so a hook or deny rule holds even in bypassPermissions and allowed_tools never restricts anything.
  • Subagents, skills and MCP tool search all keep the main context small by loading detail only when it is needed, and a subagent returns only its final message.
  • A session saves the conversation and not the files, and compaction replaces old history with a summary, so durable rules belong in CLAUDE.md or hooks and durable progress belongs in files.
  • Set max_turns, max_budget_usd and the permission mode explicitly, check the result subtype, and run unattended agents inside a container or sandbox.

Claude Code GitHub Actions: the SDK as an unattended agent in CI

AnthropicDocumented in official docs

Claude Code GitHub Actions (the anthropics/claude-code-action repository) is Anthropic's GitHub Action for running Claude in repository workflows. Its page in the Claude Code documentation describes the two run modes and the inputs, and states that the action is built on the Agent SDK. The action's package.json confirms the dependency. [17][19][18]

The problem

A repository wants an agent that answers @claude mentions on issues and pull requests, or runs on a schedule, with no person at a terminal to approve tool calls. The run happens on a CI runner with repository secrets nearby, so it has to be bounded. Only people with write access should be able to start it, bots must not trigger it in a loop, the agent should hold only the tools the task needs, and a confused run must stop before it burns through Actions minutes and API tokens.

Where this topic fits

The action is a wrapper around the harness. A GitHub event starts the workflow, the action checks who triggered it, and then it runs the agent on the runner with the checked-out repository as the working directory. The SDK's controls are surfaced as workflow inputs: claude_args carries flags such as --allowedTools and --max-turns, and settings carries permission rules. Results leave as a comment on the issue or pull request, or in the workflow log.

How it is applied, step by step

  1. A workflow file subscribes to GitHub events (comments, pull requests or a cron schedule) and passes an API key from the repository's secrets to the action.
  2. Before Claude starts, the action checks the triggering actor. On issue and pull request events the user needs write access, and bot actors are rejected unless they are listed in allowed_bots.
  3. The action picks a mode from the configuration. Without a prompt input it waits for the trigger phrase in a comment and replies there. With a prompt input it runs immediately in automation mode.
  4. A checkout step gives the harness a local copy of the repository, which becomes the working directory for its file and search tools.
  5. Tool access is granted explicitly. For a plain-text prompt the agent has no shell or GitHub API access until the workflow names tools with --allowedTools or a permissions.allow rule.
  6. The run is bounded with --max-turns in claude_args, a workflow-level timeout and GitHub's concurrency controls.
  7. The harness loops until it finishes or reaches a limit. The outcome appears as a comment or in the run log, where a person reviews it before anything is merged.

Why this approach fits

CI is the standard unattended environment. Nobody can answer a permission prompt, so everything the agent may do has to be decided in advance. The harness already has the pieces for that: an allow list of tools, a turn limit and a repository on local disk for its file tools. Building the action on the SDK also means it follows the same project files that developers use interactively. The page says Claude follows the repository's CLAUDE.md in the action, and that a skill in .claude/skills/ can be run by passing its name as the prompt.

Limitation or tradeoff

An allow list is only as tight as its rules. The permissions reference says a Bash rule matches the command text Claude writes and is not a security boundary around the program, so Bash(rm *) in a deny list does not stop /bin/rm. Issue and comment text is also untrusted input that the agent reads, which is a prompt injection path. The write-access check narrows who can supply that text but does not remove the risk. Each run costs GitHub Actions minutes and API tokens. On public repositories GitHub withholds secrets from runs triggered by fork pull requests, so the documented review workflow runs only for branches in the same repository.

What the sources document

  • The Claude Code GitHub Actions page states that the Claude Code GitHub Action is built on the Claude Agent SDK, and the action repository's package.json lists @anthropic-ai/claude-agent-sdk among its dependencies (version range ^0.3.296 when accessed). [17][19]
  • With no prompt input the action runs in interactive mode and waits for the trigger phrase, @claude by default. With a prompt input it runs in automation mode without waiting for a mention, and by default its results appear in the workflow run log. [17]

4Common mistakes

  1. Treating allowed_tools as the list of tools the agent is able to use.

    Why it causes problems
    The option only pre-approves calls. Every other built-in tool is still in Claude's context, and with bypassPermissions each of them is approved, so an agent you believed to be read-only can run shell commands and write files.
    How to recognise it
    The tools array in the init system message lists tools you never named, or Bash and Write calls appear in the message stream of an agent that was meant only to read.
    How to fix it
    Use the tools option to name the built-ins that should exist, or put bare names in disallowed_tools to remove them. Pair allowed_tools with dontAsk mode so that any call that would need approval is refused.

  2. Putting a safety check in can_use_tool while the same tool is auto-approved.

    Why it causes problems
    A call approved by an allow rule, by acceptEdits or by bypassPermissions never reaches the callback, so the check is skipped silently for exactly the calls it was written to inspect.
    How to recognise it
    Logging inside the callback never fires for a tool that is clearly being used. In TypeScript the SDK also emits a process warning with the code CLAUDE_SDK_CAN_USE_TOOL_SHADOWED.
    How to fix it
    Move any check that must see every call into a PreToolUse hook. Hooks run before all other permission steps, and a hook's deny applies even in bypassPermissions mode.

  3. Running without max_turns or max_budget_usd and reading the result without checking its subtype.

    Why it causes problems
    Neither limit exists by default, so an open-ended prompt can run and spend for a long time, with subagents adding their own requests. When a limit does end the run, the result text is empty, and code that assumes success passes nothing downstream.
    How to recognise it
    Sessions with a large num_turns and total_cost_usd in the final message, and application code that reads the result field with no branch for the error subtypes.
    How to fix it
    Set both limits from the turn counts and costs of successful runs, leave headroom on the budget, branch on the subtype, and keep the session ID so that a capped run can be resumed.

  4. Using bypassPermissions on a developer laptop or a shared host to stop the prompts.

    Why it causes problems
    The agent then has the full access of the account it runs under, and so does every subagent, because a subagent inherits the mode. A prompt injection in a file or web page can turn that access against you.
    How to recognise it
    The mode appears in options or settings outside a container, or runs happen in a home directory that holds credentials and unrelated projects.
    How to fix it
    Keep bypassPermissions for containers, virtual machines and CI runners that hold nothing you care about. Elsewhere use acceptEdits with scoped allow rules, or dontAsk with an explicit allow list, and add deny rules and hooks for what must never happen.

  5. Leaving the default setting sources on in a service that serves several users.

    Why it causes problems
    The harness reads settings, CLAUDE.md instructions, skills and memory from the host's filesystem, so one tenant's project instructions or a developer's personal configuration can shape another tenant's run.
    How to recognise it
    The init message lists skills or MCP servers you did not configure, or the agent follows conventions that appear nowhere in your code or prompt.
    How to fix it
    Pass setting_sources=[] and set CLAUDE_CODE_DISABLE_AUTO_MEMORY=1, give each tenant its own working directory and config directory, and supply instructions through the system prompt.

  6. Keeping must-follow instructions only in the first prompt of a long session.

    Why it causes problems
    Automatic compaction summarises older history, and the summary is not guaranteed to keep a specific early instruction. The agent then breaks a rule it followed correctly for the first hour.
    How to recognise it
    Behaviour changes after a compact_boundary system message appears in the stream, or late in sessions but never early.
    How to fix it
    Put durable rules in CLAUDE.md, which is sent with every request, enforce hard rules in hooks or deny rules, and write progress to files instead of relying on the conversation to carry it.

The permissions guide (opens in a new tab) describes six checks. Write a small Python model of them and use it to predict outcomes. This is a teaching model, not the SDK. It needs only the standard library and makes no API calls.

Use these simplified rules:

  1. Hook. config["hook"](call) returns "deny", "allow" or None. A deny blocks the call. An allow still goes through steps 2 and 3 and is then approved.
  2. Deny rules. Any match blocks the call, in every mode.
  3. Ask rules. Any match sends the call to the prompt step (step 6).
  4. Mode. bypassPermissions approves the call. acceptEdits approves Edit and Write. Other modes pass the call on.
  5. Allow rules. Any match approves the call. Read, Glob and Grep need no approval and are approved here too.
  6. Prompt step. In dontAsk mode the call is denied. Otherwise config["can_use_tool"](call) decides, and a missing callback means the call is denied.

A call is a (tool, argument) pair. A rule is a bare tool name such as Read, or Tool(pattern). A pattern that ends in a space and * matches any argument that starts with the text before it, and also that text alone. A pattern with no * matches only the exact argument.

"""A teaching model of the Agent SDK's documented permission order. It is not the SDK's code."""

EDIT_TOOLS = {"Edit", "Write"}
NO_APPROVAL_NEEDED = {"Read", "Glob", "Grep"}  # reads inside the working directory


def rule_matches(rule, call):
    """A rule is 'Tool' or 'Tool(pattern)'. A call is a (tool, argument) pair."""
    tool, argument = call
    if "(" not in rule:
        return rule == tool
    name, pattern = rule[:-1].split("(", 1)
    if name != tool:
        return False
    if pattern.endswith(" *"):  # trailing wildcard: a prefix, or the bare command
        prefix = pattern[:-2]
        return argument == prefix or argument.startswith(prefix + " ")
    return argument == pattern  # no wildcard: exact text only


def any_match(rules, call):
    return any(rule_matches(rule, call) for rule in rules)


def prompt(call, config):
    """Step 6: what happens when nothing earlier resolved the call."""
    if config.get("mode") == "dontAsk":
        return "denied (dontAsk never prompts)"
    callback = config.get("can_use_tool")
    if callback is None:
        return "denied (no callback)"
    return "runs (callback allowed)" if callback(call) else "denied (callback)"


def decide(call, config):
    tool, _ = call
    mode = config.get("mode", "default")
    hook_decision = config["hook"](call) if "hook" in config else None  # step 1
    if hook_decision == "deny":
        return "blocked (hook)"
    if any_match(config.get("deny", []), call):                         # step 2
        return "blocked (deny rule)"
    if any_match(config.get("ask", []), call):                          # step 3
        return prompt(call, config)
    if hook_decision == "allow":
        return "runs (hook allowed)"
    if mode == "bypassPermissions":                                     # step 4
        return "runs (mode)"
    if mode == "acceptEdits" and tool in EDIT_TOOLS:
        return "runs (mode)"
    if any_match(config.get("allow", []), call):                        # step 5
        return "runs (allow rule)"
    if tool in NO_APPROVAL_NEEDED:
        return "runs (no approval needed)"
    return prompt(call, config)                                         # step 6


# ... paste protect_tests, the four configurations and CASES here ...

if __name__ == "__main__":
    for number, (label, config, call) in enumerate(CASES, start=1):
        print(f"{number:>2} {label:<12} {call[0]}({call[1]}) -> {decide(call, config)}")

It prints the 13 lines shown under expected behaviour. Why each interesting case comes out as it does:

  • Case 2. The rule Bash(python3 -m unittest *) ends in a space and *, so it also accepts the bare command. That matches the documented behaviour of Bash(ls *), which matches ls.
  • Case 3. The hook runs first. Nothing later can override its deny, although Edit is on the allow list.
  • Cases 5 and 8. Deny rules are step 2, before the mode at step 4, so the same rule blocks the call in dontAsk and in bypassPermissions.
  • Case 7. The allow list is step 5. In bypass mode the call is approved at step 4 and never gets there, so listing only Read restricted nothing.
  • Case 9. The rule text starts with rm, and the command starts with /bin/rm. No match, so the mode approves it. Rules match text, which is why isolation has to come from a container or sandbox.
  • Case 11. In default mode an unsettled call goes to the callback, and with no callback it is denied.
  • Case 13. acceptEdits approves edits only. The ask rule sends the push to the callback, which refuses.

The model leaves out a great deal on purpose, including plan and auto modes, compound shell commands and the actions no mode approves. Use it to reason about ordering, not as a specification.

Check your answer

  • Do cases 5 and 8 both end blocked by the deny rule, although one configuration is in dontAsk mode and the other in bypassPermissions?
  • Does case 7 run even though that configuration's allow list contains only Read?
  • Does case 9 run because the rule text does not match a command that starts with /bin/rm?
  • Does case 2 match the allow rule although the command has nothing after unittest?
  • If you change the hook so that it returns allow for every call, are cases 5 and 8 still blocked?

Exercise 2

Configure a pull-request review agent for CI

DesignIntermediateAbout 40 min (estimate)Hypothetical scenario

A team wants an agent that reviews every pull request in CI. It runs in a fresh container with the repository checked out. Findings must be posted through one function, post_review_comment(path, line, body), which the team will expose as an in-process MCP tool on a server named review.

Write a function build_options(repo_dir) that returns a ClaudeAgentOptions object meeting the requirements below, together with the tool definition and any hooks it needs. Then answer four questions:

  1. Claude decides it wants to run the test suite with Bash. What happens?
  2. Claude calls the comment tool for the eleventh time. Which permission step decides, and what does Claude see?
  3. The run reaches its turn limit. What does your CI script receive, and what should it do?
  4. A colleague changes the mode to bypassPermissions so that "nothing can get stuck on a prompt". Which of your protections still hold, and what did the change open up?

You can complete this on paper from the tables in this lesson. Running the result is optional and needs the claude-agent-sdk package and an API key.

Requirements

  • The agent can read and search the repository but cannot edit files, run shell commands or use the web.
  • Nothing is loaded from settings files on the runner or in the repository. Review conventions are given in the system prompt.
  • The comment tool runs without asking, and no other call can ever wait for an approval.
  • A subagent named security-reviewer exists, with its own prompt and read-only tools.
  • Every tool call, including calls made inside the subagent, is written to the CI log.
  • The comment tool may be called at most 10 times in a run. A further attempt is refused with a reason that Claude can read.
  • The run stops after 25 tool-use turns or about 2 US dollars of spend, whichever comes first.

Expected behaviour

build_options returns options with setting_sources=[], a tools list holding only Read, Grep, Glob and Agent, the review server in mcp_servers, an allowed_tools list with the three read tools and mcp__review__post_review_comment, permission_mode="dontAsk", an agents entry for security-reviewer, two PreToolUse hooks (one with no matcher for logging and one matched on the comment tool for the limit), max_turns=25 and max_budget_usd=2.0.

The answers in brief: (1) nothing runs, because Bash is not in tools and Claude never sees it; (2) step 1, where the hook denies and Claude receives the reason as the tool result; (3) a result with subtype error_max_turns and no result text, which CI should report as an incomplete review; (4) the missing tools, the hook and the limits still hold, but every available tool that dontAsk would have refused is now approved.

Hint 1

Ask of each requirement whether it concerns availability, permission or policy. Availability is the tools option, permission is allowed_tools plus the mode, and a policy such as a call limit needs a hook.

Hint 2

A PreToolUse matcher is compared with the tool name, and an MCP tool's name has the form mcp__server__tool.

Hint 3

A HookMatcher with no matcher runs for every tool call.

Hint 4

Hook input for a call made inside a subagent carries an agent_type field, which you can read with get.

Show solution
python
import asyncio
import itertools

from claude_agent_sdk import (
    AgentDefinition,
    ClaudeAgentOptions,
    ClaudeSDKClient,
    HookMatcher,
    ResultMessage,
    create_sdk_mcp_server,
    tool,
)

MAX_COMMENTS = 10
COMMENT_TOOL = "mcp__review__post_review_comment"


@tool("post_review_comment", "Post one review comment on the pull request",
      {"path": str, "line": int, "body": str})
async def post_review_comment(args):
    print(f"COMMENT {args['path']}:{args['line']} {args['body']}")
    return {"content": [{"type": "text", "text": "posted"}]}


def make_comment_limiter(limit):
    attempts = itertools.count(1)

    async def limit_comments(input_data, tool_use_id, context):
        if next(attempts) <= limit:
            return {}
        return {
            "hookSpecificOutput": {
                "hookEventName": input_data["hook_event_name"],
                "permissionDecision": "deny",
                "permissionDecisionReason": f"Limit of {limit} comments reached. Put the rest in your final answer.",
            }
        }

    return limit_comments


async def log_tool_call(input_data, tool_use_id, context):
    print(f"LOG {input_data.get('agent_type') or 'main'}: {input_data['tool_name']}")
    return {}


def build_options(repo_dir):
    review_server = create_sdk_mcp_server(name="review", version="1.0.0", tools=[post_review_comment])
    return ClaudeAgentOptions(
        cwd=repo_dir,
        setting_sources=[],                           # nothing from the runner or the repository
        system_prompt="You review pull requests. Report only problems you can point to by file and line.",
        tools=["Read", "Grep", "Glob", "Agent"],      # no Bash, Edit, Write or web tools exist
        mcp_servers={"review": review_server},
        allowed_tools=["Read", "Grep", "Glob", COMMENT_TOOL],
        permission_mode="dontAsk",                    # nobody is there to answer a prompt
        agents={
            "security-reviewer": AgentDefinition(
                description="Security reviewer. Use for vulnerability review of changed files.",
                prompt="Look for injection, leaked secrets and unsafe deserialisation. Give file, line, severity.",
                tools=["Read", "Grep", "Glob"],
            )
        },
        hooks={
            "PreToolUse": [
                HookMatcher(hooks=[log_tool_call]),   # no matcher: every tool call, subagents included
                HookMatcher(matcher=COMMENT_TOOL, hooks=[make_comment_limiter(MAX_COMMENTS)]),
            ]
        },
        max_turns=25,
        max_budget_usd=2.0,
    )


async def main():
    async with ClaudeSDKClient(options=build_options(".")) as client:
        await client.query("Review the changes on this branch and post your findings.")
        async for message in client.receive_response():
            if isinstance(message, ResultMessage):
                print(f"review finished: {message.subtype}")


if __name__ == "__main__":
    asyncio.run(main())

The hook logic was tested against a stub of the SDK (ten attempts pass, the eleventh is denied). The script was not run against the live API.

Why it is built this way. Each requirement maps to one layer. "Cannot edit or run commands" is availability, so those tools are left out of tools. Claude cannot attempt what it cannot see, and no later setting can bring them back. "Runs without asking" is permission, so the comment tool is on the allow list under its full mcp__review__post_review_comment name. "Nothing can wait" is the mode: dontAsk turns every would-be prompt into a denial. "At most 10" and "log everything" are policy that no rule can express, so they are hooks, and hooks run before every other step.

Answers.

  1. Nothing runs. Bash is not in tools, so it is not in Claude's context. Claude would have to say that it cannot run the tests.
  2. Step 1. The limiter hook returns deny, the tool does not run, and Claude receives the reason as the tool result, so it can put the remaining findings in its final answer.
  3. A ResultMessage with subtype error_max_turns and no result text. The CI script should mark the review incomplete instead of treating silence as approval. Resuming needs the transcript, which is lost with an ephemeral container unless it was saved, so rerunning with a higher limit is the practical route.
  4. The tools missing from tools are still missing, the hooks still run and can still deny, and the turn and budget limits still apply. What changed is that every available tool is approved without a rule, so a second MCP server added later would be usable in full with no allow-list entry. The documentation also says the harness refuses to start in this mode as root outside a recognised sandbox, which is how many CI containers run, so the change may stop the job from starting.

Check your answer

  • Is Bash absent from your tools list, and not merely absent from allowed_tools?
  • Does your allowed_tools entry for the comment tool use the full mcp__review__post_review_comment name?
  • Would the eleventh comment be stopped by a hook, and not by a prompt that nobody can answer?
  • Does your CI script distinguish the success subtype from error_max_turns and error_max_budget_usd?
  • Can you explain why the limit and the logging are hooks instead of rules or a can_use_tool callback?
