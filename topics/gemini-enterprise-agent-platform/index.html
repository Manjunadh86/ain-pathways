Gemini Enterprise Agent Platform

Gemini Enterprise Agent Platform is Google Cloud's platform for building, deploying, governing and evaluating AI agents. It is Vertex AI renamed and extended: a managed runtime that hosts agent code, with session and memory services, per-agent identity and gateway controls, and tracing and evaluation tools around it.

1Overview

Why it matters

An agent that works on a laptop still needs four things before other people can depend on it: a place to run, a place to keep conversation state, an identity whose permissions someone can review, and a way to tell whether its answers are getting worse. You can assemble those from a container service, a database, a service account and a tracing tool, or you can rent them as one platform. This is Google Cloud's version of the second option, and choosing it decides what you operate yourself, what Google operates, and what ties you to one cloud.

The platform is also a naming problem. Its console, documentation, SDKs, command-line flags and API paths use three generations of names for the same resources. An engineer who reads "Agent Runtime" in a design document, reasoningEngines in an audit log and agent_engine in a deploy script needs to know that these are one thing. Engineers who deploy ADK agents, platform and security teams who approve them, and anyone comparing this platform with Amazon Bedrock AgentCore or Microsoft Foundry all need that map.

Key terms

Agent Platform
The short name Google's documentation uses for Gemini Enterprise Agent Platform, the product that was called Vertex AI before April 2026.
Agent Runtime
The managed service that hosts and scales agent code on the platform. It was called Vertex AI Agent Engine before the rename.
reasoningEngine
The API resource type created when you deploy an agent to Agent Runtime. Its name appears in URLs, IAM principals, logs and deletion commands.
Agent Development Kit (ADK)
Google's open-source framework for writing agents in code. It can deploy to Agent Runtime, Cloud Run, Google Kubernetes Engine or any container host.
Session
The stored record of one conversation between a user and an agent, made of ordered events plus temporary state.
Memory Bank
A managed service that uses a language model to extract facts from conversations and keep them across sessions for a given scope.
Scope
The key that a collection of memories belongs to, such as a user ID. Memories are only consolidated and retrieved within exactly the same scope.
Agent Identity
A unique principal given to one deployed agent, so that IAM roles are granted to that agent and its actions can be told apart in logs.
Agent Registry
The catalog of agents, MCP servers and endpoints in a project or organisation that policies can refer to.
Agent Gateway
The managed network component that agent traffic passes through, where access policies and content screening are enforced.

2Explanation

Introduction

In Agent Deployment Architecture you saw what a deployed agent needs around it: a process that stays up, a store for conversation state, credentials for its tools and a record of what it did. In Google Agent Development Kit (ADK) you built an agent that runs on your own machine with adk web and keeps its sessions in memory. Close the terminal and the agent and its sessions are both gone.

Gemini Enterprise Agent Platform is where that agent can go next on Google Cloud. Compare it to moving from cooking at home to renting a licensed commercial kitchen. The recipe, which is your agent code, does not change. What you rent is everything around it: a stove that is always lit (a managed runtime), order tickets that survive a change of shift (sessions and memory), a badge reader on the storeroom door (identity and gateway policies) and an inspector's checklist (tracing and evaluation).

The platform was not built from nothing. Google introduced it in April 2026 as the evolution of Vertex AI (opens in a new tab), its existing machine learning platform, and renamed the agent services that already lived there. Three names are easy to confuse:

  • Gemini Enterprise Agent Platform, shortened to Agent Platform in the documentation, is the developer platform this lesson covers.
  • Gemini Enterprise is a separate product: the application in which employees find and use agents. Agents hosted on the platform can be published into it.
  • ADK is the open-source framework. It is one way to write an agent for the platform, and it can also deploy elsewhere.

Google's overview (opens in a new tab) sorts the platform's parts into four pillars.

This lesson works through those pillars in the order you meet them: what the rename changed, what Agent Runtime does when you deploy, how an ADK agent gets there, how Sessions and Memory Bank keep state, how identity and the gateway control tool access, and how tracing and evaluation close the loop. The worked example then calls a deployed agent and prices a month of traffic.

How it works

What changed from Vertex AI, and what did not

Google's name-change table (opens in a new tab) maps each Vertex AI product to its new name. The release notes entry dated 22 April 2026 states that Vertex AI and Agent Builder are now part of the platform, and the launch post adds that all Vertex AI services and roadmap evolutions will be delivered exclusively through Agent Platform. The rename changed labels in the console and documentation. Most identifiers that you type or read in logs kept their old spelling.

Two habits follow. Search IAM policies, audit logs and quotas by resource type (reasoningEngines) and API host (aiplatform.googleapis.com), because those are stable. And expect sample code to disagree: when this lesson was checked, the quickstart called client.agent_engines.create(...) on a vertexai.Client, the deployment guide called client.runtimes.create(...), and the identity guide imported a newer agentplatform package. All three create the same resource, so follow one page per script and pin the package version it names. The product page itself was headed "Gemini platform" on that day while the documentation kept the full name. Treat names as labels and resource types as the facts.

Agent Runtime: what a deployment is

Agent Runtime hosts your agent code. Deploying creates one reasoningEngine resource named projects/PROJECT_NUMBER/locations/LOCATION/reasoningEngines/RESOURCE_ID. Queries, sessions, memories, the agent's identity and its traces all hang off that name. The deployment guide (opens in a new tab) lists five ways to create it:

MethodWhat you hand overLanguages
Developer ConnectA linked Git repository and a revisionPython
Source filesLocal source sent inline, at most 8 MBPython
DockerfileLocal source plus a DockerfileAny
Container imageAn image in Artifact RegistryAny
SDK objectAn in-memory agent object, pickled and staged in Cloud StoragePython

The two container methods must follow a documented runtime contract. The agent_framework setting accepts google-adk, langchain, langgraph, ag2, llama-index and custom, so the runtime is not tied to ADK.

The same guide documents the settings that decide behaviour and cost: min_instances (default 1), max_instances (default 100), resource_limits (default 4 vCPU and 4 GiB per container) and container_concurrency (default 9; the guide recommends 2 × CPU + 1). These four were marked Preview when this lesson was checked. Environment variables can point at Secret Manager secrets, and a deployment can use a private network interface and a customer-managed encryption key. The April 2026 release notes add long-running operations of up to seven days and sub-second cold starts.

Deploying an ADK agent

There are three documented routes from an ADK project to a reasoningEngine:

  • ADK command line. adk deploy agent_engine packages the agent folder, builds a container and deploys it to the managed Agent Runtime service.
  • SDK. Wrap the agent in AdkApp and call create. This is the quickstart's version, shortened:
python
import vertexai
from vertexai import agent_engines, types
from google.adk.agents import Agent

client = vertexai.Client(project="PROJECT_ID", location="LOCATION")
agent = Agent(model="gemini-3.5-flash", name="currency_exchange_agent",
              tools=[get_exchange_rate])   # get_exchange_rate is a plain Python function
app = agent_engines.AdkApp(agent=agent)

remote_agent = client.agent_engines.create(
    agent=app,
    config={
        "requirements": ["google-cloud-aiplatform[agent_engines,adk]"],
        "staging_bucket": "gs://YOUR_BUCKET",
        "identity_type": types.IdentityType.AGENT_IDENTITY,
    },
)
  • Agents CLI. agents-cli scaffold enhance --deployment-target agent_runtime adds deployment files, CI/CD configuration and Terraform to an existing project, and agents-cli deploy ships it.

A deployed ADK agent exposes named operations, including async_create_session and async_stream_query. You call them through the SDK or over REST at the resource's :query and :streamQuery endpoints.

Sessions and Memory Bank

A session is the ordered record of one conversation: events (user messages, model replies, function calls and their results) plus state that matters only during that conversation. For an ADK agent on Agent Runtime, session storage is handled automatically. An ADK agent running elsewhere can use the same store through ADK's VertexAiSessionService, passing the reasoning engine name as the app name.

Memory Bank holds what should outlive a session (see Agent Memory). When you trigger generation it runs two steps with a language model. Extraction keeps only information that matches the instance's memory topics, which by default cover personal information, preferences, key conversation events and explicit "remember this" instructions. Consolidation compares the result with existing memories in the same scope, for example {"user_id": "123"}, and adds, updates or removes entries. Retrieval returns either every memory in a scope or the closest matches to a query by embedding distance (three by default), and only ever within exactly the scope you pass.

The documentation attaches three warnings. Not every conversation produces a memory. Extraction is not a privacy filter, so assume sensitive details can be stored. And a memory written from a manipulated conversation will be trusted in later sessions, which Google calls memory poisoning (see Prompt Injection and LLM Security).

In ADK you connect Memory Bank with VertexAiMemoryBankService, read it with the preload_memory or load_memory tool, and write to it by calling add_session_to_memory, usually in a callback. Memory Bank needs an Agent Runtime instance to attach to, but the agent itself does not have to run there.

Govern: identity, registry and gateway

Agent Identity gives one deployed agent its own principal instead of a shared service account (see Agent Identity, Permissions and Least Privilege). The format is principal://agents.global.org-ORG_ID.system.id.goog/resources/aiplatform/projects/PROJECT_NUMBER/locations/LOCATION/reasoningEngines/ID. It is based on the SPIFFE standard, its credentials are bound to a certificate so that a copied token cannot be replayed from elsewhere, and you grant IAM roles to it like any principal. You opt in with identity_type=AGENT_IDENTITY. Without that setting the deployment keeps using service accounts.

Agent Registry is the catalog of agents, MCP servers and endpoints that policies refer to. Agents deployed to the runtime are registered automatically.

Agent Gateway is where policy is enforced on the network path. It has two modes: Client-to-Agent for traffic coming in to an agent, and Agent-to-Anywhere for calls an agent makes to tools, MCP servers and other agents. For outbound calls, every check below has to pass, and having no matching access policy means the call is denied. The release notes list Agent Gateway and Agent Registry as generally available since 18 June 2026, and IAM access policies (Google's name is IAM Unified Access Policies) since 31 August 2026.

Content screening is done by Model Armor, which scans prompts and tool responses for prompt injection, sensitive data and harmful content. Semantic governance policies are rules in plain language about how tools may be used. For MCP traffic the gateway can read attributes such as the tool name and whether the tool is read-only, so a policy can allow reading mail and block sending it on the same server.

Optimize: traces, evaluation and monitors

ADK emits OpenTelemetry traces, logs and metrics, and since the June 2026 release tracing is on by default for newly deployed ADK agents on the runtime. The data lands in Cloud Trace, Cloud Logging and Cloud Monitoring, and the console shows per-agent dashboards for sessions, token use, latency percentiles, error rates and per-tool behaviour (see LLM and Agent Observability).

The documented evaluation process (opens in a new tab) is a loop: define eval cases, run them (with simulated users if needed), capture each run as a trace, score traces with automated raters, analyse failures, then change the agent and repeat. On deployed agents you can score chosen traces or whole sessions on demand, or set up an online monitor that samples live traces on a schedule and writes scores to Cloud Monitoring. Evaluating Agents covers the method; the platform supplies the plumbing.

What you pay for

The pricing page (opens in a new tab) bills the runtime on the vCPU-hours and GiB-hours allocated while an agent is working, and does not bill idle time between turns; the deployment guide warns that this idle-time behaviour is subject to change while the customised resource controls are in Preview. Sessions, Memory Bank and gateway calls are counted as operations and converted into vCPU-hours, and the page dates the start of that billing at 13 July 2026 for the gateway and 1 September 2026 for Sessions and Memory Bank. Model tokens are billed separately. The worked example turns these rules into a number.

Worked example: One conversation with a deployed ADK agent over REST, then the runtime bill for 20,000 of them

Part 1: one conversation. The commands and responses come from the ADK documentation's deployment (opens in a new tab) and testing (opens in a new tab) pages, with variables in place of the page's template markers. Reproducing them needs a Google Cloud project with billing enabled.

bash
adk deploy agent_engine \
  --project=$PROJECT_ID \
  --region=us-central1 \
  --display_name="My First Agent" \
  multi_tool_agent

The output ends with the resource name. Its last segment is the resource ID.

text
AgentEngine created. Resource name: projects/123456789/locations/us-central1/reasoningEngines/751619551677906944

Create a session, then send a message in it:

bash
BASE=https://us-central1-aiplatform.googleapis.com/v1/projects/$PROJECT_ID/locations/us-central1/reasoningEngines/$RESOURCE_ID
AUTH="Authorization: Bearer $(gcloud auth print-access-token)"

curl -H "$AUTH" -H "Content-Type: application/json" "${BASE}:query" \
  -d '{"class_method": "async_create_session", "input": {"user_id": "u_123"}}'

curl -H "$AUTH" -H "Content-Type: application/json" "${BASE}:streamQuery?alt=sse" \
  -d '{"class_method": "async_stream_query", "input": {"user_id": "u_123",
       "session_id": "4857885913439920384", "message": "Hey whats the weather in new york today?"}}'

The first call returns the new session:

json
{"output": {"userId": "u_123", "lastUpdateTime": 1757690426.337745, "state": {},
            "id": "4857885913439920384", "appName": "9888888855577777776", "events": []}}

The second streams three events. This is the shape the documentation prints for the Python client, with call IDs removed and long values shortened:

text
{'parts': [{'function_call': {'name': 'get_weather', 'args': {'city': 'new york'}}}], 'role': 'model'}
{'parts': [{'function_response': {'name': 'get_weather', 'response': {'status': 'success', ...}}}], 'role': 'user'}
{'parts': [{'text': 'The weather in New York is sunny ...'}], 'role': 'model'}

The stream is the agent loop made visible: a tool request, the tool result, then the answer. All of it is stored under the session ID, so a later call with the same ID continues the conversation.

Part 2: the bill. The pricing page lists Agent Compute at $0.085 per vCPU-hour and Agent Memory at $0.009 per GiB-hour, with the first 50 vCPU-hours and 100 GiB-hours of each month free per billing account. Session operations cost one vCPU-hour per 1,000,000 writes or 3,000,000 reads, and outbound gateway calls one vCPU-hour per 15,000.

Our assumptions: 20,000 conversations a month like the one above; each keeps a container busy for 8 seconds; no two share a container, which makes this an upper bound; each makes 5 session writes (one create and four events) and 1 read; each sends 2 tool calls through the gateway. Session storage stays under the free 1 GiB, and model tokens are left out. The pricing page counts gateway "API calls or Authorization requests" and we count one per tool call. Counting two per call would give 183.22 vCPU-hours and $12.02 at the default size, and 49.88 vCPU-hours, still free, when resized.

python
VCPU_HOUR_USD, GIB_HOUR_USD = 0.085, 0.009
FREE_VCPU_HOURS, FREE_GIB_HOURS = 50, 100
WRITES_PER_VCPU_HOUR, READS_PER_VCPU_HOUR = 1_000_000, 3_000_000
GATEWAY_CALLS_PER_VCPU_HOUR = 15_000


def monthly_bill(requests, active_seconds, vcpu, memory_gib,
                 session_writes=5, session_reads=1, gateway_calls=2):
    runtime_vcpu_hours = requests * active_seconds * vcpu / 3600
    gib_hours = requests * active_seconds * memory_gib / 3600
    session_vcpu_hours = (requests * session_writes / WRITES_PER_VCPU_HOUR
                          + requests * session_reads / READS_PER_VCPU_HOUR)
    gateway_vcpu_hours = requests * gateway_calls / GATEWAY_CALLS_PER_VCPU_HOUR
    vcpu_hours = runtime_vcpu_hours + session_vcpu_hours + gateway_vcpu_hours
    compute_usd = max(0.0, vcpu_hours - FREE_VCPU_HOURS) * VCPU_HOUR_USD
    memory_usd = max(0.0, gib_hours - FREE_GIB_HOURS) * GIB_HOUR_USD
    return {"vcpu_hours": round(vcpu_hours, 2), "gib_hours": round(gib_hours, 2),
            "compute_usd": round(compute_usd, 2), "memory_usd": round(memory_usd, 2),
            "total_usd": round(compute_usd + memory_usd, 2)}


print("default 4 vCPU / 4 GiB:", monthly_bill(20_000, 8, vcpu=4, memory_gib=4))
print("resized 1 vCPU / 1 GiB:", monthly_bill(20_000, 8, vcpu=1, memory_gib=1))

Edge cases and limitations

Memory generation is selective and is not a privacy filter
Memory Bank stores only what its extraction step judges useful for the configured topics, so a conversation can end with no new memory, and tests that expect one memory per session will fail at random. The documentation also warns that sensitive or personal details may still be stored even though the service is instructed to leave them out. Set a time to live on memories, restrict who can read each scope with IAM conditions, and review stored memories for the data classes you must not keep.
The two gateway modes do not offer the same controls
Client-to-Agent mode is supported only for agents on Agent Runtime, and neither Agent Registry checks nor IAM access policies are available for inbound traffic. On an ingress gateway a semantic governance policy cannot be combined with Model Armor. Agents inside Gemini Enterprise are covered only for outbound calls. Check the mode table in the gateway overview before promising a control to a security reviewer.
Global endpoints, data residency and encryption keys
Choosing an EU location for Memory Bank keeps stored memories in that region, but the documentation says model processing falls back to global Gemini endpoints when the chosen model has no regional endpoint (its examples are Gemini 3 models and Asia single regions). The release notes add that customer-managed encryption keys cannot be used when Sessions or Memory Bank are configured for the global endpoint. If residency is a requirement, confirm the model's regional availability and the endpoint type together.
Console guardrails in Gemini Enterprise do not cover your registered ADK agent
The Gemini Enterprise registration page states that Model Armor settings made in the Google Cloud console for Gemini Enterprise do not automatically protect ADK agents, and that developers must configure Model Armor through the REST API in the agent's own application code. An agent that looks protected because it appears in the employee app may be running without content screening. Test with a known injection string after registering.

When to use it, and when something simpler is enough

Use it when

  • Your agent is written with ADK, LangGraph or another supported framework, your organisation already runs on Google Cloud, and you want sessions, memory and tracing without operating a database and a collector yourself.
  • A security team requires that each agent has its own identity and that tool access is denied by default and granted per MCP server or per tool through reviewable IAM policies.
  • The agent must be offered to employees inside the Gemini Enterprise app, whose registration path for ADK agents requires them to be hosted on Agent Runtime.
  • Conversations need to resume later or carry preferences across sessions, and you would otherwise build extraction, consolidation and per-user isolation of memories by hand.

Think twice when

  • The feature is one stateless model call from an existing service. A direct call to the model API has fewer moving parts and nothing to deploy.
  • The agent has to run outside Google Cloud, on premises or in an environment with no connection to it. Sessions, Memory Bank and Agent Gateway are Google Cloud services; ADK's own documentation points to plain containers for disconnected use.
  • You need direct control of the serving stack, for example to host open-weight models next to the agent. ADK's deployment overview names Google Kubernetes Engine as a good option for that.
  • Your change policy forbids pre-release features and the control you depend on is still marked Preview, as customised resource limits and the Cloud Trace integration for Agent Gateway were when this lesson was checked.

A simpler alternative. Package the ADK agent as a container, run it on Cloud Run, keep sessions in your own database with ADK's DatabaseSessionService and export OpenTelemetry traces to the backend you already use. That is enough for a single agent with a handful of tools. It stops being enough when you need managed long-term memory, one identity per agent with centrally enforced tool policies, or distribution through Gemini Enterprise.

Key takeaways

  • Gemini Enterprise Agent Platform is Vertex AI renamed and extended for agents, so old identifiers such as reasoningEngines, aiplatform.googleapis.com and agent_engine still appear next to the new product names.
  • Deploying to Agent Runtime creates one reasoningEngine resource, and its name is the handle for queries, sessions, memories, identity and traces.
  • Sessions store one conversation as ordered events, while Memory Bank extracts facts with a model and keeps them per scope, so the scope key is what separates one user's memories from another's.
  • Agent Identity gives each agent its own principal, and Agent Gateway denies an outbound call unless an access policy grants that principal the target and content screening passes.
  • Evaluation on the platform runs on traces, so correct OpenTelemetry output from the agent is a precondition for online monitors and for scoring past sessions.
  • Runtime charges follow allocated vCPU and memory multiplied by active seconds, which makes container size the first setting to check when estimating cost.

Example 1 of 5

Color Health's Color Assistant: an ADK agent hosted on Agent Engine, now Agent Runtime

Color HealthDocumented in a case study

Color Health runs a virtual cancer clinic in the United States and launched the Color Assistant with Google Cloud in October 2025. The joint press release describes the technology, a post by Color's president describes the clinical workflow, and Google's April 2026 launch post quotes Color's head of AI platform. [26][27][18][19][7]

The problem

Color's own post names the bottleneck: clinical capacity to identify eligible people and order screens. Before a mammogram can be ordered, someone has to explain why screening matters, collect a history that decides eligibility (risk factors, family history, the date of the last screening, symptoms) and generate an order. Color's president adds that a primary-care history is, at best, a few minutes long, with no time to work through a patient's questions. The press release cites a National Institutes of Health figure that 20 to 30 percent of eligible women in the United States are not up to date on mammograms.

Where this topic fits

The agent sits at the front of the screening pathway and hands over to clinicians. It is written with ADK, uses Gemini 2.5 models and is hosted on what the 2025 press release calls Agent Engine, within Vertex AI, and the 2026 launch post calls Agent Runtime: Google's rename table maps one name to the other. When the conversation ends the agent turns what it heard into a structured assessment and requests a clinical review. Color's clinical team orders any imaging and delivers results.

How it is applied, step by step

  1. A woman opens the screening page and starts a conversation with the agent. In a typical Agent Runtime deployment the request reaches the agent's reasoningEngine and the platform's Sessions service keeps the conversation so far. The sources do not describe Color's session setup.
  2. The ADK agent asks about risk factors, family history, previous screening and symptoms, and answers the user's own questions along the way. The press release describes this as a guided conversation managed by Gemini 2.5 models.
  3. The agent turns what it heard into a structured assessment. Color's post says the agent asks what is relevant and gives clinicians a clear, structured assessment to review in seconds.
  4. The agent requests a clinical review by a clinician in Color Medical's affiliated 50-state medical group, as the press release describes. The release adds that Color's clinical team may order other imaging, and it does not spell out how eligibility is split between the agent and the reviewing clinician.
  5. Per the press release, Color's care teams then contact eligible women to coordinate appointments, and Color clinicians deliver results and coordinate next steps for abnormal findings. The release's opening paragraph also credits the Assistant with scheduling and follow-up, so the exact split is not specified.
  6. A typical ADK deployment of this kind is created with the adk deploy command or the SDK, as the quickstart shows, and produces a reasoningEngine resource. The sources do not say which route Color used.

Why this approach fits

The task is a long interview in which the next question depends on the last answer, which is what an agent framework is for, and its output is a document for a person to review, which limits the harm one wrong step can do. Hosting on a managed runtime suits a small platform team in a regulated field: scaling, patching and the conversation store are the provider's job, so the team can spend its time on the questions the agent asks and on the hand-off to clinicians. The programme also had a fixed end date, and a runtime that follows traffic avoids buying capacity for a campaign whose demand is unknown.

Limitation or tradeoff

The public sources say which platform parts were used but give no architecture, evaluation results or outcome figures. "Tens of thousands" of screenings is the programme's stated aim, not a measured result, and the press release's statements about security are the vendor's own. A managed runtime does not by itself satisfy health-data obligations: agreements with the provider, access controls, retention of conversation records and clinical safety review remain the operator's work. The design as described depends on a clinician reviewing the assessment, so clinician time still bounds throughput. The agent moves the bottleneck from collecting a history to reviewing one.

What the sources document

  • The joint press release says the Color Assistant is powered by the Gemini 2.5 family of models, uses the Agent Development Kit as its agentic framework, and operates within Vertex AI using Agent Engine. [26]
  • The press release says the assistant collects information to determine mammogram eligibility, answers the user's questions and requests a clinical review by a clinician in Color Medical's affiliated 50-state medical group. [26]
  • Color's post says the agent tackles clinical capacity to identify eligible individuals and order screens, and that it turns details given in the user's own words into a structured assessment for clinicians to review. [27]
  • In Google's April 2026 launch post, Color's head of AI platform says the Color Assistant was built with the Agent Development Kit and is scaled via Agent Runtime, and that it engages users to check screening eligibility, connects them to clinicians and helps schedule appointments. [18]
  • The ADK deployment overview describes Agent Runtime as a fully managed auto-scaling service for deploying, managing and scaling agents built with frameworks such as ADK, and Google's quickstart deploys an ADK agent by creating a reasoningEngine resource. [19][7]

The facts above come from the cited sources. The steps and analysis in this example are our explanation of how they fit together.

Example 2 of 5

Payhawk's Financial Controller Agent keeping user habits across sessions with Memory Bank

PayhawkDocumented in an engineering article

Payhawk offers a Financial Controller AI Agent for expense management in its product. Google's April 2026 launch post quotes Payhawk's principal applied AI engineer on its use of Memory Bank, Payhawk's help centre describes what the agent does for employees, and Google's Memory Bank documentation describes the mechanism. [18][28][10][11][12]

The problem

Expense handling repeats itself in ways that are specific to each person: the same categories, the same custom fields, the same kind of receipt every month. In the launch post Payhawk's engineer says the company moved from stateless interactions to long-term context retention, so that its agents can anticipate needs from past behaviour instead of only reacting to prompts. A stateless agent either asks again for details the user has given many times, or guesses.

Where this topic fits

In the pattern the Memory Bank documentation describes, Memory Bank sits beside the agent, outside the model. During or after a conversation the agent sends the conversation's events to Memory Bank, which extracts facts and consolidates them under a scope. At the start of a later conversation the agent retrieves the memories for that scope and places them in its context. Payhawk has not published its own wiring, so this is the documented pattern and not its architecture. Payhawk's help page shows where those conversations happen: employees submit and approve expenses in chat, inside Payhawk's apps or in a connected channel such as Slack.

How it is applied, step by step

  1. An employee submits an expense in chat. The agent guides the submission and asks for required details such as categories and custom fields, as Payhawk's help page describes.
  2. The conversation's events become the source for memory generation. With the platform's Sessions service the source is a stored session; Memory Bank also accepts events passed to it directly.
  3. Generation is triggered. The extraction step keeps only information that matches the configured memory topics, and consolidation merges it with memories already stored for the same scope.
  4. A scope keyed on the user keeps one employee's habits apart from another's, because consolidation and similarity search only consider memories with exactly the same scope. The sources do not say which scope Payhawk uses.
  5. On a later submission the agent retrieves that user's memories, either all of them or the closest matches to the new message, and adds them to its context.
  6. With the habits in context the agent can fill in a submission instead of asking. Payhawk's engineer says the agent now remembers a user's habits to auto-submit expenses.

Why this approach fits

The useful facts here are small, personal and slow to change: preferences and habits. That is the kind of information the default memory topics target, and a few retrieved facts cost far less context than the transcripts of old conversations. Scoping by user gives the isolation a finance product needs without building a store per user. Consolidation matters as well: when a habit changes, the old memory should be replaced and not joined by one that contradicts it.

Limitation or tradeoff

The reduction in submission time is Payhawk's own figure, given in a vendor's announcement without a published method. The sources do not describe Payhawk's memory topics, scope design, retention or review process. A memory written by a model can be wrong, and the documentation warns that not every interaction produces a memory and that sensitive details may be stored. For expenses, a wrongly remembered habit could file a claim under the wrong category without anyone being asked. An agent that submits on the user's behalf therefore needs a confirmation step or an easy reversal, and remembered facts should be visible to the user and correctable.

What the sources document

  • In Google's launch post, Payhawk's principal applied AI engineer says the company used Memory Bank to move from stateless interactions to long-term context retention, and that its Financial Controller Agent now remembers a user's habits to auto-submit expenses. He reports that this reduced submission time by over 50 percent. [18]
  • Payhawk's help centre says the Financial Controller AI Agent guides employees through expense submissions, matches receipts, and lets employees submit and approve expenses in a conversational chat flow. [28]
  • The Memory Bank documentation says generation performs extraction, which persists only information matching the instance's memory topics, and consolidation, which decides whether existing memories in the same scope should be updated or deleted. [11]
  • The documentation says similarity search only considers memories with exactly the same scope as the request and returns three results by default, and that every session must have a user ID to which extracted memories are mapped. [12][10]

Google's mortgage underwriting reference deployment: default-deny, per-tool access to MCP servers

The problem

The agent can reach three tools with very different risk: a document management system, an income verification service and corporate email. An underwriter needs it to read tax returns and verify income. Nobody wants a language model that can send email from the company domain because a document told it to (see Prompt Injection and LLM Security). Writing that rule into the agent's instructions is a request, not a control. The codelab enforces it outside the agent, per tool, with an audit trail, and keeps values such as Social Security numbers out of responses.

Where this topic fits

The gateway sits on the network path between the agent on Agent Runtime and the MCP servers on Cloud Run, in Agent-to-Anywhere mode. The agent carries an agent identity. Each MCP server is registered in Agent Registry, which is also where the agent finds its tools at start-up. Two service extensions are attached to the gateway: one calls Identity-Aware Proxy to check IAM, the other calls Model Armor to screen content (see Guardrails and Content Safety).

How it is applied, step by step

  1. Terraform provisions the network, the three Cloud Run services, a Model Armor template, the Agent Gateway with its two extensions, and registry entries for the MCP servers and the Google APIs the agent needs.
  2. The mortgage agent is deployed to Agent Runtime with agent identity enabled and the gateway attached. It lists MCP servers in the registry at start-up, so no tool URL is written into the agent code.
  3. A script grants the agent's principal the role roles/iap.egressor on specific MCP servers. A server with no grant cannot be reached, because the default is to deny.
  4. On the email server the grant carries an IAM condition that allows only read-only tools, using attributes the gateway extracts from MCP traffic.
  5. The policy runs first in dry-run mode. The agent can still send email, which lets the team compare the policy with real traffic before it can break anything.
  6. Enforcement is switched on. The same follow-up prompt now ends with the agent saying it cannot send the email, while reading documents and verifying income still work.
  7. Model Armor screens content, and the codelab expects Social Security numbers to be redacted in the agent's answer. Traces include spans for the gateway, the IAM check and the content check.

Why this approach fits

The rule "may read mail, may not send it" is about a tool, not about a server or a network address, and only a component that understands MCP traffic can enforce it. Enforcing at the gateway means the rule holds whatever the model is persuaded to attempt, applies to every agent that uses the server, and can be reviewed as an IAM policy by people who never read the agent's code. Dry-run mode matches how access policies are introduced in practice: observed first, enforced second.

Limitation or tradeoff

This is a reference deployment, not a production system, and it shows how much surrounding machinery the control needs: the codelab reports about 40 Terraform resources on its simplest path and requires organisation-level permissions. Its sample extension definitions set failOpen: true with a one-second timeout, so decide what your gateway should do when a policy service does not answer before copying them. Grants are tied to the reasoning engine ID and have to be repeated after a redeploy that creates a new resource. Content screening lowers the chance that injected text or sensitive values get through, but it is a filter with an error rate and not a guarantee.

Continuous evaluation of a deployed ADK agent: OpenTelemetry traces scored by online monitors

Documented in official docs

The platform's evaluation documentation describes online monitors, which score a sample of a deployed agent's live traces on a schedule. The ADK documentation describes the OpenTelemetry spans the framework emits. The two meet in a shared set of span attributes, and the release notes record when tracing became the default for ADK agents on the runtime. [15][25][16][14][4]

The problem

An agent that passed its tests at launch can get worse without a code change: users start asking different things, a tool's data changes, a model version is replaced. The documentation calls this quality drift. Reading traces by hand does not scale, and re-running the offline test set tells you about the test set, not about today's traffic. The team needs a quality signal computed from production conversations, at a cost it can cap.

Where this topic fits

This is the Optimize pillar working on output from the Scale pillar. The agent on Agent Runtime emits traces. Cloud Trace and Cloud Logging store them. An online monitor reads a sample, has the evaluation service score it, and writes results to Cloud Logging and Cloud Monitoring, where the console's per-agent Evaluation view charts them.

How it is applied, step by step

  1. The ADK agent is deployed to Agent Runtime with tracing on. ADK creates an invoke_agent span for each run, with child spans for model calls and tool executions, following the OpenTelemetry conventions for generative AI.
  2. Two environment variables make ADK record message content as events, which the evaluation service needs: an opt-in to the latest generative AI conventions, and a setting that captures message content in events only.
  3. An administrator creates a monitor for the agent, optionally with a filter such as duration or token usage, and chooses the metrics to track, for example safety.
  4. Sampling is set with two numbers: the percentage of live traffic to evaluate and a maximum number of samples per run. The second number is the cost cap.
  5. About every ten minutes the monitor queries the stored traces, scores the sample and reports. Numeric scores go to Cloud Monitoring, where they can sit beside latency and error rate.
  6. When a score drops, an engineer opens the sampled traces from the monitor, reads the rater's rationale on a trace's Evaluation tab, and turns the failing conversations into offline eval cases.

Why this approach fits

Scoring stored traces means the evaluation sees exactly what users saw, tool results included, and adds no latency to the user's request because it runs afterwards. Standard span attributes keep the coupling loose: the evaluation page says trace-based scoring works on traces from production traffic or external logs, so one instrumentation effort can serve offline and online evaluation. A hard cap on samples per run turns evaluation cost from a function of traffic into a budget line.

Limitation or tradeoff

A monitor is only as good as its raters. Scores come from automated raters, many of them model-based, so they carry their own error and should be compared with human labels before an alert is trusted (see LLM-as-a-Judge). Capturing message content puts user text into telemetry storage, which brings retention and access duties. The documentation warns that monitors rely on a project-level service account and that anyone allowed to create one can attach it to any agent in the project, so that permission needs restricting. Sampled, delayed scoring detects drift; it does not stop a bad answer from reaching a user. And when the required attributes are missing, the monitor is active but shows no results.

What the sources document

  • The online monitoring page says monitors run on a scheduled loop, typically every 10 minutes, that samples data from Cloud Trace and Cloud Logging, runs the configured metrics with the evaluation service, writes results to Cloud Logging and exports numeric scores to Cloud Monitoring. [15]
  • It lists the required telemetry: an invoke agent span with gen_ai.agent.name, gen_ai.agent.description and gen_ai.conversation.id, and inference events carrying input messages, output messages, system instructions and tool definitions, enabled in ADK by two environment variables. [15]
  • The ADK documentation says ADK implements the OpenTelemetry semantic conventions for generative AI and emits an invoke_agent span whose key attributes include gen_ai.agent.name, gen_ai.agent.description and gen_ai.conversation.id, alongside spans for tool execution and model calls. [25]
  • The release notes entry for 18 June 2026 states that OpenTelemetry tracing is enabled by default for newly deployed ADK agents on Agent Engine. [4]

4Common mistakes

  1. Leaving the default 4 vCPU, 4 GiB container on an agent that mostly waits for model and tool responses.

    Why it causes problems
    The runtime bills allocated vCPU and memory for every active second, so the default allocation costs four times what one vCPU would for the same traffic. In the worked example the default container produces a charge of 11.80 USD for 20,000 conversations that a 1 vCPU container would run inside the free monthly allowance.
    How to recognise it
    The deployment config has no resource_limits entry, a load test shows the container waiting on model and tool calls instead of computing, and Agent Compute is the largest line of the platform bill.
    How to fix it
    Load test with smaller limits, then set resource_limits and container_concurrency explicitly in the deployment config. These resource controls were marked Preview when this lesson was checked, so confirm their status first.

  2. Deleting and recreating the deployment on every release instead of updating it in place.

    Why it causes problems
    A new reasoningEngine ID means a new agent identity. IAM grants and gateway policies written for the old principal no longer match, so tool calls return 403. A Gemini Enterprise registration still points at the old resource path, and a forced delete removes the managed session resource along with the agent, as the quickstart's clean-up step does.
    How to recognise it
    The number at the end of the resource name changes between releases, and tool calls fail with PermissionDenied straight after a deploy that changed no policy.
    How to fix it
    Keep the resource name in configuration and release with an update to the existing resource, which the deployment guide shows as client.runtimes.update. The principal embeds the resource ID, so an update keeps it; confirm with spec.effectiveIdentity after the first one. Where a new resource is unavoidable, read the new principal from the deployment response and make re-granting access and re-registering part of the same pipeline.

  3. Using one memory scope for every user, or building the scope from text the user can type.

    Why it causes problems
    Retrieval returns whatever is stored under the scope it is given. A shared scope hands one person's remembered details to another, and a scope taken from the message lets a user read someone else's memories by claiming their ID.
    How to recognise it
    The scope dictionary has no user key, a single scope holds facts about several people, or the code that builds the scope reads from the request body instead of the authenticated identity.
    How to fix it
    Build the scope from the authenticated user ID, plus a tenant ID where there are several customers. Restrict access to scopes with IAM conditions and set a time to live on memories.

  4. Leaving the gateway's IAM enforcement in dry-run mode after the testing period.

    Why it causes problems
    Policies are visible in the console and reviews pass, but nothing is blocked. In Google's own codelab the agent sends the email it was supposed to be unable to send for exactly this reason, until the mode is changed.
    How to recognise it
    A call that policy forbids succeeds. The gateway's observability dashboard reports the enforcement mode next to the traffic it lists.
    How to fix it
    Give dry run an end date, switch to enforcement through the same reviewed change process, and keep one automated test that makes a forbidden call and expects a denial.

  5. Creating online monitors or evaluating past traces without the telemetry the evaluation service requires.

    Why it causes problems
    The monitor is active but produces no scores, so the team believes quality is being watched when it is not. The gap is usually noticed only when someone looks for a score after an incident.
    How to recognise it
    The Evaluation view stays empty, and traces in Cloud Trace lack the gen_ai attributes or the message content events that the documentation lists as required.
    How to fix it
    Set the two documented OpenTelemetry environment variables on the deployed agent, confirm the attributes on a fresh trace, and use the monitor's initial inspection step to check that its filter matches traffic.

python
from urllib.parse import urlparse

from gateway_data import BINDINGS, BLOCKED_PHRASES, REGISTRY, REQUESTS


def resolve_target(url, registry):
    """Return (target, entry): a registry name for a registered host, else the URL's origin."""
    parsed = urlparse(url)
    for name, entry in registry.items():
        if entry["host"] == parsed.hostname:
            return name, entry
    return f"{parsed.scheme}://{parsed.hostname}", None


def condition_holds(condition, entry, tool):
    if condition is None:
        return True
    if condition == "read_only_tools":
        return tool is None or (entry is not None and entry["tools"].get(tool, False))
    return False  # an unknown condition never grants access


def policy_denial(principal, target, entry, tool, bindings):
    """Return a reason string when no binding allows the call, else None."""
    matching = [b for b in bindings if b["principal"] == principal and b["target"] == target]
    if not matching:
        return f"no access policy for {target}"
    if not any(condition_holds(b["condition"], entry, tool) for b in matching):
        return f"policy condition not met for tool {tool} on {target}"
    return None


def decide(principal, url, tool, payload, registry, bindings, enforce=True):
    """Return (verdict, reason) for one outbound call from an agent."""
    target, entry = resolve_target(url, registry)
    denial = policy_denial(principal, target, entry, tool, bindings)
    if denial and entry is None:
        return "DENY", f"unregistered destination: {denial}"   # never relaxed by dry run
    if denial and enforce:
        return "DENY", denial
    if any(phrase in payload.lower() for phrase in BLOCKED_PHRASES):
        return "DENY", "content screening blocked the payload"
    if denial:
        return "ALLOW", f"dry run, would deny: {denial}"
    return "ALLOW", f"forwarded to {target}"


if __name__ == "__main__":
    for enforce in (True, False):
        print("enforce" if enforce else "dry run")
        for number, request in enumerate(REQUESTS, start=1):
            verdict, reason = decide(*request, REGISTRY, BINDINGS, enforce=enforce)
            print(f"  {number}. {verdict}: {reason}")

This prints exactly the output shown under expected behaviour.

How the model maps to the platform:

  • Default deny (requests 4 and 5) is documented: with no matching access policy the gateway denies the call. An unregistered destination needs an explicit policy for its URL, which is why request 7 passes and request 4 does not.
  • Per-tool conditions (request 3) mirror the codelab's condition on the tool's read-only attribute. The decision trusts the tool metadata in the registry. Change send_email to True in the data and request 3 is allowed, which is why registered tool specifications deserve review.
  • Identity (request 5) is the whole principal string. A redeploy that changes the last number turns AGENT into a stranger.
  • Dry run (requests 3 and 5 in the second block) forwards the call and records what would have happened. Treat it as a testing stage with an end date.
  • Simplifications. A phrase list stands in for Model Armor. The rule that unregistered destinations stay blocked in dry run follows the codelab's note that the gateway drops them before the identity check, and the real order of checks is not something to rely on.

Map a regulated assistant's requirements to platform components and settings

DesignAdvancedAbout 45 min (estimate)Hypothetical scenario

An insurer in the EU has built a claims assistant with ADK. It answers adjusters' questions about a claim, reads documents through a claims MCP server, and looks up payment status through a payments MCP server, which also exposes a tool that issues refunds. The team wants to move it from a laptop to Gemini Enterprise Agent Platform. These requirements are agreed:

  • R1. Adjusters use the assistant inside the company's Gemini Enterprise app.
  • R2. A conversation can be resumed the next day and can be tied to the insurer's claim number.
  • R3. The assistant remembers each adjuster's working preferences across conversations, never mixes adjusters, and forgets after 90 days.
  • R4. Stored conversations and memories stay in the EU.
  • R5. The assistant may use every tool on the claims server but only read-only tools on the payments server. No other destination is reachable.
  • R6. Prompts and tool responses are screened for prompt injection and leaked personal data.
  • R7. Every action is attributable to this agent, not to a shared account, and access rules are tested before they can block anything.
  • R8. Quality on live traffic is tracked continuously, with a fixed ceiling on evaluation volume.
  • R9. Releases are built from the Git repository and must not break the access rules.

Write a plan as a table with one row per requirement: the platform component, the specific setting or action, and one caveat from this lesson that the team must check. Then list, in order, three things you would verify on the first day after go-live. You need no cloud account for this exercise.

Requirements

  • Every requirement from R1 to R9 is mapped to a named component and a concrete setting or action, not to a pillar name alone.
  • Each row carries a caveat that comes from documented behaviour covered in this lesson.
  • The plan states which identity the access policies are written for and what happens to it on a redeploy.
  • The plan includes a dry-run stage before enforcement and says how the team will know enforcement is on.
  • The three first-day checks are tests with an observable expected result.

Expected behaviour

A complete answer has nine rows that each name something you could point to in a deployment config, a policy or a console screen, for example identity_type set to AGENT_IDENTITY, a memory scope keyed on the adjuster's user ID, or a monitor with a sampling percentage and a maximum number of samples per run. The first-day checks include one forbidden call that must be denied, one test that two adjusters do not share memories, and one confirmation that the monitor is scoring traces.

First-day checks, in order:

  1. A forbidden call is denied. From the Gemini Enterprise app, ask the assistant to issue a refund. Expected: the assistant reports that it cannot, the trace shows a 403 from the IAM check, and the gateway dashboard shows enforcement and not dry run. This comes first because every other control assumes the gateway is really enforcing.
  2. Memories are separated. Sign in as a second adjuster and ask what the assistant remembers about your preferences. Expected: nothing belonging to the first adjuster, and a listing of memories shows one scope per user.
  3. The monitor is scoring. After about twenty minutes of traffic, open the monitor. Expected: sampled traces with scores. If it is empty, look for the gen_ai attributes on a fresh trace before changing anything else.

Why the plan has this shape: the resource name created in R1 is the anchor for R2, R3, R7 and R9, which is why R9's rule about updating in place protects four other rows. R5 and R7 are two halves of one control, since a policy needs a principal to name. And R4 is the row most likely to be answered too quickly: choosing an EU location settles storage, while processing location depends on the model.

Check your answer

  • Does every row name a setting you could find in a config file, a policy or a console screen?
  • Are the policies written for the agent's own principal, and does the plan say what happens when the resource ID changes?
  • Is there a dry-run stage with an end date and a test that proves enforcement is on?
  • Does the memory scope come from the authenticated user and not from text in the conversation?
  • Did you separate where data is stored from where a model processes it?
