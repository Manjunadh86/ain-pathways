Testing Agents (Unit, Integration, Regression)

Testing an agent means using automated checks that can fail a build. Ordinary unit tests cover the tools and the loop, a scripted or recorded model stands in for the real one in multi-step tests, and repeated trials with tolerant assertions cover the real model, whose output varies from run to run.

1Overview

Why it matters

A chat session with an agent proves little. The same prompt can succeed five times and fail on the sixth, a prompt edit can fix one case and quietly break three others, and a tool whose error message changed can stop the model from recovering. Without automated tests, teams learn about these problems from users, reproduce them by hand and hope nothing else regressed. Anthropic's engineers describe exactly this reactive loop in their guide to agent evals.

The opposite mistake is just as common: every test calls a live model, so the suite is slow, costs money on every commit and fails at random until people stop reading it. Most of an agent is ordinary code (tools, argument checks, the loop, step limits, error handling) and can be tested exactly, in milliseconds, with no model at all. Only a thin slice needs the real model, and that slice needs a different kind of test: repeated runs, tolerant assertions and a pass rate instead of one pass or fail. Anyone who ships an agent that touches real data, money or customers needs to know where each kind of check belongs.

What you will be able to do

  • Separate an agent into deterministic code and model calls, and say which kind of test suits each part.
  • Write unit tests for a tool that cover the success path, each rejection path and unchanged state after a rejection.
  • Replace the model with a scripted fake to test error recovery, multi-step flow and step limits offline.
  • Assert on end state, tool-call trajectory and invariants instead of the exact wording of a reply.
  • Record and replay model calls in CI, and recognise when a recording has gone stale.
  • Compute pass@k and pass^k from repeated trials and choose a gate for a regression suite.

Key terms

Test double
Any stand-in that replaces a real dependency in a test, such as a fake database, a stubbed web service or a fake model.
Scripted model
A test double for the language model that returns a fixed list of replies in order, so every run of the test sees the same tool calls. Frameworks ship their own versions under names like fake or test models.
Trajectory
The sequence of messages and tool calls an agent produces on the way to its final answer. Tests compare it with an expected sequence or check rules about it.
Cassette
A file that stores the requests and responses of a real run so a later test run can replay the responses without any network call. The word comes from the VCR family of libraries.
Regression test
A test that keeps a behaviour that once worked, or a failure that was once fixed, from breaking again.
Trial
One complete run of an agent on one task. Because outputs vary, one task is usually run several times.
Flaky test
A test that sometimes passes and sometimes fails on the same code.
pass@k
The chance that at least one of k trials of a task succeeds. It suits cases where one good result is enough.
pass^k
The chance that all k trials of a task succeed, averaged over tasks. It suits agents that must work every time, and it falls as k grows.
Golden baseline
A recorded, human-verified run that later runs are compared against to detect unexpected changes.

2Explanation

Introduction

Testing ordinary code relies on one promise: the same input gives the same output, so a test written today still means something next month. An agent breaks that promise in exactly one place. The language model samples its reply, so the same task can lead to different tool calls on different runs. The rest of the agent keeps the promise: the tool functions, the code that checks arguments, the loop that feeds results back and enforces a step limit.

Think of the agent as two kinds of code. Deterministic code is everything you wrote, including the loop described in The Agent Loop and the tools from Designing Tools for Agents. Model calls are the places where text comes back from a model you do not control. You test the first kind exactly. For the second kind you do one of two things: replace the model with a stand-in whose replies you script, or accept the variation and measure how often the agent does the right thing.

That gives four layers of tests. The lower layers are cheap, fast and numerous; the upper layers are slow, cost money and are few. Each layer catches a different class of bug, and none of them can stand in for another.

Evaluating LLM Applications and Evaluating Agents cover how to measure quality with scores and judges. This lesson is about the pass or fail checks that run in continuous integration (CI), the automated build that runs on every change, and that decide whether a change may merge. The two overlap at the top layer, where an evaluation suite becomes a regression gate.

The lesson walks down the layers, then covers what to assert, how to handle nondeterminism with repeated trials, and how to wire the layers into CI. A worked example builds a small refund agent and tests it with nothing but the Python standard library.

Level 1: unit-test the tools

A tool is a function with a contract: given arguments, return a result or an error the model can read. Test the contract exactly:

  • The success path, including the exact shape of the result.
  • Every rejection path, asserting the exact error text. The model reads that text, and it decides whether the model recovers (see Designing Tools for Agents).
  • That a rejected call leaves state unchanged.
  • That repeating a call is safe or is refused cleanly, because agents do repeat calls.

Write many inputs as a table. The FastMCP documentation (opens in a new tab) shows the pattern for MCP servers: a pytest fixture wraps the server in a client, and a parametrize table feeds arguments to each tool and compares the results. Do not mock your own tool code; fake only the edges: network, clock and randomness. The pytest monkeypatch fixture (opens in a new tab) patches an attribute for one test and undoes it afterwards. The same page shows a global fixture that deletes the requests library's request method, so any accidental HTTP call fails; it covers only requests, so patch the equivalent for your SDK's HTTP library.

Level 2: replace the model with a test double

Framework documentation describes three styles of fake model:

  • A scripted fake returns a list of replies in order. LangChain's GenericFakeChatModel (opens in a new tab) takes an iterator of messages and returns one per call, so you decide every tool call, including bad ones.
  • A function model is a function that receives the messages so far and returns the next reply, so the reply can depend on what the agent showed it. The Pydantic AI testing guide (opens in a new tab) describes FunctionModel this way.
  • A schema-driven stub generates valid arguments from the tools' schemas and calls every tool, as Pydantic AI's TestModel does. It is fast and good for smoke tests, but its values are arbitrary.

Two safeguards belong with any fake. Block real requests globally, as Pydantic AI does with ALLOW_MODEL_REQUESTS = False, so a missing override fails loudly instead of billing you. And make the fake raise an error when called more often than it has replies, so a runaway loop fails the test.

These tests prove that your code handles given replies correctly, not that the real model would produce them; Level 3 and repeated trials cover that.

What to assert

Prefer assertions in this order, because each is more stable than the next:

  1. End state. The database row, the file or the sent message is what the task was for. A reply that says "refunded" proves nothing if the row did not change.
  2. Trajectory. Which tools ran, in what order, with which arguments. The AgentEvals package used in LangChain's agent evals (opens in a new tab) offers four match modes: strict (same calls, same order), unordered (same calls, any order), subset (no tool outside the reference) and superset (at least the reference tools).
  3. Invariants. Rules that must hold on every run, for example "a refund is preceded by a lookup of the same order". Write each as a small function that takes a trajectory, so one rule checks scripted runs now and live runs later.
  4. Structure. Message types, tool names, argument shapes, a non-empty final message. LangChain's integration-testing guidance is to assert on this structure rather than on exact output strings.
  5. Exact wording. Only for text your code fixed, such as an error message from a tool.

Level 3: integration tests with a real or recorded model

An integration test sends real requests to a model API. It checks things no fake can: that credentials work, that the model emits arguments your tool accepts, that latency is acceptable. They are also slow, cost money and vary, so keep them in a separate group excluded from the default run, and run them in CI or before deploy. The LangChain integration-testing page (opens in a new tab) suggests a smaller model for structure-only checks, a cap on output tokens and one behaviour per test.

To run such a test in CI without paying each time, record it once and replay it. The vcrpy library (opens in a new tab) stores HTTP request and response pairs in a cassette file. Its record modes decide what happens next: once replays an existing cassette (raising an error for any new request) and records one when none exists; none never records, so a missing cassette or a new request fails; all re-records everything. In CI, prefer none (check how your pytest plugin selects it), so that a missing cassette fails visibly instead of silently calling, and paying for, the live API.

Three cautions. First, vcrpy's default matching (opens in a new tab) compares only method, scheme, host, port, path and query. Model APIs usually take every call as a POST to one URL, so by default a changed prompt still matches the old recording and replays the old answer; add body to match_on to make the test notice. Second, a request that no longer matches, or a different number of requests than were recorded, fails the test; delete the stale cassette, record again and review the new one like a code change. Third, replay checks your code against one frozen answer and cannot notice that the live model has changed. Filter API keys and authorization headers out of cassettes before committing.

Level 4: regression suites

A regression suite keeps fixed problems fixed, and its raw material is real failures. Rechat's Lucy assistant, described in Hamel Husain's write-up (opens in a new tab), has hundreds of assertion-style tests, updated as new failures appear, and Husain says he often runs that level on every code change. Anthropic's guide to agent evals (opens in a new tab) separates two kinds of suite. Capability evals start with a low pass rate and give the team something to climb. Regression evals should pass at close to 100%, so a drop means something broke. A capability eval with a high pass rate can graduate into the regression suite.

Split the suite by cost. Cheap deterministic checks (Levels 1 and 2, plus replayed recordings) run on every change and block the merge. Costly live-model runs happen nightly, when a prompt or model changes, and before release. A golden baseline is another way to detect change: Google's Agent Development Kit (opens in a new tab) (ADK) records a verified run, then compares later runs against it.

Handling nondeterminism

Variation comes from sampling, from provider-side model updates, from tool results that change (live data, clocks) and, in multi-turn tests, from a simulated user that is itself a model. A fixed seed reduces it but does not remove it: OpenAI's cookbook entry (opens in a new tab) on its seed parameter says determinism is not guaranteed and backend changes can alter outputs. Design tests to tolerate variation:

  • Pin the model version where the provider lets you, and fix everything you control: fixtures, clock, tool outputs.
  • Start every trial from a clean state. Anthropic reports that leftover files and other shared state make failures correlated, and that in some internal evals Claude gained an unfair advantage by reading git history left by earlier trials.
  • Assert on outcomes, run each task several times and judge the rate, not a single run.

Do not retry until green. A task that passes 6 times in 10 passes at least once in three attempts with probability 1−0.43=0.9361 - 0.4^3 = 0.9361−0.43=0.936, so retry-until-pass hides a 60% success rate behind a green build.

With nnn trials of a task and ccc successes, the τ-bench paper (opens in a new tab) gives unbiased estimates of the two standard metrics, averaged over tasks:

from math import comb

def pass_hat_k(successes, trials, k):   # chance that k sampled trials all succeed
    return comb(successes, k) / comb(trials, k)

def pass_at_k(successes, trials, k):    # chance that at least one of k sampled trials succeeds
    return 1 - comb(trials - successes, k) / comb(trials, k)

Take a task with 8 successes in 10 trials. pass_hat_k(8, 10, 3) is 56/120, about 0.467, and pass_at_k(8, 10, 3) is 1.0, because only 2 trials failed, so any 3 include a success. Use pass@k when one good answer is enough, as with generated code that tests can verify. Use pass^k when every run must work, as with an agent that issues refunds. Worked example: Testing a refund agent with no model, from tool test to step limit

The task: an agent can look up an order and issue a refund. We test it at three levels without any model or network. Tools are unit-tested directly. A ScriptedModel drives the real loop through a typo, a recovery and a refund. An invariant function checks the trajectory. Save everything as test_refund_agent.py; it uses only the Python standard library (3.9 or later).

python
import unittest


def fresh_db():
    return {"A-100": {"total": 40.00, "refunded": False},
            "B-200": {"total": 15.50, "refunded": True}}


def make_tools(db):
    def lookup_order(order_id):
        if order_id not in db:
            return {"error": f"unknown order {order_id!r}. Valid ids: {', '.join(sorted(db))}"}
        return {"order_id": order_id, **db[order_id]}

    def issue_refund(order_id, amount):
        order = db.get(order_id)
        if order is None:
            return {"error": f"unknown order {order_id!r}"}
        if order["refunded"]:
            return {"error": "order already refunded"}
        if not 0 < amount <= order["total"]:
            return {"error": f"amount must be between 0 and {order['total']:.2f}"}
        db[order_id] = {**order, "refunded": True}
        return {"ok": True, "refunded": amount}

    return {"lookup_order": lookup_order, "issue_refund": issue_refund}


def run_agent(task, model, tools, max_steps=6):
    messages, calls = [{"role": "user", "content": task}], []
    for _ in range(max_steps):
        reply = model(messages)
        if "final" in reply:
            return {"status": "finished", "answer": reply["final"], "calls": calls}
        name, args = reply["tool"], reply["args"]
        try:
            result = tools[name](**args)
        except (KeyError, TypeError) as error:
            result = {"error": f"bad tool call {name!r}: {error!r}"}
        calls = [*calls, (name, args)]
        messages = [*messages, {"role": "assistant", "content": reply},
                    {"role": "tool", "content": result}]
    return {"status": "step_limit", "answer": None, "calls": calls}


class ScriptedModel:
    """Replays fixed replies and remembers every message list it was shown."""

    def __init__(self, replies):
        self.replies, self.seen = list(replies), []

    def __call__(self, messages):
        self.seen = [*self.seen, list(messages)]
        if len(self.seen) > len(self.replies):
            raise AssertionError("the agent called the model more often than the script allows")
        return self.replies[len(self.seen) - 1]


def lookup_before_refund(calls):
    """Trajectory rule: a refund must follow a lookup of the same order."""
    looked_up = set()
    for name, args in calls:
        if name == "lookup_order":
            looked_up = looked_up | {args["order_id"]}
        if name == "issue_refund" and args["order_id"] not in looked_up:
            return False
    return True


class ToolTests(unittest.TestCase):
    def setUp(self):
        self.db = fresh_db()
        self.tools = make_tools(self.db)

    def test_refund_marks_the_order_refunded(self):
        self.assertEqual(self.tools["issue_refund"]("A-100", 40.0), {"ok": True, "refunded": 40.0})
        self.assertTrue(self.db["A-100"]["refunded"])

    def test_refund_above_total_is_rejected_and_changes_nothing(self):
        self.assertEqual(self.tools["issue_refund"]("A-100", 45.0),
                         {"error": "amount must be between 0 and 40.00"})
        self.assertFalse(self.db["A-100"]["refunded"])

    def test_second_refund_is_rejected(self):
        self.assertEqual(self.tools["issue_refund"]("B-200", 15.5),
                         {"error": "order already refunded"})


class FlowTests(unittest.TestCase):
    def test_recovers_from_a_typo_then_refunds(self):
        db = fresh_db()
        model = ScriptedModel([
            {"tool": "lookup_order", "args": {"order_id": "A100"}},
            {"tool": "lookup_order", "args": {"order_id": "A-100"}},
            {"tool": "issue_refund", "args": {"order_id": "A-100", "amount": 40.0}},
            {"final": "Refunded 40.00 for order A-100."},
        ])
        result = run_agent("Refund order A-100 in full.", model, make_tools(db))
        self.assertEqual(result["status"], "finished")
        self.assertEqual([name for name, _ in result["calls"]],
                         ["lookup_order", "lookup_order", "issue_refund"])
        self.assertTrue(db["A-100"]["refunded"])  # the outcome, not the wording
        self.assertIn("Valid ids: A-100, B-200", model.seen[1][-1]["content"]["error"])
        self.assertTrue(lookup_before_refund(result["calls"]))

    def test_rule_catches_a_refund_without_lookup(self):
        model = ScriptedModel([{"tool": "issue_refund", "args": {"order_id": "A-100", "amount": 40.0}},
                               {"final": "Done."}])
        result = run_agent("Refund A-100.", model, make_tools(fresh_db()))
        self.assertFalse(lookup_before_refund(result["calls"]))

    def test_step_limit_ends_a_model_that_never_finishes(self):
        model = ScriptedModel([{"tool": "lookup_order", "args": {"order_id": "A100"}}] * 10)
        result = run_agent("Refund A-100.", model, make_tools(fresh_db()), max_steps=3)
        self.assertEqual((result["status"], len(result["calls"])), ("step_limit", 3))


if __name__ == "__main__":
    unittest.main()

Run python3 -m unittest test_refund_agent -v. All six tests pass; the last lines are:

text

What to notice:

  • The flow test never asks what the model said, only what happened. It checks the status, the order of tool calls and the database row. It also checks that the second model call was shown the error with the valid ids, which proves the loop returns tool errors to the model.
  • The scripted model fails loudly. In the step-limit test it holds 10 replies, but the loop stops after 3 calls. A loop that ignored max_steps would exhaust the script and raise the AssertionError.
  • Break it on purpose. Replace if order["refunded"]: in issue_refund with if False: and rerun. One test fails with {'ok': True, 'refunded': 15.5} != {'error': 'order already refunded'}, and the other five pass. A test that cannot fail when the code is wrong is worth nothing, so check yours this way.
  • What this suite cannot see. Every model reply was written by us. Whether a real model asks for A100 or A-100, and how often it forgets the lookup, is unknown until you run it many times. The next step is to point the same flow test at a recorded or live model and apply lookup_before_refund to every trial.

Edge cases and limitations

A passing test can leave branches unexercised
A fake or stub decides which branches of your code run. If the arguments it generates always send a tool down one branch, the other branch is never executed, and the test count looks healthy while a bug waits there. Measure coverage of the tool and loop code, not just the number of tests, and use the break-it-on- purpose check from the worked example on the branches you care about.
The script encodes your guess about the model
A scripted reply says the model will send the amount as the number 40.0 and spell the id correctly. A real model may send "40.00" as a string or invent an id. If the fake is more forgiving than the real tool schema, tests pass and production fails. Validate scripted replies against the tool's schema, build scripts from real traces, and keep a few recorded or live tests whose arguments come from a real model.
Replayed tests cannot see the model change
A cassette freezes one answer. If the provider updates the model behind an alias, replayed CI stays green while live behaviour drifts. In the other direction, LangChain's documentation warns that after you change a prompt, add a tool or alter the expected trajectory, saved cassettes become outdated and tests fail until you re-record. vcrpy's default matching ignores the request body, so check that your matcher includes it, or a changed prompt may replay the old answer. Treat replay as a check of your code and schedule live runs to check the model.
Few trials give noisy pass rates
A success rate estimated from n trials has a standard error of about $\sqrt{p(1-p)/n}$. At p = 0.8 and n = 10 that is roughly 0.13, so a drop from 80% to 70% is inside the noise. Use more trials for the tasks that matter, compare with a stored baseline using a margin, and look at which tasks changed before reacting to the suite average.
Strict trajectory matching punishes harmless variation
An exact tool order fails when the model checks two independent facts in the opposite order or adds a harmless extra lookup. LangChain's AgentEvals offers strict, unordered, subset and superset modes for this reason. Use strict only where order is a rule, such as a policy lookup before an authorisation, and prefer an invariant function over a full reference trajectory when only one rule matters.
Shared state makes tests depend on each other
If trials or tests reuse one database, one working directory or one cache, one run can cause the next failure or leave behind help for the next success, and results then depend on execution order. Build fresh state in every unit test (as setUp does in the worked example) and start every live trial from a clean environment, so that a pass rate measures the agent and not the leftovers.

When to use it, and when something simpler is enough

Use it when

  • The agent's tools change state or cost money, so a regression is expensive. A tool unit test and a scripted flow test take minutes to write and then run on every change.
  • Prompts, tools or the model version change regularly and you need to know whether a change broke something that used to work.
  • A failure has already reached a user. Turn it into a permanent regression case. Husain's write-up says Rechat's team continuously updates its tests from the new failures it observes.
  • The agent must work every time, as with refunds, bookings or data changes. Invariant checks and a pass^k gate express that requirement directly.

Think twice when

  • You want to know how good or helpful the answers are. That is a graded evaluation with rubrics, judges or human review, not a pass or fail unit test.
  • The only available assertion is the exact wording of free text from a model. The test will fail on harmless rephrasing and teach the team to ignore red builds.
  • The suite would call a live model on every commit and take minutes or cost real money. Schedule it and gate merges on the fast layers instead.
  • The project is a throwaway demo with no users and no side effects. Manual checks are cheaper there.

A simpler alternative. A few tool unit tests plus one scripted flow test, run by a single command such as `python3 -m unittest` or `pytest`, together with a saved list of 10 to 20 real prompts that failed before, re-run by hand before each release. This stops being enough when prompts or models change weekly, when several people edit the agent, or when the manual re-run takes longer than writing the automated check.

Key takeaways

  • Most of an agent is ordinary deterministic code, so test the tools and the loop exactly with no model, and keep live-model calls to a thin top layer of tests.
  • A scripted or function-based fake model lets you drive the real loop through error recovery, malformed replies and step limits offline, but it proves only that your code handles those replies, not that the real model produces them.
  • Assert on end state first, then on the tool-call trajectory and invariants, and last on wording, and pick the trajectory match mode (strict, unordered, subset or superset) to fit how much order matters.
  • Record and replay model calls so integration tests are cheap and repeatable in CI, treat a stale recording as a prompt to re-record and review, and still run the live model on a schedule.
  • Turn every real failure into a regression case, run the cheap checks on every change, and reserve costly live-model suites for nightly runs and for changes to prompts or models.
  • Because outputs vary, run each task several times and judge pass rates: pass@k when one success is enough and pass^k when every run must succeed. Retrying until the build is green hides unreliability.

Example 1 of 5

FastMCP tests an MCP server's tools through a pytest client fixture

FastMCPDocumented in official docs

The FastMCP documentation page "Testing your FastMCP Server" (its header shows version 4.0.5) explains how the maintainers recommend testing an MCP server and the tools it exposes. [2]

The problem

An MCP server exposes tools that an agent calls over a protocol. Trying them by hand in a separate inspector tool after every change is slow and cannot be repeated automatically. The contract of a tool (arguments in, result out) is deterministic, so it should be checkable by an automated test in which no language model takes part.

Where this topic fits

This is Level 1 of the lesson. The test sits below the agent: a pytest fixture opens a FastMCP client on the server, each test calls a tool by name through that client and compares the returned data with an expected value. No model is involved, so nothing depends on how a model would phrase a request.

How it is applied, step by step

  1. Install pytest-asyncio and set pytest's asyncio mode to auto, so async test functions and fixtures need no decorator.
  2. Write a fixture that opens a FastMCP Client on the server object and yields it. Every test then receives a connected client, and the developer no longer needs a separate tool such as MCP Inspector to try the tools.
  3. Call list_tools through the client and assert how many tools the server exposes, or compare the whole listing with a stored snapshot.
  4. Use pytest's parametrize decorator to run one test over a table of argument sets. Each case calls the tool with call_tool, giving a name and an arguments mapping, and asserts the type and value of the returned data.
  5. Assert large server responses with inline-snapshot, and use dirty-equals for values that change between runs.

Why this approach fits

Tools are the one part of an agent that is fully deterministic and fully yours, so a plain table of inputs and expected outputs gives exact, instant feedback. Calling through the client rather than the bare function also exercises the tool as the server registers it, with its name and arguments, which is how an agent would reach it.

Limitation or tradeoff

These tests prove the tool contract and nothing more. They cannot show that a model will choose this tool, fill in its arguments correctly or recover from its error text, and no assertion on results checks the tool description that the model reads. Those questions belong to the scripted-model and live-model layers.

What the sources document

  • The page recommends combining the FastMCP Client with pytest to test servers, and installing pytest-asyncio with the asyncio mode set to auto in the pytest configuration. [2]
  • Its fixture example wraps the server in a Client and yields it. The page says this enables a tight development loop because it avoids using a separate tool such as MCP Inspector during development. [2]
  • Its parametrize example calls a tool named add through call_tool with a name and an arguments mapping over three pairs of numbers, then asserts that the returned data is an integer equal to the expected sum. [2]
  • It recommends the inline-snapshot library for asserting complex data structures coming from the server, and the dirty-equals library for flexible assertions on dynamic or non-deterministic values. [2]
  • It points to the FastMCP repository, which it says contains thousands of tests for the client and server, as a source of examples. [2]

Pydantic AI swaps the model for TestModel or FunctionModel in agent unit tests

PydanticDocumented in official docs

The Pydantic AI documentation page "Unit testing", hosted by Pydantic, sets out a testing strategy for agents built with the library and walks through a weather-forecast agent that has a tool and a database. [1]

The problem

The weather agent calls a language model, which would add usage cost, latency and variability to every test run. Its tool also branches on whether the requested date is in the past or the future. The authors want to exercise the application code, including the function that stores results in a database, without calling a real model and without rewriting the application so that test objects can be passed in.

Where this topic fits

This is Level 2. During the test the agent's model is replaced with a test double through the Agent.override context manager, so the application function under test runs unchanged. Before it comes the pytest harness and a global switch that blocks real model requests; after it come assertions on the stored result and on the captured messages.

How it is applied, step by step

  1. Set models.ALLOW_MODEL_REQUESTS to False, so that any accidental call to a real model raises an error instead of reaching a provider.
  2. Run the application function inside a with block that overrides the agent's model with TestModel. TestModel calls every tool with arguments it generates from the tool's schema and then returns a text or structured reply.
  3. Use capture_run_messages to record the exchange between the agent and the model, and assert on the request, the tool call and the tool result. Use dirty-equals' IsNow for timestamps.
  4. Read the captured messages and notice that TestModel passed a date in the past, so the future-date branch never ran. A passing test left that branch unexercised.
  5. Write a FunctionModel function that reads the messages. On the first call it extracts a date from the prompt and returns a tool call; on the second it wraps the tool's return value in a text reply. Assert on what the application stored.
  6. Move the override into a pytest fixture so that many tests share it.

Why this approach fits

The approach keeps the application code as written and replaces the single nondeterministic dependency. TestModel gives a cheap smoke test of the whole wiring. FunctionModel lets the test choose the arguments, so it can steer the tool into exactly the branch the test wants to cover.

Limitation or tradeoff

The page's own example shows the main hazard: the generated date was in the past, one branch of the tool went untested, and the test still passed. The doubles also say nothing about how the real model behaves, TestModel cannot emulate provider-executed native tools (they must be overridden away), and the class and argument names are specific to the library version.

  • The page recommends pytest as the harness, TestModel or FunctionModel in place of the real model to avoid the usage, latency and variability of real LLM calls, Agent.override to replace the model, dependencies or toolsets inside application logic, and ALLOW_MODEL_REQUESTS=False set globally to block accidental requests. [1]
  • By default TestModel calls all the agent's tools and then returns plain text or a structured response. The page says it contains no ML or AI and uses procedural Python to generate data that satisfies each tool's JSON schema. [1]
  • In the page's example TestModel called the weather tool with a date in the past, so WeatherService.get_forecast was never called, and the page therefore turns to FunctionModel to exercise the tool fully. [1]
  • The page shows capture_run_messages for asserting the exchange between agent and model and dirty-equals helpers such as IsNow for timestamps, and it states that TestModel cannot emulate provider-executed native tools. [1]

LangChain separates fake-model unit tests, live integration tests and recorded replays

LangChainDocumented in official docs

LangChain's documentation has a Test section for agents built with create_agent. Its unit-testing and integration-testing pages describe fake chat models, in-memory state, pytest markers, structural assertions and HTTP record and replay with vcrpy. [3][4][6][7]

The problem

Agents built with LangChain call model APIs whose answers differ between runs, whose calls cost money and need credentials, and which are much slower than ordinary tests. Teams still need a suite that runs often in CI and catches broken wiring, without paying for every run and without failing at random.

Where this topic fits

This covers Levels 2 and 3. Unit tests replace the model with a scripted fake and keep conversation state in memory. Integration tests sit above them: they carry a marker that the default run excludes, and they use structural assertions. For builds that run constantly, a recorded cassette stands in for the live API.

How it is applied, step by step

  1. For unit tests, build a GenericFakeChatModel from an iterator of replies (messages or tool calls) so each invocation returns the next scripted item, and pass an InMemorySaver as the checkpointer to simulate several turns on one thread id.
  2. Tag tests that call a real model with a pytest marker named integration, register the marker, and set the addopts option to exclude it by default. Run them explicitly in CI or before deploy.
  3. Assert on structure instead of exact text: that a tool call with the expected name was made, that the last message has the expected type and is not empty, and how many messages there are.
  4. Keep cost down with a smaller model, a cap on output tokens and one behaviour per test.
  5. For tests that run on every build, record the HTTP traffic once with vcrpy and pytest-recording, filter authorization headers and API keys out of the cassette, and replay it on later runs with no network call.
  6. When a prompt, a tool or the expected trajectory changes, delete the stale cassette and record it again.

Why this approach fits

Splitting by marker keeps the default run fast and free, while the integration group still checks what fakes cannot: valid credentials, tool calls emitted by a real model and acceptable latency. Structural assertions survive rephrasing, and a cassette turns a paid, variable call into a repeatable one after the first recording.

Limitation or tradeoff

A cassette freezes one answer, so replay cannot reveal that the live model has changed, and the page itself warns that changed prompts, tools or expected trajectories make saved cassettes fail until they are deleted and re-recorded. vcrpy's documentation says its default matching treats requests with the same URL and method as identical, so for a model API a changed prompt can replay the old answer unless the matcher includes the request body. Structural assertions are also weaker than outcome checks: a test that sees only that get_weather was called does not know whether the final answer was right.

What the sources document

  • The unit-testing page says a fake chat model (GenericFakeChatModel) takes an iterator of responses and returns one per invocation, which makes tests fast, free and repeatable without API keys, and that InMemorySaver lets a test simulate multiple turns. [3]
  • The integration-testing page says integration tests are slower and need API credentials, so they should be kept separate from unit tests with a pytest marker that the default run excludes. [4]
  • It advises asserting on structural properties of the response (message types, tool call names, argument shapes, message count) rather than exact strings, because LLM responses vary between runs. [4]
  • It lists cost controls: a smaller model, a cap on output tokens, one behaviour per test, and running integration tests selectively rather than on every file save. [4]
  • It describes recording HTTP interactions with vcrpy and pytest-recording and replaying them on later runs, and warns that new prompts, new tools or changed trajectories make existing cassettes outdated, so the tests fail until the cassettes are deleted and recorded again. [4][6]

Google ADK checks tool trajectories with test files, evalsets and a recorded conformance baseline

GoogleDocumented in official docs

The Agent Development Kit (ADK) documentation page on evaluation describes how to test agents built with ADK in Python: test files, evalsets, pass criteria, a pytest integration and the adk conformance command. [9]

The problem

The ADK page notes that deterministic pass or fail assertions are often unsuitable for agents because model output varies. Teams still need an automated check that an agent keeps calling the right tools in the right order when code, prompts or models change, and a way to stop a pull request that changes the agent's expected behaviour.

Where this topic fits

This spans Levels 3 and 4. A saved session (user turns, expected tool calls, a reference reply) is run against the agent and scored against thresholds. Small single-session files act as unit tests during development, evalsets with long sessions act as integration tests that run less often, and conformance tests compare the agent with a recorded golden baseline in CI.

How it is applied, step by step

  1. Capture a session, for example with Add current session in the adk web Eval tab, or write a .test.json file holding the user turns, the expected tool uses and a reference final response.
  2. Set pass criteria in test_config.json. Without configuration the tool trajectory must match fully (1.0) and the response similarity must reach 0.8.
  3. Run the cases through the web UI, the adk eval command, or pytest by calling AgentEvaluator.evaluate with the agent module and the path of the test file.
  4. Put several longer sessions in an evalset for multi-turn flows, and run these less often than the quick test files.
  5. For regression, write a spec.yaml per case, record a baseline with adk conformance record, and review the generated recordings and session files. These form the golden baseline.
  6. In CI run adk conformance test. It runs the agent and compares its LLM requests, responses and tool calls with the recorded ones, and it fails on a mismatch, which blocks the pull request.

Why this approach fits

Comparing tool calls is cheap, fast and free of model judgement, so it suits frequent automated checks. The page recommends the trajectory and response-match criteria for CI and regression testing for this reason. Wording is compared with a tolerant similarity threshold instead of equality, and a recorded baseline turns "the agent behaves as it did when we approved it" into a command that fails the build.

Limitation or tradeoff

A trajectory threshold of 1.0 fails on harmless variation such as an extra lookup or a reordering, and a word-overlap score can pass text that overlaps with the reference but is wrong. The page marks conformance Live mode as work in progress and says criteria that need expected tool use or responses are not supported with user simulation. A baseline recorded from a wrong run enshrines the mistake, so a person has to review it.

What the sources document

  • The page says test files, each holding one session of one or more turns, are most effective during development as a form of unit testing, while evalsets that hold several lengthy sessions suit integration tests and are typically run less often. [9]
  • If no criteria are provided, the defaults are tool_trajectory_avg_score at 1.0, requiring a full match of the tool-use trajectory, and response_match_score at 0.8. [9]
  • It shows running evaluations through the web UI, the adk eval command and pytest with AgentEvaluator.evaluate, and says the pytest route lets evaluations join CI/CD pipelines or larger test suites. [9]
  • adk conformance test checks current agent outputs against baseline data recorded earlier. Because it fails on a mismatch, the page says it suits CI/CD, where it can run whenever someone opens a pull request and block code that changes the agent's expected behaviour. [9]
  • The efficiency criteria (tool call count, inference call count, token usage and invocation duration) are reported automatically and never fail an eval. The page suggests comparing them across runs to catch a change that keeps quality flat but doubles token usage. [9]

Example 5 of 5

τ-bench scores customer-service agents by end state over repeated trials with pass^k

Documented in a paper

The τ-bench paper (Yao, Shinn, Razavi and Narasimhan, 2024) describes a benchmark in which a user simulated by a language model talks with a tool-using agent in retail and airline customer-service domains. It also introduces the pass^k metric for repeated trials. [12][10]

The problem

Customer-service agents must follow written policies and change real records correctly, and they must do so every time. One successful run says little when the same task, rerun, can end differently. The authors needed a way to score open-ended conversations objectively and to measure reliability, not only average success.

Where this topic fits

This is the repeated-trials side of Level 4 and the nondeterminism section. Each task is run several times, a grader compares the final database with the single correct outcome, and pass^k then asks how often all k trials succeed.

How it is applied, step by step

  1. Each task gives the simulated user an instruction that fixes identity, intent and preferences, so that only one end state of the database is correct under the domain policy.
  2. The agent talks with the simulated user, calls database API tools and has the policy document in its prompt.
  3. When the episode ends, the grader checks whether the final database equals the unique ground-truth database and whether the agent's messages contain the required information. The conversation wording and the order of read-only calls may differ between trials.
  4. Each task is run n times, with at least 3 trials per task for the main results. With c successes on a task, pass^k is estimated as C(c, k) divided by C(n, k), then averaged across tasks.
  5. The authors report pass^1 and pass^k side by side to separate average success from consistency.

Why this approach fits

Comparing end state tolerates the many different conversations and tool-call orders that reach the same correct result, which is what a nondeterministic agent produces. pass^k matches the demand on a deployed service: a customer expects the refund to be right each time, not on one try out of eight.

Limitation or tradeoff

Many trials are expensive. The paper gives per-task costs of about $0.38 for its gpt-4o agent and $0.23 for its gpt-4 user simulator and says one trial per task in the retail domain costs around 200 dollars. Its 115 retail tasks at those per-task figures come to nearer $70, so read the total as a rough order of magnitude; either way a k=8 gate on every commit is unrealistic. A correct end state is also necessary but not sufficient: the authors note that an agent might issue a return without explicit user confirmation, breaking the policy, and still score 1. The reported scores are for 2024 models and do not describe current ones.

What the sources document

  • The benchmark pairs a user simulated by a language model with an agent that has domain-specific API tools and a policy document, in retail and airline domains. [12]
  • Success is decided by comparing the database state at the end of the conversation with the annotated goal state, and the reward also requires the agent's replies to contain the necessary information. The authors say this leaves room for stochastic variation in the conversation itself. [12]
  • pass^k is defined as the chance that all k i.i.d. trials of a task succeed, averaged across tasks. The paper gives unbiased estimators from n trials and c successes and contrasts it with pass@k. [12]
  • The paper reports that gpt-4o with function calling succeeds on roughly 61% of retail tasks (pass^1) while pass^8 in the retail domain falls below 25%. [12]
  • Anthropic's guide to agent evals restates the idea: pass^k falls as k grows, and with a 75% per-trial success rate the probability of passing three trials is about 42%. [10]

4Common mistakes

  1. Calling a live model in every unit test.

    Why it causes problems
    The suite becomes slow, costs money on every commit and fails at random, so people stop trusting red builds or skip the tests altogether.
    How to recognise it
    The test run takes minutes, the provider bill grows with the number of commits, and failures disappear when the same commit is run again.
    How to fix it
    Use a scripted or function fake in unit and flow tests, block real model requests globally, and move live calls into a marked group that runs in CI before deploy or on a schedule.

  2. Asserting the exact wording of a model's reply.

    Why it causes problems
    A harmless rephrasing, a model update or a changed temperature breaks the test, while a wrong answer that happens to use the expected words passes.
    How to recognise it
    Tests fail after a prompt tweak although the database and the tool calls are right, and the usual fix is editing the expected strings.
    How to fix it
    Assert the end state, the tool-call trajectory and invariants first, then structure such as message types and non-empty content. Keep exact-string checks for text that your own code produces.

  3. Rerunning a failed test until it passes.

    Why it causes problems
    A task that works 60% of the time passes within three attempts about 94% of the time, so the build is green while roughly two users in five would still see the failure on a single attempt.
    How to recognise it
    A rerun-on-failure setting in CI, a habit of pressing the rerun button, or tests that pass only on the second attempt.
    How to fix it
    Run each live task several times, record the pass rate and gate on a rate or on pass^k against a stored baseline. For a flaky deterministic test, quarantine it and fix the cause instead of retrying.

  4. Writing scripted replies once and never checking them against the real tool schema or real traces.

    Why it causes problems
    The fake can send arguments in a shape no real model would, such as a number where the model sends a string. Tests pass while production hits errors that the tests never exercise.
    How to recognise it
    Production traces contain argument shapes or tool orders that no test has, or a scripted reply that the real tool would reject.
    How to fix it
    Validate every scripted reply against the tool's schema in the test helper, build scripts from real traces, and keep a few recorded or live tests whose arguments come from a real model.

  5. Re-recording cassettes or updating a baseline until the build turns green.

    Why it causes problems
    A real regression gets recorded as the new normal, and the suite stops protecting the behaviour it was written for.
    How to recognise it
    Pull requests that change recordings or expected files without explanation, or a baseline that changes in the same commit as the code it checks.
    How to fix it
    Treat a failing replay or conformance test as a question: did behaviour change on purpose? If so, re-record and review the diff in the same pull request with a note saying why. If not, fix the code.

Exercise 1

Build a record-and-replay model and test the refund agent with it

CodingIntermediateAbout 45 min (estimate)Hypothetical scenario

Start from test_refund_agent.py in the worked example and keep it in the same folder. You will write a small version of what vcrpy does for HTTP, but for the model: a recording wrapper and a strict replay model. You need only the Python standard library and no API key.

In a new file cassette_model.py, write:

  • RecordingModel(inner, path): a callable with the same signature as a model (it takes messages and returns a reply). It calls inner, stores each request with its response, and writes the whole list to path as JSON after every call.
  • ReplayModel(path): loads the file. For each call it returns the response of the first unused entry whose recorded request equals the messages. If there is none it raises CassetteMiss, with a message that says no recorded response matches and that the cassette must be deleted to re-record. It never calls a real model.

Then add two tests to the same file. First, record the refund flow from the worked example, using ScriptedModel as a stand-in for a live model, replay it against a fresh database and check the status, the database row and lookup_before_refund. Second, replay with the changed task text "Please refund order A-100." and check that CassetteMiss is raised.

Requirements

  • `RecordingModel` returns exactly what the inner model returns, and the cassette file holds one entry per model call.
  • `ReplayModel` never calls the inner model, and answers each recorded entry at most once.
  • Requests are compared after a JSON round trip, so the comparison works for dicts, lists, strings and floats.
  • A request that is not in the cassette raises `CassetteMiss` with a message that tells the reader how to fix it.
  • The replayed run returns the same status, calls and answer as the recorded run.

Expected behaviour

Both tests pass. The cassette written in the first test holds 4 entries, one per model call of the scripted flow. In the second test the very first replayed call fails, because the task text is part of the first request. The message reads: no unused recorded response for a request with 1 messages (the cassette holds 4 entries). Delete the cassette to re-record.

Hint 1

Write the file with `json.dumps(entries, indent=2, sort_keys=True)`, and pass each new request through `json.loads(json.dumps(messages))` before comparing, so both sides went through the same round trip.

Hint 2

Keep the set of used entry indexes inside the replay model, so a request that was recorded once cannot be answered twice.

Hint 3

Use `tempfile.TemporaryDirectory()` so the tests leave no files behind.

Show solution

Save this as cassette_model.py next to test_refund_agent.py.

python
import json
import tempfile
import unittest
from pathlib import Path

from test_refund_agent import ScriptedModel, fresh_db, lookup_before_refund, make_tools, run_agent


class CassetteMiss(Exception):
    """Raised by ReplayModel when a request is not in the cassette."""


class RecordingModel:
    def __init__(self, inner, path):
        self.inner, self.path, self.entries = inner, Path(path), []

    def __call__(self, messages):
        reply = self.inner(messages)
        self.entries = [*self.entries, {"request": messages, "response": reply}]
        self.path.write_text(json.dumps(self.entries, indent=2, sort_keys=True))
        return reply


class ReplayModel:
    def __init__(self, path):
        self.entries = json.loads(Path(path).read_text())
        self.used = frozenset()

    def __call__(self, messages):
        wanted = json.loads(json.dumps(messages))  # the same JSON round trip the cassette went through
        for index, entry in enumerate(self.entries):
            if index not in self.used and entry["request"] == wanted:
                self.used = self.used | {index}
                return entry["response"]
        raise CassetteMiss(
            f"no unused recorded response for a request with {len(messages)} messages "
            f"(the cassette holds {len(self.entries)} entries). Delete the cassette to re-record."
        )


SCRIPT = [
    {"tool": "lookup_order", "args": {"order_id": "A100"}},
    {"tool": "lookup_order", "args": {"order_id": "A-100"}},
    {"tool": "issue_refund", "args": {"order_id": "A-100", "amount": 40.0}},
    {"final": "Refunded 40.00 for order A-100."},
]
TASK = "Refund order A-100 in full."


class CassetteTests(unittest.TestCase):
    def record(self, folder):
        path = Path(folder) / "refund.json"
        first = run_agent(TASK, RecordingModel(ScriptedModel(SCRIPT), path), make_tools(fresh_db()))
        return path, first

    def test_replay_reproduces_the_recorded_run(self):
        with tempfile.TemporaryDirectory() as folder:
            path, first = self.record(folder)
            db = fresh_db()
            second = run_agent(TASK, ReplayModel(path), make_tools(db))
            self.assertEqual(first, second)
            self.assertTrue(db["A-100"]["refunded"])
            self.assertTrue(lookup_before_refund(second["calls"]))
            self.assertEqual(len(json.loads(path.read_text())), 4)

    def test_a_changed_task_misses_the_cassette(self):
        with tempfile.TemporaryDirectory() as folder:
            path, _ = self.record(folder)
            with self.assertRaises(CassetteMiss) as caught:
                run_agent("Please refund order A-100.", ReplayModel(path), make_tools(fresh_db()))
            self.assertIn("Delete the cassette", str(caught.exception))


if __name__ == "__main__":
    unittest.main()

  1. Compute the suite-level pass^k for k = 1, 2, 3 and 5 and pass@3. For one task with ccc successes in nnn trials, pass^k is comb(c, k) / comb(n, k) and pass@k is 1 - comb(n - c, k) / comb(n, k); average across tasks.

  3. Sort the tasks into three groups: regression cases the nightly gate may block on, capability cases to watch and improve, and cases to investigate before trusting the result at all. Justify each choice.
  4. Write the gate rule in one or two sentences, and say what you would change before blocking a release on it.

Requirements

  • Report the five suite-level numbers and the five per-task pass^3 values, rounded to two decimals.
  • Assign every task to exactly one of the three groups and give a one-sentence reason for each.
  • State which metric you gate on (a per-task rate or a suite-level pass^k) and why it fits an agent that issues refunds.
  • Say what the gap between pass^3 and pass@3 means for the team.

Expected behaviour

Hint 1

Compute per task first with `comb(c, k) / comb(n, k)`, then take the mean over the five tasks. Do not compute pass^k from the suite-level success rate.

Hint 2

A task that fails every trial can be a broken task or a broken grader. Check that a reference solution passes the grader before you change the agent.

Hint 3

With only 5 trials, one extra failure moves a task's rate by 20 points. Think about what that does to a gate that blocks on a drop.

Show solution

A short script gives the numbers:

python
from math import comb

TRIALS = 5
SUCCESSES = {
    "full-refund": 5,
    "partial-refund": 5,
    "wrong-order-id-typo": 4,
    "already-refunded-order": 3,
    "refund-above-total": 0,
}


def pass_hat_k(successes, trials, k):
    return comb(successes, k) / comb(trials, k)


def pass_at_k(successes, trials, k):
    return 1 - comb(trials - successes, k) / comb(trials, k)


def suite_average(metric, k):
    return sum(metric(c, TRIALS, k) for c in SUCCESSES.values()) / len(SUCCESSES)


for k in (1, 2, 3, 5):
    print(f"k={k}: pass^k={suite_average(pass_hat_k, k):.2f}  pass@k={suite_average(pass_at_k, k):.2f}")
print()
for name, c in SUCCESSES.items():
    print(f"{name:24} {c}/{TRIALS}  pass^3={pass_hat_k(c, TRIALS, 3):.2f}")

Check that a reference solution passes the grader, that the expected end state is unambiguous and that the tool's rejection message is reachable. Only then change the agent.

Gate rule: the nightly job fails when any regression case drops below its stored 5-of-5 baseline or when a refund-related invariant such as lookup_before_refund is violated in any trial. Suite-level pass^3 is reported on the dashboard but does not block, because it mixes tasks the team has not yet fixed. Before blocking a release, raise the trials per regression task above 5, since a single unlucky trial would otherwise block a release by moving a rate 20 points.

The gap between pass@3 = 0.80 and pass^3 = 0.50 is the average chance that three sampled trials of a task disagree, with some passing and some failing. On those tasks the agent can succeed but does not do so reliably. A customer gets one attempt, not three, so a refund agent is judged on pass^k and not pass@k.

Check your answer

  • Did you average the per-task values rather than compute pass^k from the overall 17 of 25 success rate?
  • Is pass^3 = 0.50 and pass@3 = 0.80 in your output?
  • Did you treat the 0 of 5 task as something to verify before changing the agent?
  • Can you say why a blocking gate on 5 trials per task would block releases for reasons unrelated to the agent?
