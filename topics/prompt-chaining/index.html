Prompt Chaining

Prompt chaining is a workflow in which your code splits a task into a fixed sequence of language-model calls and passes the output of each call to the next one. Between calls, ordinary code can check the intermediate result, a check known as a gate, and decide whether to continue, retry or stop.

1Overview

Why it matters

A single prompt that must extract facts, write copy, respect a length limit and translate the result asks the model to do four jobs at once. When the answer is wrong you cannot tell which job failed, and nothing can be checked until the whole answer exists. A chain gives each model call one job and gives your code a place between calls to catch a bad result before more work is built on it. Many production LLM features that teams call pipelines, such as a text-to-SQL tool or a support bot that checks its own reply, are chains.

The pattern has a price. Every extra call adds its full response time and its tokens, and a mistake in an early step flows into every later step unless a gate stops it. Whoever designs the feature has to decide how many steps the task is worth, what each gate checks and what happens when a check fails. Those three decisions shape accuracy, latency and cost more than the wording of any one prompt.

Key terms

Prompt chaining
Running several model calls in a fixed order, where each call receives the output of the one before it.
Workflow
A system in which the order of model calls and tool calls is fixed in code. In an agent, by contrast, the model decides its own next step.
Step
One model call in a chain. It has its own prompt and one objective, and it can have its own model and settings.
Hand-off
The data passed from one step to the next, usually only the previous step's output in an agreed format such as JSON.
Gate
A check between two steps that inspects the intermediate output and decides whether the chain continues. A programmatic gate is plain code and needs no model call.
Intermediate output
The result of a step that is not the final answer, for example an outline, a list of facts or a draft.
Latency
The time from sending a request to holding the complete result. In a chain the latencies of the steps add up.
Cascading error
A mistake in an early step that is carried into every later step, because each step treats its input as correct.
Retry with feedback
Calling the same step again with the gate's reason for rejection added to the prompt, up to a fixed number of attempts.
Fallback
What the program does when a gate keeps failing, such as stopping with a named error, returning a safe default or handing the case to a person.

2Explanation

Introduction

In What Are AI Agents? you met the split between workflows, where your code fixes the order of the steps, and agents, where the model chooses its own next step. Prompt chaining is the simplest workflow: a straight line of model calls in which the output of one call becomes the input of the next.

You already work this way when a job is too big to do well in one pass. To write a report you draft an outline, check that the outline covers what was asked for, write the text from the outline, and then proofread it. Each stage is easier than producing a finished report from a blank page, and the check after the outline stops you from writing three pages on the wrong structure.

Anthropic's article Building effective agents (opens in a new tab) describes the pattern in the same terms. A task is decomposed into a sequence of steps, each LLM call processes the output of the previous one, and you can add programmatic checks, which the article calls gates, on any intermediate step to confirm the process is still on track. One of its two examples is the report case exactly: write an outline, check that it meets certain criteria, then write the document from it.

A chain has three kinds of part:

  • Steps. Each step is one model call with one objective, such as extracting facts or translating a paragraph.
  • Hand-offs. The data that travels from one step to the next, in a format both sides agree on.
  • Gates. Code between steps that looks at an intermediate output and decides whether the chain goes on.

The same article says what the pattern is for: it trades latency for higher accuracy by making each LLM call an easier task. This lesson covers how to choose the steps, how to write gates and what to do when one fails, how to put numbers on the trade between latency and accuracy, and how a chain differs from the agent loop and from the other workflow patterns.

How it works

A chain is ordinary code

Stripped down, a chain is a loop over a list of prompts. Anthropic's cookbook implements it as a function of a few lines (opens in a new tab) that calls the model once per prompt and feeds each result into the next call. The pseudocode below adds the gate. The worked example is the runnable version.

python
data = task_input
for step in steps:                        # the order is fixed in code
    output = model(step.prompt + data)    # one LLM call, one objective
    if not step.gate(output):             # a programmatic check: plain code
        return handle_failure(step, output)
    data = output                         # hand-off: only this goes to the next step
return data

Three properties follow from this shape:

  • Your code decides what runs next. The model never picks the next step, so every run makes the same calls in the same order, plus any retries. That is what makes a chain a workflow.
  • Each call starts fresh. A step sees its own prompt and whatever you hand it. Unlike the agent loop, no transcript grows from call to call, so prompts stay small and each step can be tested alone with a saved input.
  • Each step is configured separately. Steps can use different prompts, different models and different settings, for example a small fast model for classification and a larger one for writing.

Choosing the steps

  • Give each step one objective. Extract, classify, plan, write, translate and format are different jobs. A step whose prompt contains the word "and" three times is a candidate for splitting.
  • Cut where the result can be checked. A good boundary produces something concrete, such as a JSON object, an outline or a list of table names, that code or a person can inspect.
  • Define the hand-off. Ask for a fixed format (see Structured Outputs) and pass forward everything the next step needs and nothing else. Information dropped at a hand-off is gone for every later step.
  • Keep the chain short. Each step adds latency and one more place to fail. Start from a single prompt and split off a step only when testing shows one identifiable sub-task going wrong.

AWS's guidance on the pattern (opens in a new tab) gives matching reasons for choosing it: you need transparency and control across stages, with intermediate results you can audit, or you want to plug validation, filtering or enrichment logic in between steps.

Gates

A gate takes an intermediate output and returns either a pass or a reason for failing. Gates differ in what they can catch and in what they cost.

Run the cheapest gate first and pay for an expensive one only when the cheap one is not enough. A gate may itself call a model, as long as it returns a structured verdict and your code makes the decision. The OpenAI Agents SDK repository has a small example (opens in a new tab) of this: a checker agent returns two booleans about a story outline, and plain Python stops the flow unless both are true. In the LangGraph documentation the gate is a function on a conditional edge (opens in a new tab) that returns "Pass" or "Fail" and so selects the next node.

When a gate fails

There are four responses, listed from cheapest to most expensive:

  1. Repair in code. Strip a stray code fence or fix a known formatting slip, then run the gate again. No model call is spent.
  2. Retry with feedback. Call the step again with the gate's reason added to the prompt. Cap the number of attempts.
  3. Fall back. Take a simpler path, return a safe default, or hand the case to a person (see Human-in-the-Loop).
  4. Stop. Return a status that names the step and the reason.

The one thing a chain must never do is pass a failed output forward as if it were good.

Trading latency for accuracy

Steps run one after another, so their latencies add. With ℓi\ell_iℓi​ the time of one call of step iii and aia_iai​ the number of attempts it needed:

Lchain=∑i=1nai ℓiL_{\text{chain}} = \sum_{i=1}^{n} a_i \, \ell_iLchain​=i=1∑n​ai​ℓi​

One call takes roughly a fixed wait t0t_0t0​ for the first token plus the output length divided by the generation speed. Take t0=0.6t_0 = 0.6t0​=0.6 seconds and 50 tokens per second as illustrative figures:

The chain is about 2.5 times slower than the single prompt, and one retry adds another 6.6 seconds. Token cost rises in the same way, because every call is billed.

What the extra time buys is an easier task per call. But a chain is only right when every step is right. If step iii produces an acceptable output with probability pip_ipi​, and the steps fail independently, an ungated chain succeeds with probability

Pchain=∏i=1npiP_{\text{chain}} = \prod_{i=1}^{n} p_iPchain​=i=1∏n​pi​

With p=0.95p = 0.95p=0.95 at every step, three steps give 0.953=0.8570.95^3 = 0.8570.953=0.857 and seven steps give 0.957=0.6980.95^7 = 0.6980.957=0.698. So if one large prompt gets the whole task right 70% of the time, a three-step chain of 95% steps is clearly better, and a seven-step chain is slightly worse. Splitting helps only when the product of the step success rates is higher than the success rate of the single prompt.

Gates change the arithmetic. Suppose a gate catches a fraction ccc of the bad outputs and the step is retried once. The step now ends well with probability p+(1−p) c pp + (1 - p)\,c\,pp+(1−p)cp. For p=0.95p = 0.95p=0.95 that is 0.9975 with a gate that catches everything and 0.988 with one that catches 80%.

The model is simplified, since real steps are not independent and real gates miss things, but the directions hold. Each step costs time and reliability. Gates buy reliability back for the price of an occasional extra call, and they turn silent errors into visible stops.

Where chains sit among the other patterns

  • Against a single prompt. Anthropic's prompting guide (opens in a new tab) notes that, with adaptive thinking and subagent orchestration, Claude handles most multistep reasoning internally, and that explicit chaining is still useful when you need to inspect intermediate outputs or enforce a specific pipeline structure. Chain in order to check, enforce or configure steps differently, not to help the model think.
  • Against an agent. In a chain the code fixes the order. In an agent loop the model chooses it. The OpenAI Agents SDK documentation (opens in a new tab) describes orchestrating in code as more deterministic and predictable in speed, cost and performance. Use a chain when the same steps apply to every input.
  • Against the other workflows. Routing adds a branch, parallelization runs independent steps at the same time, and the evaluator-optimizer pattern turns a generate-then-check pair into a loop.

Frameworks offer the chain as a primitive. Google's Agent Development Kit documents a SequentialAgent (opens in a new tab) that runs its sub-agents in listed order without a model deciding anything (the page adds that from ADK 2.0 for Python and Go, templated workflows like this one have been superseded by graph-based and dynamic workflows), and AWS Step Functions ships a starter template (opens in a new tab) whose state machine chains Amazon Bedrock prompts in sequence. None of them is required. Anthropic's advice is to begin with direct API calls, because many of these patterns take only a few lines of code.

Worked example: A three-step chain with gates that turns a release note into a Spanish announcement

The task: turn a four-line internal release note into a customer announcement in Spanish, at most 30 words long, with every number correct. The chain has three steps (extract the facts, draft the announcement, translate it) and a gate after each one. So that everyone gets identical output, the model is replaced by a list of pre-written replies. Everything else is real. The first draft in the script is deliberately too long, so that you can watch a gate reject it.

Save this as chain.py. It needs only the Python standard library.

python
import json
import re

SOURCE = """Tideline 2.4 ships on 14 March.
Offline mode now syncs up to 500 notes.
Search is 3 times faster on large notebooks.
The Android crash on rotate is fixed."""
WORD_LIMIT = 30
MAX_ATTEMPTS = 2


def numbers(text):
    return set(re.findall(r"\d+(?:\.\d+)?", text))


def check_facts(output, step_input):
    try:
        facts = json.loads(output)
    except json.JSONDecodeError:
        return "not valid JSON"
    if not isinstance(facts, dict):
        return "not a JSON object"
    missing = {"product", "version", "changes"} - set(facts)
    if missing:
        return f"missing keys: {sorted(missing)}"
    invented = numbers(output) - numbers(step_input)
    return f"numbers not in the source: {sorted(invented)}" if invented else None


def check_draft(output, step_input):
    count = len(output.split())
    if count > WORD_LIMIT:
        return f"{count} words, the limit is {WORD_LIMIT}"
    invented = numbers(output) - numbers(step_input)
    return f"numbers not in the facts: {sorted(invented)}" if invented else None


def check_translation(output, step_input):
    lost = numbers(step_input) - numbers(output)
    return f"numbers lost in translation: {sorted(lost)}" if lost else None


STEPS = [
    {"name": "extract", "gate": check_facts,
     "prompt": "Extract the facts as JSON with keys product, version, date, changes. "
               "Use only what the text states.\n\n{input}"},
    {"name": "draft", "gate": check_draft,
     "prompt": f"Write a customer announcement of at most {WORD_LIMIT} words "
               "using only these facts.\n\n{input}"},
    {"name": "translate", "gate": check_translation,
     "prompt": "Translate into Spanish. Keep names and numbers unchanged.\n\n{input}"},
]


def run_chain(source, steps, model, max_attempts=MAX_ATTEMPTS):
    data, calls = source, 0
    for step in steps:
        feedback = ""
        for attempt in range(1, max_attempts + 1):
            prompt = step["prompt"].replace("{input}", data) + feedback
            output = model(prompt)                   # one LLM call
            calls += 1
            problem = step["gate"](output, data)     # the gate: plain code, no model
            verdict = "PASS" if problem is None else f"FAIL ({problem})"
            print(f"{step['name']} attempt {attempt}: sent {len(prompt)} chars -> {verdict}")
            if problem is None:
                break
            feedback = f"\n\nYour last answer was rejected: {problem}. Correct it."
        else:                                        # every attempt failed the gate
            return {"status": "stopped", "step": step["name"], "problem": problem, "calls": calls}
        data = output                                # hand-off: only this goes forward
    return {"status": "finished", "output": data, "calls": calls}


def scripted_model(replies):
    remaining = iter(replies)   # stands in for an LLM: one scripted reply per call
    return lambda prompt: next(remaining)


FACTS = json.dumps({"product": "Tideline", "version": "2.4", "date": "14 March",
                    "changes": ["offline mode syncs up to 500 notes",
                                "search is 3 times faster on large notebooks",
                                "Android crash on rotate fixed"]})
LONG_DRAFT = ("We are thrilled to announce that Tideline 2.4 arrives on 14 March. Offline mode "
              "now syncs up to 500 notes, search is 3 times faster on large notebooks, and the "
              "Android crash on rotate has finally been fixed.")
DRAFT = ("Tideline 2.4 arrives on 14 March. Offline mode now syncs up to 500 notes, search is "
         "3 times faster on large notebooks, and the Android rotate crash is fixed.")
SPANISH = ("Tideline 2.4 llega el 14 de marzo. El modo sin conexión sincroniza hasta 500 notas, "
           "la búsqueda es 3 veces más rápida y se corrigió el fallo de Android al girar.")
BAD_FACTS = FACTS.replace("500", "5000")

if __name__ == "__main__":
    print(run_chain(SOURCE, STEPS, scripted_model([FACTS, LONG_DRAFT, DRAFT, SPANISH])))
    print(run_chain(SOURCE, STEPS, scripted_model([BAD_FACTS, BAD_FACTS])))

Run python3 chain.py. The first call to run_chain prints:

text
extract attempt 1: sent 255 chars -> PASS
draft attempt 1: sent 267 chars -> FAIL (38 words, the limit is 30)
draft attempt 2: sent 338 chars -> PASS
translate attempt 1: sent 216 chars -> PASS
{'status': 'finished', 'output': 'Tideline 2.4 llega el 14 de marzo. El modo sin conexión sincroniza hasta 500 notas, la búsqueda es 3 veces más rápida y se corrigió el fallo de Android al girar.', 'calls': 4}

What to notice:

  • Gate 2 caught a real defect. The first draft had 38 words against a limit of 30. The check is one line of arithmetic. Its reason was appended to the retry prompt, which is why that prompt grew from 267 to 338 characters, and the second draft of 29 words passed.
  • Prompts stay small. The four calls sent 255, 267, 338 and 216 characters. Nothing accumulates. The translate step never saw the release note, only the approved draft.
  • Numbers are guarded at every hand-off. Each gate compares the numbers on both sides of its step, so 2.4, 14, 500 and 3 reach the Spanish text unchanged.
  • The trade is visible. One prompt would have been one call. The chain made four, so if each call took 3 seconds it needs about 12 seconds, not 3, in exchange for three checked hand-offs.

The second call to run_chain scripts an extraction that says 5000 notes where the note says 500:

text
extract attempt 1: sent 255 chars -> FAIL (numbers not in the source: ['5000'])
extract attempt 2: sent 336 chars -> FAIL (numbers not in the source: ['5000'])
{'status': 'stopped', 'step': 'extract', 'problem': "numbers not in the source: ['5000']", 'calls': 2}

The chain stopped at the first gate after two calls. The draft and translate steps never ran, so nothing was spent polishing and translating a wrong fact, and the caller gets a status that names the step and the reason.

To use a live model, replace scripted_model(...) with any function that takes a prompt string and returns the reply text. The chain and the gates stay the same.

Edge cases and limitations

The reply wraps the payload in extra text
Models often add a sentence before the data or put JSON inside a code fence. In the saved output of Anthropic's cookbook notebook, the third step of the example chain opens with a sentence introducing its sorted list, and that sentence is handed to the fourth step along with the data. LinkedIn reports the same family of problem: about 10% of its model outputs were invalid against the schema or not valid YAML until a defensive parser patched the common mistakes. Extract the payload in code before the gate runs, and reject what cannot be extracted.
A gate passes an answer that is well formed and wrong
Format and rule checks confirm shape, not truth. Zalando reports that it still sees approximately 10% surface attribution error, where a technology that is merely mentioned in a postmortem is treated as its cause, even with Claude Sonnet 4 and negative examples in the prompt. The post describes such an error as a well-structured, authoritative explanation. List the errors each gate cannot see, sample outputs for human review, and never report a gate's pass rate as the chain's accuracy.
An early mistake is polished by every later step
Each step treats its input as correct, so a wrong fact from step 1 arrives at the end fluent, translated and formatted. The AI Chains study observes that a wrong extraction in the first step could lead to a poor final paragraph. Put the strictest gate after the earliest step, where a failure is cheapest to catch. The worked example does this and stops after two calls.
A hand-off drops something a later step needs
A summary, a pruned schema or a list of extracted facts is smaller than its source by design. If the part that was dropped mattered, no later step can recover it, and the final output still looks complete. When a later step needs original detail, pass the source alongside the intermediate output or fetch the detail from a system of record. Zalando takes figures such as losses and repair times from an internal incident dataset because its pipeline could not extract them reliably.
Retries make the slowest runs far slower than the average
With two attempts per step, a three-step chain makes between three and six calls. Most runs take three, so the average looks fine while the worst case takes twice as long. DoorDash names latency as a notable drawback of its guardrail, since a response may be generated, checked and retried, and says that defaulting to human agents for the relatively small number of problematic responses can keep the user experience good. Set a time budget for the whole chain, cap the attempts per step and choose a fallback that is fast.
A model upgrade makes a step unnecessary
Chains are often built around the limits of one model generation. Uber's QueryGPT article describes large schemas that could break calls to the largest model available at the time, which supported only 32K tokens, and Anthropic's current prompting guide says Claude handles most multistep reasoning internally when adaptive thinking and subagent orchestration are used. After a model change, test whether two steps merged into one call still meet your quality bar. Fewer steps mean less latency and fewer hand-offs to guard.

When to use it, and when something simpler is enough

Use it when

  • The task splits into the same few subtasks for every input, in an order you can write down before seeing the input.
  • An intermediate result can be checked by code or by a person before more work is built on it, for example a parsed object, an outline or a list of tables.
  • Steps need different treatment, such as a small model for classification and a larger one for writing, or prompts owned by different teams.
  • You have to log, audit or evaluate each stage separately, so that a failure can be traced to one step.
  • Testing shows a single prompt failing at one identifiable sub-task, and the user can accept the added seconds.

Think twice when

  • One well-built prompt already meets the quality bar. Extra steps would add only latency, cost and hand-offs.
  • The number or order of steps depends on what earlier steps find. That calls for routing or an agent loop.
  • The response-time budget cannot absorb several sequential calls, as in voice or type-ahead features.
  • The subtasks do not depend on each other. Run them in parallel instead of in a line.

A simpler alternative. A single prompt with clear instructions, a few examples and a structured output format, run on a model that reasons before it answers. It stops being enough when evaluation shows one sub-task failing repeatedly, when an intermediate result has to be inspected or approved, or when the input is too large or too noisy for one call to handle reliably.

Key takeaways

  • A prompt chain is a fixed sequence of model calls in which your code, not the model, decides the order and passes each output to the next step.
  • Good steps have one objective each and end in an output that can be checked, in a hand-off format the next step expects.
  • A gate is code between steps that inspects the intermediate output. On failure the chain repairs, retries with feedback, falls back or stops, and it never passes the bad output on.
  • Latencies add across steps, so a chain is slower and costs more than one call. What it buys is an easier task per call and a checkpoint between calls.
  • Without gates the per-step success rates multiply, so every added step lowers the chance that the whole chain is right. Gates win much of that back.
  • Start with one prompt and add a step only when testing shows a specific sub-task failing and the user can accept the extra seconds.

Example 1 of 5

Uber QueryGPT: a chain of LLM agents that narrows a question down to one SQL query

UberDocumented in an engineering article

Uber's engineering article on QueryGPT (September 2024) describes an internal tool that turns an English question into a SQL query against Uber's data platform. The article compares the first hackathon version, built around one generation call, with the multi-step design that runs in production. [10]

The problem

The first version retrieved a few table schemas and sample queries by similarity search and put them, with the question and Uber-specific instructions, into a single query-generation call. That worked for a handful of tables. As more tables and samples were added, the team saw accuracy decline: a plain similarity search between a question and table definitions did not return relevant results, and going straight from a question to the right schemas proved very hard. Size was the second problem. Some tables span more than 200 columns and could use 40 to 60 thousand tokens in the request, and the article says that three or more of them would break the call, because the largest model available at the time supported only 32K tokens.

Where this topic fits

The current design places three narrow LLM calls in front of the generation call. A question passes through an intent agent, a table agent and a column prune agent, in that order, and only then reaches query generation. Each call reduces what the next one has to consider: first the business domain, then the tables, then the columns. A human check sits in the middle, where the user confirms the table list.

How it is applied, step by step

  1. Every question first goes to the intent agent, an LLM call that maps it to one or more workspaces. A workspace is a curated set of tables and sample queries for a business domain such as Mobility or Ads.
  2. Retrieval then looks for tables and sample queries inside the chosen workspaces only, which the article says drastically narrowed the search radius.
  3. The table agent, a second LLM call, picks the tables for the query. The list is shown to the user, who accepts it or edits it. This is a human gate between two model steps.
  4. The column prune agent, a third LLM call, removes irrelevant columns from the schemas of the confirmed tables and returns a much smaller schema for each.
  5. The final call writes the SQL query and an explanation from the pruned schemas, the sample queries and the question.
  6. To see which step is at fault when a query is wrong, the team scores intent, table selection and the final SQL separately, and also runs a decoupled flow that feeds the correct intent and tables to the later steps.

Why this approach fits

Every question needs the same narrowing in the same order, so nothing is gained by letting a model choose the steps. Each early step is a small classification or filtering job, which the team found models do well, and each one shrinks the input of the next. Pruning columns is an extra model call, yet the article reports that it improved token size, the cost of each LLM call and latency, because the input became much smaller. It gives no figures and does not say whether end-to-end time fell, so treat this as the team's qualitative report. It suggests that an added step can pay for itself when it shrinks the prompts that follow.

Limitation or tradeoff

Errors still cascade. A wrong intent or a wrong table leads to a wrong query however good the final call is, which is why the table list goes to the user and why evaluation is done per step. The article describes no automatic gate on the final SQL. It says the model still sometimes uses tables or columns that do not exist, and it describes a validation step as something the team is looking into. The human gate also means that the documented flow depends on a person being present to confirm the tables.

What the sources document

  • Every incoming question first runs through an intent agent, which uses an LLM call to map the question to one or more business domains (workspaces). The article says that picking a business domain drastically narrowed the search radius for retrieval. [10]
  • A table agent, described as another LLM agent, picks the tables and sends the list to the user, who either accepts it or edits it before query generation. [10]
  • A column prune agent uses an LLM call to remove irrelevant columns from the schemas. The article says this greatly improved token size and the cost of each LLM call, and reduced latency because the input was much smaller. [10]
  • In its learnings the article says the intermediate agents improved accuracy a lot over the first version, and that the intent, table and column prune agents did well because each was asked to work on a single unit of work and not on a broad, general task. [10]
  • The article states that the LLM still sometimes generates queries with tables or columns that do not exist and that a Validation agent is being looked at. From a limited release it reports about 300 daily active users, about 78% of whom say the generated queries reduced their authoring time. [10]

The facts above come from the cited sources. The steps and analysis in this example are our explanation of how they fit together.

Example 2 of 5

DoorDash Dasher support: a generated answer passes a two-tier gate before it is shown

DoorDashDocumented in an engineering article

DoorDash's engineering post on LLM-based Dasher support automation (September 2024) describes the chatbot that answers delivery drivers' questions from knowledge-base articles, and the guardrail that checks every generated answer before the driver sees it. [11]

The problem

A generated support answer can read well and still be wrong. The post lists replies that drift from the knowledge-base content, replies in the wrong language, and actions that do not match the reply text. The check also has to be cheap and fast. The post names latency as a challenge and says larger prompts give slower responses, and its team first tried a more sophisticated guardrail model and found the added response time and token usage prohibitively expensive.

Where this topic fits

A request flows through a fixed sequence: condense the conversation, retrieve knowledge-base articles, generate the reply, then check the reply. The check is the gate at the end of the chain. It is built in two tiers: a cheap in-house similarity check first, and a second model call only when that check flags a reply.

How it is applied, step by step

  1. The system condenses the conversation, which may span several messages, into a summary of the core problem.
  2. The summary is used to find the most similar past cases. Each one points to a knowledge-base article, and those articles are placed into the prompt template.
  3. The model generates a reply from the conversation, the issue summary and the articles.
  4. Gate, tier one: code compares the reply with segments of the knowledge-base articles, using a sliding window and a semantic similarity measure. A close match is taken as a sign that the reply is grounded.
  5. Gate, tier two, only when tier one flags the reply: a prompt holding the reply, the articles and the conversation history goes to an evaluation model, which judges whether the reply is grounded and can give a rationale for debugging.
  6. Only a reply that passes is shown. A failed reply may be regenerated and checked again, and the post says defaulting to human agents for the relatively small number of problematic responses can be an effective way to keep quality high.

Why this approach fits

The order of the gates follows their cost. The similarity check needs no second model call, so a typical implementation pays for the expensive evaluator only when the cheap check gives a reason for doubt. The post also names a failure action in advance: defaulting to human agents for problematic responses. That makes the chain safer to run at volume without requiring every generated answer to be perfect.

Limitation or tradeoff

The post itself names latency as a notable drawback, since the worst case is generate, check, regenerate and check again. Similarity to an article is also only a proxy. A reply can sit close to the article text and still be the wrong advice for this Dasher's situation, and a correct paraphrase can score low and trigger the second tier. The reported reductions are DoorDash's own figures, and the post does not describe how they were measured.

LinkedIn's assistant: a fixed three-step pipeline with a parser guarding the hand-off

LinkedInDocumented in an engineering article

LinkedIn's engineering post Musings on building a Generative AI product (April 2024) describes the assistant that answers members' questions about feed posts and job postings, including its pipeline design and the problems the team met while building it. [12]

The problem

Answering a member's question needs LinkedIn's own data about people, companies and jobs, which the model was never trained on. One model step therefore has to decide which internal APIs to call and write the parameters in a structured format that code can read. The post reports that about one output in ten was wrong at this hand-off: the parameters did not match the schema, or the text was not valid YAML at all, and the code parsing it failed.

Where this topic fits

The product runs a fixed pipeline of three steps: routing, retrieval and generation. The hand-off in question sits inside retrieval, between the model's decision about which API to call and the code that calls it. That is the narrowest point of the chain, where free text has to become machine input, and it is where LinkedIn placed a programmatic check.

How it is applied, step by step

  1. Routing decides whether the question is in scope and which specialised agent should handle it.
  2. In retrieval, the agent's LLM chooses which internal APIs to call. LinkedIn wraps these APIs as skills and asks the model to write the call parameters as YAML.
  3. A defensive YAML parser written by the team processes that output. It detects the mistakes the model commonly makes and patches them in code before parsing.
  4. The APIs are called with the parsed parameters, and their results are collected as grounding for the answer.
  5. Generation, run on a larger model, filters the retrieved data and writes the final response.
  6. Each step has its own evaluation pipeline, so a regression can be traced to routing, retrieval or generation.

Why this approach fits

A format error is the cheapest kind of failure to detect and often the cheapest to fix. The post notes that the usual remedy, asking the model again, costs an extra model call and noticeable latency. Repairing in code costs neither. Keeping the pipeline fixed also let LinkedIn use small models for the two classification-like steps, keep the larger model for writing, and tune each step against its own test data.

Limitation or tradeoff

A parser can only guarantee shape. A call that is valid YAML with the wrong search term passes the gate and feeds the wrong material to generation. The patches also encode the habits of one model, so a model change can bring mistakes the parser has not seen. And the hand-off was not the hard part overall: the post says the last 20% of quality in generation took most of the work, and separately that the team reached 80% of the basic experience in a month and then spent four more months trying to pass 95% of the full experience.

  • Under what worked, the post lists a fixed 3-step pipeline. Routing decides whether the query is in scope and which agent gets it, retrieval is a recall-oriented step in which the agent decides which services to call and how, and generation is a precision-oriented step that filters the retrieved data and produces the final response. [12]

Zalando postmortem analysis: a five-stage LLM pipeline with human sampling between stages

ZalandoDocumented in an engineering article

Zalando's engineering post Dead Ends or Data Goldmines? (September 2025) describes an LLM pipeline that reads thousands of archived incident postmortems and reports recurring failure patterns in the company's datastores. [13]

The problem

A person needs 15 to 20 minutes to read one postmortem carefully, so questions that span thousands of documents, such as why datastores fail repeatedly at scale, could not be answered quickly. A notebook tool that summarised documents cut reading time but was still too slow at this scale and, according to the post, hallucinated and lost incident context. The team also observed that very long inputs suffer a lost-in-the-middle effect, in which details in the middle are overlooked or distorted.

Where this topic fits

The whole analysis is one chain. Each postmortem passes through Summarization, Classification and Analyzer. The resulting digests for one technology are combined in a Patterns stage, and an Opportunity stage turns the patterns into investment proposals. Every intermediate output is short, readable text, and people check samples of it between stages.

How it is applied, step by step

  1. Summarization: one call per postmortem produces a structured summary with five fields (issue summary, root causes, impact, resolution, preventive actions). The prompt forbids guessing and requires the summary to say so when something is unclear or missing.
  2. Classification: the summary and a list of technologies go to a call that returns only the technologies with a confirmed direct connection to the incident, or None. The prompt prohibits inference and includes negative examples.
  3. Analyzer: for each classified summary, a call writes a digest of three to five sentences describing the role the technology played in the failure.
  4. Patterns: all digests for one technology are placed in a single prompt, and the model returns a one-page list of recurring failure themes.
  5. Human curation acts as the gate. During development people compared every digest with its original postmortem and voted it up or down. Later this dropped to a random sample of 10 to 20% of each batch, and people still proofread the final report.
  6. An Opportunity stage takes the patterns and the postmortem corpus and produces investment opportunities.

Why this approach fits

Every document goes through the same stages, so a fixed chain is enough. Giving each stage one objective keeps each prompt short and strict, and it produces intermediate text that a person can read in under a minute and compare with the source. The per-document stages are independent of one another, which lets them run as a batch before the single aggregating call. The design also avoids placing thousands of documents into one very large context.

Limitation or tradeoff

The gates here are people, so quality control costs reviewer time and, once the system matured, covers only a sample. Some errors pass every stage: the post says it still observes approximately 10% surface attribution error, where a technology that is merely mentioned is credited with an incident, and that numerical details could not be extracted reliably. Time is a constraint as well. The team set a 120-second ceiling per document, and an early 27B-parameter model took 90 to 120 seconds in its stage, leaving no room to chain several.

AI Chains: a controlled study of chained prompts against a single prompt

Google Research and University of WashingtonDocumented in a paper

The paper AI Chains (Wu, Terry and Cai, CHI 2022) introduces an interactive system in which a task is built as a chain of LLM steps with visible, editable intermediate results. It reports a user study that compares the system with a single-prompt interface running the same model. [14]

The problem

The authors start from three weaknesses of a single LLM run on a complex task: weak multi-step reasoning, errors that build up over a long generation, and sensitivity to how the prompt is phrased. Their walkthrough task is rewriting blunt feedback about someone's presentation into a friendly paragraph with concrete suggestions for each problem. With one prompt, they note, there is no obvious edit that makes the model add suggestions for a problem it has passed over.

Where this topic fits

Chaining is the method under test. The feedback task becomes three steps, each an independent run of the model: split the feedback into separate problems, generate suggestions for each problem, and compose everything into one paragraph. The interface shows the output of every step and lets the person edit it before it flows on, which makes each hand-off a human gate.

How it is applied, step by step

  1. The first step extracts the individual presentation problems from the original feedback as a list.
  2. The second step runs once per problem and generates suggestions for improvement.
  3. The third step composes the problems and the suggestions into one friendly paragraph.
  4. Between steps, each output is parsed into the data type the next step expects, for example a numbered list split into items, and the user can edit any intermediate result.
  5. In the study, 20 participants completed a task with the chained interface and with a single-prompt sandbox, both backed by the same model. Two people who had not taken part then compared the paired results without knowing which interface had produced them.

Why this approach fits

The study isolates the effect of chaining: the model is identical in both conditions, so differences come from the structure. Splitting gave every sub-task a clear goal, and participants used the separate steps like unit tests, tracing a poor final paragraph back to the step that caused it. Some also set a different temperature per step, higher for generating ideas and lower for rewriting, which a single prompt does not allow.

Limitation or tradeoff

The evidence is small and dated: 20 participants, two tasks and a model from 2021, so the size of the benefit should not be assumed for current models. The paper records costs too. Nine participants found the chains more complex, with a steeper learning curve, four had trouble seeing how an edit in one step would affect the final result, and the authors acknowledge the computational overhead of running the model several times, although they judge the saved effort to outweigh it. Completion took slightly longer with chaining, although the difference was not statistically significant.

What the sources document

  • The paper defines Chaining as breaking up complex tasks into smaller steps, where each step can be completed by an independent run of an LLM and the output of one or more steps is used as input for the next. [14]
  • The evaluation was a within-subject study in which 20 participants completed a task using both the Chaining interface and a non-chaining Sandbox interface, with the same underlying LLM (LaMDA, described as a 137 billion parameter model) powering both. [14]
  • Two independent raters, blind to the condition, preferred the Chaining results 85% and 80% of the time, and participants rated Chaining higher for transparency, control, collaboration and helping them think through the task. [14]
  • Participants spent 12.4 minutes on average in Sandbox and 14.6 minutes in Chaining, a difference that a t-test did not find significant. [14]
  • Nine participants noted that Chains, although transparent, were more complex with steeper learning curves, and four had questions about how a change to one data entry would affect the final result. [14]

4Common mistakes

  1. Passing each output to the next step without any check.

    Why it causes problems
    The chain has the latency of several calls and none of the safety. A malformed or wrong intermediate result is treated as correct by every later step, and the final output hides where it went wrong.
    How to recognise it
    Code in which the result of one model call is inserted directly into the next prompt, and defects that are only ever noticed in the final output.
    How to fix it
    Add at least a format gate and a rule gate after every step, starting with the first. Make each gate return a reason, and decide in advance whether a failure means repair, retry, fallback or stop.

  2. Splitting a task into many steps because more steps feels more thorough.

    Why it causes problems
    Latencies add and per-step success rates multiply. Seven steps that are each right 95% of the time are right together about 70% of the time, and the user waits for seven calls.
    How to recognise it
    Steps whose output is never checked or used on its own, adjacent steps that always change together, and an end-to-end success rate below that of the single prompt you started from.
    How to fix it
    Merge steps until every remaining boundary has a reason: a gate that runs there, a different model, or an output someone inspects. Compare the chain with a one-prompt baseline on the same test set.

  3. Treating a passed format check as proof that the content is right.

    Why it causes problems
    Valid JSON with a wrong value passes straight through. The team sees a high gate pass rate and assumes the chain is accurate while users receive confident, well-formed errors.
    How to recognise it
    Gates that only parse and count, a pass rate near 100% alongside user complaints, and no human review of sampled outputs.
    How to fix it
    Add content gates where they are cheap, such as comparing numbers and names with the source. Add a grounding check or a model check for the riskiest step, and review a random sample by hand on a schedule.

  4. Retrying a failed step with the identical prompt, or with no limit on attempts.

    Why it causes problems
    The model receives no new information, so it often repeats the failure, and each attempt adds a full call of latency. Without a cap, a single bad input can hold a request for a long time.
    How to recognise it
    Latency percentiles far above the average, logs with several identical prompts in a row, and the same rejection reason on every attempt.
    How to fix it
    Try a repair in code first. When retrying, append the gate's reason to the prompt, cap attempts at a small number, and define the fallback that follows the last attempt.

  5. Measuring only the final output of the chain.

    Why it causes problems
    When quality drops there is no way to tell which step caused it, so teams rewrite the last prompt even when the first step is at fault, and fixes become guesswork.
    How to recognise it
    A single end-to-end score on the dashboard, no saved intermediate outputs, and arguments about which prompt to change.
    How to fix it
    Log every step's input and output, keep a small test set per step, and evaluate later steps with known-good inputs so that their scores do not depend on earlier steps. Uber and LinkedIn both describe evaluating per step.

  6. Handing the next step loose text instead of a defined format.

    Why it causes problems
    Introductory sentences, code fences and stray commentary travel downstream as if they were data. The next step may summarise the preamble, translate it or fail to parse the payload.
    How to recognise it
    Phrases that introduce a result showing up inside later outputs, and parsing code that keeps gaining special cases.
    How to fix it
    Specify the hand-off format in the prompt, use the structured output feature of your API where it has one, extract the payload in code, and reject anything that does not match.

python
import re

from chain import (DRAFT, FACTS, MAX_ATTEMPTS, SOURCE, SPANISH, STEPS,
                   run_chain, scripted_model)

FENCE = "`" * 3
FENCED_FACTS = f"Here is the JSON you asked for:\n{FENCE}json\n{FACTS}\n{FENCE}"
FENCED_BAD_FACTS = FENCED_FACTS.replace("500", "5000")


def extract_json(output):
    """Return the text from the first { to the last }, or the output unchanged."""
    match = re.search(r"\{.*\}", output, re.S)
    return match.group(0) if match else output


REPAIRS = {"extract": extract_json}


def check_with_repair(step, output, data, repairs):
    """Run the gate. If it fails, try a repair in code and run the gate again."""
    problem = step["gate"](output, data)
    repair = repairs.get(step["name"])
    if problem is None or repair is None:
        return output, problem, 0
    candidate = repair(output)
    if candidate == output:
        return output, problem, 0
    candidate_problem = step["gate"](candidate, data)
    if candidate_problem is None:
        return candidate, None, 1                  # repaired: no extra model call
    return output, candidate_problem, 0            # report the more precise reason


def run_chain_with_repair(source, steps, model, repairs=REPAIRS, max_attempts=MAX_ATTEMPTS):
    data, calls, repaired = source, 0, 0
    for step in steps:
        feedback = ""
        for attempt in range(1, max_attempts + 1):
            prompt = step["prompt"].replace("{input}", data) + feedback
            output, problem, fixed = check_with_repair(step, model(prompt), data, repairs)
            calls, repaired = calls + 1, repaired + fixed
            if problem is None:
                break
            feedback = f"\n\nYour last answer was rejected: {problem}. Correct it."
        else:
            return {"status": "stopped", "step": step["name"], "problem": problem,
                    "calls": calls, "repairs": repaired}
        data = output
    return {"status": "finished", "output": data, "calls": calls, "repairs": repaired}


if __name__ == "__main__":
    before = run_chain(SOURCE, STEPS, scripted_model([FENCED_FACTS, FACTS, DRAFT, SPANISH]))
    print("without repair:", before["status"], before["calls"])
    after = run_chain_with_repair(SOURCE, STEPS, scripted_model([FENCED_FACTS, DRAFT, SPANISH]))
    print("with repair:", after["status"], after["calls"], after["repairs"])
    print(after["output"] == SPANISH)
    print(run_chain_with_repair(SOURCE, STEPS, scripted_model([FENCED_BAD_FACTS] * 2)))

How it works:

  • check_with_repair runs the gate first. A passing output is never touched, so a repair cannot damage a good reply.
  • A repaired text is accepted only after the same gate passes it. The repair is a guess about what the model meant, and the gate is what makes the guess safe.
  • A successful repair returns before the retry logic, so it costs no model call. The fenced reply now takes 3 calls where the original chain took 4.
  • When the repaired text still fails, the helper returns the gate's reason for the repaired text. The fenced reply with 5000 is reported as an invented number, which is the real defect, and not as invalid JSON. That reason is what the retry prompt gives the model.
  • Repair fixes form only. No code can turn 5000 back into 500 without reading the source, so content errors still go to a retry and then to a stop.

One set at the average would cut off every run that needed a retry and went on to finish, which is about one run in five.

Their product is 0.9386. Imperfect gates still lift the chain from 78% to 94%. The loss against perfect gates is more than 4 points of success. With perfect gates every failure is a visible stop, while here most failures are wrong replies that reach the customer, because a bad output that the gate misses is passed on as if it were good.

Part 4. The merged chain has steps of 0.98, 0.84 and 0.96. With perfect gates and one retry they end well with 0.9996, 1 - 0.16² = 0.9744 and 0.9984, a product of 0.9725. The average time is 1.224 + 5.5 × 1.16 + 4.680 = 12.28 s. The proposal meets the 13-second budget and costs 0.9817 - 0.9725 = 0.0092, about 0.9 percentage points of success. It also removes a hand-off and lowers the worst case to 2 × 11.2 = 22.40 s. Notice what happens without gates: the merged chain scores 0.98 × 0.84 × 0.96 = 0.7903, slightly better than the four-step chain's 0.7790. The extra planning step only pays for itself when a gate checks it.

Part 5. One reasonable set of gates:

  • Extract: the output parses as JSON, has the required keys, and any order number in it also appears in the email.
  • Plan: between two and six lines, each starting with a bullet marker and each under a word limit.
  • Draft: within the length limit, every number and name in the draft appears in the extracted JSON, and no unfilled template markers remain.
  • Translate: every number and order number in the draft is still present, and the length is within a sensible ratio of the draft's length.

Check your answer

  • Is your no-gate success rate 0.7790 and your no-gate time 12.70 seconds?
  • Did you get 0.9817, 13.56 seconds on average and 25.40 seconds in the worst case for perfect gates with one retry?
  • Did the merged design come out at 0.9725 and 12.28 seconds?
  • Can each of your four gates run without a model call and return a reason when it fails?
