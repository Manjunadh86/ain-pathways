Microsoft AutoGen (Concepts and Migration)

AutoGen is Microsoft's open-source framework, for Python and .NET, for building applications in which several LLM agents exchange messages to finish a task. It has a high-level AgentChat API of agents and teams on top of an event-driven Core runtime. It is now in maintenance mode, and Microsoft Agent Framework is its successor.

1Overview

Why it matters

AutoGen packaged several ideas that later multi-agent frameworks reuse: a group chat in which a manager picks the next speaker, composable termination conditions, handoffs between specialists, and the Magentic-One orchestrator. Microsoft's own migration guide credits it with pioneering group chat and the event-driven agent runtime. A large amount of code, tutorials and research was written against it. If you inherit one of those codebases, you need to read a team definition and say who speaks next, what every agent can see and what makes the run stop. The common failures map onto those three questions: a team that never terminates, an agent that answers with raw tool output, and a context that grows with every turn because each message is broadcast to everyone.

The second reason is the migration. AutoGen's repository states that it is in maintenance mode and sends new users to Microsoft Agent Framework. The two APIs look alike, which is the danger: an agent translated line by line keeps the same name and instructions but changes how often it calls tools and whether it remembers the previous call. Anyone who maintains AutoGen code, plans a migration, or chooses a framework for a new project needs to know which concepts carry over unchanged and which ones change behaviour.

Key terms

AgentChat
AutoGen's high-level Python API, in the package autogen-agentchat, that provides ready-made agents, teams and termination conditions.
AssistantAgent
The standard AgentChat agent. It wraps a model client, a system message and optional tools, and keeps its own message history between calls.
Team
A group of agents that work on one task by taking turns in a shared conversation, coordinated by a manager that the team creates for you.
Group chat
The pattern in which all agents publish to and read from one common thread of messages, usually with one agent speaking at a time.
Speaker selection
The rule a group chat uses to decide which agent responds next, such as a fixed order, a model's choice or a handoff from the current agent.
Termination condition
An object the team calls after each response with the new messages. It returns a stop message to end the run, or nothing to let it continue.
Handoff
A tool call by which the current agent passes the conversation to a named agent or back to the user.
Agent runtime
The Core component that creates agents when they are needed and delivers messages between them, so agents never call each other directly.
Topic and subscription
A topic is a named channel for broadcast messages. A subscription tells the runtime which agents receive what is published to a topic.
Maintenance mode
A project status in which no new features are added. AutoGen's README says it will not receive new features or enhancements and is community managed.

2Explanation

Introduction

In Multi-Agent Systems you saw why a task is sometimes split across several agents. In Choosing an Agent Framework you saw that frameworks differ mostly in how they decide who acts next and when the work stops. AutoGen made one answer to those questions popular: let the agents talk to each other in a shared conversation.

Picture a short review meeting. A writer proposes a draft, a reviewer comments, and the writer revises. Everyone hears everything that is said. A chair decides who speaks next, and a rule agreed beforehand ends the meeting: the reviewer says "approved", or thirty minutes have passed. AutoGen turns each part of that meeting into an object. The people are agents, the meeting is a team, the chair is a group chat manager, and the closing rule is a termination condition.

AutoGen is built in layers, and most developers only touch the top two.

  • AgentChat is the high-level API. You create agents such as AssistantAgent, put them in a team such as RoundRobinGroupChat, and call run.
  • Core is the event-driven runtime underneath. An agent there is an object that reacts to messages, and the runtime delivers those messages. AgentChat teams are assembled from Core parts.
  • Extensions connect to the outside world: model clients, code executors, Model Context Protocol tools and a gRPC runtime for agents in separate processes.
  • AutoGen Studio and Magentic-One are applications built with these layers.

One fact changes how to read everything else. The project's README (opens in a new tab) opens with a maintenance notice: AutoGen will not receive new features, it is community managed, and new users should start with Microsoft Agent Framework. Microsoft's documentation calls Agent Framework the direct successor (opens in a new tab) of both AutoGen and Semantic Kernel.

So this lesson has two jobs. It teaches the AutoGen concepts well enough to read, run and debug existing AutoGen code. It also shows how each concept maps to Microsoft Agent Framework and where behaviour changes in the move. All code targets the current API, in the packages autogen-agentchat, autogen-core and autogen-ext. Version 0.2 used a different API, which the edge cases cover.

Short snippets use await at the top level, as in a notebook. In a script, put them inside an async function and call asyncio.run, as the worked example does.

How it works

AgentChat agents

An AssistantAgent wraps a model client, a system message and optional tools:

python
from autogen_agentchat.agents import AssistantAgent
from autogen_ext.models.openai import OpenAIChatCompletionClient

async def get_weather(city: str) -> str:
    """Get the weather for a city."""
    return f"{city}: 21 degrees, clear"

agent = AssistantAgent(
    "assistant",
    model_client=OpenAIChatCompletionClient(model="gpt-4.1"),
    tools=[get_weather],
)
result = await agent.run(task="What is the weather in Oslo?")

The agents tutorial (opens in a new tab) documents three behaviours that surprise people who arrive from other frameworks.

  • The agent is stateful. Each call to run adds to the agent's own message history, so you pass only the new message, not the whole conversation.
  • It makes one round of tool calls by default. After the tools run, the agent returns their output as a ToolCallSummaryMessage without asking the model again. Set reflect_on_tool_use=True to get a written answer, or raise max_tool_iterations (default 1) to let it loop as in The Agent Loop.
  • run returns a TaskResult holding messages and a stop_reason. run_stream yields the messages as they are produced.

Teams and termination conditions

A team (opens in a new tab) is a group of agents working on one task. RoundRobinGroupChat is the simplest. Agents respond in a fixed order, and each response is broadcast to all the other agents, so the whole team shares one context.

python
from autogen_agentchat.conditions import MaxMessageTermination, TextMentionTermination
from autogen_agentchat.teams import RoundRobinGroupChat

stop = TextMentionTermination("APPROVE") | MaxMessageTermination(10)
team = RoundRobinGroupChat([writer, critic], termination_condition=stop)
result = await team.run(task="Write a one-line slogan for a bike repair shop.")
print(result.stop_reason)

A termination condition (opens in a new tab) is a callable. After each agent responds, the team passes it the messages produced since the last check. It returns a StopMessage to end the run or None to continue. Four rules:

  • Conditions keep state during a run and reset automatically when the run ends.
  • | stops when either side fires and & when both have. Built-in conditions include MaxMessageTermination, TextMentionTermination, TokenUsageTermination, TimeoutTermination, HandoffTermination and ExternalTermination.
  • The task itself counts as a message.
  • With no condition, the class documentation says the group chat runs indefinitely.

A team keeps its state. run() with no task resumes from the next speaker, and reset() clears the team and every agent in it.

Group-chat patterns

Every AgentChat team is a group chat: one shared thread and a manager that decides who acts next. Most teams have one speaker at a time. The teams differ in who picks the next speaker.

  • SelectorGroupChat (opens in a new tab) asks a model to choose, using the conversation history and each participant's name and description. The descriptions are therefore part of your prompt. By default the same agent is not chosen twice in a row. A selector_func can decide in code and return None to fall back to the model.
  • Swarm (opens in a new tab) has no central chooser. An agent created with handoffs=["refunds", "user"] can emit a HandoffMessage, and the most recent one names the next speaker. Set parallel_tool_calls=False on the model client, because parallel tool calls can produce several handoffs at once. HandoffTermination(target="user") stops the run so a person can answer.
  • MagenticOneGroupChat puts a planning orchestrator in the manager's seat (see the first real-world example).
  • GraphFlow follows a directed graph that you define, with conditional edges. The migration guide calls it experimental.

The teams tutorial advises moving to a team only when the task needs collaboration, since a team takes more scaffolding to steer than a single agent.

The Core runtime underneath

In Core, an agent is any object that handles messages. You subclass RoutedAgent and mark methods with @message_handler. The type hint on the message parameter decides which handler gets which message. Agents never call each other. They give messages to a runtime, in one of two ways (opens in a new tab):

Direct messageBroadcast
Callsend_message(message, agent_id)publish_message(message, topic_id)
RecipientOne named agentEvery agent subscribed to the topic
ReplyThe handler's return value; exceptions reach the senderNone. It is one way only
python
from dataclasses import dataclass
from autogen_core import (DefaultTopicId, MessageContext, RoutedAgent,
                          SingleThreadedAgentRuntime, default_subscription, message_handler)

@dataclass
class Draft:
    text: str

@default_subscription
class Reviewer(RoutedAgent):
    @message_handler
    async def on_draft(self, message: Draft, ctx: MessageContext) -> None:
        print(f"reviewing: {message.text}")

runtime = SingleThreadedAgentRuntime()
await Reviewer.register(runtime, "reviewer", lambda: Reviewer("Reviews drafts"))
runtime.start()
await runtime.publish_message(Draft("Fix it fast, ride it far."), topic_id=DefaultTopicId())
await runtime.stop_when_idle()

A topic (opens in a new tab) has a type and a source. TypeSubscription(topic_type="triage", agent_type="triage_agent") routes anything published to a triage topic to a triage_agent whose key equals the topic source. Publishing to ("triage", "session-1") reaches AgentId("triage_agent", "session-1"), and the runtime creates that instance if it does not exist. One registration can therefore serve many sessions or tenants.

An AgentChat team is this machinery assembled for you. The Core guide builds a group chat by hand (opens in a new tab) in the same shape: each participant subscribes to its own topic and to a shared group topic, and a manager publishes a request to speak to the next speaker's topic.

SingleThreadedAgentRuntime runs everything in one process, and a team creates one unless you pass runtime=. A distributed runtime for agents in separate processes also exists. The migration guide calls it experimental.

Maintenance status

The README notice says that AutoGen will not receive new features or enhancements, that it is community managed, and that new users should start with Microsoft Agent Framework. Two dates show the handover: PyPI lists autogen-agentchat 0.7.5 (opens in a new tab), released on 30 September 2025, as the latest version, and Agent Framework 1.0 (opens in a new tab) was announced on 3 April 2026 with stable APIs and long-term support.

Existing code keeps running and pinned versions keep installing, but treat an AutoGen dependency as frozen.

Migrating to Agent Framework

The migration guide (opens in a new tab) maps the two APIs. The last column shows where translated code behaves differently.

The guide also lists what you gain: a workflow can pause for a person through requests and responses, checkpoint its progress and resume later, and run middleware around agent and tool calls. The guide says AutoGen's Team has no built-in checkpointing. A team can export its state (opens in a new tab) with save_state() and load_state(), but your code decides when to save and where to keep it. In the other direction, the guide says local code execution tools were still planned for Agent Framework when it was written.

Worked example: A writer and critic team run twice with scripted replies, stopped once by a message cap and once by approval

This example runs a real AutoGen team without a model provider. Each agent gets a ReplayChatCompletionClient (opens in a new tab), a model client from autogen-ext that returns a list of scripted replies in order. Everything else is the normal AgentChat machinery, so the output is the same on every machine and you can check each stop by hand.

Install the two packages, pinned to the latest release (Python 3.10 or later):

bash
pip install "autogen-agentchat==0.7.5" "autogen-ext==0.7.5"

Save this as slogan_team.py:

python
import asyncio

from autogen_agentchat.agents import AssistantAgent
from autogen_agentchat.conditions import MaxMessageTermination, TextMentionTermination
from autogen_agentchat.teams import RoundRobinGroupChat
from autogen_ext.models.replay import ReplayChatCompletionClient

TASK = "Write a one-line slogan for a bike repair shop."


async def main() -> None:
    writer = AssistantAgent(
        "writer",
        model_client=ReplayChatCompletionClient([
            "Fix it fast, ride it far.",
            "Same-day repairs, so you never miss a ride.",
        ]),
        system_message="You write short slogans.",
    )
    critic = AssistantAgent(
        "critic",
        model_client=ReplayChatCompletionClient([
            "Too generic. Say that repairs are done the same day.",
            "APPROVE",
        ]),
        system_message="Give one line of feedback. Reply APPROVE when the slogan is good.",
    )
    stop = TextMentionTermination("APPROVE") | MaxMessageTermination(3)
    team = RoundRobinGroupChat([writer, critic], termination_condition=stop)

    first = await team.run(task=TASK)
    second = await team.run()  # no task: resume where the team stopped

    for label, result in (("run 1", first), ("run 2", second)):
        print(f"{label}: {result.stop_reason}")
        for message in result.messages:
            print(f"  {message.source}: {message.to_text()}")


asyncio.run(main())

Run python slogan_team.py. The expected output is:

text
run 1: Maximum number of messages 3 reached, current message count: 3
  user: Write a one-line slogan for a bike repair shop.
  writer: Fix it fast, ride it far.
  critic: Too generic. Say that repairs are done the same day.
run 2: Text 'APPROVE' mentioned
  writer: Same-day repairs, so you never miss a ride.
  critic: APPROVE

The team checks the combined condition after the task arrives and after every response. Each check sees only the new message:

CheckNew messageMessages counted in this runContains APPROVEOutcome
1user: the task1nocontinue, writer speaks
2writer: Fix it fast, ride it far.2nocontinue, critic speaks
3critic: Too generic...3nostop, the cap of 3 is reached
4writer: Same-day repairs...1nocontinue, critic speaks
5critic: APPROVE2yesstop, the text was mentioned

What to notice:

  • The task counts. The first run ends after only two agent responses, because the user's task is the first of the three messages. A cap of 3 gave the writer no chance to act on the feedback.
  • Conditions reset between runs. At check 4 the count starts again from 1. If it had carried over, the second run would have stopped immediately.
  • The team remembers. run() with no task did not start over. The writer spoke next because it follows the critic in the round-robin order, and its second scripted reply answers the feedback because both agents still hold the earlier conversation.
  • stop_reason names the exit. The first run ended because of a limit and the second because the work was approved. Code that calls a team should branch on this value. A capped run is not a finished one.

Change the cap to MaxMessageTermination(10) and run only team.run(task=TASK). The single run then returns all five messages and stops with Text 'APPROVE' mentioned.

To use a live model, replace each ReplayChatCompletionClient([...]) with OpenAIChatCompletionClient(model="gpt-4.1") from autogen_ext.models.openai (install autogen-ext[openai]). The team code does not change, but the stop is no longer predictable: nothing guarantees that the critic ever writes APPROVE, which is why the cap stays in the condition.

In Agent Framework the same program becomes a GroupChatBuilder with a round-robin selection_func, and the two condition objects become one function that inspects the conversation, for example a check that the last message comes from the critic and contains APPROVE, combined with a length limit. The agents no longer remember earlier runs on their own, so resuming needs a session or a checkpoint.

Edge cases and limitations

A text-only stop rule can run forever
TextMentionTermination fires only if the text appears in a message. A model that keeps giving feedback and never writes APPROVE keeps the team running, and the class documentation states that a group chat with no termination condition runs indefinitely. The test is a case-sensitive substring match on every message, so a critic who writes "not ready to APPROVE" also stops the team. Always combine a content rule with a hard limit such as MaxMessageTermination, TokenUsageTermination or TimeoutTermination (a RoundRobinGroupChat also takes a max_turns argument), and check stop_reason to see which one ended the run.
An agent returns raw tool output where you expected an answer
AssistantAgent performs one round of tool calls and then returns the tool results as a ToolCallSummaryMessage, with no further model call. In a team, the next agent receives that raw output. Set reflect_on_tool_use=True when you want a written answer, or raise max_tool_iterations for multi-step tool use. The Agent Framework Agent loops until it has a final answer, so the same agent behaves differently after migration.
Parallel tool calls break a Swarm
In a Swarm the next speaker is whoever the latest HandoffMessage names, and a handoff is a tool call. The Swarm documentation warns that a model which calls tools in parallel can emit several handoffs in one reply, which leads to unexpected behaviour. Create the model client with parallel_tool_calls=False for any agent that has handoffs. The Agent Framework migration guide gives the same instruction for agents wrapped as tools with AgentTool.
Two different APIs share the name AutoGen
Version 0.4 was a rewrite with an asynchronous, event-driven design. Tutorials that show import autogen, llm_config, initiate_chat or GroupChatManager target version 0.2 and do not run on the current packages. The v0.2 migration guide also states that releases of the pyautogen package have not come from Microsoft since version 0.2.34. Install autogen-agentchat and autogen-ext, and check which API a tutorial uses before copying from it.
Every message reaches every agent
Group chat teams broadcast each response to all participants, so each agent's context holds the whole conversation, including turns that have nothing to do with its role. Token use per turn therefore grows with the number of turns, and SelectorGroupChat adds a model call per turn to choose the speaker. Keep teams small, cap them, and move work that only one agent needs into a tool or a nested agent.
The migration guide can lag behind the framework
The migration guide lists handoff and model-selected group chat as patterns still in development, while the Agent Framework orchestration pages, dated later, document HandoffBuilder and GroupChatBuilder. The Magentic orchestration page adds its own warning that the pattern is untested outside the original Magentic-One design. Check the dated orchestration pages and the installed package version before you conclude that a pattern is missing or equivalent.

When to use it, and when something simpler is enough

Use it when

  • You maintain an existing codebase on the autogen-agentchat or autogen-core packages and need to fix, test or trace it before a planned migration.
  • You are reproducing research or a tutorial written against AutoGen, such as Magentic-One or a group chat experiment, and need the original API to get the same behaviour.
  • You want to learn group chat, speaker selection and termination by running them. A team with a replay model client is free, deterministic and small enough to trace by hand.
  • You depend on a capability the migration guide marks as not yet available in Agent Framework, such as local code execution tools, and you accept maintenance-only support for it.

Think twice when

  • You are starting a new production system. The README sends new users to Microsoft Agent Framework, and AutoGen will not receive new features or enhancements.
  • The process must pause for approval and resume hours later, or survive a restart. Agent Framework workflows have requests, responses and checkpoints built in. An AutoGen team gives you termination conditions that hand control to a person, plus save_state and load_state, and you build the rest.
  • The steps are known in advance or one agent with tools can do the job. A team adds turns, tokens and a termination problem that a function or a single agent does not have.
  • Agents must not see each other's messages. Group chat broadcasts every response to all participants.

A simpler alternative. A single AssistantAgent with tools and a raised max_tool_iterations, or plain Python that calls one agent after another and passes the result along. This stops being enough when distinct roles must respond to each other over several rounds, for example a critic whose feedback decides whether the writer goes again, or when the specialist needed next depends on what the last one found.

Key takeaways

  • AutoGen has a high-level AgentChat layer of agents and teams built on a Core runtime in which agents only exchange messages, directly or through topics.
  • Every AgentChat team is a group chat with a shared thread, and the team types differ in who picks the next speaker: a fixed order, a model, the current agent's handoff, a planning orchestrator or a graph.
  • A team stops only when a termination condition fires, so always pair a content rule with a hard limit and read stop_reason to learn which one ended the run.
  • AutoGen is in maintenance mode, which means existing code keeps working but new projects should start on Microsoft Agent Framework.
  • Most AutoGen constructs have a named Agent Framework equivalent, but tool looping, conversation state and termination behave differently and must be tested when you migrate.

Example 1 of 5

Magentic-One: an orchestrator-led AutoGen team for open-ended web and file tasks

Microsoft ResearchDocumented in an engineering article

Magentic-One is a multi-agent system from Microsoft Research, built on AutoGen and described in a Microsoft Research article of 4 November 2024. The AutoGen documentation has a page on running it as an AgentChat team. [27][10]

The problem

The tasks are open-ended: find something on the web, read a file, write and run some code, and combine the results, in an order nobody can write down in advance. A single agent with every tool attached has to plan, browse, code and track its own progress in one context. The researchers wanted one system that works across domains, notices when it is stuck and changes its plan.

Where this topic fits

The Orchestrator is a group chat manager with a plan. In AgentChat terms the system is MagenticOneGroupChat, a team in which the manager does not follow a fixed order or ask a model a one-line question about who is next. It keeps two written ledgers and uses them to choose the next agent and the instruction to give it. The first implementation was written directly on the Core layer and was later ported to AgentChat.

How it is applied, step by step

  1. A task arrives and the Orchestrator writes a Task Ledger holding the facts it knows, its educated guesses and a plan.
  2. In each step of the inner loop the Orchestrator updates a Progress Ledger, reflecting on how far the task has come, and assigns a subtask to one of the four agents.
  3. The chosen agent does the work. WebSurfer drives a Chromium browser, FileSurfer reads local files through a markdown preview, Coder writes code and analyses what the others collected, and ComputerTerminal runs programs in a console shell.
  4. The agent's report returns to the shared conversation, and the Orchestrator updates the Progress Ledger and chooses again.
  5. If progress has not been made for enough steps, the Orchestrator goes back to the outer loop, revises the Task Ledger and writes a new plan.
  6. A typical run ends when the Progress Ledger shows the request is satisfied and the Orchestrator reports the result, or when a limit set on the team is reached.

Why this approach fits

The right next step depends on what the last step found, so speaker selection has to reason about the whole task. That is what the ledgers make possible. Writing the plan and the progress check down also gives a person something to read when a run goes wrong, which a hidden chain of selector decisions does not. Because each skill sits behind an agent with a name and a description, the browsing agent can be improved or replaced without touching the code agent.

Limitation or tradeoff

The system acts on the real web and a real shell, and the article reports what that led to during development: agents that, after a misconfiguration, kept failing to log in until an account was suspended and then tried to reset its password, and agents that tried to recruit human help. The documentation tells users to run it in containers, watch the logs and keep a person in oversight, and it warns about prompt injection from web pages. Every inner-loop step also costs at least one Orchestrator model call on top of the agent's own work, so a run is slow and expensive compared with a single agent. The reported benchmark results are comparable to earlier systems, not ahead of them.

What the sources document

  • The article describes Magentic-One as a generalist multi-agent system for open-ended web and file-based tasks, built on AutoGen, in which a lead agent called the Orchestrator directs four other agents. [27]
  • The Orchestrator runs an outer loop that manages a Task Ledger of facts, guesses and a plan, and an inner loop that manages a Progress Ledger of current progress and task assignment. When progress is not being made for enough steps it updates the Task Ledger and creates a new plan. [27]
  • The team evaluated the system on the GAIA, AssistantBench and WebArena benchmarks and reports performance statistically comparable to the previous state of the art on GAIA and AssistantBench and competitive performance on WebArena. [27]
  • The AutoGen documentation says Magentic-One was first implemented directly on autogen-core and was then ported to autogen-agentchat, where its orchestrator, MagenticOneGroupChat, works as an AgentChat team. [10]
  • The article reports that during development a misconfiguration led agents to repeatedly fail to log in to a WebArena site until the account was temporarily suspended, after which they tried to reset its password, and that agents also tried to recruit human help. The AutoGen documentation advises running in containers, monitoring logs, keeping human oversight and limiting access, and warns about prompt injection from web pages. [27][10]

The facts above come from the cited sources. The steps and analysis in this example are our explanation of how they fit together.

Example 2 of 5

AutoGen Studio: prototyping and inspecting AgentChat teams from JSON specifications

MicrosoftDocumented in official docs

AutoGen Studio is the low-code interface distributed with AutoGen as the autogenstudio package. Its user guide and usage page describe it, and the AgentChat page on serializing components describes the mechanism it relies on. [19][20][11]

The problem

Trying a different team design normally means editing Python: another agent, a different termination rule, a new tool. Comparing variants is slow, and a transcript printed to a console makes it hard to see which agent said what and in which order. People who are not writing the code cannot try the team at all.

Where this topic fits

Studio sits on top of AgentChat. A team in Studio is a declarative JSON description of AgentChat components, and AgentChat components can write themselves out as such a description and be rebuilt from one. The lesson's concepts (agents, teams, model clients, termination conditions) appear in Studio as boxes on a canvas and as sections of the JSON.

How it is applied, step by step

  1. Define a team in Python and call dump_component on it, or compose it in the Team Builder by dragging components onto a canvas.
  2. The result is a JSON specification that covers the team, its agents, their model clients, tools and termination conditions. The Team Builder can switch to a JSON editor to change it directly.
  3. Run the team on a task in the Playground and watch the messages stream in, including the team's intermediate messages.
  4. Change a description, a system message or a termination rule in the specification and run the same task again to compare.
  5. Export the specification and load it in Python with load_component, or run it through the TeamManager class, when the design is settled.
  6. Rebuild anything that must run in production directly on the framework, since Studio is not designed to be a production application.

Why this approach fits

A team is mostly configuration: which agents, which model, which order, which stopping rule. Putting that configuration in a file separates the design of a team from the code that runs it, so a design can be edited in a visual tool, reviewed in a pull request and loaded by a script. The Playground view matters for the same reason a trace does. A multi-agent failure is usually a wrong turn in the conversation, and it is found by reading the conversation.

Limitation or tradeoff

OptiGuide on AutoGen: three conversing agents answer supply-chain questions with checked code

Microsoft ResearchDocumented in a paper

Application A4 of the original AutoGen paper (Wu and colleagues, 2023) rebuilds OptiGuide, a system for questioning optimisation solutions, as a conversation between three agents. It was written against the version 0.2 API, whose concepts the v0.2 migration guide maps to the current one. [28][18]

The problem

A planner looks at the output of a supply-chain optimiser and asks what would happen if one decision changed, or why the optimiser chose as it did. Answering means writing code against the optimisation model, running it and explaining the result. Generated code that runs against business data is a risk, so each piece of code has to be judged safe before it is executed. The paper also reports that the original workflow took a large amount of hand-written orchestration code.

Where this topic fits

This is AutoGen's founding idea, which the paper calls conversation programming: the workflow is expressed as which agent talks to which, and under what condition. A Commander agent coordinates a Writer and a Safeguard. In the current API the same roles would be agents in a team, or agents that one coordinator calls as tools.

How it is applied, step by step

  1. The user's question goes to the Commander, which coordinates the other two agents.
  2. The Commander passes the question to the Writer, which writes code to answer it.
  3. The Commander sends that code to the Safeguard, whose only job is to judge whether the code is safe to run.
  4. If the Safeguard clears the code, the Commander executes it with an external tool such as a Python interpreter.
  5. If the code is rejected or fails, the Commander returns to the Writer with the problem so that it can try again.
  6. The Commander gives the execution results to the Writer, which interprets them into an answer for the user.

Why this approach fits

Separating the roles gives each model call one narrow job. The Safeguard reads code with a single question in mind, without the Writer's context pulling it toward approving its own work. Keeping execution with the Commander means the agent that writes code is not the agent that can run it. Because the control flow is a conversation, adding the safety check meant adding a participant, not rewriting the pipeline.

Limitation or tradeoff

The Safeguard is a model's judgement and can be wrong in both directions, so it does not replace an isolated execution environment (see Code Execution and Sandboxing). The figures are the authors' own measurements with 2023 models and should not be read as what a current model would score. Each question costs several model calls. The code was written for the version 0.2 API, with its ConversableAgent classes and initiate_chat, and does not run on the current packages without porting.

What the sources document

  • The paper describes OptiGuide as a system that writes code to interpret optimisation solutions and answer user questions, such as exploring the implications of changing a supply-chain decision or understanding why the optimiser made a particular choice. [28]
  • In the AutoGen version a Commander coordinates a Writer and a Safeguard. The Writer crafts code and sends it to the Commander, the Commander checks its safety with the Safeguard and, if it is cleared, executes it with external tools such as Python and asks the Writer to interpret the results. [28]
  • The authors report that the core workflow code for OptiGuide was reduced from over 430 lines to 100 lines, and that the multi-agent design raised the F1 score for identifying unsafe code by 8% with GPT-4 and 35% with GPT-3.5-turbo. [28]
  • The authors report that the AutoGen-based OptiGuide could save around three times the user's time and reduce user interactions by three to five times on average. [28]
  • The v0.2 migration guide shows v0.2 group chat code (a GroupChat passed to a GroupChatManager) next to RoundRobinGroupChat for the same behaviour, names SelectorGroupChat for LLM-based speaker selection, and says the current API returns a TaskResult from run or run_stream. [18]

Tracing an AutoGen team into Langfuse through OpenTelemetry

LangfuseDocumented in official docs

Langfuse, an LLM observability product, documents an AutoGen integration in its guide "Integrate Langfuse with AutoGen", which exports OpenTelemetry spans through the OpenLIT library. AutoGen's own "Tracing and Observability" page documents the OpenTelemetry support in its runtime, although it does not mention Langfuse. [29][12][16]

The problem

When a team gives a wrong answer, the question is where the conversation went wrong: which agent said what, which model and tool calls it made, and how long each took. A transcript printed to a console answers that for one run on one machine. It does not help with hundreds of runs in a deployed service, or with comparing a failing run against a good one.

Where this topic fits

The connection is made below the team. AgentChat teams run on the Core runtime, and AutoGen emits OpenTelemetry spans as it works. Nothing in the agents or the team definition changes. You configure where spans are sent, and for a team you may hand it a runtime that you created yourself.

How it is applied, step by step

  1. Install the Langfuse SDK, the OpenLIT instrumentation library and the AutoGen packages, and set the Langfuse keys in the environment.
  2. Create the Langfuse client with a span filter that drops spans whose instrumentation scope is the AutoGen single-threaded runtime.
  3. Initialise OpenLIT with the Langfuse tracer, so that the AutoGen operations it captures are exported as OpenTelemetry spans to Langfuse.
  4. Run the AutoGen application exactly as before.
  5. Open the trace in Langfuse and read the run from the user's query through each agent interaction to the final response.
  6. With plain OpenTelemetry, set a tracer provider with an OTLP exporter and pass the team a runtime through its runtime argument, as AutoGen's own page does with a Jaeger backend.

Why this approach fits

A team is already a stream of discrete events: a request to speak, a model call, a tool call, a response. Those map directly onto spans, and OpenTelemetry is a vendor-neutral format that many backends accept, so the same instrumentation serves Langfuse, Jaeger or another tool. Because the hook is in the runtime and the libraries, a codebase in maintenance mode can gain tracing without edits to its agent logic. See LLM and Agent Observability for what to look for in a trace.

Limitation or tradeoff

Traces carry prompts, tool arguments and model outputs to another system, which matters when the conversation holds customer data. Both guides switch off the runtime's own spans: Langfuse filters them out and AutoGen's example disables them. Neither page says why, presumably because a runtime that traces every message it delivers produces many spans. The Langfuse guide depends on a third-party instrumentation library and reaches into an internal attribute of the Langfuse client, so an upgrade of either library can break it. A trace shows what happened and does not judge whether the answer was good.

Microsoft Agent Framework 1.0: AutoGen's group chat, handoff and Magentic patterns as workflow orchestrations

MicrosoftDocumented in official docs

Microsoft Agent Framework reached version 1.0 in April 2026. Its documentation describes group chat, handoff and Magentic orchestrations, and the Magentic page credits the Magentic-One system from AutoGen. The announcement post, the migration guide and the orchestration pages document how AutoGen's patterns were carried into the new product. [26][25][23][24][21]

The problem

AutoGen's patterns had proved useful, but the framework that held them was being succeeded, and the migration guide says its team abstraction has no built-in checkpointing and no built-in way to pause for human input. Developers with working group chats, swarms and Magentic-One teams needed a supported place to move them, without redesigning their systems from first principles.

Where this topic fits

The concepts move and the machinery under them changes. A group chat manager that picks the next speaker becomes an orchestrator at the centre of a star. A Swarm becomes a handoff mesh. The Magentic-One Orchestrator becomes a Magentic manager. Under all three, a graph-based workflow engine takes the place of Core topics and subscriptions. This is the migration target for every team type in this lesson.

How it is applied, step by step

  1. In group chat orchestration an orchestrator chooses the next speaker with a round-robin function, an orchestrator agent that reads the conversation, or custom logic. These are the same three choices as RoundRobinGroupChat, SelectorGroupChat and a selector function.
  2. After each turn the orchestrator broadcasts the response and brings every agent's own session up to date, which gives the shared context that AutoGen achieved by broadcasting on a group topic.
  3. In handoff orchestration agents are connected directly and pass control with a handoff tool call, as a Swarm does. When an agent answers without handing off, the workflow asks the user for input.
  4. In Magentic orchestration a manager plans, tracks progress and replans, with limits on rounds, stalls and resets, and an optional human review of the plan.
  5. Because each orchestration is a workflow, it can pause for human input and be checkpointed. The handoff page, for example, shows tool approval requests and a checkpoint_storage argument that lets a paused run resume after a restart. The migration guide says an AutoGen team needs both built outside the framework.
  6. A migration maps each team to its builder, rewrites termination conditions as functions over the conversation, adds sessions where agents relied on their own memory, and re-runs recorded tasks to compare behaviour.

Why this approach fits

Keeping the patterns and their names lets a team that understands its AutoGen design recognise the same design on the other side. The move from a broadcast runtime to a workflow graph adds what teams lacked: typed routing of messages, checkpoints and a pause for human input that survives a restart. A single supported framework also ends the choice between AutoGen for orchestration patterns and Semantic Kernel for enterprise features.

Limitation or tradeoff

Equivalent names do not mean identical behaviour. The Python group chat synchronises only the text of agent messages, with tool calls and results filtered out, so check what each agent can see after the move. Handoff orchestration supports only the Agent type with local tool execution, and it waits for a user whenever an agent does not hand off unless autonomous mode is enabled. The Magentic page warns that the pattern is untested outside the original Magentic-One design. Defaults also differ between languages: plan review is off by default in Python and on in .NET.

  • The announcement, dated 3 April 2026, says Agent Framework reached version 1.0 for .NET and Python as a production-ready release with stable APIs and a commitment to long-term support, lists sequential, concurrent, handoff, group chat and Magentic-One orchestration patterns as stable, and urges AutoGen users to migrate. 4Common mistakes

  1. Starting a new project on AutoGen because most multi-agent tutorials use it.

    Why it causes problems
    The framework will not gain new features, so new model capabilities, integrations and orchestration patterns will not arrive. The project begins with a migration already owed, and every month of development makes that migration larger.
    How to recognise it
    The repository README opens with a maintenance mode notice, and the package index shows no AgentChat release after 0.7.5. A requirements file for a new service that lists autogen-agentchat is the sign.
    How to fix it
    Build new systems on Microsoft Agent Framework or another supported framework. Use AutoGen to learn the patterns, to reproduce published work and to keep existing systems running until they are moved.

  2. Ending a team with a text rule alone, such as waiting for the word APPROVE or TERMINATE.

    Why it causes problems
    Nothing forces a model to write the word. A critic that keeps suggesting changes, or an agent that phrases its approval differently, keeps the team running and spending until someone stops it.
    How to recognise it
    A termination_condition with a single TextMentionTermination, runs whose message count varies wildly, and callers that never read stop_reason.
    How to fix it
    Combine the text rule with a hard limit using the or operator, for example MaxMessageTermination or TokenUsageTermination, and treat a run that ended on the limit as unfinished in the calling code.

  3. Copying code from version 0.2 tutorials, or installing pyautogen, for a current AutoGen project.

    Why it causes problems
    The 0.2 API and the current API are different designs under one name. Code fails on import, or a different package from a different publisher is installed, and time is lost debugging a mismatch that is not in your logic.
    How to recognise it
    Imports of the form import autogen, a dictionary called llm_config, calls to initiate_chat, or classes named ConversableAgent and GroupChatManager.
    How to fix it
    Install autogen-agentchat and autogen-ext, pin their versions, and translate old examples with the v0.2 migration guide before using them.

  4. Translating AssistantAgent to the Agent Framework Agent line by line and assuming the same behaviour.

    Why it causes problems
    The new agent keeps calling tools until it has an answer and forgets earlier calls unless it is given a session. Output that used to be raw tool results becomes a model-written summary, model calls and cost rise, and follow-up questions lose their context, all without an error.
    How to recognise it
    After migration, traces show several tool rounds where there was one, token use per request rises, and a second request that refers to the first is answered as if it were new.
    How to fix it
    Record tasks and transcripts from the AutoGen version first. After translating, add an AgentSession where memory is needed, set limits on tool iterations, and compare the new transcripts against the recordings.

  5. Putting every specialist into one group chat.

    Why it causes problems
    Each response is broadcast to all participants, so every agent's context holds everyone's turns. Cost per turn grows as the chat lengthens, a selector has more candidates to confuse, and agents react to messages that were not meant for them.
    How to recognise it
    Teams of six or more agents, prompt token counts that climb every turn, and transcripts in which an agent answers a question addressed to another.
    How to fix it
    Keep a team to the few roles that must hear each other. Give a single agent the other capabilities as tools or wrapped agents, or use a graph or workflow in which each step receives only the input it needs.

Start from this file, mini_runtime.py. It is a toy model of the Core runtime: agents subscribe to topics, publish queues a message, and run_until_idle delivers queued messages to every subscriber except the sender.

python
"""A toy model of AutoGen Core: topics, subscriptions and a message queue."""
from collections import deque
from dataclasses import dataclass


@dataclass(frozen=True)
class ChatMessage:
    source: str
    content: str


@dataclass(frozen=True)
class RequestToSpeak:
    pass


class Runtime:
    def __init__(self):
        self._agents = {}          # agent name -> agent object
        self._subscriptions = {}   # topic -> agent names, in registration order
        self._queue = deque()
        self.deliveries = []       # (topic, recipient, message type) for every delivery

    def register(self, name, agent, topics):
        self._agents = {**self._agents, name: agent}
        for topic in topics:
            self._subscriptions = {
                **self._subscriptions,
                topic: [*self._subscriptions.get(topic, []), name],
            }

    def publish(self, message, topic, sender=None):
        self._queue.append((message, topic, sender))

    def run_until_idle(self):
        while self._queue:
            message, topic, sender = self._queue.popleft()
            for name in self._subscriptions.get(topic, []):
                if name == sender:   # a publisher never receives its own message
                    continue
                self.deliveries.append((topic, name, type(message).__name__))
                self._agents[name].on_message(message, self)

python
from mini_runtime import ChatMessage, RequestToSpeak, Runtime

GROUP = "group"
TASK = "Write a one-line slogan for a bike repair shop."


class MaxMessages:
    def __init__(self, limit):
        self.limit, self.count = limit, 0

    def check(self, message):
        self.count += 1
        if self.count >= self.limit:
            return f"Maximum number of messages {self.limit} reached, current message count: {self.count}"
        return None

    def reset(self):
        self.count = 0


class TextMention:
    def __init__(self, text):
        self.text = text

    def check(self, message):
        return f"Text '{self.text}' mentioned" if self.text in message.content else None

    def reset(self):
        pass


class Participant:
    def __init__(self, name, replies):
        self.name = name
        self.context = []              # what this agent has seen: its private copy of the chat
        self._replies = iter(replies)  # stands in for a model client

    def on_message(self, message, runtime):
        if isinstance(message, ChatMessage):
            self.context = [*self.context, message]
        elif isinstance(message, RequestToSpeak):
            reply = ChatMessage(self.name, next(self._replies))
            self.context = [*self.context, reply]
            runtime.publish(reply, GROUP, sender=self.name)


class RoundRobinManager:
    def __init__(self, participant_names, conditions):
        self._names = participant_names
        self._conditions = conditions
        self._next = 0
        self.thread = []        # every chat message of every run
        self.new_messages = []  # messages of the current run only
        self.stop_reason = None

    def on_message(self, message, runtime):
        if not isinstance(message, ChatMessage):
            return
        self.thread = [*self.thread, message]
        self.new_messages = [*self.new_messages, message]
        reasons = [reason for reason in (c.check(message) for c in self._conditions) if reason]
        if reasons:
            self.stop_reason = ", ".join(reasons)
            for condition in self._conditions:
                condition.reset()
            return
        self.request_next_speaker(runtime)

    def request_next_speaker(self, runtime):
        speaker = self._names[self._next]
        self._next = (self._next + 1) % len(self._names)
        runtime.publish(RequestToSpeak(), speaker, sender="manager")

    def start_run(self):
        self.new_messages, self.stop_reason = [], None


def build():
    runtime = Runtime()
    writer = Participant("writer", ["Fix it fast, ride it far.",
                                    "Same-day repairs, so you never miss a ride."])
    critic = Participant("critic", ["Too generic. Say that repairs are done the same day.",
                                    "APPROVE"])
    manager = RoundRobinManager(["writer", "critic"], [TextMention("APPROVE"), MaxMessages(3)])
    runtime.register("manager", manager, [GROUP])
    for agent in (writer, critic):
        runtime.register(agent.name, agent, [GROUP, agent.name])  # shared topic + its own topic
    return runtime, manager, writer, critic


def report(label, manager):
    print(f"{label}: {manager.stop_reason}")
    for message in manager.new_messages:
        print(f"  {message.source}: {message.content}")


if __name__ == "__main__":
    runtime, manager, writer, critic = build()

    manager.start_run()                                   # run 1: publish the task
    runtime.publish(ChatMessage("user", TASK), GROUP, sender="user")
    runtime.run_until_idle()
    report("run 1", manager)

    manager.start_run()                                   # run 2: resume without a task
    manager.request_next_speaker(runtime)
    runtime.run_until_idle()
    report("run 2", manager)

    chat = sum(1 for _, _, kind in runtime.deliveries if kind == "ChatMessage")
    requests = sum(1 for _, _, kind in runtime.deliveries if kind == "RequestToSpeak")
    print(f"deliveries: {chat} chat messages, {requests} requests to speak")
    print(f"thread: {len(manager.thread)} messages; "
          f"writer context: {len(writer.context)}; critic context: {len(critic.context)}")

Running python3 group_chat.py prints the nine lines shown under expected behaviour.

Why the numbers come out this way. The task is published by user, which is not a subscriber, so all three subscribers of the shared topic receive it: 3 deliveries. Each of the four replies is published by a participant, which is skipped, so it reaches the manager and the other participant: 4 x 2 = 8 deliveries. That gives 11. Each reply was triggered by one request on a private topic, so there are 4 requests.

Both participants end with all five messages in their context although each wrote only two of them. That is the broadcast at work, and it is the reason a group chat's token use grows with every turn for every agent, not only for the one that speaks.

The manager never calls a participant. It publishes a request to a topic and returns, and the runtime delivers the request later. Swapping the round-robin index for a model call that returns a name gives you a selector group chat, and letting the last message name the next speaker gives you a swarm. Nothing else in the file would change. AutoGen's own team types follow the same design: they share the group chat machinery and differ in the manager.

2. Behaviour that changes

  • Tool looping. lookup makes one round of tool calls and returns the raw result of get_order as a ToolCallSummaryMessage. The new Agent keeps calling tools and then writes an answer. The writer receives prose in place of raw data, and each ticket costs at least one more model call.
  • Memory. AutoGen agents and the team remember everything between calls to run. The new agents are stateless without a session, so a follow-up ticket arrives with no history unless a checkpoint is restored or the earlier messages are passed in.
  • Termination. MaxMessageTermination(12) counts the ticket itself plus eleven agent messages, per run, and resets after each run. A replacement such as len(conversation) >= 12 counts whatever the conversation holds, so decide whether the user message is included. Callers that logged or branched on stop_reason need a new way to tell approval from the cap.
  • What agents see. AutoGen broadcasts each chat message, including the tool summary text. The Python group chat in Agent Framework synchronises text only and filters tool calls and results, so confirm that the writer still receives the order status.
  • Parallel tool calls. The flag was set on the shared client. Find out why before dropping it. In AutoGen it is needed for handoffs and for agents wrapped as tools, and neither is used here.

3. Two existing defects

  • The wrong message is returned. A run that ends well ends with the reviewer's message, so result.messages[-1] is the text containing APPROVE, not the draft. The function should return the last message whose source is writer. A line-by-line migration would carry the defect over.
  • Tickets leak into each other. team is one module-level object and a team keeps its conversation between runs. When saved_state is None, nothing clears it, so a new customer's ticket is appended to the previous customer's conversation. The fix in AutoGen is await team.reset() (or a new team) for a new ticket. The migration hides this defect, because the new agents are stateless, and it turns it into the opposite problem for genuine follow-ups.

4. Showing that the new version is acceptable

  1. Before changing anything, record a sample of real tickets with the transcripts and stop reasons the AutoGen version produces. Fix the two defects first so the baseline is the intended behaviour.
  2. Unit-test the new termination function without a model: feed it hand-written conversations that end in approval, hit the cap, and contain the word APPROVE in a customer's message.
  3. Run the team logic with scripted model replies on both sides and compare the order of speakers and the stopping point.
  4. Replay the recorded tickets through the new version with a live model. Compare the share of runs that end in approval, the number of model calls and tokens per ticket, and whether the reply contains the order status.
  5. Run the new version in shadow on live traffic, then switch a small share of tickets and keep the old path available until the comparison holds.

A reason not to migrate yet would be a dependency on something the migration guide lists as planned for Agent Framework, such as local code execution tools. This service has none, so the plan can proceed.

Check your answer

  • Does your mapping cover all five constructs, and does it explain why SequentialBuilder alone is not enough for a team that loops until approval?
  • Did you find that the function returns the reviewer's approval message and not the writer's draft?
  • Did you find that a new ticket is appended to the previous ticket's conversation when saved_state is None?
  • Does your plan state how many messages the cap of 12 allows the agents, which is eleven after the ticket itself?
  • Does at least one of your tests run with no live model, for example a unit test of the termination function?
