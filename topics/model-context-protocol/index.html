Model Context Protocol (MCP)

The Model Context Protocol (MCP) is an open standard for connecting AI applications to external tools and data. An application, called the host, runs one client for each server it uses, and each client and server exchange JSON-RPC 2.0 messages to find out what the server offers and to use it.

1Overview

Why it matters

Tool calling lets one application give one model a set of functions. It does not help when the same GitHub, database or ticketing integration has to work in a chat app, an IDE and an agent framework, each with its own plugin format. Without a shared protocol, every pairing of application and system needs its own connector, and every connector has to be maintained when either side changes. MCP replaces those pairings with one client implementation per application and one server per system.

Anyone who adds a server to an agent, publishes a server for a product, or debugs a connected server that shows no tools needs to know who starts what, which messages cross the wire, and how the two sides agree on a protocol version and a feature set. That agreement changed in the 2026-07-28 revision of the specification: the initialize handshake was removed, and every request now carries its own version and capabilities. Servers, examples and courses written for the earlier revisions still exist, so you have to recognise both forms.

Key terms

Host
The AI application the user works in, such as a chat app, an IDE or an agent runtime. It runs the model, creates the clients and decides what each server may see and do.
MCP client
A component inside the host that speaks the protocol to exactly one server. A host that uses three servers runs three clients.
MCP server
A program that offers tools, data and prompt templates through the protocol. It can be a local process started by the host or a remote web service.
JSON-RPC 2.0
A small standard for calling a named method on another program with JSON messages. MCP uses it as the format of every message.
Request
A JSON-RPC message with an id and a method. The receiver must answer it with a response that carries the same id and either a result or an error.
Notification
A JSON-RPC message with a method and no id. The receiver must not answer it.
Capability
An optional protocol feature that one side declares it supports, such as tools on a server or elicitation on a client. The other side may only rely on features that were declared.
Protocol revision
A dated version of the specification, written as YYYY-MM-DD. A new date is issued only when a change is not backward compatible.
Transport
The channel that carries the JSON-RPC messages. The specification defines stdio for local subprocesses and Streamable HTTP for remote servers.
Legacy and modern
The specification's names for the two families of revisions. Legacy revisions (2025-11-25 and earlier) open with an initialize handshake. Modern revisions (2026-07-28 and later) put version and capabilities on every request.

2Explanation

Introduction

In Tool Calling you described a function with a JSON Schema, passed it to a model, ran the call the model asked for and returned the result. All of that lived inside one program. The function, its schema and the code that executed it belonged to the application that talked to the model.

Now suppose you have written a good set of tools for your company's issue tracker. A colleague wants them in a coding assistant, another team wants them in a chat application, and a third is building an agent with a framework. Each of those applications loads tools in its own way, so you write the integration three times. Meanwhile every application team is doing the same for the database, the wiki and the calendar. With MMM applications and NNN systems, that is up to M×NM \times NM×N connectors. The Hugging Face MCP course calls this the M×N integration problem (opens in a new tab). Anthropic, which published MCP as an open standard in November 2024, described it in its announcement (opens in a new tab) as every new data source needing its own custom implementation.

Hardware had the same problem before common connectors, and the MCP documentation makes the comparison itself: MCP is like a USB-C port for AI applications (opens in a new tab). If every application implements the client side of one protocol once, and every system implements the server side once, the count drops to M+NM + NM+N implementations. Five applications and ten systems need 15 implementations in place of 50 connectors.

The protocol names three roles. The host is the AI application the user works in. For each server it connects to, the host creates a client, a component that speaks the protocol to exactly one server. A server is a program that offers tools and data through the protocol. It can be a local process that the host starts or a remote service on the internet.

This lesson covers the integration problem, the three roles, the JSON-RPC messages that clients and servers exchange, and how the two sides agree on a protocol version and a set of features. That last part comes in two forms, because the current revision of the specification (2026-07-28) replaced the connection handshake that every earlier revision used. What servers can offer is the subject of MCP Primitives, and the wire formats and sign-in flows are covered in MCP Transports and Authorization.

How it works

Three roles and what each is responsible for

RoleWhat it isWhat it is responsible for
HostThe AI application: a chat app, an IDE, an agent runtimeRunning the model, creating one client per server, asking the user for consent, deciding what each server may see
ClientA component inside the host, one per serverSending requests to its server, attaching the protocol version and capabilities, handing results back to the host
ServerA program that exposes tools, resources and promptsAnswering requests about its own system and nothing else

The official documentation uses Visual Studio Code as its example of a host: when it connects to a server it creates one MCP client object for that connection (opens in a new tab), and a second server gets a second client.

Two consequences of this layout are easy to miss. First, a server never talks to the model and never sees the whole conversation. The design principles in the specification (opens in a new tab) say that the full history stays with the host and that servers cannot see into each other. Second, "server" names a role and says nothing about location. A local server is usually a subprocess that the host starts and that serves that one client. A remote server is a web service that serves many clients at once.

Two layers

MCP separates what is said from how it travels.

  • The data layer defines the messages: discovery, listing and calling tools, reading resources, and change notifications.
  • The transport layer carries them. With stdio, the client launches the server as a subprocess and each message is one line of JSON on the server's standard input or output. With Streamable HTTP, each message is an HTTP POST to a single endpoint.

The same JSON message is valid on either transport.

Three kinds of message

Every MCP message is a JSON-RPC 2.0 (opens in a new tab) object. There are three kinds:

KindHas idHas methodPurpose
RequestyesyesAsk the other side to do something and answer
Responseyes, the same onenoCarry either a result or an error for that request
NotificationnoyesTell the other side something; no answer is allowed

A request to call a tool looks like this in revision 2026-07-28:

json
{
  "jsonrpc": "2.0",
  "id": 3,
  "method": "tools/call",
  "params": {
    "name": "add",
    "arguments": {"a": 19, "b": 23},
    "_meta": {
      "io.modelcontextprotocol/protocolVersion": "2026-07-28",
      "io.modelcontextprotocol/clientCapabilities": {}
    }
  }
}

Its response repeats the id, which is how the client matches answers to questions:

json
{"jsonrpc": "2.0", "id": 3,
 "result": {"resultType": "complete", "content": [{"type": "text", "text": "42"}]}}

MCP tightens JSON-RPC in a few places (opens in a new tab). An id must be a string or an integer and never null. A sender must not reuse the id of a request that is still waiting for its response. Every result carries a resultType, normally "complete". A failed request gets an error object with an integer code and a message in place of result:

CodeMeaningDefined by
-32700Parse error: the message was not valid JSONJSON-RPC
-32600Invalid requestJSON-RPC
-32601Method not foundJSON-RPC
-32602Invalid params, which MCP also uses for an unknown tool name and for missing _meta fieldsJSON-RPC
-32603Internal errorJSON-RPC
-32021The request needs a client capability that was not declaredMCP
-32022Unsupported protocol versionMCP

Agreeing on a version and capabilities in revision 2026-07-28

Two programs written by different people at different times must settle two questions before they can work together: which revision of the protocol they are speaking, and which optional features each side supports. Revisions are named by date, and a new date is issued only when a change breaks backward compatibility. Optional features are called capabilities. A server declares, for example, tools or resources. A client declares, for example, elicitation, the ability to put a question from the server to the user.

The current revision is stateless: a server must be able to process each request using only what that request contains. So the answers to both questions travel with every request, in params._meta:

_meta keyRequiredContent
io.modelcontextprotocol/protocolVersionyesThe revision this request uses
io.modelcontextprotocol/clientCapabilitiesyesWhat the client supports, possibly {}
io.modelcontextprotocol/clientInforecommendedClient name and version, for logs and display

The server has three possible reactions:

  1. It supports the version, so it processes the request.
  2. It does not support the version. It returns error -32022 with the list of versions it does support. The client retries with one of them or reports the problem to the user.
  3. The request needs something the client did not declare. It returns -32021 and names the missing capability. A server must never rely on a capability the client has not stated.

To learn what a server supports without trial and error, a client can call server/discover (opens in a new tab). Every server must implement it. The result lists supportedVersions, the server's capabilities, optional instructions for the model, and the server's name and version. Calling it is optional. Like a tool list, the result carries the caching hints ttlMs and cacheScope, so a client does not have to ask again before every request.

Statelessness has one more consequence. A server no longer sends requests to the client. When it needs input from the user, it answers the pending request with resultType set to "input_required", and the client sends the request again with the answer attached.

The handshake in revisions up to 2025-11-25

Earlier revisions settle the same two questions once per connection, in a three-phase lifecycle (opens in a new tab):

  1. Initialization. The client's first message must be an initialize request with its protocolVersion, capabilities and clientInfo. The server replies with the version it will use, its own capabilities and its serverInfo. The client then sends the notification notifications/initialized.
  2. Operation. Both sides exchange messages using only the version and capabilities agreed in phase 1.
  3. Shutdown. No shutdown message exists. The client closes the transport: on stdio it closes the server's input stream and waits for the process to exit.

Version negotiation works by echo. The client proposes the latest version it supports. A server that supports it answers with the same string. Otherwise the server answers with another version it supports, and a client that cannot use that version disconnects.

Telling the two eras apart

The specification calls handshake-based revisions legacy and per-request revisions modern. Its compatibility matrix (opens in a new tab) is blunt: a modern-only client fails against a legacy server, and a legacy client fails against a modern-only server. Implementations that support both are called dual-era.

A dual-era client on stdio starts with a probe. It sends server/discover with its preferred modern version and reads the outcome:

  • A discovery result means the server is modern.
  • A recognised modern error such as -32022 also means modern. The client picks a version from the supported list and does not fall back.
  • Any other error, or no answer within a timeout, means legacy. The client sends initialize.

On Streamable HTTP the client sends a modern request and inspects the body of a 400 Bad Request in the same way. A dual-era server needs no probe. It serves a request that carries modern _meta statelessly, and it treats an initialize request as the start of a legacy session.

Worked example: A stdio MCP server and client in one Python file: discovery, a tool call and two refusals

This example puts a complete modern exchange on your screen. One file plays both roles. Run without arguments it is the client. It starts a second copy of itself as the server (python3 mcp_demo.py serve) and talks to it over stdio, which is how a host starts a local server. The server offers one tool, add. The file needs only the Python standard library (3.9 or later) and no MCP SDK, so every message is visible in the code. Save it as mcp_demo.py:

python
import itertools
import json
import subprocess
import sys

VERSION = "2026-07-28"
KEY = "io.modelcontextprotocol/"
ADD_TOOL = {"name": "add", "description": "Add two integers.",
            "inputSchema": {"type": "object", "required": ["a", "b"],
                            "properties": {"a": {"type": "integer"}, "b": {"type": "integer"}}}}


class RpcError(Exception):
    def __init__(self, code, message, data=None):
        self.body = {"code": code, "message": message, **({"data": data} if data else {})}


def handle(method, params):
    meta = params.get("_meta", {})
    requested = meta.get(KEY + "protocolVersion")
    if requested is None or KEY + "clientCapabilities" not in meta:
        raise RpcError(-32602, "Missing required _meta fields", {"supported": [VERSION]})
    if requested != VERSION:
        raise RpcError(-32022, "Unsupported protocol version",
                       {"supported": [VERSION], "requested": requested})
    if method == "server/discover":
        return {"supportedVersions": [VERSION], "capabilities": {"tools": {}},
                "ttlMs": 3600000, "cacheScope": "public"}
    if method == "tools/list":
        return {"tools": [ADD_TOOL], "ttlMs": 300000, "cacheScope": "public"}
    if method == "tools/call":
        if params.get("name") != "add":
            raise RpcError(-32602, f"Unknown tool: {params.get('name')}")
        numbers = params["arguments"]
        return {"content": [{"type": "text", "text": str(numbers["a"] + numbers["b"])}]}
    raise RpcError(-32601, "Method not found")


def serve():
    info = {KEY + "serverInfo": {"name": "demo-server", "version": "1.0.0"}}
    for line in sys.stdin:                      # stdio: one JSON-RPC message per line
        message = json.loads(line)
        if "id" not in message:                 # a notification never gets a reply
            continue
        try:
            result = handle(message["method"], message.get("params", {}))
            reply = {"result": {"resultType": "complete", **result, "_meta": info}}
        except RpcError as error:
            reply = {"error": error.body}
        print(json.dumps({"jsonrpc": "2.0", "id": message["id"], **reply}), flush=True)


def run_client():
    server = subprocess.Popen([sys.executable, __file__, "serve"], text=True,
                              stdin=subprocess.PIPE, stdout=subprocess.PIPE)
    ids = itertools.count(1)

    def request(method, version=VERSION, **params):
        meta = {KEY + "protocolVersion": version, KEY + "clientCapabilities": {},
                KEY + "clientInfo": {"name": "demo-client", "version": "1.0.0"}}
        message = {"jsonrpc": "2.0", "id": next(ids), "method": method,
                   "params": {**params, "_meta": meta}}
        server.stdin.write(json.dumps(message) + "\n")
        server.stdin.flush()
        reply = json.loads(server.stdout.readline())
        print(f"--> {method} (id {message['id']}, version {version})")
        print(f"<-- {json.dumps(reply)}")

    request("server/discover")
    request("tools/list")
    request("tools/call", name="add", arguments={"a": 19, "b": 23})
    request("tools/list", version="2025-11-25")
    request("resources/list")
    server.stdin.close()                        # shutdown: close the server's input
    print("server exit code:", server.wait())


if __name__ == "__main__":
    if sys.argv[1:] == ["serve"]:
        serve()
    else:
        run_client()

Run python3 mcp_demo.py. Each --> line summarises a request, and each <-- line is the server's reply as received:

text

<-- {"jsonrpc": "2.0", "id": 1, "result": {"resultType": "complete", "supportedVersions": ["2026-07-28"], "capabilities": {"tools": {}}, "ttlMs": 3600000, "cacheScope": "public", "_meta": {"io.modelcontextprotocol/serverInfo": {"name": "demo-server", "version": "1.0.0"}}}}
--> tools/list (id 2, version 2026-07-28)
<-- {"jsonrpc": "2.0", "id": 2, "result": {"resultType": "complete", "tools": [{"name": "add", "description": "Add two integers.", "inputSchema": {"type": "object", "required": ["a", "b"], "properties": {"a": {"type": "integer"}, "b": {"type": "integer"}}}}], "ttlMs": 300000, "cacheScope": "public", "_meta": {"io.modelcontextprotocol/serverInfo": {"name": "demo-server", "version": "1.0.0"}}}}
--> tools/call (id 3, version 2026-07-28)
<-- {"jsonrpc": "2.0", "id": 3, "result": {"resultType": "complete", "content": [{"type": "text", "text": "42"}], "_meta": {"io.modelcontextprotocol/serverInfo": {"name": "demo-server", "version": "1.0.0"}}}}
--> tools/list (id 4, version 2025-11-25)
<-- {"jsonrpc": "2.0", "id": 4, "error": {"code": -32022, "message": "Unsupported protocol version", "data": {"supported": ["2026-07-28"], "requested": "2025-11-25"}}}
--> resources/list (id 5, version 2026-07-28)
<-- {"jsonrpc": "2.0", "id": 5, "error": {"code": -32601, "message": "Method not found"}}

What to notice:

  • No handshake. The first message could have been tools/call. The client calls server/discover because it wants the capability list, which is {"tools": {}} and nothing else.
  • Self-contained requests. request attaches the version and capabilities every time, and handle checks them every time. The server keeps no variable between requests.
  • Version mismatch (id 4). The request names 2025-11-25. The reply is error -32022, and data.supported tells the client what to retry with.
  • Undeclared capability (id 5). The server never declared resources, so resources/list returns -32601. A client that reads the discovery result does not send this request.
  • Shutdown. The client closes the server's input, the for line in sys.stdin loop ends, and the process exits with code 0.

The arithmetic is 19 + 23 = 42. A real host adds what the demo leaves out: a confirmation before a tool runs, a timeout on every request, and a model that chooses the tool.

Edge cases and limitations

A modern-only client connects to a legacy server
The specification's compatibility matrix says this fails, and it can fail in three ways: the server rejects the request with an implementation-defined error, stays silent, or processes a method that exists in both eras, such as tools/call, under legacy rules. The third case is the dangerous one because it looks like success. On stdio, send server/discover first even if you support only modern versions, so that the failure is deterministic and you can show the user an actionable message.
A legacy client connects to a modern-only server
The server rejects initialize, because it is an unknown method there and the request also lacks the required _meta fields. The error code is implementation-defined. A legacy client has no way to move forward, so the specification asks modern-only servers to name the versions they support in that error. That text may be the only diagnostic the user sees, as with the data.supported field the worked example returns for requests without _meta.
An open connection is not a session
In revision 2026-07-28 a stdio process or an HTTP connection does not identify a conversation. A client may interleave unrelated requests on it, and a server must not use an earlier request on the same connection to interpret a later one. A tool that sets a current project for later calls breaks under this rule. State that has to last, such as a shopping basket or a database transaction, is created by one tool call that returns an explicit handle, and later calls pass that handle as an ordinary argument.
Names and descriptions sent by the other side are not verified
clientInfo and serverInfo are self-reported. The specification says they are for display, logging and debugging, and that implementations should not change behaviour or make security decisions based on them. Tool annotations, such as a hint that a tool is read-only, are in the same position: clients must treat them as untrusted unless the server itself is trusted. Decide what a server may do from who operates it and how it was installed.
Partial implementations are normal
Few products implement every feature. Home Assistant's server integration documents tools, prompts and one resource as supported, and sampling and notifications as not supported. Its client integration supports tools only. Capability declarations are how this stays workable: read them before you call a method, and expect -32601 for a method the server never offered and -32021 when a server needs a client capability you did not declare.
Teaching material can describe a different revision
The communication protocol page of the Hugging Face MCP course teaches the handshake lifecycle and ends it with shutdown and exit messages, while the 2025-11-25 specification states that no shutdown messages are defined. Microsoft's MCP for Beginners says it teaches the 2026-07-28 concepts but keeps some hands-on examples at 2025-11-25 while SDK support catches up. Before copying a message sequence, check which revision it targets and compare it with the specification page for that revision.

When to use it, and when something simpler is enough

Use it when

  • The same integration has to work in more than one AI application, for example an IDE and a chat app, or you are publishing access to your product for hosts you do not control.
  • You are building a host and want users or other teams to add tools and data without changes to your application.
  • The integration is owned by a different team or company and should run in its own process with its own credentials, so that the host can approve, restrict or remove it as a unit.
  • The set of tools changes while the application runs, and the application needs a standard way to list them again and to be told when the list has changed.

Think twice when

  • One application uses a few functions that live in its own codebase and will never be used elsewhere. Passing the function definitions straight to the model API is less code and has no extra process.
  • You need agents to delegate tasks to other agents or to drive a user interface. MCP connects an application to tools and data; agent-to-agent and agent-to-UI protocols address those other problems.
  • You cannot vet the server and have no way to ask the user before a tool runs. A third-party server receives the data you send it and returns text that the model will read.
  • Every call must stay inside a very tight latency budget and the function could run in-process. A server adds a process boundary or a network hop to each call.

A simpler alternative. Plain tool calling: keep the functions in your application and pass their JSON Schemas to the model API yourself. This stops being enough when a second application needs the same integration, when integrations must be added without redeploying the application, or when the integration belongs to someone else and should be isolated from your code.

Key takeaways

  • MCP replaces one custom connector for every pairing of application and system with one client implementation per application and one server per system.
  • A host runs one client for each server, and it keeps the model, the conversation and the consent decisions to itself, so a server sees only the requests addressed to it.
  • Every MCP message is JSON-RPC 2.0: a request with an id, a response that repeats the id with a result or an error, or a notification with no id and no reply.
  • In revision 2026-07-28 each request carries its protocol version and the client's capabilities in _meta, and server/discover reports what the server supports, so there is no handshake and no session.
  • Revisions up to 2025-11-25 agree once per connection with initialize and notifications/initialized, and a client that must handle both probes with server/discover and falls back on any non-modern outcome.
  • Declared capabilities are the only features either side may rely on, and names, descriptions and annotations sent by a server are untrusted input.

Example 1 of 5

GitHub's MCP server: one integration used from VS Code and many other hosts

GitHubDocumented in an open-source project

GitHub publishes its MCP server as an open-source repository. The README describes a remote server that GitHub hosts and a local server distributed as a container image. The VS Code documentation shows the same server in its example configuration, and the MCP architecture overview names VS Code as a host. [20][19][2]

The problem

GitHub's API is useful to many AI tools at once: editors, command-line agents and chat applications. Each of those hosts has its own extension mechanism, so supporting them one at a time would mean writing and maintaining the same GitHub integration many times over.

There is a second problem inside the first. GitHub's surface is large, and every tool a host loads is described to the model. The README advises that enabling only the toolsets you need can help the model choose tools and reduces the context size.

Where this topic fits

GitHub's program takes the server role. It sits between any MCP host and GitHub's API and exposes GitHub operations as tools. VS Code takes the host role: it reads an entry from mcp.json, creates a client for it, discovers the server's tools and makes them available in chat. Configuration and sign-in come before the protocol exchange. After it, the model's tool calls reach the server as tools/call requests, and a typical implementation turns each one into calls to GitHub's API.

How it is applied, step by step

  1. GitHub implements the server once and groups its tools into toolsets such as repos, issues and pull_requests.
  2. For a host that supports remote servers, the user registers the endpoint that GitHub hosts and signs in with OAuth or supplies a personal access token.
  3. For a local setup, the host starts the published container image as a subprocess and passes the token in an environment variable. Client and server then exchange messages over the container's standard input and output.
  4. In VS Code the entry lives in the workspace file .vscode/mcp.json or in the mcp.json of the user profile. Servers defined in a workspace start under Workspace Trust. For servers from other sources, VS Code asks for a trust decision when the server first starts or its configuration changes.
  5. VS Code discovers the server's tools and offers them in chat. From this point the exchange is the list-then-call pattern described in this lesson.
  6. The same server, unchanged, is configured in the other hosts for which the README links install guides. Each host contributes only its generic MCP client.
  7. An operator narrows what the model can do with the toolsets option, an explicit list of tools or read-only mode.

Why this approach fits

GitHub maintains one codebase, and the number of hosts that can use it grows without GitHub writing host-specific code. Each host gains GitHub support without containing any GitHub-specific code. This is the M + N arithmetic of the introduction seen from the side of a service provider. The two entries in the configuration also show that a server is a role and not a location: the same tools are reachable from a hosted service and from a local container.

Limitation or tradeoff

The protocol removes duplicated code and leaves other differences in place. The README still links a separate install guide for each host, and it limits the hosted option to hosts with remote server support. A large server also has a cost that the protocol cannot hide: every tool definition a host loads takes space in the model's context, which is why the README recommends enabling only the toolsets you need. Finally, a local server runs on your machine with your token. The VS Code documentation warns that local MCP servers can run arbitrary code and tells users to add servers only from trusted sources.

What the sources document

  • The README says the GitHub MCP Server connects AI tools directly to GitHub's platform, so that agents, assistants and chatbots can read repositories and code files, manage issues and pull requests, analyse code and automate workflows. [20]
  • The README states that the remote GitHub MCP Server is hosted by GitHub, and that using it requires a compatible MCP host with remote server support, naming VS Code 1.101 or later, Claude Desktop, Cursor and Windsurf. [20]
  • The README states that enabling only the toolsets you need can help the LLM with tool choice and reduce the context size, and that write tools are skipped when read-only mode is set, even if they were requested explicitly. [20]
  • The VS Code documentation's example mcp.json contains an entry of type http for GitHub's endpoint alongside a server started with a command. It says that VS Code discovers a server's tools and makes them available in chat, that workspace servers inherit Workspace Trust, and that for servers from other sources a dialog is shown when a server first starts or its configuration changes. [19]
  • The MCP architecture overview states that Visual Studio Code acts as an MCP host and that its runtime instantiates one MCP client object for each server it connects to. [2]

Example 2 of 5

OpenAI's Responses API acting as the MCP client for remote servers

OpenAIDocumented in official docs

OpenAI's API documentation has a guide, MCP servers, that describes how a Responses API request can name a remote MCP server so that the platform lists and calls the server's tools on the developer's behalf. [21]

The problem

An application that calls a hosted model API often has no convenient place to run MCP clients. Without help, the developer must connect to each server, fetch its tool list, convert the tools into function definitions, relay every call and return every result.

The guide also names the risk that comes with the convenience. Tool calls send data to a server that a third party operates, so the developer needs control over which calls are allowed to happen.

Where this topic fits

The client role moves from the developer's program into the API platform. The developer declares a server in the tools array of a request, with a label and a URL. The platform lists the server's tools, lets the model choose among them, calls the chosen tool and gives the result back to the model. The developer's program keeps two jobs: answering approval requests and supplying credentials.

How it is applied, step by step

  1. The developer adds a tool of type mcp to the request, with a label and the URL of a remote server.
  2. The API connects to the server over Streamable HTTP or HTTP/SSE and asks for its tool list. The imported tools appear in the response as an mcp_list_tools output item.
  3. While that item stays in the context sent with later requests, the API does not fetch the list again, so one listing serves a conversation of many turns.
  4. When the model wants to call a tool, the default behaviour is to return an mcp_approval_request item and wait for an mcp_approval_response in the next request. The developer can switch approvals off for all tools or for named tools.
  5. The API calls the tool on the server and records an mcp_call item that holds the arguments the model chose and the output the server returned.
  6. To keep cost and latency down, the developer passes allowed_tools so that only the named tools are imported.

Why this approach fits

Because the server side is standard, the platform can talk to any conforming remote server with one client implementation, and a service provider's single server is reachable from this API as well as from desktop hosts. The tool list arrives as an ordinary output item, which makes the discovery step of the protocol visible in the conversation and reusable across turns. Approval requests give the developer the consent step that the protocol expects a host to provide.

Limitation or tradeoff

Only servers the platform can reach are usable. The guide covers remote servers on the public internet and a tunnel product for local or private ones, and the transports it names are HTTP-based, so a stdio-only server needs something in front of it. Imported tool definitions are billed as tokens, and the guide notes that servers with dozens of tools raise cost and latency. Data sent to a server leaves the platform and falls under that server's own policies. The guide also warns about prompt injection through servers, and it recommends official servers run by the service provider, approval for sensitive actions and logging of the data that is shared.

What the sources document

  • The guide states that the Responses API works with remote MCP servers that support either the Streamable HTTP or the HTTP/SSE transport protocols. [21]
  • When a remote MCP server is specified in the tools parameter, the API attempts to get a list of tools from it, and a successful listing appears as an mcp_list_tools output item. As long as that item is present in the context of a request, the API does not fetch the list again. [21]
  • By default OpenAI requests the developer's approval before any data is shared with a remote MCP server, by creating an mcp_approval_request item. The require_approval setting can be set to never for all tools or for a named list of tools. [21]
  • The guide says that some MCP servers have dozens of tools and that exposing many tools to the model can result in high cost and latency. The allowed_tools parameter imports only the named tools, and users pay only for tokens used when importing tool definitions or making tool calls. [21]
  • The guide states that the Responses API does not store the value provided in the authorization field. It recommends picking official servers hosted by the service providers themselves and logging the data sent to MCP servers. [21]

MCP Inspector: choosing between the initialize handshake and server/discover when debugging

Model Context Protocol projectDocumented in official docs

The MCP Inspector is the project's own tool for testing and debugging servers. Its documentation page Protocol eras describes how it connects to servers of either era, and the stdio transport specification defines the probe that its auto setting performs. [13][8]

The problem

Since revision 2026-07-28 a server under test may speak the handshake protocol, the per-request protocol or both. A debugging client has to connect to all three kinds and show the developer exactly what was sent. Probing automatically has a cost that the page spells out: a server/discover probe stalls against a legacy stdio server that stays silent, and it adds messages to the transcript the developer came to read.

Where this topic fits

The Inspector takes the host and client roles against the server being tested. Its era setting decides the first message of the connection, which is the step this lesson calls version and capability negotiation. What the tool shows afterwards, such as which tabs appear, follows from what that first exchange returned.

How it is applied, step by step

  1. Each configured server has a protocolEra value of legacy, auto or modern. It is set in the web client's server settings or in a config file, and a command-line flag overrides it for one run.
  2. With legacy, which is the default, the Inspector sends a plain initialize request and does not probe.
  3. With auto, it sends server/discover first and falls back to initialize on any outcome that is not modern.
  4. With modern, it pins revision 2026-07-28 and has no fallback, so a server that is not modern fails visibly.
  5. After connecting, the tool shows the negotiated era. On a modern connection the capabilities, the instructions and the supported versions come from the server/discover result.
  6. Features are then gated by what the server declared. The Tasks tab appears for a legacy server that advertises a tasks capability and for a modern server that advertises the tasks extension.
  7. When a server rejects a version, the Protocol tab shows the typed error -32022 together with the versions the server does support.

Why this approach fits

A debugging tool is where the negotiation has to be explicit, because the developer needs to know which dialect the server was offered before trusting anything else on the screen. The three settings match the three kinds of client the specification describes: legacy only, dual-era and modern only. The default is instructive too. The specification recommends probing for clients in general, and the Inspector declines to probe unless asked because its job is to show unmodified traffic.

Limitation or tradeoff

With the default setting a modern-only server fails to connect until the developer changes the era, which can look like a broken server. The auto setting relies on a timeout to recognise a silent legacy stdio server, so connecting is slowest in exactly that case. The page pins one modern revision, 2026-07-28, and that will have to change when a later revision is published.

What the sources document

  • The Inspector treats protocol era as a per-server setting that is independent of the transport, with the values legacy, auto and modern. Legacy sends a plain initialize with no probing, auto probes server/discover first and falls back to initialize on any non-modern outcome, and modern pins exactly 2026-07-28 with no fallback. [13]
  • Legacy is the default. The page explains that a debugging tool must not auto-probe, because a server/discover probe stalls against silent legacy stdio servers and pollutes the recorded transcript. [13]
  • On a modern connection, server/discover supplies the capabilities, including extensions, the instructions and the list of supported versions, and the server's name and version arrive in the result's _meta. [13]
  • The page says a legacy Streamable HTTP connection may carry a server-assigned session id, while a modern connection is sessionless and per-request. It lists test tools that return JSON-RPC error -32021 for a missing client capability and -32022 for an unsupported version. [13]
  • The stdio transport specification says a dual-era client should probe with server/discover. A discovery result or a recognised modern error identifies a modern server, and any other error or no response within a reasonable timeout identifies a legacy server. The fallback must not be keyed to one specific error code. [8]

4Common mistakes

  1. Printing debug output to standard output from a stdio server.

    Why it causes problems
    On stdio the server's standard output is the message channel, and the specification forbids writing anything to it that is not a valid MCP message. One stray line makes the client fail to parse a message or leaves it reading replies that are out of step with its requests.
    How to recognise it
    The client reports a JSON parse error or hangs right after the server starts. The server seems fine when you type requests into it by hand, because you skip over the extra lines without noticing.
    How to fix it
    Send all logging to standard error, which the stdio transport leaves free for that purpose, and flush standard output after every message.

  2. Keeping state in the server between requests, such as a current project chosen by an earlier call.

    Why it causes problems
    Revision 2026-07-28 requires that each request can be processed on its own. Requests from one user may arrive on different connections or server instances, and one stdio process may serve several conversations, so remembered state is lost or leaks into another conversation.
    How to recognise it
    The server works with one local client and fails after a restart, behind a load balancer, or when two conversations share it. Tool results depend on the order of earlier calls.
    How to fix it
    Return an explicit handle from the call that creates the state and require that handle as an argument on later calls. On an authenticated server, check the caller's authorization against the handle every time.

  3. Hard-coding one era, by always opening with initialize or by sending modern requests without a probe.

    Why it causes problems
    A legacy-only client cannot connect to a modern-only server at all. A modern-only client that skips the probe can have a request such as tools/call processed by a legacy server under legacy rules, which looks like success.
    How to recognise it
    Connections fail on the very first message with an unknown method or missing _meta error, or a client works with new servers and fails with every older one.
    How to fix it
    On stdio, probe with server/discover, treat a result or a recognised modern error as modern and anything else as legacy, and cache the answer per server. If you support one era only, say so in the error shown to the user and include the versions you do support.

  4. Calling methods or relying on features that the other side never declared.

    Why it causes problems
    A client that calls resources/list on a tools-only server gets -32601 and may report the whole server as broken. A server that needs user input from a client that did not declare elicitation cannot complete the request and has to fail it with -32021.
    How to recognise it
    Error codes -32601 or -32021 appear with some hosts and not with others, depending on which features each host implements.
    How to fix it
    Read the server's capabilities from server/discover, or from the initialize response on a legacy connection, before using a feature. In a server, check the client capabilities on the request and offer a path that needs none of the optional ones.

  5. Treating a connected server as trusted code and its tool descriptions as facts.

    Why it causes problems
    A server receives whatever arguments the model sends and returns text that the model reads. A malicious or compromised server can collect data or plant instructions, and a local server runs with the user's permissions on the user's machine.
    How to recognise it
    Servers were added from publishers nobody can name, tools run without any confirmation step, and nobody can say what data was sent to which server.
    How to fix it
    Install servers only from operators you can identify, require approval for actions that change or send data, load only the tools you need, and log tool inputs so that data sharing can be reviewed.

  6. Loading every tool of every connected server into the model's context.

    Why it causes problems
    MCP delivers tool definitions to the host, and the host still has to pass them to the model through ordinary tool calling. Each definition costs input tokens on every model call, and a long list makes it harder for the model to pick the right tool.
    How to recognise it
    Input token counts jump when a server is connected even if none of its tools is used, and the model starts choosing similar tools from the wrong server.
    How to fix it
    Enable only the tool groups a task needs, for example with a server's toolset options or a host's allowed-tools filter. When two servers expose a tool with the same name, have the host prefix tool names with a server identifier.

Write a client that works out whether a stdio server is legacy or modern

CodingIntermediateAbout 45 min (estimate)Hypothetical scenario

python
import json
import sys

LEGACY = "2025-11-25"


def reply_to(message, initialized):
    if message["method"] == "initialize":
        return {"result": {"protocolVersion": LEGACY, "capabilities": {"tools": {}},
                           "serverInfo": {"name": "legacy-demo", "version": "1.0.0"}}}
    if message["method"] == "tools/list" and initialized:
        return {"result": {"tools": []}}
    return {"error": {"code": -32601, "message": "Method not found"}}


def main():
    initialized = False
    for line in sys.stdin:
        message = json.loads(line)
        if message.get("method") == "notifications/initialized":
            initialized = True
        if "id" in message:
            reply = reply_to(message, initialized)
            print(json.dumps({"jsonrpc": "2.0", "id": message["id"], **reply}), flush=True)

Use only the Python standard library.

  • Treat a result as modern. Treat an error whose code is one of the MCP-defined codes -32020, -32021 or -32022 as modern too, and take the version list from data.supported without falling back.

python
import json
import subprocess
import sys

MODERN, LEGACY = "2026-07-28", "2025-11-25"
KEY = "io.modelcontextprotocol/"
MODERN_ERROR_CODES = {-32020, -32021, -32022}
META = {KEY + "protocolVersion": MODERN, KEY + "clientCapabilities": {}}


def send(server, message):
    server.stdin.write(json.dumps({"jsonrpc": "2.0", **message}) + "\n")
    server.stdin.flush()


def call(server, message):
    send(server, message)
    return json.loads(server.stdout.readline())


def modern_versions(probe):
    """Versions a modern server offers, or None when the answer is not a modern one."""
    if "result" in probe:
        return probe["result"]["supportedVersions"]
    if probe["error"]["code"] in MODERN_ERROR_CODES:
        return probe["error"].get("data", {}).get("supported", [])
    return None


def connect(command):
    server = subprocess.Popen(command, text=True, stdin=subprocess.PIPE, stdout=subprocess.PIPE)
    probe = call(server, {"id": 1, "method": "server/discover", "params": {"_meta": META}})
    offered = modern_versions(probe)
    if offered is None:                                    # legacy: do the handshake
        hello = call(server, {"id": 2, "method": "initialize", "params": {
            "protocolVersion": LEGACY, "capabilities": {},
            "clientInfo": {"name": "probe", "version": "1.0.0"}}})
        version = hello["result"]["protocolVersion"]
        if version != LEGACY:
            raise RuntimeError(f"server chose {version}, which this client does not speak")
        send(server, {"method": "notifications/initialized"})
        return server, "legacy", version
    if MODERN not in offered:                              # modern, but no shared version
        raise RuntimeError(f"no shared version; server supports {offered}")
    return server, "modern", MODERN


def list_tools(server, era):
    params = {"_meta": META} if era == "modern" else {}
    return call(server, {"id": 3, "method": "tools/list", "params": params})["result"]["tools"]


if __name__ == "__main__":
    for script in (["mcp_demo.py", "serve"], ["legacy_server.py"]):
        server, era, version = connect([sys.executable, *script])
        names = [tool["name"] for tool in list_tools(server, era)]
        print(f"{script[0]}: era={era} version={version} tools={names}")
        server.stdin.close()
        server.wait()

Output:

text
mcp_demo.py: era=modern version=2026-07-28 tools=['add']
legacy_server.py: era=legacy version=2025-11-25 tools=[]

How it works:

  • modern_versions is the whole decision. A result means modern. An error with one of the three codes that only a modern server can send also means modern, and its data.supported list replaces the discovery result. Anything else returns None, which the caller reads as legacy. The function never compares against -32601, so a legacy server that answers the probe with -32602 or any other code is handled the same way.
  • In the legacy branch the client proposes 2025-11-25 and compares the server's answer with it. This is the echo rule: a server that cannot use the proposed version answers with a different one, and a client that does not speak that version must give up.
  • notifications/initialized goes through send and not call, because a notification has no id and gets no reply. Reading a line after it would block forever.
  • list_tools builds params differently for each era. The legacy result has no resultType, and the code does not look for one.

One rule is missing on purpose. The specification also treats silence as legacy: a server that does not answer the probe within a reasonable time is assumed to need initialize. call uses a blocking readline, so against a silent server this script would wait forever. A real client reads with a timeout, for example from a reader thread, and that wait is the reason the MCP Inspector does not probe unless you ask it to.

  • After you change your modern version to one the demo server does not support, does the script stop with the supported list and without sending initialize?
  • Can you point to the line where a real client needs a timeout, and say which era a silent server is assumed to be?

B. JSON-RPC itself allows a null id, and MCP removes that option: an id must be a string or an integer. A reply with a null id could not be matched to its request reliably, so the server should reject the message as an invalid request.

C. The id matches line A, so this is the reply to tools/list. In revision 2026-07-28 every result carries resultType, and list results also carry the caching fields ttlMs and cacheScope. A client must still accept it, because a missing resultType is read as "complete" for compatibility with older servers. The line is evidence that the server is not really implementing 2026-07-28.

D. The method name says notification and the id says request. Notifications must not include an id. There are two further problems in the modern revision: a server must not send requests to a client at all, and a list-changed notification is only delivered to a client that opened a subscriptions/listen stream, tagged with that subscription's id in _meta.

E. params contains only name and arguments, so the protocol version and the client capabilities are both absent. A modern server must reject the request with -32602 (invalid params). The same bytes would be a correct tools/call on a legacy connection after initialize, which is why the specification calls such methods era-ambiguous and recommends probing first.

F. This is a well-formed error response for a request with id 10 that asked for 2025-06-18. The client should retry with 2026-07-28 if it speaks that revision, and otherwise report to the user that no shared version exists. It must not fall back to initialize: only a modern server sends -32022, so the era is already known.
