What Are AI Agents? (Agents vs Workflows)

An AI agent is a system in which a large language model uses tools in a loop to reach a goal, choosing each next step itself from the results of the steps before. A workflow also combines model calls and tools, but a developer fixes the steps and their order in code.

1Overview

Why it matters

The word agent is attached to almost every AI product, from a chatbot that makes one model call to a system that edits code unattended for an hour. These are different architectures with different costs, failure modes and testing needs. If you cannot tell them apart, you cannot judge a vendor's claim, estimate a bill or decide what to build.

The distinction decides real outcomes. A team that builds an agent for a task whose steps never change pays for several times the tokens, waits longer for each answer and gets a system that behaves differently from run to run, with nothing gained. A team that hard-codes a workflow for a task whose steps cannot be predicted ends up with a growing pile of special cases that still miss what users ask. Developers, product managers and anyone who reviews AI designs need one question they can put to any system: who decides what happens next, the code or the model?

Key terms

AI agent
A system in which a language model uses tools in a loop to reach a goal, deciding each next step from the results so far.
Workflow
A system in which model calls and tools run along paths a developer wrote in code. The model fills in steps but does not choose the overall sequence.
Agentic system
Anthropic's umbrella term for both workflows and agents: any system that orchestrates model calls, usually with tools, instead of making a single call.
Augmented LLM
A single model call extended with retrieval, tools and memory. It is the building block of both workflows and agents.
Tool
A function that the model can ask for by name and that your program runs, such as a database lookup or sending a message.
Harness
The program around the model that supplies tools, runs the loop and manages what the model sees. Also called scaffolding.
Ground truth
What really happened in the environment after an action, such as a test result or an API response, reported back to the model so it can judge its progress.
Guardrail
A check or limit enforced outside the model, such as a step cap, a permission prompt or a rule inside a tool, that bounds what an agent can do.

2Explanation

Introduction

In Prompt Engineering you worked with one kind of interaction: you write a prompt, the model writes a response, and that is the end of it. The model produces text and nothing else. It cannot look anything up, change a file or check whether its answer was right.

Two additions change that. First, give the model tools: functions your program runs when the model asks for them, such as searching a database or sending an email. Second, put the model in a loop: after each tool runs, show the model the result and let it decide what to do next. A model using tools in a loop to reach a goal is an AI agent. Anthropic's guide Building effective agents (opens in a new tab) describes agents as, in most cases, simply LLMs that use tools in a loop, guided by feedback from their environment. Simon Willison's one-line version is "An LLM agent runs tools in a loop to achieve a goal", and his 2025 post (opens in a new tab) explains why he thinks the term has finally settled on that meaning.

A kitchen makes the idea concrete. A recipe is a fixed list of steps: chop, fry, simmer for ten minutes, serve. Anyone can follow it and the result is predictable, but it fails the moment something unexpected happens, such as a missing ingredient. A cook who is told "make dinner from whatever is in the fridge" works differently. The cook looks, decides, tastes, adjusts and decides again. Nobody wrote those steps down in advance, because each one depends on how the last one turned out.

Software built on language models comes in the same two styles:

  • A workflow is the recipe. A developer writes the steps and their order in code. The model fills in individual steps, for example classifying a message or drafting a reply.
  • An agent is the cook. The developer supplies a goal, a set of tools and some limits. The model chooses the steps.

Both are useful, and many production systems contain both. This lesson covers the building block they share (the augmented LLM), the exact difference between a workflow and an agent, what an agent's extra freedom costs, the tasks agents are typically used for, and how to recognise when you should not build one. The Agent Loop then shows how to implement the loop itself.

How it works

The building block: the augmented LLM

A bare model call maps text to text. Anthropic's guide calls the basic unit of every system in this lesson the augmented LLM: a model call extended with three capabilities.

AugmentationWhat it addsCovered in
RetrievalLooks up documents or records and puts them in the prompt, so the model answers from your dataRAG
ToolsLets the model request a function call, which your program executes and reports backTool Calling
MemoryKeeps information from earlier steps or sessions available to later onesAgent Memory

The model does not execute anything itself. The Hugging Face Agents Course says it plainly: an LLM can only generate text, and it acts on the world because developers gave it tools (What is an Agent? (opens in a new tab)). An augmented LLM on its own is still a single step. What surrounds it makes the system a workflow or an agent.

Workflows: the code decides

Anthropic defines workflows as systems in which LLMs and tools are orchestrated along code paths that were defined in advance. You can read the control flow in the source before any request arrives. The block below is pseudocode:

python
def handle(ticket):                      # a workflow: the steps are fixed here
    category = llm_classify(ticket)      # model call 1
    if category == "refund":
        return llm_draft_refund_reply(ticket, lookup_order(ticket))   # model call 2
    return llm_draft_general_reply(ticket)                            # model call 2

The model's output can select a branch, but only a branch a developer wrote. The guide describes five workflow patterns, each with its own lesson here: prompt chaining, routing, parallelization, orchestrator-workers and evaluator-optimizer.

Agents: the model decides

Agents, in the same guide, are systems in which the LLM directs its own process and tool use as it goes and stays in control of how the task gets done. The code no longer lists the steps. It only runs a loop (pseudocode again):

python
def run(goal, tools, max_steps=20):      # an agent: the model picks each step
    history = [goal]
    for _ in range(max_steps):
        reply = llm(history, tools)      # the model chooses a tool or finishes
        if reply.is_final:
            return reply.answer
        result = tools[reply.tool](**reply.args)   # your program runs the tool
        history = [*history, reply, result]        # feedback for the next decision
    return "stopped: step limit reached"

OpenAI's practical guide to building agents (opens in a new tab) lists three core components: a model that reasons and decides, tools that act, and instructions that define how the agent should behave. The fourth part is the loop that connects them, which the guide calls central to how an agent runs. The program that runs the loop, supplies the tools and manages what the model sees is often called the harness. Three details of that loop matter:

  • Feedback. After every action the model sees what really happened, such as a test result or an API response. Anthropic calls this ground truth from the environment. It is what lets an agent notice a mistake and correct it.
  • Limits. A stopping condition such as a maximum number of steps keeps control with the program.
  • Oversight. Autonomy is not all or nothing. Agents can pause for a person at checkpoints or when they are blocked. OpenAI's guide recommends human review for high-risk actions, such as large refunds or payments, and whenever an agent exceeds a failure threshold.

One question tells them apart

Ask: who decides the next step? If you can list the steps by reading the code, it is a workflow. If the list exists only after the run has finished, it is an agent.

Agency is a spectrum more than a switch. The smolagents documentation (opens in a new tab) grades systems by how much the model's output controls the program: it has no effect on program flow, it picks an if/else branch (a router), it picks which function runs (a tool call), or it controls whether the loop continues (a multi-step agent).

OpenAI's guide draws the same line from the other side: applications that use an LLM but do not let it control how the workflow executes, such as simple chatbots, single-turn calls and sentiment classifiers, are not agents.

Names are unreliable. Products built as fixed pipelines are often called agents. Classify a system by its control flow, never by its label.

What the freedom costs

Anthropic's guide says agentic systems often trade latency and cost for better task performance. Three costs grow with every step the model decides for itself:

  • Tokens. Anthropic reports that in its data agents typically use about 4 times more tokens than chat interactions, and multi-agent systems about 15 times more (How we built our multi-agent research system (opens in a new tab)).
  • Time. Each step is a full model call plus a tool execution. Anthropic's SWE-bench coding agent (opens in a new tab) solved one example task in 12 steps, but many successful runs took hundreds of turns.
  • Compounding errors. If each step succeeds independently with probability ppp, a run of nnn steps with no way to recover succeeds with probability
P(all n steps succeed)=pnP(\text{all } n \text{ steps succeed}) = p^nP(all n steps succeed)=pn

With p=0.95p = 0.95p=0.95 and n=10n = 10n=10 this is 0.9510≈0.600.95^{10} \approx 0.600.9510≈0.60. A step that is right 19 times out of 20 gives a ten-step run that fails 4 times in 10.

Treat the formula as a warning, not a forecast. Feedback from the environment lets an agent catch and repair a bad step, which is why agents work best where results can be checked.

Typical use cases

Agents are used most where a task is open-ended and its results can be checked:

  • Coding. Tests give objective feedback, and the agent can iterate until they pass.
  • Customer support. A conversation that needs both information (order history, help articles) and actions (refunds, ticket updates), with success measured by resolution.
  • Computer use and research. Operating software through its interface, or searching many sources, where the path depends on what is found. Computer use is one of the examples in Anthropic's guide, and Anthropic describes its Research feature in the multi-agent post linked above.

Anthropic's guide singles out the first two as particularly promising and says what they share: they mix conversation with action, success can be judged clearly, the work produces feedback the agent can use, and people stay meaningfully involved. Microsoft's AI Agents for Beginners (opens in a new tab) gives a matching test: open-ended problems, multi-step processes and improvement over time.

When not to build an agent

Anthropic's first recommendation is to look for the simplest design that works, which can mean building no agentic system at all. Work up this ladder and stop at the first rung that meets your quality bar:

  1. One LLM call with a good prompt, retrieved context and examples. The guide says this is usually enough for many applications.
  2. A workflow, when the task splits into steps you can name in advance.
  3. An agent, when you cannot predict the number of steps or hardcode a path, and you can test it in a sandbox with guardrails.

Skip the agent when the steps are known, when an answer is needed within a couple of seconds, when a wrong action cannot be undone, or when exact rules must hold every time. Rules of that kind belong in code. An agent is also the wrong first move when you have no way to measure success, because you cannot tell whether the extra complexity helped.

Worked example: One refund request, two designs: a fixed workflow and an agent on the same two tickets

A small shop wants to automate refund requests. Refunds are allowed within 30 days of delivery. We build the feature twice with the same three tools and run both versions on two tickets. So that everyone gets identical output, the model calls are replaced by small stand-in functions whose names start with llm_. Everything else is real, runnable code.

Save this as two_designs.py (Python 3.9 or later, standard library only).

python
import re

ORDERS = {
    "A17": {"item": "kettle", "total": 40.0, "days_ago": 12},
    "B42": {"item": "desk lamp", "total": 65.0, "days_ago": 9},
    "B43": {"item": "phone case", "total": 15.0, "days_ago": 45},
}
CUSTOMERS = {"dana@example.com": ["A17"], "lee@example.com": ["B42", "B43"]}
REFUND_WINDOW_DAYS = 30
MAX_STEPS = 6


# Tools: ordinary functions. Both designs use the same three.
def get_order(order_id):
    return {"id": order_id, **ORDERS[order_id]}


def find_orders(email):
    return [{"id": key, "item": ORDERS[key]["item"]} for key in CUSTOMERS.get(email, [])]


def refund(order_id):
    if ORDERS[order_id]["days_ago"] > REFUND_WINDOW_DAYS:  # the rule is enforced in code
        return f"ERROR: {order_id} is outside the {REFUND_WINDOW_DAYS}-day window"
    return f"refunded {order_id} ({ORDERS[order_id]['total']:.2f})"


TOOLS = {"get_order": get_order, "find_orders": find_orders, "refund": refund}


# Stand-ins for model calls, so that everyone gets the same output.
def llm_extract_order_id(text):
    match = re.search(r"\b[A-Z]\d{2}\b", text)
    return match.group(0) if match else None


def llm_write_reply(outcome):
    return outcome


def llm_choose_next_step(ticket, history):
    """Return ("tool", name, args) or ("final", answer). A real agent asks an LLM this."""
    if not history:
        order_id = llm_extract_order_id(ticket["text"])
        if order_id:
            return ("tool", "get_order", {"order_id": order_id})
        return ("tool", "find_orders", {"email": ticket["email"]})
    name, result = history[-1]
    if name == "find_orders":
        matches = [order["id"] for order in result if order["item"] in ticket["text"]]
        if len(matches) != 1:
            return ("final", "asked the customer which order they mean")
        return ("tool", "get_order", {"order_id": matches[0]})
    if name == "get_order":
        return ("tool", "refund", {"order_id": result["id"]})
    return ("final", result)


def run_workflow(ticket):
    """Design 1, a workflow: this function fixes the order of the steps."""
    order_id = llm_extract_order_id(ticket["text"])       # model call 1
    if order_id is None:                                  # gate written by a developer
        return {"result": "escalated to a human", "model_calls": 1, "tool_calls": 0}
    order = get_order(order_id)                           # tool call 1
    outcome = refund(order["id"])                         # tool call 2
    return {"result": llm_write_reply(outcome), "model_calls": 2, "tool_calls": 2}


def run_agent(ticket):
    """Design 2, an agent: the model's reply decides what happens next."""
    history = []
    for step in range(1, MAX_STEPS + 1):
        decision = llm_choose_next_step(ticket, history)  # one model call per step
        if decision[0] == "final":
            return {"result": decision[1], "model_calls": step, "tool_calls": len(history)}
        _, name, args = decision
        result = TOOLS[name](**args)                      # the program runs the tool
        print(f"    step {step}: {name}({args}) -> {result}")
        history = [*history, (name, result)]              # the result is fed back
    return {"result": "stopped: step limit", "model_calls": MAX_STEPS, "tool_calls": len(history)}


TICKETS = [
    {"email": "dana@example.com", "text": "Order A17: my kettle arrived broken. Please refund it."},
    {"email": "lee@example.com", "text": "My desk lamp stopped working. I want my money back."},
]

if __name__ == "__main__":
    for number, ticket in enumerate(TICKETS, start=1):
        print(f"ticket {number}: {ticket['text']}")
        print("  workflow:", run_workflow(ticket))
        print("  agent:   ", run_agent(ticket))

Run python3 two_designs.py:

text

  workflow: {'result': 'refunded A17 (40.00)', 'model_calls': 2, 'tool_calls': 2}
    step 1: get_order({'order_id': 'A17'}) -> {'id': 'A17', 'item': 'kettle', 'total': 40.0, 'days_ago': 12}
    step 2: refund({'order_id': 'A17'}) -> refunded A17 (40.00)
  agent:    {'result': 'refunded A17 (40.00)', 'model_calls': 3, 'tool_calls': 2}
ticket 2: My desk lamp stopped working. I want my money back.
  workflow: {'result': 'escalated to a human', 'model_calls': 1, 'tool_calls': 0}
    step 1: find_orders({'email': 'lee@example.com'}) -> [{'id': 'B42', 'item': 'desk lamp'}, {'id': 'B43', 'item': 'phone case'}]
    step 2: get_order({'order_id': 'B42'}) -> {'id': 'B42', 'item': 'desk lamp', 'total': 65.0, 'days_ago': 9}
    step 3: refund({'order_id': 'B42'}) -> refunded B42 (65.00)
  agent:    {'result': 'refunded B42 (65.00)', 'model_calls': 4, 'tool_calls': 3}

What the output shows:

  • Ticket 1 is the case the developer planned for. Both designs issue the same refund. The workflow needs 2 model calls and the agent needs 3, because the agent spends one call on each decision, including the decision that it has finished.
  • Ticket 2 has no order number. The workflow has no step for that, so its gate hands the ticket to a person. The agent looks up the customer's orders, matches "desk lamp" to B42, checks it and refunds it in 4 model calls. No line of run_agent lists that path. The loop takes each step from the stand-in's reply to the tool results, as it would from a model's.
  • The rule is in the tool. refund checks the 30-day window itself. Change ticket 2 to "My phone case cracked. I want my money back." and step 3 returns ERROR: B43 is outside the 30-day window. Neither design can break the rule, whatever the model decides.

Now put numbers on the trade. Suppose 90% of tickets look like ticket 1 and 10% look like ticket 2. Per 1,000 tickets:

DesignModel callsTickets sent to a person
Workflow900 × 2 + 100 × 1 = 1,900100
Agent900 × 3 + 100 × 4 = 3,1000

The agent makes 3,100 / 1,900 ≈ 1.63 times as many model calls and removes 100 hand-offs. Whether that is worth it depends on what a hand-off costs, and on how often a real model would pick a wrong step, which this scripted stand-in never does. To try a real model, replace the body of llm_choose_next_step with an API call that sends the ticket, the history and the tool list (see Tool Calling).

Edge cases and limitations

A product called an agent can be a workflow
Uber's QueryGPT article describes an intent agent, a table agent and a column prune agent, each an LLM call given a single unit of work. The article presents them as successive stages and does not describe a model choosing which component runs next, so by this lesson's test the system reads as a workflow. The label tells you nothing about cost or risk. Ask who decides the next step, then plan testing and limits from the answer.
Workflows and agents nest inside each other
Classification applies to each component, not to the whole product. Stripe's blueprints are workflows in which some nodes are agent loops. Airbnb's platform goes the other way and offers its existing workflows to an LLM as tools. When you review a design, mark each part as code-decided or model-decided, because the model-decided parts are where step limits, sandboxes and evaluations are needed.
One tool call does not make an agent
A chat assistant that calls a weather function once and then answers has tools but no loop. The code knows there will be at most two model calls. The smolagents documentation lists the two cases as separate rows of its agency table: in a tool call the model's output controls which function runs, and in a multi-step agent it also controls whether the loop continues. Treat the first as one augmented LLM step. It needs none of the step limits or whole-run tests that an agent needs.
The multiplication rule can mislead in both directions
The formula p to the power n assumes independent failures and no recovery. It is too pessimistic when the agent gets feedback it can act on, such as a failing test it can read and fix. It is too optimistic when failures are silent. Anthropic's SWE-bench write-up notes that the model often believed it had succeeded when hidden tests showed it had not. Use the formula to size risk, then measure real runs.
Orchestrator-workers sits on the boundary
In the orchestrator-workers pattern a model decides at run time which subtasks to create, yet Anthropic lists it among the workflows. One way to read this is that the surrounding structure (split, delegate, combine) is still fixed in code. Do not spend effort arguing which word applies. Note which decisions the model makes and bound those, for example with a cap on the number of subtasks.

When to use it, and when something simpler is enough

Use it when

  • Build an agent when you cannot predict how many steps a task needs or in what order, because each result changes what should happen next. Debugging and open-ended research are typical.
  • The environment returns feedback the model can check itself against, such as test output, API responses or search results.
  • Wrong actions are cheap to undo, confined to a sandbox, or held for a person to approve, so a bad step does not cause lasting damage.
  • The task is valuable enough to pay for several times the tokens of a single call, and users can accept a response time that varies from run to run.
  • Choose a workflow when the task splits into steps you can name in advance and you want the same path, cost and behaviour on every run.

Think twice when

  • Avoid an agent when one well-prompted call with retrieved context and a few examples already meets the quality bar.
  • The steps are known and stable. Hard-coding them as a workflow is cheaper, faster and easier to test than asking a model to rediscover them on every run.
  • The answer is needed within a couple of seconds. Every model-decided step adds a full model call and a tool execution.
  • An exact rule must hold every time, or an action cannot be reversed or reviewed, as with payments or claims. Enforce such rules in code.
  • You have no test set or success measure. Without one you cannot show that the added autonomy improved anything.

A simpler alternative. Start with a single LLM call that has a clear prompt, retrieved context and a few examples. If the task has several stages, move to a workflow such as a prompt chain or a router, where your code calls the model at fixed points. These stop being enough when real inputs keep falling outside the branches you wrote and each fix adds another special case. That is the sign that the model needs to choose the steps.

Key takeaways

  • An AI agent is a language model that uses tools in a loop to reach a goal, choosing each next step from the results of the previous ones.
  • A workflow uses the same building blocks, but a developer fixes the steps in code. To classify any system, ask who decides the next step.
  • The augmented LLM, a model call with retrieval, tools and memory, is the unit that both workflows and agents are built from, and one such call is often enough.
  • An agent's freedom costs tokens and time, and errors compound across steps, so agents fit tasks that are open-ended, checkable through feedback and valuable enough to justify the cost.
  • Try a single call first, then a workflow, and build an agent only when simpler designs demonstrably fall short.
  • Rules that must always hold belong in code or inside tools, and every agent needs limits and human oversight for risky actions.

Example 1 of 5

Claude Code: a coding agent that chooses its own next tool call

AnthropicDocumented in official docs

Claude Code is Anthropic's coding agent for the terminal, IDEs and other interfaces. Its official documentation page How Claude Code works describes the agentic loop the product runs, the built-in tools the model can call and the controls a user has over it. [11]

The problem

A request such as "fix the failing tests" cannot be turned into a fixed list of steps. Which files to read, what to change and whether the change worked all depend on what the previous step revealed. The documentation says Claude decides what each step requires from what it learned in the step before.

Where this topic fits

This is the agent end of the spectrum. The model does the reasoning, the tools do the acting, and Claude Code is the layer around the model that supplies the tools and manages what the model sees. The documentation calls that layer the agentic harness. The person who gave the task stays in the loop: they can interrupt at any point, and a permission mode decides which actions need approval first.

How it is applied, step by step

  1. The user states a goal in plain language, without listing the files to read or the commands to run.
  2. The model gathers context by calling search and file-reading tools. The harness executes each call and returns the result to the model.
  3. The model takes action by asking for file edits or shell commands, which the harness runs subject to the current permission mode.
  4. The model verifies its work, for example by running the tests again, and uses the output to decide whether to continue, change approach or stop.
  5. The cycle repeats until the model judges the task complete or the user interrupts to steer it in a different direction.
  6. Before each file edit the current contents are snapshotted, so the user can rewind local changes if the agent went wrong.

Why this approach fits

Coding has the properties that make an agent worth its cost. The path cannot be hardcoded, because every bug is different. The environment gives feedback the model can check, since a test passes or fails. Local mistakes are recoverable, because edits are snapshotted. A fixed workflow of "read file, edit file, run tests" would fail on the first task that needed two files or a second attempt.

Limitation or tradeoff

The autonomy is bounded, and the bounds have gaps. The documentation states that checkpoints only cover file changes, so actions on remote systems such as databases, APIs and deployments cannot be rewound and have to be controlled through permissions. Long sessions fill the context window, and when the conversation is summarised to make room, detailed instructions from early in the session may be lost. The number of steps, and so the time and cost of a task, is not known when it starts.

What the sources document

  • The documentation says that when given a task Claude works through three phases (gather context, take action, verify results), that the phases blend together, and that Claude uses tools throughout. [11]
  • It states that Claude works out what each step needs from what the previous step taught it, stringing together dozens of actions and correcting course as it goes. [11]
  • It attributes the loop to two components, models for reasoning and tools for acting, notes that a model without tools can produce only text, and uses the term agentic harness for Claude Code as the layer that supplies the tools and manages the context the model sees. [11]
  • For the request to fix failing tests it lists a possible sequence: run the test suite, read the error output, search for the relevant source files, read those files, edit them, and run the tests again to verify. [11]
  • It states that Claude Code saves a snapshot of a file before editing it, that these checkpoints cover file changes only, and that actions on remote systems such as databases, APIs and deployments cannot be checkpointed. [11]

The facts above come from the cited sources. The steps and analysis in this example are our explanation of how they fit together.

Example 2 of 5

Airbnb's support platform: from static workflows to an LLM loop that uses those workflows as tools

AirbnbDocumented in an engineering article

Airbnb's engineering article Automation Platform v2 (October 2024) describes how the company's conversational AI platform for customer support moved from version 1, built on static workflows, to version 2, designed for LLM applications. [12]

The problem

Version 1 modelled its conversational AI products as predefined, step-by-step workflows that product engineering and business teams could design and manage. The article names two problems with this. The products were not flexible enough, because they followed a predefined and usually rigid process. They were also hard to scale, because someone had to create workflows and tasks by hand for every scenario and repeat the work for each new use case.

Where this topic fits

Version 2 adds what the article calls a Chain of Thought workflow, which in this lesson's terms is an agent loop: an LLM acts as the reasoning engine that decides which tools to use and in which order. The older workflows were not thrown away. They became the tools the LLM can call, and the article says some products should stay on a workflow instead of an LLM.

How it is applied, step by step

  1. In version 2, when an inquiry arrives the platform collects context such as chat history, user id and user role, and assembles a prompt for the LLM.
  2. The LLM replies with a request to run a tool. The platform executes it, for example a service call that fetches a reservation, and saves the result into the context.
  3. The platform sends the updated context back to the LLM. The reasoning loop continues until the LLM produces a result instead of another tool request.
  4. The tools on offer are the actions and workflows built for version 1, which the article says suit this role because they have a unified interface and a managed execution environment.
  5. A guardrails framework monitors communication with the LLM. Its guardrails can run in parallel, and they include rule-based tool guardrails that block bad executions such as a listing update with an invalid setup.
  6. The article says a claims product, which needs sensitive data and strict validation, is better suited to a traditional workflow than to an LLM.

Why this approach fits

Support conversations are open-ended. Customers describe problems in their own words and in any order, which is exactly where a predefined flow runs out of branches. Letting the model choose among existing, tested actions keeps the flexibility in the decision and the reliability in the execution. Each tool is an action or workflow whose steps were defined in advance.

Limitation or tradeoff

The article is open about the limits. It says LLM applications were still maturing on production requirements such as latency and hallucination, and that it was too early to rely on them fully for experiences that serve millions of customers. It gives claims as a case better handled by a workflow, because they involve sensitive data and many strict validations. The result is a mixed system, which is more work to operate than either style alone.

Example 3 of 5

Uber QueryGPT: a sequence of narrow LLM calls, called agents, that turns questions into SQL

UberDocumented in an engineering article

Uber's engineering article QueryGPT – Natural Language to SQL Using Generative AI (September 2024) describes an internal service that generates SQL queries from questions written in English, and how its design changed between the first hackathon version and the version running in production. [13]

The problem

Writing a query at Uber means finding the right tables among a very large catalogue and then writing the SQL. The first version of QueryGPT made one generation call with tables and sample queries found by similarity search. The article reports that accuracy declined as more tables were added, that going straight from a user's question to the relevant schemas was very hard, and that some table schemas were large enough to break the model's token limit.

Where this topic fits

The article calls its components agents, but it describes each one as a single LLM call with one narrow job, presented as successive stages, and it never describes a model choosing which component runs next. On that reading, which is ours, the system is a workflow in this lesson's vocabulary: a prompt chain with a human approval gate in the middle. It shows that a team can get the benefit of several model calls without giving a model control of the sequence.

How it is applied, step by step

  1. Every incoming question first goes to the intent agent, an LLM call that maps it to one or more business domains, called workspaces.
  2. The chosen workspace narrows the similarity search to the tables and sample queries curated for that domain.
  3. The table agent, a second LLM call, proposes the tables to use.
  4. The user sees the proposed tables and either accepts them or edits the list. This is a gate held by a person.
  5. The column prune agent, a third LLM call, removes irrelevant columns from the selected schemas so that the final prompt is smaller.
  6. A final LLM call generates the SQL query together with an explanation of how it was built.

Why this approach fits

As the article presents it, every question goes through the same stages: find the domain, find the tables, trim the schemas, write the SQL. When the steps are known, a workflow gives each call an easier job. The article draws this conclusion itself, saying the intermediate components worked well because each handled one small, specialised job. A fixed pipeline can also be evaluated stage by stage, and the team tracks separate signals such as intent accuracy and table overlap.

Limitation or tradeoff

A fixed path cannot repair its own output. The article reports that the system still sometimes generates queries with tables or columns that do not exist, and that the team was looking at adding a validation agent that recursively tries to fix such hallucinations, which would add a loop to the design. Quality also depends on the question: the article notes that short or vague prompts hurt accuracy and that users expect queries to simply work.

What the sources document

  • The article states that Uber's data platform handles approximately 1.2 million interactive queries each month, and estimates that a query takes around 10 minutes to author by hand against about 3 minutes with QueryGPT. [13]
  • It says every incoming prompt first runs through an intent agent, an LLM call that assigns the question to one or more business domains, which it calls workspaces, and that choosing a domain sharply reduced how much the retrieval step has to search. [13]
  • It describes a table agent that picks tables and sends them to the user to acknowledge or edit, and a column prune agent that uses an LLM call to remove irrelevant columns, which reduced token size, cost and latency. [13]
  • Under its learnings, the article says the intent, table and column prune agents each performed very well because each was given one narrow job instead of a broad, general one. [13]
  • It reports about 300 daily active users in a limited release, with about 78% saying the generated queries reduced the time they would have spent writing from scratch, and says hallucinated tables and columns remain an unsolved problem. [13]

Honeycomb Query Assistant: one well-supplied LLM call, chosen over chaining and agents

HoneycombDocumented in an engineering article

Honeycomb is an observability product. The article All the Hard Stuff Nobody Talks About when Building Products with LLMs, by Phillip Carter, describes how the team built Query Assistant, a feature that turns a natural-language request into a Honeycomb query, and which designs they rejected. [14]

The problem

A user types something like "which service has the highest latency?" and expects a runnable query a moment later. The article lists the constraints: a single model call took from two to more than fifteen seconds, some customers have schemas with over 5,000 fields that do not fit in a prompt, and anything connected to an LLM is exposed to prompt injection.

Where this topic fits

This is the first rung of the ladder: one LLM call given the right context, with ordinary code before and after it. The team considered chaining several calls and decided against it, and the article says they had no wish to run an LLM-powered agent inside their infrastructure. It is a documented case of a team choosing one call over a chain and declining to run an agent.

How it is applied, step by step

  1. The user types a request in natural language. The article says the feature is deliberately not plugged into a chat UI.
  2. Code assembles one prompt containing the request, a description of what makes a valid query, domain knowledge, the relevant schema, several examples, any existing query and instructions.
  3. To fit the context window, the schema is limited to fields that received data in the past seven days, and truncated further for some customers.
  4. A single LLM call returns a candidate query.
  5. Code parses the output, validates it and corrects it when it is correctable.
  6. The query runs in the regular query engine, and the user refines the result with the existing query builder.

Why this approach fits

The task is one transformation, from a sentence to a query, and the person who asked is looking at the result and can fix it immediately. There is no sequence of decisions for a model to make, so a loop would add waiting time and more places to fail without adding capability. Keeping the model away from databases and other services also means that a manipulated prompt can do very little.

Limitation or tradeoff

One call can only use what is already in its prompt. The article describes the result as hit or miss when the fields that mattered were truncated out of the schema, and says there is no complete solution to the context window problem. The speed measurements date from the models of the time (the article names gpt-3.5-turbo), so the latency argument is weaker with faster models. The compounding argument is not affected by model speed.

What the sources document

  • The article lists what is passed to the model: the user's input, information about what constitutes a Honeycomb query, domain information, the schema, several examples, the existing query and instructions. It says the output is parsed, corrected if correctable and then executed. [14]
  • It reports that producing a valid query takes from two to more than fifteen seconds depending on the model and inputs, and says chaining LLM calls makes the latency problem worse, which was a nonstarter for the team. [14]
  • It works through compound probabilities: five repetitions of a process that is right 90% of the time come out about 59% accurate. It adds that prompt tuning softens the drop in practice, and that the team saw no real gain in query generation from chaining LLM calls. [14]
  • Among its prompt injection measures, the article says the LLM is not connected to the company's databases or any other service and that its output is non-destructive and undoable. It adds that the team does not want an LLM-powered agent carrying out tasks inside its infrastructure. [14]

Example 5 of 5

Stripe Minions: blueprints that mix deterministic steps with agent loops

StripeDocumented in an engineering article

Stripe's two-part engineering article Minions: Stripe's one-shot, end-to-end coding agents (February 2026) describes an internal system of unattended coding agents. A run typically starts from a Slack message and ends in a pull request for human review. [15][16]

The problem

Minions run with no human supervising, in a codebase the first article describes as hundreds of millions of lines. Some parts of the job are unpredictable, such as how to implement a change. Other parts must happen the same way every time, such as running linters and pushing the branch. A pure agent might skip or mishandle the mandatory steps, and every decision left to the model costs tokens. A pure workflow cannot write the code.

Where this topic fits

Stripe's answer is a hybrid it calls a blueprint. The second article defines a workflow as a fixed graph of steps and an agent as a loop with tools, citing Anthropic's guide, and then describes blueprints as workflows defined in code in which any node can run deterministic code or an agent loop. The model decides inside agent nodes. Code decides everything between them.

How it is applied, step by step

  1. An engineer starts a run, most often by tagging the minion app in a Slack thread. The run gets an isolated developer machine with the code already loaded.
  2. Deterministic code gathers context before the agent starts, running relevant tools over links found in the request.
  3. An agent node implements the task. Inside this node the model chooses its own tool calls from a deliberately small set of tools.
  4. Deterministic nodes run the configured linters, looping on them locally before the push, and then push the branch. These nodes do not call a model.
  5. Continuous integration runs. Known autofixes are applied automatically, and failures without an autofix go back to an agent node for one more attempt.
  6. After the second push and CI run the branch returns to its human operator, and the resulting pull request is reviewed by a person.

Why this approach fits

The design applies this lesson's central question node by node. Where the next step is always the same (lint, push, run CI), code decides, which is cheaper and cannot be forgotten. Where the next step depends on what the code looks like, the model decides. Running the agent on an isolated machine also contains its mistakes, which is what makes it reasonable to let it work without approval prompts.

Limitation or tradeoff

The approach rests on infrastructure most teams do not have: prewarmed isolated machines, a test suite the articles put at over three million tests, and a central server of internal tools. The loop is cut off after two rounds of CI, so unfinished work returns to a person, and all minion code is still human-reviewed. A blueprint must be written and maintained like any workflow, so it only pays off for tasks that recur often.

What the sources document

  • The second article says over 1,300 Stripe pull requests merged each week are written entirely by minions, with human review but no human-written code, up from 1,000 at the time of the first article. [16]
  • It defines a workflow as an LLM system that runs through a fixed graph of steps and an agent as a simpler loop-with-tools pattern in which the LLM uses its own judgment to call tools repeatedly. It says a blueprint is a workflow written in code whose nodes can each run either deterministic code or an agent loop. [16]
  • It gives "Implement task" and "Fix CI failures" as agent-like nodes with wide latitude, and "Run configured linters" and "Push changes" as fully deterministic nodes that do not invoke an LLM. [16]
  • It says that handling small, predictable decisions in code cuts token and CI spending at scale and leaves the agent fewer chances to make a mistake. [16]
  • The articles state that minion runs have at most two rounds of CI, after which the branch goes back to its human operator. They also say the developer machines the runs use are isolated from production resources and the internet, which lets minions run unattended without human permission checks, and the second article adds that an internal security control framework stops their tools from performing destructive actions. [15][16]

4Common mistakes

  1. Building an agent for a task whose steps are the same every time.

    Why it causes problems
    The model has to rediscover a known sequence on every run. You pay for extra model calls, wait longer for each answer and accept run-to-run variation, and the best possible outcome is the result a few lines of ordinary code would have produced.
    How to recognise it
    Traces of successful runs all show the same tools in the same order. The system prompt reads like a numbered procedure the model is told to follow exactly.
    How to fix it
    Write the sequence as a workflow and call the model only at the steps that need language understanding. Keep an agent loop only for the part of the task where the traces really differ.

  2. Deciding how to test and control a system from its name instead of its control flow.

    Why it causes problems
    A fixed pipeline marketed as an agent gets step limits and autonomy reviews it does not need, while a real agent described as an assistant ships with no step cap, no sandbox and no whole-run evaluation.
    How to recognise it
    Nobody on the team can answer who decides the next step for each component, or design documents use agent, assistant and workflow as if they meant the same thing.
    How to fix it
    Mark each component as code-decided or model-decided. Give every model-decided loop a step limit, a spend limit, logging of each step and an evaluation that covers complete runs.

  3. Putting a hard business rule in the prompt and trusting the model to follow it.

    Why it causes problems
    Instructions are followed most of the time, not all of the time, and user text can argue the model out of them. A refund outside the policy window or a discount above the cap is then issued by a tool that did exactly what it was asked.
    How to recognise it
    The only place a rule appears is the system prompt, and the tool that performs the action accepts any arguments without checking them.
    How to fix it
    Enforce the rule in code, inside the tool or in a check before it, as the refund function in the worked example does. Keep the prompt for guidance on judgment calls, and require human approval for high-risk actions.

  4. Giving an agent actions whose results it cannot observe.

    Why it causes problems
    Without feedback the model cannot tell a successful step from a failed one, so it reports success on assumption and later steps build on an error. This is how small mistakes compound into a wrong final result.
    How to recognise it
    Tools return only OK or nothing at all, or the final answer claims something no tool result in the trace supports.
    How to fix it
    Make every tool return what changed or what was found, including clear error messages. Add a way to verify the outcome, such as tests for code or a read-back after a write.

  5. Adding agent steps without measuring whether they improve results.

    Why it causes problems
    Each added step raises cost and latency for certain and may lower reliability. Honeycomb's team saw no real gain from chaining calls for their feature, which they could only know because they checked.
    How to recognise it
    There is no fixed set of test inputs with expected outcomes, and design changes are justified by one or two impressive demonstrations.
    How to fix it
    Collect a small set of real tasks with known good outcomes. Measure the single-call version first, and keep a more complex design only if it beats that baseline by a margin that justifies its cost.

  6. Starting with a framework or several agents before one loop with a few tools works.

    Why it causes problems
    Layers of abstraction hide the prompts and tool results you need to see when something goes wrong, and more agents mean more tokens and more coordination to debug.
    How to recognise it
    You cannot print the exact text sent to the model at a given step, or the architecture diagram has more agents than the task has distinct jobs.
    How to fix it
    Build the first version directly on a model API with one loop and a small set of tools. Add a framework or split into several agents only when a measured problem calls for it, such as a single agent that keeps picking the wrong tool.

Classify six systems as a single step, a workflow or an agent

For each system below, answer three questions. Who decides the next step, the code or the model? Is it one augmented LLM step with no loop, a workflow or an agent? What is the largest number of model calls one request can cause? You need only pen and paper.

  1. Review labeller. A nightly job sends each new product review to a model with the instruction to label it positive, negative or neutral, and stores the label.

Exercise 2

Cost out a workflow, an agent and a hybrid for a support queue

CodingBeginnerAbout 35 min (estimate)Hypothetical scenario

A support team receives 1,000 tickets a day and is choosing between three designs. All figures below are invented for practice. Use Python, a spreadsheet or pen and paper.

QuantityValue
Average cost of one model call0.02 USD
Cost of a person handling one ticket3.00 USD
Design W (workflow)2 model calls per ticket, resolves 80% of tickets
Design A (agent)6 model calls per ticket on average, resolves 92% of tickets
Design H (hybrid)Every ticket goes through the workflow first. The 20% it cannot resolve go to the agent, which resolves 60% of those

A ticket that is not resolved automatically goes to a person. In every design a ticket still uses its model calls even when it ends up with a person.

  1. Compute the daily cost of design W and of design A (model calls plus people).
  2. Find the cost of a person per ticket at which W and A cost the same.
  3. Compute the daily cost and the overall resolution rate of design H.
  4. Suppose a typical agent run makes 6 model-decided steps and each is right with probability 0.97, independently. What is the chance that all six are right? What per-step probability would be needed for all six to be right 92% of the time?

Requirements

  • Show the model cost and the people cost separately for each design before adding them.
  • Give the break-even cost of a person per ticket to two decimal places.
  • State which design is cheapest at 3.00 USD per escalated ticket and why.
  • Give the per-step probability in part 4 to four decimal places.

Expected behaviour

Daily costs: W = 640.00 USD, A = 360.00 USD, H = 304.00 USD. W and A cost the same when a person costs about 0.67 USD per ticket. H resolves 92% of tickets, the same as A. Six steps at 0.97 all succeed with probability about 0.833, and 92% overall needs about 0.9862 per step.

Hint 1

Daily cost = model calls × cost per call + tickets sent to a person × cost of a person.

Hint 2

For the break-even, write both daily costs with the cost of a person as an unknown h and solve for h.

Hint 3

In design H, 1,000 tickets use the workflow's 2 calls each and 200 of them use 6 more calls each.

Hint 4

For the last part, take the sixth root of 0.92, which in Python is 0.92 ** (1 / 6).

Show solution
python
TICKETS_PER_DAY = 1000
MODEL_CALL_COST = 0.02   # USD, average per call
HUMAN_COST = 3.00        # USD per escalated ticket


def daily_cost(model_calls, escalated_tickets, human_cost=HUMAN_COST):
    return model_calls * MODEL_CALL_COST + escalated_tickets * human_cost


# Design W: fixed workflow, 2 calls per ticket, resolves 80%.
workflow_calls = TICKETS_PER_DAY * 2
workflow_escalated = TICKETS_PER_DAY * (1 - 0.80)

# Design A: agent, 6 calls per ticket on average, resolves 92%.
agent_calls = TICKETS_PER_DAY * 6
agent_escalated = TICKETS_PER_DAY * (1 - 0.92)

# Design H: workflow first; its 20% leftovers go to the agent, which resolves 60% of them.
leftovers = TICKETS_PER_DAY * 0.20
hybrid_calls = TICKETS_PER_DAY * 2 + leftovers * 6
hybrid_escalated = leftovers * (1 - 0.60)

for name, calls, escalated in [
    ("workflow", workflow_calls, workflow_escalated),
    ("agent", agent_calls, agent_escalated),
    ("hybrid", hybrid_calls, hybrid_escalated),
]:
    resolved = 1 - escalated / TICKETS_PER_DAY
    print(f"{name:8s} calls={calls:6.0f} escalated={escalated:4.0f} "
          f"resolved={resolved:.0%} cost={daily_cost(calls, escalated):7.2f}")

# Break-even human cost h between workflow and agent:
#   workflow_calls*c + workflow_escalated*h = agent_calls*c + agent_escalated*h
break_even = (agent_calls - workflow_calls) * MODEL_CALL_COST / (workflow_escalated - agent_escalated)
print(f"break-even human cost: {break_even:.2f}")

# Reliability of six model-decided steps in a row.
print(f"0.97 ** 6 = {0.97 ** 6:.3f}")
print(f"per-step reliability needed for 0.92 overall: {0.92 ** (1 / 6):.4f}")

text

Step by step:

  1. W: 2,000 calls × 0.02 = 40 USD for the model, and 200 tickets × 3.00 = 600 USD for people, 640 USD in total. A: 6,000 × 0.02 = 120 USD and 80 × 3.00 = 240 USD, 360 USD in total. The agent triples the model bill and still costs less overall, because people are the expensive part.
  2. Break-even: 40 + 200h = 120 + 80h gives 120h = 80, so h ≈ 0.67 USD. If handling a ticket by hand cost less than that, the workflow would be the cheaper design.
  3. H: 1,000 × 2 + 200 × 6 = 3,200 calls, which is 64 USD. The agent resolves 60% of the 200 leftovers, so 80 go to people, which is 240 USD. The total is 304 USD. The resolution rate is 80% + 20% × 60% = 92%. The hybrid is cheapest because it spends agent-level effort only on the tickets that need it. Airbnb and Stripe also mix fixed workflows with agent loops in the examples above, though they arrange them differently.
  4. Reliability: 0.97 to the power 6 is about 0.833, so roughly one run in six has at least one wrong step if nothing catches it. To reach 0.92 without any recovery, each step would need to be right 98.62% of the time. In practice an agent gets there by checking results and retrying, which is why feedback matters more than raw per-step accuracy.

    A six-course specialization from Vanderbilt University.
