Recommender Systems

A recommender system predicts which items a particular person is likely to want, using records of what people have viewed, bought or rated together with descriptions of the items, and returns a short ranked list from a catalogue that is too large to browse.

1Overview

Why it matters

Wherever a catalogue is larger than a screen (a shop, a video service, a job board, a news feed), something decides which handful of items each person sees. If that something is "most popular", everyone gets the same list, a new item never receives its first click and niche items stay invisible. A recommender makes the list depend on the person, and its design decides what gets discovered at all.

The failures are specific and repeatable. A model is accurate on logged ratings and still recommends badly, because the log only contains what the previous model chose to show. A product listed this morning has no interactions, so a model built on interactions cannot place it. A model that scores every item for every request is correct and far too slow. Machine learning engineers, data scientists and the product owners who answer for ranking metrics need to know the mechanisms behind these cases: collaborative filtering, matrix factorization, content-based filtering, two-tower retrieval followed by ranking, cold start and feedback loops.

Key terms

Interaction matrix
A table with one row per user and one column per item, whose cells hold what is known about each pair, such as a star rating or a count of views. Most cells are empty.
Explicit feedback
A preference the user states directly, such as a star rating or a thumbs-up.
Implicit feedback
Behaviour recorded as a side effect of using the product, such as clicks, purchases and watch time. It is plentiful but noisy, and it rarely says what a user dislikes.
Collaborative filtering
Recommending from patterns in many users' interactions, without looking at what the items are.
Content-based filtering
Recommending items whose attributes resemble the items a user already liked, without using other users' behaviour.
Matrix factorization
A collaborative filtering model that gives every user and every item a short vector and predicts a rating from the dot product of the two vectors.
Two-tower model
Two neural networks, one turning user features into a vector and one turning item features into a vector, trained so that the dot product is high for pairs that interacted.
Candidate generation (retrieval)
The first stage of a recommender, which cheaply narrows the whole catalogue to a few hundred plausible items for one request.
Cold start
The situation in which a new user or a new item has no interactions yet, so a model trained on interactions has nothing to go on.
Feedback loop
The cycle in which a recommender's output decides which interactions get logged, and those logs then train the next version of the recommender.

2Explanation

Introduction

You already use two recommendation strategies without any software. Ask a friend whose taste matches yours what to watch, and you are borrowing other people's experience: that is collaborative filtering. Pick another book by an author you enjoyed, and you are matching the properties of the item itself: that is content-based filtering. A recommender system automates both for millions of people and items.

The raw material is a log of interactions: who rated, bought, clicked or watched what. Arrange it as a table with a row per user and a column per item and you have the interaction matrix. Almost all of it is empty, because each person touches a tiny part of the catalogue. Recommending means estimating the empty cells and showing each user the items with the highest estimates. A rating someone typed is explicit feedback. A click or a purchase is implicit feedback, which is far more plentiful but is weaker evidence of liking.

Both prerequisites return here. Embeddings give each user and each item a vector, so that "this user would like this item" becomes "these two vectors point the same way". k-nearest neighbours is the search that finds the item vectors closest to a user vector.

A production system cannot score every item for every request, so the work is split into stages. Candidate generation narrows the catalogue to a few hundred items, a ranking model scores those carefully, and a re-ranking step applies filters and variety rules.

Follow the path out of the bottom of the diagram. What users do with the list is logged, the log trains the next models, and those models are deployed back into the pipeline (the dashed arrows). That feedback loop means the system partly creates its own training data.

This lesson covers neighbour-based collaborative filtering, matrix factorization, content-based filtering, two-tower retrieval followed by ranking, the cold start problem for users and items with no history, and how feedback loops arise and can be weakened.

Content-based filtering

A content-based recommender never looks at other users. Each item gets a feature vector built from what it is (genre flags, words in the description, an image or audio embedding), a user's profile vector is built from the items that user liked, and candidates are scored by the dot product of the two. Google's course lists the trade-offs (opens in a new tab): it needs no data from other users and can serve niche tastes, but the features must be engineered with domain knowledge and the model can only suggest more of what the user already likes. A common use today is covering items that have no interactions yet.

Two towers, then a ranker

A two-tower model merges the two ideas. One neural network maps user features (recently watched items, search terms, country) to a vector, a second maps item features (id, category, text) to a vector of the same size, and the score is their dot product (opens in a new tab). Matrix factorization is the special case in which each tower is a lookup table keyed by id. Training pairs come from the log: an interaction is a positive example, and other items, usually sampled, serve as negatives.

The design pays off at serving time. The towers never see each other's inputs, so every item vector can be computed in advance and stored in an approximate nearest-neighbour index. A request computes one user vector and asks the index for the closest few hundred items. The Instagram Explore team (opens in a new tab) names this cacheability as the main advantage, and names its price: the model cannot use features that describe one specific user-item pair.

Those pair features (how often has this user watched this channel?) are the strongest signals, so a second, heavier ranking model scores only the retrieved candidates. YouTube's two-stage design (opens in a new tab) cuts millions of videos to hundreds and then to the dozens shown. The ranker's target matters as much as its architecture: the same paper ranks by expected watch time because ranking by click-through rate promoted clickbait. A final re-ranking (opens in a new tab) pass removes items the user rejected and enforces freshness and variety.

Cold start

A model trained on interactions has no row for a new user and no column for a new item. Four fixes are common, and they are often combined:

  • Use features instead of ids. An item tower or a content-based model can embed an item from its description on the day it is listed.
  • Borrow a vector. Google's course suggests averaging the embeddings of items in the same category (opens in a new tab) and, once a few interactions arrive, solving for that one item's vector with all user vectors held fixed.
  • Explore. Reserve a share of impressions for new items so they can collect data. Amazon Personalize documents exploration (opens in a new tab) that adds items with few interactions to its recommendations. For the recipes and use cases that expose it, such as User-Personalization, an exploration weight between 0 and 1 sets how much to explore, with 0.3 as the default. The newer User-Personalization-v2 recipe configures exploration itself and uses a promotion filter on creation time to push new items.
  • Ask or fall back. For a new user, ask for a few preferences at sign-up, use context such as country and device, and otherwise show popular, varied items until behaviour accumulates.

Feedback loops

A recommender's log records reactions only to what the recommender chose to show. Items ranked first receive the impressions, therefore the clicks, therefore higher scores in the next model, while an item that is never shown can never prove itself. The authors of a Spotify bandit paper (opens in a new tab) describe the recommender as deciding its own training data, and connect the result to filter bubbles.

A small calculation shows the trap. Videos A and B have true click rates of 0.10 and 0.13. By bad luck B's first 7 impressions earned no clicks, so its estimated rate (clicks ÷ impressions) is 0, while A has 1 click from 10. Each round serves 100 impressions and adds the expected clicks, impressions × true rate, to each video's totals. A greedy policy gives every impression to the video with the higher estimate. An ε-greedy policy with ε = 0.1 gives 90 impressions to the leader and splits the other 10 evenly between the two videos, so the leader gets 95 and the other video 5.

Greedy never shows B again, so its estimate stays at zero for good. With 10 % exploration B's estimate passes A's after five rounds and the better video takes over. Across ten rounds the expected clicks are 115 against 100.

Practical defences follow the same logic. Explore a little, and record the probability with which each item was shown so that training can reweight the log. Train on interactions from every surface, not only on clicks the recommender caused. Model presentation effects such as screen position during training and neutralise them at serving. Settle decisions with A/B tests, because offline metrics computed on a biased log inherit the bias.

Step 3: matrix factorization with SGD

Now factorise the same table with two numbers per user and per film. The code uses only the Python standard library and leaves out the bias terms bub_ubu​ and bib_ibi​ to stay short.

import random

users = ["Ana", "Ben", "Chloe", "Dev", "Eli"]

]
mu = sum(stars for _, _, stars in ratings) / len(ratings)  # global mean, 3.0

def predict(p, q, u, i):
    return mu + sum(a * b for a, b in zip(p[u], q[i]))

def train(reg, k=2, lr=0.05, epochs=300):
    rng = random.Random(0)
    p = {u: [rng.uniform(-0.1, 0.1) for _ in range(k)] for u in users}  # user vectors
    q = {i: [rng.uniform(-0.1, 0.1) for _ in range(k)] for i in items}  # item vectors
    for _ in range(epochs):
        for u, i, stars in ratings:
            error = stars - predict(p, q, u, i)
            for f in range(k):
                pu, qi = p[u][f], q[i][f]
                p[u][f] += lr * (error * qi - reg * pu)
                q[i][f] += lr * (error * pu - reg * qi)
    return p, q

for reg in (0.2, 0.02):

Edge cases and limitations

A dot-product score quietly favours popular items
Google's candidate-generation page notes that the dot product rewards embeddings with a large norm, which makes popular items more likely to be recommended, while cosine similarity looks only at direction. The effect is that a factorization or two-tower model can return the same bestsellers for very different users. Measure what share of all recommendations goes to the 100 most popular items, and compare retrieval with dot product against cosine before blaming the model.
Missing ratings are not a random sample of opinions
People rate and click what they chose to consume, and they chose it partly because something recommended it. A model can therefore have a low error on the observed cells and still be wrong about the cells that matter, the items the user has never seen. Hu, Koren and Volinsky make the related point that with implicit data the unobserved pairs are where most negative feedback lies. Judge a recommender by how well it ranks held-out future interactions, not by error on ratings alone.
Random splits leak the future and create cold rows
The YouTube paper reports that holding out a random item from each history leaks future information and that predicting the next watch from earlier actions performed better in live tests. Spark's ALS documentation adds a mechanical problem: a random split often puts users or items in the evaluation set that are absent from training, the model returns NaN for them, and the metric becomes NaN unless coldStartStrategy is set to drop. Split by time, and count how many evaluation rows had no trained vector.
An implicit positive that is not a preference
A purchase may be a gift, and a channel may stay on while the viewer sleeps. These are the examples Hu, Koren and Volinsky give for why implicit feedback is noisy. A single event is weak evidence and a repeated one is stronger, which is why their model attaches a confidence to each observation instead of treating every click as a vote. When choosing what counts as a positive, prefer signals that cost the user something, such as finishing a video or buying again.
Embeddings from different training runs do not mix
The axes of a factor model have no fixed meaning. Retraining the worked example with a different random seed gives the same predictions from vectors that are rotated or mirrored. A user vector from this week's model scored against item vectors from last week's index therefore produces noise. Version the two sides together, rebuild the item index on every retrain and switch both at once.

When to use it, and when something simpler is enough

Use it when

  • The catalogue is far larger than a person can scan, and different people want different things from it.
  • You log interactions per user or per session (purchases, plays, clicks, ratings) in large enough numbers that items and users each appear many times.
  • Discovery matters, meaning that items a person never searched for could still be valuable to them.
  • You can compare against a popularity baseline on held-out future data and, ideally, run online experiments.

Think twice when

  • The catalogue is small enough to show in full or to sort by one obvious attribute such as price or date. Filters and a sort order serve better.
  • The user has said exactly what they want. That is a search problem, and relevance to the query should dominate.
  • There are too few interactions per user and per item to beat "most popular in this category". Collect data first.
  • The outcome is high-stakes for the person, as in lending or hiring, and you cannot yet explain or audit the ranking.

A simpler alternative. Show the most popular items of the last week, optionally within the category the user is browsing, plus "more from the same author or brand". That needs a grouped count and no model, it works for new users, and it is the baseline every recommender must beat. It stops being enough when people with clearly different histories are getting the same list and a personalised model ranks the items they later choose noticeably higher on held-out data.

Key takeaways

  • A recommender estimates the empty cells of a sparse user-by-item interaction matrix and shows each user the items with the highest estimates.
  • Collaborative filtering learns from who interacted with what, either by comparing item columns directly or by factorising the matrix into user and item vectors whose dot product predicts the interaction.
  • Content-based filtering scores items by their own attributes, which makes it the standard fallback for items and users that have no history.
  • Large systems retrieve a few hundred candidates with a cacheable factorization or two-tower model, then rank only those with a heavier model that can use features of the specific user-item pair.
  • Logged interactions reflect what the previous recommender chose to show, so a model trained on them reinforces its own choices unless you explore, correct for exposure and verify with online experiments.
  • Low training error is not evidence of good recommendations. Choose model size and regularisation on held-out interactions and compare against a popularity baseline.

Amazon.com: an offline similar-items table that turns recommending into a lookup

Amazon.comDocumented in a paper

In a 2003 industry report in IEEE Internet Computing, three Amazon.com engineers describe the algorithm the store used to personalise its pages, which they call item-to-item collaborative filtering. A 2019 Amazon Science article recounts how the method was later refined. [11][12]

The problem

The paper lists the conditions an e-commerce recommender works under: tens of millions of customers and millions of catalogue items, results needed in real time within about half a second, new customers with only a few purchases and long-standing customers with thousands. Traditional user-based collaborative filtering does its expensive work at request time, comparing the customer with other customers, and the authors report severe scaling problems for it at this size. The two alternatives they review, customer clusters and search-style content matching, move work offline but gave recommendations the authors judged to be relatively poor.

Where this topic fits

Neighbour-based collaborative filtering is the whole method here, split into two parts. An offline job turns purchase history into a table of similar items. The online part runs when a page is built: it looks up the items in the customer's history or shopping cart and merges their neighbours into one list. The paper shows the result on the home page's recommendations area and beside the shopping cart.

How it is applied, step by step

  1. Represent each item as a vector with one dimension per customer, marking who bought it. This flips the usual view, in which each customer is a vector over items.
  2. Offline, for each item, walk through the customers who bought it and the other items those customers bought, counting how often each pair of items shares a customer.
  3. Turn the counts into a similarity score for every pair that shares at least one customer, for example the cosine between the two item vectors, and store each item's most similar items.
  4. Online, take the items the customer has bought, rated or placed in the cart and fetch each one's similar items from the table.
  5. Combine the fetched lists, drop what the customer already owns and show the strongest items.
  6. Rebuild the table as new purchases arrive. The paper does not give a schedule, and a typical implementation runs the offline job in batch.

Why this approach fits

The costly part of collaborative filtering is comparing vectors across the whole data set. This design moves that cost into a batch job and leaves a request with a handful of table lookups, so latency depends on how much one customer has bought and not on how large the business has grown.

It also behaves well at both ends of the customer range. A new customer with two or three purchases already has neighbours to draw on, and a customer's latest purchase changes the result at once because it simply adds more lookups. Each suggestion can be explained by the purchase that triggered it.

Limitation or tradeoff

An item nobody has bought has no row in the table, so new products are invisible until they collect purchases some other way. The table is the same for every customer: personalisation comes only from which rows are looked up. A purchase is also treated as a liking, although it may have been a gift.

Raw co-purchase counts favour bestsellers, which share customers with almost everything. The Amazon Science article says the team therefore measured relatedness against the average customer's chance of buying B, and reports a correction several years later: heavy buyers are unusually likely to buy B whatever they bought before, so the team discounted their extra likelihood according to how much they buy.

Netflix Prize: matrix factorization with bias terms for predicting star ratings

Netflix Prize competition (BellKor team)Documented in a paper

In IEEE Computer (August 2009), Yehuda Koren, Robert Bell and Chris Volinsky describe the matrix factorization models behind their team's leading entries in the Netflix Prize, a public contest run on Netflix's movie-rating data. The Apache Spark documentation shows the same family of models as a library feature and cites Netflix Prize work for part of its implementation. [7][13]

The problem

Netflix released a large set of star ratings and asked teams to predict held-out ratings more accurately than its own system, measured by root-mean-square error (RMSE). The matrix is extremely sparse, because each customer rated a small share of the films. Much of the variation in ratings also has nothing to do with matching tastes: some customers rate everything high, and some films are rated high by nearly everyone.

Where this topic fits

Matrix factorization is the predictor itself. Each customer and each film gets a vector learned from the known ratings, and a missing rating is predicted from their dot product plus bias terms. The authors then extend the same model with implicit feedback, with parameters that drift over time and with per-observation confidence weights.

How it is applied, step by step

  1. Give each film a vector q and each customer a vector p with the same number of factors, starting from small random values.
  2. Predict a rating as the global average, plus a film bias, plus a customer bias, plus the dot product of q and p.
  3. Minimise the squared error over the known ratings only, with a penalty on the size of the vectors and biases so that the model does not memorise the few ratings each customer gave.
  4. Fit by stochastic gradient descent, looping over the ratings and nudging both vectors after each one, or by alternating least squares when the work must be spread across machines.
  5. Set the penalty strength by cross-validation and compare model variants by RMSE on held-out ratings.
  6. Add refinements inside the same framework, such as which films a customer rated at all (an implicit signal) and biases that change with time.

Why this approach fits

The contest supplied explicit ratings and scored entries by squared error, so a model trained to minimise squared error on ratings is aimed directly at the target. Factorization suits the sparsity: a customer who rated twenty films still gets a full vector, because every rating of every film helps to position the film vectors that the customer's vector is fitted against.

The bias terms matter because they remove variation that is not about taste before the factors are asked to explain anything. The model is also easy to extend, which is how the authors added implicit signals and time effects without changing the training procedure.

Limitation or tradeoff

Rating error is a stand-in for the real goal. A model can shave RMSE by predicting 3.4 instead of 3.6 for films nobody would be shown anyway, while the order of the top ten, which is what a user sees, barely changes. The ratings are also not a random sample, since people rate what they chose to watch.

The paper itself notes that collaborative filtering cannot handle products and users that are new to the system, and that the leading entries blended more than 100 predictor sets, which is far from a single model one would train and serve.

What the sources document

  • Netflix released a training set of more than 100 million ratings from about 500,000 anonymous customers on more than 17,000 movies, each on a scale of 1 to 5 stars. Teams submitted predictions for a test set of about 3 million ratings, scored by RMSE, and the first team to improve on Netflix's algorithm by 10 percent or more would win 1 million US dollars. [7]
  • The basic model maps users and items into a joint latent factor space and estimates a rating as the inner product of the item and user vectors. It is learned by minimising a regularised squared error over the known ratings, with a regularisation constant that is usually determined by cross-validation. [7]
  • With bias terms a rating is modelled as the global average plus an item bias, a user bias and the user-item interaction. The paper illustrates the baseline with an average of 3.7 stars, a film rated 0.5 above average and a critical user who rates 0.3 below average, giving 3.9 stars. [7]
  • The authors' team won the 2007 Progress Prize with a score 8.43 percent better than Netflix's system and, together with another team, the 2008 Progress Prize with 9.46 percent. Their winning entries consisted of more than 100 predictor sets, most of them factorization models. The paper's accuracy chart gives 0.9514 as the RMSE of Netflix's system and 0.8563 as the accuracy required for the grand prize. [7]
  • Spark's ALS documentation says it scales the regularisation parameter by the number of ratings a user generated or a product received, names the approach ALS-WR and attributes it to a paper on large-scale parallel collaborative filtering for the Netflix Prize. [13]

Instagram Explore: two-tower retrieval feeding a multi-stage ranking funnel

Instagram (Meta)Documented in an engineering article

Explore is one of the largest recommendation surfaces on Instagram, where people go to discover new content. A 2023 article on Meta's engineering blog, written by two Meta engineers, describes how its pipeline is organised and how each stage is kept cheap enough to run. [14]

The problem

The system must pick the most relevant content for each person in real time out of billions of options. The article is direct about the constraint: with unlimited compute and no latency limit one could rank everything, but a real system cannot. The most powerful features describe a specific user-item pair, and a model that uses them cannot precompute anything per item.

Where this topic fits

The two-tower model appears twice in the funnel. It is one of the retrieval sources that cut billions of items to a manageable pool, and a second two-tower model serves as the lightweight first-stage ranker. A heavier multi-task model ranks what survives, and a rule-based reranking step comes last.

How it is applied, step by step

  1. Train a two-tower network in which the user tower sees only user-side features and the item tower only item-side features, with the objective of predicting engagement events such as a like from the similarity of the two embeddings.
  2. Run the item tower offline over candidate items and load the resulting embeddings into an approximate nearest-neighbour search service.
  3. At request time, compute the user embedding from the freshest user features and fetch the nearest item embeddings.
  4. Add candidates from other sources, such as items similar to those the person recently liked or saved and heuristic sources like trending posts, and mix the sources with tunable weights.
  5. Trim the pool with a first-stage ranker, another two-tower model that is trained to reproduce the ordering of the heavier model after it.
  6. Score about 100 remaining candidates with a multi-task network that predicts the probability of several actions, including negative ones such as "see less", using user-item interaction features.
  7. Combine the probabilities into one value with weights, then apply integrity filtering and diversity rules before the list is shown.

Why this approach fits

Each stage spends more computation per item on fewer items. The two-tower model is what makes the first cut affordable: item embeddings are computed once and reused for every request, and one user embedding is enough to search the whole index. Using the same architecture for the first-stage ranker keeps that property, and training it to imitate the second stage reduces the risk that the cheap model throws away items the expensive model would have ranked highly.

The weighted combination at the end lets the team trade one outcome against another, for example fewer "see less" taps against more likes, without retraining a model.

Limitation or tradeoff

The article states the price of cacheability plainly: the two-tower model cannot use user-item interaction features, usually the most powerful ones, so retrieval is blind to anything that depends on the specific pair. An item that retrieval misses cannot be rescued by a better ranker.

Where item embeddings are regenerated daily by an offline pipeline, a post created after the last run has no embedding until the next one (our inference), and the article lists real-time retrieval sources alongside pre-generated ones. The authors also note that the system has hundreds of tunable parameters, so the weights that combine sources and predictions need their own tuning process.

What the sources document

  • The article describes a multi-stage funnel made of retrieval, first-stage ranking, second-stage ranking and final reranking, in which the purpose of a retrieval source is to select hundreds of relevant items from a media pool of billions, and the second-stage ranker operates on the 100 best candidates from the first stage. [14]
  • In the Two Tower model each network consumes only features related to its own entity and outputs an embedding, and the learning objective is to predict engagement events, such as someone liking a post, as a similarity measure between user and item embeddings. [14]
  • The article gives cacheable user and item embeddings as the main advantage of the approach: item embeddings are generated daily by an offline pipeline and can be placed in an approximate nearest-neighbour service (FAISS and HNSW are named), the user embedding is generated on the fly during online retrieval, and the model cannot consume user-item interaction features without losing this cacheability. [14]
  • The first-stage ranker is a Two Tower model trained to predict the output of the second stage, which the authors present as distilling knowledge from the heavier model. The second stage is a multi-task multi-label network that predicts the probability of engagement events and can consume user-item interaction features. [14]
  • Predictions are combined into an expected value, a weighted sum in which the probability of "see less" is subtracted, and final reranking can filter or downrank items on integrity-related scores and apply rules such as not showing items from the same author in a sequence. [14]

Spotify research internship: predicting collaborative-filtering vectors from audio for unheard songs

Spotify (research internship project)Documented in an engineering article

Sander Dieleman's August 2014 post describes work he did as an intern at Spotify in New York: a convolutional network that predicts, from a song's audio alone, the latent factors that one of Spotify's collaborative filtering models would assign to it. It is a first-person account of an experiment on Spotify's catalogue, written before any A/B test. [15]

The problem

Collaborative filtering depends on listening data. The post explains the consequence: popular songs are easy to recommend because they have plenty of data, while new and unpopular songs cannot be recommended at all. For a music service that is the cold-start problem in its sharpest form, since newly released tracks have no plays on the day they matter most.

Where this topic fits

This is content-based filtering used as a bridge into a collaborative filtering model. The item's content (audio) is the input, and the target is the vector that collaborative filtering learned for the same track. A new track then gets a vector in the same space as every other track without a single play.

How it is applied, step by step

  1. Take the latent factor vectors that an existing collaborative filtering model has learned for tracks with plenty of listening data.
  2. Turn a 30-second excerpt of each of those tracks into a mel-spectrogram, a time-by-frequency picture of the sound.
  3. Train a convolutional network to map the spectrogram to the track's latent vector, minimising the mean squared error between predicted and actual vectors.
  4. For a track with no listening data, run the network on its audio to obtain a predicted vector.
  5. Use the predicted vector wherever a learned one would be used, for example to find the tracks nearest to it. The author checked quality this way, by building playlists of nearest neighbours in the predicted space.
  6. Once a track has accumulated plays, a typical system would switch to, or blend in, the vector learned from behaviour. The post does not describe that step.

Why this approach fits

Predicting the collaborative filtering vector, instead of building a separate content-based recommender, means everything downstream keeps working unchanged: nearest-neighbour search, playlist generation and ranking features all consume the same kind of vector. Audio exists for every track from the moment it is delivered, so the model's input is never missing.

Learning the features from spectrograms also avoids the usual cost of content-based filtering, which is hand-built attributes that need domain experts to define and maintain.

Limitation or tradeoff

The post reports an experiment, not a launch. The author says he hopes parts of the work will be ready for A/B testing, so it gives no evidence of effect on listeners. A predicted vector is also an estimate of an estimate, and the post itself stresses the large gap between an audio signal and the many things that shape what people want to hear.

The network was trained on the most popular tracks, so its predictions for styles that are rare in that set deserve less trust. Audio also carries nothing about an artist's following or the moment a track is released into.

  • Dieleman writes that he was interning at Spotify in New York in the summer of 2014, working on content-based music recommendation using convolutional neural networks. [15]
  • The post explains that because collaborative filtering relies on usage data, popular items are much easier to recommend than unpopular ones, and that new and unpopular songs cannot be recommended when there is no usage data, which it calls the cold-start problem. [15]
  • The approach is a regression model trained to predict the latent representations of songs that were obtained from a collaborative filtering model. The network's output layer predicts 40 latent factors from vector_exp, described as one of the collaborative filtering algorithms used at Spotify. It is trained to minimise mean squared error between vectors that are first normalised to unit length, which reduces the influence of song popularity. [15]
  • The network's input is mel-spectrograms with 599 frames and 128 frequency bins, taken from 30-second excerpts from the middle of the 1 million most popular tracks on Spotify, of which about half were used for training. [15]
  • The author lists the intended uses as an extra signal in Spotify's recommendation pipeline, filtering outliers from other algorithms' output and recommending new and unpopular music, and says he hopes some of it will be ready for A/B testing soon. [15]

YouTube: training-data rules and a position-bias tower against the feedback loop

YouTube (Google)Documented in a paper

Two papers by Google engineers describe YouTube's recommender: the 2016 RecSys paper on its candidate-generation and ranking networks, and the 2019 RecSys paper on the multitask ranking model behind the "watch next" list. Both discuss how the system's own behaviour distorts the implicit feedback it is trained on. [16][17][18]

The problem

YouTube trains on implicit feedback, mainly watches and clicks. Those logs are shaped by the recommender that produced the page. The 2019 paper gives the core case: a person may click a video because it was ranked high, not because it was the best choice, so a model trained on that data inherits the bias and feeds it forward. The 2016 paper adds related distortions: a model trained on weeks of history favours older videos, and a small group of very active users can dominate the loss.

Where this topic fits

The corrections sit at three points of the pipeline: which examples are allowed into the training set, which input features are added during training and neutralised at serving, and which outcome the ranking model is asked to predict. None of them changes the two-stage architecture.

How it is applied, step by step

  1. Build training examples from every watch on the platform, including videos embedded on other sites, so that discoveries made outside the recommender still reach the model.
  2. Generate the same number of training examples for each user, so that the heaviest users do not define what the model learns.
  3. Feed the age of each training example as an input feature and set it to zero at serving time, so that predictions reflect the end of the training window instead of its average.
  4. Train the ranker to predict expected watch time instead of click probability.
  5. In the 2019 ranker, give the on-screen position, crossed with device type, to a small side network whose output is added to the main model's logit during training.
  6. Drop the position feature for a random 10 percent of training examples so that the main model cannot lean on it, and treat position as missing at serving time.
  7. Confirm each change with live A/B experiments, which both papers treat as the final test.

Why this approach fits

All of these corrections work on data the system already has. The alternative for measuring position effects is to randomise what users see, which costs user experience, and the 2019 paper presents the side tower as a way to learn the bias without such random experiments. Watches that happen outside the recommender play a similar role for the 2016 model: they are a supply of interactions that the recommender did not choose.

The corrections are also cheap to keep. An extra input feature or a sampling rule survives a change of model architecture, which matters in a system that is retrained continuously.

Limitation or tradeoff

Position is only one kind of selection bias, and the 2019 paper itself calls reducing such biases an open question. None of these measures tells the model anything about a video that was never shown to anyone, which only exploration can do. The reported gain from the side tower is small in relative terms, and it is measured on an engagement metric, not on a direct measure of satisfaction.

Watches from outside the recommender are not unbiased either. They reflect search results, social sharing and the rest of the web, each with its own skew.

What the sources document

  • The 2016 paper states that training examples are generated from all YouTube watches, including those embedded on other sites, and not only from watches of recommended videos, because otherwise it would be very difficult for new content to surface and the recommender would be overly biased towards exploitation. [16]
  • It reports that generating a fixed number of training examples per user improved live metrics by preventing a small cohort of highly active users from dominating the loss, and that feeding the age of the training example as a feature, set to zero at serving time, corrects the model's bias towards the past. [16]
  • The ranking objective is described as generally a simple function of expected watch time per impression, because ranking by click-through rate often promotes deceptive videos that the user does not complete. [16]
  • The 2019 paper names implicit selection biases in user feedback as a main challenge: a user might click and watch a video simply because it was ranked high, so models trained on data generated by the current system will be biased, which the paper calls a feedback loop effect. [17][18]
  • Its shallow tower takes features that contribute to selection bias, such as position, and its output is added to the final logit of the main model. Position is used in training with a 10 percent feature drop-out rate and treated as missing at serving. In live experiments the shallow tower changed the engagement metric by +0.24 percent, against -0.07 percent for position as a plain input feature and +0.01 percent for an adversarial loss. [17]

4Common mistakes

  1. Evaluating on a random split of interactions and judging the model by rating error alone.

    Why it causes problems
    A random split lets the model train on a user's later behaviour and be tested on earlier behaviour, which flatters it. It also leaves users and items in the test set that the model never saw. And a low error on ratings says little about the order of the first ten items, which is all a user sees.
    How to recognise it
    Offline numbers improve from one version to the next while online results do not move. Evaluation rows are silently dropped or come back as NaN, as Spark's ALS does by default for unseen users and items.
    How to fix it
    Split by time, train on the past and test on the future. Report a ranking measure such as recall at 10 next to any error measure, compare against a most-popular baseline, and confirm with an A/B test.

  2. Treating unobserved implicit interactions as either ignorable or as certain dislikes.

    Why it causes problems
    If only the observed pairs are used and all of them are positives, predicting 1 for everything minimises the loss. If every unobserved pair is a firm zero, the zeros outnumber the positives by orders of magnitude and drag all predictions towards zero. Google's matrix factorization page describes both outcomes.
    How to recognise it
    Scores are nearly identical for all items, or every user receives the same few popular items. The training loss is close to zero after very few steps.
    How to fix it
    Give unobserved pairs a small weight instead of none or full weight, as weighted matrix factorization and the confidence scheme of Hu, Koren and Volinsky do, or train with sampled negatives.

  3. Serving an id-only model with no path to exposure for new items and no answer for new users.

    Why it causes problems
    A new item has no vector, so it is never retrieved, never clicked and never earns a vector. New users get an error, an empty list or an arbitrary one. The catalogue the recommender shows grows stale while the real catalogue moves on.
    How to recognise it
    Measure the share of impressions that go to items listed in the last seven days, and the share of requests whose user id is unknown to the model. If the first is near zero, new items are locked out.
    How to fix it
    Define the fallback chain explicitly: a vector from content features or the category average for new items, a reserved share of impressions for exploration, and popular or onboarding-based lists for new users.

  4. Optimising the ranker for clicks because clicks are the easiest outcome to log.

    Why it causes problems
    A click measures how attractive the title and thumbnail are, not whether the item was worth the time. YouTube's team reports that ranking by click-through rate promoted deceptive videos that users did not finish.
    How to recognise it
    Click-through rate rises while completion rate, repeat visits or purchases stay flat or fall, and negative actions such as hides and "see less" taps increase.
    How to fix it
    Predict an outcome closer to satisfaction, such as watch time, completion or a purchase that is not returned. Where several outcomes matter, predict each and combine them with weights, giving negative weight to negative actions.

  5. Retraining on the recommender's own logs without recording or correcting for exposure.

    Why it causes problems
    The model learns "was shown in the first slot" as if it were "is preferred". Each retrain concentrates impressions on fewer items, and items that were never shown can never recover.
    How to recognise it
    The share of impressions taken by the top 1 % of items grows release after release, and a large part of the catalogue has zero impressions. Predicted scores correlate strongly with the position items held in the previous version.
    How to fix it
    Log every impression with its position and, if you randomise, the probability of showing it. Reserve a small share of traffic for exploration, use position as a training-only feature, and include interactions that did not come from recommendations.

from collections import defaultdict
from math import sqrt

purchases = {
    "c1": {"tent", "sleeping bag", "stove"},
    "c2": {"tent", "sleeping bag", "headlamp"},
    "c3": {"tent", "stove", "headlamp", "water bottle"},
    "c4": {"yoga mat", "water bottle"},
    "c5": {"yoga mat", "water bottle", "resistance bands"},
    "c6": {"sleeping bag", "water bottle"},
    "c7": {"yoga mat", "resistance bands"},
}
category = {
    "tent": "camping", "sleeping bag": "camping", "stove": "camping", "headlamp": "camping",
    "camp chair": "camping", "yoga mat": "fitness", "resistance bands": "fitness", "water bottle": "fitness",
}

# Offline: count buyers per item and shared buyers per pair, then convert the counts to cosine similarity.
buyers = defaultdict(int)
together = defaultdict(int)
for basket in purchases.values():
    for a in basket:
        buyers[a] += 1
        for b in basket:
            if a != b:
                together[a, b] += 1

similar = defaultdict(dict)  # similar[a][b] = cosine between the 0/1 purchase columns of a and b
for (a, b), count in together.items():
    similar[a][b] = count / sqrt(buyers[a] * buyers[b])

def ranked(scores):
    return sorted(scores.items(), key=lambda pair: (-pair[1], pair[0]))

def recommend(owned, table, top_n=3):
    scores = defaultdict(float)
    for item in owned:
        for other, s in table.get(item, {}).items():
            if other not in owned:
                scores[other] += s
    return ranked(scores)[:top_n]

def show(label, pairs):
    print(label, [(name, round(score, 2)) for name, score in pairs])

show("similar to tent:", ranked(similar["tent"]))
show("cart {tent, stove}:", recommend({"tent", "stove"}, similar))
show("cart {water bottle}:", recommend({"water bottle"}, similar))
print("camp chair has a row:", "camp chair" in similar)

# Cold start: give the new item the average similarity row of the items in its category.
def borrowed_row(new_item):
    peers = sorted(i for i in similar if category[i] == category[new_item])
    row = defaultdict(float)
    for peer in peers:
        for other, s in similar[peer].items():
            row[other] += s / len(peers)
    return dict(row)

table = {item: dict(row) for item, row in similar.items()}
table["camp chair"] = borrowed_row("camp chair")
for other, s in table["camp chair"].items():  # keep the table symmetric
    table[other]["camp chair"] = s

show("camp chair row:", ranked(table["camp chair"]))
show("cart {tent, stove} again:", recommend({"tent", "stove"}, table, top_n=4))
show("cart {yoga mat} again:", recommend({"yoga mat"}, table, top_n=4))

Exercise 2

Design a two-stage recommender, its cold-start plan and its feedback-loop safeguards for a recipe app

DesignIntermediateAbout 1 h (estimate)Hypothetical scenario

You are asked to design the home feed of a recipe app. The scenario is invented.

  • 200,000 recipes, and about 500 new ones are published every day.
  • 3 million monthly users. About 40 % of sessions come from users with fewer than five logged actions.
  • The feed shows 20 recipes, and the service has 150 ms to return them.
  • Logged actions: recipe opened, recipe saved, "cook mode" started, and a "not for me" button.
  • Recipe metadata: title, ingredient list, cuisine, diet tags, preparation time and one photo.
  • Today the feed is "most saved this week", identical for everyone.

Write a one-page design that answers:

  1. Which candidate sources will you use (at least three), and what does each contribute?
  2. For a two-tower retrieval model, what goes into each tower, and what are the positive and negative training examples?
  3. What does the ranking model predict, which features can it use that retrieval cannot, and how are its predictions combined into one score?
  4. How does a recipe published one hour ago reach the feed? How is a first-time user served?
  5. What will you log and do so that the system does not simply reinforce its own choices?
  6. How will you decide whether the new feed is better than "most saved this week"?

Requirements

  • Name at least three candidate sources, including one that works for a recipe with no interactions.
  • Keep user-item pair features out of the retrieval towers and explain where they are used instead.
  • Define the ranking score with at least one negative signal and justify the choice of positive signal.
  • Give an explicit fallback for new recipes and one for new users, each usable on day one.
  • Include impression logging and a bounded amount of exploration, with a number for the bound.
  • State an offline evaluation with a time-based split and an online test with a guardrail metric.

Expected behaviour

A good answer reads as a pipeline with numbers at each stage: several sources returning a few hundred recipes in total, one ranking model scoring them, and a short rule-based pass producing 20. Every cold-start case has a named mechanism that needs no interaction data. The logging section records what was shown and where, not only what was clicked. The evaluation compares against the current popularity feed on future data and then in an A/B test, and names what would count as harm.

Hint 1

Start from the latency budget. Anything that must look at all 200,000 recipes per request has to be a precomputed lookup or a nearest-neighbour search.

Hint 2

Opening a recipe is cheap for the user. Saving it or starting cook mode costs more, so it is stronger evidence. Decide which one is your positive label before choosing a model.

Hint 3

A recipe's ingredients, cuisine and photo exist before anyone has opened it. Ask which parts of your design can use them.

Hint 4

For the feedback loop, ask what the training data would look like after six months if the model only ever saw reactions to its own top 20.

Show solution

1. Candidate sources (about 400 recipes in total)

  • Two-tower retrieval, 200 recipes: the personalised source, served from a nearest-neighbour index.
  • Item-to-item neighbours of the user's last five saved or cooked recipes, 100 recipes: reacts within a session, and each result can be explained ("because you cooked X").
  • Fresh recipes by content, 50 recipes published in the last 7 days whose content embedding is closest to the user's profile: the path for items with no interactions.
  • Popular this week, by cuisine, 50 recipes: the safety net, and the main source for new users.

2. Two-tower model

  • User tower: embeddings of the last 50 recipes opened, saved or cooked (averaged), diet tags inferred from history, country, device and hour of day. No recipe-specific features.
  • Item tower: recipe id embedding plus content features (text embedding of title and ingredients, cuisine, diet tags, preparation-time bucket, photo embedding). Because the tower reads content, a new recipe gets a usable vector before anyone has opened it.
  • Positives: (user, recipe) pairs with a save or a cook-mode start. Opens alone are too cheap.
  • Negatives: other recipes sampled from the catalogue, plus a share of recipes that were shown and marked "not for me".
  • Item vectors are recomputed for the whole catalogue on each retrain and hourly for new recipes, and loaded into the index together with the matching user tower version.

3. Ranking model

Scores the 400 candidates with one multi-task model that predicts P(open), P(save), P(cook) and P(not for me). It can use pair features that retrieval cannot: how many recipes of this cuisine the user cooked, overlap between the recipe's ingredients and those of the user's saved recipes, whether the user has already seen this recipe and how often, and which source nominated it.

score=1.0⋅P(cook)+0.5⋅P(save)+0.1⋅P(open)−2.0⋅P(not for me)\text{score} = 1.0 \cdot P(\text{cook}) + 0.5 \cdot P(\text{save}) + 0.1 \cdot P(\text{open}) - 2.0 \cdot P(\text{not for me})score=1.0⋅P(cook)+0.5⋅P(save)+0.1⋅P(open)−2.0⋅P(not for me)

The weights are starting values to be tuned in experiments. Cooking is the outcome closest to the product's purpose, and opens are weighted low so that an attractive photo alone cannot win. A re-ranking pass then removes recipes that conflict with stated diet tags, limits each cuisine to four of the 20 slots and drops recipes shown three times without an open.

4. Cold start

  • New recipe: the item tower embeds it from content within the hour, and the fresh-recipes source guarantees it can be nominated. Two of the 20 slots are reserved for recipes with fewer than 100 impressions. After a few dozen interactions the id embedding starts to carry weight.
  • New user: an optional first screen asks for diet and three favourite cuisines, which fill the user tower's profile features. Without answers the feed is popular-by-cuisine for the user's country, mixed across cuisines. The item-to-item source takes over after the first save.

5. Feedback-loop safeguards

  • Log every impression: user, recipe, slot, source, model version and, for the exploration slots, the probability with which the recipe was chosen.
  • Explore with a hard bound: 2 of 20 slots (10 %) are filled by sampling from candidates outside the ranker's top 20.
  • Give the ranker the slot index as a training-only feature and set it to a fixed value at serving.
  • Train on saves and cooks from every entry point (search, shared links, collections), not only the feed.
  • Monitor weekly: share of impressions going to the top 1 % of recipes, share going to recipes younger than 7 days, and the number of recipes with zero impressions.

6. Evaluation

  • Offline: train on weeks 1 to 8, test on week 9. Report recall at 20 for saves and cooks, separately for users with fewer than five actions, against the popularity feed.
  • Online: A/B test against the current feed for at least two weeks. Primary metric: cook-mode starts per user per week. Guardrails: "not for me" rate, and 7-day return rate must not fall.
  • Keep a small holdout on the popularity feed after launch to measure long-term drift.

Check your answer

  • Can a recipe published an hour ago, with zero opens, reach a user's feed through at least one named source?
  • Do your retrieval towers contain only user-side or only item-side features, with pair features reserved for the ranker?
  • Does your ranking score subtract something, and can you say why your main positive signal is harder to game than a click?
  • Do your logs record what was shown and in which slot, so that a later model can tell "not clicked" from "never shown"?
  • Is your offline split by time, and does your online test name a guardrail metric and the baseline it is compared with?
