Front Ends for AI Prototypes (Streamlit, Gradio, React)

A front end for an AI prototype is the thin interface, such as a chat box, a form or a results page, that lets people other than the developer try the system. Streamlit and Gradio generate that interface from Python code, while a React app is a JavaScript interface that you build yourself and connect to your own API.

1Overview

Why it matters

A prototype that only runs in a terminal cannot be judged by the people it is meant for. A working interface turns a demo into feedback from a customer or a colleague, and that feedback is the reason to build a prototype at all. The common ways to build the interface behave very differently under load and under attack, and the differences are documented but easy to miss.

Streamlit runs your whole script again on every interaction and keeps conversation state in memory for each browser tab. Gradio queues requests and, by default, runs one call at a time per function. A React app cannot keep an API key secret, because everything delivered to a browser can be read by its user, so it always needs a server of its own. Prototypes that ignore these facts fail in familiar ways: a public share link that anyone can use to spend your API budget, a conversation that vanishes when the tab closes, model output rendered as HTML, or a demo that stalls when six people click at once.

Forward deployed engineers and AI engineers build these interfaces constantly and quickly. Knowing which tool fits, how to show sources and intermediate steps so users can judge an answer, and which shortcuts to remove before real users arrive is what separates a demo that earns trust from one that has to be pulled down.

  • Review a prototype against a hardening checklist covering secrets, authentication, spend limits, output rendering and file exposure.

Key terms

Rerun
Streamlit's execution model. The whole Python script runs again from top to bottom whenever the user interacts with a widget or the source file changes.
Session state
A dictionary in Streamlit (st.session_state) that survives reruns for one browser tab. It is lost when the tab closes or the server crashes.
ChatInterface
Gradio's high-level class that turns one Python function, taking the new message and the history, into a complete chatbot interface.
Queue and concurrency limit
Gradio places requests in a queue and runs at most a set number of calls of one function at a time. The documented default for that number is 1.
Message part
One typed piece of a chat message, such as text, reasoning, a source link or a tool call. A message made of parts lets the interface draw each piece in its own way.
Server-sent events (SSE)
A text format for a one-way stream from server to browser, in which each message is a block of lines such as data: followed by a blank line.
JSON lines (NDJSON)
A streaming format with one complete JSON object per line. The Azure sample in this lesson streams answers this way.
Proxy route
A route on your own server that sits between the browser and a paid or private API, adds the secret key on the server and forwards the request.
Denial of wallet
OWASP's name for abuse of a pay-per-use model API in which excessive requests produce a large bill rather than a crash.

2Explanation

Introduction

In LLM APIs and Streaming you called a model from Python and printed tokens as they arrived, and in REST APIs and System Integration you saw how programs talk over HTTP. Both ran in a terminal. The next step is to put an interface in front of that code so that a customer, a colleague or a manager can try it without one.

There are three common ways to do it, and they differ in how much of the interface you write. Streamlit treats a Python script as the app: each widget call, such as st.chat_input or st.slider, draws something and returns the user's current input, and the whole script runs again after every interaction. Gradio treats a Python function as the app: you hand it a function and it builds the inputs, outputs, request queue and a public API around it. For chat, gr.ChatInterface needs only a function that receives the message and the history. A React app is an ordinary web page: you write the components, and because a browser cannot keep an API key secret, you also write a small server that calls the model and streams the reply back.

An analogy: Streamlit and Gradio are like filling in a form template. They are fast and consistent, and limited to the template's shape. React is like designing the form on blank paper. It is slower, but you decide everything, including the login, the layout and what a citation looks like.

The lesson follows the order in which a prototype grows. It first shows how each tool works, then how to stream a chat and display sources and intermediate steps so that users can judge answers, and finally what to change before real users arrive. Five documented applications at the end show the same choices in real projects.

How it works

What each tool is, and what you still own

Gradio's quickstart (opens in a new tab) describes it as an open-source Python package for building a demo or web application for a machine learning model, an API or any Python function. It has three levels: Interface for inputs-to-outputs demos, ChatInterface for chatbots and Blocks for custom layouts and data flows. Streamlit's documentation (opens in a new tab) describes an app model in which the script runs again whenever the user interacts with a widget. React is different in kind. It draws the interface in the browser, and calling the model, holding keys and checking who the user is remain your job on a server.

Streamlit: a script that reruns

Streamlit runs the script from top to bottom when the source file changes and whenever the user interacts with a widget, so ordinary variables are rebuilt every time. Anything that must survive goes in st.session_state, which the documentation (opens in a new tab) describes as variables shared between reruns for one user session. Each browser tab that connects gets its own session, and the state is lost when the tab closes or the server crashes.

The chat elements are built for this model. st.chat_input returns the submitted text on the run that follows a submit and None on other runs, st.chat_message draws one message, and st.write_stream shows a generator as it produces text and returns the complete text at the end (tutorial (opens in a new tab)).

python
import streamlit as st

st.title("Policy assistant")
if "messages" not in st.session_state:
    st.session_state.messages = []

for m in st.session_state.messages:              # redraw history on every rerun
    with st.chat_message(m["role"]):
        st.markdown(m["content"])

if prompt := st.chat_input("Ask a question"):    # None unless a message was just sent
    st.session_state.messages = [*st.session_state.messages, {"role": "user", "content": prompt}]
    with st.chat_message("user"):
        st.markdown(prompt)
    with st.chat_message("assistant"):
        reply = st.write_stream(token_stream(prompt))   # your generator of text pieces
    st.session_state.messages = [*st.session_state.messages, {"role": "assistant", "content": reply}]

Two rules follow. The model call sits inside the if, so it runs once per message and not on every unrelated click. The loop at the top is not optional, because every rerun rebuilds the screen from scratch. For slow work, st.status (opens in a new tab) gives a container with the states running, complete and error that you can update and collapse.

Gradio: a function, a queue and an API

gr.ChatInterface needs one function that takes the new message and the history, a list of dictionaries with role and content keys. Return a string for a one-shot reply, or yield growing strings to stream; while it streams, the Submit button becomes a Stop button. Retry, undo and clear buttons come built in, additional_inputs adds controls such as a system prompt box, and gr.load_chat points a chat UI at an OpenAI-compatible endpoint (guide (opens in a new tab)).

python
import gradio as gr

def respond(message, history):
    partial = ""
    for piece in token_stream(message):
        partial += piece
        yield partial          # each yield replaces the reply shown so far

gr.ChatInterface(respond).launch()

Gradio does not rerun anything per click; it queues requests. The performance guide (opens in a new tab) says requests are processed in order and gives the defaults: default_concurrency_limit is 1 (one running call per event listener), max_size is None (no cap on waiting requests) and max_threads is 40. With limit ccc, calls of TTT seconds each and kkk users who submit at the same moment, and assuming a call holds its slot until its response has finished, user kkk waits

waitk=⌊k−1c⌋T\text{wait}_k = \left\lfloor \frac{k-1}{c} \right\rfloor Twaitk​=⌊ck−1​⌋T

seconds before the call starts. With T=20T = 20T=20 the sixth user waits 100 seconds at the default and 20 seconds at a limit of 5.

A higher limit costs memory and uses up your API rate limit, so choose it deliberately and set max_size so a surge is refused rather than queued without end. Every Gradio app also exposes an API with Python and JavaScript clients, which is why a Gradio back end can later feed a React front end.

React: a browser app plus a server of your own

A React chat has two halves. The browser half holds the input and the message list. The server half receives the conversation, calls the model with the key it keeps secret, and streams the reply back. Vercel's AI SDK shows the usual split (chatbot docs (opens in a new tab)): a useChat hook returns messages, sendMessage, stop, regenerate, error and a status of submitted, streaming, ready or error, and each message is a list of typed parts such as text, reasoning, source-url and source-document. Its stream protocol (opens in a new tab) is server-sent events carrying JSON chunks such as text-delta, source-url, tool-input-available and tool-output-available, ending with data: [DONE].

The browser's EventSource takes a URL and an optional withCredentials flag (MDN (opens in a new tab)), with no way to set a method or a body. A chat client that must POST the history therefore usually reads the response body of fetch. This reader was checked under Node 24 against the stream in the worked example. It buffers until a blank line because network chunks do not respect message boundaries:

javascript
async function streamChat(url, body, onEvent) {
  const res = await fetch(url, {
    method: "POST", headers: { "Content-Type": "application/json" }, body: JSON.stringify(body),
  });
  if (!res.ok || !res.body) throw new Error(`HTTP ${res.status}`);
  const reader = res.body.pipeThrough(new TextDecoderStream()).getReader();
  let buffer = "";
  for (;;) {
    const { value, done } = await reader.read();
    if (done) return;
    buffer += value;
    let end;
    while ((end = buffer.indexOf("\n\n")) !== -1) {
      const payload = buffer.slice(0, end).replace(/^data: /, "");
      buffer = buffer.slice(end + 2);
      if (payload === "[DONE]") return;
      onEvent(JSON.parse(payload));
    }
  }
}

Showing sources and intermediate steps

Users trust an answer more when they can check it, and developers debug faster when they can see the steps. Both need the server to send more than text. A design that works in all three tools is a stream of typed events: step (what the system is doing), source (a document with a number the text can cite) and text-delta (a piece of the answer). The Azure sample in this lesson does the same: the first streamed line carries the context, meaning retrieved data points and a record of thoughts, and later lines carry text deltas. Sending sources first lets the interface show them, and resolve markers such as [1], before the first word.

Each tool has a native place for the extra events. Streamlit has st.status. Gradio's chatbot reads a metadata dictionary on a message: a title makes a collapsible accordion, status set to pending shows a spinner and done closes it, log and duration add detail, and id with parent_id nest steps (agents guide (opens in a new tab)). React message parts map onto components you write. Keep the extras short and collapsible.

What to harden before real users arrive

A prototype's shortcuts are safe only while the audience is you. Before anyone else uses it, check seven things.

  1. Secrets stay on the server. Keys come from environment variables or a secret store, never from source files or code shipped to a browser.
  2. Real authentication, not a link. A public share link, a basic password or a login button is not an access policy (see the edge cases below).
  3. Bound spend and load. OWASP's Unbounded Consumption (opens in a new tab) entry names denial of wallet and recommends input limits, rate limits, quotas, timeouts and monitoring. In practice: a maximum input length, a maximum output length, a per-user message cap, and a queue size and concurrency limit that you chose.
  4. Render model output as inert text. OWASP's Improper Output Handling (opens in a new tab) entry says to treat model output like untrusted user input. Gradio's Chatbot (opens in a new tab) has sanitize_html on by default and warns against turning it off. In React, avoid dangerouslySetInnerHTML (opens in a new tab) for anything a model wrote.
  5. Know which files you serve. Decide which directories the framework may expose.
  6. Keep conversations somewhere durable if users expect history or you need an audit trail, because Streamlit session state ends with the tab.
  7. Treat retrieved text and tool output as untrusted. See Prompt Injection and LLM Security.

Worked example: One typed event stream, rebuilt as a message with steps, sources and text

The pipeline below answers a question from four short policy documents using only the Python standard library (3.9 or later). Retrieval and the model are stand-ins, so everyone gets identical output. What is real is the shape of the stream: typed events, sources before text, server-sent-events framing, and a client that rebuilds one message from chunks that can split anywhere. Save it as stream_demo.py.

python
import json
import re

DOCS = {
    1: ("Leave accrual", "Employees accrue 1.5 days of annual leave per month."),
    2: ("Leave carry-over", "Up to 5 days of unused annual leave carry over to the next year."),
    3: ("Expenses", "Expenses over 50 euros need a receipt."),
    4: ("Remote work", "Staff may work remotely 3 days per week."),
}
STOPWORDS = {"how", "much", "do", "i", "and", "does", "the", "a", "of", "to", "up", "per", "is", "are", "can"}


def words(text):
    return {w for w in re.findall(r"[a-z]+", text.lower()) if w not in STOPWORDS}


def retrieve(question, top_k=2):  # stand-in for vector search: rank by shared words
    scored = [(len(words(question) & words(title + " " + body)), doc_id)
              for doc_id, (title, body) in DOCS.items()]
    ranked = sorted((s for s in scored if s[0] > 0), key=lambda s: (-s[0], s[1]))
    return [doc_id for _, doc_id in ranked[:top_k]]


def answer_events(question):  # the pipeline yields typed events, not one string
    yield {"type": "step", "label": f"Searching {len(DOCS)} documents"}
    hits = retrieve(question)
    for n, doc_id in enumerate(hits, start=1):
        yield {"type": "source", "n": n, "title": DOCS[doc_id][0]}
    yield {"type": "step", "label": f"Writing an answer from {len(hits)} sources"}
    answer = " ".join(f"{DOCS[doc_id][1]} [{n}]" for n, doc_id in enumerate(hits, start=1))
    for token in re.findall(r"\S+\s*", answer or "I could not find that in the documents."):
        yield {"type": "text-delta", "delta": token}  # stand-in for the model's tokens
    yield {"type": "finish"}


def to_sse(event):
    return f"data: {json.dumps(event)}\n\n"


def parse_sse(chunks):  # chunks can split anywhere, so buffer until a blank line
    buffer = ""
    for chunk in chunks:
        buffer += chunk
        while "\n\n" in buffer:
            block, buffer = buffer.split("\n\n", 1)
            payload = block.removeprefix("data: ")
            if payload == "[DONE]":
                return
            yield json.loads(payload)


def apply_event(message, event):  # returns a new message; the old one is never edited
    kind = event["type"]
    if kind == "step":
        return {**message, "steps": [*message["steps"], event["label"]]}
    if kind == "source":
        return {**message, "sources": [*message["sources"], f'[{event["n"]}] {event["title"]}']}
    if kind == "text-delta":
        return {**message, "text": message["text"] + event["delta"]}
    return {**message, "done": True}


if __name__ == "__main__":
    question = "How much annual leave do I accrue, and does unused leave carry over?"
    wire = "".join(to_sse(e) for e in answer_events(question)) + "data: [DONE]\n\n"
    chunks = [wire[i:i + 40] for i in range(0, len(wire), 40)]  # the network may split anywhere
    message, first_text = {"steps": [], "sources": [], "text": "", "done": False}, None
    for count, event in enumerate(parse_sse(chunks), start=1):
        message = apply_event(message, event)
        first_text = first_text or (count if message["text"] else None)
    print("\n".join(wire.split("\n\n")[:5]))
    print(f"events={count} bytes={len(wire)} chunks={len(chunks)} first_text_event={first_text}")
    print(json.dumps(message))

data: {"type": "step", "label": "Writing an answer from 2 sources"}

  • Events and chunks do not line up. The 38 chunks of at most 40 characters cut events in the middle, so parse_sse emits an event only after it sees the blank line that ends it.
  • Four events arrive before the first word. first_text_event=5 means two steps and two sources can be on screen while the model is still starting. A plain text stream would show nothing for that time.
  • Citations resolve. The text contains [1] and [2], and the sources list has the same numbers.

The same events in Streamlit

After pip install streamlit, save this as app.py beside stream_demo.py and run streamlit run app.py. A submitted question is the only run that calls the pipeline; any other interaction reruns the script, redraws the stored history and calls nothing.

python
import streamlit as st
from stream_demo import answer_events

st.title("Policy assistant")
if "history" not in st.session_state:
    st.session_state.history = []

for item in st.session_state.history:              
    with st.chat_message(item["role"]):
        st.markdown(item["text"])
        for source in item.get("sources", []):
            st.caption(source)

if question := st.chat_input("Ask about leave, expenses or remote work"):
    st.session_state.history = [*st.session_state.history, {"role": "user", "text": question}]
    with st.chat_message("user"):
        st.markdown(question)
    with st.chat_message("assistant"):
        status = st.status("Working", expanded=True)
        box = st.empty()
        text, sources = "", []
        for event in answer_events(question):
            if event["type"] == "step":
                status.write(event["label"])
            elif event["type"] == "source":
                sources = [*sources, f'[{event["n"]}] {event["title"]}']
                status.write(sources[-1])
            elif event["type"] == "text-delta":
                text += event["delta"]
                box.markdown(text)
        status.update(label="Done", state="complete", expanded=False)
        for source in sources:
            st.caption(source)
    st.session_state.history = [*st.session_state.history,
                                {"role": "assistant", "text": text, "sources": sources}]

In Gradio the same events become a list of gr.ChatMessage objects, the first with metadata={"title": "Steps and sources", "status": "pending"}, yielded after each event. In React, the streamChat reader above delivers the same 30 events and the same text from a server that sends this wire text (checked under Node 24).

Edge cases and limitations

A model call outside the chat guard repeats on every rerun
Streamlit reruns the script for any widget interaction, not only for a submitted message. An LLM call placed outside the if st.chat_input block therefore runs again when a sidebar slider moves, spending tokens and redrawing a different answer. Keep model calls inside the guard or behind a button, store the result in session state, and cache pure helper functions with st.cache_data, which the documentation offers for skipping costly work on reruns.
The conversation on screen is not the conversation sent to the model
The computer use demo keeps its own copy of tool results in session state, with a code comment saying the tool result sent back to the API is not enough to redraw every detail such as screenshots. It also has a setting for how many recent images are sent to the model. Keep two things apart: display state for the interface, and model context for the API call. Mixing them either loses detail on screen or sends every screenshot to the model on every turn.
A public link or a login button is not access control
Gradio says share links are publicly accessible to anyone who has them and expire after one week, that its built-in auth is a basic layer unsuited to stringent access control, and that adding gr.LoginButton does not stop users who have not logged in from running events. Use these for a short demo with non-sensitive data, and for anything else put the app behind your organisation's single sign-on or a platform that enforces roles.
Citations that point nowhere
If the interface prints text first and sources last, users read claims before they can check them, and a marker such as [2] cannot be resolved while the answer streams. A model can also cite a number you never sent. Send sources first with stable numbers, and when the text contains a marker with no matching source, drop the marker or flag it instead of rendering a dead link.
Streams behave differently once deployed
MDN notes that over HTTP/1.1 a browser allows only six server-sent-event connections per domain, shared across all tabs, while HTTP/2 negotiates a larger number. Separately, reverse proxies and some hosting layers can hold a response back until it finishes, so tokens arrive in one lump even though the code streams. Test streaming on the deployed address, not only on localhost, and keep each stream short-lived.

When to use it, and when something simpler is enough

Use it when

  • People outside the team must try a model-backed workflow within days, and the audience is a small group of colleagues, customers or workshop attendees whom you can name.
  • The logic is already Python, such as a pipeline, a notebook or an agent loop, and one developer will maintain the interface.
  • You want feedback on answers, sources and steps rather than on visual design, so a standard chat layout is enough.
  • You expect to learn from the prototype and may discard the interface, so the real logic is kept behind a function or an API that any front end can call.

Think twice when

  • The app will be open to the public or to many simultaneous users with nothing in front of it. Neither Streamlit nor Gradio is a substitute for an authentication and rate-limiting layer.
  • The product needs custom interactions, an audited accessible interface or a place inside an existing web app. Start in React, or whatever the product already uses.
  • Users must keep conversations across devices and sessions, with per-user permissions. Per-tab session state cannot do that.

A simpler alternative. A notebook or a command-line script shared on screen, or a recorded run, is enough while only the team needs to see results. Move to Streamlit or Gradio when someone outside the team must try the system alone, and move to a React app when login, layout or embedding requirements start to dominate the work.

Key takeaways

  • Choose by what you must control: Streamlit for a Python script that reruns around widgets and data, Gradio for a function or chat that you may also want to expose as an API, and React when you need your own login, layout or a place inside an existing web app.
  • Streamlit reruns the whole script on every interaction, so history lives in session state, the model call belongs inside the chat-input guard, and everything in session state is lost when the tab closes.
  • Gradio queues requests and, by default, runs one call at a time per function, so a demo for several simultaneous users needs a concurrency limit and a queue size that you chose on purpose.
  • A streaming chat is best built on typed events for steps, sources and text, with sources sent before the text, so that every front end can show progress and resolvable citations as they arrive.
  • A React front end always needs a server route that holds the API key, because anything delivered to the browser can be read by the user.
  • Before real users arrive, remove the shortcuts: move secrets out of the code, add real authentication, set spend and rate limits, render model output as inert text, restrict file exposure and store conversations somewhere durable.

Example 1 of 5

Streamlit as the control room for Anthropic's computer use reference demo

AnthropicDocumented in an open-source project

Anthropic's claude-quickstarts repository contains a computer use reference demo. Its README lists a Streamlit app as the way to interact with the agent loop, and the demo's streamlit.py source shows how that app renders each message and tool result. [19][20][5]

The problem

Someone evaluating computer use has to watch a model operate a desktop. They send an instruction and then need to see each model message, each tool call and each tool result, including screenshots, as the run proceeds. The README also states that computer use poses risks distinct from ordinary chat features, and the demo is packaged as a Docker container that holds both the interface and the desktop being controlled.

Where this topic fits

Streamlit is the whole front end, sitting on top of the agent loop. The script keeps the message list in session state, redraws it on every rerun, and passes rendering callbacks into the loop function sampling_loop, so each assistant block and tool result is drawn as it arrives. The desktop itself is shown by a separate viewer on another port.

How it is applied, step by step

  1. The container starts the Streamlit app next to a virtual desktop. The README lists separate local addresses for a combined page, the Streamlit-only page, a desktop-only view and a VNC connection.
  2. On every rerun the script redraws the stored messages inside a Chat tab. Tool results are redrawn from a second copy kept in session state, because a code comment says the result sent back to the API is not enough to show every detail.
  3. When the user submits text through st.chat_input, the script appends it to the stored messages and calls the agent loop with the messages and three callback functions.
  4. The output callback draws assistant text, thinking blocks and tool-use blocks. Tool results are drawn as code or markdown for output, as an error box for failures and as an image for screenshots.
  5. Another callback stores each HTTP request and response exchanged with the API and draws it in an HTTP Exchange Logs tab, giving the developer a raw view next to the readable one.
  6. Sidebar controls let the user hide screenshots and set how many recent images stay in the conversation sent to the model.
  7. Safety sits around the app rather than inside it: the README advises a dedicated virtual machine or container with minimal privileges, no sensitive data, a domain allowlist and human confirmation for consequential actions.

Why this approach fits

The agent loop is already Python, so Streamlit lets the same process draw the run with a handful of calls and no JavaScript. Callbacks fit a loop that produces many kinds of output in sequence, and the audience is developers who want to see raw steps, not a polished product. The rerun model costs little here because the interface keeps its own history in session state.

Limitation or tradeoff

This is a demonstration for developers on a trusted machine, not a multi-user product. Exposing its ports to a network would put an agent with desktop control in front of anyone who can reach them, and the README's protections concern isolating the machine, not authenticating people. The source also passes unsafe_allow_html=True to inject its own CSS constant, which Streamlit's documentation tells developers not to do. Text that comes from a model or a tool should keep the default HTML escaping, as the demo's tool output does.

What the sources document

4Common mistakes

  1. Putting the model API key in browser code or in a variable that the build exposes to the browser

    Why it causes problems
    Anything delivered to a browser can be read by its user, so a key in the bundle or in a public-prefixed variable can be copied and used, and the owner pays for what is spent. Rotating the key then breaks every deployed copy that contains it.
    How to recognise it
    Open the browser's developer tools and search the loaded scripts and network requests for the key or its prefix. In a Next.js app, check whether the variable name starts with NEXT_PUBLIC_, which the Agent Chat UI README reserves for values that are not secret.
    How to fix it
    Keep the key in a server-side environment variable or secret store and call the model from a server route. Put authentication in front of that route, because a proxy that adds the key for every caller only moves the problem, as the Agent Chat UI README warns.

  2. Treating a Gradio share link, a shared password or a login button as access control

    Why it causes problems
    Gradio documents that share links are public to anyone who has them, that its built-in auth is a basic layer, and that adding a login button does not stop users who have not logged in from running events. A link pasted into a chat channel reaches people you never intended, and the app spends your budget and reads your data on their behalf.
    How to recognise it
    Open the link in a private window on a different network and ask a question. If it answers, anyone with the URL can use it. Search the code for gr.LoginButton and check whether any function actually tests who the caller is.
    How to fix it
    Use share links only for short demos with harmless data. For anything else, host the app behind your organisation's single sign-on or on a platform that enforces roles, and check identity inside the functions that touch data.

  3. Rendering model output with HTML enabled

    Why it causes problems
    Model text is shaped by prompts, retrieved documents and tool output, any of which may contain markup. OWASP lists cross-site scripting from model-generated Markdown or JavaScript as an example of improper output handling. Enabling HTML turns a text problem into code running in the user's session.
    How to recognise it
    Search for unsafe_allow_html=True in Streamlit code, sanitize_html=False in Gradio, and dangerouslySetInnerHTML in React. Then ask the model to answer with a script tag or an image tag that points at a test URL, and see whether it runs or loads.
    How to fix it
    Leave the defaults on: Streamlit escapes HTML, and Gradio's chatbot sanitizes it. In React render text through JSX or a Markdown renderer that sanitizes. If you need rich output, allow a short list of tags instead of everything.

  4. Leaving Gradio's queue and concurrency at their defaults for a multi-user demo

    Why it causes problems
    With the documented defaults, each function runs one call at a time and the queue has no size cap. With 20-second calls the sixth simultaneous user waits 100 seconds, and a surge builds a long queue of requests that nobody is still waiting for. Raising the limit without measuring can exhaust memory or your provider rate limit instead.
    How to recognise it
    Open the app in six tabs, submit a question in each at once and note how long each takes to start answering. Watch server memory and the provider's rate-limit responses during the test.
    How to fix it
    Set the concurrency limit from measured capacity, set a queue size so that a surge is refused early, cap output length on the model call, and rehearse the demo with a scripted load before real people arrive.

  5. Streaming plain text only and adding sources or steps as an afterthought

    Why it causes problems
    The interface cannot show progress or citations until the end, markers inside the text cannot be resolved, and when an answer is wrong nobody can see which documents or steps led to it. Retrofitting structure later means changing the server and every client together.
    How to recognise it
    Watch the first seconds of a run. If nothing appears until the first word, or the sources appear only after the last word, the stream carries no structure.
    How to fix it
    Define typed events (step, source, text-delta, finish) at the start, send sources first with stable numbers, and keep the event format independent of the front end so that Streamlit, Gradio or React can each render it.

python
import logging

import streamlit as st
from stream_demo import answer_events

MAX_QUESTIONS = 5
MAX_CHARS = 300
log = logging.getLogger("policy_assistant")

st.title("Policy assistant")
if "history" not in st.session_state:
    st.session_state.history = []
    st.session_state.asked = 0

for item in st.session_state.history:
    with st.chat_message(item["role"]):
        st.markdown(item["text"])
        for source in item.get("sources", []):
            st.caption(source)

limit_reached = st.session_state.asked >= MAX_QUESTIONS
if limit_reached:
    st.info(f"This session has used its {MAX_QUESTIONS} questions.")

question = st.chat_input("Ask about leave, expenses or remote work",
                         max_chars=MAX_CHARS, disabled=limit_reached)
if question and not limit_reached:
    st.session_state.asked = st.session_state.asked + 1
    st.session_state.history = [*st.session_state.history, {"role": "user", "text": question}]
    with st.chat_message("user"):
        st.markdown(question)
    with st.chat_message("assistant"):
        status = st.status("Working", expanded=True)
        box = st.empty()
        text, sources = "", []
        try:
            for event in answer_events(question):
                if event["type"] == "step":
                    status.write(event["label"])
                elif event["type"] == "source":
                    sources = [*sources, f'[{event["n"]}] {event["title"]}']
                    status.write(sources[-1])
                elif event["type"] == "text-delta":
                    text += event["delta"]
                    box.markdown(text)
        except Exception:
            log.exception("pipeline failed (question length %d)", len(question))
            status.update(label="Failed", state="error")
            st.error("Something went wrong. Please try again.")
        else:
            status.update(label="Done", state="complete", expanded=False)
            for source in sources:
                st.caption(source)
            st.session_state.history = [*st.session_state.history,
                                        {"role": "assistant", "text": text, "sources": sources}]

How each requirement is met. max_chars makes the browser refuse a 301st character. The counter lives in session state and increases before the pipeline runs, so failed questions count too. limit_reached is computed before the widget is created so that the input is disabled on the next rerun, and the and not limit_reached test is a second guard in case a sixth submission arrives anyway. The try covers only the event loop. The except branch logs details on the server and shows a fixed sentence, so no exception text reaches the page. The assistant message is saved only in the else branch, so a failure leaves the question without a half-finished answer. All text goes through st.markdown and st.caption with the default HTML escaping.

Refreshing the page resets the counter, because session state belongs to the tab. That makes the cap a courtesy to a well-behaved user, not a spending limit: anyone can refresh. A real quota must be enforced on the server and keyed to something the user cannot reset, such as an authenticated user id, which is why authentication comes before rate limiting in the hardening list.

This solution was checked against a stand-in module that records Streamlit calls, not in Streamlit itself. It uses only calls described in the Streamlit documentation cited in this lesson, but run it yourself and compare the result with the expected behaviour above.

Networkserver_name="0.0.0.0"Binds to every network interfaceBind locally and let a gateway handle external access
Filesallowed_paths=["/srv/customer_notes"]Files in that folder can be fetched by URL from a publicly reachable appRemove it and keep data outside served paths
Spend and loadDefault queue, no input or output limitsOne user can send huge inputs or many requests and run up the bill (denial of wallet)Set max_size, a concurrency limit, an input cap and max_tokens
RobustnessNo error handling or loggingFailures show up as confusing errors and leave no server-side traceCatch errors, show a fixed message and log details on the server
Prompt injectionNotes are pasted into the prompt as trusted textA note containing instructions can steer the modelDelimit untrusted text and limit what the model can do

The first three to fix are the public share link with server_name and allowed_paths (they decide who can reach the data), the missing authentication (without it nothing else can be enforced per user), and the whole-file prompt (it exposes all customers to every user). The hard-coded key is serious but is limited once the app is no longer public. A safer sketch, where search_notes_for_user is a function you would still have to write:

python
import os

import gradio as gr
from openai import OpenAI

client = OpenAI(api_key=os.environ["OPENAI_API_KEY"])
MAX_CHARS = 500


def answer(message, history):
    if len(message) > MAX_CHARS:
        return f"Please keep questions under {MAX_CHARS} characters."
    notes = search_notes_for_user(message)  # only passages this user may see
    reply = client.chat.completions.create(
        model="some-model",
        max_tokens=400,
        messages=[{"role": "user", "content": notes + "\n\nQuestion: " + message}],
    )
    return reply.choices[0].message.content


demo = gr.ChatInterface(answer)
demo.queue(max_size=20, default_concurrency_limit=4)
demo.launch()  # reach it through the company's authenticating proxy

  • Did you find at least eight problems and tie each to a line of the code?
  • Can you explain why binding to 0.0.0.0, share=True and allowed_paths are different exposure routes rather than three names for the same problem?
  • Did your fixes include limits on input size, output size and queue length, and not only secrecy?
  • Can you say why authentication ranks above the hard-coded key once the app is no longer public?
