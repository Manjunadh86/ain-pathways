ML Pipelines, Feature Stores and Continuous Training

An ML pipeline is a training workflow written as code: ordered, automated steps that validate data, build features, train a model, test it and register it. Continuous training means an orchestrator reruns that pipeline on a schedule or a trigger, so production models are refreshed without anyone repeating the steps by hand.

1Overview

Why it matters

A model trained once in a notebook starts ageing the day it is deployed. Prices change, customers change, an upstream team renames a column, and the model keeps answering as confidently as it did on its training data. If retraining means one person rerunning cells from memory, it happens rarely, it is never done the same way twice, and nobody can say which data produced the model that is live. Google's MLOps guide notes that only a small fraction of a real-world ML system is ML code. The rest is data collection, validation, feature computation, serving and monitoring, and much of what goes wrong in production goes wrong there.

Three failures decide whether an ML system keeps working, and each has an answer at the pipeline level. Bad data reaches training unnoticed, so pipelines check every batch against a schema before any compute is spent. Features are computed one way for training and another way for live requests, so teams keep a single definition behind a feature store. A retrained model turns out worse than the one it replaces, so an automated gate compares the two before promotion. ML engineers, data engineers and anyone who owns a model after launch need this vocabulary, because production reviews ask exactly these questions: what triggers retraining, what stops a bad batch, and how a model travels from the registry to users.

Key terms

MLOps
The practice of running ML systems with software delivery discipline (automation, testing, versioning and monitoring) so that models can be built, released and operated reliably.
Pipeline
A training workflow split into steps with declared inputs and outputs, so that software can run the steps in order and record what each one produced.
DAG (directed acyclic graph)
A set of tasks joined by one-way dependencies with no loops. An orchestrator uses it to decide which task may run next. Airflow 3 writes it as "Dag".
Orchestrator
The service that starts pipeline runs, launches each task once its upstream tasks have succeeded, retries failures and keeps the run history. Airflow and Kubeflow Pipelines are examples.
Schema
A written description of valid data (column names, types, allowed ranges and categories) that every new batch is checked against.
Training-serving skew
Any difference between the data or feature logic a model was trained with and what it receives when it serves predictions.
Feature store
A system that holds each feature definition once and serves its values both to training (full history, offline) and to live prediction (latest value, online).
Point-in-time join
Building training rows by attaching to each labelled event the feature values that were known at that event's timestamp, and none computed later.
Continuous training (CT)
Automatically retraining and releasing a model when a schedule, new data or a monitoring signal starts the pipeline.
Champion and candidate
The champion is the model serving now. A candidate is a newly trained model that must beat the champion in an automated comparison before it replaces it.

2Explanation

Introduction

You can already train a model, log the run and register the result (see experiment tracking and model registries). That answers "which model is this, and how was it made?". It leaves open who retrains it next month, on which data, and how anyone knows the new version is safe to release.

Compare a recipe that one cook follows from memory with a production line. On the line every station has a fixed job, receives a checked input and hands on a labelled output, and an inspector can stop the line before a faulty part reaches a customer. An ML pipeline is that line for a model: validate the data, build the features, train, evaluate, register. An orchestrator such as Apache Airflow or Kubeflow Pipelines is the software that runs the stations in order. Continuous training (CT) means the line starts by itself, on a schedule or when a trigger fires.

MLOps is the name for running ML systems with this discipline. Google's MLOps guide (opens in a new tab) defines it as an engineering culture and practice that unifies ML system development and ML system operation. Four principles run through that guide and through this lesson:

  • Automate every step that will be repeated, including retraining.
  • Version code, data and models together, so any model can be traced to what produced it.
  • Test data and models, not only code.
  • Monitor the live system and feed what you observe back into the pipeline.

The guide describes three maturity levels by how much of this is automated:

Microsoft's MLOps maturity model (opens in a new tab) cuts the same journey into five levels, from "No MLOps" and "DevOps but no MLOps" through "Automated training" and "Automated model deployment" to "Full MLOps automated operations". Both documents treat the move as gradual: a team can automate training long before it automates deployment.

The rest of the lesson walks the pipeline from left to right: its stages, the orchestrators that run them, the data checks that stop a bad batch, feature stores and why training and serving must agree, and finally CI/CD and automated retraining. It builds on feature engineering and hands over to model deployment and monitoring and drift.

How it works

The stages of a training pipeline

A pipeline is a chain of steps. Each step reads named inputs and writes named outputs, often called artefacts: a dataset snapshot, a statistics file, a model, a metrics report. An automated pipeline has eight stages, two of which are gates.

  1. Ingest a defined slice of data, such as last week's orders, and save it as a snapshot.
  2. Validate the data against a schema and against earlier batches. A failure stops the run.
  3. Build features, or fetch them from a feature store.
  4. Train a candidate model and log the run.
  5. Evaluate it on data it has not seen.
  6. Validate the model against the one in production. A failure keeps the old model.
  7. Register and deploy the winner.
  8. Monitor live inputs and outcomes, which supply the signals that start the next run.

Two properties separate this from a long script. Any step can be rerun without the others, and every run records which inputs produced which outputs, so a live model can be traced back to its data.

Orchestration: Airflow and Kubeflow Pipelines

An orchestrator executes a DAG (directed acyclic graph): tasks joined by one-way dependencies, with no loops. It starts runs, launches each task when its upstream tasks have finished, retries failures and keeps the history.

Apache Airflow is a general-purpose orchestrator whose workflows are Python files. In Airflow 3 a Dag is declared with decorators from airflow.sdk:

python
import pendulum
from airflow.sdk import dag, task

@dag(schedule="0 3 * * 1", start_date=pendulum.datetime(2026, 1, 5, tz="UTC"),
     catchup=False, default_args={"retries": 2})
def retrain_delivery_model():
    @task()
    def validate() -> str:
        # raise an exception here when the batch breaks the schema
        return "s3://ml/delivery/2026-03-02.parquet"

    @task()
    def train(batch: str) -> str:
        return "models:/delivery/candidate"

    @task.short_circuit()
    def beats_champion(candidate: str) -> bool:
        return True      # a falsy value skips everything downstream

    @task()
    def promote(candidate: str) -> None: ...

    candidate = train(validate())
    beats_champion(candidate) >> promote(candidate)

retrain_delivery_model()

Calling one task with another's result passes the value and declares the dependency. By default (opens in a new tab) a task runs only when all its upstream tasks succeeded, so a failed validate leaves train in the upstream_failed state. The second gate uses @task.short_circuit (opens in a new tab): a falsy return value skips the downstream tasks without failing the run. Tasks exchange small values such as paths and model URIs; the data itself stays in storage. Besides cron expressions, a Dag can be scheduled on an asset (opens in a new tab), so retraining starts when the task that refreshes a table completes successfully.

Kubeflow Pipelines (KFP) is built for ML on Kubernetes. Components are usually Python functions, the SDK compiles the pipeline to a YAML file, and at run time each component execution is one container execution (opens in a new tab). Because steps exchange declared parameters and artefacts, KFP can reuse a cached result instead of rerunning a step, and it tracks and visualises runs and artefacts in its UI. A compiled pipeline runs on the open-source backend or on Google Cloud Vertex AI Pipelines.

Choose by what you already run. Airflow fits when data pipelines are scheduled there and training is one more job. KFP fits when steps need their own images and hardware (a GPU for training, a small pod for validation) and you want artefact tracking built in.

Data and schema validation

A schema states what a valid batch looks like: column names, types, allowed ranges and categories, and which columns may be missing. Validation computes statistics for the new batch and compares them with the schema. TensorFlow Data Validation (opens in a new tab) (TFDV) can infer a first schema from data, and its guide warns that the inferred schema is best-effort and must be reviewed. Keep the schema in version control and change it through review, like code.

Checks on one batch catch missing columns, wrong types, out-of-range values and unexpected categories. Checks across batches catch two more problems:

  • Drift: this batch differs from earlier ones.
  • Training-serving skew: the training data differs from what the live service receives.

For a categorical feature, a readable distance is the largest change in any category's share, the L-infinity distance:

d∞(p,q)=max⁡i∣pi−qi∣d_\infty(p, q) = \max_i \lvert p_i - q_i \rvertd∞​(p,q)=imax​∣pi​−qi​∣

Suppose payment types in training were card 0.60, cash 0.30 and wallet 0.10, and last week's live requests show 0.45, 0.30 and 0.25. The differences are 0.15, 0.00 and 0.15, so d∞=0.15d_\infty = 0.15d∞​=0.15. With a threshold of 0.01 the feature is flagged, and the largest gap shows which category to investigate.

What happens next depends on the anomaly. Google's guide separates schema skews (an unexpected, missing or malformed feature), where the pipeline should stop so people can investigate, from data value skews (the statistics moved because the world changed), which are a reason to retrain.

Feature stores and training-serving consistency

The features a model receives when serving must match the ones it was trained on. The match breaks in two common ways. The first is two code paths: a pandas function builds a feature for training, a re-implementation in the service builds it for live requests, and they disagree on rounding, time zones or missing values. The second is time travel: the training set attaches feature values that were not yet known when the labelled event happened.

A feature store addresses both. Each feature is defined once. An offline store keeps its full history for building training sets, and an online store keeps the latest value per key for fast lookup at request time. Materialisation is the job that copies fresh values into the online store.

For training, the store performs a point-in-time join: for each labelled event it returns the newest feature value at or before the event's timestamp, looking back no further than a time-to-live (TTL). Take avg_minutes_7d, which a nightly job computes for each courier:

OrderOrdered atValue known thenLatest value today
o11 March 18:3030.0 (computed 1 March)41.0
o22 March 09:1534.0 (computed 2 March)41.0
o43 March 12:0041.0 (computed 3 March)41.0

Joining the latest value gives o1 and o2 a number that includes deliveries made after they were placed. The model learns from information it will never have at request time, so it scores better offline than it performs live. In Feast (opens in a new tab), an open-source feature store, get_historical_features does the point-in-time join for training and get_online_features reads the same feature by the same name when serving.

Without a feature store, the cheapest protection is rule 29 of Google's Rules of ML (opens in a new tab): log the features the service actually used and train on that log.

CI, CD and CT for models

Software delivery has continuous integration (CI: every change is built and tested) and continuous delivery (CD: tested changes are released automatically); see CI/CD pipelines. ML keeps both and adds a third loop, because a model can go wrong when no code changed at all.

LoopStarts whenTestsReleases
CICode or pipeline definition changesFeature logic, a short training run that must converge, how components fit togetherPackaged pipeline components
CDCI passesThe pipeline runs in a test environment; the prediction service responds within its latency targetThe training pipeline, and through it the prediction service
CTSchedule, new data or a monitoring signalData validation and model validation inside the pipelineA new model version

The model validation gate is the centre of CT. The pipeline compares the candidate with the champion on the same held-out data, overall and on important slices, and checks that the candidate loads in the serving environment. In TFX, the Evaluator (opens in a new tab) component marks a model as "blessed" only when it meets thresholds relative to a baseline, and the component that pushes models to serving will not push one that is not blessed. A promoted model becomes a new registry version; how it then reaches users is covered in model deployment.

What triggers retraining

Google's guide lists the triggers: on demand, on a schedule, when new training data is available, when model performance degrades, and when the data distribution changes significantly. A schedule is the simplest and is enough when labels arrive steadily. Signal-based triggers depend on monitoring and save compute while the world is stable. To choose a cadence, measure it: evaluate one model on each later week of data and see how fast its error grows. The worked example does exactly that.

Worked example: Eight weeks of a delivery-time model: frozen versus continuously retrained

A delivery service predicts minutes from distance. The script below plays eight weeks of it. world is what really happens: 40 deliveries a week, and from week 4 every kilometre takes a little longer each week (roadworks, so the relationship itself drifts). extract is what the pipeline receives; in week 6 an upstream change sends the distance in metres. Each weekly run validates the batch, fits a least-squares line on the first 30 rows, compares it with the champion on the last 10, and promotes it only if its mean absolute error (MAE) is at most 90 % of the champion's.

python
import random
import statistics

SCHEMA = {"km": (0.2, 40.0), "minutes": (2.0, 180.0)}   # allowed range per column
GATE = 0.90   # promote only if the candidate's error is at most 90 % of the champion's

def world(week):
    """What really happened: 40 deliveries. From week 4, every km takes longer."""
    rng = random.Random(week)
    slope = 2.5 + 0.3 * max(0, week - 3)
    rows = []
    for _ in range(40):
        km = round(rng.uniform(1, 12), 1)
        rows.append({"km": km, "minutes": round(6 + slope * km + rng.gauss(0, 2), 1)})
    return rows

def extract(week):
    """What the pipeline receives. In week 6 an upstream change sends metres."""
    rows = world(week)
    if week == 6:
        rows = [{**r, "km": r["km"] * 1000} for r in rows]
    return rows

def validate(rows):
    return [f"{col}: {bad} of {len(rows)} values outside [{lo}, {hi}]"
            for col, (lo, hi) in SCHEMA.items()
            if (bad := sum(not lo <= r[col] <= hi for r in rows))]

def train(rows):
    xs, ys = [r["km"] for r in rows], [r["minutes"] for r in rows]
    mx, my = statistics.fmean(xs), statistics.fmean(ys)
    w = sum((x - mx) * (y - my) for x, y in zip(xs, ys)) / sum((x - mx) ** 2 for x in xs)
    return {"w": w, "b": my - w * mx}

def mae(model, rows):
    return statistics.fmean(abs(r["minutes"] - model["b"] - model["w"] * r["km"]) for r in rows)

def run_pipeline(week, champion):
    rows = extract(week)
    problems = validate(rows)
    if problems:
        return champion, "STOP     " + problems[0]
    candidate = train(rows[:30])                  # first 30 rows train, last 10 are held out
    if champion is None:
        return candidate, "promote  first model"
    old, new = mae(champion, rows[30:]), mae(candidate, rows[30:])
    if new <= GATE * old:
        return candidate, f"promote  champion {old:.2f}, candidate {new:.2f}"
    return champion, f"keep     champion {old:.2f}, candidate {new:.2f}"

champion, decision = run_pipeline(1, None)
frozen = champion
print(f"week 1  {decision}  (w={champion['w']:.2f}, b={champion['b']:.2f})")
for week in range(2, 9):
    live = champion                               # the model that served this week's requests
    champion, decision = run_pipeline(week, champion)
    print(f"week {week}  frozen {mae(frozen, world(week)):.2f}  live {mae(live, world(week)):.2f}  {decision}")

week 3  frozen 1.98  live 1.98  keep     champion 2.29, candidate 2.10
week 4  frozen 2.75  live 2.75  promote  champion 2.46, candidate 1.02
week 5  frozen 4.94  live 2.56  promote  champion 2.05, candidate 0.85

frozen is the error of the week-1 model on that week's 40 real deliveries. live is the error of whichever model was serving when the week began.

WeeksWhat the pipeline didWhy

4 and 5PromotedThe slope moved from 2.5 to 2.8 and then 3.1 minutes per km. The candidates more than halved the held-out error.

By week 8 the model nobody retrained is wrong by 9.23 minutes on average, and the continuously trained one by 1.85.

Now remove the first gate: change the km range in SCHEMA to (0.2, 99999.0) and rerun. Week 6 prints promote champion 19842.36, candidate 2.19, and week 7 shows live 23.01. The model gate approved a model fitted to metres, because the held-out rows carried the same bug and the candidate fitted them well. Live requests then arrived in kilometres and the model, whose slope was 0.0034 minutes per metre, predicted about six minutes for every delivery. A model gate cannot see an error that is present in both the training rows and the held-out rows. That is why data validation comes first and why it stops the run instead of merely logging a warning.

A production pipeline would train on a rolling window of several weeks and use a larger held-out set, which makes the gate less noisy than ten rows allow here.

Edge cases and limitations

The model gate cannot see a bug that is also in the held-out data
If a batch is corrupted before the split (wrong units, a shifted column, duplicated rows), the training rows and the held-out rows carry the same error and the candidate looks excellent. The worked example shows a model trained on metres passing the gate and then missing by 23 minutes. Only data validation, run before training against a schema that predates the batch, catches this.
Labels that arrive late limit how often retraining is useful
A click is known in minutes, a loan default in months. A pipeline can only train and evaluate on rows whose outcome is known, so the newest usable data is always older than the label delay. Retraining daily on a label that takes 30 days adds little. Until labels arrive, watch input drift and prediction distributions as early signals.
A schema violation is not drift, and retraining on it makes things worse
A changed distribution has two possible causes: the world changed, or a pipeline upstream broke. If a join started dropping rows or a default value of -1 flooded a column, retraining teaches the model the bug. Stop the run on schema anomalies and unexplained jumps, and retrain automatically only on shifts that pass the schema.
The online store can be staler than the training set assumed
A point-in-time join gives each training row the newest value at its timestamp. If materialisation to the online store runs once a day, live requests may see a value up to a day older. The two then differ even though the definition is shared. Set the join's TTL and the features' freshness to match what the serving path can really deliver, and monitor materialisation lag.
Retraining on data the model itself shaped
When predictions decide what users see, next week's training data contains only outcomes for the items the model chose to show. Each retrain reinforces earlier choices and the held-out data shares the bias, so the gate will not flag it. Keep a small share of traffic on random or held-back decisions so that unbiased examples keep arriving.

When to use it, and when something simpler is enough

Use it when

  • The model will be retrained many times because new data keeps arriving and its patterns move, as with prices, demand or fraud.
  • More than one person must be able to reproduce the model, audit which data produced it, or take it over.
  • A bad batch or a worse model reaching users has a real cost, so you need automated stops before deployment.
  • The same features are needed in batch for training and at request time for online predictions, or by several models.

Think twice when

  • The work is a one-off analysis or a prototype of unproven value. Automate after the model has shown it is worth keeping.
  • The data changes once a year or less and the model is retrained as rarely. A documented script run by hand costs less than a platform.
  • You have no trustworthy labels or evaluation set. Automatic promotion without a sound gate only ships regressions faster.
  • You have one batch-scored model and are considering a feature store. A shared transformation function used by both training and scoring is enough.

A simpler alternative. One script, kept in version control, that validates, trains, evaluates and registers for a given date (for example python train.py --date 2026-03-02), started by cron or by a scheduled CI job. That already gives you repeatability and the two gates. Move to an orchestrator when steps need different hardware or independent retries, when you need run history and backfills, or when several pipelines depend on each other.

Key takeaways

  • A production ML system deploys a training pipeline and not just a model. The pipeline is a set of ordered steps that validate data, build features, train, evaluate and register, and an orchestrator runs them.
  • Maturity grows from manual notebooks to an automated, triggered pipeline, and then to CI/CD that tests and releases the pipeline itself. A team can automate one capability at a time.
  • Data validation runs before training because a model gate cannot detect an error that is present in both the training rows and the held-out rows.
  • Training-serving skew is prevented by computing each feature from one definition and by joining feature values to labels as of each event's timestamp.
  • Continuous training needs a trigger and a gate. Retrain on a schedule, on new data or on a monitoring signal, and promote the candidate only when it beats the champion.
  • Choose the retraining cadence by measuring how fast an old model loses accuracy, and start with a scheduled script before adopting a platform.

Example 1 of 5

Uber Michelangelo: one feature store feeding training and online prediction

UberDocumented in an engineering article

Michelangelo is Uber's internal ML platform. Its product manager and engineering manager described it in the 2017 Uber Engineering article "Meet Michelangelo", which covers the data pipelines, the shared Feature Store and the UberEATS delivery-time model that uses them. [16]

The problem

Before the platform, the article says, Uber had no systems for building reliable, uniform and reproducible pipelines for training and prediction data, and no established path for putting a model into production. The UberEATS delivery-time model shows what such pipelines must deliver. At request time it needs features of three ages: fields from the request itself, historical aggregates such as a restaurant's average meal preparation time over the last seven days, and near-real-time aggregates such as the same average over the last hour. The values the online service reads must be the ones the model was trained on.

Where this topic fits

The feature store sits between raw data and the two consumers of features. Upstream are batch jobs over the HDFS data lake and streaming jobs over Kafka. Downstream are training jobs, which read features offline, and the online prediction service, which reads them from Cassandra by key. One step later, inside each model's configuration, a small DSL selects and transforms the features that model uses.

How it is applied, step by step

  1. Batch jobs written in Spark and Hive SQL compute historical features over the data lake. Features in the shared store are recalculated every day.
  2. The same batch output is bulk-loaded into Cassandra on a regular basis, so the online service reads values produced by the pipeline that also produced the training data.
  3. For features that must be fresh, events are published to Kafka and Samza streaming jobs compute the aggregates. Results are written to Cassandra for serving and logged back to HDFS for later training.
  4. A new streaming feature has no history yet, so a backfill tool runs the computation as a batch job over historical logs to generate training data for it.
  5. A model's configuration names the features it needs by their canonical names and adds DSL expressions for the final selection and transformation. The platform applies the same expressions when training and when predicting.
  6. At request time the UberEATS services call the deployed model over the network. The model combines fields from the request with feature values fetched by key.

Why this approach fits

Skew comes from duplicated logic. Both paths here are built so that one computation produces one output, which is then delivered to two places: a store for training and a store for serving. Nobody re-implements a feature for the online service.

Canonical names turn "add this feature to my model" into a configuration change, and with roughly ten thousand features in the store, reuse across teams becomes the normal case. Putting the last transformations into the model configuration closes the remaining gap, because logic applied after the lookup is also a place where training and serving can diverge.

Limitation or tradeoff

Batch features loaded into Cassandra "on a regular basis" are only as fresh as the last load, so online values can lag behind what an offline training query would return for the same moment. The platform also has two storage systems to operate and keep in step.

A feature store makes features consistent. It does not by itself make training continuous. The article notes that many teams scripted regular retraining through the platform's API, while the UberEATS delivery-time models were still trained and deployed manually through the web UI.

What the sources document

  • Before Michelangelo there were no systems for building reliable, uniform and reproducible pipelines for creating and managing training and prediction data at scale, and no established path for deploying a model into production. [16]
  • One option for online features is to bulk precompute historical features and load them from HDFS into Cassandra on a regular basis; the article says this guarantees that the same data and batch pipeline is used for training and serving. [16]
  • For near-real-time features, metrics are published to Kafka and Samza streaming jobs generate aggregate features that are written to Cassandra for serving and logged back to HDFS for future training jobs; a backfill tool generates training data from historical logs to avoid a cold start. [16]
  • The Feature Store held approximately 10,000 features at the time of writing, its features are automatically calculated and updated daily, and they are consumed online and offline by referencing a canonical name in the model configuration. DSL expressions in that configuration are applied at training time and at prediction time. [16]
  • UberEATS uses gradient boosted decision tree regression models to predict delivery time from request information, historical features and near-real-time features. Many teams had automation scripts for regular retraining and deployment through Michelangelo's API, while training and deployment of the UberEATS delivery-time models were triggered manually through the web UI. [16]

Example 2 of 5

Spotify: replacing ad hoc ML workflows with a shared Kubeflow Pipelines platform

SpotifyDocumented in an engineering article

A December 2019 Spotify Engineering post by Josh Baer and Samuel Ngahane recounts three iterations of Spotify's ML infrastructure, ending with a platform built on TensorFlow Extended (TFX) components and Kubeflow Pipelines that the company offers to its ML teams. [17][8][9]

The problem

The post says Spotify's engineers were spending more of their time maintaining data and backend systems in support of the ML code than iterating on the model. A first set of in-house Scala libraries did not spread, because some ML engineers would never add Scala to a Python workflow. The company's orchestration framework, Luigi, had been built for data pipelines and struggled with the constraints of ML workflows. Nothing tied the separate tools into one end-to-end experience, and keeping track of experiments and comparing their results was still manual.

Where this topic fits

Kubeflow Pipelines is the orchestration layer. Beneath it sit a common data format and TFX components for the individual steps, including TensorFlow Data Validation. Above it sits a thin Spotify layer, a Python SDK and a command-line tool, that hides cluster and container details from ML teams.

How it is applied, step by step

  1. Agree on the interface between steps first. Spotify standardised the storage format exchanged between workflow steps, so that a step written by one team can feed a step written by another.
  2. Adopt a validation component. TensorFlow Data Validation let engineers understand their data during development and detect skew, erroneous values and too many nulls in production pipelines.
  3. Put an ML orchestrator on top. With Kubeflow Pipelines each stage runs as a component, and every iteration is recorded in a metadata store and shown in a web UI without extra work by the user.
  4. Run the infrastructure centrally. A platform team deploys and operates the Kubeflow clusters, so product teams do not manage Kubernetes themselves.
  5. Wrap it in familiar tools. A Python SDK and a CLI start runs and take care of building container images, and components can be created once and shared between teams.
  6. Avoid repeated work. Spotify added caching to its Kubeflow Pipelines setup so that steps whose results already exist are not executed again.

Why this approach fits

With many teams the expensive part is the glue between steps, and it was being rebuilt by every team. A fixed interface between steps plus an orchestrator that records every run removes that repeated work. Kubeflow Pipelines suited the gap the post describes because it supplied the missing orchestration and the automatic tracking in one product, and because its SDK lets teams share components.

Offering it as a "paved road", an opinionated default with managed clusters, means a team starting an ML project gets validation, orchestration and tracking by following the standard path.

Limitation or tradeoff

Example 3 of 5

Google TFX: schema validation that catches bad batches and training-serving skew

GoogleDocumented in a paper

"Data Validation for Machine Learning" by Breck, Polyzotis, Roy, Whang and Zinkevich, published at the 2019 SysML conference, describes the data validation system deployed in TFX, Google's end-to-end ML platform, and reports results from production pipelines, including the Google Play app recommender. [18][11]

The problem

The paper starts from the observation that ML pipelines keep running when their input goes wrong: a feature silently disappears, a backend starts emitting a default value, or training and serving data are produced by different code paths and drift apart. Nothing crashes, and the model simply gets worse. Its predictions are often logged and used as later training data, so the damage can compound. The pipelines in question run continuously, with a new batch of data arriving periodically and triggering a new run, so the checks have to be automatic and their alerts have to be specific enough for an on-call engineer to act on.

Where this topic fits

Validation is the stage between ingestion and training. The paper's pipeline ingests a batch of training data, passes it to data validation, then to the training algorithm, and finally pushes the model to serving. The same system also receives a logged sample of serving data, which it compares with the training data to detect skew.

How it is applied, step by step

  1. A data analyser computes statistics over each incoming batch. By default the whole batch is used, not a sample, so that rare anomalies in small slices are not missed.
  2. An initial schema is inferred automatically. Engineers review it, edit it with their domain knowledge, and commit it to version control before training starts.
  3. A validator compares every batch with the schema. A disagreement raises an alert for the on-call engineer, together with a suggested schema edit for cases where the data has legitimately evolved.
  4. The owner then chooses one of two responses: fix the code that generates the data, or accept the change by updating the schema, which is versioned like source code.
  5. To find training-serving skew, the serving system logs a sample of what it received. The validator joins those rows to the corresponding training rows by key and compares feature values one by one.
  6. For distributions, the validator computes the largest change in probability of any single value between two batches and alerts when it exceeds a threshold stored in the schema.
  7. Separately, synthetic examples generated from the schema are run through the training code as a unit test, which exposes assumptions in the code that the schema does not state.

Why this approach fits

The failures in question are silent, so only a check that runs on every batch will find them, and it must run before training so that no compute is spent and no bad model is produced. A schema is a good vehicle for the check because it turns tacit knowledge ("age is in years", "country codes are upper case") into something a machine can compare against and a reviewer can read.

The choice of distance measure is practical. The paper explains that statistical tests fire on harmless differences when batches contain many millions of rows, whereas "no value's share may move by more than 1 %" is a rule a product team can understand, tune, and trace back to a culprit value.

Limitation or tradeoff

A person still has to respond. In the paper's own analysis some anomalies were never fixed, and the authors warn that noisy alerts raise the cognitive load on on-call engineers and may lead them to switch validation off. An inferred schema that is too tight produces exactly that noise.

The schema cannot express every property of the data, and the paper names one kind of skew, where only some scored items are ever shown and labelled, as harder to detect than the others. Thresholds for distribution checks also need tuning for each feature.

What the sources document

  • The data validation system is deployed in production as an integral part of TFX and, according to the paper, is used by hundreds of product teams to continuously monitor and validate several petabytes of production data per day. [18]
  • In the workflow the paper analyses across a sample of more than 700 pipelines, users obtain an initial schema through automatic inference, review and manually edit it, and commit it to a version control system; when an alert fires they either fix the data generation process or update the schema. [18]
  • The paper attributes training-serving skew mostly to different code paths for generating training and serving data. The serving infrastructure logs a sample of serving data that is imported back into the training pipeline, and feature skew is detected with a key-join between training and serving batches followed by a feature-wise comparison. [18]
  • To compare distributions the system uses the maximum absolute difference between the probabilities of any single value, chosen because teams can interpret it and set a threshold such as 1 %; in the paper's experiment a chi-square test fired on 7 of 10 trials when 0.01 % of 100 million points were replaced. [18]
  • Using the system, Google Play found a few features that were always missing from the serving logs but always present in training, and an online A/B experiment showed that removing this skew improved the app install rate on the store's main landing page by 2 %. A video recommendation team diagnosed and fixed silently dropped features in two days, where similar issues had taken months. [18]

Facebook ads click prediction: measuring staleness to set the retraining cadence

FacebookDocumented in a paper

"Practical Lessons from Predicting Clicks on Ads at Facebook" (He and colleagues, ADKDD 2014) describes Facebook's click-prediction model, boosted decision trees whose outputs feed a logistic regression, and reports experiments on how the freshness of training data affects accuracy. [19]

The problem

Click prediction runs in an environment where the data distribution changes over time, so a model loses accuracy as it ages. Retraining is not free: the paper notes that building a boosted-tree model with hundreds of trees from hundreds of millions of examples can take more than 24 hours on a single core, and a few hours with enough parallelism and memory. The team needed to know how often retraining was worth it, and how to keep the model fresh between expensive retrains.

Where this topic fits

This is the trigger and cadence decision of continuous training. It comes after a pipeline exists and before anyone fixes its schedule. The paper also describes the data path that makes a fast cadence possible, a stream that joins ad impressions to clicks to produce labelled training examples, and the safeguard that protects that loop from bad data.

How it is applied, step by step

  1. Measure staleness directly. Train a model on one day of data, then evaluate it on each of the six following days and record the loss (normalised entropy, where lower is better) for each day.
  2. Read the curve. Accuracy fell as the gap between training and test data grew, and moving from weekly to daily training was worth about 1 % of normalised entropy, so the team concluded that retraining at least daily pays off.
  3. Split the model by training cost. The boosted trees, which are expensive, are retrained daily or every couple of days in batch. The linear classifier on top is cheap and can be updated in near real time with online learning.
  4. Build the labelled stream. An "online joiner" matches each ad impression with a later click by request ID. An impression that receives no click within a fixed waiting window is emitted as a negative example.
  5. Tune the waiting window. A long window delays training data and uses memory; a short one drops late clicks, which biases the measured click rate downwards.
  6. Guard the loop. If the click stream goes stale, the joined data shows almost no clicks and an online learner would follow it, so the paper suggests anomaly detection that disconnects the trainer when the training data distribution changes abruptly.

Why this approach fits

The cadence was set by measurement. Evaluating one model on each later day shows how quickly it goes stale, and that curve can be weighed against the cost of a retrain. The same experiment is cheap to repeat on any dataset with timestamps, which is why the worked example in this lesson copies its design.

Splitting the model follows from the same reasoning. The slow, expensive part is refreshed on a schedule and the cheap part continuously, so most of the freshness gain arrives without paying for a full retrain every few minutes. The guard is data validation applied to a stream: a rule that stops training when its input no longer looks plausible.

Limitation or tradeoff

The 1 % figure belongs to this system and this metric. Other problems go stale faster or slower, and the paper itself reports that models relying on contextual features depend more on freshness than models relying on long-term historical features.

Faster loops also fail faster. A labelling rule based on a waiting window always mislabels some late clicks, and a bad input reaches an online learner within minutes, which is why the guard is not optional. The paper presents the online joiner as an experimental system and describes the disconnect rule as an example of what anomaly detection can do, not as a measured safeguard.

What the sources document

  • In the data freshness experiment a model was trained on one day of data and evaluated on the six consecutive days; prediction accuracy degraded for both model types as the delay grew, and the authors state that normalised entropy can be reduced by approximately 1 % by going from weekly to daily training, concluding that it is worth retraining on a daily basis. [19]
  • The paper states that the boosted decision trees can be trained daily or every couple of days while the linear classifier can be trained in near real time using online learning, and that building a boosting model with hundreds of trees from hundreds of millions of instances may take more than 24 hours on a single core but a few hours with sufficient concurrency. [19]
  • The online joiner is introduced as an experimental system that joins click labels to ad impressions using a request ID, treats an impression as a negative example if no click arrives within a fixed waiting window, and has to balance recency against click coverage. [19]
  • The paper warns that a stale click stream would make the joiner produce training data with a very small or zero empirical click-through rate, and gives as an example of protection automatically disconnecting the online trainer from the online joiner if the real-time training data distribution changes abruptly. [19]
  • In a comparison of feature types, the model with contextual features relied more heavily on data freshness than the model with historical features, which the authors explain by historical features describing long-term accumulated user behaviour. [19]

4Common mistakes

  1. Retraining on a schedule and deploying the result without comparing it with the current model.

    Why it causes problems
    A new model is not automatically a better one. A small or unusual batch, a label problem or plain noise can produce a weaker model, and an ungated pipeline ships it to every user on the next run.
    How to recognise it
    The pipeline has no step that loads the production model, or the comparison exists but its result is only logged. Production metrics move up and down in step with the retraining schedule.
    How to fix it
    Evaluate candidate and champion on the same held-out data and promote only when the candidate wins by a stated margin, overall and on the slices you care about. Otherwise keep the champion and record why.

  2. Writing feature logic twice, once in the training notebook and once in the serving code.

    Why it causes problems
    The two versions drift apart on details such as rounding, time zones, default values and category spellings. Offline metrics stay good while live predictions degrade, and nothing raises an error.
    How to recognise it
    Log the feature vector the service used for a sample of requests, recompute the same features with the training code, and compare them value by value. Any systematic difference is skew.
    How to fix it
    Keep one implementation: a shared function or package imported by both sides, a feature store, or training directly on the features logged at serving time.

  3. Joining the latest feature values onto historical labels when building the training set.

    Why it causes problems
    Aggregates such as a seven-day average then include events that happened after the label's timestamp. The model is trained on information it will not have at request time and its offline score is inflated.
    How to recognise it
    Offline accuracy is clearly better than live accuracy from the first day. In the training table, a feature's computed-at timestamp is later than the event timestamp of the row it is attached to.
    How to fix it
    Store features with the time they were computed and join as of each event's timestamp, with a TTL. Add a test that fails if any joined feature is newer than its row's event time.

  4. Accepting an inferred schema unreviewed, then silencing the alerts it produces.

    Why it causes problems
    An inferred schema encodes whatever the first batch happened to contain. Too tight and it alerts on every new postcode; too loose and it lets a column of nulls through. Teams that are flooded with alerts turn validation off, which removes the protection entirely.
    How to recognise it
    The schema file has never been edited by a person, validation failures are marked as allowed to fail, or the same anomaly has fired every day for weeks.
    How to fix it
    Review the inferred schema with someone who knows the data, keep it in version control, and treat each alert as a decision between fixing the data and updating the schema through review.

  5. Passing datasets between orchestrator tasks, or writing tasks that cannot be rerun safely.

    Why it causes problems
    Task-to-task messaging is meant for small values, so large payloads slow down or break the orchestrator. A task that appends on every run duplicates rows whenever it is retried.
    How to recognise it
    Tasks return data frames or long lists. Row counts in an output table grow after a retry, or a rerun of last month's run produces a different dataset.
    How to fix it
    Have each task write to storage at a path derived from the run date, overwrite that path on rerun, and return only the path or the model URI to the next task.

Hint 1

For one order, first filter the feature rows to the same courier, then to rows with computed_at no later than ordered_at.

Hint 2

python
def latest_join(orders, features):
    """The leaky version: attach each courier's most recent value, whatever its date."""
    latest = {}
    for courier, computed_at, value in sorted(features, key=lambda f: f[1]):
        latest[courier] = value
    return {order_id: latest.get(courier) for order_id, courier, _, _ in orders}

def point_in_time_join(orders, features, ttl):
    """Attach the newest value computed at or before the order time and no older than ttl."""
    joined = {}
    for order_id, courier, ordered_at, _ in orders:
        candidates = [
            (computed_at, value)
            for f_courier, computed_at, value in features
            if f_courier == courier and ordered_at - ttl <= computed_at <= ordered_at
        ]
        joined[order_id] = max(candidates)[1] if candidates else None
    return joined

leaky = latest_join(ORDERS, FEATURES)
correct = point_in_time_join(ORDERS, FEATURES, ttl=timedelta(days=1))
no_ttl = point_in_time_join(ORDERS, FEATURES, ttl=timedelta(days=3650))

print("order  latest  as-of(ttl=1d)  as-of(no ttl)")
for order_id, *_ in ORDERS:
    print(f"{order_id:5}  {leaky[order_id]!s:6}  {correct[order_id]!s:13}  {no_ttl[order_id]!s}")

wrong = [o for o in leaky if leaky[o] != correct[o]]
print("rows where the latest-value join differs:", wrong)

The serving side must guarantee the mirror image, namely that a request at time t reads the newest value computed at or before t and never a value older than the TTL used in training.

Here the data has legitimately evolved, so the schema is updated through review and the encoding is changed to handle unseen categories. Had it been a typo upstream, the fix would belong in the export.

3. Trigger and label delay. Use a weekly schedule on Monday at 03:00 UTC, one hour after the export. If the export itself ran in Airflow, scheduling on its asset would be tighter. The 30-day delay means the newest row usable for training or evaluation is a month old. The evaluation set is therefore the newest labelled month, held out from training, and retraining more often than weekly would add almost no new labelled rows. To cover the blind month, monitor the inputs of recent, unlabelled customers, for example the share of each plan value with an L-infinity threshold.

4. The Dag. Written against the Airflow 3 TaskFlow API:

python
import pendulum
from airflow.sdk import dag, task


@dag(
    schedule="0 3 * * 1",                    # Mondays 03:00 UTC, after the 02:00 export
    start_date=pendulum.datetime(2026, 1, 5, tz="UTC"),
    catchup=False,
    default_args={"retries": 2},
)
def churn_retraining():
    @task()
    def extract_labelled_snapshot() -> str:
        """Write customers whose 30-day outcome is known to a dated path; return the path."""
        return "s3://ml/churn/snapshots/latest.parquet"

    @task(retries=0)                         # bad data is not fixed by retrying
    def validate(snapshot: str) -> str:
        """Compare columns, types, ranges and plan values with the schema file."""
        problems: list[str] = []             # filled by the real checks
        if problems:
            raise ValueError(f"schema violations: {problems}")
        return snapshot

    @task()
    def train(snapshot: str) -> str:
        """Train on all but the newest labelled month; return the candidate's URI."""
        return "models:/churn/candidate"

    @task.short_circuit()
    def beats_champion(candidate: str) -> bool:
        """Score both models on the newest labelled month, overall and per plan."""
        candidate_auc, champion_auc = 0.84, 0.82     # computed by the real evaluation
        return candidate_auc >= champion_auc + 0.005

    @task()
    def promote(candidate: str) -> None:
        """Move the registry alias 'champion' to the candidate version."""

    snapshot = validate(extract_labelled_snapshot())
    candidate = train(snapshot)
    beats_champion(candidate) >> promote(candidate)


churn_retraining()

If validate raises, the task fails, train never starts and the champion keeps serving. If beats_champion returns False, promote is skipped and the run still finishes without an error, which is correct: keeping a good model is a normal outcome.

5. Not automated yet. Keep a human approval between beats_champion and the alias change for the first months, and automate it once the gate has repeatedly made the decision a reviewer would have made. Schema changes should always stay behind review.

Check your answer

  • Did you identify level 0 from what is deployed (a file) and how training is started (by hand)?
  • Would your validation task have failed on the first batch that contained the plan value student?
  • Is your evaluation set the newest month with known labels, and is it excluded from training?
  • In your Dag, does train take the output of validate, so that a validation failure prevents training?
  • Does a candidate that fails the comparison end the run as skipped instead of failed?
