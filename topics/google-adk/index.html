Google Agent Development Kit (ADK)

Google's Agent Development Kit (ADK) is an open-source framework in which AI agents and multi-agent systems are written as ordinary code, then tested and deployed from the same project. It supplies agent and workflow classes, tool support, sessions and state, callbacks, an evaluation harness and deployment tooling, and it works with Gemini and with other models.

1Overview

Why it matters

Moving an agent from a notebook to something a team can run means answering questions that a single model call never raises. Where does conversation state live? How do you test a system whose output varies? How do you make sure review always runs after drafting? What happens to a conversation when the process restarts? ADK packages answers to these as one framework, so the code that defines the agent is also the code you test, trace and deploy.

Two things make it worth learning carefully now. First, its orchestration model changed in ADK 2.0: the SequentialAgent, ParallelAgent and LoopAgent classes that many tutorials use are now superseded by graph workflows. The Python and Go docs say so, and TypeScript logs a deprecation warning, though the classes still run. Second, Google's launch post (opens in a new tab) says ADK is built on the same framework that powers its Agentspace and Customer Engagement Suite agents, and customers such as Revionics, Color Health and PayPal describe using it, so you are likely to meet it on teams that build on Google Cloud. Anyone choosing a framework, reviewing how an agent stores state, or debugging a pipeline that ran in the wrong order needs the concepts in this lesson.

Key terms

Agent
The ADK unit that combines a model, an instruction and optional tools. The model decides at each turn whether to answer or to call a tool. The documentation uses the names `Agent` and `LlmAgent` for it.
Runner
The component that receives a user message, asks the agent to run, and commits each event the agent yields to the session before letting the agent continue.
Event
The unit of history in ADK. An event carries content such as text, a function call or a function response, and actions such as a change to session state.
Session
One ongoing conversation between a user and an agent application, holding its events and its state.
State
Key-value data stored with a session that agents, tools and instructions can read and write. A key prefix sets whether it belongs to the session, the user, the whole app, or just the current invocation.
Memory
A searchable store of information that can span many past sessions, reached through a memory service rather than through session state.
Workflow
ADK's word for any application with more than one agent or executable node. It can be template-based, graph-based, dynamic or collaborative.
Node
In ADK 2.0, an executable unit of a workflow graph: a plain Python function, an agent, a tool, a human-input step or a nested workflow.
Callback
A function attached to an agent that runs before or after an agent, model or tool step and can replace that step's result by returning a value.
Evaluation set
A JSON file of test conversations with expected tool calls and reference answers, used together with a config file that sets score thresholds.

2Explanation

Introduction

In Choosing an Agent Framework you compared what frameworks offer. This lesson takes one of them apart. Google's Agent Development Kit (ADK) is a framework for writing agents as ordinary code, with the surrounding machinery supplied: a command that runs the agent, a development UI, stored conversations, a test harness and a route to deployment. The ADK documentation (opens in a new tab) describes it as open source and available for Python, TypeScript, Go, Java and Kotlin. The examples here are Python.

The loop from The Agent Loop is a good starting comparison. There you wrote the loop yourself: call the model, run the tool it asks for, append the result, repeat. In ADK the Agent object holds the model, the instruction and the tools, while a separate Runner drives the loop and keeps the books. It records each step as an event in a session, applies state changes, and streams events back to your application. Tool Calling is the mechanism underneath: ADK builds the tool declarations from your Python function's name, signature and docstring.

A second question is who decides what runs next. In open-ended work the model decides. In work with a known shape, such as draft, review, publish, you would rather decide in code. ADK supports both and lets you combine them. Since ADK 2.0 (opens in a new tab) the main way to write the code-decided part is a graph workflow: nodes (plain functions or agents) joined by edges, with routes for branching. The older template classes still exist, but many tutorials written for ADK 1.x teach only them.

Version note. This lesson follows the ADK 2.0 documentation, which says ADK Python 2.0 became generally available on 19 May 2026 and that ADK 2.0 is available for Python, TypeScript and Go. When the lesson was reviewed on 11 October 2026, the google-adk package on PyPI (opens in a new tab) listed 2.11.0 as the latest release (uploaded on 2 October 2026), and it needs Python 3.10 or newer. The documentation moved from google.github.io/adk-docs to adk.dev, and the old address redirects.

The lesson covers agents and tools, the runner and its events, the four workflow styles, sessions, state and memory, callbacks, evaluation and deployment. It then follows one request and one test case through a small agent, and ends with five documented uses.

How it works

An agent is a model, an instruction and tools

An LLM agent is defined by a name, a model and an instruction, plus optional tools. The LLM agent page (opens in a new tab) says the model uses the tool names, descriptions and parameter schemas to decide which tool to call. Useful optional settings are description (recommended in multi-agent systems), output_key (store the final reply in session state), output_schema (force JSON output), include_contents (whether the agent sees earlier conversation), generate_content_config, planner and code_executor.

A Python function becomes a tool when you list it in tools. ADK reads its name, docstring, type hints and defaults: a parameter without a default is required, and the function tools page (opens in a new tab) stresses a thorough docstring because it is the description the model sees. Return a dict that includes a status key. A parameter typed ToolContext is supplied by ADK and hidden from the model; it is how a tool reads and writes session state.

The Runner and the event loop

The runtime event loop (opens in a new tab) is a hand-off between the Runner and your agent code. The Runner appends the user's message to the session through the SessionService and asks the agent to run. The agent runs until it has something to report, yields an Event and pauses. The Runner commits the event, applying its state_delta through append_event(), forwards it to your app, then lets the agent resume. Code after a yield can therefore rely on the state change being stored. Partial streaming events are shown but not committed. Three services sit behind the Runner: SessionService for events and state, an optional MemoryService for long-term search, and ArtifactService for binary data.

Four ways to decide what runs next

The workflows overview (opens in a new tab) names four styles, set out in the table below.

Template workflows run sub-agents in a fixed pattern with no model involved in the ordering. Agents hand data over through state: an agent with output_key="draft" stores its reply under draft, and the next agent's instruction can use {draft}, filled from state.

python
from google.adk.agents import LlmAgent, SequentialAgent

writer = LlmAgent(name="writer", model="gemini-flash-latest", output_key="draft",
                  instruction="Write a two-sentence blurb for: {topic}")
reviewer = LlmAgent(name="reviewer", model="gemini-flash-latest", output_key="review",
                    instruction="List two weaknesses of this blurb:\n{draft}")
pipeline = SequentialAgent(name="pipeline", sub_agents=[writer, reviewer])

These classes are the older style: the Python and Go docs say ADK 2.0 supersedes them with graph and dynamic workflows, and the ADK 2.0 page (opens in a new tab) says TypeScript logs a deprecation warning. They still run.

Two documented details trip people up. A ParallelAgent (opens in a new tab) runs its sub-agents concurrently with no shared history or state between branches, so give each its own output_key and merge later. A LoopAgent (opens in a new tab) stops at max_iterations, or earlier when a tool sets tool_context.actions.escalate = True.

Graph workflows use Workflow(name=..., edges=[...]). Each edge is a tuple of connected nodes and "START" is the entry. A node is a Python function, which runs no model, or an agent. As the data handling page (opens in a new tab) explains, a node's output becomes the next node's input. To branch, a node returns Event(output=..., route="X") and a later edge (node, {"X": next_node}) maps routes to targets. The routes page (opens in a new tab) also shows loops made by routing back to an earlier node (a back-edge), a DEFAULT_ROUTE fallback, and fan-out from several START edges to a JoinNode.

python
from google.adk import Event, Workflow

def write(node_input: str):                  # START passes the user's request
    return f"draft v1 for: {node_input}"

def review(node_input: str):                 # deterministic check, no model call
    return Event(output=node_input, route="DONE" if len(node_input) > 50 else "REVISE")

def revise(node_input: str):
    return node_input + " (revised)"

def publish(node_input: str):
    return f"Published: {node_input}"

root_agent = Workflow(name="draft_loop", edges=[
    ("START", write, review),
    (review, {"REVISE": revise, "DONE": publish}),
    (revise, review),                        # back-edge: loop until DONE
])

For the request "Announce our new bike lights" (28 characters), write returns a 42-character draft, review routes to REVISE, revise makes it 52 characters, and the second review routes to DONE. This snippet follows the documented patterns but was not run against ADK. The routes page warns that graph cycles are not bounded automatically and this loop has no cap, so in real code count attempts in state with Event(state={"attempts": n + 1}) and route to DONE at your limit.

Dynamic workflows write the flow as ordinary Python, so branches and loops are plain control flow. Collaborative workflows give a coordinator Agent a list of sub_agents and let that agent, a model, delegate tasks to them as it works.

Sessions, state and memory

A session is one conversation: its events and its state, tied to an app_name and a user_id. State (opens in a new tab) is key-value data in the session, and the key prefix sets its scope.

PrefixScopeSurvives a restart?
nonethis sessiononly with a persistent session service (database or Vertex AI)
user:every session of one usersame condition
app:every user of the appsame condition
temp:this invocation onlynever persisted

Update state with output_key, with ToolContext.state or CallbackContext.state, or with an event whose EventActions carries a state_delta. Do not edit a session.state object you fetched from the service: that bypasses the event history. Memory (opens in a new tab) is a separate store of searchable knowledge that can span sessions. The docs list InMemoryMemoryService (keyword matching, lost on restart), VertexAiMemoryBankService (managed, semantic search over memories extracted from conversations) and VertexAiRagMemoryService (vector similarity over transcripts). An agent reads memory through the load_memory tool, when it chooses to, or preload_memory, which retrieves at the start of each turn. See Agent Memory for the general design.

Callbacks

The callback types page (opens in a new tab) lists before and after hooks for the agent, the model call and the tool call, plus error hooks for model and tool failures in Python. One rule covers them: return None and the step proceeds; return a value of the right type and it replaces the step. A before_model_callback that returns an LlmResponse skips the model call, and a before_tool_callback that returns a dict skips the tool and uses the dict as its result.

python
import re
from google.adk.agents import LlmAgent
from google.adk.models import LlmResponse
from google.genai import types

def block_card_numbers(callback_context, llm_request):
    last = llm_request.contents[-1] if llm_request.contents else None
    text = (last.parts[0].text or "") if last and last.role == "user" and last.parts else ""
    if re.search(r"\b\d{13,16}\b", text):     # sketch: unbroken digit runs only
        return LlmResponse(content=types.Content(
            role="model", parts=[types.Part(text="I can't process card numbers.")]))
    return None                              # None: let the model call proceed

agent = LlmAgent(name="support", model="gemini-flash-latest", instruction="Help with orders.",
                 before_model_callback=block_card_numbers)

Evaluation

ADK's evaluation guide (opens in a new tab) checks two things: the trajectory (which tools were called, in what order, with what arguments) and the final response. A .test.json file holds single-session cases; an evalset holds multi-session ones. A test_config.json in the same folder sets the criteria.

  • tool_trajectory_avg_score has a default threshold of 1.0. Per ADK's source (opens in a new tab), it gives each invocation 1.0 or 0.0 and averages them, with match types EXACT, IN_ORDER and ANY_ORDER.
  • response_match_score has a default threshold of 0.8 and is a ROUGE-1 F-measure against a reference.
  • LLM-judged criteria such as final_response_match_v2, and rubric-based checks, cover meaning.

Run them with adk eval, with pytest through AgentEvaluator.evaluate, or in the adk web UI.

Running and deploying

adk create scaffolds a project, adk run chats in the terminal, and adk web opens the development UI, which the quickstart (opens in a new tab) says is not for production. adk api_server exposes a REST API (opens in a new tab) on port 8000 by default, with /run and /run_sse. The deployment page (opens in a new tab) lists Agent Runtime on Agent Platform (managed), Cloud Run, GKE, and any other container host. adk deploy cloud_run (opens in a new tab) takes --session_service_uri and --artifact_service_uri; without them the deployment uses in-memory storage and loses data when instances are recycled. Gemini Enterprise Agent Platform covers Agent Runtime.

Worked example: One request through a weather agent, then a scored test case

This example follows one request through a small weather agent and then scores a test case for it by hand. The tool function and the scoring script are plain Python that you can run now with no API key. The ADK parts follow the documentation and were not run here, so read their output as the documented shape, not a recording.

1. The agent

python
# weather_agent/agent.py
from google.adk import Agent

def get_weather(city: str) -> dict:
    """Returns the current weather for a city.

    Args:
        city: City name in lower case, for example "new york".
    """
    reports = {"new york": "sunny, 25 degrees Celsius (77 degrees Fahrenheit)"}
    key = city.strip().lower()
    if key in reports:
        return {"status": "success", "report": f"The weather in {city} is {reports[key]}."}
    return {"status": "error", "error_message": f"No weather data for '{city}'."}

root_agent = Agent(
    name="weather_agent",
    model="gemini-flash-latest",
    description="Answers questions about the weather in a city.",
    instruction="Use get_weather to answer weather questions. If it returns an error, say so plainly.",
    tools=[get_weather],
)

Per the quickstart (opens in a new tab), adk create weather_agent scaffolds agent.py, .env and __init__.py, the key goes in .env as GOOGLE_API_KEY, and agent.py must define root_agent. Calling get_weather("new york") directly returns {'status': 'success', 'report': 'The weather in new york is sunny, 25 degrees Celsius (77 degrees Fahrenheit).'}, and 25×9/5+32=7725 \times 9/5 + 32 = 7725×9/5+32=77. An unknown city returns {'status': 'error', 'error_message': "No weather data for 'Atlantis'."}.

2. One request, three events

From the folder that contains weather_agent/, start adk api_server, create a session, then post a message to /run. The request format is the one on the API server page (opens in a new tab).

bash
curl -X POST http://localhost:8000/apps/weather_agent/users/u_123/sessions/s_123 \
  -H "Content-Type: application/json" -d '{}'
curl -X POST http://localhost:8000/run -H "Content-Type: application/json" -d '{
  "appName": "weather_agent", "userId": "u_123", "sessionId": "s_123",
  "newMessage": {"role": "user", "parts": [{"text": "What is the weather in new york?"}]}}'

The response is a list of events. Using the event shapes on that page with this tool's values, a typical run has three:

#RoleContentstateDelta
1modelfunctionCall: get_weather with {"city": "new york"}{}
2userfunctionResponse: the success dict from step 1{}
3modeltext built from the report; the wording varies{}

The Runner commits each event as it arrives. None changes state, so every stateDelta is empty; with output_key="answer" set, event 3 would also store the reply under answer. The model never runs the tool. Your code runs it between events 1 and 2, and event 2 is what lets the model write event 3.

4. Scoring three runs by hand

The three runs below are invented to show the arithmetic; real runs vary. The trajectory score for one invocation is 1.0 if the actual tool calls equal the expected ones and 0.0 otherwise. EXACT needs the same number of calls, in order, with argument dicts that compare equal. The response score is the ROUGE-1 F-measure over word counts, where the overlap sums the smaller count of each word:

F1=2⋅overlap∣reference∣+∣candidate∣F_1 = \frac{2 \cdot \text{overlap}}{|\text{reference}| + |\text{candidate}|}F1​=∣reference∣+∣candidate∣2⋅overlap​

This sketch lowercases and splits on non-alphanumeric characters. ADK's own response-match code (opens in a new tab) also applies stemming, which leaves the counts unchanged for these sentences.

python
import re
from collections import Counter

def words(text): return re.findall(r"[a-z0-9]+", text.lower())

def rouge1_f(reference, candidate):
    ref, cand = Counter(words(reference)), Counter(words(candidate))
    overlap = sum(min(ref[w], cand[w]) for w in ref)
    return 2 * overlap / (sum(ref.values()) + sum(cand.values()))

ref = "The weather in New York is sunny and 25 degrees Celsius."
print(round(rouge1_f(ref, "The weather in new york is sunny, 25 degrees Celsius (77 degrees Fahrenheit)."), 3))  # 0.833
print(round(rouge1_f(ref, "It is probably sunny and warm in New York today."), 3))                              # 0.571
print(round(rouge1_f(ref, "The weather in New York is not sunny and 25 degrees Celsius."), 3))                  # 0.957

2get_weather("New York")0.010 / 11, 130.833fails trajectory
3none0.06 / 11, 100.571fails both

What the numbers say:

  • Run 2 gives a correct answer and still fails, because the evaluator compares argument dicts with ==, and "New York" is not "new york". State the casing rule in the docstring, as the tool above does, or accept that exact matching is strict.
  • Run 1 passes at 0.833 although it adds "(77 degrees Fahrenheit)", because extra words only lower precision.
  • The third print shows the weakness of response matching. An answer that says the opposite ("not sunny") scores 0.957 and passes the 0.8 threshold. Add an LLM-judged or rubric criterion when meaning matters.
  • A case with several invocations averages their scores. One passing turn and one failing turn give (1.0 + 0.0) / 2 = 0.5, which fails a threshold of 1.0.

Edge cases and limitations

Parallel branches do not see each other
A ParallelAgent starts its sub-agents concurrently and, according to its documentation page, shares no conversation history or state between branches while they run. Results are gathered afterwards and their order may not be deterministic. Give every branch a distinct output_key, merge in a later agent that reads all the keys, and never write a prompt that assumes one branch can see another branch's partial work.
ADK 2.0 changed the execution model under old code
In 2.0, BaseAgent extends BaseNode and agents run as nodes in a graph. The 2.0 page says custom overrides of methods such as _run_async_impl() are bypassed, that events must be yielded rather than appended with context.session.events.append(), and that broad try/except blocks hide failures from the framework's retry and human-pause handling. Code written for 1.x can start without an error and still behave differently, so read that page before upgrading and let exceptions propagate unless you can truly handle them.
Most state disappears unless you choose a persistent service
InMemorySessionService, and a Cloud Run deployment made without session and artifact URIs, lose everything when the process restarts or an instance is recycled. Even with a database, keys prefixed temp: are never persisted, so do not put anything there that a later turn needs. A local SQLite file belongs to one instance, so a deployment with several instances needs a shared database or the managed Vertex AI session service.
Curly braces in an instruction are read as state placeholders
Instruction text such as {draft} is filled from session state, and according to the state page a missing key raises an error unless you write {draft?}. The pattern matches any valid Python identifier in single braces, so literal braces in a prompt, such as a template or a JSON sample, can be mistaken for placeholders. The state page says to supply an InstructionProvider function for an instruction that contains literal braces, because it bypasses state injection. When an agent fails or misbehaves right after you add braces to its prompt, check them before you rewrite the prompt.
Passing an evaluation does not mean the answer is right
Under EXACT matching, tool_trajectory_avg_score fails a correct run that differs only in argument casing, while response_match_score is a word-overlap measure that scored 0.957 for an answer contradicting the reference in this lesson's example. Treat both as cheap regression checks. For meaning, add the LLM-judged final_response_match_v2 or a rubric criterion, and read some passing and failing traces by hand at first.

When to use it, and when something simpler is enough

Use it when

  • You want the agent, its tools, its tests and its deployment to live in one code-first project, and your team writes Python, TypeScript, Go, Java or Kotlin.
  • You will run on Google Cloud (Cloud Run, GKE or Agent Runtime) or use Gemini, and want documented paths for sessions, memory, tracing and deployment there.
  • Part of the process has a fixed shape, such as draft, review, publish or fan-out and gather, and other parts need model judgement. Graph workflows let you mix both in one application.
  • Conversation state must survive restarts, or you need to run recorded test cases against the agent before every release.

Think twice when

  • One prompt with one or two tools solves the task. A plain tool-calling loop is smaller and easier to read than any framework.
  • Your team is committed to another framework's ecosystem and has no use for Google Cloud paths. Compare options first in the framework-choice lesson instead of adding a second framework.
  • You cannot absorb API churn. ADK 2.0 superseded its template workflow classes and changed the event schema and execution model, so pin versions and budget time for upgrades.

A simpler alternative. A hand-written loop around one model call and a few functions, as in The Agent Loop, is enough while there is a single agent, in-memory history and no formal testing. Move to ADK when you need persistent sessions, orchestration you can reason about, tracing or an evaluation harness, because those are the parts that cost the most to build yourself.

Key takeaways

  • An ADK agent is a model, an instruction and tools. The Runner drives it, stores each step as an event in a session, and commits state changes before the agent resumes.
  • Decide who picks the next step: the model, through an LLM agent or a coordinator with sub-agents, or your code, through a graph or dynamic workflow. In ADK 2.0 the Sequential, Parallel and Loop template agents are superseded by graph workflows.
  • Data moves between agents through output_key and {key} placeholders, or through return values in a graph. A key's prefix sets its scope, and state survives a restart only with a persistent session service such as the database or Vertex AI ones.
  • Callbacks return None to let a step run and a value to replace it, which makes them the place for guardrails, caching and argument checks.
  • Evaluation scores the tool trajectory and the final answer separately. Exact trajectory matching and ROUGE are strict about wording and blind to meaning, so add LLM-judged or rubric criteria where meaning matters.
  • Deploy with persistent session and artifact storage on Cloud Run, GKE or Agent Runtime. In-memory services and the development UI are for local work.

Example 1 of 5

Revionics building a multi-agent retail pricing system with ADK

RevionicsDocumented in a case study

Revionics builds pricing AI for retailers. Google Cloud's April 2025 post quotes a Revionics executive on using ADK to build a multi-agent pricing system, and Revionics's own general-availability announcement names the three agents and says its engineers used ADK. [21][22]

The problem

Retailers must set prices that stay competitive without eroding margin, and they need an estimate of what a price change will do before they make it. In the Google Cloud post, Revionics calls data central to its process and says ADK lets agents reason over big data through storage artifacts instead of relying only on the model's context.

Where this topic fits

ADK is the agent layer between the retailer's question and Revionics's existing pricing AI. According to the quoted description, it handles transfers between specialised agents (data retrieval) and tools (constraint application), and it lets agents reason over big data through storage artifacts instead of relying only on the model's context.

How it is applied, step by step

  1. A retailer works with the system through a natural-language conversation, which is how Revionics describes using it.
  2. The first agent surfaces competitive gaps, which Revionics lists as the first of its three agents' jobs; the 2025 quote describes the data side as specialised agents for data retrieval. A typical ADK implementation keeps large results in an artifact and puts only a short summary and a reference into the model's context.
  3. A second agent models the financial impact of closing those gaps, which Revionics lists as the second of its three agents' jobs.
  4. A third agent enforces the retailer's business rules and executes the price changes. The quoted description puts constraint application in a tool, which keeps exact rules out of free-text reasoning.
  5. ADK's transfer and planning logic decides when control passes between the agents and the tools.

Why this approach fits

Pricing mixes judgement (what to look at next, how to explain a result) with exact rules (margin floors, price ladders). Splitting the work across specialised agents and a rule-applying tool keeps the exact rules in code. Artifacts keep large data out of the prompt, where its size would otherwise be limited by the context window and would add cost to every call.

Limitation or tradeoff

The sources are one executive's quote in Google's post and Revionics's own announcement. Neither gives measurements of accuracy, speed or revenue effect, and neither shows code. A model that chooses when to transfer can transfer wrongly, and a system that executes price changes needs approvals and an audit trail around that step. Making the system available on Google Agentspace is stated as a plan, not as something delivered.

What the sources document

The problem

An agent that calls a model and several tools in a loop is hard to debug from logs alone. You need to see which agent ran, what each model call received, which tool was called with what arguments, and what the run cost. In a multi-agent system you also need to know which sub-agent did what.

Where this topic fits

The integration wraps the ADK application from outside. An OpenInference instrumentor for Google ADK hooks the runs and emits OpenTelemetry spans, and Langfuse receives them. According to the setup steps, you switch it on once at start-up instead of editing each agent definition.

How it is applied, step by step

  1. Install google-adk 2.x (Langfuse states Python 3.10 or newer), the Langfuse SDK and the OpenInference ADK instrumentation package.
  2. Set the Langfuse public key, secret key and base URL, and the Google API key, as environment variables.
  3. Create the Langfuse client and call the instrumentor once, before any agent runs.
  4. Run the agent as usual. Each run is captured as a trace, with nested spans for agents, model generations and tool calls.
  5. Pass user_id and session_id to the runner. Langfuse maps them to its user and session fields, so the runs of one conversation group together.
  6. Use the traces to debug, track token usage and cost, and build datasets for later evaluation.

Why this approach fits

Tracing is a cross-cutting concern that does not belong inside each agent. OpenTelemetry is a vendor-neutral export format, so the choice of backend is not written into the agent code, and the nested spans mirror the way ADK nests agents, model calls and tools.

Its page also warns that the synchronous runner.run() executes the agent on a background thread, so attributes set with propagate_attributes do not reach the ADK spans; use runner.run_async() for those. 4Common mistakes

  1. Reusing one output_key in parallel branches, or assuming branches can read each other's results.

    Why it causes problems
    Parallel sub-agents share no history or state while they run, and their results arrive in no guaranteed order. With one shared key, one branch's result can replace another's, and the merge step then summarises incomplete data without any error.
    How to recognise it
    The merged report mentions only some of the topics, and which ones change from run to run. Inspecting the stored state shows fewer keys than there are branches.
    How to fix it
    Give each branch its own output_key, then add a later agent whose instruction names every key. Treat result order as unspecified.

  2. Deploying with in-memory sessions or serving the development UI to users.

    Why it causes problems
    In-memory session and artifact services lose conversations when the process restarts or the platform recycles an instance, so users lose context without warning. The quickstart says the adk web interface is for development only.
    How to recognise it
    After a redeploy or a scale-down, a follow-up message in an existing conversation gets a fresh start or a session-not-found error. The deploy command has no --session_service_uri.
    How to fix it
    Set --session_service_uri and --artifact_service_uri to a database, the managed session service or Cloud Storage, leave out --with_ui, and test by restarting the service in the middle of a conversation.

  3. Writing a fixed process into the instruction ("first do X, then Y, then Z") instead of building a workflow.

    Why it causes problems
    The model may skip, repeat or reorder steps, and every turn spends tokens restating the procedure. Failures appear as occasional wrong behaviour that is hard to reproduce or test.
    How to recognise it
    Traces from identical requests show different tool orders, and trajectory evaluations pass on some runs and fail on others.
    How to fix it
    Move the fixed order into a graph or template workflow, with function nodes for deterministic steps. Keep the model only where judgement is needed.

  4. Giving an agent every tool an MCP server exposes.

    Why it causes problems
    The model can call destructive or costly actions, such as refunds or deletions, by mistake or because of a prompt injection hidden in data. A long tool list also adds tokens and makes tool choice less reliable.
    How to recognise it
    The traced tool list contains tools unrelated to the task, and logs show write calls on requests that only asked a question.
    How to fix it
    Expose only the tools the task needs, using the server's own tool option or the toolset's tool_filter. Add a before_tool_callback or tool confirmation for actions with side effects.

  5. Following a 1.x tutorial on 2.x, or wrapping node code in a broad try/except.

    Why it causes problems
    Superseded classes keep working for now, but the docs steer new work to graph workflows. Overrides of internals can be ignored by the new execution engine, and swallowed exceptions stop the framework from retrying or pausing for human input.
    How to recognise it
    Deprecation warnings may appear when template agents are created (the ADK 2.0 page documents this for TypeScript), custom _run_async_impl code seems to be skipped, and a failed tool call is never retried.
    How to fix it
    Check the documentation version, express flows as graph workflows, append no events by hand, and let exceptions propagate unless you can recover from them.

critic = ToyAgent("critic", "Review this draft: {draft}", "criticism",

                  else "Too short: add detail.")
refiner = ToyAgent("refiner", "Improve {draft} using {criticism}", "draft",

start = {"topic": "ADK"}

Requirements

  • run_sequential applies the agents in order and returns a new dict; the mapping passed in must not be modified.
  • run_loop repeats the agent list up to max_iterations times and checks should_exit(state) after every single agent, stopping at once when it is true.
  • run_loop returns the number of iterations used, counting the iteration in which the exit happened, or max_iterations if the loop was never satisfied.
  • Running an agent whose instruction needs a key that is not in state raises the KeyError that render already produces.

Expected behaviour

The demo prints exactly these three lines:

text

{'topic': 'ADK', 'draft': 'ADK agents use tools.'}

Hint 1

Because run_agent returns a new dict, run_sequential can simply rebind its state variable inside a for loop. Nothing needs to be mutated.

Hint 2

In run_loop, put the exit check inside the inner loop, right after run_agent, not after the whole list. That mirrors a tool that escalates in the middle of an iteration.

Hint 3

Use range(1, max_iterations + 1) so that the iteration number you return is 1-based.

Show solution
python
def run_sequential(agents: Sequence[ToyAgent], state: Mapping[str, str]) -> dict:
    for agent in agents:
        state = run_agent(agent, state)      # new dict each time; the input is never changed
    return dict(state)

def run_loop(agents, state, max_iterations, should_exit):
    """Return (final_state, iterations_used)."""
    for iteration in range(1, max_iterations + 1):
        for agent in agents:
            state = run_agent(agent, state)
            if should_exit(state):           # like escalate: stop immediately
                return dict(state), iteration
    return dict(state), max_iterations

With the given agents, the draft starts at 4 words. The critic needs at least 9 words to approve, and each refiner pass adds 2 words ("More detail."), so the word counts at the critic are 4, 6, 8 and then 10. The critic approves in iteration 4 and the exit check fires straight after it, so the refiner runs only in iterations 1 to 3. That is why the final draft contains "More detail." three times and used is 4.

We ran this code with Python 3.13 and it printed the three lines shown above. The never-approving critic with max_iterations=3 returned 3, and running the critic with no draft in state printed "state key 'draft' was not set before this agent ran".

How this maps to ADK: output_key is the output_key of an LLM agent, render is the {key} filling of instructions, the should_exit check plays the part of a tool that sets escalate, and max_iterations is the same guard LoopAgent has. Returning a fresh dict instead of editing the old one is the toy version of a state_delta that the Runner commits.

Exercise 2

Choose workflow styles and evaluation criteria for a support-ticket assistant

DesignIntermediateAbout 40 min (estimate)Hypothetical scenario

A support team wants an assistant for incoming tickets. For each ticket it must do the following.

  1. Classify the ticket as billing or other.
  2. For a billing ticket, look up the customer's invoices with a tool and draft a reply.
  3. Check the draft against a refund policy with a deterministic rule. Any refund above 100 needs human approval.
  4. If the check finds a fixable problem, revise the draft, at most twice.
  5. Send the reply, after approval where the policy requires it.

Write a one-page design that answers five questions.

  • a. For each step, who should decide what happens next, a model or code? Name the ADK building block you would use.
  • b. Sketch the graph as an edges list, with node names and route names.
  • c. Where does the "at most twice" limit live, and how does data move between nodes?
  • d. Write two evaluation cases (input, expected tool calls, reference reply) and choose criteria and thresholds, including one that would catch a reply that contradicts the policy.
  • e. Name two things that must be stored outside the process if the assistant runs on Cloud Run, and say how you would configure that.

Requirements

  • Every step where the order is fixed or the rule is exact is handled by code (a function node, a route or a deterministic check), not by wording in an instruction.
  • The design includes exactly one loop, built as a back-edge or a LoopAgent, with its limit enforced in code that you control.
  • At least one evaluation case uses an exact tool-trajectory check and at least one criterion judges meaning rather than word overlap.
  • The storage answer names the session service and the artifact service, and says what happens to a conversation if neither is configured.

Expected behaviour

A coherent design in which the model is used for classification and drafting, code is used for routing, the policy check and the revision limit, and a human approval step sits before any refund above 100. The evaluation plan combines a cheap lexical check with an LLM-judged one, and the deployment plan avoids in-memory storage.

Hint 1

Classification and drafting need judgement. The policy check and the attempt counter are exact, so they belong in function nodes.

Hint 2

Graph nodes pass their return values on, but a model node inside the loop only returns text, so keep the attempt count in session state, which a node can set with `Event(state=...)`. The graph itself does not count for you.

Hint 3

A reply that approves a refund of 500 can share most of its words with a reply that says approval is needed, so word overlap will not separate them.

c. The limit and the data. The limit lives in policy_check, a function node. The reviser is a model call and returns only text, so a counter carried in the data would be lost on the way round the loop. Keep it in state instead: ADK fills a function node's parameters from state by name (the data handling page's attempts example shows the pattern), so policy_check reads revisions, emits Event(output=..., route="REVISE", state={"revisions": revisions + 1}), and routes to GIVE_UP once two revisions have been made. A LoopAgent with max_iterations=2 would be the template equivalent, but the docs describe template workflows as superseded in ADK 2.0. Data otherwise moves as return values, so anything a later node needs, such as the customer id, must be returned by earlier nodes or placed in state.

d. Evaluation. Case 1: "I was charged twice for invoice 1042", expected tool call get_invoices(customer_id="C-77"), reference reply "I found a duplicate charge on invoice 1042 and have started a refund of 40." Case 2: "Refund my 500 order", the same expected tool call, reference reply "A refund of 500 needs human approval, so I have passed your request to a colleague." Criteria: tool_trajectory_avg_score at 1.0, because the lookup is deterministic; response_match_score at 0.8 as a cheap regression check; and the LLM-judged final_response_match_v2 at 0.8 for meaning, which is the one that fails a reply promising an immediate refund of 500.

e. Storage. Cloud Run recycles instances, so set --session_service_uri to a database or the managed Vertex AI session service, so that conversations and pending approvals survive, and set --artifact_service_uri to a Cloud Storage bucket for attachments. With neither flag, ADK uses in-memory storage and a customer's next message after a recycle starts from nothing.
