LLM Gateways and Reliability (Rate Limits, Retries, Fallbacks)

An LLM gateway is a service between your applications and one or more model providers that takes over the shared work of calling them: keys, routing, rate limits, retries, fallbacks, budgets and logging. Reliability is the set of rules that keeps a feature working when a provider is slow, overloaded, throttling you or down.

1Overview

Why it matters

Every provider returns 429 and 5xx responses (Anthropic signals overload with 529, OpenAI with 503) and stalled streams from time to time, so an application that calls one provider inherits that provider's bad hours. Handling them badly is often worse than not handling them: a retry loop at every layer of a stack multiplies load on a provider that is already struggling, a retry of a monthly spend cap wastes minutes, and a fallback to a model with different abilities can quietly change what users receive.

Once more than one team shares provider accounts, the same questions become organisational. Who holds the real API keys? Which job drained the token quota that the customer-facing feature needed? Which model actually answered, and what did it cost? Engineers who ship LLM features, platform teams who run a shared gateway, and anyone who deploys these systems into a customer's environment need to design these answers on purpose.

  • Name what a gateway should own (keys, routing, limits, budgets, logging) and the costs of adding one.
  • Describe a graceful-degradation plan for the moment every route fails.

Key terms

Rate limit
A cap on how much you may use a provider over a short window, such as requests per minute or tokens per minute. Exceeding it returns a 429 that usually clears within seconds.
Spend limit
A cap on total cost over a long period, such as a calendar month. Reaching it also returns a 429 on some providers, but waiting does not help until the period resets.
Exponential backoff
A retry schedule in which the wait grows after each failure, for example 1, 2, 4 and 8 seconds, usually up to a cap.
Jitter
A random amount added to or used instead of a retry delay, so that many clients that failed together do not all retry at the same moment.
Retry budget
A limit on how much of your traffic may be retries, either per request (for example three attempts) or per client (for example retries under 10% of requests).
Circuit breaker
A switch that stops sending traffic to a failing route for a cool-down period after repeated failures, then lets a few trial requests through to see whether it has recovered.
Fallback
An alternative route, another provider or another model, that a request is sent to when the primary route fails or is unavailable.
LLM gateway
A proxy that exposes one API for model calls and applies authentication, limits, routing, reliability rules and logging in front of the providers. Also called an LLM proxy or AI gateway.
Virtual key
A credential issued by a gateway to an application or team, so that the real provider keys stay inside the gateway and usage can be limited and attributed per key.
Graceful degradation
Giving users a reduced but useful result, such as a cached answer or a shorter reply, when the full experience cannot be delivered.

2Explanation

Introduction

In LLM APIs and Streaming you learned that a model call is an HTTP request that can fail in several ways: a 429 when you send too much, a 5xx or 529 when the provider is struggling, a timeout when nothing comes back. You also met the SDK defaults that quietly retry twice. This lesson covers what a production system builds on top of those defaults.

Think of phoning a busy restaurant. If the line is engaged you wait a little and call again, not every second. If they say they are full until nine, calling back at five past is pointless. If they stay unreachable you book a second restaurant, and if that fails too you cook something simple at home. Reliability for model calls is the same four moves: retry when the problem is brief, stop when it is not, route elsewhere when a provider stays unavailable, and degrade to something simpler when nothing is available.

Writing those rules into every application duplicates code and invites mistakes. An LLM gateway (also called an LLM proxy or AI gateway) moves them into one service between your applications and the providers. Applications send ordinary model requests to the gateway. The gateway authenticates them, checks budgets and rate limits, picks a provider, retries or fails over when a call goes wrong, and writes one log of everything that happened.

The lesson follows a request through those stages: rate limits and quotas, timeouts, retries, circuit breakers, fallbacks, what a gateway should own, and what to show when every route fails. A worked example simulates a whole policy in about seventy lines of Python, and five documented systems show how real products make the same decisions.

How it works

Four kinds of failure, four reactions

A reliability layer first has to tell failures apart, because the right reaction differs.

KindTypical signalRight reaction
Capacity: you sent too much429 with a retry-after headerSlow down, wait, retry
Money: a cap was reached429 without retry-after, or a 400 or 402Stop and alert a person
Provider trouble500, 503, 529, timeout, dropped connectionRetry briefly, then route elsewhere
Your request is wrong400, 401, 403, 404, 413Fail fast and fix the request

A failure can also arrive after a stream has started. The status is already 200, so the error appears as an event inside the stream, as the Claude API errors page (opens in a new tab) explains. That case needs its own rule, covered under retries.

Rate limits and quotas

Providers meter use in requests per minute (RPM) and tokens per minute (TPM). OpenAI defines limits per organisation and project, not per user, and applies whichever limit you reach first (OpenAI rate limits (opens in a new tab)). Anthropic splits tokens into input (ITPM) and output (OTPM), refills a token bucket continuously, and warns that a limit of 60 requests per minute may be enforced as one per second (Claude rate limits (opens in a new tab)). A quota or spend cap differs in kind: it bounds total use or cost over a long period and does not clear in seconds.

Counting rules differ, and they matter for capacity planning. OpenAI computes a request's rate-limit usage as the larger of max_tokens and an estimate from the request's character count, so an inflated max_tokens reserves capacity you never use. Anthropic evaluates output tokens as they are produced and ignores max_tokens, and for most models cached input tokens do not count toward ITPM.

The cheapest way to handle a rate limit is to avoid hitting it. Put a token bucket in front of the provider: a bucket of capacity CCC that refills at rrr units per second, from which a request must take what it needs before it is sent. Use one bucket for requests and one for tokens, and cap concurrency. By Little's law, requests in flight equal arrival rate times average latency, so 5 requests per second at 8 seconds each means 40 in flight, and a cap of 20 holds throughput to 2.5 requests per second. When a limit is still exceeded, read retry-after and the remaining-capacity headers instead of guessing.

A shared account also needs per-consumer limits. Without them one noisy job, such as a nightly batch run, can drain the quota that a user-facing feature depends on. Gateways enforce these limits per key, team or subscription.

Timeouts: how long to wait

A request without a timeout can hold a connection, a thread and a user's attention indefinitely. The AWS article on timeouts, retries and backoff with jitter (opens in a new tab) picks a timeout by choosing an acceptable false-timeout rate, such as 0.1%, and reading the matching latency percentile of the downstream service. LLM calls make that harder because latency grows with the length of the reply. For streaming calls, split the wait into three:

  • Time to first token is how long until the stream starts. It is the signal of a sick provider, so keep it short, for example 5 to 15 seconds. Vercel's gateway clears its provider timeout at the first chunk, and Claude Code offers a first-byte deadline for streaming requests.
  • Stall timeout is the longest silence allowed between chunks once the stream is running.
  • Total deadline is the longest the caller will wait for the whole answer, covering every retry and fallback. Google's SRE book describes passing the remaining deadline down the call chain, so a 30-second deadline with 7 seconds already spent leaves 23 seconds for the next hop.

The worst-case time on one route is attempts times the per-attempt timeout, plus the largest backoffs. Three attempts of 5 seconds with backoffs of up to 1 and 2 seconds is 18 seconds, which leaves a 20-second deadline only 2 seconds for a fallback. Set explicit timeouts: the OpenAI Python SDK defaults to 10 minutes and two retries, and the Anthropic SDK also retries twice.

Retries: when, how often, and at which layer

Retry only failures that can clear by themselves: a 429 with a retry-after value, 5xx and 529 responses, timeouts and dropped connections. The wait before attempt n+1n+1n+1 is capped exponential backoff with full jitter:

dn=min⁡(c,  b⋅2 n−1),wn∼Uniform(0, dn)d_n = \min\bigl(c,\; b \cdot 2^{\,n-1}\bigr), \qquad w_n \sim \mathrm{Uniform}(0,\, d_n)dn​=min(c,b⋅2n−1),wn​∼Uniform(0,dn​)

with base bbb and cap ccc. If the server sent retry-after, use it as a floor for wnw_nwn​. Jitter spreads clients out so they do not all return at the same instant.

Three limits stop retries from becoming the problem:

  1. A per-request cap. In Google's SRE book a request that has failed three times is returned to the caller.
  2. A retry budget. The same book allows a retry only while retries stay below 10% of requests for that client. The AWS SDK uses a token bucket for the same purpose: retries run while tokens remain.
  3. One layer retries. If every layer retries, attempts multiply.

A gateway setup has at least three layers: the SDK, your application code and the gateway. Leave retries on in one of them and set the others to zero.

A retry re-sends the request, so it is only safe when repeating it has no side effects. AWS says APIs with side effects are not safe to retry unless they are idempotent. A plain completion costs tokens and nothing else, but an agent turn that has already run tool calls does not. Do not replay a stream that has delivered completed text or tool calls; keep what finished and continue from it (see the Claude Code example).

Circuit breakers and cooldowns

Retries assume the problem passes soon. When it will not, every caller waits through the full retry schedule. A circuit breaker watches recent failures per route and, past a threshold, stops sending traffic for a cool-down. The Azure pattern (opens in a new tab) has three states: closed (traffic flows and failures are counted), open (calls fail immediately) and half-open (a few trial calls decide whether to close or reopen). LiteLLM calls its version a cooldown, set by allowed_fails and cooldown_time. Azure API Management can take the trip duration from Retry-After, which Azure recommends accepting even though the value can be large, for example a day. Keep one breaker per provider, model and key rather than one per provider. AWS notes that breakers add hard-to-test modal behaviour and prefers a local retry token bucket; the two combine.

Fallbacks: somewhere else to go

A fallback sends the request to another route. The levels, from least to most visible to users, are the same model through another provider or region, a different model, and a degraded feature.

Decide three things in advance. What triggers it. Overload, 5xx, timeouts and an open breaker are safe triggers. A 429 should trigger one only when the fallback has its own quota: OpenRouter lists rate limiting, downtime, moderation flags and context-length errors as triggers, while Claude Code never falls back on rate-limit errors. An invalid request should not trigger one, except a context-window error that a larger-window model solves. What must stay the same. The model version (Azure advises against failing over from version X to X+1), the context window, tool and structured-output support, data-residency rules and price. Run your evaluation suite against every fallback. How long the chain is. Claude Code allows three models, and OpenRouter's Messages endpoint accepts three fallbacks. Each step adds latency.

What a gateway owns

A gateway is a reverse proxy that speaks an LLM API. Across the products in this lesson, its work falls into six jobs.

JobWhat it means
Keys and identityReal provider keys stay in the gateway; callers get virtual keys or managed identities
RoutingChoose provider, model or deployment by order, weight, priority, latency or cost
Limits and budgetsRate, token and spend caps per key, team or subscription
ReliabilityTimeouts, retries, circuit breaking and fallbacks, in one place
LoggingOne record per attempt: who called, which route served, tokens, cost, status
PolicyCaching, content safety checks

A gateway has costs. It adds a network hop and a component that can itself fail; Azure advises against tying other regions' availability to the region that holds your gateway. Its counters may be approximate across instances. Its logs hold prompt text, so apply the retention rules in Data Privacy and Compliance. And Azure notes that if you control a few easy-to-update clients, the same logic can live in client code instead.

Graceful degradation

When every route fails, the product still decides what the user sees. Plan it, best option first: a cached or earlier answer; a smaller model with a shorter max_tokens; the feature without its model step, such as search results without a summary; a queue that answers later; and last, an honest error message. Azure's circuit-breaker example serves cached or default responses while the breaker is open and tells users some data is temporarily unavailable. Google's SRE chapters describe the same idea as serving reduced-quality results and shedding the lowest-priority traffic first, so tag batch traffic as sheddable before an incident.

Worked example: One policy, three requests - retries, a circuit breaker and a fallback, simulated by hand

This example simulates one reliability policy from end to end. It needs no network and no API key, so everyone gets identical output: a fake clock replaces sleeping, the providers return scripted outcomes, and the random generator is seeded.

The policy. The caller waits at most 20 seconds in total. Each attempt waits at most 5 seconds for the first token. A route gets up to 3 attempts, spaced by capped exponential backoff with full jitter (base 1 s, cap 8 s) and never shorter than a retry-after value. After 3 consecutive failures a route is cut off for 30 seconds, and the next route in the list is tried.

The script. The primary answers request A with a 529 after 0.4 s, then a 429 with retry-after: 3 after 0.2 s, then never starts streaming. The backup is healthy. Requests B and C arrive later and show the circuit breaker at work.

Save this as resilient_call.py (Python 3.9 or later, standard library only) and run python3 resilient_call.py.

python
import random

DEADLINE_S = 20.0           # total time the caller is willing to wait
FIRST_TOKEN_TIMEOUT_S = 5.0
MAX_ATTEMPTS = 3            # per route: 1 try + 2 retries
BASE_S, CAP_S = 1.0, 8.0    # capped exponential backoff
OPEN_AFTER_FAILS = 3
OPEN_FOR_S = 30.0
RETRYABLE = {"overloaded", "rate_limited", "timeout"}


class Route:
    """A provider with scripted outcomes: (kind, seconds_taken, retry_after)."""

    def __init__(self, name, script):
        self.name, self.script = name, list(script)
        self.fails, self.open_until = 0, None

    def send(self, timeout_s):
        kind, took, retry_after = self.script.pop(0)
        return (kind, timeout_s, None) if kind == "timeout" else (kind, took, retry_after)

    def state(self, now):
        if self.open_until is None:
            return "closed"
        return "open" if now < self.open_until else "half-open"


def call(start, routes, rng):
    now, log = start, []

    def note(route, attempt, text):
        log.append(f"  t={now - start:5.2f}s  {route.name:<8} #{attempt}  {text}")

    for route in routes:
        state = route.state(now)
        if state == "open":
            note(route, 0, "breaker open, skipped")
            continue
        attempts = 1 if state == "half-open" else MAX_ATTEMPTS
        for attempt in range(1, attempts + 1):
            remaining = DEADLINE_S - (now - start)
            kind, took, retry_after = route.send(min(FIRST_TOKEN_TIMEOUT_S, remaining))
            now += took
            if kind == "ok":
                route.fails, route.open_until = 0, None
                note(route, attempt, "ok" + (" (half-open probe)" if state == "half-open" else ""))
                return now, f"ok via {route.name}", log
            route.fails += 1
            if route.fails >= OPEN_AFTER_FAILS or state == "half-open":
                route.open_until = now + OPEN_FOR_S
                note(route, attempt, f"{kind}; breaker opens for {OPEN_FOR_S:.0f}s")
                break
            wait = max(retry_after or 0.0, rng.uniform(0, min(CAP_S, BASE_S * 2 ** (attempt - 1))))
            out_of_time = now + wait - start >= DEADLINE_S
            if kind not in RETRYABLE or attempt == attempts or out_of_time:
                note(route, attempt, f"{kind}; give up on this route")
                break
            note(route, attempt, f"{kind}; wait {wait:.2f}s")
            now += wait
    return now, "failed", log


rng = random.Random(7)
primary = Route("primary", [("overloaded", 0.4, None), ("rate_limited", 0.2, 3.0), ("timeout", 0, None), ("ok", 0.9, None)])
backup = Route("backup", [("ok", 1.2, None), ("ok", 1.2, None)])
clock = 0.0
for name, gap in [("A", 0.0), ("B", 2.0), ("C", 45.0)]:
    start = clock + gap
    end, outcome, log = call(start, [primary, backup], rng)
    print(f"request {name} arrives at t={start:.2f}s")
    print("\n".join(log))
    print(f"  -> {outcome} after {end - start:.2f}s\n")
    clock = end

A retry-after larger than the cap is honoured by the code unless waiting would pass the deadline, in which case it gives up on that route.

Edge cases and limitations

A spend cap that looks like a rate limit
The Claude API answers a reached monthly spend cap with a 429 of the same type as an ordinary rate limit but with no retry-after header, and the SDK's automatic retries fail until access resumes. Check the error code (enforced_spend_limit_reached) and the missing header before choosing backoff. A limit you set yourself returns a 400 instead. Treat both as stop-and-alert.
A long Retry-After can park a backend for a long time
Azure documents that an Azure OpenAI backend answering 429 can send a Retry-After value that can be large, for example one day, and recommends breaker rules that accept it. Honouring it protects a throttled backend, but the breaker then keeps the deployment out of rotation for that long even if capacity returns sooner, for example after a quota increase. Our suggestion, not Azure's, is to put a ceiling on the trip duration, keep a periodic probe, and alert when the ceiling is hit so that a person decides.
Counters and breakers that are only approximate
Azure documents that its token counters run independently per gateway instance, that near-concurrent requests can briefly exceed a token limit because usage is known only after the response, and that breaker tripping and load balancing are approximate across instances. Leave headroom below hard provider limits, and use a shared store with strict checks where a budget must never be exceeded.
A stream that fails after the user has seen text
The status is already 200, so the failure arrives as an error event or a closed connection. Replaying the request repeats text the user read and can run tool calls twice. Claude Code keeps completed blocks, runs finished tool calls and continues from their results, and the OpenAI Python SDK does not retry stream consumption because replaying could duplicate delivered output. A chat UI can keep the partial text, mark it incomplete and offer to continue.
A fallback that changes behaviour
A different model may follow the prompt differently, reject a tool schema, return another output format or sit under other data-retention terms. Azure advises failing over only between deployments of the same model version, and when Claude Code compacts a conversation it will not use a fallback with a smaller context window than the primary's. Test every fallback with your evaluations and record which route served each request.
Stateful sessions cannot hop between backends
When a client relies on server-side state, such as the Assistants API on Azure, a request that fails over to another backend arrives where the conversation history does not exist. Azure's guide advises pinning the client to one backend and, if that backend is throttled, returning a 429 so the client handles the outage knowingly instead of hiding it.

When to use it, and when something simpler is enough

Use it when

  • Several teams or applications share provider accounts and you need separate keys, budgets and rate limits so one consumer cannot drain the others' quota.
  • A feature has an availability target that one provider cannot meet alone, so you need a second route that you have tested.
  • You do not control the client code, for example applications run by customers or other teams, and a gateway is the only place where you can change policy quickly.
  • You need one audit trail of who called which model, what it cost and which route served the request.

Think twice when

  • You run one application against one provider with few users. The SDK's retries with explicit timeouts and a provider-side spend limit are enough, and a gateway adds a component to operate.
  • Data-residency rules forbid sending traffic across regions. A unified cross-region gateway would break them, so use one gateway per region instead.
  • No fallback can do the same job, for example a task that depends on one model's behaviour. Failing visibly beats a silent change in output.

A simpler alternative. Use the SDK's retries and timeouts with values you set yourself, one fallback model in application code, and a spend limit at the provider. Move to a gateway when more than one team or provider is involved, or when you cannot ship client changes quickly. Azure's guidance makes the same point: with a few clients you control, the logic can live in the code.

Key takeaways

  • Decide by cause, not by status code: a 429 can be a rate limit that clears in seconds or a spend cap that lasts until the period resets, and only the first deserves a retry.
  • Retry transient failures with capped exponential backoff and full jitter, treat retry-after as a floor, cap attempts per request and per client, and let exactly one layer of the stack do the retrying.
  • Give streaming calls three clocks, time to first token, stall time and a total deadline, and make the retries and the fallback fit together inside that deadline.
  • A fallback is safe only when the new route can do the same job: the same model version, enough context window, the same tool support, acceptable data handling and quality you have measured.
  • A gateway centralises keys, routing, limits, budgets, reliability rules and logging, at the price of an extra hop, a component that can fail and counters that may be approximate.
  • Plan graceful degradation before the incident, because when every route fails the product must still show the user something specific.

Example 1 of 5

LiteLLM Proxy as a team gateway with virtual keys, budgets and fallbacks

LiteLLMDocumented in an open-source project

LiteLLM is an open-source proxy server (its documentation now calls it the AI Gateway) and Python router that puts one OpenAI-compatible endpoint in front of many model providers. Its documentation pages on virtual keys, budgets and rate limits, the router and proxy reliability describe the features used in this example. [4][3][1][2][5]

The problem

A platform team gives several teams access to models from more than one provider. The teams should not hold the provider's real API key, one runaway job should not spend the whole budget, and one provider's outage or rate limit should not take every application down. Doing this inside each application would mean every team writing, and getting right, the same key handling, limits and failover code.

Where this topic fits

The proxy is the only service that talks to the providers. Applications know the proxy URL and their own virtual key. Inside the proxy a request passes the key and budget checks, is routed to a deployment of the requested model name, and is retried or moved to a fallback model if the call fails.

How it is applied, step by step

  1. An administrator starts the proxy with a master key and a database and lists model deployments in config.yaml. Several deployments can share one model_name, so the router can balance across them and skip one that is cooling down.
  2. For each team or application the administrator calls /key/generate with the master key, setting the allowed models, a max_budget, a budget_duration and optionally rpm_limit and tpm_limit. The application receives only this virtual key; the real provider keys stay in the proxy's configuration.
  3. On each request the proxy checks the virtual key, its budget and its rate limits before anything is sent to a provider. A key over budget gets an error that names the entity that crossed the limit.
  4. The router picks a deployment for the requested model name and calls it with request_timeout. A failed call is retried up to num_retries times, and a deployment that fails more than allowed_fails times in a minute is cooled down for cooldown_time seconds.
  5. If every deployment of that model name fails, the fallbacks setting sends the request to the next model name in the list, here a smaller model. A setting (enforce_fallback_model_access) applies the key's model-access checks to fallback targets, and the key's budget is re-checked against each fallback target unless that is switched off.
  6. Because every application calls the same endpoint, spend is tracked per key, and a team can be given a different budget or fallback list without any change to its code.

Why this approach fits

The three needs, hiding credentials, bounding spend and surviving a provider problem, are all things an individual application cannot enforce on itself. The proxy sees every request, so keys, limits and failover are enforced in one place and do not depend on each team implementing them correctly.

Limitation or tradeoff

Budget enforcement depends on spend read from a database, so a proxy without one caps nothing. The budget documentation describes fail-closed settings, one of which validates spend against the database before every budgeted request is admitted, which is stricter but adds database reads, although the page says these are coalesced and cached for a few seconds. The proxy is also one more service to run, and its retries stack with an application SDK's own retries unless one side is switched off.

What the sources document

  • Virtual keys let the proxy track spend and control model access per key. Creating them needs a master key and a Postgres database, and a key is issued by calling /key/generate with the master key; accepted parameters include models, duration, max_budget, rpm_limit and tpm_limit. [4]
  • Budgets can be personal (a key without a team), shared by a team, or set per team member. max_budget is a dollar amount and budget_duration sets the reset period in seconds, minutes, hours or days. Every budget is enforced against spend read from a database, so none caps anything without one. Rate limits use rpm_limit and tpm_limit. [3]
  • The proxy estimates a request's maximum cost from the request body and the model's pricing, and a key over its budget gets an error such as ExceededTokenBudget. A fail-closed setting makes every budgeted request validate spend against the database before it is admitted. [3]
  • The proxy's reliability settings include num_retries, request_timeout and in-order fallbacks. A model is cooled down when it fails more than allowed_fails calls within a minute, and context-window and content-policy errors have their own fallback lists. [1]

Example 2 of 5

Azure API Management as an AI gateway with token limits, circuit breakers and spillover

Microsoft AzureDocumented in official docs

Microsoft documents API Management's AI gateway capabilities, the llm-token-limit policy, backend pools and circuit breakers, and an Azure Architecture Center guide on placing a gateway in front of several Foundry model deployments. [7][8][9][6]

The problem

Many applications share the tokens-per-minute quotas of a few model deployments. One application can use the whole quota and block the others, a throttled deployment answers 429 with a Retry-After that can be long, and provisioned capacity that sits unused wastes money, so the architecture guide suggests slightly under-provisioning it and bursting to a standard deployment.

Where this topic fits

The gateway sits between the applications and the model deployments. A token-limit policy runs on the way in, a pool of backends with priorities decides where the request goes, and a circuit breaker on each backend removes a throttled or failing deployment from rotation.

How it is applied, step by step

  1. Each application or team gets its own subscription key. The policy uses it as the counter key, for example `<llm-token-limit counter-key="@(context.Subscription.Id)" tokens-per-minute="5000" estimate-prompt-tokens="false" />`, so every consumer has a separate token budget.
  2. Once a consumer's usage passes its tokens-per-minute rate, the gateway rejects its further requests with a 429, and passing a period quota gives a 403. With prompt-token estimation switched on, the gateway can also reject an oversized prompt before sending it.
  3. Requests that pass go to a backend pool. The provisioned deployment is placed in the highest priority group and a pay-as-you-go deployment in a lower one.
  4. A circuit breaker rule on each backend trips after a number of 429 or 5xx responses in an interval, and with acceptRetryAfter set it uses the backend's Retry-After value as the pause.
  5. While the provisioned backend is tripped, the lower-priority group serves the traffic. When the trip duration ends the circuit resets and traffic returns to the provisioned deployment.
  6. The gateway emits token metrics and logs per consumer, so the team sees who used what and how often a backend was skipped.

Why this approach fits

Quota sharing is a problem of the whole portfolio of applications, so it has to be solved where all their traffic meets. Enforcing a token limit per consumer at the gateway stops one application that has used its share from consuming more of the shared deployment, and a breaker that follows the backend's own Retry-After reacts to the authoritative signal instead of guessing when capacity returns.

Limitation or tradeoff

The documentation lists limits of its own. Token counts for a request are known only after the response, so near-concurrent requests can briefly exceed a limit, and streaming requests use estimated counts. Counters and breaker rules are kept per gateway instance, so tripping and balancing are approximate, and only one circuit-breaker rule per backend is supported at the time of writing. The gateway can also become a single point of failure, which the architecture guide warns about for multi-region designs.

What the sources document

  • The llm-token-limit policy limits token use per counter key by a tokens-per-minute rate, by a quota over a period from hourly to yearly, or by both. Exceeding the rate returns 429 Too Many Requests and exceeding the quota returns 403 Forbidden. [7]
  • The backend circuit breaker trips on a count or percentage of failures in an interval, stops sending requests for a trip duration and returns 503 meanwhile. The page cautions that an Azure OpenAI backend can return a 429 with a Retry-After value that can be large (for example, 1 day) and recommends breaker rules that accept it. [8]
  • Backend pools support round-robin, weighted and priority-based balancing, and lower-priority groups are used only when all backends in higher-priority groups are unavailable because their circuit breaker rules have tripped. [8]
  • The architecture guide describes pairing a provisioned instance with a standard instance so that clients first use the pre-allocated throughput and then burst to the standard deployment, and it advises failing over only to endpoints running the same model at the same version. [9]
  • The AI gateway extends API Management's existing gateway rather than being a separate offering, and its listed capabilities include load balancing across AI endpoints, token limits per consumer and logging of prompts and completions. [6]

Example 3 of 5

Vercel AI Gateway with provider timeouts, provider order and model fallbacks

VercelDocumented in official docs

Vercel's AI Gateway is a hosted endpoint that routes model requests across providers. Its documentation pages on provider options, provider timeouts and model fallbacks describe how an application controls failover from inside the request. [11][12][13]

The problem

A chat feature streams answers to users who notice a slow start. A provider can be slow or erroring, and the team wants failover without writing retry code in every route handler. It also wants to see afterwards which provider and model really served each request.

Where this topic fits

The application sends its normal model request to the gateway's base URL. Routing and failover options ride along in the request body under providerOptions.gateway. The gateway tries providers in order, applies the timeout to the start of the stream, then moves to the next provider and, once a model has no working provider, to the next model.

How it is applied, step by step

  1. The application calls the gateway with its gateway API key, using the chat completions, messages or responses format. By default the gateway chooses providers from recent uptime and latency.
  2. To control the sequence, the request lists providers in order, for example Anthropic first and Bedrock second, optionally restricting the set with only.
  3. With the team's own provider credentials (BYOK), providerTimeouts sets a limit in milliseconds per provider. If a provider has not started responding in time, the gateway aborts that attempt and tries the next provider.
  4. For a streaming request the timeout is cleared when the first chunk arrives, so it guards the time to first token. A running stream is not cut off by it.
  5. If every provider for the requested model fails, the models array supplies backup models, tried in order. The answer comes from the first model and provider combination that succeeds.
  6. The response metadata lists each model and provider attempt with its success flag, status code and error, which the team can log to track how often failover happens.

Why this approach fits

A streaming answer is judged by its first token, and a provider that stops answering is far more common than one that is permanently gone. A first-token timeout turns "slow" into "failed" quickly enough for a fallback to still beat the user's patience, and putting the policy in the request keeps it out of the application's control flow.

Limitation or tradeoff

The documentation says provider timeouts apply to BYOK credentials only and that some providers cannot cancel a stream, so a timed-out request may still be billed. Every failed attempt also consumes part of the user's wait. Backup models may answer differently, and the gateway cannot tell whether the alternative meets your quality bar, so the fallback list needs the same evaluation as the primary choice.

What the sources document

  • By default AI Gateway dynamically chooses providers using a combination of recent uptime and latency, and the order and only options in providerOptions.gateway control which providers handle a request and in what sequence. [11]
  • providerTimeouts sets a timeout in milliseconds per provider. If the provider does not start responding in time, the gateway aborts the request and falls back to the next available provider. Allowed values run from 1,000 ms to 789,000 ms. [12]
  • Provider timeouts apply to BYOK credentials only. For streaming requests the timeout is cleared at the first stream chunk, and because some providers do not support stream cancellation a timed-out request may still be charged. [12]
  • The models array lists backup models tried in order. When all providers for one model fail, the gateway tries the next model, and the response comes from the first successful model and provider combination. [13]
  • Provider metadata includes a modelAttempts array, with providerAttempts inside it, that records for each attempt the provider, success flag, status code and error, so a team can see which route served a request. [13][12]

Example 4 of 5

Claude Code's client-side retries, timeouts, partial-response rule and fallback models

AnthropicDocumented in official docs

Claude Code is Anthropic's command-line coding agent. Its error reference, model configuration page and CLI reference document the reliability rules built into the client, which apply with or without a gateway. [14][15][16]

The problem

An agent session runs for a long time and makes many model calls, some of which come back after tool calls with side effects. A transient failure in the middle of a turn must not lose the work done so far or run a tool twice, a stalled connection must not hang the session, and an unattended job needs a deliberate choice between failing fast and waiting out a capacity problem.

Where this topic fits

The rules wrap each model request inside the agent loop (see The Agent Loop). Retries and timeouts apply to every request, a rule about where in the response a failure arrived decides whether a re-send is safe, and an optional fallback chain applies when the primary model is overloaded or unavailable.

How it is applied, step by step

  1. Each model request is retried on transient failures, namely server errors, overloaded responses, request timeouts before streaming begins, dropped connections and temporary 429 throttles, with exponential backoff. A gateway's spend-limit 429 is not treated as a throttle.
  2. The retry count defaults to 10 and is set by CLAUDE_CODE_MAX_RETRIES. API_TIMEOUT_MS sets the per-request timeout, and CLAUDE_STREAM_FIRST_BYTE_TIMEOUT_MS (Claude Code v2.1.242 or later) sets a deadline for the first response byte of a streaming request.
  3. A response stream that stalls before any of Claude's response has arrived is aborted and the request is re-sent at most once, so a silent connection cannot hold the session indefinitely.
  4. If a failure arrives after Claude has completed a block of text or a tool call, the request is not re-sent. Claude Code keeps the completed work, runs the finished tool calls and continues from their results.
  5. When a fallback chain is configured with the --fallback-model flag or the fallbackModel setting, an overloaded or unavailable primary model causes the next model in the list to be tried for the current turn. Rate-limit errors never trigger the switch.
  6. The next message tries the primary model first again. When the chain covers compaction, Claude Code does not fall back to a model with a smaller context window than the primary's, because summarising there would cut off part of the conversation.

Why this approach fits

Whether a retry is safe depends on what the client has already done. A failure before any output leaves nothing to repeat, while a failure after a finished tool call would repeat a side effect. Putting that line at "a completed block of text or a tool call" is the idempotency rule applied to an agent, and the fallback chain keeps a session usable during an overload without changing the model for the rest of the work.

Limitation or tradeoff

Ten retries with backoff can keep a turn waiting for a long time before an error appears, which is why the docs expose the retry count as a setting. A fallback model may behave differently from the primary within that turn. The documented exclusion of rate-limit errors from fallback shows that the choice is a design decision: a gateway whose fallback has separate quota can sensibly choose otherwise, as OpenRouter's documented triggers include rate limiting.

What the sources document

  • Claude Code retries transient failures up to 10 times with exponential backoff before showing an error. The count is set by CLAUDE_CODE_MAX_RETRIES, and API_TIMEOUT_MS sets the per-request timeout with a default of 600000 ms. [14]
  • CLAUDE_STREAM_FIRST_BYTE_TIMEOUT_MS sets the deadline for the first response byte of a streaming request. A stalled stream that has produced none of Claude's response is aborted and streamed again at most once. [14]
  • Retried failures include server errors, overloaded responses, request timeouts before any response has streamed, dropped connections and temporary 429 throttles, but not a gateway's spend-limit 429. [14]
  • After a completed text block or tool call, Claude Code does not re-run the request because that could execute the same tool calls twice. It keeps what Claude completed, runs the finished tool calls and continues the turn from their results. [14]
  • A fallback chain applies when the primary model is overloaded, unavailable or returns another non-retryable server error. Authentication, billing, rate-limit, request-size and transport errors never trigger a switch, chains are capped at three models, and the switch lasts for the current turn only. [15][16]

Example 5 of 5

The Claude API's rate limits and spend caps, seen from the provider's side

AnthropicDocumented in official docs

Anthropic's rate limits and API errors pages describe how the Claude API meters an organisation's usage, what a 429 carries, and how the official SDKs retry. They are the upstream limits that a client or gateway limiter sits in front of. [17][18]

The problem

A provider must protect shared capacity and its customers' budgets, but a client that sees only "429" cannot tell a limit that clears in seconds from a cap that lasts until the month ends. A client that retries both the same way either hammers a closed door or gives up on a request that would have succeeded after a short wait.

Where this topic fits

This is the outermost layer. Its response headers feed a client-side limiter, its error codes feed the classifier that decides between waiting and stopping, and its limit definitions decide how much capacity a gateway can safely hand out to its own consumers.

How it is applied, step by step

  1. The API measures requests per minute, input tokens per minute and output tokens per minute for each model class at organisation level. Optional workspace limits can set lower caps for part of an organisation.
  2. Capacity is a token bucket that refills continuously, so a short burst can trigger a 429 even when the per-minute average is below the limit.
  3. A request over a rate limit gets a 429 of type rate_limit_error with a retry-after header in seconds, and anthropic-ratelimit headers report remaining capacity and reset times.
  4. The official SDK retries transient failures twice by default with exponential backoff, using retry-after when it is present.
  5. A reached monthly spend cap also returns a 429 of type rate_limit_error but with no retry-after header and the code enforced_spend_limit_reached. Retrying, including the SDK's retries, fails until access resumes.
  6. A client or gateway classifies the response by that code and header, retries or backs off for the first kind, and stops and alerts a person for the second.

Why this approach fits

The same status code carries two different instructions, so the decision has to use the cause. Reading the error code and the header costs nothing, prevents a pointless retry loop on a spend cap, and routes the expensive case to a person or an alert instead of a log line nobody reads.

Limitation or tradeoff

The numbers differ by usage tier and model class and change over time, so a gateway should read the headers and the Rate Limits API instead of hard-coding them. The page also calls limits maximums rather than guarantees, and warns that a sharp rise in traffic can trigger acceleration limits, so traffic should ramp up gradually. Other providers count differently: OpenAI includes max_tokens in its estimate.

What the sources document

  • Messages API rate limits are measured in requests per minute, input tokens per minute and output tokens per minute for each model class. Exceeding one returns a 429 with a retry-after header that says how long to wait. [17]
  • The API uses a token bucket, so capacity is continuously replenished up to the maximum instead of resetting at fixed intervals, and a limit of 60 requests per minute might be enforced as one request per second so that short bursts can trigger errors. [17]
  • When a tier's monthly spend cap is reached the API returns a 429 of type rate_limit_error with no retry-after header and the error code enforced_spend_limit_reached. Retries, including the SDK's, fail until access resumes, and a spend limit that the customer set returns a 400 instead. [17][18]
  • The official SDKs automatically retry transient failures such as connection errors, rate limits and 5xx errors with exponential backoff, twice by default, honouring the retry-after header when present. [18]
  • For most Claude models only uncached input tokens count toward ITPM, so with a 2,000,000 ITPM limit and an 80% cache hit rate the page says you could process 10,000,000 input tokens per minute in total. [17]

4Common mistakes

  1. Leaving retries on in the SDK, the application and the gateway at the same time

    Why it causes problems
    Attempts multiply across layers. Three attempts at each of three layers send up to 27 requests to the provider for one user request, which turns a brief brownout into a retry storm and burns rate-limit capacity that healthy traffic needs.
    How to recognise it
    Provider-side request counts are several times the number of user requests during an incident, and the gateway log shows repeated attempts for calls that your application logs show as single requests.
    How to fix it
    Pick one layer to own retries, usually the gateway, and set max_retries to 0 in the SDKs and the application. OpenAI's rate-limit guide gives the same advice for application-managed retries. Give the owner a per-request cap and a retry budget.

  2. Retrying every 429 and every 5xx in the same way

    Why it causes problems
    A spend-cap 429 or a 4xx error fails again on every attempt, so the request wastes the whole retry schedule while the user waits. A real rate limit that is retried before the retry-after time just fails again and keeps the bucket empty.
    How to recognise it
    Attempt logs show the same error code on every attempt, or retries that start sooner than the retry-after value.
    How to fix it
    Classify by cause. Retry only transient failures, use retry-after as the minimum wait, and send spend-cap and invalid-request errors straight to an alert or a clear error.

  3. Using one long total timeout for a streaming call

    Why it causes problems
    With a 10-minute SDK default, a provider that accepts the connection and then goes silent leaves the user looking at a blank screen for minutes, and the fallback never gets the chance to help in time.
    How to recognise it
    The 99th percentile of time to first token in your traces is far above the median, and incident reports describe spinners instead of errors.
    How to fix it
    Set a short first-token timeout, a stall timeout between chunks and a total deadline, and size the retries and the fallback so that together they fit inside the deadline.

  4. Adding fallback models without testing them

    Why it causes problems
    The fallback may follow the prompt differently, lack a tool or structured-output feature, have a smaller context window or sit under other data-retention terms. Users then get different answers during an incident, which is when nobody is watching quality.
    How to recognise it
    Schema failures or quality complaints rise only when the fallback rate rises, and the gateway log shows requests served by a model that was never evaluated.
    How to fix it
    Run the evaluation suite against every fallback, require the same model version and enough context, record the route that served each request, and alert on the fallback rate.

  5. Replaying a request after part of the answer was delivered

    Why it causes problems
    The user sees duplicated or contradictory text, and an agent turn can run the same tool call twice, which may charge a card or send an email a second time.
    How to recognise it
    Duplicate side effects appear in downstream systems after provider incidents, or chat transcripts restart in the middle of a sentence.
    How to fix it
    Re-send only when nothing completed has been delivered. Otherwise keep the completed work, mark the answer as incomplete or continue from it, and give side-effecting tools idempotency keys.

  6. Treating the gateway as free infrastructure

    Why it causes problems
    A single unmonitored gateway instance becomes the outage for every application, and prompt logs collected by default can store personal or confidential text without any retention rule.
    How to recognise it
    Application errors appear whenever one gateway instance restarts, or the log store holds raw customer text that nobody approved.
    How to fix it
    Run more than one instance with health checks, decide what clients do if the gateway is down, and set redaction and retention rules for prompt logs before turning logging on.

Exercise 1

Schedule requests so neither the request limit nor the token limit is exceeded

CodingIntermediateAbout 40 min (estimate)Hypothetical scenario

A provider allows 10 requests per minute and 10,000 tokens per minute. Both limits behave as token buckets that refill continuously. A new client starts with both buckets full. Your application has 12 requests ready at time 0, and each one counts as 1,500 tokens against the token limit (the prompt estimate plus the reply budget).

Write a scheduler in Python, standard library only, that decides the earliest start time of each request so that neither bucket is ever overdrawn. Use a virtual clock: compute the times and do not sleep. Process the requests in order, one at a time. Then change the cost to 800 tokens per request and run it again.

Requirements

  • Implement a TokenBucket class with a capacity, a refill rate per second, a method that returns the earliest time a given cost is available, and a method that takes the cost at a given time.
  • Keep one bucket for requests (capacity 10, refilling 10 per minute) and one for tokens (capacity 10,000, refilling 10,000 per minute).
  • A request starts at the earliest time at which both buckets can pay for it, and never before the previous request started.
  • Print the start times of all 12 requests, rounded to one decimal, for each of the two token costs.

Expected behaviour

With 1,500 tokens per request the start times are 0.0 for requests 1 to 6, then 3.0, 12.0, 21.0, 30.0, 39.0 and 48.0. The token bucket is the limit that binds. With 800 tokens per request requests 1 to 10 start at 0.0 and the last two start at 6.0 and 12.0, because now the request bucket binds.

Hint 1

Store the bucket's level and the time of the last update. The level at time t is the stored level plus elapsed seconds times the refill rate, capped at the capacity.

Hint 2

If the cost minus the current level is zero or less, the cost is available now. Otherwise wait for the missing amount divided by the refill rate.

Hint 3

Take from both buckets at the chosen start time, not at the time you first asked.

Show solution

The only subtle part is that a request must wait for the slower of the two buckets. Saving this as token_bucket_schedule.py and running it reproduces the expected times.

python
class TokenBucket:
    """A bucket that refills continuously. Time is passed in; nothing sleeps."""

    def __init__(self, capacity, refill_per_s):
        self.capacity, self.refill_per_s = capacity, refill_per_s
        self.level, self.updated_at = float(capacity), 0.0

    def level_at(self, t):
        return min(self.capacity, self.level + (t - self.updated_at) * self.refill_per_s)

    def earliest(self, cost, t):
        missing = cost - self.level_at(t)
        return t if missing <= 0 else t + missing / self.refill_per_s

    def take(self, cost, t):
        self.level, self.updated_at = self.level_at(t) - cost, t


def schedule(n_requests, tokens_each, rpm=10, tpm=10_000):
    requests, tokens = TokenBucket(rpm, rpm / 60), TokenBucket(tpm, tpm / 60)
    t, starts = 0.0, []
    for _ in range(n_requests):
        t = max(t, requests.earliest(1, t), tokens.earliest(tokens_each, t))
        requests.take(1, t)
        tokens.take(tokens_each, t)
        starts.append(round(t, 1))
    return starts


for cost in (1_500, 800):
    print(f"{cost:>5} tokens each:", schedule(12, cost))

Why these numbers: six requests use 9,000 of the 10,000 tokens, so the seventh is 500 tokens short. The token bucket refills 10,000 / 60, about 166.7 tokens per second, so it waits 3.0 seconds. After that each request needs 1,500 tokens, which takes 1,500 / 166.7 = 9.0 seconds to refill, so requests follow every 9 seconds. The sustained rate is 10,000 / 1,500, about 6.7 requests per minute, below the 10-per-minute request limit, so tokens are the limit that binds. At 800 tokens the token bucket could pay for 12.5 requests per minute, which is more than 10, so the request bucket binds: ten requests go at once and the rest follow every 6 seconds. Lowering the reply budget therefore changes which limit you hit first.

Design the reliability policy for a support-reply assistant

DesignIntermediateAbout 35 min (estimate)Hypothetical scenario

You own the reliability policy for an assistant that drafts replies for customer-support agents. Agents wait for the draft, so the hard limit is 12 seconds from the click to a finished draft, and the first token should appear within 3 seconds.

What you know:

  • Primary route P: model M at provider A. It is approved for EU customer data.
  • Secondary route B: the same model family at provider B, also approved for EU data and about 20% slower.
  • Last resort S: a small model approved for EU data that writes shorter, less tailored drafts.
  • A nightly batch job that re-drafts old tickets shares provider A's account with the live assistant.
  • Last quarter's incidents: (1) every morning at 09:00 a burst of 429 responses while the batch job ran; (2) 20 minutes of 529 responses from provider A; (3) a 40-minute episode in which provider A accepted requests but sent the first token only after 25 seconds.

Write the policy as a short table, then calculate the worst-case time of your primary route and of the primary plus secondary routes.

Requirements

  • Give a first-token timeout, a maximum number of attempts and a backoff cap for each route, and show that the worst-case total fits inside the 12-second limit with time left for the degraded path.
  • State which failures trigger a fallback and which do not, including what you do with a 429 that has no retry-after header.
  • State how the batch job is kept from affecting the live assistant.
  • Describe the degraded experience shown if every route fails.
  • List the fields you would log for every attempt.

Expected behaviour

A complete answer has a table of timeouts, attempts and triggers per route, a worst-case calculation that is at most 12 seconds, a separation between the batch job and the live traffic, a degraded path that needs no model call, and a log schema that records the route, error and timing of each attempt. Worst case on a route is attempts times the first-token timeout plus the largest backoff between attempts. Slower routes need proportionally longer timeouts.

Hint 2

Incident 3 shows why a first-token timeout matters more than a total timeout. Incident 1 is a quota sharing problem, not a provider problem.

Hint 3

A circuit breaker changes the worst case: once P is open, requests skip it and the later routes get more of the 12 seconds.

Degraded path. If all routes fail or the 12 seconds run out, show the agent the ticket summary and the closest saved reply template with the message "Draft unavailable, use this template", and allow a manual retry.
