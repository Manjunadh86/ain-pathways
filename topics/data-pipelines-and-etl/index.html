Data Pipelines and ETL

A data pipeline is an automated series of steps that moves data from the systems where it is created to a place where it can be analysed or used. ETL (extract, transform, load) and ELT (extract, load, transform) are the two usual orders for those steps.

1Overview

Why it matters

Every dashboard, machine learning feature and retrieval index is only as good as the pipeline that feeds it, and pipelines fail in ways that are easy to miss. A task is retried after a timeout and yesterday's revenue is counted twice. A nightly job that rebuilds a whole table takes a little longer each week until it no longer finishes before the morning report. A row is deleted in the source and lives on in the warehouse for months. None of these raises an error, so the first sign is usually a number that someone has stopped trusting.

A forward deployed engineer meets this on almost every engagement, because the first technical job is usually to get a customer's data out of their systems and into a shape the product can use. You need to be able to read an existing Airflow Dag, judge whether a requirement really needs streaming, pick a load strategy that survives a rerun, and add the checks that catch bad data before the customer does. The same skills apply when the destination is a vector index or a feature table instead of a warehouse.

Key terms

Data pipeline
An automated sequence of steps that moves data from source systems to a destination, on a schedule or continuously.
ETL
Extract, transform, load. The data is reshaped in a separate engine before it is written to the destination.
ELT
Extract, load, transform. Raw data is written to the destination first and reshaped there, usually with SQL.
Batch processing
Processing a bounded slice of data, such as one day of orders, in a job that starts, finishes and stops.
Stream processing
Processing records continuously as they arrive, on data that has no end.
Orchestrator
A service that runs pipeline tasks in dependency order on a schedule, retries failures and records what ran. Apache Airflow is one.
Data interval
The time range of data that one scheduled run is responsible for, such as 00:00 on 1 March up to 00:00 on 2 March.
Incremental load
A load that processes only the rows that are new or changed since the previous run, instead of the whole table.
Idempotent
Describes an operation that leaves the same result whether it runs once or several times with the same input.
Upsert
A write that inserts a row when its key is new and updates the existing row when the key is already present. Also called a merge.

2Explanation

Introduction

In SQL and Relational Databases you queried tables that already existed. A data pipeline is how those tables get filled and kept current. It is a program, or a chain of programs, that copies data out of the systems where it is created (an order database, a CRM, a stream of click events), reshapes it, and writes it somewhere built for analysis, such as a data warehouse.

You have probably run a pipeline by hand. Every Monday someone exports a CSV from the billing tool, deletes the test accounts, fixes the date column and pastes the result into the sales report. Those are the three classic steps:

  • Extract: read data from a source system.
  • Transform: clean it, join it with other data and compute the columns people need.
  • Load: write the result to the destination.

Done in that order the process is called ETL. If the raw export is loaded first and the tidying happens inside the destination, it is ELT. Either way, a data pipeline is the Monday routine with the person removed.

Removing the person is where the engineering starts. The person noticed when the export was empty, never pasted the same file twice, and knew that last week's numbers had since been corrected. A program has to be told all of that. Sooner or later the source is unreachable at 02:00, the job dies halfway through the load, the same file is delivered twice, a row changes a week after it was first copied, and the table grows from a million rows to a billion.

This lesson covers six ideas for working under those conditions:

  1. ETL versus ELT: where the transformation runs.
  2. Batch versus streaming: how often the pipeline runs.
  3. Orchestration: what runs the steps in order and reruns them after a failure, with Apache Airflow as the example.
  4. Distributed processing: how one step is spread across many machines, with Apache Spark as the example.
  5. Incremental and idempotent loads: how to process only what changed, and how to make a rerun harmless.
  6. Data quality checks: how to stop bad data before anyone reads it.

How it works

ETL and ELT: where the transform runs

Microsoft's architecture guide reduces the difference to a single point (opens in a new tab): where the transformation happens. In ETL a separate engine reshapes the data, often in staging tables, and only finished tables reach the destination. In ELT the raw data is loaded first and the destination's own SQL engine transforms it, usually through a tool such as dbt that runs SELECT statements and stores the results as tables.

  • Choose ETL when the destination is too small for heavy transforms, or when sensitive fields must be removed or audited before the data lands.
  • Choose ELT when the destination is a warehouse or lakehouse with elastic compute and you want the raw data kept, so a wrong transform can be fixed and rerun without extracting again.

Batch and streaming: how often it runs

A batch pipeline wakes on a schedule, processes a bounded slice of data (yesterday's orders) and stops. A streaming pipeline never stops: it handles records as they arrive. Micro-batch sits between them, a small batch every few seconds or minutes.

The line is blurred. Spark's Structured Streaming (opens in a new tab) runs a stream as a series of small batch jobs by default, and its documentation gives end-to-end latencies as low as 100 milliseconds.

Streaming exposes a problem that batch hides. An event has an event time (when it happened) and a processing time (when the pipeline saw it), and the two drift apart when a phone is offline or a network is slow. A stream processor therefore keeps a watermark. In Spark, a window ending at time TTT accepts late data (opens in a new tab) until

max event time seen−allowed lateness>T\text{max event time seen} - \text{allowed lateness} > Tmax event time seen−allowed lateness>T

Past that point the engine may discard the window's state and drop later arrivals for it. Data inside the allowance is never dropped.

Start from the freshness the consumer needs. A finance report read each morning is a batch job. A fraud check that must act before a payment clears is a stream. Streaming costs more to build and operate, so "real time" should be a requirement that someone can justify.

Orchestration: Apache Airflow

A real pipeline has many steps that depend on each other. An orchestrator runs each step when its inputs are ready, retries failures and records what ran. In Apache Airflow (3.3 at the time of writing) a workflow is a Dag, a directed acyclic graph of tasks written in Python. A scheduler triggers runs and hands tasks to workers, and a metadata database stores every task's state.

python
import pendulum
from airflow.sdk import CronDataIntervalTimetable, dag, task

@dag(schedule=CronDataIntervalTimetable("0 0 * * *", timezone="UTC"),
     start_date=pendulum.datetime(2026, 3, 1, tz="UTC"), catchup=False)
def orders_daily():
    @task(retries=3)
    def extract_load(*, data_interval_start, data_interval_end):
        ...  # copy rows changed in [start, end) into the raw table

    @task
    def transform(): ...

    @task
    def quality_checks(): ...

    extract_load() >> transform() >> quality_checks()

orders_daily()

Each run owns a data interval. The run for 1 March covers 00:00 on 1 March up to 00:00 on 2 March and starts after that interval has ended (opens in a new tab), so the whole day's data exists. Because the task receives the interval instead of asking the clock, any day can be run again later. With catchup on, the scheduler creates a run for every interval since the start date that has not run yet (it is off by default in Airflow 3). Backfill runs a chosen past range: airflow backfill create --dag-id orders_daily --from-date 2026-03-01 --to-date 2026-03-07.

One version detail: in Airflow 3 the setting create_cron_data_intervals defaults to False, so a bare cron string such as "@daily" gets a trigger timetable (opens in a new tab) instead of a data-interval one. A trigger timetable has no data interval: data_interval_start and data_interval_end are the same and equal the time the run is triggered. That is why the Dag above asks for CronDataIntervalTimetable by name.

Distributed processing: Apache Spark

When one machine cannot hold or finish a transform, the step goes to a cluster. In Spark your program is the driver. It asks a cluster manager for executors, processes on worker machines that hold slices of the data called partitions and run one task per partition.

python
from pyspark.sql import SparkSession, functions as F

spark = SparkSession.builder.getOrCreate()
orders = spark.read.parquet("/lake/raw/orders/")            # lazy: only a plan so far
daily = (orders.filter(F.col("status") == "paid")           # runs inside each partition
               .groupBy("order_date")                         # needs a shuffle
               .agg(F.sum("amount_cents").alias("revenue_cents")))
daily.write.mode("overwrite").parquet("/lake/marts/daily_revenue/")   # the action that starts the job

filter and groupBy are lazy: Spark only records them. The write is an action that starts a job, which Spark splits into stages. Filtering happens inside each partition in parallel. Grouping needs all rows with the same key in one place, so Spark performs a shuffle, copying data between executors at the cost of disk I/O, serialisation and network I/O. Much of Spark tuning is about shuffling less data. For data that fits in one database or one machine's memory, Spark mostly adds start-up time and moving parts.

Incremental loads: process only what changed

A full refresh rebuilds the destination from all source data on every run. It is simple and always correct, and it gets slower every day. Uber reported (opens in a new tab) ingestion runs that had to convert a table of over 100 terabytes in full each time, to take in over 100 gigabytes of new data a day. An incremental load processes only the rows that are new or changed since the last run.

The pipeline needs a marker for "changed":

  • A high-water mark. Remember the largest updated_at loaded so far and ask for rows beyond it. It misses hard deletes and any update that did not touch the timestamp.
  • The data interval. Ask for rows inside the run's interval. Easy to rerun, with the same blind spots.
  • Change data capture (CDC). Read the database's replication log, which records every insert, update and delete.

Data arrives late, so incremental loads usually reprocess a lookback window of recent days and rely on the next property to absorb the overlap.

Idempotent loads: a rerun changes nothing

Tasks get retried, backfills replay old intervals and message brokers deliver twice. A load is idempotent when running it again with the same input leaves the destination exactly as one run would. Airflow's best practices (opens in a new tab) give the rule in three parts: treat a task like a database transaction that never leaves partial results, use an upsert where a rerun would otherwise insert duplicates, and read and write a specific partition, never "the latest data". The write statement decides the outcome. dbt offers the same choices as incremental strategies (opens in a new tab).

Streaming uses the same idea. Under at-least-once delivery (opens in a new tab) a message is never lost but may arrive again, so the consumer must make a repeat harmless. Uber's ad-event pipeline gives each aggregated record a random UUID (opens in a new tab) that serves as an idempotency and deduplication key downstream, and its Pinot store upserts on it.

Data quality checks: stop bad data at the gate

A pipeline can finish without errors and still deliver nonsense. A quality check is a query with an expected answer, run after a load and before consumers see the result.

CheckQuestion it asks
UniquenessDoes any key appear twice?
CompletenessIs a required column null?
ValidityIs every value in the allowed set or range?
Referential integrityDoes every order point at a real customer?
Volume and freshnessDid roughly the usual number of rows arrive, and recently?
ReconciliationDo source and destination totals agree?

dbt writes each check as a data test, a SELECT that returns the failing rows and passes when it returns none. Airflow's SQL provider has check operators (opens in a new tab) such as SQLColumnCheckOperator and SQLTableCheckOperator. Either way, a failed check must block publication. A warning in a log that nobody reads protects no one.

Worked example: A daily orders load in SQLite that survives a retry, a late update and a backfill

The pipeline below copies orders from a source system into a small warehouse. It is ELT: each run loads a raw copy of one day's changes, then SQL inside the database turns the raw rows into the orders table. SQLite stands in for the warehouse, so all you need is Python 3 with SQLite 3.24 or later, the version that added upsert (opens in a new tab).

The source holds seven change records. Four orders are created on 1 March. On 2 March order 1003 moves from pending to paid, order 1002 is refunded and order 1005 is new. To show the difference a load strategy makes, every run writes to two tables: orders_append with a plain INSERT, and orders with an upsert.

Save this as orders_pipeline.py and run python3 orders_pipeline.py.

python
import sqlite3

SOURCE = [  # order_id, customer, amount_cents, status, updated_at
    (1001, "c1", 2500, "paid",     "2026-03-01T09:15"),
    (1002, "c2", 4000, "paid",     "2026-03-01T11:40"),
    (1003, "c1", 1500, "pending",  "2026-03-01T18:05"),
    (1004, "c3", 9900, "paid",     "2026-03-01T22:30"),
    (1003, "c1", 1500, "paid",     "2026-03-02T08:10"),
    (1002, "c2", 4000, "refunded", "2026-03-02T10:00"),
    (1005, "c4", 3200, "paid",     "2026-03-02T13:45"),
]
COLS = "order_id, customer, amount_cents, status, updated_at"

db = sqlite3.connect(":memory:")
db.executescript(f"""
CREATE TABLE raw_orders ({COLS}, interval_start);
CREATE TABLE orders_append ({COLS});
CREATE TABLE orders (order_id PRIMARY KEY, customer, amount_cents, status, updated_at);
""")

CHECKS = {  # each query counts the rows that break a rule; 0 means the check passes
    "order_id is unique": "SELECT COUNT(*) - COUNT(DISTINCT order_id) FROM {t}",
    "status is known": "SELECT COUNT(*) FROM {t} WHERE status NOT IN ('pending', 'paid', 'refunded')",
    "amount is not negative": "SELECT COUNT(*) FROM {t} WHERE amount_cents IS NULL OR amount_cents < 0",
}

def failed_checks(table):
    return [name for name, sql in CHECKS.items() if db.execute(sql.format(t=table)).fetchone()[0] > 0]

def run(start, end):
    rows = [r for r in SOURCE if start <= r[4] < end]      # extract one data interval
    with db:                                               # one transaction: all of it or none of it
        db.execute("DELETE FROM raw_orders WHERE interval_start = ?", (start,))
        db.executemany("INSERT INTO raw_orders VALUES (?,?,?,?,?,?)", [r + (start,) for r in rows])
        db.execute(f"INSERT INTO orders_append SELECT {COLS} FROM raw_orders WHERE interval_start = ?", (start,))
        db.execute(f"""
            INSERT INTO orders SELECT {COLS} FROM raw_orders WHERE interval_start = ?
            ON CONFLICT(order_id) DO UPDATE SET
                customer = excluded.customer, amount_cents = excluded.amount_cents,
                status = excluded.status, updated_at = excluded.updated_at
            WHERE excluded.updated_at >= orders.updated_at""", (start,))
        failures = failed_checks("orders")
        if failures:
            raise ValueError(f"quality checks failed: {failures}")   # leaving the block rolls back

def report(label):
    parts = [label.ljust(22)]
    for table in ("orders_append", "orders"):
        rows, paid = db.execute(
            f"SELECT COUNT(*), SUM(CASE WHEN status = 'paid' THEN amount_cents ELSE 0 END) FROM {table}").fetchone()
        parts.append(f"{table}: {rows:>2} rows, paid {paid / 100:>6.2f}")
    print(" | ".join(parts))

DAY1 = ("2026-03-01", "2026-03-02")
DAY2 = ("2026-03-02", "2026-03-03")
run(*DAY1); report("day 1")
run(*DAY1); report("day 1 again (retry)")
run(*DAY2); report("day 2")
run(*DAY1); report("day 1 again (backfill)")
print("failing on orders_append:", failed_checks("orders_append"))
print("failing on orders:", failed_checks("orders"))

It prints:

text
day 1                  | orders_append:  4 rows, paid 164.00 | orders:  4 rows, paid 164.00
day 1 again (retry)    | orders_append:  8 rows, paid 328.00 | orders:  4 rows, paid 164.00
day 2                  | orders_append: 11 rows, paid 375.00 | orders:  5 rows, paid 171.00
day 1 again (backfill) | orders_append: 15 rows, paid 539.00 | orders:  5 rows, paid 171.00
failing on orders_append: ['order_id is unique']
failing on orders: []

Read it one line at a time:

  • Day 1. Both tables agree: four orders, and paid revenue of 25.00 + 40.00 + 99.00 = 164.00 (order 1003 is still pending).
  • Retry. The plain INSERT doubles everything to 328.00. The upsert finds the four keys already present and changes nothing.
  • Day 2. The true figure is 164.00 − 40.00 (refund) + 15.00 (1003 is now paid) + 32.00 (new order) = 171.00, and orders has it. orders_append holds three rows for order 1002 and counts two of them as paid.
  • Backfill. Replaying day 1 after day 2 leaves orders untouched, because the last line of the upsert refuses to overwrite a row with an older version. Delete that WHERE line and the backfill turns 1002 back to paid and 1003 back to pending, and the total becomes a wrong 196.00.

One SQLite detail: when an INSERT takes its rows from a SELECT, the SELECT needs a WHERE clause before ON CONFLICT, or the parser cannot tell the upsert from a join. Here the interval filter does that job.

Four decisions made orders safe to rerun. The slice comes from the interval arguments, never from the clock. The raw slice is replaced, not appended. The target is upserted by key, with a guard on the version. Everything runs in one transaction with the checks inside it, so a failed check leaves no trace.

Edge cases and limitations

A timestamp filter cannot see deleted rows
A query for rows whose updated_at is beyond the high-water mark returns nothing for a row that was deleted, because the row is no longer there to be returned. The destination keeps it for good. Shopify lists this as a limitation of its query-based extraction tool, together with updates that never touched the timestamp. Use soft deletes (a deleted_at column), read the change log with CDC, or run a periodic full comparison of keys between source and destination.
One batch holds two versions of the same key
If an order changes twice inside one interval, a batch built from a change log holds two rows with the same key. Some databases reject a merge that would touch a target row twice, and others apply the versions in whatever order the rows happen to arrive. dbt's documentation warns that an incremental model may fail when a unique_key matches more than one row. Reduce the batch to the latest version per key before the merge, for example with ROW_NUMBER() over the key ordered by the version column.
Data arrives after its window or lookback has closed
A stream processor drops an event that arrives after the watermark has passed its window, and a batch job with a three-day lookback never revisits day four. Spark's documentation says plainly that data later than the threshold starts getting dropped. Size the allowance from measured lateness, count what is dropped, and keep a slower corrective path, such as a weekly rebuild of recent partitions, for whatever falls outside it.
An overwrite is not atomic on plain file storage
Spark's documentation states that its save modes use no locking and are not atomic, and that an overwrite removes the existing data before writing the new data. A job that fails halfway leaves the output empty or partial, and a reader in that window sees missing data. Write to a new location and switch readers over only after the checks pass, or use a table format or database that commits a replacement as one transaction.
The run for 1 March starts on 2 March
An Airflow run that owns a data interval starts after the interval has ended, and its logical date marks the start of the interval. A Dag with a start_date of 1 March and a daily interval first runs just after midnight on 2 March. Newcomers read this as the pipeline being a day late and compensate with date arithmetic that breaks backfills. In Airflow 3 a bare cron schedule behaves differently again, with both ends of the interval equal to the trigger time, so check which timetable a Dag uses before trusting its dates.
A new source column silently fails to appear
Schemas change upstream without notice. dbt's default for an incremental model, on_schema_change set to ignore, leaves a newly added column out of the target table, and a removed column makes the run fail. Its documentation adds that none of the settings fills in old rows for a new column. Compare the source schema with the expected one as a check, and plan a full refresh when a column must be populated for past rows.

When to use it, and when something simpler is enough

Use it when

  • The same data has to move from a source to a destination again and again, on a schedule or continuously, and people or systems depend on the copy being current.
  • A question needs data from several systems joined together, such as orders from an application database with accounts from a CRM, and no single source can answer it.
  • Analytical queries would slow down the operational database, so they should run on a copy that is shaped for analysis.
  • You need history that the source overwrites, such as every status an order has had, or you need to rebuild a result later from the raw inputs.

Think twice when

  • The analysis is a one-off. Export the data once or query a read replica; a scheduled pipeline is upkeep with nothing to justify it.
  • The data is small and can be queried where it lives, through a view or a read replica, without hurting the source.
  • Nobody acts on the data within minutes. Streaming then adds cost and on-call work for freshness that is never used.
  • The data fits in one database or on one machine. A cluster engine such as Spark then adds start-up time and failure modes without making anything faster.

A simpler alternative. A scheduled SQL script, for example cron running one file of statements against the warehouse, or a materialized view that the database refreshes on a schedule. This is enough for one source, a handful of steps and a daily refresh. It stops being enough when steps depend on each other across systems, when a failure at 02:00 needs an automatic retry and a record of what ran, or when you have to rerun last Tuesday without touching the other days. That is the point to adopt an orchestrator.

Key takeaways

  • ETL and ELT differ only in where the transformation runs, either in a separate engine before the load or inside the destination after a raw load.
  • Choose batch or streaming from the freshness the consumer needs, because streaming buys low latency at the price of handling late, out-of-order and duplicate events around the clock.
  • An orchestrator such as Airflow runs tasks in dependency order, gives each run a data interval, retries failures and can replay past intervals as a backfill.
  • Spark spreads a transform over a cluster by running one task per partition, and the shuffle that regroups rows across machines is usually what makes a job slow.
  • An incremental load processes only what changed, and it is safe only when the write is idempotent, so that retries, overlaps and backfills all leave the same result.
  • Data quality checks are queries with expected answers that run before publication and stop the pipeline when they fail.

Example 1 of 5

GitLab's data platform loading raw data into Snowflake and transforming it with dbt

GitLabDocumented in a case study

GitLab publishes its internal handbook. The Data Platform page of the enterprise data team describes the company's analytics stack in detail: the extraction tools, Airflow for orchestration, Snowflake as the warehouse, dbt for transformation and the tests that guard the result. [21][20][2]

The problem

The data that GitLab reports on is created in many places, including GitLab.com's own databases, the CustomersDot application and other sources that managed connectors can reach. Each source has to be copied into one warehouse on a known schedule, turned into models that analysts can rely on, and kept recoverable when a load goes wrong. The handbook defines a replication frequency for its data sources (how often new and updated data is loaded) and a service level objective, which it describes as the time between real time and the data being made available for consumption.

Where this topic fits

The whole stack is an ELT pipeline. Extract and load come first and put unmodified data into a raw database. Transformation happens afterwards, inside Snowflake, where dbt builds a prep layer and then a prod layer. Airflow sits above the custom extraction jobs as the orchestrator, and the Trusted Data Framework supplies the quality checks.

How it is applied, step by step

  1. Managed connectors (Stitch and Fivetran) copy some sources straight into Snowflake. The handbook describes them as ELT tools that take away the work of building and orchestrating those movements.
  2. Other sources are extracted by custom Python pipelines that Airflow runs on Kubernetes. Airflow's scheduler starts each pipeline on its schedule and its workers execute the tasks.
  3. Everything lands in the raw database first. No dbt models exist there, so the data is exactly what the source sent.
  4. dbt models, which are SQL statements executed by Snowflake, build the prep database as a first layer of verification and transformation, and then the prod database that the BI tool is allowed to query.
  5. Incremental extraction tables overlap the previous extract by 30 minutes to check for missing transactions, and some tables are extracted in full because incremental extraction is not feasible for them. Repeated records build up in the raw layer, which the handbook ties to extracting more often, and three weekly Airflow jobs build a deduplicated copy that keeps the latest records.
  6. The Trusted Data Framework defines tests for schemas, column values and row counts, and its row count test compares the number of rows in the source database with the number in Snowflake. For the most critical (Tier 1) data, Monte Carlo monitors freshness and volume anomalies.

Why this approach fits

Snowflake can run heavy SQL, so there is no separate transformation cluster to operate, and the people who know the business rules can write them as SQL models. Keeping the raw copy is what makes the pipelines repeatable: when a model turns out to be wrong, it is corrected and rebuilt from data that is already in the warehouse, without going back to the source. Three layers also separate two questions that are easy to mix up, what the source said and what the business means by it.

Limitation or tradeoff

Loading raw data first means that whatever the source held, sensitive fields included, is in the warehouse before any transformation has run, so access to the raw layer has to be controlled separately. The handbook says duplicate records have grown as extracts became more frequent, and it describes a dedicated deduplication framework to clean them up, which is one more pipeline to maintain. Any extract that deliberately re-reads rows, such as an overlapping window, makes repeats likely, so the raw layer cannot be assumed to hold each row once. Row count reconciliation is a coarse check: equal counts do not prove that the values in the rows match.

What the sources document

  • The handbook states that GitLab uses Stitch and Fivetran for some data sources and calls them off-the-shelf ELT tools that move data into its Snowflake warehouse. It lists custom pipelines built in Python and orchestrated via Airflow among the other extraction methods, says that Airflow on Kubernetes is used for orchestration, and says that dbt is used for all transformations. [21]
  • Three primary Snowflake databases are described. Data is first loaded into raw, where no dbt models exist. Prep is the first layer of verification and transformation and is not yet ready for general business use. Prod holds data that has been transformed and modeled for business use, and it is the database Tableau can query. [21]
  • The platform vision lists idempotent data pipelines as a property, and the backup section says the vast majority of data in Snowflake is copied or derived from copies of the data sources and managed idempotently with dbt. [21]
  • Incremental extraction tables overlap by 30 minutes to check for missing transactions, and CustomersDot data is extracted in full twice a day. The Trusted Data Framework defines schema tests, column value tests and row count tests, and a row count test reconciles source and target. [21]
  • The deduplication section says that GitLab.com and CustomersDot extracts now run more often, which has increased duplicate records and Snowflake storage needs. Three Airflow deduplication jobs run weekly and build a deduplicated table that keeps the latest records. [21]

Example 2 of 5

Facebook replacing hundreds of sharded Hive jobs with one 60 TB Spark job

Meta (Facebook)Documented in an engineering article

A 2016 article on Facebook's engineering blog, Apache Spark @Scale, describes moving a production batch pipeline from Hive to Spark. The pipeline prepares features for the company's entity ranking systems. [22][8][9]

The problem

Raw feature values for real-time entity ranking were generated offline and then loaded into a serving system. The Hive pipeline that produced them had three logical stages, and each stage was split into hundreds of smaller Hive jobs sharded by entity id, because one large Hive job per stage was less reliable and ran into the limit on tasks per job. The article says the pipeline took roughly three days to finish and was hard to manage, since hundreds of sharded jobs made monitoring difficult.

Where this topic fits

This is the transform step of a batch pipeline, run on a cluster. Before it, feature data sits in the warehouse. After it, the output is loaded into the system that serves ranking queries. Spark replaces the engine that does the transform, and the concept at work is distributed processing: the input is cut into partitions, executors run one task per partition, and a shuffle regroups the rows by key.

How it is applied, step by step

  1. The job reads about 60 TB of compressed input. Spark divides it into partitions and schedules one task per partition on the cluster's executors. The article reports more than 250,000 tasks for the job and attributes that to the 60 TB input and a 256 MB HDFS block size.
  2. The first logical stage filters the features. A filter needs no data from other partitions, so every partition is processed in parallel where it sits.
  3. The second logical stage aggregates per pair of entity and target. All rows of a pair must be on the same executor, so Spark shuffles the data. The article reports a 90 TB shuffle and sort.
  4. The third logical stage splits the result into shards and passes each shard through a custom program that writes the index files used for serving.
  5. All three stages run as one Spark job, which removes the temporary tables that the Hive pipeline wrote between its stages.
  6. The team did not start at full size. They ran the job on 50 GB of input, then 300 GB, 1 TB and 20 TB, and fixed the reliability and performance problems that appeared at each size.

Why this approach fits

The hundreds of small jobs existed only to work around the limits of running one large job. An engine that can plan the whole computation and run it reliably makes that manual sharding unnecessary, and one job is far easier to monitor than hundreds. Keeping the three stages inside one job also means the data flows from stage to stage without being written out as a table and read back in between.

Limitation or tradeoff

At this size Spark did not work unmodified. The article lists a series of reliability fixes and performance improvements that the team made to Spark and its shuffle service before the job ran in production. The 90 TB shuffle is where the cost sits, and in a 20 TB test the team found that three of the ten hours of runtime went on moving output files from a staging directory to their final location. A single huge job also raises the stakes of a late failure, which is why much of the engineering went into fault tolerance.

Example 3 of 5

Uber replacing daily snapshot re-ingestion with incremental upserts in Hadoop

UberDocumented in an engineering article

Uber's 2018 engineering article on its big data platform walks through the platform's generations. It explains why the second generation's snapshot-based ingestion stopped scaling and how the third generation, built around the Hudi library, made ingestion and downstream jobs incremental. [23]

The problem

In the second generation HDFS and Parquet could not update data in place, so every ingestion run created a new snapshot of the whole table. The article gives the example of a table that gained over 100 GB of new data a day while each run had to convert the entire dataset of over 100 TB. Such jobs could take over twenty hours with more than 1,000 Spark executors, and new data reached users only once every 24 hours.

Where this topic fits

The concept sits in the load step and in every transform downstream of it. Changes from upstream databases arrive as changelogs in Kafka. Ingestion applies them to the stored tables as upserts. Jobs that build derived tables then ask a source table only for the records changed since their last checkpoint, and upsert their results in turn.

How it is applied, step by step

  1. Upstream datastores publish their changes to Kafka as changelog events.
  2. Uber's Marmaray ingestion platform runs in mini-batches, picks up the changelogs from Kafka and applies them to the existing Parquet data in Hadoop through Hudi, which can update, insert and delete records instead of recreating the whole table.
  3. Two tables are kept for each upstream table: a changelog history table with every change received, and a merged snapshot table with the latest merged view.
  4. A reader chooses a view. Latest mode returns the whole table as of now. Incremental mode returns only the records that are new or updated since a given timestamp.
  5. A downstream job stores a checkpoint timestamp, pulls only the records changed since then, transforms them and upserts the output into its derived table, touching old partitions without rebuilding them.

Why this approach fits

When a day's change is about a thousandth of the table, the work should scale with the change. Doing that needs two things from the storage layer, and the article names both: a way to upsert, so that ingestion can apply a change without recreating the table, and a way to ask what changed since a point in time, so that every derived table can be incremental as well. The second is what stops the full rebuild from simply moving one step downstream.

Limitation or tradeoff

Incremental processing moves the difficulty to correctness. A checkpoint that is saved before the output is committed loses data after a crash, and one saved too late reprocesses it, so the upsert has to be idempotent. Updating stored files also has a cost. The article describes the first version of Hudi as rewriting the entire source Parquet file whenever a record is updated, which significantly increased write amplification, and a later merge-on-read design that stores updated records in a separate delta file. Freshness improved from 24 hours to about 30 minutes for raw data and under an hour for derived tables, which is still micro-batch. The article lists stricter schema and semantic checks on incoming data as work that remained.

What the sources document

  • Under snapshot-based ingestion, which the article ties to HDFS and Parquet not supporting updates, a table that gained over 100 gigabytes of new data a day still had its whole dataset of over 100 terabytes converted on every run. The article says such jobs could take over twenty hours with over 1,000 Spark executors. [23]
  • Users could reach new data only once every 24 hours, which the article calls too slow for making real-time decisions. [23]
  • Hudi (Hadoop Upserts anD Incremental) is described as an open source Spark library that provides an abstraction layer on top of HDFS and Parquet and lets Uber update, insert and delete existing Parquet data. A table can be read in latest mode, which gives a view of the whole table at that moment, or in incremental mode, which returns only the records that are new or updated since a given timestamp. [23]
  • Ingestion Spark jobs run every 10 to 15 minutes and give a 30-minute raw data latency, and ETL jobs finish in under 30 minutes, giving end-to-end latency of less than one hour for derived tables. [23]
  • The article says the first version of Hudi's copy-on-write storage rewrites the entire source Parquet file whenever a record is updated, which significantly increases write amplification, and that a merge-on-read design stores the updated record in a separate delta file instead. Downstream modeling jobs pass a checkpoint timestamp to the Hudi reader to fetch only changed records. [23]

Shopify moving from hourly query-based extraction to log-based change data capture

ShopifyDocumented in an engineering article

A 2021 Shopify Engineering article describes Longboat, the company's in-house batch extraction tool, and the change data capture platform built with Debezium and Kafka to read changes from the sharded MySQL databases behind Shopify's main application. [25][17]

The problem

Longboat extracted data by querying each table for the rows changed since its previous query and storing the result in cloud storage. The article lists what this approach cannot do. It misses every hard delete. It depends on each write updating the updated_at column. Rows that change several times between two queries lose their intermediate states. A table could be queried at most once an hour because of the load on the database, so the data was at least an hour old. The article also points out that snapshots of different tables carry different high-water marks, so a join across them has no single freshness time.

Where this topic fits

This is the extract step, and it is a choice between batch and streaming. The query-based tool is batch extraction with a high-water mark. The replacement is streaming extraction: it reads the database's replication log continuously and publishes each change to Kafka, where batch and streaming consumers alike can pick it up.

How it is applied, step by step

  1. A Debezium connector for each database shard reads the MySQL binary log, the same log MySQL uses for its own replication, and turns each committed row change into a record.
  2. The records are written to Kafka. Output is arranged so that each logical table maps to one topic, which hides the database sharding from consumers.
  3. Records are keyed by the source table's primary key and the topics are compacted, so the most recent record for every key is retained and a consumer can rebuild the current state of a table.
  4. Consumers read the topics at their own pace. Because a record can be delivered again after a failure, a typical consumer writes with an upsert on the primary key so that a repeat changes nothing.
  5. A new connector first takes a snapshot of the rows that already exist, then follows the log from that point on.

Why this approach fits

The database already writes every committed change, in order, to its replication log. Reading that log captures deletes and intermediate states that no query against the current table can return, and it avoids scanning large tables every hour. Because the changes arrive within seconds, the same extraction can feed both the warehouse and applications that need fresh data.

Limitation or tradeoff

The article is frank about the costs. Consumers become tightly coupled to the internal data model of the source, so a schema change in the application can break them. The initial snapshot of a table holds a read lock and can take hours. Records above Kafka's default size limit needed special handling. The platform is also a large system to operate, with around 150 connectors and hundreds of terabytes in Kafka. A streaming extract does not remove the need for idempotent loads downstream.

  • Longboat runs queries against the source database at intervals and collects every row of a table that changed since its previous query. The extracted data is kept in cloud storage. [25]
  • The article lists the limitations of this approach: query-based capture misses all hard deletes, it relies on updated_at being modified by every query, rows updated several times between queries lose their intermediate state, a table can be queried only as often as once an hour, and Longboat-sourced data is at a minimum one hour old. Amazon verifying datasets with Deequ before they are published to consumers

AmazonDocumented in an engineering article

An AWS Big Data Blog post written by Amazon engineers and researchers introduces Deequ, an open source library built on Apache Spark for defining and running data quality checks, and describes how it is used on production datasets inside Amazon. [26][27]

The problem

A dataset that many teams consume changes with every new version, and a problem in one version, such as missing values or a shifted distribution, spreads to everything built on top of it. Producers needed a way to state what a good version looks like and to have every new version verified automatically, at the size of the data, before consumers could read it.

Where this topic fits

The checks sit between producing a new version of a dataset and publishing it. The pipeline computes metrics on the new version, compares them with the constraints the producer declared, and only then decides whether the version goes out. This is the quality gate at the end of the flow diagram in this lesson, run as a Spark job.

How it is applied, step by step

  1. The producer of a dataset declares constraints in code, for example a minimum number of rows, columns that must never be null, a column that must be unique and a list of allowed values.
  2. For each new version of the dataset, Deequ turns the declared checks into Spark jobs that compute the required metrics, such as the fraction of non-null values in a column.
  3. Each metric is compared with its constraint, and the result lists every constraint with a status and, on failure, the measured value.
  4. If every constraint passes, the version is published to consumers.
  5. If one fails, publication can be stopped and the producer is notified, so the bad version goes no further.

Why this approach fits

The checks are declared by the people who know the data, kept in code next to the pipeline, and executed by the same engine that processes the data, so they scale with it. Tying publication to the result turns a check from a report into a gate, which is the difference between knowing about bad data and stopping it.

Limitation or tradeoff

A constraint only catches what someone thought to declare, and thresholds need upkeep as the data changes for legitimate reasons. Computing the metrics is extra Spark work over the whole dataset on every version. A failing gate also delays the data for every consumer, so someone has to own the alert. The post's own example shows a further point: its uniqueness check on a column that looked like a key failed with a measured value of about 0.987. A failing check does not say whether the data or the rule that was declared for it is wrong, so someone has to investigate. Deequ is also published as separate releases for each Spark version, so the Spark version you run limits which release you can use.

  • Dataset producers can add and edit data quality constraints. 4Common mistakes

  1. Loading with a plain INSERT and assuming the task will only ever run once.

    Why it causes problems
    Orchestrators retry failed tasks, and people rerun and backfill them. Each extra run adds the same rows again, so sums and counts inflate without any error being raised. In the worked example a single retry doubles revenue from 164.00 to 328.00.
    How to recognise it
    COUNT(*) is larger than COUNT(DISTINCT key) in the target table, or a total changes after rerunning an interval whose source data did not change.
    How to fix it
    Write with an upsert on the business key, or replace the whole partition, inside one transaction. Add a uniqueness check on the key that fails the run.

  2. Calling the current date or time inside a task to decide which data to process.

    Why it causes problems
    A rerun tomorrow, or a run delayed past midnight, processes a different slice from the one intended. A day can be skipped or loaded twice, and a backfill of last month reloads today instead. Airflow's best practices warn that now() leads to a different outcome on each run.
    How to recognise it
    Search the task code for now(), today() and CURRENT_DATE. Rerun yesterday's task and check whether it reads yesterday's rows.
    How to fix it
    Take the slice from the run's data interval, which the orchestrator passes in, and write to the partition named after it.

  3. Treating updated_at as a complete record of what changed in the source.

    Why it causes problems
    Hard deletes, and updates that skip the timestamp, never reach the destination, so it drifts away from the source a few rows at a time. Shopify documents both gaps in its query-based extraction tool.
    How to recognise it
    Row counts or sets of keys differ between source and destination and the difference grows over time, or records that were deleted in the application still show up in reports.
    How to fix it
    Add a reconciliation job that compares keys on a schedule, switch the application to soft deletes, or move the extraction to change data capture from the database log.

  4. Running quality checks after the data is published, or only logging their failures.

    Why it causes problems
    Consumers read the bad batch before anyone reacts, and every dashboard or model built on it has to be corrected and explained afterwards. A warning in a log does not stop the next task.
    How to recognise it
    Check failures appear in the logs of runs that are marked successful, or the check task sits downstream of the task that makes the data visible to users.
    How to fix it
    Run the checks inside the load transaction, or as a blocking task before the publish step, so that a failure stops the run. Amazon describes its Deequ-based system this way, with publication stopped when a constraint fails.

  5. Passing data between orchestrator tasks through local files or large return values.

    Why it causes problems
    Tasks can run on different machines, so a file written by one task may not exist for the next. Airflow's guidance is to use XCom only for small messages and to put larger data in remote storage such as S3 or HDFS.
    How to recognise it
    A Dag works on a laptop and fails on the cluster with a missing file, or tasks return whole datasets from their Python functions.
    How to fix it
    Have each task write its output to shared storage or a warehouse table and pass on only a reference, such as a path or a partition name.

  6. Building a streaming pipeline because real time sounds better than a schedule.

    Why it causes problems
    A stream has to handle late, out-of-order and duplicate events and has to run continuously, which means state to manage and someone on call. If the data is read once a day, that cost buys nothing.
    How to recognise it
    Ask who acts on the data and how soon. If the honest answer is the next morning, the freshness requirement is one day.
    How to fix it
    Start with a batch at the frequency the consumer needs, hourly if necessary, and move one path to streaming when a named decision depends on it.

The fix has four parts: a key on each table, an upsert for the detail rows, a partition overwrite for the summary, and one transaction around both with the checks inside it.

python
import sqlite3

BATCHES = {  # arrival date -> rows of (payment_id, paid_at, amount_cents)
    "2026-03-02": [("p1", "2026-03-01T08:30", 1000), ("p2", "2026-03-01T12:10", 2500),
                   ("p3", "2026-03-01T19:45", 4000)],
    "2026-03-03": [("p4", "2026-03-02T09:05", 3000), ("p5", "2026-03-02T16:20", 1200),
                   ("p6", "2026-03-01T23:58", 800),    # happened on 1 March, arrived a day late
                   ("p2", "2026-03-01T12:10", 2500)],  # delivered a second time
}

db = sqlite3.connect(":memory:")
db.executescript("""
CREATE TABLE payments (payment_id PRIMARY KEY, paid_at, amount_cents);
CREATE TABLE daily_revenue (day PRIMARY KEY, payments, revenue_cents);
""")

def check(name, sql):
    bad = db.execute(sql).fetchone()[0]
    if bad:
        raise ValueError(f"check failed: {name} ({bad})")

def load_batch(arrival_date):
    rows = BATCHES[arrival_date]
    days = sorted({paid_at[:10] for _, paid_at, _ in rows})      # partitions this batch touches
    marks = ",".join("?" * len(days))
    with db:                                                     # one transaction for both tables
        db.executemany(
            """INSERT INTO payments VALUES (?,?,?)
               ON CONFLICT(payment_id) DO UPDATE SET
                   paid_at = excluded.paid_at, amount_cents = excluded.amount_cents""", rows)
        db.execute(f"DELETE FROM daily_revenue WHERE day IN ({marks})", days)
        db.execute(
            f"""INSERT INTO daily_revenue
                SELECT substr(paid_at, 1, 10), COUNT(*), SUM(amount_cents)
                FROM payments WHERE substr(paid_at, 1, 10) IN ({marks})
                GROUP BY 1""", days)
        check("payment_id is unique",
              "SELECT COUNT(*) - COUNT(DISTINCT payment_id) FROM payments")
        check("amounts are positive",
              "SELECT COUNT(*) FROM payments WHERE amount_cents IS NULL OR amount_cents <= 0")
        check("summary reconciles with detail",
              """SELECT (SELECT COALESCE(SUM(amount_cents), 0) FROM payments)
                      - (SELECT COALESCE(SUM(revenue_cents), 0) FROM daily_revenue)""")
    return days

def snapshot():
    return db.execute("SELECT * FROM daily_revenue ORDER BY day").fetchall()

print("rebuilt", load_batch("2026-03-02"), "->", snapshot())
print("rebuilt", load_batch("2026-03-03"), "->", snapshot())
before = snapshot()
load_batch("2026-03-03")            # retry
load_batch("2026-03-02")            # backfill of an older batch
print("unchanged after retry and backfill:", snapshot() == before)
print("rows in payments:", db.execute("SELECT COUNT(*) FROM payments").fetchone()[0])

BATCHES["2026-03-04"] = [("p7", "2026-03-03T10:00", 500), ("p8", "2026-03-03T11:00", -900)]
try:
    load_batch("2026-03-04")
except ValueError as error:
    print(error)

      db.execute("SELECT COUNT(*) FROM payments").fetchone()[0])

  • Days come from the data. The partitions to rebuild are taken from each row's paid_at, not from the arrival date. The second batch therefore touches both 1 March and 2 March, and the late payment p6 lands in the right day: 7500 + 800 = 8300.

The watermark only moves forward. An out-of-order event with an earlier time does not pull it back.

Hint 2

Exercise 3

Design the pipelines for a retailer's three data requests

DesignIntermediateAbout 40 min (estimate)Hypothetical scenario

You are deployed with a regional grocery chain (an invented customer). Three teams have asked for data.

NeedWho wants whatSourceDetails
AFinance wants revenue by store for the previous day on a dashboard by 07:00The orders table in the company's Postgres database80 million rows. About 150,000 rows are inserted or updated per day. A trigger maintains updated_at. Voided orders are hard-deleted. The destination is a cloud data warehouse.
BThe fraud team wants every card transaction scored within 5 secondsThe payment service publishes each transaction to a Kafka topicThe service retries on timeouts, so a transaction can be published more than once. Terminals on poor networks send some events minutes late.

For each need:

  1. Choose batch, micro-batch or streaming, and justify the choice from the stated freshness.
  2. Choose ETL or ELT, and say where the transform runs.
  3. Say how the pipeline knows what changed, and which load strategy it uses.
  4. Name two data quality checks that should block bad data.

Then, for need A only, sketch the Airflow Dag: the schedule, the tasks in order, the retry setting and how the tasks know which slice of data to process. Finally, say what happens if the run for 3 March is executed a second time.

Requirements

  • Each need has a cadence that is justified by its freshness requirement, not by preference.
  • Each need states where the transform runs and why.
  • Each need names a change marker and a load strategy that is safe to rerun.
  • The design for need A accounts for the hard-deleted orders.
  • The design for need B accounts for transactions that are published twice and for late events.
  • The Dag for need A takes its slice from the run's data interval, sets retries and places the quality checks where a failure fails the run.

Expected behaviour

A good answer uses three different shapes: a daily ELT batch for finance, a streaming path with an idempotent sink for fraud, and a weekly distributed batch for sessions. It names the gap that a timestamp filter leaves for deleted rows and closes it. Its Dag has no call to the current time, and running any day twice leaves the warehouse unchanged.

Hint 1

Start each need from the question of who acts on the data and how soon.

Hint 2

For need A, ask what a filter on updated_at returns for a row that no longer exists.

Hint 3

For need B, a retry by the publisher means the consumer sees the same transaction id twice.

Hint 4

For need C, estimate whether the data fits on one machine before choosing an engine.

Show solution

Need A: finance dashboard.

  • Cadence. Batch, once a day. The dashboard is read at 07:00 and shows the previous day, so a run at 04:00 leaves three hours of slack for retries. Nothing here needs streaming.
  • Order of steps. ELT. Copy the changed rows into a raw table in the warehouse and transform them there with SQL. The warehouse has the compute, and keeping the raw rows means a wrong revenue rule can be fixed and rebuilt without touching Postgres again.
  • What changed. Rows whose updated_at falls in the run's data interval, with a one-hour overlap for safety. That is about 150,000 rows instead of 80 million. The filter cannot see the hard-deleted voided orders, so add a step that compares primary keys with the source and removes orders that no longer exist there, or ask the customer for soft deletes or change data capture.
  • Load. Upsert into orders on order_id, guarded so that an older version never overwrites a newer one. Rebuild revenue_by_store by partition overwrite for every order date the batch touched.
  • Checks. order_id is unique and not null. Every store_id exists in the stores table. The day's revenue total in the warehouse equals the same total queried from Postgres.

Need B: fraud scoring.

  • Cadence. Streaming. Five seconds from event to score rules out a scheduled batch. A micro-batch engine with a trigger interval of about a second also meets it.
  • Order of steps. The transform runs in the stream processor, before the result is written, so this path is ETL-shaped. Land the raw events in cheap storage as well, for later analysis.
  • What changed. Every event is new. The consumer's position in the topic, saved with a checkpoint, marks what has been processed.
  • Load. Write scores with an upsert on the transaction id. The service republishes after a timeout, so the same transaction will arrive twice and must not be scored or stored twice. Per-card aggregates, such as spend in the last ten minutes, need event-time windows with a watermark because some events arrive late.
  • Checks. Validate each event against the schema and send failures to a dead-letter topic instead of stopping the stream. Alert when consumer lag exceeds the 5-second budget, and track the rate of duplicates.

Need C: weekly sessions.

  • Cadence. Batch, weekly.
  • Order of steps. The data is already loaded, raw, in object storage, so transform it where it lives with a cluster engine such as Spark. Two terabytes a week is beyond the single database server. Sessionising needs all of a visitor's events together and in time order, which is a shuffle by visitor id.
  • What changed. The week's folder of files.
  • Load. Partition overwrite of that week's output. An overwrite on file storage is not atomic, so write to a new path and switch the report over after the checks pass.
  • Checks. The number of events inside sessions equals the number of input events. The session count is within a sensible range of earlier weeks, and no visitor id is null.
