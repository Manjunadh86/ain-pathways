Finding and Publishing MCP Servers (the MCP Registry)

The MCP Registry is the official, community-run catalogue of publicly reachable Model Context Protocol servers. Each entry is a small server.json metadata record that names a server, says who may publish under that name and points to the package or URL where the server actually lives. The registry stores no server code.

1Overview

Why it matters

Running an MCP server from a client's configuration file works on your own machine. It does not tell anyone else where your server is, whether the name is really yours, or which command and environment variables it needs. Before a shared catalogue existed, servers were spread across many registries and repositories (the problem GitHub's launch post for its own registry describes), and a listing had no standard link to whoever controlled the name.

Three groups need to understand the registry. Server authors need it to make a server installable by name. People building clients, marketplaces or internal developer portals need to know that the official registry is a feed to curate from, not a vetted store. Anyone responsible for a team's agents needs to know what a listing proves (someone who controls a GitHub account or a domain published it) and what it does not prove (that the code is safe, maintained or free of vulnerabilities), because a local MCP server runs with the privileges of whoever starts it.

Key terms

MCP Registry
The official public catalogue at registry.modelcontextprotocol.io. It holds metadata about publicly accessible MCP servers and serves it through a REST API.
server.json
The JSON metadata format for one version of one server: its name, version, description and how to install or reach it.
Namespace
The part of a server name before the slash, written in reverse-DNS form such as io.github.alice or com.example. Only someone who proves control of the matching GitHub account or domain can publish under it.
Package registry
A service such as npm, PyPI, NuGet, crates.io or Docker Hub that hosts the actual code or container image. The MCP Registry points at packages there instead of storing them.
Remote server
An MCP server reached over the network at a public URL, rather than started as a process on the user's machine.
Aggregator
A downstream service, such as a server marketplace, that copies registry metadata on a schedule and adds value such as ratings or security scans.
Subregistry
An aggregator that also serves the official registry's OpenAPI interface, so that host applications can read it in the same way they would read the official one.
Private registry
An organisation's own catalogue of approved servers, ideally serving the same API so that existing host applications can read it.
Allow-list
A client or administrator policy naming the only servers that may start. Anything not listed is blocked.
mcp-publisher
The command-line tool that creates a server.json template, authenticates to the registry and publishes a version.

2Explanation

Introduction

In Building an MCP Server you wrote a server and started it from a client's configuration file. That is enough on your own machine. It does not answer the next questions: how does anyone else find your server, how do they know the name is really yours, and how do they learn the exact command and environment variables it needs?

Think of a package manager. npm hosts the code, but someone choosing a database connector still needs to know which package is the genuine one. The MCP Registry splits those jobs. Code stays in the package registry where it already lives (npm, PyPI, NuGet, crates.io, Docker Hub and similar). The registry holds a small metadata record, server.json, that gives the server a unique name, says where its package or URL is and describes how to run it. It is closer to a phone-book entry than to the building the entry lists.

The registry also ties each name to an owner. Names look like io.github.alice/weather or com.example/acme-analytics, and you can publish under a prefix only after proving that you control the matching GitHub account or domain. That is its main trust feature, and a limited one: it shows who published a record, not that the code behind it is safe.

Because the official registry is deliberately permissive about content, most people meet it through something else. Marketplaces and client applications copy its data and add curation, and companies run private registries and allow-lists of their own. This lesson covers the record, the publishing flow, the consuming side, private registries, and the judgement you still have to apply. The official documentation describes the registry as a preview, so endpoints and fields can change before general availability.

How it works

What a registry entry contains

A server.json record describes one version of one server. Its JSON schema (opens in a new tab) requires only name, description and version. The name must have the form namespace/server with exactly one slash and is 3 to 200 characters long. The description is limited to 100 characters. Everything else is optional, but a record is only useful if it also has packages, remotes or both. The record below is our illustration in the shape the documentation shows.

json
{
  "$schema": "https://static.modelcontextprotocol.io/schemas/2025-12-11/server.schema.json",
  "name": "io.github.alice/weather",
  "description": "Weather forecasts for MCP clients.",
  "version": "1.0.1",
  "repository": {"url": "https://github.com/alice/weather-mcp", "source": "github"},
  "packages": [{
    "registryType": "npm",
    "identifier": "@alice/weather-mcp",
    "version": "1.0.1",
    "transport": {"type": "stdio"},
    "environmentVariables": [{"name": "WEATHER_API_KEY", "isRequired": true, "isSecret": true}]
  }],
  "remotes": [{"type": "streamable-http", "url": "https://weather.example.com/mcp"}]
}

A package entry describes a local server: the package type, an exact version, the transport (usually stdio), and optional command-line arguments and environment variables, each of which can be flagged as a secret. A remote entry describes a hosted server: a public URL, a transport of streamable-http (sse only to serve existing clients, because the documentation calls it deprecated), optional {variable} placeholders in the URL and optional headers. Both can appear in one record, so that a host application can choose.

Namespaces and ownership checks

The part of the name before the slash is a namespace in reverse-DNS form. The login method you use decides which namespaces you may publish under:

GitHub (mcp-publisher login github, or github-oidc inside GitHub Actions)io.github.<user or org>/You control that GitHub account or organisation
DNSReverse-DNS of your domain, such as com.example/You can publish a TXT record holding your public key, and you sign in with the matching private key
HTTPSameYou can host your public key at /.well-known/mcp-registry-auth on the domain

The registry does not validate the MCPB hash; clients do. It also delegates security scanning to the package registries and to aggregators. Proving that you control a name is not the same as proving your code is safe.

Publishing a version

The registry only hosts metadata, so the package must exist first. The quickstart (opens in a new tab) order is: add the ownership proof to the package (for npm, an mcpName property in package.json), publish the package, install mcp-publisher, create server.json, log in, publish.

bash
mcp-publisher init            # writes a server.json template from your project
mcp-publisher login github    # prints a device code; approve it at github.com/login/device
mcp-publisher publish         # validates the record and stores this version
curl "https://registry.modelcontextprotocol.io/v0.1/servers?search=io.github.alice/weather"

Each version string must be unique and cannot be changed once published, so you correct metadata by publishing a new version. The registry recommends semantic versioning and rejects strings that look like ranges (^1.2.3, 1.x, >=1.2.3). It tries to parse each version as semver to decide which one is "latest": a version that does not parse is always marked latest, and a prerelease such as 1.2.3-1 published after 1.2.3 is not. The FAQ (opens in a new tab) says you currently cannot delete or unpublish a server. For continuous delivery, the GitHub Actions guide (opens in a new tab) uses mcp-publisher login github-oidc with the id-token: write permission, so the registry login needs no dedicated secret.

Reading the registry

The official registry has an unauthenticated, read-only REST API at https://registry.modelcontextprotocol.io:

  • GET /v0.1/servers lists servers. The registry's OpenAPI specification (opens in a new tab) gives it limit (default 30, maximum 100), cursor, updated_since (an RFC 3339 timestamp), search (a substring match on the name), version (latest or an exact version) and include_deleted.
  • GET /v0.1/servers/{serverName}/versions lists the versions of one server.
  • GET /v0.1/servers/{serverName}/versions/{version} returns one version, and latest is accepted.

Path parameters must be URL-encoded, so io.modelcontextprotocol/everything becomes io.modelcontextprotocol%2Feverything. In the live responses we read, and in the specification, each entry holds a server object beside a _meta object whose io.modelcontextprotocol.registry/official key carries registry-set facts: status (active, deprecated or deleted), isLatest and timestamps such as publishedAt and updatedAt. Version metadata is immutable except status. A plain list leaves deleted servers out unless include_deleted is set, but the specification says deleted servers are always included when updated_since is given, which is how an incremental sync learns about takedowns.

The documentation says the official registry is meant for aggregators, which are expected to copy it on a regular but infrequent schedule (hourly is the example) into their own store. The registry gives no uptime or data durability guarantees. Host applications should not read it directly; they should read marketplaces or other registries that follow its OpenAPI specification. An aggregator that serves that specification is a subregistry, and it can add its own data (ratings, download counts, scan results) under a key of its own in _meta.

Private registries and allow-lists

The official registry does not accept private servers, such as ones on mcp.acme-corp.internal or behind a private package registry. Its documentation recommends hosting your own registry for those, and notes that a private registry can implement the same OpenAPI specification so that existing host applications can read it.

An allow-list is the client-side counterpart: only listed servers may start. Clients differ in what they match. GitHub's "Registry only" Copilot policy compares server names or IDs with a registry. Claude Code has no built-in registry to browse. Its allowedMcpServers and deniedMcpServers (opens in a new tab) settings filter servers that are already configured, and an entry can match a serverName, an exact serverCommand or a serverUrl pattern with * wildcards. Its documentation says a serverName entry is not a security control, because the name is only a label the user chooses. A server that matches any deny entry is blocked, and the allow-list is authoritative only when an administrator sets allowedMcpServers together with allowManagedMcpServersOnly in a managed settings source, because otherwise allow-lists from a user's own settings merge in. Matching on a name alone is the weaker design, as the examples below show.

Deciding whether to trust a listing

The moderation policy (opens in a new tab) says the registry removes illegal content, malware, spam and non-functioning servers. It will not remove low-quality servers, buggy ones or ones with security vulnerabilities, and it tells consumers to assume minimal-to-no moderation. A listing is a starting point, and the decision is yours:

  1. Who published it? Read the namespace. io.github.alice/ means a GitHub account; com.vendor/ means someone who controls that domain. Check that the repository link belongs to the owner you expect. This is our rule of thumb, not a registry guarantee.
  2. What will run? A package entry runs code on your machine with your privileges. The MCP security guidance (opens in a new tab) warns that local servers can execute arbitrary commands and says a client that offers one-click setup must show the exact command before running it. A remote entry runs on someone else's server and receives whatever you send it.
  3. Is it pinned? Records name an exact package version, and an OCI identifier can use a digest instead of a tag. Keep the pin and review upgrades.
  4. What can it reach? Give it the narrowest token you can and sandbox it where the client allows. See Code Execution and Sandboxing and Agent Identity, Permissions and Least Privilege.
  5. Does it keep behaving? In September 2025 a CSO Online report (opens in a new tab) described an npm package named postmark-mcp that impersonated the genuine Postmark MCP server and, from version 1.0.16, silently added a hidden BCC to every email it sent. The article does not say the package was listed in the MCP Registry. The point is that a name check at publish time says nothing about what a later version does; see Prompt Injection and LLM Security for the related risk of untrusted tool descriptions.

Worked example: Check a server.json before publishing, then sync a registry feed the way an aggregator does

This example has two halves and needs only Python 3.9 or later, with no network access. Part 1 imitates the local checks you want to pass before running mcp-publisher publish. Part 2 imitates what an aggregator does with the list endpoint. The rules in Part 1 are our approximation of the documented ones, and the registry's own validator is authoritative. The records in Part 2 are fixtures we wrote in the shape the live API returns: a server object beside a _meta object. A plain live list leaves deleted servers out unless include_deleted is set, while a list filtered with updated_since includes them, so the fixture contains one to exercise the status filter.

Part 1: check a record before publishing

Save this as check_server.py. The record follows the quickstart's weather server and keeps its placeholder names, and the package declares mcpName, which npm packages must carry.

python
import re

NAME_RE = re.compile(r"^[a-zA-Z0-9.-]+/[a-zA-Z0-9._-]+$")
RANGE_RE = re.compile(r"^[\^~<>=]|(^|\.)[xX*](\.|$)|\s-\s|\|\|")


def check(server, package_json, github_user):
    problems = []
    for field in ("name", "description", "version"):
        if not server.get(field):
            problems.append(f"missing required field: {field}")
    name = server.get("name", "")
    if not (3 <= len(name) <= 200 and NAME_RE.match(name)):
        problems.append(f"name {name!r} breaks the schema pattern")
    if not name.startswith(f"io.github.{github_user}/"):
        problems.append(f"GitHub login needs the prefix io.github.{github_user}/")
    if RANGE_RE.search(server.get("version", "")):
        problems.append(f"version {server['version']!r} looks like a range")
    for package in server.get("packages", []):
        if package["registryType"] == "npm" and package_json.get("mcpName") != name:
            problems.append(f"mcpName {package_json.get('mcpName')!r} must equal {name!r}")
    return problems


server = {"name": "io.github.my-username/weather", "version": "1.0.1",
          "description": "An MCP server for weather information.",
          "packages": [{"registryType": "npm", "identifier": "@my-username/mcp-weather-server",
                        "version": "1.0.1", "transport": {"type": "stdio"}}]}
pkg = {"mcpName": "io.github.my-username/weather"}
cases = {"valid": (server, pkg),
         "no mcpName": (server, {}),
         "version range": ({**server, "version": "^1.0.1"}, pkg),
         "wrong namespace": ({**server, "name": "com.example/weather"}, pkg)}
for label, (srv, package_json) in cases.items():
    print(f"{label:16}", check(srv, package_json, "my-username") or "OK")

Expected output:

text
valid            OK
no mcpName       ["mcpName None must equal 'io.github.my-username/weather'"]
version range    ["version '^1.0.1' looks like a range"]
wrong namespace  ['GitHub login needs the prefix io.github.my-username/', "mcpName 'io.github.my-username/weather' must equal 'com.example/weather'"]

Each failure maps to a documented rule: the package must carry the server name, ranges are rejected, and a GitHub login only unlocks io.github.<you>/. The last case fails twice because changing the name in server.json also breaks the match with mcpName.

Part 2: sync a feed like an aggregator

Save this as sync.py. It walks two pages with a cursor, keeps only the latest version of each server and drops servers whose status is deleted.

python
from urllib.parse import quote

OFFICIAL = "io.modelcontextprotocol.registry/official"


def record(name, version, status="active", is_latest=True):
    return {"server": {"name": name, "version": version},
            "_meta": {OFFICIAL: {"status": status, "isLatest": is_latest}}}


PAGES = {None: {"servers": [record("io.github.alice/weather", "1.0.0", is_latest=False),
                            record("io.github.alice/weather", "1.0.1"),
                            record("com.example/acme-analytics", "2.0.0")],
                "metadata": {"count": 3, "nextCursor": "com.example/acme-analytics:2.0.0"}},
         "com.example/acme-analytics:2.0.0": {
             "servers": [record("io.github.bob/fixed-reply", "0.0.1", status="deleted"),
                         record("io.github.carol/notes", "0.3.0", status="deprecated")],
             "metadata": {"count": 2}}}

index, cursor, seen = {}, None, 0
while True:
    print("GET /v0.1/servers?limit=3" + (f"&cursor={cursor}" if cursor else ""))
    page = PAGES[cursor]
    for entry in page["servers"]:
        seen += 1
        meta = entry["_meta"][OFFICIAL]
        if meta["isLatest"] and meta["status"] != "deleted":
            index[entry["server"]["name"]] = (entry["server"]["version"], meta["status"])
    cursor = page["metadata"].get("nextCursor")
    if cursor is None:
        break
print(f"read {seen} records, indexed {len(index)}")
for name, (version, status) in sorted(index.items()):
    print(f"  {name} {version} [{status}]")
print(quote("io.modelcontextprotocol/everything", safe=""))

Expected output:

text
GET /v0.1/servers?limit=3
GET /v0.1/servers?limit=3&cursor=com.example/acme-analytics:2.0.0
read 5 records, indexed 3
  com.example/acme-analytics 2.0.0 [active]
  io.github.alice/weather 1.0.1 [active]
  io.github.carol/notes 0.3.0 [deprecated]
io.modelcontextprotocol%2Feverything

Five records came from two pages. The old weather version 1.0.0 is skipped because it is not the latest, and fixed-reply is skipped because its status is deleted, the status the moderation policy sets when it removes a server. The deprecated server is kept but carries its status, so a marketplace can show a warning. A real aggregator would persist the index and, as the documentation suggests, repeat the sync only occasionally.

Edge cases and limitations

The registry is a preview and says so
Each registry documentation page we read carries a note that breaking changes or data resets may occur before general availability, and the aggregator guide states that there are no uptime or durability guarantees. Aggregators and private registries should therefore keep their own copy of the data, pin to the /v0.1 paths, and expect to adapt. Re-check the documentation before relying on a field.
Private servers do not belong in the official registry
Servers on a private network or behind a private package registry are explicitly unsupported, and a record is public to everyone who calls the API. Host your own registry for internal servers. Be careful with the self-hosting advice you find: the MCP documentation says the official registry codebase is not designed for self-hosting and cannot be supported, while GitHub's Copilot documentation lists forking it among hosting options. Choosing to fork means you operate it yourself.
Latest does not always mean highest
The registry parses versions as semver where it can. A version that does not parse is always marked latest, even after semantic versions, and a prerelease such as 1.2.3-1 published after 1.2.3 does not become latest. Mixing version styles, or using a prerelease for a registry-only metadata fix, can leave consumers on a surprising version, so choose one scheme and keep it.
Removal is a status change, not a deletion
The FAQ says publishers currently cannot delete or unpublish a server. When maintainers remove a server for spam, malware or illegality they set its status to deleted, and the metadata normally stays readable through the API. In extreme cases, such as unlawful metadata, the moderation policy allows it to be overwritten or erased. A plain list leaves deleted servers out unless include_deleted is set, but an updated_since query always includes them. Anything that copies the registry must read the status field on every sync, or it will keep advertising servers that were taken down.
A verified name can still front unsafe code
Namespace authentication proves control of an account or domain, and package checks prove that the package names the server. Neither inspects behaviour, and the registry does not remove buggy servers or ones with vulnerabilities. For MCPB bundles the registry does not even validate the SHA-256 hash; the clients do. Treat the checks as identity evidence only.
Name-based allow-lists can be sidestepped
GitHub's documentation states that its registry enforcement matches only on server name or ID, that a user can edit local configuration files to get round it, and that strict prevention of non-registry installs is not available yet. Claude Code's documentation likewise says a serverName entry is not a security control, because the name is only a label the user assigns. Matching on the command or URL a server actually uses, and distributing settings from a managed location, closes more of the gap.

When to use it, and when something simpler is enough

Use it when

  • You publish a public MCP server, open or closed source, and want clients and marketplaces to find it under a name you can prove you own.
  • You build a client, marketplace or internal developer portal and need a machine-readable list of public servers to copy and curate.
  • An organisation wants one reviewed list of servers that developer tools can read and enforce, which means a private registry plus an allow-list.

Think twice when

  • The server is reachable only inside a private network or through a private package registry, because the official registry does not accept it.
  • You want a listing to act as a security approval. The official registry assumes minimal-to-no moderation, so a listing says nothing about safety.
  • Your host application would query the official registry directly in production. Read an aggregator or your own registry instead.

A simpler alternative. For one team and a handful of servers, a version-controlled project file such as .mcp.json or .vscode/mcp.json that lists the exact commands is usually enough, and it pins what actually runs. Move to a registry when many people need to find servers, when you publish for strangers, or when a policy has to be enforced centrally.

Key takeaways

  • The MCP Registry stores metadata, not code. A server.json record names a server and points to a package or a public URL that lives elsewhere.
  • Names are reverse-DNS and tied to proof of control. A GitHub login unlocks io.github.<user>/, DNS or HTTP proof unlocks a domain prefix, and each package type has its own ownership check.
  • Published versions are immutable, ranges are rejected and servers cannot be deleted, so a mistake is corrected by publishing a new version.
  • The official registry is a preview feed for aggregators and subregistries. Host applications should read those, or a private registry that serves the same API.
  • A listing proves who published a server, not that its code is safe, and moderation is minimal. Check the owner, read the command, pin versions, sandbox and enforce an allow-list where it matters.
  • Allow-lists that match only a name can be bypassed, so prefer rules that check the command or URL and settings that the user cannot edit.

Example 1 of 5

GitHub lists its own MCP server in the official registry as both a container and a remote endpoint

GitHubDocumented in official docs

The live record for io.github.github/github-mcp-server in the official registry's API, read on 2026-10-11, together with the registry's authentication, package-type, remote-server and FAQ pages that explain each field of such a record. [13][3][4][5][9]

The problem

GitHub's MCP server can be used in two ways: run locally from a container image, or reached at a hosted endpoint. Clients and marketplaces need both options, a name they can recognise as GitHub's, and a warning about the secret the user must supply, all in one machine-readable place. Without a registry, GitHub would have to publish separate install instructions for every client.

Where this topic fits

The record is the registry entry itself. The name uses the GitHub-authenticated namespace for the github organisation, packages carries the container image, and remotes carries the hosted URL. An aggregator or client reads the record through the list or versions/latest endpoint.

How it is applied, step by step

  1. The record's name starts with io.github.github/, the form the authentication documentation reserves for publishers who log in with GitHub for the account or organisation named github.
  2. The packages entry gives the local option: an OCI image on GitHub Container Registry at an exact tag, run over stdio. For OCI images the registry checks that the image carries an annotation equal to the server name, which binds the image to the name.
  3. The remotes entry gives the hosted option: a Streamable HTTP endpoint. Its Authorization header is marked secret, so a client knows to ask the user for a token and to treat it as sensitive.
  4. A client or marketplace reads the record from the list or versions/latest endpoint and chooses one option: the container for a local setup or the URL for a hosted one.
  5. Each release is a new immutable version. The record we read listed 2.0.2 as the latest, and earlier versions remain available as separate records.

Why this approach fits

One record serves two audiences without GitHub maintaining a separate guide for each client. Because the registry stores only metadata, GitHub keeps its image on its own container registry and its endpoint on its own domain, and the reverse-DNS name lets a client see at a glance which account published the entry.

Limitation or tradeoff

The record says where the code is and how to call it. It does not show that the image is safe, that the hosted endpoint behaves as described, or what scopes a user's token should carry. Values such as the version, tag and runtime arguments change with each release, so a client should read the latest record rather than copy values from a document, and the page you fetch today may differ from the one we read.

What the sources document

  • The live registry record for io.github.github/github-mcp-server, read on 2026-10-11, listed version 2.0.2 as the latest active version, with an OCI package at ghcr.io/github/github-mcp-server:2.0.2 using stdio transport and a streamable-http remote at https://api.githubcopilot.com/mcp/. [13]
  • The remote entry in that record declares an Authorization header marked secret, described as taking a personal access token or an app token. [13]
  • With GitHub-based authentication a server name must take the form io.github.username/* or io.github.orgname/*. [3]
  • Docker and OCI images are verified through an io.modelcontextprotocol.server.name annotation that must match the server name, and ghcr.io is one of the supported OCI registries. [4]
  • A record may carry both remotes and packages so that host applications can choose how to install, and a publisher changes metadata by submitting a new server.json under a new, unique version because published version metadata is immutable. [5][9]

The facts above come from the cited sources. The steps and analysis in this example are our explanation of how they fit together.

Example 2 of 5

The GitHub MCP Registry adds curation and one-click install on top of the community registry

GitHubDocumented in an engineering article

GitHub's September 2025 launch post for the GitHub MCP Registry, the VS Code documentation for installing servers from the @mcp gallery and for MCP server trust, and the MCP Registry's own moderation policy and preview announcement, which describe the division of labour between the official registry and downstream catalogues. [15][16][8][14]

The problem

GitHub describes MCP servers as scattered across many registries, repositories and community threads, so a developer working in an editor had no single place to find a server, see how widely it was used and install it. The official registry is deliberately unopinionated metadata, so something downstream had to supply the curation and the one-click experience.

Where this topic fits

The registry's moderation policy names the GitHub MCP Registry as a downstream subregistry. In GitHub's account it sits between the community registry that authors publish to and the editor that developers use, adding an ordering by stars and activity and an install path, while authors publish only once.

How it is applied, step by step

  1. GitHub's September 2025 post says developers would be able to self-publish servers to the OSS MCP Community Registry, the registry this lesson covers, proving namespace ownership as in the publishing flow above.
  2. GitHub's registry launched with a curated directory of servers from partners and the open source community, each backed by its GitHub repository and sorted by GitHub stars and community activity. The post says servers published to the community registry would then appear in GitHub's registry automatically.
  3. In VS Code, entering @mcp in the Extensions view lists the servers in its MCP server gallery. 4Common mistakes

  1. Treating a registry listing as proof that a server has been reviewed and is safe

    Why it causes problems
    The official registry authenticates namespaces and removes only illegal content, malware, spam and non-functioning servers. It keeps servers that are buggy or have known vulnerabilities, and it assumes consumers will do their own checking. A team that installs whatever is listed runs unreviewed code with the user's privileges.
    How to recognise it
    Nobody can say who approved a given server, or the install instructions simply say to pick it from the registry. There is no allow-list, no pinned version and no record of the command that is run.
    How to fix it
    Make the listing the first step, not the last. Check the owner and repository, read the run command, pin the version, sandbox the server and give it narrow credentials. For a team, add a reviewed allow-list that checks the command or URL.

  2. Publishing server.json before the package carries the matching ownership proof

    Why it causes problems
    The registry checks that the package names the server: mcpName for npm, an mcp-name string in the README for PyPI, NuGet and Cargo, an image annotation for OCI. If the proof is missing or differs from the name in server.json, publishing fails with a package validation error, and a proof added later requires a new package release first.
    How to recognise it
    mcp-publisher publish reports that registry validation failed for the package, or says you lack permission for the server name because the name prefix does not match the login method.
    How to fix it
    Add the proof, publish the package, then publish the record. Make the name in server.json equal the proof character for character, and use the prefix that fits your login: io.github.<user>/ for GitHub, or your reversed domain for DNS or HTTP.

  3. Reusing a version number, or putting a range such as ^1.2.0 in the version field

    Why it causes problems
    Published versions are immutable and each version string must be unique, so a second publish of the same string fails. Version ranges are rejected on purpose. A scheme that does not parse as semver is always marked latest, which can leave consumers on the wrong version.
    How to recognise it
    The publisher rejects the version, or the registry's latest version is not the one you expect. Consumers report seeing old metadata after you fixed a typo.
    How to fix it
    Publish every correction as a new version. Use semantic versioning and keep the server version aligned with the package version. The documentation suggests prerelease suffixes such as 1.2.3-1 for repeated registry-only updates, but a prerelease published after 1.2.3 is not marked latest, so once 1.2.3 is out, publish a higher version instead.

  4. Pointing production tooling at the official registry and polling it often

    Why it causes problems
    The official registry is a preview with no uptime or durability guarantees, and data resets are possible. A product that queries it on every start-up inherits those failures, and frequent polling goes against the guidance for aggregators.
    How to recognise it
    Client start-up depends on a call to registry.modelcontextprotocol.io, or logs show many requests per hour from one service. Servers disappear from your catalogue after a reset.
    How to fix it
    Sync on a schedule such as hourly into your own store, using updated_since and cursors, and have clients read your copy. Persist the status field and refresh it on every sync.

  5. Enforcing an allow-list by server name alone

    Why it causes problems
    A name is just a label in a configuration file. GitHub's documentation says its registry enforcement matches only on name or ID and can be bypassed by editing configuration, so a developer can point an approved name at a different command or URL.
    How to recognise it
    A developer's local configuration uses an approved name but runs an unexpected command or contacts an unexpected host, and nothing was blocked.
    How to fix it
    Match on the command or URL as well, for example with serverCommand and serverUrl rules, and deliver the policy through managed settings that users cannot edit (in Claude Code, set allowManagedMcpServersOnly with the allow-list). Audit local configurations from time to time.

Exercise 1

Survey the live registry the way an aggregator would

CodingIntermediateAbout 30 min (estimate)

Write a Python 3 script, using only the standard library, that reads at most three pages of the official registry's list endpoint and summarises what it finds. It needs internet access and no account.

Each page comes from GET https://registry.modelcontextprotocol.io/v0.1/servers?limit=100, with an extra cursor parameter for pages after the first. The JSON holds a servers list whose entries look like {"server": {...}, "_meta": {...}}, and a metadata object that contains nextCursor while more pages exist. The registry-set facts are under _meta["io.modelcontextprotocol.registry/official"], which has status and isLatest.

Report: pages read, records read, records kept after filtering, the number of distinct namespaces and the three namespaces with the most servers, how many kept servers have remotes only, packages only, both or neither, and a count of the registryType values across their packages.

Requirements

  • Use only the standard library and build the query string with urllib.parse.urlencode.
  • Read at most three pages in one run, with no retry loop, and stop earlier when nextCursor is missing.
  • Keep a record only when isLatest is true and status is not deleted.
  • On a network or HTTP error, or an unexpected response shape, exit with a one-line message instead of a traceback.
  • The four server-shape counts must add up to the number of kept records.

Expected behaviour

The script prints a pages/records line, a namespace line, one line for each server shape and a dictionary of registryType counts. The numbers change from day to day because the registry changes, so do not compare them with anyone else's. What must hold is that the shape counts sum to the kept count and that the kept count is no larger than the records read.

Hint 1

The official metadata is the value of the key "io.modelcontextprotocol.registry/official" inside each entry's _meta object.

Hint 2

Not every server has a remotes or packages key, so use server.get("remotes") and server.get("packages", []).

Hint 3

The namespace is everything before the slash in the name, and Counter.most_common(3) gives the top three.

Hint 4

urllib.error.URLError also covers HTTPError, and json.JSONDecodeError is a kind of ValueError.

Show solution
python
import json
import sys
import urllib.error
import urllib.parse
import urllib.request
from collections import Counter

BASE = "https://registry.modelcontextprotocol.io/v0.1/servers"
OFFICIAL = "io.modelcontextprotocol.registry/official"
PAGE_SIZE, MAX_PAGES = 100, 3


def get_page(cursor):
    query = {"limit": PAGE_SIZE, **({"cursor": cursor} if cursor else {})}
    request = urllib.request.Request(f"{BASE}?{urllib.parse.urlencode(query)}",
                                     headers={"Accept": "application/json"})
    with urllib.request.urlopen(request, timeout=30) as response:
        return json.load(response)


def survey():
    namespaces, shapes, types = Counter(), Counter(), Counter()
    read = kept = pages = 0
    cursor = None
    while pages < MAX_PAGES:
        page = get_page(cursor)
        pages += 1
        for entry in page["servers"]:
            read += 1
            meta, server = entry["_meta"][OFFICIAL], entry["server"]
            if not meta["isLatest"] or meta["status"] == "deleted":
                continue
            kept += 1
            namespaces[server["name"].split("/")[0]] += 1
            shapes[(bool(server.get("remotes")), bool(server.get("packages")))] += 1
            types.update(p["registryType"] for p in server.get("packages", []))
        cursor = page["metadata"].get("nextCursor")
        if not cursor:
            break
    return pages, read, kept, namespaces, shapes, types


try:
    pages, read, kept, namespaces, shapes, types = survey()
except (urllib.error.URLError, TimeoutError, KeyError, ValueError) as error:
    sys.exit(f"registry survey failed: {error}")

print(f"pages {pages}, records read {read}, kept {kept}")
print("distinct namespaces:", len(namespaces), "| top:", namespaces.most_common(3))
for (has_remote, has_package), count in sorted(shapes.items()):
    print(f"remotes={has_remote!s:5} packages={has_package!s:5} -> {count}")
print("registryType counts:", dict(types))

The loop is the same cursor walk as in the worked example, with a hard page cap so that the script behaves like a polite aggregator. Filtering on isLatest and status mirrors what an index should do, and the shape counts reconcile because every kept record falls into exactly one of the four combinations.

When we ran a version of this on 2026-10-11, the first pages appeared to be ordered by name, so the sample was dominated by names that start early in the alphabet. Do not draw conclusions about the whole registry from three pages. To estimate how common each package type is, you would have to read every page, which is the job of a scheduled sync and not of an ad-hoc script.

Check your answer

  • Does the script stop after three pages even though nextCursor is still present?
  • Do the remotes-only, packages-only, both and neither counts add up to the kept count?
  • Does a network failure produce a one-line message and a non-zero exit status?
  • Can you explain why the numbers from the first three pages should not be generalised to the whole registry?

Exercise 2

Design the MCP server controls for a 200-developer company

DesignIntermediateAbout 45 min (estimate)Hypothetical scenario

Northwind Logistics is an invented company with 200 developers who use VS Code with GitHub Copilot and Claude Code. Security wants three things:

  • Developers may use GitHub's hosted MCP server at https://api.githubcopilot.com/mcp/ and an internal orders server at https://mcp.northwind.example/orders/mcp.
  • Every other MCP server is blocked until it has been reviewed.
  • A request for a new server gets a yes or no within five working days.

Write a short design that covers the registry, the Copilot policy, the Claude Code settings, the review checklist and the ways the controls can be bypassed.

Requirements

  • Say which registry you would host and why the official registry cannot hold the internal server.
  • Write the record for the internal server in server.json form, valid under the schema's name and description rules.
  • Write Claude Code allowedMcpServers settings that use only serverName, serverCommand and serverUrl, with wildcard patterns where needed, and say how the list is kept from being widened in user settings.
  • State the Copilot policy you would set, and what GitHub's documentation says about the limits of that enforcement.
  • Give a review checklist of six to eight items, each tied to a field or fact that a registry record or the server's repository can show.
  • Describe two ways a developer could get round the controls and how you would detect or close each one.

Expected behaviour

A coherent design in which the internal server lives in a private registry, the allow-list is enforced at both clients, and the document is honest about what name-based enforcement cannot stop. Every control traces to something the documentation says.

Hint 1

The official registry does not accept servers that are reachable only inside a private network, and private registries can implement the same API.

Hint 2

A reversed domain makes a good namespace for the internal record. For northwind.example it would begin with example.northwind.

Hint 3

Hint 4

GitHub says its enforcement matches on name or ID and recommends managed-settings.json for stronger control.

Hint 5

Show solution

Registry. Host a private registry that serves the v0.1 list and version endpoints with the required CORS headers, for example Azure API Center (managed) or a small service you run. GitHub's September 2025 changelog also described a static JSON file over HTTPS, but its current configuration page asks for the three v0.1 endpoints, so test the exact paths your editors request. The official registry cannot hold the internal server, because it does not accept servers reachable only on a private network. The registry contains two entries: a copy of the GitHub record and the internal one.

json
{
  "$schema": "https://static.modelcontextprotocol.io/schemas/2025-12-11/server.schema.json",
  "name": "example.northwind/orders",
  "description": "Order lookup for support agents.",
  "version": "1.2.0",
  "remotes": [{"type": "streamable-http", "url": "https://mcp.northwind.example/orders/mcp"}]
}

The name has one slash, matches the schema pattern, and the 32-character description is under the 100-character limit.

Copilot. Upload the registry URL in the enterprise policy and set Registry only. Because GitHub says this enforcement is name or ID based and can be bypassed by editing configuration files, treat it as a guardrail and also define restrictions in the enterprise managed-settings.json file, which GitHub recommends. GitHub also says URL-based enforcement that users cannot override locally is available through the enterprise allowlist.

Claude Code. Because an allow-list is present, any server that matches no entry is filtered out, including stdio servers.

json
{
  "allowManagedMcpServersOnly": true,
  "allowedMcpServers": [
    {"serverUrl": "https://api.githubcopilot.com/*"},
    {"serverUrl": "https://mcp.northwind.example/orders/*"}
  ]
}

Deliver it through a managed settings source, not through user files. Without allowManagedMcpServersOnly, allow-lists from each developer's own settings merge with yours, so a developer could widen the list. That lock is a separate setting and not one of the three matching keys. Claude Code v2.1.259 or later can also provide the orders server to every user through the managedMcpServers setting, whose entries load without an allow-list entry, so that developers do not configure it themselves.

Review checklist for a new server request.

  1. Owner: the namespace and repository belong to the party the requester says they do.
  2. Kind: package or remote, and for a package the exact command that will run.
  3. Pin: an exact version or image digest, not a moving tag.
  4. Secrets: every environment variable or header marked secret, each with the narrowest scope.
  5. Data: what leaves the machine, and where the remote operator is located.
  6. Maintenance: recent releases, an issue tracker and a named person who will re-review upgrades.
  7. Isolation: whether it can run in a container or sandbox with limited filesystem and network access.

Bypasses. First, a developer edits a local configuration file so that an approved name points at a different command. The name-only match passes, so close it with the Claude Code URL and command rules and managed settings, and audit local configuration files periodically. Second, a developer uses a client that does not read either policy. Close it by keeping an inventory of approved clients and by allowing outbound connections only to approved MCP hostnames at the network proxy, which also catches new remote servers.

  • Is every Claude Code rule built only from serverName, serverCommand or serverUrl?
