Advanced Retrieval (Hybrid Search, Reranking, Query Rewriting)

Advanced retrieval is the set of techniques added around basic vector search in a RAG system: running keyword (BM25) search next to vector search and merging the results, reordering candidates with a reranker, rewriting or expanding the query, restricting results with metadata filters, and adding document context to chunks before they are indexed.

1Overview

Why it matters

A RAG system can only answer from the chunks that retrieval hands to the model. Basic vector search fails in a few recognisable ways. It misses exact strings such as error codes, part numbers and surnames. It returns the right paragraph from the wrong year, product version or customer. It ranks the useful chunk fourteenth when only five are sent to the model. It searches on a follow-up such as "and for the EU?" that means nothing without the earlier conversation. In each case the model then answers from poor evidence, and the answer looks fluent anyway.

Each of those failures has a specific fix, and each fix has a price in latency, money or operational work. Engineers who build or debug RAG systems need to read a retrieval trace, name the failure and add only the stage that addresses it. Teams that skip the diagnosis tend to bolt on every technique at once, pay the latency and cost of all of them, and still cannot say which stage helped.

Key terms

BM25
A keyword scoring function that rewards chunks containing the query's words, giving more weight to rare words and adjusting for repeated words and chunk length.
Dense retrieval
Search that compares an embedding vector of the query with embedding vectors of the chunks. It is also called vector search or semantic search.
Hybrid search
Running keyword search and vector search for the same query and merging the two ranked lists into one.
Reciprocal rank fusion (RRF)
A way to merge ranked lists that gives each item 1 divided by (k plus its rank) from every list it appears in and sorts by the total.
Reranker
A model that takes the query and a shortlist of candidate chunks and returns the candidates in a better order, usually with a relevance score for each.
Cross-encoder
A model that reads the query and one candidate text together in a single pass and outputs a relevance score. Most rerankers are cross-encoders.
Query rewriting
Using a model to turn what the user typed, plus any conversation history, into a standalone query that searches well.
Query expansion
Searching with several queries derived from the original, such as rephrasings, sub-questions or a hypothetical answer, and merging the results.
Metadata filter
A condition on fields stored with each chunk, such as tenant, product version or date, that a chunk must satisfy to be returned at all.
Contextual retrieval
Prepending a short, model-written description of where a chunk sits in its document to the chunk before it is embedded and keyword-indexed.

2Explanation

Introduction

In Retrieval-Augmented Generation you built the basic pipeline: split documents into chunks, embed them, and at question time fetch the chunks whose vectors lie closest to the question's vector. Chunking and Document Ingestion covered how to produce good chunks. That baseline works when the question and the answer use similar language. This lesson is about the queries where it does not.

Think about how you find a file on your own laptop. Sometimes you remember an exact fragment, such as invoice_2291, and a literal text match finds it at once. Sometimes you only remember what it was about ("the budget thing Priya sent in spring"), and literal matching is useless. You also narrow the search without thinking about it: only PDFs, only this year. And when the list of hits is long, you read the first few properly before opening one. Each habit has a counterpart in a retrieval pipeline:

  • Hybrid search runs a keyword search (BM25) next to the vector search and merges the two result lists, so exact terms and paraphrases are both covered.
  • Reranking has a slower, more accurate model read the best candidates and reorder them.
  • Query rewriting and expansion turn what the user typed into one or more queries that search well.
  • Metadata filters restrict the search to chunks with the right product, date, owner or permission.
  • Contextual retrieval repairs the chunks themselves by adding a sentence or two of document context to each one before it is indexed.

The evidence that the baseline has blind spots comes from teams that run search for real users. When Stack Overflow described how it was implementing semantic search (opens in a new tab), its engineers wrote that semantic search does worse on short queries of two or three words and when someone looks for a specific error code or unique keyword, and they required a vector database that could run lexical and semantic search over the same data. Anthropic gives a concrete case of the same weakness: for a query about one particular error code, an embedding model finds text about error codes in general and can miss the exact match that BM25 finds.

None of these techniques is free. Each adds latency, cost or another index to maintain. The lesson therefore pairs every technique with the failure it fixes and with what it costs. The worked example builds a small hybrid search in plain Python so that you can check every number yourself.

How it works

Two retrievers with opposite blind spots

Vector search, also called dense retrieval, compares the embedding of the query with the embedding of each chunk (see Embeddings). It matches meaning, so "cannot download my bills" can find a chunk about "invoice export". It is weak on tokens that carry little meaning for the model, such as part numbers, error codes and rare names.

Keyword search matches literal tokens. Its standard scoring function is BM25. For a query QQQ and a chunk DDD:

score(D,Q)=∑t∈QIDF(t)⋅f(t,D) (k1+1)f(t,D)+k1(1−b+b ∣D∣avgdl)\text{score}(D, Q) = \sum_{t \in Q} \text{IDF}(t) \cdot \frac{f(t, D)\,(k_1 + 1)}{f(t, D) + k_1\left(1 - b + b\,\frac{|D|}{\text{avgdl}}\right)}score(D,Q)=t∈Q∑​IDF(t)⋅f(t,D)+k1​(1−b+bavgdl∣D∣​)f(t,D)(k1​+1)​

Here f(t,D)f(t, D)f(t,D) counts how often term ttt occurs in the chunk, ∣D∣|D|∣D∣ is the chunk's length in tokens and avgdl is the average chunk length. The formula combines three ideas:

  • IDF (inverse document frequency) gives rare terms more weight. Lucene and Elasticsearch use ln⁡(1+N−nt+0.5nt+0.5)\ln\left(1 + \frac{N - n_t + 0.5}{n_t + 0.5}\right)ln(1+nt​+0.5N−nt​+0.5​), where NNN is the number of chunks and ntn_tnt​ is the number that contain the term.
  • Saturation (k1k_1k1​, 1.2 by default in Elasticsearch): the fifth occurrence of a word adds much less than the first.
  • Length normalisation (bbb, 0.75 by default): a long chunk needs more occurrences to earn the same score as a short one.

BM25 is exact about E-4012 and blind to synonyms. The two retrievers miss different things, which is the reason to run both.

Fusing two ranked lists

The two scores cannot simply be added. Azure AI Search's documentation lists BM25 scores as having no upper limit, while its cosine scores fall between 0.333 and 1.00. The most common fix ignores the scores and uses ranks. Reciprocal rank fusion (RRF) gives each chunk

RRF(d)=∑r∈R1k+rankr(d)\text{RRF}(d) = \sum_{r \in R} \frac{1}{k + \text{rank}_r(d)}RRF(d)=r∈R∑​k+rankr​(d)1​

summed over every ranked list rrr in which the chunk appears, where rank 1 is the best. With k=60k = 60k=60, a chunk ranked 1st in one list and 2nd in the other scores 1/61+1/62=0.03251/61 + 1/62 = 0.03251/61+1/62=0.0325. A chunk ranked 1st in one list and absent from the other scores 1/61=0.01641/61 = 0.01641/61=0.0164. Agreement between retrievers beats one high rank.

The constant kkk sets how much. The original RRF paper (opens in a new tab) fixed k=60k = 60k=60 during a pilot study, found it near-optimal and reported that the choice was not critical. Elasticsearch defaults its rank_constant to 60, and Azure AI Search's documentation names 60 as a good value. Qdrant counts ranks from 0 and defaults its constant to 2, which equals k=1k = 1k=1 in the formula above. A small kkk lets the top of each list dominate, as the plot shows.

Engines also let you tilt the balance between retrievers. Weaviate's default method, relativeScoreFusion, rescales each score list so that its best score is 1 and its worst is 0, then mixes the two with a weight alpha (0 is keyword only, 1 is vector only, 0.75 is the server default, though Weaviate's documentation advises setting it explicitly because some client libraries do not leave the default in place). Qdrant and OpenAI's vector stores accept per-retriever weights inside RRF. Start with unweighted RRF and change it only when an evaluation set shows a gain.

Reranking: a slower, sharper second pass

Neither first-stage retriever reads a chunk next to the query. Embeddings of the query and the chunk are computed separately (a bi-encoder), and BM25 only counts tokens. A reranker is usually a cross-encoder: the query and one candidate pass through a transformer together, so attention runs across both texts. The Sentence Transformers documentation (opens in a new tab) states the tradeoff: accuracy is higher, but scoring thousands or millions of pairs would be slow. Rerankers therefore work on a shortlist:

  1. Retrieve generously. Sentence Transformers suggests on the order of 100 hits, Anthropic's experiments used 150, and Azure's semantic ranker reads the top 50.
  2. Score every (query, chunk) pair with the reranker.
  3. Keep the best few for the prompt. Anthropic kept 20.

A hosted reranker is a single call. This sketch uses the parameter names from Cohere's documentation; it needs an API key and was not run for this lesson:

python
response = co.rerank(
    model="rerank-v4.0-pro",   # a model name listed in Cohere's docs when this lesson was written
    query=question,
    documents=candidate_texts,  # the shortlist from the first stage
    top_n=5,                    # how many to keep
)
# Each result holds the index of a document in candidate_texts and a relevance score from 0 to 1.

A reranker can only reorder what the first stage found. If the right chunk is not among the candidates, no reranker will produce it.

Rewriting and expanding the query

People do not type search queries. They write a full sentence asking for the height of the main office building, or a follow-up such as "and for the EU?" that depends on the conversation. A rewrite step asks a model for a standalone search query. OpenAI's retrieval documentation shows its built-in rewriter turning that first request into primary office building height.

Expansion sends several queries and fuses the results:

  • Variants. Azure's query rewrite, a preview feature when this lesson was written, creates up to 10 variants of a query, fixing typos and adding synonyms.
  • Decomposition. Amazon Bedrock Knowledge Bases can split a question that compares two teams' World Cup scores into one sub-query per team.
  • HyDE (hypothetical document embeddings). A model writes a made-up answer, and the system embeds that text in place of the question, because answer-shaped text lies closer to real answers in vector space. Invented details in the fake answer never reach the user; only the real chunks it retrieves do.

Each of these adds a model call before retrieval starts, and a rewrite can drift from what the user meant. Log the rewritten query next to the original.

Metadata filters

Similarity cannot enforce a hard constraint. The 2023 and 2025 versions of a policy are nearly identical in wording. A metadata filter is a condition on fields stored with each chunk (tenant, product, version, date, access group) that must hold for the chunk to be returned. This one uses the syntax of OpenAI's vector stores; the date is a Unix timestamp for 1 January 2024:

json
{"type": "and", "filters": [
  {"type": "eq",  "key": "region", "value": "us"},
  {"type": "gte", "key": "date",   "value": 1704067200}
]}

Some filters are static: your code sets them from the session, for example the user's tenant and permissions. Others are dynamic: a model reads the question and builds the filter from a schema of the available fields. Bedrock calls this implicit metadata filtering.

Where the filter runs matters. A pre-filter narrows the set before the vector search. A post-filter runs afterwards and can leave too few results. The pgvector README (opens in a new tab) gives the arithmetic: with its default HNSW setting of 40 candidates, a condition that matches 10% of rows leaves about 4.

Contextual retrieval

The last technique changes the index, not the query. Chunking strips context. The example in Anthropic's post (opens in a new tab) is a chunk saying that the company's revenue grew by 3% over the previous quarter, which names neither the company nor the quarter. Contextual retrieval has a model read the whole document and write 50 to 100 tokens that situate each chunk, for instance that it comes from a filing about ACME Corp's second quarter of 2023. That text is prepended to the chunk before it is embedded and before it enters the BM25 index.

The cost moves to ingestion: one model call per chunk. Prompt caching lowers it because the document is read once and reused for each of its chunks. The context must be regenerated when a document changes.

Choosing what to add

Add one stage at a time and measure each against a fixed set of questions with known relevant chunks, as described in Evaluating RAG Systems. Recall@k, the share of relevant chunks that appear in the top k results, is the number these techniques are meant to move.

Worked example: Hybrid search by hand: BM25, a stand-in embedding, a version filter and RRF over six support chunks

A support assistant for an invoicing product has six chunks in its knowledge base. Chunk c3 documents the old version 2 of the product; the rest describe version 3. A version 3 customer writes: "cannot download my bills, error E-4012". The correct chunk is c1.

The script uses only the Python standard library (3.9 or later). BM25 is implemented in full. The embedding model is replaced by a small stand-in, embed, that counts words per concept, so that "download" and "export" land on the same dimension. A real system would call an embedding model here; the stand-in keeps the numbers identical for everyone. Save it as hybrid_search.py.

python
import math
import re

CHUNKS = [
    {"id": "c1", "version": 3, "text": "Invoice export fails with error E-4012 when the customer has no tax profile. Add one, then export again."},
    {"id": "c2", "version": 3, "text": "If saving an invoice as PDF fails, check your connection and try again."},
    {"id": "c3", "version": 2, "text": "Error E-4012 means the export queue is full. Wait ten minutes and retry."},
    {"id": "c4", "version": 3, "text": "Reports: pick a date range, then select Export to save the report as CSV."},
    {"id": "c5", "version": 3, "text": "Error codes: E-4010 payment declined, E-4011 card expired, E-4013 bank refused."},
    {"id": "c6", "version": 3, "text": "Release notes: reworded the E-4012 message and fixed a login bug on mobile."},
]
QUERY = "cannot download my bills, error E-4012"
K1, B = 1.2, 0.75   # BM25 defaults in Elasticsearch
RRF_K = 60          # constant from the original RRF paper

# Stand-in for an embedding model: words with the same meaning share a dimension.
CONCEPTS = {
    "export": ["export", "download", "saving", "save"],
    "billing": ["invoice", "bills", "payment", "card"],
    "failure": ["error", "fails", "cannot"],
    "tax": ["tax", "profile"],
    "reports": ["report", "reports", "date", "range"],
    "access": ["login"],
}


def tokenize(text):
    return re.findall(r"[a-z0-9]+(?:-[a-z0-9]+)*", text.lower())


def bm25_scores(query, chunks):
    docs = [tokenize(chunk["text"]) for chunk in chunks]
    average_length = sum(len(doc) for doc in docs) / len(docs)
    scores = {}
    for chunk, doc in zip(chunks, docs):
        score = 0.0
        for term in set(tokenize(query)):
            tf = doc.count(term)                       # occurrences in this chunk
            df = sum(term in other for other in docs)  # chunks containing the term
            if tf == 0:
                continue
            idf = math.log(1 + (len(docs) - df + 0.5) / (df + 0.5))
            score += idf * tf * (K1 + 1) / (tf + K1 * (1 - B + B * len(doc) / average_length))
        scores[chunk["id"]] = score
    return scores


def embed(text):
    tokens = tokenize(text)
    return [sum(tokens.count(word) for word in words) for words in CONCEPTS.values()]


def cosine(a, b):
    dot = sum(x * y for x, y in zip(a, b))
    norm = math.sqrt(sum(x * x for x in a)) * math.sqrt(sum(y * y for y in b))
    return dot / norm if norm else 0.0


def dense_scores(query, chunks):
    query_vector = embed(query)
    return {chunk["id"]: cosine(query_vector, embed(chunk["text"])) for chunk in chunks}


def ranked(scores, allowed, top_n):
    ids = [doc_id for doc_id in scores if doc_id in allowed and scores[doc_id] > 0]
    return sorted(ids, key=lambda doc_id: scores[doc_id], reverse=True)[:top_n]


def rrf(rankings, k=RRF_K):
    fused = {}
    for ranking in rankings:
        for rank, doc_id in enumerate(ranking, start=1):
            fused[doc_id] = fused.get(doc_id, 0.0) + 1 / (k + rank)
    return sorted(fused.items(), key=lambda item: item[1], reverse=True)


def hybrid_search(query, chunks, version=None, top_n=3):
    allowed = {chunk["id"] for chunk in chunks if version is None or chunk["version"] == version}
    keyword = ranked(bm25_scores(query, chunks), allowed, top_n)
    dense = ranked(dense_scores(query, chunks), allowed, top_n)
    return keyword, dense, rrf([keyword, dense])


if __name__ == "__main__":
    bm25, dense = bm25_scores(QUERY, CHUNKS), dense_scores(QUERY, CHUNKS)
    for chunk in CHUNKS:
        print(chunk["id"], f"bm25={bm25[chunk['id']]:.3f}", f"cosine={dense[chunk['id']]:.3f}")
    for label, version in (("no filter", None), ("version == 3", 3)):
        keyword, semantic, fused = hybrid_search(QUERY, CHUNKS, version)
        print(f"--- {label}")
        print("bm25 :", keyword)
        print("dense:", semantic)
        print("fused:", [(doc_id, round(score, 5)) for doc_id, score in fused])

Edge cases and limitations

The RRF constant differs between engines
Elasticsearch defaults rank_constant to 60 with ranks starting at 1, and Azure AI Search's documentation names 60 as a good value. Qdrant counts ranks from 0 and defaults its constant to 2, which equals k = 1 in this lesson's formula, and has let you set it since version 1.16.0. The same two result lists can fuse into a different order on a different engine, because a small k lets a single first place outweigh agreement lower down. When you migrate or compare engines, set the constant explicitly and rerun your evaluation set.
A post-filter quietly shrinks the result list
With approximate vector indexes, some engines apply the filter after the index scan. The pgvector README works through the case: with HNSW and the default hnsw.ef_search of 40, a condition matching 10% of rows leaves about 4 rows. pgvector 0.8.0 added iterative index scans that keep scanning until enough rows pass. Azure AI Search defaults to preFilter and warns that post-filtered queries can return fewer results than requested. If a filtered query returns fewer chunks than you asked for, check the filter mode first.
The reranker never sees the chunk the first stage missed
Azure's documentation is explicit that its semantic ranker reranks the top 50 results and cannot rerun the query over the whole corpus. The same holds for any reranker. The sign is an evaluation in which reranking improves the order of the top 5 but recall over the candidate list stays flat. Fix the first stage (add BM25, rewrite the query, widen the candidate list) before tuning the reranker.
Long candidates are cut down before they are scored
Rerankers have input limits. Cohere documents a 32,768-token context for rerank-v4.0 and 4,096 tokens for rerank-v3.5 and rerank-v3.0, and splits longer documents into pieces that are scored separately, keeping the highest score. Azure builds a summary string of at most 2,048 tokens per result and trims fields in the priority order you configured, so a passage at the end of a very long chunk may never be read. Keep chunks inside the reranker's limit and put the most informative field first.
Fusion promotes whatever both retrievers agree on, including stale content
RRF has no notion of correctness. In the worked example the outdated version 2 chunk ranks 1st in BM25 and 2nd in vector search, so fusion puts it first. Near-duplicate documents that differ by version, year or region behave this way in real corpora. Fusion will not separate them; a metadata filter or removing superseded documents will.
RRF scores are tiny and are not confidence values
With two lists and k = 60 the highest possible RRF score is 2/61, about 0.033. Azure's troubleshooting table notes that a score of 0.03 can still indicate a strong match. Do not apply a cosine-style threshold such as 0.7 to fused scores. If you need a cut-off, apply it to reranker scores and choose it from labelled queries; Cohere suggests testing 30 to 50 representative queries to find one.

When to use it, and when something simpler is enough

Use it when

  • Queries mix natural-language questions with exact identifiers such as error codes, SKUs, function names or people's names. Hybrid search covers both kinds without routing logic.
  • The corpus contains near-duplicate content that differs by version, date, region or owner. A metadata filter is the only stage that can enforce such a constraint.
  • An evaluation shows that the relevant chunk is usually within the top 50 to 150 candidates but outside the handful you pass to the model. That gap is what a reranker closes.
  • Users ask conversational, multi-part or follow-up questions. Rewriting or decomposing the question before searching gives the retrievers something they can match.
  • Chunks are ambiguous when read alone, as in financial filings, contracts and long manuals, and the corpus changes slowly enough to afford one model call per chunk at ingestion.

Think twice when

  • The whole knowledge base fits in the prompt. Anthropic suggests skipping retrieval below about 200,000 tokens, roughly 500 pages, and using prompt caching instead.
  • You have no evaluation set yet. Without recall measured per stage you cannot tell whether a new stage helps, so build the question set first.
  • The latency budget has no room for another model call. A rewrite and a rerank each add a round trip, so leave out any stage that does not move measured recall.
  • Documents change many times a day and each change would trigger regenerating context for every chunk. Contextual retrieval suits corpora that are indexed far more rarely than they are queried.

A simpler alternative. Plain top-k vector search over well-made chunks, as in the RAG fundamentals lesson, or no retrieval at all for a small corpus that fits in the prompt. It stops being enough when traces show one of three things: queries with exact terms that return nothing useful, chunks from the wrong version or customer, or the relevant chunk sitting just outside the top k.

Key takeaways

  • Keyword search (BM25) and vector search miss different queries, so running both and fusing the results covers exact identifiers and paraphrases together.
  • Reciprocal rank fusion adds 1/(k + rank) across result lists, which avoids comparing raw scores and favours chunks that several retrievers agree on.
  • A reranker reads the query and each candidate together, which is more accurate but slower, so it only reorders a shortlist and cannot recover a chunk that the first stage missed.
  • Query rewriting and metadata filters repair the input to retrieval: one turns the user's message into a searchable query, the other enforces constraints that similarity cannot express.
  • Contextual retrieval prepends a short model-written description of the document to each chunk before indexing, trading ingestion cost for fewer failed retrievals.
  • Every stage adds latency or cost, so add one at a time and keep it only if a retrieval metric such as recall@k improves on your own questions.

Anthropic measuring contextual embeddings, contextual BM25 and reranking across four knowledge domains

AnthropicDocumented in an engineering article

Anthropic's engineering post Introducing Contextual Retrieval (September 2024) describes the method, the instruction given to the model that writes the context, and retrieval experiments over codebases, fiction, arXiv papers and science papers. The post used Cohere's reranker for the final stage, whose interface is described in Cohere's Rerank documentation. [1][13]

The problem

Splitting documents into chunks removes the information that tells a retriever what a chunk is about. The post's example is a chunk from a financial filing stating that revenue grew by 3% over the previous quarter. The chunk names neither the company nor the quarter, so a question about that company's second-quarter revenue growth has little to match, in either an embedding index or a BM25 index.

Where this topic fits

Contextual retrieval sits at ingestion, between chunking and indexing. Everything after it is the hybrid pipeline from this lesson: BM25 and embedding search over the contextualised chunks, rank fusion of the two result lists, an optional reranker over the top candidates, and the surviving chunks placed in the prompt.

How it is applied, step by step

  1. Documents are split into chunks in the usual way.
  2. For each chunk, a model receives the whole document and the chunk, with an instruction to write a short context that situates the chunk within the document for search purposes. The post used Claude 3 Haiku, a small and inexpensive model at the time.
  3. The context, usually 50 to 100 tokens, is prepended to the chunk. The combined text is embedded (contextual embeddings) and added to the BM25 index (contextual BM25).
  4. At query time BM25 and embedding search each return their top chunks, and the two lists are combined and deduplicated with rank fusion.
  5. In the reranking configuration the top 150 candidates are passed to a reranking model together with the query, and the 20 highest-scoring chunks are kept.
  6. The kept chunks are added to the prompt from which the model writes its answer.
  7. Each configuration is scored by 1 minus recall@20: the share of relevant chunks that are missing from the top 20.

Why this approach fits

The defect is in the chunk text, so no query-side technique can repair it: a retriever cannot match a company name that the chunk does not contain. Writing the missing context into the chunk fixes both indexes at once. The embedding gains the topic, and BM25 gains the literal names and identifiers. Because contextualising, hybrid search and reranking act at different points, their gains add up, which is what the post's stacked results show.

Limitation or tradeoff

Ingestion now costs one model call per chunk and must be repeated when a document changes. The post's cost figure depends on prompt caching and on model prices at the time it was written. The quality of the context depends on the instruction and the model, and a generic or mistaken context adds misleading terms to both indexes. The reported gains are averages over Anthropic's own test sets with one embedding model, and the starting failure rate was already 5.7%, so the absolute improvement is a few percentage points. Reranking adds latency and cost to every query.

What the sources document

  • The method prepends chunk-specific explanatory context to each chunk before embedding it and before building the BM25 index. The context is generated by Claude from the whole document and the chunk and is usually 50 to 100 tokens long. [1]
  • Measured as 1 minus recall@20, contextual embeddings reduced the top-20 retrieval failure rate from 5.7% to 3.7%, adding contextual BM25 reduced it to 2.9%, and adding reranking reduced it to 1.9%. [1]
  • The experiments covered codebases, fiction, arXiv papers and science papers. The published graphs show averages across those domains using the best-performing embedding configuration, Gemini Text 004, and the top 20 chunks. [1]
  • For reranking, the authors retrieved the top 150 chunks, scored them with Cohere's reranker and kept the top 20. They note that reranking adds a small amount of latency at runtime. Cohere documents Rerank as taking a query and a list of documents and ordering the documents by relevance. [1][13]
  • With prompt caching, the post estimates the one-time cost of generating contextualised chunks at 1.02 US dollars per million document tokens, assuming 800-token chunks, 8,000-token documents, 50 tokens of instructions and 100 tokens of context per chunk. [1]

Azure AI Search merging BM25 and vector results with RRF, then reranking the top 50

MicrosoftDocumented in official docs

Azure AI Search is Microsoft's managed search service. Its documentation on hybrid search scoring, on creating hybrid queries and on semantic ranking describes how a single request runs a keyword query and a vector query, how the two result sets are merged, and how an optional second-stage ranker reorders the merged list. [5][6][7]

The problem

A hybrid request produces two result sets whose scores are on unrelated scales. The documentation lists BM25 scores as having no upper limit and cosine vector scores as falling between 0.333 and 1.00, so one list cannot be sorted against the other by score. The merged list also still reflects two fairly coarse first-stage rankings, which leaves room for a slower model to improve the order of the best results.

Where this topic fits

Fusion and reranking happen inside the search service at query time. The text query and each vector query execute in parallel. RRF merges their ranked results into one list with a new score. If the request asks for semantic ranking, the top of that list is rescored by Microsoft-hosted language models before the response is returned to the application, which then builds the prompt.

How it is applied, step by step

  1. The application sends one request containing a search string and one or more vector queries. The service runs the keyword query and the vector queries in parallel.
  2. An optional filter on filterable fields is applied. The default mode, preFilter, narrows the documents before the queries run.
  3. Each query produces a ranked result set. For every document in a set the service assigns the reciprocal rank score 1/(rank + k), where k is a constant. The documentation says experiments show the algorithm performs best with a small k such as 60.
  4. The scores a document earned in each set are added, and documents are sorted by the total. This fused list is the hybrid result.
  5. When the request sets the query type to semantic, the top 50 fused results are summarised to fit the ranking model's input and given a reranker score from 0 to 4.
  6. The response is ordered by reranker score and reports it separately from the RRF score, so the application can log both.

Why this approach fits

A search service must merge lists from retrievers it knows nothing in advance about: any analyzer, any embedding model, any number of vector fields. RRF needs only ranks, so it works for all of them without per-index calibration. Putting the expensive language models after fusion means they score at most 50 documents per query however large the index is, which keeps the cost of the second stage fixed.

Limitation or tradeoff

RRF discards score magnitude, so a near-perfect vector match and a marginal one earn the same credit if they hold the same rank. The semantic ranker only reorders the top 50 and reads a trimmed summary of each, so it cannot surface a document the first stage missed or a passage beyond the token limit. The documentation also warns that combining heavy vector settings, large text recall and semantic reranking in one request raises latency and can cause throttling on small service tiers. Semantic ranker is a premium feature billed by usage; free use is subject to the free tier's service limits.

What the sources document

  • RRF is used whenever more than one query executes in parallel, such as a hybrid query. Each document in each ranked list receives a score of 1/(rank + k), the scores are summed per document, and the documentation says the algorithm performs best with a small k such as 60. [5]
  • The documentation's score table gives BM25 full-text scores no upper limit, cosine vector scores a range of 0.333 to 1.00 and semantic ranker scores a range of 0.00 to 4.00, and states that semantic ranking occurs after RRF merging. [5]
  • Semantic ranker adds a secondary ranking over BM25-ranked or RRF-ranked results using multilingual deep learning models adapted from Microsoft Bing. Only the top 50 results progress to semantic ranking, and it cannot rerun the query over the entire corpus. [6]
  • As of November 2024 the summary string passed to the semantic ranker for each document is at most 2,048 tokens, and overly long field content is trimmed in the priority order of the semantic configuration. [6]
  • The how-to page says to set k to 50 when using semantic ranking with vectors, states that preFilter is the default filter mode, and notes that post-filtering can return fewer results than top. [7]

The problem

Dash has to answer questions over business data that the post describes as diverse (emails, documents, meeting notes, task data), fragmented across many applications and spread over several modalities. The team names three trade-offs in choosing a retrieval system: latency against quality, data freshness against scalability, and budget against user experience. A larger embedding-based search may be more relevant but slower, frequent re-indexing can hurt throughput, and more compute costs more.

Where this topic fits

The decision concerns the first stage of Dash's RAG pipeline and the stage directly after it. A lexical index finds candidate documents, the documents are chunked at query time, a reranking step orders the chunks, and the top chunks become the context for the model that writes the answer.

How it is applied, step by step

  1. The post describes two common designs: a vector index in which pre-chunked data is indexed by its embeddings, and a traditional search index in which documents are indexed by lexical features such as the words in the title or body. It notes that many other options exist.
  2. They judged the options against the three named trade-offs, with the stated goal of reasonable latency, high quality and reasonable data freshness.
  3. They chose the traditional information retrieval approach and combined it with chunking at query time and reranking.
  4. At query time the lexical index returns candidate documents, and those documents are chunked on the fly so that only the relevant sections are pulled.
  5. A larger but still efficient embedding model re-sorts the chunks so that the most relevant ones come first.
  6. The top chunks go to the language model. To choose models, the team evaluated several open-source and closed-source models on public question-answering datasets and kept the system model agnostic.

Why this approach fits

A typical lexical index over whole documents is cheaper to keep fresh when content changes constantly across many connected applications, because an update does not require re-embedding every chunk (the post names the freshness-versus-scalability trade-off but does not spell out this mechanism). Moving the embedding model to the reranking stage spends the expensive computation on a short candidate list, not on the whole corpus. The design shows that "advanced retrieval" does not have to begin with a vector index: the semantic model can sit in the second stage.

Limitation or tradeoff

The first stage is purely lexical, so it inherits vocabulary mismatch: a document that uses different words from the question may never become a candidate, and the reranker cannot recover it. The post itself notes that the lexical option adds latency at serving time because chunking and reranking happen on the fly. The post gives a latency figure but no retrieval-quality comparison against a vector index, so it should be read as one team's trade-off under its own constraints, not as evidence that lexical search is better in general.

4Common mistakes

  1. Adding raw BM25 and cosine scores together to produce the hybrid ranking.

    Why it causes problems
    BM25 has no upper bound while cosine similarity stays inside a narrow band, so the sum is dominated by BM25 and the vector retriever stops influencing the order. The balance also shifts whenever the corpus or the embedding model changes.
    How to recognise it
    The fused order matches the BM25 order almost exactly, and switching the vector retriever off leaves your evaluation results unchanged.
    How to fix it
    Fuse by rank with RRF, or rescale each score list to a common range before a weighted sum, as Weaviate's relativeScoreFusion does. Introduce weights only after an evaluation shows they help.

  2. Reranking only the handful of chunks that would have been sent to the model anyway.

    Why it causes problems
    A reranker can promote a chunk only if it is among the candidates. Reranking five chunks into five changes their order and nothing else, so a relevant chunk at rank 6 or lower still never reaches the model.
    How to recognise it
    Recall@5 is identical before and after reranking in your evaluation, and the reranker's input size in the configuration equals the final number of chunks.
    How to fix it
    Retrieve a much longer candidate list first (the documented systems in this lesson use 50 to 150), rerank that list, and only then cut it down to what the prompt needs.

  3. Relying on a model-written filter, or a filter on one retriever only, to control who can see a chunk.

    Why it causes problems
    A model can omit or miswrite the filter, and a filter applied to the vector query but not to the keyword query lets restricted chunks back in through the other list. Either way a user is shown content they are not allowed to read.
    How to recognise it
    Log in as a user without access to a known document and search for its exact title. Also scan query logs for requests that reached a retriever without a tenant or permission condition.
    How to fix it
    Set access filters in code from the authenticated session and apply them as a pre-filter on every retriever. Treat model-generated filters as an extra condition that can narrow results further but never replaces the access filter.

  4. Throwing away the user's original wording once the query has been rewritten.

    Why it causes problems
    A rewrite can drop the token that mattered, such as an error code, a product name or a negation. The search then runs without it, and no later stage can put it back.
    How to recognise it
    Log both strings for every request. In failed cases, look for an identifier that appears in the original message but not in the rewritten query.
    How to fix it
    Tell the rewriter to copy identifiers and quoted strings unchanged, keep both versions in the trace, and for important flows search with the original and the rewritten query and fuse the two result lists.

  5. Switching on hybrid search, rewriting, reranking and contextual chunks in one release with no evaluation set.

    Why it causes problems
    You cannot tell which stage helped and which hurt. You pay the latency and cost of all of them, and a harmful stage, such as an over-strict filter, stays hidden behind gains from the others.
    How to recognise it
    The team can quote an end-to-end answer quality score but not recall@k after each stage, and nobody can say which stage to remove when latency has to come down.
    How to fix it
    Build a set of questions with known relevant chunks, record baseline recall@k and latency, then add one stage at a time and keep it only if recall improves enough to justify the added time.

from hybrid_search import bm25_scores

DOCS = [
    {"title": "Billing v3 guide, section on invoice export error E-4012", "chunks": [
        ("k1", "Invoice export can stop with an error code."),
        ("k2", "The cause is a customer record without a tax profile."),
        ("k3", "To fix it, open the customer record, add a tax profile and run the export again."),
    ]},
    {"title": "Payments guide, section on declined cards", "chunks": [
        ("k4", "To fix a declined card, ask the customer to update the card details and retry."),
    ]},
    {"title": "Reports guide, section on report export error E-5100", "chunks": [
        ("k5", "This error appears when a report is too large. To fix it, pick a shorter date range."),
    ]},
]
QUERIES = [("how to fix error E-4012", "k3"), ("what is the cause of E-4012", "k2")]


def contextualize(title, text):
    """Stand-in for the LLM call that writes a short context for one chunk."""
    return f"This chunk is from the {title}. {text}"


def build_index(with_context):
    return [
        {"id": chunk_id, "text": contextualize(doc["title"], text) if with_context else text}
        for doc in DOCS
        for chunk_id, text in doc["chunks"]
    ]


def rank_of(answer_id, query, chunks):
    scores = bm25_scores(query, chunks)
    order = sorted((i for i in scores if scores[i] > 0), key=lambda i: scores[i], reverse=True)
    return order, (order.index(answer_id) + 1 if answer_id in order else None)


if __name__ == "__main__":
    for with_context in (False, True):
        chunks = build_index(with_context)
        hits = 0
        print("contextual chunks" if with_context else "plain chunks")
        for query, answer in QUERIES:
            order, rank = rank_of(answer, query, chunks)
            hits += rank is not None and rank <= 2
            print(f"  {query!r}: order={order} rank of {answer}={rank}")
        print(f"  recall@2 = {hits}/{len(QUERIES)}")

Why the plain index fails on the first query. The query's tokens are how, to, fix, error and e-4012. The plain text of k3 contains only to and fix. Those two words are in three of the five chunks, so they carry little weight. k4 has the same two matches, with to twice in a slightly shorter chunk, and k5 has them plus error. Even k1, a short chunk that matches only the rarer word error, edges ahead (1.044 against 0.992). Now k3 matches four query terms, including one that only the three billing chunks contain, and it ranks first.   3. Query: "maximum operating temperature of the K2 pump". Datasheets from 2019 and 2024 both come back, and the 2019 one, whose value is out of date, ranks first. Every chunk has a year field.
  4. On 200 test questions the relevant chunk is in the fused top 50 for 94% of questions but in the top 5, which is all the model sees, for only 61%.
  5. The chunk "The limit was raised to 40 hours in this revision." answers "What is the service interval of the K2 pump?" but is never retrieved for it.

Part C. Fit a latency budget. Retrieval must finish within 600 ms. Measured times: query rewrite 350 ms; BM25 40 ms and vector search 90 ms, run in parallel; fusion 5 ms; reranking 50 candidates 300 ms.

  1. What is the total with every stage switched on?
  2. The dominant problem is trace 4. Which stage do you drop to meet the budget, and what is the new total?
  3. About 30% of requests are follow-up turns like trace 2. Propose a rule for when to run the rewrite, and say whether those requests then meet the budget.

Requirements

  • Show the arithmetic for Part A to at least four decimal places and state any ties.
  • Give exactly one technique per trace in Part B and place it before retrieval, inside it or after it.
  • In Part C, add parallel stages as the slower of the two and sequential stages as a sum.
  • Justify the stage you drop in Part C by referring to the trace that matters most.

Expected behaviour

Part A gives d2 first under both constants, with d4 second for k=60k = 60k=60 and fourth for k=2k = 2k=2. Part B maps the five traces to hybrid search, query rewriting, a metadata filter, a reranker and contextual retrieval, in that order. Part C gives 745 ms with everything on and 395 ms after dropping the rewrite, with a routing rule that still leaves the rewritten requests over budget unless something else changes.

Hint 1

A document that appears in only one list gets a single term. A document in both lists gets two terms added together.

Hint 2

For Part B, ask what is wrong in each trace: the query text, the candidate list, the order of the candidates, or the chunk itself.

Hint 3

For Part C, a stage that runs in parallel with another does not add its full time to the total.

The document whose fate changes is d4. It sits low in both lists. With k=60k = 60k=60 two modest ranks add up to nearly twice a single first place (0.0310 against 0.0164), so d4 is second and reaches the model. With k=2k = 2k=2 a first place is worth 0.3333 and d4's two terms total only 0.3095, so both single-list leaders pass it and d4 drops to fourth, outside the top 3. A large kkk favours agreement between retrievers, and a small kkk favours each retriever's top pick. The ties are real: an engine breaks them by an internal rule, so do not read meaning into the order of d7 and d5.

Part B.

  1. Hybrid search. The part number is an exact token that the embedding model blurs with similar numbers. Add a BM25 retriever inside the retrieval stage and fuse it with the vector results.
  2. Query rewriting. Before retrieval, a model turns the conversation into a standalone query such as "warranty of the older K2 pump model". The retrievers never see the bare follow-up.
  3. Metadata filter. A pre-filter on year, applied inside retrieval to both retrievers, removes the 2019 datasheet. Removing superseded documents at ingestion would also work. Fusion and reranking would not, because both chunks match the query equally well.
  4. Reranker. The chunk is found (94%) but ordered badly (61%). A reranker after fusion reads the top 50 and passes on the best 5. It cannot lift the result above 94%, the ceiling set by the first stage.
  5. Contextual retrieval. The chunk names neither the pump nor the service interval. At ingestion, a short context saying which manual and section it comes from is prepended before indexing.

Part C.

  1. Rewrite 350, then the two searches in parallel at max(40, 90) = 90, fusion 5 and reranking 300: 350 + 90 + 5 + 300 = 745 ms, which is 145 ms over the budget.
  2. Keep the reranker, because it is the stage that fixes trace 4, and drop the rewrite: 90 + 5 + 300 = 395 ms.
  3. Run the rewrite only when the request has earlier turns in the conversation, and skip it for single-turn requests. Then 70% of requests take 395 ms. The 30% that are rewritten still take 745 ms and miss the budget, so an average under 600 ms would hide a slow tail. To bring those requests in, shorten another stage for them: rerank fewer candidates, or use a faster model for the rewrite, and measure recall again after the change.

Check your answer

  • Is d2 first under both constants, with a score of 0.0323 for k = 60 and 0.5 for k = 2?
  • Did you find that d4 is second with k = 60 but fourth with k = 2?
  • Did you assign five different techniques to the five traces in Part B?
  • Does your Part C total use 90 ms, not 130 ms, for the two parallel searches?
  • Did you notice that routing the rewrite fixes the average but not the slowest 30% of requests?

    When you move from a prototype to a vector database and want fusion and rescoring to run server-side.
