Tokens and Context Windows

A token is the unit of text a language model reads and writes: a word, a piece of a word, a punctuation mark or a few bytes. The context window is the maximum number of tokens a model can handle in one request, counting everything sent to it and everything it generates in reply.

1Overview

Why it matters

Tokens are the unit for three things you cannot avoid when you build on a language model: how much text fits in a request, how long a reply may be, and what each call costs. A request that is too long is rejected. A reply that reaches its output limit stops in the middle of a sentence or a JSON object. A chat that resends its whole history is billed for that history on every turn, so a feature that cost cents in testing can cost far more once real conversations get long.

Anyone who writes prompts, builds a chat or an agent, estimates a budget or debugs a cut-off answer needs to count in tokens instead of words or characters. The same knowledge explains product behaviour that otherwise looks arbitrary: why a coding assistant loses track of an instruction given an hour earlier, why an invoice does not match a word count, and why moving to a newer model can change the token count of a prompt you did not edit.

Key terms

Token
The unit of text a model processes. A token can be a whole word, part of a word, a punctuation mark, a space joined to a word, or a few bytes of a character.
Tokenizer
The program that splits text into tokens and maps each one to a number before the model sees it, and that turns the model's output numbers back into text.
Vocabulary
The fixed list of tokens a tokenizer knows, each with an integer ID. A model can only read and write IDs from its own vocabulary.
Byte-pair encoding (BPE)
A method for building a vocabulary by starting from single characters or bytes and repeatedly merging the most frequent neighbouring pair into a new token.
Context window
The maximum number of tokens a model can work with in one request. It holds the input and the output together.
Input tokens
The tokens you send in a request, including the system prompt, tool definitions, earlier messages, documents and images. Also called prompt tokens.
Output tokens
The tokens the model generates in a response, including any hidden reasoning tokens. Also called completion tokens.
Max output tokens
A cap on how many tokens one response may contain. Each model has a ceiling, and a request can set a lower one with a parameter such as max_tokens.
Stop reason
A field in an API response that says why generation ended, for example because the model finished or because a token limit was reached.
Compaction
Replacing the older part of a long conversation with a shorter summary so that the conversation can continue inside the context window.

2Explanation

Introduction

In How Large Language Models Work you saw that a model writes text by predicting the next token, again and again. This lesson looks at that unit. A model never sees letters or words. Before your prompt reaches it, a program called a tokenizer cuts the text into tokens and replaces each one with a number from a fixed list, the vocabulary. The model reads those numbers and predicts more numbers, and the tokenizer turns its output back into text.

A token is often a whole common word, but a rare or long word is split into pieces, and punctuation, spaces and digits use tokens too. Google's Gemini documentation gives a workable rule of thumb for English: a token is about 4 characters, and 100 tokens are about 60 to 80 words (opens in a new tab). It is only an estimate. The OpenAI Cookbook shows a nine-character Japanese greeting taking between 8 and 14 tokens, depending on which tokenizer is used.

Tokens matter because every limit and every price is stated in them. The most important limit is the context window. Anthropic's documentation describes it as everything a model can refer to while it generates a response, the response itself included (opens in a new tab), and compares it to working memory. Picture a desk of fixed size. Your instructions, the documents you paste in, the whole conversation so far and the reply being written must all lie on the desk at the same time. When the desk is full, something has to come off before anything new can go on.

Three practical facts follow from this picture:

  • Size is measured in tokens. You need a way to count them before you send a request.
  • Input and output share the space but are priced separately. Providers charge per million tokens, and usually charge more for output than for input.
  • A conversation grows with every turn. The model keeps no memory between calls, so the history is sent again each time, and sooner or later it no longer fits.

The rest of the lesson covers how a tokenizer splits text, how to count tokens, how the input and output limits interact, how to turn token counts into a cost, and what real APIs and products do when a conversation exceeds the window.

How it works

How a tokenizer splits text

The best-known method is byte-pair encoding (BPE). It began as a compression algorithm and was adapted for neural machine translation in a 2015 paper by Sennrich, Haddow and Birch (opens in a new tab), which represented rare and unknown words as sequences of smaller units. Hugging Face's course lists GPT, GPT-2, RoBERTa, BART and DeBERTa among the models that use it, and OpenAI's tiktoken library is a BPE tokenizer.

Training a BPE tokenizer takes three steps, repeated many times:

  1. Start with a base vocabulary of single symbols: the characters in the training text, or the 256 possible byte values.
  2. Count every pair of neighbouring symbols in the training text and find the most frequent pair.
  3. Add that pair to the vocabulary as one new token and record the merge. Go back to step 2 until the vocabulary reaches its target size.

The ordered list of merges is the tokenizer. To tokenize new text, split it into base symbols and replay the merges in the order they were learned. The worked example does this by hand.

The tiktoken README (opens in a new tab) lists the properties this gives: the encoding is reversible and lossless, it works on text the tokenizer has never seen, it compresses text (on average a token covers about 4 bytes), and common fragments get their own token, so encoding may split into encod and ing. Three consequences matter in practice:

  • The tokenizer belongs to the model. A different model family has a different vocabulary and gives a different count for the same text. Anthropic notes that Claude 4.7 and later models use a newer tokenizer that produces about 30% more tokens for the same text than earlier Claude models.
  • Spaces and capitals change the result. In the OpenAI Cookbook, tiktoken is great! becomes six tokens: t, ikt, oken, is, great and !. The space travels with the word that follows it.
  • Other inputs become tokens too. Gemini counts an image of up to 384 by 384 pixels as 258 tokens and audio as 32 tokens per second.

System prompts and tool definitions are input you pay for on every call, although the user typed none of them. The guide also says that the count is an estimate, and that the endpoint is free and has its own rate limit.

One window, two limits

Every request is subject to two limits. The context window WWW covers input and output together. The maximum output is a separate ceiling for one response: the model has one, and your request sets its own with a parameter such as max_tokens. A request is safe when

Tin+Tmax out≤WT_{\text{in}} + T_{\text{max out}} \le WTin​+Tmax out​≤W

The numbers differ widely by model. Anthropic's documentation gives its current models a 1M-token window with up to 128k output tokens per request, and older models a 200k window. OpenAI's conversation-state guide uses gpt-4o-2024-08-06 as its example: a 128k window and at most 16,384 output tokens.

Reasoning tokens (see Reasoning Models) come out of the output budget. Anthropic states that thinking tokens are a subset of max_tokens and are billed as output. OpenAI states that reasoning tokens are not visible but still occupy the window, and recommends reserving at least 25,000 tokens for reasoning and output when you start with its reasoning models.

Every response reports what it used and why it ended. This excerpt follows the example response in Anthropic's stop reason documentation:

json
{
  "stop_reason": "end_turn",
  "usage": { "input_tokens": 100, "output_tokens": 50 }
}

In the Claude API, stop_reason is end_turn when the model finished and max_tokens when the reply was cut off at your limit. Check it before you use the reply.

Output costs five times as much as input in every row. A request to Claude Sonnet 5.5 with 6,000 input tokens and 800 output tokens costs (6000×2+800×10)/106=0.02(6000 \times 2 + 800 \times 10) / 10^6 = 0.02(6000×2+800×10)/106=0.02 dollars. The output is 12% of the tokens and 40% of the cost.

Three modifiers on the same page change the arithmetic. Input read from the prompt cache is charged at a tenth of the input price or less. The Batch API gives a 50% discount for work that can wait. Claude Haiku 5.5 charges a higher rate for any request whose prompt is over 100,000 tokens. LLM Cost and Latency Optimization covers these levers.

When a conversation exceeds the window

If the first request of a conversation has bbb input tokens and each turn adds ddd tokens (the reply plus the next message), request number kkk sends

Tin(k)=b+(k−1) dT_{\text{in}}(k) = b + (k - 1)\,dTin​(k)=b+(k−1)d

With b=10,000b = 10{,}000b=10,000, d=12,000d = 12{,}000d=12,000, a 200k window and 16,000 tokens reserved for output, requests 1 to 15 fit. Request 16 sends 190,000 tokens and leaves less room than the reserve. Request 17 would send 202,000 tokens and cannot be accepted at all. By request 15 the conversation is 178,000 tokens long, but the fifteen requests have sent 1,410,000 input tokens in total, because each one carried the whole history again.

What happens at the limit depends on the API and on the product built around it:

An application has four ways to respond, and most combine several:

  • Stop. Tell the user the conversation is full and start a new one. This is honest and loses nothing silently.
  • Trim. Drop the oldest turns until the request fits. It is simple and cheap, and the model forgets whatever was dropped.
  • Summarise. Replace older turns with a summary, which is called compaction. Anthropic offers it as a server-side feature (opens in a new tab). The gist survives, and details can be lost.
  • Keep bulk out. Send only the relevant parts of documents, cap the size of tool results and remove old ones.

Whichever you choose, keep the system prompt and standing rules outside the part that gets trimmed. A larger window is not a cure by itself: Anthropic's documentation warns that accuracy and recall degrade as the token count grows, an effect it calls context rot. Context Engineering takes this further.

Worked example: Train a three-merge BPE tokenizer by hand and count tokens with it

The corpus is the one used in Hugging Face's Byte-Pair Encoding chapter (opens in a new tab): five words, each with the number of times it occurs. We learn three merges from it and then count the tokens in text the tokenizer has not seen. Production tokenizers run the same procedure on a huge corpus and keep many thousands of merges.

Save this as tiny_bpe.py. It needs only the Python standard library (3.9 or later).

python
from collections import Counter

CORPUS = {"hug": 10, "pug": 5, "pun": 12, "bun": 4, "hugs": 5}  # word: how often it occurs
NUM_MERGES = 3
UNKNOWN = "[UNK]"


def count_pairs(splits, corpus):
    """Count every pair of neighbouring symbols, weighted by word frequency."""
    pairs = Counter()
    for word, frequency in corpus.items():
        symbols = splits[word]
        for pair in zip(symbols, symbols[1:]):
            pairs[pair] += frequency
    return pairs


def merge_pair(symbols, pair):
    """Return a new symbol list in which every occurrence of pair is joined."""
    merged, i = [], 0
    while i < len(symbols):
        if tuple(symbols[i:i + 2]) == pair:
            merged.append(symbols[i] + symbols[i + 1])
            i += 2
        else:
            merged.append(symbols[i])
            i += 1
    return merged


def train(corpus, num_merges):
    splits = {word: list(word) for word in corpus}
    vocab = [UNKNOWN, *sorted({character for word in corpus for character in word})]
    merges = []
    for step in range(1, num_merges + 1):
        pairs = count_pairs(splits, corpus)
        best = max(pairs, key=pairs.get)
        print(f"merge {step}: {best} occurs {pairs[best]} times")
        splits = {word: merge_pair(symbols, best) for word, symbols in splits.items()}
        merges = [*merges, best]
        vocab = [*vocab, "".join(best)]
    return merges, vocab


def encode(text, merges, vocab):
    tokens = []
    for word in text.split():
        symbols = [character if character in vocab else UNKNOWN for character in word]
        for pair in merges:
            symbols = merge_pair(symbols, pair)
        tokens = [*tokens, *symbols]
    return tokens


if __name__ == "__main__":
    merges, vocab = train(CORPUS, NUM_MERGES)
    print("vocabulary:", vocab)
    for text in ["hugs", "bug", "mug", "hugs pun bun pugs bug mug"]:
        tokens = encode(text, merges, vocab)
        ids = [vocab.index(token) for token in tokens]
        print(f"{text!r}: {len(tokens)} tokens {tokens} ids {ids}")
    for text in ["mug", "café", "日本"]:
        print(f"{text!r} as UTF-8 bytes: {list(text.encode('utf-8'))}")

What to notice:

  • A token count is not a word count or a character count. The last test string has 6 words and 25 characters, and it is 13 tokens. hugs costs 2 tokens because hug was frequent enough to earn its own entry. pugs costs 3.
  • Unseen words still work. bug is not in the corpus, yet it splits into the known pieces b and ug. This is why a model can read a word it never met in training.
  • Unseen characters do not. m is missing from the base vocabulary, so mug becomes [UNK] plus ug, and the original word can no longer be recovered.
  • Bytes fix that, at a price. The Hugging Face chapter explains that GPT-2 and RoBERTa start from the 256 possible byte values, so every string can be encoded and no unknown token is needed. The last three output lines show the cost: 日本 is 2 characters but 6 bytes. Text in such scripts starts from more symbols per character, which is one reason the 4-characters-per-token rule fails outside English.
  • The model sees only the IDs. hugs reaches it as [10, 6]. A tokenizer with different merges would produce different IDs and a different count, which is why you count with the tokenizer of the model you are calling.

Edge cases and limitations

The same text has a different token count on a different model
A tokenizer is part of a model, so counts do not transfer. Anthropic states that Claude 4.7 and later models use a newer tokenizer that produces approximately 30 percent more tokens for the same text than earlier models, and that billing follows the new counts. The OpenAI Cookbook shows one Japanese string as 14 tokens under two older encodings, 9 under cl100k_base and 8 under o200k_base. When you change model, recount your real prompts with that model's tokenizer or count endpoint before you reuse a budget or a cost estimate.
Hidden reasoning can use the whole output budget
Reasoning tokens count as output even though you never see them. OpenAI's reasoning guide shows a usage record with 1,186 output tokens of which 1,024 are reasoning tokens, and warns that a response can end with status incomplete before any visible text is produced, while the input and reasoning tokens are still billed. If a reasoning model returns an empty or cut-off answer, check the stop or status field and raise the output limit before you change the prompt.
A reply cut off at the output limit is not a shorter answer
Generation stops at the token where the limit is reached, which can be the middle of a JSON object or of a tool call. Anthropic's stop reason documentation says that when a response is cut off at max_tokens with an incomplete tool use block, the request must be retried with a higher max_tokens value. Check the stop reason before you parse anything, and treat max_tokens as a failure for structured output.
Tokens you never typed are in every request
The system prompt, tool definitions and any text the provider adds to enable tools are input tokens on every call. In Anthropic's token counting examples a two-word greeting with a short system prompt is 14 tokens, while a one-line question with a single tool definition is 403. An agent with dozens of tools can spend thousands of tokens before the user says anything. Count a complete request, not only the user's text.
Self-hosted models may default to a much smaller window
With a local runtime the context length is a setting you choose, and it costs memory. Ollama's documentation gives default context lengths of 4k on machines with less than 24 GiB of VRAM, 32k from 24 to 48 GiB and 256k above that. It recommends at least 64,000 tokens for agents and coding tools, and notes that a larger context length needs more memory. Check the configured length before you assume a model's advertised maximum.
Crossing a size threshold can change the price per token
Cost is not always proportional to length. Anthropic's pricing page lists Claude Haiku 5.5 at 0.10 USD per million input tokens for prompts up to 100,000 tokens and 0.50 USD for prompts over that, with output prices rising in the same ratio, and a request over the threshold pays the higher prices. The input of a 110,000-token prompt therefore costs about six times as much as the input of a 90,000-token prompt. When a provider prices by prompt length, treat the threshold as a budget line.

When to use it, and when something simpler is enough

Use it when

  • Count tokens exactly when a prompt contains variable-length content such as documents, retrieved passages, tool results or chat history that could bring the request close to the window.
  • Estimate cost from measured token counts and current prices before you launch a feature, compare models, or quote a price that depends on usage.
  • Choose an overflow policy (stop, trim, summarise or keep bulk out) in advance for any chat or agent that can run for many turns.
  • Set the output limit with headroom and check the stop reason whenever the reply must be complete, as with JSON, code or a tool call.

Think twice when

  • Do not add a count call to short, fixed prompts that are far below the window. The four-characters estimate and the usage field of the response are enough.
  • Do not count with one vendor's tokenizer for another vendor's model. A tiktoken count says little about a Claude or Gemini request.
  • Do not fill a large window because it is available. Every token in the prompt is billed on every call, and a longer context makes the model less reliable at using the part that matters.

A simpler alternative. Divide the character count by four for a first estimate, then log the input and output token counts that each response reports and budget from those. This stops being enough when requests regularly use more than about half the window, when the text is mostly code or a language other than English, or when you pass token costs on to customers. At that point count each request before sending it.

Key takeaways

  • A model reads and writes tokens, which are pieces of text chosen by its tokenizer, and the same text has a different token count on a different model.
  • About four characters per token is a usable estimate for English, and an exact count needs the model's own tokenizer or its provider's count endpoint.
  • The context window holds input and output together, so a request fits only when its input tokens plus the output you allow stay within the window.
  • Cost is input tokens times the input price plus output tokens times the output price, per million tokens, and output usually costs several times more than input.
  • A conversation resends its history on every turn, so its input grows until it no longer fits, and you are billed for the history each time.
  • At the limit an API rejects the request or cuts the reply short, and products respond by trimming or summarising older content, so anything that must persist belongs outside the trimmed history.

Example 1 of 5

tiktoken counting tokens locally before a request to OpenAI models

OpenAIDocumented in an open-source project

tiktoken is OpenAI's open-source tokenizer library. Its README on GitHub describes the library, and the OpenAI Cookbook recipe How to count tokens with tiktoken, now marked as archived, shows how to use it to count the tokens of strings and chat messages before calling the API. [8][9]

The problem

An application that sends variable text to a model needs two answers before each call: will this text fit, and what will it cost? The cookbook names exactly these two uses of a token count. Asking the API means a network round trip, and for a generation call it means paying for the request before you know its size. The count also has to follow the same splitting rules as the model, because the cookbook shows one string producing different counts under different encodings.

Where this topic fits

The tokenizer runs in your own process, between assembling the prompt and sending it. Its output is a list of integers, and the length of that list is the token count. The count feeds a budget check (does the input plus the output reserve fit the window?) and a cost estimate. After the call, the usage figures in the API response give the authoritative count to compare against.

How it is applied, step by step

  1. Pick the encoding that matches the model. The cookbook maps o200k_base to gpt-4o and gpt-4o-mini and cl100k_base to gpt-4-turbo, gpt-4, gpt-3.5-turbo and the embedding models, and the library can look the encoding up from a model name.
  2. Encode the text. The result is a list of token IDs whose length is the token count. In the cookbook the string "tiktoken is great!" becomes six IDs.
  3. For a chat request, add the overhead of the message format. The cookbook's helper adds 3 tokens for every message and 3 more because every reply is primed with an assistant header.
  4. Compare the total with the budget, which is the context window minus the tokens reserved for the reply, and multiply by the input price for a cost estimate.
  5. After the call, read the prompt token count the API reports and compare it with the local count. The cookbook does this for several models and the numbers agree.

Why this approach fits

A local tokenizer answers the size question with no network call and no charge, and no text leaves the process. Because it applies the same BPE vocabulary as the model, the count for plain text is exact and not an estimate from character length. BPE is also reversible, so the same library can cut a text at a token boundary and decode the kept part back to text when something has to be shortened.

Limitation or tradeoff

The count is only valid for the models whose encodings the library ships. It says little about a request to another vendor's model. The overhead that a chat format, tool definitions or images add is specific to each model: the cookbook warns that the way message tokens are counted may change from model to model and calls its helper an estimate. The recipe itself is archived and lists older models, so check current documentation for the encoding of a newer one. Hidden reasoning tokens cannot be counted in advance at all.

What the sources document

  • The README describes tiktoken as a fast BPE tokeniser for use with OpenAI's models. It lists properties of BPE: it is reversible and lossless, works on arbitrary text, and compresses text so that on average each token corresponds to about 4 bytes. [8]
  • The cookbook says that knowing how many tokens are in a text string tells you whether the string is too long for a text model to process and how much an OpenAI API call costs. [9]
  • The cookbook's encoding table maps o200k_base to gpt-4o and gpt-4o-mini, cl100k_base to gpt-4-turbo, gpt-4, gpt-3.5-turbo and embedding models, p50k_base to Codex models and text-davinci-002 and 003, and r50k_base to GPT-3 models such as davinci. [9]
  • With the gpt-4o-mini encoding the string "tiktoken is great!" encodes to [83, 8251, 2488, 382, 2212, 0], and counting it with o200k_base returns 6. The Japanese example string is 14 tokens under r50k_base and p50k_base, 9 under cl100k_base and 8 under o200k_base. [9]
  • The cookbook's helper for chat messages counts 3 tokens per message plus 3 to prime the reply. Its results equal the counts returned by the API in the example: 129 for gpt-3.5-turbo and gpt-4, and 124 for gpt-4o and gpt-4o-mini. The page notes that this counting may change from model to model. [9]

Example 2 of 5

Claude Code compacting a long coding session that approaches the context window

AnthropicDocumented in official docs

Claude Code is Anthropic's coding agent for the terminal, IDEs and the web. Its documentation pages How Claude Code works, Explore the context window and Manage costs effectively describe what fills the context window during a session and what the product does when the window is nearly full. [13][14][15]

The problem

A coding session reads files, runs commands and collects test output, and every result stays in the conversation. The documentation's walkthrough shows a single bug fix adding file reads of 1,100 to 2,400 tokens each, on top of about 7,850 tokens that are loaded before the user types anything. Hours of such work exceed any fixed window. Ending the session with an error would throw away work in progress, and sending everything again on every step is also what makes a long session expensive.

Where this topic fits

The context window is the agent's working memory. It holds system instructions, CLAUDE.md files, auto memory, skill descriptions, the conversation, file contents and command output. Context management sits at the point where usage approaches the limit: before the next model call the harness shrinks the history and then carries on with the task.

How it is applied, step by step

  1. At the start of a session Claude Code loads the system prompt, CLAUDE.md files, auto memory, environment information, MCP tool names and skill descriptions, before the user has typed anything.
  2. As the agent works, each file read, search result, command output and hook message is added to the conversation and counts against the window.
  3. When usage approaches the limit, Claude Code first clears older tool outputs, which are bulky and often no longer needed.
  4. If that is not enough, it summarises the conversation and continues from the summary. This is the compaction step.
  5. After compaction it reloads what lives on disk: the project-root CLAUDE.md and auto memory are injected again, and up to five recently modified files are read again.
  6. The user can steer the process. The /context command shows what is using space, /compact with a focus says what to keep, /clear starts fresh, and a subagent keeps large reads in its own window.

Why this approach fits

Content in a coding session is not equally valuable. Standing rules, the files being edited and the last few steps matter, while the full output of a test run from an hour ago mostly does not. Clearing the least valuable content first and summarising only when necessary keeps the session alive without asking the user to manage tokens. Rules stored in files survive because they are read again from disk and do not depend on the summary.

Limitation or tradeoff

A summary is lossy. The documentation says that detailed instructions from early in the conversation may be lost, and that path-scoped rules and nested CLAUDE.md files are summarised away until their trigger file is touched again. A single file or tool output that is too large can refill the window straight after each summary, in which case Claude Code stops compacting after a few attempts and shows an error. Compaction also costs tokens: the cost page notes that /compact reads the conversation it summarises, so compacting a large context is itself a large request.

  • As the limit approaches, Claude Code clears older tool outputs first and then summarises the conversation if needed. Requests and key code snippets are preserved, but detailed instructions from early in the conversation may be lost. [13]

Example 3 of 5

Claude Managed Agents billing a session by input, output and cached tokens

AnthropicDocumented in official docs

Anthropic's pricing documentation lists a price per million tokens for each Claude model and describes how Claude Managed Agents, its hosted agent service, bills a session. The page includes a worked cost example for a one-hour session. [3]

The problem

Two agent sessions of the same length can involve very different amounts of model work, so a flat price per session or per request would fit neither. The provider needs a billing unit that follows the work done, and the customer needs to be able to predict a bill from measurements. An agent also resends a large and mostly unchanged prefix of instructions, tool definitions and history on every model call. Charging the full input price for that prefix each time would make long sessions expensive.

Where this topic fits

The token counts reported for each model call are the meter. Each category of token has its own price: input that was not cached, cache writes, cache reads and output. The bill is the sum of count times price over the session. Managed Agents adds one item that is not measured in tokens, the time the session spends running.

How it is applied, step by step

  1. Every model call in the session reports its input and output token counts. With prompt caching the input is split into uncached input, cache writes and cache reads.
  2. Each count is multiplied by the model's price per million tokens. For Claude Opus 5 the page lists 5 USD for input and 25 USD for output.
  3. Tokens read from the prompt cache are charged at 0.1 times the base input price on most models, so a repeated prefix is charged at a tenth of the normal input price.
  4. Session runtime is added at 0.08 USD per session-hour, and it accrues only while the session status is running.
  5. The total is the sum of these lines. The page's example comes to 0.705 USD without caching and 0.525 USD when 40,000 of the 50,000 input tokens are cache reads.

Why this approach fits

Tokens are a direct measure of how much the model had to read and write, so the price follows the work: a long prompt or a long answer costs more than a short one. Separate rates show where the cost sits, since output is priced at five times input in every row of the table. The cache-read rate rewards a stable prefix, which is exactly what an agent sends again on each step. A customer can reproduce the bill from the usage figures and the price table.

Limitation or tradeoff

The bill is hard to predict before a call, because the number of output and thinking tokens is only known afterwards. The price per token is not always constant: the page prices Claude Haiku 5.5 higher for prompts over 100,000 tokens. Token counts depend on the tokenizer, and the page notes that newer models produce approximately 30% more tokens for the same text. The example leaves out cache writes, which cost more than plain input (1.25 times for the 5-minute cache), and the Batch API discount does not apply to Managed Agents sessions. Prices also change, so the figures here are a dated snapshot.

What the sources document

  • Prices are listed per million tokens (MTok), with separate prices for base input, cache writes, cache hits and output. Claude Opus 5 is listed at 5 USD per MTok for input and 25 USD per MTok for output. [3]
  • Claude Managed Agents is billed on two dimensions: tokens at the model pricing rates, and session runtime at 0.08 USD per session-hour, which accrues only while the session's status is running. [3]
  • The page's worked example is a one-hour session on Claude Opus 5 that consumes 50,000 input tokens and 15,000 output tokens, for a total of 0.705 USD. If 40,000 of the input tokens are cache reads, the total is 0.525 USD. [3]
  • A cache read costs 0.1 times the base input price on most models, a 5-minute cache write costs 1.25 times and a 1-hour cache write costs 2 times. The Batch API's 50% discount is listed as not applying to Claude Managed Agents sessions. [3]
  • Claude Haiku 5.5 is priced by prompt length. A request whose prompt is over 100,000 tokens pays 0.50 USD per MTok for input and 2.50 USD for output, against 0.10 USD and 0.50 USD for shorter prompts. [3]

Gemini API converting images, video and audio into token counts

GoogleDocumented in official docs

Google's Gemini API documentation page Understand and count tokens explains how the API counts tokens for text and for images, video and audio, and how to read a model's input and output token limits. [10]

The problem

A model that accepts pictures, recordings and video still has one context window and one price list, and both are stated in tokens. Before uploading a file, a developer needs to know how much of the window it will occupy and roughly what it will cost. A file's size in megabytes or its length in minutes does not answer that directly.

Where this topic fits

The conversion happens on the input side. Each image, second of audio and second of video is assigned a token count by fixed rules. Those tokens are added to the text, the system instruction and the tool definitions, and the total has to stay within the model's input limit. The same totals are the basis of the bill.

How it is applied, step by step

  1. Text is tokenized as usual. For Gemini models the documentation gives about 4 characters per token.
  2. An image that is at most 384 pixels in both dimensions counts as 258 tokens. A larger image is tiled into 768 by 768 pixel tiles, and each tile counts as 258 tokens.
  3. Audio is counted at 32 tokens per second.
  4. Video in the default static mode has its frames sampled at 1 frame per second and counts as about 100 tokens per second at low resolution or about 300 at high resolution.
  5. The media tokens are added to the text, system instruction and tool tokens, and the sum is compared with the model's input token limit, which can be read from the API.
  6. For an exact figure the developer calls the count method before sending, and reads the usage data of the response afterwards.

Why this approach fits

Using one unit for every kind of input means that the same window check and the same cost formula cover a prompt that mixes text, pictures and recordings. Rates that depend only on duration and resolution let a developer estimate the size of a file before uploading it, and decide in advance whether to send audio only, lower the resolution or split a long recording.

Limitation or tradeoff

The rates are approximate and belong to one provider and one documentation version. Other providers apply their own rules to media, so these numbers do not transfer. Video dominates everything else: by the documented rates, an hour of high-resolution video is about a million tokens. The page's agentic mode loads only the parts of a video needed to answer and can be far cheaper, but its token use varies with the content, so it cannot be predicted exactly. Lowering the resolution saves tokens and loses visual detail.

What the sources document

  • For Gemini models a token is equivalent to about 4 characters, and 100 tokens are equal to about 60 to 80 English words. [10]
  • Images of at most 384 pixels in both dimensions count as 258 tokens. Larger images are tiled into 768 by 768 pixel tiles, each counting as 258 tokens. [10]
  • Audio is counted at 32 tokens per second, and the page's example puts a 60-second clip at about 1,920 tokens. [10]
  • In the default static mode, video is about 100 tokens per second at low resolution or about 300 at high resolution, with frames sampled at 1 FPS. The page says a 1-hour lecture that would use about 1.08M tokens in static mode might use about 108K in agentic mode. [10]
  • The context window is described as the combined limit of input and output tokens, a model's input and output token limits can be read programmatically, and system instructions and tools count as input tokens. [10]

Aider fitting a map of a whole repository into a fixed token budget

AiderDocumented in an open-source project

Aider is an open-source AI pair-programming tool that runs in the terminal. Its documentation pages Repository map and Token limits describe how it gives the model an overview of a codebase and how it deals with the token limits of the model in use. [16][17]

The problem

To edit one file well, a model needs to know about classes and functions defined elsewhere in the repository. Sending every file would raise the cost of each request and, for most projects, would not fit. The documentation adds that for a large repository even a condensed map of the code may be too large for the model's context window.

Where this topic fits

The repository map is one slice of the prompt, next to the system prompt, the files the user has added to the chat and the chat history. Aider gives that slice its own token budget. A ranking step decides which parts of the map earn a place inside the budget, and the rest of the window stays free for the files being edited and for the reply.

How it is applied, step by step

  1. Aider builds a map of the repository that lists files together with their most important classes and functions, including types and call signatures, and leaves out the full file contents.
  2. It builds a graph in which each source file is a node and edges connect files that depend on each other, and ranks the map's contents with a graph ranking algorithm.
  3. It keeps the highest-ranked parts that fit in the map's token budget. The budget is set by the --map-tokens switch and defaults to 1k tokens.
  4. It sends the map with each change request. If the model needs more code, it can name the files it wants and aider offers to add them to the chat.
  5. Aider adjusts the budget as the chat changes, and expands the map significantly when no files have been added to the chat yet.
  6. If a request still exceeds a model limit, aider reports the provider's error, and the user can free space with /drop and /clear after checking usage with /tokens.

Why this approach fits

A fixed budget turns an open question (how much of this repository can we afford to show?) into a ranking problem with a known answer size. Signatures carry much of what the model needs to call existing code correctly at a fraction of the tokens of full files. The cost of the overview per request stays predictable whether the repository has fifty files or fifty thousand.

Limitation or tradeoff

A map of about a thousand tokens leaves out most of a large codebase, and the ranking can miss the one file that matters, in which case the model writes code that duplicates or misuses something it never saw. The documentation states that aider's token counts are estimates and that aider does not enforce limits itself; it only reports the errors the API provider returns. The output limit is a separate constraint: the page's sample error shows a request that used 4,096 of 4,096 output tokens while the input was far below the context window.

  • For large repositories even the repository map might be too large for the context window, so aider selects the most relevant portions with a graph ranking algorithm, computed on a graph where each source file is a node and edges connect files which have dependencies. [16]
  • The token budget for the map is set by the --map-tokens switch, which defaults to 1k tokens. Aider adjusts the size of the map dynamically and expands it significantly at times, especially when no files have been added to the chat. [16]
  • The Token limits page says a model's context window limits how many total tokens of input and output it can process, and that each model also has a limit on output tokens. 4Common mistakes

  1. Estimating tokens from a word count, or with a tokenizer that belongs to a different model.

    Why it causes problems
    Budgets and cost forecasts come out wrong by a wide margin. Code, numbers, long identifiers and text in languages other than English use more tokens per word than English prose, and a newer tokenizer can produce noticeably more tokens for unchanged text. The error surfaces later as a rejected request or an invoice that does not match the forecast.
    How to recognise it
    The input token count in the response usage is consistently higher than your estimate, or a prompt that fitted on one model is rejected as too long on another.
    How to fix it
    Count with the tokenizer or count endpoint of the model you will call, on samples of real traffic, and recount whenever you change model. Keep the four-characters rule for rough sizing only.

  2. Parsing a response without checking why generation stopped.

    Why it causes problems
    A reply that hit the output limit ends mid-sentence or mid-object. Code that assumes it is complete fails on invalid JSON, runs a half-written tool call, or shows users an answer that silently lacks its conclusion.
    How to recognise it
    Intermittent JSON parse errors on long answers, replies that end without punctuation, and responses whose output token count equals your max output setting exactly.
    How to fix it
    Read the stop reason or status on every response. Treat a token-limit stop as a failure for structured output, retry with a higher limit, and set the limit from measured reply lengths plus headroom.

  3. Resending the whole conversation forever with no plan for a full window.

    Why it causes problems
    The application works in every test and then fails for the most engaged users, at whichever turn their history crosses the limit. Until then each turn costs more than the one before, because the entire history is billed again as input.
    How to recognise it
    Input tokens per request that rise steadily within a session, errors saying the prompt is too long that appear only in long sessions, and cost per conversation that grows faster than its number of turns.
    How to fix it
    Track input tokens per request, pick a threshold well below the window, and decide in advance what happens there: stop, trim the oldest turns, summarise, or move bulky content out of the history.

  4. Budgeting from the input price alone, or forgetting that reasoning tokens are billed as output.

    Why it causes problems
    Output is commonly priced several times higher than input, so a feature with long answers or heavy reasoning can cost far more than an input-based estimate. Hidden reasoning tokens add output cost that never appears in the visible reply.
    How to recognise it
    The usage data shows output or reasoning token counts much larger than the visible text would explain, and the monthly bill is dominated by output although prompts are far longer than replies.
    How to fix it
    Price input and output separately using measured averages for both, include reasoning tokens in the output figure, and cap output with a limit that matches the task.

  5. Treating the context window as storage and filling it because the space exists.

    Why it causes problems
    Every token in the prompt is billed again on every call, and a long context makes the model less reliable at finding and using the part that matters. Anything kept only in the conversation is also the first thing lost when history is trimmed or summarised.
    How to recognise it
    Prompts that carry whole manuals or full chat logs for questions that need one paragraph, and answers that ignore an instruction given much earlier in a long session.
    How to fix it
    Send only what the current request needs, retrieve relevant passages in place of whole documents, and keep standing rules in the system prompt or in files that are reloaded, not in old turns.

  6. Counting only the user's message and ignoring system prompts, tool definitions and media.

    Why it causes problems
    The parts nobody typed are often the largest. Tool definitions, long system prompts and images are sent on every request, so an estimate based on the visible message can be several times too low.
    How to recognise it
    A short question produces an input token count in the hundreds or thousands, and the count barely changes when the question changes.
    How to fix it
    Count the complete request as it is sent, including system prompt, tools and attachments. Remove tools and instructions the task does not need, and cache the stable prefix where the provider supports it.

WINDOW = 4096                      # tokens the model can hold: input plus output
MAX_OUTPUT = 512                   # tokens reserved for each reply

PRICE_IN, PRICE_OUT = 1.00, 5.00   # USD per million tokens
# (user_tokens, assistant_tokens) for each exchange, in order
EXCHANGES = [(120, 380), (90, 410), (200, 450), (60, 300), (150, 500),
             (110, 420), (80, 360), (170, 480), (140, 390), (100, 440)]


def input_tokens(history, user_tokens):
    """Tokens sent in one request: system prompt, kept history, new user message."""
    return SYSTEM + sum(user + assistant for user, assistant in history) + user_tokens


def fits(tokens_in):
    return tokens_in + MAX_OUTPUT <= WINDOW


def trim(history, user_tokens):
    """Drop the oldest whole exchanges until the request fits. Returns a new list."""
    kept = list(history)
    while kept and not fits(input_tokens(kept, user_tokens)):
        kept = kept[1:]
    return kept


def simulate(trimming):
    history, rows, total_in, total_out = [], [], 0, 0
    for number, (user_tokens, assistant_tokens) in enumerate(EXCHANGES, start=1):
        if trimming:
            history = trim(history, user_tokens)
        tokens_in = input_tokens(history, user_tokens)
        if not fits(tokens_in):
            return [*rows, (number, len(history), tokens_in, "DOES NOT FIT")], total_in, total_out
        rows = [*rows, (number, len(history), tokens_in, "ok")]
        total_in, total_out = total_in + tokens_in, total_out + assistant_tokens
        history = [*history, (user_tokens, assistant_tokens)]
    return rows, total_in, total_out


def report(title, trimming):
    rows, total_in, total_out = simulate(trimming)
    print(title)
    for number, kept, tokens_in, status in rows:
        print(f"  request {number:2}: history {kept}, input {tokens_in:4}, "
              f"with reserve {tokens_in + MAX_OUTPUT:4}  {status}")
    cost = (total_in * PRICE_IN + total_out * PRICE_OUT) / 1_000_000
    print(f"  billed: {total_in} input + {total_out} output tokens = {cost:.6f} USD")


if __name__ == "__main__":
    report("Without trimming", trimming=False)
    report("With drop-oldest trimming", trimming=True)

Over 20,000 requests that is 3,030 million tokens, or 3,030×2=6,0603{,}030 \times 2 = 6{,}0603,030×2=6,060 dollars per day for input alone, about twenty times the current $300. The request fits the window, but fitting is not the same as being affordable, and a long context also makes it harder for the model to use the right passage. Retrieving the few relevant policy sections for each ticket keeps the prompt small (see Retrieval-Augmented Generation).

  • Did you count 19,900 cache reads and not 20,000?
  • Did you name latency as the reason the Batch API does not suit a live chat?
  • Does your answer to question 4 end with recounting on the current model and not with a fixed multiplier?
  • Did you get 6,060 USD per day of input for the full manual?
