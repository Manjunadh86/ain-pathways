Context Engineering

Context engineering is the practice of deciding, for every model call, which tokens go into the context window: instructions, tool definitions, retrieved data, tool results, conversation history and memory. The aim is the smallest set of information that lets the model do the next step well.

1Overview

Why it matters

A language model can only use what is in its context window on a given call. In a single question and answer, that is a prompt you wrote. In an agent or a long chat, most of the window is filled by things nobody wrote on purpose: tool outputs, old turns, retrieved chunks and the definition of every connected tool. When an agent picks the wrong tool out of sixty, repeats a search it ran twenty steps ago, forgets the constraint from the first message, or keeps acting on a wrong fact it saved in its own notes, the cause is usually in the context and not in the model or the wording of the prompt.

Anyone who builds RAG pipelines, agents or long-running assistants needs this skill, because the context decides quality, cost and latency together. Every token is paid for again on each call (at a lower rate when a cached prefix is reused), a full window forces you to drop or summarise something, and published measurements show accuracy falling as inputs get longer even when the window is far from full. Compaction, isolation and memory are the standard remedies, and each one loses information in a specific way that you have to plan for.

Key terms

Context
Everything the model receives on one call: instructions, tool definitions, retrieved data, tool results, earlier messages and any memory that was read back in.
Context window
The maximum number of tokens a model can take as input plus output on one call. It is a hard limit, and quality can fall well before it is reached.
Context engineering
Choosing, compressing and ordering what goes into the context on every call, and deciding what to keep outside it.
Context rot
The measured tendency of models to use information less reliably as the number of input tokens grows.
Compaction
Replacing older parts of a conversation with a shorter summary so that work can continue in less space.
Tool-result clearing
Replacing old tool outputs with a short placeholder while keeping the record that the tool was called.
Just-in-time context
Keeping only references such as file paths, URLs or tool names in the window and loading the content when a step needs it.
Agentic memory
Notes, plans or facts that an agent saves outside the context window and reads back later, so they survive compaction and new sessions.
Context isolation
Running a subtask in a separate context window, usually a subagent, so that its working material never enters the main context.
Prompt caching
A provider feature that reuses the computation for an unchanged prompt prefix, making repeated tokens cheaper and faster as long as nothing earlier in the prompt changes.

2Explanation

Introduction

You have already put things into a model's context on purpose. In Retrieval-Augmented Generation you pasted retrieved chunks into the prompt, and in Tool Calling you sent tool definitions and fed tool results back. Each lesson looked at one ingredient. Context engineering looks at the whole input: everything the model receives on one call, and whether each part deserves its place.

Think of briefing a colleague who is taking over a task and has ten minutes to read. You would not hand over every email, log file and chat thread from the last month. You would give the goal, the rules that matter, the two documents they need and a note on what has been tried. With too little they guess. With too much, the important line is buried on page 40. A model is in that position on every call, except that it starts from nothing each time and reads only what your program sends.

Context is that complete input: the set of tokens the model sees when it generates. Context engineering is deciding what goes into it. Anthropic's engineering team describes it (opens in a new tab) as curating and maintaining the optimal set of tokens during inference, including everything that lands there besides the prompt. LangChain's overview (opens in a new tab) compares the model to a CPU and the context window to its RAM: working memory with a fixed capacity that something has to manage.

The diagram shows the shape of the job. Several stores hold far more than can be sent. Before each call your program selects from them, compresses what is too long and orders the result. After the call, the reply and any tool result flow back into the history, and anything worth keeping is written to memory. In an agent this happens on every iteration of the loop, so the work is never finished in the way a prompt is finished.

This lesson covers what competes for the window, how long contexts fail, the four moves that fix them (select, compress, write, isolate), how compaction and isolation work in real systems, and where context engineering ends and prompt engineering begins.

How it works

What competes for the window

Six kinds of content share one token budget.

ContentComes fromHow it growsMain lever
InstructionsSystem prompt, rules files, examplesSlowly, as rules are addedKeep the minimal set that fully specifies the behaviour
Tool definitionsYour tools, MCP serversWith every tool connectedFewer, clearer tools; load definitions on demand
Retrieved dataSearch and RAGWith every chunk per queryRank, filter and cap by tokens
Tool resultsOutput of each tool callFastest: one per stepTrim at the source, clear old ones, store by reference
HistoryEarlier messagesWith every turnSummarise old turns, keep recent ones
MemoryNotes saved outside the windowOnly by what is read backRead selectively, verify before writing

Claude Code's documentation gives representative numbers (opens in a new tab) for a coding session. About 7,850 tokens load before the user types (system prompt, instruction files, memory, environment details, skill descriptions and a list of tool names), and then each file read adds between 1,100 and 2,400 tokens. The fixed part is small. Tool results and history grow without anyone deciding, so most of the engineering goes there.

How long contexts fail

A context can fail long before it is full. Two effects have been measured directly.

  • Context rot. Chroma tested 18 models (opens in a new tab) and found that performance becomes less reliable as input length grows, even on simple tasks. On a conversational memory benchmark, models answered markedly better from a focused prompt of about 300 tokens than from the full history of about 113,000 tokens that contained the same facts.
  • Position effects. The paper Lost in the Middle (opens in a new tab) found that models do best when the relevant passage sits at the beginning or end of the input and significantly worse when it sits in the middle. The models it tested date from 2023, so measure the size of the effect on the model you use.

The essay How Long Contexts Fail (opens in a new tab) names four more ways in which content already in the window does damage.

The common thread is that the model weighs everything in the window. Irrelevant content is not skipped. It competes with the content that matters.

Four moves: select, compress, write, isolate

LangChain's overview groups the remedies into four moves, and the names are worth memorising.

Select: load by reference, on demand. Keep identifiers in the window (file paths, URLs, tool names) and fetch the content only when a step needs it. Anthropic calls this just-in-time context. Cursor applies it to tool definitions: it sends only the names of MCP tools and lets the agent look up a description when needed. In Cursor's A/B test this reduced total agent tokens by 46.9% (opens in a new tab) in runs that called an MCP tool. For retrieval, selecting means ranking, a relevance threshold and a token cap in place of a fixed top-k.

Compress: keep the meaning, drop the bulk. There are three levels, from least to most lossy:

  1. Trim at the source. Make the tool return the 20 relevant lines and not the whole log.
  2. Clear old tool results. Replace results the agent has already used with a short placeholder. The record of the call stays, so the model still knows what it did.
  3. Compact. Replace older turns with a summary and continue from it.

Providers now offer the last two as API features. The Claude API's context editing (opens in a new tab) (in beta) clears the oldest tool results once the prompt passes a threshold. Its compaction (opens in a new tab) (also in beta) writes a summary on the server, either when your code requests one or, with threshold compaction (opens in a new tab), when input tokens reach a trigger (150,000 by default). Anthropic's context editing page calls server-side compaction the primary strategy for most long-running conversations and keeps tool-result clearing for cases that need finer control. OpenAI's Responses API has a comparable server-side compaction (opens in a new tab) setting. This Claude request parameter, sent with the beta header context-management-2025-06-27, clears old tool results:

python
context_management = {"edits": [{
    "type": "clear_tool_uses_20250919",
    "trigger": {"type": "input_tokens", "value": 30000},        # default: 100,000
    "keep": {"type": "tool_uses", "value": 3},                  # newest results stay
    "clear_at_least": {"type": "input_tokens", "value": 5000},  # skip small clears
}]}

What a summary keeps decides whether the agent can carry on. It needs the goal, the decisions already made, the open problems and the references required to reload details. Anthropic describes Claude Code's compaction as preserving architectural decisions, unresolved bugs and implementation details while discarding redundant tool output, and warns that overly aggressive compaction loses subtle but critical context.

Prefer compression that is restorable. When Manus drops a web page from the context it keeps the URL, so the agent can fetch the page again if it turns out to matter.

Write: keep state outside the window. A plan, a to-do list or a notes file saved to disk survives compaction and costs a few hundred tokens to read back. The Claude API's memory tool (opens in a new tab) is a directory of files that the model checks before a task and updates as it works, while your application stores the files. Agent Memory covers memory design in depth.

Isolate: give a subtask its own window. A subagent starts with a fresh context, does the token-heavy exploring there and returns only a summary.

Anthropic notes that a subagent may use tens of thousands of tokens and return 1,000 to 2,000. The price is more total tokens, plus the risk that the summary leaves out something the lead agent needed.

Order and stability

Two details matter besides what is included.

  • Keep the front of the prompt stable. Providers cache the computation for an unchanged prefix. A timestamp at the top of the system prompt, a reordered tool list or an edit to an old message invalidates the cache for everything after it. Put stable content first and append new content at the end.
  • Put what must not be forgotten near the end. Manus has its agent rewrite a to-do file as it works, which restates the goal in the most recent part of the context. The Manus author says this keeps the objectives out of the middle of a long context, where models use information least reliably.

How this differs from prompt engineering

Prompt engineeringContext engineering
QuestionHow should the instructions be worded?What should the model see on this call?
Unit of workOne prompt, written and versionedThe whole window, rebuilt on every call
InputsInstructions, examples, output formatThose plus tool definitions, retrieved data, tool results, history and memory
Typical failureAn ambiguous or missing instructionA correct instruction that is buried, contradicted or crowded out
Done whenThe prompt passes its evaluationNever: it runs on each iteration

Prompt engineering is one part of context engineering, not something it replaces. A clear system prompt is still required. In a 50-step agent run it is a small fraction of the tokens the model reads, and the rest needs the same care.

Worked example: Twenty agent steps under three context policies (none, tool-result clearing, compaction)

An agent has 3,460 tokens of fixed context: 1,200 of instructions, 1,800 of tool definitions, 400 of memory and a 60-token task. Each step adds a tool call of 80 tokens and a tool result of 2,500 tokens. The script measures how many input tokens each of 20 model calls would send under three policies:

  • Unmanaged. Send everything, as in the formula from The Agent Loop.
  • Clearing. When a request would exceed 24,000 tokens, keep the 3 newest tool results and replace each older one with a 20-token placeholder. This mirrors the trigger and keep settings shown above.
  • Compaction. When a request would exceed 24,000 tokens, replace everything except the 2 newest steps with a 600-token summary and continue from there.

Save this as context_budget.py. It needs only the Python standard library.

python
FIXED = {"instructions": 1200, "tool definitions": 1800, "memory": 400, "task": 60}
CALL, RESULT = 80, 2500     # tokens added per step: the model's tool call, then the tool result
TRIGGER = 24000             # manage the context when a request would exceed this
KEEP_RESULTS = 3            # clearing: newest tool results kept word for word
PLACEHOLDER = 20            # clearing: tokens left where a result was removed
KEEP_STEPS = 2              # compaction: newest steps kept word for word
SUMMARY = 600               # compaction: tokens in the summary of older steps
BASE = sum(FIXED.values())


def unmanaged(steps_done):
    return BASE + steps_done * (CALL + RESULT)


def clearing(steps_done):
    """Stateless: the client keeps the full history, the edit is applied to each request."""
    if unmanaged(steps_done) <= TRIGGER:
        return unmanaged(steps_done)
    kept = min(steps_done, KEEP_RESULTS)
    cleared = steps_done - kept
    return BASE + steps_done * CALL + kept * RESULT + cleared * PLACEHOLDER


def run(calls=20):
    rows, history, summary, summariser_input = [], 0, 0, 0
    for call in range(1, calls + 1):
        steps_done = call - 1
        if call > 1:
            history += CALL + RESULT                 # the previous step joins the history
        if BASE + summary + history > TRIGGER:       # compaction is stateful: it rewrites history
            summariser_input += BASE + summary + history
            summary, history = SUMMARY, KEEP_STEPS * (CALL + RESULT)
        rows.append((call, unmanaged(steps_done), clearing(steps_done), BASE + summary + history))
    return rows, summariser_input


rows, summariser_input = run()
print("call  unmanaged  clearing  compaction")
for call, a, b, c in rows:
    if call in (1, 5, 8, 9, 10, 14, 15, 16, 20):
        print(f"{call:>4}  {a:>9,}  {b:>8,}  {c:>10,}")
totals = [sum(row[i] for row in rows) for i in (1, 2, 3)]
print(f"input tokens over 20 calls: {totals[0]:,} | {totals[1]:,} | {totals[2]:,}")
print(f"extra input read by the summariser: {summariser_input:,}")
print(f"largest request: {max(r[1] for r in rows):,} | {max(r[2] for r in rows):,} | {max(r[3] for r in rows):,}")

Check call 9 by hand. Eight steps are done, so the unmanaged request is 3,460 + 8 × 2,580 = 24,100 tokens, which is over the trigger. Clearing keeps all 8 tool calls (640), 3 full results (7,500) and 5 placeholders (100): 3,460 + 640 + 7,500 + 100 = 11,700. Compaction keeps the summary (600) and 2 full steps (5,160): 3,460 + 600 + 5,160 = 9,220.

What the numbers mean:

  • Unmanaged growth is the expensive default. The last request is 52,480 tokens and the 20 calls send 559,400 in total. On a model with a 32,000-token window, call 12 (31,840 tokens) leaves almost no room for a reply and call 13 (34,420) does not fit at all.
  • Clearing is cheap and steady. After the trigger each step adds only 100 tokens. The model still sees every tool call it made but the content of only the last three results. If step 4 held a fact that matters at step 18, the agent must have written it down or must call the tool again.
  • Compaction produces a sawtooth. The context falls to 9,220 and climbs again by 2,580 a step, so it compacts a second time at call 15. Each compaction is itself a model call that reads the oversized context (24,100, then 24,700 tokens, 48,800 together), which brings its real total to 336,760. Whatever the summary omits is gone for good.
  • Neither policy is free. Both rewrite earlier parts of the prompt, which invalidates a prompt cache from the edited point onward, and the totals here assume no caching at all. With caching, an append-only context is cheaper per token than this comparison suggests. In this simple model, clearing edits the prompt on every call after the trigger. The clear_at_least setting exists to batch such edits, so that each one removes enough tokens to be worth the lost cache.

Real systems combine the two. Claude Code's documentation says it clears older tool outputs first and summarises the conversation only if that is not enough.

Edge cases and limitations

Clearing or compacting throws away the prompt cache
Both edits rewrite earlier parts of the prompt, and a cached prefix is only reusable while it is unchanged. The Claude context editing documentation states that clearing tool results invalidates cached prompt prefixes and offers the clear_at_least setting so that a clear only happens when it removes enough tokens to be worth the new cache write. Set the trigger high enough that edits are occasional, and never edit the context a little on every call.
Instructions given in conversation can vanish at compaction
A summary keeps what the summariser judged important. The Claude Code documentation warns that detailed instructions from early in a conversation may be lost, and that path-scoped rules, which load into message history, are summarised away with everything else. Rules in the project-root instruction file are re-injected from disk instead. In your own agent, keep must-follow rules in a pinned section that your code re-adds after every compaction, and do not rely on the summary to carry them.
One oversized tool result defeats compaction
If a single file or command output is larger than the space compaction frees, the context refills at once. Claude Code documents this case: it stops auto-compacting after a few attempts and reports an error instead of looping. Summarising cannot fix an input that is too big on arrival. Cap output inside the tool, or write it to a file and return the path with a short preview.
Deleting failures and keeping falsehoods are opposite mistakes
The Manus team leaves failed actions and their error messages in the context, because seeing a failure makes the model less likely to repeat that action. Context poisoning is a different thing: a false statement recorded as if it were true. Keep honest records of what was tried and what happened. Correct or delete claims that are untrue, especially in memory files, which are read back as trusted input.
A subagent's summary can omit what the lead agent needed
Isolation is lossy by design, since only the summary crosses the boundary. Anthropic's research system addresses this by letting subagents store their full output in an external system and pass back a lightweight reference, which avoids a game of telephone through the lead agent. Ask for a specific output format in the task brief, and keep the full material retrievable by reference.

When to use it, and when something simpler is enough

Use it when

  • An agent runs for more than a handful of steps, so tool results and history, not your prompt, make up most of the input.
  • A conversation or session is expected to outlast the context window, or to run long enough that the cost of resending the context matters.
  • The application connects many tools or MCP servers and the model picks the wrong tool or overlooks the right one.
  • Retrieval returns more text than the question needs, and answers cite the wrong passage or miss the right one.
  • Facts must persist across sessions, which means deciding what is written to memory and what is read back.

Think twice when

  • The task is a single model call with a short, fixed input. Careful prompt wording and an evaluation set are enough.
  • All the reference material fits comfortably and does not change during the task. Sending it whole in a stable, cached prefix is simpler than building retrieval or compaction.
  • You are considering subagents for tightly coupled work in which every part needs the same details. Isolation hides exactly the context those parts must share.
  • You have not yet measured where the tokens go. Add a per-category token count first, because the right fix depends on which category is growing.

A simpler alternative. Start a fresh session for each task, keep a sliding window of the most recent turns and write a clear system prompt. That is enough for short chats and single-purpose assistants. It stops being enough when the agent needs something that has scrolled out of the window, when one task no longer fits in one window, or when tool definitions and tool results outweigh the conversation itself.

Key takeaways

  • The context is everything the model receives on a call, and in agents most of it is tool results and history that nobody wrote deliberately.
  • More context is not safer: reliability falls as inputs grow, facts in the middle are used less, and wrong, irrelevant or contradictory content actively harms answers.
  • The four moves are select (load by reference when needed), compress (trim, clear, summarise), write (keep notes and memory outside the window) and isolate (give a subtask its own window).
  • Clearing old tool results is cheap and keeps the record of each call, while compaction can free more space at once but permanently loses whatever the summary leaves out.
  • Rules that must survive belong in a pinned part of the context that is re-added after compaction, and stable content belongs at the front where prompt caching can reuse it.
  • Prompt engineering words the instructions once, whereas context engineering rebuilds the whole input on every call and treats the prompt as one part of it.

Example 1 of 5

Anthropic's multi-agent research system isolating searches in subagent context windows

AnthropicDocumented in an engineering article

Anthropic's engineering article How we built our multi-agent research system (June 2025) describes the system it built for open-ended research questions in Claude. A lead agent plans the work and delegates searching to subagents. The later article Effective context engineering for AI agents links to it as a pattern that showed a substantial improvement over single-agent systems on complex research tasks. [7][1]

The problem

An open-ended research question needs many searches and page reads, and nobody can say in advance which ones. Each search returns far more text than the final answer will use. If one agent did everything in a single context, the raw results of early searches would crowd its window while it was still deciding what to look for next, and the article notes that a context over 200,000 tokens is truncated.

Where this topic fits

Isolation sits between planning and synthesis. Before it, the lead agent analyses the query and writes a plan. After it, the lead agent reads condensed findings, decides whether more research is needed and passes the result to a citation step. The bulky middle part, searching and reading, happens in separate context windows.

How it is applied, step by step

  1. The lead agent analyses the query, develops a strategy and saves its plan to memory so the plan survives if its own context is later truncated.
  2. It writes a task description for each subagent that gives an objective, an output format, guidance on which tools and sources to use, and clear boundaries.
  3. Each subagent runs its own search loop in its own context window, evaluating results after each tool call and refining the next query. Several subagents run in parallel.
  4. Each subagent condenses what it found and returns that to the lead agent. For large outputs it can store the full work in an external system and return a lightweight reference.
  5. The lead agent synthesises the returned findings and either starts more subagents or finishes. A citation agent then attaches sources to the report.

Why this approach fits

Research splits into directions that can be explored independently, so each direction can have its own window without the others needing to see its working material. The lead agent's context then holds only plans and conclusions, which is what it needs for synthesis. Running the subagents in parallel also means the system can read more than one context window's worth of material in the time of one search loop.

Limitation or tradeoff

Isolation costs tokens. The article reports that multi-agent systems use about 15 times more tokens than chat interactions, so the task has to be valuable enough to justify that. Subagents that receive vague briefs duplicate each other's searches or misread the task. The article also says the approach suits tasks that parallelise and is a poor fit when all agents need the same context or the subtasks depend on each other, and it names most coding tasks as an example.

What the sources document

  • The system uses an orchestrator-worker pattern in which a lead agent coordinates the process and delegates to specialised subagents that operate in parallel. [7]
  • The article says subagents facilitate compression by operating in parallel with their own context windows, exploring different aspects of the question before condensing the most important tokens for the lead research agent. [7]
  • Anthropic reports that a multi-agent system with Claude Opus 4 as lead agent and Claude Sonnet 4 subagents outperformed single-agent Claude Opus 4 by 90.2% on its internal research evaluation, and that multi-agent systems use about 15 times more tokens than chats. [7]
  • Each subagent needs an objective, an output format, guidance on the tools and sources to use, and clear task boundaries. With vague instructions, subagents misinterpreted the task or performed the same searches as other agents. [7]
  • The context engineering article states that a subagent may use tens of thousands of tokens or more while exploring but returns a condensed summary, often of 1,000 to 2,000 tokens. [1]

The facts above come from the cited sources. The steps and analysis in this example are our explanation of how they fit together.

Example 2 of 5

Manus keeping a long agent context cache-friendly, restorable and focused

ManusDocumented in an engineering article

Manus is a general-purpose AI agent product. In Context Engineering for AI Agents: Lessons from Building Manus (July 2025), Yichao "Peak" Ji describes the context design the team arrived at after rebuilding its agent framework four times. [6]

The problem

A Manus task takes many tool calls, and each one appends an action and an observation to the context while the model's output stays short. Input tokens therefore dominate both cost and latency. Observations such as web pages and PDFs can be huge, and the agent tends to drift from its original goal over a long run.

Where this topic fits

The design governs how every request in the agent loop is laid out: what sits at the front and never changes, how new steps are added, where large observations go, and what is placed at the end of the context before each model call.

How it is applied, step by step

  1. The system prompt and tool definitions form a stable prefix. Nothing that changes from call to call, such as a timestamp precise to the second, is placed at the start.
  2. The context is append-only. Earlier actions and observations are not edited, and serialisation is deterministic so that the same content always produces the same tokens.
  3. The set of tool definitions stays fixed during a task. To limit which tools can be chosen at a given point, the team constrains the model's output while decoding and leaves the definitions untouched.
  4. Large observations are kept in the sandbox file system. The context keeps the URL or file path, so the content can be dropped from the context and read again later if needed.
  5. The agent maintains a todo.md file and rewrites it as the task proceeds, which places the current objectives at the end of the context.
  6. Failed actions and their error output stay in the context so the model can see what did not work.

Why this approach fits

When input outweighs output by about 100 to 1, the price of resending the context is the main cost, and prefix caching only helps if the prefix stays the same. An append-only layout gets that for free. Keeping large content in files and only references in the context gives the agent an effectively unlimited store without paying for it on every call, and because the reference remains, nothing is lost for good.

Limitation or tradeoff

Constraining the model's output during decoding requires control over the inference stack or a provider feature such as response prefill, which not every hosted API offers. A kept URL only restores content if the page is still there and unchanged. Leaving every failed attempt in the context makes it longer, so this design still needs a compression step for very long runs. The article presents these as lessons from one product, not as measured comparisons.

What the sources document

  • The author calls the KV-cache hit rate the single most important metric for a production-stage AI agent and reports an average input-to-output token ratio of around 100 to 1 in Manus. [6]
  • The article quotes Claude Sonnet prices of 0.30 USD per million cached input tokens against 3 USD per million uncached, and advises keeping the prompt prefix stable, making the context append-only and serialising deterministically. [6]
  • Manus avoids adding or removing tools in the middle of a task because tool definitions sit near the front of the context and any change invalidates the cache for what follows. It masks token logits during decoding to prevent or enforce the choice of certain actions. [6]
  • The team treats the file system as context and designs compression to be restorable: a web page's content can be dropped as long as the URL is preserved, and a document's content omitted if its path remains available in the sandbox. [6]
  • A typical Manus task requires around 50 tool calls on average. The agent creates a todo.md file and updates it step by step, which the author says recites the objectives into the end of the context and avoids lost-in-the-middle issues. [6]

The facts above come from the cited sources. The steps and analysis in this example are our explanation of how they fit together.

Example 3 of 5

Dropbox Dash replacing many retrieval tools with one search tool and a search agent

DropboxDocumented in an engineering article

Dropbox Dash is an AI assistant for finding and working with a company's content across connected apps. The Dropbox Tech article How Dash uses context engineering for smarter AI (November 2025) describes what changed as Dash grew from a retrieval pipeline into an agent that plans and acts. [9]

The problem

Dash connects to many applications, and each one came with its own retrieval tool. The team found that more tools often meant slower and less accurate decisions, because the model spent effort choosing among overlapping options. Tool definitions also consumed tokens on every call, and accuracy degraded on longer-running jobs, an effect the article calls context rot.

Where this topic fits

The changes apply to two parts of the context: the tool definitions sent on every call, and the retrieved content that enters after a search. Planning happens before retrieval and answer writing after it, and both now see a smaller, more relevant context.

How it is applied, step by step

  1. The many app-specific retrieval tools are replaced by one retrieval tool backed by the Dash universal search index, so the model has a single way to look things up.
  2. Content from the connected sources is brought into that unified index, and a knowledge graph over it links people, activity and content.
  3. Results are ranked using those connections before they reach the model, so the context receives only content the platform has already judged relevant.
  4. Building a good search query needed long instructions, so that work moves into a specialised search agent with its own prompt. The planning agent decides when to search and delegates the query writing.
  5. The same single retrieval tool is offered to other MCP-compatible applications through the Dash MCP server, with a short description.

Why this approach fits

Two failure modes are addressed at their source. Fewer tool definitions remove the choice among near-identical tools, which is context confusion. Ranking before the model sees anything keeps irrelevant passages out, which protects against distraction. Moving the query-writing instructions into a separate agent is isolation applied to instructions: the planner no longer carries guidance it rarely needs.

Limitation or tradeoff

The article gives no measurements, so the size of the improvement is not documented. A single search tool moves the difficulty into the index and the ranker. If ranking is wrong, the model has no second tool to route around it. A unified index also has to be built, kept fresh and made to respect each source's permissions, which is substantial engineering, and the search agent adds one more model call to each retrieval.

What the sources document

  • Dropbox reports that as Dash gained capabilities, more tools often meant slower, less accurate decision making, and that the overall accuracy of Dash degraded on longer-running jobs, which the article describes as context rot. [9]
  • The team consolidated retrieval into a single purpose-built tool backed by the Dash universal search index, replacing separate retrieval tools for each connected app. [9]
  • A knowledge graph built on top of the unified index connects people, activity and content across sources so that results can be ranked, and the model only sees content the platform has already determined to be relevant. [9]
  • Search was moved into its own agent: the main planning agent decides when a search is needed and delegates query construction to a specialised agent with its own prompt. [9]

Example 4 of 5

Claude Code compacting a coding session and re-injecting what must survive

AnthropicDocumented in official docs

Claude Code is Anthropic's coding agent for the terminal. Its documentation pages Explore the context window and How Claude Code works describe what is loaded into a session, what happens when the context fills up, and what is restored after compaction. [11][12]

The problem

A coding session reads files, runs commands and searches the code base, and each of those adds a tool result to the context. A long session reaches the window limit. Summarising the conversation frees space, but a summary can drop project rules and the content of files the agent is in the middle of editing.

Where this topic fits

Compaction runs inside the agent loop when the context approaches the limit, or when the user asks for it with a command. What matters is the step straight after the summary is written, when the harness rebuilds the context from the summary plus content reloaded from disk.

How it is applied, step by step

  1. At the start of a session a fixed set loads: the system prompt, CLAUDE.md instruction files, the first part of the auto memory file, environment details, skill descriptions and the names of MCP tools, whose full schemas are deferred until needed.
  2. As work proceeds, file contents, search results and command output are appended. Rules scoped to particular paths load when a matching file is read.
  3. Near the limit, Claude Code first clears older tool outputs. If that is not enough, it summarises the conversation.
  4. After the summary, the project-root CLAUDE.md and auto memory are re-injected from disk, and up to five files that were read or edited are re-read, most recently modified first.
  5. The user can steer the process by compacting with a stated focus, clearing the context between unrelated tasks, or sending heavy reading to a subagent whose file reads stay in its own window.

Why this approach fits

The design separates content by how it should be recovered. Conversation can be summarised because an approximate record is good enough. Project rules cannot, so they live in a file and are reloaded word for word. Recently touched files are re-read because the agent is most likely to need their exact text next. Clearing tool outputs before summarising applies the least lossy compression first.

Limitation or tradeoff

The documentation states the losses plainly. Detailed instructions given early in the conversation may be lost, and rules that were loaded into message history, such as path-scoped rules, are summarised away with everything else. Only up to five files are re-read, and a file over 5,000 tokens returns as a path reference without its content. If one file or tool output is so large that the context refills immediately, auto-compaction stops after a few attempts and reports an error.

  • As the context approaches the limit, Claude Code clears older tool outputs first and then summarises the conversation if needed. Requests and key code snippets are preserved, but detailed instructions from early in the conversation may be lost. [12]
  • After compaction, project-root CLAUDE.md and auto memory are re-injected from disk, and Claude Code re-reads up to five of the files read or edited in the session, most recently modified first. A file over 5,000 tokens comes back as a path reference without its content. [11]

4Common mistakes

  1. Treating a larger context window as the fix and sending everything you have.

    Why it causes problems
    Every token is paid for again on each call, and measured reliability falls as inputs get longer. The passage the model needs is also more likely to end up in the middle of the input, where it is used least.
    How to recognise it
    Input tokens per call climb steadily through a session. The same question is answered correctly in a short test and wrongly late in a long session. Nobody on the team can say which category of content holds most of the tokens.
    How to fix it
    Log a token count per category (instructions, tools, retrieved data, tool results, history, memory) on every call. Give each category a budget, and make additions justify themselves against it.

  2. Connecting every tool and MCP server up front and sending all their definitions on every call.

    Why it causes problems
    Definitions use up tokens before the task has started, and near-duplicate tools force the model to choose among options it cannot tell apart. Dropbox reports that more tools made Dash slower and less accurate.
    How to recognise it
    Tool definitions are one of the largest categories in the token breakdown. The model calls a tool that is unrelated to the task, or alternates between two tools that do almost the same thing.
    How to fix it
    Merge overlapping tools, send only the tools the current kind of task needs, or send tool names with a lookup step that loads a full definition on demand.

  3. Compacting with a generic summary and trusting it to carry rules and exact values.

    Why it causes problems
    A summary keeps the gist. It drops identifiers, exact error text and constraints stated once, so after compaction the agent breaks a rule it followed earlier or asks again for something it was already given.
    How to recognise it
    Behaviour changes immediately after a compaction event in the trace. Rules that were followed early in the session are ignored later, with no user message in between that changed them.
    How to fix it
    Keep must-follow rules in a pinned section that your code re-adds after each compaction. Tell the summariser what to preserve, keep paths, URLs and IDs so details can be reloaded, and test by forcing a compaction in the middle of a task.

  4. Changing the start of the prompt on every call, for example with a timestamp or a reshuffled tool list.

    Why it causes problems
    Prompt caching works on an unchanged prefix. A difference in the first lines means the whole request is processed and billed at the full rate every time, and latency rises with it.
    How to recognise it
    Cache-read token counts in the API usage data stay near zero although consecutive requests share almost all of their content. Comparing two consecutive requests shows a difference near the top.
    How to fix it
    Put volatile values in the newest message, serialise tool definitions and JSON with a fixed key order, and append to the context instead of editing earlier parts of it.

  5. Letting the agent save unverified conclusions to memory or to a summary.

    Why it causes problems
    A guess that is written down gets read back later as a fact, in this session and in future ones. The agent then builds plans on it, and each new step makes the false entry look better supported.
    How to recognise it
    The same wrong claim appears in several sessions. Tracing it back leads to a memory file or a summary and not to any tool result or user message.
    How to fix it
    Write to memory only what a tool result or the user has confirmed, with its source and date. Review and expire entries, and give users a way to see and correct what is stored.

  6. Delegating to a subagent with a one-line task and expecting it to know what the lead agent knows.

    Why it causes problems
    A subagent starts with an empty context. With a vague brief it repeats work another subagent is doing, misreads the goal, or returns pages of raw material that refill the lead agent's window.
    How to recognise it
    Two subagents return overlapping findings, returned summaries are as long as the material they were meant to condense, or the lead agent redoes the research itself.
    How to fix it
    Give every subagent an objective, an output format with a size limit, guidance on tools and sources, and boundaries. Keep full outputs in a store and pass back a reference with a short summary.

Exercise 1

Assemble one request under a 6,000-token budget

CodingIntermediateAbout 45 min (estimate)Hypothetical scenario

A support assistant is about to answer the customer's seventh message. The model call may use at most 6,000 input tokens, but the material available adds up to 11,200. Write a function assemble(budget) that decides what is sent. Token counts are given, so you need no tokenizer and only the Python standard library.

python
BUDGET = 6000
RETRIEVAL_CAP = 1500      # most tokens the retrieved chunks may use in total
MIN_SCORE = 0.5           # chunks scoring below this are never sent
PLACEHOLDER = 15          # tokens for "[result stored at <ref>]"
SUMMARY = 120             # tokens for one summary of all dropped turns

PINNED = [("system-prompt", 900), ("tool-definitions", 1100),
          ("customer-profile-memory", 250), ("current-question", 80)]
CHUNKS = [("refund-policy-s3", 700, 0.91), ("refund-policy-s1", 650, 0.84),
          ("shipping-faq", 800, 0.52), ("warranty-terms", 900, 0.47),
          ("press-release", 600, 0.21)]
TURNS = [300, 260, 420, 380, 310, 350]                  # turn 1 (oldest) to turn 6 (newest)
TOOL_RESULTS = [("orders/A-1001.json", 1200), ("tracking/ZX-77.json", 900),
                ("orders/A-1001-v2.json", 1100)]        # oldest to newest

Apply these rules in order:

  1. Pinned items are always sent. If they alone exceed the budget, raise an error.
  2. Retrieved chunks are considered from the highest score down. A chunk is sent only if its score is at least MIN_SCORE and it fits within RETRIEVAL_CAP.
  3. The newest tool result is sent in full. Each older one is replaced by a placeholder of PLACEHOLDER tokens that names where the result is stored.
  4. History is filled from the newest turn backwards with whatever budget remains. Stop at the first turn that does not fit. If any turn is dropped, all dropped turns are replaced by one summary of SUMMARY tokens, and room for it must be reserved before any turn is added.

Print the tokens used per section, the items in each section and the total.

Requirements

  • The function returns a list of (section, item, tokens) entries and never exceeds the budget it is given.
  • Chunks below the minimum score are excluded even when there is room for them.
  • Older tool results appear as placeholders that include the storage reference, not as nothing at all.
  • History stays contiguous. Once a turn does not fit, no older turn is sent in full.
  • The summary is included only when at least one turn was dropped, and its tokens count towards the total.
  • A budget too small for the pinned items, or with no room left for history, raises a clear error.

Expected behaviour

With the data above and a budget of 6,000 the program prints:

text

retrieved     1350  refund-policy-s3, refund-policy-s1
tool results  1130  [result stored at orders/A-1001.json], [result stored at tracking/ZX-77.json], orders/A-1001-v2.json
history       1160  summary of turns 1-3, turn 4, turn 5, turn 6
total         5970  of 6000 (everything would be 11200)

assemble(7000) sends all six turns with no summary and totals 6,830. assemble(5000) sends only the summary as history and totals 4,930. assemble(4900) and assemble(2300) raise errors.

Hint 1

Work out the retrieval section first by sorting on score, and keep a running total of tokens used by chunks so you can test each one against the cap.

Hint 2

Before adding any turn, compare the total of all turns with the remaining budget. If they do not all fit, subtract the summary size from the remaining budget straight away.

Hint 3

Iterate over the turns from newest to oldest and use break, not continue, when one does not fit. Using continue would let an older, shorter turn jump the queue.

Show solution
python
BUDGET = 6000
RETRIEVAL_CAP = 1500      # most tokens the retrieved chunks may use in total
MIN_SCORE = 0.5           # chunks scoring below this are never sent
PLACEHOLDER = 15          # tokens for "[result stored at <ref>]"
SUMMARY = 120             # tokens for one summary of all dropped turns

PINNED = [("system-prompt", 900), ("tool-definitions", 1100),
          ("customer-profile-memory", 250), ("current-question", 80)]
CHUNKS = [("refund-policy-s3", 700, 0.91), ("refund-policy-s1", 650, 0.84),
          ("shipping-faq", 800, 0.52), ("warranty-terms", 900, 0.47),
          ("press-release", 600, 0.21)]
TURNS = [300, 260, 420, 380, 310, 350]                  # turn 1 (oldest) to turn 6 (newest)
TOOL_RESULTS = [("orders/A-1001.json", 1200), ("tracking/ZX-77.json", 900),
                ("orders/A-1001-v2.json", 1100)]        # oldest to newest


def assemble(budget=BUDGET):
    plan = []                                           # (section, item, tokens)
    for name, tokens in PINNED:
        plan.append(("pinned", name, tokens))
    if sum(t for _, _, t in plan) > budget:
        raise ValueError("pinned content alone exceeds the budget")

    used_by_chunks = 0
    for name, tokens, score in sorted(CHUNKS, key=lambda c: c[2], reverse=True):
        if score >= MIN_SCORE and used_by_chunks + tokens <= RETRIEVAL_CAP:
            plan.append(("retrieved", name, tokens))
            used_by_chunks += tokens

    for index, (ref, tokens) in enumerate(TOOL_RESULTS):
        newest = index == len(TOOL_RESULTS) - 1
        plan.append(("tool results", ref if newest else f"[result stored at {ref}]",
                     tokens if newest else PLACEHOLDER))

    remaining = budget - sum(t for _, _, t in plan)
    if sum(TURNS) > remaining:
        remaining -= SUMMARY                            # reserve room for the summary first
    if remaining < 0:
        raise ValueError("no room left for history; lower the retrieval cap")
    kept = []
    for number in range(len(TURNS), 0, -1):             # newest turn first
        tokens = TURNS[number - 1]
        if tokens > remaining:
            break                                       # stop: never skip over a turn
        kept.append((number, tokens))
        remaining -= tokens
    dropped = len(TURNS) - len(kept)
    if dropped:
        plan.append(("history", f"summary of turns 1-{dropped}", SUMMARY))
    for number, tokens in reversed(kept):
        plan.append(("history", f"turn {number}", tokens))
    return plan


plan = assemble()
everything = (sum(t for _, t in PINNED) + sum(t for _, t, _ in CHUNKS)
              + sum(TURNS) + sum(t for _, t in TOOL_RESULTS))
for section in ("pinned", "retrieved", "tool results", "history"):
    rows = [(item, tokens) for s, item, tokens in plan if s == section]
    print(f"{section:<13}{sum(t for _, t in rows):>5}  " + ", ".join(item for item, _ in rows))
total = sum(t for _, _, t in plan)
print(f"total        {total:>5}  of {BUDGET} (everything would be {everything})")

Running it prints the five lines shown under expected behaviour. The reasoning, section by section:

  • Pinned (2,330). Instructions, tool definitions, memory and the current question are not optional, so they are placed first and the budget is checked against them alone.
  • Retrieved (1,350). The two refund-policy chunks score 0.91 and 0.84 and use 1,350 tokens. The shipping FAQ passes the score threshold at 0.52 but would bring the section to 2,150, over the 1,500 cap. The last two chunks fail the threshold. A fixed top-3 would have spent 800 tokens on a weakly related chunk.
  • Tool results (1,130). The newest order lookup is kept at 1,100 tokens. The two older results become 15-token placeholders that name their storage path, so the model knows they exist and where to find them. This is restorable compression.
  • History (1,160). After the first three sections 1,190 tokens remain. All six turns need 2,020, so 120 is reserved for a summary, leaving 1,070. Turns 6, 5 and 4 fit (350 + 310 + 380 = 1,040). Turn 3 needs 420 and only 30 remain, so the loop stops and turns 1 to 3 are summarised.

The total is 2,330 + 1,350 + 1,130 + 1,160 = 5,970, which is 53% of the 11,200 tokens available. Note the order of the checks. Reserving the summary after choosing the turns would overspend the budget whenever the kept turns leave less than 120 tokens.

The feature is in beta, and the page points to server-side compaction as the main strategy for most long conversations.
    When to use it
    Use it when you are ready to add tool-result clearing to an agent built on the Claude API.
