Tool Calling (Function Calling)

Tool calling, also called function calling, is an API feature in which you describe functions to a language model and the model can reply with a structured request to run one of them. Your code runs the function and sends the result back, and the model uses that result to continue.

1Overview

Why it matters

A language model only produces text. It cannot read an order status, look up today's price or send an email. Tool calling is the standard interface that connects a model to those things. It is what a support chatbot uses to check a database and what a coding assistant uses to run a shell command, and it is the mechanism underneath agents and the Model Context Protocol.

The mechanism is small, but the mistakes are specific. Applications break when a tool result is missing or attached to the wrong call id, when code expects one call and the model sends three, when arguments are executed without validation, or when sixty tool definitions fill the context before the user has typed a word. OpenAI, Anthropic and Google expose the same five-step exchange under different field names, so anyone who builds on more than one provider, or reads another team's traces, needs to recognise each shape.

Before you start

  • Structured OutputsIntermediate

What you will be able to do

  • Write a tool definition with a name, a description and a JSON Schema for its parameters, and say what the model does with each part.
  • Trace the five-step round trip and state which party produces each message.
  • Execute tool calls in code by dispatching on the name, validating the arguments and returning a result or an error matched to the call id.
  • Handle several tool calls in one response and return every result in the shape the API requires.
  • Choose between automatic, required, named and disabled tool choice, and name the limits each provider documents.
  • Translate a definition, a call and a result between the OpenAI, Anthropic and Gemini APIs.

Key terms

Tool
A function that you tell the model it may ask for. It usually lives in your application; OpenAI and Google call the kind you define yourself a function.
Tool definition
The description of one tool that is sent with a request, made of a name, a plain-language description and a JSON Schema for the arguments. Google calls it a function declaration.
JSON Schema
A standard vocabulary for describing the shape of JSON data, such as which properties an object has, what type each one is and which are required.
Tool call
A structured part of the model's response that names a tool and supplies arguments for it. It is a request, and nothing has run when you receive it.
Call id
An identifier the API attaches to each tool call. You send it back with the result so that the model knows which call the result answers.
Tool result
The output of the function, or an error message, that your code sends to the model in the next request.
Parallel tool calls
Several tool calls returned in a single model response, which your code may run at the same time.
Tool choice
A request setting that controls whether the model may, must or must not call a tool on this turn.
Strict mode
A per-tool setting that constrains generation so that the arguments always conform to the tool's schema.
Server tool
A tool that the model provider runs on its own infrastructure, such as web search. You enable it and read the result, and you do not execute it. OpenAI calls these built-in tools.

2Explanation

Introduction

In Structured Outputs you made a model return JSON that matches a schema. Tool calling uses the same skill for a different purpose. The JSON is no longer the answer. It is a request: please run this function with these arguments and tell me what came back.

Think of a new colleague who understands customers well but has no login to any company system. You give them a set of request forms, one for looking up an order and one for issuing a refund. When a customer asks where a parcel is, the colleague fills in the lookup form and hands it to you. You run the lookup and hand back the result, and the colleague writes the reply. They never touch the system. They choose a form and fill it in.

A model with tools works the same way, and the exchange always has five steps. The numbering follows OpenAI's function calling guide (opens in a new tab):

  1. Your application sends the conversation together with a list of tool definitions.
  2. The model replies with a tool call: the name of a tool and arguments for it.
  3. Your code executes the function. Google's guide stresses that the model does not run the function itself (opens in a new tab).
  4. Your application sends a second request that contains the tool result.
  5. The model writes its answer, or asks for more calls.

Two things in this picture are easy to miss. First, the model is called twice for one user question, so a tool call always costs at least one extra round trip. Second, the model keeps no memory between the two requests. The second request must carry the original question, the model's tool call and your result (or, in APIs that store history on the server, a reference to the first response). Without them the model cannot tell what the result refers to.

Anthropic's documentation calls this arrangement a contract (opens in a new tab): you specify which operations exist and what their inputs look like, and the model decides when and how to call them.

This lesson covers each side of that contract: writing definitions with JSON Schema, reading the model's request, executing it safely, returning results, handling several calls at once and steering the model with tool choice. It shows the field names of the OpenAI, Anthropic and Gemini APIs side by side. Repeating the round trip until a task is finished is the subject of The Agent Loop.

How it works

Step 1: declare the tool with JSON Schema

A tool definition has three parts. This one uses Anthropic's field names:

json
{
  "name": "get_exchange_rate",
  "description": "Return how many units of the quote currency one unit of the base currency buys. Use it whenever the user asks to convert an amount of money. It returns one rate per call and does not multiply amounts.",
  "input_schema": {
    "type": "object",
    "properties": {
      "base": {"type": "string", "enum": ["EUR", "GBP", "JPY", "USD"], "description": "ISO 4217 code to convert from"},
      "quote": {"type": "string", "enum": ["EUR", "GBP", "JPY", "USD"], "description": "ISO 4217 code to convert to"}
    },
    "required": ["base", "quote"],
    "additionalProperties": false
  }
}
  • Name. What the model writes when it wants this tool.
  • Description. The only explanation the model gets of what the tool does and when to use it. Anthropic's guidance (opens in a new tab) ranks a detailed description above every other factor in tool performance and suggests at least three or four sentences per tool.
  • Parameter schema. A JSON Schema (opens in a new tab) object. properties lists the arguments and their types, enum restricts a value to a fixed list, and required names the arguments that must be present. In JSON Schema a property is optional unless required lists it, and unknown properties are allowed unless additionalProperties is false.

OpenAI and Gemini use the same three parts in a different wrapper (see the grid below). Definitions are not free. OpenAI's guide says they are injected into the system message and billed as input tokens, and Anthropic adds a tool-use system prompt on top (286 tokens on Claude Opus 5.5 with automatic tool choice). They are sent again with every request.

Step 2: the model requests a call

The model reads the definitions as part of its prompt. It can answer in text or emit a tool call, and nothing has run at that point. For the question "How many yen is 250 euros?" the Anthropic API returns something like:

json
{
  "role": "assistant",
  "stop_reason": "tool_use",
  "content": [
    {"type": "text", "text": "I'll look up the rate."},
    {"type": "tool_use", "id": "toolu_01", "name": "get_exchange_rate", "input": {"base": "EUR", "quote": "JPY"}}
  ]
}

Three details matter in every API: the signal that a call was made (stop_reason here), the call id, and the form of the arguments. OpenAI's Responses API expresses the same request as an output item, with the arguments as a JSON-encoded string that you must parse:

json
{"type": "function_call", "id": "fc_1", "call_id": "call_1", "name": "get_exchange_rate", "arguments": "{\"base\":\"EUR\",\"quote\":\"JPY\"}"}

Gemini's Interactions API returns a step, with the arguments as an object, as Anthropic does:

json
{"type": "function_call", "id": "fc_1", "name": "get_exchange_rate", "arguments": {"base": "EUR", "quote": "JPY"}}

The Gemini column shows the Interactions API, which Google recommends for new development (opens in a new tab). The older generateContent API remains supported; it nests declarations under functionDeclarations and returns a functionCall part with name and args. Self-hosted servers such as vLLM (opens in a new tab) accept OpenAI's Chat Completions format, in which the definition sits under a function key and calls arrive in message.tool_calls.

Step 3: execute the call in your code

A tool call is model output, so treat it like input from any untrusted client. For each call a dispatcher finds the function by name, checks the arguments against the schema, checks that this user may perform this action, and runs the function inside a try block. (Provider-run tools such as web search skip steps 3 and 4: the provider executes them and you only read the result.)

Without strict mode, conformance to the schema is best effort. Anthropic's documentation gives the examples of "2" arriving where an integer was expected and of a required field being left out. OpenAI and Anthropic both accept strict: true on a tool, which constrains generation so that the arguments always match the schema. OpenAI's strict mode requires additionalProperties: false on every object and every property listed in required; an optional field is expressed by allowing null. On the Responses API, leaving strict out makes OpenAI try to convert the schema to strict mode and fall back to best-effort calling when it cannot; Chat Completions stays non-strict by default. Strict mode guarantees the shape and not the sense: a well-formed call can still name the wrong customer.

Step 4: return the result

The result goes back in the next request, tagged with the call id. A string is the common denominator, and JSON text is the usual choice:

json
{
  "role": "user",
  "content": [
    {"type": "tool_result", "tool_use_id": "toolu_01", "content": "{\"base\": \"EUR\", \"quote\": \"JPY\", \"rate\": 160.0}"}
  ]
}

When the function fails, send the failure as the result. Anthropic has an is_error flag for this. OpenAI leaves the format of the output string to you, so an error message goes in the same field. Write the message for the model: say what was wrong and what to try next. A function with nothing to return should still send a short confirmation such as "success".

Parallel tool calls

A model can put several calls in one response, for example two rate lookups for one question. OpenAI's guide advises assuming there may be zero, one or several. Three rules cover the handling:

  • Run them in whatever order suits your tools. Independent read-only calls can run concurrently. Calls with side effects or ordering requirements are safer in sequence.
  • Return exactly one result per call, matched by id. With Anthropic all results go in a single user message (opens in a new tab), before any text. If you decide not to run a call, still return a result for it, marked as an error.
  • To receive at most one call per response, set parallel_tool_calls: false (OpenAI) or disable_parallel_tool_use: true inside tool_choice (Anthropic).

Tool choice

By default the model decides whether to call a tool. The other settings in the grid require some call, require one named tool, or forbid calls. Gemini adds a validated mode, described as ensuring adherence to the function schema. Requiring a call is useful when the first step is always the same, such as classifying a ticket through a tool. OpenAI's allowed_tools restricts a turn to a subset of tools without changing the tools list, which OpenAI recommends so that you keep the savings from prompt caching.

Requiring a call has documented limits. With Anthropic, a forced call starts the response directly with the tool call, with no text or thinking before it. Manual extended thinking does not allow forcing, and Claude Opus 5.5, Sonnet 5.5, Fable 5.1 and Mythos 5.1 reject any and tool with a 400 error; the documented alternative is auto with strict tools. Google's guide adds a schema limit that applies in every mode: only a subset of the OpenAPI schema is supported, and the API may reject very large or deeply nested schemas.

What definitions cost

Every definition is input on every request. Anthropic published the sizes (opens in a new tab) for one five-server setup:

That is 58 tools and about 55,000 tokens before the user's first word. OpenAI suggests starting a turn with fewer than 20 functions, and Google suggests an active set of 10 to 20. OpenAI and Anthropic both offer tool search, which loads a definition only when the model looks for it (on OpenAI it needs gpt-5.4 or a later model). Worked example: Two parallel exchange-rate lookups, traced from the first request to the final answer

The question is I have 250 EUR. How much is that in Japanese yen and in British pounds? Answering it needs two exchange rates, so the model should ask for two calls in one response. To give everyone the same output, the script replaces the model with a function that returns two fixed replies in the shape of the Anthropic Messages API. The tool definition, the dispatch, the result message and the history are real. The rates are teaching data.

Save it as tool_round_trip.py. It needs only the Python standard library.

python
import json

RATES = {("EUR", "JPY"): 160.0, ("EUR", "GBP"): 0.85, ("EUR", "USD"): 1.10}  # teaching data, not live rates
CURRENCIES = ["EUR", "GBP", "JPY", "USD"]

TOOLS = [{
    "name": "get_exchange_rate",
    "description": (
        "Return how many units of the quote currency one unit of the base currency buys. "
        "Use it whenever the user asks to convert an amount of money. "
        "It returns one rate per call and does not multiply amounts."
    ),
    "input_schema": {
        "type": "object",
        "properties": {
            "base": {"type": "string", "enum": CURRENCIES, "description": "ISO 4217 code to convert from"},
            "quote": {"type": "string", "enum": CURRENCIES, "description": "ISO 4217 code to convert to"},
        },
        "required": ["base", "quote"],
        "additionalProperties": False,
    },
}]


def get_exchange_rate(base, quote):
    if (base, quote) not in RATES:
        pairs = ", ".join(f"{b}->{q}" for b, q in RATES)
        raise LookupError(f"no rate stored for {base}->{quote}. Available pairs: {pairs}")
    return {"base": base, "quote": quote, "rate": RATES[(base, quote)]}


FUNCTIONS = {"get_exchange_rate": get_exchange_rate}


def fake_model(messages):
    """Stands in for the API. Replies use the shape of the Anthropic Messages API."""
    if len(messages) == 1:  # first request: two calls in one response
        return {"role": "assistant", "stop_reason": "tool_use", "content": [
            {"type": "text", "text": "I'll look up both rates."},
            {"type": "tool_use", "id": "toolu_01", "name": "get_exchange_rate",
             "input": {"base": "EUR", "quote": "JPY"}},
            {"type": "tool_use", "id": "toolu_02", "name": "get_exchange_rate",
             "input": {"base": "EUR", "quote": "GBP"}},
        ]}
    rates = {block["tool_use_id"]: json.loads(block["content"])["rate"] for block in messages[-1]["content"]}
    text = f"250 EUR is {250 * rates['toolu_01']:,.0f} JPY or {250 * rates['toolu_02']:,.2f} GBP."
    return {"role": "assistant", "stop_reason": "end_turn", "content": [{"type": "text", "text": text}]}


def run_tool(call):
    """Execute one tool_use block and wrap the return value as a tool_result block."""
    output = FUNCTIONS[call["name"]](**call["input"])
    return {"type": "tool_result", "tool_use_id": call["id"], "content": json.dumps(output)}


def main():
    question = "I have 250 EUR. How much is that in Japanese yen and in British pounds?"
    messages = [{"role": "user", "content": question}]
    print("REQUEST 1  tools:", [tool["name"] for tool in TOOLS], "| messages:", len(messages))

    reply = fake_model(messages)                                   # step 2: the model requests calls
    messages = [*messages, {"role": "assistant", "content": reply["content"]}]
    calls = [block for block in reply["content"] if block["type"] == "tool_use"]
    print("RESPONSE 1 stop_reason:", reply["stop_reason"], "| tool calls:", len(calls))

    results = [run_tool(call) for call in calls]                   # step 3: your code runs them
    for call, result in zip(calls, results):
        print(" ", call["id"], json.dumps(call["input"]), "->", result["content"])
    messages = [*messages, {"role": "user", "content": results}]   # step 4: one message, every result

    print("REQUEST 2  roles:", [message["role"] for message in messages])
    final = fake_model(messages)                                   # step 5: the model answers
    print("RESPONSE 2 stop_reason:", final["stop_reason"], "|", final["content"][0]["text"])


if __name__ == "__main__":
    main()

Running python3 tool_round_trip.py prints:

text
REQUEST 1  tools: ['get_exchange_rate'] | messages: 1
RESPONSE 1 stop_reason: tool_use | tool calls: 2
  toolu_01 {"base": "EUR", "quote": "JPY"} -> {"base": "EUR", "quote": "JPY", "rate": 160.0}
  toolu_02 {"base": "EUR", "quote": "GBP"} -> {"base": "EUR", "quote": "GBP", "rate": 0.85}
REQUEST 2  roles: ['user', 'assistant', 'user']
RESPONSE 2 stop_reason: end_turn | 250 EUR is 40,000 JPY or 212.50 GBP.
StepWhat is sent or doneProduced by
1The question and one tool definitionyour code
2Two tool_use blocks, toolu_01 and toolu_02, with stop_reason set to tool_usethe model
3get_exchange_rate runs twice and returns 160.0 and 0.85your code
4One user message holding two tool_result blocks, each tagged with its call idyour code
5A text answer with stop_reason set to end_turnthe model

Check the arithmetic in the answer: 250 × 160.0 = 40,000 JPY and 250 × 0.85 = 212.50 GBP.

What to notice:

  • The history grows by two messages. Request 2 sends the question, the assistant message containing both tool calls, and the user message with both results. Leave out the middle one and the results refer to calls the model cannot see.
  • Ids do the matching. The stand-in model reads each rate by tool_use_id, not by position. A real model relies on the same ids.
  • Both results travel together. One user message answers both calls. Sending a separate user message per result is the formatting mistake Anthropic's parallel tool use guide warns about.

To call a live model, replace fake_model(messages) with client.messages.create(model=..., max_tokens=1024, tools=TOOLS, messages=messages) from the anthropic package. The SDK returns objects, so read reply.stop_reason and block.type in place of dictionary keys. The exercises harden the dispatcher and port the exchange to the OpenAI and Gemini shapes.

Edge cases and limitations

Well-formed arguments that are still wrong
Without strict mode a model can send a string where a number belongs, leave out a required field, or fill a gap with a guess. Anthropic's overview shows a weather tool being called with an invented location when the user named none, and says Claude Opus is more likely to ask for the missing value while Claude Sonnet may infer one. Validate arguments before executing and turn on strict mode where the provider offers it. Strict mode fixes only the shape. A schema-valid call can still name the wrong account, so authorisation checks stay in your code.
Forced tool choice is not available everywhere
Anthropic's define-tools page lists two restrictions. Manual extended thinking does not support the any or tool settings, and Claude Opus 5.5, Sonnet 5.5, Fable 5.1 and Mythos 5.1 return a 400 error for both. The documented replacement is auto with strict tools, or structured outputs when you need a fixed JSON shape. Where forcing is supported, the response starts directly with the tool call and has no explanatory text or thinking block. Google's guide has a separate schema limit: it supports only a subset of the OpenAPI schema and says that, in any of its modes, the API may reject very large or deeply nested schemas. Check the current page for your model before designing a flow that depends on a forced call.
A missing or misplaced result is rejected
With Anthropic, tool results must arrive in the message immediately after the assistant message that holds the calls, and inside that user message every tool_result block must come before any text. A request that breaks these rules is rejected with an error. This usually happens when code skips a call, for example because an earlier call in the batch failed or a person declined an approval. Return a result for the skipped call anyway, with is_error set to true and a short reason such as that it was not executed.
Calls in one batch that depend on each other
A model sometimes puts two calls in one response although the second needs the outcome of the first, such as writing a file and then reading it. Running that batch concurrently fails. Anthropic's guidance is that execution order is your choice: run such a batch in sequence, stop at the first failure and return error results for the rest, or let the dependent call fail with its natural error so the model reissues it. If your tools are rarely independent, disable parallel calls. OpenAI also notes that with a fine-tuned model strict mode is switched off for calls made in a multi-call turn.
Tool results can carry instructions from strangers
A result often contains text you do not control, such as a web page, an inbound email or an uploaded file. All of it reaches the model as context, so an attacker can plant sentences that try to steer the model into calling other tools. Anthropic's handle-tool-calls page tells developers to treat such content as untrusted and to keep it inside tool result blocks, never in the system prompt. Limit what each tool can do and require approval for actions with side effects. The Prompt Injection and LLM Security lesson covers the defences in detail.
Dropping the model's own items from the history
The second request must include what the model produced in the first, not only your result. Google's guide for stateless use says to pass back every model-generated step from the first turn, including thought steps, exactly as received, and OpenAI's example appends the whole response output to the input list before adding results. Filtering the history down to visible text removes the tool call, and on a reasoning model it can remove state the model needs. Append the response unchanged, or use the provider's server-side history, which in Gemini's Interactions API means passing previous_interaction_id.

When to use it, and when something simpler is enough

Use it when

  • The answer depends on data the model cannot know, such as live prices, account records, today's calendar or the contents of your database.
  • The user wants something done and not just described: a record updated, a message sent, a file written. Only code can perform a side effect.
  • A request could map to several operations, and the model has to pick one and fill in its arguments from natural language.
  • You are connecting a model to systems that already have APIs and want a typed, logged boundary between the two.

Think twice when

  • The model can answer from what it already knows or from text already in the prompt, as with summarising, translating or rewriting.
  • Your code needs the same data every time. Fetch it yourself and put it in the prompt; a tool call would spend a round trip deciding something that is already decided.
  • The response must be near-instant. Every tool call adds at least one more model request plus the run time of the function.
  • The action cannot be undone and you have no validation, permission check or approval step in front of it.

A simpler alternative. If you only need the model's output in a fixed shape, use structured outputs and skip the second request. If you always need the same lookup, call the function in your code and include its result in the prompt. Tool calling earns its extra round trip when the model has to decide whether a function is needed, which one, and with what arguments, and your code cannot make that decision in advance.

Key takeaways

  • Tool calling is a five-step exchange: you send definitions, the model returns a structured call, your code executes it, you send the result back, and the model answers.
  • The model only requests and never executes, so validation, permission checks and error handling belong in your code.
  • A tool definition is a name, a description and a JSON Schema, and the description does most of the work of telling the model when to use the tool.
  • Every tool call needs exactly one result matched by its call id, including calls that failed and calls you chose not to run.
  • A response may contain several tool calls, so handle them as a list, run independent ones concurrently and return all the results together.
  • OpenAI, Anthropic and Gemini implement the same exchange with different field names, tool choice values and limits, so read the current documentation before forcing a tool or porting code.

Example 1 of 5

Home Assistant giving LLM conversation agents smart-home controls as tools

Home AssistantDocumented in official docs

Home Assistant is an open-source home automation platform. Its developer documentation describes an LLM API through which conversation integrations for different model providers receive the same set of tools, and its OpenAI integration page describes the user-facing setting that switches it on. [11][12]

The problem

A household wants to say turn off the kitchen lights to an assistant backed by whichever model provider they chose. Home Assistant supports providers through separate integrations, and each provider's API expects tools in its own format. Device control also has to stay inside what the owner agreed to expose: the model must not reach every entity in the house or perform administrative tasks.

Where this topic fits

Tool calling is the boundary between a conversation integration and Home Assistant's own intent system. Before it, the user picks which LLM API a conversation agent may use and which entities are exposed. During a request, the integration converts Home Assistant's tool objects into the provider's tool format, sends them with the chat messages, and hands any tool call back to Home Assistant, which validates the arguments and runs the tool. After it, the result is added to the chat log and the model is called again.

How it is applied, step by step

  1. The user enables control of Home Assistant for a conversation agent and chooses which devices and entities are exposed to it.
  2. For each request the integration asks the chat log for the tools of the selected LLM API. The built-in Assist API offers Home Assistant's intents as tools.
  3. The integration formats each tool the way its provider expects, a conversion the documentation leaves to the integration, and sends the tools with the messages.
  4. When the model returns a tool call, Home Assistant converts and validates the arguments against the tool's parameter schema and calls the tool's async_call method.
  5. The tool returns a ToolResult whose data is a JSON-serialisable dict. If the tool raises a HomeAssistantError, Home Assistant catches it and returns a result marked as an error.
  6. The integration calls the model again while there are tool results it has not yet responded to. The documented example caps this at 10 iterations.

Why this approach fits

Home Assistant already had a typed description of what a household can ask for: its intents. Presenting those as tools gives every model the same narrow, validated interface in place of raw access to the system, and keeps the provider-specific part down to one formatting function per integration. Because the model can only request and Home Assistant executes, the exposed-entities setting is enforced in one place whichever model is on the other end.

Limitation or tradeoff

How well control works depends on the model's tool selection, which varies with the provider and the size of the model; a small local model may pick the wrong intent or the wrong light. Tool definitions, and whatever the API's prompt says about exposed devices, are sent on every request, so the prompt grows with the home. Tool annotations default to the least safe assumptions, which is the cautious choice but means an integration author has to fill them in before a model or client can benefit from them. The developer documentation explains the mechanism and reports no accuracy figures.

What the sources document

  • The developer documentation says that by exposing a Home Assistant API to an LLM, the LLM can fetch data or control Home Assistant, and that the built-in Assist API lets LLMs interact with Home Assistant via intents and cannot perform administrative tasks. [11]
  • A tool is an llm.Tool with a name, a recommended description that helps the LLM understand when and how to call it, and a parameters schema. The ToolInput passed to async_call carries tool_name, tool_args and an id, and tool_args are converted and validated using the parameters schema. [11]
  • async_call returns a ToolResult whose data must be a dict that can be serialised as JSON. When a tool raises HomeAssistantError, Home Assistant catches it and returns a ToolResult that names the exception and has error set. [11]
  • The documented conversation entity example formats each tool for its LLM and then loops up to 10 times, stopping when the chat log has no unresponded tool results. [11]
  • The OpenAI integration page says controlling Home Assistant is done by giving the AI access to the Assist API, and that the model can only control or provide information about entities that are exposed to it. [12]

The facts above come from the cited sources. The steps and analysis in this example are our explanation of how they fit together.

Example 2 of 5

vLLM turning the text output of open-weight models into structured tool calls

vLLMDocumented in official docs

vLLM is an open-source inference server for open-weight models with an OpenAI-compatible API. Its Tool Calling documentation describes how the server supports each tool_choice option and which parser each model family needs. [13]

The problem

A team that hosts its own model still wants to use standard tool-calling client code. An open-weight model emits plain text, and each model family writes tool calls in its own format: JSON for some, Python-like call syntax for others. Something has to put the tool definitions into the prompt in the form the model was trained on, recognise a tool call in the generated text, and return it in the structured shape client libraries expect. When the application requires a specific tool, the output must also be valid for that tool's schema.

Where this topic fits

vLLM sits where a hosted provider's API would. The client sends an ordinary chat completion request with tools and tool_choice. Inside the server a chat template renders the tools and earlier tool messages into the prompt, the model generates, and a tool-call parser chosen at start-up extracts calls from the text. For named and required tool choice the server constrains generation with its structured outputs backend. The client receives message.tool_calls and runs the functions itself.

How it is applied, step by step

  1. The operator starts the server with automatic tool choice enabled and names the parser that matches the model family, for example llama3_json for Llama 3.1, together with a chat template that can render tool messages.
  2. The client sends a chat completion request with a tools array and tool_choice set to auto, required, none or a named function.
  3. With auto, the model generates freely and the parser extracts any tool calls from the raw text into structured tool_calls entries.
  4. With a named function or required, vLLM constrains generation. The page says structured outputs make the response match the JSON Schema in the tools parameter, and for parsers that use structural tags it pins a tool's own argument schema only when that tool sets strict or the server raises its strictness level.
  5. The client reads the function name and arguments from the response, executes the function and continues the conversation, as it would against a hosted API.
  6. An operator who wants stricter behaviour for every client can raise the server's tool strictness level so that the call envelope, or the argument schemas as well, are constrained even when clients do not set strict.

Why this approach fits

Keeping the OpenAI request and response shapes means application code written for a hosted API works against a self-hosted model with only the base URL changed. Putting format knowledge into a per-model parser and chat template keeps it out of every client. Constrained decoding for required calls addresses the weakest point of small open models, which is producing arguments that parse at all. Running Open-Weight Models covers the serving side.

Limitation or tradeoff

The documentation is frank about the limits. With automatic tool choice and no strict setting, calls are extracted from raw text, so arguments can be malformed or violate the schema. A named call is guaranteed to be parsable, not to be a good call. Parallel calls depend on the model: the page lists them as unsupported for Llama 3 (Llama 4 supports them) and unreliable for Mistral 7B. For parsers that use structural tags, a tool's declared argument schema is enforced only when that tool sets strict, so a named or required call without strict gets only broad argument-syntax constraints. The first use of a named function adds several seconds while the constraint is compiled. In a typical deployment, a parser or template that does not match the model is the first thing to check when tool calls arrive as ordinary text, because the parser cannot recognise the format.

What the sources document

  • vLLM supports named function calling and the auto, required and none options for the tool_choice field in the chat completion API, with required available from vllm 0.8.3. [13]
  • Automatic tool choice needs the --enable-auto-tool-choice and --tool-call-parser flags, and the quickstart serves Llama 3.1 8B with the llama3_json parser and a tool chat template from the examples directory. [13]
  • Named function calling uses the structured outputs backend to make the response match the tool's JSON Schema. The page says this guarantees a validly parsable function call and not a high-quality one, and that the first use adds several seconds of latency while the constraint is compiled and cached. [13]
  • When structural tags apply, the call envelope is always constrained for required and named choices, but a tool's declared parameter schema is enforced only when that tool sets strict or the server uses the parameter strictness level. When they do not apply under tool_choice auto, vLLM extracts tool calls from raw text, so arguments may occasionally be malformed or violate the function's schema. [13]
  • The known issues listed include that parallel tool calls are not supported for Llama 3 models, though Llama 4 models support them, and that Mistral 7B struggles to generate parallel tool calls correctly. [13]

Example 3 of 5

Stripe's MCP server covering a large payments API with a few generic tools

StripeDocumented in official docs

Stripe hosts a Model Context Protocol server at mcp.stripe.com. Stripe's documentation lists the tools it exposes and how access is controlled, and the MCP specification defines the tools/list and tools/call messages that carry tool definitions and calls between a client and such a server. [14][15]

The problem

Stripe's documentation lists a long series of supported API methods. Exposing each one as its own tool would put a large amount of schema text into the context of every agent that connects. Every AI client, whether an IDE, a chat application or an autonomous agent, would also need the definitions in its own model provider's format. And some of the operations move money, where a mistaken call is costly.

Where this topic fits

MCP moves tool definitions out of the application and onto a server. An MCP client asks the server for its tools, receives each one with a name, a description and a JSON Schema for its input, and passes them to its model as ordinary tool definitions. When the model emits a tool call, the client forwards it to the server and returns the server's result to the model. The model-side exchange is the five steps of this lesson; MCP standardises where definitions come from and where execution happens. Model Context Protocol covers the protocol itself.

How it is applied, step by step

  1. A developer adds the server URL to an MCP client such as an IDE or a coding agent and authorises it with OAuth, or gives an autonomous client an agent API key limited to the permissions it needs.
  2. The client sends tools/list. The server answers with tool definitions, each with a name, a description and an inputSchema that is a JSON Schema object.
  3. The client includes those definitions in its model request, in the model provider's own tool format.
  4. For a task such as finding a customer, a typical sequence is for the model to call the search tool to find the relevant API method, the details tool to learn its parameters, and then the read tool to run a GET method.
  5. Each tool call from the model becomes a tools/call request with the tool name and an arguments object. The server runs it against the Stripe API and returns content, with isError set when execution failed.
  6. For certain write actions, such as refunds and outbound payments, Stripe requires a person to confirm in the browser before the action is taken, and the agent retries after approval.

Why this approach fits

Four generic tools (search, details, read, write) cover the API with a small, fixed amount of definition text, and the model fetches parameter details only for the method it is about to use. Stripe's page makes the point itself: the read and write tools make much of the API available without increasing the context window unnecessarily. Serving the definitions over MCP means one description of the tools works in every compatible client, and splitting read from write gives permissions and confirmation a clear line to attach to.

Limitation or tradeoff

Generic tools trade schema precision for size. The input schema of a tool that can run any GET method cannot describe each method's parameters, so the model depends on an extra lookup call and the server has to validate what arrives. A task therefore takes more round trips than it would with a dedicated tool. Remote tools also widen the attack surface: Stripe's page tells users to turn on tool approval in the client and to take care when combining the server with others, because of prompt injection. Human confirmation covers certain write actions, not all of them.

What the sources document

  • Stripe's MCP server provides tools that AI agents can use to interact with the Stripe API and search its knowledge base. The listed tools include stripe_api_search, stripe_api_details, stripe_api_read for any GET method and stripe_api_write for POST, PATCH, PUT and DELETE methods. [14]
  • The page states that the read and write tools make much of the API available through MCP without increasing the context window unnecessarily. [14]
  • Stripe requires human confirmation before certain stripe_api_write actions such as refunds and outbound payments, and recommends turning on the MCP client's tool-approval setting so that tool calls can be reviewed before they run. [14]
  • In the MCP specification a tool definition includes a name, a description and an inputSchema that must be a valid JSON Schema object. Clients discover tools with tools/list and invoke one with tools/call, passing a name and arguments. [15]
  • The specification separates protocol errors from tool execution errors. Execution errors are reported in the result with isError set to true, and clients should provide them to the language model so that it can correct itself. [15]

Example 4 of 5

Claude's Research feature using parallel tool calls to shorten multi-source research

AnthropicDocumented in an engineering article

Anthropic's engineering article How we built our multi-agent research system (June 2025) describes the Research feature in Claude, in which a lead agent plans a research task and subagents search for information. One of the lessons it lists concerns parallel tool calling. [16][6]

The problem

A research question such as listing the board members of many companies needs a large number of searches across many sources. The article says the team's early agents ran their searches one after another and describes the result as painfully slow. Each sequential search costs a full model request plus the search itself, so the time grows with the number of sources.

Where this topic fits

Parallel tool calling is used at two levels of the system. The lead agent starts several subagents at once, and each subagent issues several search tool calls in one response. In a typical implementation of either level, one model response carries multiple calls, the calls are executed together and all the results go back in the next request; the article does not describe those mechanics. The round trip is the one in this lesson. What changes is how many calls share a trip.

How it is applied, step by step

  1. The lead agent analyses the user's query, plans an approach and decides how many subagents the task needs.
  2. It creates three to five subagents in parallel instead of one after another, each with its own research task.
  3. Each subagent calls three or more tools in parallel, for example several web searches with different queries, in a single response.
  4. A typical harness executes those calls concurrently and returns every result in one message. The subagent then evaluates them and decides on the next round of searches.
  5. Subagents return condensed findings to the lead agent, which synthesises them and decides whether more research is needed.

Why this approach fits

The searches in one round do not depend on each other, which is the condition under which calls can safely run together. Putting them in one response removes whole model round trips and not just tool time: three searches cost one model request and the slowest search, where a sequential design costs three requests and the sum of all three searches. Research tasks contain many such independent lookups, so the saving compounds.

Limitation or tradeoff

The reported saving is specific to the task. The article itself says most coding tasks have fewer truly parallelisable steps than research, and that these architectures use far more tokens: in Anthropic's data, multi-agent systems used about 15 times the tokens of a chat. Parallel results also land in the context together, so three verbose results cost more to read than one. The figure of up to 90% is Anthropic's own measurement on complex queries and covers both kinds of parallelism together, so it cannot be attributed to parallel tool calls alone.

What the sources document

  • The article states that the team's early agents executed sequential searches, which it describes as painfully slow. [16]
  • For speed the team introduced two kinds of parallelisation: the lead agent spins up 3 to 5 subagents in parallel instead of serially, and the subagents use 3 or more tools in parallel. [16]
  • Anthropic reports that these changes cut research time by up to 90% for complex queries. [16]
  • The article reports that in Anthropic's data agents typically use about 4 times more tokens than chat interactions and multi-agent systems about 15 times more, and that most coding tasks involve fewer truly parallelisable tasks than research. [16]
  • Anthropic's API documentation states that Claude 4 and later models make parallel tool calls by default when a request benefits from multiple tools, and that the API does not prescribe the order in which an application executes them. [6]

Sidekick is Shopify's AI assistant for merchants. The Shopify Engineering article Building production-ready agentic systems (August 2025), based on a talk at ICML 2025, describes how the assistant's tool-calling architecture changed as its tool inventory grew. [18]

As the team added capabilities, the tool inventory grew from a handful to dozens. The article describes three stages: up to about 20 tools the boundaries were clear; between 20 and 50 they blurred and combinations of tools caused unexpected outcomes; beyond 50 there were several ways to do the same task and the system became hard to reason about. Guidance for all those tools had piled up in the system prompt, a state the team calls death by a thousand instructions.

Where this topic fits

The change is in step 4 of the round trip, the tool result. Guidance about how to use a tool's output used to sit in the system prompt, where it was present on every request whether or not the tool was used. Sidekick now returns the relevant instructions together with the tool's data, so the model reads them just after it has called that tool. The round trip keeps the same shape; what changes is the content of the result.

How it is applied, step by step

  1. A merchant asks a question in natural language, and the model chooses a tool and arguments, for example a customer query with a location filter.
  2. The application executes the tool against the store's data.
  3. The tool result returns the data together with instructions that apply to this tool and situation, which the team calls just-in-time instructions.
  4. The model reads the data and the instructions together and writes the response or the next tool call.
  5. Because the instructions travel with the tool result and are not part of the system prompt, they can be varied by beta flag, model version or page context without changing the shared prompt prefix.

Why this approach fits

Instructions that apply to one tool are only useful just after that tool has run. Returning them in the result keeps them out of the prompt for the many requests that never touch the tool, and places them next to the data they govern. The article lists the benefits the team saw: guidance is localised, the core system prompt stays focused on fundamental behaviour, and instructions can be adjusted without breaking prompt caches.

Limitation or tradeoff

Instructions inside a tool result have the same standing as any other result text, so the pattern depends on results being trustworthy. A tool that returns third-party content must not be able to slip its own instructions into the same channel (see Prompt Injection and LLM Security). The pattern reduces prompt sprawl but not the selection problem of 50 overlapping tools, and the team's stated advice is still to resist adding tools without clear boundaries. The article says performance improved across all metrics after the change and gives no figures for it.

  • It gives three stages of tool inventory: 0 to 20 tools with clear boundaries, 20 to 50 tools where boundaries become unclear and tool combinations cause unexpected outcomes, and 50 or more tools where there are multiple ways to accomplish the same task and the system is difficult to reason about. 4Common mistakes

  1. Executing whatever the model asks for without validating arguments or checking permissions.

    Why it causes problems
    The call is model output shaped by user text and by earlier tool results. A wrong id, an out-of-range amount or an injected instruction becomes a real database write or a real refund, carried out with your application's credentials.
    How to recognise it
    Tool handlers that pass arguments straight into SQL, shell commands or internal APIs, and no code path that is able to refuse a call.
    How to fix it
    Validate every call against its schema, check that the signed-in user may perform that action on that record, and put an approval step in front of tools whose effects cannot be undone.

  2. Reading only the first tool call in a response.

    Why it causes problems
    When the model sends two or three calls, the others get no result. The next request is rejected because of unanswered call ids, or the model answers with half the data it asked for.
    How to recognise it
    Code that indexes the first call, such as tool_calls[0], or breaks out of a loop after the first match, and errors that appear only when a user asks a question with several parts.
    How to fix it
    Loop over every call in the response and build one result per call id. If your tools cannot run together, disable parallel calls explicitly with the provider's setting.

  3. Writing a one-line description and trusting the tool name to explain the rest.

    Why it causes problems
    The description is the model's only documentation. With little to go on it picks the wrong one of two similar tools, calls a tool when it should answer directly, or guesses the format of an argument.
    How to recognise it
    Traces in which the model calls a neighbouring tool or sends dates and ids in the wrong format, next to descriptions that are shorter than a sentence.
    How to fix it
    Say what the tool does, when to use it and when not to, what each parameter means and what comes back. Use enums for fixed choices, and test the definition with the phrasing real users write.

  4. Letting a failed function raise an exception that ends the request.

    Why it causes problems
    The user sees a server error for a problem the model could have fixed on its next turn, such as a mistyped code, and the conversation is left holding a tool call that has no result.
    How to recognise it
    Stack traces in the logs where a tool result should be, and conversations that cannot be resumed after one bad call.
    How to fix it
    Catch exceptions around each tool and return the message as the result, with the error flag where the API has one. Say in the message what a valid call looks like.

  5. Sending every tool you have on every request.

    Why it causes problems
    Each definition is billed as input on every call and takes space the conversation needs. Selection also gets worse as similar tools pile up: Anthropic names wrong tool selection and incorrect parameters as the most common failures with large tool sets.
    How to recognise it
    Input token counts in the tens of thousands on a first message, and a tools list that is identical for every user, every screen and every task.
    How to fix it
    Send only the tools relevant to the current task, merge tools that are always used together, and use a provider's tool search or deferred loading when the library is large.

  6. Assuming one provider's shapes when porting code to another.

    Why it causes problems
    OpenAI sends arguments as a JSON string, while Anthropic and Gemini send an object. Result fields, ids and tool choice values all have different names. Code that works on one API fails, or quietly misreads the response, on another.
    How to recognise it
    A json.loads call applied to something that is already a dictionary, a TypeError on a string that should have been parsed, or tool choice values rejected as invalid.
    How to fix it
    Keep one internal representation of a tool, a call and a result, and write a small adapter for each provider. Test each adapter with a recorded response from that provider.

Make the dispatcher safe for bad calls and for batches of calls

CodingIntermediateAbout 45 min (estimate)Hypothetical scenario

run_tool in the worked example trusts the model completely: an unknown tool name or a bad argument crashes the program, and the conversation is left with tool calls that never get a result. Start from tool_round_trip.py and write a new file, safe_dispatch.py, that imports FUNCTIONS and TOOLS from it and handles this response, which contains five tool calls:

REPLY = {"role": "assistant", "stop_reason": "tool_use", "content": [
    {"type": "tool_use", "id": "toolu_11", "name": "get_exchange_rate", "input": {"base": "EUR", "quote": "USD"}},

Only the first call is good. The second uses a currency that is not in the enum, the third names a tool that does not exist, the fourth is valid against the schema but asks for a pair with no stored rate, and the fifth is missing a required argument and has an unexpected one.

Write run_tool_safely(call) and handle_response(reply). You need only the Python standard library.

Requirements

  • run_tool_safely never raises. It always returns a tool_result block with the tool_use_id of the call it was given.
  • An unknown tool name produces a result with is_error set to True and a message that lists the available tools. No function runs.
  • Arguments are checked against the tool's input_schema before the function runs: required properties, unexpected properties when additionalProperties is False, and enum values. A violation produces an error result that names the argument and, for an enum, the allowed values.
  • An exception raised by the function produces an error result containing the exception type and its message.
  • handle_response returns one user message whose content holds exactly one tool_result per tool_use block, in the same order.
  • A successful call returns the same content as in the worked example, with no is_error key.

Expected behaviour

Printing the role and the number of blocks, then one line per block with its id, ok or ERROR, and its content, gives:

text
user 5
toolu_11 ok    {"base": "EUR", "quote": "USD", "rate": 1.1}
toolu_12 ERROR Invalid arguments: 'quote' must be one of ['EUR', 'GBP', 'JPY', 'USD'], got 'CHF'.
toolu_13 ERROR Unknown tool 'convert_amount'. Available tools: get_exchange_rate.

Hint 1

Build a dictionary from tool name to input_schema out of TOOLS so the dispatcher can look up the schema for the tool being called.

Hint 2

Collect all validation problems for a call in a list and report them together. A model that is told about one problem at a time needs more round trips to fix the call.

Hint 3

Wrap only the function call in try and except. Validation failures are ordinary return values and do not need exception handling.

Show solution

Save this next to tool_round_trip.py as safe_dispatch.py:

python
import json

from tool_round_trip import FUNCTIONS, TOOLS

SCHEMAS = {tool["name"]: tool["input_schema"] for tool in TOOLS}

REPLY = {"role": "assistant", "stop_reason": "tool_use", "content": [
    {"type": "tool_use", "id": "toolu_11", "name": "get_exchange_rate", "input": {"base": "EUR", "quote": "USD"}},
    {"type": "tool_use", "id": "toolu_12", "name": "get_exchange_rate", "input": {"base": "EUR", "quote": "CHF"}},
    {"type": "tool_use", "id": "toolu_13", "name": "convert_amount", "input": {"amount": 250, "to": "USD"}},
    {"type": "tool_use", "id": "toolu_14", "name": "get_exchange_rate", "input": {"base": "GBP", "quote": "JPY"}},
    {"type": "tool_use", "id": "toolu_15", "name": "get_exchange_rate", "input": {"base": "EUR", "amount": 250}},
]}


def validation_errors(args, schema):
    """Check the three rules this schema uses: required, additionalProperties and enum."""
    properties = schema.get("properties", {})
    errors = [f"missing required argument '{name}'" for name in schema.get("required", []) if name not in args]
    for name, value in args.items():
        if name not in properties:
            if schema.get("additionalProperties") is False:
                errors.append(f"unexpected argument '{name}'")
            continue
        allowed = properties[name].get("enum")
        if allowed is not None and value not in allowed:
            errors.append(f"'{name}' must be one of {allowed}, got {value!r}")
    return errors


def error_result(call, message):
    return {"type": "tool_result", "tool_use_id": call["id"], "content": message, "is_error": True}


def run_tool_safely(call):
    name, args = call["name"], call["input"]
    if name not in FUNCTIONS:
        return error_result(call, f"Unknown tool '{name}'. Available tools: {', '.join(FUNCTIONS)}.")
    errors = validation_errors(args, SCHEMAS[name])
    if errors:
        return error_result(call, "Invalid arguments: " + "; ".join(errors) + ".")
    try:
        output = FUNCTIONS[name](**args)
    except Exception as error:  # the model can read this message and try again
        return error_result(call, f"{type(error).__name__} in {name}: {error}")
    return {"type": "tool_result", "tool_use_id": call["id"], "content": json.dumps(output)}


def handle_response(reply):
    calls = [block for block in reply["content"] if block["type"] == "tool_use"]
    return {"role": "user", "content": [run_tool_safely(call) for call in calls]}


if __name__ == "__main__":
    message = handle_response(REPLY)
    print(message["role"], len(message["content"]))
    for block in message["content"]:
        flag = "ERROR" if block.get("is_error") else "ok   "
        print(block["tool_use_id"], flag, block["content"])

Running python3 safe_dispatch.py prints the five lines shown under the expected behaviour.

Why it is built this way. The checks run in the order of the dispatch diagram: name, then arguments, then execution. The first two never reach the function, so a bad call cannot have a side effect. Every branch returns a block that carries the call id, which is what keeps the next request valid: the API needs a result for each of the five calls, including the four that did nothing. The messages are written for the model. Listing the allowed currencies or the available pairs gives it what it needs to send a corrected call on the next turn, where a bare "failed" would leave it guessing.

This validator covers only the three keywords the schema uses. In a real project use a JSON Schema library, or strict mode where the provider offers it, and keep the permission check that no schema can express.

tool_choice("openai", "any") is "required", tool_choice("anthropic", "any") is {"type": "any"} and tool_choice("gemini", "tool", "get_exchange_rate") is {"allowed_tools": {"mode": "any", "tools": ["get_exchange_rate"]}}. The Gemini tool's parameters have the keys properties, required and type, with no additionalProperties.

Hint 1

OpenAI's arguments field is a string, so it needs json.loads before the function can be called. Gemini's arguments field is already a dictionary.

Hint 2

The id to send back is call_id for OpenAI, not the id field of the item. For Gemini it is the id of the function_call step, sent back under the key call_id.

Hint 3

Prune the schema recursively: the properties object contains more schemas, and each of those may carry keywords you want to drop.

Hint 4

Gemini's tool choice lives inside generation_config. Your function only needs to return the value for the tool_choice key.

Show solution

python
import json

from tool_round_trip import FUNCTIONS, TOOLS

GEMINI_KEYWORDS = {"type", "properties", "required", "enum", "items", "description"}

OPENAI_OUTPUT = [
    {"type": "function_call", "id": "fc_1", "call_id": "call_1", "name": "get_exchange_rate",
     "arguments": '{"base":"EUR","quote":"JPY"}'},
    {"type": "function_call", "id": "fc_2", "call_id": "call_2", "name": "get_exchange_rate",
     "arguments": '{"base":"EUR","quote":"GBP"}'},
]
GEMINI_STEPS = [
    {"type": "function_call", "id": "fc_a", "name": "get_exchange_rate",
     "arguments": {"base": "EUR", "quote": "JPY"}},
    {"type": "function_call", "id": "fc_b", "name": "get_exchange_rate",
     "arguments": {"base": "EUR", "quote": "GBP"}},
]


def to_openai_tool(tool):
    return {"type": "function", "name": tool["name"], "description": tool["description"],
            "parameters": tool["input_schema"], "strict": True}


def prune(schema):
    """Keep only the schema keywords that appear in Gemini's function calling guide."""
    kept = {key: value for key, value in schema.items() if key in GEMINI_KEYWORDS}
    if "properties" in kept:
        kept["properties"] = {name: prune(sub) for name, sub in kept["properties"].items()}
    if "items" in kept:
        kept["items"] = prune(kept["items"])
    return kept


def to_gemini_tool(tool):
    return {"type": "function", "name": tool["name"], "description": tool["description"],
            "parameters": prune(tool["input_schema"])}


def openai_results(output):
    results = []
    for item in output:
        if item["type"] != "function_call":
            continue
        args = json.loads(item["arguments"])                 # OpenAI: arguments are a JSON string
        value = FUNCTIONS[item["name"]](**args)
        results.append({"type": "function_call_output", "call_id": item["call_id"],
                        "output": json.dumps(value)})
    return results


def gemini_results(steps):
    results = []
    for step in steps:
        if step["type"] != "function_call":
            continue
        value = FUNCTIONS[step["name"]](**step["arguments"])  # Gemini: arguments are an object
        results.append({"type": "function_result", "name": step["name"], "call_id": step["id"],
                        "result": [{"type": "text", "text": json.dumps(value)}]})
    return results


def tool_choice(provider, setting, name=None):
    table = {
        "openai": {"auto": "auto", "any": "required", "none": "none",
                   "tool": {"type": "function", "name": name}},
        "anthropic": {"auto": {"type": "auto"}, "any": {"type": "any"}, "none": {"type": "none"},
                      "tool": {"type": "tool", "name": name}},
        "gemini": {"auto": "auto", "any": "any", "none": "none",
                   "tool": {"allowed_tools": {"mode": "any", "tools": [name]}}},
    }
    return table[provider][setting]


if __name__ == "__main__":
    print(sorted(to_openai_tool(TOOLS[0])))
    print(sorted(to_gemini_tool(TOOLS[0])["parameters"]))
    for item in openai_results(OPENAI_OUTPUT):
        print(json.dumps(item))
    for step in gemini_results(GEMINI_STEPS):
        print(json.dumps(step))
    for provider in ("openai", "anthropic", "gemini"):
        print(provider, json.dumps(tool_choice(provider, "any")),
              json.dumps(tool_choice(provider, "tool", "get_exchange_rate")))

What the port shows. The function and its schema did not change; only the wrapper around them did. The strict-mode check passes because the schema's only object sets additionalProperties to false and both of its properties are listed in required. The Gemini adapter drops additionalProperties because the guide says only a subset of the OpenAPI schema is supported and its examples do not use that keyword; test against the live API before relying on any keyword outside that set. The two result functions differ in exactly the places the grid predicts: where the arguments need parsing, which id is echoed, and how the output is wrapped. In a real application remember that forcing a tool is not accepted by every model, so treat the values from tool_choice as requests the API may reject.
