LLM APIs and Streaming

An LLM API is an HTTP interface to a hosted language model: your program sends a list of role-labelled messages and receives the model's next message. Streaming is a way of receiving that message piece by piece while it is being generated, instead of all at once when it is finished.

1Overview

Why it matters

Every LLM application, from a chatbot to a retrieval pipeline to an agent, comes down to these requests. The chat window hides how they work. The server remembers nothing between calls, so your code decides what the model sees every single time, and that is where most cost and context problems start. Streaming decides whether a user stares at a spinner for ten seconds or starts reading after half a second, and it changes error handling, because a stream can fail after the server has already answered with status 200.

The failures in this area are ordinary engineering failures: a retry loop that hammers a rate limit, a client that crashes on a keep-alive line, a bot that seems to forget because the history was not resent, a long request cut off by a proxy. Anyone who builds, debugs or reviews LLM features needs to be able to read a raw request, a raw response and a raw stream, and to know which errors are worth retrying.

  • Classify an API error as retryable or not, and apply Retry-After and exponential backoff with jitter.
  • Decide when to stream a response and when one unstreamed response is the better choice.

Key terms

Message
One entry in a conversation sent to the model, made of a role (who is speaking) and content (what was said).
Role
The label on a message that says who wrote it. The common roles are system or developer, user, assistant and tool.
Stateless API
An API that keeps nothing between calls. Each request must contain everything the server needs, including the earlier turns of the conversation.
Stop reason
The field in a response that says why generation ended, such as a natural end, the output token cap, or a tool call. OpenAI's Chat Completions API calls it finish_reason.
Server-sent events (SSE)
A plain-text format for sending a sequence of events over one HTTP response. Each event is a few lines of the form field, colon, value, followed by a blank line.
Delta
One small piece of a streamed response, such as a few characters of text, that the client appends to what has already arrived.
Time to first token (TTFT)
The delay between sending a request and receiving the first piece of generated output.
OpenAI-compatible API
An API from another provider or a local server that accepts the same paths and JSON as OpenAI's API, so that OpenAI client code can call it after a change of base URL.
SDK
A software development kit: a library published for one programming language that wraps the HTTP API and adds types, retries, timeouts and streaming helpers.
Exponential backoff
A retry strategy that waits longer after each failed attempt, for example 1, 2 and then 4 seconds, usually with a small random amount added.

2Explanation

Introduction

You have probably used a chat app such as ChatGPT or Claude. You type, the answer appears a few words at a time, and the app seems to remember what you said earlier. An LLM API is what such an app calls behind the scenes, and it behaves differently from how the app feels. It is an ordinary web API: your program sends one HTTP POST request containing JSON and gets JSON back.

The request holds a list of messages. Each message has a role, which says who is speaking, and content, which is what they said. The response is the next message in the conversation, written by the model with the role assistant.

json
{
  "model": "gpt-6-astra",
  "messages": [
    {"role": "developer", "content": "You are a helpful assistant."},
    {"role": "user", "content": "Hello!"}
  ]
}

That is the request body from an example in OpenAI's Chat Completions reference (opens in a new tab). Model names change often, so copy the current one from your provider's documentation. The example reply carries the assistant message Hello! How can I assist you today?, a finish_reason of stop, and a usage block that reports 19 prompt tokens and 10 completion tokens, the units you met in Tokens and Context Windows.

Two facts about this exchange explain most of the lesson.

The API has no memory. Picture an expert who answers letters brilliantly but keeps no files. If you want your earlier letters taken into account, you must enclose copies of the whole correspondence every time you write. A chat app does exactly that. On each turn it resends the entire conversation with the newest message at the end.

The answer is produced one token at a time. By default the API waits until the model has finished and returns everything in one response. With streaming switched on, it sends each piece as soon as it exists, which is how chat apps show text appearing while you watch.

The rest of the lesson covers the request and its roles, conversation state without server memory, streamed and unstreamed responses and the server-sent events format that carries a stream, why so many providers copy OpenAI's API shape, what SDKs add, and how to handle errors and rate limits.

How it works

Anatomy of a request

A call has three parts. The endpoint is a URL, such as https://api.openai.com/v1/chat/completions or https://api.anthropic.com/v1/messages. The headers carry your API key (Authorization: Bearer <key> for OpenAI, x-api-key for Anthropic) and the content type. The body is JSON: a model name, the messages, and options such as a cap on output tokens.

Three message-based API shapes are in wide use. They carry the same information under different names.

OpenAI recommends the Responses API for new projects and keeps Chat Completions supported. Chat Completions is the shape other providers copy, so the worked example uses it.

Every response also says why generation stopped: finish_reason in Chat Completions (stop, length, tool_calls, content_filter) and stop_reason in the Messages API (end_turn, max_tokens, tool_use and others). Read it before you use the text. length or max_tokens means the output cap cut the answer short.

OpenAI's text generation guide (opens in a new tab) describes developer messages as prioritised ahead of user messages, and compares the pair to a function definition and its arguments. In Chat Completions, developer replaces system for newer models. The Messages API takes instructions in a top-level system field. A role tells the model how much weight a message carries. It does not make instructions hidden inside user-supplied text harmless (see Prompt Injection and LLM Security).

Conversation state without server memory

Anthropic's guide says it directly: the Messages API is stateless (opens in a new tab), so you always send the full conversational history. OpenAI's conversation state guide (opens in a new tab) likewise calls each text generation request independent and stateless. Three consequences follow.

  • The conversation is a list your program owns. After each reply, append the assistant message and then the next user message, and send the whole list. If you forget to append, the model appears to have amnesia.
  • History is editable data. Earlier turns do not have to come from the model, so you can trim, summarise or rewrite them. Context Engineering covers how.
  • Every turn pays for all earlier turns again. Input tokens are counted on each call, so a long chat costs more per turn and eventually reaches the context window.

Some APIs will keep the list for you. OpenAI's Responses API accepts a previous_response_id or a conversation id, and you then send only the new input. The model still reads the entire history, and OpenAI notes that all earlier input tokens in the chain are still billed. Server-side state saves bookkeeping and bandwidth. It does not save tokens, and it stores your conversation with one provider.

Streamed and unstreamed responses

By default the API generates the whole answer and returns it in one HTTP response. Set "stream": true and the body becomes a stream of server-sent events (SSE), a plain-text format from the HTML standard (opens in a new tab) with the content type text/event-stream. The format has few rules.

  • A line has the form field: value. LLM APIs use the fields data and event.
  • A blank line ends one event.
  • A line that starts with : is a comment. Servers send comments to keep a quiet connection open.
text
event: content_block_delta
data: {"type": "content_block_delta", "index": 0, "delta": {"type": "text_delta", "text": "Hello"}}

That is one event from a Claude stream. Its delta is a piece of text to append to what has already arrived. Your code, or an SDK, joins the deltas to rebuild the message. Providers frame their streams differently.

Streaming does not make the model faster. It changes when you see the output. Let t0t_0t0​ be the time to first token (TTFT), rrr the generation rate in tokens per second and NNN the number of output tokens. Both modes finish at

OpenAI's latency guide (opens in a new tab) ranks streaming as the most effective single way to make users wait less. There is a second reason to stream that has nothing to do with users: a long unstreamed request leaves the connection silent, and networks drop idle connections. The first real-world example below shows how Anthropic's SDKs deal with that.

OpenAI-compatible APIs

Chat Completions became a de facto standard. Many servers accept the same paths and JSON (/v1/chat/completions, messages, stream, choices), so existing code works after two settings change: the base URL and the API key.

python
from openai import OpenAI

client = OpenAI(base_url="http://localhost:11434/v1/", api_key="ollama")  # a local Ollama server

Ollama (opens in a new tab) and vLLM (opens in a new tab) offer this for self-hosted models. Google's Gemini API (opens in a new tab) and Anthropic's Claude API (opens in a new tab) offer it for hosted ones. Compatible means the server accepts the same shape. It does not mean identical behaviour. Ollama documents a subset of the API, Google describes its support as still in beta, and Anthropic states that most unsupported fields are silently ignored and recommends its native API for the full feature set. Read the provider's compatibility page before you depend on a parameter.

SDKs

You can call these APIs with any HTTP client. Official SDKs wrap the same requests and add what you would otherwise write yourself: reading the key from an environment variable, typed request and response objects, helpers that parse SSE and accumulate deltas, timeouts, retries and typed exceptions. Learn the defaults, because they interact with your own code. The OpenAI and Anthropic Python SDKs both retry connection errors and 408, 409, 429 and 5xx responses twice with exponential backoff, and both time a request out after 10 minutes.

Errors and rate limits

A call can fail at three points, and each needs a different response.

Before generation starts, the API returns an HTTP error status with a JSON body that names the error. Codes in the 400s other than 429 mean the request itself is wrong (400 malformed, 401 bad key, 403 no permission, 404 unknown resource, 413 too large). Sending it again unchanged will fail again.

Rate limits produce status 429. Providers cap requests per minute and tokens per minute for your whole organisation, by model and by usage tier. OpenAI counts RPM and TPM. Anthropic counts RPM, input tokens per minute and output tokens per minute, refills capacity continuously with a token bucket, and notes that a limit of 60 requests per minute may be enforced as one per second. Response headers such as x-ratelimit-remaining-tokens (OpenAI) and anthropic-ratelimit-tokens-remaining (Anthropic) show what is left, and Retry-After gives the number of seconds to wait. The correct reaction has three parts.

  1. Wait at least as long as Retry-After says, plus a small random delay.
  2. With no header, use exponential backoff with jitter: wait about 1 s, then 2 s, then 4 s, each plus a random amount, so that many clients do not retry at the same instant.
  3. Cap the number of attempts and the total time.

Server errors (500, OpenAI's 503 and Anthropic's 529 for overload) and timeouts get the same treatment. A 429 can also mean that a quota, billing or spend limit has been reached. Waiting does not fix that, so do not retry it.

After a stream has started, the status is already 200 and cannot change. A failure arrives as an error event inside the stream, or the connection simply closes. Check that the stream ended properly ([DONE], message_stop or response.completed) before you trust the text, and do not automatically replay a request whose partial output a user has already seen.

Worked example: Rebuilding a streamed chat completion by hand, then building the request for the next turn

The task is to read a streamed reply the way an SDK does, using only the Python standard library, and then to build the request for the next turn. So that everyone gets identical output without an API key, the stream is a fixture: WIRE holds a response body written by hand in the documented Chat Completions format, and the token counts in it are made up. The parser and the accumulator are real and work unchanged on a live stream.

Save this as read_stream.py (Python 3.9 or later).

python
import json

REQUEST = {
    "model": "example-model",
    "messages": [
        {"role": "system", "content": "Answer in one short sentence."},
        {"role": "user", "content": "What is the capital of France?"},
    ],
    "stream": True,
    "stream_options": {"include_usage": True},
}

# The response body for that request, exactly as it would travel over HTTP.
WIRE = b"""data: {"choices":[{"index":0,"delta":{"role":"assistant","content":""},"finish_reason":null}]}

: keep-alive

data: {"choices":[{"index":0,"delta":{"content":"The capital"},"finish_reason":null}]}

data: {"choices":[{"index":0,"delta":{"content":" of France"},"finish_reason":null}]}

data: {"choices":[{"index":0,"delta":{"content":" is Paris."},"finish_reason":null}]}

data: {"choices":[{"index":0,"delta":{},"finish_reason":"stop"}]}

data: {"choices":[],"usage":{"prompt_tokens":25,"completion_tokens":7,"total_tokens":32}}

data: [DONE]

"""


def sse_events(byte_pieces):
    """Yield (event_name, data) for each server-sent event in a stream of byte pieces."""
    buffer, event_name, data_lines = b"", "message", []
    for piece in byte_pieces:
        buffer += piece
        while b"\n" in buffer:                      # only complete lines are safe to parse
            raw_line, buffer = buffer.split(b"\n", 1)
            line = raw_line.decode("utf-8").rstrip("\r")
            if line == "":                          # a blank line ends the event
                if data_lines:
                    yield event_name, "\n".join(data_lines)
                event_name, data_lines = "message", []
            elif line.startswith(":"):              # a comment, often used as a keep-alive
                continue
            elif line.startswith("event:"):
                event_name = line[6:].strip()
            elif line.startswith("data:"):
                data_lines.append(line[5:].removeprefix(" "))


def read_chat_stream(byte_pieces):
    """Rebuild the assistant message from Chat Completions chunks."""
    parts, finish_reason, usage = [], None, None
    for _, data in sse_events(byte_pieces):
        if data == "[DONE]":                        # end-of-stream marker, not JSON
            break
        chunk = json.loads(data)
        usage = chunk.get("usage") or usage
        for choice in chunk["choices"]:
            text = choice["delta"].get("content")
            if text:
                parts.append(text)
                print(f"delta {len(parts)}: {text!r}")
            finish_reason = choice["finish_reason"] or finish_reason
    return {"role": "assistant", "content": "".join(parts)}, finish_reason, usage


if __name__ == "__main__":
    reads = [WIRE[i:i + 100] for i in range(0, len(WIRE), 100)]   # what the socket hands over
    print(f"{len(WIRE)} bytes arrived in {len(reads)} reads")
    print("read 2 ends with:", reads[1][-24:])

    message, finish_reason, usage = read_chat_stream(reads)
    print("assembled:", message)
    print("finish_reason:", finish_reason, "| usage:", usage)

    # Turn 2. The API kept nothing, so the client sends the whole conversation again.
    turn_2 = [*REQUEST["messages"], message, {"role": "user", "content": "And of Italy?"}]
    print("turn 2 sends", len(turn_2), "messages:", [m["role"] for m in turn_2])

Running python3 read_stream.py prints:

text
544 bytes arrived in 6 reads
read 2 ends with: b'nish_reason":null}]}\n\nda'
delta 1: 'The capital'
delta 2: ' of France'
delta 3: ' is Paris.'
assembled: {'role': 'assistant', 'content': 'The capital of France is Paris.'}
finish_reason: stop | usage: {'prompt_tokens': 25, 'completion_tokens': 7, 'total_tokens': 32}
turn 2 sends 4 messages: ['system', 'user', 'assistant', 'user']

What to notice:

  • Network reads are not events. The 544 bytes arrived in six reads of up to 100 bytes, and read 2 ends with da, the first half of the word data. sse_events therefore buffers bytes and parses only complete lines. Code that calls json.loads on each read passes a quick local test and then fails on a real network.
  • Not every line is JSON. The : keep-alive comment and the [DONE] marker would both crash json.loads. The comment is skipped, and [DONE] ends the loop.
  • The deltas rebuild the unstreamed message. Joining the three deltas gives The capital of France is Paris., exactly what choices[0].message.content holds in an unstreamed response. The first chunk carried only the role, and the chunk with finish_reason carried no text.
  • Usage arrives last. Because the request set stream_options.include_usage, a final chunk with an empty choices list reports the token counts. Code that reads choices[0] on every chunk breaks on it.
  • Turn 2 resends everything. The next request holds four messages: the original two, the assistant reply that was just assembled, and the new question. Nothing was stored on the server.

To read a live stream, pass the byte chunks of the HTTP response body in place of reads. Exercise 1 does this against a small local server.

Edge cases and limitations

The stream fails after the server has already said 200
Once the first bytes of a stream are sent, the HTTP status cannot change. Anthropic's API reports a later overload as an error event inside the stream, where a non-streaming call would have returned HTTP 529. OpenRouter sends a data event that carries an error object and a finish_reason of error, and notes that this can be the first and only event in the stream. Treat a 200 response as provisional until you have seen the end marker and a stop reason, and mark anything else as failed.
Lines in the stream that are not JSON
OpenRouter documents that it occasionally sends SSE comments such as a line reading OPENROUTER PROCESSING after a colon to stop connections timing out, and warns that passing such a line to a JSON parser throws. Anthropic's streams contain ping events and may gain new event types, which its documentation asks clients to handle gracefully. Skip comment lines and ignore event types you do not recognise.
A browser EventSource reconnects by itself
The HTML standard says an SSE client reconnects when the connection closes. For a news feed that is helpful, but for an LLM call it would start the same generation again. Cloudflare's Workers AI example therefore closes the EventSource explicitly when the [DONE] message arrives. If you consume a stream in a browser, close it yourself at the end marker.
The answer stopped because it hit the output cap
A finish_reason of length (Chat Completions) or a stop_reason of max_tokens (Messages API) means the model was cut off, so the text may end in the middle of a sentence or of a JSON object. The HTTP status is still 200. Check the stop reason before parsing or storing the output, and either raise the cap or ask for a shorter answer.
A 429 that waiting will not fix
Not every 429 is a rate limit. Anthropic returns 429 with the same rate_limit_error type when an organisation reaches its monthly spend cap, with no retry-after header, and states that retries keep failing until access resumes. OpenAI returns 429 for exhausted credit and spend limits, identified by error codes such as credit_balance_exhausted. OpenAI can also return a slow_down 429 when traffic rises too quickly even though it is inside its per-minute limits. Read the error code, not only the status.
A compatible endpoint accepts a field and ignores it
Anthropic's OpenAI compatibility layer documents that response_format and the strict flag on function calling are ignored, and that system and developer messages are hoisted and concatenated into one system prompt wherever they appeared. Ollama lists tool_choice and n as unsupported. The request succeeds either way, so the only symptom is output that does not have the shape you expected. Test each parameter you rely on against each provider.

When to use it, and when something simpler is enough

Use it when

  • Stream when a person is waiting and the answer is longer than a sentence or two, so that reading can start at the time to first token instead of at the end.
  • Stream when a generation may run for minutes or uses a large output cap, even if nobody is watching, and let the SDK accumulate the final message. This keeps the connection active.
  • Stream when your code can act on partial output, for example to cancel a bad answer early, to show progress, or to start the next step before the response is complete.
  • Use an OpenAI-compatible endpoint when you want to switch providers or run a local model without rewriting client code, and you rely only on the common subset of the API.

Think twice when

  • Do not show streamed text when the output must be checked as a whole first, such as JSON you will parse or content that needs moderation. Call unstreamed, or buffer the stream and release it after the check.
  • Skip streaming for short machine-to-machine calls such as classification or extraction, where nothing consumes partial output and the extra parsing code only adds failure modes.
  • Do not use synchronous calls for large, non-urgent workloads. A batch API takes them off your per-minute rate limits.
  • Avoid a compatibility layer when you need provider-specific features. Anthropic lists prompt caching and citations among the features that require its native API.

A simpler alternative. One unstreamed call through the provider's official SDK: a single function call that returns a complete object, with retries and timeouts already handled. It stops being enough when users wait more than a couple of seconds for the first visible text, or when responses become long enough that an idle connection may be dropped before the answer arrives.

Key takeaways

  • An LLM API call is an HTTP POST whose JSON body holds a model name and a list of role-labelled messages. The response is the next assistant message with a stop reason and token usage.
  • The API is stateless. Your application keeps the conversation and resends all of it on every turn, so input tokens and cost grow as the chat gets longer.
  • Streaming delivers the same answer as deltas over server-sent events. Total time is unchanged, but the user starts reading at the time to first token.
  • A stream can fail after status 200, so parse it line by line, skip comments and unknown events, and treat a missing end marker as a failure.
  • OpenAI-compatible endpoints let one client reach many providers by changing the base URL, but each one implements a subset and may silently ignore fields it does not support.
  • Retry only transient failures such as rate-limit 429s, 5xx errors and timeouts, using Retry-After or exponential backoff with jitter. Never retry bad requests or quota errors.

Example 1 of 5

Claude API and SDKs: streaming as the transport for long generations

AnthropicDocumented in official docs

Anthropic's Claude API documentation describes how the Messages API streams a response and how the official SDKs treat long requests. The streaming guide gives the event sequence, the errors page explains long requests and errors that occur after a 200 response, and the Python SDK page documents the SDK's 10-minute rule. [10][11][16][14]

The problem

A request for a long output can run for many minutes. With an unstreamed call nothing travels over the connection during that time, and the documentation warns that some networks drop idle connections, so the request can fail or time out without ever receiving a response. The client also needs a way to learn about a failure, such as an overloaded service, that happens after generation has begun and the HTTP status has already been sent.

Where this topic fits

Streaming is the transport for the whole response. The request sets stream to true, the server answers with a server-sent event stream of named events, and the SDK either passes those events to the application or accumulates them into the same Message object that an unstreamed call returns.

How it is applied, step by step

  1. The client sends a Messages request with stream set to true. In the Python and TypeScript SDKs the messages.stream() helper sets it.
  2. The API replies with a message_start event that contains a message with empty content and a null stop reason.
  3. Each content block arrives as a content_block_start event, one or more content_block_delta events and a content_block_stop event. Ping events can appear anywhere in between, and a client ignores them.
  4. One or more message_delta events report top-level changes such as the stop reason and the cumulative output token count, and a message_stop event ends the stream.
  5. If the service becomes overloaded part-way through, the stream carries an error event. The client cannot rely on the HTTP status, which was sent as 200 at the start.
  6. An application that does not need partial text asks the SDK to accumulate the events, for example with get_final_message() in Python, and receives the complete message as if it had not streamed.
  7. For a non-streaming request that it expects to run longer than about 10 minutes, the Python SDK raises a ValueError, which pushes long generations onto the streaming path.

Why this approach fits

A stream keeps data moving for the whole generation, so proxies and load balancers between client and server see an active connection instead of a silent one. Named, typed events let a single stream carry text, tool-call arguments, thinking and usage without ambiguity, and the client can tell a finished message from a broken one by whether message_stop arrived. The accumulation helper keeps the simple programming model of an unstreamed call for code that only wants the final answer.

Limitation or tradeoff

Error handling becomes the client's job. A mid-stream error does not follow the normal HTTP mechanisms, and the documentation notes that tool-use and thinking blocks cannot be partially recovered after an interruption, only text. A hand-written integration must also cope with event types it has never seen, because new ones can be added. The 10-minute check is an estimate made by the SDK, so a direct HTTP integration gets no such warning.

What the sources document

  • Setting stream to true makes the Messages API stream its response incrementally using server-sent events. Each event has a named event type and JSON data that includes the matching type. [10]
  • The documented event flow is message_start, then for each content block a content_block_start, one or more content_block_delta events and a content_block_stop, then one or more message_delta events and a final message_stop. Ping events may appear in the stream, and the token counts in message_delta usage are cumulative. [10]
  • The API may send an error event in the stream, for example an overloaded_error that would normally correspond to HTTP 529. The errors page says an error can occur after a 200 response when streaming, and that it then does not follow the standard error mechanisms. [10][11]
  • The errors page advises against a large max_tokens value without streaming or the Message Batches API because some networks drop idle connections, and says the SDKs validate that non-streaming requests are not expected to exceed a 10-minute timeout. [11]
  • The Python SDK page says the SDK throws a ValueError when a non-streaming request is expected to take longer than approximately 10 minutes. The API reference says stop_reason is null in the message_start event of a stream and non-null otherwise. [16][14]

The facts above come from the cited sources. The steps and analysis in this example are our explanation of how they fit together.

Example 2 of 5

Codex CLI keeping every request stateless by resending the conversation

OpenAIDocumented in an engineering article

OpenAI's engineering article Unrolling the Codex agent loop (January 2026) explains how Codex CLI, a coding agent that runs on the developer's machine, calls the Responses API. Its section on performance explains why the CLI sends the full conversation in every request instead of using server-side state. [9][3]

The problem

A coding session can involve a great many model calls, and each call needs everything that came before: instructions, tool definitions, earlier messages, tool calls and their outputs. The Responses API offers a previous_response_id parameter that would let the client send only what is new, but then the provider has to store the conversation. The article says that storing this data would be at odds with customers who have opted into Zero Data Retention.

Where this topic fits

Conversation state lives in the client. Codex builds the input list, sends it with instructions and tools in one HTTP POST, reads the reply as a server-sent event stream, and appends the new items to its own copy of the list before the next call.

How it is applied, step by step

  1. Codex builds the first request from three main fields: instructions, a list of tool definitions, and an input list in which each item has a role.
  2. The server replies with a server-sent event stream. Codex uses text delta events to update the screen and turns completed output items into entries for its own input list.
  3. For the next call Codex sends the whole list again with the new items at the end: the model's tool call and its output, or the assistant message and the user's next message.
  4. Because items are only ever appended, each prompt is an exact prefix of the next one, which lets the provider's prompt cache reuse the computation for the earlier part.
  5. When a setting such as the working directory changes during a conversation, Codex appends a new message describing the change. Editing an earlier message would break the shared prefix.
  6. When the conversation passes a token threshold, Codex compacts it by replacing the input with a smaller list of items that represents what has happened so far.

Why this approach fits

A stateless request can be served by any endpoint that implements the API, and the article lists several that Codex can target, including a local server. Nothing has to be stored by the provider, which is what makes Zero Data Retention possible. The cost of resending is mostly recovered by keeping the list append-only so that prompt caching applies, and the article notes that sampling the model, not network traffic, dominates the cost.

Limitation or tradeoff

The request body grows with every step, and the article agrees that the total JSON sent over a conversation is quadratic. The saving depends on cache hits, which are fragile: the article lists changing the tools, the model or the sandbox configuration mid-conversation as causes of a cache miss, and describes a bug in which tools were listed in an inconsistent order. The context window still fills up, so long sessions need compaction, which replaces detail with a summary.

What the sources document

  • Codex CLI sends HTTP requests to the Responses API, and the endpoint is configurable: the article lists a ChatGPT backend endpoint, api.openai.com/v1/responses, a local endpoint at localhost:11434/v1/responses when run with the --oss flag, and Responses API endpoints hosted by a cloud provider. [9]
  • The server replies with a Server-Sent Events stream. Events such as response.output_text.delta support streaming in the UI, and other events are transformed into objects that are appended to the input for subsequent Responses API calls. [9]
  • The article confirms that the amount of JSON sent over a conversation is quadratic, and says Codex does not use previous_response_id, primarily to keep requests fully stateless and to support Zero Data Retention configurations. [9]
  • The old prompt is intentionally an exact prefix of the new prompt so that prompt caching applies, and with cache hits sampling the model is linear rather than quadratic. [9]
  • OpenAI's conversation state guide documents previous_response_id as a way to chain responses, and states that all previous input tokens for responses in the chain are still billed as input tokens. [3]

LinkedIn streaming a multi-step assistant end to end

LinkedInDocumented in an engineering article

LinkedIn's engineering post Musings on building a Generative AI product (April 2024) describes an assistant that answers members' questions about posts and jobs. Its pipeline routes a question to an agent, retrieves information through internal APIs and Bing, and generates a response. The section on capacity and latency explains how the team used streaming. [25]

The problem

The post says that a full answer might take minutes to complete, and that capacity and perceived member latency were always top of mind. Techniques that improved answer quality, such as chain-of-thought prompting, produce tokens the member never sees, which lengthens the wait before any visible text appears.

Where this topic fits

Streaming is used at every hop of the pipeline, not only at the last one. The model call that decides which internal APIs to invoke is read as a stream and parsed while it arrives, and the final answer is streamed through LinkedIn's realtime messaging infrastructure to the member's client.

How it is applied, step by step

  1. A member's question is routed to an agent, which first has to decide which services to call.
  2. The model response that names those calls is consumed as a stream and parsed progressively. Each API call is fired as soon as its parameters are complete, without waiting for the rest of the response.
  3. The retrieved data goes to the generation step, whose output is streamed as well.
  4. The answer travels to the client over the realtime messaging infrastructure, with processing such as trust and Responsible AI classification applied incrementally on the way.
  5. The service runs as an asynchronous, non-blocking pipeline, so that threads are not tied up waiting on slow model calls.
  6. The team distinguishes time to first token from time between tokens, having found that putting a bound on only the first was not enough.

Why this approach fits

In a pipeline with several model calls, waiting for each call to finish before starting the next adds the delays together. Parsing a stream as it arrives lets retrieval overlap with generation, and streaming the final answer lets the member start reading while the rest is produced. Measuring time to first token and time between tokens separately shows which part of the wait a change will affect.

Limitation or tradeoff

Streaming made processing harder. Safety classification has to work on partial text, and structured output has to be parsed before it is complete. The post is also clear that streaming does not solve capacity: time to first token and time between tokens rose with utilisation, and when chain-of-thought prompts added hidden tokens, the slower token rate caused tasks to hit timeouts during a public ramp until the team added capacity.

What the sources document

  • The post states that a full answer might take minutes to complete, so the team makes all requests stream to reduce perceived latency, and streams end to end within the pipeline. [25]
  • The LLM response that decides which APIs to call is progressively parsed, and API calls are fired as soon as their parameters are ready, without waiting for the full LLM response. [25]
  • The final synthesised response is streamed all the way to the client using LinkedIn's realtime messaging infrastructure, with incremental processing for things like trust and Responsible AI classification. [25]
  • The team reports that TimeToFirstToken and TimeBetweenTokens often increase with utilisation, and gives the example that for a 200-token reasoning step even a 10 ms increase in time between tokens means an extra 2 s of latency. [25]
  • The team built a fully asynchronous non-blocking pipeline so that service throughput is not wasted on threads blocked on I/O during long LLM calls. [25]

The OpenAI Python SDK's built-in retries, timeouts and typed errors

OpenAIDocumented in an open-source project

The official OpenAI Python library is open source. Its README documents what the client does when a request fails: which failures it retries, how long it waits for a response, which exception each HTTP status becomes, and why a stream that has started is never replayed. OpenAI's rate limit and error code guides describe the server's side of the same contract. [8][5][6]

The problem

Calls to a hosted model fail for reasons that have nothing to do with the request: a dropped connection, a 429 because the organisation briefly exceeded its tokens-per-minute limit, a 503 while a model is overloaded. An application without a policy for these either crashes on the first 429 or retries in a tight loop, and the rate limit guide points out that unsuccessful requests still count towards the per-minute limit.

Where this topic fits

The SDK sits between application code and the HTTP API. Every call passes through its retry and timeout layer, so the application sees either a result or a typed exception raised after the SDK's own attempts have run out.

How it is applied, step by step

  1. The application calls a method such as client.chat.completions.create.
  2. The SDK sends the HTTP request with a default timeout of 10 minutes.
  3. On a connection error or a 408, 409, 429 or 5xx response, the SDK waits with a short exponential backoff and sends the request again, up to two retries by default.
  4. If the request still fails, the SDK raises an exception whose class identifies the cause, such as RateLimitError for 429 or APIConnectionError when the server could not be reached.
  5. Statuses such as 400, 401, 403 and 404 are not on the retry list. They surface at once as BadRequestError, AuthenticationError, PermissionDeniedError and NotFoundError.
  6. While a stream is being consumed the SDK does not retry, because sending the request again could repeat output the application has already received.
  7. The application catches the specific classes, logs the request id, and decides whether to queue the work, fall back or report the failure.

Why this approach fits

A retry policy written once in the SDK is applied to every call and has sensible defaults, so an application handles a brief rate limit or overload without any code of its own. Typed exceptions turn the question of whether to retry into a question of which class was raised, which is much harder to get wrong than matching on error message text.

Limitation or tradeoff

The defaults can surprise you. Two retries with a 10-minute timeout mean that one call can occupy a worker for about 30 minutes in the worst case. If the application wraps the call in its own retry loop, the two layers multiply, and the rate limit guide says to disable SDK retries or account for them. Retrying cannot help with quota and billing errors, which also arrive as 429. The guide also notes that handling of long Retry-After values varies by SDK version, so check the version you have installed.

What the sources document

  • The README says certain errors are automatically retried 2 times by default with a short exponential backoff: connection errors, 408 Request Timeout, 409 Conflict, 429 Rate Limit and internal errors of 500 or above. The max_retries option configures or disables this. [8]
  • The README says requests time out after 10 minutes by default, that a timeout raises APITimeoutError, and that requests which time out are retried twice by default. [8]
  • The README maps status codes to exception classes: 400 BadRequestError, 401 AuthenticationError, 403 PermissionDeniedError, 404 NotFoundError, 422 UnprocessableEntityError, 429 RateLimitError, 500 and above InternalServerError, and APIConnectionError when there is no response. [8]
  • The README says stream consumption is not automatically retried, because replaying a request could duplicate output already delivered to the application. [8]
  • The rate limit guide says applications that manage their own retries should disable SDK retries or account for them so that nested retry loops do not multiply requests, and that unsuccessful requests contribute to the per-minute limit. The error codes guide says retrying billing, spend or quota errors will not restore API access. [5][6]

4Common mistakes

  1. Sending only the newest user message on each turn.

    Why it causes problems
    The model receives a question with no context, so a follow-up such as "And of Italy?" gets a confused or generic answer. To the user it looks as if the model forgot the conversation, when in fact it was never shown it.
    How to recognise it
    Log the request body. The messages list has one entry on every turn, and replies never refer to earlier turns.
    How to fix it
    Keep the list in your application, append both the assistant reply and the next user message, and send all of it. When the list gets long, trim or summarise it deliberately instead of dropping it.

  2. Running a JSON parser on every network read or every line of a stream.

    Why it causes problems
    A network read can end in the middle of an event, and a stream contains lines that are not JSON, such as keep-alive comments and the [DONE] marker. The parser throws and the stream loop dies part-way through an answer.
    How to recognise it
    JSON decoding errors that appear only under load, on slow connections or with one provider, with a stack trace that points into the stream loop.
    How to fix it
    Buffer bytes until you have complete lines, skip blank and comment lines, handle the end marker before parsing, and prefer the SDK or a spec-compliant SSE parser over hand-written splitting.

  3. Treating HTTP 200 as success for a streamed call.

    Why it causes problems
    A stream that was cut off or that carried an error event still began with status 200. The truncated text is stored or shown as a complete answer, and token usage for the call is missing.
    How to recognise it
    Saved answers that end in the middle of a sentence, and stream logs with no end marker and no stop reason.
    How to fix it
    Require the end marker and a stop reason before marking a response complete, check each event for an error, and record anything else as failed or partial.

  4. Retrying every failed request immediately, including bad requests and quota errors.

    Why it causes problems
    A malformed request fails the same way every time, and a quota error needs a person to act. OpenAI's guide notes that unsuccessful requests still count towards the per-minute limit, so a tight retry loop keeps the application locked out for longer.
    How to recognise it
    Bursts of identical requests a few milliseconds apart in the logs, and a 429 rate that rises after the first 429 instead of falling.
    How to fix it
    Classify the failure by status and error code, honour Retry-After, use exponential backoff with jitter and a cap on attempts for transient errors, and raise an alert for quota and billing errors.

  5. Wrapping an SDK call in your own retry loop without checking the SDK's defaults.

    Why it causes problems
    The layers multiply. Five attempts of your own around an SDK that makes up to three attempts each can send 15 requests for one logical call, and with a 10-minute default timeout a single hung call can block a worker for a very long time.
    How to recognise it
    The provider's usage dashboard shows several times more requests than your application logs show calls.
    How to fix it
    Choose one layer. Either set max_retries to 0 and own the policy, or configure the SDK's retries and remove yours. Set an explicit timeout that matches how long your caller is willing to wait.

  6. Assuming an OpenAI-compatible endpoint supports every parameter your code sends.

    Why it causes problems
    A field such as response_format or tool_choice can be accepted and ignored, so the output changes shape with no error. Code that parses the reply then fails somewhere far from the cause.
    How to recognise it
    The same code works against one provider and produces parsing failures against another, while the API itself reports success.
    How to fix it
    Read the provider's compatibility page, write one small test per feature you rely on for each provider, and validate the structure of every response before using it.

It expects the header Authorization: Bearer test-key, takes 0.4 s to produce the first word and 0.1 s for each of 8 words, and for the model name flaky it fails in the middle of the stream.

python
import json
import time
from http.server import BaseHTTPRequestHandler, HTTPServer

WORDS = ["Streaming", " shows", " text", " while", " it", " is", " being", " written."]


class Handler(BaseHTTPRequestHandler):
    def do_POST(self):
        body = json.loads(self.rfile.read(int(self.headers["Content-Length"])))
        if self.headers.get("Authorization") != "Bearer test-key":
            return self.reply(401, {"error": {"type": "authentication_error", "message": "bad key"}})
        time.sleep(0.4)                                    # the model reads the prompt
        if not body.get("stream"):
            time.sleep(0.1 * len(WORDS))                   # the model writes the whole answer
            message = {"role": "assistant", "content": "".join(WORDS)}
            return self.reply(200, {"choices": [{"index": 0, "message": message, "finish_reason": "stop"}]})
        self.send_response(200)
        self.send_header("Content-Type", "text/event-stream")
        self.end_headers()
        self.emit(": keep-alive")
        for position, word in enumerate(WORDS):
            if body["model"] == "flaky" and position == 3:
                return self.emit('data: {"error": {"type": "overloaded_error", "message": "Overloaded"}}')
            chunk = {"choices": [{"index": 0, "delta": {"content": word}, "finish_reason": None}]}
            self.emit("data: " + json.dumps(chunk))
            time.sleep(0.1)                                # one word every 100 ms
        self.emit('data: {"choices": [{"index": 0, "delta": {}, "finish_reason": "stop"}]}')
        self.emit("data: [DONE]")

    def emit(self, text):
        self.wfile.write((text + "\n\n").encode("utf-8"))
        self.wfile.flush()

    def reply(self, status, payload):
        data = json.dumps(payload).encode("utf-8")
        self.send_response(status)
        self.send_header("Content-Type", "application/json")
        self.send_header("Content-Length", str(len(data)))
        self.end_headers()
        self.wfile.write(data)

    def log_message(self, *args):                          # keep the terminal quiet
        pass


if __name__ == "__main__":
    HTTPServer(("127.0.0.1", 8808), Handler).serve_forever()

Show solution
python
import json
import time
import urllib.error
import urllib.request

URL = "http://127.0.0.1:8808/v1/chat/completions"
QUESTION = [{"role": "user", "content": "Why stream a response?"}]


class StreamError(Exception):
    """The server reported an error, or went away, after the stream had started."""


def post(model, stream, api_key="test-key"):
    body = json.dumps({"model": model, "messages": QUESTION, "stream": stream}).encode("utf-8")
    headers = {"Content-Type": "application/json", "Authorization": f"Bearer {api_key}"}
    return urllib.request.urlopen(urllib.request.Request(URL, data=body, headers=headers), timeout=30)


def ask_unstreamed(model):
    started = time.perf_counter()
    with post(model, stream=False) as response:
        reply = json.load(response)
    return reply["choices"][0]["message"]["content"], time.perf_counter() - started


def ask_streamed(model):
    started, first_text_at, parts, finished = time.perf_counter(), None, [], False
    try:
        with post(model, stream=True) as response:
            for raw_line in response:                 # one line at a time, as it arrives
                line = raw_line.decode("utf-8").rstrip("\r\n")
                if not line.startswith("data:"):      # blank separators and ": keep-alive" comments
                    continue
                data = line[5:].strip()
                if data == "[DONE]":
                    finished = True
                    break
                chunk = json.loads(data)
                if "error" in chunk:
                    raise StreamError(f"{chunk['error']['type']} after {''.join(parts)!r}")
                text = chunk["choices"][0]["delta"].get("content")
                if text:
                    if first_text_at is None:
                        first_text_at = time.perf_counter() - started
                    parts.append(text)
                    print(text, end="", flush=True)
    finally:
        print()                                       # end the line of streamed text
    if not finished:
        raise StreamError("connection closed before [DONE]")
    return "".join(parts), first_text_at, time.perf_counter() - started


if __name__ == "__main__":
    text, total = ask_unstreamed("demo")
    print(f"unstreamed: nothing for {total:.1f} s, then {len(text)} characters at once")

    text, first, total = ask_streamed("demo")
    print(f"streamed: first text after {first:.1f} s, complete after {total:.1f} s")

    try:
        ask_streamed("flaky")
    except StreamError as error:
        print("stream failed:", error)

    try:
        post("demo", stream=True, api_key="wrong")
    except urllib.error.HTTPError as error:
        print("HTTP", error.code, json.load(error)["error"]["type"])

How it works:

  • urlopen returns as soon as the response headers arrive, and iterating over the response yields each line when the server flushes it. That is what makes the text appear word by word.
  • Time to first token is measured at the first non-empty content delta. The keep-alive comment arrives earlier but is not model output, so it does not count.
  • The flaky run shows a failure that HTTP status codes cannot express. The status was 200, three words had already been printed, and the only signal is the error object inside a data line. The client raises, and it is up to the caller to keep or discard the partial text.
  • The finished flag catches the other mid-stream failure, a connection that closes with no [DONE].
  • The wrong key fails before any stream exists, so it arrives as an ordinary HTTPError with a JSON body.

C: sleeps=[1.5, 2.5, 4.5] -> GaveUp: retries exhausted (HTTP 500 after 4 attempt(s))
D: sleeps=[] -> GaveUp: not retryable: fix the request (HTTP 400 after 1 attempt(s))
E: sleeps=[] -> GaveUp: server asked for 120 s, more than max_wait (HTTP 429 after 1 attempt(s))

The wording of the reasons may differ. The sleep lists and the attempt counts must match.

Hint 1

Decide in this order. Success, then not retryable, then out of attempts, then a wait that is too long, and only then sleep.

Hint 2

With jitter fixed at 0.5 and base 1.0, backoff waits are 1.5, 2.5 and 4.5 seconds, and a retry-after of 3 becomes 3.5.

Hint 3

Converting the header with float() inside a try block handles both a missing header and a value that is not a number.

Show solution

Replace the call_with_retries stub in the harness with the following.

python
RETRYABLE = {408, 429, 500, 502, 503, 504, 529}
NEEDS_A_PERSON = {"credit_balance_exhausted", "organization_spend_limit_exceeded",
                  "project_spend_limit_exceeded", "organization_usage_limit_exceeded"}


def retry_after_seconds(headers):
    """The server's retry-after hint in seconds, or None when it is missing or invalid."""
    try:
        seconds = float(headers.get("retry-after", ""))
    except ValueError:
        return None
    return seconds if seconds >= 0 else None


def call_with_retries(send, max_attempts=4, base=1.0, cap=30.0, max_wait=60.0,
                      sleep=time.sleep, jitter=random.random):
    for attempt in range(1, max_attempts + 1):
        status, headers, body = send()
        if 200 <= status < 300:
            return body
        code = (body.get("error") or {}).get("code")
        if status not in RETRYABLE:
            raise GaveUp("not retryable: fix the request", status, attempt)
        if code in NEEDS_A_PERSON:
            raise GaveUp(f"not retryable: {code}", status, attempt)
        if attempt == max_attempts:
            raise GaveUp("retries exhausted", status, attempt)
        hint = retry_after_seconds(headers)
        if hint is not None and hint > max_wait:
            raise GaveUp(f"server asked for {hint:.0f} s, more than max_wait", status, attempt)
        wait = hint if hint is not None else min(cap, base * 2 ** (attempt - 1))
        sleep(wait + jitter() * base)   # never sooner than the hint, never all clients at once

Why each scenario ends as it does:

  • A. The 503 has no header, so the first wait is backoff: 1.0 × 2⁰ + 0.5 = 1.5 s. The 429 carries retry-after: 3, so the second wait is 3 + 0.5 = 3.5 s, which is longer than the 2.5 s that backoff alone would have chosen. The third call succeeds.
  • B. The status is 429, but the code says the credit balance is exhausted. Waiting cannot fix that, so the function stops after one call without sleeping.
  • C. Every call fails with 500. The waits are 1.5, 2.5 and 4.5 s, and the fourth failure ends the run. Four calls and three sleeps is the most this configuration will ever spend on one request.
  • D. A 400 means the request is wrong. It is never retried.
  • E. The server asks for 120 s, more than the caller is willing to wait. Retrying sooner would break the server's instruction, so the function gives up and lets the caller defer the work.

Two details matter in real use. HTTP header names are case-insensitive, so normalise them to lower case before the lookup. And if you call through an SDK, remember that it has retries of its own: set its max_retries to 0 when you use a function like this one.

Check your answer

  • Does scenario A sleep for 1.5 s and then 3.5 s before succeeding on the third call?
  • Do scenarios B and D stop after a single call with an empty sleep list?
  • Does scenario C make exactly four calls and three sleeps?
  • Does scenario E give up without sleeping, instead of retrying sooner than the server asked?
  • Would your function ever sleep for less than a valid retry-after value?
