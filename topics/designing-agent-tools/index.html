Designing Tools for Agents

Designing tools for agents is the work of deciding which actions an agent can take and how each one is presented to the model: its name, its description, its parameters, and what it returns on success and on failure. The model reads all of these as text, so they act as prompts.

1Overview

Why it matters

An agent can only act through its tools, and it knows about each tool only what the definition says. When an agent picks the wrong tool, passes a customer's name where an id was expected, pulls 4,000 rows into its context or repeats a failing call five times, the cause is often not the model or the system prompt. It is a vague name, a one-line description, a loose parameter, a bloated result, or an error that says only that something failed.

These problems are cheap to fix and the effect can be measured. Anthropic reports spending more time on its tools than on the overall prompt when it built a coding agent. The SWE-agent research project kept the model fixed and changed only the interface, and the share of tasks solved on a 300-task benchmark rose from 11% to 18%. Anyone who writes a function for a model to call, builds an MCP server or debugs an agent trace needs to be able to read a tool the way the model does.

What you will be able to do

  • Write a tool name, description and JSON Schema that tell a model when to use the tool and how to fill in each parameter.
  • Apply schema techniques (enums, unambiguous names, required fields, absolute paths) that make wrong calls hard to produce.
  • Shape tool results with filters, limits and truncation notes so they stay small and still let the agent continue.
  • Turn failures into error results that state what was wrong, what is valid and what to try next.
  • Decide how much one tool should do, and when to merge, split, defer or replace tools.
  • Name the main design decision and the main risk for web search, code execution, database, file system, API and messaging tools.

Key terms

Tool definition
The text a model is given about a tool, made up of a name, a description and a parameter schema.
Parameter schema
A JSON Schema object that lists a tool's parameters, their types, their allowed values and which ones are required.
Agent-computer interface (ACI)
The full set of tools and feedback through which an agent acts on a system, named by analogy with the human-computer interface.
Poka-yoke
A Japanese term for mistake-proofing. For tools it means changing the parameters so that a wrong call is hard or impossible to make.
Enum
A parameter that only accepts one of a fixed list of values.
Namespacing
Giving related tools a shared prefix, such as slack_ or github_, so that their names neither collide nor blur together.
Tool result
What a tool sends back to the model after a call. It joins the context and is resent on every later model call.
Actionable error
An error result that says what was wrong, what is valid and what the model should do next.
Granularity
How much work one tool does, from a single API endpoint to a whole user task in one call.
Tool search
Keeping most tool definitions out of the prompt and loading a definition only when the model searches for it.

2Explanation

Introduction

In Tool Calling you wrote a function definition and watched a model ask for it. In The Agent Loop you saw that every iteration starts with the model reading its instructions, its tool list and everything observed so far. This lesson is about the two parts of that reading matter that you write yourself: the tool definitions going in and the tool results coming back.

Think of a paper form at a public office. A good form has labelled boxes, tick-box options where free text would invite mistakes, an example next to the date field, and a clerk who tells you which box to fix when something is wrong. A bad form has one box marked "Details" and comes back stamped "rejected". The same person fills in both, but only the first form gets a usable answer at the first attempt.

A model calling a tool is the person with the form, with one difference: it cannot ask anyone. It has only the text you gave it. Anthropic's guide Building Effective Agents (opens in a new tab) calls this surface the agent-computer interface (ACI) and suggests giving it as much design effort as teams give to interfaces for people. A tool has four parts that the model reads:

  • the name, which often decides whether the tool is considered at all;
  • the description, which says what the tool does and when to use it;
  • the parameter schema, which says what to fill in and which values are allowed;
  • the result, including the error text when a call fails.

The first three are sent with every model call. The fourth arrives after each tool call and then stays in the context. The lesson takes them in turn, then looks at granularity (how much one tool should do) and at the choices that are specific to six common tool families: web search, code execution, database queries, file system access, API requests and messaging.

How it works

Definitions are prompt text, sent on every call

A tool definition has three parts: a name, a description and a parameter schema written in JSON Schema. The provider turns them into prompt text. Anthropic's Define tools (opens in a new tab) page shows the system prompt that the Claude API builds from the tools list. OpenAI's function calling guide (opens in a new tab) says that function definitions are injected into the system message, count against the context limit and are billed as input tokens. So every word of a definition steers the model, and every definition is paid for on every model call of the loop, whether or not the tool is used.

Names and descriptions

A name should say what the tool does and to what: orders_search, not get_data. When tools come from several services, a shared prefix (github_list_prs, slack_send_message) keeps similar tools apart. APIs also restrict names. Claude accepts letters, digits, underscores and hyphens, up to 128 characters, and the MCP specification (opens in a new tab) recommends 1 to 128 characters with no spaces.

The description carries most of the weight. Anthropic's documentation ranks detailed descriptions as the most important factor in tool performance and asks for at least three or four sentences that cover:

  • what the tool does and what it returns;
  • when to use it, and when not to;
  • what each parameter means;
  • caveats, such as what the tool does not return.

OpenAI's guide offers a quick test: could an intern use the function correctly, given only what you gave the model? A description can also carry workflow advice. In LangChain's SQL agent tutorial (opens in a new tab), the description of the schema tool tells the model to confirm that the tables exist by calling the table-listing tool first, and the query tool's description says what to do when a query comes back with an error.

Descriptions need testing like any other prompt. Anthropic reports (opens in a new tab) that when its web search tool launched, Claude kept appending the year 2025 to queries, which biased the results. The fix was a better tool description.

Parameters that are hard to get wrong

TechniqueExampleMistake it prevents
Unambiguous namesuser_id, not userA display name passed where an id is needed

Formats that need no bookkeepingReplace an exact string, not a line-numbered diffMiscounted lines, escaping errors

The last two rows come from published guidance. OpenAI advises against making the model fill in arguments you already know. Appendix 2 of Building Effective Agents warns against formats with overhead, such as keeping an accurate count of thousands of lines or escaping code inside JSON, and names the general idea poka-yoke (mistake-proofing): change the arguments until mistakes are hard to make.

A schema is only advice until something enforces it, so validate arguments in your code before running anything. Claude and OpenAI both offer a strict mode (strict: true) that constrains generated arguments to the schema, using the technique described in Structured Outputs. For tools with nested or format-sensitive inputs, Claude also accepts input_examples. OpenAI notes that examples can hurt reasoning models, so measure before you keep them.

Results: return what the next decision needs

A tool result joins the context and is resent on every later call. Three habits keep results useful:

  • Return meaning, not plumbing. Names, titles and statuses help the model decide what to do. Internal ids, MIME types and audit fields mostly do not. Keep only the identifiers that a follow-up call needs.
  • Bound anything that can grow. Add filters, pagination and a default limit. When you truncate, say how much was left out and how to get it. Anthropic states that Claude Code restricts tool responses to 25,000 tokens by default.
  • Offer a detail switch when both forms are needed. In Anthropic's Slack example, a response_format parameter lets the agent choose a concise reply (72 tokens) or a detailed one that includes the ids needed for follow-up calls (206 tokens).

The SWE-agent research project measured choices like these. Its interface shows files 100 lines at a time, summarises search results with a cap of 50, and rejects edits that fail a syntax check. With the model held fixed, removing the syntax check, changing the window size or switching to page-by-page search results each lowered the share of tasks solved.

Errors the model can act on

The MCP specification separates two kinds of failure. Protocol errors (an unknown tool, a malformed request) concern the request itself, and the model is less likely to be able to fix them. Tool execution errors (bad input, a failed API call, a broken business rule) come back as an ordinary result flagged isError: true, and the specification says clients should pass these to the model so that it can correct itself. The Claude API has the same flag, is_error (opens in a new tab), on a tool result.

An actionable error states what was wrong, what is valid and what to do next. These pairs are illustrations:

UnhelpfulActionable
KeyError: 'status'Invalid status 'in transit'. Valid values: pending, shipped, delivered, cancelled.
Error 4134,120 rows match, which is too many to return. Add a date range or set limit (maximum 200).
FailedThe billing API is rate limited. Wait 60 seconds, then retry once.

Error text goes into the prompt, so keep secrets, stack traces and other users' data out of it. A failure that no retry can fix, such as a missing credential, should end the run or go to a person (see Human-in-the-Loop).

Granularity

Granularity is how much work one tool does. Both extremes fail.

  • Too fine. One tool per API endpoint makes the model chain calls and carry intermediate data in its context. Block reports that an early Linear integration built this way needed four to six calls to find the issues one person was working on.
  • Too coarse. A single run(action, payload) tool hides the schema, so the model gets no guidance, and you cannot allow reads without also allowing writes.

Working rules:

  1. Start from the tasks users ask for. Anthropic's example is a schedule_event tool that finds availability and books the meeting, in place of separate tools to list users, list events and create an event.
  2. Merge steps that are always called in sequence, as OpenAI's guide advises.
  3. Keep one risk level per tool, read-only or state-changing, so that approval can be set per tool. This is Block's rule. Anthropic's documentation suggests grouping related operations under an action parameter; the two fit together if you group within one risk level.
  4. Keep the visible set small. OpenAI suggests fewer than 20 functions at the start of a turn, and Anthropic's tool search documentation (opens in a new tab) says selection accuracy degrades beyond 30 to 50 tools. Past that point, defer definitions and let the model search for the ones it needs.
  5. For very large APIs, expose a query language or code execution. Cloudflare's Code Mode server (opens in a new tab) covers an API of more than 2,500 endpoints with two tools: one searches the API specification and one runs code against the API.

Common tool families

The same decisions recur in six families of tools, each with a different main risk.

Two questions place any new tool in this table. Can it change something outside the conversation (send, write, delete, spend)? Can its output contain text written by strangers (pages, messages, files)? A yes to the first calls for approval or narrow permissions. A yes to the second means the result is untrusted data.

Some tools in these families run on the provider's side. Claude's web search tool (opens in a new tab) and code execution tool (opens in a new tab) are configured, not implemented, and hosted connectors such as Slack's MCP server (opens in a new tab) arrive with their tools already defined. The design questions remain. You still choose limits (max_uses, allowed domains), scopes and which tools to expose, and your code still has to handle the error codes they return.

Test tools on tasks

None of this can be settled by reading a definition. Anthropic's advice is to run realistic multi-step tasks, read the transcripts for wrong tool choices and malformed calls, change one thing and run again, and to keep a held-out set of tasks so that descriptions are not tuned to the examples (see Evaluating Agents).

Worked example: One order-lookup tool, two designs, measured

A support agent needs to look up a customer's orders. Version 1 is the tool many teams write first. Version 2 applies this lesson. The script holds both, plus a small argument checker, and calls them with arguments a model could plausibly send. It uses no model and no API key, so your output will match exactly. Save it as tool_design.py (Python 3.9 or later, standard library only).

python
import json

STATUSES = ["pending", "shipped", "delivered", "cancelled"]
CUSTOMERS = ["dana@example.com", "lee@example.com", "sam@example.com"]
ORDERS = [{"order_id": f"ORD-{1000 + i}", "uuid": f"7f3c9a2e-41d0-4b6e-9c11-{i:012d}",
           "customer_email": CUSTOMERS[i % 3], "status": STATUSES[i % 4],
           "placed_on": f"2026-{1 + i % 9:02d}-{1 + (i * 7) % 28:02d}",
           "total_usd": 20 + i * 7.25, "audit": {"etag": "e" * 32, "revision": i}}
          for i in range(36)]
MAX_ROWS = 5

V1 = {"name": "get_data", "description": "Gets data.",
      "input_schema": {"type": "object", "properties": {"q": {"type": "string"}}}}
V2 = {"name": "orders_search",
      "description": "Search one customer's orders, newest first. Use it when the user asks "
                     "about the status, date or total of their orders. Returns at most 5 "
                     "orders and the count of all matches. It cannot change or cancel an "
                     "order and does not return line items.",
      "input_schema": {
          "type": "object", "additionalProperties": False, "required": ["customer_email"],
          "properties": {
              "customer_email": {"type": "string",
                                 "description": "Full email address, e.g. dana@example.com"},
              "status": {"type": "string", "enum": STATUSES,
                         "description": "Only return orders in this state."}}}}


def get_data(q=""):  # version 1: substring match over raw records
    return json.dumps([order for order in ORDERS if q in json.dumps(order)])


def orders_search(customer_email, status=None):  # version 2
    found = sorted((o for o in ORDERS if o["customer_email"] == customer_email
                    and status in (None, o["status"])),
                   key=lambda o: o["placed_on"], reverse=True)
    if not found:
        return "ERROR: No orders match. Check the email spelling, or drop the status filter."
    lines = [f"{o['order_id']} | {o['status']} | {o['placed_on']} | {o['total_usd']:.2f} USD"
             for o in found[:MAX_ROWS]]
    hint = " Filter by status to narrow the list." if len(found) > MAX_ROWS else ""
    return "\n".join([*lines, f"Showing {len(lines)} of {len(found)} orders.{hint}"])


def check(schema, args):
    """Return None if args fit the schema, otherwise a message the model can act on."""
    rules = schema["properties"]
    for key in schema.get("required", []):
        if key not in args:
            return f"ERROR: Missing required parameter '{key}': {rules[key]['description']}"
    for key, value in args.items():
        if key not in rules:
            return f"ERROR: Unknown parameter '{key}'. Valid parameters: {', '.join(rules)}."
        if value not in rules[key].get("enum", [value]):
            return f"ERROR: Invalid {key} '{value}'. Valid values: {', '.join(rules[key]['enum'])}."
    return None


def call(tool, function, args):
    return check(tool["input_schema"], args) or function(**args)


if __name__ == "__main__":
    dana = {"customer_email": "dana@example.com"}
    print("definition characters:", len(json.dumps(V1)), "(v1)", len(json.dumps(V2)), "(v2)")
    print("v1 {'q': 'in transit'} ->", call(V1, get_data, {"q": "in transit"}))
    for args in ({"email": "dana@example.com"}, {**dana, "status": "in transit"},
                 {**dana, "status": "shipped"}):
        print(f"v2 {args} ->\n{call(V2, orders_search, args)}")
    old, new = call(V1, get_data, {"q": "dana@example.com"}), call(V2, orders_search, dana)
    print("result characters:", len(old), "(v1)", len(new), "(v2)")

Running python3 tool_design.py prints:

text

v1 {'q': 'in transit'} -> []
v2 {'email': 'dana@example.com'} ->

v2 {'customer_email': 'dana@example.com', 'status': 'in transit'} ->
ERROR: Invalid status 'in transit'. Valid values: pending, shipped, delivered, cancelled.
v2 {'customer_email': 'dana@example.com', 'status': 'shipped'} ->

ORD-1021 | shipped | 2026-04-08 | 172.25 USD
ORD-1009 | shipped | 2026-01-08 | 85.25 USD

What to notice:

  • A silent empty result. Version 1 accepts in transit, matches nothing and returns []. The model cannot tell "no such status" from "no such orders", so it is likely to report that the customer has none.
  • Errors that carry the fix. Version 2 rejects the same value and lists the four valid ones. The wrong parameter name email gets the right name and an example. One more step is enough to correct each call.
  • Result size. For Dana's 12 orders, version 1 returns 3,022 characters of raw records, including a UUID and an audit block the agent never needs. Version 2 returns 289 characters: five lines and a note that it is showing 5 of 12. That is about a tenth of the size.
  • Where the characters go. Version 2's definition is 512 characters longer (638 against 126) and is sent on every model call. One version 1 result is 2,733 characters longer than a version 2 result, and it is also resent on every later call. After the first lookup, each model call is therefore 2,221 characters smaller with version 2.

Characters are counted because they are exact. Token counts depend on the tokenizer (see Tokens and Context Windows). The check function covers only required fields, unknown names and enums. In production, use a JSON Schema library or your framework's validation.

Edge cases and limitations

Examples in a definition can help one model and hurt another
Claude's API accepts input_examples for tools with nested or format-sensitive inputs, and its documentation puts the cost of a simple example at roughly 20 to 50 prompt tokens. OpenAI's guide recommends examples for recurring failures but notes that they may hurt performance for reasoning models. An example can also anchor the model, so that it copies the sample value in place of the user's. Add examples only for a failure you have observed, vary them, and compare task results with and without them.
Strict mode guarantees the shape of the arguments, not their sense
With strict tool use the arguments always match the schema, so missing fields and wrong types disappear. A well-formed call can still be wrong: a real customer id that belongs to someone else, a limit of 20 on a query that matches a million rows, a departure date in the past. The MCP specification's own example of a tool execution error is a date that fails a must-be-in-the-future rule. Keep business-rule checks inside the tool and return their failures as actionable errors.
Text inside a tool result can contain instructions
Web pages, emails, tickets and files are written by other people, and some of them contain text addressed to the agent. Anthropic's documentation on handling tool calls warns that tool results often carry content from sources outside your control and that it should be treated as untrusted. Keep such content inside the tool result, never copy it into the system prompt, and require approval before actions that send data out. The lesson Prompt Injection and LLM Security covers the defences.
A truncated result that does not say so looks complete
If a tool returns the first 50 rows of 4,000 with no note, the agent will count or summarise 50 rows as if they were everything. Offering page after page has its own cost: the SWE-agent authors found that agents given many search results to step through tended to inspect every one, and that this did worse than having no search tool at all. State the total, state what was shown, and say how to narrow the request.
Tool annotations are hints, not controls
MCP lets a server attach annotations to a tool, for example a hint that it only reads. The specification says clients must treat annotations as untrusted unless they come from a trusted server, and a tool labelled read-only can still be backed by a credential that is allowed to write. Enforce the limit where it cannot be talked around: a read-only database role, a token with narrow scopes, a sandbox. The lesson Agent Identity, Permissions and Least Privilege covers this.
A deferred tool that the search cannot find is a missing tool
With tool search the model sees a few definitions and looks up the rest. Anthropic's documentation says the search covers tool names, descriptions, argument names and argument descriptions, and returns up to five matches by default. A tool described in internal jargon, without the words a user would use, may never be loaded, and the agent will behave as if the capability does not exist. Use consistent prefixes, put the user's vocabulary in descriptions, and keep the three to five most used tools loaded up front.

When to use it, and when something simpler is enough

Use it when

  • A model will choose this tool from among several, so its name and description decide whether it is picked for the right requests.
  • The tool can return more than a screenful of text (search hits, logs, table rows, file contents), so it needs filters, a default limit and a truncation note.
  • Traces show the same malformed or repeated call to one tool, which points at its schema or its error text and not at the system prompt.
  • You are exposing an existing REST, GraphQL or SQL interface to an agent and must choose between endpoint-level, task-level and query-level tools.

Think twice when

  • The steps are fixed and your own code always calls the same function in the same order. Call it directly; nothing needs a model-facing definition.
  • A general tool in a sandbox already does the job, such as a shell over well-documented files. Vercel reports that swapping seventeen specialised tools for a shell and a SQL tool made its data agent faster and more reliable on its benchmark queries.
  • You have no transcripts yet. Polishing descriptions before the agent has run on real tasks optimises for mistakes you are guessing at.

A simpler alternative. Start with the smallest set that could work: one or two general tools, each with a plain description of three or four sentences, and code that validates arguments and returns clear errors. Run ten real tasks and read the transcripts. This stops being enough when the same mistake appears twice, whether a wrong tool choice, a malformed argument or a flooded context. Then fix the part of that one tool that caused it.

Key takeaways

  • A tool's name, description, parameter schema and results are all text that the model reads, so each one should be written and tested as carefully as a prompt.
  • A good description says what the tool does, when to use it and when not to, what each parameter means and what the tool does not return.
  • Schemas prevent mistakes when they use unambiguous names, enums, required fields and formats that need no bookkeeping, and when your code validates the arguments before running anything.
  • A result should contain only what the next decision needs, with a limit and a note saying how much was left out and how to get it.
  • A useful error says what was wrong, what is valid and what to do next, and it goes back to the model as a result instead of crashing the loop.
  • Tools should match the tasks users ask for, keep to one risk level each and stay few enough to choose between, and every change should be checked on real tasks.

Example 1 of 5

Anthropic's SWE-bench agent: absolute paths and string-replace edits

AnthropicDocumented in an engineering article

Two Anthropic engineering posts, Building Effective Agents (December 2024) and Raising the bar on SWE-bench Verified with Claude 3.5 Sonnet (January 2025), describe the coding agent the company built for the SWE-bench Verified benchmark. The second post reproduces the descriptions of its two tools. [1][3][8][9]

The problem

The agent has to navigate a real repository, run commands and edit files over hundreds of turns with nobody correcting it. The authors saw two tool-level problems. The model sometimes got relative file paths wrong after it had moved out of the repository's root directory. And there are several ways to ask a model for a file edit (a diff, a rewrite of the whole file, a replacement), which are not equally reliable.

Where this topic fits

The tool definitions are most of the design. The agent is a prompt, a Bash tool and an Edit tool, and the model decides everything else. The authors put their effort into the description and parameters of each tool, tested them on many tasks, and rewrote them where the model misunderstood.

How it is applied, step by step

  1. Keep the tool set small. One tool runs shell commands and one views, creates and edits files, so the model has few options to weigh on each turn.
  2. Write each description as a list of behaviours and limits. The Bash tool's description says, among other things, that there is no internet access, that state persists between calls and that commands producing very large output should be avoided.
  3. Run the agent on many tasks, look for ways the model misreads a tool, and edit the description to pre-empt each one.
  4. After seeing relative paths go wrong once the agent had changed directory, make the path parameter accept absolute paths only, and put an example path in its description.
  5. Choose the edit format the model handles most reliably: replace one exact string with another. When the old string is not unique in the file, perform no replacement, so the model has to add surrounding context.
  6. Clip long output and mark it as clipped, so the model knows that more exists.

Why this approach fits

An absolute path removes hidden state from the call: the same arguments mean the same file wherever the shell happens to be. String replacement asks the model for text it has just read, with no line counting and no diff headers, which follows the same guide's advice to avoid formats with bookkeeping overhead. The uniqueness rule turns a risky ambiguity into a visible error at the moment it occurs. Each change moves a mistake from something the model must avoid to something the tool prevents or reports.

Limitation or tradeoff

String replacement fails when the model's memory of the file differs from the file by a space or a tab, and each failure costs a turn. The uniqueness rule makes the model send extra surrounding lines for short or repeated snippets. The post lists the cost of the whole approach: many successful runs took hundreds of turns and more than 100,000 tokens. The descriptions were tuned by watching one model family in 2024, so the same wording should be tested again when the model changes.

What the sources document

  • The post reports that the upgraded Claude 3.5 Sonnet reached 49% on SWE-bench Verified with this agent, against 45% for the previous state of the art. [3]
  • The agent described has two tools, a Bash tool for running commands and an Edit tool for viewing and editing files and directories, and the post reproduces the description text given to the model for each. [3]
  • Building Effective Agents says that while building the SWE-bench agent the team spent more time optimising its tools than the overall prompt. Both posts describe the model making mistakes with relative file paths after the agent had moved out of the root directory, and the change to always require absolute paths. [1][3]
  • The authors say they tried several strategies for specifying edits and had the highest reliability with string replacement, where the model supplies old_str and new_str. The tool description states that the replacement is not performed when old_str is not unique in the file. [3]
  • Anthropic's API documentation describes a built-in text editor tool with view, str_replace, create and insert commands and tells implementers to return an error when the text to replace matches no location or several. It also documents a code execution tool whose sub-tools run shell commands and edit files in a sandboxed container without internet access. [8][9]

The facts above come from the cited sources. The steps and analysis in this example are our explanation of how they fit together.

Example 2 of 5

SWE-agent: a linter-guarded editor, a 100-line viewer and capped search

Princeton University and Stanford UniversityDocumented in a paper

The paper SWE-agent: Agent-Computer Interfaces Enable Automated Software Engineering (Yang and colleagues, 2024) builds a custom set of commands for a language model that fixes GitHub issues, and measures on SWE-bench how each interface choice changes the number of issues resolved. [12]

The problem

The authors start from the observation that a plain Linux shell is a poor interface for a model. It has no simple command for editing a small part of a file and gives no feedback when an edit is invalid. Its search commands can return far more text than is useful, and a model that sees a long list of results tends to step through all of them.

Where this topic fits

The interface sits between the model and the shell. In place of raw commands the model gets a few purpose-built ones for searching, viewing and editing, and each returns short, structured feedback. The paper then removes or alters one piece at a time to see which design choices carry the result.

How it is applied, step by step

  1. Provide three search commands (find a file, search within a file, search a directory) that return a summary of matches.
  2. Cap each search at 50 results. Above the cap, report no results and suggest that the agent write a more specific query.
  3. Show files through a viewer with a window of at most 100 lines, plus commands to scroll and to jump to a line.
  4. Edit by line range: the command takes a start line, an end line and the replacement text. After a successful edit the viewer shows the updated lines.
  5. Run a linter on every edit. If it reports an error, revert the edit and show the agent the error together with the code before and after, so it can try again.
  6. When a command prints nothing, return an explicit message that it ran successfully without output, so silence is never ambiguous.
  7. Test each choice by ablation on the 300-task SWE-bench Lite set: change one part of the interface, rerun, and compare the share of tasks resolved.

Why this approach fits

Each piece gives the model feedback at the point where a mistake would otherwise spread. A syntax error caught at the edit never reaches the test run, where it would look like a different problem. Bounded search and a windowed viewer keep the context for reasoning instead of filling it with text the model did not ask for. And because the authors measured each choice with the model held fixed, the gains can be attributed to the interface.

Limitation or tradeoff

Guardrails limit the damage but do not make editing reliable. By the paper's own count about half of all runs hit at least one rejected edit, and recovery became much less likely after the first failure. Line-range edits also depend on the model tracking line numbers, which is the kind of bookkeeping that string-replace editors avoid. The 100-line window and the 50-result cap were tuned for GPT-4 Turbo and Claude 3 Opus in 2024. The principle carries over to other models, but the numbers need measuring again.

  • With GPT-4 Turbo, SWE-agent resolved 12.47% of the 2,294 tasks in the full SWE-bench test set and 18.00% of the 300-task Lite split, against 11.00% on Lite for an agent that had only a shell. [12]

GitHub Copilot in VS Code: 13 core tools, with the rest behind expandable groups

The problem

The default toolset in VS Code had about 40 built-in tools, and with MCP servers installed the number could reach the hundreds. The post says that an oversized toolset makes the agent slower, and that in offline benchmarks the full built-in toolset lowered the task resolution rate.

Where this topic fits

This is the granularity decision at the level of the whole catalogue: not how one tool is written, but which definitions are in the context when a turn starts. It happens before the model sees anything, and again during the turn when the model asks to open a group.

How it is applied, step by step

  1. Use tool usage statistics and performance data to pick a core set of 13 tools covering repository structure, reading and editing files, searching for context and using the terminal.
  2. Put the remaining built-in tools into four groups (Jupyter Notebook, Web Interaction, VS Code Workspace and Testing). The model sees one entry per group, called a virtual tool, and can expand it when needed.
  3. For MCP tools, compute an embedding for each tool with an internal embedding model and cluster tools by cosine similarity, so that groups are stable and reproducible.
  4. Because opening a group costs an extra round trip and a cache miss, compare the user's query embedding with the tool embeddings and expand the most likely tools before the model's first call.
  5. Measure the result with Tool Use Coverage, the share of cases in which the right tool is already visible when the model needs it, and with latency in an online A/B test.

Why this approach fits

Definitions cost tokens and attention on every call, yet most coding tasks use the same few tools. A core set keeps the common path short, and groups keep rare tools reachable without listing them. Routing by embedding addresses the weak point of grouping, which is that the model has to guess which group to open.

Limitation or tradeoff

Every tool that is not pre-expanded costs an extra round trip, a cache miss and a chance to fail, as the post itself notes. Routing is only as good as the embeddings and the wording of tool descriptions: a coverage of 94.5% still leaves roughly one case in twenty where the right tool was not visible. The figures are GitHub's own measurements on its benchmarks and traffic, so the right core size for another product has to be measured there.

Block's Linear and Google Calendar MCP servers: from endpoint tools to query tools

BlockDocumented in an engineering article

Block's engineering post Block's Playbook for Designing MCP Servers (June 2025) draws on the more than 60 MCP servers the company says it has built, and walks through how its Linear and Google Calendar servers were redesigned. [14]

The problem

The first versions mirrored the underlying APIs, one tool per operation. For Linear, a question such as which issues a named person is working on needed four to six tool calls, depending on how many teams the person belonged to. For Google Calendar, common requests such as describing someone's day meant chaining several calls, and analytical questions were hard to answer at all.

Where this topic fits

This is the granularity decision for an existing API. It comes after the team knows which questions users really ask and before any description is written, because it fixes how many tools exist and what each one takes as input. A second decision, which tools may change data, is made at the same time.

How it is applied, step by step

  1. Version one of the Linear server exposes many small tools that are variations of GraphQL queries, such as get_issue, get_issue_labels and get_team_members.
  2. The team observes that ordinary questions need several chained calls and that the model has a long list of similar tools to choose from.
  3. Version two folds related read-only lookups into one tool with a category parameter. get_issue_info takes an issue id and an info_category such as details, comments, labels or children.
  4. The latest version exposes two tools that each accept a GraphQL document: execute_readonly_query and execute_mutation_query. A question that took four or more calls becomes one query.
  5. The calendar server takes the same route with SQL: calendar data is loaded into DuckDB tables and a single query_database tool runs SQL over them, with macros for common needs such as free slots.
  6. Throughout, each tool keeps to one risk level, read-only or not, so that a user can approve reads and writes differently.

Why this approach fits

Models write GraphQL and SQL well, so a query tool lets one call express what used to take a chain, and the join happens in the service instead of in the model's context. Splitting reads from mutations keeps the permission question simple even though each tool is now very general. The intermediate stage shows a useful middle option when a full query language is too much: one tool per resource, with an enum that selects what to fetch.

Limitation or tradeoff

A query tool moves work into the prompt. The model has to know the schema, a wrong query fails or returns far too much, and the service's error text has to be good enough to recover from. Access control can no longer rely on which tools exist, because one read tool can now reach everything the token can read; the credential's own permissions must carry it. Approval also gets coarser, since every mutation arrives through the same tool and a reviewer has to read the query to know what it does.

The problem

The first design gave the model a long list of specialised tools for schema lookup, join finding, query planning, syntax validation and result formatting, surrounded by heavy prompt engineering. Where this topic fits

The decision is about what the tools are for. The old tools each did part of the model's reasoning. The new ones only give access: one runs shell commands in a sandbox that holds the semantic-layer files, and one runs SQL. What to read and how to build the query is left to the model.

How it is applied, step by step

  1. The original agent registers seventeen tools, with names such as SearchSchema, JoinPathFinder, GenerateAnalysisPlan, SyntaxValidator, ExecuteSQL and FormatResults.
  2. The team concludes that these tools summarise information the model could read for itself and constrain reasoning it could do unaided.
  3. In the new design the semantic layer, a directory of YAML, Markdown and JSON files that define dimensions, measures and joins, is written into a sandbox.
  4. The agent gets two tools: ExecuteCommand, which runs a shell command in that sandbox, and ExecuteSQL.
  5. The model explores the files with grep, cat, find and ls, as an analyst would, then writes and runs the SQL.
  6. The team benchmarks both designs on five representative queries and compares time, success, tokens and steps.

Why this approach fits

The knowledge that the specialised tools encoded was already written down in well-structured files. A shell over those files lets a capable model fetch exactly the definitions it needs, in an order it chooses, with commands it knows well. Fewer tools also means fewer selection mistakes and fewer steps. The case is a counterweight to the habit of adding a tool for every sub-problem.

Limitation or tradeoff

The evidence is five queries, which is enough to show a direction and not enough to size the effect. The authors add their own condition: it worked because the semantic layer was already good documentation, and a messy data layer would only yield wrong queries sooner. A shell tool needs a sandbox, and a tool that runs free-form SQL needs a database role that can only read what the agent should see. The design also leans on a strong model, so it should be tested again before moving to a smaller one.

4Common mistakes

  1. Wrapping every API endpoint as its own tool.

    Why it causes problems
    The model has to chain several calls for one user request and carry ids and intermediate lists in its context. The catalogue fills with near-identical tools, which makes selection less accurate and costs tokens on every call.
    How to recognise it
    Traces in which one question takes four or more calls to the same service, or in which list and get calls alternate. Dozens of tools for a single integration.
    How to fix it
    Write down the ten most common user requests and design tools that answer each in one or two calls. Merge calls that always occur in sequence, and consider a query tool when the questions are too varied to list.

  2. Writing a one-line description, or pasting in the API's developer docstring.

    Why it causes problems
    The model cannot tell when the tool applies, what the parameters expect or what will come back, so it guesses. Developer docstrings assume knowledge of the system that the model does not have.
    How to recognise it
    The tool is called for requests it cannot serve, or ignored when it should be used. Descriptions shorter than two sentences, and parameters with no description at all.
    How to fix it
    Write at least three or four sentences: what the tool does, when to use it and when not to, what each parameter means and what it does not return. Then check that a newcomer could use it from the text alone.

  3. Returning the raw API payload or the whole table.

    Why it causes problems
    Thousands of tokens of ids, URLs and metadata enter the context and are resent on every later call. The fields that matter are buried, and long runs reach the context limit early.
    How to recognise it
    A jump in input tokens after one tool call that never comes back down. Results that contain UUIDs, etags or nested objects nobody asked for.
    How to fix it
    Return selected fields as short text, add filters and a default limit, and end with a line that says how many items matched and how to get the rest.

  4. Accepting an invalid argument and returning an empty result.

    Why it causes problems
    The model reads an empty list as a fact about the data and tells the user there is nothing, when the real problem was a misspelt status or a date in the wrong format.
    How to recognise it
    Confident answers of "none found" that turn out to be wrong. Tool code that passes arguments straight into a query without checking them against the schema.
    How to fix it
    Validate every argument before running anything. Reject unknown values with a message that lists the valid ones, and keep empty results for valid queries that match nothing.

  5. Putting reads and writes behind one tool or one action parameter.

    Why it causes problems
    Approval and permissions are set per tool, so the user must either approve every harmless lookup or approve deletions in advance. A reviewer cannot see the risk of a call from its name.
    How to recognise it
    A tool whose action enum mixes list or get with delete or send. An approval prompt that appears on read-only calls and is clicked through without reading.
    How to fix it
    Give each tool one risk level. Bundle related read-only actions, keep state-changing actions in separate tools, and require approval only for those.

  6. Editing a tool description and shipping it without rerunning any tasks.

    Why it causes problems
    A sentence that fixes one failure can change when the tool is chosen for other requests. Without a task set, the regression is found by users.
    How to recognise it
    Tool definitions that change in commits with no evaluation result attached, and no saved transcripts to compare before and after.
    How to fix it
    Keep a set of realistic multi-step tasks with checkable answers, record calls, errors and tokens for each task, and hold some tasks back so that descriptions are not tuned to the examples.

Exercise 1

Harden a file-reading tool

CodingIntermediateAbout 45 min (estimate)Hypothetical scenario

An agent has this tool for reading files in a project workspace:

python
def read_file(path):
    return open(path).read()

It fails in four ways covered in this lesson. A relative path is resolved against whatever directory the process happens to be in. Nothing stops ../ from leaving the workspace. A large file floods the context. And every failure is a Python exception with no advice in it.

Rewrite it as read_file(root, path, start_line=1, max_lines=50), where root is supplied by your application and not by the model. Then write the tool definition (name, description and input schema) that you would give the model.

Use this helper to create a workspace to test against. It makes docs/notes.txt with 120 lines (note 1 to note 120) and docs/tasks.txt with one line. You need only the Python standard library.

python
import os
import tempfile


def make_workspace():
    root = os.path.realpath(tempfile.mkdtemp(prefix="workspace-"))
    os.makedirs(os.path.join(root, "docs"))
    with open(os.path.join(root, "docs", "notes.txt"), "w") as handle:
        handle.write("".join(f"note {n}\n" for n in range(1, 121)))
    with open(os.path.join(root, "docs", "tasks.txt"), "w") as handle:
        handle.write("ship the tool\n")
    return root

Requirements

  • The function never raises for bad input. It returns a dictionary with is_error (true or false) and content (the text the model will read).
  • A relative path is rejected with a message that tells the model to pass an absolute path and shows the workspace root.
  • A path that resolves outside the workspace root is rejected, including paths that use .. to escape.
  • A missing file returns an error that lists up to five file names from the same folder, so that a near-miss name can be corrected in one step.
  • A successful read returns numbered lines for the requested window, then a final line stating which lines were shown, the total, and the start_line to use next.
  • max_lines is limited to 200, and a start_line beyond the end of the file returns an error that states how many lines the file has.
  • The tool definition has a description of at least three sentences that says what the tool cannot do, and it does not expose root as a parameter.

Show solution

python
MAX_LINES_CAP = 200


def error(message):
    return {"is_error": True, "content": f"ERROR: {message}"}


def read_file(root, path, start_line=1, max_lines=50):
    if not os.path.isabs(path):
        return error(f"'{path}' is a relative path. Pass an absolute path that starts with {root}/")
    real = os.path.realpath(path)
    if os.path.commonpath([root, real]) != root:
        return error(f"'{path}' is outside the workspace. Only files under {root}/ can be read.")
    if not os.path.isfile(real):
        folder = os.path.dirname(real)
        names = sorted(os.listdir(folder))[:5] if os.path.isdir(folder) else []
        listing = f" Files in that folder: {', '.join(names)}." if names else ""
        return error(f"No file at '{path}'.{listing}")
    if not isinstance(max_lines, int) or not 1 <= max_lines <= MAX_LINES_CAP:
        return error(f"max_lines must be a whole number from 1 to {MAX_LINES_CAP}.")
    with open(real, encoding="utf-8", errors="replace") as handle:
        lines = handle.read().splitlines()
    total = len(lines)
    if not isinstance(start_line, int) or not 1 <= start_line <= max(total, 1):
        return error(f"start_line must be from 1 to {total}; the file has {total} lines.")
    end = min(start_line + max_lines - 1, total)
    body = "\n".join(f"{n}: {lines[n - 1]}" for n in range(start_line, end + 1))
    more = f" Call again with start_line={end + 1} to continue." if end < total else " End of file."
    return {"is_error": False, "content": f"{body}\n[Lines {start_line}-{end} of {total}.{more}]"}


if __name__ == "__main__":
    root = make_workspace()
    notes = os.path.join(root, "docs", "notes.txt")
    calls = [
        ("relative", {"path": "docs/notes.txt"}),
        ("outside", {"path": os.path.join(root, "..", "etc", "passwd")}),
        ("missing", {"path": os.path.join(root, "docs", "note.txt")}),
        ("too far", {"path": notes, "start_line": 500}),
        ("window", {"path": notes, "start_line": 118, "max_lines": 2}),
        ("tail", {"path": notes, "start_line": 119}),
    ]
    for label, args in calls:
        result = read_file(root, **args)
        print(f"{label}: is_error={result['is_error']}")
        print(result["content"].replace(root, "<ROOT>"))

Two customers are named 'Dana Reyes': dana.reyes@example.com (3 tickets) and d.reyes@example.org
(1 ticket). Ask the user which one they mean, then call again with customer_email.

No agent is named 'Pria'. Closest names: Priya Nair, Priyanka Shah. Nothing was changed. Call again
with one of these names.

Why this design. The three read tools can run without approval and the one write tool can require it. If your policy needs approval for customer messages but not for reassignment, move customer_message into a tool of its own so the two can be approved separately. No tool takes a customer id or an agent id, so the model never carries opaque identifiers between calls. Request C shows a limit of description writing: no wording fixes a tool set that cannot answer the question, and the remedy was a new capability.

Check your answer

  • Did you get 10 calls for request A and 3 for request B with the original tools?
  • Did you find that request C needs every customer's ticket list, and so more than 2,000 calls?
  • Does each of your tools either only read or only change data, never both?
  • Can each of the three requests be answered in at most two calls with your tools?
  • Do both error messages list the candidates and state that nothing was changed or what to ask the user?
