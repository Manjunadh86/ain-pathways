OpenAI Agents SDK

The OpenAI Agents SDK is an open-source Python library, with a JavaScript/TypeScript counterpart, for building agents. You describe each agent as a model plus instructions, tools and handoffs, and a Runner executes the tool-calling loop for you, with guardrails, session memory and tracing built in.

1Overview

Why it matters

A hand-written agent loop is short, but a product needs more around it: routing between specialised prompts, checks on what users send and what the agent returns, conversation history that survives a restart, and a record of every model call and tool call for debugging. The Agents SDK supplies those parts in a small API, so the code you still write is the instructions, the tools and the decisions about where each control goes.

Those decisions are where projects go wrong. A guardrail attached to the wrong agent never runs. A turn limit left at its default ends a long task with an exception that nobody catches. Traces are uploaded with customer data in them because tracing is on by default. Anyone who builds on the SDK, reviews such code or debugs one of its traces needs to know what the Runner does on each turn and which setting controls it.

What you will be able to do

  • Define an Agent with instructions, function tools and handoffs, and say what each field changes in a model call.
  • Trace a Runner run turn by turn and predict how it ends, whether by final output, turn limit or guardrail tripwire.
  • Write a function tool and explain how its name, description and schema are derived and what the model sees when it fails.
  • Choose between a handoff and an agent used as a tool, and place input, output and tool guardrails where they will run.
  • Pick a way to carry conversation state between runs and say what a session stores.
  • Decide what the built-in traces may contain and where they are sent.

Key terms

Agent
A configuration object that pairs a model with instructions, tools, handoffs and guardrails. It holds no conversation state and does nothing until a Runner runs it.
Runner
The class that executes the agent loop. It calls the model, runs the requested tools, switches agents on a handoff and stops on a final output, a turn limit or a guardrail tripwire.
Turn
One model invocation inside a run, together with any tool calls that follow from it. The max_turns setting counts turns.
Function tool
A Python function exposed to the model as a tool. The SDK builds its name, description and argument schema from the function itself.
Handoff
A transfer of the conversation from one agent to another inside a single run. The model triggers it by calling a tool named after the target agent.
Agent as a tool
An agent wrapped with as_tool so that another agent can call it and get its answer back, without giving up control of the conversation.
Guardrail
A check that runs on the first input, on the final output or around a function tool call, and can stop the run.
Tripwire
The signal a guardrail returns to stop a run. The Runner turns it into an exception that the application catches.
Session
A store of conversation items identified by a session id. The Runner loads it before a run and appends the new items after the run.
Trace and span
A trace is the record of one workflow. It is made of spans, which are timed records of single operations such as a model call, a tool call or a handoff.

2Explanation

Introduction

In The Agent Loop you wrote the loop by hand: call the model, run the tool it asks for, append the result, and repeat until the model answers or a limit is reached. In Choosing an Agent Framework you saw that frameworks differ mostly in how much of that loop they take over. The OpenAI Agents SDK takes over the loop and the parts you would add next, and leaves everything else as ordinary Python.

Think of a support desk. Each employee has a job description and a set of systems they may use. A supervisor makes sure every request reaches someone, keeps the case moving until it is answered, and stops it if it drags on. A screening rule turns some requests away at the door, a case file carries what was said earlier, and a call log records who did what. The SDK has one part for each of these:

  • Agent: the job description. A model plus instructions, tools, and the agents it may hand over to.
  • Runner: the supervisor. It runs the loop for whichever agent currently holds the conversation.
  • Function tools: the systems. Python functions the model may call.
  • Handoffs: passing the case to a colleague.
  • Guardrails: the screening rules on what comes in and what goes out.
  • Sessions: the case file, kept between runs.
  • Tracing: the call log.

The SDK is open source under the MIT licence and is installed with pip install openai-agents on Python 3.10 or later. For OpenAI models it uses the Responses API by default, and its repository (opens in a new tab) describes it as provider-agnostic. OpenAI's own guidance (opens in a new tab) on when to reach for it is short: use the SDK when you want the runtime to manage turns, tool execution, guardrails, handoffs or sessions, and call the Responses API directly when you want to own the loop. OpenAI Agents Platform covers the hosted services around it.

This lesson describes version 0.23.1 of the Python package, the latest release on PyPI when the lesson was reviewed in October 2026. The version number still starts with 0, and the project raises the middle number for breaking changes, so read the release notes (opens in a new tab) before copying code from an older tutorial. The worked example runs offline on the SDK's scripted test model, so you can follow every turn without an API key.

How it works

An agent is configuration

An Agent object describes how one model should behave. Creating it calls nothing. These are the fields you will use most, from the agents guide (opens in a new tab):

FieldWhat it controls
nameRequired. Shown in traces and used to build handoff tool names.
instructionsThe system prompt, as a string or as a function that builds it for each run.
model, model_settingsWhich model to call, and settings such as tool_choice. Since 0.20.0 the default model is gpt-5.6-luna.
toolsFunction tools, hosted tools, and other agents exposed as tools.
handoffs, handoff_descriptionThe agents this one may transfer to, and the hint a model sees when this agent is a target.
input_guardrails, output_guardrailsChecks on the first input and on the final output.
output_typeA Pydantic model or other type. When set, the model returns structured output of that type.
python
from agents import Agent, Runner, function_tool


@function_tool
def get_order(order_id: str) -> str:
    """Look up one order.

    Args:
        order_id: The order id, for example A-1001.
    """
    return f"{order_id}: delivered, total 49.90 USD"


agent = Agent(
    name="Support agent",
    instructions="Answer questions about orders. Look an order up before you answer.",
    tools=[get_order],
)
result = Runner.run_sync(agent, "Where is order A-1001?")  # needs OPENAI_API_KEY
print(result.final_output)

State that tools need, such as a database handle or the signed-in user, goes in a context object passed as Runner.run(..., context=...). Tools receive it inside a RunContextWrapper. The context guide (opens in a new tab) states that this object is never sent to the model.

The Runner loop

Runner.run() is asynchronous, Runner.run_sync() wraps it for synchronous code, and Runner.run_streamed() yields events while the run is in progress. All three execute the loop described in the running agents guide (opens in a new tab):

  1. Call the model for the current agent with the current input.
  2. If the output is final, end the loop and return the result.
  3. If the model asked for a handoff, switch the current agent and loop again.
  4. If the model asked for tool calls, run them, append the results and loop again.
  5. If the turn count passes max_turns, raise MaxTurnsExceeded.

Output is final when it is text of the expected type and contains no tool calls. One turn is one model invocation, so a handoff uses up a turn like any other step. max_turns defaults to 10 (the constant DEFAULT_MAX_TURNS in the SDK source), and max_turns=None removes the limit. To return a fallback answer where the exception would be raised, pass error_handlers={"max_turns": handler}.

The return value is a RunResult (opens in a new tab). Its final_output is the answer and last_agent is the agent that produced it. new_items lists every message, tool call, tool output and handoff of the run as typed objects, and to_input_list() converts the run into input items for a following turn.

Function tools

@function_tool turns a Python function into a tool. The tools guide (opens in a new tab) lists what is derived: the tool name from the function name, the description from the docstring, the JSON schema from the type annotations (built with Pydantic), and each argument's description from the docstring's Args section. The function may be sync or async. Version 0.19.0 added agents.decorators.tool as a shorter alias, and the current documentation uses it, so @tool and @function_tool are the same decorator.

Function tools run in your process. They are one of five tool categories. The others are hosted OpenAI tools such as web search, local runtime tools such as shell and computer use, agents exposed as tools, and an experimental Codex tool.

When a function tool raises, the run continues. The Runner calls the tool's failure_error_function and sends the text it returns to the model as the tool result. In the current source the default text is one fixed sentence, "An error occurred while running the tool. Please try again.", with no exception message in it. When the model needs detail to recover, return that detail from the function or supply your own error function. Passing failure_error_function=None makes the error propagate to your code.

Handoffs and agents as tools

A handoff (opens in a new tab) transfers the conversation to another agent. To the model it is one more tool: an agent named Refund agent listed in handoffs appears as transfer_to_refund_agent. When the model calls it, the Runner makes the target the current agent and runs the next turn with the target's instructions, model and tools. By default the new agent sees the whole conversation so far. An input_filter passed to handoff() can trim that history, for example with the built-in handoff_filters.remove_all_tools.

The alternative is agent.as_tool(...), which exposes an agent as a tool of a manager agent. The agents guide describes the difference: with agents as tools a central agent keeps control of the conversation and calls specialists, while with handoffs a specialist takes over the conversation. Use the first when one agent must combine several specialists' results into one answer, and the second when the specialist should answer the user directly.

Guardrails

A guardrail (opens in a new tab) is a function that returns GuardrailFunctionOutput(output_info=..., tripwire_triggered=...). A tripwire stops the run with an exception for your application to catch.

Two details cause most surprises. First, agent-level guardrails follow the run and not the list of agents: input guardrails run only for the agent that starts the run, and output guardrails only for the agent that finishes it. Second, input guardrails run in parallel with the agent by default. That keeps latency low, but the guardrails guide warns that the agent may already have consumed tokens and executed tools when the tripwire fires. In the SDK source, the non-streaming Runner.run path starts the guardrail and the first model turn together and waits for both before a second turn begins, so the turn that overlaps the check is the starting agent's first one, including any tool that agent calls in it. Set run_in_parallel=False when the check must finish first. For ready-made checks, OpenAI's separate Guardrails library offers GuardrailAgent (opens in a new tab), which builds an ordinary Agent with guardrails from a configuration file. Guardrails and Content Safety covers what to check for.

Sessions and conversation state

A run does not remember the previous run. The SDK documents four ways to carry state forward:

StrategyWhere the state livesWhat you pass on the next turn
result.to_input_list()In your applicationThe list plus the new message
session=In storage you choose, managed by the SDKThe same session
conversation_id=In the OpenAI Conversations APIThe id and the new message
previous_response_id=In the OpenAI Responses APIThe last response id and the new message

With a session, the Runner prepends the stored history to the input before the run and stores the run's new items after it. SQLiteSession("id") keeps history in memory and SQLiteSession("id", "chat.db") writes it to a file. Redis, SQLAlchemy, MongoDB, Dapr and encrypted sessions ship as extensions, and you can write your own by implementing four methods. A session cannot be combined with conversation_id or previous_response_id in the same run. Agent Memory discusses what belongs in history in the first place.

Tracing

Tracing (opens in a new tab) is on by default. Each run becomes a trace, named Agent workflow unless you set workflow_name, and inside it the SDK records a span for each agent, model generation, function tool call, guardrail and handoff. With an OpenAI API key present, traces are exported in batches to the Traces dashboard. Decide three things before production:

  • What is captured. Generation and function spans store inputs and outputs unless trace_include_sensitive_data is set to False.
  • Where it goes. add_trace_processor() adds a destination next to OpenAI's. set_trace_processors() replaces the default exporter.
  • Whether it is on. Turn it off with OPENAI_AGENTS_DISABLE_TRACING=1, set_tracing_disabled(True) or RunConfig(tracing_disabled=True). Tracing is unavailable to organisations under a Zero Data Retention policy.

LLM and Agent Observability explains how to read traces once you have them.

Worked example: A two-agent support desk run offline, with a handoff, a tool call, a session, a turn limit and a guardrail

The SDK's testing module (opens in a new tab) provides ScriptedModel, a stand-in model that returns the replies you script and records every call it receives. The Runner, the tool, the handoff, the session and the guardrail below are all real, and only the model is scripted, so the output is the same on every run and no API key is needed.

Install the package with pip install openai-agents and save this as support_desk.py. Do not name the file agents.py, because that would hide the package of the same name.

python
import asyncio
import re

from agents import (Agent, GuardrailFunctionOutput, InputGuardrailTripwireTriggered,
                    MaxTurnsExceeded, RunConfig, Runner, SQLiteSession,
                    function_tool, input_guardrail)
from agents.testing import ScriptedModel, assistant_message, function_call

ORDERS = {"A-1001": ("delivered", 49.90), "A-1002": ("in transit", 120.00)}
OFFLINE = RunConfig(tracing_disabled=True)  # nothing is exported
REQUEST = "I want a refund for order A-1001."


@function_tool
def get_order(order_id: str) -> str:
    """Look up one order.

    Args:
        order_id: The order id, for example A-1001.
    """
    if order_id not in ORDERS:
        return f"No order with id {order_id}."
    status, total = ORDERS[order_id]
    return f"{order_id}: {status}, total {total:.2f} USD"


@input_guardrail(run_in_parallel=False)
def block_card_numbers(ctx, agent, user_input) -> GuardrailFunctionOutput:
    found = re.search(r"\d{16}", str(user_input)) is not None
    return GuardrailFunctionOutput(output_info={"card_number": found},
                                   tripwire_triggered=found)


def build(model):
    refund = Agent(name="Refund agent", instructions="You handle refunds.", model=model,
                   tools=[get_order], input_guardrails=[block_card_numbers])
    return Agent(name="Triage agent", instructions="You route requests.", model=model,
                 handoffs=[refund], input_guardrails=[block_card_numbers])


def script():
    return [
        [function_call("transfer_to_refund_agent", {}, call_id="call_1")],
        [function_call("get_order", {"order_id": "A-1001"}, call_id="call_2")],
        [assistant_message("Order A-1001 was delivered. A refund of 49.90 USD is approved.")],
    ]


async def main():
    model, session = ScriptedModel(script()), SQLiteSession("customer-42")
    result = await Runner.run(build(model), REQUEST, session=session, run_config=OFFLINE)
    print("final_output:", result.final_output)
    print("last_agent:", result.last_agent.name)
    print("new_items:", [type(item).__name__ for item in result.new_items])
    for number, call in enumerate(model.calls, start=1):
        print(f"call {number}: {call.system_instructions!r}",
              [tool.name for tool in call.tools],
              [handoff.tool_name for handoff in call.handoffs], len(call.input))

    model.enqueue([assistant_message("The total for order A-1001 was 49.90 USD.")])
    followup = await Runner.run(result.last_agent, "What was the total again?",
                                session=session, run_config=OFFLINE)
    print("follow-up:", followup.final_output, "| input items:", len(model.last_call.input))

    limited = ScriptedModel(script())
    try:
        await Runner.run(build(limited), REQUEST, max_turns=2, run_config=OFFLINE)
    except MaxTurnsExceeded as error:
        print("stopped:", error, "| unused steps:", limited.remaining_steps)

    blocked = ScriptedModel(script())
    try:
        await Runner.run(build(blocked), "Refund card 1234567812345678.", run_config=OFFLINE)
    except InputGuardrailTripwireTriggered as error:
        print("blocked:", error.guardrail_result.output.output_info,
              "| model calls:", len(blocked.calls))


asyncio.run(main())

What each line shows:

  • The handoff swapped the configuration (calls 1 and 2). Call 1 went out with the triage instructions, no tools and one handoff tool. After the model called transfer_to_refund_agent, call 2 carried the refund agent's instructions and its get_order tool. last_agent confirms who finished.
  • The input grew by two items per turn (1, 3, 5). Each turn appended a call and its output: first the handoff pair, then the get_order pair. The five new_items plus the user message are the six items the session stored.
  • The session supplied the history (7 items). The follow-up run was given only the new question. The Runner prepended the six stored items, so the model could answer about "the total" of an order the new message never names. The follow-up starts at result.last_agent, which is why the refund agent carries the guardrail too: input guardrails run only for the agent that starts a run.
  • The turn limit counted the handoff. With max_turns=2 the handoff used turn 1 and the tool call used turn 2, so the Runner raised MaxTurnsExceeded before the third model call, and one scripted step was left unused.
  • The blocking guardrail stopped the run first. The message with sixteen digits tripped block_card_numbers, and because it runs with run_in_parallel=False the model was never called.

To run the same agents against a live model, delete the model=model arguments and set OPENAI_API_KEY. The model then chooses the handoff and the tool call itself, and its wording will vary between runs.

Edge cases and limitations

A handoff passes the whole history, tool outputs included, to the next agent
By default the receiving agent sees everything the previous agents saw and produced, so a specialist can read tool results that were never meant for it, and prompts grow with every transfer. An input_filter on handoff() controls this, and handoff_filters.remove_all_tools drops the structured tool items. The handoffs guide adds two limits: input filters are not supported when the conversation is managed by OpenAI through conversation_id or previous_response_id, and the summarising alternative, nested handoff history, is an opt-in beta that is off by default.
Forcing a tool with tool_choice applies only until the first tool call
Setting ModelSettings(tool_choice="required") or naming a tool does not make the agent call tools on every turn. To prevent an endless tool loop the SDK resets tool_choice to auto after a tool call, which the agents guide documents under reset_tool_choice (default True). If the tool's result should be the answer, set tool_use_behavior="stop_on_first_tool". Be aware that an output guardrail then inspects a tool result that has already been produced, so it can withhold the text but cannot undo the call.
A model that names a tool that does not exist ends the run
When the model emits a function call whose name matches no tool, the Runner raises ModelBehaviorError by default, as the running agents guide describes. Setting RunConfig(tool_not_found_behavior="return_error_to_model") appends an error for the unresolved call as its output and calls the model again, which the guide recommends when you want the run to remain recoverable. It covers only function tool calls whose name cannot be found.
The turn limit counts handoffs as well as tool rounds
One turn is one model invocation. A run with one handoff, two tool calls made one after the other and a final answer uses four of the default ten turns, and a chain of specialists reaches the limit sooner than a single agent would. Models that request several tools in one response use fewer turns than models that request them one at a time, so the same task can sit comfortably under the limit with one model and pass it with another. Measure how many turns good runs take and set max_turns explicitly.
A session id selects history but does not prove who is asking
The sessions guide states that a session id does not authenticate a user or authorise access to that history. If the id comes straight from a browser, one user can read or continue another user's conversation by sending their id. Derive the id on the server from the authenticated user. Two related limits: a session cannot be used in the same run as conversation_id or previous_response_id, and every run loads the full history unless SessionSettings(limit=N) caps it.
Breaking changes arrive in minor versions
The package version still starts with 0, and the release notes say the middle number increases for breaking changes. Recent examples from those notes: 0.15.0 began raising ModelRefusalError where a refusal used to come back as empty output, and 0.16.0 and 0.20.0 each changed the default model that agents use when none is set. Pin the version, set the model explicitly on every agent, and read the release notes before upgrading.

When to use it, and when something simpler is enough

Use it when

  • You need a tool-calling loop with routing between a few specialised agents, checks on input and output, and conversation memory, and you want orchestration to stay in ordinary Python or TypeScript code.
  • The conversation naturally moves from a triage step to a specialist who answers the user directly. A handoff expresses that with one list on the agent and no routing code.
  • You want every model call, tool call and handoff recorded without instrumenting anything, either in OpenAI's Traces dashboard or in an observability tool you already use through a trace processor.
  • You want to test orchestration deterministically. The scripted model lets a test assert which agent ran, which tools were offered and what input each model call received, with no network access.

Think twice when

  • One model call, or one tool round trip, answers the request. OpenAI's own guidance is to call the Responses API directly for short-lived work that mainly returns the model's response.
  • The process is a fixed sequence that you can write down in advance. Calling agents one after another from plain code, or not using agents at all, is cheaper and easier to test than letting a model choose handoffs.
  • A run must survive a process crash or wait days for an approval, and you need that built in. A run lives in one process, and the SDK's documentation points to RunState, which can resume a paused run, and to durable execution integrations such as Temporal for this.
  • You cannot pin dependencies or absorb breaking changes. The package is still at major version 0 and changes public interfaces in minor releases.

A simpler alternative. A loop written directly against the Responses API, as in The Agent Loop lesson: call the model, run the requested function, send back the output, and stop on a message or a step limit. It is about thirty lines and has no dependency to track. It stops being enough when you find yourself rebuilding what the SDK already has, which usually means a second agent with its own prompt, a check that must run before the model, history that must outlive the process, or a trace you need in order to debug a bad run.

Key takeaways

  • An Agent is configuration (instructions, model, tools, handoffs, guardrails), and the Runner is the loop that calls the model, runs tools and switches agents until there is a final output.
  • A run normally ends in one of three ways: a final output with no tool calls, a MaxTurnsExceeded error once the turn limit (ten by default) is passed, or a guardrail tripwire exception. The application must handle all three.
  • A handoff is a tool call that replaces the current agent's instructions and tools with another agent's, while an agent used as a tool returns its answer to the caller, which keeps control.
  • Agent-level guardrails run once per run, on the first agent's input and the last agent's output, so checks that must apply to every step belong on tools or on every agent that can start a run.
  • A session loads stored history before a run and saves the new items after it, which makes the session id a key to private data that the server must issue and check.
  • Tracing is on by default and records inputs and outputs, so decide what it may capture and where it is sent before real user data flows through the agent.

Example 1 of 5

Temporal running the Runner loop as a durable workflow

TemporalDocumented in an engineering article

Temporal publishes temporalio-openai-agents, an integration between its durable execution platform and the OpenAI Agents SDK. Temporal's blog post and the package README describe it, and the SDK's running agents guide lists it among the durable execution integrations. [17][16][3]

The problem

An agent run is a chain of model calls and tool calls, and any link can fail: a rate limit, a network error, or a crash of the process itself. The README points out that the longer an agent has been running, the more it costs to start the job over. A plain Runner.run call keeps its progress in the memory of one process, so a crash near the end of a long task loses all of it.

Where this topic fits

The agent code keeps its shape. Agent and Runner.run are written as usual, but inside the run method of a Temporal workflow class. The integration's plugin registers an activity for model calls and configures the SDK so that every model invocation in the Runner loop is executed as that activity. Tools that perform I/O are wrapped as activities as well. Temporal saves the result of each completed activity, and that record is what lets a restarted worker continue the loop where it stopped.

How it is applied, step by step

  1. The developer writes the agent and the Runner.run call inside a class marked as a Temporal workflow. The README's first example is a haiku agent whose workflow method contains nothing but ordinary Agents SDK code.
  2. The worker process starts with OpenAIAgentsPlugin. According to the README the plugin registers an activity for model calls, configures the SDK to run model calls as activities, handles serialisation of Pydantic types and propagates the SDK's tracing context.
  3. When the Runner loop reaches a model call, the call runs as a Temporal activity and its result is saved with the workflow.
  4. A tool that calls an external API is written as an activity and given to the agent through activity_as_tool, so its result is saved in the same way. A pure calculation can stay a normal function tool, which then runs inside the workflow.
  5. If a model call is rate limited or a worker crashes, Temporal retries the activity or replays the workflow. Steps that already completed are taken from the saved results, and the loop goes on from the first step that has none.

Why this approach fits

The Runner loop already divides a run into discrete steps with a clear boundary between deciding (the model call) and acting (the tool call). Durable execution needs exactly that division: orchestration code that behaves the same way when replayed, and side effects isolated in units whose results can be saved. Putting the save points at model calls and tool calls means the expensive and unreliable parts of a run are never repeated after a failure, and the developer does not write checkpointing code.

Limitation or tradeoff

The integration does not make ordinary function tools durable. The README states that tools created with @function_tool are not converted into activities and run inside the workflow, so they must be deterministic and must not do network, database or file I/O. A tool that calls an API from there breaks the replay model, and the fix is to rewrite it as an activity. The README also notes that tools that run as activities receive a copy of the SDK context and cannot update it. Beyond the code, the team has to operate a Temporal service and workers, which is a large addition for an agent that finishes in a few seconds.

What the sources document

  • The SDK's running agents guide lists Temporal under durable execution integrations and says the integration can run durable, long-running workflows, including human-in-the-loop tasks. The same section lists Dapr, Restate and DBOS integrations. [3]
  • The README gives the release stage as Generally Available and says that model invocations are automatically routed through Temporal activities, while the logic that coordinates them lives in the workflow. [16]
  • The README states that user-defined function tools, including those created with @function_tool, are not automatically converted into Temporal activities and execute in the workflow, and that activity_as_tool creates a FunctionTool whose invocation schedules the underlying activity. [16]
  • Temporal's blog post, published on 30 July 2025, carries a note that the integration became Generally Available on 23 March 2026. It explains that OpenAI made the Runner an abstract base class, which allowed Temporal to supply an implementation that creates an activity for each agent invocation. [17]

Example 2 of 5

Coinbase AgentKit turning onchain wallet actions into function tools

CoinbaseDocumented in an open-source project

Coinbase's open-source AgentKit repository contains an OpenAI Agents SDK extension, published as the package coinbase-agentkit-openai-agents-sdk, and example chatbots that use it. The extension's README, its single source file and the smart wallet chatbot example describe how it works. [18][19][20][4]

The problem

AgentKit describes each blockchain operation as an action with a name, a description, a Pydantic model for its arguments and an invoke method. The example chatbot loads actions from five providers, covering wallet operations, ERC-20 tokens, price feeds and more. An Agents SDK agent can only call things that are presented to it as tools. Writing a decorated wrapper function for every action by hand would duplicate each schema and drift out of date whenever an action changed.

Where this topic fits

The extension sits between AgentKit and the Agent. One function, get_openai_agents_sdk_tools, takes the configured AgentKit instance and returns a list of FunctionTool objects, which the application passes as Agent(tools=...). From then on the Runner treats them like any other function tool: it sends their schemas to the model and executes the one the model calls.

How it is applied, step by step

  1. The application creates an AgentKit instance with a wallet provider and a list of action providers. The example chatbot uses a smart wallet provider and the CDP API, ERC-20, Pyth, wallet and WETH action providers.
  2. The extension asks the AgentKit instance for its actions.
  3. For each action it takes the JSON schema of the action's Pydantic argument model and adjusts it for OpenAI's rules: no additional properties, every property required and default values removed, applied recursively to nested schemas.
  4. It builds a FunctionTool directly, without the decorator, from the action's name, its description, the adjusted schema and an async function that parses the model's JSON arguments and calls the action.
  5. The list goes into Agent(tools=...). When the model calls one of these tools during a run, the Runner invokes that function and returns its string result to the model as the tool output.

Why this approach fits

A function tool is four things: a name, a description, a JSON schema and an async callable. AgentKit actions already carry all four, so the mapping is mechanical and stays correct when actions are added. Building FunctionTool objects directly suits tools that are discovered at run time, where there is no Python function to decorate. Nothing about an action depends on the Agents SDK, which is why the whole conversion fits in one small package that sits beside AgentKit.

Limitation or tradeoff

These tools sign and send transactions, and the conversion passes only a name, a description, a schema and the invoke function. It attaches no approval rule and no tool guardrail, so any limit on what the agent may spend has to come from the wallet configuration or be added by the application. The example defaults to the base-sepolia test network, which is the right place to try it. The SDK documentation also says that a hand-built FunctionTool must handle errors inside on_invoke_tool, so the automatic error message that decorated tools get does not apply here. Finally, the invoke function calls the action synchronously, which holds up the event loop while a transaction is submitted.

What the sources document

  • The extension's README describes it as the OpenAI Agents SDK extension of AgentKit, which enables agentic workflows to interact with onchain actions. It is installed with pip install coinbase-agentkit coinbase-agentkit-openai-agents-sdk and requires a CDP API key and an OpenAI API key. [18]
  • The source file defines get_openai_agents_sdk_tools, which reads the actions from an AgentKit instance and returns one FunctionTool per action, built from the action's name, description, the JSON schema of its args_schema and an on_invoke_tool coroutine that parses the JSON input and calls action.invoke. [19]
  • A helper in the same file sets additionalProperties to false, lists every property as required and removes default values, recursing into each property and into anyOf, oneOf and allOf subschemas. [19]
  • The smart wallet chatbot example is a terminal chatbot built with the extension. Its README suggests prompts such as transferring ETH, asking the price of BTC, deploying an NFT and deploying an ERC-20 token, and states that NETWORK_ID defaults to base-sepolia. [20]
  • The SDK's tools guide says a FunctionTool can be created directly by providing name, description, params_json_schema and on_invoke_tool, and that with a manually created FunctionTool you must handle errors inside on_invoke_tool. [4]

OpenAI's airline customer service demo routing between specialists with handoffs

OpenAIDocumented in an open-source project

OpenAI publishes the Customer Service Agents Demo, an open-source airline support application. Its Python backend is built on the Agents SDK and its chat interface uses ChatKit. The README describes the agents and three demo conversations, and the backend files airline/agents.py and airline/guardrails.py define them. [21][22][24][23][5]

The problem

An airline support conversation covers unrelated jobs: seat changes, flight status, cancellations and rebooking, policy questions, and compensation after a disruption. A single prompt that holds every policy and every tool is long and hard to keep accurate, and it offers a cancellation tool while the customer is asking about baggage. Customers also change subject in the middle of a conversation, as the first demo flow does when it moves from a seat change to flight status to a question about the aircraft.

Where this topic fits

Handoffs are the routing layer of the backend. The Triage Agent is the entry point, each specialist is an Agent with its own instructions and a short tool list, and the handoffs lists define who may transfer to whom. Input guardrails sit in front of the agents and decide whether a message is handled at all.

How it is applied, step by step

  1. Each specialist is defined with a handoff_description, such as one saying that it updates seats and handles medical or special service seating, plus only the tools that job needs.
  2. The triage agent's handoffs list names five specialists. Two entries are wrapped in handoff(agent=..., on_handoff=...), and the callback fills in the flight and confirmation numbers in the shared context before the specialist starts.
  3. The specialists have handoffs lists too. Each can return to triage, and some transfer directly to another specialist, for example from flight information to booking and cancellation when a delayed flight needs rebooking.
  4. Every agent's instructions begin with RECOMMENDED_PROMPT_PREFIX, the text the SDK suggests for explaining handoffs to the model.
  5. Every agent lists the relevance guardrail and the jailbreak guardrail as input guardrails. Each guardrail runs a small classifier agent with a structured output type and triggers the tripwire when the message is unrelated to airline travel or is unsafe.
  6. When a message arrives, the model of the agent that holds the conversation either answers with its tools or calls a transfer tool, and the Runner switches to the target agent within the same run.

Why this approach fits

Each specialist answers the customer directly, which is the case handoffs are meant for: one tool call swaps the instructions and the tool list, and the conversation history carries over. The guardrails are on every agent for a reason that follows from how the Runner works. Input guardrails run only for the agent that starts a run, and the demo's server starts each message at the agent it has stored as the conversation's current agent, so a guardrail on the triage agent alone would stop checking after the first handoff.

Limitation or tradeoff

This is a demonstration with mock flight data, and the README says so. Routing is a model decision, so a request can be sent to the wrong specialist, and because every specialist can return to triage the graph has cycles in which a confused model could bounce until the turn limit. Each guardrail is a separate model call, so every user message adds two classifier calls to the work of the agent itself. By default a handoff passes the full history on, which means prompts keep growing over a long conversation unless an input filter trims them.

What the sources document

  • The README describes the repository as a demo of a customer service interface built on the OpenAI Agents SDK, with a Python backend that handles the agent orchestration logic and a Next.js interface that uses ChatKit. It lists six agents: a Triage Agent that is the entry point and routes to specialists, and Flight Information, Booking and Cancellation, Seat and Special Services, FAQ, and Refunds and Compensation agents. [21]
  • In python-backend/server.py each chat message is run with Runner.run_streamed, starting from the agent that is stored as the conversation's current agent. The stored name starts as the triage agent and is updated after a handoff and from result.last_agent at the end of the run. The server keeps history as input items taken from to_input_list and does not use an SDK session. [23]
  • In the README's second demo flow, asking for a poem about strawberries trips the Relevance Guardrail and asking for the system instructions trips the Jailbreak Guardrail. In both cases the reply is that the assistant can only answer questions related to airline travel. [21]
  • In airline/agents.py every agent, including the triage agent, is constructed with input_guardrails=[relevance_guardrail, jailbreak_guardrail], and the triage agent's handoffs are set to five specialists, two of them through handoff(agent=..., on_handoff=...). [22]

MongoDB Atlas keeping Agents SDK conversation history with MongoDBSession

MongoDBDocumented in official docs

MongoDB's Atlas documentation has a page on integrating MongoDB with the OpenAI Agents SDK, with a tutorial that builds a travel assistant. The SDK's sessions guide documents the MongoDBSession class that the tutorial uses. [25][7]

The problem

A session held in the memory of one process disappears on restart and is invisible to every other process. A deployment with several workers, containers or serverless functions needs any instance to be able to continue a conversation that another instance started. Teams whose application data is already in MongoDB also do not want to deploy and secure a separate memory service for their agents.

Where this topic fits

The session is the session= argument of Runner.run. Before a run the Runner asks the session for the stored history, and after the run it hands the session the new items. MongoDBSession implements those operations on two collections in the application's database. The agents in the tutorial, a triage agent that calls two specialists as tools, contain no storage code.

How it is applied, step by step

  1. Install the SDK with its mongodb extra, which brings in a version of pymongo that provides AsyncMongoClient.
  2. Create one AsyncMongoClient for the application. The tutorial's tools use it to read reference data about destinations and travel policy.
  3. Create MongoDBSession with a session id, that client and a database name, and call ping to confirm the connection before the first run.
  4. Run the first question with session=session. The Runner loads the empty history, runs the agents and writes the turn to the session's collections.
  5. Run the second question with the same session. The Runner loads the stored turn first, so a question about the hotel budget for "that trip" is understood as the Lisbon trip from the first question.
  6. Any other process that creates a MongoDBSession with the same session id on the same cluster continues the same conversation.

Why this approach fits

The session interface is small: get the items, add items, pop the last item, clear. Conversation history is an ordered, append-mostly list of JSON-like items of varying shape (messages, tool calls, tool outputs), which maps directly onto documents. Keeping it in a shared database makes the workers stateless, and because the history sits in ordinary collections the team can query it to audit what an agent did.

Limitation or tradeoff

A session stores everything and, by default, loads everything. Each run sends the whole stored history to the model unless SessionSettings(limit=N) or a compaction step caps it, so cost grows with the length of the conversation. The SDK guide notes that each write is one batch document that must fit within MongoDB's single-document size limit, and that an oversized batch fails without storing a partial one. The stored history includes tool outputs, which often contain personal data, so it needs the same retention and access rules as the rest of the database. The session id is only a lookup key, and the application must check that the caller is allowed to use it.

What the sources document

  • MongoDB's page states that the Agents SDK provides MongoDBSession, a session implementation that persists conversation history in MongoDB, and that session state then lives in the cluster, so any worker, container or serverless function connected to the same cluster can continue a conversation. [25]
  • The tutorial builds a multi-agent travel assistant in which a triage agent answers by calling two specialist agents as tools, and both specialists read reference data from the same cluster that stores the conversation session. [25]
  • The page says MongoDBSession writes each conversation turn to the agent_sessions and agent_messages collections, that both names are configurable, and that the session creates the required indexes on first use. [25][7]
  • The page explains that because the session stores the first turn in MongoDB, the assistant resolves "that trip" in the second question without the application passing the history itself. [25]
  • The SDK's sessions guide lists MongoDBSession as suited to applications that already use MongoDB or need multi-process storage, and notes that each non-empty add_items call writes one logical-batch document that must fit within MongoDB's single-document size limit. [7]

LangSmith receiving Agents SDK traces through a trace processor

LangChainDocumented in official docs

LangSmith, LangChain's observability product, documents an integration for the OpenAI Agents SDK that is built on the SDK's trace processor interface. The SDK's tracing guide lists LangSmith among its external tracing processors. [26][8]

The problem

By default the SDK sends its traces to OpenAI's Traces dashboard. A team that already keeps the traces of its other LLM applications in LangSmith wants agent runs in the same place, with the agent steps, model calls, tool calls and handoffs visible, and without adding instrumentation to every agent and tool.

Where this topic fits

The integration sits at the end of the tracing pipeline. The Runner creates the trace and its spans as it always does. A trace processor is an object that the SDK notifies when each trace and span starts and ends. LangSmith ships such a processor, and registering it takes one line at start-up, before any agent runs.

How it is applied, step by step

  1. Install langsmith with its openai-agents extra and set LANGSMITH_API_KEY, plus LANGSMITH_PROJECT to choose a project.
  2. Call set_trace_processors with a list containing an OpenAIAgentsTracingProcessor before running agents.
  3. Run the agents unchanged. For each run the SDK opens a trace and creates spans for the agents, generations, function tools and handoffs, and notifies the processor as each one starts and finishes.
  4. The processor sends what it receives to LangSmith, where the run appears with its spans and their details. A typical implementation maps each SDK span to one nested run in the LangSmith trace.
  5. Because set_trace_processors replaces the default list, the SDK's own exporter is no longer registered and these traces do not go to OpenAI. Registering the processor with add_trace_processor keeps both destinations.

Why this approach fits

The processor interface is the SDK's documented extension point for tracing, and it sees everything the Runner records, including guardrails and handoffs that the application's own code never touches. A vendor can therefore support the SDK without hooks inside agents or tools, and a team can change or add a destination without editing any agent. LangSmith covers the product itself.

Limitation or tradeoff

The choice between set_trace_processors and add_trace_processor decides whether OpenAI still receives the traces, and picking the wrong one either doubles the places that hold user data or silently empties a dashboard someone relied on. A processor receives span data with model inputs, outputs and tool arguments unless trace_include_sensitive_data is turned off. The SDK guide warns that processors are independent observers, so a redaction processor registered before an exporter does not stop the exporter if redaction fails. When export must depend on redaction, both belong in one exporter. The guide also says that integrations are supported by their maintainers and that a listing is not an endorsement.

What the sources document

  • The SDK's tracing guide says add_trace_processor adds a processor in addition to sending traces to OpenAI's backend, while set_trace_processors replaces the default processors, so traces are not sent to the OpenAI backend unless one of the new processors does so. [8]
  • The tracing guide lists LangSmith in its external tracing processors list and states that the integration maintainers provide support and that inclusion does not constitute an OpenAI endorsement or security certification. [8]

4Common mistakes

  1. Attaching input guardrails to the triage agent only, then starting later turns from result.last_agent.

    Why it causes problems
    Input guardrails run only for the agent that starts a run. From the second message on, the run starts at a specialist that lists no guardrail, so off-topic requests, jailbreak attempts or personal data pass unchecked while the team believes every message is screened.
    How to recognise it
    Traces of later turns contain no guardrail span. A test that sends a blocked message as the second turn of a conversation gets a normal answer back.
    How to fix it
    Attach the guardrail to every agent that can start a run, or set it once for all runs with RunConfig.input_guardrails. Add a scripted-model test that sends the blocked message after a handoff.

  2. Relying on a default, parallel input guardrail to keep a tool from running.

    Why it causes problems
    In parallel mode the starting agent's first turn runs while the guardrail is still deciding. By the time the tripwire fires that agent may have called a tool, so an email can be sent or a record changed for a request that was then rejected.
    How to recognise it
    A trace of a rejected request shows a function span that finished before the guardrail span, or a tripwire exception arrives together with evidence of the tool's side effect.
    How to fix it
    Set run_in_parallel=False on guardrails that must finish before any action, and protect the tool itself with a tool input guardrail or an approval step.

  3. Raising exceptions inside function tools for problems the model could correct.

    Why it causes problems
    The default error function sends the model a fixed message without the exception text. The model cannot tell a wrong id from a timeout, so it repeats the same call until max_turns is passed and the user gets an error where a second attempt would have worked.
    How to recognise it
    Traces show the same tool call several times in a row, each followed by the identical generic error output, and runs that end in MaxTurnsExceeded.
    How to fix it
    Return correctable problems as a string that names what was wrong and what a valid call looks like, or pass a failure_error_function that returns details you are willing to show the model. Keep exceptions for failures a retry cannot fix.

  4. Calling Runner.run without handling MaxTurnsExceeded and the guardrail tripwire exceptions.

    Why it causes problems
    These are normal outcomes of a run and they arrive as exceptions. An endpoint that does not catch them turns a blocked message or a long task into a server error, and the user sees a failure with no explanation.
    How to recognise it
    Error logs contain MaxTurnsExceeded or InputGuardrailTripwireTriggered stack traces from request handlers, and no test covers a run that hits the limit.
    How to fix it
    Catch the tripwire exceptions and reply with a refusal message. Either catch MaxTurnsExceeded or register a max_turns error handler that returns a fallback answer, and set max_turns from measured runs.

  5. Using a handoff when the calling agent still needs the specialist's answer.

    Why it causes problems
    After a handoff the specialist owns the rest of the run and its output is the final output. The first agent never sees the result, so it cannot combine two specialists' answers, apply its own output type or run its own output guardrails on the reply.
    How to recognise it
    Answers cover only one part of a two-part question, last_agent is always a specialist, and output guardrails defined on the first agent never appear in traces.
    How to fix it
    Expose the specialist with as_tool so that its answer comes back to the calling agent as a tool result. Keep handoffs for cases where the specialist should talk to the user directly.

  6. Leaving tracing at its defaults in an application that handles personal data.

    Why it causes problems
    Tracing is on by default and generation and function spans store inputs and outputs. Customer messages and tool results are exported to OpenAI's trace store, or to whichever processor is registered, without anyone having decided that they should be.
    How to recognise it
    The Traces dashboard shows full user messages and tool outputs from production, and nobody on the team can say which settings control that.
    How to fix it
    Decide per environment. Set trace_include_sensitive_data to False or disable tracing where the data may not leave, choose destinations deliberately with set_trace_processors, and put redaction and delivery in one exporter when export depends on redaction.

python
import asyncio

from agents import (Agent, RunConfig, RunErrorHandlerInput, RunErrorHandlerResult, Runner,
                    ToolCallOutputItem, function_tool)
from agents.testing import ScriptedModel, assistant_message, function_call

INVOICES = {"INV-7": 120.00, "INV-8": 15.50}
OFFLINE = RunConfig(tracing_disabled=True)
QUESTION = "How much do I owe on INV-7?"
FALLBACK = "I could not finish in time. A colleague will follow up by email."


@function_tool
def get_invoice(invoice_id: str) -> str:
    """Return the amount due on one invoice.

    Args:
        invoice_id: The invoice id, for example INV-7.
    """
    if invoice_id not in INVOICES:
        return f"No invoice with id {invoice_id}. Known ids: {', '.join(INVOICES)}."
    return f"{invoice_id}: {INVOICES[invoice_id]:.2f} USD due"


def build(model):
    billing = Agent(name="Billing agent", instructions="You answer invoice questions.",
                    handoff_description="Invoices and amounts due.", model=model,
                    tools=[get_invoice])
    refund = Agent(name="Refund agent", instructions="You handle refunds.",
                   handoff_description="Refunds for delivered orders.", model=model)
    return Agent(name="Triage agent", instructions="You route requests.", model=model,
                 handoffs=[billing, refund])


def script():
    return [
        [function_call("transfer_to_billing_agent", {}, call_id="call_1")],
        [function_call("get_invoice", {"invoice_id": "INV-7"}, call_id="call_2")],
        [assistant_message("You owe 120.00 USD on invoice INV-7.")],
    ]


def on_max_turns(_data: RunErrorHandlerInput[None]) -> RunErrorHandlerResult:
    return RunErrorHandlerResult(final_output=FALLBACK, include_in_history=False)


async def main():
    model = ScriptedModel(script())
    result = await Runner.run(build(model), QUESTION, run_config=OFFLINE)
    print("last_agent:", result.last_agent.name)
    print("tool output:", [item.output for item in result.new_items
                           if isinstance(item, ToolCallOutputItem)])
    print("triage offered:", [handoff.tool_name for handoff in model.first_call.handoffs])
    model.assert_complete()

    limited = ScriptedModel(script())
    result = await Runner.run(build(limited), QUESTION, max_turns=1, run_config=OFFLINE,
                              error_handlers={"max_turns": on_max_turns})
    print("fallback:", result.final_output)


asyncio.run(main())

Why it works:

  • Part 1. Returning a string for an unknown id keeps the detail visible to the model. Had the function raised, the default error function would have replaced the message with a generic sentence.
  • Part 2. A handoff needs nothing more than the target in the handoffs list. The order of that list is the order of the handoff tools in the model call, which is what the third printed line shows.
  • Part 3. The script is the expected shape of the run: one step per model call. assert_complete() fails if the run ended early and left steps unused, and an extra model call would raise UnexpectedModelCall, so the test notices if the orchestration changes.
  • Part 4. With max_turns=1 the handoff is turn 1. Before the second model call the turn count is 2, which passes the limit. The Runner then calls the handler and returns its final_output as a normal RunResult. include_in_history=False keeps the fallback sentence out of the conversation history.

10  generation  Booking agent

Answer these questions:

a. How many turns did this run use, and how many more would it take to pass the default limit? b. Which output guardrails checked the final answer of this run? c. The customer's second message starts a run at result.last_agent. Which input guardrails check it? d. Suppose off_topic_check takes two seconds and the first message is one it should reject. Can book_flight run before the tripwire stops the run? What if the same guardrail were also attached to the booking agent? What would you change? e. Requirements

  • Each answer names the SDK rule that decides it, such as which agent's guardrails run or what a turn is.
  • Answer a gives two numbers and shows how the turns were counted from the span list.
  • Answer d separates what the guardrail mode can guarantee from what must be enforced on the tool.
  • Answer g is a concrete list of settings and code changes, not general advice.

Expected behaviour

A complete review finds five problems: the output guardrail never runs on the specialist's answers, later messages skip the input guardrail, a parallel guardrail overlaps the starting agent's first turn and so cannot be what protects the payment tool, the session id is not tied to the signed-in user, and traces carry customer data to a default destination nobody chose. It also reports that this run used 4 of the 10 default turns, and it ends with specific changes.

Hint 1

Count the generation spans. Each one is a model call, and each model call is a turn.

Hint 2

Ask which agent started the run and which agent produced the final output, then apply the guardrail rules to those two agents only.

Hint 3

For question d, read the description of parallel execution in the Guardrails section again. Ask which agent's first turn overlaps the guardrail, and which tools that agent can call.

Show solution

a. Turns. There are four generation spans (3, 6, 8 and 10), so the run used four turns: the triage call that produced the handoff, two booking calls that each asked for a tool, and the booking call that wrote the answer. The default max_turns is 10. The exception is raised when the count passes the limit, so six more turns would be allowed and the seventh additional turn would raise MaxTurnsExceeded.

b. Output guardrails. None. Output guardrails run only for the agent that produces the final output. That was the booking agent, which has none. no_internal_notes belongs to the triage agent, which did not write the final answer, so it did not run.

c. Input guardrails on the second message. None. Input guardrails run only for the agent that starts a run. The second run starts at the booking agent, and off_topic_check is attached to the triage agent.

d. Parallel guardrail and the payment tool. In the default parallel mode the guardrail and the starting agent's first turn run together, and Runner.run waits for both before it begins a second turn. For the first message the starting agent is the triage agent, so the overlapping turn is the triage model call that produces the handoff. That call costs tokens, and the handoff may be carried out, but the tripwire is raised before the booking agent's first turn, so book_flight cannot run in this wiring. That is an accident of the layout and not a guarantee. The guardrails guide says an agent may already have consumed tokens and executed tools when the tripwire fires, and that is exactly what happens once the guardrail is also attached to the booking agent, as fix g.1 below does. Later messages then start at the booking agent, whose first turn can call book_flight while the two-second check is still running. Two changes are needed. Set run_in_parallel=False on off_topic_check so that it completes before the first model call and a rejected message never reaches an agent. That check reads only the user's message and says nothing about what the model later decides to book, so also guard the tool itself, with a tool input guardrail on book_flight or an approval step before it executes.

e. Session id. A session id selects a stored history and does not authenticate anyone. If the browser chooses it, a user who sends another customer's chat_id gets that customer's conversation loaded into the model's input and can continue it. Create the id on the server and bind it to the authenticated user, for example by looking it up from the user's account, and reject ids that do not belong to the caller.

f. Trace destination and content. With tracing at its defaults and an OpenAI API key configured, the spans are exported to OpenAI's Traces dashboard. Generation spans (3, 6, 8, 10) store model inputs and outputs, which include the customer's messages. Function spans (7, 9) store tool inputs and outputs, which for book_flight may include passenger and payment details. The agent, handoff and guardrail spans (1, 2, 4, 5) describe the structure of the run and carry far less content.

g. Changes before launch.

  1. Attach off_topic_check to both agents, or pass it in RunConfig.input_guardrails for every run, and make it blocking with run_in_parallel=False.
  2. Move no_internal_notes to the booking agent, or to every agent that can produce a final answer.
  3. Put a tool input guardrail or an approval requirement on book_flight.
  4. Generate the session id on the server from the authenticated user, and cap loaded history with SessionSettings(limit=...).
  5. Set max_turns explicitly from measured runs, and register a max_turns error handler or catch MaxTurnsExceeded. Catch InputGuardrailTripwireTriggered and OutputGuardrailTripwireTriggered and reply with a refusal.
  6. Set trace_include_sensitive_data=False, or route traces to an approved store with set_trace_processors, before real customer data flows through.

Check your answer

  • Did you count 4 turns by counting generation spans, with 6 turns left before the default limit is passed?
  • Did you answer "none" to both b and c, and give the first-agent and last-agent rules as the reasons?
  • Does your answer to d say which agent's turn overlaps the guardrail, and include both a blocking guardrail and a control on book_flight itself?
  • Does your list in g change the guardrail placement, the session id, the turn limit handling and the tracing settings?
