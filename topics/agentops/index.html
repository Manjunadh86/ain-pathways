AgentOps

AgentOps is an observability platform for AI agents. Its SDK records each agent run as a trace made of nested spans (agents, model calls and tool calls), and its dashboard replays the run step by step with token counts, an estimated cost and an error status for every step.

1Overview

Why it matters

An agent that takes twelve steps to answer one request can fail at any of them. A tool times out, the model repeats the same call, or one agent hands the task to the wrong colleague. The final answer does not show which step went wrong, and lines printed to a terminal lose the order and nesting of the calls as soon as several agents take turns. AgentOps keeps that structure, so you can open one run and read it as a timeline.

The second reason is money. Every step of an agent run resends a growing context, so the price of a run is hard to guess from the prompt alone. AgentOps attaches token counts and an estimated cost to each model call and adds them up per run. Engineers who debug agents, people who pay the model bill and anyone choosing between tracing tools need to know what AgentOps records automatically, what you must add yourself, and which of its numbers are estimates.

Key terms

Trace
The complete record of one run, identified by a trace ID and made of spans. AgentOps also calls it a session.
Span
One timed step inside a trace. It has a name, a start and end time, a status, a set of attributes and usually a parent span.
Span kind
The label that says what a span represents. The AgentOps documentation lists SESSION, AGENT, WORKFLOW, OPERATION or TASK, LLM and TOOL, and the SDK also defines GUARDRAIL for input and output checks.
Session replay
The dashboard view that shows a recorded run as a timeline of spans with the details of the span you select. It displays what happened and does not run the agent again.
Auto-instrumentation
Code in the SDK that wraps supported model clients and agent frameworks so that their calls are recorded without changes to your own functions.
Decorator
A marker such as @agent or @tool written above your own class or function so that each use of it becomes a span.
End state
The final status of a trace. AgentOps accepts Success, Error and Indeterminate, and uses Success when you give none.
Tag
A short label attached to a trace, used to filter and group runs in the dashboard.
Price table
A list of per-token prices for each model. The open-source AgentOps backend takes its table from the tokencost project.
OTLP
The OpenTelemetry Protocol, the standard format in which the SDK sends finished spans to the AgentOps backend.

2Explanation

Introduction

In LLM and Agent Observability you learned the vocabulary of tracing: a trace is the record of one request, and a span is one timed step inside it. That lesson was about the idea. This one is about a specific product that applies the idea to agents.

Think of the flight recorder on an aircraft. Nobody looks at it during a normal flight. After an incident, investigators replay it and see every control input in order, with timestamps. A session replay in AgentOps is the same kind of record for an agent run: each model call, each tool call and each error, in order, with how long it took and what it cost. Replaying the recording does not fly the plane again, and replaying a session does not run the agent again. You are reading what happened.

AgentOps has two parts. The first is an open-source SDK, agentops, for Python (a TypeScript SDK also exists). You call agentops.init() once and it starts recording model calls and the activity of the agent frameworks it supports. The second is a backend with a dashboard, where recorded runs are stored and displayed. The AgentOps homepage (opens in a new tab) lists a hosted free tier of up to 5,000 events and a paid tier that starts at $40 per month. The backend can also be self-hosted.

One warning about the name. "AgentOps" is also used as a general word for operating agents in production, in the way "MLOps" is used for models. In this lesson it always means the product from agentops.ai.

The lesson covers how the SDK turns a run into spans, how to read a replay, how the cost figures are calculated, how AgentOps connects to agent frameworks, and how to find agent-specific failures such as loops and answers that are quietly wrong. It also points out where the product's marketing, its documentation and its code disagree, because you will meet those gaps the first time you rely on a feature.

How it works

Two lines, then automatic recording

python
import agentops

agentops.init()   # reads the AGENTOPS_API_KEY environment variable

After init(), the SDK looks for supported libraries that are installed, such as the OpenAI and Anthropic clients, and wraps their API calls. The core concepts page (opens in a new tab) says the SDK is built on OpenTelemetry, so what it produces are ordinary OpenTelemetry spans. They are queued and exported in batches to an OTLP endpoint. The SDK reference (opens in a new tab) gives the default endpoint as https://otlp.agentops.ai/v1/traces and the default export interval as one second.

By default init() also starts one trace that lasts until the program exits. That suits a script. A web service or a batch job should pass auto_start_session=False and start one trace per request or per task, as shown below.

This lesson describes SDK version 0.4.21, the current release on PyPI (opens in a new tab). It was published in August 2025 and was still the newest release in October 2026, so look at the release history before you adopt it. Older tutorials use agentops.record(), ActionEvent, track_agent and end_session(). The SDK reference marks all of these as deprecated and due for removal in version 4.0. The documentation also uses "session" and "trace" for the same thing: the root span has the kind SESSION, and the dashboard views are still named after sessions.

What a run looks like: the span hierarchy

Every recorded step is a span with an ID, a name, a kind, a start and end time, a status and attributes. The kind decides where the span sits in the tree.

Span kindCreated byWhat it carries
SESSIONinit(), start_trace() or @traceTrace name, tags, end state, host and SDK details
AGENT@agent on a class, or a framework integrationThe agent's name
WORKFLOW@workflowA named group of operations
OPERATION or TASK@operation or @task (aliases)Arguments, return value, duration
LLMAutomatic instrumentation of the model clientModel, provider, prompt and completion tokens, estimated cost, messages
TOOL@tool, or a framework integrationTool name, input, output, duration, optional declared cost

A @guardrail decorator also exists. It records an input or output check as a span of its own.

Adding spans for your own code

Automatic instrumentation sees model calls. It cannot know which of your functions is the refund agent and which is the order lookup tool. Decorators supply that.

python
import agentops
from agentops.sdk.decorators import agent, operation, tool

agentops.init(auto_start_session=False, default_tags=["support", "prompt-v12"])

@tool(name="lookup_order", cost=0.002)      # cost: USD you declare for one call
def lookup_order(order_id: str) -> dict:
    ...

@tool(name="issue_refund")
def issue_refund(order_id: str, amount: float) -> str:
    ...

@agent(name="RefundAgent")
class RefundAgent:
    @operation
    def handle(self, ticket: str) -> dict:
        ...                                   # model calls made here become LLM spans

trace = agentops.start_trace("refund-ticket", tags=["ticket-8841"])
outcome = RefundAgent().handle("Order A-1007 arrived broken.")
agentops.end_trace(trace, end_state="Success" if outcome["refunded"] else "Error")

Three choices in this snippet matter more than the decorators do:

  • Trace boundary. One trace per ticket gives one replay per ticket.
  • Tags. A tag such as prompt-v12 lets you compare runs before and after a prompt change.
  • End state. The last line decides whether the run counts as a success. The section on failures explains why you should not leave this to the default.

Session replay: reading the waterfall

The dashboard page (opens in a new tab) describes a Session Drawer for finding past sessions and three views:

  • Session Drilldown lists recorded sessions with data such as total execution time, shows model calls as a chat history, and charts which kinds of event ran and how long they took.
  • Session Waterfall is the replay. The left side is a timeline of model calls, actions, tool calls and errors. The right side shows the details of the selected event, for example the exact prompt and completion of a model call.
  • Session Overview aggregates all sessions in one view.

Read a waterfall from top to bottom with four questions. Which span is longest? Which spans are marked as errors? Does any span name repeat? Do the prompt token counts climb from one model call to the next?

Cost and token tracking

A model API returns token counts, not prices. AgentOps turns them into money with a price table:

cost=prompt tokens106×pin+completion tokens106×pout\text{cost} = \frac{\text{prompt tokens}}{10^{6}} \times p_{\text{in}} + \frac{\text{completion tokens}}{10^{6}} \times p_{\text{out}}cost=106prompt tokens​×pin​+106completion tokens​×pout​

Here pinp_{\text{in}}pin​ and poutp_{\text{out}}pout​ are the model's prices per million tokens. In the open-source backend the table is loaded from tokencost, a price list that AgentOps maintains on GitHub. Costs are summed per trace. The read-only Public API (opens in a new tab) returns them as prompt_cost, completion_cost and total_cost, next to prompt_tokens, completion_tokens, cache_read_input_tokens and reasoning_tokens.

Three limits follow from this mechanism:

  • The figure is an estimate from list prices. It knows nothing about your discounts.
  • In the open-source backend, a model name that is missing from the table is priced at zero. It is not flagged.
  • A call that is not a model call costs nothing unless you declare a price with @tool(cost=...). In the SDK source, the decorator stores that number on the span as the attribute gen_ai.usage.total_cost (decorator code (opens in a new tab), attribute names (opens in a new tab)). The open-source backend's metrics code (opens in a new tab) uses a span's stored total cost when it has one and sums these into the trace's total_cost. A declared tool fee therefore raises total_cost without raising prompt_cost or completion_cost.

Finding agent-specific failures

A web request fails loudly, with an error code. An agent often fails quietly: it returns a polite answer after its tools have failed. AgentOps gives you four signals, and no single one is enough.

  1. Trace end state. Success, Error or Indeterminate, which map to the OpenTelemetry statuses OK, ERROR and UNSET. The traces page (opens in a new tab) states that the default is success when you pass no end state. A run that merely finished is recorded as a success unless your code says otherwise.
  2. Span status. A decorated function's span records a failure when an exception escapes the function. An agent loop usually catches a tool error and hands the message back to the model, so in that design no exception escapes and the status alone can look clean.
  3. Trace metrics. The Public API reports success_count, fail_count and indeterminate_count for a trace.
  4. Patterns in the replay. The same tool call repeated with the same arguments, two agents passing work back and forth, and prompt tokens that grow on every call.

Do not expect the fourth signal to be raised for you. Partner pages for AG2 and AutoGen list "recursive thought detection" as a feature, but the roadmap table in the AgentOps repository (opens in a new tab) marks infinite-loop and recursive-thought detection as still in progress. Keep the step limit from The Agent Loop in your own code and check for repetition yourself, as the worked example does.

Getting data out, and running it yourself

The Public API exchanges a project API key for a bearer token and then serves traces, spans and their metrics by ID. An MCP server wraps the same API so that a coding assistant can read a trace. If traces must stay on your own infrastructure, the self-hosting guide (opens in a new tab) describes the stack: a FastAPI server, a Next.js dashboard, PostgreSQL through Supabase, ClickHouse for trace analytics and an OpenTelemetry Collector.

Worked example: Replaying a refund run that reports success after three failed tool calls

A support agent handled one ticket, a refund for order A-1007. It answered the customer and returned without an exception, so the trace ended as Success. Its recorded spans are written below as Python data so that everyone gets identical output. The field names are modelled on the span records of the AgentOps Public API (span_id, parent_span_id, span_name, status_code), with token counts and tool arguments as attributes. The tool_cost line in the metrics is our own addition: the Public API has no such field, and a declared tool fee is folded into total_cost. The trace is a teaching example, not a real customer run. The prices are the tokencost list prices for gpt-4o-mini: $0.15 per million prompt tokens and $0.60 per million completion tokens.

Save this as replay.py and run python3 replay.py. It needs only the standard library.

python
from collections import Counter

PRICE = {"gpt-4o-mini": (0.15, 0.60)}   # USD per 1M prompt / completion tokens
OK, ERR = "STATUS_CODE_OK", "STATUS_CODE_ERROR"
REFUND = '{"order_id": "A-1007", "amount": 49.0}'
# (span_id, parent_span_id, kind, span_name, start_ms, duration_ms, status_code, attributes)
SPANS = [
    ("s1", None, "SESSION", "refund-agent.session", 0, 9400, OK, {}),
    ("a1", "s1", "AGENT", "RefundAgent", 20, 9360, OK, {}),
    ("l1", "a1", "LLM", "gpt-4o-mini", 40, 860, OK, {"prompt": 620, "completion": 45}),
    ("t1", "a1", "TOOL", "lookup_order", 910, 400, OK, {"args": '{"order_id": "A-1007"}', "cost": 0.002}),
    ("l2", "a1", "LLM", "gpt-4o-mini", 1320, 980, OK, {"prompt": 790, "completion": 52}),
    ("t2", "a1", "TOOL", "issue_refund", 2310, 1010, ERR, {"args": REFUND}),
    ("l3", "a1", "LLM", "gpt-4o-mini", 3330, 1050, OK, {"prompt": 960, "completion": 48}),
    ("t3", "a1", "TOOL", "issue_refund", 4390, 1010, ERR, {"args": REFUND}),
    ("l4", "a1", "LLM", "gpt-4o-mini", 5410, 1090, OK, {"prompt": 1130, "completion": 48}),
    ("t4", "a1", "TOOL", "issue_refund", 6510, 1010, ERR, {"args": REFUND}),
    ("l5", "a1", "LLM", "gpt-4o-mini", 7530, 1830, OK, {"prompt": 1300, "completion": 130}),
]


def llm_cost(name, attrs):
    prompt_price, completion_price = PRICE[name]
    return attrs["prompt"] * prompt_price / 1e6, attrs["completion"] * completion_price / 1e6


def depth(span_id, parents):
    return 0 if parents[span_id] is None else 1 + depth(parents[span_id], parents)


parents = {s[0]: s[1] for s in SPANS}
print("WATERFALL")
for sid, _, kind, name, start, dur, status, _ in SPANS:
    flag = "FAIL" if status == ERR else "ok"
    print(f"{start:>5} ms {dur:>5} ms  {flag:<4} {'  ' * depth(sid, parents)}{kind} {name}")

llms = [s for s in SPANS if s[2] == "LLM"]
tools = [s for s in SPANS if s[2] == "TOOL"]
costs = [llm_cost(s[3], s[7]) for s in llms]
prompt_cost, completion_cost = sum(c[0] for c in costs), sum(c[1] for c in costs)
tool_cost = sum(s[7].get("cost", 0) for s in tools)
metrics = {
    "span_count": len(SPANS),
    "success_count": sum(s[6] == OK for s in SPANS),
    "fail_count": sum(s[6] == ERR for s in SPANS),
    "prompt_tokens": sum(s[7]["prompt"] for s in llms),
    "completion_tokens": sum(s[7]["completion"] for s in llms),
    "prompt_cost": f"{prompt_cost:.7f}",
    "completion_cost": f"{completion_cost:.7f}",
    "tool_cost": f"{tool_cost:.7f}",
    "total_cost": f"{prompt_cost + completion_cost + tool_cost:.7f}",
}
print("\nMETRICS")
for key, value in metrics.items():
    print(f"{key:<18}{value}")

print("\nFINDINGS")
if SPANS[0][6] == OK and metrics["fail_count"]:
    print(f"- root span is OK but {metrics['fail_count']} child spans failed")
for (name, args), n in Counter((s[3], s[7]["args"]) for s in tools).items():
    if n >= 3:
        print(f"- {name} was called {n} times with identical arguments")
first_fail = min(s[4] for s in SPANS if s[6] == ERR)
retry = sum(sum(llm_cost(s[3], s[7])) for s in llms if s[4] > first_fail)
print(f"- LLM calls after the first failure cost {retry:.7f} USD, "
      f"{retry / (prompt_cost + completion_cost):.0%} of LLM spend")
print(f"- prompt tokens per call: {[s[7]['prompt'] for s in llms]}")

What the numbers say:

  • The status is wrong. The root span is OK, yet three TOOL spans failed. The function returned normally, so nothing told AgentOps that the task failed. Ending the trace with end_state="Error" when no refund was issued corrects the record.
  • It is a loop. issue_refund ran three times with identical arguments. A retry that changes nothing cannot succeed. In the waterfall this is one span name repeating with a model call in between.
  • The loop cost most of the money. 4,800 prompt tokens × $0.15 / 1,000,000 = $0.00072 and 323 completion tokens × $0.60 / 1,000,000 = $0.0001938, so the model calls cost $0.0009138. The three calls after the first failure account for $0.0006441 of that, which is 70%.

  • The tool fee dominates. The declared $0.002 for lookup_order is more than twice the model spend. Without @tool(cost=...) it would be missing from the total.

Edge cases and limitations

A caught tool error leaves the span and the trace looking healthy
A decorated function's span records a failure only when an exception leaves the function. Agent loops normally catch tool errors and give the message to the model as an observation. If the tool function itself catches the error and returns a message, even the TOOL span ends cleanly, and the trace keeps its default end state of Success. Decide in code what failure means for the task, let the tool raise or record the failure as an attribute, and pass an explicit end state to end_trace.
A model that is missing from the price table costs zero
In the open-source backend's ClickHouse functions, the price lookup falls back to 0 when the model name is not in the table, and the result is rounded to seven decimal places. A newly released model, a fine-tune with a custom name or a self-hosted model can therefore appear to be free. Before trusting a total, look for LLM spans that have token counts but a cost of zero.
An advertised feature may not be in the product you are running
The homepage advertises Time Travel Debugging, and partner pages list recursive thought detection. In the open-source dashboard code read for this lesson, the time travel page renders a notice that the feature was removed, and the repository's roadmap table marks loop detection as in progress. The v2 documentation pages read for this lesson describe neither feature. Test a feature on your own traces before a design depends on it.
One long trace swallows many requests
By default init() starts a trace and keeps it until the process ends. In a web server or a queue worker, every user's request then lands in the same trace, and replays, tags and per-trace cost stop meaning anything. Pass auto_start_session=False and open one trace per request with the trace decorator, start_trace or the context manager. The quickstart notes that with this setting nothing is recorded until you start a trace yourself.
End-state words differ between documentation pages
The traces page documents Success, Error and Indeterminate. The quickstart shows Fail in a commented example, and the SDK reference says any descriptive string is accepted. The trace metrics endpoint counts success, fail and indeterminate. Use the three documented values consistently, and check in the dashboard how a custom string is displayed before you rely on one.

When to use it, and when something simpler is enough

Use it when

  • Your agent is built on a framework AgentOps instruments, such as Google ADK, the OpenAI Agents SDK or AG2, and you want step-by-step replays without writing tracing code.
  • Several agents take turns in one run and you need to see which agent made each model call and each tool call.
  • You want an estimated cost per run that can include fees you declare for tools, not only model tokens.
  • You are prototyping or run a small workload. The homepage lists the hosted free tier as free up to 5,000 events, and the SDK repository is MIT-licensed.

Think twice when

  • You need prompt versioning, evaluation datasets and experiments in the same tool. The v2 documentation read for this lesson covers tracing, replay and cost, so compare the other tracing tools in this roadmap first.
  • Traces would contain personal or regulated data and you can neither self-host the backend nor get an enterprise agreement. LLM spans store the prompt and completion text.
  • Your team already sends OpenTelemetry spans to an observability backend it runs. A second dashboard for agents splits debugging across two tools.
  • You need an exact bill per customer. The cost figures are estimates from public list prices.

A simpler alternative. Structured logging. Write one JSON line per model call and tool call with a run ID, the step number, token counts, duration and any error, then analyse the file with a short script like the one in the worked example. This is enough for a single agent in one process. It stops being enough when several agents or concurrent runs interleave, when teammates need to open and share one specific run, or when you want cost and failures compared across hundreds of runs.

Key takeaways

  • AgentOps records each agent run as a trace: a root session span that contains agent, operation, model-call and tool-call spans, which the dashboard replays as a timeline.
  • One call to agentops.init() before the agent runs instruments supported model clients and frameworks, and decorators add spans for your own agents, operations and tools.
  • Cost figures are estimates made from token counts and a public price table, so an unlisted model can show as free, and tool fees appear only when you declare them.
  • A trace ends as Success by default, so set the end state from the task outcome and look inside the replay for failed spans, repeated tool calls and growing prompts.
  • Framework integrations work by attaching to or patching the framework, so test them again after an upgrade and check advertised features against the current documentation.

Example 1 of 5

Google ADK agents traced by replacing ADK's own tracer

Google Agent Development KitDocumented in official docs

The Agent Development Kit documentation has a page titled AgentOps observability for ADK that explains how the integration works internally. The AgentOps documentation has a matching Google ADK page with a runnable sample. [27][13]

The problem

An ADK application can chain several agents, each making model calls and tool calls. The ADK page says that ADK includes its own OpenTelemetry-based tracing, aimed mainly at tracing the basic flow of execution. A developer debugging a multi-step run wants more than the flow: the prompt, completion, token counts and errors of every step, in one hierarchy. Two tracers recording the same calls would also produce duplicate spans.

Where this topic fits

agentops.init() goes at the top of the script that runs the ADK Runner, before any agent executes. Nothing else in the ADK code changes. After the run, the developer reads the trace in the AgentOps dashboard.

How it is applied, step by step

  1. The developer installs agentops, sets AGENTOPS_API_KEY and calls agentops.init() at the beginning of the ADK application script.
  2. With the default auto_start_session=True, init() creates a root session span whose name comes from the trace_name argument.
  3. AgentOps detects ADK and swaps ADK's internal tracer for a no-op tracer, so ADK's own attempts to create spans produce nothing.
  4. AgentOps wraps the method that runs an agent. Each agent execution becomes a span named in the form adk.agent.AgentName, and a sub-agent's span nests under the span of the agent that called it.
  5. Each model call becomes a child span named after the model, in the form adk.llm.model-name. It holds the prompt and model parameters and, when the call completes, the completion, token usage and finish reason.
  6. Each tool call becomes a single child span named after the tool, in the form adk.tool.ToolName, holding the input parameters and the returned result.
  7. The dashboard shows these spans as a waterfall, so the developer can follow the order and duration of every step and open any span for its details.

Why this approach fits

A multi-agent run is a tree, and the naming scheme makes the tree readable at a glance: every span name says whether it is an agent, a model call or a tool. Making one tracer authoritative avoids the double-counting of tokens and cost that two overlapping tracers would cause. Because the wrappers reuse the data ADK already extracts for its own telemetry, the attributes match what ADK itself considers the request and response.

Limitation or tradeoff

The integration patches ADK internals, including private methods. An ADK release that renames or moves them can leave you with missing spans and no error message, so check a known trace after every ADK upgrade. Silencing ADK's native tracer also has a side effect to plan for: if another backend in your stack depends on ADK's own spans, expect it to stop receiving them once AgentOps is initialised, and test that before turning it on in production. The ADK page labels the integration as supported in ADK Python, so check before relying on it with another ADK language.

What the sources document

  • The ADK documentation states that ADK includes its own OpenTelemetry-based tracing system, primarily aimed at tracing the basic flow of execution within agents, and presents AgentOps as a dedicated platform that adds replay analytics, debugging of spans, and cost and latency tracking. [27]

OpenAI Agents SDK handoffs and tool calls captured through the trace-processor interface

[30][14][17][18]

The problem

The Agents SDK already traces a run: model generations, function tool calls, guardrails and handoffs between agents. By default those traces go to OpenAI's own Traces dashboard, and the tracing page states that tracing is unavailable for organisations under a Zero Data Retention policy. A team that wants the same step-level record next to cost figures and next to traces from other frameworks needs those spans delivered somewhere else.

Where this topic fits

agentops.init() runs before any Agent is created or any Runner call is made. During the run the SDK emits its own trace events, and the AgentOps instrumentation converts them. Afterwards the run appears in AgentOps as one trace containing agent, generation, function and handoff spans.

How it is applied, step by step

  1. The application calls agentops.init(). According to the AgentOps integration page, the Agents SDK is then instrumented automatically.
  2. The instrumentation registers its own trace processor with the SDK. A trace processor is the extension point through which the SDK reports the start and end of each trace and of each agent, function, generation and handoff span.
  3. In the instrumentor code, the processor is installed with set_trace_processors, so it replaces the SDK's default processor instead of running beside it. The README also describes patching the Runner class to capture streamed runs, but the instrumentor code read for this lesson contains no such patch.
  4. When the SDK reports the start of a span, the exporter opens an OpenTelemetry span and leaves it open with an unset status.
  5. When the SDK reports the end of that span, the exporter adds the final attributes such as outputs and token usage, sets the status to OK or ERROR, and ends the span, so its duration is the real duration of the step.
  6. A handoff becomes its own span recording the agent that gave up control and the agent that received it, which lets a reader of the replay see who held the task at each moment.

Why this approach fits

The SDK already knows where an agent run, a tool call and a handoff begin and end, and it publishes that through a documented interface. Listening there is more reliable than guessing the structure from raw model calls. Handoffs matter for agent debugging in particular: when an answer is wrong, the first question is which agent produced it, and a handoff span answers that directly.

Limitation or tradeoff

The OpenAI page distinguishes adding a processor, which keeps sending traces to OpenAI as well, from replacing the processors, which stops that unless the new processor sends them there. The AgentOps and OpenAI pages do not say which one AgentOps does. The instrumentor code calls set_trace_processors with only its own processor, so by OpenAI's description the run no longer reaches OpenAI's own Traces dashboard once agentops.init() has run, unless you add a processor that sends it there. That is our reading of the code, so confirm it in your own project. The AgentOps sources also disagree with each other: the module docstring says add_trace_processor, the README says Runner is patched, and the code does neither. The integration depends on the SDK's trace-processor interface, so test it again after an Agents SDK upgrade. The OpenAI page still links to an AgentOps v1 documentation URL, while the current guide lives under v2.

tokencost, the open-source price table behind AgentOps cost estimates

AgentOps (tokencost project)Documented in an open-source project

tokencost is an open-source Python library in the AgentOps-AI GitHub organisation. Its README describes what it calculates. Two files in the open-source AgentOps backend show how the backend uses a price table: a cost module in the OpenTelemetry Collector builder and a ClickHouse migration. [25][19][20]

The problem

A model API reports how many tokens a call used. It does not report what the call cost. Prices differ for every model, differ between prompt and completion tokens, and change when providers update their price lists. An agent run may mix several models, so a per-run cost needs a maintained table and one consistent calculation.

Where this topic fits

The calculation happens after the SDK has recorded token counts on each LLM span and before a cost is shown. The inputs are a model name and two token counts. The output is a prompt cost and a completion cost, which are summed per trace.

How it is applied, step by step

  1. The SDK records the model name, the prompt tokens and the completion tokens on each LLM span, taken from the provider's response.
  2. tokencost maintains a price file with one entry per model: a price per input token and per output token, and for some models a price for cached and reasoning tokens.
  3. The backend's collector builder loads that price file from the installed tokencost package and converts the prices to exact decimal values.
  4. In ClickHouse, a dictionary keyed by model name holds a prompt price and a completion price per thousand tokens.
  5. Two SQL functions do the arithmetic. Each divides the token count by 1,000, multiplies by the price looked up for the model and rounds to seven decimal places.
  6. Prompt cost and completion cost are added for each span and summed over the trace, which is the total a reader sees for a run.

Why this approach fits

Keeping prices in one table and applying one formula gives the same cost for the same tokens whichever framework produced the call. The calculation needs no access to a provider's billing system, so it works for any model with a published price, and the table can be updated without changing the SDK that runs inside your application.

Limitation or tradeoff

The result is an estimate. A list price knows nothing about negotiated discounts or batch pricing. The migration shows a second problem: a model that is not in the dictionary is priced at 0 without any warning, so new, renamed, fine-tuned or self-hosted models can make a run look cheaper than it was. Token counts are only as good as their source too. The tokencost README says it approximates token counts for older Claude models with an OpenAI tokenizer, which matters if you estimate a cost before sending a request. Reconcile the dashboard total with the provider's invoice before using it in a budget.

What the sources document

  • The tokencost README describes the library as client-side token counting and price estimation and says it calculates the estimated USD cost of prompts and completions for major LLM APIs, through functions named calculate_prompt_cost and calculate_completion_cost. [25]
  • The README states that strings and messages are tokenized with Tiktoken, that the Anthropic token counting API is used for Anthropic models above version 3, and that older Claude models are approximated with Tiktoken's cl100k_base encoding. [25]
  • The README's cost table, as read on the access date, lists gpt-4o-mini at 0.15 US dollars per million prompt tokens and 0.6 US dollars per million completion tokens. [25]
  • The cost module of the collector builder loads model costs from the tokencost package's model_prices.json file and reads input_cost_per_token, output_cost_per_token, cache_read_input_token_cost and reasoning_cost_per_token for each model, converting them to Decimal values. [19]
  • The ClickHouse migration creates a dictionary named model_costs_dict with a prompt and a completion cost per 1k tokens, and functions calculate_prompt_cost and calculate_completion_cost that divide tokens by 1000, multiply by the dictionary price with a default of 0, and round to 7 places.   4. The assistant reads the span list: names, parent IDs, durations and status codes, plus the trace's failure counts, token totals and cost.
  5. For a suspicious span it calls get_span to read the full attributes, such as the prompt and the completion of a model call.

The data an assistant needs to debug an agent is already structured: a tree of spans with statuses, inputs, outputs and token counts. 4Common mistakes

  1. Calling agentops.init() after the agent has already started running.

    Why it causes problems
    Instrumentation is attached when init() runs. Model calls and framework activity that happen before it are not wrapped, so the replay starts in the middle of the run or has no LLM spans, and the cost total is too low.
    How to recognise it
    A trace that shows fewer model calls than your provider's usage page for the same run, or whose first steps have no LLM spans, token counts or cost.
    How to fix it
    Call init() once at program start, before any agent is created and before the first model call. The ADK page puts it at the beginning of the application script, and the AG2 page before any use of AG2.

  2. Leaving the trace end state at its default.

    Why it causes problems
    The documented default is success. Every run that returns without an exception is counted as successful, so the success rate looks perfect while users receive apologies and wrong answers.
    How to recognise it
    A success rate close to 100 percent that disagrees with user complaints, or traces marked Success that contain failed tool spans, as in the worked example.
    How to fix it
    Compute the outcome in code (was the refund issued, did the tests pass) and pass Success, Error or Indeterminate to end_trace. Use Indeterminate when the code cannot tell.

  3. Relying on automatic instrumentation alone for a hand-written agent.

    Why it causes problems
    Automatic instrumentation records model calls only. Without decorators they hang directly under the session, tool calls are absent, and you cannot tell which agent or which step caused a model call or spent the money.
    How to recognise it
    A waterfall that is a flat list of LLM spans with no AGENT, OPERATION or TOOL spans, and no way to answer the question of which agent cost the most.
    How to fix it
    Put the agent decorator on agent classes, the operation decorator on their methods and the tool decorator on tool functions. Framework integrations do this for you; your own code needs it written.

  4. Treating the dashboard's cost total as the invoice.

    Why it causes problems
    The total is an estimate from list prices. Models missing from the price table count as zero, and tool fees are missing unless declared. A budget or a customer charge built on it will usually be too low.
    How to recognise it
    The month's total in AgentOps does not match the provider's invoice, or some LLM spans show token counts next to a cost of zero.
    How to fix it
    Reconcile against the provider's invoice regularly, declare tool fees with the cost argument of the tool decorator, and use the figures to compare runs with each other, not to bill anyone.

  5. Copying setup code from older tutorials that use record(), ActionEvent or end_session().

    Why it causes problems
    The SDK reference lists these as legacy functions that are deprecated and will be removed in version 4.0. They log deprecation warnings today and will stop working after an upgrade. The repository README's quick start still shows end_session, so the old style is easy to pick up.
    How to recognise it
    Deprecation warnings in your logs, or imports of ActionEvent, ToolEvent, ErrorEvent, LLMEvent or track_agent in your code.
    How to fix it
    Use the trace decorator or start_trace and end_trace for run boundaries, and the decorators from agentops.sdk.decorators for agents, operations and tools.

  6. Sending every prompt and completion to the hosted backend without a data review.

    Why it causes problems
    LLM spans store the prompt and completion text and tool spans store inputs and outputs. Customer messages, internal documents and secrets pasted into prompts end up in a third-party system that everyone with access to the project can read.
    How to recognise it
    Open any LLM span in the dashboard and read its detail panel. If a real customer's message is readable there, the review has not been done.
    How to fix it
    Decide what may be recorded before production. Redact sensitive fields in your own code before the model call, set env_data_opt_out to stop host details being collected, and self-host the backend if the data may not leave your infrastructure.

Exercise 1

Attribute cost to each agent and detect two agents passing work back and forth

CodingIntermediateAbout 40 min (estimate)Hypothetical scenario

A trip-planning system has two agents. Planner uses gpt-4o and Booker uses gpt-4o-mini. One run was recorded and its spans are below, in start order. The run ended as Success, but no booking was made. Use only the Python standard library.

Prices in USD per million tokens (prompt, completion): gpt-4o 2.50 and 10.00, gpt-4o-mini 0.15 and 0.60.

python
OK, ERR = "STATUS_CODE_OK", "STATUS_CODE_ERROR"
# (span_id, parent_span_id, kind, span_name, status_code, attributes), in start order
SPANS = [
    ("s1", None, "SESSION", "trip-planner.session", OK, {}),
    ("a1", "s1", "AGENT", "Planner", OK, {}),
    ("l1", "a1", "LLM", "gpt-4o", OK, {"prompt": 1200, "completion": 150}),
    ("t1", "a1", "TOOL", "search_flights", OK, {"cost": 0.01}),
    ("l2", "a1", "LLM", "gpt-4o", OK, {"prompt": 1900, "completion": 90}),
    ("a2", "s1", "AGENT", "Booker", OK, {}),
    ("l3", "a2", "LLM", "gpt-4o-mini", OK, {"prompt": 2100, "completion": 60}),
    ("t2", "a2", "TOOL", "confirm_booking", ERR, {}),
    ("a3", "s1", "AGENT", "Planner", OK, {}),
    ("l4", "a3", "LLM", "gpt-4o", OK, {"prompt": 2600, "completion": 70}),
    ("a4", "s1", "AGENT", "Booker", OK, {}),
    ("l5", "a4", "LLM", "gpt-4o-mini", OK, {"prompt": 2800, "completion": 60}),
    ("t3", "a4", "TOOL", "confirm_booking", ERR, {}),
    ("a5", "s1", "AGENT", "Planner", OK, {}),
    ("l6", "a5", "LLM", "gpt-4o", OK, {"prompt": 3300, "completion": 110}),
]

Write a script that reports the cost of each agent, detects whether the two agents are passing the task back and forth, and recommends the end state the run should have had.

Requirements

  • Print one row per agent name with its number of LLM calls, prompt tokens, completion tokens, total cost in USD to six decimal places and share of the run's cost.
  • Attribute a span's cost to the agent whose AGENT span is its parent, and include declared tool costs as well as model costs.
  • Report a ping-pong when four consecutive AGENT spans alternate between exactly two agent names.
  • Recommend the end state Success only if at least one confirm_booking TOOL span has an OK status, and Error otherwise.
  • Keep the functions pure. Each takes the span list as an argument and returns a value without changing the list.

Expected behaviour

The script prints a table in which Planner has 4 LLM calls, 9,000 prompt tokens, 420 completion tokens and a cost of 0.036700 USD (97.8% of the run), and Booker has 2 LLM calls, 4,900 prompt tokens, 120 completion tokens and a cost of 0.000807 USD (2.2%). The total is 0.037507 USD. It reports the ping-pong Planner, Booker, Planner, Booker and recommends the end state Error.

Hint 1

Build a dictionary from the span ID of every AGENT span to its agent name, then look up each span's parent in it.

Hint 2

Several AGENT spans share one agent name, so accumulate into a dictionary keyed by the name and not by the span ID.

Hint 3

For the ping-pong, take the list of agent names in order and slide a window of four over it.

Show solution
python
PRICE = {"gpt-4o": (2.50, 10.00), "gpt-4o-mini": (0.15, 0.60)}  # USD per 1M tokens
REQUIRED_TOOL = "confirm_booking"
# OK, ERR and SPANS as given in the prompt


def span_cost(kind, name, attrs):
    if kind == "LLM":
        prompt_price, completion_price = PRICE[name]
        return (attrs["prompt"] * prompt_price + attrs["completion"] * completion_price) / 1e6
    return attrs.get("cost", 0.0)


def per_agent(spans):
    agent_of = {s[0]: s[3] for s in spans if s[2] == "AGENT"}
    rows = {}
    for _, parent, kind, name, _, attrs in spans:
        if parent not in agent_of:
            continue
        row = rows.setdefault(agent_of[parent], {"llm_calls": 0, "prompt": 0, "completion": 0, "cost": 0.0})
        row["cost"] += span_cost(kind, name, attrs)
        if kind == "LLM":
            row["llm_calls"] += 1
            row["prompt"] += attrs["prompt"]
            row["completion"] += attrs["completion"]
    return rows


def ping_pong(spans, min_turns=4):
    turns = [s[3] for s in spans if s[2] == "AGENT"]
    for start in range(len(turns) - min_turns + 1):
        window = turns[start:start + min_turns]
        if len(set(window)) == 2 and all(window[i] != window[i + 1] for i in range(min_turns - 1)):
            return window
    return None


def end_state(spans, required_tool):
    succeeded = any(s[2] == "TOOL" and s[3] == required_tool and s[4] == OK for s in spans)
    return "Success" if succeeded else "Error"


rows = per_agent(SPANS)
total = sum(row["cost"] for row in rows.values())
print(f"{'agent':<9}{'llm_calls':>10}{'prompt':>8}{'completion':>12}{'cost_usd':>11}{'share':>7}")
for name, row in sorted(rows.items(), key=lambda item: -item[1]["cost"]):
    print(f"{name:<9}{row['llm_calls']:>10}{row['prompt']:>8}{row['completion']:>12}"
          f"{row['cost']:>11.6f}{row['cost'] / total:>7.1%}")
print(f"total cost: {total:.6f} USD")
print("ping-pong:", ping_pong(SPANS))
print("recommended end state:", end_state(SPANS, REQUIRED_TOOL))

Start from this uninstrumented code:

  1. Initialise AgentOps so that no trace starts automatically, with two default tags.
  2. Make lookup_order a tool with a declared cost of 0.002 USD per call, TriageAgent an agent and handle an operation.
  3. Process the three tickets with one trace per ticket, each tagged with the ticket ID.
  4. End each trace as Success or Error according to the resolved field.
  5. Run the script and open the three traces in the dashboard.
  6. Change the last step so that end_trace receives no end state, run again, and compare ticket T-2.

Requirements

  • Pass auto_start_session=False to init() and start every trace yourself with start_trace.
  • Use the tool, agent and operation decorators from agentops.sdk.decorators, with cost=0.002 on the tool.
  • End every trace exactly once, including when handle() raises an unexpected exception.
  • Derive the end state from the outcome dictionary, never from whether an exception occurred.
  • Do not use the deprecated functions start_session, end_session or record.

Expected behaviour

The script prints three lines: T-1 and T-3 resolved with the reply Your order is delivered., and T-2 unresolved with the reply I could not find that order (unknown order A-9999).

In the dashboard you should find three traces named triage-ticket, each carrying its ticket ID as a tag. T-1 and T-3 end as Success and T-2 as Error. Inside each trace there should be an agent span for TriageAgent, an operation span for handle_ticket and a tool span for lookup_order that carries the declared cost, which also counts toward the trace's total cost. The dashboard may show the span kind appended to each name, for example lookup_order.tool. In T-2 the tool span records the LookupError.

After step 6, all three traces end as Success, although T-2 still contains the failed tool span. That difference is the point of the exercise.

Hint 1

The documented manual pattern is start_trace(name, tags=[...]) followed later by end_trace(trace, end_state="...").

Hint 2

Create the TriageAgent instance after the trace has started, so that its agent span belongs to that trace.

Hint 3

Wrap the call to handle() in try and except so that an unexpected exception still ends the trace, then re-raise it.

Show solution
python
import os

import agentops
from agentops.sdk.decorators import agent, operation, tool

agentops.init(
    os.environ["AGENTOPS_API_KEY"],
    auto_start_session=False,              # one trace per ticket, started below
    default_tags=["exercise", "triage-v1"],
)

# ORDERS and TICKETS exactly as given in the prompt


@tool(name="lookup_order", cost=0.002)
def lookup_order(order_id: str) -> dict:
    if order_id not in ORDERS:
        raise LookupError(f"unknown order {order_id}")
    return ORDERS[order_id]


@agent(name="TriageAgent")
class TriageAgent:
    @operation(name="handle_ticket")
    def handle(self, ticket: dict) -> dict:
        try:
            order = lookup_order(ticket["order_id"])
        except LookupError as error:       # the agent recovers, so no exception leaves handle()
            return {"resolved": False, "reply": f"I could not find that order ({error})."}
        return {"resolved": True, "reply": f"Your order is {order['status']}."}


for ticket in TICKETS:
    trace = agentops.start_trace("triage-ticket", tags=[ticket["id"]])
    try:
        outcome = TriageAgent().handle(ticket)
    except Exception:
        agentops.end_trace(trace, end_state="Error")
        raise
    agentops.end_trace(trace, end_state="Success" if outcome["resolved"] else "Error")
    print(ticket["id"], outcome)

Printed output:

text
T-1 {'resolved': True, 'reply': 'Your order is delivered.'}
T-2 {'resolved': False, 'reply': 'I could not find that order (unknown order A-9999).'}
T-3 {'resolved': True, 'reply': 'Your order is delivered.'}

Why it is built this way:

  • auto_start_session=False stops init() from opening one trace for the whole script. The loop opens one per ticket, so each ticket has its own replay, tags and cost.
  • The tool raises and the agent catches. The exception leaves lookup_order, so the tool span records it. It does not leave handle, so the operation span and the trace would both look healthy if you stopped there.
  • The end state comes from outcome["resolved"]. The except Exception branch is only for bugs you did not plan for, and it re-raises so that they are not hidden.
  • For step 6, replace the last end_trace call with agentops.end_trace(trace). The documented default is success, so T-2 is then recorded as a successful run that happens to contain a failed tool call.

The printed output above was checked with a local stand-in for the agentops module. What you see in the dashboard depends on your account and SDK version, so compare it with the expected behaviour and note any difference.
