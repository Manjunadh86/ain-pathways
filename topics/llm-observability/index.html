LLM and Agent Observability (Tracing)

LLM and agent observability means recording what an AI application does on each request as a trace: a tree of timed spans for model calls, tool calls and agent steps, annotated with tokens, cost, latency and errors, so that you can explain afterwards why a run behaved as it did.

1Overview

Why it matters

A conventional web request follows code you wrote, so the same input takes the same path. An LLM application chooses its path at run time. The same prompt can lead to a different sequence of tool calls on the next attempt, every model call costs money in proportion to the tokens it carries, and a final answer can look fine while an earlier step quietly failed. Without a record of the steps, a report such as "the assistant gave the wrong refund date" cannot be traced to a model call, a tool result or a retrieval step.

Anyone who runs an LLM feature beyond a demo needs this: to debug a bad answer, to explain a slow response, to attribute spend to a model, an agent or a feature, and to decide what is safe to store. The last point is easy to miss. Prompts, tool arguments and tool results hold user data, so a trace store that records everything can quietly become a second copy of your customers' private information.

What you will be able to do

  • Describe a trace, a span and a generation, and map them to the names used by OpenTelemetry, the OpenAI Agents SDK, Langfuse and LangSmith.
  • Name the span types and attributes the OpenTelemetry GenAI conventions define for model calls, tool calls and agent invocations.
  • Record tokens and latency on spans and compute the cost of a run correctly, including cached tokens.
  • Decide what to capture by default, what to redact, and where in the telemetry pipeline the redaction should run.
  • Read a trace to find where the time, tokens and errors of a multi-step run came from.
  • Judge the limits of the conventions, including their Development status and the places where tools disagree.

Key terms

Trace
The record of one end-to-end operation, such as one user request to an agent. It is a set of spans that share one trace ID.
Span
One timed unit of work inside a trace, such as a model call or a tool call. It has a name, start and end times, a parent span, attributes and a status.
Attribute
A key-value pair attached to a span or metric, for example the model name or the number of output tokens.
Generation
Langfuse's name for an observation that records a call to a model, including prompt, token usage and cost. OpenTelemetry calls the same thing an inference or chat span.
Semantic conventions
Agreed names and meanings for attributes, so telemetry from different libraries can be read the same way. The OpenTelemetry GenAI conventions use names that start with gen_ai.
Conversation (session)
A group of traces that belong to one multi-turn chat. Tools call it a session, a thread, a group or a conversation.
Instrumentation
The code that creates spans and metrics, either automatically inside a library or written by hand around your own functions.
Collector
An OpenTelemetry service that receives telemetry, can filter, redact and route it, and forwards it to one or more backends.
Redaction
Removing or masking sensitive values from telemetry before it is stored or sent on.
Cached tokens
Input tokens that a provider served from a prompt cache. They are usually priced differently from other input tokens, so cost calculations have to count them separately.

2Explanation

Introduction

In LLM APIs and Streaming you sent a request to a model and read back the answer, the token counts and the finish reason. For a single call that is all the bookkeeping you need: print the response and its usage and you can see what happened. An application that makes several model calls per request, lets the model choose tools, and serves thousands of users does not fit in a print statement. A user reports a wrong refund date. You need to know which model call produced it, what the tool returned just before, how many tokens that step used and whether a retry was involved, without asking the user to repeat the conversation.

Think of the difference between a card statement and an itemised receipt. The statement gives the total. The receipt lists each purchase with its time, place and amount. Observability for LLM applications is the receipt: a recorded list of every step of a run, with timing, tokens and outcome for each step, tied together so one run can be read from start to finish.

The vocabulary comes from distributed tracing, which engineers developed for requests that cross many services. A trace is the record of one end-to-end operation. It is made of spans. A span is one timed unit of work, with a name, a start and end time, a parent span and key-value attributes. Spans nest, so a trace is a tree. OpenTelemetry defines traces and spans (opens in a new tab) in this way, and its GenAI semantic conventions (opens in a new tab) say which names and attributes a model call, a tool call or an agent run should carry. Other tools use their own words for the same ideas. Langfuse, for example, calls a model-call span a generation.

The diagram shows the trace you will build by hand in the worked example: one agent run with two model calls and a tool call between them. This lesson covers what such a trace contains, the OpenTelemetry names for its parts, how tokens, cost and latency are recorded, and the decision that matters most in production: which content to capture, which to redact, and where the redaction must run.

How it works

Traces, spans and nesting

A span records a name, start and end timestamps, a status, a parent span, attributes, and a span context made of a trace ID and a span ID (OpenTelemetry: Traces (opens in a new tab)). A child's parent ID equals its parent's span ID, and a span without a parent is the root. All spans of one operation share a trace ID, so a backend can rebuild the tree. When work crosses a process boundary, for example an agent calling a tool server, context propagation carries the trace ID across so that the remote spans join the same trace.

Each span has a kind: Client for a synchronous outgoing call, Internal for work inside one process, and Server, Producer and Consumer for incoming and queued work. In the GenAI conventions a model call is normally a Client span, and tool, agent and workflow spans are normally Internal.

The GenAI span types

Semantic conventions are agreed names, so that a dashboard written for one library also works on another. In the GenAI conventions (opens in a new tab) the attribute gen_ai.operation.name says what kind of span it is. The conventions now live in their own repository, and the old opentelemetry.io address (opens in a new tab) shows only a notice that they moved.

The same page also defines operations for embeddings, retrieval and memory stores. The agent spans page (opens in a new tab) distinguishes an agent running in your process (Internal span) from a hosted agent you call over a network (Client span).

What a model-call span records

The inference span (opens in a new tab) assigns each attribute a requirement level:

LevelAttributes
Requiredgen_ai.operation.name, gen_ai.provider.name
Conditionally requiredgen_ai.request.model; error.type when the call failed; gen_ai.conversation.id when you really have one; gen_ai.prompt.name and gen_ai.prompt.version when a named prompt template is used
Recommendedgen_ai.request.temperature, gen_ai.request.max_tokens, gen_ai.response.model, gen_ai.response.id, gen_ai.response.finish_reasons, gen_ai.usage.input_tokens, gen_ai.usage.output_tokens
Opt-ingen_ai.input.messages, gen_ai.output.messages, gen_ai.system_instructions, gen_ai.tool.definitions

Record both models: the request attribute is the exact name you asked for, the response attribute is the exact model that answered, and they can differ. The finish reasons form an array, and an error entry marks a generation that ended abnormally. The prompt name and version let you tie a bad answer to a prompt version (see Prompt Management and Versioning). A tool span requires gen_ai.tool.name, recommends gen_ai.tool.call.id, and makes gen_ai.tool.call.arguments and gen_ai.tool.call.result opt-in because they may hold sensitive data.

Tokens and cost

A provider returns token counts. Cost is something you derive by multiplying counts by prices. The conventions say that gen_ai.usage.input_tokens should include cached tokens, with gen_ai.usage.cache_read.input_tokens and gen_ai.usage.cache_write.input_tokens as subsets of it, and reasoning tokens as a subset of the output count (inference span (opens in a new tab)). With III input tokens, RRR cache-read tokens, WWW cache-write tokens, OOO output tokens and prices ppp per million tokens:

Other tools choose differently. Langfuse (opens in a new tab) stores exclusive buckets, where input excludes cached tokens, and it subtracts cache counts from OpenTelemetry gen_ai.usage.* input when it ingests them. The Claude Code input token type also excludes cache tokens. Which formula is right depends on where the number came from, and the wrong choice counts cached tokens twice. Cost is also an estimate: a price table changes over time, and the Claude Code documentation tells readers to use the provider's billing data for official figures.

Latency

A span's duration is its end time minus its start time. In a sequential agent run the root span lasts as long as its children plus self time, which is waiting, framework overhead and anything not wrapped in a child span. Parallel children can add up to more than the root. For streamed answers also record the time to the first chunk (gen_ai.response.time_to_first_chunk), because users notice it first.

For aggregates the conventions define histograms: gen_ai.client.inference.duration in seconds, with suggested bucket boundaries from 0.01 s doubling up to 81.92 s, and, in the metrics page (opens in a new tab), gen_ai.execute_tool.duration and, per agent invocation, gen_ai.invoke_agent.duration, gen_ai.invoke_agent.inference_calls and gen_ai.invoke_agent.tool_calls. Histograms let a backend report p95 and p99, which expose the slow tail that an average hides. The token metrics (opens in a new tab) split the same way: the usage counters track spend over time, while the per-operation token histograms are for percentiles, not for totals or cost. A span covers the logical operation, including automatic retries.

Which signal answers which question

  • Traces answer why this one run behaved as it did.
  • Metrics answer how much, how fast and how often, over time and across runs.
  • Events or log records carry content when you choose to record it.

Different tools, different words

Once you know the OpenTelemetry names you can read the others. Langfuse (opens in a new tab) says it is built on OpenTelemetry, the Vercel AI SDK (opens in a new tab)'s OpenTelemetry integration emits gen_ai.* attributes, and the OpenAI Agents SDK has its own trace and span classes that you export through trace processors. LangSmith's concepts page (opens in a new tab) adds the thread for grouping the traces of a multi-turn chat.

What to capture and what to redact

Prompts, system instructions, model outputs, tool arguments and tool results are the data that makes a trace most useful and the data most likely to be personal, confidential or simply large. The conventions mark these attributes as likely to contain sensitive information, tell instrumentations not to capture them by default, and describe three patterns:

  1. Default: do not record instructions, inputs or outputs.
  2. Record on spans: use the content attributes. This suits pre-production, or cases where volume is manageable and storage complies with privacy rules.
  3. Store externally, keep references on spans: the recommended production pattern when volume or sensitivity is a concern, because external storage can have its own access controls.

The default still leaves model, tokens, durations, tool names, finish reasons, error types and the shape of the tree. That is enough for most debugging, and sizes and counts can stand in for text.

Redaction can run at several points. The OpenTelemetry guidance (opens in a new tab) says the best protection is not to collect data that might be sensitive. After that, the SDK can mask values before export (Langfuse's mask hooks (opens in a new tab) and the OpenAI Agents SDK's trace_include_sensitive_data setting do this). A Collector can then remove, hash or filter attributes, but it sees data after it has left the application, so it must sit inside your trust boundary. Three rules help:

  • Fail closed. The OpenAI Agents SDK tracing docs (opens in a new tab) warn that processors are independent observers, so a redaction processor placed before an exporter does not stop that exporter receiving data if redaction fails. Redact and deliver in the same step, and drop the batch if redaction fails.
  • Prefer allowlists. The Collector's redaction processor deletes attributes that are not on an allowed list, so new attributes from a library upgrade are removed instead of leaked.
  • Hash with care. OpenTelemetry notes that hashes of small input spaces, such as numeric user IDs, can be reversed in practice.

Linking runs into conversations

A multi-turn chat is several traces. Tools group them with gen_ai.conversation.id, a trace group_id, a Langfuse session or a LangSmith thread. The conventions say to set the conversation ID only when you have a real one, and not to invent a fallback such as a fresh UUID or the trace ID.

Worked example: Tracing a two-call support agent run, with cost and redaction

This script uses only the Python standard library. It records the run drawn in the first diagram with a fake clock, so every run prints the same numbers. The prices are assumed teaching values (3.00, 0.30 and 15.00 USD per million input, cache-read and output tokens), not any provider's price list. Save it as mini_trace.py and run python3 mini_trace.py.

python
import re
from contextlib import contextmanager

PRICE_IN, PRICE_CACHE, PRICE_OUT = 3.00, 0.30, 15.00  # assumed USD per million tokens
EMAIL = re.compile(r"[\w.+-]+@[\w-]+\.[\w.]+")


class Recorder:
    def __init__(self, capture=False, redact=lambda text: text):
        self.t, self.spans, self.stack, self.n = 0, [], [], 0  # t is a fake clock in ms
        self.capture, self.redact = capture, redact

    @contextmanager
    def span(self, name, **attrs):
        self.n += 1
        sid, parent, start = f"s{self.n}", (self.stack[-1] if self.stack else None), self.t
        self.stack.append(sid)
        late = {}  # attributes that are only known when the span ends
        try:
            yield late
        finally:
            self.stack.pop()
            self.spans.append({"id": sid, "parent": parent, "name": name, "start": start,
                               "end": self.t, "attrs": {**attrs, **late}})

    def content(self, key, value):  # opt-in content, redacted before it is stored
        return {key: self.redact(value)} if self.capture else {}


def run_agent(rec):
    chat = {"gen_ai.operation.name": "chat", "gen_ai.provider.name": "demo",
            "gen_ai.request.model": "demo-model"}
    tool = {"gen_ai.operation.name": "execute_tool", "gen_ai.tool.name": "get_order"}
    result = '{"status": "shipped", "contact": "maria.lopez@example.com"}'
    with rec.span("invoke_agent support_agent", **{"gen_ai.operation.name": "invoke_agent"}):
        rec.t += 10
        with rec.span("chat demo-model", **chat) as late:
            rec.t += 1800
            late.update({"gen_ai.usage.input_tokens": 1200, "gen_ai.usage.output_tokens": 85})
        rec.t += 5
        with rec.span("execute_tool get_order", **tool, **rec.content("gen_ai.tool.call.result", result)):
            rec.t += 350
        rec.t += 5
        with rec.span("chat demo-model", **chat) as late:
            rec.t += 2400
            late.update({"gen_ai.usage.input_tokens": 1540, "gen_ai.usage.output_tokens": 120,
                         "gen_ai.usage.cache_read.input_tokens": 1200})
        rec.t += 10


def cost(a, input_includes_cache=True):
    cached = a.get("gen_ai.usage.cache_read.input_tokens", 0)
    fresh = a["gen_ai.usage.input_tokens"] - (cached if input_includes_cache else 0)
    return (fresh * PRICE_IN + cached * PRICE_CACHE + a["gen_ai.usage.output_tokens"] * PRICE_OUT) / 1e6


def report(rec):
    by_id = {s["id"]: s for s in rec.spans}
    depth = lambda s: 0 if s["parent"] is None else 1 + depth(by_id[s["parent"]])
    for s in sorted(rec.spans, key=lambda s: s["start"]):
        print("  " * depth(s) + f'{s["name"]}  {s["end"] - s["start"]} ms')
    chats = [s["attrs"] for s in rec.spans if s["attrs"]["gen_ai.operation.name"] == "chat"]
    print("cost, cache-aware  :", round(sum(cost(a) for a in chats), 6), "USD")
    print("cost, double-counts:", round(sum(cost(a, False) for a in chats), 6), "USD")
    root = next(s for s in rec.spans if s["parent"] is None)
    kids = sum(s["end"] - s["start"] for s in rec.spans if s["parent"] == root["id"])
    print("root self time     :", root["end"] - root["start"] - kids, "ms")


for label, rec in (("capture off", Recorder()), ("capture on, raw", Recorder(True)),
                   ("capture on, redacted", Recorder(True, lambda t: EMAIL.sub("[email]", t)))):
    run_agent(rec)
    if label == "capture off":
        report(rec)
    tool_span = next(s for s in rec.spans if s["name"].startswith("execute_tool"))
    print(f"{label:21}", tool_span["attrs"].get("gen_ai.tool.call.result", "(not recorded)"))

Output:

text

  chat demo-model  1800 ms
  execute_tool get_order  350 ms
  chat demo-model  2400 ms

Latency. The root lasts 4580 ms. The two model calls take 1800 + 2400 = 4200 ms (91.7%), the tool takes 350 ms (7.6%) and 30 ms (0.7%) is self time. The second model call is the largest single item.

Tokens. Input tokens are 1,200 + 1,540 = 2,740, of which 1,200 were cache reads on the second call. Output tokens are 85 + 120 = 205.

Cost, per call. The unit helps: at 3.00 USD per million tokens, one input token costs 3 millionths of a dollar, so the arithmetic below is in millionths of a dollar.

CallFresh inputCache readOutputTotal
11,200 × 3.00 = 3,600085 × 15.00 = 1,2754,875
2(1,540 − 1,200) × 3.00 = 1,0201,200 × 0.30 = 360120 × 15.00 = 1,8003,180

The run costs 8,055 millionths of a dollar, which is 0.008055 USD. If you treat the 1,540 as excluding the cache, price all of it at the full input price and still add the 1,200 cache reads on top, call 2 becomes 6,780 (4,620 + 360 + 1,800) and the run 11,655, which is 44.7% too high. The longer the conversation and the better the cache hit rate, the larger this error grows.

Content. With capture off, which is the default pattern, the tool span carries only its name and operation. Turning capture on without redaction stores the customer's email address in the trace. Redacting before the span is stored keeps the useful structure (the status) and removes the address. The redaction happens inside the recorder, before the span reaches any exporter, which is the fail-closed shape described earlier. A real pipeline would use an allowlist rather than one regular expression, which only catches email addresses.

Edge cases and limitations

The conventions are still in Development
Every GenAI page in the OpenTelemetry repository is marked Development, so span definitions and attribute names can change. The conventions also moved to their own repository, and the old addresses under opentelemetry.io now show only a moved notice. Check which version your instrumentation library implements (Datadog's announcement names v1.37 and later), pin it, and expect older tutorials to use names that differ from the current text. The Claude Code Monitoring page gives one concrete case: older versions of the conventions named the cache-write attribute gen_ai.usage.cache_creation.input_tokens, the current text calls it gen_ai.usage.cache_write.input_tokens, and you have to use the name your backend expects.
Retries hide inside one span
The conventions say a span should cover the logical operation, including automatic retries after a transient failure. A model call that lasted nine seconds may be three attempts, and the span alone will not say so. If you need per-attempt timing, add a child span or an event for each attempt in your own retry code.
A failed call can report zero tokens
When a generation fails, is cancelled or a stream ends early, the conventions report a finish reason of error, and the token counters record 0 if the response never arrived or carried no usage. Zero therefore means that no usage was reported, not that the call was free. When you reconcile traces against the provider's bill, expect failed calls to be missing from the totals and treat the gap as unknown.
Token counts follow different conventions
OpenTelemetry defines input tokens as including cached tokens. Langfuse stores exclusive buckets, and the Claude Code token counter's input type excludes cache tokens. Copying a number from one tool to another without checking its definition double counts or undercounts. Langfuse also warns that an extra key in an OpenAI-style usage object makes it store the object as flat keys, with no subtraction of cached tokens.
Content-capture defaults differ between tools
OpenTelemetry tells instrumentations not to capture prompts and outputs by default, and Claude Code redacts prompt text unless you opt in. The OpenAI Agents SDK sets trace_include_sensitive_data to true by default, and the Vercel AI SDK records inputs and outputs by default. Never assume that a tool is private: read its default and set the option explicitly in code or configuration.
Hidden reasoning tokens and estimated cost
Reasoning models spend tokens you never see. The conventions count reasoning tokens inside the output total, and Langfuse says it cannot tokenize hidden reasoning, so cost cannot be inferred for those models unless the provider's counts are ingested. Cost figures from observability tools are estimates; the Claude Code documentation calls its own approximations and points to the provider for official billing.

When to use it, and when something simpler is enough

Use it when

  • The application makes more than one model or tool call per request, or lets the model choose its next step, so the path of a request cannot be read from the code.
  • Real users send inputs you did not test, and you need to explain a bad answer, a slow response or a surprising bill from recorded data instead of reproducing it.
  • More than one team needs the same view of cost, latency and errors per model, agent or feature.
  • You must be able to say what data leaves your systems, because a defined capture and redaction policy is easier to audit than ad hoc logging.

Think twice when

  • The prototype makes a single model call per request and you already log its request and response; a tracing pipeline would add upkeep for little extra insight.
  • You would store raw prompts and tool outputs by default in a system with broad access while the data carries legal or contractual limits; design the redaction and storage first, or capture metadata only.
  • You only need total spend per month, which the provider's own usage reporting may already cover.

A simpler alternative. Structured logs with a request ID, model name, token counts, latency and finish reason from each API response go a long way for an app with one or two model calls per request, together with the provider's usage dashboard for spend. Move to traces when you need to see a nested sequence of calls inside one request, or when the same "what happened in that run?" question comes up every week.

Key takeaways

  • A trace is a tree of timed spans for one run, and the spans that matter for LLM work are the model call, the tool call and the agent or workflow invocation, each carrying model, token, finish-reason and error attributes.
  • OpenTelemetry's GenAI conventions give these spans shared names such as chat, execute_tool and invoke_agent, but they have Development status, so pin the version you use and expect other tools to use different words for the same ideas.
  • Cost is derived from recorded token usage and a price table, so you must know whether a tool's input count includes cached tokens, or the cost will be wrong by a large factor; treat it as an estimate and check it against the provider's bill.
  • Prompts, outputs, tool arguments and tool results are sensitive and large, so capture them off by default, opt in per environment, and prefer references to a separately controlled store in production.
  • Redaction should fail closed and run before data leaves your trust boundary, preferably with allowlists, because a redactor that fails open or runs as a separate step can still let data through.
  • Start with structure, meaning counts, durations, names and outcomes, because that answers most debugging questions without reading anyone's conversation.

Example 1 of 5

OpenAI Agents SDK, built-in traces for agent runs, handoffs and tools

OpenAIDocumented in official docs

The OpenAI Agents SDK for Python turns tracing on by default. The Tracing page of its documentation describes the trace and span model, which spans the runner creates automatically, the sensitive-data setting and how to send traces to other backends. [10]

The problem

A workflow made of several agents, tool calls, guardrails and handoffs is hard to debug from its final answer alone. The SDK documentation describes tracing as a record of LLM generations, tool calls, handoffs, guardrails and custom events that you can use to debug, visualise and monitor workflows in development and production. The same spans can hold sensitive model inputs and tool results, so the design also has to let a team keep that content out.

Where this topic fits

Tracing lives inside the runner, which is the agent loop. Every call to the runner is wrapped in a trace, and the runner opens agent, generation, function, guardrail and handoff spans as the loop proceeds. Your code adds only what the SDK cannot know, such as a workflow name or a group ID. Exporters sit after the spans: the default one sends them to OpenAI's backend, and you can add or replace processors.

How it is applied, step by step

  1. The runner opens a trace for the whole run. The default workflow name is "Agent workflow" unless you set one.
  2. Each time an agent runs it gets an agent span, and each model call gets a generation span that holds the model input and output.
  3. Each function tool the model calls gets a function span with the call's input and output. Handoffs and guardrails get their own span types.
  4. To make several runner calls part of one trace, wrap them in a with-trace block. To link the traces of one chat, pass a group ID, which the page documents as a trace property.
  5. A batch processor exports spans in the background. In short-lived workers, flush_traces() forces delivery at the end of a unit of work.
  6. For sensitive deployments, set trace_include_sensitive_data to false so model spans omit request input and response output.
  7. To send traces elsewhere, add a processor next to the default exporter, or replace the default processors.

Why this approach fits

An agent loop makes control flow depend on data, so the runner is the only component that knows when a handoff, a guardrail or a tool call happened. Tracing inside the runner means the span tree matches the real execution without each developer writing instrumentation. The processor interface lets a team keep the backend it already uses.

Limitation or tradeoff

Tracing is on by default, and by default the spans include model and function inputs and outputs, so a team that changes nothing sends conversation content to the trace backend. Tracing is unavailable for organizations under a Zero Data Retention policy. Redaction needs care too: processors are independent observers, so a redactor registered before an exporter does not protect you if it fails.

What the sources document

  • Tracing is enabled by default. It can be disabled globally with the OPENAI_AGENTS_DISABLE_TRACING environment variable or set_tracing_disabled(True), or for one run through the run configuration. The page says tracing is unavailable for organizations under a Zero Data Retention policy. [10]
  • By default the SDK wraps each runner call in a trace and creates spans for agents, LLM generations, function tool calls, guardrails and handoffs, plus a task span for each runner invocation and a turn span for each model turn, which can be switched off for a more compact hierarchy. A trace has a workflow name and an optional group ID for linking the traces of one conversation. [10]
  • generation_span stores the inputs and outputs of the LLM generation and function_span stores those of function calls. RunConfig.trace_include_sensitive_data controls whether they are captured, and it defaults to true. [10]
  • add_trace_processor adds a processor in addition to the default OpenAI exporter, while set_trace_processors replaces the defaults. The page lists many third-party tracing integrations and says their maintainers support them. [10]
  • The page warns that a redaction processor registered before an exporter does not stop the exporter from receiving data if redaction fails. It recommends keeping redaction and delivery in one application-owned exporter that discards the batch when redaction fails. [10]

Langfuse, turning token usage into cost per generation with model price definitions

LangfuseDocumented in official docs

Langfuse is an LLM observability platform. Its documentation on token and cost tracking describes how generation observations carry usage and cost, how prices are looked up from model definitions, and how cached and reasoning tokens must be stored. [16][15][14]

The problem

Providers report token usage in different shapes, and some counts include cached tokens while others do not. Models have different prices per token type, and the same trace can arrive through an SDK, an integration or OpenTelemetry. The platform must turn all of that into one cost figure per generation without counting cached tokens twice.

Where this topic fits

Cost accounting is a step applied to generation and embedding observations at ingestion time. Usage details, and optionally cost details, come in. A model definition is matched against the model name, and the resulting cost is stored with the observation next to the trace-level attributes such as user and session.

How it is applied, step by step

  1. An SDK, integration or OpenTelemetry exporter sends a generation observation with the model name and usage_details, for example input, output and cache_read_input_tokens.
  2. Inclusive provider counts are converted to exclusive buckets. For an OpenAI-style response with 17,903 prompt tokens, of which 17,817 were cache hits, and 188 completion tokens, the stored values are input 86, input_cached_tokens 17,817 and output 188.
  3. If you also send cost_details, they are stored as ingested. Otherwise Langfuse matches the model string against model definitions, using a regular expression, and multiplies each usage type by its price.
  4. If no usage was sent and the model has a tokenizer configured, Langfuse can count the tokens itself. Ingested values always take priority over inferred ones.
  5. Where a model has pricing tiers, the first tier whose conditions match supplies the prices, for example a large-context tier that applies when input exceeds 200,000 tokens.
  6. A price change affects only generations logged afterwards.

Why this approach fits

Cost depends on the type of token, so "total tokens times one price" is wrong whenever caching or reasoning is involved. Exclusive buckets turn cost into a plain sum, and attaching cost to a generation shows which step of a trace spent the money.

Limitation or tradeoff

Inferred cost is only as good as the model definitions and tokenizers. The documentation says the Claude tokenizer is not accurate for Claude 3 models, that hidden reasoning tokens cannot be counted without ingested usage, and that a gateway adding an extra key to an OpenAI-style usage object makes Langfuse store flat keys without subtracting cached tokens. Overlapping buckets overstate cost.

What the sources document

  • Langfuse's generation observation type logs generations of AI models including prompts, token usage and costs. Each generation or embedding records usage_details and cost_details, and a usage type must match exactly the corresponding key in the model definition's prices. [16][15]
  • Usage and cost can be ingested or inferred, and ingested values take priority. Inferred cost is calculated from the model definition's per-unit prices, found by matching a regular expression against the model name. Price changes apply only to generations logged afterwards. [16]
  • Every key in usage_details is a separate, non-overlapping bucket, so input excludes input_* keys. Inclusive provider counts must be converted first. The page's example turns 17,903 prompt tokens, of which 17,817 were cached, into input 86 and input_cached_tokens 17,817. [16]
  • For OpenTelemetry gen_ai.usage.* attributes Langfuse subtracts cache reads and writes from input. Flat usage_details are stored unchanged, so their values must already be exclusive. Hidden reasoning tokens cannot be tokenized, so their cost cannot be inferred without ingested counts. [16]
  • Langfuse organises data into observations, traces and sessions. Trace-level attributes such as user_id and session_id are propagated to every observation, and the page says Langfuse is built on OpenTelemetry. [14]

4Common mistakes

  1. Logging only the final prompt and answer instead of one span per step

    Why it causes problems
    When an agent's answer is wrong you cannot tell whether retrieval, a tool call or the last model call failed, and you cannot attribute tokens or time to any step. Debugging becomes guessing and re-running.
    How to recognise it
    A run in your backend appears as one record, or its model calls and tool calls show up as unrelated traces. The question "which step was slow?" has no answer.
    How to fix it
    Create a root span for the request and a child span for every model call and tool call. Wrap multi-call workflows in one trace so they share a trace ID, as the OpenAI Agents SDK does when you put a trace block around several runner calls.

  2. Capturing full prompts, tool results and outputs in production by default

    Why it causes problems
    Prompts and tool results contain customers' personal and business data. In a trace store that data sits under different access rules, retention and regulation than your application database, and it makes the store large and costly.
    How to recognise it
    Search the trace backend for an email address, phone number or customer name from a test conversation. If it appears, content is being stored.
    How to fix it
    Default to metadata only and make content capture an explicit opt-in per environment. Redact before export. In production, store large or sensitive content in a separate store with its own access controls and keep only a reference on the span.

  3. Pricing total input tokens in full and adding the cached tokens on top

    Why it causes problems
    Under the OpenTelemetry convention the cached tokens are already inside the input count, so this charges them twice. In the worked example it inflates the run's cost by 44.7%, and the error grows with the cache hit rate and the length of the conversation.
    How to recognise it
    Your computed cost is higher than the provider's usage report for runs with many cache hits, and the gap widens as cache hits grow.
    How to fix it
    Read each tool's definition of its token counts. With the OpenTelemetry convention, subtract cache reads and writes from the input count and price each part separately, then compare a sample with the provider's usage report.

  4. Registering a redaction processor beside the exporter and assuming the data is clean

    Why it causes problems
    Processors are independent observers. If redaction throws, or another exporter takes the data first, unredacted content still reaches a backend, and nobody notices because the pipeline looks healthy.
    How to recognise it
    In a test, make the redactor raise an error and check whether the raw payload still arrives at the exporter. Read the order in which processors and exporters are registered.
    How to fix it
    Make redaction and delivery one step: copy the payload, redact the copy, send only the result, discard the batch on failure and log a fixed message without the payload. Prefer allowlists to deny-lists.

  5. Putting free text or unbounded values into metric attributes

    Why it causes problems
    Each distinct attribute value can create a separate time series, so prompt text, user IDs or full error messages multiply series, slow dashboards and raise the bill. They can also leak data into a store that is widely readable.
    How to recognise it
    A metric has thousands of distinct label values, or a dashboard times out after one attribute is added.
    How to fix it
    Keep metric attributes to a small, bounded set such as operation, provider, model, token type and error class. The conventions ask for error.type to be a low-cardinality identifier. Put detail on spans or events instead, where it can be sampled and access-controlled.

python
PRICE_IN, PRICE_CACHE, PRICE_OUT = 3.00, 0.30, 15.00
ALLOWED = {"gen_ai.operation.name", "gen_ai.tool.name", "gen_ai.usage.input_tokens",
           "gen_ai.usage.output_tokens", "gen_ai.usage.cache_read.input_tokens", "error.type"}


def duration(span):
    return span["end"] - span["start"]


def chat_cost(attrs):
    cached = attrs.get("gen_ai.usage.cache_read.input_tokens", 0)
    fresh = attrs["gen_ai.usage.input_tokens"] - cached
    return (fresh * PRICE_IN + cached * PRICE_CACHE + attrs["gen_ai.usage.output_tokens"] * PRICE_OUT) / 1e6


def allowlisted(span):
    """Return a new span that keeps only allowed attribute keys; the input is not changed."""
    return {**span, "attrs": {k: v for k, v in span["attrs"].items() if k in ALLOWED}}


def analyse(spans):
    chats = [s for s in spans if s["attrs"]["gen_ai.operation.name"] == "chat"]
    root = next(s for s in spans if s["parent"] is None)
    kids = [s for s in spans if s["parent"] == root["id"]]
    slowest = max(kids, key=duration)
    failed = [s for s in spans if "error.type" in s["attrs"]]
    return {
        "input_tokens": sum(s["attrs"]["gen_ai.usage.input_tokens"] for s in chats),
        "output_tokens": sum(s["attrs"]["gen_ai.usage.output_tokens"] for s in chats),
        "cache_read_tokens": sum(s["attrs"].get("gen_ai.usage.cache_read.input_tokens", 0) for s in chats),
        "cost_usd": round(sum(chat_cost(s["attrs"]) for s in chats), 6),
        "slowest_child": (slowest["name"], duration(slowest)),
        "root_self_ms": duration(root) - sum(duration(s) for s in kids),
        "errors": [(s["name"], s["attrs"]["error.type"], duration(s)) for s in failed],
        "failed_share_of_root": round(sum(duration(s) for s in failed) / duration(root), 3),
    }


for key, value in analyse(SPANS).items():
    print(f"{key}: {value}")
leaky = {"id": "x", "parent": None, "name": "chat demo-model", "start": 0, "end": 10,
         "attrs": {"gen_ai.operation.name": "chat", "gen_ai.input.messages": "secret",
                   "customer.email": "a@b.example"}}
print(allowlisted(leaky)["attrs"], "| original untouched:", sorted(leaky["attrs"]))

8NeverKeep this text off spans. It belongs in prompt management; record the prompt name and version, as in field 9, so a bad answer can be tied to a version.
9Alwaysgen_ai.prompt.name and gen_ai.prompt.version are small identifiers and make regressions traceable.
10Capture after redactionNever store the raw ID: in a searchable backend it lets any engineer link a trace to a person. If you need per-user grouping, issue an opaque, rotating pseudonym in your application. A plain hash of a numeric ID can be reversed, so it does not count as anonymisation.
11Always, if the application has oneRecord it only when the application really has a conversation ID. Do not invent one from a UUID or the trace ID.
12Always for the type; message after redactionerror.type is a low-cardinality class and safe. Free-text messages can echo inputs, so redact or omit them.

Where redaction runs: the first line of defence is not to collect, which means content capture stays off in production and the application never puts fields 5 to 7 on spans. The second is an allowlist in the Collector, such as the redaction processor with a list of allowed keys, which runs inside your network. You rely mainly on the first, and use the second as protection against mistakes such as a library upgrade that adds a new attribute.

If redaction fails, the batch is dropped and a fixed message that contains no payload is logged. The application never falls back to exporting unredacted spans. Redaction and delivery are one step, as the OpenAI Agents SDK documentation recommends.

Test: create a fake employee with an obvious email address and a distinctive plan name, ask the assistant three questions about them in a staging environment with production settings, and search the trace backend for the email, the name and the plan. Any hit is a leak. Repeat with a deliberately failing redactor and confirm that no spans from that batch arrive.

Check your answer

  • Did you give all 12 fields a decision, and is each reason a rule rather than a feeling?
  • Does your policy keep working if a library upgrade adds a new attribute that holds user text?
  • Did you avoid treating a plain hash of the employee ID as anonymous?
  • Could a colleague run your test and tell from the result whether the policy leaks?
