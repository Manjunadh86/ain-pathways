Cloud Platform Fundamentals (AWS, Azure, GCP)

A public cloud platform rents you computing, storage, networking and identity services through an API and bills you for what you use. AWS, Microsoft Azure and Google Cloud offer the same four building blocks under different names, and all three divide security work between provider and customer under a shared responsibility model.

1Overview

Why it matters

Most AI systems you will deploy end up on someone's cloud: a model endpoint, a vector store, a queue, a bucket of source documents. Whether they work depends on four questions that have nothing to do with AI. Can the code reach the data? Is the traffic allowed to flow, and does it stay off the public internet? Which identity makes each call, and what is that identity allowed to do? Who patches and monitors each layer?

Without these basics the usual failures follow. A service times out because it sits in a private subnet with no route to the model API. An agent is given an administrator role "to make it work" and can later read data it was never meant to see. A customer's security team rejects a design because prompts travel over the public internet. A forward deployed engineer who can read a customer's network and access diagram, and who asks for the right role and the right private endpoint, avoids most of these before the first request is sent.

  • Choose between a virtual machine, a container service and a function by what each leaves you to patch and operate.

  • Evaluate a simple access policy by hand using default deny, explicit deny and least privilege.
  • State, for a given service type, which security tasks belong to the provider and which to the customer.

Key terms

Region
A geographic location where a provider clusters data centers. You choose one for most resources, usually for latency, cost or legal reasons.
Availability zone
A separate location inside a region, built to fail independently of the others, so a service spread over two zones survives the loss of one.
Virtual network (VPC or VNet)
A private, software-defined network inside the cloud whose address range and routes you control. AWS and Google Cloud call it a VPC, Azure calls it a virtual network.
Subnet
A slice of a virtual network's address range. Routes and firewall rules are usually applied per subnet.
CIDR block
An address range written as a starting address and a prefix length, for example 10.20.0.0/16, which holds 65,536 addresses.
Private endpoint
A private IP address inside your network that leads to a managed service, so traffic needs no internet path. AWS PrivateLink, Azure Private Link and Google Private Service Connect provide it.
Role
In AWS, an identity that a workload or person assumes to receive temporary credentials. In Azure and Google Cloud, a named set of permissions that you grant to an identity.
Least privilege
Granting only the actions on only the resources that a task needs, and nothing broader.
Shared responsibility model
The division of security duties between provider and customer. The provider secures the underlying infrastructure, and the customer secures their data, identities and configuration on top of it.
Object storage
Storage for whole files, called objects, found by bucket name and key over an HTTP API rather than mounted as a disk. Examples are Amazon S3, Azure Blob Storage and Google Cloud Storage.

2Explanation

Introduction

In Networking Essentials you met IP addresses, DNS, TLS, proxies and firewalls on networks you could picture: a laptop, a router, a server in a rack. A public cloud offers the same ideas as an API. Instead of buying a server you ask for one, and instead of cabling a network you declare an address range and some routes. The provider owns the buildings, the hardware and the virtualisation layer. You own your account and everything you configure inside it.

Amazon Web Services (AWS), Microsoft Azure and Google Cloud differ in names, defaults and pricing, but each is built from four building blocks:

  • Compute runs your code, as virtual machines, containers or functions.
  • Storage keeps your data, as object storage for files, block storage for disks and file storage for shared folders.
  • Networking connects everything with virtual networks, subnets, routes, firewalls and private connections.
  • Identity decides who may do what, through users, roles and the policies attached to them.

One idea cuts across all four: shared responsibility. The provider secures the cloud itself, and you secure what you build in it. Where the line falls depends on the kind of service you pick, and the incidents that make the news tend to happen on the customer's side of it.

Google publishes a page that maps its services to AWS and Azure equivalents (opens in a new tab), and the grid above is drawn from it. The page calls the entries similar or comparable offerings, not identical ones, so use the table to find the right product page and then read what that product actually does.

This lesson takes the four building blocks in turn, then the shared responsibility model. A worked example plans a small network and tests an access policy by hand, and five documented cases show each idea in a real product or incident. Later lessons build on this one: Infrastructure as Code writes these resources as files, and Deploying in Customer Environments applies them inside a customer's own account.

How it works

Accounts, regions and zones

Every cloud resource lives inside a container that carries billing and permissions: an AWS account, an Azure subscription or a Google Cloud project. Containers can be grouped. Azure role assignments can be made at four scopes (management group, subscription, resource group and resource), and Google Cloud arranges organization, folders and projects in a hierarchy where a policy set on a container also applies to everything inside it. The container tells you whose bill a resource lands on and which permissions can reach it.

Most resources also live in one region. AWS's S3 documentation notes that you might choose a region to optimise latency, minimise cost or meet regulatory requirements, and that objects stored in a region never leave it unless you explicitly copy or replicate them. Inside a region, providers offer separate zones so that a service spread over two of them survives the loss of one.

Compute: choose how much you operate

Compute services form a ladder. Each rung takes work off you and takes some control away.

RungExamples (AWS, Azure, Google Cloud)You still manage
Virtual machineEC2, Azure Virtual Machines, Compute EngineGuest operating system, patches, runtime, application
Managed KubernetesEKS, AKS, GKEWorkloads and images; node management depends on the mode
Serverless containerFargate, Container Apps, Cloud RunThe container image and its settings
FunctionLambda, Azure Functions, Cloud Run functionsThe function code and its settings

The rung decides who patches what. AWS says that for EC2 the customer manages the guest operating system, including updates and security patches. Choose a higher rung when you can live with its limits, because every layer you do not operate is a layer you cannot forget to patch.

Storage: three shapes

  • Object storage (S3, Blob Storage, Cloud Storage) holds whole files called objects in containers called buckets. An object is found by bucket plus key, such as photos/puppy.jpg, through an HTTP API. S3 describes itself as a basic map from bucket, key and version to an object, so there is nothing to mount and you replace an object rather than edit part of it. Use it for documents, datasets, model files and backups.
  • Block storage (EBS, Managed Disks, Hyperdisk) is a virtual disk attached to a virtual machine, which formats it and treats it like a local drive.
  • File storage (EFS, Azure Files, Filestore) is a shared file system that several machines mount at the same time.

S3 buckets and the objects in them are private until you grant access, and Block Public Access settings are on by default at the bucket level. Public data is a deliberate choice, not a default.

Networking: a private network you design

A virtual network is a private address space that you divide into subnets and connect with routes. Resources get private addresses from their subnet. Only resources that you give a public address and a route to an internet gateway can be reached from outside, which is what people mean by a public subnet. A private subnet has no such route. Its resources reach the internet, if at all, through a NAT gateway placed in a public subnet. The three clouds draw the boundaries differently:

Firewalls are separate objects that you attach: security groups and network ACLs on AWS, network security groups on Azure, and VPC firewall rules on Google Cloud. Defaults differ. Google's VPC documentation states that its implied rules allow egress and deny ingress, and Azure's documentation states that resources in a virtual network can reach the internet outbound by default. A private subnet is therefore not an isolated one unless you also restrict outbound traffic.

Managed services such as object stores and model APIs normally sit outside your network, behind public addresses. A private endpoint brings a path to them inside it. AWS describes a VPC endpoint as a way to connect to AWS services privately without an internet gateway or NAT device, and Azure describes Private Link as private access to a specific instance of a service. In AWS's Bedrock documentation, the provider creates a network interface in each subnet you enable, and with private DNS switched on the service's normal hostname resolves to it. Without private DNS your code must name the endpoint URL itself.

Identity: who is calling, and what may they do

Every API call is checked twice. Authentication establishes who is calling. Authorization decides whether that identity may perform the action on the resource. The clouds model authorization differently:

  • AWS IAM attaches JSON policies to identities, and some resources carry their own. By default every request is implicitly denied, an explicit allow is needed to permit it, and an explicit deny overrides any allow.
  • Azure RBAC works through role assignments. A role assignment joins a security principal, a role definition (a set of permitted actions) and a scope. Assignments are additive, so effective permissions are the sum.
  • Google Cloud IAM answers "who can do what on which resource". An allow policy on a resource lists role bindings, and a policy set on an organization, folder or project is inherited by the resources below it.

People sign in. Workloads need identities too, and the safe pattern is to attach one to the workload (an AWS role, an Azure managed identity, a Google Cloud service account) so that it receives short-lived credentials automatically. Code running outside the cloud, such as a CI pipeline, can swap a token from its own identity provider for short-lived cloud credentials through workload identity federation. Example 5 shows this. Apply least privilege throughout: start with no access and add specific actions on specific resources.

The shared responsibility model

All three providers publish the same basic split. AWS calls it security of the cloud (hardware, software, networking and facilities, which AWS protects) versus security in the cloud (which the customer handles, with the amount depending on the service). Microsoft's guidance says that in every deployment type you keep responsibility for your data, your endpoints, your accounts and your access management. Google lists customer responsibility for access policies and data protection, and offers blueprints and landing zones under what it calls shared fate.

The grid follows Microsoft's matrix. Treat labels with care: Microsoft classes Azure Storage as platform as a service, while Google's page lists Cloud Storage under infrastructure as a service. Read the responsibility statement for the specific service rather than trusting the category name.

Worked example: Plan a two-tier network for a document-search service and test its access policy

The scenario: a document-search service for a customer will run in AWS. It needs a small public subnet for a load balancer and a larger private subnet for the application containers in each of two availability zones, a and b. Its indexing worker reads source documents from one bucket and writes embeddings to another, and it must not be able to read the HR folder. The script below, which needs only the Python standard library (3.9 or later), does two jobs. First it checks that every subnet sits inside the VPC range and that no two overlap, and it counts the usable addresses using AWS's rule of five reserved addresses per subnet. Then it evaluates five requests against one access policy using three rules that AWS documents: requests are implicitly denied by default, an explicit allow is needed to permit one, and an explicit deny overrides any allow.

Save it as cloud_plan.py.

python
import ipaddress
import re

# ---------- Part 1: subnet plan for a VPC (AWS reserves 5 addresses per subnet) ----------
RESERVED_PER_SUBNET = 5  # first four addresses and the last one
VPC = ipaddress.ip_network("10.20.0.0/16")
PLAN = {
    "public-a": "10.20.0.0/26",
    "public-b": "10.20.0.64/26",
    "private-a": "10.20.16.0/24",
    "private-b": "10.20.17.0/24",
}


def check_plan(vpc, plan):
    """Return the subnets as network objects, or raise if one is outside the VPC or overlaps another."""
    networks = {name: ipaddress.ip_network(cidr) for name, cidr in plan.items()}
    for name, net in networks.items():
        if not net.subnet_of(vpc):
            raise ValueError(f"{name} {net} is outside {vpc}")
    names = list(networks)
    for i, first in enumerate(names):
        for second in names[i + 1:]:
            if networks[first].overlaps(networks[second]):
                raise ValueError(f"{first} overlaps {second}")
    return networks


networks = check_plan(VPC, PLAN)
used = 0
for name, net in networks.items():
    usable = net.num_addresses - RESERVED_PER_SUBNET
    first_usable = net.network_address + 4
    last_usable = net.broadcast_address - 1
    used += net.num_addresses
    print(f"{name:10} {str(net):15} total {net.num_addresses:4}  usable {usable:4}  {first_usable} - {last_usable}")
print(f"VPC {VPC} has {VPC.num_addresses} addresses; the plan uses {used} ({used / VPC.num_addresses:.2%}).")


# ---------- Part 2: a tiny model of "implicit deny, explicit deny wins" ----------
def matches(pattern, value):
    """AWS-style wildcard: * matches any run of characters, ? matches one character."""
    regex = "^" + re.escape(pattern).replace(r"\*", ".*").replace(r"\?", ".") + "$"
    return re.match(regex, value) is not None


def matches_any(patterns, value):
    patterns = [patterns] if isinstance(patterns, str) else patterns
    return any(matches(pattern, value) for pattern in patterns)


def decide(policy, action, resource):
    allowed = False
    for statement in policy["Statement"]:
        if not (matches_any(statement["Action"], action) and matches_any(statement["Resource"], resource)):
            continue
        if statement["Effect"] == "Deny":
            return "explicit deny"      # one matching Deny ends the evaluation
        allowed = True
    return "allow" if allowed else "implicit deny"


POLICY = {
    "Version": "2012-10-17",
    "Statement": [
        {"Effect": "Allow", "Action": "s3:GetObject", "Resource": "arn:aws:s3:::acme-docs/*"},
        {"Effect": "Allow", "Action": "s3:PutObject", "Resource": "arn:aws:s3:::acme-index/embeddings/*"},
        {"Effect": "Deny", "Action": "s3:*", "Resource": "arn:aws:s3:::acme-docs/hr/*"},
    ],
}
REQUESTS = [
    ("s3:GetObject", "arn:aws:s3:::acme-docs/policies/travel.pdf"),
    ("s3:GetObject", "arn:aws:s3:::acme-docs/hr/salaries.csv"),
    ("s3:PutObject", "arn:aws:s3:::acme-index/embeddings/2026-10.parquet"),
    ("s3:PutObject", "arn:aws:s3:::acme-docs/policies/travel.pdf"),
    ("iam:CreateUser", "arn:aws:iam::123456789012:user/backdoor"),
]
for action, resource in REQUESTS:
    print(f"{decide(POLICY, action, resource):14} {action:14} {resource}")

What to notice:

  • Capacity. A /26 has 64 addresses and 59 are usable, because AWS reserves the first four addresses and the last one in every subnet. In 10.20.16.0/24, 10.20.16.0 is the network address, .1 is the VPC router, .2 is the DNS server, .3 is held for future use and .255 is the broadcast address, which a VPC does not support. The first usable address is therefore 10.20.16.4, the last is 10.20.16.254, and the count is 251.
  • Headroom. The four subnets use 64 + 64 + 256 + 256 = 640 of the 65,536 addresses in the /16, which is 0.98%. Real plans leave room for more subnets and for ranges that must not overlap with the customer's other networks.
  • Why the public subnets are small. They hold only a load balancer and a NAT gateway, so a /26 is plenty. The chart shows what a very small subnet costs: on a /28 the five reserved addresses are almost a third of the space.
  • Default deny. Request 4 asks to write to acme-docs. No statement allows that action on that bucket, so the result is an implicit deny with no Deny statement involved. Request 5 is denied for the same reason, because the policy never mentions IAM.
  • Explicit deny wins. Request 2 matches the first Allow (every object in acme-docs) and also the Deny on the hr/ prefix. The deny decides the outcome, which is how you carve an exception out of a broad grant.
  • Limits of the model. The decide function covers one identity-based policy in one account. Real AWS evaluation also weighs resource-based policies, organization policies, permissions boundaries and session policies, and it supports conditions. Check a real policy with your provider's policy simulator before you rely on it.

Edge cases and limitations

The same word has a different scope on each cloud
An AWS subnet lives in one availability zone, so a design that spans two zones needs two subnets. An Azure virtual network and its subnets span all zones of a region, and a Google Cloud VPC network is global with regional subnets. Copying an AWS diagram into Azure produces redundant subnets, and copying a Google layout into AWS leaves you in one zone. Check the scope of each object before you translate a diagram.
A role is not the same object on every cloud
In AWS a role is an identity that a workload assumes to receive temporary credentials. In Azure and Google Cloud a role is a named set of permissions that you assign to an identity at some scope. "Give it the Contributor role" and "attach a role to the instance" describe different actions. Ask three questions: which identity, which permissions, and at what scope.
Private DNS decides whether a private endpoint is used
AWS documents that with private DNS enabled on a Bedrock interface endpoint, calls to the usual regional hostname go through the endpoint with no code change, while without it your code must name the endpoint URL. A common failure is an endpoint that exists but is never used, because the hostname still resolves to a public address. From a subnet with no internet route the call then simply times out. Resolve the hostname from inside the subnet and confirm that it returns a private address.
Private does not mean closed to the internet
Outbound traffic is open by default on Google Cloud and Azure, as the networking section notes, and on any cloud a NAT gateway gives a private subnet a path to every internet address. A compromised workload can therefore send data out even though nothing can reach in. For sensitive data, restrict egress with firewall rules, route service traffic through private endpoints, and attach endpoint policies that name the allowed actions.
Identity changes take time to take effect
AWS documents IAM as eventually consistent. A change to a user, role or policy must replicate before it is visible everywhere, and AWS advises against putting IAM changes in critical, high-availability code paths. A script that creates a role and uses it a second later can fail intermittently. Separate setup from use and verify that the change has propagated before production traffic depends on it.
The three-column split does not cover what an agent may do
Microsoft's shared responsibility page links to separate models for generative AI workloads and for autonomous, tool-using AI agents. The infrastructure, platform and software split in this lesson says who patches the host, but not which tools an agent may call or what data a prompt may reveal. Those decisions are yours in every column. See [Agent Identity, Permissions and Least Privilege](/topics/agent-identity-and-permissions/).

When to use it, and when something simpler is enough

Use it when

  • Demand is uncertain or spiky, or you need hardware such as GPU instances that would take months to buy and install, and you can pay for what you use.
  • The customer already runs in a cloud account and the system must live inside their network and identity boundary, so your deployment uses their VPC, their roles and their private endpoints.
  • You want the provider to carry the patching and hardware for a layer, because your team cannot staff that work. Pick the highest rung on the compute ladder that still meets your control needs.

Think twice when

  • Data may not leave a facility, country or air-gapped network that the provider does not serve. A private data center or a sovereign cloud region is the better fit.
  • The workload is steady, always on and heavy enough that owning the hardware may cost less. Compare the full cost of both options before you commit to the cloud.
  • A single prototype needs a public demo for a week. Provisioning networks, roles and endpoints takes longer than the demo needs.

A simpler alternative. For prototypes and demos, a platform that hides the cloud, such as the hosted app services covered in [Hugging Face Spaces](/topics/hugging-face-spaces/) and [Rapid Prototyping and Demos](/topics/rapid-prototyping-and-demos/), is usually enough. It stops being enough when a customer requires private networking, their own identity system, a named region or audit evidence of who can reach what.

Key takeaways

  • Every cloud is built from compute, storage, networking and identity, and the shapes match across AWS, Azure and Google Cloud even when the product names differ, so learn the shape once and look up the name.
  • The more managed a compute service is, from virtual machine to container to function, the fewer layers you patch and operate and the less control you have over them.
  • A virtual network is a private address range divided into subnets and joined by routes. A private endpoint lets a workload reach a managed service without an internet path, but only if DNS and firewalls point traffic at it.
  • Identity decides every API call. Requests are denied by default, an explicit deny beats any allow, and workloads should use short-lived credentials from a role or federated identity rather than stored keys.
  • Under shared responsibility the provider secures the infrastructure, while your data, identities and configuration are yours at every service level.
  • Scopes and defaults differ between providers, for example zonal against regional subnets and reserved address counts, so confirm them in each provider's documentation before copying a design.

Example 1 of 5

Capital One and the OCC - customer-side cloud controls after a 2019 incident

Capital OneDocumented in a case study

The US Office of the Comptroller of the Currency (OCC) issued Consent Order 2020-036, signed on 5 August 2020, and a press release dated 6 August 2020 about Capital One's move of IT operations to a public cloud. Capital One's own page about its 2019 cyber incident gives the bank's account of the cause and the dates. None of the three documents names the cloud provider. [24][25][26]

The problem

A bank moved significant IT operations to a public cloud environment around 2015. In 2019 an unauthorised party reached customer data, and Capital One attributes the incident to a configuration vulnerability. The regulator's question was not whether the provider's data centers were physically secure. It was whether the bank had assessed the risks of the move and then designed and operated its own controls in the new environment.

Where this topic fits

This is the customer side of the shared responsibility model. A provider secures the infrastructure, but network security controls, data loss prevention and alert handling inside a customer's cloud environment are designed and run by the customer. The OCC's findings list exactly those controls and do not allege a failure of the provider's facilities. Because the sources do not name the provider, we apply the general model that AWS, Microsoft and Google each publish rather than any one provider's wording.

How it is applied, step by step

  1. Around 2015 the bank migrated significant IT operations to a cloud operating environment. The OCC finds that it had not first established effective risk assessment processes.
  2. Inside that environment, the OCC finds, the bank also lacked appropriate risk management, including appropriate design and implementation of certain network security controls, adequate data loss prevention controls and effective dispositioning of alerts.
  3. Capital One says that unauthorised access occurred on March 22 and 23, 2019. It says an external security researcher reported the configuration vulnerability through its Responsible Disclosure Program on July 17, 2019, and that it immediately fixed the issue and began working with federal law enforcement.
  4. The OCC finds that the bank's internal audit failed to identify numerous control weaknesses and gaps in the cloud environment and did not effectively report them to the Audit Committee.
  5. On August 6, 2020 the OCC announced an 80 million US dollar civil money penalty, set out in a consent order in which the bank neither admitted nor denied the findings.

Why this approach fits

Shared responsibility explains why "we run on a reputable cloud" is not a control. The provider secures the hardware and the facility. The customer decides which ports are open, which roles can reach which data and which alerts a person actually reads. The consent order shows a regulator examining that customer side. For a forward deployed engineer it is a preview of the questions a customer's security review will ask.

Limitation or tradeoff

These documents are not a technical post-mortem. They do not describe how the intrusion worked, name the provider or the affected system, or divide fault between the bank and anyone else, and the bank neither admitted nor denied the OCC's findings. The order also applies US banking rules to a regulated bank, and other sectors and countries phrase their duties differently.

What the sources document

  • The consent order finds that in or around 2015 the bank failed to establish effective risk assessment processes before migrating its IT operations to the cloud operating environment, and failed to establish appropriate risk management for that environment, including appropriate design and implementation of certain network security controls, adequate data loss prevention controls and effective dispositioning of alerts. [24]
  • The order also finds that internal audit failed to identify numerous control weaknesses and gaps in the cloud environment and did not effectively report them to the Audit Committee, and that the Board failed to take effective action to hold management accountable for certain concerns. [24]
  • The order requires an 80 million US dollar civil money penalty, which the bank agreed to without admitting or denying the findings. The OCC's press release announcing the penalty is dated August 6, 2020. [24][25]
  • Capital One's own page says the configuration vulnerability was reported by an external security researcher through its Responsible Disclosure Program on July 17, 2019, that the access occurred on March 22 and 23, 2019, and that it immediately fixed the issue. The page does not name a cloud provider. [26]

The facts above come from the cited sources. The steps and analysis in this example are our explanation of how they fit together.

Example 2 of 5

Hugging Face Inference Endpoints - managed model serving on a cloud and hardware you choose

Hugging FaceDocumented in official docs

Hugging Face's Inference Endpoints documentation (the about, pricing and private-link pages) describes a managed service that runs a model on infrastructure in AWS, GCP or Azure. Together the pages show which compute decisions the service takes over and which stay with the customer. [21][22][23]

The problem

Serving an open model needs GPU machines, matching drivers, a container that runs an inference engine, scaling rules and a secure network path. A team without a dedicated infrastructure group struggles to assemble and operate that stack. The documentation presents Inference Endpoints as a way to skip that work while the customer still chooses where and on what hardware the model runs.

Where this topic fits

Compute is the layer being rented. The model runs in a container on cloud machines of the chosen type, and the service starts, stops and scales it. That places it between running your own virtual machine, where you patch and scale, and calling a hosted model API, where you choose nothing about the hardware. The customer still decides the provider, the hardware family and whether the endpoint is reachable only privately.

How it is applied, step by step

  1. The customer picks a model from the Hugging Face Hub and an inference engine such as vLLM, TGI, SGLang, llama.cpp or Text Embeddings Inference.
  2. The customer chooses a cloud provider and a hardware type from the options the pricing page lists for that provider: CPU, GPU or an accelerator.
  3. The service packages the engine as a prebuilt Docker container together with the model weights downloaded from the Hub, then launches it on the chosen infrastructure.
  4. As traffic rises and falls the service scales the container, including scaling to zero when it is idle, and monitors it for health and performance.
  5. For private access on AWS, the customer ticks the PrivateLink option, which makes the endpoint available only through an intra-region AWS PrivateLink connection, then creates a VPC interface endpoint in their own account using the service name that the service shows.
  6. Applications call the endpoint URL. The customer is billed by the minute while the endpoint runs.

Why this approach fits

GPU machines are expensive to leave idle, and inference traffic is often bursty. Packaging the engine as a container that the service scales, with billing by the minute and scale-to-zero, matches cost to use without the customer operating a cluster. Choosing the provider lets the endpoint sit in the same cloud as the customer's other systems or satisfy a customer's requirement about where workloads run.

Limitation or tradeoff

You are limited to the hardware the service offers on each provider. Example 3 of 5

Common Crawl - a public web archive stored in Amazon S3

Common Crawl FoundationDocumented in official docs

Common Crawl's Get Started page and the Registry of Open Data on AWS entry describe how the Common Crawl web archive is stored and read. Amazon's S3 documentation describes the bucket and key model that the archive's paths rely on. [19][20][14]

The problem

A web archive has to be stored durably, located by path and read by many unrelated people and jobs, some of them inside the cloud and some on a laptop or cluster elsewhere. The data is a growing series of crawl files (WARC, WAT and WET formats), so the storage cannot depend on a shared server or a database that the publisher has to run.

Where this topic fits

Object storage is the whole storage layer. The data sits in one bucket, commoncrawl, in the us-east-1 region, and each file is an object whose key looks like a path. The publisher offers two routes to the same paths: the S3 interface for jobs running in that region, and an HTTP(S) address for everyone else.

How it is applied, step by step

  1. The Common Crawl Foundation stores each crawl as objects in the `commoncrawl` bucket in the US East (N. Virginia) region, under keys shaped like `crawl-data/CC-MAIN-[year]-[week]/segments/[timestamp]/[type]/`.
  2. Files come in three types: WARC (raw crawl data), WAT (computed metadata as JSON) and WET (extracted plain text). A reader fetches only the representation that the job needs.
  3. A job running inside AWS reads objects through the S3 interface, with `s3://commoncrawl/...` URIs (or `s3a://` on Hadoop). The page says this must happen from us-east-1, and it notes that S3 API access from the Amazon cloud is only allowed for authenticated users.
  4. A reader outside AWS requests the same paths over HTTP(S) under `https://data.commoncrawl.org/`, using any HTTP download agent such as `wget`. The page says that route needs no AWS account.
  5. Because each object is found by bucket plus key, a processing job can fetch many segments in parallel, and a typical design places that job in us-east-1, next to the data.

Why this approach fits

Object storage suits an archive of large files that are written once and read by many: there are no servers to run, any HTTP client can fetch a path, and the region choice lets analysis jobs run next to the data. Offering an HTTP(S) address as well means readers outside AWS need no cloud account, which is how an open dataset reaches the widest audience.

Limitation or tradeoff

Documentation can disagree with itself. The Get Started page shows a --no-sign-request command for anonymous access while also saying that S3 API access from the cloud is only for authenticated users, and the registry entry labels the bucket as account-required. Test the route you plan to use. Placement also matters: reading from compute outside us-east-1, or from outside AWS, means moving the bytes across the network yourself, which is slower and may carry transfer charges. Objects are fetched whole by key, and there is no directory tree to mount.

What the sources document

  • Common Crawl says its data is hosted through Amazon Web Services' Open Data Sets Sponsorships program in the bucket s3://commoncrawl/, in the US-East-1 (Northern Virginia) region, under paths of the form crawl-data/CC-MAIN-[YEAR]-[WEEK]/segments/[TIMESTAMP]/[TYPE]/ with WARC, WAT and WET file types. [19]
  • For access from the AWS cloud, the page says the data must be accessed from the region where it is located (us-east-1) and that S3 API access from the Amazon cloud is only allowed for authenticated users. Its AWS CLI example uses --no-sign-request, which the page says allows anonymous access without an AWS account. [19]
  • For access from outside the AWS cloud, the page says any HTTP download agent can fetch the data under the URL prefix https://data.commoncrawl.org/, and that there is no need to create an AWS account for that method. [19]
  • The AWS Registry of Open Data entry lists the resource as an S3 bucket labelled "Account Required", with the ARN arn:aws:s3:::commoncrawl in the us-east-1 region and the CLI access example aws s3 ls s3://commoncrawl/. [20]
  • Amazon S3 buckets and the objects in them are private unless access is explicitly granted. An object is identified within a bucket by its key, and objects stored in a Region never leave it unless you transfer or replicate them. [14]

Example 4 of 5

Amazon Bedrock over AWS PrivateLink - calling a model API with no internet path

Amazon Web ServicesDocumented in official docs

The Amazon Bedrock User Guide page on interface VPC endpoints documents how workloads inside a VPC call Bedrock APIs privately. The Amazon VPC guide describes the VPC endpoint feature that it builds on. [15][5]

The problem

A security team wants an application's prompts and model responses to travel only over the provider's private network, and wants the application's subnets to have no internet gateway, no NAT device and no public IP addresses. The model API normally sits behind a public regional hostname, so by default the call leaves the VPC through the internet path.

Where this topic fits

The private endpoint sits between the application's private subnet and the managed service. It is a network interface with a private address in your own subnet. Before it comes the network design: subnets, route tables and security groups. After it comes identity, because IAM still decides which principal may call which model.

How it is applied, step by step

  1. Place the application in private subnets that have no route to an internet gateway and no public IP addresses.
  2. Create an interface endpoint for the service, for example `com.amazonaws.<region>.bedrock-runtime` for the runtime API. AWS creates an endpoint network interface in each subnet that you enable.
  3. A typical setup attaches a security group to the endpoint that allows HTTPS from the application's own security group and nothing else.
  4. Enable the private DNS name option so that the standard regional hostname resolves to the endpoint from inside the VPC. Without it the code must pass the endpoint URL explicitly.
  5. Optionally attach an endpoint policy that lists the principals, actions and resources allowed through the endpoint. The default policy allows full access to the service.
  6. The application calls the Bedrock Runtime API through its SDK as usual. IAM still evaluates every call against the application's role.

Why this approach fits

The private endpoint moves the network boundary. Traffic to the service never needs the public internet, so the subnets can stay closed to outbound internet access, and the endpoint policy adds a second control at the network edge that limits what the VPC may ask of the service, independently of the roles inside it. That is the shape a customer's network security review usually asks for.

Limitation or tradeoff

Private connectivity is not authorization. The default endpoint policy allows full access to Bedrock through the endpoint, so IAM roles and endpoint policies still have to be right. Each API has its own endpoint service (control plane, runtime, agents and agent runtime among them), so one endpoint does not cover everything, and endpoints are regional. The DNS setting is the usual failure: an endpoint without private DNS is silently bypassed. It is also another component to create, secure and monitor in every VPC and Region you use.

What the sources document

  • AWS PrivateLink creates a private connection between your VPC and Amazon Bedrock. You can reach Bedrock without an internet gateway, NAT device, VPN connection or Direct Connect connection, and instances in the VPC do not need public IP addresses. [15]
  • An interface endpoint places an endpoint network interface in each subnet that you enable. Service names take the form com.amazonaws.{region}.bedrock-runtime, with separate names for the control plane (bedrock), agents (bedrock-agent) and agent runtime (bedrock-agent-runtime). [15]
  • With private DNS enabled, calls from inside the VPC to the default regional DNS name route through the endpoint with no code changes. Without private DNS you must specify the VPC endpoint URL in your API calls. [15]
  • An endpoint policy is an IAM resource attached to the interface endpoint. The default policy allows full access to Amazon Bedrock through the endpoint, and a custom policy specifies the principals, actions and resources allowed. [15]
  • The Amazon VPC guide separately describes a VPC endpoint as the way to connect to AWS services privately, without the use of an internet gateway or NAT device. [5]

Example 5 of 5

GitHub Actions deploying to AWS with OpenID Connect instead of stored keys

GitHub and Amazon Web ServicesDocumented in official docs

GitHub documents the integration from its side (the OpenID Connect concept page and the guide to configuring it for AWS). AWS documents OIDC federation in the IAM User Guide and names GitHub Actions as its example. [16][17][18]

The problem

A CI pipeline has to call AWS APIs to deploy, but an AWS access key stored in the pipeline's secrets is long-lived. It can leak, someone has to rotate it by hand, and it usually carries more access than any single job needs.

Where this topic fits

This is the identity layer at the boundary between a CI provider and the cloud. The workflow proves who it is with a signed token, and the cloud turns that proof into temporary credentials for one narrowly scoped role. Networking and compute are not involved at all, which is the point.

How it is applied, step by step

  1. An AWS administrator registers GitHub's OIDC provider as an IAM identity provider, with provider URL `https://token.actions.githubusercontent.com` and audience `sts.amazonaws.com`.
  2. They create an IAM role whose trust policy accepts tokens from that provider and constrains the audience and subject claims, so that only a named repository and branch or environment can assume it. The role's permission policy lists only what the deployment needs.
  3. The workflow requests `id-token: write` permission, plus `contents: read` for checkout. GitHub notes that `id-token: write` does not give the workflow permission to write to any resources.
  4. At run time GitHub's OIDC provider generates a unique token for the job. The `aws-actions/configure-aws-credentials` action presents it to AWS.
  5. AWS validates the token against the trust policy and returns short-lived credentials for the role, valid only while the job runs.
  6. Later steps call AWS with those credentials. There is no stored secret to leak or to rotate.

Why this approach fits

The pattern replaces a secret with an identity. Nothing is stored, so nothing can leak or need rotating, the credentials expire when the job ends, and the subject condition ties the role to one repository and branch, which gives each pipeline its own least-privilege role. The same idea works on the other clouds: GitHub's page lists AWS, Azure, GCP and HashiCorp Vault, and the service-comparison grid earlier names a workload identity federation feature on all three.

Limitation or tradeoff

All of the security sits in the trust policy. A role that checked only the audience would give any workflow that can obtain a token for that audience a chance to assume it, which is why the guide says to evaluate the subject. The subject format also changes: GitHub warns that for repositories created after July 15, 2026, or those that opt in to immutable subject claims, the subject includes immutable owner and repository IDs, so conditions copied from older examples may stop matching. The pattern covers CI jobs, not human sign-in.

What the sources document

  • GitHub's guide says OIDC lets workflows access AWS resources without storing AWS credentials as long-lived GitHub secrets. Setup uses provider URL token.actions.githubusercontent.com and audience sts.amazonaws.com. [16]
  • The guide says AWS IAM recommends evaluating the token.actions.githubusercontent.com:sub condition key in the trust policy of any role that trusts GitHub's OIDC provider, and its example conditions on both aud and sub. It warns that for repositories created after July 15, 2026, or that have opted in to immutable subject claims, the sub claim includes immutable owner and repository IDs. [16]
  • A workflow needs id-token: write permission to request the token and contents: read for checkout. The guide states that setting id-token: write does not give the workflow permission to modify or write to any resources, and it uses the aws-actions/configure-aws-credentials action to exchange the token. [16]
  • GitHub's concept page describes four steps: trust is established between the cloud provider and GitHub, the OIDC provider generates a unique token for each job, the workflow presents it to the cloud provider, and the provider issues a short-lived access token valid only during the job. It lists claims including sub, aud, iss, repository, ref and environment, and says OIDC works with AWS, Azure, GCP and HashiCorp Vault. [17]
  • The AWS IAM guide strongly recommends not storing AWS credentials long-term in applications outside AWS and instead requesting temporary credentials through OIDC federation, which map to a role with only the permissions the application needs. It names GitHub Actions as an example. [18]

4Common mistakes

  1. Giving a workload an administrator or wildcard role to get past a permission error.

    Why it causes problems
    Any bug, leaked token or prompt injection in that workload now holds every permission the role has. Agents make this worse because they choose their actions at run time. A broad role also hides which permissions the workload really needs, so nobody ever removes the extras.
    How to recognise it
    Policies with Action "*" on Resource "*", Owner or Contributor assigned at subscription scope, or a basic role such as Editor on a project, attached to an application identity.
    How to fix it
    Start from no permissions. Read the denied action in the error, add exactly that action on exactly that resource, and repeat. Test a policy in your provider's policy simulator before relying on it.

  2. Storing long-lived access keys in code, configuration files or CI secrets.

    Why it causes problems
    Keys leak through repositories, logs and laptops, stay valid until someone rotates them, and carry the same permissions wherever they are used. AWS's IAM guide strongly recommends against keeping long-term credentials in applications outside AWS.
    How to recognise it
    Access key IDs or JSON key files in repository history, or cloud secrets in CI settings that have not changed in months.
    How to fix it
    Attach an identity to the workload (an AWS role, an Azure managed identity or a Google Cloud service account) and federate CI through OIDC as in example 5. Then delete the old keys.

  3. Assuming a private subnet, or a private service, has no internet exposure.

    Why it causes problems
    Outbound traffic is usually allowed by default, so a compromised workload can send data to any address. A managed service may also remain reachable by its public hostname even when your own subnets are private.
    How to recognise it
    A route table with a default route to a NAT gateway, firewall rules that allow all outbound traffic, or a service hostname that resolves to a public address from inside the subnet.
    How to fix it
    Decide outbound access on purpose: deny by default and allow named destinations. Use private endpoints with endpoint policies for managed services, and test from inside the subnet.

  4. Choosing address ranges without checking the customer's other networks.

    Why it causes problems
    Networks with overlapping ranges cannot be routed to each other, so peering, VPN or private connections to the customer's data center or other VPCs fail. Fixing it usually means recreating subnets and the resources in them.
    How to recognise it
    A plan that uses a default range such as 10.0.0.0/16 without anyone having asked the customer's network team which ranges are free.
    How to fix it
    Ask for the customer's allocated ranges first. Record the plan as data, as in the worked example, and check it for overlaps with code before you create anything.

  5. Treating shared responsibility as "the provider handles security".

    Why it causes problems
    Nobody owns configuration, outbound controls, alert handling or access reviews, so these gaps are where incidents start. The OCC consent order in example 1 lists exactly these customer-side controls.
    How to recognise it
    A design document with no named owner for patching virtual machines, network rules, role reviews or alerts, or a sentence like "it is on the cloud, so it is secure".
    How to fix it
    Add a responsibility table to the design, one row per service, starting from the provider's matrix, with a named owner for every customer-side row.

Use these rules from AWS's subnet documentation. Every subnet must lie inside the VPC range. Subnets in one VPC must not overlap. A subnet's prefix length must be between /16 and /28. AWS reserves five addresses in every subnet, the first four and the last one, so a subnet can hold its size minus five.

Requirements

  • Report a subnet that lies outside the VPC range.
  • Report each pair of subnets whose ranges overlap, once per pair.
  • Report a subnet whose prefix length is outside the allowed range.
  • Report a subnet in NEEDED whose usable address count is smaller than the number required, and say both numbers.
  • Print the number of problems, then one line per problem. Then run the script on a corrected plan that reports zero problems.

Expected behaviour

The draft plan has four problems: db-a is outside the VPC, tiny-a has a prefix longer than /28, app-a overlaps app-b, and app-a needs 300 addresses but has only 251 usable. Your wording may differ. After your corrections the script prints 0 problem(s).

Hint 1

`ipaddress.ip_network(...)` gives objects with `.subnet_of()`, `.overlaps()`, `.prefixlen` and `.num_addresses`.

Hint 2

Compare every pair of subnets once. Looping over `names[i + 1:]` for each index `i` avoids reporting a pair twice.

Hint 3

For the corrected plan, work out which prefix gives at least 300 usable addresses. A `/24` holds 251, so you need the next size up.

Show solution

One way to write the script, with the corrected plan appended:

python
import ipaddress

RESERVED = 5            # AWS reserves the first four addresses and the last one
MIN_PREFIX, MAX_PREFIX = 16, 28   # allowed subnet sizes in an AWS VPC

VPC = "10.30.0.0/16"
PLAN = {
    "web-a": "10.30.0.0/25",
    "web-b": "10.30.0.128/25",
    "app-a": "10.30.1.0/24",
    "app-b": "10.30.1.128/25",
    "db-a": "10.31.0.0/24",
    "tiny-a": "10.30.9.0/29",
}
NEEDED = {"web-a": 100, "app-a": 300, "app-b": 100}


def audit(vpc, plan, needed, reserved=RESERVED):
    """Return a list of problems found in a subnet plan."""
    vpc_net = ipaddress.ip_network(vpc)
    nets = {name: ipaddress.ip_network(cidr) for name, cidr in plan.items()}
    findings = []
    for name, net in nets.items():
        if not net.subnet_of(vpc_net):
            findings.append(f"{name} {net} is outside {vpc_net}")
        if not MIN_PREFIX <= net.prefixlen <= MAX_PREFIX:
            findings.append(f"{name} {net} must use a prefix between /{MIN_PREFIX} and /{MAX_PREFIX}")
    names = list(nets)
    for i, first in enumerate(names):
        for second in names[i + 1:]:
            if nets[first].overlaps(nets[second]):
                findings.append(f"{first} {nets[first]} overlaps {second} {nets[second]}")
    for name, count in needed.items():
        usable = nets[name].num_addresses - reserved
        if usable < count:
            findings.append(f"{name} needs {count} addresses but has {usable} usable")
    return findings


def report(label, vpc, plan, needed):
    problems = audit(vpc, plan, needed)
    print(f"{label}: {len(problems)} problem(s)")
    for problem in problems:
        print(f"  - {problem}")


report("Draft plan", VPC, PLAN, NEEDED)

FIXED = {
    "web-a": "10.30.0.0/25",
    "web-b": "10.30.0.128/25",
    "app-a": "10.30.2.0/23",
    "app-b": "10.30.4.0/23",
    "db-a": "10.30.8.0/24",
    "tiny-a": "10.30.9.0/28",
}
report("Fixed plan", VPC, FIXED, NEEDED)

Running it prints:

text
Draft plan: 4 problem(s)
  - db-a 10.31.0.0/24 is outside 10.30.0.0/16
  - tiny-a 10.30.9.0/29 must use a prefix between /16 and /28
  - app-a 10.30.1.0/24 overlaps app-b 10.30.1.128/25
  - app-a needs 300 addresses but has 251 usable
Fixed plan: 0 problem(s)

The fixes: app-a becomes a /23 (512 addresses, 507 usable) at 10.30.2.0, app-b moves to its own /23 at 10.30.4.0 so that it no longer overlaps, db-a moves inside the VPC range, and tiny-a becomes a /28. Each fixed range is a block that does not touch the others, which is why the overlap check passes.
