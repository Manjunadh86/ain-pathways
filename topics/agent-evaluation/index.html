Evaluating Agents

Agent evaluation measures how well an AI agent does a task by grading a recorded run on what the agent finally said, what it actually changed in its environment, and the tool calls, steps and resources it used to get there.

1Overview

Why it matters

An agent can give a perfect final sentence and still have done the wrong thing. It can say a refund was issued when no refund tool was ever called, issue the refund without the identity check your policy requires, or reach the right result after forty tool calls that cost ten times what the task is worth. A score on the final text alone hides all three. Teams that evaluate only the answer find out from customers, from the bill or from an audit.

The opposite mistake is as common. A test that demands one exact sequence of tool calls fails every run in which the agent found a different valid route, so the suite goes red for harmless changes and people stop trusting it. Anyone who ships an agent, changes its prompt, swaps its model or reviews someone else's benchmark number needs to know which layer of a run a metric looks at, what that layer cannot see, and how many trials stand behind the number.

What you will be able to do

  • Distinguish final-response, outcome and trajectory evaluation, and name a failure that each one misses.
  • Compute exact, in-order and any-order match, precision and recall for a predicted tool-call list against a reference.
  • Diagnose a tool-call failure as a wrong tool, wrong arguments, a missing call or a wrong order.
  • Summarise repeated trials with pass rate, pass@k and pass^k, and report cost and step metrics beside them.
  • Design an evaluation for a conversational agent that uses a simulated user and an outcome check.
  • Plan a human review of traces that calibrates automated graders and feeds new test cases.

Key terms

Task
One test case, made of the input given to the agent and the criteria that decide whether an attempt succeeded.
Trial
One attempt at a task. Because agent runs vary, the same task is usually run for several trials.
Trajectory
The ordered list of tool calls, with their arguments, that the agent made during a trial. Some vendors use the word for the complete record of the trial, which this lesson calls the trace or transcript.
Outcome
The state of the environment when the trial ends, such as a database row, a file or a booking. It is what really happened, whatever the agent said.
Grader
The logic that scores one aspect of a trial. It can be code, a judge model with a rubric, or a person.
Reference trajectory
The list of tool calls a test author expects for a task, used as ground truth when matching the agent's calls.
Final-response evaluation
Scoring only the last message the agent returns to the user, in the same way a single model output is scored.
pass^k
The probability that all k independent trials of a task succeed. It measures consistency and falls as k grows, unlike pass@k, which asks for at least one success.
Simulated user
A second language model that plays the customer in a test conversation, following a hidden scenario instead of a fixed script.
Annotation queue
A review workflow that hands selected runs or conversations to human reviewers one at a time, each with a rubric to fill in.

2Explanation

Introduction

In Evaluating LLM Applications every test case had the same shape: one input, one output, one score. An agent breaks that shape. As The Agent Loop showed, an agent makes a series of model calls and tool calls, and some of those calls change things outside the conversation: a database row, a file, a booking. The text it finally returns is only the last line of a longer record.

Think about a driving test. The examiner does not only ask whether you reached the test centre. They watch whether you checked the mirrors and stopped at the red light, they confirm that the car really is inside the parking bay, and nobody passes a candidate who needs three hours for a ten-minute route. A candidate who announces a perfect park while the car sits on the kerb still fails, however confident the announcement.

Agent evaluation asks the same four questions about a recorded run:

  • Final response. Is what the agent told the user correct and complete?
  • Outcome. Is the environment in the state the task required? This is task completion.
  • Trajectory. Did the agent call the right tools, with the right arguments, in an acceptable order?
  • Efficiency. How many steps, tokens, seconds and dollars did the run consume?

The vocabulary in this lesson follows Anthropic's Demystifying evals for AI agents (opens in a new tab). A task is one test with defined inputs and success criteria. A trial is one attempt at it. A grader is the logic that scores some aspect of the attempt. The transcript, also called the trace or trajectory, is the complete record of the trial, and the outcome is the final state of the environment. Google's ADK documentation (opens in a new tab) divides the work into evaluating the trajectory and tool use and evaluating the final response, and there trajectory means the list of steps the agent took before it replied. This lesson uses that narrower meaning for trajectory and says trace or transcript for the whole record.

The sections below take each layer in turn, then show how to combine repeated trials into a reliability number, how to test a conversational agent with a simulated user, and why people still have to read traces after every grader has been automated.

How it works

What a trial leaves behind

A trial produces four things you can grade. They answer different questions and fail in different ways, so a serious evaluation uses more than one.

Graders come in three kinds. Code-based graders (string checks, state checks, test suites, tool-call checks) are fast, cheap and reproducible, but brittle when a valid result does not match the expected pattern. Model-based graders, an LLM with a rubric as in LLM-as-a-Judge, handle open-ended output but are non-deterministic and must be calibrated against people. Human graders are the reference standard and the slowest. Anthropic's advice is to choose deterministic graders where possible, model graders where necessary, and human graders judiciously for validation.

Final-response evaluation

This layer reuses single-call evaluation unchanged. Two of ADK's built-in criteria show the usual options when a reference answer exists: response_match_score is ROUGE-1 word overlap with the reference (default threshold 0.8), and final_response_match_v2 has a judge model decide whether the answer means the same as the reference. Without a reference you write a rubric.

Its blind spot is the reason agent evaluation exists as a separate topic. Anthropic's example is a flight-booking agent that ends with "Your flight has been booked": the outcome is whether a reservation exists in the environment's database.

Task completion: grade the outcome

The most trustworthy pass or fail signal is a check on the end state. τ-bench compares the final database with the one correct database for the task. SWE-bench, as Anthropic describes it, grades a solution by running the test suite, and the Berkeley Function-Calling Leaderboard compares the state of a simulated backend with the expected state. For your own agent the check is usually a short function that queries the system the agent was supposed to change and compares it with the expected values.

Outcome checks need two things: a task whose instructions allow exactly one correct end state, and a clean environment for every trial, so that one run cannot inherit another's files or records.

Trajectory evaluation and tool-call correctness

A trajectory check compares the tool calls the agent made (the predicted trajectory) with the calls you expected (the reference trajectory). Google Cloud's agent evaluation service (opens in a new tab) defines six trajectory metrics (the page is marked Preview), and ADK's tool_trajectory_avg_score offers the first three as the match types EXACT, IN_ORDER and ANY_ORDER:

MetricScores 1 when
Exact matchthe same calls appear in the same order, with nothing extra
In-order matchevery reference call appears, in order; extra calls are allowed
Any-order matchevery reference call appears; order and extra calls are ignored
Single tool useone named tool appears at least once

Precision and recall give partial credit between 0 and 1:

precision=predicted calls found in the referenceall predicted callsrecall=reference calls found in the predictionall reference calls\text{precision} = \frac{\text{predicted calls found in the reference}}{\text{all predicted calls}} \qquad \text{recall} = \frac{\text{reference calls found in the prediction}}{\text{all reference calls}}precision=all predicted callspredicted calls found in the reference​recall=all reference callsreference calls found in the prediction​

A tool call can go wrong in four ways, and a failed match should tell you which one happened: the wrong tool was chosen, the right tool received wrong arguments, a needed call is missing, or the calls came in the wrong order. Under ADK's exact match, a difference in tool name, arguments or order counts as a failure, and so does any extra or missing call.

Strict matching is a regression tool, not a quality measure. Anthropic reports that checking for a specific sequence of tool calls proved too rigid, because agents regularly find valid approaches the eval designer did not anticipate, and recommends grading what the agent produced over the path it took. Use trajectory checks in three situations: the path is itself a requirement (verify identity before a refund), you are guarding a fixed workflow against regressions, or you are diagnosing why an outcome check failed. For looser rules, ADK's rubric_based_tool_use_quality_v1 has a judge model answer yes or no to rubric statements, for example that one named tool is called before another.

Combining graders into a verdict

One task usually carries several graders. Anthropic describes three ways to combine them: binary (every grader must pass), weighted (the combined score must reach a threshold) or a hybrid. A sensible default is to make the outcome check and any policy check mandatory, and to record response quality and efficiency as scores. Keep two suites. Capability evals start with a low pass rate and give you something to improve. Regression evals should stay close to 100% and warn you when a change breaks behaviour that used to work.

Trials, pass@k and pass^k

Agent runs vary, so one trial per task says little. Run each task nnn times and count the successes ccc. Two summaries pull in opposite directions. If each trial succeeds with probability ppp:

pass@k=1−(1−p)kpassk=pk\text{pass@}k = 1 - (1 - p)^k \qquad \text{pass}^k = p^kpass@k=1−(1−p)kpassk=pk

pass@k is the chance that at least one of kkk attempts succeeds, which suits tools where a person picks the best attempt. pass^k is the chance that all kkk succeed, which is what a customer-facing agent needs. With p=0.75p = 0.75p=0.75, pass^3 is 0.753≈0.420.75^3 \approx 0.420.753≈0.42.

From real counts, the τ-bench authors estimate pass^k for one task as (ck)/(nk)\binom{c}{k} / \binom{n}{k}(kc​)/(kn​) and average over tasks.

Cost and step metrics

Every trial should also record what it used. ADK reports four efficiency criteria for every eval with no configuration: tool_call_count_v1, inference_call_count_v1, token_usage_v1 and invocation_duration_v1. They are informational and never fail a case. Their job is comparison across runs: a prompt change that keeps quality flat but doubles token usage shows up here and nowhere else. Read together, model calls and tokens separate the two ways a turn gets expensive, which are more calls or a larger context per call.

Report cost beside accuracy, never in place of it. A useful single figure is:

cost per successful task=total cost of all trialsnumber of successful trials\text{cost per successful task} = \frac{\text{total cost of all trials}}{\text{number of successful trials}}cost per successful task=number of successful trialstotal cost of all trials​

Simulated users

A scripted list of user messages cannot test a conversational agent, because the next user message depends on what the agent just said. If the agent needs two values, it may ask for both at once or one at a time. The fix is a second model that plays the user. In ADK (Python 1.18.0 and later) a ConversationScenario gives the simulator a fixed starting_prompt, a conversation_plan that describes the user's goals, and optionally a user_persona (personas need version 1.26.0 or later). A cap, max_allowed_invocations (20 by default, and the starting prompt counts as one), ends conversations that never finish.

Two consequences follow. Reference-based criteria such as tool_trajectory_avg_score and response_match_score are not supported with user simulation, because no fixed expected turn exists, so you grade the outcome and use rubrics. And the simulator is itself a model that can leave the script, which is why ADK includes per_turn_user_simulator_quality_v1 to check that it followed the plan and persona.

Human review of traces

Automated scores say how often the agent fails. Reading traces says why, and whether the grader was right. Anthropic's team writes that it does not take eval scores at face value until someone has read some transcripts, and that failures should seem fair: it is clear what the agent got wrong.

Make the reading systematic. LangSmith annotation queues (opens in a new tab) group runs and threads for reviewers, show a rubric beside each item, and can be filled automatically by rules that match, for example, runs with errors or low user scores. OpenAI's trace grading (opens in a new tab) attaches structured scores to traces. Reviewed traces then become test cases: an OpenAI Cookbook notebook (opens in a new tab) turns reviewer feedback on traces into evals that can be rerun. OpenAI's agent evaluation guide (opens in a new tab) orders the work the same way: start with traces while you are still debugging behaviour, and move to datasets and repeatable eval runs once you know what good looks like. The traces themselves come from the tracing described in LLM and Agent Observability.

Worked example: Scoring four recorded trials of a refund agent on every layer

The task given to a support agent is "Refund order 1042 to the original payment method." Company policy says identity must be verified before any refund. The test author wrote a reference trajectory of three tool calls and the state the order must end in. Four trials were recorded. So that everyone gets identical numbers, the trials are stored as data and the script only grades them. In a real harness each calls list comes from a trace and each state from a query against the test database.

Save this as score_trials.py. It needs Python 3.8 or later and only the standard library.

python
from math import comb

VERIFY = ("verify_identity", {"user": "u7"})
ORDER = ("get_order", {"order_id": 1042})
POLICY = ("get_refund_policy", {})
REFUND = ("issue_refund", {"order_id": 1042, "amount": 59.0})

REFERENCE = [VERIFY, ORDER, REFUND]                   # expected tool calls, in order
GOAL_STATE = {"status": "refunded", "refunded": 59.0}  # what the order row must look like
UNTOUCHED = {"status": "delivered", "refunded": 0.0}
USD_PER_M_INPUT, USD_PER_M_OUTPUT = 3.00, 15.00        # illustrative prices per million tokens

TRIALS = {
    "A": {"calls": [VERIFY, ORDER, REFUND], "state": GOAL_STATE,
          "answer": "I have refunded 59.00 USD to your card.", "tokens": (4200, 320)},
    "B": {"calls": [VERIFY, ORDER, POLICY, REFUND], "state": GOAL_STATE,
          "answer": "Your refund of 59.00 USD is on its way.", "tokens": (6100, 420)},
    "C": {"calls": [VERIFY, ORDER], "state": UNTOUCHED,
          "answer": "Done. A refund of 59.00 USD has been issued.", "tokens": (2900, 260)},
    "D": {"calls": [ORDER, REFUND], "state": GOAL_STATE,
          "answer": "I refunded 59.00 USD for order 1042.", "tokens": (2800, 240)},
}


def in_order(predicted, reference):
    remaining = iter(predicted)                 # each match consumes the iterator,
    return all(step in remaining for step in reference)  # so order is enforced


def any_order(predicted, reference):
    return all(step in predicted for step in reference)


def precision(predicted, reference):
    return sum(step in reference for step in predicted) / len(predicted)


def recall(predicted, reference):
    return sum(step in predicted for step in reference) / len(reference)


def verified_before_refund(predicted):
    names = [name for name, _ in predicted]
    if "issue_refund" not in names:
        return True
    return "verify_identity" in names[:names.index("issue_refund")]


def cost_usd(tokens):
    return (tokens[0] * USD_PER_M_INPUT + tokens[1] * USD_PER_M_OUTPUT) / 1_000_000


def flag(value):
    return "yes" if value else "NO"


print("trial answer outcome exact in_order any_order precision recall policy calls  cost")
passed = []
for name, trial in TRIALS.items():
    calls = trial["calls"]
    answer_ok = "refund" in trial["answer"].lower() and "59.00" in trial["answer"]
    outcome_ok = trial["state"] == GOAL_STATE
    policy_ok = verified_before_refund(calls)
    passed.append(outcome_ok and policy_ok)
    print(f"{name:<5} {flag(answer_ok):<6} {flag(outcome_ok):<7} {flag(calls == REFERENCE):<5} "
          f"{flag(in_order(calls, REFERENCE)):<8} {flag(any_order(calls, REFERENCE)):<9} "
          f"{precision(calls, REFERENCE):<9.2f} {recall(calls, REFERENCE):<6.2f} "
          f"{flag(policy_ok):<6} {len(calls):<5} {cost_usd(trial['tokens']):.4f}")

n, c, k = len(passed), sum(passed), 2
total = sum(cost_usd(trial["tokens"]) for trial in TRIALS.values())
print(f"pass rate      {c}/{n} = {c / n:.2f}")
print(f"pass^{k}         {comb(c, k) / comb(n, k):.3f}")
print(f"pass@{k}         {1 - comb(n - c, k) / comb(n, k):.3f}")
print(f"mean calls     {sum(len(t['calls']) for t in TRIALS.values()) / n:.2f}")
print(f"cost/success   {total:.4f} / {c} = {total / c:.4f} USD")

What the rows show:

  • Trial C is the reason to check outcomes. Its answer says a refund was issued and passes the final-response check, but issue_refund was never called and the order is untouched. Its precision is 1.00, because both calls it made are in the reference. Precision says nothing about completeness. Recall, 2 of 3 or 0.67, does.
  • Trial D is the reason to check trajectories. The answer is right and the money moved, yet the refund went out with no identity check. Only a trajectory check catches it: the policy rule fails, and so do the exact and in-order matches.
  • Trial B is the reason not to treat exact match as a quality score. One extra read-only call fails exact match and lowers precision to 3/4, while in-order match, the outcome and the policy rule all pass.
  • The verdict combines layers. A trial passes when the outcome is right and the policy rule holds, so A and B pass: 2 of 4.

Edge cases and limitations

A broken task or grader looks exactly like a weak agent
Anthropic reports that Opus 4.5 first scored 42% on CORE-Bench until a researcher found rigid grading that penalised 96.12 when 96.124991 was expected, ambiguous task specifications and tasks that could not be reproduced exactly; after the fixes and a less constrained scaffold the score was 95%. The same article says that with frontier models a 0% pass rate across many trials most often signals a broken task. Before reading a low score as an agent problem, write a reference solution that passes every grader, and read the transcripts of the failures.
The agent finds a valid path the reference never listed
Exact trajectory matching fails a run that added a harmless lookup or reordered two independent calls, as trial B in the worked example shows. Anthropic describes a sharper case in which a model failed a tau2-bench flight task as written because it found a loophole in the policy that gave the user a better result. When several routes are acceptable, use in-order or any-order matching on the few calls that must happen, or grade the outcome and keep the trajectory for diagnosis.
The simulated user changes the difficulty of the task
A simulator that volunteers every detail in its first message makes the task easier than real users would, and one that forgets its goal makes the task impossible. Both move the score without any change to the agent. Write scenarios that leave only one acceptable outcome, cap the number of turns, and score the simulator as well as the agent. ADK has a criterion for this, per_turn_user_simulator_quality_v1, and the tau-bench authors rewrote task instructions repeatedly after reading trajectories until the ambiguity was gone.
Trials that share state are not independent
If one trial leaves files, records or caches behind, the next trial starts from a different world. Anthropic gives an example from its internal evals in which Claude gained an unfair advantage on some tasks by examining the git history left by earlier trials. Leftover state can also cause several trials to fail for the same infrastructure reason, which makes pass^k look worse than the agent is. Start every trial from a fresh copy of the environment.
Dollar and time figures are not stable properties of the agent
Token prices change, and wall-clock time moves with the load on the model server. ADK's documentation warns that a duration is a single measurement and that you should compare distributions across runs, not two individual numbers. Its token count is also reported as not available, never as zero, when a model backend does not return usage data. Store raw token and call counts with every result so that cost can be recomputed later, and compare latency over many trials.

When to use it, and when something simpler is enough

Use it when

  • The agent calls tools that change something, such as records, files, bookings or messages, so the final text cannot prove what happened.
  • You are about to change a prompt, a model, a tool description or a framework version and need to know whether behaviour that worked before still works.
  • The agent holds multi-turn conversations whose course depends on the user, so fixed input and output pairs cannot cover them.
  • You must choose between agent configurations that differ in cost, and need accuracy, reliability over repeated trials and cost per successful task side by side.

Think twice when

  • The system makes one model call with no tools and no side effects. Final-response evaluation from the LLM evaluation lesson already covers it.
  • Nobody can yet say what a successful run looks like. Read twenty real traces and write the success criteria first; an automated score for an undefined goal is noise.
  • The task is open-ended with many valid routes and you only have exact trajectory matching available. It will fail good runs and teach the team to ignore the suite.

A simpler alternative. Score only the final response against a small set of reference answers, as in single-call LLM evaluation, and read the traces of every failure by hand. That is enough for a read-only agent with a handful of tools during early development. It stops being enough as soon as the agent writes to another system, a policy constrains the order of its actions, or you need to compare the cost of two versions.

Key takeaways

  • A trial leaves a final response, an outcome, a trajectory and usage figures, and each one can be right while another is wrong.
  • The outcome, meaning the end state of the environment, is the most trustworthy measure of task completion because it does not depend on what the agent claims.
  • Trajectory metrics compare tool calls with a reference list; exact match suits regression tests, while in-order, any-order, precision and recall tolerate valid variation and help diagnose failures.
  • One trial per task is not a measurement, so run several and report pass^k when users need the agent to succeed every time.
  • Tool calls, model calls, tokens, duration and cost per successful task belong next to every accuracy number.
  • People must still read traces, because that is how broken tasks, unfair graders and behaviours no metric was looking for are found.

Example 1 of 5

Google ADK checking tool trajectories and final responses in a regression suite

Google (Agent Development Kit)Documented in official docs

The Agent Development Kit (ADK) is Google's open-source agent framework. Its evaluation documentation describes built-in criteria that score an agent's tool trajectory and its final response against recorded cases, run from pytest, the adk eval command or the web UI. [3][4]

The problem

The documentation starts from the observation that the probabilistic nature of models makes deterministic pass or fail assertions on output unsuitable for agents. A team still needs a repeatable signal that a change to an instruction, a model or a tool has not altered which tools the agent calls or what it finally says, and the signal has to be cheap enough to run on every change.

Where this topic fits

Evaluation sits between building the agent and deploying it. ADK separates two cases. Test files hold one simple session each and act as unit tests during development. Evalsets hold several, possibly long, multi-turn sessions and act as integration tests that run less often. Both store, for every turn, the user's message, the expected tool calls and the reference final response, so both layers of the run can be checked together.

How it is applied, step by step

  1. A developer talks to the agent in the ADK web UI and saves the session as an eval case with the Add current session button, which captures the user content, the tool calls and the final response.
  2. The case is stored in a test file ending in .test.json or in an evalset. Each turn records user_content, the expected tool_uses under intermediate_data, and the reference final_response.
  3. A test_config.json next to the cases sets the criteria and thresholds. With no configuration the defaults are a tool trajectory score of 1.0 and a response match score of 0.8.
  4. The suite runs from pytest through AgentEvaluator.evaluate or from the adk eval command. ADK runs the agent on each recorded user message and compares what it did with what the case expects.
  5. For each turn the trajectory criterion gives 1.0 when the tool calls match under the chosen match type and 0.0 otherwise, then averages over the turns of the case. A typical setup compares each configured criterion's score with its threshold to label the case Pass or Fail.
  6. Efficiency figures (tool calls, model calls, tokens and duration) are reported for every case without affecting pass or fail, so a cost regression is visible in the same report.
  7. For a failure, the web UI shows actual and expected output side by side, and the Trace tab shows the model requests, responses and tool calls behind it.

Why this approach fits

Both default criteria compare against stored references with no judge model, so they are deterministic given the agent's output, add no model cost and suit a check that runs on every commit. Scoring the trajectory and the response separately also localises a failure: a case that fails only on the trajectory means the agent reached a similar answer by a different route, while a case that fails only on the response means the route held and the wording or content moved. The three match types let a team decide how much variation in the route it will tolerate before the check goes red.

Limitation or tradeoff

Reference-based checks only know the route and wording that were recorded. Exact matching fails a run that adds a harmless lookup, and ROUGE-1 measures shared words, so a response can score well while stating a wrong value or score badly after a correct rephrasing. The references must be re-recorded whenever intended behaviour changes. The documentation also states that these reference-based criteria are not supported together with user simulation, and that several of the judge-based criteria need access to a Google Cloud evaluation service.

What the sources document

  • The ADK documentation divides agent evaluation into two components: evaluating the trajectory and tool use, and evaluating the final response. It describes the trajectory as the list of steps the agent took before it returned to the user, which is compared with the list of expected steps. [3]
  • When no criteria are provided, ADK uses tool_trajectory_avg_score with a default of 1.0, requiring a 100% match in the tool usage trajectory, and response_match_score with a default of 0.8. [3]
  • tool_trajectory_avg_score compares the agent's tool calls with the expected calls using one of three match types, EXACT, IN_ORDER or ANY_ORDER. Each invocation scores 1.0 on a match and 0.0 otherwise, and the final value is the average across the invocations in the eval case. [4]
  • For CI/CD pipelines and regression testing the documentation recommends tool_trajectory_avg_score and response_match_score, describing them as fast, predictable and suitable for frequent automated checks. [3]
  • Four efficiency criteria (tool_call_count_v1, inference_call_count_v1, token_usage_v1 and invocation_duration_v1) are reported for every eval without configuration and never pass or fail an eval case. [4]

Example 2 of 5

τ-bench testing customer-service agents with a simulated user and a database check

SierraDocumented in a paper

τ-bench is a benchmark published in 2024 by researchers at Sierra, whose blog says its research team developed it in June 2024. The paper describes two domains, retail and airline, in which an agent with API tools and a policy document serves a user who is played by a language model. [7][8]

The problem

The authors argue that earlier benchmarks did not test agents on their interaction with human users or on following domain-specific rules, both of which matter for deployment. They also note why this is hard to measure: the trajectory for the same task can be extremely diverse, success has several facets, and judging it has usually needed end users and domain experts.

Where this topic fits

Three ideas from this lesson make up the whole method. A simulated user drives the conversation, so each trial unfolds differently. Task completion is graded on the outcome by comparing the database at the end of the conversation with an annotated goal state. Every task is then run for several trials and summarised with pass^k, which the paper introduces.

How it is applied, step by step

  1. Each task has two hidden parts: an instruction for the simulated user that fixes identity, intent and preferences, and an annotation of the database write actions and required outputs that count as correct.
  2. A language model plays the user. It sees its instruction and the conversation so far, and it cannot see the agent's tool calls.
  3. The agent, given the domain policy and the tools, alternates between messages to the user and tool calls. Some tools only read the database and others write to it, and the retail policy requires explicit user confirmation before a consequential write.
  4. The episode ends when the simulated user sends a stop token. The paper limits each task to at most 30 agent actions, counting both tool calls and replies to the user.
  5. The grader computes a reward of 1 only if the final database is identical to the single correct database and the agent's messages contain every required piece of information.
  6. Tasks are run for several trials, and pass^k is estimated for each task from the number of successful trials and averaged over tasks.
  7. The authors then read failed trajectories by hand and sort them into categories: wrong argument or information, incorrect decision-making, and partial resolution of compound requests.

Why this approach fits

A customer conversation can go a thousand ways, so grading the dialogue turn by turn would need a person. Grading the database sidesteps that: however the conversation went, the order was either returned correctly or it was not. The simulated user supplies the natural variation that a fixed script cannot, and because the instruction and the database stay the same across trials, differences between trials isolate the agent's own inconsistency. That is the quantity pass^k reports, and it is the one a support team cares about.

Limitation or tradeoff

The paper is explicit that a reward of 1 may be necessary but not sufficient: an agent can reach the right database state after skipping a confirmation the policy requires. The method also moves the effort into task writing, since every instruction must lead to exactly one outcome, and the authors iterated on instructions with many agent trials to remove ambiguity. The simulator is a language model, so it adds its own cost and its own errors: for a gpt-4o agent with a gpt-4 simulator on the retail domain, the paper reports 0.38 US dollars per task for the agent and 0.23 for the simulation. In the authors' sample of failed trajectories, some failures came from typos or ambiguity in the user instruction and not from the agent.

What the sources document

  • A language model (gpt-4-0613) simulates the user from a system prompt holding the task instruction plus the conversation so far, and it cannot see the agent's interaction with the API tools. The episode reward is the product of two binary terms: whether the final database is identical to the unique ground-truth outcome database, and whether the agent's responses contain all necessary information. [7]
  • The paper defines pass^k as the chance that all k independent trials of a task are successful, averaged across tasks, and gives the estimator C(c, k) / C(n, k) for a task run n times with c successes, beside the matching estimator for pass@k. [7]
  • With function calling, gpt-4o scored a pass^1 of 61.2 on the retail domain and 35.2 on the airline domain, and the paper reports that its pass^8 on retail fell below 25%. Sierra's blog post says early agents succeeded on fewer than 50% of tasks and on about 25% when the same task was repeated eight times. [7][8]
  • In a sample of 115 gpt-4o trajectories on retail, 40 tasks failed. On manual examination the authors attributed 4 failures to a typo or ambiguity in the user instruction, which they then fixed, and the remaining 36 to the agent. [7]
  • On the retail domain, with a gpt-4o agent and gpt-4 user simulation, the paper reports costs of 0.38 US dollars per task for the agent and 0.23 US dollars per task for the user simulation, mostly from the long system prompt of domain policy and function definitions. [7]

Example 3 of 5

Berkeley Function-Calling Leaderboard grading tool calls by end state and by required calls

UC Berkeley (Gorilla project)Documented in an engineering article

The Berkeley Function-Calling Leaderboard (BFCL) is a public leaderboard from the Gorilla project at UC Berkeley that scores how accurately language models call functions, which are the tools of an agent. Its first post describes checking a single call by parsing it into an abstract syntax tree. Its V3 post adds multi-turn, multi-step tasks run against simulated backends such as a file system, a trading platform and a booking system, and explains how those tasks are graded. [9][10][11]

The problem

In a multi-turn task a model can take different but equally valid routes. It may list a directory before creating a folder, recover from a failed call, or make a harmless extra lookup. The V3 post explains that an earlier approach, which required the model's calls to match the ground truth in full, would mark such behaviour wrong and so penalise exploration and correct recovery. The benchmark needed a grader that accepts any sound route but still catches a wrong end state, and also catches a model that guesses a value it should have looked up.

Where this topic fits

BFCL touches several layers of this lesson. The single-call AST check is tool-call correctness: the right tool with the right arguments. The state-based check is the outcome layer, because it compares the state of the backend with the expected state. The subset-matched response check is a trajectory check close in spirit to the any-order match described above: the labelled calls must appear, and extra calls are allowed. The 20-step cap and the cost and latency columns belong to the efficiency layer.

How it is applied, step by step

  1. Each test entry has its own initial configuration, which sets up the state of a simulated backend such as a file system or a trading platform. The model is not shown that state directly and must find out about it by calling functions.
  2. Expert human labelers write the ground truth for every turn: the minimal list of function calls that must be executed to produce the response the user asked for, given the initial state.
  3. The model's function calls in a turn are executed against the backend. If the model takes more than 20 steps within one turn, the turn is stopped and the entry is marked incorrect, which ends loops early.
  4. At the end of each turn the state-based check compares the backend's state, leaving out private attributes, with the expected state. This sees writes and deletes but cannot see read-only calls.
  5. The response-based check compares the calls the model executed with the labelled minimal path. The turn passes when the model's calls contain the labelled calls, even if it also made extra calls or took a different route.
  6. An entry counts as correct only if both checks pass in every turn. An entry that hit the step limit is marked wrong even if the checks would have passed.
  7. For single calls, the first BFCL post parses the model's output into an abstract syntax tree and checks the function name, the required parameters, that no parameter outside the function documentation was invented, and the types and values of the arguments.
  8. The leaderboard shows cost and latency next to accuracy, so a model's score can be read together with what it took to get there.

Why this approach fits

A state check accepts any route that ends in the right state, so it does not punish a harmless extra lookup, and a check on the required calls catches what state cannot show: a read-only call the model skipped by guessing. Together they follow the pattern in this lesson, in which the outcome decides pass or fail and a short list of must-happen calls guards the path. In the sketch, run B passes despite an extra lookup, run D passes the state check but fails the subset check because it guessed the zip code, and run E passes the subset check but fails the state check because of a stray folder. The step cap is a cheap budget check that also ends loops.

Limitation or tradeoff

Both checks are only as good as the labelled ground truth and the simulated backend. The V3 post says that expert labelers reviewed every data point and that the data went through 11 rounds of filtering, which is costly to copy for your own tools. A subset check accepts any run that contains the labelled calls, so it cannot flag a wasteful or risky extra call that leaves the state unchanged, and the state check cannot tell which route was taken. The post describes user queries that the authors write, so the design does not exercise a simulated user whose replies depend on the agent, as τ-bench does. Scores come from synthetic backends and say little about how a model handles your own tools.

What the sources document

  • BFCL V3 grades multi-turn entries with two checks run at the end of every turn. State-based evaluation compares the backend system's state, excluding private attributes that start with an underscore, with the ground truth. Response-based evaluation compares the model's execution path with the minimal viable path labelled in the ground truth. An entry is correct only if it passes both checks in all turns. [9]
  • The response-based check is subset-matched: a result is correct if it contains the ground truth as a subset, even with additional function calls or a different trajectory. The post says that the earlier full-match approach would unfairly penalise valid alternative trajectories, error recovery and redundant actions. [9]
  • The post notes that state-based evaluation cannot tell whether functions with no effect on state, such as get_zipcode_by_city, were called, and uses the response-based check so that a model that looks up a zip code is told apart from one that guesses it. [9]
  • If a model takes more than 20 steps within a turn, the turn is force-terminated and the entry is marked incorrect, which the post says saves time and cost. Expert human labelers review all data points and label the ground truth for each question, function list and initial configuration. [9]
  • The first BFCL post describes AST evaluation of a single call: the function name must match, the required parameters must be present, only parameters from the function documentation may be used, and types and values are checked strictly. The current leaderboard page defines cost as an estimate for the entire benchmark in US dollars and latency as measured in seconds. [10][11]

Example 4 of 5

Anthropic's Research feature judged by a rubric and checked by human testers

AnthropicDocumented in an engineering article

Anthropic's June 2025 engineering article on its multi-agent Research feature, in which a lead Claude agent plans a research task and starts parallel subagents that search for information, has a section on how the team evaluated the system while building it. [2]

The problem

The article explains that traditional evaluation assumes the system follows the same steps each time, and that multi-agent systems do not: from identical starting points one agent might search three sources and another ten, or use different tools to find the same answer. Checking for prescribed steps was therefore not possible. The output is also free-form text that rarely has a single correct answer, so it is difficult to evaluate programmatically.

Where this topic fits

Evaluation ran alongside development, starting early with a small sample. It graded the final research output and whether the process was reasonable, not a fixed trajectory. Three pieces worked together: a small fixed set of queries rerun after each change, a judge model applying a rubric to each output, and people using the system and reading what it produced.

How it is applied, step by step

  1. The team began with a set of about 20 queries that represented real usage and reran them after changes, on the reasoning that early changes have effects large enough to see in a few cases.
  2. A judge model scored each output against a rubric with five criteria: factual accuracy, citation accuracy, completeness, source quality and tool efficiency.
  3. After trying several judges for separate components, the team settled on a single judge call with one prompt that returns scores from 0.0 to 1.0 and a pass or fail grade.
  4. Where a test query had a clear answer, the judge was used simply to check whether the answer was correct.
  5. People tested the agents by hand and found a pattern the automated evaluation had missed: the early agents preferred search-optimised content farms to authoritative sources that ranked lower.
  6. The team added source-quality heuristics to the prompts to correct that behaviour.

Why this approach fits

When there is no reference trajectory and no single reference answer, the reference-based checks have nothing to compare with. A rubric states what a good result has in common across all valid routes, and a judge model can apply it to hundreds of outputs. The rubric here still reaches into the trajectory through the tool-efficiency criterion, so wasteful runs are penalised without prescribing a path. A set of twenty queries was enough because the team was looking for large effects, and human testing covered the question a rubric cannot ask: what is wrong that nobody thought to check?

Limitation or tradeoff

The judge is a model, so its scores have to be compared with human judgement before they are trusted; the article says the single-call design was chosen because it was the most consistent and best aligned with human judgements. The source-selection bias shows the limit of the approach: a source-quality criterion existed, yet it was people who noticed the pattern. A small query set detects only large changes and cannot rank two versions that differ by a few points. The article also warns that these systems use far more tokens than chat, which makes every evaluation run expensive.

  • The team experimented with multiple judges per component and found that a single LLM call with a single prompt outputting scores from 0.0 to 1.0 and a pass-fail grade was the most consistent and aligned with human judgements. [2]

Princeton's Holistic Agent Leaderboard reporting cost beside accuracy

Princeton UniversityDocumented in a paper

The 2024 paper AI Agents That Matter, by researchers at Princeton University, argues that agent evaluations must be cost-controlled. The same group runs the Holistic Agent Leaderboard (HAL), a public site and evaluation harness that lists a dollar cost next to the accuracy of every agent. [12][13][14]

The problem

The paper's starting point is that accuracy alone can be bought. Language models are stochastic, so calling a model repeatedly, or retrying until a test passes, raises accuracy with no apparent limit on the compute spent. A leaderboard with one number therefore rewards extremely costly agents, and the authors conclude that the field reached mistaken conclusions about where accuracy gains came from. A developer choosing an agent to deploy cannot tell from such a leaderboard what a result would cost.

Where this topic fits

This is the efficiency layer applied across whole benchmarks. Accuracy still comes from each benchmark's own outcome grader. What changes is that every run also records token usage and cost, and results are read on two axes at once, looking for the agents that no other agent beats on both.

How it is applied, step by step

  1. Each agent is run on a benchmark through one shared harness, so that tasks, graders and logging are the same for every agent.
  2. The harness logs the model calls of every run and tracks token usage, from which a dollar cost is calculated.
  3. Results are published as accuracy together with cost for each combination of agent scaffold and model.
  4. The points are read as a cost and accuracy trade-off. An agent is on the Pareto frontier when no other agent is better on both dimensions.
  5. Complex agents are compared with simple baselines that spend their budget plainly, such as retrying a model or escalating from a cheap model to a dearer one when a test fails.
  6. The logs are kept and inspected, because behaviour that a score hides, such as taking a shortcut, shows up only in the trace.

Why this approach fits

Cost is the one metric an agent can trade directly for accuracy, by retrying, voting or using a larger model, so an accuracy number with no cost attached does not say whether an agent is better designed or only better funded. Putting both on one chart turns "which agent is best" into a question a buyer can answer for a budget. A shared harness matters as much as the second axis: costs are comparable only when every agent ran the same tasks under the same logging.

Limitation or tradeoff

Dollar costs age. The paper itself notes that, unlike accuracy, costs tend to come down over time, which is why it separates the needs of model developers from those of downstream developers. The headline comparison also needs care: the paper's Table A1 lists several LDB variants, and the one built on GPT-4 and GPT-3.5 costs less than the warming baseline, so the over-50% wording fits only some of them. A leaderboard also measures benchmark tasks, not yours, and its entries go stale: the HAL home page states that updates for new models are paused while the team focuses on measuring reliability. Treat the method as the thing to copy, and rerun the measurement on your own tasks at current prices.

What the sources document

  • AI Agents That Matter argues that agent evaluations must be cost-controlled. On HumanEval the authors compared published agents with simple baselines (retry, warming and escalation) and found no significant accuracy difference between their warming strategy and the best-performing agent architecture. [12]
  • The paper reports that for substantially similar accuracy the cost of agents can differ by almost two orders of magnitude, with Reflexion and LDB costing over 50% more than the warming strategy and LATS over 50 times more. [12]
  • HAL describes itself as a standardized, cost-aware, third-party leaderboard for evaluating agents, with cost-controlled evaluations as the default and a harness that has built-in logging and cost tracking. [13]
  • On 11 October 2026 the HAL home page listed the top three TAU-bench Airline entries as 56.0% at 42.11 US dollars, 56.0% at 11.36 US dollars and 54.0% at 180.49 US dollars. [13]
  • The HAL paper's abstract reports 21,730 agent rollouts across 9 models and 9 benchmarks at a total cost of about 40,000 US dollars, and says LLM-aided log inspection uncovered behaviours such as an agent searching for the benchmark on HuggingFace instead of solving a task. [14]

4Common mistakes

  1. Grading only the final message of an agent that takes actions.

    Why it causes problems
    The message is the agent's own report of what it did. A run that says the refund was issued without ever calling the refund tool scores as a success, and the suite stays green while customers are told about refunds that do not exist.
    How to recognise it
    Every grader in the suite takes the answer text as its only input, and no test queries the database, file system or API the agent was supposed to change.
    How to fix it
    Add an outcome check for every task with a side effect: read the end state from the environment and compare it with the expected state. Keep the final-response check as a second, separate grader.

  2. Requiring one exact tool sequence for a task that has several valid routes.

    Why it causes problems
    Runs that reach the right result by another route fail, so the pass rate drops after harmless prompt or model changes. The team learns to rerun or ignore the suite, and real regressions are missed with the false ones.
    How to recognise it
    Trajectory failures whose outcome check passes, and diffs in which the only difference is an extra read-only call or two independent calls in the other order.
    How to fix it
    Reserve exact match for fixed workflows. Elsewhere use in-order or any-order matching on the calls that must happen, express ordering rules as explicit policy checks, and let the outcome decide pass or fail.

  3. Reporting a pass rate measured with one trial per task.

    Why it causes problems
    A task the agent solves three times in four looks solved or broken depending on luck, so the difference between two versions is mostly noise. The number also says nothing about consistency, which is what users of a deployed agent experience.
    How to recognise it
    The score moves by several points when the same version is run twice, and nobody can say how many trials stand behind a number in a report.
    How to fix it
    Run several trials per task from a clean environment each time, report the trial count, and add pass^k for the number of consecutive successes your use case needs.

  4. Trusting a judge model or a test suite that nobody has compared with human judgement.

    Why it causes problems
    A grader that rejects valid solutions makes a capable agent look weak, and one that accepts bad ones hides failures. Either way the team optimises the agent against the grader's errors. In the τ-bench authors' review of 40 failed retail trajectories, 4 traced back to a typo or ambiguity in the task and not to the agent.
    How to recognise it
    A task with a 0% pass rate over many trials, failures that seem unfair when you read the transcript, or a judge score that disagrees with a reviewer on traces they both looked at.
    How to fix it
    Write a reference solution that passes every grader for each task, have people label a sample of traces and measure the judge's agreement with them, and read the transcripts behind any surprising score.

  5. Publishing accuracy without the cost and step counts that produced it.

    Why it causes problems
    Retries, voting and larger models raise accuracy by spending more, so a version can look better while costing many times as much per completed task. The cost shows up later as a bill or as latency that users will not accept.
    How to recognise it
    A comparison table with one column of scores, and no record of tokens, model calls, tool calls or duration per trial in the stored results.
    How to fix it
    Record usage for every trial, report cost per successful task and mean steps next to accuracy, and compare versions on both before choosing one.

Hint 1

For in-order matching, turn the predicted list into an iterator and test each reference call with the in operator. Every successful test consumes the iterator up to the match, which enforces the order.

Hint 2

Tuples that contain dictionaries compare by value in Python, so a call equals a reference call only when both the name and every argument are the same.

Hint 3

Show solution

Append this to the data from the prompt and run it with python3.

python
from math import comb


def in_order(predicted, reference):
    remaining = iter(predicted)
    return all(step in remaining for step in reference)


def any_order(predicted, reference):
    return all(step in predicted for step in reference)


def diagnose(predicted, reference):
    reference_names = [name for name, _ in reference]
    predicted_names = [name for name, _ in predicted]
    labels = []
    for call in predicted:
        if call in reference:
            labels.append("match")
        elif call[0] in reference_names:
            labels.append("wrong_args")
        else:
            labels.append("extra")
    missing = [name for name in reference_names if name not in predicted_names]
    return labels, missing


successes = 0
for name, (calls, state) in TRIALS.items():
    labels, missing = diagnose(calls, REFERENCE)
    outcome = state == GOAL
    successes += outcome
    precision = labels.count("match") / len(calls)
    recall = sum(step in calls for step in REFERENCE) / len(REFERENCE)
    print(f"{name} outcome={'pass' if outcome else 'FAIL'} exact={calls == REFERENCE} "
          f"in_order={in_order(calls, REFERENCE)} any_order={any_order(calls, REFERENCE)} "
          f"precision={precision:.2f} recall={recall:.2f} labels={labels} missing={missing}")

n = len(TRIALS)
for k in (1, 2, 3):
    print(f"pass^{k} = {comb(successes, k)}/{comb(n, k)} = {comb(successes, k) / comb(n, k):.2f}")

Whether T5 should pass is a policy question (must Dana be told after the move, not before?), and if the answer is yes it belongs in an explicit rule, not in exact match.
  • T2 and T4 have the same recall, 2 of 3, for different reasons. T2 called the right tool with the wrong start time, which the wrong_args label shows, and its precision is 0.67 because the bad call is not in the reference. T4 made only correct calls, so its precision is 1.00, but it never sent the message, which the missing list shows.
  • Three of five trials succeed. pass^1 is 3/5. For pass^2, 3 of the 10 possible pairs of trials are all success. For pass^3, only 1 of the 10 possible triples is. An agent that looks 60% reliable on one try is 10% reliable when three consecutive successes are needed.

  3. Compute pass^1, pass^2, pass^4 and pass@2 with the per-task estimators, and the cost per successful trial.
  4. Say which task you would investigate first and what you would look for.
  5. Outline a human review of the 24 traces.

Requirements

  • The scenario must leave exactly one correct final booking, whatever the agent asks.
  • Every requirement in part 2 is mapped to one grader type and one layer, with a one-line reason.
  • Part 3 uses C(c, k) / C(n, k) for pass^k and 1 - C(n - c, k) / C(n, k) for pass@k on each task, averaged over the six tasks.
  • The review plan in part 5 says who reads what, which questions they answer, and what happens to the labels.

Expected behaviour

A good answer has a scenario with an explicit fallback for a fee above the limit, four grader choices that use code wherever a check can be exact, and these numbers: pass^1 = 17/24 = 0.708, pass^2 = 22/36 = 0.611, pass^4 = 3/6 = 0.500, pass@2 = 29/36 = 0.806, a total cost of 1.68 USD and a cost per successful trial of about 0.099 USD. Task 6 is investigated first as a suspected broken task.

Hint 1

Ask of your scenario what the simulated user does if the fee is 80 USD, if two flights leave after 14:00, and if the agent never asks for the booking code. Each unanswered case is a second possible outcome.

Hint 2

For pass^2 on a task with c successes out of 4, count the pairs of successful trials, C(c, 2), and divide by the 6 possible pairs.

Hint 3

A task that fails every trial is more often evidence about the task than about the agent.

Show solution

1. Scenario. In the shape ADK uses for a conversation scenario:

json
{
  "starting_prompt": "Hi, I need to change a flight.",
  "conversation_plan": "You hold booking QX7 on the 09:10 Lisbon to Berlin flight on 14 May. Give the booking code only when asked. Ask for the first direct flight after 14:00 on the same day and accept no other flight. If the agent quotes a change fee of 50 USD or less, confirm it. If the fee is higher, decline and keep the original booking. When the agent confirms the result, end the conversation."
}

Every sentence closes off a second outcome: "first direct flight" and "accept no other flight" fix the flight, the fee rule fixes what happens on either side of the limit, and the last sentence gives the simulator a reason to stop. The goal state is annotated separately, as the flight the booking must end on in the test database.

2. Graders.

RequirementGraderLayerReason
(a) Right flightCodeOutcomeQuery booking QX7 after the trial and compare the flight id.
(b) Fee quoted and confirmed firstCode, plus a judge for the confirmationTrajectoryquote_change_fee must come before change_flight; a rubric line checks that the customer agreed in between.
(c) Polite under pressureJudge model with a rubric, calibrated on human labelsFinal and intermediate responsesTone has no exact form.
(d) At most 12 user turnsCodeTrajectoryCount the user turns in the trace.

Set the simulator's own turn cap a little above 12 so that a conversation which hits it is recorded as a failure of (d) and not cut off silently.

3. Numbers. With n=4n = 4n=4 and successes c=4,4,3,2,4,0c = 4, 4, 3, 2, 4, 0c=4,4,3,2,4,0:

  • pass^1 is the mean of c/4c/4c/4: (4+4+3+2+4+0)/24=17/24=0.708(4+4+3+2+4+0)/24 = 17/24 = 0.708(4+4+3+2+4+0)/24=17/24=0.708.
  • pass^2 uses (c2)/6\binom{c}{2}/6(2c​)/6: the numerators are 6, 6, 3, 1, 6, 0, so 22/36=0.61122/36 = 0.61122/36=0.611.
  • pass^4 uses (c4)/1\binom{c}{4}/1(4c​)/1: the numerators are 1, 1, 0, 0, 1, 0, so 3/6=0.5003/6 = 0.5003/6=0.500.
  • pass@2 uses 1−(4−c2)/61 - \binom{4-c}{2}/61−(24−c​)/6: the numerators are 0, 0, 0, 1, 0, 6, so 1−7/36=0.8061 - 7/36 = 0.8061−7/36=0.806.

The 24 trials cost 24×0.07=1.6824 \times 0.07 = 1.6824×0.07=1.68 USD, of which 0.48 USD is the simulator. With 17 successes the cost per successful trial is 1.68/17≈0.0991.68 / 17 \approx 0.0991.68/17≈0.099 USD, against 0.07 USD per trial.

4. First investigation. Task 6, at 0 of 4. Anthropic's guidance is that a 0% pass rate across many trials most often signals a broken task; four trials are few, so treat it as a strong hint and not as proof. Read the four traces and check that the scenario allows one outcome, that the annotated goal flight exists in the test data, that the simulator gave the booking code when asked, and that the outcome check reads the right record. Only then treat it as an agent failure. Task 4, at 2 of 4, is next: compare a passing and a failing trace to find where they diverge.

5. Human review. Twenty-four traces are few enough to read in full.

  • One reviewer reads every trace; a second reviewer also reads the seven failures.
  • Each trace gets the same questions: Was the verdict fair? Did the simulated user follow its plan? Was the fee quoted and confirmed before the change? Is anything wrong that no grader looks at?
  • Each failure gets one cause from a fixed list. Agent causes: wrong tool, wrong argument, policy step skipped, gave up. Harness causes: ambiguous task, simulator off plan, grader wrong.
  • Harness causes are fixed first and the run is repeated. Each agent cause that recurs becomes a new task or a new rubric line. The reviewers' tone labels are compared with the judge model's scores for (c), and the judge is used unattended only once they agree.

Check your answer

  • Does your scenario say what the customer does when the fee is above 50 USD?
  • Did you get 22/36 for pass^2 and 3/6 for pass^4?
  • Is your cost per successful trial higher than the 0.07 USD cost per trial, and can you say why?
  • Does your review plan separate failures caused by the agent from failures caused by the task, simulator or grader?

6Curated resources

Chosen for accuracy and usefulness, not search rank. Time figures are estimates.

  • Demystifying evals for AI agents (opens in a new tab)

    Anthropic

    ArticleIntermediateFreeAbout 45 minutes (estimate)

    What it teaches
    A vocabulary for agent evals (task, trial, grader, transcript, outcome), the strengths and weaknesses of code, model and human graders, worked grader configurations for coding and conversational agents, pass@k against pass^k, and a step-by-step roadmap from no evals to a maintained suite.
    When to use it
    Read it straight after this lesson, before you design your first suite. Return to the roadmap section when you have twenty failing cases and need to organise them.

  • Why evaluate agents (opens in a new tab)

    Google (Agent Development Kit documentation)

    DocumentationIntermediateFreeAbout 30 minutes (estimate)

    What it teaches
    How one framework implements the ideas here: test files and evalsets, the default trajectory and response criteria, the efficiency criteria, user simulation, and running evaluations from the web UI, pytest and the command line.
    When to use it
    When you want to run a real trajectory and final-response evaluation on your own machine, or need the exact file formats and commands.

  • τ-bench: A Benchmark for Tool-Agent-User Interaction in Real-World Domains (opens in a new tab)

    arXiv

    PaperAdvancedFreeAbout 1 to 2 hours (estimate)

    What it teaches
    A complete design for evaluating conversational agents: language-model user simulation, tasks written so that only one database outcome is correct, the pass^k metric with its estimator, and a manual breakdown of failure types.
    When to use it
    Before you build an evaluation for an agent that talks to customers and writes to a system of record.

  • Build an Agent Improvement Loop with Traces, Evals, and Codex (opens in a new tab)

    OpenAI (Cookbook)

    InteractiveAdvancedFreeAbout 1 to 2 hours (estimate)

    What it teaches
    An end-to-end notebook that traces an Agents SDK agent, attaches example reviewer feedback and model-generated observations to the traces, and generates rerunnable evals from them with deterministic assertions and rubric judges.
    When to use it
    Once you have traces and want to turn review comments into tests. Reading it is free; running it calls paid model APIs.

  • AI Agents That Matter (opens in a new tab)

    arXiv

    PaperAdvancedFreeAbout 1 hour (estimate)

    What it teaches
    Why accuracy without cost misleads, how to read agents on a cost and accuracy Pareto frontier, how simple retry baselines compare with complex agents, and how benchmark shortcuts and weak holdout sets distort results.
    When to use it
    When you compare agent designs or read a leaderboard, and before you report a single accuracy number to a decision-maker.
