AG-UI (Agent-User Interaction Protocol)

AG-UI (Agent-User Interaction Protocol) is an open, event-based protocol that connects an agent backend to a user-facing application. The application sends one JSON request that describes a run, and the agent answers with an ordered stream of typed events (text, tool calls, state changes, lifecycle) that the application turns into live UI.

1Overview

Why it matters

An agent is not an ordinary API call. It can run for seconds or minutes, call several tools, edit a form or a document along the way, and sometimes need a person to approve a step. If the front end only waits for a final JSON answer, users stare at a spinner, cannot see which tool ran, and have nowhere to approve, correct or interrupt anything. If every agent framework also streams in its own format, the front end needs a new parser for each one. AWS describes exactly that cost in its FAST starter template post (opens in a new tab): with its plain HTTP patterns, each of three agent frameworks needs a separate parser, while its two AG-UI patterns share one.

The people who need this are engineers who put a chat, copilot or dashboard in front of an agent, forward deployed engineers who hand an agent to a customer's staff, and anyone reviewing an agent product who has to decide where progress display, approvals and shared state live. A wrong choice shows up as a UI that freezes, a page that disagrees with the agent about the current plan, or a side-effecting tool that runs without a person ever seeing the request.

Key terms

Run
One execution of an agent, started by one RunAgentInput request and ended by a RUN_FINISHED or RUN_ERROR event. It has a runId.
Thread
A conversation. Several runs share a threadId, and messages and state accumulate across them.
RunAgentInput
The single message the application sends to start a run. Only threadId, runId and messages are required; tools, context, state, forwardedProps and resume are optional.
Event stream
The ordered sequence of typed JSON events (RUN_STARTED, TEXT_MESSAGE_CONTENT, STATE_DELTA and so on) that the agent sends back during a run.
Server-Sent Events (SSE)
A web standard for a one-way text stream over HTTP. AG-UI's default binding sends one JSON event in the data field of each SSE frame.
Snapshot and delta
A snapshot replaces a whole value; a delta amends it. State deltas are RFC 6902 JSON Patch arrays applied to the consumer's current copy.
Frontend tool
A tool the application offers in RunAgentInput.tools and executes itself, for example showing a chart or asking the user to pick a time. The agent proposes the call; the application runs it.
Interrupt
A pause reported in RUN_FINISHED.outcome. The run ends and lists what it is waiting for; the next run answers through its resume list.
Generative UI
An interface whose components or layout are chosen by the agent at run time, for example by calling a tool that the front end renders as a chart.

2Explanation

Introduction

In The Agent Loop you saw that an agent does not answer in one step. It reasons, calls a tool, reads the result and repeats, so one task can involve many model calls. In LLM APIs and Streaming you saw how a model's tokens can reach a browser while they are still being generated. This lesson joins the two ideas: how does everything an agent does along the way, not only its words, reach a user interface?

Think of a live match on a sports site. You do not reload the page to learn the score. Small updates arrive as they happen (a goal, a substitution, a card), and each update says which part of the page to change. AG-UI gives an agent the same kind of connection to an interface. The agent does not return one large answer. It emits small, typed events: "a text message started", "here are the next few characters of it", "a tool call named search_flights began", "the shared plan changed at this path", "the run finished". The application listens and updates the screen.

AG-UI stands for Agent-User Interaction Protocol. Its documentation (opens in a new tab) calls it an open, lightweight, event-based protocol that standardizes how AI agents connect to user-facing applications, and it motivates the design with four traits of agents: they run for a long time and stream intermediate work, they are nondeterministic, they mix structured and unstructured input and output, and they can be composed with sub-agents. Because the protocol is shared, a front end that speaks it can work with any backend that speaks it.

One request goes out and an ordered stream of events comes back; that exchange is a run. Several runs on one conversation make a thread. The rest of the lesson covers the request and the event families, how snapshots and deltas keep the agent's state and the page in step, how a run hands control back for an approval or a browser-side tool, which transports can carry the stream, and where AG-UI ends and MCP, A2A and A2UI begin.

How it works

One request in, one ordered stream out

The application starts a run by sending one message, RunAgentInput. The 1.0 specification (opens in a new tab) requires three fields: threadId (the conversation), runId (this run) and messages (the whole history so far, because the protocol has no side channel for earlier turns). The optional fields carry what the agent may need: tools (functions the application offers and executes), context (description and value pairs for the model to see), state (the shared state the run starts from), forwardedProps (a channel the protocol passes through untouched), resume (answers to an earlier pause) and protocolVersion.

In the default HTTP binding the request is a POST with Content-Type: application/json and Accept: text/event-stream. The response is a stream of Server-Sent Events frames, each holding exactly one event as JSON in its data: line:

text
POST /agent HTTP/1.1
Content-Type: application/json
Accept: text/event-stream

{"threadId":"thr-9","runId":"run-1","messages":[{"id":"u1","role":"user","content":"Hi"}]}

HTTP/1.1 200 OK
Content-Type: text/event-stream

data: {"type":"RUN_STARTED","threadId":"thr-9","runId":"run-1"}

data: {"type":"TEXT_MESSAGE_START","messageId":"m1","role":"assistant"}

data: {"type":"TEXT_MESSAGE_CONTENT","messageId":"m1","delta":"Hello! How can I help?"}

data: {"type":"TEXT_MESSAGE_END","messageId":"m1"}

data: {"type":"RUN_FINISHED","threadId":"thr-9","runId":"run-1"}

Inside a run there is no other direction. Events flow from the agent to the application, and the only thing that flows back is the next RunAgentInput: the specification states that the protocol has no mid-run channel from the consumer. That single fact explains most of the protocol's design, including how approvals work.

Eight event families

The specification groups its thirty-one event types into eight families. Only the run lifecycle is mandatory for a producer; every other family is something it sends when it has something to say, and a consumer must accept all of them.

The run lifecycle

A stream must begin with RUN_STARTED or RUN_ERROR and each run ends with RUN_FINISHED or RUN_ERROR. Everything a run opened (messages, tool calls, steps) must be closed before RUN_FINISHED. RUN_FINISHED reports how the run ended in its optional outcome: success (also what an absent outcome means), an interrupt that lists what the run is waiting for, or a cancellation for a run stopped on purpose. It may also carry a result and per-provider token usage.

Two consequences matter for client code. First, an HTTP 200 only means the stream opened; a failure after that travels in the stream as RUN_ERROR, and a consumer must not infer success from the status code. Second, a connection that dies without a terminal event is a truncated run, which has no outcome. The consumer must not invent a RUN_FINISHED for it.

Streaming text and tool calls

Text messages and tool calls follow one pattern: an opening event, any number of content events, and a closing event, all matched by an identifier (messageId or toolCallId). Deltas concatenate in arrival order. A producer may not send content for an item that is not open, and may not leave one open when the run finishes. Messages, tool calls and steps may interleave. A compact TEXT_MESSAGE_CHUNK / TOOL_CALL_CHUNK form exists for producers that would otherwise buffer; consumers expand it into the full triad.

A tool call streams its name in TOOL_CALL_START and its arguments as text pieces in TOOL_CALL_ARGS. The concatenated text is conventionally JSON, but the protocol does not validate it, and until TOOL_CALL_END arrives it is only a prefix, so a consumer must not act on it. The result of a tool the agent ran itself comes in TOOL_CALL_RESULT, which is a separate tool message and does not reopen the call.

Shared state: snapshot and delta

State is a JSON value that the agent and the application keep in agreement, such as a plan, a form or a document under construction. STATE_SNAPSHOT replaces the consumer's copy outright, with no merging. STATE_DELTA carries an RFC 6902 JSON Patch, an array of operations applied in order and atomically. At the start of a run the baseline is the state field of the input; afterwards it is whatever the run's own snapshots and deltas have made of it. A producer may not send a delta for a value it has not given the consumer a baseline for.

A well-formed patch can still fail to apply, for example because its path does not exist. The consumer must not keep a half-applied result; it surfaces a warning and may continue with its prior value. From then on the two sides may disagree, so the producer should resynchronize with a snapshot, and the consumer must adopt the next snapshot whatever it skipped. State persists across runs: the next input carries it back, so the page's edits reach the agent. Because state is a remote write into application memory, the application must validate what it reads from it, and a producer should keep secrets out of it because it round-trips through the client.

Handing control back: frontend tools and interrupts

A run cannot wait for the user in the middle of the stream, because the protocol has no mid-run channel from the application. Two mechanisms work around that by ending the run and continuing in the next one.

  • Frontend tool call. The application lists a tool in tools. When the agent calls it, the producer streams the call but does not answer it, and finishes the run as a success. It may name the unanswered calls in pendingToolCallIds. The application runs the tool, with user consent where needed, and the next run's messages must contain a tool message for every one of those calls. A failure or a refusal is still an answer.
  • Interrupt. When the agent explicitly stops to ask, RUN_FINISHED carries outcome.type = "interrupt" and one or more interrupts, each with an id, a reason, an optional human-readable message, an optional toolCallId and an optional responseSchema the application can turn into a form. The next run carries resume entries, one per interrupt, each resolved with a payload or cancelled. The resume list must cover every interrupt; omitting one is not the same as abandoning it.

Transports

A transport is a binding, not part of the meaning of events. It must deliver the run's events completely and in order, deliver the input before any event, give a consumer a way to tell a clean end from truncation, and reject invalid input before RUN_STARTED through an error path outside the stream. Two bindings are standard. HTTP with SSE is the default, and an implementation that speaks HTTP must support it. HTTP with Protobuf returns length-prefixed binary frames chosen by content negotiation and is optional. Other channels such as WebSockets are allowed if they keep the same event model; a custom transport that carries JSON should frame events exactly as the SSE binding does.

The SSE binding has no resumption. It does not use Last-Event-ID, so a broken stream cannot be re-entered; the consumer starts a new run with a new runId. The protocol also defines no credential. Authentication belongs to the channel and the application, for example an HTTP Authorization header.

Neighbouring protocols

AG-UI covers agent to user application. MCP connects an agent to tools and data, and A2A connects an agent to other agents. The AG-UI documentation describes them as complementary and says a single agent can use all three at once. A2UI is a different thing again: a specification for describing generated UI, not an interaction protocol, and AG-UI can sit underneath such specifications as the connection that delivers them. See A2UI for that layer.

Growing without breaking

The specification separates unrecognised material from malformed values. An event of an unknown type must not abort the run, and neither must an unknown property or an unrecognised union member; the consumer drops or strips it and warns. A field the protocol does describe that carries a value the schema rejects is fatal: the consumer fails the run instead of repairing the value. The protocol version travels in-band, declared by the consumer in RunAgentInput.protocolVersion and by the producer in RUN_STARTED.protocolVersion.

Worked example: Replaying a recorded run to rebuild the screen

A shopping-list assistant shows the list ["bread"]. The user types "Add milk and eggs, then read me the list." The application sends this request body (headers omitted):

json
{"threadId": "thr-1", "runId": "run-1", "state": {"list": ["bread"]},
 "messages": [{"id": "u1", "role": "user", "content": "Add milk and eggs, then read me the list."}],
 "tools": [], "context": [], "forwardedProps": {}}

The agent streams back the sixteen events below. They are written one JSON object per line, which is what the data: field of each SSE frame contains. Save them as stream.jsonl.

text
{"type":"RUN_STARTED","threadId":"thr-1","runId":"run-1"}
{"type":"TEXT_MESSAGE_START","messageId":"m1","role":"assistant"}
{"type":"TEXT_MESSAGE_CONTENT","messageId":"m1","delta":"Adding "}
{"type":"TEXT_MESSAGE_CONTENT","messageId":"m1","delta":"two items"}
{"type":"TEXT_MESSAGE_CONTENT","messageId":"m1","delta":"."}
{"type":"TEXT_MESSAGE_END","messageId":"m1"}
{"type":"TOOL_CALL_START","toolCallId":"c1","toolCallName":"add_items","parentMessageId":"m1"}
{"type":"TOOL_CALL_ARGS","toolCallId":"c1","delta":"{\"items\": [\"mi"}
{"type":"TOOL_CALL_ARGS","toolCallId":"c1","delta":"lk\", \"eggs\"]}"}
{"type":"TOOL_CALL_END","toolCallId":"c1"}
{"type":"STATE_DELTA","delta":[{"op":"add","path":"/list/-","value":"milk"},{"op":"add","path":"/list/-","value":"eggs"}]}
{"type":"TOOL_CALL_RESULT","messageId":"t1","toolCallId":"c1","content":"Added 2 items."}
{"type":"TEXT_MESSAGE_START","messageId":"m2","role":"assistant"}
{"type":"TEXT_MESSAGE_CONTENT","messageId":"m2","delta":"Your list: bread, milk, eggs."}
{"type":"TEXT_MESSAGE_END","messageId":"m2"}
{"type":"RUN_FINISHED","threadId":"thr-1","runId":"run-1"}

The next program is a minimal consumer in plain Python. It keeps the message list, the tool calls, the set of items that are still open, and the state. It parses tool arguments only at TOOL_CALL_END, applies deltas to a copy of the state, and refuses RUN_FINISHED while anything is open. Save it as replay.py next to the stream file and run python3 replay.py.

python
import copy
import json


def patch(doc, ops):
    """RFC 6902 subset (add, replace). Returns a new document; the input is untouched."""
    doc = copy.deepcopy(doc)
    for op in ops:
        *path, last = op["path"].strip("/").split("/")
        target = doc
        for key in path:
            target = target[int(key)] if isinstance(target, list) else target[key]
        if isinstance(target, list):
            index = len(target) if last == "-" else int(last)
            if op["op"] == "add":
                target.insert(index, op["value"])
            else:
                target[index] = op["value"]
        else:
            target[last] = op["value"]
    return doc


def replay(events, state):
    messages, by_id, calls, open_items, status = [], {}, {}, set(), "no events"
    for ev in events:
        kind = ev["type"]
        if kind == "RUN_STARTED":
            status = "running"
        elif kind == "TEXT_MESSAGE_START":
            msg = {"id": ev["messageId"], "role": ev.get("role", "assistant"), "content": ""}
            messages.append(msg)
            by_id[msg["id"]] = msg
            open_items.add(("message", msg["id"]))
        elif kind == "TEXT_MESSAGE_CONTENT":
            by_id[ev["messageId"]]["content"] += ev["delta"]
        elif kind == "TEXT_MESSAGE_END":
            open_items.discard(("message", ev["messageId"]))
        elif kind == "TOOL_CALL_START":
            call = {"id": ev["toolCallId"], "name": ev["toolCallName"], "args": ""}
            calls[call["id"]] = call
            parent = by_id.get(ev.get("parentMessageId"))  # optional in the protocol
            if parent is not None:
                parent.setdefault("toolCalls", []).append(call)
            open_items.add(("call", call["id"]))
        elif kind == "TOOL_CALL_ARGS":
            calls[ev["toolCallId"]]["args"] += ev["delta"]
        elif kind == "TOOL_CALL_END":
            call = calls[ev["toolCallId"]]
            call["args"] = json.loads(call["args"])  # complete only after END
            open_items.discard(("call", call["id"]))
        elif kind == "TOOL_CALL_RESULT":
            messages.append({"id": ev["messageId"], "role": "tool", "content": ev["content"]})
        elif kind == "STATE_SNAPSHOT":
            state = ev["snapshot"]
        elif kind == "STATE_DELTA":
            state = patch(state, ev["delta"])
        elif kind == "RUN_FINISHED":
            assert not open_items, f"still open at RUN_FINISHED: {open_items}"
            status = "finished"
    return messages, state, ("truncated" if status == "running" else status)


events = [json.loads(line) for line in open("stream.jsonl")]
start_state = {"list": ["bread"]}
messages, state, status = replay(events, start_state)
print(status, json.dumps(state))
for message in messages:
    print(json.dumps(message))
print("cut early:", replay(events[:-1], start_state)[2])

The output is:

text
finished {"list": ["bread", "milk", "eggs"]}
{"id": "m1", "role": "assistant", "content": "Adding two items.", "toolCalls": [{"id": "c1", "name": "add_items", "args": {"items": ["milk", "eggs"]}}]}
{"id": "t1", "role": "tool", "content": "Added 2 items."}
{"id": "m2", "role": "assistant", "content": "Your list: bread, milk, eggs."}
cut early: truncated

Read the result against the stream:

  • Events 3 to 5 are three pieces of one message. Concatenated in arrival order they give "Adding two items."
  • Events 8 and 9 split the argument text in the middle of a JSON string. After event 8 the text is {"items": ["mi, and json.loads would raise an "Unterminated string" error. Only after event 10 is it complete and safe to parse.
  • Event 11 is a JSON Patch against the state the request carried. Each add to /list/- appends, so ["bread"] becomes ["bread", "milk", "eggs"]. A producer that computed its patch against a different baseline would leave the page and the agent disagreeing.
  • Event 12 is a tool message with its own id. The agent ran add_items itself, so the result arrives in the stream. Had add_items been a frontend tool, the run would have finished without it.
  • The last line replays the stream without event 16. A consumer must report that as truncated and never as finished, because the run has no outcome.

Edge cases and limitations

HTTP 200 does not mean the run succeeded
The status line is sent before the agent has done any work, so a failure that happens later cannot change it. It arrives as RUN_ERROR inside the stream, and the specification even admits a RUN_ERROR after a RUN_FINISHED for a failure that surfaced late, such as a transport error while flushing. Decide success from the terminal event, not from the status code, and treat a late RUN_ERROR as failure.
A broken stream cannot be resumed
The SSE binding does not use Last-Event-ID, so a stream that drops mid-run is a truncated run with no outcome, and the consumer must not fabricate a RUN_FINISHED. Keep what already arrived, tell the user the run was interrupted by the connection, and start a new run with a new runId whose input carries whatever state and messages you kept. Anything the agent did on the server before the drop, such as calling a side-effecting tool, has still happened.
Tool-call arguments are text until the call closes
The concatenated TOOL_CALL_ARGS deltas are a prefix of the final arguments until TOOL_CALL_END, so parsing or executing them early fails or, worse, acts on half an instruction. Even after the end event, the protocol checks completeness and not validity, so models that emit malformed JSON still reach you. Parse in a try block and validate against the declared parameter schema before running anything.
A patch that fails to apply leaves the two sides out of step
A well-formed STATE_DELTA can point at a path your copy does not have. The patch is atomic, so you keep your previous value, log a warning that names the operation, and carry on. From then on your copy may differ from the agent's. Adopt the next STATE_SNAPSHOT unconditionally. If failures repeat, send your current state in the next RunAgentInput, because the producer must compute its deltas against that value until its own first snapshot replaces it.
An unanswered frontend tool call corrupts the next request
When a run finishes with a frontend tool call pending, the thread can only continue if the next run's messages answer every pending call, keyed by toolCallId. A failure or a user's refusal is a valid answer, silence is not. Many model APIs reject a history that contains a tool call with no result, so a skipped answer shows up as an error on the following turn rather than at the call that caused it.
A newer producer may send events your client does not know
Unknown event types and unknown properties are not errors under the 1.0 processing model, so a conforming consumer drops or strips them and warns. A known field with a wrong type, such as a numeric messageId, is fatal and must not be coerced. Log the warnings in development, because they are the first sign that your client library is behind the backend's protocol version.

When to use it, and when something simpler is enough

Use it when

  • The agent runs long enough, or does enough visible work, that users need streamed text, tool-call progress or intermediate state instead of a spinner.
  • The user must approve, edit or supply something in the middle of a task, and you want that handled by protocol events rather than a custom side channel.
  • The agent and a UI edit the same structure, such as a form, plan, document or canvas, and both need to see each other's changes.
  • You want to swap the agent framework or the front-end library independently, or serve web, mobile and command-line clients from the same endpoint.

Think twice when

  • The feature is a single model call whose text you stream to a chat box; the provider's own streaming format already does that with less machinery.
  • The caller is another service rather than a person, with no UI to drive; agent-to-agent calls belong to A2A and tool access to MCP.
  • You need a guaranteed, resumable delivery channel; the standard SSE binding cannot be resumed, so build durability around it or choose a transport that provides it.

A simpler alternative. Stream the model provider's token events to the browser and show a status line per tool call. That is enough until you need typed tool-call rendering, shared state that both sides edit, or approvals that resume a specific run, at which point rebuilding those by hand is what AG-UI standardizes.

Key takeaways

  • AG-UI is a contract between an agent backend and a user-facing application, in which one RunAgentInput request starts a run and an ordered stream of typed events reports everything the agent does.
  • The 1.0 specification groups thirty-one event types into eight families and makes only the run lifecycle mandatory for a producer, so a client must accept every family but cannot expect any beyond it.
  • Text, tool-call arguments and state are rebuilt on the client from deltas, so tool arguments are only valid after TOOL_CALL_END, and state follows snapshot-replaces, delta-patches.
  • A run never waits for the person in mid-stream; frontend tool calls and interrupts end the run, and the next run's input carries the answer.
  • The default transport is HTTP plus SSE, which cannot be resumed, so success is decided by a terminal event and a dropped connection means a new run.
  • AG-UI complements MCP for tools and A2A for agent-to-agent calls, and treats everything crossing it, including model output and client state, as untrusted input to validate.

Example 1 of 5

Microsoft Agent Framework: tool approvals carried as AG-UI interrupts

MicrosoftDocumented in official docs

Microsoft Agent Framework (MAF) is Microsoft's framework for building agents; its Microsoft Learn pages have separate Python, .NET and Go sections. The documentation describes an AG-UI integration and a human-in-the-loop tutorial, and CopilotKit's announcement post describes the same compatibility from the front-end side. [15][16][17][14]

The problem

An agent that can transfer money, send email or delete files must not run those tools until a person has seen the exact arguments and agreed. When the agent runs as a remote web service and the person is in a browser, the approval cannot be a blocking prompt inside the agent's own process. The framework already knows which tools need approval; what is missing is a standard way to carry the request to the user's screen and the answer back.

Where this topic fits

The approval decision stays inside the framework, where the tool is marked as approval-required. AG-UI is the carrier. The server adapter ends the run with an interrupt outcome, the client shows the request, and the user's choice comes back as a resume entry on the next run of the same thread.

How it is applied, step by step

  1. The developer marks a tool as requiring approval, with approval_mode="always_require" in Python or by wrapping the function in ApprovalRequiredAIFunction in .NET. Read-only tools stay unmarked.
  2. The agent is exposed as an AG-UI endpoint, through a FastAPI endpoint in the Python package or MapAGUIServer in ASP.NET Core. The client sends RunAgentInput and receives the usual text and tool-call events.
  3. When the model calls an approval-required tool, the adapter does not run it. It finishes the run with RUN_FINISHED whose outcome is an interrupt with reason tool_call, the toolCallId and a response schema asking for an accepted flag.
  4. The client shows the tool name and arguments and asks the user. It then starts a new run on the same thread with a resume entry that names the interrupt and carries accepted true or false.
  5. On approval the framework runs the tool through its normal pipeline and streams the result and the final text. On rejection the agent continues without running it. A cancelled resume entry aborts the pending batch.

Why this approach fits

Approval is the clearest case where a run has to stop and ask, and the interrupt outcome is the protocol's standard way to say so. Because the framework decides which tools need approval and AG-UI only transports the question and the answer, a safety policy can change without touching the front end, and any AG-UI client that can render an interrupt can serve as the approval screen.

Limitation or tradeoff

Consent is only as good as what the user is shown. If the client renders a vague message or hides the arguments, the approval is hollow, which is why the Microsoft tutorial advises clear tool descriptions and descriptive argument names. The overview page also says Agent Framework support for the AG-UI scenarios varies by SDK, so read the section for your language before relying on a feature.

What the sources document

  • Microsoft Learn lists, for the Python integration, remote hosting over HTTP, streaming with Server-Sent Events, protocol-managed thread ids and built-in approval support as what AG-UI adds compared with running an agent directly in the application. [15]
  • In the Python tutorial a tool marked approval_mode="always_require" makes the run finish with a canonical AG-UI interrupt, a RUN_FINISHED event whose outcome type is interrupt, with reason tool_call and the id of the tool call. [16]
  • The client resumes the same thread with a resume array whose entries carry interruptId, a status of resolved and a payload with accepted true or false, and a status of cancelled aborts the approval resume and clears queued approval state for the thread. [16]
  • In .NET, wrapping a function in ApprovalRequiredAIFunction and hosting the agent with MapAGUIServer makes the adapter finish the run with a tool-call interrupt instead of executing the function, and AGUIChatClient surfaces it as ToolApprovalRequestContent. [16]
  • CopilotKit announced on 11 November 2025 that Microsoft Agent Framework is AG-UI compatible, and the Microsoft Learn overview shows a CopilotKit React front end connecting by registering the Agent Framework endpoint as an HttpAgent. [17][15]

The facts above come from the cited sources. The steps and analysis in this example are our explanation of how they fit together.

Example 2 of 5

Amazon Bedrock AgentCore Runtime: hosting an AG-UI server with managed authentication and session isolation

Amazon Web ServicesDocumented in official docs

Amazon Bedrock AgentCore Runtime is AWS's managed environment for running agent containers. The developer guide page "Deploy AG-UI servers in AgentCore Runtime" documents how an AG-UI server is built, deployed and invoked there. [18][12][13]

The problem

An AG-UI endpoint that works on a laptop still has to be put on the internet safely. Callers must be authenticated, each conversation's traffic must stay separate from the others, and capacity has to follow load. Writing that around every agent server is repeated work, and getting it wrong exposes tools that can act on behalf of users.

Where this topic fits

AgentCore sits in front of the AG-UI server as a pass-through proxy. The protocol is untouched: the container still receives RunAgentInput and streams events, while the platform adds identity, session isolation and scaling around it. A deployment flag tells the runtime that the container speaks AG-UI rather than plain HTTP, MCP or A2A.

How it is applied, step by step

  1. The developer builds an AG-UI server in a container. The guide's example is a FastAPI app that wraps a Strands agent with the ag-ui-strands library and encodes events for the request's Accept header.
  2. The server listens on port 8080, serves AG-UI requests on POST /invocations (or /ws for WebSocket) and answers health checks on /ping, which the guide says AgentCore requires for AG-UI containers.
  3. The agent is registered with the AgentCore CLI using --protocol AGUI and an authorizer such as a JWT with a Cognito discovery URL. The flag is how the runtime tells AG-UI from the plain HTTP protocol, which shares the port and path.
  4. A client calls the runtime with a bearer token and a session id header. AgentCore authenticates the call and passes the request body to the container unchanged.
  5. The client reads the SSE stream exactly as it would from a local server. The guide's examples print TEXT_MESSAGE_CONTENT deltas and report RUN_ERROR events.

Why this approach fits

AG-UI over HTTP is ordinary HTTP plus a documented event stream, so a managed runtime can host it by proxying and leaving the bytes alone. The same agent code can be tested locally with curl and then run in the cloud, and the platform's identity and isolation features apply without any change to how events are produced or consumed.

Limitation or tradeoff

Because requests pass through unmodified, the platform does not check that the events follow the specification. The guide's troubleshooting list includes event format errors and a mismatch between the authentication method of the request and the one configured, so correctness of the stream remains the container's job. The standard SSE binding also cannot be resumed, so a dropped connection to a long run still ends that run's stream.

Pydantic AI: an AG-UI adapter that treats client input as untrusted

PydanticDocumented in official docs

Pydantic AI is a Python agent framework. Its documentation page on the Agent-User Interaction (AG-UI) Protocol describes the AGUIAdapter class, shared state, and how the adapter treats the data a browser sends. [20]

The problem

When an agent endpoint accepts a RunAgentInput from a browser, everything in it is controlled by the caller: the message history, the shared state, the context entries and even a system message. A server that hands all of it to the model lets a malicious or compromised client rewrite the agent's instructions or feed it forged state.

Where this topic fits

The adapter sits between the web framework and the agent. It parses the request into the agent's own message and dependency types, runs the agent, and converts the agent's events back into AG-UI events. Validation and trust decisions happen in that conversion step.

How it is applied, step by step

  1. The developer exposes the agent with a few lines in a FastAPI or Starlette route that call AGUIAdapter.dispatch_request with the agent.
  2. For shared state the agent declares StateDeps with a Pydantic model as its dependencies type. The adapter validates RunAgentInput.state against that model, and the page's example passes a per-request copy of the dependencies so state stays isolated between requests.
  3. The agent's own instructions stay authoritative. By default a system message sent by the front end is stripped with a warning, and the server's system prompt is used instead.
  4. Client-supplied context entries are not given to the model automatically. The developer reads them from the run input and delivers them as data, never as instructions, and authorises side-effecting tools from facts the server established, such as the authenticated user.
  5. Events stream back as SSE. Tools can attach AG-UI events such as a state snapshot to their return value, and newer protocol features are gated by the installed ag-ui-protocol version.

Why this approach fits

Typed state means a malformed or hostile payload fails validation at the boundary instead of reaching prompts or tools, and a server-owned system prompt means a front end cannot rewrite the agent's rules. The AG-UI specification takes the same stance: its security notes say tool-call arguments are untrusted input and that an application must validate what it reads out of state.

Limitation or tradeoff

Validation proves shape, not honesty. The documentation itself warns that context delivered as data is still indirect prompt-injection input, so scoped tools and server-established identity remain the developer's job. Behaviour also depends on versions: the page says interrupts need ag-ui-protocol 0.1.19 or later, and that on older installs the adapter silently emits a bare RUN_FINISHED with no outcome and ignores resume entries, so an approval-required tool would not pause as intended.

What the sources document

  • On the way in, a message role or input content type that the installed ag-ui-protocol package has no class for is skipped with a UserWarning that names the tag, and the rest of the request runs, so a front end on a newer protocol version keeps working minus the content the server cannot represent. [20]
  • AGUIAdapter.dispatch_request takes an agent and a Starlette request from an AG-UI frontend and returns a streaming response of AG-UI events, and it accepts per-request dependencies, for example ones based on the authenticated user. [20]
  • StateDeps validates RunAgentInput.state against a Pydantic model, custom dependencies must implement the StateHandler protocol, and a new dependencies object is built per request. If state is sent but the dependencies cannot receive it, Pydantic AI warns and ignores the state. [20]

4Common mistakes

  1. Treating an HTTP 200 or the end of the stream as proof that the run succeeded.

    Why it causes problems
    The status line is sent before any work is done, and a connection can close silently. A UI that shows "done" when the stream ends reports a failed or half-finished run as complete, and the user acts on partial results.
    How to recognise it
    Make the agent raise an error after its first token, then kill the server mid-run. If the screen still shows a completed state in either case, the success check is wrong.
    How to fix it
    Track each run as running until RUN_FINISHED (success, interrupt or cancelled) or RUN_ERROR arrives. Treat a closed connection with neither as interrupted, and show the four endings differently.

  2. Parsing or executing tool-call arguments before TOOL_CALL_END arrives.

    Why it causes problems
    Until the call closes, the accumulated text is only a prefix. Parsing it fails with a JSON error, and a lenient partial parser can run an action on half an instruction, such as a refund with the amount cut off.
    How to recognise it
    Log the argument text at each TOOL_CALL_ARGS event. If your code calls json.loads or runs the tool inside that handler rather than in the end handler, it acts on a prefix.
    How to fix it
    Buffer deltas by toolCallId, show only a placeholder while they stream, parse once at TOOL_CALL_END inside a try block, and validate the result against the tool's declared parameter schema before running it.

  3. Applying state deltas blindly and never resynchronizing after a failure.

    Why it causes problems
    A patch that fails to apply leaves the page with a value the agent does not share. Every later delta is then computed against a baseline the page does not have, so the drift grows and the agent answers from state the user cannot see.
    How to recognise it
    Watch for patch-failure warnings in the logs, or for an agent that refers to items missing from the page. Replaying a recorded stream and comparing the final state with the producer's last snapshot exposes it.
    How to fix it
    Apply each patch atomically to a copy, warn and keep the old value on failure, and replace your state with the next STATE_SNAPSHOT unconditionally. On the server, start a run that continues an old thread with a snapshot, and send the current state in every RunAgentInput.

  4. Trusting what crosses the boundary, such as model-written tool arguments, client state and context entries.

    Why it causes problems
    Tool arguments come from a model, and state and context come from a browser the user controls. Used unchecked in prompts, queries or shell commands they allow prompt injection, forged state and unauthorised actions. State also round-trips through the client, so any secret placed in it is exposed.
    How to recognise it
    Search for places where state, context or argument text is interpolated into a system prompt, SQL, a shell command or HTML, and for tool calls that run without any user-visible approval.
    How to fix it
    Validate arguments against the declared schema, require user consent before side-effecting tools, keep secrets and permissions on the server, and pass client-supplied facts to the model as data rather than as instructions.

  5. Leaving messages, tool calls or steps open when a run ends, or reusing an open identifier, in a producer you write.

    Why it causes problems
    A conforming consumer treats content for an unopened id, a start for an already open id and anything still open at RUN_FINISHED as protocol violations that are fatal to the run. The same stream may appear to work in a lenient client and fail in a strict one.
    How to recognise it
    Replay your own output through a checker like the one in the worked example. Runs that end in an error only on some clients, or messages that never appear complete, point to an unclosed item.
    How to fix it
    Close what you open in a finally block, generate a fresh id for every message and tool call, and report RUN_ERROR instead of RUN_FINISHED when you cannot close cleanly. Use the chunk events when you cannot buffer enough to emit explicit start and end events.

Exercise 1

Serve a run over SSE and consume it with the right outcome logic

CodingIntermediateAbout 40 min (estimate)Hypothetical scenario

Build a tiny AG-UI-style server and client with only the Python standard library, so you see the wire format yourself. No model or API key is needed: the "agent" repeats the user's last message word by word.

The server listens on 127.0.0.1:8765 and handles POST /agent, which receives a RunAgentInput JSON object and answers as a Server-Sent Events stream. The client sends one RunAgentInput, prints the text as it arrives, and ends by printing exactly one outcome.

Exercise three inputs: a normal message, a message containing the word boom, and a body that has no runId. The point of the third and second inputs is that a rejected request and a failed run look different on the wire.

Requirements

  • Reject a body that is not valid JSON, or that lacks threadId, runId or a non-empty messages list, with HTTP 400 and no event stream.
  • For a valid body answer 200 with Content-Type text/event-stream and send RUN_STARTED, TEXT_MESSAGE_START, one TEXT_MESSAGE_CONTENT per word, TEXT_MESSAGE_END and RUN_FINISHED, each as one JSON object on a data line followed by a blank line, flushed after every frame.
  • If the last message contains "boom", send RUN_STARTED and then RUN_ERROR with a message and a code, never RUN_FINISHED, while the HTTP status stays 200.
  • The client starts with the outcome "truncated" and changes it only on RUN_FINISHED, RUN_ERROR or an HTTP error status.

Expected behaviour

Running the client prints one line per input. The first streams the words and then reports the outcome.

text
You said: hello world [finished]
[failed: simulated failure]
[rejected before the run: HTTP 400]

With the server running, curl -N -X POST http://127.0.0.1:8765/agent -H "Content-Type: application/json" -d '{"threadId":"t","runId":"r","messages":[{"id":"u","role":"user","content":"hi there"}]}' prints eight data: frames separated by blank lines.

Hint 1

Call `self.wfile.flush()` after writing each frame, or the client sees nothing until the handler ends. The handler returning closes the connection, which ends the stream.

Hint 2

Do all validation before `send_response(200)`. Once the status line is out, an error can only travel as RUN_ERROR.

Hint 3

In the client, iterate over the response line by line and act only on lines that start with `data:`. Ignore everything else, as the SSE binding requires.

Show solution

Start with the server. Validation happens before any header is sent, so a bad request becomes a plain HTTP 400 and the run never starts. After send_response(200) the only way to report trouble is an event.

python
import json
from http.server import BaseHTTPRequestHandler, ThreadingHTTPServer


def frame(event):
    return f"data: {json.dumps(event, separators=(',', ':'))}\n\n".encode()


class Agent(BaseHTTPRequestHandler):
    def emit(self, event):
        self.wfile.write(frame(event))
        self.wfile.flush()

    def do_POST(self):
        if self.path != "/agent":
            return self.send_error(404)
        try:
            body = json.loads(self.rfile.read(int(self.headers.get("Content-Length", 0))))
            thread_id, run_id = body["threadId"], body["runId"]
            question = body["messages"][-1]["content"]
        except (ValueError, KeyError, IndexError, TypeError):
            return self.send_error(400, "invalid RunAgentInput")  # no stream: the run never started
        self.send_response(200)
        self.send_header("Content-Type", "text/event-stream")
        self.send_header("Cache-Control", "no-cache")
        self.end_headers()
        self.emit({"type": "RUN_STARTED", "threadId": thread_id, "runId": run_id})
        if "boom" in question:  # failure after the 200 was sent travels in the stream
            return self.emit({"type": "RUN_ERROR", "message": "simulated failure", "code": "demo"})
        self.emit({"type": "TEXT_MESSAGE_START", "messageId": "m1", "role": "assistant"})
        for word in f"You said: {question}".split():
            self.emit({"type": "TEXT_MESSAGE_CONTENT", "messageId": "m1", "delta": word + " "})
        self.emit({"type": "TEXT_MESSAGE_END", "messageId": "m1"})
        self.emit({"type": "RUN_FINISHED", "threadId": thread_id, "runId": run_id})


ThreadingHTTPServer(("127.0.0.1", 8765), Agent).serve_forever()

The client assumes the worst until it sees a terminal event, which is how it distinguishes a clean finish from a dropped connection. Save it as client.py, start the server in one terminal with python3 server.py, and run python3 client.py in another.

python
import json
import urllib.error
import urllib.request

URL = "http://127.0.0.1:8765/agent"


def run(message, run_id="run-1"):
    body = {"threadId": "thr-1", "runId": run_id, "state": {}, "tools": [], "context": [],
            "forwardedProps": {}, "messages": [{"id": "u1", "role": "user", "content": message}]}
    if run_id is None:
        del body["runId"]
    request = urllib.request.Request(
        URL, data=json.dumps(body).encode(),
        headers={"Content-Type": "application/json", "Accept": "text/event-stream"})
    outcome = "truncated"  # no terminal event seen yet
    try:
        with urllib.request.urlopen(request) as response:
            for raw in response:
                line = raw.decode().rstrip("\n")
                if not line.startswith("data:"):
                    continue
                event = json.loads(line[5:])
                if event["type"] == "TEXT_MESSAGE_CONTENT":
                    print(event["delta"], end="", flush=True)
                elif event["type"] == "RUN_FINISHED":
                    outcome = "finished"
                elif event["type"] == "RUN_ERROR":
                    outcome = f"failed: {event['message']}"
    except urllib.error.HTTPError as err:
        outcome = f"rejected before the run: HTTP {err.code}"
    print(f"[{outcome}]")


run("hello world")
run("boom")
run("no run id", run_id=None)

Output:

text
You said: hello world [finished]
[failed: simulated failure]
[rejected before the run: HTTP 400]

The second input shows a failed run with a 200 status, and the third shows an input rejected before RUN_STARTED. To see truncation, add time.sleep(0.4) before each content frame, start a run and stop the server with kill -9: the client prints [truncated] because no terminal event arrived.

  • If you stop the server mid-run, does the client print truncated instead of finished?

Exercise 2

Design the event sequence for a refund that needs approval

DesignAdvancedAbout 35 min (estimate)Hypothetical scenario

A support agent has a backend tool issue_refund(order_id, amount). Refunds above 100 USD need a person's approval before the tool runs. The support representative can approve, approve with a lower amount, or reject.

Design the AG-UI exchange for the request "Refund order A-1002, 140 USD":

  1. Write the closing events of run 1, from TOOL_CALL_START to RUN_FINISHED, as JSON, including the interrupt and a responseSchema the application can turn into a form.
  2. Write the resume list of run 2 for each of the three decisions.
  3. Say how the exchange would differ if issue_refund were a frontend tool that the application executes, and name one practical consequence for the thread's messages.

Requirements

  • Run 1 must not execute the refund and must not emit TOOL_CALL_RESULT.
  • The interrupt must carry an id, a reason, the toolCallId of the refund call and a response schema.
  • Each resume entry must name the interrupt id and a status, and the reject case must not omit the entry.
  • The frontend-tool variant must say how the unanswered call is reported and how the next run answers it.

Expected behaviour

A sequence in which run 1 streams the refund call and ends with an interrupt outcome, and run 2 on the same thread carries one resume entry that either approves (possibly with an edited amount) or rejects. The frontend-tool variant instead ends run 1 as a success that names the pending call, and the next run's messages contain a tool message for that call.

Hint 1

The response schema is opaque to the protocol, so you choose its fields. An `accepted` boolean and an optional `amount` number are enough.

Hint 2

Rejecting is still an answer. Use a resolved entry whose payload says `accepted` is false; reserve the cancelled status for abandoning the interrupt.

Hint 3

A frontend tool's result is not a resume entry. It travels in the next run's messages as a tool message keyed by toolCallId.

Show solution

Run 1 streams the call and then ends instead of executing it:

text
{"type":"TOOL_CALL_START","toolCallId":"call-1","toolCallName":"issue_refund","parentMessageId":"m1"}
{"type":"TOOL_CALL_ARGS","toolCallId":"call-1","delta":"{\"order_id\":\"A-1002\",\"amount\":140}"}
{"type":"TOOL_CALL_END","toolCallId":"call-1"}
{"type":"RUN_FINISHED","threadId":"thr-3","runId":"run-1","outcome":{"type":"interrupt","interrupts":[
  {"id":"int-1","reason":"tool_call","toolCallId":"call-1",
   "message":"Approve a 140 USD refund for order A-1002?",
   "responseSchema":{"type":"object","properties":{"accepted":{"type":"boolean"},"amount":{"type":"number"}},"required":["accepted"]}}]}}

Run 2 is a new run on the same thread, so it carries "threadId":"thr-3", a new runId, the history so far, and one of these resume lists:

text
Approve:             "resume":[{"interruptId":"int-1","status":"resolved","payload":{"accepted":true}}]
Approve, lower sum:  "resume":[{"interruptId":"int-1","status":"resolved","payload":{"accepted":true,"amount":100}}]
Reject:              "resume":[{"interruptId":"int-1","status":"resolved","payload":{"accepted":false}}]

The list must cover every interrupt of the run being continued, so even a rejection is an entry. The agent decides what to do with amount; the protocol does not interpret the payload. A "status":"cancelled" entry would instead abandon the interrupt without an answer.

As a frontend tool, issue_refund would be listed in RunAgentInput.tools, and the agent would still stream TOOL_CALL_START, TOOL_CALL_ARGS and TOOL_CALL_END. Run 1 would then finish as a success, not an interrupt, optionally naming pendingToolCallIds: ["call-1"], and would not answer the call. The application runs the refund itself, after its own consent check, and the next run's messages must contain a tool message with toolCallId: "call-1" and the result, or an error, or text saying the user declined. The practical difference is where the code runs and who owns the decision: with an interrupt the agent's side executes the tool after the answer, with a frontend tool the application does.

5  {"type":"TOOL_CALL_ARGS","toolCallId":"c1","delta":"{\"q\": \"agui\"}"}
6  {"type":"TEXT_MESSAGE_CONTENT","messageId":"m2","delta":"Found it."}
7  {"type":"STATE_DELTA","delta":[{"op":"replace","path":"/results","value":[1]}]}
8  {"type":"TOOL_CALL_END","toolCallId":"c1"}
9  {"type":"RUN_FINISHED","threadId":"t1","runId":"r1"}
10 {"type":"TEXT_MESSAGE_END","messageId":"m1"}

Requirements

  • Give a verdict for all ten events, naming the rule that decides each one.
  • Separate fatal violations from the one event that is only a warning.
  • State which events would have been fine if the order of other events were corrected.

Expected behaviour

Events 1, 6, 9 and 10 are violations, event 7 is a warning, and events 2, 3, 4, 5 and 8 are fine. Event 1 breaks the rule about how a stream opens, event 6 sends content for an item that is not open, event 9 finishes the run with a message still open, and event 10 arrives after the run closed.

Hint 1

Start with the first event. What may a stream begin with?

Hint 2

For each content or end event, ask whether its id was opened and is still open at that point.

Hint 3

A JSON Patch `replace` needs an existing target. What does the state look like when event 7 arrives?

Show solution
  • Event 1, violation. A stream must begin with RUN_STARTED or RUN_ERROR; nothing else may come first. Putting event 2 before it would make event 1 legal.
  • Event 2, fine in itself. It is the right opener, though it arrives after the offending event 1.
  • Event 3, fine. m1 was opened by event 1 and is open.
  • Events 4 and 5, fine. A tool call may open while a message is open and streams its arguments.
  • Event 6, violation. Content for m2, which was never opened, is a malformed sequence and is fatal.
  • Event 7, warning only. The patch is well formed, but the state is {} and replace needs /results to exist. The patch is atomic, so the consumer keeps its value, warns, and adopts the next snapshot. An add operation would have worked.
  • Event 8, fine. It closes c1 before the run finishes.
  • Event 9, violation. m1 is still open, and everything a run opened must be closed before RUN_FINISHED. Sending TEXT_MESSAGE_END for m1 first would fix it.
  • Event 10, violation. After a run closes, only a new RUN_STARTED or a late RUN_ERROR may follow, so a TEXT_MESSAGE_END is rejected. Moving it before event 9 fixes both events 9 and 10.

Check your answer

  • Did you identify exactly four fatal events and one warning?
  • Can you say why event 7 is not fatal even though it fails?
  • Did you find that moving one event fixes two violations?
