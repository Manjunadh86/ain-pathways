Agentic RAG

Agentic RAG is retrieval-augmented generation in which a language model controls retrieval instead of receiving search results once. Search is a tool the model may call, so the model decides whether to retrieve, what to ask for, whether the results are good enough, and whether to search again before it answers.

1Overview

Why it matters

A fixed retrieve-then-generate pipeline fails in a few predictable ways. The user's wording does not match the wording of the documents. The question needs facts from two different places. The top results look related but do not contain the answer, and the pipeline answers from them anyway. In this lesson's worked example, a store assistant that searches once retrieves only the return-window passages, so a generator reading them would tell a customer they can return an item that the policy excludes. Agentic RAG addresses these failures by letting the model rewrite and split queries, search more than once, and by checking what comes back before an answer is written.

It also multiplies model calls, adds latency that varies from one question to the next, and introduces loops that have to be bounded. Anyone building a support assistant, a research tool or a coding agent needs to know which retrieval decisions to hand to the model, which to keep in code, and how to tell from a trace whether planning, retrieval, grading or generation went wrong.

  • Estimate how hit rate per search, number of hops and retries combine into a success rate and a call count.
  • Decide when single-shot RAG is enough and when agentic RAG is worth its latency and cost.

Key terms

Single-shot RAG
A fixed pipeline that runs one search with the user's question, puts the top results in the prompt and generates an answer from whatever was found. Also called 2-step or naive RAG.
Retrieval tool
A search function described to the model with a name, a description and a query parameter, which the model may call or ignore.
Query planning
Deciding, before or between searches, which queries to run: rewriting a question, splitting it into sub-questions, or choosing a source.
Query decomposition
Splitting one question that has several parts into separate sub-queries that are searched on their own.
Routing
Choosing which source or retrieval method a query goes to, such as a policy index, an order database or web search.
Multi-step retrieval
Running several searches in sequence, where what one search returns shapes the next query. Also called multi-hop retrieval.
Grader
A check, usually a small model call with a fixed output format, that labels a retrieved passage as relevant or not relevant to the question.
Self-correction
What the system does after a failed check: rewrite the query, try another source, regenerate the answer or decline to answer.
Groundedness
Whether every claim in an answer is supported by the passages the answer cites.
Search budget
A hard cap, enforced in code, on the number of searches or failed attempts allowed for one question.

2Explanation

Introduction

In Retrieval-Augmented Generation you built a fixed pipeline: take the user's question, run one search, paste the top results into the prompt, generate. In The Agent Loop you saw a model choose its own next action, read the result and choose again. Agentic RAG puts retrieval inside that loop.

Think about how you look something up yourself. You type a query, skim the results, notice they are about the wrong thing, and rephrase. For a question with two parts you run two searches. If the first three results do not answer the question, you do not write an answer from them anyway. Single-shot RAG does none of this. It searches once with the user's literal words and answers from whatever comes back.

Agentic RAG gives the model those four habits:

  • Decide whether to retrieve. Search is a tool the model can call. A greeting needs no search, and a policy question does.
  • Plan the query. The model writes the search text, splits a question into parts and picks a source.
  • Retrieve in several steps. What one search returns can shape the next one.
  • Grade and correct. Retrieved passages are checked for relevance, and a failed check leads to a rewrite, a different source or an honest "not found".

The Hugging Face Agents Course puts the difference this way: instead of answering on top of documents automatically, the agent (Alfred, in the course's example) can decide to use any other tool or flow (opens in a new tab) to answer the question.

Each of those decisions is another model call, so an agentic system is usually slower and more expensive per question than the pipeline it replaces. This lesson explains the four parts, runs them on a small corpus with a real keyword retriever, and shows how to bound the loop and when the simpler pipeline is the better choice.

How it works

Retrieval becomes a tool call

In single-shot RAG your code calls the retriever. In agentic RAG you describe the retriever to the model as a tool (see Tool Calling), and the model decides whether to call it and with what query. A definition written for this lesson's worked example:

json
{
  "name": "search_handbook",
  "description": "Search the store policy handbook (returns, shipping, membership, warranty). Returns up to 2 passages with their ids. Write the query in the handbook's vocabulary, not the customer's.",
  "input_schema": {
    "type": "object",
    "properties": {
      "query": {"type": "string", "description": "3 to 6 keywords"}
    },
    "required": ["query"]
  }
}

The description does retrieval work. It tells the model what the corpus covers, which is how the model knows when a search is pointless, and how to phrase a query (Designing Tools for Agents covers this in depth).

Hosted search tools follow the same contract. Anthropic's web search tool (opens in a new tab) documentation says that Claude determines when to search based on the prompt, the API runs the searches, the process can repeat several times within one request, and the final response carries citations. It lists what triggers a search (recent events, current prices, an explicit request to look something up) and what does not (established facts, greetings, analysis of content already in the conversation). A max_uses parameter caps the searches per request. In LangGraph's agentic RAG tutorial (opens in a new tab) the first node is named generate_query_or_respond: the model, bound to a retriever tool, either emits a tool call or answers.

Who decides what

Agentic RAG is a range of designs. LangChain's retrieval documentation (opens in a new tab) compares three: 2-step RAG, where retrieval always runs before generation; agentic RAG, where an agent decides when and how to retrieve; and a hybrid that adds validation steps. It rates them on control, flexibility and latency. The agentic design gets the least control, and both it and the hybrid get a latency the page calls variable.

The middle column is a sound default. The model chooses the queries, where its judgement helps most, and code guarantees that grading runs and that the loop ends.

Query planning

Planning is what happens before a search, or between two searches. There are three moves:

MoveWhat it doesExample
RewriteTurns the user's wording into the corpus's wording"send back helmet" becomes "return window Plus members"
DecomposeSplits a question with several parts into sub-queriesA before, during and after question becomes three queries
RoutePicks the source or method for a queryPolicy handbook, order database or web search

The Hugging Face course lists the first two, plus query expansion (several wordings of the same query), among the things a retrieval agent (opens in a new tab) can do. LlamaIndex documents each as a module. Its SubQuestionQueryEngine (opens in a new tab) example takes a question about how Paul Graham's life differed before, during and after YC, generates one sub-question for each period and then combines the three answers. Its routers (opens in a new tab) use an LLM to choose among a set of choices defined by metadata, such as the description attached to each query engine tool. The page's use case is deciding between summarisation and semantic search. The same documentation calls these modules agentic in nature (opens in a new tab), because an LLM makes the decision. Routing can also choose how much retrieval to do: the Adaptive-RAG paper (opens in a new tab) trains a smaller language model as a classifier that predicts how complex each question is and picks no retrieval, single-step retrieval or iterative (multi-step) retrieval.

Timing matters. A plan written up front can run its sub-queries in parallel, so the added latency is one planning call plus the slowest search. A plan made one step at a time can use what earlier searches found, and some questions need that.

Multi-step retrieval

Multi-step retrieval is the agent loop with a search tool: search, read the observation, decide the next query. It is required when a later query depends on an earlier result. "What is the on-call policy of the team that owns the billing service?" cannot be answered with parallel searches, because the second query needs the team name that the first search returns. A question that needs a chain of searches like this is called multi-hop, and each search in the chain is a hop.

The same loop handles uncertainty about wording. Anthropic's guidance for its research agents is to start with short, broad queries, look at what is available, and then narrow.

Grading retrieved documents

A retriever returns its best matches whether or not any of them is good. Its score tells you which passages are closest to the query, not whether any of them answers the question. A grader asks that second question directly. The Self-RAG paper (opens in a new tab) trains a model to emit special reflection tokens: one decides whether to retrieve at all, and three judge the results. Those three are a useful checklist for any system:

CheckLooks atQuestion
Relevancequestion and passageDoes this passage provide useful information for the question?
Supportpassage and answerIs each claim in the answer supported by the passage?
Usefulnessquestion and answerDoes the answer respond to what was asked?

In practice the relevance grader is a small model call with a constrained output (see Structured Outputs). The LangGraph tutorial uses a schema with a single field, binary_score, that holds "yes" or "no". Its grader reads all the retrieved text as one block, so a single "no" discards everything. Grading each passage separately, as the worked example below does, keeps the good passages, and only the passages that survive go to the generator.

Self-correction

A failed check is only useful if something different happens next. The options are:

  • Rewrite and search again. In the LangGraph tutorial, a "no" from the grader routes to a rewrite_question node, which feeds back into the first node.
  • Change source. Corrective RAG, described in the examples below, falls back to web search when every retrieved document scores poorly.
  • Regenerate. When the support check fails, generate again from the same evidence.
  • Decline. Say that the sources do not cover the question, or ask the user to clarify.

Every one of these paths needs a cap enforced in code. The tutorial graph's rewrite edge has no counter of its own, so a question the corpus cannot answer could keep cycling until a framework limit stops it.

What it costs

Count the calls first. A run with sss searches that grades up to kkk passages per search makes s+1s + 1s+1 agent calls and up to sksksk grader calls. Three searches with two passages each is up to ten model calls, where single-shot RAG makes one.

Retries pay for themselves on multi-hop questions. Suppose one search finds a relevant passage with probability ppp, a question needs nnn hops, and each hop may be retried rrr times. If attempts were independent, the chance that every hop succeeds would be:

P(all hops succeed)=(1−(1−p)r+1)nP(\text{all hops succeed}) = \left(1 - (1 - p)^{r+1}\right)^{n}P(all hops succeed)=(1−(1−p)r+1)n

With p=0.8p = 0.8p=0.8 and three hops this gives 51.2% with no retry, 88.5% with one and 97.6% with two.

Read the curve as an upper bound. Real retries are not independent: when the corpus lacks the answer, every rewrite fails. The second retry also adds far less than the first, while the worst-case latency grows by the same amount each time. Measure the hit rate on your own questions (see Evaluating RAG Systems) before choosing a retry count.

Worked example: A store-policy assistant where one search gives the wrong answer and three graded searches give the right one

A bike shop's handbook has six passages. A customer writes: I am a Plus member. Can I send back the clearance helmet I got 45 days ago? The right answer needs two passages: Plus members have 60 days, and clearance items cannot be returned at all.

The retriever below is real BM25 keyword scoring (see Advanced Retrieval). As in The Agent Loop, the models are scripted so that everyone gets the same output: replies holds the agent model's decisions and relevant holds the grader's verdicts. Save this as agentic_rag.py. It needs only the Python standard library (3.9 or later).

python
import math
import re
from collections import Counter

DOCS = {
    "returns-standard": "Standard members can return unused items within 30 days of delivery for a full refund.",
    "returns-plus": "Plus members have a longer return window. They can return unused items within 60 days of delivery.",
    "returns-exclusions": "Clearance items are final sale. They cannot be returned or exchanged, whatever the membership tier.",
    "shipping": "Orders ship within 2 business days. Standard delivery takes 3 to 5 days. Plus members get free shipping.",
    "membership": "Plus membership costs 49 USD per year. A Plus member gets free shipping, priority support and early access to clearance events.",
    "warranty": "Every helmet carries a 1 year warranty against manufacturing defects. Frames carry a 5 year warranty.",
}
K1, B = 1.5, 0.75                 # standard BM25 constants
MAX_SEARCHES, MAX_MISSES = 4, 2   # search budget, and failed searches allowed in a row


def tokenize(text):
    words = re.findall(r"[a-z0-9]+", text.lower())
    return [w[:-1] if len(w) > 3 and w.endswith("s") else w for w in words]  # crude plural stripping


TOKENS = {doc_id: tokenize(text) for doc_id, text in DOCS.items()}
AVG_LEN = sum(len(tokens) for tokens in TOKENS.values()) / len(TOKENS)
DF = Counter(term for tokens in TOKENS.values() for term in set(tokens))


def search(query, k=2):
    """The retrieval tool: BM25 over the handbook, best k passages that score above zero."""
    scored = []
    for doc_id, tokens in TOKENS.items():
        counts, score = Counter(tokens), 0.0
        for term in set(tokenize(query)):
            tf = counts[term]
            idf = math.log((len(DOCS) - DF[term] + 0.5) / (DF[term] + 0.5) + 1)
            score += idf * tf * (K1 + 1) / (tf + K1 * (1 - B + B * len(tokens) / AVG_LEN))
        scored.append((round(score, 2), doc_id))
    return [(doc_id, score) for score, doc_id in sorted(scored, reverse=True)[:k] if score > 0]


def run(replies, relevant):
    """replies stands in for the agent model's decisions, relevant for the grader model's verdicts."""
    evidence, searches, graded, misses = [], 0, 0, 0
    for kind, text, *cited in replies:                    # one reply = one model call
        if kind == "answer":
            grounded = set(cited[0]) <= set(evidence)     # may cite only what was retrieved and kept
            return {"status": "answered" if grounded else "rejected", "answer": text,
                    "cited": cited[0], "searches": searches, "graded": graded}
        hits = search(text)                               # the model asked for a search
        searches, graded = searches + 1, graded + len(hits)
        kept = [doc_id for doc_id, _ in hits if doc_id in relevant]   # grade every hit
        evidence = evidence + [doc_id for doc_id in kept if doc_id not in evidence]
        misses = 0 if kept else misses + 1
        print(f"  search {searches}: {text!r} -> {hits} -> kept {kept}")
        if misses == MAX_MISSES or searches == MAX_SEARCHES:
            break
    return {"status": "not_found", "answer": None, "cited": [], "searches": searches, "graded": graded}


Q1 = "I am a Plus member. Can I send back the clearance helmet I got 45 days ago?"
Q1_REPLIES = [
    ("search", "send back helmet"),
    ("search", "return window Plus members"),
    ("search", "clearance items returned or exchanged"),
    ("answer", "No. Plus members get 60 days, but clearance items are final sale.",
     ["returns-plus", "returns-exclusions"]),
]
Q2_REPLIES = [   # Q2: What is the warranty on an e-bike battery?
    ("search", "e-bike battery warranty"),
    ("search", "battery guarantee"),
    ("answer", "Batteries have a 1 year warranty.", ["warranty"]),
]

if __name__ == "__main__":
    print("single-shot:", search(Q1))
    print(run(Q1_REPLIES, relevant={"returns-plus", "returns-exclusions"}))
    print(run(Q2_REPLIES, relevant=set()))

Running python3 agentic_rag.py prints:

text
single-shot: [('returns-plus', 3.3), ('returns-standard', 2.75)]
  search 1: 'send back helmet' -> [('warranty', 1.58)] -> kept []
  search 2: 'return window Plus members' -> [('returns-plus', 4.15), ('returns-standard', 1.55)] -> kept ['returns-plus']
  search 3: 'clearance items returned or exchanged' -> [('returns-exclusions', 6.7), ('membership', 0.93)] -> kept ['returns-exclusions']
{'status': 'answered', 'answer': 'No. Plus members get 60 days, but clearance items are final sale.', 'cited': ['returns-plus', 'returns-exclusions'], 'searches': 3, 'graded': 5}
  search 1: 'e-bike battery warranty' -> [('warranty', 2.24)] -> kept []
  search 2: 'battery guarantee' -> [] -> kept []
{'status': 'not_found', 'answer': None, 'cited': [], 'searches': 2, 'graded': 1}

What to notice:

  • One search is confidently wrong. Searching with the customer's sentence returns the two return-window passages. returns-exclusions scores 2.71 and misses the top two by 0.04. A generator given those passages would say yes, since 45 days is inside 60.
  • Grading caught a bad search. "send back helmet" matched only the warranty passage, through the word "helmet". You can check the score by hand. The word is in 1 of 6 passages, so its idf is ln(5.5 / 1.5 + 1) = 1.540. The passage has 16 tokens against an average of 17, so the score is 1.540 × 2.5 / (1 + 1.5 × (0.25 + 0.75 × 16 / 17)) = 1.58. The grader rejected the passage, and the next query used the handbook's own words.
  • One search per sub-question. Searches 2 and 3 each returned one relevant passage and one distractor, and grading dropped the distractors.
  • The second question ends honestly. The warranty passage matches the word "warranty" but says nothing about batteries. After two misses in a row the loop returns not_found. The third scripted reply, a wrong answer built on the rejected passage, is never used.
  • Cost. Question 1 took 3 searches, 4 agent calls and 5 grader calls. The single-shot pipeline takes 1 search and 1 model call.

In a live system, replies becomes a tool-calling model and relevant becomes a grader call.

Edge cases and limitations

The grader is wrong more often than you assume
A grader is a model making a judgement, and it errs in both directions. A false "irrelevant" sends the loop into rewrites or a not-found answer when the right passage had already been retrieved. A false "relevant" passes a distractor to the generator. The CRAG authors measured this on the PopQA dataset: their fine-tuned evaluator judged retrieval quality correctly 84.3% of the time, against 58.0% to 64.7% for ChatGPT depending on the prompting method. Label 50 to 100 question-passage pairs from your own corpus and measure your grader's agreement with them before you rely on it.
Related is not the same as sufficient
The grading prompt in LangGraph's tutorial counts a document as relevant when it contains keywords or semantic meaning related to the question. By that standard the warranty passage in the worked example is related to a battery-warranty question, yet it cannot answer it. A lenient criterion lets the generator stretch a nearby fact into an answer. A strict one (does this passage contain the information needed?) rejects more passages and causes more searches. Choose the criterion deliberately and put one accepted and one rejected example in the grader prompt.
The corpus does not contain the answer
No rewrite can retrieve a passage that does not exist, so a loop that only knows how to rewrite spends its whole budget and then fails, or answers from weak evidence. Anthropic reports that its early research agents scoured the web endlessly for nonexistent sources. Give the loop a counter for consecutive misses and a distinct not-found result, and log the questions that end there, because they are a list of gaps in your content.
The model answers from memory and skips the search
Once search is optional, the model can decide that it already knows. For general knowledge that is the intended saving. For questions about your own policies, prices or code it produces a fluent answer with no source behind it. Anthropic's web search documentation notes that triggering can be steered through the system prompt. For a private corpus, name the topics that must always be looked up, require citations in the answer format, and treat an uncited policy answer as a failed check. A hybrid design that makes the first search mandatory removes the risk.
Simple questions get the expensive treatment
An agent with a search tool and no guidance tends to over-investigate. Anthropic describes early agents that spawned 50 subagents for simple queries, and it added explicit effort rules to the prompt, such as one agent and 3 to 10 tool calls for simple fact-finding. The Adaptive-RAG paper argues the same from the research side: handling simple queries with a multi-step method is unnecessary overhead. Send easy questions down the cheap path and keep the loop for the questions that need it.
Retrieved text can carry instructions
An agentic system reads whatever its searches return, and a web page or a shared document can contain text written to redirect a model. Single-shot RAG has the same exposure, but an agent that chooses its next action from what it has just read can be steered further, including into more tool calls. Treat every retrieved passage as data and never as instructions, keep tools that change things out of the search agent's toolset or behind approval, and restrict search to trusted sources where you can. Anthropic's web search tool, for example, accepts lists of allowed or blocked domains, and the LangGraph tutorial's grading prompt tells the grader to treat the document as data and ignore any instructions in it. That wording helps but is not a guarantee, so the other controls still matter.

When to use it, and when something simpler is enough

Use it when

  • Failure analysis of a single-shot pipeline shows questions that need facts from more than one passage or more than one source, and those questions matter to your users.
  • Users phrase questions differently from the documents, so the first query often misses and a rewrite in the corpus's vocabulary would hit.
  • The agent has several knowledge tools (an index, a database, web search) and the right one depends on the question.
  • A wrong answer is costly enough that a few extra seconds and several extra model calls per question are an acceptable price for checking the evidence.
  • You can record every query, grade and citation, and you have an evaluation set to show that each added step improves results.

Think twice when

  • Most questions are single-fact lookups that the single-shot pipeline already answers correctly on your evaluation set. The extra calls add cost and latency and nothing else.
  • There is a strict latency budget, as in voice or autocomplete, that a variable number of model calls cannot meet.
  • Retrieval fails because of the index itself: bad chunking, missing metadata or missing documents. Rewriting queries against a broken index repeats the failure at higher cost.

A simpler alternative. Single-shot RAG with a well-built retriever: hybrid search, a reranker and one fixed query-rewriting step before the search. It has one path, a predictable latency and far fewer ways to fail. It stops being enough when your failure analysis keeps finding questions that need a second search informed by the first, a choice between sources, or a check that the retrieved passages really contain the answer.

Key takeaways

  • Agentic RAG makes retrieval a tool the model calls, so the model decides whether to search, what to search for and whether to search again.
  • Query planning has three moves: rewrite the question into the corpus's vocabulary, decompose it into sub-queries, and route each query to the right source.
  • A similarity score ranks passages but does not say whether any of them answers the question, so grade retrieved passages and pass on only the ones that survive.
  • Every correction path needs a cap enforced in code and an honest not-found exit, because no rewrite can retrieve an answer the corpus does not contain.
  • Each added decision costs model calls and latency, so start from single-shot RAG and add planning, grading and retries only where your evaluation shows failures that they fix.

Example 1 of 5

Azure AI Search agentic retrieval: query planning, source selection and one graded retry in a managed service

MicrosoftDocumented in official docs

Microsoft's documentation for Azure AI Search describes agentic retrieval, a multi-query pipeline for complex questions in chat and copilot apps. The overview page explains the workflow and billing, the retrieve how-to shows a request and its response, and the reasoning-effort page says how much model processing each level adds. The overview says the same service underpins Foundry IQ, the knowledge layer for agents in Microsoft Foundry. [12][13][14]

The problem

One search query handles some questions badly, and the overview names them: questions with several asks at once (its example is a hotel near the beach, with airport transportation, within walking distance of vegetarian restaurants), questions that depend on earlier turns of the conversation, queries that need rewriting or paraphrasing to match the content, and spelling mistakes. The reasoning-effort page adds a fifth case: a first pass whose results are not relevant enough. Without a managed service, a team typically writes and operates its own planning, fan-out, checking and merging code.

Where this topic fits

Query planning, source selection and parallel execution sit inside the search service, between the application and its indexes. At the medium effort level a relevance check and one follow-up pass sit there too. The application calls a knowledge base with the query and the conversation history. The knowledge base plans subqueries, runs them against its knowledge sources and returns merged grounding data. Writing the final answer stays with the application's own model, or with the service's answer synthesis option, which the documentation marks as preview.

How it is applied, step by step

  1. The application sends a retrieve request to a knowledge base, with the conversation as messages and the knowledge sources to query. It can set a retrieval reasoning effort on the request or use the knowledge base default, which is low.
  2. At low and medium effort the knowledge base passes the query and conversation history to an LLM, which selects knowledge sources and writes focused subqueries. At minimal effort this planning step is skipped and the sources are searched directly. At auto, the service starts with a lightweight pass and moves on to LLM planning, up to medium, only when that pass does not give enough grounding.
  3. All subqueries run at the same time against the selected sources, as keyword, vector or hybrid searches. The semantic ranker reranks the results of each subquery, and references are kept so that answers can cite them.
  4. At medium effort, after the first search, a semantic classifier judges whether the retrieved documents are relevant enough. If they are not, the service runs one follow-up iteration with a revised query plan, which can reuse the same sources or pick different ones. The documentation says there is only one retry, because each iteration adds latency and cost.
  5. The service merges the best results into one response. On request it also returns the source references and an activity log of the steps it ran.
  6. The application passes the grounding data to its model to write the answer, and can read the activity log to see which subqueries were issued and how many tokens each step used.

Why this approach fits

The questions the overview lists are the ones where a single query cannot cover every part. Planning all subqueries up front lets the service run them in parallel, so the wider coverage costs one planning call plus the slowest subquery, and not one round trip per sub-question. Medium effort adds the grade-and-retry idea of this lesson in a bounded form: a classifier checks the first results and at most one revised pass follows. Because this lives in the service, every application that uses the knowledge base gets the same behaviour, and the activity log shows which plan was executed, which makes a bad plan visible.

Limitation or tradeoff

The overview states that agentic retrieval adds latency compared with a single-query pipeline, and that it is billed by tokens from two services: the search service for subquery execution and ranking, and Azure OpenAI for query planning. LLM-based query planning, the non-minimal effort levels and answer synthesis are preview capabilities. The generally available API version covers only minimal, extractive retrieval, and Microsoft's notice says preview features are not recommended for production workloads. The correction loop is shallow by design: medium effort retries once, and it is available only in select regions. The page gives no accuracy figures for the classifier, so measure its judgement on your own questions. A question that needs a longer chain of dependent searches is best handled by the calling agent issuing further retrieve calls.

What the sources document

  • The overview defines agentic retrieval in Azure AI Search as a multi-query pipeline designed for complex questions posed by users or agents in chat and copilot apps, intended for RAG patterns and agent-to-agent workflows. [12]
  • Retrieval reasoning effort sets how much LLM processing happens. Minimal skips LLM query planning and searches the knowledge sources directly. Low, the default, runs a single pass of LLM-based query planning and knowledge source selection and fans the subqueries out. Uber Genie: query-optimising and source-picking agents for an on-call copilot

UberDocumented in an engineering article

Uber's engineering blog (May 2025) describes Enhanced Agentic RAG, a redesign of the answer pipeline in Genie, the company's internal on-call copilot. Genie answers questions in Slack help channels and cites Uber's internal documentation. [15]

The problem

Genie was meant for Slack channels where wrong security and privacy advice is costly. Subject matter experts curated a golden set of more than 100 test questions, and Genie was connected to more than 40 engineering security and privacy policy documents. The article reports that many answers were incomplete, inaccurate or missed relevant information, and that the experts judged the quality too low for a broader rollout. Two of the redesign's agents address retrieval problems: queries that are ambiguous or lack context, and finding which of the many policy documents is likely to hold the answer.

Where this topic fits

The agents sit before and after a conventional retrieval step. Two pre-retrieval agents plan the search: one repairs the query and one narrows which documents to search. Retrieval itself is a vector search plus a BM25 keyword search. A post-processing agent then tidies the retrieved chunks, and a single LLM call writes the answer.

How it is applied, step by step

  1. Offline, policy documents are loaded from Google Docs with a custom loader and enriched by an LLM with summaries, frequently asked questions and keywords, which become chunk metadata and a list of documents.
  2. The Query Optimizer agent rewrites a query that is ambiguous or lacks context, and breaks a complex query into simpler ones.
  3. The Source Identifier agent reads the document list (titles, summaries and FAQs), guided by few-shot examples, and picks the subset of policy documents most likely to hold the answer.
  4. A vector search and a BM25 retriever both run, and the final retrieval output is the union of their results.
  5. The Post-Processor agent removes duplicate chunks and orders the rest by their position in the original documents.
  6. The original question, the optimised queries and the processed context go to the answer-generating LLM.
  7. An LLM judge scores each answer from 0 to 5 against the experts' reference answers, so a change to the pipeline can be evaluated in minutes.

Why this approach fits

Policy questions fail in two specific ways that planning addresses: the question is underspecified, and the right answer lives in one of dozens of similar documents. Repairing the query and choosing the documents before searching attacks both. It does so with a small, fixed number of extra model calls in a known order, which keeps response time predictable in a chat channel. The golden set and the judge let the team tell whether each added component earned its place.

Limitation or tradeoff

This is the planning half of agentic RAG without the feedback half. The agents run in a fixed sequence, and nothing in the described pipeline grades the retrieved chunks and triggers another search. The authors' own next steps include an iterative Chain-of-RAG approach for multi-hop questions and a self-critique agent after answer generation. The reported gains are relative figures for one team's policy questions. The article does not define "acceptable" or "incorrect advice", or say whether experts or the LLM judge produced the numbers, so they do not predict results on another corpus. It credits the move from traditional RAG to its enhanced agentic approach, which also changed document loading and enrichment, so the gain cannot be assigned to the agents alone.

Example 3 of 5

Claude Research: a lead agent and parallel subagents running multi-step web search

AnthropicDocumented in an engineering article

Anthropic's engineering article How we built our multi-agent research system (June 2025) describes the Research feature in Claude, which searches the web, Google Workspace and connected integrations to work on open-ended questions. [16]

The problem

Research questions are open-ended: the steps cannot be listed in advance, and each finding changes what is worth looking for next. The article contrasts this with traditional RAG, which it describes as static retrieval: fetching the chunks most similar to the input query and answering from them.

Where this topic fits

Multi-step retrieval is the whole product. A lead agent plans the research and delegates parts of it. Each subagent runs its own search loop in its own context window. A final citation step attaches sources to the report. In this curriculum's terms it is agentic RAG combined with Orchestrator-Workers.

How it is applied, step by step

  1. The lead agent analyses the user's question, develops a strategy, saves its plan to memory and creates subagents, each with a specific research task.
  2. Each subagent runs web searches on its own. After each tool result it uses interleaved thinking to evaluate what it found before it chooses the next query.
  3. Following the prompt guidance, subagents start with short, broad queries, look at what is available and then narrow their focus.
  4. Subagents return their findings to the lead agent, which synthesises them and decides whether more research is needed. If so, it creates more subagents or changes its strategy.
  5. Once enough information has been gathered, the system leaves the research loop and passes the findings to a citation agent, which identifies the specific source locations for the claims in the report.
  6. The report is returned to the user with its citations.

Why this approach fits

Open-ended questions reward breadth, and independent lines of enquiry can run at the same time. Giving each subagent its own context window keeps raw search results out of the lead agent's context, so the lead agent reasons over findings and not over pages. The thinking step after every search is grading in an informal form: the subagent judges what it retrieved before it spends another search.

Limitation or tradeoff

The cost is high. The article reports that agents use about 4 times the tokens of a chat interaction and multi-agent systems about 15 times, and concludes that the approach needs tasks valuable enough to pay for it. It lists early failures that are specific to autonomous search: 50 subagents spawned for simple queries, endless searching for sources that did not exist, and a preference for search-optimised content farms over authoritative sources. The headline quality figure comes from Anthropic's internal research evaluation, so it cannot be compared with public benchmarks.

Corrective RAG (CRAG): a retrieval evaluator that triggers correction before generation

Documented in a paper

Corrective Retrieval Augmented Generation (Yan, Gu, Zhu and Ling; arXiv, version 3 dated October 2024) is a research system that adds a relevance evaluator and corrective actions to a standard RAG pipeline. Section 4 of the paper describes the method and section 5 reports experiments on four public datasets. [11]

The problem

RAG depends on the retrieved documents being relevant, and the generator has no defence when they are not. The abstract frames the research question as how the model behaves if retrieval goes wrong. Retrieval from a fixed corpus returns its best matches even when none of them answers the question, and a relevant document still contains sentences that have nothing to do with it.

Where this topic fits

The evaluator sits between retrieval and generation. It scores each retrieved document against the question. The scores select one of three actions, and the action decides what knowledge the generator finally sees: refined internal documents, refined web search results, or both.

How it is applied, step by step

  1. Documents are retrieved for the question in the usual way.
  2. A fine-tuned T5-large model, the retrieval evaluator, scores each question-document pair for relevance.
  3. If at least one document scores above an upper threshold, the action is Correct. The documents are split into smaller strips, each strip is scored, irrelevant strips are dropped and the rest are joined again.
  4. If every document scores below a lower threshold, the action is Incorrect. The retrieved documents are discarded, the question is rewritten into a keyword query, and a web search supplies replacement knowledge, which is refined in the same way.
  5. In all other cases the action is Ambiguous, and the refined internal knowledge and the web knowledge are combined.
  6. The generator answers the question from the knowledge that the chosen action produced.

Why this approach fits

The correction happens before generation, when it is cheapest: a bad retrieval is replaced instead of being turned into a fluent wrong answer. The evaluator is a small dedicated model, so grading every document does not cost a large-model call each time. The third, ambiguous outcome avoids forcing a yes-or-no decision when the evaluator is unsure, which limits the damage of a wrong grade.

Limitation or tradeoff

The authors name the main one themselves: the method requires fine-tuning an external retrieval evaluator, and removing that dependency is left to future work. The thresholds were set empirically and differ between datasets, so they would need tuning on any new corpus. The design applies one round of correction and does not loop. The web fallback adds latency and brings in sources nobody has vetted. The results use 7-billion-parameter generators on four benchmarks, so the size of the gains will not carry over to current models.

What the sources document

  • The retrieval evaluator is initialised from T5-large and fine-tuned, and it assesses the relevance of each retrieved document to the question individually. The paper contrasts its size, 0.77 billion parameters, with the 7-billion-parameter critic used by Self-RAG. [11]
  • A retrieval is assumed Correct when the confidence score of at least one retrieved document is above the upper threshold, Incorrect when the scores of all retrieved documents are below the lower threshold, and Ambiguous in the remaining cases, where both kinds of knowledge are combined. [11]
  • For web search, the inputs are rewritten into keyword queries by ChatGPT, a commercial web search API is used, and authoritative pages such as Wikipedia are preferred. For knowledge refinement, documents are split into strips, each strip is scored by the evaluator, and irrelevant strips are filtered out. [11]
  • With SelfRAG-LLaMA2-7b as the generator, Table 1 reports CRAG against standard RAG at 59.8 versus 52.8 accuracy on PopQA, 74.1 versus 59.2 FactScore on Biography, 75.6 versus 39.0 accuracy on PubHealth and 68.6 versus 53.2 accuracy on Arc-Challenge. [11]
  • On PopQA the T5-based evaluator reached 84.3% accuracy in judging retrieval quality, against 58.0% for ChatGPT, 62.4% for ChatGPT with chain of thought and 64.7% for few-shot ChatGPT. The conclusion states that fine-tuning an external retrieval evaluator is inevitable in this approach. [11]

Claude Code: agentic search over a codebase with file tools instead of a prebuilt index

AnthropicDocumented in official docs

Claude Code is Anthropic's coding agent. Its documentation describes how it gathers context with search tools, and Anthropic's engineering article on context engineering (September 2025) explains the retrieval design behind it. [17][18][19]

The problem

To fix a bug, the agent has to find the few relevant files among everything in a repository. Code changes constantly, so an index built earlier can be out of date. The question the agent needs to ask, such as where a function is called or which test covers a code path, often becomes clear only after it has read something else.

Where this topic fits

Retrieval is the first phase of the documented agentic loop: gather context, take action, verify results. The retrieval tools are a search for files by name pattern, a search of file contents by regular expression, and a file read. A small amount of context, the project's CLAUDE.md file, is loaded up front. Everything else is fetched when the model asks for it.

How it is applied, step by step

  1. At the start of a session the project's CLAUDE.md file is placed in context.
  2. Given a task, the model chooses a search: files whose names match a pattern, or lines that match a regular expression.
  3. The results are file paths or matching lines. The model decides which files to read in full.
  4. What it reads shapes the next search. A typical sequence finds a function's definition, then searches for the places that call it.
  5. Where the Grep and Glob tools are enabled, a rejected pattern or a cut-short result list is reported in the tool result, and the model corrects the pattern or narrows it.
  6. For broad exploration the work can go to a subagent with its own context window, which returns a summary.
  7. The agent then edits and runs the tests. A failing test sends it back to searching.

Why this approach fits

Searching the live files means there is no index to go stale. Code is full of exact identifiers, which a pattern search finds precisely and which similarity search can blur. Each result supplies the name needed for the next query, so the task is multi-hop by nature and suits a loop. The tools also report their own failures, such as a rejected pattern or a truncated list, which gives the model what it needs to correct a search.

Limitation or tradeoff

Anthropic's article states the tradeoff directly: runtime exploration is slower than retrieving precomputed data, and it takes careful engineering to give the model the right tools and heuristics. Without them an agent can waste context by misusing tools, chasing dead ends or missing key information. Pattern search also needs a name to search for, so it is weak for a concept whose identifier you do not know. The same article suggests that a hybrid of up-front retrieval and exploration may suit less dynamic content, such as legal or finance work, better.

What the sources document

  • The Claude Code documentation describes three phases (gather context, take action, verify results), lists a search tool category that finds files by pattern and searches content with regex, and says Claude decides what each step requires based on what it learned from the previous step. [18]
  • The tools reference says that on macOS, Linux and WSL Claude Code leaves the Glob and Grep tools out of the default tool set and Claude searches with find and grep through the Bash tool. [19]

4Common mistakes

  1. Letting the rewrite loop run with no cap on searches or failed attempts.

    Why it causes problems
    A question the corpus cannot answer cycles through rewrites until a framework limit or a timeout stops it. Every cycle costs a search, several grader calls and an agent call, and the user waits for an answer that never improves.
    How to recognise it
    Traces with many near-identical queries for one question, and latency percentiles far above the median.
    How to fix it
    Count searches and consecutive misses in code, stop at a small cap such as two failed attempts, and return a distinct not-found status that the interface can show honestly.

  2. Describing the retrieval tool in one vague line such as "searches documents".

    Why it causes problems
    The model cannot tell when the tool applies or how to phrase a query. It either skips the search or pastes the user's whole message in as the query, which reproduces single-shot RAG at a higher cost.
    How to recognise it
    Logged queries that are identical to the user's message, or policy questions answered with no tool call at all.
    How to fix it
    State what the corpus covers, what it does not cover, what a good query looks like and what comes back. Review a sample of logged queries after every change to the description.

  3. Trusting the grader without measuring it.

    Why it causes problems
    A grader that is too strict turns answerable questions into not-found results and extra searches. One that is too lenient waves distractors through, and the answer then looks checked when it is not.
    How to recognise it
    A not-found rate that jumps after a grader prompt change, or wrong answers whose cited passages are only loosely related to the question.
    How to fix it
    Label a set of question-passage pairs from your own corpus, compute how often the grader agrees with the labels, and repeat the measurement whenever the grader's model or prompt changes.

  4. Appending every retrieved passage to the context, whether or not it passed grading.

    Why it causes problems
    Each search adds text that is resent on every later model call. Irrelevant passages cost tokens on every step and give the generator material to build a wrong answer from.
    How to recognise it
    Input tokens that climb with each search, and answers that quote passages the grader rejected.
    How to fix it
    Return only the passages that passed the grade, trimmed to the relevant span and labelled with their ids, and keep rejected passages in the trace instead of the prompt.

  5. Adding agents to compensate for a poor index.

    Why it causes problems
    If chunks cut tables in half or lack the terms people search for, every rewritten query still searches the same broken index. The loop multiplies cost without raising the ceiling on quality.
    How to recognise it
    Ideal queries written by hand also fail to retrieve the right chunk for the failing questions.
    How to fix it
    Fix ingestion first. In the Uber example the team changed its document loader and added generated summaries, FAQs and keywords as metadata in the same project that introduced the agents.

  6. Evaluating only the final answer.

    Why it causes problems
    A correct answer can hide a wasteful path, and a wrong answer does not show whether planning, retrieval, grading or generation failed, so you cannot tell what to fix.
    How to recognise it
    A dashboard with one accuracy number and no per-step data, and debugging sessions that begin by re-running the question by hand.
    How to fix it
    Record every query, the passages returned, each grade and the citations. Measure retrieval and grading separately from answer quality, and track searches per question as a cost metric.

python
import re

from agentic_rag import DOCS, MAX_MISSES, MAX_SEARCHES, Q1_REPLIES, Q2_REPLIES, search


def unsupported_numbers(answer, cited):
    """Numbers that appear in the answer but in none of the cited passages."""
    cited_numbers = {n for doc_id in cited for n in re.findall(r"\d+", DOCS.get(doc_id, ""))}
    return [n for n in re.findall(r"\d+", answer) if n not in cited_numbers]


def run_checked(replies, relevant, max_answer_retries=1):
    evidence, searches, graded, misses, rejections = [], 0, 0, 0, 0
    for kind, text, *cited in replies:
        if kind == "answer":
            problems = [d for d in cited[0] if d not in evidence] + unsupported_numbers(text, cited[0])
            if not problems:
                return {"status": "answered", "answer": text, "cited": cited[0],
                        "searches": searches, "graded": graded, "rejections": rejections}
            rejections += 1
            print(f"  rejected answer {rejections}: unsupported {problems}")
            if rejections > max_answer_retries:
                return {"status": "ungrounded", "answer": None, "cited": [],
                        "searches": searches, "graded": graded, "rejections": rejections}
            continue                      # a live loop would send `problems` back to the model here
        hits = search(text)
        searches, graded = searches + 1, graded + len(hits)
        kept = [doc_id for doc_id, _ in hits if doc_id in relevant]
        evidence = evidence + [doc_id for doc_id in kept if doc_id not in evidence]
        misses = 0 if kept else misses + 1
        if misses == MAX_MISSES or searches == MAX_SEARCHES:
            break
    return {"status": "not_found", "answer": None, "cited": [],
            "searches": searches, "graded": graded, "rejections": rejections}

Size a retry budget from a hit rate and a latency limit

Part 2. One attempt costs 0.9 + 0.2 + 0.5 = 1.6 s. The worst case uses 3(r+1)3(r + 1)3(r+1) attempts and then writes the answer.

  • 0 retries: 3 × 1.6 + 1.5 = 6.3 s
  • 1 retry: 6 × 1.6 + 1.5 = 11.1 s
  • 2 retries: 9 × 1.6 + 1.5 = 15.9 s

Part 3. One retry per hop. It nearly doubles the success chance, from 42.2% to 82.4%, and its worst case of 11.1 s fits inside the 12 s limit. A second retry would add 13 percentage points but its worst case of 15.9 s breaks the limit.

Part 4. A hop uses one search, plus a second with probability 0.25, so 1.25 searches on average. Three hops use 3 × 1.25 = 3.75 searches. The expected latency is 3.75 × 1.6 + 1.5 = 7.5 s, well below the worst case, which is why you should report both numbers.

Part 5. Two reasons, from any of these:

  • If the corpus does not contain the fact, every attempt fails. The failures are perfectly correlated and no number of retries helps.
  • A rewritten query is often close to the original, so it tends to retrieve the same passages and fail in the same way.
  • The grader can reject a relevant passage. A retry then repeats a search that had already succeeded, and the 75% figure, which was measured on retrieval alone, does not describe the graded loop.
  • A later hop depends on the earlier one. A hop that "succeeds" with the wrong passage sends every later query in the wrong direction.

What to measure: the success rate of the second attempt on the questions where the first attempt failed. If it is far below 75%, the real benefit of a retry is much smaller than the formula says. Measuring the share of failures that end as not-found because the corpus lacks the answer tells you how much of the remaining gap is a content problem.

Check your answer

  • Did you get 42.2%, 82.4% and 95.4% for zero, one and two retries?
  • Are your worst-case latencies 6.3 s, 11.1 s and 15.9 s?
  • Does your choice in part 3 name both the gain in success chance and the latency limit?
  • Is your expected latency for one retry 7.5 s, from 3.75 expected searches?
