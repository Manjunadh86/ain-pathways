n8n AI Agents

n8n is a workflow automation platform in which a trigger starts a chain of connected nodes that move data between services. Its AI Agent node adds a language model that decides which connected tools to call, with optional memory and human approval before sensitive actions.

1Overview

Why it matters

Most of an agent project is not the model call. Something has to start the run (a chat message, a web request, a timer), fetch data from business systems with stored credentials, hand a bounded task to a model, write the result somewhere, and pause for a person before anything irreversible happens. n8n packages that plumbing as visual nodes, so a small team can ship the surrounding workflow without writing and hosting all of the glue code itself.

The choices that matter are mostly operational. Which tools sit behind an approval step decides whether a wrong model decision becomes a wrong refund. Where memory is stored decides whether a conversation survives in production. Running n8n Cloud or running it yourself decides who looks after the server and where customer data is processed. Operations teams, forward deployed engineers and developers who inherit a workflow built by a colleague all need to read these settings with confidence.

Key terms

Workflow
A set of connected nodes in n8n that starts at a trigger and runs from left to right, passing data from each node to the next.
Trigger node
A node that starts a workflow when something happens, such as a web request, a chat message or a schedule. A workflow that should run on its own needs one.
Item
One unit of data passed between nodes. Items travel as a list of objects, and each object keeps its fields under a json key.
Expression
A short piece of code written between double curly braces, such as a field lookup, that n8n evaluates when the node runs.
AI Agent node
An n8n node that sends a prompt and a list of tools to a chat model and runs the tools the model chooses, repeating until it has an answer or reaches its iteration limit.
Sub-node
A node that plugs into a root node such as the AI Agent node and supplies one capability, for example the chat model, the memory or a tool.
Tool
A sub-node the agent may call to get information or take an action, such as an HTTP request, another n8n workflow or a connected app.
Session key
The identifier a memory node uses to decide which stored conversation history belongs to the current chat.
Human review
An n8n setting that pauses an AI Agent's tool call and asks a person to approve or deny it, in the chat or in a messaging or email service, before the tool runs.
Publish
The n8n action that lets a workflow run automatically from its trigger. New workflows are unpublished, and older material may call this activating.

2Explanation

Introduction

In What Are AI Agents? you met the difference between a workflow, where code fixes the order of steps, and an agent, where a model chooses the next step. n8n is a tool in which you build both on one canvas. You draw a workflow as boxes called nodes joined by lines, and any one of those boxes can be an AI agent.

A kitchen is a fair comparison. A workflow is a recipe card: fetch the order, check the stock, send the confirmation. An agent is a cook who is handed a goal and a set of tools and decides what to do next. Useful kitchens, and useful AI systems, use recipe cards for the routine parts and ask for the cook's judgement only where the steps cannot be written down in advance.

Every n8n workflow starts with a trigger node, which starts the workflow when something happens: a chat message arrives, a web request is received, a timer fires. The nodes after it fetch, transform or send data. Between nodes, data travels as a list of items, and each node works on every item it receives. The AI Agent node is the node whose job is a decision loop (the loop is explained in The Agent Loop). It sends your prompt and a list of tools to a chat model, runs the tool the model picks, and repeats.

This lesson follows the diagram from left to right. It covers triggers and nodes, the AI Agent node with its tools and memory, human approval steps, and the choice between n8n Cloud and running n8n yourself. The worked example is a small Python model of an approval-gated agent, so you can trace the numbers without a model account. The five real examples come from n8n's own documentation and from customer case studies that n8n publishes, so read the figures in them as statements by those companies.

How it works

Workflows, triggers and nodes

A workflow is a set of nodes joined by connections. Each node does one job: it starts the workflow, fetches or sends data, or processes it. Trigger nodes start a workflow when something happens, and a workflow that should run on its own needs one. Three triggers cover most agent projects:

TriggerStarts a run whenDetails from the documentation
Webhook (opens in a new tab)an HTTP request arrivesA test URL shows data in the editor; a production URL is registered when you publish, and its runs appear in the Executions tab. Authentication: Basic, Header, JWT or none. Default maximum payload: 16 MB.
Schedule Trigger (opens in a new tab)a timer firesIntervals from seconds to months, or a cron expression. You must save and publish. It uses the workflow timezone, else the instance timezone.
Chat Trigger (opens in a new tab)a chat message arrivesHosted chat uses n8n's built-in interface; embedded chat uses n8n's widget or your own. Every message executes the workflow. It must connect to an agent or chain.

You can run a workflow by hand (opens in a new tab) with Execute Workflow while you test. New workflows are unpublished, and a workflow with a trigger or webhook node only runs automatically once you publish it (older tutorials call this activating).

Between nodes, data travels as an array of items (opens in a new tab). Each item keeps its fields under a json key (files go under binary), and a node that receives several items processes each one in turn. An expression such as {{ $json.order_id }} reads a field of the current item.

json
[
  { "json": { "order_id": "1042", "total": 19.99 } },
  { "json": { "order_id": "1043", "total": 5.5 } }
]

The AI Agent node

The AI Agent node (opens in a new tab) lets you build an agent: you connect a chat model and one or more tools, and the agent decides which tools to call to finish the task. At least one tool is required. The agent is the central node, and the model, memory and tools are sub-nodes plugged into it. In current versions every AI Agent node works as a Tools Agent (the old agent-type setting is deprecated from n8n 1.82.0), which uses the model's native tool calling (see Tool Calling). The settings map onto the loop from The Agent Loop:

SettingWhat the documentation saysLoop counterpart
PromptTake it from the previous node (a field called chatInput), or "Define below" with text or an expressionthe task
System MessageA message sent to the agent before the conversation startsinstructions
Chat model sub-nodeThe model that decides; providers listed include OpenAI, Groq, Mistral Cloud, Anthropic and Azure AI Foundryreason
Tool sub-nodesWhat the agent may callact
Max IterationsHow many times the model may run to try to produce a good answer; defaults to 10step limit
Return Intermediate StepsInclude the steps the agent took in the outputtrace

The Tools Agent page (opens in a new tab) also covers output parsers, streaming and the Human review setting below. The pages read for this lesson do not say what the node returns when Max Iterations is reached, so test that on your own version.

Tools

n8n's tool overview (opens in a new tab) highlights three: the Call n8n Workflow tool, which loads any n8n workflow as a tool, a Custom Code tool, and the HTTP Request tool for calling a website or API. Each tool has a description, which the Call n8n Workflow tool (opens in a new tab) page says tells the agent when to use it.

Tools need arguments the model should choose. The $fromAI() function (opens in a new tab) marks a tool field as one the AI fills in. Its arguments are a key, an optional description, an optional type (string, number, boolean or json) and an optional default, and it only works on tools connected to an AI Agent node:

text
{{ $fromAI('amount', 'Refund amount in the order currency', 'number') }}

The model reads the key and the description, so write them as you would a tool parameter in code (see Designing Tools for Agents). n8n's AI page (opens in a new tab) also says you can enable MCP on your instance so that clients such as Claude can call your workflows (see Model Context Protocol).

Memory

The model remembers nothing between executions. A memory sub-node stores the conversation and loads it back (the Tools Agent page says to attach one for an ongoing conversation). Two settings matter:

  • Session key picks which stored conversation belongs to the current chat, so chats with different keys keep separate histories. With the Chat Trigger, n8n recommends connecting the trigger and the agent to the same memory sub-node.
  • Context window length is the number of previous interactions to consider, so only recent history reaches the model. See Agent Memory for the wider design space.

Where the history lives matters in production. Simple Memory (opens in a new tab) does not work in an active production workflow when n8n runs in queue mode (explained below), because calls may reach different workers. The Postgres Chat Memory (opens in a new tab) node stores history in a table it creates, and several Postgres memory nodes in one workflow share the same memory by default unless you give them different session IDs.

Human approval

Two mechanisms put a person in the loop. The first works inside the agent: in the Tools connector you add a Human review step, choose a channel and place the sensitive tools behind it. The documentation (opens in a new tab) lists nine channels (n8n Chat, Slack, Discord, Telegram, Microsoft Teams, Google Chat, WhatsApp Business Cloud, Gmail and Microsoft Outlook). On approve, the tool runs with the input the AI chose. On deny, the action is canceled and the AI is informed of the rejection. In the approval message, $tool.name is the tool's node name and $tool.parameters holds the values the AI proposed, so the reviewer sees exactly what would be sent. The channel can differ from the user's: a customer chats in n8n Chat while approvals go to Slack. The page advises including the tool setup and the human review steps in the system prompt, and it is wise to say what the agent should do after a denial. See Human-in-the-Loop for the design questions behind this.

The second mechanism sits in the ordinary workflow. The Wait node (opens in a new tab) pauses an execution and resumes after a time interval, at a set time, on a webhook call or when a form is submitted. In webhook-call mode it provides a resume URL, unique to each execution, through $execution.resumeUrl.

Running n8n: Cloud or self-hosted

The deployment page (opens in a new tab) frames the first decision as Cloud or self-hosted.

The code is published under the Sustainable Use License (opens in a new tab), which allows use for your own internal business purposes and for non-commercial or personal use. If you plan to resell n8n or host it for other companies, read it first. To try self-hosting, the Docker install page (opens in a new tab) gives these commands. The page is marked outdated in favour of the Docker Compose install page, but it still lists this single-container command, enough for a throwaway test, and it recommends Cloud if you are not experienced at running servers. The named volume keeps your data when the container is replaced, and GENERIC_TIMEZONE sets the zone that schedule nodes use:

bash
docker volume create n8n_data

docker run -it --rm \
  --name n8n \
  -p 5678:5678 \
  -e GENERIC_TIMEZONE="<YOUR_TIMEZONE>" \
  -e TZ="<YOUR_TIMEZONE>" \
  -e N8N_ENFORCE_SETTINGS_FILE_PERMISSIONS=true \
  -v n8n_data:/home/node/.n8n \
  n8nio/n8n

For more load, queue mode (opens in a new tab) splits the work. The main instance handles timers and webhook calls and creates an execution without running it, Redis holds the queue of pending execution IDs, and workers pick them up. The documentation advises against SQLite in queue mode, so use a database such as PostgreSQL. Binary data cannot use filesystem storage there; the page points to S3, a paid feature on the deployment page.

n8n's AI page (opens in a new tab) says you can inspect every execution to see the prompt sent, the model's response and what happened next, and that rule-based nodes can constrain inputs and validate outputs. With the Chat Trigger's no-authentication option, anyone with the URL can run your agent and its tools. See LLM and Agent Observability for tracing in general.

Worked example: Trace one chat message through an agent whose refund tool needs approval

The task: a customer writes "Refund order 1042 in full." The agent has two tools. get_order only reads a record, so it runs freely. issue_refund moves money, so it sits behind a Human review step. The n8n side of this agent is configured like this (each setting is described on the documentation pages in this lesson's sources):

PartSetting
Chat TriggerHosted chat, so every message starts one execution
AI AgentPrompt "Take from previous node automatically"; Max Iterations left at the default of 10
Tool get_orderHTTP Request tool pointing at your order API; the description says what it returns
Tool issue_refundHTTP Request tool whose amount field is {{ $fromAI('amount', 'Refund amount', 'number') }}; placed behind Human review in Chat
System message"issue_refund needs a reviewer's approval. If it is denied, tell the customer no refund was made and do not retry."

To trace the numbers without a model, the Python below models that behaviour. It is our simplification, not n8n code: the model's replies are scripted, so every run gives identical output. It needs only Python 3.8 or later. Save it as agent_model.py.

python
import json

ORDERS = {"1042": {"customer": "ana@example.com", "total": 19.99, "status": "delivered"}}
NEEDS_APPROVAL = {"issue_refund"}   # tools placed behind a Human review step
DEFAULT_MAX_ITERATIONS = 10         # the documented default of the AI Agent node


def get_order(order_id):
    return ORDERS[order_id]


def issue_refund(order_id, amount):
    return {"order_id": order_id, "refunded": amount}


TOOLS = {"get_order": get_order, "issue_refund": issue_refund}


def call_tool(name, args, approve):
    """Run a tool, asking a person first when the tool is gated."""
    if name in NEEDS_APPROVAL:
        print(f"  review: The AI wants to use {name} with {json.dumps(args)}")
        if not approve(name, args):
            return "DENIED: the reviewer rejected this action and it was not run."
    return json.dumps(TOOLS[name](**args))


def run_agent(chat_input, replies, approve, max_iterations=DEFAULT_MAX_ITERATIONS):
    context = [chat_input]
    for model_calls, reply in enumerate(replies, start=1):
        if model_calls > max_iterations:
            return {"status": "max_iterations", "output": None, "model_calls": max_iterations}
        print(f"model call {model_calls}: sees {len(context)} messages")
        if "final" in reply:
            return {"status": "finished", "output": reply["final"], "model_calls": model_calls}
        observation = call_tool(reply["tool"], reply["args"], approve)
        print(f"  result: {observation}")
        context = [*context, reply, observation]
    return {"status": "script_ended", "output": None, "model_calls": len(replies)}


REFUND = {"tool": "issue_refund", "args": {"order_id": "1042", "amount": 19.99}}
LOOKUP = {"tool": "get_order", "args": {"order_id": "1042"}}
APPROVED = [LOOKUP, REFUND, {"final": "Refunded 19.99 for order 1042."}]
DENIED = [LOOKUP, REFUND, {"final": "I could not refund order 1042: a reviewer denied it."}]
TASK = "Refund order 1042 in full."

print("== approved ==")
print(run_agent(TASK, APPROVED, lambda name, args: True))
print("== denied ==")
print(run_agent(TASK, DENIED, lambda name, args: False))
print("== limit of 2 ==")
print(run_agent(TASK, APPROVED, lambda name, args: True, max_iterations=2))

Run python3 agent_model.py. The output is:

What to notice:

  • Model calls, not executions. One chat message was one execution, but the agent made three model calls in it. The context grew from 1 message to 3 to 5 because each tool result is added before the next call. Max Iterations caps the model calls per execution.
  • Only the gated tool asked for permission. get_order ran with no review, and issue_refund produced one review request showing the tool name and the parameters, like the $tool.name and $tool.parameters message in the documentation.
  • A denial is information. In the second run the refund did not happen. The tool result tells the model so, and the model's last reply explains it to the customer. The documentation says the AI is notified of a rejection.
  • A low limit can end a run after a side effect. With a limit of 2, the refund ran and the run stopped with status max_iterations before any reply. What the real node returns at its limit is not stated on the pages read, so test it.
  • Budgeting. A six-message conversation is six executions. If each needs three model calls that is 18 calls, and the worst case under the default limit is 6 x 10 = 60.

Edge cases and limitations

A low Max Iterations can stop a run after a side effect
In the worked example a limit of 2 lets the refund run and then ends the run with no reply to the customer. The AI Agent node documents Max Iterations as the number of times the model runs, with a default of 10, but the pages read for this lesson do not say what the node returns when the limit is hit. Test the limit on your version with a harmless tool, and make write tools safe to repeat or easy to check.
Only the tools behind Human review are gated
Human review applies to the tools you place in the review step. A tool left outside runs as soon as the model chooses it, including a second tool that can do the same harm another way. When a reviewer denies, the AI is told and may try a different path. Gate every tool that can cause the harm, and describe the review steps in the system prompt, as the documentation advises, including what to do after a denial.
Simple Memory breaks in queue mode
The documentation says that when n8n uses queue mode, the Simple Memory node does not work in an active production workflow. Moving from one process to workers can therefore make an agent forget a conversation that worked in testing. Use a persistent memory node such as Postgres Chat Memory, and give separate conversations separate session keys, because Postgres memory nodes in one workflow share the same memory by default.
Every chat message is one execution
The Chat Trigger documentation warns that every message to it executes the workflow. A six-message conversation is six executions, and each execution can run the model up to Max Iterations times, which is 60 model calls in the worst case at the default of 10. Budget executions and model calls separately, and check how your plan counts executions.
An unpublished workflow does nothing
Workflows start unpublished, and schedule and webhook triggers only run automatically after you publish. A test webhook URL is not the production URL: the test URL shows data in the editor, while production runs appear only in the Executions tab. A team that tests with the test URL and never publishes finds that nothing runs overnight. Check the Executions tab, not the editor, to see what really ran.
A self-hosted schedule can run at the wrong hour
The Schedule Trigger uses the workflow timezone if one is set, and otherwise the instance timezone, whose default on self-hosted instances is New York time. A job set for 09:00 can run at an unexpected hour on a server in another region. Set the workflow timezone, and set GENERIC_TIMEZONE on the instance as the Docker page shows.

When to use it, and when something simpler is enough

Use it when

  • The job connects several business systems and needs only occasional judgement from a model, such as classifying, summarising or choosing among a few tools, so most nodes can stay deterministic.
  • People who are not full-time developers must build, read or change the workflow, and a visual canvas with a record of every execution helps them debug it.
  • Actions need a person's approval in the place that person already works, such as Slack, Teams, email or the chat window.
  • Customer data must be processed on infrastructure you control and your team can operate a server, which makes self-hosting a realistic option.

Think twice when

  • The agent needs intricate custom state, branching and automated tests inside a software repository. A code-first framework suits that better (see Choosing an Agent Framework).
  • The steps are fixed and known in advance. An agent adds cost, latency and variation where a plain workflow would be exact.
  • Nobody can patch, back up and monitor a server, and your data rules allow a hosted service. Self-hosting would add operational risk for no gain.

A simpler alternative. A fixed workflow with one model call: a trigger, deterministic nodes, a single chain-style call to the model for the judgement step, and a node that writes the result. Move to the AI Agent node when which tool to call, or how many times, depends on what earlier results show.

Key takeaways

  • An n8n workflow is a trigger followed by nodes that pass lists of items, and it runs automatically only after you publish it; a manual test run is not a production run.
  • The AI Agent node needs a chat model and at least one tool, and the model decides which tool to call, up to Max Iterations model runs per execution (10 by default).
  • Memory is a separate sub-node selected by a session key. Simple Memory does not work in an active production workflow in queue mode, so production agents need a persistent memory store.
  • Human review protects only the tools you place behind it. Approval runs the tool with the AI's chosen input, denial cancels it and tells the AI, and the system prompt should explain both.
  • n8n Cloud means n8n hosts and manages the instance, while self-hosting means you provide and manage the infrastructure in return for full control over deployment.
  • Use a plain workflow when the steps are fixed, and add an agent only where the sequence of tool calls cannot be written in advance.

Example 1 of 5

Delivery Hero routes account lockouts through manager approval and API nodes

Delivery HeroDocumented in a case study

n8n's customer case study on Delivery Hero describes a workflow that automates employee account recovery. The page does not mention AI. It is included because it shows the trigger, approval and action-node pattern that an agent workflow also relies on. The Wait node documentation describes the pause mechanism a typical implementation would use. [22][14]

The problem

Employees locked out of their accounts had to contact IT. The case study says there were around 800 such requests a month and that recovery took 35 minutes on average to complete. The remedy it describes is to take IT out of the approval and let the employee's direct manager approve the recovery.

Where this topic fits

This is a workflow with no agent: a request starts the run, an approval step sits in the middle, and action nodes call the systems that restore access. An agent workflow has the same shape. The difference is that the approval is attached to a tool call that a model chose, instead of to a fixed step.

How it is applied, step by step

  1. A lockout request starts the workflow. The page does not say which trigger node is used; a typical implementation would use a form or webhook trigger.
  2. The workflow asks the employee's direct manager to approve the recovery, instead of leaving the decision to the IT team.
  3. A typical implementation pauses the execution while it waits. n8n's Wait node can resume on a webhook call or a submitted form and gives each execution its own resume URL.
  4. After approval, automated API calls to Okta, Jira and Google systems carry out the recovery.
  5. The page reports that the average time locked out fell from 35 to 20 minutes, which it totals as 200 fewer locked-out hours per month.

Why this approach fits

The steps are known in advance and the only judgement call belongs to a person with authority and context, so a plain workflow with an approval step is enough. Moving the decision from IT to the manager removes a queue, and the API nodes make the approved action immediate. It is a useful reminder that many "agent" problems are really workflow problems.

Limitation or tradeoff

The saving depends on managers answering promptly. If an approval sits unanswered, the wait simply moves from IT to the manager, and the page does not describe reminders or time-outs. The figures are the company's own for one workflow, and the page does not explain how they were measured.

What the sources document

  • Before the change there were around 800 lockout recovery requests a month, and each took 35 minutes on average to complete. [22]
  • In the new workflow the employee's direct manager approves the recovery instead of the IT team, and automated API calls to Okta, Jira and Google systems follow. [22]
  • The page reports the average time locked out falling from 35 to 20 minutes, described as 200 hours less locked-out time per month in total, with a time to deployment of 5 hours on Enterprise n8n. [22]
  • The page says the result inspired Delivery Hero to automate other manual processes with n8n, for example account offboarding and software license assignments. [22]
  • The Wait node can resume after a time interval, at a specified time, on a webhook call or when a form is submitted, and it exposes a resume URL for each execution. [14]

The facts above come from the cited sources. The steps and analysis in this example are our explanation of how they fit together.

Example 2 of 5

Oversee uses n8n to orchestrate AI that assembles case context for its support team

OverseeDocumented in a case study

n8n's case study on Oversee, a travel technology company, describes workflows in which AI investigates incoming service requests and hands a structured report to the operations team, with n8n orchestrating the steps. The page does not name the node used; the AI Agent node documentation describes the components a typical implementation would use. [23][2]

The problem

According to the case study, the operations team had to jump across systems, look up a case's full history, pull technical context and check account performance before taking the next step. The page calls this repetitive context gathering a major waste of time that slowed customer-facing work.

Where this topic fits

The AI step sits between the trigger (a service request arrives) and the human decision. Its work is read-only research and summarising, and a person decides what happens next. That is a low-risk place for an agent, because its output is information for a reader rather than an action taken on a customer.

How it is applied, step by step

  1. A service request coming in starts the n8n workflow, as the case study describes.
  2. The workflow hands the request to the AI step. The page does not name the node; a typical implementation uses an AI Agent node with a chat model and a system message that says what a good investigation report contains.
  3. The AI looks for relevant information across the case database. In n8n a typical implementation gives the agent tool sub-nodes for this, for example an HTTP Request tool that calls a search endpoint.
  4. The AI assembles the technical and operational background into a structured report. A typical implementation switches on the node's Require Specific Output Format option so the report has fixed sections.
  5. The operations team receives the report and decides the next action.
  6. The company says it plans to extend the workflows to end-to-end automation, including customer communication when a case needs no human. That is a plan, not a described feature.

Why this approach fits

What to search second depends on what the first search returned, which is the situation where a model choosing the next tool beats a fixed sequence. Restricting the tools to reads and ending with a person who decides keeps the cost of a wrong step small.

Limitation or tradeoff

The case study reports outcomes but not the agent's configuration, model or error rate, and the figures are the company's own. A report that leaves out a relevant case is hard for a reader to notice, so the human step has to include a check, not only a decision.

What the sources document

  • Oversee is a travel technology company that offers air and hotel re-shopping to travel management companies, and the page says it is expanding into agentic AI for travel support. [23]
  • When a service request comes in, AI looks for relevant information across the case database and assembles the technical and operational background into a structured report. With n8n orchestrating the steps, the operations team receives that context and then decides on the next action. [23]
  • The page reports a 50% reduction in first response time on tickets, with a goal of 70% by the end of the year, and gives an example of reports built in two to three hours that used to take two weeks. [23]

Example 3 of 5

SanctifAI plugs human workers into agent workflows as a tool

SanctifAIDocumented in a case study

n8n's case study on SanctifAI describes a company that brings human intelligence into AI agent workflows through its Human as a Tool and Human as a Model products, built on a self-hosted n8n. n8n's own documentation has a matching example, in which an agent calls a second workflow that asks a person for help in Slack. [24][4][6][5]

The problem

An agent sometimes reaches a step it cannot or should not do alone, such as a judgement call or a piece of work only a person can do. The case study's own examples are sign-off on financial documentation and a second opinion on a medical diagnosis. It says the solution needed to be horizontally scalable, distributed and highly composable, and that the team did not want to build from scratch or maintain an in-house codebase. It evaluated LangChain tools and found it needed more flexibility.

Where this topic fits

In a typical implementation the human is one entry in the agent's tool list, and the agent decides when to call it, as with any tool. The case study says tasks are published to a worker portal and the response is streamed back to n8n, where a typical implementation hands it to the agent as the tool result. This is the opposite of an approval gate: the person supplies information or work instead of approving an action.

How it is applied, step by step

  1. SanctifAI's Human as a Tool is configured by selecting the appropriate credentials and workflow ID in the n8n node configuration, as the page states. The page does not show the agent wiring; a typical implementation attaches it, or a Call n8n Workflow tool that wraps it, as one of the agent's tools.
  2. During a run the agent decides it needs human input and calls that tool, as it would any other tool.
  3. The task is published to the SanctifAI Worker Portal and assigned to the appropriate workforce.
  4. When a worker completes it, the response is streamed back to n8n, where in a typical implementation it becomes the tool's result.
  5. The agent reads the result like any other observation and carries on with its loop (see The Agent Loop).

Why this approach fits

An agent framework already treats a tool call as "ask something outside the model, wait, read the answer". A person fits that interface, so human input becomes one more option for the agent rather than a separate process. The queues, routing and schedulers in a workflow engine help when the answer takes minutes or hours instead of milliseconds.

Limitation or tradeoff

A human tool is slow and costs more than an API call, so the execution has to be able to wait. The agent may call it too often or never, depending on how the tool is described. The "three times faster" figure is the company's statement about building workflows compared with writing Python controls for LangChain, not about runtime speed, and the page does not say how it was measured.

What the sources document

  • SanctifAI integrates human intelligence with AI agent workflows through its Human as a Tool and Human as a Model products, and the page lists its version of n8n as self-hosted. [24]
  • The page says the products are configured in the customer portal by selecting credentials and the workflow ID in the n8n node configuration. Tasks for human workers are published to a Worker Portal and assigned to the appropriate workforce, and the response is streamed back to n8n. [24]
  • SanctifAI says it evaluated a number of LangChain tools and needed more flexibility to add logic that is not novel to LangChain. It reports building its first n8n workflow in little over two hours and describes development as three times faster than writing Python controls for LangChain. [24]

4Common mistakes

  1. Leaving a write tool outside the Human review step

    Why it causes problems
    Only the tools you place behind the review step wait for a person. A refund, email or delete tool left outside runs the moment the model chooses it, so a wrong or manipulated model decision takes effect with nobody asked.
    How to recognise it
    Compare the tools listed under Human review on the AI Agent node with your list of tools that change data or contact people. In a test run, check that every one of those tools produces a review request.
    How to fix it
    List every tool that moves money, sends messages or changes records and add each one to the review step. Describe the review steps in the system prompt, including what to do after a denial, and keep read-only tools outside the gate.

  2. Relying on Simple Memory for a production agent that runs in queue mode

    Why it causes problems
    The documentation says Simple Memory does not work in an active production workflow when n8n uses queue mode. A conversation that worked in testing loses its history once workers run the executions, and the agent starts asking for details the customer already gave.
    How to recognise it
    The agent forgets earlier messages only in production, or only after you enable queue mode, while the same chat in the editor keeps its history.
    How to fix it
    Use a persistent store such as Postgres Chat Memory, use one session key per conversation, and connect the Chat Trigger and the agent to the same memory node as n8n recommends.

  3. Testing with the test URL or a manual run and assuming the workflow is live

    Why it causes problems
    New workflows are unpublished, and webhook and schedule triggers only run automatically after you publish. The test webhook URL works only while the editor is listening. Real requests then arrive and nothing happens, or the job never fires.
    How to recognise it
    The Executions tab is empty, the production URL gives an error, or a scheduled job never runs although the manual run worked.
    How to fix it
    Save and publish, call the production URL, and confirm the run in the Executions tab. For schedules, set the workflow timezone, because a self-hosted instance defaults to New York time.

  4. Giving tools vague names and descriptions and leaving $fromAI keys undescribed

    Why it causes problems
    The model chooses a tool and fills its arguments from the text it reads. Vague text leads to the wrong tool, invented argument values and repeated attempts that use up Max Iterations.
    How to recognise it
    Switch on Return Intermediate Steps and read the trace. Look for the wrong tool being picked, the same tool called repeatedly, or arguments that look guessed.
    How to fix it
    Name each tool by its action, say in the description when to use it and when not to, give every `$fromAI()` key a description and a type, and re-read the intermediate steps after each change.

  5. Choosing n8n Cloud or self-hosting on price alone

    Why it causes problems
    The Community edition is free, but you provide and manage the infrastructure. Cloud is fully managed, but your data rules may not allow it. Choosing by price leaves an unpatched server or data in a place your policy forbids.
    How to recognise it
    Nobody can say who updates, backs up and monitors the instance, or where the workflow data and the model calls are processed.
    How to fix it
    Write down the data rules and the named owner of the server first. Start with Cloud for speed unless a rule requires control, as K33 and XIBIX documented for their own reasons, and plan patching, backups and monitoring before you self-host.

Exercise 1

Run n8n locally and build a webhook workflow you test and publish

Hands-onBeginnerAbout 45 min (estimate)Hypothetical scenario

Build the smallest useful n8n workflow on your own computer. It uses the same trigger, node and item model that the AI Agent node sits inside, and everything is free. You need Docker and curl.

  1. Start n8n with the commands from the Docker install page (shown in the lesson; that page is marked outdated in favour of Docker Compose, but one container is fine for this throwaway exercise), replacing <YOUR_TIMEZONE> with a zone such as Europe/Berlin. Open http://localhost:5678 and complete the setup screens.

  2. Create a workflow with three nodes connected in a line: a Webhook node (HTTP Method POST, Respond set to "Using 'Respond to Webhook' Node"), an Edit Fields node, and a Respond to Webhook node (Respond With "First Incoming Item").

  3. In Edit Fields add two fields: received (type String) with the expression {{ $json.body.message }} and characters (type Number) with the expression {{ $json.body.message.length }}.

  4. Select Listen for test event on the Webhook node and send a request to the Test URL shown on the node:

    bash
    curl -X POST "<TEST_URL>" -H "Content-Type: application/json" -d '{"message": "hello n8n"}'

  5. Publish the workflow, send the same request to the Production URL, and find that run.

  6. Stop the container with Ctrl+C, run the same docker run command again, and check that your workflow is still there.

Requirements

  • The Webhook node accepts POST requests, and the reply is produced by a Respond to Webhook node.
  • Edit Fields creates the fields `received` and `characters` from the request body with expressions.
  • You send one request to the test URL and one to the production URL, and find the production run in the Executions tab.
  • The workflow is still present after the container is stopped and started again.

Expected behaviour

Both requests return JSON that includes "received": "hello n8n" and "characters": 9. The count is 9 because "hello" has 5 characters, the space 1 and "n8n" 3. Depending on the Include in Output and Keep Only Set Fields settings of Edit Fields, the reply may also contain the incoming headers, params, query and body fields. The test request shows its data on each node in the editor. The production request does not, but it appears in the Executions tab. After restarting, the workflow is still there.

Hint 1

If the reply says the workflow got started instead of returning your fields, open the Webhook node and check that Respond is set to "Using 'Respond to Webhook' Node".

Hint 2

If `characters` is empty, open the Webhook node's output. The JSON you sent should be under `body`, which needs the `Content-Type: application/json` header.

Hint 3

The production URL only works after you publish, and the test URL only works while the node is listening.

Hint 4

Your data survives a restart only because of the named volume `n8n_data` mounted at `/home/node/.n8n`.

Show solution

Start n8n with the two commands from the Docker install page (the volume, then docker run with -p 5678:5678 and -v n8n_data:/home/node/.n8n) and open http://localhost:5678.

Build the workflow as Webhook, then Edit Fields, then Respond to Webhook:

NodeSettings
WebhookHTTP Method POST; Respond Using 'Respond to Webhook' Node
Edit FieldsField received (String) = {{ $json.body.message }}; field characters (Number) = {{ $json.body.message.length }}
Respond to WebhookRespond With First Incoming Item

Test URL request and reply:

text
$ curl -X POST "<TEST_URL>" -H "Content-Type: application/json" -d '{"message": "hello n8n"}'
{"received":"hello n8n","characters":9}

Your reply may carry extra fields if Edit Fields passes the input through. The point is that the two new fields are present. Now publish the workflow and send the same request to the Production URL. The reply is the same, but the editor stays empty and the run is listed in the Executions tab.

What moved between the nodes was a list with one item. The Webhook node produced an item whose json held headers, params, query and body. Edit Fields added received and characters to that item, and Respond to Webhook sent back the JSON of the first item. This is the same list-of-items shape that the AI Agent node receives as its prompt and returns as its answer.

Finally press Ctrl+C and run the same docker run command again. The workflow is still listed because the n8n_data volume holds the data folder. Without the -v option, the data would be lost when the container was removed.

Check your answer

  • Does the reply for the message "hello n8n" contain a characters value of 9?
  • Can you explain why the production run is missing from the editor but present in the Executions tab?
  • After restarting the container, is the workflow still there, and can you say which option made that happen?
  • Can you name the key under which an item keeps its fields, and show it in the Webhook node's output?

Exercise 2

Design the approval, memory and hosting controls for a refund-capable support agent

DesignIntermediateAbout 40 min (estimate)Hypothetical scenario

A 40-person online shop in the EU wants a chat support agent built in n8n. Facts:

  • 2,000 customer chat messages arrive per day, and 5% of messages end in a refund request.
  • The candidate tools are search_orders(email), get_customer(customer_id), send_email(to, subject, body) and issue_refund(order_id, amount).
  • The shop's own GDPR policy says customer data must stay on servers it controls.
  • One engineer will run the system. The team already operates Docker and PostgreSQL.
  • Assume Max Iterations stays at 10, and an average message needs 3 model calls.

Write a one-page design note that covers: which tools sit behind Human review and why, and through which channel; the system message sentences about approvals and denials; the memory node and session key; the hosting choice and whether you need queue mode; and the daily numbers of executions, model calls and approvals.

Requirements

  • Classify each of the four tools as reviewed or not reviewed and give a one-sentence reason for each.
  • Write the system message sentences that cover approval and denial.
  • Choose a memory node and a session key, and justify the choice for production.
  • Choose Cloud or self-hosted with two reasons and one cost of your choice, and say whether queue mode is needed yet.
  • Calculate executions per day, worst-case model calls per day, expected model calls per day and approvals per day.

Expected behaviour

A coherent note with these numbers: 2,000 executions per day, a worst case of 20,000 model calls, an expected 6,000 model calls and about 100 refund approvals per day. The note gates the tools that move money or contact customers, uses a persistent memory node, and defends its hosting choice against the stated policy.

Hint 1

For each tool ask whether the action can be undone and whether it leaves your own systems.

Hint 2

Each chat message is one execution, and Max Iterations caps the model calls inside one execution.

Hint 3

Simple Memory has a documented limit in queue mode, and a session key should identify a conversation, not a person.

Hint 4

100 approvals in an 8-hour day is roughly one every five minutes, which affects who reviews and whether small refunds need a rule.

Show solution

Tools. issue_refund moves money and cannot be recalled, so it goes behind Human review. send_email leaves the building and cannot be unsent, so it is also reviewed. search_orders and get_customer only read, so they run freely, but return only the fields the agent needs because the results become part of the prompt. Send approvals to the support lead in Slack or Teams. The documentation allows the review to happen in a different channel from the customer's chat.

System message. "issue_refund and send_email need a reviewer's approval. If a reviewer denies a call, tell the customer plainly that the action was not taken, do not try it again, and offer to hand the chat to a person."

Memory. Use Postgres Chat Memory, because history must survive restarts, Simple Memory is documented as not working in an active production workflow in queue mode, and the team already runs PostgreSQL. Use a per-conversation identifier as the session key and connect the Chat Trigger and the agent to the same memory node. A customer's email address would merge separate conversations.

Hosting. Self-host, because the policy requires control of where customer data lives and the team can run Docker and PostgreSQL. The cost is that the engineer owns patching, backups, monitoring and upgrades. Cloud would be defensible only if the policy allowed n8n as a processor. Note that a hosted chat model API would also receive customer text, so decide that separately. Start with a single instance on PostgreSQL. Move to queue mode (Redis, workers and PostgreSQL) when load or isolation demands it, and keep the Postgres memory node.

Numbers.

QuantityCalculationResult
Executions per dayone per message2,000
Worst-case model calls per day2,000 x 1020,000
Expected model calls per day2,000 x 36,000
Refund approvals per day2,000 x 0.05100

With 100 refund approvals in an 8-hour day (480 minutes), a reviewer sees one about every 4.8 minutes, and approvals for send_email come on top (the prompt gives no figure for them). Consider a rule-based node that auto-approves refunds below a small amount, so people review only the larger ones.

Check your answer

  • Does every tool that moves money or contacts a customer sit behind review?
  • Is the session key per conversation rather than per customer?
  • Do your numbers keep executions (2,000) apart from model calls (up to 20,000)?
  • Did you name what self-hosting costs the team, and not only why it meets the policy?
