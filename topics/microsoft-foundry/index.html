Microsoft Foundry

Microsoft Foundry is Microsoft's Azure platform for building and running AI applications and agents. One Foundry resource holds projects, deployments of models chosen from a catalog, a managed agent runtime called Foundry Agent Service, shared tools and knowledge sources, and built-in tracing, evaluation and access controls.

1Overview

Why it matters

An agent that works on a laptop still needs a home before a company can use it. It needs a model endpoint with quota and a contract behind it, storage for conversations, a credential for every tool, logs that show what the agent did, tests that catch regressions, and rules about who may change it or call it. Teams that assemble these pieces themselves tend to find the gaps late: one API key shared by every developer, or conversation history sitting where the security team cannot audit it. Foundry packages those concerns into one Azure resource. They become configuration choices, and you have to understand each choice to make it well.

Engineers who deploy into Microsoft-centred organisations meet Foundry whether they pick it or not, because the customer's models, identities and network rules already live there. To work in it you need to know which agent type fits the workload, where state is stored, which identity a tool call runs under, and what the platform leaves to you, such as checking that a user owns a conversation or failing over to another region.

What you will be able to do

  • Describe how a Foundry resource, its projects and its model deployments relate, and what each one isolates.
  • Choose between a prompt agent, a hosted agent and direct Responses API calls for a given workload.
  • Write the calls that create an agent version and hold a multi-turn conversation with it.
  • Pick an authentication mode for a tool or knowledge connection and explain what a toolbox adds.
  • Read an evaluation result and turn its pass and fail counts into a release decision.
  • Apply the enterprise controls (roles, agent identity, guardrails, standard setup) to a concrete requirement.

Key terms

Foundry resource
The single Azure resource at the top of a Foundry environment. Access control, networking and policy are applied to it, and it contains one or more projects.
Foundry project
A workspace inside a Foundry resource. Agents in one project share its files, conversation history and search indexes, and cannot reach the data of another project.
Model deployment
A callable instance of a catalog model inside a Foundry resource. Requests name the deployment, and the deployment type decides where processing happens and how it is billed.
Foundry Agent Service
The managed runtime in Foundry that stores agent definitions and conversations, runs responses, calls tools on the agent's behalf and hosts agent code.
Prompt agent
An agent defined only by configuration (a model, instructions and tools) and stored in a project as a named, versioned resource that Foundry runs for you.
Hosted agent
Your own agent code, built with any framework, packaged as a container and run by Agent Service in an isolated sandbox per session with a managed endpoint and identity.
Conversation
A durable, server-side list of items such as messages, tool calls and tool outputs that later responses can read as history.
Toolbox
A curated, versioned set of tools exposed through one managed MCP-compatible endpoint, with authentication and guardrails configured once for every agent that uses it.
Agent identity
A Microsoft Entra ID identity made for an AI agent. Foundry uses it to obtain access tokens when the agent calls a tool, so no secret has to be stored in prompts or code.
Guardrail
A named collection of controls. Each control names a risk to detect, the point in the request where it is checked, and the action to take when it is found.

2Explanation

Introduction

In Microsoft Agent Framework you built an agent in code: a chat client, instructions, tools and a session. In Agent Deployment Architecture you saw what has to surround that code in production: a runtime, state, identity, observability and a release process. Microsoft Foundry is Microsoft's managed version of that surrounding layer on Azure.

Think of a shared commercial kitchen. You bring the recipe and do the cooking. The building supplies the stoves, the cold storage, the door locks, the inspection log and the rule about who holds which key. You can cook at home without any of that, but once you serve the public somebody has to provide it. Foundry plays the building. You bring instructions, tools and, if you want, your own agent code. It supplies models, a runtime, storage for conversations, identities, traces, evaluations and access rules.

Read the diagram from the bottom up. A Foundry resource is the Azure resource that carries access control, networking and policy. Inside it, projects separate teams or workloads. A project holds model deployments, agents, tools and knowledge connections, and the telemetry they produce.

Names in this area have changed several times, which makes older tutorials confusing. The overview page (opens in a new tab) gives the mapping: Azure AI Studio and Azure AI Foundry are now Microsoft Foundry, Azure AI Services are Foundry Tools, and the Assistants API with its threads, messages and runs has given way to the Responses API with conversations, items and responses. There are also two portals. This lesson describes the current portal and Foundry projects as documented in October 2026. Hub-based projects remain in the portal labelled Foundry (classic). Anything marked preview below may still change.

The lesson takes the platform in five parts: projects and the model catalog, Foundry Agent Service, tools and knowledge connections, tracing and evaluation, and enterprise controls. The worked example then takes one small agent from its definition to a release decision.

How it works

Resources, projects and deployments

A Foundry resource is one Azure resource with projects inside it: a single management grouping for agents, models and tools, with unified role-based access control, networking and policies. A project is the unit of sharing and isolation. The environment setup guide (opens in a new tab) states that agents in one project share file storage, conversation history and search indexes, and cannot reach another project's data.

Each project has one endpoint:

text
https://<resource-name>.services.ai.azure.com/api/projects/<project-name>

Client code builds one project client against that endpoint (the azure-ai-projects 2.x package in Python) and obtains an OpenAI-compatible client from it for conversations and responses. The 2.x package is not compatible with 1.x, which belongs to the classic portal.

The model catalog

The catalog (opens in a new tab) lists more than 10,000 models in two groups.

Sold by AzurePartner and community
Sold and supported byMicrosoft, under Microsoft Product Terms, with enterprise SLAsThe provider, on its own terms; support varies
BillingAzure metersAzure Marketplace
ReviewMicrosoft's Responsible AI reviewUsually validated by the provider

You never call a catalog entry. You call a deployment of it, and the deployment name is the value of the model parameter. Most models use a serverless deployment, where Microsoft hosts the model and bills per token. The deployment type sets where processing happens and how capacity is bought. Global Standard, Data Zone Standard and regional Standard are pay-per-token; the provisioned types reserve capacity. Managed compute instead puts model weights on dedicated virtual machines billed by core hours; the overview points to hub-based projects in the classic portal for it. Choosing a Model and Provider covers how to compare candidates.

Foundry Agent Service

Agent Service is the managed runtime. It offers three ways to run an agent, which differ in how much you own.

A prompt agent is pure configuration: a model, instructions and tools, stored as a named, versioned resource. A hosted agent is your own code (Agent Framework, LangGraph or anything else) shipped as a container image. Each session runs in its own VM-isolated sandbox with a persistent $HOME, and the compute is released after an idle timeout of 15 minutes by default. Calling the Responses API directly gives what the documentation calls an ephemeral agent: the definition lives in your application and nothing is stored in Foundry. A voice-based prompt agent also exists for real-time speech.

Whatever the type, the runtime (opens in a new tab) works with three objects:

ObjectWhat it isWhen you need it
AgentA reusable definition, identified by name and versionSeveral requests need the same behaviour
ConversationA durable list of items: messages, tool calls, tool outputsLater turns need server-side history
ResponseOne unit of execution that reads input and produces output itemsAlways
python
agent = project.agents.create_version(
    agent_name="returns-helper",
    definition=PromptAgentDefinition(model="gpt-5-mini", instructions="..."),
)
openai = project.get_openai_client(agent_name="returns-helper")
conversation = openai.conversations.create()
reply = openai.responses.create(conversation=conversation.id, input="Can I return shoes?")

Without a conversation you can chain turns with previous_response_id, or set store=False and resend the history yourself when nothing may be kept on the server. It is the loop from The Agent Loop, except that for server-side tools the service, not your process, runs the tool-calling iterations inside one response.

Tools and knowledge connections

Built-in tools include web search, file search, code interpreter and memory. Custom tools arrive as functions, OpenAPI specifications or MCP servers. Function calling is the exception to server-side execution: the response returns a function_call item and your code runs it.

A toolbox (opens in a new tab) groups tools behind one managed MCP-compatible endpoint. Authentication, guardrails and versions are configured once on the toolbox, and any MCP client can consume it, including agents that run outside Foundry. A tool connection authenticates in one of four ways: a key, Microsoft Entra (the agent's identity or the project's managed identity), OAuth identity passthrough on behalf of the signed-in user, or no authentication.

For knowledge, the simplest option is file search over uploaded files. Foundry IQ (opens in a new tab) is the managed knowledge layer. A knowledge base references knowledge sources such as Azure Blob Storage, SharePoint, OneLake or the web, and answers with agentic retrieval: it splits a question into subqueries, runs them in parallel, reranks the results and returns passages with citations. It can enforce document permissions at query time by running under the caller's Entra identity. Azure AI Search provides the indexes underneath. Agentic RAG explains the retrieval pattern itself.

Tracing and evaluation

Tracing (opens in a new tab) follows the OpenTelemetry GenAI semantic conventions and stores data in the Application Insights resource connected to the project. A trace is a tree of spans such as invoke_agent and execute_tool, with attributes for inputs, outputs, tool arguments, token counts and duration. Because the conventions are open, agents built with LangChain, LangGraph or the OpenAI Agents SDK can send traces to the same place. LLM and Agent Observability covers how to read them.

Evaluation applies evaluators to agent output. The agent evaluators (opens in a new tab) come in two families. System evaluators judge the outcome (task completion, task adherence, intent resolution). Process evaluators judge the steps (tool selection, tool input accuracy, tool call success). Most are LLM judges that need a judge model deployment and return pass or fail with a reason. An evaluation run sends each row of a test dataset to the agent and scores the result against testing criteria like this one:

python
testing_criteria = [{
    "type": "azure_ai_evaluator",
    "name": "task_adherence",
    "evaluator_name": "builtin.task_adherence",
    "initialization_parameters": {"deployment_name": judge_deployment},
    "data_mapping": {"query": "{{item.query}}", "response": "{{sample.output_items}}"},
}]

{{item.query}} reads a field of the dataset row, and {{sample.output_items}} is the agent's full output including tool calls. The same evaluators run in CI through the microsoft/ai-agent-evals GitHub Action (opens in a new tab), and against production traffic as continuous evaluation.

Enterprise controls

Access. With Microsoft Entra authentication, built-in roles (opens in a new tab) decide who can do what:

RoleIntended for
Foundry Agent ConsumerCallers that only invoke agent endpoints
Foundry UserDevelopers building and testing in a project
Foundry Project ManagerLeads who manage projects and publish agents
Foundry Account OwnerAdministrators who manage the resource and models but do not build
Foundry OwnerFull control of both building and administration

Roles can be assigned at resource, project or single-agent scope. Key-based authentication skips all of this, because a key grants full access.

Agent identity. Each agent acts under a Microsoft Entra agent identity (opens in a new tab), a special service principal. Unpublished prompt agents in a project share one identity. A published agent, and every hosted agent, gets its own, and role assignments do not carry over. When the agent calls a tool, Agent Service exchanges that identity for a token scoped to the target service, so no secret sits in a prompt or in code. Agent Identity, Permissions and Least Privilege goes deeper.

Guardrails. A guardrail (opens in a new tab) is a named set of controls. Each control names a risk (hate, prompt attacks, personal data and others), an intervention point (user input, tool call, tool response or output) and an action. A guardrail assigned to an agent fully replaces the one on its model deployment.

Data and network. Basic setup keeps agent state in storage that Microsoft manages. Standard setup stores conversations, files and vector indexes in your own Azure Cosmos DB, Storage and AI Search, and can add your own virtual network so that agent traffic stays private.

Fleet view. Foundry Control Plane lists agents, models and tools across projects, with cost, compliance and security signals from Microsoft Defender and Microsoft Purview.

Worked example: Take a returns-policy agent from its definition to a release decision

The goal is to define a small prompt agent, hold a two-turn conversation with it, and then decide from an evaluation run whether it may ship. Steps 1 and 2 need a Foundry project with a deployed model, which means an Azure subscription. Step 3 runs anywhere with Python 3.9 or later.

Step 1: define the agent and talk to it

Install azure-ai-projects 2.3.0 or later and azure-identity, sign in with az login, then run this script. It follows the prompt agent quickstart (opens in a new tab).

python
from azure.identity import DefaultAzureCredential
from azure.ai.projects import AIProjectClient
from azure.ai.projects.models import PromptAgentDefinition

ENDPOINT = "https://<resource-name>.services.ai.azure.com/api/projects/<project-name>"
AGENT_NAME = "returns-helper"

project = AIProjectClient(endpoint=ENDPOINT, credential=DefaultAzureCredential())

agent = project.agents.create_version(
    agent_name=AGENT_NAME,
    definition=PromptAgentDefinition(
        model="gpt-5-mini",  # a model deployed in this project
        instructions="You answer questions about the returns policy in two sentences or fewer.",
    ),
)
print(f"{agent.name} version {agent.version}")

openai = project.get_openai_client(agent_name=AGENT_NAME)
conversation = openai.conversations.create()
for question in ["Can I return shoes after 20 days?", "And if I lost the box?"]:
    response = openai.responses.create(conversation=conversation.id, input=question)
    print(response.output_text)

create_version stores a new version of the agent each time it runs. Each responses.create call gives the whole conversation to the model and appends the output to it, which is why the second question can start with "And" without repeating the first. The model's wording differs from run to run. The structure does not.

The first turn as a raw request, in the form the quickstart documents:

bash
curl -X POST "https://<resource-name>.services.ai.azure.com/api/projects/<project-name>/agents/returns-helper/endpoint/protocols/openai/responses?api-version=v1" \
  -H "Content-Type: application/json" \
  -H "Authorization: Bearer $AZURE_AI_AUTH_TOKEN" \
  -d '{"input": [{"role": "user", "content": "Can I return shoes after 20 days?"}]}'
Step 2: evaluate

An evaluation run sends a dataset of queries to the agent and applies the testing criteria to each answer. The sample run in the evaluation guide (opens in a new tab) uses three queries and three criteria, and reports these counts:

Testing criterionPassedFailedErrored
Agent Quality (a rubric scored by an LLM judge)120
Violence (content safety)300
Coherence210
Step 3: turn the counts into a release decision

The guide suggests an acceptance threshold such as an 85% pass rate before release. Save the script below as eval_gate.py. It needs only the standard library, and the embedded JSON is the sample result above in the field names the service returns.

python
import json

GATE = 0.85  # minimum pass rate for every testing criterion

RUN = json.loads("""
{
  "result_counts": {"total": 3, "passed": 1, "failed": 2, "errored": 0},
  "per_testing_criteria_results": [
    {"testing_criteria": "Agent Quality", "passed": 1, "failed": 2, "errored": 0},
    {"testing_criteria": "Violence", "passed": 3, "failed": 0, "errored": 0},
    {"testing_criteria": "Coherence", "passed": 2, "failed": 1, "errored": 0}
  ]
}
""")


def pass_rate(row):
    scored = row["passed"] + row["failed"]
    return row["passed"] / scored if scored else 0.0


def check(run, gate):
    """Return (criterion, pass rate, ok) for every testing criterion in a run."""
    return [
        (row["testing_criteria"], pass_rate(row), pass_rate(row) >= gate and row["errored"] == 0)
        for row in run["per_testing_criteria_results"]
    ]


if __name__ == "__main__":
    results = check(RUN, GATE)
    for name, rate, ok in results:
        print(f"{name:<14}{rate:>7.1%}  {'ok' if ok else 'BELOW GATE'}")
    counts = RUN["result_counts"]
    print(f"rows with every criterion passed: {counts['passed']}/{counts['total']}")
    print("release:", "allowed" if all(ok for _, _, ok in results) else "blocked")

python3 eval_gate.py prints:

text
Agent Quality   33.3%  BELOW GATE
Violence       100.0%  ok
Coherence       66.7%  BELOW GATE
rows with every criterion passed: 1/3
release: blocked

Check the arithmetic: 1/3 is 33.3%, 3/3 is 100% and 2/3 is 66.7%. Two criteria are below 85%, so the release is blocked.

What to notice:

  • The gate is per criterion. A perfect safety score does not make up for a failing quality score.
  • Three rows prove very little. One more passing row would move Coherence from 66.7% to 100%. Exercise 1 adds a confidence bound so that a small dataset cannot pass by luck.
  • The fix starts in the row-level output. Each failed row carries the evaluator's reason. Change the instructions or tools, create a new agent version, and rerun under the same evaluation so that the two runs are comparable.

Edge cases and limitations

Publishing an agent changes the identity its tool calls use
Unpublished agents call tools with the project's shared agent identity. A published agent gets a new, distinct identity, and the agent identity documentation states that the shared identity's role assignments do not carry over. A tool that worked in development then fails with an authorisation error in production. Reassign the roles to the new identity as part of the release. The same page notes that the publishing experience is changing, so check the current behaviour before you rely on it.
A long conversation is silently cut down for the model
The runtime documentation says that when a conversation exceeds the model's context size, the model truncates the input automatically. The stored conversation stays complete, but only a subset reaches the model. An agent can therefore forget an early instruction without any error. Watch input token counts in traces, and start a new conversation or summarise when a session grows long.
The agent's guardrail replaces the model's, including what it leaves out
Risks are detected according to the guardrail assigned to the agent, which fully replaces the guardrail of the underlying model deployment. The guardrails page gives the example of a model deployment that scans user input and output for violence at one threshold, while the agent's guardrail uses a different threshold and has no controls for tool calls or tool responses. The agent's settings win, and those two points are not scanned at all. Review the agent's guardrail as its own artefact.
Being in the catalog does not make a model usable by an agent
Agent Service works with a subset of the catalog, and tool availability depends on both the model and the region. The baseline reference architecture states this directly. Models that deploy only to managed compute follow different project rules again. Confirm the model on the Agent Service model list for your region before you design around it.
Some evaluators are unreliable for some tools
The agent evaluators page lists tools with limited support, including Azure AI Search, Bing grounding, code interpreter and web search, and advises against using tool call accuracy, tool input accuracy, tool output utilization, tool call success or groundedness when a conversation includes calls to them. A low score there may describe the evaluator and not the agent. Use outcome evaluators or a custom evaluator for those agents.

When to use it, and when something simpler is enough

Use it when

  • The organisation already runs on Azure and Microsoft Entra ID and needs agents to follow the same identity, network and policy rules as its other workloads.
  • You want a managed runtime for conversations, tool orchestration and agent identity so that your team does not have to build and operate one.
  • You need models from several providers under one Azure resource, with the same sign-in and access rules and with the charges on the Azure bill.
  • Compliance requires agent state in your own storage and traffic on a private network, which standard setup with your own virtual network provides.
  • Agents must reach users inside Microsoft Teams or Microsoft 365 Copilot, which Agent Service can publish to.

Think twice when

  • The feature is one model call with no tools or stored history. A direct call to a model deployment is simpler and has fewer moving parts.
  • You need controls the service does not expose, such as canary routing between agent versions or automatic failover of agent state to another region. Those need your own routing or orchestration layer.
  • The workload has to run outside Azure, on premises or in another cloud, where the runtime and its identity model are not available.
  • The model or tool the design depends on is not supported by Agent Service in the region you must use.

A simpler alternative. Call a model deployment through the Responses API on the project endpoint and keep the instructions and tools in your own code, which the documentation calls an ephemeral agent. You still get catalog models and platform tools. It stops being enough when several applications need the same agent behaviour, when history has to live on the server across sessions, or when each agent needs its own identity, version history and access rules.

Key takeaways

  • A Foundry resource is the Azure boundary for access, network and policy, and projects inside it are the unit that isolates agents and their data.
  • You call a deployment of a catalog model, not the catalog entry, and the deployment type decides where data is processed and how the model is billed.
  • Agent Service runs prompt agents from configuration and hosted agents from your code, and both use the same three objects: agent versions, conversations and responses.
  • Every tool and knowledge connection has an authentication mode, and an agent identity lets the agent reach a service without a stored secret.
  • Traces show what an agent did and evaluation runs score it, but the release rule (which criteria, what pass rate, how many rows) is yours to define.
  • Foundry does not check that a user owns a conversation, split traffic between agent versions or recover agent state in another region, so those remain your design work.

Example 1 of 5

Commerzbank's Ava, a customer banking agent built on Foundry Agent Service

Commerzbank AGDocumented in a case study

A customer story published by Microsoft Foundry Labs, dated November 2025, describes Ava, an AI-powered banking agent that Commerzbank built on Foundry Agent Service and Microsoft Agent Framework for digital customer support. [23]

The problem

According to the story, the bank needed to modernise digital customer support while dealing with fragmented legacy systems, changing regulatory requirements, fraud prevention and customers who expect instant, personal service. A banking agent has to hold an open conversation, complete bounded account tasks and remember what was said, all under stricter rules than most industries face.

Where this topic fits

Foundry Agent Service and Agent Framework form the agent layer. The story names the Azure services around it and the job each one does. In this lesson's terms they are a model deployment (Azure OpenAI), a knowledge connection (Azure AI Search), a state store in the bank's own resource (Azure Cosmos DB) and a safety control (Azure AI Content Safety).

How it is applied, step by step

  1. A customer message reaches the Ava application, which the story says uses Azure Kubernetes Service for scalability.
  2. The agent, built with Microsoft Agent Framework on Foundry Agent Service, passes the conversation to an Azure OpenAI model to work out what the customer wants.
  3. When the request needs bank information, the agent retrieves it through Azure AI Search, which the story describes as the source of trusted data. A typical implementation exposes the index to the agent as a retrieval tool.
  4. For account tasks such as the credit card lifecycle steps, balance inquiries and account adjustments named in the story, a typical implementation gives the agent tools that call the bank's own systems. The story does not describe these integrations.
  5. Conversation memory is kept in Azure Cosmos DB so that context persists between turns.
  6. Azure AI Content Safety screens the exchange. The story credits it with fraud detection and data protection.
  7. The reply returns as text or, through text-to-speech, as voice.

Why this approach fits

The work mixes open conversation with a small set of well-defined transactions, which is what a tool-calling agent handles well. Because the setting is regulated, the parts a bank cannot improvise (content filtering, durable conversation state in a database it controls, and governance over who can change the agent) matter as much as answer quality. Taking those from a platform lets the bank's team spend its effort on the banking logic.

Limitation or tradeoff

The figures are headline metrics that the bank and vendor report in a promotional story. The page gives no method for deciding that a request was resolved autonomously, and a quarter of requests still need another path, presumably a person. It says nothing about evaluation, escalation or failure handling. The design also joins several services, each with its own cost and failure modes, so the numbers should not be read as what a different team would get.

What the sources document

  • The story states that Commerzbank built Ava, an AI-powered conversational agent, on Microsoft Foundry Agent Service and Microsoft Agent Framework, deployed on Azure infrastructure. [23]
  • The story reports that Ava automates more than 30,000 customer conversations a month and resolves 75% of requests autonomously. [23]
  • It states that Ava uses Azure OpenAI for natural language understanding, Azure AI Content Safety for fraud detection and data protection, Azure Cosmos DB for persistent conversation memory, Azure Kubernetes Service for scalability, Azure AI Search for trusted data retrieval and text-to-speech for voice interactions. [23]
  • The story says Ava handles workflows including credit card lifecycle management, balance inquiries and account adjustments. [23]
  • The story lists development that was twice as fast with Agent Framework among its headline results, and quotes Gerald Ertl, Managing Director and Head of Strategic AI Program, as saying that Foundry Agent Service gives the bank the building blocks for the future. [23]

The facts above come from the cited sources. The steps and analysis in this example are our explanation of how they fit together.

Example 2 of 5

Azure Architecture Center's baseline chat design: network-isolated agents on standard setup

Microsoft Azure Architecture CenterDocumented in official docs

The Baseline Microsoft Foundry chat reference architecture in the Azure Architecture Center, which links to a deployable reference implementation in the Azure-Samples/microsoft-foundry-baseline repository, shows an enterprise chat application whose agent runs in Foundry Agent Service. [19][15]

The problem

An enterprise chat application has to keep all traffic and all agent state inside the organisation's own network and subscription, control which internet destinations an agent can reach, and still let a user come back to an earlier conversation. The default, quick-start configuration of an agent platform does none of these.

Where this topic fits

Agent Service hosts a prompt agent as the orchestration layer. In front of it is a web application on Azure App Service behind Application Gateway and a web application firewall. Behind it are the model deployment and two tools, Azure AI Search for grounding data and web search. The architecture uses standard agent setup, so the agent's state lives in the workload's own Azure Cosmos DB, Storage and AI Search, reached over private endpoints.

How it is applied, step by step

  1. A user request passes through Application Gateway and the web application firewall to the web application on App Service.
  2. The web application calls the agent through the Microsoft Agent Framework, which invokes the server-side agent definition over the Responses API. The call uses a private endpoint and the application's managed identity.
  3. The agent follows its system prompt and decides whether to use its tools, Azure AI Search for grounding data and web search for public data.
  4. AI Search is reached through a private endpoint. Calls to most external tools leave through Azure Firewall, which allows only approved domain names.
  5. The agent calls its model deployment with the context it has gathered.
  6. The request, the response and the tool details are stored as conversation items in the workload's Cosmos DB, so the user can resume later.
  7. On every request the web application, not Foundry, checks that the signed-in user owns the conversation identifier before forwarding it.

Why this approach fits

Standard setup exists for this case. The agent still runs in a managed service, but everything it remembers sits in resources the organisation owns, can back up and can audit, and every network path is private or goes through a firewall the organisation controls. The team avoids building an orchestration service and keeps the controls that its security review asks for.

Limitation or tradeoff

The page is frank about what the design lacks. It is a single-region design, and Agent Service has no built-in disaster recovery, so losing the orchestration layer means rebuilding it from source control and backups. There is no blue-green or canary deployment of agents without a routing layer in front. Private endpoints are defined per resource, so projects in one resource cannot be segmented by network. The agent may also call a connected tool when it is not relevant to the request, which makes cost harder to predict.

What the sources document

  • The architecture uses the Foundry Agent Service standard agent setup, in which the workload brings its own virtual network and its own Azure resources to store chat and agent state. The setup guide lists those resources as Azure Storage, Azure AI Search and Azure Cosmos DB. [19][15]
  • The web application calls the agent through the Microsoft Agent Framework, which invokes the server-side agent definition through the OpenAI-compatible Responses API over a private endpoint, authenticating to Foundry with its managed identity. [19]
  • Conversation history is stored in Azure Cosmos DB as conversation items (messages, tool calls and tool outputs). Azure Storage holds files uploaded during chat sessions, and AI Search holds a chunked index of files uploaded through the File Search tool. [19]
  • The page states that Foundry Agent Service does not enforce per-user authorization on conversations, and that the application server must verify on every request that the authenticated user owns the referenced conversation. [19]
  • The page states that Foundry Agent Service provides no built-in disaster recovery and that Foundry has no built-in support for blue-green or canary deployments of agents. It recommends defining agents as code in source control and placing a routing layer in front of the agent API for controlled rollouts. [19]

Hosting a Microsoft Agent Framework agent as a Foundry hosted agent

MicrosoftDocumented in official docs

The Agent Framework documentation page Foundry Hosted Agents describes the framework's hosting integration for Foundry Agent Service. The Foundry page Hosted agents in Foundry Agent Service describes the platform side: sandboxes, sessions, identity and protocols. [21][17][20][6]

The problem

A team has an agent with custom orchestration code. Running it themselves means building a web server, a container pipeline, scaling rules, state that is isolated per user, and an identity for the agent. They want to keep the code and hand everything around it to the platform.

Where this topic fits

This is the hosted agent type of Agent Service. The code is an Agent Framework agent that reaches a model deployment through the project endpoint. A small host server exposes it over the Responses protocol, and the Azure Developer CLI builds and deploys it. Tools reach the agent through a toolbox endpoint, not through the agent definition.

How it is applied, step by step

  1. Write the agent with Agent Framework. Its FoundryChatClient points at the project endpoint and names a model deployment.
  2. Wrap the agent in ResponsesHostServer, which serves the OpenAI-compatible responses endpoint.
  3. Test locally with the azd ai agent run command and a POST to port 8088 on localhost.
  4. Run azd deploy, which packages the code as a container image, pushes it to Azure Container Registry and deploys it to Agent Service.
  5. The platform creates a dedicated Microsoft Entra agent identity and an endpoint for the agent, and injects the project endpoint, the model deployment name and the Application Insights connection string as environment variables.
  6. Each session gets its own VM-isolated sandbox. After the idle timeout the compute is released, and the session's home directory and uploaded files are restored on the next request.
  7. Add tools by connecting the agent to a toolbox, which any MCP-compatible client can consume, so the tool list can change without redeploying the container.
  8. Clients call the agent endpoint with any OpenAI-compatible SDK.

Why this approach fits

The team keeps full control of the agent's logic and its framework, and the platform takes the parts that are the same for every agent: the endpoint, scaling, identity and saved session state. A sandbox per session suits agents that write files or run code, because one user's session cannot see another's.

Limitation or tradeoff

An agent endpoint serves exactly one version and cannot split traffic, so a gradual rollout needs a second agent and your own router. Compute is billed for the CPU and memory of every active session, so a generous sandbox size is multiplied by concurrency. Sessions are deleted after 30 days without activity. The Agent Framework page also warns that the session store's conflict checks do not give exactly-once execution of tool side effects, so tools must be safe to repeat.

4Common mistakes

  1. Forwarding a conversation identifier from the client to Agent Service without checking who owns it.

    Why it causes problems
    Foundry does not enforce per-user authorisation on conversations. Any signed-in user who copies or guesses an identifier can read another person's history or add messages to it. The reference architecture names this a Broken Object Level Authorization vulnerability.
    How to recognise it
    An API handler passes the conversation value from the request body straight into the responses call, and there is no record of which user created which conversation. A test in which user B sends user A's identifier succeeds.
    How to fix it
    Record the owner when a conversation is created, look it up on every request, and refuse the request before calling Agent Service when the signed-in user is not the owner.

  2. Giving a calling service the Foundry User role or an API key when it only needs to invoke an agent.

    Why it causes problems
    Foundry User can build and change things inside a project, and a key carries no role restrictions at all. The credential of a front-end service can then modify agents or read other project data if it leaks.
    How to recognise it
    The role assignments on the resource show application service principals holding Foundry User, or application settings contain a Foundry key.
    How to fix it
    Authenticate with Microsoft Entra ID and assign Foundry Agent Consumer at project scope or at the scope of the single agent. The RBAC page notes that the Azure portal assigns this role only at account scope, so use the Azure CLI for the narrower scopes.

  3. Publishing an agent and assuming the tool permissions it had in development came with it.

    Why it causes problems
    A published agent runs under a new identity that has none of the shared project identity's roles. Tool calls fail in production, and under pressure someone grants a broad role to make the error go away.
    How to recognise it
    Authorisation errors from tool calls that start immediately after publishing, while role assignments exist only for the project's shared agent identity. A wrong audience value on the tool connection gives the same symptom even when the roles are right.
    How to fix it
    Make the role assignments for the published agent's identity a scripted release step, scoped to the specific resource, and check that the connection's audience is the downstream service's resource identifier and not the tool server's URL.

  4. Editing agents by hand in the portal while the model deployment is allowed to upgrade itself.

    Why it causes problems
    Behaviour changes with no record. Nobody can reproduce last week's agent, an automatic model update alters answers before any test has run, and because Agent Service has no built-in recovery, a definition that exists only in the service can be lost for good.
    How to recognise it
    Agent versions with no matching commit or pipeline run, and a deployment whose version upgrade option is set to upgrade automatically.
    How to fix it
    Keep agent definitions, instructions and connections in source control, create versions from a pipeline, pin the model version, and rerun the evaluation before changing either one.

  5. Treating a pass on a handful of test rows as proof that the agent is ready.

    Why it causes problems
    With few rows one answer moves the pass rate by tens of points, and an LLM judge adds its own run-to-run variation. A regression ships, or a good change is blocked, by chance.
    How to recognise it
    A dataset of a dozen queries, pass rates that change between identical runs, and reports that show a percentage with no interval around it.
    How to fix it
    Grow the dataset from production traces and synthetic queries, gate on a lower confidence bound and not on the raw rate, and compare versions under the same evaluation. The GitHub Action reports confidence intervals and significance tests for this reason.

  6. Leaving content recording on for traces of conversations that contain personal data or secrets.

    Why it causes problems
    Prompts, tool arguments and tool results are copied into telemetry, which has different readers and a different retention period from the conversation store. Data that was carefully protected in one place is now exposed in another.
    How to recognise it
    Full message text and tool arguments are visible in span attributes in Application Insights, and people with a log reader role can see customer content.
    How to fix it
    Turn content recording off or redact sensitive values before they reach telemetry, restrict access to the table that holds sensitive content, and apply the same retention policy as for other production logs.

The gate in the worked example blocks a release when a pass rate is below 85%. It has two weaknesses: it ignores how many rows the rate is based on, and it prints no reason. Write wilson_gate.py, using only the Python standard library, to fix both.

Hint 1

Compute the pass rate from passed and failed only. Check the errored count as a separate condition, so that a row the evaluator could not score never counts as a pass.

Hint 2

When every row passes, the square root term in the formula simplifies and the lower bound becomes n divided by (n plus z squared). Use that to check your function by hand for n = 3.

Hint 3

For the last requirement a loop that tries n = 1, 2, 3 and so on is enough.

Show solution
python
import math

Z = 1.96            # 95% confidence
MIN_RATE = 0.85     # the observed pass rate must reach this
MIN_LOWER = 0.80    # the Wilson lower bound must reach this

SMALL_RUN = [
    {"testing_criteria": "task_adherence", "passed": 52, "failed": 8, "errored": 0},
    {"testing_criteria": "tool_call_accuracy", "passed": 55, "failed": 5, "errored": 0},
    {"testing_criteria": "violence", "passed": 60, "failed": 0, "errored": 0},
]
LARGE_RUN = [
    {"testing_criteria": "task_adherence", "passed": 172, "failed": 28, "errored": 0},
    {"testing_criteria": "tool_call_accuracy", "passed": 181, "failed": 19, "errored": 0},
    {"testing_criteria": "violence", "passed": 199, "failed": 0, "errored": 1},
]


def wilson_lower(passed, total, z=Z):
    """Lower end of the Wilson score interval for a pass rate."""
    if total == 0:
        return 0.0
    p = passed / total
    centre = p + z * z / (2 * total)
    margin = z * math.sqrt(p * (1 - p) / total + z * z / (4 * total * total))
    return (centre - margin) / (1 + z * z / total)


def decide(run):
    """Return (criterion, pass rate, lower bound, reasons) for every criterion."""
    report = []
    for row in run:
        total = row["passed"] + row["failed"]
        rate = row["passed"] / total if total else 0.0
        lower = wilson_lower(row["passed"], total)
        reasons = []
        if row["errored"] > 0:
            reasons.append(f"{row['errored']} errored")
        if rate < MIN_RATE:
            reasons.append("rate below 85%")
        if lower < MIN_LOWER:
            reasons.append("lower bound below 0.80")
        report.append((row["testing_criteria"], rate, lower, reasons))
    return report


def show(title, run):
    report = decide(run)
    print(title)
    for name, rate, lower, reasons in report:
        verdict = "ok" if not reasons else "FAIL: " + ", ".join(reasons)
        print(f"  {name:<20}{rate:>7.1%}  lower {lower:.3f}  {verdict}")
    blocked = any(reasons for *_, reasons in report)
    print("  release:", "blocked" if blocked else "allowed")


def clean_rows_needed(target, z=Z):
    """Smallest n for which n passes out of n gives a lower bound of at least target."""
    n = 1
    while wilson_lower(n, n, z) < target:
        n += 1
    return n


if __name__ == "__main__":
    show("small run (60 rows)", SMALL_RUN)
    show("large run (200 rows)", LARGE_RUN)
    print(f"3 of 3 passed -> lower bound {wilson_lower(3, 3):.3f}")
    print("clean rows needed for a lower bound of 0.85:", clean_rows_needed(0.85))

Running python3 wilson_gate.py prints the output shown under expected behaviour.

Why the two runs differ. Task adherence passes about 86% of rows in both runs, but 52 of 60 is weaker evidence than 172 of 200. The lower bound is 0.758 for the small run and 0.805 for the large one, so only the large run supports the claim that the true rate is at least 80%. The large run is still blocked, because one violence row errored. An errored row is a row nobody scored, and a safety criterion should not pass on missing data.

The last two lines put a number on the worked example's warning. Three passes out of three give a lower bound of 3 / (3 + 3.8416) = 0.438, which is compatible with an agent that fails more than half the time. You need 22 clean rows before a perfect score supports a rate of 85%: 22 / 25.8416 = 0.851, while 21 rows give 0.845.

The microsoft/ai-agent-evals GitHub Action reports confidence intervals and a significance test when it compares agent versions. The same reasoning applies there. Read the interval, not only the score.
