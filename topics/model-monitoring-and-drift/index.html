Model Monitoring and Drift

Model monitoring is the continuous measurement of a deployed model's inputs, predictions and, once the true outcomes arrive, its accuracy. Drift is the change it looks for: the input data moving away from the training data, the relationship between inputs and outcomes changing, or the serving pipeline computing features differently from the training pipeline.

1Overview

Why it matters

A model that has gone wrong does not throw an exception. It keeps returning well-formed predictions at normal latency, so the service dashboards stay green while quality decays. Google's Rules of Machine Learning records a Google Play table that was stale for six months; refreshing it alone raised the install rate by 2%. Uber describes a dataset used to train its fares models that lost one field in 10% of sessions for 45 days, until a data scientist found the gap by hand. Nothing crashed in either case.

The offline evaluation you ran before deployment cannot catch this, because it describes one frozen dataset. After launch the population of requests shifts, behaviour changes, upstream teams rename fields, and the true labels may not arrive for weeks. ML engineers, the data scientists who own a model and the platform engineers who run the serving stack all need to know which signals exist at each moment, which kind of change each signal can reveal, and which response fits: fix a pipeline, roll back, retrain, or leave the model alone.

  • Decide whether an alert calls for a pipeline fix, a rollback, a retrain or no action, and define the triggers that start a retraining run.

Key terms

Baseline (reference) window
The data a monitor compares against. It is usually the training set or an earlier stretch of production traffic.
Data drift
A change in the distribution of the model's inputs, written P(X), while the rule that links inputs to outcomes may be unchanged. Also called covariate shift.
Concept drift
A change in the relationship between inputs and the true outcome, written P(y|X), so that the same input now deserves a different prediction.
Training-serving skew
A difference between the data or code path used to train a model and the one used to serve it. It is typically an engineering discrepancy, not a change in the world.
Prediction drift
A change in the distribution of the model's outputs, such as the mean score or the share of positive predictions.
Ground truth (label)
The true outcome for a prediction, such as whether the customer really cancelled. In production it often arrives days or months after the prediction was made.
Label delay
The time between making a prediction and learning its true outcome. A window of predictions is mature once this time has passed for every row in it.
Population stability index (PSI)
A distance between two binned distributions. It sums, over the bins, the difference in share multiplied by the logarithm of the ratio of the shares.
Kolmogorov-Smirnov statistic
The largest vertical gap between the cumulative distributions of two samples. It is a number between 0 and 1.
Retraining trigger
The rule that starts a retraining run, such as a schedule, the arrival of new labelled data, a drop in measured accuracy or a drift alert.

2Explanation

Introduction

You have trained a classifier, measured its precision and recall on a held-out test set, and put it behind an API. Those numbers describe one dataset, frozen on the day you built it. Production is not frozen: next month's requests come from different people, in a different season, through code that someone has since changed.

Take a subscription service that scores every customer each week with the probability that they will cancel within 30 days. This churn model was trained on January's customers. Three different things can go wrong after launch, and they need different responses:

  • Data drift. A marketing campaign brings in thousands of brand-new customers. The model now sees far more short-tenure customers than it was trained on. The inputs changed.
  • Concept drift. The company raises its prices on 1 February. A customer with exactly the same usage pattern as before is now more likely to cancel. The inputs look the same; the right answer changed.
  • Training-serving skew. The training pipeline computed sessions_7d over a full seven days, but the serving code counts sessions since midnight. The model receives smaller numbers than it learned from. Nothing in the world changed; the two pipelines disagree.

In all three cases the service keeps returning a number between 0 and 1 within a few milliseconds. No error is raised. There is a fourth difficulty on top: the true label, "cancelled within 30 days", does not exist until 30 days after the prediction, so accuracy cannot be measured on the day it starts to fall.

Model monitoring is how you find out anyway. Every prediction is logged together with the inputs the model saw. A scheduled job then compares a recent window of that log with a baseline (the training data, or an earlier stretch of production traffic) at three layers: the inputs, the predictions and, when they finally arrive, the true outcomes. If a comparison crosses a threshold, someone is alerted, works out which kind of change it is, and chooses a response.

This lesson covers how to tell the three kinds of change apart, what to log, how to measure the distance between two distributions and set a threshold on it, how to work with labels that arrive late, and how alerts turn into decisions to fix, roll back or retrain. It builds on model deployment and serving and classification metrics, and it supplies the triggers used in ML pipelines and continuous training.

How it works

Three ways production diverges from training

A supervised model learns from pairs of inputs XXX and outcomes yyy. Their joint distribution factors as

P(X,y)=P(X) P(y∣X)P(X, y) = P(X)\,P(y \mid X)P(X,y)=P(X)P(y∣X)

The review by Lu and colleagues (opens in a new tab) defines concept drift as a change in this joint distribution over time and separates its sources. If only P(X)P(X)P(X) moves, the mix of inputs has changed while the rule that maps an input to its outcome has not. The review calls this virtual drift; this lesson uses the common industry name, data drift. If P(y∣X)P(y \mid X)P(y∣X) moves, the same input now has a different correct answer and accuracy falls. This lesson reserves concept drift for that case. In practice both often move together. Drift also has a shape in time: sudden (a price change), gradual or incremental (habits shifting over months) or recurring (seasons).

Training-serving skew is different in kind. Google's Rules of Machine Learning (opens in a new tab) define it as a difference between performance during training and performance during serving, and the first cause they list is a discrepancy between how the two pipelines handle data. That is an engineering error, present from the first request. Rule #37 gives the test: a model applied to the same example in training and at serving should give exactly the same result.

Product documentation uses these words more loosely. Google's managed monitoring, for example, calls any gap between the production and training distributions "training-serving skew" and change over time "drift", whatever the cause. Check the definition before comparing tools.

Log every prediction

Monitoring reads from a prediction log. For each request, store a unique ID, a timestamp, the model version, the feature values exactly as the model received them, and the output. Logging the served features (Rule #29 in the same guide) is what makes skew measurable, and the ID is what lets a label that arrives weeks later be joined to its prediction.

Three layers of signals

  1. Inputs, available immediately. Data-quality checks come first: the null rate, the type-error rate and the out-of-range rate of each feature, three metrics that Azure Machine Learning's monitoring guide (opens in a new tab) defines precisely. Then comes a distribution distance per feature against the baseline.
  2. Predictions, available immediately. Track the distribution of scores, their mean and the share of positive predictions. The ML Test Score (opens in a new tab) rubric recommends watching the average prediction per slice as a canary: an unbiased model is not necessarily good, but a biased one has a problem.
  3. Outcomes, available after the label delay. The metrics you computed offline, such as precision, recall and calibration, now on labelled production data, in total and per slice.

Add two cheap operational signals: service health (latency, error rate) and the age of the model and of every table it reads.

Each layer has a blind spot. Inputs and predictions arrive at once but cannot reveal concept drift: the NannyML documentation (opens in a new tab) states that, apart from very specific cases, it cannot be identified without ground truth. Outcomes reveal everything, late.

Measuring the distance between two distributions

Put the baseline values and the current values of a feature into the same bins (for a categorical feature, one bin per value). Let pip_ipi​ be the baseline share of bin iii and qiq_iqi​ the current share.

  • L-infinity distance: d∞=max⁡i∣pi−qi∣d_\infty = \max_i |p_i - q_i|d∞​=maxi​∣pi​−qi​∣, the largest change in share of any single bin. A threshold reads as "no value may gain or lose more than 5 points", and the bin that attains the maximum is the first place to look.
  • Population stability index: PSI=∑i(qi−pi) ln⁡(qi/pi)\text{PSI} = \sum_i (q_i - p_i)\,\ln(q_i / p_i)PSI=∑i​(qi​−pi​)ln(qi​/pi​). Every term is zero or positive. This is the formula in Evidently's open-source implementation (opens in a new tab), which flags drift at 0.1 by default.
  • Jensen-Shannon divergence: with mi=(pi+qi)/2m_i = (p_i + q_i)/2mi​=(pi​+qi​)/2, JS=12∑ipilog⁡2(pi/mi)+12∑iqilog⁡2(qi/mi)\text{JS} = \tfrac{1}{2}\sum_i p_i \log_2 (p_i/m_i) + \tfrac{1}{2}\sum_i q_i \log_2 (q_i/m_i)JS=21​∑i​pi​log2​(pi​/mi​)+21​∑i​qi​log2​(qi​/mi​). It is symmetric and stays between 0 and 1 even when a bin is empty.
  • Kolmogorov-Smirnov (KS) statistic: D=max⁡x∣Fp(x)−Fq(x)∣D = \max_x |F_p(x) - F_q(x)|D=maxx​∣Fp​(x)−Fq​(x)∣, the largest gap between the two cumulative distributions. It needs no bins, and scipy.stats.ks_2samp (opens in a new tab) returns it together with a p-value.

Google's managed monitoring uses L-infinity for categorical features and Jensen-Shannon for numerical ones, with a default alert threshold of 0.3 (overview (opens in a new tab)). Defaults differ between tools because no threshold is universal.

Alert on the distance, not on a p-value. A p-value answers "could this gap be sampling noise?", and with enough rows the answer is always no. For two windows of nnn and mmm rows, the large-sample KS p-value is approximately

p≈2∑k=1∞(−1)k−1e−2k2λ2,λ=Dnmn+mp \approx 2\sum_{k=1}^{\infty} (-1)^{k-1} e^{-2k^2\lambda^2}, \qquad \lambda = D\sqrt{\frac{nm}{n+m}}p≈2k=1∑∞​(−1)k−1e−2k2λ2,λ=Dn+mnm​​

The same harmless 2-point gap is "not significant" at 2,000 rows per window and "highly significant" at 20,000. The authors of Google's data validation system report the same problem (opens in a new tab) with chi-square tests, and Evidently's default methods (opens in a new tab) switch from statistical tests to distances once the reference data exceeds 1,000 rows. Use p-values only on small windows, and require a minimum row count before any distance may raise an alert.

Baselines and windows

Comparing with the training data detects skew from day one and accumulates slow drift. Comparing with an earlier production window detects sudden change and adapts to seasonality, but a slow drift never crosses the threshold because the baseline drifts with it. Many teams run both. Make the current window long enough to hold a stable number of rows and one full weekly cycle, and keep it from overlapping the baseline window.

Labels that arrive late

  • Join by ID. When an outcome becomes known, write it with the prediction's ID and join it to the log. SageMaker Model Monitor (opens in a new tab) documents this pattern: labels are uploaded later and merged with captured predictions on an inference ID. (The same page notes that the service is no longer open to new customers.)
  • Wait for maturity. Evaluate only windows whose label period has fully elapsed. A week-old batch of 30-day churn predictions has labels only for customers who have already cancelled. Counting the rest as negatives understates both the churn rate and the precision.
  • Use early signals meanwhile. Prediction drift, a faster proxy outcome (cancellations in the first 7 days), human-labelled samples, or performance estimated from calibrated scores. Estimates assume P(y∣X)P(y \mid X)P(y∣X) has not changed, so they account for data drift only.
  • Beware of labels your model shapes. If a high score triggers a retention offer, the outcome is no longer what would have happened without the model. Keep a small untreated holdout, as in an A/B test.

Alerts and retraining triggers

An alert needs a metric, a window, a threshold, an owner and a first action. Set thresholds by replaying the monitor over past weeks and placing the limit above normal week-to-week variation. Page a person for hard data-quality failures and confirmed accuracy drops; send distribution drift to a ticket or a dashboard. Alerts that are noisy or not actionable get ignored.

Diagnose before responding. Skew or a broken upstream source calls for a pipeline fix or a rollback, not a retrain, because retraining teaches the model the broken data. Data drift without labels calls for watching the affected slice. Concept drift confirmed by labels calls for retraining on recent data.

Google's MLOps guide (opens in a new tab) lists the triggers for a retraining pipeline: on demand, on a schedule, when new training data is available, on performance degradation, and on significant change in the data distributions. A schedule set by how fast accuracy decays, plus a performance trigger for surprises, covers most systems. Whatever starts the run, the new model must beat the current one on recent held-out data before it is promoted.

Step 3: confirm in Python

The script uses only the standard library.

python
from math import log

ref_counts = [1000, 2000, 2500, 2500, 2000]   # training data
cur_counts = [500, 480, 400, 360, 260]        # last 7 days

def shares(counts):
    total = sum(counts)
    return [c / total for c in counts]

def l_infinity(p, q):
    return max(abs(a - b) for a, b in zip(p, q))

def psi(p, q):
    return sum((b - a) * log(b / a) for a, b in zip(p, q))

def js_divergence(p, q):
    m = [(a + b) / 2 for a, b in zip(p, q)]
    kl = lambda u, v: sum(a * log(a / b, 2) for a, b in zip(u, v) if a > 0)
    return 0.5 * kl(p, m) + 0.5 * kl(q, m)

def ks_binned(p, q):
    gap = cum_p = cum_q = 0.0
    for a, b in zip(p, q):
        cum_p, cum_q = cum_p + a, cum_q + b
        gap = max(gap, abs(cum_p - cum_q))
    return gap

p, q = shares(ref_counts), shares(cur_counts)
print(f"L-infinity {l_infinity(p, q):.4f}  PSI {psi(p, q):.4f}  "
      f"JS {js_divergence(p, q):.4f}  KS {ks_binned(p, q):.4f}")

avg_score = [0.30, 0.18, 0.10, 0.07, 0.05]    # mean predicted churn probability per bin
print(f"mean score: baseline {sum(a * s for a, s in zip(p, avg_score)):.4f}, "
      f"current {sum(b * s for b, s in zip(q, avg_score)):.4f}")

Step 4: read the input layer

A PSI of 0.209 is above Evidently's default of 0.1, and Evidently's comparison of drift methods (opens in a new tab) labels 0.2 and above a significant change. An L-infinity of 0.15 is below the 0.3 default of Google's managed monitoring. The same data alerts in one tool and not in another, which is why a threshold has to be set per feature from that feature's own history. L-infinity also names the culprit: the 0–30 day bin grew from 10% to 25% of customers. That matches the marketing campaign, so this is real data drift and not a pipeline fault.

Step 5: read the prediction layer

Suppose the model's average predicted churn probability in the five bins is 0.30, 0.18, 0.10, 0.07 and 0.05 in both periods. The mean score is the share-weighted average: 0.10×0.30+0.20×0.18+⋯=0.11850.10 \times 0.30 + 0.20 \times 0.18 + \dots = 0.11850.10×0.30+0.20×0.18+⋯=0.1185 in training and 0.25×0.30+0.24×0.18+⋯=0.15730.25 \times 0.30 + 0.24 \times 0.18 + \dots = 0.15730.25×0.30+0.24×0.18+⋯=0.1573 now. The mean prediction rose by a third, yet the model behaves exactly as before inside every bin. The prediction drift is fully explained by the change in the input mix. Nothing so far says the model is wrong.

What the three layers said

  • Day 0, inputs: data drift in tenure_days with a known cause. Response: record it and watch the new-customer slice.
  • Day 0, predictions: the mean score moved from 11.9% to 15.7%, all of it explained by the inputs.
  • Day 30, outcomes: 21.75% actual churn against 15.7% predicted, wrong within segments. Response: retrain on data from after the price change, and validate the new model on the most recent labelled week before promoting it.

The input alert arrived a month before the proof, and it pointed at a different cause. Data drift showed where to look; only the labels showed that the model had become wrong.

Edge cases and limitations

Drift that does not hurt, and harm that shows no drift
A feature the model barely uses can drift far without changing a single decision, and a model can lose accuracy while every input distribution stays flat, because concept drift changes the outcome and not the inputs. An input alert is therefore a reason to look, not proof of damage, and a quiet input dashboard is not proof of health. Weight input alerts by feature importance and always pair them with a label-based metric, however late it arrives.
An empty bin makes PSI infinite
PSI divides one share by the other and takes a logarithm, so a category that is new in production (a baseline share of zero) or one that has vanished gives an infinite or undefined value. Evidently's implementation replaces zero shares with a small positive number such as 0.0001 before computing. Either apply a floor like that, or use L-infinity or Jensen-Shannon, which stay finite. Treat the appearance of a new category as a data-quality event in its own right.
Small windows give noisy distances
With 200 rows spread over ten bins, each share carries a sampling error of a few percentage points. In a simulation run for this lesson, two 200-row samples drawn from the same ten-bin distribution gave a PSI above 0.1 in about 39% of runs, and in about 3% of runs when one side was a 10,000-row baseline. Require a minimum number of rows before a distance may alert, and widen the window or use fewer bins for low-traffic models.
Seasonality looks like drift
Weekend traffic differs from weekday traffic, and December differs from June. A daily window compared with a baseline built on a different part of the cycle will alert every week. Use windows that cover a whole cycle, compare like with like (this Monday against last Monday), or build the baseline from a period long enough to contain the cycle. Recurring drift is expected and should not trigger a retrain by itself.
The model changes its own labels
When a prediction causes an action, the outcome you later record is no longer independent of the model. A ranking model only gets clicks on the items it chose to show, and a churn model that triggers retention offers lowers the churn it predicted. Measured accuracy is then biased and the next training set inherits the bias. Keep a small randomly chosen group that is not acted on, and compute monitoring metrics on that group.
Text, images and embeddings have no natural bins
Per-feature histograms assume a small number of meaningful columns. For raw text, Evidently's documentation describes a different approach: train a classifier to tell baseline rows from current rows and use its ROC AUC as the drift score, with a default alert above 0.55 on larger datasets. An AUC near 0.5 means the two periods are indistinguishable. Simple descriptors such as text length can also be monitored like any numeric feature.

When to use it, and when something simpler is enough

Use it when

  • The model's predictions drive decisions for weeks or months after training, so the data it sees will differ from the data it learned from.
  • Labels arrive late, or only for some predictions, so input and prediction signals are the only early warning you have.
  • Features come from pipelines or teams you do not control, where a renamed field or a stale table would not raise an error.
  • Retraining is automated and needs a gate that stops bad data or a worse model from being promoted.

Think twice when

  • The model is used once for a batch analysis and never refreshed. Evaluate it on a holdout and stop.
  • Traffic is a few dozen predictions a week. Distances on windows that small are noise, so review the predictions and outcomes by hand in a periodic report.
  • You have no prediction log and no data-quality checks yet. Build those first, because a drift alert on features that were never logged cannot be investigated.

A simpler alternative. Retrain on a fixed schedule, compare each new model with the current one on the most recent labelled data, and keep three cheap checks: the null rate and value range of each feature, the mean prediction per day, and the age of the model. This is often enough when labels arrive within days and a mistake is cheap. It stops being enough when labels take weeks, when upstream data changes without notice, or when one bad week of predictions is expensive.

Key takeaways

  • A deployed model fails silently, so its inputs, its predictions and its outcomes have to be measured continuously against a baseline.
  • Data drift is a change in the inputs, concept drift is a change in the correct answer for the same input, and training-serving skew is a disagreement between the two pipelines, and each needs a different response.
  • Input and prediction signals are available immediately but cannot prove that the model is wrong. Only labelled outcomes can, and they arrive late.
  • Alert on a distance such as L-infinity, PSI or Jensen-Shannon, with a threshold tuned from the feature's own history, because p-values flag trivial differences on large windows.
  • Measure accuracy only on windows whose labels have matured, joined to the predictions by a logged ID.
  • Diagnose before retraining. Fix or roll back for skew and broken data, retrain for concept drift confirmed by labels, and validate every new model before promoting it.

Example 1 of 5

Google Play recommendations: TFX data validation finds features missing at serving time

GoogleDocumented in a paper

"Data Validation for Machine Learning" (Breck and co-authors, SysML 2019) describes the data validation component of TFX, Google's machine learning platform, and reports case studies from its production use, including the Google Play app recommender. The TensorFlow Data Validation get-started guide documents the skew and drift comparators of the open-source library. [14][15]

The problem

Training data and serving data are usually produced by different code paths, because offline generation and online serving have very different latency and throughput needs. When the two paths disagree, for example a feature is present in training but missing or pinned to a default value at serving, the model keeps producing predictions at lower quality and nothing fails. The paper's opening example is a refactoring in the serving stack that sets an integer feature to -1 for part of the traffic; since -1 is a valid value, the error flows into the next day's training data unnoticed.

Where this topic fits

The validator sits between the serving logs and the training pipeline. The serving infrastructure logs a sample of the serving data, which is imported back into the training pipeline. The validator compares batches of training and serving data continuously, checks each batch against a schema, and sends anomalies to the platform's standard alerting, where an on-call engineer picks them up.

How it is applied, step by step

  1. Describe the expected data in a schema: the type of each feature, whether it must be present and which values it may take. The schema is versioned and reviewed like code.
  2. Log a sample of real serving requests with their feature values and import them into the training pipeline next to the training batches.
  3. To find feature skew, join training and serving examples on a key and compare the two versions of each example feature by feature. The values should be identical.
  4. To find distribution skew, compute the L-infinity distance between the training and serving distributions of each feature and compare it with the threshold stored in the schema for that feature.
  5. Raise an anomaly that names the feature and the value whose share changed most, so that the on-call engineer starts with a concrete suspect such as a default value that has become common.
  6. Fix the code path so the feature is produced the same way on both sides, and confirm the effect with an online experiment.

Why this approach fits

Skew is an engineering fault, so the direct test is to put the two pipelines' outputs side by side. That needs no labels and works from the first day of serving. The L-infinity distance suits an on-call workflow: its threshold has a plain meaning (the largest allowed change in the share of any one value) and every alert arrives with the value responsible.

Limitation or tradeoff

The method needs serving data to be logged and, for feature-level comparison, a key to join on. Thresholds must be chosen per feature. The paper says the third kind of skew it describes, scoring/serving skew, where only the items that were actually shown ever receive labels, is harder to detect than the other two. A clean comparison of inputs also says nothing about concept drift.

What the sources document

  • The data validation system is deployed in production as part of TFX and is used by hundreds of product teams to continuously monitor and validate several petabytes of production data per day. [14]
  • The paper divides training-serving skew into feature skew, distribution skew and scoring/serving skew, and names different code paths for generating training and serving data as the most common cause. [14]
  • For distribution skew the authors use the L-infinity distance, the largest change in probability for any value, because teams can set a threshold on it easily and an alert comes with a culprit value. In their experiment a chi-square test rejected in 7 of 10 trials after 10 thousand of 100 million points had been replaced. [14]
  • Using the system, Google Play found a few features that were always missing from the logs but always present in training. An online A/B experiment showed that removing this skew improved the app install rate on the main landing page of the store by 2%. [14]

Facebook ad click prediction: measuring staleness to justify daily retraining

Facebook (Meta)Documented in a paper

"Practical Lessons from Predicting Clicks on Ads at Facebook" (He and co-authors, ADKDD 2014) reports experiments on Facebook's ad click-prediction system. It measures how accuracy changes with the age of the training data and describes an experimental "online joiner" that attaches click labels to ad impressions. [16]

The problem

Click prediction runs in an environment where, in the paper's words, the data distribution changes over time. The team needed to know how fast a trained model loses accuracy, and therefore how often it must be retrained. Training on fresh data also needs fresh labels, and a non-click is never observed directly: there is no "no click" button, only the absence of a click after some time.

Where this topic fits

Monitoring ideas appear in two places. An offline experiment measures the cost of staleness, which turns drift into a number and sets the retraining trigger, here a schedule. The label pipeline then handles delayed labels: impressions wait in a buffer for a fixed window before they are emitted as clicked or not clicked, and a guard watches the resulting stream.

How it is applied, step by step

  1. Train a model on one day of data and evaluate it on each of the six following days, using normalized entropy as the metric (lower is better).
  2. Read the staleness curve: accuracy degrades as the gap between training day and test day grows, for boosted trees and for logistic regression alike.
  3. Turn the curve into a schedule. The measured gain from weekly to daily training supports retraining the trees daily or every couple of days, and updating the linear layer continuously.
  4. Build labels for fresh data. Log each impression with its features and a request ID, wait a fixed window for a click with the same ID, then emit a positive example if one arrived and a negative example if not.
  5. Tune the window. A long window delays training data and costs memory; a short window loses late clicks, which labels true positives as negatives and biases the observed click rate downward.
  6. Guard the loop. If the click stream goes stale, the joiner emits almost no positives, so the paper suggests anomaly detection that disconnects the online trainer when the training stream changes abruptly.

Why this approach fits

In advertising, labels arrive within minutes, so accuracy on labelled production data is available almost at once. That makes it possible to measure what drift costs directly, in the model's own metric, and to set the retraining interval from evidence. A schedule is also the easiest trigger to operate: it is predictable, and it needs no alert threshold.

Limitation or tradeoff

The figures describe one system in 2014 and should not be copied; each model needs its own staleness curve, and the curve can change. A schedule retrains even when nothing has changed and cannot react faster than its interval to a sudden shift. The waiting window trades label accuracy against freshness, and a continuously trained model can be corrupted quickly by bad input data, which is why the paper adds a guard.

What the sources document

  • The authors train a model on one day of data and evaluate it on the six consecutive days. They report that prediction accuracy clearly degrades for both models as the delay between training and test set increases. [16]
  • The paper states that normalized entropy can be reduced by approximately 1% by going from training weekly to training daily, and concludes that it is worth retraining on a daily basis. [16]
  • An impression receives a negative label if the user did not click within a fixed waiting window. Too long a window delays the real-time training data, and too short a window loses clicks, which lowers click coverage and makes the empirical click-through rate somewhat lower than the truth. [16]
  • The online joiner performs a distributed stream-to-stream join of ad impressions and ad clicks using a request ID as the primary component of the join predicate. [16]
  • The paper describes protecting the system with anomaly detection, for example automatically disconnecting the online trainer from the online joiner if the real-time training data distribution changes abruptly. [16]

The pages are published under the vertex-ai documentation path and name the product Gemini Enterprise Agent Platform. [12][13]

The problem

A team with a tabular model on an online endpoint wants to be told when the input features move away from the training data, or away from earlier production traffic, without building the request logging, histogram computation and alert delivery themselves. The overview's own example is a customer lifetime value model whose features lose relevance as customer habits change.

Where this topic fits

The feature is configured on the endpoint, after deployment. It covers the input layer only: it logs prediction requests, computes one distance per feature at a fixed interval and sends alerts. What to do about an alert, such as adjusting a feature pipeline or retraining, is left to the team.

How it is applied, step by step

  1. Enable monitoring on the endpoint and set the sampling rate for request logging and the monitoring frequency, which also sets the size of the window analysed in each run.
  2. Choose the objective. Skew detection needs the training data and the name of the target column; drift detection needs no training data. Both can be enabled together.
  3. The service logs incoming prediction requests to a BigQuery table and builds the baseline distribution: the training data for skew, earlier production data for drift.
  4. At each interval it computes the latest distribution of every feature and a distance from the baseline: L-infinity for categorical features and Jensen-Shannon divergence for numerical ones.
  5. Each distance is compared with that feature's threshold, 0.3 unless you set another value. If any feature exceeds its threshold, an email names the feature, the threshold and the measured distance.
  6. Optionally the anomaly is also written to Cloud Logging, from where it can be forwarded to other services, and the team inspects the per-feature histograms in the console.

Why this approach fits

For a tabular model on a managed endpoint this removes most of the plumbing: logging, binning, distance computation, scheduling and notification are configuration. The service alerts on distances with per-feature thresholds, not on p-values, so the alert rate does not grow with traffic, and sampling keeps the cost of logging under control.

Limitation or tradeoff

The v1 feature described on these pages watches input feature distributions. It does not compare predictions with labels, so it can report data drift and skew but not concept drift or a fall in accuracy. The 0.3 default is generic and should be tuned per feature. The type of detection, the frequency and the sampling rate are shared by all models on an endpoint. The overview describes v2, which adds output drift and feature attribution objectives, as a Preview offering.

What the sources document

  • The overview says training-serving skew occurs when the feature data distribution in production deviates from the distribution used to train the model, and inference drift occurs when the production feature distribution changes significantly over time. At each monitoring interval, if at least one feature exceeds its threshold, an email alert reports the time of the job, the feature name, the alerting threshold and the recorded distance. Uber D3: learned thresholds on column statistics after a 45-day silent data incident

The problem

A fare component went missing from a critical fares dataset for 10% of sessions in key US cities after an app experiment changed how fares were logged. Nothing failed, and the gap was found by hand 45 days later. The post explains that data observability at the time relied on manually written SQL tests with static alert thresholds, which need constant re-calibration as data trends change, and that configuring more than 100 monitors per dataset by hand took days.

Where this topic fits

D3 sits upstream of the models, on the datasets that feed training and analytics. It is monitoring of the input layer before a model is trained on the data: each column statistic becomes a time series, an anomaly detector judges the newest point, and alerts go to the dataset's owners.

How it is applied, step by step

  1. For each dataset, compute column monitors such as the null percentage, percentiles, mean, standard deviation and distinct count, optionally split by a dimension.
  2. Treat each monitor as a time series with one value per period, so that the question becomes whether the newest value fits the series' history.
  3. Forecast the expected value from that history with a model that handles trend and seasonality (Prophet by default) and flag values outside the predicted limits. The threshold therefore moves with the data.
  4. Protect alert quality. Tune for high precision with conservative limits, let users tag flagged points as true or false outliers, and disable alerting on series that a diagnosis job finds too noisy to forecast.
  5. Send alerts through the existing data monitoring service and on-call paging, as for other services.
  6. Onboard datasets automatically by choosing the most-used columns and default monitors for each data type, so coverage does not depend on manual setup.

Why this approach fits

The incident was a change in a simple statistic, the share of rows missing one field, that nobody had written a rule for. Watching many statistics per column catches that class of fault without predicting it in advance, and learned thresholds make this workable across hundreds of datasets where hand-set limits would be either too loose or permanently firing. Checking data before it is used for training protects every model built on it.

Limitation or tradeoff

This monitors data, not model quality. A column statistic can stay inside its limits while the relationship between features and outcomes changes. A forecast that adapts to trend can absorb a slow drift as normal, tuning for precision means some real issues are missed, and series that are switched off for noise are blind spots. The post names monitoring feature drift and training-serving differences for ML models as future work for the framework.

4Common mistakes

  1. Starting a retraining run automatically whenever a drift alert fires.

    Why it causes problems
    If the alert was caused by a pipeline bug or a broken upstream source, retraining teaches the model the broken data. The data validation paper from Google describes exactly this loop: a serving bug writes a default value, the serving data becomes the next day's training data, and the new model inherits the fault. When the drift is harmless, the retrain spends compute and adds release risk for nothing.
    How to recognise it
    Retraining jobs are triggered by input-distance alerts with no diagnosis step between them. A retrain "fixes" the alert because the baseline was refreshed, yet live quality does not recover. The alert coincides with a jump in a null rate or in the share of one default value, or with a deployment.
    How to fix it
    Put a diagnosis step between alert and action: check data-quality signals and recent deployments first. Trigger retraining mainly on a schedule and on measured performance, and require the new model to beat the current one on recent labelled data before promotion.

  2. Using a statistical test's p-value below 0.05 as the alert condition on large windows.

    Why it causes problems
    With tens of thousands of rows per window, a difference too small to affect any prediction is statistically significant. Every feature alerts on every run, the on-call engineer learns to ignore the channel, and the one alert that matters is lost among them.
    How to recognise it
    Nearly all features are flagged as drifted in every run, the number of flags rises with traffic, and the flagged features show distances of one or two percentage points when you look at the histograms.
    How to fix it
    Alert on an effect size such as L-infinity, PSI, Jensen-Shannon or the KS statistic itself, with a threshold tuned from history. Keep p-values for windows of roughly a thousand rows or fewer, or run the test on a fixed-size random sample.

  3. Monitoring only service health, or only label-based accuracy.

    Why it causes problems
    Latency and error-rate dashboards stay green while predictions go wrong, because a model returns a well-formed number for any input. Accuracy alone is correct but late: with a 30-day label delay, a fault introduced today is confirmed a month from now, after a month of bad decisions.
    How to recognise it
    The only alerts on the model's service are for latency, errors and resource use, or the only quality chart is a monthly accuracy figure. Incidents are first reported by users or by a business metric, not by monitoring.
    How to fix it
    Cover all three layers: data-quality checks and distribution distances on inputs, the score distribution and mean prediction, and label-based metrics on matured windows. Add the age of the model and of its source tables.

  4. Computing accuracy on windows whose labels are not complete yet.

    Why it causes problems
    Rows without a label are silently treated as negatives or dropped. For outcomes that are confirmed late, recent windows then show too few positives, so precision looks far too low, or the retained rows are an unrepresentative fast-resolving subset. A healthy model appears to collapse every time the dashboard includes the latest weeks.
    How to recognise it
    The most recent points of the accuracy chart always look different from older ones and "recover" as time passes without any change to the model. The label count for a window keeps growing after the window has been reported.
    How to fix it
    Record the label delay for the use case and report a window only once every row in it has passed that delay. Show immature windows separately and mark them as provisional, alongside the share of rows that already have a label.

  5. Comparing each window only with the one before it.

    Why it causes problems
    A rolling baseline moves with the data. A feature that shifts a little every week never exceeds the threshold, although after two months it is far from what the model was trained on. The exercise below shows a PSI that stays under 0.02 week over week while reaching 0.21 against the training data.
    How to recognise it
    Week-over-week distances are consistently small, but plotting the feature's mean or its bin shares over several months shows a steady slope. A comparison with the training data has never been run.
    How to fix it
    Keep two baselines per monitored feature: the training data, to measure the total distance from what the model learned, and a recent production window, to catch sudden changes. Reset the fixed baseline only when the model is retrained.

from math import log

def shares(counts):
    total = sum(counts)
    return [c / total for c in counts]

def l_infinity(p, q):
    gaps = [abs(a - b) for a, b in zip(p, q)]
    worst = max(range(len(gaps)), key=gaps.__getitem__)
    return gaps[worst], worst

def psi(p, q, floor=0.0001):
    p = [max(a, floor) for a in p]
    q = [max(b, floor) for b in q]
    return sum((b - a) * log(b / a) for a, b in zip(p, q))

4. A model that is worse from the first day, with matching offline results on later data, points to the pipelines and not to the world. A likely mechanism is time travel: the warehouse computes open_invoices_count as of the day the training table was built, so it includes invoices issued after the one being scored, while the serving path sees only those open at scoring time. Retraining on the same table repeats the fault. Log the features at serving time and train from that log, or rebuild the warehouse feature as of each invoice's issue date.

5. On 1 June the invoices in the window are between 6 and 12 days old. No invoice can be labelled late before day 45, so the window contains zero confirmed positives: the late rate is 0% and every predicted positive counts as a false positive. The model has not changed. Restrict the dashboard to windows in which every invoice is at least 45 days old and show newer windows as provisional.

Evaluation date. The newest invoice in the window was issued on 26 May. Adding 45 days gives 10 July (5 remaining days of May, 30 days of June, 10 days of July), so the week can be evaluated from 10 July.

Check your answer

  • Did you choose retraining as the first response for situation 2 only?
  • Did you identify situation 4 as skew because the gap existed from the first day and the same invoice IDs had different feature values?
  • Did you get 10 July as the first date on which the week of 20 to 26 May is fully labelled?
  • For situation 3, did you avoid claiming that the model's accuracy has changed, since no labels exist yet?

6Curated resources

Chosen for accuracy and usefulness, not search rank. Time figures are estimates.

  • Rules of Machine Learning: Best Practices for ML Engineering (opens in a new tab)

    Google for Developers

    ArticleIntermediateFreeAbout 1 hour (estimate)

    What it teaches
    Forty-three practical rules from Google engineers. Rules 8 to 11 cover freshness requirements, checks before export and silent failures, and rules 29 to 37 cover training-serving skew, including logging features at serving time and splitting skew into measurable parts.
    When to use it
    Before you design the prediction log and the first monitors for a model, and again when live quality is lower than offline quality and you suspect skew.

  • The ML Test Score: A Rubric for ML Production Readiness and Technical Debt Reduction (opens in a new tab)

    Google (Proceedings of IEEE Big Data 2017)

    PaperIntermediateFreeAbout 40 minutes (estimate)

    What it teaches
    A rubric of 28 tests for production ML systems, seven of which are monitoring tests: dependency changes, data invariants, training-serving skew, model staleness, numerical stability, computing performance and prediction quality. Each comes with a short "how".
    When to use it
    When you audit an existing production model and need a checklist to find which monitors are missing.

  • Data drift (how data drift detection works) (opens in a new tab)

    Evidently AI documentation

    DocumentationIntermediateFreeAbout 20 minutes (estimate)

    What it teaches
    How an open-source monitoring library chooses a drift method by column type and by the size of the reference data, which default thresholds it applies, how dataset-level drift is declared from column results, and how drift in raw text is detected with a classifier.
    When to use it
    When you move from hand-computed distances to a library and need to know what its defaults do before trusting its drift flags.

  • Model monitoring in production - Azure Machine Learning (opens in a new tab)

    Microsoft Learn

    DocumentationIntermediateFreeAbout 30 minutes (estimate)

    What it teaches
    A clear catalogue of monitoring signals (data drift, prediction drift, data quality, feature attribution drift, model performance) with the reference data each one needs, exact definitions of three data-quality metrics, and worked dates for lookback window size and offset.
    When to use it
    When you set up windows and baselines for a scheduled monitor, on any platform, and want concrete examples of non-overlapping reference and production windows.

  • Learning under Concept Drift: A Review (opens in a new tab)

    arXiv (article in IEEE Transactions on Knowledge and Data Engineering)

    PaperAdvancedFreeAbout 2 hours (estimate)

    What it teaches
    The formal definition of concept drift as a change in the joint distribution, its three sources and four temporal types, and a survey of algorithms for detecting, understanding and adapting to drift in data streams.
    When to use it
    When fixed windows and thresholds are not enough, for example for streaming models, and you need to choose a drift detection or adaptation algorithm.
