Docker and Containers

A container is an ordinary Linux process that the kernel isolates with namespaces and limits with control groups. It starts from an image, a read-only stack of filesystem layers. Docker is the tool that builds images, runs containers and connects them to storage and networks.

1Overview

Why it matters

Software fails on a new machine for dull reasons: a different Python version, a missing system library, a database that is not running, a port that is already taken. A container image packages the program together with its files and libraries, so the same artefact starts the same way on a laptop, in a CI job, on a cloud service or on a server in a customer's data centre. Many deployment targets, from serverless functions to Kubernetes clusters, take a container image as their input.

The skills that matter are specific. You need to know why a rebuild takes minutes when one line changed, why a database loses its data when a container is replaced, why one container cannot reach another by name, and why a service works locally but not behind a published port. Each has a mechanical cause in layers, volumes or networks, and this lesson explains those mechanisms so that you can debug them instead of guessing.

Before you start

No prerequisites. You can start here.

What you will be able to do

  • Explain what a container is in terms of namespaces, control groups and a shared kernel, and say how it differs from a virtual machine.
  • Describe an image as a stack of immutable layers plus one writable container layer, and predict which build steps the cache will reuse.
  • Write a Dockerfile that orders its instructions for the build cache, runs as a non-root user and starts its process in exec form.
  • Choose between the writable layer, a named volume and a bind mount for a given piece of data.
  • Explain how containers reach each other and the outside world, and what a published port does.
  • Define a two-service application in a Compose file and say what Compose does and does not wait for.

Key terms

Image
A read-only, layered package of the files, libraries and configuration needed to start a container. It is stored in a registry under a name and a tag.
Layer
The set of filesystem changes (files added, modified or deleted) produced by one build step. Once created, a layer never changes.
Container
A runnable instance of an image: an isolated process with its own filesystem view, network and process IDs, plus a thin writable layer.
Dockerfile
A text file of build instructions such as FROM, COPY, RUN and CMD from which docker build creates an image.
Registry
A server that stores and distributes images. Docker Hub is the default public registry.
Volume
Storage managed by Docker that lives outside any container's writable layer and therefore outlives the container.
Namespace
A Linux kernel feature that gives a process its own view of one kind of resource, such as process IDs, network devices or mount points.
Control group
A Linux kernel feature (cgroup) that groups processes so that their CPU, memory, I/O and process count can be limited and measured.
Published port
A mapping written HOST_PORT:CONTAINER_PORT that makes a container's port reachable from outside the Docker host.
Compose
A tool and file format (compose.yaml) for defining an application made of several containers, with their networks and volumes, and starting it with one command.

2Explanation

Introduction

You have probably met this problem: a project runs on your laptop, then fails on a teammate's machine or on the server because Python is a different version, a system library is missing, or a database is not running. Containers address it by letting you ship a program together with the files it needs, and by running it in a controlled environment on any machine that has a container runtime.

Three words carry most of the vocabulary:

  • An image is the package. It holds a filesystem (the operating system's user-space files, your language runtime, your libraries, your code) and some configuration, such as which command to start. Images are read-only.
  • A container is a running instance of an image. Docker's own explanation is that a container is an isolated process with all of the files it needs to run (opens in a new tab), and that is an accurate way to think about it.
  • Docker is the toolset that builds images, fetches and stores them in registries, and starts containers. The image and runtime formats are open standards, so other tools can build and run the same images.

The central idea is that a container is not a small computer. It is a normal process that the Linux kernel has been told to treat specially: give it its own list of processes, its own network, its own view of the filesystem, and a cap on memory and CPU. Because the kernel is shared with the host, there is no second operating system to boot, and many containers can share one machine. It is also why a Linux container needs a Linux kernel underneath it.

This lesson works from the inside out: the Linux primitives, images and layers, Dockerfiles and the build cache, volumes and networks, and Compose for applications made of several containers. It then follows five documented uses, from a self-hosted LLM observability stack to GPU containers. If you plan to run containers in a cluster, Kubernetes Basics is the natural next step.

How it works

A container is a process with a restricted view

The kernel supplies two building blocks. Namespaces change what a process can see. The Linux manual page (opens in a new tab) defines a namespace as a wrapper around a global system resource that makes it appear to the processes inside that they have their own isolated instance of it. Docker's security documentation (opens in a new tab) says that when you start a container with docker run, Docker creates a set of namespaces and control groups for it behind the scenes.

NamespaceIsolatesEffect inside a container
PIDProcess IDsThe main process is PID 1; host processes are invisible
NetworkDevices, stacks, portsOwn interfaces and ports; localhost is the container itself
MountMount pointsThe root filesystem comes from the image, not the host
UTSHostnameOwn hostname
IPCSystem V IPC, POSIX message queuesOwn shared-memory and queue objects

The manual page also lists User, Cgroup and Time namespaces, eight types in all.

Control groups (cgroups) change what a process can use. The kernel documentation (opens in a new tab) describes a cgroup as a mechanism to organise processes hierarchically and distribute system resources along that hierarchy. In cgroup v2, memory.max is a hard memory limit (when usage reaches it and cannot be reduced, the out-of-memory killer runs in that cgroup), cpu.max caps CPU bandwidth as a quota per period, and pids.max caps the number of processes. Docker's resource constraints (opens in a new tab) page says that its CPU settings modify the container's cgroup on the host, and that --cpus="1.5" is equivalent to a quota of 150000 per period of 100000 microseconds.

Unlike a virtual machine, a container has no kernel of its own. Docker's multi-platform page (opens in a new tab) draws the consequence: the code in a container must be compatible with the host's CPU architecture.

Images, layers and the writable layer

An image is a stack of layers. Each layer holds the filesystem changes from one build step, and once created it is immutable (opens in a new tab). When a container starts, the layers are stacked into one union view and Docker adds a thin writable layer for that container. Writes go to the top layer; the image layers underneath stay untouched, so many containers can share one image.

The OCI image specification (opens in a new tab) describes how an image is stored and shipped: a manifest identifies each layer by a content-addressable digest, and an image index can list one manifest per platform. A tag such as python:3.12-slim is a name that can be moved to a different image; a digest identifies exact content, which is why Docker's best practices (opens in a new tab) suggest pinning base images to a version and a digest for supply chain integrity.

The Dockerfile and the build cache

A Dockerfile is a recipe of instructions. RUN, COPY and ADD add files to the image; ENV, USER, EXPOSE and CMD record configuration. The build cache (opens in a new tab) rule is: each instruction roughly becomes a layer, and when a layer changes, every layer after it must be rebuilt. Put steps that change rarely before steps that change often:

dockerfile
# Slow: any edit to any file reruns pip install
COPY . /app
RUN pip install -r /app/requirements.txt

# Fast: pip install reruns only when requirements.txt changes
COPY requirements.txt /app/
RUN pip install -r /app/requirements.txt
COPY . /app

Four details from the Dockerfile reference (opens in a new tab) save debugging time. CMD supplies the default command, which arguments after the image name replace. ENTRYPOINT sets the executable, and arguments to docker run are appended to it. EXPOSE only documents a port; it does not publish it. Use the exec form CMD ["python", "app.py"] rather than the shell form, so that your program, not a shell, is PID 1 and docker stop can signal it directly. Docker's best practices (opens in a new tab) recommend this form for service images. Being PID 1 has a cost: the kernel delivers a signal from outside a PID namespace to its first process only if that process has installed a handler for it, as the pid_namespaces manual page (opens in a new tab) explains, so a service should handle SIGTERM. A multi-stage build compiles in one stage and copies only the result into a small final stage.

Where data lives

Data written inside a container goes to its writable layer, which is destroyed with the container. Docker's volumes (opens in a new tab) page describes the alternative: a volume is created and managed by Docker and its contents exist outside the lifecycle of any container. If you mount an empty volume over a directory that already holds files in the image, those files are copied into the volume; if you mount a non-empty volume or a bind mount there, the files in the image are hidden by the mount.

Networks and ports

Each container has its own network namespace, so localhost inside a container is that container. Per Docker's networking overview (opens in a new tab), containers on the default bridge network can reach the internet but cannot find each other by name. On a user-defined bridge network they can, through Docker's embedded DNS server, and every port is reachable between them. To reach a container from outside the Docker host you publish a port with -p HOST_PORT:CONTAINER_PORT.

Compose for several containers

Compose (opens in a new tab) describes an application as services, networks and volumes in one compose.yaml. A service is one image run with one configuration, once or several times. docker compose up creates the networks and volumes and starts the services. Compose creates a default network (opens in a new tab) and registers each service name in an internal DNS, so one service reaches another as db:5432; the host port of a mapping matters only for traffic from outside that network. By default Compose waits only until a dependency is running (opens in a new tab), not until it is ready. To wait for readiness, give the dependency a healthcheck and use depends_on with condition: service_healthy.

What actually starts the process

docker is only a client. It sends your command to the daemon, dockerd, which manages images, containers, networks and volumes. In a typical installation the daemon hands container execution to containerd (opens in a new tab), a runtime that manages the container lifecycle from image storage to execution and supervision, and containerd calls a low-level OCI runtime, usually runc (opens in a new tab). runc reads a bundle (a root filesystem and a config.json) and sets up the namespaces, cgroup limits and process that the OCI runtime specification (opens in a new tab) describes.

Worked example: Build, run and persist a visit counter, then inspect the primitives

This example packages a short Python web service, shows that its data survives container replacement only inside a volume, watches the build cache work, and reads the namespace and cgroup settings from inside. You need Docker (Docker Engine, or Docker Desktop on macOS and Windows) and curl. Put these files in an empty directory.

app.py uses only the standard library, so there is nothing to install:

python
import json
import os
import signal
import sys
from http.server import BaseHTTPRequestHandler, HTTPServer

DATA_DIR = os.environ.get("DATA_DIR", "/data")
COUNTER_FILE = os.path.join(DATA_DIR, "visits.txt")
GREETING = os.environ.get("GREETING", "hello")


def next_visit():
    try:
        with open(COUNTER_FILE) as handle:
            count = int(handle.read() or 0)
    except FileNotFoundError:
        count = 0
    count += 1
    with open(COUNTER_FILE, "w") as handle:
        handle.write(str(count))
    return count


class Handler(BaseHTTPRequestHandler):
    def do_GET(self):
        body = json.dumps({"message": GREETING, "visits": next_visit()}).encode()
        self.send_response(200)
        self.send_header("Content-Type", "application/json")
        self.send_header("Content-Length", str(len(body)))
        self.end_headers()
        self.wfile.write(body)


if __name__ == "__main__":
    # As PID 1 in a container, the process receives only signals it has a handler for.
    signal.signal(signal.SIGTERM, lambda signum, frame: sys.exit(0))
    HTTPServer(("0.0.0.0", 8000), Handler).serve_forever()

The server binds to 0.0.0.0. Bound to 127.0.0.1, it would listen only on the container's own loopback interface and a published port could not reach it.

The SIGTERM handler is there because the server runs as PID 1 inside its container. Per the pid_namespaces manual page (opens in a new tab), a signal sent from outside the namespace reaches the first process only if it has installed a handler, with SIGKILL and SIGSTOP as the exceptions. The Dockerfile reference (opens in a new tab) says docker stop sends SIGTERM unless the image sets another stop signal. Without the handler the server would ignore that signal and docker stop would end up killing the container instead of letting it exit.

Dockerfile:

dockerfile
# syntax=docker/dockerfile:1
FROM python:3.12-slim
RUN groupadd -r appuser && useradd --no-log-init -r -g appuser appuser \
    && mkdir /data && chown appuser:appuser /data
WORKDIR /app
COPY app.py .
USER appuser
EXPOSE 8000
CMD ["python", "app.py"]

Run it and see where the data lives

bash
docker build -t visit-counter:1 .
docker run -d --name vc -p 8080:8000 -v vc-data:/data visit-counter:1
sleep 1
curl -s localhost:8080
curl -s localhost:8080
docker rm -f vc
docker run -d --name vc -p 8080:8000 -v vc-data:/data visit-counter:1
sleep 1
curl -s localhost:8080
docker rm -f vc && docker volume rm vc-data
docker run -d --name vc -p 8080:8000 visit-counter:1
sleep 1
curl -s localhost:8080
docker rm -f vc

The sleep 1 gives the server a moment to start listening before the first request.

RequestOutputWhy
1st curl{"message": "hello", "visits": 1}The volume vc-data is new and empty, so Docker fills it from the image's /data, which appuser owns
2nd curl{"message": "hello", "visits": 2}Same container, file in the volume
3rd curl{"message": "hello", "visits": 3}A new container, but it mounts the same volume
4th curl{"message": "hello", "visits": 1}No volume: a fresh writable layer, so the count restarts

Watch the build cache

Change the default greeting in app.py to "hi" and rebuild with docker build --progress=plain -t visit-counter:2 ..

InstructionAfter the editReason
FROM python:3.12-slimReusedNothing about the base image changed
RUN groupadd ...Reported as CACHEDSame instruction, same inputs
WORKDIR /appReported as CACHEDSame instruction
COPY app.py .Runs againThe copied file's content changed

If the Dockerfile had a slow pip install after the COPY, it would rerun too. That is the cascade rule from the build cache.

Look at the primitives

bash
docker run -d --name vc -p 8080:8000 visit-counter:1
docker exec vc python -c "print(open('/proc/1/cmdline').read().split('\0'))"
docker exec vc python -c "import socket; print(socket.gethostname())"
docker rm -f vc
docker run --rm -m 256m --cpus 1.5 visit-counter:1 sh -c 'cat /sys/fs/cgroup/memory.max /sys/fs/cgroup/cpu.max'

The first command prints ['python', 'app.py', '']: inside the PID namespace the server is PID 1, started in exec form. The second prints the container's short ID rather than your computer's name (UTS namespace). In the last command sh -c ... replaces the default CMD. On a host that uses cgroup v2 it should print 268435456 and 150000 100000. Check the arithmetic: 256 MiB is 256 × 1024 × 1024 = 268,435,456 bytes, and 1.5 CPUs is a quota of 1.5 × 100,000 = 150,000 microseconds per 100,000-microsecond period.

Edge cases and limitations

A container is not a virtual machine
Containers share the host kernel, so an image built for one CPU architecture does not simply run on another. An image built on an Apple Silicon laptop (arm64) may fail or run slowly under emulation on an amd64 server. Build for the target with docker buildx build --platform, or publish a multi-platform image so the pull selects the right variant. The shared kernel also makes a container a weaker boundary than a virtual machine.
Deleting a file in a later layer does not shrink the image
Layers are immutable, so a later step can only record that a file was removed; the bytes stay in the earlier layer. Hugging Face's Docker Spaces documentation warns about a related trap: changing a file's ownership with a recursive chown copies every affected file into a new layer, which can make the image very large. Use COPY --chown, clean up inside the same RUN step that created the files, or use a multi-stage build.
A server bound to 127.0.0.1 is unreachable through a published port
Inside a container, 127.0.0.1 is the container's own loopback interface. A published port forwards traffic to the container's network address, so a program that listens only on loopback never sees it. Bind to 0.0.0.0 inside the container and decide on the host side who may connect, for example by publishing to 127.0.0.1:8080:8000 so that only the host itself can reach it.
A mount can hide files that the image contains
A bind mount, or a volume that is not empty, placed over a directory that holds files in the image hides those files for as long as the mount exists. An empty named volume behaves differently: Docker copies the image's files at that path into it. If a path suddenly looks empty or stale after you add -v, check whether a mount is covering the image's content.
Access to the Docker daemon is close to root on the host
Docker's security documentation says that only trusted users should be allowed to control the daemon, because it can bind-mount host directories into containers without restriction. Adding a user to the docker group, or mounting the daemon socket into a container, hands over that power. Rootless mode and running container processes as a non-root user reduce the exposure.
Shell-form CMD can leave your program unable to stop cleanly
CMD python app.py runs your program through /bin/sh -c, so the shell may be PID 1 and may not pass the stop signal on; docker stop then waits and kills the container instead of letting the program shut down. The exec form, CMD ["python", "app.py"], fixes that. A program running as PID 1 still receives only the signals it has a handler for, so handle SIGTERM in the code or start the container with docker run --init.

When to use it, and when something simpler is enough

Use it when

  • You need the same operating system libraries, language version and dependencies in development, CI and production, or on infrastructure that a customer controls and you do not.
  • You deploy to a platform whose unit of deployment is a container image, such as a Kubernetes cluster, a serverless container service or a hosted Space.
  • An application needs several backing services (a database, a cache, a worker) that a teammate or customer should start with one command.
  • Automated tests need real dependencies, such as a database, that must start empty for every run.
  • Two applications on one machine need conflicting versions of the same runtime or library.

Think twice when

  • The workload is untrusted code that must be strongly isolated, or needs its own kernel or kernel modules. A shared-kernel container is a weaker boundary than a virtual machine, so use a VM or a purpose-built sandbox.
  • The program is a script whose pure-Python dependencies a lockfile and a virtual environment already reproduce. A container then adds a build and a registry without removing a problem.
  • You would run a production database on one Compose host with no backup or failover plan. Langfuse's own documentation says its Compose setup has no high availability, scaling or backup.

A simpler alternative. A virtual environment with a lockfile reproduces Python dependencies on one machine without a container. Move to containers when the problem includes system libraries, a different operating system, several cooperating services, or a deployment target that accepts only images.

Key takeaways

  • A container is a normal Linux process that namespaces give a private view of the system and control groups limit, which is why it shares the host kernel and starts without booting an operating system.
  • An image is a stack of immutable layers and each container adds one writable layer that disappears with it, so anything that must survive replacement belongs in a volume.
  • Builds are cached from the top down and a changed layer invalidates every later one, so put rarely changing steps such as dependency installs before frequently changing source copies.
  • Containers on a user-defined network, including Compose's default network, reach each other by service name on the container port, while a published port is only for traffic from outside the Docker host.
  • Compose describes a multi-container application as services, networks and volumes, but it waits only until a dependency is running unless you add a health check and a service_healthy condition.
  • Treat containers as disposable, run them as a non-root user, keep secrets out of image layers and pin base images, because the image is the artefact that travels between environments.

Example 1 of 5

Langfuse self-hosting, a six-service stack started with docker compose up

LangfuseDocumented in official docs

Langfuse's self-hosting documentation includes a page for deploying the platform with Docker Compose on a local machine or a single virtual machine, using the docker-compose.yml in the Langfuse repository. Docker's Compose pages on networking and startup order describe the Compose behaviour that such a deployment relies on. [22][23][10][9]

The problem

The platform is not one program. The Compose file in the Langfuse repository defines six services: a web application (langfuse-web), a background worker (langfuse-worker), ClickHouse, MinIO, Redis and PostgreSQL. Someone who only wants to evaluate it would otherwise have to install, configure and connect six components by hand and keep their versions compatible.

Where this topic fits

Compose is the packaging layer for the whole application. One file declares the services and how they are connected, docker compose up starts all of them, and each component comes from an image instead of from packages installed on the host. The page positions this setup for trying Langfuse out, not for production.

How it is applied, step by step

  1. The documentation has you clone the Langfuse repository, change into it and run `docker compose up`. The repository holds the Compose file.
  2. Compose reads the file, creates a project network and starts one container per service, pulling any image that is not on the machine yet.
  3. Inside that network each service is reachable by its service name. The file's database URL points at postgres:5432 and its internal MinIO endpoint at http://minio:9000, so the web and worker containers address their backing services by name instead of by IP address. Host-side port mappings matter only for access from outside the network.
  4. Start-up order uses health checks. The worker and web services declare depends_on with condition service_healthy for postgres, minio, redis and clickhouse, and each of those services defines a healthcheck, so the application containers start only after the backing services report healthy.
  5. Only two ports are meant for people: the Langfuse UI on 3000 and MinIO on 9090, the address browsers use to upload and download media. The file and the documentation say the other ports are bound to 127.0.0.1, so the host itself can reach them (the worker on 3030, the MinIO console on 9091, the databases) but other machines cannot.
  6. Before exposing the instance you replace the secrets marked `# CHANGEME` in the Compose file with long random values.
  7. For high availability, scaling or backups the documentation points to Kubernetes instead of stretching the single-host setup.

Why this approach fits

Every component is a separate program with its own image and its own configuration, which is the case Compose is built for. A single file that can be read, reviewed and copied replaces a long installation guide, and the private project network with name-based discovery removes the need to wire IP addresses. Because the dependencies come from images, the same file behaves alike on a laptop and on a virtual machine.

Limitation or tradeoff

The documentation itself states the boundary: the Compose setup has no high availability, no scaling and no backup functionality, and it does not scale horizontally without an extra load balancer. One Docker host is one point of failure. Treat it as an evaluation setup, and plan a different deployment before real traffic depends on it. The file also ships placeholder secrets, which the page tells you to replace, so running it unchanged on a reachable machine would be unsafe. Compose alone starts containers without checking readiness; Langfuse's file adds health checks and service_healthy conditions to cover that.

What the sources document

  • The Langfuse documentation describes deploying with the repository's docker-compose.yml, locally or on a virtual machine, as the simplest way to run Langfuse to give it a try. That file defines six services: langfuse-worker, langfuse-web, clickhouse, minio, redis and postgres. [22][23]
  • The page says the default file publishes the Langfuse UI on port 3000 and MinIO on port 9090 (mapping 9090:9000), that ports bound to 127.0.0.1 (the worker on 3030, the MinIO console on 9091 and the databases) are reachable only from the host itself, and that sensitive lines are marked CHANGEME and should get long random passwords. [22]
  • The page states that the Compose setup lacks high availability, scaling and backup functionality, and recommends Kubernetes for high-availability and high-throughput use. [22]
  • In the file, langfuse-worker and langfuse-web wait with condition service_healthy for postgres, minio, redis and clickhouse, each of which defines a healthcheck. Docker's Compose documentation says that by default Compose waits only until a dependency is running, not until it is ready. [23][10]
  • Docker's Compose networking documentation says each service registers its name with an internal DNS server so containers reach each other by service name, that service-to-service traffic uses the container port, and that the host port is only used from outside the network. [9]

The facts above come from the cited sources. The steps and analysis in this example are our explanation of how they fit together.

Example 2 of 5

AWS Lambda functions packaged and deployed as container images

Amazon Web ServicesDocumented in official docs

The AWS Lambda Developer Guide describes container images as one of two deployment package types. Its pages on creating functions from container images and on Python images explain the build, test and deploy workflow, and the quotas page lists the size limits. [24][25][26][13]

The problem

A Lambda function needs a deployment package that holds its code and every dependency. For a .zip archive the unzipped contents, including layers and custom runtimes, may not exceed 250 MB. Code with large dependencies, or a team whose build pipeline already produces images, needs a package type that fits that workflow. The documented limit for a container image is 10 GB uncompressed.

Where this topic fits

The image is the deployment package. You build it with the Docker toolchain, push it to Amazon ECR and create the function from the repository URI. Lambda then runs the image as the function's environment, with a runtime interface client translating between Lambda's runtime API and your handler.

How it is applied, step by step

  1. Start the Dockerfile from an AWS base image, which the documentation says is preloaded with a language runtime, a runtime interface client and a runtime interface emulator. Any other base image also works if you add the runtime interface client yourself.
  2. Copy requirements.txt and run pip install before copying the function code, then set CMD to the handler name. This is the same dependencies-before-code order that keeps the build cache useful.
  3. Build for one architecture with `docker buildx build --platform linux/amd64 --provenance=false`, the form the Python page gives for making the image compatible with Lambda.
  4. Test the same image locally. Run it with a port mapping such as 9000:8080 and post an event to the local invocation endpoint that the runtime interface emulator serves.
  5. Tag the image for an ECR repository in the same Region as the function, push it, and create the function with package type Image and the image URI.
  6. To ship a change, rebuild and push, then run update-function-code. Lambda resolves the tag to a digest at deploy time, so moving the tag alone does not update the function.

Why this approach fits

The artefact that runs in the cloud is the same one a developer can start locally with the emulator, so a test exercises the real packaging. The image formats are the open Docker and OCI formats, which means existing build, registry and scanning pipelines carry over. The 10 GB limit leaves room for heavy libraries that would not fit a 250 MB archive.

Limitation or tradeoff

Lambda sets constraints that a plain container does not have. The image must run on a read-only file system apart from a writable /tmp, must be Linux-based, and must target a single architecture. You cannot change the package type of an existing function. After each upload Lambda optimises the image, and the function stays Pending until that finishes. A function that is not invoked for several weeks becomes Inactive, and its first invocation is rejected while the image is optimised again. AWS updates base images periodically, but you must rebuild and redeploy to pick up an update. Lambda also supplies its own least-privileged user, so the non-root advice of this lesson is handled by the platform rather than by a USER line.

What the sources document

  • Lambda supports two deployment package types, container images and .zip archives. You build the image locally, upload it to an Amazon ECR repository in the same Region and give Lambda the repository URI. It accepts Docker image manifest V2 schema 2 or OCI images, up to 10 GB uncompressed including all layers. [24]
  • The quotas page lists the .zip deployment package limit as 250 MB unzipped, including layers and custom runtimes, and the container image code package limit as 10 GB of uncompressed image size including all layers. [26]
  • A Lambda container image must implement the Lambda runtime API through a runtime interface client, run on a read-only file system with a writable /tmp directory, be Linux-based, and target a single architecture even though AWS provides multi-architecture base images. Example 3 of 5

GitHub Actions service containers as disposable test databases

GitHubDocumented in official docs

GitHub's documentation page Communicating with Docker service containers explains how a workflow job can start Docker containers for the services its tests need, and how the job connects to them. [27]

The problem

Integration tests need a real database or cache, and they are only repeatable when every run starts from an empty state. Installing and cleaning databases on a shared build machine is brittle, and a long-lived test database carries state from one run to the next.

Where this topic fits

Containers act as disposable infrastructure around one CI job. The job's services section names each dependency and its image. GitHub starts the containers for the job and removes them when it ends, so the test steps see a fresh instance every time.

How it is applied, step by step

  1. Under `services:` in the job, give each dependency a label and an image, plus any environment settings the image needs.
  2. GitHub creates a fresh container for each service when the job starts. Pinning the image tag, for example postgres:16, fixes the version that the tests run against.
  3. If the job itself runs in a container, it reaches a service by using the label as the hostname, because the hostname of the service container is mapped to the label.
  4. If the job runs directly on the runner, you map a port such as 5432:5432 and connect to localhost on that port, because a service container's ports are not exposed to the runner by default.
  5. A typical workflow adds health options to the service so that the test steps wait until the database accepts connections.
  6. When the job completes GitHub destroys the service containers, so no cleanup step is needed and the next run starts clean.

Why this approach fits

The test talks to the same kind of database that production uses, and the dependency's life is tied to the job, so there is no teardown code to forget. GitHub pulls and starts the image, so nothing has to be installed on the runner, which keeps the CI machine generic.

Limitation or tradeoff

Each job gets its own service containers, so two jobs in one workflow cannot share a database instance or its data. Service containers need a Linux runner with Docker. The container is only a stand-in: a managed database in production can differ in version, extensions and configuration from the image used in CI.

What the sources document

  • GitHub describes service containers as Docker containers that provide a simple, portable way to host services you might need to test or operate your application in a workflow, such as a database and a memory cache for integration tests. [27]
  • Service containers are configured for each job in a workflow. GitHub creates a fresh Docker container for each service configured in the workflow and destroys the service container when the job completes. [27]
  • When a job runs in a container, it accesses a service container by the label configured in the workflow, because the hostname of the service container is automatically mapped to the label name. When a job runs directly on the runner, it reaches the service through localhost and a mapped port, because the service does not expose its ports to the runner by default. [27]
  • For GitHub-hosted runners you must use an Ubuntu runner, and for self-hosted runners you must use a Linux machine with Docker installed. [27]

Hugging Face Docker Spaces hosting a custom ML app from a Dockerfile

Hugging FaceDocumented in official docs

The Hugging Face Hub documentation page Docker Spaces explains how to run an app that is not a Streamlit or Gradio app by supplying a Dockerfile, and lists the rules of the hosting platform. Docker's build secrets page explains the mechanism the platform uses for build-time secrets. [28][14]

The problem

Besides Streamlit and Gradio apps, ML demos and tools may need a FastAPI service, a Go endpoint, a Phoenix app or a search server running beside the app. A hosting platform that accepts code from many people must build and run such stacks, route traffic to them and decide where secrets and persistent data go.

Where this topic fits

The Dockerfile is the app definition. The Space's README front matter says that the SDK is Docker and which port the app serves. The platform builds the image from the repository, runs it as a container and sends outside traffic to the declared port. The platform's few rules, such as the user ID and the secret handling, are the contract the Dockerfile has to follow.

How it is applied, step by step

  1. Create the Space with the Docker SDK. This sets `sdk: docker` in the README.md YAML block, and you can change the default exposed port 7860 with `app_port`.
  2. Write a Dockerfile that creates a user with ID 1000, switches to it and sets WORKDIR before any COPY or download, because the container runs with user ID 1000.
  3. Use `COPY --chown=user` instead of copying as root and running a recursive chown afterwards. A metadata change copies each file into a new layer and can make the image very large.
  4. Pass configuration through variables, which arrive as build arguments at build time and as environment variables at runtime. Expose secrets at build time with `RUN --mount=type=secret`, and read them at runtime from the environment.
  5. Start the server on the declared port. The app may use other ports internally, but only that one is reachable from outside.
  6. Plan for data: files written to disk are lost when the Space restarts, so persistent data goes to an attached storage bucket, a dataset repository or an external service.

Why this approach fits

A Dockerfile is a portable, widely understood build recipe, so the platform does not need to know your language or framework. It defines a small contract of port, user and storage rules and leaves the rest to you. You can run the same image on your own machine to debug before pushing.

Limitation or tradeoff

The contract has sharp edges. The container runs as user ID 1000, so files copied as root cause permission errors. Disk data is ephemeral across restarts. A Space exposes one public port, and the documentation suggests a reverse proxy such as Nginx if you need several. No GPU is available during the image build, so commands such as nvidia-smi or torch.cuda.is_available() cannot run in the Dockerfile.

What the sources document

  • Docker Spaces host custom Docker containers for apps outside Streamlit and Gradio, such as FastAPI and Go endpoints. Choosing the Docker SDK sets sdk: docker in the README.md YAML block, and the default exposed port is 7860, changeable with app_port. The container runs with user ID 1000. [28]
  • The documentation warns that updating a file's metadata creates a new copy in a new layer, so a recursive chown can produce a very large image, and says to use COPY --chown instead. [28]
  • Secrets are exposed at build time by mounting them as a file with RUN --mount=type=secret and read from /run/secrets, and at runtime they are available as environment variables. Data written to disk is lost when the Space restarts. [28]
  • Docker's documentation says build arguments and environment variables are inappropriate for build secrets because they persist in the final image, and describes secret mounts that are available only for the duration of a build instruction. [14]

Example 5 of 5

NVIDIA Container Toolkit giving containers access to the host GPU

NVIDIADocumented in official docs

NVIDIA's Container Toolkit documentation describes how GPU-accelerated containers run under Docker and other engines. The architecture page explains how the toolkit plugs into the OCI runtime, and the install guide gives the setup for each engine. The runc and containerd project pages describe the runtimes it attaches to. [29][30][20][21]

The problem

A container shares the host kernel, so the GPU driver belongs to the host and not to the image. By default a container has no GPU access, and something must give each container the GPU devices it was asked for at start-up. Frameworks such as PyTorch inside the container cannot work around that on their own.

Where this topic fits

The toolkit sits between the container engine and runc. Its runtime wrapper edits the container's OCI configuration to add a hook, and runc runs that hook after the container is created and before the container's command starts. This is the point of the lesson's dockerd, containerd and runc chain where a vendor can add behaviour without changing the engine.

How it is applied, step by step

  1. Install the NVIDIA GPU driver on the host. The install guide lists it as the prerequisite, and the image does not carry the kernel driver.
  2. Install the toolkit and run `nvidia-ctk runtime configure --runtime=docker`, which modifies `/etc/docker/daemon.json` on the host, then restart Docker.
  3. Start a container with GPU access, for example `docker run --rm --runtime=nvidia --gpus all ubuntu nvidia-smi`, which should print a table of the GPUs the container can see.
  4. The engine passes the container's spec to the configured runtime. `nvidia-container-runtime` injects the NVIDIA Container Runtime Hook as a prestart hook and calls the native runC with the modified spec.
  5. runC creates the container and, after creation but before start, invokes the hook. The hook reads config.json and calls `nvidia-container-cli`, whose most important flag selects which GPU devices to inject.
  6. The container's command then starts with the selected GPUs visible, and `nvidia-smi` inside prints the GPU table.

Why this approach fits

GPU access is a property of the host, so it has to be granted per container when the container starts and cannot be baked into an image. Using the standard OCI hook point means neither the engine nor the image needs NVIDIA-specific code, and the same image can run on any host that has a compatible driver and the toolkit configured.

Limitation or tradeoff

Portability stops at the host. A machine without the driver, or without the toolkit configured for its container engine, cannot run the container with GPU access, so an image alone does not guarantee that it will run. The documentation describes the mechanism for runC-based runtimes such as Docker and containerd, and says other runtimes follow different integration paths. The install guide documents CDI as the route for Podman, so the hook-based path traced here is not the only one.

What the sources document

  • The architecture page says nvidia-container-runtime takes a runC spec as input, injects the NVIDIA Container Runtime Hook as a prestart hook and calls the native runC with the modified spec. runC invokes the hook after the container is created but before it starts, and the hook uses config.json to call nvidia-container-cli, with the choice of GPU devices to inject as an important flag. [29]
  • The install guide lists the NVIDIA GPU driver on the host as a prerequisite, and says that `nvidia-ctk runtime configure --runtime=docker` modifies /etc/docker/daemon.json on the host, after which Docker is restarted. [30]
  • The install guide lists Docker, containerd, CRI-O and Podman as supported container engines, with a separate configuration step for each, and recommends the Container Device Interface (CDI) for Podman. [30]
  • The runc README describes runc as a CLI tool for spawning and running containers on Linux according to the OCI specification, a low-level tool mostly used by higher-level container software. [20]
  • The containerd project describes itself as an industry-standard container runtime that manages the container lifecycle from image transfer and storage to execution and supervision, with Docker among its adopters. [21]

4Common mistakes

  1. Copying the whole project into the image before installing dependencies

    Why it causes problems
    Every source edit invalidates the COPY layer and, by the cascade rule, every layer after it, including the dependency install. A one-line change then costs a full reinstall, which turns a rebuild of seconds into minutes and teaches people to avoid rebuilding.
    How to recognise it
    Run docker build --progress=plain after a one-line code change. If the install step runs instead of reporting CACHED, the order is wrong. CI image builds that take as long on the tenth run as on the first point to the same cause.
    How to fix it
    Copy only the dependency manifest (requirements.txt or package-lock.json) first, run the install, and copy the rest of the source afterwards. Add a .dockerignore so that .git, caches and local virtual environments do not enter the build context.

  2. Keeping database files or uploads in the container's writable layer

    Why it causes problems
    The writable layer is deleted with the container. Recreating the container to upgrade the image, change a flag or recover from a crash silently deletes the data, often without any error.
    How to recognise it
    Data disappears after docker rm, docker compose down or an image upgrade. docker inspect on the container shows no mount at the directory where the program writes.
    How to fix it
    Mount a named volume at the data directory, with -v name:/path or volumes in Compose, and treat the container as replaceable. Back up volumes like any other data store, and remember that docker compose down -v deletes them.

  3. Passing secrets through ARG, ENV or COPY

    Why it causes problems
    Docker's documentation says build arguments and environment variables persist in the final image, where docker history and docker inspect expose them. A key file added with COPY stays in its layer even if a later step deletes it. Anyone who can pull the image can read the secret.
    How to recognise it
    Run docker history --no-trunc or docker inspect on the image and look for the value. A secret scanner run on the pushed image flags it as well.
    How to fix it
    Use RUN --mount=type=secret together with docker build --secret for build-time secrets, and supply runtime secrets as environment variables or mounted files from the platform's secret store. Rotate any secret that was ever baked into an image that was pushed.

  4. Building from the latest tag or from an unpinned base image

    Why it causes problems
    A tag is a name that can move. The same Dockerfile built a month apart can produce different images, and a new major version of the base can break the build on a day when you changed nothing.
    How to recognise it
    FROM lines without a version or digest, and two builds of the same commit that give different image IDs in docker image ls.
    How to fix it
    Pin a specific version tag such as python:3.12-slim and, where exact repeatability matters, a digest. Let a tool such as Dependabot propose base image updates so that changes arrive as reviewed pull requests.

  5. Expecting depends_on to wait for readiness, or EXPOSE to publish a port

    Why it causes problems
    Compose waits only until the dependency container is running, so an application that connects to a database at start-up fails while the database is still initialising. EXPOSE documents a port but publishes nothing, so a service can be healthy and still unreachable from the host.
    How to recognise it
    Connection errors on first start that disappear on retry, and docker ps showing no host port mapping for a service whose Dockerfile has EXPOSE.
    How to fix it
    Add a healthcheck to the dependency and use depends_on with condition service_healthy, and make the client retry its connection. Publish ports explicitly with ports in Compose or -p on docker run.

  6. Running the application as root with broad host mounts

    Why it causes problems
    A process that runs as root inside a container and mishandles a mount has more reach than a non-root process. Docker's security documentation warns that daemon access allows host directories to be mounted into containers without restriction, so a wide mount such as / or the Docker socket is close to root on the host.
    How to recognise it
    docker exec on the container prints uid=0 for id, and docker inspect lists mounts of / , /etc or /var/run/docker.sock.
    How to fix it
    Create a user, switch to it with USER after installing packages, and give it ownership of only the directories it writes. Mount only the specific paths needed, read-only with :ro where possible.

Exercise 1

Make the visit counter cache-friendly, limited and read-only

Hands-onBeginnerAbout 40 min (estimate)Hypothetical scenario

Start from the worked example's app.py and Dockerfile. You need Docker and curl, both free. Make four changes and prove that each one works.

  1. Add a requirements.txt that contains the single line six==1.16.0. The app does not import it. It only gives the build a dependency-install step that is worth caching. Change the Dockerfile so that pip install --no-cache-dir -r requirements.txt runs before COPY app.py ..
  2. Add a .dockerignore that excludes .git, __pycache__ and *.md.
  3. Run the container with a 128 MiB memory limit, half a CPU and a read-only root filesystem, keeping /data on the named volume vc-data.
  4. Show that the root filesystem is read-only, that /data is still writable, and what the cgroup files memory.max and cpu.max contain.

Requirements

  • After you edit app.py and rebuild with --progress=plain, the pip install step is reported as CACHED.
  • After you change the version pinned in requirements.txt, the pip install step runs again.
  • The container started with --read-only, -m 128m and --cpus 0.5 still answers on port 8080 with a counter that increases.
  • You can state the values of memory.max and cpu.max inside the container and show how each number is computed.

Expected behaviour

Rebuilding after an app.py edit reuses the pip install layer. Writing to the root filesystem fails with touch: cannot touch '/tmp/x': Read-only file system, while the counter, which writes to the volume at /data, keeps increasing. On a cgroup v2 host memory.max prints 134217728 and cpu.max prints 50000 100000.

Hint 1

Order is the whole trick. Which changes less often, requirements.txt or app.py? Put its steps first.

Hint 2

--read-only makes the container's root filesystem read-only. Paths backed by a volume or by --tmpfs stay writable.

Hint 3

Inside the container, memory.max and cpu.max are files under /sys/fs/cgroup on a cgroup v2 host. Convert 128 MiB to bytes, and write 0.5 CPU as a quota over a 100000 microsecond period.

Show solution

Dockerfile with the install step before the code copy:

dockerfile
# syntax=docker/dockerfile:1
FROM python:3.12-slim
RUN groupadd -r appuser && useradd --no-log-init -r -g appuser appuser \
    && mkdir /data && chown appuser:appuser /data
WORKDIR /app
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt
COPY app.py .
USER appuser
EXPOSE 8000
CMD ["python", "app.py"]

.dockerignore:

text
.git
__pycache__
*.md

Commands:

bash
docker build --progress=plain -t visit-counter:3 .
# edit app.py (change the greeting), then rebuild: the pip install step is CACHED
docker build --progress=plain -t visit-counter:3 .
# change requirements.txt to six==1.17.0, then rebuild: pip install runs again
docker build --progress=plain -t visit-counter:3 .
docker run -d --name vc -p 8080:8000 -m 128m --cpus 0.5 --read-only -v vc-data:/data visit-counter:3
sleep 1
curl -s localhost:8080
curl -s localhost:8080
docker exec vc touch /tmp/x
docker exec vc sh -c 'cat /sys/fs/cgroup/memory.max /sys/fs/cgroup/cpu.max'
docker rm -f vc

Expected results, in order: the two curl calls print visits that increase by one (the volume may already hold a count from earlier runs), the touch fails with Read-only file system, and the cgroup files print 134217728 and 50000 100000.

Why these values: 128 MiB is 128 × 1024 × 1024 = 134,217,728 bytes. Docker's --cpus is a quota over a period of 100,000 microseconds, so 0.5 CPU is a quota of 0.5 × 100,000 = 50,000. On a cgroup v1 host the files are in different places, so read the limits from docker inspect instead (the fields HostConfig.Memory, in bytes, and HostConfig.NanoCpus, in billionths of a CPU).

Why the cache behaves this way: the pip install step depends only on the layers before it and on requirements.txt. Editing app.py changes only the later COPY layer. Editing requirements.txt changes the earlier COPY, so the install and everything after it rebuild.

Check your answer

  • Did the install step stay CACHED after you changed only app.py, and rerun after you changed requirements.txt?
  • Does docker exec vc touch /tmp/x fail, while the counter still increases?
  • Can you explain why the counter still works with --read-only, and where it is written?
  • Did you compute 134217728 and 50000 100000 from the flags, rather than only reading them?

    Open it when you want to see exactly what a container engine hands to the runtime, or when a tool such as the NVIDIA runtime modifies that configuration.
