LLM Cost and Latency Optimization

LLM cost and latency optimization is the set of techniques that make a language-model application cheaper and faster while keeping its answers good enough for the job: reusing work with prompt and semantic caches, moving non-urgent work to batch APIs, sending each request to the cheapest model that can handle it, and generating and showing fewer tokens sooner.

1Overview

Why it matters

A prototype that costs a few cents per conversation becomes a budget line once thousands of people use it, and an agent that re-sends a growing context on every step can multiply the bill again. Latency matters just as much: an answer that appears after eight seconds feels broken even when it is correct. The levers in this lesson, such as caching a repeated prompt prefix, halving the price by batching, or streaming the first words, are often worth more than any rewording of the prompt, and several of them are a few lines of configuration.

They are also where careless changes do the most damage. A cache that silently never hits, a router that sends hard questions to a weak model, or a length cap that cuts a JSON reply in half all look like savings until quality falls. Engineers who ship LLM features, and the people who own their budgets, need to know what each lever saves, what it risks, and how to confirm from logs that it worked.

  • Use output limits, effort settings and streaming to cut generation time or the time until the user sees text.
  • Judge when a semantic cache is safe, and verify any optimization from usage logs and an evaluation set.

Key terms

Prompt caching
A provider feature that keeps the processed form of a prompt's leading tokens, so later requests that start with the identical prefix are billed at a reduced rate and begin generating sooner.
Cache write
The request that stores a prefix. Some providers bill it at a premium over normal input, for example 1.25 times the base input price for Anthropic's 5-minute cache.
Cache read
A request whose prefix matched a stored entry. The matched tokens are billed at the cached-input rate and reported in a usage field such as cache_read_input_tokens.
Time to first token (TTFT)
The delay between sending a request and receiving the first generated token, which covers the work the model does before it starts writing.
Batch API
An asynchronous interface that accepts many independent requests together, returns results within a stated window such as 24 hours, and charges about half the normal price.
Model routing
Choosing which model handles a request before any model is called, using rules or a trained classifier.
Cascade
Calling a cheap model first and escalating to a stronger one only when a check says the first answer is not reliable enough.
Semantic cache
A store of earlier prompts and answers that returns a stored answer when a new prompt is close enough in embedding space, without calling the model at all.
Streaming
Receiving a response in pieces as it is generated, usually as server-sent events, so an interface can show text before the full answer exists.
max_tokens
A request parameter that sets a hard upper limit on generated tokens. A response that reaches it is cut off, even in the middle of a word.

2Explanation

Introduction

In Tokens and Context Windows you saw that a request is billed per token and that the model reads the whole prompt each time. LLM and Agent Observability showed how to record those tokens and how long each call takes. This lesson is about acting on those numbers.

Think of an LLM request as a taxi ride with two meters. One meter charges for tokens: input tokens at a low rate, output tokens at several times that rate. The other is the clock the passenger watches. Nearly every optimization does one of three things. It stops a meter from running, by not sending or not generating tokens. It runs the meter at a lower rate, through a cached prefix, a half-price batch or a smaller model. Or it changes what the passenger sees while the meter runs, which is what streaming does.

Six levers cover most of the savings, and each acts at a different point on a request's path. Prompt caching and output limits only change how you build the request. Batching needs work that can wait. Routing, cascades and semantic caching can all return a worse answer than the strongest model would have, so they need an evaluation set before you trust them.

The rest of the lesson explains how each lever works and what it can break, then works one example in which a daily bill falls from $225 to about $30. Five documented uses follow, from Manus and Quora to Amazon Bedrock and Azure API Management.

How it works

What the bill and the wait are made of

Each token class has its own price per million tokens (MTok):

cost=nin pin+nwrite pwrite+nread pread+nout pout\text{cost} = n_{\text{in}}\,p_{\text{in}} + n_{\text{write}}\,p_{\text{write}} + n_{\text{read}}\,p_{\text{read}} + n_{\text{out}}\,p_{\text{out}}cost=nin​pin​+nwrite​pwrite​+nread​pread​+nout​pout​

Output tokens cost several times more than input tokens: $15 against $3 per MTok on Claude Sonnet 4.6 and $10 against $2 on the newer Claude Sonnet 5.5, both in Anthropic's pricing table (opens in a new tab). They are also produced one after another, so they dominate waiting time. Latency is roughly TTFT plus output tokens divided by generation speed. OpenAI's latency guide (opens in a new tab) gives the rule of thumb: cutting 50% of output tokens may cut about 50% of latency, while cutting 50% of the prompt may improve latency by only 1 to 5%. Log the usage fields of every response first. The largest term tells you which lever matters.

Prompt caching: reuse the prefix

A model must read every input token before it writes the first output token. Providers can keep the intermediate state computed for a prompt prefix and reuse it when a later request begins with exactly the same tokens. Both major providers describe the same rules:

  • Only a prefix is cached. Anthropic builds the prompt as tools, then system, then messages, and caches up to the block carrying cache_control. A change anywhere earlier invalidates everything after it. OpenAI advises putting stable instructions first and timestamps or user-specific text last.
  • Reads are cheap, writes may cost extra. Anthropic bills 5-minute writes at 1.25 times the input price, 1-hour writes at 2 times, and reads at 0.1 times (some newer models are lower). OpenAI documents the same 1.25 write and 0.1 read multipliers for its newest models (0.05 on one of them), with no write surcharge on older ones.
  • Entries expire. Anthropic's lasts 5 minutes and every hit refreshes it at no charge; an optional 1-hour lifetime costs more to write. OpenAI's default is 30 minutes on its newest models.
  • Short prompts are skipped silently. Anthropic's minimum is 512 to 4,096 tokens depending on the model, and a shorter prompt is processed uncached with no error.
  • Usage fields prove it works. Anthropic reports cache_creation_input_tokens, cache_read_input_tokens and input_tokens (the part after the last breakpoint). OpenAI reports usage.input_tokens_details.cached_tokens.
json
{
  "model": "claude-sonnet-4-6",
  "max_tokens": 300,
  "system": [
    {"type": "text", "text": "<5,800 tokens: policies, tool rules, examples>",
     "cache_control": {"type": "ephemeral"}}
  ],
  "messages": [{"role": "user", "content": "Where is my refund?"}]
}

The request above places an explicit breakpoint on the system block, which suits a fixed prefix. Anthropic's docs also describe automatic caching: one top-level cache_control field makes the system put the breakpoint on the last cacheable block and move it forward as a conversation grows.

With a 1.25 write and a 0.1 read, a cached prefix is cheaper after a single reuse (1.25+0.1=1.351.25 + 0.1 = 1.351.25+0.1=1.35 units against 2 uncached). A 1-hour write at 2 times needs two reuses.

Batch APIs: trade time for price

A batch API takes many independent requests at once and returns results later, in exchange for 50% off at both Anthropic (opens in a new tab) and OpenAI (opens in a new tab). The window is 24 hours, though Anthropic says most batches finish within an hour. Each request carries a custom_id, because results can arrive in a different order from the input. Batches cap at 100,000 requests or 256 MB on Anthropic and 50,000 requests or 200 MB on OpenAI, and Anthropic's do not support stream: true. Use them for evaluations, backfills, classification and nightly summaries, never for something a person is waiting on. They combine with caching, but Anthropic says hits inside a batch are best-effort because requests run concurrently and in any order, and it suggests the 1-hour cache for shared context, since a batch can outlast 5 minutes.

Model routing and cascades

A router picks the model before any call. RouteLLM (opens in a new tab) trains routers on human preference data to predict whether a strong model would beat a weak one. Amazon Bedrock offers a managed version. A cascade calls the cheapest model first, scores its answer, and escalates only when the score falls below a threshold, as in FrugalGPT (opens in a new tab). For three stages with costs cic_ici​, where qiq_iqi​ is the share of requests reaching stage iii that it rejects, expected cost is c1+q1 (c2+q2 c3)c_1 + q_1\,(c_2 + q_2\,c_3)c1​+q1​(c2​+q2​c3​), ignoring the cost of the scorer that judges each answer.

A router pays nothing for a failed attempt but must judge before seeing an answer. A cascade sees the real answer but pays for each failed attempt and adds latency when it escalates. The cheapest router is a rule: classification and extraction go to a small model. Whatever you choose, measure quality on your own evaluation set (Evaluating LLM Applications). The workflow version of this idea is Routing.

Controlling output length

Output is the costliest and slowest part, so shape it deliberately. Ask for the form you need ("one sentence", "only these JSON fields"); Anthropic notes that sentence or paragraph limits work better than word counts. max_tokens is a hard ceiling, not a style control, and a capped reply may stop mid-word, so keep it for short answers and as a safety net. For reasoning models, thinking tokens are billed as output tokens and count toward max_tokens (Anthropic's thinking guide (opens in a new tab)). Anthropic's effort setting (low to max) affects text, tool calls and thinking together, and the docs call it a behavioural signal rather than a strict budget. See Reasoning Models.

Streaming: show the answer as it forms

Streaming changes when the user sees text, not how many tokens are generated or what they cost. Anthropic's stream sends server-sent events in a fixed order: message_start, then for each content block a content_block_start, many content_block_delta events (text arrives as text_delta) and a content_block_stop, then message_delta with the stop reason and cumulative usage, and message_stop. OpenAI calls streaming the single most effective way to cut the wait to a second or less. The costs are real: you cannot check the whole answer before showing it, an error can arrive mid-stream, and tool arguments arrive as partial JSON. See LLM APIs and Streaming.

Semantic caching: skip the call

An exact-match cache returns a stored answer for a byte-identical prompt. A semantic cache embeds the prompt, finds the nearest stored prompt, and returns its answer when the distance is inside a threshold (see Embeddings). A hit avoids the whole call, unlike prompt caching, which still runs the model. The risk is a near miss served as a hit: Azure's documentation warns that such answers can be incorrect, outdated or unsafe, and recommends partitioning the cache per user or group.

Worked example: Pricing a support assistant through four optimizations

This is a hypothetical workload with real prices. A support assistant handles 10,000 requests a day, spread evenly. Every request has 5,800 tokens that never change (tool rules, policy text, examples) followed by 200 tokens that do (the customer's message), so 6,000 input tokens, and the model writes 300 output tokens. Prices are from the Anthropic prompt caching pricing table (opens in a new tab) as read on 2026-10-11, in dollars per million tokens. The two models below, Claude Sonnet 4.6 and Claude Haiku 4.5, are earlier-generation models that the table still lists. The same table prices the newer Sonnet 5.5 and Haiku 5.5 differently, and Sonnet 5.5 reads its cache at 0.05 times the input price, not 0.1. Those newer models also think by default, and thinking tokens are billed as output, so they would add to the 300. The method is identical, so for real work put the current table's numbers into the script.

Claude Haiku 4.5$1.00$1.25$0.10$5.00

Assumptions: one request every 8.6 seconds keeps each cache entry warm inside its 5-minute lifetime, so each model writes its prefix once a day and reads it otherwise. The router is a free rule that sends 60% of requests (simple ones) to Haiku 4.5. The 5,800-token prefix clears both minimums (1,024 tokens for Sonnet 4.6, 4,096 for Haiku 4.5). Shorter answers (an average of 180 tokens) are assumed to pass your evaluation set. Treating every request after the first as a cache read is an upper bound on the saving, because real hit rates are lower; log cache_read_input_tokens to measure yours.

python
from dataclasses import dataclass

@dataclass(frozen=True)
class Price:
    inp: float    # USD per million input tokens
    write: float  # 5-minute cache write
    read: float   # cache read
    out: float    # output

SONNET = Price(3.00, 3.75, 0.30, 15.00)  # Claude Sonnet 4.6
HAIKU = Price(1.00, 1.25, 0.10, 5.00)    # Claude Haiku 4.5
PREFIX, VARIABLE, DAILY = 5_800, 200, 10_000
MTOK = 1_000_000

def day_cost(price, requests, out_tokens, cached):
    """USD per day on one model; with caching: one write, then reads."""
    output = requests * out_tokens * price.out / MTOK
    if not cached:
        return requests * (PREFIX + VARIABLE) * price.inp / MTOK + output
    prefix = PREFIX * (price.write + (requests - 1) * price.read) / MTOK
    return prefix + requests * VARIABLE * price.inp / MTOK + output

steps = [
    ("0 baseline", day_cost(SONNET, DAILY, 300, cached=False)),
    ("1 + prompt caching", day_cost(SONNET, DAILY, 300, cached=True)),
    ("2 + shorter answers", day_cost(SONNET, DAILY, 180, cached=True)),
    ("3 + 60% to Haiku", day_cost(HAIKU, 6_000, 180, True) + day_cost(SONNET, 4_000, 180, True)),
]
baseline = steps[0][1]
print(f"{'step':22s}{'USD/day':>9s}{'cents/req':>11s}{'saved':>8s}")
for name, usd in steps:
    print(f"{name:22s}{usd:9.2f}{usd / DAILY * 100:11.4f}{100 * (1 - usd / baseline):7.1f}%")

nightly = day_cost(SONNET, DAILY, 300, cached=False)
print(f"nightly job: sync {nightly:.2f} USD, batch {nightly * 0.5:.2f} USD")
TTFT, SPEED = 0.8, 50  # assumed seconds and tokens per second
print(f"300 tokens: {TTFT + 300 / SPEED:.1f} s total, first text at {TTFT} s when streamed")
print(f"180 tokens: {TTFT + 180 / SPEED:.1f} s total")

Check step 1 by hand. Baseline input is 6,000 tokens at $3 per MTok, which is $0.018, plus 300 output tokens at $15, which is $0.0045, so $0.0225 a request and $225.00 a day. With caching, the prefix costs one write (5,800 tokens at $3.75 is $0.02175) plus 9,999 reads (each 5,800 tokens at $0.30 is $0.00174), together $17.42. Add $6.00 for the uncached 200 tokens a request and $45.00 for output: $68.42.

Three lessons follow. After caching, output is $45.00 of the $68.42, which is why step 2 targets answer length. Routing then saves a further $20.15 a day but carries the most quality risk, so it needs the evaluation set most. And the speed figures are assumptions, not measurements: with the assumed 0.8 s TTFT and 50 tokens per second, a 300-token answer takes 6.8 s, yet a streamed reply shows its first words at 0.8 s. Shortening it to 180 tokens saves 2.4 s of total time, and streaming changes only what the user sees meanwhile. The nightly job is a separate workload, a batch of the same size that no one waits for, and it costs half as much.

Edge cases and limitations

One changed token near the top discards the cache
Caches match exact prefixes, so a timestamp in the system prompt, JSON keys serialised in a different order, or a tool added mid-session invalidates every token after the change. Anthropic also lists tool choice, images, and thinking or effort settings among the changes that invalidate parts of the cache. Compare cache_read_input_tokens with total input after each prompt change, and keep volatile text at the end.
Sparse traffic can make caching cost more
A 5-minute entry that expires before the next request is written again at 1.25 times the input price and never read. Three requests 20 minutes apart cost more with caching than without. Concurrent requests can also miss, because an entry only becomes available once the first response begins. Cache only prefixes that are reused within the lifetime, or pay for the 1-hour option if gaps are longer.
Batch results are late, unordered and can expire
A batch has a 24-hour window and no latency guarantee inside it. Results can come back in a different order from the input, so join them by custom_id. Anthropic reports four outcomes per request: succeeded, errored, canceled and expired, and bills only the succeeded ones. Validation errors surface when the batch ends, so test the request shape on the normal API first.
Routers and cascades fail quietly outside their training data
The RouteLLM authors report that routers trained only on chatbot-arena preference data performed near random on the MMLU benchmark until the data was augmented. Bedrock documents that its routing is tuned for English and cannot learn from your application's results. A cascade needs labelled examples drawn from the same distribution as live traffic. Evaluate the router on your own cases before trusting its savings.
A length cap can cut off the answer or the thinking
When a response hits max_tokens it ends wherever it is, which breaks JSON and leaves sentences unfinished. On reasoning models the thinking counts toward the same limit, so a tight cap can leave no room for the answer. Prefer asking for a short format, treat max_tokens as a safety net, and check the stop reason for max_tokens in logs.
Near-duplicate prompts are not duplicate questions
Embedding distance measures similarity of wording and topic, not equality of meaning. A request to cancel one order and a request to cancel a different order, or a question and its negation, can sit close together, and a loose threshold then returns the wrong stored answer. Azure's guidance is to start with a strict threshold and to partition entries per user or group; keeping account-dependent answers out of the cache altogether is our own recommendation.

When to use it, and when something simpler is enough

Use it when

  • A large block of the prompt is identical across requests, such as a system prompt, tool definitions, a long document or an agent's growing history, and requests arrive within the cache lifetime.
  • The work does not need to finish in seconds, for example evaluation runs, backfills, classification of a stored dataset or nightly summaries, so a batch API's discount is free money.
  • Traffic mixes easy and hard requests and you have an evaluation set that shows a smaller model is good enough on the easy part.
  • A person watches the response appear, so time to first visible text matters more than total generation time.
  • Many users ask the same public, slow-changing questions, so a stored answer is as good as a fresh one.

Think twice when

  • You have not measured yet. Without usage logs and a latency breakdown you cannot tell which term of the bill or the wait to attack, and a lever aimed at the wrong term gains almost nothing.
  • You have no evaluation set. Routing, cascades, shorter outputs and semantic caches all trade quality for savings, and without a way to measure quality the trade is blind.
  • The answer depends on a user's account, the current time or live data, which rules out semantic caching and makes cached prefixes harder to keep stable.

A simpler alternative. Before adding any of these, try a smaller model, a shorter prompt and a shorter answer format, and ask whether an LLM is needed at all. OpenAI's latency guide suggests hard-coding constrained replies and pre-computing answers. Move to caching, batching and routing when the simple changes stop being enough.

Key takeaways

  • Output tokens cost several times more than input tokens and set most of the waiting time, so shortening answers usually saves more than trimming the prompt.
  • A prompt cache matches an exact prefix, so put stable content first, keep volatile text at the end, and confirm hits from the usage fields instead of assuming them.
  • A batch API halves the price of any work that can wait up to a day, but its results arrive late and out of order and must be matched by custom_id.
  • Routers choose a model before the call and cascades escalate after a weak answer, and both are only as good as the evaluation set used to tune them.
  • Streaming and semantic caching change different things, because streaming shows text sooner without reducing cost, while a semantic cache skips the call but can serve a wrong stored answer.
  • Measure usage and latency before choosing a lever, and check quality and cache hit rate in the logs after each change.

Example 1 of 5

Manus shaping its agent context around the KV-cache

ManusDocumented in an engineering article

The Manus engineering post "Context Engineering for AI Agents: Lessons from Building Manus" (Yichao "Peak" Ji, 18 July 2025) explains how the team designs the context of its production agent so that the model provider's KV-cache keeps hitting. [12]

The problem

An agent calls the model in a loop and appends each action and observation to the context. The post says the average input-to-output token ratio in Manus is around 100:1, so almost every token in a call belongs to a long context that is mostly the same as in the previous call. Any change early in that context makes the provider reprocess everything after it, at the uncached price and with a longer wait for the first token.

Where this topic fits

Prompt caching sits underneath the agent loop. The agent does not call the cache; the context design either preserves the prefix between iterations or destroys it. Every rule in the post is a rule about what may change between one iteration and the next.

How it is applied, step by step

  1. Keep the system prompt and tool definitions identical from call to call, so every request opens with the same tokens.
  2. Leave volatile text, such as a timestamp precise to the second, out of the start of the system prompt, because a single different token invalidates the cache from that token onward.
  3. Append each action and observation to the end of the context and never edit earlier entries, so the whole context of the previous call is a valid prefix of the next one.
  4. Serialise structured data deterministically, for example with a fixed key order, so identical data always produces identical tokens.
  5. Where the provider needs explicit cache breakpoints, place them so they include at least the end of the system prompt and allow for cache expiry.
  6. For self-hosted models, make sure prefix caching is enabled and route the requests of one session to the same worker.

Why this approach fits

When 99 of every 100 tokens are input, input price and prefill time are the bill and the wait. Keeping the prefix stable turns most of each call into cache reads, and it costs nothing in quality because the model receives exactly the same tokens it would have received anyway. The change is to how the context is built, not to what the agent does.

Limitation or tradeoff

The discipline works against context trimming. Rewriting or dropping old observations to save space breaks the prefix, so a team has to trade context size against cache hit rate. The price figures are for one provider at the time of writing, and a cache entry still expires if the agent pauses for longer than the provider's cache lifetime.

What the sources document

  • The author calls the KV-cache hit rate the single most important metric for a production-stage AI agent, because it directly affects both latency and cost. [12]
  • The post reports an average input-to-output token ratio of around 100:1 in Manus, and says contexts with identical prefixes can use the KV-cache to cut time-to-first-token and inference cost sharply. [12]
  • Using Claude Sonnet as its example, the post says cached input tokens cost 0.30 USD per million tokens while uncached ones cost 3 USD, a tenfold difference. [12]
  • The listed practices are to keep the prompt prefix stable, naming a second-precise timestamp at the start of the system prompt as a common mistake, to make context append-only with deterministic serialisation because unstable JSON key order can silently break the cache, and to mark cache breakpoints explicitly when the provider needs them. [12]
  • For self-hosted models on frameworks such as vLLM, the post advises enabling prefix caching and using session IDs to route requests consistently across distributed workers. [12]

Example 2 of 5

Quora running summaries and highlights through Anthropic's Message Batches API

QuoraDocumented in a case study

Anthropic's October 2024 announcement of the Message Batches API names Quora as a customer, and the current batch processing documentation describes the interface, limits and pricing that such a job uses. [13][3]

The problem

Quora built new end-user features on summarization and highlight extraction, which means running a large number of model queries. Its product manager says those queries do not need to be processed in real time, so paying the interactive price and managing many parallel live queries is the wrong shape for the job.

Where this topic fits

In a typical implementation, batching sits at the back end of a content pipeline, away from the user. Items are collected, submitted as one batch, and joined back to their records by id when the batch ends. Nothing between submission and collection is interactive, and the finished text is stored and served like any other content. The announcement does not describe Quora's pipeline, so this placement is our illustration.

How it is applied, step by step

  1. Collect the items to summarise or extract highlights from, for example a stored set of answers that no user is waiting on.
  2. Build one request per item with a unique custom_id and the same params object a normal Messages call would take.
  3. Submit the list in one call. The batch starts as in_progress and is processed asynchronously, with each request handled independently.
  4. Poll the batch until its processing_status is ended. Most batches finish within an hour, and the maximum is 24.
  5. Stream the results file and match each result to its item by custom_id, since the order may differ from the input.
  6. Resubmit items whose result was errored or expired, which are not billed, and store the successful output for the product to use.

Why this approach fits

Both tasks are independent per item and can wait, which are the two properties a batch needs. The discount applies to the whole job, and the provider's queue replaces the client's own pool of parallel workers.

Limitation or tradeoff

A batch is not interactive. Results can take up to 24 hours, arrive in any order, and individual requests can error or expire, so the pipeline must tolerate delay and resubmit. It cannot serve a feature in which a visitor triggers a summary and waits for it. Anthropic also notes that a batch can slightly exceed a workspace's configured spend limit.

What the sources document

  • Anthropic's announcement, dated 8 October 2024, says Quora uses the Batches API for summarization and highlight extraction to create new end-user features. [13]
  • Quora's product manager is quoted saying the API gives cost savings and reduces the complexity of running a large number of queries that do not need real-time processing. [13]
  • At launch a batch could hold up to 10,000 queries, was processed in under 24 hours, and cost 50% less than standard API calls. [13]
  • The current documentation allows 100,000 requests or 256 MB per batch, charges all usage at 50% of standard prices, says most batches finish within an hour, and keeps results for 29 days. [3]
  • Each request has a unique custom_id of 1 to 64 characters, results are read from a results_url as a JSONL file, and errored, canceled and expired requests are not billed. [3]

Example 3 of 5

Amazon Bedrock routing each prompt between two models of one family

Amazon Web ServicesDocumented in official docs

The Amazon Bedrock User Guide documents intelligent prompt routing, a single serverless endpoint that sends each request to one of the models in a family after predicting how good each model's answer would be. [14]

The problem

Sending all traffic to a large model overpays for easy prompts, and sending it all to a small model loses quality on hard ones. A team that wants both has to build and maintain its own routing rules and quality estimator. AWS lists removing that orchestration work as one of the feature's benefits.

Where this topic fits

The router is the first step of a request, before any model runs. It reads the prompt, predicts the quality of each candidate model's response, and forwards the request to one model. Everything after that, such as prompt caching or output limits, applies inside the chosen model's call.

How it is applied, step by step

  1. Choose a model family. The default routers use select Amazon Nova and Meta Llama models, and configured routers allow more choices.
  2. For a configured router, pick exactly two models in the family, one of them the fallback model, and a response quality difference that says how much better the other model must be before the router switches.
  3. For each request, Bedrock analyses the prompt and predicts the response quality of each specified model.
  4. If the criteria is not met, the request goes to the fallback model. Otherwise Bedrock picks the model with the best combination of response quality and cost.
  5. The chosen model's response is returned together with information about which model produced it.
  6. The team reviews which model served which prompts, along with cost and performance metrics, and adjusts the criteria or the models.

Why this approach fits

Whether a prompt is easy or hard is rarely visible to keyword rules in open-ended traffic, so a learned predictor can route better than a hand-written rule. A managed endpoint gives a small team routing without training or hosting a classifier, and the fallback model gives a predictable default when the predictor sees no advantage in switching.

Limitation or tradeoff

AWS lists limits: the feature is optimised only for English prompts, it cannot adjust routing decisions from application-specific performance data, and its effectiveness depends on its initial training data, so it may be suboptimal for unusual use cases. It also chooses between only two models, so a team still has to evaluate the routed output on its own traffic before trusting the savings.

What the sources document

  • Intelligent prompt routing provides a single serverless endpoint that routes requests between different foundation models in the same model family. It predicts the response quality of each model for each request and routes to the model with the best response quality, to optimise quality and cost. [14]
  • Default routers are pre-configured and use select Amazon Nova and Meta Llama models. Configured routers let you set your own routing criteria, and in the console you must choose exactly two models within the same family. [14]
  • A configured router has a fallback model that acts as an anchor and a response quality difference criteria, and requests go to the fallback model when the criteria is not met. [14]
  • The response to a routed request includes information about the model that was used to process it. [14]
  • The documented limitations are that routing is optimised only for English prompts, cannot adjust its decisions using application-specific performance data, and may not be optimal for unique or specialised use cases. [14]

Example 4 of 5

FrugalGPT learning an LLM cascade for headlines, legal text and reading comprehension

Documented in a paper

The FrugalGPT paper (Lingjiao Chen, Matei Zaharia and James Zou, arXiv, May 2023) studies how to cut the cost of querying LLM APIs and evaluates a learned cascade on three datasets with 12 LLM APIs from 5 providers. [11]

The problem

The authors find that popular LLM APIs have heterogeneous pricing, with fees that can differ by two orders of magnitude, so running the best model on every query is expensive. Many queries could be answered correctly by a cheaper model, but a system must decide for each query without knowing the right answer.

Where this topic fits

The cascade is the whole serving policy. It sits in front of a list of APIs ordered from cheap to expensive. A trained scoring function reads each query and answer pair, and a threshold per stage decides whether to accept the answer or ask the next model. The last model answers whatever reaches it.

How it is applied, step by step

  1. Order the candidate APIs from cheap to expensive. For the HEADLINES dataset the learned order was GPT-J, then J1-L, then GPT-4.
  2. Send the query to the first model and take its answer.
  3. Score the query and answer pair with a trained regression model that returns a reliability score between 0 and 1.
  4. If the score is above the stage's threshold, 0.96 for GPT-J on HEADLINES, return the answer. Otherwise query the next model, whose threshold was 0.37 for J1-L.
  5. GPT-4, the last stage, produces the answer for everything the earlier stages rejected.
  6. Learn the order and thresholds from labelled examples with an optimizer that maximises task performance within a budget.

Why this approach fits

Cheap models answer many queries correctly, and judging a finished answer is an easier learning problem than producing it. Because the check looks at the real answer, the cascade reacts to each query's actual difficulty instead of a guess made before seeing any output, and only the hard queries pay the top price.

Limitation or tradeoff

The authors state that the cascade needs labelled examples, that training queries must come from the same or a similar distribution as test queries, and that learning it takes resources, a one-time cost they call beneficial when the final query set is larger than the training data. A rejected query also pays for every model it passed through and waits for each in turn. The results use 2023 APIs and the paper's cost units, so the percentages should not be expected to carry over to current models and prices.

What the sources document

  • The paper proposes three strategies for cutting LLM cost, prompt adaptation, LLM approximation and LLM cascade, and presents FrugalGPT as an instantiation of the cascade that learns which combinations of LLMs to use for different queries. [11]
  • A cascade sends a query to a list of LLM APIs in sequence. If one API's response is judged reliable it is returned and no further APIs are queried. [11]
  • On HEADLINES the learned cascade calls GPT-J, J1-L and GPT-4 in turn, accepting GPT-J's answer when its score is above 0.96 and J1-L's answer when its score is above 0.37. [11]
  • Table 3 reports cost savings that match the best single LLM of 98.3% on HEADLINES, 73.3% on OVERRULING and 59.2% on COQA. The abstract states up to 98% cost reduction, or 4% higher accuracy than GPT-4 at the same cost. [11]
  • The stated limitations are the need for labelled examples, the need for training examples from the same or a similar distribution as test examples, and the resources needed to learn the cascade. [11]

Example 5 of 5

Azure API Management caching LLM answers by meaning at the gateway

Microsoft AzureDocumented in official docs

Microsoft Learn documents the llm-semantic-cache-lookup and llm-semantic-cache-store policies of Azure API Management, and a how-to article lists the components needed to enable semantic caching for an LLM API. [15][16]

The problem

Users of an LLM-backed API often ask the same question in different words. Without a cache, every variant reaches the backend model, consumes tokens and rate limit, and waits for a full generation. The documentation says response caching reduces the bandwidth and processing the backend LLM API must handle and lowers the latency that API consumers see.

Where this topic fits

The cache lives in the gateway, outside the application. An inbound policy checks it before the request is forwarded, and an outbound policy stores the model's response. On a miss the request continues to the model, where the provider's own prompt caching still applies.

How it is applied, step by step

  1. Add the LLM API to API Management, for example an Azure OpenAI deployment, and deploy an embeddings model to be used only for the cache.
  2. Create an Azure Managed Redis instance with the RediSearch module and configure it as the external cache of the API Management instance.
  3. In the inbound section, the lookup policy sends the incoming prompt to the embeddings backend and searches the cache for the closest earlier prompt.
  4. If the similarity is within the score threshold, the gateway returns the stored response without calling the LLM.
  5. Otherwise the request goes to the model, and the outbound store policy saves the response for the configured duration.
  6. A vary-by expression, such as the caller's subscription ID, partitions entries, and a rate-limit policy after the lookup protects the backend if the cache is unavailable.
  7. Trace requests in the test console to confirm hits, and adjust the threshold from what the traces show.

Why this approach fits

Traffic made of support-style questions repeats in meaning far more than in wording, so an exact-match cache would rarely hit, while embeddings catch paraphrases. Putting the cache in the gateway applies it to every client of the API without changing application code, and a hit costs one embedding call and one cache query instead of a full generation.

Limitation or tradeoff

The documentation warns that similarity is not equality, so a hit can be incorrect, outdated or unsafe for the current request, and that a threshold above 0.2 may cause mismatches. A typical implementation also adds an embedding call and a cache lookup to every miss, so a workload with few repeats can end up slightly slower and costlier than no cache. Anything personal must be partitioned or left out.

What the sources document

  • The lookup policy returns cached LLM responses based on vector proximity of the prompt to earlier requests and a score threshold, and the documentation says this reduces processing on the backend LLM API and lowers the latency API consumers perceive. [15]
  • The lookup policy needs a matching store policy and an embeddings backend, and the how-to article requires an Azure Managed Redis instance with the RediSearch module, which can only be enabled when the cache is created. [15][16]
  • The score-threshold ranges from 0.0 to 1.0 and lower values require higher semantic similarity. The documentation suggests starting with a low value such as 0.05 and warns that a threshold above 0.2 may lead to cache mismatch. [15]
  • A vary-by expression partitions the cache, and the documentation recommends specifying user or user group identifiers to control cross-user access to cache entries. [15]
  • Because it matches on similarity rather than exact text, semantic caching can surface responses that are incorrect, outdated or unsafe for the current request, and the documentation recommends a rate-limit policy right after the lookup in case the cache is unavailable. [15]

4Common mistakes

  1. Putting a timestamp, request ID or user name at the top of a long prompt.

    Why it causes problems
    The cache matches an exact prefix, so text that differs on every request makes every request a miss. You keep paying the full input price, and on Anthropic's 5-minute cache you also pay the 1.25 times write premium each time without ever collecting a read.
    How to recognise it
    cache_read_input_tokens (Anthropic) or cached_tokens (OpenAI) stays at zero across repeated requests that look identical to a human reader. Diff the rendered prompts of two consecutive requests and look at where they first differ.
    How to fix it
    Move all per-request text after the last cache breakpoint, render JSON with sorted keys, and alert when cached tokens divided by total input tokens drops below the rate you measured at launch.

  2. Marking a prompt for caching without checking its length or how often it is reused.

    Why it causes problems
    A prompt below the model's minimum cacheable length is processed uncached with no error. A prefix reused less often than the cache lifetime is written again every time, which costs more than not caching.
    How to recognise it
    Usage shows zero cache writes and zero reads (below the minimum), or large cache writes with zero reads (expired entries). Compare the gaps between requests with the lifetime.
    How to fix it
    Look up the model's minimum, pad or merge the stable content to reach it only if the reads justify it, and choose the 1-hour lifetime only when the prefix is reused at least twice within the hour.

  3. Rolling out a router, cascade or shorter output limit without a quality baseline.

    Why it causes problems
    The savings appear on the billing dashboard immediately, while the quality loss is invisible until users complain. Hard queries sent to a small model fail quietly, and a router tuned on public data can behave like a coin flip on your domain.
    How to recognise it
    Cost per request falls while task success, thumbs-down rate or escalations to humans drift up a week later. A router's choices all look the same regardless of query difficulty.
    How to fix it
    Build an evaluation set from real traffic first. Score routed answers against always-strong answers, release behind a flag to a small share of traffic, and track quality per route.

  4. Setting max_tokens low to control cost and calling that output control.

    Why it causes problems
    A response that reaches the cap stops mid-sentence or mid-JSON, which breaks parsers, and on reasoning models the thinking tokens share the same limit, so the answer may never start.
    How to recognise it
    The stop reason is max_tokens on a noticeable share of responses, or a parser reports unterminated JSON only on long inputs.
    How to fix it
    Ask for the short format in the prompt, pick a cap above the longest legitimate answer you have measured, treat the cap as a safety net, and alert on stop reason max_tokens.

  5. Putting a semantic cache in front of personalised or action-taking requests.

    Why it causes problems
    Similar wording does not mean the same request. A near miss can return another user's answer, an outdated policy, or the confirmation of an action that never ran for this user.
    How to recognise it
    Reviewing cache hits shows high-scoring pairs whose key details differ, such as an order number, a date or a negation. Users report answers about someone else's account.
    How to fix it
    Restrict the cache to public, slow-changing question types, partition entries by user or tenant, keep the threshold strict, check identifiers exactly before a hit, and log hit pairs for regular review.

Exercise 1

Replay request times against a prompt cache

CodingIntermediateAbout 30 min (estimate)Hypothetical scenario

A service sends the same 5,000-token prefix on every request and pays $3.00 per million input tokens. A cache hit costs 0.1 times the base price. A cache write costs 1.25 times for a 5-minute cache and 2.0 times for a 1-hour cache. Request start times, in seconds, are:

python
TIMES = (0, 120, 290, 700, 1000, 1250, 1500, 2600, 2700, 3900)
SPARSE = (0, 1000, 2000)

A request is a cache read when it starts at most ttl seconds after the start of the previous request (a read or a write refreshes the entry). Otherwise it is a cache write. Using only the standard library, write replay(times, ttl, write_multiplier) that returns (writes, reads, cost_usd) for the prefix, and compare the no-cache, 5-minute (300 s) and 1-hour (3600 s) options.

Requirements

  • replay returns a tuple of writes, reads and the prefix cost in dollars rounded to 4 decimals.
  • Print the cost without caching, then the 5-minute and 1-hour results for TIMES.
  • Print the same three results for SPARSE and add a comment explaining why the 5-minute cache costs more than no cache there.
  • Do not modify the input tuples or keep state outside the function.

Expected behaviour

The output is:

text
no cache        0.15
5-minute cache  (4, 6, 0.084)
1-hour cache    (1, 9, 0.0435)
sparse: no cache 0.045 5-minute (3, 0, 0.0562) 1-hour (1, 2, 0.033)

The 5-minute cache saves about 44% on TIMES and the 1-hour cache about 71%. On SPARSE every gap exceeds 300 s, so the 5-minute cache pays three writes and no reads.

Hint 1

Track only the start time of the previous request. The time since that request decides read or write.

Hint 2

The unit cost of one full-price pass over the prefix is 5,000 × 3.00 / 1,000,000 dollars.

Hint 3

Floating-point rounding can make 0.05625 print as 0.0562, so compare against the output shown, not a hand calculation.

Show solution
python
PREFIX_TOKENS = 5_000
BASE_PER_MTOK = 3.00
READ = 0.10                                   # multiplier of the base price
TIMES = (0, 120, 290, 700, 1000, 1250, 1500, 2600, 2700, 3900)
SPARSE = (0, 1000, 2000)

def replay(times, ttl, write_multiplier):
    """Return (writes, reads, cost in USD) for one prefix."""
    writes = reads = 0
    last_use = None
    for t in times:
        if last_use is not None and t - last_use <= ttl:
            reads += 1
        else:
            writes += 1
        last_use = t                          # a read or a write refreshes the entry
    unit = PREFIX_TOKENS * BASE_PER_MTOK / 1_000_000
    return writes, reads, round(unit * (writes * write_multiplier + reads * READ), 4)

def no_cache(times):
    return round(len(times) * PREFIX_TOKENS * BASE_PER_MTOK / 1_000_000, 4)

print("no cache       ", no_cache(TIMES))
print("5-minute cache ", replay(TIMES, 300, 1.25))
print("1-hour cache   ", replay(TIMES, 3600, 2.0))
# SPARSE: every gap is 1,000 s, longer than 300 s, so each request rewrites the
# entry at 1.25 times the price and none is ever read.
print("sparse: no cache", no_cache(SPARSE), "5-minute", replay(SPARSE, 300, 1.25), "1-hour", replay(SPARSE, 3600, 2.0))

Walk through TIMES by hand. With a 300 s lifetime, requests at 0, 700, 2600 and 3900 are writes because the previous request was more than 300 s earlier, and the other six are reads: 4 × 1.25 + 6 × 0.1 = 5.6 units of $0.015, which is $0.084 against $0.15. With a 3,600 s lifetime only the first request writes: 2.0 + 9 × 0.1 = 2.9 units, or $0.0435. The lesson of SPARSE is that a short lifetime with sparse traffic loses money, while the 1-hour option still wins because it bridges the gaps.

Check your answer

  • Does your output match the four lines shown, including (4, 6, 0.084) for the 5-minute cache?
  • Can you say why a read refreshes the entry and what that means for a steady stream of requests?
  • If the gaps in SPARSE were 200 s instead of 1,000 s, would the 5-minute cache beat no caching? Give both costs in units of one uncached pass over the prefix.

Exercise 2

Find the threshold of a toy semantic cache

CodingIntermediateAbout 35 min (estimate)Hypothetical scenario

A support bot stores three answered prompts. To stay dependency-free, the "embedding" of a prompt is its word counts, and similarity is cosine similarity. A real system would use an embedding model, but the threshold trade-off is the same.

python
import math
from collections import Counter

STORE = {
    "what is your refund policy": "refund-answer",
    "how long does shipping take": "shipping-answer",
    "cancel order 1234": "cancelled-1234",
}
# query -> stored prompt whose answer is correct for it, or None when no stored answer is right
CASES = {
    "what is the refund policy": "what is your refund policy",
    "how long will shipping take": "how long does shipping take",
    "what's your refund policy": "what is your refund policy",
    "cancel order 1235": None,
    "do not cancel order 1234": None,
    "refund policy for shipping": None,
}

def cosine(a, b):
    ca, cb = Counter(a.split()), Counter(b.split())
    dot = sum(ca[w] * cb[w] for w in ca)
    norm = math.sqrt(sum(v * v for v in ca.values())) * math.sqrt(sum(v * v for v in cb.values()))
    return round(dot / norm, 6) if norm else 0.0

Write lookup(query, threshold) that returns the best-matching stored prompt when its similarity is at least threshold, or None. Then, for thresholds 0.6, 0.7 and 0.8, count how many of the six cases get the right stored prompt and how many get a wrong one. Finally add a guard that blocks a hit when the numbers in the query differ from the numbers in the stored prompt, and count again.

Requirements

  • lookup returns the stored prompt string or None, never a partial match below the threshold.
  • A hit is right only when it equals the expected stored prompt in CASES. Any other hit, including a hit for a case that expects None, is wrong.
  • Print right and wrong counts at 0.6, 0.7 and 0.8, with and without the number guard.
  • Write two or three sentences on which wrong hit the guard cannot remove and what you would do about it.

Expected behaviour

The counts are (right, wrong):

text
0.6 plain: (3, 2) digit guard: (3, 1)
0.7 plain: (2, 1) digit guard: (2, 1)
0.8 plain: (2, 0) digit guard: (2, 0)

No threshold keeps all three paraphrases without accepting at least one wrong hit.

Hint 1

The scores are 0.8 for the first two cases, about 0.671 for the third, about 0.667 for the order 1235 case and about 0.775 for the negation case.

Hint 2

Rounding the similarity to six places avoids a 0.8 case failing a 0.8 threshold because of floating-point error.

Hint 3

To extract numbers, keep the words of a prompt that contain a digit and compare the two sets.

Show solution

Add this to the code in the prompt:

python
def digits(text):
    return {word for word in text.split() if any(ch.isdigit() for ch in word)}

def lookup(query, threshold, digits_must_match=False):
    """Return the stored prompt whose answer to reuse, or None for a miss."""
    best, best_score = None, 0.0
    for stored in STORE:
        if digits_must_match and digits(query) != digits(stored):
            continue
        score = cosine(query, stored)
        if score > best_score:
            best, best_score = stored, score
    return best if best_score >= threshold else None

def count_outcomes(threshold, guard):
    right = wrong = 0
    for query, want in CASES.items():
        got = lookup(query, threshold, guard)
        if got is not None and got == want:
            right += 1
        elif got is not None:
            wrong += 1
    return right, wrong

for threshold in (0.6, 0.7, 0.8):
    print(threshold, "plain:", count_outcomes(threshold, False), "digit guard:", count_outcomes(threshold, True))

At 0.6 the cache accepts the legitimate paraphrase "what's your refund policy" (0.671) but also "cancel order 1235" (0.667) and "do not cancel order 1234" (0.775). At 0.7 the paraphrase is lost and the negation is still accepted. At 0.8 nothing wrong gets through, but a real paraphrase is thrown away. The digit guard removes the order 1235 hit, because the numbers differ. It cannot remove the negation hit, because the numbers match and the words overlap heavily. Two fixes follow the spirit of Azure's advice to partition entries and evaluate carefully: do not cache requests that act on an account or that can be negated into an opposite meaning, and restrict the cache to public FAQ-style intents, partitioned by user where answers can differ. A real embedding model would put several of these near-misses even closer together, which is why a threshold alone is never the safeguard.

  • Do your counts match the three lines shown for all six combinations of threshold and guard?
  • Can you explain why raising the threshold to 0.8 removed every wrong hit and also what it cost?
  • Which cases would you refuse to cache at all in a production support bot, and why?
