Gradient Boosting (XGBoost, LightGBM)

Gradient boosting builds a prediction model as a sum of many small decision trees, added one at a time so that each new tree corrects the errors the current sum still makes. XGBoost, LightGBM and CatBoost are fast, regularised libraries that implement the idea.

1Overview

Why it matters

When the data is a table (rows of customers, requests, transactions or sensor readings, with columns of mixed numbers and categories), a gradient-boosted tree model is usually the first strong model to try, and often the one that ships. Bot detection, ad click prediction, search ranking and arrival-time estimation all have documented uses of it, and the real-world examples in this lesson come from those settings, plus a survey of competition-winning solutions.

It is also easy to get wrong in ways that look fine in a notebook. The number of trees, the learning rate and the tree size trade against each other. Choosing them on the same data you report results on gives optimistic scores. A model that wins on a table can be the wrong choice for images, free text, or a trend that continues beyond the training range. Data scientists, ML engineers and analysts who tune or review these models need to know what each setting does and which evidence should decide it.

Key terms

Weak learner
A deliberately simple model, here a shallow decision tree, that is only a little better than predicting the average. Boosting adds many of them.
Residual
The observed value minus the current model's prediction for one row. Positive means the model predicted too low.
Pseudo-residual (negative gradient)
The direction and size in which a row's prediction should move to reduce the loss fastest. For squared error it equals the residual; for other losses it does not.
Learning rate (shrinkage)
A number between 0 and 1 that scales every new tree before it is added, so that each tree makes only a small correction.
Boosting round
One pass of the loop: compute pseudo-residuals, fit one tree, add it to the model. The number of rounds is called n_estimators or num_boost_round, depending on the library.
Early stopping
Halting training when the loss on held-out validation data has not improved for a set number of rounds. XGBoost's scikit-learn interface and CatBoost's use_best_model setting can then predict with the best round instead of the last one.
Histogram binning
Grouping each feature's values into a few hundred bins before training, so that split search scans bins instead of every distinct value.
Leaf-wise growth
Growing a tree by repeatedly splitting the one leaf whose split reduces the loss most, instead of splitting every leaf at the same depth.
Hessian
The second derivative of the loss with respect to the prediction. XGBoost uses it together with the gradient to score splits and set leaf values.
Regularisation (lambda, gamma)
Penalties in XGBoost's objective that shrink leaf values (lambda) and make every extra leaf earn its place (gamma).

2Explanation

Introduction

You already know two ways of combining trees. A single decision tree is easy to read but unstable. A random forest grows many deep trees independently and averages them, which cancels much of their variance. Gradient boosting takes the opposite route: it adds many shallow trees one after another, and each new tree is trained to repair what the trees before it still get wrong.

Think of an editor and a manuscript. The first editor makes a rough pass. The second does not start again from the original; they read the edited draft and fix only what is still wrong. The third does the same to the second draft. No single editor has to be good. In boosting, the first draft is a constant, the average of the target, and each later tree predicts the residual: the observed value minus what the model currently predicts. The final model is that constant plus the small, scaled-down corrections of every tree.

The word "gradient" has a precise meaning. Predicting the residual is gradient descent, the method from loss functions and gradient descent, applied to the model's predictions instead of to a vector of weights. For squared error the negative gradient of the loss is exactly the residual. For other losses it is a different number, and swapping the loss is how one algorithm serves regression, classification and ranking. Friedman's paper Greedy Function Approximation: A Gradient Boosting Machine (opens in a new tab) presents boosting in exactly these terms.

XGBoost, LightGBM and CatBoost are open-source libraries that implement this loop with the engineering that makes it fast, regularised and practical on millions of rows. The lesson covers the mechanism, a six-row example you can finish by hand, how the learning rate, number of trees and early stopping interact, how the three libraries differ, why boosted trees are the usual baseline to beat on tabular data, and five documented real-world uses.

Learning rate and number of trees

Shrinkage makes each tree a small step, so reaching the same fit takes more trees. scikit-learn's guide states that smaller learning rates need more estimators, and it passes on the recommendation of Hastie, Tibshirani and Friedman to use a learning rate of 0.1 or less with a number of trees large enough for early stopping to apply. Defaults differ between libraries: XGBoost's parameter reference (opens in a new tab) lists eta = 0.3, while CatBoost's tuning guide (opens in a new tab) says the rate is chosen automatically from the dataset and the number of iterations.

The plot shows one-feature data, 60 training rows and 300 validation rows, boosted with stumps (the code is in the first exercise). With a rate of 1.0 the validation error is lowest after 11 trees and then climbs while the training error keeps falling. At 0.3 the minimum is at 81 trees and at 0.1 at 271 trees. The best validation errors are close (0.182, 0.182 and 0.185 mean squared error). What the small rate buys is a gentler approach, a wider range of tree counts that are nearly as good, and less damage when you overshoot: at 300 trees the three runs sit at 0.260, 0.202 and 0.185. The price is more trees to train and to evaluate.

Two other levers act on each tree. Size (depth or number of leaves) sets how many features can interact inside one tree; shallow trees give a simpler model. Sampling a fraction of rows per tree (stochastic gradient boosting) or of columns per tree adds randomness that reduces variance.

Early stopping

Instead of guessing the number of trees, set a generous maximum, hold out validation data, and stop when the validation loss has not improved for a set number of rounds (the patience). scikit-learn's histogram estimators expose early_stopping, n_iter_no_change and validation_fraction, and switch early stopping on by default for training sets of roughly 10,000 rows or more. XGBoost has early_stopping_rounds, and its scikit-learn interface (opens in a new tab) uses the best iteration automatically when predicting. LightGBM's tuning guide (opens in a new tab) names early_stopping_round with a validation set, and CatBoost has an overfitting detector.

The validation set has now helped choose the model, so its score is optimistic. Report the final number on a separate test set, as described in train/test splits and cross-validation.

Speed: histograms, leaf-wise growth and sampling

The expensive step is finding the best split. Sorting every feature at every node is slow, so modern libraries use histograms: continuous values are bucketed into bins (about 256 by default in XGBoost's hist method and in scikit-learn), and a split search scans bins. LightGBM's features page (opens in a new tab) also describes building the histogram for only one child and getting its sibling by subtraction.

LightGBM grows trees leaf-wise: it always splits the leaf with the largest loss reduction. For a fixed number of leaves this tends to reach lower loss than level-wise growth, but the tree can become deep and lopsided. The tuning guide therefore calls num_leaves the main complexity control, advises keeping it below 2max_depth2^{\text{max\_depth}}2max_depth, and calls min_data_in_leaf very important against overfitting. The LightGBM paper (opens in a new tab) adds two sampling tricks: GOSS drops many rows with small gradients, and EFB bundles features that are rarely non-zero together. Its abstract claims speed-ups of up to over 20 times at almost the same accuracy.

CatBoost attacks a different problem. Its paper (opens in a new tab) identifies a kind of target leakage, called prediction shift, in existing boosting implementations and proposes ordered boosting, a permutation-driven alternative, together with its own algorithm for categorical features. By default CatBoost builds symmetric trees, where every node at one depth uses the same split.

Why boosting does so well on tables

Part of the evidence is track record. The XGBoost paper reports that 17 of the 29 challenge-winning solutions published on Kaggle's blog in 2015 used XGBoost. Part is controlled comparison: Grinsztajn, Oyallon and Varoquaux (opens in a new tab) tested tree-based models against neural networks on 45 tabular datasets of about 10,000 training rows and found the trees ahead after heavy hyperparameter search. They offer three reasons: neural networks are biased toward smooth functions while tabular targets are often irregular; they are less robust to uninformative features; and rotation-invariant learners lose the meaning of individual columns. Trees also need no feature scaling, and several of the libraries above handle missing values and categories directly. The limits matter: that benchmark capped training sets at 10,000 rows (50,000 in an appendix), removed missing data and categorical features with more than 20 values, and leaves very large datasets as an open question. Uber's account below shows a team outgrowing XGBoost at scale.

The script below does the same computation with the standard library only. It needs no installation; the output was produced with Python 3.13.

python
def best_stump(xs, residuals):
    """Return (threshold, left_value, right_value) with the smallest squared error."""
    pairs = sorted(zip(xs, residuals))
    best = None
    for i in range(1, len(pairs)):
        if pairs[i - 1][0] == pairs[i][0]:
            continue
        threshold = (pairs[i - 1][0] + pairs[i][0]) / 2
        left = [r for x, r in pairs if x < threshold]
        right = [r for x, r in pairs if x >= threshold]
        left_value, right_value = sum(left) / len(left), sum(right) / len(right)
        sse = sum((r - left_value) ** 2 for r in left) + sum((r - right_value) ** 2 for r in right)
        if best is None or sse < best[0]:
            best = (sse, threshold, left_value, right_value)
    return best[1:]

def predict(model, x):
    base, learning_rate, stumps = model
    return base + sum(learning_rate * (lv if x < t else rv) for t, lv, rv in stumps)

def fit(xs, ys, learning_rate, rounds):
    """Return the model after every round; models[0] is the constant."""
    base = sum(ys) / len(ys)
    models = [(base, learning_rate, ())]
    for _ in range(rounds):
        current = models[-1]
        residuals = [y - predict(current, x) for x, y in zip(xs, ys)]
        models.append((base, learning_rate, current[2] + (best_stump(xs, residuals),)))
    return models

xs, ys = [1, 2, 3, 4, 5, 6], [1, 3, 8, 12, 13, 23]
for m, model in enumerate(fit(xs, ys, 0.5, 3)):
    predictions = [predict(model, x) for x in xs]
    mse = sum((y - p) ** 2 for y, p in zip(ys, predictions)) / len(ys)
    print(m, predictions, round(mse, 4))

Edge cases and limitations

Trees cannot extrapolate beyond the training range
Each leaf holds a constant, so the model is a step function. For an input larger than anything seen in training, the prediction stays at the last step however steeply the real relationship continues. The sign is a forecast of a growing quantity that flattens at the training maximum. Fit the trend with a simple model first and boost its residuals, predict a change or a ratio instead of the level, or add time-aware features. The Uber arrival-time example below corrects a routing engine's estimate instead of replacing it.
Squared error chases outliers
With squared error the pseudo-residual is the raw residual, so one mislabelled row with a huge error pulls every new tree toward it and can use up splits that belong to the bulk of the data. The sign is a validation error dominated by a handful of rows. Use absolute error or Huber loss, which scikit-learn's GradientBoostingRegressor offers (its histogram estimators have absolute error and quantile loss but not Huber), inspect the largest residuals before trusting them, and raise the minimum leaf size so that one row cannot form a leaf alone.
Reweighting classes distorts probabilities
XGBoost's tuning guide separates two goals. If you only care about ranking quality such as AUC, balance positive and negative weights with scale_pos_weight. If you need accurate probabilities you cannot rebalance the dataset, and the guide suggests a small finite max_delta_step. After reweighting, the scores are no longer calibrated probabilities: fit a calibration step on untouched validation data, or leave the weights alone and choose the decision threshold from the cost of each error.
Leaf-wise growth overfits small datasets
LightGBM's guide warns that for a fixed number of leaves a leaf-wise tree is typically much deeper than a depth-wise one, and advises keeping num_leaves below 2^max_depth and raising min_data_in_leaf. On a few hundred rows, leaves can end up holding only a handful of rows each, and those memorise noise. The sign is a training error near zero beside a much larger validation error. Lower num_leaves, raise the minimum leaf size and lower the learning rate.
A short patience stops early stopping too soon
Validation curves are noisy, most of all with small validation sets and low learning rates. In the lesson's experiment with a rate of 0.1, a patience of 5 rounds stops at round 98 and keeps the round-93 model with validation error 0.214. A patience of 50 runs to round 321 and keeps the round-271 model at 0.185 (the run continued to 600 trees). Set the patience to a sizeable fraction of the expected number of trees, use a validation set large enough to be stable, and look at the curve.

When to use it, and when something simpler is enough

Use it when

  • The data is a table with mixed numeric and categorical columns, missing values, non-linear effects and interactions, and thousands to millions of rows.
  • You want a strong model quickly with little feature scaling or preprocessing, as the baseline to beat before trying anything more elaborate.
  • You have a ranking, click or risk-scoring problem where a library offers the objective directly, such as XGBoost's ranking objectives, and inference must be fast without a GPU.

Think twice when

  • The inputs are raw images, audio or free text. Learn representations with neural networks, and use boosting on the resulting embeddings only if a table-style model is still useful.
  • The target must be extrapolated beyond the training range, such as a growing trend, unless the trend is modelled separately.
  • You need coefficients with confidence intervals for inference, or you have only a few dozen rows, where a regularised linear model is more stable and easier to defend.

A simpler alternative. Start with a regularised linear or logistic model and a random forest with default settings. A forest is hard to overfit by adding trees and needs little tuning. Move to boosting when held-out data shows a gain large enough to justify tuning the learning rate, the number of trees and the tree size.

Key takeaways

  • Gradient boosting adds shallow trees one at a time, each fitted to the negative gradient of the loss at the current predictions, which is the residual when the loss is squared error.
  • The learning rate and the number of trees trade against each other, so set a small rate and let early stopping choose the count; a smaller rate also degrades more gently past the optimum.
  • Early stopping picks the number of trees using validation data, so that score is optimistic and the final estimate must come from a separate test set.
  • XGBoost, LightGBM and CatBoost share the loop but differ in tree growth, categorical handling and speed techniques, so tune the settings that bound tree size, such as depth or number of leaves and the minimum leaf size.
  • Boosted trees are the default baseline for tables because they cope with irregular targets, uninformative features and unscaled columns, but they cannot extrapolate and they lose to neural networks on images, text and audio.

Example 1 of 5

Cloudflare Bot Management: CatBoost scoring every web request

CloudflareDocumented in an engineering article

Cloudflare's engineering post "Cloudflare Bot Management: machine learning and more" (6 May 2020) describes the machine-learning detection inside Cloudflare Bot Management and names CatBoost, a gradient boosting library, as its core. The CatBoost paper explains the library's boosting scheme. [16][11]

The problem

Cloudflare has to decide, for each HTTP request that reaches its network, whether it most likely came from a human or an automated program. The decision sits in the request path at a rate the post puts above 10 million requests per second, very few human visitors may be labelled as bots, and the inputs mix numbers with categorical attributes that can take a very large number of values. The adversaries adapt.

Where this topic fits

Machine learning is one of several detection mechanisms next to heuristics, behavioural analysis and verified-bot checks. The gradient boosted model sits in the middle of the ML path: request features go in, a single score comes out, and customers can set a threshold on that score. Its training labels come from the heuristics running beside it.

How it is applied, step by step

  1. Heuristics that are very sure about a request classify it as human or automated. The post says these high-certainty classifications are used to train the ML models, which are meant to generalise the learned behaviour beyond the rules themselves.
  2. For each request the system builds categorical and numerical features from the request's attributes and from features calculated across requests using those attributes.
  3. CatBoost trains a gradient boosted ensemble: trees are added one after another, each lowering the loss left by the earlier ones, and its categorical-feature support lets very high-cardinality columns be used directly.
  4. Several trained models are deployed to the edge. All of them run in shadow mode on every request on every machine, and one runs in active mode.
  5. For each request the active model's output becomes a score from 0 to 100, where a high value means a likely human. The post states that applying a model takes under 50 microseconds, which keeps scoring inside the request's time budget.

Why this approach fits

A request must be scored in microseconds on ordinary edge hardware. A tree ensemble is evaluated by following short paths through each tree, with no matrix multiplication, which suits that budget. The inputs are what tree models take without scaling: counts, rates and categories. CatBoost's categorical handling matters because identifier-like columns have very many values. Using heuristic verdicts as labels lets the model learn combinations of weak signals that no single rule captures.

Limitation or tradeoff

The labels come from heuristics, so the model inherits their blind spots: bots that no heuristic is sure about are probably under-represented in training. The post stresses that human visitors must almost never be mistaken for bots and that the adversaries keep adapting, which calls for monitoring and retraining. The post explains how quickly models can be deployed but not how often they are retrained. A score from 0 to 100 is also not a calibrated probability unless someone checks it as one.

What the sources document

Example 2 of 5

Facebook ad click prediction: boosted trees as a feature transformer

FacebookDocumented in a paper

The ADKDD 2014 paper "Practical Lessons from Predicting Clicks on Ads at Facebook" (He et al.) reports experiments on the click-prediction model that produces the final predictions for Facebook ads, the last stage of a cascade of classifiers. [15]

The problem

Facebook's ad system has to estimate how likely a user is to click each candidate ad. The paper describes more than 750 million daily active users and over a million active advertisers, so the model must be accurate and well calibrated, must keep up as the data distribution shifts from day to day, and must stay small and fast enough to run for every ad request. The paper scores models with normalized entropy (NE): the model's average log loss divided by the log loss of always predicting the overall click rate, so lower is better.

Where this topic fits

The boosted trees are not the final predictor. They are a supervised feature transformer placed in front of a logistic regression. The tree ensemble turns raw features into a short binary vector; the logistic regression produces the click probability and can be updated continuously.

How it is applied, step by step

  1. Train a boosted decision tree model in batch on logged impressions. The paper uses the classic L2-TreeBoost algorithm, in which each new tree models the residual of the previous trees.
  2. Pass every impression through every tree and record the leaf it reaches. A path from the root to a leaf is a rule over a few features, so the leaf index captures non-linear effects and feature interactions.
  3. Encode each tree as a categorical feature whose value is the leaf index, using one-hot (1-of-K) coding. With two trees of three and two leaves, an impression in leaf 2 of the first and leaf 1 of the second becomes [0, 1, 0, 1, 0].
  4. Train a logistic regression on these binary vectors. It learns one weight per rule, so the linear model is in effect weighting the rules the trees discovered.
  5. Refresh the two parts at different speeds: retrain the trees daily or every couple of days in batch, and train the linear classifier in near real time with online learning as labelled impressions arrive.
  6. Keep the trees affordable. The paper varies the number of trees from 1 to 2,000 with at most 12 leaves each and finds that almost all of the gain comes from the first 500.

Why this approach fits

Logistic regression is cheap to update online and returns a probability, but it can only add up per-feature effects. Building the bins and feature crosses that capture interactions by hand is slow work. Boosted trees find those splits and crosses from the data, and boosting points each later tree at what the earlier ones missed, so a modest number of small trees yields a useful set of rules. The pair keeps the linear model's freshness and the trees' expressiveness.

Limitation or tradeoff

The tree half is trained in batch, so it ages. The paper measures accuracy falling as the gap between training and test data grows and reports that moving from weekly to daily training lowers normalized entropy by about 1 per cent. Every extra tree costs prediction time and memory with diminishing returns, and the paper sees one sub-model get worse after 1,000 trees because its training data was four times smaller. The paper dates from 2014 and describes one architecture at that time; it does not say what Facebook uses today.

What the sources document

  • Adding tree feature transformations lowers normalized entropy by more than 3.4 per cent relative to the model without them, and the paper reports that the hybrid of decision trees and logistic regression beats either method alone by over 3 per cent. [15]
  • Each boosted tree is treated as a categorical feature whose value is the index of the leaf an instance falls in, with 1-of-K coding. The trees are built with the classic L2-TreeBoost algorithm, where each new tree models the residual of the previous trees. [15]
  • Table 1 gives normalized entropy relative to the trees-only model as 96.58 per cent for logistic regression plus trees, 99.43 per cent for logistic regression only and 100 per cent for trees only. [15]
  • Accuracy degrades as the delay between training and test data grows, and moving from weekly to daily training reduces normalized entropy by approximately 1 per cent. The boosted trees can be trained daily or every couple of days, while the linear classifier can be trained in near real time with online learning. [15]
  • In the experiment varying the number of trees from 1 to 2,000 with at most 12 leaves each, almost all of the improvement comes from the first 500 trees, the last 1,000 trees lower normalized entropy by less than 0.1 per cent, and one sub-model regresses after 1,000 trees because of overfitting. [15]

Example 3 of 5

Web search ranking with LambdaMART, boosted trees on a ranking gradient

Microsoft ResearchDocumented in a paper

Chris Burges's Microsoft Research report MSR-TR-2010-82 gives a self-contained account of LambdaMART, the boosted-tree member of the RankNet family, with web search ranking as its running example. XGBoost's learning-to-rank tutorial documents the same algorithm as a library feature. [14][5][3]

The problem

A search engine has to order the documents that match a query so that the most relevant ones come first. Quality is measured by ranking metrics such as NDCG (normalised discounted cumulative gain, which rewards putting highly relevant documents near the top). These depend on the order of a whole list and are not smooth functions of the model's scores. An ordinary regression or classification loss does not optimise them directly, and no gradient can be taken in the usual way.

Where this topic fits

The boosting loop is unchanged. LambdaMART changes the pseudo-residual: instead of y minus F, each document receives a value computed from pairs of documents within the same query, and the trees are fitted to those values. The training data is grouped by query.

How it is applied, step by step

  1. Collect judged examples: for each query, a list of documents with feature values and a graded relevance label. Keep the rows of one query together and identify them with a query id.
  2. Start from a constant score for every document.
  3. For each query, compare pairs of documents with different relevance labels and turn the comparisons into one pseudo-residual per document (a lambda). XGBoost's documentation describes a proxy gradient for each pair, and describes its plain pairwise objective as having no metric scaling, which implies that the NDCG objective scales by the metric.
  4. Fit a regression tree to the lambdas, set the leaf values with a Newton step as in other gradient boosting, and add the tree with the learning rate.
  5. Repeat for the chosen number of trees while tracking NDCG on validation queries. The report names the number of trees, a fixed learning rate and the number of leaves as the settings the user chooses.
  6. Combine several trained rankers into an ensemble, as the winning entry of the Yahoo challenge did.

Why this approach fits

Boosting only needs, for every row, a direction in which to push its score. That signal does not have to be the derivative of a smooth loss. LambdaMART supplies it directly from the ranking problem, so the same tree-fitting machinery ends up optimising what the search team cares about. Trees also cope with the mix of differently scaled, heterogeneous features that rankers use.

Limitation or tradeoff

Training needs relevance labels grouped by query, which are costly to obtain. The competition result shows what the method achieved on one benchmark in 2010; the report does not describe how any search engine deploys it. Pairwise computation grows with the number of documents per query, which is why XGBoost offers pair-sampling options (mean and topk) to control the cost.

What the sources document

  • LambdaMART is the boosted tree version of LambdaRank, which is based on RankNet. The report states that an ensemble of LambdaMART rankers won Track 1 of the 2010 Yahoo! Learning To Rank Challenge, and it uses ranking for web search as its concrete example throughout. [14]
  • MART is described as gradient descent in function space using regression trees: each tree models the derivative of the cost with respect to the current model score, step sizes are computed exactly or with Newton's approximation, and a step smaller than the optimal one acts as a form of regularisation. [14]
  • The settings chosen by the user are the number of trees, a fixed learning rate that multiplies every leaf value, and the number of leaves. [14]
  • XGBoost's learning-to-rank tutorial says its default objective rank:ndcg is based on LambdaMART, compares every pair of samples in a query group to compute a proxy gradient, and needs training rows sorted by query id. [5]
  • XGBoost's parameter reference lists rank:ndcg as the objective that uses LambdaMART to perform pair-wise ranking. [3]

Example 4 of 5

Uber arrival times: gradient-boosted trees correcting a routing engine

UberDocumented in an engineering article

Two Uber Engineering posts. "DeepETA: How Uber Predicts Arrival Times Using Deep Learning" (10 February 2022) describes the earlier system for estimated times of arrival (ETAs), in which gradient-boosted trees refined a routing engine's estimate. "Productionizing Distributed XGBoost to Train Deep Tree Models with Large Data Sets at Uber" (10 December 2019) describes how Uber trains XGBoost models on its Michelangelo platform. [18][17]

The problem

Uber needs accurate estimated times of arrival for rides and deliveries. A routing engine can estimate travel time from the road graph, but its estimate differs systematically from what really happens, and the size of the gap depends on place, time and live conditions. The correction has to be learned from a very large history of trips and served fast enough for what the post calls the highest-QPS (queries per second) model at Uber.

Where this topic fits

The boosted model is a post-processing stage after the routing engine. The DeepETA post calls the hybrid approach ETA post-processing: machine learning predicts the residual between the routing engine's ETA and real-world outcomes, and gradient-boosted tree ensembles refined ETAs this way for several years before DeepETA. The post does not spell out that the XGBoost model's target was exactly this residual, so that detail is our reading. A residual target suits boosting: the base estimate already explains most of the variation, so the trees only have to learn the systematic remainder.

How it is applied, step by step

  1. The routing engine predicts travel time over the road graph and produces a base ETA for the trip.
  2. Training rows combine historical trips with real-time signals; the post lists spatial and temporal features such as origin, destination and request time, plus real-time traffic. In the residual formulation the target is the observed outcome minus the routing engine's ETA.
  3. Gradient-boosted trees are trained on that target. The DeepETA post says the ETA model and its training data grew with each release and that Uber's Spark team contributed upstream changes to XGBoost so the model could grow deeper. The Michelangelo post, which lists ETA accuracy among its use cases, describes the training setup: XGBoost on Spark with its all-reduce implementation, building deep trees (depth 16 and beyond) on billions of records.
  4. At request time, a typical implementation adds the predicted residual to the routing ETA (the post does not spell out the combination step). The DeepETA post states the serving constraint for this stage: an ETA within a few milliseconds at most, from what it calls the highest-QPS model at Uber.
  5. The Michelangelo post lists the operational traps: out-of-memory errors and segmentation faults, JVM heap versus off-heap memory, and mixing sparse and dense vector formats.
  6. As data and model size grew, Uber reports that scaling XGBoost became untenable and moved the post-processing model to deep learning.

Why this approach fits

A correction model leaves the bulk of the signal to the existing estimate, and the ensemble spends its capacity on structured errors, such as places and hours where the routing engine is consistently optimistic. Tree models take mixed spatial, temporal and categorical inputs as they are, and a trained ensemble is a fixed set of cheap lookups at serving time.

Limitation or tradeoff

Uber's own conclusion marks the limit: the post says that increasing the dataset and the model size with XGBoost became untenable, and that deep learning scaled more easily with data-parallel training. Deep trees on billions of rows also demand careful distributed memory management, as the Michelangelo post shows. A residual model inherits the base estimator's errors: if the routing ETA is wrong in a way the features cannot explain, the correction cannot repair it.

What the sources document

  • The DeepETA post says Uber used gradient-boosted decision tree ensembles to refine ETA predictions for several years, and describes a hybrid "ETA post-processing" approach in which machine learning predicts the residual between the routing engine's ETA and real-world observed outcomes. [18]
  • The post states that the model must return an ETA within a few milliseconds at most and that this post-processing model is the highest-QPS model at Uber. [18]
  • The post says the ETA model and its training dataset grew with each release, that Uber's Apache Spark team contributed upstream improvements to XGBoost so the model could grow ever deeper, making it one of the largest and deepest XGBoost ensembles in the world at that time, and that eventually increasing the dataset and model size with XGBoost became untenable, so Uber explored deep learning for its relative ease of scaling to large datasets with data-parallel stochastic gradient descent. [18]
  • The Michelangelo XGBoost post lists forecasting rider demand, fraud detection, food discovery and recommendation for Uber Eats, and improving ETA accuracy as use cases. It describes training deep trees (depth 16 and beyond) on billions of records with Spark MLlib and XGBoost's all-reduce implementation, and reports significant gains in model performance without publishing figures. [17]
  • The same post names out-of-memory errors and segmentation faults as the two most common issues, recommends tuning spark.executor.memoryOverhead to decouple heap and off-heap memory, and warns that mixing SparseVector and DenseVector inputs gives inconsistent predictions. [17]

4Common mistakes

  1. Choosing the number of trees or the learning rate on the test set, or quoting the early-stopping validation score as the final result

    Why it causes problems
    The rows used to pick the model have helped fit it, so the reported score is optimistically biased. The more settings you try against the same rows, the larger the bias, and an apparent gain over a simpler model can vanish on new data.
    How to recognise it
    The test score was looked at more than once, or the same rows served as the early-stopping set and as the reported evaluation. A drop when a fresh batch of data arrives is the late symptom.
    How to fix it
    Split off a test set first and touch it once. Do early stopping and tuning on a validation split, or by cross-validation inside the training data, and report the single test number. For time-ordered data keep validation and test later in time than training.

  2. Leaving the defaults, a fixed number of trees with a large learning rate

    Why it causes problems
    Libraries ship defaults, not answers. XGBoost's eta defaults to 0.3, and a fixed tree count either stops before the loss has converged or runs past the point where validation error rises. In the lesson's experiment, a rate of 1.0 is best at 11 trees and clearly worse by 300.
    How to recognise it
    Training error keeps falling while validation error is flat or rising, or both are still falling when training stops. Plot validation loss against the number of trees instead of reading a single final number.
    How to fix it
    Use a learning rate of 0.1 or less, set the number of trees high and let early stopping choose it, as scikit-learn's guide recommends. Then tune the tree size before the other settings.

  3. Using deep trees or many leaves, with tiny leaves, on a small dataset

    Why it causes problems
    Leaves that hold a handful of rows memorise noise. Each added tree then fits the noise left by the earlier ones, so the training error shrinks while the validation error grows.
    How to recognise it
    Training error near zero with a large gap to validation error, even though early stopping is on.
    How to fix it
    Lower the depth or num_leaves, raise min_child_weight or min_data_in_leaf, add row and column subsampling and the lambda and gamma penalties, and lower the learning rate.

  4. Target-encoding categorical columns by hand using the whole training set

    Why it causes problems
    Replacing a category with the mean label of its rows lets each row's own label leak into its feature. The trees exploit the leak, the score looks good inside the pipeline, and the model does worse on new data. The CatBoost paper builds its categorical-feature algorithm around avoiding this kind of target leakage.
    How to recognise it
    A feature derived from a categorical column dominates the importances, and the validation score collapses when the encoding is recomputed out of fold or evaluated on a later period.
    How to fix it
    Use the library's native categorical handling, or compute target statistics out of fold so that no row's encoding sees its own label.

  5. Splitting randomly when rows are ordered in time or grouped by customer or device

    Why it causes problems
    Rows from the same customer or the same week land on both sides of the split, so the model is tested on near-copies of what it trained on. Boosted trees are very good at memorising such repeats, which inflates the score.
    How to recognise it
    The score drops sharply when you evaluate on a later period or on customers that were not in the training data.
    How to fix it
    Split by time, training on the past and validating on the future, or by group, keeping all rows of one entity on one side. Use the same split for early stopping.

Hint 1

A stump search is a loop over the sorted x values. For each gap between neighbours, average the residuals on each side and add up the squared leftovers.

Hint 2

Store a model as the base value, the learning rate and a tuple of (threshold, left_value, right_value) stumps, and write one predict function that training and evaluation both use.

Hint 3

Recompute the residuals from the current model at the start of every round instead of updating them by hand.

Hint 4

For early stopping, remember the best validation value and its round, count the rounds since the last improvement, and stop when the count reaches the patience.

Show solution

One file does all three parts. best_stump tries every threshold, fit repeats the boosting round and early_stopping scans the validation errors.

python
import math
import random


def best_stump(xs, residuals):
    """Return (threshold, left_value, right_value) with the smallest squared error."""
    pairs = sorted(zip(xs, residuals))
    best = None
    for i in range(1, len(pairs)):
        if pairs[i - 1][0] == pairs[i][0]:
            continue
        threshold = (pairs[i - 1][0] + pairs[i][0]) / 2
        left = [r for x, r in pairs if x < threshold]
        right = [r for x, r in pairs if x >= threshold]
        left_value, right_value = sum(left) / len(left), sum(right) / len(right)
        sse = sum((r - left_value) ** 2 for r in left) + sum((r - right_value) ** 2 for r in right)
        if best is None or sse < best[0]:
            best = (sse, threshold, left_value, right_value)
    return best[1:]


def predict(model, x):
    base, learning_rate, stumps = model
    return base + sum(learning_rate * (lv if x < t else rv) for t, lv, rv in stumps)


def fit(xs, ys, learning_rate, rounds):
    """Return the model after every round; models[0] is the constant."""
    base = sum(ys) / len(ys)
    models = [(base, learning_rate, ())]
    for _ in range(rounds):
        current = models[-1]
        residuals = [y - predict(current, x) for x, y in zip(xs, ys)]
        models.append((base, learning_rate, current[2] + (best_stump(xs, residuals),)))
    return models


def mse(model, xs, ys):
    return sum((y - predict(model, x)) ** 2 for x, y in zip(xs, ys)) / len(ys)


def make_data(n, rng):
    xs = [rng.uniform(0, 10) for _ in range(n)]
    ys = [math.sin(x) + rng.gauss(0, 0.4) for x in xs]
    return xs, ys


def early_stopping(errors, patience):
    """Return (stop_round, best_round) for validation errors indexed by round."""
    best_round, since_best = 0, 0
    for r in range(1, len(errors)):
        if errors[r] < errors[best_round]:
            best_round, since_best = r, 0
        else:
            since_best += 1
            if since_best >= patience:
                return r, best_round
    return len(errors) - 1, best_round


# Part A
xs, ys = [1, 2, 3, 4, 5, 6], [1, 3, 8, 12, 13, 23]
for rate in (0.5, 1.0):
    model = fit(xs, ys, rate, 3)[3]
    print("A", rate, [round(predict(model, x), 2) for x in xs], round(mse(model, xs, ys), 4))

# Part B
rng = random.Random(7)
train_x, train_y = make_data(60, rng)
valid_x, valid_y = make_data(300, rng)
for rate in (1.0, 0.3, 0.1):
    errors = [mse(m, valid_x, valid_y) for m in fit(train_x, train_y, rate, 300)]
    best = min(range(len(errors)), key=errors.__getitem__)
    print("B", rate, "best round", best, round(errors[best], 4), "round 300", round(errors[300], 4))

# Part C
errors = [mse(m, valid_x, valid_y) for m in fit(train_x, train_y, 0.1, 600)]
for patience in (5, 50):
    stop, best = early_stopping(errors, patience)
    print("C patience", patience, "stops at", stop, "keeps round", best, round(errors[best], 4))

  • Is the best validation round for rate 1.0 far earlier than for rate 0.1 (11 against 271)?
  • Does patience 5 stop earlier and keep a worse model than patience 50 for rate 0.1?

Exercise 2

Compare learning rates with early stopping in scikit-learn

Hands-onIntermediateAbout 40 min (estimate)Hypothetical scenario

With scikit-learn (free; pip install scikit-learn), study how the learning rate changes the number of boosting iterations that early stopping needs, and check that your final score is reported honestly.

Start from this code:

python
from sklearn.datasets import make_classification
from sklearn.ensemble import HistGradientBoostingClassifier
from sklearn.metrics import log_loss
from sklearn.model_selection import train_test_split

X, y = make_classification(n_samples=20000, n_features=20, n_informative=6,
                           flip_y=0.05, random_state=0)
X_train, X_test, y_train, y_test = train_test_split(X, y, test_size=0.25, random_state=0)
  1. For learning rates 0.5, 0.1 and 0.03, fit HistGradientBoostingClassifier(max_iter=1000, early_stopping=True, validation_fraction=0.15, n_iter_no_change=20, random_state=0) and record n_iter_ (the number of boosting iterations that were run), the test log loss and the fit time.
  2. Repeat the rate-0.5 run with early_stopping=False, so that all 1000 iterations are used.
  3. Put the four results in a table and write two sentences on what you see.
  4. Explain why the test log loss is a fair estimate while the validation score used inside early stopping is not.

Requirements

  • Use the same data split and random seeds for every run, and never use the test set to choose a setting.
  • Report n_iter_, the test log loss and the fit time for all four runs in one table.
  • Include the run with early stopping switched off, at learning rate 0.5.

Expected behaviour

A table with four rows. With early stopping, n_iter_ should grow as the learning rate shrinks (the smallest rate may come close to the 1000 cap), and the three test log losses should be close to one another. The run without early stopping uses all 1000 iterations, takes longer, and is likely to end with a worse test log loss because a large rate can overfit when it is allowed to continue. Exact numbers depend on your scikit-learn version, so compare the pattern rather than the digits, and if your result differs, report what you see and say why.

Hint 1

`model.n_iter_` is available after `fit`, and `log_loss(y_test, model.predict_proba(X_test))` scores the predicted probabilities.

Hint 2

Wrap `model.fit` between two calls to `time.perf_counter()` to time it.

Hint 3

When early stopping is off, scikit-learn ignores validation_fraction and n_iter_no_change.

Show solution
python
import time

from sklearn.datasets import make_classification
from sklearn.ensemble import HistGradientBoostingClassifier
from sklearn.metrics import log_loss
from sklearn.model_selection import train_test_split

X, y = make_classification(n_samples=20000, n_features=20, n_informative=6,
                           flip_y=0.05, random_state=0)
X_train, X_test, y_train, y_test = train_test_split(X, y, test_size=0.25, random_state=0)


def run(learning_rate, early_stopping):
    model = HistGradientBoostingClassifier(
        learning_rate=learning_rate, max_iter=1000, early_stopping=early_stopping,
        validation_fraction=0.15, n_iter_no_change=20, random_state=0)
    start = time.perf_counter()
    model.fit(X_train, y_train)
    seconds = time.perf_counter() - start
    loss = log_loss(y_test, model.predict_proba(X_test))
    return model.n_iter_, loss, seconds


for rate in (0.5, 0.1, 0.03):
    n_iter, loss, seconds = run(rate, True)
    print(f"rate {rate}: stopped after {n_iter} iterations, test log loss {loss:.4f}, {seconds:.1f}s")

n_iter, loss, seconds = run(0.5, False)
print(f"rate 0.5, no early stopping: {n_iter} iterations, test log loss {loss:.4f}, {seconds:.1f}s")

The pattern to expect, not exact digits: the rate-0.5 run stops first, the rate-0.1 run later, and the rate-0.03 run needs the most iterations, possibly approaching the 1000 cap. The three early-stopped models reach similar test log loss, so the smaller rates buy a smoother path to the optimum, not a dramatically better optimum, in line with the stump experiment. The rate-0.5 run without early stopping uses all 1000 iterations and is likely to score worse, because its probabilities can grow overconfident once the model fits the label noise (about 5 per cent of the labels are assigned at random).

The test log loss is fair because no decision about the settings used the test rows. The validation score inside early stopping is not: that data chose when to stop, so it is a slightly flattering estimate of performance on new data. If you also tuned the learning rate by comparing validation scores, the bias is larger still.

Check your answer

  • Is n_iter_ for rate 0.03 larger than n_iter_ for rate 0.5?
  • Did you leave the test set out of every choice of setting?
  • Can you explain why early-stopped models with different learning rates reach similar test log loss?
