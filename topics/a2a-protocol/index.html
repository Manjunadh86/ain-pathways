Agent2Agent (A2A) Protocol

The Agent2Agent (A2A) protocol is an open standard that lets one AI agent find another agent, hand it a task over HTTP, and receive messages and results back without seeing how the other agent works inside. An agent describes itself in a JSON Agent Card, and the work is tracked as a task with a defined lifecycle.

1Overview

Why it matters

Agents inside one program can call each other as objects. Agents owned by different teams, vendors or clouds cannot: they run as separate services, use different frameworks, and are not allowed to share memory or code. Without a shared protocol every pair needs its own connector, the security model is improvised each time, and work that takes minutes has nowhere to live in a plain request and response. A2A defines the missing pieces: how a client finds an agent and learns what it can do, how work is tracked as a task, and how results, questions and progress travel back.

You meet it when you plug a third-party agent into a product (Jira can assign work items to remote agents using a subset of A2A), when you publish an agent for others to call, or when a platform team puts a gateway in front of internal agents. Two things make it easy to get wrong. First, A2A is not a tool-calling protocol: the other side is an agent that may ask questions and take hours. Second, the wire format changed between version 0.3 and the stable 1.0, and documentation, SDKs and gateways in the wild still mix both.

Key terms

A2A client
The application or agent that acts for a user, reads the remote agent's card and starts the conversation. The documentation also calls it the client agent.
A2A server
An agent or agentic system that exposes an HTTP endpoint implementing A2A. To the client it is a black box, so its memory, tools and reasoning stay private. Also called the remote agent.
Agent Card
A JSON document, normally served at /.well-known/agent-card.json, that states an agent's name, skills, capabilities, supported interfaces and security requirements.
Skill
An entry in the Agent Card describing one kind of work the agent can do, with an id, a description, tags and optional examples.
Message
One turn of communication between client and agent, with a role (user or agent) and a list of parts.
Part
The smallest unit of content in a message or artifact. It holds one of: text, inline bytes, a URL pointing to a file, or structured JSON data.
Task
A stateful unit of work created by the server, with an id, a status and optional artifacts. It moves through states such as working, input-required and completed.
Artifact
A deliverable produced by a task, such as a document, an image or structured data, made of parts. Messages are the conversation; artifacts are the results.
contextId
An identifier that groups related messages and tasks into one conversation so that context carries across several tasks.
Protocol binding
The concrete way the A2A operations are carried: JSON-RPC 2.0 over HTTP, gRPC, or HTTP with JSON (REST-style). An Agent Card lists the bindings an agent supports.

2Explanation

Introduction

In Multi-Agent Systems the agents usually live in one program: an orchestrator calls workers as functions and they share a process. In Model Context Protocol you saw a standard way to connect an agent to tools and data. A2A covers a third situation: the other party is itself an agent, run by someone else, and all you have is a network address.

Think of hiring an outside agency. First you read its public profile to see what it does and how to contact it. You send a request and get back a ticket number. The agency may reply with a question ("which budget?"), send progress updates, and finally deliver files. You never see its staff, tools or internal notes. A2A formalises exactly this exchange: a profile (the Agent Card), a ticket (the task), conversation turns (messages) and deliverables (artifacts), all carried over ordinary web technology.

Google announced A2A in April 2025 with more than 50 technology partners and listed five design principles: embrace agentic capabilities, build on existing standards, secure by default, support long-running tasks, and stay modality agnostic. It is now an open project. In August 2026 the Agentic AI Foundation, which the Linux Foundation hosts, announced that A2A is joining it as a hosted project. The specification page lists 1.0.0 as the current version, with 0.3.0, 0.2.6 and 0.1.0 before it.

This lesson follows the order in which a client meets the protocol: discovery, the operations and their wire format, messages and parts, tasks and their lifecycle, getting progress back, security, and how A2A fits with MCP. A runnable example then shows a complete conversation, and five documented products show A2A at work.

How it works

Two roles, and a remote agent that stays opaque

An A2A client acts for a user and starts the conversation. An A2A server, also called the remote agent, exposes an HTTP endpoint that implements the protocol. The documentation describes the server as a black box to the client: its internal workings, memory and tools stay hidden. That is the difference from a local sub-agent, and it is why the protocol only defines what crosses the wire.

A2A reuses web standards: HTTPS, JSON-RPC 2.0 and Server-Sent Events (SSE), a one-way stream of events over a long-lived HTTP response. Version 1.0 offers the same operations over three protocol bindings: JSON-RPC, gRPC and HTTP+JSON. The Protocol Buffers file a2a.proto is the normative definition.

Step 1: discovery with the Agent Card

The client first needs the Agent Card. The documentation names three ways to find one:

  • Well-known URI. The server hosts the card at https://{domain}/.well-known/agent-card.json, following RFC 8615.
  • Curated registry. An intermediary service keeps cards that clients query by criteria. The Agent Discovery page notes that the specification does not prescribe a standard API for registries.
  • Direct configuration. The client is given the address through configuration, environment variables or a proprietary API.

The card is a JSON document. These are the fields that matter most:

FieldWhat it tells the client
name, description, version, providerWho the agent is and which version of it this is
supportedInterfacesAn ordered list. Each entry has url, protocolBinding (JSONRPC, GRPC or HTTP+JSON) and protocolVersion. The first entry the client can speak wins
capabilitiesBooleans streaming, pushNotifications and extendedAgentCard, plus extensions
skillsWhat it can do: id, name, description, tags, optional examples
defaultInputModes, defaultOutputModesMedia types it accepts and produces, such as text/plain
securitySchemes and the security requirementsHow to authenticate: API key, HTTP auth, OAuth 2.0, OpenID Connect or mutual TLS
signaturesOptional cryptographic signatures over the card

A card endpoint needs authentication if the card holds sensitive detail. When capabilities.extendedAgentCard is true, a client can call GetExtendedAgentCard after authenticating to receive a fuller card.

Step 2: the operations and the wire format

The client chooses an interface from the card and sends an A2A-Version header such as 1.0. The builder's guide warns that a missing header means 0.3, not "latest". The core operations are:

OperationPurposeHTTP+JSON form
SendMessageStart or continue work; blocking by defaultPOST /message:send
SendStreamingMessageSame, with the reply as an event streamPOST /message:stream
GetTaskRead a task's state, artifacts and historyGET /tasks/{id}
ListTasksList tasks with filters and paginationGET /tasks
CancelTaskAsk the agent to stopPOST /tasks/{id}:cancel
SubscribeToTaskAttach a stream to an existing taskPOST /tasks/{id}:subscribe (a2a.proto says GET)
push notification config (create, get, list, delete)Manage webhooks for one task/tasks/{task_id}/pushNotificationConfigs
GetExtendedAgentCardFetch the fuller, authenticated cardGET /extendedAgentCard

In JSON-RPC the method name is the operation name. This request starts a task, and the response is the one the worked example produces:

json
{"jsonrpc": "2.0", "id": 1, "method": "SendMessage",

                        "parts": [{"text": "Convert 25 degrees"}]}}}
json
{"jsonrpc": "2.0", "id": 1,

   "status": {"state": "TASK_STATE_INPUT_REQUIRED",
     "message": {"messageId": "task-1-q", "role": "ROLE_AGENT", "taskId": "task-1", "contextId": "ctx-1",
                 "parts": [{"text": "Celsius to Fahrenheit, or Fahrenheit to Celsius?"}]}}}}}

Two details of the 1.0 JSON: enum values are SCREAMING_SNAKE_CASE strings such as ROLE_USER and TASK_STATE_WORKING, and the kind of a part is given by which member is present (text, raw, url or data), with no kind field.

Step 3: messages, parts and artifacts

A message is one turn. It has a messageId chosen by its creator, a role (ROLE_USER for the client, ROLE_AGENT for the server) and a list of parts. Optional fields link it to earlier work: contextId, taskId and referenceTaskIds. A part carries exactly one kind of content: text, raw (inline bytes), url (a pointer to a file) or data (structured JSON), with optional mediaType and filename.

An artifact is a deliverable produced by a task. It has an artifactId, an optional name and description, and parts. The documentation separates the two on purpose: messages are the conversation, artifacts are the results. A streaming server can send a large artifact in chunks, using the append and lastChunk flags of TaskArtifactUpdateEvent.

Step 4: tasks and their lifecycle

The server decides how to answer a SendMessage. For a quick, self-contained exchange it replies with a Message and nothing is left to track. For work that has progress, may need input or produces results, it replies with a Task. The documentation describes three server styles: message-only, task-generating (always returns tasks, even for simple replies) and hybrid, which settles the scope in messages and then commits to a task.

A task has a server-generated id, a contextId, a status (state, optional message, timestamp), artifacts and optional history. A client cannot choose the task id. The contextId groups related messages and tasks. The server assigns it on a first message, and the client repeats it, and the taskId, in follow-up messages.

Two groups of states matter. Terminal states end the task: completed, failed, canceled and rejected (the agent decided not to do the task). Interrupted states pause it: input-required, where the agent needs more from the user, and auth-required, where it needs credentials. The client resumes an interrupted task by sending another message with the same taskId and contextId. A terminal task cannot restart. A follow-up or a refinement becomes a new task in the same context, which can point back to the earlier one with referenceTaskIds. One context can therefore hold several tasks, such as a flight booking and then a hotel.

Step 5: getting progress and results back

By default SendMessage blocks until the task finishes or pauses. That suits short jobs and causes timeouts on long ones, so a client can set returnImmediately: true in the request configuration to receive the task at once. After that there are three ways to follow it:

A stream follows one of two shapes: a single Message, or a Task followed by statusUpdate and artifactUpdate events for that task. In 1.0 the server enforces that shape: sending a Message after a Task, sending several Messages, or sending a status update before the first Task raises InvalidAgentResponseError, where 0.3 servers tolerated it.

For push, the client supplies a TaskPushNotificationConfig holding a webhook url (the specification recommends HTTPS), an optional token and authentication details, either in the first request or through a separate operation. The server posts the same event objects a stream would carry to that webhook. The specification requires the server to authenticate itself to the webhook and the receiver to verify every call before trusting it.

Step 6: security

Production traffic must use HTTPS. A2A payloads do not carry user or client identity. Identity travels in standard HTTP headers, for example Authorization: Bearer <token>, obtained outside the protocol by whichever scheme the card advertises. The server authenticates every request, answers 401 or 403 when it cannot, and can authorize per skill. If a task needs extra credentials midway it moves to auth-required, and the client obtains them out of band.

An Agent Card can be signed: a JSON Web Signature (RFC 7515) over the card canonicalised with RFC 8785. Clients should verify a signature when present, and a valid one shows the card was not altered. The builder's guide is explicit that this is separate from deciding whether you trust the organisation behind the key. Treat whatever a remote agent sends back as untrusted input, as you would a tool result.

How A2A fits with MCP

The two protocols run along different lines. MCP is vertical: it deepens one agent by connecting it to tools and resources, which have well-defined structured inputs and outputs and are often stateless. A2A is horizontal: it connects agents across a boundary for multi-turn, task-oriented work. The A2A documentation's example is an auto repair shop. A customer talks to a shop-manager agent, and a mechanic agent negotiates with a parts-supplier agent over A2A, while the mechanic uses diagnostic scanners and repair manuals as tools over MCP. An MCP tool call invokes a function; an A2A message hands over a goal.

Worked example: A two-turn conversation with a temperature agent

This example runs a complete A2A conversation on your machine with the Python standard library only. The script is about 100 lines. Its server publishes an Agent Card, answers JSON-RPC SendMessage and GetTask calls in the 1.0 format, and keeps tasks in a dictionary; its client reads the card and runs the conversation. It is a teaching server with no streaming, push, authentication or error handling, so do not deploy it. Save it as a2a_demo.py and run python3 a2a_demo.py (tested on Python 3.13; change PORT if 9753 is busy).

python
import json
import re
import threading
from http.server import BaseHTTPRequestHandler, HTTPServer
from itertools import count
from urllib.request import Request, urlopen
from uuid import uuid4

PORT = 9753
BASE = f"http://127.0.0.1:{PORT}"
CARD = {
    "name": "Temperature Agent",
    "description": "Converts a temperature between Celsius and Fahrenheit.",
    "version": "0.1.0",
    "supportedInterfaces": [{"url": BASE + "/", "protocolBinding": "JSONRPC", "protocolVersion": "1.0"}],
    "capabilities": {"streaming": False, "pushNotifications": False},
    "defaultInputModes": ["text/plain"],
    "defaultOutputModes": ["text/plain"],
    "skills": [{"id": "convert", "name": "Convert", "description": "C to F and back.", "tags": ["units"]}],
}
TASKS, VALUES, IDS = {}, {}, count(1)


def convert(text, value):
    text = text.lower()
    if "celsius to fahrenheit" in text:
        return f"{value:g} C = {value * 9 / 5 + 32:.1f} F"
    if "fahrenheit to celsius" in text:
        return f"{value:g} F = {(value - 32) * 5 / 9:.1f} C"


def send_message(params):
    message = params["message"]
    text = message["parts"][0]["text"]
    task_id = message.get("taskId")
    if task_id is None:  # a new task: the server chooses both ids
        n = next(IDS)
        task_id, context_id = f"task-{n}", message.get("contextId") or f"ctx-{n}"
        VALUES[task_id] = float(re.search(r"-?\d+(?:\.\d+)?", text).group())
    else:
        context_id = TASKS[task_id]["contextId"]
    answer = convert(text, VALUES[task_id])
    task = {"id": task_id, "contextId": context_id, "status": {"state": "TASK_STATE_COMPLETED"}}
    if answer:
        task["artifacts"] = [{"artifactId": task_id + "-a1", "name": "result", "parts": [{"text": answer}]}]
    else:
        task["status"] = {"state": "TASK_STATE_INPUT_REQUIRED", "message": {
            "messageId": task_id + "-q", "role": "ROLE_AGENT", "taskId": task_id, "contextId": context_id,
            "parts": [{"text": "Celsius to Fahrenheit, or Fahrenheit to Celsius?"}]}}
    TASKS[task_id] = task
    return {"task": task}


METHODS = {"SendMessage": send_message, "GetTask": lambda params: TASKS[params["id"]]}


class Handler(BaseHTTPRequestHandler):
    def respond(self, body):
        data = json.dumps(body).encode()
        self.send_response(200)
        self.send_header("Content-Type", "application/json")
        self.send_header("Content-Length", str(len(data)))
        self.end_headers()
        self.wfile.write(data)

    def do_GET(self):
        if self.path == "/.well-known/agent-card.json":
            self.respond(CARD)

    def do_POST(self):
        request = json.loads(self.rfile.read(int(self.headers["Content-Length"])))
        result = METHODS[request["method"]](request["params"])
        self.respond({"jsonrpc": "2.0", "id": request["id"], "result": result})

    def log_message(self, *args):
        pass


def rpc(method, params):
    body = {"jsonrpc": "2.0", "id": 1, "method": method, "params": params}
    headers = {"Content-Type": "application/json", "A2A-Version": "1.0"}
    with urlopen(Request(BASE + "/", json.dumps(body).encode(), headers)) as response:
        return json.load(response)["result"]


def say(text, **ids):
    return {"message": {"messageId": uuid4().hex, "role": "ROLE_USER", "parts": [{"text": text}], **ids}}


def show(task):
    reply = task["status"].get("message") or task["artifacts"][0]
    print(task["id"], task["contextId"], task["status"]["state"], "|", reply["parts"][0]["text"])


if __name__ == "__main__":
    server = HTTPServer(("127.0.0.1", PORT), Handler)
    threading.Thread(target=server.serve_forever, daemon=True).start()
    card = json.load(urlopen(BASE + "/.well-known/agent-card.json"))
    binding = card["supportedInterfaces"][0]
    print(card["name"], binding["protocolBinding"], binding["protocolVersion"])
    first = rpc("SendMessage", say("Convert 25 degrees"))["task"]
    show(first)
    ids = {"taskId": first["id"], "contextId": first["contextId"]}
    show(rpc("SendMessage", say("celsius to fahrenheit", **ids))["task"])
    show(rpc("GetTask", {"id": first["id"]}))
    show(rpc("SendMessage", say("Convert 100 celsius to fahrenheit", contextId=first["contextId"]))["task"])
    server.shutdown()

Output:

text

task-1 ctx-1 TASK_STATE_COMPLETED | 25 C = 77.0 F

2SendMessage "Convert 25 degrees", no idstask-1, state TASK_STATE_INPUT_REQUIRED, a questionThe server created both ids. The task is paused, not finished
3SendMessage with taskId and contextId from step 2: "celsius to fahrenheit"Same task, TASK_STATE_COMPLETED, artifact "25 C = 77.0 F"Resuming means repeating the ids. Check: 25 x 9/5 + 32 = 45 + 32 = 77

5SendMessage with only contextId: "Convert 100 celsius to fahrenheit"New task-2 in ctx-1, completed, "100 C = 212.0 F"The finished task is not reopened. Check: 100 x 9/5 + 32 = 180 + 32 = 212

A production server would also issue UUIDs for ids, store tasks durably, honour A2A-Version, validate input, return protocol errors, and add the authentication its card declares.

Edge cases and limitations

A version mismatch looks like a missing method
A 1.0 client that sends SendMessage to a 0.3 server, or the reverse, fails with an unknown method or parts the other side cannot read. An absent A2A-Version header means 0.3, and vendor documentation lags: the AWS contract page still shows message/send, and Microsoft keeps a separate preview tool type for 0.3. Read the protocolVersion on every supportedInterfaces entry. The card path is not a reliable signal: the builder's guides place the rename from agent.json to agent-card.json in 0.3, so only older material shows agent.json. A server can list both versions as separate entries, and a gateway can translate between them but not for every operation.
Blocking is the default, so long tasks time out
A client that calls SendMessage without returnImmediately waits until the task finishes or pauses. For work that runs for minutes, a proxy or client timeout can cut the connection while the server keeps working. Set returnImmediately, record the task id from the response, and then poll with GetTask, stream, or register a push webhook.
A finished task cannot be reopened
After a task reaches completed, failed, canceled or rejected, further interaction must start a new task in the same contextId. A client that keeps targeting the old task id gets nowhere. Put the earlier task id in referenceTaskIds so the agent can see what you are refining, and keep your own record of which artifact belongs to which task.
The reply may be a Message or a Task
A server may answer with a plain Message, with a Task, or, on a stream, with events that must follow one of two shapes. A client written only for Task objects breaks on message-only agents. Check which field of the response is present before reading it, and treat a 1.0 stream that mixes shapes as an error.
A signed card proves integrity, not trust
A valid signature shows that the card was not changed since it was signed. It does not tell you whether the organisation behind the key should receive your data or your delegated work. An unsigned card fetched over plain HTTP can be spoofed. Keep credentials and internal detail out of the public card; the specification advises that even an authenticated extended card should not hold sensitive information that could be exploited if leaked.
In-memory task stores lose work on restart
The builder's guide says the default in-memory task store is for samples only. After a restart, GetTask for an old id fails even though the client still holds it. Push webhook registrations kept in memory vanish on deploy while tasks continue, so production servers need a durable task store paired with a durable store for push configurations.

When to use it, and when something simpler is enough

Use it when

  • The other agent is owned and released by a different team, vendor or organisation, and you want a documented contract instead of shared code, as when a third-party agent is plugged into a platform such as Microsoft Foundry.
  • The work is a multi-step job that may run for minutes or hours and may need clarifying questions, credentials or approvals midway, so it needs task state rather than one function call.
  • Agents are written in different languages or frameworks and must interoperate through a standard interface that each side can implement with its own SDK.

Think twice when

  • The capability is a deterministic function with structured inputs and outputs, such as a lookup or a calculation. Expose it as a tool through function calling or an MCP server instead of wrapping it as an agent.
  • Both agents live in one codebase and need shared memory or very low latency. ADK's documentation recommends local sub-agents for in-application organisation, high-frequency calls and shared context.
  • You expect the protocol itself to decide which agents to trust or how to find them at scale. The specification prescribes no standard registry API, and a valid card signature proves integrity, not that the organisation behind it should receive your data.

A simpler alternative. A tool that calls an ordinary HTTP API is often enough when the other system is not an agent; see the Tool Calling and MCP lessons. If the helpers can live in your process, an orchestrator with worker agents is simpler than a network protocol. Move to A2A when the callee is a separately deployed agent that reasons, can run for a long time and may ask questions.

Key takeaways

  • A2A is a wire protocol between opaque agents: a client reads the server's Agent Card, sends messages over JSON-RPC, gRPC or HTTP+JSON, and receives either a Message or a Task in return.
  • A task is the unit of work: the server assigns its id, the contextId groups related work, completed, failed, canceled and rejected are terminal, and input-required or auth-required pause it until the client replies.
  • Results arrive as artifacts, and progress arrives by blocking, polling with GetTask, streaming over SSE or push webhooks, depending on the capability flags in the Agent Card.
  • MCP connects an agent to tools and data while A2A connects an agent to other agents, so real systems often use both at once.
  • Version 1.0 changed the wire format from 0.3, so check protocolVersion on each interface and send the A2A-Version header, because a missing header means 0.3.
  • The card advertises authentication but identity travels in HTTP headers, and a signed card proves integrity rather than trustworthiness, so treat a remote agent's output as untrusted input.

Example 1 of 5

Amazon Bedrock AgentCore Runtime hosting A2A servers

Amazon Web ServicesDocumented in official docs

AWS documents how to deploy an A2A server on Amazon Bedrock AgentCore Runtime in the guide "Deploy A2A servers in AgentCore Runtime" and lists what an A2A container must provide in "A2A protocol contract". The Linux Foundation's April 2026 announcement names AgentCore Runtime as AWS's A2A support. [15][16][11]

The problem

A team has built an agent that speaks A2A, using Strands Agents, LangGraph or Google ADK, and needs to run it as a managed service with isolated sessions per caller, enterprise authentication and scaling. They want this without changing the protocol the agent speaks and without a custom wrapper for each framework.

Where this topic fits

AgentCore Runtime acts as a transparent proxy in front of the container. The A2A server is the same HTTP server it would be anywhere else, listening on port 9000 at the root path with its Agent Card at the well-known path. Discovery and message exchange work as the specification describes; the platform adds authentication (OAuth 2.0 bearer tokens or SigV4) and a session header around them.

How it is applied, step by step

  1. The developer scaffolds a project with the AgentCore CLI using the A2A protocol option. The generated main.py wraps an agent in an A2A executor and starts the server with the SDK's serve_a2a helper.
  2. The server listens on 0.0.0.0:9000 and serves its Agent Card at /.well-known/agent-card.json, plus a /ping health endpoint, as the protocol contract requires.
  3. The command agentcore deploy packages the code, uploads it to Amazon S3, creates a runtime and returns an agent runtime ARN.
  4. A client sends a bearer token and a session id header to the runtime's invocations URL with /.well-known/agent-card.json appended, and receives the card, which carries the URL to use for later calls.
  5. The client then sends JSON-RPC messages to that URL. The platform passes each payload to the container unchanged and returns the container's response.
  6. Platform errors come back as JSON-RPC error bodies with the real HTTP status code, so the client has to parse the body even on 4xx and 5xx responses.

Why this approach fits

An A2A server is an ordinary HTTP server with a small fixed contract: a port, a path, a card location and a health check. A platform can therefore host agents from any framework without understanding their internals. Authentication and session isolation live outside the agent, which matches the protocol's rule that identity travels in HTTP headers rather than inside A2A payloads.

Limitation or tradeoff

Version drift is visible on the page itself. The contract's sample request uses the 0.3-style method name message/send with a kind field, and its sample card lists protocolVersion 0.3.0, while the current specification is 1.0 with different method names and part shapes. Check which version your SDK and card actually use rather than copying a sample. AWS also notes that, unlike what it calls the specification's convention of returning JSON-RPC errors over HTTP 200, the runtime returns the real HTTP status code, so a client that only inspects 200 responses can miss the error.

Where this topic fits

The A2A tool sits inside the Foundry agent's own tool-calling loop. The model decides to call it, Foundry acts as the A2A client using a stored project connection for the endpoint and its credentials, the remote agent does its work, and the reply comes back as the tool result from which the Foundry agent writes its answer.

How it is applied, step by step

  1. An administrator creates a project connection of kind RemoteA2A holding the remote agent's endpoint and an authentication method, such as a key header, OAuth, the project's managed identity or an agent identity, so credentials are stored once and reused across agent versions.

  3. At run time the model chooses to call the tool. The sample forces this by setting tool_choice to required, so a question such as "What can the secondary agent do?" always goes to the remote agent.
  4. Foundry fetches the remote agent's Agent Card, anonymously by default or with credentials when configured, sends the request and receives the remote agent's response.
  5. The Foundry agent uses that response to generate its answer and keeps managing the conversation with the user.
  6. Alternatively the tool can be added through a toolbox that exposes an MCP-compatible endpoint. The agent then attaches the toolbox as an MCP tool, so one agent uses MCP to reach an A2A agent.

Why this approach fits

The remote agent is another reasoning system, so treating it as a tool whose result is text keeps the Foundry agent in charge of the user conversation while it delegates one sub-problem. Atlassian Jira assigning work items to remote agents on a subset of A2A

AtlassianDocumented in official docs

Atlassian's developer guide "Integrate remote agents with Jira" describes how an agent hosted outside Atlassian can be assigned Jira work items, mentioned in comments and chatted with. The guide says Jira's Remote Agent task handling uses concepts from the A2A protocol, that its method schemas are based on a subset of the A2A specification, and that a full A2A implementation is not needed. It targets A2A 1.0 over JSON-RPC. This is therefore a partial application of A2A, not a complete one. [18]

The problem

Software teams want to hand a ticket to an external AI agent and watch it make progress inside Jira. A shared platform cannot practically ship a custom connector for every vendor's agent, and each agent runs on its own infrastructure with its own framework. Work on a ticket can take minutes, may need clarification from the person who assigned it, and ends with a final message that the user can turn into a comment.

Where this topic fits

A subset of A2A is the contract between Jira and the agent's service. A Forge app declares the agent in its manifest and names the JSON-RPC endpoint that Jira will call. Assignment, mentions and follow-ups become SendMessage calls, progress becomes task states that Jira reads with GetTask, and the agent's final message is shown to the user. Discovery differs from the rest of A2A: the agent is registered through the manifest, and the guide text we read does not mention an Agent Card.

How it is applied, step by step

  1. The developer adds a rovo:agentConnector module to the Forge manifest that names the agent, lists Jira as a product context and declares the agent2Agent protocol at version 1.0 with a JSON-RPC endpoint.
  2. When a user assigns a work item or mentions the agent, Jira sends SendMessage. The message carries a text part with the instruction and a data part with structured fields such as the user's account id and the invocation type.
  3. The agent service replies with a task. Because Jira's first message has no contextId, the service must create one and return it.
  4. Jira periodically polls GetTask while a task is in an active or interrupted state, or uses SendStreamingMessage when the manifest declares streaming. The explanatory message in the task status is displayed to the user in Jira.
  5. If the task moves to input-required, the user's reply goes back as another SendMessage that carries the contextId of the existing conversation. A user who cancels causes Jira to send CancelTask.
  6. On completion Jira shows the agent's final message with the option to draft a comment on the work item that shares the outcome.

Why this approach fits

Assigning a ticket is a long-running, stateful delegation, which is what an A2A task models: an id to poll, states for working and waiting for input, and a result. Jira needs only the task and message vocabulary, not knowledge of the agent's framework, so a vendor can take part by implementing the subset that Atlassian lists. Authentication stays at the HTTP layer, through the Forge Invocation Token in the Authorization header.

Limitation or tradeoff

The integration applies only part of A2A, and its limits come from the product as much as from the protocol. Because Atlassian says a full A2A implementation is not required, an agent that satisfies this guide may not be a complete A2A server for other clients. Each context can hold only one active task at a time, a context is private to one user and one agent, and work item text reaches the agent as plain text rather than rich text. The guide also warns against memory shared across a Jira tenant because it would ignore individual permissions. A terminal task cannot restart, so a retry after a failure has to be a new task.

What the sources document

  • Atlassian says Jira's Remote Agent task handling uses concepts from the A2A protocol, that its method schemas and conventions are based on a subset of the A2A specification, and that a full A2A implementation is not needed to integrate an agent. The guide refers to A2A 1.0 task states, and the Forge manifest declares the agent2Agent protocol at version 1.0 with a JSON-RPC transport. [18]
  • Jira calls SendMessage when an assignment, comment mention, workflow, manual trigger or automation rule invokes the agent. MuleSoft gateway policies that govern A2A traffic and bridge versions

MuleSoft's gateway documentation describes two A2A policies. The A2A Agent Card policy rewrites the URL in agent cards so that traffic passes through the gateway, and the A2A v1 to v0.3 transcoder policy converts messages between protocol versions. The current documentation calls the product Omni Gateway. [22][23][8]

The problem

An organisation runs A2A agent backends and wants every client call to pass through an API gateway, so that security and access policies and call metrics apply. An Agent Card tells clients where to send requests, so a card that names the backend lets clients bypass the gateway. Some clients may also speak A2A 1.0 while backends still speak 0.3, and the two wire formats differ.

Where this topic fits

The gateway sits between clients and the agent backend, as it would for any API. The card policy changes what discovery returns, and the transcoder policy changes what flows over the JSON-RPC connection afterwards. Neither changes how the agent itself behaves.

How it is applied, step by step

  1. A backend agent serves an Agent Card whose URL points at the backend's own address.
  2. A client requests the card through the gateway. The Agent Card policy rewrites the URL in the response to the gateway's public endpoint. The policy's Consumer URL setting defaults to the server instance's public endpoint, and its Card Path setting names where the agent presents its card.
  3. The client reads the rewritten card and sends its JSON-RPC requests to the gateway, where the organisation's other policies apply, instead of straight to the backend.
  4. For a 1.0 client in front of a 0.3 backend, the transcoder converts each request on the way in, for example SendMessage to message/send, and each response on the way back, for example the enum value submitted to TASK_STATE_SUBMITTED.
  5. Calls the older protocol cannot express are refused at the gateway: ListTasks and the push notification methods return documented error codes, and REST bindings are not supported.
  6. The card policy also enables a Total Agent Calls metric that counts successful and failed calls to the agent.

Why this approach fits

Because A2A is plain HTTP with a discoverable card, existing gateway tooling can stand in front of agents and apply the same authentication, authorisation and monitoring it applies to other APIs. The A2A documentation recommends API management for externally exposed servers for the same reason. Rewriting the card is the one A2A-specific step, because the card is where a client learns the address.

Limitation or tradeoff

The card policy documents support for A2A 0.3.0 only and is not available in Local Mode. It controls what the card says, not what the network allows, so a client that already knows the backend address can still try it unless network rules block that path. The transcoder handles JSON-RPC only and rejects ListTasks and push notifications, so a 1.0 client loses those features when it talks to a 0.3 backend.

  • The A2A Agent Card policy rewrites the URL in agent card responses to the gateway's public endpoint, so client requests are routed through the gateway, which enforces security and access controls and prevents direct access to backend services. [22]
  • The policy supports A2A protocol version 0.3.0, was first available in gateway version 1.9.3, is not supported in Local Mode, and enables a Total Agent Calls metric. [22]
  • The A2A v1 to v0.3 transcoder translates messages in both directions between A2A 1.0 JSON-RPC clients and 0.3 backends, covering method names, message structures, enumeration values, error formats, agent cards and server-sent events. [23]
  • Through the transcoder, ListTasks returns error -32601 (UNSUPPORTED_METHOD_FOR_V03), the push notification methods return -32003 (PUSH_NOTIFICATION_NOT_SUPPORTED), and only JSON-RPC clients are supported, not REST bindings. [23]

4Common mistakes

  1. Wrapping a plain API or function as an A2A agent

    Why it causes problems
    You add discovery, task state and a second protocol for something that never reasons, asks questions or runs long. Callers must handle tasks and artifacts to get a value that a function call would return directly, and you gain nothing the protocol was designed for.
    How to recognise it
    The "agent" has fixed inputs and outputs, never asks a clarifying question and finishes in one short call, and its Agent Card lists a single skill that is really a function.
    How to fix it
    Expose it as a tool, either as a function in your agent framework or as an MCP server. Use A2A when the callee is an agent that plans, can be interrupted and may take a long time.

  2. Assuming the client library and the server speak the same A2A version

    Why it causes problems
    A 1.0 client calling a 0.3 server, or the reverse, fails with unknown methods, unreadable parts or enum values that do not match. A missing A2A-Version header is read as 0.3, so a careless 1.0 client can end up speaking 0.3 without noticing.
    How to recognise it
    Errors such as "method not found" for SendMessage or message/send, parts that carry a kind field where you expect a text member, or task states written as completed instead of TASK_STATE_COMPLETED.
    How to fix it
    Read protocolVersion on each supportedInterfaces entry, send A2A-Version on every request, test against each server you integrate, and support both formats or put a translating gateway in front while the ecosystem migrates.

  3. Using blocking SendMessage for long-running work

    Why it causes problems
    The request stays open until the task finishes or pauses. A proxy or client timeout then ends the connection while the server keeps working, and users retry and create duplicate tasks.
    How to recognise it
    Gateway timeouts or client errors on long jobs while the server logs show the task still in the working state.
    How to fix it
    Set returnImmediately, store the task id from the response, and then poll with GetTask, stream with SubscribeToTask or register a push webhook. Track which task belongs to which user request so a retry does not start the work twice.

  4. Sending a follow-up to a task that has already finished

    Why it causes problems
    A task in completed, failed, canceled or rejected cannot restart, so a follow-up aimed at its id cannot continue it. The user's refinement is lost or the client keeps showing the old result.
    How to recognise it
    A SendMessage that includes the taskId of a task whose state is terminal, or an agent that keeps returning the previous artifact after the user asked for a change.
    How to fix it
    Check the state first. Resume only interrupted tasks (input-required or auth-required) with the same taskId and contextId. For anything else send a new message with the same contextId and list the earlier task in referenceTaskIds.

  5. Treating the Agent Card or a remote agent's output as trusted

    Why it causes problems
    A spoofed or altered card can redirect your requests, and text returned by a remote agent can contain instructions aimed at your own model. Either can send data out of your system or trigger actions nobody intended.
    How to recognise it
    Cards fetched over plain HTTP or from an unvetted registry, remote output pasted straight into a prompt, and no check of who operates the endpoint or whether the card is signed.
    How to fix it
    Fetch cards over HTTPS, verify signatures when present, decide separately which organisations may receive work, authenticate with the scheme the card declares, and treat remote messages and artifacts as untrusted data in your own agent's context. The Prompt Injection and LLM Security lesson covers the second risk.

  6. Running production on the sample in-memory task and webhook stores

    Why it causes problems
    Task ids and push webhook registrations disappear on restart or redeploy. Clients polling GetTask then get errors for work they were promised, and tasks that are still running never notify anyone.
    How to recognise it
    Tasks vanish after a deploy, or webhooks stop firing while the tasks they belong to are still running.
    How to fix it
    Back the task store with a database, and pair it with a database-backed store for push notification configurations so the two survive restarts together. Decide how long finished tasks are kept.

Add non-blocking SendMessage and polling to the temperature agent

CodingIntermediateAbout 45 min (estimate)Hypothetical scenario

Start from a2a_demo.py in the worked example. Its server always answers SendMessage after the work is done, which is the blocking default. Real agents often need minutes, so extend the demo to support returnImmediately. You need only the Python standard library.

Put your changes in a new file, a2a_async.py, that imports a2a_demo. The pretend work should take one second. Test it with the message "Convert 100 celsius to fahrenheit", which already names a direction so the task never needs input.

Requirements

  • When `params["configuration"]["returnImmediately"]` is true, `SendMessage` returns at once with a task in state `TASK_STATE_WORKING` and no artifacts.
  • About one second later, `GetTask` for the same id returns state `TASK_STATE_COMPLETED` with the artifact "100 C = 212.0 F".
  • Without `returnImmediately`, the server behaves exactly as before.
  • Write a client helper that polls `GetTask` every 0.25 seconds until the state is terminal and returns the final task and the number of polls.

Expected behaviour

The script prints two lines. The first shows the immediate response, immediate: task-1 TASK_STATE_WORKING. The second shows the final result, final: TASK_STATE_COMPLETED 100 C = 212.0 F after 5 polls. The number of polls depends on timing and is usually between 4 and 6.

Hint 1

Reuse the existing `send_message` function to compute the finished task, then replace what you store and return when `returnImmediately` is set.

Hint 2

`threading.Timer(seconds, function, args=...)` runs a function later on another thread. Use it to put the finished task into `TASKS` after the delay.

Hint 3

The handler looks up `METHODS` when each request arrives, so assigning `demo.METHODS["SendMessage"]` swaps the behaviour without editing `a2a_demo.py`.

Show solution

The idea is to compute the finished task as before, then hide it behind a working task until a timer fires.

python
import threading
import time
from http.server import HTTPServer

import a2a_demo as demo

TERMINAL = {"TASK_STATE_COMPLETED", "TASK_STATE_FAILED", "TASK_STATE_CANCELED", "TASK_STATE_REJECTED"}
WORK_SECONDS = 1.0
blocking_send_message = demo.send_message


def send_message(params):
    response = blocking_send_message(params)  # computes and stores the finished task
    if not params.get("configuration", {}).get("returnImmediately"):
        return response
    finished = response["task"]
    working = {key: value for key, value in finished.items() if key != "artifacts"}
    working["status"] = {"state": "TASK_STATE_WORKING"}
    demo.TASKS[finished["id"]] = working
    threading.Timer(WORK_SECONDS, demo.TASKS.__setitem__, args=(finished["id"], finished)).start()
    return {"task": working}


demo.METHODS["SendMessage"] = send_message


def wait_for_terminal(task_id, poll_seconds=0.25):
    polls = 0
    while True:
        task = demo.rpc("GetTask", {"id": task_id})
        polls += 1
        if task["status"]["state"] in TERMINAL:
            return task, polls
        time.sleep(poll_seconds)


if __name__ == "__main__":
    server = HTTPServer(("127.0.0.1", demo.PORT), demo.Handler)
    threading.Thread(target=server.serve_forever, daemon=True).start()
    params = {**demo.say("Convert 100 celsius to fahrenheit"), "configuration": {"returnImmediately": True}}
    first = demo.rpc("SendMessage", params)["task"]
    print("immediate:", first["id"], first["status"]["state"])
    done, polls = wait_for_terminal(first["id"])
    print("final:", done["status"]["state"], done["artifacts"][0]["parts"][0]["text"], "after", polls, "polls")
    server.shutdown()

Run python3 a2a_async.py. Output on Python 3.13 (eight runs gave five polls every time):

text
immediate: task-1 TASK_STATE_WORKING
final: TASK_STATE_COMPLETED 100 C = 212.0 F after 5 polls

The working task is built as a new dictionary rather than by editing the finished one, so the finished task stays intact for the timer to store later. A client that gets TASK_STATE_WORKING back knows only that the work was accepted. It must keep the task id and ask again, which is exactly the situation that streaming and push notifications are designed to improve.

Check your answer

  • Does the first response contain state TASK_STATE_WORKING and no artifacts?
  • Does GetTask return TASK_STATE_COMPLETED with the artifact "100 C = 212.0 F" after about one second?
  • Does a request without returnImmediately still return the completed task immediately?
  • Does your polling loop stop on any of the four terminal states, not only on completed?

States of one booking. TASK_STATE_SUBMITTED, then TASK_STATE_WORKING while fares are searched. The agent asks "aisle or window?" and moves to TASK_STATE_INPUT_REQUIRED. The client shows the question and sends the answer with the same taskId and contextId. The task returns to TASK_STATE_WORKING and ends in TASK_STATE_COMPLETED with the itinerary as an artifact. If the route is unsupported the agent may answer TASK_STATE_REJECTED, on an error TASK_STATE_FAILED, and if the user cancels the client sends CancelTask and expects TASK_STATE_CANCELED. A pause that waits for a person, such as a manager's approval or a missing detail like a cost centre, fits TASK_STATE_INPUT_REQUIRED. The specification describes TASK_STATE_AUTH_REQUIRED as the state for when authentication is needed to proceed, which an approval is not.

Security. First, call only over HTTPS and authenticate with the scheme the card declares, sending the token in the HTTP headers, because A2A payloads do not carry identity. Second, verify every push notification the webhook receives, for example by checking a signed token, and verify the card's signature if it has one. Treat the itinerary text as untrusted input before it enters the assistant's prompt.

Check your answer

  • Did you use a plain tool or MCP for the rates API and the calendar, with a reason based on structure and state?
  • Is your Agent Card valid JSON, and does it list protocolVersion 1.0 in a supportedInterfaces entry?
  • Does your push choice for the mobile app depend on capabilities.pushNotifications being true?
  • Does your state list pause the task for the seat question and resume it with the same taskId and contextId?
