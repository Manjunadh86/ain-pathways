Langflow

Langflow is an open-source tool for building AI applications, such as tool-using agents and retrieval pipelines, on a visual canvas as flows of connected components. A finished flow can be tested in a built-in Playground, called through an API, exposed as an MCP server, and deployed as a service.

1Overview

Why it matters

An agent is more than a model call. It needs instructions, a model, tools, memory, an input channel and an output channel, and those parts must be wired together and then offered to something else: a web page, a script, or another AI application. Langflow draws that wiring on a canvas, so you can see which component feeds which, run the flow, and inspect each step before you write glue code.

It matters most in two situations. When a team prototypes an agent with people who do not write code every day, a shared visual flow is easier to discuss than a repository. And when the prototype works, the same flow can be called over HTTP, offered as tools to MCP clients such as Claude Desktop or Cursor, or packaged in a container, so nothing is rebuilt for the next stage. The cost is that a Langflow server executes code and does not isolate users from each other inside one process, so who may edit flows, which API callers may change which settings, and where the server runs are security decisions, not conveniences.

Key terms

Flow
A saved graph of connected components that represents one application workflow, such as a chat agent. It is stored in Langflow's database and can be exported as a JSON file.
Component
One node in a flow. It has inputs, outputs and parameters, and its behaviour is defined by Python code that inherits from a base Component class.
Port
The connection point on a component's border where an edge attaches. Each port accepts or produces one data type, and the editor colours it by type.
Playground
The chat panel in the editor for testing a flow. For an agent it also shows which tools were used and what each one returned.
Tool Mode
A switch in a component's header menu that offers the component to an Agent as a tool, through a Toolset port that connects to the Agent's Tools port.
Session ID
The label that groups chat messages into one conversation. It defaults to the flow ID, so callers should send their own ID for each conversation.
Tweak
A per-request override of a component parameter, sent in the run request. It applies to that request only and does not change the saved flow.
Project
A folder-like group of flows. In Langflow each project is also an MCP server whose tools are its flows.
Runtime deployment
A backend-only Langflow server that serves finished flows without the editor, in contrast to the IDE deployment used to build them.

2Explanation

Introduction

In What Are AI Agents? an agent was a language model that chooses tools and acts on their results. Writing one in code means assembling the same few parts every time: pick a model, define tools, keep a conversation history, run the agent loop, and put an interface on the front. Langflow lets you assemble those parts on a canvas instead. If you have chained spreadsheet formulas or drawn a data pipeline, the idea is familiar: boxes with inputs and outputs, joined by lines that carry values.

In Langflow the boxes are components, the lines are edges attached at ports, and the whole diagram is a flow. A Chat Input component receives the user's message, an Agent component calls a language model and decides whether to use tools, and a Chat Output component shows the answer. Each component is Python code underneath, so you can open it, change it, or write your own. The Langflow site (opens in a new tab) calls it a low-code AI builder for agentic and RAG applications and a tool to build and deploy AI agents and MCP servers, and it ships as an open-source Python package.

The diagram below is the flow that the Langflow quickstart builds from its Simple Agent template. Notice that the two tools are not steps in a sequence. Both attach to the Agent's Tools port, and on every question the agent decides which tool, if any, to call.

A flow that works in the editor is still only a prototype until something else can call it. This lesson follows that path: how a flow is built and run, how the Agent component and its tools work, how a program calls a flow through the API, how a project becomes an MCP server for clients such as Claude Desktop and Cursor, and which deployment options and security settings decide whether the result is safe to share. It follows the documentation for Langflow 1.12.x, current in October 2026, and names the version wherever a default matters.

How it works

Flows, components and ports

A flow is a functional representation of an application workflow. You build it in the workspace by dragging components onto the canvas and joining them with edges. Each component has inputs, outputs, parameters and controls. An edge attaches at a port, the circle on a component's border, and a port accepts or produces one data type. The editor colours ports by type: the components page lists, for example, indigo for Message, fuchsia for LanguageModel, cyan for Tool, orange for Memory, red for JSON and pink for Table (Components (opens in a new tab)). In Python, component results are typed objects such as Message (chat text with sender and session details), Data (a JSON-like record) and DataFrame (a table), as the custom components page (opens in a new tab) shows.

When you run a flow, Langflow builds a directed acyclic graph from the components and edges and executes the components in dependency order, passing each result to the components that need it (Flows (opens in a new tab)). An agent's repeated tool calls therefore happen inside the Agent component, not as a cycle you draw. Every component is Python: select it and choose Code to read the class, which inherits from a base Component class.

Testing in the Playground

The Playground is the editor's chat panel and needs a Chat Input component to receive prompts. For a flow with an Agent it prints the tools the agent used and the output of each, which is how you check that the right tool ran (Playground (opens in a new tab)). Messages are grouped by a session ID. By default the session ID is the flow ID, so everything lands in one long conversation until you set another ID in Chat Input or send session_id through the API. The documented 1.12.x Playground also asks you to approve or reject a tool call when a flow pauses for human approval; see Human-in-the-Loop.

The Agent component

The Agent component is the reasoning step of most agent flows. It sends the instructions, the session history, the user's message and the descriptions of its tools to a language model, runs the tools the model asks for, and returns the final answer. That is the agent loop packaged as one component. In the v1.12.0 source (opens in a new tab) it is built with LangChain's create_agent, and its main fields are:

The latest 1.12.x patch release when this lesson was reviewed, v1.12.5 (opens in a new tab), has the same defaults.

The component has two outputs: response, a chat Message with the final answer, and structured_response, a Data object that follows output_schema when you define one. max_iterations is your step limit, so set it a little above what successful runs need, as the loop lesson explains.

Tools

Any component can become a tool. Open its header menu and enable Tool Mode; the component then has a Toolset port, which you connect to the Agent's Tools port. The agent chooses among tools using each tool's description, which tells it what the tool can do (Agents (opens in a new tab)). The Tools port also accepts another Agent component, so one agent can be a tool of another, and accepts MCP servers through the MCP Tools component. In your own components you mark the inputs the model may fill with tool_mode=True (Custom components (opens in a new tab)). Writing a good description is the craft covered in Designing Tools for Agents.

Running a flow from code

Every flow can be called over HTTP. The Share menu's API access pane generates Python, JavaScript and curl snippets for your flow. The run endpoint requires a Langflow API key, sent in an x-api-key header (the reference also allows a query parameter). A request to POST /api/v1/run/FLOW_ID takes a JSON body (Run flow (opens in a new tab)):

FieldMeaning
input_valueThe message text.
input_type, output_typechat or text for input; chat, any or debug for output. Both default to chat.
session_idWhich conversation the message belongs to; send one per user conversation.
tweaksPer-request overrides of component parameters, keyed by component ID. They apply to that request only.

Adding ?stream=true returns tokens as they are generated, closed by an end event.

Flows as MCP servers, and Langflow as an MCP client

Each Langflow project is also an MCP server whose tools are the project's flows. A flow needs a Chat Output component to qualify. The server answers at /api/v1/mcp/project/PROJECT_ID/streamable, uses streamable HTTP by default with SSE as a fallback, and can require an API key or OAuth. The client's model picks a tool from its name and description, and the defaults are the flow's UUID, so edit them (MCP server (opens in a new tab)). In the other direction, the MCP Tools component connects to an external MCP server so that an Agent can call its tools. See Model Context Protocol for the protocol itself.

Deployment options and the settings that matter

The same flow runs in every option above. What changes is who can reach it and how much state it shares. For anything others can reach, review these settings first (Docker (opens in a new tab), API keys and authentication (opens in a new tab), production practices (opens in a new tab), tweaks policy (opens in a new tab), blocking custom components (opens in a new tab)):

SettingWhy it matters
LANGFLOW_AUTO_LOGIN=false and LANGFLOW_SUPERUSER_PASSWORDRequire sign-in; the password is required unless auto-login is on.
LANGFLOW_SECRET_KEYThe encryption secret. The authentication page advises setting your own key in production so that multi-instance deployments encrypt consistently, and the prod profile requires a usable Fernet key.
LANGFLOW_DATABASE_URLPoints at the database; use PostgreSQL when several instances share state.
LANGFLOW_DEPLOYMENT_PROFILE=prodRuns boot-time checks and refuses to start if one fails. The required checks cover PostgreSQL, external file storage, a usable secret key and a pgVector connection.
LANGFLOW_TWEAKS_POLICYLimits what API callers may override: declared allows only fields marked API, off allows only the message and session ID.
LANGFLOW_ALLOW_CUSTOM_COMPONENTS=falseBlocks creating custom components, editing component code and running built-in code-execution components (a beta feature).

Langflow's security page (opens in a new tab) states that it does not enforce isolation between users within a single process, nor restrict access to local disk or network resources. If you serve several tenants you provide that isolation yourself, and you treat custom components and LLM-generated code as code that runs on your server.

Worked example: Call the Simple Agent over HTTP and hold a two-turn conversation

This example runs the quickstart's Simple Agent from a Python script and shows what a session ID does. You need Python 3.10 to 3.14, uv, and an API key for any model provider that supports tool calling (a local model also works; see the first exercise).

Step 1. Start Langflow. Install it and start the server (installation (opens in a new tab)), then open http://127.0.0.1:7860.

bash
uv venv langflow-env
source langflow-env/bin/activate
uv pip install langflow
uv run langflow run

Step 2. Build and test the flow. In the editor choose New Flow, then the Simple Agent template (quickstart (opens in a new tab)). In the Agent component click Setup Provider, add your key under Settings, Model Providers, and pick a model. Open the Playground and ask "I want to add 4 and 4"; you should see the Calculator tool used.

Step 3. Create an API key. Click your user icon, then Settings, Langflow API Keys, Add New. Export it as LANGFLOW_API_KEY. The flow ID is in the snippet that the Share menu's API access pane generates; export it as FLOW_ID.

Step 4. Send the first question with curl.

bash
curl -X POST "http://127.0.0.1:7860/api/v1/run/$FLOW_ID" \
  -H "Content-Type: application/json" \
  -H "x-api-key: $LANGFLOW_API_KEY" \
  -d '{"input_value": "What is 17 * 23?", "input_type": "chat", "output_type": "chat", "session_id": "demo-session-1"}'

The response is a large JSON document. The reference page shows the reply at outputs[0].outputs[0].results.message.text, while the quickstart's script reads it from outputs[0].outputs[0].outputs.message.message. The quickstart's full sample response (dated June 2025) holds the text under both of those and under results.message.data.text. Because the shape may differ between versions and settings, the client below tries all three paths and fails loudly if none matches.

Step 5. Run a client that keeps one session. Save as client.py (standard library only):

python
import json
import os
import sys
import urllib.error
import urllib.request

BASE_URL = os.environ.get("LANGFLOW_SERVER_URL", "http://localhost:7860").rstrip("/")
API_KEY = os.environ["LANGFLOW_API_KEY"]
FLOW_ID = os.environ["FLOW_ID"]

MESSAGE_PATHS = (  # where the reply text can sit inside one component output
    ("outputs", "message", "message"),
    ("results", "message", "text"),
    ("results", "message", "data", "text"),
)


def run_flow(question, session_id):
    payload = {"input_value": question, "input_type": "chat",
               "output_type": "chat", "session_id": session_id}
    request = urllib.request.Request(
        f"{BASE_URL}/api/v1/run/{FLOW_ID}",
        data=json.dumps(payload).encode("utf-8"),
        method="POST",
        headers={"Content-Type": "application/json", "x-api-key": API_KEY},
    )
    try:
        with urllib.request.urlopen(request, timeout=120) as response:
            return json.load(response)
    except urllib.error.HTTPError as error:
        detail = error.read().decode("utf-8", errors="replace")[:300]
        raise RuntimeError(f"Langflow returned HTTP {error.code}: {detail}") from error


def message_text(result):
    output = result["outputs"][0]["outputs"][0]
    for path in MESSAGE_PATHS:
        node = output
        for key in path:
            if not isinstance(node, dict) or key not in node:
                break
            node = node[key]
        else:
            return node
    raise KeyError("no chat message at any known path; print the response and adjust MESSAGE_PATHS")


if __name__ == "__main__":
    session = sys.argv[1] if len(sys.argv) > 1 else "demo-session-1"
    for question in ("What is 17 * 23?", "Now add 9 to that."):
        print(f"[{session}] {question}")
        print(message_text(run_flow(question, session)))

Run python client.py demo-session-1. The model's wording will differ, but the numbers should not:

text
[demo-session-1] What is 17 * 23?
17 * 23 = 391
[demo-session-1] Now add 9 to that.
391 + 9 = 400

Step 6. Read what happened. The counts below are what we expect from a tool-calling model with default settings; check them in the Playground or your provider's usage log.

RequestSessionHistory the Agent loadsModel callsTool callReply contains
"What is 17 * 23?"demo-session-1none2 (tool request, final answer)Calculator: 17 * 23391
"Now add 9 to that."demo-session-1request 1 and its reply2Calculator: 391 + 9400
"Now add 9 to that."demo-session-3none1 or morenone expecteda request for clarification

Run python client.py demo-session-2 to reproduce the first two rows in a new session, then edit the script to send only the second question with demo-session-3. The agent has no earlier messages for that session, so it cannot know what "that" means. The conversation lives in the session, not in the script.

Step 7. Try a tweak. Add this field to the request body to change the Agent's instructions for one call only, replacing Agent-ZOknz with your Agent's component ID from the API access pane. With the default permissive tweaks policy the field does not have to be marked API first:

json
"tweaks": {"Agent-ZOknz": {"system_prompt": "Answer in one short sentence."}}

Open the flow afterwards: the saved instructions are unchanged. Each request carries its own overrides.

Finally, a step-limit check using the Agent field table earlier in this lesson. With max_iterations at 15, a run that needs nnn rounds of tool use makes n+1n + 1n+1 model calls (one per tool request, plus the final answer). If the cap permits exactly 15 calls, n+1≤15n + 1 \le 15n+1≤15 allows at most 14 rounds. The two requests above used 1 round each, far inside the cap.

Edge cases and limitations

The reply sits at different paths in different documentation pages
The quickstart's script reads the reply from outputs[0].outputs[0].outputs.message.message, while the run-endpoint reference shows it under results.message.text. The quickstart's full sample response, dated June 2025, contains the text under both of those and under results.message.data.text, and neither page says which versions or settings change the shape. Confirm the shape against your own server: print one raw response, and extract with a function that raises a clear error when no known path matches, as the worked example does.
Callers that omit session_id share one conversation
The default session ID is the flow ID, so every caller that sends no session_id appends to the same history, and the Agent loads up to n_messages (100 by default in v1.12.0) of it. In a multi-user application one user's questions then appear in another user's context. Send a distinct session_id for each user or conversation.
max_iterations counts model calls, not tool calls
In the v1.12.0 source, max_iterations (default 15) is passed to LangChain's ModelCallLimitMiddleware as run_limit, so it caps model calls. A run with n rounds of tool use needs n + 1 model calls. The component also derives a LangGraph recursion limit from it, so that the model-call cap rather than a raw recursion error ends the run; v1.12.0 uses run_limit * 2 + 5 (35 by default) and v1.12.5 uses run_limit * 4 + 10 (70 by default, with one more step per cycle when a tool needs approval). That internal formula changed between patch releases, so do not depend on it. Test what your callers receive when the cap is reached, because the component passes only run_limit to the middleware.
The default tweaks policy lets API callers change almost any field
With LANGFLOW_TWEAKS_POLICY at its default of permissive, a caller with a valid API key can override nearly any component field except code fields and privileged settings, not only the fields marked as API. For a flow exposed to other teams or the public, use declared, which allows only fields marked API, or off, which allows only input_value and session_id. A refused tweak returns HTTP 422. One catch: under declared, a flow that marks no field as API behaves like permissive, so mark the fields you want callers to set before you rely on it.
One Langflow process does not isolate its users
The security page says Langflow does not enforce isolation between users in a single process and does not restrict disk or network access, and flows can run custom Python. Serving several customers from one server therefore needs isolation at process, disk, network and database level that you provide, for example one deployment per tenant, plus blocking custom components in deployments that never need them.

When to use it, and when something simpler is enough

Use it when

  • You are prototyping an agent or retrieval pipeline and want to see, run and share the wiring, including with people who do not write code every day.
  • You want one artifact, the flow, that can be tested in a chat panel and then served as an HTTP endpoint, an MCP tool or a container without being rebuilt.
  • Most of what you need is composition of existing integrations (models, vector stores, web fetching, MCP servers), with Python custom components for the gaps.

Think twice when

  • You must serve mutually untrusted tenants from one process or let end users edit flows, because Langflow itself provides no per-user isolation.
  • Your agent needs unit tests, code review of every change and fine control over state and branching; a flow stored as JSON is awkward to review and diff.
  • The task is a single model call with no tools, where an API call from your own code is shorter and clearer.

A simpler alternative. A short script that calls a model API with tool calling is often enough for one agent and is easy to test and review. Move to Langflow when the visual wiring, the built-in Playground or the ready-made API and MCP serving save real time, and move to a code framework (see Choosing an Agent Framework) when you need tests, review and precise control over state.

Key takeaways

  • A flow is a graph of typed components that runs in dependency order, and the Agent component packages the model calls, tool calls and step limit of the agent loop.
  • Any component becomes a tool through Tool Mode, and the agent chooses among tools by their descriptions, so a vague description leads to wrong choices.
  • One flow can be served by the run API, an embedded widget, an OpenAI-style endpoint or an MCP server, and the session_id decides whose conversation a call continues.
  • Build in the IDE and serve from a backend-only runtime, with auto-login off, a fixed secret key, PostgreSQL and an API key on every endpoint.
  • Langflow does not isolate users inside one process, and tweaks and custom components change what a flow does, so restrict them before a server is shared.

Example 1 of 5

The Simple Agent template from the Langflow quickstart

LangflowDocumented in official docs

The Langflow quickstart builds a working agent from the Simple Agent template, the Agents page explains how tools are attached and chosen, and the Agent component's v1.12.0 source shows how it runs and when it stops. [11][5][6][12][13]

The problem

Some questions cannot be answered well by a model alone: arithmetic that must be exact, and questions that depend on the current text of a web page. The quickstart's flow gives the model two tools, a calculator and a URL fetcher, and lets it decide for each question which one to use, so a single flow handles both kinds of request.

Where this topic fits

The Agent component sits between Chat Input and Chat Output. The Calculator and URL components attach to its Tools port, and the language model is a setting on the Agent itself. Before the Agent comes the user's message; after it, Chat Output shows the final answer and the Playground lists the tools that were used.

How it is applied, step by step

  1. Choose New Flow and the Simple Agent template. It contains an Agent, Chat Input, Chat Output, a Calculator and a URL component.
  2. In the Agent component click Setup Provider, add the provider's API key under Settings, Model Providers, and select a model.
  3. Send a message in the Playground. The Agent sends its instructions, the session history, the message and the descriptions of its tools to the model.
  4. If the model asks for a tool, Langflow runs that component and returns its output to the model. The cycle repeats until the model answers or max_iterations model calls have been used.
  5. Chat Output shows the response, and the Playground lists which tools ran and what each returned.
  6. To add a tool of your own, write a custom component whose input has tool_mode=True, enable Tool Mode on it, and connect its Toolset port to the Agent.

Why this approach fits

The two tools are specialised, cheap to describe in a sentence each, and independent of each other, so a model choosing between them is enough and no fixed sequence of steps is needed: the question decides the path. Visual wiring also makes the next tool a small change, since you add a component, enable Tool Mode and connect one port.

Limitation or tradeoff

The agent chooses only from the tool descriptions, so vague or overlapping tools lead to wrong choices. A URL tool puts fetched page text into the model's context, which is a route for prompt injection. The iteration cap bounds cost and runaway loops, but it does not make an answer correct.

What the sources document

  • The quickstart's Simple Agent template contains an Agent component, Chat Input and Chat Output components, a Calculator component and a URL component. In the Playground, a request to add 4 and 4 is meant to trigger the Calculator and a current-events question to trigger the URL tool. [11]
  • Components become tools by enabling Tool Mode, which creates a Toolset port that connects to the Agent's Tools port. The tool's description tells the agent what the tool can do so that it can decide whether the tool suits the request. [5]
  • In the v1.12.0 source the Agent component is built with langchain.agents.create_agent, and its Max Iterations input, default 15, is described as the maximum number of model calls the agent can make before stopping. [6]
  • A custom component inherits from the Component class, lists its inputs and outputs, and each Output names the method that produces it. Setting tool_mode=True on an input makes it usable when the component serves as a tool for an Agent. [12]
  • Langflow's own Text Input component, marked legacy in v1.12.0 with Chat Input as its replacement, imports Output from lfx.io and Message from lfx.schema.message, and the method named in its Output returns a Message built with text=. [13]

The facts above come from the cited sources. The steps and analysis in this example are our explanation of how they fit together.

Example 2 of 5

Serving one flow to a script, a website and OpenAI-style client code

LangflowDocumented in official docs

Langflow's page on triggering flows documents how a finished flow is called by other software, and the OpenAI Python library README documents the client that Langflow's OpenAI Responses compatible endpoint is designed to work with. [14][7][15][16][17]

The problem

An existing front end or backend already talks to an AI service with chat-style requests, and the team wants the logic behind it to be a flow they can edit visually, without rewriting the callers. Different callers need different entry points: a script wants a plain HTTP endpoint with conversation handling, a web page wants a drop-in chat box, and code written for the OpenAI client wants an OpenAI-shaped endpoint.

Where this topic fits

After the flow works in the Playground, the documentation offers four ways to reach it from outside: the Langflow API (with generated snippets), an embedded chat widget, an MCP server and an OpenAI Responses compatible endpoint. The flow does not change between them. Only the way a request arrives, and how the conversation is identified (a session_id, or previous_response_id on the Responses endpoint), differs.

How it is applied, step by step

  1. Build the flow with Chat Input and Chat Output components. The widget needs both, and the Responses endpoint needs Chat Input.
  2. Create a Langflow API key and keep it where server-side code can read it, for example an environment variable.
  3. For a script or backend, call POST /api/v1/run/FLOW_ID with input_value and a session_id that identifies the conversation.
  4. For a website, add the langflow-chat web component with the HTTPS host URL, the flow ID and an API key, and optionally pass a session_id to separate visitors.
  5. For code written against the OpenAI Python client, point base_url at the Langflow server's /api/v1/ path, send the Langflow key in an x-api-key header, and pass the flow ID or endpoint name as the model.
  6. Decide what callers may change by setting LANGFLOW_TWEAKS_POLICY to declared or off for flows that other teams or the public can reach.

Why this approach fits

Callers keep their existing code or a few lines of HTML, while the model, tools and prompts behind the entry point are changed in the editor without redeploying them. A per-conversation session_id (or previous_response_id on the Responses endpoint) keeps visitors' histories apart, and the tweaks policy gives the flow owner a say in what callers may override.

Limitation or tradeoff

The Responses endpoint does not support the tools parameter, because tools belong to the flow, and it expects the Langflow key in x-api-key rather than a Bearer token. A chat widget on a public page needs a key the browser can read, so use a key you can revoke or put a backend in between. The default permissive tweaks policy lets key holders override almost any field.

What the sources document

  • The page lists four ways to run a flow from an application: the Langflow API, with Python, JavaScript and curl snippets from Share, API access; an embedded chat widget from Share, Embed into site; a Langflow MCP server; and an OpenAI Responses compatible endpoint. The widget needs Chat Input and Chat Output components and, as minimum props, an HTTPS host_url, the flow_id and an api_key. [14]
  • The run endpoint is POST /api/v1/run/FLOW_ID with an x-api-key header, and its JSON body accepts input_value, input_type, output_type, session_id and tweaks. [7]
  • POST /api/v1/responses takes the flow ID or endpoint name as model plus input, requires a Chat Input component, does not support the tools parameter, and authenticates with x-api-key rather than a Bearer token. The page shows the OpenAI Python client with base_url and default_headers set for it. [15]
  • The OpenAI Python library README shows the Responses API call client.responses.create with model and input, reading the answer from response.output_text, and shows that the base URL can be customised with the base_url parameter or the OPENAI_BASE_URL environment variable. [16]

Offering flows as MCP tools to Claude Desktop, Cursor and other clients

LangflowDocumented in official docs

Langflow's MCP server page documents how a project's flows become MCP tools, its MCP client page documents the reverse direction, and the Model Context Protocol site documents how a client such as Claude Desktop registers a server. [8][18][19]

The problem

A team wants an assistant it already uses, such as a desktop chat app or a code editor, to call a workflow it built, without writing a separate integration for each assistant. MCP is the shared protocol for this, and the Langflow documentation turns each project into an MCP server so that no integration code is needed on the Langflow side.

Where this topic fits

The flow sits behind the project's MCP endpoint. The MCP client lists the project's tools, its own model picks one by name and description, and Langflow runs the matching flow and returns the Chat Output result. The reverse direction also exists: the MCP Tools component lets a Langflow agent call tools of an external MCP server.

How it is applied, step by step

  1. Put the flow in a project and make sure it contains a Chat Output component, which the documentation requires for a flow to work as an MCP tool.
  2. Open the project's MCP Server tab, choose an authentication method (API key, OAuth or none), and use Edit Tools to give each flow a descriptive name and description.
  3. Take the endpoint, which ends in /api/v1/mcp/project/PROJECT_ID/streamable, or use the auto install option for the clients that support it (Cursor, Claude and Windsurf).
  4. For a client configured with an mcpServers JSON entry, run the endpoint through uvx mcp-proxy with the streamablehttp transport, adding the API key as a header if the project requires one.
  5. Restart the client. It lists the project's tools, and its model calls them when a request matches a name and description.
  6. To go the other way, register an external server (for example the STDIO command uvx mcp-server-fetch) under Settings, MCP Servers, drag it onto the canvas as an MCP Tools component, enable Tool Mode and connect its Toolset port to an Agent.

Why this approach fits

The integration is written once, on the server, and every MCP client gets it. The client keeps its own interface and decides when to call a tool, while Langflow keeps the flow, its credentials and its logic, so a change to the flow reaches every client without touching their configuration.

Limitation or tradeoff

Which tool a client calls depends only on names and descriptions, and the defaults are UUIDs that tell the model nothing. An endpoint with no authentication is open to anyone who can reach it, along with the model keys and data sources the flow uses. Clients that speak only stdio need a proxy such as mcp-proxy, which adds a process to run and maintain.

What the sources document

  • Each Langflow project can serve as an MCP server whose tools are its flows, and a flow needs a Chat Output component to be used as a tool. Default tool names use the flow ID, and the page warns that unclear names and descriptions can make the agent choose tools incorrectly. [8]
  • The project endpoint follows /api/v1/mcp/project/PROJECT_ID/streamable on a default server address of http://localhost:7860, and Langflow supports streamable HTTP by default with Server-Sent Events as a fallback. [8]
  • Authentication can be an API key, OAuth or none, where none creates a public endpoint. The page shows a client configuration that runs uvx mcp-proxy with --transport streamablehttp and an optional --headers x-api-key argument. [8]
  • Langflow acts as an MCP client through the MCP Tools component, which connects to a server so that an Agent can use its tools. A server can be registered over STDIO (for example uvx mcp-server-fetch), HTTP/SSE, or by pasting JSON, and Tool Mode exposes it to the Agent. [18]
  • Claude Desktop reads an mcpServers object with command and args from claude_desktop_config.json, opened through Settings, Developer, Edit Config, and must be fully restarted to load the change. [19]

Running exported flows as a production service on Docker and Kubernetes

LangflowDocumented in official docs

The Langflow Docker page, its Kubernetes production page and its production best-practices page document how a flow built in the editor is packaged and served, and the flow import and export page documents the JSON file that carries it. [20][21][22][23][24]

The problem

A flow that works in the editor must become a stable service. Every environment has to run the same flow definition, the editor should not sit in the path of production traffic, several replicas must share state, and a misconfigured server should refuse to start instead of failing later in front of users.

Where this topic fits

Deployment comes after the flow is built and tested in the IDE. The flow is exported as JSON, packaged into an image or downloaded at start-up, and served by a backend-only runtime that applications reach through the run API or an MCP endpoint, as in the earlier examples.

How it is applied, step by step

  1. Export the flow as JSON from the editor. Keep model keys in global variables so that the file holds variable names, not secret values.
  2. Build an image from langflowai/langflow that copies the JSON into /app/flows and sets LANGFLOW_LOAD_FLOWS_PATH, then test it on port 7860 and call the run endpoint.
  3. Install the langflow-runtime Helm chart with the image repository and tag, or point downloadFlows at a flow URL, and set the replica count and resource requests. The documentation example uses 3 replicas.
  4. Store provider keys in a Kubernetes secret and reference it through extraEnv instead of baking it into the image.
  5. Set LANGFLOW_DEPLOYMENT_PROFILE=prod so that the server refuses to start without PostgreSQL, external object storage, a usable secret key and a pgVector connection, and set LANGFLOW_ALLOW_CUSTOM_COMPONENTS=false where nobody needs to edit code.
  6. Keep the langflow-ide chart for editing. Roll out each flow change as a new image tag and let applications call only the runtime service.

Why this approach fits

The image carries the flow definition, so staging and production run the same thing. The runtime chart is backend-only, so the editor is not exposed to production traffic, and its replicas can be scaled without touching the development environment. The prod profile turns configuration mistakes into start-up failures, which is where they are cheapest to find.

Limitation or tradeoff

Flows baked into an image change only through a new build and rollout. Several replicas need shared state, and the production page warns that the default in-memory cache and in-process job queue are not shared and prefers Redis for both. The prod profile also demands PostgreSQL, external object storage and a pgVector connection, which is more infrastructure than a laptop needs. Langflow still does not isolate tenants, so each customer needs its own deployment.

What the sources document

  • The official image is langflowai/langflow and serves on port 7860. A custom image can embed flows by copying JSON files into /app/flows and setting LANGFLOW_LOAD_FLOWS_PATH. As of Langflow 1.11.x the official images set auto-login off, and LANGFLOW_SUPERUSER_PASSWORD is then required unless auto-login is enabled. [20]
  • The langflow-runtime Helm chart is described as tailored for production, with stability, performance, isolation and security as its focus, and it installs with image.repository and image.tag or with flows downloaded from URLs. The best-practices page describes Runtime as a backend-only headless service and recommends 3 replicas with at least 2Gi of memory and 1 CPU each. [21][22]
  • With LANGFLOW_DEPLOYMENT_PROFILE=prod, boot-time preflight checks require a reachable PostgreSQL database, an external object store, a usable LANGFLOW_SECRET_KEY and a pgVector connection with the vector extension installed, and a failed check aborts boot with a non-zero exit. [22]
  • Setting LANGFLOW_ALLOW_CUSTOM_COMPONENTS to false blocks creating custom components, changing code in the visual editor and running built-in code-execution components, and Langflow runs the server's own component templates instead of code stored in a flow. The page calls this a beta feature and advises also running Langflow in an isolated, containerized environment when it handles untrusted or LLM-generated code. [23]
  • An exported flow is a JSON file of nodes, edges and metadata. When keys are saved with it, a literal key typed into a field is exported as-is, while a key held in a global variable is exported by name only, so the importing server needs a matching variable. [24]

Tracing Langflow runs in Langfuse

LangfuseDocumented in official docs

Langflow's documentation describes its Langfuse integration from the Langflow side, and Langfuse's documentation describes the same integration from the Langfuse side. [25][26]

The problem

After flows serve real users, someone has to be able to see what a particular run did: which model and tool calls happened, in what order, with what inputs and outputs. The Playground shows only chats you run yourself in the editor, and the API response is built for the caller, not for reviewing many runs afterwards.

Where this topic fits

Outside the flow. Tracing is switched on by environment variables on the Langflow server, so nothing is added to the canvas. Runs from the Playground and from the API both produce traces that appear in Langfuse.

How it is applied, step by step

  1. Create API keys in Langfuse Cloud or in a self-hosted Langfuse.
  2. Put LANGFUSE_SECRET_KEY, LANGFUSE_PUBLIC_KEY and the Langfuse host URL in the .env file that the Langflow server reads.
  3. Start Langflow with uv run langflow run --env-file .env.
  4. Run a flow from the Playground or the API. According to the documentation, tracing then happens without any further setup.
  5. Open the trace in Langfuse and walk through the recorded steps to find the one that produced a wrong or slow result.
  6. To turn tracing off, remove the variables and restart the server.

Why this approach fits

Because tracing is configured on the server, every flow on it is traced the same way, including flows imported from other people, and authors do not have to remember to add anything. The traces live in Langfuse rather than in Langflow's own database, so the history survives a redeploy of the Langflow server.

Limitation or tradeoff

Traces of agent runs typically include prompts, tool arguments and model outputs, so sending them to a hosted service is a data-protection decision (see Data Privacy and Compliance). The two pages name the host variable differently, so check which one your Langflow version reads. A trace shows what happened, not whether it was right; judging quality is a separate task, covered in LLM and Agent Observability and Langfuse.

What the sources document

  • Langflow's page says to set LANGFUSE_SECRET_KEY, LANGFUSE_PUBLIC_KEY and LANGFUSE_BASE_URL in a .env file and start Langflow with uv run langflow run --env-file .env. Tracing then happens automatically, and removing the variables and restarting disables it. [25]
  • The older LANGFUSE_HOST variable is still supported for backward compatibility, but Langflow's page prefers LANGFUSE_BASE_URL. [25]
  • Langfuse's page lists LANGFUSE_SECRET_KEY, LANGFUSE_PUBLIC_KEY and LANGFUSE_HOST, says that using Langflow's chat or API lets you view the trace of your conversations in Langfuse, and describes the integration as native since Langflow v1.0.17. [26]

4Common mistakes

  1. Calling the run endpoint without a session_id from a multi-user application

    Why it causes problems
    The default session ID is the flow ID, so every caller shares one conversation. The Agent loads earlier messages from that session, so one user's questions and data can appear in another user's answers.
    How to recognise it
    The agent refers to things the current user never said, or two test users see each other's context. Look at the stored messages for the flow: if there is only one session ID, it is the flow ID.
    How to fix it
    Send a session_id for every user or conversation, for example a user ID plus a conversation ID, and send the same value on every turn of that conversation.

  2. Leaving the laptop defaults on a server that other people can reach

    Why it causes problems
    Auto-login, the permissive tweaks policy and editable custom components are convenient locally. On a shared server they let anyone with a key override nearly any field of a flow, and anyone who can edit a flow run Python on the host.
    How to recognise it
    A request carrying an unexpected tweak, such as a different system_prompt, succeeds. The editor opens without a login. Component code can be edited in the editor of the production server.
    How to fix it
    Set LANGFLOW_AUTO_LOGIN=false with a superuser password, set LANGFLOW_TWEAKS_POLICY to declared or off, serve production traffic from a runtime deployment, and set LANGFLOW_ALLOW_CUSTOM_COMPONENTS=false where nobody needs to edit code.

  3. Exporting flows with API keys typed into component fields and committing the JSON

    Why it causes problems
    When keys are saved with an export, a key typed directly into a field is written into the JSON as-is. A committed or shared file then leaks the key, and revoking it breaks every copy of the flow.
    How to recognise it
    Search the exported JSON for provider key prefixes or long random strings inside component fields. A leaked key often shows up as unexpected usage on the provider's dashboard.
    How to fix it
    Store keys as global variables so that exports contain only the variable name, export without keys when sharing a flow, and rotate any key that has appeared in a file.

  4. Exposing a flow as an MCP tool with its default UUID name and no description

    Why it causes problems
    The client's model chooses tools by name and description. A UUID gives it nothing to match, so it calls the wrong flow or never calls the right one, and the failure looks like a model problem.
    How to recognise it
    The client lists tools whose names are UUIDs. A prompt that names the tool explicitly works, while the natural phrasing of the request does not.
    How to fix it
    In the project's MCP Server tab, use Edit Tools to give each flow a descriptive name such as document_qa_for_resume and a description that says what it takes and what it returns.

  5. Treating the Playground or the Shareable Playground as the production front end

    Why it causes problems
    The documentation says the Shareable Playground is for testing purposes only and that the Playground isn't meant for embedding flows in applications, and Langflow Desktop does not include the Shareable Playground at all. A demo link becomes a dependency nobody supports.
    How to recognise it
    Real users reach the flow through a link into the editor, or the plan for a customer-facing page is to embed the Shareable Playground.
    How to fix it
    Serve users through the run API, the embedded chat widget or your own front end, and keep the editor on a separate development deployment.

Exercise 1

Give a Langflow agent a custom tool and call it through the API

Hands-onIntermediateAbout 1 h 15 min (estimate)Hypothetical scenario

You will extend the Simple Agent flow with a tool of your own and call the result from outside Langflow. The scenario is invented for practice: a small shop needs an agent that totals orders correctly.

Setup. Install and start Langflow as in the worked example. You need a chat model that supports tool calling. A hosted provider key works; so does a local model served by Ollama, which costs nothing, if you choose it in the Agent component.

Task. Add a custom component called Order Total that takes comma-separated prices and returns the subtotal, the 8% sales tax rounded half up to the cent, and the total. For the prices 19.99, 5.50, 42.00 it must return exactly Subtotal 67.49, tax 5.40, total 72.89. Enable Tool Mode on it, connect it to the Agent, and make the Agent use it for order totals. Then call the flow through POST /api/v1/run/FLOW_ID in two sessions to see what a session does.

Requirements

  • The component has the display name Order Total, one input named amounts with tool_mode=True, and one output whose method returns a Message.
  • For 19.99, 5.50, 42.00 the returned text is exactly "Subtotal 67.49, tax 5.40, total 72.89", computed with decimal arithmetic and with the tax rounded half up to the cent.
  • Empty or non-numeric input returns an error message that tells the model how to retry. It does not raise an exception.
  • In the Playground, "What is the total for items costing 19.99, 5.50 and 42.00?" makes the Agent call Order Total, and the Playground shows the call.
  • Two API calls with session_id "shop-a" ask that question and then "Add 10.00 shipping to that total, with no tax on shipping." A third call with session_id "shop-b" asks only the follow-up.

Expected behaviour

The first reply contains 72.89. The second reply, in the same session, contains 82.89. The third reply, in a new session, cannot know what "that total" refers to, so the agent asks for the total or says it does not know; it must not produce 82.89. Wording differs between models, but these numbers do not.

Hint 1

Write and test the plain Python function first, with the three-price example, and paste it into the component afterwards. decimal.Decimal avoids float rounding surprises.

Hint 2

Select a component and choose Code to see its class, or use New Custom Component. The Output must name the method that produces it, and that method should return a Message.

Hint 3

A tool is only as usable as its description. Say when to use the tool in the component's description, and show an example price list in the input's info text.

Hint 4

If the agent answers without calling the tool, check that Tool Mode is on, that the Toolset port is connected to the Agent's Tools port, and that the model supports tool calling.

Show solution

The component. The arithmetic lives in a plain function so that you can test it outside Langflow. The component imports follow those of Langflow's own Text Input component and the custom components page, but the class itself was not run here, because it needs a Langflow install.

python
from decimal import ROUND_HALF_UP, Decimal, InvalidOperation

from lfx.custom.custom_component.component import Component
from lfx.io import MessageTextInput, Output
from lfx.schema.message import Message

TAX_RATE = Decimal("0.08")
CENT = Decimal("0.01")
EXAMPLE = "19.99, 5.50, 42.00"


def order_total(amounts_text):
    """Sum comma-separated prices, add 8% tax rounded half up, and describe the result."""
    try:
        amounts = [Decimal(part.strip()) for part in amounts_text.split(",") if part.strip()]
        if amounts and all(amount.is_finite() for amount in amounts):
            subtotal = sum(amounts).quantize(CENT, rounding=ROUND_HALF_UP)
            tax = (subtotal * TAX_RATE).quantize(CENT, rounding=ROUND_HALF_UP)
            return f"Subtotal {subtotal:.2f}, tax {tax:.2f}, total {subtotal + tax:.2f}"
    except InvalidOperation:
        pass  # fall through to the retry message below instead of raising into the agent
    return f"Error: send prices as numbers separated by commas, for example {EXAMPLE}."


class OrderTotalComponent(Component):
    display_name = "Order Total"
    description = "Adds up comma-separated prices and applies 8% sales tax. Use it for any order total."
    icon = "calculator"
    name = "OrderTotal"

    inputs = [
        MessageTextInput(
            name="amounts",
            display_name="Prices",
            info="Comma-separated prices, for example 19.99, 5.50, 42.00",
            tool_mode=True,
        ),
    ]
    outputs = [Output(display_name="Total", name="total", method="build_total")]

    def build_total(self) -> Message:
        text = getattr(self.amounts, "text", self.amounts)
        return Message(text=order_total(str(text)))

Running order_total("19.99, 5.50, 42.00") in plain Python prints Subtotal 67.49, tax 5.40, total 72.89, and order_total("abc") returns the error text instead of raising. The sum is 19.99 + 5.50 + 42.00 = 67.49, the tax is 67.49 * 0.08 = 5.3992, which rounds to 5.40, and the total is 67.49 + 5.40 = 72.89.

Wiring. Paste the code into a New Custom Component, enable Tool Mode in its header menu, and connect its Toolset port to the Agent's Tools port. In the Playground the tool call should appear when you ask the question.

The API calls. Use the client from the worked example, or curl with the same body each time:

bash
curl -X POST "http://127.0.0.1:7860/api/v1/run/$FLOW_ID" \
  -H "Content-Type: application/json" -H "x-api-key: $LANGFLOW_API_KEY" \
  -d '{"input_value": "Add 10.00 shipping to that total, with no tax on shipping.", "input_type": "chat", "output_type": "chat", "session_id": "shop-a"}'

Send the price question with shop-a first. The follow-up in shop-a should mention 82.89, because 72.89 + 10.00 = 82.89. The same follow-up in shop-b has no history to refer to. The memory belongs to the session, so a missing session_id would have put all three calls into one shared conversation.

Exercise 2

Write a retrying Langflow client and test it against a fake server

CodingIntermediateAbout 45 min (estimate)Hypothetical scenario

Callers of a Langflow flow should survive a short outage and should not retry errors that retrying cannot fix. Write langflow_client.py using only the Python standard library, plus a unittest file that tests it against a fake server that you start on 127.0.0.1 in a thread. No Langflow install or API key is needed.

The documentation shows the chat reply at different places in the run response. Your code must accept all three of these component outputs, found at result["outputs"][0]["outputs"][0]:

json
{"outputs": {"message": {"message": "hi"}}}
{"results": {"message": {"text": "hi"}}}
{"results": {"message": {"data": {"text": "hi"}}}}

Requirements

  • extract_reply(result) returns the text from any of the three shapes and raises KeyError when none matches.
  • run_flow(base_url, flow_id, api_key, question, session_id, sleep=time.sleep) POSTs to /api/v1/run/FLOW_ID with an x-api-key header and a body that includes input_value and session_id.
  • Responses with status 500, 502, 503 or 504, and connection errors, are retried, with at most 3 attempts in total and a wait of 1 second and then 2 seconds between attempts.
  • Other error statuses, such as 403 or 422, are raised at once without a retry.
  • The tests cover all three shapes, the unknown shape, a 503 followed by success, a 403 that is not retried, and a persistent 503 that stops after 3 attempts. The tests inject sleep so they do not wait.

Expected behaviour

All five tests pass. The fake server sees 3 requests for the 503, 503, 200 sequence, 1 request for the 403, and 3 requests for the persistent 503. The recorded waits for the first sequence are exactly 1 and 2 seconds.

Hint 1

urllib.error.HTTPError is a subclass of urllib.error.URLError, so catch HTTPError first or the status check never runs.

Hint 2

Passing sleep as an argument lets a test record the waits with a list's append method instead of waiting.

Hint 3

Start the fake server with HTTPServer(("127.0.0.1", 0), Handler) so the operating system picks a free port, and close it with shutdown() and server_close() after each test.

Show solution

The client keeps the retry rule in one loop. A retryable failure falls through to the sleep at the bottom, and everything else is re-raised.

python
import json
import time
import urllib.error
import urllib.request

MAX_ATTEMPTS = 3
RETRYABLE_STATUS = {500, 502, 503, 504}
MESSAGE_PATHS = (
    ("outputs", "message", "message"),
    ("results", "message", "text"),
    ("results", "message", "data", "text"),
)


def extract_reply(result):
    output = result["outputs"][0]["outputs"][0]
    for path in MESSAGE_PATHS:
        node = output
        for key in path:
            if not isinstance(node, dict) or key not in node:
                break
            node = node[key]
        else:
            return node
    raise KeyError("no chat message at any known path")


def run_flow(base_url, flow_id, api_key, question, session_id, sleep=time.sleep):
    payload = {"input_value": question, "input_type": "chat",
               "output_type": "chat", "session_id": session_id}
    request = urllib.request.Request(
        f"{base_url.rstrip('/')}/api/v1/run/{flow_id}",
        data=json.dumps(payload).encode("utf-8"),
        method="POST",
        headers={"Content-Type": "application/json", "x-api-key": api_key},
    )
    for attempt in range(1, MAX_ATTEMPTS + 1):
        try:
            with urllib.request.urlopen(request, timeout=30) as response:
                return json.load(response)
        except urllib.error.HTTPError as error:  # before URLError, its parent class
            if error.code not in RETRYABLE_STATUS or attempt == MAX_ATTEMPTS:
                raise
        except urllib.error.URLError:
            if attempt == MAX_ATTEMPTS:
                raise
        sleep(2 ** (attempt - 1))  # 1 second, then 2

The tests start a fake server that answers with a scripted list of status codes and records the session ID of every request. Save as test_client.py and run python3 test_client.py:

python
import contextlib
import json
import threading
import unittest
import urllib.error
from http.server import BaseHTTPRequestHandler, HTTPServer

from langflow_client import extract_reply, run_flow

GOOD = {"outputs": [{"inputs": {}, "outputs": [{"results": {"message": {"text": "hello"}}}]}]}


@contextlib.contextmanager
def fake_langflow(statuses):
    calls = []

    class Handler(BaseHTTPRequestHandler):
        def do_POST(self):
            body = json.loads(self.rfile.read(int(self.headers["Content-Length"])))
            calls.append(body["session_id"])
            status = statuses[min(len(calls), len(statuses)) - 1]
            self.send_response(status)
            self.end_headers()
            self.wfile.write(json.dumps(GOOD if status == 200 else {"detail": "error"}).encode())

        def log_message(self, *args):
            pass

    server = HTTPServer(("127.0.0.1", 0), Handler)
    threading.Thread(target=server.serve_forever, daemon=True).start()
    try:
        yield f"http://127.0.0.1:{server.server_address[1]}", calls
    finally:
        server.shutdown()
        server.server_close()


class ClientTests(unittest.TestCase):
    def test_extracts_each_documented_shape(self):
        shapes = [{"outputs": {"message": {"message": "a"}}},
                  {"results": {"message": {"text": "a"}}},
                  {"results": {"message": {"data": {"text": "a"}}}}]
        for component in shapes:
            self.assertEqual(extract_reply({"outputs": [{"outputs": [component]}]}), "a")

    def test_unknown_shape_raises(self):
        with self.assertRaises(KeyError):
            extract_reply({"outputs": [{"outputs": [{"results": {}}]}]})

    def test_retries_503_then_succeeds(self):
        sleeps = []
        with fake_langflow([503, 503, 200]) as (url, calls):
            result = run_flow(url, "flow-1", "key", "hi", "user-42", sleep=sleeps.append)
        self.assertEqual(extract_reply(result), "hello")
        self.assertEqual(calls, ["user-42"] * 3)
        self.assertEqual(sleeps, [1, 2])

    def test_does_not_retry_403(self):
        with fake_langflow([403]) as (url, calls):
            with self.assertRaises(urllib.error.HTTPError) as caught:
                run_flow(url, "flow-1", "bad", "hi", "user-42", sleep=lambda s: None)
        self.assertEqual(caught.exception.code, 403)
        self.assertEqual(len(calls), 1)

    def test_gives_up_after_three_attempts(self):
        with fake_langflow([503]) as (url, calls):
            with self.assertRaises(urllib.error.HTTPError):
                run_flow(url, "flow-1", "key", "hi", "user-42", sleep=lambda s: None)
        self.assertEqual(len(calls), 3)


if __name__ == "__main__":
    unittest.main(verbosity=2)
